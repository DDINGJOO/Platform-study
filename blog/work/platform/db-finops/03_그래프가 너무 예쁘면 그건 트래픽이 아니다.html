DB 읽기 전용 인스턴스의 92일치 지표를 뽑다가 손이 멈췄어요.

reader Queries p10 6.86 p50 6.97 p95 7.25 p99 7.34 reader SelectThroughput p10 2.91 p50 2.94 p95 3.01 p99 3.05 reader CPUUtilization p10 12.94 p50 13.55 p95 14.18 p99 14.32

p10과 p99의 차이가 SELECT 0.14/초입니다. CPU는 1.4%p 폭 안에서만 움직여요.

처음 든 생각은 "부하가 굉장히 안정적이네"였습니다. 그런데 그게 아니었어요. 사람이 쓰는 서비스는 이런 그래프가 나올 수 없습니다.

1. 안정적인 게 아니라 이상한 것이다

새벽 4시와 오전 10시의 트래픽이 같을 수가 없어요. 사람은 자고, 출근하고, 점심을 먹습니다. 그래서 사용자 트래픽 그래프는 반드시 하루 주기로 출렁입니다.

업무시간과 야간을 갈라봤습니다.

reader 업무 09-18 7.09 / 야간 18-09 6.94 → 차이 2.2%

차이가 2.2%입니다. 낮과 밤이 사실상 같습니다.

여기서 판단이 뒤집혔어요. 이 부하는 사람이 만든 게 아닙니다. 심장박동처럼 일정한 무언가가 기계적으로 쿼리를 보내고 있는 거죠.

그림 1. 하루 주기가 없다는 것이 단서였다

2. 범인은 커넥션 풀의 검증 쿼리였다

커넥션 풀은 빌려준 커넥션이 아직 살아 있는지 확인합니다. DB가 유휴 커넥션을 조용히 끊거나 네트워크 장비가 세션을 정리해버릴 수 있으니까요.

그래서 주기적으로, 그리고 커넥션을 꺼내줄 때 아주 가벼운 쿼리를 보냅니다. 이게 사용자 요청과 무관하게 일정한 간격으로 돕니다.

애플리케이션 요청 없어도 풀이 유휴 커넥션을 주기적으로 점검 → 일정 간격 쿼리 풀 크기가 고정이면 그 빈도도 고정 → 낮과 밤이 같다

여기에 이 시스템의 사정이 겹쳤어요. 접속 URL이 쓰기·읽기 두 엔드포인트를 모두 참조하고 있었고, 드라이버가 양쪽에 커넥션 풀을 유지하면서 실제 쿼리는 전부 쓰기 쪽으로 보내고 있었습니다. 읽기 쪽으로 간 건 검증 쿼리뿐이었죠.

그러니까 저 예쁜 그래프는 애플리케이션 트래픽이 아니라 인프라 자체가 내는 상시 오버헤드였습니다. 92일 내내 쓰기가 정확히 0이었던 것도 같은 이유고요.

💡 상시 오버헤드는 읽기 전용 노드에서 특히 잘 보인다
쓰기 노드에서는 이 부하가 실제 트래픽에 묻혀서 안 보입니다. 실측으로 쓰기 노드도 업무시간에 3.7%만 올랐는데, 그건 애플리케이션 부하가 상시 오버헤드에 묻히는 수준이었다는 뜻이에요.

트래픽이 거의 없는 노드가 오히려 인프라가 스스로 내는 소리를 들려주는 관측 지점이 됩니다.

3. 가설을 어떻게 확인했나

"검증 쿼리다"는 아직 가설이에요. 그래프 모양만으로는 부족합니다. 그래서 서로 독립된 증거를 찾았습니다.

① 쓰기가 92일 내내 정확히 0 사용자 트래픽이면 읽기 전용 노드라도 0 이 나오기 어렵다 검증 쿼리는 SELECT 하나뿐이므로 0 이 자연스럽다 ② 접속 URL 이 두 엔드포인트를 모두 참조한다 드라이버가 양쪽에 풀을 유지하는 구조 → 검증 쿼리만 흘러가는 경로가 설명된다 ③ 분포 폭이 SELECT 0.14/초 기계적 신호의 특징

여기서 중요한 건 ①과 ②가 서로에게 의존하지 않는다는 점입니다. 하나가 틀려도 다른 하나가 남아요. ③은 ①·②와 같은 현상을 다르게 표현한 것이라 독립 증거가 아니고, 그래서 근거를 셋으로 세고 있었지만 실은 둘이었습니다.

그림 2. 근거를 셀 때는 서로 독립인지 따져야 한다

그리고 사실 산수로 확정할 수 있었습니다. 검증 쿼리는 규칙적이니 빈도를 계산할 수 있어요.

상시 QPS ≈ 유지하는 커넥션 수 ÷ 검증 주기(초) 관측값 SELECT 2.94/초 를 이 식에 넣으면 커넥션 30개 / 10초 주기 → 3.0/초 거의 일치 커넥션 10개 / 10초 주기 → 1.0/초 안 맞는다

풀 설정을 열어서 이 식과 맞춰보면 "검증 쿼리다"가 추론에서 계산으로 바뀝니다. 관측값이 설정에서 나오는 값과 맞으면 가설이 확정되고, 안 맞으면 다른 게 섞여 있다는 뜻이니 그것도 정보예요.

저는 이걸 안 하고 넘어갔습니다. 결론이 맞았으니 문제는 없었지만, 근거가 "모양이 이상하다"에서 멈춘 것과 "설정에서 나온 숫자와 일치한다"까지 간 것은 다릅니다. 다음엔 여기부터 하려고 합니다.

4. 그래서 무엇을 다르게 읽나

모니터링 그래프를 볼 때 이걸 먼저 봅니다.

1. 하루 주기로 출렁이는가 아니오 → 사람이 만든 부하가 아닐 가능성 2. 분위수 폭이 비정상적으로 좁은가 p10~p99 가 소수점 두 자리 안 → 기계적 신호 3. 업무시간 / 야간 비율이 1에 가까운가 가깝다 → 사용자와 무관한 부하

셋 다 "안정적이다"로 읽히기 쉬운 특징인데, 실은 "이 노드는 일을 안 하고 있다"는 신호입니다. 그리고 안 하고 있다면 왜 돈을 내고 있는지 물어봐야 하죠.

거꾸로도 성립합니다. 진짜 트래픽이 흐르는 노드의 그래프가 갑자기 평평해지면 그건 안정이 아니라 트래픽이 안 오고 있다는 뜻일 수 있어요. 라우팅이 끊겼거나, 앞단의 캐시가 요청을 다 처리하고 있는 경우입니다.

⚠️ 다만 집계 해상도를 먼저 확인할 것
평평한 그래프의 원인이 하나 더 있습니다. 긴 구간을 조회하면 모니터링 도구가 자동으로 굵은 해상도를 씁니다. 1시간 평균을 내면 튀는 값이 평균에 흡수돼서 원래 평평해져요.

저도 92일을 한 번에 조회해서 일부 구간이 1시간 평균이었습니다. 그래서 "분포가 평평하다"는 근거가 생각보다 약했어요. 결론은 다른 증거 두 개(쓰기 0, 접속 URL 구조)가 받쳐줘서 버텼지만, 근거를 셋으로 세고 있었는데 실은 둘이었습니다.

평평함을 근거로 쓰려면 짧은 구간을 세밀한 해상도로 다시 뽑아야 합니다.
✍️ 오늘의 요약
그래프가 자로 잰 것처럼 평평하면 "부하가 안정적이다"가 아니라 "이건 사람이 만든 부하가 아니다"로 읽습니다. 하루 주기가 없다는 건 사용자가 없다는 뜻이니까요.

범인은 커넥션 풀의 검증 쿼리였습니다. 애플리케이션과 무관하게 일정 간격으로 도는 인프라 자체의 상시 오버헤드였어요. 트래픽이 거의 없는 노드가 오히려 그 소리를 들려줍니다. 다만 평평함을 근거로 쓰기 전에 집계 해상도를 확인해야 합니다. 평균이 만든 평평함과 부하가 만든 평평함은 그래프에서 똑같이 생겼습니다.
