state 버킷의 기본 암호화를 바꿨어요. AWS 가 알아서 관리해 주는 키에서, 우리가 만들고 우리가 정책을 붙인 키로. 키를 만들고, 키 정책을 쓰고, 파이프라인 역할 네 개에 복호화 권한을 주고, 버킷의 기본 암호화 설정을 바꿨습니다. plan 초록, apply 성공, 커밋 하나, ADR 하나.

그런 다음 새로 올라간 state 객체의 속성을 열어봤어요. 암호화 방식이 그대로였습니다. 옛날 방식 그대로요.

실패한 게 아니에요. 에러도 없고, 경고도 없고, plan 에 빨간 줄 하나 없었어요. 콘솔의 버킷 속성 화면도 새 키를 정확히 가리키고 있었고요. 설정은 전부 옳았고 apply 도 성공했는데, 효과만 0이었습니다. 오늘 글은 "설정했다"와 "적용됐다"가 다른 말인 경우에 대한 이야기예요.

1. state 는 왜 시크릿인가 — 전제부터

첫날 글에 이런 규칙을 적었어요. "시크릿을 Terraform 으로 만들지 않는다. 콘솔에서 만들고 코드에는 ARN 만 참조한다." 시크릿 값이 코드에도 state 에도 들어오지 않게 하는 흔한 방어선이고, 저도 그걸 지키고 있다고 믿었습니다.

그런데 그 규칙을 지켜도 state 는 시크릿을 담아요. 내가 직접 넣지 않아도 담깁니다. 경로가 여러 개예요.

데이터 소스로 읽은 값이 그대로 기록됩니다. 파라미터 스토어의 값을 data 로 읽으면, 그 값은 읽힌 순간 state 안에 평문으로 앉아요. 리소스가 반환한 속성도 마찬가지고요 — 생성된 초기 비밀번호, 발급된 인증서, 조립된 연결 문자열. 그리고 프로바이더가 자기 편의로 state 에 적어두는 필드들도 있습니다. sensitive = true 는 화면 출력만 가리지, state 파일 안에는 평문 그대로예요. 가려지는 건 사람의 눈이지 파일이 아닙니다.

우리 경우엔 아주 구체적인 방아쇠가 있었어요. 알럿을 외부 모니터링 서비스로 보내는 구독을 만들어야 하는데, 그 엔드포인트가 URL 안에 API 키를 끼워 넣는 형식이에요. 값이 리터럴이어야 하니까 "참조만 두고 값은 안 넣는" 패턴 자체가 성립하지 않습니다. 이걸 코드로 들이는 순간 state 에 키가 들어옵니다. 그래서 전제를 바꿨어요 — state 에 시크릿이 들어올 수 있다고 인정하고, 대신 state 자체를 시크릿처럼 다룬다.

이건 9편의 짝이다

9편에서 저는 plan 역할의 state 읽기 권한을 버킷 전체로 넓혔어요. 스택이 하나 늘 때마다 파일 이름으로 못 박은 경계가 깨졌고, 그걸 고치려면 매번 사람이 로컬에서 bootstrap 을 apply 해야 했거든요. 넓히는 게 옳은 판단이었다고 지금도 생각하는데, 그 판단에는 값이 따라옵니다.

AWS 관리형 키로 암호화된 객체는 s3:GetObject 하나만 있으면 복호화가 자동으로 됩니다. 복호화라는 별도의 관문이 없어요. 즉 읽기를 넓힌 만큼 방어가 그대로 얇아집니다. 여기에 시크릿이 들어오면 plan 역할이 곧 전 환경 시크릿 열람 권한이 되는 거예요.

우리 키를 쓰면 관문이 하나 더 생겨요. S3 권한을 통과해도 키 정책을 통과하지 못하면 못 읽습니다. 이 두 번째 관문은 S3 권한과 독립적으로 감사할 수 있고, 독립적으로 회수할 수 있어요. 9편에서 넓힌 권한을 여기서 일부 되받는 셈입니다.

AWS 관리형 키 (SSE-S3) 복호화 조건 : s3:GetObject ← 관문 1개 회수 방법 : IAM 정책만 우리 키 (CMK) 복호화 조건 : s3:GetObject AND kms:Decrypt (키 정책 통과) ← 관문 2개 회수 방법 : IAM 정책, 또는 키 정책에서 역할 하나만 빼기

2. 또 하나의 닭과 달걀 — 왜 두 단계로 쪼갰나

첫날에도 닭과 달걀을 하나 풀었어요. 그건 이런 모양이었습니다. Terraform 으로 state 버킷을 만들고 싶은데, Terraform 이 돌려면 state 를 둘 버킷이 이미 있어야 한다. 해법은 순환 밖에 사람을 한 번 세우는 거였어요 — bootstrap/ 디렉터리만 사람이 로컬 state 로 1회 apply 하고, 그 다음부터 원격 버킷을 쓴다. 한 번의 예외로 고리를 끊었습니다.

이번 건 비슷하게 생겼는데 종류가 다릅니다. 키를 만드는 코드가 bootstrap/ 에 있어요. 그런데 bootstrap/ 의 backend 가 아직 존재하지 않는 키를 가리키면 init 자체가 실패합니다. init 이 실패하면 apply 를 못 하고, apply 를 못 하면 키가 안 생기고, 키가 없으니 backend 는 계속 없는 걸 가리켜요. 게다가 이건 bootstrap 하나로 끝나지 않습니다 — 모든 스택이 같은 버킷을 쓰니까, backend 를 먼저 바꾸면 저장소의 CI 체크가 전부 한 번에 막혀요.

여기선 사람을 한 명 세워도 소용이 없어요. 자원이 없어서 생긴 고리가 아니라, 선언과 생성이 같은 코드 안에 있어서 생긴 고리거든요. 그래서 이번엔 사람이 아니라 시간으로 끊었습니다. 같은 변경을 두 개의 PR 로 쪼개서, 순서를 만들었어요.

1단계 (PR 하나) 키 생성 + 별칭 키 정책 : 루트 + 파이프라인 역할 4개만 IAM : plan·apply 역할에 kms:Decrypt / GenerateDataKey / DescribeKey 버킷 기본 암호화를 우리 키로 변경 ※ backend 는 손대지 않는다 2단계 (1단계 apply 이후, 별도 PR) backend 블록 4곳에 kms_key_id 추가
⚠️ 1단계에서 같이 안 넣으면 전부 죽는 것
• IAM 에 kms 권한을 같이 주지 않으면 plan · apply · drift 가 한 번에 전부 AccessDenied 로 죽는다. 키 정책과 IAM 양쪽에 넣어야 한다 — 한쪽만으론 안 된다
• 나중에 역할이 하나 늘면 키 정책에도 추가해야 한다. 잊으면 그 역할의 state 접근이 통째로 막힌다
• 로컬에 .terraform/ 캐시가 있으면 2단계에서 재구성 프롬프트가 뜬다. init -reconfigure 로 넘긴다 (CI 는 매번 새 체크아웃이라 해당 없음)
그림 1. 자원이 없어서 생긴 고리는 사람이 끊고, 선언과 생성이 붙어서 생긴 고리는 순서가 끊는다

3. 1단계를 끝냈는데 아무것도 안 바뀐 이유

여기가 오늘의 반전이에요. 1단계를 apply 한 뒤, 새로 쓰인 state 객체는 여전히 옛 방식으로 암호화돼 있었습니다. 원인은 "기본값"이라는 단어를 제가 너무 넓게 읽은 것이었어요.

S3 의 버킷 기본 암호화는 이름 그대로 기본값입니다. 정확히는 요청이 암호화 방식을 지정하지 않았을 때 대신 채워 넣는 값이에요. 버킷에 올라오는 모든 객체를 강제로 그 방식으로 바꾸는 규칙이 아닙니다.

그런데 Terraform 의 S3 backend 에는 encrypt = true 라는 설정이 있어요. 이건 "암호화해서 저장해 줘"가 아니라 "이 방식으로 암호화해서 저장해 줘"라고 헤더를 실어 보내는 동작입니다. 즉 backend 는 매 업로드마다 암호화 방식을 명시하고 있었어요. 그리고 명시된 요청은 버킷 기본값을 덮어씁니다.

그래서 버킷 기본값을 우리 키로 바꿔도 아무 일이 안 일어난 거예요. 요청이 계속 옛 방식을 지정해서 오고 있으니까, S3 는 시키는 대로 옛 방식으로 저장합니다. 기본값은 쓰일 자리가 없었어요.

이게 관측하기 어려운 이유

이 상황에서 거짓말을 하는 화면이 하나도 없습니다. plan 은 바뀐 리소스를 정확히 보여줬고, apply 는 성공했고, 버킷 속성 조회는 "우리 키"라고 정직하게 답해요. 전부 사실이에요. 다만 그 사실들 중 어느 것도 "그래서 객체가 그 키로 저장되고 있다"를 뜻하지 않을 뿐입니다.

실패가 아니기 때문에 아무도 알려주지 않아요. 에러는 누군가 나에게 와서 말을 걸지만, 효과 없음은 가만히 있습니다. 확인하려면 설정이 아니라 산출물을 — 실제로 저장된 객체의 암호화 속성을 — 직접 열어봐야 해요.

# 버킷 설정 — 바뀌었다 aws s3api get-bucket-encryption --bucket {state 버킷} "SSEAlgorithm": "aws:kms" ✅ 우리 키 # 그 뒤에 새로 쓰인 state 객체 — 안 바뀌었다 aws s3api head-object --bucket {state 버킷} \ --key env/prod/terraform.tfstate "ServerSideEncryption": "AES256" ❌ 옛 방식 그대로

2단계에서 backend 에 키를 명시하고 나서야 비로소 동작했어요. 결국 덮어쓰는 쪽을 고쳐야 했던 것이지, 덮어씌워지는 쪽을 아무리 잘 고쳐도 소용이 없었던 겁니다.

그림 2. 고쳐야 했던 건 덮어씌워지는 쪽이 아니라 덮어쓰는 쪽이었다

4. 왜 하필 지금 하나 — 소급이 안 되니까

이 작업은 급하지 않아 보였어요. 아직 state 에 시크릿이 하나도 없었거든요. 그런데도 다른 일을 미루고 이걸 먼저 한 이유가 있습니다.

state 버킷에는 버저닝이 켜져 있어요. 실수로 state 를 날려도 이전 버전으로 되돌리기 위해서죠. 좋은 설정인데, 여기에 딸려오는 성질이 하나 있습니다. 이미 저장된 버전은 영원히 그때의 암호화 방식으로 남습니다. 나중에 버킷 설정을 바꿔도, backend 를 고쳐도, 과거 버전은 안 바뀌어요. S3 는 기존 객체를 알아서 재암호화해 주지 않으니까요.

그러니 순서가 이렇게 됩니다. 만약 시크릿이 들어간 다음에 암호화를 바꾸면, 시크릿이 담긴 그 버전은 옛 방식으로 박제돼요. 그리고 그 버전은 s3:GetObject 하나만으로 읽힙니다 — 9편에서 넓힌 그 권한으로요. 새 버전은 잘 보호되는데 정작 문제의 버전은 무방비인, 제일 안 좋은 상태가 됩니다.

그래서 순서를 못 박았어요. 1단계(키) → 2단계(backend) → 그 다음에야 시크릿을 담는 리소스를 코드로 들인다. 이 순서를 뒤집으면 되돌릴 방법이 없습니다.

⏳ 두 종류의 "나중에"
• 나중에 해도 되는 일 — 지금 하든 다음 달에 하든 결과가 같다. 태그 정리, 모듈 리팩터링, 문서 보강
• 지금 아니면 소급이 안 되는 일 — 데이터가 쌓이기 시작한 뒤에 켜면 과거분은 영영 그대로다. 버저닝 · 감사 로그 · 암호화 · 보존 정책
• 두 번째 목록은 우선순위 목록이 아니라 순서 목록이다. 중요도로 미룰 수 있는 게 아니다

5. 왜 키 ID 가 아니라 별칭을 쓰나

2단계에서 backend 에 넣은 값은 키의 ID 가 아니라 별칭이에요. 별칭은 키에 붙이는 사람이 읽을 수 있는 이름이고, 다른 키로 옮겨 붙일 수 있습니다.

backend "s3" { bucket = "{state 버킷}" key = "env/prod/terraform.tfstate" region = "{리전}" encrypt = true # 별칭 ARN 이라 키를 재생성해도 이 값은 안 바뀐다. # 대신 이 별칭이 사라지면 모든 스택의 init 이 깨진다. kms_key_id = "arn:aws:kms:{리전}:{계정ID}:alias/{state 키 별칭}" use_lockfile = true }

이유는 변경의 파급을 한 곳에 가두기 위해서예요. 키 ID 를 직접 적으면, 언젠가 키를 교체할 때 backend 블록 네 곳을 전부 고치고 모든 스택을 재구성해야 합니다. 그건 그날 하루를 통째로 잡아먹는 작업이고, 하나를 빠뜨리면 그 스택만 조용히 다른 키를 쓰게 돼요. 별칭을 쓰면 키를 갈아끼워도 코드에 적힌 문자열은 한 글자도 안 바뀝니다.

그런데 같은 성질이 반대편에서는 이렇게 읽혀요. 이 별칭 하나가 사라지면 모든 스택의 init 이 동시에 깨집니다. 의존 지점을 하나로 모았다는 건, 그 하나가 단일 실패 지점이 됐다는 뜻이기도 하니까요. 넷을 고칠 일이 없어진 대신, 하나가 무너지면 넷이 같이 무너집니다.

그리고 더 무거운 게 하나 더 있어요. 키 삭제는 되돌릴 수 없습니다. 삭제 유예를 최대치인 30일로 뒀지만, 그 기간이 지나 키가 사라지면 그 키로 암호화된 state 는 영구히 못 읽어요. 백업도 소용없습니다 — 백업본도 같은 키로 암호화돼 있으니까요. "bootstrap 에서는 terraform destroy 를 절대 실행하지 않는다"는 규칙이 어제까지는 "버킷과 역할을 잃는다"였는데, 오늘부터는 "state 를 영구히 잃는다"가 됐습니다. 같은 규칙인데 무게가 달라졌어요.

6. 설정했다와 적용됐다는 다른 말이다

오늘 배운 걸 두 문장으로 남겨둡니다.

첫째, "설정했다"와 "적용됐다"는 다릅니다. 특히 기본값을 바꾸는 설정이 그래요. 기본값은 아무도 지정하지 않았을 때만 쓰이니까, 그 값을 덮어쓰는 명시가 어딘가에 하나라도 있으면 아무 일도 하지 않습니다. 그리고 이건 실패가 아니라서 아무도 알림을 보내주지 않아요.

이 함정은 암호화만의 것이 아니에요. 기본 태그, 기본 보존 기간, 기본 리소스 요청량, 기본 타임아웃 — 전부 같은 구조입니다. 어딘가의 명시가 조용히 이기고 있고, 대시보드는 기본값을 보여주면서 사실을 말하고 있죠. 그래서 규칙 하나를 만들었어요. 기본값을 바꿨으면 설정 화면이 아니라 실제 산출물을 열어서 확인한다. 객체 하나를 골라 속성을 찍어보는 데 30초면 되고, 그 30초가 "다 해놨다"는 착각을 몇 달간 방지합니다.

둘째, 소급이 안 되는 결정은 순서가 곧 설계입니다. 대부분의 기술 결정은 나중에 다시 할 수 있어요. 잘못 고르면 고치면 되고, 고치는 비용은 대개 계산 가능합니다. 그런데 일부는 그렇지 않아요. 버저닝, 감사 로그, 암호화 — 이것들은 켜는 순간부터 앞으로만 적용되고 과거는 손댈 수 없습니다.

이런 항목에는 "중요하지만 급하지 않다"는 칸이 없어요. 데이터가 쌓이기 시작하는 그 시점이 마감이고, 그 마감은 알림을 주지 않은 채 조용히 지나갑니다. 그러니 새 시스템을 세울 때 물어야 할 질문은 "이걸 언제 할까"가 아니라 "이걸 나중에 해도 같은 결과가 나오나"예요. 답이 아니오면, 그건 지금 할 일입니다.

✍️ 오늘의 요약
state 버킷의 기본 암호화를 우리 키로 바꾸고 apply 까지 성공했는데, 새로 올라간 객체는 여전히 옛 방식이었다. backend 의 encrypt = true 가 매 업로드마다 암호화 방식을 명시해서 보내고, 명시된 요청은 버킷 기본값을 덮어쓰기 때문이다. 실패가 아니라서 에러도 경고도 없었고, 확인하려면 설정이 아니라 저장된 객체를 직접 열어봐야 했다.

두 단계로 쪼갠 건 또 다른 닭과 달걀 때문이었다. 키를 만드는 코드가 bootstrap 인데, backend 가 아직 없는 키를 가리키면 init 부터 죽는다. 첫날의 고리는 사람이 한 번 끊었지만, 이번 고리는 순서로 끊었다. 그리고 버저닝이 켜진 이상 과거 버전은 영원히 옛 방식이라, state 에 시크릿이 들어오기 전인 지금이 유일한 시점이었다.

기본값을 바꾸는 설정은 그 기본값을 덮는 명시가 있으면 아무 일도 하지 않는다. 그러니 설정을 바꿨으면 설정 화면이 아니라 산출물을 열어라. 그리고 소급이 안 되는 일에는 우선순위가 아니라 순서를 매겨라.
