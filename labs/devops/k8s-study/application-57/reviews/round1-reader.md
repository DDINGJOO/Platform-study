## R1. 임시 요청 파드를 만들기 전에 exec부터 실행한다

- 위치: 4절 첫 코드블록, HTML 131행.
- 원문: `kubectl -n app-capstone exec request-client -- ...`
- 근거: 1절이 적용하는 `application-v1.json`에는 Namespace·ConfigMap·Deployment·Service만 있고 `request-client` Pod는 없다. 별도 `client.json`에 Pod가 정의되어 있지만 본문에 생성·준비 대기 명령이나 해당 파일 링크가 없다. 본문 순서로 따라오는 독자는 `pods "request-client" not found`에서 중단된다. 마지막 재현 자료 링크만으로는 이 선행 조건을 알기 어렵다.
- 수정안: 4절 코드블록 앞에 `client.json` 링크와 아래 두 명령을 추가한다.

```bash
kubectl apply -f labs/devops/k8s-study/application-57/client.json
kubectl -n app-capstone wait --for=condition=Ready pod/request-client --timeout=120s
```

  이 파일은 `nodeSelector.kubernetes.io/hostname: k8s-worker2`로 고정되어 있다. 다른 환경에서는 앱과 다른 노드의 실제 hostname으로 바꾸고 `get pods -o wide`로 배치를 확인한다는 한 문장을 붙이면, 이후의 노드 간 요청 관찰도 재현할 수 있다.

## R2. NodePort 설명이 첫 화면·접속 명령보다 뒤에 있다

- 위치: 1절 실행 화면 1 캡션(42행)·외부 curl(53행), 용어박스는 4절에 있다.
- 원문: “실행 화면 1. NodePort로 접속한 실제 앱이에요.”
- 근거: 처음 읽는 독자는 Service와 노드 포트의 관계를 모른 채 먼저 캡처와 `192.168.64.3:30057`을 보게 된다. 1절의 IP 안내는 접근 가능한 주소라는 점을 설명하지만, 왜 30057로 접근하는지는 4절까지 기다려야 한다. 쉬운 설명 가이드는 생소한 용어의 첫 등장 위치에 짧은 정의를 요구한다.
- 수정안: 4절의 기존 NodePort 용어박스를 1절 첫 캡처 직전으로 옮긴다. “노드의 지정된 포트로 Service를 노출하는 방식이며, 이번에는 30057→Service 80→앱 8080으로 연결한다”로 쓰면 초기 접속 명령과 바로 연결된다. 새 용어박스를 추가할 필요는 없다.

## R3. UID가 첫 등장한 뒤 네 절 뒤에 정의된다

- 위치: 2절 마지막 문단(91행), 정의는 6절(181행).
- 원문: “하나의 파드 이름과 UID로 연결할 수 있어요.”
- 근거: UID가 파드 이름·PID·IP와 어떤 관계인지 아직 설명되지 않았다. 이 문단은 여러 계층의 실행 정보를 연결하는 결론이라 객체 식별자라는 최소 정의가 그 자리에서 필요하다.
- 수정안: 첫 등장만 `UID(객체 식별자)`로 바꾼다. 파드 교체 시 새 UID가 생긴다는 6절의 용어박스는 그대로 유지한다.

## 확인한 장점

- APP_POD 자리표시자의 대입 방법, 고정된 과거 파드 이름을 현재 이름으로 바꿔야 하는 이유가 바로 설명되어 있다.
- HTTP 000과 curl 종료 코드, 준비 검사와 프로세스 실행의 차이를 구분해 준다.
- 실제 브라우저 화면과 저장 출력을 렌더링한 이미지를 캡션에서 구분한다.
- 주소가 실습 Mac에 한정된다는 점과 앱 소스·이미지·데이터 영속성의 실험 범위를 밝혀 외부 독자의 오해를 줄인다.
- rollout의 성공 표본과 파드 교체의 실패 표본이 같은 성공담으로 합쳐지지 않는다.
