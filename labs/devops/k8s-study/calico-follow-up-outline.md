# Calico 해부: k8s 스터디 51~56편 목차안

작성일: 2026-11-14. 기존 1~50편을 잇는 기획안이며, 아래 제목과 번호는 발행 전 초안이다. 새 실험의 예상 결과를 관측 사실처럼 쓰지 않는다.

## 목표와 기존 글의 연결

Pod 하나의 생성부터 같은 노드·다른 노드·클러스터 밖으로 보내는 요청, 정책 차단과 장애 진단까지 연결한다. 구성 요소 이름을 나열하는 대신 API 객체, 프로세스, 네트워크 네임스페이스, 인터페이스, 커널 경로, 실제 패킷을 대조한다.

최신 글은 이 작업 트리의 `posts/CS/DevOps/k8s-study`에 50편까지 있다. 기존에 충분히 다룬 주제는 독립된 새 글로 반복하지 않는다.

| 기존 글 | 이미 다룬 내용 | 후속 글에서 쓰는 방법 |
|---|---|---|
| 6편 | CNI 설치, 이중 NIC, IPIP 경로, 기본 정책 | 설치 과정은 연결하고 현재 구성만 재확인 |
| 28·47편 | Service DNAT, conntrack, kube-proxy 모드와 성능 | Pod 간 통신과 Service 통신을 비교할 때 연결 |
| 29편 | 네임스페이스별 Service DNS, search와 ndots | 정책 실험과 진단의 DNS 분기에서 연결 |
| 30편 | BIRD 중단, 경로 삭제, 3.33의 Felix 경로 설정 | BGP와 실제 전달 경로를 구분하는 근거로 연결 |
| 31편 | podCIDR과 Calico IPAM, 블록 추가와 주소 용량 | 할당 구조는 연결하고 화면·패킷의 실제 IP를 대조 |
| 34편 | CNI ADD/DEL, IP 반환, 노드 장애와 누수 | IP 사용량 재생 자료를 보강 후보로 사용 |
| 43편 | Pod의 네트워크 공유, pause와 샌드박스 재생성 | 네임스페이스 개념 설명은 줄이고 실제 장치 추적에 집중 |

공통 환경: Lima VM 4대, Kubernetes v1.37.2, Calico v3.33.0. 11월 14일 조회에서는 IPPool `10.244.0.0/16`, blockSize 26, IPIP Always, VXLAN Never였다. 이후 실험마다 버전·풀·데이터플레인·정책 설정을 다시 기록한다. 다른 Calico 버전이나 eBPF 모드까지 결과를 일반화하지 않는다.

## 51편. 파드의 eth0 반대편에는 무엇이 있을까, Calico의 netns와 veth 추적

독자의 질문: 파드 안에서는 eth0만 보이는데 노드에는 왜 cali 인터페이스가 생길까?

1. Pod IP 하나에서 출발해 컨테이너 PID와 네트워크 네임스페이스를 찾는다.
2. 앱 컨테이너와 샌드박스의 netns 식별자를 대조하고, hostNetwork Pod와 비교한다. Kubernetes namespace와 Linux netns도 구분한다.
3. netns 안의 eth0와 노드의 cali 장치를 ifindex·iflink·peer 정보로 짝짓는다. `@if3` 숫자가 보인다는 것만으로 연결 관계를 단정하지 않는다.
4. Pod 내부 주소·라우팅·이웃 테이블과 호스트의 `/32` 경로를 함께 읽는다. 기본 경로와 게이트웨이는 실제 출력으로 설명한다.
5. CNI 바이너리·IPAM·Felix·BIRD·커널의 역할을 생성 시점과 지속 동작으로 나눈다. 30·34·43편의 검증 결과와 이번 관측을 구분한다.

실험: 임시 Pod 두 개를 사용해 PID/netns 식별자, 양쪽 링크 정보, 주소와 경로를 수집한다. Pod 생성 전후의 장치·경로 차이를 기록하고 해당 Pod만 정리한다.

필수 자료: Pod→netns→eth0↔cali→호스트 라우팅 도식, 양쪽 실제 출력, 생성 전후 차이. `ip route get`은 경로 선택 결과이며 패킷 전달 성공 자체의 증거는 아니라는 점을 적는다.

현재 확보: worker1의 `calie620301c135@if3`, MTU 1480, link-netns, `10.244.194.74`의 호스트 경로. 반대편 netns까지의 짝 검증은 추가로 필요하다.

## 52편. 다른 노드의 파드까지 패킷은 어떻게 갈까, Calico IPIP를 tcpdump로 보기

독자의 질문: Pod IP로 보낸 패킷이 노드 네트워크를 어떻게 통과할까?

1. 같은 노드와 다른 노드의 목적지 Pod를 고정하고 같은 요청을 보낸다.
2. 출발 Pod의 eth0와 호스트 cali 장치에서 내부 출발지·목적지 IP를 확인한다.
3. 다른 노드로 가는 경로와 tunl0, 실제 송신 NIC를 대조한다.
4. 물리 NIC 캡처에서 바깥 노드 IP와 안쪽 Pod IP를 함께 읽고 IP protocol 4를 확인한다. TCP 포트 번호와 IP 프로토콜 번호를 구분한다.
5. 도착 노드의 수신·터널 해제·Pod 전달과 응답 경로를 이어 붙인다. BGP는 경로 정보 교환, IPIP는 이번 구성의 패킷 운반이라는 점을 30편과 연결한다.

실험: 작은 요청을 고유 포트·시간·연결 정보로 식별하고 양쪽 노드에서 동시에 제한된 범위로 캡처한다. 같은 노드와 다른 노드 요청을 분리한다.

필수 자료: 지점별 캡처 표, 내부/외부 헤더 도식, pcap 원본과 필터·시간·명령. tunl0나 cali 한 곳의 캡처만으로 전체 경로를 입증했다고 쓰지 않는다. offload로 인한 체크섬·크기 표시 차이도 확인한다.

현재 확보: IPIP Always와 `dev tunl0 proto 80` 경로. 실제 패킷 캡처는 아직 수행하지 않았다.

## 53편. 작은 요청은 되는데 큰 요청은 왜 멈출까, Calico MTU와 PMTUD

독자의 질문: 연결은 되는데 응답 크기나 전송 방식에 따라 멈추는 이유는 무엇일까?

1. 노드 NIC·tunl0·Pod eth0의 MTU를 나란히 읽는다.
2. IPv4 IPIP 헤더와 유효 MTU를 계산하고 ping payload·IP 패킷·프레임 크기를 구분한다.
3. DF를 설정한 크기별 요청으로 성공·실패 경계를 찾고 패킷 캡처와 대조한다.
4. ICMP fragmentation needed가 어디에서 생기고 돌아오는지 확인한다. 발신지에서 즉시 거절된 경우와 경로 중간에서 실패한 경우를 나눈다.
5. 격리한 경로에서 PMTUD 실패를 재현하고 TCP의 MSS·재전송과 연결한다. 큰 HTTP 응답 한 번의 성공만으로 MTU가 정상이라고 결론 내리지 않는다.

실험: 정상 경로를 먼저 측정한 뒤 별도 netns나 전용 실습 경로에 MTU 불일치를 만든다. 공유 노드 NIC나 운영 중인 Calico 풀을 변경하는 방식은 기본 실험에서 제외한다.

필수 자료: 크기별 결과 표, ICMP·TCP 캡처, 실제 경로 MTU와 헤더 계산. 현재 보이는 1480의 이유는 하부 경로 MTU와 캡슐화 설정을 함께 검증한다.

## 54편. NetworkPolicy를 적용했는데 왜 어떤 연결은 계속될까

독자의 질문: 정책을 만들었는데 차단 여부가 요청마다 다르게 보이는 이유는 무엇일까?

1. 정책이 없는 상태의 연결을 기준으로 기록하고 대상 Pod의 라벨을 확인한다.
2. default deny의 적용 방향과 Pod 선택 범위를 나누어 확인한다.
3. ingress와 egress를 각각 열고 여러 허용 정책의 합집합을 실험한다.
4. Pod IP 요청과 DNS 이름 요청을 나누고 DNS의 UDP/TCP 53 허용 여부를 확인한다.
5. 기존 keep-alive 연결과 새 TCP 연결을 별도로 만들어 정책 변경 전후를 비교한다. 관측 결과는 현재 Calico 데이터플레인과 설정에 한정한다.
6. 정책 객체·Felix의 적용 흔적·현재 iptables/nft 규칙이나 카운터·패킷을 대조해 어디서 막혔는지 설명한다.

실험: 전용 namespace 안의 client/server Pod와 표준 Kubernetes NetworkPolicy만으로 시작한다. 네임스페이스·Pod 선택자를 실제 라벨로 검증하고 테스트가 끝나면 실험 자원만 제거한다.

필수 자료: 허용/차단 행렬, 정책 YAML, 연결 생성 시각, 규칙·패킷 근거. 기존 연결이 유지되거나 끊기는 동작을 Kubernetes의 보편적 보장으로 쓰지 않는다. Calico 정책·전역 정책·티어는 별도 심화 후보로 둔다.

## 55편. 파드가 밖으로 나갈 때 출발지 IP는 어디서 바뀔까, Calico NAT와 conntrack

독자의 질문: 외부 서버에는 Pod IP와 노드 IP 중 무엇이 보이며 응답은 어떻게 돌아올까?

1. 일반 Pod·hostNetwork Pod·노드에서 같은 통제 가능한 외부 수신기로 요청한다.
2. 출발지의 주소·경로와 IPPool의 natOutgoing, 관련 NAT 규칙을 함께 확인한다.
3. Pod 쪽과 노드 송신 NIC, 외부 수신기에서 같은 연결을 대조해 SNAT 위치를 찾는다.
4. conntrack의 원래 방향과 응답 방향 정보를 읽고 반환 패킷이 Pod에 닿는 경로를 연결한다.
5. Calico NAT와 Lima/macOS 상위 네트워크의 NAT를 구분한다. NAT가 없을 때 필요한 반환 경로는 격리 환경에서 검증한다.

실험: 외부 수신기의 원격 주소와 양쪽 캡처를 확보한다. 공용 IP 조회 서비스 하나의 출력으로 Calico SNAT를 증명하지 않는다. natOutgoing 변경 비교는 전용 풀·별도 환경이 준비된 경우에만 수행한다.

필수 자료: 각 관측 지점의 IP/포트 표, NAT 규칙·카운터, 연결 추적 기록, 반환 경로 도식. 외부 수신기를 확보하지 못하면 제목과 결론의 범위를 노드 송신 경계까지로 줄인다.

## 56편. 파드 통신 장애는 어디부터 볼까, Calico 장애를 구간별로 좁히기

독자의 질문: 통신이 안 될 때 어떤 증거로 DNS·Service·정책·노드 경로 문제를 구분할까?

1. 목적지·포트·시간·증상부터 고정하고 애플리케이션의 listen 상태와 로컬 요청을 확인한다.
2. 같은 노드 Pod IP와 다른 노드 Pod IP 요청을 비교해 조사할 구간을 좁힌다.
3. Pod IP·ClusterIP·DNS 이름 요청을 비교하고 28·29편의 EndpointSlice·규칙·DNS 분석을 연결한다.
4. 정책·호스트 경로·터널·노드 간 도달성을 대조한다. `blackhole /26`과 실제 Pod `/32`는 최장 접두사 일치로 설명하고, 빈 IP의 경로 선택도 확인한다.
5. 한 번에 원인 하나만 넣은 사례를 풀고, 복구 후 새 연결과 기존 연결을 재검증한다.
6. 장애 당시 상태를 보존하는 최소 수집 목록을 만든다. 증상만 보고 BGP나 CNI를 범인으로 단정하지 않는다.

실험: 포트 불일치, EndpointSlice 대상 부재, 정책 차단 등 전용 실험 자원으로 재현 가능한 사례부터 만든다. 노드 경로·터널 장애는 격리된 대상과 자동 복구 수단이 있을 때 추가한다.

필수 자료: 증상→가설→판별 명령→결정적 관측→수정→재검증 표. TCP timeout, connection refused, DNS 실패, TLS/HTTP 오류를 분리한다. 분기표는 조사 순서이며 단일 원인 판정표가 아니다.

원본은 별도 실습 저장소 `/Users/dding/orca/workspaces/k8s/tang/shared/calico`에 있다. 글에 넣을 때 관련 원문과 이미지를 이 저장소의 글별 증거 디렉터리로 선별해 옮기고 민감정보·경로·이미지 링크를 확인한다. 지금은 기존 글이나 발행 파일을 수정하지 않는다.

## 글 공통 작성·검증 기준

- 한 편마다 실제 문제 장면, 가설, 실험 조건, 명령 원문, 결과 해석, 버전 근거, 적용 범위를 갖춘다. 본문은 기존 글의 해요체와 HTML 형식을 따른다.
- 핵심 도식 2~4개와 필요한 출력만 넣되 재현에 필요한 명령·원문·pcap·매니페스트는 별도로 보관한다. 글의 도식은 기존 스케치 SVG 형식을 따른다.
- 비교 실험은 한 변인씩 바꾸고 성공 경로와 실패 경로를 모두 기록한다. 측정 주기와 명령 실행 시간을 구분한다.
- 정리는 생성한 실험 자원만 대상으로 하고, 종료 후 자원·설정·통신 복귀를 확인한다.
- 공식 문서와 설치 버전의 소스로 동작을 대조한다. 패킷 전달, 경로 작성 주체, 정책 변경 후 기존 연결 처리는 관측만으로 과도하게 일반화하지 않는다.
- 실제 집필 때 글 작성 파이프라인의 별도 리뷰와 사실 감사를 진행한다. 현재 문서는 목차 단계이므로 신규 실험 완료나 글 발행을 뜻하지 않는다.

## 본편 이후 심화 후보

블록 borrowing과 `/32` 경로 광고, IPIP와 비캡슐화 구성의 하부 라우팅 비교, BGP route reflector와 장애 범위, VXLAN·eBPF 데이터플레인 비교를 별도 환경에서 검증할 수 있다. 본편의 Linux·IPIP 구성 결과와 섞지 않는다.

IP/CIDR·라우팅·ARP·TCP·NAT 같은 독립 네트워크 시리즈는 이 실험들에서 드러난 질문을 바탕으로 분리한다. k8s 본편에는 해당 실험을 이해하는 데 필요한 설명부터 넣는다.
