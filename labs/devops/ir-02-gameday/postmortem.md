# 사후 분석: 재고 경로 지연으로 주문 약 30% 실패 (run-1)

이 문서는 게임데이 실행 `run-1` 의 실제 기록으로만 썼다. 시각은 장애 주입을 T+00:00 으로 둔 상대 시간이고,
원자료는 `results/run-1/timeline.md`, `timeline.json`, `notifications.json` 이다(자동 생성, `scripts/timeline.py`).

| 항목 | 값 |
|---|---|
| 상태 | 완료, 조치 항목 추적 중 |
| 지휘자 / 운영 / 소통 | 대응자 1인이 모두 맡음(게임데이) |
| 장애 시작 | T+00:00 (재고 경로에 latency 900ms, jitter 300ms 주입) |
| 사용자 영향 | T+00:02.8 ~ T+02:02.8 (503 카운터 기준, 스크레이프 5초 단위) |

## 요약

T+00:02.8부터 약 2분 동안 주문 요청의 약 30%(2,500건 중 747건)가 503으로 실패했다. 주문 서비스는 재고 서비스에 재고를 묻고
응답 대기가 1초를 넘으면 주문을 실패시키는데, 재고 서비스로 가는 네트워크 경로가 0.6~1.2초로 느려지면서 그중 1초를 넘는 요청이 실패했다.
T+01:53 page 경고를 받고 T+02:01 재고 확인을 보류하는 완화를 켜서 실패를 멈췄다. 이후 받은 주문 1,825건은 '확인 보류'로 접수됐다.
T+03:28 경로 지연을 제거하고 T+03:32 정상 경로로 되돌렸다.

## 영향

- 실패한 주문: 747건 (영향 구간 전체 주문 2,500건의 29.9%). 1분 창 실패율 최고 32.8%
- 재고 확인 없이 접수된 주문: 1,825건. 재고가 부족한 주문이 섞였을 수 있어 사후 확인이 필요하다(실습이라 재고 차감 로직은 없다)
- 데이터 손실: 없음
- 셈 방법: `http_server_requests_total{service="order",code="503"}` 의 증가분, 같은 구간의 전체 요청 증가분, `order_deferred_total` 증가분

## 탐지: 113초는 어디에 쓰였나

| 구간 | 시간 | 무엇이 정한 시간인가 |
|---|---|---|
| 주입 → 첫 503 스크레이프 | 2.8초 | 스크레이프 간격 5초 |
| 첫 503 → 실패율 기준(5%) 초과, pending | 20.0초 | `rate(...[1m])` 창이 실패를 쌓는 시간 + 규칙 평가 간격 10초 |
| pending → firing | 60.0초 | 규칙의 `for: 1m` |
| firing → 웹훅 수신 | 30.5초 | Alertmanager `group_wait: 30s` |
| **합계 (TTD)** | **113.3초** | 사람이 개입하기 전. 90초는 고정 설정, 23.3초는 주기와 실패 비율 |

## 트리거와 기여 요인

- **트리거**: 재고 서비스로 가는 네트워크 경로의 지연(게임데이 주입).
- **기여 요인 1**: 주문 서비스는 재고 응답을 1초까지만 기다리고, 넘으면 재시도나 대체 경로 없이 바로 503을 낸다. 0.6~1.2초에 고르게 퍼진 지연(Toxiproxy 는 latency ± jitter 범위에서 고르게 뽑는다)에서 1초를 넘는 약 3분의 1이 그대로 사용자 실패가 됐다.
- **기여 요인 1-1**: 그 1초는 요청 전체의 상한이 아니다. 파이썬 `urllib` 의 timeout 은 소켓 동작 하나하나에 걸린다. 주입 중 110초 동안 주문 응답 2,195건 중 1,020건이 1초를 넘겼는데 실패(503)는 약 673건이었다. 약 347건은 1초를 넘기고도 성공했다(`results/run-1/buckets.md`). 타임아웃을 '요청당 1초'로 읽으면 사용자가 기다리는 최대 시간을 과소평가한다.
- **기여 요인 2**: 완화 수단(재고 확인 보류)은 있었지만 사람이 켜야 한다. 켜기까지의 시간이 곧 영향 시간이다.
- **기여 요인 3**: 탐지 113초 중 90초(`for: 1m` + `group_wait: 30s`)는 고정 설정이고, 나머지 23초는 스크레이프·평가 주기와 실패 비율이 정했다. 이 경고가 늦은 게 아니라, 이렇게 설계돼 있다.

## 교훈

### 잘된 것
- 절차서 2단계 표의 첫 줄(재고 서버 p99 대 주문이 본 재고 호출 p99)로 첫 진단에서 "서버가 아니라 경로"를 가렸다. page 수신부터 완화 명령까지 7.7초.
- 완화를 켠 뒤 2초 안에 503이 멈췄다(T+02:01.0 명령, T+02:02.8 마지막 503 스크레이프).
- page 알림에 `summary` 와 `runbook_url` 이 실려 와서, 알림에서 바로 절차서로 갔다.

### 잘 안 된 것
- **완화가 진단 신호를 지웠다.** fallback 을 켜자 주문 서비스가 재고를 부르지 않아 "주문이 본 재고 호출 p99" 가 비었다. 절차서 5단계("재고 호출 p99 가 평소로 돌아왔는지 본다")를 그대로 따를 수 없어 경로를 손으로 찔렀다.
- **ticket 경고가 영향이 끝난 뒤에 울렸다.** OrderLatencyHigh 는 T+02:12.8 firing, T+02:43.4 수신. 완화는 T+02:01.0. p99 를 1분 창으로 보고 `for: 2m` 을 걸었기 때문이다. 대응 중인 사람에게는 새 장애처럼 보일 수 있다.
- **resolved 알림이 3분 51초 늦었다.** 실패율 경고의 endsAt 은 T+03:02.4 인데 resolved 수신은 T+06:53.7. firing 알림(T+01:53.3) 뒤 `group_interval: 5m` 타이머가 돌아온 시각이다. 알림 수신 시각으로 복구 시간을 재면 실제보다 길게 나온다.
- **resolved 알림의 요약이 "실패율 5.719%" 였다.** 해결 알림인데 기준(5%)을 넘는 숫자가 적혀 있다. Prometheus 는 경고가 참인 평가에서만 주석을 다시 계산하므로, 해결 알림에는 마지막으로 참이었던 평가의 값이 남는다.

### 운이 좋았던 것
- 대응자가 절차서를 쓴 사람이고, 진단·완화 명령이 스크립트로 준비돼 있었다. page 수신부터 완화까지 7.7초는 사람이 깨어나 노트북을 여는 실제 상황의 숫자가 아니다.
- 재고 경로 지연이 고정 값이 아니라 0.6~1.2초로 퍼져 있어 실패가 약 30%에 그쳤다. 1.2초로 고정이었다면 전부 실패했을 것이다.
- 게임데이 도구(Toxiproxy)가 이번 실행에서는 정상이었다. 같은 날 버린 첫 시도에서는 독을 거는 API 호출이 응답하지 않았고, 독이 하나도 없는데 프록시 경유 경로가 막혀 프록시를 재시작해야 했다(`results/toxiproxy-remove/first-incident.md`).
