## Spring Cloud Config 1편: LOW 1건

- 위치: `posts/open-source-contribute/spring-cloud-config/01_1편 - 웹훅이 가리킨 저장소만 만료시키기.html:2`
- 근거: lead가 “만료 대상을 해당 저장소로 **좁힌 과정과**, Bitbucket Server 샘플을 모든 페이로드로 일반화했던 **설명을 정정했어요**”라고 끝난다.
- 문제: 병렬 목적어가 같은 서술어에 연결되면서, 구현 과정을 기록했다는 뜻과 과거 설명을 정정했다는 뜻이 모두 “정정했다”로 합쳐진다. 본문의 구현 경위와 설명 정정은 서로 다른 행동이므로 서술어를 나눠야 요약이 정확해진다.
- 최소 수정 예시: “Spring Cloud Config Server에 refresh-rate를 걸면 웹훅 알림 뒤에도 이전 커밋을 받을 수 있어요. 만료 대상을 해당 저장소로 좁힌 과정을 적고, Bitbucket Server 샘플을 모든 페이로드로 일반화했던 설명을 정정했어요.” 공백 포함 144자로 길이 조건도 유지한다.
- 나머지 변경 표현: 35행은 주된 과거 구현 SHA와 최신 대응을 구분하고, 163행은 당시 인용의 일반화를 바로 정정한다. OPEN/변경 요청 상태, 링크 유무에 따른 적용 범위도 구분되어 있다.

## Spinnaker 2편: LOW 1건

- 위치: `posts/open-source-contribute/spinnaker/02_2편 - 승인 코멘트의 후속 8항목을 이슈 하나와 PR 둘로 옮긴 과정.html:170`
- 근거: “**각 PR에서 고친 파일 다섯 개(#8208 네 개, #8209 한 개)**를 당시 재현 SHA와 최신 head 사이에 대조하니…”라고 썼다.
- 문제: “각 PR”은 PR마다 다섯 개라는 뜻인데 괄호와 조사 기록은 두 PR 합계가 다섯 개임을 뜻한다. 수치 자체보다 수량을 한정하는 주어 범위가 충돌한다.
- 최소 수정안: “**두 PR에서 고친 파일 총 다섯 개(#8208 네 개, #8209 한 개)**를 당시 재현 SHA와 최신 head 사이에 대조하니…”로 바꾼다.
- 나머지 변경 표현: 당시 재현 SHA를 유지하고 현재 head를 별도로 적었다. main 동기화와 PR 고유 변경, build 성공과 Mergify 권한 실패, NEUTRAL과 전체 체크 통과를 구분한다. UTC 기준은 도입의 기존 선언을 따른다.

### Spinnaker 2편 수정 재검

- 최초 지적 공유 뒤 저자가 “두 PR에서 고친 파일은 **합계 다섯 개**(#8208 네 개, #8209 한 개)이고…”로 수정한 것을 동일 170행에서 확인했다.
- 전체 수량과 각 PR의 수량이 구분되어 문제가 해소됐다. 라운드 2 APPROVE, 잔여 지적 0건.

## 공통 확인 및 한계

- 네 글 모두 lead가 80~150자 범위다. 길이는 HTML 주석 구분자와 바깥 공백을 제외한 내용으로 계산했다.
