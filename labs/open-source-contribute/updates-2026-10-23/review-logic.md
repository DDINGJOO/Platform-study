# 오픈소스 기존 글 최신화: 논리 모순 독립 퇴고

- 관점: 논리 모순. 저자와 별도 검수자가 검토했다.
- 기준: `4719a097d08cfc471415a226f872cc3e1b65f549` 이후 네 HTML의 변경 diff와 인접 문맥.
- 공통 근거: `BRIEF.md`, `sources.md`, `status.json`, 기존 HTML의 보존된 재현·테스트·한계 설명.
- 경계: 공개 upstream의 최신 상태를 다시 조회한 독립 사실 감사가 아니다. 제공된 조사 기록과 글의 결론·시점·집계 범위 사이 모순을 검사했다. 과거 실험 또는 최신 head를 실행하지 않았고, upstream·저자 HTML·코드·증거를 수정하지 않았다. 이 보고서만 작성했다.

## 라운드 1: Spring Cloud Config 1편

- 파일: `posts/open-source-contribute/spring-cloud-config/01_1편 - 웹훅이 가리킨 저장소만 만료시키기.html`
- 판정: **APPROVE**
- 지적: **0건** (CRITICAL 0 / HIGH 0 / MEDIUM 0 / LOW 0)

확인한 논리 경계:

1. 도입에서 OPEN·CHANGES_REQUESTED·미머지를 유지하고, 주된 구현 기록이 `3ba94c12` 시점임을 명시한다. 새 URL 매칭·반환값을 과거 코드의 실행 결과처럼 바꾸지 않는다.
2. Bitbucket Server 푸시 전체에 URL이 없다는 일반화를 철회하고, 당시 링크 없는 샘플과 clone 링크가 있는 별도 샘플을 구분한다. 표의 푸시 행을 정정했음을 앞에서 밝히므로 과거 커밋 설명과 최신 정보가 혼재한 사실을 숨기지 않는다.
3. 남겨 둔 당시 영어 코멘트 바로 뒤에서 그 주장이 과도했음을 명시한다. 해당 인용을 현재 결론으로 다시 사용하지 않는다.
4. 링크가 있고 설정 원격과 맞는 경우 만료 가능, 링크가 없는 경우 만료 없이 알림만 유지라는 조건을 구분한다. 이로부터 원래 Bitbucket 사례 전체 해결이나 이슈 종료를 추론하지 않는다.
5. 저장소 순회 코드 블록을 과거 SHA의 코드로 한정하며 최신 boolean 반환 계약과 혼동하지 않는다.

## 라운드 1: Spring Cloud Config 2편

- 파일: `posts/open-source-contribute/spring-cloud-config/02_2편 - 매칭은 느슨하게, lastRefresh는 그대로 둔 이유.html`
- 판정: **APPROVE**
- 지적: **0건** (CRITICAL 0 / HIGH 0 / MEDIUM 0 / LOW 0)

확인한 논리 경계:

1. 처음 받은 여섯 요청과 `53b59abc`의 수정을 1~7절의 과거 기록으로 한정하고, 기존 8절 안에 후속 세 요청과 `f6c23d31`을 분리한다. 7절 테스트 결과를 최신 head의 테스트 결과로 바꾸지 않는다.
2. URI 추출 헬퍼의 이동은 구조 변경이며, Bitbucket clone 링크 처리의 최초 구현이라고 확대하지 않는다. 링크가 없는 기존 fixture와 링크가 있는 추가 테스트의 관계가 1편의 정정과 일치한다.
3. 반환된 boolean을 단락 평가 없이 `|=`로 누적하는 이유를 전체 저장소 만료와 연결한다. 첫 일치 뒤 다른 저장소 호출을 생략하는 것으로 설명하지 않는다.
4. URI가 존재하나 모든 호출이 미매칭이고 예외가 없을 때의 debug와, 호출 예외가 난 경우의 warn을 구분한다. 예외를 미매칭으로 확정하거나 실패를 정상 성공으로 처리한다는 설명이 없다.
5. 최신 head 공개 체크 DCO 한 개의 성공과 이전 로컬 테스트를 분리한다. 공개 체크의 제한된 관측으로 전체 테스트 성공을 주장하지 않는다.
6. 새로운 메인테이너 리뷰가 왔다는 사실과 `lastRefresh` 논점에 승인·반박이 없다는 사실을 함께 설명한다. 이전의 '메인테이너가 아직 답하지 않았다'는 포괄 문장을 특정 논점의 합의 부재로 좁혀 시점 모순을 없앴다.
7. `lastRefresh` 변경 대안을 실제로 실행하지 않았다는 기존 한계를 보존한다. 저자의 경로 분석과 기존 코드 테스트가 대안 구현의 실증 또는 메인테이너 승인이라는 결론으로 바뀌지 않는다.

## 라운드 1: Spinnaker 2편

- 파일: `posts/open-source-contribute/spinnaker/02_2편 - 승인 코멘트의 후속 8항목을 이슈 하나와 PR 둘로 옮긴 과정.html`
- 판정: **APPROVE**
- 지적: **0건** (CRITICAL 0 / HIGH 0 / MEDIUM 0 / LOW 0)

확인한 논리 경계:

1. 본문의 `d91a2724c3`·`92bd5f89b3`을 당시 재현 SHA로 유지하고 최신 head `9e5c3b725519`·`182ca9d32ac3`을 별도로 기록한다. 최신 head를 로컬 실행했다는 주장을 하지 않는다.
2. main 병합 동기화와 PR 고유 수정 파일의 불변을 구분한다. 제공된 SHA-256 비교 기록은 PR별 4개와 1개, 총 다섯 파일의 old/new 쌍이 동일하다. 이 범위에서 새 기능 수정·회귀 테스트 추가가 없었다는 설명은 일치하며 main 전체가 불변이라고 쓰지 않는다.
3. build·wrapper 체크 성공, Mergify 자동 갱신 규칙 실패, Merge Queue NEUTRAL, Summary 성공을 별개로 설명한다. 앱의 workflows 권한 거부를 코드 테스트 실패와 구분하면서도 전체 체크 통과 또는 머지 준비 완료로 결론 내리지 않는다.
4. OPEN·REVIEW_REQUIRED와 리뷰·인라인 댓글·일반 코멘트 부재를 유지한다. 이슈 댓글 두 개가 작성자 본인의 것임을 밝혀 메인테이너 응답으로 세지 않는다.
5. 원래 #8174 승인과 후속 PR 둘의 미승인을 구분하며, 아직 고치지 않은 경로·제약과 다음 방향 미합의의 결론을 보존한다.

## 라운드 1: Debezium 2편

- 파일: `posts/open-source-contribute/debezium/02_2편 - DEFAULT를 데이터베이스 이름으로 읽던 문법.html`
- 판정: **APPROVE**
- 지적: **0건** (CRITICAL 0 / HIGH 0 / MEDIUM 0 / LOW 0)

확인한 논리 경계:

1. Debezium #8225의 OPEN·head 불변·새 승인 부재와, 별도 상류 grammars-v4 #5039의 기존 머지를 구분한다. 새 코드 변경 또는 새 머지가 생긴 것처럼 쓰지 않는다.
2. 10월 22일 CI 설명 코멘트의 작성자가 본인임을 명시하고, 수정 모듈 밖이라는 설명을 메인테이너 원인 확인·승인과 분리한다. Commit message 체크 성공도 다른 실패의 원인 규명으로 사용하지 않는다.
3. 과거 확인한 성공30/실패6, 최신 head 전체 체크58개(성공36/실패6/건너뜀16), 실행 `39574509122`의 55잡(성공33/실패6/건너뜀16)의 집계 범위가 다르다고 명시한다. 36+6+16=58 및 33+6+16=55로 수치 자체도 모순이 없다.
4. 위 수치 차이를 새 실패 발생·CI 개선의 근거로 쓰지 않는다. 6절의 과거 로그와 로컬 단위 테스트·CI 로그 열람·미실행 통합 테스트의 경계를 보존한다.
5. 기존 MySQL 콜백 타이밍 설명이 추정이며 직접 수정 실행하지 않았다는 한계를 유지한다. 새 코멘트가 그 추정을 입증한 것으로 바뀌지 않는다.

## 공통 보존 확인과 제한

- 네 파일의 기준 커밋/현재 내용에서 CSS, SVG, 시리즈 박스를 추출해 원문 동일성을 검사했다. **네 파일 모두 동일**했다.
- 제공된 Spinnaker SHA-256 비교 열 개 기록을 `(PR, path)`로 독립 그룹화해 다섯 old/new 쌍 모두 동일함을 확인했다. upstream 바이트를 새로 내려받아 감사한 것은 아니다.
- 신규 구현 코드가 없는 기존 HTML 설명 변경이다. LSP 진단 도구는 제공되지 않아 실행하지 않았다. 형식·브라우저·마스킹은 별도 검증 대상이다.
- 최종 논리 관점 판정: **4편 모두 라운드 1 지적 0건**. 별도 원자료 사실 감사와 발행 검증을 대체하지 않는다.
