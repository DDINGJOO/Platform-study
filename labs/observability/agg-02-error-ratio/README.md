# 집계와 분포 실습-2: 에러율을 PromQL에서 비율로 그린다

앱 두 대(`app-a` 가 요청의 90%, `app-b` 가 10%)에 k6 로 출렁이는 트래픽을 주고, 중간에 500 비율을 바꾼다.
같은 지표를 "초당 5xx 건수"와 "5xx 비중"으로 그려 어떻게 다르게 읽히는지, 0으로 나누기와 빈 분자를
PromQL 에서 어떻게 다루는지 본다. 모든 요청의 3%는 400(잘못된 요청)으로 돌려준다.

## 시나리오 (run.sh, 9분 30초)

| 시각 | 초당 요청 | 500 비율 |
|---|---|---|
| 0:00-1:00 | 20 | 0 (5xx 시계열이 아직 없다) |
| 1:00-2:00 | 20 | 2% |
| 2:00-4:00 | 20 → 100 (피크) | 2% |
| 4:00-4:30 | 100 → 10 | 2% |
| 4:30-6:30 | 10 | 30% (장애) |
| 6:30-8:00 | 20 | app-a 2%, app-b 50% |
| 8:00-9:30 | 0 (k6 종료) | |

## 돌리기

```bash
cd labs/observability/agg-02-error-ratio
docker compose up -d --build
./run.sh                     # 9분 30초. k6 출력은 k6.log, 실패율 변경 시각은 화면에
docker compose --profile load down -v
```

- Grafana http://localhost:23100 → 대시보드 「실습-2 에러 건수와 에러 비중」
- Prometheus http://localhost:23190, 앱 http://localhost:23181, http://localhost:23182
- 실패율 직접 바꾸기: `curl -X POST 'http://localhost:23181/admin/fail-rate?value=0.3'`

## 버전

Spring Boot 4.1.1 (Micrometer 1.17.1), Prometheus 3.15.0 (scrape 5s, rate 창 20s), Grafana 13.2.3, k6 2.3.0

## 돌리다 만난 함정

- 5xx 가 한 번도 안 난 동안은 `outcome="SERVER_ERROR"` 시계열이 없다. 기본 비율 식은 0이 아니라 **빈 결과**가 된다.
  분자에 `or vector(0)` 을 붙이면 0이 된다.
- 트래픽이 0이 되면 분자·분모가 모두 0이라 비율은 `NaN` 이다. `/ (분모 > 0)` 으로 거르면 빈 결과가 된다.
- 트래픽이 끊기는 순간 비율이 한 칸 튄다. 글에 쓴 실행에서는 50%(app-b 의 마지막 스크레이프 구간 479.0~484.0초에 들어온 4건 중 2건이 500),
  처음 실행에서는 83%(6건 중 5건)였다. 20초 창에 app-b 의 마지막 증가분만 남은 시점이다. 타깃마다 스크레이프
  시각이 달라서 생긴다. `/ (분모 >= 1)` 처럼 최소 트래픽을 걸면 사라진다.
- 같은 Docker VM 에서 다른 무거운 컨테이너와 동시에 돌리면 k6 가 목표 요청 수를 못 채운다(`dropped_iterations`).
  한 번 그렇게 망친 실행은 버리고 다시 돌렸다. k6 요약의 `http_reqs` 가 17,850건인지 확인한다.
- 처음 시나리오는 k6 단계 끝에 "목표 0으로 90초"를 넣었는데, k6 가 8:00에 중단 표시(✗)로 끝났다.
  원인을 확인하지 못해서 트래픽 0 구간은 k6 없이 run.sh 가 기다리게 바꿨다.
