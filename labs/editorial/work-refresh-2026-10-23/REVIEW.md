# 독립 퇴고·감사 기준

`BRIEF.md`, `PLAN.md`, 적용 스킬을 읽는다. 작성자와 다른 에이전트만 검토한다. 역할은 퇴고 `code-reviewer`, 감사 `verifier`이며 설치된 역할 파일은 `/Users/dding/.codex/agents/`에 있다. 배정 관점과 범위는 리더 메시지를 따른다. 글·원본 저장소·공통 설정을 수정하지 않는다. 자신에게 배정된 보고 JSON만 쓴다. 재위임하지 않는다.

전체 글 목록은 `baseline.json`이다. 편집 전 원문은 그 파일의 `commit`에서 `git show COMMIT:경로`로 읽는다. 현재 HTML, `writers/번호.json`, `checks.json`, `titles.json`, `technical-corrections.json`을 함께 본다. 긴 CSS·SVG 도형·코드는 보존 검사로 동일 여부를 확인할 수 있지만, 기술 주장을 검토할 때 필요한 코드와 라벨을 생략하지 않는다. 여러 글이면 작은 묶음으로 읽고 각 번호의 검토 결과를 기록한다.

퇴고 관점은 네 가지다.

- 사실관계: 달라진 문장의 수치·설정·인과·실행 여부가 실제 근거와 맞는지, 보존한 발췌에 오류가 있으면 본문에서 오해 없이 한정했는지 확인한다.
- 논리: 글 안과 같은 시리즈 안의 앞뒤 모순, 본문·그림·요약 간 차이, 당시 판단과 후속 정정의 구분을 확인한다.
- 독자: 설명 없이 등장하는 내부 관행·약어·전제, 사용자가 자기 상황에 적용할 때 오해할 생략을 확인한다.
- 문장: 문체·시제·용어 일관성, 남은 과장·비유·억지 반전·집필 설명·명언형 결론, 실제 중복 문단을 확인한다. 취향 차이는 지적하지 않는다.

독립 감사자는 퇴고 보고를 승인 근거로 쓰지 않는다. 원자료의 코드·ADR·고정 커밋·실습 출력과 직접 대조하고 `확인 / 불일치 / 확인 불가 / 과장`으로 판정한다. `완료`, `전부`, `그 뒤로`, `한 번도`, `이제 안전`처럼 범위를 넘어서는 완결 주장에 반례를 먼저 찾는다. 최소한 각 글의 핵심 결정·인과·수치·실행 주장을 식별하고 확인 경로를 기록한다. 해당 자료가 없으면 없는 그대로 `확인 불가`로 남기며 글에 적절한 관찰 범위가 명시돼 있는지도 평가한다. 이번 편집으로 실제 운영·과거 실험을 새로 실행했다고 해석하지 않는다. 기술 문서를 조회해야 하면 공식 일차 자료만 쓰고 URL을 남긴다.

`/Users/dding/orca/platform-IaC`는 다른 작업자가 수정 중인 읽기 전용 자료다. 인용된 고정 커밋을 우선하고 변경을 정리하지 않는다. 실제 조직 식별자·비공개 경로·금액·원본 값을 보고서에 복사하지 않는다. 회사 Notion·Slack에 접속하지 않는다. 모르는 사실을 보완하지 않는다.

보고서는 `role`, `round`, `checked_numbers`, `issues`, `limits`를 포함한다. 지적마다 `number`, `location`, `kind`, `problem`, `evidence`, `suggested_fix`, `severity`를 적는다. 감사는 여기에 `claims`(글 번호·주장·판정·근거·한정의 적절성), `distribution`, `least_confident`를 더한다. 승인만 나열하지 말고 실제 읽은 범위와 한계를 적는다. 지적이 없으면 빈 배열로 낸다. 지적이 틀렸으면 기각하고 근거를 쓴다. 형식·마스킹 검사는 내용 감사의 대체가 아니다.

수정은 파일마다 한 명만 담당하고, 수정 뒤 같은 관점으로 해당 지적을 재검한다. 최대 세 라운드이며 남은 항목을 숨기거나 자동으로 통과 처리하지 않는다.
