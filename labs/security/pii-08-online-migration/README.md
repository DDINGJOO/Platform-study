# pii-08-online-migration

개인정보 암호화 8편 「운영 중인 테이블을 무중단으로 암호화 전환하는 순서」의 실습.

평문 30만 행이 든 MySQL 테이블을, 앱 두 대가 롤링 배포로 교체되는 동안 쉬지 않고 요청을 받게 해 두고
암호화로 전환한다. 단계마다 실패 요청(5xx·연결 오류)과 값 틀림(200 인데 암호문이나 다른 값을 돌려줌)을 센다.

## 구성

| 무엇 | 어디 | 비고 |
|---|---|---|
| MySQL 8.4 | 컨테이너, 호스트 포트 38080 | `compose.yaml` |
| 앱 인스턴스 | 호스트 JVM, 포트 38081~38089 | `src/Lab.java serve` |
| 채우기·복원·검증 배치 | 호스트 JVM | `src/Lab.java batch` |
| 부하 생성기 | 호스트 python3 | `scripts/loadgen.py`, 작업자 8개 x 초당 40건 |

앱 버전은 읽기 컨버터와 쓰기 스위치의 조합이다.

| 버전 | 읽기 | 쓰기 |
|---|---|---|
| v0 | 그대로 (원래 코드) | 평문 |
| v1 | 관대 (접두어면 복호화, 아니면 그대로) | 평문 |
| v2 | 관대 | 암호화 |
| v2-off | 관대 | 평문 (스위치가 읽히지 않은 v2, 또는 되돌릴 때 쓰기를 끈 판) |
| v3 | 엄격 (암호문이 아니면 예외) | 암호화 |

요청 종류: 한 건 조회 55%, 목록 20행 15%, 로그인 20%(부분 갱신 없이 모든 컬럼을 다시 쓰는 UPDATE),
값 변경 후 다른 대에서 다시 읽기 10%. 기대값은 시작 시점 덤프이고, 값을 바꾸는 요청은 그 id 를 맡은 작업자만 보낸다.

데이터: `000000-` 로 시작하는 가짜 주민번호 형식. 500번째 행마다 이상한 값 6종(뒤에 문자, 자릿수 틀림,
전각 숫자, 빈 문자열, 공백 한 칸, 뒤 공백)을 100행씩, 997번째 행마다 NULL.

암호는 AES-GCM(IV 12바이트 난수), 저장 형식은 `LABENC1:` + base64(IV||암호문||태그). 키와 접두어는 이 실습 전용이다.

## 실행

```bash
scripts/setup.sh                 # 드라이버 jar 를 lib/ 에 두고 컴파일 (Java 21+)
docker compose up -d --wait
scripts/run.sh happy             # 시나리오 하나. 목록은 scripts/run.sh 머리말
docker compose down -v
```

| 시나리오 | 무엇을 보나 |
|---|---|
| count-demo | 이상한 값 하나씩에 대해 검증 COUNT 조건별로 걸리는가 |
| fake-prefix | 접두어만 맞는 값을 SQL COUNT 와 복호화 검증이 각각 세는가 |
| ddl | VARCHAR(20) 을 63/255 로 넓힐 때 INPLACE 가 되는가 |
| happy | v0 → v1 → v2 → 채우기(중간에 kill -9 뒤 재개) → 검증 → v3 |
| skip-read | v0 → v2 로 바로 |
| strict-early | 평문 모양만 채우고 평문 모양 COUNT 0 을 믿고 v3 |
| config-miss | v2 두 대 중 한 대가 스위치를 못 읽음(v2-off), 채우기 뒤 10초마다 다시 센다 |
| rollback-wrong | 쓰기를 켠 채 복원 → v0 |
| rollback-right | v2-off 로 쓰기 먼저 끔 → 복원 → 암호문 0 확인 → v0 |

## 결과 (2026-10-17, `results/*.txt`)

| 시나리오 | 요청 | 실패 | 값 틀림 | 핵심 |
|---|---:|---:|---:|---|
| happy | 29,401 | 0 | 0 | 채우기 kill -9 때 저장된 커서 82000 에서 재개, 끝난 뒤 암호문 아님 0 |
| skip-read | 9,066 | 0 | 164 | 전부 섞이는 구간의 v0 가 돌려준 값 |
| strict-early | 26,893 | 42 | 0 | 평문 모양 COUNT 0, 암호문 아님 COUNT 597, 실패는 전부 v3 |
| config-miss | 27,763 | 0 | 0 | 암호문 아님 499 → 965 → 1407 → 1810 (10초 간격). 요청은 하나도 안 실패 |
| rollback-wrong | 28,897 | 0 | 223 | 복원 직후 암호문 663 행, 끝날 때 1130 행 |
| rollback-right | 34,935 | 0 | 0 | 복원 직후·끝 모두 암호문 0 행 |

count-demo 합계(값 11개): 평문 모양 `[0-9]` 2, `\d` 3, 암호문 아님(IS NOT NULL) 8, `<> ''` NO PAD 7, `<> ''` PAD SPACE 6, 엄격 형식 아님 9.
fake-prefix: SQL 암호문 아님 0, 복호화 검증 decryptFailed 1.
ddl: VARCHAR(63) INPLACE 0.10초 성공, VARCHAR(255) INPLACE 는 ERROR 1846, COPY 0.37초(그동안 쓰기 한 건 224ms).

## 한계

- 롤링 배포는 대수 2, 섞이는 구간 8초로 흉내 냈다. 실제 배포의 섞이는 시간과 비율은 다르다. 값 틀림 건수는 그 시간과 쓰기 비율에 비례하니 절대값보다 0인가 아닌가를 본다.
- 30만 행은 좁은 행이라 COPY 가 0.37초에 끝났다. 큰 테이블의 COPY 시간은 여기서 추정하지 않는다.
- 부하 생성기는 롤링으로 빠지는 대에 보낸 요청을 1초 기다린 뒤 끈다. 첫 실행 두 번은 포트를 다시 쓰는 새 인스턴스에 끊긴 옛 연결을 재사용해 배포와 무관한 연결 오류가 섞였고, 연결을 인스턴스(PID)별로 두도록 고친 뒤 전 시나리오를 다시 돌렸다. `results/` 는 그 세 번째 실행이다.
