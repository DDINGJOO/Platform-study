확정 목록에 올려둔 개발용 로드밸런서 하나를 지우려고 삭제 명령을 넣었어요. 타깃도 0, 지난 한 달 요청도 0, DNS 레코드도 없고 알람도 없다는 걸 이미 다 확인해둔 상태였습니다. 그냥 지우면 끝나는 줄 알았죠.

그런데 거부됐어요. ResourceInUse. 그리고 뒤에 이런 문장이 붙어 있었습니다. "이 자원은 하나 이상의 타깃그룹에 타깃으로 등록되어 있으므로 삭제할 수 없습니다."

여기서 손이 멈춥니다. 등록되어 있다는 건 누가 쓰고 있다는 뜻인가요? 조금 전까지 아무도 안 쓴다고 확인했는데, AWS 가 쓰이고 있다고 말하는 것 같잖아요. 그러면 확인을 다시 해야 할 것 같고, 잘못 지우면 무언가 끊길 것 같고요.

그날 하루에 로드밸런서, NAT 게이트웨이, 사용이 끝난 어떤 서비스의 잔재 열한 종, 검색 인덱스, 이미지와 스냅샷을 차례로 지웠어요. 그러면서 알게 된 건 삭제에도 문법이 있다는 것이었습니다. 지우는 순서에 규칙이 있고, 오류 메시지를 읽는 방법에도 규칙이 있어요. 그 문법을 모르면 위 오류에서 잘못 멈추거나, 반대로 순서를 틀려서 아무도 끌 수 없는 알람을 만듭니다.

1. ResourceInUse 를 사용 중으로 읽으면 잘못 멈춘다

결론부터 쓰면, 그 오류는 이 자원이 쓰이고 있다는 신호가 아니라 삭제 순서 제약이었어요.

구조는 이랬습니다. 어떤 타깃그룹이 이 로드밸런서를 자기 타깃으로 등록해두고 있었어요. 그런데 그 타깃그룹을 쓰는 상위 로드밸런서는 이미 삭제된 상태였습니다. 타깃그룹의 연결 목록이 비어 있었어요. 즉 트래픽이 흐를 경로 자체가 없는데, 등록 관계라는 껍데기만 남아 있던 거예요.

AWS 는 그 껍데기를 근거로 삭제를 거부합니다. 등록이 남아 있는 동안은 못 지우게 되어 있어요. 그러니까 오류 문장이 요구하는 것은 "쓰이고 있는지 다시 확인해라"가 아니라 "등록을 먼저 해제해라"입니다.

받은 오류 ResourceInUse: 이 자원은 하나 이상의 타깃그룹에 타깃으로 등록되어 있으므로 삭제할 수 없습니다. 삭제하려면 모든 타깃그룹에서 등록을 먼저 해제해야 합니다. 내가 읽은 것 "누가 쓰고 있다" -> 멈춘다 실제 의미 "앞의 것을 먼저 지워라" -> 순서를 바꾼다 delete-target-group // 상위가 없는 고아 타깃그룹. 바로 지워진다 -> delete-load-balancer // 등록이 사라졌으므로 이제 지워진다

등록만 떼는 명령도 있어요. 그런데 그 타깃그룹을 남길 이유가 없었으니 타깃그룹째로 지웠고, 타깃그룹이 사라지면서 등록도 함께 사라졌습니다. 그 다음 로드밸런서는 아무 저항 없이 지워졌어요.

같은 종류의 거부를 다른 작업에서도 만났습니다. 방화벽 규칙 묶음을 지울 때는 배포가 하나라도 붙어 있으면 WAFAssociatedItemException 으로 거부돼요. 컨테이너 클러스터는 용량 공급자가 붙어 있으면 삭제되지 않습니다. 전부 같은 문법이에요. 참조하는 쪽이 남아 있으면 참조되는 쪽을 지울 수 없습니다.

이걸 "AWS 가 안전장치를 걸어준다"로 읽으면 고마운 일이고, 실제로 그렇게 동작합니다. 문제는 그 메시지가 말해주는 것이 참조가 있다까지라는 점이에요. 그 참조가 살아 있는지 껍데기인지는 말해주지 않습니다. 트래픽이 흐르는 타깃그룹에 등록된 자원도 같은 문장으로 거부되고, 이번처럼 상위가 사라진 고아 타깃그룹에 등록된 자원도 같은 문장으로 거부돼요. 한 문장이 두 상황을 덮으니 구분은 읽는 사람이 해야 합니다. 방법은 하나예요. 참조하는 쪽을 열어보는 것입니다. 그 타깃그룹의 연결 목록이 비어 있는지, 붙어 있는 상위가 실제로 존재하는지요.

그리고 그 제약은 이미 적혀 있었다

더 뼈아픈 건 이거였어요. 작업 문서의 그 항목 비고에 "상위 로드밸런서 타깃 등록 해제 선행"이라고 적혀 있었습니다. 지금 만난 제약을 정확히 가리키는 문장이에요. 저는 그걸 읽었고, 순서를 지키지 않았습니다.

왜 안 지켰냐면, 그 비고를 다른 뜻으로 읽었기 때문이에요. "상위에서 등록을 떼는 작업이 선행되어야 한다"를 저는 "누군가 그 경로를 의도적으로 설계했다"로 읽었습니다. 그래서 오히려 삭제를 한 번 보류했어요. 이름에 외부 연동을 시사하는 문자열이 들어 있었고, 그 서비스의 이미지 저장소는 남기라는 판단이 따로 있었으니 다시 배포할 여지가 있다면 이 로드밸런서가 필요해질 수도 있다고 봤고요.

그래서 진입 경로를 전부 열어봤습니다. 이 로드밸런서를 타깃으로 가진 타깃그룹은 하나였고 그 타깃그룹의 연결은 비어 있었어요. DNS 레코드는 전체 호스팅 영역을 뒤져도 없었고, 리스너는 평문 하나에 기본 액션이 가리키는 타깃그룹조차 없었습니다. 요청이 와도 갈 곳이 없는 상태였어요. 알람도 없고 코드에서 참조하는 곳도 없었습니다.

우려 세 가지가 다 해소돼서 삭제로 돌아왔고, 그때 저 오류를 만난 거예요. 그러니까 같은 한 줄이 두 가지로 읽혔습니다.

비고: "상위 로드밸런서 타깃 등록 해제 선행" 설계 의도로 읽으면 누군가 이 경로를 만들었다 -> 삭제를 보류한다 API 제약으로 읽으면 지우는 순서가 이렇다 -> 순서대로 지운다 판단이 정반대로 갈린다. 그런데 확인하는 데 걸린 시간은 조회 한 번이었다.

그래서 규칙 하나가 생겼어요. 비고에 적힌 선행 조건은 그 자리에서 이유를 확인합니다. 조건만 읽고 넘어가면 그게 설계 의도인지 API 제약인지 모르는 채로 지나가고, 둘은 정반대의 결론으로 이어져요. 확인 비용은 조회 한 번인데 틀렸을 때의 비용은 유휴 자원을 몇 달 더 두는 것이거나 순서를 틀려 사고를 내는 것입니다.

그림 1. 안전장치가 내는 거부와 진짜 사용 중은 같은 문장으로 온다

2. 알람을 먼저 걷어내야 하는 두 가지 이유

순서 이야기가 나왔으니 가장 앞에 오는 것부터 쓸게요. 실물보다 알람이 먼저입니다. 실물을 먼저 지우면 두 종류의 사고가 나요. 그리고 둘 다 이 저장소에서 이미 겪은 일입니다.

사고 하나. 스택 전체의 plan 이 막힌다

알람 코드가 감시 대상을 data 소스로 조회하는 구조일 때 생깁니다. 왜 그렇게 짰냐면, 로드밸런서의 지표 차원에는 이름 뒤에 랜덤 16진수가 붙어요. 그걸 손으로 옮겨 적다 한 글자 틀리면 그 알람은 데이터를 받지 못하고, 결측 처리 설정에 따라 영구 경보가 되거나 영구 침묵이 됩니다. 둘 다 조용한 실패예요. 그래서 이름만 목록으로 두고 접미사는 조회로 받게 했습니다.

이 설계에는 의도된 부작용이 있어요. 대상이 사라지면 조회가 실패하면서 plan 이 시끄럽게 죽습니다. 조용히 빠지는 것보다 낫다고 판단해서 그렇게 둔 거예요. 그런데 이건 실물을 먼저 지우면 그 스택의 모든 plan 이 막힌다는 뜻이기도 합니다.

과거에 실제로 그렇게 됐어요. 로드밸런서 하나를 코드보다 먼저 지웠더니, 그 자원과 아무 관계 없는 PR 둘이 동시에 멈췄습니다. 같은 스택을 건드리는 PR 이었을 뿐인데요. 잠금 단위가 스택이니 폭발 반경도 스택입니다.

사고 둘. 아무도 끌 수 없는 경보가 남는다

알람에는 지표가 안 올 때 어떻게 판정할지를 정하는 설정이 있어요. missing_data 입니다. 값이 안 오는 상황을 위반으로 볼지, 정상으로 볼지, 판정을 보류할지 고르는 거죠.

결측을 위반으로 취급하는 알람은 감시 대상이 사라지면 어떻게 되냐면요. 지표가 영원히 오지 않으니 영원히 경보 상태입니다. 정상으로 돌아갈 조건이 세상에서 사라졌으니까요. 알람을 지우는 것 말고 끄는 방법이 없어요.

이 설정이 왜 있느냐면, 그게 필요한 자리가 있기 때문입니다. 컨테이너 자동 확장 그룹의 인스턴스 수를 보는 알람에서 지표가 끊긴 것은 좋은 신호가 아니에요. 지표 수집이 꺼졌거나 그룹이 없어졌다는 뜻이고, 둘 다 알아야 하는 사건입니다. 그래서 일부 알람은 일부러 결측을 위반으로 뒀어요. 그 선택이 삭제 순서를 강제합니다.

여기에 하나가 더 붙어요. 매일 도는 알람 커버리지 검사가 코드에 있는데 실물에 없는 것을 유령으로 잡습니다. 실물을 먼저 지우면 그 다음 아침부터 검사가 매일 울려요. 알람은 멀쩡히 돌고 있는데 가드만 우는 상태가 되고, 그런 가드는 며칠이면 아무도 안 봅니다.

그래서 순서가 이렇게 고정된다 1. 코드에서 알람을 제거한다 (PR 하나. 다른 변경을 섞지 않는다) 2. apply plan 기대값과 실제를 대조한다 3. 알람 0건 확인 지운 자원의 접두사로 조회한다 4. 남아야 하는 알람 생존 확인 옆 자원의 알람까지 지우지 않았나 5. 실물 삭제 6. 삭제 확인 + 그 자원을 쓰던 것들이 정상인지 확인 4번을 빠뜨리기 쉽다. 목록에서 한 줄 지울 때 옆 줄이 같이 지워지는 일이 실제로 일어나고, 그건 알람 0건 확인으로는 잡히지 않는다.

2번에서 한 번 틀렸어요. 삭제가 다섯 건일 줄 알았는데 네 건이 나왔습니다. 목록을 for_each 로 펼치는 곳이 두 군데라 알람도 두 개로 셌는데, 그중 하나는 module 이 아니라 data 소스였어요. 데이터소스는 리소스가 아니라서 삭제 카운트에 들어가지 않습니다. 그래서 하나가 덜 나왔고요. 규칙으로 적으면 for_each 개수만 세지 말고 그것이 module 인지 data 인지 봐야 합니다.

기대값과 실제가 다를 때 "예상보다 적게 지워지니 안전하다"로 넘기면 안 돼요. 대상이 잘못 잡혔다는 뜻일 수도 있습니다. 그래서 숫자가 맞아떨어질 때까지 원인을 찾고, 원인이 "데이터소스는 안 세는 것이 맞다"로 확인된 뒤에 apply 로 넘어갔습니다.

3. 의존 순서는 참조 방향을 따른다

알람을 걷어내면 그 다음은 실물 차례인데, 여기도 순서가 있어요. 그리고 규칙은 하나로 정리됩니다. 참조하는 쪽을 먼저 지웁니다.

세 가지 사례가 그날 다 나왔어요.

검색 인덱스와 상위 지식 베이스. 상위 지식 베이스가 인덱스 컬렉션을 참조하는 구조입니다. 그래서 상위를 먼저 지웠어요. 순서를 바꾸면 가리킬 컬렉션이 없는 지식 베이스가 남고, 그 상태에서는 삭제 요청이 오류로 거부됩니다.

DNS 레코드와 로드밸런서. 이건 API 제약이 아니라 사용자가 보는 상태 때문이에요. 로드밸런서를 먼저 지우면 레코드는 살아 있는데 가리키는 대상이 없는 구간이 생깁니다. 그 사이에 누가 접속하면 응답이 아예 안 오거나 엉뚱한 것을 받아요. 그래서 레코드를 먼저 지웠습니다.

그날 정리한 서비스가 마침 그 모양이었어요. 레코드는 살아 있고 뒤의 로드밸런서에는 타깃이 없어서, 그 주소로 접속하면 오류 응답이 돌아왔습니다. 그런 구간을 정리하러 가서 같은 구간을 새로 만들 이유는 없죠. 순서를 뒤집으면 정확히 그게 됩니다. 그리고 뒤집은 쪽이 더 나빠요. 오류 응답은 적어도 무언가 있다는 신호인데, 가리킬 대상이 사라진 이름은 그 신호조차 주지 않습니다.

컨테이너 클러스터와 용량 공급자. 클러스터에 용량 공급자가 붙어 있으면 클러스터가 안 지워집니다. 그래서 클러스터에서 공급자를 떼고, 공급자를 지우고, 자동 확장 그룹과 시작 템플릿을 지우고, 클러스터를 마지막에 두는 순서로 갔어요. 이 가운데 공급자를 떼는 것부터 시작 템플릿까지 네 단계는 제가 알아낸 게 아니라 알람 파일 주석에 이미 적혀 있던 순서입니다. 이전 세션에서 비슷한 자원을 지운 사람이 기록해뒀고, 그대로 썼습니다.

사용이 끝난 어떤 서비스의 잔재 열한 종을 지운 순서 코드에서 알람 제거 -> apply // 알람 넷이 사라진다 -> DNS 레코드 // 로드밸런서보다 먼저. 죽은 구간을 안 만든다 -> 로드밸런서 // 운영·개발 각 하나 -> 타깃그룹 -> 클러스터에서 용량 공급자 떼기 -> 용량 공급자 -> 자동 확장 그룹 -> 시작 템플릿 -> 컨테이너 클러스터 -> 이미지 저장소 · 배포용 버킷 // 참조하는 것이 다 사라진 뒤 마지막에 로드밸런서 · 클러스터 · 확장 그룹 · 저장소 · 버킷 조회가 전부 0 으로 나오는 것까지 확인한다.

이 목록에서 실제로 돈이 빠지는 건 로드밸런서 둘과 이미지 저장소 둘뿐이에요. 확장 그룹, 클러스터, 시작 템플릿, 타깃그룹은 과금이 없습니다. 그런데도 지운 이유는 6장에 씁니다.

그런데 그 마지막 확인이 하나를 놓쳤다

정리를 끝낸 뒤 별건 목록을 다시 훑다가 알았어요. 컨테이너 클러스터 하나가 그대로 남아 있었습니다. 작업 기록에는 삭제 완료로 적혀 있는 항목이에요.

막힌 이유는 이 장의 규칙 그대로였습니다. 그 클러스터에는 서비스 정의 하나가 실행 수 0 인 채로 활성 상태로 남아 있었어요. 태스크가 하나도 안 도니 자원 목록에서는 비어 보이는데, 정의가 활성이면 클러스터 삭제는 거부됩니다. 참조하는 쪽이 남아 있으면 참조되는 쪽을 지울 수 없다는 그 문장이 여기서도 그대로 걸린 거예요.

더 아픈 쪽은 왜 못 잡았느냐입니다. 마지막 확인을 목록 조회 결과가 0 인지로 했어요. 조회가 0 을 돌려줬으니 완료로 적었고요. 5장에서 다시 쓸 이야기인데, 0 은 정말 없다는 뜻일 수도 있고 내가 잘못된 곳을 봤다는 뜻일 수도 있습니다. 지운 것을 확인할 때도 똑같이 적용돼요. 게다가 이 자원은 과금이 없어서 청구서로도 안 걸립니다. 그래서 완료라고 적은 한 줄이 사실과 어긋난 채로 남았습니다.

그래서 확인 절차에 한 줄이 붙었어요. 지웠다고 기록하기 전에 그 자원을 이름으로 직접 조회해봅니다. 목록 조회가 0 인 것과 그 이름이 없는 것은 다른 확인입니다.

그림 2. 각 지점에서 순서를 뒤집으면 터지는 것이 서로 다르다

4. 관리 주체가 다르면 API 도 다르다

이미지와 스냅샷을 정리할 때 다른 종류의 벽을 만났어요. 오래된 이미지 하나를 등록 해제하려는데 이렇게 거부됐습니다.

AuthFailure: 이 이미지는 백업 서비스가 관리하고 있으며 EC2 API 로 삭제할 수 없습니다. 삭제하려면 백업 서비스의 API 나 CLI 또는 콘솔을 사용하세요. deregister-image -> 거부 delete-recovery-point -> 볼트 이름과 복구지점 식별자를 넘긴다

같은 이미지, 같은 계정, 같은 리전인데 어느 API 로 부르는지에 따라 되고 안 됩니다. 그 이미지는 원래 백업 계획이 만든 복구지점이었고, 백업 서비스가 소유권을 갖고 있었어요. EC2 쪽에서 보면 그냥 이미지처럼 보이는데 실제 관리 주체는 다른 서비스였던 거예요.

재미있는 건 이 오류 이름이 AuthFailure 라는 점입니다. 권한 문제처럼 보이죠. 그래서 여기서 역할에 권한을 더 붙이려는 시도가 나올 수 있어요. 그런데 권한을 아무리 붙여도 안 됩니다. 권한이 없어서 거부된 게 아니라 그 API 의 관할이 아니어서 거부된 거니까요. 다행히 오류 문장이 "백업 API 를 쓰라"고 정확히 알려주고 있었습니다.

그리고 그 백업 계획은 이미 삭제된 상태였어요. 계획이 사라져도 복구지점은 남습니다. 그래서 다섯 개가 잔재로 남아 용량을 차지하고 있었고요. 여기서도 규칙 하나가 나옵니다. 상위 설정을 지우는 것이 그것이 만든 산출물을 지우는 것은 아니에요.

이미지를 지울 때는 두 곳을 본다

이미지 삭제에는 별도의 확인 절차가 필요했습니다. 근거는 런북에 이미 적혀 있었어요. "이미지가 삭제됨 → 시작 템플릿 이전 버전으로 되돌림" 이라는 복구 절차가 문서로 존재합니다. 즉 이건 실제로 났던 사고이고, 그래서 절차가 만들어졌다는 뜻이에요.

시작 템플릿이 참조하는 이미지를 지우면 자동 확장 그룹이 인스턴스를 못 띄웁니다. 그런데 여기서 한 번 더 조심할 게 있어요. 시작 템플릿은 버전을 여러 개 갖습니다. 최신 버전만 보고 판단하면, 롤백해서 이전 버전을 쓰는 순간 없는 이미지를 가리켜요. 그러니까 모든 버전을 봐야 합니다.

🔎 이미지 삭제 대상은 두 목록의 여집합이다
• 목록 하나: 시작 템플릿의 모든 버전이 참조하는 이미지. 최신 버전만 보면 롤백 경로가 끊깁니다
• 목록 둘: 실행 중과 정지 중 인스턴스가 쓰는 이미지. 정지 중을 빼면 다시 켤 때 못 뜹니다
• 둘 다에 없는 것만 삭제 대상이에요
이번에 이 확인이 실제로 하나를 걸렀습니다. 삭제 후보에 올려뒀던 이미지 하나가 실행 중 인스턴스가 쓰고 있어서 마지막에 제외됐어요. 앞선 조회에서는 안 걸렸고 두 번째 목록에서 걸렸습니다. 그리고 남긴 것 중에 하나는 참조가 없는데도 뒀어요. 다른 이미지의 기반으로 보여서 판단을 보류했습니다. 참조 0 이 삭제 가능과 같은 말은 아니에요.

결과적으로 지운 것은 다시 받을 수 있는 공용 이미지의 복사본, 참조가 어디에도 없는 오래된 이미지, 계획이 삭제된 뒤 남은 복구지점 다섯, 그리고 붙어 있지 않은 볼륨 하나였습니다. 자동 보존 정책이 만드는 스냅샷은 손대지 않았어요. 보존 기간이 이미 닷새와 이레로 짧아서 더 줄이면 복구 여지를 깎는 쪽이 됩니다. 여기서는 지울 수 있는 것과 지워도 되는 것이 다릅니다.

5. 청구는 있는데 자원이 안 보였다

이번 정리에서 가장 오래 헤맨 건 삭제가 아니라 찾기였어요.

청구서에 검색 서비스 항목이 잡혀 있었습니다. 그런데 그 서비스의 도메인 목록을 조회하니 0개가 나왔어요. 리전을 잘못 봤나 싶어 다른 리전도 뒤졌는데 거기도 없었습니다. 청구는 계속 붙는데 자원이 없는 상태였죠.

답은 조회 API 를 바꾸는 것이었어요. 그 서비스에는 기존 도메인 방식과 서버리스 방식이 따로 있고, 서버리스 자원은 기존 도메인 조회 API 에 안 잡힙니다. 서버리스 컬렉션 조회로 넘어가서야 세 개가 나왔습니다.

💡 청구는 있는데 자원이 안 보일 때
• 먼저 다른 리전을 봅니다. 여기까지는 대부분 합니다
• 그래도 없으면 같은 서비스의 다른 배포 형태를 봅니다. 서버리스 계열은 조회 API 가 아예 다른 경우가 있어요
• 조회 결과 0 을 "없다"로 결론내기 전에 그 값이 나올 수 없는 조건을 하나 붙입니다. 3편에서 적은 규칙인데, 여기서는 청구가 붙고 있다는 사실이 그 조건이었어요
0 은 두 가지를 뜻할 수 있습니다. 정말 없거나, 내가 잘못된 곳을 봤거나. 이 둘을 구분하지 않으면 청구 항목 하나가 계속 미제로 남아요.

셋 중 하나는 아무도 접근할 수 없었다

나온 컬렉션은 셋이었는데 상위 지식 베이스는 둘이었어요. 하나가 고아였습니다. 상위가 삭제되면서 컬렉션만 남은 거예요. 그 상태로 열한 달 동안 과금됐습니다.

이게 왜 특히 나쁘냐면, 고아 컬렉션은 누구도 접근할 수 없습니다. 상위를 통해서만 쓰는 자원인데 상위가 없으니까요. 쓸 수 없는 상태로 요금만 나가고 있었고, 그 열한 달 동안 아무도 그 사실을 눈치채지 못했어요. 눈치챌 방법이 없었기도 해요. 자원 목록에 나타나지 않는 조회 API 를 쓰고 있었으니까요.

하나만 남겨도 절감이 없는 과금 구조

그럼 셋 중에 남길 것을 고민할 수 있죠. 그런데 이 서비스는 그 고민이 무의미했어요. 과금 단위가 컬렉션 개수가 아닙니다. 처리 단위 기준으로 매기고, 그 최소 단위가 계정과 리전 수준에서 유지됩니다.

그래서 셋 중 하나만 남겨도 최소 단위는 그대로예요. 컬렉션을 둘 지워도 청구액은 거의 그대로 나옵니다. 전부 지워야 전액이 빠집니다.

그래서 판단이 "셋 중 몇 개를 지울까"에서 "셋을 다 지울 수 있나"로 바뀌었어요. 부분 정리는 보통 안전한 선택입니다. 절반만 지우면 위험도 절반이니까요. 그런데 이 과금 구조에서는 부분 정리가 위험만 절반이고 절감은 0 입니다. 다 지울 수 없으면 그 항목은 절감 후보에서 아예 빠지는 쪽이 맞아요.

금액이 거의 0 이라는 것은 미사용의 증거가 아니었다

삭제 근거를 세우다가 한 번 성급했습니다. 처음에 "상위 모델 사용료가 거의 0 이니 미사용"이라고 단정했어요. 그럴듯하죠. 안 쓰니까 요금이 안 나온다고 읽는 겁니다.

그런데 이건 불완전한 근거였어요. 검색용 조회 API 는 상위 모델 요금을 발생시키지 않습니다. 즉 이런 구성이 가능해요.

검색만 하고 생성은 다른 모델로 하는 구성 앱 -> 지식 베이스 조회 API (검색 결과를 받는다) 상위 모델 요금 0 앱 -> 다른 모델 (그 결과로 답을 만든다) 다른 항목으로 청구 => 상위 모델 요금이 0 이면서 지식 베이스를 매일 쓰고 있을 수 있다. "요금 0 = 미사용" 이 성립하지 않는다.

그래서 금액으로 확정하지 않았어요. 사용 여부를 사람에게 확인한 뒤 진행했습니다. 조회를 더 해서 해결할 문제가 아니었어요. 요금 지표는 아무리 정확하게 봐도 이 구성을 구별해주지 않으니까요.

여기서 남은 규칙이 하나 있습니다. 어떤 금액이 0 이라는 사실이 무엇을 배제하는지 먼저 적어봅니다. 이번 경우 상위 모델 요금 0 이 배제하는 것은 "그 모델로 생성까지 한다"뿐이었어요. "이 지식 베이스를 안 쓴다"는 배제하지 못합니다. 그 차이를 적어보면 근거가 부족한 게 바로 보여요.

6. 과금이 없는 자원을 지운 이유

3장 목록에 과금 없는 자원이 여럿 있었어요. 확장 그룹, 시작 템플릿, 컨테이너 클러스터, 타깃그룹입니다. 절감액에 한 푼도 기여하지 않아요. 그런데 지웠습니다.

이유는 1장에서 나왔어요. 로드밸런서를 지우려다 ResourceInUse 를 받았을 때, 저는 그 타깃그룹이 무엇인지 조사해야 했습니다. 이름에 상위 유형을 시사하는 문자열이 들어 있어서 그 상위가 어디 있는지 찾았고, 연결 목록을 열어보고 나서야 이미 삭제됐고 타깃그룹만 남았다는 걸 알았어요.

그 조사에 든 시간은 길지 않습니다. 조회 두세 번이에요. 문제는 그 조사를 하기 전까지는 얼마나 걸릴지 알 수 없다는 점입니다. 상위가 살아 있을 가능성이 있으니 확인해야 하고, 확인해보니 없었던 거죠. 그리고 그 판단이 끝나기 전에는 로드밸런서를 지울 수 없었습니다.

그래서 상위가 없는 타깃그룹은 다음 사람에게 같은 조사를 시킵니다. 과금이 없으니 청구서에는 안 보이고, 자원 목록에는 계속 나와요. 다음 사람은 그것이 진짜 유휴인지 판단하려면 상위를 찾아봐야 하고요. 이름에 상위 유형이 적혀 있으면 더 그렇습니다. 이름이 있었던 것을 시사하니까요.

정리하는 이유는 둘이다 과금이 있는 자원 지우면 청구서가 줄어든다 과금이 없는 자원 지우면 다음 사람의 조사 시간이 줄어든다 두 번째를 안 하면 계정에 "정체를 조사해야 하는 것" 이 계속 쌓인다. 그 재고는 청구서에 안 나오고, 다음 정리 작업의 비용으로 나온다.

같은 이유로 남긴 것도 있어요. 어떤 데이터 분석 플랫폼이 쓰던 네트워크 구성에서 과금되는 것만 지우고 가상 네트워크와 서브넷, 라우팅, 피어링은 남겼습니다. 이름에 실험을 뜻하는 접두사가 붙어 있어서 처음에는 실험 잔재로 봤는데 아니었고, 그 이야기는 6편에서 다뤘어요. 과금이 없다는 점은 타깃그룹과 같은데 판단이 반대예요. 차이는 그것이 무엇인지 이미 확정됐고, 다시 쓸 경로가 문서에 적혀 있다는 점입니다. 다음 사람이 조사할 필요가 없고, 되살릴 때는 그 구성이 남아 있는 편이 훨씬 빨라요.

그러니까 기준은 "과금이 있나"가 아니에요. 다음 사람이 이걸 보고 조사를 시작할까입니다. 조사를 유발하면 지우고, 조사가 끝난 상태로 기록과 함께 남길 수 있으면 남깁니다.

7. 삭제는 참조 그래프를 역순으로 걷는 일이다

하루를 정리하면서 남은 게 이거예요. 삭제는 자원 하나를 지우는 일이 아닙니다. 자원 하나에는 그것을 가리키는 것들이 붙어 있고, 그것을 지우려면 가리키는 것부터 걷어내야 해요. 그러니까 삭제는 참조 그래프를 역순으로 걷는 일입니다.

그 그래프에는 세 층이 있었어요.

참조 그래프의 세 층 코드와 감시 알람 정의 · 데이터소스 조회 · 커버리지 검사 목록 => 실물을 참조한다. 그래서 가장 먼저 걷어낸다 사용자 경로 DNS 레코드 => 실물을 참조한다. 죽은 구간을 만들지 않으려면 먼저 지운다 자원 사이 타깃그룹 -> 로드밸런서 · 지식 베이스 -> 컬렉션 클러스터 -> 용량 공급자 · 시작 템플릿 -> 이미지 => 참조하는 쪽부터. 안 지키면 API 가 거부한다

첫 층을 사람들이 잘 빠뜨립니다. 알람과 코드도 실물을 참조하는 쪽이라는 감각이 잘 안 생겨요. 알람은 자원이 아니라 부속물처럼 느껴지니까요. 그런데 데이터소스로 실물을 조회하는 코드는 참조가 끊기면 그 스택 전체를 멈추고, 결측을 위반으로 보는 알람은 대상이 사라지면 끌 수 없는 경보가 됩니다. 참조가 끊길 때의 파괴력으로 보면 가장 강하게 참조하는 층이에요.

그리고 "역순으로 걷는다"는 말에 한 가지가 빠져 있어요. 참조를 떼는 것과 자원을 지우는 것은 다른 동작입니다. 클러스터와 용량 공급자가 그랬습니다. 참조하는 쪽이 클러스터인데 클러스터는 마지막까지 남겨야 하는 자원이니, 삭제 순서를 짜는 게 아니라 살아 있는 쪽에서 참조를 먼저 떼는 단계가 중간에 끼어들어요. 그러니까 순서를 정하는 대상은 자원이 아니라 참조입니다. 참조를 끊는 순서가 먼저 정해지고, 자원 삭제는 그 결과로 가능해져요.

그리고 오류 메시지를 읽는 규칙 하나가 남았습니다. 삭제 거부는 대부분 "쓰이고 있다"가 아니라 "순서가 틀렸다"를 말합니다. ResourceInUse 도, 붙어 있는 방화벽 규칙 묶음의 거부도, 다른 서비스가 관리한다는 AuthFailure 도 전부 그래요. 마지막 것은 순서가 아니라 문법이 틀렸다는 쪽이지만, "이 자원은 쓰이고 있다"가 아니라는 점은 같습니다.

이 규칙이 왜 실용적이냐면, 거부를 받았을 때 다음 행동이 정해지기 때문이에요. "쓰이고 있다"로 읽으면 다음 행동은 조사를 다시 하는 것이고 결론은 보통 보류입니다. "순서가 틀렸다"로 읽으면 다음 행동은 참조하는 쪽을 열어보는 것이고, 그러면 몇 분 안에 답이 나와요. 그 자원이 정말 쓰이고 있으면 참조하는 쪽에 살아 있는 상위가 있을 테고, 껍데기라면 비어 있을 테니까요.

그러니까 두 해석 중에 하나를 고르는 게 아닙니다. 순서 제약으로 먼저 읽고, 참조하는 쪽을 열어서 확인합니다. 확인이 판정을 대신하니까요.

✍ 오늘의 요약
삭제 거부는 대부분 "쓰이고 있다" 가 아니라 "순서가 틀렸다" 를 말한다. 상위가 이미 사라진 고아 타깃그룹에 등록되어 있다는 이유로 로드밸런서 삭제가 거부됐고, 그것을 사용 중 신호로 읽으면 그 자리에서 잘못 멈춘다. 작업 문서 비고에 그 선행 조건이 이미 적혀 있었는데도 순서를 지키지 않았고, 그 한 줄이 설계 의도인지 API 제약인지에 따라 판단이 정반대로 갈렸다. 그래서 비고에 적힌 선행 조건은 그 자리에서 이유를 확인한다.

순서의 가장 앞은 실물이 아니라 알람과 코드다. 데이터소스로 실물을 조회하는 스택은 실물이 사라지면 모든 plan 이 막히고, 결측을 위반으로 취급하는 알람은 대상이 사라지면 아무도 끌 수 없는 경보가 된다. 그 다음이 DNS 이고, 그 다음이 참조하는 쪽이고, 마지막이 참조되던 쪽이다. 관리 주체가 다르면 API 도 다르므로 권한을 더 붙이는 것이 답이 아닐 때가 있고, 이미지는 시작 템플릿의 모든 버전과 실행·정지 인스턴스 두 곳에 다 없는 것만 지울 수 있다. 과금이 개수에 비례하지 않는 자원은 전부 지워야 전액이 빠지고, 요금이 거의 0 이라는 사실은 미사용의 증거가 되지 못한다. 그리고 과금이 없는 고아 자원을 함께 지우는 이유는 절감이 아니라 다음 사람의 조사 시간이다. 그런데 그렇게 지운 것 중 하나는 실제로 남아 있었다. 실행 수 0 인 서비스 정의가 활성으로 남아 클러스터 삭제가 거부됐는데, 마지막 확인을 목록 조회가 0 인지로만 해서 완료로 적혔다. 목록 조회가 0 인 것과 그 이름이 없는 것은 다른 확인이다. 삭제는 자원 하나를 지우는 일이 아니라 참조 그래프를 역순으로 걷는 일이다.
