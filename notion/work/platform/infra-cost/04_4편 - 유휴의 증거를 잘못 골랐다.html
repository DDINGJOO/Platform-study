로드밸런서 목록을 요금 기준으로 정렬해놓고 세어봤어요. 38개 중 33개가 사용량 단위 요금이 0 이었습니다. 청구액이 최소 요금과 정확히 같다는 뜻이에요.

33개가 후보처럼 보였습니다. 실제로 지운 것은 4개였어요.

이 글은 "안 쓰는 것 같다"를 "안 쓴다"로 읽었다가 되돌린 기록입니다. 유휴 판정에 증거로 쓸 수 있는 0 과 쓸 수 없는 0 이 갈리는 자리를 정리했어요.

1. 최소 요금과 같다는 것은 유휴가 아니다

로드밸런서 요금은 두 조각입니다. 켜져 있는 시간에 붙는 요금과, 처리한 양에 붙는 요금이에요. 뒤쪽 단위가 LCU 인데, 이게 0 이면 청구액이 앞쪽만 남아 최소 요금과 같아집니다.

그래서 제가 읽은 문장은 "아무도 안 쓴다"였어요. 그런데 LCU 가 실제로 말하는 것은 처리량이 과금 최소 단위 아래라는 것뿐입니다. 요청이 적은 것과 아무도 쓰지 않는 것은 다릅니다.

확실한 신호는 하나가 아니라 둘이었어요. 타깃 0 과 요청 0 을 함께 만족하는 경우입니다.

로드밸런서 38개 사용량 단위 요금 0 33개 "청구액이 최소 요금과 같다" 타깃 0 · 요청 0 4개 -> 실제 삭제 33 - 4 = 29 는 "요청이 적은 것" 이었다
💡 0 하나로는 판정이 안 되는 이유
두 신호는 각각 다른 것을 놓칩니다.

• 타깃 0 인데 요청이 있다 : 누군가 계속 부르고 있고 뒤가 비어 있는 상태예요. 유휴가 아니라 고장이거나 배포 중일 수 있습니다
• 타깃은 있는데 요청 0 : 경로는 살아 있고 트래픽만 없는 상태예요. 조회 창 밖에 트래픽이 있을 수 있습니다
• 둘 다 0 : 부를 사람도 없고 요청이 와도 갈 곳이 없습니다

둘 다 0 일 때만 "지금 안 쓴다"와 "앞으로도 못 쓴다"가 동시에 성립해요.

2. 30일 창은 부족하다

어떤 네트워크 로드밸런서를 30일로 봤습니다. ActiveFlowCount, NewFlowCount, ProcessedBytes 가 전부 정확하게 0 이었어요. 앞 장의 기준으로도 통과입니다.

90일로 늘렸습니다. 서로 다른 두 날에 연결이 각 1건 있었어요.

조회 창 30일 ActiveFlowCount 0 NewFlowCount 0 ProcessedBytes 0 전부 정확하게 0 조회 창 90일 연결 1건 + 연결 1건 서로 다른 두 날

30일 창의 0 은 "없다"가 아니라 "30일 안에는 없었다"입니다. 드물게 쓰이는 자산은 30일 창에서 사라져요. 분기 1회 배치, 대체 경로, 재해가 났을 때만 쓰는 경로가 그렇습니다. 그리고 그런 용도일수록 평소에 조용합니다.

이 자산이 정확히 그 모양이었어요. 뒤에 회사 주요 웹사이트를 서비스하는 다른 로드밸런서가 붙어 있고, 90일 요청이 1천만 건을 넘었습니다. 이 네트워크 로드밸런서는 그 앞단의 고정 IP 경로였고, DNS 레코드가 없어서 IP 로 직접 접속하는 구조였어요.

그러면 되돌림 비용이 달라집니다. 지우면 같은 IP 를 다시 확보할 수 없어요. 재생성이 몇 분인 자산과, 다시 만들어도 같은 것이 나오지 않는 자산은 같은 근거로 판단할 수 없습니다.

그래서 규칙을 하나 만들었어요. 되돌리기 어려울수록 조회 창을 넓힌다. 창의 길이는 자산의 성질이 아니라 실수했을 때 물러설 수 있는지가 정합니다.

그런데 창을 넓히는 데는 대가가 있어요. 조회 창이 길어지면 지표를 합치는 최소 간격도 함께 커집니다. 90일을 한 번에 보면 데이터가 시간 단위 이상으로 합쳐져 나와요. 여기서 통계를 잘못 고르면 넓힌 창이 오히려 증거를 지웁니다. 하루 한 건짜리 연결은 평균으로 보면 0 에 가깝게 희석돼요. 이번에 두 건이 보인 것은 합계와 최댓값으로 봤기 때문입니다. 그러니 규칙은 반쪽만 적으면 안 됩니다. 창을 넓힐 때는 통계도 같이 바꿔야 해요. 넓힌 창에 평균을 씌우면 30일의 0 을 90일의 0 으로 바꾸기만 합니다.

그림 1. 조회 창의 길이는 자산이 아니라 되돌림 비용이 정한다

3. 지표가 발행되지 않은 것과 값이 0인 것은 다르다

이게 이 글에서 제일 실용적인 구분이라고 생각해요.

NAT 게이트웨이 두 개를 지웠습니다. NAT 는 라우팅 테이블에 등록하는 것 말고 연결 수단이 없어요. 그러니 라우팅 참조가 0 이면 논리적으로 트래픽이 있을 수 없습니다. 근거가 충분해 보였는데, 제가 못 본 경로가 있을 가능성을 배제하려고 30일 트래픽 0 을 함께 확인했어요.

그때 확인한 것이 정확히 무엇이었는지가 중요합니다. "지표 없음"이 아니라 "30일 내내 0 을 발행"이었어요.

라우팅 테이블 참조 없음 BytesOutToDestination 30일 합계 0 · 일최대 0 <- 발행된 0 BytesInFromSource 30일 합계 0 · 일최대 0 <- 발행된 0 ActiveConnectionCount 데이터 없음 <- 증거로 쓸 수 없다 Transit Gateway 없음 우회 경로 배제

같은 표에 두 종류의 0 이 섞여 있습니다. 지표 부재는 감시가 안 붙었다는 뜻으로도 읽히고 발행된 0 만이 트래픽 부재의 직접 증거예요.

이 구분이 없으면 조회 실패와 "아무 일도 없었다"가 같은 화면으로 보입니다. 그 함정은 앞 편에서 두 번 밟아 따로 적었으니, 여기서는 다른 쪽을 봐요. 모든 지표에서 "발행된 0" 을 기대할 수 있는 것은 아니라는 점입니다.

바이트나 연결 수처럼 상태를 주기적으로 보고하는 지표는 값이 0 이어도 0 을 발행합니다. 그래서 위 표의 두 줄이 증거가 됐어요. 반대로 사건이 있을 때만 찍히는 지표는 사건이 없으면 데이터 포인트 자체를 남기지 않습니다. 요청 수가 그렇습니다. 요청이 없는 로드밸런서는 요청 수를 0 으로 발행하는 게 아니라 아무것도 발행하지 않아요. 그런 자원에 "발행된 0 을 가져와라"라고 요구하면 영원히 충족되지 않습니다.

그러면 판정이 막히나요. 아니에요. 발행된 0 을 얻을 수 없는 자원은 참조 쪽을 여러 겹으로 닫아서 판정합니다. 지표 한 줄을 참조 확인 여러 줄로 갈아 끼우는 거예요. 5장이 그 방법을 쓴 자리입니다. 1장에서 요청 0 하나로 판정하지 않고 타깃 0 을 함께 요구한 이유도 여기에 있어요. 요청 쪽의 0 은 그 자체로 부재의 증거가 못 되기 때문입니다.

그림 2. 측정된 0 만 증거이고, 그 하나로도 판정은 끝나지 않는다

4. 주석의 "아직 없다"가 전제를 숨긴다

그 NAT 의 알람 코드에 주석이 하나 있었어요. 지우기 전에 읽었는데, 답이 절반쯤 적혀 있었습니다.

# 이 NAT 는 아직 이 지표를 발행한 적이 없다. 포트 할당 활동이 생기면 # 자동으로 감시가 시작된다. 그 전까지 이 알람은 데이터를 받지 못한다.

사실 관계는 맞아요. 지표가 없는 것도 사실이고 활동이 생기면 감시가 붙는 것도 사실입니다. 문제는 현상만 적고 원인을 적지 않았다는 것이었어요.

발행한 적이 없던 이유가 라우팅 부재였습니다. 라우팅에 붙어 있지 않으니 포트를 할당할 일이 없고 그래서 활동이 생길 일이 없었어요. 그러니까 이 주석이 실제로 묘사한 것은 잠깐 조용한 자산이 아니라 구조적으로 트래픽이 도달할 수 없는 자산이었습니다.

"아직 없다"는 "앞으로 생길 것"을 전제합니다. 그 전제가 틀리면 문장 전체가 뒤집혀요. 유휴 자산이 정상 대기 상태로 위장되고 알람이 데이터를 못 받는 것도 정상으로 읽힙니다. 그래서 주석을 원인까지 적도록 고쳤어요.

# 이 NAT 는 라우팅 테이블 어디에서도 참조되지 않아 30일간 0 바이트를 # 처리했다. 지표를 발행한 적이 없는 것은 트래픽이 없어서다.
⚠️ "아직"이 들어간 문장을 만나면
"아직"은 시간에 대한 서술처럼 보이지만 실제로는 미래에 대한 주장입니다. 그 자리에서 질문 하나를 붙여보면 갈립니다.

• 무엇이 생기면 이 값이 0 을 벗어나나요?
• 그 조건이 발생할 수 있는 상태인가요?

두 번째에 답을 못 하면 "아직"이 아니라 "앞으로도"입니다. 주석에 현상만 적으면 다음 사람이 그 판단을 처음부터 다시 하게 돼요.

5. 보류 판단도 실측으로 뒤집는다

반대 방향의 실수도 있었습니다. 개발용 로드밸런서 하나가 확정 목록에 있었어요. 근거는 "타깃 0, 30일 요청 0" 이라 앞 장의 기준을 통과합니다. 그런데 세 가지가 걸렸어요.

첫째, 이름이 외부 연동을 시사했습니다. 둘째, 비고에 선행 조건이 붙어 있었어요. 누군가 경로를 의도적으로 설계했다는 뜻으로 읽혔습니다. 셋째, 관련 이미지 저장소는 남기라는 판단이 이미 있었어요. 다시 배포할 여지가 있다면 이 로드밸런서가 필요해집니다.

이 계정에는 외부 파트너가 쓰기 때문에 남긴 자산이 이미 있었습니다. 그러니 상시 요청 0 이 정상인 경로일 가능성을 배제할 수 없었어요. 그래서 삭제를 멈추고 진입 경로를 전부 확인했습니다.

이 LB 를 타깃으로 가진 타깃그룹 1개, 그런데 상위 LB 목록이 비어 있다 그 타깃그룹을 쓰는 상위 LB 없음 (이미 삭제됨, 타깃그룹만 고아) DNS 별칭 레코드 없음 (호스팅 영역 전수 조회) 리스너 평문 1개 · 인증서 없음 리스너 기본 액션의 타깃그룹 없음 -> 요청이 와도 갈 곳이 없다 알람 (수동 생성 포함) 없음 코드 참조 없음 RequestCount 30일 데이터 없음 -> 발행된 0 이 아니다

결과는 상위 로드밸런서가 이미 삭제돼 타깃그룹만 고아로 남은 상태였어요. 진입 지점이 없고 들어와도 기본 액션이 가리키는 곳이 없습니다. 요청이 없던 것은 조용한 파트너 때문이 아니라 요청이 성립할 수 없는 구성이었던 거예요.

맨 아래 줄이 앞 장에서 말한 그 경우입니다. 요청 수는 요청이 없으면 발행되지 않으니 여기서는 발행된 0 을 얻을 방법이 없었어요. 그래서 그 줄은 근거에서 빼고 위의 일곱 줄로 판정했습니다. 지표가 못 해준 일을 참조 확인 일곱 개가 대신한 거예요.

우려 셋이 다 해소됐습니다. 이름이 시사한 외부 연동은 도달 경로가 없어서 성립하지 않아요. 비고의 선행 조건도 확인해보니 도달 경로가 있다는 뜻이 아니었습니다. 이미지 저장소를 남기는 판단과도 충돌하지 않아요. 이미지는 그대로 두고 다시 배포할 때 로드밸런서만 새로 붙이면 됩니다.

이름과 비고에서 온 우려는 이름과 비고로 풀리지 않고 실측으로 풀립니다. 앞 장들이 "0 을 보고 지우지 말라"였다면, 이 장은 반대예요. 불안을 근거로 남기지도 말라는 것입니다. 근거 없이 남긴 자산은 다음 사람이 같은 조사를 처음부터 다시 합니다.

6. 같은 영역에 있다는 것이 자원을 공유한다는 뜻이 아니다

마지막으로 하나 더 있었어요. 삭제 대상 NAT 와 같은 가용영역에 운영 인스턴스가 돌고 있었습니다.

여기서 두 방향으로 틀릴 수 있어요. 같은 영역이니 위험하다고 보고 멈추거나, 무관하다고 보고 그냥 진행합니다. 둘 다 같은 실수예요. 라우팅 테이블을 안 봤다는 것입니다.

같은 영역 운영 인스턴스가 돌고 있다 삭제 대상 NAT 도 같은 영역 라우팅 테이블 기본 경로 -> 다른 영역 NAT 즉 삭제와 무관하다

그 인스턴스의 라우팅은 다른 영역의 NAT 를 가리켰습니다. 같은 영역의 NAT 를 쓰지 않는 구성이었어요. 가용영역은 자원의 위치이고 어디로 나가는지는 라우팅이 정합니다. 위치가 같다는 것은 관계가 있다는 증거가 아닙니다.

정리하면, 이번에 제가 증거로 쓰려다 실패한 것들은 전부 같은 모양이었어요. 요금이 최소치와 같다는 것, 30일 창이 비었다는 것, 지표가 안 보인다는 것, 같은 영역에 있다는 것. 넷 다 유휴와 상관관계는 있지만 유휴를 뜻하지는 않는 신호였습니다.

그래서 유휴 판정은 하나의 지표로 나지 않아요. 참조 부재와 트래픽 부재를 함께 보고, 조회 창의 길이를 되돌림 비용에 맞춰 정해야 합니다. 앞의 것은 판정의 폭이고, 뒤의 것은 판정의 깊이예요.

✍️ 오늘의 요약
로드밸런서 38개 중 33개가 사용량 단위 요금이 0 이었지만 지울 수 있었던 것은 4개였습니다. 요청이 적은 것과 아무도 쓰지 않는 것은 다르고, 그 둘을 가르는 것은 타깃 0 과 요청 0 을 함께 보는 일이었어요.

0 에도 종류가 있었습니다. 지표가 발행되지 않은 것은 감시 미설정으로도 읽히고 30일 내내 발행된 0 만이 트래픽 부재의 직접 증거였어요. 그리고 모든 지표가 0 을 발행하지는 않습니다. 요청 수처럼 사건이 있을 때만 찍히는 지표는 요청이 없으면 아무것도 남기지 않으니, 그런 자원은 지표 대신 참조 쪽을 여러 겹으로 닫아서 판정했습니다. 알람 주석의 "아직 발행한 적이 없다"는 현상만 적고 원인을 적지 않아서 라우팅에서 떨어진 자산을 정상 대기 상태로 보이게 만들고 있었습니다.

반대로 이름과 비고에서 온 불안 때문에 보류하려던 자산은, 진입 경로를 전부 훑어보니 요청이 성립할 수 없는 구성이었어요. 유휴는 하나의 지표가 알려주지 않습니다. 참조 부재와 트래픽 부재를 함께 보고, 조회 창의 길이는 되돌림 비용이 정합니다. 창을 넓혔으면 통계도 같이 바꿔야 해요. 넓힌 창에 평균을 씌우면 짧은 사용이 그대로 희석됩니다.
