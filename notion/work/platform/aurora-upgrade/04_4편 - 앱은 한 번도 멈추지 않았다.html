📚 Aurora 5.7 → 8.0, 4부작
1편 · 확장 지원료가 마감을 만들었다
2편 · 되돌릴 수 있는 단계를 쌓았다
3편 · 6분 만에 넘어갔다
4편 · 앱은 한 번도 멈추지 않았다 ← 지금 이 글

같은 작업을 하루 뒤에 한 번 더 했습니다. 이번엔 다른 클러스터였어요.

결과가 달라졌습니다. DB 쓰기 중단 약 5초, 앱 정지 0회입니다. 1초 간격 폴러가 1,195번 찔러서 200이 아닌 응답이 0건이었어요.

그런데 이 글에서 하고 싶은 이야기는 5초가 아닙니다. 설계 문서에 "앱 정지"가 필수 단계로 적혀 있었는데, 그걸 지우고도 안전했던 이유와, 그 과정에서 발견한 되돌릴 수단이 함정으로 돌아가는 길이었다는 사실입니다.

1. 제약이 사라져서 할 수 있게 됐다

1편에서 Blue/Green 을 한 번 기각했었습니다. 최대 근거가 "공유 파라미터그룹을 건드리면 다른 팀 DB 가 영향을 받는다"였어요. 그 근거가 사실이 아니었다는 게 1편의 내용이고요.

이번엔 근거 자체가 없어졌습니다. 3편에서 앞선 클러스터를 8.0 으로 옮기면서 그 공유 파라미터그룹을 쓰는 클러스터가 하나만 남았기 때문입니다. 공유 그룹인데 사용자가 하나면 사실상 전용 그룹이에요. 앞선 작업의 계획을 지배했던 제약이 그 작업 때문에 사라진 겁니다.

돈은 그대로 새고 있었습니다.

확장 지원료 4대 × 2 vCPU × $0.120/vCPU-hr × 730h = $700.80 / 월 2027-03-01 부터 단가 2배 = $1,401.60 / 월

이 클러스터를 넘기면 남는 5.7 은 하나입니다. 그건 아직 전용 파라미터그룹조차 없어서 절차가 한 단계 더 붙어요.

2. 절차에 "앱 정지"가 필수로 적혀 있었다

설계 문서가 정한 순서는 이랬습니다.

... 4. Blue/Green 생성 → 검증 5. 알람 3종 추가 6. 앱 정지 → 스위치오버 → 기동 ← 필수라고 적어둔 단계 7. 관측 후 옛 클러스터 삭제

왜 정지가 필수였냐면, 운영 JDBC 접속 URL 이 호스트를 두 개 나열한 형태였고 두 번째가 읽기 전용 엔드포인트였기 때문입니다.

jdbc:mysql://<클러스터>.cluster-... ← 쓰기 <클러스터>.cluster-ro-... ← 읽기 전용 /<DB>?autoReconnect=true

스위치오버 순간에 첫 호스트가 끊기면 드라이버가 두 번째 호스트로 넘어갑니다. 그리고 autoReconnect=true 라서 넘어간 상태에 그대로 머물러요. 그러면 쓰기가 전부 읽기 전용 오류로 실패하고, 앱을 재기동하기 전까지 풀리지 않습니다.

앞선 클러스터에는 없던 위험이었습니다. 그쪽 URL 은 호스트가 하나였으니까요.

그림 1. 호스트를 두 개 적어둔 것이 전환 순간에 함정이 된다

3. 정지 대신 순서를 바꿨다

정지가 필요한 이유는 함정이 앱 안에 있다는 것이었습니다. 그러면 앱을 멈추는 대신 함정을 먼저 없애면 됩니다.

호스트 파일의 compose 설정에 환경변수 하나를 덮어썼어요. 스프링의 완화된 이름 규칙 덕분에 환경변수가 이미지 안 설정 파일을 이깁니다.

SPRING_DATASOURCE_URL=jdbc:mysql://<단일 호스트>/<DB>?... ↑ 읽기 전용 엔드포인트를 목록에서 뺐다

그다음 같은 이미지로 무중단 배포를 한 번 돌려서, 돌고 있는 앱을 단일 호스트 URL 판으로 갈아끼웠습니다. 앱이 하는 일은 하나도 안 바뀌고 읽기 전용으로 넘어갈 경로만 사라져요.

그리고 나서 전환했습니다.

1. 앱 배포 (단일 호스트 URL) → 무중단. DB 는 아직 5.7 2. 스위치오버 → 커넥션이 끊기고 writer 로 재연결

순서가 전부입니다. 반대로 하면 함정이 그대로 남은 앱이 전환을 맞습니다.

그림 2. 두 작업의 순서를 바꾸는 것만으로 필수 단계가 사라진다

고친 범위도 좁았습니다. 저장소도 이미지도 건드리지 않았어요. 호스트의 compose 설정 한 곳만 바꿨습니다.

💡 전환이 끝난 뒤에도 되돌리지 않았다
단일 호스트 URL 을 임시 조치로 쓰고 원래대로 돌릴 수도 있었어요. 그렇게 하지 않고 기본값 자체를 단일 호스트로 바꿨습니다.

이 함정이 스위치오버에서만 발동하는 게 아니기 때문입니다. writer 페일오버나 순간적인 단절에서도 똑같이 발동해요. 그때는 전환 작업 중이 아니니 아무도 원인을 짐작하지 못합니다.

전환 때문에 찾은 문제였지만 전환에만 있던 문제가 아니었던 거죠.

4. 32분과 5초

실측값이 예상과 어긋난 곳이 하나 있었습니다.

앞선 클러스터 1.30 GiB → Blue/Green 생성 53분 이번 클러스터 48.25 GiB → Blue/Green 생성 32분

데이터가 37배 큰데 생성은 더 빨랐어요. 생성 시간을 지배하는 건 데이터 크기가 아니라 인스턴스를 띄우는 고정비였습니다. 그리고 이 32분은 운영에 영향이 없어요. 그동안 기존 클러스터가 계속 서비스하니까요.

실제 중단 창은 스위치오버 하나뿐이고 그게 쓰기 약 5초였습니다.

검증은 두 갈래로 나눴습니다. 하나는 스키마를 비교하는 것, 하나는 운영 이미지를 실제로 붙여보는 것이었어요.

스키마 비교 (기존 vs 새 클러스터) 테이블 수 104 = 104 테이블 콜레이션 general_ci 101 / unicode_ci 3 양쪽 동일 컬럼 콜레이션 general_ci 541 / unicode_ci 8 양쪽 동일 VIEW · 함수 · 트리거 · 이벤트 전부 0 = 0 달라진 값 sql_mode 에서 8.0 이 없앤 항목 하나가 빠짐

여기서 설계 문서의 예상이 하나 틀렸습니다. 개발 환경 도커로 미리 실험할 때 콜레이션이 8.0 기본값으로 갈려서 기존 컬럼과 비교할 때 오류가 나는 함정을 발견했었는데, 실물에서는 재현되지 않았어요.

🎯 같은 함정이 방식에 따라 있고 없다
Blue/Green 업그레이드는 기존 테이블의 콜레이션을 바꾸지 않습니다. 그래서 이미 있는 테이블은 그대로 넘어와요.

그 함정은 전환 후에 새로 만드는 테이블에서만 생깁니다. 즉 이건 이관 작업으로 막을 문제가 아니라 앞으로의 DDL 규약으로 막을 문제였습니다.

개발 환경에서 찾은 함정이 실물에 없다는 걸 확인한 것도 소득이에요. 없는 위험을 대비 목록에 남겨두면 정말 있는 위험이 그 안에 섞여서 안 보입니다.

두 번째 검증이 더 마음에 들었습니다. 운영 이미지를 그대로 새 클러스터에 붙여서 기동했어요. 다만 nginx 에 연결하지 않은 로컬 포트로 띄워서 운영 트래픽과 완전히 격리했습니다.

스키마 검증 오류 0 기동 실패 0 기동 시간 기존 32.596초 → 새 클러스터 32.36초 (회귀 없음) 드라이버 의도한 드라이버가 잡힌 것을 로그로 확인

부수적으로 안전했던 이유가 하나 있었어요. 새 클러스터가 아직 읽기 전용이라 분산 락을 잡을 수 없었습니다. 그래서 스케줄 작업이 물리적으로 돌 수 없는 상태였습니다. 격리를 의도해서 만든 게 아니라 상태 때문에 얻은 격리였고, 그래서 다음에도 같은 순서라면 같은 보호를 받습니다.

5. 되돌릴 수단이 함정으로 돌아가는 길이었다

이 글에서 제일 아찔했던 대목입니다.

롤백 스크립트를 읽어봤어요. 컨테이너를 되살리는 방식이 새로 만드는 것이 아니라 멈춰둔 것을 다시 시작하는 것이었습니다.

그러면 이미 만들어져 있던 컨테이너는 그때의 환경으로 부활합니다. 대기 쪽 컨테이너는 이틀 전에 기동된 것이었고, 거기엔 오늘 추가한 그 환경변수가 없었어요.

롤백을 누르면 → 이틀 전 컨테이너가 그대로 다시 시작 → 환경변수 없음 → 호스트 두 개짜리 URL 로 복귀 ← 방금 없앤 함정 → 그런데 DB 는 이미 8.0 으로 넘어간 상태

즉 문제가 생겼을 때 누르라고 만들어둔 것이 문제를 다시 만드는 경로였습니다.

조치는 단순했어요. 대기 쪽과 활성 쪽이 완전히 같은 이미지였으니 대기 컨테이너는 되돌릴 가치가 0 이고 위험만 있었습니다. 그래서 지웠습니다. 이제 롤백 스크립트는 대상을 찾지 못해 시끄럽게 실패하고, 되돌릴 때는 새로 배포하게 됩니다. 새로 배포하면 단일 호스트 기본값이 적용되고요.

🚨 조용히 옛 상태로 되살아나는 것보다 시끄럽게 실패하는 게 낫다
이 저장소에서 반복해서 나오는 모양입니다. 3부작에서도 롤백 스크립트가 조회 실패를 "대상 없음" 으로 잘못 읽어 아무것도 안 하고 성공처럼 끝나는 결함이 있었어요.

안전장치가 실패하는 방식에는 두 가지가 있습니다. 못 했다고 알리며 실패하는 것과 한 것처럼 보이며 실패하는 것이요. 뒤쪽이 훨씬 비쌉니다.

그리고 두 번 다 스크립트를 읽어봐서 알았습니다. 돌려보지 않은 안전장치는 안전장치가 아니라는 이야기를 3부작에서 했는데, 읽어보지도 않은 것은 그 앞 단계였어요.

부수 효과가 하나 더 있었습니다. 대기 컨테이너를 지우면서 메모리 3.7GB 가 회수됐어요. 호스트 여유가 9.6GB 에서 13.5GB 로 늘었습니다.

이게 의미가 있는 게, 이 호스트가 사흘 전에 49분 전면 중단을 낸 그 호스트입니다. 그때 원인이 "대기와 활성 두 몫의 JVM 힙이 호스트 메모리를 다 채운 것"이었는데, 지금은 그 조건이 성립하지 않는 상태가 됐습니다. 이번 작업의 목적은 아니었고 곁에서 얻은 결과예요.

6. 새 인스턴스는 크레딧 0 에서 시작한다

전환 전 점검에서 앞선 클러스터의 CPU 크레딧 알람 두 개가 울리고 있었습니다. 3편에서 "전환 직후가 가장 위험한 구간인데 그때 감시가 가장 부정확하다" 고 썼던 그 알람 계열이에요.

추이를 보니 방향이 반대였습니다.

12시간 전 현재 방향 writer 117 189 오르는 중 (시간당 +6) reader 160 255 오르는 중 (시간당 +8) 알람 임계값 < 400 400 도달까지 writer 약 35시간

크레딧이 떨어져서 울린 게 아니라 아직 안 찼는데 울린 것이었어요. Blue/Green 이 만든 인스턴스는 크레딧 0 에서 시작합니다. 그러니 임계값이 400 이면 채워지는 동안 계속 울립니다.

용량 문제가 아니라 인스턴스를 교체한 직후의 정상적인 과도 상태입니다. 그런데 그게 더 나쁜 면도 있어요. 인스턴스를 교체할 때마다 며칠씩 울리는 알람은 사람에게 "이 알람은 무시해도 된다" 를 가르칩니다.

그림 3. 교체 직후의 정상 상태를 이상으로 읽는 임계값

그래서 이번 클러스터의 알람은 다르게 잡았습니다. 실측을 근거로요.

CPU 사용률 > 30% 기준선 그 자체. 넘으면 크레딧이 빠지기 시작하니 선행 지표이고, 교체 직후에 울릴 이유가 없다. 실측 최대 23.3% 대비 여유 1.3배 크레딧 잔량 < 100 쓰로틀링 임박을 알리는 후행 지표. 0 에서 100 까지는 약 3시간이라 교체 후 오탐 구간이 짧다 여유 메모리 < 800MB 실측 최소 2,420MB 의 약 1/3

같은 것을 감시하는데 선행 지표를 기준선으로 잡으면 교체 오탐이 사라집니다. 크레딧 하나로 선행과 후행을 겸하게 만들었던 게 문제였어요.

전환 후 실측도 이 판단을 받쳐줬습니다.

writer CPU 평균 5.7 구간 17.0% → 8.0 구간 18.5% (+1.5%p) writer CPU 최대 23.3% → 20.7% (증가 없음) 여유 메모리 최소 2,420MB → 2,430MB (동일)

기준선 30% 아래이므로 크레딧은 소모되지 않고 쌓이는 방향입니다. 8.0 으로 올린 것 때문에 자원이 더 필요해진 건 없었어요. 인스턴스 등급을 올릴 이유도 없습니다.

⚠️ 다만 아직 확인하지 못한 게 있습니다
전환을 트래픽이 매우 낮은 시각에 했습니다. 초당 0.1건 수준이었어요.

그래서 위 실측은 한산할 때의 8.0 거동입니다. 부하가 있는 상태에서 어떤지는 업무시간을 한 번 지나야 압니다.

3편에서도 같은 형식으로 적었는데 다시 적습니다. "검증했다" 가 아니라 "여기까지 검증했다" 로 남겨두면 나중에 원인을 좁힐 때 훨씬 쓸모 있어요.
✍️ 오늘의 요약
두 번째 클러스터는 앱을 한 번도 멈추지 않고 넘겼습니다. DB 쓰기 중단은 약 5초였고 폴러 1,195 샘플에서 오류가 0건이었어요. 정지를 없앤 것은 새 도구가 아니라 순서입니다. 함정이 앱 안에 있었으니, 앱을 멈추는 대신 함정을 먼저 없애고 전환했습니다.

실측이 예상을 두 번 정정했습니다. 데이터가 37배인데 복제본 생성은 더 짧았으니 그 시간을 지배하는 건 데이터 크기가 아니었고, 개발 환경에서 찾은 콜레이션 함정은 이 방식에서는 실물에 없었습니다.
