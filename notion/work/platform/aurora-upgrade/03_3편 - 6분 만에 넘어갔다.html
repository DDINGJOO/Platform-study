📚 Aurora 5.7 → 8.0, 5부작
1편 · 확장 지원료가 마감을 만들었다
2편 · 되돌릴 수 있는 단계를 쌓았다
3편 · 6분 만에 넘어갔다 ← 지금 이 글
4편 · 앱은 한 번도 멈추지 않았다
5편 · 옛것이 사라진 뒤에 무엇으로 증명하나

복제본이 준비됐고 준비 작업도 끝났습니다. 남은 건 이름을 맞바꾸는 것 하나였어요.

결과는 중단 약 6분, 데이터 유실 0입니다. 그런데 이 글에서 정작 하고 싶은 이야기는 그 6분 안에서 순서를 한 번 틀렸다는 것과, 전환이 끝난 뒤에 알게 된 것들입니다.

1. 무증거 항목이 하나 남아 있었다

2편까지 왔을 때 검증되지 않은 항목이 딱 하나였습니다. 운영이 쓰는 접속 방식으로 8.0에 붙어본 적이 없다는 것이었어요.

개발 환경에서 미리 검증은 했습니다. 그런데 개발은 일반 접속 모드였고 운영은 페일오버를 지원하는 전용 모드였습니다. 드라이버가 서로 다른 코드 경로를 실행합니다.

그래서 기록해둔 이미지 다이제스트로 컨테이너 하나를 따로 띄웠습니다. 운영 이미지와 운영 프로필, 운영 환경변수를 그대로 사용했습니다.

compose 에 추가하지 않고 단독으로 ← 남의 배포가 라이브를 재시작하는 것을 막는다 프로필은 앱만, 배치 프로필 제외 ← 배치 프로필은 파기 스케줄러를 켠다 스키마 자동 초기화 never ← 읽기전용인 복제본에 쓰기 위험 제거

1차 시도는 실패했습니다. 제 테스트 하네스에 인증 관련 환경변수를 안 넘긴 게 원인이었어요. 돌고 있는 컨테이너의 환경변수를 그대로 물려받아 재시도했습니다.

커넥션 풀 기동 완료 Started ... in 27.099 seconds health(40s): {"status":"UP"} 에러 스캔: (비어 있음)

운영 드라이버 + 전용 모드 + 8.0 조합이 실제로 돌았습니다.

⚠️ 다만 무엇이 확인되지 않았는지도 적어둡니다
API 7개가 전부 401이었습니다. 인증 필터 뒤의 비즈니스 로직은 실행해보지 못했어요.

확인된 것: 드라이버 접속 · 풀 기동 · ORM 초기화 · 헬스체크(데이터소스 검사 포함이라 복제본 왕복 쿼리 성공).
확인 안 된 것: ORM이 생성하는 엔티티 쿼리.

그래서 확인되지 않은 부분은 SQL로 직접 확인했습니다. 문자열 조인 3건(최대 52만 행)과 GROUP BY 2건을 실제 데이터로 실행해 에러 0을 확인했어요.

"검증했다"가 아니라 "여기까지 검증했다"로 적는 게 나중에 사고 원인을 좁힐 때 훨씬 쓸모 있습니다.

여기서 로그 한 줄이 눈에 걸렸습니다.

Using dialect: org.hibernate.dialect.MySQL57Dialect

8.0에 붙었는데 ORM은 5.7 방언을 씁니다. 그리고 복제본의 설정을 확인할 때 이것도 봤어요. 8.0 기본값에 들어 있는 엄격 모드 하나가 빠져 있었습니다.

둘을 겹쳐 보면 지금 상태는 8.0 위에서 5.7처럼 도는 것입니다. 그리고 이건 목적을 생각하면 맞는 트레이드오프예요. 목적이 비용 제거였으니까요. 엄격 모드를 켜면 5.7에서 통과하던 쿼리가 깨질 수 있고, 그건 이번 창에서 감당할 위험이 아닙니다.

다만 "언제 켤 것인가"를 적어두지 않으면 영구히 꺼진 채로 남습니다. 그래서 이 문단이 그 기록입니다. 비용을 먼저 없애고, 엄격성은 별도 작업으로 미뤘습니다.

2. 데이터 대조: 여섯 테이블 전부 일치

전환 직전에 원본과 복제본의 행 수를 맞춰봤습니다.

A B C D E F 원본 (5.7): 158897 138240 288997 62535 437744 190 복제본(8.0): 158897 138240 288997 62535 437744 190

여섯 테이블이 전부 정확히 일치했습니다. 복제가 따라잡았고 데이터가 같다는 증거입니다. 이게 전환 전 마지막 게이트였어요.

3. 그리고 순서를 틀렸다

원래 밤 10시 계획이었는데 오후 5시로 옮겼습니다. 협의체가 "짧고 되돌릴 수 없는 작업은 밤에"라고 한 근거가 "트래픽이 적을 때"였고, 10시가 목적이 아니라 한산함이 목적이었으니까요. 그 시각이 마침 한산했습니다.

순서는 정해져 있었습니다. 정지 → 전환 → 기동.

그런데 전환이 진행 중인 상태에서 앱 기동이 먼저 나갔습니다. 앱이 떴고 커넥션 풀도 붙었는데, 그 시점 엔드포인트는 아직 옛 클러스터를 가리켰습니다.

그림 1. "전환" 한 줄은 명령을 보내는 것이지 완료되는 것이 아니었다

이게 실수가 아니라 체크리스트의 문제라고 생각합니다. 전환 명령은 즉시 반환되고 완료는 상태를 폴링해서 알아야 합니다. 그러면 "전환"이라는 한 줄은 명령을 보내는 것일 뿐이에요. 순서를 지키려면 "완료를 기다린다"가 별도 단계로 있어야 했고, 없었습니다.

바로 다시 정지시키고 전환 완료를 기다린 뒤 기동했습니다. 원래 순서가 복원됐어요.

🚨 무해했던 게 아니라 시간대가 구해줬다
피해는 0이었습니다. 그런데 왜 0이었는지를 정확히 적어야 해요. 그 시각에 트래픽이 없었기 때문입니다.

운영 드라이버는 전용 모드에서 인스턴스 엔드포인트를 캐시합니다. 앱이 그대로 떠 있었고 요청이 들어왔다면, 커넥션이 옛 클러스터를 향한 채 남아 쓰기가 갈라졌을 겁니다. 전환 후 새 클러스터와 옛 클러스터에 각각 다른 데이터가 들어가는 상태입니다.

낮이었으면 데이터 분기였습니다. "실피해 0"으로 적고 넘어가면 다음에 같은 순서로 낮에 합니다.

4. 전환 자체는 6분이었다

17:20 앱·배치 정지 → 앱 서버 커넥션이 사라진 것 확인 전환 명령 → 진행 중 → 완료 17:23:30 컨테이너 기동 17:24:40 health UP (70초)

커넥션 확인에도 배운 게 있었습니다. 처음엔 "커넥션 0"을 진행 조건으로 잡았는데, 관리용 내부 커넥션 7개는 절대 사라지지 않습니다. 영원히 못 넘어가는 조건이었어요. 앱 서버 주소 기준으로 고쳤습니다.

전환 후 이름이 승계됐습니다.

복제본 클러스터 → 원래 이름을 물려받는다 복제본 인스턴스 → 원래 인스턴스 이름을 물려받는다 옛 클러스터 → 이름에 -old 가 붙는다

그래서 앱 접속 URL을 바꿀 필요가 없었고, 알람 16개(1편에서 센 10개에 2편에서 8.0 클러스터용으로 추가한 것을 더한 수)가 인스턴스 식별자로 이름을 조립하므로 자동으로 새 클러스터를 보게 됐습니다. 1편에서 신규 클러스터 방식을 버린 이유가 여기서 효과를 냈어요.

5. 그런데 "롤백 자산"이라는 말이 정확하지 않다

뒤처리 계획에 이렇게 적었습니다. "관측 3영업일 후 옛 클러스터 삭제. 그때까지 이게 롤백 자산이다."

옛 클러스터는 살아 있습니다. 그건 맞아요. 그런데 복제가 전환 시점에 끊겼습니다. 옛 클러스터의 데이터는 컷오버 순간 상태에 그대로 멈춰 있습니다.

그리고 전환 직후부터 새 클러스터에는 데이터가 쌓이고 있어요. 전송 17건이 성공했고 증가 추이도 남았습니다.

그림 2. 살아 있다는 것과 되돌릴 수 있다는 것은 다르다

그러니까 지금 롤백하면 전환 이후 쌓인 데이터가 없는 상태로 돌아갑니다. 그건 되돌리기가 아니라 전환 시점으로 되감기 + 그 뒤 유실이에요.

이 저장소에 그 제목의 글이 이미 있습니다. 개발 DB를 옮길 때 쓴 글이고, 제목이 "롤백은 되감기가 아니다"였습니다. 같은 함정을 같은 사람이 다시 밟았고, 이번엔 그 글을 참조하지 않았습니다.

3영업일이면 유실량은 작을 수 있습니다. 문제는 크기가 아니라 표현이에요. "롤백 자산"이라고 적어두면 급할 때 그게 무손실 복귀라고 믿고 누릅니다. 필요한 건 한 줄입니다. "롤백 시 전환 이후 데이터는 유실된다. 그러므로 롤백 판단에는 유실 감수 결정이 포함된다."

6. 새 버전을 옛 기준으로 감시하고 있다

사후 관찰은 깨끗했습니다. 전송 17건 전부 성공, 커넥션이 전환 직후 101에서 3으로 정상화, SQL 에러 0, 헬스체크 5회 연속 200이었습니다.

다운타임 구간에 알람 1건이 울렸는데 그건 정상입니다. 그 구간에 정상 호스트가 0이었으니까요. 타깃 상태를 직접 확인해 정상임을 봤고, 새 데이터포인트가 들어오면 자동 복귀합니다.

그런데 뒤처리 목록에 이 줄이 있습니다.

알람 임계값 5종 재측정 — 전부 5.7 · 옛 인스턴스 기준 실측값이었다

이게 후속에 있으면 안 됩니다. 지금 이 순간 8.0 클러스터를 5.7 시절 기준으로 감시하고 있어요. Aurora 3는 메모리 사용 패턴이 다르니 임계가 안 맞으면 못 울리거나 불필요하게 울립니다.

전환 직후가 가장 위험한 구간인데 그때 감시가 가장 부정확한 상태입니다.

🎯 이 저장소가 반복해서 밟는 자리
이 시리즈에서 계속 같은 모양이 나옵니다.

• 야간 축소: 조치했는데 남는 쪽을 보는 알람이 없었다
• 메모리 고갈: 조치했는데 상한에 닿은 걸 알 수단이 없었다
• 이번 작업: 버전을 올렸는데 알람은 옛 버전 기준이다

조치를 끝내는 것과 조치를 지켜보는 장치를 만드는 것은 다른 작업이고, 두 번째가 계속 뒤로 밀립니다. 첫 번째가 끝나면 문제가 해결된 기분이 들기 때문이라고 생각해요.
✍️ 오늘의 요약
전환은 6분이었고 데이터 유실은 0이었습니다. 이름이 승계되니 앱도 알람도 그대로 새 클러스터를 봤어요. 되돌릴 수 있는 단계를 앞에 쌓아둔 효과가 여기서 나왔습니다.

다만 순서를 한 번 틀렸고, 그건 단순한 부주의가 아니라 비동기 명령을 동기처럼 적은 체크리스트 때문이었습니다. 피해가 0이었던 건 시간대 덕분이고요. 그리고 살아 있는 옛 클러스터를 "롤백 자산"이라 불렀는데, 살아 있다는 것과 되돌릴 수 있다는 것은 다릅니다. 복제는 전환 시점에 끊겼고 그 뒤 데이터는 거기 없습니다.
