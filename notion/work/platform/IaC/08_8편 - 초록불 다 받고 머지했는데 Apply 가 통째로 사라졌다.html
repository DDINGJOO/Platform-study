PR 체크가 네 개였고 전부 초록불이었어요. fmt / validate / tflint, checkov, plan (dev), plan (prod). 리뷰도 받았고, 승인 도장도 찍혔고, 머지도 했습니다. 여기까지는 그냥 평범한 하루였어요.

그리고 main 에 push 가 들어간 순간, Terraform Apply 워크플로가 잡을 하나도 만들지 못하고 끝났습니다. 실패한 잡이 있는 게 아니라 잡 목록이 비어 있었어요. 화면에 남은 건 이 한 줄뿐이었습니다.

Terraform Apply · main · push status: failure jobs: 0 개 message: This run likely failed because of a workflow file issue.

실패한 잡이 없으니 로그도 없고, 로그가 없으니 어느 파일 몇 번째 줄이 문제인지도 안 알려줍니다. dev 자동 apply 도 안 돌고, 수동 dispatch 를 눌러도 똑같이 잡 0 개로 끝나요. 인프라 반영 경로가 통째로 사라진 상태였습니다.

1. 재사용 워크플로의 권한은 계약이다

이 저장소의 apply 파이프라인은 환경마다 같은 절차를 반복해요. init 하고, plan 뜨고, 파괴적 변경 가드를 통과하고, apply 하고, 끝나면 이슈를 닫습니다. 그래서 그 절차 전체를 _apply-env.yml 이라는 재사용 워크플로 하나로 빼고, 부르는 쪽은 uses: 한 줄로 환경만 갈아끼우게 만들어뒀습니다.

이때 권한이 어떻게 넘어가는지가 오늘의 핵심이에요. 재사용 워크플로는 부르는 잡의 권한을 물려받지 않습니다. 대신 호출 잡이 선언한 permissions 가 상한이고, 불려가는 워크플로가 선언한 permissions 는 그 부분집합이어야 해요. 이건 권장 사항이 아니라 계약입니다.

그럼 계약을 어기면 어떻게 될까요. 여기서 직관이 한 번 어긋납니다. 저는 막연히 "요구한 권한이 런타임에 깎여서 그 스텝이 403 으로 실패하겠지"라고 생각했어요. 실제로는 그렇게 점잖게 처리되지 않습니다. GitHub 은 이걸 워크플로 파일을 파싱하고 잡 그래프를 만드는 단계의 검증 실패로 처리해요.

그 차이가 피해 범위를 결정합니다. 런타임 실패라면 그 잡 하나만 빨간불이 되고 나머지는 정상적으로 돌아요. 그런데 파싱 실패는 잡을 만들기 전에 나기 때문에 그 파일에 정의된 모든 잡이 생성 자체를 못 합니다. 권한과 아무 상관 없는 옆 잡까지 같이 죽는 거예요. 실패한 잡이 하나도 없는 게 아니라, 애초에 태어난 잡이 없었던 겁니다.

2. 호출부가 둘인데 하나만 고쳤다

여기서부터는 남 얘기가 아니라 제가 낸 사고예요. 하루 전 커밋에서 저는 이미 두 호출부 모두에 잡 단위 permissions 를 붙여뒀습니다. id-token: write, contents: read, actions: read 세 개가 양쪽에 똑같이 있었고, 불려가는 쪽이 요구하는 것도 정확히 그 셋이었어요. 그때는 완전했습니다.

사고는 그 다음 커밋에서 났어요. prod 반영이 끝나면 prod-pending 이슈를 자동으로 닫는 스텝을 _apply-env.yml 에 추가하면서, 요구 권한에 issues: write 를 한 줄 더했습니다. 그러면 호출부 두 곳에도 똑같이 한 줄씩 넣었어야 하는데, 수동 dispatch 잡에만 넣고 push 트리거로 도는 dev-auto 잡에는 넣지 않았어요.

# _apply-env.yml — 불려가는 쪽이 요구하는 권한 permissions: id-token: write contents: read actions: read issues: write # apply 성공 시 이슈를 닫는다 ← 이번에 추가한 줄 # terraform-apply.yml — 부르는 쪽, 호출부가 둘이다 jobs: dev-auto: # push 트리거 permissions: id-token: write contents: read actions: read # issues 가 없다 ← 여기를 빠뜨렸다 uses: ./.github/workflows/_apply-env.yml dispatch: # workflow_dispatch 트리거 permissions: id-token: write contents: read actions: read issues: write # 여기만 맞췄다 uses: ./.github/workflows/_apply-env.yml

이 상태가 되는 순간 dev-auto 는 "불려가는 쪽이 부르는 쪽보다 큰 권한을 요구하는" 잡이 됩니다. 그리고 앞에서 말한 대로 그 대가는 잡 하나가 아니라 파일 하나예요. 잘못 없는 dispatch 잡까지 같이 죽어서 수동 반영 경로도 함께 막혔습니다.

변명거리가 하나도 없는 게, 이 커밋은 리뷰 승인을 받은 뒤에 얹은 커밋이었어요. 블로그 글을 쓰다가 발견한 결함 두 개를 "이왕 열려 있는 김에" 같은 PR 에 밀어 넣었죠. 승인은 그 시점에 무효화되고, 실제로 머지된 코드는 아무도 두 번째로 읽지 않은 코드가 됐습니다. 사람 눈이 빠진 자리에 CI 라도 있었어야 했는데, 그게 왜 없었는지가 다음 장입니다.

그림 1. 계약을 어긴 잡은 하나인데, 죽는 것은 파일 하나다

3. 그런데 PR 체크 네 개는 뭘 보고 있었나

여기가 이 글의 본론이에요. 저 결함은 YAML 파일 두 개를 나란히 놓고 보면 5초 만에 보이는 종류입니다. 그런데 PR 체크 네 개가 전부 초록불이었어요. 어떻게 그럴 수 있었을까요.

답은 싱겁습니다. 그 네 개 중에 워크플로 파일을 본 검사는 하나도 없었어요. fmt / validate / tflint 와 checkov 는 Terraform 코드를 봅니다. plan (dev) 와 plan (prod) 는 실제로 AWS 에 붙어서 계획을 뜨죠. 넷 다 .tf 파일 검사기입니다. .github/workflows/ 아래는 아무도 안 봐요.

"그건 GitHub 이 알아서 검증해주지 않나요?" 해준다면 해줍니다. 다만 GitHub 은 워크플로 파일을 실제로 그 파일이 실행될 때만 검증해요. 정확히는 이벤트가 들어와서 그 파일로 run 을 만들려고 시도하는 순간에 파싱하고, 잡 그래프를 만들고, 권한 계약을 확인합니다. 저장소에 있다고 검증해주는 게 아니라, 불려야 검증됩니다.

그리고 Terraform Apply 워크플로의 트리거는 push 와 workflow_dispatch 두 개뿐이에요. prod 자원을 건드리는 파이프라인이니 PR 에서 도는 게 오히려 이상하죠. 그러니까 이 파일은 pull_request 이벤트에서 단 한 번도 실행되지 않고, 따라서 단 한 번도 검증받지 않습니다. PR 을 백 번 올려도 검증 횟수는 0 회예요.

정리하면 이렇습니다. 저 저장소에는 PR 체크가 구조적으로 검증할 수 없는 파일이 들어 있었어요. 초록불 네 개의 의미는 "이 변경은 안전하다"가 아니라 "우리가 검사할 수 있는 것들은 통과했다"였습니다. 저는 그걸 앞의 문장으로 읽고 머지 버튼을 눌렀고요.

그림 2. 초록불 네 개는 사각지대 안쪽에서 켜졌다

4. 그래서 검사를 직접 만들었다

수리 자체는 한 줄이에요. dev-auto 에 issues: write 를 넣으면 끝납니다. 그런데 원인이 "사람이 두 곳 중 한 곳을 빠뜨렸다"라면, 그 한 줄은 다음번에 또 빠질 거예요. 호출부가 늘어나면 더 잘 빠지고요. 그러니 사람이 아니라 기계가 막아야 합니다.

GitHub 이 실행 시점에 하는 그 검사를, 파일만 읽어서 흉내 내는 스크립트를 하나 썼습니다. 하는 일은 단순해요. 워크플로 디렉터리의 모든 파일을 열어서 로컬 재사용 워크플로를 호출하는 잡을 찾고, 불려가는 파일이 요구하는 각 scope 를 호출 잡이 준 것과 none < read < write 순위로 비교합니다.

RANK = {"none": 0, "read": 1, "write": 2} for caller_path in sorted(WF_DIR.glob("*.yml")): for job_name, job in (load(caller_path).get("jobs") or {}).items(): uses = str(job.get("uses", "")) if not uses.startswith("./.github/workflows/"): continue # 로컬 호출만 본다 # lstrip("./") 은 문자 집합을 지우므로 쓰면 안 된다. # "./.github/..." 가 "github/..." 로 뭉개진다. called = Path(uses.removeprefix("./")) required = load(called).get("permissions") or {} granted = job.get("permissions") or {} for scope, need in required.items(): have = granted.get(scope, "none") # 선언이 없으면 none 이다 if RANK[str(have)] < RANK[str(need)]: problems.append( f"{caller_path} 의 `{job_name}` 잡이 " f"`{scope}: {need}` 를 주지 않습니다 (현재: {have})" )

중요한 건 이걸 어디에 매달았느냐예요. pull_request 에서 도는 static 잡, 그러니까 fmt / validate / tflint 와 같은 잡의 스텝으로 넣었습니다. AWS 자격증명도 OIDC 토큰도 필요 없어요. 파일 두 개를 읽고 딕셔너리를 비교하는 게 전부니까요. 검증이 안 되던 파일을, 검증이 되는 이벤트 위로 끌고 온 겁니다.

그리고 검사기를 만들었으면 반드시 해야 하는 일이 하나 더 있어요. 일부러 고장 내서 잡히는지 확인하는 것입니다. 호출부에서 권한을 하나 지우고 돌려서 빨간불이 뜨는 걸 보고 나서야 커밋했습니다. 이걸 안 하면 "항상 통과하는 검사"를 초록불로 착각하게 되는데, 그건 없느니만 못해요.

⚠️ 이 검사가 못 보는 것 두 가지
• 스칼라 권한 선언: permissions: write-all 이나 read-all 처럼 딕셔너리가 아닌 형태로 쓰면 비교 대상에서 빠집니다. 지금은 그냥 건너뛰어요.
• 원격 재사용 워크플로: org/repo/.github/workflows/x.yml@ref 형태는 파일이 로컬에 없으니 요구 권한을 읽을 방법이 없습니다. ./ 로 시작하는 호출만 검사해요.

지금 이 저장소에는 둘 다 해당 사항이 없어서 안 막았습니다. 다만 언젠가 생깁니다. 그때 이 검사는 조용히 통과할 거고, 조용히 통과하는 검사가 제일 위험하다는 걸 오늘 배웠으니 적어둡니다.

5. 실행돼야 검증되는 것들의 목록

이 사고에서 남길 건 issues: write 가 아니에요. 그건 다음 주면 잊습니다. 남길 건 두 가지예요.

첫째, "실행돼야 검증되는 것"은 실행되지 않는 경로에서 영원히 검증되지 않습니다. 이건 워크플로 파일만의 성질이 아니에요. 한 달에 한 번 도는 크론 잡, 릴리스 태그를 달아야 도는 배포 파이프라인, 진짜 장애가 나야 도는 재해복구 스크립트가 전부 같은 성질을 가집니다. 평소에는 아무도 실행하지 않으니 아무도 검증하지 않고, 정작 실행되는 그 순간은 실패하면 가장 곤란한 순간이죠.

이런 것들을 위한 검사는 저절로 생기지 않아요. 직접 만들어서 PR 경로 위에 올려놔야 합니다. 저장소를 한 번 훑어보고 "PR 에서 실행되지 않는 파일"의 목록을 만들어보면, 그게 그대로 사각지대 목록이 됩니다.

둘째, 초록불이 무엇을 보장하는지 세어봐야 합니다. 체크 네 개가 초록이라는 건 정확히 그 네 개가 통과했다는 뜻이에요. 그 이상도 이하도 아닙니다. 이번엔 그 넷이 전부 .tf 파일 검사기였고, 제가 고친 건 .yml 이었죠. 커버리지가 0% 인 변경에 초록불 네 개가 붙어 있었던 겁니다.

그래서 저는 요즘 PR 을 머지하기 전에 이렇게 한 번 물어봐요. "내가 이번에 고친 파일을, 저 체크 중에 실제로 열어본 게 있나?" 없으면 초록불은 그 변경에 대해 아무 말도 하지 않은 겁니다. 침묵을 승인으로 읽지 않는 게 오늘 얻은 유일한 습관이에요.

💡 머지 전 3문
• 이번 변경이 건드린 파일 종류를, PR 체크 중 하나라도 실제로 열어봤는가?
• 이 설정이 여러 곳에 중복 선언돼 있다면, 그 짝이 맞는지 세는 검사가 있는가?
• 승인 도장을 받은 뒤에 얹은 커밋이 있는가? 있다면 그건 리뷰받지 않은 코드다.
✍️ 오늘의 요약
재사용 워크플로의 permissions 는 호출 잡이 준 것의 부분집합이어야 하고, 초과하면 그 잡이 실패하는 게 아니라 워크플로 파일 전체가 무효가 된다. 호출부 두 곳 중 한 곳만 맞춘 탓에 무관한 dispatch 잡까지 함께 죽어, apply 경로가 통째로 사라졌다.

PR 체크 네 개가 이걸 못 잡은 이유는 실력이 부족해서가 아니라 Apply 워크플로가 pull_request 에서 실행되지 않아 검증 대상 자체가 아니었기 때문이다. 그래서 그 검사를 직접 만들어 PR 경로 위에 올렸다.

초록불은 안전하다는 뜻이 아니라, 우리가 검사할 수 있는 것들이 통과했다는 뜻이다.
