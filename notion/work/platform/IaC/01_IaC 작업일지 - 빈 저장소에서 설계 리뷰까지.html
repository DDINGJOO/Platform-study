커밋 1개짜리 저장소를 받았어요. Terraform 코드는 0줄이고, 워크플로도 브랜치 보호도 없었습니다. 이름만 IaC였어요. 여기에 조직 인프라의 코드화 파이프라인을 처음부터 끝까지 세우는 게 이번 작업이었습니다.

이 글은 그 과정을 편집 없이 따라가는 작업 일지예요. 도구를 고른 0번째 결정부터, 커밋 로그에 그대로 남은 삽질들, 그리고 마지막에 설계 리뷰에서 네 발 얻어맞은 것까지 그대로 담았습니다. "머지 버튼 하나가 운영 인프라를 바꾸는 파이프라인은 어떻게 설계해야 하는가"가 오늘의 질문입니다.

1. 0번째 결정: 왜 Terraform인가

사실 이 질문을 제일 나중에 받았어요. ADR을 0001부터 썼는데, 정작 그보다 먼저 있었던 결정, 즉 도구 선택은 문서가 없더라고요. 리뷰어가 "왜 테라폼인지는 안 궁금해?"라고 물어서야 정리했습니다.

후보는 셋이었어요. Pulumi(범용 언어), CloudFormation(AWS 네이티브), Terraform. Pulumi를 먼저 떨어뜨렸는데, 이유는 표현력이 부족해서가 아니라 넘쳐서입니다. 범용 언어로 인프라를 쓰면 다섯 명이 다섯 가지 방언을 만들고, 추상화가 쌓이면 "이 계정에 지금 뭐가 있지?"라는 질문에 코드가 답을 못 하게 돼요. IaC는 프로그램이 아니라 지도여야 합니다. 선언형 HCL은 못 하는 게 많아서 좋은 거예요. 제약이 곧 일관성이니까요.

그런데 이 논리는 CloudFormation을 못 죽입니다. CFN도 선언형이고, 심지어 state 파일을 AWS가 대신 관리해 주죠. 처음엔 "멀티 클라우드 대비"라고 답했다가 바로 반격당했어요. aws_s3_bucket이 GCP 리소스로 자동 변환되는 게 아니니까, Terraform은 멀티 클라우드 도구지 클라우드 중립 도구가 아닙니다. 정직하게 남는 기각 사유는 이거였어요. 우리가 파이프라인에 이미 넣은 검증 체인(tflint, checkov)과 모듈 생태계, 그리고 새벽 3시에 에러 메시지를 검색하면 답이 나오는 사례 밀도가 Terraform 쪽에 있다. "업계 표준이라서"는 ADR에 못 쓰는 문장이지만, 표준이 만들어내는 이런 운영상 성질들은 전부 검증 가능한 논거입니다.

2. develop 브랜치를 만들지 않기로 했다

우리 조직 서비스 저장소는 전부 master + develop 모델이에요. develop에 머지하면 dev 배포, master에 머지하면 운영 배포, 그리고 배포가 성공하면 봇이 master를 develop으로 자동 역머지합니다. 운영에 나간 코드와 개발 브랜치가 벌어지지 않게 기계가 맞춰주는 관행입니다. 관례대로라면 IaC 저장소도 이 모델을 따라야 자연스럽죠.

그런데 그 관례를 IaC에 이식하면 체인이 하나 생깁니다. 역머지 봇의 커밋이 develop에 꽂히고, 그 커밋이 dev apply를 트리거해요. 사람이 한 번도 보지 않은 커밋이 인프라를 바꾸는 경로가 구조적으로 생기는 겁니다. 앱은 롤백이 멱등하니까 이게 견딜 만한 위험인데, Terraform의 롤백은 그 자체가 또 하나의 파괴적 변경이에요. 브랜치가 갈리면 state도 갈리고, prod plan이 dev에만 있는 리소스를 destroy로 계산하는 사고도 따라옵니다.

그래서 브랜치 대신 디렉터리로 갈랐어요. 단일 트렁크 main에 envs/dev, envs/prod, 그리고 공유 modules/를 뒀어요. 환경 차이는 모듈에 넘기는 값의 차이로만 표현되고, dev와 prod의 diff가 한 PR 안에서 보입니다. 승격이 "머지"라는 반사적 행위가 아니라 "값을 바꾸는 PR"이라는 명시적 행위가 돼요.

그림 1. 브랜치 모델을 거절한 진짜 이유는 브랜치가 아니라 역머지 봇이었다

3. bootstrap: 닭과 달걀부터 풀기

Terraform으로 인프라를 만들려면 state를 담을 S3 버킷과 CI가 쓸 IAM 역할이 필요한데, 그것들 자체도 Terraform으로 만들고 싶잖아요. 전형적인 닭과 달걀이라, bootstrap/ 디렉터리만 사람이 로컬에서 1회 apply하는 예외로 뒀습니다. 대신 이 디렉터리는 CI apply 대상에서 영구 제외입니다. CI가 자기 state 버킷을 파괴할 수 있는 경로는 처음부터 만들지 않습니다.

역할은 환경×용도로 4개(dev/prod × plan/apply)를 만들었어요. 재미있는 건 plan 역할인데, "읽기 전용"이라고 부르지만 순수 ReadOnly가 될 수 없습니다. Terraform 1.10의 네이티브 잠금(use_lockfile)이 .tflock 객체를 만들고 지우거든요. ReadOnly만 붙이면 첫 PR부터 plan이 실패하고, 사람들은 -lock=false를 붙이기 시작하고, 그게 그대로 조직 습관으로 굳어요. 그래서 "전체 읽기 + 자기 잠금 파일 하나만 쓰기"라는 비대칭 권한으로 만들었습니다.

단일 AWS 계정에 dev/prod가 공존하는 조건이라 격리는 3중 방어로 구성했어요. state 키 프리픽스 분리, default_tags로 env 태그를 강제하고 apply 역할에 반대 환경 태그 리소스에 대한 명시적 Deny, 그리고 prod 리소스의 prevent_destroy입니다. 태그 조건을 지원하지 않는 서비스(IAM, Route53 등)는 못 막는다는 한계까지 ADR의 "감수하는 것"에 적었습니다. 이 문서화가 나중에 절 한 번 구해줘요.

4. 삽질 로그: 커밋이 증거다

여기부터는 커밋 로그에 fix가 줄줄이 남은 구간이에요. 첫 번째 지뢰는 허무했습니다. IAM 역할 description을 한글로 썼더니 CreateRole이 ValidationError로 거부돼요. AWS가 description에 허용하는 문자는 사실상 ASCII + Latin-1뿐이라, 한글은 물론이고 em-dash(—) 하나로도 죽습니다.

두 번째는 꽤 오래 헤맸어요. OIDC 신뢰 정책을 문서 그대로 repo:org/repo:... 형식으로 썼는데 AssumeRole이 계속 거부됩니다. 알고 보니 우리 조직은 불변 주체 클레임이 켜져 있어서 sub가 다른 형식으로 발급되고 있었어요.

기대한 sub: repo:{조직}/{저장소}:ref:refs/heads/main 실제 sub: repo:{조직}@{조직ID}/{저장소}@{저장소ID}:ref:refs/heads/main 확인 방법: gh api repos/<org>/<repo>/actions/oidc/customization/sub --jq .sub_claim_prefix

세 번째가 이번 작업의 최대 반전입니다. 원래 설계는 prod apply를 GitHub Environment의 required reviewer로 막는 거였어요. "승인 전에는 job이 시작되지 않으니 OIDC 자격증명 자체가 발급되지 않는다"는 논리였고, 저는 이 설계가 깔끔하다고 생각했어요. 그런데 구현하려고 API를 호출해 보니 이런 응답이 돌아왔습니다.

PUT /repos/{조직}/{저장소}/environments/prod {"reviewers": [{"type": "User", "id": ...}]} → 422 "Please ensure the billing plan supports the required reviewers protection rule."

조직 플랜이 GitHub Team이었던 거예요. 문서의 "Team 플랜은 private 저장소에서 Environment를 구성할 수 있다"는 Environment 객체를 만들 수 있다는 뜻이지, 보호 규칙을 걸 수 있다는 뜻이 아니었습니다. 실제로 Environment는 생성되는데 protection_rules가 빈 배열이에요. 즉 워크플로에 environment: prod를 써도 아무 게이트도 안 걸립니다. 그대로 두면 main 머지 = 무승인 prod apply. 설계의 전제가 무너졌으니 ADR-0002로 공개 정정하고, prod 트리거 자체를 workflow_dispatch 수동 실행으로 바꿨어요. 두 사람의 관여는 브랜치 보호의 필수 승인 1인(+관리자 예외 없음)이 담당하고요.

💣 오늘 밟은 지뢰 3개
• IAM description은 ASCII만 받는다. 한글도 em-dash도 CreateRole을 죽인다
• 불변 주체 클레임이 켜진 조직은 OIDC sub 형식이 다르다. 문서 예제를 그대로 복사하면 안 된다
• "Environment를 만들 수 있다" ≠ "보호 규칙을 걸 수 있다". 플랜 문서는 끝까지 읽자
그림 2. 최종 파이프라인: 사람이 안 본 변경이 닿는 경로는 없다…고 이때는 믿었다

5. 설계 리뷰에서 네 발 맞았다

다 만들고 나서 설계 리뷰를 받았는데, 지적 4건이 전부 같은 부위였어요. "만든 사람의 행복 경로"와 "실제 이벤트·권한 모델의 동작" 사이의 틈.

① prod plan을 아무도 안 읽는다. 수요일에 dispatch 버튼을 누르면, 월요일에 다른 사람이 머지해 둔 변경까지 함께 계산된 plan이, 아무도 그 전체를 확인하지 않은 채 같은 run 안에서 바로 apply됩니다. 자동 가드가 있긴 하지만 destroy만 잡아요. 삭제가 없는 변경은 무사통과입니다. 해법은 Terraform이 공짜로 주는 안전장치를 믿는 것이었어요. 저장된 plan은 그 사이 state가 변하면 apply가 stale 에러로 거부되니까, plan과 apply를 붙여둘 이유가 없습니다. dispatch를 plan 단계와 apply 단계로 쪼개고, 사람이 그 사이에서 plan 요약을 읽게 만들면 돼요.

② iam:* 하나로 3중 방어가 우회된다. apply 역할에 iam:*를 열어주면서 파이프라인 역할(platform-iac-*)만 Deny로 보호했는데, 그 목록 밖 이름으로 관리자 역할을 새로 만들어 갈아타면 태그 Deny까지 전부 무력화됩니다. 수리는 sts:AssumeRole 명시적 Deny와 "permissions boundary 없이는 역할 생성 불가" 조건을 조합하는 것이었어요.

③ 에러 메시지가 거짓말을 한다. 파괴적 변경 가드가 "allow-destroy 라벨을 붙이고 다시 실행하세요"라고 안내하는데, github.event는 이벤트 발생 순간의 payload 박제라서 Re-run은 라벨을 붙이기 전 스냅샷을 다시 읽어요. 안내대로 하면 영원히 통과 못 합니다. 라벨은 실행 시점에 API로 조회해야 해요.

④ dev를 지우려고 누른 버튼이 prod에도 적용된다. dispatch에 환경 선택 입력이 없어서, allow_destroy를 켜고 실행하면 dev와 prod가 함께 돌아요. env 입력 하나를 추가해 폭발 반경을 좁히기로 했습니다.

🔧 리뷰 후 패치 목록 (PR 두 개 분량)
• prod를 2단계 dispatch로 분리 + env 선택 입력 추가
• 머지 직후 "prod 미반영 변경" 이슈 자동 생성: 24시간 drift 대기를 즉시 알림으로
• sts:AssumeRole Deny + permissions boundary 강제
• 라벨 가드를 실행 시점 API 조회로 교체 + unlabeled 트리거 추가
그림 3. 리뷰에서 가장 아팠던 지적: iam:* 권한 승격 경로

6. 하루를 마치며: 점수보다 남은 것

리뷰 최종 점수는 10점 만점에 7.5점이었어요. 깎인 2.5점이 전부 위의 4건이었고, 패치를 반영하면 재채점 예상은 8.5~9점입니다. 그런데 점수보다 남은 게 두 가지 있습니다.

하나는 ADR의 힘이에요. 리뷰 중에 "단일 계정에서 태그 기반 격리는 IAM 같은 서비스엔 안 통하지 않냐"는 지적이 왔는데, "인지하고 있고 ADR의 '감수하는 것'에 적어뒀다"로 받아칠 수 있었습니다. 한계를 먼저 문서화한 설계만이 지적을 방어할 수 있어요. 반대로 문서에 없던 부분들, 즉 dispatch plan 리뷰와 iam:* 문제는 고스란히 얻어맞았고요.

다른 하나는 질문 패턴입니다. 네 건의 지적은 전부 "이 버튼을 잘못 누르면?", "이 입력은 어디까지 전파되지?", "이 값은 언제 찍힌 스냅샷이지?"라는 질문에서 나왔어요. 설계 단계에서 이 질문을 스스로 던졌다면 리뷰 전에 절반은 잡았을 겁니다.

✍️ 오늘의 요약
IaC 파이프라인 설계의 핵심은 "사람이 보지 않은 변경이 인프라에 닿는 경로"를 전부 세는 일이었습니다. 역머지 봇, 무승인 apply, 박제된 이벤트 payload, 목록 밖 역할. 오늘 만난 문제 전부가 그 경로의 변종이었어요.

그리고 그 경로는 행복 경로 설계에서는 절대 보이지 않습니다. 설계는 "잘 되면 어떻게 되는가"가 아니라 "잘못 누르면 어디까지 가는가"를 적는 일입니다.
