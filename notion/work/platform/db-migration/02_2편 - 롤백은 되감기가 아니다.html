이관을 끝내고 작업 문서에 이렇게 적었어요.

## 롤백 수단 (보관 중) | 수단 | 위치 | 비고 | |---------------|---------------------------------|--------------------| | 5.7 논리 백업 | ~/backup-20260803.sql (44MB) | 이관 직전 시점 | | 5.7 데이터 볼륨 | Docker volume (해시명) | 유일한 물리 롤백 |

두 줄을 적고 나니 마음이 놓였어요. 뭐가 터져도 돌아갈 데가 있으니까요. 그리고 며칠 뒤에 질문 하나를 받았습니다.

"그거 실제로 돌려본 적 있어요?"

없었어요. 그리고 그 질문을 따라가다 보니, 제가 "롤백"이라는 단어를 잘못 이해하고 있었다는 걸 알게 됐습니다.

1. 왜 물리 볼륨까지 들고 있어야 했나

MySQL 8.0 은 컨테이너를 새 이미지로 올리면 데이터 디렉터리를 자동으로 업그레이드해줘요. 편한데, 이 변환은 단방향이라 다시 내려갈 수 없습니다. 8.0 이 한 번 손댄 datadir 은 5.7 이 못 읽어요.

그래서 롤백 수단이 두 개 필요했습니다. 성격이 완전히 다르거든요.

# 수단 A) 논리 백업 — 텍스트 SQL. 복원에 시간이 걸린다 mysql app_db < backup-20260803.sql # 수단 B) 물리 볼륨 — 붙이면 바로 뜬다 docker run -d -v app-mysql57-data:/var/lib/mysql mysql:5.7
⚠️ 8.0 이 한 번 뜨면 그 datadir 은 5.7 이 못 읽어요
이건 "권장하지 않음"이 아니라 지원하지 않음이에요. 기동이 실패하면 그나마 다행이고, 더 나쁜 건 뜨긴 뜨는데 미묘하게 깨진 상태로 도는 경우입니다.
그래서 전환 전에 물리 볼륨을 보존하는 게 선택이 아니라 필수였어요. 논리 백업만 들고 있으면 "복원에 걸리는 시간"만큼은 무조건 장애 시간이 됩니다.

2. 롤백은 되감기가 아니에요

여기까지는 잘 했다고 생각했어요. 그런데 실제로 롤백하는 상황을 머릿속으로 끝까지 돌려보니 이상한 게 나왔습니다.

5.7 볼륨을 다시 붙인다는 건 DB 를 이관 직전 시점으로 되돌린다는 뜻이에요. 그런데 그 사이에 되돌아가지 않는 게 하나 있습니다. 애플리케이션 코드요.

이관하면서 스키마를 표준 규격으로 바꿨거든요. 콜레이션을 표준으로 올리고, 시간 컬럼을 DATETIME(6) 으로 바꾸고, 인덱스 이름도 규칙에 맞게 정리했어요. 그 상태를 기대하는 코드가 이미 배포돼 있습니다.

그런데 5.7 볼륨 안의 테이블은 general_ci 에 초 단위 DATETIME 이에요. 그러면 과거의 데이터와 현재의 코드가 만나는, 한 번도 존재한 적 없는 조합이 만들어집니다.

그림 1. 롤백은 과거로 돌아가는 게 아니라, 처음 보는 조합을 만드는 일이에요
🕳️ 롤백 수단이 있는데 롤백이 안 되는 상태
운영 설정에서 spring.jpa.hibernate.ddl-auto 는 validate 예요. 엔티티와 테이블 매핑이 안 맞으면 기동 자체가 실패합니다.
즉 5.7 볼륨을 붙이면 DB 는 살아나는데 앱이 안 떠요. 새벽에 롤백 버튼을 눌렀는데 서비스가 안 돌아오는 상황이 여기서 만들어집니다.

인증 플러그인도 같은 종류의 함정이에요. 8.0 으로 옮기면서 구형 클라이언트 호환 때문에 mysql_native_password 로 기동 플래그를 줬는데, 5.7 로 되돌아가면 그 조합이 또 달라집니다. 롤백 한 번에 DB 버전, 스키마 규격, 인증 방식이 동시에 바뀌는 거예요. 셋 중 하나만 어긋나도 앱은 안 뜹니다.

정리하면 롤백은 변수 하나를 되돌리는 일이 아니라 여러 개를 동시에 흔드는 일이었어요. 그런데 저는 "볼륨을 보관했다"는 변수 하나만 보고 안심하고 있었습니다.

3. "운이 좋으면 안 잃는다"는 계획이 아니에요

그다음 질문은 데이터였어요. 5.7 볼륨을 붙이면 8.0 으로 전환한 뒤에 쌓인 데이터는 전부 사라집니다. 롤백은 합치는 게 아니라 시계를 되감는 거니까요.

여기서 제가 처음에 한 생각이 이거였어요. "dev 니까, 운이 좋으면 그동안 아무도 안 건드렸을 수도 있지."

그런데 이 문장이 왜 위험하냐면, 롤백한 다음에 운이 좋았는지 나빴는지를 확인할 방법이 없기 때문이에요. 5.7 볼륨을 3306 에 붙이는 순간 8.0 볼륨은 그냥 덮이거나 버려집니다. 비교 대상이 사라져요.

새벽 3시에 서비스는 떴고, 슬랙에 "롤백 완료"라고 쓰려는데 "잃은 게 없다"를 증명할 방법이 없는 상태가 됩니다. 온콜에서 제일 나쁜 건 손실이 아니에요. 손실 여부를 모르는 것입니다. 그러면 그 뒤로 아무 주장도 할 수 없거든요.

"dev 니까 괜찮다"는 생각도 다시 봐야 했어요. dev 는 팀 전체가 같이 쓰는 공용 환경입니다. 누군가는 어제 하루 종일 테스트 데이터를 만들어 뒀을 수 있고, 다른 팀은 그 데이터로 연동 테스트 시나리오를 잡아뒀을 수 있어요.

되돌리는 순간 그게 다 사라지는데, 사라졌다는 사실조차 아무도 모르는 게 진짜 문제입니다. 며칠 뒤에 "어제까지 되던 게 안 되는데요?" 라는 말이 나오고, 그때는 이미 원인을 되짚을 수 없어요.

4. 그래서 롤백 절차의 첫 줄은 "지금 것을 봉인한다"

해결은 생각보다 간단했어요. 5.7 을 붙이기 전에 8.0 볼륨을 먼저 떠놓는 것입니다.

# ❌ 이렇게 시작하면 비교 대상이 사라진다 docker stop app-dev-mysql8 docker run -d -v app-mysql57-data:/var/lib/mysql -p 3306:3306 mysql:5.7 # ✅ 첫 줄은 "지금 것을 봉인" 이다 docker stop app-dev-mysql8 docker volume create app-mysql8-preRollback docker run --rm -v app-mysql8-data:/from -v app-mysql8-preRollback:/to \ alpine sh -c 'cp -a /from/. /to/' # 이제 5.7 을 붙여도 비교 대상이 남아있다

이 세 줄이 들어가면 "운이 좋으면 안 잃는다"가 "무엇을 잃었는지 말할 수 있다"로 바뀝니다. 데이터를 안 잃게 되는 건 아니에요. 잃은 게 뭔지 관측 가능해지는 겁니다. 그 차이가 큽니다.

그리고 봉인만큼 중요한 게 이름이었어요. 제가 보관한 5.7 볼륨은 Docker 가 자동으로 붙인 해시명이었거든요. 유일한 물리 롤백 수단인데 식별자가 알아볼 수 없는 문자열입니다.

안정화되면 정리하려고 "1주 후 청소"라고 적어뒀는데, 그 시점에 볼륨 목록을 보고 어느 게 그건지 확신할 수 있을까요. 옆에 비슷한 볼륨이 서너 개 더 있을 텐데요. 롤백 자산은 이름을 붙여두거나, 최소한 볼륨 ID 를 문서에 명시해둬야 해요. 지울 때 헷갈리는 순간, 그건 롤백 수단이 아니라 사고 원인이 됩니다.

그림 2. 봉인 세 줄이 "운"을 "관측 가능한 사실"로 바꿔줘요

5. 그런데 두 볼륨을 어떻게 비교하죠

봉인을 했다고 칩시다. 이제 5.7 볼륨과 8.0 봉인본을 비교해야 하는데, 여기서 또 막혔어요.

제가 처음 떠올린 건 "청크 단위로 쪼개서 체크섬을 비교한다" 였습니다. 방향은 맞았어요. 실제로 그걸 해주는 업계 표준 도구가 있거든요. Percona Toolkit 의 pt-table-checksum 입니다. 그런데 이 도구는 못 씁니다.

💡 pt-table-checksum 은 복제 토폴로지 전제 도구예요
이 도구는 master 에서 체크섬 쿼리를 실행하고, 그 쿼리가 binlog 를 타고 replica 로 전파돼서 각 서버가 자기 데이터로 계산한 결과를 대조하는 구조예요. 그래서 binlog_format=STATEMENT 를 요구합니다.
제 상황은 복제 관계가 없는 두 개의 볼륨이었어요. 전파될 경로가 없으니 도구를 아예 적용할 수 없습니다.
그림 3. 도구를 고를 때는 기능보다 "이 도구가 뭘 전제하는가"를 먼저 봐야 해요

그럼 무엇을 써야 할까요. 여기가 이 시리즈에서 제일 허무했던 지점입니다. 크로스 메이저 버전 대조에는 딱 맞는 표준 도구가 없어요. CHECKSUM TABLE 도 row format 에 의존해서 5.7 과 8.0 사이의 값 비교를 보장하지 않습니다.

결국 손으로 정규화하는 수밖에 없었어요. 버전과 무관하게 결정적인 값을 직접 뽑아서 대조하는 방식입니다.

-- 양쪽에서 각각 돌려서 결과를 대조한다 SELECT COUNT(*), SUM(CRC32(slug)), SUM(CRC32(IFNULL(s3_key, ''))) FROM landing_page_version;

"업계 표준 도구가 있을 것"이라는 가정이 안 통하는 영역이 있다는 걸 여기서 배웠어요. 그리고 도구가 없다는 걸 새벽 3시에 알게 되면 늦습니다.

🧪 종이 위 롤백 수단은 검증 안 된 가정이에요
제가 문서에 적은 두 줄은 "이렇게 하면 될 것이다" 였지 "이렇게 해봤다" 가 아니었어요. 그 차이를 메우는 방법은 하나뿐입니다. 한가한 시간에 실제로 한 번 돌려보는 것이요.
8.0 봉인 → 5.7 붙이기 → 앱 기동 → 어디서 막히는지 확인 → 원상복구. 이걸 해본 적 없으면, 그 롤백 절차는 아직 문장일 뿐입니다.

리허설을 언제 하느냐도 중요했어요. 롤백이 필요한 순간은 정의상 이미 뭔가 터진 뒤입니다. 그때 처음 해보면 장애 시간 위에 학습 시간이 그대로 얹혀요. 도구를 쓸 수 없다는 것도, 앱이 validate 에서 막힌다는 것도 그 자리에서 알게 되고요.

그래서 아무 일도 없는 평일 오후에 한 번 돌려보는 게 맞습니다. 그때는 실패해도 아무 일도 안 일어나니까요. 리허설의 목적은 성공하는 게 아니라, 어디서 막히는지 미리 알아두는 거예요.

✍️ 오늘의 요약
롤백은 과거로 되돌아가는 게 아니라, 과거 데이터와 현재 코드가 처음 만나는 새 조합을 만드는 일이에요. 그래서 롤백 수단을 보관했다는 것과 롤백할 수 있다는 건 다른 이야기입니다.

롤백 절차의 첫 줄은 "지금 것을 먼저 봉인한다" 여야 해요. 그래야 "운이 좋으면 안 잃는다"가 "무엇을 잃었는지 말할 수 있다"로 바뀝니다.

돌려본 적 없는 롤백 계획은 계획이 아니라 희망이에요.
