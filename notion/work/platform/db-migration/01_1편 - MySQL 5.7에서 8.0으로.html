📚 dev DB 메이저 버전 이관, 1편
dev MySQL 5.7 을 8.0.42 로 옮긴 5단계 ← 지금 이 글
롤백 수단을 보관했다는 착각
검증표가 전부 ✅ 였는데 폭탄이 3개 남아 있었다

새로 만든 테이블 DDL 을 dev 에 올리는데 이런 에러가 떴어요.

ERROR 1273 (HY000): Unknown collation: 'utf8mb4_0900_ai_ci'

전사 표준으로 쓰기로 한 콜레이션인데, dev DB 가 그런 건 모른다고 합니다. 이유는 허무했어요. dev 는 MySQL 5.7 이었고, 그 콜레이션은 8.0 부터 생긴 것이거든요. 그리고 이 서비스의 prod 는 Aurora MySQL 3.10.3, 즉 MySQL 8.0.42 호환 버전이었습니다.

즉 dev 에서 통과한 DDL 이 prod 에서 통과할지, dev 에서 막힌 게 prod 에서도 막힐지 아무것도 보장되지 않는 상태로 몇 달을 쓰고 있었던 거예요. 그래서 dev DB 를 5.7 에서 8.0.42 로 옮겼습니다. 5단계로 나눠서, 매 단계마다 되돌릴 수 있는 상태를 유지하면서요.

1. 메이저 버전이 다르면 뭐가 보장되지 않나

"dev 랑 prod 버전이 좀 다른데 뭐 어때"라고 넘기기 쉬운데, 안 되는 이유가 생각보다 많아요. 콜레이션 하나만 봐도 그렇습니다.

5.7 에서는 utf8mb4_general_ci 나 utf8mb4_unicode_ci 정도를 씁니다. 8.0 에서 기본값이 된 utf8mb4_0900_ai_ci 는 아예 존재하지 않습니다. 그러니까 신규 테이블에 전사 표준을 적용하고 싶어도 dev 에서 그 DDL 을 테스트할 방법 자체가 없었어요. 검증 없이 prod 에 올리는 수밖에요.

예약어도 늘었습니다. 8.0 에서 rank, groups, system, lead 같은 단어가 예약어가 됐어요. 5.7 에서 잘 돌던 쿼리가 8.0 에서 문법 에러로 죽을 수 있다는 뜻입니다. 이런 건 dev 가 5.7 인 채로는 절대 못 잡아요.

그래서 목표를 dev · CI · prod 세 곳의 버전을 8.0.42 하나로 통일하는 것으로 잡았습니다. CI 는 testcontainers 를 쓰고 있었으니 이미지 태그만 mysql:8.0.42 로 고정하면 되고, 문제는 dev 였어요.

2. 백업은 만드는 게 아니라 검증하는 것

제일 먼저 논리 백업을 떴습니다. 여기서 옵션 하나가 중요했어요.

# --all-databases 가 아니라 --databases mysqldump --databases app_db --single-transaction > backup.sql # 검증 1) 중간에 끊기지 않았나 tail -1 backup.sql # -- Dump completed on ... 이 나와야 정상 # 검증 2) 테이블이 다 들어왔나 grep -c 'CREATE TABLE' backup.sql
💡 --databases 와 --all-databases 는 다른 명령이에요
--all-databases 는 mysql 시스템 DB 까지 같이 덤프해요. 그걸 8.0 에 복원하면 5.7 구조의 권한 테이블이 8.0 시스템 테이블 위에 덮여요. 8.0 은 시스템 테이블 구조가 바뀌었기 때문에 여기서 사고가 납니다.
메이저 버전을 넘어갈 때는 내 데이터만 옮기고, 시스템 DB 는 새 버전이 자기가 만든 걸 쓰게 두세요.

그리고 백업은 떴다고 끝이 아니에요. 44MB 파일이 생겼다는 사실이 그 안에 데이터가 온전히 들어있다는 뜻은 아니거든요. 디스크가 차서 중간에 끊겼을 수도 있고요. 그래서 덤프 말미에 -- Dump completed on 이 찍혔는지, CREATE TABLE 개수가 원본 테이블 수와 같은지를 확인했습니다. 이 두 개가 "파일이 있다"를 "복원할 수 있다"로 바꿔주는 최소 조건이에요.

3. 블루그린으로 옮기면 되돌릴 수 있다

제일 무서운 방식은 5.7 컨테이너를 내리고 그 자리에 8.0 을 올리는 거예요. 복원이 실패하면 그때부터 서비스도 없고 검증할 대상도 없습니다.

그래서 8.0 을 3307 포트에 따로 띄웠어요. 3306 의 5.7 은 계속 서비스 중인 상태로요. 복원하고, 검증하고, 통과했을 때만 포트를 바꿨습니다.

# 8.0 을 3307 에 띄운다 — 3306 의 5.7 은 그대로 서비스 중 docker run -d --name app-dev-mysql8 -p 3307:3306 mysql:8.0.42 # "ready for connections" 로그를 믿지 말고 실제 쿼리로 확인 until docker exec app-dev-mysql8 mysql -uroot -p"$PW" -e 'SELECT 1' &> /dev/null; do sleep 2 done
⚠️ "ready for connections" 는 준비 완료가 아니에요
MySQL 컨테이너 로그에 이 문장이 두 번 나와요. 하나는 X Plugin(33060) 것이고 하나는 실제 SQL 포트 것입니다. 앞의 걸 보고 복원을 시작하면 커넥션이 거부돼요.
로그 문자열을 grep 하지 말고, 위처럼 SELECT 1 이 실제로 응답할 때까지 도는 루프를 쓰는 게 안전합니다. 로그는 상태를 말해주지만 응답은 상태를 증명해요.

검증 항목은 세 개였어요. 전 테이블 행수 diff 가 0인지, mysql.user 의 계정이 그대로 넘어왔는지, 그리고 앱이 붙어서 API 가 200 을 주는지를 확인했습니다. 특히 계정은 5.7 → 8.0 에서 인증 플러그인 기본값이 바뀌기 때문에 꼭 봐야 했습니다.

그림 1. 병행 기동해두면 "복원 실패"가 "장애"로 번지지 않아요

4. 진짜 어려운 건 5.7 이 되살아나지 못하게 만드는 것

포트를 바꾸고 API 가 200 을 주는 걸 확인했을 때, 솔직히 다 끝났다고 생각했어요. 그런데 여기가 이 작업에서 가장 많이 놓치는 지점이었습니다.

dev 서버에는 컨테이너를 띄우는 경로가 여러 겹으로 쌓여 있었어요. systemd 유닛이 헬스체크 스크립트를 부르고, 그게 start 스크립트를 부르고, 그게 compose 를 실행하는 구조였습니다. 그리고 그 층 중 두 곳에 5.7 이 문자열로 박혀 있었어요.

지금은 8.0 이 잘 돌고 있지만, 다음 재부팅 때 systemd 가 그 경로를 타면 5.7 컨테이너가 다시 올라옵니다. 그러면 3306 포트를 어느 쪽이 먼저 차지하느냐에 따라 결과가 갈리거나, 최악의 경우 예전 볼륨을 붙인 5.7 이 서비스를 받게 돼요. 며칠 뒤 "데이터가 사라졌다"는 제보를 받고 원인을 못 찾는 상황이 이렇게 만들어집니다.

그림 2. 이관은 데이터를 옮기는 일이 아니라 "옛 버전으로 가는 길"을 끊는 일이에요

그래서 부팅 경로를 전부 따라가면서 5.7 참조를 지웠어요. compose 의 db 서비스는 mysql:8.0.42 + 새 볼륨 + 표준 기동 플래그로 전부 교체하고, 헬스체크·유틸 스크립트의 컨테이너명도 일괄 교체했습니다. crontab 이 따로 없다는 것까지 확인해서 실행 경로가 systemd 하나뿐임을 증명하고 끝냈어요.

그런데 이 작업, 정작 검증은 못 했습니다. "지금 재부팅하면 8.0 이 뜬다"를 증명하는 방법은 실제로 재부팅해보는 것뿐인데, 그걸 안 했으니까요. 코드를 다 고쳤다는 것과 부팅이 실제로 그 코드를 탄다는 건 다른 이야기예요.

5. 인플레이스 업그레이드는 되돌아갈 수 없어요

여기서 성격이 완전히 다른 위험이 하나 등장합니다. MySQL 8.0 은 컨테이너를 새 이미지로 올리면 데이터 디렉터리를 자동으로 업그레이드해줘요. 편한데, 이 변환은 단방향이라 다시 내려갈 수 없습니다.

8.0 이 한 번 손댄 데이터 디렉터리는 5.7 이 못 읽어요. 그래서 물리 볼륨을 따로 보존하는 게 필수였습니다. 논리 백업(44MB SQL 파일)도 있었지만, 그건 복원에 시간이 걸리는 수단이고, 볼륨은 붙이면 바로 뜨는 수단이니까요. 성격이 다른 두 개를 다 들고 있어야 했어요.

🕳️ 놓친 것: 목표 버전을 처음부터 고정하지 않았어요
Phase 2 에서 "8.0" 컨테이너에 복원하고, Phase 4 에서 이미지를 8.0.42 로 교체하는 2단계로 진행했어요. 그런데 만약 Phase 2 가 mysql:8.0 태그였다면 8.0.43 이상을 받았을 수 있고, 그러면 Phase 4 는 업그레이드가 아니라 다운그레이드예요. InnoDB 는 그걸 지원하지 않습니다.
결과적으로는 무사히 지나갔지만, 애초에 첫 컨테이너부터 prod 와 똑같은 패치 버전으로 고정했으면 Phase 4 자체가 필요 없었어요. 2단계로 나눈 대가가 리스크뿐이었던 거죠.

6. 스키마 표준화, 그리고 남겨둔 미봉책

버전이 맞았으니 이제 처음에 하려던 걸 할 수 있게 됐어요. 이미 데이터가 들어있는 테이블 6개를, 데이터를 보존하면서 표준 규격으로 바꿨습니다.

-- ① 콜레이션 — 테이블을 재구성해요 (데이터는 보존) ALTER TABLE landing_page CONVERT TO CHARACTER SET utf8mb4 COLLATE utf8mb4_0900_ai_ci; -- ② 시간 컬럼 정밀도 — 초 단위로는 이벤트 순서가 깨져요 ALTER TABLE landing_page MODIFY created_at DATETIME(6) NOT NULL DEFAULT CURRENT_TIMESTAMP(6); -- ③ 인덱스 명명 — 메타데이터만 바뀌어서 즉시 끝나요 ALTER TABLE landing_page RENAME INDEX uq_lp_slug TO uk_lp_slug;

세 개의 성격이 완전히 달라요. ①은 테이블을 통째로 다시 쓰는 작업이라 데이터가 크면 오래 걸리고, ③은 이름만 바꾸는 거라 메타데이터 수정으로 끝납니다. 같은 ALTER TABLE 이라고 비용이 같지 않아요. prod 에 적용할 때 이 차이를 모르면 예상 시간이 크게 틀립니다.

🕳️ 놓친 것: 콜레이션은 신규 테이블만 바꿨어요
Phase 2 가 5.7 덤프를 논리 복원했기 때문에, 나머지 수십 개 테이블은 5.7 시절 콜레이션(general_ci)을 그대로 들고 왔어요. 표준으로 바꾼 건 신규 6개뿐입니다.
즉 한 DB 안에 콜레이션이 두 종류 섞인 상태가 됐고, 저는 이걸 "표준화 완료"라고 기록했어요. 정확하지 않은 기록이었습니다.

이 혼재가 왜 문제인지가 재미있어요. 콜레이션은 저장되는 바이트를 바꾸지 않습니다. 같은 '한글' 을 넣으면 두 테이블에 완전히 같은 바이트가 들어가요. 콜레이션이 바꾸는 건 비교와 정렬 규칙이거든요.

그래서 저장은 안전한데, 경계를 넘어 문자열을 비교하는 순간 쿼리가 죽습니다.

그림 3. 콜레이션은 저장을 바꾸지 않고 비교를 바꿔요. 그래서 배포 후에 터집니다

다행히 지금은 안 터져요. 신규 테이블이 legacy 를 참조하는 컬럼이 전부 BIGINT 라서 숫자 비교만 하고 있거든요. 숫자에는 콜레이션이 개입하지 않습니다. 그런데 이건 설계를 잘해서가 아니라 아직 지뢰를 안 밟았을 뿐이에요. 문자열로 경계를 넘는 쿼리가 하나 추가되는 날 터집니다. 에러가 안 나도 인덱스를 못 타서 조용히 느려지는 경로가 먼저 생기고요.

그래서 이건 "완료"가 아니라 "혼재 상태: 경계를 넘는 문자열 비교 금지" 로 문서에 남기고 별도 과제로 뺐어요. 전체 테이블 콜레이션 변환은 데이터 크기만큼 시간이 드는 작업이라 이관과 같이 할 일이 아니었습니다.

✍️ 오늘의 요약
메이저 버전 이관은 5단계로 쪼개면 매 단계마다 되돌릴 수 있어요. 백업은 검증까지, 이관은 병행 기동으로, 그리고 옛 버전으로 가는 부팅 경로를 전부 끊어야 끝납니다.

놓친 것도 남았습니다. 목표 버전을 처음부터 고정하지 않아 불필요한 다운그레이드 위험을 만들었고, 콜레이션은 신규 테이블만 바꿨는데 "표준화 완료"라고 적었어요.

결국 데이터를 옮기는 게 어려운 일이 아니었습니다. 어려운 건 옛 버전으로 돌아가는 모든 길을 찾아서 끊는 일이었어요.
