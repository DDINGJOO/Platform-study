배포하는 날의 풍경을 떠올려볼게요. 서버에 접속해서 빌드된 파일을 손으로 올리고, 프로세스를 재시작하고, 브라우저를 새로고침하면서 기도합니다. 어딘가 하나라도 사람 손을 타는 순간, 실수는 시간 문제예요.

AWS는 이 여정 전체를 서비스 몇 개로 쪼개서 자동화해 놨습니다. 이 글이 답할 질문은 하나예요. 코드가 커밋된 순간부터 프로덕션에 뜨기까지, 각 단계를 어떤 AWS 리소스가 받아서 어떻게 다음으로 넘기는가?

1. 개념은 다섯 단계, 일꾼은 넷

소프트웨어 생명주기는 교과서적으로 Code → Build → Test → Deploy → Provision 흐름이에요. AWS에 이걸 얹으면 단계마다 담당 서비스가 하나씩 매핑되는데, 딱 한 군데 겹칩니다. Build와 Test는 별개 단계지만, 실제로는 CodeBuild 한 명이 buildspec 안에서 빌드와 유닛테스트를 같이 처리해요. 테스트 전용 stage를 따로 만들어도 그 안에서 도는 건 결국 CodeBuild입니다.

그리고 Provision, 즉 인프라를 까는 일은 Code 시리즈가 아니라 IaC 도구인 CloudFormation(또는 CDK)의 몫이에요. 이 다섯 단계를 아래처럼 두 층으로 그리면 지도가 완성됩니다.

그림 1. SDLC 다섯 단계는 AWS에서 네 명의 일꾼에게 배정된다

2. 오케스트레이터와 아티팩트 릴레이

CodePipeline은 직접 일하지 않아요. 빌드도, 배포도 남을 시킵니다. 대신 어느 단계가 끝나면 누가 다음인지, 실패하면 어디서 멈출지를 관리하는 오케스트레이터예요.

그럼 단계 사이에 결과물은 어떻게 넘어갈까요? 여기에 이 구조의 핵심이 있습니다. 각 단계의 산출물(아티팩트)은 S3 버킷에 output으로 내려놓고, 다음 단계가 그걸 input으로 집어 드는 릴레이 방식이에요. 바통을 손에서 손으로 건네는 게 아니라, 정해진 사물함에 넣어두면 다음 주자가 꺼내가는 그림입니다. 그래서 파이프라인을 만들면 아티팩트 저장용 S3 버킷이 함께 생겨요.

그림 2. 바통 터치가 아니라 사물함 릴레이

3. 코드는 어떻게 감지되나 — polling vs event

파이프라인의 출발점은 "코드가 바뀌었다"는 신호예요. 이걸 알아채는 방식이 두 가지입니다. polling은 파이프라인이 주기적으로 저장소를 두드려보며 "바뀐 거 있어?"라고 묻는 방식이고, event 기반은 저장소 쪽에서 변경이 생기는 순간 webhook이나 EventBridge로 파이프라인을 깨우는 방식이에요. polling은 지연도 있고 헛질문이 대부분이라, AWS 권장은 event 기반입니다.

event 기반 아키텍처는 응용도 넓어요. 예를 들어 A리전과 B리전 양쪽에서 저장소를 관리하고 싶다면, A리전 repo의 변경 이벤트를 EventBridge가 받아 ECS 태스크를 invoke하고, 그 태스크가 B리전 repo로 git push해서 복제하는 설계가 가능합니다. CodeCommit에 자체 크로스 리전 복제 기능이 없어서 나온 우회 패턴인데, "이벤트가 파이프라인 밖의 일도 시킬 수 있다"는 좋은 예시예요.

⚠️ CodeCommit은 사실상 은퇴 준비 중
2024년 7월부터 CodeCommit은 신규 고객 가입이 막혔어요. 기존 사용자는 계속 쓸 수 있지만, 새 프로젝트라면 Source는 GitHub/GitLab을 CodeStar Connections(콘솔에서는 "연결")로 붙이는 게 표준입니다. 시험공부든 실무든 이 각주는 꼭 달아두세요.

4. 사람 손을 거치는 문 — 수동 승인

프로덕션 배포 직전만큼은 사람이 확인하고 싶을 때가 있죠. 그럴 때 stage 사이에 승인 게이트를 끼워 넣습니다. 액션 설정으로는 owner AWS, category Approval, provider Manual이에요. 승인 요청이 생기면 SNS 토픽으로 이메일을 쏘게 연결할 수 있고요.

여기에 지뢰가 하나 있어요. 이메일을 받는 것과 승인할 수 있는 것은 별개라서, 승인자의 IAM에 파이프라인 조회 권한과 PutApprovalResult 권한이 있어야 합니다. 이메일 링크를 눌렀는데 권한 에러가 나면 십중팔구 이거예요.

{ "Effect": "Allow", "Action": [ "codepipeline:GetPipeline*", // 파이프라인 보기 "codepipeline:PutApprovalResult" // 승인/거부 버튼 누르기 ], "Resource": "arn:aws:codepipeline:*:*:MyPipeline/Prod/ManualApproval" }
💡 승인 게이트 체크리스트
• SNS 발행은 파이프라인 서비스 롤의 몫, 승인 클릭은 승인자 IAM의 몫 — 주체가 달라요
• 승인 대기는 기본 7일, 지나면 파이프라인이 실패 처리돼요
• "approve"라는 액션명은 없어요. 공식 명칭은 PutApprovalResult

5. CloudFormation과 짜는 설계 — 일회용 테스트 인프라

Provision 담당인 CloudFormation을 파이프라인 안으로 끌어들이면 재미있는 설계가 가능해집니다. 빌드가 끝나면 CF가 테스트용 인프라(ALB, ASG, 앱까지)를 스택으로 통째로 세우고, 그 위에서 검증을 돌린 뒤, 테스트 스택을 삭제해서 흔적 없이 치우고, 그다음에야 프로덕션 스택을 배포하는 흐름이에요.

수동으로 서버를 깔던 시절엔 상상 못 할 사치죠. 인프라가 코드이기 때문에, 테스트 환경을 일회용 컵처럼 만들고 버릴 수 있는 거예요. 테스트 환경이 프로드와 미묘하게 다른 "환경 드리프트" 문제도 매번 새로 찍어내니 사라집니다.

그림 3. Test 단계를 확대하면 — 세우고, 검증하고, 부수고, 그다음 프로드

마지막으로 하나 더. 같은 stage 안의 액션들은 runOrder 값으로 순서를 정하는데, 같은 숫자를 주면 병렬로 동시에 실행돼요. 두 리전에 동시에 배포하고, 둘 다 끝나면 스모크 테스트를 돌리는 식의 설계가 숫자 하나로 됩니다.

"actions": [ { "name": "DeployToSeoul", "runOrder": 1 }, { "name": "DeployToTokyo", "runOrder": 1 }, // 같은 숫자 = 병렬 실행 { "name": "SmokeTest", "runOrder": 2 } // 다음 숫자 = 앞이 다 끝나야 시작 ]
✍️ 오늘의 요약
SDLC 다섯 단계(Code→Build→Test→Deploy→Provision)는 AWS에서 GitHub · CodeBuild · CodeDeploy · CloudFormation 네 일꾼에게 배정되고, CodePipeline이 S3 아티팩트 릴레이로 전체를 지휘합니다.

변경 감지는 polling 대신 event로, 프로드 앞엔 수동 승인 게이트(PutApprovalResult 권한 필수)를, 테스트 인프라는 CF로 세웠다 부수는 일회용으로. 결국 파이프라인 설계란 사람 손이 닿는 지점을 의도한 곳 하나로 줄이는 일이에요.
