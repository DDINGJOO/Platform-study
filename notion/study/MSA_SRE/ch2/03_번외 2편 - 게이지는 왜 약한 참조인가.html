Micrometer 시리즈에서 이상한 버그를 하나 만났었죠. 게이지로 큐 길이를 쟀는데 어느 날부터 메트릭이 조용히 NaN이 되는 것이었어요. 게이지가 관측 대상을 "약한 참조"로만 쥔다는 게 원인이었죠. 그런데... 참조에 강하고 약한 게 있다고요?

있어요. 자바의 참조는 사실 4단계고, 이건 GC와 대화하는 언어예요. 게이지의 각주에서 시작해서 JVM의 방 하나를 여는 게 이번 편입니다.

1. 강한 참조: 이름 없는 기본값

먼저 놀라운 사실부터 말하면, 여러분이 지금까지 쓴 모든 참조가 강한 참조입니다.

Order order = new Order(); // ← 이게 강한 참조 this.repository = repo; // ← 이것도 list.add(item); // ← 이것도 (리스트가 item을 강하게 쥠)

StrongReference라는 클래스는 없어요. 강한 참조가 기본값이고, 나머지 셋만 이름이 붙은 거죠. "일반 볼펜"이라는 특수 볼펜이 없는 것과 같아요. 특이한 것들(지워지는 펜, 형광펜)만 이름을 얻는 법이니까요.

GC의 규칙은 이래요. GC 루트(스택의 지역변수, static 필드, 활성 스레드)에서 출발해 강한 참조 사슬을 따라가서, 도달 가능하면 생존, 아니면 수거. 그래서 자바의 메모리 누수란 "안 쓰는 객체를 누군가 강한 참조로 계속 쥐고 있는 상태"예요. static 컬렉션에 넣고 안 빼는 경우가 전형이죠.

2. 약한 참조: 투표권 없는 구경꾼

이제 게이지의 그 "약한 참조(WeakReference)"예요. 계약이 명확합니다: "나는 이 객체를 가리키지만, 살릴지 말지 투표에서 나를 세지 마."

Object obj = new Object(); WeakReference<Object> ref = new WeakReference<>(obj); ref.get(); // → 객체 (아직 obj라는 강한 참조가 있으니까) obj = null; // 강한 참조 소멸. 이제 약한 참조"만" 남음 System.gc(); ref.get(); // → null (수거됨)

약한 참조만 남은 객체는 다음 GC에서 수거 대상이 돼요. Micrometer 게이지의 실제 구현이 정확히 이 구조예요:

public class DefaultGauge<T> implements Gauge { private final WeakReference<T> ref; // ← 약하게만 쥔다 public double value() { // 발행 시점마다 호출 T obj = ref.get(); if (obj != null) return f.applyAsDouble(obj); return Double.NaN; // ← 그 NaN의 출처! } }

왜 이렇게 설계했을까요? 관측 도구가 관측 대상의 수명을 연장하면 안 되니까요. 감시 카메라가 피사체를 못 떠나게 붙잡으면 이상하잖아요. 앱이 버린 객체는 게이지가 있든 말든 GC가 치울 수 있어야 해요. 그 대가가 바로 그 버그입니다. 게이지"만" 아는 객체는 수거되고, 메트릭은 조용히 NaN이 되죠. 해법은 관측 대상을 비즈니스 코드가 필드로(강하게) 소유하는 것이고요.

같은 철학의 대표 사용처가 WeakHashMap이에요. 키를 약하게 쥐는 맵인데, 주 객체(키)가 앱 어디에서도 안 쓰이게 되면 엔트리가 자동으로 사라져요. "본체가 죽으면 부가 정보도 따라 죽는" 구조라서, 수동 remove() 없이 누수를 막죠. 여기서 파생된 유명한 함정이 ThreadLocal 누수예요: 내부 맵의 키(ThreadLocal)는 약한데 값은 강해서, 키만 수거되고 값이 좀비로 남을 수 있어요. 스레드풀처럼 스레드가 안 죽는 환경에서 remove()를 부르라는 잔소리의 근원이 이 비대칭이에요.

3. 소프트 참조: 메모리가 궁할 때만 버려라

강함과 약함 사이에 SoftReference가 있어요. 계약: "GC가 돌아도 살려두되, 메모리가 부족해지면 버려도 좋다." JVM은 OutOfMemoryError를 던지기 전에 소프트 참조를 전부 수거하는 걸 보장해요. "남는 메모리를 캐시로 쓰다가 필요하면 반납"인 셈이니, 이론상 캐시에 완벽해 보이죠.

그런데 실무 반전: 요즘 캐시 라이브러리들은 소프트 참조를 안 써요. 수거 시점을 JVM 힙 사정이 정하니 캐시 동작이 비결정적이 되거든요. 힙 크기를 바꾸면 히트율이 변하고, GC 정책을 바꾸면 캐시가 통째로 사라집니다. Guava와 Caffeine의 결론은 "제어할 수 없는 자동보다 제어 가능한 수동"이었어요. 명시적 크기 제한과 LRU 계열이죠. 좋아 보이는 메커니즘도 예측 가능성이 없으면 운영 도구로는 실격이라는, 꽤 보편적인 교훈이에요.

4. 팬텀 참조: 장례식 알림 서비스

마지막 하나는 기괴합니다. PhantomReference는 get()이 항상 null이에요. 객체에 접근하는 용도가 아예 아니라는 뜻이죠. 그럼 어디에 쓰느냐면, "그 객체, 수거됐어요"라는 통지를 받는 용도예요.

ReferenceQueue<Resource> queue = new ReferenceQueue<>(); PhantomReference<Resource> ref = new PhantomReference<>(resource, queue); // 별도 스레드에서 Reference<?> dead = queue.remove(); // 수거가 일어나면 깨어남 ⚰️ // → "죽었어요" 통지 수신 → 연관 네이티브 메모리 해제 등 뒷정리

참조가 수거되면 그 껍데기가 ReferenceQueue에 들어와요. 장례식 알림인 셈이죠. 용도는 finalize()의 대체품이에요. finalize는 부활 가능(안에서 this를 어딘가 담으면 되살아남!), 실행 보장 없음, 성능 재앙으로 퇴출됐는데, 팬텀은 get()이 null이라 부활이 원천 불가능해서 안전해요. JDK 9+의 Cleaner API가 이걸로 구현돼 있고, DirectByteBuffer의 네이티브 메모리 해제가 대표 사용처예요. 직접 쓸 일은 드물지만 "자바가 finalize를 어떻게 버렸나"의 답이 이거예요.

5. 한 장으로 정리

그림 1. 참조 4단계 스펙트럼: GC에 보내는 네 가지 신호
🧠 기억법
강 = 소유("내 거야, 치우지 마") / 소프트 = 여유("공간 남으면 놔둬") / 약 = 구경("보고만 있을게, 치워도 돼") / 팬텀 = 조문("가면 알려만 줘")
✍️ 오늘의 요약
자바 참조는 GC에 보내는 4가지 신호다. 강한 참조는 이름조차 없는 기본값(도달 가능 = 생존)이고, 약한 참조는 "관찰하되 수명에 개입하지 않겠다"는 선언이라 게이지와 WeakHashMap의 재료가 되며, 소프트는 이론상 캐시용이지만 비결정성 때문에 밀려났고, 팬텀은 부활 불가능한 finalize의 후계자다.

게이지의 NaN 버그 하나를 따라왔을 뿐인데 GC의 방까지 왔다. 좋은 도구의 설계 결정은 이렇게 그 아래 층의 문을 열어주는 법이다.
