🚀 배포 안전성, 4편
1편. 같은 앱도 플랫폼마다 다른 모양으로 포장된다
2편. 한 번에 하나만 살아남는 배포
3편. 카나리는 누구와 비교하느냐가 전부다
4편. 깃옵스는 배포를 밀지 않고 당긴다 ← 지금 이 글
실습-1. 하이랜더와 블루그린을 Argo Rollouts로 돌려 본다
실습-2. 카나리를 통계로 판정해 자동으로 되돌린다
실습-3. 클러스터를 손으로 고치면 깃옵스가 되돌린다

금요일 밤 11시, 주문 API가 느려집니다. 당직자가 터미널을 열어 kubectl scale로 파드를 두 개에서 여섯 개로 늘리고, 메모리 한도도 kubectl edit로 올려요. 20분 뒤 그래프가 내려오고 다들 잠자리에 듭니다. 월요일 오전, 누군가 다른 기능을 배포합니다. CI 파이프라인이 Git에 있는 매니페스트로 kubectl apply를 돌리고, 파드는 다시 두 개, 메모리 한도는 예전 값으로 돌아가요. 점심 무렵 같은 장애가 납니다.

금요일의 수정은 어디에도 기록되지 않았습니다. 클러스터에는 있었지만 Git에는 없었고, 파이프라인은 그 사실을 몰랐어요. 파이프라인은 실행되는 순간에만 클러스터를 보기 때문입니다. 이번 편은 이 틈을 다른 방향에서 메우는 방법인 깃옵스(GitOps)를 다룹니다. 배포를 밖에서 밀어 넣지 않고, 클러스터 안의 에이전트가 Git을 당겨 와서 계속 맞추는 방식이에요.

🧭 이 글에서 확인할 것
• 파이프라인이 kubectl apply로 끝나는 배포는 무엇을 놓치나?
• 깃옵스의 원칙 네 가지는 정확히 무엇을 요구하나? Git 이벤트로 스크립트를 돌리면 깃옵스인가?
• Argo CD는 Git의 변화와 클러스터의 변화를 각각 얼마나 빨리 알아채나?
• Git에서 지운 리소스, Git에 넣을 수 없는 시크릿은 어떻게 다루나?
• 파이프라인에 있던 테스트는 어디로 옮겨 가나?

1. 밀어 넣는 배포는 배포가 끝나면 클러스터를 보지 않는다

흔한 CI/CD 파이프라인은 이렇게 생겼습니다. 코드를 받아 린트와 단위 테스트를 돌리고, 컨테이너 이미지를 빌드해 레지스트리에 올리고, 마지막 단계에서 kubectl apply나 helm upgrade로 클러스터에 적용해요. 단계는 시간 순서로 돌고, 한 단계가 실패하면 파이프라인이 멈춥니다. 이런 구조를 푸시형 배포라고 불러요. 바깥의 파이프라인이 클러스터 쪽으로 변경을 밀어 넣기 때문입니다.

푸시형에는 구조에서 오는 약점이 셋 있습니다.

첫째, 파이프라인이 클러스터 자격증명을 가집니다. 마지막 단계에서 kubectl apply를 하려면 CI 러너에 클러스터 자격증명이 있어야 해요. 운영 클러스터가 여러 개면 자격증명도 여러 개가 CI에 모입니다. CI 도구가 배포까지 맡으면 관심사가 섞이고, 공격받기 쉬운 시스템에 운영 환경 접근 권한을 주게 돼요(Weaveworks의 주장, InfoQ 2018 소개 기사).

둘째, 파이프라인은 배포한 뒤의 클러스터를 보지 않습니다. 파이프라인이 성공했다는 건 "그 시점에 apply가 성공했다"는 뜻이에요. 그 뒤에 누가 kubectl edit로 값을 바꿔도 파이프라인은 다음 실행 때까지 모릅니다. 서두의 금요일 밤이 정확히 이 경우였어요. Git과 클러스터가 서로 다른 말을 하는 상태가 주말 내내 이어졌습니다.

📖 용어: 드리프트 (drift)
실제로 돌고 있는 시스템의 상태가 원하는 상태에서 벗어났거나 벗어나는 중인 것입니다. 손으로 고친 설정, 다른 컨트롤러가 바꾼 값, 지운 줄 알았는데 남아 있는 리소스가 모두 드리프트예요.

셋째, 실패한 배포는 저절로 되돌아가지 않습니다. 배포 단계가 성공하고 그다음의 기능 테스트 단계가 실패했다고 해 볼게요. 파이프라인은 빨간불로 끝나지만 클러스터에는 새 버전이 이미 올라가 있습니다. 파이프라인 실행이 실패로 표시된다고 해서 앞 단계가 한 일이 취소되지는 않으니까요. 되돌리려면 이전 커밋으로 파이프라인을 다시 돌리거나 롤백 단계를 따로 짜 넣어야 합니다.

셋 다 원인이 같아요. 푸시형 배포에서 "클러스터가 지금 어떤 상태인가"를 책임지는 주체가 없습니다. 파이프라인은 변경을 전달할 뿐이고, 전달한 뒤의 상태는 아무도 지켜보지 않아요.

2. 깃옵스의 네 가지 원칙

깃옵스라는 말은 2017년 Weaveworks가 "operations by pull request"라는 블로그 글로 소개하면서 퍼졌다고 알려져 있어요. 원래 글이 있던 Weaveworks 사이트는 지금 열리지 않고, 지금 기준이 되는 정의는 CNCF 아래의 OpenGitOps 프로젝트가 2021년에 낸 원칙 v1.0.0입니다. 원문은 네 줄이에요.

1. Declarative A system managed by GitOps must have its desired state expressed declaratively. 2. Versioned and Immutable Desired state is stored in a way that enforces immutability, versioning and retains a complete version history. 3. Pulled Automatically Software agents automatically pull the desired state declarations from the source. 4. Continuously Reconciled Software agents continuously observe actual system state and attempt to apply the desired state.

옮기면 이렇습니다. 원하는 상태를 선언형으로 적는다. 그 선언을 고칠 수 없고 버전이 붙으며 전체 이력이 남는 곳에 둔다. 소프트웨어 에이전트가 그 선언을 자동으로 당겨 온다. 에이전트가 실제 상태를 계속 관찰하면서 원하는 상태를 적용하려고 시도한다.

📖 용어: 원하는 상태 (desired state)
OpenGitOps 용어집은 "시스템을 다시 만들기에 충분한 설정 데이터 전체"로 정의해요. 쿠버네티스라면 Deployment, Service, ConfigMap 같은 매니페스트 묶음입니다. 어떤 명령을 어떤 순서로 실행하라는 절차는 들어가지 않고, 끝났을 때 무엇이 있어야 하는지만 적어요.

네 줄에서 두 가지를 짚고 넘어갈게요.

원칙에는 Git이라는 단어가 없습니다. 2번이 요구하는 건 "고칠 수 없고, 버전이 붙고, 전체 이력이 남는 저장소"이고, 용어집은 이걸 상태 저장소(state store)라고 부르며 변경에 대한 접근 제어와 감사 기록도 요구해요. Git이 이 조건을 가장 쉽게 채우니 대부분 Git을 쓰지만, Argo CD와 Flux는 OCI 레지스트리에 올린 매니페스트도 원천으로 받습니다. 그리고 "Git에 있다"만으로 2번이 채워지지는 않아요. 누구나 main 브랜치에 강제 푸시할 수 있다면 이력은 고쳐질 수 있고, 감사도 안 됩니다. 브랜치 보호와 리뷰가 원칙의 일부인 셈이에요.

Git 이벤트로 스크립트를 돌리는 것은 깃옵스가 아닙니다. "커밋이 들어오면 파이프라인이 자동으로 배포한다"를 깃옵스로 소개하는 글이 꽤 있는데, 그건 1장의 푸시형 파이프라인에 트리거를 단 것이에요. 3번과 4번이 빠져 있습니다. 당기는 주체가 클러스터 쪽 에이전트가 아니고, 배포가 끝난 뒤에 실제 상태를 계속 보는 주체도 없어요. 깃옵스를 가르는 건 저장소의 종류가 아니라 누가 당기고, 누가 계속 맞추느냐입니다.

그림 1. 자격증명이 어디 있느냐와 배포 뒤에 누가 보느냐가 함께 바뀐다
📖 용어: 조정 (reconciliation)
실제 상태가 원하는 상태와 같아지도록 만드는 과정입니다. 쿠버네티스 컨트롤러들이 원래 이렇게 동작해요. Deployment 컨트롤러가 "파드 세 개"라는 선언을 보고 모자라면 만들고 남으면 지우는 것도 조정이고, 깃옵스 에이전트는 같은 일을 Git과 클러스터 사이에서 합니다.

Argo CD 문서도 같은 이점을 적어 둡니다. 자동 동기화를 켜면 CI/CD 파이프라인이 Argo CD API 서버에 직접 접근할 필요가 없어지고, 대신 추적 중인 Git 저장소에 매니페스트 변경을 커밋하고 푸시하면 된다고요. CI의 마지막 일은 kubectl apply가 아니라 커밋이 됩니다.

대신 잃는 것도 있어요. 푸시형 파이프라인은 kubectl rollout status를 기다렸다가 성공과 실패를 파이프라인 결과로 돌려줄 수 있었습니다. 풀형에서 CI는 커밋을 남기고 끝나니, 배포가 실제로 끝났는지, 새 버전이 건강한지를 CI 화면에서 알 수 없어요. 그 정보는 이제 에이전트 쪽에 있습니다. Argo CD라면 Application의 동기화 상태와 헬스를 보거나, 알림 컨트롤러로 동기화 성공·실패와 헬스 저하를 채팅이나 웹훅으로 보내야 해요. 그리고 에이전트 자신은 누가 설치하고 업그레이드하느냐는 질문도 남습니다. 흔히 처음 한 번은 손이나 스크립트로 설치하고, 그 뒤로는 Argo CD가 자기 설정 저장소를 바라보게 해서 스스로를 관리하게 해요.

3. 계속 맞춘다: 폴링, 워치, selfHeal

4번 원칙의 "continuously"는 "즉시"와 다릅니다. 용어집은 조정이 계속 일어난다는 뜻이지 순간적이어야 한다는 뜻은 아니라고 따로 적어 두었어요. 그러면 실제 도구는 얼마나 자주 맞출까요? Argo CD를 기준으로 보면 변화가 들어오는 길이 둘이고, 길마다 속도가 다릅니다.

Git 쪽 변화는 폴링으로 알아챕니다. Argo CD는 Git 저장소를 주기적으로 다시 읽어요. 흔히 "3분마다"라고 알려져 있고 웹훅 문서도 그렇게 적지만, 정확히는 기본 120초에 최대 60초의 무작위 지연(지터)을 더한 값입니다. FAQ와 컨트롤러 소스(defaultAppResyncPeriod = 120, defaultAppResyncPeriodJitter = 60)가 같은 값을 말하고, 자동 동기화 문서는 이를 "최대 3분"으로 요약해요.

그런데 소스를 따라가 보면 3분은 상한이 아닙니다. 늦어지는 이유가 두 가지 있어요. 하나는 주기의 기준입니다. 컨트롤러는 120초마다 Application을 훑으면서 마지막으로 Git과 비교한 시각(reconciledAt)이 120초를 넘었는지를 봐요. 동기화 직후처럼 다른 이유로 비교가 막 일어났다면 그 차례를 건너뛰고 다음 차례까지 기다립니다. 다른 하나는 캐시입니다. 브랜치 이름(main)을 커밋 해시로 바꾸는 일은 repo-server가 하는데, 그 결과를 기본 3분 동안 캐시해요(--revision-cache-expiration). 주기 새로고침은 이 캐시를 그대로 쓰기 때문에, 푸시 직전에 캐시된 옛 해시를 보고 "바뀐 것 없음"으로 끝날 수 있습니다. 사람이 누른 새로고침이나 웹훅이 일으킨 새로고침은 이 캐시를 건너뛰어요.

그래서 폴링에만 기대면 반영 시간은 "몇 분"으로 잡는 게 맞습니다. 이 대기가 싫으면 Git 서버가 푸시 직후 Argo CD의 /api/webhook을 부르도록 웹훅을 겁니다.

웹훅을 걸어도 풀형이라는 성질은 그대로예요. 웹훅이 전하는 건 "저장소가 바뀌었으니 다시 읽어 보라"는 알림뿐이고, 매니페스트를 가져와 적용하는 건 여전히 클러스터 쪽 에이전트입니다. 웹훅이 빠져도 폴링이 남아 있으니 늦어질 뿐 놓치지는 않아요. FAQ가 폴링 주기를 0으로 꺼서 웹훅에만 기대는 설정을 권하지 않는 이유도 이겁니다.

클러스터 쪽 변화는 워치로 알아챕니다. Argo CD 컨트롤러는 관리하는 리소스를 쿠버네티스 API의 워치로 지켜보는 캐시를 들고 있어요. 누가 kubectl scale로 Deployment를 바꾸면 그 이벤트가 캐시로 들어오고, 컨트롤러는 그 리소스를 가진 Application을 다시 비교하라는 요청을 큐에 넣습니다(소스의 handleObjectUpdated). 폴링 주기를 기다리지 않아요.

그림 2. 비교는 두 방향에서 시작되고, 적용은 selfHeal이 허락할 때만 일어난다

그런데 알아채는 것과 되돌리는 것은 별개입니다. 자동 동기화(syncPolicy.automated)만 켜면 Argo CD는 Git에 새 커밋이 생겼을 때 동기화해요. 클러스터에서 누가 손으로 바꾼 것은 OutOfSync로 표시만 하고 그대로 둡니다. 문서는 이렇게 적어요. 기본적으로 라이브 클러스터에 가한 변경은 자동 동기화를 일으키지 않고, 그렇게 하려면 selfHeal을 켜야 한다고요.

📖 용어: selfHeal
Argo CD 자동 동기화의 옵션입니다. 켜 두면 Git은 그대로인데 클러스터가 Git과 달라졌을 때도 Git의 상태로 다시 적용해요. 끄면 차이를 화면에 표시만 합니다.

selfHeal이 얼마나 빨리 되돌리는지는 문서와 소스가 다르게 말합니다. 자동 동기화 문서에는 "self-heal 타임아웃(기본 5초) 뒤에 다시 시도한다"고 적혀 있어요. 그런데 3.5.4 소스의 기본값은 고정 타임아웃이 아니라 지수 백오프입니다. 시작 2초, 배수 3, 상한 300초(--self-heal-backoff-timeout-seconds, -factor, -cap-seconds)예요. 2024년 10월에 병합된 PR이 기본 동작을 지수 백오프로 바꿨고, 문서 한 줄이 그 뒤를 따라가지 못한 것으로 보입니다. 문서가 가리키는 --self-heal-timeout-seconds 플래그도 --self-heal-backoff-timeout-seconds를 0으로 꺼야 효과가 있어요.

selfHeal 시도 횟수(autoHealAttemptsCount)에 따른 대기 시간, 3.5.4 소스 기준 횟수 0 1 2 3 4 5 6 이상 대기 0초 2초 6초 18초 54초 162초 300초(상한) 실제 대기 = 위 값 − 직전 동기화가 끝난 뒤 흐른 시간 (0보다 작으면 바로)

여기서 중요한 건 횟수가 어디에 쌓이느냐예요. 횟수는 Application의 operation 상태에 들어 있고, 같은 Git 리비전에서 selfHeal을 할 때마다 하나씩 늘어납니다. 3.3 전에는 일정 시간 동안 동기 상태가 유지되면 횟수를 0으로 되돌리는 쿨다운 옵션이 있었는데, 그 옵션이 오히려 횟수를 너무 자주 0으로 만들어 백오프가 무력해지는 문제가 있어 3.3에서 효과 없는 옵션이 됐어요. 그래서 지금은 시간이 지나도 횟수가 내려가지 않고, 새 동기화 작업이 시작될 때만 0이 됩니다. 새 커밋의 자동 동기화, 사람이 누른 수동 동기화, Application의 source 스펙 변경이 그런 경우예요. 반대로 이 앱의 경로를 건드리지 않은 커밋은 새 동기화를 만들지 않을 수 있습니다. 손으로 고치는 일이 드물면 매번 바로 되돌리지만, 다른 컨트롤러가 같은 필드를 계속 바꾸는 상황이라면 되돌리는 간격이 몇 분까지 벌어져요. 이 백오프는 Argo CD와 다른 컨트롤러가 같은 필드를 놓고 끝없이 서로 덮어쓰며 API 서버를 두드리는 상황을 막으려고 들어간 것입니다.

⚠️ 주의: Git에 없는 필드는 드리프트가 아니다
• Argo CD의 기본 비교 방식(legacy)은 실제 상태, 원하는 상태, last-applied-configuration 어노테이션 셋을 놓고 비교합니다. 매니페스트에 없는 라벨을 손으로 붙이면 비교 대상이 아니라서 Synced로 남고, selfHeal도 그 라벨을 지우지 않아요
• 반대로 HPA가 바꾸는 replicas처럼 Git에도 있고 다른 컨트롤러도 바꾸는 필드는 끝없는 드리프트가 됩니다. 매니페스트에서 그 필드를 빼거나 ignoreDifferences로 비교에서 제외해야 해요
• Git에 처음부터 없던 리소스는 Argo CD의 관리 대상이 아닙니다. 같은 네임스페이스에 손으로 만든 리소스는 지워지지 않고, 기본 설정에서는 화면에도 나오지 않아요

Flux는 같은 원칙을 조금 다르게 구현합니다. GitRepository의 interval은 필수 필드이고, Kustomization도 자기 interval마다 매니페스트를 다시 만들어 서버 측 적용의 드라이런으로 드리프트를 찾고 고쳐요. 클러스터 쪽 변화를 이벤트로 바로 잡는 Argo CD와 달리 주기마다 맞추는 쪽에 가깝습니다. 어느 쪽이든 "계속"의 실제 의미는 도구의 주기와 트리거가 정해요.

4. 지운 것과 넣을 수 없는 것: prune과 시크릿

Git에서 service.yaml을 지우고 푸시했다고 해 볼게요. Argo CD는 그 Service가 이제 원하는 상태에 없다는 걸 알아챕니다. 그런데 자동 동기화를 켜 두었어도 기본값으로는 지우지 않아요. 문서는 이걸 "안전장치"라고 부릅니다. 자동 동기화는 기본적으로 Git에 더 이상 정의되지 않은 리소스를 삭제하지 않고, 지우려면 prune: true를 켜거나 사람이 prune을 체크해서 수동 동기화를 해야 해요.

📖 용어: prune
Git에서 사라진 리소스를 클러스터에서도 지우는 동작입니다. Argo CD는 자기가 만든 리소스에 추적 어노테이션(argocd.argoproj.io/tracking-id, 3.0부터 기본)을 달아 두고, 그 표시가 있는 리소스만 지울 후보로 봐요.

prune을 켜면 또 하나의 안전장치가 붙습니다. 동기화 결과로 Application의 리소스가 전부 지워지게 되는 경우에는 지우지 않아요. 경로를 잘못 바꾸거나 디렉터리를 통째로 옮긴 커밋 하나가 서비스를 통째로 내리는 걸 막는 장치이고, 정말 비우고 싶으면 allowEmpty: true를 같이 줘야 합니다. 깃옵스에서는 Git의 삭제가 곧 운영 환경의 삭제라서, 삭제만큼은 한 번 더 확인하도록 기본값이 짜여 있어요.

시크릿은 반대 문제입니다. 지우는 게 아니라 처음부터 Git에 넣을 수 없어요. 그런데 원하는 상태는 시스템을 다시 만들기에 충분해야 하고, DB 비밀번호 없이는 시스템이 다시 서지 않습니다. 쿠버네티스 Secret을 그대로 커밋하면 안 되는 이유는 분명해요. 쿠버네티스 문서도 Secret은 기본적으로 etcd에 암호화되지 않은 채 저장되고, 네임스페이스에 파드를 만들 수 있는 사람은 그 네임스페이스의 Secret을 읽을 수 있다고 경고합니다. data 필드의 base64는 인코딩일 뿐이에요.

해법은 크게 두 갈래입니다.

암호문을 Git에 넣는다. Sealed Secrets는 클러스터 안 컨트롤러의 공개 키로 Secret을 암호화한 SealedSecret 리소스를 만들어요. README에 따르면 이 암호문은 대상 클러스터의 컨트롤러만 풀 수 있어서 공개 저장소에 둬도 되고, 기본 범위(strict)에서는 이름과 네임스페이스까지 암호문에 묶여 다른 곳으로 옮기면 풀리지 않습니다. SOPS로 파일 일부를 암호화해 커밋하는 방식도 같은 갈래예요.

참조만 Git에 넣는다. External Secrets Operator는 "이 Secret의 값은 외부 비밀 저장소의 이 경로에서 가져와라"는 리소스만 Git에 두고, 실제 값은 클러스터 안 오퍼레이터가 Vault나 클라우드의 비밀 관리 서비스에서 받아 와 Secret을 만들어요. Secrets Store CSI 드라이버는 값을 파드에 파일로 마운트합니다.

Argo CD 문서는 둘 다 "대상 클러스터에서 채우는" 방식으로 묶어 강하게 권하고, 반대로 Argo CD가 매니페스트를 만드는 단계에서 플러그인으로 비밀 값을 끼워 넣는 방식(argocd-vault-plugin 같은)은 강하게 말립니다. 이유가 구체적이에요. Argo CD가 생성한 매니페스트를 Redis 캐시에 평문으로 저장하기 때문에 끼워 넣은 비밀 값도 거기 평문으로 남고, 비밀 값의 갱신이 관계없는 배포의 동기화에 묶이기 때문입니다.

5. 파이프라인의 테스트는 어디로 가나

깃옵스로 바꾸면 CI 파이프라인이 사라질까요? 아니요. CI는 커밋에서 멈출 뿐, 커밋 전에 할 수 있는 검사는 전부 그대로 CI에 남습니다.

린트, 단위 테스트, SAST, 시크릿 검사(4장의 비밀 값이 실수로 커밋됐는지 보는 검사)는 커밋 전에 끝나니 CI에 남아요.

보안 테스트 중 SAST(정적 애플리케이션 보안 테스트)는 소스 코드와 의존 라이브러리를 읽어 알려진 취약점과 위험한 코드 사용을 찾아요. DAST(동적 애플리케이션 보안 테스트)는 실행 중인 애플리케이션 바깥에서 공격용 입력을 넣어 봅니다. OWASP DevSecOps 가이드라인의 정의도 "실행 중인 애플리케이션에 악의적인 페이로드를 주입해 보안 취약점과 약점을 찾는 것"이에요. DAST는 떠 있는 애플리케이션이 필요하니 스테이징 배포 뒤에 돌리는 경우가 많아요.

📖 용어: 동기화 훅 (sync hook)
Argo CD가 동기화의 특정 단계에서 실행하는 리소스입니다. 어노테이션 argocd.argoproj.io/hook에 PreSync, Sync, PostSync, SyncFail 같은 값을 주면, 보통 Job으로 만든 작업이 매니페스트 적용 앞이나 뒤에 돌아요.

CI에서 할 수 없는 검사는 클러스터 쪽으로 옮겨 갑니다. 새 버전이 올라가기 전에 해야 하는 DB 마이그레이션은 PreSync 훅으로, 올라간 뒤의 스모크 테스트는 PostSync 훅으로 두는 게 Argo CD 문서가 드는 예예요. PreSync 훅이 실패하면 동기화 전체가 멈추고 새 매니페스트는 적용되지 않습니다. 순서가 필요한 리소스는 argocd.argoproj.io/sync-wave 어노테이션으로 웨이브를 나눠요. 낮은 번호부터 적용하고, 앞 웨이브가 동기화되고 Healthy가 돼야 다음 웨이브로 넘어가요. 그리고 웨이브 하나를 적용한 직후에는 다른 컨트롤러가 반응할 시간을 주려고 기본 2초(ARGOCD_SYNC_WAVE_DELAY)를 쉽니다(소스의 delayBetweenSyncWaves). 이 2초는 Healthy가 된 뒤에 더하는 시간이 아니라 Healthy가 되기를 기다리는 시간과 겹쳐요. 그래서 2초 안에 Healthy가 되는 리소스라면 웨이브 간격은 2초 남짓입니다.

그림 3. 커밋 전에 할 수 있는 검사는 CI에, 클러스터가 있어야 하는 검사는 동기화 안에

헬스 체크도 배포의 일부입니다. Argo CD는 Deployment의 롤아웃이 끝나야 Healthy로 보고, 롤아웃은 파드의 레디니스 프로브가 통과해야 끝나요. 이때 프로브에 무엇을 넣을지가 중요합니다. 쿠버네티스 문서에 따르면 리브니스 프로브가 실패하면 kubelet이 컨테이너를 재시작하고, 레디니스 프로브가 실패하면 그 파드를 서비스의 엔드포인트에서 뺄 뿐 재시작하지 않아요. 그리고 백엔드 의존성 확인은 레디니스에 두고 리브니스는 앱 자신이 건강한지만 보라고 권합니다. DB 확인을 리브니스에 넣으면 DB가 잠깐 아플 때 멀쩡한 파드가 전부 재시작해 장애를 키워요.

마지막으로 롤백입니다. 깃옵스에서 롤백은 Git의 되돌리기 커밋이에요. git revert로 이전 상태를 새 커밋으로 만들고 푸시하면 에이전트가 그 상태로 맞춥니다. Argo CD에도 이전 동기화 이력으로 돌아가는 argocd app rollback 명령이 있지만, 문서는 자동 동기화가 켜진 Application에서는 롤백을 할 수 없다고 적어요. 클러스터만 되돌리면 Git과 다시 어긋나고, 자동 동기화가 곧바로 Git 쪽으로 되돌려 놓을 테니까요.

⚠️ 주의: Synced는 성공이 아니다
Argo CD의 동기화 상태(Synced/OutOfSync)와 헬스(Healthy/Progressing/Degraded)는 다른 축입니다. 존재하지 않는 이미지 태그를 커밋하면 매니페스트 적용은 성공하니 Synced가 되지만, 새 파드는 이미지를 받지 못해 헬스는 Progressing을 거쳐 Degraded로 갑니다. Argo CD는 여기서 이전 버전으로 자동으로 돌아가지 않아요. 헬스를 보고 판정해 되돌리는 일은 Argo Rollouts 같은 점진적 배포 도구나 사람의 git revert 몫입니다. 1장의 셋째 약점은 깃옵스만으로 풀리지 않아요. 바뀌는 건 되돌리는 방법이 커밋 하나로 정해진다는 점이에요.
💡 실무에서는
• 애플리케이션 코드 저장소와 배포 매니페스트 저장소를 나누는 경우가 많아요. CI는 이미지를 빌드한 뒤 매니페스트 저장소의 이미지 태그만 바꾸는 커밋을 남깁니다
• 매니페스트 저장소의 main 브랜치는 보호하고 리뷰를 거쳐 병합해요. 원칙 2번의 "고칠 수 없는 이력"은 도구가 아니라 저장소 설정이 지킵니다
• 웹훅을 걸어도 폴링 주기는 0으로 끄지 않아요. 웹훅이 한 번 빠지면 그 변경은 다음 폴링까지 반영되지 않습니다
• 장애 중에 손으로 고쳐야 한다면 selfHeal이 되돌린다는 걸 먼저 떠올려요. 같은 변경을 Git에 커밋하거나, 그 Application의 자동 동기화를 잠시 끄고 고친 뒤 Git에 반영하고 다시 켭니다
• 시크릿은 암호문이나 참조만 Git에 둬요. 매니페스트 생성 단계에서 값을 끼워 넣는 플러그인은 Argo CD 문서가 말리는 방식입니다
✍️ 오늘의 요약
깃옵스는 Git에 배포 트리거를 다는 일이 아니라, 클러스터 안의 에이전트가 원하는 상태를 당겨 와서 실제 상태와 계속 맞추게 하는 일이에요. OpenGitOps 원칙 네 가지(선언형, 버전과 불변, 자동으로 당기기, 지속적 조정) 중 뒤의 둘이 푸시형 파이프라인과 갈리는 지점입니다.

Argo CD는 Git의 변화를 기본 120초에 지터 최대 60초 주기로 폴링하거나(캐시 때문에 실제로는 몇 분까지 늦어질 수 있어요) 웹훅으로 알아채고, 클러스터의 변화는 워치로 바로 알아채요. 손으로 바꾼 것을 되돌리는 건 selfHeal을 켰을 때만이고, 그 간격은 지수 백오프로 최대 300초까지 벌어집니다. 지우기는 prune으로 한 번 더 확인하고, 시크릿은 암호문이나 참조만 Git에 두고, 롤백은 되돌리기 커밋으로 해요. 깃옵스에서 배포의 진실은 파이프라인 로그가 아니라 Git 이력에 남습니다.
