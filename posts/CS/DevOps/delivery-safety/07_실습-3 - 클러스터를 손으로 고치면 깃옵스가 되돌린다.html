2편. 한 번에 하나만 살아남는 배포
3편. 카나리는 누구와 비교하느냐가 전부다
4편. 깃옵스는 배포를 밀지 않고 당긴다

4편에서 깃옵스 에이전트는 클러스터를 계속 지켜보다가 Git과 달라지면 되돌린다고 했어요. 문서에는 Git 폴링이 "최대 3분", selfHeal 재시도는 "기본 5초"라고 적혀 있고, 소스는 조금 다른 말을 했습니다. 그래서 직접 재 봤어요. 손으로 kubectl scale을 치면 몇 초 만에 돌아오는지, 같은 짓을 여러 번 하면 어떻게 되는지, Git에 푸시한 변경은 정말 3분 안에 오는지요.

결론부터 말하면 둘 다 문서의 숫자와 달랐습니다. 손으로 바꾼 replicas는 0.3초 만에 돌아왔지만 같은 커밋에서 여섯 번째로 바꿨을 때는 299초가 걸렸고, 웹훅 없이 푸시한 변경은 네 번 중 세 번이 3분을 넘겼어요. 숫자와 화면은 전부 이번에 돌린 결과입니다.

🧭 이 글에서 확인할 것
• 손으로 바꾼 값은 몇 초 만에 돌아오고, 반복하면 왜 느려지나?
• 손으로 한 일 중 Argo CD가 드리프트로 보지 않는 것은 무엇인가?
• 웹훅 없이 푸시한 커밋은 언제 반영되나? 웹훅을 걸면?
• Git에서 지운 리소스, sync wave의 순서는 실제로 어떻게 움직이나?
• 잘못된 커밋은 어떻게 보이고, 어떻게 되돌리나?

1. 실습 환경: kind, Gitea, Argo CD

kind 클러스터 하나 안에 Git 서버와 Argo CD를 같이 띄웠어요. 외부 Git 호스팅을 쓰지 않으니 웹훅까지 노트북 안에서 끝납니다. Argo CD는 Gitea의 lab/demo 저장소에서 apps/web 디렉터리(Deployment, Service, ConfigMap)를 읽어 demo 네임스페이스에 맞춰요.

📖 용어: kind (Kubernetes IN Docker)
도커 컨테이너 하나를 쿠버네티스 노드로 써서 노트북에 클러스터를 띄우는 도구입니다. 노드 이미지의 태그가 곧 쿠버네티스 버전이고, kind delete cluster 한 줄로 흔적 없이 지울 수 있어요.
그림 1. Git도, Argo CD도, 앱도 한 클러스터 안에 있다
📖 용어: Application (Argo CD)
Argo CD가 "어느 저장소의 어느 경로를 어느 클러스터의 어느 네임스페이스에 맞출지"를 적어 두는 쿠버네티스 리소스입니다. 동기화 정책(자동 동기화, selfHeal, prune)도 여기에 적어요.
kind 0.33.0 노드 이미지 kindest/node:v1.36.4 (Argo CD 3.5 검증 대상이 k8s 1.33~1.36) Argo CD v3.5.4 (install.yaml, server-side apply) Gitea 28.1.0-rootless 앱 traefik/whoami:v1.12.0 실행 환경 Docker Desktop(메모리 8GB), Apple M5 Pro, kind 클러스터 3~4개가 동시에 떠 있었다

kind 0.33의 기본 노드 이미지는 1.37인데, Argo CD 3.5 문서의 검증 대상 표가 1.36까지라 1.36으로 내렸어요. Application의 동기화 정책은 automated에 selfHeal: true, prune: false로 시작합니다. 실습 코드는 GitHub 저장소의 labs/devops/ds-03-gitops에 있어요.

필요한 도구는 Docker, kind, kubectl, python3, git, argocd CLI예요. 결과는 out/에 실험 이름으로 저장됩니다. 글의 2절 표는 out/drift-scale-clean.txt인데, 같은 실험의 다른 실행과 구분하려고 손으로 이름을 바꾼 파일이에요. 직접 돌리면 out/drift-scale-gap1.txt에 저장돼요.

측정은 scripts/lab.py가 합니다. 클러스터 상태와 Application 상태를 0.2초 간격으로 읽어서 "바꾼 순간부터 몇 초 뒤에 돌아왔나"를 기록해요. 이 간격 때문에 0.3초는 사실상 "다음에 읽었을 때 이미 돌아와 있었다"는 뜻입니다.

2. 손으로 바꾼 replicas는 0.3초 만에 돌아온다

먼저 selfHeal이 꺼져 있으면 어떻게 되는지 봤어요. kubectl scale deploy web --replicas=5(Git에는 3)을 치자 Application은 0.3초 만에 OutOfSync가 됐고, 60초 뒤에도 replicas는 5 그대로였습니다. Argo CD는 차이를 보고만 있었어요.

그림 2. selfHeal을 끄면 Argo CD는 이 한 줄의 차이를 보여 주기만 한다

selfHeal을 다시 켜자 0.3초 만에 3으로 돌아왔습니다. 이때는 Deployment에 새 변화가 없었어요. kubectl scale은 60초 전에 끝났으니까요. 곧바로 돌아온 건 selfHeal을 켜는 Application 스펙 변경이 그 자리에서 Git 비교를 요청하기 때문입니다(소스의 automatedSyncEnabled, 5절에서 prune과 비교해요). 워치가 일하는 모습은 아래 반복 실험에서 보여요.

그다음은 같은 짓을 반복하기예요. replicas를 5로 바꾸고, Git 값(이번 실행에서는 2)으로 돌아오면 1초 쉬고 다시 바꾸기를 여섯 번 했습니다. 새 커밋으로 동기화가 한 번 일어난 직후에 시작했어요. 1회차의 0.3초는 selfHeal이 켜진 채 replicas만 바뀐 경우라, Deployment가 바뀐 이벤트를 워치로 받아 바로 다시 비교한 결과예요. 폴링 주기(120초)를 기다리지 않았습니다.

2회차부터 기다리는 시간이 4.8초, 16.8초, 52.8초, 160.6초, 298.9초로 늘었어요. 4편에서 소스로 본 지수 백오프(시작 2초, 배수 3, 상한 300초)에서 직전 동기화 뒤 흐른 1~2초를 뺀 값과 맞습니다. 부하가 높던 다른 실행의 컨트롤러 로그에도 Skipping auto-sync: already attempted sync to [...] (retrying in 2m39.66s) 같은 줄이 남았어요(out/controller-log-notes.txt). 자동 동기화 문서에 적힌 "기본 5초"는 이 버전의 동작이 아니었습니다.

📖 용어: autoHealAttemptsCount
Application의 status.operationState.operation.sync 안에 있는 값으로, 같은 Git 리비전에서 selfHeal을 몇 번 했는지 셉니다. 백오프 대기 시간은 이 횟수로 정해져요.

예상하지 못한 건 이 횟수가 시간이 지나도 줄어들지 않는다는 점이었어요. 1회차 시작 때 이미 1이었는데, 컨트롤러 로그를 보면 새 커밋의 동기화가 끝난 같은 초에 같은 리비전으로 동기화가 한 번 더 시작됐어요. 그 동기화가 selfHeal로 세어진 것으로 보입니다(out/controller-log-notes.txt). 앞선 시험으로 횟수가 4까지 쌓인 상태에서 같은 실험을 돌렸을 때는(부하가 높던 실행) 두 번째 회차의 되돌림이 181초 뒤에야 시작됐어요(out/drift-scale-accumulated.txt). 소스를 보면 횟수는 시간이 아니라 새 동기화 작업이 시작될 때 0으로 돌아가요. 새 커밋의 자동 동기화, 사람이 누른 수동 동기화, Application의 source 스펙 변경이 그런 경우입니다. 다만 이 앱의 경로를 건드리지 않은 커밋은 새 동기화를 만들지 않을 수 있어요. 장애 중에 같은 리소스를 여러 번 손보면 몇 번째부터는 Argo CD가 5분 가까이 지나서야 되돌린다는 뜻이고, 반대로 그 5분 동안은 손으로 바꾼 값이 살아 있다는 뜻이에요.

⚠️ 주의: 클러스터가 바쁘면 숫자가 크게 흔들린다
이 실습을 하는 동안 다른 kind 클러스터들이 같은 Docker Desktop VM에서 돌았고, VM의 load average가 160을 넘은 구간이 있었어요(노드 컨테이너의 /proc/loadavg, out/controller-log-notes.txt). 그때 같은 실험을 돌리자 OutOfSync를 알아채는 데 길게는 44초, 동기화 한 번이 길게는 96초 걸렸습니다(out/drift-scale-under-load.txt, out/drift-scale-accumulated.txt). 되돌림이 공식보다 일찍 시작된 적은 없었지만 늦게는 40초까지 더 걸렸어요. 횟수 7에서 공식대로라면 297초 뒤에 시작해야 할 동기화가 337초 뒤에 시작된 식입니다. 위 표는 부하가 내려간 뒤(load average 약 7~15) 다시 돌린 결과예요.

3. 드리프트로 보지 않는 손질도 있다

replicas 말고 다른 손질도 해 봤어요(lab.py drift-misc). ConfigMap 수정과 Deployment 삭제 사이에는 60초를 쉬어 백오프가 끼지 않게 했습니다.

손질 결과 Deployment 에 라벨 owner=me 추가 15초 뒤에도 Synced, 라벨 그대로 남음 ConfigMap web-config 의 값 수정 0.3초 뒤 Git 값으로 복구 Deployment web 삭제 0.3초 뒤 새 uid 로 다시 생성 같은 네임스페이스에 ConfigMap 손으로 생성 15초 뒤에도 Synced, 그대로 남음

라벨은 Git의 매니페스트에 없는 필드라서 비교 대상이 아니에요. Argo CD의 기본 비교 방식은 Git의 원하는 상태와 last-applied-configuration에 적힌 필드만 보니, 그 바깥에 붙은 라벨은 드리프트가 아닙니다. 손으로 만든 ConfigMap도 Argo CD의 추적 어노테이션이 없으니 이 Application의 것이 아니에요. 4편에서 문서로 본 내용이 그대로 나왔습니다. selfHeal은 "클러스터를 Git과 똑같이 만든다"가 아니라 "Git에 적힌 것을 Git대로 되돌린다"예요.

4. 웹훅 없이 푸시하면 3분을 넘긴다

이번엔 반대 방향입니다. Git에서 replicas를 바꿔 커밋하고 푸시한 뒤, Application이 새 리비전을 인식하고 클러스터에 반영할 때까지를 쟀어요. 한 회차가 끝나면 5초 쉬고 다음 커밋을 푸시했습니다.

웹훅 없음 (폴링만) 회차 새 리비전 인식(초) replicas 반영(초) 1 86.5 121.3 2 216.6 219.1 3 224.6 227.2 4 239.6 241.9 웹훅 켬 (1회차는 푸시 전부터 클러스터 값이 같아서 뺐다) 회차 새 리비전 인식(초) replicas 반영(초) 2 1.1 4.5 3 1.1 4.0 4 0.7 3.4

"최대 3분"이라면 넘을 수 없는 숫자가 세 번 나왔어요. 컨트롤러 로그에서 주기 새로고침(comparison expired, requesting refresh)이 찍힌 간격을 31분 동안 세어 보니 122초에서 300초까지였습니다. 원인은 4편에서 소스로 짚은 두 가지예요.

첫째, 주기 새로고침은 120초마다 돌지만 마지막 비교 시각이 120초를 넘은 앱만 Git과 다시 비교해요. 이 실험처럼 직전 회차의 동기화가 막 끝났다면 첫 차례는 건너뛰고 다음 차례에 비교합니다. 둘째, repo-server가 main을 커밋 해시로 바꾼 결과를 3분 동안 캐시해요. 웹훅을 잘못 설정한 채 돌린 회차에서 이게 그대로 보였습니다. 푸시 8초 전에 주기 새로고침이 한 번 있었고, 그때 캐시된 옛 해시가 푸시 152초 뒤의 새로고침에서도 쓰여 그냥 지나갔어요. 396초 뒤의 새로고침에서야 새 커밋을 인식했습니다(out/poll-refresh-intervals.txt, out/controller-log-notes.txt).

📖 용어: 리비전 캐시 (revision cache)
repo-server가 "브랜치 main은 지금 커밋 abc123이다" 같은 해석 결과를 잠시 저장해 두는 캐시입니다. 기본 만료가 3분이라, 그 안에 푸시된 커밋은 주기 새로고침에 보이지 않을 수 있어요. 사람이 누른 새로고침과 웹훅은 이 캐시를 건너뜁니다.

웹훅을 켜자 1초 안팎에 새 리비전을 인식하고 4초 안팎에 반영했어요. 그런데 처음 켰을 때는 웹훅이 오는데도 아무 일이 없었습니다. argocd-server 로그에 이런 줄만 남았어요.

Received push event repo: http://localhost:26030/lab/demo, revision: main, touchedHead: true

Argo CD는 웹훅에 실린 저장소 주소를 Application의 repoURL과 비교해서 새로고침할 앱을 고릅니다. Gitea는 이 주소를 자기 ROOT_URL 설정으로 만드는데, 저는 브라우저로 열 주소(localhost:26030)를 넣었고 Application은 클러스터 안 주소(gitea.gitea.svc:3000)를 쓰고 있었어요. 주소가 다르니 맞는 앱이 없었고, 오류 없이 조용히 지나갔습니다. ROOT_URL을 클러스터 안 주소로 바꾸자 바로 동작했어요. 웹훅이 깨져도 폴링이 몇 분 늦게 받쳐 주기 때문에 이런 설정 오류는 "배포가 좀 느리네"로만 보일 수 있습니다.

5. prune과 sync wave

Git에서 service.yaml을 지우고 푸시했어요(웹훅 켬, prune: false). Argo CD는 0.3초 만에 새 커밋을 인식했고 Service를 requiresPruning: true, OutOfSync로 표시했지만 지우지 않았습니다. 컨트롤러 로그에는 need to prune extra resources only but automated prune is disabled가 남았어요. 지울 것만 남은 커밋이라 동기화 자체를 시작하지 않은 거예요.

kubectl patch로 prune: true를 켜자 Service는 124.6초 뒤에 지워졌어요. 바로 지워질 줄 알았는데요. 소스를 보니 Application 스펙이 바뀔 때 컨트롤러가 곧바로 Git 비교를 요청하는 건 자동 동기화나 selfHeal이 새로 켜질 때뿐이었습니다(automatedSyncEnabled). prune만 바꾸면 다음 주기 새로고침까지 기다려요. 급하면 UI나 CLI에서 새로고침을 누르면 됩니다.

sync wave는 별도 Application(waves)으로 봤어요. 5초 걸리는 PreSync 훅 Job, wave -1 ConfigMap, wave 0 Deployment, wave 1 Service를 한 파일에 넣고, Application을 만든 순간부터 각 리소스가 처음 보인 시각을 기록했습니다.

0.3초 Job db-migrate (PreSync 훅) 생성 8.1초 Job 성공 확인, ConfigMap (wave -1) 생성 10.2초 Deployment (wave 0) 생성 10.5초 Deployment Ready 12.3초 Service (wave 1) 생성

PreSync 훅이 끝나야 본 동기화가 시작됐고, ConfigMap에서 Deployment까지 2.1초, Deployment에서 Service까지도 2.1초였어요. "Ready 뒤 1.8초"로 읽으면 기본 2초보다 짧아 보이는데, 소스를 보면 이유가 있습니다. 2초 대기(delayBetweenSyncWaves)는 Healthy가 된 뒤가 아니라 웨이브를 적용한 직후에 들어가요. 컨트롤러는 그 2초를 쉰 다음에 앞 웨이브가 Healthy인지 보고, 그렇다면 다음 웨이브를 적용합니다. 이번 Deployment는 대기 중에 Ready가 돼서 2초가 끝나자마자 Service로 넘어갔어요. 게다가 Ready 시각은 0.2초 간격으로 읽은 값이라 실제보다 늦게 찍혔을 수 있습니다. 기동이 2초보다 느린 앱이라면 Service는 Healthy 판정이 날 때까지 더 늦게 생겨요.

6. 잘못된 커밋은 Synced인 채로 Degraded가 된다

마지막으로 존재하지 않는 이미지 태그(traefik/whoami:v9.9.9)를 커밋하고 푸시했어요. 실습용으로 Deployment의 progressDeadlineSeconds를 60초로 줄여 둔 상태였습니다(기본 600초).

📖 용어: progressDeadlineSeconds
Deployment의 롤아웃이 진척 없이 이 시간을 넘기면 쿠버네티스가 Progressing 조건을 실패(ProgressDeadlineExceeded)로 바꾸는 기한입니다. Argo CD는 이 조건을 보고 Deployment의 헬스를 Degraded로 판정해요. 롤아웃을 멈추거나 되돌리지는 않습니다.
0.0s sync=Synced health=Healthy rev=b7977e9 0.6s sync=OutOfSync health=Healthy rev=8ce76ff op=Running 2.8s sync=Synced health=Progressing rev=8ce76ff op=Succeeded 62.8s sync=Synced health=Degraded rev=8ce76ff op=Succeeded 준비된 파드/전체: 3/4 web-6b6dfbf64d-xq82z traefik/whoami:v9.9.9 false ErrImagePull web-6cbcb964cc-... traefik/whoami:v1.12.0 true (3개)

매니페스트 적용은 성공했으니 동기화는 2.8초 만에 Succeeded, 상태는 Synced였어요. 헬스만 Progressing이었다가 롤아웃 기한 60초를 넘기자 Degraded가 됐습니다. 그동안 기존 파드 세 개는 Ready 상태로 남아 있었어요(이번 실습은 트래픽을 보내지 않았습니다). replicas 3에 기본 롤링 업데이트(maxUnavailable 25%를 내림하면 0, maxSurge 25%를 올림하면 1)라서 새 파드 하나만 먼저 띄우고, 그게 Ready가 되기 전에는 옛 파드를 내리지 않기 때문이에요.

그림 4. 같은 실험을 한 번 더 돌려 찍은 화면. Synced와 Sync OK 옆에 Degraded가 함께 있다

여기서 Argo CD의 롤백 명령을 써 봤어요.

$ argocd app rollback web --core # kubeconfig 의 현재 네임스페이스를 argocd 로 둔 상태 rpc error: code = FailedPrecondition desc = rollback cannot be initiated when auto-sync is enabled

자동 동기화가 켜진 앱은 롤백할 수 없다는 문서 그대로예요. 대신 git revert HEAD로 되돌리기 커밋을 만들어 푸시하자 2.7초 만에 Synced, Healthy로 돌아왔습니다. 클러스터를 새로 띄워 다시 해 봤을 때도 Degraded까지 63.2초, 되돌리기 2.8초로 거의 같았어요(out/validate-fresh-cluster.txt). Git 이력에는 잘못된 커밋과 그걸 되돌린 커밋이 둘 다 남아요.

💡 실무에서는
• 장애 중 손으로 고칠 리소스가 있다면 그 Application의 selfHeal을 잠시 끄거나 같은 변경을 바로 Git에 커밋해요. 둘 다 아니면 첫 번째 손질은 0.3초 만에 사라집니다
• 반대로 같은 리소스를 여러 번 고치면 되돌림이 최대 300초까지 늦어져요. "selfHeal이 있으니 금방 원래대로 돌아오겠지"를 기대하지 않는 게 좋아요
• 웹훅을 건 뒤에는 argocd-server 로그의 Received push event repo: 주소가 Application의 repoURL과 같은지 한 번 확인해요
• 배포 알림은 Synced가 아니라 헬스로 겁니다. 이번 잘못된 커밋은 2.8초 만에 Synced였어요
✍️ 오늘의 요약
Argo CD는 손으로 바꾼 replicas를 0.3초 만에 되돌렸지만, 같은 커밋에서 반복해 바꾸면 되돌리는 간격이 4.8초, 16.8초, 52.8초를 거쳐 299초까지 늘었어요. 소스의 지수 백오프(2초, 배수 3, 상한 300초) 그대로였고, 횟수는 시간이 아니라 새 동기화 작업(새 커밋, 수동 동기화, source 변경)이 시작될 때만 0으로 돌아갑니다. Git에 없는 라벨과 손으로 만든 리소스는 드리프트로 보지 않았어요.

웹훅 없이 푸시한 커밋은 네 번 중 세 번이 216~240초 뒤에야 새 리비전으로 인식돼 "최대 3분"을 넘겼고, 웹훅을 켜자 4초 안팎이었어요. 잘못된 이미지 태그는 Synced인 채로 Degraded가 됐고, 롤백은 git revert 한 번으로 2.7초 만에 끝났습니다. 깃옵스가 되돌리는 속도는 "즉시"가 아니라 백오프와 캐시와 주기가 정해요.
