3편에서 카나리를 운영 중인 인스턴스 전체와 비교하면 막 뜬 프로세스라는 이유만으로 떨어질 수 있다고 했어요. 같은 시각에 같은 수로 띄운 베이스라인과 비교해야 버전 차이만 남는다고도 했고요. 이번에는 그 말을 직접 돌려서 확인합니다.

kind 클러스터에 Argo Rollouts와 Prometheus를 올리고, 나쁜 버전을 카나리로 내보내 자동으로 멈추는 것부터 봅니다. 그다음 Kayenta의 판정기를 파이썬으로 옮겨 붙이고, 같은 카나리를 두 비교 대상에 동시에 판정시켜요. 숫자와 화면은 전부 이번에 돌린 결과입니다.

🧭 이 글에서 확인할 것
• 에러율 임계값 분석은 나쁜 버전을 얼마 만에 멈추고, 그동안 사용자는 에러를 몇 건 받나?
• 아무것도 바꾸지 않은 버전을 운영본과 비교하면 어떻게 판정되고, 베이스라인과 비교하면 어떻게 되나?
• 23% 느려진 버전은 언제 걸리나?
• 트래픽을 줄이면 같은 판정이 어떻게 달라지나? 1% 에러율은 잡히나?

1. 실습 환경

앱은 표준 라이브러리만 쓴 작은 파이썬 HTTP 서버입니다. /work를 받으면 평균 20ms 남짓 잠들었다 응답하고, 환경변수로 버전 이름, 추가 지연(EXTRA_MS), 에러 비율(ERROR_RATE)을 바꿔요. 버전을 바꾸는 것은 Rollout의 파드 템플릿 환경변수를 바꾸는 일이라, 같은 이미지로 좋은 버전과 나쁜 버전을 만듭니다.

예열 효과도 일부러 넣었어요. 막 뜬 프로세스는 30ms × exp(-가동 시간/120초)만큼 더 느립니다. JIT 컴파일, 캐시, 커넥션 풀이 데워지는 효과를 흉내 낸 것이고, 모든 버전에 똑같이 들어 있어요. 실제 서비스의 예열은 이렇게 깔끔한 곡선이 아니지만, 비교 대상에 따라 판정이 갈리는지 보려면 이 정도면 충분합니다.

그림 1. 세 무리의 파드가 Service 하나로 트래픽을 나눠 받고, 판정 서버는 해시로 둘을 골라 비교한다
📖 용어: Rollout (Argo Rollouts)
Deployment 자리에 쓰는 Argo Rollouts의 리소스입니다. 파드 템플릿은 Deployment와 같고, 여기에 카나리나 블루/그린 단계와 분석을 적어요. 템플릿이 바뀌면 컨트롤러가 그 단계대로 새 ReplicaSet을 키웁니다.

파드를 가르는 열쇠는 rollouts-pod-template-hash 레이블이에요. Argo Rollouts는 ReplicaSet마다 다른 해시를 붙이고, Experiment로 띄운 베이스라인과 카나리도 파드 스펙이 각각 운영본과 새 버전과 같은데 해시는 따로 받습니다. Prometheus 스크레이프 설정에서 이 레이블을 hash 라벨로 옮겨 두면 "이 해시의 파드들"을 쿼리로 고를 수 있어요.

kind 0.33.0 (노드 이미지 kindest/node v1.37.0) Argo Rollouts 1.10.0 (2026년 8월 릴리스, 컨트롤러와 kubectl 플러그인) Prometheus 3.15.0 k6 2.3.0 앱, 판정 서버 Python 3.13 (alpine), 표준 라이브러리만 실행 환경 Docker Desktop 29.5 (메모리 8GB), Apple M5 Pro

실습 코드는 GitHub 저장소의 labs/devops/ds-02-canary에 있습니다. 클러스터 만들기부터 이미지 넣기, Argo Rollouts 설치까지 스크립트 하나로 합니다.

git clone https://github.com/DDINGJOO/Platform-study.git cd Platform-study/labs/devops/ds-02-canary ./scripts/up.sh # kind 클러스터 ds-02, Rollouts, Prometheus, judge kubectl --context kind-ds-02 apply -f k8s/rollout-threshold.yaml # 첫 버전 v1, 파드 5개 kubectl --context kind-ds-02 apply -f k8s/load.yaml # 초당 50건

부하는 클러스터 안의 k6가 constant-arrival-rate로 초당 50건씩 보냅니다. noConnectionReuse를 켜서 요청마다 새 연결을 맺게 했어요. 연결을 재사용하면 이미 맺은 연결이 기존 파드에 붙어 있어서, 나중에 뜬 카나리가 트래픽을 거의 못 받습니다.

⚠️ 주의: 이 실습을 돌리다 걸린 것들
• Argo Rollouts의 install.yaml을 그냥 kubectl apply하면 CRD 두 개가 metadata.annotations: Too long: may not be more than 262144 bytes로 거절돼요. 클라이언트 쪽 apply가 객체 전체를 주석에 저장하기 때문이라 --server-side로 넣어야 합니다
• 여러 플랫폼이 든 이미지를 kind load docker-image로 넣으면 content digest ... not found로 실패했어요. 노드 플랫폼 하나만 docker save --platform으로 저장해 kind load image-archive로 넣었습니다
• 같은 Docker 위에 다른 클러스터들이 함께 돌던 첫 시도에서는 controller-manager가 리더 리스를 못 갱신해 계속 재시작했고, 노드가 NotReady로 찍혀 판정 서버 엔드포인트가 빠졌어요. 리더 선출을 끄고 노드 판정 유예를 5분으로 늘린 클러스터에서 아래 결과를 얻었습니다

2. 에러율 임계값으로 나쁜 버전을 멈춘다

먼저 3편 2장의 첫 번째 방식, 고정 임계값부터 봅니다. Rollout은 새 버전 비율을 20%(파드 5개 중 1개)로 올리고 5분을 기다리게 했고, 그 단계부터 background 분석이 카나리 파드의 에러율을 30초마다 재요.

strategy: canary: analysis: templates: [{templateName: error-threshold}] startingStep: 1 args: - name: hash valueFrom: {podTemplateHashValue: Latest} # 새 버전 ReplicaSet 의 해시 steps: - setWeight: 20 - pause: {duration: 5m} --- metrics: - name: canary-error-ratio interval: 30s failureLimit: 1 # 두 번째 실패에서 분석 실패 successCondition: result[0] < 0.02 provider: prometheus: query: | (sum(rate(demo_requests_total{hash="{{args.hash}}",code="500"}[1m])) or vector(0)) / sum(rate(demo_requests_total{hash="{{args.hash}}"}[1m]))

요청의 10%를 500으로 실패시키는 버전을 내보냈습니다.

./scripts/deploy.sh v2-bad 0 0.10 # VERSION, EXTRA_MS, ERROR_RATE

2초마다 상태를 찍은 기록과 이벤트를 맞춰 보면 이렇게 흘러갔어요. 시각은 배포 명령부터 잰 경과 시간입니다.

+0초 새 ReplicaSet 0→1, 운영본 5→4 +7초 카나리 준비 완료, setWeight 20 단계 완료, 분석 시작 +7초 1차 측정 Error "metric result is nil or empty: no data returned" +17초 2차 측정 Failed 0.076 +47초 3차 측정 Failed 0.089 → failed (2) > failureLimit (1) +47초 롤아웃 중단(Degraded), 카나리 1→0, 운영본 4→5 카나리가 받은 요청 411건 중 500 응답 36건

배포에서 중단까지 47초였고, 그동안 사용자가 받은 500은 36건이었어요(카나리 파드의 마지막 스크레이프 기준). 같은 버전을 파드 5개 전부에 한 번에 내보냈다면 같은 47초 동안 그 다섯 배쯤을 받았을 겁니다.

예상하지 못한 것은 첫 측정이었습니다. 카나리가 막 떠서 Prometheus에 그 해시의 시계열이 아직 없었고, 쿼리 결과가 비어서 successCondition을 평가하지 못했어요. 이 측정은 실패가 아니라 Error로 기록되고, 컨트롤러는 30초가 아니라 10초 뒤에 다시 쟀습니다. Argo Rollouts 소스의 기본값을 보면 Error가 난 측정은 DefaultErrorRetryInterval 10초 뒤에 다시 하고, 연속 Error는 DefaultConsecutiveErrorLimit 4번까지 봐주고 다섯 번째에 분석이 Error로 끝나요. 지표 저장소가 잠깐 비거나 닿지 않는 것을 실패와 구분해 주는 장치입니다.

📖 용어: background 분석
Rollout의 strategy.canary.analysis에 적는 분석입니다. 지정한 단계부터 롤아웃이 끝날 때까지 뒤에서 계속 측정하고, 실패하면 그 시점에 롤아웃을 중단해요. 특정 단계에서 결과를 기다렸다 넘어가는 분석 단계와 구분됩니다.

이 분석은 에러율에는 잘 맞았지만, 지연은 보지 않았습니다. 지연을 같은 방식으로 "p99가 몇 ms 미만"으로 걸면 어떻게 될지는 4절의 그림 2가 보여 줘요.

3. Kayenta의 판정기를 옮겨 붙인다

비교 판정에는 Kayenta의 NetflixACAJudge를 파이썬으로 옮긴 판정 서버(judge/)를 씁니다. 맨-휘트니 검정과 신뢰구간 계산(MannWhitney.scala), 근 찾기(BrentSolver.java), Pass/High/Low 분류(MannWhitneyClassifier.scala. 신뢰수준 0.98과 tolerance 0.25는 NetflixACAJudge.scala가 고정), 그룹 가중 점수(WeightedSumScorer.scala)를 그대로 옮겼어요. 제대로 옮겼는지는 Kayenta 저장소의 테스트 스위트로 확인했습니다. 신뢰구간과 추정치 4건, 분류 18건, 22건이 모두 기대값과 같았어요(CLES 효과 크기와 critical 문턱 테스트는 옮기지 않아 뺐습니다).

git clone https://github.com/spinnaker/kayenta.git /tmp/kayenta # 대조한 커밋은 5310ab7 python3 judge/test_port.py /tmp/kayenta OK Mann-Whitney Confidence Interval & Estimate: Tie out with R Version -0.500003 -3.5e-05 -0.499997 ... ok 22 fail 0

처음에는 근 찾기를 이분법으로 짰다가 신뢰구간 테스트 세 건과 분류 테스트 한 건이 어긋났어요(results/counts.txt). 순위합 함수가 계단 모양이라 근이 계단의 경계에 걸리는데, Kayenta의 BrentSolver(R의 uniroot가 쓰는 zeroin 알고리즘, 허용 오차 1e-4)가 멈추는 자리를 그대로 따라가야 소수점 아래까지 같아졌습니다.

Argo Rollouts에서는 web 공급자로 이 서버를 부릅니다. 판정 서버는 두 해시의 시계열을 query_range로 10초 간격으로 가져와 지표 세 개(에러율, 성공 요청의 평균 지연, 성공 요청의 p99)를 판정하고 점수를 JSON으로 돌려줘요. 에러율은 critical, 세 지표 모두 늘어나는 쪽만 실패로 봅니다.

- name: mann-whitney initialDelay: 2m interval: 2m count: 5 consecutiveErrorLimit: 30 # 판정 서버에 잠깐 못 닿는 것은 실패로 보지 않는다 successCondition: result.score >= 95 failureCondition: result.score < 95 provider: web: url: "http://judge.ds02/judge?control={{args.control}}&experiment={{args.experiment}}&window=600&step=10"
📖 용어: web 공급자 (web metric provider)
AnalysisTemplate이 지표 저장소 대신 임의의 HTTP 주소를 부르게 하는 설정입니다. 응답 JSON이 result에 담기고, successCondition이 그 값을 보고 성공과 실패를 정해요.

Rollout의 첫 단계는 Experiment입니다. 베이스라인(specRef: stable)과 카나리(specRef: canary)를 하나씩 10분 동안 띄우고, 같은 판정을 두 번 걸었어요. vs-baseline은 카나리를 베이스라인과 비교하고, 실패하면 롤아웃을 멈춥니다. vs-production은 같은 카나리를 운영본 전체(podTemplateHashValue: Stable)와 비교하되 기록만 하는 템플릿(mw-observe, 항상 성공)이에요. 같은 시각, 같은 카나리 데이터에서 비교 대상만 다릅니다.

📖 용어: Experiment (Argo Rollouts)
정해진 시간 동안 ReplicaSet 몇 개를 따로 띄우고 분석을 붙이는 리소스입니다. 카나리 단계 안에 두면 specRef: stable로 운영본과 같은 파드를, specRef: canary로 새 버전 파드를 띄워요. 분석이 실패하면 Experiment가 실패하고 롤아웃이 중단됩니다.
kubectl --context kind-ds-02 apply -f k8s/rollout-experiment.yaml # 운영본 파드가 모두 10분 넘게 떠 있을 때까지 기다린 뒤 ./scripts/deploy.sh v2 0 0 # 이름만 바뀐 버전. 코드 동작은 v1과 같다

4. 아무것도 안 바꾼 버전이 운영본 비교에서는 떨어진다

v2는 버전 이름만 다르고 동작은 v1과 똑같아요. 판정 서버가 2분마다 낸 결과를 그대로 옮겼습니다. 점의 개수는 카나리 쪽이고, 운영본은 10분 구간 전체인 61개였어요. 지연은 그 구간의 평균입니다.

경과 점 vs-baseline (대조군 vs 카나리) vs-production (운영본 vs 카나리) 평균 지연(ms) 판정 점수 평균 지연(ms) 판정 점수 2분 12 40.5 / 40.5 Pass 100 23.6 / 40.5 High 50 Fail 4분 24 34.6 / 34.6 Pass 100 22.3 / 34.6 High 50 Fail 6분 36 31.1 / 31.1 Pass 100 21.8 / 31.1 High 50 Fail 8분 48 29.0 / 28.9 Pass 100 21.7 / 28.9 High 50 Fail 10분 60 27.5 / 27.5 Pass 100 21.6 / 27.5 High 50 Fail p99도 vs-production 은 다섯 번 모두 High (예: 10분 37.0ms / 43.1ms), vs-baseline 은 모두 Pass

같은 카나리가 대조군과 비교하면 다섯 번 모두 100점, 운영본과 비교하면 다섯 번 모두 50점이었어요. vs-production이 기록 전용이 아니었다면 이 무해한 배포는 2분 만에 중단됐을 겁니다. 점수 50은 지연 그룹의 두 지표가 모두 High라 지연 그룹이 0점, 에러 그룹이 100점이라서 나온 값이에요.

그림 2. 베이스라인과 카나리는 한 줄처럼 겹치고, 운영본만 아래에 떨어져 있다

그래프는 1분 이동 구간의 평균 지연이에요. 베이스라인(초록)과 카나리(청록)는 51ms 근처에서 같이 시작해 같은 곡선으로 내려오고, 10분쯤에야 운영본(빨강)과 만납니다. 3편 그림 1에서 손으로 그렸던 모양이 그대로 나왔어요. 카나리와 운영본의 차이는 버전이 아니라 가동 시간의 차이였습니다.

마지막 판정이 10분째인데도 High였던 이유도 여기서 보입니다. 판정 구간이 카나리가 뜬 순간부터라서, 이미 다 데워진 마지막 몇 분보다 차가웠던 처음 몇 분이 평균을 끌어올려요. Spinnaker 카나리 설정에 예열 시간(warm-up period)을 두는 칸이 있는 이유가 이것이고, 이 실습의 템플릿은 그 기능을 넣지 않았습니다.

2절의 질문으로 돌아가면, 지연을 "p99 50ms 미만" 같은 고정 임계값으로 걸었어도 이 정상 버전은 처음 몇 분 동안 50ms를 넘었으니 떨어졌을 거예요.

5. 23% 느린 버전은 세 번째 판정에서 걸렸다

v2가 운영본이 되고 그 파드들이 모두 10분 넘게 뜬 뒤, 요청마다 5ms를 더 쓰는 버전을 내보냈습니다. 평균 21.6ms에 5ms면 약 23% 느려진 거예요. 에러는 없습니다.

./scripts/deploy.sh v3-slow 5 0 경과 점 vs-baseline 평균 지연(ms) 판정 점수 2분 12 40.8 / 45.8 Pass (3개 지표 모두) 100 4분 24 34.6 / 40.0 Pass 100 8분16초 39 30.8 / 36.0 평균 지연 High 75 Marginal → 95 미만이라 실패 → Experiment Failed, 롤아웃 중단(Degraded). 배포부터 496초 vs-production 은 세 번 모두 50 Fail (운영본 평균 22.0~23.7ms)

두 가지가 예상과 달랐어요.

첫째, 처음 두 번은 놓쳤습니다. 2분째 평균만 보면 카나리가 5ms 느린데 Pass였어요. 예열 곡선 때문으로 봅니다. 판정 구간 안의 점들이 51ms에서 30ms대까지 넓게 퍼져 있어서, 두 집단을 순위로 섞으면 5ms 차이가 그 퍼짐에 묻히고 신뢰구간이 0을 품게 돼요. 다만 예열을 끈 조건과 나란히 돌려 보지는 않았으니, 표본 수(12개, 24개)의 몫과 구간 안의 변동의 몫을 갈라 확인한 것은 아니에요. 그림 3에 정리했습니다.

그림 3. 두 곡선의 간격은 처음부터 같지만, 구간 안의 기울기가 그 간격을 가린다

둘째, 세 번째 판정이 늦었고 점이 모자랐습니다. 예정은 6분째였는데 실제 호출은 8분 16초였어요. 그 2분 남짓 동안 호스트가 다시 몹시 바빴고, 판정 서버 로그도 그 시각에 호출을 받은 것으로 찍혀 있습니다. 컨트롤러가 왜 늦게 불렀는지까지는 확인하지 못했어요. 점도 49개쯤 있어야 할 자리에 39개였습니다. 2초 간격 스크레이프가 그 8분 동안 240번 있어야 했는데 172번만 성공했고, 판정 간격과 같은 10초짜리 rate 창에 샘플이 두 개 미만이면 그 점은 값이 없어요. 3편에서 집계 구간을 간격과 같게 맞추면 이웃한 점의 겹침이 준다고 했는데, 창이 스크레이프 간격의 다섯 배밖에 안 되면 스크레이프 누락이 그대로 점 누락이 된다는 걸 이번에 알았습니다. 3편 3장의 주의도 이 경우를 다뤄요.

vs-production은 이번에도 세 번 모두 50점이었어요. 4절의 정상 버전에도 똑같이 50점을 줬으니 아무것도 구별하지 못한 셈입니다.

6. 트래픽을 줄이면

마지막으로 트래픽만 바꿔 봤어요. 롤아웃과 상관없이 Experiment 하나로 대조군(v2)과 나쁜 카나리를 하나씩 띄워 두었습니다. 이번 카나리는 요청마다 10ms를 더 쓰고 1%를 500으로 실패해요. 10분 예열한 뒤 전체 부하를 초당 50건, 10건, 2건으로 10분씩 바꾸고, 각 구간 끝에서 같은 10분을 step 10초, 30초, 60초로 판정했습니다.

kubectl --context kind-ds-02 apply -f k8s/experiment-lowtraffic.yaml kubectl --context kind-ds-02 -n ds02 port-forward svc/judge 25080:80 & ./scripts/lowtraffic.sh # 예열 10분, 이후 50 → 10 → 2건/초 각 10분 python3 scripts/summarize.py # results/raw 의 판정을 표로

10ms 늘어난 평균 지연은 아홉 번 모두 잡혔어요. 대조군 평균이 25~30ms였으니 30% 넘게 느려진 셈이라, 점 11개로도 충분히 컸습니다. 갈린 것은 1%짜리 에러율이에요.

초당 50건에서 step 10초면 카나리 점 하나에 요청이 70건쯤 들어갑니다. Experiment 파드도 app=demo 레이블이라 Service가 운영본 5개와 함께 파드 7개로 나눠 보내니, 카나리는 전체의 7분의 1인 초당 7건쯤을 받아요. 진짜 에러율이 1%여도 70건 중 에러가 0건일 확률이 절반쯤이고, 실제로 카나리 점 61개 중 39개(64%)가 0이었어요. 대조군은 전부 0이고요.

순위 검정 자체는 이 차이를 잡습니다. 점별 값은 남겨 두지 못해서 0 39개와 양수 22개로 다시 계산해 보니 순위합 통계량이 z ≈ 5.1이었어요. 문제는 판정이 검정의 p값이 아니라 위치 이동량의 신뢰구간으로 이뤄진다는 데 있습니다. 짝 차이 3,721개 중 2,379개(64%)가 0이라 이동량 추정치가 0.000067로 0에 붙었어요. 그리고 카나리를 0보다 조금만 아래로 옮겨도 카나리의 0들이 대조군의 0들 밑으로 내려가 순위가 확 바뀌니, 신뢰구간 하한도 0에 막혔습니다. 3편 3장의 규칙은 하한이 0.25 × 추정치(0.000017)보다 커야 High인데, 하한이 0이라 Pass였어요. critical로 걸어 둔 에러율이 실제로 0.86% 실패하는 카나리를 통과시킨 것입니다. step을 60초로 늘리자 카나리 점 11개 중 0인 점이 하나도 없었고, step 30초와 60초 모두 High가 나와 점수가 0이 됐어요.

초당 10건에서는 어떤 step으로도 에러율을 잡지 못했습니다. 이 10분은 우연히 1.8%로 실패했는데도요. step 60초에서는 하한이 0.000068로 0을 넘었지만, 허용 폭 0.0057(추정치 0.023의 4분의 1)보다 작아 역시 Pass였어요. 초당 2건에서는 10분 동안 카나리가 166건을 받았고 500이 한 번도 없었어요. 1% 결함이 166건에서 한 번도 안 나올 확률은 0.99166 ≈ 19%라 드문 일도 아닙니다. 데이터에 없는 결함은 어떤 통계로도 찾을 수 없어요. 초당 2건의 step 10초 판정에서 점이 61개가 아니라 56개인 것도 요청이 한 건도 없던 10초가 있었기 때문입니다.

⚠️ 주의: 내가 판정 서버에서 틀렸던 것
처음 돌렸을 때 판정 서버는 step과 상관없이 rate 창을 10초로 고정해 두었어요. 그래서 step 60초 판정은 1분마다 마지막 10초의 요청만 보고 나머지 50초를 버렸습니다. 초당 50건 구간의 step 30초, 60초 에러율이 그때는 둘 다 Pass였어요. 창을 step과 같게 고친 뒤(judge.py) Prometheus에 남아 있는 같은 구간을 같은 끝 시각으로 다시 판정했고(scripts/rejudge-s3.sh), 위 표가 그 결과입니다. step을 바꿀 때는 집계 창도 같이 바꿔야 해요.

p99는 반대로 step을 늘리자 Pass로 바뀌었어요. 점이 21개, 11개로 줄어서라고 생각하기 쉽지만, 고치기 전(창 10초) 판정과 맞춰 보면 아닙니다. 같은 21개 점이라도 창이 10초일 때는 세 부하 모두 High였고, 11개 점에서도 초당 10건은 High였어요. 바뀐 것은 집계 창입니다. 창을 30초, 60초로 넓히자 점 하나의 p99가 대조군부터 커졌고(초당 10건에서 49.5 → 62.3 → 69.0ms), 두 집단의 평균 차이는 13.6ms에서 9~10ms로 줄었어요. 신뢰구간 하한은 0 아래로 내려갔습니다(초당 10건 step 60초에서 -6.0ms). 창이 넓을수록 왜 이렇게 되는지는 따로 실험하지 않았어요.

그러니 step과 집계 창은 지표마다 따로 정하는 게 맞습니다. 드문 사건의 비율(에러율)은 점 하나에 요청을 많이 담도록 길게 잡고, p99처럼 창 크기에 따라 값 자체가 달라지는 지표는 창을 정해 두고 판정마다 바꾸지 않는 편이 안전해요. 둘 다 부족하면 남는 방법은 구간을 늘리는 것, 곧 시간입니다.

💡 실무에서는
• 지연 같은 상대 지표는 Experiment로 베이스라인을 같이 띄워 비교해요. 운영본 전체와 비교하면 정상 버전도 떨어집니다
• 판정 구간에서 예열 시간을 빼요. 이 실습처럼 처음부터 재면 정상 버전은 운영본 비교에서 떨어지고, 나쁜 버전은 베이스라인 비교에서 늦게 걸려요
• 에러율처럼 기준이 분명한 지표는 고정 임계값 분석을 함께 걸어 두면 빨리 멈출 수 있어요. 이번에는 47초였습니다
• web 공급자로 판정 서버를 부르면 consecutiveErrorLimit을 넉넉히 둬요. 기본값이면 연속 Error 4번까지 봐주고 다섯 번째에 분석이 Error로 끝나요
• rate 창을 판정 간격과 같게 두면 스크레이프 누락이 점 누락이 돼요. 스크레이프 간격의 몇 배는 되게 잡아요
• 에러율처럼 드문 사건의 비율은 점 하나에 요청이 충분히 담기도록 step을 길게 잡아요. 대조군이 전부 0이고 카나리 점의 절반 이상이 0이면, 순위 검정이 차이를 잡아도 위치 이동량의 신뢰구간 하한이 0에 막혀 Pass가 나와요
✍️ 오늘의 요약
같은 카나리를 같은 시각에 두 번 판정했더니, 같이 띄운 대조군과 비교하면 다섯 번 모두 100점, 운영본과 비교하면 다섯 번 모두 50점이었어요. 차이는 버전이 아니라 프로세스의 가동 시간에서 나왔고, 대조군과 카나리는 10분 내내 한 곡선을 그렸습니다.

에러율 임계값은 10% 실패하는 버전을 47초 만에 멈췄고, 통계 판정은 23% 느린 버전을 세 번째 판정에서 잡았어요. 처음 두 번을 놓친 이유는 예열 구간의 변동이었습니다. 1% 에러율은 점의 대부분이 0이면 위치 이동량의 신뢰구간이 0에 막혀 통과했어요. 카나리 판정은 비교 대상, 판정 구간, 점 하나에 담기는 요청 수가 함께 맞아야 믿을 수 있습니다.
