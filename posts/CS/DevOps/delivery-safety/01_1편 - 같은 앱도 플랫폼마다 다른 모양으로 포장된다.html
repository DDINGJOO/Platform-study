🚀 배포 안전성, 1편
1편. 같은 앱도 플랫폼마다 다른 모양으로 포장된다 ← 지금 이 글
2편. 한 번에 하나만 살아남는 배포
3편. 카나리는 누구와 비교하느냐가 전부다
4편. 깃옵스는 배포를 밀지 않고 당긴다
실습-1. 하이랜더와 블루그린을 Argo Rollouts로 돌려 본다
실습-2. 카나리를 통계로 판정해 자동으로 되돌린다
실습-3. 클러스터를 손으로 고치면 깃옵스가 되돌린다

월요일 아침, 보안팀에서 메시지가 옵니다. 회사가 쓰는 자바 기본 이미지의 TLS 라이브러리에 취약점이 나왔으니 이번 주 안에 전 서비스에 패치를 반영해 달라는 내용이에요. 코드는 한 줄도 바뀌지 않았습니다. 바뀌어야 하는 건 앱 아래에 깔린 운영체제 패키지 하나예요.

그런데 서비스마다 일이 다르게 흘러갑니다. 아직 VM에서 도는 서비스는 새 머신 이미지를 굽고 오토스케일링 그룹을 갈아 끼워야 해요. 쿠버네티스로 옮긴 서비스는 컨테이너 이미지를 다시 빌드해야 하는데, 마지막 배포 이후 main 브랜치에 다른 변경이 쌓여 있어서 "운영에 나가 있는 그 커밋"을 먼저 찾아야 합니다. PaaS에 올린 서비스는 운영체제 패치라면 플랫폼이 인스턴스를 다시 띄우며 반영해 줍니다. 그런데 같은 공지에 자바 런타임 패치까지 걸려 있으면 빌드팩을 올리고 앱을 재배포해야 들어간다는 걸 그제야 알게 돼요.

같은 스프링 부트 jar인데 왜 플랫폼마다 포장 모양이 이렇게 다를까요? 그리고 모양이 다른데도 안전하게 배포하는 방법은 왜 비슷할까요? 이 시리즈는 배포를 안전하게 만드는 원리를 다룹니다. 이번 편에서 배포 단위가 어떤 모양인지 보고, 2편에서 그 단위를 갈아 끼우는 전략, 3편에서 새 버전을 통계로 검증하는 카나리, 4편에서 깃 저장소를 기준으로 클러스터를 맞추는 깃옵스를 봐요. 실습 세 편은 그 주장을 kind 클러스터에서 직접 돌려 확인합니다.

🧭 이 글에서 확인할 것
• IaaS, 컨테이너 플랫폼, PaaS는 각각 무엇을 배포 단위로 받는가?
• 서버를 고치지 않고 바꾼다는 불변 인프라는 배포에 무엇을 보장해 주는가?
• 기본 이미지만 바꾸고 싶을 때 컨테이너 포장은 왜 번거로워지는가?
• 서버 그룹과 클러스터라는 말은 AWS와 쿠버네티스에서 각각 무엇을 가리키는가?
• 전달 파이프라인은 어떤 사건에서 시작해야 하는가?

1. 플랫폼이 받는 배포 단위가 다르다

앱을 돌리는 플랫폼은 크게 세 갈래로 나뉩니다. 갈래를 나누는 기준은 "플랫폼에 무엇을 넘기느냐"예요.

IaaS(서비스형 인프라)는 가상 머신을 빌려줍니다. 하드웨어와 하이퍼바이저는 클라우드가 책임지고, 그 위의 운영체제부터는 우리 몫이에요. 그래서 넘기는 단위는 VM 이미지입니다. AWS에서는 AMI(Amazon Machine Image)라고 불러요. 앱 jar만 있어서는 VM을 띄울 수 없으니, 누군가 운영체제와 자바 런타임과 앱을 한 이미지로 묶어야 합니다.

컨테이너 플랫폼은 VM 대신 컨테이너를 돌립니다. 쿠버네티스가 대표적이에요. 넘기는 단위는 컨테이너 이미지입니다. 운영체제 커널은 노드와 나눠 쓰지만, 사용자 영역의 패키지와 자바 런타임과 앱은 이미지 안에 들어가요. 그래서 파이프라인에 이미지를 빌드해 레지스트리에 올리는 단계가 하나 더 붙습니다.

PaaS(서비스형 플랫폼)는 한 단계 더 올라갑니다. jar나 소스를 넘기면 플랫폼이 이미지를 만들어 띄워 줘요. Cloud Foundry와 Heroku가 이 모양입니다. 대신 이미지 안에 무엇이 들어가는지는 플랫폼의 빌드팩이 정해요. 자바 버전을 올리려면 빌드팩을 갱신하고 앱을 다시 올려야 하고, 그 재배포는 플랫폼이 대신해 주지 않습니다.

그림 1. 포장 모양은 플랫폼이 무엇을 받느냐로 정해진다

그림 1의 세 줄을 나란히 놓으면 차이와 공통점이 함께 보여요. 차이는 누가 이미지를 굽느냐입니다. IaaS에서는 우리 파이프라인이, 컨테이너 플랫폼에서는 우리 빌드가, PaaS에서는 플랫폼이 구워요. 공통점은 셋 다 기본 이미지 위에 앱을 얹은 결과물을 한 번 만들고, 그 결과물을 고치지 않고 여러 벌 복제한다는 점입니다. 이 공통점이 다음 장의 주제예요.

그래서 어느 플랫폼을 고를지는 포장의 편의로 정할 일이 아닙니다. 세 갈래 모두 비슷한 수준까지 자동화할 수 있어요. 차이가 크게 나는 건 기동 시간, 특정 클라우드에 묶이는 정도, 비용, 보안 패치를 누가 책임지느냐 쪽입니다.

2. 서버를 고치지 않고 바꾼다

VM 시절에는 배포를 이렇게 하는 팀이 많았어요. 떠 있는 서버에 접속해 새 jar를 복사하고 프로세스를 재시작합니다. 운영체제 패치는 따로 패키지 관리자로 올리고요. 이 방식은 간단하지만 시간이 지날수록 서버마다 상태가 달라집니다. 어떤 서버는 패치가 실패한 채로 남고, 누군가 장애 대응 중에 설정 파일 한 줄을 손으로 고치고 기록을 남기지 않아요. 몇 달 뒤에는 같은 역할의 서버 열 대가 서로 조금씩 다른 상태가 됩니다.

📖 용어: 불변 인프라 (immutable infrastructure)
한 번 띄운 서버나 컨테이너를 고치지 않고, 바꿀 일이 생기면 새 이미지로 새 인스턴스를 띄워 갈아 끼우는 운영 방식입니다. 실행 중인 인스턴스의 상태가 이미지와 같다는 것을 보장해요.

Kief Morris는 2013년 martinfowler.com의 글에서 이것을 불변 서버(immutable server)라고 부르고, "한 번 배포하면 절대 고치지 않고 새 인스턴스로 교체만 하는 서버"로 정의했어요. 변경은 기본 이미지에 넣어 테스트한 뒤 내보내고, 변경이 없는 옛 서버는 내리고 새 이미지로 띄운 서버로 바꿉니다. 같은 글은 오래 떠 있으며 계속 고쳐 온 서버에서 설정 드리프트가 생긴다고 지적해요.

12 Factor App의 다섯 번째 원칙도 같은 생각을 배포 단계로 풀어 놓았습니다. 빌드는 코드를 실행 가능한 묶음으로 바꾸고, 릴리스는 그 빌드에 환경 설정을 합치고, 실행은 릴리스 하나를 골라 프로세스를 띄워요. 실행 중에는 코드를 바꿀 수 없고, 릴리스는 고유한 ID를 갖고 추가만 됩니다. 한 번 만든 릴리스를 고칠 수 없으니 바꾸려면 새 릴리스를 만들어야 해요. 그 대가로 롤백은 예전 릴리스 ID를 다시 고르는 일이 됩니다.

배포 안전성 쪽에서 보면 불변 인프라가 주는 보장은 하나예요. "지금 도는 인스턴스 묶음은 정확히 어떤 버전인가"에 답이 하나뿐이라는 것입니다. 서버를 제자리에서 고치면 버전이 서버마다, 시점마다 달라져서 이 질문에 답하기 어려워요. 버전이 하나로 고정된 묶음이 있어야 "새 묶음으로 트래픽을 옮긴다", "옛 묶음으로 되돌린다"는 말이 성립합니다. 2편에서 볼 배포 전략은 전부 이 전제 위에 서 있어요.

⚠️ 주의: 불변인 것은 이미지이지 데이터가 아니다
불변 인프라는 상태를 인스턴스 밖에 두는 앱에서만 성립해요. 12 Factor의 표현으로는 프로세스가 무상태여야 합니다. 로컬 디스크에 세션이나 업로드 파일을 쌓는 앱은 인스턴스를 갈아 끼우는 순간 그 데이터를 잃어요. 세션은 외부 저장소로, 파일은 오브젝트 스토리지로 먼저 옮겨야 배포 전략을 고를 수 있습니다.

3. VM은 굽는다: 베이킹

IaaS에서 배포 단위인 VM 이미지를 만드는 과정을 베이킹이라고 불러요. 기본 이미지로 임시 인스턴스를 띄우고, 앱과 앱이 필요로 하는 시스템 패키지를 설치하고, 그 상태를 스냅숏으로 떠서 새 이미지로 등록합니다. 이 이미지가 오토스케일링 그룹이 인스턴스를 띄울 때 쓰는 틀이 돼요.

📖 용어: 베이킹 (baking)
기본 VM 이미지에 앱과 의존성을 설치한 뒤 스냅숏을 떠서 새 VM 이미지를 만드는 일입니다. 인스턴스가 뜰 때 설치하지 않고 미리 구워 두기 때문에, 새 인스턴스는 이미지 그대로 뜹니다.

이 일을 하는 대표 도구가 HashiCorp의 Packer예요. 템플릿 하나로 여러 클라우드용 머신 이미지를 만들어 줍니다. Spinnaker의 이미지 베이커리(Rosco)도 내부에서 Packer 템플릿을 호출하는데, Spinnaker 문서는 그 이유를 "불변 인프라 개념이 Spinnaker의 핵심이기 때문"이라고 적어요(Spinnaker 문서, Bakery).

앱을 이미지에 넣는 방법은 운영체제 패키지가 깔끔합니다. 기본 이미지가 데비안 계열이면 .deb, 레드햇 계열이면 .rpm으로 앱을 포장하고, 베이킹 중에 apt-get install로 설치해요. 설치 경로, 실행 사용자, 서비스 등록 스크립트가 패키지 안에 정해져 있어서 서비스마다 베이킹 스크립트를 따로 짤 필요가 줄어듭니다. Netflix가 공개한 Gradle 플러그인(nebula-plugins의 gradle-ospackage-plugin)이 빌드에서 바로 .deb과 .rpm을 만들어 주는 도구예요.

빌드 ./gradlew buildDeb → app_1.4.2_all.deb 베이킹 packer build (기본 AMI + apt-get install app) → ami-새것 배포 새 시작 템플릿으로 새 오토스케일링 그룹 app-v043 생성 트래픽 전환 로드 밸런서에 app-v043 붙이고 app-v042 떼기

여기서 하나 짚어 둘 것이 있어요. AWS 오토스케일링 그룹의 시작 템플릿을 새 AMI로 바꿔도 이미 떠 있는 인스턴스는 그대로입니다. 새 템플릿은 앞으로 띄울 인스턴스에만 적용돼요. 떠 있는 인스턴스를 새 AMI로 바꾸려면 인스턴스 새로 고침(instance refresh)으로 묶음 단위 교체를 돌리거나, 새 오토스케일링 그룹을 만들고 트래픽을 옮겨야 합니다(AWS 문서, instance refresh). Spinnaker의 AWS 제공자는 뒤쪽 방식을 써요. 문서에 따르면 가장 흔한 쓰임은 AMI를 만들어 새 오토스케일링 그룹에 배포하고 이전 그룹을 지우는 것입니다.

새 그룹을 만드는 방식에는 장점이 하나 더 있어요. 옛 그룹이 지워지기 전까지는 고스란히 남아 있으니, 문제가 생기면 트래픽만 옛 그룹으로 돌리면 됩니다. 이 "옛 묶음을 얼마나 오래, 얼마나 크게 남겨 두느냐"가 2편의 핵심 질문이에요.

4. 컨테이너는 빌드에서 굽는다, 그래서 기본 이미지가 번거롭다

컨테이너 플랫폼에서는 이미지 빌드가 보통 앱 빌드와 한 파이프라인에 붙어 있어요. Dockerfile로 빌드하든, Jib이나 스프링 부트의 빌드팩 지원(bootBuildImage)으로 빌드하든 결과는 기본 이미지 레이어 위에 앱 레이어를 얹은 이미지입니다. 스프링 부트 문서는 Maven과 Gradle 플러그인에서 Cloud Native Buildpacks로 바로 이미지를 만들 수 있다고 적어요. Dockerfile이 없어도 됩니다.

📖 용어: 기본 이미지 (base image)
앱을 얹기 전의 바탕 이미지입니다. 운영체제 사용자 영역 패키지와 자바 런타임이 여기에 들어 있어요. Dockerfile의 FROM 줄이 가리키는 이미지가 기본 이미지입니다.

이 포장의 약점은 서두의 장면에서 드러나요. 기본 이미지의 운영체제 패키지가 앱 이미지 안에 함께 들어 있으니, 기본 이미지를 바꾸려면 앱 이미지를 다시 빌드해야 합니다. 그런데 다시 빌드하려면 두 가지를 감수해야 해요.

첫째, 운영에 나가 있는 코드 버전을 먼저 찾아야 합니다. main 브랜치에는 마지막 배포 이후의 변경이 쌓여 있을 수 있어요. 기본 이미지만 올리려던 배포에 아무도 검토하지 않은 기능 변경이 딸려 나갈 수 있습니다. 둘째, 같은 커밋을 다시 빌드해도 같은 결과가 나온다는 보장이 없어요. 의존성 버전 범위, 빌드 도구 버전, 빌드 시점에 받아 오는 파일이 바뀌면 바이너리가 달라집니다. 기본 이미지 하나를 바꾸려다 앱 바이너리까지 바뀌는 셈이에요.

이 문제를 푸는 방향은 앱 레이어와 기본 이미지 레이어를 따로 갈아 끼우는 것입니다. Cloud Native Buildpacks의 pack rebase가 이 일을 해요. buildpacks.io 문서는 rebase가 앱 이미지의 레이어 메타데이터를 새 기본 이미지 버전을 가리키도록 고치고, 레이어 재배치 덕분에 앱을 다시 빌드하지 않아도 된다고 설명합니다. 앱 레이어는 그대로 두고 아래쪽 레이어만 바꾸니 바이너리 재현성 문제가 생기지 않아요.

⚠️ 주의: 오래된 예제가 가리키는 이미지와 도구
• 예제 코드에 흔한 FROM openjdk:8의 openjdk 공식 이미지는 Docker Hub에서 공식적으로 폐기(deprecated)됐어요. Docker Hub는 eclipse-temurin, amazoncorretto 같은 대체 이미지를 안내합니다
• 컨테이너 이미지를 클러스터 안에서 굽는 도구로 자주 소개되던 Kaniko는 GoogleContainerTools 저장소가 2025년 6월에 보관(archived) 처리됐어요. 마지막 공식 릴리스는 2025년 5월의 v1.24.0이고, 지금은 Chainguard 등이 포크로 유지합니다
• 기본 이미지는 누가 검토하고 승인하는지가 정해져 있어야 해요. VM 이미지와 컨테이너 이미지 모두 마찬가지입니다

정리하면 VM의 베이킹과 컨테이너의 이미지 빌드는 같은 일을 다른 시점에 합니다. 베이킹은 앱 빌드가 끝난 뒤 파이프라인 단계에서 기본 이미지와 앱을 합치고, 컨테이너 빌드는 보통 앱 빌드 안에서 합쳐요. 합치는 시점이 앱 빌드에서 떨어져 있을수록 기본 이미지만 따로 교체하기 쉽습니다.

PaaS는 기본 이미지를 대신 관리해 줄까

PaaS가 운영체제 패치까지 알아서 해 준다는 설명을 자주 듣습니다. 절반만 맞아요. 플랫폼이 운영체제 계층을 갱신할 때도 결국 인스턴스를 하나씩 내리고 다시 띄웁니다. 운영체제 갱신 자체가 앱 동작을 바꿀 수 있으니, 플랫폼이 우리 대신 자동으로 적용해도 되는 변경의 범위는 따로 정해 둬야 해요. 그 범위를 벗어나는 변경, 예를 들어 자바 메이저 버전 교체는 앞에서 말한 대로 빌드팩을 바꾸고 앱을 다시 올려야 들어갑니다. 결국 기본 이미지가 바뀌면 누가 언제 재배포하는가라는 질문은 PaaS에서도 사라지지 않아요. 답하는 주체가 플랫폼과 우리로 나뉠 뿐입니다.

Cloud Foundry 문서의 롤링 배포 절도 이 점을 보여 줘요. cf push --strategy rolling은 새 인스턴스를 띄워 정상이 되면 옛 인스턴스를 내리는 방식으로 무중단 배포를 하는데, 문서는 그동안 옛 버전과 새 버전이 같은 경로에서 함께 응답하므로 API 변경이 하위 호환되지 않으면 클라이언트가 깨질 수 있고, 데이터베이스 마이그레이션은 배포가 처리해 주지 않는다고 적어요(cf CLI v7 이상). 플랫폼이 추상화를 올려도 두 버전이 동시에 산다는 사실은 그대로 남습니다. 2편에서 이 "동시에 사는 시간"을 전략별로 비교해요.

5. 포장이 기동 시간을 정하고, 기동 시간이 롤백 시간을 정한다

포장 모양이 다르면 인스턴스 하나를 새로 띄우는 데 걸리는 시간도 달라요. VM은 인스턴스를 할당받고 운영체제를 부팅한 다음 앱을 시작합니다. 컨테이너는 노드가 이미 떠 있으니 이미지를 받아 프로세스를 시작하면 되고, 이미지가 노드에 캐시돼 있으면 더 빨라요. 어느 쪽이든 마지막에는 앱 자체의 준비 시간이 붙습니다. 자바 앱은 클래스 로딩, 커넥션 풀 생성, 캐시 적재 때문에 프로세스가 뜬 뒤에도 요청을 받을 준비가 될 때까지 시간이 더 걸려요.

이 시간은 플랫폼 설정에도 드러납니다. AWS 오토스케일링에는 인스턴스가 InService가 된 뒤 초기화가 끝났다고 볼 때까지의 시간인 인스턴스 워밍업 설정이 있고, 인스턴스 새로 고침은 새 인스턴스가 이 시간을 다 채운 뒤에야 다음 교체로 넘어가요. 쿠버네티스에서는 readiness probe가 통과해야 파드가 Service의 엔드포인트에 들어가고, minReadySeconds를 주면 그만큼 더 지켜본 뒤에야 사용 가능으로 칩니다.

📖 용어: readiness probe
쿠버네티스가 파드에 "지금 요청을 받을 수 있나"를 주기적으로 묻는 검사입니다. 통과하기 전까지 그 파드는 Service로 들어오는 트래픽을 받지 않아요. 프로세스가 살아 있는지 보는 liveness probe와는 따로 둡니다.

배포 전략 이야기에서 이 시간이 중요한 이유는 롤백 때문이에요. 되돌아갈 옛 서버 그룹에 인스턴스가 살아 있으면 트래픽만 돌리면 됩니다. 인스턴스가 없으면 옛 이미지로 인스턴스를 새로 띄워야 하고, 롤백은 기동 시간만큼 걸려요. 롤백 속도는 배포 도구가 아니라 "옛 버전 인스턴스가 지금 떠 있는가"가 정합니다. 기동이 느린 앱일수록 옛 인스턴스를 남겨 두는 값이 커져요. 2편은 이 판단을 전략별로 나눠 보고, 실습-1은 기동에 10초가 걸리는 앱으로 그 차이를 잽니다.

6. 서버 그룹과 클러스터: 버전 하나에 묶음 하나

배포 전략을 플랫폼과 상관없이 이야기하려면 공통 용어가 필요해요. Spinnaker가 정한 용어가 널리 쓰입니다. Spinnaker는 Netflix가 만들어 2015년에 공개한 멀티 클라우드 배포 도구예요. 그 개념 문서의 정의를 옮기면 이렇습니다.

📖 용어: 서버 그룹 (server group)
배포할 결과물(VM 이미지, 도커 이미지)과 인스턴스 수 같은 기본 설정을 정한 자원이고, 배포되면 그 결과물을 실행하는 인스턴스의 묶음이 됩니다. 한 서버 그룹 안의 인스턴스는 모두 같은 코드와 설정이에요. 버전 하나에 서버 그룹 하나가 대응합니다.
📖 용어: 클러스터 (cluster, Spinnaker의 뜻)
같은 역할을 하는 서버 그룹들을 논리적으로 묶은 것입니다. 배포할 때마다 서버 그룹이 하나씩 늘고, 그 서버 그룹들이 한 클러스터에 모여요. Spinnaker 문서는 이 클러스터가 쿠버네티스 클러스터와 다른 것이라고 따로 적어 둡니다.

위로는 애플리케이션이 여러 클러스터를 묶고, 아래로는 인스턴스가 서버 그룹을 이룹니다. 옆에는 서버 그룹의 인스턴스들에 요청을 나눠 주는 로드 밸런서와 접근 규칙을 정하는 방화벽이 붙어요. 이 단어들이 AWS와 쿠버네티스에서 무엇에 해당하는지 Spinnaker의 제공자 문서를 기준으로 맞춰 보면 그림 2가 됩니다.

그림 2. 같은 개념, 플랫폼별 이름. 핵심은 가운데 줄이다

AWS에서는 대응이 직관적이에요. 버전마다 오토스케일링 그룹을 새로 만들고, app-v042, app-v043처럼 이름 끝의 순번으로 버전을 구분합니다. 같은 접두어를 가진 그룹들이 한 클러스터예요.

쿠버네티스는 조금 더 따져 봐야 합니다. 지금의 Spinnaker 쿠버네티스 제공자(V2) 문서는 서버 그룹을 ReplicaSet, Deployment 같은 워크로드에, 로드 밸런서를 Service와 Ingress에, 방화벽을 NetworkPolicy에 대응시키고, 클러스터는 moniker.spinnaker.io/cluster 주석으로 묶는 논리적인 무리로 둡니다. 예전 V1 제공자 문서(Legacy, 1.21에서 제거 예정으로 표시)는 더 구체적이었어요. 서버 그룹을 ReplicaSet에, 클러스터를 Deployment에 선택적으로 대응시키고, Spinnaker의 배포 전략(블루그린, 하이랜더)이 쿠버네티스 Deployment의 롤링 업데이트가 관리하는 ReplicaSet을 함께 관리하게 하지 말라고 경고했습니다. 둘은 같이 동작하도록 만들어지지 않았다는 거예요.

V1 문서는 왜 ReplicaSet을 서버 그룹으로, Deployment를 클러스터로 봤을까요? 쿠버네티스 Deployment는 파드 템플릿이 바뀔 때마다 새 ReplicaSet을 하나 만듭니다. 그리고 옛 ReplicaSet을 0개로 줄여 가며 새 ReplicaSet을 늘려요. 옛 ReplicaSet은 지우지 않고 기본 10개까지 남겨 둡니다(revisionHistoryLimit). 그러니 ReplicaSet 하나가 버전 하나이고, Deployment는 그 ReplicaSet들을 거느린 묶음이에요. 서버 그룹과 클러스터의 관계와 같은 모양입니다.

Spinnaker가 Deployment 대신 ReplicaSet을 직접 배포할 때는 이 관계를 이름으로 드러내요. 문서에 따르면 ReplicaSet과 ConfigMap 같은 자원은 "버전이 붙는 자원"으로 분류돼 배포할 때마다 vNNN 순번이 붙은 새 자원으로 만들어지고, 제자리에서 고치지 않습니다. 스스로 갱신 정책을 가진 Deployment나 StatefulSet과 달리 ReplicaSet을 제자리에서 고치면 예상하지 못한 결과가 나오고 이력이 지워질 수 있다는 이유예요. AWS의 app-v043과 같은 규칙을 쿠버네티스 자원에 적용한 셈입니다.

📖 용어: pod-template-hash 레이블
Deployment 컨트롤러가 파드 템플릿을 해시한 값을 ReplicaSet과 그 파드에 붙이는 레이블입니다. 같은 Deployment 아래의 ReplicaSet들이 서로의 파드를 차지하지 않도록 구분해요. 쿠버네티스 문서는 이 레이블을 바꾸지 말라고 적습니다.
$ kubectl -n lab set env deploy/web VERSION=v2 $ kubectl -n lab get rs -l app=web NAME DESIRED CURRENT READY AGE web-554f7755d 0 0 0 66s ← 이전 버전. 0개로 줄었지만 남아 있다 web-76b9457679 4 4 4 54s ← 현재 버전

위 출력은 실습-1의 kind 클러스터에서 파드 4개짜리 Deployment(k8s/deploy-rolling-prestop.yaml)의 환경변수 하나를 바꾸고 롤아웃이 끝난 직후에 본 모습이에요. 원본은 실습 디렉터리의 results/rs-after-set-env.txt에 있어요. 이름 뒤의 해시가 pod-template-hash입니다. kubectl rollout undo는 이 0개짜리 ReplicaSet을 다시 키우는 명령이에요. 다만 0개로 줄어든 서버 그룹은 인스턴스가 없으니 되돌릴 때 파드를 새로 띄워야 하고, 그 시간이 롤백 시간이 됩니다. 이 차이를 2편과 실습-1에서 숫자로 확인해요.

7. 전달 파이프라인은 결과물이 생길 때 시작한다

포장과 배포 단위가 정해지면 그다음은 파이프라인이에요. 흔한 모양은 빌드, 포장, 테스트 환경 배포, 검증, 승인, 운영 배포 순서입니다. 파이프라인 도구는 Spinnaker 말고도 많아요. 무엇을 고르든 세 가지는 확인해 볼 만합니다.

첫째, 자동 트리거. 파이프라인은 사람이 버튼을 눌러서가 아니라 새 결과물이 생겼다는 사건으로 시작하는 게 좋아요. 레지스트리에 새 이미지가 올라오거나, 저장소에 새 패키지가 게시되는 사건입니다. 여기서 그림 3의 요점이 나와요. 트리거는 앱 결과물과 기본 이미지, 두 군데에 걸어야 합니다. 기본 이미지에 새 패치 버전이 나오면 그것만으로 다시 굽고 배포하는 파이프라인이 돌아야 서두의 패치 반영이 다음 기능 배포를 기다리지 않아요.

그림 3. 파이프라인 입구는 두 개다

기본 이미지 트리거를 걸어도 모든 서비스가 같은 속도로 따라오지는 않아요. 운영 배포까지 전부 자동인 서비스는 몇 분 안에 패치가 나가고, 수동 승인 단계가 많은 서비스는 며칠이 걸립니다. 어느 쪽이 맞는지는 서비스마다 다르지만, 적어도 "기본 이미지가 바뀌었다"는 사건이 파이프라인을 깨우게는 해 둬야 해요. 컨테이너 쪽에서는 Dependabot 같은 도구가 Dockerfile의 기본 이미지 태그 갱신을 풀 리퀘스트로 올려 주기도 합니다.

둘째, 플랫폼 중립성. 회사가 커지면 VM, 쿠버네티스, PaaS가 섞여 돌아가는 경우가 많아요. 파이프라인 도구가 한 플랫폼에만 묶이면 플랫폼마다 배포 도구를 따로 갖춰야 합니다. 쿠버네티스 커스텀 리소스로 배포 전략을 정하는 도구(실습에서 쓸 Argo Rollouts가 여기에 해당해요)는 쿠버네티스 안에서는 편하지만 그 밖으로는 나가지 못한다는 점을 알고 고르면 됩니다.

셋째, 단계마다 드는 자원이 다르다는 점. 배포 단계는 플랫폼 API를 부르고 기다리는 일이라 자원이 거의 들지 않아요. 반면 빌드나 테스트 스크립트를 돌리는 단계는 CPU와 메모리를 많이 씁니다. 둘을 한 서버에서 돌리면 무거운 빌드가 배포 단계까지 느리게 만들어요. 무거운 작업은 컨테이너 스케줄러 같은 별도 실행기에 넘기는 편이 안전합니다.

💡 실무에서는
• 운영에 나가 있는 각 서비스가 어떤 기본 이미지의 어떤 버전 위에 있는지 조회할 수 있게 해 두세요. 이미지 레이블이나 SBOM(이미지에 든 패키지와 버전을 적은 목록, Software Bill of Materials)에 남겨 두면 취약점 공지가 왔을 때 대상 목록부터 바로 나와요
• 기본 이미지 태그는 latest 대신 고정 버전이나 다이제스트로 적고, 갱신은 자동 풀 리퀘스트로 받아요. 무엇이 언제 바뀌었는지 기록이 남아요
• 배포 결과물에는 커밋 해시를 태그로 붙여요. "운영에 나간 그 커밋"을 찾는 시간이 사라져요
• 쿠버네티스에서 롤백할 수 있는 범위는 revisionHistoryLimit가 정해요. 0으로 두면 옛 ReplicaSet이 지워져서 rollout undo를 할 수 없어요
✍️ 오늘의 요약
IaaS는 VM 이미지, 컨테이너 플랫폼은 컨테이너 이미지, PaaS는 앱 바이너리를 받아요. 누가 이미지를 굽느냐는 다르지만, 기본 이미지와 앱을 한 이미지로 묶고 그 결과물을 고치지 않고 복제한다는 원칙은 같아요. 그래서 "지금 도는 묶음은 어떤 버전인가"에 답이 하나로 정해져요.

그 묶음을 Spinnaker는 서버 그룹이라고 부르고, AWS에서는 오토스케일링 그룹, 쿠버네티스에서는 ReplicaSet이 그 자리에 와요. 컨테이너 포장은 기본 이미지와 앱이 한 빌드에 묶여 있어서 기본 이미지만 바꾸기가 번거롭고, 그래서 파이프라인 입구를 앱 결과물과 기본 이미지 두 군데에 둬야 해요. 배포는 서버를 고치는 일이 아니라, 버전 하나짜리 묶음을 새로 만들고 트래픽을 옮기는 일이에요.
