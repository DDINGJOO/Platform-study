2편. SNAPSHOT과 latest는 버전이 아니라 포인터다
3편. 빌드 파일에 적은 버전과 jar에 들어간 버전은 다르다
4편. grep은 글자를 찾고, 타입이 붙은 구문 트리는 호출을 찾는다
실습-1. 같은 좌표가 다른 바이너리를 가리키는 순간을 만든다
실습-2. 서비스 열 개에서 취약한 라이브러리를 쓰는 곳을 SBOM으로 찾는다
실습-3. Maven과 Gradle이 같은 의존성 그래프를 다르게 푼다
실습-4. grep, OpenRewrite, 커버리지가 센 호출 수가 다르다

금요일 오후에 보안 공지가 하나 올라옵니다. logback-core 1.5.x 계열의 1.5.13 이전 버전에 취약점(CVE-2024-12798)이 있으니, 해당 버전을 쓰는 운영 서비스를 오늘 안에 목록으로 달라는 내용이에요. 담당자는 사내 Git 서버의 코드 검색 창에 logback-core를 칩니다. 결과가 열댓 개 나와요. 빌드 파일에 버전을 직접 적은 저장소가 몇 개, 버전 없이 적은 저장소가 몇 개, 아예 언급이 없는 저장소가 대부분입니다.

이 결과를 그대로 보고해도 될까요? 검색이 본 것은 각 저장소 main 브랜치의 지금 모습이에요. 운영에 떠 있는 건 몇 주 전 커밋으로 만든 이미지일 수 있습니다. 빌드 파일에 적힌 버전이 jar 안에 들어간 버전과 같다는 보장도 없어요. 언급이 없는 저장소도 스프링 부트를 거쳐 logback을 끌어오고 있을 겁니다. 그리고 검색 결과 어디에도 "그 서비스가 지금 어느 클러스터에서 몇 개 떠 있는지"는 나오지 않아요.

이 시리즈는 운영에 떠 있는 것에서 출발해 그 안의 코드까지 거슬러 올라가는 법을 다룹니다. 이번 편은 "지금 무엇이 떠 있나"를 어디에 물어야 하는지, 2편은 그 답을 버전 하나로 고정하려면 버전이 어떤 성질을 가져야 하는지, 3편은 빌드 파일과 jar 사이에서 의존성 버전이 바뀌는 이유, 4편은 라이브러리 단위를 넘어 메서드 호출 단위까지 찾는 법을 봐요. 실습 네 편은 그 주장을 로컬 저장소와 빌드 도구로 직접 확인합니다.

🧭 이 글에서 확인할 것
• 운영 인벤토리에는 어떤 질문을 던지게 되는가?
• 커밋에서 실행 중인 인스턴스까지 무엇을 기록해 두어야 거꾸로 따라갈 수 있는가?
• Git에 적힌 상태와 클러스터에서 실제로 도는 상태는 어디서 갈라지는가?
• 쿠버네티스, 레지스트리, 앱 자신에게 각각 무엇을 물으면 되는가?
• 매번 실시간으로 물을 것인가, 주기적으로 찍어 둘 것인가?

1. 질문에는 늘 "지금 운영에"가 붙어 있다

운영을 하다 보면 비슷한 모양의 질문을 반복해서 받습니다. 몇 가지를 적어 보면 이래요.

• logback-core 1.5.13 미만을 쓰는 서비스 중, 외부 트래픽을 받는 운영 서비스는 어디인가? • 그 서비스들의 소유 팀은 누구인가? • 어제 머지한 커밋 a1b2c3d 는 지금 어느 환경까지 나가 있는가? • 기본 이미지를 석 달 넘게 갈지 않은 운영 워크로드는 몇 개인가? • 사내 공통 라이브러리 2.x 의 폐기 예정 메서드를 아직 호출하는 서비스는 몇 개인가?

다섯 질문 모두 대상이 "저장소에 있는 코드"가 아니라 "배포돼서 돌고 있는 것"이에요. 첫 질문은 실행 중인 바이너리 안의 라이브러리 버전을, 둘째는 배포 단위의 소유자를, 셋째는 커밋과 배포의 대응을, 넷째는 이미지의 내력을, 다섯째는 바이너리 안의 메서드 호출을 묻습니다. 그리고 답에는 시각이 붙어요. 지금 운영에 떠 있는 것은 한 시간 뒤에 달라질 수 있습니다.

📖 용어: 자산 인벤토리 (asset inventory)
배포된 것을 항목별로 조회할 수 있는 기록입니다. 이 시리즈에서는 "어떤 앱이, 어느 클러스터와 환경에, 어떤 버전의 바이너리로, 몇 개 떠 있는가"에 답하는 목록을 뜻해요. 클라우드와 컨테이너 환경에서는 인스턴스가 수시로 생기고 사라지니 손으로 적은 표로는 따라가지 못합니다.

가상 머신에 이름을 붙여 오래 쓰던 시절에는 이 목록을 손으로 관리할 수 있었어요. 머신 이름이 잘 안 바뀌고, 머신마다 도는 앱도 정해져 있었으니까요. 오토스케일링 그룹과 쿠버네티스에서는 인스턴스 이름이 배포할 때마다, 때로는 부하에 따라 몇 분마다 바뀝니다. 목록은 사람이 적는 대상이 아니라 플랫폼에서 읽어 오는 대상이 됐어요.

2. 커밋에서 인스턴스까지, 고리마다 식별자를 남긴다

운영 인스턴스에서 소스 코드까지 거꾸로 따라가려면 그 사이의 모든 단계가 이어져 있어야 합니다. 커밋을 빌드하고, 결과물을 저장소에 게시하고, 배포하고, 실행하는 흐름이에요. 이 흐름을 거꾸로 걸을 수 있게 고리마다 식별자를 남긴 것을 출처 체인이라고 부릅니다.

📖 용어: 출처 체인 (provenance chain)
실행 중인 인스턴스에서 출발해 배포, 결과물, 빌드, 커밋까지 한 단계씩 되짚을 수 있게 이어 둔 기록입니다. 고리 하나라도 식별자가 빠지면 그 지점에서 추적이 끊겨요. 공급망 보안 쪽에서는 빌드가 남기는 이런 기록을 provenance라 부르고, SLSA 같은 규격이 형식을 정해 두었습니다.
그림 1. 기록은 왼쪽에서 오른쪽으로 쌓이고, 질문은 오른쪽에서 출발한다

그림 1의 위쪽 줄이 흐름이고, 상자 아래의 작은 글씨가 각 고리에서 남길 식별자예요. 최소한으로는 두 개가 이어져 있어야 합니다. 배포된 결과물의 바뀌지 않는 버전과 그 결과물을 만든 커밋 해시예요. 이 둘만 있어도 "운영의 이 파드는 어느 커밋으로 만들었나"에 답할 수 있습니다.

그보다 깊이 가려면 빌드가 더 많은 것을 남겨야 해요. 빌드 도구가 의존성을 해소한 결과 전체를 남기면 "어느 라이브러리 몇 버전이 들어 있나"에 답할 수 있고, 소스를 타입 정보가 붙은 구문 트리로 남기면 "어느 메서드를 호출하나"까지 내려갈 수 있습니다. 앞쪽이 3편의 SBOM, 뒤쪽이 4편의 OpenRewrite 이야기예요.

여기서 중요한 건 기록하는 방향과 질의하는 방향이 반대라는 점입니다. 기록은 커밋에서 시작해 빌드, 게시, 배포 순으로 쌓이지만, 질문은 거의 항상 오른쪽 끝, 실행 중인 것에서 출발해요. 그래서 오른쪽 끝의 목록이 정확하지 않으면 왼쪽에 아무리 꼼꼼히 기록해도 소용이 없습니다. 질문의 출발점인 "지금 무엇이 떠 있나"를 어디서 얻느냐가 첫 번째 문제예요.

3. Git은 의도를 적고, 플랫폼은 실제를 안다

가장 먼저 떠오르는 출발점은 Git입니다. 특히 깃옵스로 배포한다면 운영 클러스터에 들어갈 매니페스트가 전부 저장소에 있으니, 저장소를 읽으면 운영 상태를 알 수 있을 것 같아요. 깃옵스가 클러스터를 Git에 맞추는 방식은 「배포 안전성」 시리즈 4편에서 다뤘으니 여기서는 되풀이하지 않겠습니다. 이 글에서 볼 것은 "Git을 읽어서 운영 인벤토리 질문에 답할 수 있는가"예요.

답하기 어려운 이유가 여럿 있습니다. Git에 적힌 것과 실제로 도는 것이 갈라지는 지점을 하나씩 짚어 볼게요.

첫째, 태그는 바뀐다. 매니페스트에 image: orders:1.4라고 적혀 있어도 그 태그가 가리키는 이미지는 레지스트리에서 바뀔 수 있어요. 태그가 다른 이미지로 옮겨지면 옛 코드와 새 코드가 섞인 파드 묶음이 생길 수 있어요(쿠버네티스 문서, Images). 노드에 이미 그 태그의 이미지가 있으면 기본 정책(IfNotPresent)에서는 다시 받지 않으니, 노드마다 다른 이미지로 파드가 뜰 수 있어요. 이 문제는 2편에서 버전의 성질로 다시 다룹니다.

📖 용어: 이미지 다이제스트 (image digest)
이미지 매니페스트 내용의 해시값입니다. sha256:9f86d0… 모양이에요. 내용이 한 바이트라도 다르면 다이제스트가 달라지니, 다이제스트로 가리킨 이미지는 바뀌지 않습니다. 태그는 사람이 붙이는 이름이고 언제든 다른 다이제스트로 옮겨 붙일 수 있어요.

둘째, 클러스터가 매니페스트를 고친다. API 서버는 저장할 때 빠진 필드에 기본값을 채우고, 변경 어드미션 웹훅은 들어오는 객체를 고쳐서 저장해요. 서비스 메시가 사이드카 컨테이너를 넣는 것, 보안 정책 도구가 이미지 태그를 다이제스트로 바꿔 적는 것이 대표적입니다. 서드파티 어드미션 컨트롤러가 파드를 태그 대신 다이제스트로 돌도록 고치기도 해요(쿠버네티스 문서, Images). 그래서 kubectl get pod -o yaml로 본 파드는 Git에 커밋한 매니페스트와 같은 문서가 아닙니다.

📖 용어: 변경 어드미션 웹훅 (mutating admission webhook)
쿠버네티스 API 서버가 객체를 저장하기 직전에 호출하는 외부 HTTP 서버입니다. 요청받은 객체를 고친 패치를 돌려줄 수 있어서, 사이드카 주입이나 기본 레이블 추가 같은 일을 해요. 고친 결과는 클러스터에만 있고 Git에는 없습니다.

셋째, 사람과 컨트롤러가 값을 바꾼다. HPA(부하에 따라 파드 수를 바꾸는 오토스케일러)는 레플리카 수를 바꾸고, 장애 대응 중에 누군가 kubectl rollout undo로 이전 버전을 되살릴 수 있어요. 깃옵스 도구는 이런 변화를 상당 부분 감지합니다. 다만 무엇을 감지하는지는 정해져 있어요. 「배포 안전성」 실습-3에서 Argo CD로 재 보니 Git에 적힌 필드를 손으로 바꾸면 0.3초 만에 되돌렸지만, Git에 없는 레이블을 붙이거나 추적 표시가 없는 리소스를 손으로 만들면 드리프트로 보지 않고 그대로 뒀습니다. 깃옵스 도구는 Git에 적힌 것을 기준으로 클러스터를 봐요.

넷째, Git에 아직 배포되지 않은 커밋이 있다. 앱 저장소의 main 브랜치에는 마지막 배포 뒤의 변경이 쌓여 있는 게 보통입니다. 서두의 코드 검색이 틀린 이유가 이거예요. 검색은 main의 빌드 파일을 봤지만, 운영 이미지는 그보다 앞선 커밋으로 만들어졌을 수 있습니다.

다섯째, 빌드 파일은 바이너리 내용을 다 말하지 않는다. 이건 플랫폼과 Git 사이가 아니라 소스와 바이너리 사이의 틈이에요. 의존성의 실제 버전은 빌드할 때 해소 규칙과 충돌 처리로 정해집니다. 3편의 주제라서 여기서는 이름만 적어 둘게요.

그림 2. Git은 원하는 상태를, 클러스터는 일어난 상태를 갖고 있다

그렇다고 "깃옵스는 실제 상태를 전혀 모른다"고 말하면 과장이에요. Argo CD 같은 도구는 클러스터의 실제 객체(live state)를 읽어 Git의 원하는 상태와 비교하고, 차이와 헬스 상태를 화면과 API로 보여 줍니다. 그러니 정확한 표현은 이렇습니다. 깃옵스 도구는 Git에 적힌 것과 비교하는 데 필요한 만큼 클러스터를 읽고, 인벤토리 질문은 Git에 적히지 않은 것까지 묻는다. 사이드카가 어떤 버전인지, 각 파드가 실제로 어떤 다이제스트로 떴는지, 깃옵스 밖에서 배포된 워크로드가 무엇인지는 결국 플랫폼에 직접 물어야 해요.

4. 플랫폼에 묻는다: 쿠버네티스, 레지스트리, 그리고 앱 자신

"지금 무엇이 떠 있나"를 묻기 좋은 곳은 세 군데입니다. 각자 아는 것이 달라서 보통은 셋을 이어 붙여요.

쿠버네티스 API: 무엇이 어디에 몇 개, 어떤 다이제스트로

파드 객체에는 두 가지 이미지 정보가 있어요. spec.containers[].image는 요청한 이미지 이름이고, status.containerStatuses[].imageID는 컨테이너 런타임이 실제로 띄운 이미지의 식별자입니다. 이 값은 런타임이 해석한 결과라서 스펙에 적은 이미지와 다를 수 있어요(쿠버네티스 API 문서, ContainerStatus). 보통 저장소 이름에 @sha256: 다이제스트가 붙은 모양입니다. 인벤토리 질의는 뒤쪽을 기준으로 해야 해요.

kubectl get pods -A -o jsonpath='{range .items[*]}{.metadata.namespace}{"\t"}{.metadata.labels.app\.kubernetes\.io/name}{"\t"}{range .status.containerStatuses[*]}{.image}{"\t"}{.imageID}{"\n"}{end}{end}' shop orders registry.example/orders:1.4 registry.example/orders@sha256:9f86d0… shop orders registry.example/orders:1.4 registry.example/orders@sha256:9f86d0… shop orders registry.example/orders:1.4 registry.example/orders@sha256:41c3a7…

위 출력은 형식을 보여 주려고 만든 예시예요. 세 번째 줄처럼 같은 태그 아래 다이제스트가 다른 파드가 섞여 있으면, 태그가 중간에 옮겨졌고 그 노드는 옛 이미지를 쓰고 있다는 뜻입니다. 이런 상황은 실습-1에서 레지스트리와 컨테이너 두 개로 직접 만들어 봐요.

앱 이름, 버전, 소유 팀은 레이블로 붙여 둡니다. app.kubernetes.io/name, app.kubernetes.io/instance, app.kubernetes.io/version, app.kubernetes.io/component, app.kubernetes.io/part-of, app.kubernetes.io/managed-by가 쿠버네티스의 권장 레이블이에요(쿠버네티스 문서, Recommended Labels). 소유 팀은 권장 목록에 없으니 조직이 이름을 정해서 붙여야 합니다. 레이블도 서비스 카탈로그도 없으면 서두의 질문 중 "소유 팀은 누구인가"에 답할 길이 없어요.

레지스트리: 다이제스트에서 커밋으로

다이제스트를 알았으면 그 이미지를 어느 커밋으로 만들었는지 알아야 합니다. 이 용도의 표준 주석(annotation) 키가 있고(OCI 이미지 규격, annotations), 같은 키를 이미지 레이블로도 쓰는 게 관례예요. org.opencontainers.image.revision은 "패키징한 소프트웨어의 소스 관리 리비전 식별자", org.opencontainers.image.source는 "이미지를 빌드한 소스 코드를 받을 수 있는 URL"입니다. 빌드할 때 이 둘을 이미지 레이블로 넣어 두면, 다이제스트 하나로 레지스트리에서 설정을 읽어 커밋과 저장소를 찾을 수 있어요.

docker build \ --label org.opencontainers.image.revision=$(git rev-parse HEAD) \ --label org.opencontainers.image.source=https://git.example/shop/orders \ -t registry.example/orders:1.4 . docker buildx imagetools inspect registry.example/orders@sha256:9f86d0… \ --format '{{json .Image.Config.Labels}}'

레이블을 직접 넣지 않아도 단서가 남는 경우가 있어요. Docker의 buildx는 레지스트리로 내보낼 때(docker 드라이버면 containerd 이미지 저장소를 켰을 때) 기본으로 SLSA 형식의 출처 증명(provenance)을 함께 올리는데, 실습-1에서 열어 보니 그 안에 빌드한 Git 저장소 주소와 커밋 해시가 들어 있었습니다. 다만 빌드 도구의 기본값에 기대는 것이라, 질의에 쓸 거라면 레이블처럼 명시적으로 넣는 편이 확실해요.

앱 자신: /actuator/info와 /actuator/sbom

세 번째 방법은 실행 중인 앱에게 직접 묻는 거예요. 스프링 부트는 클래스패스 루트에 git.properties 파일이 있으면 /actuator/info에서 git.branch, git.commit.id, git.commit.time을 보여 줍니다. 이 파일은 Maven의 git-commit-id-maven-plugin이나 Gradle의 com.gorylenko.gradle-git-properties 플러그인이 빌드할 때 만들어요. 스프링 부트 3.3부터는 /actuator/sbom 엔드포인트도 있습니다. 빌드할 때 CycloneDX 플러그인으로 만든 SBOM을 jar 안에 넣어 두면, 실행 중인 앱이 자기 의존성 목록을 돌려줘요.

📖 용어: SBOM (Software Bill of Materials)
결과물 안에 든 구성 요소와 그 버전을 적은 목록입니다. 사람이 쓰는 문서가 아니라 빌드 도구가 해소한 결과를 기계가 읽을 수 있는 형식(CycloneDX, SPDX)으로 남긴 파일이에요. 취약점 공지가 오면 이 목록에서 해당 버전을 찾습니다.

SBOM에도 한계가 하나 있어요. 빌드할 때 Gradle이나 Maven이 해소한 결과를 적은 것이라, 빌드 뒤에 이미지에 얹힌 것은 모릅니다. 실습-2에서 배포할 때 옛 logback jar를 클래스패스 앞에 얹은 서비스를 하나 만들었더니, 그 서비스의 /actuator/sbom은 빌드 때 들어간 새 버전을 말했고 실제 JVM은 얹힌 옛 jar에서 클래스를 읽고 있었어요. 서비스 열 개 중 취약한 넷을 SBOM은 셋 찾았고, 놓친 하나가 이 경우였습니다.

앱에게 묻는 방법은 플랫폼에 묻는 방법을 대신하지 않아요. 앱은 자기 이야기만 하고, 자기가 몇 개 떠 있는지, 어느 클러스터에 있는지는 모릅니다. 그래서 순서는 이렇게 됩니다. 플랫폼에서 떠 있는 워크로드와 다이제스트 목록을 받고, 각 다이제스트나 인스턴스에 대해 레지스트리나 앱에서 커밋과 의존성을 읽어 붙여요.

⚠️ 주의: sbom과 info를 바깥에 열지 않는다
• 스프링 부트는 기본으로 health만 HTTP에 노출해요. info와 sbom을 켜려면 management.endpoints.web.exposure.include에 직접 넣어야 합니다
• SBOM은 공격자 입장에서 "이 서버에 든 라이브러리와 버전 목록"이에요. 켤 때는 management.server.port로 관리용 포트를 따로 두고, 그 포트는 클러스터 안에서만 닿게 하세요
• info의 git 정보도 기본은 브랜치, 커밋 ID, 커밋 시각 세 개뿐이에요. management.info.git.mode=full로 늘리기 전에 무엇이 나가는지 확인하세요

5. 스피나커가 보여 준 모양: 한 번의 질의로 모든 클라우드를

이 일을 오래전부터 도구 차원에서 해 온 곳이 Spinnaker예요. Spinnaker는 지원하는 모든 클라우드 제공자에서 배포 인프라를 읽어, 애플리케이션, 클러스터, 서버 그룹, 인스턴스라는 같은 모양으로 보여 줍니다. AWS의 오토스케일링 그룹도, 쿠버네티스의 ReplicaSet도 서버 그룹이라는 한 단어로 묶여요. 이 용어는 「배포 안전성」 1편에서 정리했습니다. UI와 모든 API 호출은 API 게이트웨이인 Gate를 거치고, 앱 목록은 Gate의 /applications에서 시작해요.

읽는 방식도 짚어 둘 만합니다. 질문이 올 때마다 클라우드에 묻는 게 아니에요. Clouddriver라는 서비스가 "캐싱 에이전트"를 기본 30초마다 돌려 각 클라우드의 배포 자원을 읽고 색인해 두고, 질의는 그 색인에서 답합니다(Spinnaker 문서, Configure Spinnaker's Usage of Redis). 핵심은 색인의 원천이 "배포하려고 적어 둔 기록"이 아니라 "플랫폼에서 읽은 결과"라는 점이에요.

이 모델 위에서는 인벤토리 질문이 짧은 질의 하나가 됩니다. 아래는 "쿠버네티스에서 도는 앱을 소유한 팀 목록"을 의사코드로 적은 거예요.

delivery.getApplications() .filter(app -> app.getClusters() .anyMatch(c -> c.getCloudProvider().equals("kubernetes"))) .map(app -> app.getOwner()) .collect(toSet()); // 서버 그룹마다 결과물(그룹:이름:버전)이 하나씩 붙어 있으면, 한 단계만 더 내려가면 된다 delivery.getApplications() .flatMap(Application::getClusters) .flatMap(Cluster::getServerGroups) .filter(sg -> sg.getArtifact().getDependencies().stream() .anyMatch(d -> d.is("ch.qos.logback", "logback-core") && d.versionBelow("1.5.13")));

이 방식의 장점은 배포 이력을 따로 관리하는 중앙 기록이 필요 없다는 거예요. 누가 손으로 롤백하거나 서버 그룹을 직접 띄워도 다음 캐싱 주기에 답에 반영됩니다. 단점도 같은 곳에서 나와요. 색인은 지금 상태만 들고 있어서 지난주 화요일에 무엇이 떠 있었는지는 물을 수 없고, 마지막 캐싱 뒤에 생긴 변화는 다음 주기까지 보이지 않습니다.

Spinnaker를 쓰지 않아도 같은 모양을 만들 수 있어요. 오늘 많이 쓰는 조합으로 바꿔 적으면 이렇습니다.

질문 어디서 답을 얻나 ─────────────────────────────────── ───────────────────────────────────────────── 무엇이 어디에 몇 개 떠 있나 쿠버네티스 API (클러스터마다), 클라우드 API 그 인스턴스는 어떤 이미지인가 파드 status.containerStatuses[].imageID 그 이미지는 어느 커밋인가 이미지 레이블 org.opencontainers.image.revision 또는 앱의 /actuator/info git.commit.id 그 안에 어떤 라이브러리가 몇 버전인가 빌드 때 만든 SBOM (이미지 첨부 또는 /actuator/sbom) 누가 소유하나 워크로드 레이블, 서비스 카탈로그 Git과 다른 점은 무엇인가 깃옵스 도구의 diff (Git에 적힌 필드에 한해)

표의 왼쪽 열은 모두 "지금"을 묻는 질문이에요. 오른쪽 열의 첫 줄, 플랫폼 API가 나머지 줄의 입력을 만듭니다. Git은 맨 아래 줄 한 곳에만 등장해요. Git이 쓸모없다는 뜻이 아닙니다. Git은 "원래 무엇을 의도했나"에 답하는 곳이고, 인벤토리 질문은 대개 "실제로 무엇이 일어났나"를 묻는다는 뜻이에요.

6. 매번 물을까, 찍어 둘까

마지막으로 남는 선택은 질의 시점이에요. 두 방식이 있고 둘 다 대가가 있습니다.

실시간 질의는 질문이 올 때 모든 클러스터와 앱에 묻고 답을 조합하는 방식이에요. 답은 항상 최신이지만, 플랫폼 API가 느리거나 일부 클러스터에 닿지 않으면 답이 비거나 늦습니다. 앱의 /actuator/sbom을 수백 개 인스턴스에 매번 부르는 것도 부담이에요. 같은 버전의 인스턴스는 같은 SBOM을 돌려주니, 다이제스트 단위로 한 번씩만 물으면 됩니다.

주기적 스냅숏은 몇 분이나 몇 시간마다 위 표의 결과를 모아 저장하는 방식이에요. 질의가 빠르고, "지난 장애 시각에 어떤 버전이 떠 있었나"처럼 과거를 물을 수 있습니다. 대신 스냅숏 사이에 생긴 변화는 다음 수집 때까지 보이지 않아요. 보안 공지가 와서 급하게 묻는 질문에는 그 공백이 문제가 될 수 있습니다.

그림 3. 실시간 질의는 과거를 잃고, 스냅숏은 사이의 변화를 잃는다

Spinnaker의 30초 캐시는 둘 사이에 있어요. 주기가 짧은 스냅숏이지만 과거를 남기지 않으니, 과거를 물으려면 그 결과를 따로 쌓아야 합니다. 실무에서는 둘을 같이 쓰는 경우가 많아요. 평소 대시보드와 감사 기록은 스냅숏으로, 보안 공지 같은 급한 질문은 실시간 질의로 답합니다. 어느 쪽이든 입력은 같아요. 플랫폼 API가 돌려준 "지금 떠 있는 것"입니다.

답을 얻은 뒤의 순서도 정해 두면 좋아요. 취약한 버전이 운영과 테스트 환경 양쪽에서 나오면 운영 쪽부터 고칩니다. 테스트 환경은 운영으로 코드를 넘기는 경로라서 다음 차례예요. 인벤토리에 환경 정보(레이블이나 네임스페이스)가 붙어 있어야 이 순서를 목록에서 바로 뽑을 수 있습니다.

💡 실무에서는
• 이미지를 빌드할 때 org.opencontainers.image.revision과 org.opencontainers.image.source 레이블을 넣어 두세요. 다이제스트 하나에서 커밋까지 한 번에 갈 수 있어요
• 앱에는 git.properties를 넣고 /actuator/info를 관리 포트에 열어 두세요. 레지스트리에 닿지 않는 환경에서도 앱에게 직접 물을 수 있어요
• 워크로드에는 app.kubernetes.io/name, app.kubernetes.io/version과 팀 레이블을 붙이세요. 레이블이 빠진 워크로드 수를 세는 것부터가 인벤토리 점검이에요
• 인벤토리 질의는 태그가 아니라 imageID의 다이제스트로 하세요. 같은 태그 아래 다이제스트가 둘 이상이면 그것 자체가 알릴 만한 사건이에요

여기까지 오면 서두의 질문에 다시 답할 수 있어요. 코드 검색 대신 클러스터마다 파드의 다이제스트를 모으고, 다이제스트마다 SBOM을 열어 logback-core 버전을 봅니다. 결과에서 운영 네임스페이스를 먼저 골라 소유 팀 레이블로 묶어요. 실습-2에서 서비스 열 개로 이 질의를 돌려 보니, main 브랜치의 빌드 파일로 찾은 답은 취약한 넷 중 하나만 맞히고 하나를 잘못 짚었고, 실행 중인 서비스의 SBOM은 넷 중 셋을 오탐 없이 찾았어요. 빌드 파일이 놓친 셋은 운영에 옛 커밋이 떠 있던 서비스, 버전을 버전 카탈로그에 적어 둔 서비스, 배포할 때 jar를 얹은 서비스였어요. 마지막 하나는 SBOM도 놓쳤습니다.

그런데 이 체인이 성립하려면 고리마다 남긴 식별자가 한 가지 성질을 가져야 해요. 같은 이름이 언제나 같은 바이너리를 가리켜야 합니다. 1.4라는 태그나 1.0.0-SNAPSHOT이라는 버전은 이 성질을 보장하지 않아요.

✍️ 오늘의 요약
인벤토리 질문은 거의 다 "지금 운영에 떠 있는 것"을 묻고, 그 답은 Git이 아니라 플랫폼이 갖고 있어요. Git에 적힌 매니페스트는 태그 이동, 어드미션 웹훅, HPA와 손 롤백, 배포되지 않은 커밋 때문에 실제와 갈라집니다. 깃옵스 도구도 Git에 적힌 필드만큼만 클러스터를 비교해요.

그래서 질의는 플랫폼 API에서 시작합니다. 파드의 imageID로 다이제스트를, 이미지 레이블이나 /actuator/info로 커밋을, SBOM으로 라이브러리 버전을 이어 붙여요. 출처 체인은 커밋에서 쌓이지만, 질문은 언제나 실행 중인 쪽 끝에서 출발합니다.
