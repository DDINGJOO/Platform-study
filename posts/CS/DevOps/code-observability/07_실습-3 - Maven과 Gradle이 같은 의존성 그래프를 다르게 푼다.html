3편에서 빌드 파일은 요청만 적고, jar에 들어가는 버전은 빌드 도구가 해소할 때 정해진다고 했어요. Maven은 가까운 쪽을, Gradle은 높은 쪽을 고른다는 것도 문서로 봤습니다. 이번에는 그 그래프를 직접 만들어 두 도구에 풀게 했어요. 같은 소스, 같은 의존성 선언을 두 도구로 빌드하고, 무엇이 jar에 들어갔는지 보고, 실행까지 시켰습니다.

결과를 먼저 말하면 모듈 일곱 개 중 셋에서 두 도구가 서로 다른 버전을 골랐고, 두 도구 모두 실행 중에 NoSuchMethodError를 냈어요. 컴파일은 전부 통과했습니다. 미사용 의존성 분석기 두 개는 같은 네 건을 보고했는데, 그대로 지우면 안 되는 것이 둘 섞여 있었어요. 하나는 빼자마자 실행이 깨졌고, 다른 하나는 Maven에서 들어가는 버전을 바꿨어요. 쓰지 않는 Spring Data REST starter 하나는 내부용 감사 로그를 HTTP로 지울 수 있게 열어 줬습니다. 숫자는 전부 이번에 돌린 결과예요.

1. 실습 환경: 파일 저장소 하나, 빌드 도구 둘

공개 저장소의 실제 라이브러리로는 원하는 모양의 그래프를 만들기 어려워서, 작은 라이브러리를 직접 만들어 파일 기반 Maven 저장소에 올렸어요. 핵심은 c입니다. 1.0에는 legacy()가 있고, 2.0은 그걸 지우고 encodeFast()를 더했어요. a는 c 1.0의 legacy()를, d는 c 2.0의 encodeFast()를 부릅니다. b는 d를 거쳐 c 2.0을 끌고 와요.

그림 1. 저장소도 소스도 같고, 빌드 도구만 다르다
📖 용어: 파일 기반 Maven 저장소
저장소 서버 없이 디렉터리 하나를 group/artifact/version/artifact-version.jar와 .pom 배치로 채워 두고 file:// URL로 가리키는 방식입니다. Maven과 Gradle 모두 원격 저장소와 같은 방식으로 읽어서, 실습용 그래프를 몇 KB로 만들 수 있어요.

소비자 모듈은 일곱 개예요. 각 모듈의 Main은 클래스패스에 올라온 c의 버전을 리플렉션으로 읽고(c를 직접 import하지 않으려고요), 선언한 라이브러리의 run()을 하나씩 불러 성공과 실패를 찍습니다.

모듈 선언(순서대로) 노리는 것 m1 a, b 깊이가 다른 충돌 (c 1.0 은 깊이 2, c 2.0 은 깊이 3) m2 b, a m1 과 선언 순서만 바꿈 m3 x, y 깊이가 같은 충돌 (둘 다 깊이 2), x 가 먼저 m4 y, x m3 과 선언 순서만 바꿈 m5 a, b, c 2.0 c 를 직접 선언해 버전을 고정 an b, e, drv, konst c 를 import 하지만 선언하지 않음 an-decl b, c 2.0 c 를 import 하고 선언도 함

2. 일곱 개 중 세 개 모듈에서 고른 버전이 달랐다

먼저 각 모듈의 런타임 클래스패스에 어느 c가 올라왔는지 봤어요.

모듈 Maven Gradle m1 c 1.0 c 2.0 다름 m2 c 1.0 c 2.0 다름 m3 c 2.0 c 2.0 m4 c 1.0 c 2.0 다름 m5 c 2.0 c 2.0 an c 2.0 c 2.0 an-decl c 2.0 c 2.0

Gradle은 일곱 개 모두 c 2.0이었어요. 요청된 버전 중 높은 것을 고르니 경로와 순서는 상관없습니다. Maven은 경로와 순서에 따라 갈렸어요. mvn dependency:tree -Dverbose가 이유까지 보여 줍니다.

lab.co3.consumer:m1:jar:1.0 +- lab.co3:a:jar:1.0:compile | \- lab.co3:c:jar:1.0:compile \- lab.co3:b:jar:1.0:compile \- lab.co3:d:jar:1.0:compile \- (lab.co3:c:jar:2.0:compile - omitted for conflict with 1.0)

m1에서 c 1.0은 a 아래 깊이 2, c 2.0은 b → d 아래 깊이 3이에요. 가까운 c 1.0이 남고 2.0은 "충돌로 생략"됐습니다. m2는 선언 순서를 바꿨지만 깊이가 그대로라 결과도 같았어요. 순서가 결과를 바꾼 건 깊이가 같은 m3와 m4였습니다.

lab.co3.consumer:m3:jar:1.0 lab.co3.consumer:m4:jar:1.0 +- lab.co3:x:jar:1.0:compile +- lab.co3:y:jar:1.0:compile | \- lab.co3:c:jar:2.0:compile | \- lab.co3:c:jar:1.0:compile \- lab.co3:y:jar:1.0:compile \- lab.co3:x:jar:1.0:compile \- (lab.co3:c:jar:1.0:compile \- (lab.co3:c:jar:2.0:compile - omitted for conflict with 2.0) - omitted for conflict with 1.0)

pom.xml에서 두 줄의 순서만 바꿨는데 jar에 들어가는 c가 바뀌었어요. 문서의 "깊이가 같으면 먼저 선언한 쪽이 이긴다"가 그대로 나왔습니다. 코드 리뷰에서 의존성 선언 두 줄의 순서가 바뀐 diff를 보고 jar 내용이 바뀐다고 알아챌 사람은 많지 않을 거예요.

📖 용어: dependencyInsight (Gradle)
Gradle에서 라이브러리 하나를 지정해 "어떤 버전이 골라졌고, 누가 어떤 버전을 요청했고, 어떤 규칙으로 정해졌나"를 보여 주는 태스크입니다. Maven의 dependency:tree -Dverbose에 해당하는 질문을 라이브러리 기준으로 뒤집어 묻는 도구예요.

Gradle 쪽 이유는 dependencyInsight로 봤어요. 아래 명령은 lab.sh resolve가 Gradle 컨테이너 안에서 실행한 것이에요.

$ gradle -q :m1:dependencyInsight --dependency lab.co3:c --configuration runtimeClasspath lab.co3:c:2.0 Selection reasons: - By conflict resolution: between versions 2.0 and 1.0 lab.co3:c:2.0 \--- lab.co3:d:1.0 \--- lab.co3:b:1.0 \--- runtimeClasspath lab.co3:c:1.0 -> 2.0 \--- lab.co3:a:1.0 \--- runtimeClasspath

c:1.0 -> 2.0은 a가 1.0을 요청했지만 충돌 해소로 2.0이 들어갔다는 뜻이에요. 같은 출력의 속성 표에는 org.gradle.status = release도 찍혀 있었어요. 3편에서 POM으로 읽은 모듈은 SNAPSHOT이 아니면 release 상태가 된다고 했는데, 이 직접 만든 저장소의 모듈도 그렇게 분류됐습니다.

3. 컴파일은 모두 통과했고, 실행은 두 도구 모두 깨졌다

이제 각 모듈의 Main을 실행했어요. 고른 버전에 따라 어느 라이브러리가 깨지는지가 갈립니다.

모듈 호출 Maven Gradle m1 a OK FAIL NoSuchMethodError: Codec.legacy m1 b FAIL NoSuchMethodError: Codec.encodeFast OK m2 a OK FAIL NoSuchMethodError: Codec.legacy m2 b FAIL NoSuchMethodError: Codec.encodeFast OK m3 x, y OK OK m4 x, y OK OK m5 a FAIL NoSuchMethodError: Codec.legacy FAIL NoSuchMethodError: Codec.legacy m5 b OK OK

Maven과 Gradle이 각각 세 번씩 실패했어요. 그런데 실패한 자리가 달랐습니다. m1과 m2에서 Maven은 b를, Gradle은 a를 깨뜨렸어요. 둘 다 컴파일은 통과했고, 실패는 그 메서드를 실제로 부르는 순간에야 나왔습니다. 컴파일러가 본 건 앱의 소스뿐이고, a와 d는 이미 다른 버전의 c를 보고 컴파일된 jar로 들어왔기 때문이에요.

📖 용어: NoSuchMethodError
컴파일할 때는 있던 메서드가 실행할 때 클래스패스의 클래스에는 없을 때 JVM이 던지는 오류입니다. 소스 코드 오류가 아니라 버전이 어긋났다는 신호라서, 대개 의존성 해소 결과를 의심해야 해요.

m5는 c 2.0을 직접 선언해서 두 도구의 결과를 맞췄어요. b는 두 쪽 모두 살아났지만 a는 두 쪽 모두 깨졌습니다. a는 1.0에만 있는 메서드를, d는 2.0에만 있는 메서드를 부르니 둘 다 동작하는 c는 존재하지 않습니다. 버전을 고정하는 건 어느 쪽을 깨뜨릴지 사람이 정하는 일이지 충돌을 없애는 일이 아니에요. 이 경우의 해결은 a를 c 2.0과 호환되는 버전으로 올리는 것뿐입니다.

m3와 m4는 고른 버전이 달랐는데도 둘 다 문제없이 돌았어요. x와 y는 두 버전에 모두 있는 encode()만 부르기 때문입니다. 버전이 다르다는 사실만으로 장애가 나지는 않아요. 그래서 이런 차이는 평소에 드러나지 않다가, 어느 날 한쪽 라이브러리가 사라진 메서드를 부르기 시작할 때 나타납니다.

💡 실무에서는
• Maven이라면 Enforcer 플러그인의 requireUpperBoundDeps를 걸어 두면 m1 같은 경우(가까운 쪽이 더 낮은 버전을 고른 경우)에서 빌드가 멈춰요.
• Gradle은 높은 쪽을 고르니 "누군가 낮은 버전을 요구했는데 무시됐다"가 조용히 지나가요. dependencyInsight의 -> 표시를 CI에서 모아 보거나, resolutionStrategy.failOnVersionConflict()를 걸어 버전 충돌 자체를 빌드 실패로 바꿔요. 리치 버전의 strictly는 실패를 만드는 장치가 아니에요. 다른 경로의 요청을 덮어 그 버전으로 고정하고, 받아들일 수 있는 버전이 하나도 없을 때만 해소가 실패합니다.

4. 분석기 둘은 같은 네 건을 보고했고, 그대로 지우면 안 되는 것이 섞여 있었다

다음은 미사용, 미선언 분석이에요. an 모듈은 일부러 이렇게 짰습니다. c를 import하지만 선언하지 않았고(b → d → c로 들어옴), e는 선언만 하고 쓰지 않고, drv는 Class.forName("lab.drv.Driver")로만 읽고, konst는 컴파일 타임 상수 K.NAME만 씁니다. 모듈 일곱 개 전부에 두 도구를 돌렸어요. 아래 명령은 lab.sh analyze가 각 컨테이너 안에서 실행한 것이에요.

$ mvn -f maven/pom.xml -pl an dependency:analyze [WARNING] Used undeclared dependencies found: [WARNING] lab.co3:c:jar:2.0:compile [WARNING] Unused declared dependencies found: [WARNING] lab.co3:e:jar:1.0:compile [WARNING] lab.co3:drv:jar:1.0:compile $ mvn -f maven/pom.xml -pl m5 dependency:analyze [WARNING] Unused declared dependencies found: [WARNING] lab.co3:c:jar:2.0:compile $ gradle buildHealth Advice for :an Unused dependencies which should be removed: implementation("lab.co3:drv:1.0") implementation("lab.co3:e:1.0") These transitive dependencies should be declared directly: implementation("lab.co3:c:2.0") Advice for :m5 Unused dependencies which should be removed: implementation("lab.co3:c:2.0")

두 도구의 결론이 정확히 같았어요. 미선언 1건(an의 c), 미사용 3건(an의 e, an의 drv, m5의 c)입니다. 나머지 다섯 모듈은 둘 다 문제없다고 했어요. 그럼 "미사용" 셋은 정말 지워도 될까요? an에서 하나씩 빼고 실행해 봤습니다(scripts/remove-check.sh, 호스트의 JDK 25에서 --release 17로 컴파일).

--- 뺀 것: e RESULT an c=2.0 c2:an RESULT an b fast:d RESULT an drv drv-loaded RESULT an konst konst --- 뺀 것: drv RESULT an c=2.0 c2:an RESULT an b fast:d Exception in thread "main" java.lang.ClassNotFoundException: lab.drv.Driver

e는 정말 필요 없었고 drv는 빼자마자 ClassNotFoundException이 났어요. 리플렉션으로만 쓰는 의존성은 바이트코드에 클래스 참조가 남지 않으니 두 분석기 모두 보지 못합니다. m5의 c 2.0은 더 미묘해요. m5의 코드는 c를 직접 부르지 않으니 "안 쓴다"는 판정은 글자 그대로는 맞습니다. 그런데 m5에서 그 한 줄을 지우면 m1과 똑같은 선언(a, b)이 돼요. 직접 지워서 돌리지는 않았지만, m1의 결과대로라면 Maven은 c 1.0을 고르고 깨지는 라이브러리가 a에서 b로 바뀝니다. jar에 들어가는 c가 달라지는 거예요. 버전을 정하려고 적어 둔 선언을 분석기는 "안 쓰는 선언"으로 봅니다. Gradle에서는 지워도 어차피 2.0이 골라지니 이 조언이 맞고, Maven에서는 틀린 조언이 돼요. 같은 보고가 빌드 도구에 따라 맞기도 틀리기도 합니다.

📖 용어: 상수 풀 (constant pool)
클래스 파일 안에 있는 표로, 그 클래스가 참조하는 다른 클래스, 메서드, 문자열 상수를 모아 둡니다. 바이트코드 명령은 이 표의 번호로 대상을 가리켜요. 바이트코드 수준 분석기는 대개 이 표에 어떤 클래스가 있는지로 "쓴다"를 판단합니다.

konst는 두 도구 모두 "쓴다"고 판정했어요. 상수 값은 쓰는 쪽 바이트코드에 복사되니 흔적이 안 남을 수도 있다고 생각했는데, 이 사례에서는 남아 있었습니다. an은 K.NAME을 문자열 연결이라는 표현식 안에서 써요. 같은 소스를 컨테이너의 javac 21로 컴파일하고 javap -v로 열어 봤어요(scripts/const-check.sh, 결과는 results/const-check-jdk21.txt).

javac 21.0.12.1 == Main : 상수 풀의 'Class lab/konst/K' 항목 1 개 #67 = Class #68 // lab/konst/K #69 = String #70 // RESULT an konst konst == SwitchUse : 상수 풀의 'Class lab/konst/K' 항목 0 개 29: ldc #13 // String konst == AnnotationUse : 상수 풀의 'Class lab/konst/K' 항목 0 개

값을 읽는 명령은 문자열을 바로 올리는 ldc인데도 Class lab/konst/K 항목이 남았어요. javac가 의존성 추적용으로 일부러 남기는 항목입니다(JDK 8의 JDK-7153958, 필드 초기화식은 JDK 9의 JDK-8073372). 분석기는 이 항목을 보고 "쓴다"로 봤어요. 비교하려고 같은 상수를 switch의 case 라벨에만 쓰는 SwitchUse와 어노테이션 값에만 쓰는 AnnotationUse를 더 컴파일해 봤더니 이 항목이 0개였어요. 그러니 "상수만 쓰는 의존성은 안 쓴다고 나올 수 있다"는 말은 쓰는 방식에 따라 맞기도 틀리기도 합니다. 이 두 클래스로 분석기를 다시 돌리지는 않았어요. 실행할 때는 konst를 빼도 잘 돌았습니다. 값이 이미 복사돼 있으니까요. 컴파일에는 필요하고 실행에는 필요 없는 의존성이라, 이 사례의 "쓴다" 판정은 컴파일 관점에서 맞는 셈이에요.

⚠️ 주의: Maven의 -q는 분석 결과를 지운다
처음에는 mvn -q dependency:analyze로 돌렸다가 m5의 경고가 하나도 안 나와서 "문제없음"으로 읽을 뻔했어요. -q는 오류만 남기고 WARNING을 지우는데, dependency:analyze는 결과를 WARNING으로 찍습니다. 결과를 파일로 모을 때는 -q를 빼고 WARNING 줄을 걸러야 해요. CI에서 쓰려면 -DfailOnWarning=true로 종료 코드에 반영합니다.

5. b를 2.0으로 올리자 미선언 모듈 하나만 컴파일이 깨졌다

b 2.0은 더 이상 d를 쓰지 않아서 c도 끌고 오지 않아요. 1차 의존성 b의 버전만 올리고(-Db.version=2.0, Gradle은 -PbVersion=2.0) 일곱 모듈을 다시 컴파일했습니다.

모듈 Maven Gradle m1..m5 compile OK compile OK an compile FAIL compile FAIL an-decl compile OK compile OK [ERROR] /work/maven/an/src/main/java/lab/co3/Main.java:[4,13] package lab.c does not exist [ERROR] /work/maven/an/src/main/java/lab/co3/Main.java:[9,45] cannot find symbol [ERROR] /work/maven/an/src/main/java/lab/co3/Main.java:[9,69] cannot find symbol

깨진 건 an 하나였고, 오류는 세 개(import 한 줄, Codec을 쓰는 두 곳)였어요. Maven 기준이에요. Gradle 출력에는 열 번호가 없어서 같은 줄의 오류 둘이 합쳐져 두 개로 셌어요. 4절에서 분석기 둘이 "선언하지 않고 쓴다"고 지적한 바로 그 모듈입니다. c를 직접 선언한 an-decl은 같은 코드인데도 멀쩡했어요. 미선언 보고는 이번 실습에서 한 번도 틀리지 않았습니다. 3편의 "쓰는데 선언 안 했다는 보고는 대체로 바로 고쳐도 안전하다"와 맞는 결과예요.

m1과 m2는 b를 쓰지만 c를 리플렉션으로만 읽어서 컴파일이 통과했어요. 대신 c를 공급하던 경로가 a 하나만 남으니, 그래프대로라면 이 두 모듈의 c는 Gradle에서도 1.0으로 바뀝니다(이번에 실행으로 확인하지는 않았어요). 1차 의존성 하나를 올렸을 때 바뀌는 건 컴파일 결과만이 아니에요.

6. 쓰지 않는 starter 하나가 내부 감사 로그를 지울 수 있게 열었다

마지막은 Spring Boot예요. 두 앱을 변형 넷으로 빌드했습니다. plain은 webmvc와 actuator에 /hello 하나뿐이고, plain-unused는 여기에 data-rest, data-jpa, h2를 더했지만 코드는 한 줄도 바꾸지 않았어요. audit은 JPA로 감사 로그(AuditLog 엔티티, AuditLogRepository)를 내부에서만 쓰는 앱이고 공개 API는 POST /orders 하나입니다. audit-rest는 여기에 data-rest만 더했어요. 각각 네 번 띄웠고, 첫 회는 디스크 캐시가 데워지는 회차라 범위에서 뺐습니다.

변형 jar lib 수 빈 수 매핑 수 Started(초, 2~4회차) plain 22.0MB 42 252 10 1.09 ~ 1.34 plain-unused 56.4MB 84 409 42 1.99 ~ 2.06 audit 54.6MB 74 337 10 2.08 ~ 2.13 audit-rest 56.4MB 84 412 42 2.41 ~ 2.42 빈 수: /actuator/beans, 매핑 수: /actuator/mappings 의 dispatcherServlet 항목 Started: 기동 로그의 "Started ... in N seconds" 측정 중 호스트 load average 약 8~10 (다른 실습이 같이 돌았다)

코드에서 쓰지 않는 의존성 셋(starter 둘과 h2)이 jar를 2.6배로 키우고, 라이브러리 42개, 빈 157개, 매핑 32개를 더했어요. 기동은 0.7~0.9초 늘었습니다(2~4회차 범위끼리 비교). data-rest 하나만 놓고 보면(audit → audit-rest) 라이브러리 10개, 빈 75개, 매핑 32개였어요. 크기는 1.8MB라 무시할 만했습니다. 문제는 매핑이에요.

audit-rest 에만 있는 매핑 (32개 중 일부) {GET [/{repository}], ...} {GET [/{repository}/{id}], ...} {POST [/{repository}], ...} {PUT [/{repository}/{id}], ...} {PATCH [/{repository}/{id}], ...} {DELETE [/{repository}/{id}], ...} {GET [/profile]} {GET [/ || ], ...} ...

Repository 이름 자리를 변수로 받는 조회, 생성, 수정, 삭제 경로가 통째로 생겼어요. 실제로 불러 봤습니다.

요청 audit audit-rest GET / 404 200 GET /profile 404 200 GET /auditLogs 404 200 (감사 로그 3건이 그대로 나옴) DELETE /auditLogs/1 404 204 GET /auditLogs 404 200 (2건 남음)

코드 어디에도 /auditLogs라는 경로는 없어요. 개발자가 공개한 API는 POST /orders 하나였는데, 빌드 파일의 한 줄 때문에 인증 없이 감사 로그를 읽고 지울 수 있게 됐습니다. Spring Data REST의 기본 노출 전략(DEFAULT)은 소스 주석 그대로 "public 인터페이스이거나 @RepositoryRestResource를 붙인 것"을 내보내고, 이 앱의 Repository는 흔히 그렇듯 public이었어요. 이 starter를 넣은 사람이 쓸 생각이었는지와 상관없이요. 3편에서 쓰지 않는 의존성은 크기보다 자동 구성이 문제라고 했던 게 이 장면입니다.

💡 실무에서는
• 배포 전에 /actuator/mappings를 떠서 이전 배포와 비교해요. 코드 리뷰에 없던 경로가 생겼다면 의존성 변경이 원인일 가능성이 높습니다.
• Spring Data REST를 실제로 쓰더라도 노출 전략을 spring.data.rest.detection-strategy=annotated로 바꿔 @RepositoryRestResource를 붙인 것만 열리게 해요. 의도하지 않은 Repository가 열리는 걸 막는 가장 싼 방법입니다.
• 미사용 분석기가 starter를 지적하면 지우기 전에 이 표의 네 숫자(jar, 빈, 매핑, 기동)를 지우기 전후로 재 봐요. 효과가 숫자로 보여요.
✍️ 오늘의 요약
같은 선언으로 Maven과 Gradle이 일곱 모듈 중 셋에서 다른 c를 골랐고, 두 도구 모두 컴파일은 통과한 뒤 실행 중에 세 번씩 NoSuchMethodError를 냈어요. Maven에서는 선언 두 줄의 순서만 바꿔도 jar에 든 c가 바뀌었어요.

미사용 분석기 둘은 같은 네 건을 보고했고, 그중 리플렉션으로만 쓰는 drv는 빼자마자 깨졌고, 버전 고정용 선언은 빼면 Maven에서 깨지는 라이브러리가 a에서 b로 바뀌어요(m1과 같은 선언). 미선언 보고는 b를 올렸을 때 실제로 깨진 유일한 모듈을 정확히 짚었습니다. 그리고 쓰지 않는 data-rest 하나가 매핑 32개를 더해 내부 감사 로그를 HTTP로 지울 수 있게 만들었어요. 빌드 파일이 아니라 해소 결과와 열린 경로를 직접 확인해야 하는 이유가 여기 있습니다.
