🧬 소스 코드 관찰, 3편
1편. 지금 운영에 무엇이 떠 있는지는 Git이 아니라 플랫폼에 묻는다
2편. SNAPSHOT과 latest는 버전이 아니라 포인터다
3편. 빌드 파일에 적은 버전과 jar에 들어간 버전은 다르다 ← 지금 이 글
4편. grep은 글자를 찾고, 타입이 붙은 구문 트리는 호출을 찾는다
실습-1. 같은 좌표가 다른 바이너리를 가리키는 순간을 만든다
실습-2. 서비스 열 개에서 취약한 라이브러리를 쓰는 곳을 SBOM으로 찾는다
실습-3. Maven과 Gradle이 같은 의존성 그래프를 다르게 푼다
실습-4. grep, OpenRewrite, 커버리지가 센 호출 수가 다르다

보안팀 공지가 옵니다. 어떤 라이브러리의 특정 버전에 원격 코드 실행 취약점이 있으니, 그 버전을 쓰는 서비스를 오늘 안에 알려 달라는 내용이에요. 가장 먼저 떠오르는 방법은 사내 저장소 전체에서 pom.xml과 build.gradle을 검색하는 겁니다. 몇 분이면 목록이 나와요.

그런데 그 목록은 두 방향으로 틀립니다. 빌드 파일에 그 라이브러리가 한 줄도 없는 서비스의 jar를 열어 보면 문제의 버전이 들어 있어요. 반대로 빌드 파일에 그 버전을 적어 둔 서비스의 jar에는 다른 버전이 들어 있기도 합니다. 둘 다 빌드 도구가 일을 제대로 해서 생긴 결과예요. 빌드 파일은 요청을 적은 문서이고, jar에 들어가는 건 빌드 도구가 그 요청들을 해소한 결과이기 때문입니다.

이번 편에서 볼 질문은 이렇습니다. 빌드 파일에 없는 라이브러리는 어디서 오나? 같은 라이브러리를 두 버전으로 요청하면 무엇이 남나? 왜 Maven과 Gradle은 같은 그래프에서 다른 답을 내나? 2.10.+와 latest.release는 무엇을 고르나? 해소 결과는 어디에 남겨야 나중에 질의할 수 있나? 쓰지도 않는 의존성은 왜 위험한가?

1. 빌드 파일에는 1차 의존성만 적힌다

Spring Boot로 웹 서비스를 하나 만들면 빌드 파일에는 보통 네다섯 줄이 적힙니다. spring-boot-starter-web, spring-boot-starter-actuator, 테스트용 starter 정도예요. 그런데 빌드가 끝난 실행 jar의 BOOT-INF/lib를 열면 jar가 수십 개 들어 있습니다. 내장 톰캣, Jackson, Logback, Micrometer, SnakeYAML 같은 것들이요. 빌드 파일에 적지 않은 것이 대부분입니다.

이건 각 라이브러리가 자기 POM에 다시 의존성을 적어 두었기 때문이에요. starter는 Jackson이 필요하다고 적고, Jackson은 또 다른 모듈이 필요하다고 적습니다. 빌드 도구는 이 사슬을 끝까지 따라가서 실행에 필요한 전체 목록을 만들어요.

📖 용어: 이행 의존성과 이행 종결 (transitive dependency, transitive closure)
내가 직접 적은 의존성(1차 의존성)이 다시 필요로 하는 의존성을 이행 의존성이라고 합니다. 1차 의존성에서 출발해 사슬을 끝까지 따라가 모은 전체 집합이 이행 종결이에요. jar에 실제로 들어가는 건 이 집합입니다.

그렇다면 1차 의존성의 POM을 저장소에서 받아 재귀로 따라가면 이행 종결을 재현할 수 있을까요? 같은 결과가 나오지 않습니다. 사슬을 따라가다 보면 같은 라이브러리를 서로 다른 버전으로 요청하는 경로가 반드시 나오고, 그중 하나를 고르는 규칙이 도구마다 다르기 때문이에요. 게다가 빌드 스크립트가 해소 도중에 버전을 바꿀 수도 있습니다. 이 두 가지가 2장과 3장의 내용입니다.

테스트 의존성은 이 이야기에서 빼도 됩니다. JUnit이나 Mockito는 테스트를 돌리는 동안에만 클래스패스에 있고 배포되는 jar에는 들어가지 않아요. 운영 질의의 대상은 런타임 클래스패스(Gradle의 runtimeClasspath, Maven의 compile과 runtime 스코프)입니다.

2. 같은 그래프를 Maven은 가까운 쪽으로, Gradle은 높은 쪽으로 푼다

가장 작은 예를 보겠습니다. 앱이 라이브러리 A와 B를 쓰고, A는 C 1.0을, B는 D를 거쳐 C 2.0을 요청해요. 클래스패스에는 C가 하나만 올라갈 수 있으니 빌드 도구가 하나를 골라야 합니다.

그림 1. 같은 요청 그래프, 다른 해소 규칙, 다른 jar

Maven은 트리에서 앱에 가장 가까운 정의를 고릅니다. A → B → C → D 2.0과 A → E → D 1.0이 있으면 E를 거치는 경로가 짧으니 D 1.0이 쓰여요(Maven, Introduction to the Dependency Mechanism). 깊이가 같으면 POM에 먼저 선언한 쪽이 이겨요. 위 그림에서는 C 1.0이 남습니다. 버전 숫자는 판단에 쓰이지 않아요.

Gradle은 그래프 전체에서 요청된 버전을 모두 모은 뒤 기본적으로 가장 높은 버전을 고릅니다(Gradle 문서 Graph Resolution). 같은 그림에서 C 2.0이 남아요. 경로의 길이도, 선언 순서도 상관없습니다.

📖 용어: 의존성 중재, 충돌 해소 (dependency mediation, conflict resolution)
그래프 안에서 같은 라이브러리가 여러 버전으로 요청될 때 하나를 고르는 규칙입니다. Maven에서는 mediation, Gradle에서는 conflict resolution이라고 불러요. 규칙이 다르니 같은 그래프라도 결과가 다를 수 있습니다.

어느 쪽이 옳다고 말하기는 어렵습니다. 둘 다 실행 중에 깨질 수 있어요. D가 C 2.0에서 새로 생긴 메서드를 부른다면 Maven이 고른 C 1.0 위에서는 그 호출이 NoSuchMethodError로 끝납니다. 반대로 A가 쓰던 메서드가 C 2.0에서 지워졌다면 Gradle 쪽에서 A가 깨지고요. 컴파일은 둘 다 통과합니다. 컴파일러는 앱의 소스만 검사하고, A와 D는 이미 컴파일된 jar로 들어오기 때문이에요. 충돌 해소는 빌드를 통과시키는 규칙이지 실행을 보장하는 규칙이 아닙니다.

규칙이 다르다는 사실은 운영 질의에도 그대로 걸립니다. Maven과 Gradle을 섞어 쓰는 조직에서 "C 1.0을 쓰는 서비스"를 찾으려고 POM을 재귀로 따라가는 도구를 만들었다면, 그 도구는 둘 중 한 규칙을 흉내 낼 수밖에 없어요. 다른 도구로 빌드한 서비스에서는 답이 틀립니다. 실습-3에서 이 그래프를 로컬 저장소에 직접 만들어 두 도구에 풀게 하고, 실행까지 시켜서 어느 쪽이 어디서 깨지는지 확인해요.

💡 실무에서는
• 해소 결과는 추측하지 말고 도구에게 물어요. Maven은 mvn dependency:tree -Dverbose로 버려진 버전과 이유("omitted for conflict with 1.0")까지 보여 주고, Gradle은 ./gradlew dependencyInsight --dependency C --configuration runtimeClasspath로 어떤 요청이 어떤 규칙으로 이겼는지 보여 줘요.
• 버전이 서로 맞아야 하는 모듈 묶음(Jackson의 core, databind, 각종 datatype 모듈)은 BOM으로 한 번에 맞춰요. Maven은 dependencyManagement에 BOM을 import하고, Gradle은 platform(...)을 씁니다. 다만 Gradle의 platform은 권고라서 다른 경로가 더 높은 버전을 요청하면 충돌 해소로 올라갈 수 있고, 강제하려면 enforcedPlatform(...)을 써요.

3. 빌드 스크립트가 해소 도중에 버전을 바꾼다

충돌 규칙 위에 사람이 적은 규칙이 한 겹 더 얹힙니다. 어떤 라이브러리의 1.2에 치명적인 버그가 있어 1.2.1로 바꿔야 한다고 해 볼게요. 그 라이브러리를 직접 쓰지 않고 다른 라이브러리를 통해 끌려 들어온다면, 빌드 파일에서 버전을 고칠 자리가 없습니다. 그래서 Gradle은 해소 과정에 끼어드는 훅을 줘요.

configurations.configureEach { resolutionStrategy.eachDependency { if (requested.group == "org.example" && requested.name == "some-library") { useVersion("1.2.1") because("1.2 에 치명적 버그") } } }

이 블록은 요청이 1.2든 1.0이든 결과를 1.2.1로 바꿉니다. Maven에서는 dependencyManagement가 같은 역할을 해요. dependencyManagement는 이행 의존성에서 그 라이브러리를 만났을 때 쓸 버전을 직접 정하고, 의존성 중재보다 우선해요(Maven 문서). 특정 경로의 의존성을 아예 빼는 exclusions도 있어요.

Gradle에는 버전을 한 숫자보다 풍부하게 적는 방법도 있습니다.

📖 용어: 리치 버전 (rich version)
Gradle에서 버전 요청에 의도를 덧붙이는 문법입니다. strictly(이 범위 밖은 모두 제외), require(이보다 낮아질 수는 없지만 충돌 해소로 높아질 수는 있음), prefer(더 강한 요청이 없을 때만 적용), reject(이 버전이 골라지면 해소 실패)가 있어요.

여기서 중요한 건 이 규칙들이 어디에 남느냐예요. resolutionStrategy는 소비하는 쪽의 빌드 스크립트 안에서만 돕니다. 이 서비스를 빌드한 결과를 저장소에 게시해도 POM에는 선언한 1차 의존성과 그 버전이 적힐 뿐이에요. 기본값(선언한 버전을 게시)에서는 해소 규칙이 바꾼 버전이 게시물에 반영되지 않아요(Gradle, Maven Publish 문서). 그러니 POM만 읽는 범용 분석 도구는 이 규칙을 볼 방법이 없어요. 아티팩트 저장소의 표준 메타데이터만으로는 실제로 jar에 들어간 이행 종결을 정확히 재현할 수 없다는 뜻입니다.

Gradle은 이 틈을 일부 메우는 설정을 줍니다. 게시할 때 versionMapping { usage("java-runtime") { fromResolutionResult() } }을 쓰면 POM에 선언한 버전 대신 해소된 버전을 적어요. 쓰임새는 동적 버전으로 빌드했지만 소비자에게는 정확한 버전을 보여 주고 싶을 때, 잠금으로 고정한 버전을 게시할 때예요. 다만 이 설정은 POM에 이미 적히는 의존성들의 버전을 바꿔 적는 방식이라 목록이 이행 종결 전체로 늘어나지는 않아요. 전체 목록을 남기는 방법은 5장에서 다룹니다.

4. 동적 버전은 빌드할 때마다 다시 묻는다

버전을 숫자 하나로 고정하지 않고 "이 범위에서 가장 최신"으로 적을 수도 있어요. Gradle은 2.10.+(접두어가 2.10.인 것 중 가장 높은 버전), latest.release, latest.integration을 받고, Maven은 [1.0,2.0) 같은 범위와 RELEASE, LATEST를 받습니다.

📖 용어: 동적 버전 (dynamic version)
구체적인 버전 대신 조건을 적어 두고, 빌드할 때 저장소에 있는 버전 목록을 보고 실제 버전을 정하는 방식입니다. 같은 빌드 파일이라도 저장소에 새 버전이 올라오면 다른 jar가 만들어져요.

먼저 "가장 높은"의 기준부터 보겠습니다. 버전 문자열을 사전순으로 정렬하면 2.10.9가 2.10.10보다 뒤에 와요("9" > "1"). 그래서 2.10.+가 2.10.9를 고른다는 설명을 가끔 보는데, Gradle의 버전 정렬은 그렇게 동작하지 않아요. 버전을 . - _ +로 나눈 뒤 숫자 부분은 숫자로 비교하고, 숫자 부분은 문자 부분보다 높게 칩니다(Gradle, Declaring Versions). 이 규칙대로라면 2.10.10이 더 높아요. 실습-1에서 두 버전을 로컬 저장소에 올려 놓고 실제로 무엇을 고르는지 확인합니다.

더 자주 사람을 놀라게 하는 건 문자 부분이에요. dev는 다른 어떤 문자 부분보다 낮고, rc, snapshot, final, ga, release, sp는 다른 문자보다 높으며 이 순서를 따라요(같은 문서). 그리고 latest.release는 "상태가 release인 가장 높은 버전"이에요. 문제는 상태를 정하는 방식입니다. POM으로 메타데이터를 읽는 모듈의 상태는 SNAPSHOT이면 integration, 나머지는 모두 release예요(Gradle, Component Metadata Rules). 2.11.0.rc1도 SNAPSHOT이 아니니 release입니다.

그림 2. 동적 버전은 정렬 규칙과 상태 규칙 두 개를 거쳐 하나를 고른다

Maven의 RELEASE도 사정이 비슷합니다. 이 값은 저장소의 maven-metadata.xml에 적힌 <release>를 읽는데, 이 칸은 릴리스 후보와 마일스톤을 가려 주지 않아요. 이 글을 쓰는 날(2026-10-12) Maven Central의 메타데이터 두 개를 열어 봤습니다.

$ curl -s https://repo1.maven.org/maven2/org/apache/maven/apache-maven/maven-metadata.xml | grep release <release>4.0.0-rc-7</release> $ curl -s https://repo1.maven.org/maven2/org/springframework/boot/spring-boot/maven-metadata.xml | grep release <release>4.2.0-M2</release>

메타데이터가 말하는 "release"는 SNAPSHOT이 아닌 가장 최근 버전이라는 뜻일 뿐이에요. Maven 3.9 계열의 최신 버전이 따로 있는데도 이 칸에는 4.0의 릴리스 후보가, Spring Boot는 4.2의 두 번째 마일스톤이 적혀 있습니다. 참고로 Maven 3부터는 플러그인 버전에 RELEASE와 LATEST를 쓸 수 없게 됐고(MNG-4205), 의존성에는 아직 쓸 수 있어요.

동적 버전에는 시간 문제도 있습니다. 2편에서 본 Gradle의 24시간 캐시가 동적 버전에도 걸려서, 같은 커밋을 오늘 빌드한 노트북과 내일 빌드한 CI가 다른 버전을 넣을 수 있어요. 2편의 "같은 이름이 다른 바이너리를 가리키는" 문제가 버전 하나가 아니라 의존성 목록 전체에서 생기는 셈이에요.

⚠️ 주의: 릴리스 후보를 거르는 장치는 따로 걸어야 한다
동적 버전을 꼭 써야 한다면 rc와 마일스톤을 거르는 장치를 직접 둬요. 방법은 몇 가지가 있습니다.
• 저장소 선언에 content { excludeVersionByRegex(그룹, 이름, ".*rc.*") }를 걸어 해당 패턴을 아예 후보에서 빼요.
• component metadata rule로 버전 문자열에 rc나 M이 들어간 모듈의 상태를 release가 아닌 값으로 바꿔요. 그러면 latest.release가 그 버전을 건너뜁니다.
• 리치 버전의 reject로 특정 패턴을 거부해요.
셋 다 정규식을 사람이 관리해야 해서, 라이브러리마다 다른 접미사(.rc1, -RC1, -M2, .pr1)를 빠뜨리기 쉬워요. 그래서 다음 장의 잠금과 함께 써야 안전합니다.

5. 잠금은 결과를 고정하고, 카탈로그는 요청을 모은다

동적 버전의 편리함은 살리면서 빌드마다 결과가 달라지는 건 막고 싶다면 의존성 잠금을 씁니다. Gradle은 --write-locks로 빌드할 때 해소된 버전을 각 프로젝트 디렉터리의 gradle.lockfile에 group:artifact:version 한 줄씩 적어요. 이 잠금은 이행 의존성에도 걸리고(내부적으로 strictly 제약을 겁니다), 이후 해소 결과가 잠금과 다르면 빌드가 실패합니다(Gradle, Dependency Locking). 새 버전을 받아들이려면 사람이 잠금을 다시 써야 해요. 잠금 파일은 Git에 커밋되니 "그 커밋이 어떤 이행 종결로 빌드됐나"가 소스와 같이 남습니다.

여기서 자주 헷갈리는 것이 버전 카탈로그예요. gradle/libs.versions.toml에 라이브러리 좌표와 버전을 모아 두고 여러 모듈이 같은 이름으로 가져다 쓰는 장치입니다. 버전을 한 곳에서 관리하게 해 주지만, 카탈로그는 버전을 요청할 뿐 강제하지 않아요(Gradle, Version Catalogs). 그래프의 다른 경로가 더 높은 버전을 요청하면 2장의 규칙대로 그쪽이 이깁니다. 카탈로그에 1.2를 적어 두었다고 jar에 1.2가 들어간다는 보장은 없어요.

무엇이 고정되나 선언(1차) 이행 의존성 빌드마다 같은 결과 버전 카탈로그 모은다 손대지 않음 보장 안 함 Maven BOM / dependencyManagement 맞춘다 맞춘다 동적 버전이 없으면 같음 Gradle platform 권고 권고(더 높은 요청이 이김) Gradle enforcedPlatform 강제 강제 resolutionStrategy (Gradle) 바꾼다 바꾼다 규칙에 따라 의존성 잠금 (Gradle) 고정 고정 같음 (다르면 빌드 실패)

Maven에는 Gradle 같은 잠금 파일이 기본으로 없습니다. 대신 동적 버전을 쓰지 않고, BOM과 dependencyManagement로 이행 의존성의 버전까지 명시하는 쪽이 일반적이에요. Maven Enforcer 플러그인의 dependencyConvergence(그래프 안에서 같은 라이브러리의 버전이 갈리면 실패)나 requireUpperBoundDeps(해소된 버전이 어떤 경로가 요청한 버전보다 낮으면 실패) 규칙을 걸면, 2장처럼 가까운 쪽이 낮은 버전을 고르는 순간을 빌드에서 잡을 수 있습니다.

6. 해소 결과는 jar와 함께 남겨야 질의할 수 있다

지금까지의 이야기를 거꾸로 읽으면 결론이 하나 나옵니다. 운영 중인 서비스에 어떤 버전이 들어 있는지 알려면 빌드 파일을 다시 해석하지 말고, 빌드할 때 해소된 결과를 산출물과 함께 남겨야 해요. 해소는 그 빌드의 그 시점, 그 저장소 상태, 그 빌드 스크립트에서 한 번 일어나고, 나중에 똑같이 재현된다는 보장이 없기 때문입니다.

그림 3. 질의는 해소 앞이 아니라 해소 뒤의 기록에서 출발해야 한다

예전에는 해소된 목록을 POM의 <properties>에 문자열로 적어 넣는 방식이 쓰였어요(Netflix Nebula 플러그인 묶음의 info, maven-manifest가 그런 일을 했습니다). 지금은 이 자리를 SBOM(구성 요소 목록, 1편의 용어 박스 참고)이 CycloneDX, SPDX 같은 표준 형식으로 채웁니다. 빌드 도구 플러그인이 해소된 결과를 보고 만들기 때문에 빌드 파일이 아니라 실제로 들어간 것을 적어요.

Maven은 cyclonedx-maven-plugin, Gradle은 org.cyclonedx.bom 플러그인으로 빌드할 때 CycloneDX SBOM을 만들어요. Spring Boot는 3.3부터 이 플러그인 설정을 미리 잡아 두고, 만든 SBOM을 실행 jar 안에 넣고, Actuator의 sbom 엔드포인트로 노출합니다(Spring 블로그 "SBOM support in Spring Boot 3.3", Actuator 문서). 이렇게 하면 "지금 떠 있는 서비스에 무엇이 들어 있나"를 그 프로세스에 직접 물을 수 있어요. 어디에 떠 있는지를 플랫폼에 묻는 건 1편의 이야기이고, 서비스 열 개에 이 질의를 실제로 던져서 빌드 파일 기준 답과 비교하는 건 실습-2에서 합니다.

💡 실무에서는
• SBOM은 jar 밖의 파일로만 두지 말고 jar 안에도 넣어요. 운영 서버에 떠 있는 바이너리와 SBOM이 서로 다른 빌드에서 나오는 일을 막아 줍니다.
• sbom 엔드포인트를 열 때의 노출 범위와 관리 포트 이야기는 1편의 주의 콜아웃을 따라요.
• Gradle에서 동적 버전을 쓴다면 잠금 파일과 SBOM을 같이 남겨요. 잠금 파일은 "의도한 결과", SBOM은 "실제로 들어간 결과"라서 둘을 비교하면 잠금이 빠진 구성(configuration)을 찾을 수 있어요.

7. 쓰지 않는 의존성은 크기보다 자동 구성이 문제다

해소된 목록을 들여다보면 하나 더 눈에 띄는 게 있습니다. 코드에서 한 번도 쓰지 않는 라이브러리요. 예전에 시도해 보고 지우지 않은 starter, 복사해 온 빌드 파일에 딸려 온 의존성 같은 것들입니다. jar가 조금 커지는 정도라면 사소한 문제예요. Spring Boot 같은 프레임워크에서는 사정이 다릅니다.

📖 용어: 자동 구성 (auto-configuration)
클래스패스에 특정 클래스가 있으면 프레임워크가 알아서 관련 빈(bean)을 만들고 설정하는 기능입니다. Spring Boot의 자동 구성 클래스는 대개 @ConditionalOnClass로 "이 클래스가 있으면 켠다"는 조건을 달고 있어요. 코드에서 쓰지 않아도 jar만 있으면 켜집니다.

대표적인 예가 Spring Data REST예요. Spring MVC가 켜져 있으면 Spring Data REST는 Repository 구현을 REST 엔드포인트로 노출할 수 있어요(Spring Boot How-to). 앱이 JPA Repository를 내부용으로만 쓰고 있었는데 누군가 spring-boot-starter-data-rest를 빌드 파일에 남겨 뒀다면, 그 Repository가 조회, 수정, 삭제까지 되는 HTTP 엔드포인트로 열릴 수 있어요. 2017년에 공개된 CVE-2017-8046은 Spring Data REST 2.6.9, 3.0.1 이전 버전(Spring Boot 1.5.9, 2.0 M6 이전)에 조작된 JSON을 담은 PATCH 요청으로 임의 코드를 실행할 수 있는 취약점이었습니다(NVD CVSS 3.x 9.8). 이 기능을 쓸 생각이 없던 앱이라도 라이브러리가 클래스패스에 있고 엔드포인트가 열려 있었다면 공격 지점이 됐어요. 실습-3에서는 쓰지 않는 data-rest와 JPA starter를 넣었을 때 jar 크기, 기동 시간, 빈 수, 열린 매핑 수가 얼마나 늘어나는지, 내부용 Repository가 실제로 열리는지 확인합니다.

반대 방향의 문제도 있습니다. 코드는 직접 쓰는데 빌드 파일에는 선언하지 않은 의존성이에요. 앱이 C의 클래스를 import하고 있지만 C는 B를 통해 이행 의존성으로만 들어오는 경우입니다. 지금은 잘 빌드되지만 B가 다음 버전에서 C를 빼면 앱의 컴파일이 깨져요. "소스 코드가 직접 쓰는 의존성은 명시적으로 선언하는 것이 좋은 관행"이라는 권고의 근거도 바로 이 예(B가 C에 대한 의존을 바꾸거나 지우면 A의 빌드가 실패할 수 있다)예요(Maven 문서). 앞에서 본 충돌 해소와 겹치면 더 나빠요. 선언하지 않았으니 C의 버전을 앱이 정하지 못하고, 다른 경로의 요청에 따라 바뀝니다.

둘을 찾아 주는 도구는 이렇습니다.

Maven mvn dependency:analyze "Used undeclared dependencies found" 선언 안 하고 쓰는 것 "Unused declared dependencies found" 선언하고 안 쓰는 것 (maven-dependency-plugin 3.11.0, 바이트코드 수준 분석) Gradle com.autonomousapps.dependency-analysis (또는 settings 의 build-health) ./gradlew buildHealth unused, used transitive, 잘못된 구성(api / implementation) 을 보고 nebula.lint 의 unused-dependency, undeclared-dependency 규칙 (규칙은 2026-10 기준 저장소에 남아 있지만 Kotlin DSL 빌드 스크립트는 미지원)

Maven의 분석기는 컴파일된 바이트코드에서 클래스 참조를 찾아 판단해요. 그래서 바이트코드에 흔적이 남지 않는 사용은 놓칩니다. maven-dependency-plugin 3.11.0의 기본 분석기는 바이트코드 수준에서 동작해 한계가 있고, 리플렉션으로만 로드되는 의존성은 usedDependencies 옵션으로 직접 "사용 중"이라고 표시해야 해요(analyze 목표 문서). Gradle의 dependency-analysis 플러그인은 바이트코드 참조에 더해 상수 값과 소스의 import까지 함께 봅니다(3.19.2 소스의 ComputeUsagesTask). 그래도 Class.forName으로 이름만 넘겨 읽는 JDBC 드라이버는 두 쪽 모두 "안 쓴다"고 할 수 있어요. 자동 구성으로만 쓰이는 starter도 마찬가지입니다.

상수만 쓰는 라이브러리는 쓰는 방식에 따라 갈려요. javac는 컴파일 타임 상수의 값을 쓰는 쪽에 복사하면서도, 표현식에서 쓴 상수의 소유 클래스는 의존성 추적용으로 상수 풀에 남깁니다(JDK 8의 JDK-7153958, 필드 초기화식은 JDK 9의 JDK-8073372). 그런데 상수를 switch의 case 라벨이나 어노테이션 값에만 쓰면 이 참조가 남지 않아요. 이때 바이트코드만 보는 분석기는 "안 쓴다"고 할 수 있습니다(상수는 maven-dependency-analyzer 문서의 한계 목록에도 있어요). 실행에는 정말 필요 없지만 컴파일에는 필요한 의존성이라, 지우면 빌드가 깨져요.

더 헷갈리는 경우는 버전을 고정하려고 일부러 적어 둔 선언이에요. 코드가 그 라이브러리를 직접 부르지 않으니 분석기에는 "안 쓰는 선언"으로 보이는데, Maven에서는 그 한 줄이 2장의 가까운 쪽 규칙을 이겨서 버전을 정하고 있을 수 있습니다. 지우면 다른 버전이 jar에 들어가요. 그러니 이 보고는 지울 후보 목록이지 지워도 된다는 판정이 아니에요. 실습-3에서 두 도구가 같은 프로젝트를 보고 몇 개를 보고하는지, 그중 몇 개가 틀렸는지 셉니다.

⚠️ 주의: "안 쓴다"는 보고를 그대로 지우면 기동이 깨질 수 있다
• starter는 코드를 거의 담지 않은 묶음이라 분석 도구에는 대개 "안 쓴다"로 보여요. 지우기 전에 그 starter가 켜던 자동 구성이 정말 필요 없는지 /actuator/conditions나 기동 로그의 조건 평가 보고서로 확인해요.
• 반대로 "쓰는데 선언 안 했다"는 보고는 대체로 고치기 쉬워요. 선언을 하나 추가할 뿐이에요. 다만 Maven에서는 그 선언이 가장 가까운 정의가 되니, 지금 해소된 버전과 같은 버전을 적거나 BOM에 맡겨요.
✍️ 오늘의 요약
빌드 파일은 1차 의존성의 요청만 적고, jar에 들어가는 이행 종결은 충돌 규칙, 해소 규칙, 동적 버전, 캐시를 거쳐 빌드할 때 한 번 정해져요.

같은 그래프를 Maven은 가까운 쪽으로, Gradle은 높은 쪽으로 풀고, latest.release와 RELEASE는 릴리스 후보를 고를 수 있어요. 잠금은 결과를 고정하고, 카탈로그는 요청을 모을 뿐이에요. 그래서 운영 질의는 빌드 파일을 다시 해석하는 데서가 아니라 빌드할 때 jar와 함께 남긴 SBOM에서 출발해야 해요. 그리고 쓰지 않는 의존성은 크기가 아니라 자동 구성이 여는 문으로 따져야 합니다. 버전은 적는 순간이 아니라 해소되는 순간에 정해집니다.
