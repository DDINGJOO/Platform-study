1. 실습 환경: 모노레포 하나, 서비스 열 개, 커밋 둘

서비스 열 개는 한 Gradle 빌드 안의 하위 프로젝트예요. 코드는 모두 같고 빌드 파일만 다릅니다. 모든 서비스에 액추에이터, CycloneDX 플러그인(SBOM), git.properties 플러그인을 붙였고, 의존성 버전은 스프링 부트 BOM을 Gradle의 platform()으로 받아요. 이 BOM이 정한 logback은 1.5.38입니다.

📖 용어: BOM (Bill of Materials POM)
여러 라이브러리의 버전을 한곳에 모아 둔 POM입니다. 스프링 부트의 spring-boot-dependencies가 대표적이에요. Gradle에서는 implementation platform(...)으로 받으면 버전 없이 적은 의존성에 그 버전이 들어가고, 다른 경로로 들어온 같은 라이브러리와는 높은 쪽이 이깁니다.
Spring Boot 4.1.1 (Java 21, 이미지 eclipse-temurin:21-jre) CycloneDX Gradle plugin 3.0.0 (스프링 부트 문서의 예시 버전) gradle-git-properties 4.0.1 Gradle 9.8.1 / Maven 3.10.0 (POM 해소용) logback (BOM 기본값) 1.5.38 실행 환경 Docker Desktop 29.5.3, Apple M5 Pro
⚠️ 주의: 문서 예시 버전 그대로는 빌드가 깨졌다
스프링 부트 문서의 git 정보 예시는 com.gorylenko.gradle-git-properties 2.4.1을 적어요. Gradle 9.8.1에서는 generateGitProperties 태스크가 No signature of method: java.io.FilterOutputStream.write()로 실패했습니다. 플러그인 포털의 최신판 4.0.1로 올리니 통과했어요.

작업용 Git 저장소는 실행할 때 저장소 밖(/tmp/co-02-work)에 새로 만들어요. 커밋을 두 개 만들고, s04만 첫 커밋으로 빌드한 이미지를 띄웁니다. 나머지 아홉은 두 번째 커밋 이미지예요. 컨테이너는 lab.co02=1 레이블을 달고 docker run으로 하나씩 띄웠어요. 이 레이블이 1편에서 말한 "플랫폼에 묻기"의 입구입니다.

git clone https://github.com/DDINGJOO/Platform-study.git cd Platform-study/labs/devops/co-02-sbom-inventory python3 scripts/lab.py prepare # 작업 저장소, 커밋 둘, jar·POM·이미지 빌드 (첫 실행은 의존성 내려받기로 몇 분) python3 scripts/lab.py deploy # 서비스 열 개를 30101~30110 포트로 python3 scripts/lab.py query # 질의 세 가지와 정답 비교 → results/query.txt python3 scripts/lab.py trace s04 # 운영본에서 소스 한 줄까지 → results/trace.txt python3 scripts/lab.py down

코드는 GitHub 저장소의 labs/devops/co-02-sbom-inventory에 있어요.

2. 옛 logback을 숨긴 다섯 가지 방법

다섯(s02, s03, s04, s06, s07)에는 옛 logback을 숨기는 장치를, s05, s08, s09에는 판정을 헷갈리게 하는 변형을 넣었어요.

서비스 빌드 파일에 한 일 의도 s01 webmvc 만 기본형 s02 resolutionStrategy.force 로 logback 1.5.12 고정 해소 규칙으로 내림 s03 'ch.qos.logback:logback-core:1.5.12' 직접 선언 옛 선언이 남아 있음 s04 커밋1 에 s02 와 같은 force, 커밋2 에서 삭제. 운영에는 커밋1 Git 과 운영의 차이 s05 Log4j2 로 교체, spring-boot-starter-logging 제외 logback 없음 s06 빌드는 s01 과 같음. 배포 이미지에서 옛 logback 을 loader.path 로 빌드 뒤에 바뀜 s07 버전 카탈로그에 logback = { strictly = "1.5.12" } 버전이 빌드 파일 밖에 s08 'ch.qos.logback:logback-core:1.5.+' 동적 버전 s09 'ch.qos.logback:logback-classic' (버전 없음) BOM 이 정함 s10 webflux 기본형
📖 용어: loader.path
스프링 부트 실행 jar를 PropertiesLauncher로 띄울 때, jar 바깥의 디렉터리나 jar를 클래스패스에 더하는 설정입니다. 운영 쪽에서 앱을 다시 빌드하지 않고 jar를 얹을 때 쓰여요. s06은 이걸로 옛 logback 두 개를 얹었습니다.

3. 정답은 실행 중인 JVM에게 묻는다

비교하려면 정답이 있어야 해요. SBOM도 빌드 파일도 아닌 기준이 필요해서, 서비스마다 엔드포인트를 하나 넣었습니다. JVM이 logback 클래스를 실제로 어느 jar에서 읽었는지 돌려줘요.

@GetMapping("/lab/logback") // Class.forName(...).getProtectionDomain().getCodeSource().getLocation() s02: core=jar:nested:/app/app.jar/!BOOT-INF/lib/logback-core-1.5.12.jar!/ s06: core=file:/app/extra/logback-core-1.5.12.jar s05: core=none

s02는 실행 jar 안의 1.5.12를, s06은 jar 바깥에 얹은 1.5.12를 읽고 있었어요. 실행 jar 안에는 BOM의 1.5.38도 들어 있지만, loader.path에 적은 쪽이 먼저 읽혔습니다. 이 결과로 정답이 정해졌어요. 취약한 서비스는 s02, s04, s06, s07 넷입니다.

그림 1. 왼쪽 둘은 저장소만 보고, 오른쪽 둘은 플랫폼이 알려 준 프로세스에 묻는다

비교한 질의는 셋이에요. A는 Git HEAD의 각 서비스 build.gradle에서 ch.qos.logback:logback-core:버전 꼴을 찾습니다. 코드 검색과 같은 시선이에요. B는 운영에 떠 있는 커밋으로 만든 POM(게시했다면 함께 올라갔을 POM을 생성만 했어요)을 Maven으로 해소해 logback-core 버전을 봅니다. 저장소의 표준 메타데이터만 읽는 분석 도구의 시선이에요. C는 플랫폼에서 떠 있는 컨테이너 목록을 받고, 각 서비스의 /actuator/sbom/application에서 logback-core를 찾습니다.

📖 용어: CycloneDX
SBOM을 적는 표준 형식 중 하나입니다. 구성 요소마다 이름, 버전, 패키지 URL(purl), 해시를 JSON으로 적어요. 스프링 부트는 Gradle에 CycloneDX 플러그인이 붙어 있으면 그 결과를 실행 jar의 META-INF/sbom/application.cdx.json에 넣고, /actuator/sbom으로 내보냅니다. 이번 SBOM은 규격 1.6, 서비스당 구성 요소 56~79개였어요.

5. 각 방법이 틀린 자리

A. Git HEAD의 빌드 파일

s03 오탐: 빌드 파일에 1.5.12가 적혀 있지만 Gradle은 충돌하면 높은 버전을 고르니 BOM의 1.5.38이 들어갔어요. s04 미탐: HEAD에서는 핀을 지웠지만 운영에는 핀이 있던 커밋이 떠 있었어요. s07 미탐: 버전이 libs.versions.toml에 있어서 빌드 파일에는 libs.logback.core뿐이었어요. s06 미탐: 빌드 파일은 아무 잘못이 없었고, jar는 배포 이미지에서 얹혔어요. s08 판정 불가: 1.5.+는 빌드한 날 저장소에 무엇이 있었는지 알아야 버전이 정해집니다. 맞힌 s02는 resolutionStrategy.force 줄에 좌표가 그대로 적혀 있었기 때문이에요.

B. 배포본 POM을 Maven으로 해소

B는 운영 커밋 기준이라 s04의 커밋 차이 문제는 없어야 할 것 같지만, s04도 놓쳤어요. 핀이 resolutionStrategy에 있었고, 그 규칙은 POM에 실리지 않기 때문입니다. s02도 같은 이유로 놓쳤어요. 3편이 말한 "POM만으로는 실제 해소 결과를 알 수 없다"가 그대로 나온 거예요.

s03 오탐은 반대 방향입니다. Gradle은 BOM의 1.5.38을 골랐지만, 그 POM을 Maven이 풀면 직접 선언한 1.5.12가 가장 가까운 정의라서 이겼어요. Gradle은 빌드 스크립트를, Maven은 그 스크립트가 만든 POM을 풀어서 답이 갈렸어요. 이 차이는 실습-3의 주제예요. s07은 Gradle의 strictly 1.5.12가 POM에 그냥 1.5.12로 적혔고, Maven에서도 직접 선언이 이겨서 우연히 맞았습니다.

Gradle 이 만든 POM 의 logback-core 버전 표기 s03: <version>1.5.12</version> s07: <version>1.5.12</version> ← 빌드 파일에서는 strictly 였다 s08: <version>1.5.+</version> $ mvn -f s08.pom dependency:list [ERROR] Failed to execute goal on project s08: Could not resolve dependencies for project lab.inventory:s08:pom:1.0.0 [ERROR] dependency: ch.qos.logback:logback-core:jar:1.5.+ (runtime)

s08에서는 예상하지 못한 일이 하나 더 있었어요. Gradle은 동적 버전 1.5.+를 POM에 그대로 적었고, Maven은 이 표기를 읽지 못해 해소 자체가 실패했습니다. 표준 메타데이터를 읽는 도구가 Gradle로 빌드한 서비스를 만나면 이렇게 답을 못 낼 수 있어요. 처음 스크립트는 이 실패를 "logback 없음"으로 셌어요.

C. 실행 중 SBOM

C가 놓친 하나는 s06이에요. SBOM은 Gradle이 빌드할 때 해소한 결과라서, 이미지를 만들 때 loader.path로 얹은 jar를 모릅니다. s06의 SBOM은 1.5.38을 말했고 JVM은 얹힌 1.5.12를 쓰고 있었어요. 이미지 파일을 훑는 스캐너라면 볼 수 있겠지만 이번에는 재지 않았어요.

⚠️ 주의: 옛 logback으로 내린 서비스는 로그 형식이 깨져 있었다
• 정답 기준 취약한 넷(s02, s04, s06, s07)은 모두 기동할 때 There is no conversion class registered for composite conversion word [clr] 같은 logback 설정 오류를 남겼고, 기동이 끝날 때까지 PARSER_ERROR가 든 줄이 서비스마다 12줄씩 찍혔어요
• 이후 로그 줄은 %PARSER_ERROR[clr] … Started App in 0.838 seconds처럼 형식이 깨진 채로 찍혔어요. 앱은 정상으로 떴고 헬스 체크도 UP이었습니다
• 스프링 부트 4.1.1의 기본 로그 설정이 쓰는 변환기를 1.5.12에서 등록하지 못한 것으로 보여요. 버전을 내리는 핀은 취약점만이 아니라 이런 조용한 고장도 같이 데려옵니다

6. 운영본에서 소스 한 줄까지, 네 단계

s04를 찾은 다음에는 "왜 이 버전인가"를 소스에서 확인해야 해요. trace가 밟은 단계는 이랬습니다.

1) 플랫폼: docker ps 에서 s04 -> 이미지 co02/s04:9d208f4, 포트 30104 이미지 라벨 org.opencontainers.image.revision = 9d208f491193 2) 앱: GET /actuator/info -> git.commit.id = 9d208f4, branch = main 3) 저장소: 9d208f4 -> 9d208f491193, HEAD 는 e376913b7390 (같은가: False) 4) 소스: git show 9d208f4:s04/build.gradle 에서 logback 줄 resolutionStrategy.force 'ch.qos.logback:logback-core:1.5.12', 'ch.qos.logback:logback-classic:1.5.12' HEAD 의 같은 파일에서 logback 줄 (없음) 그 사이 커밋: e376913 c2: s04 drops the logback pin

플랫폼, 앱(또는 이미지 레이블), 저장소, 소스의 네 단계였어요. 이미지 레이블과 /actuator/info가 같은 커밋을 말해서 둘 중 하나만 있어도 됐습니다. 마지막 줄이 이 실습의 요점을 다시 보여 줘요. 고친 커밋은 이미 main에 있고, 운영에는 나가지 않았어요. 이 경우 할 일은 코드 수정이 아니라 재배포입니다.

📖 용어: git.properties
빌드할 때 Git 정보(브랜치, 커밋 ID, 커밋 시각 등)를 적어 jar 안에 넣는 파일입니다. 스프링 부트는 이 파일이 클래스패스에 있으면 /actuator/info의 git 항목으로 보여 줘요. 기본으로는 브랜치, 짧은 커밋 ID, 커밋 시각만 나갑니다.

C는 이미 해소된 결과를 읽기만 하니 열 개에 0.1초 안쪽이었어요. 서비스가 수백 개로 늘면 이 차이가 질의 방식을 가릅니다. 다만 C는 서비스가 떠 있어야 하고 관리 엔드포인트에 닿아야 해요. 1편에서 말한 대로 같은 다이제스트는 한 번만 물으면 되니, 실제로는 서비스 수가 아니라 다이제스트 수만큼 호출합니다.

💡 실무에서는
• 취약점 질의의 출발점은 저장소 검색이 아니라 플랫폼의 실행 목록이에요. 이번 실습에서 그 차이가 미탐 셋과 하나로 나왔어요
• SBOM은 빌드 때 기록이에요. 배포 단계에서 jar를 얹거나 에이전트를 붙이는 서비스가 있다면, 이미지 단위 스캔이나 런타임 확인을 한 번 더 두세요
• POM 기반 분석 도구를 Gradle 서비스에 쓴다면 해소 실패를 "없음"으로 세지 않는지 확인하세요. 동적 버전이 POM에 그대로 실립니다
✍️ 오늘의 요약
서비스 열 개 중 취약한 넷을 찾는 질의에서 실행 중인 SBOM은 셋을 오탐 없이 찾았고, Git HEAD의 빌드 파일과 배포본 POM은 각각 하나만 맞혔어요. 빌드 파일은 운영과 다른 커밋, 버전 카탈로그, 충돌 해소, 배포 때 얹은 jar 때문에 틀렸고, POM은 해소 규칙이 실리지 않고 Maven이 Gradle의 동적 버전을 읽지 못해서 틀렸어요.

SBOM도 하나를 놓쳤어요. 배포할 때 얹은 jar는 빌드 때 기록에 없기 때문입니다. 정답은 결국 떠 있는 프로세스가 갖고 있고, 질의는 그 프로세스를 아는 플랫폼에서 시작해야 해요.
