이번 실습은 로컬에 Maven 저장소와 도커 레지스트리를 하나씩 띄우고, 같은 이름에 다른 내용을 일부러 다시 올리고, 그때마다 빌드 컨테이너들이 받은 jar의 SHA-256과 이미지 다이제스트를 적었어요. 숫자와 출력은 전부 이번에 돌린 결과예요.

1. 실습 환경: 저장소 둘, 캐시가 다른 빌드 컨테이너 다섯

Maven 저장소는 Reposilite로, 도커 레지스트리는 CNCF Distribution(registry 이미지)으로 띄웠어요. 빌드는 Gradle과 Maven 공식 이미지 컨테이너에서 하고, 컨테이너마다 캐시를 다른 볼륨에 둬서 볼륨 하나가 기계 한 대 역할을 해요.

그림 1. 저장소는 하나인데, 그걸 보는 기계마다 기억하는 시점이 다르다
Reposilite 3.6.3, registry 3.1.2, Gradle 9.8.1, Maven 3.10.0 (JDK 21 공식 이미지) Docker Engine 29.5.3, buildx 0.34.1 (Docker Desktop, Apple M5 Pro)

실습 코드는 GitHub 저장소의 labs/devops/co-01-coordinates에 있어요. Docker와 Python 3만 있으면 됩니다. 실험마다 결과가 results/<실험>.txt로 남아요.

git clone https://github.com/DDINGJOO/Platform-study.git cd Platform-study/labs/devops/co-01-coordinates python3 scripts/lab.py up python3 scripts/lab.py snapshot # 2절 python3 scripts/lab.py release # 3절 python3 scripts/lab.py tag # 4절 python3 scripts/lab.py dynamic # 5, 6절 python3 scripts/lab.py rebuild # 7절 python3 scripts/lab.py down docker rm -f co01-node-a co01-node-b; docker images 'localhost:30500/lab/*' -q | xargs docker rmi -f

2. SNAPSHOT을 두 번 올리면 여섯 중 둘이 옛 jar에 남는다

lab:lib:1.0.0-SNAPSHOT을 내용만 바꿔 두 번 게시했어요(build-1, build-2). 첫 게시 직후 gradle-a와 maven-a가 한 번 받아 두고, 두 번째 게시 뒤 여섯 경우로 다시 받았습니다.

두 번째 게시 뒤 받은 소비자 받은 파일 버전 SHA-256(앞 16자) gradle-a (첫 게시 때 캐시, 옵션 없음) 20261012.064614-1 7a5a47c1f272c614 ← 옛것 gradle-b (캐시 없음) 20261012.064627-2 b30c4627ae3955c0 gradle-a --refresh-dependencies 20261012.064627-2 b30c4627ae3955c0 maven-a (로컬 저장소 있음, 옵션 없음) 1.0.0-SNAPSHOT 7a5a47c1f272c614 ← 옛것 maven-b (로컬 저장소 없음) 1.0.0-SNAPSHOT b30c4627ae3955c0 maven-a -U 1.0.0-SNAPSHOT b30c4627ae3955c0

여섯 중 둘이 옛 jar를 그대로 썼고, 어느 쪽도 경고 한 줄 없이 성공했어요. Gradle은 변하는 모듈을 24시간, Maven은 updatePolicy 기본값대로 하루 동안 저장소에 다시 묻지 않으니 문서대로의 동작입니다.

📖 용어: Reposilite
가벼운 Maven 저장소 서버입니다. 저장소마다 재게시 허용(redeployment)과 옛 스냅숏 보존(preserveSnapshots) 설정을 둬요. 이 실습은 기본값을 쓰고, 2절의 lib-p 실험에서만 preserveSnapshots를 켰어요.

예상과 달랐던 것: 옛 스냅숏 파일이 사라졌다

두 번째 게시 뒤 저장소의 파일 목록을 보니 -1 파일이 없었어요. 남은 건 lib-1.0.0-20261012.064627-2.jar와 그 체크섬, 그리고 maven-metadata.xml뿐이었습니다. 스냅숏 저장소의 preserveSnapshots가 기본값 false라서, 새 스냅숏이 들어오면 옛 타임스탬프 파일을 지운 거예요. 옛 jar를 쥔 gradle-a와 maven-a는 저장소에 더는 없는 바이너리로 빌드하고 있는 셈입니다.

gradle-ci, 첫 게시의 시각이 붙은 버전 1.0.0-20261012.064614-1 를 직접 적으면: BUILD FAILED GET lib-1.0.0-20261012.064614-1.jar -> 404 preserveSnapshots=true 로 바꾸고 lib-p 로 같은 일을 반복: 저장소의 jar: lib-p-1.0.0-20261012.064654-1.jar, lib-p-1.0.0-20261012.064657-2.jar lab:lib-p:1.0.0-20261012.064654-1 → sha256=7a5a47c1f272c614 (첫 게시) lab:lib-p:1.0.0-SNAPSHOT → sha256=b30c4627ae3955c0 (두 번째 게시)

보존을 켜야 2편에서 말한 "시각이 붙은 버전으로 고정하기"가 통했어요.

3. 릴리스는 409로 막혔지만, 목록 파일은 막히지 않았다

lab:lib:1.0.0을 올린 뒤, 같은 좌표에 내용만 바꿔 다시 올렸어요.

> Could not PUT 'http://reposilite:8080/releases/lab/lib/1.0.0/lib-1.0.0.jar'. > Received status code 409 from server: Conflict PUT releases/lab/lib/1.0.0/lib-1.0.0.jar -> 409 {"status":409,"message":"Redeployment is not allowed"} GET releases/lab/lib/1.0.0/lib-1.0.0.jar -> 200, sha256=a2cb82ca89fff625 (처음 것과 같나: True)

Gradle 게시도, 직접 보낸 PUT도 409로 거절됐고 저장소의 jar는 처음 그대로였어요. 그런데 같은 저장소에서 아티팩트 단위 목록 파일에 <metadata/> 한 줄을 PUT 하자 200이 돌아왔고, 다시 읽으니 그 한 줄만 남아 있었어요.

PUT releases/lab/lib/maven-metadata.xml -> 200 GET /releases/lab/lib/maven-metadata.xml -> 200 <metadata/>

이 파일은 "이 아티팩트에 어떤 버전들이 있고 최신 릴리스가 무엇인가"를 적은 목록이에요. 게시할 때마다 새로 써야 하는 파일이라, Reposilite는 이 파일을 재게시 금지 대상에서 뺍니다(소스 Repository.kt). 5절의 동적 버전이 읽는 게 바로 이 목록이에요.

⚠️ 주의: 목록 파일이 깨지면 누가 영향을 받나
별도 실행(scripts/lockcheck.sh)에서 lab:dyn의 목록 파일을 <metadata/>로 덮어쓰고 다시 빌드했어요. 잠금 없는 2.10.+ 빌드는 no versions of lab:dyn are available로 실패했고, 같은 빌드 파일에 잠금(2.10.10)을 켠 빌드와 고정 버전 빌드는 2.10.10을 그대로 받았어요.

4. 같은 태그로 다시 푸시하면 먼저 뜬 컨테이너의 IMAGE 칸에는 ID가 찍힌다

busybox 위에 문자열 하나를 적는 이미지를 localhost:30500/lab/app:1.0으로 푸시하고 컨테이너 co01-node-a를 띄웠어요. 그다음 내용을 v2로 바꿔 같은 태그로 다시 푸시하고 co01-node-b를 띄웠습니다.

첫 푸시 뒤 레지스트리의 1.0 -> sha256:7ffe34901be2fac5… 두 번째 푸시 뒤 레지스트리의 1.0 -> sha256:ed86a2fc023ea6b2… co01-node-a: 요청한 이미지 localhost:30500/lab/app:1.0, 실제 sha256:7ffe3490…, 내용 v1 co01-node-b: 요청한 이미지 localhost:30500/lab/app:1.0, 실제 sha256:ed86a2fc…, 내용 v2 $ docker ps --format '{{.Names}} IMAGE={{.Image}}' co01-node-b IMAGE=localhost:30500/lab/app:1.0 co01-node-a IMAGE=7ffe34901be2

두 컨테이너의 설정에는 똑같이 lab/app:1.0이 적혀 있지만 실제 이미지가 달라요. 그리고 docker ps는 먼저 뜬 컨테이너의 IMAGE 칸에 태그 대신 ID 앞부분만 보여 줬습니다. 1편에서 질의를 다이제스트로 하라고 한 이유예요.

마지막으로 로컬 태그를 지우고 첫 번째 다이제스트로 받아 봤어요. docker pull localhost:30500/lab/app@sha256:7ffe3490…가 그대로 성공했습니다. 레지스트리가 옛 매니페스트를 지우지 않았으니 다이제스트로 적어 둔 롤백 대상은 살아 있어요.

5. 동적 버전은 무엇을 골랐나

lab:dyn을 2.9.0, 2.10.9, 2.10.10, 2.11.0-rc1 순서로 게시하고, 나중에 rc 다음의 핫픽스인 2.10.11을 하나 더 올렸어요. 해석 규칙은 3편에서 다뤘으니 결과만 적을게요. 24시간 캐시를 피하려고 Gradle은 모두 --refresh-dependencies, Maven은 -U로 받았어요.

표기 도구 2.10.11 게시 전 게시 후 2.10.+ Gradle 2.10.10 2.10.11 latest.release Gradle 2.11.0-rc1 2.11.0-rc1 latest.release (rc 제외) Gradle 2.10.10 2.10.11 [2.10,2.11) Gradle 2.10.10 2.10.11 [2.10,2.11) Maven 2.11.0-rc1 2.11.0-rc1 RELEASE Maven 2.11.0-rc1 2.10.11 LATEST Maven 2.11.0-rc1 2.10.11

"게시 후" 열의 Gradle 중 latest.release 말고 세 줄은 스크립트가 끝난 직후 같은 저장소 상태에서 손으로 잰 값이에요(results/extra.txt).

첫째, 2.10.+는 2.10.10을 골랐습니다. 글자 순 정렬이 아니라 숫자 비교였어요. 둘째, latest.release는 rc를 골랐습니다. SNAPSHOT이 아닌 버전은 모두 상태가 release이기 때문이에요. 저장소 선언에 excludeVersionByRegex('lab', '.*', '.*-rc.*')를 걸자 2.10.10으로 내려왔어요.

셋째, 같은 범위 [2.10,2.11)를 두 도구가 다르게 풀었습니다. Maven은 2.11.0-rc1을, Gradle은 2.10.11을 골랐어요. Maven에서는 2.11.0-rc1 < 2.11이라 상한 안쪽에 들어요([1.0,2.0)이 2.0-rc1을 포함하는 것은 "대부분이 예상하는 것과 반대"인 동작이에요. Maven POM 문서). Gradle 쪽은 정렬로 봐도 숫자 부분이 더 있는 2.11.0-rc1이 2.11보다 높고, "배타적 상한은 접두어 제외처럼 동작한다"는 규칙도 있어 2.11로 시작하는 버전을 모두 뺍니다(Gradle 문서, Declaring Versions). 넷째, Maven RELEASE는 가장 높은 버전이 아니라 마지막으로 게시한 버전을 따라갔어요. 2.10.11을 올리자 Gradle이 목록 파일의 <release>와 <latest>가 둘 다 2.10.11로 바뀌었고, Maven은 rc에서 2.10.11로 "내려갔어요". 같은 시점에 Gradle latest.release는 여전히 2.11.0-rc1이었습니다.

📖 용어: 동적 버전 (dynamic version)
2.10.+, latest.release, [2.10,2.11)처럼 조건으로 적고, 빌드할 때 저장소의 버전 목록(maven-metadata.xml)을 읽어 실제 버전을 정하는 표기입니다.

6. 잠금 파일은 변화를 0으로 만들었다

lab:dyn:2.10.+와 lab:util:latest.release 두 개를 쓰는 소비자를 만들고, 2.10.11과 util 1.1.0을 올리기 전에 잠금 파일을 썼어요.

$ gradle dependencies --configuration runtimeClasspath -Plock --write-locks # gradle.lockfile lab:dyn:2.10.10=runtimeClasspath lab:util:1.0.0=runtimeClasspath
📖 용어: 의존성 잠금 (dependency locking)
동적 버전을 한 번 해소한 결과를 gradle.lockfile에 적고, 이후 빌드는 그 버전으로만 해소하게 하는 Gradle 기능입니다.

새 버전 두 개를 올린 뒤 같은 소스를 --refresh-dependencies로 다시 빌드했어요.

새 버전 게시 전 새 버전 게시 후 잠금 없음 dyn 2.10.10, util 1.0.0 dyn 2.10.11, util 1.1.0 → 2/2 바뀜 잠금 있음 dyn 2.10.10, util 1.0.0 dyn 2.10.10, util 1.0.0 → 0/2 바뀜

목표대로 0이었어요. 잠금 상태에서 빌드 파일만 2.11.+로 고치면 어떻게 되는지도 봤습니다. 처음 짠 확인 태스크는 해소 실패를 삼켜 dyn이 빠진 채 성공했고, 파일 목록을 실제로 요구하게 고치자 빌드가 멈췄습니다.

> Could not resolve lab:dyn:2.11.+. Dependency path: ... 'lab:dyn:2.11.+' ... rejected version 2.11.0-rc1 Constraint path: ... 'lab:dyn:{strictly 2.10.10}' ... Dependency version enforced by Dependency Locking

잠금은 해소 결과에 strictly 제약을 거는 방식으로 동작해요. 빌드 파일이 잠금과 어긋나면 조용히 넘어가지 않고 실패하니, 잠금 파일을 갱신하는 커밋이 따로 생깁니다.

7. 같은 소스를 두 번 빌드하면 같은 결과물인가

2편의 "다시 빌드하지 말고 승격하라"를 확인하려고, 같은 소스를 3초 간격으로 두 번씩 빌드했어요.

대상 1회차 2회차 같은가 Gradle 9.8.1 jar (기본) fb1d048304b251da fb1d048304b251da 예 Gradle, preserveFileTimestamps=true bf9b468885f567f3 5201cbe1a29ae338 아니오 Maven 3.10.0 jar (기본) 1b9e8ed9579bc96e 1b9e8ed9579bc96e 예 Maven, outputTimestamp=x 13bb824299692d18 1a2b3ea0c6befb26 아니오 이미지, --no-cache sha256:c171d441… sha256:2ef3e180… 아니오 이미지, SOURCE_DATE_EPOCH, rewrite-timestamp sha256:745d46c3… sha256:defb9b43… 아니오 이미지, 위 + --provenance=false sha256:20060dd0… sha256:20060dd0… 예

jar는 두 도구 모두 기본 설정에서 같았고, 예전 동작으로 되돌리면 3초 차이로도 달라졌어요.

예상과 다른 건 이미지였어요. 시각을 고정해도 다이제스트가 달라서 인덱스를 열어 봤습니다.

repro:1 arm64 sha256:2bfce8c59eef… unknown(출처 증명) sha256:46e829e7edf8… repro:2 arm64 sha256:2bfce8c59eef… unknown(출처 증명) sha256:33e2f18ace1e… 증명 안의 invocationId: kpoogt5a… / ma433h3f…, startedOn: 06:49:31.21Z / 06:49:35.30Z 같은 증명의 vcs.revision: 30fd178c0713… (빌드한 Git 커밋)
📖 용어: 출처 증명 (provenance attestation)
이미지를 어떤 입력과 절차로 빌드했는지 적은 문서입니다. buildx는 SLSA 형식의 증명을 인덱스에 별도 매니페스트(위의 unknown)로 붙여요.

이미지 매니페스트는 두 빌드가 같았고, buildx가 레지스트리로 내보낼 때 기본으로 붙이는 출처 증명만 달랐어요. 증명에 빌드마다 새 호출 ID와 시작 시각이 들어가니, 증명까지 묶은 인덱스의 다이제스트는 빌드할 때마다 바뀝니다. --provenance=false로 증명을 빼면 같아졌어요.

💡 실무에서는
• 스냅숏 저장소의 보존 설정을 확인하세요. 옛 스냅숏을 지우면 SNAPSHOT으로 만든 결과물은 재현할 수 없어요
• 재게시 금지가 바이너리만 막는지, 목록 파일까지 보호하는지 따로 보세요

SNAPSHOT을 두 번 올리자 여섯 소비자 중 둘이 경고 없이 옛 jar에 남았고, 기본 설정의 저장소는 그 옛 jar를 지워 버렸어요. 같은 태그로 다시 푸시하자 같은 이름의 컨테이너 둘이 다른 이미지로 떠 있었고, 동적 버전은 rc를 고르거나 마지막에 올린 버전을 따라갔어요.

릴리스 재게시는 409로 막혔고, 잠금은 변화를 2에서 0으로 줄였고, jar는 비트 단위로 같게 다시 만들어졌어요. 이름이 같아도 내용이 같다는 보장은 저장소 설정, 잠금, 다이제스트가 따로 지켜 줍니다.
