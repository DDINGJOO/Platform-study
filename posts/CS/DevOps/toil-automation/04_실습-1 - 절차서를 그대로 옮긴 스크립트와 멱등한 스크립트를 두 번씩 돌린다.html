1편. 수고의 적은 손이 아니라 선형 증가다
2편. 자동화도 유지비를 내야 본전을 뽑는다
3편. 절차서를 코드로 옮기면 두 번 돌려도 같아야 한다
실습-1. 절차서를 그대로 옮긴 스크립트와 멱등한 스크립트를 두 번씩 돌린다 ← 지금 이 글
실습-2. 경고를 받아 스스로 고치는 스크립트에 상한을 건다

3편은 서두에 사고 두 개를 놓았어요. VPN이 끊긴 뒤 다시 돌린 스크립트가 "이미 있음"으로 끝나 경로가 영영 안 생긴 사고, 두 사람이 같은 티켓을 동시에 돌려 DB 행과 경로가 둘씩 생긴 사고입니다. 그리고 절차서를 그대로 옮긴 스크립트를 수렴형으로 고치면 두 번 돌려도, 끊긴 뒤 다시 돌려도, 동시에 돌려도 결과가 같아진다고 했어요.

이번 실습은 그 주장을 셉니다. 신규 고객사 등록 절차(DB 행 추가, nginx에 경로 추가, 설정 반영)를 두 스크립트로 옮기고, 차례로 두 번, 동시에 두 번, 단계마다 죽였다 다시, 부하를 건 채로 돌렸어요. 숫자는 전부 이번에 돌린 결과입니다. 틀린 설정을 반영할 때 어느 쪽이 실패하는지는 3편 5장이 정리한 대로 멈추는 방법에 달려 있었는데, 그 차이도 6장에서 nginx 소스와 함께 확인했어요.

🧭 이 글에서 확인할 것
• 절차서 그대로인 스크립트를 동시에 두 번 돌리면 불일치가 몇 건 생기나?
• 멱등 스크립트에서 잠금(flock)을 빼면, "바뀌었나"의 비교 대상을 바꾸면 무엇이 달라지나?
• 단계마다 죽이고 다시 돌리면 어느 쪽이 스스로 복구되나?
• 부하 중에 멈췄다 켜기와 다시 읽기(reload)는 요청을 몇 건 잃나?
• 틀린 설정을 반영하면 stop, kill, reload는 각각 어떻게 끝나나?

1. 실습 환경: 고객사마다 경로 한 줄

컨테이너 넷으로 이뤄져 있어요. nginx가 고객사마다 location /t/<이름>/ 한 줄로 요청을 파이썬 업스트림에 넘기고, 고객사 목록은 PostgreSQL의 tenants 테이블에 있습니다. 운영 스크립트는 nginx 컨테이너 안에서 돌아요(psql, flock, curl을 넣어 뒀어요). 테이블은 절차서 시절 그대로라 이름에 UNIQUE 제약이 없고, idem.sh가 실행할 때 UNIQUE 인덱스를 스스로 만듭니다.

그림 1. 고객사 하나 = DB 행 하나 + location 한 줄 + 실제로 200이 오는 경로

두 스크립트의 차이는 3편 2장의 표에 잠금과 naive의 맨 앞 확인을 더한 것이에요.

단계 naive.sh (절차서 그대로) idem.sh (수렴형) 잠금 없음 flock -n, 잡혀 있으면 종료 코드 75 DB 행 맨 앞에서 SELECT, 있으면 중단 UNIQUE 인덱스 + INSERT ... ON CONFLICT DO NOTHING INSERT 설정 파일 echo "location ..." >> apps.conf DB 목록으로 파일 전체를 만들고, 다르면 임시 파일 + rename 설정 반영 nginx -s stop, 내려갈 때까지 기다림, 마지막으로 reload에 성공한 내용과 다르면 nginx nginx -t 후 nginx -s reload 확인 없음 새 경로가 200을 줄 때까지 최대 5초, 못 받으면 종료 코드 1 변형 (idem.sh 환경변수) LOCK=0 flock 을 끈다 APPLIED=file "바뀌었나"를 이번 실행에서 파일을 고쳤는지로만 판단한다 (처음 짠 판) DRY_RUN=1 바꾸지 않고 diff 만 보여 준다

check.sh가 매 시행 뒤 상태를 셉니다. 중복 행, 같은 location 두 줄, DB에 있는데 200이 안 오는 경로, 설정에는 있는데 DB에 없는 경로를 더한 값을 불일치라고 불렀어요. nginx가 살아 있는지도 따로 봅니다.

📖 용어: ON CONFLICT DO NOTHING
PostgreSQL의 INSERT 옵션이에요. 넣으려는 행이 UNIQUE 인덱스(또는 제약)에 걸리면 오류를 내는 대신 아무것도 하지 않고 넘어갑니다(PostgreSQL 문서, INSERT). 두 실행이 동시에 넣어도 행이 하나만 생기는 건 UNIQUE 인덱스 덕분이고, ON CONFLICT는 그때 둘째 실행이 오류로 멈추지 않게 해 줘요.
git clone https://github.com/DDINGJOO/Platform-study.git cd Platform-study/labs/devops/auto-01-idempotent docker compose up -d --build ./scripts/run_all.sh # 실험 전부. 하나만: ./scripts/run_all.sh e2 python3 scripts/summarize.py # out/ -> results/summary.md docker compose down -v

이미지는 nginx:1.29-alpine(로그에 찍힌 버전은 nginx/1.29.8), postgres:18.6-alpine, python:3.13-alpine이고, Docker 29.5.3과 Compose v5.1.4(docker --version, docker compose version 출력), Apple M5 Pro(sysctl -n machdep.cpu.brand_string 출력)에서 돌렸어요. 코드는 labs/devops/auto-01-idempotent에 있고, 요약은 results/summary.md, 시행별 원자료는 out/에 있습니다.

⚠️ 주의: 첫 실행은 초기화 단계에서 멈췄다
처음 돌렸을 때 컨테이너가 뜬 지 7분(docker ps의 Up 7 minutes)이 지나도 첫 실험의 출력 파일이 비어 있었어요. 컨테이너 안의 ps 출력은 이랬습니다(그 실행은 버렸고, 이 출력은 실습 README의 "고친 것"에 옮겨 뒀어요).
PID 1 tail -f /dev/null / PID 8 [nginx] <defunct>
nginx를 멈췄다 켜도 컨테이너가 살아 있도록 PID 1을 tail로 뒀는데, tail은 끝난 자식 프로세스를 거두지 않아요. 멈춘 nginx 마스터가 좀비로 남았고, "nginx가 내려갈 때까지 기다린다"는 pgrep -x nginx 루프가 그 좀비를 계속 찾아냈습니다. compose에 init: true를 넣어 좀비를 거두는 init(tini)을 PID 1로 두고 다시 돌렸어요. 프로세스가 사라졌는지를 이름으로 기다리는 스크립트는 좀비까지 셉니다.
📖 용어: 좀비 프로세스 (zombie)
이미 끝났지만 부모가 종료 상태를 읽어 가지 않아 프로세스 표에 남아 있는 프로세스예요. ps에 Z 상태, <defunct>로 보입니다. 부모가 죽으면 PID 1이 넘겨받아 거두는데, PID 1이 그 일을 하지 않는 프로그램이면 계속 남아요.

2. 차례로 두 번: 둘 다 멀쩡했다

같은 고객사 t1을 차례로 두 번 등록했어요.

## naive 1회차 [naive] t1 done ## naive 2회차 [naive] t1 already exists ## naive 확인 rows=2 dup_rows=0 locations=2 dup_locations=0 missing_routes=0 orphan_routes=0 nginx_up=1 mismatch=0 ## idem 1회차 [idem] t1 ok (changed=1) ## idem 2회차 [idem] t1 ok (changed=0) ## idem 확인 rows=2 dup_rows=0 locations=2 dup_locations=0 missing_routes=0 orphan_routes=0 nginx_up=1 mismatch=0

둘 다 불일치 0이에요. 3편이 말한 "그 좁은 경우에는 멱등해요"가 그대로 나왔습니다. 첫 실행이 끝까지 성공했고, 그 사이 아무도 끼어들지 않았으니까요. 차이는 출력 한 줄에만 있어요. naive는 "already exists"로 멈췄고, idem은 단계마다 확인한 뒤 바꿀 게 없다고(changed=0) 지나갔습니다. 이 차이가 숫자로 드러나는 건 다음 세 경우예요.

3. 동시에 두 번: naive는 20번 모두 깨졌다

같은 고객사 t1을 한 셸에서 두 개 동시에 띄웠어요(naive.sh t1 & naive.sh t1 & wait). 변형마다 20번, 시행마다 처음 상태로 되돌린 뒤입니다.

같은 고객사 둘을 동시에, 20회씩 중복 행 중복 location 경로 누락 nginx 꺼진 채 끝남 불일치 합 naive 20/20 20/20 20/20 1/20 61 idem LOCK=0 (잠금 끔) 0/20 0/20 0/20 0/20 0 idem LOCK=1 (기본) 0/20 0/20 0/20 0/20 0

naive는 3편 4장의 타임라인을 20번 모두 재현했어요. 둘 다 SELECT에서 "없음"을 보고, 둘 다 INSERT하고, 둘 다 같은 줄을 덧붙였습니다. 그다음이 예상과 달랐어요.

nginx: [emerg] duplicate location "/t/t1/" in /etc/nginx/apps/apps.conf:3 [naive] nginx -s stop rc=1 [naive] 10초 기다려도 nginx 가 내려가지 않음 nginx: [emerg] duplicate location "/t/t1/" in /etc/nginx/apps/apps.conf:3 [naive] nginx 시작 실패

→ 설정 파일에 같은 경로가 두 번 있어서, 멈추는 명령부터 실패했다는 뜻이에요. nginx -s stop은 신호를 보내기 전에 설정 파일을 읽는데, 읽다가 중복 location을 만나 종료 코드 1로 끝났고 신호는 가지 않았습니다(소스 근거는 6장). nginx는 옛 설정으로 계속 돌았어요. 그래서 경로 누락이 20/20입니다. t1은 DB에 행이 둘이나 있는데 nginx는 t1을 모르고 404를 돌려줬어요.

스크립트에는 "멈출 때까지 기다린다" 루프가 있었습니다. 처음 판에는 상한이 없어서, 멈추지 않는 nginx를 영원히 기다렸을 거예요. 이번 실습에서는 10초 상한을 넣었고, 40번의 실행 중 38번이 그 상한에 걸렸습니다. 절차서를 따르는 사람이라면 "stop 실패"를 보고 멈췄을 자리예요. 스크립트는 종료 코드를 보지 않고 다음 줄로 갔습니다.

예외가 한 번 있었어요(11번째 시행). 한쪽의 nginx -s stop이 다른 쪽이 줄을 덧붙이기 전에 설정을 읽어 성공했고, 실제로 nginx가 멈췄습니다. 그런데 켜는 시점에는 이미 중복 줄이 들어가 있어서 둘 다 시작에 실패했어요. 시행이 끝났을 때 nginx가 꺼져 있었고, base 경로까지 응답하지 않아 불일치가 하나 더 붙었습니다(합 61). 3편 5장이 말한, 멈출 때와 켤 때 설정이 다르면 멈추기는 성공하고 켜기는 실패한다는 경우가 20번 중 이 한 번, 두 실행이 엇갈린 순간에 나온 거예요.

📖 용어: nginx -s
실행 중인 nginx 마스터 프로세스에 신호를 보내는 명령이에요. stop은 빠른 종료, quit은 우아한 종료, reload는 설정 다시 읽기입니다(nginx 문서, Beginner's Guide). 신호를 보내기 전에 설정 파일을 끝까지 읽고(파싱), 설정이 틀리면 신호 없이 종료 코드 1로 끝나요(6장의 소스 근거).

잠금을 빼도 불일치는 0이었다

idem은 잠금을 꺼도(LOCK=0) 20번 모두 불일치 0이었어요. 구조상 이 경우를 막은 건 flock이 아니라 아래 두 장치예요. 이 둘은 빼 보지 않았으니 코드를 읽고 내린 판단입니다.

UNIQUE + ON CONFLICT가 행을 하나로 지켰어요. 두 INSERT가 동시에 들어가도 하나는 아무것도 하지 않고 넘어갑니다. 전체 재생성이 location을 하나로 지켰어요. 두 실행 모두 DB에서 목록을 다시 읽어 파일 전체를 쓰니, 늦게 쓴 쪽도 같은 내용을 씁니다. 줄을 덧붙이는 동작이 없으니 줄이 둘이 될 수 없어요.

잠금을 껐을 때 남은 흔적은 출력에 있었어요. 40번의 실행이 전부 changed=1을 찍었습니다. 시행마다 reload가 두 번 일어났다는 뜻이에요. 잠금을 켜면 20번 모두 한쪽이 "다른 실행이 진행 중이라 종료"(종료 코드 75)로 바로 빠졌고, reload는 한 번이었습니다.

잠금이 꼭 필요한 경우를 만들려고, 이번에는 서로 다른 고객사 t1과 t2를 동시에 등록해 봤어요. 한쪽이 상대의 INSERT 전에 목록을 읽으면, 늦게 rename한 쪽이 상대 경로가 빠진 파일로 덮어쓸 수 있습니다.

다른 고객사 둘(t1, t2)을 동시에, 20회씩 불일치 합 출력 naive 0 20/20 시행에서 한쪽이 "nginx 시작 실패" (종료 코드 1) 12/20 시행에서 한쪽이 10초 대기 상한에 걸림 idem LOCK=0 0 40번 모두 ok, changed=1 idem LOCK=1 0 20/20 시행에서 한쪽이 종료 코드 75로 빠짐 (등록 안 됨)

20번으로는 그 덮어쓰기가 한 번도 나오지 않았어요. 두 실행 모두 INSERT를 먼저 하고 목록을 읽기 때문에, 목록을 읽는 시점에는 대개 두 행이 다 들어가 있었을 거예요(읽은 시점은 재지 않았어요). 틈이 없다는 뜻이 아니라 이 환경에서 20번 안에 걸릴 만큼 넓지 않았다는 뜻이에요. 그래서 이 실습에서 flock이 막았다고 말할 수 있는 건 "reload 두 번"까지입니다.

다른 두 줄이 더 눈에 띄었어요. naive는 최종 상태가 20번 모두 맞았는데도 20번 모두 한쪽이 실패로 끝났습니다. 20번 중 12번은 한쪽이 "아직 안 내려감"으로 10초를 기다리다 상한에 걸렸고, 20번 모두 그 한쪽이 결국 시작 단계에서 실패했어요. 다른 쪽이 멈췄다 켠 nginx가 이미 돌고 있었기 때문으로 보여요. 실패가 아닌데 실패를 보고하는 스크립트는, 다음에 진짜 실패했을 때 아무도 믿지 않게 됩니다. idem의 잠금은 반대 방향의 대가를 냈어요. 잠금을 켜면 20번 모두 t2나 t1 중 하나가 등록되지 않고 75로 끝났습니다. 불일치 0은 "남은 상태가 앞뒤가 맞다"는 뜻일 뿐이고, 등록 요청 하나는 호출한 쪽이 다시 시도해야 해요.

💡 실무에서는
• flock -n으로 빠지는 스크립트는 "다른 실행 중"을 실패와 다른 종료 코드로 돌려주고, 호출하는 쪽(CI, 작업 큐)이 그 코드를 보고 다시 시도하게 합니다. 이번에는 75(EX_TEMPFAIL, 임시 실패)를 썼어요
• 기다리지 않고 순서대로 처리해야 하면 -n 대신 -w 30처럼 상한이 있는 대기를 씁니다

4. 단계마다 죽였다 다시 돌리면

스크립트가 정해진 지점에서 스스로 kill -9하게 하고(CRASH_AT), 바로 같은 명령을 한 번 더 돌렸어요. 3편 서두에서 VPN이 끊긴 뒤 다시 친 명령이에요.

변형 끊은 지점 끊긴 직후 다시 돌린 뒤 다시 돌린 결과 naive DB 행 뒤 1 1 "t1 already exists" (경로 영영 없음) naive 설정 파일 뒤 1 1 "t1 already exists" (파일엔 있고 nginx는 모름) APPLIED=file DB 행 뒤 1 0 ok (changed=1) APPLIED=file 설정 파일 뒤 1 1 확인 실패: /t/t1/ 가 404 (종료 코드 1) APPLIED=file reload 뒤 0 0 ok (changed=0) APPLIED=marker DB 행 뒤 1 0 ok (changed=1) APPLIED=marker 설정 파일 뒤 1 0 ok (changed=1) APPLIED=marker reload 뒤 0 0 ok (changed=0) (APPLIED=file, APPLIED=marker 는 idem.sh 의 변형. marker 가 기본값) (숫자는 불일치. 1 = t1 경로가 200을 주지 않음)

naive는 어디서 끊기든 다시 돌려도 고쳐지지 않았어요. 맨 앞의 SELECT가 행을 보고 "이미 있음"으로 끝내니 남은 단계가 돌 기회가 없습니다. 설정 파일 뒤에서 끊긴 경우가 더 나빠요. 파일에는 경로가 있으니 파일을 열어 본 사람은 "등록됐네"라고 판단하는데, nginx는 그 파일을 다시 읽은 적이 없습니다.

이 표에서 구분해야 할 게 하나 있어요. 3편 2장의 표는 설정 반영을 "마지막으로 반영에 성공한 내용과 다를 때만 nginx -t로 검사 후 reload"라고 적었습니다. "다를 때"를 그 기록 대신 이번 실행에서 파일을 고쳤는가로 판단한 것이 APPLIED=file 변형이에요. 이 변형은 설정 파일 뒤에서 끊기면 다시 돌려도 파일이 이미 원하는 내용이라 changed=0이 되고, reload를 건너뜁니다. 3편 3장이 경고한, 파일만 보고 "이미 맞음"이라고 판단하는 함정 그대로예요. 기본값은 마지막으로 reload에 성공했을 때 적어 둔 해시(/run/apps.applied)와 비교하는 APPLIED=marker이고, 이쪽은 세 지점 모두 다시 돌리기만으로 복구됐습니다. 다만 이것도 돌고 있는 설정을 직접 읽은 값이 아니라 기록이에요. 누군가 손으로 reload하거나 nginx를 다시 띄우면 실제와 어긋날 수 있고, 3편 3장이 체크포인트에 대해 한 경고가 여기에도 적용됩니다.

APPLIED=file이 복구는 못 했지만 거짓말은 하지 않았다는 점도 봐 둘 만해요. 마지막 단계의 200 확인이 404를 잡아 종료 코드 1로 끝났습니다. naive는 같은 상태에서 종료 코드 0이었어요. 고치지 못하는 스크립트와, 고치지 못했다고 말하는 스크립트는 다릅니다.

그림 2. 끊긴 뒤 같은 명령을 한 번 더. 무엇과 비교해 "이미 맞음"을 판단하느냐가 결과를 갈랐다

5. 부하 중 반영: 멈췄다 켜면 처리 중이던 요청이 끊긴다

부하기를 20초 돌리고, 8초째에 새 고객사를 등록했어요. 부하는 초당 100건의 빠른 요청(요청마다 새 연결)과, 늘 4개씩 동시에 처리 중인 1초짜리 요청입니다. naive(stop 후 start)와 idem(reload)을 각각 5번 돌렸어요.

시행 빠른 요청 실패 처리 중이던 1초 요청 반영에 걸린 시간 naive (stop -> start) 5 6, 5, 5, 6, 8 / 2000 5번 모두 4개 중 4개 끊김 0.074 ~ 0.097초 idem (reload) 5 0 / 2000 (5번 모두) 0 / 80 (5번 모두) 0.140 ~ 0.249초 naive 실패 종류 (빠른 요청 30건) ConnectionResetError 25, ConnectionRefusedError 5 (1초 요청) 반영 직전 0.73 ~ 0.78초에 시작한 4개가 RemoteDisconnected

naive가 nginx를 멈췄다 켜는 데는 0.1초도 걸리지 않았어요. 그 짧은 사이에 빠른 요청이 시행마다 5~8건 실패했습니다. 대부분은 연결이 맺어진 직후 끊긴 경우(ConnectionReset)였고, 아예 연결을 거부당한 경우는 시행마다 0~2건이었어요. 더 확실한 피해는 1초 요청 쪽이었습니다. 반영 순간 처리 중이던 4개가 다섯 번 모두 예외 없이 끊겼어요. nginx -s stop은 빠른 종료라 처리 중인 요청을 기다리지 않습니다.

1초 요청의 실패 수는 표에 넣지 않았어요. 부하기의 1초 요청 루프는 실패하면 곧바로 다음 요청을 보내서, 연결이 거부되는 동안에는 같은 0.01초 안에 수십 번 실패를 셉니다. 원자료에서 연결 거부로 센 수(시행마다 20~109건)는 피해 크기가 아니라 재시도 속도를 보여 줘요. 그래서 "처리 중이던 요청 중 몇 개가 끊겼나"만 셌습니다.

idem은 reload에 0.14~0.25초가 걸렸지만 다섯 번 모두 한 건도 잃지 않았어요(앞의 시간에는 DB 조회와 200 확인이 들어 있습니다). 반영이 더 오래 걸린 쪽이 손실 0이었습니다. 3편 5장의 설명대로 옛 워커가 붙어 있던 요청을 끝까지 처리하고, 새 연결은 새 워커가 받았어요.

그림 3. 공백은 0.1초가 안 됐지만, 그 순간 처리 중이던 요청은 하나도 남지 않았다

등록 한 번에 빠른 요청 6건과 처리 중이던 요청 4개예요. 1편의 팀처럼 등록이 한 달에 스무 번이면, 이번 부하기 설정(초당 100건, 1초 요청 4개)과 프록시 한 대 기준으로 한 달에 빠른 요청 약 120건(시행 평균 6.0건 x 20)과 처리 중 요청 80개를 잃는 셈입니다. 1편의 팀은 프록시가 네 대라 그 기준과는 또 달라요. 3편이 "자동화는 그 멈춤을 반영 횟수만큼 곱한다"고 한 곱셈이에요.

6. 틀린 설정을 반영하면: stop은 실패했고, kill은 nginx를 내렸다

3편 5장은 멈출 때와 켤 때 설정이 다르면 꺼진 채 남을 수 있고, 어느 쪽이 실패하는지는 멈추는 방법에 달렸다고 정리했어요. 3장에서는 nginx -s stop이 먼저 실패했습니다. 이걸 따로 확인하려고, 부하를 건 채 설정에 중복 location 한 줄을 넣고 세 가지 방법으로 반영해 봤어요.

중복 location을 넣고 반영 멈추기 켜기/reload 반영 뒤 nginx 빠른 요청 실패 nginx -s stop -> nginx 종료 코드 1 종료 코드 1 옛 설정으로 돎 0 / 2000 (10초 대기 상한에 걸림) kill -TERM <마스터> -> nginx 종료 코드 0 종료 코드 1 꺼짐 1223 / 2000 nginx -s reload (해당 없음) 종료 코드 1 옛 설정으로 돎 0 / 2000 ("켜기"는 nginx 명령. 첫 줄의 둘째 종료 코드 1은 옛 nginx가 그대로 떠 있고 설정도 틀린 상태에서 다시 켜려다 난 실패) nginx: [emerg] duplicate location "/t/base/" in /etc/nginx/apps/apps.conf:2

→ 중복 location 오류는 설정을 읽는 단계에서 나요. nginx -s stop과 nginx -s reload는 둘 다 신호를 보내기 전에 설정을 읽어서, 둘 다 신호를 보내지 않고 종료 코드 1로 끝났습니다. nginx는 아무 일 없다는 듯 옛 설정으로 돌았고, 요청은 한 건도 실패하지 않았어요. nginx 1.29.8 소스로 보면 src/core/nginx.c의 main()은 설정을 읽는 ngx_init_cycle을 먼저 부르고 실패하면 바로 1을 돌려주며(293~300행), 신호를 보내는 ngx_signal_process는 그 뒤에 있어요(329~330행). 그래서 -s로 보내는 명령은 설정이 틀리면 어떤 신호도 보내지 못합니다.

멈추기는 성공하고 켜기는 실패하는 순서가 나온 건 설정을 읽지 않고 멈추는 쪽이었습니다. 마스터 프로세스에 kill -TERM을 직접 보내면 nginx는 설정과 상관없이 멈추고, 켜는 nginx가 중복 location에서 실패해요. 부하기가 끝날 때까지 약 12초 동안 nginx가 없었고, 그사이 빠른 요청 2,000건 중 1,223건이 실패했습니다. 서비스 관리자가 프로세스에 신호를 보내 멈추는 구성이라면 이쪽이 됩니다. 3장의 11번째 시행도 같은 모양이었어요. 멈출 때는 설정이 맞았고 켤 때는 틀려 있었습니다.

정리하면 stop/start의 위험은 "틀린 설정에서 켜기가 실패한다"보다 넓어요. 멈추는 시점과 켜는 시점에 설정이 같다는 보장이 없으면 꺼진 채 남을 수 있습니다. reload는 같은 시점에 검사하고 적용하니 그 틈이 없어요.

reload가 0으로 끝나고 실패한 경우

3편 5장은 "reload가 실패해도 명령 자체는 신호를 보내는 데 성공했다고 끝나는 경우가 있다"고도 했어요. 중복 location에서는 reload가 종료 코드 1로 실패를 알렸으니 그 경우가 아닙니다. 그래서 읽는 단계는 통과하고 적용하는 단계에서 실패하는 설정을 만들었어요. 이 컨테이너에 없는 문서용 주소 192.0.2.1:81에 listen하는 server 블록입니다.

## nginx -t nginx: the configuration file /etc/nginx/nginx.conf syntax is ok nginx: [emerg] bind() to 192.0.2.1:81 failed (99: Address not available) nginx: configuration file /etc/nginx/nginx.conf test failed t_rc=1 ## nginx -s reload [notice] 61538#61538: signal 1 (SIGHUP) received from 61561, reconfiguring reload_rc=0 workers_replaced=0 healthz=200 ## 마스터의 오류 로그 (out/e3c-bind.txt 에서 줄임) [emerg] 61538#61538: bind() to 192.0.2.1:81 failed (99: Address not available) [emerg] 61538#61538: bind() to 192.0.2.1:81 failed (99: Address not available)

→ nginx -s reload는 설정을 파싱만 하고 소켓은 열어 보지 않은 채 신호를 보낸 뒤 종료 코드 0으로 끝났어요. 신호를 받은 마스터가 새 설정을 적용하다 소켓을 열지 못했고, 오류는 마스터의 로그에만 남았습니다. 워커는 바뀌지 않았고 옛 설정으로 계속 응답했어요. 3편의 문장이 맞는 경우는 이쪽입니다. 그리고 nginx -t는 이 오류도 잡았어요. "syntax is ok" 다음 줄에서 bind 실패를 내고 종료 코드 1로 끝났습니다. 소스도 이렇게 갈려요. src/core/ngx_cycle.c의 ngx_init_cycle은 -s로 띄운 신호 프로세스라면 파싱 직후 돌아가고(314행 if (ngx_process == NGX_PROCESS_SIGNALLER) return cycle;), nginx -t는 630행의 ngx_open_listening_sockets까지 가서 bind를 해 봐요. 마스터는 새 설정이 실패하면 옛 설정을 그대로 씁니다(src/os/unix/ngx_process_cycle.c 225~228행). reload의 종료 코드는 "신호를 보냈다"까지만 말해 줘요. 반영 전의 nginx -t와 반영 뒤의 200 확인이 둘 다 필요한 이유입니다.

7. 드라이런과 빈 목록

마지막으로 3편 6장의 두 주장을 짧게 확인했어요.

## DRY_RUN=1 idem.sh t1 [dry-run] DB: INSERT t1 [dry-run] @@ -1 +1,2 @@ [dry-run] location /t/base/ { proxy_pass http://app:8080/; } [dry-run] +location /t/t1/ { proxy_pass http://app:8080/; } ## 드라이런 뒤 상태 rows=1 locations=1 mismatch=0 ## DB 조회가 실패해 빈 목록을 받는 경우 (PGDATABASE=nope) psql: error: ... FATAL: database "nope" does not exist [idem] DB 에서 고객사 목록을 못 읽었다. 멈춤 rc=2 ## 그 뒤 상태 rows=1 locations=1 mismatch=0

드라이런은 바뀔 내용을 diff로 보여 주고 아무것도 바꾸지 않았어요. DB 조회가 실패했을 때는 목록이 비었다는 걸 알아채고 설정 파일을 건드리지 않은 채 종료 코드 2로 멈췄습니다. 이 확인이 없었다면 빈 목록으로 경로가 하나도 없는 파일을 만들었을 거예요. 경로 수가 절반 아래로 줄면 멈추는 두 번째 안전장치도 스크립트에 있지만, 이번에는 첫 번째 확인에서 먼저 멈춰서 그 장치까지 가지 않았습니다.

• 절차서를 옮긴 스크립트는 같은 입력으로 동시에 두 번 돌려 보는 시험을 먼저 해 봅니다. 이번 실습에서 naive는 20번 중 20번 깨졌어요
• DB 행은 UNIQUE + ON CONFLICT로, 설정 파일은 전체 재생성으로 지킵니다. 이번 실습에서는 잠금 없이도 이 둘이 불일치를 0으로 막았어요
• "바뀌었나"는 파일끼리가 아니라 마지막으로 반영에 성공한 내용과 비교합니다. 파일끼리 비교한 판은 설정 파일 뒤에서 끊기면 다시 돌려도 복구되지 않았어요
• 설정 반영은 nginx -t 후 reload, 그리고 새 경로의 200 확인으로 끝냅니다. reload의 종료 코드 0은 성공을 뜻하지 않았어요
• stop/start를 꼭 써야 하면 각 명령의 종료 코드를 확인하고, 기다리는 루프에는 상한을 둡니다. 컨테이너 안이라면 PID 1이 좀비를 거두는지도 봐요
✍️ 오늘의 요약
차례로 두 번 돌리면 두 스크립트 모두 멀쩡했어요. 차이는 동시에, 끊긴 뒤에, 부하 중에 나왔습니다. 같은 고객사를 동시에 두 번 등록하자 절차서 그대로인 스크립트는 20번 모두 중복 행, 중복 경로, 응답 없는 경로를 남겼고, 수렴형은 잠금을 꺼도 0이었어요. 단계마다 죽인 뒤 다시 돌리면 절차서 판은 한 번도 복구되지 않았고, 수렴형은 "바뀌었나"를 마지막으로 reload에 성공한 내용의 기록과 비교할 때만 세 지점 모두 복구됐어요. 부하 중 stop/start는 반영 한 번에 빠른 요청 5~8건과 처리 중이던 요청 4개를 잃었고, reload는 0건이었어요.

틀린 설정에서는 nginx -s stop이 먼저 실패해 nginx가 옛 설정으로 남았고, 설정을 읽지 않는 kill로 멈추면 nginx가 꺼진 채 1,223건이 실패했어요. 적용 단계에서 실패하는 설정은 reload가 종료 코드 0으로 끝났고 nginx -t만 잡았어요. 스크립트를 믿게 만드는 건 명령의 종료 코드가 아니라 반영 전의 검사와 반영 뒤의 확인이에요.
