실습-1. 절차서를 그대로 옮긴 스크립트와 멱등한 스크립트를 두 번씩 돌린다
실습-2. 경고를 받아 스스로 고치는 스크립트에 상한을 건다

밤 11시, 신규 고객사 등록 스크립트를 돌리던 중에 VPN이 끊깁니다. 다시 접속해서 같은 명령을 칩니다. 스크립트는 "이미 있음"을 출력하고 정상 종료해요. 다음 날 아침 그 고객사에서 접속이 안 된다는 연락이 옵니다. DB에는 고객사 행이 있는데, 프록시 설정에는 경로가 없어요. 첫 실행은 DB 행을 넣은 직후에 끊겼고, 두 번째 실행은 그 행을 보고 "다 끝났다"고 판단했습니다.

같은 주에 다른 일도 생겨요. 같은 티켓을 두 사람이 동시에 집어 들고 각자 스크립트를 돌렸습니다. 둘 다 "없음"을 확인하고 둘 다 등록했어요. DB 행이 둘, 프록시 설정의 경로가 둘이 됐고, 프록시는 다음 설정 반영 때 같은 경로가 두 번 있다며 설정을 거부했습니다.

두 사고 모두 스크립트에 버그가 있어서 난 게 아니에요. 스크립트는 절차서를 정확히 옮겼습니다. 절차서가 사람을 전제로 쓰였을 뿐이에요. 사람은 끊긴 작업을 다시 할 때 어디까지 했는지 확인하고, 동료가 이미 하고 있으면 알아챕니다. 코드로 옮기면 그 전제가 사라져요. 그럼 코드로 옮긴 절차는 어떤 성질을 갖춰야 할까요?

🧭 이 글에서 확인할 것
• "이미 있으면 중단"은 왜 멱등성이 아닌가? 수렴은 무엇이 다른가?
• 중간에 끊긴 스크립트는 어떻게 다시 시작하나?
• 같은 스크립트 두 개가 동시에 돌면 무엇이 깨지나? 잠금은 어디에 거나?
• 설정을 반영할 때 멈췄다 켜기와 다시 읽기는 무엇이 다른가?
• 드라이런은 언제 믿을 수 있나?
• 경고를 받아 스스로 고치는 자동화는 어디서 멈춰야 하나?

1. "이미 있으면 중단"은 멱등성이 아니다

요청과 메시지의 멱등성은 다른 시리즈에서 다뤘어요. 결제 메시지를 두 번 받아도 한 번만 처리하는 법은 추적과 디버깅 4편(주문이 두 번 결제됐어요)에서, 재시도해도 되는 요청은 트래픽 관리 4편(요청을 한 번 더 보내면 빨라진다)에서 봤습니다. 이번에는 같은 성질을 운영 스크립트에 요구해요.

📖 용어: 멱등성 (운영 작업의)
어떤 작업을 한 번 수행한 결과와, 그 사이에 다른 개입 없이 여러 번 수행한 결과가 정확히 같은 성질이에요(Ansible 문서, Glossary). 운영 스크립트라면 두 번째 실행이 아무것도 바꾸지 않아야 합니다.

절차서를 그대로 옮긴 코드는 대개 이런 모양이에요. 웹 서버(IIS)에 새 애플리케이션을 배포하는 절차서를 의사 코드로 옮긴 흔한 예를 줄여서 적었습니다.

appcmd list app <site>/<app> # 이미 있는지 확인 IF 결과가 비어 있지 않다 THEN RETURN "Application already exists" ELSE mkdir <physical_path> appcmd add app /site.name:<site> /path:/<app> /physicalPath:<physical_path> appcmd recycle apppool <pool> appcmd stop site <site> appcmd start site <site> IF 에러 THEN RETURN error ELSE RETURN success

첫 줄의 확인은 두 번 돌리는 경우를 생각한 장치예요. 실제로 처음 실행이 끝까지 성공했다면 두 번째 실행은 아무것도 바꾸지 않습니다. 그 좁은 경우에는 멱등해요. 문제는 그 밖의 경우입니다.

  • 중간에 끊긴 뒤: appcmd add app까지 하고 끊겼다면 다시 돌릴 때 확인에 걸려 "already exists"로 끝나요. 사이트를 다시 시작하는 단계는 영영 실행되지 않습니다. 서두의 첫 사고예요.
  • mkdir에서 다시 걸릴 때: mkdir만 하고 끊겼다면 두 번째 실행은 확인을 통과하고 mkdir에서 "이미 있음" 에러로 멈춰요. 디렉터리를 사람이 지워 줘야 앞으로 갑니다.
  • 동시에 두 개가 돌 때: 둘 다 확인 단계에서 "없음"을 보고 둘 다 등록 단계로 갑니다. 서두의 두 번째 사고예요(4장).
  • 매번 멈췄다 켤 때: 마지막 두 줄은 앱 하나를 더할 때마다 사이트 전체를 멈춥니다. 그 사이 들어온 요청은 실패해요(5장).

정리하면 첫 줄의 확인은 첫 단계의 결과만 보고 전체가 끝났다고 판단해요. 확인하는 대상과 판단하는 범위가 어긋난 거예요.

사람이 이 절차서를 따를 때는 이 어긋남이 문제가 되지 않았습니다. "already exists"를 본 사람은 정말 다 끝났는지 사이트를 열어 보고, 디렉터리가 이미 있으면 왜 있는지 한 번 생각한 뒤 넘어가요. 절차서의 한 줄 뒤에는 늘 사람의 확인이 따라붙어 있었던 거예요. 코드로 옮기면 그 확인이 사라집니다. 그래서 절차서를 코드로 옮길 때는 절차서에 적힌 줄만이 아니라 사람이 줄 사이에서 하던 확인까지 옮겨야 해요. 2편에서 의사 코드를 거치라고 한 이유가 이것입니다.

2. 확인을 단계마다 두고, 원하는 상태로 맞춘다

고치는 방향은 단순합니다. 맨 앞에서 한 번 묻고 전부를 건너뛰지 말고, 단계마다 "원하는 상태인가?"를 묻고 아니면 그 단계만 맞춰요. 이런 방식을 수렴이라고 부릅니다.

📖 용어: 수렴 (convergence)
"무엇을 할지"가 아니라 "어떤 상태여야 하는지"를 적고, 지금 상태와 비교해 다른 부분만 바꾸는 방식이에요. 몇 번을 돌려도 결국 같은 상태에 닿고, 이미 그 상태면 아무것도 하지 않습니다. Ansible, Terraform, Kubernetes 컨트롤러가 이 방식으로 동작해요.

신규 고객사 등록을 수렴 방식으로 다시 쓰면 단계마다 이런 짝이 생겨요.

단계 명령형 (절차서 그대로) 수렴형 DB 행 INSERT UNIQUE 제약 + INSERT ... ON CONFLICT DO NOTHING 설정 파일 echo "location ..." >> apps.conf DB에서 전체 목록을 읽어 파일 전체를 새로 만든다 내용이 같으면 쓰지 않는다 쓸 때는 임시 파일에 쓰고 rename 한다 설정 반영 stop; start 마지막으로 반영에 성공한 내용과 다를 때만 nginx -t 로 검사 후 reload 확인 (없음) 새 경로로 요청해 200 확인. 실패하면 종료 코드 1

몇 가지를 짚어 볼게요.

DB 행: INSERT 앞에서 SELECT로 확인하는 것보다 테이블에 UNIQUE 제약을 거는 쪽이 강합니다. 확인과 삽입 사이에 틈이 없고, 스크립트가 아닌 다른 경로(사람이 콘솔에서 넣는 경우)까지 막아요. 2편에서 본 automatic의 작은 예이기도 해요. 멱등성을 스크립트가 아니라 시스템이 보장합니다.

설정 파일: >>로 한 줄을 덧붙이는 건 두 번 돌리면 두 줄이 되는 대표적인 명령형 동작이에요. 수렴형은 "이 파일의 내용은 DB의 고객사 목록에서 만든 것이어야 한다"를 원하는 상태로 놓고 파일 전체를 다시 만듭니다. 내용이 지금과 같으면 쓰지 않아요. 이 비교 결과가 "바뀌었나(changed)"이고, Ansible 모듈이 결과마다 ok와 changed를 구분해 보고하는 것과 같은 구조예요. 다만 다음 단계(설정 반영)가 이 값을 그대로 쓰면 안 됩니다. 파일을 쓴 직후에 끊기면, 다시 돌릴 때 파일은 이미 원하는 내용이라 changed가 거짓이 되고 반영을 건너뛰어요. 그래서 반영 여부는 파일끼리가 아니라 마지막으로 반영에 성공한 내용(예: 그때의 해시를 적어 둔 파일)과 비교해서 정합니다. 3장 끝의 "파일만 보고 이미 맞음" 함정이 이 자리예요. 다만 이것도 돌고 있는 설정을 직접 읽은 값이 아니라 기록이라, 누군가 손으로 reload하거나 프로세스를 다시 띄우면 실제와 어긋날 수 있어요. 3장의 체크포인트 경고가 여기에도 걸립니다.

임시 파일과 rename: 파일을 제자리에서 고쳐 쓰다 끊기면 반쯤 쓴 파일이 남아요. 같은 디렉터리의 임시 파일에 다 쓴 뒤 rename으로 바꿔치면, 같은 파일 시스템 안에서는 원자적으로 바뀌어서 읽는 쪽은 옛 파일 아니면 새 파일만 봅니다.

확인: 2편에서 코드로 옮길 때 가장 먼저 빠지는 줄이라고 했던 결과 검증이에요. 마지막에 새 경로로 요청을 보내 200을 받지 못하면 실패로 끝냅니다. 이 줄이 있어야 "스크립트는 성공했는데 고객은 접속이 안 된다"가 사라져요.

3. 두 번 돌려도 되면 중간에 끊겨도 된다

수렴형으로 바꾸면 덤이 하나 따라옵니다. 끊긴 스크립트를 다시 시작하는 별도 장치가 필요 없어져요. 어디서 끊겼든 처음부터 다시 돌리면, 이미 된 단계는 "이미 원하는 상태"라서 지나가고 안 된 단계만 실행됩니다.

그림 1. 끊긴 뒤 다시 돌렸을 때. 앞에서 한 번 묻는 스크립트는 남은 단계를 건너뛴다

이 성질이 실제로 얼마나 차이 나는지는 실습-1에서 단계마다 일부러 죽여 보고 다시 돌려서 셌어요. 절차서를 그대로 옮긴 스크립트는 DB 행 뒤에서 끊기든 설정 파일 뒤에서 끊기든 다시 돌려도 "already exists"로 끝나 경로가 생기지 않았습니다. 수렴형은 반영 여부를 마지막 reload 성공 때 적어 둔 해시와 비교한 판(APPLIED=marker)에서만 세 지점 모두 다시 돌리기로 복구됐고, 파일끼리 비교한 판(APPLIED=file)은 설정 파일 뒤에서 끊기면 복구하지 못했어요(마지막 200 확인이 404를 잡아 실패로 끝나기는 했습니다). 여기서는 설계상 주의할 점 두 가지만 짚을게요.

단계 순서를 정할 때 "반쯤 된 상태가 해로운가"를 본다. 수렴형이라도 끊긴 순간과 다시 돌리는 순간 사이에는 반쯤 된 상태가 운영 중에 노출됩니다. 프록시 경로를 먼저 만들고 DB 행을 나중에 넣으면, 그 사이에 들어온 요청은 경로는 있는데 고객사 정보가 없는 상태를 만나요. DB 행을 먼저 넣으면 아무도 그 행을 쓰지 않으니 해롭지 않습니다. 소비하는 쪽보다 제공하는 쪽을 먼저 만들고, 지울 때는 반대 순서로 해요.

"어디까지 했나"를 따로 기록하지 않는다. 끊긴 지점부터 다시 시작하려고 단계마다 체크포인트 파일을 남기는 방식도 있어요. 그런데 체크포인트는 실제 상태와 어긋날 수 있습니다. 체크포인트를 쓰기 직전에 끊기면 실제로는 된 단계를 안 된 걸로 기록하고, 누군가 손으로 상태를 되돌리면 된 걸로 기록된 단계가 실제로는 안 된 상태가 돼요. 수렴형은 기록 대신 지금 상태를 직접 읽어서 판단하니 이 어긋남이 생기지 않습니다. 다만 "지금 상태"를 어디서 읽는지는 조심해야 해요. 설정 파일은 바뀌었는데 프로세스가 아직 다시 읽지 않았다면, 파일만 보고 "이미 맞음"이라고 판단하는 순간 같은 함정에 빠집니다.

다시 돌릴 수 없는 단계는 따로 표시한다. 외부에 이메일을 보내거나 결제를 일으키는 단계는 두 번 실행되면 되돌릴 수 없어요. 이런 단계는 맨 끝으로 미루고, "보냈음"을 기록하는 곳(DB 열 하나면 충분합니다)을 먼저 확인합니다. 메시지 처리의 인박스 패턴을 스크립트에 적용한 셈이에요.

4. 동시에 두 개가 돌면 확인과 실행 사이가 벌어진다

서두의 두 번째 사고는 수렴형으로 바꿔도 다 막히지 않습니다. 확인과 실행 사이에 틈이 있는 한, 두 실행이 같은 틈에 동시에 들어갈 수 있거든요.

📖 용어: 경쟁 상태 (race condition)
두 실행이 같은 자원을 다룰 때, 결과가 둘의 실행 순서에 따라 달라지는 상황이에요. "확인하고 나서 실행한다(check-then-act)" 구조는 확인과 실행 사이에 다른 실행이 끼어들면 둘 다 같은 확인 결과를 믿고 움직입니다.
시각 실행 A 실행 B t1 SELECT ... → 없음 t2 SELECT ... → 없음 t3 INSERT (행 1) t4 INSERT (행 2) ← 중복 t5 echo location >> apps.conf t6 echo location >> apps.conf ← 같은 경로 두 줄 t7 nginx 반영 → 실패 (duplicate location)

실습-1에서는 이 틈이 수렴형에서 잡히지 않았어요. 잠금을 끈 채 같은 고객사 둘, 다른 고객사 둘을 각각 20번씩 동시에 돌렸는데 40번 모두 불일치가 0이었습니다. 두 실행 모두 INSERT를 먼저 하고 목록을 다시 읽어서, 목록을 읽을 즈음에는 대개 두 행이 다 들어가 있었던 것으로 보여요(읽은 시점은 재지 않았습니다). 틈이 없다는 뜻이 아니라 그 환경에서 20번 안에 걸릴 만큼 넓지 않았다는 뜻입니다. 잠금을 끈 흔적은 같은 반영(reload)이 두 번씩 일어난 것으로만 보였어요. 반면 절차서 판은 같은 고객사 둘을 동시에 돌리자 20번 모두 행과 경로가 둘씩 생겼습니다.

막는 방법은 세 층이 있어요.

시스템 쪽 제약: 2장의 UNIQUE 제약이 가장 아래층입니다. 두 실행이 동시에 INSERT해도 하나만 성공해요. 다만 이 제약은 DB 행만 지키고, 설정 파일 같은 다른 단계는 지키지 못합니다.

스크립트 전체를 감싸는 잠금: 같은 호스트에서 도는 스크립트라면 flock이 가장 간단해요. 파일 하나에 배타 잠금을 걸고, 이미 잠겨 있으면 기다리거나(-w) 바로 포기합니다(-n).

exec 9>/var/lock/register-tenant.lock flock -n 9 || { echo "다른 실행이 진행 중이라 종료"; exit 75; } # 여기부터 스크립트 본문. 프로세스가 끝나면 fd 가 닫히며 잠금도 풀린다
📖 용어: 권고 잠금 (advisory lock)
잠금을 확인하기로 약속한 프로세스끼리만 지켜지는 잠금이에요. flock 잠금이 여기 속합니다. 잠금을 확인하지 않는 프로세스(사람이 직접 친 명령)는 그냥 파일을 고칠 수 있어서, 일관성을 보장하지는 못해요(macOS flock(2) 매뉴얼).

프로세스가 죽으면 파일 디스크립터가 닫히면서 잠금도 풀려요. "잠금 파일이 있으면 실행 중"이라고 보는 방식(파일을 만들고 끝날 때 지우는 방식)은 프로세스가 죽으면 파일이 남아서 다음 실행을 영원히 막습니다. 잠금은 파일의 존재가 아니라 커널이 들고 있는 잠금으로 거는 게 안전해요.

여러 호스트에 걸친 잠금: flock은 한 호스트 안에서만 통해요. 운영자 두 명이 각자 다른 배스천 호스트에서 같은 스크립트를 돌리면 잠금 파일도 둘이라 서로 못 봅니다. 이때는 둘 다 접근하는 곳에 잠금을 둬요. DB의 권고 잠금(PostgreSQL의 pg_try_advisory_lock)이나, 작업 실행을 한 곳(CI 작업, 작업 큐)으로 모으는 방법이 있습니다. 실행 경로를 한 곳으로 모으면 잠금과 함께 실행 기록도 한 곳에 남아요.

5. 멈췄다 켜지 말고 다시 읽힌다

1장 예의 마지막 두 줄, 사이트를 멈췄다 켜는 단계로 돌아가 볼게요. 설정을 반영하는 가장 확실한 방법처럼 보이지만, 멈춘 순간부터 다시 켜질 때까지 새 연결을 받지 못하고, 처리 중이던 요청도 끊길 수 있습니다. 앱 하나를 더할 때마다 사이트 전체가 잠깐씩 내려가는 거예요. 그리고 더 나쁜 경우가 있어요. 멈출 때와 켤 때 설정이 다르면, 멈추기는 성공하고 켜기는 실패해서 꺼진 채 남습니다. 어느 쪽이 실패하는지는 멈추는 방법에 달려 있어요. 실습-1에서 서두의 중복 경로를 넣고 반영해 보니, nginx -s stop은 신호를 보내기 전에 설정 파일을 읽다가 중복 location에서 종료 코드 1로 끝났고 nginx는 옛 설정으로 계속 돌았어요. 멈추기부터 실패한 거예요. 소스도 그렇습니다. nginx 1.29.8의 src/core/nginx.c main()은 설정을 읽는 ngx_init_cycle을 먼저 부르고 실패하면 1을 돌려주며(293~300행), 신호를 보내는 ngx_signal_process는 그 뒤에 있어요(329~330행). 설정을 읽지 않고 마스터 프로세스에 kill -TERM을 직접 보냈을 때만 멈추기가 성공하고 켜기가 실패해 nginx가 꺼진 채 남았습니다. 두 실행이 엇갈려 한쪽이 설정이 맞을 때 멈추고 다른 쪽이 틀린 줄을 넣은 뒤 켜는 경우도 같은 결과였어요(동시 실행 20번 중 1번).

nginx의 다시 읽기(reload, HUP 신호)는 이 두 문제를 모두 피하도록 만들어져 있습니다. 동작 순서를 옮기면 이래요(nginx 문서, Controlling nginx).

1. 마스터 프로세스가 새 설정의 문법을 검사한다 2. 새 설정을 적용해 본다 (로그 파일, 새 listen 소켓 열기) → 실패하면 바꾼 것을 되돌리고 옛 설정으로 계속 동작한다 3. 성공하면 새 워커 프로세스를 띄우고, 옛 워커에게 우아하게 끝내라고 알린다 4. 옛 워커는 listen 소켓을 닫고, 붙어 있던 클라이언트를 끝까지 처리한 뒤 종료한다

2단계 덕분에 틀린 설정은 반영되지 않고 옛 설정이 계속 돌아요. 3, 4단계 덕분에 처리 중이던 요청은 옛 워커가 마무리하고, 새 연결은 새 워커가 받습니다. 그래도 반영 전에 nginx -t로 따로 검사하는 습관은 남겨 둬요. reload가 실패해도 명령 자체는 신호를 보내는 데 성공했다고 끝나는 경우가 있어서, 스크립트가 실패를 알아채려면 검사를 먼저 해야 합니다. 실습-1에서 보면 중복 location처럼 설정을 읽는 단계에서 나는 오류에서는 nginx -s reload가 신호를 보내지 않고 종료 코드 1로 끝났어요. 읽기는 통과하고 적용하는 단계에서 실패하는 설정(이 호스트에 없는 주소에 listen)에서는 종료 코드 0으로 끝났는데, 워커는 바뀌지 않았고 오류는 마스터의 로그에만 남았습니다. nginx -t는 두 경우를 모두 잡았어요. 소스로 보면 -s로 띄운 신호 프로세스는 설정을 파싱한 직후 돌아가 소켓을 열어 보지 않고(src/core/ngx_cycle.c 314행), nginx -t는 630행의 ngx_open_listening_sockets까지 가서 bind를 해 봅니다. 신호를 받은 마스터는 새 설정이 실패하면 옛 설정을 그대로 써요(src/os/unix/ngx_process_cycle.c 225~228행).

그림 2. 멈췄다 켜면 빈칸이 생기고, 다시 읽히면 옛 워커와 새 워커가 겹친다

이 "검사한 뒤 다시 읽히기" 짝은 nginx만의 것이 아니에요. HAProxy는 haproxy -c -f로 설정을 검사하고, Prometheus는 promtool check config로 검사한 뒤 SIGHUP이나 /-/reload로 다시 읽힙니다. 도구마다 명령은 달라도 순서는 같아요. 새 설정을 파일에 쓰고, 검사기로 확인하고, 통과했을 때만 실행 중인 프로세스에 다시 읽으라고 알립니다. 검사기에 걸리면 운영 중인 프로세스는 옛 설정 그대로 두고 스크립트는 실패로 끝내요. 그래야 틀린 설정 하나가 장애로 번지지 않고 스크립트의 실패로 끝납니다.

모든 소프트웨어가 nginx 같은 다시 읽기를 지원하지는 않아요. 그럴 때는 인스턴스를 여러 대 두고 한 대씩 빼서 반영하는 방법(배포 안전성 시리즈의 2편에서 본 블루-그린이나 롤링)을 씁니다. 원칙은 같아요. 설정 반영이 서비스를 멈추게 만들면, 자동화는 그 멈춤을 반영 횟수만큼 곱한다. 1편의 선형 증가가 여기서는 다운타임으로 나타나요.

6. 드라이런은 수렴형 스크립트에서만 믿을 수 있다

스크립트를 운영에 돌리기 전에 "무엇을 바꿀지"를 먼저 보고 싶을 때가 많아요. 드라이런(dry run)입니다. Ansible의 --check는 원격 시스템을 바꾸지 않고 바뀔 수 있는 내용만 출력하고, --diff는 지원하는 모듈에서 무엇이 바뀌었는지(파일이면 unified diff 형식)를 보여 줘요. 다만 무슨 일이 생길지 감을 잡는 용도이지 제대로 된 스테이징 환경을 대신하지는 못한다는 단서가 같이 붙어 있어요(Ansible 문서, Glossary).

📖 용어: 드라이런 (dry run)
실제로 바꾸지 않고, 실행하면 무엇이 바뀔지만 계산해서 보여 주는 실행이에요. 운영에 적용하기 전에 변경 범위를 사람이 확인하는 데 씁니다.

드라이런이 가능하려면 스크립트가 "지금 상태"와 "원하는 상태"를 따로 계산할 수 있어야 해요. 수렴형은 원래 그 둘의 차이를 구해서 움직이니, 차이를 출력하고 멈추기만 하면 드라이런이 됩니다. 명령형은 다릅니다. echo ... >> apps.conf를 드라이런으로 만들려면 "이 줄을 덧붙일 것"이라고 출력할 수밖에 없는데, 그 줄이 이미 있는지는 계산하지 않아요. 드라이런 결과가 실제 결과와 다릅니다.

드라이런이 틀리는 경우가 수렴형에도 하나 있어요. 앞 단계의 결과에 기대는 단계입니다. 1단계에서 디렉터리를 만들고 2단계에서 그 디렉터리에 파일을 쓰는 스크립트를 드라이런하면, 1단계는 실제로 만들지 않으니 2단계는 "디렉터리가 없다"고 판단해요. 드라이런 출력에 이런 경고가 섞여 있으면 스크립트가 틀린 게 아니라 드라이런의 한계입니다. 그래서 드라이런은 변경 범위를 보는 도구로 쓰고, 결과를 보증하는 도구로 쓰지 않아요.

⚠️ 주의: 빈 목록이 "전부"가 되는 자리
• 2편에서 본 디스크 삭제 사고는 대상 목록이 비어 있을 때 그 빈 집합이 "전부"로 해석돼서 났어요(Google SRE Book, The Evolution of Automation at Google)
• 수렴형 스크립트에도 같은 함정이 있어요. "DB의 고객사 목록으로 설정 파일을 다시 만든다"는 DB 조회가 실패해 빈 목록을 받으면 모든 경로를 지운 설정을 만들어요
• 원하는 상태를 계산한 결과가 지금보다 크게 줄어들면(예: 경로 수가 절반 아래로) 적용하지 말고 멈춰서 사람에게 넘겨요. 드라이런의 diff 크기를 그대로 안전 장치로 쓸 수 있어요

7. 스스로 고치는 자동화에는 상한과 넘기는 조건이 있어야 한다

여기까지는 사람이 실행하는 스크립트였어요. 자동화의 다음 단계는 사람 없이 도는 것입니다. 경고가 울리면 웹훅을 받아 정해진 조치(재시작, 캐시 비우기, 트래픽 빼기)를 하는 자동 복구예요. 장애 대응 1편에서 "완화 자동화"라고 부른 단계입니다.

앞의 성질은 여기서 전부 더 중요해져요. 같은 경고가 짧은 간격으로 여러 번 오고, 여러 인스턴스에서 동시에 오기 때문입니다. 같은 조치가 두 번 와도 안전해야 하고(멱등성), 같은 대상에 두 조치가 겹치면 안 되고(잠금), 무엇을 할지 기록이 남아야 해요. 그리고 사람이 실행하는 스크립트에는 없던 문제가 하나 더 생깁니다. 언제 그만둘지예요.

재시작으로 고쳐지는 장애가 있고, 재시작으로 증상만 잠깐 사라지는 장애가 있습니다. 메모리 누수라면 재시작하면 한동안 정상이다가 다시 차오르고, 다시 경고가 울리고, 다시 재시작해요. 자동 복구는 이 순환을 몇 번이고 돌 수 있고, 도는 동안 경고는 켜졌다 꺼졌다를 반복하며 사람은 아무도 원인을 보지 않습니다. 고치는 게 아니라 가리는 거예요. 게다가 사람이 같은 일을 했다면 세 번째 재시작쯤에서 "이거 재시작으로 안 되는 거 아냐?"라고 물었을 텐데, 스크립트는 그 질문을 하지 않습니다. 그 질문을 코드로 미리 적어 두는 게 상한이에요.

그래서 자동 복구에는 조치 자체보다 멈추는 조건이 더 중요합니다. 다섯 가지를 함께 둬요.

1. 횟수 상한 같은 대상에 정해진 창 안에서 N번까지만 (예: 30분에 3번) 2. 효과 확인 조치 뒤 일정 시간 안에 증상이 다시 나오면 "효과 없음"으로 센다 3. 범위 상한 한 번에 전체의 일부만 (예: 인스턴스의 25%). 빈 목록이나 전부는 거부 4. 사람에게 넘기기 1~3 중 하나라도 걸리면 조치를 멈추고 사람을 부르는 경고를 보낸다 5. 기록 조치마다 시각, 대상, 이유, 결과를 남긴다. 사후 분석의 재료가 된다

다섯 가운데 4번이 핵심이에요. 자동화가 안전하지 않은 조건을 만나면 기본값으로 사람 운영자에게 넘겨야 하고(SRE Workbook, Eliminating Toil), 넘길 때는 "자동 조치를 세 번 했는데 30분 안에 다시 났다"는 사실 자체를 알림에 담습니다. 사람은 그 문장을 보고 "재시작으로는 안 되는 장애"라는 것부터 알고 시작해요.

이 상한은 이미 많은 시스템에 들어 있습니다. Kubernetes는 컨테이너가 계속 죽으면 다시 띄우는 간격을 10초, 20초, 40초로 늘리고, 간격이 300초에 닿으면 더 늘리지 않은 채 재시작을 계속합니다. 10분 동안 문제없이 돌면 간격을 처음으로 되돌려요(Kubernetes 문서, Pod Lifecycle). Docker 재시작 정책의 on-failure에는 재시도 횟수 상한을 붙일 수 있고요(Docker 문서). 둘 다 "계속 다시 해 보되, 점점 덜 자주" 또는 "몇 번까지만"이라는 같은 생각입니다. 직접 만드는 자동 복구에도 같은 장치를 둬야 해요.

경고 쪽에도 숨은 상한이 하나 있어요. Alertmanager는 같은 경고 묶음의 후속 알림을 group_interval(기본 5분)마다, 변화 없이 계속 울리는 경고의 재알림을 repeat_interval(기본 4시간)마다 보냅니다(Prometheus 문서, Alertmanager Configuration). 웹훅을 받아 움직이는 자동 복구는 이 간격보다 자주 깨어나지 않아요. 기본값이라면 같은 경고 묶음에 대해 많아야 5분에 한 번이고, 이 간격을 줄이면 자동 복구의 회전도 빨라집니다. 다만 "많아야"는 상한일 뿐 5분마다 계속 돈다는 뜻은 아니에요. 실습-2에서 기본값으로 돌려 보니 자동 복구는 한 번 재시작한 뒤 멈췄습니다. 경고가 해결됐다가, 그 해결을 알릴 다음 group_interval 틱이 오기 전에 같은 라벨로 다시 울려서 Alertmanager가 "지난번에 알린 그 경고가 아직 울리는 중"으로 보았기 때문이에요. 그 뒤 실행이 끝날 때까지 약 547초 동안 알림이 0건이었고, 소스대로라면 repeat_interval(4시간)까지 다시 깨어나지 않습니다. 간격을 줄인 설정에서는 10분 동안 75~80초 간격으로 8번 재시작했어요. 실습-2의 자동 복구기에는 다섯 장치 중 횟수 상한, 사람에게 넘기기, 기록이 들어갔습니다. 효과 확인은 "효과 없음"을 기록만 하고 판단에는 쓰지 않았고, 범위 상한은 대상이 하나라 넣지 않았어요. 그래서 실습-2가 센 것은 횟수 상한이 만든 차이입니다.

💡 실무에서는
• 절차서를 코드로 옮길 때 "이미 있으면 중단"은 단계마다의 "원하는 상태인가?"로 바꿔요
• DB에는 UNIQUE 제약을, 파일은 전체를 다시 만들어 임시 파일과 rename으로 바꿔요
• 스크립트 맨 위에 flock -n을 두고, 여러 호스트에서 돌 수 있으면 잠금을 DB나 작업 큐로 옮겨요
• 설정 반영은 검사(nginx -t) 후 reload. stop/start는 다시 읽기를 지원하지 않을 때만, 그때도 한 대씩
• 드라이런은 diff를 보여 주는 용도로 쓰고, diff가 지나치게 크면 적용하지 않고 멈춰요
• 끝에 결과 검증(새 경로가 200인가)을 두고, 실패하면 0이 아닌 종료 코드로 끝내요
• 자동 복구에는 횟수 상한, 효과 확인, 범위 상한, 사람에게 넘기기, 기록을 같이 둬요
✍️ 오늘의 요약
절차서를 코드로 옮긴 스크립트는 두 번 돌려도, 중간에 끊겼다 다시 돌려도, 동시에 두 개가 돌아도 같은 결과여야 해요. "이미 있으면 중단"은 첫 단계만 보고 전체를 판단해서, 끊긴 실행을 반쯤 된 채로 남기고 동시 실행은 막지 못합니다. 단계마다 원하는 상태와 비교해 다른 부분만 맞추는 수렴형으로 바꾸면 다시 돌리기가 곧 복구가 되고, 드라이런도 믿을 만해져요.

동시 실행은 시스템 제약(UNIQUE), 프로세스 잠금(flock), 여러 호스트라면 공유 잠금으로 막고, 설정 반영은 멈췄다 켜지 않고 검사 후 다시 읽혀요. 사람 없이 도는 자동 복구에는 횟수와 범위의 상한, 그리고 상한에 닿으면 사람을 부르는 길이 조치보다 먼저 있어야 합니다. 자동화의 안전은 무엇을 하느냐보다 언제 하지 않느냐에서 나와요.
