쿠버네티스 아키텍처를 공부하던 날 제 메모에는 "Calico에서 BIRD가 중요하대"라는 줄이 있어요. 6편에서 Calico를 설치하고 노드마다 파드 IP용 /26 블록이 생기는 것까지는 봤지만 그 블록으로 가는 경로를 누가 만드는지는 들여다보지 않았어요. 그래서 worker1의 calico-node 안에서 다른 노드와 BGP로 경로를 주고받는 BIRD에게 상태를 물었더니 BGP 세션 세 개가 모두 Established였어요. 나머지 노드 세 대와 BGP로 연결돼 있다는 뜻이에요.

그렇다면 BIRD를 멈추면 다른 노드로 가는 파드 통신이 끊겨야 맞아요. worker3의 calico-node 안에서 sv stop bird로 BIRD만 멈추고 worker1에서 worker3의 myweb 파드(10.244.100.222)로 몇 초 간격으로 curl을 보냈어요. 그런데 15:21:44부터 15:23:25까지 보낸 요청 15번이 모두 HTTP 200을 받았어요. 반대로 BIRD는 그대로 두고 worker1의 라우팅 표에서 worker3 블록으로 가는 경로 한 줄을 지우자 바로 다음 요청이 실패했어요. 그 경로는 37초 안에 저절로 다시 생겼어요. 경로를 넣는 쪽은 BIRD가 아니었던 거예요.

메모의 다음 줄은 "calicoctl도 있대"였어요. calicoctl을 설치해 BGP 상태를 보려 했더니 calicoctl node status는 Calico 프로세스가 멀쩡히 떠 있는데도 Calico process is not running.이라고 답했어요. 이번 글에서는 세 장면이 왜 그렇게 됐는지 차례로 따라가 봐요. 클러스터는 Lima VM 4대(k8s-master, k8s-worker1~3)에 kubeadm v1.37.2와 Calico v3.33.0(매니페스트 설치, IPIP Always)을 올린 실습 환경이에요.

이 글에서 다룰 것
· calico-node 파드 안에서는 어떤 프로세스가 돌고 BIRD는 무슨 일을 할까?
· 노드 네 대는 BGP로 무엇을 주고받을까?
· worker3의 BIRD를 멈추면 무엇이 바뀌고 무엇이 그대로일까?
· 노드 간 파드 경로를 지우면 누가 다시 넣을까? 예전 버전과는 무엇이 다를까?
· calicoctl은 어떻게 설치하고 node status가 not running이라고 하면 BGP 상태를 어디서 볼까?

1. calico-node 파드 하나에 BIRD와 Felix가 같이 떠 있다

calico-node는 노드마다 하나씩 뜨는 DaemonSet 파드예요(6편). 이 파드는 프로그램 하나만 돌리지 않아요. worker1에서 관련 프로세스를 골라 보면 이렇게 나와요.

worker1$ ps -eo pid,ppid,args | grep -E 'bird|felix|confd|runsv' | grep -v grep 2415 1873 /usr/local/bin/runsvdir -P /etc/service/enabled 2508 2415 runsv confd 2509 2415 runsv bird 2510 2415 runsv bird6 2511 2415 runsv node-services 2512 2415 runsv felix 2513 2512 calico component felix 2517 2508 calico component confd 2674 2510 bird6 -R -s /var/run/calico/bird6.ctl -d -c /etc/calico/confd/config/bird6.cfg 2675 2509 bird -R -s /var/run/calico/bird.ctl -d -c /etc/calico/confd/config/bird.cfg

→ runsvdir가 서비스마다 runsv를 하나씩 띄우고 각 runsv가 confd, bird, bird6, node-services, felix를 맡아 돌린다는 뜻이에요. bird는 /etc/calico/confd/config/bird.cfg를 설정 파일로 읽고 /var/run/calico/bird.ctl 소켓으로 명령을 받아요. bird6은 IPv6용 BIRD이고 이 클러스터는 IPv4만 써요.

📖 용어: runsvdir·runsv·sv (runit)
runit이라는 프로세스 관리 도구에 들어 있는 프로그램들이에요. runsvdir는 디렉터리 안의 서비스마다 runsv를 하나씩 띄우고 runsv는 맡은 프로그램이 끝나면 다시 띄워요. sv는 서비스를 멈추거나(sv stop) 상태를 묻는(sv status) 명령이에요. sv로 멈춘 서비스는 runsv가 다시 띄우지 않아요.

세 프로세스가 맡은 일은 Calico 구성 요소 문서에 정리돼 있어요. Felix는 노드마다 돌면서 경로와 ACL(접근 제어 규칙)을 커널에 넣는 에이전트예요. 문서에는 Felix의 주 업무가 "그 노드의 엔드포인트에 필요한 연결을 위해 경로, ACL, 그 밖에 필요한 것을 호스트에 프로그래밍한다"라고 적혀 있어요. BIRD는 경로를 BGP 상대(BGP로 연결된 다른 노드나 라우터)에게 나눠 주는 BGP 데몬이에요. BIRD의 주 업무는 "Felix에게서 경로를 받아 노드 사이 라우팅을 위해 BGP 상대에게 나눠 준다"라고 적혀 있어요. confd는 Calico 데이터스토어(이 클러스터에서는 쿠버네티스 API)에서 AS 번호나 IPAM(IP 주소 관리) 정보 같은 값이 바뀌는지 지켜보다가 BIRD 설정 파일을 새로 만들고 BIRD가 그 파일을 다시 읽게 해요. 정리하면 confd는 BIRD의 설정 파일을 만들고 BIRD는 다른 노드와 경로를 주고받고 Felix는 커널에 경로와 ACL을 넣어요.

📖 용어: BGP와 AS 번호
BGP(Border Gateway Protocol)는 라우터끼리 "이 주소 대역은 나에게 보내라"는 경로 정보를 주고받는 표준 프로토콜이에요. TCP 179번 포트로 연결을 맺어요. AS(Autonomous System) 번호는 한 조직이 관리하는 라우터 묶음에 붙이는 번호이고 AS 번호가 같은 라우터끼리 맺는 BGP를 iBGP라고 해요. Calico에서는 각 노드의 BIRD가 BGP로 자기 노드의 파드 블록을 알려요.

BIRD가 중요하다는 메모는 적어도 한 군데에서는 그대로 맞아요. calico-node DaemonSet의 상태 검사 명령을 보면 이래요.

mac$ kubectl -n kube-system get ds calico-node -o jsonpath='readiness: {.spec.template.spec.containers[0].readinessProbe.exec.command}{"\n"}liveness: {.spec.template.spec.containers[0].livenessProbe.exec.command}{"\n"}' readiness: ["calico","component","node","health","--felix-ready","--bird-ready"] liveness: ["calico","component","node","health","--felix-live","--bird-live"]

→ kubelet이 이 명령으로 calico-node의 준비 상태와 생존 상태를 판정하는데 두 검사 모두에 BIRD 항목(--bird-ready, --bird-live)이 들어 있다는 뜻이에요. BIRD가 멈춘 채로 있으면 calico-node 파드 자체가 준비되지 않은 상태가 되고 결국 재시작돼요. 3절에서 실제로 이 일이 일어나요.

📖 용어: 준비 검사(readinessProbe)와 생존 검사(livenessProbe)
kubelet이 컨테이너마다 정해진 주기로 돌리는 검사예요. 쿠버네티스 문서에 따르면 준비 검사가 실패하면 그 파드는 Service의 EndpointSlice에서 빠지고 READY가 0/1로 보여요. 생존 검사가 허용한 횟수만큼 연달아 실패하면 kubelet이 컨테이너를 다시 시작해요.

2. 노드 네 대는 BGP full mesh로 서로의 /26 블록을 알린다

calico-node 컨테이너 안에는 BIRD 소켓에 명령을 보내는 birdcl이 들어 있어요. worker1의 calico-node에서 birdcl로 BGP 세션 목록을 확인했어요.

그림 1. worker1의 BIRD는 다른 노드 세 대와 BGP 세션을 하나씩 맺고 있었다

proto 열이 BGP인 세 줄이 BGP 세션이에요. 이름 끝이 상대 노드의 IP라서 Mesh_192_168_104_1은 master, _4는 worker2, _5는 worker3과 맺은 세션이에요. 셋 다 state가 up이고 info가 Established예요. 연결이 맺어져 경로를 주고받는 중이라는 뜻이에요. 그 위의 static1, kernel1, device1, direct1은 BGP가 아니에요. BIRD가 노드 자신의 정적 경로, 커널 라우팅 표, 네트워크 장치를 읽고 쓰기 위한 내부 프로토콜이에요. since 열의 05:42:00은 UTC라서 한국 시각으로는 14:42예요.

TCP 연결로 봐도 같아요. worker1에서 179번 포트를 쓰는 연결은 세 개였어요.

worker1$ sudo ss -tn state established '( sport = :179 or dport = :179 )' Recv-Q Send-Q Local Address:Port Peer Address:Port Process 0 0 192.168.104.3:179 192.168.104.4:46705 0 0 192.168.104.3:179 192.168.104.5:37173 0 0 192.168.104.3:52777 192.168.104.1:179

→ worker2(.4)와 worker3(.5)는 worker1의 179번 포트로 연결해 들어왔고 worker1은 master(.1)의 179번 포트로 연결해 나갔다는 뜻이에요. 방향은 달라도 상대 노드마다 연결이 하나씩이에요.

📖 용어: BGP full mesh (node-to-node mesh)
모든 노드가 다른 모든 노드와 BGP 세션을 하나씩 맺는 구성이에요. Calico BGP 문서에 따르면 Calico는 BGP를 켜면 기본으로 이 구성(iBGP full mesh)을 만들고 노드 100대 정도까지는 이 구성으로 잘 동작해요. 세션 수는 노드가 N대일 때 N(N-1)/2개로 늘어요. 문서는 그보다 훨씬 큰 규모에서는 full mesh가 비효율적이라며 route reflector를 권해요.
그림 2. 노드 4대면 세션은 6개이고 worker1이 맺은 것은 그중 3개다

세션으로 주고받는 것은 각 노드가 할당받은 파드 블록이에요. worker1의 BIRD 경로 표에서 다른 노드의 블록만 골라 보면 이래요.

worker1$ birdcl -s /var/run/calico/bird.ctl show route # 다른 노드의 블록만 발췌 10.244.235.192/26 via 192.168.104.1 on eth0 [Mesh_192_168_104_1 05:42:00] * (200/0) [i] via 192.168.104.1 on eth0 [Mesh_192_168_104_1 05:42:00] (100/0) [i] via 192.168.104.1 on tunl0 [kernel1 05:41:59] (10) 10.244.126.0/26 via 192.168.104.4 on eth0 [Mesh_192_168_104_4 05:42:00] * (200/0) [i] via 192.168.104.4 on eth0 [Mesh_192_168_104_4 05:42:00] (100/0) [i] via 192.168.104.4 on tunl0 [kernel1 05:41:59] (10) 10.244.100.192/26 via 192.168.104.5 on eth0 [Mesh_192_168_104_5 05:42:00] * (200/0) [i] via 192.168.104.5 on eth0 [Mesh_192_168_104_5 05:42:00] (100/0) [i] via 192.168.104.5 on tunl0 [kernel1 05:41:59] (10)

→ 블록마다 그 블록을 가진 노드와 맺은 세션(Mesh_…)에서 받은 경로가 있고 같은 블록에 kernel1에서 온 줄도 하나씩 있다는 뜻이에요. kernel1 줄은 BIRD가 커널 라우팅 표를 읽어서 알게 된 경로예요. 이 줄이 무엇을 뜻하는지는 4절에서 다시 봐요.

커널 라우팅 표에는 6편에서 본 네 줄이 그대로 있어요.

worker1$ ip route | grep -E 'bird|blackhole|tunl0' 10.244.100.192/26 via 192.168.104.5 dev tunl0 proto 80 onlink mtu 1480 10.244.126.0/26 via 192.168.104.4 dev tunl0 proto 80 onlink mtu 1480 blackhole 10.244.194.64/26 proto 80 10.244.235.192/26 via 192.168.104.1 dev tunl0 proto 80 onlink mtu 1480

→ 다른 노드의 블록으로 가는 패킷은 그 노드의 eth0 주소를 거쳐 tunl0(IPIP)으로 보내고 자기 블록은 blackhole로 막아 둔다는 뜻이에요. tunl0, mtu 1480, blackhole의 뜻은 6편에서 다뤘어요. 6편에서 그냥 지나친 것은 줄마다 붙은 proto 80이에요. 이 숫자가 이 경로를 누가 넣었는지 알려 줘요. 실제로 worker1에서 worker3의 myweb 파드(10.244.100.222)로 가는 경로를 물으면 via 192.168.104.5 dev tunl0이 나오고 이때 보낸 curl은 HTTP 200을 받았어요.

3. worker3의 BIRD를 멈춰도 curl은 계속 200이었다

첫 번째 실험이에요. worker3의 블록은 10.244.100.192/26이고 그 안에 myweb 파드 10.244.100.222가 있어요. 실험 스크립트는 worker3의 calico-node 안에서 sv stop bird를 실행한 뒤 몇 초 간격으로 네 가지 값을 한 줄에 함께 찍었어요. worker1 커널에 있는 worker3 블록 경로, worker1의 BIRD가 보는 worker3 세션 상태, worker1에서 그 파드로 보낸 curl의 응답 코드, worker3 calico-node 파드의 READY와 재시작 횟수예요.

→ worker3의 BIRD가 내려가면서 "관리자가 세션을 내린다(Administrative shutdown)"는 알림을 보냈고 worker1의 BIRD는 세션을 닫은 뒤 그 세션으로 받았던 worker3 블록 경로 두 줄을 자기 표에서 지웠다는 뜻이에요. 그 뒤 세션은 상대가 다시 붙기를 기다리는 상태(start, Passive)로 있다가 다시 맺어졌어요.

BGP 쪽만 보면 worker1의 BIRD 표에서 worker3의 블록이 사라졌어요. 그런데 커널 라우팅 표의 10.244.100.192/26 via 192.168.104.5 dev tunl0 proto 80은 한 글자도 바뀌지 않았고 curl도 계속 200이었어요. 패킷이 나갈 경로는 BIRD의 표가 아니라 커널 라우팅 표가 정해요. BIRD의 표에서 경로가 빠져도 커널에 경로가 남아 있으면 파드 통신은 끊기지 않아요. 커널 경로가 그대로 남은 것은 그 경로를 넣은 쪽이 BIRD가 아니었기 때문이에요. 누가 넣었는지는 다음 절에서 확인해요.

파드는 0/1이 됐다가 재시작됐다

대신 worker3 calico-node 파드의 상태가 바뀌었어요. BIRD를 멈춘 지 25초 뒤에 확인했을 때 READY가 0/1이었고 58초 뒤에는 재시작 횟수가 8에서 9로 늘어 있었어요. 검사 주기와 맞춰 보면 이유가 보여요.

readiness: {"exec":{"command":["calico","component","node","health","--felix-ready","--bird-ready"]},"failureThreshold":3,"periodSeconds":10,"successThreshold":1,"timeoutSeconds":10} liveness: {"exec":{"command":["calico","component","node","health","--felix-live","--bird-live"]},"failureThreshold":6,"initialDelaySeconds":10,"periodSeconds":10,"successThreshold":1,"timeoutSeconds":10}

→ 준비 검사는 10초마다 돌고 세 번 연달아 실패하면 파드를 준비되지 않은 상태로 바꾼다는 뜻이에요. 생존 검사도 10초마다 돌고 여섯 번 연달아 실패하면 컨테이너를 다시 시작해요. 실패가 쌓이기까지 각각 대략 30초와 60초가 걸리니 25초 확인과 58초 확인에서 본 변화와 맞아요.

검사가 무엇을 보는지는 v3.33.0 소스(node/pkg/health/health.go)에 있어요. --bird-live는 sv status로 confd와 bird 서비스가 run 상태인지 보고 birdcl show status에 BIRD가 답하는지 확인해요. --bird-ready는 BIRD 소켓에 붙어 BGP 상대 목록과 상태를 가져와요. BIRD를 sv stop으로 멈췄으니 두 검사 모두 실패했어요. 생존 검사에 걸려 컨테이너가 다시 시작되자 BIRD도 새 컨테이너에서 처음부터 다시 떴고 66초 뒤 확인에서 세션이 Established로 돌아왔어요. 스크립트가 75초 지점에 보낸 sv start bird의 응답은 ok: run: bird: (pid 202) 17s였어요. 그보다 17초 전부터 BIRD가 이미 돌고 있었다는 뜻이에요.

4. 경로 한 줄을 지우자 바로 끊겼고 37초 안에 다시 생겼다

두 번째 실험은 반대예요. BIRD는 그대로 두고 worker1의 커널 라우팅 표에서 worker3 블록으로 가는 경로만 지웠어요.

그림 4. 경로를 지우자 패킷이 기본 경로(lima1)로 빠졌고 15:24:25 확인에서 같은 경로가 돌아와 있었다

지운 직후 ip route get 10.244.100.222의 답이 via 192.168.64.1 dev lima1로 바뀌었어요. worker3 블록으로 가는 경로가 없어지자 기본 경로를 탄 거예요. lima1은 Mac 쪽으로만 통하는 NIC라서(3편) 이 경로로는 worker3에 닿지 않아요. curl은 1초 제한 안에 응답을 하나도 받지 못해 000을 찍었어요. 이 값은 HTTP 상태 코드를 받기 전에 요청이 끝났다는 뜻이에요.

그 뒤 0.5초 간격으로 열 번 확인했을 때와 15:24:00부터 5초 간격으로 확인했을 때 모두 15:24:20까지는 경로가 없었어요. 15:24:25에 확인했을 때 지우기 전과 같은 줄(via 192.168.104.5 dev tunl0 proto 80 onlink mtu 1480)이 다시 보였어요. 경로를 지운 15:23:48부터 따지면 약 32~37초 사이에 다시 생긴 거예요. 15:25:12에 보낸 curl은 다시 200을 받았어요.

누가 다시 넣었나: proto 80, BIRD의 필터, FelixConfiguration

단서는 세 가지예요. 이 실험 뒤에 같은 클러스터에서 경로를 누가 넣는지 알려 주는 설정만 따로 모아 봤어요.

그림 5. BIRD는 파드 대역을 BGP 상대에게는 내보내고 커널에는 넣지 않는다. 커널의 그 경로는 모두 proto 80이다

첫째, 경로에 붙은 proto 80이에요. FelixConfiguration 문서의 표현을 빌리면 리눅스 경로의 proto는 "경로의 주인을 알아보는 데 쓰는 8비트 표시"예요. Felix 소스(v3.33.0 dataplane_defs.go)에는 DefaultRouteProto netlink.RouteProtocol = 80이 정의돼 있어요. 같은 버전의 route_mgr.go에서는 IPIP 경로와 blackhole 경로에 이 값을 붙이는데 주석에 그 이유가 적혀 있어요. Felix 설정의 기본 표시인 RTPROT_BOOT(3)는 다른 프로세스도 쓸 수 있으니 더 안전한 값을 고른다는 내용이에요. worker1에서 ip route show proto 80을 실행했더니 다른 노드의 블록 세 줄과 자기 블록의 blackhole 한 줄이 나왔고 ip route show proto bird는 0줄이었어요.

둘째, BIRD 설정의 필터예요. confd가 만든 bird_ipam.cfg에는 필터가 둘 있어요. BGP 상대에게 경로를 내보내는 calico_export_to_bgp_peers는 10.244.0.0/16 안의 경로를 accept하고 커널로 경로를 내보내는 calico_kernel_programming은 같은 대역을 reject해요. reject하는 줄에는 Cluster routes are handled by Felix.라는 주석이 달려 있어요. BIRD는 파드 대역을 다른 노드에 알리기는 하지만 커널에 넣지는 않는다는 뜻이에요. 2절의 BIRD 표에서 블록마다 보였던 kernel1 줄은 Felix가 커널에 넣은 경로를 BIRD가 읽어 온 거예요.

셋째, Felix의 설정 리소스인 FelixConfiguration이에요. Calico가 처음 뜰 때 만든 FelixConfiguration default(생성 시각 2026-11-04T12:21:43Z, 손대지 않았어요)에 programClusterRoutes: EnabledIPIPOnly가 들어 있고 BGPConfiguration default에는 programClusterRoutes: EnabledNoEncapOnly가 들어 있어요. 이 값의 뜻은 다음 절에서 봐요.

약 32~37초라는 시간은 Felix 설정 하나와 견줘 볼 수 있어요. FelixConfiguration 문서의 routeRefreshInterval은 "다른 프로세스가 실수로 Calico의 규칙을 망가뜨리지 않았는지 Felix가 데이터플레인의 경로를 다시 확인하는 주기"이고 기본값은 1m30s예요. 이 클러스터에서는 이 값을 따로 정하지 않았어요. 32~37초는 이 주기 안에 들어가요. 다만 Felix가 정확히 어떤 계기로 그 순간에 경로를 다시 넣었는지는 로그로 확인하지 못했어요.

그림 6. BIRD를 멈추면 BGP 쪽만 비고 커널 경로를 지우면 통신이 바로 끊긴다

두 실험을 나란히 놓고 보면 Felix와 BIRD의 역할이 나뉘어요. worker1의 커널에 노드 간 파드 경로를 넣는 것은 Felix였고 BIRD는 그 대역을 BGP 상대에게 알리기만 했어요.

5. Calico 3.33부터 IPIP 풀의 노드 간 경로는 Felix가 넣는다

"BIRD가 노드 간 경로를 넣는다"는 설명은 예전 버전에서는 맞았어요. Calico 3.32의 FelixConfiguration 문서를 보면 programClusterRoutes는 Disabled와 Enabled 두 값만 받고 기본값은 Disabled예요. 설명에는 "Disabled면 confd와 BIRD가 그 경로를 넣는다고 본다"라고 적혀 있어요. 3.32까지는 기본값 그대로 IPIP 풀을 쓰면 노드 간 경로를 BIRD가 넣었다는 뜻이에요.

3.33에서 이 기본값이 바뀌었어요. 3.33 릴리스 노트에는 이렇게 적혀 있어요.

Felix, rather than BIRD, programs the cluster routes for IPIP IP Pools by default. BIRD programming of IPIP cluster routes is deprecated and is intended for removal in v3.35.

→ 이제 기본 설정에서는 IPIP 풀의 노드 간 경로(cluster route)를 BIRD가 아니라 Felix가 넣는다는 뜻이에요. BIRD가 IPIP 경로를 넣는 방식은 폐기 예정이고 v3.35에서 없앨 계획이에요.

📖 용어: cluster route
한 노드에서 다른 노드에 있는 파드로 가려면 필요한 경로예요. 2절의 커널 라우팅 표에서 다른 노드의 /26 블록으로 가는 세 줄이 여기에 해당해요. Calico 문서는 이 경로를 cluster route라고 불러요. 누가 넣을지는 FelixConfiguration과 BGPConfiguration의 programClusterRoutes로 정해요.

3.33의 FelixConfiguration 문서를 보면 programClusterRoutes가 받는 값이 넷으로 늘었고 기본값은 EnabledIPIPOnly예요. 이 설정은 vxlanMode가 Never인 풀에만 적용되고 VXLAN 풀의 경로는 원래부터 항상 Felix가 넣어요.

FelixConfiguration 값Felix가 경로를 넣는 풀이 클러스터
Disabled없음 (3.32까지의 기본값)
EnabledIPIPOnlyIPIP 풀 (3.33 기본값)FelixConfiguration default
EnabledNoEncapOnly캡슐화하지 않는 풀
EnabledIPIP 풀과 캡슐화하지 않는 풀 모두

같은 문서에는 경고도 있어요. 이 값은 BIRD가 어떤 풀의 경로를 넣을지 정하는 BGPConfiguration의 programClusterRoutes와 짝이 맞아야 해요. "같은 종류의 풀을 Felix와 BIRD가 모두 맡으면 경로를 두고 싸우고 둘 다 맡지 않으면 cluster route가 아예 없다"라고 적혀 있어요. 그리고 IPIP 경로를 BGP에 맡기는 값(Disabled, EnabledNoEncapOnly)은 v3.33부터 폐기 예정이고 v3.35에서 없앤다고 해요. 이 클러스터는 FelixConfiguration이 EnabledIPIPOnly, BGPConfiguration이 EnabledNoEncapOnly예요. IPIP 풀은 Felix가, 캡슐화하지 않는 풀은 BIRD가 맡는 짝이라서 맡는 풀이 겹치지도 않고 비지도 않아요. 이 클러스터의 풀은 IPIP 하나뿐이니 노드 간 경로는 모두 Felix가 넣어요.

그림 7. 3.32까지의 기본값에서는 BIRD가 넣던 IPIP 경로를 3.33부터는 Felix가 넣고 BIRD는 BGP로 알리기만 한다

Felix가 경로를 계산할 때 쓰는 정보도 BGP에서 오지 않아요. FelixConfiguration 문서를 보면 routeSource의 기본값은 CalicoIPAM이고 "IPAM 데이터로 경로를 만든다"는 설명이 붙어 있어요. Calico 데이터스토어에는 10.244.100.192/26 블록이 worker3 것이라는 기록(31편에서 볼 IPAM 블록과 BlockAffinity)이 그대로 있었어요. 그래서 worker3의 BIRD가 BGP 세션을 내려도 worker1의 Felix는 그 블록으로 가는 경로를 지우지 않았고 누가 경로를 지워도 다시 넣었어요.

그렇다고 BIRD가 할 일이 없어진 것은 아니에요. 지금 이 클러스터에서 BIRD가 맡은 일은 이래요.

· 노드끼리 BGP 세션을 맺고 파드 블록을 서로 알려요(2절, calico_export_to_bgp_peers의 accept).
· 캡슐화하지 않는 풀이 생기면 그 풀의 경로는 BIRD가 넣어요(BGPConfiguration의 EnabledNoEncapOnly).
· 클러스터 밖 라우터(ToR 스위치 같은 장비)나 route reflector와 BGP로 연결할 때 경로를 알리는 것도 BIRD예요. 이 클러스터에서는 calicoctl get bgppeer 결과가 비어 있으니 밖과 맺은 세션은 없어요.
· calico_backend가 bird인 지금 설치에서는 calico-node의 준비 검사와 생존 검사가 BIRD 상태를 확인해요(3절).

Calico의 overlay 문서에도 "Felix가 cluster route를 넣는 경우 클러스터 안의 경로를 위해서는 BGP가 필요 없다. 다만 cluster route를 클러스터 밖 BGP 상대에게 알려야 한다면 여전히 BGP가 필요하다"라고 적혀 있어요. 3절에서 BGP 세션이 1분 넘게 끊겨 있는 동안에도 노드 간 통신이 그대로였던 결과와 맞는 설명이에요. 캡슐화하지 않는 풀이라면 BIRD가 경로를 넣으니 같은 실험의 결과가 다를 수 있어요. 그 구성은 이번에 실험하지 않았어요.

⚠️ 주의: 같은 3.33 문서에도 예전 설명이 남은 곳이 있어요
• 위에서 인용한 overlay 문서의 "Cluster route programming" 절에는 바로 앞 문장에 "기본으로 Felix는 VXLAN 풀의 경로를 넣고 IP-in-IP 풀과 캡슐화하지 않는 풀의 경로는 BGP가 나눠 준다"라고 적혀 있고 operator 설치의 clusterRoutingMode 기본값도 BIRD라고 나와 있어요(2026-11-14 확인)
• 같은 3.33의 Installation API 레퍼런스에는 clusterRoutingMode를 비워 두면 operator가 두 programClusterRoutes 값을 따로 설정하지 않아 Calico 기본값을 따르고 v3.33의 기본값은 FelixIPIPOnly와 같다고 적혀 있어요. FelixConfiguration 문서, 릴리스 노트, 이 클러스터의 실제 값도 이쪽과 맞아요
• 문서 문장 하나를 믿기보다 내 클러스터의 FelixConfiguration·BGPConfiguration 값과 노드의 ip route show proto 80을 직접 보세요
💡 실무에서는: Calico를 3.33 이상으로 올릴 때 확인할 것
• kubectl get felixconfigurations.crd.projectcalico.org default -o jsonpath='{.spec.programClusterRoutes}'와 BGPConfiguration의 같은 값을 읽어 같은 종류의 풀을 양쪽이 모두 맡거나 아무도 맡지 않는 짝이 아닌지 봐요
• FelixConfiguration에 Disabled나 EnabledNoEncapOnly를 직접 적어 뒀다면 IPIP 경로를 BIRD 쪽에 맡기고 있는 거예요. v3.35에서 없앨 동작이니 Felix 쪽으로 옮길 계획을 세워요
• operator로 설치했다면 Installation의 calicoNetwork.clusterRoutingMode(BIRD, Felix, FelixIPIPOnly)를 봐요
• 올린 뒤에는 노드에서 ip route show proto 80과 ip route show proto bird로 cluster route를 실제로 누가 넣었는지 확인해요

6. calicoctl로 Calico 상태를 보고 BGP는 birdcl로 확인한다

설치: 클러스터의 Calico와 같은 버전으로

calicoctl 설치 문서는 calicoctl을 "Calico 정책과 설정을 관리하고 자세한 클러스터 상태를 보는" 도구로 소개하고 이렇게 당부해요.

Make sure you always install the version of calicoctl that matches the version of Calico running on your cluster.

→ 클러스터에서 도는 Calico와 같은 버전의 calicoctl을 설치하라는 뜻이에요. 이 클러스터는 v3.33.0이라서 같은 버전의 arm64 실행 파일을 GitHub 릴리스에서 받아 마스터의 /usr/local/bin에 두었어요. 파일 크기는 93,456,621바이트(약 89MiB)였어요. 3.33 릴리스 노트에 따르면 이제 Calico 패키지 저장소에서 Debian·Ubuntu와 RPM 패키지로도 받을 수 있어요.

master# curl -fsSL -o /usr/local/bin/calicoctl \ https://github.com/projectcalico/calico/releases/download/v3.33.0/calicoctl-linux-arm64 master# chmod +x /usr/local/bin/calicoctl master# ls -l /usr/local/bin/calicoctl | awk '{print $1, $5, $NF}' -rwxr-xr-x 93456621 /usr/local/bin/calicoctl

calicoctl은 따로 설정하지 않으면 기본 kubeconfig로 쿠버네티스 API를 읽어요(설정 문서). 이번에 둘러볼 때는 DATASTORE_TYPE=kubernetes와 KUBECONFIG를 환경 변수로 줬어요.

둘러보기

그림 8. 버전은 클라이언트와 클러스터가 같았고 node status만 엉뚱한 답을 냈다

calicoctl version은 클라이언트와 클러스터가 모두 v3.33.0이라고 답했어요. Cluster Type의 kdd는 Calico가 데이터를 쿠버네티스 API에 저장한다(Kubernetes API datastore)는 표시예요. calicoctl get nodes -o wide의 ASN 열은 네 노드 모두 (64512)예요. calicoctl v3.33.0 소스(calicoctl/calicoctl/resourcemgr/node.go와 commands/common/printer.go)를 보면 노드에 AS 번호를 따로 정하지 않았을 때 괄호를 치고 BGPConfiguration의 값이나 기본값 64512를 보여 줘요. calicoctl get bgpconfig에서도 MESHENABLED와 ASNUMBER 칸이 비어 있었어요(-). BGPConfiguration 문서의 기본값대로 full mesh가 켜져 있고 AS 번호는 64512라는 뜻이에요. calicoctl get bgppeer는 빈 목록이었어요. calicoctl get ippool -o wide로는 풀 10.244.0.0/16이 NAT true, IPIPMODE Always, VXLANMODE Never인 것을 확인했어요. calicoctl ipam show와 ipam check는 31·34편에서 IPAM과 함께 봐요.

kubectl로 보는 것과 calicoctl로 보는 것

같은 IP 풀을 두 도구로 읽으면 apiVersion이 달라요. kubectl은 crd.projectcalico.org/v1, calicoctl은 projectcalico.org/v3로 보여 줘요. 그리고 이 클러스터의 쿠버네티스에는 projectcalico.org API 그룹으로 등록된 리소스가 0개였어요. Calico API 서버를 설치하지 않았다는 뜻이에요.

📖 용어: crd.projectcalico.org와 projectcalico.org
Calico 설정을 담는 두 API 그룹이에요. projectcalico.org/v3는 사용자가 다루라고 만든 API이고 crd.projectcalico.org/v1은 Calico가 쿠버네티스 CRD에 데이터를 저장할 때 쓰는 내부 표현이에요. Calico API 서버가 없는 이 클러스터에서는 쿠버네티스에 내부 표현 쪽만 보여서 kubectl로 읽으면 v1으로 나와요.

calicoctl 설치 문서에는 이 차이가 분명히 적혀 있어요. projectcalico.org/v3 리소스는 kubectl에 없는 검증과 기본값 채우기를 calicoctl이 해 주니 calicoctl로 다루라고 하면서 이런 주의를 붙였어요.

Never modify resources in the crd.projectcalico.org API group directly.

→ crd.projectcalico.org 그룹의 리소스는 내부 데이터 표현이니 직접 고치지 말라는 뜻이에요. 이 글에서는 FelixConfiguration과 BGPConfiguration을 kubectl로 읽기만 했어요. 고칠 때는 calicoctl이나 Calico API 서버를 거쳐야 해요.

calicoctl 설정 문서는 한 걸음 더 나가요. 새 버전에서는 Calico API 서버가 같은 검증과 기본값 채우기를 서버 쪽에서 해 주니 대부분의 작업은 API 서버를 설치하고 kubectl로 하라고 권해요. 그래도 calicoctl node, calicoctl ipam, calicoctl version을 쓰려면 calicoctl이 있어야 해요. 3.33 릴리스 노트에는 projectcalico.org/v3 API를 aggregation API 서버에서 쿠버네티스 네이티브 CRD로 옮기는 중이라는 내용도 있어요. 네이티브 v3 CRD를 쓰면 kubectl이 API 서버 없이 projectcalico.org/v3 리소스를 바로 다룰 수 있다고 해요.

node status가 "Calico process is not running."이라고 할 때

node status 레퍼런스에 따르면 이 명령은 그 노드의 Calico 상태와 BGP 상대 표를 보여 주고 상태를 보려는 노드에서 직접 실행해야 해요. 그래서 마스터에서 root로 실행했는데 첫 줄만 찍고 끝났어요.

master$ sudo calicoctl node status Calico process is not running. # 15:28:45 마스터의 프로세스 발췌 (pid, comm, args) 2684 runsv runsv bird 2688 calico calico component confd 2692 calico calico component felix 2865 bird bird -R -s /var/run/calico/bird.ctl -d -c /etc/calico/confd/config/bird.cfg

→ calicoctl은 Calico가 돌지 않는다고 했지만 마스터에는 felix, confd, bird가 모두 떠 있었다는 뜻이에요.

이유는 calicoctl v3.33.0 소스(calicoctl/calicoctl/commands/node/status.go)에 있어요. node status는 프로세스 목록에서 felix를 찾는데 찾는 이름이 둘뿐이에요.

// For older versions of calico/node, the process was called `calico-felix`. Newer ones use `calico-node -felix`. if !psContains([]string{"calico-felix"}, processes) && !psContains([]string{"calico-node", "-felix"}, processes) { ... return fmt.Errorf("Calico process is not running.") }

→ 프로세스 인자가 calico-felix이거나 calico-node -felix일 때만 Calico가 돈다고 본다는 뜻이에요. 1절에서 본 대로 3.33의 calico-node 안에서 felix는 calico component felix라는 인자로 떠요. 두 이름 중 어느 것과도 맞지 않으니 BIRD에 묻기도 전에 끝나 버려요. v3.33.0의 node status는 felix를 예전 프로세스 이름으로만 찾아서 Calico가 떠 있어도 not running이라고 답해요.

이 문제는 이미 고쳐졌어요. PR #14135(제목 "Calico node status not working on 3.33")가 2026-10-02에 기본 브랜치(master)에 커밋 a7d2026b7e "fix: calico node status (#14135)"로 들어갔어요. 조건에 psContains([]string{"calico", "component", "felix"}, processes) 한 줄을 더하는 수정이에요. 이 수정은 2026-11-04에 release-v3.33 브랜치로 옮겨졌고(#14483) v3.33.1 태그의 status.go에 들어 있어요. 하지만 이 글을 쓰는 2026-11-14 기준으로 GitHub 릴리스의 최신(Latest) 버전은 v3.33.0이에요. v3.33.1은 릴리스 페이지가 없고 calicoctl 실행 파일 주소도 404였어요. 클러스터와 같은 버전을 쓰라는 문서의 당부까지 생각하면 v3.33.1이 나오기 전까지 이 클러스터에서는 node status를 쓰기 어려워요.

그동안은 node status가 보여 주려던 정보를 BIRD에 직접 물으면 돼요. 그림 1의 birdcl show protocols 출력이 바로 그 정보예요. 레퍼런스 예시 출력의 PEER ADDRESS는 birdcl에서 Mesh_ 뒤의 이름으로 나오고 STATE, SINCE, INFO는 같은 이름의 열로 나와요.

💡 실무에서는: BGP 상태는 이렇게 확인해요
• kubectl -n kube-system exec <그 노드의 calico-node> -c calico-node -- birdcl -s /var/run/calico/bird.ctl show protocols로 Mesh_로 시작하는 줄이 모두 Established인지 봐요. full mesh라면 그 수가 노드 수보다 하나 적어야 해요
• 노드에서 ss -tn state established '( sport = :179 or dport = :179 )'로 179번 포트 연결 수를 함께 봐요
• calico-node가 READY 0/1이면 kubectl describe의 Events에서 Readiness probe failed 문구를 읽어요. 준비 검사에 Felix와 BIRD가 모두 들어 있으니 문구가 felix 쪽인지 BIRD 쪽인지 보면 원인을 가를 수 있어요
• v3.33.1 이상의 calicoctl이 나오면 sudo calicoctl node status를 그 노드에서 다시 써 볼 수 있어요
✍️ 오늘의 요약
Calico 3.33의 IPIP 풀에서 노드 간 파드 경로는 Felix가 넣고 BIRD는 그 블록을 BGP로 알려요.

calico-node 안에서는 runsvdir 아래 confd, BIRD, Felix가 함께 돌고 노드 네 대는 TCP 179로 BGP 세션 여섯 개를 맺어 서로의 /26 블록을 주고받았어요. worker3의 BIRD를 멈추자 worker1의 BIRD 표에서는 worker3 블록이 빠졌지만 커널의 proto 80 경로는 그대로라서 curl 15번이 모두 200이었어요. calico-node는 검사 주기대로 25초 확인에서 0/1이 됐고 58초 확인에서는 재시작돼 있었어요. 반대로 커널 경로를 지우자 curl이 바로 000을 찍었고 37초 안에 Felix가 경로를 다시 넣었어요. 3.32까지의 기본값에서는 BIRD가 넣던 경로를 3.33부터는 Felix가 넣어요. BIRD 쪽 IPIP 경로 기능은 v3.35에서 없앨 예정이니 Calico를 올릴 때는 FelixConfiguration과 BGPConfiguration의 programClusterRoutes 짝을 확인해요. calicoctl은 클러스터와 같은 버전으로 설치하고 v3.33.0의 node status 대신 birdcl show protocols로 BGP 상태를 봐요. 경로를 누가 넣었는지 알려면 문서의 설명보다 커널 라우팅 표의 proto부터 보는 편이 빨라요.
