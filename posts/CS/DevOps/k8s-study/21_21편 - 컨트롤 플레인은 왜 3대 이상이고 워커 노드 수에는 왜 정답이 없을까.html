1. 컨트롤 플레인을 여러 대로 두면 무엇이 여러 개가 될까

kubeadm의 HA 토폴로지 문서를 보면 컨트롤 플레인 노드마다 kube-apiserver, kube-scheduler, kube-controller-manager가 하나씩 떠요. 세 대로 만들면 이 셋이 세 벌 생기는 거예요. 그런데 세 벌이 모두 같은 방식으로 일하지는 않아요.

API 서버는 여러 대가 동시에 요청을 받아요. 워커 노드와 kubectl은 API 서버 앞에 둔 로드밸런서 주소로 붙고 로드밸런서가 요청을 살아 있는 API 서버로 나눠 보내요. Lease 문서에 따르면 API 서버는 저마다 kube-system에 apiserver-로 시작하는 Lease를 하나씩 만들어 자기가 떠 있다고 알려요. 그래서 이 Lease 개수로 API 서버가 몇 대인지 알 수 있어요.

컨트롤러 매니저와 스케줄러는 달라요. 같은 문서는 Lease가 kube-controller-manager와 kube-scheduler의 리더 선출에도 쓰인다고 설명해요. HA 구성에서는 두 구성 요소 모두 한 번에 인스턴스 하나만 실제로 일하고 나머지는 대기한다고 적혀 있어요. 20편에서 본 대로 컨트롤러는 원하는 상태와 현재 상태의 차이를 메우는 쪽인데 같은 컨트롤러가 둘 이상 동시에 움직이면 같은 차이를 여러 번 메우려 들 수 있어요. 그래서 리더 하나만 움직이게 한다고 저는 이해했어요.

📖 용어: 리더 선출과 Lease
Lease는 "지금 이 자리는 누가 쥐고 있고 언제 갱신했는지"를 적는 작은 API 객체예요(coordination.k8s.io 그룹). 컨트롤러 매니저와 스케줄러에서는 같은 이름의 Lease를 먼저 쥐고 계속 갱신하는 인스턴스가 리더가 되고 리더가 갱신을 멈추면 대기하던 다른 인스턴스가 그 Lease를 가져가요. 이 과정을 리더 선출(leader election)이라고 불러요.

우리 클러스터의 Lease를 보면 이 구조가 한 대짜리로 나타나요.

그림 1. 리더 Lease 둘은 모두 마스터가 쥐고 있고 API 서버 Lease는 하나뿐이다

kube-controller-manager와 kube-scheduler Lease의 주인(HOLDER)은 둘 다 lima-k8s-master로 시작해요. 경쟁할 다른 인스턴스가 없으니 마스터가 리더예요. 두 매니페스트 모두 leader-elect=true로 설정돼 있어서 다른 컨트롤 플레인 노드가 생기면 그대로 리더 선출에 들어가요. kube-controller-manager 문서에는 --leader-elect의 기본값이 true이고 "고가용성을 위해 구성 요소를 여러 개 띄울 때 켜라"는 설명이 있어요. DURATION 15는 --leader-elect-lease-duration의 기본값 15초예요. 문서는 이 값을 리더가 멈춘 뒤 다른 후보가 리더가 되기까지 걸릴 수 있는 최대 시간이라고 설명해요. API 서버 Lease는 apiserver-slupzodazdrbewijviwya35vwq 하나뿐이었어요. API 서버도 한 대라는 뜻이에요.

그림 2. 세 대가 되면 API 서버는 셋이 모두 일하고 컨트롤러 매니저와 스케줄러는 리더 하나만 일한다

2. 3대인 이유는 etcd가 과반이 동의해야 쓰기 때문이다

API 서버, 컨트롤러 매니저, 스케줄러만 보면 두 대로도 한 대가 죽었을 때 버틸 수 있을 것 같아요. 그런데 대수는 etcd가 정해요. etcd는 여러 멤버가 같은 데이터를 나눠 갖고 쓰기마다 멤버의 동의를 받아요.

📖 용어: 쿼럼 (quorum, 과반수)
쓰기를 확정하려면 동의해야 하는 최소 멤버 수예요. etcd FAQ는 멤버가 n개일 때 쿼럼을 (n/2)+1(소수점 아래는 버림)로 적어요. 클러스터 상태를 바꾸는 제안은 키·값 변경이든 멤버 변경이든 이 수만큼 동의를 받아야 반영돼요.

etcd FAQ의 "What is failure tolerance?" 절에는 멤버 수별로 과반과 견딜 수 있는 장애 수를 적은 표가 있어요. 1부터 5까지 옮기면 이래요.

그림 3. 2대는 1대보다 나을 것이 없고 4대는 3대와 같은 1대까지만 견딘다

2대짜리 etcd는 과반이 2라서 한 대만 죽어도 쓰기를 확정하지 못해요. 견디는 장애는 1대짜리와 같은 0인데 죽을 수 있는 기계만 둘로 늘었어요. 4대는 과반이 3이라 견디는 장애가 3대와 같은 1대예요. FAQ는 멤버 수를 짝수로 맞추려고 하나를 더해도 견디는 장애 수는 늘지 않는다고 적어요. 홀수로 두면 네트워크가 갈라졌을 때도 계속 일할 수 있는 과반 쪽이 반드시 하나 생긴다는 점도 함께 들어요. 컨트롤 플레인을 2대가 아니라 3대로, 4대가 아니라 5대로 늘리는 이유는 etcd의 과반수 규칙이에요.

kubeadm 문서도 결론이 같아요. HA 토폴로지 문서는 stacked 구성에서 노드 하나가 죽으면 etcd 멤버와 컨트롤 플레인 인스턴스를 함께 잃는다고 설명한 뒤 "HA 클러스터라면 stacked 컨트롤 플레인 노드를 최소 3대 두라"고 적어요. kubeadm HA 구성 문서의 준비물에는 컨트롤 플레인 노드 수를 홀수로 두면 기계나 존에 장애가 났을 때 리더를 고르는 데 도움이 된다고 적혀 있어요. 더 늘릴 때의 기준은 etcd 운영 문서에 있어요. 이 문서는 운영 클러스터라면 멤버 5개로 고정한 etcd를 쓰라고 강하게 권하고 신뢰성을 더 원하면 3개에서 5개로 늘리는 것이 합리적이라고 해요. etcd FAQ는 멤버를 7개보다 많이 두지 않는 편이 좋다고 하고 멤버가 늘수록 쓰기 성능이 떨어진다는 점도 함께 적어요.

과반을 잃으면 어떻게 될까요? FAQ는 etcd가 과반을 모을 수 있는 동안만 동작한다고 해요. 과반이 깨지면 새 쓰기를 확정할 수 없으니 API 서버를 거치는 변경도 함께 멈춰요. 컨트롤 플레인이 여러 대여도 20편에서 본 "변경이 멈춘 상태"가 생길 수 있다는 뜻이에요.

3. kubeadm HA는 init 때 정한 공용 주소 하나에서 시작한다

kubeadm으로 HA 컨트롤 플레인을 만드는 방법은 etcd를 어디에 두느냐에 따라 둘로 나뉘어요. HA 토폴로지 문서의 설명을 표로 옮기면 이래요.

토폴로지etcd는 어디에좋은 점약점최소 대수
stacked etcd (kubeadm 기본)컨트롤 플레인 노드마다 etcd 멤버가 같이 뜨고 그 노드의 API 서버하고만 통신한다만들기 쉽고 복제 관리가 단순하다노드 하나가 죽으면 etcd 멤버와 컨트롤 플레인을 함께 잃는다컨트롤 플레인 3대
external etcd별도 호스트에 etcd 클러스터를 두고 모든 API 서버가 거기에 붙는다컨트롤 플레인 하나나 etcd 멤버 하나를 잃어도 영향이 적다호스트가 stacked의 두 배 필요하다컨트롤 플레인 3대 + etcd 3대

어느 쪽이든 API 서버 앞에는 로드밸런서를 둬요. kubeadm HA 구성 문서의 첫 단계가 kube-apiserver용 로드밸런서를 만드는 일이에요. 클라우드라면 TCP를 그대로 넘기는 로드밸런서 뒤에 컨트롤 플레인 노드를 두고 상태 확인은 API 서버 포트(기본 6443)에 TCP로 붙어 보는 방식으로 해요. 문서에는 로드밸런서 주소가 kubeadm의 ControlPlaneEndpoint와 늘 같아야 하고 클라우드에서 IP를 바로 쓰는 것은 권하지 않는다고 적혀 있어요.

📖 용어: controlPlaneEndpoint
모든 컨트롤 플레인 노드가 함께 쓰는 공용 주소예요. kubeadm init의 --control-plane-endpoint 플래그나 설정 파일의 ClusterConfiguration.controlPlaneEndpoint로 정하고 IP나 DNS 이름 뒤에 포트를 붙여 적어요. 노드 하나의 API 서버 주소를 정하는 --apiserver-advertise-address와는 다른 값이에요.

첫 컨트롤 플레인은 이 주소를 넣어 init하고 나머지는 --control-plane을 붙여 join해요. 문서의 명령을 자리표시자를 남긴 채 옮기면 이래요.

# 첫 컨트롤 플레인 노드 sudo kubeadm init --control-plane-endpoint "LOAD_BALANCER_DNS:LOAD_BALANCER_PORT" --upload-certs # init 출력에 찍히는 명령을 나머지 컨트롤 플레인 노드에서 실행 sudo kubeadm join LOAD_BALANCER_DNS:LOAD_BALANCER_PORT --token <토큰> \ --discovery-token-ca-cert-hash sha256:<CA 공개키 해시> \ --control-plane --certificate-key <인증서 키>

→ init이 공용 주소를 기준으로 클러스터를 만들고 컨트롤 플레인끼리 나눠 써야 하는 인증서를 클러스터에 올려 둬요. join하는 노드는 --certificate-key로 그 인증서를 받아 컨트롤 플레인으로 들어온다는 뜻이에요. 워커는 --control-plane과 --certificate-key 없이 같은 주소로 join해요.

--upload-certs는 5편에서 본 kubeadm init 출력의 [upload-certs] 단계를 실제로 실행하게 하는 플래그예요. 그때는 이 플래그를 주지 않아서 그 단계를 건너뛰었어요. 문서에 따르면 이 플래그를 주면 첫 컨트롤 플레인의 인증서가 암호화돼 kubeadm-certs Secret에 올라가요. 인증서를 직접 복사해 나눠 주고 싶으면 이 플래그를 빼고 수동 배포 절차를 따르면 돼요.

⚠️ 주의: --certificate-key는 비밀번호만큼 지켜야 해요
• kubeadm 출력과 문서 모두 인증서 키가 클러스터의 민감한 데이터에 접근하게 해 준다며 비밀로 지키라고 경고해요. 키는 32바이트 AES 키를 16진수로 적은 문자열이에요
• kubeadm-certs Secret과 복호화 키는 2시간 뒤 만료돼요. 2시간이 지나 컨트롤 플레인을 더 붙이려면 이미 들어온 컨트롤 플레인 노드에서 sudo kubeadm init phase upload-certs --upload-certs로 다시 올리고 새 키를 받아요
• join 명령을 공유 문서나 채팅에 그대로 붙여 두지 마세요. 토큰과 키가 함께 들어 있어요

4. 이 클러스터는 단일 컨트롤 플레인이고 kubeadm은 HA 전환을 지원하지 않는다

그림 4. controlPlaneEndpoint는 없고 etcd 멤버와 컨트롤 플레인 노드는 k8s-master 하나다

위 그림은 16시 18분에 우리 클러스터를 확인한 결과예요. kubeadm-config의 ClusterConfiguration에서 etcd 항목 아래에는 local과 dataDir: /var/lib/etcd가 있어요. 마스터 디스크에 etcd를 두는 stacked 구성이라는 뜻이에요. controlPlaneEndpoint는 0줄이었어요. etcdctl member list에는 k8s-master 멤버 하나가 started로 있고 control-plane 라벨이 붙은 노드도 k8s-master 하나예요. 1절 그림에서 컨트롤 플레인 1만 남기고 로드밸런서를 뺀 모양이에요.

그림의 마지막 줄도 눈여겨볼 만해요. Mac에서 쓰는 kubeconfig의 API 서버 주소는 https://192.168.64.2:6443이에요. 마스터 VM의 vzNAT 쪽 주소예요. 마스터 안의 kubeconfig는 20편의 오류 메시지에 나온 대로 192.168.104.1:6443을 가리켜요. 둘 다 마스터 한 대의 주소예요. 컨트롤 플레인을 한 대 더 붙여도 이 주소를 쓰는 클라이언트는 여전히 마스터 한 대에만 요청을 보내요.

그럼 지금 이 클러스터에 컨트롤 플레인 두 대를 더 붙여 HA로 만들 수 있을까요? kubeadm 클러스터 만들기 문서의 "Considerations about apiserver-advertise-address and ControlPlaneEndpoint" 절 마지막에 답이 있어요.

Turning a single control plane cluster created without `--control-plane-endpoint` into a highly available cluster is not supported by kubeadm.

→ --control-plane-endpoint 없이 만든 단일 컨트롤 플레인 클러스터를 고가용성 클러스터로 바꾸는 것은 kubeadm이 지원하지 않는다는 뜻이에요. 2026-11-14에 v1.37 문서에서 이 문장을 확인했어요.

같은 문서는 그 앞에서 방법도 알려 줘요. 나중에 HA로 키울 계획이 있다면 처음 init할 때 --control-plane-endpoint로 모든 컨트롤 플레인 노드가 함께 쓸 주소를 정하라고 권해요. 문서가 든 예시는 첫 컨트롤 플레인 노드의 IP를 cluster-endpoint라는 사용자 정의 DNS 이름에 매핑해 두고 init과 join에 --control-plane-endpoint=cluster-endpoint를 넘기는 방식이에요. 나중에 HA로 갈 때는 cluster-endpoint가 로드밸런서 주소를 가리키게 바꾸면 된다고 해요. 처음에는 컨트롤 플레인이 한 대여도 공용 이름 하나를 정해 두면 나중에 그 이름이 가리키는 곳만 바꿔서 HA로 갈 수 있어요. 우리 실습 클러스터는 이 이름 없이 만들었으니 kubeadm이 지원하는 방법으로 HA 실습을 하려면 클러스터를 다시 만들어야 해요.

💡 실무에서는: 한 대로 시작해도 공용 주소는 이름으로 정해 둬요
• kubeadm init에 --control-plane-endpoint=<DNS 이름>:6443을 넣고 그 이름이 처음에는 첫 컨트롤 플레인 IP를 가리키게 해요. 문서가 "(Recommended)"로 적어 둔 단계예요
• 이미 IP로 만든 클러스터는 kubeadm 문서 기준으로 HA 전환이 지원되지 않아요. 새로 만들 클러스터부터 이름을 정해 두세요
• 컨트롤 플레인을 늘릴 때는 3대나 5대로, 홀수를 유지하며 늘려요. etcd 운영 문서는 etcd 클러스터에 오토스케일링 그룹을 걸지 말라고도 적어요

5. 워커 노드 수에는 "12개 국룰"이 없다

이제 두 번째 질문이에요. "워커 노드도 12개 국룰 이런 거 통하나?" 카프카에서 파티션을 12개로 잡는 관행에는 나름의 이유가 있어요. 카프카 설계 문서에는 토픽이 파티션으로 나뉘고 파티션 하나는 구독하는 컨슈머 그룹마다 한 번에 정확히 한 컨슈머가 읽는다고 적혀 있어요. 그래서 파티션 수가 컨슈머 수로 나눠떨어지면 컨슈머마다 같은 수의 파티션을 맡아요. 12는 1, 2, 3, 4, 6, 12로 나눠떨어지니 컨슈머를 몇 개로 바꿔도 고르게 나누기 쉬운 수예요. 다만 제가 읽은 설계 문서에 12라는 숫자가 나오지는 않았어요. 문서의 규칙이 아니라 나눗셈에서 나온 관행이에요.

쿠버네티스 워커 노드에는 이런 나눗셈이 없어요. 파드는 파티션과 달리 노드 수로 나눠 담는 단위가 아니에요. 스케줄러가 그때그때 들어갈 수 있는 노드를 골라요(23편). 워커끼리 투표하는 일도 없으니 etcd의 과반수 규칙도 적용되지 않아요. 공식 문서에 노드 수로 적혀 있는 것은 상한이에요. 대형 클러스터 고려 사항 문서는 v1.37이 노드 5,000대까지의 클러스터를 지원한다고 하고 쿠버네티스가 아래 조건을 모두 만족하는 구성을 수용하도록 설계됐다고 적어요.

No more than 110 pods per node # 노드당 파드 110개 이하 No more than 5,000 nodes # 노드 5,000대 이하 No more than 150,000 total pods # 전체 파드 150,000개 이하 No more than 300,000 total containers # 전체 컨테이너 300,000개 이하

→ 이만큼까지는 버티도록 만들었다는 상한이지 이만큼 두라는 권장 수가 아니라는 뜻이에요. 우리 워커의 allocatable pods 110도 이 상한과 같은 값이에요.

같은 문서에서 대수 이야기가 나오는 곳은 컨트롤 플레인 쪽이에요. 보통 장애 영역(failure zone)마다 컨트롤 플레인 인스턴스를 하나나 둘 둔다고 하고 장애를 견디려면 장애 영역마다 적어도 하나는 두라고 해요. 워커 노드의 최소 대수나 홀수 규칙은 이 문서에 없어요. kubeadm HA 구성 문서의 준비물 목록에 워커용 기계도 3대 이상이라고 나오지만 그 이유는 적혀 있지 않았어요.

그렇다면 워커 수는 무엇으로 정할까요? 우리 클러스터의 워커부터 볼게요.

그림 5. 워커 세 대는 같은 크기이고 requests는 CPU의 12~17%, 메모리는 1% 이하만 잡혀 있다
📖 용어: allocatable과 requests
allocatable은 노드 용량에서 시스템 몫을 떼고 남아 파드에 줄 수 있는 양이에요. 노드 자원 예약 문서는 스케줄러가 allocatable을 넘겨 배치하지 않는다고 적어요. requests는 파드가 "이만큼은 있어야 한다"고 적어 둔 값이고 스케줄러는 노드마다 이미 놓인 파드의 requests 합을 allocatable에서 빼고 남은 자리에 새 파드를 놓아요.

워커 세 대는 모두 allocatable이 CPU 2개, 메모리 약 3.7GiB(3896020Ki 안팎), 파드 110개예요. 이미 놓인 파드의 requests 합은 CPU 250m(12%), 350m(17%), 350m(17%)이고 메모리는 0, 70Mi, 70Mi(1% 이하)였어요. 네 노드 모두 topology.kubernetes.io/zone과 region 라벨이 없었어요. 노트북 한 대 안의 VM이니 장애 영역도 하나뿐이에요.

6. 워커 수는 N+1과 장애 영역, 그리고 requests로 센다

워커 수를 정할 때 제가 쓸 기준은 셋이에요. 한 대가 빠져도 남은 노드에 다 들어가는가(N+1), 장애 영역이 여럿이면 영역 하나가 빠져도 들어가는가, 그 계산의 바탕인 requests가 실제와 맞는가예요.

📖 용어: N+1
필요한 노드 N대에 한 대를 더 둬서 아무 노드 한 대가 빠져도 남은 노드만으로 일을 감당하게 하는 여유 기준이에요. 쿠버네티스가 정한 규칙이 아니라 용량을 계획할 때 흔히 쓰는 말이에요. 쿠버네티스에서는 "가장 큰 노드 한 대를 빼도 모든 파드의 requests가 남은 노드에 들어가는가"로 따져요.

한 대가 빠지면 남은 노드에 들어가나: w21에서 직접 계산

숫자로 확인하려고 w21 네임스페이스에 CPU 800m을 요청하는 파드를 만들어 봤어요. 다른 실습과 클러스터를 같이 쓰고 있어서 노드를 실제로 끄지는 않았어요. 대신 nodeAffinity로 worker3을 후보에서 빼서 "worker3이 빠진 클러스터"를 흉내 냈어요. 실험이 끝난 뒤 네임스페이스째 지웠어요.

그림 6. 800m 파드는 노드마다 2개씩, 세 대면 6자리이고 한 대가 빠지면 4자리다

계산은 그림 6의 3번에 있어요. worker1은 2000m에서 250m을 빼면 1750m이 남으니 800m 파드가 2개 들어가고 150m이 남아요. worker2와 worker3은 1650m이 남아 2개씩 들어가요. 세 대를 다 쓰면 6자리, worker3이 빠지면 4자리예요. 여기에 같은 파드 5개를 조건을 바꿔 두 번 띄웠어요.

그림 7. 세 대일 때 다 뜨던 5개가 worker3을 빼자 4개만 뜨고 1개는 CPU가 모자라 Pending이었다
그림 8. 같은 Deployment라도 노드 한 대를 빼면 다섯 번째 파드가 들어갈 자리가 없다

세 대를 모두 쓸 수 있게 만든 all3은 20초 뒤에 보니 5개 모두 Running이었고 worker1에 1개, worker2와 worker3에 2개씩 놓였어요. worker3을 뺀 같은 5개(no-w3)는 worker1과 worker2에 2개씩 놓였고 다섯 번째 파드는 Pending이었어요. 스케줄러가 남긴 이유는 이랬어요.

0/4 nodes are available: 1 node(s) didn't match Pod's node affinity/selector, 1 node(s) had untolerated taint(s), 2 Insufficient cpu. preemption: 0/4 nodes are available: 2 No preemption victims found for incoming pod, 2 Preemption is not helpful for scheduling.

→ 노드 넷 가운데 하나(worker3)는 nodeAffinity에 맞지 않고 하나(마스터)에는 이 파드가 견디지 못하는 taint가 있고 남은 둘(worker1·2)은 CPU가 모자라다는 뜻이에요. 뒤의 preemption 줄은 우선순위가 낮은 파드를 밀어내서 자리를 만들 수도 없다는 뜻이고요. 마스터가 빠지는 이유는 5편의 control-plane taint예요.

이 결과를 N+1로 읽으면 이래요. 이 서비스가 800m짜리 파드를 원한다면 워커 세 대로 띄울 수 있는 것은 6개이고 아무 워커 한 대가 빠져도 모두 다시 뜰 수 있는 것은 4개까지예요. 5개가 꼭 필요하면 워커를 한 대 더 두거나 파드 크기를 줄여야 해요. 워커 수는 정해진 숫자가 아니라 "한 대를 뺀 나머지에 내 파드가 다 들어가는가"를 계산해서 나오는 값이에요.

이때 남은 CPU를 합쳐서 세면 틀려요. worker1과 worker2에 남은 CPU를 더하면 3400m이라 800m 파드 4.25개가 들어갈 것 같지만 파드 하나는 노드 하나에만 놓이니 실제 자리는 노드별로 내림한 2+2=4개예요. worker1에 남는 150m은 어떤 800m 파드도 쓸 수 없어요. 그리고 실제로 노드가 죽으면 그 노드의 파드가 다른 노드로 옮겨 가기까지 시간이 더 걸려요. 노드가 응답을 멈춘 뒤 파드를 내보내기까지의 흐름은 25편에서 따로 봐요.

흉내가 아니라 노드가 실제로 멈춘 경우도 한 번 봤어요. 25편의 실험에서 worker3의 kubelet을 멈추고 45초 뒤에 보니 worker3은 Ready=Unknown이었고 unreachable taint가 붙어 있었어요. taint가 붙은 시각은 17:23:26이었어요. 그로부터 300초 뒤인 17:28:26에 worker3에 있던 myweb 파드 2개를 대신할 새 파드가 worker1과 worker2에 하나씩 만들어졌고 곧 Running이 됐어요. 이 300초는 파드에 기본으로 붙는 unreachable toleration이 taint를 견디는 시간이에요. myweb은 requests를 하나도 적지 않은 파드라서 스케줄러 계산에는 0으로 들어가요(아래에서 다시 봐요). 그래서 남은 두 노드에서 자리를 찾는 데 막힐 것이 없었어요. 이번에는 이렇게 다시 떴지만 requests가 큰 파드라면 다시 뜨기 전에 그림 8과 같은 자리 계산을 통과해야 해요.

장애 영역이 여럿이면 영역 하나를 통째로 뺀다

클라우드에서 워커를 여러 가용 영역(zone)에 나눠 두면 N+1의 "한 대"가 "영역 하나"로 커져요. 영역 하나가 통째로 빠져도 남은 영역에 다 들어가야 하니까요. 노드에 topology.kubernetes.io/zone 라벨이 붙어 있으면 파드를 영역마다 고르게 퍼뜨릴 수 있어요. Pod Topology Spread Constraints 문서는 topologySpreadConstraints로 파드를 region, zone, node 같은 장애 영역에 걸쳐 어떻게 퍼뜨릴지 정할 수 있고 그렇게 하면 고가용성과 자원 활용에 도움이 된다고 설명해요.

📖 용어: 장애 영역과 토폴로지 라벨
장애 영역(failure zone)은 전원·네트워크 같은 장애가 한꺼번에 영향을 주는 범위예요. 클라우드의 가용 영역이 대표적이에요. 쿠버네티스는 노드에 붙은 topology.kubernetes.io/zone, topology.kubernetes.io/region 라벨로 노드가 어느 영역에 있는지 알고 스케줄러와 topologySpreadConstraints가 이 라벨을 읽어요.

같은 문서에 따르면 클러스터 수준 기본값을 따로 정하지 않아도 스케줄러는 kubernetes.io/hostname 기준 maxSkew 3, topology.kubernetes.io/zone 기준 maxSkew 5를 ScheduleAnyway로 정한 것과 똑같이 동작해요. 다만 이 기본값은 노드에 두 라벨이 모두 있을 때를 전제로 하므로 라벨이 없는 노드는 그 기준으로 점수를 매기지 않는다는 주의가 붙어 있어요. 우리 클러스터에는 zone 라벨이 없으니 영역으로 퍼뜨리는 효과는 기대할 수 없어요.

영역을 쓴다면 영역마다 워커를 같은 수로 두는 편이 계산이 쉬워요. 파드가 영역마다 고르게 퍼지는데 영역마다 노드 수가 다르면 작은 영역이 먼저 차요. 워커 수를 "영역 수의 배수"로 맞추는 것은 공식 규칙이 아니라 이 계산을 단순하게 하려는 선택이에요. 카프카의 12도 이런 나눗셈에서 나온 관행이었어요.

requests를 적지 않은 파드는 자리 계산에서 0이다

N+1 계산은 모두 requests를 바탕으로 해요. 컨테이너 자원 관리 문서에는 스케줄러가 자원 종류마다 노드에 놓인 컨테이너의 requests 합이 노드 용량보다 작게 유지되도록 한다고 적혀 있어요. 같은 문서는 실제 사용량이 아무리 낮아도 이 용량 확인을 통과하지 못하면 스케줄러가 파드를 놓지 않는다고 해요. 반대로 말하면 requests를 적지 않은 파드는 실제로 얼마를 쓰든 스케줄러의 자원 필터(CPU·메모리 검사)에서는 0으로 계산되고 노드에 점수를 매길 때만 컨테이너마다 CPU 100m·메모리 200Mi를 요청한 것으로 쳐요.

우리 클러스터에서 requests와 실제 사용량이 얼마나 다른지 봤어요. 16시 18분 기준으로 파드 32개 가운데 requests가 하나도 없는 파드가 22개였어요(myweb 5, kube-proxy 4, node-exporter 4 등). 16시 40분에 kubelet의 /stats/summary를 API 서버 프록시로 읽어 실제 메모리 사용량을 봤어요. metrics-server가 없어도 kubelet이 직접 내놓는 값이에요.

워커 memory requests 합 파드 memory workingSet 합 (그중 requests 없는 파드) 노드 전체 workingSet worker1 0 533Mi (8개) 253Mi (7개) 1454Mi worker2 70Mi 991Mi (8개) 551Mi (6개) 1762Mi worker3 70Mi 975Mi (8개) 613Mi (6개) 1779Mi

→ 스케줄러가 자리를 셀 때 보는 메모리 requests 합은 노드마다 0~70Mi인데 파드가 실제로 쓰는 메모리는 533~991Mi였다는 뜻이에요. requests를 안 적은 파드만 모아도 253~613Mi예요. 노드 전체 값은 운영체제와 kubelet·containerd까지 포함한 거예요.

⚠️ 주의: requests 기준 N+1은 requests가 실제와 맞을 때만 맞아요
• 위 숫자로 메모리 N+1을 계산하면 "worker2가 빠져도 70Mi만 옮기면 된다"는 결론이 나와요. 하지만 그 노드의 파드가 실제로 쓰는 메모리는 991Mi로 열 배가 넘어요. 이 값에는 노드마다 떠서 옮겨 가지 않는 DaemonSet 파드도 들어 있어요
• 스케줄러는 실제 사용량을 보지 않아요. 남은 노드에 requests 기준으로 자리가 있으면 놓고 그 노드의 메모리가 실제로 모자라면 그때 가서 노드 쪽에서 문제가 나요
• 그래서 N+1을 계산하기 전에 자주 쓰는 파드부터 requests를 실제 사용량에 가깝게 적어 둬요
💡 실무에서는: 워커 수를 정하는 순서
• 파드마다 requests를 실제 사용량에 맞게 적어요. 안 적힌 파드가 많으면 아래 계산이 모두 낮게 나와요
• kubectl describe node의 Allocated resources로 노드별 requests 합을 보고 가장 큰 노드 한 대를 뺀 나머지에 모든 파드가 들어가는지 노드별로 내림해서 세요
• 장애 영역을 여럿 쓰면 영역 하나를 통째로 빼고 같은 계산을 하고 영역마다 노드 수도 맞춰요
• 노드당 파드 상한(기본 110)과 클러스터 상한(노드 5,000대)은 마지막에 확인해요. 이 값에 닿는 경우는 드물어요

그래서 "12개 국룰"에 대한 제 답은 이래요. 컨트롤 플레인에는 etcd 과반수 때문에 3, 5 같은 홀수 규칙이 있지만 워커에는 그런 규칙이 없어요. 워커 수는 내 파드의 requests 합과 한 대(또는 한 영역)를 잃었을 때 남는 자리에서 거꾸로 계산해요. 이 클러스터의 800m 파드라면 그 답이 "세 대로 4개까지"였어요.

✍️ 오늘의 요약
컨트롤 플레인 수는 etcd 과반수 규칙으로 정해지고 워커 수는 한 대를 뺀 나머지에 requests가 들어가는지로 계산해요.

컨트롤 플레인을 여러 대로 두면 API 서버는 로드밸런서 뒤에서 모두 요청을 받고 컨트롤러 매니저와 스케줄러는 Lease를 쥔 리더 하나만 일해요. etcd는 과반이 동의해야 쓰기를 확정해서 2대는 1대보다 나을 것이 없고 4대는 3대와 같은 1대만 견뎌요. 그래서 3대, 5대로 늘려요. kubeadm HA는 init 때 --control-plane-endpoint로 정한 공용 주소에서 시작하고 이 주소 없이 만든 단일 컨트롤 플레인을 HA로 바꾸는 것은 kubeadm이 지원하지 않아요. 우리 클러스터가 그 경우예요. 워커 수에는 카프카의 12 같은 나눗셈 규칙도 공식 권장 수도 없고 문서에는 상한만 있어요. CPU 800m 파드로 계산하니 워커 세 대에서 한 대가 빠져도 다 뜨는 것은 4개까지였고 worker3을 후보에서 빼서 흉내 낸 실험에서 5개를 띄우자 1개가 Pending이었어요. 그 계산은 requests를 제대로 적은 만큼만 맞아요.
