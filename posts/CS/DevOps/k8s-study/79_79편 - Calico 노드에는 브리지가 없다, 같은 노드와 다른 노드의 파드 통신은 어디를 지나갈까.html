worker3에서 ip -br link show type bridge를 실행했더니 한 줄도 나오지 않았어요. 파드 네트워크를 설명하는 흔한 그림은 노드마다 브리지(tunl0)가 하나 있고 파드마다 생긴 veth(caliXXX)가 그 브리지에 붙는다고 그려요. 그래서 같은 노드에서 tunl0의 종류도 확인했어요(labs/devops/k8s-study/out/79-calico-tunl0-not-bridge.txt).

## 노드의 브리지 인터페이스 (ip -br link show type bridge) (줄 수: 0) ## tunl0 의 종류 (ip -d link show tunl0) 5: tunl0@NONE: <NOARP,UP,LOWER_UP> mtu 1480 qdisc noqueue state UNKNOWN mode DEFAULT group default qlen 1000 link/ipip 0.0.0.0 brd 0.0.0.0 promiscuity 0 allmulti 0 minmtu 0 maxmtu 0 ipip any remote any local any ttl inherit nopmtudisc ...

→ 브리지 종류의 장치는 0개였고 tunl0는 link/ipip, MTU 1480인 IPIP 터널 장치였어요. 그림의 "브리지(tunl0)"라는 상자는 이 노드에 없었어요.

그림이 실제와 다르면 장애를 볼 때 엉뚱한 곳부터 보게 돼요. 브리지가 있다고 믿으면 브리지의 MAC 표를 찾고, 모든 파드 통신이 tunl0를 지난다고 믿으면 같은 노드의 두 파드가 통신하지 못할 때도 터널부터 의심해요. 51편에서는 파드의 eth0와 노드의 cali 장치가 veth 한 쌍이라는 걸, 52편에서는 다른 노드로 가는 패킷이 IPIP로 감싸지는 걸 tcpdump로 확인했어요. 이번 글은 그 결과를 진단 순서로 묶어요. 통신이 안 될 때 두 파드가 같은 노드에 있는지 다른 노드에 있는지부터 가르고 각각 어느 경로와 어느 카운터를 봐야 하는지 실제 출력으로 정해요. 클러스터는 Lima VM 4대(마스터 1, 워커 3, arm64)에 kubeadm v1.37.2, Calico v3.33.0(IPIP Always), kube-proxy iptables 모드를 올린 실습 환경이에요.

1. worker3에는 브리지가 0개였고 tunl0는 다른 노드로 갈 때만 쓰는 터널이었다

📖 용어: 리눅스 브리지 (Linux bridge)
커널이 만드는 가상 스위치예요. 붙어 있는 포트들의 MAC 주소를 배워서 이더넷 프레임을 해당 포트로 넘겨요. Docker 기본 네트워크의 docker0, CNI의 bridge 플러그인을 쓰는 구성이 이 방식으로 컨테이너를 같은 L2 구간에 묶어요. ip link show type bridge로 노드에 있는지 볼 수 있어요.

흔한 그림은 브리지형 CNI의 모습에 가까워요. 그 구성에서는 같은 노드의 파드들이 한 브리지에 붙어 같은 L2 구간에 있고 브리지가 MAC 주소를 보고 프레임을 상대 파드의 veth로 넘겨요. Calico의 이번 구성은 브리지를 만들지 않았어요. worker3에서 브리지 종류의 장치를 세면 0이었어요.

📖 용어: tunl0
리눅스 ipip 모듈이 만드는 기본 IPIP 터널 장치예요. 이 장치로 내보낸 IPv4 패킷 앞에 바깥 IPv4 헤더가 하나 더 붙어요. Calico의 IPIP 모드는 다른 노드에 있는 파드로 가는 패킷을 이 장치로 보내요. MTU 1480은 노드 NIC의 1500에서 바깥 헤더 20바이트를 뺀 값이고 53편에서 자세히 봤어요.

tunl0 출력의 remote any local any는 이 장치가 상대 끝을 하나로 정해 두지 않았다는 뜻이에요. 바깥 헤더의 목적지를 어느 노드로 할지는 tunl0를 가리키는 경로의 via 주소가 정해요. 4절의 캡처에서 바깥 목적지가 경로의 via 주소인 192.168.104.5와 같았던 것으로 확인할 수 있어요. 그러니 tunl0는 파드들을 묶는 장치가 아니라 다른 노드로 나가는 출구 하나예요.

그림 1. tunl0는 파드를 묶는 브리지가 아니라 다른 노드로 나가는 출구였어요.

같은 그림 계열에는 "pod eth0 → veth(cali) → vRouter(calico) → tunl0 → 노드 NIC → 상대 노드" 순서로 그린 것도 있어요. 이 순서는 실제와 거의 같아요. 다만 vRouter는 따로 떠 있는 장치나 프로세스가 아니에요. 노드 커널의 라우팅 표이고 그 표에 경로를 넣는 것은 calico-node 안의 Felix예요(30편). 패킷은 커널이 전달하고 Calico 프로세스를 거쳐 가지 않아요. 우리 클러스터에서는 그림의 노드 NIC 자리가 eth0(192.168.104.x)예요.

2. 브리지 대신 파드마다 /32 경로가 있고 커널이 그 경로로 cali를 고른다

브리지가 없으면 노드는 어떤 장치로 파드에게 패킷을 넘길까요? 같은 파일에서 worker3의 두 파드 IP로 가는 경로를 조회한 결과예요.

## 이 노드 파드로 가는 경로: 파드마다 caliXXXX 로 /32 10.244.100.228 dev cali6d8ce9c91fa src 192.168.104.5 uid 501 10.244.100.193 dev cali7986f7b7af3 src 192.168.104.5 uid 501 ## 파드 안에서 본 eth0 와 기본 경로 3: eth0 inet 10.244.100.228/32 scope global eth0 ... default via 169.254.1.1 dev eth0 169.254.1.1 dev eth0 scope link

→ 노드는 파드 IP마다 그 파드의 cali 장치를 가리키는 경로를 하나씩 갖고 있어요. 파드 안의 eth0 주소는 /32이고 기본 경로는 169.254.1.1을 거쳐요. 169.254.1.1에 노드 쪽 cali가 proxy ARP로 대신 답하는 구조는 51편에서 확인했어요.

📖 용어: 파드별 /32 경로
주소 하나만 가리키는 경로예요. Calico는 노드에 뜬 파드마다 <파드 IP> dev <cali 장치> 한 줄을 노드 라우팅 표에 둬요. 같은 노드의 블록(/26)보다 범위가 좁으니 최장 접두사 일치로 이 줄이 먼저 선택돼요.

파드끼리 통신할 때 브리지가 veth를 찾아 주나? 이 구성에서는 아니에요. pp1이 pp2에게 보내는 패킷을 따라가 볼게요. pp1의 eth0는 /32라서 같은 링크에 이웃이 없다고 봐요. 그래서 목적지가 같은 노드의 pp2여도 모든 패킷을 기본 게이트웨이 169.254.1.1로 보내요. 패킷은 veth를 지나 노드의 cali6d8ce9c91fa로 나오고 노드 커널이 목적지 IP로 라우팅 표를 찾아 10.244.100.193 dev cali7986f7b7af3를 골라요. MAC 주소를 배워 두는 표가 아니라 IP 경로가 상대 veth를 찾아 주는 거예요.

그래서 같은 노드 안의 통신도 라우팅을 한 번 거쳐요. 52편의 캡처에서 같은 노드 요청의 TTL이 출발 쪽 64에서 도착 쪽 63으로 줄었던 것도 이 때문이에요. 브리지는 프레임을 넘길 때 TTL을 건드리지 않고 라우터는 패킷을 넘길 때마다 TTL을 하나 줄여요. 두 파드가 같은 /26 블록의 주소를 받았다고 같은 L2 구간에 있는 것은 아니에요.

3. 같은 노드 파드끼리 ping 20번을 해도 tunl0 카운터는 1528 그대로였다

같은 노드 통신이 tunl0를 지나지 않는다는 건 카운터로도 확인할 수 있어요. worker3에 pp1과 pp2를 고정하고 pp1에서 pp2로 ping 20번을 보내면서 그 전후로 tunl0와 두 파드의 cali 장치가 받은 패킷 수와 보낸 패킷 수를 읽었어요(79-same-node-ping-counters.txt, 같은 이름의 .sh).

📖 용어: 인터페이스 카운터 (rx_packets, tx_packets)
커널이 장치마다 세는 누적 패킷 수예요. /sys/class/net/<장치>/statistics/에서 읽어요. 노드 쪽 cali의 rx는 노드가 그 장치에서 받은 패킷, 즉 파드가 보낸 패킷이고 tx는 파드 쪽으로 넘긴 패킷이에요.

그림 2. ping 20번이 오가는 동안 tunl0의 두 카운터는 하나도 움직이지 않았어요.

tunl0는 전후 모두 rx 1528, tx 599였어요. cali6d8ce9c91fa는 rx 2에서 27, tx 2에서 33으로, cali7986f7b7af3는 rx 3에서 28, tx 1에서 33으로 늘었어요. 20개 요청과 20개 응답은 두 cali 사이에서만 오갔고 손실은 0%였어요. 증가량이 20보다 조금 많은 것은 ping 말고도 다른 패킷이 섞였기 때문인데, 그 패킷의 종류는 이번에 따로 확인하지 않았어요.

두 cali의 시작 값이 rx 2, rx 3으로 작은 것도 눈여겨볼 만해요. 이 두 파드는 1·2절의 출력을 얻은 실험에서 같은 이름(ch05 네임스페이스의 pp1, pp2)으로 만들었다가 지운 뒤 다시 만든 파드예요. 장치 이름은 같았지만 카운터는 처음부터 다시 셌어요. 6절에서 이유를 봐요.

⚠️ tunl0 카운터는 노드 전체의 합계예요
• tunl0는 노드에 하나뿐이라서 그 노드로 드나드는 모든 파드의 노드 간 트래픽이 같은 카운터에 쌓여요
• 이번 실습 클러스터는 조용해서 전후 차이가 내 ping과 정확히 맞았지만, 바쁜 노드에서는 차이만으로 내 패킷이라고 단정할 수 없어요
• 그때는 52편에서 한 대로 노드 eth0에서 tcpdump -ni eth0 'ip proto 4'로 안쪽 주소를 보고 좁혀요. cali 카운터는 파드 하나에 하나씩이라 그 파드의 트래픽만 세요

4. 다른 노드로 가면 출발 노드의 경로가 tunl0를 가리키고 도착 노드의 tunl0 rx가 3 늘었다

이번에는 worker1의 src1에서 worker3의 dst3로 ping 3번을 보냈어요. 두 노드에서 경로를 조회하고 worker3의 eth0에서 IPIP 패킷만 잡았어요(79-cross-node-ipip.txt, 같은 이름의 .sh).

그림 3. 출발 노드는 tunl0로, 도착 노드는 상대 파드의 cali로 경로를 골랐어요.

worker1에서 dst3(10.244.100.210)로 가는 경로는 via 192.168.104.5 dev tunl0였어요. worker3 노드 주소를 다음 홉으로 삼아 tunl0로 내보내라는 뜻이에요. 같은 주소를 worker3에서 조회하면 dev calie3e75f17935였어요. 도착 노드에서는 다시 2절과 같은 /32 경로가 쓰여요.

worker3 eth0 캡처의 첫 줄은 IP 192.168.104.3 > 192.168.104.5: IP 10.244.194.90 > 10.244.100.210: ICMP echo request였어요. 바깥 헤더는 worker1에서 worker3로 가는 노드 주소이고 안쪽 헤더는 파드 주소 그대로예요. 바깥 목적지 192.168.104.5는 worker1 경로의 via 주소와 같아요. 헤더 구조와 길이는 52편에서 바이트 단위로 확인했으니 여기서는 다시 풀지 않아요.

카운터도 달랐어요. worker3의 tunl0 rx_packets는 1528에서 1531이 됐어요. 바깥 헤더를 벗긴 echo request 3개가 tunl0로 들어왔다는 뜻이에요. 3절 실험의 전후와 이 실험의 시작 때 값이 모두 1528이었으니, 그 1분 남짓 동안 worker3로 터널을 타고 들어온 패킷은 없었어요. 그래서 +3을 이 ping의 요청 세 개로 읽을 수 있어요.

그림 4. 같은 노드는 cali 두 개 사이에서, 다른 노드는 tunl0와 eth0를 두 번씩 지나서 도착했어요.

5. 클러스터 라우팅 테이블은 하나가 아니라 노드마다 커널에 있다

클러스터 라우팅 테이블은 어디 있나? "클러스터가 노드 IP를 담은 라우팅 테이블을 저장한다"는 설명을 자주 봐요. 그런데 클러스터에 저장된 라우팅 테이블이라는 객체는 찾을 수 없어요. 클러스터에 저장된 것과 노드 커널에 있는 것을 나란히 놓아 봤어요(79-node-to-node-routes.txt, 같은 이름의 .sh).

## Calico 가 노드마다 나눠 준 파드 블록 (blockaffinities CR = 클러스터에 저장된 원본) NODE CIDR STATE k8s-master 10.244.235.192/26 confirmed k8s-worker1 10.244.194.64/26 confirmed k8s-worker2 10.244.126.0/26 confirmed k8s-worker3 10.244.100.192/26 confirmed ## k8s-worker3 의 커널 라우팅 표 중 파드 대역 blackhole 10.244.100.192/26 proto 80 10.244.126.0/26 via 192.168.104.4 dev tunl0 proto 80 onlink mtu 1480 10.244.194.64/26 via 192.168.104.3 dev tunl0 proto 80 onlink mtu 1480 10.244.235.192/26 via 192.168.104.1 dev tunl0 proto 80 onlink mtu 1480
📖 용어: BlockAffinity
Calico IPAM이 "이 /26 블록은 이 노드 것"이라고 적어 두는 CRD 객체예요(blockaffinities.crd.projectcalico.org). 쿠버네티스 API를 거쳐 etcd에 저장돼요. 블록을 나누는 방식과 podCIDR과의 차이는 31편에서 봤어요.

→ 클러스터(etcd)에 있는 것은 블록 소유 기록 네 줄이에요. 경로가 아니라 "어느 노드가 어느 /26을 가졌나"라는 데이터예요. 실제 경로는 노드마다 커널에 있어요. worker3의 표에는 다른 세 노드의 블록으로 가는 경로 세 줄과 자기 블록의 blackhole 한 줄이 있었어요. 네 노드 모두 같은 모양이었어요. 각 노드는 자기를 뺀 세 블록을 그 블록 주인의 노드 IP로 보내요. 자기 블록은 blackhole로 두고, 그 블록 안의 실제 파드는 더 좁은 /32 경로로 찾아가요. blackhole이 정상 파드를 막지 않는 이유는 56편에서 봤어요.

📖 용어: 경로의 proto 값
커널 경로에 붙는 출처 표시 번호예요. 경로를 넣은 프로그램이 자기 번호를 붙이고 /etc/iproute2/rt_protos가 번호에 이름을 붙여요. 같은 출력에서 12는 bird였어요. 파드 대역 경로는 모두 80이었어요.

그 경로를 누가 넣었는지는 proto 값이 알려 줘요. worker3에서는 bird와 bird6 프로세스가 돌고 있었고 rt_protos에서 BIRD의 번호는 12였어요. 그런데 파드 대역 경로는 모두 proto 80이었어요. 30편에서는 Calico v3.33.0 Felix 소스의 기본 경로 표시가 80이라는 것, BIRD를 멈춰도 이 경로가 남는다는 것, 경로를 지우면 Felix가 다시 넣는다는 것을 확인했어요. Felix는 BlockAffinity 같은 IPAM 데이터를 읽어 자기 노드의 커널에 경로를 써요.

그림 5. 클러스터에는 경로가 아니라 블록 소유가 저장되고 경로는 네 노드의 커널에 따로 있어요.
💡 다른 노드로만 안 될 때 경로를 확인하는 순서
• kubectl get blockaffinities.crd.projectcalico.org -o custom-columns=NODE:.spec.node,CIDR:.spec.cidr로 목적지 파드 IP가 어느 노드의 블록인지 봐요
• 출발 노드에서 ip route show proto 80을 실행해 그 블록이 주인 노드의 IP를 via로 해서 tunl0에 걸려 있는지 봐요. 30편에서 이 명령은 다른 노드 블록 세 줄과 자기 블록의 blackhole 한 줄을 돌려줬어요. 노드가 블록을 둘 이상 가지면 줄도 그만큼 늘어요
• 줄이 없으면 패킷은 기본 경로로 빠지고 via가 다르면 엉뚱한 노드로 가요. 30편에서 경로 한 줄을 지우자 바로 다음 요청이 실패했고 Felix가 37초 안에 다시 넣었어요

6. cali 이름은 네임스페이스와 파드 이름의 SHA-1에서 나오니 노드에서 바로 계산할 수 있다

3절에서 본 두 파드는 앞 실험에서 지웠다가 같은 이름으로 다시 만든 파드였어요. 파드 IP는 10.244.100.228에서 10.244.100.216으로, 10.244.100.193에서 10.244.100.242로 바뀌었는데 cali 이름은 두 번 다 cali6d8ce9c91fa, cali7986f7b7af3이었어요. IP가 아닌 다른 무언가에서 이름이 나온다는 뜻이에요. Calico v3.33.0 소스에서 이름을 정하는 함수를 찾았어요(79-calico-v3.33.0-vethname-excerpts.txt).

// libcalico-go/lib/backend/k8s/conversion/workload_endpoint_default.go (v3.33.0) func (wc defaultWorkloadEndpointConverter) VethNameForWorkload(namespace, podname string) string { // A SHA1 is always 20 bytes long, and so is sufficient for generating the // veth name and mac addr. h := sha1.New() h.Write(fmt.Appendf(nil, "%s.%s", namespace, podname)) prefix := os.Getenv("FELIX_INTERFACEPREFIX") if prefix == "" { // Prefix is not set. Default to "cali" prefix = "cali" } ... return fmt.Sprintf("%s%s", prefix, hex.EncodeToString(h.Sum(nil))[:11]) }

→ "네임스페이스.파드이름" 문자열의 SHA-1 값을 16진수로 쓴 뒤 앞 11자를 잘라 cali 뒤에 붙인다는 뜻이에요. 접두사는 FELIX_INTERFACEPREFIX 환경 변수로 바꿀 수 있고 기본은 cali예요. 합쳐서 15자이고 리눅스 인터페이스 이름에 쓸 수 있는 최대 길이와 같아요.

테스트 코드를 빼면 이 함수를 부르는 곳은 두 군데예요. CNI 플러그인이 파드의 veth를 만들 때(cni-plugin/pkg/k8s/k8s.go 438행), 그리고 파드 객체를 WorkloadEndpoint로 바꿀 때(workload_endpoint_default.go 155행)예요. 155행 위의 주석은 "This must match the host-side veth configured by the CNI plugin"이에요. 파드 객체에서 WorkloadEndpoint를 만드는 쪽도 같은 함수로 이름을 계산하니, CNI가 만든 장치의 이름과 반드시 같아야 한다는 뜻이에요. 그래서 파드의 네임스페이스와 이름만 알면 누구든 같은 이름을 얻을 수 있어요.

📖 용어: WorkloadEndpoint
Calico가 파드 하나의 네트워크 끝점을 나타내는 객체예요. 인터페이스 이름, 파드 IP, 적용할 프로필 같은 값을 담아요. 이번 클러스터와 같이 쿠버네티스 API를 데이터스토어로 쓰면 파드 객체를 변환해서 만들어요. Felix는 이 객체를 보고 노드의 cali 장치에 경로와 정책을 걸어요.

계산이 맞는지 Mac에서 확인했어요. printf 'ch05.pp1' | shasum -a 1의 앞 11자는 6d8ce9c91fa, ch05.pp2는 7986f7b7af3, 4절의 ch05.dst3는 e3e75f17935였어요. 세 cali 이름과 모두 같아요. 우연이 아닌지 보려고 worker2에 파드를 고정하고 blog-79, blog-81 네임스페이스에서 이름과 네임스페이스를 바꿔 가며 새로 실험했어요(79-cali-name-hash.txt, 같은 이름의 .sh).

1) 처음 만든 파드 blog-79/web IP=10.244.126.52 경로 dev=calif27d0b7a09b 계산값=calif27d0b7a09b 일치=yes ifindex=82 rx_packets=1 파드를 지운 뒤 노드에서 calif27d0b7a09b 조회: Device "calif27d0b7a09b" does not exist. 2) 같은 이름으로 다시 blog-79/web IP=10.244.126.21 경로 dev=calif27d0b7a09b 계산값=calif27d0b7a09b 일치=yes ifindex=83 rx_packets=2 3) 다른 네임스페이스 blog-81/web IP=10.244.126.38 경로 dev=calie330e958bd7 계산값=calie330e958bd7 일치=yes ifindex=85 rx_packets=3 4) 다른 파드 이름 blog-79/web2 IP=10.244.126.47 경로 dev=cali27304031fe0 계산값=cali27304031fe0 일치=yes ifindex=86 rx_packets=1

→ 네 경우 모두 노드 경로가 가리킨 장치 이름과 계산값이 같았어요. 같은 이름으로 다시 만든 파드는 IP가 바뀌어도 같은 이름을 받았고 파드 이름이 같아도 네임스페이스가 다르면 다른 이름을 받았어요. 파드를 지운 뒤에는 그 장치가 노드에서 사라졌고 다시 만든 장치의 ifindex는 82에서 83으로 바뀌었어요. 이름만 같은 새 장치라는 뜻이에요. 3절의 cali 카운터가 rx 2, rx 3에서 시작한 것도 같은 이유예요.

⚠️ 이름이 같은 cali가 같은 장치는 아니에요
• 파드를 다시 만들면 veth도 새로 만들어져요. 이름은 같아도 ifindex가 바뀌고 카운터는 0부터 다시 세요
• 파드를 다시 만든 시점을 사이에 두고 카운터를 빼면 엉뚱한 값이 나와요. 비교 전후로 파드의 UID나 장치의 ifindex가 그대로인지 봐요
• 코드대로라면 이름이 고정되는 StatefulSet 파드(web-0 등)는 다시 만들어져도 같은 cali 이름을 받고 이름 끝이 무작위인 Deployment 파드는 다시 만들어질 때마다 이름이 바뀌어요

진단에서는 이 성질이 편해요. 장애가 난 파드의 네임스페이스와 이름만 알면 kubectl exec 없이 노드에서 바로 그 파드의 cali를 찾아 카운터를 읽을 수 있어요. 지금까지의 관찰을 진단 순서로 정리하면 이래요.

💡 같은 노드냐 다른 노드냐부터 가르는 진단 순서
• 먼저 kubectl get pod -o wide로 두 파드의 노드를 봐요
• 같은 노드: 출발 노드에서 ip route get <목적지 파드 IP>가 dev cali...인지 보고 두 파드의 cali 카운터를 요청 전후로 비교해요. 이름은 printf '네임스페이스.파드' | shasum -a 1 | cut -c1-11로 계산해요. tunl0와 노드 간 경로는 볼 필요가 없어요. 여기서 막히면 정책(54편)이나 앱의 listen 상태(56편)를 봐요
• 다른 노드: 출발 노드의 경로가 via <목적지 노드 IP> dev tunl0인지, 그 via가 BlockAffinity의 주인 노드와 맞는지 봐요. 도착 노드에서 tunl0 rx가 느는지, eth0에 ip proto 4 패킷이 오는지(52편) 보고 큰 요청만 멈추면 MTU(53편)를 봐요
• 이 순서는 IPIP Always와 iptables 데이터플레인인 이번 구성에서 관찰한 것이에요. VXLAN 모드나 eBPF 데이터플레인은 장치와 경로가 다를 수 있는데 이번에 실험하지 않았어요

✍️ 오늘의 요약

worker3에는 브리지가 하나도 없었고 tunl0는 다른 노드로 갈 때만 쓰는 IPIP 터널 장치였어요. 같은 노드의 파드끼리는 노드 커널의 파드별 /32 경로가 상대 cali를 골라 줬고 ping 20번 동안 tunl0 카운터는 rx 1528, tx 599 그대로였어요. 다른 노드로 갈 때는 출발 노드의 경로가 via 노드IP dev tunl0였고 도착 노드의 tunl0 rx가 ping 세 번만큼 늘었어요.

클러스터에 저장된 것은 노드마다 /26 블록을 누가 가졌는지 적은 BlockAffinity였고 실제 라우팅 표는 네 노드의 커널에 따로 있었어요. 그 경로는 모두 proto 80으로 Felix가 넣은 것이었어요. cali 이름은 "네임스페이스.파드이름"의 SHA-1 앞 11자라서, 같은 이름으로 다시 만든 파드는 같은 이름의 새 장치를 받았어요.

파드 통신이 안 될 때는 두 파드가 같은 노드에 있는지부터 가르고 같은 노드면 cali와 /32 경로를, 다른 노드면 tunl0 경로와 블록 소유와 IPIP를 보면 돼요.
