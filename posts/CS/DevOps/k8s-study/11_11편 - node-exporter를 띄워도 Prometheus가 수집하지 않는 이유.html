Mac에서 Prometheus의 수집 대상 목록을 불러오자 14줄이 나왔어요. 가운데 열은 한 줄도 빠짐없이 up이었습니다. API 서버, 노드 4대의 kubelet, 노드 4대의 cAdvisor, kube-state-metrics, 그리고 Service 엔드포인트 4개가 모두 응답하고 있었어요. 그런데 목록을 다시 훑어보니 9100으로 끝나는 주소가 하나도 없었어요. 9100은 node-exporter가 노드의 CPU·메모리·디스크 수치를 내놓는 포트예요. 그 node-exporter 파드는 같은 시각에 worker1~3에서 하나씩 Running이었습니다.

exporter는 노드마다 떠 있었고 Prometheus도 정상이었는데 둘이 서로 이어져 있지 않았던 거예요. 실패한 대상이 하나도 없으니 화면에 빨간 줄도 없었어요. 8편에서는 이 장면이 무엇을 뜻하는지 다뤘고 이번 글에서는 원인을 따라갑니다. 질문은 "Prometheus는 수집 대상을 어떻게 찾고 노드마다 떠 있던 exporter는 왜 그 목록에 들어가지 못했나"예요. 강의에서 들은 "푸시 방식"이라는 표현도 공식 문서와 맞춰 봤어요.

· 고친 뒤 Prometheus가 정말 긁어 가고 있는지는 어디서 확인할까?

1. 강의 슬라이드에서는 노드마다 exporter를 두고 Prometheus로 모았다

강의 슬라이드는 두 장이었어요. 강의 자료라서 이미지는 싣지 않고 내용을 말로 옮길게요. 첫 장은 흐름도예요. k-master, k-worker01, k-worker02 노드마다 exporter가 하나씩 있고 각 exporter에서 나온 metrics가 Prometheus로 모여요. Prometheus 다음에는 Grafana, Visualization, Web UI가 차례로 이어집니다. 강의에서는 이 구조를 "프로메테우스 푸시 방식 + 데몬셋"이라고 설명했어요.

📖 용어: exporter (익스포터)
어떤 시스템의 상태를 Prometheus가 읽을 수 있는 텍스트 형식으로 바꿔 HTTP로 내놓는 프로그램이에요. node-exporter는 리눅스 노드의 CPU·메모리·디스크·네트워크 수치를 9100 포트의 /metrics 경로에 내놓습니다. exporter는 수치를 어디로도 보내지 않아요. 요청이 오면 그 순간의 값으로 응답할 뿐이에요.

"데몬셋"은 이 클러스터 구성과 그대로 맞아요. DaemonSet은 노드마다 파드를 하나씩 띄우는 리소스이고(1편) 쿠버네티스 DaemonSet 문서도 대표 용도로 "모든 노드에서 노드 모니터링 데몬을 돌리는 것"을 꼽아요. 노드가 클러스터에 추가되면 그 노드에도 파드가 추가되니 exporter를 노드 수만큼 직접 챙길 필요가 없어요.

둘째 장은 구축 구조였어요. 왼쪽에 수집 대상이 세 종류 있어요. Node Exporter(호스트·OS 수치), 쿠버네티스 프로세스(쿠버네티스 메트릭), 그리고 MinIO·Velero·Longhorn 같은 서비스가 Prometheus 형식으로 내놓는 엔드포인트예요. 가운데 Prometheus 서버 상자 안에는 Retrieval, TSDB, HTTP Server, Service Discovery가 있고 Service Discovery는 쿠버네티스 API로 수집 대상을 찾는다고 적혀 있었어요. 수집 대상에서 Retrieval로 가는 화살표에는 "pull metrics"라고 쓰여 있었습니다. 오른쪽에서는 Grafana가 PromQL로 데이터를 조회하고 Prometheus가 Alertmanager로 "push alerts"를 보내면 Alertmanager가 웹훅·Slack·메일로 알려요. 맨 위에는 Prometheus Operator가 있었어요. Operator가 Prometheus, AlertManager, AlertManagerConfig, ServiceMonitor, PodMonitor 같은 CRD를 지켜보다가 Prometheus와 Alertmanager를 관리하고 설정을 만들어 준다고 적혀 있었습니다.

📖 용어: CRD와 Operator
CRD(CustomResourceDefinition)는 쿠버네티스에 원래 없던 종류의 오브젝트를 새로 정의하는 방법이에요. Operator는 그렇게 정의한 오브젝트를 지켜보다가 실제 리소스를 만들고 고치는 컨트롤러입니다. Prometheus Operator 문서에 따르면 Prometheus 리소스 하나를 만들면 Operator가 같은 네임스페이스에 Prometheus를 돌릴 StatefulSet을 만들어요.

Operator 문서의 CRD 목록은 슬라이드보다 길어서 ThanosRuler, PrometheusAgent, Probe, ScrapeConfig, PrometheusRule도 있어요. 그중 이 글과 바로 이어지는 것은 ServiceMonitor 설명이에요. Service가 라벨 셀렉터로 파드를 찾아 EndpointSlice에 넣고 ServiceMonitor는 그 EndpointSlice를 찾아 Prometheus가 해당 파드를 수집하도록 설정을 만든다고 적혀 있어요. Operator를 쓰든 쓰지 않든 Service가 먼저 파드를 고르고 Prometheus는 그 결과를 보고 수집 대상을 정한다는 순서는 같아요. 이 순서가 5절과 6절에서 문제가 된 지점이에요.

슬라이드의 화살표는 데이터가 흐르는 방향이에요. 그런데 수집 방식을 따질 때는 연결을 누가 먼저 여는지가 더 중요해요. 같은 구조를 이 클러스터의 노드 4대로 바꾸고 요청이 시작되는 방향으로 다시 그리면 그림 1이 됩니다.

그림 1. 슬라이드의 화살표는 데이터 흐름이고 수집 연결은 Prometheus 쪽에서 먼저 연다

2. 강의의 "푸시 방식"과 공식 문서의 pull

강의 표현은 "푸시 방식"이었는데 같은 강의 슬라이드의 수집 화살표에는 "pull metrics"라고 적혀 있었어요. 강의에서 이 말을 어떤 뜻으로 썼는지는 제가 판단할 수 없어요. 그래서 강의 표현은 강의 표현으로 두고 Prometheus 공식 문서에 무엇이라고 적혀 있는지만 확인했어요.

Prometheus 개요 문서의 주요 특징 목록에는 두 줄이 나란히 적혀 있어요. 시계열 수집은 HTTP 위의 pull 모델로 이루어지고 시계열 push는 중간 게이트웨이를 거쳐 지원한다고요. 아키텍처 설명도 같아요. Prometheus는 계측된 작업에서 메트릭을 직접 긁어 오거나 짧게 끝나는 작업이라면 중간의 push gateway를 거쳐 긁어 온다고 적혀 있어요.

📖 용어: 스크레이프 (scrape)
Prometheus가 수집 대상의 HTTP 주소(보통 /metrics)에 요청을 보내 그 순간의 수치를 받아 저장하는 수집 한 번을 말해요. "긁는다"는 표현이 이 동작을 가리킵니다. 강의 저장소의 Prometheus 설정에는 이 일을 5초마다 하라고(scrape_interval: 5s) 적혀 있어요.

왜 pull인지는 FAQ에 따로 답이 있어요. HTTP로 긁어 오면 개발하면서 노트북에 감시용 인스턴스를 더 띄울 수 있고, 대상이 내려갔는지 더 쉽고 확실하게 알 수 있으며, 브라우저로 대상에 직접 가서 상태를 볼 수 있다는 세 가지예요. 그러면서도 pull이 push보다 조금 낫다고 보지만 모니터링 시스템을 고를 때 큰 기준으로 삼을 정도는 아니라고 덧붙여요. push해야 하는 경우를 위해서는 Pushgateway를 제공한다고 해요.

공식 문서에서 push가 나오는 곳은 세 군데였어요.

첫째, Pushgateway예요. Pushing metrics 문서는 긁어 갈 수 없는 구성 요소를 감시해야 할 때가 있다면서 짧게 끝나는 서비스 수준 배치 작업이 Pushgateway로 시계열을 push하고 Prometheus는 그 Pushgateway를 긁어 간다고 설명해요. push는 배치 작업과 Pushgateway 사이에서 일어나고 Prometheus 쪽에서 보면 여전히 긁어 오는 거예요.

📖 용어: Pushgateway
긁어 갈 주소를 오래 열어 둘 수 없는 작업(몇 초 만에 끝나는 배치 작업 등)이 메트릭을 대신 맡겨 두는 중간 서버예요. 작업은 끝나기 전에 Pushgateway로 값을 보내고 Prometheus는 Pushgateway의 /metrics를 다른 exporter와 똑같이 긁어 가요.

When to use the Pushgateway 문서는 일부 제한된 경우에만 쓰라고 권해요. 여러 인스턴스를 Pushgateway 하나로 받으면 그곳이 단일 장애 지점이자 병목이 되고, 스크레이프마다 생기는 up 메트릭으로 인스턴스 상태를 자동 감시하는 기능을 잃으며, Pushgateway는 받은 시계열을 API로 지우기 전까지 영원히 내놓는다는 이유예요. 그리고 Pushgateway를 쓸 만한 경우는 보통 서비스 수준 배치 작업의 결과를 담을 때뿐이라고 해요.

둘째, remote write예요. Integrations 문서에 따르면 Prometheus의 remote write·remote read 기능은 샘플을 다른 시스템으로 보내고 받게 해 주며 주로 장기 저장용이에요. 설정 문서의 remote_write 항목에도 url이 "샘플을 보낼 엔드포인트의 URL"이라고 적혀 있어요. 여기서 보내는 쪽은 exporter가 아니라 Prometheus 자신이에요.

셋째, 경고예요. Alerting overview는 Prometheus의 경고가 두 부분으로 나뉜다고 설명해요. Prometheus 서버의 경고 규칙이 Alertmanager로 경고를 보내고 Alertmanager가 그 경고를 묶거나(aggregation), 잠시 끄거나(silencing), 다른 경고 때문에 억제하고(inhibition), 메일·호출 시스템·채팅으로 알림을 보내요. 슬라이드의 "push alerts"가 이 방향이에요.

그림 2. push가 나오는 곳은 배치 작업, 원격 저장, 경고이고 노드 수치 수집은 Prometheus가 요청한다

정리하면 이 실습에서 node-exporter의 수치가 Prometheus에 들어가는 길은 그림 2의 ① 하나예요. 강의 구성에는 Pushgateway도 remote write도 없어요. 그러면 pull이 실제로 일어나는지 눈으로 볼 수 있을까요? Prometheus 웹 화면의 수집 대상 페이지에 그 기록이 남아요. 7절에서 확인합니다. pull과 push의 장단점 자체는 메트릭 수집 2편 - 프로메테우스는 왜 긁어가는가에서 더 깊이 다뤘어요.

3. kube-prometheus-stack은 Operator 이미지를 받지 못해 10분을 넘겼다

슬라이드의 둘째 장은 Prometheus Operator를 쓰는 구성이었어요. 그 구성을 한 번에 설치하는 Helm 차트가 kube-prometheus-stack이에요. 차트 설명에도 Prometheus Operator를 써서 쿠버네티스 클러스터 모니터링을 처음부터 끝까지 제공한다고 적혀 있어요. 그래서 처음에는 9편에서 마스터에 설치한 Helm으로 이 차트를 올리려고 했어요. 차트 버전은 93.1.1이고 차트가 정한 Operator 버전(appVersion)은 v0.95.1이에요.

그림 3. 다른 파드는 다 떴는데 Operator 파드 하나가 이미지를 받지 못했고 설치는 613초 만에 시간 초과로 끝났다

--wait --timeout 10m으로 설치했는데 613초 뒤에 Error: INSTALLATION FAILED: context deadline exceeded로 끝났어요. 정해 둔 10분 안에 모든 리소스가 준비되지 않았다는 뜻이에요. 파드 목록에서 Grafana(3/3), kube-state-metrics(1/1), node-exporter 4개는 Running이었고 prometheus-kube-prometheus-operator 하나만 worker3에서 0/1 ImagePullBackOff(이미지 받기에 실패해 재시도 간격을 늘려 가며 기다리는 상태)였어요. node-exporter 4개는 k8s-master를 포함한 네 노드에 하나씩 떠 있었어요. 이 숫자는 6절에서 다시 나와요. 설치를 기다리는 동안 본 이벤트는 이랬어요.

master$ kubectl -n monitoring get events --sort-by=.lastTimestamp | grep -i -E "warn|fail|error|pull" | tail -8 9m28s Normal Pulling pod/prometheus-grafana-7f9f876497-2gmw2 Pulling image "docker.io/grafana/grafana:13.3.0-distroless" 7m3s Normal Pulled pod/prometheus-grafana-7f9f876497-2gmw2 Successfully pulled image "docker.io/grafana/grafana:13.3.0-distroless" in 2m24.99s (2m24.99s incl 6m50s Normal Pulling pod/prometheus-kube-prometheus-operator-86db4c96dd-vthhs Pulling image "quay.io/prometheus-operator/prometheus-operator:v0.95.1" 6m49s Warning Failed pod/prometheus-kube-prometheus-operator-86db4c96dd-vthhs Error: ErrImagePull 6m49s Warning Failed pod/prometheus-kube-prometheus-operator-86db4c96dd-vthhs Failed to pull image "quay.io/prometheus-operator/prometheus-operator:v0.95.1": rpc error: code = 4m33s Warning Failed pod/prometheus-kube-prometheus-operator-86db4c96dd-vthhs Error: ImagePullBackOff 4m18s Normal BackOff pod/prometheus-kube-prometheus-operator-86db4c96dd-vthhs Back-off pulling image "quay.io/prometheus-operator/prometheus-operator:v0.95.1"

→ Grafana 이미지는 2분 24.99초 만에 받았고 Operator 이미지는 받기 시작한 지 1초 만에 ErrImagePull로 실패한 뒤 재시도를 기다리는 상태로 넘어갔다는 뜻이에요.

목록에서 더 눈여겨볼 것은 없는 파드예요. Prometheus 서버 파드도, Alertmanager 파드도 없었어요. 1절에서 본 대로 Prometheus 리소스를 보고 StatefulSet을 만드는 일은 Operator가 맡아요. Operator가 뜨지 못하면 Prometheus 리소스는 API 서버에 저장만 될 뿐 그 리소스를 파드로 만들 프로그램이 없어요. 이 차트로 Prometheus를 띄우려면 Operator 이미지 하나는 반드시 받아야 했던 거예요. 수집기와 대시보드가 다 떠 있어도 그 수치를 모을 Prometheus는 Operator 하나에 달려 있었어요.

설치하던 때는 오류 문장이 rpc error: code =에서 잘려 있어서 원인을 보지 못했어요. 강의 저장소의 매니페스트로 방향을 바꾸면서 설치도 지웠고요(helm uninstall, monitoring.coreos.com CRD 삭제, monitoring 네임스페이스 삭제). 원인은 글을 쓰면서 두 단계로 다시 확인했어요.

먼저 quay.io에 있는 이 태그의 이미지 인덱스(여러 CPU 아키텍처용 이미지를 한 태그에 묶은 목록)를 열어 봤어요. 증명(attestation)용 항목을 빼면 이미지 항목이 다섯 개였고 플랫폼 표시는 모두 linux/amd64였어요. 그런데 항목마다 실제 이미지 설정을 열어 보니 amd64, arm64, arm/v7, ppc64le, s390x였어요. 태그는 2026-11-05에 갱신돼 있었어요.

그다음 같은 워커(k8s-worker3, uname -m이 aarch64)에서 같은 태그를 crictl pull로 다시 받아 봤어요. 그날 잘렸던 오류의 뒷부분이 나왔어요.

worker3$ sudo crictl pull quay.io/prometheus-operator/prometheus-operator:v0.95.1 ... rpc error: code = NotFound desc = get image config descriptor: no match for platform in manifest sha256:9c2490af...bbb83: not found

→ 런타임은 인덱스의 플랫폼 표시를 보고 노드에 맞는 항목을 골라요. arm64판 이미지는 인덱스 안에 있었지만 표시가 모두 amd64라서 arm64 노드의 containerd는 고를 항목을 찾지 못했어요. 설치하던 날과 같은 날, 같은 노드, 같은 태그로 다시 받아 본 결과라서 그날 잘린 오류도 같은 오류였다고 봐요. 다만 설치 시점의 오류 원문 자체는 남아 있지 않아요.

4. 강의 저장소를 그대로 받으면 세 곳에서 걸린다

그래서 강의 저장소(github.com/brayanlee/k8s-prometheus)의 매니페스트로 바꿨어요. 이 저장소는 Helm이나 Operator 없이 YAML 매니페스트를 kubectl apply로 적용하는 방식이에요. README는 없고 마지막 push는 2025-10-24예요. GitHub API로 보면 라이선스도 등록돼 있지 않아요. 그래서 이 글에는 설명에 필요한 몇 줄만 인용하고 우리가 고친 내용은 diff로만 보여 드릴게요. 폴더는 셋이에요.

· prometheus/: ClusterRole·ClusterRoleBinding, 수집 설정 ConfigMap, node-exporter DaemonSet과 Service, Prometheus Deployment, NodePort 30003 Service
· kube-state/: kube-state-metrics의 ServiceAccount·ClusterRole·ClusterRoleBinding·Deployment·Service (네임스페이스 kube-system)
· grafana/: Grafana Deployment, NodePort 30004 Service, 대시보드 JSON

이미지는 prom/prometheus:latest, 태그가 없는 prom/node-exporter, grafana/grafana:latest, 그리고 kube-state-metrics용으로 liupeng0518/quay.io.coreos.kube-state-metrics:v1.8.0-rc.1이었어요.

📖 용어: kube-state-metrics
쿠버네티스 API 서버에서 Deployment·파드·노드·Job 같은 오브젝트의 상태를 읽어 메트릭으로 내놓는 exporter예요. "파드가 몇 번 재시작했나", "노드에 할당 가능한 CPU가 얼마인가" 같은 값을 냅니다. node-exporter가 노드 운영체제의 수치를 낸다면 kube-state-metrics는 쿠버네티스 오브젝트의 수치를 내요.

하나: Namespace 매니페스트가 없고 kubectl이 대시보드 JSON을 매니페스트로 읽는다

대부분의 리소스가 monitoring 네임스페이스를 쓰는데 그 네임스페이스를 만드는 파일이 없어요. 그래서 네임스페이스부터 만들고 폴더 셋을 차례로 적용했어요.

master$ kubectl create namespace monitoring namespace/monitoring created master$ kubectl apply -f prometheus/ clusterrole.rbac.authorization.k8s.io/prometheus created clusterrolebinding.rbac.authorization.k8s.io/prometheus created configmap/prometheus-server-conf created daemonset.apps/node-exporter created service/node-exporter created deployment.apps/prometheus-deployment created service/prometheus-service created master$ kubectl apply -f kube-state/ clusterrole.rbac.authorization.k8s.io/kube-state-metrics created clusterrolebinding.rbac.authorization.k8s.io/kube-state-metrics created deployment.apps/kube-state-metrics created service/kube-state-metrics created serviceaccount/kube-state-metrics created master$ kubectl apply -f grafana/ deployment.apps/grafana created service/grafana created error: error validating "grafana/kubernetes-cluster-prometheus_rev1.json": error validating data: [apiVersion not set, kind not set]; if you choose to ignore these errors, turn validation off with --validate=false

→ 매니페스트는 모두 만들어졌고 grafana/ 폴더의 대시보드 JSON만 apiVersion·kind가 없는 매니페스트로 읽혀 검증 오류가 났다는 뜻이에요.

마지막 오류는 다른 리소스에 영향이 없었어요. 같은 폴더의 Deployment와 Service는 만들어졌어요. kubectl apply -f에 폴더를 주면 폴더 안의 .json 파일도 매니페스트로 읽기 때문에 생긴 오류예요. 이 JSON은 Grafana 화면에서 가져오는 대시보드 파일이라(12편) 폴더를 나누거나 YAML 파일만 골라서 적용하면 이 오류는 나지 않아요.

모든 파일이 created로 끝났다고 해서 고칠 곳이 없는 것은 아니었어요. 이 출력의 service/node-exporter created 한 줄이 6절에서 볼 문제의 원인이에요. 이때는 몰랐어요.

둘: kube-state-metrics 이미지가 2020년에 올라간 amd64 전용 이미지다

Docker Hub에서 이 태그를 조회하면 2020-01-07에 올라간 이미지 하나가 나와요. 플랫폼은 linux/amd64 하나뿐이에요. 이름을 보면 quay.io/coreos의 kube-state-metrics 이미지를 개인 계정에 옮겨 둔 것 같은데 내용이 원본과 같은지는 확인하지 않았어요. 원본 kube-state-metrics의 v1.8.0-rc.1은 2019-09-24에 나온 릴리스 후보이고 정식 v1.8.0의 README 호환표에는 Kubernetes 1.11~1.15까지만 적혀 있어요. 이 클러스터는 노드가 arm64이고 Kubernetes는 1.37.2예요. 그래서 이 이미지는 실행해 보지 않고 적용하기 전에 바꿨어요.

바꾼 이미지는 공식 레지스트리의 registry.k8s.io/kube-state-metrics/kube-state-metrics:v2.20.0이에요. v2.20.0은 2026-08-18에 나온 릴리스이고 README에는 이 이미지가 amd64, arm, arm64, ppc64le, s390x를 지원한다고 적혀 있어요. 이미지만 바꾸고 끝나지는 않았어요. 헬스체크 경로와 권한도 함께 바꿨어요.

# 강의 저장소 사본에서 git diff, kube-state/kube-state-Deployment.yaml (일부) - - image: liupeng0518/quay.io.coreos.kube-state-metrics:v1.8.0-rc.1 + - image: registry.k8s.io/kube-state-metrics/kube-state-metrics:v2.20.0 ... livenessProbe: httpGet: - path: /healthz + path: /livez port: 8080 ... readinessProbe: httpGet: - path: / + path: /readyz port: 8081

→ 이미지를 공식 v2.20.0으로, 컨테이너가 살아 있는지 보는 liveness 경로를 8080의 /livez로, 요청을 받을 준비가 됐는지 보는 readiness 경로를 8081의 /readyz로 바꿨다는 뜻이에요.

경로를 바꾼 근거는 README의 헬스체크 설명이에요. 메트릭 포트(8080)의 /healthz는 프로그램이 돌고 있으면 200으로 응답하므로 startup probe에 쓰라고 해요. 같은 포트의 /livez는 API 서버 장애의 영향을 받지 않은 상태면 200이라 liveness probe에, 자체 지표 포트(8081)의 /readyz는 요청을 받아 메트릭을 내놓을 준비가 됐을 때 200이라 readiness probe에 쓰라고 권해요. 공식 예제 Deployment도 같은 경로를 써요. 강의 매니페스트의 readiness 경로 /는 이 목록에 없는 경로예요.

ClusterRole은 v2.20.0 공식 예제(examples/standard/cluster-role.yaml)의 규칙으로 통째로 바꿨어요. 강의 판에는 공식 예제에 없는 extensions API 그룹이 들어 있었고 공식 예제에 있는 serviceaccounts, EndpointSlice, Lease, Ingress·IngressClass, RBAC 오브젝트, admission 정책 같은 리소스의 권한은 없었어요. 바꾼 뒤 공식 예제와 비교하면 규칙은 같고 metadata의 라벨만 달라요. 공식 예제 Deployment에 있는 securityContext(루트가 아닌 사용자로 실행, 읽기 전용 루트 파일시스템 등)는 이번에 옮기지 않았어요.

⚠️ 주의: 호환표에는 1.37이 아직 없어요
kube-state-metrics README의 호환표에서 v2.20.0은 client-go v1.36과 짝지어져 있어요. 이 클러스터는 1.37.2라서 마이너 버전이 하나 차이 나요. README는 최신 릴리스를 쓰라고 권하면서 아주 최근 쿠버네티스를 쓴다면 지원하는 리소스 전체를 쓰기 위해 아직 릴리스되지 않은 버전이 필요할 수도 있다고 덧붙여요. 이번 실습에서 필요했던 노드·파드·컨테이너 요청량 메트릭은 나왔지만(12편) 1.37에서 새로 생긴 리소스까지 읽는지는 확인하지 않았어요.

셋: 버전이 적혀 있지 않은 이미지와 받을 곳이 없는 경고

Prometheus·node-exporter·Grafana는 태그가 없거나 latest였어요. 이날 받은 Prometheus를 API로 물어보니 3.16.0이었고 Grafana는 13.3.0이었어요. 같은 매니페스트를 다음 달에 적용하면 다른 버전이 뜰 수 있어요. 이 글의 출력과 같은 결과를 보려면 이날 확인한 버전으로 태그를 적어 두는 것이 좋아요.

ConfigMap의 경고 설정도 하나 적어 둘게요. 경고를 보낼 곳이 alertmanager.monitoring.svc:9093으로 적혀 있는데 강의 저장소에는 Alertmanager 매니페스트가 없어서 이 주소를 받을 Service가 없어요. 경고 규칙 두 개 중 메모리 규칙은 kube_node_status_allocatable_memory_bytes를 분모로 쓰는데 우리 Prometheus에는 이 이름의 시계열이 0개였어요(이름이 바뀐 사정은 12편에서 다뤄요). 분모가 비어 있으면 식의 결과도 비기 때문에 이 규칙은 경고를 낼 수 없어요. 경고 화면은 이번에 확인하지 않았어요.

5. 수집 대상 14개가 모두 up인데 9100이 없다

적용 결과부터 볼게요. 롤아웃은 모두 성공했어요.

master$ kubectl -n monitoring rollout status deploy --timeout=300s; kubectl -n monitoring rollout status ds --timeout=300s; kubectl -n kube-system rollout status deploy/kube-state-metrics --timeout=300s Waiting for deployment "grafana" rollout to finish: 0 of 1 updated replicas are available... deployment "grafana" successfully rolled out deployment "prometheus-deployment" successfully rolled out daemon set "node-exporter" successfully rolled out deployment "kube-state-metrics" successfully rolled out master$ kubectl -n monitoring get pods -o wide | awk '{print $1, $2, $3, $4, $7}' | column -t; kubectl -n kube-system get pods -l app=kube-state-metrics -o wide | awk '{print $1, $2, $3, $4, $7}' | column -t NAME READY STATUS RESTARTS NODE grafana-6f6dd58ffc-nd9zq 1/1 Running 0 k8s-worker3 node-exporter-6z7xv 1/1 Running 0 k8s-worker1 node-exporter-dhpln 1/1 Running 0 k8s-worker2 node-exporter-dp4qx 1/1 Running 0 k8s-worker3 prometheus-deployment-54f6c75f48-p8c9r 1/1 Running 0 k8s-worker2 NAME READY STATUS RESTARTS NODE kube-state-metrics-849dd5cd8d-zzpgc 1/1 Running 0 k8s-worker1 master$ kubectl get svc -A | grep -E 'NAMESPACE|prometheus|grafana|node-exporter|kube-state' NAMESPACE NAME TYPE CLUSTER-IP EXTERNAL-IP PORT(S) AGE kube-system kube-state-metrics ClusterIP None <none> 8080/TCP,8081/TCP 2m19s kube-system node-exporter NodePort 10.102.57.138 <none> 9100:31672/TCP 2m19s monitoring grafana NodePort 10.106.61.19 <none> 3000:30004/TCP 2m18s monitoring prometheus-service NodePort 10.106.79.156 <none> 8080:30003/TCP 2m19s

지금 보면 이 출력에 원인이 다 들어 있어요. node-exporter 파드는 3개이고 Service는 파드와 다른 네임스페이스에 있어요. 그런데 daemon set "node-exporter" successfully rolled out은 성공으로 나왔어요. DaemonSet의 롤아웃 성공은 "배치하기로 한 노드에 다 떴다"는 뜻이지 "모든 노드에 떴다"는 뜻이 아니에요. 이 DaemonSet이 배치하기로 한 노드가 처음부터 3대였기 때문이에요(6절).

Prometheus는 NodePort 30003으로 열려 있어서 Mac에서 HTTP API로 바로 물어볼 수 있었어요.

그림 4. 14줄이 모두 up이었지만 노드 수치를 낼 9100은 한 줄도 없었다

Prometheus 버전은 3.16.0이었어요. 14개를 작업(job)별로 나누면 kubernetes-apiservers 1개, kubernetes-nodes 4개, kubernetes-cadvisor 4개, kube-state-metrics 1개, kubernetes-service-endpoints 4개예요. 노드 4대의 kubelet과 cAdvisor는 API 서버를 거쳐 /api/v1/nodes/<노드>/proxy/metrics 경로로 긁고 있었어요. 마지막 4개의 포트는 9153 두 개, 3000, 9090이에요. 9153은 CoreDNS 파드 두 개, 3000은 Grafana, 9090은 Prometheus 자신이에요. 이 목록 어디에도 9100은 없어요.

여기서 up이 무엇을 나타내는지 확인했어요. Jobs and instances 문서에 따르면 Prometheus는 대상을 한 번 긁을 때마다 up 시계열에 샘플을 하나 남겨요. 대상에 닿았으면 1, 수집이 실패했으면 0이에요. 그러니 up은 수집 대상 목록에 들어간 대상에만 있어요. 목록에 들어가지 못한 exporter는 up이 0이 되는 것이 아니라 up 시계열 자체가 없어요. "up이 0이면 알린다"는 규칙은 이 상황을 잡지 못하고 화면에는 초록색 up 14개만 남아요. 빨리 종료되는 파드로 같은 현상을 만난 적이 있어요. 서비스 디스커버리 목록에서 바로 빠진 파드는 up이 0이 아니라 아예 없는 상태가 됐는데 그 실험은 메트릭 수집 실습-2 : 앱이 죽으면 pull과 push는 다르게 조용해진다에서 다뤘어요.

그러면 Prometheus는 이 14개를 어떻게 골랐을까요. 답은 강의 ConfigMap의 scrape_configs에 있어요. 작업이 여섯 개 적혀 있어요. kube-state-metrics 작업만 주소를 직접 적었고(kube-state-metrics.kube-system.svc.cluster.local:8080) 나머지 다섯 개는 쿠버네티스 API에 물어 대상을 찾는 kubernetes_sd_configs를 써요.

📖 용어: 서비스 디스커버리 (kubernetes_sd_configs)
수집할 주소를 설정 파일에 직접 적지 않고 쿠버네티스 API에서 노드·Service·파드·엔드포인트 목록을 받아 수집 대상을 만드는 Prometheus 기능이에요. 설정 문서는 이 방식이 클러스터 상태와 늘 동기화된다고 설명해요. role 값(node, service, pod, endpoints, endpointslice 등)으로 무엇을 기준으로 대상을 만들지 정해요.

node-exporter가 들어갈 자리는 kubernetes-service-endpoints 작업이에요. 해당 부분만 옮기면 이래요.

# prometheus/prometheus-ConfigMap.yaml (강의 저장소, 일부) - job_name: 'kubernetes-service-endpoints' kubernetes_sd_configs: - role: endpoints relabel_configs: - source_labels: [__meta_kubernetes_service_annotation_prometheus_io_scrape] action: keep regex: true

→ Service의 엔드포인트 목록에서 대상을 찾되 그 Service에 prometheus.io/scrape 어노테이션이 true로 붙어 있는 대상만 남기라는 뜻이에요.

role: endpoints는 Service의 엔드포인트 목록에서 주소 하나, 포트 하나마다 대상을 하나씩 만들어요. 그 엔드포인트가 Service에 속해 있으면 Service의 메타데이터를 라벨로 붙여 주는데 Service의 어노테이션은 __meta_kubernetes_service_annotation_<이름> 라벨이 돼요. 라벨 이름에 쓸 수 없는 점과 슬래시가 밑줄로 바뀌어서 prometheus.io/scrape는 prometheus_io_scrape로 들어가요.

📖 용어: relabel (relabel_configs)
Prometheus가 찾아낸 대상의 라벨을 수집하기 전에 바꾸거나 조건에 맞지 않는 대상을 버리는 규칙이에요. 설정 문서에 따르면 keep 동작은 정규식에 맞지 않는 대상을 버려요. 강의 ConfigMap은 Service의 어노테이션으로 수집 여부·경로·포트를 정하는 데 relabel을 써요.

정리하면 node-exporter 파드가 수집 대상이 되려면 네 단계를 지나야 해요. 파드가 노드에 떠야 하고, Service가 그 파드를 골라 엔드포인트에 넣어야 하고, Prometheus가 그 엔드포인트를 발견해야 하고, relabel의 keep을 통과해야 해요. 고치기 전 상태를 이 네 단계에 맞춰 보면 그림 5와 같아요.

그림 5. 고치기 전에는 ②와 ④ 두 곳에서 끊겼고 ①에서는 마스터가 처음부터 빠져 있었다

6. 끊긴 곳은 두 군데였고 마스터는 처음부터 빠져 있었다

그림 6. 파드는 monitoring에 3개, Service는 kube-system에 있었고 Service의 엔드포인트는 비어 있었다

Service는 자기 네임스페이스의 파드만 고른다

그림 6의 첫 명령으로는 모든 네임스페이스에서 k8s-app=node-exporter 라벨이 붙은 파드를 찾았어요. 3개 모두 monitoring 네임스페이스에 있고 worker1~3에서 Running이에요. 둘째 명령으로는 kube-system에 있는 node-exporter Service의 EndpointSlice를 봤어요. PORTS와 ENDPOINTS가 모두 <unset>이었어요. Service가 고른 파드가 하나도 없다는 뜻이에요. 마지막 줄에서 Mac이 NodePort 31672로 보낸 요청도 000(응답을 받지 못함)으로 끝났어요. 요청을 넘겨줄 파드가 없는 Service였으니까요.

2편에서 본 대로 Service를 만들면 컨트롤 플레인이 셀렉터에 맞는 파드를 찾아 EndpointSlice를 채워요. 셀렉터는 k8s-app: node-exporter였고 파드의 라벨도 같았어요. 라벨이 맞는데 왜 하나도 고르지 못했을까요. 쿠버네티스 개념 문서에서는 이 규칙을 한 문장으로 적은 곳을 찾지 못했어요. 그래서 EndpointSlice를 채우는 컨트롤러 코드를 이 클러스터 버전(v1.37.2) 태그에서 직접 열어 봤어요.

// pkg/controller/endpointslice/endpointslice_controller.go (kubernetes v1.37.2, 406~407행) podLabelSelector := labels.Set(service.Spec.Selector).AsSelectorPreValidated() pods, err := c.podLister.Pods(service.Namespace).List(podLabelSelector)

→ Service의 셀렉터로 파드를 찾을 때 처음부터 그 Service와 같은 네임스페이스(service.Namespace)의 파드 목록 안에서만 찾는다는 뜻이에요.

이 코드가 EndpointSlice를 만드는 쪽이에요. Prometheus의 role: endpoints가 읽는 Endpoints 오브젝트는 다른 컨트롤러가 채우는데 같은 태그의 Endpoints 컨트롤러도 e.podLister.Pods(service.Namespace)로 파드를 찾아요. Endpoints는 v1.33부터 deprecated가 붙은 옛 API이지만 지금도 EndpointSlice와 함께 만들어져요(2편). Service 문서의 설명도 이와 맞아요. 셀렉터 없는 Service를 쓰는 예로 "다른 네임스페이스나 다른 클러스터의 Service를 가리키고 싶을 때"를 들고 그런 경우에는 셀렉터 없이 Service를 정의할 수 있다고 안내해요. 라벨이 맞아도 네임스페이스가 다르면 Service는 파드를 고르지 못해요.

⚠️ 주의: 다른 네임스페이스에 만들어도 created로 끝나요
강의 매니페스트를 적용할 때 service/node-exporter created가 나왔고 경고는 없었어요. kube-system에 셀렉터가 있는 Service를 만드는 요청 자체는 API 서버가 거절할 이유가 없기 때문이에요. 파드를 하나도 고르지 못한 상태는 오류가 아니라 "엔드포인트가 비어 있는 Service"로 남아요. 롤아웃 확인도 이 문제를 잡지 못했어요. 그래서 Service를 만든 뒤에는 kubectl -n <네임스페이스> get endpointslices -l kubernetes.io/service-name=<이름>로 주소가 들어갔는지 확인하세요. 한 파일 안에서 DaemonSet과 Service의 namespace가 서로 다르게 적혀 있다면 그 부분부터 의심해 볼 만해요.

수집 표시가 없었다

그림 6의 셋째 명령으로는 Service의 어노테이션을 출력했어요. 어노테이션은 kubectl apply가 남기는 last-applied-configuration 하나뿐이고 prometheus.io/scrape는 없었어요. 5절의 keep 규칙은 이 표시가 true인 Service만 남겨요. 그러니 Service가 파드를 제대로 골랐더라도 node-exporter 대상은 relabel 단계에서 버려졌을 거예요. 같은 강의 저장소의 prometheus-service와 grafana Service에는 prometheus.io/scrape: 'true'가 붙어 있어서 9090과 3000이 목록에 있었어요. CoreDNS의 9153이 목록에 있으니 그 Service에도 표시가 붙어 있어 keep 규칙을 통과했다는 뜻이에요.

이 표시는 Prometheus에 내장된 기능이 아니에요. 이 ConfigMap의 relabel 규칙이 정한 약속이에요. Prometheus 저장소의 쿠버네티스 예제 설정을 보면 같은 이름의 kubernetes-service-endpoints 작업에 이 규칙이 주석 처리된 예시로만 들어 있고 어노테이션 이름도 example.io/should_be_scraped로 적혀 있어요. 설정이 다른 Prometheus에서는 prometheus.io/scrape를 붙여도 아무 효과가 없을 수 있어요. Service에 붙일 표시는 그 클러스터의 Prometheus 설정을 열어 보고 정해야 해요.

마스터에는 처음부터 뜨지 않았다

마지막은 수집 대상 목록과는 따로 생긴 문제예요. node-exporter 파드는 3개였고 worker1~3에만 있었어요. 5편에서 본 대로 kubeadm은 마스터에 node-role.kubernetes.io/control-plane:NoSchedule taint를 붙이고 이 taint를 허용하는 toleration이 있는 파드만 마스터에 배치돼요. DaemonSet 문서의 표에 따르면 DaemonSet 컨트롤러가 자동으로 붙여 주는 toleration은 not-ready, unreachable, disk-pressure, memory-pressure, pid-pressure, unschedulable, network-unavailable이에요. control-plane taint는 이 목록에 없어요.

같은 문서의 예제 DaemonSet에는 control-plane toleration이 직접 적혀 있고 "컨트롤 플레인 노드에서도 돌게 하려는 toleration이니 컨트롤 플레인 노드에서 파드를 돌리지 않을 거라면 지우라"는 주석이 달려 있어요. 강의 매니페스트에는 이 toleration이 없었어요. 그래서 DaemonSet이 배치하기로 한 노드가 3대였고 롤아웃은 3개로 성공했어요. 3절의 kube-prometheus-stack이 띄운 node-exporter는 마스터를 포함해 4개였어요. 차트 값은 열어 보지 않았지만 결과로 보면 그쪽은 마스터에도 띄우는 구성이었어요.

마스터를 수집할지는 선택이에요. 하지만 이 실습에서 마스터는 API 서버·etcd·스케줄러가 도는 노드라서 그 노드의 CPU·메모리를 보지 못하면 컨트롤 플레인이 바쁠 때 원인을 찾기 어려워요. 그래서 마스터에도 띄우기로 했어요.

7. 고친 뒤: 노드 4대, 그리고 Last scrape

고친 곳은 세 군데이고 모두 같은 파일이에요.

# 강의 저장소 사본에서 git diff, prometheus/prometheus-DaemonSet-nodeexporter.yaml (주석 줄은 뺐다) spec: + tolerations: + - key: node-role.kubernetes.io/control-plane + operator: Exists + effect: NoSchedule containers: - image: prom/node-exporter ... name: node-exporter - namespace: kube-system + namespace: monitoring + annotations: + prometheus.io/scrape: 'true' + prometheus.io/port: '9100'

→ DaemonSet 파드가 마스터의 control-plane taint를 허용하게 하고 Service를 파드와 같은 monitoring 네임스페이스로 옮기면서 수집 표시와 포트(9100)를 붙였다는 뜻이에요.

prometheus.io/port는 relabel 규칙에서 대상 주소의 포트를 그 값으로 바꾸는 데 쓰여요. 이 Service는 포트가 9100 하나뿐이라 없어도 같은 주소가 나왔겠지만 어느 포트를 긁는지 Service에 적어 두는 쪽이 읽기 쉬워서 함께 붙였어요. 그리고 Service의 네임스페이스는 apply로 옮길 수 없어요. 네임스페이스가 다르면 다른 오브젝트라서 그대로 apply하면 kube-system의 옛 Service가 남아요. 그래서 옛 Service를 먼저 지웠어요.

그림 7. Service가 파드 4개를 고르자 Prometheus의 :9100 대상이 4개 생겼고 모두 up이었다

monitoring 네임스페이스의 EndpointSlice에는 포트 9100과 주소 4개(10.244.235.193, 10.244.194.84, 10.244.100.208 외 1개)가 들어갔어요. 10.244.235.193은 6편에서 본 마스터의 파드 블록 10.244.235.192/26 안의 주소라서 마스터에 뜬 node-exporter예요. 000이던 NodePort 31672도 이제 node_arp_entries, node_boot_time_seconds, node_context_switches_total 같은 node_ 메트릭을 내놓아요. Prometheus의 :9100 대상은 10.244.126.12, 10.244.194.84, 10.244.100.208, 10.244.235.193 네 개 모두 up이고 노드마다 시계열이 하나씩 나오는 node_uname_info를 세면 4예요.

이제 2절에서 미뤄 둔 질문이에요. Prometheus가 정말 긁어 가고 있는지는 어디서 볼 수 있을까요? Prometheus 웹 화면의 Status > Target health 페이지예요.

그림 8. Last scrape 열은 Prometheus가 각 대상에 마지막으로 요청한 시각과 걸린 시간을 보여 준다

풀(작업)마다 몇 개 중 몇 개가 up인지가 오른쪽에 있고 대상마다 Last scrape 열에 숫자 두 개가 있어요. 위의 숫자는 Prometheus가 그 대상에 마지막으로 요청을 보낸 뒤 지난 시간이고 아래 숫자는 그 요청에 걸린 시간이에요. kube-state-metrics는 3.766초 전에 긁었고 4ms 걸렸어요. API 서버는 1.118초 전에 110ms, cAdvisor는 worker2가 2.085초 전에 30ms, worker3이 2.556초 전에 21ms였어요. 화면 위의 "Hiding 1 empty pools"는 대상이 하나도 없는 풀 하나를 숨겼다는 안내예요. 그림 4의 목록에도 kubernetes-pods 작업의 대상은 하나도 없었으니 숨긴 풀은 그 작업으로 보여요. 이 작업에는 prometheus.io/scrape 표시가 붙은 파드만 남기는 규칙이 있어서 그런 파드가 없으면 비어요.

그림 9. node-exporter 4개에도 Last scrape가 찍혔다. 마지막으로 요청한 시각은 요청을 보낸 쪽만 알 수 있다

필터에 9100을 넣으면 node-exporter 대상 4개만 남아요. 풀 이름은 kubernetes-service-endpoints이고 8/8 up이에요. 고치기 전의 4개(CoreDNS 2개, Grafana, Prometheus)에 node-exporter 4개가 더해진 숫자예요. 대상마다 붙은 k8s_app="node-exporter", kubernetes_name="node-exporter", kubernetes_namespace="monitoring" 라벨은 relabel 규칙이 Service의 라벨·이름·네임스페이스를 옮겨 붙인 거예요. Last scrape는 5.477초, 6.606초, 7.906초, 8.447초 전이고 요청은 5~12ms 걸렸어요. 설정한 수집 주기 5초보다 긴 값도 있는데 이 화면은 페이지를 열고 5초를 기다린 뒤 필터를 입력하고 3초를 더 기다려 찍은 화면이에요. 그사이 화면이 대상 목록을 새로 받아 왔는지는 확인하지 않아서 이 숫자로 수집 간격을 따지지는 않을게요.

pull의 증거로 볼 것은 숫자의 크기가 아니라 이 열이 무엇을 재는가예요. node-exporter의 컨테이너 설정에는 Prometheus 주소가 한 줄도 없어요. node-exporter는 9100 포트를 열어 두고 기다릴 뿐이에요. "마지막으로 요청한 시각"과 "걸린 시간"은 요청을 보낸 쪽만 잴 수 있는 값이고 그 값이 Prometheus 화면에 대상마다 찍혀 있어요. 대상 목록이 만들어진 과정도 마찬가지예요. exporter가 자기를 알린 것이 아니라 Prometheus가 쿠버네티스 API에서 엔드포인트 목록을 읽어 대상을 만들었어요. 강의 구성에서 연결을 먼저 여는 쪽은 처음부터 끝까지 Prometheus였어요.

하나 더 적어 둘 것이 있어요. Prometheus 설정 문서는 role: endpoints 설명에서 Endpoints API가 Kubernetes v1.33 이상에서 deprecated이니 EndpointSlice를 쓰고 endpointslice role로 바꾸라고 권해요. 강의 ConfigMap은 endpoints role을 쓰고 이 클러스터에서는 그대로 동작했어요. 다음에 이 설정을 손볼 일이 있으면 같이 바꿀 생각이에요.

⚠️ 주의: 강의 매니페스트의 node-exporter는 노드가 아니라 컨테이너를 볼 수도 있어요
node_exporter README에는 node_exporter가 호스트 시스템을 감시하도록 만들어졌고 컨테이너로 띄울 때는 컨테이너 자신을 감시하지 않도록 따로 신경 써야 한다고 적혀 있어요. 예시는 호스트 네트워크와 호스트 PID 네임스페이스를 쓰고(--net="host" --pid="host") 호스트의 루트를 /host에 읽기 전용으로 붙인 뒤 --path.rootfs=/host를 주는 방식이에요. 강의 DaemonSet에는 이 중 어느 것도 없어요. 그래서 일부 수치는 노드가 아니라 node-exporter 컨테이너의 네트워크·파일시스템 기준일 수 있어요. 이번에는 값마다 노드 기준인지 컨테이너 기준인지 확인하지 않았어요. 쿠버네티스에서는 파드의 hostNetwork·hostPID 설정과 hostPath 마운트가 이 옵션들에 해당해요.

8. 인증 없이 열린 포트 세 개

이번에는 Mac에서 바로 확인하려고 강의의 NodePort를 그대로 썼어요. 그 결과 인증 없이 열린 포트가 셋 생겼어요. 이 글에서 쓴 curl은 모두 인증 정보 없이 성공했어요.

Prometheus(30003)는 모든 시계열을 조회하는 API가 열려 있어요. Prometheus 보안 모델 문서는 신뢰할 수 없는 사용자도 Prometheus의 HTTP 엔드포인트에 접근할 수 있다고 가정하고 그 사용자는 데이터베이스의 모든 시계열과 여러 운영 정보를 볼 수 있다고 설명해요. 그래서 Prometheus 구성 요소의 HTTP 엔드포인트를 인터넷 같은 공개 네트워크에 노출하지 말라고 강조해요. 시계열을 지우는 관리 API(--web.enable-admin-api)와 설정 재적재·종료(--web.enable-lifecycle)는 기본으로 꺼져 있고 강의 Deployment의 인자도 설정 파일과 저장 경로 두 개뿐이라 둘 다 꺼진 상태예요. Prometheus는 TLS와 HTTP 기본 인증을 지원해요.

node-exporter(31672)는 노드에 닿을 수 있는 사람이면 누구나 노드 수치를 읽을 수 있어요. 수집에는 Service의 엔드포인트만 쓰니 Prometheus 수집만 생각하면 NodePort는 필요 없어요.

Grafana(30004)는 Deployment의 환경 변수에 이렇게 적혀 있어요.

# grafana/grafana-Deployment.yaml (강의 저장소, 일부) - name: GF_AUTH_ANONYMOUS_ENABLED value: "true" - name: GF_AUTH_ANONYMOUS_ORG_ROLE value: Admin

→ 로그인하지 않은 사용자에게도 Grafana를 열어 주고 그 사용자에게 Admin 역할을 주라는 뜻이에요.

이 환경 변수는 Grafana 문서의 [auth.anonymous] 설정에 해당해요. enabled를 true로 두면 로그인 없이 Grafana에 접근할 수 있고 org_role은 예시 값이 Viewer이며 Editor와 Admin도 쓸 수 있어요. Grafana는 GF_로 시작하는 환경 변수로 설정 파일의 값을 덮어쓰기 때문에 이 매니페스트로 뜬 Grafana는 NodePort에 닿는 사람 누구에게나 로그인 없이 Admin 권한을 줘요. 데이터 소스와 대시보드를 바꿀 수 있는 권한이에요. Grafana 쪽 이야기는 12편에서 이어 가요.

💡 실무에서는: 실습이 끝나면 NodePort를 닫아요
• 이 실습의 192.168.64.x 노드 주소는 이 Mac 안에서만 닿는 주소라 위험이 Mac 밖으로 나가지는 않아요. 같은 매니페스트를 공인 IP가 붙은 노드에 적용하면 세 포트가 그대로 바깥에 열려요
• 화면이 필요할 때만 9편의 Headlamp와 같은 방식으로 Service를 ClusterIP로 두고 kubectl port-forward로 여세요. port-forward는 API 서버를 거치고 kubeconfig의 자격 증명이 필요해요
• Prometheus를 계속 열어 둬야 한다면 웹 설정 파일로 TLS와 기본 인증을 켜고 Grafana는 익명 접근을 끄거나 역할을 Viewer로 낮추세요
• node-exporter는 Prometheus가 클러스터 안에서 긁으니 NodePort 없이 ClusterIP로 충분해요
✍️ 오늘의 요약
노드마다 exporter를 띄워도 Prometheus의 수집 대상 목록에 들어가기 전까지는 아무도 그 수치를 가져가지 않아요.

Prometheus 공식 문서의 기본 수집 방식은 HTTP pull이고 push는 Pushgateway와 remote write, Alertmanager로 가는 경고에서 쓰여요. 강의 매니페스트에서는 node-exporter Service가 파드와 다른 네임스페이스에 있어 파드를 하나도 고르지 못했고 수집 표시도 없어서 node-exporter가 목록에 들어가지 못했어요. 마스터는 toleration이 없어 처음부터 빠져 있었어요. 목록에 없는 대상은 up이 0이 아니라 아예 없어서 14개가 모두 up인 화면은 빠진 것을 알려 주지 않았어요. Service를 monitoring으로 옮기고 표시와 toleration을 넣자 노드 4대가 모두 수집됐어요. 수집 대상 화면이 전부 초록색이라는 것은 목록에 있는 대상이 응답한다는 뜻이지 봐야 할 대상이 모두 목록에 있다는 뜻은 아니에요.
