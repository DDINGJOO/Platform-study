resource mapping not found for name: "old-deploy" namespace: "blog-75" from "manifests.yaml": no matches for kind "Deployment" in version "extensions/v1beta1" ensure CRDs are installed first

막힌 셋은 extensions/v1beta1 Deployment, policy/v1beta1 PodDisruptionBudget, autoscaling/v2beta2 HorizontalPodAutoscaler였어요. 각각 1.16, 1.25, 1.26에 서빙이 끝난 버전이에요. 72편에서 서버는 같은 HPA를 v1과 v2로 바꿔 보여 줬어요. 서버 코드에는 extensions 그룹의 Deployment를 apps 그룹과 같은 저장소로 묶은 줄도 남아 있어요. 그런데 옛 버전은 왜 바꿔 주지 않고 거절할까요?

이 글은 그 메시지가 어디서 나오는지 확인한 뒤 "버전을 언제 빼도 되는가"를 정한 deprecation policy가 2017년부터 어떻게 바뀌었는지 PR과 KEP 원문으로 따라가요. 실험 원본은 labs/devops/k8s-study/out/73-old-manifests-dry-run-scan.txt와 같은 디렉터리의 73-old-manifests-dry-run-scan.sh예요. 실험 네임스페이스는 blog-75를 썼고 파일 첫 줄 제목도 75로 적혀 있어요. 이 글은 그 파일의 1·2절을 인용하고 3·4절은 75편에서 인용해요.

1. no matches for kind는 그 버전을 서버가 더 이상 서빙하지 않는다는 뜻이다

먼저 질문 하나에 답할게요. 옛 YAML은 왜 안 먹을까요? 여섯 개를 한 번에 보낸 화면이에요.

그림 1. 통과 3개 중 하나는 경고가 붙었고 옛 버전 3개는 같은 메시지로 막혔어요.

72편의 strict decoding 오류와 모양이 달라요. 그 오류는 Error from server (BadRequest)로 시작했어요. 서버가 요청을 받아 본문을 풀다가 거절했다는 표시예요. 이번 메시지는 resource mapping not found로 시작하고 Error from server가 없어요. kubectl이 discovery 문서에서 그 kind와 apiVersion에 맞는 리소스를 찾지 못해 요청을 보낼 경로를 정하지 못한 것으로 읽혀요. 같은 groupVersion을 discovery에 직접 물어보면 이유가 보여요.

## 2. 각 groupVersion을 discovery에 직접 물으면 GET /apis/apps/v1 → 서빙 중 GET /apis/extensions/v1beta1 → (NotFound): the server could not find the requested resource GET /apis/policy/v1beta1 → (NotFound): the server could not find the requested resource GET /apis/autoscaling/v2beta2 → (NotFound): the server could not find the requested resource GET /apis/discovery.k8s.io/v1 → 서빙 중

막힌 셋의 groupVersion은 모두 NotFound였어요. 서버가 그 버전을 서빙 목록에서 뺐으니 kubectl은 매핑할 곳이 없어요. 덧붙은 "ensure CRDs are installed first"는 이 경우에 맞지 않는 안내예요. 내장 리소스의 옛 버전이라면 CRD를 설치할 일이 아니라 apiVersion을 지금 서빙하는 버전으로 바꿔야 해요. 58편 원자료의 extensions/v1beta1 Deployment도 같은 메시지였어요(labs/devops/k8s-study/out/58-kind-apiversion.txt).

📖 용어: 서빙 중단(no longer served)
이행 가이드(Deprecated API Migration Guide)는 옛 버전을 "no longer served"라고 적고 항목마다 "All existing persisted objects are accessible via the new API"를 붙여요. 그 버전의 REST 경로를 닫았을 뿐 이미 저장된 객체는 새 버전으로 그대로 읽을 수 있다는 뜻이에요. API 버전을 "제거했다"는 말은 대개 이 서빙 중단을 가리켜요.

그러면 서버는 왜 옛 버전을 받아서 새 버전으로 바꿔 주지 않을까요? 1.16의 사례를 보면 받을 수 없어서가 아니라 받지 않기로 정했기 때문이에요. 1.16 CHANGELOG는 extensions/v1beta1의 Deployment 등을 "no longer served by default"로 바꾸면서 --runtime-config로 임시로 다시 켤 수 있다고 적었어요. 1.18에 와서야 다시 켤 수도 없게 됐어요(#85903). 어떤 버전을 서빙할지는 정책이 정하고 서버는 그에 맞춰 경로를 열고 닫아요. 그 정책이 deprecation policy예요.

📖 용어: deprecation policy
쿠버네티스가 API 버전, 플래그, 기능을 deprecated로 표시하고 실제로 빼기까지 지켜야 할 규칙을 적은 문서예요. 이 글에서 다루는 것은 REST API 버전에 관한 Rule #4a와 #4b예요. 2026년 8월에 문서 위치가 /docs/reference/using-api/에서 /docs/reference/로 옮겨졌어요.

1.16의 이행이 특히 아팠던 이유도 이행 가이드에 남아 있어요. 이름만 바뀐 것이 아니었어요. Deployment 항목의 Notable changes예요.

* spec.rollbackTo is removed * spec.selector is now required and immutable after creation * spec.progressDeadlineSeconds now defaults to 600 seconds (the default in extensions/v1beta1 was no deadline) * spec.revisionHistoryLimit now defaults to 10 (the default in apps/v1beta1 was 2, the default in extensions/v1beta1 was to retain all) * maxSurge and maxUnavailable now default to 25% (the default in extensions/v1beta1 was 1)

→ selector를 반드시 적어야 하고, 적지 않은 칸의 기본값이 바뀐다는 뜻이에요. extensions/v1beta1에서 apiVersion 한 줄만 apps/v1으로 바꾸면 기한이 없던 롤아웃에 600초 기한이 생기고 maxSurge와 maxUnavailable이 1이던 롤링 업데이트가 25% 단위로 바뀌어요. DaemonSet은 updateStrategy 기본값이 OnDelete에서 RollingUpdate로 바뀌었어요. 저장된 객체는 서버가 변환해 줬지만 사람이 들고 있던 YAML, Helm 차트, 컨트롤러 코드는 사람이 고쳐야 했어요. apps/v1은 1.9부터 있었으니 1.16까지 일곱 릴리스 동안 옛 버전에 머물 수 있었던 셈이에요.

⚠️ apiVersion 한 줄만 바꾸고 끝내지 마세요
• 이행 가이드의 해당 릴리스 항목에서 Notable changes를 먼저 봐요. 필드 이름이 바뀌거나 기본값이 달라진 경우가 있어요. 1.22의 Ingress는 serviceName이 service.name으로 바뀌고 pathType이 필수가 됐어요
• 가이드가 안내하는 kubectl convert는 기본으로 설치되지 않는 플러그인이고 가이드 스스로 "This conversion may use non-ideal default values"라고 적어요. 변환 결과도 사람이 다시 읽어야 해요
• 고친 매니페스트는 kubectl apply --dry-run=server로 지금 서버가 받는지 확인해요

2. 첫 규칙은 beta 3개월이었고 뒤처진 노드에서 장애를 겪은 뒤 3릴리스로 늘었다

deprecation policy는 2016년 12월 5일 Tim Hockin이 연 website PR #1856으로 시작해 2017년 1월 3일에 들어갔어요. 첫 판의 Rule #4는 deprecated를 알린 뒤 옛 버전을 지원해야 하는 최소 기간을 이렇게 적었어요.

Rule #4: Other than the most recent API version in each track, older API versions must be supported after their announced deprecation for a duration of no less than: * GA: 1 year or 2 releases (whichever is longer) * Beta: 3 months or 1 release (whichever is longer) * Alpha: 0 releases

당시 문서는 릴리스 주기를 "approximately 3 months (4 per year)"로 봤어요. beta는 deprecated 뒤 한 릴리스만 버티면 뺄 수 있었어요. 지금 문서는 같은 예시에서 "approximately 4 months (3 per year)"라고 적어요. 첫 판 리뷰에는 Hockin이 lavalamp의 의견으로 GA 버전 제거를 "latter half of the calendar year"나 "odd-numbered releases"에만 하자는 제안을 옮긴 기록도 있어요. 지금 문서에는 그런 규칙이 없어요.

2017년 9월의 #5338에서 beta는 6개월 또는 2릴리스로 늘었어요. 저장 버전을 언제 올릴 수 있는지 정한 Rule #4b도 이때 들어왔어요. 큰 변화는 2018년 5월에 왔어요. Hockin이 연 #8666의 설명이에요.

Removing annotations caused a major outage with nodes that lagged the master. We used annotations as would-be fields, though we don't any more. Now we just add fields. That makes them part of the API version. These annotations are effectively part of the API version, too.

→ 필드처럼 쓰던 annotation을 지웠더니 마스터보다 버전이 뒤처진 노드에서 큰 장애가 났고, 그런 annotation도 API 버전의 일부로 봐야 한다는 뜻이에요. 리뷰에서 bgrant0607은 deprecation policy가 버전 skew 정책과 맞지 않는다고 짚었어요. "Which doesn't take into account the 2 minor releases of skew between the master and nodes." 이어서 kubelet이나 kube-proxy 같은 노드 에이전트가 쓰는 beta API나 annotation은 노드 에이전트가 그것을 쓰지 않게 된 뒤 최소 두 마이너 릴리스가 지나야 뺄 수 있다는 문장을 제안했어요.

📖 용어: 버전 skew(version skew)
클러스터 구성 요소끼리 허용하는 버전 차이예요. bgrant0607이 인용한 당시 정책은 노드가 마스터보다 두 마이너 릴리스까지 뒤처지는 것을 허용했어요. 업그레이드 중에는 API 서버와 노드의 버전이 한동안 다를 수 있어서 API 서버가 먼저 빼 버린 것을 오래된 노드가 아직 쓰고 있을 수 있어요.

그림 2. 1릴리스 규칙으로는 두 릴리스 뒤처진 노드가 쓰던 beta가 먼저 사라질 수 있어요.

#8666은 GA를 12개월 또는 3릴리스, beta를 9개월 또는 3릴리스로 늘리고 "This covers the maximum supported version skew of 2 releases"라는 이유를 붙여 2018년 5월 29일에 들어갔어요. 지금 문서도 같은 이유를 적어요. 이틀 뒤 들어간 liggitt의 #8825는 다른 쪽을 분명히 했어요. 이슈 #52185가 풀리기 전에는 저장된 적이 있는 버전을 코드에서 지울 수 없고 REST 경로의 서빙만 끌 수 있다는 내용이에요. 1장에서 본 "서빙 중단"과 "제거"의 구분을 정책 문서에 적은 것이 이 PR이에요.

3. beta에 시한을 걸었고(KEP-1635) 그래도 모자라 새 beta를 기본으로 껐다(KEP-3136)

3릴리스 규칙은 deprecated를 알린 뒤의 기간만 정했어요. deprecated를 알리지 않으면 beta는 얼마든지 남을 수 있었어요. 2019년 10월 deads2k가 작성한 KEP-1635의 Motivation이에요.

When a REST API reaches beta, it is turned on by default. This is great for getting feedback, but it can also lead to state where users and vendors start building important infrastructure against APIs that are not considered stable. In addition, once a REST API is on by default, the incentive to further stabilize appears to diminish. See the REST API that have been beta for a long time: CSRs and Ingresses as examples.

→ beta가 기본으로 켜지면 사용자와 벤더가 그 위에 중요한 인프라를 쌓고, 한번 켜진 뒤에는 GA로 다듬을 동기가 약해진다는 뜻이에요. KEP는 "a single actor has been cleaning up behind a lot of the project to unstick perma-beta APIs"라고도 적었어요. 2020년 소개 블로그는 Ingress를 두고 "did you realize that it actually went beta in 2015?"라고 물었어요.

📖 용어: KEP(Kubernetes Enhancement Proposal)
쿠버네티스에 기능이나 절차 변경을 제안하고 승인받는 문서예요. 동기, 목표, 하지 않을 것, 위험을 적고 kep.yaml에 alpha, beta, stable 단계를 몇 번째 릴리스에 밟을지 기록해요.

KEP-1635는 1.19에 stable이 됐고 beta에 시한을 정했어요. "every beta API will be deprecated in nine months and removed in 18 months." beta가 된 뒤 9개월(3릴리스) 안에 GA가 되거나 새 beta를 내야 하고, 그러지 못하면 세 번째 릴리스에 deprecated가 되고 다시 3릴리스 뒤에 빠져요. KEP의 예시는 1.16에 나온 v1beta1을 1.16~1.18 동안 평가하고 1.19에 deprecated, 1.22에 제거하는 순서예요. 영향 목록에는 cronjobs.v1beta1.batch를 비롯해 CSR, PSP, events, endpointslices, ingresses, runtimeclasses, PDB 등이 올랐어요.

이 시한은 코드 생성기에 들어가 있어요. v1.37.2의 storagemigration.k8s.io/v1beta1 타입에는 introduced=1.35, deprecated=1.37 태그는 있고 removed 태그는 없어요. 그런데 생성된 코드의 APILifecycleRemoved는 1.40을 돌려줘요. 생성 코드 주석은 removed를 적지 않으면 deprecated에 3을, deprecated를 적지 않으면 introduced에 3을 더한다고 적어요.

1.16부터 몇 릴리스에 걸쳐 오래 쓰인 beta가 빠졌어요. CHANGELOG와 이행 가이드에 남은 큰 묶음이에요.

1.16 묶음을 끊은 PR #70672는 2018년 11월 5일에 열려 2019년 6월 22일에 머지됐어요. 약 7.5개월이 걸렸어요. 이행 가이드의 마지막 항목은 1.32의 flowcontrol.apiserver.k8s.io/v1beta3이고 그 뒤 릴리스 항목은 없어요.

시한을 걸어도 beta는 여전히 기본으로 켜져 있었어요. 2022년 1월 13일에 작성된 KEP-3136은 그 기본값을 바꿨어요.

Beta APIs are not considered stable and reliance upon APIs in this state leads to exposure to bugs, guaranteed migration pain for users when the APIs move to stable, and the risk that dependencies will grow around unfinished APIs. Enabling beta APIs by default, exacerbates these problems by making them on in nearly every cluster. We observed these problems as we removed long-standing beta APIs and the PRR survey tells us that over 90% of cluster-admins leave production clusters with these APIs enabled.

→ 오래된 beta를 빼면서 이 문제들을 겪었고 설문에서 클러스터 관리자의 90% 이상이 운영 클러스터에서 beta API를 켜 둔 채로 둔다는 결과가 나왔다는 뜻이에요. KEP는 "This is now practical to do since conformance no longer relies on non-stable APIs."라고 덧붙여요. 그 전제는 KEP-1333의 "A production distribution should not be required to enable non-GA features or REST APIs in order to pass conformance tests."예요. KEP-1333에는 kube-scheduler가 1.16에서 실수로 beta Events API를 쓰게 된 사례도 적혀 있어요.

범위는 좁혀 뒀어요. 이미 있던 beta와 그 beta의 새 버전은 계속 기본으로 켜 두고 1.24부터 새로 나오는 beta API만 기본으로 꺼요. feature gate의 기본값(alpha 꺼짐, beta 켜짐)은 바꾸지 않는다고 Non-Goal에 적었어요. 위험 절에는 "Adoption of beta features will slow. Given how kubernetes is now treated, this is a good thing, not a bad thing."이라는 문장이 있어요. 기본으로 꺼진 beta를 쓰려면 관리자가 API 서버 플래그로 켜야 해요.

📖 용어: --runtime-config
kube-apiserver가 어떤 API 그룹, 버전, 리소스를 서빙할지 켜고 끄는 플래그예요. KEP-3136은 그룹/버전/리소스=true 형식으로 리소스 하나만 켤 수 있게 넓혔어요. 1.16 CHANGELOG가 옛 workload API를 임시로 다시 켜는 방법으로 안내한 것도 이 플래그예요.

우리 클러스터에서 확인했어요. API 서버에는 --runtime-config와 --feature-gates가 없었고 서빙 중인 alpha·beta groupVersion은 Calico가 설치한 CRD의 policy.networking.k8s.io/v1alpha2 하나였어요(labs/devops/k8s-study/out/59-alpha-beta-served.txt). 내장 alpha·beta는 0개예요. 1.37 CHANGELOG는 Workload와 PodGroup을 scheduling.k8s.io/v1beta1로 올렸다고 적지만 우리 클러스터에서 /apis/scheduling.k8s.io/v1beta1은 NotFound였어요(labs/devops/k8s-study/out/72-discovery-storage-version-hash.txt 4절). 새로 beta가 된 리소스는 기본으로 꺼진다는 KEP-3136과 맞는 결과예요.

💡 내 클러스터에서 켜진 alpha·beta를 보는 법
• kubectl api-versions | grep -E 'alpha|beta'로 서빙 중인 것을 봐요
• 나온 그룹이 내장인지 CRD인지는 kubectl get crd로 구분해요. 우리 클러스터의 v1alpha2는 Calico가 설치한 CRD였어요
• kube-apiserver 정적 파드 매니페스트에서 --runtime-config를 찾아 누가 무엇을 켰는지 봐요
⚠️ 문서끼리 숫자가 다른 곳이 있어요
• API 개요 문서(using-api)는 기본으로 켜지는 예외를 "beta versions of APIs introduced prior to Kubernetes 1.22"라고 적지만 KEP-3136과 CHANGELOG-1.24는 1.24부터라고 적어요
• 1.16 CHANGELOG는 extensions/v1beta1 Ingress의 서빙 중단을 "in v1.20"이라고 예고했지만 2019년 블로그의 지금 판과 이행 가이드, 실제 중단은 1.22예요. 바뀐 경위는 확인하지 못했어요
• 날짜와 버전은 CHANGELOG와 이행 가이드를 함께 보고 실제 클러스터에서 api-versions로 확인하는 편이 안전해요

4. GA는 major 버전 안에서 지우지 않기로 했다

2022년 1월 liggitt가 연 website #31389는 GA 쪽 규칙을 바꿨어요. 새 문장은 "GA API versions may be marked as deprecated, but must not be removed within a major version of Kubernetes"예요. 그 전까지 GA도 deprecated 뒤 12개월 또는 3릴리스가 지나면 뺄 수 있었어요. 리뷰에서 Hockin이 이 변경의 목적을 이렇게 적었어요.

The whole point of this thread is to assure users that using GA things is SO MUCH better than using beta things that they don't need to use beta in prod.

→ GA를 쓰는 것이 beta를 쓰는 것보다 확실히 낫다고 보장해서 운영 환경에서 beta를 쓸 이유를 없애자는 뜻이에요.

반대 의견도 있었어요. sftim은 "The X Window System ended up really struggling with its legacy of APIs."라며 아무도 쓰지 않는 API를 계속 광고하게 될 위험을 들어 "I'm opposed to a flat MUST NOT here."라고 적었어요. 그는 쿠버네티스 v2.x 같은 major 버전에서는 뺄 수 있게 하자고 했어요. liggitt는 "there are no current plans for a v2.x stream"이라고 답하고 그런 문장이 stable API를 버리는 v2의 동기가 될까 걱정했어요. 생태계가 python2와 python3처럼 갈라지는 것을 예로 들었어요. smarterclayton은 Linux syscall이 10년 넘게 안정적이었다는 점을 들며 v1을 바꾸는 대신 옆에 새 API를 두자고 했어요. 그가 든 예가 "endpoint to endpoint slice"였어요.

문장은 그대로 들어갔고 2022년 9월 #36663이 KEP-1635, KEP-3136과 함께 지금의 Rule #4a 문구로 정리했어요. 지금 문서에는 "There are no current plans for a major version revision of Kubernetes that removes GA APIs."라는 note도 있어요.

smarterclayton이 든 예는 실제로 그렇게 됐어요. 1.33 CHANGELOG는 "The v1 Endpoints API is now officially deprecated (though still fully supported). The API will not be removed, but all users should use the EndpointSlice API instead."라고 적어요. 도입부의 dry-run에서 v1 Endpoints가 경고와 함께 통과한 이유예요. 그 경고 문구 v1 Endpoints is deprecated in v1.33+; use discovery.k8s.io/v1 EndpointSlice에는 언제부터 못 쓰는지 알리는 부분이 없어요.

그림 3. beta는 시한이 정해져 있고 GA는 deprecated가 되어도 major 버전 안에서는 남아요.

여기까지의 규칙은 모두 "서빙"에 관한 것이에요. #8825가 적은 대로 저장된 적이 있는 버전은 서빙을 끊어도 API 서버가 계속 읽을 줄 알아야 해요. 지금 문서도 "Until #52185 is resolved, no API versions that have been persisted to storage may be removed."라고 적어요. 그러면 etcd에 옛 버전으로 저장된 객체는 언제 새 버전으로 바뀌고, 서버는 언제 그 버전의 코드를 버릴 수 있을까요? 서빙 목록만 봐서는 답이 나오지 않는 질문이에요.

📝 정리

no matches for kind는 서버가 그 groupVersion을 더 이상 서빙하지 않아 kubectl이 보낼 경로를 찾지 못했다는 뜻이에요. 1.37 서버에서 extensions/v1beta1, policy/v1beta1, autoscaling/v2beta2는 discovery에서 모두 NotFound였어요. 서버가 변환할 줄 몰라서가 아니라 deprecation policy에 따라 서빙을 끊은 것이고, 옛 YAML을 고칠 때는 apiVersion과 함께 바뀐 필드와 기본값도 고쳐야 해요.

규칙의 숫자는 겪은 일을 따라 바뀌었어요. 2017년 첫 판의 beta 3개월·1릴리스는 뒤처진 노드에서 장애를 겪은 뒤 2018년에 2릴리스 skew를 덮는 3릴리스가 됐어요. beta가 영구 의존성이 되자 KEP-1635(1.19)가 시한을 걸었고 KEP-3136(1.24)이 새 beta를 기본으로 껐어요.

GA는 2022년부터 major 버전 안에서 지우지 않아요. 바꾸고 싶으면 옆에 새 API를 두고 옛 것은 deprecated로 남겨요. 1.33의 v1 Endpoints가 그 예예요.
