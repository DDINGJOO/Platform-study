3편. VM으로 실습 노드를 만들 때 네트워크를 두 개 붙이는 이유
4편. kubeadm 설치 전에 swap을 꺼야 하는 이유
5편. kubeadm init이 만드는 인증서와 kubeconfig, 정적 파드 ← 지금 이 글
6편. kubeadm 다음에 CNI를 따로 설치해야 하는 이유
7편. 노드를 재시작한 직후의 Ready를 믿으면 안 되는 이유

./lab up이 마스터 VM에서 실행한 kubeadm init 부분만 로그에서 잘라 봤어요. 명령은 한 줄인데 출력은 80줄이 넘었습니다. 줄마다 [certs], [kubeconfig] 같은 단계 이름이 앞에 붙어 있었고 가장 많은 것은 인증서를 만들었다는 [certs] 15줄이었어요. 그다음이 [bootstrap-token] 8줄, 구성 요소 상태를 확인한 [control-plane-check] 7줄, [kubeconfig] 6줄 순이었습니다. 컨트롤 플레인을 띄우는 명령인데도 출력의 상당 부분은 프로그램을 실행했다는 말이 아니라 파일을 만들었다는 보고였어요.

이 글에서는 그 출력을 위에서부터 차례로 읽어 볼게요. 질문은 두 가지예요. kubeadm init 한 줄은 무엇을 만드는가. 그리고 kubeadm join은 처음 만나는 워커와 마스터가 무엇을 근거로 서로를 믿게 하는가. 실습 환경은 Apple Silicon Mac에 띄운 Lima VM 4대(마스터 1대, 워커 3대)이고 쿠버네티스는 v1.37.2예요.

이 글에서 다룰 것
· init에 넘긴 설정 파일의 각 줄이 없으면 무엇이 잘못될까?
· init 출력 맨 앞의 경고 두 줄은 무시해도 될까?
· API 서버가 아직 없는데 API 서버 파드는 누가 띄울까?
· 처음 만나는 워커와 마스터는 무엇으로 서로를 확인할까?
· Mac에서는 IP로 접속하는데 인증서는 왜 이름으로 확인할까?

1. 기본값에 맡기면 NIC 두 개 중 엉뚱한 쪽이 골라질 수 있다

kubeadm init은 플래그로도 설정을 받지만 우리는 설정 파일을 하나 만들어 --config로 넘겼어요. 마스터 준비 스크립트 scripts/master-init.sh가 VM 안에서 이 파일을 작성하고 바로 init을 실행합니다. 마스터에 남은 파일에서 주석만 빼고 옮기면 이래요.

master$ sudo cat /etc/kubernetes/kubeadm-config.yaml apiVersion: kubeadm.k8s.io/v1beta4 kind: InitConfiguration localAPIEndpoint: advertiseAddress: 192.168.104.1 bindPort: 6443 nodeRegistration: name: k8s-master criSocket: unix:///run/containerd/containerd.sock --- apiVersion: kubeadm.k8s.io/v1beta4 kind: ClusterConfiguration clusterName: k8s-lab kubernetesVersion: v1.37.2 apiServer: certSANs: - k8s-master - 192.168.64.2 - 127.0.0.1 networking: podSubnet: 10.244.0.0/16 serviceSubnet: 10.96.0.0/12 --- apiVersion: kubelet.config.k8s.io/v1beta1 kind: KubeletConfiguration cgroupDriver: systemd

→ 노드 한 대의 설정(InitConfiguration), 클러스터 전체 설정(ClusterConfiguration), kubelet 설정(KubeletConfiguration) 세 문서를 ---로 이어 붙인 파일이에요. 192.168.104.1과 192.168.64.2는 스크립트가 실행될 때 마스터의 eth0과 lima1에서 읽어 넣은 값입니다.

한 줄씩 보면 대부분은 "이 값을 비워 두면 무엇이 잘못 잡히나"라는 질문의 답이에요.

advertiseAddress는 API 서버가 자기 주소라고 알리는 IP이고 워커는 join할 때 이 주소로 접속해요. 비워 두면 kubeadm은 기본 게이트웨이가 연결된 NIC(네트워크 인터페이스)에서 IP를 고릅니다. 공식 문서에 따르면 게이트웨이가 둘 이상일 때는 처음 찾은 것을 쓰는데 그 순서는 OS와 커널 버전에 따라 다를 수 있어요. 우리 VM에는 NIC가 둘 있어요. 하나는 VM끼리 통하는 eth0(192.168.104.0/24)이고 다른 하나는 Mac에서 VM으로는 닿지만 VM끼리는 통하지 않는 lima1(192.168.64.0/24)이에요. lima1 쪽 IP가 골라지면 워커는 닿지 않는 주소로 API 서버를 찾아가게 돼요. NIC가 둘인 VM에서는 주소를 기본값에 맡기지 않고 직접 적어야 했어요.

nodeRegistration.name은 노드 객체의 이름이에요. 비워 두면 머신의 호스트 이름을 쓰는데 Lima가 붙인 호스트 이름은 lima-k8s-master였어요. 이 이름은 kubelet이 API 서버에 내미는 클라이언트 인증서의 CN(인증서 주인의 이름을 적는 칸)에도 들어갑니다. 워커도 join 명령 끝에 --node-name k8s-worker1을 붙여 이름을 정했어요.

certSANs는 API 서버 인증서에 추가로 넣을 이름이에요. Mac의 kubectl은 마스터의 lima1 IP인 192.168.64.2로 접속하는데 이 IP가 인증서에 없으면 TLS 검증 단계에서 접속이 거절돼요.

📖 용어: SAN (Subject Alternative Name)
서버 인증서에 적힌 "이 인증서가 유효한 DNS 이름과 IP 목록"이에요. 클라이언트는 자기가 접속한 주소가 이 목록에 있는지 확인하고 없으면 연결을 끊어요. kubeadm은 기본 이름들을 알아서 넣고 certSANs에 적은 이름을 거기에 더합니다.

podSubnet · serviceSubnet은 파드와 서비스가 쓸 IP 대역이에요. 서비스 대역 10.96.0.0/12는 kubeadm 기본값과 같은 값을 눈에 보이게 적어 둔 것이고 파드 대역은 사정이 달랐어요. 공식 문서는 파드 네트워크가 호스트 네트워크와 겹치면 문제가 생기기 쉬우니 겹칠 때는 다른 대역을 골라 init과 네트워크 플러그인 설정 양쪽에 넣으라고 안내해요. Calico 설치 문서와 매니페스트 주석에서 예로 드는 파드 대역 192.168.0.0/16은 VM 대역 두 개를 모두 포함해요. 그래서 파드 대역은 겹치지 않는 10.244.0.0/16으로 정했어요. Calico가 이 값을 따르게 한 방법은 6편에서 다룹니다.

cgroupDriver: systemd는 사실상 효력이 없는 줄이에요. 4편에서 본 대로 v1.34부터 kubelet은 이 값을 무시하고 컨테이너 런타임(containerd)에 cgroup 드라이버를 물어 정해요. 실제로 효력이 있는 쪽은 containerd 설정의 SystemdCgroup = true입니다.

💡 실무에서는: 컨트롤 플레인 IP는 처음에 정하고 바꾸지 않는다
advertiseAddress로 적은 IP는 API 서버와 etcd 인증서 안에 들어가요(3절 출력). 공식 문서에 따르면 이 IP를 바꾸려면 인증서를 새로 서명하고 해당 구성 요소를 재시작해야 해요. 그래서 ./lab up은 이미 만든 클러스터를 다시 켤 때 설정 파일의 advertiseAddress와 현재 eth0 IP를 비교합니다. 둘이 다르면 "마스터 IP 가 바뀌었습니다" 경고를 내고 클러스터가 정상 동작하지 않으면 지우고 새로 만들라고 안내해요.

2. 경고 두 줄은 노드 이름을 DNS에서 찾지 못했다는 뜻이었다

init을 실행하면 맨 먼저 preflight(사전 점검)가 돌아요. 여기서 경고가 두 줄 나왔어요.

[preflight] Running pre-flight checks [WARNING Hostname]: hostname "k8s-master" could not be reached [WARNING Hostname]: hostname "k8s-master": lookup k8s-master on 127.0.0.53:53: server misbehaving

→ 노드 이름 k8s-master를 DNS로 조회했는데 VM 안의 DNS 리졸버(127.0.0.53)가 그런 이름은 모른다고 답했다는 뜻이에요.

원인은 1절에서 정한 노드 이름이에요. k8s-master는 kubeadm에 넘긴 이름일 뿐 VM의 호스트 이름(lima-k8s-master)이 아니고 어느 DNS에도 등록돼 있지 않아요. 공식 문서의 preflight 목록에서도 이 항목("host name cannot be reached via network lookup")은 오류가 아니라 경고로 분류돼 있어요. 오류로 분류된 항목이었다면 init은 여기서 멈췄을 거예요.

무시해도 된다고 판단한 근거는 두 가지예요. 첫째, 이 클러스터에는 노드를 이름으로 찾아가는 곳이 없어요. API 서버 주소, join 명령의 접속 주소, 각 노드 kubelet의 --node-ip가 모두 IP로 적혀 있어요. 둘째, kubeadm은 API 서버가 kubelet에 접속할 때 쓸 주소의 우선순위를 InternalIP,ExternalIP,Hostname으로 정해 둡니다. 공식 문서에 따르면 노드 호스트 이름을 해석할 수 없는 환경에서도 kubectl logs 같은 통신이 되도록 이렇게 정한 거예요. 실제로 노드 4대가 모두 Ready가 됐고 워커의 join에서도 같은 경고 두 줄이 나왔지만 조인은 끝까지 진행됐어요. 경고는 이름을 못 찾았다는 뜻이고 이 클러스터는 이름이 아니라 IP로 서로를 찾아요.

3. [certs] 15줄은 CA 셋과 그 CA가 서명한 인증서다

컨트롤 플레인 구성 요소들은 서로 네트워크로 통신해요. API 서버는 etcd에, controller-manager와 scheduler는 API 서버에, API 서버는 다시 각 노드의 kubelet에 접속합니다. 상대를 확인할 수단이 없으면 같은 네트워크에 붙은 다른 프로그램이 API 서버나 kubelet 행세를 해도 구분할 수 없어요. 그래서 kubeadm은 맨 먼저 클러스터 전용 CA를 만들어요.

📖 용어: CA (Certificate Authority, 인증 기관)
다른 인증서에 서명해 주는 인증서와 키 쌍이에요. 상대가 내민 인증서에 이 CA의 서명이 있는지 확인할 수 있으면 그 상대를 클러스터가 인정한 구성 요소로 믿을 수 있어요. kubeadm이 만든 CA는 /etc/kubernetes/pki/ca.crt와 ca.key예요.
그림 1. kubelet을 켜기 전에 [certs] 15줄과 [kubeconfig] 6줄이 먼저 찍힌다

출력의 Generating 줄은 11개예요. 그중 셋은 CA(ca, front-proxy-ca, etcd/ca)이고 sa는 인증서가 아니라 ServiceAccount 토큰 서명에 쓰는 키 쌍이에요. 나머지 일곱 개는 CA가 서명한 인증서입니다. API 서버의 서버 인증서, API 서버가 kubelet과 etcd에 접속할 때 쓰는 클라이언트 인증서, etcd끼리 통신하거나 etcd 상태를 확인할 때 쓰는 인증서 등이에요. 만든 파일은 /etc/kubernetes/pki에 .crt와 .key 짝으로 남고 etcd용은 그 아래 etcd/ 폴더에 있어요.

이 중 가장 눈여겨볼 줄은 API 서버 인증서가 어떤 이름으로 서명됐는지 보여 주는 줄이에요.

[certs] apiserver serving cert is signed for DNS names [k8s-master kubernetes kubernetes.default kubernetes.default.svc kubernetes.default.svc.cluster.local] and IPs [10.96.0.1 192.168.104.1 192.168.64.2 127.0.0.1]

→ API 서버 인증서는 이 DNS 이름 5개와 IP 4개 중 하나로 접속한 클라이언트에게만 유효하다는 뜻이에요.

이름마다 출처가 있어요. kubernetes로 시작하는 넷은 kubeadm이 항상 넣는 기본 이름이고 10.96.0.1은 서비스 대역의 첫 주소이자 클러스터 안의 파드가 API 서버를 찾아갈 때 쓰는 kubernetes 서비스의 주소예요. k8s-master는 노드 이름에서, 192.168.104.1은 advertiseAddress에서 왔어요. 192.168.64.2와 127.0.0.1은 certSANs로 더한 이름입니다. 127.0.0.1이 들어 있으니 VM 안에서 https://127.0.0.1:6443으로 접속해도 검증을 통과해요. 1절 설정 파일의 값이 실제로 남는 곳이 바로 이 인증서예요.

인증서 다음은 [kubeconfig] 6줄이에요. 첫 줄은 폴더를 알리고 나머지 다섯 줄은 파일을 하나씩 썼다는 보고예요.

📖 용어: kubeconfig
API 서버 주소, 그 서버를 확인할 CA 인증서, 내가 누구인지 증명할 클라이언트 인증서와 키를 한 파일에 담은 접속 설정이에요. kubectl도, controller-manager와 scheduler도 이 파일을 읽어 API 서버에 접속해요.

다섯 파일은 쓰는 주체가 각각 달라요. kubelet.conf, controller-manager.conf, scheduler.conf는 이름 그대로 각 구성 요소가 자기 신원으로 접속할 때 써요. admin.conf는 관리자와 kubeadm 자신이 쓰는 파일이에요. 이 파일에 든 인증서의 그룹은 kubeadm:cluster-admins이고 init이 이 그룹에 클러스터 관리자 권한을 묶어 둡니다. super-admin.conf의 그룹은 system:masters인데 이 그룹은 RBAC(역할별 권한 규칙)를 아예 거치지 않아요. 공식 문서에서는 RBAC 설정을 잘못해 클러스터에 접근할 수 없게 된 비상 상황에 쓰는 파일이라고 설명합니다.

⚠️ 주의: admin.conf를 노드 밖으로 꺼낼 때
실습이라서 Mac용 kubeconfig를 admin.conf에서 만들었어요(6절). 하지만 공식 문서는 admin.conf를 컨트롤 플레인 노드에 두고 다른 사용자와 공유하지 말라고 하고 super-admin.conf는 안전한 곳에 따로 보관하라고 해요. 두 파일 모두 인증 키가 그대로 들어 있기 때문이에요. 여러 사람이 쓰는 클러스터라면 kubeadm kubeconfig user로 사용자별 파일을 따로 만들어 나눠 줍니다.

4. API 서버를 띄우는 건 kubeadm이 아니라 kubelet이다

여기서 순서 문제가 하나 생겨요. 보통 파드는 먼저 API 서버에 등록되고 스케줄러가 노드를 정한 뒤 그 노드의 kubelet이 띄워요(2편). 그런데 지금 띄우려는 것이 바로 API 서버와 스케줄러예요. 아직 아무것도 떠 있지 않으니 그 경로를 쓸 수 없어요.

kubeadm은 이 문제를 정적 파드로 풀어요. 컨트롤 플레인 구성 요소를 직접 실행하지 않고 파드 정의 파일 네 개를 /etc/kubernetes/manifests에 써 둔 뒤 kubelet을 켜요.

📖 용어: 정적 파드 (static Pod)
API 서버를 거치지 않고 kubelet이 특정 폴더의 매니페스트 파일을 직접 읽어 띄우는 파드예요. 폴더에 파일이 생기면 띄우고 사라지면 지워요. API 서버에는 "미러 파드"로 보이기만 해서 kubectl로 미러 파드를 지워도 kubelet은 정적 파드를 지우지 않고 미러 파드를 다시 만들어요.
[etcd] Creating static Pod manifest for local etcd in "/etc/kubernetes/manifests" [control-plane] Using manifest folder "/etc/kubernetes/manifests" [control-plane] Creating static Pod manifest for "kube-apiserver" [control-plane] Creating static Pod manifest for "kube-controller-manager" [control-plane] Creating static Pod manifest for "kube-scheduler" master$ ls /etc/kubernetes/manifests etcd.yaml kube-apiserver.yaml kube-controller-manager.yaml kube-scheduler.yaml

→ etcd와 컨트롤 플레인 구성 요소 셋의 파드 정의를 파일로 썼고 마스터의 그 폴더에 실제로 파일 네 개가 남아 있다는 뜻이에요. 워커의 같은 폴더는 비어 있어요.

그다음 kubeadm은 kubelet 설정 파일을 쓰고 kubelet을 켠 뒤 정적 파드가 뜨기를 기다려요.

[kubelet-start] Starting the kubelet [wait-control-plane] Waiting for the kubelet to boot up the control plane as static Pods from directory "/etc/kubernetes/manifests" [kubelet-check] Waiting for a healthy kubelet at http://127.0.0.1:10248/healthz. This can take up to 4m0s [kubelet-check] The kubelet is healthy after 330.1µs [control-plane-check] Waiting for healthy control plane components. This can take up to 4m0s [control-plane-check] Checking kube-apiserver at https://192.168.104.1:6443/livez [control-plane-check] Checking kube-controller-manager at https://127.0.0.1:10257/healthz [control-plane-check] Checking kube-scheduler at https://127.0.0.1:10259/livez

→ kubelet을 켜고 매니페스트 폴더의 정적 파드로 컨트롤 플레인이 뜨기를 기다리며 세 구성 요소의 상태 확인 주소(/livez, /healthz)를 차례로 확인했다는 뜻이에요.

이어지는 세 줄에서 세 구성 요소 모두 healthy로 확인됐어요. controller-manager와 scheduler는 밀리초 단위로 응답했고 API 서버는 초 단위로 가장 늦었어요. 기다리는 동안 kubeadm은 상태 확인 주소에 요청을 보내 보기만 했어요.

정리하면 kubeadm은 매니페스트를 쓰는 데까지만 하고 컨트롤 플레인을 실제로 띄우고 지켜보는 쪽은 kubelet이에요. 1편에서 본 kube-system 목록에서 이 네 파드의 소유자(OWNER)가 Node로 나오고 이름 끝에 노드 이름 -k8s-master가 붙어 있던 것도 이 때문이에요.

API 서버가 응답하고 나면 출력의 성격이 바뀌어요. 이제부터는 디스크가 아니라 API 서버에 객체를 만듭니다. [upload-config]는 init에 넘긴 설정을 kube-system의 ConfigMap(설정 값을 담아 두는 쿠버네티스 객체) kubeadm-config에, kubelet 공통 설정을 kubelet-config에 저장해요. 워커의 join 출력에는 kubeadm-config를 읽었다는 줄이 나오는데 그게 바로 이 ConfigMap이에요. [upload-certs]는 컨트롤 플레인 인증서를 Secret으로 올리는 단계인데 --upload-certs를 주지 않아서 건너뛰었어요.

[mark-control-plane] Marking the node k8s-master as control-plane by adding the labels: [node-role.kubernetes.io/control-plane node.kubernetes.io/exclude-from-external-load-balancers] [mark-control-plane] Marking the node k8s-master as control-plane by adding the taints [node-role.kubernetes.io/control-plane:NoSchedule]

→ 마스터에 컨트롤 플레인임을 나타내는 라벨 두 개와 일반 파드를 배치하지 말라는 taint 하나를 붙였다는 뜻이에요.

📖 용어: taint (테인트)
노드에 붙이는 "이 표시를 견디겠다고 밝힌 파드만 받는다"는 표시예요. NoSchedule taint가 붙은 노드에는 파드 정의에 그 taint를 허용하는 toleration이 있는 파드만 스케줄러가 배치해요.

공식 문서에 따르면 보안상의 이유로 기본적으로 컨트롤 플레인 노드에는 파드를 스케줄하지 않아요. 2편에서 hello 파드를 만들었을 때 스케줄러가 마스터를 후보에서 뺀 것도 이 taint 때문이에요. 반대로 이 taint를 견디는 설정(toleration)이 있는 파드는 마스터에도 배치될 수 있어요. coredns가 그런 파드라서 1편에서 coredns가 마스터에 없었던 이유를 이 taint 때문이라고 단정할 수는 없어요. 노드 한 대로 실습할 때는 kubectl taint nodes --all node-role.kubernetes.io/control-plane-로 이 taint를 지워 마스터에도 파드를 올립니다.

[bootstrap-token] 8줄은 join에 필요한 준비예요. 이 단계에서 init은 토큰을 만들어요. 그리고 그 토큰으로 인증한 노드가 인증서 발급 요청을 내고 자동으로 승인받을 수 있도록 RBAC 규칙을 만들고 kube-public 네임스페이스에 cluster-info ConfigMap도 만들어요. 이것들이 어떻게 쓰이는지는 5절에서 볼게요. 마지막으로 [addons]가 CoreDNS와 kube-proxy를 설치하면 init이 끝나요. 다만 공식 문서에 따르면 CoreDNS는 배포되더라도 CNI를 설치하기 전에는 스케줄되지 않아요. 출력 끝의 "You should now deploy a pod network" 안내가 바로 이 이야기이고 6편의 주제예요.

그림 2. API 서버가 응답하기 전에는 파일을 쓰고 응답한 뒤에는 API로 객체를 만든다

5. join은 두 번 확인한다: 워커가 마스터를, 마스터가 워커를

워커 하나가 192.168.104.1:6443에 접속한다고 해 볼게요. 워커 입장에서는 그 주소에서 응답하는 프로그램이 진짜 우리 API 서버인지 알 방법이 없어요. 서버 인증서를 확인하려면 CA 인증서가 있어야 하는데 워커는 아직 그 인증서를 받지 못했으니까요. 마스터 입장에서도 접속해 온 VM을 아무 확인 없이 노드로 받아 줄 수는 없어요. join 명령에 넣는 값들이 이 두 문제를 해결해요.

worker1$ sudo kubeadm join 192.168.104.1:6443 --token abcdef.0123456789abcdef --discovery-token-ca-cert-hash sha256:<CA 공개키 해시> --node-name k8s-worker1

→ API 서버 주소, 부트스트랩 토큰, CA 공개키 해시, 노드 이름을 넘긴다는 뜻이에요. 토큰과 해시는 실제 값 대신 자리표시자로 바꿔 적었어요.

📖 용어: 부트스트랩 토큰 (bootstrap token)
abcdef.0123456789abcdef 형식의 짧은 토큰이에요. 앞 6자리는 토큰 ID로 공개해도 되는 값이고 뒤 16자리가 비밀이에요. 아직 인증서가 없는 노드가 클러스터에 처음 접속할 때 쓰는 임시 신원이고 kubeadm init이 만드는 토큰은 24시간 동안 유효해요.

공식 문서는 join의 신뢰를 두 방향으로 나눠 설명해요. discovery 단계에서는 노드가 컨트롤 플레인을 믿고 TLS bootstrap 단계에서는 컨트롤 플레인이 노드를 믿어요.

discovery에서 워커는 먼저 kube-public의 cluster-info ConfigMap을 인증 없이 읽어요. init이 이 ConfigMap만큼은 인증받지 않은 사용자도 읽을 수 있게 열어 두었어요. 안에는 API 서버 주소와 CA 인증서, 그리고 토큰으로 만든 서명이 들어 있어요. 워커는 두 가지를 확인해요. 하나는 그 서명이 자기가 받은 토큰의 비밀 부분으로 검증되는지 여부예요. 다른 하나는 받아 온 CA 인증서의 공개키 해시가 --discovery-token-ca-cert-hash로 넘겨받은 값과 같은지 여부예요. 이 해시는 CA 인증서의 공개키 정보(SPKI)를 SHA-256으로 계산한 값이고 init 출력 끝의 join 명령에 함께 찍혀 나와요. 둘 다 맞으면 워커는 그 CA를 믿고 이번에는 그 CA로 검증한 연결에서 CA 인증서를 다시 받아 처음 받은 것과 같은지까지 비교해요.

해시까지 확인하는 데는 이유가 있어요. 공식 문서는 부트스트랩 토큰을 가진 쪽이면 누구나 그 토큰으로 유효한 서명을 만들 수 있다고 경고해요. 토큰만으로 확인하면 토큰을 얻은 다른 누군가가 API 서버 행세를 해도 워커는 구분하지 못해요. CA 공개키 해시는 init이 만든 바로 그 CA만 통과시켜요. 토큰은 여럿이 나눠 가진 비밀이라 마스터를 특정하지 못해요. 마스터를 특정하는 것은 CA 해시예요.

⚠️ 주의: 해시 검증을 끄는 플래그
해시를 미리 알 수 없을 때 쓰라고 --discovery-token-unsafe-skip-ca-verification이라는 플래그가 있어요. 공식 문서에 따르면 이 플래그는 kubeadm의 보안 모델을 약하게 만들어요. 다른 노드가 컨트롤 플레인 행세를 할 수 있게 되기 때문이에요. 해시는 init 출력에도, 마스터에서 kubeadm token create --print-join-command를 실행한 출력에도 나오므로 실습에서도 이 플래그 없이 조인했어요.

TLS bootstrap은 반대 방향이에요. 워커의 kubeadm은 토큰을 담은 임시 접속 파일 bootstrap-kubelet.conf를 쓰고 kubelet을 켜요. kubelet은 이 토큰으로 API 서버에 인증하는데 이때 신원은 system:bootstrap:<토큰 ID> 사용자이고 init이 권한을 준 그룹에 속해요. init 출력의 [bootstrap-token] 줄을 보면 이 그룹에는 노드 조회와 CSR 제출 권한이 주어져 있어요. kubelet은 이 권한으로 자기 인증서를 발급해 달라는 CSR을 내요.

📖 용어: CSR (CertificateSigningRequest)
"이 공개키로 인증서를 만들어 달라"는 요청이에요. 쿠버네티스에서는 API 객체로 만들어지고 승인되면 클러스터 CA가 서명한 인증서가 그 객체에 채워져요. kubelet은 키 쌍을 노드에서 직접 만들고 공개키만 담아 요청하므로 개인 키는 노드 밖으로 나가지 않아요.

kubelet이 낸 CSR은 controller-manager의 CSR 승인 컨트롤러가 자동으로 승인해요. init이 "부트스트랩 토큰으로 인증한 노드의 CSR은 자동 승인한다"는 RBAC 규칙을 미리 만들어 두었기 때문이에요(init 출력의 [bootstrap-token] 줄들). 승인되면 kubelet은 서명된 인증서를 받아 정식 접속 파일 kubelet.conf를 만들고 임시 파일 bootstrap-kubelet.conf는 지워져요. 워커의 join 출력 마지막 부분에 이 과정이 나와요.

[kubelet-start] Waiting for the kubelet to perform the TLS Bootstrap This node has joined the cluster: * Certificate signing request was sent to apiserver and a response was received. * The Kubelet was informed of the new secure connection details.

→ kubelet이 TLS Bootstrap을 마치기를 기다렸고 CSR을 보내 응답을 받았으며 kubelet이 새 인증서로 접속하게 됐다는 뜻이에요. discovery 단계는 출력에 따로 찍히지 않아요.

마스터에서 CSR 목록을 보면 이 과정의 흔적이 남아 있어요.

master$ kubectl get csr NAME AGE SIGNERNAME REQUESTOR REQUESTEDDURATION CONDITION csr-5trwk 6m7s kubernetes.io/kube-apiserver-client-kubelet system:bootstrap:ttnlk6 <none> Approved,Issued csr-lrnfd 6m21s kubernetes.io/kube-apiserver-client-kubelet system:node:k8s-master <none> Approved,Issued csr-q98fn 6m7s kubernetes.io/kube-apiserver-client-kubelet system:bootstrap:ixo4bs <none> Approved,Issued csr-zl6gp 6m7s kubernetes.io/kube-apiserver-client-kubelet system:bootstrap:ein9m8 <none> Approved,Issued

→ 워커 3대가 낸 요청은 요청자가 system:bootstrap:<토큰 ID>이고 kubelet 클라이언트 인증서용 서명자(kube-apiserver-client-kubelet)를 지정했으며 네 요청이 모두 승인되고 발급됐다(Approved,Issued)는 뜻이에요.

표를 보다가 두 가지가 눈에 띄었어요. 첫째, 워커 셋의 토큰 ID가 ttnlk6, ixo4bs, ein9m8로 모두 달라요(토큰 ID는 공개 정보라 그대로 옮겼어요). 워커들이 init이 만든 토큰 하나를 같이 쓴 게 아니라는 뜻이에요. ./lab의 조인 함수는 워커마다 마스터에서 kubeadm token create --print-join-command를 실행해 새 토큰이 든 join 명령을 받아 씁니다. 둘째, 마스터의 요청자는 system:node:k8s-master예요. 마스터의 kubelet은 init이 만든 kubelet.conf로 이미 노드 신원을 얻은 상태라서 부트스트랩 토큰이 아니라 그 신원으로 요청했어요. init은 system:nodes 그룹이 낸 인증서 갱신 요청도 자동으로 승인되도록 설정해 둡니다(출력의 "certificate rotation" 줄).

💡 실무에서는: join 명령은 필요할 때 새로 받는다
init 출력 끝의 join 명령에 든 토큰은 24시간 뒤에 만료돼요. 나중에 워커를 더 붙일 때는 마스터에서 kubeadm token create --print-join-command를 실행해 새 토큰과 CA 해시가 든 join 명령을 받으면 됩니다. ./lab은 조인할 때마다 이 명령으로 새 토큰을 받기 때문에 init의 토큰이 만료된 뒤에도 조인 단계가 그대로 동작해요.
그림 3. 앞 단계에서는 워커가 마스터를, 뒤 단계에서는 마스터가 워커를 확인한다

6. Mac에서는 IP로 접속하고 인증서는 이름으로 확인한다

마지막은 Mac에서 kubectl을 쓰는 이야기예요. admin.conf의 서버 주소는 advertiseAddress인 https://192.168.104.1:6443인데 이 eth0 대역은 VM끼리만 통해서 Mac에서는 닿지 않아요(3편). Mac에서 마스터에 닿는 주소는 lima1의 192.168.64.2예요. 그래서 ./lab up은 마지막 단계에서 admin.conf를 Mac 쪽 .lab/kubeconfig로 가져오면서 서버 주소를 바꿔요.

sed -E "s|^( *)server: https://.*\$|\1server: https://${HOST_IP}:6443\n\1tls-server-name: kubernetes|" /etc/kubernetes/admin.conf

→ admin.conf의 server 줄을 지금의 lima1 IP로 바꾸고 그 바로 아래에 tls-server-name: kubernetes 한 줄을 끼워 넣는다는 뜻이에요. 결과는 Mac 쪽 .lab/kubeconfig에 저장돼요.

서버 주소만 바꿔도 지금은 접속이 돼요. 192.168.64.2를 certSANs로 인증서에 넣어 두었으니까요. 이 IP가 바뀌면 문제가 생겨요. 인증서에는 init할 때의 IP만 들어 있어서 kubeconfig의 주소를 새 IP로 바꾸는 순간 검증에 실패해요.

tls-server-name으로 이 문제를 풀어요. kubeconfig 레퍼런스에 따르면 이 값은 서버 인증서를 확인할 때 쓰는 이름이고 비어 있으면 접속에 쓴 호스트 이름(여기서는 IP)으로 확인해요. 값을 kubernetes로 두면 kubectl은 192.168.64.2로 접속하되 인증서에 kubernetes라는 이름이 있는지를 확인해요. kubernetes는 kubeadm이 API 서버 인증서에 항상 넣는 기본 이름이라서 IP가 바뀌어도 이 확인은 통과해요. 그리고 ./lab up은 실행할 때마다 kubeconfig를 다시 만들어 서버 주소를 그때의 IP로 맞춥니다.

이 방법은 검증을 끄는 것과 달라요. CA로 서명을 확인하는 과정은 그대로 두고 인증서의 이름 목록에서 무엇을 찾을지만 바꾼 거예요. 접속 주소와 검증할 이름을 따로 적을 수 있어서 주소가 바뀌어도 검증을 끌 필요가 없었어요.

그림 4. 인증서 하나에 이름이 9개 들어 있고 Mac은 접속 주소와 검증할 이름을 따로 쓴다
✍️ 오늘의 요약
kubeadm init은 컨트롤 플레인을 직접 실행하지 않아요. 인증서와 kubeconfig, 정적 파드 매니페스트를 파일로 써 두고 kubelet을 켜면 kubelet이 매니페스트를 읽어 API 서버를 띄워요.

API 서버가 응답한 뒤에는 taint, 부트스트랩 토큰, cluster-info, CoreDNS와 kube-proxy를 API로 만들어요. join에서는 워커가 CA 공개키 해시로 마스터를 확인하고 마스터는 토큰으로 인증한 CSR을 승인해 워커를 받아들여요. 클러스터의 신뢰는 init이 맨 처음 만든 CA 한 쌍에서 시작합니다.
