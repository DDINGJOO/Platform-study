terminationGracePeriodSeconds가 모두 30인 파드 세 개를 같이 지웠어요. 첫째는 preStop으로 10초를 쉬는 sleep infinity 파드, 둘째는 preStop exec로 sleep 45를 실행하는 sleep infinity 파드, 셋째는 preStop 10초에 SIGTERM을 받으면 바로 끝나는 셸 파드였어요. 노드 로그에서 첫째 파드는 +10.0초에 SIGTERM을 받았고 SIGKILL은 +30.1초에 받았어요. 30초에 10초가 더해지지 않았어요. 둘째 파드는 +30.1초에야 SIGTERM을 받았고 SIGKILL은 그 2초 뒤인 +32.1초에 받았어요. 셋째 파드는 SIGTERM을 +10.1초에 받고 그 자리에서 끝났어요.

같은 날 정지 신호를 바꾸는 필드도 시험했어요. 1.37의 kubectl explain에는 lifecycle.stopSignal이 보여서 sleep infinity 파드에 stopSignal: SIGKILL을 넣었어요. 생성은 경고 없이 성공했는데 지우자 32.7초가 걸렸고 containerd는 여전히 SIGTERM을 보냈어요.

64~66편에서는 PID 1이 신호를 받을 수 있는지를 봤어요. 이번에는 신호를 보내는 쪽을 봐요. preStop과 terminationGracePeriodSeconds는 어디서부터 세고, 1.37의 stopSignal은 왜 안 먹을까요? 근거는 kubelet v1.37.2와 containerd v2.4.1 소스, 그리고 같은 버전의 우리 클러스터 실험이에요.

이 글에서 다룰 것
· 30초는 SIGTERM부터 셀까, preStop부터 셀까?
· preStop이 grace를 넘기면 어떻게 될까?
· 정지 신호는 누가 어떤 순서로 고를까?
· 1.37.2 클러스터에 stopSignal을 넣으면 왜 아무 일도 없을까?
· stopSignal은 언제 기본으로 켜질까?

1. grace 30초는 SIGTERM이 아니라 preStop 시작부터 센다

📖 용어: preStop 훅
컨테이너를 멈추기 직전에 kubelet이 실행하는 작업이에요. 컨테이너 안에서 명령을 실행하는 exec, HTTP 요청을 보내는 httpGet, 정해진 초만큼 기다리는 sleep 세 종류가 있어요. 엔드포인트에서 빠질 시간을 벌거나 앱에 정리 신호를 보내는 데 써요. preStop이 끝나거나 grace를 다 쓰면 그다음에 정지 신호가 가요(2절).

실험은 grace 30초인 파드 세 개를 같이 지우고 노드의 containerd·kubelet 로그를 삭제 요청 기준으로 정렬했어요. 원본은 labs/devops/k8s-study/out/67-prestop-grace.txt와 같은 디렉터리의 67-prestop-grace.sh예요. 노드 시계와 Mac 시계의 차이는 실행 때 재서 보정했어요.

그림 1. timeout 값이 20, 2로 줄어든 것이 preStop 시간을 grace에서 뺀 흔적이에요.

p10-sleep의 첫 줄이 StopContainer for "<cid>" with timeout 20 (s)였어요. kubelet이 containerd에 넘긴 timeout이 30이 아니라 20이었어요. preStop에 쓴 10초를 뺀 값이에요. 그래서 SIGTERM은 +10.0초, SIGKILL은 그 20초 뒤인 +30.1초였고 합계는 30초 그대로였어요. kubelet v1.37.2의 killContainer가 이 계산을 해요.

gracePeriod := setTerminationGracePeriod(ctx, pod, containerSpec, containerName, containerID, reason) ... // Run the pre-stop lifecycle hooks if applicable and if there is enough time to run it if containerSpec.Lifecycle != nil && containerSpec.Lifecycle.PreStop != nil && gracePeriod > 0 { gracePeriod = gracePeriod - m.executePreStopHook(ctx, pod, containerID, containerSpec, gracePeriod) } // if we care about termination ordering, then wait for this container's turn to exit if there is // time remaining if ordering != nil && gracePeriod > 0 { // grace period is only in seconds, so the time we've waited gets truncated downward gracePeriod -= int64(ordering.waitForTurn(containerName, gracePeriod)) } // always give containers a minimal shutdown window to avoid unnecessary SIGKILLs if gracePeriod < minimumGracePeriodInSeconds { gracePeriod = minimumGracePeriodInSeconds } ... err := m.runtimeService.StopContainer(ctx, containerID.ID, gracePeriod)

→ grace를 정한 뒤 preStop을 실행하고, preStop이 실제로 걸린 초를 grace에서 빼고, 남은 값을 StopContainer의 timeout으로 넘긴다는 뜻이에요. executePreStopHook()은 걸린 시간을 초 단위 정수로 돌려줘요. 사이드카의 종료 순서를 기다리는 시간도 같은 방식으로 빠져요(사이드카 순서는 70편). 남은 값이 2초보다 작으면 2초로 올려요.

처음 grace를 정하는 setTerminationGracePeriod()는 파드 객체의 deletionGracePeriodSeconds가 있으면 그 값을 먼저 써요. 없으면 spec의 terminationGracePeriodSeconds를 쓰는데, liveness나 startup 프로브 실패로 죽이는 경우에는 프로브에 적은 terminationGracePeriodSeconds가 있으면 그 값을 써요.

📖 용어: deletionTimestamp와 deletionGracePeriodSeconds
파드 삭제를 요청하면 API 서버가 객체에 적는 두 필드예요. deletionGracePeriodSeconds는 이번 삭제에 쓸 grace이고 deletionTimestamp는 이 시각까지 기다리겠다는 예정 시각이에요. kubectl이 Terminating으로 보여 주는 것이 이 필드가 있는 파드예요(63편).

실험의 세 파드는 모두 deletionGracePeriodSeconds가 30이었고 deletionTimestamp가 요청 시각 +29초로 찍혔어요. 초 단위로 잘린 값이에요. 이 시각은 kubelet이 SIGKILL을 보내는 시각을 정하지 않아요. kubelet은 이 grace 값에서 preStop 시간을 빼서 timeout을 만들 뿐이에요.

p10-trap은 이 계산의 다른 면을 보여 줘요. PID 1이 trap "exit 0" TERM; sleep infinity & wait인 셸이라 SIGTERM에 바로 끝나는 파드인데도 +10.1초에 끝났어요. 신호를 잘 처리하는 앱도 preStop만큼은 늦게 끝나요. preStop은 정지를 늦추는 장치이고 그 시간은 grace 안에서 써요.

그림 2. preStop이 짧으면 SIGKILL 시각은 그대로이고, preStop이 grace를 넘으면 SIGTERM 뒤에 2초만 남아요.

2. preStop이 grace를 다 쓰면 SIGTERM 뒤에 2초만 남는다

p45-exec는 preStop이 grace보다 긴 경우예요. executePreStopHook()은 훅을 고루틴에서 돌리고 grace만큼만 기다려요. 시간이 지나면 V(2) 수준의 "PreStop hook not completed in grace period" 로그를 남기고 걸린 시간을 돌려줘요. 30초를 다 썼으니 남은 grace는 0이고, 앞에서 본 최소값 규칙으로 2초가 돼요. 상수는 kuberuntime_manager.go에 있어요.

// A minimal shutdown window for avoiding unnecessary SIGKILLs minimumGracePeriodInSeconds = 2

→ 불필요한 SIGKILL을 피하려고 최소한의 정지 시간 2초를 둔다는 뜻이에요. 로그도 이 계산과 맞았어요. p45-exec는 +30.1초에 with timeout 2 (s)로 SIGTERM을 받았고 +32.1초에 SIGKILL을 받았어요. 같은 시각 kubelet은 이 줄을 남겼어요.

E1115 21:21:07.736829 1574 kuberuntime_container.go:794] "PreStop hook failed" err="command 'sleep 45' exited with 137: " pod="why-pid1/p45-exec"

→ preStop으로 실행한 sleep 45가 종료 코드 137로 끝났다는 뜻이에요. 줄 번호 794는 v1.37.2 소스의 executePreStopHook 안 logger.Error(err, "PreStop hook failed", ...) 줄과 같아요. kubelet은 30초에서 훅을 기다리는 것만 멈추고 훅은 계속 돌게 둬요. 컨테이너가 SIGKILL로 끝나면서 그 안의 sleep 45도 137로 끝났다고 읽을 수 있어요.

공식 문서의 Pod Termination Flow도 같은 동작을 적어요. "If the preStop hook is still running after the grace period expires, the kubelet requests a small, one-off grace period extension of 2 seconds." grace가 끝났는데 preStop이 아직 돌고 있으면 kubelet이 2초짜리 일회성 연장을 요청한다는 뜻이에요. 바로 아래 note는 preStop이 기본 grace보다 오래 걸리면 terminationGracePeriodSeconds를 거기에 맞게 바꿔야 한다고 적어요.

sleep 액션은 막고 exec는 막지 않는다

같은 실험의 첫 줄은 preStop을 sleep 액션 45초로 준 파드를 server-side dry-run으로 보낸 결과였어요.

The Pod "p45-sleep" is invalid: spec.containers[0].lifecycle.preStop.sleep: Invalid value: 45: must be non-negative and less than terminationGracePeriodSeconds (30)

→ preStop sleep 액션의 초는 0 이상이고 terminationGracePeriodSeconds보다 작아야 한다는 검증 오류예요. 그런데 exec로 sleep 45를 실행하는 p45-exec는 그대로 만들어졌어요. API 서버는 exec 명령이 몇 초 걸릴지 알 수 없으니 검사할 방법이 없어요. 검증 코드(validation.go의 validateSleepAction)의 실제 조건은 sleep.Seconds > *gracePeriod예요. 그래서 30초짜리 sleep은 통과하는데 메시지는 "less than"이라고 적어요.

⚠️ preStop을 넣으면 grace도 같이 늘려야 해요
grace는 preStop과 앱 정리를 합친 예산이에요. preStop 15초에 앱 정리가 20초 걸리면 기본 30초로는 앱이 SIGTERM 뒤 15초밖에 못 받아요. terminationGracePeriodSeconds를 preStop + 앱 정리 시간보다 크게 잡아요. exec preStop은 API 서버가 길이를 검사하지 않으니 grace를 넘겨도 아무 오류가 없고, 실제로는 앱에게 2초만 남아요.

3. 정지 신호는 containerd가 스펙, 이미지 STOPSIGNAL, SIGTERM 순으로 고른다

kubelet이 StopContainer에 넘기는 것은 timeout뿐이에요. CRI의 StopContainerRequest에는 컨테이너 ID와 timeout 두 필드만 있어요. 신호를 지정하는 자리는 컨테이너를 만들 때 쓰는 ContainerConfig에 있어요.

📖 용어: CRI ContainerConfig.stop_signal
kubelet이 컨테이너를 만들 때 런타임에 넘기는 설정 묶음이 ContainerConfig예요. v1.37.2의 cri-api api.proto에는 18번 필드로 Signal stop_signal이 있어요. 정지 신호는 멈출 때가 아니라 만들 때 정해진다는 뜻이에요. 값이 0(SIGNAL_RUNTIME_DEFAULT)이면 런타임의 기본 동작을 따라요.

containerd v2.4.1의 stopContainer()가 이 값을 읽어요.

if timeout > 0 { stopSignal := "SIGTERM" if signal := container.Config.GetStopSignal(); signal != runtime.Signal_SIGNAL_RUNTIME_DEFAULT { stopSignal, err = criSignalToOCIStopSignal(signal) ... } else if container.StopSignal != "" { stopSignal = container.StopSignal } else { ... if image.ImageSpec.Config.StopSignal != "" { stopSignal = image.ImageSpec.Config.StopSignal } } ... log.G(ctx).Infof("Stop container %q with signal %v", id, sig) if err = task.Kill(ctx, sig); err != nil && !errdefs.IsNotFound(err) { ...

→ 기본값은 SIGTERM이고, CRI 스펙의 stop_signal이 있으면 그 값을 먼저, 없으면 컨테이너를 만들 때 기록한 이미지의 STOPSIGNAL을 쓴다는 뜻이에요. 마지막 else는 그 기록이 없는 옛 컨테이너를 위해 이미지 설정을 다시 읽는 경로예요. 65편에서 nginx 파드가 SIGQUIT(quit)을 받은 것이 둘째 순서였어요. 이 stop_signal을 반영하는 코드는 containerd PR #11774(2026-04-28 머지)로 들어왔고 2.3.0부터 포함됐어요.

공식 문서도 "Many container runtimes respect the STOPSIGNAL value defined in the container image"라고 적고, 이미지에 STOPSIGNAL이 없으면 런타임의 기본값을 쓰며 그 값이 containerd와 CRI-O 모두 SIGTERM이라고 적어요.

그림 3. 신호는 생성 때의 설정과 이미지에서 오고, 지금 우리 클러스터에서는 첫 번째 길이 끊겨 있어요.

파드 스펙으로 신호를 바꾸자는 요청은 2016년에 나왔다

이미지의 STOPSIGNAL만으로 충분한지는 오래된 질문이에요. 2016-08-04 thockin이 연 이슈 #30051은 "Docker added STOPSIGNAL to let container images change which signal is delivered to kill the container. Should we support that?"로 시작해요. yujuhong이 kubelet은 docker stop을 쓰니 이미지의 STOPSIGNAL이 그대로 쓰인다고 답하자 thockin은 "ACK, then I think we can close this."라고 했어요. 이슈는 닫히지 않았고, thockin은 2020-03-18에 요청을 다시 정리했어요.

Dockerfile supports STOPSIGNAL and we support that transparently. However, not everyone builds their own images, and telling folks they have to build a custome image just to set this is pretty hostile. Docker supports --stop-signal as a flag to docker run. Kubernetes has no equivalent as part of Pod or Container APIs. I posit that we should have something.

→ 이미지의 STOPSIGNAL은 이미 지원하지만 모두가 이미지를 직접 만들지는 않으니 신호 하나 바꾸려고 이미지를 새로 만들라는 것은 가혹하고, Docker의 --stop-signal 같은 것이 Pod API에도 있어야 한다는 뜻이에요.

이 요청이 KEP-4960 Container Stop Signals가 됐어요. Summary는 "Kubernetes has no equivalent for STOPSIGNAL as part of Pod or Container APIs."라고 적어요. User Story 1은 nginx가 SIGTERM에 요청을 떨어뜨리는 문제와 지금의 우회책을 들어요. 우회책은 preStop에서 직접 신호를 보내는 거예요.

lifecycle: preStop: exec: command: ["/bin/sh", "-c", "kill -SIGUSR1 $(pidof my-app)"]

→ 컨테이너 안의 셸로 앱의 PID를 찾아 원하는 신호를 보내는 preStop이에요. 1절에서 본 대로 preStop은 grace 안에서 실행되고, 이미지에 sh와 pidof가 있어야 해요.

📖 용어: KEP
Kubernetes Enhancement Proposal의 줄임말이에요. 쿠버네티스에 기능을 넣거나 바꿀 때 동기, 설계, 단계별 졸업 조건, 버전 호환을 적는 문서이고 kubernetes/enhancements 저장소에 있어요. 각 KEP에는 진행을 추적하는 이슈와 kep.yaml의 단계(alpha, beta, stable)와 목표 버전이 있어요.

4. 1.37.2에서 stopSignal은 경고 없이 저장 단계에서 사라진다

📖 용어: 기능 게이트(feature gate)와 알파
아직 완성되지 않은 기능을 켜고 끄는 스위치예요. 구성 요소마다 --feature-gates로 바꿀 수 있고, 각 게이트에는 버전별 단계와 기본값이 있어요. 알파 게이트는 기본으로 꺼져 있어요. 꺼진 게이트의 API 필드는 스키마에는 보여도 동작하지 않을 수 있어요.

stopSignal 실험은 게이트 상태부터 봤어요. 원본은 labs/devops/k8s-study/out/67-stopsignal-gate.txt와 같은 디렉터리의 67-stopsignal-gate.sh예요. 게이트는 바꾸지 않고 각 구성 요소의 /metrics에서 읽기만 했어요.

그림 4. 매니페스트에 SIGKILL을 적었는데 저장된 객체에는 아무것도 남지 않았어요.

결과를 순서대로 보면 이래요.

· kubernetes_feature_enabled{name="ContainerStopSignals",stage="ALPHA"} 0이 kube-apiserver와 kubelet 4대 모두에서 나왔어요. 게이트가 꺼져 있어요.
· kubectl explain pod.spec.containers.lifecycle.stopSignal에는 필드 설명과 열거값 65개가 나왔고 alpha라는 말은 없었어요.
· stopSignal: SIGKILL과 os: {name: linux}를 넣은 파드는 pod/s-kill created로 만들어졌는데 저장된 .spec.containers[0].lifecycle은 빈 값이었어요. .spec.os는 남아 있었어요.
· 리눅스에 없는 이름 SIGFOO를 넣고 spec.os도 뺀 매니페스트가 server-side dry-run을 통과했어요.
· status.containerStatuses[0].stopSignal도 빈 값이었어요.
· s-kill을 지우자 32.7초 뒤에 사라졌어요. containerd는 삭제 요청 기준 +1.4초에 Stop container "<cid>" with signal terminated를, +31.5초에 Kill container를 남겼어요.

이번 실행에서는 kubelet의 StopContainer 호출이 삭제 요청 +1.4초에 왔고, 같은 날 앞선 실행에서는 +0.0초였어요. 그 차이의 이유는 보지 않았어요. 이번 실행에서 SIGKILL은 StopContainer 뒤 30.1초에 갔어요.

검증보다 먼저 필드를 지운다

SIGFOO가 통과한 이유는 API 서버가 저장을 준비하는 순서에 있어요. v1.37.2의 kube_features.go에서 이 게이트의 항목은 하나뿐이에요.

ContainerStopSignals: { {Version: version.MustParse("1.33"), Default: false, PreRelease: featuregate.Alpha}, },

→ 1.33에 알파로 들어왔고 기본값은 꺼짐이며, 1.37.2까지 다음 단계가 추가되지 않았다는 뜻이에요. 게이트가 꺼져 있으면 pkg/api/pod/util.go의 dropContainerStopSignals()가 기존 객체에서 이미 쓰던 경우가 아닌 한 모든 컨테이너의 Lifecycle.StopSignal을 nil로 만들고, 그 결과 lifecycle이 비면 lifecycle까지 nil로 만들어요.

func dropContainerStopSignals(podSpec, oldPodSpec *api.PodSpec) { if utilfeature.DefaultFeatureGate.Enabled(features.ContainerStopSignals) || containerStopSignalsInUse(oldPodSpec) { return } ... if ctr.Lifecycle.StopSignal != nil { ctr.Lifecycle.StopSignal = nil if *ctr.Lifecycle == (api.Lifecycle{}) { ctr.Lifecycle = nil } }

이 함수는 파드 생성의 PrepareForCreate()에서 DropDisabledPodFields()를 거쳐 불려요. 그리고 apiserver의 BeforeCreate()는 PrepareForCreate를 먼저(create.go 128줄), Validate를 나중에(146줄) 불러요. stopSignal에 spec.os.name을 요구하고 리눅스 신호 목록에 있는지 보는 validateStopSignal()은 Validate 안에 있으니, 필드가 이미 지워진 뒤라 검사할 것이 없어요. 경고도 돌아오지 않아요. kubelet 쪽의 getContainerConfigStopSignal()도 게이트가 꺼져 있으면 nil을 돌려줘서 ContainerConfig에 stop_signal을 넣지 않아요.

📖 용어: PrepareForCreate와 Validate
API 서버가 객체를 저장하기 전에 거치는 두 단계예요. PrepareForCreate는 status를 초기화하고 꺼진 게이트의 필드를 지우는 등 객체를 손보는 단계이고, Validate는 손본 객체가 규칙에 맞는지 검사하는 단계예요. 순서가 이렇기 때문에 지워진 필드는 검증 오류도 내지 않아요.

KEP-4960의 Version Skew Strategy도 같은 조용함을 적어요. API 서버만 게이트를 켜면 검증은 통과하지만 kubelet이 "silently dropped" 한다고 해요. 그러니 이 필드는 API 서버와 kubelet 양쪽이 모두 켜져야 동작해요.

게이트를 켜면 어떻게 될지는 이 글에서 시험하지 않았어요. 클러스터의 기능 게이트는 바꾸지 않았어요. containerd 2.4.1에 stop_signal을 읽는 코드가 있으니 켜면 동작할 것으로 보지만, 1.37에서 바뀐 CRI 열거값 이름(#139251, #138826)과의 호환은 확인하지 않았어요. 그리고 켜더라도 64편의 규칙은 그대로예요. 핸들러가 없는 PID 1에게 SIGKILL·SIGSTOP이 아닌 신호를 지정하면 커널이 버려요. KEP의 Risks도 컨테이너가 처리하지 않는 신호를 지정하면 grace 동안 멈춰 있다가 SIGKILL로 끝난다고 적어요.

💡 stopSignal을 쓰기 전에 확인할 것
• 게이트 상태: kubectl get --raw /metrics | grep 'kubernetes_feature_enabled{name="ContainerStopSignals"'로 API 서버를, kubectl get --raw /api/v1/nodes/<노드>/proxy/metrics로 kubelet을 봐요.
• 저장된 결과: apply 뒤 kubectl get pod <이름> -o jsonpath='{.spec.containers[0].lifecycle}'에 stopSignal이 남았는지 봐요. 성공 메시지와 dry-run 통과는 근거가 되지 않아요. SIGFOO도 통과했어요.
• 그전까지의 방법: 이미지를 고칠 수 있으면 Dockerfile의 STOPSIGNAL, 없으면 preStop에서 신호를 보내는 우회책이에요. 우회책은 grace를 쓰니 1절의 계산에 넣어요.

✍️ 오늘의 요약

terminationGracePeriodSeconds는 preStop 시작부터 SIGKILL까지의 예산이에요. kubelet v1.37.2의 killContainer는 preStop이 걸린 초를 grace에서 빼서 StopContainer의 timeout으로 넘기고 최소 2초를 남겨요. 실험에서 preStop 10초 파드는 +10초 SIGTERM, +30초 SIGKILL이었고 preStop 45초 파드는 +30초 SIGTERM, +32초 SIGKILL이었어요.

정지 신호는 containerd가 CRI 스펙의 stop_signal, 이미지 STOPSIGNAL, SIGTERM 순으로 골라요. 스펙에서 신호를 바꾸는 lifecycle.stopSignal(KEP-4960)은 1.37.2에서 1.33 알파 그대로 기본 꺼짐이라, API 서버가 검증 전에 필드를 지우고 SIGFOO도 경고 없이 통과했어요. 1.38 베타·기본 켜짐은 2026-11-06 master에 머지됐어요.

preStop을 쓰면 grace를 preStop과 앱 정리를 합친 시간보다 크게 잡고, 새 필드를 쓰기 전에는 게이트 지표와 저장된 객체로 실제로 남았는지 확인해야 해요.
