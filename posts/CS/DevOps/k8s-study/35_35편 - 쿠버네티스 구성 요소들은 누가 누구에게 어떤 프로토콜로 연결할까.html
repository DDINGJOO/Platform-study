37편. 마스터 노드에도 일반 파드를 올릴 수 있을까, taint와 toleration

쿠버네티스 주요 구성 요소를 하나씩 정리하던 저녁에 제가 본 설명 하나에는 "kubectl은 API 서버와 HTTP REST로 통신하고 스케줄러와 컨트롤러 매니저는 gRPC로 통신한다"고 적혀 있었어요. 그 문장을 보고 제가 처음 던진 질문은 "왜 얘네들은 gRPC를 골랐는지 조사 가능해?"였어요. 그런데 이유를 찾기 전에 정말 gRPC인지부터 확인해야 했어요. 스케줄러와 컨트롤러 매니저의 kubeconfig에 적힌 서버 주소는 kubectl과 같은 https://192.168.104.1:6443이었고 실제로 맺힌 연결도 같은 6443 포트를 향했거든요.

차이는 요청 본문에 있었어요. 마스터에서 같은 REST 경로 /api/v1/namespaces/default/services/kubernetes로 GET을 두 번 보내면서 Accept 헤더만 바꿔 봤어요. JSON을 달라고 한 응답은 {로 시작했고 protobuf를 달라고 한 응답은 k 8 s \0이라는 4바이트로 시작했어요. 스케줄러와 컨트롤러 매니저가 기본으로 쓰는 형식은 이 두 번째 형식이에요. 포트도 경로도 같고 본문 형식만 달랐던 거예요. gRPC는 다른 곳에 있었어요.

이런 차이는 아키텍처 그림만 봐서는 드러나지 않아요. 19편에서는 그림의 화살표를 실제 TCP 연결로 세어 "모든 화살표가 API 서버로 모인다"는 것을 확인했어요. 이번 편에서는 그 화살표마다 네 가지를 더 붙여요. 누가 연결을 여는지, 받는 쪽은 어느 주소와 포트에서 기다리는지, 어떤 프로토콜과 형식으로 말하는지, 어떤 신원으로 들어가서 무엇까지 할 수 있는지예요. 방화벽 규칙을 쓸 때도, 구성 요소 하나가 API 서버에 붙지 못할 때도, 인증서가 만료됐을 때도 결국 이 네 가지를 묻게 돼요.

이번 편은 36편부터 50편까지를 묶는 허브이기도 해요. 36~42편은 구성 요소를 하나씩 깊게 보고 43~50편은 "쿠버네티스는 왜 이렇게 만들었나"를 KEP와 이슈 같은 1차 출처로 따라가요. 그래서 이번 편의 표에는 화살표마다 자세히 다루는 편 번호를 붙이고 마지막 장에 두 묶음의 지도를 그려 둘게요. 클러스터는 Lima VM 4대(k8s-master, k8s-worker1~3)에 kubeadm v1.37.2, containerd 2.4.1, Calico v3.33.0을 올린 실습 환경이에요. 이번 편을 위해 새로 모은 출력은 모두 22시 무렵 조회만 해서 얻었어요.

이 글에서 다룰 것
· 컨트롤 플레인 구성 요소는 어디에 무엇으로 떠 있고 kubectl get nodes의 ROLES 칸은 어디서 올까?
· 누가 누구에게 연결을 열까? 어떤 포트는 노드 밖에서 닿고 어떤 포트는 127.0.0.1에만 열려 있을까?
· 연결마다 쓰는 프로토콜과 형식은 무엇일까? gRPC는 정확히 어디에 있을까?
· 구성 요소는 API 서버에 어떤 신원으로 들어가고 그 신원에는 어떤 권한이 붙을까?
· "etcd는 API 서버하고만 통신한다", "모듈형 구조라서 안정적이다"를 정확히 말하면 무엇일까?
· 36~50편은 각각 어떤 질문에 답할까?

1. 컨트롤 플레인 넷은 마스터의 정적 파드이고 ROLES 칸은 라벨에서 나온다

먼저 상자부터 확인했어요. 컨트롤 플레인 파드에 붙는 라벨 tier=control-plane으로 파드를 골라 노드, 이미지, 소유자(OWNER)를 함께 뽑았어요.

그림 1. 컨트롤 플레인 넷은 모두 k8s-master에 있고 소유자가 Node다. 마스터의 manifests 폴더에 같은 이름의 파일 넷이 있다

네 파드 모두 k8s-master에 있고 OWNER가 Node예요. 소유자가 Node라는 것은 그 노드의 kubelet이 /etc/kubernetes/manifests 폴더의 파일을 읽어 직접 띄운 정적 파드라는 뜻이에요(5편, 19편). ReplicaSet이나 DaemonSet 같은 컨트롤러가 만든 파드였다면 OWNER에 그 종류가 찍혔을 거예요. API 서버 목록에 보이는 것은 kubelet이 따로 만들어 둔 미러 파드예요. 클라우드 컨트롤러 매니저는 0개였어요. 클라우드 API와 이어 줄 프로그램이 없는 온프레미스 클러스터라서 그래요(24편, 42편).

워커에는 이 넷이 하나도 없었어요. 워커 kubelet 설정의 staticPodPath도 마스터와 같은 /etc/kubernetes/manifests였지만 그 폴더가 비어 있었고 kube-apiserver 프로세스는 마스터에만 1개 있었어요. 워커를 포함해 네 노드의 kubelet은 모두 https://192.168.104.1:6443, 곧 마스터의 API 서버에 붙어 있었어요. API 서버를 왜 파드로 띄우는지와 매니페스트의 플래그가 각각 무엇을 정하는지는 36편에서 다뤄요.

그다음 kubectl get nodes를 쳤을 때 제가 남긴 말은 "롤이 있네"였어요.

# 35-node-roles.txt 발췌 (19:35:03 KST) $ kubectl get nodes NAME STATUS ROLES AGE VERSION k8s-master Ready control-plane 9d v1.37.2 k8s-worker1 Ready worker 9d v1.37.2 k8s-worker2 Ready worker 9d v1.37.2 k8s-worker3 Ready worker 9d v1.37.2 $ kubectl get nodes -L node-role.kubernetes.io/control-plane,node-role.kubernetes.io/worker (라벨 키만 골라 봄) k8s-master role 라벨=['node-role.kubernetes.io/control-plane'] taints=['node-role.kubernetes.io/control-plane:NoSchedule'] k8s-worker1 role 라벨=['node-role.kubernetes.io/worker'] taints=없음 (worker2·3 도 worker1 과 같음)

→ 마스터에는 control-plane 라벨과 NoSchedule taint가 붙어 있고 워커 셋에는 worker 라벨만 있고 taint가 없다는 뜻이에요.

Node 객체에 "역할"이라는 필드가 따로 있는 것은 아니에요. ROLES 칸은 노드 라벨 중 node-role.kubernetes.io/로 시작하는 키에서 그 뒤의 글자를 꺼내 채운 값이에요. 이 칸을 채우는 쪽은 kubectl이 아니라 API 서버예요. kubectl get은 API 서버에 표 모양 응답(Table)을 달라고 요청해요. API 개념 문서는 이 방식을 "delegating specific details of printing to the server", 곧 출력의 세부를 서버에 맡기는 방식이라고 설명해요. API 서버가 Node 표를 만드는 v1.37.2 소스(printers.go의 findNodeRoles)를 보면 node-role.kubernetes.io/ 뒤의 글자와 kubernetes.io/role 라벨의 값을 역할로 모으고 하나도 없으면 <none>을 넣어요.

라벨을 붙인 쪽은 노드마다 달라요. 마스터의 control-plane 라벨과 control-plane:NoSchedule taint는 kubeadm init이 붙였어요. kubeadm 구현 문서의 "Mark the node as control-plane" 절에 이 두 가지가 그대로 적혀 있어요. 워커의 worker 라벨은 우리 실습 스크립트 ./lab이 노드가 모두 뜬 뒤 kubectl label node … node-role.kubernetes.io/worker=로 붙였어요. kubeadm 구현 문서에서 역할 라벨을 붙이는 단계는 컨트롤 플레인 노드의 것뿐이에요. 이 줄이 없었다면 워커의 ROLES는 <none>이었을 거예요. 잘 알려진 라벨 문서에도 "Kubernetes defines one specific node role, control-plane"이라고 적혀 있어요. 쿠버네티스가 정한 노드 역할은 control-plane 하나이고 worker는 우리가 붙인 표시예요.

그래서 ROLES 칸은 라벨을 보여 줄 뿐이고 일반 파드가 마스터를 비켜 가게 만드는 것은 라벨이 아니라 taint예요. 23편에서 Pending 파드의 이벤트에 찍힌 "1 node(s) had untolerated taint(s)"가 바로 마스터의 control-plane:NoSchedule이었어요. 이 taint를 견디는 파드를 마스터에 올려 보는 실험은 37편에서 다뤄요.

그림 2. 네 노드의 kubelet은 같은 폴더를 보지만 파일은 마스터에만 있다. ROLES 칸은 라벨에서, 마스터를 비켜 가는 동작은 taint에서 나온다

2. 연결은 거의 모두 6443으로 열리고 API 서버가 먼저 여는 곳은 etcd와 kubelet이다

방화벽 규칙을 쓰거나 "연결이 거부됐다"는 오류를 볼 때 먼저 알아야 할 것은 어느 쪽이 연결을 여는지예요. 연결을 받는 쪽만 포트를 열어 두고 기다리기 때문에 화살표의 방향을 거꾸로 알면 엉뚱한 노드의 방화벽을 열게 돼요. 19편에서는 이미 맺힌(established) 연결을 셌으니 이번에는 반대쪽을 봤어요. 각 프로그램이 어느 주소와 포트에서 연결을 기다리는지를 노드마다 뽑았어요.

📖 용어: 바인드 주소와 LISTEN
서버 프로그램은 "이 주소의 이 포트로 오는 연결을 받겠다"고 운영체제에 등록한 뒤 연결을 기다려요. 이 상태를 LISTEN이라고 하고 등록한 주소를 바인드 주소라고 해요. 127.0.0.1이면 같은 노드 안에서 온 연결만 받고 0.0.0.0이나 *이면 노드의 모든 네트워크 인터페이스로 온 연결을 받아요. 192.168.104.1 같은 특정 IP를 적으면 그 주소로 온 연결만 받아요.
그림 3. 노드 밖에서 닿는 주소로 받는 것은 6443, 2379·2380, 10250, 10256, 179뿐이고 나머지는 127.0.0.1에서만 받는다

worker2와 worker3의 목록도 worker1과 같았고 containerd의 포트 번호만 달랐어요. 받는 주소로 나누면 두 묶음이에요.

· 노드 밖에서 닿는 주소: kube-apiserver의 *:6443, etcd의 192.168.104.1:2379와 2380, kubelet의 *:10250, kube-proxy의 *:10256, BIRD의 0.0.0.0:179예요. 공식 포트 표는 6443을 쓰는 쪽을 "All", 2379-2380을 "kube-apiserver, etcd", 10250을 "Self, Control plane", 10256을 "Self, Load balancers"로 적어요. 10256은 kube-proxy의 상태 확인 포트이고 179는 Calico의 BIRD가 노드끼리 BGP 세션을 맺는 포트예요(30편).
· 127.0.0.1에서만 받는 주소: kube-scheduler 10259, kube-controller-manager 10257, etcd 2379와 2381, kube-proxy 10249, kubelet 10248, calico 9099, containerd의 임의 포트예요. 같은 노드 안의 프로그램만 붙을 수 있어요.

눈여겨볼 곳은 스케줄러와 컨트롤러 매니저예요. kube-scheduler와 kube-controller-manager 레퍼런스에 적힌 --bind-address의 기본값은 0.0.0.0이에요. 그런데 kubeadm이 만든 두 매니페스트에는 --bind-address=127.0.0.1이 들어 있어서 노드 밖에서는 이 포트에 닿지 않아요. 10259와 10257은 --secure-port의 기본값이고 레퍼런스는 이 포트를 인증과 인가를 거쳐 HTTPS를 내주는 포트로 설명해요. 5편에서 본 kubeadm init의 상태 확인이 바로 이 포트의 /healthz와 /livez를 불렀어요. 포트 표에도 두 포트를 쓰는 쪽은 "Self"로만 적혀 있어요. 다른 구성 요소가 일을 시키려고 스케줄러나 컨트롤러 매니저에 연결하지 않으니 노드 밖에 열어 둘 이유가 없어요. 노드와 컨트롤 플레인 통신 문서의 "None of the other control plane components are designed to expose remote services"라는 문장이 이 LISTEN 목록에서 그대로 보여요. 둘은 할 일을 API 서버에서 받아 오고 결과도 API 서버에 적어요.

나머지 127.0.0.1 포트도 설정에서 정체를 확인했어요. etcd의 2381은 매니페스트의 --listen-metrics-urls=http://127.0.0.1:2381로 연 메트릭 포트예요. kube-proxy ConfigMap에는 metricsBindAddress와 healthzBindAddress가 빈 값이라서 kube-proxy 설정 레퍼런스의 기본값 127.0.0.1:10249(메트릭)와 0.0.0.0:10256(상태 확인)이 쓰였어요. kubelet의 10248은 노드 안에서만 받는 상태 확인 포트예요(26편). calico의 9099는 Felix의 상태 확인 포트예요. Calico v3.33.0 매니페스트는 calico-node에 FELIX_HEALTHENABLED=true를 넣고 FelixConfiguration 설명에 HealthPort의 기본값을 9099로 적어요.

containerd가 127.0.0.1의 임의 포트(마스터 43891, worker1 33287 …)로 받는 연결은 CRI 스트리밍 서버예요. worker1의 containerd 설정은 stream_server_address = '127.0.0.1', stream_server_port = '0'이었고 containerd 2.4.1의 CRI 설정 문서에도 같은 기본값이 적혀 있어요. 포트에 0을 주면 운영체제가 비어 있는 포트를 골라 줘요. CRI 정의(api.proto)에는 Exec, Attach, PortForward가 각각 "prepares a streaming endpoint", 곧 스트리밍 엔드포인트를 준비하는 호출로 적혀 있어요. 이 엔드포인트가 127.0.0.1에 있으니 노드 밖에서는 닿지 않아요. 그래서 kubectl exec의 스트림은 API 서버에서 kubelet의 10250을 거쳐 containerd의 이 스트리밍 포트로 이어지는 것으로 보여요. 이 길을 패킷으로 따라가 보지는 않았어요.

그럼 6443에는 누가 연결을 열까요? 20시 8분에 노드마다 API 서버로 가는 연결을 프로세스와 파드 단위로 세어 봤어요(35-apiserver-clients.txt). 노드마다 kubelet 1개, kube-proxy 1개, calico-node 3개가 있었고 마스터에는 스케줄러 2개, 컨트롤러 매니저 2개, kubectl 1개가 더 있었어요. 파드 안에서 붙은 것은 CoreDNS 파드 두 개가 1개씩, calico-kube-controllers 1개, kube-state-metrics 1개, Prometheus 4개, local-path-provisioner 1개였어요. 파드 안의 프로그램은 kubernetes Service의 주소 10.96.0.1:443으로 붙고 kube-proxy 규칙을 거쳐 192.168.104.1:6443에 닿아요(19편). 클러스터를 지켜보는 모니터링 도구(kube-state-metrics, Prometheus)와 애드온(CoreDNS, local-path-provisioner)도 결국 같은 6443의 클라이언트였어요. Mac의 kubectl은 192.168.64.2:6443으로 마스터에 붙어요(5편).

반대로 API 서버가 먼저 여는 연결은 몇 군데 없었어요. 마스터의 kube-apiserver 프로세스가 맺은 연결 중 자기 6443이 아닌 쪽에서 나간 것만 골라 상대 포트별로 셌어요.

그림 4. API 서버가 먼저 연 연결은 etcd(2379) 93개와 kubelet(10250) 4개였고 웹훅과 외부 APIService는 0개였다

etcd로 93개, kubelet으로 4개, 자기 자신의 6443으로 1개였어요. API 서버의 --etcd-servers는 https://127.0.0.1:2379라서 같은 노드의 etcd에 루프백 주소로 붙어요. 자기 6443으로 연 1개는 무엇에 쓰는 연결인지 이번에는 확인하지 않았어요. kubelet 쪽 연결은 19편에서 본 대로 파드 로그 가져오기, attach, port-forward에 쓰여요. 통신 문서는 컨트롤 플레인에서 노드로 가는 길을 두 가지로 적어요. 하나가 이 kubelet 연결이고 다른 하나는 API 서버의 proxy 기능으로 노드, 파드, Service에 붙는 연결이에요. API 서버가 바깥으로 연결하는 경우는 이 밖에 어드미션 웹훅과 API 서버 밖에서 도는 APIService도 있어요. 우리 클러스터에는 웹훅 설정도 Local이 아닌 APIService도 0개였어요. 이 클러스터에서 API 서버가 먼저 여는 연결은 etcd와 kubelet 두 방향뿐이었고 나머지 화살표는 모두 6443으로 들어왔어요.

etcd의 피어 포트 2380은 192.168.104.1에서 받고 있었지만 맺힌 연결은 0개였어요. 피어 포트는 etcd 멤버끼리 Raft 로그를 주고받는 포트인데 우리 etcd는 멤버가 하나뿐이에요(21편). 여러 멤버가 무엇을 어떻게 주고받는지는 48편에서 다뤄요.

일반 CRI 호출은 TCP 포트 대신 Unix 소켓을 써요. 앞에서 본 exec·attach·port-forward의 스트리밍 연결은 별도예요. kubelet 설정의 containerRuntimeEndpoint는 unix:///var/run/containerd/containerd.sock이고 kubelet은 노드 안의 이 소켓 파일로 containerd를 불러요(26·27편). 지금까지 본 것을 한 장에 모으면 이래요. 화살표는 연결을 여는 쪽에서 나가고 상자 안의 주소는 받는 쪽이 기다리는 주소예요.

그림 5. 검은 화살표는 모두 6443으로 들어가고 API 서버가 여는 화살표는 초록(etcd)과 주황(kubelet) 둘이다. 번호는 아래 표의 번호다

3. 6443으로 가는 요청은 모두 REST이고 gRPC는 etcd와 CRI에서만 쓴다

도입의 설명으로 돌아가 볼게요. 같은 6443에 붙는다는 사실만으로 REST인지 gRPC인지는 가를 수 없어요. 실제 API 요청 경로와 클라이언트의 전송 설정을 함께 봐야 해요. 두 kubeconfig에 적힌 서버는 https://192.168.104.1:6443이었고 실제 연결도 6443으로 2개씩이었어요. 두 클라이언트가 쓰는 요청 본문의 형식도 확인했어요.

📖 용어: Accept와 Content-Type 헤더
HTTP 요청의 Accept는 "응답을 이 형식으로 달라"는 헤더이고 Content-Type은 "내가 보내는 본문은 이 형식이다"라는 헤더예요. API 개념 문서에 따르면 쿠버네티스 API는 HTTP로 JSON, YAML, CBOR, protobuf를 주고받을 수 있고 같은 REST 경로에서 이 두 헤더를 보고 형식을 골라요.
그림 6. kubectl은 JSON(Table)을 달라고 하고 kubelet과 kube-proxy의 기본 형식은 protobuf다. 같은 경로에 Accept만 바꾸면 응답 첫 바이트가 {와 k8s\0으로 갈린다

위에서부터 읽으면 이래요.

· kubectl get이 보낸 Accept는 application/json;as=Table…이었어요. JSON으로, 그리고 표 모양으로 달라는 요청이에요. 1장의 ROLES 칸을 API 서버가 채운 것도 이 as=Table 때문이에요.
· 같은 경로를 Accept만 바꿔 요청하자 JSON 응답은 {로, protobuf 응답은 k 8 s \0으로 시작했어요. 이 4바이트는 쿠버네티스가 protobuf 데이터를 감싸는 봉투의 맨 앞에 붙이는 표시예요. 22편에서 etcd에 저장된 Deployment 값의 맨 앞에서 본 것과 같은 바이트예요.
· worker1의 kubelet이 실제로 쓰는 설정(/configz)의 contentType은 application/vnd.kubernetes.protobuf였어요. kubelet 설정 레퍼런스에 적힌 기본값도 같아요.
· kube-proxy ConfigMap의 contentType은 빈 값이었어요. kube-proxy v1.37.2 소스(defaults.go)는 이 값이 비어 있으면 application/vnd.kubernetes.protobuf를 넣어요.

스케줄러와 컨트롤러 매니저의 매니페스트에는 형식을 정하는 플래그도 --config도 없어서 바이너리 기본값을 써요. 두 바이너리의 --help에는 --kube-api-content-type의 기본값이 "application/vnd.kubernetes.protobuf"로 적혀 있었어요(35-apiserver-protocols.txt). 정리하면 6443으로 가는 요청은 모두 HTTPS 위의 같은 REST API이고 kubectl은 JSON으로, 클러스터 안의 구성 요소는 protobuf로 본문을 주고받아요.

클러스터 안쪽 구성 요소에 protobuf를 쓰게 한 이유는 2016년에 쿠버네티스 API에 protobuf를 넣자고 낸 제안서에 적혀 있어요. 제안서는 API가 처리하는 요청의 "as much as 90%"가 노드, 컨트롤러, 프록시 같은 내부 구성 요소의 요청이고 JSON 직렬화와 역직렬화 비용이 API 서버의 CPU와 네트워크 사용을 좌우한다고 적었어요. 그래서 내부 구성 요소가 골라 쓸 수 있는 protobuf 직렬화("can optionally be used by intra-cluster components")를 제안했어요. 지금의 API 개념 문서도 protobuf를 "the more efficient binary Protobuf representation for better performance at scale", 곧 규모가 커질 때 성능을 위한 더 효율적인 이진 표현이라고 소개해요. 같은 제안서에는 "gRPC was considered, but is a larger change that requires more core refactoring"이라는 문장도 있어요. gRPC도 검토했지만 핵심 코드를 더 크게 고쳐야 했어요. 그래서 REST는 그대로 두고 본문 형식만 바꾼 거예요.

protobuf를 모든 리소스에 쓸 수 있는 것은 아니에요. API 개념 문서의 호환성 절에 따르면 CustomResourceDefinition으로 정의한 리소스와 aggregation 계층으로 제공되는 리소스에는 쿠버네티스 protobuf 인코딩을 쓸 수 없어요. Calico의 IPPool 같은 CRD 객체가 etcd에 JSON으로 저장돼 있던 것도 같은 이유예요(22편).

📖 용어: gRPC
호출할 함수와 주고받을 메시지의 모양을 .proto 파일로 정의하고 그 정의에서 만든 코드로 원격 함수를 부르는 RPC 방식이에요. 전송에는 HTTP/2를 쓰고 메시지는 protobuf로 인코딩해요. REST 요청이 "이 경로의 리소스를 GET하라"는 모양이라면 gRPC 요청은 "이 서비스의 이 함수를 불러라"는 모양이에요.

그럼 gRPC는 어디에 있을까요? 두 군데예요. 하나는 API 서버와 etcd 사이(⑦)예요. etcd 3.7의 API 문서에는 "Every API request sent to an etcd server is a gRPC remote procedure call."이라고 적혀 있어요. etcd 서버로 가는 API 요청은 모두 gRPC 원격 호출이에요. 다른 하나는 kubelet과 containerd 사이(⑨)예요. CRI 문서는 "The kubelet acts as a client when connecting to the container runtime via gRPC."라고 적어요. kubelet은 gRPC 클라이언트로 런타임에 붙고 우리 kubelet은 그 호출을 2장에서 본 유닉스 소켓으로 보내요. 두 연결은 API 서버의 뒤(etcd)와 kubelet의 아래(런타임)에 있어요. 다른 구성 요소는 이 두 연결을 직접 쓰지 않아요.

etcd라고 해서 모든 연결이 gRPC인 것도 아니에요. 멤버끼리 Raft 로그를 주고받는 피어 포트(⑩)는 etcd 안의 rafthttp 패키지가 맡는데 etcd v3.7.0 소스의 패키지 설명이 "Package rafthttp implements HTTP transportation layer for raft pkg."예요. 멤버끼리 오가는 Raft 메시지는 etcd 안의 HTTP 전송 계층을 타요. 우리 etcd는 멤버가 하나라 이 연결을 직접 볼 수는 없었어요.

그림 7. 6443으로 가는 요청은 본문 형식만 다른 같은 REST이고 gRPC는 API 서버 뒤의 etcd와 kubelet 아래의 런타임에만 있다

그래서 "왜 얘네들은 gRPC를 골랐는지"라는 제 질문은 "왜 etcd와 CRI는 gRPC를 골랐고 쿠버네티스 API는 REST에 남았는지"로 바뀌었어요. 그날 저는 "단순히 빠르고 편하다 말고 그게 그렇게 큰 오버헤드를 주나? 그때는 gRPC 많이 쓰던 때가 아니었는데"라고도 물었어요. CRI를 처음 제안한 이슈와 etcd v3 설계 문서를 원문으로 따라간 답은 46편에 적어요.

💡 실무에서는: 연결마다 맞는 도구로 본다
• 6443은 HTTPS REST라서 kubectl get --raw나 curl로 봐요. grpcurl 같은 gRPC 도구는 6443에 쓸 수 없어요
• etcd(2379)와 CRI 소켓은 gRPC라서 etcdctl, crictl 같은 전용 도구로 봐요(22·27편)
• 직접 만든 컨트롤러가 기본 리소스를 protobuf로 주고받게 하더라도 CRD는 protobuf가 안 돼요. API 개념 문서의 예시대로 Accept: application/vnd.kubernetes.protobuf, application/json을 보내 JSON도 받겠다고 적어 둬요

4. 구성 요소마다 인증서나 토큰으로 이름을 얻고 바인딩으로 권한을 받는다

6443은 모든 노드의 모든 프로그램이 연결하는 포트예요. 그러니 받은 요청이 누구의 것이고 무엇까지 해도 되는지를 API 서버가 정해야 해요. 32편에서 본 대로 클라이언트 인증서의 CN은 사용자 이름이 되고 O는 그룹이 돼요. 구성 요소마다 그 이름을 확인하려고 마스터의 kubeconfig에 든 인증서를 풀어 보고 같은 kubeconfig로 kubectl auth whoami를 실행해 API 서버가 그 요청을 누구로 보는지 물었어요. 그다음 그 이름에 권한을 붙이는 ClusterRoleBinding을 찾았어요.

📖 용어: ClusterRole과 ClusterRoleBinding
ClusterRole은 "어떤 리소스에 어떤 동작(get, list, create …)을 해도 되는지"를 적은 목록이고 ClusterRoleBinding은 그 목록을 사용자, 그룹, ServiceAccount에 붙이는 객체예요. 둘의 이름이 같은 경우가 많지만 서로 다른 객체예요. 바인딩이 없으면 역할은 누구에게도 효력이 없어요.
그림 8. 인증서의 CN과 O가 그대로 API 서버가 보는 사용자와 그룹이 되고 그 이름마다 ClusterRoleBinding이 역할을 붙인다

구성 요소별로 읽으면 이래요.

스케줄러. scheduler.conf의 인증서 CN은 system:kube-scheduler였고 whoami도 같은 이름이었어요. 이 사용자에게는 ClusterRole system:kube-scheduler와 system:volume-scheduler가 바인딩돼 있었어요. RBAC 문서의 "Core component roles" 표에 적힌 기본 역할과 기본 바인딩 그대로예요. 역할 안을 보면 파드는 get·list·watch·delete, pods/binding은 create, pods/status는 patch·update였어요(35-scheduler-cycle.txt 0절). 파드를 만드는(create) 권한은 없어요. 스케줄러가 하는 일은 파드에 노드를 적는 바인딩이고 컨테이너를 띄우는 일은 kubelet 몫이에요(41편). 파드 delete 권한은 선점(preemption)에 쓰여요. v1.37.2 소스(executor.go)를 보면 우선순위가 높은 파드를 위해 희생 파드를 고른 뒤 그 파드에 DisruptionTarget 조건을 붙이고 지워요.

컨트롤러 매니저. 인증서 CN은 system:kube-controller-manager였어요. 그런데 매니페스트에 --use-service-account-credentials=true가 있어요. RBAC 문서에 따르면 이 플래그를 주면 "kube-controller-manager starts each controller using a separate service account"이고 컨트롤러마다 system:controller:로 시작하는 역할이 있어요. 컨트롤러마다 다른 ServiceAccount로 API 서버에 붙는다는 뜻이에요. 우리 클러스터의 kube-system에는 이름이 -controller로 끝나는 ServiceAccount가 30개 있었고(35-controller-manager.txt 2절) system:controller:로 시작하는 ClusterRoleBinding 41개는 모두 kube-system의 ServiceAccount를 가리켰어요. ReplicaSet 컨트롤러는 replicaset-controller라는 이름으로, Deployment 컨트롤러는 deployment-controller라는 이름으로 따로 권한을 받아요. 바이너리 하나에 컨트롤러 49개가 들어 있어도 그 컨트롤러들이 권한 하나를 통째로 나눠 쓰지는 않아요(42편).

kubelet. kubelet.conf가 가리키는 인증서는 O=system:nodes, CN=system:node:k8s-master였고 worker1에서는 CN이 system:node:k8s-worker1이었어요. kubelet의 권한은 Node 인가자가 정해요. RBAC 문서도 system:node 역할 대신 Node 인가자와 NodeRestriction 어드미션 플러그인을 쓰라고 하고 우리 클러스터의 system:node 바인딩은 subjects가 비어 있었어요. 자기 노드에 배정된 파드가 쓰는 Secret만 읽게 막는 실험은 32편에서 했어요.

kube-proxy. kube-proxy는 ServiceAccount kube-proxy의 토큰으로 들어가요. kubeadm 구현 문서에 kube-proxy의 자격(ca.crt와 토큰)이 ServiceAccount에서 오고 그 ServiceAccount를 system:node-proxier 역할에 묶는다고 적혀 있어요. 실제 바인딩 이름은 kubeadm:node-proxier였어요. RBAC 문서의 기본 바인딩은 system:kube-proxy라는 사용자를 가리키는데 kubeadm은 그 사용자 대신 ServiceAccount를 묶었어요. calico-node, calico-kube-controllers, CoreDNS에도 저마다 ServiceAccount와 바인딩이 있었어요.

클라이언트가 된 API 서버. API 서버는 etcd에 붙을 때 apiserver-etcd-client.crt(CN=kube-apiserver-etcd-client, 발급자 etcd-ca)를 내요. kubelet에 붙을 때는 apiserver-kubelet-client.crt(CN=kube-apiserver-kubelet-client, 발급자 kubernetes)를 내고 이 사용자에게는 kubeadm:apiserver-kubelet-client 바인딩으로 system:kubelet-api-admin 역할이 붙어 있어요. kubelet은 인가 모드가 Webhook이라서(26편) 이 요청을 받으면 그 권한을 API 서버에 되물어요. kubelet 인증·인가 문서에 "the kubelet calls the SubjectAccessReview API on the configured API server to determine whether each request is authorized"라고 적혀 있어요. API 서버가 kubelet에 연 연결(⑧)의 권한 확인이 다시 API 서버로 돌아오는 셈이에요.

정리하면 구성 요소가 누구인지는 인증서나 토큰이 정하고 무엇을 할 수 있는지는 그 이름에 붙은 바인딩과 인가 모드가 정해요. 같은 6443으로 들어와도 스케줄러는 파드를 만들 수 없고 kubelet은 자기 노드와 관련된 Secret만 읽을 수 있어요.

그림 9. 자격 파일이 이름을 정하고 바인딩이 권한을 정한다. 컨트롤러 매니저는 컨트롤러마다 ServiceAccount 이름을 따로 쓴다
⚠️ 주의: API 서버는 kubelet의 서버 인증서를 확인하지 않아요
• 노드와 컨트롤 플레인 통신 문서에는 "By default, the API server does not verify the kubelet's serving certificate"라고 적혀 있어요. 우리 API 서버에도 --kubelet-certificate-authority가 없었어요
• worker1의 kubelet 서버 인증서는 발급자가 k8s-worker1-ca@…인 자체 서명 인증서였어요. kubeadm 인증서 문서도 "By default the kubelet serving certificate deployed by kubeadm is self-signed"라고 적어요
• 그래서 ⑧ 연결은 TLS로 암호화되지만 상대가 진짜 그 노드의 kubelet인지는 확인하지 않아요. 노드 사이 네트워크를 믿기 어렵다면 같은 문서의 "Enabling signed kubelet serving certificates" 절에 따라 kubelet 서버 인증서를 클러스터 CA로 서명받게 하고 API 서버에 --kubelet-certificate-authority를 주는 방법을 검토해요
• TLS로 연결하더라도 상대 인증서까지 확인하는지는 별개예요. 연결마다 누가 누구의 인증서를 확인하는지까지 봐야 해요

5. "etcd는 API 서버하고만 통신한다"와 "모듈형이라 안정적이다"를 정확히 말하면

etcd에 붙을 수 있는 것은 etcd CA가 서명한 인증서를 가진 쪽이다

etcd를 보던 중 저는 "etcd는 API 서버랑만 통신 가능하대"라고 적고 바로 "당연한 거지"라고 덧붙였어요. 2장의 숫자만 보면 맞는 말이에요. 2379에 연결을 연 프로세스는 kube-apiserver뿐이었어요. 그런데 etcd 설정에 "API 서버만 받는다"는 규칙은 없어요. etcd가 정해 둔 것은 인증서 조건이에요.

# 35-etcd-clients.txt 발췌 (19:56:50 KST, master /etc/kubernetes/manifests/etcd.yaml) - --client-cert-auth=true - --listen-client-urls=https://127.0.0.1:2379,https://192.168.104.1:2379 - --trusted-ca-file=/etc/kubernetes/pki/etcd/ca.crt # 35-etcd-certs.txt 발췌 (22:03:08 KST) ## 1. k8s-master: etcd-ca 가 서명한 인증서 (subject / issuer / 확장 키 용도) etcd/healthcheck-client.crt subject=/CN=kube-etcd-healthcheck-client issuer=/CN=etcd-ca | TLS Web Client Authentication etcd/peer.crt subject=/CN=k8s-master issuer=/CN=etcd-ca | TLS Web Server Authentication, TLS Web Client Authentication etcd/server.crt subject=/CN=k8s-master issuer=/CN=etcd-ca | TLS Web Server Authentication, TLS Web Client Authentication apiserver-etcd-client.crt subject=/CN=kube-apiserver-etcd-client issuer=/CN=etcd-ca | TLS Web Client Authentication etcd 의 클라이언트 인증서를 쓰는 정적 파드 플래그: - --etcd-certfile=/etc/kubernetes/pki/apiserver-etcd-client.crt ## 2. 워커의 /etc/kubernetes/pki [k8s-worker1] ca.crt

→ etcd는 클라이언트 인증서를 요구하고(--client-cert-auth=true) 그 인증서가 etcd CA로 서명됐는지를 본다는 뜻이에요. 2379는 127.0.0.1뿐 아니라 노드 IP 192.168.104.1에서도 받아요. 마스터에는 CA를 빼고 etcd CA가 서명한 인증서가 넷 있었고 넷 모두 클라이언트 인증 용도가 들어 있었어요. 정적 파드 매니페스트에서 etcd 클라이언트 인증서를 쓰는 플래그는 kube-apiserver의 --etcd-certfile 하나뿐이었어요. 워커 세 대의 /etc/kubernetes/pki에는 클러스터 CA(ca.crt) 하나만 있었어요. 그래서 worker1에서 인증서 없이 2379에 붙자 TLS 단계에서 끊겼어요(curl 종료 코드 56, 22편).

📖 용어: 확장 키 용도 (Extended Key Usage)
인증서를 어디에 써도 되는지 적어 두는 칸이에요. TLS Web Server Authentication이 있으면 서버 인증서로, TLS Web Client Authentication이 있으면 클라이언트 인증서로 쓸 수 있어요. etcd의 server.crt와 peer.crt에는 두 용도가 다 들어 있어요.

정확히 말하면 "etcd는 API 서버하고만 통신한다"는 etcd의 규칙이 아니라 etcd CA가 서명한 클라이언트 인증서를 쓰도록 설정된 프로그램이 API 서버뿐이라는 결과예요. 마스터에서 root 권한이 있으면 다른 인증서로도 붙을 수 있어요. 22편에서 etcd 파드 안의 etcdctl로 /registry 키를 열어 볼 때 낸 클라이언트 인증서도 etcd의 server.crt였어요. "당연한 것"은 저절로 지켜지지 않아요. 인증서를 누구에게 나눠 줬는지와 마스터의 파일 권한으로 지켜져요.

⚠️ 주의: etcd 인증서는 클러스터 전체 권한과 같은 무게다
• etcd에 직접 붙으면 API 서버의 인증, 인가, 어드미션을 하나도 거치지 않아요. 22편에서는 etcd의 server.crt 하나로 /registry 아래 키를 그대로 읽었고 암호화를 켜지 않은 Secret은 평문이었어요
• 그래서 마스터의 /etc/kubernetes/pki/etcd와 apiserver-etcd-client.key는 admin.conf와 같은 수준으로 지켜야 해요. etcd 스냅숏 파일도 마찬가지예요(40편)
• 컨트롤 플레인이 한 대이고 API 서버가 127.0.0.1:2379로 붙는 구성이라면 다른 노드에서 192.168.104.1:2379로 올 연결이 지도에 없어요. 이런 구성에서는 다른 노드에서 오는 2379를 방화벽에서 막아 두는 편이 안전해요

모듈형 구조가 안정적인 이유와 그 대가

구성 요소를 다 보고 나서 제가 남긴 감상은 "이런 모듈형 구조가 안정성이랑 확장성이 좋은 것 같아"였어요. 감상으로 끝내지 않으려고 지금까지의 실험에서 근거를 찾아봤어요.

안정성: 하나가 멈춰도 나머지는 자기 일을 한다. 구성 요소끼리 서로를 부르지 않고 API 서버에 적힌 기록만 보기 때문에 하나가 멈추면 그 구성 요소의 일만 멈췄어요. 20편에서 API 서버를 멈춘 동안에도 파드 IP로 보낸 curl은 200이었고 스케줄러를 멈추자 새 파드만 Pending에 머물렀어요. 25편에서 worker3의 kubelet을 멈춘 165초 동안에도 파드 IP로 보낸 curl은 200이었고 26편에서 containerd와 kubelet을 재시작해도 nginx 프로세스 번호가 그대로였어요. 28편에서 kube-proxy 파드를 지우는 동안 보낸 ClusterIP curl 24번도 모두 200이었고 30편에서 BIRD를 멈춰도 커널 경로가 남아 통신이 이어졌어요. 이 결과는 19편 5절의 표에 모아 두었어요.

멈췄다 다시 떠도 잃을 것이 없는 이유는 상태를 쥔 곳이 etcd 하나이기 때문이에요. 컨트롤 플레인 정적 파드가 노드에 쓸 수 있게 마운트한 경로를 보면 차이가 분명해요.

# 35-connection-map.txt 7절 (미러 파드 spec 의 hostPath 마운트, readOnly 여부) etcd-k8s-master 쓰기 가능: /var/lib/etcd, /etc/kubernetes/pki/etcd 읽기 전용: 없음 kube-apiserver-k8s-master 쓰기 가능: 없음 읽기 전용: /etc/ssl/certs, /etc/ca-certificates, /etc/kubernetes/pki, /usr/local/share/ca-certificates, /usr/share/ca-certificates kube-controller-manager-k8s-master 쓰기 가능: 없음 읽기 전용: /etc/ssl/certs, /etc/ca-certificates, /etc/kubernetes/pki, /etc/kubernetes/controller-manager.conf, /usr/local/share/ca-certificates, /usr/share/ca-certificates kube-scheduler-k8s-master 쓰기 가능: 없음 읽기 전용: /etc/kubernetes/scheduler.conf

→ 노드 디스크에 무언가를 쓸 수 있게 마운트한 것은 etcd뿐이고 API 서버, 컨트롤러 매니저, 스케줄러는 인증서와 kubeconfig를 읽기만 한다는 뜻이에요. 이 셋은 다시 뜨면 필요한 것을 API 서버와 etcd에서 다시 읽어요. 20편에서도 API 서버의 매니페스트를 되돌리자 5초 뒤 /readyz가 ok로 돌아왔어요.

확장성: 같은 일을 하는 인스턴스를 늘리고 부품을 바꿔 끼울 수 있다. API 서버는 상태를 갖지 않으니 여러 대를 로드밸런서 뒤에 둘 수 있고 스케줄러와 컨트롤러 매니저는 리더 선출로 한 번에 한 대만 일해요(21편). 우리 클러스터에서도 두 구성 요소는 --leader-elect=true로 떠 있었고 리더 Lease의 leaseDurationSeconds는 15였어요(35-scheduler-cycle.txt, 35-controller-manager.txt의 0절). 부품을 바꿔 끼우는 자리는 구성 요소 사이의 경계마다 있어요. 쿠버네티스 확장 문서는 클러스터의 확장 지점을 일곱 군데로 정리해요. 이 시리즈에서 직접 본 것만 꼽아도 이래요.

· CRI: kubelet은 containerd가 아니어도 CRI를 지키는 런타임이면 붙어요(⑨, 26·27·45편).
· CNI: 파드 네트워크는 Calico가 맡았어요(30·31·34편).
· CRD: Calico는 자기 설정을 CRD로 API 서버에 등록했어요. 등록된 리소스 종류 94개 중 22개가 Calico의 CRD였어요(20편).
· 스케줄러 플러그인: 필터와 스코어를 플러그인 단위로 켜고 가중치를 줘요(23편).
· 어드미션: 기본으로 켜지는 어드미션 플러그인 25개에 웹훅으로 만든 검사를 더할 수 있어요. 우리 클러스터의 웹훅 설정은 0개였어요(33편).
· CSI: 스토리지도 같은 방식의 플러그인 인터페이스로 붙여요. 이 시리즈에서는 아직 다루지 않았어요.

대가: 이음매에서 늦거나 어긋난다. 구성 요소가 기록으로만 이어지니 한쪽이 늦거나 멈추면 다른 쪽은 옛 기록을 믿고 움직여요. 28편에서 worker1의 kube-proxy만 없는 동안 파드 수가 바뀌자 worker1의 규칙은 지워진 파드까지 가리켰고 worker1에서 보낸 curl 30번 중 22번이 실패했어요. 34편에서는 죽은 노드에 있던 calico-kube-controllers가 다른 노드에서 다시 뜬 뒤 약 23분 35초 동안 IPAM 정리를 시작하지 못했어요. kubelet을 멈추고 다른 노드에 새 파드가 만들어지기까지도 기본 설정에서 5분 45초가 걸렸어요(25편). kubelet, node-lifecycle-controller, taint 기반 축출이 저마다 정해진 간격과 유예 시간으로 기록을 주고받기 때문이에요. 이 숫자들이 왜 그 값인지는 49·50편에서 다뤄요.

그래서 "모듈형이라 안정적이다"를 정확히 말하면 이래요. 구성 요소 하나가 멈춰도 이미 만들어진 컨테이너와 규칙은 그대로 남고 변경만 멈춰요. 대신 이음매의 기록이 늦게 따라오는 동안에는 옛 기록대로 움직여요.

2부의 흐름을 문장으로 이으면 이래요. 쿠버네티스는 컨테이너가 아니라 파드를 단위로 삼아 파드마다 IP 하나를 줬어요(43편). 그러면 노드 한 대에 파드를 몇 개까지 올릴지 정해야 해요(44편). 그 파드를 띄우는 kubelet은 한때 Docker에 묶여 있었고 쿠버네티스는 그 경계를 CRI로 떼어 냈어요(45편). 떼어 낸 경계(⑨)와 저장소 경계(⑦)에는 gRPC가 놓였어요(46편). 파드 IP는 파드가 바뀔 때 달라질 수 있으니 Service가 고정된 주소를 주고 kube-proxy가 그 주소를 파드 IP로 바꿔요. 그 방식이 iptables와 IPVS를 거쳐 nftables까지 바뀌어 왔어요(47편). 이 모든 상태는 etcd 한 곳에 모이고 etcd는 Raft로 멤버 사이의 일관성을 지켜요(48편). 그 한 곳에 노드마다 10초 간격으로 하트비트를 쓰면 노드가 많아질수록 부담이 커지고 그 부담을 줄이려고 하트비트를 Lease로 옮겼어요(49편). 마지막으로 그 하트비트를 보고 장애를 판단하는 숫자가 50초와 300초예요(50편).

✍️ 오늘의 요약
구성 요소의 연결은 거의 모두 API 서버의 6443으로 열리고 API 서버가 먼저 여는 곳은 etcd와 kubelet 둘이에요. gRPC는 etcd와 CRI에서만 써요.

컨트롤 플레인 넷은 마스터의 정적 파드였고 ROLES 칸은 API 서버가 node-role 라벨로 채운 값이었어요. 노드 밖에서 연결을 받는 것은 API 서버 6443, etcd 2379·2380, kubelet 10250, kube-proxy 10256, BIRD 179였고 스케줄러와 컨트롤러 매니저는 받을 일이 없어서 127.0.0.1에만 열려 있었어요. kubectl은 JSON으로, 스케줄러·컨트롤러 매니저·kubelet·kube-proxy는 protobuf로 같은 REST API를 불렀고 gRPC는 API 서버와 etcd 사이, kubelet과 containerd 사이에만 있었어요. 구성 요소의 이름은 kubeconfig 인증서의 CN과 O나 ServiceAccount 토큰이 정했고 권한은 ClusterRoleBinding과 Node 인가자가 정했어요. API 서버는 kubelet의 자체 서명 인증서를 확인하지 않았어요. etcd에 API 서버만 붙는 것은 etcd CA 인증서를 쓰도록 설정된 쪽이 API 서버뿐이기 때문이었어요. 모듈형 구조는 하나가 멈춰도 이미 만든 것을 지켰지만 이음매의 기록이 늦을 때는 옛 기록대로 움직였어요. 아키텍처는 상자보다 연결로 읽어야 하고 연결은 여는 쪽, 받는 주소, 형식, 신원 네 가지로 읽혀요.
