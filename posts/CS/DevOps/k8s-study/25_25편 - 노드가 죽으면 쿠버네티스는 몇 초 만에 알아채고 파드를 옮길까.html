14시 58분 41초에 worker3에서 sudo systemctl stop kubelet을 실행하고 10초마다 노드 상태를 찍었어요. 10초, 21초, 31초, 41초가 지나도 kubectl get node는 worker3을 Ready=True로 보여 줬어요. 52초째 확인에서야 Ready가 Unknown으로 바뀌었고 노드에 taint 두 개가 붙었어요. 그 노드의 myweb 파드는 그 뒤로도 API에서 Running이었고 파드 IP로 직접 보낸 curl은 165초 동안 한 번도 실패하지 않았어요.

제가 적어 둔 한 줄에서 이 글을 시작했어요. "노드도 오브젝트로 관리해서 가용성 체크 같은 걸 한대." 노드가 파드나 Deployment와 같은 API 객체라면 노드가 살아 있는지는 누가 어디에 적고 누가 보고 판단하는지 궁금했어요. 노드가 죽었다고 판단한 뒤 파드가 언제 다른 노드로 옮겨지는지도 궁금했어요.

이번 글에서는 Node 객체에 무엇이 적혀 있는지부터 봐요. 이어서 kubelet이 보내는 하트비트 두 갈래와 그 하트비트를 보고 판단하는 컨트롤러 매니저의 기본값을 살펴보고 kubelet을 멈춘 실험의 타임라인을 거쳐 파드가 실제로 옮겨지기까지 걸리는 시간을 따라가요. 클러스터는 지금까지 써 온 실습 환경(Lima VM 4대, kubeadm v1.37.2)이에요.

이 글에서 다룰 것
· Node 객체에는 무엇이 적혀 있고 누가 적을까?
· kubelet은 얼마나 자주 "살아 있다"고 알릴까?
· 노드가 응답하지 않으면 몇 초 만에 Unknown이 될까?
· Unknown이 된 노드의 파드는 바로 옮겨질까?
· 쫓겨난 옛 파드는 언제 API에서 사라질까?
· 이 시간을 줄이려면 무엇을 바꿀까?

1. 노드도 API 객체라서 상태를 적어 두는 칸이 있다

먼저 worker1의 Node 객체를 열어 봤어요(15:40).

그림 1. Node 객체의 status에는 조건(conditions)과 용량, 버전 정보가 함께 들어 있다

위 다섯 줄이 conditions예요. Node Status 문서의 표를 따라 읽으면 MemoryPressure·DiskPressure·PIDPressure는 메모리·디스크·프로세스 수가 모자란지, NetworkUnavailable은 노드의 네트워크 설정이 잘못됐는지, Ready는 노드가 건강해서 파드를 받을 수 있는지를 나타내요. Ready만 True이고 나머지가 모두 False면 정상이에요.

📖 용어: 노드 조건 (Node condition)
Node 객체의 status.conditions에 들어가는 항목이에요. 항목마다 type, status(True·False·Unknown), reason, 그리고 마지막으로 보고된 시각인 lastHeartbeatTime이 있어요. kubectl get node의 STATUS 열에 보이는 Ready나 NotReady는 이 가운데 Ready 조건을 줄여 보여 주는 거예요.

reason 열을 보면 조건마다 누가 적었는지 알 수 있어요. 네 조건의 reason은 KubeletReady, KubeletHasSufficientMemory 등 kubelet이 붙인 이름이고 lastHeartbeatTime도 06:33:24Z로 같아요. NetworkUnavailable만 reason이 CalicoIsUp이고 시각도 05:55:56Z로 달라요. Calico v3.33.0 소스(node/pkg/lifecycle/utils/utils.go)에 reason "CalicoIsUp", message "Calico is running on this node"로 이 조건을 False로 적는 코드가 있어요. 노드의 네트워크를 책임지는 CNI가 직접 적는 칸이에요.

아래 다섯 줄은 노드의 크기와 기본 정보예요. capacity는 노드 전체 용량이고 allocatable은 파드에 나눠 줄 수 있는 양이에요. 메모리를 보면 3998420Ki와 3896020Ki로 102400Ki(100Mi) 차이가 나요. 2절에서 볼 kubelet 설정의 evictionHard에 memory.available: 100Mi가 있고 Reserve Compute Resources 문서에는 "resources reserved for evictions are not available for pods"라고 적혀 있어요. 그 100Mi만큼 파드 몫에서 빠진 거예요. 23편에서 스케줄러가 비교한 값이 이 allocatable이었어요. nodeInfo의 kubelet·containerd·커널 버전과 spec의 podCIDR도 모두 이 객체에 있어요.

2. kubelet의 하트비트는 Lease와 Node status 두 갈래다

노드가 살아 있다는 신호는 어디에 남을까요? Nodes 문서에는 두 가지가 적혀 있어요.

For nodes there are two forms of heartbeats: * Updates to the .status of a Node. * Lease objects within the kube-node-lease namespace. Each Node has an associated Lease object.

→ 하나는 방금 본 Node 객체의 status를 고치는 것이고 다른 하나는 kube-node-lease 네임스페이스에 노드마다 하나씩 있는 Lease 객체를 고치는 것이에요.

📖 용어: Lease (노드 하트비트용)
coordination.k8s.io API 그룹의 작은 객체예요. Leases 문서에 따르면 kubelet의 하트비트는 이 객체의 spec.renewTime을 고치는 update 요청이고 컨트롤 플레인은 이 시각으로 노드가 살아 있는지 판단해요. 24편에서 본 컨트롤러 매니저의 리더 선출에도 같은 종류의 객체를 써요.

두 갈래가 실제로 얼마나 자주 갱신되는지 보려고 worker1의 Lease와 Node를 4초 간격으로 찍었어요.

그림 2. Lease는 10초마다 갱신되고 Node status의 하트비트 시각은 7분 넘게 그대로였다

Lease의 renewTime은 06:40:33 → 06:40:43 → 06:40:53 → 06:41:03으로 약 10초 간격으로 바뀌었어요. 같은 25초 동안 Node의 Ready lastHeartbeatTime은 06:33:24Z에서 06:40:43Z로 한 번 바뀌었어요. 06:33:24Z는 한국 시각 15:33:24이고 26편 실험에서 worker1의 kubelet을 재시작한 시각이에요. 그러니 06:33:24Z부터 06:40:43Z까지 7분 19초 동안 Node status의 하트비트 시각은 그대로였어요.

kubelet의 실행 설정(/configz)을 보면 이유가 나와요. nodeStatusUpdateFrequency 10s, nodeStatusReportFrequency 5m0s, nodeLeaseDurationSeconds 40이었어요. kubelet 설정 문서에 따르면 kubelet은 10초마다 노드 상태를 계산하지만 API 서버에 보내는 것은 "either when it changes or when nodeStatusReportFrequency has elapsed since the last report", 즉 상태가 바뀌었거나 마지막 보고 뒤 5분이 지났을 때뿐이에요. Lease 갱신 주기는 같은 문서에 "The lease is currently renewed every 10s"라고 적혀 있어요. Node Status 문서에는 그 이유가 "Compared to updates to .status of a Node, a Lease is a lightweight resource"라고 적혀 있어요. 큰 Node 객체를 10초마다 다시 쓰는 대신 작은 Lease만 자주 고친다는 뜻이에요.

5분인데 7분 19초가 걸린 이유는 v1.37.2 kubelet 소스(kubelet_node_status.go)를 보면 알 수 있어요. kubelet이 막 시작했거나 상태가 바뀐 뒤에는 다음 정기 보고까지의 간격에 nodeStatusReportFrequency의 −50%~+50% 사이 무작위 값(calculateDelay)을 더해요. 주석에 적힌 목적은 모든 노드의 정기 보고가 API 서버에 한꺼번에 몰리지 않게 하는 것이에요. 5분 ± 2분 30초이니 2분 30초에서 7분 30초 사이이고 관찰한 7분 19초는 그 안에 들어가요.

노드가 살아 있다는 신호는 10초마다 고치는 Lease가 맡고 Node status는 바뀔 때나 몇 분에 한 번만 갱신돼요. 그래서 Node의 lastHeartbeatTime이 몇 분 전이라고 해서 노드가 죽은 것은 아니에요.

3. 판단은 컨트롤러 매니저의 node-lifecycle-controller가 한다

하트비트를 보내는 쪽이 kubelet이면 받아서 판단하는 쪽은 24편에서 본 KCM 안의 node-lifecycle-controller예요. 그 기본값을 KCM 바이너리의 --help에서 꺼냈어요(설명은 줄였어요).

--node-monitor-period 5s The period for syncing NodeStatus in NodeLifecycleController. --node-monitor-grace-period 50s Amount of time which we allow running Node to be unresponsive before marking it unhealthy. --node-startup-grace-period 1m0s Amount of time which we allow starting Node to be unresponsive before marking it unhealthy. --node-eviction-rate 0.1 Number of nodes per second on which pods are deleted in case of node failure when a zone is healthy --secondary-node-eviction-rate 0.01 우리 KCM 에 이 플래그를 따로 준 것: 0개 (= 기본값 사용)

→ 5초마다 노드를 확인하고 실행 중인 노드가 50초 동안 응답하지 않으면 건강하지 않다고 표시한다는 뜻이에요. 막 시작한 노드에는 1분을 줘요. 우리 KCM에는 이 플래그가 하나도 없으니 모두 기본값이에요.

📖 용어: node-lifecycle-controller
KCM 안에서 노드의 건강을 지켜보는 컨트롤러예요. Nodes 문서에 따르면 노드에 닿지 않을 때 Ready 조건을 Unknown으로 바꾸고 노드 문제에 맞는 taint를 붙여서 스케줄러가 그 노드에 새 파드를 놓지 않게 해요.

무엇을 보고 "응답한다"고 판단하는지는 v1.37.2 소스(node_lifecycle_controller.go)에 나와 있어요. 컨트롤러는 노드마다 마지막으로 소식을 들은 시각(probeTimestamp)을 기억해 두고 Ready 조건이 갱신되거나 Lease의 renewTime이 바뀌면 그 시각을 현재 시각으로 고쳐요. 주석에 "Always update the probe time if node lease is renewed."라고 적혀 있어요. 그리고 현재 시각이 probeTimestamp에 50초를 더한 시각을 지났으면 Ready를 Unknown으로 바꾸고 reason을 NodeStatusUnknown, message를 "Kubelet stopped posting node status."로 적어요. 같은 파일에서 그 노드의 파드를 NotReady로 표시하는 MarkPodsNotReady도 불러요.

그러니 2절에서 본 대로 Node status가 7분 넘게 그대로여도 문제가 없었던 거예요. 10초마다 Lease가 갱신되니 probeTimestamp는 늘 최근 시각이에요. 반대로 kubelet이 멈추면 Lease 갱신도 멈추고 마지막 갱신에서 50초가 지나면 Unknown이 돼요.

그림 3. kubelet은 적기만 하고 노드가 죽었다는 판단과 표시는 node-lifecycle-controller가 한다

4. kubelet을 멈추면 약 50초 뒤 Unknown이 되고 파드는 계속 응답한다

이제 도입의 실험을 자세히 볼게요. worker3에 있는 myweb 파드(10.244.100.222)를 골라 두고 worker3의 kubelet만 멈췄어요. VM과 containerd, 컨테이너는 그대로 두었어요. 그다음 10초마다 노드의 Ready 조건, 노드의 taint, API가 보여 주는 파드 상태, 마스터에서 파드 IP로 보낸 curl 결과를 한 줄씩 찍었어요.

그림 4. 노드는 41초 확인까지 Ready였고 52초 확인에서 Unknown이었다. 파드 IP로 보낸 curl은 끝까지 200이었다

타임라인으로 정리하면 이래요.

경과 노드 Ready 노드 taint 파드(API) curl 파드IP +10~41s True / KubeletReady 없음 Running, ready=True 200 +52s Unknown / NodeStatusUnknown unreachable:NoSchedule, :NoExecute Running, ready=False 200 ~+165s (그대로) (그대로) (그대로) 200 kubelet 시작 5초 뒤 True / KubeletReady 없음

→ Unknown으로 바뀐 순간은 +41s와 +52s 사이예요. 마지막 Lease 갱신은 kubelet을 멈추기 전 10초 안의 어느 때였을 거예요. 거기에 50초와 확인 주기 5초를 더하면 멈춘 뒤 40~55초 사이에 바뀌어야 하고 관찰한 값도 그 범위 안에 있어요.

같은 확인 시점에 Unknown 말고도 두 가지가 더 바뀌었어요. 노드에 node.kubernetes.io/unreachable taint가 NoSchedule과 NoExecute 두 effect로 붙었고 파드의 ready가 False가 됐어요. Taints and Tolerations 문서는 unreachable taint를 "This corresponds to the NodeCondition Ready being "Unknown"."이라고 설명해요. Ready 조건이 Unknown인 상태에 대응하는 taint라는 뜻이에요. NoSchedule 쪽은 23편의 TaintToleration 필터에서 새 파드를 이 노드에 놓지 못하게 하고 NoExecute 쪽은 5절에서 볼 축출의 출발점이에요.

그런데 파드의 phase는 Running 그대로였어요. phase를 고치는 쪽은 그 노드의 kubelet인데 kubelet이 멈춰 있으니 아무도 고치지 않은 거예요. API에 보이는 Running은 "kubelet이 마지막으로 보고한 상태"일 뿐이에요.

컨테이너는 kubelet 없이도 돈다

curl은 165초 내내 200이었어요. kubelet은 컨테이너를 만들고 지켜보는 관리자일 뿐 요청이 지나가는 길에 있지 않아요. 26편에서 보겠지만 컨테이너 프로세스의 부모는 kubelet이 아니라 containerd-shim이라 kubelet이 멈춰도 컨테이너는 그대로 돌아요. 파드 IP로 가는 경로도 Calico가 이미 깔아 둔 것이라 kubelet과 상관이 없어요. "노드가 Unknown"은 컨트롤 플레인이 그 노드 소식을 못 듣는다는 뜻이지 노드 위의 파드가 멈췄다는 뜻이 아니에요.

Service 트래픽은 먼저 빠진다

파드 IP로 직접 보내면 응답하지만 Service로 보내는 트래픽은 어떨까요? 몇 분 뒤 같은 파드로 실험을 한 번 더 했어요. kubelet을 멈추고 65초 뒤에 그 파드의 EndpointSlice 항목을 봤어요.

그림 5. 65초 뒤 EndpointSlice에서 그 파드는 ready=False, serving=False가 됐고 kubectl logs는 kubelet에 닿지 못했다

EndpointSlice의 그 파드 항목이 ready=True·serving=True에서 ready=False·serving=False로 바뀌었어요. EndpointSlices 문서에 따르면 serving은 파드의 Ready 조건에 대응하고 ready는 "serving이면서 terminating이 아님"을 줄여 쓴 조건이에요. node-lifecycle-controller가 파드를 NotReady로 표시하자 EndpointSlice 컨트롤러가 따라 바꾼 거예요. kube-proxy는 ready인 엔드포인트로 Service 규칙을 만드니(28편) 이때부터 Service로 오는 요청은 다른 myweb 파드로만 가요. 파드는 살아 있는데 Service 대상에서는 빠진 상태예요.

같은 시각 kubectl logs는 실패했어요. 메시지는 dial tcp 192.168.104.5:10250: connect: conn에서 끝나는데 스크립트가 출력을 160자에서 잘랐기 때문이에요. 로그는 API 서버가 그 노드 kubelet의 10250 포트에서 직접 가져와요. 19편에서 본 kube-apiserver → :10250 연결이 이 길이고 kubelet이 멈춰서 10250 포트에서 연결을 기다리는 프로세스가 없으니 연결이 되지 않았어요. kubelet을 다시 시작하고 20초 뒤에는 노드도 EndpointSlice도 원래대로 돌아와 있었어요.

그림 6. 노드 장애를 알아채는 것과 파드를 옮기는 것 사이에는 300초가 더 있다

5. 파드를 옮기는 것은 300초 toleration이 끝난 뒤다

그림 4 위쪽의 toleration 두 줄에 이 글 제목이 묻는 나머지 절반의 답이 있어요. 실험 파드에는 이런 toleration이 붙어 있었어요.

node.kubernetes.io/not-ready NoExecute 300 node.kubernetes.io/unreachable NoExecute 300

→ not-ready나 unreachable taint가 NoExecute로 붙어도 300초 동안은 견딘다는 뜻이에요. 저는 myweb Deployment에 toleration을 적은 적이 없어요.

이 300초는 어드미션 단계에서 붙어요. 19편에서 컨테이너 하나만 적은 파드를 --dry-run=server로 보내 봤을 때 저장될 spec에 DefaultTolerationSeconds 플러그인이 정확히 이 두 줄(not-ready·unreachable, NoExecute, 300)을 붙였어요. Admission Controllers 문서에 따르면 이 플러그인은 파드에 그런 toleration이 아직 없을 때 API 서버의 default-not-ready-toleration-seconds와 default-unreachable-toleration-seconds 값으로 붙여요. 두 값의 기본값은 "The default value ... is 5 minutes."라고 적혀 있어요.

📖 용어: NoExecute taint와 tolerationSeconds
Taints and Tolerations 문서에 따르면 NoExecute는 이미 돌고 있는 파드에도 영향을 주는 effect예요. 견디지 못하는 파드는 바로 쫓겨나요(evict). tolerationSeconds 없이 견디는 파드는 계속 남고 tolerationSeconds를 적은 파드는 그 시간 동안만 남았다가 쫓겨나요.

그러니 순서는 이래요. 노드가 Unknown이 되면서 unreachable:NoExecute taint가 붙고 파드는 300초를 기다려요. 300초가 지나면 파드가 축출(삭제)되고 KCM의 replicaset-controller가 ReplicaSet의 파드 개수를 맞추려고 새 파드를 만들어요. 스케줄러는 새 파드를 다른 노드에 놓아요. worker3에는 unreachable:NoSchedule taint가 있어서 23편의 필터에서 빠지기 때문이에요. 같은 문서의 메모에는 "these automatically-added tolerations mean that Pods remain bound to Nodes for 5 minutes after one of these problems is detected"라고 적혀 있어요. 축출을 실제로 하는 쪽은 KCM 안의 taint-eviction-controller예요. 같은 문서에 1.29 이후로 taint 기반 축출을 node controller에서 떼어 taint-eviction-controller라는 별도 컨트롤러로 옮겼다는 메모가 있고 24편의 KCM 목록 49개에도 이 이름이 있어요.

kubelet을 29분 멈춰 본 결과: taint가 붙고 정확히 300초 뒤에 축출됐다

이 순서가 실제로 그대로 일어나는지 보려고 worker3의 kubelet을 다시 멈추고 이번에는 300초가 한참 지날 때까지 기다렸어요. 17:22:41에 멈추고 17:51:57에 다시 켰으니 약 29분이에요. worker3에는 myweb 파드 두 개(bn4k8, zjdrs)가 있었고 둘 다 not-ready·unreachable NoExecute 300 toleration이 붙어 있었어요. 15초마다 노드와 myweb 파드를 찍은 기록을 줄이면 이래요.

17:22:41 +0s k8s-worker3$ sudo systemctl stop kubelet 17:23:11 +30s Ready=True | taints: 없음 17:23:26 +45s Ready=Unknown | taints: unreachable:NoSchedule@2026-11-14T08:23:26Z unreachable:NoExecute@2026-11-14T08:23:26Z myweb: 4hfpn@k8s-worker2(Running) bn4k8@k8s-worker3(Running) q7mc8@k8s-worker2(Running) ... 17:28:16 +335s Ready=Unknown | (taint 그대로, myweb 다섯 개 그대로) 17:28:32 +350s myweb: 2vkcp@k8s-worker1(Running) bn4k8@k8s-worker3(Running del=2026-11-14T08:28:56Z) czgx5@k8s-worker2(Running) zjdrs@k8s-worker3(Running del=2026-11-14T08:28:...) ... (줄이고 일부 파드는 ...로 생략했어요)

→ +30초 확인까지 Ready였고 +45초 확인에서 Unknown이 됐어요. taint에 붙은 timeAdded가 08:23:26Z(한국 시각 17:23:26)예요. 4절 실험의 41~52초와 같은 범위이고 노드가 응답하지 않는다고 알아채는 데 약 45초가 걸린 셈이에요. 그 뒤 5분 가까이 아무 변화가 없다가 +350초 확인에서 새 파드 2vkcp와 czgx5가 보였고 옛 파드 두 개에는 del=(deletionTimestamp)이 붙었어요.

그림 7. NodeNotReady에서 정확히 5분 뒤 축출 이벤트와 새 파드 생성이 함께 찍혔다

이벤트 목록의 나이(AGE)를 보면 NodeNotReady는 7m23s, TaintManagerEviction과 SuccessfulCreate는 2m23s로 정확히 5분 차이예요. TaintManagerEviction은 taint 기반 축출이 남기는 이벤트이고 메시지는 "Marking for deletion Pod default/myweb-859c4764d4-bn4k8"이에요. 같은 순간 replicaset/myweb-859c4764d4가 새 파드 2vkcp와 czgx5를 만들고 SuccessfulCreate 이벤트를 남겼어요. 새 파드의 생성 시각(CREATED)은 둘 다 08:28:26Z이고 taint의 timeAdded 08:23:26Z에서 딱 300초 뒤예요. 새 파드는 worker1과 worker2로 갔어요. worker3에는 unreachable:NoSchedule taint가 있으니 23편의 필터에서 빠진 거예요.

이제 제목의 질문에 숫자로 답할 수 있어요. kubelet을 멈춘 17:22:41부터 새 파드가 생긴 17:28:26까지 5분 45초가 걸렸어요. 알아채는 데 걸린 약 45초에 기본 toleration 300초를 더한 값이에요. 알아채는 시간은 마지막 Lease 갱신이 언제였는지에 따라 40~55초 사이에서 달라지니 기본값에서는 대략 6분 안쪽이라고 보면 돼요. Nodes 문서에도 "By default, the node controller waits 5 minutes between marking the node as Unknown and submitting the first eviction request."라고 적혀 있어요.

쫓겨난 파드는 kubelet이 없으면 Terminating으로 남는다

옛 파드는 바로 사라지지 않았어요. 두 파드의 DELETED(deletionTimestamp)는 08:28:56Z로 축출 시각보다 30초 뒤였어요. Pod Lifecycle 문서에 적힌 기본 삭제 유예 시간("defaults to 30 seconds")만큼 뒤로 잡힌 값이에요. 그런데 그 시각이 지나도 두 파드는 목록에서 사라지지 않았어요. 기록에는 Running(del=…)으로 찍혔고 kubectl로 보면 Terminating인 상태로 남아 있었어요.

Force Delete StatefulSet Pods 문서가 이 상태를 설명해요. "A Pod is not deleted automatically when a node is unreachable. The Pods running on an unreachable Node enter the 'Terminating' or 'Unknown' state after a timeout." 같은 문서는 이런 파드가 API 서버에서 지워지는 방법을 셋으로 꼽아요. 첫째는 Node 객체가 지워지는 것, 둘째는 그 노드의 kubelet이 다시 응답해 파드를 정리하는 것, 셋째는 사용자가 강제로 지우는 것이에요. 파드를 API에서 지우는 마지막 단계는 그 노드의 kubelet이 컨테이너를 정리했다고 확인해 주는 일인데 kubelet이 없으니 끝나지 않은 거예요.

셋째 방법을 확인해 보려고 17:30:49에 두 파드를 kubectl delete pod <파드> --grace-period=0 --force로 지웠어요.

그림 8. 강제 삭제로 API의 파드는 사라졌지만 worker3에서는 nginx 컨테이너 두 개가 아직 돌고 있었다

명령은 바로 끝났고 두 파드는 API에서 사라졌어요. 같은 순간 worker3에서는 nginx 컨테이너 2개가 아직 돌고 있었어요. 4절에서 본 대로 kubelet이 멈춰도 컨테이너는 그대로 돌기 때문이에요. Taints and Tolerations 문서가 경고한 "the pods that are scheduled for deletion may continue to run on the partitioned node"가 실제로 일어난 거예요. 그 파드 IP(10.244.100.228)로 가는 노드의 경로는 이미 없었어요. worker3의 calico-node 로그를 보면 강제 삭제와 같은 08:30:49Z(한국 시각 17:30:49)에 Felix가 그 파드의 엔드포인트가 지워진 것을 알아채고("Local endpoint deleted") 10.244.100.228/32 경로를 지우는 RouteRemove를 처리했어요. 파드 객체가 사라지자 Felix가 경로를 걷어 낸 거예요.

Calico IPAM에도 흔적이 남았어요. calicoctl ipam check는 강제 삭제 직후부터 17:50:57까지 20분 넘게 "Found 2 IPs that are allocated in IPAM but not actually in use"를 보고했어요. 파드를 정상적으로 지울 때는 노드에서 샌드박스를 정리하며 CNI DEL로 IP를 돌려주는데(27편) 그 단계를 건너뛰었기 때문이에요. 이 IP가 언제 어떻게 회수되는지는 34편에서 다뤄요.

마지막으로 17:51:57에 kubelet을 다시 켰어요. 25초 뒤 확인했을 때 worker3은 Ready였고 taint도 없었어요. worker3의 nginx 컨테이너는 0개가 됐어요. 돌아온 kubelet이 API에 더 이상 없는 파드의 컨테이너를 정리한 거예요. 이때의 calicoctl ipam check 결과는 "found 0 problems"였어요.

⚠️ 주의: --force는 kubelet의 확인을 건너뛴다
• 문서에는 "Force deletions do not wait for confirmation from the kubelet that the Pod has been terminated."라고 적혀 있어요. 이번 실험에서도 강제 삭제 뒤 worker3에 컨테이너 두 개가 계속 돌고 있었어요
• StatefulSet 파드는 특히 위험해요. 강제 삭제는 파드 이름을 API 서버에서 바로 비우는데 문서는 그 결과를 "This would let the StatefulSet controller create a replacement Pod with that same identity; this can lead to the duplication of a still-running Pod"라고 설명해요. 식별자가 같은 파드가 둘 돌면 쿼럼 기반 시스템에서는 split brain과 데이터 손실로 이어질 수 있다고 문서는 경고해요
• 문서가 권하는 쪽은 강제 삭제가 아니에요. 노드가 확실히 죽었다면(전원이 꺼졌거나 네트워크에서 영구히 떨어졌다면) Node 객체를 지우고 네트워크 문제라면 복구를 기다려 kubelet이 정리하게 해요
• 강제로 지운 파드의 Calico IP는 IPAM에 남을 수 있어요(34편)
⚠️ 주의: 축출은 한꺼번에 일어나지 않을 수 있다
• Nodes 문서에 따르면 node controller는 축출 속도를 --node-eviction-rate(기본 0.1, 10초에 노드 1대)로 제한해요
• 한 영역(zone)에서 건강하지 않은 노드의 비율이 높으면(기본 55% 이상) 속도를 더 낮추는데 노드 50대 이하의 작은 클러스터라면 아예 멈춰요. 네트워크 문제로 여러 노드가 한꺼번에 끊긴 상황에서 파드를 대량으로 지우지 않으려는 장치예요
• DaemonSet 파드는 not-ready·unreachable을 tolerationSeconds 없이 견디도록 만들어져서 축출되지 않아요

6. 기다리는 시간을 줄이는 법과 노드 객체를 직접 고치는 cordon

약 6분이 너무 길다면 줄일 수 있는 곳은 세 군데예요.

어디서 무엇을 범위 파드 spec tolerations 의 tolerationSeconds 를 직접 적는다 그 파드만 kube-apiserver 플래그 --default-not-ready-toleration-seconds 클러스터 전체 --default-unreachable-toleration-seconds (기본 300) (새로 만드는 파드) kube-controller-manager --node-monitor-grace-period (기본 50s) 클러스터 전체

→ 가장 안전한 것은 첫째예요. 빨리 옮겨야 하는 상태 없는 서비스만 짧게 적고 나머지는 기본값대로 둘 수 있어요. 파드에 not-ready나 unreachable toleration을 직접 적었으면 DefaultTolerationSeconds는 그 taint의 toleration을 덧붙이지 않아요.

둘째의 두 플래그는 kube-apiserver 문서에 기본값 300으로 적혀 있고 설명에는 "Indicates the tolerationSeconds of the toleration for unreachable:NoExecute that is added by default to every pod that does not already have such a toleration."라고 적혀 있어요. 어드미션에서 붙이는 값이니 이미 만들어진 파드에는 영향이 없을 거예요. 셋째는 알아채는 시간 자체를 줄여요. 다만 우리 KCM의 --help에는 이 값이 kubelet의 nodeStatusUpdateFrequency의 N배여야 하고 HTTP2 ping·read idle 타임아웃의 합보다 커야 한다고 적혀 있어요. v1.37.2 소스 주석에 따르면 그 합은 30초 + 15초예요.

💡 실무에서는: 짧게 줄이기 전에 따져 볼 것
• tolerationSeconds를 너무 짧게 주면 잠깐의 네트워크 끊김에도 파드가 지워지고 새로 만들어져요. 옮기는 비용이 큰 파드(캐시를 데우는 데 오래 걸리는 파드 등)는 오히려 길게 두는 편이 나을 수 있어요. 문서 예시는 6000초예요
• Service 트래픽에서는 4절에서 본 대로 Unknown 시점(약 50초)에 이미 그 파드가 빠져요. 사용자 요청이 걱정이라면 축출 시간보다 이 시간과 다른 노드에 남은 레플리카 수를 먼저 봐야 해요
• 노드 점검 일정을 미리 안다면 장애를 기다리지 말고 cordon과 drain으로 파드를 옮겨요

cordon: 사람이 Node 객체를 고치는 일

지금까지는 kubelet과 컨트롤러가 Node 객체를 고쳤어요. 사람이 고치는 대표적인 명령이 cordon이에요. worker3에 cordon과 uncordon을 해 봤어요.

15:41:08 mac$ kubectl cordon k8s-worker3 spec.unschedulable=true taints=node.kubernetes.io/unschedulable:NoSchedule k8s-worker3 Ready,SchedulingDisabled 15:41:08 mac$ kubectl uncordon k8s-worker3 spec.unschedulable= taints=

→ cordon하자 Node 객체의 spec.unschedulable이 true로 바뀌었고 node.kubernetes.io/unschedulable:NoSchedule taint가 따라붙었어요. uncordon하니 둘 다 사라졌어요.

제가 바꾼 것은 spec 한 칸인데 taint는 누가 붙였을까요? v1.37.2 node_lifecycle_controller.go에 node.Spec.Unschedulable이면 unschedulable taint를 붙이는 코드가 있어요. 여기서도 node-lifecycle-controller가 일했어요. STATUS 열의 SchedulingDisabled는 조건이 아니에요. Node Status 문서의 메모에 따르면 "SchedulingDisabled is not a Condition in the Kubernetes API"이고 kubectl이 spec.unschedulable을 보고 덧붙여 보여 주는 표시예요. Nodes 문서에는 cordon이 "prevents the scheduler from placing new pods onto that Node but does not affect existing Pods"라고 적혀 있어요. 새 파드만 막고 이미 있는 파드는 그대로 둔다는 뜻이고 이미 있는 파드를 옮기려면 drain을 따로 해야 해요.

✍️ 오늘의 요약
노드도 API 객체라서 kubelet이 Lease와 status에 하트비트를 적고 KCM의 node-lifecycle-controller가 그 기록을 보고 노드의 생사를 판단해요.

Lease는 10초마다 갱신되고 Node status는 바뀔 때나 5분(±2분 30초 무작위)마다만 갱신돼서 lastHeartbeatTime이 7분 넘게 그대로인 것도 정상이었어요. node-lifecycle-controller는 5초마다 확인해 50초 동안 소식이 없으면 Ready를 Unknown으로 바꾸고 unreachable taint를 붙이고 파드를 NotReady로 표시해요. 실험에서는 kubelet을 멈추고 41초와 52초 사이에 Unknown이 됐고 그 뒤 EndpointSlice에서 파드가 빠졌지만 컨테이너는 계속 돌아 파드 IP로는 165초 내내 200 응답이 왔어요. 파드를 다른 노드로 옮기는 축출은 어드미션이 붙인 기본 toleration 300초가 지난 뒤예요. kubelet을 29분 멈춘 실험에서는 taint가 붙고 정확히 300초 뒤 새 파드 두 개가 worker1·worker2에 생겼어요. kubelet을 멈춘 때부터 5분 45초 뒤였어요. 옛 파드는 kubelet이 없어 Terminating으로 남았고 강제로 지워도 노드의 컨테이너는 kubelet이 돌아온 뒤에야 정리됐어요. 알아채는 것과 옮기는 것은 다른 단계이고 둘 사이의 300초는 파드마다 정할 수 있어요.
