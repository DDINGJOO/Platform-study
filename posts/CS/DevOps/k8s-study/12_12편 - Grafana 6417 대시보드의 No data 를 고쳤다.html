12편. Grafana 6417 대시보드의 No data 를 고쳤다 ← 지금 이 글

강의에서 Grafana 대시보드 번호 하나가 나왔어요. "그라파나 6417 번을 애용한대." 11편에서 Prometheus 가 노드 네 대의 node-exporter 와 kube-state-metrics 를 모두 긁고 있는 것까지 확인해 둔 참이라, 남은 일은 화면을 띄우는 것뿐이었어요. Grafana 의 가져오기 화면에 6417 을 넣고 Import 를 눌렀습니다.

맨 윗줄 네 칸이 모두 N/A 였어요. 클러스터 전체의 파드·CPU·메모리·디스크 사용률을 보여 줄 칸이에요. 바로 아래 CPU·메모리·디스크 용량 그래프 세 개에는 No data 가 떠 있었고, 아래로 내려가도 컨테이너 재시작 수, CPU·메모리 요청량, Job 세 칸이 N/A 였어요. 노드 수 4, 실행 중인 파드 23, Deployment 레플리카 7 은 제대로 나왔습니다. 수집은 돌고 있고 Grafana 는 Prometheus 에 붙어 있는데, 패널 29개 가운데 11개가 N/A, 3개가 No data 였고 1개는 선 세 개 중 하나만 그렸어요.

패널의 수식을 열어 보니 문제는 이름이었어요. 6417 이 마지막으로 고쳐진 날은 2018년 6월 6일이고, 패널이 찾는 메트릭 이름 25개 가운데 14개가 지금 우리 Prometheus 에는 없었습니다. 이 글의 질문은 "가져온 대시보드가 N/A 를 보여 줄 때, 그것은 무엇이 없다는 뜻이고 어디까지 고쳐야 하는가"예요.

이 글에서 다룰 것
· 6417 은 어떤 대시보드이고, 가져오기 전에 Grafana 에 무엇을 연결해야 할까?
· 화면의 N/A 와 No data 는 0 과 무엇이 다를까?
· 패널이 찾는 메트릭 25개 중 14개는 언제, 왜 사라졌을까?
· 수식 18개를 고친 뒤 채워진 숫자는 믿어도 될까?
· 끝까지 N/A 로 남은 Jobs 패널은 고쳐야 할까?

1. 6417 은 2018년 6월에 마지막으로 고친 대시보드다

먼저 6417 이 무엇인지 grafana.com 의 API 로 확인했어요.

mac$ curl -s https://grafana.com/api/dashboards/6417 | jq -r '"\(.id) \(.name) revision=\(.revision) updated=\(.updatedAt)"' 6417 Kubernetes Cluster (Prometheus) revision=1 updated=2018-06-06T23:51:56.000Z

→ 6417 번 대시보드의 이름은 Kubernetes Cluster (Prometheus) 이고, 판(revision)은 1 하나뿐이며, 마지막으로 갱신된 때가 2018년 6월 6일 23시 51분(UTC)이라는 뜻이에요.

강의 저장소(github.com/brayanlee/k8s-prometheus)의 grafana 폴더에 들어 있던 kubernetes-cluster-prometheus_rev1.json 이 바로 이 대시보드예요. 파일 안의 gnetId 가 6417 이고, uid 4XuMd2Iiz 는 뒤에서 볼 가져오기 화면의 값과 같아요. 11편에서 kubectl apply -f grafana/ 가 "apiVersion not set, kind not set" 에러를 낸 파일도 이것이에요. 쿠버네티스 매니페스트가 아니라 Grafana 에 넣는 대시보드 정의라서 kubectl 은 읽을 수 없었어요.

📖 용어: 대시보드 JSON 과 uid
Grafana 대시보드 하나를 통째로 적은 JSON 파일이에요. 패널 배치, 패널마다 보낼 PromQL 수식, 값을 화면에 어떻게 표시할지가 모두 들어 있어요. grafana.com 에 올라간 대시보드는 번호를 받고, 파일의 gnetId 에 그 번호가 남아요. uid 는 Grafana 안에서 대시보드를 구분하는 값이라서, 원본과 고친 판을 함께 두려면 uid 를 다르게 줘야 해요.

파일 앞부분의 __requires 를 보면 이 JSON 은 Grafana 4.6.2 에서 만들어졌고, 패널 종류는 singlestat(숫자 하나를 크게 보여 주는 패널), graph, table 이에요. 행 구분 6개를 빼면 패널은 29개이고, 거기 적힌 PromQL 수식은 36개입니다. 우리 Grafana 는 13.3.0 이에요.

가져온 뒤 Grafana API 로 대시보드를 다시 꺼내 보니 schemaVersion 이 16 에서 42 로 올라가 있었고, singlestat 24개는 stat 으로, graph 4개는 timeseries 로 바뀌어 있었어요. 화면 형식은 Grafana 가 새 버전에 맞게 옮겨 준 거예요. 그런데 수식 36개는 원본과 한 글자도 다르지 않았어요. Grafana 는 2018년의 패널 형식은 옮겨 줬지만, 2018년의 메트릭 이름까지 고쳐 주지는 않았어요.

2. 대시보드보다 데이터 소스가 먼저다

대시보드를 가져오기 전에 Grafana 가 수식을 보낼 곳을 등록해야 했어요. 강의 저장소의 Grafana 매니페스트에는 데이터 소스 설정이 들어 있지 않아서, Grafana 화면의 Connections > Data sources 에서 Prometheus 를 하나 추가했어요.

📖 용어: 데이터 소스 (data source)
Grafana 가 수식을 보내 값을 받아 오는 대상이에요. 이 구성에서 메트릭은 Prometheus 에 쌓이고, Grafana 는 패널마다 적힌 PromQL 수식을 데이터 소스로 등록한 Prometheus 에 보내 돌아온 결과를 그려요. 데이터 소스가 없으면 대시보드를 가져와도 수식을 보낼 곳이 없어요.
그림 1. 주소는 Mac 에서 닿는 주소가 아니라 클러스터 안의 Service 이름으로 적었다

주소는 http://prometheus-service.monitoring.svc:8080 으로 적었어요. monitoring 네임스페이스에 있는 prometheus-service 라는 Service 의 8080 포트라는 뜻이고, 11편에서 만든 Service 예요. 이 이름은 클러스터 안의 DNS 에서만 풀려요. Mac 의 브라우저는 이 주소를 알지 못하는데도 아래 테스트는 성공했어요. 그러니 질의를 보낸 쪽은 브라우저가 아니라 클러스터 안에서 도는 Grafana 파드예요. 인증 방식은 No Authentication 으로 두었어요. 11편에서 본 대로 이 Prometheus 에는 인증이 없습니다.

그림 2. Save & test 의 성공은 Grafana 파드가 그 주소의 Prometheus 에 닿았다는 뜻이다

나머지 칸은 기본값 그대로 두고 맨 아래 Save & test 를 눌렀어요. Grafana 가 이 주소로 질의를 한 번 보내 보는 단추예요. 초록 상자의 "Successfully queried the Prometheus API." 는 그 질의가 성공했다는 뜻입니다.

두 화면 오른쪽 위에 Sign in 이 보이는 것은 로그인하지 않은 상태라는 뜻이에요. 강의 매니페스트가 익명 사용자에게 Admin 권한을 주도록 되어 있어서(GF_AUTH_ANONYMOUS_ORG_ROLE=Admin) 로그인 없이 데이터 소스까지 만들 수 있었어요. 이 Mac 안에서만 닿는 실습 주소라 그대로 두었지만, 이 설정의 위험은 11편의 보안 메모에서 따로 다뤘어요. 데이터 소스 테스트가 알려 주는 것은 Grafana 와 Prometheus 가 연결됐다는 사실까지예요. 대시보드의 수식이 맞는지는 이 단계에서 알 수 없어요.

3. ID 로 가져오자 N/A 가 열한 칸이었다

가져오기 화면(주소 /dashboard/import)의 입력칸에 6417 을 넣고 Load 를 누르면 Grafana 가 grafana.com 에서 JSON 을 받아 와요.

그림 3. API 의 2018-06-06T23:51:56Z 가 한국 시각 2018-06-07 08:51:56 으로 보인다

갱신 시각은 2018-06-07 08:51:56 으로 나왔어요. API 가 돌려준 2018-06-06T23:51:56Z 를 한국 시각(UTC+9)으로 바꾼 값이에요. UID 칸의 4XuMd2Iiz 는 강의 저장소 JSON 의 uid 와 같아요. 맨 아래 DS_PROMETHEUS 는 이 대시보드가 쓸 Prometheus 데이터 소스를 고르는 칸이에요. JSON 의 __inputs 에 이 이름의 입력이 적혀 있고, 패널 29개의 datasource 값이 모두 ${DS_PROMETHEUS} 라서 여기서 고른 데이터 소스가 모든 패널에 들어가요. 2절에서 만든 prometheus 를 고르고 Import 를 눌렀어요.

그림 4. 사용률 네 칸은 N/A, 용량 그래프 세 개는 No data, 노드 수 4 는 정상
그림 5. 파드·컨테이너 수는 나오고, 재시작·요청량·Job 칸은 N/A

위쪽 화면부터 보면 Cluster Pod Usage·CPU Usage·Memory Usage·Disk Usage 네 칸이 N/A 예요. Cluster CPU·Mem·Disk Capacity 그래프는 No data 이고, Cluster Pod Capacity 그래프는 allocatable·capacity·requested 세 선 가운데 requested 하나만 22 에서 23 으로 올라가 있어요. Deployment 줄은 값이 나왔고, Node 줄은 Number Of Nodes 4, Nodes Out of Disk N/A, Nodes Unavailable 0 이었어요. 아래쪽 화면에서는 Pods Running 23, Pending·Failed·Succeeded·Unknown 0, Containers Running 23, Waiting 0, Terminated 0 이 나왔고, Containers Restarts, CPU Cores Requested, Memory Requested, 그리고 Jobs 줄 세 칸이 N/A 였어요.

📖 용어: capacity 와 allocatable
노드 자원을 세는 두 값이에요. kubernetes.io 의 Node Status 문서는 capacity 를 노드가 가진 자원의 전체 양으로, allocatable 을 그중 일반 파드가 쓸 수 있는 양으로 설명해요. 스케줄러는 allocatable 을 파드에 내줄 수 있는 용량으로 보고 그 이상을 배치하지 않아요. 6417 의 용량 그래프는 이 두 값과 파드가 요청한 양(requested)을 한 칸에 겹쳐 그려요.

N/A 와 No data 는 0 이 아니다

N/A 라는 글자는 Grafana 가 지어낸 말이 아니라 이 JSON 이 정한 표시예요. singlestat 패널마다 "값이 null 이면 N/A 라고 쓴다"는 규칙이 들어 있어요. 아래는 Nodes Out of Disk 패널의 일부예요.

# 6417 원본 JSON 의 "Nodes Out of Disk" 패널 중 일부 (줄바꿈만 줄였다) "colorBackground": true, "colors": ["#299c46", "rgba(237, 129, 40, 0.89)", "#d44a3a"], "thresholds": "1", "valueMaps": [ { "op": "=", "text": "N/A", "value": "null" } ], "valueName": "current", "targets": [ { "expr": "sum(kube_node_status_condition{condition=\"OutOfDisk\", node=~\"$node\", status=\"true\"})" } ]

→ 수식 결과가 비어 값이 없으면(null) 숫자 대신 N/A 라고 쓰고, 값은 화면 범위 안의 마지막 값(current)을 보여 주며, 임계값 1 을 기준으로 배경색을 바꾸라는 뜻이에요.

그래프 패널의 No data 도 같은 상황이에요. 수식이 시계열을 하나도 돌려주지 않았다는 뜻이에요. 0 은 Prometheus 가 그 시계열을 가지고 있고 값이 0 이라는 뜻이고, N/A 는 물어본 이름의 시계열이 한 개도 없다는 뜻이에요. 같은 sum() 수식인데 Nodes Unavailable 은 0, Cluster CPU Usage 는 N/A 가 나온 차이가 여기서 생겨요.

그림 6. 0 은 측정한 값이고, N/A 는 물어본 이름으로 받아 온 것이 없다는 표시다
⚠️ 주의: N/A 인데 배경은 초록이었어요
Nodes Out of Disk 패널은 colorBackground 가 켜져 있고 임계값은 1 하나예요. 색 목록의 첫 번째가 초록(#299c46)이라 1 미만이면 초록 배경이 됩니다. 그런데 값이 없는 N/A 도 화면에서는 초록 배경으로 나왔어요(그림 4). 한눈에 보면 "디스크가 찬 노드 없음"으로 읽히지만, 실제로는 그 조건을 하나도 받아 오지 못한 상태였어요. 색이 붙은 칸은 색보다 글자를 먼저 읽어야 해요.

값이 나온 칸에도 읽는 법이 필요했어요. Deployment Replicas - Unavailable 은 0.150 이었어요. 준비되지 않은 레플리카 수가 소수일 수는 없어요. JSON 을 보면 이 패널은 valueName 이 avg 라서 화면 범위(Last 30 minutes) 동안의 평균을 보여 줘요. 그 30분 안에 준비되지 않은 레플리카가 있던 구간이 평균에 섞여 0.150 이 된 거예요. 뒤에서 볼 수정판 화면에서는 같은 칸이 0.120 이었어요. 화면을 연 시각이 달라 30분 범위가 달라졌기 때문이에요. Deployment Replicas 와 Number Of Nodes 도 avg 를 써요. 평균이 아무도 겪지 않은 값을 만드는 문제는 집계와 분포 1편에서 다뤘어요. 이 대시보드에서 숫자 한 칸을 읽으려면 수식과 함께 valueName 과 valueMaps 까지 봐야 했어요.

4. 패널이 찾는 메트릭 25개 중 14개가 없었다

N/A 칸의 수식을 하나씩 보면 공통점이 있었어요. 그래서 JSON 에서 수식 36개를 모두 꺼내 메트릭 이름 25개를 추리고, 이름마다 우리 Prometheus 에 시계열이 몇 개 있는지 셌어요. count({__name__="이름"}) 으로 물으면 그 이름의 시계열 개수가 나오고, 하나도 없으면 결과가 비어요(아래 화면에서는 0 으로 적었어요).

그림 7. 6417 이 찾는 이름은 모두 0개였고, 바뀐 이름에는 시계열이 있었다

위쪽 12줄이 6417 이 찾는 이름이고 모두 0 이었어요. 아래쪽 6줄은 지금 쓰는 이름이에요. kube_node_status_allocatable 과 kube_node_status_capacity 가 각각 32개, kube_pod_container_resource_requests 가 13개, kube_pod_container_status_restarts_total 이 23개, node_filesystem_free_bytes 와 node_filesystem_size_bytes 가 각각 16개 있었어요. 화면에는 Job 메트릭을 kube_job_status_succeeded 하나만 넣었는데, kube_job_status_active 와 kube_job_status_failed 도 같은 이유로 없었어요.

없던 14개는 사라진 이유에 따라 세 갈래로 나뉘어요. kube-state-metrics 가 바꾼 이름 9개, node_exporter 가 바꾼 이름 2개, 그리고 이름은 지금도 맞는데 Job 이 없어서 시계열이 없던 3개예요. 나머지 11개(kube_pod_info, kube_node_info, kube_pod_status_phase, kube_deployment_status_replicas 등)는 이름이 그대로라 패널이 정상으로 나왔어요.

📖 용어: kube-state-metrics
쿠버네티스 API 서버에 있는 오브젝트(노드, 파드, Deployment, Job 등)의 상태를 읽어 Prometheus 메트릭으로 내놓는 프로그램이에요. 노드의 할당 가능 CPU, 파드가 요청한 메모리, Job 의 성공 수 같은 값이 여기서 나와요. 6417 의 메트릭 25개 중 23개가 이 프로그램의 메트릭이고, 나머지 2개는 노드의 디스크를 재는 node_exporter 의 메트릭이에요.

이름 여덟 개는 kube-state-metrics v2 가 지웠다

kube-state-metrics 의 CHANGELOG 에서 v2.0.0-alpha(2020-09-16) 항목을 보면 "v2: Remove deprecated stable metrics" 라는 줄 아래에 지운 이름이 나열돼 있어요. 6417 이 쓰는 노드 할당량·용량 이름 6개와 파드 요청량 이름 2개가 모두 그 목록에 있어요. 같은 항목에 대신 쓸 메트릭도 적혀 있어요. 노드 쪽은 kube_node_status_capacity 와 kube_node_status_allocatable, 파드 쪽은 kube_pod_container_resource_requests 이고, 자원 이름은 resource 라벨로, 단위는 unit 라벨로 나타낸다고 해요. 정식 v2.0.0 은 2021-04-13 에 나왔어요.

# kube-state-metrics v2.0.0-alpha (2020-09-16) 에서 지운 이름 → 대신 쓰는 이름 kube_node_status_allocatable_cpu_cores → kube_node_status_allocatable{resource="cpu"} kube_node_status_allocatable_memory_bytes → kube_node_status_allocatable{resource="memory"} kube_node_status_allocatable_pods → kube_node_status_allocatable{resource="pods"} kube_node_status_capacity_cpu_cores → kube_node_status_capacity{resource="cpu"} kube_node_status_capacity_memory_bytes → kube_node_status_capacity{resource="memory"} kube_node_status_capacity_pods → kube_node_status_capacity{resource="pods"} kube_pod_container_resource_requests_cpu_cores → kube_pod_container_resource_requests{resource="cpu"} kube_pod_container_resource_requests_memory_bytes → kube_pod_container_resource_requests{resource="memory"} # kube-state-metrics 문서 기준 v1.1.0 → v1.2.0 (2018-01-15) 사이에 바뀐 이름 kube_pod_container_status_restarts → kube_pod_container_status_restarts_total # node_exporter 0.16.0 (2018-05-15) 에서 바뀐 이름 node_filesystem_free → node_filesystem_free_bytes node_filesystem_size → node_filesystem_size_bytes

→ 이름 끝에 붙어 있던 자원 이름(_cpu_cores, _memory_bytes, _pods)이 라벨로 옮겨 갔고, 재시작 수와 디스크 이름에는 접미사가 붙었다는 뜻이에요.

📖 용어: 시계열과 라벨 (time series, label)
Prometheus 는 메트릭 이름과 라벨 묶음이 같은 값의 흐름 하나를 시계열 하나로 다뤄요. 라벨은 {resource="cpu", node="k8s-worker1"} 같은 키와 값의 쌍이에요. v2 의 kube_node_status_allocatable 은 이름 하나에 resource 라벨로 CPU, 메모리, 파드 수 등을 나눠 담아요. 그래서 이름만 맞히면 끝나지 않고 라벨까지 골라야 원하는 값이 나와요.

새 이름이 v2 에서 처음 생긴 것은 아니에요. 파드 쪽 kube_pod_container_resource_requests 는 CHANGELOG 의 v1.4.0 첫 후보판(v1.4.0-rc.0, 2018-08-06) 항목에 "Add generic resource metrics for Pods" 로 들어왔고, 같은 줄에 옛 이름이 deprecated 가 된다고 적혀 있어요. 6417 이 마지막으로 갱신되고 두 달 뒤의 일이에요. v1.8.0 문서의 노드 메트릭 표에는 kube_node_status_allocatable 과 kube_node_status_allocatable_cpu_cores 가 나란히 있고, 옛 이름에는 DEPRECATED 가 붙어 있어요. 한동안은 두 이름이 함께 나오다가 v2 에서 옛 이름이 빠진 거예요.

그러니 이 여덟 칸이 비게 된 직접적인 계기는 우리 쪽에 있어요. 강의 저장소는 kube-state-metrics v1.8.0-rc.1 이미지를 썼는데, 11편에서 이 이미지가 amd64 전용이라 공식 v2.20.0 으로 바꿨어요. v1.8.0 문서대로라면 옛 이름이 아직 나오던 버전이에요. 우리 노드는 arm64 라 그 이미지를 직접 돌려 보지는 않았어요. 강의 저장소에서는 JSON 과 kube-state-metrics 가 같은 시절의 이름을 쓰고 있었고, 그중 kube-state-metrics 만 바꾸자 여덟 칸이 비었어요.

restarts 는 대시보드보다 먼저 바뀌어 있었다

kube_pod_container_status_restarts 는 사정이 달라요. kube-state-metrics CHANGELOG 에는 이 이름이 바뀌었다는 항목이 없어요. 대신 태그마다 들어 있는 메트릭 문서를 비교하면 v1.1.0(2017-10-19) 문서에는 kube_pod_container_status_restarts 가, v1.2.0(2018-01-15) 문서에는 kube_pod_container_status_restarts_total 이 적혀 있어요. 6417 이 마지막으로 갱신되기 다섯 달 전이에요. v1.8.0 문서에도 _total 쪽만 있어서, 강의 저장소의 원래 kube-state-metrics 로 돌렸더라도 이 칸은 N/A 였을 가능성이 커요.

디스크 두 개는 node_exporter 0.16 에서 _bytes 가 붙었다

node_exporter CHANGELOG 의 0.16.0(2018-05-15) 항목은 "Breaking changes" 로 시작해요. 지금의 이름 규칙에 맞추느라 많은 메트릭의 이름과 라벨이 바뀌었다고 적었고, 많은 카운터 이름에 _total 을 붙였으며, 기본 단위를 이름에 넣었다고 해요. 예로 든 것이 node_cpu 가 node_cpu_seconds_total 이 된 경우예요. 함께 올린 업그레이드 안내는 옛 이름을 새 이름으로 옮겨 주는 recording rule 예시 파일을 링크하는데, 그 파일에 node_filesystem_free 를 node_filesystem_free_bytes 로, node_filesystem_size 를 node_filesystem_size_bytes 로 옮기는 규칙이 있어요.

0.16.0 은 6417 이 마지막으로 갱신되기 3주 전에 나왔어요. 6417 은 마지막으로 고친 날에도 디스크 칸에 0.16 이전 이름을 쓰고 있었던 거예요. 11편의 node-exporter 는 이미지 태그를 적지 않아 latest 를 받았으니, 우리 Prometheus 에는 _bytes 가 붙은 이름만 있었어요.

그림 8. 6417 이 고정한 이름 중 셋은 갱신하던 날 이미 바뀌어 있었고, 나머지는 그 뒤에 바뀌었다

Job 세 개는 이름 문제가 아니었다

마지막 세 개(kube_job_status_succeeded·active·failed)는 지금도 쓰는 이름이에요. 이 클러스터에 Job 이 하나도 없어서 시계열이 없었을 뿐이에요. 이 셋은 고칠 대상인지부터 따져야 해서 7절에서 따로 다뤄요.

💡 실무에서는: 가져오기 전에 이름부터 세 봐요
공개 대시보드를 가져올 때는 JSON 의 수식에서 메트릭 이름을 뽑아 우리 Prometheus 에 있는지 먼저 세 보세요. jq -r '.. | .expr? // empty' 로 수식만 꺼내고, 이름마다 count({__name__="..."}) 를 물으면 돼요. grafana.com 의 갱신 날짜와 우리가 쓰는 exporter 버전을 나란히 놓는 것도 도움이 됩니다. 갱신일이 kube-state-metrics v2.0.0(2021-04) 이전이면 노드·파드 자원 메트릭 이름을, node_exporter 0.16.0(2018-05) 이전이면 _bytes·_seconds 같은 단위 접미사를 먼저 의심할 수 있어요.

5. 수식 18개와 제목 2개를 고쳤다

원본 파일은 그대로 두고 사본 kubernetes-cluster-prometheus_rev1_k8s-lab.json 을 만들어 고쳤어요. uid 는 k8s-lab-6417 로, 제목은 "Kubernetes Cluster (Prometheus) · k8s-lab 수정판" 으로 바꿨어요. uid 가 다르니 원본과 수정판을 Grafana 에 함께 두고 비교할 수 있어요. 수식 36개 중 18개를 고쳤고, 패널 제목 두 개를 바꿨어요. 두 파일의 수식만 꺼내 비교하면 이래요(앞 12줄).

mac$ cd ~/k8s-playground/shared/k8s-prometheus/grafana && diff <(jq -r '.. | .expr? // empty' kubernetes-cluster-prometheus_rev1.json) <(jq -r '.. | .expr? // empty' kubernetes-cluster-prometheus_rev1_k8s-lab.json) | grep '^[<>]' | head -12 < sum(kube_pod_info{node=~"$node"}) / sum(kube_node_status_allocatable_pods{node=~".*"}) < sum(kube_pod_container_resource_requests_cpu_cores{node=~"$node"}) / sum(kube_node_status_allocatable_cpu_cores{node=~"$node"}) < sum(kube_pod_container_resource_requests_memory_bytes{node=~"$node"}) / sum(kube_node_status_allocatable_memory_bytes{node=~"$node"}) < (sum (node_filesystem_size{nodename=~"$node"}) - sum (node_filesystem_free{nodename=~"$node"})) / sum (node_filesystem_size{nodename=~"$node"}) < sum(kube_node_status_allocatable_pods{node=~"$node"}) < sum(kube_node_status_capacity_pods{node=~"$node"}) > sum(kube_pod_info{node=~"$node"}) / sum(kube_node_status_allocatable{resource="pods",node=~".*"}) > sum(kube_pod_container_resource_requests{resource="cpu",node=~"$node"}) / sum(kube_node_status_allocatable{resource="cpu",node=~"$node"}) > sum(kube_pod_container_resource_requests{resource="memory",node=~"$node"}) / sum(kube_node_status_allocatable{resource="memory",node=~"$node"}) > (sum (node_filesystem_size_bytes{nodename=~"$node"}) - sum (node_filesystem_free_bytes{nodename=~"$node"})) / sum (node_filesystem_size_bytes{nodename=~"$node"}) > sum(kube_node_status_allocatable{resource="pods",node=~"$node"}) > sum(kube_node_status_capacity{resource="pods",node=~"$node"})

→ < 로 시작하는 줄이 원본, > 로 시작하는 줄이 수정판이에요. 위쪽 네 줄은 사용률 네 칸, 마지막 두 줄은 Cluster Pod Capacity 그래프의 수식이고, 수식의 모양은 그대로 둔 채 메트릭 이름과 라벨만 바뀌었다는 뜻이에요.

고친 방식은 하나예요. 이름 끝의 _pods·_cpu_cores·_memory_bytes 를 떼고, 그 자리를 resource="pods"·resource="cpu"·resource="memory" 라벨로 옮겼어요. 디스크 이름 뒤에는 _bytes 를, 재시작 수 뒤에는 _total 을 붙였어요. 18개를 세면 사용률 네 칸 4개, 용량 그래프 네 개의 수식 10개, 재시작·CPU 요청·메모리 요청 칸 3개, 그리고 뒤에서 볼 디스크 조건 칸 1개예요. 원본 Cluster Pod Usage 의 분모가 node=~".*" 로 적혀 있는 것은 그대로 두었어요. 수식의 뜻은 바꾸지 않고 이름만 옮기는 것이 이번 수정의 범위였어요.

이름만 바꾸고 라벨을 빼먹으면 어떻게 되는지는 글을 쓰며 확인해 봤어요. 먼저 kube_node_status_allocatable 의 resource 라벨에 어떤 값이 있는지 셌어요.

mac$ curl -s http://192.168.64.3:30003/api/v1/query --data-urlencode 'query=count by (resource) (kube_node_status_allocatable)' | jq -r '.data.result[] | [.metric.resource, .value[1]] | @tsv' hugepages_64Ki 4 memory 4 pods 4 cpu 4 ephemeral_storage 4 hugepages_1Gi 4 hugepages_2Mi 4 hugepages_32Mi 4

→ 노드마다 resource 값이 여덟 가지이고 노드가 4대라 시계열이 32개라는 뜻이에요. 그림 7 의 32 와 같은 숫자예요.

⚠️ 주의: 라벨을 빼먹으면 N/A 가 아니라 틀린 숫자가 나와요
sum(kube_node_status_allocatable) 은 CPU 코어 수, 메모리 바이트, 파드 수, 임시 저장소 바이트, hugepages 를 한데 더해요. CPU 사용률 수식에서 resource 라벨을 분자와 분모 모두 빼고 돌려 보니 약 0.002025 가 나왔어요(원자료 12-recheck.txt). 화면에는 0.203% 로 보였을 값이에요. 에러도 N/A 도 없이 그럴듯한 작은 숫자가 나오기 때문에, 이름이 틀렸을 때보다 알아차리기 어려워요. 라벨로 나뉜 메트릭으로 옮길 때는 이름과 함께 라벨까지 적어야 해요.

OutOfDisk 는 이름이 아니라 조건 값이 사라졌다

Nodes Out of Disk 칸은 그림 7 의 목록에 걸리지 않았어요. 수식이 쓰는 kube_node_status_condition 은 지금도 있는 이름이에요. 문제는 라벨 값이었어요. 수식은 condition="OutOfDisk" 이고 status="true" 인 시계열을 세는데, OutOfDisk 라는 조건 자체가 없었어요.

📖 용어: 노드 조건 (node condition)
kubelet 이 노드 상태를 API 서버에 보고할 때 쓰는 항목이에요. Ready, DiskPressure, MemoryPressure 같은 이름마다 True·False·Unknown 중 하나가 붙어요. kube-state-metrics 는 이것을 kube_node_status_condition 하나로 내놓고, 조건 이름은 condition 라벨에, 상태는 status 라벨에 담아요.
mac$ curl -s http://192.168.64.3:30003/api/v1/query --data-urlencode 'query=count by (condition) (kube_node_status_condition)' | jq -r '.data.result[] | [.metric.condition, .value[1]] | @tsv' NetworkUnavailable 12 MemoryPressure 12 DiskPressure 12 PIDPressure 12 Ready 12 mac$ curl -s http://192.168.64.3:30003/api/v1/query --data-urlencode 'query=kube_node_status_condition{condition="OutOfDisk"}' | jq '.data.result | length' 0

→ 우리 노드가 보고하는 조건은 다섯 가지이고, 조건마다 노드 4대 × 상태 3가지(true·false·unknown)라 시계열이 12개씩이라는 뜻이에요. OutOfDisk 인 시계열은 0개예요. 글을 쓰며 2026-11-09 21:08 에 조회한 결과예요.

kubernetes.io 의 Node Status 문서도 노드 조건의 예로 Ready, DiskPressure, MemoryPressure, PIDPressure, NetworkUnavailable 다섯 가지를 들어요. OutOfDisk 가 빠진 시점은 쿠버네티스 CHANGELOG 에 있어요. v1.14.0(2019-03-25) 항목에 "Removed stale OutOfDisk condition from kubelet side" 가 있고, 같은 변경(#72507)이 v1.13.4(2019-02-28)에도 들어갔어요. 6417 이 갱신될 때 있던 조건을 이 클러스터(v1.37.2)의 kubelet 은 보고하지 않아요.

그래서 이 칸은 DiskPressure 를 세도록 바꾸고, 제목을 "Nodes Disk Pressure (원래 Out of Disk)" 로 고쳤어요. 제목에 원래 이름을 남긴 이유는 두 조건의 뜻이 같지 않아서예요. 노드 압박 축출 문서에 따르면 kubelet 은 노드의 루트·이미지·컨테이너 파일시스템의 남은 공간이나 inode 가 축출 기준에 닿으면 DiskPressure 를 켜요. 기본 축출 기준에는 nodefs.available<10%, imagefs.available<15% 가 있어요. 디스크가 다 찼다는 뜻이 아니라, kubelet 이 파드를 내보내기 시작할 기준에 닿았다는 뜻이에요. 이름이 있다고 끝이 아니었어요. 라벨에 들어가는 값도 그 시절의 값이었어요.

고친 파일은 가져오기 화면에서 JSON 파일을 올리는 방식으로 넣었어요. 데이터 소스는 같은 prometheus 를 골랐어요.

6. 채워진 숫자도 손으로 다시 계산했다

그림 9. 이름을 고치자 사용률 네 칸과 용량 그래프 네 개가 채워졌다
그림 10. 재시작 0, CPU 요청 1.85, 메모리 요청 252 MB. Jobs 세 칸만 N/A 로 남았다

수정판에서는 위쪽 네 칸이 Pod 5.23%, CPU 23.1%, Memory 1.58%, Disk 21.9% 로 채워졌어요. 용량 그래프 네 개에도 선이 모두 그려졌고, Nodes Disk Pressure 는 0, Containers Restarts 는 0, CPU Cores Requested 는 1.85, Memory Requested 는 252 MB 였어요. 원본에서 N/A 였던 11칸 중 8칸이 숫자로 바뀌었고, 남은 3칸은 Jobs 줄이에요.

값이 채워졌다고 맞는 값이라는 보장은 없어서, 수식에 들어간 값을 Prometheus 에 직접 물어 다시 계산했어요.

# 글을 쓰며 다시 조회 (2026-11-09 21:08). 큰 숫자는 읽기 쉽게 세 자리마다 쉼표를 넣었다 sum(kube_node_status_allocatable{resource="pods"}) 440 sum(kube_node_status_allocatable{resource="cpu"}) 8 sum(kube_pod_container_resource_requests{resource="cpu"}) 1.85 sum(kube_node_status_allocatable{resource="memory"}) 15,958,106,112 sum(kube_pod_container_resource_requests{resource="memory"}) 251,658,240 sum(kube_node_status_capacity{resource="cpu"}) 8 sum(kube_node_status_capacity{resource="memory"}) 16,377,536,512

→ 노드 4대를 합쳐 할당 가능한 파드는 440개, CPU 는 8코어이고 그중 1.85코어가 요청돼 있으며, 할당 가능한 메모리 15,958,106,112 바이트 중 251,658,240 바이트가 요청돼 있다는 뜻이에요. 마지막 두 줄은 capacity 예요.

계산해 보면 이래요. 파드 사용률은 화면을 찍을 때의 파드 23개(Pods Running 23)를 할당 가능 파드 440 으로 나눈 값이라 5.227…% 이고, 화면의 5.23% 와 맞아요. 440 은 노드 4대 × 110 이에요. kubelet 설정 문서에 maxPods 기본값이 110 으로 적혀 있어요. CPU 사용률은 요청 1.85 코어를 할당 가능 8 코어로 나눈 23.125% 라서 23.1% 와 맞아요. 메모리는 251,658,240 을 15,958,106,112 로 나눈 1.577…% 라서 1.58% 와 맞아요. Memory Requested 칸의 252 MB 는 251,658,240 바이트를 1000 단위로 나눈 값이에요(패널 단위 decbytes). 1024 단위로 나누면 240 MiB 예요.

메모리의 capacity 와 allocatable 차이는 419,430,400 바이트, 곧 400 MiB 이고 노드당 100 MiB 예요. 노드 압박 축출 문서가 적은 kubelet 의 기본 축출 기준 memory.available<100Mi 와 같은 크기예요. 그 문서는 축출용으로 남겨 둔 자원은 파드가 쓸 수 없다고 설명해요.

여기서 "사용률"이라는 제목은 조심해서 읽어야 해요. 이 대시보드의 CPU·메모리 사용률은 실제로 쓰고 있는 양이 아니라, 파드가 요청(requests)한 양을 할당 가능량으로 나눈 값이에요. 수식의 분자가 kube_pod_container_resource_requests 예요. 23.1% 는 "CPU 가 23.1% 바쁘다"가 아니라 "할당 가능 CPU 의 23.1% 가 파드에 예약돼 있다"는 뜻이에요.

디스크 21.9% 는 맞았지만 용량은 세 배로 잡혔다

디스크 칸은 계산이 맞지 않았어요. Cluster Disk Capacity 그래프의 limit 선이 400 GB 눈금 가까이에 있었는데(그림 9), 이 클러스터의 VM 은 3편의 ./lab up 출력 기준으로 디스크가 한 대에 30GiB 이고 네 대예요. node-exporter 가 어떤 파일시스템을 보고 있는지 물어봤어요.

# 글을 쓰며 조회 (2026-11-09 21:05). 큰 숫자는 읽기 쉽게 세 자리마다 쉼표를 넣었다 mac$ curl -s http://192.168.64.3:30003/api/v1/query --data-urlencode 'query=count by (device, fstype, mountpoint) (node_filesystem_size_bytes)' | jq -r '.data.result[] | [.metric.device, .metric.fstype, .metric.mountpoint, .value[1]] | @tsv' /dev/vda1 ext4 /etc/hostname 4 /dev/vda1 ext4 /etc/hosts 4 /dev/vda1 ext4 /etc/resolv.conf 4 tmpfs tmpfs /var/run/secrets/kubernetes.io/serviceaccount 4 mac$ curl -s http://192.168.64.3:30003/api/v1/query --data-urlencode 'query=sum(node_filesystem_size_bytes)' | jq -r '.data.result[0].value[1]' 376,963,424,256 master$ df -B1 --output=source,fstype,size,used / Filesystem Type 1B-blocks Used /dev/vda1 ext4 30,083,776,512 5,797,945,344 worker1$ df -B1 --output=source,fstype,size,used / /dev/vda1 ext4 30,083,776,512 7,814,635,520 worker2$ df -B1 --output=source,fstype,size,used / /dev/vda1 ext4 30,083,776,512 6,313,816,064 worker3$ df -B1 --output=source,fstype,size,used / /dev/vda1 ext4 30,083,776,512 7,745,204,224

→ node-exporter 가 보고한 파일시스템은 노드마다 네 개이고, 그중 세 개(/etc/hostname, /etc/hosts, /etc/resolv.conf)가 같은 /dev/vda1 이라는 뜻이에요. 노드의 루트 디스크는 /dev/vda1 하나이고 크기는 노드마다 30,083,776,512 바이트예요(worker 세 대의 df 머리글 줄은 생략).

/etc/hosts 같은 경로는 노드의 디스크가 아니라 컨테이너 안에 붙은 파일이에요. node-exporter 가 컨테이너 자신의 마운트 목록을 읽었고, 그 파일들이 노드의 /dev/vda1 위에 있으니 같은 디스크가 세 번 잡혔어요. 나머지 하나는 서비스 어카운트 토큰이 들어가는 tmpfs 예요. node_exporter README 는 이 상황을 직접 경고해요. node_exporter 는 호스트를 감시하도록 만들어졌고, 컨테이너로 띄울 때는 컨테이너 자신을 감시하지 않도록 따로 신경 써야 한다고 해요. 그러려면 호스트의 / 를 컨테이너에 바인드 마운트하고 그 경로를 --path.rootfs 로 알려 주라는 예시도 있어요. 강의 저장소의 node-exporter DaemonSet 에는 그런 마운트도 인자도 없어요.

그림 11. 루트 디스크 하나가 bind 마운트 세 개를 통해 세 번 더해졌다

숫자로 보면 이래요. 수식 분모인 sum(node_filesystem_size_bytes) 는 376,963,424,256 바이트예요. vda1 크기가 노드 4대 × 3번, 모두 12번 더해지고 tmpfs 4개가 더해진 값이에요. 실제 루트 디스크 네 개를 더하면 120,335,106,048 바이트라 세 배가 넘어요. 사용률은 사정이 조금 나아요. 분자와 분모에 같은 디스크가 똑같이 세 번씩 더해지니 비율은 거의 유지되고, 거의 비어 있는 tmpfs 가 분모를 조금 키울 뿐이에요. df 로 잰 네 노드의 사용량 합은 27,671,601,152 바이트라 실제 사용률은 23.0% 예요. 대시보드의 사용률 수식을 직접 물어보면 22.2%(21:39) 가 나왔고, 화면의 21.9% 는 같은 수식이 그보다 앞서 낸 값이에요.

이 문제는 이번 수정에서 고치지 않았어요. 메트릭 이름이 아니라 node-exporter 를 띄우는 방식의 문제라서 DaemonSet 에 호스트 마운트를 넣어야 하고, 고친 뒤에는 디스크 칸을 다시 계산해 봐야 해요. N/A 는 없는 값을 없다고 보여 줬지만, 용량 그래프는 세 번 센 값을 아무 표시 없이 그렸어요.

⚠️ 주의: 수정판에 그대로 남겨 둔 원본의 버릇
이번에는 이름만 옮기기로 해서 아래 네 가지는 손대지 않았어요. 수정판을 가져다 쓴다면 같이 알고 있어야 해요.
• Cluster CPU Capacity 의 범례가 뒤바뀌어 있어요. capacity 를 세는 수식에 allocatable, allocatable 을 세는 수식에 capacity 라는 범례가 붙어 있어요. 이 클러스터는 두 값이 모두 8 이라 화면에서 티가 나지 않아요. 메모리 쪽은 두 값이 다르고 범례도 맞게 붙어 있어요.
• Containers Restarts 는 카운터인 재시작 수에 delta() 를 써요. Prometheus 함수 문서는 delta 를 게이지에만 쓰라고 하고, 카운터의 증가량은 리셋을 보정해 주는 increase() 로 구하라고 해요. 또 이 수식은 namespace="kube-system" 으로 고정돼 있어, 제목과 달리 kube-system 의 재시작만 세요.
• 변수 node 와 namespace 는 값이 .* 하나뿐인 constant 라서 화면에서 노드나 네임스페이스를 고를 수 없어요. 디스크 수식이 거는 nodename 라벨은 우리 node-exporter 시계열에 없는데도 디스크 칸이 나왔어요. Prometheus 문서대로 빈 값과 맞는 matcher(=~".*")는 그 라벨이 아예 없는 시계열도 고르기 때문이에요. 노드를 고를 수 있게 바꾸면 이 칸은 비게 돼요.
• Cluster Pod Usage 는 분자를 $node 로, 분모를 .* 로 걸러요. 노드를 고를 수 있게 바꾸면 "그 노드의 파드 수 ÷ 클러스터 전체 할당 가능 파드 수"가 돼요.

7. 끝까지 N/A 였던 Jobs 는 고칠 대상이 아니었다

수정판에서 N/A 로 남은 칸은 Jobs 줄의 세 개뿐이었어요(그림 10). 이 화면을 보고 처음 든 질문은 "이 N/A 도 쿼리를 고쳐야 하나?" 였어요. 수식을 보면 이름은 지금도 쓰는 kube_job_status_succeeded·active·failed 예요. 그렇다면 남은 가능성은 시계열 자체가 없는 경우예요.

📖 용어: Job
한 번 실행하고 끝나는 작업을 위한 쿠버네티스 오브젝트예요. kubernetes.io 문서의 설명대로 Job 은 파드를 하나 이상 만들고, 정해진 수의 파드가 성공적으로 끝날 때까지 실행을 다시 시도해요. 이 클러스터에는 그때까지 Job 이 하나도 없었어요.
그림 12. Job 이 없으면 결과가 0개였고, Job 하나를 끝내자 hello 1 이 나왔다

Job 이 하나도 없을 때 kube_job_status_succeeded 를 물으면 결과가 0개였어요. busybox:1.37 로 echo hi 만 하고 끝나는 Job hello 를 만들고, kubectl wait --for=condition=complete 로 완료될 때까지 기다린 뒤 다시 물으니 job_name 이 hello 이고 값이 1 인 시계열 하나가 나왔어요. kube-state-metrics 는 Job 오브젝트마다 시계열을 만들기 때문에, Job 이 없으면 이 이름의 시계열도 없어요. 더할 시계열이 없으니 패널 수식의 sum() 결과도 비고, 3절의 valueMaps 규칙에 따라 N/A 가 돼요. 이 N/A 는 수식이 틀렸다는 뜻이 아니라, 셀 Job 이 없다는 뜻이었어요.

그림 13. Job 하나를 만들자 Succeeded 1, Active 0, Failed 0. 0 과 N/A 가 같은 칸에서 바뀌었다

Job 하나를 만든 뒤 대시보드는 Jobs Succeeded 1, Jobs Active 0, Jobs Failed 0 을 보여 줬어요. 같은 화면에서 Pods Succeeded 는 1, Containers Terminated 는 1 이 됐어요. hello 의 파드가 명령을 마치고 Succeeded 상태로 남았기 때문이에요. Active 와 Failed 가 N/A 가 아니라 0 이 된 점도 봐 둘 만해요. hello 라는 Job 이 생기면서 그 Job 의 active·failed 시계열도 생겼고, 값이 0 이라서 0 이 나왔어요. 3절에서 본 0 과 N/A 의 차이가 같은 칸 안에서 바뀐 거예요.

이 화면을 만들면서 원본의 실수도 하나 찾았어요. 원본 Jobs 줄에는 "Jobs Succeeded" 라는 제목의 칸이 두 개 있어요(그림 5). 그런데 두 번째 칸의 수식은 kube_job_status_active 를 세요. 실행 중인 Job 파드 수를 세는 칸에 제목만 잘못 붙어 있었던 거예요. 수정판에서는 제목을 "Jobs Active (원본 제목: Jobs Succeeded)" 로 고치고, Grafana API 로 같은 uid(k8s-lab-6417)에 덮어써 다시 가져왔어요. 그림 13 의 가운데 칸이 그 결과예요. 테스트로 만든 Job hello 는 default 네임스페이스에 그대로 두었어요. 지울 때는 kubectl delete job hello 를 쓰면 돼요.

or vector(0) 로 0 을 보여 줄 수는 있다

Job 이 없을 때 N/A 대신 0 을 보여 주고 싶다면 수식 끝에 or vector(0) 를 붙이는 방법이 있어요. Prometheus 연산자 문서에 따르면 vector1 or vector2 는 vector1 의 원소를 모두 담고, vector1 에 같은 라벨 묶음이 없는 vector2 의 원소를 더해요. 함수 문서에 따르면 vector(0) 은 라벨이 없는 원소 하나짜리 벡터예요.

sum(kube_job_status_failed{namespace=~"$namespace"}) or vector(0)

→ 왼쪽 sum() 에 값이 있으면 그 값을 쓰고, 왼쪽이 비어 있으면 라벨 없는 0 하나를 내놓으라는 뜻이에요.

대신 잃는 것이 있어요. Job 이 없어서 비어 있는 경우와, kube-state-metrics 가 멈춰 아무것도 받아 오지 못해 비어 있는 경우가 모두 0 이 돼요. 두 번째 경우를 직접 만들어 보지는 않았지만, kube-state-metrics 가 멈추면 kube_job_* 시계열이 들어오지 않으니 왼쪽 sum() 은 똑같이 비어요. 그러면 화면에 "Jobs Failed 0" 이 떠요. 수집이 끊긴 상태가 정상 상태와 같은 숫자로 보이는 거예요. 그래서 이 클러스터에서는 N/A 를 그대로 두었어요.

그림 14. or vector(0) 는 "없다"와 "못 본다"를 같은 0 으로 만든다

N/A 로 둔다고 문제가 다 풀리지는 않아요. 그림 14 의 첫째 줄을 보면 N/A 도 "Job 이 없다"와 "수집이 끊겼다"를 구분하지 못해요. 둘을 가르려면 수집 상태를 따로 물어야 해요. Prometheus 문서에 따르면 Prometheus 는 대상을 수집할 때마다 up 시계열에 성공이면 1, 실패면 0 을 적어요. 우리 설정에서 kube-state-metrics 는 주소를 직접 적은 수집 대상(static_configs)이라, 문서대로라면 멈춰도 up 시계열은 남고 값이 0 이 돼요. 반대로 수집 대상이 서비스 디스커버리 목록에서 빠지면 up 이 0 이 아니라 아예 사라질 수 있어요. 그 경우는 메트릭 수집 실습-2에서 직접 재 봤어요.

💡 실무에서는: 0 을 보여 주려면 수집 상태를 옆에 둬요
Job 칸을 0 으로 보이게 하고 싶다면 or vector(0) 와 함께 up{job="kube-state-metrics"} 를 보여 주는 칸을 같은 줄에 두세요. up 이 1 일 때의 0 은 "Job 이 없다"이고, up 이 0 일 때의 0 은 "모른다"예요. 알람도 같은 방식으로 나눠요. 있어야 할 시계열이 없을 때 울려야 하면 absent() 를 쓰고(함수 문서: 넘긴 벡터가 비어 있으면 1 을 돌려준다), 수집 실패는 up == 0 으로 따로 잡아요.
✍️ 오늘의 요약
6417 원본에서 N/A 였던 열한 칸 가운데 여덟 칸은 이름이나 라벨 값 때문이었어요. kube-state-metrics v2 가 지운 이름 8개, v1.2 문서부터 _total 이 붙은 재시작 수, node_exporter 0.16 에서 _bytes 가 붙은 디스크 이름 2개, 그리고 kubelet 이 2019년에 보고를 멈춘 OutOfDisk 조건이 원인이었어요. 남은 세 칸은 Job 이 없어서 N/A 가 맞는 표시였어요.

수식 18개와 제목 2개를 고친 수정판에서는 파드 5.23%, CPU 23.1%, 메모리 1.58% 가 손으로 계산한 값과 맞았어요. 다만 디스크 용량은 node-exporter 가 자기 컨테이너의 마운트를 읽어 세 배 넘게 잡혔고, 이 "사용률"은 실제 사용량이 아니라 요청량의 비율이었어요. N/A 는 고칠 곳을 알려 줬고, 채워진 숫자는 다시 계산해 본 뒤에야 믿을 수 있었어요. 대시보드를 가져온다는 것은 그 대시보드가 만들어진 시절의 메트릭 이름까지 함께 가져온다는 뜻이에요.
