64편. sleep infinity 파드는 왜 지우는 데 30초가 걸릴까, 컨테이너 PID 1과 커널 규칙

nginx 컨테이너 두 개를 한 파드에 넣은 Deployment를 apply하고 바로 kubectl rollout status를 실행했어요. 61편에서 본 대로 두 nginx는 같은 80번 포트에 bind하려고 하니 둘째 컨테이너가 계속 죽는, 처음부터 정상이 될 수 없는 구성이에요. 그런데 rollout status는 1초 만에 성공을 알렸어요(labs/devops/k8s-study/out/62-rollout-status-false-success.txt).

## kubectl apply deployment.apps/same-port-deploy created exit=0 ## kubectl rollout status (progressDeadlineSeconds: 20) Waiting for deployment "same-port-deploy" rollout to finish: 0 of 1 updated replicas are available... deployment "same-port-deploy" successfully rolled out exit=0 걸린 시간 1초

CI 파이프라인이었다면 배포 단계가 통과로 끝났을 거예요. 같은 두 컨테이너 구성을 다시 만들어 30초 뒤에 보니 파드는 1/2 Error였고 재시작은 2번, Deployment의 Available 조건은 False였어요. 성공이라고 답한 명령과 실제 상태가 30초 만에 엇갈렸어요.

이 글은 rollout status가 무엇을 보고 성공이라고 판단하는지 v1.37.2 소스로 확인하고, minReadySeconds·progressDeadlineSeconds·readinessProbe가 이 실패를 잡는지 같은 구성으로 실험해요. 실험은 모두 Lima VM 4대(마스터 1, 워커 3)에 올린 kubeadm v1.37.2 클러스터에서 했어요.

이 글에서 다룰 것
· rollout status는 무엇을 보고 성공이라고 할까?
· 클라이언트는 created가 뜨면 된 줄 아는데 무엇을 더 봐야 할까?
· progressDeadlineSeconds를 30초로 줬는데 왜 실패까지 75초가 걸렸을까?
· readinessProbe를 달면 이 실패를 잡을까?
· rollout status가 끝난 순간 옛 파드는 어떤 상태일까?

1. rollout status는 1초 만에 성공을 냈고 30초 뒤 파드는 Error였다

같은 망가진 구성을 minReadySeconds만 바꿔 두 번 배포했어요. 컨테이너 포트는 적지 않았고 replicas는 1, progressDeadlineSeconds는 30이에요. rollout status가 끝난 직후와 30초 뒤에 Deployment와 파드를 봤어요(62-rollout-minready.txt, 같은 이름의 .sh).

## minReadySeconds: 0 rollout status: exit=0, 1초, 마지막 줄: deployment "sp-minready0" successfully rolled out [rollout status 끝난 직후] availableReplicas=1 파드: 2/2 Running restarts=0 Available=True MinimumReplicasAvailable Progressing=True NewReplicaSetAvailable [30초 뒤] availableReplicas= 파드: 1/2 Error restarts=2 Progressing=True NewReplicaSetAvailable Available=False MinimumReplicasUnavailable

→ rollout status가 끝난 순간에는 파드가 2/2 Running이었고 availableReplicas도 1이었어요. 30초 뒤에는 1/2 Error, 재시작 2번이었고 Available이 False로 바뀌었어요. 그런데 Progressing은 여전히 True NewReplicaSetAvailable이었어요. 이 차이는 2절에서 다시 봐요.

그림 1. minReadySeconds 0은 1초 만에 성공, 10은 76초 만에 실패로 끝났어요.

망가진 파드가 어떻게 그 순간에는 2/2였을까

61편의 로그를 보면 둘째 nginx는 bind에 실패해도 바로 끝나지 않고 try again to bind() after 500ms를 남기며 잠깐 더 버텨요. 그동안 컨테이너는 running 상태예요. 이 구성에는 readinessProbe가 없었고 v1.37.2 kubelet의 prober_manager.go는 그런 컨테이너를 실행 중이기만 하면 준비됐다고 봐요.

// The check whether there is a probe which hasn't run yet. w, exists := m.getWorker(pod.UID, c.Name, readiness) ready = !exists // no readinessProbe -> always ready

→ readinessProbe가 없으면 running인 컨테이너는 항상 ready라는 뜻이에요. 두 컨테이너가 모두 막 뜬 그 순간 파드는 Ready가 됐고 minReadySeconds가 0이니 곧바로 available로 세어졌어요.

📖 용어: availableReplicas와 minReadySeconds
Deployment의 status.availableReplicas는 Ready 상태가 minReadySeconds 이상 이어진 파드 수예요. 필드 설명대로 minReadySeconds의 기본값은 0이고 "pod will be considered available as soon as it is ready", 즉 Ready가 되는 순간 available로 세어져요. 10을 주면 컨테이너가 죽지 않고 Ready가 10초 이어져야 available이 돼요.

rollout status는 무엇을 보고 성공이라고 할까?

rollout status는 Deployment를 지켜보다가 status가 아래 조건을 처음 만족하는 순간 끝나요. v1.37.2의 rollout_status.go에서 Deployment 부분을 옮겼어요(62-k8s-v1.37.2-rollout-excerpts.txt).

if cond != nil && cond.Reason == deploymentutil.TimedOutReason { return "", false, fmt.Errorf("deployment %q exceeded its progress deadline", ...) } if deployment.Status.UpdatedReplicas < *deployment.Spec.Replicas { ...Waiting... } if deployment.Status.Replicas > deployment.Status.UpdatedReplicas { ...old replicas are pending termination... } if deployment.Status.AvailableReplicas < deployment.Status.UpdatedReplicas { ...Waiting... } return fmt.Sprintf("deployment %q successfully rolled out\n", ...), true, nil

→ Progressing 조건의 사유가 시간 초과면 실패로 끝나요. 아니면 새 버전 파드 수가 목표에 닿았는지, 옛 버전 파드가 남았는지, 새 버전 파드가 모두 available인지를 차례로 보고 셋 다 통과하는 첫 순간에 성공으로 끝나요. 그 상태가 몇 초 이어졌는지는 보지 않아요. available이 얼마나 오래 유지돼야 하는지는 Deployment의 minReadySeconds가 정하고, rollout status는 그 결과를 한 번 읽을 뿐이에요.

클라이언트는 created가 뜨면 된 줄 아는데?

apply가 돌려준 deployment.apps/same-port-deploy created와 exit 0은 API 서버가 명세를 검증하고 저장했다는 뜻이에요. API 서버는 스키마와 정적 규칙만 봐요. 61편에서 같은 파드에 같은 containerPort를 두 번 적었을 때 거절 대신 경고만 낸 것도 그 때문이에요. 파드가 노드에 배치되고 이미지를 받고 컨테이너가 뜨는 일은 그 뒤에 컨트롤러와 kubelet이 하고 결과는 status에 쌓여요. created는 시작일 뿐이고 그다음 판단을 rollout status에 맡겼는데 그 판단이 1초짜리 순간을 성공으로 읽은 거예요.

2. 성공으로 기록된 뒤에는 Deployment가 실패를 다시 알리지 않는다

앞 결과의 30초 뒤 줄에서 Available은 False였지만 Progressing은 True NewReplicaSetAvailable 그대로였어요. progressDeadlineSeconds 30초가 지나도 이 Deployment는 ProgressDeadlineExceeded로 바뀌지 않아요. Deployment 컨트롤러의 progress.go에 이유가 있어요.

// If there is only one replica set that is active then that means we are not running // a new rollout and this is a resync where we don't need to estimate any progress. currentCond := util.GetDeploymentCondition(d.Status, apps.DeploymentProgressing) isCompleteDeployment := newStatus.Replicas == newStatus.UpdatedReplicas && currentCond != nil && currentCond.Reason == util.NewRSAvailableReason // Check for progress only if there is a progress deadline set and the latest rollout // hasn't completed yet. if util.HasProgressDeadline(d) && !isCompleteDeployment { switch { case util.DeploymentComplete(d, &newStatus): // → NewReplicaSetAvailable case util.DeploymentProgressing(d, &newStatus): // → ReplicaSetUpdated, lastUpdateTime 갱신 case util.DeploymentTimedOut(ctx, d, &newStatus): // → ProgressDeadlineExceeded } }

→ Progressing의 사유가 한 번 NewReplicaSetAvailable이 되고 옛 버전이 남지 않으면 그 배포는 끝난 것으로 보고 진행 여부를 더 계산하지 않아요. 1초짜리 순간에 완료로 기록된 이 배포는 그 뒤 파드가 계속 죽어도 시간 초과로 바뀌지 않아요. 망가졌다는 신호는 Available=False와 MinimumReplicasUnavailable, 파드의 재시작 횟수와 BackOff 이벤트에만 남아요.

그림 2. 완료로 한 번 기록되면 그 배포는 진행 검사 대상에서 빠지고 실패는 되돌아갈 수 있어요.

이래서 선언형 구조가 문제일까?

반은 맞아요. 선언형이라는 것은 원하는 상태를 적어 두면 컨트롤러가 계속 그 상태로 맞추려 한다는 뜻이지, 그 상태가 실현 가능한지 받아들이기 전에 확인한다는 뜻이 아니에요. 그래서 받아들여진 명세가 동작한다는 보장은 없어요. 이번 Deployment도 API 서버가 받아 저장했고 컨트롤러는 한순간의 Ready를 보고 완료로 기록했어요.

나머지 반은 그 뒤에 있어요. 쿠버네티스는 실패해도 멈추지 않고 계속 시도해요. kubelet은 web2를 계속 다시 띄웠고 3절의 minReadySeconds 10 배포에서는 재시작 횟수가 30초 사이에 3에서 4로 올라갔어요. progressDeadlineSeconds의 필드 설명도 "The deployment controller will continue to process failed deployments"라고 적었어요(62-deployment-fields-explain.txt). 실패로 판정한 배포도 컨트롤러가 계속 처리한다는 뜻이에요. 실패는 숨겨지지 않고 status와 이벤트에 계속 쌓여요. 문제는 그 신호를 apply의 출력이나 rollout status의 한 줄이 아니라 status에서 읽어야 한다는 데 있어요.

⚠️ 배포가 끝난 뒤의 고장은 Progressing이 알려 주지 않아요
• Progressing=True NewReplicaSetAvailable은 "이번 배포가 한 번 완료에 닿았다"는 기록이에요. 지금 파드가 정상이라는 뜻이 아니에요
• 지금 상태는 Available 조건과 status.unavailableReplicas, 파드의 재시작 횟수로 봐요
• 모니터링 경보를 Progressing=False에만 걸면 이 글의 경우를 놓쳐요. Available=False가 일정 시간 이어지는 것도 함께 봐요

3. minReadySeconds 10을 주자 rollout status가 제대로 실패했다

같은 구성에 minReadySeconds 10만 줬어요. 이번에는 rollout status가 76초 만에 exit 1로 끝났어요.

## minReadySeconds: 10 rollout status: exit=1, 76초, 마지막 줄: error: deployment "sp-minready10" exceeded its progress deadline [rollout status 끝난 직후] availableReplicas= 파드: 1/2 Error restarts=3 Available=False MinimumReplicasUnavailable Progressing=False ProgressDeadlineExceeded [30초 뒤] availableReplicas= 파드: 1/2 Error restarts=4 Available=False MinimumReplicasUnavailable Progressing=True ReplicaSetUpdated

→ web2가 Ready인 시간은 매번 10초보다 짧았으니 파드는 한 번도 available이 되지 못했어요. Deployment는 완료에 닿지 못했고 진행 검사가 계속됐어요. 결국 Progressing=False ProgressDeadlineExceeded가 됐고 rollout status는 그 사유를 읽고 exit 1로 끝났어요. CI에서 받아야 할 결과가 이거예요.

30초 뒤 줄도 눈여겨볼 만해요. Progressing이 다시 True ReplicaSetUpdated로 돌아갔어요. 그림 2의 점선 길이에요. 실패 사유는 영구적인 표시가 아니라서 그 뒤에 ready가 한 번만 늘어도 진행 중으로 바뀌어요. rollout status는 시간 초과를 처음 본 순간 exit 1로 끝나니 CI는 실패를 받지만, 나중에 Deployment를 열어 본 사람은 실패 기록을 못 볼 수도 있어요.

📖 용어: progressDeadlineSeconds와 Progressing 조건
Deployment가 진행 없이 이 시간(기본 600초)을 넘기면 컨트롤러가 Progressing 조건을 False, 사유 ProgressDeadlineExceeded로 바꿔요. 여기서 "진행"은 새 파드가 늘거나 옛 파드가 줄거나 ready·available 파드가 늘어난 것이고 그때마다 조건의 lastUpdateTime이 갱신돼요. 컨트롤러는 이 시각부터 시간을 다시 세요.

progressDeadlineSeconds를 30초로 줬는데 왜 실패까지 75초가 걸렸을까?

minReadySeconds 10인 같은 구성을 다시 만들고 Progressing의 lastUpdateTime을 1초마다 읽었어요(62-progress-deadline-reset.txt). 경과 시간은 apply 뒤 Mac에서 잰 값이고 괄호 안은 컨트롤러가 기록한 UTC 시각이에요.

경과 ready avail | Progressing 사유 (lastUpdateTime) | 파드 READY 재시작 + 1s ready=0 avail=0 | ReplicaSetUpdated (2026-11-15T12:02:06Z) | 0/2 restarts=0 + 2s ready=1 avail=0 | ReplicaSetUpdated (2026-11-15T12:02:07Z) | 2/2 restarts=0 + 4s ready=1 avail=0 | ReplicaSetUpdated (2026-11-15T12:02:10Z) | 2/2 restarts=1 + 8s ready=0 avail=0 | ReplicaSetUpdated (2026-11-15T12:02:10Z) | 1/2 restarts=1 + 18s ready=1 avail=0 | ReplicaSetUpdated (2026-11-15T12:02:24Z) | 2/2 restarts=2 + 22s ready=0 avail=0 | ReplicaSetUpdated (2026-11-15T12:02:24Z) | 1/2 restarts=2 + 43s ready=1 avail=0 | ReplicaSetUpdated (2026-11-15T12:02:49Z) | 2/2 restarts=3 + 47s ready=0 avail=0 | ReplicaSetUpdated (2026-11-15T12:02:49Z) | 1/2 restarts=3 + 75s ready=0 avail=0 | ProgressDeadlineExceeded (2026-11-15T12:03:20Z) | 1/2 restarts=3

→ web2가 다시 뜰 때마다 파드가 잠깐 2/2가 됐고 그때마다 lastUpdateTime이 12:02:07, :10, :24, :49로 갱신됐어요. 진행으로 친 근거는 deployment_util.go의 DeploymentProgressing이에요. 진행의 조건 네 가지 가운데 하나가 newStatus.ReadyReplicas > deployment.Status.ReadyReplicas예요(62-k8s-v1.37.2-deployment-progress-excerpt.go). available이 하나도 늘지 않았어도 ready가 0에서 1로 오르면 진행이에요.

갱신 간격은 3초, 14초, 25초로 늘었어요. web2가 죽은 뒤 다시 뜨기까지 kubelet이 기다린 시간이 늘었기 때문이에요. 표에서 +8초에 죽은 web2는 +18초에 다시 떴고 +22초에 죽은 web2는 +43초에 다시 떴어요. 재시작 대기가 10초에서 20초로 두 배가 됐어요. 그다음 대기는 30초를 넘었고 :49 이후 다음 진행이 오기 전에 30초가 지나 12:03:20에 ProgressDeadlineExceeded가 됐어요. 30초라는 설정은 "배포 시작부터 30초"가 아니라 "마지막 진행부터 30초"예요.

그림 3. 막대 하나가 30초 기한이에요. 다음 초록 눈금이 막대 안에 오면 기한이 새로 시작됐어요.

그러니 progressDeadlineSeconds만으로는 "배포에 몇 초 이상 걸리면 실패"를 정할 수 없어요. 재시작을 반복하며 Ready를 잠깐씩 찍는 파드는 기한을 계속 늘려요. 이번에는 재시작 대기가 늘어나는 덕분에 75초 만에 끝났지만 그 시간은 설정이 아니라 재시작 간격이 정했어요.

그림 4. 기한 30초를 준 배포가 실패로 기록되기까지 75초가 걸렸어요.

4. readinessProbe를 달아도 같은 포트에서는 web1이 대신 답했다

rollout status가 1초짜리 순간을 성공으로 읽은 것은 readinessProbe가 없어서였어요. 그렇다면 web2에 readinessProbe를 달면 될까요? 같은 망가진 구성에서 web2에만 80번 포트를 보는 httpGet 프로브를 달고 minReadySeconds는 주지 않았어요. web1에는 프로브가 없어요(62-readiness-shared-port.txt, 같은 이름의 .sh, 네임스페이스 blog-62).

- name: web2 image: nginx:1.27-alpine readinessProbe: httpGet: {path: /, port: 80} 저장된 web2 프로브: {"failureThreshold":3,"httpGet":{"path":"/","port":80,"scheme":"HTTP"}, "periodSeconds":10,"successThreshold":1,"timeoutSeconds":1} ## kubectl rollout status exit=0 0.6초 마지막 줄: deployment "probe-demo" successfully rolled out

→ 프로브를 달았는데도 rollout status는 0.6초 만에 exit 0으로 끝났어요. 그 뒤 60초 동안 web2의 상태가 바뀔 때만 적은 기록에서 뜨고 죽는 줄을 골랐어요.

경과 | web2 ready 상태 재시작 | web1 ready | deploy ready/available | Progressing 사유 + 0.8s web2 ready=true running restarts=0 | web1 ready=true | ready=1 available=1 | NewReplicaSetAvailable + 5.0s web2 ready=true running restarts=1 | web1 ready=true | ready=1 available=1 | NewReplicaSetAvailable + 8.5s web2 ready=false terminated(Error) restarts=1 | web1 ready=true | ready= available= | NewReplicaSetAvailable + 14.4s web2 ready=false waiting(CrashLoopBackOff) restarts=1 | ... + 18.6s web2 ready=true running restarts=2 | web1 ready=true | ready=1 available=1 | NewReplicaSetAvailable + 22.5s web2 ready=false terminated(Error) restarts=2 | ... + 45.2s web2 ready=true running restarts=3 | web1 ready=true | ready=1 available=1 | NewReplicaSetAvailable + 48.7s web2 ready=false terminated(Error) restarts=3 | ...

→ web2는 뜰 때마다 ready=true가 됐다가 몇 초 뒤 Error로 죽었어요. readinessProbe가 실패를 막지 못했을 뿐 아니라 매번 통과했어요. 누가 그 프로브에 답했는지는 web1의 nginx 접근 로그에 남아 있었어요.

## 프로브 요청을 받은 쪽: web1 의 nginx 접근 로그에서 kube-probe 요청 (web1 에는 프로브가 없다) kube-probe 줄 수: 4 192.168.104.3 - - [15/Nov/2026:12:45:04 +0000] "GET / HTTP/1.1" 200 615 "-" "kube-probe/1.37" "-" 192.168.104.3 - - [15/Nov/2026:12:45:07 +0000] "GET / HTTP/1.1" 200 615 "-" "kube-probe/1.37" "-" ## web2 의 마지막으로 죽은 실행 로그 2026/11/15 12:45:47 [emerg] 1#1: bind() to 0.0.0.0:80 failed (98: Address in use)

→ 프로브가 없는 web1의 로그에 User-Agent가 kube-probe/1.37인 요청이 4번 찍혔어요. 출력한 앞의 두 줄은 200이었고 web2는 뜰 때마다 ready=true가 됐으니 네 번 모두 통과한 셈이에요. 보낸 곳 192.168.104.3은 이 파드가 배치된 worker1의 노드 주소, 즉 kubelet이에요. 4라는 횟수는 web2가 뜬 횟수(재시작 0~3)와 같았어요. kubelet은 web2의 프로브로 파드 IP의 80번 포트를 불렀고 그 포트를 쥔 web1이 200으로 답했어요. 이벤트에도 Readiness probe failed는 한 줄도 없었고 실패를 알린 이벤트는 BackOff 6번뿐이었어요.

📖 용어: readinessProbe
kubelet이 컨테이너가 요청을 받을 준비가 됐는지 주기적으로 묻는 검사예요. 실패하면 그 컨테이너를 not ready로 표시해 파드가 Service의 준비된 대상에서 빠지고, 재시작은 하지 않아요. httpGet 프로브는 host를 적지 않으면 파드 IP로 요청해요(필드 설명 "defaults to the pod IP"). 57편에서 앱의 /readyz로 Ready를 끄고 켜 봤어요.

그림 5. 같은 파드에서는 포트가 하나뿐이라 프로브가 어느 컨테이너의 응답인지 구별하지 못해요.

periodSeconds가 10인데 몇 초밖에 살지 못한 web2가 매번 검사를 받은 이유도 kubelet 소스에 있어요. 앞에서 본 prober_manager.go의 같은 자리는 프로브가 있는데 아직 결과가 없으면 // Trigger an immediate run of the readinessProbe to update ready state로 즉시 한 번 검사를 돌려요. 그래서 web2가 뜰 때마다 첫 검사가 바로 나갔고 그 검사를 web1이 받았어요.

이 실험이 보여 준 것은 readinessProbe가 쓸모없다는 게 아니에요. 프로브는 컨테이너가 아니라 파드 IP의 포트에 묻기 때문에 그 포트를 쥔 프로세스가 답해요. 같은 파드 안의 다른 컨테이너가 같은 포트를 쓰거나, 사이드카 프록시가 앱 대신 그 포트에서 응답하는 구성이라면 프로브의 통과는 대상 컨테이너가 준비됐다는 증거가 되지 못해요. 이번 경우의 근본 원인은 포트 충돌이라서 고칠 곳도 프로브가 아니라 포트예요.

5. rollout status가 끝난 순간 옛 파드는 아직 종료 중이었다

rollout status의 조건에는 "옛 버전 파드가 남았는가"도 있었어요. 그럼 성공이 떴을 때 옛 파드는 다 사라졌을까요? nginx 이미지를 1.27에서 1.28로 바꾸는 정상 배포로 확인했어요. 옛 파드가 오래 종료 중이도록 terminationGracePeriodSeconds를 20초로 주고 SIGTERM을 받으면 15초 뒤에 끝나게 했어요(62-rollout-terminating.txt).

## rollout status 끝남 (+7s) deploy status: replicas=2 updated=2 available=2 terminatingReplicas=2 POD IMAGE PHASE DELETION term-demo-5cf449689f-vxr95 nginx:1.28-alpine Running <none> term-demo-5cf449689f-wvc6b nginx:1.28-alpine Running <none> term-demo-5dc665fc76-5wrkf nginx:1.27-alpine Running 2026-11-15T12:04:11Z term-demo-5dc665fc76-z64nk nginx:1.27-alpine Running 2026-11-15T12:04:04Z ## 20초 뒤 terminatingReplicas=0

→ rollout status가 끝난 순간 nginx:1.27 파드 두 개는 deletionTimestamp가 찍힌 채 아직 Running이었어요. 그런데 Deployment의 replicas는 2였어요. 종료 중인 두 파드는 replicas에 세지 않고 terminatingReplicas=2로 따로 셌다는 뜻이에요. rollout status의 "옛 파드가 남았는가"는 replicas와 updatedReplicas를 비교하니 이미 삭제가 요청된 파드는 기다리지 않아요. 20초 뒤에 terminatingReplicas가 0이 됐어요. deletionTimestamp에 미래 시각이 찍힌 이유와 종료 중인 파드의 phase는 63편에서 다뤄요.

📖 용어: terminatingReplicas
Deployment와 ReplicaSet의 status에 있는 필드로, 삭제가 요청됐지만 아직 끝나지 않은 파드 수예요. KEP-3973의 DeploymentReplicaSetTerminatingReplicas 기능으로 1.33에 알파(기본 꺼짐), 1.35에 베타(기본 켜짐)로 들어왔어요. 우리 1.37.2 클러스터에서는 기본으로 채워져요.

CI가 다음 단계에서 옛 버전이 모두 내려갔다고 가정한다면 이 필드를 기다리면 돼요. busybox로 SIGTERM을 받으면 15초 뒤 exit 0으로 끝나는 Deployment를 만들고 환경 변수를 바꿔 배포한 뒤 rollout status 다음에 kubectl wait를 붙였어요(62-wait-terminating.txt).

## kubectl set env deploy/wait-demo V=2 → kubectl rollout status deployment "wait-demo" successfully rolled out +2.4s rollout status 끝남, terminatingReplicas=2 ## kubectl wait --for=jsonpath='{.status.terminatingReplicas}'=0 deployment.apps/wait-demo condition met exit=0 +18.0s

→ rollout status는 2.4초에 끝났고 그때 옛 파드 2개가 종료 중이었어요. kubectl wait는 18.0초에 terminatingReplicas=0을 확인하고 끝났어요. 그 사이 15초 남짓은 옛 버전이 아직 돌던 시간이에요. 옛 파드는 exit 0으로 끝나 Succeeded로 표시됐어요. 지우는 중에 exit 0으로 끝난 파드는 restartPolicy가 Always여도 Succeeded가 된다는 것을 따로 확인한 기록은 62-deleted-pod-phase.txt에 있고 63편에서 phase와 함께 봐요.

6. CI에서 rollout status를 믿으려면 무엇을 더 봐야 할까

런타임 오류는 따로 잡아야 할까?

그래요. 지금까지의 결과를 신호별로 모으면 이래요.

신호알려 주는 것이 글의 실험에서
apply의 created, exit 0API 서버가 명세를 검증하고 저장했다실행될 수 없는 구성도 created
rollout status exit 0어느 한 순간 새 파드가 모두 available이었다0.6~1초 만에 거짓 성공
minReadySecondsReady가 N초 이어져야 available로 센다10초로 실패를 잡음(76초 뒤 exit 1)
readinessProbe파드 IP의 그 포트·경로가 응답한다포트를 같이 쓰는 web1이 대신 통과시킴
progressDeadlineSeconds마지막 진행 뒤 N초 동안 진행이 없었다Ready 깜빡임마다 다시 셈, 완료 기록 뒤엔 안 봄
terminatingReplicas옛 파드가 아직 종료 중이다rollout status는 기다리지 않음
Available 조건, 재시작 횟수지금 파드가 버티고 있는가30초 뒤 False, 재시작 2회

rollout status 하나가 이 모든 신호를 대신하지 못해요. rollout status는 Deployment가 내린 판단을 그대로 읽어 오는 도구이고, 그 판단을 정확하게 만드는 일은 Deployment 명세의 minReadySeconds와 readinessProbe가 맡아요. 7편에서 노드를 재부팅한 직후 rollout status가 재부팅 전 값으로 통과한 것도 같은 구조였어요. 명령은 지금 보이는 status를 읽을 뿐이에요.

💡 CI 배포 단계를 이렇게 짜요
• minReadySeconds를 앱이 뜨고 안정되는 데 걸리는 시간에 맞춰 줘요. 이 글에서는 10초로 몇 초 만에 죽는 컨테이너를 걸렀어요
• readinessProbe는 그 컨테이너만 답할 수 있는 포트와 경로로 정해요. 같은 파드의 다른 컨테이너나 프록시가 같은 포트에서 응답하면 프로브의 통과가 대상 컨테이너의 상태를 말해 주지 못해요
• rollout status는 --timeout을 progressDeadlineSeconds보다 넉넉히 주고 exit 코드로 실패를 받아요. exit 1과 exceeded its progress deadline이 실패 신호예요
• 옛 버전이 모두 내려가야 하는 단계 앞에는 kubectl wait deploy/<이름> --for=jsonpath='{.status.terminatingReplicas}'=0을 둬요
• 끝난 뒤 Available 조건과 파드 재시작 횟수를 한 번 더 확인해요. 완료로 기록된 뒤의 고장은 Progressing에 나타나지 않아요

✍️ 오늘의 요약

rollout status는 새 파드가 모두 available인 첫 순간에 성공으로 끝나고 그 상태가 이어지는지는 보지 않아요. readinessProbe도 minReadySeconds도 없는 망가진 Deployment는 컨테이너가 막 뜬 1초 동안 Ready가 되어 exit 0을 받았고, 한 번 완료로 기록된 뒤에는 파드가 계속 죽어도 Progressing이 실패로 바뀌지 않았어요.

minReadySeconds 10을 주자 76초 뒤 exit 1로 제대로 실패했어요. 다만 progressDeadlineSeconds는 ready가 오를 때마다 다시 세서 30초 기한이 75초가 됐어요. web2에 readinessProbe를 달아도 파드 IP의 80번 포트를 쥔 web1이 대신 200을 돌려줘 프로브가 통과했어요. 성공이 뜬 순간 옛 파드는 종료 중이었고 terminatingReplicas가 0이 될 때까지 15초 남짓 더 돌았어요.

rollout status는 Deployment가 내린 판단을 한 번 읽어 오는 도구예요. 판단을 정확하게 만드는 것은 minReadySeconds와 그 컨테이너만 답할 수 있는 readinessProbe이고, 배포 뒤의 상태는 Available과 재시작 횟수로 따로 확인해야 해요.
