68편. 쿠버네티스 Job에 사이드카를 붙이면 왜 끝나지 않을까

파드 세 개에 똑같은 일을 20번씩 했어요. kubectl exec <파드> -- sh -c 'sleep 1 >/dev/null 2>&1 &', 백그라운드로 1초짜리 sleep을 띄우고 바로 빠져나오는 명령이에요. 3초 뒤 각 컨테이너 안의 좀비 수와 cgroup의 프로세스 수를 셌어요.

## 시작 전 z-sleep 좀비 0개 / pids.current 3 z-tini 좀비 0개 / pids.current 4 z-share 좀비 0개 / pids.current 3 ## 20번 뒤 (마지막 exec 후 3초) z-sleep 좀비 20개 / pids.current 23 z-tini 좀비 0개 / pids.current 4 z-share 좀비 0개 / pids.current 3

→ PID 1이 sleep infinity인 z-sleep에는 끝난 sleep 20개가 좀비로 남아 프로세스 수가 20 늘었고, tini가 PID 1인 z-tini와 pause가 PID 1인 z-share에는 하나도 남지 않았다는 뜻이에요. 원본은 labs/devops/k8s-study/out/66-zombie-pile.txt와 같은 디렉터리의 66-zombie-pile.sh예요.

64편과 65편에서는 PID 1이 신호를 처리하지 못하는 문제를 봤어요. 셸을 걷어내고 앱에게 PID 1을 넘기면 신호 문제는 풀리지만, PID 1에게는 신호 말고 하나의 일이 더 있어요. Docker에는 이 일을 대신해 줄 작은 init을 끼워 넣는 docker run --init이 있는데 쿠버네티스 Pod API에는 그런 필드가 없어요. 쿠버네티스에는 왜 docker run --init이 없을까요?

이 글에서 다룰 것
· 고아 프로세스는 왜 컨테이너의 PID 1에게 갈까?
· tini와 pause는 무엇을 하길래 좀비가 0개였을까?
· Docker의 --init은 어떻게 생겼고 왜 기본으로 꺼져 있을까?
· 쿠버네티스는 왜 pause를 신호 전달 init으로 만들지 않았을까?
· 파드에 init 옵션을 달자는 요청은 지금 어디에 있을까?

1. 좀비 20개의 부모는 모두 컨테이너의 sleep infinity였다

📖 용어: 좀비 프로세스
실행은 끝났지만 부모가 아직 종료 상태를 거두지 않아서 프로세스 표에 남아 있는 프로세스예요. ps에서 STAT이 Z로 보여요. 부모가 wait 계열 시스템 콜을 부르면 사라져요. CPU와 메모리는 거의 쓰지 않지만 PID 번호 하나를 계속 차지해요.

z-sleep의 ps 앞 6줄에 보인 좀비는 모두 [sleep], STAT Z, PPID 1이었어요. 노드에서 세어 보면 20개 전부가 같았어요. 컨테이너의 PID 1인 sleep infinity가 노드에서는 호스트 PID 50858이었고, 이 프로세스의 자식 중 Z 상태가 20개였어요.

그림 1. 좀비의 부모는 컨테이너 안에서 PID 1, 노드에서는 그 PID 1의 호스트 PID 50858이었어요.

그런데 sleep infinity는 이 sleep들을 띄운 적이 없어요. 띄운 것은 kubectl exec로 들어온 sh였어요. exec로 들어온 프로세스는 노드 쪽의 containerd-shim이 만들어서 부모가 shim이에요(shim은 26편). sh는 sleep 1 &를 띄우자마자 끝났고, 1초 뒤 끝난 sleep은 부모를 이미 잃은 고아였어요. 고아를 누가 맡는지는 커널이 정해요.

📖 용어: 고아 입양과 subreaper
부모가 먼저 끝난 프로세스를 고아라고 하고, 커널은 고아에게 새 부모를 정해 줘요. 새 부모는 끝난 자식의 종료 상태를 거둘 책임도 넘겨받아요. 어떤 프로세스가 prctl(PR_SET_CHILD_SUBREAPER)로 자신을 subreaper로 등록하면 자기 밑의 고아를 먼저 받아요.

v6.8 kernel/exit.c의 find_new_reaper() 주석이 순서를 적어 둬요.

/* * When we die, we re-parent all our children, and try to: * 1. give them to another thread in our thread group, if such a member exists * 2. give it to the first ancestor process which prctl'd itself as a * child_subreaper for its children (like a service manager) * 3. give it to the init process (PID 1) in our pid namespace */

→ 끝나는 프로세스의 자식은 같은 스레드 그룹의 다른 스레드, 위쪽의 subreaper, 자기 PID 네임스페이스의 PID 1 순서로 넘어간다는 뜻이에요. 코드의 subreaper 탐색은 task_pid(reaper)->level == ns_level인 동안만, 즉 같은 네임스페이스 깊이 안에서만 올라가요. 노드 쪽 shim까지는 올라가지 않아요. 그래서 컨테이너 안에서 생긴 고아는 컨테이너의 PID 1에게 갔어요.

PID 1이 된 sleep infinity는 자식의 종료 상태를 거두는 코드가 없어요. 넘겨받은 자식이 끝나도 wait를 부르지 않으니 좀비로 남아요. tini를 만든 krallin은 tini 이슈 #8(2015-10-07)에서 이 책임을 "unlike other processes, PID 1 has a unique responsibility, which is to reap zombie processes"라고 적었어요. Yelp의 dumb-init README는 "most processes won't wait() on random processes that happen to become attached to them, so containers often end with dozens of zombies rooted at PID 1"이라고 결과를 적어요. 대부분의 프로그램은 우연히 넘겨받은 프로세스를 wait하지 않아서 컨테이너의 PID 1 밑에 좀비 수십 개가 쌓인다는 뜻이에요.

📖 용어: pids.current
cgroup v2의 pids 컨트롤러가 그 cgroup 안의 프로세스(스레드 포함) 수를 보여 주는 파일이에요. 좀비도 PID를 차지하므로 여기에 세어져요. 쿠버네티스는 파드나 노드의 PID 수에 상한을 걸 수 있고, 상한에 닿으면 새 프로세스를 만들지 못해요.

z-sleep의 pids.current는 3에서 23이 됐어요. 개수를 세는 동안 exec로 들어온 sh와 cat도 함께 세어져서 시작 전 값이 3(tini 파드는 tini가 하나 더 있어 4)으로 보여요. 좀비 20개가 그대로 더해졌어요. tini README는 이런 좀비가 "can (over time!) starve your entire system for PIDs"라고 경고해요. 시간이 지나면 시스템의 PID가 바닥날 수 있다는 뜻이에요. PID 상한까지 좀비를 채워 fork가 실패하는 모습은 이 글에서 실험하지 않았어요.

그림 2. 고아는 노드의 shim이 아니라 컨테이너 네임스페이스의 PID 1에게 갔어요.

2. tini는 핸들러 없이 신호를 받아 넘기고 좀비를 거뒀다

z-tini의 PID 1은 tini였어요. alpine:3.20 이미지의 init 컨테이너가 apk add tini-static로 받은 tini 0.19.0을 emptyDir로 넘기고, 본 컨테이너가 /shared/tini -- sleep infinity로 시작했어요. 이미지를 고치지 않고 tini를 끼운 방법이에요.

📖 용어: tini
컨테이너의 PID 1로 쓰라고 만든 아주 작은 init이에요. 자식 하나를 띄우고, 받은 신호를 그 자식에게 넘기고, 넘겨받은 고아들의 종료 상태를 거두다가 자식이 끝나면 같은 종료 코드로 끝나요. Thomas Orozco(krallin)가 2015-02-22에 첫 커밋을 했어요. 비슷한 일을 하는 dumb-init은 Yelp가 2015-08-11에 저장소를 만들었어요.

tini README는 하는 일을 "spawn a single child ..., and wait for it to exit all the while reaping zombies and performing signal forwarding"으로 요약해요. 자식 하나를 띄우고 그 자식이 끝날 때까지 좀비를 거두며 신호를 넘긴다는 뜻이에요. v0.19.0의 tini.c에서 좀비를 거두는 부분은 pause와 같은 모양이에요.

current_pid = waitpid(-1, &current_status, WNOHANG); ... if (current_pid == child_pid) { if (WIFEXITED(current_status)) { *child_exitcode_ptr = WEXITSTATUS(current_status); } else if (WIFSIGNALED(current_status)) { /* Our process was terminated. Emulate what sh / bash * would do, which is to return 128 + signal number. */ *child_exitcode_ptr = 128 + WTERMSIG(current_status);

→ 끝난 자식이면 누구든 waitpid(-1, ..., WNOHANG)으로 거두고, 그게 자기가 띄운 자식이면 종료 코드를 기억했다가 그대로 쓴다는 뜻이에요. 자식이 신호로 죽었으면 셸과 같이 128 + 신호 번호를 써요. 65편의 삭제 실험에서 h-tini가 0.7초에 143으로 끝난 것이 이 규칙이에요. tini가 sleep에게 SIGTERM을 넘겼고, sleep은 PID 1이 아니라서 기본 동작으로 죽었고, tini가 128 + 15를 돌려줬어요.

SigCgt가 0인데 SIGTERM을 받았다

여기서 64편의 규칙과 맞지 않아 보이는 결과가 하나 있었어요. 64편의 신호 마스크 실험에서 tini의 SigCgt는 0이었어요. 핸들러가 하나도 없는데 PID 1인 tini가 SIGTERM을 받아서 넘겼어요. krallin은 이슈 #8에서 "Tini does install explicit signal handlers"라고 썼지만 우리가 쓴 0.19.0의 코드는 다른 방법을 써요.

/* Block all signals that are meant to be collected by the main loop */ if (sigfillset(parent_sigset_ptr)) { ... if (sigprocmask(SIG_SETMASK, parent_sigset_ptr, sigconf_ptr->sigmask_ptr)) { ... if (sigtimedwait(parent_sigset_ptr, &sig, &ts) == -1) { ... /* Forward anything else */ if (kill(kill_process_group ? -child_pid : child_pid, sig.si_signo)) {

→ 대부분의 신호를 sigprocmask로 막아 두고, 막힌 채 대기 중인 신호를 sigtimedwait로 하나씩 꺼내서 자식(옵션에 따라 자식의 프로세스 그룹)에게 kill한다는 뜻이에요.

📖 용어: 신호 막기와 sigtimedwait
프로세스는 특정 신호를 막아(block) 둘 수 있어요. 막힌 신호는 버려지지 않고 대기 상태로 남아요. sigtimedwait는 지정한 신호가 대기 상태가 될 때까지 기다렸다가 핸들러를 거치지 않고 꺼내 주는 시스템 콜이에요.

커널 쪽 이유는 v6.8 signal.c의 sig_ignored()에 있어요. "Blocked signals are never ignored, since the signal handler may change by the time it is unblocked." 막힌 신호는 나중에 핸들러가 바뀔 수 있으니 버리지 않는다는 주석이고, 64편에서 본 sig_task_ignored()보다 먼저 이 검사를 해요. 그래서 핸들러가 없는 PID 1이어도 신호를 막아 두면 커널이 버리지 않아요. 마스크를 읽은 순간 tini의 SigBlk도 0이었는데, do_sigtimedwait()가 기다리는 동안 원래 마스크를 real_blocked로 옮겨 두기 때문으로 보여요. 이 부분은 소스로만 설명했고 따로 계측하지는 않았어요.

그림 3. tini는 핸들러 대신 막아 둔 신호를 꺼내 넘기고, 자식이 끝날 때마다 고아까지 거둬요.

신호를 넘기는 범위는 도구마다 기본값이 달라요. tini README는 기본으로 직계 자식에게만 보내고 -g를 주면 자식의 프로세스 그룹 전체에 보낸다고 적어요. 예로 든 것이 sh -c 'sleep 10'에 ctrl-C를 눌러도 sh가 sleep을 기다리느라 반응하지 않는 경우예요. dumb-init README는 기본으로 자식을 중심으로 세션을 만들고 그 프로세스 그룹 전체에 신호를 보낸다고 적어요.

3. Docker는 1.13에서 --init을 넣었지만 기본은 꺼 두었다

tini와 dumb-init은 이미지 안에 넣어서 쓰는 도구예요. Docker는 이걸 런타임 옵션으로 바꿨어요. 2016-08-26 Michael Crosby(crosbymichael)가 연 moby PR #26061의 본문이에요.

This adds a small C binary for fighting zombies. It is mounted under /dev/init and is prepended to the args specified by the user. You enable it via a daemon flag, dockerd --init, as it is disable by default for backwards compat. You can also override the daemon option or specify this on a per container basis with docker run --init=true|false.

→ 좀비를 거두는 작은 C 바이너리를 컨테이너의 /dev/init에 마운트하고 사용자가 준 명령 앞에 붙여 실행한다는 뜻이에요. 이미지를 고칠 필요가 없어요. 하위 호환 때문에 기본은 꺼져 있고 데몬 전체(dockerd --init)나 컨테이너마다(docker run --init) 켜요. 이 바이너리의 이름이 grimes였고 PR은 2016-09-20에 머지됐어요.

머지 뒤 2016-10-06에 asottile이 "Curious why a new implementation of a docker init system was chosen over other implementations which have tests, many more users"라며 dumb-init과 tini를 들었어요. 테스트와 사용자가 이미 많은 구현을 두고 왜 새로 만들었느냐는 질문이에요. 2016-11-03의 PR #28037은 "There is no reason to duplicate efforts and tini is well built and better than grimes."라며 grimes를 tini로 바꿨어요. 2017-01-18에 나온 Docker 1.13.0의 CHANGELOG에는 "Add boolean flag --init on dockerd and on docker run to use tini a zombie-reaping init process as PID 1"이 들어갔어요. tini README도 Docker 1.13 이상이면 tini가 Docker에 들어 있다고 안내해요.

같은 PR에서 기본값을 두고 의견이 갈렸어요. tianon은 이미지 작성자가 좀비가 생길지 가장 잘 아니 이미지 메타데이터로 기본값을 켜자고 했고 ndeloof도 LABEL io.docker.init='true' 같은 표시를 제안했어요. crosbymichael은 "yes, we will add a dockerfile instruction"이라고 답했어요. 이 지시어가 실제로 생겼는지는 이 글에서 확인하지 않았어요. 반대쪽에서 thaJeztah는 2016-11-15에 이렇게 적었어요.

In cases where a zombie reaper is required (in most cases, it should not even be needed), it should be added by the image author. I think this PR should be seen as a "last effort" if the image is not under control of the user.

→ 좀비를 거둘 init이 필요하면(대부분은 필요조차 없어야 하고) 이미지 작성자가 넣어야 하며, 이 옵션은 사용자가 이미지를 고칠 수 없을 때 쓰는 마지막 수단으로 봐야 한다는 뜻이에요. "런타임이 기본으로 해 줘야 한다"와 "이미지가 책임져야 한다"는 두 입장이 이때부터 나왔고 이 글 끝까지 이어져요.

4. 쿠버네티스는 pause에 좀비 수거만 맡기고 신호 전달은 넣지 않았다

쿠버네티스에도 이미 모든 파드에 PID 1 후보가 하나 있었어요. pause예요. 2016-07-28 dims가 연 PR #29747 "light-weight init that can forward signals and reap zombies"는 dumb-init을 바탕으로 pause를 신호 전달과 좀비 수거를 하는 init으로 만들려 했어요. thockin은 신호를 어디로 보낼지에 대해 "pass the signal on to all of the "root" processes (the first process of each container)"를 제안했어요. 각 컨테이너의 첫 프로세스 모두에게 넘기자는 뜻이에요. dims는 당시 Docker에서 pause의 PID 네임스페이스에 붙은 다른 컨테이너의 고아가 pause 밑으로 오지 않고 PPID 0으로 보인다고 보고했고("They don't end up under the pause process"), thockin은 이를 Docker 버그로 보고 이슈를 열었어요. 이 PR은 머지되지 않고 2016-11-17에 닫혔어요.

#29747이 닫히기 이틀 전인 2016-11-15 verb가 연 PR #36853은 pause에 SIGCHLD 핸들러, 즉 좀비 수거만 넣었어요. 64편에서 본 pause.c의 sigreap이에요. vishh가 신호 전달도 하자고 하자 verb가 이렇게 답했어요.

I'd really like to avoid forwarding signals and other init features which would be better handled by the kubelet.

→ 신호 전달과 다른 init 기능은 pause에 넣지 않고 싶고, 그런 기능은 kubelet이 더 잘 다룬다는 뜻이에요. 이 문장은 kubelet이 신호를 전달한다는 뜻으로도 읽혀서 vishh가 kubelet이 어떻게 신호를 전달하느냐고 되물었어요. verb는 2017-01-14에 "I don't expect the kubelet to forward signals. I meant that init features other than signal handling are better handled by the kubelet."이라고 고쳐 말했어요. kubelet이 신호를 전달하리라 보지는 않고, kubelet이 더 잘 다룬다고 한 것은 신호 처리가 아닌 init 기능이었다는 뜻이에요. 그 예로 "users should rely on the kubelet to start processes in a pod rather than running an init system in the container"를 들었어요. 컨테이너 안에서 init 시스템을 돌리기보다 kubelet이 파드의 프로세스를 띄우는 쪽에 기대라는 뜻이에요. 이 PR은 신호 전달 없이 좀비 수거만 넣은 채 2017-01-20에 머지됐어요.

PID 공유를 1.7에서 기본으로 켰다가 1.8에서 되돌렸다

pause가 좀비를 거두려면 앱이 pause의 PID 네임스페이스에 있어야 해요. 1.7의 PR #45236(2017-05-10 머지)은 Docker 1.13.1 이상에서 파드 안 PID 네임스페이스 공유를 기본으로 켰어요. 릴리스 노트는 이제 kubectl exec {pod} kill 1이 컨테이너 하나가 아니라 파드를 재시작시킨다고 경고했어요.

2017-07-14에 이슈 #48937이 열렸어요. systemd를 PID 1로 띄우는 GlusterFS 이미지가 "Couldn't find an alternative telinit implementation to spawn"으로 뜨지 못했어요. PID 1 자리를 pause가 차지했기 때문이에요. yujuhong은 2017-08-08 "looks like some images have to be run as PID 1"이라고 정리했고 dchen1107은 같은 날 "we need to figure out how to resolve this conflict with shared pid namespace. If we cannot, we have to disable that setting for 1.8"이라고 적었어요. rhatdan은 "running systemd in a container is a critical need for us"라고 했어요. 2017-08-30 verb가 SIG Node 결과로 "we'll disable this by default in 1.8 and revisit for 1.9"를 알렸고 PR #51634(2017-09-06 머지)가 기본값을 되돌렸어요. PR 본문의 이유는 "There exist container images that expect always to be PID 1"이에요.

그 뒤 PID 공유는 파드마다 고르는 필드가 됐어요. KEP-495의 shareProcessNamespace는 1.10 알파, 1.12 베타, 1.17 GA이고 기본값은 false예요. KEP의 Non-Goals에는 "Creating a general purpose container init solution"이 적혀 있어요. 범용 컨테이너 init을 만드는 것은 목표가 아니라는 뜻이에요. 같은 시기 smarterclayton은 이슈 #1615(2017-09-13)에 "we're missing the actual usability improvement, which is the container --init equivalent"라고 적고 "Saying the only way you can get --init is to remove walls between containers may not be sufficient."라고 덧붙였어요. 정말 필요한 것은 컨테이너용 --init이고, 그걸 얻는 유일한 길이 컨테이너 사이의 벽을 허무는 것이어서는 부족하다는 뜻이에요.

📖 용어: shareProcessNamespace
파드 spec에 shareProcessNamespace: true를 쓰면 파드의 모든 컨테이너가 PID 네임스페이스 하나를 같이 써요. 이 네임스페이스의 PID 1은 pause가 되고 앱은 PID 1이 아니게 돼요. 다른 컨테이너의 프로세스가 보이고 신호도 보낼 수 있게 돼요.

우리 실험의 z-share가 이 경우예요. pause가 PID 1이라 고아를 넘겨받았고 SIGCHLD 핸들러로 거둬서 좀비가 0개였어요. 65편의 삭제 실험에서 같은 모양의 g-share는 0.6초에 143으로 끝났어요. 이건 pause가 신호를 넘겨서가 아니에요. 64편의 마스크 실험에서 g-share의 sleep은 PID 6이었어요. containerd는 정지 신호를 그 컨테이너 자신의 첫 프로세스인 sleep에 보냈고, sleep은 이제 어느 네임스페이스의 init도 아니라서 SIGTERM의 기본 동작으로 죽었어요.

그림 4. 쿠버네티스가 준 init은 PID 공유를 켰을 때의 pause뿐이고, pause는 신호를 넘기지 않아요.

⚠️ shareProcessNamespace는 컨테이너 사이의 벽을 허물어요
KEP-495의 Risks and Mitigations는 세 가지를 적어요. 앱이 PID 1이 아니게 되어 kill 1이 pause에게 가고 파드가 재시작될 수 있어요. 다른 컨테이너의 프로세스가 /proc로 보여서 인자나 환경 변수로 넘긴 비밀번호도 보여요. /proc/$pid/root로 다른 컨테이너의 파일시스템도 보여서 비밀은 일반 파일 권한으로만 보호돼요. 좀비 수거를 위해 켤 때는 이 값을 같이 치른다는 것을 알고 켜야 해요.

5. 파드에 init 옵션을 달자는 이슈 #84210은 2019년부터 KEP 없이 열려 있다

2019-10-23 segevfiner가 이슈 #84210 "Support adding an init process to containers"를 열었어요.

Add support for adding an init process (PID 1) to containers started by Kubernetes, across the supported container runtimes. This should be toggled by an appropriate flag on the Container spec. A possible implementation is basically bind mounting a statically built init executable (e.g. tini) into the container and passing the containers entrypoint+cmd to it

→ Container spec의 플래그 하나로 모든 런타임에서 컨테이너에 init을 붙이게 하자는 제안이고, 구현은 정적으로 빌드한 tini 같은 바이너리를 마운트해서 원래 명령을 넘기는 방식, 즉 Docker의 --init과 같은 방식을 예로 들었어요. 이유로는 잘못 만든 이미지가 많고 사용자가 자기 이미지로 작업을 제출하는 시스템처럼 이미지에 init을 넣으라고 요구하기 어려운 경우를 들었어요.

찬성 코멘트는 대부분 같은 수고를 말해요. arnaudlacour는 2021-04-08 "We add tini to our images for this reason even it's now embedded in Docker. I greatly dislike the redundancy but it's needed currently for k8s deployment."라고 적었어요. Docker에는 들어 있는데도 쿠버네티스 배포 때문에 이미지마다 tini를 넣고 있다는 뜻이에요. BlaineEXE는 2024-05-21 복잡한 bash 스크립트를 liveness 프로브로 쓸 때 좀비가 남는 문제를 들며 "Being able to use an init: true boolean without enabling PID sharing would be great."라고 했어요. 2021-06-24에는 triage/accepted와 priority/important-longterm 라벨이 붙었어요.

진전이 없던 이유는 리뷰어의 코멘트에 보여요. liggitt는 2022-09-12 "this is unlikely to make progress as an issue. A proposal that works through the design along with the implications of such a change can be opened as a KEP"라고 적었어요. 이슈로는 진전이 어렵고 설계와 영향을 정리한 KEP가 필요하다는 뜻이에요. 2022-11-24에는 "I have similar concerns around making init process part of the declarative spec"라고 다시 적었어요. sanmai-NL은 "The init executable should be specified by the image builder"라며 spec 필드로 바이너리를 집어넣는 것이 불변 이미지를 선언하는 Container spec과 어울리지 않는다고 반대했고, redbaron은 "defaults matter, too many devs are not aware of signal handling"이라고 맞섰어요. 2016년 Docker PR의 두 입장이 그대로 다시 나왔어요.

hholst80은 shareProcessNamespace: true를 넣으면 된다고 했고 segevfiner는 "This has other side effects though. Much more likely to break stuff than just injecting an init process."라고 답했어요. 2026-11-15 현재 이 이슈는 열려 있고 라벨은 needs-triage로 돌아가 있어요. 2023년부터 코멘트는 대부분 오래된 이슈 표시를 떼는 /remove-lifecycle stale 명령이에요. kubernetes/kubernetes와 kubernetes/enhancements를 "init process", "tini", "zombie"로 찾았을 때 관련 KEP는 없었어요. SIG Node 회의록 같은 다른 곳의 논의는 찾지 않았어요.

💡 실무에서는 셋 중 하나를 고른다
• 앱이 직접 처리한다. 자식을 만들지 않는 앱이면 SIGTERM 핸들러만 있으면 돼요. 자식을 만드는 앱이면 고아까지 거두는 코드가 있는지 확인해야 해요.
• 이미지에 tini를 넣는다. 빌드 러너, 스크립트를 실행하는 프로브, 셸 스크립트 진입점처럼 손자 프로세스가 생기는 이미지에 맞아요. ENTRYPOINT를 ["tini", "--", "앱"]으로 두고, 자식이 셸이라 그 아래까지 신호를 보내야 하면 -g를 줘요. 이미지를 고칠 수 없으면 이 글의 실험처럼 init 컨테이너로 tini를 emptyDir에 복사해 command 앞에 붙일 수 있어요.
• shareProcessNamespace를 켠다. pause가 좀비를 거두고 앱은 PID 1이 아니게 돼서 SIGTERM의 기본 동작도 살아나요. 대신 위 경고의 격리 비용을 치르고 pause는 신호를 넘기지 않아요.

✍️ 오늘의 요약

컨테이너 안에서 부모를 잃은 프로세스는 커널 규칙(exit.c find_new_reaper)에 따라 그 PID 네임스페이스의 PID 1에게 가요. PID 1이 sleep이면 거두지 않아서 exec 20번에 좀비 20개, pids.current 3 → 23이 됐고 tini나 pause가 PID 1이면 0개였어요. tini는 핸들러 없이 신호를 막아 두고 sigtimedwait로 꺼내 자식에게 넘기고, waitpid(-1)로 고아까지 거둬요.

Docker는 2016년 #26061(grimes)과 #28037(tini)로 1.13.0(2017-01-18)에 --init을 넣었지만 하위 호환 때문에 기본은 껐어요. 쿠버네티스는 pause를 신호 전달 init으로 만드는 #29747을 머지하지 않았고 #36853으로 좀비 수거만 넣었어요. 1.7의 PID 공유 기본값은 systemd 이미지를 깨서(#48937) 1.8에서 되돌렸고 shareProcessNamespace라는 파드 옵션으로 남았어요.

파드에 init 플래그를 달자는 #84210은 2019년부터 열려 있고 KEP는 없어요. 지금 쿠버네티스에서 PID 1의 책임은 앱이나 이미지 작성자에게 있으니, 자식을 만드는 이미지라면 tini를 넣거나 격리 비용을 알고 PID 공유를 켜야 해요.
