15시 17분, 실습용 Secret 하나를 만들고 kubectl로 값을 읽었어요. kubectl get secret ssot-demo -o jsonpath='{.data.password}'로 받은 값은 aGVsbG8tc3NvdA==였어요. 알아보기 힘든 문자열이라 암호화된 값으로 보기 쉽지만 이 값은 base64로 바꿔 적은 것뿐이에요. 같은 Secret을 etcd에서 직접 꺼내 보니 바이트 사이에 제가 넣은 hello-ssot가 그대로 들어 있었어요.

1. 클러스터 상태의 원본은 etcd 하나이고 etcd에 붙는 것은 API 서버뿐이다

📖 용어: 단일 진실 공급원 (SSOT, Single Source of Truth)
같은 정보의 원본을 한 곳에만 두고 나머지는 모두 그 원본을 따르게 하는 설계예요. 쿠버네티스에서는 "어떤 객체가 있고 각 객체의 spec과 status가 무엇인지"의 원본이 etcd예요. 컨트롤러, 스케줄러, kubelet이 들고 있는 값은 API 서버에서 watch로 받아 둔 사본이에요.

원본이 한 곳뿐이라는 점은 etcd에 닿는 길이 하나뿐이라는 데서도 드러나요. 19편에서 마스터의 TCP 연결을 프로세스별로 셌을 때 etcd의 2379 포트에 붙어 있던 것은 kube-apiserver뿐이었어요.

# 19-hub-and-authz.txt 에서 마스터 쪽 일부 (16:05, ss 로 센 ESTABLISHED 연결) etcd :2379 ← 받는 쪽 연결 92개 kube-apiserver → :2379 연결 92개 kube-controller → :6443 연결 2개 kube-scheduler → :6443 연결 2개 kubelet → :6443 연결 1개

→ etcd가 받은 연결 92개는 모두 kube-apiserver가 건 것이고 컨트롤러 매니저, 스케줄러, kubelet은 API 서버(6443)에만 붙어 있다는 뜻이에요.

그래서 20편에서 API 서버를 30초 멈췄다가 되돌렸을 때도 잃은 것이 없었어요. 상태는 etcd에 그대로 있었고 다시 뜬 API 서버는 그 상태를 읽어 9일 된 노드 넷을 다시 보여 줬어요. 이렇게 만든 이유는 1·2편에서도 인용한 etcd 운영 문서의 문장에 있어요. etcd에 접근하는 것은 클러스터의 root 권한을 갖는 것과 같으니 이상적으로는 API 서버만 접근해야 한다고 적혀 있어요.

그렇다면 다른 프로그램은 정말 etcd에 붙을 수 없을까요? 글을 쓰며 etcd의 설정과 인증서를 다시 확인했어요.

그림 1. etcd는 노드 IP에서도 연결을 받지만 etcd CA가 서명한 클라이언트 인증서가 없으면 TLS 단계에서 연결을 끊는다

etcd는 127.0.0.1:2379뿐 아니라 노드 IP인 192.168.104.1:2379에서도 연결을 받아요. 대신 --client-cert-auth=true와 --trusted-ca-file=/etc/kubernetes/pki/etcd/ca.crt가 설정돼 있어서 etcd CA가 서명한 클라이언트 인증서를 내야 붙을 수 있어요. worker1에서 인증서 없이 curl을 보내 보니 TLS 단계에서 "alert certificate required"로 끊겼고 curl은 종료 코드 56으로 끝났어요. worker1의 /etc/kubernetes/pki에는 클러스터 CA 인증서(ca.crt) 하나뿐이라 etcd에 낼 인증서가 없어요.

API 서버는 --etcd-certfile=/etc/kubernetes/pki/apiserver-etcd-client.crt에 적힌 인증서로 etcd에 붙어요. 이 인증서의 주체는 kube-apiserver-etcd-client이고 발급자는 etcd-ca이며 클라이언트 인증 용도로만 쓸 수 있어요. 5편에서 본 kubeadm의 인증서 묶음 가운데 하나예요. etcd에 직접 붙을 수 있는 것은 etcd CA가 서명한 인증서를 가진 쪽뿐이고 이 클러스터에서 그 연결을 실제로 쓰는 것은 API 서버뿐이었어요. Calico도 DATASTORE_TYPE=kubernetes라서 etcd가 아니라 API 서버에 데이터를 저장해요(1편).

2. etcd 파드 안의 etcdctl로 etcd 상태를 열어 봤다

etcd를 들여다볼 도구는 etcd 파드 안에 이미 있어요. etcd 이미지에 etcdctl이 들어 있어서 kubectl exec으로 파드 안에서 실행하면 따로 설치할 것이 없어요. 15시 17분에 실행한 명령은 이랬어요.

mac$ kubectl -n kube-system exec etcd-k8s-master -- etcdctl \ --endpoints=https://127.0.0.1:2379 \ --cacert=/etc/kubernetes/pki/etcd/ca.crt \ --cert=/etc/kubernetes/pki/etcd/server.crt \ --key=/etc/kubernetes/pki/etcd/server.key \ endpoint status -w table

→ etcd 파드 안에서 자기 자신(127.0.0.1:2379)에 붙되 etcd CA로 서버를 확인하고 etcd의 server.crt를 클라이언트 인증서로 내라는 뜻이에요.

📖 용어: etcdctl
etcd에 붙어 키를 읽고 쓰고 상태를 보고 스냅숏을 뜨는 명령줄 도구예요. kubectl이 API 서버의 객체를 다룬다면 etcdctl은 그 아래 etcd의 키와 값을 그대로 다뤄요. 그래서 인증, 인가, 어드미션 같은 API 서버의 확인을 하나도 거치지 않아요.

여기서 쓴 인증서는 API 서버의 것이 아니라 etcd 서버 자신의 인증서(server.crt)예요. 그림 1의 3번을 보면 이 인증서는 CN이 k8s-master이고 발급자가 같은 etcd-ca이며 서버 인증과 클라이언트 인증에 함께 쓰도록 만들어져 있어서 클라이언트 인증서로도 쓸 수 있어요. 거꾸로 말하면 kube-system의 etcd 파드에 exec할 수 있는 사람은 etcd 전체를 읽고 쓸 수 있다는 뜻이기도 해요. 2편의 주의대로 이번에도 읽기만 했어요.

# 22-etcd-ssot.txt 의 endpoint status 표에서 열 일부 (15:17:20) ENDPOINT VERSION DB SIZE IN USE PERCENTAGE NOT IN USE QUOTA IS LEADER RAFT TERM RAFT INDEX https://127.0.0.1:2379 3.7.0 22 MB 3.2 MB 86% 2.1 GB true 9 143152

→ 버전은 etcd 3.7.0이에요. 데이터 파일은 22 MB인데 그중 실제로 쓰는 공간은 3.2 MB이고 쓰지 않는 공간이 86%예요. 용량 한도는 2.1 GB이고 이 멤버가 리더라는 뜻이에요. 멤버가 하나뿐이라 자기 자신이 리더예요.

DB SIZE와 IN USE가 크게 다른 이유는 etcd가 값을 덮어쓰지 않고 바뀔 때마다 새 리비전으로 쌓기 때문이에요.

📖 용어: 리비전과 MVCC
etcd는 키 공간이 바뀔 때마다 1씩 오르는 클러스터 전체 카운터(리비전)를 두고 바뀐 내용을 그 리비전 번호로 저장해요. 옛 값도 한동안 남겨 두는 이 방식을 MVCC(다중 버전 동시성 제어)라고 불러요. 쌓인 옛 리비전을 지우는 일을 컴팩션(compaction), 지운 자리를 파일 시스템에 돌려주는 일을 조각 모음(defragmentation)이라고 해요.

API 서버는 기본으로 5분마다 etcd에 컴팩션을 요청해요. kube-apiserver 문서에 따르면 --etcd-compaction-interval의 기본값은 5m0s이고 우리 API 서버에는 이 플래그가 따로 없었어요(그림 1의 2번에 --etcd로 시작하는 플래그가 모두 나와 있어요). 그런데 etcd 유지보수 문서에 따르면 컴팩션으로 옛 리비전을 지워도 데이터 파일 안에 빈자리가 생길 뿐 디스크 공간은 돌아오지 않고 조각 모음을 해야 돌아와요. DB SIZE 22 MB 가운데 쓰지 않는 86%가 바로 그 빈자리예요.

QUOTA 2.1 GB는 etcd의 저장 용량 한도예요. 우리 etcd에는 --quota-backend-bytes 플래그가 없었고(그림 1의 1번) etcd FAQ는 이 한도의 기본값을 2GB라고 적어요. 같은 문서와 유지보수 문서에 따르면 데이터가 한도를 넘으면 etcd가 클러스터 전체에 경보를 걸고 읽기와 삭제만 받는 유지보수 모드로 들어가요. 쓰기 요청에는 mvcc: database space exceeded 오류가 돌아가요. etcd가 쓰기를 받지 않으면 API 서버도 아무것도 저장하지 못하니 20편에서 본 "변경이 멈춘 상태"가 돼요.

💡 실무에서는: etcd 용량은 두 숫자를 같이 봐요
• etcdctl endpoint status -w table의 DB SIZE가 QUOTA에 가까워지는지 봐요. 한도에 닿으면 클러스터의 모든 변경이 멈춰요
• DB SIZE는 큰데 IN USE가 작으면 지운 자리가 많다는 뜻이에요. 유지보수 문서에 따르면 조각 모음(etcdctl defrag)이 그 공간을 돌려주는데 그 작업이 도는 동안 그 멤버는 읽기와 쓰기를 막아요. 멤버가 여럿이면 하나씩 해요
• 이벤트가 많이 쌓이는 클러스터일수록 키 공간이 빨리 커져요. 3절에서 보듯 우리 클러스터도 키의 약 43%가 이벤트였어요

3. 객체 하나가 /registry 아래 키 하나가 된다

그림 2. /registry 아래 키는 856개였고 myweb 하나가 키 열 개로 나뉘어 있었다

etcdctl get /registry --prefix --keys-only로 /registry 아래 키 이름만 모두 꺼냈더니 856개였어요. 쿠버네티스 객체는 대부분 /registry/<리소스>/<네임스페이스>/<이름> 모양의 키 하나로 들어가요. myweb Deployment라면 /registry/deployments/default/myweb인 식이에요. 네임스페이스가 없는 클러스터 범위 객체는 그 칸이 빠지고 CRD로 만든 객체는 리소스 앞에 그룹 이름이 붙어요. Calico의 IP 풀은 /registry/crd.projectcalico.org/ippools/default-ipv4-ippool이었어요. Service는 조금 달라서 /registry/services/specs/…와 /registry/services/endpoints/… 두 갈래로 나뉘어요.

그림 3. etcd에서 가장 많은 키는 이벤트였고 그다음은 RBAC 객체였다

키 이름의 세 번째 칸(리소스 이름이나 그룹 이름)으로 세면 events가 366개로 856개의 약 43%였어요. 이벤트도 API 객체라서 etcd에 키로 저장되고 8편에서 본 대로 기본 1시간이 지나면 지워져요. 그다음이 RBAC 객체인 clusterroles 82개와 clusterrolebindings 72개, 그리고 serviceaccounts 58개였어요. crd.projectcalico.org 40개는 Calico가 저장한 객체이고 apiextensions.k8s.io 23개는 20편에서 센 CRD 정의 23개와 같은 수예요. pods 32개는 21편에서 한 시간 뒤에 센 전체 파드 수 32개와 같았어요. services 18개는 specs와 endpoints 두 갈래를 함께 센 값이에요.

myweb 하나에 딸린 키는 이벤트 55개를 빼고 열 개였어요. deployments 1, replicasets 1, pods 5, services/specs 1, services/endpoints 1, endpointslices 1이에요. 2편에서 Deployment hello 하나가 키 여섯 개가 된 것과 같은 구조이고 replicas가 5라서 pods 키만 다섯 개로 늘었어요. 그 가운데 제가 직접 만든 것은 deployments와 services/specs 둘이고 나머지는 컨트롤러가 API 서버에 요청해서 생긴 키예요(2편). kubectl get으로 보는 객체 하나하나가 etcd의 키 하나였고 "Deployment 하나"는 etcd에서 키 열 개였어요.

4. resourceVersion은 etcd의 mod_revision이고 동시에 고치는 것을 막는다

그림 4. kubectl이 보여 준 resourceVersion과 etcd 키의 mod_revision은 세 번 모두 같은 숫자였다

kubectl로 본 Deployment myweb의 resourceVersion과 etcd의 /registry/deployments/default/myweb 키의 mod_revision을 나란히 찍었어요. 처음에는 둘 다 103241, replicas를 6으로 바꾸고 2초 뒤에는 둘 다 103287, 5로 되돌리고 2초 뒤에는 둘 다 103310이었어요. 세 번 모두 같은 숫자였어요.

이 일치는 우연이 아니에요. 쿠버네티스 커뮤니티의 API 규약 문서에는 resourceVersion이 지금은 etcd의 mod_revision으로 구현돼 있다고 적혀 있어요. 같은 문단은 애플리케이션이 이 구현 세부에 기대면 안 되고 앞으로 타임스탬프나 객체별 카운터로 바뀔 수도 있다고 덧붙여요. API 개념 문서도 resourceVersion은 받은 그대로 서버에 돌려줘야 하는 값이라고 해요. v1.35부터는 같은 리소스 종류 안에서 resourceVersion을 정수로 크기 비교할 수 있어야 한다는 것이 적합성 인증 요건에 들어갔다는 설명도 있어요.

숫자가 1이 아니라 46과 23씩 뛴 이유는 etcd의 리비전이 키마다 따로 있지 않고 클러스터 전체에 하나뿐이기 때문이에요. etcd API 문서에 따르면 etcd는 키 공간이 바뀔 때마다 1씩 오르는 64비트 카운터를 두고 mod_revision은 그 키가 마지막으로 바뀐 리비전이에요. replicas를 바꾸면 ReplicaSet과 파드, 이벤트, EndpointSlice 같은 다른 키도 함께 바뀌니 그 사이 리비전이 그만큼 오른 거예요. Deployment 키 자체도 spec이 바뀐 뒤 컨트롤러가 status를 고쳐 쓰면서 여러 번 바뀌었을 수 있고 그 가운데 마지막 리비전이 보인 거예요.

📖 용어: 낙관적 동시성 제어 (optimistic concurrency)
여럿이 같은 객체를 고칠 때 미리 잠그지 않고 "내가 읽은 뒤로 아무도 안 바꿨으면 저장하고 바뀌었으면 거절하라"는 조건을 붙여 쓰는 방식이에요. API 규약 문서는 쿠버네티스가 resourceVersion으로 낙관적 동시성을 구현한다고 적어요. 조건이 맞지 않으면 API 서버는 409 Conflict로 거절해요.

resourceVersion이 실제로 무엇을 막는지 w22 네임스페이스에서 확인했어요. ConfigMap 하나를 만들고 사용자 A와 B가 같은 버전을 읽어 둔 뒤 차례로 고쳐 쓰게 했어요.

그림 5. 같은 버전을 들고 늦게 쓴 B는 409를 받았고 버전을 지우고 다시 보내자 A의 변경을 덮어썼다
그림 6. resourceVersion을 들고 쓰면 늦은 쓰기가 거절되고 버전을 빼면 앞선 변경이 조용히 사라진다

A는 117049를 들고 v=2로 바꿔 replace했고 그대로 저장됐어요. resourceVersion과 mod_revision은 117050이 됐고 etcd의 version(이 키가 바뀐 횟수)은 2가 됐어요. B는 같은 117049를 들고 v=3으로 replace했는데 API 서버가 "Operation cannot be fulfilled on configmaps "occ-demo": the object has been modified; please apply your changes to the latest version and try again"이라는 오류로 거절했어요. 값은 A가 쓴 v=2 그대로였어요. API 개념 문서에 적힌 대로 PUT 요청에 담긴 resourceVersion이 이미 낡았으면 API 서버가 409 Conflict로 응답해서 변경이 유실되는 것을 막은 거예요.

그림의 마지막 줄이 더 중요해요. B가 b.json에서 resourceVersion을 지우고 다시 보내자 이번에는 replaced가 나왔고 값은 v=3이 됐어요. 비교할 버전이 없으니 조건 없이 덮어쓴 거예요. A의 v=2는 아무 경고 없이 사라졌어요. 같은 문서에는 PUT 요청에 resourceVersion을 채우는 일이 클라이언트 책임이라고 적혀 있어요. 이번에는 리비전이 117049, 117050, 117051로 1씩만 올랐어요. 1초 남짓한 사이에 다른 키가 바뀌지 않았다는 뜻이에요.

💡 실무에서는: "the object has been modified"를 만나면
• 최신 객체를 다시 읽고 그 위에 내 변경을 다시 적용해서 보내요. 오류 메시지가 하라는 그대로예요
• 저장되게 하려고 resourceVersion을 지우고 보내지 마세요. 그림 5의 마지막 실행과 같이 남의 변경을 덮어써요
• 직접 짠 컨트롤러나 스크립트가 읽고 고치고 쓰는 일을 한다면 409를 받았을 때 다시 읽고 다시 시도하는 처리를 넣어요. API 개념 문서도 조건부 요청을 쓰는 클라이언트는 충돌이 나면 재시도를 처리하라고 해요

5. Deployment는 protobuf, CRD는 JSON, Secret은 평문으로 들어 있다

그림 7. 기본 리소스는 k8s\x00으로 시작하는 protobuf, CRD는 JSON이었고 Secret 값은 평문이었다

Deployment myweb 키의 값은 k8s\x00 네 바이트로 시작했어요. API 개념 문서의 Protobuf 인코딩 절에 따르면 쿠버네티스는 protobuf 데이터를 감싸는 봉투의 맨 앞에 이 4바이트 매직 넘버를 붙여 디스크나 etcd에 있는 내용이 JSON이 아니라 protobuf임을 알아보게 해요. 그 뒤에 apiVersion과 kind를 담은 typeMeta가 오고 객체 본문이 따라와요. 출력에 보이는 apps/v1과 Deploym(ent)이 그 typeMeta예요.

📖 용어: protobuf
Protocol Buffers의 줄임말로 필드 번호와 길이를 앞에 붙여 데이터를 바이너리로 적는 형식이에요. JSON보다 작고 빠르게 읽고 쓸 수 있지만 사람이 그대로 읽기는 어려워요. 다만 문자열 값은 바이트 사이에 원래 글자 그대로 들어가요.

Calico의 IPPool은 {"apiVersion":"crd.projectcalico.org/v1","kind":"IPPool",...로 시작하는 JSON 그대로였어요. 같은 문서에 CustomResourceDefinition으로 정의한 리소스에는 Kubernetes protobuf 인코딩을 쓸 수 없다고 적혀 있어요. 그래서 CRD 객체는 JSON으로 저장돼요.

이제 Secret이에요. 먼저 API 서버 설정에서 --encryption-provider-config 플래그를 찾아 세어 보니 0개였어요. 저장 데이터 암호화 문서는 이 플래그 없이 kube-apiserver를 돌리면 저장 시 암호화(encryption at rest)가 켜져 있지 않은 것이고 API 서버는 기본으로 리소스를 평문 표현 그대로 etcd에 저장한다고 적어요.

그 상태에서 password=hello-ssot인 Secret ssot-demo를 만들었어요. kubectl이 보여 준 data.password는 aGVsbG8tc3NvdA==였고 이 문자열을 base64로 풀면 hello-ssot예요. Secret 문서에는 data 필드의 값이 base64로 인코딩된 문자열이어야 한다고 적혀 있어요. 레지스트리 인증 정보를 담은 Secret 예시의 주의 문구는 base64로 적은 auth 값을 두고 "가려져 있을 뿐 비밀은 아니다(obscured but not secret)"라고 해요. base64는 누구나 되돌릴 수 있는 인코딩이에요.

etcd에서 꺼낸 값에는 그 base64조차 없었어요. \n\x08password\x12\nhello-ssot는 protobuf로 적은 키·값 한 쌍이에요. \n(0x0a)은 1번 필드라는 표시이고 \x08은 길이 8이라서 password 여덟 글자가 이어져요. \x12는 2번 필드라는 표시이고 그다음 \n(0x0a)은 길이 10이라서 hello-ssot 열 글자가 이어져요. kubectl에서는 base64로 보이던 Secret이 etcd에는 원래 글자 그대로 들어 있었어요. 실습용 Secret은 바로 지웠고 지운 뒤 etcd에서 같은 키를 찾아보니 0개였어요.

그림 8. 같은 Secret이 kubectl에서는 base64, 지금 etcd에서는 평문으로 보이고 암호화를 켜야 etcd에서 암호문이 된다
⚠️ 주의: Secret을 읽을 수 있는 길은 생각보다 많아요
• Secret 문서의 주의 문구에 따르면 Secret은 기본으로 etcd에 암호화되지 않은 채 저장되고 API에 접근할 수 있는 사람과 etcd에 접근할 수 있는 사람은 누구나 Secret을 읽거나 바꿀 수 있어요
• 같은 문구는 어떤 네임스페이스에 파드를 만들 권한이 있으면 그 네임스페이스의 Secret을 모두 읽을 수 있다고 해요. Deployment를 만들 권한 같은 간접적인 권한도 포함돼요
• 그래서 문서는 최소한 저장 데이터 암호화 켜기, Secret RBAC을 최소 권한으로 정하기, Secret을 쓸 컨테이너 제한하기, 외부 Secret 저장소 고려하기를 권해요

6. etcd 백업은 클러스터 백업이고 그 파일도 Secret만큼 지켜야 한다

상태의 원본이 etcd 하나뿐이라는 말은 etcd를 잃으면 클러스터 상태를 잃는다는 뜻이기도 해요. etcd 운영 문서의 백업 절은 이렇게 시작해요. 모든 쿠버네티스 객체는 etcd에 저장되고 컨트롤 플레인 노드를 모두 잃는 재해에서 클러스터를 되살리려면 etcd 데이터를 주기적으로 백업하는 것이 중요하다고 해요. 스냅숏 파일에는 쿠버네티스의 모든 상태와 중요한 정보가 들어 있으니 민감한 데이터를 지키려면 스냅숏 파일을 암호화하라는 말이 이어져요.

📖 용어: etcd 스냅숏
특정 시점의 etcd 키 공간 전체를 파일 하나로 뜬 것이에요. etcd 운영 문서에 따르면 살아 있는 멤버에서 etcdctl snapshot save로 뜨거나 etcd 프로세스가 쓰지 않는 데이터 디렉터리의 member/snap/db 파일을 복사해서 만들어요. 스냅숏을 뜨는 동안에도 멤버의 성능에는 영향을 주지 않아요.
# etcd 운영 문서의 예시 형식 (인증서 경로는 이 클러스터의 etcd 파드 기준) ETCDCTL_API=3 etcdctl --endpoints=https://127.0.0.1:2379 \ --cacert=/etc/kubernetes/pki/etcd/ca.crt --cert=<인증서> --key=<키> \ snapshot save <백업 파일 위치> # 뜬 스냅숏 확인 etcdutl --write-out=table snapshot status <백업 파일>

→ 2절에서 쓴 것과 같은 방식으로 etcd에 붙어 키 공간 전체를 파일 하나로 뜨고 그 파일의 해시, 리비전, 키 개수, 크기를 표로 확인한다는 뜻이에요. 이 형식으로 실제로 뜬 스냅숏은 조금 뒤에 열어 봐요.

되살릴 때는 순서가 정해져 있어요. 같은 문서의 주의 문구에 따르면 API 서버가 떠 있는 동안에는 etcd를 복원하면 안 되고 모든 API 서버를 멈추고 모든 etcd 인스턴스를 복원한 뒤 API 서버를 다시 켜야 해요. kube-scheduler, kube-controller-manager, kubelet도 다시 시작해 옛 데이터에 기대지 않게 하라고 권해요. 그리고 etcd 스냅숏에 들어 있는 것은 API 객체예요. 파드가 볼륨에 쓴 데이터는 etcd에 없으니 따로 백업해야 해요.

5절에서 본 대로 이 클러스터의 etcd에는 Secret이 평문으로 들어 있어요. 그러면 etcd의 데이터 파일과 스냅숏 파일도 Secret 원문을 담은 파일이에요. 마스터의 데이터 디렉터리를 확인하니 /var/lib/etcd와 그 아래 member, snap 폴더는 drwx------ root, 실제 데이터 파일 member/snap/db는 -rw------- root였어요(그림 1과 같은 스크립트 출력의 5번). root만 읽을 수 있게 돼 있어요. 백업 파일을 다른 곳에 옮기는 순간 이 권한은 따라가지 않아요.

실제로 뜬 스냅숏에도 Secret이 평문으로 들어 있었다

스냅숏 파일에 정말 Secret 원문이 들어가는지 보려고 17시 20분에 스냅숏을 실제로 떠 봤어요. 먼저 암호화 설정이 없는 상태에서 password=plain-before인 Secret enc-before를 만들었어요. etcd에 저장된 값은 5절과 같이 k8s\x00 다음에 v1과 Secret이 이어지는 protobuf였고 그 안에 plain-before가 평문으로 들어 있었어요. 그 상태에서 etcdctl snapshot save로 스냅숏 파일을 떴어요.

그림 9. 스냅숏 파일 안에도 plain-before가 그대로 있었고 파일 권한은 root 전용이었다

etcdutl로 본 스냅숏은 리비전 120464, 키 573개, 크기 22 MB였어요. 키 수는 etcdutl이 센 전체 키 수라서 약 2시간 전에 3절에서 /registry 아래를 센 856개와는 세는 방식도 시각도 달라요. 이 파일에서 plain-before를 찾으니 한 줄이 나왔어요. 파일 권한은 -rw------- root였지만 이 권한은 파일이 마스터의 그 자리에 있을 때만 해당해요. 다른 서버나 저장소로 복사하면 권한은 옮겨 간 곳의 설정을 따르지만 내용은 그대로 옮겨 가요. Secret을 암호화하지 않은 클러스터라면 etcd 백업 파일에 그 클러스터 Secret의 원문이 모두 들어 있어요. etcd 운영 문서가 스냅숏 파일을 암호화하라고 한 이유가 여기 있어요. 확인한 스냅숏 파일은 바로 지웠어요.

etcd 쪽에서 Secret을 지키려면 저장 데이터 암호화를 켜요. 저장 데이터 암호화 문서의 순서는 이래요. EncryptionConfiguration 파일에 암호화할 리소스(secrets 등)와 공급자를 적고 kube-apiserver에 --encryption-provider-config로 그 파일을 넘겨요. 새로 쓰는 데이터는 목록의 첫 공급자로 암호화하니 이미 저장된 Secret은 kubectl get secrets --all-namespaces -o json | kubectl replace -f -로 한 번씩 다시 써야 암호화돼요. 확인하는 방법은 이 글에서 한 것과 같아요. etcdctl로 Secret 키를 꺼냈을 때 값이 k8s:enc:aescbc:v1: 같은 접두어로 시작하면 암호화된 거예요.

📖 용어: 저장 데이터 암호화 (encryption at rest)와 공급자
API 서버가 etcd에 쓰기 직전에 리소스를 암호화하고 읽은 직후에 복호화하는 기능이에요. 어떤 방식으로 암호화할지를 공급자(provider)로 고르고 기본값인 identity는 암호화를 하지 않아요. 문서의 표에 따르면 aescbc는 패딩 오라클 공격에 약해 권하지 않고 aesgcm은 쓰기 20만 번마다 키를 바꿔야 해요. kms v2는 외부 키 관리 도구를 쓸 때 좋은 선택이라고 해요.

문서는 한계도 분명히 적어요. 키를 로컬 파일(EncryptionConfiguration)에 두는 방식은 etcd가 털리는 것은 막지만 호스트가 털리는 것은 막지 못한다고 해요. 키가 그 호스트의 파일에 있기 때문이에요. KMS 공급자를 쓰면 데이터 키를 외부 키 관리 서비스의 키로 한 번 더 감싸서 공격자가 etcd와 KMS를 모두 뚫어야 평문을 얻어요. 실습 클러스터에서는 문서의 순서대로 잠깐 켰다가 다시 껐어요.

암호화를 켜면 새로 쓰는 Secret부터 암호문이 된다

설정은 저장 데이터 암호화 문서의 예시를 따랐어요. EncryptionConfiguration에는 secrets 리소스의 공급자로 aescbc 키(key1) 하나를 먼저 적고 그 뒤에 identity를 두었어요. 문서 예시에는 identity가 암호화되지 않은 Secret도 읽을 수 있게 하는 대비책이라고 적혀 있어요. kube-apiserver 매니페스트에는 --encryption-provider-config=/etc/kubernetes/enc/enc.yaml 플래그와 그 폴더를 API 서버 컨테이너에 읽기 전용으로 마운트하는 볼륨을 더했어요. 경로도 문서 예시와 같아요. 키 값은 글에도 원자료에도 남기지 않았어요. 문서는 이 설정 파일에 etcd의 내용을 풀 수 있는 키가 들어 있으니 kube-apiserver를 실행하는 사용자만 읽을 수 있게 권한을 제한하라고 주의를 줘요.

aescbc를 고른 것은 문서의 예시와 확인 방법이 모두 aescbc라서 결과를 견주기 쉬웠기 때문이에요. 앞의 용어 박스에 적은 대로 문서의 공급자 표는 aescbc를 패딩 오라클 공격에 약하다며 권하지 않아요. 이번 설정은 동작을 확인하려는 실험용이었고 실제로 켤 때는 그 표를 보고 공급자를 골라야 해요.

그림 10. 매니페스트에 플래그와 볼륨을 더하자 kubelet이 API 서버를 새로 띄웠고 약 41초 뒤에 다시 응답했다

매니페스트를 저장한 17:20:18부터 /readyz에서 ok가 돌아온 17:20:59까지 약 41초가 걸려서야 API 서버가 다시 응답했어요. 2초 간격으로 /readyz를 물어서 잰 값이라, 옛 API 서버가 언제 내려갔는지까지는 재지 않았어요. 정적 파드 매니페스트가 바뀌면 kubelet이 그 파드를 새로 띄우기 때문이에요(20편). 그동안은 클러스터를 바꿀 수 없었어요. 컨트롤 플레인이 여러 대라면 문서의 안내대로 API 서버마다 차례로 바꾸고 모든 컨트롤 플레인 노드의 암호화 설정을 같게 맞춰요.

그림 11. 켠 뒤에 만든 Secret만 처음부터 암호문이었고 켜기 전에 만든 Secret은 다시 써야 암호문이 됐다. 되돌린 뒤 암호문은 0개였다

암호화를 켠 뒤에 password=hello-enc인 Secret enc-after를 만들었더니 etcd에 저장된 값이 k8s:enc:aescbc:v1:key1:로 시작했고 hello-enc라는 글자는 없었어요. 문서가 확인 방법으로 든 접두어 그대로예요. 그런데 켜기 전에 만든 enc-before는 여전히 k8s\x00으로 시작하는 평문이었어요. 암호화는 새로 쓰는 데이터에만 적용되기 때문이에요. kubectl로 읽으면 둘 다 원래 값(hello-enc, plain-before)이 나왔어요. API 서버가 etcd에서 읽을 때 풀어서 응답하니 kubectl 쪽에서는 차이가 보이지 않아요.

문서의 명령대로 kubectl get secret enc-before -o json | kubectl replace -f -로 enc-before를 같은 내용으로 다시 쓰자 etcd에 저장된 값도 k8s:enc:aescbc:v1:key1:로 시작하게 바뀌었고 평문이 사라졌어요. 이때 /registry/secrets 아래 값 5개 가운데 암호문은 실습용 Secret 2개뿐이었어요. 암호화를 켜는 것만으로는 이미 저장된 Secret이 바뀌지 않고 한 번씩 다시 써야 암호문이 돼요.

되돌릴 때도 문서의 해제 순서를 따랐어요. 실습용 Secret 두 개를 지운 뒤 providers에서 identity를 맨 앞으로 옮기고 API 서버를 다시 띄웠어요. 그다음 kubectl get secrets -A -o json | kubectl replace -f -로 모든 Secret을 다시 써서 암호문을 평문으로 되돌렸어요. 남은 Secret 3개 가운데 암호문이 0개인 것을 확인한 뒤에야 매니페스트를 원래대로 돌리고 키 파일을 지웠어요. 순서를 거꾸로 해서 설정과 키부터 지우면 etcd에 남은 암호문을 풀 수 없어요. 문서도 키가 바뀌어 풀 수 없게 된 리소스가 있으면 올바른 키를 되찾거나 etcd에서 직접 지우기 전까지 그 리소스를 읽는 API 요청이 모두 실패한다고 경고해요. 17시 22분 이후 다시 확인했을 때 매니페스트, 실행 중인 kube-apiserver 프로세스 인자, 미러 파드 어디에도 암호화 설정이 없었고 /readyz는 ok였어요.

💡 실무에서는: etcd를 지키는 체크리스트
• etcd 스냅숏을 주기적으로 뜨고 스냅숏 파일을 암호화해서 클러스터 밖에 보관해요. 복원 연습도 한 번은 해 봐요
• /var/lib/etcd와 백업 파일은 Secret 원문이 든 파일로 다뤄요. 권한, 보관 위치, 접근 기록을 Secret과 같은 수준으로 관리해요
• etcd 인증서와 키(/etc/kubernetes/pki/etcd/*)를 가진 사람, kube-system의 etcd 파드에 exec할 수 있는 사람은 etcd에 직접 붙을 수 있어요(2절). 이 권한을 줄 사람을 좁혀요
• --encryption-provider-config로 Secret 암호화를 켜고 기존 Secret을 한 번 다시 써요. 가능하면 로컬 키보다 KMS 공급자를 써요
✍️ 오늘의 요약
etcd는 클러스터 상태의 유일한 원본이고 그 안에는 Secret까지 원래 글자 그대로 들어 있었어요.

etcd에 붙어 있는 것은 API 서버뿐이었고 etcd는 etcd CA가 서명한 클라이언트 인증서가 없으면 TLS 단계에서 연결을 끊었어요. etcd 파드 안의 etcdctl로 열어 보니 /registry 아래 키가 856개였고 그중 약 43%가 이벤트였으며 myweb 하나는 키 열 개였어요. kubectl의 resourceVersion은 etcd 키의 mod_revision과 같은 숫자였고 같은 버전을 들고 늦게 쓴 쪽은 409 Conflict를 받았어요. 버전을 빼고 쓰면 앞선 변경을 덮어썼어요. Deployment는 k8s\x00으로 시작하는 protobuf, CRD는 JSON으로 저장됐고 암호화 설정이 없는 API 서버는 Secret을 평문으로 etcd에 썼어요. kubectl의 base64는 암호화가 아니에요. 실제로 뜬 스냅숏 파일에도 그 평문이 들어 있었고 암호화를 잠깐 켜 보니 켠 뒤에 쓰거나 다시 쓴 Secret만 암호문이 됐어요. 그래서 etcd 백업은 곧 클러스터 상태의 백업이고 etcd 데이터 파일과 백업 파일은 Secret과 같은 수준으로 지켜야 해요.
