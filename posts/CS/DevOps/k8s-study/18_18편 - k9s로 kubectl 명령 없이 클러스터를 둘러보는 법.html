1. k9s는 클러스터가 아니라 내 터미널에서 도는 화면이다

k9s 저장소의 README 첫머리에는 k9s가 쿠버네티스 클러스터를 다루는 터미널 UI라고 적혀 있어요. 실제로 배포된 애플리케이션을 더 쉽게 둘러보고 관찰하고 관리하게 하는 것이 목표이고 k9s는 쿠버네티스의 변화를 계속 지켜보면서 지켜본 리소스에 쓸 명령을 제공한다고 해요. 공식 사이트 k9scli.io의 소개도 같아요. 라이선스는 Apache-2.0이에요. 이날 설치한 v0.51.0은 2026-06-06에 나온 릴리스이고 글을 쓰는 2026-11-11에 확인한 GitHub의 최신 릴리스도 v0.51.0이었어요.

📖 용어: TUI (터미널 UI)
터미널 창 안에 표와 메뉴를 그려 놓고 키보드로 조작하는 프로그램이에요. kubectl은 보통 명령 한 줄을 받아 결과를 출력하고 끝나지만 TUI는 창을 띄워 둔 채 내용을 계속 다시 그려요. k9s 설정 설명에 따르면 화면을 갱신하는 간격(refreshRate)은 기본 2초예요.

같은 날 강의에서는 Portainer도 다뤘고(16·17편) 9편에서는 Headlamp를 설치했어요. 여기에 늘 쓰던 kubectl까지 넷을 나란히 놓으면 차이가 잘 보여요. 넷 다 결국 API 서버에 요청을 보내는데 어디서 돌고 누구 권한으로 요청하는지가 달라요. 이 실습에서 확인한 내용으로 표를 만들면 이래요.

도구어디서 도나클러스터에 만든 것누구 권한으로 요청하나이 실습에서 연 포트
kubectl내 터미널, 명령 한 줄마다 실행없음kubeconfig의 사용자없음
k9s내 터미널, 화면을 띄워 둔 채 계속 갱신없음kubeconfig의 사용자(kubectl과 같다)없음
Headlamp (9편)클러스터 안 파드, 브라우저로 접속ServiceAccount·Secret·ClusterRoleBinding(cluster-admin)·Service·Deployment로그인 칸에 넣은 토큰의 주인(9편에서는 cluster-admin이 묶인 headlamp 계정)없음. NodePort 30466을 닫고 kubectl port-forward로만 연다
Portainer (16·17편)클러스터 안 파드, 브라우저로 접속Namespace·ServiceAccount·PVC·ClusterRoleBinding(cluster-admin)·Service·Deployment사람은 Portainer 계정으로 로그인하고 파드는 cluster-admin이 묶인 portainer-sa-clusteradmin으로 뜬다NodePort 30777(HTTP)·30779(HTTPS)·30776(edge)

k9s 줄은 kubectl 줄과 "어디서 도나" 칸만 달라요. 명령 한 줄로 끝나느냐 화면을 띄워 두느냐의 차이예요. k9s는 kubectl과 같은 kubeconfig를 읽고 같은 API 서버에 직접 요청하기 때문에 할 수 있는 일도 그 kubeconfig의 사용자가 kubectl로 할 수 있는 일과 같아요. Headlamp와 Portainer는 클러스터 안에 파드로 떠 있고 브라우저가 그 파드에 접속해요. 그래서 클러스터에 오브젝트를 만들어야 했고 그 파드에 닿는 길도 따로 정해야 했어요. Portainer 파드가 portainer-sa-clusteradmin 계정으로 뜬다는 것은 Portainer 설치 문서가 안내하는 매니페스트(downloads.portainer.io/ce-lts/portainer.yaml)의 serviceAccountName에서 확인했어요.

그림 1. kubectl과 k9s는 내 kubeconfig로 API 서버에 바로 가고 Headlamp와 Portainer는 클러스터 안 파드를 거친다

표의 마지막 열은 k9s 화면으로도 확인할 수 있어요. 4절에서 다룰 명령 모드에서 :svc를 입력하면 모든 네임스페이스의 Service 목록이 나와요.

그림 2. NodePort로 열린 것은 Portainer와 지난 실습의 모니터링 도구였고 k9s의 Service는 목록에 없었다

services(all)[9] 가운데 NodePort는 네 개예요. grafana(3000►30004), node-exporter(9100►31672), prometheus-service(8080►30003), portainer(9000►30777, 9443►30779)이고 ► 오른쪽 숫자가 노드 포트예요. headlamp는 ClusterIP라서 80►0으로 나와요. 9편에서 NodePort를 닫고 port-forward로만 열기로 한 결과예요. 이 목록에 k9s와 관련된 Service는 없어요. k9s는 클러스터 쪽에서 요청을 받는 프로그램이 아니기 때문이에요.

2. 설치는 내 컴퓨터에 실행 파일 하나, 클러스터에는 아무것도 없다

README의 설치 절을 보면 Linux·macOS·Windows용 k9s 실행 파일이 릴리스 페이지에 tar 묶음으로 올라와 있고 Homebrew·snap 같은 패키지 관리자로도 설치할 수 있어요. 실습에서는 kubectl을 쓰던 마스터 VM(Ubuntu, arm64)에 릴리스 파일을 받아 설치했어요. 릴리스에는 파일마다 SHA-256 해시를 적은 checksums.sha256이 함께 올라와 있어서 받은 파일과 대조했어요.

master$ T=v0.51.0 master$ curl -fsSLO https://github.com/derailed/k9s/releases/download/$T/k9s_Linux_arm64.tar.gz master$ curl -fsSLO https://github.com/derailed/k9s/releases/download/$T/checksums.sha256 master$ grep " k9s_Linux_arm64.tar.gz$" checksums.sha256 | sha256sum -c - k9s_Linux_arm64.tar.gz: OK # 압축을 풀어 PATH에 둔 뒤 확인한 버전 정보 Version v0.51.0 Commit 558caafe7ba067467de46b320cc22ef11fef9c34 Date 2026-06-06T14:04:25Z

→ 체크섬 목록에서 이 파일의 줄만 골라 sha256sum으로 대조했고 내려받은 파일의 해시가 목록에 적힌 값과 같았다(OK)는 뜻이에요. 받는 도중 파일이 깨졌거나 다른 파일로 바뀌었다면 FAILED가 나와요.

설치는 이게 다예요. Helm 차트도 매니페스트도 없었고 클러스터에 만든 오브젝트도 없었어요. 9편의 Headlamp는 helm install 한 줄로 ServiceAccount와 cluster-admin 바인딩까지 만들었고 16편의 Portainer 매니페스트도 cluster-admin이 묶인 ServiceAccount를 만들었어요. k9s를 설치하고 나서 생긴 것은 마스터의 실행 파일 하나뿐이었어요.

다만 README의 노드 셸(Node Shell) 항목을 보면 클러스터에 파드를 띄우는 기능이 있어요. nodeShell 기능 게이트를 켜면 노드 목록에 s(Shell) 키가 생기고 k9s가 고른 노드에 셸용 파드를 띄워요. 기본 이미지는 BusyBox라고 해요. 이번에는 켜지 않았고 5절에서 볼 노드 목록에도 s 키는 없었어요.

📖 용어: kubeconfig와 컨텍스트
kubeconfig는 API 서버 주소, 그 서버를 확인할 CA 인증서, 나를 증명할 인증 정보를 담은 파일이에요. 컨텍스트는 그 안에서 "어느 클러스터에 어느 사용자로 붙을지"를 묶어 이름을 붙인 항목이고요. kubectl과 k9s는 둘 다 이 파일을 읽어요. 이번 실습의 컨텍스트 이름은 kubernetes-admin@k8s-lab이고 k8s-lab 클러스터에 kubernetes-admin 사용자로 붙는다는 뜻이에요.

클러스터에 깔 것은 없지만 내 컴퓨터에는 갖춰 둘 것이 있어요. README의 사전 점검(PreFlight Checks) 항목에는 k9s가 256색 터미널 모드를 쓰니 TERM을 맞추고(export TERM=xterm-256color) 리소스를 편집하려면 EDITOR와 KUBE_EDITOR 환경 변수를 정해 두라고 적혀 있어요. 쿠버네티스는 1.28 이상의 최근 버전을 권해요.

그리고 kubectl도 있어야 해요. v0.51.0 소스(internal/view/exec.go, browser.go)를 보면 e(Edit)를 누를 때 k9s가 PATH에서 kubectl을 찾아 kubectl edit을 실행하고 컨테이너 셸(s)도 kubectl exec으로 열어요. kubectl을 찾지 못하면 kubectl command is not in your path 오류를 내요. kubectl을 직접 치지 않을 뿐 몇몇 키는 뒤에서 kubectl을 부르는 셈이에요.

화면을 찍을 때는 k9s를 tmux 창(가로 110칸, 세로 34줄) 안에서 이렇게 띄웠어요.

master$ k9s --logoless -n default -c pod

→ 오른쪽 위 로고를 숨기고(--logoless) default 네임스페이스에서(-n) 파드 목록을 첫 화면으로(-c pod) 연다는 뜻이에요. k9s --help에는 -c가 "앱을 시작할 때 처음 띄울 리소스를 바꾼다"는 설명으로 나와요.

그림 3. 첫 화면은 왼쪽 연결 정보, 가운데 네임스페이스 번호, 오른쪽 키 목록, 아래 표로 나뉜다

화면은 네 구역으로 나뉘어요. 왼쪽 위 일곱 줄은 지금 어디에 누구로 붙어 있는지를, 가운데는 숫자 하나로 옮겨 갈 네임스페이스를, 오른쪽은 지금 화면에서 누를 수 있는 키를 보여 줘요. 아래 표는 고른 리소스의 목록이에요.

왼쪽 일곱 줄: 누구로, 어디에, 어떤 버전으로

Context는 kubernetes-admin@k8s-lab, Cluster는 k8s-lab, User는 kubernetes-admin이에요. 마스터의 kubeconfig에 적힌 그대로예요. Context 끝의 [RW]는 k9s가 쓰기 모드로 떠 있다는 표시예요. v0.51.0 소스(internal/ui/types.go)에는 쓰기 모드 표시가 [RW], 읽기 전용 표시가 [R]로 정의돼 있어요. 이 표시는 6절에서 다시 다뤄요. K9s Rev의 v0.51.0은 k9s 버전이고 K8s Rev의 v1.37.2는 API 서버 버전이에요.

CPU와 MEM이 n/a인 것은 이 클러스터에 metrics-server가 없기 때문이에요. 8편에서 kubectl top nodes를 실행했을 때 error: Metrics API not available로 끝난 것과 같은 이유예요.

📖 용어: Metrics API와 metrics-server
노드와 파드의 CPU·메모리 사용량을 쿠버네티스 API(metrics.k8s.io 그룹)로 조회하게 해 주는 API예요. 쿠버네티스의 Resource metrics pipeline 문서에는 이 API를 쓰려면 metrics-server나 같은 API를 내놓는 다른 어댑터를 배포해야 한다고 적혀 있어요. kubectl top과 HorizontalPodAutoscaler도 이 API를 써요.

k9s가 이 칸을 어떻게 채우는지는 소스에서 확인했어요(internal/view/cluster_info.go, internal/client/client.go). k9s는 API 서버가 알려 주는 API 그룹 목록에 metrics.k8s.io가 있는지 보고 없으면 "No metrics-server detected"로 처리해 n/a를 띄워요. 그룹이 있어도 지금 사용자에게 노드 메트릭을 list할 권한이 없으면 역시 n/a예요. 11편에서 띄운 Prometheus는 이 칸과 상관이 없어요. k9s는 Prometheus가 아니라 Metrics API에 묻기 때문이에요. n/a는 k9s가 고장 났다는 뜻이 아니라 클러스터에 Metrics API가 없다는 신호예요.

가운데 숫자: 즐겨찾기 네임스페이스

<0> all, <1> kube-node-lease, <2> default, <3> monitoring은 숫자 키 하나로 옮겨 갈 네임스페이스예요. 0은 모든 네임스페이스예요. 공식 설정 문서에는 컨텍스트별 설정의 namespace 항목에 favorites(즐겨찾기 네임스페이스) 목록과 "k9s의 즐겨찾기 갱신을 끈다"는 lockFavorites 설정이 있어요. 소스(internal/config/data/ns.go)를 보면 k9s는 네임스페이스를 옮길 때마다 그 이름을 즐겨찾기에 넣고 최대 9개까지 남겨요. 그래서 여기에 어떤 이름이 보이는지는 그동안 어느 네임스페이스로 옮겨 다녔는지에 따라 달라요.

오른쪽 키 목록: 지금 화면에서 누를 수 있는 키

오른쪽은 파드 목록에서 쓸 수 있는 키예요. <a> Attach, <ctrl-d> Delete, <d> Describe, <e> Edit, <?> Help, <shift-j> Jump Owner, <l> Logs, <p> Logs가 보이고 넷째 열은 창 폭이 모자라 Kil…, Port, Sani, Shel로 잘렸어요. 소스에 적힌 이름은 Kill, Port-Forward, Sanitize, Shell이고 <p>도 Logs Previous(이전 컨테이너의 로그)예요. 잘린 이름은 ?를 눌러 도움말을 열면 볼 수 있어요. 이 키 목록은 화면마다 바뀌어요. 5절에서 이 점이 가장 중요해져요.

아래 표: 리소스(네임스페이스)[개수]

표 제목 pods(default)[7]은 "리소스(네임스페이스)[개수]"로 읽어요. default 네임스페이스의 파드는 7개였어요. 지난 실습에서 남은 Job 파드 hello-9w94f가 0/1 Completed였고 15편 실험에서 만든 loadgen 하나와 myweb 다섯 개가 1/1 Running이었어요. NAME 옆의 ↑는 이름 순으로 정렬했다는 표시예요. 표 아래의 <pod>는 지나온 화면을 순서대로 보여 주는 표시(crumbs)이고 그 아래 "Viewing v1/pods in namespace default"는 방금 연 화면을 알려 주는 메시지예요.

그림 4. 네임스페이스 목록에서 +는 즐겨찾기, (*)는 지금 쓰는 네임스페이스다

여기서 /monitoring으로 목록을 거르고 Enter를 두 번 눌렀어요. 첫 Enter는 필터를 확정하고 둘째 Enter는 고른 줄로 들어가요. 소스를 보면 네임스페이스 줄에서 Enter를 누르면 그 네임스페이스를 지금 네임스페이스로 바꾸고 파드 목록으로 넘어가요. 화면은 pods(monitoring)[6]이 됐고 grafana 1개, node-exporter 4개(k8s-master 포함), prometheus-deployment 1개가 보였어요. 11편에서 고친 node-exporter가 노드 4대에 하나씩 떠 있는 모습이에요.

그림 11. 노드 목록에서 r은 Restart가 아니라 Drain이다

노드 4대가 모두 Ready이고 버전은 v1.37.2예요. 마스터에는 taint가 1개(5편에서 본 control-plane NoSchedule) 있고 파드는 마스터 7개, worker1 8개, worker2 9개, worker3 8개예요. 오른쪽 키는 <c> Cordon, <u> Uncordon, <r> Drain이에요. Deployment 목록에서 재시작이던 r이 노드 목록에서는 노드의 파드를 내보내는 Drain이에요. 소스를 보면 Drain은 옵션을 고르는 창을 먼저 띄우지만 키 하나 차이로 전혀 다른 작업에 들어서게 돼요.

📖 용어: cordon과 drain
cordon은 노드를 스케줄 불가(unschedulable)로 표시해 새 파드가 그 노드에 배치되지 않게 하는 일이에요. drain은 노드를 점검하기 전에 그 노드의 파드를 안전하게 내보내는(evict) 일이고 이때 노드도 스케줄 불가로 표시돼요. uncordon은 노드가 다시 새 파드를 받게 되돌려요(Safely Drain a Node).

같은 방법으로 :event를 입력하면 이벤트 목록이 최근 순으로 나와요. 이날은 events(all)[43]이었고 맨 위에는 50분 전 Kubeshark를 지울 때(14편) 남은 Killing 이벤트가 있었어요. 8편에서 본 대로 이벤트는 1시간이 지나면 사라지니 무슨 일이 막 생겼을 때 먼저 열어 볼 만한 화면이에요.

6. [RW]는 관리자가 쓰기 모드로 붙었다는 뜻이다

이번 k9s는 마스터에서 띄웠고 마스터의 kubeconfig는 admin.conf에서 온 kubernetes-admin 사용자예요. 5편에서 본 대로 이 인증서의 그룹은 kubeadm:cluster-admins이고 kubeadm은 이 그룹에 클러스터 관리자 권한을 묶어 둬요. 그래서 그림 3의 [RW]는 "쓰기 모드인 k9s가 클러스터 관리자로 붙어 있다"는 뜻이었어요. 오른쪽 위에 보이던 Delete, Kill, Edit, Scale, Restart, Drain을 RBAC 쪽에서 막는 것이 없는 상태예요.

k9s가 무엇을 할 수 있는지는 k9s가 아니라 kubeconfig 사용자의 권한이 정해요. README의 RBAC 절에는 k9s가 리소스와 메트릭을 보여 주려면 클러스터와 네임스페이스 수준의 읽기 권한이 최소한 있어야 하고 편집·삭제를 하려면 그 이상이 필요하다고 적혀 있어요. 같은 절에는 nodes·namespaces·RBAC 오브젝트·CRD·metrics.k8s.io에 get·list·watch만 주는 k9s용 ClusterRole 예시도 있어요. 소스를 봐도 k9s는 편집이나 재시작을 하기 전에 지금 사용자에게 그 권한이 있는지 먼저 묻고 없으면 current user can't edit resource 같은 오류를 띄워요.

--readonly는 k9s 화면에서 바꾸는 키를 감춘다

master$ k9s --help | grep -E "readonly|write|--command|--namespace" -c, --command string Overrides the default resource to load when the application launches -n, --namespace string If present, the namespace scope for this CLI request --readonly Sets readOnly mode by overriding readOnly configuration setting --write Sets write mode by overriding the readOnly configuration setting

→ --readonly는 설정 파일의 readOnly 값을 덮어써 읽기 전용으로 켜고 --write는 반대로 쓰기 모드로 켠다는 뜻이에요.

README에는 k9s --readonly가 클러스터를 바꾸는 명령을 모두 끈 채로 시작하는 방법이라고 적혀 있어요. 설정 문서에는 readOnly가 delete·kill·edit 같은 수정 명령을 끌지 정하는 값이고 기본값은 false라고 나와요. 특정 컨텍스트만 골라 읽기 전용으로 둘 수도 있어요. 이번에는 읽기 전용 화면을 찍지 않았어요. 그래서 켰을 때 무엇이 달라지는지는 v0.51.0 소스로 확인했어요.

· Context 줄 끝의 표시가 [RW]에서 [R]로 바뀌어요(internal/ui/types.go).
· 목록 화면의 공통 키인 e(Edit)와 Ctrl+D(Delete)가 빠져요(internal/view/browser.go).
· 파드 목록에서 Ctrl+K(Kill), s(Shell), a(Attach), t(Transfer), z(Sanitize)가 빠져요(pod.go).
· Deployment 목록에서 s(Scale)와 r(Restart)가, 노드 목록에서 c(Cordon), u(Uncordon), r(Drain)이 빠져요(scale_extender.go, restart_extender.go, node.go).

다만 readOnly는 k9s가 키를 감추는 설정이지 클러스터 권한을 줄이는 설정이 아니에요. 같은 kubeconfig로 kubectl을 쓰면 그대로 지울 수 있고 k9s도 --write를 붙이면 쓰기 모드로 돌아와요. readOnly는 잘못 누르는 실수를 줄이는 장치이고 할 수 있는 일 자체는 RBAC로 줄여야 해요. 여러 사람이 운영 클러스터를 들여다봐야 한다면 README의 ClusterRole 예시를 바탕으로 읽기 권한만 묶은 사용자를 만들어 그 사용자의 kubeconfig를 나눠 주는 쪽이 맞아요.

확인 창이 있는 키와 없는 키

공식 명령 문서에 따르면 Ctrl+D는 Tab과 Enter로 한 번 더 확인해야 지워지고 Ctrl+K는 확인 창 없이 바로 지워요. 문서에는 Ctrl+K가 kubectl delete --now와 같다고 적혀 있어요. 파드 목록의 z(Sanitize)는 소스에 "완료(completed)나 오류(error) 상태인 파드를 모두 지운다"는 안내와 함께 정의돼 있고 Yes Please!를 직접 입력해야 실행돼요. 그림 3의 default 네임스페이스라면 Completed인 hello-9w94f가 그 대상이에요.

⚠️ 주의: 마스터에서 k9s를 띄웠다면
• 컨텍스트가 kubernetes-admin@…이고 Context 끝이 [RW]라면 클러스터 관리자로 쓰기 모드예요
• 둘러보기만 할 때는 k9s --readonly로 띄우고 Context 끝이 [R]인지 확인하세요
• Ctrl+K는 확인 없이 지워요. Ctrl+D와 손이 헷갈리지 않을 때까지는 읽기 전용으로 연습하는 편이 안전해요
💡 실무에서는: 운영 컨텍스트만 읽기 전용으로 묶어 둬요
• 컨텍스트별 설정 파일에 readOnly를 적어 두면 그 컨텍스트에 붙을 때만 읽기 전용이 돼요. 파일 위치는 k9s info로 확인할 수 있어요
• 바꿔야 할 때만 --write로 열고 일이 끝나면 다시 기본값으로 엽니다
• 공유하는 kubeconfig에는 README의 k9s ClusterRole 예시(get·list·watch만)를 바탕으로 만든 읽기 전용 사용자를 넣어요
# $XDG_DATA_HOME/k9s/clusters/<클러스터>/<컨텍스트>/config.yaml (README의 컨텍스트 설정 예시 형식) k9s: readOnly: true

→ 이 컨텍스트로 k9s를 열면 --readonly를 붙이지 않아도 읽기 전용으로 시작한다는 뜻이에요.

다시 처음 정리로: kubectl이 어려운 사람만 쓰는 도구일까

처음에 내린 정리는 "kubectl 어려운 사람들 이런 거 쓰라고"였어요. 명령을 외우지 않아도 목록을 보고 키를 고르면 되니 입문자에게 편한 것은 맞아요. 그런데 공식 사이트의 기능 목록에는 "Power Users Welcome!"이라는 항목이 있고 로그·스케일·포트 포워드·재시작 같은 관리 명령, 직접 정하는 명령 별칭과 단축키, 플러그인, 필터 모드를 묶어 소개해요. 같은 목록의 첫 항목은 클러스터 리소스의 활동을 실시간으로 따라간다는 내용이에요. 저는 이 두 항목을 숙련자가 상태를 띄워 둔 채 로그나 Describe로 바로 넘어가는 용도까지 생각한 도구라는 뜻으로 읽었어요.

그리고 5절에서 본 키의 뜻(describe, logs, edit, rollout restart, drain)은 kubectl의 동작 그대로예요. 그 동작을 모르면 k9s의 키도 똑같이 위험해요. 써 보고 나니 k9s는 kubectl을 몰라도 쓰는 도구라기보다 kubectl로 하던 일을 덜 타이핑하고 더 빨리 보게 해 주는 도구에 가까웠어요.

✍️ 오늘의 요약
k9s는 클러스터에 아무것도 설치하지 않고 내 kubeconfig로 API 서버를 직접 읽는 터미널 화면이에요.

마스터에 체크섬을 확인한 실행 파일 하나만 두고 띄웠고 Headlamp·Portainer와 달리 클러스터에 생긴 오브젝트도, 새로 연 포트도 없었어요. 첫 화면에서는 Context 줄의 사용자와 [RW], 그리고 metrics-server가 없다는 뜻인 CPU·MEM의 n/a부터 읽어요. :로 볼 리소스를 바꾸고 /로 줄을 거르고 0으로 모든 네임스페이스를 본 뒤 줄을 골라 d·l·y·e·Shift+F·Ctrl+D 같은 키 하나로 kubectl의 일을 해요. 같은 s와 r이 파드·Deployment·노드 목록에서 Shell·Scale·Restart·Drain으로 바뀌니 누르기 전에 오른쪽 위 키 목록을 봐요. 관리자 kubeconfig로 둘러보기만 할 때는 --readonly로 열어 [R]을 확인하고 권한 자체는 RBAC로 줄여요. k9s로 할 수 있는 일은 그 kubeconfig의 권한을 넘지 않아요.
