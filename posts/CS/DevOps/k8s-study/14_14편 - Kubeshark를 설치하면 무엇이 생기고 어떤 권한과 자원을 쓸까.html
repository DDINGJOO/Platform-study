20:45에 마스터의 터미널에서 ks tap을 실행했어요. 대상 파드 이름이 한 줄씩 지나간 뒤 이런 줄이 찍혔습니다.

INF helm.go:132 > Downloading Helm chart: ... url=https://github.com/kubeshark/kubeshark.github.io/releases/download/kubeshark-53.6.0/kubeshark-53.6.0.tgz INF helm.go:151 > Installing using Helm: kube-version=">= 1.16.0-0" release=kubeshark ... version=53.6.0 INF helm.go:62 > creating 21 resource(s) INF tapRunner.go:99 > Installed the Helm release: kubeshark

→ Kubeshark CLI가 GitHub에서 Helm 차트 53.6.0을 내려받아 kubeshark라는 이름으로 설치했고 그 과정에서 리소스 21개를 만들었다는 뜻이에요.

마스터에 설치한 것은 CLI 바이너리 하나였어요. 그런데 명령 한 줄에 Helm 릴리스가 생겼고 1초 뒤에 Ctrl+C로 명령을 끝냈는데도 리소스는 그대로 남았어요. 생성 2분 13초 뒤에 파드 목록을 다시 보니 워커 3대에 수집기 파드가 하나씩 Running이었어요. 그 수집기는 privileged 컨테이너였고 노드의 루트 디렉터리 /를 붙이고 있었어요.

13편에서는 eBPF와 kprobe가 사이드카 없이 노드의 연결을 보는 원리를 다뤘어요. 이번에는 그 원리로 만든 도구를 실제로 설치했을 때 클러스터에 무엇이 남는지 따라가요. 운영 클러스터에 Kubeshark를 늘 설치해 둘지 판단하려면 답해야 할 질문이 세 가지였어요. tap 한 번이면 클러스터에 무엇이 생길까요? 수집기는 어떤 권한과 자원을 쓸까요? 그리고 무엇을 보지 못할까요? 실습 클러스터는 Lima VM 4대(마스터 1대, 워커 3대, 각 2 CPU·4GiB)에 쿠버네티스 v1.37.2를 올린 것이고 Kubeshark는 v53.6.0을 썼어요.

1. CLI를 설치해도 클러스터에는 아무것도 생기지 않는다

실습을 시작하면서 처음 궁금했던 것은 명령 이름이었어요. kubeshark는 아홉 글자라 매번 치기 번거로워서 보통 ks로 줄여 쓰는지 찾아봤어요. 설치 문서와 GitHub README에는 ks라는 말이 나오지 않아요. v53.6.0 CLI 소스에도 명령 별칭은 정의돼 있지 않았어요. ks는 각자 셸에 거는 개인 별칭이에요. kubectl을 k로 줄여 쓰는 것과 같은 종류예요.

마스터는 arm64라서 GitHub 릴리스에서 v53.6.0의 linux_arm64 바이너리를 받아 설치하고 별칭을 걸었어요.

master$ T=v53.6.0; curl -fsSLo kubeshark https://github.com/kubeshark/kubeshark/releases/download/$T/kubeshark_linux_arm64 master$ curl -fsSLo kubeshark.sha256 https://github.com/kubeshark/kubeshark/releases/download/$T/kubeshark_linux_arm64.sha256 expected: 5afdd92e413d2a11… actual: 5afdd92e413d2a11… master$ sudo install -m 755 kubeshark /usr/local/bin/kubeshark master$ kubeshark version v53.6.0 master$ sed -n "/>>> kubeshark >>>/,/<<< kubeshark <<</p" ~/.bashrc # >>> kubeshark >>> source <(kubeshark completion bash) alias ks=kubeshark complete -o default -F __start_kubeshark ks # <<< kubeshark <<< master$ bash -ic "type ks; ks version; complete -p ks" ks is aliased to `kubeshark' v53.6.0 complete -o default -F __start_kubeshark ks

→ 릴리스에 함께 올라온 체크섬과 받은 파일이 같은지 확인한 뒤 설치했고 .bashrc에 자동 완성, 별칭, 별칭용 자동 완성을 차례로 넣었다는 뜻이에요.

셋째 줄이 있어야 ks 뒤에서도 Tab 키로 하위 명령이 완성돼요. kubectl 빠른 참조 문서에도 별칭 k가 자동 완성과 함께 동작하게 하는 방법으로 alias k=kubectl과 complete -o default -F __start_kubectl k 두 줄이 나와 있어요. 하위 명령 목록에서 이 글과 이어지는 것은 네 개예요.

master$ kubeshark --help # Available Commands 일부 clean Removes all Kubeshark resources pcapdump Store all captured traffic (including decrypted TLS) in a PCAP file. proxy Open the web UI (front-end) in the browser via proxy/port-forward tap Capture the network traffic in your Kubernetes cluster

→ tap이 수집을 시작하고 proxy가 대시보드를 열며 clean이 Kubeshark 리소스를 모두 지운다는 설명이에요. pcapdump는 복호화한 TLS를 포함한 트래픽을 PCAP 파일로 저장해요.

여기까지 한 일은 마스터에 바이너리를 놓고 .bashrc를 고친 것뿐이에요. CLI를 설치한 것만으로는 클러스터에 아무것도 생기지 않아요. 리소스를 만드는 것은 tap이에요. v53.6.0의 tapRunner.go를 보면 tap은 대상 파드 목록을 로그로 찍은 뒤 Helm으로 kubeshark 릴리스를 설치해요. 같은 이름의 릴리스가 이미 있으면 설치를 건너뛰고 대상 조건 같은 설정 값만 다시 써요. 도입부의 "creating 21 resource(s)"가 그 Helm 설치였어요.

📖 용어: Helm 릴리스 (release)
Helm 차트(쿠버네티스 매니페스트 묶음)를 클러스터에 한 번 설치한 단위예요. 이름이 붙고 Helm이 그 설치로 어떤 리소스를 만들었는지 기록해 둬요. 그래서 helm uninstall 한 번으로 그 리소스를 함께 지울 수 있어요. kubeshark tap은 이 릴리스를 대신 만들어 줘요.

릴리스는 default 네임스페이스에 들어갔어요. 차트 values에서 릴리스 네임스페이스(tap.release.namespace)의 기본값이 default이기 때문이에요.

master$ helm list -A | grep -E "NAME|kubeshark" NAME NAMESPACE REVISION UPDATED STATUS CHART APP VERSION kubeshark default 1 2026-11-11 20:45:31 +0900 KST deployed kubeshark-53.6.0

→ 20:45:31에 default 네임스페이스로 첫 리비전이 배포됐고 차트는 kubeshark-53.6.0이라는 뜻이에요. APP VERSION 칸은 비어 있었어요.

첫 tap은 설치 직후에 Ctrl+C로 끝났어요. 마지막 줄은 이랬어요.

INF tapRunner.go:180 > Added: pod=kubeshark-hub ^C WRN tapRunner.go:119 > To re-establish a proxy/port-forward, run: command="kubeshark proxy"

→ tap 명령은 끝났고 대시보드에 다시 연결하려면 kubeshark proxy를 실행하라는 안내예요. 설치한 리소스를 지웠다는 말은 없어요.

⚠️ 주의: Ctrl+C는 설치를 지우지 않아요
tap을 Ctrl+C로 끝내도 Helm 릴리스와 리소스 21개는 그대로예요. 실제로 64초 뒤에 tap을 다시 실행하자 "Found an existing installation, skipping Helm install"이 찍혔어요. 지우려면 kubeshark clean을 실행해야 해요(6절 끝). CLI 없이 Helm으로 직접 설치했다면 차트 README에 적힌 대로 helm uninstall kubeshark로 지워요.

2. tap 한 번이 만든 리소스 21개는 무슨 일을 하나

Helm이 만든 리소스를 종류와 이름으로 뽑아 셌어요.

그림 1. 릴리스 하나에 리소스 21개가 들어 있었다. 실제로 일하는 것은 Deployment 2개와 DaemonSet 1개다

21개를 하는 일로 나누면 다섯 묶음이에요.

· 실제로 일하는 것: Deployment kubeshark-hub와 kubeshark-front, DaemonSet kubeshark-worker-daemon-set
· 연결: Service 4개. front(80), hub(80), hub-metrics(9100), worker-metrics(49100)이고 모두 ClusterIP예요
· 권한: ServiceAccount 1개, ClusterRole과 ClusterRoleBinding, Role과 RoleBinding (3절)
· 설정: ConfigMap 2개(kubeshark-config-map, kubeshark-nginx-config-map)와 Secret 3개(kubeshark-secret, SAML용 x509 인증서와 키)
· 접근 제한: NetworkPolicy 4개(dex, front, hub, worker)

실행 단위 세 개가 하는 일은 Kubeshark 구성 문서에 나와 있어요. worker는 노드 단위로 뜨는 DaemonSet이고 무거운 일을 맡아요. hub는 Deployment이고 worker들이 보낸 스트림을 하나로 모아요. 문서에는 hub가 대시보드 연결이 있을 때만 동작한다고 적혀 있어요. front는 React로 만든 대시보드를 내놓는 Deployment이고 hub와 WebSocket으로 통신해요. 수집한 데이터는 주로 worker의 메모리에서 처리하고 일부만 worker 노드의 디스크에 두는데 기본값에서는 임시 저장이에요. 사용자가 직접 내보내지 않는 한 데이터가 클러스터 밖으로 나가지 않는다고도 적혀 있어요.

📖 용어: sniffer와 tracer
worker 파드 안의 두 컨테이너예요. sniffer는 AF_PACKET(리눅스에서 네트워크 장치를 지나는 패킷을 받아 보는 소켓)으로 패킷을 잡아요. tracer는 eBPF로 커널 공간과 사용자 공간의 함수를 추적해요(13편). tracer는 선택 사항이라 차트 값 tap.tls로 켜고 끌 수 있어요.

생성 29초 뒤와 2분 13초 뒤의 파드 목록이에요.

mac$ kubectl get pods -n default -o wide | grep kubeshark # 20:46, 설치 직후 kubeshark-front-7fb9788cdd-w7whb 0/1 ContainerCreating 0 29s k8s-worker2 kubeshark-hub-fbd9d8db-zcsjv 0/1 ContainerCreating 0 29s k8s-worker2 kubeshark-worker-daemon-set-kdxl2 0/2 Init:0/1 0 29s k8s-worker2 kubeshark-worker-daemon-set-wq4ps 0/2 Init:0/1 0 29s k8s-worker1 kubeshark-worker-daemon-set-zkf86 0/2 Init:0/1 0 29s k8s-worker3 mac$ kubectl get svc,ds,deploy -n default | grep -E "NAME|kubeshark" NAME TYPE CLUSTER-IP EXTERNAL-IP PORT(S) AGE service/kubeshark-front ClusterIP 10.110.107.238 <none> 80/TCP 29s service/kubeshark-hub ClusterIP 10.111.237.62 <none> 80/TCP 29s service/kubeshark-hub-metrics ClusterIP 10.103.87.26 <none> 9100/TCP 29s service/kubeshark-worker-metrics ClusterIP 10.100.126.244 <none> 49100/TCP 29s NAME DESIRED CURRENT READY UP-TO-DATE AVAILABLE NODE SELECTOR AGE daemonset.apps/kubeshark-worker-daemon-set 3 3 0 3 0 <none> 29s NAME READY UP-TO-DATE AVAILABLE AGE deployment.apps/kubeshark-front 0/1 1 0 29s deployment.apps/kubeshark-hub 0/1 1 0 29s mac$ kubectl get pods -n default -o wide | grep kubeshark # 20:47:44 kubeshark-front-7fb9788cdd-w7whb 1/1 Running 0 2m13s k8s-worker2 kubeshark-hub-fbd9d8db-zcsjv 1/1 Running 0 2m13s k8s-worker2 kubeshark-worker-daemon-set-kdxl2 2/2 Running 0 2m13s k8s-worker2 kubeshark-worker-daemon-set-wq4ps 2/2 Running 0 2m13s k8s-worker1 kubeshark-worker-daemon-set-zkf86 2/2 Running 0 2m13s k8s-worker3

→ hub와 front는 worker2에 떴고 worker DaemonSet은 DESIRED 3으로 worker1~3에 하나씩 떴다는 뜻이에요. 처음에 Init:0/1이던 worker 파드는 생성 2분 13초 뒤에 보니 컨테이너 두 개가 모두 준비된 2/2였어요.

Init:0/1은 init 컨테이너가 아직 끝나지 않았다는 표시예요. 설치에 쓴 kubeshark-53.6.0.tgz를 받아 worker 템플릿을 열어 보면 mount-bpf라는 init 컨테이너가 있어요. 노드에 BPF 파일시스템이 마운트돼 있지 않으면 mount -t bpf bpf /sys/fs/bpf로 마운트하는 컨테이너예요. 차트 README의 tap.mountBpf 항목에는 eBPF가 제대로 동작하려면 BPF 파일시스템이 마운트돼 있어야 한다고 적혀 있고 기본값은 true예요. 이 init 컨테이너도 privileged로 떠요.

이미지는 docker.io/kubeshark의 worker, hub, front였고 태그는 v53.6이었어요. 크기는 worker 약 72MB, hub 약 46MB, front 약 59MB예요. 노드가 모두 arm64였는데 kubelet은 세 이미지를 모두 받아 문제없이 실행했어요. 받는 데 걸린 시간은 대기 시간까지 합쳐 hub가 1분 45초, front가 2분 4.5초였어요. 이 2분이 5절의 connection refused와 이어져요.

kubeshark-secret에는 LICENSE, OIDC_CLIENT_ID, OIDC_CLIENT_SECRET, SCRIPTING_ENV 네 키가 있었어요. 값은 열어 보지 않았어요. 차트 템플릿에서 LICENSE 키에는 Helm 값 license가 들어가는데 이번에는 그 값을 주지 않았어요. 5절에서 볼 라이선스 표시 NOT DETECTED와 이어지는 부분이에요.

NetworkPolicy 4개는 Kubeshark 자신의 파드에 거는 정책이에요. 템플릿을 보면 정책마다 hub, front, dex, worker 중 하나를 고르고 들어오는 연결을 정해진 포트로만 허용해요(hub 8080·9100, front 8080, dex 5556, worker 48999·49100). 나가는 연결은 모두 허용해요. dex는 인증에 쓰는 구성 요소인데 이번에는 dex 파드가 뜨지 않았어요. dex Deployment는 인증 설정이 있을 때만 만들어지지만 NetworkPolicy 4개는 조건 없이 만들어지기 때문이에요.

📖 용어: NetworkPolicy
파드로 들어오고 나가는 연결을 라벨과 포트로 제한하는 쿠버네티스 리소스예요. 쿠버네티스 문서에 따르면 정책을 실제로 집행하는 것은 네트워크 플러그인(CNI)이고 NetworkPolicy를 지원하는 플러그인을 써야 효과가 있어요.

지금까지 본 것을 노드 위에 놓으면 그림 2가 돼요.

그림 2. 수집기는 워커 3대에 하나씩 떴고 hub와 front는 worker2에 떴다. 마스터에는 아무것도 뜨지 않았다

리소스 21개 가운데 트래픽을 직접 보는 것은 worker DaemonSet 하나이고 나머지는 그 결과를 모으고 보여 주고 지키는 리소스예요. 그래서 권한과 자원을 따질 때도 worker부터 봐야 해요.

3. 수집기 worker는 노드의 root와 거의 같은 권한으로 뜬다

worker DaemonSet의 보안 설정과 볼륨, 그리고 ServiceAccount에 묶인 ClusterRole을 출력했어요.

그림 3. 수집기는 privileged에 hostNetwork이고 노드의 /까지 붙인다. ClusterRole에는 NetworkPolicy를 지우는 권한도 있다

privileged, hostNetwork, hostPath

세 가지가 눈에 띄어요. 첫째, sniffer와 tracer가 모두 privileged=true예요. 쿠버네티스 Pod API 문서의 privileged 필드 설명에는 "privileged 컨테이너의 프로세스는 호스트의 root와 본질적으로 같다(essentially equivalent to root on the host)"라고 적혀 있어요.

📖 용어: privileged 컨테이너
컨테이너를 노드에서 격리하는 장치 대부분을 풀고 띄운 컨테이너예요. 리눅스의 커널 권한(capability)을 모두 받고 노드의 장치에도 접근할 수 있어요. 보통 컨테이너는 이 권한 가운데 일부만 받아요.

둘째, 파드에 hostNetwork=true가 걸려 있어요. 같은 문서에서 hostNetwork는 호스트의 네트워크 네임스페이스를 쓰라는 설정이에요. worker 파드는 자기만의 네트워크 공간 없이 노드의 네트워크 인터페이스를 그대로 써요. 차트 README에도 이 값을 켜면 worker 파드가 호스트의 네트워크 네임스페이스를 쓴다고 적혀 있고 기본값은 true예요.

셋째, 노드의 디렉터리를 hostPath로 붙여요. /proc, /sys, /lib/modules, /etc/os-release, 그리고 노드의 루트 /예요. 템플릿을 보면 /proc은 /hostproc에, /sys는 /sys에 읽기 전용으로 붙고 노드의 /는 tracer 컨테이너의 /hostroot에 읽기 전용으로 붙어요. root 볼륨은 tap.tls가 켜져 있을 때만 생겨요. README에서 tap.tls는 OpenSSL 같은 암호화 라이브러리를 거치는 TLS 트래픽을 잡는 설정이고 기본값은 true예요. 읽기 전용이라도 노드의 파일 전체를 읽을 수 있는 경로예요.

📖 용어: hostPath 볼륨
노드의 파일이나 디렉터리를 파드 안에 그대로 붙이는 볼륨이에요. 파드는 붙인 경로 아래에 있는 노드의 파일을 읽을 수 있고 읽기 전용으로 붙이지 않았다면 쓸 수도 있어요. 파드를 지워도 노드의 파일은 남아요.

목록 끝의 data와 hub-internal-token은 hostPath가 아니에요. data는 수집한 트래픽을 두는 emptyDir이에요(6절). hub-internal-token은 audience가 kubeshark-hub이고 유효 시간이 3600초인 ServiceAccount 토큰을 파일로 붙인 볼륨이에요.

세 설정은 쿠버네티스가 정한 파드 보안 기준에서 모두 금지 항목이에요. Pod Security Standards의 Baseline 정책에는 "privileged 파드는 대부분의 보안 장치를 끄므로 허용하지 않아야 한다", "호스트 네임스페이스 공유는 허용하지 않아야 한다", "hostPath 볼륨은 금지해야 한다"는 항목이 있어요. Baseline은 알려진 권한 상승을 막는 최소한의 기준이에요. Kubeshark worker는 그 최소 기준을 통과하지 못하는 설정으로 떠요. 사이드카 없이 노드의 모든 파드를 본다는 것은 노드마다 root에 가까운 프로세스를 하나씩 둔다는 뜻이에요.

차트에는 privileged를 끄는 설정(tap.securityContext.privileged: false)도 있어요. 템플릿을 보면 그때는 privileged 대신 필요한 커널 권한만 골라 넣어요. 패킷 수집용으로 NET_RAW·NET_ADMIN, eBPF용으로 SYS_ADMIN·SYS_PTRACE·SYS_RESOURCE·IPC_LOCK이 values에 적혀 있어요. 이 설정은 시험하지 않았어요. 다만 Baseline이 더할 수 있게 허용하는 커널 권한 목록에는 NET_RAW도 SYS_ADMIN도 없고 hostNetwork와 hostPath는 그대로 남아요. privileged를 꺼도 Baseline을 통과하는 설정은 아니에요.

ClusterRole과 Role

차트 템플릿을 보면 hub, front, worker는 모두 kubeshark-service-account 하나를 써요. 이 ServiceAccount에 묶인 ClusterRole의 규칙은 네 줄이었어요.

그림 4. worker 파드 하나에 붙은 권한. 노드 안에서는 root에 가깝고 API로는 클러스터 전체를 읽는다
⚠️ 주의: 운영 클러스터에 늘 설치해 두기 전에
• 노드마다 privileged·hostNetwork 컨테이너가 노드의 /를 붙인 채 떠 있게 돼요. 그 노드에 root와 거의 같은 프로세스가 하나 더 생기는 셈이에요
• 네임스페이스에 Pod Security의 baseline이나 restricted를 강제해 두었다면 Kubeshark를 설치할 네임스페이스는 privileged 수준으로 따로 열어야 해요
• 기본값대로 설치하면 default 네임스페이스에 들어가고 그 네임스페이스의 Secret을 읽을 수 있는 Role이 함께 생겨요. CLI에는 릴리스 네임스페이스를 바꾸는 -s(--release-namespace) 옵션이 있지만 이번에는 써 보지 않았어요
• 이 권한 범위라면 필요할 때 설치하고 확인이 끝나면 지우는 쓰임이 맞다고 봐요

마스터에 수집기가 뜨지 않은 이유

2절에서 DaemonSet의 DESIRED는 3이었어요. 마스터에는 처음부터 배치하지 않았다는 뜻이에요. 5편에서 본 대로 kubeadm은 마스터에 node-role.kubernetes.io/control-plane:NoSchedule taint를 붙여요. 이 taint를 허용하는 toleration이 있는 파드만 마스터에 배치돼요.

📖 용어: taint와 toleration
taint는 노드에 붙이는 "이 조건을 받아들이는 파드만 오라"는 표시이고 toleration은 파드 쪽에서 그 표시를 받아들이겠다고 적는 설정이에요. effect가 NoSchedule인 taint가 있으면 맞는 toleration이 없는 새 파드는 그 노드에 배치되지 않아요. NoExecute는 이미 떠 있는 파드까지 내보내요.

차트 values에서 worker의 toleration 기본값은 하나뿐이에요.

# helm-chart/values.yaml (kubeshark v53.6.0, 일부) tolerations: hub: [] workers: - operator: Exists effect: NoExecute front: []

→ worker는 key와 상관없이 effect가 NoExecute인 taint만 허용한다는 뜻이에요.

Taint 문서에는 key가 비어 있으면 operator는 Exists여야 하고 이때 모든 key와 value에 맞는다고 적혀 있어요. 다만 effect는 따로 맞아야 해요. 마스터의 taint는 effect가 NoSchedule이라서 이 toleration과 맞지 않아요. DaemonSet 컨트롤러가 자동으로 붙여 주는 toleration에도 control-plane taint는 없어요(DaemonSet 문서). 11편에서 node-exporter가 마스터에 뜨지 않았던 것과 같은 이유예요.

그래서 보지 못하는 것

마스터에 수집기가 없으니 Kubeshark는 마스터의 네트워크 인터페이스를 지나는 패킷도, 마스터 커널의 함수 호출도 보지 못해요. 마스터 안에서만 오가는 연결(API 서버와 etcd 사이의 연결 등)은 이 구성으로는 볼 수 없다고 봐야 해요. 이 부분은 대시보드에서 따로 확인하지는 않았어요.

반대로 한쪽 끝이 워커에 있는 연결은 워커 쪽에서 잡혀요. 15편 실험에서 마스터가 myweb 파드로 보낸 요청은 받는 쪽 워커에서 잡혔고 출발지는 마스터의 Calico 터널 주소 10.244.235.192로 나왔어요. 마스터가 관여한 연결 중에서는 워커에 닿는 연결만 보이는 셈이에요.

컨트롤 플레인까지 보려면 worker의 toleration에 control-plane taint를 더하면 될 거예요. 시험해 보지는 않았어요.

# values 파일 예 (시험하지 않음) tap: tolerations: workers: - operator: Exists effect: NoExecute - key: node-role.kubernetes.io/control-plane operator: Exists effect: NoSchedule

→ 기본값의 NoExecute 허용은 그대로 두고 마스터의 NoSchedule taint를 허용하는 줄을 더한 값이에요. values의 목록은 통째로 바뀌기 때문에 기본값 줄도 다시 적었어요.

다만 마스터도 2 CPU·4GiB VM이고 컨트롤 플레인이 함께 돌아요. 6절에서 볼 수집기 메모리(노드당 0.7GiB 안팎)가 그 위에 더해져요. 라이선스의 노드 수는 수집기가 없는 지금도 이미 4로 셌기 때문에(5절) 이번 화면 기준으로는 마스터를 넣어도 노드 수가 늘지 않을 거예요.

5. 대시보드는 어디서 열리고 언제 잠기나

ks proxy는 명령을 실행한 VM의 127.0.0.1에 열린다

첫 tap을 끝낼 때 안내받은 대로 마스터에서 ks proxy를 실행했어요(줄 앞의 시각은 뺐어요).

→ 마스터의 127.0.0.1:8899에 프록시를 열어 front에 닿아 보고 안 되자 front 파드로 port-forward를 시도했지만 파드 안의 8080 포트가 연결을 거부해 실패했다는 뜻이에요.

이 로그에서 두 가지를 알 수 있어요. 첫째, proxy는 마스터 VM의 127.0.0.1에 열려요. v53.6.0의 proxy.go를 보면 CLI는 proxy-host(기본값 127.0.0.1)의 8899 포트에 작은 HTTP 서버를 열고 요청을 API 서버의 Service 프록시 경로(/api/v1/namespaces/default/services/kubeshark-front:80/proxy)로 넘겨요. 이 방법이 안 되면 front 파드로 port-forward를 열어요. 어느 쪽이든 CLI를 실행한 기계의 127.0.0.1이라서 마스터 VM 안에서만 닿아요. 마스터에는 브라우저도 없어서 두 번째 tap의 끝에는 xdg-open을 찾지 못했다는 오류가 찍혔어요.

둘째, connection refused는 시점 문제였어요. 오류 원문은 파드의 네트워크 네임스페이스 안에서 localhost:8080에 연결하지 못했다는 내용이에요. 네트워크 네임스페이스는 이미 있었는데 그 안에서 8080을 듣는 프로세스가 없었다는 뜻이에요. 20:46의 파드 목록에서 front는 아직 ContainerCreating이었고 front 이미지를 받는 데는 대기 시간까지 2분 4.5초가 걸렸어요. ks proxy를 실행한 시각은 20:45:43~20:46:27이라서 front 컨테이너가 뜨기 전이었어요. 20:47:44에 확인했을 때는 front가 Running이었어요.

Mac에서는 마스터 VM의 127.0.0.1에 닿을 수 없어요. 그래서 Mac의 kubectl로 API 서버를 거치는 port-forward를 Mac의 localhost에 열었어요. 9편에서 Headlamp를 열 때 쓴 방법과 같아요.

mac$ kubectl -n default port-forward svc/kubeshark-front 8899:80 Forwarding from 127.0.0.1:8899 -> 8080 Forwarding from [::1]:8899 -> 8080 mac$ curl -s -o /dev/null -w "front %{http_code}\n" http://127.0.0.1:8899/ front 200

→ Service의 80 포트가 가리키는 front 컨테이너의 8080을 Mac의 8899로 이었고 http://127.0.0.1:8899/가 200으로 응답했다는 뜻이에요. 그림 5가 이렇게 연 화면이에요.

문서에 나온 다른 방법도 있어요. 차트 README의 tap.proxy.host 항목에는 0.0.0.0으로 바꾸면 바깥에 열린다고 적혀 있어요. 설치 문서에서는 Ingress 컨트롤러를 가장 권장하는 방법으로 꼽아요. 그런데 요금제 문서의 Community 항목에는 SSO도, 권한 관리도, 민감 정보 마스킹도 없다고 적혀 있어요. 이 대시보드에는 클러스터 안의 HTTP 요청과 응답이 그대로 보여요. Community 판을 인증 없이 바깥에 열면 그 주소에 닿는 누구나 클러스터의 트래픽을 읽을 수 있어요.

💡 실무에서는: 대시보드는 port-forward로 열어요
• 대시보드를 볼 사람의 PC에서 kubectl port-forward svc/kubeshark-front 8899:80를 실행하세요. API 서버를 거치니 kubeconfig 자격 증명이 있는 사람만 열 수 있어요
• CLI를 PC에 설치했다면 그 PC에서 kubeshark proxy를 실행해도 돼요. 소스로 보면 그 PC의 127.0.0.1에 열리는데 이번에는 시험하지 않았어요
• 열기 전에 kubectl -n default rollout status deploy/kubeshark-front로 front가 준비됐는지 먼저 확인하세요. 이미지를 받는 동안에는 connection refused가 나요
• proxy-host를 0.0.0.0으로 바꾸거나 Community 판의 대시보드를 인증 없이 Ingress로 여는 것은 피하세요

무료 한도: 문서에는 3노드·60파드, 화면에는 Node limit 4/3

요금제 문서를 보면 무료인 Community는 "노드 3대 또는 파드 60개까지의 클러스터(Clusters of up to 3 nodes or 60 pods)"에서 쓸 수 있고 인터넷 연결이 필요해요. 라이선스 문서에는 Community 사용자도 License Portal에서 키를 받아 Helm 값 license로 넣는다고 나와 있어요. 그리고 "Community 라이선스는 인터넷 연결이 살아 있어야 하고 텔레메트리가 성공해야 라이선스가 유효하다"고 적혀 있어요. tap 로그에도 텔레메트리가 켜져 있다는 줄(Telemetry enabled=true)이 찍혔어요. 차트 README에는 tap.telemetry.enabled가 익명 사용 통계를 모으는 설정으로 적혀 있어요.

우리는 키를 넣지 않았어요. 그래도 설치하고 약 20분 동안은 아무 창 없이 대시보드를 썼어요. 그러다 21:05~21:06 무렵 화면에 이 창이 떴어요.

그림 6. 설치 약 20분 뒤 로그인하라는 창이 떴다. 노드 칸은 4/3이었다
LOG IN TO CONTINUE Information - Please log in to continue using Kubeshark! Node limit: 4/3 Pod limit: 29/60 Expires: Never Features: realtime, snapshot [Login/Signup]

→ 계속 쓰려면 로그인하라는 안내이고 노드는 한도 3대에 4대, 파드는 한도 60개에 29개로 셌다는 뜻이에요.

창 뒤의 목록은 Preparing에 멈춰 있었고 표시된 항목은 0개였어요. 창이 뜬 이유는 화면에 따로 적혀 있지 않았어요. 눈에 띄는 것은 노드 칸이에요. 수집기는 워커 3대에만 떠 있었는데 노드 수는 4로 셌어요. 이 화면은 수집기가 뜬 노드가 아니라 클러스터의 노드 전체를 센 것으로 보여요. 파드 29개는 처음 대상 23개에 그사이 15편 실험용으로 default에 띄운 파드 6개(myweb 5개, loadgen 1개)를 더한 수와 같아요. 세는 기준은 문서에서 찾지 못했어요.

한도를 넘었을 때 어떻게 되는지는 요금제 문서에도 라이선스 문서에도 나오지 않아요. v53.1.0 릴리스 노트에 "노드·파드 한도를 넘었을 때 Community 라이선스의 유예 용량을 늘렸다(Extend community license grace capacity on node and pod limit overflow)"는 줄이 있을 뿐이에요. 우리가 20분 동안 창 없이 쓴 것이 이 유예 때문인지는 확인하지 못했어요. 로그인은 해 보지 않아서 로그인하면 창이 풀리는지도 확인하지 못했어요. 창이 뜬 뒤로는 대시보드 화면을 더 찍지 못했어요.

⚠️ 주의: 수집기를 3노드에만 띄워도 노드는 4대로 셌어요
수집기를 3노드에만 띄우면 Community 한도 안에 들 거라고 생각하기 쉬워요. 이번에는 마스터에 수집기가 없었는데도 노드 칸이 4/3이었어요. 노드가 4대 이상인 클러스터에 Community 판을 상시 설치할 계획이라면 이 창이 뜨는지부터 확인해 두세요. 공식 문서로 확인한 사실은 "노드 3대 또는 파드 60개"라는 한도와 인터넷 연결·텔레메트리 조건까지예요.

6. 워커 노드마다 0.7GiB를 쓰는 수집기, 대상을 좁히면 줄어들까

강의 슬라이드에는 "Kubeshark는 Network, Memory 자원을 많이 사용하므로 kubeshark tap 명령 사용 시 대상을 정확히 지정하여 Trace하는 것을 권장"한다는 문장이 있었어요. 강의에서 중요하다고 짚은 장이에요. 얼마나 쓰는지부터 쟀어요. 11편에서 띄운 Prometheus(NodePort 30003)에 cAdvisor가 내놓는 컨테이너별 메모리를 물었어요.

대상이 전체일 때

# 20:59:30, 대상: 전체 (ks tap 기본값, 네임스페이스 6개) mac$ curl -s http://192.168.64.3:30003/api/v1/query --data-urlencode 'query=sum by (pod, container) (container_memory_working_set_bytes{namespace="default", pod=~"kubeshark.*", container!=""})' kubeshark-front-7fb9788cdd-w7whb kubeshark-front 3 MiB kubeshark-hub-fbd9d8db-zcsjv hub 75 MiB kubeshark-worker-daemon-set-kdxl2 sniffer 359 MiB kubeshark-worker-daemon-set-kdxl2 tracer 422 MiB kubeshark-worker-daemon-set-wq4ps sniffer 314 MiB kubeshark-worker-daemon-set-wq4ps tracer 403 MiB kubeshark-worker-daemon-set-zkf86 sniffer 277 MiB kubeshark-worker-daemon-set-zkf86 tracer 418 MiB

→ Prometheus에 Kubeshark 파드의 컨테이너별 working set 메모리를 묻고 MiB 단위로 출력했다는 뜻이에요.

📖 용어: working set 메모리
컨테이너가 쓰는 메모리 가운데 커널이 쉽게 비울 수 없는 부분이에요. cAdvisor는 메모리 사용량에서 비활성 파일 캐시를 뺀 값을 container_memory_working_set_bytes라는 이름으로 내놓아요. 컨테이너가 실제로 차지한 메모리를 볼 때 이 지표를 써요.

노드별로 sniffer와 tracer를 더하면 worker1(wq4ps)이 717MiB, worker2(kdxl2)가 781MiB, worker3(zkf86)이 695MiB예요. VM에 준 메모리 4GiB(4,096MiB)의 17.0~19.1%에 해당해요. worker2에는 hub(75MiB)와 front(3MiB)도 떠 있어서 그 노드에서 Kubeshark가 쓴 메모리는 859MiB, 약 21%였어요.

이 숫자를 차트 기본값과 나란히 놓아 봤어요. v53.6.0 차트의 values와 CLI 기본 설정에서 sniffer와 tracer의 requests는 각각 CPU 50m, 메모리 50Mi이고 limits는 메모리 5Gi예요. CPU limit은 "0"으로 되어 있어서 템플릿이 아예 적지 않아요. 이번 설치에 실제로 들어간 값은 클러스터에서 출력해 보지 않았어요.

그림 7. 워커 노드 메모리 4GiB 가운데 수집기가 쓴 양과 스케줄러가 잡아 둔 양(requests)

스케줄러는 requests를 보고 파드를 놓을 노드를 정해요. 그러니 스케줄러가 worker 파드 하나에 잡아 두는 메모리는 50Mi 두 개, 100Mi예요. 실제로는 그 7~8배를 썼어요. 스케줄러가 계산한 것보다 노드마다 메모리가 0.6~0.7GiB 적게 남아 있었던 셈이에요. 차트 기본값대로라면 limit은 컨테이너마다 5Gi라서 노드 메모리 4GiB보다 커요. 그렇다면 이 노드에서는 컨테이너 단위의 메모리 상한이 사실상 걸려 있지 않은 셈이에요.

메모리 말고 디스크도 써요. tap 로그의 "Kubeshark will store the traffic up to a limit (per node) … limit=10Gi"는 노드마다 트래픽을 10Gi까지 저장하고 한도에 닿으면 오래된 TCP/UDP 스트림부터 지운다는 뜻이에요. 템플릿에서 이 저장 공간은 sizeLimit이 10Gi인 emptyDir이에요. emptyDir은 노드의 저장 장치에 만들어지니 노드 디스크의 여유도 함께 봐야 해요.

CPU는 대상을 좁힌 뒤에 2분 평균으로 sniffer 28~41m, tracer 17~30m였어요. 노드별로 더하면 45~62m라서 노드의 CPU 2개(2000m)의 2~3%예요.

슬라이드 명령을 그대로 실행하면 calico는 잡히지 않는다

슬라이드의 예시 명령은 kubeshark tap -n default "(calico*|myweb*)"였어요. calico 파드와 myweb 파드만 보겠다는 의도로 읽혀요. 21:08:21에 그대로 실행했어요.

master$ kubeshark tap -n default "(calico*|myweb*)" INF tapRunner.go:54 > Kubeshark will store the traffic up to a limit (per node). ... limit=10Gi INF tapRunner.go:72 > Targeting pods in: namespaces=["default"] INF tapRunner.go:139 > Targeted pod: myweb-859c4764d4-4tjzk INF tapRunner.go:139 > Targeted pod: myweb-859c4764d4-5xtpv INF tapRunner.go:139 > Targeted pod: myweb-859c4764d4-k2hfq INF tapRunner.go:139 > Targeted pod: myweb-859c4764d4-n9rd8 INF tapRunner.go:139 > Targeted pod: myweb-859c4764d4-v87c6 INF tapRunner.go:94 > Found an existing installation, skipping Helm install...

→ 대상 네임스페이스가 default 하나로 줄었고 그 안에서 이름이 맞는 파드는 myweb 5개였으며 Helm 설치는 다시 하지 않았다는 뜻이에요.

calico 파드는 하나도 잡히지 않았어요. calico-node와 calico-kube-controllers는 kube-system 네임스페이스에 있는데 -n default가 대상 네임스페이스를 default 하나로 정했기 때문이에요. CLI 소스(provider.go)를 보면 지정한 네임스페이스마다 파드를 나열한 뒤 그 안에서만 이름을 정규식에 맞춰 봐요. 슬라이드의 의도대로 calico까지 보려면 네임스페이스도 함께 줘야 해요. -n은 여러 값을 받는 옵션이라 -n default,kube-system으로 쓸 수 있을 거예요. 이 형태는 시험하지 않았어요.

정규식도 의도와 조금 달라요. calico*를 셸 와일드카드로 읽으면 "calico로 시작하는 이름"이지만 정규식에서 *는 바로 앞 글자 하나를 0번 이상 반복한다는 뜻이에요. 그래서 calico*는 "calic 뒤에 o가 0개 이상", myweb*는 "mywe 뒤에 b가 0개 이상"이에요. 그리고 CLI는 Go의 MatchString으로 파드 이름을 맞춰 봐요. Go 문서에 따르면 MatchString은 문자열 안에 정규식과 맞는 부분이 하나라도 있는지를 봐요. 앞뒤를 고정하지 않으니 calico*는 이름 어딘가에 calic만 있어도 맞아요. 이번에는 결과에 차이가 없었지만 "calico나 myweb으로 시작하는 파드"를 뜻하려면 ^(calico|myweb)로 쓰는 쪽이 정확해요.

"Found an existing installation, skipping Helm install"도 눈여겨볼 줄이에요. 1절에서 본 대로 tap은 기존 설치가 있으면 Helm 설치를 건너뛰고 kubeshark-config-map의 POD_REGEX와 NAMESPACES 같은 값을 다시 써요(tapRunner.go의 updateConfig). worker DaemonSet은 그대로라서 수집기는 여전히 워커 3대에 컨테이너 두 개씩 떠 있어요. 대상을 좁히는 것은 수집기를 줄이는 일이 아니라 수집기가 처리할 파드를 고르는 조건을 바꾸는 일이에요.

대상 지정 문서에는 이 필터를 잘 쓰면 컴퓨팅 자원 사용을 크게 줄일 수 있다고 적혀 있어요. 좁힌 지 약 4분 뒤인 21:12:54에 같은 질의를 다시 실행했어요.

그림 8. 대상을 좁히기 전(20:59:30)과 좁힌 지 약 4분 뒤(21:12:54)의 컨테이너별 메모리

좁힌 뒤 sniffer는 313~398MiB, tracer는 404~425MiB였어요. 좁히기 전(sniffer 277~359MiB, tracer 403~422MiB)과 비슷하거나 조금 많았어요. 노드별 합은 733~823MiB예요. hub만 75MiB에서 46MiB로 줄었어요.

그렇다고 "좁혀도 메모리는 그대로"라고 결론 내리기는 어려워요. 두 측정은 조건이 달랐어요. 앞의 측정은 15편의 트래픽 실험이 돌던 중이었고 대시보드도 정상이었어요. 뒤의 측정은 트래픽 실험이 없었고 대시보드는 5절의 로그인 창으로 잠긴 상태였어요. 4분이라는 시간도 짧아요. 이번에 확인한 것은 수집기가 워커 노드마다 0.7GiB 안팎을 쓰고 대상을 좁힌 지 4분 안에는 그 값이 줄지 않았다는 데까지예요.

💡 실무에서는: tap 대상은 이렇게 정해요
• 네임스페이스는 -n으로, 이름은 정규식으로 따로 정해요. 정규식은 파드 이름에만 적용되고 네임스페이스 조건을 넘지 않아요
• "~로 시작하는 이름"은 ^를 붙여 ^(calico|myweb)로 써요. 셸 와일드카드의 *를 그대로 쓰면 뜻이 달라져요
• CLI 소스에는 실제로 tap하지 않고 정규식에 맞는 파드만 보여 주는 --dry-run 옵션이 있어요(옵션 설명: "Preview of all pods matching the regex, without tapping them"). 다만 그 목록도 4절에서 본 미리보기예요
• 대상을 좁혀도 worker DaemonSet은 워커마다 그대로 떠 있어요. 수집기가 쓰던 메모리를 노드에 돌려주려면 kubeshark clean으로 지워야 해요

정리: kubeshark clean

실습을 마치고 21:13:45에 kubeshark clean으로 지웠어요.

master$ kubeshark clean INF helm.go:177 > Starting delete for "kubeshark-worker-network-policy" NetworkPolicy INF helm.go:177 > Starting delete for "kubeshark-hub-network-policy" NetworkPolicy INF helm.go:177 > Starting delete for "kubeshark-front-network-policy" NetworkPolicy INF helm.go:177 > Starting delete for "kubeshark-dex-network-policy" NetworkPolicy INF helm.go:177 > purge requested for kubeshark INF clean.go:28 > Uninstalled the Helm release: kubeshark

릴리스를 지우면 Helm이 그 릴리스로 만든 리소스를 함께 지워요. 15편 실험용 myweb과 loadgen은 kubectl로 따로 만든 것이라 Helm 릴리스와 상관이 없어서 남겨 뒀어요.

✍️ 오늘의 요약
kubeshark tap 한 줄은 default 네임스페이스에 Helm 릴리스(리소스 21개)를 만들고 워커 노드마다 privileged·hostNetwork 수집기를 띄워요.

수집기는 노드의 /까지 읽기 전용으로 붙이고 ServiceAccount에는 클러스터 전체를 읽는 권한과 NetworkPolicy를 만들고 지우는 권한이 있어요. 마스터에는 control-plane taint를 허용하는 toleration이 없어서 수집기가 뜨지 않았고 CLI가 고른 23개 가운데 마스터의 파드 7개는 대시보드에서 빠졌어요. 대시보드는 VM 안의 ks proxy 대신 Mac에서 port-forward로 열었어요. 메모리는 워커 노드마다 0.7GiB 안팎을 썼는데 차트의 requests는 컨테이너당 50Mi였어요. Community 한도는 문서상 3노드·60파드이고 이번 화면은 수집기가 없는 마스터까지 4노드로 셌어요. Kubeshark가 사이드카 없이 파드의 트래픽을 보는 대가는 노드마다 떠 있는 root에 가까운 수집기예요. 그 수집기는 지우기 전까지 계속 떠 있어요.
