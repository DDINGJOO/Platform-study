1. 다섯 번 재시작하는 동안 파드 UID와 IP는 그대로였다

kubelet이 재시작하는 건 파드인가 컨테이너인가? 컨테이너예요. 위 출력에서 restarts가 0에서 5까지 올라가는 동안 파드 객체는 하나였어요. UID가 같으니 API 서버에 저장된 파드가 지워졌다가 새로 만들어진 적이 없어요. IP가 같다는 것은 파드의 샌드박스, 곧 pause 컨테이너가 쥔 네트워크 네임스페이스도 그대로였다는 뜻이에요(43편). kubelet은 그 샌드박스 안에서 끝난 컨테이너만 새로 띄웠어요.

📖 용어: CrashLoopBackOff
컨테이너가 끝난 뒤 kubelet이 다시 띄우기 전에 기다리는 상태를 가리키는 대기 사유예요. 컨테이너 상태의 state.waiting.reason에 적혀요. 파드의 phase 값이 아니고 쿠버네티스에 CrashLoopBackOff라는 phase는 없어요.
📖 용어: restartCount와 lastState
status.containerStatuses[]의 필드예요. restartCount는 이 파드 안에서 그 컨테이너를 다시 띄운 횟수이고 lastState.terminated는 직전 실행이 끝난 기록(exitCode, reason, finishedAt)이에요. kubectl logs --previous가 보여 주는 것도 그 직전 실행의 로그예요.

파드를 새로 만드는 것은 kubelet이 아니라 ReplicaSet 같은 컨트롤러의 일이에요. 파드 객체가 지워지면 컨트롤러가 새 이름, 새 UID의 파드를 만들고 스케줄러가 다시 노드를 고르고 새 IP를 받아요(60편). crashy는 컨트롤러 없이 만든 단독 파드였지만 지워지지 않았으니 그 일은 일어나지 않았어요.

이 구분은 백오프에도 이어져요. kubelet은 재시작을 미룰 시간을 컨테이너마다 키 하나로 기억하는데, v1.37.2 helpers.go의 키에는 파드 UID가 들어가요(81-k8s-v1.37.2-backoff-status-excerpts.txt).

func GetBackoffKey(pod *v1.Pod, container *v1.Container) string { // Include stable identifiers (name, namespace, uid) as well as any // fields that should reset the backoff when changed. key := []string{ pod.Name, pod.Namespace, string(pod.UID), container.Name, container.Image, container.Resources.String(), } ...

→ 파드를 지워서 컨트롤러가 새 파드를 만들면 UID가 달라져 백오프가 처음부터 시작돼요. 같은 파드여도 컨테이너의 이미지나 자원 설정을 바꾸면 키가 바뀌어 역시 처음부터예요. 반대로 지운 파드를 다시 만들어도 원인이 그대로면 같은 실패를 처음부터 다시 겪어요.

💡 CrashLoopBackOff 파드를 만나면
• kubectl logs <파드> --previous로 죽은 실행의 로그를 봐요. 그냥 logs는 지금 막 다시 뜬 실행의 로그예요
• kubectl get pod <파드> -o jsonpath='{.status.containerStatuses[0].lastState.terminated}'로 exitCode와 reason을 봐요. 137이면 SIGKILL(메모리 초과 등), 1이면 앱이 스스로 끝낸 경우가 많아요
• RESTARTS 칸과 BackOff 이벤트의 count가 늘고 있으면 kubelet이 계속 다시 띄우는 중이에요. 파드를 지우면 백오프는 초기화되지만 원인은 남아요

2. 첫 재시작은 바로, 그다음은 끝난 시각부터 10초·20초·40초·80초를 기다린다

kubelet이 재시작 여부를 정하는 코드는 v1.37.2 kuberuntime_manager.go의 doBackOff예요.

// Use the finished time of the latest exited container as the start point to calculate whether to do back-off. ts := cStatus.FinishedAt key := GetBackoffKey(pod, container) if backOff.IsInBackOffSince(key, ts) { m.recorder...Eventf(containerRef, v1.EventTypeWarning, events.BackOffStartContainer, "Back-off restarting failed container %s in pod %s", container.Name, format.Pod(pod)) backoff := backOff.Get(key) err := fmt.Errorf("back-off %s restarting failed container=%s pod=%s", ...) return true, err.Error(), kubecontainer.NewBackoffError(kubecontainer.ErrCrashLoopBackOff, ts.Add(backoff)) } backOff.Next(key, ts) return false, "", nil

→ 기준 시각은 컨테이너가 끝난 시각(FinishedAt)이에요. 끝난 지 아직 백오프 시간이 지나지 않았으면 BackOff 이벤트를 남기고 이번에는 시작하지 않아요. 지났으면 백오프를 다음 단계로 올리고 컨테이너를 시작해요.

📖 용어: flowcontrol.Backoff
client-go에 들어 있는 백오프 도구예요. 키마다 현재 대기 시간과 마지막 갱신 시각을 기억하고 Next를 부를 때마다 대기 시간을 두 배로 늘리되 최댓값에서 멈춰요. kubelet은 flowcontrol.NewBackOff(10초, 300초)로 만들어서 대기 시간 자체에는 무작위 값을 더하지 않아요.

첫 재시작이 바로 일어난 이유도 여기서 나와요. 처음 끝난 컨테이너에는 키가 아직 없어서 IsInBackOffSince가 false를 돌려줘요. 그래서 기다리지 않고 시작하면서 Next가 키를 10초로 만들어요. 두 번째로 끝났을 때 비로소 10초를 기다리고 그 뒤로 20초, 40초, 80초, 160초, 300초로 올라가요. 두 실행의 간격을 백오프와 나란히 놓으면 이래요. 두 번째 실행은 3절의 watch 실험이에요(81-crashloop-watch.txt).

간격은 컨테이너 상태의 초 단위 시각(finishedAt, startedAt)으로 잰 값이라 1초 안팎의 오차가 있어요. 백오프 단계는 두 실행에서 같았는데 더해진 시간은 실행마다 달랐어요. 이 차이는 3절에서 봐요.

그림 1. 주황 막대는 정해진 백오프이고 빨간 꼬리는 실행마다 달라지는 시간이에요.

백오프가 영원히 쌓이지는 않아요. kubelet.go는 백오프를 만들면서 초기화 조건을 따로 넣었어요.

klet.crashLoopBackOff = flowcontrol.NewBackOff(base, boMax) klet.crashLoopBackOff.HasExpiredFunc = func(eventTime time.Time, lastUpdate time.Time, maxDuration time.Duration) bool { return eventTime.Sub(lastUpdate) > 600*time.Second }

→ 컨테이너가 끝난 시각이 마지막으로 백오프를 올린 시각보다 600초 넘게 뒤라면 그 기록을 만료로 보고 처음부터 다시 시작해요. 마지막 재시작 뒤 10분 넘게 잘 돌다 죽은 컨테이너는 다시 바로 재시작하고 다음 대기는 10초부터예요.

최댓값 300초는 노드마다 낮출 수 있다

초기값과 최댓값을 정하는 newCrashLoopBackOff에는 기능 게이트 두 개가 걸려 있어요(81-k8s-v1.37.2-crashloop-gates.txt). KubeletCrashLoopBackOffMax는 1.32에 KEP-4603의 일부로 알파가 됐고, 2025년 9월 그 KEP에서 갈라져 나온 KEP-5593으로 1.35에 베타가 되면서 기본으로 켜졌어요. 켜져 있으면 kubelet 설정의 crashLoopBackOff.maxContainerRestartPeriod가 최댓값이 돼요. 필드 설명대로 1초에서 300초 사이 값만 받고, 비워 두면 300초예요. 초기값보다 작게 주면 초기값도 그 값으로 내려가요. KEP-4603에 남은 ReduceDefaultCrashLoopBackOffDecay는 1.33 알파이고 기본으로 꺼져 있어요. 코드로는 이 게이트가 켜지면 초기값 1초, 최댓값 60초를 먼저 두지만, 바로 아래에서 KubeletCrashLoopBackOffMax가 켜져 있으면 최댓값을 kubelet 설정 값으로 다시 바꿔요. 그 설정을 비워 두면 기본값이 300초라서, 두 게이트가 모두 켜진 노드의 최댓값은 kubelet 설정이 정해요.

## A. 노드 kubelet 의 백오프 관련 설정과 기능 게이트 (configz, metrics 를 읽기만 함) syncFrequency=1m0s crashLoopBackOff={'maxContainerRestartPeriod': '5m0s'} featureGates=None kubernetes_feature_enabled{name="ContainerRestartRules",stage="BETA"} 1 kubernetes_feature_enabled{name="EventedPLEG",stage="ALPHA"} 0 kubernetes_feature_enabled{name="KubeletCrashLoopBackOffMax",stage="BETA"} 1 kubernetes_feature_enabled{name="ReduceDefaultCrashLoopBackOffDecay",stage="ALPHA"} 0

→ 실험한 worker3의 kubelet은 KubeletCrashLoopBackOffMax가 켜져 있고 최댓값이 기본값 5분(300초)이었어요. 줄인 쪽 게이트는 꺼져 있으니 초기값 10초, 최댓값 300초가 그대로 적용된 상태예요. 이 값은 노드 설정을 읽기만 해서 확인했어요.

💡 백오프 최댓값을 바꾸고 싶다면
• 1.35 이후 노드라면 kubelet 설정 파일에 예를 들어 crashLoopBackOff: {maxContainerRestartPeriod: 30s}를 넣어 그 노드의 최댓값을 낮출 수 있어요. 300초보다 늘리는 값은 받지 않아요
• 노드 단위 설정이라 특정 파드만 바꾸는 방법은 아니에요. 재시작이 잦은 Job만 모아 두는 노드를 따로 둘 때 고려해요
• 이번 글에서는 클러스터 설정을 바꾸지 않았으니 값을 바꾼 뒤의 간격은 직접 확인해야 해요

3. 간격에 더해진 1~17초는 다음 동기화를 예약할 때 붙는 지터의 범위 안이었다

백오프가 정확히 10초, 20초인데 왜 몇 초씩 더 걸렸을까요? kubelet은 백오프가 끝나는 순간에 깨어나도록 타이머를 거는 것이 아니라, 파드를 다시 처리할 시각을 작업 큐에 예약해요. 그 예약 시각에 무작위 값이 붙어요.

📖 용어: PLEG (Pod Lifecycle Event Generator)
kubelet이 컨테이너 런타임의 상태를 주기적으로 다시 읽어 컨테이너 시작·종료 같은 변화를 이벤트로 만드는 부분이에요. 기본 방식(generic PLEG)은 1초마다 다시 읽어요. 런타임 이벤트를 받는 EventedPLEG는 1.37에서도 알파이고 위 출력에서도 꺼져 있었어요.
📖 용어: 파드 워커와 동기화(sync)
kubelet이 파드마다 두는 처리 루프예요. 한 번의 동기화에서 파드의 status를 만들고 필요한 컨테이너를 시작하거나 멈춰요. 동기화가 끝나면 다음 동기화 시각을 작업 큐에 넣고 kubelet은 1초마다 때가 된 파드를 꺼내 동기화해요.

컨테이너가 끝나면 PLEG가 1초 안쪽에서 알아채고 동기화가 돌아요. 그 동기화에서 doBackOff가 백오프 중이라고 답하면, 백오프가 끝나는 시각을 담은 오류가 파드 워커까지 올라가요. pod_workers.go의 completeWork가 그 시각으로 다음 동기화를 예약해요.

default: // Error occurred during the sync; back off and then retry. If the error includes a backoff expiration, // wait until then instead of the default to avoid adding extra time to the backoff. backoff := p.backOffPeriod if backoffAt, isBackoffErr := kubecontainer.MinBackoffExpiration(syncErr); isBackoffErr { backoff = backoffAt.Sub(p.clock.Now()) } if backoff < 0 { backoff = 0 } else if backoff > p.resyncInterval { backoff = p.resyncInterval } p.workQueue.Enqueue(podUID, wait.Jitter(backoff, workerBackOffPeriodJitterFactor))

→ 남은 백오프 시간만큼 기다리되 동기화 주기(syncFrequency, 기본 1분)를 넘지 않게 자르고, 거기에 wait.Jitter(d, 0.5)를 씌워요(같은 파일 330행 workerBackOffPeriodJitterFactor = 0.5). wait.Jitter는 d에서 1.5d 사이의 무작위 시간을 돌려줘요. 그러니 재시작은 백오프가 끝난 시각에서 남은 시간의 최대 절반만큼 늦어질 수 있어요.

이 코드는 1.35에 들어왔어요. 이슈 #123602는 예전 동작을 두고 "the error retry period is 10s, which adds up to 10s to the backoff time"이라고 적었어요. 예전에는 파드 워커가 백오프 시각을 모른 채 자기 재시도 주기 10초로 다시 예약해서 백오프에 최대 10초가 더해질 수 있었다는 뜻이에요. PR #133066이 백오프가 끝나는 시각을 오류에 담아 파드 워커까지 올려 보내게 바꿨고 v1.35.0부터 들어 있어요. 지터는 그 뒤에도 남았어요.

관찰과 맞춰 볼게요. 남은 시간은 백오프에서 감지까지 걸린 1초 안팎을 뺀 값이에요. 10초 백오프면 최대 4~5초, 20초면 9~10초, 40초면 19~20초가 더해질 수 있어요. 여기에 1초마다 큐를 확인하는 간격과 컨테이너를 시작하는 시간이 조금 더 붙어요. 첫 실행의 +3, +7, +8과 둘째 실행의 +1, +8, +17은 모두 이 안에 있었어요. 80초 백오프는 1분으로 잘린 뒤 다시 예약되는 경우가 있어 계산이 복잡하고 +8도 그 범위 안이에요. 둘째 실행의 BackOff 이벤트가 컨테이너가 끝난 10:31:15에서 1초 뒤인 10:31:16에 처음 찍힌 것도 감지에 1초 안쪽이 걸린다는 설명과 맞아요. 다만 각 값을 감지 지연, 1초 주기, 지터로 정확히 나누지는 못했어요. 관찰로 말할 수 있는 것은 더해진 시간이 실행마다 달랐고 코드가 허용하는 범위 안이었다는 데까지예요.

STATUS 칸에 CrashLoopBackOff가 보인 시간은 0.1초였다

첫 실행의 출력을 다시 보면 이상한 점이 있어요. 약 1초 간격으로 읽었는데 STATUS 칸에 CrashLoopBackOff가 한 번도 찍히지 않았어요. 백오프 동안에는 계속 Error였어요. 그래서 watch로 API의 모든 변경을 받아 STATUS 칸과 컨테이너 상태 필드를 함께 기록했어요(81-crashloop-watch.txt, 같은 이름의 .sh, 네임스페이스 blog-81).

그림 2. STATUS 칸은 백오프 내내 Error였고 CrashLoopBackOff는 다시 뜨기 직전에만 지나갔어요.

+8.2초에 Error가 된 뒤 +18.3초까지 10초 동안 STATUS는 Error였어요. +18.3초에 CrashLoopBackOff가 찍히고 0.1초 뒤 +18.4초에 Running이 됐어요. 그다음 두 번도 같았어요(+48.3초와 +48.4초, +107.3초와 +107.4초). 그동안 [필드] 줄의 컨테이너 상태는 terminated: Error였고 waiting: CrashLoopBackOff는 재시작 직전 한 번만 나타났어요. BackOff 이벤트는 네 번 기록됐어요.

이 순서는 kubelet이 한 번의 동기화에서 일하는 순서로 설명할 수 있어요. 아래 설명은 코드 순서에서 추론한 것이고 kubelet 로그로 동기화 시점을 확인하지는 않았어요. v1.37.2 kubelet.go의 SyncPod는 2108행에서 status를 먼저 만들고, 2267~2268행에서 컨테이너를 시작한 결과를 reasonCache에 적어요. kubelet_pods.go는 reasonCache에 사유가 있을 때만 컨테이너 상태를 Waiting으로 바꾸고, 없으면 "the container will be restarted soon, so we prefer the original state here"라며 Terminated를 그대로 둬요.

그러니 컨테이너가 죽은 직후의 동기화는 Terminated(Error)로 status를 쓰고, 그다음에 백오프에 걸려 CrashLoopBackOff를 reasonCache에 적어요. 이 사유가 status에 실리는 건 다음 동기화예요. 1.35부터는 다음 동기화가 백오프가 끝날 때로 예약되니, 그 동기화가 status에 CrashLoopBackOff를 쓰자마자 같은 동기화에서 컨테이너를 시작해요. 컨테이너 하나짜리 이 파드에서 CrashLoopBackOff가 0.1초만 보인 이유로 보여요. 컨테이너가 둘인 62편의 파드에서는 waiting(CrashLoopBackOff)이 +14.4초 기록부터 +18.6초에 running이 될 때까지 4초가량 관찰된 적이 있어요. 그때 어떤 동기화가 끼어들었는지는 이번에 확인하지 않았어요.

⚠️ STATUS가 Error로만 보여도 백오프 중일 수 있어요
• 1.37.2 클러스터에서 컨테이너 하나짜리 파드는 백오프 동안 STATUS가 Error로 남았어요. "CrashLoopBackOff가 안 보이니 재시작 루프가 아니다"라고 판단하면 틀려요
• RESTARTS 칸의 숫자가 늘어나는지, kubectl get events --field-selector reason=BackOff의 count가 오르는지로 봐요
• 모니터링에서 waiting.reason == CrashLoopBackOff만 세면 놓칠 수 있어요. restartCount의 증가량을 함께 봐요

4. CrashLoopBackOff 중에도 phase는 Running이고 Failed는 다시 시작하지 않을 때만 된다

그림 2의 [필드] 줄에서 phase는 컨테이너가 처음 뜬 +2.6초부터 끝까지 Running이었어요. STATUS 칸이 Error든 CrashLoopBackOff든 phase는 바뀌지 않았고 Ready만 True와 False를 오갔어요. STATUS 칸은 phase가 아니라 컨테이너의 대기·종료 사유를 먼저 보여 주는 칸이에요. Terminating이 phase가 아닌 것과 같은 이야기이고 63편에서 그 코드를 봤어요.

같은 컨테이너를 restartPolicy만 바꿔 함께 띄운 파드도 150초 뒤에 확인했어요.

## C. 같은 컨테이너를 restartPolicy 만 바꿔 실행한 파드 (생성 약 150초 뒤) [STATUS열] onfailure 0/1 Error restarts=4 [STATUS열] never 0/1 Error restarts=0 [필드] onfailure phase=Running Ready=False restartCount=4 lastExit=1 exit=1 [필드] never phase=Failed Ready=False restartCount=0 lastExit= exit=1

→ 두 파드 모두 STATUS 칸은 Error였어요. OnFailure 파드는 네 번 재시작했고 phase가 Running이었어요. Never 파드는 한 번도 재시작하지 않았고 phase가 Failed였어요. STATUS 칸이 같아도 phase는 달랐어요.

kubelet이 phase를 정하는 곳은 v1.37.2 kubelet_pods.go의 getPhase예요. 실행 중인 컨테이너가 하나도 없고 멈춘 컨테이너가 있을 때의 분기를 옮겼어요. 재시작을 기다리는 컨테이너(Waiting이면서 직전 종료 기록이 있는 컨테이너)도 여기서는 멈춘 컨테이너로 세요.

case running == 0 && stopped > 0 && unknown == 0: if podIsTerminal { ... 모두 성공이면 Succeeded, 아니면 Failed ... } ... if spec.RestartPolicy == v1.RestartPolicyAlways { // All containers are in the process of restarting return v1.PodRunning } if stopped == succeeded { return v1.PodSucceeded } if spec.RestartPolicy == v1.RestartPolicyNever { // RestartPolicy is Never, and all containers are // terminated with at least one in failure return v1.PodFailed } // RestartPolicy is OnFailure, and at least one in failure // and in the process of restarting return v1.PodRunning

→ Failed는 "컨테이너가 실패했다"가 아니라 "모든 컨테이너가 멈췄고 하나라도 실패했으며 다시 시작하지 않을 파드"예요. Always 파드는 모든 컨테이너가 다시 시작하는 중이라 Running이고 OnFailure 파드도 실패한 컨테이너를 다시 띄우는 중이라 Running이에요. 실패로 끝날 수 있는 건 Never 파드와, 지우거나 축출해서 끝나는 중인 파드(podIsTerminal)예요. 63편에서 지우는 중에 SIGKILL로 끝난 Always 파드가 Failed가 된 것이 뒤쪽 경우예요. 이 클러스터는 컨테이너마다 재시작 규칙을 주는 ContainerRestartRules가 켜져 있어 코드상 그 게이트의 분기를 타요. 파드 단위 restartPolicy만 쓴 이번 실험의 결과는 위 분기와 같았어요. 컨테이너별 규칙은 71편에서 봤어요.

그림 3. 지우는 중인 파드를 빼면 Failed로 가는 길은 Never 하나였어요.

phase의 다섯 값 중 Unknown도 잠깐 짚을게요. 노드와 연락이 끊기면 파드가 Unknown이 될 것 같지만 우리 클러스터에서는 그러지 않았어요. 25편에서 worker3의 kubelet을 멈추고 10초마다 확인했을 때 52초 지점에서 노드는 Ready=Unknown이었지만 그 노드 파드는 API 기준으로 Running, ready=False였어요(labs/devops/k8s-study/out/25-kubelet-stop.txt). v1.37.2 노드 컨트롤러의 MarkPodsNotReady는 파드의 Ready 조건만 False로 바꾸고 phase는 건드리지 않아요. 그 뒤 축출 시간이 지나면 파드가 지워지고 대체 파드가 생겨요(50편).

5. conditions는 다섯 개이고 Unschedulable은 type이 아니라 reason이다

파드 conditions를 소개하는 표에는 Initialized, Ready, ContainerReady, PodScheduled, Unschedulable 다섯 줄이 자주 나와요. 실제 파드를 열어 봤어요. 정상 파드 하나와 nodeSelector가 어느 노드와도 맞지 않는 파드 하나를 만들었어요(81-pod-conditions.txt, 같은 이름의 .sh).

## cond-ok phase=Running type=PodReadyToStartContainers status=True reason= type=Initialized status=True reason= type=Ready status=True reason= type=ContainersReady status=True reason= type=PodScheduled status=True reason= ## cond-nonode phase=Pending type=PodScheduled status=False reason=Unschedulable 0/4 nodes are available: 1 node(s) had untolerated taint(s), 3 node(s) didn't match Pod's node affinity/selector. preemption: 0/4 nodes are available: 4 Preemption is not helpful for scheduling.
📖 용어: condition의 type·status·reason
type은 무엇을 확인했는지를 나타내는 이름이고 status는 그 확인 결과(True, False, Unknown)예요. reason은 왜 그 결과인지를 한 단어로, message는 사람이 읽을 설명으로 적어요. 같은 type이 상황에 따라 다른 reason을 가질 수 있어요.

Unschedulable은 condition일까? type으로는 아니에요. 스케줄할 수 없는 파드에는 condition이 PodScheduled 하나뿐이었고 그 status가 False, reason이 Unschedulable이었어요. 노드가 정해지지 않았으니 kubelet이 쓰는 다른 condition은 아예 없었고 phase는 Pending이었어요. API 정의에도 reason으로 나와요.

// staging/src/k8s.io/api/core/v1/types.go (v1.37.2) // PodReasonUnschedulable reason in PodScheduled PodCondition means that the scheduler // can't schedule the pod right now, for example due to insufficient resources in the cluster. PodReasonUnschedulable = "Unschedulable"

표에 Unschedulable이 type으로 남은 데는 이력이 있어요. 예전 버전 문서인 1.16의 pod-lifecycle 문서에는 type 목록에 Unschedulable이 있었고 1.17 문서부터 빠졌어요. 흔히 보는 표에는 단수형 ContainerReady로 적힌 것도 있는데 실제 이름은 복수형 ContainersReady예요.

반대로 표에 흔히 빠지는 것이 PodReadyToStartContainers예요. 샌드박스와 네트워크가 준비됐다는 condition이고 1.37에서 GA가 됐어요. 정상 파드 목록의 맨 앞에 있었어요. 언제 True가 되는지는 63편에서 봤어요. 이 다섯 개 말고도 API에는 DisruptionTarget, PodResizePending, PodResizeInProgress 같은 type이 정의돼 있지만 축출이나 크기 변경 같은 일이 있을 때만 붙어요. Initialized의 문서 설명도 1.16의 "all init containers have started successfully"에서 지금의 "have completed successfully"로 바뀌었어요. init 컨테이너가 시작만 한 것이 아니라 모두 성공하고 끝나야 True예요.

lastProbeTime은 왜 모두 null일까

condition에는 lastProbeTime과 lastTransitionTime 두 시각 필드가 있어요. 정상 파드의 다섯 condition에서 lastProbeTime은 모두 null이었어요(81-status-subresource.txt). 스케줄러가 쓴 Unschedulable 파드의 PodScheduled도 lastProbeTime=null이었어요(81-crashloop-watch.txt D절). API 필드 설명은 "Last time we probed the condition"이지만 kubelet이 다섯 condition을 만드는 generate.go에는 LastProbeTime을 채우는 줄이 없어요. 제가 읽은 kubelet 상태 코드(generate.go, status_manager.go, kubelet_pods.go)에서 이 값을 채우는 곳은 status_manager.go의 크기 변경 condition 하나였어요. 순서나 걸린 시간을 볼 때는 lastTransitionTime을 보고 그 값도 쓴 구성 요소의 시계라는 점(63편)을 기억해요.

6. status는 kubectl edit로 고쳐지지 않고 /status로 덮어도 kubelet이 10초 주기로 되돌린다

kubectl edit로 status를 고칠 수 있을까? 실행 중인 파드 st-demo의 status를 두 경로로 바꿔 봤어요(81-status-subresource.txt, 같은 이름의 .sh).

그림 4. 본 리소스로는 바뀌지 않았고 /status로 바꾼 것은 12초 뒤 kubelet이 다시 채웠어요.

첫째, 본 리소스로 {"status":{"phase":"Failed"}}를 merge 패치했어요. 결과는 patched (no change)였고 phase는 Running 그대로였어요. kubectl edit도 기본으로는 이 본 리소스에 패치를 보내요. API 서버의 파드 저장 규칙인 strategy.go에 이유가 있어요.

func (podStrategy) PrepareForUpdate(ctx context.Context, obj, old runtime.Object) { newPod := obj.(*api.Pod) oldPod := old.(*api.Pod) newPod.Status = oldPod.Status ... func (podStatusStrategy) PrepareForUpdate(ctx context.Context, obj, old runtime.Object) { newPod := obj.(*api.Pod) oldPod := old.(*api.Pod) newPod.Spec = oldPod.Spec newPod.DeletionTimestamp = nil

→ 본 리소스 업데이트는 보낸 status를 버리고 저장돼 있던 status로 되돌려요. 그래서 바뀐 것이 없다는 답이 왔어요. 반대로 /status 경로의 업데이트는 spec을 옛 값으로 되돌려요. 같은 파드인데 spec과 status를 바꾸는 길이 나뉘어 있어요.

📖 용어: status 하위 리소스 (/status subresource)
같은 객체의 status만 바꾸는 별도 API 경로예요(/api/v1/namespaces/<ns>/pods/<이름>/status). RBAC에서도 pods와 pods/status를 따로 허용해요. kubectl edit와 kubectl patch에 --subresource=status를 주면 이 경로를 써요.

둘째, --subresource=status로 conditions에 lab/demo 하나만 넣어 merge 패치했어요. 이번에는 patched였고 conditions가 lab/demo 하나만 남았어요. JSON merge 패치는 목록을 통째로 바꾸기 때문에 kubelet의 다섯 condition이 사라진 거예요. 그런데 12초 뒤에 다시 읽으니 lab/demo PodReadyToStartContainers Initialized Ready ContainersReady PodScheduled였어요. 다섯 개가 돌아왔고 lab/demo는 지워지지 않고 남았어요.

되돌린 것은 kubelet의 status 관리자예요. status_manager.go는 10초마다 모든 파드의 status를 API의 값과 비교하고 다르면 다시 보내요. 비교 함수 위의 주석이 그 이유를 적어 뒀어요.

const syncPeriod = 10 * time.Second ... // needsReconcile compares the given status with the status in the pod manager (which // in fact comes from apiserver), returns whether the status needs to be reconciled with // the apiserver. Now when pod status is inconsistent between apiserver and kubelet, // kubelet should forcibly send an update to reconcile the inconsistence, because kubelet // should be the source of truth of pod status.

→ API 서버의 파드 status와 kubelet이 기억하는 status가 다르면 kubelet이 강제로 다시 보낸다는 뜻이고 이유는 "kubelet should be the source of truth of pod status"예요. 12초는 10초 주기와 맞는 관찰이에요.

lab/demo가 남은 이유도 같은 파일에 있어요. 다시 보낼 status를 만드는 mergePodStatus는 API에 있던 condition 가운데 kubelet 소유가 아닌 것은 그대로 두고, kubelet 소유인 것만 자기 값으로 채워요. kubelet 소유 목록(pod_status.go)에는 PodScheduled, Ready, Initialized, ContainersReady와 크기 변경 condition이 있고, PodReadyToStartContainers는 기능 게이트를 거쳐 들어가요. 출력에서 lab/demo가 맨 앞에, 다섯 개가 그 뒤에 붙은 순서도 이 함수의 순서와 같아요.

그림 5. 사용자의 패치는 한 번이고 kubelet의 비교는 10초마다 돌아요.

그렇다고 파드 status를 kubelet 혼자 쓰는 것은 아니에요. 노드가 정해지기 전에는 스케줄러가 PodScheduled=False, Unschedulable을 써요. 노드와 연락이 끊기면 노드 컨트롤러가 Ready를 False로 바꿔요. 축출할 때는 DisruptionTarget이 붙고, kubelet은 이 condition을 "함께 쓰는" 것으로 따로 다뤄요. 정리하면 파드가 노드에 올라간 뒤 phase와 컨테이너 상태, 자기 소유 condition은 kubelet이 기준이 되어 계속 맞추고, 다른 구성 요소가 쓴 condition은 kubelet이 지우지 않고 남겨 둬요.

⚠️ status를 고치지 말고 원인을 고쳐요
• CrashLoopBackOff 파드의 phase를 Failed로 바꾸거나 Ready를 True로 바꿔도 본 리소스로는 바뀌지 않고 /status로 바꾼 값은 kubelet이 다음 비교에서 되돌려요
• 고칠 곳은 spec(이미지, 명령, 환경 변수, 프로브)이나 그 컨테이너가 기대하는 외부 조건이에요. Deployment라면 템플릿을 고쳐 새 파드가 만들어지게 해요
• 외부 도구가 파드 상태에 신호를 남겨야 한다면 kubelet 소유가 아닌 자기 condition type을 /status로 쓰고 spec.readinessGates로 연결하는 방식이 있어요. 이번 글에서 readinessGates는 실험하지 않았어요

✍️ 오늘의 요약

CrashLoopBackOff에서 kubelet이 다시 띄운 것은 파드가 아니라 컨테이너였어요. 다섯 번 재시작하는 동안 파드 UID와 IP는 그대로였고 파드를 새로 만드는 것은 파드가 지워졌을 때 컨트롤러가 하는 일이에요. 백오프 키에 파드 UID가 들어가서 새 파드는 백오프도 처음부터예요.

첫 재시작은 백오프 기록이 없어 바로 일어났고 그다음은 컨테이너가 끝난 시각부터 10·20·40·80초를 기다렸어요. 1.35부터 kubelet은 백오프가 끝나는 시각에 다음 동기화를 예약하지만 남은 시간의 최대 절반까지 지터를 붙이고, 두 실행에서 더해진 1~17초는 그 범위 안이었어요. STATUS 칸은 백오프 내내 Error였고 CrashLoopBackOff는 재시작 0.1초 전에만 보였는데, 코드 순서로 보면 이것도 이 예약 방식 때문으로 보여요. 그동안 phase는 Running이었고, 이번 실험에서 Failed는 다시 시작하지 않는 Never 파드에서만 나왔어요.

Unschedulable은 PodScheduled=False의 reason이었고 lastProbeTime은 비어 있었어요. status는 본 리소스로는 바뀌지 않았고 /status로 덮어도 kubelet이 10초 주기의 비교로 자기 condition을 다시 채웠어요. 파드 상태가 이상하면 status를 고칠 게 아니라 status를 쓰는 쪽이 왜 그렇게 썼는지를 읽어야 해요.
