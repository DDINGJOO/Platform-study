containers 항목에 이름과 이미지만 적은 파드를 실험용 네임스페이스 w32에 --dry-run=server로 보냈어요. 돌아온 spec에는 제가 쓰지 않은 칸이 여럿 생겨 있었어요. 그 가운데 어드미션 플러그인이 붙이는 칸만 골라 보면 serviceAccountName: default, kube-api-access라는 볼륨과 그 마운트, 300초짜리 toleration 두 개, 그리고 priority: 0이었어요. 그다음 메모리 한도를 건 ResourceQuota를 만들고 같은 파드를 실제로 만들자 403 Forbidden으로 거절됐어요. 그런데 LimitRange 하나를 더 만들고 똑같은 YAML을 다시 보내자 이번에는 저장됐어요.

앞 편과 이번 편의 출발점은 아키텍처 그림 한 장이었어요. 그림 왼쪽에는 kubectl apply -f pod.yaml 요청이 0) TLS, 1) Authentication check, 2) Authorization check, 3) Admission controller를 지나 API 서버로 들어간다고 적혀 있었고 저는 이 그림을 두고 "해석 좀"이라고 물었어요. 32편에서는 앞의 세 칸을 따라가며 401과 403이 어디서 나오는지 봤고 403이 인가와 어드미션 두 곳에서 나온다는 것까지 확인했어요. 이번 편에서는 남은 마지막 칸인 어드미션을 풀어요. 어드미션이 요청의 무엇을 고치고 무엇을 거절하는지, 고치는 일과 거절하는 일의 순서가 왜 결과를 바꾸는지 확인해요.

클러스터는 1~7편에서 만든 실습 환경(Lima VM 4대, kubeadm으로 설치한 쿠버네티스 v1.37.2)이에요. 실험은 32편과 같은 날 전용 네임스페이스 w32에서 했고 끝난 뒤 네임스페이스째 지웠어요.

· 우리 클러스터에서는 어떤 어드미션 플러그인이 돌까? 문서의 목록과 바이너리의 목록은 같을까?

· 어드미션이 거절하면 늘 403일까?
· ResourceQuota에 막히던 파드가 LimitRange 하나로 통과한 이유는 무엇일까?

1. 인가가 보지 못하는 객체 내용은 어드미션이 본다

인가가 볼 수 있는 것은 누가, 어떤 리소스에, 어떤 동작을 하려는가까지예요. 파드에 메모리 한도를 적었는지, 보안 설정을 했는지는 볼 수 없어요. 32편의 kubelet 실험이 좋은 예였어요. worker1의 kubelet 자격으로 물은 can-i delete pods는 yes였는데 worker2에 배정된 파드를 실제로 지우려 하자 node "k8s-worker1" can only delete pods with spec.nodeName set to itself로 막혔어요. 지우려는 파드의 spec.nodeName은 객체를 열어 봐야 알 수 있고 그 확인을 한 것이 NodeRestriction이라는 어드미션 플러그인이었어요.

Authorization 문서에도 특정 객체의 특정 칸에 따라 달라지는 정책은 어드미션 컨트롤러가 맡고 어드미션은 인가가 허락한 요청에만 일어난다고 적혀 있어요. Admission Control 문서에 따르면 어드미션 컨트롤러는 API 서버 바이너리 안에 들어 있는 코드이고 객체를 만들고 고치고 지우는 요청에 적용돼요. API 서버 프록시를 거쳐 파드에 접속하는 것과 같은 별도 동작도 막을 수 있어요. 읽기 요청(get, watch, list)은 어드미션 단계를 아예 거치지 않으므로 어드미션으로 막을 수도 없어요.

📖 용어: 어드미션 플러그인 (mutating, validating)
어드미션 컨트롤러 하나하나를 API 서버에서는 플러그인이라고 불러요. mutating 플러그인은 요청에 담긴 객체를 고칠 수 있고 validating 플러그인은 고치지 못하고 통과 여부만 정해요. 두 역할을 모두 하는 플러그인도 있어요. 문서에 따르면 처리는 두 단계로 나뉘어서 mutating 플러그인이 모두 먼저 돌고 그다음에 validating 플러그인이 돌아요. 어느 단계에서든 하나가 거절하면 요청 전체가 그 자리에서 거절돼요.
그림 1. 이번 실험에서 작동한 플러그인을 v1.37.2 소스에서 실제로 거절하는 단계에 놓은 모습. 고치는 단계의 플러그인도 거절할 수 있다

그림 1은 이번 실험에서 결과를 직접 본 플러그인을 v1.37.2 소스에서 실제로 불리는 단계에 놓은 거예요. API 서버는 mutating 단계에서 각 플러그인의 Admit 함수를, validating 단계에서 Validate 함수를 호출하는데(chain.go) Admit 함수도 요청을 거절할 수 있어요. 없는 ServiceAccount(serviceaccount/admission.go), 없는 네임스페이스(lifecycle/admission.go), 남의 노드 파드(noderestriction/admission.go)에 대한 거절은 모두 Admit 함수에서 나요. LimitRanger의 최댓값 검사, ResourceQuota, PodSecurity는 Validate 함수에서 거절해요. Admission Control 문서에는 NamespaceLifecycle과 NodeRestriction의 Type이 Validating으로 적혀 있어서 이 부분은 문서의 Type 표기와 소스 동작이 달라요. 인가는 요청의 겉모습으로 판단하고 어드미션은 저장될 객체의 내용으로 판단해요.

2. 우리 클러스터에서 도는 어드미션은 바이너리 기본 25개와 NodeRestriction이다

어드미션 플러그인이 바이너리에 든 것만 있는 건 아니에요. Admission Control 문서의 extension points 절에서는 특별한 플러그인 네 개를 따로 소개해요. MutatingAdmissionWebhook과 ValidatingAdmissionWebhook은 API에 등록한 웹훅(외부 HTTP 서버)에 판단을 맡기고 MutatingAdmissionPolicy와 ValidatingAdmissionPolicy는 외부 호출 없이 고칠 내용이나 검사할 조건을 API 객체에 적게 해요. 그래서 먼저 우리 클러스터에 그런 객체가 있는지 봤어요.

그림 2. 웹훅과 정책 객체는 하나도 없었고 기본 플러그인은 바이너리 기준 25개였다

웹훅 설정과 정책 객체는 네 종류 모두 0개였어요. 우리 클러스터에서 요청을 고치거나 거절하는 것은 API 서버 바이너리에 든 플러그인 코드뿐이라는 뜻이에요. 어떤 플러그인이 기본으로 켜지는지는 두 곳에서 확인했어요. 우리 v1.37.2 바이너리의 kube-apiserver --help에는 기본 목록에 25개가 적혀 있었고 Admission Control 문서의 1.37 기본 목록은 20개였어요.

# kube-apiserver --help 의 기본 목록 (v1.37.2 바이너리, 25개, 적힌 순서) NamespaceLifecycle LimitRanger ServiceAccount TaintNodesByCondition PodSecurity Priority DefaultTolerationSeconds DefaultStorageClass StorageObjectInUseProtection PodGroupProtection PersistentVolumeClaimResize RuntimeClass CertificateApproval CertificateSigning ClusterTrustBundleAttest CertificateSubjectRestriction DefaultIngressClass PodTopologyLabels NodeDeclaredFeatureValidator PodResizeValidator MutatingAdmissionPolicy MutatingAdmissionWebhook ValidatingAdmissionPolicy ValidatingAdmissionWebhook ResourceQuota # Admission Control 문서의 Kubernetes 1.37 기본 목록 (20개, 문서에 적힌 순서) CertificateApproval, CertificateSigning, CertificateSubjectRestriction, DefaultIngressClass, DefaultStorageClass, DefaultTolerationSeconds, LimitRanger, MutatingAdmissionPolicy, MutatingAdmissionWebhook, NamespaceLifecycle, PersistentVolumeClaimResize, PodSecurity, Priority, ResourceQuota, RuntimeClass, ServiceAccount, StorageObjectInUseProtection, TaintNodesByCondition, ValidatingAdmissionPolicy, ValidatingAdmissionWebhook 바이너리에만 있는 것: ClusterTrustBundleAttest NodeDeclaredFeatureValidator PodGroupProtection PodResizeValidator PodTopologyLabels 문서에만 있는 것: (없음)

→ 문서 목록 20개는 모두 바이너리 목록에 있었고 바이너리에만 있는 것이 다섯 개였다는 뜻이에요.

다섯 개 가운데 PodTopologyLabels와 NodeDeclaredFeatureValidator는 같은 문서의 플러그인 설명 절에 기능 게이트가 켜지면 쓰인다고 적혀 있어요. 나머지 셋(PodGroupProtection, ClusterTrustBundleAttest, PodResizeValidator)은 이 문서에서 찾지 못했어요. 문서도 켜진 플러그인은 kube-apiserver -h로 직접 확인하라고 안내하니 우리 클러스터에서는 바이너리 쪽 25개를 기준으로 삼았어요. 여기에 kubeadm이 API 서버 매니페스트에 --enable-admission-plugins=NodeRestriction을 넣어 하나를 더 켜요. 이 플래그는 --help 설명대로 기본 목록에 "더해" 켜는 플러그인을 적는 곳이에요.

--help의 플래그 설명 끝에는 "The order of plugins in this flag does not matter"라고 적혀 있어요. 플래그에 적는 순서로 실행 순서를 바꿀 수는 없다는 뜻이고 실행은 문서에 적힌 대로 mutating 단계부터 해요. 우리 클러스터의 어드미션은 웹훅 없이 바이너리 기본 25개와 NodeRestriction 하나로 돌고 있었어요.

3. mutating 플러그인은 보내지 않은 칸을 채운다

mutating 플러그인이 무엇을 고치는지 보려면 저장되기 직전의 객체를 받아 봐야 해요. 실제로 만들면 그 뒤에 스케줄러와 kubelet이 칸을 더 채우니 어드미션이 한 일만 따로 보기 어려워요.

📖 용어: --dry-run=server
요청을 API 서버까지 보내서 인증, 인가, 어드미션, 검증을 모두 거치게 하되 저장만 하지 않게 하는 kubectl 옵션이에요. 어드미션이 고친 결과를 돌려받을 수 있어서 저장될 모습을 미리 보는 데 써요. 클라이언트 쪽에서만 처리하는 --dry-run=client와는 달라요.
그림 3. 이름과 이미지만 보낸 파드에 ServiceAccount, 300초 toleration, priority가 채워졌다

그림 위쪽이 mutating 결과예요. 어드미션이 붙이는 칸만 골라 보니 보내지 않은 칸이 다섯 개 생겼고 맨 아래 resources가 비어 있는 것은 이 네임스페이스에 아직 LimitRange가 없었기 때문이에요(5절). 플러그인별로 나누면 이래요.

ServiceAccount. serviceAccountName을 default로 정하고 API 토큰을 담은 kube-api-access 볼륨을 붙인 뒤 컨테이너의 /var/run/secrets/kubernetes.io/serviceaccount에 마운트했어요. ServiceAccount 관리 문서에 적힌 동작 그대로이고 순서는 이래요. 파드에 serviceAccountName이 없으면 default로 정해요. 그다음 파드가 가리키는 ServiceAccount가 있는지 확인해요. ServiceAccount와 파드 어느 쪽도 automountServiceAccountToken을 false로 두지 않았다면 토큰 볼륨과 마운트를 더해요. 32편에서 본 CoreDNS 같은 파드가 10.96.0.1:443으로 API 서버에 붙을 때 쓰는 토큰이 이렇게 들어가요. 그 토큰의 수명이 어떻게 정해지는지는 10편에서 봤어요.

📖 용어: taint와 toleration
taint는 노드에 붙이는 표시로 "이 표시를 견디지 못하는 파드는 받지 않는다(NoSchedule)" 또는 "이미 있는 파드도 내보낸다(NoExecute)"를 뜻해요. toleration은 파드 쪽에 적는 "이 taint는 견딘다"는 선언이고 NoExecute taint에는 tolerationSeconds로 몇 초 동안 견딜지 적을 수 있어요.

DefaultTolerationSeconds. node.kubernetes.io/not-ready와 node.kubernetes.io/unreachable taint를 NoExecute로 300초 견디는 toleration 두 개를 붙였어요. 문서에 따르면 이 값은 API 서버 플래그 default-not-ready-toleration-seconds와 default-unreachable-toleration-seconds에서 가져오고 기본값은 5분이며 파드에 이미 그런 toleration이 있으면 붙이지 않아요. 25편에서 worker3의 kubelet을 멈췄을 때 노드에 unreachable taint가 붙고도 파드가 바로 쫓겨나지 않은 것도 이 칸 때문이에요. 노드 장애를 알아채는 시간과 이 300초를 합친 이야기는 25편에 있어요.

Priority. priorityClassName을 보고 priority 숫자를 채우는 플러그인이에요. priorityClassName을 적지 않은 이 파드에는 0이 채워졌어요. 문서에는 적은 클래스를 찾지 못하면 파드를 거절한다는 내용도 있어요.

dry-run 결과에는 이 밖에도 imagePullPolicy: IfNotPresent 같은 값이 들어 있었어요(19편 원자료). 이런 값은 어드미션이 아니라 API가 객체를 만들 때 기본값을 채우는 과정에서 들어가요. 스케줄러와 kubelet이 손대기 전에 이미 API 서버 안에서 파드의 모양이 바뀌어 있었어요.

4. 어드미션 플러그인의 거절은 대개 403이지만 404도 있다

그림 3 아래쪽은 거절된 요청 두 개예요. 없는 ServiceAccount nobody를 적은 파드는 pods "sa-missing" is forbidden: error looking up service account w32/nobody: serviceaccount "nobody" not found로 거절됐어요. ServiceAccount 관리 문서에 따르면 이 플러그인은 파드가 가리키는 ServiceAccount가 없으면 파드를 거절하고 default ServiceAccount에도 같은 확인을 해요.

없는 네임스페이스 w32-none에 만들려던 파드는 Error from server (NotFound): ... namespaces "w32-none" not found로 거절됐어요. 이 일은 NamespaceLifecycle 플러그인이 맡아요. 문서에 따르면 이 플러그인은 지우는 중인 네임스페이스에 새 객체를 만들지 못하게 하고 없는 네임스페이스로 온 요청을 거절해요. v1.37.2 소스(lifecycle/admission.go)를 보면 네임스페이스를 저장소에서 찾지 못했을 때 그 NotFound 오류를 그대로 돌려주고 지우는 중인 네임스페이스에는 Forbidden을 돌려줘요. 어드미션이 거절해도 404가 나올 수 있다는 뜻이에요.

세 번째는 네임스페이스 라벨 하나로 거절 기준을 바꾸는 PodSecurity예요.

그림 4. restricted 라벨을 붙이자 있던 파드에는 경고만 나왔고 새 파드는 403으로 거절됐다

Pod Security Admission 문서에 따르면 PodSecurity 플러그인은 네임스페이스 라벨 pod-security.kubernetes.io/<모드>: <수준>에 적힌 Pod Security Standards 수준(privileged, baseline, restricted)으로 파드를 검사하고 enforce 모드에서는 위반한 파드를 거절해요. w32에 enforce=restricted를 붙이자 새 파드 bare2는 allowPrivilegeEscalation, capabilities, runAsNonRoot, seccompProfile 네 칸을 restricted 기준대로 적지 않아서 403을 받았어요. 라벨을 붙이기 전에는 이름만 다른 같은 YAML(bare)이 통과했어요.

⚠️ 주의: Pod Security 라벨은 새로 만드는 파드부터 막아요
• 문서에 따르면 Pod Security 제한은 파드를 만들 때 네임스페이스 단위로 적용돼요. 실험에서도 라벨을 붙이는 요청은 성공했고 이미 있던 bare 파드에는 경고만 나왔어요
• 그래서 enforce를 걸고 나서 한참 뒤 Deployment를 고치거나 파드가 다시 만들어지는 순간에야 처음으로 거절이 나올 수 있어요
• 문서의 모드 표에는 위반해도 허용하면서 사용자에게 경고만 보내는 warn과 감사 로그에만 남기는 audit 모드가 있어요. enforce 전에 warn으로 먼저 걸어 두면 어떤 파드가 걸릴지 미리 볼 수 있어요

거절 메시지를 32편의 인가 거절과 나란히 놓으면 차이가 보여요. 인가에서 막힌 403에는 사용자 이름과 동작이 찍혔어요(User "..." cannot list resource "pods"). 이번에 본 어드미션의 거절 메시지에는 사용자 이름 대신 플러그인이 적은 이유가 붙었어요. 메시지만 보고도 어느 관문에서 막혔는지 가를 수 있어요.

5. LimitRange가 채운 값을 ResourceQuota가 센다

mutating 단계가 먼저 돈다는 순서가 결과를 바꾸는 장면을 직접 보고 싶었어요. 17편에서 Portainer로 메모리 한도를 건 네임스페이스에 배포했을 때 메모리를 적지 않은 Deployment는 파드를 하나도 만들지 못했어요. 그 상황을 w32에서 kubectl로 다시 만들고 LimitRange를 하나 더해 봤어요.

📖 용어: LimitRange와 ResourceQuota
둘 다 네임스페이스에 두는 객체예요. ResourceQuota는 네임스페이스 전체가 쓸 수 있는 자원의 합계 한도를 정하고 ResourceQuota 플러그인(validating)이 그 한도를 넘는 요청을 거절해요. LimitRange는 컨테이너 하나의 기본값과 최솟값·최댓값을 정하고 LimitRanger 플러그인(mutating이면서 validating)이 비어 있는 칸을 기본값으로 채우고 범위를 벗어난 요청을 거절해요.
그림 5. 같은 bare 파드가 LimitRange를 만들기 전에는 must specify로 403, 만든 뒤에는 기본값이 채워져 저장됐다

ResourceQuota mem은 requests.memory와 limits.memory를 각각 256Mi로 제한해요. 이렇게 메모리 한도를 건 쿼터가 있으면 메모리를 적지 않은 파드는 셀 값이 없어서 failed quota: mem: must specify limits.memory for: c; requests.memory for: c로 거절돼요. kubectl의 -v=6 로그를 보면 이 POST 요청의 응답은 403 Forbidden이었어요.

LimitRange mem-default를 만든 뒤 똑같은 파드를 다시 보냈더니 이번에는 저장됐어요. 저장된 파드에는 limits 128Mi, requests 64Mi가 들어 있었고 annotation kubernetes.io/limit-ranger에 "LimitRanger plugin set: memory request for container c; memory limit for container c"라는 기록이 남았어요. 쿼터 사용량도 64Mi/256Mi, 128Mi/256Mi로 올라갔어요. LimitRanger가 mutating 단계에서 빈 칸을 채운 뒤에 ResourceQuota가 validating 단계에서 그 값을 셌기 때문에 같은 파드가 통과했어요.

그다음 160Mi를 적은 파드는 LimitRange 최댓값 192Mi 안쪽이었지만 쿼터에 남은 128Mi를 넘어서 exceeded quota: mem, requested: limits.memory=160Mi, used: limits.memory=128Mi, limited: limits.memory=256Mi로 403을 받았어요. 300Mi를 적은 파드는 쿼터를 따지기 전에 LimitRanger의 검사에 걸려 maximum memory usage per Container is 192Mi, but limit is 300Mi로 거절됐어요. LimitRanger는 칸을 채우기도 하고 범위를 검사하기도 하는 플러그인이에요.

그림 6. ResourceQuota가 보는 것은 내가 보낸 YAML이 아니라 mutating 단계를 거친 뒤의 객체다

17편 원자료와 나란히 놓으면 그때 왜 그랬는지 알 수 있어요. Portainer가 만든 pt-lab 네임스페이스에는 ResourceQuota만 있고 LimitRange는 없었어요. 그래서 메모리를 적지 않은 no-limit의 파드는 pods "no-limit-c85f9544-xd5qx" is forbidden: failed quota: portainer-rq-pt-lab: must specify limits.memory for: nginx; requests.memory for: nginx로 거절됐고 128Mi를 적은 with-limit은 파드가 세 개까지만 만들어지고 그다음 파드부터 is forbidden: exceeded quota: portainer-rq-pt-lab으로 거절됐어요. w32에서 본 순서를 따르면 그 네임스페이스에 기본값을 채워 주는 LimitRange만 있었어도 must specify 거절은 나지 않았을 거예요.

⚠️ 주의: Deployment의 파드가 어드미션에 막혀도 배포 요청은 성공으로 끝나요
• 17편에서 no-limit은 0/2, with-limit은 3/5에서 멈췄는데 Deployment를 만든 요청 자체는 성공했어요. 어드미션에 거절된 것은 제 요청이 아니라 ReplicaSet 컨트롤러가 보낸 파드 생성 요청이었어요
• 그래서 Forbidden 메시지는 배포 요청의 응답이 아니라 ReplicaSet의 FailedCreate 이벤트에 남았고 kubectl get pods에는 실패한 파드가 한 줄도 없었어요
• READY 숫자가 모자라면 kubectl describe rs나 kubectl get events에서 "is forbidden"을 찾아요
💡 실무에서는: 어드미션에서 막혔을 때 보는 순서
• 파드를 직접 만드는 요청이라면 같은 매니페스트를 --dry-run=server로 다시 보내 거절 메시지와 채워질 칸을 저장 없이 확인해요
• 메시지에 quota가 보이면 kubectl -n <네임스페이스> get resourcequota,limitrange로 한도와 기본값이 있는지, PodSecurity가 보이면 네임스페이스의 pod-security 라벨을 봐요
• ResourceQuota만 걸고 LimitRange를 두지 않으면 자원을 적지 않은 매니페스트는 모두 must specify로 막혀요. 쿼터를 걸 때 기본값을 채울 LimitRange를 같이 두면 예상하지 못한 거절이 줄어요

어드미션까지 모두 통과한 요청은 객체 종류별 검증을 거쳐 etcd에 기록돼요. 그 기록이 etcd 키로 어떻게 남는지는 22편에서 봤어요.

ResourceQuota가 세는 것은 내가 보낸 YAML이 아니라 mutating 단계를 거친 객체예요.
