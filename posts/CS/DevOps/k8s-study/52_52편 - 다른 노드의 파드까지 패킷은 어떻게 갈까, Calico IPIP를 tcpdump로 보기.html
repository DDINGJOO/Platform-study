파드에서 다른 노드의 nginx로 curl을 보냈어요. 목적지는 10.244.126.10인데 노드의 eth0를 캡처하니 먼저 보이는 목적지는 192.168.104.4였어요. tcpdump는 한 패킷 안에서 IP를 두 번 출력했고 바깥쪽에는 proto IPIP (4), 안쪽에는 proto TCP (6)가 붙었어요.

51편에서 파드의 eth0와 노드의 cali 장치를 연결했어요. 이번에는 그 장치를 출발점으로, 같은 노드와 다른 노드의 파드까지 실제 요청이 지나는 지점을 대조해요. 라우팅 표만 읽는 것으로 끝내지 않고 TCP 연결 하나의 주소·포트·시퀀스 번호를 여덟 곳에서 맞춰 봤어요.

2026년 11월 14일의 개인 Lima 실습 환경이에요. Kubernetes v1.37.2, Calico v3.33.0이고 파드 대역은 10.244.0.0/16이에요. 아래 주소와 장치 이름은 이 실행에서 얻은 값이며 다른 클러스터에서는 다시 조회해야 해요.

1. 목적지만 바꾸기 위해 파드 세 개를 두 노드에 고정했다

출발지는 worker1의 curl 파드 하나로 고정했어요. nginx 두 개 중 local은 같은 worker1, remote는 worker2에 배치했어요. Service나 DNS를 거치지 않고 각 Pod IP의 80번 포트를 직접 호출해요. 이번에 관측할 것은 kube-proxy의 변환이 아니라 파드 사이의 경로예요.

Pod Node Pod IP 역할 client k8s-worker1 10.244.194.75 curl 출발지 local k8s-worker1 10.244.194.78 같은 노드의 nginx remote k8s-worker2 10.244.126.10 다른 노드의 nginx Node eth0: worker1=192.168.104.3, worker2=192.168.104.4 IPPool: ipipMode=Always, vxlanMode=Never, blockSize=26

Namespace는 calico-blog-52로 분리했어요. 노드의 경로나 정책을 변경하지 않고 해당 파드만 생성했어요. IPPool의 IPIP Always는 다른 노드로 가는 통신의 캡슐화 설정이에요. 같은 노드의 파드끼리도 반드시 터널을 탄다는 뜻은 아니에요.

📖 용어: IPIP와 캡슐화
기존 IP 패킷 앞에 IP 헤더를 하나 더 붙여 노드 사이로 보내는 방식이에요. 안쪽에는 원래 Pod 주소를, 바깥쪽에는 터널 양 끝의 노드 주소를 넣어요. 이 글의 IPIP는 IPv4 안에 IPv4를 넣는 구성이에요.
📖 용어: 5-tuple과 TCP 시퀀스 번호
출발지·목적지 IP, 출발지·목적지 포트, 전송 프로토콜 다섯 값으로 연결을 구분해요. TCP 시퀀스 번호는 TCP 바이트 흐름에서의 위치를 나타내요. SYN은 TCP 연결을 시작하는 패킷이고, 이번에는 그 첫 시퀀스 번호를 비교했어요. IPv4 헤더의 식별 필드인 IP ID도 보조로 대조했어요. 이 값 하나만으로 같은 패킷이라고 판단하지 않아요.

같은 노드 요청에는 출발지 포트 45252, 다른 노드 요청에는 45253을 지정했어요. 캡처를 시작한 뒤 두 요청을 차례로 보냈고 모두 HTTP 200을 받았어요.

# client 파드 안에서 실행한 명령 curl --noproxy '*' --local-port 45252 --connect-timeout 3 --max-time 5 -sS -o /dev/null -w 'HTTP %{http_code} ' http://10.244.194.78/ curl --noproxy '*' --local-port 45253 --connect-timeout 3 --max-time 5 -sS -o /dev/null -w 'HTTP %{http_code} ' http://10.244.126.10/ local: HTTP 200 10.244.194.75:45252 → 10.244.194.78:80 remote: HTTP 200 10.244.194.75:45253 → 10.244.126.10:80

2. 같은 노드의 파드는 cali 장치 두 개 사이로 전달됐다

worker1에서 client IP로 가는 호스트 경로는 cali0e224c51a15, local IP로 가는 경로는 calid971ba37c65를 가리켰어요. 각각 출발 파드와 도착 파드의 노드 쪽 veth예요. client 네트워크 네임스페이스 안의 eth0도 따로 캡처했어요.

📖 용어: 캡처 지점
tcpdump가 패킷을 관찰하는 네트워크 네임스페이스와 인터페이스의 조합이에요. 파드 안의 eth0와 노드의 eth0는 이름만 같고 다른 장치예요. 같은 노드에서도 어느 쪽 장치를 읽는지 명시해야 해요.

45252 연결의 패킷은 client의 eth0, client 쪽 cali, local 쪽 cali에서 각각 12개 보였어요. 출발 SYN의 Pod 주소·포트·시퀀스 번호는 같았고 TTL(라우터를 거칠 때 줄어드는 IPv4 전달 한도)은 출발 쪽 64에서 local 쪽 63으로 줄었어요. 이 세 지점에서 본 해당 연결에는 바깥 노드 IP 헤더가 없었어요.

양쪽 노드 eth0에서는 노드 간 IPIP를 따로 캡처했어요. 그 캡처 안에서도 45252 연결은 발견되지 않았어요. 이 관측은 이번 요청과 캡처 구간에 한정해요. 클러스터의 모든 동작을 이 한 번으로 보장하지는 않아요.

그림 1. 같은 노드의 요청은 로컬 cali로, 다른 노드의 요청은 IPIP 구간으로 이어졌어요.

3. 다른 노드의 Pod IP는 tunl0 경로를 골랐다

이번에는 worker2의 remote로 목적지만 바꿔요. worker1에서 그 Pod IP의 경로를 조회하면 다음 결과가 나왔어요.

worker1$ ip route get 10.244.126.10 10.244.126.10 via 192.168.104.4 dev tunl0 src 10.244.194.64 uid 501 cache mtu 1480

목적지 Pod로 가려면 192.168.104.4 노드 쪽으로 tunl0를 사용하라는 결과예요. 이 명령은 패킷을 보내는 테스트가 아니라 경로 선택 조회예요. 특히 src 10.244.194.64는 이 조회 조건에서 노드가 직접 보낼 때 고를 출발 주소예요. client에서 전달되는 패킷의 주소가 이 값으로 바뀌었다는 증거가 아니에요. 실제 캡처에서는 출발 주소 10.244.194.75가 유지됐어요.

📖 용어: underlay와 overlay
여기서 underlay는 노드 IP끼리 도달하는 네트워크예요. overlay는 그 위에서 Pod IP 패킷을 IPIP로 운반하는 구성이에요. 바깥 헤더는 노드 간 도달에, 안쪽 헤더는 최종 Pod 전달에 사용돼요.

client의 eth0와 호스트 cali에서 보인 45253 SYN은 tunl0에서도 보였어요. 출발지·목적지·포트와 시퀀스 번호는 같았고 내부 IP의 TTL은 64에서 63으로 바뀌었어요. tunl0에서 tcpdump가 출력한 것은 아직 내부 Pod IP 패킷이었어요. 이 화면 하나만으로 외부 IP 헤더까지 확인했다고 쓰면 안 돼요.

⚠️ 숫자 80과 4는 같은 종류의 값이 아니에요
커널 경로의 proto 80은 경로 출처를 구분하는 메타데이터이고, TCP 목적지 포트 80은 nginx의 수신 포트예요. 다음 절의 IPIP (4)는 바깥 IP 헤더의 프로토콜 번호예요. IPIP를 허용할 때 TCP 4번 포트를 여는 것으로 바꾸어 읽으면 안 돼요.

4. eth0에서는 노드 헤더 안에 Pod 패킷이 들어 있었다

worker1의 노드 eth0에서 같은 SYN을 읽으면 IP 헤더가 두 겹으로 나와요. tcpdump -nn -vvv -S -r로 저장한 pcap을 읽었고, 아래는 첫 세 줄의 원문이에요.

2026-11-14 23:34:22.830996 IP (tos 0x0, ttl 63, id 53933, offset 0, flags [DF], proto IPIP (4), length 80) 192.168.104.3 > 192.168.104.4: IP (tos 0x0, ttl 63, id 3100, offset 0, flags [DF], proto TCP (6), length 60) 10.244.194.75.45253 > 10.244.126.10.80: Flags [S], cksum 0x3ab7 (correct), seq 3184915459, win 64800, options [mss 1440,sackOK,TS val 1556085327 ecr 0,nop,wscale 7], length 0

첫 줄의 IP 길이는 80바이트이고 프로토콜은 IPIP 4예요. 둘째 줄 앞의 주소는 worker1 노드에서 worker2 노드로 가는 192.168.104.3 → 192.168.104.4예요. 그 안의 IP 길이는 60바이트, 프로토콜은 TCP 6이고 마지막 줄의 주소는 원래 Pod 쌍이에요. 이 SYN에서는 바깥 IPv4 헤더 20바이트 + 안쪽 IP 패킷 60바이트 = 80바이트였어요.

RFC 2003의 IP-in-IP 정의에서도 바깥 주소는 터널의 양 끝, 안쪽 주소는 원래 송수신자로 구분해요. 이 실행에서는 그 두 쌍을 실제로 함께 관찰했어요.

그림 2. 이 SYN의 안쪽 60바이트 앞에 노드 주소를 담은 헤더 20바이트가 추가됐어요.

이 예는 주소를 다른 값으로 바꾸는 NAT와 달라요. 캡슐화 뒤에도 안쪽에는 Pod 주소가 남아 있었어요. IPPool에 natOutgoing=true가 있다고 해서 이 Pod 사이 요청도 노드 주소로 SNAT됐다고 판단하면 안 돼요.

노드 eth0의 필터는 ip proto 4 and host 192.168.104.3 and host 192.168.104.4였어요. 바깥 헤더가 노드 IP인 패킷에 host 10.244.194.75만 적용하면 안쪽까지 의도대로 찾지 못할 수 있어요. 먼저 IPIP를 저장한 뒤 안쪽 주소와 출발지 포트로 실험 연결을 골랐어요.

5. 도착 노드에서는 바깥 헤더가 사라지고 Pod 경로로 이어졌다

worker2의 eth0에서도 같은 내부 SYN을 담은 IPIP가 보였어요. 반면 worker2의 tunl0에는 Pod IP 패킷이, remote 쪽 calic93d2b3627d에는 TTL이 62로 줄어든 Pod IP 패킷이 보였어요. 시퀀스 번호 3184915459와 내부 IP ID 3100이 각 지점에서 일치했어요.

응답은 반대 방향이었어요. remote 쪽 cali에서는 10.244.126.10:80 → 10.244.194.75:45253이 보였고, 노드 eth0에서는 바깥 주소가 192.168.104.4 → 192.168.104.3인 IPIP 안에 그 응답이 들어 있었어요. client에서 HTTP 200을 받은 사실까지 함께 확인했어요. 도착 Pod 내부 eth0를 직접 캡처한 것은 아니므로 그 지점의 화면까지 확보했다고 주장하지는 않아요.

저장한 pcap을 파싱해 해당 두 연결만 센 결과예요. 노드 eth0에는 다른 IPIP 트래픽도 있었으므로 전체 pcap의 패킷 수와 아래 수치는 달라요.

Capture point local:45252 remote:45253 remote SYN TTL outer IPIP client-eth0 12 12 64 no client-cali 12 12 64 no local-cali 12 0 - no worker1-tunl0 0 12 63 no worker1-eth0 0 12 63 yes worker2-eth0 0 12 63 yes worker2-tunl0 0 12 63 no remote-cali 0 12 62 no

그림 3. 실제 pcap 분석 출력을 터미널 형태로 렌더링했어요. 새로 실행 중인 실시간 화면은 아니에요.

같은 연결이라는 판단은 시각 하나가 아니라 주소·포트·시퀀스 번호·IP ID를 함께 대조해서 내려요. 이 캡처에서는 노드별 시각도 어긋나 보였어요. 두 노드에 찍힌 시각을 단순히 빼서 전송 지연으로 발표하지 않았어요.

6. 캡처를 읽을 때는 BGP·체크섬·관측 범위를 따로 본다

패킷이 calico-node 프로세스 안으로 들어가 BIRD를 거쳐 나오는 모습을 찾는 것이 이번 실험의 목표는 아니에요. 캡처에서 연결한 것은 네트워크 장치와 커널 전달 경로예요. 경로 정보를 교환하는 BGP와 그 경로로 데이터를 전달하는 동작은 구분해야 해요. BIRD를 멈췄을 때 커널 경로가 남았던 이유와 Calico 3.33의 경로 작성 주체는 기존 30편에서 별도 실험으로 확인했어요. 이번 패킷 캡처로 그 작성 주체까지 새로 입증한 것은 아니에요.

📖 용어: checksum offload
TCP 체크섬 계산을 전송 경로의 뒤 단계로 미룰 수 있는 기능이에요. 계산 완료 전 지점을 캡처하면 tcpdump가 incorrect로 표시할 수 있어요. 그 표시 하나로 수신 측이 손상 패킷을 받았다고 결론 내리지 않아요.

실제로 client의 eth0와 worker1 tunl0에서는 이 SYN의 TCP 체크섬이 incorrect로 표시됐지만, 양쪽 노드 eth0와 도착 cali에서는 correct였어요. worker1 eth0의 ethtool -k 결과는 tx-checksumming: off, generic-receive-offload: on이었어요. 출발지 가상 장치의 미완성 체크섬이 뒤에서 완성될 가능성과 맞는 관측이에요. 다만 모든 장치의 offload 설정과 커널 경로를 추적한 것은 아니라서 정확히 어느 함수가 계산했는지까지 확정하지 않아요.

💡 재현할 때는 인터페이스와 필터부터 다시 구해요
실험 스크립트는 새 Pod의 IP와 호스트 경로에서 cali 이름을 얻고, 샌드박스 PID의 netns에 nsenter로 들어가 eth0를 캡처해요. 10초 timeout으로 끝내며 snaplen은 256바이트라 큰 응답 본문 전체는 보존하지 않아요. 이번 비교는 SYN과 헤더·연결 상태에 집중했어요. 서비스 이름을 쓰면 DNS와 Service 변환이 추가되므로 재현 시 Pod IP 직접 요청을 유지해요.

원문과 재현 코드는 52편 실험 자료에 모았어요. experiment.py는 전용 namespace에 파드 세 개를 만들고 캡처를 수집한 뒤 삭제해요. analyze-pcap.py는 저장된 pcap에서 연결 연속성과 헤더를 검증해요. 여덟 캡처 모두 커널 드롭 카운터는 0이었지만 이것이 네트워크 전체의 무손실 보장은 아니에요. 종료 후 namespace가 NotFound인 것과 생성한 임시 pcap 파일 제거를 확인했어요.

구성의 선택지는 Calico 3.33 overlay 문서, 호스트의 라우팅·정책 처리 원리는 Calico 데이터 경로 문서와 대조했어요. 체크섬 해석은 Linux checksum offload 문서를 참고했어요. 이 글의 실측은 IPv4 IPIP 구성에 한정하며 VXLAN이나 eBPF 데이터플레인에서 같은 장치·경로가 나온다고 일반화하지 않아요.

✍️ 오늘의 요약
같은 노드의 파드 사이에서는 로컬 cali 경로가, 다른 노드 사이에서는 노드 주소를 담은 IPIP 구간이 관찰됐어요.

노드 eth0의 바깥 헤더 안에서도 원래 Pod 주소와 TCP 연결 정보는 유지됐어요. 경로 표, 캡처 지점, 같은 연결의 헤더를 함께 읽어야 실제 전달 경로를 설명할 수 있어요.
