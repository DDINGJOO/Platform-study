busybox:1.37 이미지로 sleep infinity만 도는 파드를 세 번 만들고 세 번 지웠어요. 세 번 모두 Terminating에 30초 넘게 머물렀고 kubectl get이 NotFound를 돌려준 시각은 삭제 요청 뒤 +32.5초, +31.7초, +31.7초였어요. 노드의 로그에는 +31.2초, +30.5초, +30.4초에 Kill container가 찍혔고 파드는 Error로 끝났어요. 원본은 63편과 같은 labs/devops/k8s-study/out/63-termination-timing.txt예요.

같은 날 같은 30초를 두 번 더 봤어요. 앱이 끝나면 사이드카도 멈추는 네이티브 사이드카 파드에서 신호를 처리하지 않는 사이드카(while true; do sleep 1; done)는 앱이 끝난 11:30:43에서 31초 뒤인 11:31:14에 exit 137로 끝났어요(labs/devops/k8s-study/out/64-native-sidecar-finish.txt). 노드에서 파드의 pause 프로세스에 SIGTERM을 보냈을 때는 pause가 0.2초 만에 사라졌는데, kubelet이 샌드박스를 다시 만들려고 앱 컨테이너를 멈추는 데 다시 30초가 걸렸어요.

파드 삭제, 사이드카 종료, 샌드박스 재생성은 서로 다른 경로인데 셋 다 30초에 SIGKILL로 끝났어요. PID 1 문제는 왜 이렇게 여기저기서 나올까요? 이 글은 sleep이 SIGTERM을 받고도 살아남는 이유를 커널 소스에서 찾고, 컨테이너 안과 노드에서 kill을 직접 보내 확인해요. 클러스터는 Lima VM 4대의 kubeadm v1.37.2, containerd 2.4.1이고 노드 커널은 Ubuntu 6.8.0-149(arm64)예요.

이 글에서 다룰 것
· 30초는 누가 세고 30초 뒤 SIGKILL은 누가 보낼까?
· SIGTERM의 기본 동작은 종료인데 sleep은 왜 살아 있을까?
· 커널은 언제부터, 어떤 조건으로 PID 1에게 온 신호를 버릴까?
· kill이 0을 돌려줬는데 프로세스는 왜 그대로일까?
· pause는 같은 SIGTERM에 어떻게 바로 끝났을까?

1. 30초는 SIGTERM을 보내고 SIGKILL까지 기다리는 시간이다

파드를 지우면 API 서버는 객체에 삭제 예정 시각을 적어요. 노드의 kubelet이 그걸 보고 컨테이너를 멈추는데, 직접 신호를 보내지는 않아요. kubelet은 컨테이너 런타임에 CRI StopContainer를 부르고 이 요청에는 컨테이너 ID와 timeout 두 필드만 있어요(v1.37.2 cri-api api.proto의 StopContainerRequest). timeout에는 파드의 grace period가 들어가요. 기본값은 30초예요.

📖 용어: terminationGracePeriodSeconds (grace period)
파드가 스스로 정리하고 끝날 수 있게 기다려 주는 시간이에요. 파드 spec에 적고 기본값은 30초예요. 이 시간이 지나도 컨테이너가 살아 있으면 런타임이 SIGKILL로 끝내요. preStop 훅이 있으면 이 시간을 세는 기준이 달라지고 그 계산은 67편에 있어요.

신호를 고르고 보내는 쪽은 containerd예요. containerd v2.4.1의 container_stop.go에서 흐름에 필요한 줄만 옮기면 이래요.

if timeout > 0 { stopSignal := "SIGTERM" if signal := container.Config.GetStopSignal(); signal != runtime.Signal_SIGNAL_RUNTIME_DEFAULT { stopSignal, err = criSignalToOCIStopSignal(signal) ... } else if container.StopSignal != "" { stopSignal = container.StopSignal } ... log.G(ctx).Infof("Stop container %q with signal %v", id, sig) if err = task.Kill(ctx, sig); err != nil && !errdefs.IsNotFound(err) { ... sigTermCtx, sigTermCtxCancel := context.WithTimeout(ctx, timeout) ... err = c.waitContainerStop(sigTermCtx, container) if err == nil { // Container stopped on first signal no need for SIGKILL return nil } } log.G(ctx).Infof("Kill container %q", id) if err = task.Kill(ctx, syscall.SIGKILL); err != nil && !errdefs.IsNotFound(err) { ...

→ timeout이 0보다 크면 정지 신호를 한 번 보내고 timeout 동안 컨테이너가 끝나기를 기다린다는 뜻이에요. 정지 신호는 파드 스펙의 값, 이미지의 STOPSIGNAL, 기본값 SIGTERM 순으로 정해져요. 그 안에 끝나지 않으면 Kill container 로그를 남기고 SIGKILL을 보내요. 그러니 30초는 컨테이너가 SIGTERM에 반응하지 않았을 때 SIGKILL을 받기까지 기다린 시간이에요.

노드 로그도 이 순서를 그대로 보여 줘요. 5절의 실험에서 kubelet이 sleep 컨테이너를 멈출 때 containerd는 +0.3초에 Stop container "<cid>" with signal terminated를, +30.3초에 Kill container "<cid>"를 남겼어요. terminated는 SIGTERM의 이름이에요. 처음에 본 세 번의 삭제에서도 Kill container가 +30.4~31.2초에 찍혔고 kubelet의 Pod removed broadcasted는 그 약 1초 뒤인 +31.5~32.3초였어요.

📖 용어: 종료 코드 137
신호로 죽은 프로세스의 종료 코드를 셸과 런타임은 128 + 신호 번호로 적어요. SIGKILL은 9번이라 137이고 SIGTERM은 15번이라 143이에요. 쿠버네티스는 137로 끝난 컨테이너의 reason을 Error로 기록해요. 137을 보면 컨테이너가 스스로 끝나지 않고 SIGKILL로 끝났다는 뜻으로 읽으면 돼요.

그림 1. kubelet은 timeout만 넘기고, containerd가 SIGTERM 뒤 30초를 기다렸다가 SIGKILL을 보내요.

2. SIGTERM의 기본 동작은 종료인데 sleep은 살아 있었다

여기서 이상한 점이 하나 있어요. 리눅스에서 프로세스가 SIGTERM을 받았을 때 따로 처리하는 함수를 걸어 두지 않았다면 커널은 기본 동작을 해요. SIGTERM의 기본 동작은 프로세스를 끝내는 거예요. 그래서 노트북 터미널에서 띄운 sleep은 kill -TERM 한 번에 끝나요. 그런데 컨테이너의 sleep은 SIGTERM을 받고도 30초를 버텼어요.

먼저 컨테이너마다 첫 프로세스가 어떤 신호를 직접 처리하는지 봤어요. 리눅스는 /proc/<PID>/status에 신호 상태를 비트 마스크로 보여 줘요.

📖 용어: 신호 핸들러와 SigCgt·SigIgn
신호 핸들러는 프로세스가 특정 신호를 받으면 실행하라고 커널에 등록해 둔 함수예요. /proc/<PID>/status의 SigCgt는 핸들러를 건 신호, SigIgn은 일부러 무시하기로 한 신호, SigBlk는 잠시 막아 둔 신호를 16진수 비트로 보여 줘요. 신호 번호 n이 비트 n-1에 대응해서 SIGTERM(15)은 0x4000이에요.

여러 모양의 파드를 띄워 PID 1의 마스크를 읽은 결과예요. 원본은 labs/devops/k8s-study/out/64-pid1-sigmask.txt이고 스크립트는 같은 디렉터리의 64-pid1-sigmask.sh예요. 마스크 뒤 괄호는 스크립트가 비트를 신호 이름으로 풀어 적은 거예요.

## a-sleep command: ["sleep","infinity"] PID PPID STAT COMMAND 1 0 S sleep infinity PID 1 sleep SigBlk=0000000000000000 (없음) SigIgn=0000000000000000 (없음) SigCgt=0000000000000000 (없음) ## f-nginx command: ["/docker-entrypoint.sh","nginx","-g","daemon off;"] 1 0 S nginx: master process nginx -g daemon off; PID 1 nginx SigBlk=0000000000000000 (없음) SigIgn=0000000040001000 (PIPE SYS) SigCgt=0000000018016a07 (HUP INT QUIT USR1 USR2 ALRM TERM CHLD WINCH IO)

→ sleep은 어떤 신호에도 핸들러를 걸지 않았고 nginx는 TERM을 포함해 신호 열 개에 핸들러를 걸었다는 뜻이에요. 같은 실험에서 shareProcessNamespace: true 파드의 PID 1로 보인 pause는 INT, TERM, CHLD에 핸들러를 걸었어요. 핸들러가 없는 sleep에게는 SIGTERM의 기본 동작이 적용돼야 해요. 그런데 적용되지 않았어요. 차이는 sleep이 그 컨테이너에서 PID 1이라는 점에 있어요.

📖 용어: PID 네임스페이스와 init(PID 1)
PID 네임스페이스는 프로세스 번호를 따로 매기는 공간이에요. 새 네임스페이스에서 처음 만들어진 프로세스가 그 안의 PID 1이 되고 init 역할을 맡아요. 쿠버네티스 기본 설정에서는 컨테이너마다 PID 네임스페이스가 따로 있어서 컨테이너의 첫 프로세스가 곧 그 컨테이너의 PID 1이에요. 노드에서는 같은 프로세스가 노드의 번호로 따로 보여요.

노드에서 보면 이 이중 번호가 그대로 드러나요. 5절의 실험에서 sleep의 /proc/58133/status에는 NSpid: 58133 1이 있었어요. 노드에서는 58133번이고 자기 네임스페이스에서는 1번이라는 뜻이에요. 같은 파드의 pause도 58105 1이었어요. 43편에서 본 것과 같이 기본 파드에서는 pause와 앱이 각자 자기 PID 네임스페이스의 PID 1이에요.

3. 커널은 2009년부터 컨테이너 init에게 온 신호를 걸러 왔다

PID 1을 보호하는 규칙은 원래 호스트의 init을 위한 것이었어요. kill(2)의 NOTES는 이렇게 적어요.

The only signals that can be sent to process ID 1, the init process, are those for which init has explicitly installed signal handlers. This is done to assure the system is not brought down accidentally.

→ init이 핸들러를 건 신호만 PID 1에게 보낼 수 있고, 시스템이 실수로 내려가지 않게 하려는 장치라는 뜻이에요. 호스트에서 systemd가 아무 신호에나 죽으면 기계 전체가 멈추니 이해가 가는 규칙이에요.

PID 네임스페이스가 생긴 뒤에는 네임스페이스마다 init이 생겼어요. 2009-04-02 Sukadev Bhattiprolu의 커밋 세 개가 이 init(커밋 메시지는 container-init, 줄여서 cinit이라 불러요)에도 같은 보호를 넣었어요. 핵심은 921cf9f63089의 첫 문단이에요.

Drop early any SIG_DFL or SIG_IGN signals to container-init from within the same container. But queue SIGSTOP and SIGKILL to the container-init if they are from an ancestor container.

→ 같은 컨테이너 안에서 container-init에게 보낸 신호 중 핸들러가 없는(SIG_DFL) 신호와 무시하기로 한(SIG_IGN) 신호는 일찍 버리고, 조상 컨테이너에서 온 SIGSTOP과 SIGKILL만 대기열에 넣는다는 뜻이에요. 이어진 b3bfa0cba867은 이미 대기열에 들어온 신호도 꺼낼 때 다시 걸러 SIGKILL과 SIGSTOP 말고는 기본 동작을 하지 않게 했고, 마지막에 "set SIGNAL_UNKILLABLE for container-inits"로 컨테이너 init에 보호 표시를 켰어요. 두 커밋은 v2.6.29에는 없고 v2.6.30에는 있어요.

📖 용어: SIG_DFL과 기본 동작
SIG_DFL은 "이 신호에 대해 아무 핸들러도 등록하지 않았다"는 상태예요. 이때 커널은 신호마다 정해진 기본 동작을 해요. SIGTERM과 SIGKILL은 종료, SIGSTOP은 멈춤, SIGCHLD는 아무것도 하지 않음이 기본이에요. 컨테이너 init에서는 이 기본 동작이 막혀요.

2018년에는 Eric Biederman의 3597dfe01d12가 커널 자신이 보낸 SIGKILL과 SIGSTOP은 늘 전달되게 보정했어요. 커밋 메시지는 원칙을 "A pid namespace init is only supposed to be able to ignore signals sent from itself and children with SIG_DFL."로 적었어요. PID 네임스페이스의 init이 무시할 수 있는 신호는 자기 자신과 자식이 보낸, 핸들러 없는 신호뿐이라는 뜻이에요.

지금 코드에서는 한 줄의 조건이다

우리 노드 커널의 기준인 upstream v6.8의 signal.c와 fork.c를 읽으면 규칙은 세 군데에 나뉘어 있어요. 첫째, fork.c의 copy_process()는 새 PID 네임스페이스의 첫 프로세스를 만들 때 p->signal->flags |= SIGNAL_UNKILLABLE;을 켜요. 둘째, send_signal_locked()는 보낸 프로세스가 받는 쪽 네임스페이스에서 PID를 갖지 않으면, 즉 조상 네임스페이스에 있으면 force를 참으로 둬요. 셋째, 신호를 버릴지 정하는 함수가 이 둘을 같이 봐요.

static bool sig_task_ignored(struct task_struct *t, int sig, bool force) { void __user *handler; handler = sig_handler(t, sig); /* SIGKILL and SIGSTOP may not be sent to the global init */ if (unlikely(is_global_init(t) && sig_kernel_only(sig))) return true; if (unlikely(t->signal->flags & SIGNAL_UNKILLABLE) && handler == SIG_DFL && !(force && sig_kernel_only(sig))) return true; ...

→ 보호 표시가 켜진 프로세스에서 그 신호의 핸들러가 SIG_DFL이면 버린다는 뜻이에요. 예외는 "조상 네임스페이스에서 왔고(force) 신호가 SIGKILL이나 SIGSTOP(sig_kernel_only)인 경우" 하나뿐이에요. include/linux/signal.h의 SIG_KERNEL_ONLY_MASK에는 SIGKILL과 SIGSTOP 두 개만 들어 있어요. 이 조건을 풀어 쓰면 네 경우로 갈려요.

· SIGTERM은 컨테이너 안에서 보내든 노드에서 보내든 sig_kernel_only가 아니라서 버려져요.
· SIGKILL을 컨테이너 안에서 보내면 force가 거짓이라 버려져요.
· SIGKILL을 노드에서 보내면 force와 sig_kernel_only가 모두 참이라 통과하고 프로세스가 죽어요.
· 핸들러를 건 신호는 이 조건에 걸리지 않아서 어디서 보내든 핸들러가 실행돼요.

📖 용어: 조상 PID 네임스페이스
PID 네임스페이스는 부모와 자식으로 이어져요. 컨테이너의 네임스페이스는 노드(호스트)의 네임스페이스 아래에 만들어지므로 노드가 조상이에요. 조상 쪽 프로세스는 자식 네임스페이스의 프로세스를 볼 수 있지만 반대로는 볼 수 없어요. containerd와 shim도 노드 쪽에 있어서 그들이 보낸 신호는 조상에서 온 신호로 취급돼요.

그림 2. 핸들러가 없는 컨테이너 PID 1이 받는 신호는 노드에서 온 SIGKILL·SIGSTOP뿐이에요.

pid_namespaces(7)도 같은 내용을 사람 말로 적어요. 같은 네임스페이스의 다른 프로세스는 init이 핸들러를 건 신호만 init에게 보낼 수 있고 이 제한은 권한이 있는 프로세스에도 적용된다고 해요. 조상 네임스페이스의 프로세스도 마찬가지인데 "SIGKILL or SIGSTOP are treated exceptionally: these signals are forcibly delivered when sent from an ancestor PID namespace."라고 덧붙여요. 조상에서 온 SIGKILL과 SIGSTOP만은 강제로 전달된다는 뜻이에요.

왜 컨테이너 init까지 이렇게 보호했는지는 커밋 메시지에 동작만 있고 동기 서술은 없어요. man 페이지에는 kill(2)의 "not brought down accidentally"와 pid_namespaces(7)의 "prevents other members of the PID namespace from accidentally killing the "init" process"가 남아 있어요. 당시 메일링 리스트 논의는 이 글에서 읽지 않았으니 동기는 여기까지만 적을게요. 또 인용한 소스는 upstream v6.8이고 Ubuntu의 6.8.0-149 패치본 소스는 보지 않았어요. 실제 동작은 다음 절의 실험으로 확인했어요.

4. 컨테이너 안과 노드에서 보낸 kill은 네 번 모두 0을 돌려줬다

그림 2의 네 갈래를 실제로 밟아 봤어요. SigCgt가 0인 sleep infinity 파드 k-sleep을 띄우고 컨테이너 안(같은 PID 네임스페이스)과 노드(조상 네임스페이스)에서 SIGTERM과 SIGKILL을 차례로 보냈어요. 원본은 labs/devops/k8s-study/out/64-kill-pid1-inside-vs-node.txt와 같은 디렉터리의 64-kill-pid1-inside-vs-node.sh예요.

그림 3. kill은 매번 성공을 돌려줬고 프로세스는 노드에서 보낸 SIGKILL에만 죽었어요.

보낸 곳과 신호kill 종료 코드1~2초 뒤 sleep그림 2의 갈래
컨테이너 안 kill -TERM 10살아 있음, RunningSIG_DFL, 조상 아님 → 버림
컨테이너 안 kill -KILL 10살아 있음, RunningSIGKILL이지만 조상 아님 → 버림
노드 kill -TERM 578720살아 있음, Running조상이지만 SIGTERM → 버림
노드 kill -KILL 578720호스트 PID 없음, terminated 137/Error조상에서 온 SIGKILL → 죽음

네 결과가 sig_task_ignored()의 조건과 정확히 맞아요. 삭제 때 containerd가 보낸 SIGTERM은 세 번째 줄에 해당하고 30초 뒤의 SIGKILL은 네 번째 줄에 해당해요. 컨테이너가 끝난 이유도 커널에 있어요. pid_namespaces(7)은 "If the "init" process of a PID namespace terminates, the kernel terminates all of the processes in the namespace via a SIGKILL signal."이라고 적어요. v6.8의 zap_pid_ns_processes()가 남은 프로세스마다 SIGKILL을 보내는 코드예요. PID 1이 죽으면 그 네임스페이스의 나머지도 같이 끝나요.

네 번 모두 kill이 0을 돌려준 것은 디버깅할 때 가장 헷갈리는 부분이에요. v6.8의 __send_signal_locked()는 prepare_signal()이 거짓을 돌려주면 반환값 ret을 처음 값 0으로 둔 채 빠져나가요. 신호를 버리는 판단이 이 안에서 일어나니 kill 쪽에는 실패가 돌아오지 않아요. 그래서 저는 kill의 성공을 "보낼 권한이 있고 대상이 있다"까지만 알려 주는 값으로 읽어요. 프로세스가 신호에 반응했는지는 따로 확인해야 해요.

⚠️ kubectl exec로 kill 1을 해도 컨테이너는 재시작되지 않을 수 있어요
컨테이너를 다시 띄우려고 kubectl exec <파드> -- kill 1을 쓰는 경우가 있어요. PID 1이 SIGTERM에 핸들러를 걸었으면 끝나지만 sleep, 셸 루프 같은 PID 1은 표의 첫째 줄과 같이 아무 일도 없어요. kill -9 1도 둘째 줄과 같이 버려져요. 둘 다 종료 코드 0이라 명령은 성공한 것으로 보여요. 확실히 재시작해야 하면 파드를 지우거나 노드에서 컨테이너 호스트 PID에 SIGKILL을 보내야 해요.

5. pause는 SIGTERM 핸들러를 달고 있어서 0.2초 만에 끝났다

같은 파드에 PID 1이 하나 더 있어요. pause예요. pause가 파드의 네임스페이스를 쥐고 있다는 것은 43편에서 봤고, 같은 파드의 컨테이너가 그 네임스페이스로 무엇을 함께 쓰는지는 61편에서 봤어요. pause도 자기 PID 네임스페이스의 PID 1이니 같은 커널 규칙을 받아요. 그런데 build/pause/linux/pause.c는 처음부터 핸들러를 걸어요.

static void sigdown(int signo) { psignal(signo, "Shutting down, got signal"); exit(0); } static void sigreap(int signo) { while (waitpid(-1, NULL, WNOHANG) > 0) ; } ... if (sigaction(SIGINT, &(struct sigaction){.sa_handler = sigdown}, NULL) < 0) return 1; if (sigaction(SIGTERM, &(struct sigaction){.sa_handler = sigdown}, NULL) < 0) return 2; if (sigaction(SIGCHLD, &(struct sigaction){.sa_handler = sigreap, .sa_flags = SA_NOCLDSTOP}, NULL) < 0) return 3; for (;;) pause();

→ SIGINT나 SIGTERM을 받으면 sigdown이 exit(0)으로 스스로 끝내고 SIGCHLD를 받으면 끝난 자식을 거두며, 그 밖에는 신호가 올 때까지 잠들어 있다는 뜻이에요. 핸들러를 걸었으니 그림 2에서 왼쪽 갈래로 가요.

이걸 같은 파드에서 비교했어요. 기본 파드 하나를 띄우고 노드에서 pause와 sleep의 신호 마스크를 읽은 뒤, 같은 kill -TERM을 sleep에 먼저, pause에 다음으로 보냈어요. 그 뒤 60초 동안 샌드박스와 컨테이너를 지켜봤어요. 원본은 labs/devops/k8s-study/out/64-pause-vs-sleep-sigterm.txt와 같은 디렉터리의 64-pause-vs-sleep-sigterm.sh예요. 처음 읽은 마스크는 pause가 호스트 PID 58105, NSpid 58105/1, SigCgt INT TERM CHLD였고 sleep이 호스트 PID 58133, NSpid 58133/1, SigCgt 없음이었어요.

그림 4. 같은 SIGTERM에 pause는 바로 끝났고, sleep을 멈추는 데는 다시 30초가 걸렸어요.

sleep은 kill이 0을 돌려준 1초 뒤에도 그대로였어요. pause는 kill 0.2초 뒤에 호스트 PID가 사라졌어요. 이어서 kubelet이 샌드박스가 죽은 것을 알아채고 SandboxChanged("Pod sandbox changed, it will be killed and re-created.")와 Killing 이벤트를 남겼어요. 샌드박스를 새로 만들려면 그 안의 앱 컨테이너부터 멈춰야 해요. containerd는 pause를 죽인 시각 기준 +0.3초에 sleep에 SIGTERM을 보냈고 +30.3초에 SIGKILL을 보냈어요. +30초 관측에서 sleep의 호스트 PID가 사라졌고 +45초에는 새 샌드박스가 SANDBOX_READY, restartCount가 1이었어요.

그림 5. pause와 sleep은 같은 규칙을 받았고, 갈린 것은 핸들러 하나였어요.

pause에 SIGTERM 핸들러가 들어간 것은 Go로 쓰던 시절인 2014-10-03의 커밋 9b747c3a9d예요. 그 커밋이 남긴 동기 서술은 이 글에서 확인하지 않았어요. 다만 이 글의 규칙을 적용하면 핸들러가 없는 pause가 어떻게 될지는 분명해요. sleep과 똑같이 SIGTERM을 버리고 노드에서 온 SIGKILL에만 끝났을 거예요. pause가 아무 일도 하지 않는 프로그램인데도 SIGTERM과 SIGINT 핸들러를 거는 이유를 이 규칙으로 읽을 수 있어요.

그래서 PID 1 문제는 여러 곳에서 나온다

이제 도입의 질문에 답할 수 있어요. 기본 파드에서는 모든 컨테이너의 첫 프로세스가 자기 PID 네임스페이스의 PID 1이에요. 그리고 kubelet이 컨테이너를 멈추는 경로는 파드 삭제, 롤링 업데이트, 샌드박스 재생성, 사이드카 종료처럼 여러 가지인데 모두 같은 StopContainer로 끝나요. 런타임은 그 컨테이너의 PID 1에 정지 신호를 한 번 보내고 grace만큼 기다려요. PID 1이 그 신호에 핸들러를 걸지 않았으면 경로가 무엇이든 grace를 다 쓰고 SIGKILL로 끝나요. 도입의 사이드카는 명령이 sh -c 'while true; do sleep 1; done'이라 셸이 PID 1로 남는 모양이에요. 그 사이드카의 마스크는 따로 읽지 않았지만, 같은 busybox sh가 PID 1로 남은 c-sh-c-2cmds 파드에서 셸의 SigCgt는 INT와 CHLD뿐이고 TERM은 없었어요. 30초는 경로마다 따로 생긴 문제가 아니라 "PID 1이 정지 신호를 처리하는가" 하나의 질문이 여러 번 드러난 결과예요.

해결책도 결국 PID 1이 신호를 처리하게 만드는 쪽이에요. 앱이 직접 SIGTERM 핸들러를 걸거나, 셸로 감쌌다면 exec로 앱에게 PID 1을 넘기거나, 신호를 전달해 주는 작은 init을 PID 1로 두는 방법이 있어요. grace를 줄이는 것은 SIGKILL을 앞당길 뿐이고 앱이 정리할 기회도 같이 줄여요.

💡 내 컨테이너의 PID 1이 SIGTERM을 처리하는지 확인하는 법
• 이미지에 cat이 있으면 kubectl exec <파드> -c <컨테이너> -- cat /proc/1/status에서 SigCgt를 봐요. 16진수 값에서 0x4000 비트(SIGTERM)가 켜져 있으면 핸들러가 있어요. 열여섯 자리가 모두 0이면 핸들러가 하나도 없다는 뜻이에요.
• 셸이 없는 이미지는 노드에서 봐요. crictl inspect <컨테이너 ID>의 info.pid가 호스트 PID이고 /proc/<호스트 PID>/status를 읽으면 돼요.
• 지운 파드가 grace만큼 Terminating에 머물고 종료 코드가 137이면 이 문제부터 의심해요. 0이나 143이면 컨테이너의 첫 프로세스가 정지 신호에 끝난 거예요.

✍️ 오늘의 요약

파드를 지우면 kubelet은 StopContainer에 timeout 30초만 넘기고 containerd가 PID 1에 SIGTERM을 보낸 뒤 30초를 기다렸다가 SIGKILL을 보내요. sleep infinity 파드가 31초쯤 걸리고 137로 끝나는 것은 SIGTERM이 아무 효과를 내지 못했다는 뜻이에요.

효과가 없던 이유는 커널에 있어요. 2.6.30(2009)부터 PID 네임스페이스의 init에는 SIGNAL_UNKILLABLE이 켜지고, 핸들러를 걸지 않은 신호는 버려져요. 예외는 조상 네임스페이스에서 온 SIGKILL과 SIGSTOP뿐이에요. 실험에서 컨테이너 안의 kill -TERM 1·kill -KILL 1과 노드의 kill -TERM은 모두 0을 돌려주고도 아무 일이 없었고, 노드의 kill -KILL에만 sleep이 죽었어요.

pause는 SIGTERM 핸들러를 걸어서 같은 SIGTERM에 0.2초 만에 끝났고, 핸들러가 없는 sleep을 멈추는 데는 어느 경로든 30초가 걸렸어요. 컨테이너가 늦게 지워지면 grace를 늘리거나 줄이기 전에 PID 1이 누구이고 정지 신호에 핸들러를 걸었는지부터 봐야 해요.
