kube-system 네임스페이스의 파드 목록에는 kube-apiserver-k8s-master라는 파드가 있어요. 이 줄을 보고 제가 처음 한 말은 "API 서버도 파드로 올라가 있네?"였고 곧이어 "이것도 yaml 세팅되어 있겠네?"라고 물었어요. 마스터의 /etc/kubernetes/manifests/kube-apiserver.yaml을 열어 보니 정말로 kind: Pod로 시작하는 평범한 파드 YAML이었어요. command 칸에는 --advertise-address=192.168.104.1부터 --tls-private-key-file=/etc/kubernetes/pki/apiserver.key까지 플래그가 27개 적혀 있었어요.

그 파일을 보며 "이거 분석해도 좋겠다", "그러면 API 서버도 워커에서 떠 있어?"라고 메모했고 조금 뒤에는 "Pod의 데이터 유효성 검사, 어드미션 컨트롤러가 뭐야?"라고 물었어요. 이번 글은 이 질문들을 차례로 따라가요. API 서버가 정적 파드라는 사실은 5편과 20편에서 봤고 인증·인가·어드미션은 32편과 33편에서 봤어요. 그래서 이번에는 매니페스트 한 장을 처음부터 끝까지 읽는 데 집중해요. 플래그를 요청이 지나는 단계별로 다시 묶고 적혀 있지 않은 플래그가 무엇을 뜻하는지 짚은 다음 API 서버가 실제로 어떤 요청을 얼마나 받는지 지표로 확인해요. 클러스터는 Lima VM 4대에 kubeadm v1.37.2로 만든 실습 환경이에요.

이 글에서 다룰 것
· API 서버는 왜 systemd 서비스가 아니라 파드로 떠 있고 워커에는 왜 없을까?
· 매니페스트의 플래그 27개는 요청이 지나는 어느 단계를 정할까?
· 매니페스트에 없는 플래그는 어떻게 돌고 플래그를 바꾸려면 어디를 고쳐야 할까?
· kubectl 명령 하나는 어떤 HTTP 요청이 되고 API 서버가 가장 많이 받는 요청은 무엇일까?
· 요청이 몰리면 API 서버는 누구의 요청을 먼저 처리할까?
· 형식이 틀린 파드와 규칙에 어긋난 파드는 어디서 어떻게 다르게 거절될까?

1. API 서버는 kubelet이 파일을 읽어 띄운 정적 파드다

"API 서버도 파드"라는 말을 정확히 하면 정적 파드라는 뜻이에요. 마스터의 kubelet이 /etc/kubernetes/manifests 폴더의 파일을 읽어 직접 띄우고 API에 보이는 kube-apiserver-k8s-master는 kubelet이 올려 둔 미러 파드예요(5편, 20편, 26편). 이번에 궁금했던 것은 그다음이었어요. 프로세스 하나를 띄우는 데 왜 굳이 파드를 썼을까요?

Cluster Architecture 문서의 "Control plane deployment options" 절은 컨트롤 플레인을 띄우는 방식을 넷으로 나눠요. 첫째는 전용 머신이나 VM에서 구성 요소를 직접 돌리는 전통 방식이고 문서는 이 방식이 "often managed as systemd services"라고 적어요. 둘째는 kubelet이 관리하는 정적 파드로 띄우는 방식이에요. 문서는 이것을 "a common approach used by tools like kubeadm"이라고 소개해요. 셋째는 컨트롤 플레인을 클러스터 안의 Deployment나 StatefulSet으로 띄우는 self-hosted 방식이고 넷째는 클라우드 제공자가 컨트롤 플레인을 서비스 안에 감추는 관리형 방식이에요. kubeadm으로 만든 우리 클러스터는 둘째 방식이에요.

그림 1. 네 방식은 설정을 두는 곳과 프로세스·파드를 새로 구성하는 주체가 다르다

정적 파드의 이점은 API 서버에 저장된 파드 객체 없이도 구성할 수 있다는 점이에요. 이미 배정된 파드 안의 API 서버 컨테이너가 죽으면 self-hosted 방식에서도 kubelet이 restartPolicy에 따라 다시 띄워요(파드 수명 주기 문서). 하지만 파드 자체를 새로 만들거나 다른 노드에 배치하려면 Deployment·ReplicaSet 같은 컨트롤러와 API 서버가 필요해요. 정적 파드는 kubelet이 디스크의 파일만 보고 파드를 구성하므로 API 서버가 하나도 없는 상태에서도 뜰 수 있어요. 20편에서 API 서버 매니페스트를 폴더 밖으로 옮겼다 되돌렸을 때 5초 만에 /readyz가 ok를 돌려준 것도 이 경로 덕분이에요. 그러면서도 정적 파드는 파드라서 파드에 있는 기능을 그대로 써요. 우리 매니페스트에서 파드 기능에 해당하는 칸만 골라 보면 이래요.

# 36-apiserver-manifest.txt 에서 파드 기능에 해당하는 칸만 줄여 옮김 image: registry.k8s.io/kube-apiserver:v1.37.2 startupProbe: httpGet /livez initialDelaySeconds 10, periodSeconds 10, failureThreshold 24 livenessProbe: httpGet /livez initialDelaySeconds 10, periodSeconds 10, failureThreshold 8 readinessProbe: httpGet /readyz periodSeconds 1, failureThreshold 3 resources: requests: cpu: 250m (limits 없음) hostNetwork: true priority: 2000001000 priorityClassName: system-node-critical volumeMounts: /etc/ssl/certs, /etc/ca-certificates, /etc/kubernetes/pki, /usr/local/share/ca-certificates, /usr/share/ca-certificates (모두 readOnly, hostPath)

→ API 서버의 버전은 이미지 태그가 정하고 kubelet은 세 프로브로 API 서버의 상태를 본다는 뜻이에요. 막 시작했을 때는 startupProbe가 10초 간격으로 최대 24번 기다려 주고 그 뒤로는 /livez가 8번 연달아 실패하면 kubelet이 컨테이너를 다시 띄워요. /readyz는 1초마다 확인해요. 이 1초 주기는 4절에서 API 서버가 받은 요청 수를 셀 때 다시 나와요.

hostNetwork와 priorityClassName 두 칸은 kubeadm이 정적 파드 넷에 공통으로 넣어요. kubeadm 구현 문서에 따르면 kubeadm이 만드는 정적 파드는 모두 kube-system 네임스페이스에 놓이고 system-node-critical 우선순위 클래스를 쓰며 hostNetwork를 켜요. hostNetwork를 켜는 이유는 "to allow control plane startup before a network is configured"라고 적혀 있어요. 파드 네트워크(CNI)는 API 서버가 뜬 뒤에야 설치할 수 있으니(6편) API 서버는 파드 네트워크 없이 노드의 네트워크로 떠야 해요.

📖 용어: hostNetwork
파드가 자기 네트워크 네임스페이스를 따로 받지 않고 노드의 네트워크를 그대로 쓰게 하는 설정이에요. 그래서 API 서버의 6443 포트는 파드 IP가 아니라 노드 주소 192.168.104.1에서 바로 열려요. 파드 목록에서 API 서버의 IP 칸에 노드 IP가 찍히는 것도 이 때문이에요.
📖 용어: PriorityClass system-node-critical
파드의 중요도를 숫자로 정해 두는 객체가 PriorityClass예요. Pod Priority and Preemption 문서에 따르면 쿠버네티스에는 system-cluster-critical과 system-node-critical 두 클래스가 기본으로 들어 있고 v1.37에서 system-node-critical의 값은 2000001000이에요. 매니페스트의 priority: 2000001000이 바로 이 값이에요.

파드라서 생기는 제약도 있어요. 컨테이너 안에서는 노드의 파일을 볼 수 없으니 플래그가 가리키는 파일은 모두 hostPath 볼륨으로 넣어 줘야 해요. 지금 매니페스트에는 인증서 폴더를 포함해 hostPath 다섯 개가 모두 읽기 전용으로 붙어 있어요. 플래그를 하나 더하면서 새 파일을 가리키게 하려면 볼륨도 같이 더해야 해요. 22편에서 암호화 설정 플래그를 넣을 때 볼륨을 함께 더한 것도 이 때문이에요. 감사(audit) 문서도 API 서버를 파드로 띄웠다면 정책 파일과 로그 파일 위치를 hostPath로 마운트해야 감사 기록이 남는다고 따로 적어 둬요.

워커의 kubelet도 같은 폴더를 보지만 폴더가 비어 있다

"그러면 API 서버도 워커에서 떠 있어?"라는 질문에는 노드 네 대를 직접 열어 보고 답했어요.

# 36-apiserver-where.txt (2026-11-14 19:40:55) [k8s-master] staticPodPath 파일: etcd.yaml kube-apiserver.yaml kube-controller-manager.yaml kube-scheduler.yaml | kube-apiserver 프로세스: 1 | kubelet 이 붙는 API 서버: https://192.168.104.1:6443 [k8s-worker1] staticPodPath 파일: | kube-apiserver 프로세스: 0 | kubelet 이 붙는 API 서버: https://192.168.104.1:6443 [k8s-worker2] staticPodPath 파일: | kube-apiserver 프로세스: 0 | kubelet 이 붙는 API 서버: https://192.168.104.1:6443 [k8s-worker3] staticPodPath 파일: | kube-apiserver 프로세스: 0 | kubelet 이 붙는 API 서버: https://192.168.104.1:6443 워커 kubelet 설정의 staticPodPath: staticPodPath: /etc/kubernetes/manifests

→ 워커의 kubelet도 마스터와 똑같이 /etc/kubernetes/manifests를 정적 파드 폴더로 보지만 그 폴더가 비어 있어서 워커에는 kube-apiserver 프로세스가 없다는 뜻이에요. 네 노드의 kubelet은 모두 마스터의 192.168.104.1:6443 하나에 붙어 있었어요.

그러니 API 서버가 어느 노드에 뜨는지는 스케줄러가 아니라 그 노드의 폴더에 파일이 있느냐로 정해져요. 이 파일을 쓰는 쪽은 kubeadm이에요. 마스터에서는 kubeadm init이 썼고 워커를 붙인 kubeadm join은 이 파일을 쓰지 않았어요. 컨트롤 플레인을 여러 대로 늘릴 때 join에 --control-plane을 주면 그 노드에도 같은 파일이 생기고 API 서버가 하나 더 떠요. 여러 대로 늘리는 이야기는 21편에서 했어요. API 서버는 마스터에 고정된 프로그램이 아니라 파일이 놓인 노드마다 kubelet이 띄우는 파드예요.

2. 매니페스트의 플래그는 요청이 지나는 단계별로 묶어 읽는다

플래그 27개를 적힌 순서대로 읽으면 금방 길을 잃어요. 플래그가 알파벳순으로 적혀 있어서 인증서 경로와 주소, 대역이 뒤섞여 있어요. 32편에서 본 요청 처리 순서(TLS, 인증, 인가, 어드미션, 저장)를 기준으로 다시 묶으면 18개는 요청이 지나는 길의 한 단계를 하나씩 맡고 나머지 9개는 요청을 거르는 일과 상관없는 설정을 정해요.

그림 2. 27개 가운데 18개가 요청이 지나는 단계 하나씩을 맡는다. 스키마 검증 단계에는 플래그가 없다

길 위의 플래그는 대부분 앞 편에서 하나씩 확인했어요. 단계별로 짧게 짚으면 이래요.

· 전송. --secure-port=6443과 --advertise-address=192.168.104.1로 받을 포트와 다른 구성 요소에 알릴 주소를 정하고 --tls-cert-file로 서버 인증서를 내밀어요(5편, 32편).
· 인증. 클라이언트 인증서는 --client-ca-file로, ServiceAccount 토큰은 --service-account-key-file로 확인해요(32편). --enable-bootstrap-token-auth는 kube-system에 있는 부트스트랩 토큰 Secret으로 인증하게 해 주는 플래그이고 5편에서 워커를 join할 때 쓴 토큰이 이것이에요. --requestheader-* 다섯 개는 아래에서 따로 봐요.
· 인가와 어드미션. 인가 방식은 --authorization-mode=Node,RBAC로 정하고(32편) 기본 목록에 더할 어드미션 플러그인은 --enable-admission-plugins=NodeRestriction으로 정해요(33편).
· 저장. --etcd-servers=https://127.0.0.1:2379와 etcd 클라이언트 인증서 셋이에요. etcd가 받는 클라이언트 인증서를 가진 쪽이 API 서버뿐이라는 점은 22편과 35편에서 봤어요.

스키마 검증 단계에는 플래그가 없어요. 객체 종류마다 정해진 형식 검사는 API 서버 코드에 들어 있어서 끄거나 켤 수 없어요. 이 단계가 어드미션 두 단계 사이에 있다는 점은 6절에서 소스로 확인해요.

길 밖의 9개는 대역, 토큰 발급, API 서버가 다른 곳에 붙는 방법을 정한다

플래그우리 값무엇을 정하나
--service-cluster-ip-range10.96.0.0/12Service에 ClusterIP를 나눠 줄 대역
--service-account-issuer, --service-account-signing-key-filehttps://kubernetes.default.svc.cluster.local, sa.keyServiceAccount 토큰을 발급할 때 넣는 발급자(iss)와 서명 키(10편)
--kubelet-client-certificate, --kubelet-client-keyapiserver-kubelet-client.crt·keyAPI 서버가 kubelet(10250)에 붙을 때 내미는 클라이언트 인증서
--kubelet-preferred-address-typesInternalIP,ExternalIP,Hostnamekubelet에 붙을 때 노드의 주소 가운데 무엇을 먼저 쓸지
--proxy-client-cert-file, --proxy-client-key-filefront-proxy-client.crt·keyAPI 서버가 확장 API 서버나 웹훅을 부를 때 내미는 인증서
--allow-privilegedtrueprivileged 컨테이너를 허용할지

--service-cluster-ip-range는 Service 대역이에요. kube-apiserver 레퍼런스에는 이 대역이 노드나 파드에 준 대역과 겹치면 안 된다고 적혀 있고 우리 클러스터의 파드 대역 10.244.0.0/16, 노드 주소 192.168.104.x와 겹치지 않아요. 이 대역의 첫 주소는 API 서버 자신이 가져가요. v1.37.2 소스(pkg/controlplane/apiserver/options/options.go)에는 "Select the first valid IP from ServiceClusterIPRange to use as the GenericAPIServer service IP."라는 주석과 함께 대역의 1번째 주소를 고르는 코드가 있어요. 파드가 API 서버에 붙을 때 쓰는 kubernetes Service의 10.96.0.1이 이렇게 정해져요(35편). kubeadm은 같은 대역의 10번째 주소를 DNS Service 몫으로 잡아요(kubeadm constants.go의 "Selects the 10th IP in service subnet CIDR range as dnsIP"). 29편의 kube-dns 10.96.0.10이 그 주소예요.

--kubelet-preferred-address-types는 kubeadm이 기본값을 바꾼 플래그예요. 레퍼런스의 기본값은 Hostname,InternalDNS,InternalIP,ExternalDNS,ExternalIP라서 노드 이름을 먼저 써요. kubeadm은 이것을 InternalIP,ExternalIP,Hostname으로 바꾸고 구현 문서에 그 이유를 "this makes kubectl logs and other API server-kubelet communication work in environments where the hostnames of the nodes aren't resolvable"이라고 적어 뒀어요. 5편에서 본 대로 우리 노드 이름은 DNS에서 찾을 수 없어요. 그런데도 kubectl logs가 되는 것은 API 서버가 노드 이름 대신 InternalIP(192.168.104.x)로 kubelet에 붙기 때문이에요.

--allow-privileged의 기본값은 레퍼런스에 false로 적혀 있어요. kubeadm 구현 문서에는 이 값을 true로 두는 이유가 "required e.g. by kube proxy"라고 적혀 있어요. 우리 클러스터에서도 kube-proxy와 calico-node 컨테이너가 privileged: true로 떠 있었어요(36-privileged-ds.txt). 둘 다 노드의 iptables와 라우팅을 고치는 컨테이너예요.

--requestheader-* 다섯 개와 --proxy-client-* 두 개는 API 애그리게이션에 쓰여요.

📖 용어: API 애그리게이션과 확장 API 서버
쿠버네티스 API의 일부 경로를 별도로 띄운 API 서버(확장 API 서버)가 처리하게 하는 구조예요. 클라이언트는 평소와 같이 6443에 요청하고 API 서버가 그 요청을 확장 API 서버로 넘겨요. kubectl top이 쓰는 metrics-server가 대표적인 확장 API 서버예요. 어느 경로를 누가 처리하는지는 APIService 객체에 적혀 있어요.

애그리게이션 설정 문서에 따르면 API 서버는 요청을 넘길 때 --proxy-client-cert-file의 인증서로 자신을 증명하고 원래 요청을 보낸 사용자의 이름과 그룹을 X-Remote-User, X-Remote-Group 같은 헤더에 실어 보내요. 확장 API 서버는 kube-system의 extension-apiserver-authentication ConfigMap에서 그 인증서에 서명한 CA와 허용된 이름(front-proxy-client), 헤더 이름을 읽어 이 요청을 믿어도 되는지 판단해요. 5편에서 kubeadm이 클러스터 CA와 별도로 front-proxy-ca를 만든 것도 이 용도예요. 문서는 --client-ca-file과 --requestheader-client-ca-file 두 CA 옵션이 "function independently and can conflict with each other, if not used correctly"라고 경고해요.

# 36-aggregation-idle.txt 발췌 (2026-11-14 22:06:51) ## 1. APIService: SERVICE 가 Local 이면 API 서버 자신이 처리, 서비스 이름이면 확장 API 서버로 넘김 24 Local ## 2. 어드미션 웹훅 설정 수 mutating: 0 validating: 0 ## 3. API 서버가 확장 API 서버에게 공개하는 인증 정보 (kube-system/extension-apiserver-authentication 의 키 이름만) requestheader-allowed-names ["front-proxy-client"] requestheader-client-ca-file (PEM 인증서 1개) requestheader-username-headers ["X-Remote-User"] …

→ APIService 24개가 모두 Local이라서 API 서버가 요청을 넘길 확장 API 서버가 하나도 없고 --proxy-client-* 인증서를 내밀 어드미션 웹훅도 0개라는 뜻이에요. 지금 우리 클러스터에는 이 일곱 줄을 쓸 곳이 없어요. ConfigMap에 CA와 헤더 이름이 올라가 있으니 metrics-server 같은 확장 API 서버를 설치하면 바로 쓰여요. 플래그를 단계별로 묶으면 27개 가운데 무엇이 지금 일하고 무엇이 앞으로를 위해 준비된 것인지가 갈려요.

3. 매니페스트에 없는 플래그는 기본값으로 돈다

매니페스트에는 kubeadm이 정해서 적은 플래그만 있어요. kube-apiserver 레퍼런스에는 플래그가 훨씬 많고 적히지 않은 플래그는 모두 기본값으로 돌아요. 그래서 매니페스트를 읽을 때는 "무엇이 적혀 있지 않은가"도 같이 봐야 해요. 우리 매니페스트에 없는 것 가운데 운영에서 의미가 큰 다섯 가지를 골랐어요.

없는 플래그그래서 지금은근거
--kubelet-certificate-authorityAPI 서버가 kubelet의 서버 인증서를 확인하지 않아요Control Plane-Node Communication 문서, 아래 원자료
--audit-policy-file, --audit-log-path감사 로그를 남기지 않아요Auditing 문서: "If the flag is omitted, no events are logged."
--encryption-provider-configSecret이 etcd에 평문으로 저장돼요22편 실험 뒤 되돌린 상태
--anonymous-auth기본값 true. 자격 없는 요청이 익명 사용자로 인가 단계까지 가요32편
--enable-priority-and-fairness기본값 true. 요청을 우선순위 수준별 줄로 나눠요5절

첫 줄은 2절의 --kubelet-client-*와 짝을 이뤄요. API 서버가 kubectl logs, exec, port-forward를 처리하려고 kubelet의 10250에 붙을 때 자기 인증서는 내밀지만 kubelet이 내미는 서버 인증서는 확인하지 않아요. Control Plane-Node Communication 문서는 이 상태를 이렇게 적어요. "By default, the API server does not verify the kubelet's serving certificate, which makes the connection subject to man-in-the-middle attacks and unsafe to run over untrusted and/or public networks." 그리고 이 연결을 확인하려면 --kubelet-certificate-authority로 kubelet 서버 인증서를 확인할 CA를 주라고 안내해요.

# 36-kubelet-serving-cert.txt 발췌 (2026-11-14 22:10:29) ## 1. API 서버 매니페스트의 kubelet 관련 플래그 (master) - --kubelet-client-certificate=/etc/kubernetes/pki/apiserver-kubelet-client.crt - --kubelet-client-key=/etc/kubernetes/pki/apiserver-kubelet-client.key - --kubelet-preferred-address-types=InternalIP,ExternalIP,Hostname --kubelet-certificate-authority 줄 수: 0 ## 2-1. worker1 의 kubelet 서빙 인증서 serverTLSBootstrap 줄 수(/var/lib/kubelet/config.yaml): 0 subject=CN = k8s-worker1@… issuer=CN = k8s-worker1-ca@… (worker2·worker3 도 같은 모양)

→ API 서버에는 kubelet 쪽 CA 플래그가 없고 worker1의 kubelet 서버 인증서는 클러스터 CA가 아니라 kubelet이 스스로 만든 k8s-worker1-ca가 서명했다는 뜻이에요. 그래서 플래그 한 줄만 더해서는 해결되지 않아요. kubeadm 인증서 관리 문서에도 "By default the kubelet serving certificate deployed by kubeadm is self-signed."라고 적혀 있고 클러스터 CA가 서명한 서버 인증서를 받게 하려면 kubelet 설정에 serverTLSBootstrap: true를 넣으라고 안내해요. 같은 문서는 이렇게 생긴 인증서 요청(CSR)을 컨트롤러 매니저의 기본 서명기가 자동으로 승인하지 않는다는 한계도 함께 적어요.

⚠️ 주의: 적혀 있지 않은 것도 설정이에요
• API 서버와 kubelet 사이의 연결은 기본 설정에서 kubelet의 신원을 확인하지 않아요. 이 실습 환경은 노드끼리만 닿는 내부망이지만 신뢰할 수 없는 망을 지난다면 문서의 안내대로 kubelet 서버 인증서를 CA가 서명하게 하고 --kubelet-certificate-authority를 줘요
• 감사 로그가 꺼져 있으면 누가 언제 어떤 객체를 지웠는지 API 서버에 기록이 남지 않아요. 켜려면 정책 파일과 로그 경로 플래그, 그리고 두 파일을 위한 hostPath 볼륨이 함께 필요해요
• 매니페스트만 보고 "이 클러스터는 이렇게 설정돼 있다"고 판단하면 빠지는 것이 생겨요. 적히지 않은 플래그의 기본값은 우리 바이너리의 kube-apiserver --help나 같은 버전의 레퍼런스로 확인해요

플래그를 바꿀 때는 매니페스트와 kubeadm 설정을 같이 고친다

플래그를 바꾸는 방법은 매니페스트 파일을 고치는 것뿐이에요. kubelet이 파일 변경을 보고 API 서버를 새로 띄워요. 22편에서 플래그 하나와 볼륨 하나를 더했을 때 API 서버가 다시 응답하기까지 약 41초가 걸렸고 컨트롤 플레인이 한 대인 우리 클러스터에서는 그동안 아무것도 바꿀 수 없었어요.

그런데 kubeadm은 이 매니페스트를 만들 때 쓴 설정을 따로 보관해요. kubeadm 재설정 문서에 따르면 kubeadm은 init과 upgrade 때 ClusterConfiguration을 kube-system의 kubeadm-config ConfigMap에 써 두고 apiServer 칸의 extraArgs, extraVolumes를 바꾸면 그 내용을 매니페스트에 직접 반영해야 해요. 반대로 매니페스트만 고치면 다음 업그레이드 때 그 변경이 사라질 수 있어요. 문서도 "During the execution of kubeadm upgrade on a managed node, kubeadm might overwrite configuration that was applied after the cluster was created"라고 경고해요.

# 36-apf-classify.txt 의 3절에서 ClusterConfiguration 일부 (kube-system/kubeadm-config) apiServer: certSANs: - k8s-master - 192.168.64.2 - 127.0.0.1 ... networking: dnsDomain: cluster.local podSubnet: 10.244.0.0/16 serviceSubnet: 10.96.0.0/12

→ 우리 ClusterConfiguration의 apiServer 칸에는 인증서에 넣을 이름(certSANs)만 있고 extraArgs는 없다는 뜻이에요. 그러니 매니페스트의 27개는 kubeadm이 정한 값과 init 때 준 값에서 나왔어요. 5편의 init 설정에 적은 advertiseAddress 192.168.104.1이 --advertise-address가 됐고 networking 칸의 serviceSubnet 10.96.0.0/12가 --service-cluster-ip-range가 됐어요.

💡 실무에서는: kubeadm 클러스터의 API 서버 플래그 바꾸기
• 먼저 /etc/kubernetes를 통째로 백업해요. 재설정 문서도 바꾸기 전에 이 폴더를 백업하라고 해요. 백업 파일을 /etc/kubernetes/manifests 안에 두면 kubelet이 그 파일로도 정적 파드를 띄우려 하니 폴더 밖에 둬요(20편)
• kubectl edit cm -n kube-system kubeadm-config로 ClusterConfiguration의 apiServer.extraArgs(파일을 가리키면 extraVolumes도)를 고쳐요
• 그 설정으로 kubeadm init phase control-plane apiserver --config <설정 파일>을 실행해 매니페스트를 다시 써요. 문서는 컨트롤 플레인 노드가 여럿이면 한 대씩 바꾸라고 해요
• 바뀐 뒤에는 kubectl get --raw /readyz가 ok인지 보고 새 플래그가 실제 프로세스에 들어갔는지 ps -ef | grep kube-apiserver로 확인해요

4. kubectl 명령은 HTTP 요청이 되고 가장 많은 요청은 kubectl이 보내지 않는다

지금까지는 API 서버를 설정 쪽에서 봤어요. 이번에는 API 서버가 받는 요청 쪽에서 봐요. kubectl에 -v=6을 주면 실제로 보낸 HTTP 요청이 한 줄씩 찍혀요. 같은 스크립트에서 파드 하나를 만들고 지우는 동안 watch 요청으로 어떤 이벤트가 오는지도 받아 봤어요.

그림 3. kubectl get은 GET 한 번, scale은 GET과 PATCH 두 번이었고 watch에는 파드 하나의 생애가 이벤트 12개로 흘러왔다

· kubectl get pod는 GET /api/v1/namespaces/default/pods?labelSelector=app%3Dmyweb&limit=500 한 번이었어요. 끝의 limit=500은 kubectl의 --chunk-size 기본값이에요. kubectl get 레퍼런스에 이 옵션은 "Return large lists in chunks rather than all at once."라고 적혀 있어요. 목록이 아무리 커도 500개씩 나눠 받아요.
· kubectl scale은 Deployment를 GET으로 한 번 읽고 deployments/myweb/scale 경로에 PATCH를 한 번 보냈어요. scale은 Deployment 객체 전체가 아니라 replicas만 다루는 하위 리소스(subresource)예요.
· watch는 목록 요청에 watch=true를 붙인 요청이에요. 연결을 끊지 않고 기다리다가 파드가 바뀔 때마다 이벤트를 보내 줘요.

📖 용어: watch와 resourceVersion
watch는 "이 조건에 맞는 객체가 바뀌면 알려 달라"는 요청이에요. API 서버는 객체가 생기면 ADDED, 바뀌면 MODIFIED, 지워지면 DELETED 이벤트를 같은 연결로 보내요. 이벤트마다 객체의 resourceVersion(rv)이 붙어 있어서 연결이 끊겼을 때 어느 지점부터 다시 받을지 정할 수 있어요. 컨트롤러와 kubelet은 같은 질문을 반복하는 대신 watch로 변경을 받아요. 캐시와 이어 받기 이야기는 39편에서 해요.

watch-demo 파드 하나에서 이벤트 12개가 왔어요. 처음 ADDED에서는 node가 None이었고 바로 다음 MODIFIED(rv 134416)에서 k8s-worker3이 채워졌어요. 스케줄러가 바인딩을 쓴 순간이에요(41편). 그 뒤로는 kubelet이 상태를 바꿀 때마다 MODIFIED가 와서 Pending, Running, Succeeded를 거쳐 DELETED(rv 134446)로 끝났어요. 그사이 rv는 134415에서 134446까지 올랐어요. 사람이 보낸 요청은 생성과 삭제 두 번이었는데 파드 객체는 그보다 훨씬 자주 바뀌었어요.

API 서버가 가장 많이 받는 요청은 프로브, Lease, 모니터링이었다

같은 스크립트를 돌린 19:39에 API 서버의 /metrics에서 apiserver_request_total을 동작(verb)별로 더해 보니 GET 18995, CONNECT 12844, PUT 11898, LIST 8542, WATCH 4847, POST 2766, PATCH 227, DELETE 24였어요. 이 요청이 모두 kubectl에서 왔을까요? 누가 보냈는지 보려고 21:55:56에 받은 /metrics를 대상(리소스와 경로)별로 다시 묶었어요.

그림 4. GET의 32%는 /readyz, PUT의 71%는 Lease, CONNECT는 거의 전부 nodes/proxy였다. 셋 다 사람이 보낸 요청이 아니다

숫자는 API 서버 프로세스가 17:26:05에 시작한 뒤 16190초 동안 쌓인 값이에요. 많은 순으로 세 갈래가 보였어요.

· GET의 32%는 /readyz였어요. 16190초 동안 16199번, 초당 1번꼴이에요. 1절에서 본 매니페스트의 readinessProbe가 periodSeconds 1로 /readyz를 부르니 kubelet이 1초마다 보내는 프로브가 그대로 쌓인 거예요.
· PUT의 71%는 Lease 갱신이었어요. 초당 약 1.48번이에요. Leases 문서는 kubelet의 하트비트가 "an update request to this Lease object"라고 적어요. kubelet 네 대가 10초마다 갱신하면(25편) 초당 0.4번이고 스케줄러와 컨트롤러 매니저가 리더 자리를 2초마다 갱신하면 초당 1번이에요. 2초는 kube-scheduler와 kube-controller-manager 레퍼런스에 적힌 --leader-elect-retry-period의 기본값이에요. 둘을 더한 초당 1.4번이 실제 값과 거의 같아요.
· CONNECT는 거의 전부 nodes/proxy였어요. 초당 약 1.60번이에요. 11편에서 설치한 Prometheus의 수집 설정에는 kubernetes-nodes와 kubernetes-cadvisor 두 job이 노드 지표를 kubernetes.default.svc:443의 /api/v1/nodes/${1}/proxy/metrics 경로로 긁도록 적혀 있고 수집 간격은 5초예요. job 2개가 노드 4대를 5초마다 긁으면 초당 1.6번이에요. 이 요청을 받은 API 서버는 2절의 --kubelet-client-* 인증서를 들고 각 노드의 10250에 다시 붙어요. 스냅숏에서 nodes/proxy 25928번 가운데 25251번이 200이었어요. kubelet은 자격 없는 요청에 401을 돌려주니(26편) API 서버가 내민 인증서를 kubelet이 받아들였다는 뜻이에요.

19:39의 누적값을 약 8000초로 나누면 전체 PUT은 초당 약 1.5번, CONNECT는 약 1.6번이에요. 21:55에는 전체 PUT이 초당 2.08번이었고 CONNECT는 약 1.61번이었어요. API 서버가 가장 자주 받는 요청은 사람이 친 kubectl이 아니라 kubelet의 프로브와 Lease 갱신, 모니터링 수집이었어요. 그러니 API 서버가 느려졌을 때 "요청이 몰렸다"고 하면 먼저 누가 보낸 요청인지를 나눠 봐야 해요. 하트비트 하나하나가 API 서버에 쓰기 요청이라는 점은 49편에서 다시 다뤄요.

5. 요청이 몰리면 APF가 리더 선출과 kubelet의 처리 몫을 나눈다

요청이 이렇게 여러 곳에서 오면 한 클라이언트가 폭주할 때가 문제예요. 어떤 컨트롤러가 버그로 목록 요청을 쉬지 않고 보내면 그 요청이 API 서버의 처리 자리를 다 차지해서 kubelet의 Lease 갱신이 늦어질 수 있어요. 갱신이 늦어지면 25편에서 본 대로 노드가 Unknown이 되고 파드가 쫓겨날 수도 있어요.

API 서버가 동시에 처리하는 요청 수에는 한도가 있어요. 레퍼런스에 따르면 --max-requests-inflight(기본 400)와 --max-mutating-requests-inflight(기본 200)가 그 한도예요. API Priority and Fairness 문서는 APF(API Priority and Fairness)가 켜져 있으면 "the concurrency limits defined by these flags are summed and then the sum is divided up among a configurable set of priority levels"라고 설명해요. 600자리를 우선순위 수준마다 나누고 수준별 동시 처리 제한에 따라 요청을 처리한다는 뜻이에요. 같은 문서는 기본 설정의 효과를 이렇게 적어요. "an ill-behaved Pod that floods the API server with requests cannot prevent leader election or actions by the built-in controllers from succeeding."

📖 용어: FlowSchema와 우선순위 수준(PriorityLevelConfiguration)
APF를 이루는 두 API 객체예요. FlowSchema는 "누가 어떤 요청을 보냈는가"로 요청을 분류하는 규칙이고 matchingPrecedence 숫자가 작은 것부터 맞춰 보다가 처음 맞는 것 하나만 써요. 분류된 요청은 FlowSchema가 가리키는 우선순위 수준의 줄에 서요. 우선순위 수준마다 동시 처리 자리를 나눠 갖는 몫(nominalConcurrencyShares)과 줄 길이가 정해져 있어요.

우리 클러스터에는 FlowSchema 11개가 기본으로 들어 있었고 각각 우선순위 수준 하나를 가리켜요(36-apiserver-requests.txt의 4절). 요청이 실제로 어느 줄에 서는지는 응답 헤더로 확인할 수 있어요. APF를 거친 요청의 응답에는 X-Kubernetes-PF-FlowSchema-UID와 X-Kubernetes-PF-PriorityLevel-UID 헤더가 붙어 있었어요. 같은 GET 요청을 사용자만 바꿔 가며 보내고 UID를 이름으로 바꿔 봤어요. 다른 사용자로 보낼 때는 관리자 권한으로 그 사용자 행세를 하는 --as 옵션을 썼어요.

그림 5. 같은 GET이라도 사용자에 따라 global-default, workload-high, node-high, workload-low로 갈렸고 /readyz는 APF 대기열을 건너뛰는 exempt였다
그림 6. 점선 상자(리더 선출 Lease)는 FlowSchema 설정에서 확인한 것이고 나머지 다섯은 응답 헤더로 확인했다. 몫은 nominalConcurrencyShares 값이다

그림 6을 위에서부터 읽으면 이래요.

· kubelet의 /readyz 프로브는 APF 대기열을 건너뛰어요. probes FlowSchema가 /healthz, /readyz, /livez에 대한 get을 인증 여부와 상관없이 exempt 수준으로 보내요. exempt 수준의 요청은 APF의 동시 처리 제한과 대기열을 건너뛰어요. 프로브가 APF 대기열에 막히는 일을 피하는 설정이에요. APF 문서의 "Health check concurrency exemption" 절은 제안 설정이 상태 확인 요청을 따로 대우하지 않는다고 적고 있어요. 그런데 v1.37.2 소스의 기본 설정(bootstrap/default.go)에는 "the following flow schema exempts probes"라는 주석과 함께 probes가 들어 있고 우리 클러스터에도 있었어요. 문서의 그 절이 소스의 변화를 따라가지 못한 것으로 보여요.
· kubelet의 노드 상태와 Lease는 node-high 수준으로 가요. system-node-high FlowSchema가 system:nodes 그룹의 nodes, nodes/status, leases 요청을 따로 골라내요. 그 밖의 kubelet 요청은 system-nodes FlowSchema를 거쳐 system 수준으로 가요.
· 리더 선출 Lease는 leader-election 수준을 따로 가져요. 문서는 리더 선출이 실패하면 컨트롤러가 재시작하고 그 재시작이 더 비싼 요청을 부르기 때문에 다른 트래픽과 떼어 놓는다고 설명해요.
· 스케줄러와 컨트롤러 매니저의 일반 요청은 workload-high, 파드의 ServiceAccount는 workload-low로 가요. 문서는 workload-low를 "requests from any other service account, which will typically include all requests from controllers running in Pods"라고 설명해요. 다만 4절의 Prometheus 요청(nodes/proxy)은 이 줄에 서지 않아요. v1.37.2 소스(pkg/controlplane/apiserver/config.go)는 하위 리소스가 proxy, exec, log인 요청을 오래 걸리는 요청(long-running)으로 따로 분류하고 APF 문서는 이런 요청이 "not subject to the API Priority and Fairness filter"라고 적어요.
· 관리자인 제 kubectl은 global-default에 섰어요. exempt FlowSchema는 system:masters 그룹만 고르는데 kubeadm의 관리자 인증서는 kubeadm:cluster-admins 그룹이라서(32편) 맞는 FlowSchema를 찾아 precedence 9900인 global-default까지 내려갔어요.

APF는 요청을 보낸 사람으로 줄을 나눠서 한 줄이 넘쳐도 다른 줄은 제 몫을 지키게 해요. 그림의 몫은 다른 수준과 견준 비율이에요. 문서에 따르면 한가한 수준의 자리를 바쁜 수준이 잠시 빌려 쓰기도 해요.

💡 실무에서는: API 서버가 느릴 때 APF부터 봐요
• kubectl get ... -v=8의 응답 헤더 X-Kubernetes-PF-FlowSchema-UID로 내 요청이 어느 줄에 섰는지 알 수 있어요. UID는 kubectl get flowschema -o custom-columns=NAME:.metadata.name,UID:.metadata.uid로 이름과 맞춰요
• 요청이 거절되기 시작했다면 APF 문서에 나오는 apiserver_flowcontrol_rejected_requests_total 지표를 FlowSchema와 우선순위 수준별로 봐요. 어느 줄이 넘쳤는지가 곧 누가 폭주했는지예요
• 사람이 쓰는 관리자 kubeconfig는 global-default 줄에 서요. 장애 때 kubectl이 느리다고 해서 kubelet이나 컨트롤러도 같이 막혔다고 단정하지 말고 줄별로 나눠 봐요

6. 형식이 틀리면 422로, 어드미션에서 막히면 403으로 거절된다

마지막 질문은 "Pod의 데이터 유효성 검사, 어드미션 컨트롤러가 뭐야?"였어요. 둘 다 "저장하기 전에 요청을 검사한다"는 점에서 같아 보이지만 API 서버 안에서는 다른 단계예요. 실습용 네임스페이스에서 세 가지 요청을 보내 봤어요.

그림 7. 형식이 틀린 파드는 "is invalid", 쿼터를 넘긴 파드는 "is forbidden"으로 거절됐고 통과한 파드에는 어드미션이 칸을 채웠다

· 형식이 틀린 파드는 The Pod "bad-name" is invalid로 거절됐어요. 컨테이너 이름은 소문자, 숫자, 하이픈만 쓰는 RFC 1123 형식이어야 하는데 Bad_Name에는 대문자와 밑줄이 있어요. 이 검사는 플러그인이 아니라 Pod라는 객체 종류에 정해진 검증 코드가 해요.
· 쿼터를 넘긴 파드는 Error from server (Forbidden): ... exceeded quota로 거절됐어요. 형식은 맞지만 "이 네임스페이스에는 파드 1개까지"라는 규칙에 걸렸어요. 이 판단은 validating 어드미션 플러그인 ResourceQuota가 해요(33편).
· 통과한 파드에는 ServiceAccount, DefaultTolerationSeconds, Priority 플러그인이 칸을 채웠어요. mutating 어드미션이 한 일이고 33편에서 자세히 봤어요.

두 거절은 HTTP 상태 코드부터 달라요. 33편에서 -v=6으로 본 쿼터 거절의 응답은 403 Forbidden이었어요. 형식 검사의 거절은 아래 실험에서 422 Unprocessable Entity로 돌아왔어요. v1.37.2 소스(registry/rest/create.go의 BeforeCreate)에서 errors.NewInvalid로 만들어지고 이 함수(apimachinery errors.go)는 상태 코드를 http.StatusUnprocessableEntity, 이유를 Invalid로 정해요.

📖 용어: 422 Unprocessable Entity
"요청 형식은 읽을 수 있지만 담긴 내용이 규칙에 맞지 않아 처리할 수 없다"는 HTTP 상태 코드예요. 쿠버네티스는 객체의 칸 값이 형식에 맞지 않을 때 이 코드와 함께 Reason Invalid를 돌려주고 kubectl은 이것을 "is invalid"로 보여 줘요. 권한이나 정책 때문에 거절할 때 쓰는 403 Forbidden과 구분돼요.

그럼 형식 검사는 어드미션의 앞일까요, 뒤일까요? Controlling Access 문서는 "Once a request passes all admission controllers, it is validated using the validation routines for the corresponding API object, and then written to the object store"라고 적어서 어드미션을 모두 지난 뒤에 검증한다고 읽혀요. v1.37.2 소스에서 생성 요청이 지나는 순서를 따라가면 조금 달라요.

// staging/src/k8s.io/apiserver/pkg/endpoints/handlers/create.go (v1.37.2) if mutatingAdmission, ok := admit.(admission.MutationInterface); ok && mutatingAdmission.Handles(admission.Create) { if err := mutatingAdmission.Admit(ctx, admissionAttributes, scope); err != nil { // ① mutating 어드미션 return nil, err } } result, err := requestFunc() // → r.Create(ctx, name, obj, rest.AdmissionToValidateObjectFunc(admit, ...), options) // staging/src/k8s.io/apiserver/pkg/registry/generic/registry/store.go 의 create (v1.37.2) if err := rest.BeforeCreate(e.CreateStrategy, ctx, obj); err != nil { // ② 객체 종류별 형식 검증 (422) return nil, err } if createValidation != nil { if err := createValidation(ctx, obj.DeepCopyObject()); err != nil { // ③ validating 어드미션 (403 등) return nil, err } } ... if err := e.Storage.Create(ctx, key, obj, out, ttl, dryrun.IsDryRun(options.DryRun)); err != nil { // ④ etcd 저장

→ mutating 어드미션이 객체를 고친 다음 객체 종류별 형식 검증을 하고 그다음에 validating 어드미션을 부르고 마지막에 저장한다는 뜻이에요. 형식 검증은 두 어드미션 단계 사이에 있어요. 그림 2에서 스키마 검증을 3과 5 사이에 둔 이유가 이것이에요.

소스의 순서가 실제 응답에서도 그대로인지 확인했어요. 파드를 0개까지만 허용하는 ResourceQuota(zero-pods)를 둔 실험용 네임스페이스에 형식이 맞는 파드와 컨테이너 이름이 틀린 파드를 -v=6으로 하나씩 보냈어요. 둘 다 쿼터를 넘기는 요청이고 두 번째 파드는 형식까지 틀렸어요.

그림 8. 쿼터만 넘긴 파드는 403, 형식도 틀리고 쿼터도 넘긴 파드는 422였다. 형식 검증이 ResourceQuota보다 먼저 돈다

형식이 맞는 파드는 POST .../pods → 403 Forbidden과 exceeded quota: zero-pods를 받았어요. 형식이 틀린 파드는 똑같이 쿼터를 넘겼는데도 422 Unprocessable Entity와 is invalid: spec.containers[0].name을 받았어요. 쿼터 이야기는 메시지에 아예 나오지 않았어요. validating 어드미션인 ResourceQuota까지 가기 전에 형식 검증에서 끝났다는 뜻이에요. 소스에서 읽은 순서 그대로예요.

이 순서에는 이유가 있어 보여요. mutating 어드미션이 칸을 채우거나 고친 결과도 형식에 맞아야 하니 검증은 고친 뒤에 해야 해요. 반대로 validating 어드미션은 최종 모습을 봐야 정책을 제대로 적용할 수 있어요. Dynamic Admission Control 문서도 "Admission webhooks that need to guarantee they see the final state of the object in order to enforce policy should use a validating admission webhook, since objects can be modified after being seen by mutating webhooks."라고 적어요. "is invalid"는 객체를 고쳐야 한다는 뜻이고 "is forbidden"은 권한이나 정책을 봐야 한다는 뜻이에요.

💡 실무에서는: 거절 메시지로 고칠 곳을 먼저 가려요
• is invalid(422)면 YAML을 고쳐요. 메시지에 칸 경로(spec.containers[0].name)와 지켜야 할 형식이 함께 나와요
• is forbidden(403)이면 메시지에 User "..." cannot ...이 있는지 봐요. 있으면 인가(RBAC, 32편)이고 exceeded quota나 정책 이름이 있으면 어드미션(33편)이에요
• 배포 전에 kubectl apply --dry-run=server -f ...로 보내면 형식 검증과 어드미션을 모두 거친 결과를 저장 없이 받아 볼 수 있어요
✍️ 오늘의 요약
API 서버는 kubelet이 파일 한 장으로 띄우는 정적 파드이고 그 파일의 플래그는 요청이 지나는 길의 단계마다 하나씩 놓여 있어요.

컨트롤 플레인을 띄우는 방식 넷 가운데 kubeadm은 정적 파드를 골랐고 그래서 API 서버는 API 서버 없이도 다시 뜨면서 프로브, 우선순위, hostNetwork 같은 파드 기능을 그대로 써요. 워커의 kubelet도 같은 폴더를 보지만 파일이 없어서 API 서버는 마스터에만 있었어요. 플래그 27개 가운데 18개는 전송, 인증, 인가, 어드미션, 저장 단계를 하나씩 맡고 9개는 Service 대역, 토큰 발급, kubelet과 확장 API 서버에 붙는 방법을 정해요. 그중 front-proxy 일곱 줄은 확장 API 서버와 웹훅이 없어 지금은 쉬고 있었고 적히지 않은 플래그 때문에 kubelet 서버 인증서 확인과 감사 로그는 꺼져 있었어요. API 서버가 가장 많이 받은 요청은 1초마다 오는 /readyz 프로브, Lease 갱신, Prometheus의 nodes/proxy 수집이었고 APF는 이런 요청을 보낸 쪽에 따라 다른 줄에 세워 리더 선출과 kubelet의 몫을 지켜요. 형식이 틀린 요청은 두 어드미션 단계 사이의 형식 검증에서 422로, 규칙에 어긋난 요청은 validating 어드미션에서 403으로 끝나요. 매니페스트를 읽을 때는 적힌 줄과 함께 적히지 않은 줄도 봐요.
