1. 필터 없이 열면 시스템 파드의 선 때문에 내 앱이 보이지 않는다

Kubeshark는 13편에서 본 eBPF로 노드를 지나가는 트래픽을 읽어 14편에서 설치한 대시보드에 보여 줘요. 대시보드 위쪽에는 API STREAM, MAP, SNAPSHOTS 세 탭이 있어요. API STREAM에서는 요청과 응답을 묶은 항목이 하나씩 쌓이고 MAP에서는 같은 데이터로 누가 누구와 통신했는지를 선으로 그려 보여 줘요. 이 실습의 Kubeshark는 v53.6.0이고 이 글의 화면은 모두 마스터를 뺀 워커 3대의 트래픽을 수집하던 상태에서 찍었어요.

그림 1. 필터 없이 연 MAP 탭. 33초 동안 371개 항목이 쌓였고 어느 선이 무엇인지 알아보기 어려웠다
📖 용어: 서비스맵 (Kubeshark Workload Map)
워크로드끼리 누가 누구와 통신하는지 선으로 그린 화면이에요. 공식 문서에서는 L4/L7 Workload Map이라는 이름으로 안내하고 연결마다 프로토콜을 색으로 구분한다고 설명해요. 이 실습 화면에서는 원 하나가 파드 하나였고 파드가 아닌 주소는 IP 그대로 나왔어요.

그림 1에서는 왼쪽 위의 설정 창을 열어 두었어요. 지표는 Bandwidth, 묶는 단위는 Pod / Service로 되어 있고 Show cumulative bandwidth는 꺼져 있어요. Include request sizes와 Include response sizes는 켜져 있어요. 서비스맵 문서에 따르면 Bandwidth는 워크로드 사이의 데이터 양이고 다른 선택지인 Throughput은 패킷 속도예요. cumulative를 켜면 비율(rate) 대신 누적값을 보여 준다고 해요. 그러니 이 설정에서 선의 숫자는 요청과 응답 크기를 더한 데이터 양의 초당 값으로 읽을 수 있어요.

오른쪽 위에는 "Aggregate figures represent average sizes per second since 8:55:50 PM UTC+09:00"라는 안내가 떠 있어요. 오후 8시 55분 50초부터 지금까지의 초당 평균 크기라는 뜻이에요. 이 한 줄은 5장에서 다시 중요해져요.

위쪽 파란 띠의 "Targeting 19 pods in 4 namespaces across 3 nodes"는 네임스페이스 4개에 걸친 파드 19개가 수집 대상이라는 뜻이에요. 14편에서 본 대로 수집기는 워커 3대에만 떠 있어서 노드가 3개로 나와요. 아래쪽 범례에는 네임스페이스(headlamp, monitoring, kube-system)와 internal, 프로토콜(DNS, HTTP, ICMPv6, TCP-FLOW, UDP-FLOW), 노드(k8s-master, k8s-worker1~3, no node)가 색으로 나뉘어 있어요. 클러스터의 흐름이 한 화면에 모두 그려지니 실습 앱 하나의 흐름을 보려면 화면에 남길 선부터 줄여야 해요.

선을 줄이는 방법은 둘이에요. 수집 대상 자체를 줄이는 캡처 필터와 이미 수집한 것 중에서 화면에 보일 것만 고르는 디스플레이 필터예요.

📖 용어: 캡처 필터 (Capture Filters)
어떤 파드의 트래픽을 수집할지 정하는 설정이에요. kubeshark tap 뒤에 주는 네임스페이스(-n)와 파드 이름 정규식이 여기에 해당해요(14편). Capture Filters 문서에 따르면 Kubeshark는 대상으로 정한 트래픽만 수집하고 색인하며 자원 사용량은 처리하는 트래픽 양과 직접 관련돼 있어요.
📖 용어: KFL (Kubeshark Filter Language)
Kubeshark에서 트래픽을 거르는 식 언어예요. KFL 문서에 따르면 CEL(Common Expression Language)을 바탕으로 하고 src.pod.name(출발지 파드 이름), dst.pod.name(목적지 파드 이름) 같은 필드를 ==, &&, ||로 묶어 조건을 써요. 문자열의 앞부분이 같은지는 startsWith로 봐요.

Display Filters 문서에는 디스플레이 필터가 대시보드에 보이는 것만 바꾸고 수집하는 트래픽에는 영향을 주지 않는다고 적혀 있어요. 적용 범위도 지금 보고 있는 브라우저 탭 하나여서 탭마다 다른 조건으로 같은 클러스터를 볼 수 있어요. 필터를 적용하면 식이 브라우저 주소에 들어가서 주소를 복사하면 같은 화면을 공유할 수 있다고 해요. 캡처 필터는 반대로 모든 사용자와 세션에 적용돼요. 서비스맵 문서에도 지도가 지금 걸려 있는 KFL 조건으로 거른 트래픽을 반영한다고 나와 있어요. 이번 실험에서는 수집 범위는 그대로 두고 대시보드 위쪽 입력 칸에 아래 식 하나를 넣은 뒤 Apply를 눌렀어요.

dst.pod.name.startsWith("myweb") || src.pod.name == "loadgen"

→ 목적지 파드 이름이 myweb으로 시작하거나 출발지 파드 이름이 loadgen인 항목만 보여 달라는 뜻이에요.

앞 절반은 받는 쪽으로 거르는 조건이에요. 이 실험에서는 요청을 보낸 곳 하나가 파드가 아니라 마스터 노드 자체였어요. 노드에서 보낸 요청에는 출발지 파드 이름이 없으니 받는 쪽인 myweb 파드의 이름으로 걸러야 해요. 뒤 절반은 클라이언트 파드 loadgen이 보낸 것을 모두 남기는 조건이에요. loadgen이 myweb 말고 다른 곳으로 보낸 요청도 함께 남는데 5장에서 이 조건 때문에 DNS 선이 나타나요. 지도를 보기 전에 어떤 흐름을 볼지부터 식으로 정해야 해요.

💡 실무에서는: 지도를 열면 필터부터 걸어요
• 내 앱으로 들어오는 요청: dst.pod.name.startsWith("앱 이름")
• 클라이언트 파드 하나가 보내는 것 전부: src.pod.name == "파드 이름"
• 네임스페이스 단위: dst.pod.namespace == "production" (KFL 문서의 예시)
• 디스플레이 필터는 화면만 바꿔요. 수집기의 메모리와 CPU를 줄이려면 tap 대상을 좁혀야 해요(14편)
• 필터를 적용하면 식이 브라우저 주소에 들어가니 그 주소를 공유하면 같은 조건의 화면을 함께 볼 수 있어요

2. 지도를 믿으려면 지도와 따로 센 숫자가 있어야 한다

강의 슬라이드에는 nginx:1.25.1-alpine 이미지로 myweb을 3개 띄우고 curl로 요청을 보내는 예제가 있었어요. 강의 자료라서 슬라이드 이미지는 싣지 않고 내용만 옮겨요. 이 예제를 여러 번 반복하면서 서비스맵의 유량이 어떻게 바뀌는지 보기로 했어요. 준비는 이랬어요.

master$ kubectl create deployment myweb --image=nginx:1.25.1-alpine --port=80 --replicas=3 deployment.apps/myweb created master$ kubectl get po -o wide | grep myweb # 뒤쪽 열은 뺐다 NAME READY STATUS RESTARTS AGE IP NODE myweb-859c4764d4-4tjzk 1/1 Running 0 35s 10.244.194.88 k8s-worker1 myweb-859c4764d4-5xtpv 1/1 Running 0 35s 10.244.100.213 k8s-worker3 myweb-859c4764d4-n9rd8 1/1 Running 0 35s 10.244.126.19 k8s-worker2 master$ for ip in 10.244.194.88 10.244.100.213 10.244.126.19; do curl -s -o /dev/null -w ... http://$ip/; done 10.244.194.88 200 615B 10.244.100.213 200 615B 10.244.126.19 200 615B master$ kubectl expose deployment myweb --port=80 service/myweb exposed master$ kubectl run loadgen --image=curlimages/curl:8.11.1 --command -- sleep infinity pod/loadgen created pod/loadgen condition met # Service와 loadgen 파드를 조회한 결과 NAME TYPE CLUSTER-IP EXTERNAL-IP PORT(S) AGE myweb ClusterIP 10.105.164.156 <none> 80/TCP 8s NAME READY STATUS IP NODE loadgen 1/1 Running 10.244.194.89 k8s-worker1

→ myweb 파드 3개가 워커 3대에 하나씩 떴고 마스터에서 파드 IP로 직접 요청하면 셋 다 200과 615B 페이지로 응답했다는 뜻이에요. Service myweb의 ClusterIP는 10.105.164.156이고 클라이언트 파드 loadgen은 worker1에 10.244.194.89로 떴어요.

지도 숫자가 맞는지 판단하려면 지도와 상관없이 센 숫자가 있어야 해요. 지도만 봐서는 지도가 틀린 것인지 요청이 정말 그렇게 간 것인지 구분할 수 없으니까요. 그래서 nginx의 접근 로그를 기준으로 삼았어요.

📖 용어: 접근 로그 (access log)
nginx가 요청을 하나 처리할 때마다 남기는 한 줄 기록이에요. 줄마다 요청이 들어온 시각과 클라이언트 주소가 들어 있어요. 이 실습의 nginx 이미지에서는 kubectl logs로 이 로그를 볼 수 있었어요. 지도와 상관없이 nginx가 직접 남긴 기록이라 이번 실험에서는 이 건수를 정답지로 삼았어요.

요청은 짧은 스크립트로 보냈어요. URL마다 정해진 간격으로 curl을 백그라운드로 하나씩 띄우고 다 끝나면 보낸 건수를 출력해요.

#!/usr/bin/env bash # 사용법: traffic.sh <초> <URL당 초당 요청 수> <URL>... # 각 URL 에 초당 rps 번씩 curl 을 보낸다. 끝나면 보낸 요청 수를 찍는다. dur=$1; rps=$2; shift 2 end=$(( $(date +%s) + dur )); rounds=0 interval=$(awk "BEGIN{print 1/$rps}") while [ "$(date +%s)" -lt "$end" ]; do for u in "$@"; do curl -s -o /dev/null --max-time 2 "$u" & done rounds=$((rounds+1)); sleep "$interval" done wait echo "$(date +%T) 끝: URL ${#}개 x ${rounds}번 = $(( rounds * $# ))건 (${dur}초, URL당 ${rps}/s)"

→ traffic.sh 60 10 http://주소/는 60초 동안 그 주소에 초당 10번 요청하라는 뜻이에요. curl 프로세스 하나가 요청 하나를 보내고 요청마다 새 프로세스가 뜨니 TCP 연결도 요청마다 새로 열려요. 이 점은 4장에서 다시 나와요.

단계마다 순서는 같았어요. 대시보드를 새로 열어 KFL 식을 걸고 MAP 탭으로 간 다음 60초 동안 요청을 보냈어요. 화면은 요청을 시작하고 68~69초 뒤에 찍었어요. 네 단계를 그림으로 정리하면 이래요.

그림 2. 앞의 세 단계는 마스터 노드가 보냈고 마지막 단계는 클라이언트 파드가 Service 이름으로 보냈다

실험이 끝난 뒤 Mac에서 파드마다 kubectl logs로 접근 로그를 받았어요. 로그 줄의 시각이 어느 단계의 시작과 끝 사이에 있는지로 단계를 나눠 셌고 결과는 그림 3이에요.

그림 3. nginx 접근 로그로 센 단계별·파드별 요청 수. 이 표를 정답지로 삼았다

먼저 보낸 건수와 로그 건수가 맞는지 봤어요. 스크립트가 출력한 건수는 1단계 180건, 2단계 715건(593건과 122건), 3단계 586건, 4단계 574건이었고 로그 합계도 180, 715, 586, 574로 같았어요. 보낸 요청이 모두 nginx에 닿았고 단계별로 나눈 건수도 보낸 건수와 맞았다는 뜻이에요. 출발지 주소는 앞의 세 단계가 모두 10.244.235.192였고 4단계는 loadgen의 10.244.194.89였어요. 지도와 따로 센 이 표가 있어야 지도의 숫자가 맞는지 틀리는지 말할 수 있어요.

3. 균등과 쏠림: 같은 시간이 지난 화면끼리는 지도 숫자가 요청 수에 비례했다

1단계에서는 마스터 노드에서 파드 IP 세 개에 초당 1번씩 요청했어요.

master$ IPS=$(kubectl get po -l app=myweb -o jsonpath="{.items[*].status.podIP}"); /lab/kubeshark-lab/traffic.sh 60 1 $(for i in $IPS; do echo http://$i/; done) 21:00:09 끝: URL 3개 x 60번 = 180건 (60초, URL당 1/s)

→ 파드 IP 세 개에 60번씩, 모두 180건을 보냈다는 뜻이에요. 스크립트는 마스터의 /lab/kubeshark-lab/ 아래에 있어요.

그림 4. 1단계. 세 파드가 60건씩 받았고 세 선은 모두 527.07B/s였다

세 선의 숫자는 소수점 둘째 자리까지 같았어요. 세 파드가 같은 기본 페이지를 같은 횟수만큼 응답했으니 바이트도 같아야 맞아요. 요청은 마스터 노드에서 보냈는데 지도의 출발지는 k8s-master가 아니라 노란 원의 10.244.235.192였어요. 범례에서는 이 원이 internal로 분류됐어요. 이 주소가 무엇인지는 4장에서 따라가요.

2단계에서는 worker1에 있는 파드 하나에만 초당 10번, 나머지 둘에는 초당 1번씩 보냈어요. 노드 이름으로 파드를 고를 때는 --field-selector spec.nodeName=k8s-worker1을 썼어요.

master$ A=$(kubectl get po -l app=myweb --field-selector spec.nodeName=k8s-worker1 -o jsonpath="{.items[0].status.podIP}"); O=$(kubectl get po -l app=myweb -o jsonpath="{.items[*].status.podIP}" | tr " " "\n" | grep -v "^$A$"); /lab/kubeshark-lab/traffic.sh 60 10 http://$A/ & /lab/kubeshark-lab/traffic.sh 60 1 $(for i in $O; do echo http://$i/; done); wait 21:01:33 끝: URL 1개 x 593번 = 593건 (60초, URL당 10/s) 21:01:33 끝: URL 2개 x 61번 = 122건 (60초, URL당 1/s)

→ worker1 파드에는 60초 동안 593번, 나머지 두 파드에는 61번씩 보냈다는 뜻이에요. 목표였던 600건보다 조금 적게 나갔어요.

그림 5. 2단계. 아래쪽 파드로 가는 선만 5.20kB/s였고 나머지 두 선은 535.87B/s였다

아래쪽 원은 화면 밖으로 잘려 이름이 보이지 않아요. 위의 두 원은 n9rd8과 5xtpv예요. 그러니 남은 하나는 worker1의 4tjzk예요. 지도에서 굵은 선과 가는 선의 비는 5.20kB/s ÷ 535.87B/s = 9.7배이고 로그에서는 593건 ÷ 61건 = 9.7배예요. 쏠림을 지도에서 찾는 방법은 이 그림 그대로예요. 같은 출발지에서 나가는 선들 가운데 혼자 굵은 선을 찾으면 돼요.

두 단계를 이어 보면 하나가 더 보여요. 1단계의 60건은 527.07B/s였고 2단계의 61건은 535.87B/s였어요. 61 ÷ 60 = 1.0167이고 535.87 ÷ 527.07도 1.0167이에요. 두 화면 모두 since 시각에서 69초가 지났을 때 찍었어요(8:59:08 → 9:00:17, 9:00:31 → 9:01:40). since 시각부터 같은 시간이 지난 화면끼리는 지도 숫자가 요청 건수에 비례했어요.

화면 아래의 Displayed items는 1단계 183개, 2단계 721개였어요. 보낸 요청(180건, 715건)보다 각각 3개, 6개 많았는데 남는 항목이 무엇인지는 따라가지 않았어요.

⚠️ 주의: 선의 숫자는 요청 수가 아니라 바이트예요
지표를 Bandwidth로 두고 요청·응답 크기를 모두 더했으니 선의 숫자는 데이터 양이에요. 이번 실험에서는 모든 요청이 같은 페이지를 받아서 바이트의 비율이 요청 수의 비율과 같았어요. 응답 크기가 요청마다 다른 앱이라면 큰 파일을 받는 요청 몇 건이 작은 요청 수백 건보다 굵게 그려질 수 있어요. 요청이 몰렸는지 보려면 선의 굵기와 함께 파드별 요청 수(접근 로그나 요청 수 메트릭)도 같이 보세요.

4. ClusterIP로 보내면 지도에서 Service가 보이지 않는다

3단계에서는 파드 IP 대신 Service의 ClusterIP로 초당 10번 보냈어요. 어느 파드로 보낼지는 쿠버네티스에 맡긴 거예요.

master$ C=$(kubectl get svc myweb -o jsonpath="{.spec.clusterIP}"); echo "ClusterIP $C"; /lab/kubeshark-lab/traffic.sh 60 10 http://$C/ ClusterIP 10.105.164.156 21:02:55 끝: URL 1개 x 586번 = 586건 (60초, URL당 10/s)

→ Service myweb의 ClusterIP 10.105.164.156으로 60초 동안 586번 보냈다는 뜻이에요.

그림 6. 3단계. ClusterIP로 보냈는데 Service를 뜻하는 원은 없고 10.244.235.192에서 파드 3개로 선이 바로 이어졌다

지도의 세 선은 4tjzk로 가는 선이 1.80kB/s, 5xtpv로 가는 선이 1.70kB/s, n9rd8로 가는 선이 1.60kB/s였어요. 셋의 합에서 차지하는 몫으로 바꾸면 35%, 33%, 31%예요. 로그는 200건, 199건, 187건으로 34%, 34%, 32%였어요. 몫으로 보면 지도와 로그가 거의 같아요.

더 눈에 띄는 것은 지도에 없는 것이에요. 요청은 10.105.164.156으로 보냈는데 Service myweb을 뜻하는 원이 없어요. 10.244.235.192에서 파드 3개로 선이 바로 이어져 있고 범례도 1단계와 같은 default와 internal뿐이에요. 그 이유는 패킷의 목적지가 어디서 바뀌는지 따라가면 보여요.

📖 용어: ClusterIP와 kube-proxy
ClusterIP는 Service를 만들면 쿠버네티스가 배정하는 클러스터 안의 주소예요. Service 문서에서는 가상 IP 방식에 쓰이는 주소라고 설명해요. 노드마다 도는 kube-proxy가 이 주소로 가는 트래픽을 Service 뒤의 파드 하나로 보내는 규칙을 노드에 넣어요. 목적지 주소를 바꾸는 이 처리를 DNAT(destination NAT)이라고 해요(2편).

Virtual IPs and Service Proxies 문서에 따르면 kube-proxy는 클러스터의 모든 노드에서 돌고 Service마다 노드를 설정해 ClusterIP와 포트로 가는 트래픽을 Service의 엔드포인트 하나로 보내요. 모드를 따로 정하지 않으면 Kubernetes 1.37의 기본은 iptables 모드예요. 이 클러스터의 kube-proxy 로그에도 "Using iptables Proxier"가 찍혀 있었어요(2편). iptables 모드에서는 엔드포인트별 규칙이 목적지 NAT으로 트래픽을 백엔드에 보내고 기본으로는 백엔드 파드를 무작위로 골라요. 문서에는 클라이언트가 Service의 가상 IP로 연결할 때 이 규칙이 작동해 백엔드를 고르고 클라이언트 IP를 바꾸지 않은 채 패킷을 백엔드로 넘긴다는 설명도 있어요.

3단계의 요청을 이 설명에 맞춰 따라가면 이래요. curl은 마스터 노드에서 10.105.164.156:80으로 연결을 열어요. 마스터 노드의 kube-proxy가 넣어 둔 규칙에 따라 이 연결의 목적지가 파드 IP 하나로 바뀌어요. 그 파드가 다른 노드에 있으니 패킷은 6편에서 본 Calico의 IPIP 터널로 나가고 출발지 주소는 마스터의 tunl0 주소인 10.244.235.192가 돼요. 워커 노드에 도착한 패킷의 목적지는 이미 파드 IP예요. Kubeshark 수집기는 워커 3대에만 있으니(14편) 수집기가 본 것은 10.244.235.192에서 파드 IP로 가는 패킷이에요. 목적지가 ClusterIP였던 구간은 마스터 안에서 끝났고 마스터에는 수집기가 없어요.

📖 용어: tunl0
Calico가 IPIP 모드에서 노드마다 만드는 터널 인터페이스예요. 다른 노드의 파드 대역으로 가는 경로가 이 인터페이스를 지나요(6편). 노드 자신이 다른 노드의 파드에 보낸 패킷은 이 인터페이스의 주소를 출발지로 달고 나가서 받는 쪽에서는 노드 IP가 아니라 파드 대역 안의 주소로 보여요. 이 클러스터에서 마스터의 tunl0 주소는 10.244.235.192예요.
그림 7. 목적지가 파드 IP로 바뀌는 일은 마스터 안에서 끝나고 워커의 수집기는 바뀐 뒤의 패킷만 본다

3단계 지도에 Service가 없었던 것은 수집기가 본 패킷의 목적지가 이미 파드 IP였기 때문이에요. 그러면 Service가 파드에 고르게 나눠 주는지는 지도에서 어떻게 볼까요? 같은 출발지에서 Service 뒤의 파드들로 가는 선끼리 비교하면 돼요. 그림 6의 세 선이 그 비교예요. 출발지가 파드가 아니면 지도에는 이름 대신 주소가 나온다는 것도 함께 기억해 두면 좋아요. 1~3단계의 10.244.235.192는 "마스터 노드에서 온 요청"이라는 뜻이었어요.

숫자를 읽을 때 조심할 것도 하나 있었어요. 200건과 199건은 한 건 차이인데 지도에서는 1.80kB/s와 1.70kB/s로 0.1kB/s만큼 달랐어요. 이번 화면들에서 kB 단위로 나온 숫자(1.80, 1.70, 1.60, 5.20, 1.50, 5.50)는 모두 소수 둘째 자리가 0이었고 B 단위 숫자(527.07, 535.87, 186.44, 155.37)는 둘째 자리까지 나왔어요. kB 단위 숫자는 0.1kB/s 단위로 끊겨 나오는 것으로 보여요. 그렇다면 한 건 차이가 0.1kB/s 차이로 보이기도 하고 수십 건 차이가 같은 숫자로 보이기도 해요. 지도로는 몫이 비슷한지까지만 보고 한두 건 차이는 로그로 확인하는 편이 안전해요.

그림 6에는 파드마다 0.01B/s짜리 가는 파란 선도 하나씩 있어요. 범례의 색으로는 TCP-FLOW예요. 0.01B/s가 무엇을 센 값인지는 문서에서 찾지 못했어요. 그래서 이런 흐름 선은 연결이 있었다는 표시로만 읽었어요.

⚠️ 주의: kube-proxy는 요청이 아니라 연결 단위로 골라요
문서 설명대로라면 백엔드는 클라이언트가 가상 IP로 연결할 때 골라요. 이번 실험은 요청마다 curl을 새로 띄웠으니 586건이 586개의 연결로 나갔고 세 파드가 거의 3분의 1씩 받았어요. 연결 하나로 요청을 계속 보내는 클라이언트(HTTP keep-alive를 쓰는 커넥션 풀 등)라면 같은 Service 뒤에서도 이번과 다르게 나뉠 수 있어요. 이 경우는 이번 실습에서 재현하지 않았어요. 지도에서 파드 하나만 굵은데 Service 설정에 이상이 없다면 클라이언트가 연결을 어떻게 쓰는지도 확인해 보세요.

5. 파드에서 이름으로 부르면 DNS 선이 생기고 새 파드의 선은 가늘게 나온다

마지막 단계는 실제 서비스와 가장 비슷하게 짰어요. 클라이언트 파드 loadgen 안에서 Service 이름으로 http://myweb을 약 0.1초 간격으로 60초 동안 부르고 30초가 지났을 때 myweb을 3개에서 5개로 늘렸어요.

master$ (sleep 30; echo "$(date +%T) scale"; kubectl scale deploy/myweb --replicas=5) & kubectl exec loadgen -- sh -c "end=\$(( \$(date +%s)+60 )); n=0; while [ \$(date +%s) -lt \$end ]; do curl -s -o /dev/null http://myweb; n=\$((n+1)); sleep 0.1; done; echo loadgen: \$n건"; wait; kubectl get po -l app=myweb -o wide | awk "{print \$1,\$3,\$6,\$7}" 21:03:48 scale deployment.apps/myweb scaled loadgen: 574건 NAME STATUS IP NODE myweb-859c4764d4-4tjzk Running 10.244.194.88 k8s-worker1 myweb-859c4764d4-5xtpv Running 10.244.100.213 k8s-worker3 myweb-859c4764d4-k2hfq Running 10.244.126.20 k8s-worker2 myweb-859c4764d4-n9rd8 Running 10.244.126.19 k8s-worker2 myweb-859c4764d4-v87c6 Running 10.244.100.214 k8s-worker3

→ 30초째인 21:03:48에 확장 명령이 들어갔고 loadgen은 60초 동안 574번 요청했으며 새 파드 k2hfq(worker2)와 v87c6(worker3)이 생겼다는 뜻이에요.

로그로 보면 확장 전 30초에는 4tjzk 96건, 5xtpv 98건, n9rd8 81건으로 세 파드가 29~36%씩 받았어요. 확장 뒤 30초에는 4tjzk 61건, 5xtpv 50건, k2hfq 61건, n9rd8 69건, v87c6 58건으로 다섯 파드가 17~23%씩 받았어요. 새 파드 둘도 확장 뒤 30초 동안 다른 파드와 비슷한 건수를 받은 거예요. 출발지는 모두 loadgen의 파드 IP 10.244.194.89였어요. 클라이언트 IP를 바꾸지 않고 넘긴다는 문서 설명과 맞아요.

그림 8. 4단계. 확대된 상태로 찍혀 가장자리가 잘린 화면이다. 처음부터 있던 n9rd8은 1.50kB/s, 새 파드 k2hfq는 186.44B/s였다

4단계 화면은 지도가 확대된 상태로 찍혀서 가장자리의 원과 이름이 잘렸어요. 축소해서 다시 찍으려던 때에는 노드 한도(Node limit: 4/3)를 알리는 로그인 창이 떠서 대시보드를 쓸 수 없었어요(14편). 그래서 이 화면이 4단계의 유일한 캡처예요. 화면에서 읽을 수 있는 것만 적으면 이래요.

· 가운데 원이 loadgen이에요. 출발지가 파드라서 이번에는 주소가 아니라 이름으로 나왔어요.
· 이름이 보이는 myweb 파드는 둘이에요. 처음부터 있던 n9rd8로 가는 선이 1.50kB/s, 확장으로 생긴 k2hfq로 가는 선이 186.44B/s예요.
· 155.37B/s 선과 1.70kB/s 선은 반대쪽 원의 이름이 화면 밖으로 잘렸어요.
· 왼쪽 아래로 5.50kB/s 선이 하나 더 나가요. 반대쪽 끝이 화면 밖이라 무엇과 이어진 선인지 확인하지 못했어요.
· 왼쪽의 보라색 원 두 개와 loadgen 사이에 주황색 선이 생겼어요. 원의 이름은 잘려서 끝부분만 보이는데 이 클러스터의 CoreDNS 파드 이름(coredns-559f6c778d-sqvxb, coredns-559f6c778d-bt7zz)과 끝부분이 같아요. 범례에서 보라색은 kube-system이고 주황색은 UDP-FLOW예요.
· 1~3단계와 비교하면 범례에 DNS와 UDP-FLOW가 새로 생겼고 internal은 없어졌어요. 위쪽 띠의 수집 대상은 1~3단계의 20 pods에서 22 pods로 늘었어요. Kubeshark가 새 파드 둘을 수집 대상에 넣었다는 뜻이에요.

CoreDNS로 가는 주황색 선부터 볼게요. 1~3단계에서는 IP 주소로 요청했기 때문에 이름을 물어볼 일이 없었어요. 4단계에서는 myweb이라는 이름을 주소로 바꿔야 해서 loadgen이 먼저 클러스터의 DNS 서버인 CoreDNS에 물어요. KFL 식의 뒤 절반(src.pod.name == "loadgen")이 loadgen이 보낸 것을 모두 남기니 이 질의도 지도에 나타났어요.

📖 용어: 파드의 DNS 검색 목록 (search)
kubelet이 파드마다 만들어 주는 /etc/resolv.conf에는 search 줄이 있어요. DNS for Services and Pods 문서의 예시는 search <namespace>.svc.cluster.local svc.cluster.local cluster.local이고 data라고만 물어도 이 목록을 붙여 data.test.svc.cluster.local로 넓혀 물을 수 있다고 해요. 네임스페이스를 적지 않은 질의는 파드 자신의 네임스페이스 안에서 찾아요.

같은 문서에 따르면 일반 Service의 이름은 Service의 ClusterIP로 풀려요. 그러니 loadgen의 요청은 CoreDNS에 myweb의 주소를 물어 ClusterIP를 받고 그 주소로 연결하는 순서로 진행돼요. 연결부터는 3단계와 같아요. 다만 이번에는 loadgen이 있는 worker1의 kube-proxy 규칙에 따라 목적지가 파드 IP로 바뀌어요. 주황색 선의 숫자는 0.03B/s로 HTTP 선과 견줄 수 없을 만큼 작았어요. 3단계의 TCP-FLOW 선과 마찬가지로 이 숫자가 무엇을 센 값인지는 확인하지 못했어요. 지도에서 CoreDNS로 가는 선이 보이면 그 파드가 이름을 주소로 바꾸는 질의를 보냈다는 표시로 읽으면 돼요.

이제 새 파드의 선이에요. 로그로는 확장 뒤 30초 동안 k2hfq가 61건, n9rd8이 69건을 받아 거의 같았어요. 그런데 지도에서 k2hfq로 가는 선은 186.44B/s로 n9rd8로 가는 1.50kB/s보다 훨씬 가늘었어요. 이유는 그림 8 오른쪽 위의 안내문에서 찾을 수 있어요. "average sizes per second since 9:03:17 PM", 즉 9시 3분 17초부터의 초당 평균이에요.

since 시각은 네 단계 모두 요청을 시작하기 1초 전이었어요(20:59:08, 21:00:31, 21:01:54, 21:03:17). 단계마다 페이지를 새로 열고 필터를 건 시각이에요. 4단계 화면은 그로부터 70초 뒤인 9:04:27에 찍었어요. 그 70초 가운데 n9rd8은 요청이 시작된 21:03:18부터 끝난 21:04:18 무렵까지 약 60초 동안 요청을 받았고 k2hfq는 확장된 21:03:48 뒤로 약 30초만 받았어요. 70초 전체로 나눈 평균이라면 k2hfq의 선이 가늘게 나올 수밖에 없어요.

그림 9. 확장 뒤에는 고르게 나눠 받았지만 since 시각부터의 평균으로 그린 지도에서는 새 파드의 선이 가늘었다

서비스맵의 숫자는 지금 트래픽이 어떻게 나뉘는지가 아니라 since 시각부터 쌓인 양의 평균이에요. 3장에서 같은 시간이 지난 화면끼리 비교한 것도 이 때문이에요.

다만 평균으로 숫자까지 다 설명되지는 않았어요. 70초 동안 받은 건수로 따지면 n9rd8은 150건(81건 + 69건), k2hfq는 61건이니 k2hfq의 선은 n9rd8 선의 41% 정도여야 해요. 지도에서는 186.44B/s ÷ 1.50kB/s로 12% 안팎이었어요. 3장에서는 같은 계산이 소수 넷째 자리까지 맞았는데 4단계에서는 세 배 넘게 어긋났어요. 이 차이가 어디서 생겼는지는 확인하지 못했어요. 그래서 4단계 지도에서는 "새 파드의 선이 가늘다"는 방향까지만 읽었어요.

⚠️ 주의: 스케일아웃 직후의 지도로 새 파드를 판단하지 마세요
확장 직후 새 파드의 선이 가늘다고 해서 새 파드가 요청을 못 받는다고 볼 수는 없어요. 이번 실험의 새 파드 둘은 확장 뒤 30초 동안 61건, 58건을 받았는데 지도에서는 가늘게 나왔어요. 지금의 분포를 보고 싶다면 보고 싶은 구간이 시작될 때 페이지를 새로 열어 since 시각을 맞추세요. 반대로 오래 열어 둔 페이지라면 한참 전에 몰렸던 트래픽이 아직 평균에 섞여 있을 수 있어요. 판단이 걸린 숫자는 파드별 요청 수를 로그나 메트릭으로 한 번 더 확인하세요.

6. 서비스맵을 읽을 때 확인할 다섯 가지

네 단계를 한 표로 모으면 이래요.

단계 지도 (since 시각부터의 초당 평균) nginx 로그 (건) 1 균등 527.07 / 527.07 / 527.07 B/s 60 / 60 / 60 2 쏠림 5.20k / 535.87 / 535.87 B/s (9.7배) 593 / 61 / 61 (9.7배) 3 Service 1.80k / 1.70k / 1.60k B/s (35·33·31%) 200 / 199 / 187 (34·34·32%) 4 확장 n9rd8 1.50k / k2hfq 186.44 B/s (약 12%) n9rd8 150 / k2hfq 61 (41%) # 1~3단계 파드 순서: 4tjzk / 5xtpv / n9rd8. 4단계는 이름이 보인 두 파드만 적었다

→ 1~3단계는 지도의 비율이 로그의 비율과 맞았고 4단계는 "새 파드가 적게 받았다"는 방향만 맞았다는 뜻이에요.

하나, 필터부터 걸어요. 필터 없는 지도에서는 시스템 파드의 선 때문에 내 앱의 흐름을 찾기 어려워요. 받는 쪽을 보려면 dst.pod.name, 보내는 쪽을 보려면 src.pod.name으로 거르세요. KFL은 화면만 바꾸고 수집량은 그대로라는 점도 함께 기억해 두세요.

둘, 숫자는 since 시각부터의 평균 바이트예요. 지금의 초당 요청 수가 아니에요. since 시각에서 같은 시간이 지난 화면끼리만 숫자를 비교하고 보고 싶은 구간이 바뀌면 페이지를 새로 여세요. 응답 크기가 요청마다 다르면 바이트의 비율과 요청 수의 비율이 달라져요.

셋, 이번 실험에서 Service는 원으로 나오지 않았어요. ClusterIP로 보낸 요청도 지도에서는 출발지에서 파드로 바로 이어졌어요. Service의 분산은 같은 출발지에서 파드들로 가는 선끼리 비교해서 읽어요. 출발지가 파드가 아니면 이름 대신 주소가 나오고 노드에서 보낸 요청은 tunl0 주소로 보일 수 있어요.

넷, 이름으로 부르면 DNS 선이 같이 생겨요. 파드 안에서 Service 이름으로 부르는 앱의 지도에는 CoreDNS로 가는 선도 함께 그려져요. 이 선의 숫자는 HTTP 선과 같은 기준으로 비교하기 어려웠어요.

다섯, 지도에 없는 것과 읽지 못한 것을 따로 적어 두세요. 수집기가 없는 마스터 안에서 일어난 일(ClusterIP가 파드 IP로 바뀌는 과정)은 지도에 나오지 않아요. 이번 4단계의 5.50kB/s 선은 정체를 확인하지 못했고 새 파드 선의 숫자도 로그와 맞지 않았어요. 이런 것은 해석하지 말고 로그나 메트릭으로 다시 확인할 거리로 남겨 두는 편이 안전해요.

지도로는 쏠림이 의심되는 곳을 찾고 몇 건이 어디로 갔는지는 지도와 따로 센 숫자로 확인해요.

✍️ 오늘의 요약
서비스맵의 숫자는 지금의 분포가 아니라 since 시각부터 쌓인 바이트의 평균이에요. 같은 시간이 지난 화면끼리 비교하면 요청 비율과 맞았어요.

nginx 파드 3개에 네 가지 트래픽을 60초씩 보내고 지도를 접근 로그와 맞춰 봤어요. 균등하게 보낸 1단계는 세 선이 모두 527.07B/s였고 로그도 60건씩이었어요. 쏠리게 보낸 2단계는 지도와 로그가 똑같이 9.7배였어요. ClusterIP로 보낸 3단계에서는 Service가 지도에 나오지 않았어요. 목적지가 마스터 안에서 파드 IP로 바뀌고 수집기는 워커에만 있기 때문이에요. 파드에서 이름으로 부르고 중간에 파드를 늘린 4단계에서는 CoreDNS로 가는 선이 생겼고 새 파드는 로그로는 고르게 받았는데 지도에서는 가늘었어요. 서비스맵은 쏠림이 의심되는 곳을 빠르게 찾는 데 쓰고 몇 건이 어디로 갔는지는 지도와 따로 센 숫자로 확인해야 해요.
