worker1의 Node 객체를 열어 보면 노드의 파드용 대역인 podCIDR이 10.244.2.0/24로 적혀 있어요. 그런데 같은 노드에 떠 있는 myweb 파드의 IP는 10.244.194.100과 10.244.194.101이에요. 10.244.2.x와는 한참 떨어진 주소예요. 나머지 세 노드도 마찬가지였어요. 노드에 적힌 대역과 실제 파드 IP가 맞는 노드가 하나도 없었어요.

그림 1. 노드의 podCIDR과 Calico 블록이 네 노드 모두 달랐고 파드 IP는 Calico 블록 쪽에 있었다

쿠버네티스 아키텍처를 공부하던 날 제가 남긴 메모 중에 "IPAM 이런 것도 중요한 듯"이 있어요. 그래서 노드에 적힌 대역과 Calico가 실제로 나눈 블록을 나란히 놓고 비교했고 노드 하나의 블록은 일부러 가득 채워 봤어요. 30편에서 Felix가 노드 간 경로를 "IPAM 블록"으로 계산한다고 했어요. 이번 글에서는 Calico IPAM(IP 주소 관리)이 IP 풀을 잘라 노드마다 붙여 두는 이 블록을 자세히 봐요. 블록에서 IP가 할당되고 반납되는 흐름은 34편에서 따로 다뤄요. 클러스터는 Lima VM 4대에 kubeadm v1.37.2, containerd 2.4.1, Calico v3.33.0(매니페스트 설치)을 올린 실습 환경이에요.

이 글에서 다룰 것
· kubectl get node에 보이는 podCIDR은 누가 정할까?
· 실제 파드 IP는 어디에서 나오고 왜 podCIDR과 다를까?
· 노드의 /26 블록 64칸이 다 차면 어떻게 될까?
· IP 풀 크기는 무엇을 기준으로 정할까?

1. 노드의 podCIDR은 컨트롤러 매니저가 /24로 나눠 적어 둔 값이다

노드의 podCIDR을 적는 쪽은 쿠버네티스의 컨트롤러 매니저예요. 이 클러스터의 kube-controller-manager 매니페스트에는 두 플래그가 들어 있어요.

master$ sudo grep -E -- '--(allocate-node-cidrs|cluster-cidr|node-cidr-mask-size)' /etc/kubernetes/manifests/kube-controller-manager.yaml - --allocate-node-cidrs=true - --cluster-cidr=10.244.0.0/16

→ 컨트롤러 매니저가 10.244.0.0/16을 잘라 노드마다 파드용 대역을 나눠 준다는 뜻이에요. 대역 크기를 정하는 --node-cidr-mask-size는 적혀 있지 않아요.

kube-controller-manager 레퍼런스를 보면 --allocate-node-cidrs는 노드에 파드용 CIDR을 할당할지 정하는 플래그이고 이 플래그를 쓰려면 --cluster-cidr가 함께 있어야 해요. --node-cidr-mask-size의 기본값은 IPv4에서 24예요. 이 일은 컨트롤러 매니저 안의 node-ipam-controller가 맡아요. 그래서 노드마다 /24를 하나씩 받았고(master는 10.244.0.0/24, worker1은 10.244.2.0/24) 그 값이 Node 객체의 spec.podCIDR에 적혔어요. Calico IPAM 문서에도 kubeadm에 파드 대역(--pod-network-cidr)을 주면 kubeadm이 이 노드 CIDR 할당을 자동으로 켠다고 적혀 있어요. 5편에서 kubeadm 설정에 넣은 podSubnet이 이 --pod-network-cidr에 해당하는 값이에요. kubectl get node에 보이는 podCIDR은 컨트롤러 매니저가 이렇게 나눠 적어 둔 값이에요.

📖 용어: podCIDR (node.spec.podCIDR)
Node 객체에 적히는 "이 노드의 파드가 쓸 주소 대역"이에요. kube-controller-manager의 node-ipam-controller가 --cluster-cidr를 잘라 노드마다 하나씩 적어요. 컨트롤러는 적어 두기만 하고 실제로 이 대역에서 파드 IP를 꺼내 쓸지는 노드의 CNI 설정이 정해요. kubectl get node <이름> -o jsonpath='{.spec.podCIDR}'로 볼 수 있어요.

2. 실제 파드 IP는 CNI 설정이 고른 Calico IPAM의 /26 블록에서 나온다

실제 파드 IP를 정하는 쪽은 노드의 CNI 설정이 고른 IPAM 플러그인이에요. worker1의 /etc/cni/net.d/10-calico.conflist를 요약하면 이래요.

name= k8s-pod-network | plugin type= calico | ipam type= calico-ipam | datastore= kubernetes | 그다음 plugin= portmap CNI 바이너리: calico calico-ipam

→ 파드 네트워크를 붙이는 플러그인은 calico이고 IP를 고르는 IPAM은 calico-ipam이며 기록은 쿠버네티스 API에 남긴다는 뜻이에요. 그 뒤의 portmap은 hostPort를 처리하는 플러그인이에요(쿠버네티스 네트워크 플러그인 문서).

calico-ipam은 Calico의 IP 풀(10.244.0.0/16)을 /26 블록으로 잘라 노드에 붙이고(6편) 그 블록에서 IP를 꺼내요. 블록을 노드에 붙인 이 연결을 affinity라고 하고 Calico는 BlockAffinity라는 리소스로 기록해요. Calico IPAM 문서에는 이렇게 적혀 있어요. "Calico IPAM은 쿠버네티스의 노드 CIDR 할당(Node.spec.podCIDR)을 쓰지 않으니 kube-controller-manager에 --allocate-node-cidrs=false를 줄 수 있다. 그러면 쓰지 않는 노드 CIDR을 할당하지 않고 노드의 CIDRNotAvailable 이벤트도 피할 수 있다." Calico에서 podCIDR을 실제로 쓰는 것은 host-local IPAM이에요.

📖 용어: host-local IPAM
노드마다 미리 정해 둔 대역 안에서 IP를 고르고 할당 기록을 그 노드의 파일에 남기는 단순한 IPAM 플러그인이에요. Calico CNI 설정 문서에 따르면 subnet에 usePodCidr를 적으면 쿠버네티스 API의 Node.podCIDR에서 대역을 가져와요. 문서에는 host-local을 쿠버네티스 route controller와 연동해야 하는 클러스터에서 주로 쓴다고 나와 있어요.
그림 2. 컨트롤러 매니저가 나눈 /24는 Node 객체에 적히기만 하고 실제 파드 IP는 Calico IPAM의 /26 블록에서 나온다

이 클러스터에서 파드 IP를 실제로 정하는 것은 Calico IPAM이고 node.spec.podCIDR은 파드 IP와 상관없는 값이에요. node-ipam-controller와 Calico IPAM이 같은 10.244.0.0/16을 서로 모른 채 따로 나누니 노드마다 결과가 달라요.

⚠️ 주의: Calico IPAM을 쓴다면 kubectl get node의 podCIDR을 믿지 마세요
• 먼저 노드의 CNI 설정에서 "ipam": {"type": ...}를 봐요. calico-ipam이면 podCIDR은 파드 IP와 상관이 없어요. Calico 문서도 같은 방법(10-calico.conflist의 ipam 항목)으로 Calico IPAM인지 확인하라고 안내해요
• 노드에 실제로 붙은 대역은 calicoctl ipam show --show-blocks나 kubectl get blockaffinities.crd.projectcalico.org로 봐요
• 방화벽이나 모니터링에서 "이 노드의 파드 대역"을 podCIDR로 적어 두면 실제 파드 IP와 어긋나요

파드가 뜰 때 이 블록에서 IP를 꺼내는 과정을 짧게 정리하면 이래요. kubelet이 containerd에 RunPodSandbox를 보내면 containerd가 CNI 플러그인 calico를 ADD 명령으로 실행하고 calico는 IP 고르기를 calico-ipam에 맡겨요. calico-ipam은 그 노드 블록의 빈칸 하나를 골라 기록하고 calico가 노드 쪽 veth(cali…)와 /32 경로를 만들어요. worker1에서 잰 이 과정은 RunPodSandbox 123ms 안에 끝났고 앱 컨테이너를 만들기 전이었어요. 로그로 본 자세한 순서와 파드를 지울 때 IP가 반납되는 과정, 노드가 죽으면 IP가 남는 이유는 34편에서 이어 가요.

3. 블록 64칸이 차면 노드가 블록을 하나 더 받는다

blockSize가 26이니 블록 하나는 64칸이에요. worker2의 블록 10.244.126.0/26은 64칸 중 6칸을 쓰고 있었어요. 여기에 worker2로 고정한 pause 파드 62개를 한 번에 만들었어요. 빈칸 58개보다 많은 수예요.

📖 용어: IP 풀(IPPool)과 blockSize
Calico가 파드 IP를 꺼내 쓰는 주소 범위를 정한 리소스가 IPPool이에요. 이 클러스터에는 default-ipv4-ippool(10.244.0.0/16) 하나가 있고 blockSize 26은 그 풀을 64칸(/26)짜리 블록으로 잘라 노드에 붙인다는 뜻이에요. IPPool 문서에 따르면 IPv4의 기본값이 26이고 이 값은 풀을 만들 때만 정할 수 있어요.
그림 3. 첫 블록이 64/64로 차자 두 번째 블록이 붙었고 다른 노드의 라우팅 표에도 한 줄이 늘었다

12초 뒤(15:29:49) 62개가 모두 Ready 상태가 됐고 worker2에는 두 번째 블록 10.244.126.64/26이 붙어 있었어요. 첫 블록은 64/64(100%), 두 번째 블록은 4/64였어요. 원래 쓰던 6칸에 새 파드 62개를 더한 68이 64 + 4로 나뉜 거예요. 파드 IP를 세어 보면 62개 모두 10.244.126.x였어요.

다른 노드에서도 변화가 보였어요. worker1의 라우팅 표에서 worker2(192.168.104.4)로 가는 줄이 10.244.126.0/26과 10.244.126.64/26 두 줄로 늘었어요. 블록이 하나 늘면 다른 노드의 라우팅 표에도 경로가 한 줄 늘어요. 30편에서 본 대로 이 경로도 Felix가 IPAM 블록을 보고 넣은 proto 80 경로예요.

Calico IPAM 문서에서는 이 동작을 이렇게 설명해요. Calico는 기본적으로 노드에 붙은 블록 안에서 IP를 주고 필요하면 블록을 새로 만들어요. 블록은 같은 노드의 파드 주소를 하나로 묶어 라우팅 표의 크기를 줄이려고 써요. 노드와 파드 수가 늘고 줄면 블록도 자동으로 만들어지고 없어져요. 노드에 붙은 블록 밖에서 주소를 줄 수도 있는데 IPAMConfiguration의 strictAffinity가 true면 이렇게 다른 노드의 블록에서 빌려 오는 것을 막아요(기본값 false).

이 파드 62개를 지울 때는 파드 객체가 먼저 사라졌고 IP는 약 14초 뒤에 돌아왔어요. 비어 버린 두 번째 블록은 15분 넘게 worker2에 붙어 있다가 반납됐어요. 왜 이런 순서로 일어나는지는 34편에서 봐요.

4. IP 풀 크기는 노드 수와 노드당 파드 수로 정한다

여기까지 보면 IP 풀의 크기를 정할 때 세어야 할 것은 IP 수가 아니라 블록 수라는 점을 알 수 있어요. 이 클러스터의 풀은 10.244.0.0/16(65,536개)이고 blockSize는 26(64개)이라서 블록이 1,024개 나와요. 노드는 블록을 하나 이상 가져야 하고 블록이 차면 하나를 더 받아요.

노드당 파드 수의 상한은 kubelet이 정해요. kubelet 설정 레퍼런스의 maxPods 기본값은 110이고 이 클러스터의 노드 네 대도 capacity.pods가 모두 110이었어요. worker2의 kubelet 설정 파일에는 maxPods 줄이 없었어요. 노드 하나가 꽉 차면 파드 110개에 노드 터널 IP 하나를 더한 111개가 필요해요. /26 블록으로 치면 2개예요. 계산을 정리하면 이래요.

📖 용어: maxPods
kubelet이 한 노드에서 함께 돌릴 수 있는 파드 수의 상한이에요. kubelet 설정 파일의 maxPods로 정하고 정하지 않으면 기본값 110을 써요. 이 클러스터에서는 노드 네 대 모두 Node 객체의 capacity.pods와 allocatable.pods가 110이었어요.
필요한 블록 수 ≈ 노드 수 × ⌈(maxPods + 노드 터널 IP 1) ÷ 블록 크기⌉ 이 클러스터: ⌈(110 + 1) ÷ 64⌉ = 2 블록/노드 풀 10.244.0.0/16 ÷ /26 = 1,024 블록 → 모든 노드가 꽉 찬다면 1,024 ÷ 2 = 512대까지

→ 노드가 모두 maxPods까지 찬다고 가정하면 이 풀로는 노드 512대까지 감당할 수 있다는 뜻이에요. 블록은 필요할 때만 붙으니 실제로는 더 여유가 있지만 상한을 잡을 때는 이 계산이 안전해요.

그림 4. /16 풀은 /26 블록 1,024개이고 꽉 찬 노드는 블록 2개를 쓰니 모든 노드가 꽉 찬다면 512대가 상한이다

blockSize를 바꾸면 이 계산이 달라져요. 블록을 작게 하면(예: /28, 16칸) 파드가 적은 노드가 블록을 덜 낭비하지만 블록 수가 늘어나 3절에서 본 대로 다른 노드의 라우팅 표에 줄이 늘어요. 블록을 크게 하면 반대예요. IPPool 문서에 따르면 blockSize는 IPv4에서 20~32 사이 값을 쓰고 풀을 만들 때만 정할 수 있어요. 블록 크기 변경 문서에는 설치 뒤에 바꾸려면 임시 풀을 만들고 기존 풀을 끄고 파드를 다시 띄우는 순서를 밟아야 하니 설치 전에 정하는 것이 가장 좋다고 나와 있어요. 파드 대역 자체를 설치 뒤에 바꿔도 효과가 없다는 점은 6편에서 봤어요.

💡 실무에서는: IP 풀은 설치 전에 이렇게 정해요
• 노드 수 상한 × ⌈(maxPods + 1) ÷ 블록 크기⌉가 풀의 블록 수(풀 크기 ÷ 블록 크기)를 넘지 않게 잡아요. /16 풀에 /26 블록이면 블록은 1,024개예요
• 노드당 파드가 적다면 블록을 작게(숫자를 크게) 해서 낭비를 줄일지 아니면 경로 수가 늘지 않게 기본 /26을 그대로 둘지 정해요. 풀을 만든 뒤에는 바꾸기 번거로워요
• kubeadm의 podSubnet, Calico IPPool, 노드 네트워크가 서로 겹치지 않는지 봐요(6편)
• Calico IPAM을 쓴다면 Calico 문서대로 kube-controller-manager에 --allocate-node-cidrs=false를 줄지 검토해요. 쓰지 않는 podCIDR을 나누지 않고 CIDRNotAvailable 이벤트도 피할 수 있어요
✍️ 오늘의 요약
Calico IPAM을 쓰는 클러스터에서 노드의 podCIDR은 컨트롤러 매니저가 적어 두기만 한 값이고 실제 파드 IP는 Calico의 /26 블록에서 나와요.

kube-controller-manager의 node-ipam-controller는 --cluster-cidr를 /24로 잘라 Node 객체에 적었지만 CNI 설정의 ipam.type이 calico-ipam이라서 그 값은 파드 IP와 상관이 없었어요. 실제 파드 IP는 Calico가 IP 풀을 /26 블록으로 잘라 노드에 붙여 둔 블록의 빈칸에서 나왔어요. 블록 64칸이 차자 노드는 12초 안에 블록을 하나 더 받았고 다른 노드의 라우팅 표에도 한 줄이 늘었어요. 그래서 IP 풀 크기는 IP 수가 아니라 노드마다 필요한 블록 수로 세요. 이 클러스터의 /16 풀은 /26 블록 1,024개이고 maxPods 110인 노드가 꽉 차면 블록이 2개 필요하니 노드 512대가 상한이에요. blockSize는 풀을 만들 때만 정할 수 있으니 설치 전에 정하고 노드의 실제 파드 대역은 podCIDR이 아니라 calicoctl ipam show --show-blocks로 봐요.
