이벤트는 더 많이 달랐어요. sc-normal에는 default-scheduler가 남긴 Scheduled 이벤트가 있었는데 똑같이 Running인 sc-nodename에는 Scheduled 없이 kubelet 이벤트만 있었어요. sc-other-scheduler에는 이벤트가 하나도 없었어요. 그 10초 동안 API 서버가 받은 바인딩 요청(POST pods/binding)은 19에서 20으로 하나 늘었어요. 세 파드 가운데 스케줄러를 거친 것은 sc-normal 하나뿐이었다는 뜻이에요.

스케줄러를 소개하는 글에서는 "스케줄러는 API 서버에서 파드 생성 이벤트를 받아 노드 정보를 요청하고 알맞은 노드를 고른 뒤 바인딩 사이클에서 그 결정을 클러스터에 적용해 etcd에 기록한다" 같은 설명을 자주 봐요. 틀린 말은 아니지만 위 장면을 설명하기에는 모자라요. 생성 이벤트를 받았을 텐데 두 파드는 왜 그냥 지나쳤는지, 바인딩이 "적용"하는 것이 정확히 무엇인지, 노드 정보를 정말 파드마다 묻는지가 이 문장에는 없어요. 23편에서는 필터와 스코어로 노드를 고르는 방법을 봤고 20편에서는 스케줄러를 멈춰 봤어요. 이번 글에서는 그 앞과 뒤, 곧 스케줄러가 파드를 집어 가는 조건과 고른 결과를 쓰는 방법을 실험 기록과 v1.37.2 소스로 따라가요. 클러스터는 Lima VM 4대에 kubeadm v1.37.2를 올린 실습 환경이에요.

1. 새 파드를 고를 때는 nodeName과 schedulerName을 본다

그림 1. 세 파드 중 Scheduled 이벤트가 남은 것은 sc-normal 하나였고 바인딩 요청도 하나만 늘었다

세 파드가 갈린 이유는 스케줄러가 파드 이벤트를 받는 자리에 그대로 적혀 있어요. v1.37.2 소스의 eventhandlers.go에서 파드가 새로 보일 때 불리는 addPod를 옮기면 이래요.

func (sched *Scheduler) addPod(obj interface{}) { ... if responsibleForPod(pod, sched.Profiles) && (!assignedPod(pod) || isPodDeferred) { sched.addPodToSchedulingQueue(pod) } if assignedPod(pod) { sched.addAssignedPodToCache(pod) } } // assignedPod selects pods that are assigned (scheduled and running). func assignedPod(pod *v1.Pod) bool { return len(pod.Spec.NodeName) != 0 } // responsibleForPod returns true if the pod has asked to be scheduled by the given scheduler. func responsibleForPod(pod *v1.Pod, profiles profile.Map) bool { return profiles.HandlesSchedulerName(pod.Spec.SchedulerName) }

→ 새로 배치할 일반 파드는 nodeName이 비어 있고 schedulerName이 이 스케줄러의 프로파일 이름과 같을 때 큐에 넣는다는 뜻이에요. 이미 배정된 파드는 캐시에 넣어 그 노드의 자원이 얼마나 찼는지 계산해요. 다만 관련 기능 게이트가 켜져 있고 실행 중 자원 조정이 보류된 파드는 isPodDeferred가 참이라 큐에도 넣을 수 있어요. 이번 세 파드는 이 예외에 해당하지 않아요.

📖 용어: schedulerName과 스케줄러 프로파일
파드의 spec.schedulerName은 "어느 스케줄러가 나를 맡을지"를 적는 칸이에요. kube-scheduler 하나는 프로파일을 여러 개 둘 수 있고 프로파일마다 이름과 플러그인 구성이 따로 있어요. Scheduler Configuration 문서에 따르면 기본으로 만들어지는 프로파일 이름이 default-scheduler예요. 같은 문서에는 "If a Pod doesn't specify a scheduler name, kube-apiserver will set it to default-scheduler."라는 문장도 있어요. 파드가 이 칸을 비워 두면 API 서버가 저장할 때 default-scheduler로 채운다는 뜻이에요.

세 파드에 대 보면 이래요.

· sc-normal은 schedulerName을 비워 뒀으니 API 서버가 default-scheduler로 채웠고 nodeName도 비어 있었어요. 조건 둘을 다 맞춰 큐에 들어갔고 worker3을 받았어요.
· sc-other-scheduler는 nodeName이 비어 있지만 schedulerName이 my-scheduler예요. 우리 클러스터에는 그 이름의 프로파일이 없으니 큐에도 캐시에도 들어가지 않았어요. 이벤트를 남길 쪽이 없어서 이벤트도 0건이었어요. 20편에서 스케줄러를 멈췄을 때와 같은 모습이에요.
· sc-nodename은 만들 때부터 nodeName이 차 있었어요. 스케줄러는 이 파드를 "이미 배정된 파드"로 캐시에만 넣었고 worker1의 kubelet은 자기 노드 이름이 적힌 파드를 보고 바로 컨테이너를 띄웠어요. Assigning Pods to Nodes 문서도 "If the nodeName field is not empty, the scheduler ignores the Pod and the kubelet on the named node tries to place the Pod on that node."라고 적어요. 스케줄러는 이 파드를 고르지 않고 지정된 노드의 kubelet이 그 노드에 올리려 한다는 뜻이에요.

그러니 "스케줄러가 파드 생성 이벤트를 받는다"를 정확히 말하면 이래요. 스케줄러는 모든 파드와 노드의 변화를 watch로 받고 새로 배치할 일반 파드 중에서는 nodeName이 비어 있고 schedulerName이 자기 프로파일과 같은 파드를 큐에 넣어요. 반응하는 계기도 파드 생성만이 아니에요. 같은 파일의 노드 핸들러는 노드가 바뀌면 캐시를 고치고 스케줄링에 관련된 변화가 있으면 기다리던 파드를 다시 꺼내요. 그 장면은 5절에서 봐요.

⚠️ 주의: nodeName을 직접 적으면 스케줄러의 검사도 건너뛰어요
• nodeName을 적은 파드는 taint, requests, nodeSelector를 보는 필터를 거치지 않아요. 같은 문서에는 지정한 노드에 자원이 모자라면 파드가 OutOfmemory나 OutOfcpu 같은 이유로 실패한다고 적혀 있어요
• 문서의 경고는 nodeName이 커스텀 스케줄러나 스케줄러를 일부러 건너뛰어야 하는 경우를 위한 칸이라는 거예요. 특정 노드로 보내고 싶을 때는 nodeSelector나 node affinity를 써요
• 마스터의 정적 파드(API 서버, etcd, 스케줄러 자신)도 스케줄러를 거치지 않아요. kubelet이 매니페스트 파일을 읽을 때 자기 노드 이름을 nodeName에 채워 넣어요(v1.37.2 kubelet/config/common.go의 applyDefaults). 마스터에 일반 파드를 올리는 이야기는 37편에서 해요

2. 바인딩은 POST pods/이름/binding 한 번이고 nodeName은 API 서버가 적는다

스케줄러가 노드를 골랐다면 그 결과를 어디에 어떻게 남길까요? 먼저 스케줄러가 쓸 수 있는 것이 무엇인지부터 봤어요.

그림 2. 스케줄러의 권한에는 파드를 만들거나 컨테이너를 띄우는 규칙이 없고 binding 생성이 있다

스케줄러는 마스터의 정적 파드로 뜨고 /etc/kubernetes/scheduler.conf에 든 인증서로 API 서버에 붙어요. --bind-address=127.0.0.1은 스케줄러가 여는 포트(메트릭과 상태 확인용)를 마스터 안에서만 열라는 뜻이에요. 연결 방향과 포트는 35편에서, 리더 선출 Lease는 21편과 24편에서 봤어요.

ClusterRole system:kube-scheduler에서 파드와 관련된 규칙만 골라 보면 할 수 있는 일이 좁아요. 노드는 읽기만 하고 파드는 읽기와 지우기만 해요. 파드 쪽 쓰기는 pods/binding을 만드는 것과 pods/status를 고치는 것이 중심이에요. 목록 끝의 pods/finalizers update는 DRA(동적 자원 할당)가 켜져 있을 때 붙는 규칙이에요(v1.37.2 bootstrappolicy/policy.go). 파드를 만들 권한도 컨테이너를 띄울 권한도 없어요. binding 말고 pods/status 수정과 파드 삭제가 어디에 쓰이는지는 v1.37.2 소스에서 찾았어요.

· pods/status patch: 노드를 찾지 못하면 FailedScheduling 이벤트를 남기고 파드의 PodScheduled 조건을 False로 고쳐요(schedule_one.go의 실패 처리 부분).
· pods delete: 선점(preemption) 때 쓰여요. 우선순위가 높은 파드의 자리를 만들려고 희생 파드에 DisruptionTarget 조건을 적은 뒤 그 파드를 지워요(preemption/executor.go).

결과를 남기는 일은 기본 바인드 플러그인 DefaultBinder가 해요. default_binder.go에서 API 서버로 보내는 본문을 만드는 부분은 이래요.

binding := &v1.Binding{ ObjectMeta: metav1.ObjectMeta{Namespace: p.Namespace, Name: p.Name, UID: p.UID}, Target: v1.ObjectReference{Kind: "Node", Name: nodeName}, }

→ "이 네임스페이스의 이 이름과 UID를 가진 파드를 이 노드에" 두 가지만 담은 Binding 객체를 만든다는 뜻이에요. 파드 전체를 고쳐 보내지 않아요. core/v1의 types.go는 Binding을 "Binding ties one object to another; for example, a pod is bound to a node by a scheduler."라고 설명해요. 한 객체를 다른 객체에 묶는 요청이고 대표 예가 스케줄러가 파드를 노드에 묶는 일이라는 뜻이에요.

📖 용어: binding 서브리소스
파드 주소 뒤에 /binding을 붙인 API(POST /api/v1/namespaces/<ns>/pods/<이름>/binding)예요. 본문으로 Binding 객체를 받아 그 파드에 노드를 배정해요. API 서버의 BindingREST.Create는 파드를 고친 뒤 성공 상태(Status Success)만 돌려줘요. Binding이 따로 저장되는 객체로 남지는 않아요.

요청을 받은 API 서버 쪽은 pkg/registry/core/pod/storage/storage.go의 setPodNodeAndMetadata예요. 파드를 저장소에서 꺼내 고치고 다시 쓰는 GuaranteedUpdate 하나 안에서 이런 일을 해요.

if pod.DeletionTimestamp != nil { return nil, fmt.Errorf("pod %s is being deleted, cannot be assigned to a host", pod.Name) } if pod.Spec.NodeName != "" { return nil, fmt.Errorf("pod %v is already assigned to node %q", pod.Name, pod.Spec.NodeName) } // Reject binding to a scheduling un-ready Pod. if len(pod.Spec.SchedulingGates) != 0 { return nil, fmt.Errorf("pod %v has non-empty .spec.schedulingGates", pod.Name) } pod.Spec.NodeName = machine ... podutil.UpdatePodCondition(&pod.Status, &api.PodCondition{ Type: api.PodScheduled, Status: api.ConditionTrue, })

→ 지우는 중인 파드, 이미 노드가 있는 파드, 스케줄링 게이트가 남은 파드는 거절하고 그렇지 않으면 nodeName에 노드 이름을 넣고 PodScheduled 조건을 True로 만든 뒤 한 번에 저장한다는 뜻이에요. 위 세 가지로 거절하면 assignPod가 그 에러를 409 Conflict로 감싸 돌려줘요.

📖 용어: PodScheduled 조건
파드 status.conditions에 들어가는 항목 가운데 하나예요. 파드 수명 주기 문서는 "PodScheduled: the Pod has been scheduled to a node."라고 설명해요. 스케줄이 끝나면 True가 되고 스케줄러가 자리를 찾지 못하면 False와 그 이유(Unschedulable 등)가 적혀요.

우리 출력도 이 순서와 맞아요. sc-normal의 생성 시각과 PodScheduled=True 시각은 둘 다 12:04:07Z(한국 시각 21:04:07)였어요. 같은 날 다른 파드(watch-demo)의 watch 스트림을 받아 봤을 때도 ADDED 이벤트에서 node가 None이던 파드가 바로 다음 리비전(134415 → 134416)의 MODIFIED에서 node=k8s-worker3이 됐어요. 바인딩 하나가 저장소의 쓰기 한 번으로 끝난 거예요.

누가 썼는지 적어 두는 managedFields에는 흥미로운 점이 있었어요. sc-normal의 항목은 kubectl-client-side-apply(f:containers), calico, kubelet(f:conditions, f:containerStatuses, f:podIP) 셋뿐이었고 kube-scheduler 항목은 없었어요. nodeName을 적은 주인이 기록에 남지 않은 셈이에요. BindingREST가 파드를 일반 update 경로가 아니라 저장소의 GuaranteedUpdate로 바로 고치기 때문으로 보여요.

📖 용어: managedFields
객체의 필드를 어느 클라이언트(manager)가 어떤 요청(operation)과 서브리소스로 마지막에 썼는지 적어 두는 메타데이터예요. 기본 출력에서는 숨겨져 있고 kubectl get pod <이름> --show-managed-fields -o yaml로 볼 수 있어요.

"etcd에 기록한다"는 부분도 바로잡을 수 있어요. 조회 당시 마스터의 2379 포트(etcd)에 붙어 있던 연결 92개는 모두 kube-apiserver였어요. etcd는 클라이언트 인증서를 요구하므로 worker1에서 인증서 없이 접속한 요청은 종료 코드 56으로 실패했어요. 이 스케줄러의 기본 설정에는 etcd 접속 주소나 인증서가 없고 Binding을 API 서버로 보내요. 관리 도구는 40편처럼 유효한 etcd 클라이언트 인증서로 직접 접속할 수 있어요.

그림 3. 이번 정상 배치에서 스케줄러는 Binding 하나를 보내고 그 파드에 노드를 적어 etcd에 쓰는 일은 API 서버가 한다

바인딩이 성공하면 스케줄러는 마지막으로 이벤트를 하나 남겨요. schedule_one.go의 finishBinding은 성공했을 때만 "Successfully assigned %v/%v to %v" 형식의 Scheduled 이벤트를 기록해요. 그림 1에서 sc-nodename에 Scheduled가 없던 이유가 이것이에요. 그 파드에는 바인딩이 없었어요. 이번 정상 배치에서 스케줄러가 파드에 보낸 쓰기는 "이 파드를 이 노드에"라는 Binding 하나이고 그 파드에 nodeName과 PodScheduled를 적어 etcd에 쓰는 것은 API 서버예요.

3. 스케줄링 사이클은 하나씩 돌고 바인딩 사이클은 고루틴으로 따로 돈다

sc-normal 하나를 스케줄하는 동안 스케줄러 안에서 어떤 단계가 돌았는지는 스케줄러 메트릭으로 셀 수 있어요. 파드를 만들기 전과 후에 마스터의 127.0.0.1:10259/metrics를 받아 차이만 남겼어요.

그림 4. 파드 하나에 확장 지점 12곳이 한 번씩 돌았고 PreBindPreFlight만 Skip이었다

23편에서 문서 순서대로 본 확장 지점이 실제로 한 번씩 지나갔어요. 새 파드가 들어오며 큐에 넣는 이벤트(UnscheduledPodAdd)가 하나 생겼고 시도 결과(scheduled)도 하나였어요. 단계 이름을 두 사이클로 나누면 이래요.

· 스케줄링 사이클 쪽: PreEnqueue(큐에 넣기 전), Sign, PreFilter, Filter, PreScore, Score, Reserve, Permit
· 바인딩 사이클 쪽: PreBindPreFlight(Skip), PreBind, Bind, PostBind

23편 그림에 없던 이름이 둘 있어요. Sign은 비슷한 파드끼리 앞서 계산한 결과를 다시 쓸 수 있는지 가르려고 파드마다 서명을 만드는 자리예요. v1.37.2의 프레임워크 인터페이스 주석에는 이 서명으로 "whether it can use a cached scheduling result, or needs to recompute the prioritized nodes"를 정한다고 적혀 있고 KEP-5598이 붙어 있어요. PreBindPreFlight는 PreBind 앞에서 "이 파드에 미리 할 일이 있는가"만 가볍게 묻는 자리예요. 같은 주석에 Skip은 "this PreBind plugin has nothing to do with the pod"라고 돼 있어요. 볼륨을 미리 준비하는 것 같은 일이 없었다는 뜻이에요. 이때는 바인딩 전에 nominatedNodeName을 따로 적는 요청도 보내지 않아요(schedule_one.go의 bindingCycle 주석: "otherwise the pod will be soon bound anyway"). 그래서 스케줄러가 sc-normal에 보낸 쓰기는 바인딩 하나로 끝났어요.

두 사이클이 갈리는 곳은 schedule_one.go의 scheduleOnePod에 있어요.

scheduleResult, assumedPodInfo, status := sched.schedulingCycle(schedulingCycleCtx, state, schedFramework, podInfo, start, podsToActivate) if !status.IsSuccess() { sched.FailureHandler(schedulingCycleCtx, schedFramework, assumedPodInfo, status, scheduleResult.nominatingInfo, start) return } // bind the pod to its host asynchronously (we can do this b/c of the assumption step above). go sched.runBindingCycle(ctx, state, schedFramework, scheduleResult, assumedPodInfo, start, podsToActivate)

→ 스케줄링 사이클은 이 함수 안에서 끝까지 돌고 바인딩 사이클은 go 키워드로 새 고루틴에 넘긴다는 뜻이에요. 넘기자마자 함수가 끝나니 스케줄러는 바인딩 응답을 기다리지 않고 큐에서 다음 파드를 꺼내요. 23편에서 인용한 "Scheduling cycles are run serially, while binding cycles may run concurrently."가 코드에서는 이 한 줄이에요.

주석의 "assumption step"은 스케줄링 사이클 끝의 assume이에요. 같은 파일의 assume 함수는 이렇게 시작해요.

// Optimistically assume that the binding will succeed and send it to apiserver // in the background. // If the binding fails, scheduler will release resources allocated to assumed pod // immediately. assumedPodInfo.Pod.Spec.NodeName = host ... if err := sched.Cache.AssumePod(logger, assumedPodInfo.Pod); err != nil {

→ 바인딩이 성공할 거라고 보고 파드 사본의 nodeName을 먼저 채워 스케줄러 캐시에 넣어 둔다는 뜻이에요. 실패하면 그 자원을 바로 돌려놔요.

📖 용어: assume(가정)
스케줄러가 바인딩 응답을 기다리지 않고 "이 파드는 이 노드에 붙었다"고 자기 캐시에 먼저 적어 두는 일이에요. 다음 파드를 고를 때 그 노드의 자원이 이미 쓰인 것으로 보이게 하려는 거예요. 바인딩된 파드가 watch로 들어오면 캐시의 AddPod가 가정해 둔 항목을 실제 파드로 갱신하고 바인딩이 실패하면 ForgetPod로 지워요. 이 상태의 파드 수가 메트릭 scheduler_cache_size{type="assumed_pods"}예요.

23편에서는 Reserve를 앞 파드의 바인딩을 기다리는 동안 다음 파드가 같은 자원을 또 차지하지 않게 하는 자리로 봤어요. 플러그인 쪽에서 그 일을 하는 자리가 Reserve라면 스케줄러 캐시에서 노드 자원을 미리 잡아 두는 것은 assume이에요. 바인딩 사이클이 클러스터에 적용하는 것은 "이 파드는 이 노드"라는 결정 하나이고 그동안 스케줄러는 다음 파드로 넘어가 있어요. 이미지 내려받기나 컨테이너 만들기는 바인딩 사이클에 없어요. 그 일은 nodeName을 본 kubelet이 해요.

4. 노드 정보는 파드마다 묻지 않고 watch로 채운 캐시에서 꺼낸다

"스케줄러가 API 서버에 노드 정보를 요청한다"도 확인했어요. 스케줄러 캐시의 크기를 본 뒤 파드 다섯 개를 연달아 만들고 그동안 API 서버가 받은 nodes 요청을 동사별로 셌어요.

그림 5. 파드 다섯 개를 스케줄하는 동안 nodes LIST와 WATCH는 그대로였고 바인딩은 22에서 27로 늘었다

스케줄러 캐시에는 노드 4개와 노드가 정해진 파드 31개가 들어 있었고 바인딩을 기다리는 가정 파드는 0개였어요. 파드 다섯 개를 스케줄하는 6초 동안 nodes LIST는 91, WATCH는 475 그대로였어요. 스케줄러가 파드마다 노드 목록을 받아 왔다면 LIST가 5 늘었어야 해요. GET은 1902에서 1907로 늘었지만 kubelet이 자기 Node 객체를 읽는 요청도 같은 숫자에 섞이니 누가 보낸 것인지는 이 숫자로 가를 수 없어요. 분명하게 늘어난 것은 pods/binding POST 다섯 번(22 → 27)이었어요. 다섯 개가 모두 worker3으로 간 이유는 23편의 점수 계산 몫이라 여기서는 따지지 않을게요.

📖 용어: 인포머(informer)
client-go가 제공하는 장치예요. 초기 객체를 받은 뒤 WATCH로 바뀐 것을 받아 메모리의 사본을 최신으로 유지해요. client-go v1.37.2에서는 초기 객체도 WATCH로 받는 WatchList가 기본이고 LIST 뒤 WATCH를 잇는 대체 경로도 있어요(39편). 사본이 바뀔 때마다 등록해 둔 함수(1절의 addPod 같은 것)를 불러 줘요. 스케줄러, 컨트롤러 매니저, kubelet이 이런 캐시를 활용해 API 서버를 봐요.

노드 정보가 들어오는 길은 1절의 eventhandlers.go에 있어요. 노드가 추가되면 addNodeToCache가 sched.Cache.AddNode를, 바뀌면 updateNodeInCache가 sched.Cache.UpdateNode를 불러 캐시를 고쳐요. 그리고 schedule_one.go의 schedulingCycle은 첫 줄에서 그 캐시를 스냅숏으로 옮겨요.

func (sched *Scheduler) schedulingCycle(...) (ScheduleResult, *framework.QueuedPodInfo, *fwk.Status) { if err := sched.Cache.UpdateSnapshot(klog.FromContext(ctx), sched.nodeInfoSnapshot); err != nil { return ScheduleResult{nominatingInfo: clearNominatedNode}, podInfo, fwk.AsStatus(err) } scheduleResult, status := sched.schedulingAlgorithm(ctx, state, schedFramework, podInfo, start)

→ 사이클마다 캐시의 현재 내용을 nodeInfoSnapshot에 옮겨 담고 필터와 스코어는 그 스냅숏을 본다는 뜻이에요. API 서버에 묻는 줄은 없어요. 스케줄러는 노드 정보를 파드마다 묻지 않고 watch로 채워 둔 캐시의 사본으로 노드를 골라요.

그림 6. 파드와 노드는 watch로 들어와 큐와 캐시에 쌓이고 사이클은 큐에서 파드를, 캐시에서 스냅숏을 꺼낸다

캐시에서 꺼내 쓰는 대가도 있어요. 캐시는 watch가 전해 준 만큼만 최신이라 아주 짧은 순간에는 실제 클러스터보다 늦을 수 있어요. 그래도 옛 정보로 고른 배정이 아무 검사 없이 실행되지는 않아요. 2절에서 봤듯이 API 서버는 이미 노드가 있거나 지우는 중인 파드의 바인딩을 거절하고 nodeName을 받은 노드의 kubelet도 자기 노드 자원으로 한 번 더 확인해요. 1절에서 인용한 문서가 자원이 모자라면 파드가 OutOfcpu 같은 이유로 실패한다고 적은 것이 그 확인이에요. 캐시가 늦을 때 쿠버네티스가 어떻게 버티는지는 39편에서 따로 봤어요.

💡 실무에서는: 스케줄러가 느리다고 느껴질 때 볼 메트릭
• kubeadm 클러스터의 스케줄러 메트릭은 마스터의 https://127.0.0.1:10259/metrics에 있어요. 마스터 밖에서는 열리지 않으니 마스터에서 인증서를 들고 읽거나 마스터에 붙을 수 있는 수집기로 모아요
• scheduler_cache_size로 캐시에 든 노드·파드 수가 실제와 맞는지, assumed_pods가 쌓여 있지 않은지 봐요. 가정 파드 수가 0으로 돌아오지 않으면 바인딩 응답이나 watch가 늦고 있는지 의심해 볼 수 있어요
• API 서버의 apiserver_request_total을 resource와 verb로 나누면 LIST와 Binding 전체 요청의 증가를 볼 수 있어요. 어느 클라이언트의 요청인지는 이 값만으로 구분할 수 없어요

5. 대기 파드는 관련 이벤트와 주기 점검으로 다시 큐에 오른다

바인딩까지 가지 못하는 파드도 있어요. 하나는 들어갈 노드가 없는 파드이고 다른 하나는 아직 스케줄하지 말라고 표시한 파드예요. 둘을 하나씩 만들어 스케줄러 큐에서 어디에 있는지 봤어요.

그림 7. sc-wait는 unschedulable에서 20초 동안 다시 시도되지 않다가 노드 라벨이 붙자 active로 올라갔고 sc-gated는 gated에서 기다렸다

sc-wait는 nodeSelector: lab/sched-demo=yes를 적었지만 그 라벨을 가진 노드가 없는 파드예요. 첫 시도에서 FailedScheduling을 남겼고(메시지 읽는 법은 23편) 5초 뒤 스케줄러 큐에서는 unschedulable에 1개가 있었어요. 20초를 더 기다려도 FailedScheduling 이벤트의 count는 1이었어요. 이 20초가 들어간 메트릭 차이(21:04:23 → 21:04:44)에서도 시도 결과는 라벨을 붙인 뒤의 scheduled 한 번만 늘었어요. 실패한 시도는 한 번도 없었다는 뜻이에요. 스케줄러는 같은 조건에서 같은 결과가 나올 파드를 다시 돌리지 않고 기다리게 했어요.

21:04:43에 worker3에 그 라벨을 붙이자 큐 메트릭에 event="NodeUpdateNodeLabel", queue="active"가 1 늘었고 라벨 명령 뒤 첫 조회(0.1초)에서 이미 nodeName이 k8s-worker3이었어요. 노드 핸들러 updateNodeInCache에는 이 동작의 조건이 주석으로 적혀 있어요. "Only requeue unschedulable pods if the node became more schedulable." 노드가 파드를 받기 좋은 쪽으로 바뀌었을 때만 기다리던 파드를 다시 큐에 올린다는 뜻이에요. 어떤 변화가 어떤 파드를 다시 꺼내는지는 23편에서 본 QueueingHint가 플러그인별로 정해요.

아무 변화가 없으면 영영 기다릴까요? 그렇지는 않아요. v1.37.2 scheduling_queue.go의 DefaultPodMaxInUnschedulablePodsDuration은 5분이고 주석에는 이보다 오래 unschedulable에 머문 파드를 backoff나 active로 옮긴다고 적혀 있어요. 이 점검은 30초마다 돌아요(wait.Until(..., 30*time.Second, ...)). 관련 이벤트가 오면 active나 backoff로 옮겨 다시 시도하고 그렇지 않아도 5분 넘게 남은 파드는 30초 간격 점검에서 다시 큐로 옮겨요.

sc-gated는 schedulingGates: [{name: lab/wait-for-me}]를 단 파드예요. STATUS는 SchedulingGated였고 FailedScheduling 이벤트는 0건, 큐 메트릭에서는 gated에 1개가 있었어요. 21:04:48에 게이트를 지우자 3초 뒤 worker3에서 Running이었어요.

📖 용어: schedulingGates
파드에 "아직 스케줄하지 마라"는 표시를 다는 칸이에요(v1.30부터 stable). 파드를 만들 때만 넣을 수 있고 만든 뒤에는 지우기만 할 수 있어요. 게이트가 하나라도 남아 있으면 스케줄러는 그 파드를 시도하지 않아요. 보통 외부 컨트롤러가 준비(쿼터, 자원 확보 등)를 마친 뒤 게이트를 지워요.

Pod Scheduling Readiness 문서는 이 기능이 생긴 이유를 이렇게 적어요. 필요한 자원이 없어 오래 기다리는 파드가 있는데 "These Pods actually churn the scheduler (and downstream integrators like Cluster AutoScaler) in an unnecessary manner." 그런 파드가 스케줄러와 클러스터 오토스케일러를 쓸데없이 바쁘게 만든다는 뜻이에요. 같은 문서는 scheduler_pending_pods의 gated 라벨로 "시도했지만 못 들어간 파드"와 "일부러 막아 둔 파드"를 나눠 본다고 설명해요. 우리 메트릭에서 sc-wait는 unschedulable, sc-gated는 gated로 갈린 것이 그 구분이에요.

게이트를 검사하는 것은 SchedulingGates 플러그인의 PreEnqueue예요(v1.37.2 scheduling_gates.go). 게이트가 있으면 "waiting for scheduling gates" 상태를 돌려주고 파드는 스케줄링 사이클에 들어가지 못해요. 사이클에 들어가지 않으니 FailedScheduling도 남지 않았어요. 2절에서 본 API 서버의 바인딩 검사에도 게이트 조건이 있으니 누가 바인딩을 직접 보내도 게이트가 남은 파드는 노드를 받지 못해요.

그림 8. 게이트가 있으면 큐에 들어가기 전에 멈추고 필터에서 떨어지면 unschedulable에서 관련 이벤트나 주기 점검을 기다린다

스케줄러는 파드가 만들어질 때만 일하지 않아요. 노드가 바뀌거나 게이트가 지워지는 것도 파드를 다시 꺼내는 계기예요.

💡 실무에서는: Pending 파드는 이벤트와 STATUS로 먼저 세 갈래로 나눠요
• Pending인데 이벤트가 없으면 spec.schedulerName, 스케줄러 상태(20편), schedulingGates부터 확인해요. 이벤트가 없다는 사실만으로 원인을 확정할 수는 없어요
• STATUS가 SchedulingGated면 kubectl get pod <이름> -o jsonpath='{.spec.schedulingGates}'로 남은 게이트를 보고 그 게이트를 지울 쪽이 일하고 있는지 봐요
• FailedScheduling이 있으면 23편에서 한 방법으로 메시지를 끊어 읽고 조건을 고쳐요. 파드를 다시 만들 필요는 없어요. 관련 이벤트가 없어도 unschedulable에 5분 넘게 남은 파드는 30초 간격 점검에서 active나 backoff로 옮겨져요
• 큐별로 몇 개가 기다리는지는 스케줄러 메트릭 scheduler_pending_pods{queue="..."}로 봐요

6. 흔한 설명 다섯 줄을 고쳐 읽으면

도입에서 인용한 설명을 이번 실험과 소스에 맞춰 한 줄씩 고치면 이래요.

흔한 설명정확히 말하면이번에 본 근거
파드 생성 이벤트를 받는다모든 파드와 노드의 변화를 watch로 받는다. 새로 배치할 일반 파드는 nodeName이 비어 있고 schedulerName이 자기 프로파일과 같을 때 큐에 넣는다. 관련 이벤트나 주기 점검으로 대기 파드를 다시 큐에 올린다세 파드 중 바인딩 +1(1절), 노드 라벨 뒤 0.1초 안에 배정(5절)
노드 정보를 API 서버에 요청한다인포머로 채운 캐시를 사이클마다 스냅숏으로 옮겨서 본다파드 5개 동안 nodes LIST·WATCH 증가 0(4절)
바인딩 사이클이 변경 사항을 클러스터에 적용한다고루틴에서 POST pods/이름/binding을 한 번 보낸다. 컨테이너를 만드는 것은 그 노드의 kubelet이다파드 1개에 바인딩 +1, 5개에 +5(1·4절), go runBindingCycle(3절)
결정을 etcd에 기록한다바인딩을 받은 API 서버가 nodeName과 PodScheduled를 한 번에 고쳐 etcd에 쓴다조회 당시 2379 연결은 kube-apiserver만, 생성과 PodScheduled가 같은 초, managedFields에 스케줄러 없음(2절)
kubectl이 created라고 하면 파드가 뜬 것이다created는 API 서버에 저장됐다는 뜻이다. 스케줄은 그 뒤에 따로 일어난다sc-other-scheduler는 저장됐지만 10초 뒤에도 노드가 없었다(1절)

마지막 줄은 20편에서도 봤어요. 스케줄러를 멈춘 상태에서도 kubectl create deployment에는 created가 돌아왔고 파드는 노드 없이 Pending이었어요. kubectl이 받는 응답은 API 서버가 객체를 저장했다는 확인이고 스케줄러는 그 저장을 watch로 본 뒤에야 움직여요.

바인딩 다음 단계도 짧게 확인했어요. 4절의 st-1이 뜬 worker3에서 crictl images로 CRI ImageService에 이미지 목록을 물으니 registry.k8s.io/pause:3.10.2가 보였고 그 컨테이너의 OCI 번들 config.json은 ociVersion 1.3.0, 실행 인자 ['/pause']였어요. 노드에 있는 runc는 1.5.2였어요. kubelet이 CRI로 containerd를 부르고 containerd가 OCI 번들을 만들어 runc에 넘기는 과정은 26편과 27편에서 봤어요. 이번 정상 배치에서 스케줄러가 파드에 보낸 쓰기는 그보다 앞의 Binding 요청까지였어요.

⚠️ 주의: 스크립트에서 created만 보고 다음 단계로 넘어가지 않아요
• kubectl apply 바로 뒤에 파드 IP로 요청을 보내면 아직 노드도 IP도 없을 수 있어요. 스케줄이 끝났는지는 kubectl wait --for=condition=PodScheduled pod/<이름>, 컨테이너까지 준비됐는지는 --for=condition=Ready로 기다려요
• 스케줄러가 없거나 schedulerName이 틀리면 created 뒤에 아무 일도 일어나지 않아요. wait에 --timeout을 주고 시간이 넘으면 이벤트부터 봐요
✍️ 오늘의 요약
스케줄러는 새로 배치할 일반 파드 중 nodeName이 비어 있고 schedulerName이 자기 프로파일과 같은 파드를 큐에 넣어요. 이번 정상 배치의 결과는 Binding 하나로 보냈어요. nodeName과 PodScheduled를 적어 etcd에 쓰는 것은 API 서버예요.

세 파드를 만들자 아무 설정이 없는 파드만 스케줄러를 거쳤어요. schedulerName이 다른 파드는 이벤트 없이 Pending이었고 nodeName을 직접 적은 파드는 스케줄러 없이 kubelet이 바로 띄웠어요. 스케줄러의 권한에는 파드나 컨테이너를 만드는 규칙이 없고 pods/binding 생성이 있어요. API 서버는 Binding을 받아 지우는 중이거나 이미 배정됐거나 게이트가 남은 파드를 거절하고 나머지는 nodeName과 PodScheduled를 한 번에 저장해요. 스케줄링 사이클은 하나씩 돌고 끝에서 결과를 자기 캐시에 먼저 가정해 둔 뒤 바인딩은 고루틴에 넘겨요. 노드 정보는 인포머로 채운 캐시에서 꺼내니 파드 다섯 개를 스케줄해도 nodes LIST는 늘지 않았어요. 들어갈 곳이 없는 파드는 unschedulable에서 기다리다 노드 라벨이 붙자 0.1초 안에 배정됐고 게이트를 단 파드는 시도조차 되지 않다가 게이트를 지우자 3초 뒤 Running이었어요. 스케줄러가 하는 일은 노드 이름 한 칸을 정하는 것이고 그 칸을 쓰는 것은 API 서버, 그 칸을 보고 컨테이너를 띄우는 것은 kubelet이에요.
