70편. 네이티브 사이드카는 어떤 순서로 뜨고 어떤 순서로 죽을까

같은 순간에 Job 두 개를 만들었어요. 둘 다 work 컨테이너가 5초 일하고 exit 0으로 끝나고 side 컨테이너는 SIGTERM을 받을 때까지 계속 도는 구성이에요. 두 Job의 work는 똑같이 12:15:17(UTC)에 끝났어요. 그런데 46초 뒤 kubectl get job은 한쪽을 Complete 1/1로, 다른 쪽을 Running 0/1로 보여 줬어요. 끝나지 않은 Job의 파드는 1/2 NotReady였어요.

두 Job의 차이는 side를 적은 자리 하나였어요. 끝난 쪽은 side를 initContainers에 넣고 restartPolicy: Always를 줬어요. 끝나지 않은 쪽은 side를 work와 함께 containers에 적었어요. 뒤쪽은 네이티브 사이드카가 들어오기 전(1.28 알파, 1.29부터 기본 켜짐)에 사이드카를 붙이던 방법이에요. 2016년에 올라온 이슈 하나가 바로 이 모양을 문제로 적었고 그 이슈에는 +1이 422개 달렸어요.

이번 글은 Lima VM 4대, kubeadm v1.37.2, containerd 2.4.1인 우리 클러스터에서 옛 방식과 그때의 우회책을 다시 돌려 봐요. 그리고 2016년부터 2018년까지의 이슈와 첫 KEP를 원문으로 읽어요.

이 글에서 다룰 것
· 작업 컨테이너가 끝났는데 Job은 왜 Running으로 남을까?
· 2016년의 답이었던 "끝남 파일"은 지금도 통할까? 무엇을 고쳐야 했을까?
· 옛 방식일 때 얼마나 불편했나? 시작, 종료, 재시작에서 각각 무엇이 깨졌을까?
· Istio의 /quitquitquit과 holdApplicationUntilProxyStarts는 무엇에 기댔을까?
· 사이드카를 initContainers에 넣는다고? 그 자리에서는 어떤 순서로 뜰까?
· "사이드카라는 표시를 붙이자"는 첫 제안은 어떤 모양이었을까?

1. 작업이 끝나도 사이드카가 살아 있으면 파드는 Running이다

📖 용어: 사이드카 컨테이너 (sidecar container)
앱 컨테이너 옆에서 프록시, 로그 수집, 인증서 갱신 같은 보조 일을 하는 컨테이너예요. 같은 파드에 있어서 네트워크와 볼륨을 함께 써요(파드 안에서 무엇을 공유하는지는 61편). 이 글에서 "옛 방식"은 사이드카를 containers에 앱과 나란히 적는 것이고 "네이티브 사이드카"는 initContainers에 넣고 restartPolicy: Always를 주는 지금의 모양이에요.

첫 실험의 원본은 labs/devops/k8s-study/out/68-job-completes.txt와 같은 디렉터리의 68-job-completes.sh예요. 두 Job은 사이드카 명령까지 같아요. side는 SIGTERM을 받으면 3초 정리하고 exit 0으로 끝나요.

그림 1. work는 두 Job 모두 12:15:17에 끝났어요. 끝나지 않은 쪽은 side가 아무 신호도 받지 못했어요.

job-native에서는 work가 12:15:17에 끝나자 side가 SIGTERM을 받았고 3초 정리한 뒤 12:15:20에 끝났어요. Job의 completionTime은 12:15:23이에요. 사이드카가 끝난 시각보다 뒤예요. 1.31 CHANGELOG의 "The sidecars' finish time will now be accounted for when calculating the job's finish time"(#124942)과 맞는 결과예요.

job-old에서는 work가 같은 12:15:17에 끝났지만 side는 아무 신호도 받지 않고 계속 돌았어요. 파드 phase는 Running이었고 Job은 active=1, succeeded=0이었어요. READY 칸의 1/2는 끝난 work는 ready가 아니고 side 하나만 ready라는 뜻이에요. 쿠버네티스 입장에서는 파드 안의 컨테이너 두 개가 같은 급이라서 둘 중 하나가 끝났다고 다른 하나를 멈출 이유가 없었어요.

📖 용어: 파드 phase와 Job 완료
파드 phase는 Pending, Running, Succeeded, Failed로 나타내는 파드 단위의 요약이에요. restartPolicy가 Never인 파드는 컨테이너가 모두 끝나야 Succeeded나 Failed가 되고 하나라도 돌고 있으면 Running이에요. Job 컨트롤러는 Succeeded가 된 파드 수를 세어 완료를 판정해요. phase가 바뀌는 순서는 63편에서 다뤘어요.

같은 날 먼저 돌린 실험에도 같은 모양이 남아 있어요. old-sidecar 파드는 app이 11:29:55에 끝났지만 파드를 만들고 30초가 지난 시점에도 logger가 running이었고 phase는 Running, READY와 STATUS는 1/2 NotReady였어요(labs/devops/k8s-study/out/68-init-sidecar.txt).

그림 2. 쿠버네티스는 containers에 적힌 컨테이너를 같은 급으로 다뤄요.

2016년 5월 19일 a-robinson이 올린 이슈 #25908 "Better support for sidecar containers in batch jobs"가 이 결과를 그대로 적었어요.

Currently the Job will keep running as long as the second container keeps running, which means that the user has to modify the second container in some way to detect when the first one is done so that it can cleanly exit as well.

→ 두 번째 컨테이너가 도는 동안 Job도 계속 돌기 때문에, 사용자가 두 번째 컨테이너를 고쳐서 첫 번째가 끝난 것을 알아채고 스스로 끝나게 해야 한다는 뜻이에요. 이 이슈는 2021년 2월 KEP-753으로 논의를 옮기며 닫혔고, 2026년 11월 지금 코멘트 132개와 +1 422개가 달려 있어요.

Job 컨트롤러에서 "주 컨테이너만 보고 완료 판정"을 하자는 의견도 있었어요. 2018년 2월 enisoc은 그렇게 하면 Job이 끝났다고 판정해도 파드는 계속 돌아 노드가 자원을 돌려받지 못한다고 지적했어요. 그리고 이렇게 적었어요.

it seems cleaner to me to address this at the Pod API level, if at all.

→ 푼다면 파드 API 수준에서 푸는 것이 깔끔하다는 뜻이에요. 2018년의 첫 KEP도 Job에 primaryContainer 필드를 두는 대안을 "too specific to job"이라며 버렸어요. 고칠 자리는 Job이 아니라 파드였어요.

💡 실무에서는 Job 도우미를 initContainers로 옮겨요
Job과 CronJob에 프록시나 로그 수집기 같은 도우미를 붙인다면 도우미를 initContainers로 옮기고 restartPolicy: Always를 줘요. 1.29부터 기본으로 켜져 있고 1.33에 GA가 됐어요. 이때 사이드카 이미지는 SIGTERM을 받으면 끝나도록 만들어야 해요. SIGTERM을 무시하는 사이드카는 work가 끝난 뒤에도 유예 시간 30초를 다 쓰고 나서야 끝나요. 실제 시간은 70편에서 재요.

2. 2016년의 답은 컨테이너끼리 파일로 신호를 주고받는 것이었다

이슈가 열리고 넉 달 반쯤 뒤 erictune이 내놓은 답은 쿠버네티스를 바꾸지 않는 방법이었어요(2016-10-06).

The two containers can share an emptyDir, and the first container and write an "I'm exiting now" message to a file and the other can exit when it sees that message.

→ 두 컨테이너가 emptyDir를 함께 마운트하고 첫 번째 컨테이너가 "이제 끝난다"는 파일을 쓰면 다른 컨테이너가 그 파일을 보고 끝나라는 뜻이에요.

📖 용어: emptyDir
파드가 노드에 뜰 때 만들어지고 파드가 지워질 때 함께 지워지는 빈 볼륨이에요. 같은 파드의 컨테이너들이 같은 디렉터리를 마운트해 파일로 데이터를 넘길 때 써요.

v1.37.2에서 이 방법을 그대로 돌려 봤어요. work는 끝날 때 /sig/main-done을 만들고 side는 1초마다 그 파일이 있는지 봐요. 원본은 labs/devops/k8s-study/out/68-old-workarounds.txt의 (a)와 같은 디렉터리의 68-old-workarounds.sh예요.

work: trap "touch /sig/main-done" EXIT; echo work start; sleep 5; echo work done side: while [ ! -f /sig/main-done ]; do sleep 1; done; echo side saw main-done; exit 0 job: succeeded=1 completionTime=2026-11-15T12:42:32Z conditions=SuccessCriteriaMet,Complete side: finishedAt=2026-11-15T12:42:29Z exit=0 work: finishedAt=2026-11-15T12:42:29Z exit=0

→ work와 side가 같은 초(12:42:29)에 끝났고 Job은 Complete가 됐어요. 방법 자체는 지금도 통해요.

문제는 대가예요. 두 컨테이너 모두 셸이 있어야 하고 파일 경로라는 약속을 알아야 해요. 2017년 6월 jmillikin-stripe는 Envoy에 이 방법을 적용한 스크립트를 "bash madness"라며 공유했어요. main은 trap "touch /tmp/pod/main-terminated" EXIT로 파일을 남기고 envoy 컨테이너는 Envoy를 백그라운드로 띄운 뒤 1초마다 파일을 확인해 kill하는 구조였어요. 그는 이 방식의 한계를 이렇게 적었어요.

each container needs bundled tooling to coordinate lifetimes, which means we can't directly use upstream container images.

→ 컨테이너마다 수명을 맞추는 도구를 넣어야 해서 upstream 이미지를 그대로 쓸 수 없다는 뜻이에요. 2018년 첫 KEP의 Motivation도 같은 대가를 세 줄로 정리했어요. 사이드카를 배포할 때마다 같은 생명주기 로직을 다시 써야 하고 서드파티 컨테이너는 래퍼 스크립트로 감싸야 하고 그 래퍼는 이미지 안에 셸이 있어야 해서 도구가 없는 최소 이미지에서는 동작하지 않는다는 내용이에요.

/quitquitquit: 이번에는 앱이 사이드카를 불러서 끝낸다

서비스 메시 쪽 Job 사용자도 같은 문제를 겪었어요. 2019년 6월 Istio에 istio#15041이 올라왔어요. CronJob이 끝날 때 다른 컨테이너에서 pilot-agent를 끝낼 수 있게 Envoy처럼 quitquitquit 엔드포인트를 달아 달라는 요청이었어요. 엿새 뒤 병합된 istio#15123은 설명에 목적을 적었어요.

Added a `/quitquitquit` to handle quit request from client, which mainly provide a way for k8s jobs to exit. It only handles http POST method, by default pilot-agent listens on 15020 port.

→ 주로 쿠버네티스 Job이 끝날 수 있게 하려고 pilot-agent의 15020 포트에 POST만 받는 /quitquitquit을 달았다는 뜻이에요. 2019년 7월 istio#15406에서 localhost 요청만 받도록 좁혔어요. 이 방법을 쓰려면 앱 컨테이너가 일을 마친 뒤 localhost:15020/quitquitquit에 POST를 보내야 해요.

⚠️ 두 우회 모두 사이드카가 아니라 앱을 고쳐요
끝남 파일은 앱 컨테이너의 명령을 감싸야 하고 /quitquitquit은 앱이 메시의 포트와 경로를 알아야 해요. 사이드카를 쓰는 이유가 앱 코드를 건드리지 않고 기능을 붙이는 것이었는데 Job을 끝내려면 결국 앱 쪽을 고쳐야 했어요. 메시를 바꾸거나 사이드카를 빼면 앱 이미지도 다시 손봐야 해요.

3. 옛 방식일 때 얼마나 불편했나: 시작, 종료, 재시작

Job이 끝나지 않는 문제는 가장 눈에 띄는 증상이었을 뿐이에요. 2018년 첫 KEP의 Motivation은 Jobs, Startup, Shutdown 세 항목을 나란히 적었어요. containers에 같이 적힌 컨테이너는 시작도 종료도 같은 급으로 처리됐기 때문이에요. 하나씩 v1.37.2에서 확인해 봤어요.

시작: 앱이 프록시보다 먼저 뜬다

2018년 6월 Istio의 nmittler가 올린 이슈 #65502는 앱과 istio-proxy가 동시에 시작돼서 생기는 문제를 적었어요.

Kubernetes starts both the application and istio-proxy at the same time ... if Envoy has not yet received its initial configuration from Pilot (the configuration service), the service will experience temporary traffic loss until Envoy is configured.

→ Envoy가 설정을 받기 전에 앱이 트래픽을 받기 시작하면 Envoy 설정이 끝날 때까지 트래픽을 잃는다는 뜻이에요. 당시 Istio는 앱 컨테이너에 시작 스크립트를 넣어 Envoy가 설정을 받을 때까지 앱 시작을 늦추라고 권했어요. 2019년 1월의 istio#11130은 사용자들이 앱 컨테이너에 20~30초 sleep을 넣는다고 적었고 원인을 찾는 데 며칠이 걸릴 수 있다고 덧붙였어요.

📖 용어: 서비스 메시와 Envoy
파드마다 프록시 사이드카를 넣고 iptables로 파드에 들고 나는 트래픽을 그 프록시로 돌리는 구조예요. Istio는 Envoy를 istio-proxy라는 사이드카로 넣어요. 그래서 프록시가 준비되기 전이나 먼저 끝난 뒤에는 앱의 연결이 실패해요. 사이드카 없이 노드에서 eBPF로 연결을 보는 방식은 13편에서 다뤘어요.

Istio의 답은 2020년 7월 17일 병합된 istio#24737의 holdApplicationUntilProxyStarts였어요. 설명은 이래요.

the sidecar injector injects the sidecar in front of all other containers and adds a post-start lifecycle hook to the sidecar container. The hook blocks the start of the other containers until the proxy is fully running.

→ 사이드카를 다른 모든 컨테이너보다 앞에 넣고 postStart 훅을 달아, 프록시가 완전히 뜰 때까지 다른 컨테이너의 시작을 막는다는 뜻이에요. 주입 템플릿에는 postStart.exec.command: [pilot-agent, wait]가 들어갔어요.

📖 용어: postStart 훅
컨테이너를 시작한 직후 kubelet이 실행하는 명령이나 HTTP 호출이에요. v1.37.2 kubelet은 컨테이너를 시작하는 함수 안에서 시작(Step 3) 다음에 이 훅을 끝까지 실행해요(Step 4). 훅이 끝나기 전에는 그 함수가 돌아오지 않아요.

(b)에서 이 모양을 흉내 냈어요. postStart가 5초 걸리는 proxy를 containers 맨 앞에 둔 파드와 맨 뒤에 둔 파드를 비교했어요.

hook-first (containers 순서: proxy app) app: startedAt=2026-11-15T12:42:56Z proxy: startedAt=2026-11-15T12:42:51Z hook-last (containers 순서: app proxy) app: startedAt=2026-11-15T12:42:52Z proxy: startedAt=2026-11-15T12:42:52Z

→ proxy가 맨 앞이면 app은 훅 5초가 끝난 12:42:56에야 시작했어요. 맨 뒤면 app이 먼저 시작했고 막히지 않았어요.

이 우회는 kubelet이 containers를 적힌 순서대로 하나씩 시작하고 postStart를 같은 호출 안에서 끝까지 기다린다는 구현에 기대요. v1.37.2 kuberuntime_container.go의 startContainer가 바로 그 순서로 되어 있어요. 다만 API가 약속한 동작은 아니었어요. 2023년 사이드카 KEP 리뷰에서 thockin이 이렇게 적었어요.

We don't guarantee sequential start, but it is sequential and I believe in Hyrum's law...

→ 순차 시작을 보장하지는 않지만 실제로는 순차적이고 그러면 누군가는 거기에 기댄다는 뜻이에요. 하이럼의 법칙은 관찰 가능한 동작이면 문서에 없어도 누군가 의존하게 된다는 경험칙이에요.

종료: 프록시가 앱보다 먼저 끝난다

2018년 7월 Stono가 올린 istio#7136은 반대쪽 끝을 적었어요. 파드가 정상 종료할 때 Envoy와 앱이 SIGTERM을 동시에 받고 연결이 없던 Envoy는 거의 바로 끝나요. 그 뒤 앱이 다른 서비스에 "나 내려간다"고 알리려 하면 이미 Envoy가 없어 실패해요. 그가 쓴 우회는 istio-proxy의 preStop이었어요.

preStop: exec: command: ["/bin/sh", "-c", "while [ $(netstat -plunt | grep tcp | grep -v envoy | wc -l | xargs) -ne 0 ]; do sleep 1; done"]

→ Envoy가 아닌 TCP 리스너가 하나라도 남아 있으면 1초씩 기다리는 명령이에요. 그는 istio-proxy가 다른 컨테이너의 프로세스 목록을 볼 수 없어서 리스너 수로 짐작한다고 적었어요.

(c)와 (d)에서 이 상황을 재현했어요. app은 SIGTERM을 받고 4초 동안 정리하고 proxy는 SIGTERM을 받으면 바로 끝나요. (d)는 proxy에 preStop: sleep 6만 더했어요.

그림 3. preStop이 없으면 proxy는 app보다 4초 먼저 사라졌어요.

(c)에서는 삭제 순간 app과 proxy가 같은 14.273에 SIGTERM을 받았고 proxy는 그 자리에서 끝났어요. app은 18.281까지 4초를 더 일했어요. 이 4초 동안 app이 proxy를 거쳐 밖으로 나가야 했다면 실패했을 거예요. (d)에서는 proxy가 preStop의 6초를 다 쓴 28.962에 SIGTERM을 받았고 app(26.919)보다 나중에 끝났어요.

순서는 맞췄지만 6이라는 숫자는 app의 정리 시간을 짐작한 값이에요. app이 6초보다 오래 정리하면 같은 문제가 다시 생기고 일찍 끝나면 proxy는 남은 시간을 그냥 기다려요. preStop에 쓴 시간은 파드의 유예 시간에서 빠진다는 점도 함께 계산해야 해요(67편). 로그 사이드카도 사정이 같았어요. 2023년 KEP의 Motivation은 로그 컨테이너가 먼저 멈추면 다른 컨테이너의 로그를 잃고 파드가 종료 중이라 로그 컨테이너가 다시 뜨지도 않는다고 적었어요.

재시작: Never 파드에서 죽은 사이드카는 그대로 죽는다

세 번째 불편은 덜 알려졌어요. 옛 방식의 사이드카는 파드의 restartPolicy를 그대로 따라요. Job이 흔히 쓰는 restartPolicy: Never 파드에서 사이드카가 한 번 죽으면 다시 뜨지 않아요. labs/devops/k8s-study/out/68-restart-never.txt의 never-old 파드는 app이 40초 일하는 동안 crashy 사이드카가 4초 만에 exit 1로 죽게 만든 구성이에요.

never-old phase=Failed app: restartCount=0 state=terminated(exit=0 reason=Completed msg=-) lastExit=- crashy: restartCount=0 state=terminated(exit=1 reason=Error msg=-) lastExit=-

→ crashy는 7초 시점부터 끝난 상태로 남았고 재시작 횟수는 0이었어요. app은 exit 0으로 일을 마쳤는데 파드는 Failed, kubectl get pod의 STATUS는 Error였어요. 사이드카가 앱에 보안 통신을 제공하고 있었다면 앱은 남은 30여 초 동안 그 통신 없이 돌았을 거예요.

현재 KEP-753의 Motivation이 이 경우를 적었어요. restartPolicy:Never인 Job에서 사이드카가 OOM으로 죽으면 다시 시작되지 않고 사이드카는 보통 요청량이 작아 OOM 점수 계산에서 먼저 죽을 대상이 된다는 내용이에요. 같은 파일의 never-native 파드는 같은 crashy를 네이티브 사이드카로 둔 것인데 crashy가 두 번 재시작했고 파드는 Succeeded였어요. 그 차이는 70편에서 kubelet 코드와 함께 봐요.

그림 4. 위 두 칸은 Job을 끝내려는 우회, 아래 두 칸은 시작과 종료 순서를 맞추려는 우회예요.

⚠️ postStart 순서 우회는 지금도 같은 이유로 조심해야 해요
(b)처럼 v1.37.2에서도 containers 맨 앞 컨테이너의 postStart는 다음 컨테이너 시작을 붙잡아요. 그러나 이건 구현의 순서이지 API의 약속이 아니에요. 같은 목적이면 네이티브 사이드카에 startupProbe를 다는 쪽이 공식 동작이에요. 네이티브 사이드카에서 무엇이 다음 컨테이너를 붙잡는지는 70편에서 실험해요.

4. 사이드카를 initContainers에 넣는다고? 지금 모양은 이렇게 뜬다

도입의 job-native를 보고 이렇게 물을 수 있어요. 사이드카를 이런 식으로도 쓸 수 있나요? init 컨테이너는 한 번 돌고 끝나야 다음 컨테이너로 넘어가는 자리인데, 파드가 끝날 때까지 도는 컨테이너를 거기에 넣는다고요?

답은 restartPolicy: Always에 있어요. 이 필드가 붙은 init 컨테이너는 끝나기를 기다리지 않고 "시작됐다"를 확인하면 다음 init 컨테이너로 넘어가요. labs/devops/k8s-study/out/68-init-sidecar.txt의 native-sidecar 파드는 init1, logger(사이드카), init2 순서로 initContainers를 적고 app을 containers에 둔 구성이에요.

init/init1: terminated start=2026-11-15T11:29:50Z end=2026-11-15T11:29:52Z (Completed) init/logger: running start=2026-11-15T11:29:52Z init/init2: terminated start=2026-11-15T11:29:52Z end=2026-11-15T11:29:54Z (Completed) main/app: terminated start=2026-11-15T11:29:55Z end=2026-11-15T11:30:00Z (Completed)

→ init1이 끝난 11:29:52에 logger가 시작했고 같은 초에 init2도 시작했어요. logger는 init2와 app이 도는 동안 계속 running이었어요. 사이드카가 init 순서 한가운데에 끼어 있어요. 이 파드가 끝나는 과정은 70편에서 따로 봐요.

v1.37.2 API의 필드 설명도 이 컨테이너를 사이드카라고 불러요(types.go).

this init container will be continually restarted on exit until all regular containers have terminated. Once all regular containers have completed, all init containers with restartPolicy "Always" will be shut down. This lifecycle differs from normal init containers and is often referred to as a "sidecar" container.

→ 보통 컨테이너가 모두 끝날 때까지 이 init 컨테이너는 끝나면 다시 시작되고 보통 컨테이너가 모두 끝나면 종료된다는 뜻이에요. Job이 끝나는 이유가 여기 있어요. 공식 문서도 예제의 사이드카를 일부러 initContainers 아래에 restartPolicy: Always로 적었다고 메모를 달았어요. 2024년 11월 #25908에는 "running sidecars as initContainers with restartPolicy=Always does work rather well"이라는 코멘트가 붙었어요. 8년 전 이슈에 해결 방법이 달린 셈이에요.

옛 Job을 옮길 때 바뀌는 곳은 이 정도예요.

spec: template: spec: restartPolicy: Never initContainers: # containers 에서 이쪽으로 옮긴다 - name: side image: busybox:1.37 restartPolicy: Always # 이 한 줄이 사이드카 표시 command: [sh, -c, 'trap "exit 0" TERM; while true; do sleep 1; done'] containers: - name: work image: busybox:1.37 command: [sh, -c, 'echo work; sleep 5']

왜 새 필드가 아니라 initContainers와 restartPolicy를 빌려 썼는지는 이 기능이 몇 년 멈춰 있던 이유와 이어져 있어요. 그 이야기는 69편에서 원문으로 읽어요.

5. 2017년의 제안과 2018년의 첫 KEP: 사이드카라는 표시를 붙이자

우회가 쌓이자 해법의 방향은 일찍 나왔어요. 2017년 6월 jmillikin-stripe는 #25908에서 "완료를 기다릴 컨테이너"를 지정하자는 앞선 제안과 반대로 일부 컨테이너를 사이드카로 지정하자고 했어요. 사이드카가 아닌 마지막 컨테이너가 끝나면 파드가 사이드카에 TERM을 보내자는 제안이었고 예시는 containers 안의 envoy에 sidecar: true를 붙인 모양이었어요.

📖 용어: KEP (Kubernetes Enhancement Proposal)
큰 기능을 넣기 전에 동기, 설계, 버린 대안, 알파·베타·GA 단계 계획을 적고 담당 SIG의 승인을 받는 문서예요. 사이드카는 enhancements 저장소의 추적 이슈 번호를 따라 KEP-753으로 불려요.

2018년 5월 14일 Joseph-Irving이 첫 KEP를 올렸어요(community 저장소 판, PR #2148은 2018년 11월 29일 provisional 상태로 병합). 병합된 판의 Goals는 #25908과 그 뒤 6월에 올라온 #65502를 "앱을 고치지 않고" 푸는 것이었어요. 제안은 containers 안의 컨테이너에 표시 하나를 붙이는 것이었어요.

Create a way to define containers as sidecars, this will be an additional field to the Container Spec: `sidecar: true`.

→ Container 스펙에 sidecar: true 필드를 더한다는 뜻이에요. 시작은 init 컨테이너가 끝난 뒤 사이드카가 먼저 뜨고 그다음 보통 컨테이너가 뜨는 순서였어요. 종료는 보통 컨테이너에 SIGTERM을 보내고 그것들이 모두 끝나면 사이드카에 SIGTERM을 보내는 순서였어요. preStop은 사이드카와 보통 컨테이너에 동시에 보내고 보통 컨테이너가 유예 시간 안에 끝나지 않으면 SIGKILL 뒤 사이드카에 5초나 10초의 짧은 유예를 주자고 했어요(값은 "up for debate"). Job 문제는 restartPolicy가 Always가 아닐 때 보통 컨테이너가 모두 끝나면 사이드카에 SIGTERM을 보내는 규칙으로 풀었어요.

그림 5. 시작과 종료의 순서는 지금 동작과 비슷했지만 표시를 붙이는 자리가 달랐어요.

Job 컨트롤러가 아니라 파드에서, 앱이 아니라 사이드카 쪽에 표시를 붙여 푼다는 방향은 이때 정해졌어요. 그런데 원안 자신이 남긴 메모가 있어요. Non-Goals에는 "Allowing multiple containers to run at once during the init phase. //TODO"가 있었어요. Risks에는 이 필드가 Container 스펙에 더해지는 것이라 init 컨테이너에도 붙일 수 있게 되는데 init 컨테이너는 차례로 실행되므로 그건 말이 안 된다고 적었어요. Alternatives에는 따로 된 sidecarContainers 목록과 불리언 대신 lifecycle: Sidecar 같은 값이 후보로 올라 있었어요.

메시의 프록시가 init 컨테이너의 네트워크까지 맡아야 하는 경우라면 init 단계에서도 사이드카가 돌아야 해요. 원안은 그 경우를 범위 밖에 두고 표시를 containers 안에 붙였어요. 표시를 붙이자는 데는 동의가 모였지만 어디에 붙일지는 2018년 원안부터 열려 있던 문제였어요.

📝 정리

containers에 앱과 나란히 적은 사이드카는 앱과 같은 급이에요. 작업 컨테이너가 exit 0으로 끝나도 사이드카가 돌면 파드는 Running이고 Job은 끝나지 않아요. 우리 클러스터에서 옛 방식 Job은 46초 뒤에도 0/1, 파드는 1/2 NotReady였고 사이드카를 initContainers에 restartPolicy: Always로 옮긴 Job은 12초 만에 Complete였어요.

2016년부터의 우회는 모두 사이드카 밖을 고쳤어요. 끝남 파일과 /quitquitquit은 앱 이미지와 명령을, holdApplicationUntilProxyStarts는 API가 약속하지 않은 순차 시작을, preStop 대기는 짐작한 초 수와 유예 시간을 썼어요. Never 파드에서 죽은 옛 사이드카는 다시 뜨지 않아 앱이 성공해도 파드가 Failed였어요.

그래서 2017년과 2018년의 제안은 사이드카라는 표시를 파드 API에 붙이자는 것이었어요. 문제의 자리를 Job에서 파드로 옮긴 그 결정이 다음 질문, 표시를 어디에 붙이느냐를 남겼어요.
