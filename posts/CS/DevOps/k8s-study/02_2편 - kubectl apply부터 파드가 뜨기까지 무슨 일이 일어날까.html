2편. kubectl apply부터 파드가 뜨기까지 무슨 일이 일어날까 ← 지금 이 글
3편. VM으로 실습 노드를 만들 때 네트워크를 두 개 붙이는 이유
4편. kubeadm 설치 전에 swap을 꺼야 하는 이유
5편. kubeadm init이 만드는 인증서와 kubeconfig, 정적 파드

마스터 노드에서 명령 한 줄을 쳤어요. kubectl create deployment hello --image=nginx:1.29였습니다. 명령이 끝나고 파드 목록을 보니 hello 파드는 worker3에서 Running이었고 나이(AGE)는 13초였어요. worker3에 들어가 컨테이너 목록을 열어 보니 nginx 컨테이너는 "Less than a second ago", 그러니까 만들어진 지 1초도 안 된 상태였습니다.

그 13초 동안 이 일에 관여한 프로그램들이 이벤트 목록에 이름을 남겼어요. deployment-controller, replicaset-controller, default-scheduler, kubelet 이렇게 넷입니다. 그런데 이 넷은 서로에게 한 번도 직접 요청을 보내지 않았어요. 모두 API 서버만 지켜보고 있다가 자기가 맡은 종류의 객체가 생기거나 바뀌면 움직였습니다.

1편에서는 클러스터를 켰을 때 무엇이 어디서 도는지 봤어요. 이번에는 그 프로그램들이 일을 하나 받았을 때 어떤 차례로 움직이는지 따라갑니다. 제목에는 apply라고 적었지만 실험은 kubectl create deployment로 했어요. YAML 파일을 kubectl apply로 보내도 API 서버에 Deployment가 저장된 다음부터 일어나는 일은 같습니다. 질문은 하나예요. "명령 한 줄을 친 뒤 컨테이너가 뜨기까지, 누가 무엇을 했나."

이 글에서 다룰 것
· 이벤트 목록에서 kubelet이 파드가 만들어지기도 전에 이미지를 받은 것으로 보이는 이유는 무엇일까?
· 명령 두 개를 쳤는데 etcd에 키가 여섯 개 생긴 이유는 무엇일까?
· 컨트롤러와 스케줄러는 자기 차례가 온 것을 어떻게 알까?
· worker3에서 걸린 13초는 어디에 쓰였을까?
· Service를 만들면 노드에는 무엇이 생길까?

1. 이벤트 일곱 줄은 일어난 차례대로가 아니다

실험에 쓴 명령은 세 개를 이어 붙인 한 줄이에요.

master$ kubectl create deployment hello --image=nginx:1.29 && kubectl expose deployment hello --port=80 >/dev/null && kubectl rollout status deploy/hello --timeout=120s >/dev/null deployment.apps/hello created

→ nginx:1.29 이미지로 Deployment hello를 만들고 80번 포트로 받는 Service를 붙인 뒤 롤아웃이 끝날 때까지 최대 120초를 기다리라는 뜻이에요. 뒤의 두 명령은 출력을 버려서 화면에는 첫 줄만 남았습니다.

명령이 끝난 뒤 hello에 관한 이벤트만 골라 만들어진 시각 순서로 정렬했어요.

그림 1. hello를 만들 때 남은 이벤트 일곱 줄. 둘째 줄 Pulling이 셋째 줄 파드 생성보다 위에 있다

SOURCE 열은 기록을 남긴 프로그램, REASON 열은 한 일의 종류, OBJECT 열은 그 일의 대상이에요.

📖 용어: 이벤트 (Event)
구성 요소가 "이 객체에 이런 일을 했다"고 API 서버에 남기는 짧은 기록이에요. 이벤트도 쿠버네티스 객체라서 kubectl get events로 볼 수 있고 kubectl describe pod 출력 맨 아래에 붙는 목록도 이 기록입니다.

위에서부터 읽으면 이상한 데가 있어요. 둘째 줄에서 kubelet이 파드 hello-6c444d6966-grmj4의 이미지를 받기 시작했어요(Pulling). 그런데 그 파드를 만들었다는 기록(SuccessfulCreate)은 셋째 줄에 있고 파드를 k8s-worker3에 배정했다는 기록(Scheduled)은 넷째 줄에 있습니다. 아직 만들어지지도 않았고 어느 노드로 갈지도 정해지지 않은 파드의 이미지를 worker3의 kubelet이 먼저 받을 수는 없어요.

원인은 정렬 기준에 있었습니다. 정렬에 쓴 creationTimestamp는 일이 일어난 시각이 아니라 이벤트 기록이 API 서버에 저장된 시각이에요. 게다가 초 단위까지만 남습니다. 쿠버네티스 API 라이브러리(apimachinery)의 시간 타입은 JSON으로 내보낼 때도, protobuf로 바꿀 때도 초 아래 자리를 버려요. API 문서에도 이 값이 서로 다른 작업 사이에서 일어난 순서대로 매겨진다는 보장은 없다고 적혀 있어요. 그래서 정렬 결과의 줄 순서로는 실제로 일이 일어난 차례를 알 수 없어요.

실제 차례는 "무엇이 있어야 다음 일이 가능한가"를 기준으로 다시 세워야 합니다. ReplicaSet이 있어야 파드를 만들 수 있고 파드가 있어야 노드에 배정할 수 있으며 배정이 끝나야 그 노드의 kubelet이 움직여요. 이 기준으로 다시 줄을 세우면 이렇게 됩니다.

1 deployment-controller ScalingReplicaSet ReplicaSet hello-6c444d6966 을 만듦 2 replicaset-controller SuccessfulCreate 파드 hello-6c444d6966-grmj4 를 만듦 3 default-scheduler Scheduled 그 파드를 k8s-worker3 에 배정 4 kubelet (worker3) Pulling nginx:1.29 이미지를 받기 시작 5 kubelet (worker3) Pulled 13.06초 걸려 받음 6 kubelet (worker3) Created 컨테이너 생성 7 kubelet (worker3) Started 컨테이너 시작

→ 원래 출력과 달라진 곳은 Pulling 한 줄의 자리뿐이에요. 뒤의 세 줄(Pulled, Created, Started)은 이미지를 받는 13.06초가 지난 뒤에 저장됐으니 순서가 원래 출력과 같습니다.

⚠️ 주의: 이벤트 정렬을 실행 순서로 읽지 않기
--sort-by=.metadata.creationTimestamp는 같은 초에 저장된 기록끼리는 차례를 가려 주지 못해요. 또 기록이 저장된 시각이 일이 일어난 차례와 어긋날 수도 있어요. 파드 하나가 만들어질 때는 컨트롤러, 스케줄러, kubelet의 기록이 짧은 시간 안에 연달아 저장됩니다. 원인을 찾을 때는 줄 순서를 그대로 믿지 말고 "이 일이 있어야 저 일이 가능하다"는 관계로 다시 맞춰 보세요.

아래 그림은 이 차례에 Service 쪽까지 넣어 한 장으로 그린 거예요. 남은 절에서는 그림의 번호를 하나씩 따라갑니다.

그림 2. ①~⑤는 API 서버에 기록만 늘어나는 단계다. 컨테이너는 ⑥부터 worker3에서 생긴다

2. API 서버를 거친 요청만 etcd에 남는다

그림 2의 ①부터 볼게요. kubectl은 클러스터 안에서 아무것도 직접 만들지 않아요. kubeconfig에 적힌 주소로 API 서버에 HTTPS 요청을 보낼 뿐입니다. 만약 아무 프로그램이나 etcd에 바로 쓸 수 있다면 누가 보낸 요청인지, 그럴 권한이 있는지, 내용이 올바른 Deployment인지 확인할 곳이 없어져요. 쿠버네티스 문서에도 etcd에 접근할 수 있으면 클러스터 root 권한이 있는 것과 같으니 가능하면 API 서버만 접근하게 하라고 적혀 있어요.

그래서 요청은 API 서버 안에서 여러 단계를 거쳐요. 먼저 인증으로 누가 보냈는지 확인하고 실패하면 401로 거절합니다. 다음은 인가예요. 그 사용자에게 이 일을 할 권한이 있는지 보고 모든 인가 모듈이 거부하면 403으로 거절합니다. 그다음이 어드미션 컨트롤이에요.

📖 용어: 어드미션 컨트롤 (admission control)
인증과 인가를 통과한 요청이 저장되기 전에 한 번 더 거치는 모듈들이에요. 요청 내용을 고치거나 거절할 수 있고 하나라도 거절하면 요청은 그 자리에서 실패합니다. 객체를 만들고 고치고 지우는 요청에만 작동하고 읽기만 하는 요청에는 작동하지 않아요.

어드미션을 모두 통과하면 그 객체 종류의 검증 규칙으로 내용을 확인하고 그다음에야 저장합니다(②). 저장된 결과는 etcd에서 직접 볼 수 있어요. 마스터에 떠 있는 etcd 파드 안에서 etcdctl로 /registry 아래의 키 가운데 hello가 들어간 것만 뽑았습니다. 이벤트 키는 뺐어요.

그림 3. 명령은 create와 expose 두 개였는데 etcd에는 hello 키가 여섯 개 생겼다

제가 친 명령은 두 개인데 키는 여섯 개예요. 누가 만들라고 요청했는지로 나눠 보면 이렇습니다.

/registry/deployments/default/hello kubectl create deployment (나) /registry/services/specs/default/hello kubectl expose (나) /registry/replicasets/default/hello-6c444d6966 deployment-controller /registry/pods/default/hello-6c444d6966-grmj4 replicaset-controller /registry/endpointslices/default/hello-bjc56 EndpointSlice 컨트롤러 /registry/services/endpoints/default/hello Endpoints 컨트롤러

→ 위의 두 줄만 제가 요청한 것이고 아래 네 줄은 kube-controller-manager 안의 컨트롤러들이 API 서버에 요청해서 생긴 거예요. 마지막 줄의 Endpoints는 v1.33부터 deprecated(앞으로 쓰지 말라는 표시)가 붙은 옛 API인데 지금도 EndpointSlice와 함께 만들어지고 있었습니다.

여섯 키를 etcd에 쓴 것은 모두 API 서버였지만 쓰라고 요청한 쪽은 대부분 제가 아니었어요. 나머지 넷을 누가 어떻게 알고 만들었는지는 다음 절에서 이야기합니다.

⚠️ 주의: etcd를 직접 연 것은 들여다보려고 한 일이에요
위에서는 etcd 파드 안에서 etcd 서버 인증서(server.crt)로 접속했어요. 문서 표현대로 etcd 접근은 클러스터 root 권한과 같습니다. 객체를 만들고 고치는 일은 언제나 kubectl이나 API를 거쳐야 해요. etcd에 직접 쓰면 이 절에서 본 인증, 인가, 어드미션, 검증을 하나도 거치지 않습니다.

3. 컨트롤러 둘은 지켜보다가 객체를 하나씩 더 썼다

Deployment hello가 저장된 직후로 돌아가 볼게요. ReplicaSet을 만들어야 하는 deployment-controller는 새 Deployment가 생긴 것을 어떻게 알까요? kubectl은 저장 요청을 보내고 끝났어요. 누구에게도 "새 Deployment가 있다"고 알리지 않았습니다. 알려 주는 쪽이 없으니 변화를 알고 싶은 쪽이 API 서버에 미리 요청을 걸어 두어야 합니다. 이 요청을 워치라고 불러요.

📖 용어: 워치 (watch)
클라이언트가 API 서버에서 목록을 한 번 받은 뒤 "이후 바뀌는 것을 계속 보내 달라"고 걸어 두는 요청이에요. 객체가 생기거나 바뀌거나 지워지면 API 서버가 그 변화를 보내 줍니다. 어디까지 받았는지는 객체마다 붙어 있는 resourceVersion으로 맞춰요.

kube-controller-manager 안에서는 여러 컨트롤러가 함께 돌아요. 문서의 표현을 빌리면 각 컨트롤러는 적어도 한 종류의 객체를 추적하고 현재 상태를 원하는 상태에 가깝게 맞추려고 합니다. 이번 일에서는 그중 두 개가 차례로 움직였어요.

③ deployment-controller는 hello에 맞는 ReplicaSet이 없는 것을 보고 hello-6c444d6966을 만들었어요. 이 이름은 Deployment 이름 뒤에 해시를 붙인 형식이고 해시는 그 ReplicaSet의 pod-template-hash 라벨 값과 같습니다. 그림 1의 "Scaled up replica set hello-6c444d6966 from 0 to 1"이 바로 이 기록이에요.

④ replicaset-controller는 새 ReplicaSet을 보고 원하는 파드는 1개인데 지금은 0개라는 차이를 확인했어요. 그래서 ReplicaSet 이름 뒤에 다섯 글자를 붙인 파드 hello-6c444d6966-grmj4를 만들었습니다. 이 순간에는 파드 객체에 어느 노드에서 돌지가 아직 적혀 있지 않아요.

두 컨트롤러 모두 컨테이너는 하나도 띄우지 않았습니다. 문서에서도 Job 컨트롤러를 예로 들어 컨트롤러는 파드나 컨테이너를 직접 실행하지 않고 API 서버에 파드를 만들거나 지워 달라고 요청한다고 설명해요. 컨트롤러가 한 일은 API 서버에 객체를 하나 더 써 넣은 것이 전부였고 다음 일은 그 객체를 워치하던 쪽이 알아서 이어받았어요. 등장한 구성 요소를 모두 모아 그리면 선이 API 서버로만 이어집니다.

그림 4. 구성 요소끼리 서로 부르는 선은 없다. 모두 API 서버를 워치하고 API 서버에 쓴다

4. 스케줄러는 nodeName 한 칸을 채운다

⑤ 노드가 비어 있는 파드는 kube-scheduler가 맡아요. 스케줄러는 노드가 정해지지 않은 새 파드를 워치하다가 하나가 보이면 그 파드를 돌릴 노드를 고릅니다. 고르는 방법은 두 단계예요. 먼저 필터링으로 그 파드를 돌릴 수 있는 노드만 남깁니다. 그다음 남은 노드에 점수를 매겨 가장 높은 노드를 고릅니다. 점수가 같은 노드가 여럿이면 그중 하나를 무작위로 골라요.

이 클러스터에서는 마스터가 필터링에서 빠집니다. kubeadm init이 마스터에 node-role.kubernetes.io/control-plane:NoSchedule taint를 붙여 두었고 hello 파드에는 그 taint를 허용하는 설정(toleration)이 없기 때문이에요. 이 taint는 5편에서 다룹니다. 그러면 워커 세 대가 남는데 그중 왜 worker3이었는지는 점수 기록을 남기지 않아서 확인하지 않았어요.

스케줄러는 고른 결과를 API 서버에 알립니다. 문서에서는 이 과정을 바인딩이라고 불러요.

📖 용어: 바인딩 (binding)
파드를 특정 노드에 배정하는 일이에요. 스케줄러가 결정을 API 서버에 알리면 파드의 spec.nodeName에 노드 이름이 들어갑니다. 파드는 일생에 한 번만 스케줄되고 배정된 노드에서 끝날 때까지 돌아요. 도중에 다른 노드로 옮겨 가지 않습니다.

배정이 끝난 뒤의 파드는 이렇게 보여요.

master$ kubectl get pod -l app=hello -o wide NAME READY STATUS RESTARTS AGE IP NODE NOMINATED NODE READINESS GATES hello-6c444d6966-grmj4 1/1 Running 0 13s 10.244.100.193 k8s-worker3 <none> <none>

→ NODE 열의 k8s-worker3는 스케줄러가 채운 nodeName이에요. IP 10.244.100.193은 스케줄러가 준 것이 아니라 worker3에서 파드를 준비할 때 붙은 주소입니다. 이 출력을 볼 때 파드의 나이는 13초였어요.

스케줄러도 컨테이너를 띄우지 않아요. 파드 객체의 빈칸 하나를 채우고 끝납니다. 실제 실행은 그 칸에 자기 이름이 적힌 노드의 kubelet이 맡아요.

5. worker3의 13초: 샌드박스가 먼저, 이미지는 그다음

⑥ worker3의 kubelet도 API 서버를 워치하고 있었어요. kubelet은 주로 API 서버에서 받은 파드 명세대로 컨테이너가 돌고 있게 만드는 노드 에이전트입니다. hello-6c444d6966-grmj4의 nodeName에 k8s-worker3가 들어가자 이 파드는 worker3 kubelet의 몫이 됐어요. 다만 kubelet이 컨테이너를 직접 만들지는 않습니다. 노드의 컨테이너 런타임인 containerd에게 CRI로 요청해요.

📖 용어: CRI (Container Runtime Interface)
kubelet과 컨테이너 런타임이 주고받는 gRPC 규약이에요. kubelet이 클라이언트가 되어 샌드박스 만들기, 이미지 받기, 컨테이너 만들고 시작하기 같은 요청을 보냅니다. 이 규약을 지키는 런타임이면 containerd가 아니어도 kubelet과 함께 쓸 수 있어요.

⑦ 파드 생명주기 문서에 따르면 kubelet은 런타임과 함께 먼저 파드 샌드박스를 만들고 네트워크를 설정해요. 이미지를 받고 컨테이너를 만드는 일은 그다음입니다.

📖 용어: 파드 샌드박스 (pod sandbox)
파드 안의 컨테이너들이 함께 쓰는 실행 환경이에요. 런타임은 샌드박스를 만들 때 파드의 네트워크도 설정합니다. 컨테이너는 이렇게 만들어진 샌드박스 안에 들어가요. crictl pods가 보여 주는 목록이 런타임 쪽의 샌드박스입니다.

파드 IP도 이 단계에서 정해집니다. 쿠버네티스 1.24에서 kubelet의 CNI 관련 옵션이 없어졌고 지금은 컨테이너 런타임이 CNI 플러그인을 불러 쓰도록 설정해요. 이 클러스터의 CNI는 Calico라서 containerd가 샌드박스를 만들 때 Calico의 CNI 플러그인이 10.244.100.193을 붙였습니다. 파드 IP는 이미지를 받기도 전에, 샌드박스를 만들 때 이미 정해져요. Calico가 그 주소를 어떻게 고르고 다른 노드까지 어떻게 보내는지는 6편에서 다룹니다.

⑧ 그다음이 이미지예요. worker3에서 런타임에 직접 물어보면 이 차례를 시각으로 확인할 수 있어요. crictl은 CRI로 런타임에 직접 묻는 명령줄 도구예요.

worker3$ sudo crictl pods --name hello POD ID CREATED STATE NAME NAMESPACE ATTEMPT RUNTIME 8515f66a503b7 13 seconds ago Ready hello-6c444d6966-grmj4 default 0 (default) worker3$ sudo crictl ps --name nginx CONTAINER IMAGE CREATED STATE NAME ATTEMPT POD ID POD NAMESPACE dc07c0539df83 8524ce6c9242e Less than a second ago Running nginx 0 8515f66a503b7 hello-6c444d6966-grmj4 default

→ 같은 POD ID(8515f66a503b7)인데 샌드박스는 13초 전에 만들어졌고 nginx 컨테이너는 만들어진 지 1초도 안 됐다고 나와요. 두 시각이 13초쯤 벌어져 있고 이벤트에 찍힌 이미지 pull 시간이 13.06초입니다.

파드가 만들어진 뒤 컨테이너가 뜨기까지 걸린 시간은 거의 다 이미지 pull이었어요. 이벤트 메시지에 따르면 nginx:1.29 이미지는 61310317 bytes였고 받는 데 13.06초가 걸렸습니다. 받은 뒤 컨테이너를 만들고(Created) 시작하는(Started) 일은 바로 이어졌어요.

그림 5. 샌드박스와 IP가 먼저 생기고 컨테이너는 13.06초 동안 이미지를 받은 뒤에야 생겼다

이 13초는 처음 한 번만 드는 시간일 가능성이 커요. 이미지 태그가 latest가 아니고(여기서는 1.29) imagePullPolicy를 따로 적지 않으면 정책은 IfNotPresent로 정해집니다. 노드에 이미 있는 이미지는 다시 받지 않는다는 뜻이에요. 같은 노드에서 다시 띄울 때 얼마나 빨라지는지는 이번에 재 보지 않았습니다.

⚠️ 주의: 노드에 crictl이 처음부터 있지는 않았어요
처음에는 노드에 kubeadm, kubelet, kubectl 패키지만 설치했어요. 그 상태로 노드에서 crictl을 실행하자 sudo: crictl: command not found가 나왔습니다. kubeadm 패키지를 설치해도 crictl은 같이 설치되지 않았어요. crictl은 cri-tools라는 별도 패키지에 들어 있어서 노드 준비 스크립트가 이 패키지도 설치하도록 고쳤어요. 노드 준비 과정은 4편에서 다룹니다.

6. Service는 노드마다 iptables 규칙이 된다

파드는 떴지만 문제가 하나 남아요. 10.244.100.193은 이 파드 하나의 주소라서 파드가 지워지고 새로 만들어지면 새 파드는 다른 주소를 받을 수 있습니다. 문서에도 파드는 원하는 상태에 맞춰 만들어지고 지워지는 자원이라 어느 시점에 떠 있는 파드 집합이 조금 뒤에는 달라질 수 있다고 적혀 있어요. 그래서 명령 첫 줄에서 kubectl expose로 Service를 함께 만들었습니다. 그림 2의 오른쪽 아래, 따로 진행되는 부분이에요.

Service가 저장되면 컨트롤 플레인이 셀렉터에 맞는 파드를 찾아 EndpointSlice를 자동으로 만들어요. 2절에서 본 /registry/endpointslices/default/hello-bjc56이 그 객체예요.

📖 용어: EndpointSlice
Service 하나에 지금 연결된 파드의 주소와 포트를 적어 두는 객체예요. 파드가 늘거나 줄면 컨트롤 플레인이 이 목록을 고칩니다. Service 이름은 kubernetes.io/service-name 라벨에 적혀 있어요.

마지막으로 움직이는 것은 kube-proxy예요. 1편에서 본 대로 노드마다 하나씩 떠 있고 각자 API 서버에서 Service와 EndpointSlice를 워치하다가 자기 노드의 패킷 전달 규칙을 고칩니다. worker3의 nat 테이블을 보면 hello를 위한 규칙이 들어 있어요.

worker3$ sudo iptables -t nat -S KUBE-SERVICES 2>/dev/null | grep default/hello -A KUBE-SERVICES -d 10.111.63.251/32 -p tcp -m comment --comment "default/hello cluster IP" -m tcp --dport 80 -j KUBE-SVC-STDNOFAI3EEZDIVA master$ kubectl -n kube-system logs ds/kube-proxy 2>/dev/null | grep -m1 Proxier I1104 12:19:36.991843 1 server_linux.go:144] "Using iptables Proxier"

→ 목적지가 10.111.63.251이고 TCP 80번인 패킷은 KUBE-SVC-STDNOFAI3EEZDIVA 체인으로 넘기라는 규칙이에요. 10.111.63.251이 Service hello의 클러스터 IP입니다. 아래 로그 줄은 kube-proxy가 iptables 모드로 동작한다는 뜻이에요.

이 한 줄이 끝은 아니에요. 문서에 따르면 kube-proxy는 Service마다 규칙 묶음을 만들고 그 아래에 엔드포인트(여기서는 파드)마다 규칙을 하나씩 더 둡니다. 엔드포인트 규칙이 패킷의 목적지 주소를 파드 IP로 바꾸는 NAT, 즉 DNAT를 해요. 이번에는 KUBE-SVC 체인 아래까지는 출력하지 않았습니다. 문서 설명대로라면 hello의 엔드포인트는 파드 하나뿐이니 목적지가 10.244.100.193으로 바뀌겠지만 이 부분은 출력으로 확인하지 않았어요.

kube-proxy의 기본 모드는 버전에 따라 달라요. 문서에는 쿠버네티스 1.37의 기본값이 iptables로 적혀 있고 앞으로 나올 버전에서 nftables로 바꿀 예정이라고 나와 있어요. 업그레이드하면서 모드가 바뀌는 일을 피하려면 설정에 모드를 명시하라는 권고도 있어요. kube-proxy는 패킷을 직접 전달하지 않아요. 커널 netfilter에 규칙을 넣어 두면 패킷의 목적지는 커널이 바꿉니다.

💡 실무에서는: 파드가 안 뜨면 그림 2의 몇 번에서 멈췄는지부터 봐요
• Deployment는 있는데 파드가 없다: ③④ 컨트롤러 단계예요. kubectl describe deploy와 kubectl describe rs의 이벤트를 봅니다.
• 파드가 Pending이고 NODE가 <none>이다: ⑤ 스케줄러가 노드를 못 고른 거예요. kubectl describe pod 아래 이벤트에 이유가 남습니다.
• NODE는 정해졌는데 Running이 아니다: ⑥~⑧ 그 노드의 kubelet 단계예요. Pulling과 Pulled 사이가 길면 아직 이미지를 받는 중입니다.
• Running인데 Service로 닿지 않는다: kubectl get endpointslices -l kubernetes.io/service-name=hello로 파드 주소가 목록에 들어 있는지 봐요.
✍️ 오늘의 요약
명령 한 줄 뒤에서 움직인 프로그램들은 서로를 부르지 않았어요. 각자 API 서버를 워치하다가 자기 몫의 객체가 생기면 다음 객체를 써 넣었을 뿐입니다.

Deployment, ReplicaSet, 파드, nodeName까지는 API 서버를 거쳐 etcd에 기록이 늘어나는 과정이었고 컨테이너는 worker3의 kubelet이 containerd에 샌드박스와 컨테이너를 요청하면서 처음 생겼어요. 그사이 걸린 시간의 대부분은 이미지 pull 13.06초였습니다. 쿠버네티스에 배포한다는 것은 API 서버에 원하는 상태를 적는 일이고 실행은 그 기록을 워치하는 구성 요소들이 나눠 맡습니다.
