45편에서 CRI는 kubelet이 유닉스 소켓 위에서 gRPC로 런타임을 부르는 경계였어요. dockershim을 deprecated로 바꾼 PR #94624에도 kubelet이 grpc로 부르는 별도 프로세스로 나누는 것이 맞다고 적혀 있었어요. 그런데 쿠버네티스의 다른 연결을 보면 사정이 달라요. kubectl은 API 서버에 HTTPS로 REST 요청을 보내요. 흔히 "API 서버는 kubectl과는 REST로, 스케줄러나 컨트롤러와는 gRPC로 통신한다"고 설명하는데 우리 클러스터에서 확인해 보니 스케줄러와 컨트롤러 매니저도 kubectl과 같은 6443 포트에 HTTPS로 붙었어요. 다른 점은 요청 본문의 형식이 JSON이 아니라 protobuf라는 것뿐이었어요. gRPC로 오가는 연결은 API 서버와 etcd 사이, kubelet과 containerd 사이 둘이었어요.

그 결과를 보고 제가 물은 것은 "왜 얘네들은 gRPC 골랐는지 조사 가능해?"였어요. 그리고 "단순히 빠르고 편하다 말고, 그게 그렇게 큰 오버헤드를 주나? 그때는 gRPC 많이 쓰던 때가 아니었는데"라고 덧붙였어요. 나중에 etcd가 리더의 기록을 멤버에게 복제하는 그림을 보면서는 "이런 브로드캐스트 때문이라도 gRPC가 잘 어울렸을지도"라고도 했어요. 이번 글은 이 세 질문의 답을 2015~2016년의 이슈, 설계 문서, 블로그 원문과 우리 클러스터의 메트릭으로 찾아가요.

이 글에서 다룰 것
· 우리 클러스터에서 gRPC로 오가는 연결은 어디이고 나머지는 무엇으로 오갈까?
· CRI는 왜 gRPC를 골랐고 "빠르다"는 이유는 얼마나 컸을까?
· etcd는 v3에서 왜 gRPC로 바꿨고 멤버끼리의 복제도 gRPC일까?
· 쿠버네티스 API는 왜 gRPC로 가지 않고 REST에 protobuf만 얹었을까?
· gRPC가 1.0도 되기 전에 고른 대가는 무엇이었을까?

1. 우리 클러스터에서 gRPC로 오가는 연결은 etcd와 CRI 둘이었다

먼저 스케줄러와 컨트롤러 매니저가 API 서버에 무엇으로 붙는지 봤어요. 두 바이너리의 도움말에서 API 요청 형식의 기본값을 찾고 각자 쓰는 kubeconfig의 서버 주소를 읽은 뒤 마스터에서 6443 포트에 붙은 연결을 프로세스별로 셌어요.

그림 1. 스케줄러와 컨트롤러 매니저도 kubectl과 같은 https://…:6443에 붙고 본문 형식의 기본값만 protobuf다

두 구성 요소의 --kube-api-content-type 기본값은 application/vnd.kubernetes.protobuf였고 kubeconfig의 서버 주소는 둘 다 https://192.168.104.1:6443이었어요. kubectl, kubelet, kube-proxy와 같은 포트예요. 같은 REST 경로에 Accept 헤더만 protobuf로 바꿔 요청하자 API 서버는 k8s와 0x00으로 시작하는 응답을 줬어요. 22편에서 etcd 안의 Deployment 값이 이 4바이트로 시작하는 것을 봤는데 같은 봉투 형식이에요. kubelet과 kube-proxy도 실제로 적용된 설정(/configz)을 보면 contentType이 protobuf였어요(46-client-content-types.txt).

📖 용어: gRPC
Google이 공개한 RPC 프레임워크예요. .proto 파일에 서비스와 메시지를 적으면 서버 뼈대와 클라이언트 코드가 만들어지고 둘은 HTTP/2 위에서 protobuf 메시지를 주고받아요. gRPC의 HTTP/2 규약에 따르면 요청 경로는 /서비스이름/메서드이름이고 content-type은 application/grpc로 시작해요.

그다음 HTTP/2와 gRPC를 구분해 봤어요. client-go는 HTTP/2를 써요. client-go가 쓰는 apimachinery의 SetTransportDefaults는 DISABLE_HTTP2 환경 변수가 없으면 HTTP/2를 설정해요. 그래서 "HTTP/2로 붙으니 gRPC겠지"라고 착각하기 쉬워요. worker1에서 익명으로 API 서버의 /version을 불러 보면 이래요.

그림 2. API 서버는 HTTP/2로 JSON을 주고 etcd의 2379에는 kube-apiserver만 gRPC로 붙어 Range·Txn·Watch를 부른다

API 서버는 TLS 협상(ALPN)에서 h2를 받아들였고 HTTP/2 200에 application/json으로 답했어요. HTTP/2 위의 REST예요. 반면 etcd의 메트릭에는 서비스와 메서드 이름별로 처리한 gRPC 호출 수가 쌓여 있었어요. 이 etcd 프로세스가 21:58:42에 뜬 뒤 약 15분 동안 etcdserverpb.KV/Range가 9,644번, Txn이 2,187번 처리됐고 Watch 스트림은 86개가 열려 1개만 닫혔어요. 2379로 연결을 연 프로세스는 kube-apiserver 하나뿐이었고 연결은 93개였어요. 노드에서 런타임을 부르는 쪽은 45편에서 본 그대로 kubelet이 containerd.sock으로 CRI gRPC를 불러요. crictl version의 RuntimeApiVersion: v1이 그 CRI 버전이에요.

📖 용어: ALPN
TLS 연결을 맺을 때 클라이언트와 서버가 그 위에서 쓸 프로토콜(h2 또는 http/1.1)을 함께 정하는 확장이에요. curl의 "ALPN: server accepted h2"는 서버가 HTTP/2로 대화하기로 했다는 뜻이에요. gRPC도 HTTP/2를 쓰지만 HTTP/2라고 해서 모두 gRPC는 아니에요.

정리하면 쿠버네티스의 주요 연결은 이래요.

구성 요소가 API 서버에 붙는 연결은 모두 REST였고 구성 요소 사이 연결 중 gRPC는 쿠버네티스가 바깥 저장소(etcd)와 바깥 런타임(CRI)에 붙는 두 곳이었어요. 이제 그 두 곳이 왜 gRPC를 골랐는지 차례로 봐요.

2. CRI가 gRPC를 고른 이유는 속도보다 다른 팀이 구현할 계약이었다

45편에서 본 이슈 #13768(2015-09-09)이 출발점이에요. 런타임을 kubelet 밖의 서버로 빼자는 제안에 rkt 연동을 맡던 yifan-gu가 다음 날 gRPC를 쓰자고 댓글을 달았어요. 이유는 네 가지였어요.

Besides, i would suggest using grpc as - No encoding/decoding codes needed to be written. - It is supposed to be faster than json (though currently it's not :( ) - We can get client bindings for free. - Server interfaces are generated as well. Each runtime only needs to implement them. (이슈 #13768, yifan-gu, 2015-09-10)

→ 인코딩·디코딩 코드를 직접 짤 필요가 없고 클라이언트 코드가 공짜로 생기며 서버 인터페이스도 생성되니 런타임은 그걸 구현하기만 하면 된다는 뜻이에요. 속도는 둘째 줄에 있는데 바로 "지금은 아니다"라고 단서를 달았어요. 그 단서에 링크된 grpc-go 이슈 #89는 성능 벤치마크와 최적화를 다루는 이슈였고 2016년 9월에야 닫혔어요.

같은 이유는 뒤에 나온 Client/Server container runtime 설계 문서에 그대로 옮겨졌어요. 문서는 API가 protobuf와 gRPC를 쓰는 이점으로 "Perform faster than json", "Get client bindings for free: gRPC supports ten languages", "No encoding/decoding codes needed", "Manage api interfaces easily: server and client interfaces are generated automatically"를 들어요. 그런데 CRI 자체를 정의한 CRI 설계 문서의 Non-Goals에는 "improving Kubelet's efficiency or performance"가 들어 있어요. kubelet의 효율과 성능을 높이는 것은 CRI의 목표가 아니었다는 뜻이에요.

📖 용어: IDL과 코드 생성
IDL(인터페이스 정의 언어)은 서비스가 받는 요청과 돌려주는 응답을 언어와 상관없이 적는 형식이에요. gRPC에서는 .proto 파일이 IDL이고 protoc 같은 도구가 Go, Java, C++ 같은 언어별 클라이언트 코드(stub)와 서버 인터페이스를 만들어 줘요. CRI의 api.proto가 이 파일이에요.

오히려 클라이언트·서버로 나누면 느려진다는 것도 다들 알고 있었어요. 같은 이슈에서 smarterclayton은 "I see some significant downsides to client/server, including more hops into the container for exec/attach/portforward scenarios."라고 하면서 자기라면 당분간 런타임을 kubelet에 컴파일해 넣겠다고 했어요. dchen1107은 "inefficiency caused by client/server runtime is known"이라고 답하면서 모든 런타임을 이 방식으로 옮길 계획은 아니고 당장의 후보는 hyper 하나라고 덧붙였어요. 비효율을 알면서도 쿠버네티스 밖에서 만드는 런타임을 받을 길을 열어 두려 한 거예요. 그 길은 1.7에서 CRI가 유일한 연동 방법이 되면서 모든 런타임의 길이 됐어요(45편). 당시 논의에서 gRPC의 이점으로 강조한 것은 쿠버네티스 밖의 팀이 구현할 인터페이스와 클라이언트·서버 코드 생성이었어요. 속도에 대한 기대도 있었지만 그때는 아직 충족되지 않았다고 적었어요. 45편에서 본 대로 그 계약 덕분에 containerd와 CRI-O가 kubelet 코드를 건드리지 않고 런타임이 될 수 있었어요.

exec·attach·port-forward의 바이트는 gRPC로 보내지 않았다

계약에 gRPC를 쓰기로 한 뒤에도 모든 것을 gRPC로 보내지는 않았어요. 위 설계 문서 초안의 Exec은 rpc Exec(stream ExecRequest) returns (stream ExecResponse), 즉 양방향 gRPC 스트림이었어요. 2016년 여름 이슈 #29579에서 이 부분을 다시 논의했는데 smarterclayton은 exec 하나에 스트림이 다섯 개까지 필요하다고 하면서 "I think grpc may not be the right solution for attach, exec, and portforward, and we may prefer to continue down our current path where we have good go support for this problem already."라고 했어요. kubelet이 네트워크 대역폭을 다 쓰면 안 되니 kubelet은 URL만 넘기고 API 서버가 그 주소에 직접 붙는 흐름도 제안했어요. CRI를 맡은 yujuhong도 "We are not committed to grpc if exec, attach, and portforward can't be supported easily."라고 답했어요. 이 이슈가 가리킨 요약 문서는 Google 문서라서 열어 보지 못했어요.

지금의 CRI가 그 결론이에요. cri-api v0.37.2의 api.proto에서 Exec의 설명은 "Exec prepares a streaming endpoint to execute a command in the container."이고 응답 ExecResponse에는 url 필드 하나가 있으며 주석은 "Fully qualified URL of the exec streaming server."예요. gRPC 호출은 스트리밍 서버의 주소만 받아 오고 터미널 바이트는 그 서버로 따로 흘러요. worker1의 containerd 설정과 열린 포트를 보면 그 서버가 보여요.

그림 3. containerd는 CRI gRPC와 별도로 127.0.0.1의 임의 포트에 스트리밍 서버를 열어 두었다

stream_server_address = '127.0.0.1', stream_server_port = '0'이고 실제로 containerd는 127.0.0.1:33287을 열고 있었어요. 포트 0은 운영체제가 빈 포트를 고르게 하는 값이에요. 이 서버는 노드 안에서만 닿으니 API 서버가 kubelet의 10250 포트(19편)로 보낸 exec 요청은 kubelet을 거쳐 이 서버로 이어지는 것으로 보여요. 그림 3 아래쪽의 유닉스 소켓 두 개는 반대 방향의 gRPC예요. kubelet이 서버가 되어 장치 플러그인의 등록을 받고(장치 플러그인 문서의 "The kubelet exports a Registration gRPC service") 사용 중인 장치 정보를 알려 주는 pod-resources 서비스를 열어요.

그림 4. CRI의 계약과 코드 생성은 gRPC가 맡고 exec 바이트는 HTTP 스트림으로 kubelet을 거쳐 containerd의 스트리밍 서버로 간다

3. etcd는 v3에서 watch와 lease를 위해 gRPC로 바꿨고 멤버끼리 복제는 HTTP로 남았다

etcd v3 API를 설계한 v3.0.0의 RFC 문서는 "The etcd v3 API is designed to give users a more efficient and cleaner abstraction compared to etcd v2."로 시작해요. 설계 항목에는 이런 줄들이 있어요.

4. Replace TTL key with Lease - more efficient/ low cost keep alive 6. Support efficient watching with multiple ranges 7. RPC API supports the completed set of APIs. - more efficient than JSON/HTTP 8. HTTP API supports a subset of APIs. - easy for people to try out etcd (etcd v3.0.0 Documentation/rfc/v3api.md 발췌)

→ v2의 키마다 붙던 TTL을 lease로 묶어 keep-alive 비용을 줄이고 여러 키 범위를 효율적으로 watch하며 전체 기능은 JSON/HTTP보다 효율적인 RPC API로 주고 HTTP API는 일부만 남겨 써 보기 쉽게 하겠다는 뜻이에요. 여기서 말하는 RPC API가 rpc.proto에 정의된 gRPC 서비스(KV, Watch, Lease 등)예요. 2015년 12월 etcd 엔지니어가 쓴 Gopher Academy 글은 "etcd v2.0 uses Protocol Buffer but does not support gRPC."와 "etcd v3+ uses gRPC with Protocol Buffer for v3 API."를 나란히 적고 HTTP/2의 장점을 "HTTP/2 can have multiple requests over one single TCP connection and still process them asynchronously"라고 설명해요. 요청 여러 개를 TCP 연결 하나에 동시에 실을 수 있다는 뜻이에요.

CoreOS가 gRPC를 고른 이유를 직접 밝힌 글도 있어요. 2016년 5월 grpc.io 블로그의 CoreOS 기고는 etcd와 rkt를 gRPC의 "early adopters"라고 소개하고 이렇게 적어요. "One of the key reasons CoreOS chose gRPC is because it uses HTTP/2, enabling applications to present both a HTTP 1.1 REST/JSON API and an efficient gRPC interface on a single TCP port (available for Go)." 포트 하나로 REST/JSON과 효율적인 gRPC를 함께 낼 수 있다는 점이 핵심 이유였다는 뜻이에요. 우리 etcd도 그래요. 그림 2의 마지막 두 줄에서 같은 2379 포트에 /v3/kv/range를 JSON으로 POST하자 application/json 응답이 왔어요.

📖 용어: grpc-gateway
.proto에 적은 HTTP 매핑을 보고 REST/JSON 요청을 gRPC 호출로 바꿔 주는 도구예요. etcd v3.7.0의 rpc.proto에는 Range에 post: "/v3/kv/range" 같은 매핑이 붙어 있어서 curl로도 etcd를 부를 수 있어요. 키와 값은 base64로 오가요.

모든 메서드가 JSON으로 열려 있지는 않아요. 그림 2의 etcd 메트릭에 RangeStream이 357번 찍혀 있었는데 v3.7.0의 rpc.proto는 이 메서드를 "This RPC is intentionally gRPC-only and does not provide a grpc-gateway REST mapping, because streaming chunked responses are not a good fit for standard JSON/REST semantics."라고 설명해요. 응답을 조각조각 흘려보내는 스트림은 일반 REST/JSON 모양에 맞지 않아서 일부러 gRPC로만 열었다는 뜻이에요.

📖 용어: 단항 호출과 스트림 호출
gRPC 호출은 요청 하나에 응답 하나를 받는 단항(unary) 호출과 한쪽이나 양쪽이 메시지를 계속 흘려보내는 스트림 호출로 나뉘어요. etcd의 Range·Txn은 단항, RangeStream은 서버 쪽 스트림, Watch와 LeaseKeepAlive는 양방향 스트림이에요(그림 2의 unary, server_stream).

"브로드캐스트" 질문의 답: 복제는 HTTP, 구독은 gRPC 스트림, 퍼뜨리기는 API 서버

제가 "브로드캐스트 때문이라도 gRPC가 잘 어울렸을지도"라고 한 것은 리더가 기록을 멤버들에게 복제하는 그림을 보면서였어요. 그런데 멤버끼리의 Raft 복제는 gRPC가 아니에요. etcd v3.7.0의 rafthttp 패키지 첫 줄은 "Package rafthttp implements HTTP transportation layer for raft pkg."예요. 멤버 사이 2380 포트는 etcd가 직접 구현한 HTTP 전송을 써요. 2015년 Gopher Academy 글에는 모든 etcd RPC를 gRPC로 바꾸는 작업을 하고 있다고 적혀 있었는데 v3.7.0에서도 멤버 사이 전송은 rafthttp에 남아 있어요. 우리 etcd는 멤버가 하나라 2380을 열어만 두고 맺어진 연결은 0개였어요. 복제 자체는 48편에서 다뤄요.

gRPC 스트림이 들어맞는 곳은 클라이언트 쪽 watch예요. v3.7.0 rpc.proto는 Watch를 "Both input and output are streams; the input stream is for creating and canceling watchers and the output stream sends events. One watch RPC can watch on multiple key ranges, streaming events for several watches at once."라고 설명해요. 스트림 하나로 watch를 여러 개 만들고 지우며 여러 watch의 이벤트를 한꺼번에 받는다는 뜻이에요. 서버 쪽 구현도 v3rpc/watch.go의 watchServer.Watch(stream pb.Watch_WatchServer)가 이 스트림을 받아요.

그렇다고 etcd가 쿠버네티스의 모든 구독자에게 변경을 퍼뜨리지는 않았어요. 같은 시각 API 서버에 걸린 WATCH 요청은 371개였는데 etcd 안의 watch는 85개였고 그 85개는 모두 kube-apiserver가 연 것이었어요. API 서버가 watch 캐시를 둔 리소스 종류는 84개로 etcd의 watch 수와 거의 같았어요. API 서버가 리소스마다 etcd를 대략 하나씩 지켜보고 받은 변경을 수백 개의 HTTP watch로 나눠 주는 구조로 보여요(watch 캐시는 39편). 이 마지막 구간은 gRPC가 아니에요. API 개념 문서에 따르면 watch 요청에 API 서버는 "a stream of changes"로 답하고 문서의 예시 응답은 Transfer-Encoding: chunked인 HTTP 응답이에요.

그림 5. etcd의 gRPC watch는 API 서버까지이고 수백 구독자에게 나눠 주는 일은 API 서버가 HTTP로 한다

브로드캐스트에 gRPC가 어울린다는 직감은 etcd의 watch 스트림에서는 맞았지만 멤버 복제는 HTTP였고 쿠버네티스의 진짜 퍼뜨리기는 API 서버의 HTTP watch가 맡았어요.

4. 쿠버네티스 API는 gRPC 대신 REST를 두고 본문만 protobuf로 바꿨다

그럼 API 서버도 gRPC로 바꾸면 되지 않았을까요? 같은 시기에 바로 그 질문을 다룬 문서가 있어요. 2016년 3월 smarterclayton이 쓴 Protobuf serialization and internal storage 제안서예요. 제안서는 먼저 쿠버네티스 트래픽이 클러스터 안쪽으로 몰려 있다고 해요. "as much as 90% of the requests served by the APIs are for internal cluster components like nodes, controllers, and proxies"예요. 그리고 변경에 반응하는 시간 대부분이 etcd에서 객체를 읽고 버전을 바꿔 JSON으로 직렬화했다가 클라이언트에서 되돌리는 시간이고 직렬화 비용, 전송 바이트, 그때 생기는 메모리 가비지가 API 서버의 CPU와 네트워크 사용을 지배한다고 적었어요. 노드 1만 대 클러스터로 가려면 "roughly an order of magnitude efficiency improvement", 즉 약 10배의 효율 개선이 필요하다고 했어요.

실험 결과는 protobuf가 직렬화·역직렬화 CPU를 10배, 전송 바이트를 2배, 직렬화 때 힙에 만드는 객체 수를 6~9배 줄였다는 것이었어요. 제안서의 GET 한 번 측정을 단계별로 그리면 이래요.

그림 6. JSON이 50µs·40µs를 쓰던 decode와 encode가 protobuf로 5µs가 됐고 변환에 드는 15µs는 그대로였다

제안서는 "Changing to protobuf moves our hotspot back to conversion, not serialization."이라고 적었어요. protobuf로 바꾸면 병목이 직렬화에서 형식 변환으로 돌아간다는 뜻이에요. 그리고 Alternatives에서 gRPC를 이렇게 다뤄요.

* We considered JSON compression to reduce size on wire, but that does not reduce the amount of memory garbage created during serialization and deserialization. * More efficient formats like Msgpack were considered, but they only offer 2x speed up vs. the 10x observed for Protobuf * gRPC was considered, but is a larger change that requires more core refactoring. This approach does not eliminate the possibility of switching to gRPC in the future. (Protobuf serialization and internal storage, 2016-03)

→ JSON 압축은 가비지를 줄이지 못했고 Msgpack은 2배밖에 빠르지 않았으며 gRPC는 핵심 코드를 더 많이 고쳐야 하는 큰 변경이라 이번에는 고르지 않았다는 뜻이에요. 다만 나중에 gRPC로 바꿀 가능성은 열어 뒀어요. 설계 원칙에는 "Continue to use the existing REST API patterns but offer an alternative serialization, which means existing client and server tooling can remain the same while benefiting from faster decoding."이 들어 있어요. REST 경로와 도구는 그대로 두고 본문 형식만 하나 더 주겠다는 거예요. 원문에서 찾은 gRPC를 고르지 않은 이유는 이 "더 큰 변경"이 전부였어요.

이 결정은 바로 릴리스에 들어갔어요. CHANGELOG-1.3(2016-07-01)에는 "Use protobufs by default to communicate with apiserver (still store JSONs in etcd)"가 있어요. 구성 요소와 API 서버 사이를 기본으로 protobuf로 바꾸고 etcd에는 아직 JSON으로 저장했다는 뜻이에요. CHANGELOG-1.6(2017-03-28)에서는 etcd v3가 기본 저장소가 되면서 저장 형식도 protobuf가 기본이 됐고 "Kubernetes now supports up to 5,000 nodes via etcd v3"라고 적었어요. 지금의 API 개념 문서도 "Although JSON is the default, clients may request a response in YAML, or use the more efficient binary Protobuf representation for better performance at scale."이라고 해요. 기본은 JSON이고 규모가 클 때 protobuf를 쓰라는 거예요. 같은 문서에 따르면 CRD나 aggregation layer로 제공하는 리소스는 protobuf를 쓸 수 없어서 JSON으로 오가요(22편에서 본 Calico IPPool이 JSON으로 저장된 이유예요).

⚠️ 주의: 쿠버네티스와 gRPC를 두고 흔히 하는 설명, 정확히 말하면
• "API 서버는 스케줄러·컨트롤러와 gRPC로 통신한다" → 둘 다 kubectl과 같은 HTTPS REST이고 본문 형식의 기본값만 protobuf예요(그림 1)
• "HTTP/2를 쓰니 gRPC다" → API 서버도 HTTP/2로 답하지만 REST 경로에 JSON이나 protobuf 본문이에요. gRPC는 /서비스/메서드 경로와 application/grpc 규약을 따로 지켜요
• "etcd 멤버끼리 gRPC로 복제한다" → 멤버 사이 2380은 rafthttp(HTTP)이고 gRPC는 클라이언트 쪽 2379예요
• gRPC를 쓰는 곳이 둘뿐인 것은 아니에요. 다른 팀이 만든 플러그인과 붙는 경계도 gRPC예요. CSI 스펙의 플러그인은 "a gRPC endpoint that implements the CSI Services"이고 KMS 문서는 "The KMS provider uses gRPC to communicate with a specific KMS plugin over a UNIX domain socket"이라고 해요. 장치 플러그인 등록도 kubelet의 gRPC 서비스예요(그림 3)

5. gRPC가 1.0도 되기 전에 고른 셈이고 대가도 있었다

"그때는 gRPC 많이 쓰던 때가 아니었는데"라는 짐작은 맞았어요. 날짜를 나란히 놓으면 etcd와 CRI는 gRPC가 1.0이 되기 전후에 gRPC를 골랐어요.

이슈 #13768은 gRPC 베타보다 한 달 반 먼저 열렸고 etcd v3.0.0은 gRPC 1.0보다 약 7주 먼저 나왔어요. 둘 다 "널리 쓰여서" 고른 게 아니라는 뜻이에요. 원문에 적힌 이유는 앞에서 본 대로예요. CRI는 IDL과 코드 생성으로 다른 팀과 계약을 맺으려고 gRPC를 골랐어요. etcd는 lease·watch 같은 스트림을 효율적으로 다루고 한 포트에서 REST/JSON과 gRPC를 함께 내려고 골랐어요. 그 둘이 이른 시점에 gRPC를 쓴 이유로 "Google이 만든 도구라서"를 드는 원문은 찾지 못했어요.

"그게 그렇게 큰 오버헤드를 주나?"에 대한 답은 연결마다 달랐어요.

· API 서버에서는 컸어요. 2016년 측정에서 JSON 직렬화가 API 서버 CPU를 지배했고 protobuf로 그 부분을 약 10배 줄였어요. 다만 고친 것은 본문 형식이지 전송 프로토콜이 아니었어요.
· CRI 인터페이스 제안에서는 kubelet 성능 개선을 목표 밖에 뒀어요. gRPC 전송을 제안한 논의에서는 속도에 대한 기대와 코드 생성의 편의를 함께 들었어요. 클라이언트·서버로 나누면 호출 단계가 늘어난다는 점과 당시 gRPC가 JSON보다 빠르지 않다는 점도 알고 있었어요.
· etcd에서는 효율이 이유 중 하나였어요. v3 RFC가 "more efficient than JSON/HTTP"를 적었고 lease keep-alive와 여러 범위 watch를 스트림 하나로 처리하는 것이 설계 항목이었어요.

치른 대가도 있어요.

· 사람이 바로 들여다보기 어려워졌어요. CRI는 curl로 부를 수 없어서 crictl 같은 전용 도구가 필요해요. etcd는 grpc-gateway로 일부를 JSON으로 열었지만 RangeStream은 gRPC 전용이에요.
· exec·attach·port-forward는 스트림을 여는 절차와 실제 바이트 전송을 분리하고 데이터는 별도 HTTP 스트리밍 서버로 보내요. 당시 논의에서는 기존 클라이언트 프로토콜과의 호환과 kubelet의 중계 비용도 고려했어요(2장).
· 계약을 바꾸는 비용이 생겼어요. CRI는 v1alpha1, v1alpha2를 거쳐 1.23에서 v1이 기본이 됐고 1.26에서 v1alpha2를 끊자 밖의 shim(cri-dockerd)은 11일 늦게 따라왔어요(45편).

💡 실무에서는: 연결마다 들여다보는 도구가 달라요
• API 서버는 REST라서 kubectl get --raw나 curl로 바로 볼 수 있어요. -H "Accept: application/vnd.kubernetes.protobuf"를 주면 구성 요소가 받는 protobuf 응답도 볼 수 있어요
• etcd는 etcdctl(gRPC)로 보거나 2379의 /v3/kv/range 같은 JSON 게이트웨이를 써요. 우리 클러스터에서는 두 방법 모두 etcd 클라이언트 인증서가 필요해요. JSON 게이트웨이의 키와 값은 base64로 인코딩해요
• etcd 쪽 오류와 호출량은 HTTP 상태 코드가 아니라 grpc_server_handled_total의 grpc_method·grpc_code로 나눠 봐요
• 노드의 런타임은 crictl로 CRI를 직접 불러 봐요. kubelet과 같은 소켓, 같은 gRPC 호출이에요
✍️ 오늘의 요약
쿠버네티스 안의 연결은 REST가 기본이고 gRPC는 다른 팀이 구현하는 경계(CRI)와 바깥 저장소(etcd)에 쓰였어요. 고른 이유도 속도 하나가 아니었어요.

우리 클러스터에서 스케줄러, 컨트롤러 매니저, kubelet, kube-proxy는 모두 kubectl과 같은 6443에 HTTPS REST로 붙었고 본문 형식만 protobuf였어요. gRPC는 API 서버에서 etcd로, kubelet에서 containerd로 가는 두 연결이었어요. CRI는 2015년 이슈에서 코드 생성과 인터페이스 구현의 편의를 gRPC의 이점으로 들었고 CRI 인터페이스 제안에서는 kubelet 성능 개선을 목표 밖에 뒀으며 exec·attach·port-forward의 바이트는 gRPC 대신 HTTP 스트리밍 서버로 보냈어요. etcd v3는 lease·watch 스트림과 효율을 위해 gRPC를 골랐고 CoreOS는 한 포트에서 REST/JSON과 gRPC를 함께 낼 수 있다는 점을 핵심 이유로 들었어요. 멤버 사이 Raft 복제는 rafthttp라는 HTTP 전송이고 gRPC 스트림이 어울린 곳은 watch였으며 수백 구독자에게 나눠 주는 일은 API 서버가 HTTP watch로 했어요. API 서버는 2016년에 JSON 직렬화가 CPU를 지배한다는 측정을 보고 gRPC 대신 REST에 protobuf 본문을 얹었어요. etcd와 CRI가 gRPC를 고른 시점은 모두 gRPC 1.0 전후였고 그 대가로 전용 도구와 계약 버전 관리가 따라왔어요. 프로토콜 선택에는 속도뿐 아니라 반대편의 구현 주체와 전송할 데이터의 성격도 영향을 줬어요.
