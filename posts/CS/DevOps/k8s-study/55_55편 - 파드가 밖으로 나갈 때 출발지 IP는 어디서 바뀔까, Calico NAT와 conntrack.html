Pod에서 출발 포트를 45555로 지정해 요청했는데 수신기에는 192.168.104.3:7165가 찍혔어요. 같은 노드의 hostNetwork Pod와 노드 셸에서 보낸 요청은 지정한 포트 45556과 45557을 그대로 유지했어요. HTTP 응답은 세 요청 모두 정상이었지만 출발지 주소가 같아진 과정은 달랐어요.

수신기는 인터넷 서버가 아니라 worker2의 호스트 주소 192.168.104.4:18555에 띄운 임시 HTTP 서버예요. 클러스터의 노드라도 Calico Pod 풀 밖이면 NAT 조건에 들어갈 수 있어요. 이번에는 worker1의 cali 장치, eth0, worker2의 eth0, 연결 추적 정보를 함께 읽어 변환 위치와 응답 경로를 확인해요.

실험 환경은 Kubernetes v1.37.2, Calico v3.33.0, Linux 6.8이에요. 기존 정책이나 NAT 설정은 바꾸지 않았고 전용 namespace의 Pod 두 개와 제한 시간 있는 수신기만 만들었어요. 일반 Pod의 IP는 10.244.194.92, worker1은 192.168.104.3, worker2는 192.168.104.4였어요.

1. 목적지가 노드여도 Pod 풀 밖일 수 있다

Pod에서 밖으로 나간다는 말부터 범위를 정해야 해요. 이 클러스터의 IPPool은 10.244.0.0/16 하나이고 natOutgoing: true예요. 수신기의 192.168.104.4는 여기에 속하지 않아요. 반면 같은 풀의 다른 Pod로 보내는 통신은 목적지가 풀 안에 있어요.

📖 용어: SNAT
패킷의 출발지 주소를 바꾸는 변환이에요. 이 실험에서는 Pod IP가 worker1의 노드 IP로 바뀌었고 출발지 포트도 함께 바뀌었어요.

Calico의 outgoing NAT 문서는 목적지가 모든 Calico IP 풀 밖인지로 조건을 설명해요. 단순히 “다른 노드면 NAT”, “인터넷이면 NAT”로 판별하면 이 실험을 설명할 수 없어요. 별도의 NAT 제외 풀이나 호스트 주소 제외 설정을 사용하면 조건이 달라질 수 있으므로 실제 규칙도 읽어야 해요.

kubectl get ippool default-ipv4-ippool -o yaml # 이번 spec: cidr=10.244.0.0/16, natOutgoing=true # 전용 Pod에서 목적지를 고정하고 프록시 사용을 끈 요청 kubectl -n calico-blog-55 exec pod-client -- curl \ --noproxy '*' --local-port 45555 --max-time 5 -sS \ http://192.168.104.4:18555/pod

첫 명령은 NAT 여부를 결정할 풀 설정을, 두 번째 명령은 수신기가 본 원격 주소를 보여줘요. Pod 이름·주소·포트는 전용 실습 값이에요. --local-port는 애플리케이션이 쓰는 출발 포트를 정하지만 이후 NAT에서 포트가 유지된다고 보장하지 않아요.

💡 실무에서는
같은 노드에서 일반 Pod·hostNetwork Pod·노드 셸 요청을 비교하면 애플리케이션이 보는 주소와 네트워크 경로를 분리할 수 있어요. hostNetwork Pod는 노드의 네트워크 네임스페이스를 공유하므로 일반 Pod의 IP를 출발지로 쓰지 않아요.

2. natOutgoing은 커널의 MASQUERADE 규칙으로 이어졌다

설정이 true라는 사실만으로 실제 연결이 어느 규칙을 지났다고 말할 수는 없어요. worker1에서 sudo iptables-save -t nat로 확인하니 POSTROUTING에서 cali-POSTROUTING으로 들어가고 그 안에서 cali-nat-outgoing을 호출했어요. 마지막 조건과 동작은 다음 한 줄이었어요. 읽기 편하게 식별용 주석만 뺐어요.

-A cali-nat-outgoing \ -m set --match-set cali40masq-ipam-pools src \ -m set ! --match-set cali40network-ip-pools dst \ -j MASQUERADE --random-fully

출발지가 NAT 대상 풀에 속하고 목적지가 네트워크 풀 집합에 속하지 않을 때 MASQUERADE를 적용해요. 설치 버전의 Felix 규칙 생성 코드도 두 집합 조건을 조합하고 NAT outgoing 체인을 만들어요. 이 환경의 iptables는 nf_tables 백엔드를 사용했어요. 다른 백엔드·eBPF 모드까지 동일한 규칙 모양이라고 일반화하지 않아요.

📖 용어: MASQUERADE
송신 인터페이스의 주소를 이용하는 SNAT 동작이에요. 고정 주소를 지정하는 SNAT 규칙과 구분하며, 여기서는 eth0으로 나가면서 출발지가 192.168.104.3으로 바뀌었어요.

이 체인의 매칭 패킷 카운터는 세 요청 전 22에서 뒤 23으로 늘었어요. 이것만으로 어떤 연결이 원인이었는지 확정하지는 않아요. 공유 노드의 다른 요청도 카운터에 포함될 수 있기 때문이에요. 다음 절의 패킷과 연결 추적을 함께 대조했어요.

⚠️ 주의: NAT 카운터는 전체 전송량이 아니에요
Netfilter NAT 문서가 설명하듯, 연결 추적을 사용하는 NAT 규칙은 새 연결의 첫 패킷에서 변환을 결정해요. 그 뒤 패킷에는 저장한 대응이 적용되므로 HTTP 응답에 패킷이 여러 개 있어도 NAT 규칙 카운터가 그만큼 늘어야 하는 것은 아니에요.

3. cali와 eth0에서 같은 연결의 출발지가 달라졌다

일반 Pod로 가는 호스트 경로에서 cali31e758d2ea8을 찾았어요. 이 장치와 worker1의 eth0, worker2의 eth0에서 tcp and host 192.168.104.4 and port 18555 필터로 동시에 캡처했어요. 각각 16초 제한을 걸고 원본 pcap을 남겼어요.

cali의 첫 SYN은 10.244.194.92:45555 → 192.168.104.4:18555였어요. worker1의 eth0에서는 192.168.104.3:7165 → 192.168.104.4:18555였고 worker2도 같은 변환된 주소를 받았어요. 두 SYN의 TCP 초기 시퀀스 번호는 345155042로 같았고 TCP 타임스탬프도 같았어요. 포트가 바뀌었어도 같은 연결의 패킷임을 대조할 수 있었어요.

📖 용어: 5-tuple
출발지 IP·포트, 목적지 IP·포트, 전송 프로토콜을 묶은 연결 식별 정보예요. NAT 전후에는 일부 값이 달라지므로 캡처를 비교할 때 TCP 시퀀스와 시각도 같이 확인했어요.
그림 1. cali와 eth0의 같은 TCP 연결을 대조해 SNAT 구간을 찾았어요

수신기의 HTTP 응답과 서버 로그에도 일반 Pod 요청의 원격 포트는 7165로 남았어요. iptables 확장 매뉴얼에서 --random-fully는 출발지 포트 매핑을 무작위화하는 옵션이에요. 7165는 이 규칙이 적용된 이번 연결의 관측값이며 다음 실행에서도 7165를 쓴다는 뜻은 아니에요. hostNetwork Pod 요청과 노드 요청은 각각 192.168.104.3:45556, 192.168.104.3:45557로 보였어요.

위 화면은 세 요청의 저장된 응답 원문을 모아 렌더링한 캡처예요. 터미널을 직접 촬영한 화면은 아니며 실행 시각·명령·서버 로그는 별도 실습 자료에 보관했어요.

52편의 다른 노드 Pod 통신과도 달라요. 목적지 192.168.104.4로의 호스트 경로는 eth0의 직접 경로였어요. IPIP Always라는 풀 설정이 모든 목적지의 패킷을 무조건 tunl0으로 보낸다는 뜻은 아니에요.

4. 응답이 원래 Pod로 돌아오는 정보는 conntrack에 있었다

수신기가 본 클라이언트는 노드 주소예요. 그렇다면 응답은 어떤 Pod로 보내야 할까요? worker1의 연결 추적 정보를 읽으니 일반 Pod 요청에 NAT 전 original과 NAT 후 reply가 함께 남아 있었어요.

📖 용어: conntrack
리눅스 커널이 연결의 두 방향과 상태를 추적하는 기능이에요. NAT와 함께 쓰이면 변환 전후의 대응을 보관하고 응답에 반대 변환을 적용할 수 있어요.
original 10.244.194.92:45555 → 192.168.104.4:18555 reply 192.168.104.4:18555 → 192.168.104.3:7165 src_nat true hostNetwork: src_nat=false, 원래 포트 45556 node: src_nat=false, 원래 포트 45557

위는 원문 JSON의 주소·포트를 한 줄씩 정리한 결과예요. reply는 NAT 전 original의 주소를 단순히 뒤집은 값이 아니에요. 수신기에서 돌아오는 패킷의 목적지는 192.168.104.3:7165예요. 커널이 연결을 찾아 목적지를 10.244.194.92:45555로 되돌린 뒤 Pod 방향으로 전달해요. 실제 cali 캡처에서도 SYN-ACK의 목적지는 원래 Pod 주소·포트였어요.

그림 2. conntrack의 reply 목적지는 NAT 전 Pod 주소와 달라요

이번 노드에는 conntrack CLI와 /proc/net/nf_conntrack이 없었어요. 패키지를 설치하는 대신 Python 표준 라이브러리로 커널의 nfnetlink conntrack 조회 인터페이스에 읽기 전용 dump를 요청했어요. 다른 연결 내용은 저장하지 않고 목적지 포트 18555인 TCP 연결만 출력했어요. 설치된 환경에서는 sudo conntrack -L -p tcp --dport 18555로 같은 종류의 정보를 볼 수 있어요.

이 화면도 저장된 조회 JSON에서 일반 Pod 연결 부분을 골라 렌더링했어요. 응답을 받은 뒤 조회한 결과라 TCP 연결이 이미 종료 중인 표본일 수 있어요. 이 표본만으로 연결 유지 시간이나 모든 TCP 상태 전이를 추론하지 않아요.

5. 인터넷에서 보이는 주소와 Calico가 바꾼 주소를 구분한다

이번에 수신기를 worker2의 호스트 네트워크에 둔 이유는 관측 경계를 좁히기 위해서예요. Calico 풀 밖의 주소에 요청하면서도 송신 노드와 수신기의 캡처를 모두 확보할 수 있었어요. 인터넷 전체의 경로·공인 NAT 동작을 재현한 실험은 아니에요.

그림 3. Pod 대역 밖의 수신기로 Calico NAT를 검증했고 인터넷 NAT와 구분했어요

공인 IP 조회 서비스에서 주소 하나를 받으면 그 값은 최종 수신자가 본 출발지예요. 중간에 Lima·Mac·공유기·클라우드 NAT가 있으면 노드에서 이미 변환된 주소가 다시 바뀔 수 있어요. 따라서 그 출력 하나로 “Calico가 이 공인 IP로 바꿨다”고 결론 내리지 않아요.

💡 실무에서는 이 순서로 대조해요
목적지 주소와 포트를 고정하고 Pod의 IP·경로, 실제 IPPool, NAT 조건과 카운터, 노드 송신 인터페이스의 패킷, 수신기의 원격 주소, conntrack의 original/reply를 차례로 확인해요. 주소 변경이 일어난 두 관측 지점 사이부터 조사하면 돼요.

NAT를 끄면 Pod 주소가 보존될 수 있지만 외부 수신기에서 그 Pod 대역으로 돌아오는 경로와 정책도 필요해요. 이 부분은 IPPool 설정 문서와 앞서 본 outgoing NAT 문서의 조건이에요. 이번에는 기존 풀을 바꾸지 않았으므로 NAT 비활성화 비교를 실험했다고 쓰지 않아요.

재현 스크립트와 매니페스트, 세 지점의 pcap, 조회 원문은 55편 실습 자료에 함께 두었어요. 수집기는 저장소 경로의 lab 래퍼를 사용하므로 다른 환경에서는 경로와 노드 이름을 바꿔야 해요. 실행 후 전용 namespace가 사라지고 worker2의 18555 리스너가 닫힌 것도 확인했어요.

✍️ 오늘의 요약
이번 구성에서는 Pod 풀 밖의 worker2 호스트로 보낸 일반 Pod 요청이 worker1에서 SNAT됐어요.

cali의 10.244.194.92:45555와 eth0의 192.168.104.3:7165를 같은 TCP 연결로 대조했고 conntrack에서 응답의 대응도 확인했어요. NAT를 설명할 때는 풀 설정, 실제 패킷, 연결 추적, 수신기의 관측 범위를 함께 읽어야 해요.
