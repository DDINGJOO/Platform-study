40편. etcd 3.7에서는 백업과 복원을 어떻게 할까

19시 38분에 마스터에서 etcd의 데이터 파일을 봤어요. /var/lib/etcd/member/snap/db 파일 하나가 34,672,640바이트(약 34.7MB)였어요. 같은 순간 etcdctl endpoint status는 데이터베이스 크기(dbSize)를 21.8MB라고 했고 그중 실제로 쓰는 공간(dbSizeInUse)은 2.7MB라고 했어요. 빈 페이지가 88%였어요. 파일 하나를 두고 크기가 세 가지로 나온 셈이에요.

20시 20분에 다시 보니 파일은 여전히 34.7MB였고 dbSize 21.8MB 가운데 쓰는 공간은 2.9MB였어요. 여기서 조각 모음(etcdctl defrag)을 한 번 하자 약 21ms 만에 끝났고 파일은 4.2MB, dbSize는 2.7MB가 됐어요. 파일의 약 88%가 사라졌는데 etcd의 리비전은 앞뒤 모두 138928이었어요. 지운 데이터는 하나도 없었다는 뜻이에요. 그러면 그 30MB에는 무엇이 들어 있었고 etcd는 왜 스스로 파일을 줄이지 않았을까요?

쿠버네티스의 구성 요소를 하나씩 보던 날 etcd 차례에서 제가 남긴 메모는 "etcd > 비트리 구조래"였어요. 22편에서는 etcd를 열어 키 이름과 저장 형식, Secret을 봤고 이번에는 그 키들이 디스크에 어떤 모양으로 쌓이고 언제 어떻게 지워지는지 따라가요. 클러스터는 Lima VM 4대에 kubeadm v1.37.2를 올린 실습 환경이고 etcd 3.7.0이 마스터에 멤버 하나로 떠 있어요(21편).

· 옛 값은 언제까지 읽히고 누가 지울까?

1. etcd는 메모리의 B트리 색인으로 리비전을 찾고 디스크의 B+트리에서 값을 꺼낸다

먼저 마스터의 etcd 데이터 디렉터리를 열어 봤어요.

그림 1. 데이터는 member/snap/db 파일 하나에 있고 WAL 파일 세 개가 따로 있었다. dbSize 21.8MB 가운데 쓰는 공간은 2.7MB였다

파일은 두 종류예요. etcd 문서의 저장 파일 설명에 따르면 member/snap/db는 적용(apply)이 끝난 데이터를 모두 담는 bbolt B+트리이고 member/wal/*.wal은 Raft가 받아들인 최근 변경을 적는 로그(WAL, write ahead log)예요. 변경은 WAL에 먼저 적히고 적용을 마친 결과가 db 파일에 들어가요. 이번 글이 따라가는 것은 db 파일이에요.

📖 용어: bbolt
Go로 쓴 키·값 저장 라이브러리예요. 데이터베이스 하나를 파일 하나에 담고 그 안을 같은 크기의 페이지로 나눠 B+트리로 정리해요. 따로 서버로 뜨지 않고 etcd 프로세스 안에서 라이브러리로 돌아요. etcd 3.7.0이 쓰는 버전은 v1.5.0이에요(etcd 저장소 server/go.mod).
📖 용어: B트리와 B+트리
둘 다 키를 정렬해 두고 노드 하나에 키를 여러 개 담아서 몇 단계만 내려가면 원하는 키에 닿게 만든 트리예요. B+트리는 값을 맨 아래 잎(leaf) 노드에만 두고 위쪽 노드에는 길을 찾는 키만 두는 변형이라 키를 범위로 읽기에 좋아요. 디스크를 페이지 단위로 읽고 쓰는 저장소에서 많이 써요.

그런데 이 B+트리에 들어 있는 키는 /registry/deployments/default/myweb 같은 이름이 아니에요. etcd 문서의 데이터 모델은 물리적인 저장을 이렇게 설명해요. etcd는 데이터를 "persistent b+tree"에 키·값 쌍으로 저장하고 그 키는 (main, sub, type) 세 칸으로 된 리비전이에요. main은 그 변경이 들어간 리비전이고 sub는 한 리비전 안에서 바뀐 키들을 구분하는 번호이고 type은 특별한 값에 붙는 접미사예요(지운 기록이면 t). 저장 파일 설명의 버킷 표에도 key 버킷의 키는 리비전이고 값은 키 이름, create_revision, mod_revision, version, 값, lease ID를 담은 mvccpb.KeyValue라고 적혀 있어요. v3.7.0 소스 revision.go를 보면 이 키는 main 8바이트, 밑줄(_) 1바이트, sub 8바이트를 이은 17바이트이고 지운 기록에는 끝에 t 한 바이트가 더 붙어요.

이름으로 값을 찾으려면 이름에서 리비전으로 가는 길이 따로 있어야 해요. 같은 문서는 키 범위 조회를 빠르게 하려고 etcd가 "secondary in-memory btree index"를 둔다고 해요. 이 색인의 키는 사용자가 보는 키 이름이고 값은 B+트리 안의 변경을 가리키는 포인터예요. 문서는 두 구조의 관계를 "Overall, etcd gets the revision information from btree and then uses the revision as key to fetch value from b+tree"라고 정리해요. 메모리의 B트리에서 리비전을 얻고 그 리비전을 키로 디스크의 B+트리에서 값을 꺼낸다는 뜻이에요.

그림 2. 메모리 색인은 키 이름으로 리비전을 찾고 디스크의 B+트리는 리비전을 키로 KeyValue를 저장한다

그러니 "etcd는 B트리 구조"라는 메모는 두 겹으로 맞아요. 디스크의 db 파일은 bbolt의 B+트리이고 메모리의 색인은 B트리예요(v3.7.0 소스 index.go의 treeIndex가 btree.BTree를 써요). 디스크 B+트리의 키는 키 이름이 아니라 리비전이라서 같은 키를 고칠 때마다 덮어쓰지 않고 줄이 하나 늘어나요.

2. 값을 바꾸면 덮어쓰지 않고 리비전을 하나 더 쌓는다

정말 줄이 늘어나는지 Deployment myweb의 키로 확인했어요. kubectl로 replicas를 6으로 바꿨다가 5로 되돌리면서 etcd의 키 정보를 찍었어요.

그림 3. create_revision은 그대로이고 version만 118, 123, 127로 올랐다. 6개였던 때의 값은 리비전을 주면 그대로 읽혔다
📖 용어: version과 지운 표시(tombstone)
etcd가 키마다 세는 수정 횟수예요. etcd API 문서에 따르면 키를 고칠 때마다 version이 1씩 오르고 키를 지우면 0으로 돌아가요. 데이터 모델 문서는 키를 지우면 지운 표시(tombstone)가 생기고 그 키의 지금 세대(generation)가 끝난다고 설명해요. 같은 이름으로 다시 만들면 새 세대가 version 1부터 시작해요. create_revision은 그 세대가 시작된 리비전이고 mod_revision은 마지막으로 고친 리비전이에요.

create_revision 89896은 세 번 모두 같았어요. 이 키가 처음 만들어진 리비전이에요. 반면 version은 118에서 123으로, 다시 127로 올랐어요. 만들 때 version이 1이니 이 키는 그 뒤 126번 고쳐졌어요. 첫 scale 뒤 2초 사이에 다섯 번, 두 번째 scale 뒤에는 네 번 바뀌었는데 replicas를 고친 요청 한 번 뒤에 deployment 컨트롤러가 status를 여러 번 고쳐 쓴 것으로 보여요. mod_revision은 22편에서 본 대로 kubectl의 resourceVersion과 같은 값이에요.

마지막 두 줄이 이 절의 핵심이에요. 지금 replicas는 5인데 --rev=134283을 주자 6으로 바꿨던 때의 값이 2156바이트 그대로 나왔어요. kubectl은 지금 값만 보여 주지만 etcd에는 그 앞의 값도 남아 있었어요. 데이터 모델 문서는 이 성질을 "its operations do not update the structure in-place, but instead always generate a new updated structure"라고 적어요. 값을 제자리에서 고치지 않고 늘 새 구조를 만든다는 뜻이에요.

같은 문서에는 리비전 하나에 이전 리비전과 달라진 것(delta)만 담긴다는 문장도 있어요. 여기서 달라진 것은 그 리비전에서 바뀐 키들이고 바뀐 키 하나에는 값 전체가 들어가요. v3.7.0 소스 kvstore_txn.go의 put 함수는 키 이름과 값, create_revision, mod_revision, version, lease를 담은 KeyValue를 통째로 직렬화해서 새 리비전 키로 써요. replicas 한 칸만 바꿔도 Deployment 객체 전체(이번에는 약 2KB)가 한 줄 더 쌓여요.

파드 하나는 어떨까요? etcd를 직접 watch하면서 nginx 파드 하나를 만들고 Ready가 된 뒤 지웠어요.

그림 4. 파드 하나가 만들어져 지워질 때까지 같은 키에 PUT이 11번, DELETE가 1번 기록됐다

/registry/pods/default/nginx 키 하나에 PUT이 11번, DELETE가 1번 왔어요. Ready가 됐을 때 kubectl이 본 resourceVersion 141913은 여섯 번째 PUT의 mod_revision과 같았어요. Ready가 되기까지 여섯 번 쓰였고 그 뒤 지워질 때까지 PUT 다섯 번과 DELETE 한 번이 더 있었다는 뜻이에요. 이 기록에는 어느 PUT을 누가 썼는지가 남지 않았어요. 파드를 만드는 요청, 노드를 정하는 바인딩(41편), kubelet의 상태 갱신, 삭제 표시(deletionTimestamp), 종료 상태 갱신이 모두 이 키 하나를 고치는 쓰기예요.

그림 2의 아래칸으로 옮기면 이 파드 하나가 bbolt의 key 버킷에 12줄을 남긴 거예요. 11줄은 각각 그 순간의 파드 객체 전체를 담은 KeyValue이고 마지막 한 줄은 지운 표시예요. 메모리 색인에서 이 키는 141902부터 141931까지를 묶은 세대 하나로 남아요. 파드는 사라졌지만 이 줄들은 컴팩션 전까지 지워지지 않아요.

3. 옛 리비전은 API 서버가 5분마다 컴팩션으로 지운다

이렇게 쌓기만 하면 파일은 끝없이 커지니 언젠가는 옛 줄을 지워야 해요. 같은 스크립트로 22편 실험 때(15시 17분)의 리비전 103241을 읽어 봤어요.

그림 5. 4시간 넘게 지난 리비전은 required revision has been compacted로 거절됐고 몇 초 전 리비전은 읽혔다

→ "그 리비전은 이미 컴팩션돼서 줄 수 없다"는 뜻이에요. etcd 유지보수 문서의 예시에도 컴팩션한 리비전보다 앞을 --rev로 읽으면 같은 오류가 나와요. 15시 17분의 값은 이미 지워졌고 19시 38분에 몇 초 전 쓴 134283은 아직 남아 있었어요.

지우는 쪽은 etcd 자신이 아니라 API 서버예요. etcd에도 스스로 컴팩션하는 --auto-compaction-retention 플래그가 있지만 etcd 설정 문서에 따르면 기본값 0은 자동 컴팩션을 끈다는 뜻이고 우리 etcd 매니페스트에는 이 플래그가 없었어요(38-etcd-flags.txt). 대신 kube-apiserver의 --etcd-compaction-interval(기본 5m0s, 22편)이 이 일을 맡아요. v1.37.2 소스 compact.go의 주석과 코드를 따라가면 순서는 이래요.

· API 서버는 5분마다 etcd에 트랜잭션을 하나 보내요. etcd 안의 특별한 키 compact_rev_key의 version이 자기가 기억한 값과 같으면 그 키에 지난 차례에 본 리비전을 적고 그 리비전까지 컴팩션해요.
· version이 다르면 다른 API 서버가 먼저 컴팩션했다는 뜻이라 그 값을 받아 두고 5분 뒤에 다시 시도해요. API 서버가 여러 대여도 한 차례에 컴팩션은 한 번만 일어나요.
· 지우는 기준이 5분 전에 본 리비전이라서 etcd에는 늘 적어도 최근 5분의 이력이 남고 다음 차례 직전에는 10분 가까이 쌓여요. 주석에는 컴팩션 간격이 평소 5분이고 API 서버 하나가 죽어 다른 API 서버가 넘겨받을 때는 5분보다 길고 10분보다 짧다고 적혀 있어요.

같은 파일의 다른 주석은 이 숫자의 이유를 "By default, we save the most recent 5 minutes data and compact versions > 5minutes ago"라고 적고 느린 watcher와 갑작스런 부하를 견디기에 충분하다고 덧붙여요. API 개념 문서도 etcd 3을 쓰는 클러스터는 기본으로 최근 5분의 변경을 보관한다고 해요. 그보다 옛 위치에서 watch를 이어 가려는 클라이언트는 410 Gone을 받는데 쿠버네티스가 그 410을 어떻게 받아넘기는지는 39편에서 이어 가요.

컴팩션이 무엇을 지우는지는 v3.7.0 소스 key_index.go의 keyIndex 주석에 예시와 함께 적혀 있어요. 키 하나의 색인은 세대들의 목록이고 컴팩션은 컴팩션 리비전 이하의 버전 가운데 가장 큰 것 하나만 남기고 지워요. 지운 표시로 끝난 세대는 컴팩션 리비전이 그 지운 표시를 넘어서면 통째로 사라지고 세대가 모두 사라지면 색인에서 키도 지워져요. 데이터 모델 문서의 문장으로는 "any generation ended before the compaction revision will be removed, and values set before the compaction revision except the latest one will be removed"예요. 색인에서 빠진 리비전의 줄은 bbolt의 key 버킷에서도 지워져요(kvstore_compaction.go의 scheduleCompaction이 색인이 남기기로 한 리비전이 아닌 줄을 지워요).

그림 6. 컴팩션 리비전 이하에서는 가장 큰 버전 하나만 남고 지운 표시로 끝난 세대는 통째로 사라진다. 가운데 줄은 설명을 위한 예다

nginx 파드를 지우고 5~10분이 지나면 이 키의 12줄은 색인에서도 bbolt에서도 모두 사라져요. etcd가 들고 있는 옛 값은 백업이 아니라 최근 5~10분의 이력이에요.

⚠️ 주의: etcd의 옛 리비전으로 되돌릴 생각은 하지 마세요
• 이 클러스터에서 etcd가 들고 있는 이력은 최근 5~10분이에요. 잘못 지운 객체를 etcdctl get --rev로 꺼낼 수 있는 시간은 길지 않아요
• 되돌려야 할 때를 대비하려면 etcd 스냅숏 백업(40편)을 뜨거나 매니페스트를 Git에 두어요. Deployment의 kubectl rollout undo도 etcd의 이력이 아니라 남겨 둔 옛 ReplicaSet으로 되돌려요
• etcdctl로 etcd에 직접 쓰거나 지우지 않아요. 인증, 인가, 어드미션을 하나도 거치지 않아요(2편, 22편)

4. 지운 자리는 파일 안의 빈 페이지로 남고 조각 모음을 해야 파일이 준다

컴팩션이 5분마다 줄을 지우는데도 그림 1의 파일은 34.7MB였어요. 지운 줄이 차지하던 공간이 파일 밖으로 나가지 않기 때문이에요. bbolt README의 주의 사항에 이유가 적혀 있어요. 페이지가 디스크에 놓이는 방식 때문에 bbolt는 데이터 파일을 잘라 빈 페이지를 디스크에 돌려줄 수 없고 대신 파일 안에 빈 페이지 목록(free list)을 두어 다음 트랜잭션이 다시 쓰게 해요. 그 문단의 마지막 문장은 "deleting large chunks of data will not allow you to reclaim that space on disk"예요. 큰 데이터를 지워도 그 공간을 디스크로 되찾을 수 없다는 뜻이에요.

📖 용어: 빈 페이지 목록(free list)
bbolt가 파일 안에서 지금 쓰지 않는 페이지 번호를 모아 둔 목록이에요. etcd 저장 파일 설명에 따르면 bbolt는 페이지를 제자리에서 고치지 않고 내용을 새 페이지에 복사한 다음 그 옛 페이지를 읽는 트랜잭션이 모두 끝나면 이 목록에 넣어요. 목록에 든 페이지는 다음 쓰기가 다시 가져다 써요.

etcd 쪽 문서도 같은 말을 해요. 유지보수 문서는 컴팩션 뒤 데이터베이스 안에 조각난 빈 공간이 생기고 그 공간을 etcd는 쓸 수 있지만 호스트 파일 시스템은 쓸 수 없다고 하면서 "In other words, deleting application data does not reclaim the space on disk"라고 정리해요. 저장 파일 설명은 더 짧게 "The bbolt file never shrinks on its own"이라고 적어요. 파일이 줄어드는 것은 조각 모음을 할 때뿐이에요.

그림 1의 세 숫자도 여기서 풀려요. v3.7.0 소스 backend.go를 보면 etcd가 보고하는 dbSize는 bbolt 트랜잭션의 Size()이고 bbolt(tx.go)는 이 값을 지금까지 쓴 가장 높은 페이지 번호에 페이지 크기를 곱해 계산해요. dbSizeInUse는 거기서 빈 페이지 목록에 든 페이지만큼을 뺀 값이에요. 파일 크기는 그보다도 커요. etcd는 bbolt를 열 때 처음 매핑할 크기(InitialMmapSize)를 10GiB로 주는데 이때 bbolt v1.5.0의 db.go는 파일이 모자라면 필요한 크기에 16MiB(DefaultAllocSize)를 더해 넉넉하게 늘려 둬요. 정리하면 파일 34.7MB, 쓴 페이지의 끝 21.8MB, 실제로 쓰는 페이지 2.7MB 순서예요.

그림 7. 조각 모음 한 번에 파일이 34.7MB에서 4.2MB로, dbSize가 21.8MB에서 2.7MB로 줄었고 리비전은 그대로였다

20시 20분 44초의 상태는 19시 38분과 거의 같았어요. dbSize 21.8MB 가운데 2.9MB만 쓰고 있었고 파일은 34.7MB였어요. etcdctl defrag는 약 21ms 만에 끝났고 1초 뒤 dbSize와 쓰는 공간은 모두 2.7MB, 빈 페이지는 0%, 파일은 4.2MB가 됐어요. 리비전은 앞뒤 모두 138928이었어요. 지운 데이터 없이 빈 페이지만 빠졌어요.

조각 모음은 파일을 제자리에서 줄이는 작업이 아니에요. backend.go의 defrag 함수는 같은 폴더에 db.tmp.로 시작하는 임시 파일을 만들고 남아 있는 키·값을 버킷마다 그 파일로 복사한 다음 원래 파일과 바꿔 끼워요. 저장 파일 설명의 표에도 이 임시 파일이 조각 모음 동안 생겼다가 성공하면 member/snap/db로 이름이 바뀐다고 적혀 있어요. 복사하는 동안에는 읽기와 쓰기를 모두 막아요. 소스는 쓰기 트랜잭션, 백엔드, 읽기 트랜잭션의 잠금을 차례로 잡고 유지보수 문서도 "defragmentation to a live member blocks the system from reading and writing data while rebuilding its states"라고 주의를 줘요. 우리 etcd는 멤버가 하나라서 이 21ms 동안은 클러스터 전체가 etcd를 쓰지 못했어요. 데이터가 2.7MB라 짧았을 뿐이고 복사할 데이터가 많을수록 더 오래 걸려요.

그림 8. 컴팩션은 페이지를 비우기만 하고 파일을 줄이는 것은 쓰는 페이지만 새 파일로 옮기는 조각 모음이다

컴팩션은 옛 리비전을 지워 페이지를 비우고 조각 모음은 빈 페이지를 빼고 파일을 새로 써요. 둘은 이름이 비슷하지만 하는 일도, 하는 쪽도 달라요. 컴팩션은 API 서버가 5분마다 저절로 하고 조각 모음은 누군가 따로 해야 해요.

💡 실무에서는: etcd 용량은 두 숫자를 함께 보고 조각 모음은 드물게 해요
• etcdctl endpoint status -w table의 DB SIZE와 IN USE를 같이 봐요. 메트릭으로는 유지보수 문서가 든 etcd_mvcc_db_total_size_in_bytes(빈 페이지 포함)와 etcd_mvcc_db_total_size_in_use_in_bytes(실제 사용)예요
• 22편에서 본 용량 한도(QUOTA 2.1GB)에 닿으면 etcd는 읽기와 삭제만 받아요. 유지보수 문서에 따르면 다시 쓰기를 받으려면 공간을 비우고 조각 모음을 한 뒤 경보를 풀어야 해요
• 쿠버네티스의 etcd 운영 문서는 조각 모음이 비싼 작업이라 되도록 드물게 하라고 하면서 etcd-defrag 같은 도구를 권해요
• 멤버가 여럿이면 조각 모음 요청은 클러스터에 복제되지 않아요. 유지보수 문서대로 --cluster나 --endpoints로 멤버를 지정해 한 멤버씩 해요. 그동안 그 멤버는 읽기와 쓰기를 멈춰요
⚠️ 주의: etcd 데이터 파일은 평문이에요
• 그림 7의 마지막 부분에서 db 파일 안에 myweb이라는 글자가 85번 그대로 나왔어요. etcd 매니페스트에는 저장 암호화 관련 플래그가 하나도 없었고 TLS 설정은 전송 구간만 지켜요
• etcd 보안 문서의 FAQ도 "etcd doesn't encrypt key/value data stored on disk drives"라고 답해요. Secret을 etcd에 암호문으로 두려면 API 서버의 저장 데이터 암호화(EncryptionConfiguration)를 켜요(22편)
• /var/lib/etcd와 백업 파일은 그 안의 Secret과 같은 수준으로 권한과 보관 위치를 관리해요

5. 컨트롤 플레인에서 상태를 가진 것은 etcd뿐이다

etcd를 "control plane의 유일한 Statefulset 구성 요소"라고 소개하는 문장을 보고 제가 물은 것은 "왜 스테이트풀셋이야?"였어요. 쿠버네티스에서 StatefulSet은 리소스 이름이라서 etcd도 StatefulSet으로 떠 있다는 말로 들렸거든요.

📖 용어: StatefulSet
StatefulSet 문서의 첫 설명은 "StatefulSet is the workload API object used to manage stateful applications"예요. 파드마다 바뀌지 않는 이름과 네트워크 식별자, 자기 몫의 영구 스토리지를 붙여 주는 워크로드 리소스예요.

이 문장의 Statefulset은 리소스가 아니라 "상태를 가진(stateful)"이라는 뜻으로 읽어야 맞아요. 우리 etcd는 StatefulSet이 아니에요. 그날 컨트롤 플레인 파드를 찍어 보니 etcd-k8s-master도 다른 셋과 같이 OWNER가 Node였어요. kubelet이 /etc/kubernetes/manifests의 파일을 보고 직접 띄우는 정적 파드라는 뜻이에요(5편).

# 38-control-plane.txt 발췌 (19:34) NAME NODE IMAGE OWNER etcd-k8s-master k8s-master registry.k8s.io/etcd:3.7.0-0 Node kube-apiserver-k8s-master k8s-master registry.k8s.io/kube-apiserver:v1.37.2 Node kube-controller-manager-k8s-master k8s-master registry.k8s.io/kube-controller-manager:v1.37.2 Node kube-scheduler-k8s-master k8s-master registry.k8s.io/kube-scheduler:v1.37.2 Node

상태를 가졌다는 말은 매니페스트의 볼륨에서 드러나요. 네 매니페스트에서 읽기 전용이 아닌 마운트만 골라 봤어요.

# 38-etcd-watch-registry.txt 2절 (정적 파드 매니페스트의 hostPath 볼륨 중 쓰기 가능한 것) etcd.yaml 쓰기 가능한 마운트: ['/var/lib/etcd', '/etc/kubernetes/pki/etcd'] kube-apiserver.yaml 쓰기 가능한 마운트: 없음 kube-controller-manager.yaml 쓰기 가능한 마운트: 없음 kube-scheduler.yaml 쓰기 가능한 마운트: 없음

→ 디스크에 쓸 수 있게 마운트한 것은 etcd의 데이터 디렉터리와 etcd 인증서 폴더뿐이고 나머지 셋은 쓸 수 있는 마운트가 하나도 없다는 뜻이에요.

API 서버, 스케줄러, 컨트롤러 매니저는 디스크에 상태를 남기지 않아요. 떠 있는 동안 들고 있는 것은 etcd나 API 서버에서 받아 둔 사본이고 다시 뜨면 처음부터 다시 받아요(39편). 20편에서 API 서버를 30초 멈췄다 되돌려도 잃은 것이 없었던 이유예요. 여러 대로 늘릴 때도 차이가 나요. 21편에서 본 대로 etcd는 멤버의 과반이 살아 있어야 쓰기를 받지만 API 서버는 여러 대가 함께 요청을 받고 스케줄러와 컨트롤러 매니저는 리더 하나만 일해요. 컨트롤 플레인에서 클러스터 상태를 디스크에 쓰는 것은 etcd뿐이라서 백업과 복원도 etcd의 데이터 디렉터리를 중심으로 해요(40편).

이렇게 놓고 보면 etcd는 쿠버네티스가 쓰는 키·값 데이터베이스이고 이번 글에 나온 말도 모두 데이터베이스의 말이에요. 값을 덮어쓰지 않고 버전을 쌓는 MVCC, 옛 버전을 치우는 컴팩션, 빈 페이지를 파일 밖으로 돌려주는 조각 모음이에요. etcd를 이렇게 하나씩 열어 본 날 제가 남긴 말도 "디비 관점에서 보니까 뭔 말인지 알았음"이었어요.

✍️ 오늘의 요약
etcd는 값을 덮어쓰지 않고 리비전마다 KeyValue 한 줄을 bbolt B+트리에 쌓아요. 컴팩션은 옛 줄을 지워 페이지를 비울 뿐이고 파일을 줄이는 것은 조각 모음이에요.

etcd는 메모리의 B트리 색인에서 키 이름으로 리비전을 찾고 디스크 bbolt 파일의 B+트리에서 그 리비전을 키로 값을 꺼내요. 디스크의 키가 리비전이라서 myweb Deployment 키는 scale 한 번 뒤 version이 118에서 123으로 올랐고 6개였던 때의 값도 리비전을 주면 읽혔어요. nginx 파드 하나는 같은 키에 PUT 11번과 DELETE 1번을 남겼어요. 옛 줄은 API 서버가 5분마다 5분 전 리비전까지 컴팩션해서 지우니 4시간 넘게 지난 리비전은 required revision has been compacted로 거절됐어요. 지운 줄의 페이지는 bbolt의 빈 페이지 목록으로 들어갈 뿐 파일 밖으로 나가지 않아서 파일은 34.7MB인데 실제로 쓰는 공간은 2.7MB였어요. 조각 모음은 남은 키·값을 새 파일로 복사해 약 21ms 만에 파일을 4.2MB로 줄였고 그동안 etcd는 읽기와 쓰기를 멈췄어요. 데이터 파일은 평문이고 컨트롤 플레인에서 디스크에 상태를 두는 것은 etcd뿐이에요. etcd를 운영하는 일은 결국 이 데이터 디렉터리의 크기와 내용을 지키는 일이에요.
