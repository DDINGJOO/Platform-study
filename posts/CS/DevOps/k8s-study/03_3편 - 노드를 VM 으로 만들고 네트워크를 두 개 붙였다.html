1편. 클러스터는 API 서버를 가운데 둔 프로그램 여러 개다
2편. kubectl apply 한 번이 파드가 되기까지
3편. 노드를 VM 으로 만들고 네트워크를 두 개 붙였다 ← 지금 이 글
4편. swap 을 켜면 kubelet 이 시작하지 않는다

ping 을 네 번 쳤는데 두 번은 되고 두 번은 안 됐어요. 마스터 VM 에서 worker1 의 192.168.104.3 으로 보낸 ping 은 2개가 모두 돌아왔고, 같은 worker1 의 다른 주소 192.168.64.3 으로 보낸 ping 은 하나도 돌아오지 않았습니다. Mac 에서 같은 두 주소로 보내자 결과가 정확히 뒤집혔어요. 192.168.64.3 은 2개를 다 받았고, 192.168.104.3 은 100% 손실이었습니다.

쿠버네티스 강의를 따라 하려고 Apple Silicon Mac 위에 VM 네 대(마스터 1대, 워커 3대)로 실습 클러스터를 만들던 중이었어요. worker1 에는 서로 다른 네트워크에 붙은 주소가 두 개 있었고, 어느 네트워크로 어디서 보냈는지에 따라 결과가 반씩 갈렸습니다. 결국 이 클러스터의 노드는 모두 네트워크를 두 개씩 달고 있어요.

1·2편에서는 클러스터가 무엇으로 이뤄져 있는지 봤어요. 이번 편부터는 그 클러스터를 실제로 어떻게 만들었는지 적습니다. 이번 질문은 두 가지예요. kind·minikube 를 두고 왜 VM 에 kubeadm 으로 클러스터를 만들었나, 그리고 왜 노드마다 NIC 가 둘인가.

이 글에서 다룰 것
· kind·minikube 가 있는데 왜 노드를 VM 으로 만들었을까?
· VM 을 띄우는 도구로 Lima 를 고른 이유는 무엇일까?
· ping 네 번의 결과는 왜 정확히 반씩 갈렸을까?
· 노드에 NIC 가 둘이면 무엇을 따로 정해 줘야 할까?
· 처음 ./lab up 을 친 뒤 368초 동안 무슨 일이 일어날까?

1. 노드에 들어가 swap 을 꺼 볼 수 있어야 했다

강의 실습은 클러스터 밖에서 kubectl 만 치고 끝나지 않았어요. 노드에 ssh 로 들어가 swap 을 끄고, 커널 모듈을 올리고, containerd 설정 파일을 고치고, kubelet 이 왜 뜨지 않는지 journalctl 로 로그를 봐야 했습니다. 이걸 그대로 따라 하려면 노드 한 대 한 대가 자기 커널과 swap 을 가진 리눅스 머신이어야 했어요. 그래야 worker3 한 대에만 swap 을 켜 보고 그 노드의 kubelet 이 어떻게 반응하는지 볼 수 있습니다(4편).

로컬에서 클러스터를 띄우는 도구로는 kind 와 minikube 가 먼저 떠올라요. 공식 문서를 다시 읽어 보니 둘 다 이 목적과는 조금씩 어긋났습니다.

kind 의 공식 소개 첫 문장은 "Docker 컨테이너 '노드'로 로컬 쿠버네티스 클러스터를 띄우는 도구"예요. 노드 하나가 컨테이너 하나입니다. 컨테이너는 자기 커널을 따로 갖지 않으므로, kind 로 노드 네 대를 띄우면 네 노드가 커널과 swap 을 그 컨테이너들을 돌리는 머신 하나와 같이 씁니다. 문서에는 원래 쿠버네티스 자체를 테스트하려고 설계했고, 로컬 개발이나 CI 에도 쓸 수 있다고 적혀 있어요.

minikube 는 minikube start 의 --nodes 옵션 설명이 "띄울 노드의 총수, 기본값 1"이에요. --nodes 2 로 노드를 늘릴 수는 있지만, 아무것도 지정하지 않으면 노드 한 대짜리 클러스터가 생깁니다.

두 도구 모두 클러스터를 빨리 얻는 데는 좋아요. 다만 제가 보고 싶었던 건 완성된 클러스터보다 클러스터가 만들어지는 과정이었습니다. 노드마다 무엇을 준비해야 하는지, kubeadm init 이 무엇을 만드는지, 워커가 어떻게 클러스터에 들어오는지를 직접 명령으로 치고 출력으로 확인하고 싶었어요. 그래서 노드는 VM 으로 만들고, 클러스터는 kubeadm 으로 직접 구성했습니다.

📖 용어: kubeadm
쿠버네티스 프로젝트가 만든 클러스터 구성 도구예요. 마스터에서 kubeadm init 을 치면 컨트롤 플레인이 만들어지고, 워커에서 kubeadm join 을 치면 그 노드가 클러스터에 들어와요. 그 전에 노드마다 컨테이너 런타임을 설치하고 swap 을 정리하는 준비는 사용자가 직접 해야 합니다(4편).
💡 실무에서는: 무엇을 연습할지로 도구를 고른다
매니페스트를 쓰고 kubectl apply 로 적용해 보는 연습이 목적이면 kind 나 minikube 로 충분해요. 노드 준비나 노드 장애, 노드마다 다른 설정을 다루는 실습이 필요할 때는 VM 을 쓰면 됩니다. 이 실습 환경은 노드 한 대에 swap 을 켜 보는 실험(4편)과 노드를 껐다 켜는 실험(7편)이 필요해서 VM 을 골랐어요.

2. VM 은 sudo 없이 설치되는 Lima 로 띄웠다

VM 네 대를 띄울 도구로는 Lima 를 골랐어요. 이유는 세 가지였습니다.

첫째, 설치와 네트워크 설정에 관리자 권한이 필요 없었어요. Lima 는 brew install lima 한 줄로 설치되고 sudo 를 묻지 않았습니다. VM 이 Mac 에서 닿는 주소를 받으려면 네트워크를 따로 붙여야 하는데, 공식 문서에 따르면 socket_vmnet 방식은 데몬을 켜고 끄는 데 root 권한이 필요해서 비밀번호 없는 sudo 를 켜거나 sudoers 파일에 명령을 등록해야 해요. 반면 vz VM 에서 쓰는 vzNAT 은 "socket_vmnet 도, sudoers 파일도 필요 없다"고 적혀 있습니다. 실습용 VM 을 띄우려고 Mac 의 시스템 설정을 바꿀 필요가 없었어요.

둘째, Apple Silicon 에 맞는 가상화를 기본으로 써요. Lima 의 vz 는 macOS 의 Virtualization.framework 를 쓰는 VM 방식이고, Lima v1.0 부터 macOS 13.5 이상에서 새로 만드는 VM 의 기본값입니다. 이 실습은 Lima 2.2.1 을 썼으니 VM 정의에 적은 vmType: vz 는 기본값을 명시해 둔 것이에요. 노드 커널도 arm64 용(6.8.0-142-generic)으로 떴습니다.

셋째, VM 의 첫 설정을 cloud-init 으로 처리해서, VM 정의 파일 하나로 노드 네 대를 같은 모양으로 만들 수 있었어요.

📖 용어: cloud-init
VM 이 켜질 때 사용자 계정, 패키지, 실행할 스크립트 같은 초기 설정을 읽어 적용하는 프로그램이에요. Lima 기본 템플릿 주석에 따르면 Lima 의 프로비저닝 스크립트는 부팅할 때마다 cloud-init 의 init·config·final 단계에서 처리됩니다. 그래서 스크립트는 여러 번 실행돼도 결과가 같게 짜야 한다고 적혀 있어요.

마스터와 워커가 같이 쓰는 VM 정의 파일의 앞부분은 이래요.

# lima/k8s-node.yaml (앞부분) base: template:_images/ubuntu-24.04 vmType: vz cpus: 2 memory: 4GiB disk: 30GiB mounts: [] containerd: system: true user: false

→ 우분투 24.04 이미지로 vz VM 을 만들되 CPU 2, 메모리 4GiB, 디스크 30GiB 를 주고, Mac 홈 디렉터리는 붙이지 않고, containerd 는 root 용 시스템 서비스로만 설치하라는 뜻이에요. Lima 가 nerdctl-full 번들로 containerd 2.4.1 을 깔아 줬고, kubelet 은 이 containerd 를 씁니다.

3. ping 네 번이 반씩 갈린 이유

VM 네 대가 클러스터가 되려면 네트워크에 두 가지가 필요했어요. 첫째는 VM 끼리의 통신이에요. 워커의 kubelet 은 마스터의 API 서버(6443 포트)에 접속해야 하고, 다른 노드에 있는 파드끼리도 노드 사이 네트워크를 거쳐 통신합니다. 둘째는 Mac 에서 VM 으로 가는 경로예요. Mac 터미널의 kubectl 이 API 서버에 닿아야 하고, NodePort 서비스(노드의 지정 포트로 들어온 요청을 파드로 넘기는 서비스)를 Mac 브라우저로 열려면 Mac 에서 워커 IP 로 갈 수 있어야 해요.

Lima 에서 sudo 없이 붙일 수 있는 네트워크 두 개를 후보로 놓고, worker1 에 둘 다 붙여 시험했어요.

📖 용어: user-v2
Lima 의 사용자 모드 네트워크예요. 공식 문서는 기본 사용자 모드 네트워크와 비슷하면서 VM 에서 VM 으로 가는 통신을 지원한다고 설명합니다. 이걸 켜면 Lima 의 기본 사용자 모드 네트워크는 꺼져요. 이 실습에서는 192.168.104.0/24 대역의 주소를 받았습니다.
📖 용어: vzNAT
vmType 이 vz 인 VM 에서만 쓸 수 있는 Lima 네트워크예요. Lima 기본 템플릿 주석에는 "vzNAT IP 는 호스트에서는 접근되지만 다른 게스트에서는 접근되지 않는다"고 적혀 있습니다. 이 실습에서는 192.168.64.0/24 대역의 주소를 받았어요.

두 네트워크를 붙인 worker1 의 주소부터 봤어요.

worker1$ ip -4 -br addr lo UNKNOWN 127.0.0.1/8 eth0 UP 192.168.104.3/24 metric 200 lima1 UP 192.168.64.3/24 metric 100 tunl0@NONE UNKNOWN 10.244.194.64/32

→ eth0 이 user-v2 의 192.168.104.3, lima1 이 vzNAT 의 192.168.64.3 을 받았다는 뜻이에요. tunl0 은 Calico 가 파드 트래픽용으로 만든 터널이라 여기서는 넘어갑니다(6편).

그다음 마스터와 Mac 에서 이 두 주소로 ping 을 두 개씩 보냈어요.

그림 1. 같은 worker1 이라도 어디서, 어느 주소로 보냈는지에 따라 결과가 반씩 갈렸다

숫자로 정리하면 이래요. 마스터에서 eth0(192.168.104.3)으로 보낸 ping 은 2개 중 2개가 돌아왔고 평균 0.252ms 였어요. 마스터에서 lima1(192.168.64.3)로 보낸 ping 은 100% 손실이었습니다. Mac 에서는 반대로 lima1 이 2개 중 2개, 평균 0.344ms 였고 eth0 은 100.0% 손실이었어요. user-v2 는 VM 끼리만, vzNAT 은 Mac 에서 VM 으로만 닿았습니다.

두 결과 모두 공식 문서와 맞았어요. vzNAT 은 템플릿 주석에 적힌 대로 다른 게스트에서는 닿지 않았습니다. user-v2 문서는 호스트에서 이 네트워크로 들어가려면 limactl tunnel 로 SOCKS 프록시를 만들라고 안내하는데, 이 기능은 실험 단계라고 적혀 있어요. 이 실습에서는 프록시를 쓰는 대신 vzNAT 을 하나 더 붙이는 쪽을 택했습니다.

그림 2. 어느 네트워크 하나만 골라서는 초록 칸이 하나뿐이라, 둘을 다 붙여야 했다

4. 그래서 노드마다 NIC 를 두 개 붙였다

한쪽만 되는 네트워크 두 개를 모두 붙이기로 했어요. VM 정의 파일의 networks 항목은 이렇게 생겼습니다.

networks: # eth0: VM 끼리 통신하는 클러스터 네트워크(192.168.104.0/24). 노드 IP·API 서버 주소가 여기 붙는다. # user-v2 를 첫 번째로 두면 Lima 기본 NIC(eth0)를 대신한다. - lima: user-v2 # lima1: Mac 에서 VM 으로 들어오는 길(192.168.64.0/24). kubectl·NodePort 를 Mac 에서 바로 부른다. # vzNAT 은 Mac -> VM 만 되고 VM <-> VM 은 안 되므로 클러스터 통신에는 쓰지 않는다. - vzNAT: true

→ 첫 번째로 적은 user-v2 가 eth0 이 되고, 두 번째로 적은 vzNAT 이 lima1 이 된다는 뜻이에요. user-v2 를 켜면 Lima 의 기본 사용자 모드 네트워크가 꺼지므로, 원래 기본 네트워크가 쓰던 eth0 자리를 user-v2 가 차지합니다. 앞의 ip addr 출력이 그 결과예요.

역할은 이렇게 나눴어요. eth0 은 클러스터 안의 통신을 맡습니다. kubelet 이 노드를 등록하는 IP, kubeadm 설정의 API 서버 주소 advertiseAddress(마스터의 192.168.104.1), 워커가 조인할 때 찾아가는 주소(kubeadm join 192.168.104.1:6443)가 모두 eth0 에 있어요. lima1 은 Mac 에서 들어오는 요청만 받습니다. Mac 용 kubeconfig(kubectl 이 어느 API 서버에 어떤 인증서로 붙을지 적은 설정 파일)는 서버 주소를 마스터의 lima1 IP(192.168.64.2)로 바꿔 두었고, NodePort 는 Mac 에서 워커의 lima1 IP(192.168.64.3~5)로 엽니다.

📖 용어: 노드 IP (INTERNAL-IP)
kubelet 이 노드를 클러스터에 등록할 때 함께 기록하는 그 노드의 주소예요. kubectl get nodes -o wide 의 INTERNAL-IP 칸에 나옵니다. 이 실습에서는 Calico 가 이 주소를 보고 노드 사이의 파드 경로를 만들어서, 이 값이 틀리면 다른 노드의 파드와 통신하는 경로가 엉뚱한 주소를 향하게 돼요.
그림 3. 클러스터 안의 통신은 eth0 으로, Mac 에서 들어오는 요청은 lima1 로 나눴다

NIC 가 둘이면 노드 IP 를 직접 정해 줘야 한다

NIC 를 두 개 붙이자 문제가 하나 따라왔어요. 노드에 IPv4 주소가 둘이니, 쿠버네티스 구성 요소가 "이 노드의 IP"를 스스로 고를 때 lima1 을 고를 수도 있습니다. 공식 문서를 보면 kubelet 은 --node-ip 를 주지 않으면 "노드의 기본 IPv4 주소"를 쓰고, Calico 의 기본 감지 방식(first-found)은 "첫 번째 인터페이스의 첫 번째 유효한 IP"를 골라요. 어느 기준도 eth0 을 고른다는 보장이 없습니다. 노드가 lima1 의 192.168.64.x 로 등록되면, 다른 노드는 그 주소로 이 노드에 닿지 못해요. vzNAT 은 VM 끼리 통하지 않으니까요. NIC 를 늘리면 쿠버네티스가 어느 주소를 쓸지도 직접 정해 줘야 했습니다.

그래서 두 곳에 eth0 의 IP 를 쓰라고 적었어요. kubelet 에는 /etc/default/kubelet 에 --node-ip 를 넣었고, Calico 에는 감지 방식을 kubernetes-internal-ip 로 바꿨습니다.

worker1$ cat /etc/default/kubelet KUBELET_EXTRA_ARGS=--node-ip=192.168.104.3 master$ kubectl -n kube-system get ds calico-node -o yaml | grep -A1 -E 'name: (CALICO_IPV4POOL_CIDR|IP_AUTODETECTION_METHOD|CALICO_IPV4POOL_IPIP)$' - name: IP_AUTODETECTION_METHOD value: kubernetes-internal-ip - name: CALICO_IPV4POOL_IPIP value: Always -- - name: CALICO_IPV4POOL_CIDR value: 10.244.0.0/16

→ worker1 의 kubelet 은 eth0 주소 192.168.104.3 으로 노드를 등록하고, Calico 는 직접 감지하는 대신 쿠버네티스에 등록된 노드의 첫 번째 InternalIP 를 쓰라는 뜻이에요. 나머지 두 설정(IPIP, 파드 대역)은 6편에서 다룹니다.

그 결과 노드 4대의 INTERNAL-IP 는 192.168.104.1, .3, .4, .5 로 모두 eth0 주소가 됐어요. 5절의 노드 목록에서 확인할 수 있습니다.

⚠️ 주의: NIC 가 둘인 노드는 INTERNAL-IP 부터 본다
NIC 가 여러 개인 노드로 클러스터를 만들었다면, 다른 것을 보기 전에 kubectl get nodes -o wide 의 INTERNAL-IP 가 노드끼리 통하는 대역인지 확인하세요. 이 실습이라면 전부 192.168.104.x 여야 해요. kubelet 쪽 설정은 4편, Calico 쪽 설정은 6편에서 자세히 다룹니다.

Lima 의 자동 포트 포워딩은 껐다

NIC 말고도 Lima 의 기본 동작 하나를 꺼야 했어요. 공식 문서에 따르면 Lima 는 게스트(VM)의 localhost 포트를 호스트(Mac)로 자동 포워딩해 줍니다. VM 이 한 대라면 편한 기능이지만, 쿠버네티스 노드는 모두 같은 포트를 열어요. kubelet 의 10248 포트만 해도 네 노드가 전부 엽니다. 노드 4대가 Mac 의 같은 포트를 두고 충돌하게 되니 이 기능을 껐어요.

# Lima 기본 동작은 VM 이 여는 포트를 Mac 의 localhost 로 자동 포워딩한다. # 노드 4대가 같은 포트(kubelet 10248 등)를 열어 충돌하므로 끈다. Mac 접근은 vzNAT IP 로 한다. portForwards: - guestIP: "0.0.0.0" guestIPMustBeZero: false proto: any ignore: true - guestIP: "127.0.0.1" proto: any ignore: true

→ VM 안에서 열린 포트를 프로토콜과 상관없이 Mac 으로 넘기지 말라(ignore)는 규칙 두 개예요. Lima 는 이 규칙들을 위에서부터 차례로 보고 처음 맞는 규칙을 적용합니다.

Mac 에서 노드에 닿아야 할 때는 포워딩 대신 각 노드의 lima1 주소로 직접 가요. 노드마다 주소가 다르니 네 노드가 같은 포트를 열어도 서로 부딪히지 않습니다.

5. 처음 ./lab up 의 368초

노드 네 대에 같은 준비를 손으로 반복하면 한 대만 빠뜨려도 클러스터가 어긋나요. 그래서 ./lab up 명령 하나로 VM 생성부터 노드 4대 Ready 까지 이어지게 묶었습니다. 처음 실행했을 때의 출력은 이랬어요.

그림 4. 노드마다 같은 일은 동시에, 마스터가 먼저여야 하는 일은 차례로 했다

단계마다 하는 일은 이래요. ①② limactl create 로 VM 정의 파일 하나에서 VM 4대를 만들고, 마스터를 먼저 켠 뒤 워커 3대를 동시에 켭니다. 마스터를 먼저 켜는 건 첫 실행 때 우분투 이미지를 한 번만 받아 캐시해 두고 워커가 그걸 같이 쓰게 하려는 것이에요. 출력에서 워커가 worker2, worker3, worker1 순으로 찍힌 것도 동시에 켰기 때문입니다.

③ scripts/node-setup.sh 를 네 노드에서 동시에 root 로 실행해요. swap 끄기, 커널 모듈과 sysctl, kubeadm·kubelet·kubectl 설치, containerd 설정, 앞에서 본 node-ip 고정이 여기서 일어납니다(4편). ④ 마스터에서 scripts/master-init.sh 가 kubeadm init 을 하고 Calico 매니페스트를 적용해요(5편, 6편). ⑤ 마스터에서 kubeadm token create --print-join-command 로 조인 명령을 받아 워커 3대에서 동시에 실행합니다. ⑥ 노드 4대가 Ready 가 되고 calico-node 와 coredns 가 준비될 때까지 기다린 뒤, Mac 용 kubeconfig 를 만들고 요약을 출력해요.

노드 목록의 AGE 로 거꾸로 계산해 보면 대략의 배분이 보여요. 마스터의 AGE 가 3m16s(196초)이니, 368초 중 앞의 172초쯤은 마스터가 노드로 등록되기 전, 즉 VM 생성·부팅·노드 공통 설정과 kubeadm init 의 앞부분에 들어갔다는 계산이 나옵니다. 워커는 마스터보다 14초 늦게(3m2s) 등록됐어요. AGE 는 마지막 출력 시점 기준이라 정확한 경계는 아니고, 단계별 시간을 따로 재지는 않았습니다.

두 번째 실행부터는 훨씬 빨라요. 단계마다 이미 끝난 일은 건너뛰도록 짰기 때문이에요. VM 이 있으면 만들지 않고, 마스터에 /etc/kubernetes/admin.conf 가 있으면 init 을 하지 않고, 워커에 /etc/kubernetes/kubelet.conf 가 있으면 조인하지 않습니다. 노드 공통 설정은 매번 돌지만 패키지 설치와 containerd·kubelet 설정은 이미 같으면 건너뛰어요. 그래서 꺼진 클러스터를 다시 켜는 ./lab up 은 50초, 켜져 있을 때는 약 2초에 끝났습니다. 다시 켤 때 생긴 문제는 7편에서 다뤄요.

📖 용어: 멱등성 (idempotency)
같은 작업을 여러 번 실행해도 결과가 한 번 실행한 것과 같은 성질이에요. ./lab up 의 스크립트는 이 성질을 갖도록 짜서, 다시 실행해도 이미 끝난 단계는 건너뛰고 남은 단계만 진행합니다.
💡 실무에서는: 화면에는 단계만, 자세한 출력은 노드별 로그로
./lab up 은 화면에 단계 이름만 찍고, 각 단계의 실제 출력은 .lab/logs/<노드>.log 에 남겨요. 실패하면 어느 노드의 로그를 보라고 경로를 알려 주고 멈춥니다. 노드 여러 대에 동시에 설치하는 스크립트는 이렇게 화면과 로그를 나눠 두면, 성공했을 때는 출력이 짧고 실패했을 때는 어느 노드에서 무엇이 틀렸는지 바로 찾을 수 있어요.
✍️ 오늘의 요약
강의 실습은 노드에 들어가 swap·커널·containerd 를 만져야 해서, 노드를 Lima VM 으로 만들고 kubeadm 으로 클러스터를 직접 구성했어요.

Lima 의 user-v2 는 VM 끼리만, vzNAT 은 Mac 에서 VM 으로만 닿았어요. 그래서 eth0(user-v2)에는 노드 IP 를, lima1(vzNAT)에는 Mac 에서의 접속을 맡기고, kubelet 과 Calico 가 eth0 의 IP 를 쓰도록 고정했습니다. 네트워크를 하나 더 붙이면, 쿠버네티스가 어느 주소를 쓸지도 함께 정해 줘야 해요.
