9편 끝에서 Headlamp 로그인 화면을 Mac 의 localhost:18809 로 열었어요. kubectl port-forward 가 API 서버를 거쳐 Mac 의 포트를 클러스터 안의 Headlamp 서비스로 이어 준 덕분이었습니다. 화면에는 "인증 토큰을 붙여넣어 주세요"라는 문장과 ID 토큰 입력칸 하나, 그리고 "서비스 계정 토큰 생성 방법을 확인하세요"라는 안내가 있었어요. 이 칸에 넣을 토큰을 만드는 것이 이번 글의 일이에요.

강의는 이 자리에서 admin-user 라는 ServiceAccount 를 만들고 클러스터 관리자 권한을 묶어요. 그 실습을 우리 클러스터로 옮겨 토큰을 받는 데까지는 금방이었습니다. 문제는 그다음이었어요. 받은 토큰은 한 시간이 지나면 만료됐고, 실습하는 동안 한 시간마다 토큰을 새로 받아 붙여넣는 일이 귀찮았어요. 그래서 토큰 수명을 0 으로 주기로 했습니다. 0 이면 만료가 없을 거라고 생각했거든요.

master$ kubectl -n headlamp create token admin-user --duration=0 | (토큰 가운데 부분을 풀어 sub 와 exp 만 출력, 전체 명령은 4절) sub: system:serviceaccount:headlamp:admin-user exp: 1794226746

→ admin-user 의 토큰을 수명 0 으로 발급받아, 토큰 원문 대신 안에 적힌 주인(sub)과 만료 시각(exp)만 꺼내 본 결과예요. exp 는 1970년 1월 1일 0시(UTC)부터 센 초 단위 시각입니다.

1794226746 을 한국 시간으로 바꾸면 2026년 11월 9일 21시 19분 6초예요. 토큰을 받은 지 정확히 한 시간 뒤였습니다. 수명을 0 으로 달라고 했는데, 옵션 없이 받았을 때와 똑같은 한 시간짜리 토큰이 나온 거예요. 0 은 "만료 없음"이라는 뜻이 아니었어요.

이 글은 그 한 시간이 어디서 정해지는지 따라가요. 앞쪽은 강의의 admin-user 를 우리 버전으로 옮긴 과정이에요. 처음에는 kube-system 네임스페이스에 만들었다가 전용 네임스페이스로 옮겼는데, 그 이유가 뒤의 토큰 이야기와 이어집니다. 뒤쪽은 토큰이에요. 1.24 부터 바뀐 토큰 발급 방식, --duration=0 의 실제 의미, 만료 없는 토큰을 만드는 방법과 그 대가, 그리고 그 토큰이 정말 admin-user 로 인증되는지 확인하다가 헷갈렸던 지점까지 다뤄요. 실습 환경은 앞 편들과 같은 Lima VM 4대(마스터 1대, 워커 3대)이고, 쿠버네티스는 v1.37.2 예요.

이 글에서 다룰 것
· 강의의 admin-user 는 무엇을 만들고, 우리 클러스터에서는 무엇이 달라졌을까?
· 권한은 같은데 kube-system 에 두면 왜 곤란할까?
· ServiceAccount 를 만들어도 왜 토큰이 따라오지 않을까?
· --duration=0 은 왜 한 시간짜리 토큰을 줬을까?
· 만료 없는 토큰은 어떻게 만들고, 그 대가는 무엇일까?
· kubectl auth whoami 는 왜 토큰이 아니라 인증서의 주인을 보여 줬을까?

1. 강의의 admin-user 는 ServiceAccount 하나와 바인딩 하나다

Headlamp 로그인 칸에 넣는 토큰은 API 서버가 인정하는 신원이어야 해요. 그런 신원이 없으면 로그인 화면을 넘어갈 수 없습니다. Headlamp 차트의 설정 값 설명(values.yaml)을 보면, 기본 설정에서 Headlamp 는 사용자마다 자기 토큰으로 인증하게 해요. 파드 자신의 ServiceAccount 로 모든 사용자를 인증시키는 옵션(config.unsafeUseServiceAccountToken)은 설명 첫머리에 "UNSAFE" 라고 적혀 있고 기본값이 꺼져 있어요. 그래서 로그인하는 사람이 쓸 신원이 따로 필요했습니다.

강의 슬라이드는 이 신원을 만드는 과정을 YAML 파일 두 개로 보여 줘요. 마스터에 dashboard_rbac 폴더를 만들고, 첫 파일 dashboard-admin-user.yaml 에는 kubernetes-dashboard 네임스페이스의 ServiceAccount admin-user 를 적어요. 둘째 파일 ClusterRoleBinding-admin-user.yml 은 이 계정에 ClusterRole cluster-admin 을 묶는 ClusterRoleBinding 이에요. 두 YAML 은 은퇴한 Kubernetes Dashboard 저장소의 문서 Creating sample user 에 실린 예시와 이름, 네임스페이스, 내용이 같았어요. 그 문서는 이어서 토큰을 받는 방법 두 가지를 적어 두는데, 이 글의 3절과 5절이 바로 그 두 방법이에요.

📖 용어: ServiceAccount (서비스 계정)
사람이 아닌 프로그램이 API 서버에 자기를 밝힐 때 쓰는 계정이에요. 주로 파드나 자동화 작업이 쓰고, 네임스페이스마다 따로 만들어요. 네임스페이스를 만들면 default 라는 ServiceAccount 가 자동으로 하나 생겨요. 사람 계정은 쿠버네티스 안에 객체로 존재하지 않아서, 이번 실습에서는 사람이 이 계정의 토큰으로 로그인합니다.
📖 용어: ClusterRole 과 ClusterRoleBinding
ClusterRole 은 "어떤 리소스에 어떤 동작을 할 수 있다"는 규칙 묶음이고, ClusterRoleBinding 은 그 묶음을 누구(사용자, 그룹, ServiceAccount)에게 줄지 적은 객체예요. 둘 다 네임스페이스에 속하지 않고 클러스터 전체에 효력이 있어요. 한 네임스페이스 안에서만 권한을 주려면 RoleBinding 을 씁니다.

강의를 그대로 옮기면 네임스페이스가 걸려요. 우리 클러스터에는 Dashboard 가 없으니 kubernetes-dashboard 네임스페이스도 없습니다. 처음에는 admin-user 를 Headlamp 가 있던 kube-system 에 만들었어요. 파일은 실습 저장소의 shared/headlamp_rbac/ 에 두었고, 노드에서는 공유 폴더 /lab/headlamp_rbac 로 보여요(7편). 강의 YAML 에서 바꾼 곳은 두 파일의 namespace 한 줄씩이었어요. 적용한 뒤의 결과는 이랬습니다.

master$ kubectl apply -f headlamp-admin-user.yaml -f ClusterRoleBinding-admin-user.yaml serviceaccount/admin-user unchanged clusterrolebinding.rbac.authorization.k8s.io/admin-user unchanged master$ kubectl -n kube-system get serviceaccount admin-user NAME AGE admin-user 14s master$ kubectl get clusterrolebinding admin-user -o wide NAME ROLE AGE USERS GROUPS SERVICEACCOUNTS admin-user ClusterRole/cluster-admin 14s kube-system/admin-user

→ 원자료를 남기려고 같은 apply 를 한 번 더 실행해서 unchanged(이미 같은 내용이 있음)가 찍혔어요. 새로 만들 때는 created 가 찍힙니다(2절의 출력). ClusterRoleBinding admin-user 가 ClusterRole cluster-admin 을 ServiceAccount kube-system/admin-user 에게 준다는 뜻이에요.

cluster-admin 은 쿠버네티스에 처음부터 들어 있는 기본 ClusterRole 이에요. RBAC 문서는 이 역할을 "모든 리소스에 대해 모든 동작을 허용하는 슈퍼유저 권한"이라고 설명하고, ClusterRoleBinding 으로 묶으면 "클러스터의 모든 리소스와 모든 네임스페이스를 완전히 제어하게 된다"고 적어요. 정말 그런지 kubectl auth can-i 로 물어봤어요.

master$ kubectl auth can-i '*' '*' --as=system:serviceaccount:kube-system:admin-user yes master$ kubectl auth can-i '*' '*' --as=system:serviceaccount:kube-system:nobody # 비교: 권한 없는 계정 no

→ admin-user 인 척하고 "모든 리소스에 모든 동작을 해도 되나"를 물으니 yes, 같은 네임스페이스의 nobody 로 물으니 no 라는 뜻이에요. nobody 는 만든 적이 없는 이름이라 어떤 바인딩도 받지 않았어요.

--as 는 지금의 사용자가 다른 사용자인 척하고 요청하는 옵션(impersonation)이에요. 마스터의 kubectl 은 5편에서 본 관리자 인증서로 접속하고, 그 권한에는 다른 사용자인 척할 권한도 들어 있어요. ServiceAccount 의 사용자 이름은 system:serviceaccount:<네임스페이스>:<이름> 형식이라서 네임스페이스가 이름의 일부가 됩니다. '*' '*' 는 can-i 레퍼런스의 예시대로 지금 네임스페이스에서 모든 동작이 되는지 묻는 표현이에요. 클러스터 전체에 걸친 권한이라는 것은 위의 바인딩 출력이 보여 줍니다.

차트가 이미 cluster-admin 을 하나 만들어 두었다

admin-user 를 만들기 전에도 이 클러스터에는 cluster-admin 을 가진 ServiceAccount 가 하나 있었어요. 9편에서 Helm 이 Headlamp 와 함께 만든 리소스 중에 ClusterRoleBinding headlamp-admin 이 있었습니다.

master$ kubectl get clusterrolebinding headlamp-admin -o wide NAME ROLE AGE USERS GROUPS SERVICEACCOUNTS headlamp-admin ClusterRole/cluster-admin 78s kube-system/headlamp

→ 차트가 만든 ServiceAccount kube-system/headlamp 에게 cluster-admin 이 묶여 있다는 뜻이에요(kube-system 에 설치했던 때의 출력).

Headlamp 차트 0.46.0 의 values.yaml 을 보면 clusterRoleBinding.create 의 기본값이 true, 묶을 역할을 정하는 clusterRoleBinding.clusterRoleName 의 기본값이 cluster-admin 이에요. 설치할 때 권한에 대해 아무것도 지정하지 않으면 이 바인딩이 생긴다는 뜻입니다. 차트가 설치 끝에 찍어 준 안내문도 로그인 토큰을 이 계정으로 받으라고 했어요(kubectl create token headlamp --namespace kube-system). 9편의 첫 로그인도 이 계정의 토큰으로 했습니다. 그러니 admin-user 를 만든 뒤로 이 클러스터에는 cluster-admin 을 가진 ServiceAccount 가 둘이 됐어요.

headlamp 계정에는 한 가지가 더 있어요. 차트의 automountServiceAccountToken 기본값이 true 라서 Headlamp 파드 안에는 이 계정의 토큰이 자동으로 들어가요. 그 파드의 파일을 읽을 수 있는 사람은 cluster-admin 토큰을 읽을 수 있다는 뜻이에요. 이 바인딩은 지금 그대로 두었고, 역할을 좁히거나 없애는 일은 정리할 거리로 남겨 두었어요(5절 끝의 💡).

ServiceAccount 는 네임스페이스에 속하지만, ClusterRoleBinding 으로 받은 권한은 네임스페이스와 상관없이 클러스터 전체에 미쳐요. 그림 1 은 옮긴 뒤의 모습이에요.

그림 1. 두 ServiceAccount 는 headlamp 네임스페이스에 속하지만, 바인딩으로 받은 권한은 클러스터 전체에 미친다

2. kube-system 에 두면 그 네임스페이스의 권한이 곧 cluster-admin 이 된다

kube-system 에 admin-user 를 만들고 결과까지 확인한 뒤에 네임스페이스가 마음에 걸렸어요. 강의는 Dashboard 전용 네임스페이스인 kubernetes-dashboard 에 admin-user 를 두는데, 우리는 시스템 네임스페이스에 둔 셈이었으니까요. 걸린 이유는 두 가지였어요.

첫째, kube-system 은 쿠버네티스가 스스로 만든 객체를 두는 곳이에요. 네임스페이스 문서는 kube-system 을 "쿠버네티스 시스템이 만든 객체를 위한 네임스페이스"라고 설명해요. 1편에서 본 컨트롤 플레인 정적 파드와 calico-node, kube-proxy, coredns 가 모두 여기에 있어요. 사람이 로그인할 때 쓰는 계정이 그 사이에 섞이면, 나중에 무엇이 시스템 것이고 무엇이 우리가 만든 것인지 구분하기 어려워요. 실습을 정리하면서 지울 때 엉뚱한 것을 지울 위험도 커지고요.

둘째가 더 중요했어요. 같은 네임스페이스 안에서 할 수 있는 일 몇 가지는 그 네임스페이스에 있는 ServiceAccount 의 권한으로 일하는 것과 같아요. RBAC 모범 사례 문서와 Secret 문서가 이런 경우를 짚어요.

· 어떤 네임스페이스에 파드(또는 Deployment 같은 워크로드)를 만들 수 있으면, 그 파드를 그 네임스페이스의 아무 ServiceAccount 로나 실행할 수 있어요. 문서는 이것을 "그 네임스페이스에 있는 모든 ServiceAccount 의 API 권한을 암묵적으로 받는 것"이라고 적어요.
· serviceaccounts/token 을 만들 권한(create)이 있으면 이미 있는 ServiceAccount 의 토큰을 발급할 수 있어요.
· 한 네임스페이스에 파드를 만들 수 있으면 그 네임스페이스의 Secret 을 모두 읽을 수 있어요. 5절에서 만들 만료 없는 토큰이 바로 Secret 에 저장돼요.

admin-user 가 kube-system 에 있으면, kube-system 에서 파드를 만들거나 토큰을 발급할 수 있는 주체는 누구든 cluster-admin 이 될 수 있어요. 시스템 구성 요소가 모여 있는 네임스페이스에 가장 넓은 권한을 가진 계정을 함께 둔 셈이었어요. RBAC 모범 사례 문서도 신뢰 수준이 다른 것들은 네임스페이스로 나누라고 하면서, 네임스페이스 안의 경계는 약하다고 봐야 한다고 적어요.

그래서 Headlamp 와 admin-user 를 함께 전용 네임스페이스 headlamp 로 옮겼어요. 강의가 kubernetes-dashboard 에 두는 것과 같은 방식이에요. 다만 한 가지는 분명히 해 둘게요. 옮겨도 admin-user 의 권한은 줄지 않아요. 바뀌는 것은 이 계정의 권한을 쓸 수 있는 주체의 범위예요. headlamp 네임스페이스에는 Headlamp 말고 다른 워크로드가 없고, 9편의 매니페스트 목록을 보면 차트도 이 네임스페이스에 RoleBinding 을 만들지 않아요. 적어도 "kube-system 에서 파드를 만들 수 있는 권한"이 곧 cluster-admin 으로 이어지는 연결은 끊겨요.

⚠️ 주의: 설치 문서의 예시 네임스페이스
Headlamp 의 클러스터 안 설치 문서는 helm 예시를 모두 --namespace kube-system 으로 적어 두었어요. 9편에서 처음 설치한 곳도 kube-system 이었어요. 예시를 그대로 따르면 Headlamp 와 그 로그인 계정이 시스템 네임스페이스에 들어가요. 계정과 권한을 함께 만드는 도구라면 예시를 따르기 전에 어디에 둘지 따로 정하는 편이 안전해요.
그림 2. 옮겨도 권한은 그대로다. 바뀌는 것은 admin-user 의 권한을 쓸 수 있는 주체의 범위다

옮긴 순서: 지우고, 다시 설치하고, 다시 적용한다

먼저 kube-system 의 admin-user 를 지웠어요.

master$ kubectl -n kube-system delete serviceaccount admin-user && kubectl delete clusterrolebinding admin-user serviceaccount "admin-user" deleted from kube-system namespace clusterrolebinding.rbac.authorization.k8s.io "admin-user" deleted

→ ServiceAccount 와 ClusterRoleBinding 을 둘 다 지웠다는 뜻이에요. ClusterRoleBinding 은 네임스페이스에 속하지 않으므로 -n 없이 지워요.

ClusterRoleBinding 까지 지운 데는 이유가 있어요. ServiceAccount 만 지우면 바인딩은 "kube-system 의 admin-user 에게 cluster-admin" 이라는 내용 그대로 남아요. 나중에 누군가 같은 이름의 ServiceAccount 를 다시 만들면 그 계정이 바로 cluster-admin 을 받아요. RBAC 모범 사례 문서도 지운 사용자와 같은 이름으로 계정을 만들 수 있으면 지운 사용자의 권한을 그대로 물려받는다고 경고하면서, RBAC 설정을 주기적으로 점검하라고 권해요.

다음은 Headlamp 를 옮길 차례였어요.

master$ helm uninstall headlamp -n kube-system release "headlamp" uninstalled master$ kubectl create namespace headlamp namespace/headlamp created master$ helm install headlamp headlamp/headlamp -n headlamp | head -6 NAME: headlamp LAST DEPLOYED: Mon Nov 9 20:14:10 2026 NAMESPACE: headlamp STATUS: deployed REVISION: 1 TEST SUITE: None master$ kubectl -n headlamp rollout status deploy/headlamp --timeout=180s Waiting for deployment "headlamp" rollout to finish: 0 of 1 updated replicas are available... deployment "headlamp" successfully rolled out

이번에는 --set 을 하나도 주지 않았어요. 9편에서는 NodePort 로 설치했다가 나중에 ClusterIP 로 닫았는데, 차트의 Service 기본 타입이 ClusterIP 라서 옵션 없이 설치하면 처음부터 노드 포트가 열리지 않아요. helm uninstall 은 그 릴리스가 만든 리소스를 함께 지우므로 ServiceAccount kube-system/headlamp 와 ClusterRoleBinding headlamp-admin 도 이때 사라졌고, 새 설치에서 headlamp 네임스페이스 쪽으로 다시 생겼어요.

그다음 YAML 두 개의 네임스페이스를 headlamp 로 고쳐 다시 적용했어요.

master$ cat headlamp-admin-user.yaml ClusterRoleBinding-admin-user.yaml | grep -v '^#' apiVersion: v1 kind: ServiceAccount metadata: name: admin-user namespace: headlamp apiVersion: rbac.authorization.k8s.io/v1 kind: ClusterRoleBinding metadata: name: admin-user roleRef: apiGroup: rbac.authorization.k8s.io kind: ClusterRole name: cluster-admin subjects: - kind: ServiceAccount name: admin-user namespace: headlamp master$ kubectl apply -f headlamp-admin-user.yaml -f ClusterRoleBinding-admin-user.yaml serviceaccount/admin-user created clusterrolebinding.rbac.authorization.k8s.io/admin-user created

옮긴 뒤에는 port-forward 도 새 네임스페이스로 다시 열었어요. Mac 에서 ./lab kubectl -n headlamp port-forward svc/headlamp 18809:80 을 실행하자 localhost:18809 가 다시 200 을 돌려줬어요. 이번에는 admin-user 의 10분짜리 토큰으로 로그인했습니다(10분인 이유는 3절에서 다뤄요).

그림 3. admin-user 로 들어간 개요 화면. 노드 4/4, 파드 16/16 이 보이고, 이벤트에는 옮기기 전과 후의 Headlamp 파드가 함께 남아 있다

개요 화면에는 CPU 8 단위, 메모리 15.25 GB, 파드 16/16, 노드 4/4 가 보여요. 클러스터 전체를 볼 수 있는 계정으로 들어왔다는 뜻이에요. 이벤트 표에는 경고가 16건 있었는데, 맨 위 두 줄이 이번 네임스페이스 이동을 그대로 보여 줘요. 첫 줄은 headlamp 네임스페이스의 새 파드 headlamp-86c49cb4f4-9srjd 가 24초 전에 남긴 readiness probe 실패(connection refused)예요. 컨테이너가 막 떠서 4466 포트를 열기 전에 검사가 한 번 실패한 것으로 보여요. 둘째 줄은 kube-system 에 있던 옛 파드 headlamp-86c49cb4f4-lpwl8 의 같은 경고로, 8분 23초 전 기록이에요. 파드는 helm uninstall 로 이미 지워졌지만 이벤트는 남아 있었어요. kube-apiserver 레퍼런스에 적힌 이벤트 보관 기간(--event-ttl)의 기본값이 1시간이고, 우리 kube-apiserver 매니페스트에는 이 플래그가 없어서 기본값이 적용되기 때문이에요.

3. ServiceAccount 를 만들어도 토큰은 따라오지 않는다

로그인하려면 admin-user 의 토큰이 필요해요. 쿠버네티스 1.23 까지는 ServiceAccount 를 만들면 토큰이 든 Secret 이 자동으로 따라 생겼어요. 그래서 예전 방식은 Secret 목록에서 <계정 이름>-token 으로 시작하는 Secret 을 찾아 토큰을 꺼내는 것이었어요(아래에서 볼 Headlamp 차트의 안내문에도 그 방식이 남아 있어요). admin-user 를 kube-system 에 두었을 때 그 흔적이 있는지 찾아봤어요.

master$ kubectl -n kube-system get serviceaccount admin-user -o jsonpath='{.secrets}'; echo "(secrets 필드: 비어 있음)" (secrets 필드: 비어 있음)

→ ServiceAccount 의 secrets 필드가 비어 있어 jsonpath 는 아무것도 출력하지 않았고, 뒤에 붙인 echo 문구만 찍혔다는 뜻이에요. 자동으로 만들어진 토큰 Secret 이 없어요.

ServiceAccount 개념 문서에 따르면 1.24 전에는 ServiceAccount 마다 만료 없는 토큰이 자동으로 만들어졌어요. 이 자동 생성을 막은 것이 LegacyServiceAccountTokenNoAutoGeneration 기능 게이트예요. 제거된 기능 게이트 표를 보면 1.24~1.25 에 베타로 기본으로 켜졌고, 1.26 에 GA 가 됐고, 1.28 을 끝으로 게이트 자체가 없어졌어요. 개념 문서 본문에는 "1.24~1.26 에 기본으로 켜졌고 1.27 에서 제거"로 적혀 있어 표와 버전이 조금 달라요. 어느 쪽이든 1.37 인 우리 클러스터에는 자동 생성을 다시 켤 방법이 없어요. ServiceAccount 설정 문서는 secrets 필드가 자동 생성된 Secret 에만 채워진다고도 적어요.

이 변화는 Headlamp 차트에도 그대로 남아 있어요. 설치 끝에 찍히는 안내문의 템플릿(NOTES.txt)은 클러스터의 마이너 버전이 24 이상이면 kubectl create token 을 안내하고, 그보다 낮으면 Secret 목록에서 headlamp-token 이 들어간 이름을 찾아 토큰을 꺼내라고 안내해요. 9편에서 본 안내문이 create token 이었던 것은 클러스터가 1.37 이기 때문이에요.

1.24 부터는 ServiceAccount 를 만들어도 토큰이 따라오지 않고, 필요할 때마다 API 서버에 발급을 요청해요. 그 요청이 TokenRequest API 이고, kubectl create token 이 이 API 를 부르는 명령이에요.

📖 용어: TokenRequest API
ServiceAccount 의 하위 리소스 serviceaccounts/token 에 "이 계정의 토큰을 발급해 달라"고 요청하는 API 예요. 요청할 때 유효 기간을 적을 수 있고, 발급된 토큰은 만료 시각이 지나면 쓸 수 없어요. API 서버는 발급한 토큰을 따로 기록해 두지 않아요.
master$ kubectl -n kube-system create token admin-user --duration=10m | cut -d. -f2 | python3 -c 'import sys,base64,json; p=sys.stdin.read().strip(); p+="="*(-len(p)%4); d=json.loads(base64.urlsafe_b64decode(p)); print(d["sub"], "유효시간", d["exp"]-d["iat"], "초")' system:serviceaccount:kube-system:admin-user 유효시간 600 초

→ 10분짜리 토큰을 받아 가운데 부분을 풀었더니, 주인은 kube-system 의 admin-user 이고 만료 시각에서 발급 시각을 뺀 값이 600초라는 뜻이에요.

📖 용어: JWT (JSON Web Token)
점(.)으로 구분된 세 부분으로 이뤄진 토큰이에요. 첫 부분에는 서명 방식이, 가운데에는 내용(누구의 토큰인지, 언제 발급돼 언제 만료되는지)이, 마지막에는 서명이 들어 있어요. 앞의 두 부분은 base64url 로 인코딩만 돼 있어서 토큰을 가진 사람은 누구나 풀어 읽을 수 있어요. 위조를 막는 것은 마지막 서명이고, 우리 API 서버는 5편에서 본 sa.key 로 이 서명을 만들어요.

명령이 긴 이유는 토큰 원문을 화면에 내지 않기 위해서예요. cut -d. -f2 가 토큰의 가운데 부분만 잘라 내고, 파이썬 한 줄이 base64url 에서 생략된 패딩(=)을 채워 디코딩한 뒤 sub(주인)와 exp - iat(만료 시각 빼기 발급 시각)만 출력해요. 그래서 토큰 원문은 터미널에도, 원자료 파일에도 남지 않아요. 서명이 빠진 이 출력만으로는 어디에도 인증할 수 없어요. 이 글의 모든 토큰 확인은 같은 방식으로 했어요.

화면을 찍는 로그인에는 10분짜리 토큰을 썼어요. 화면이나 기록에 혹시 남더라도 10분 뒤에는 쓸 수 없는 토큰이에요. 10분은 요청할 수 있는 가장 짧은 값이기도 해요. 쿠버네티스 소스의 TokenRequest 검증 코드(validation.go, v1.37.2)는 10분보다 짧은 기간을 "may not specify a duration less than 10 minutes" 라는 메시지로 거절해요. 더 짧은 값은 이번에 시험해 보지 않았어요.

토큰 발급을 별칭 하나로

로그인할 때마다 kubectl -n headlamp create token admin-user 를 치기 번거로워서, 마스터의 ~/.bashrc 에 별칭(alias, 긴 명령에 짧은 이름을 붙이는 셸 기능)을 getToken 이라는 이름으로 등록했어요.

master$ grep -A1 'Headlamp 로그인 토큰' ~/.bashrc # Headlamp 로그인 토큰 발급 (admin-user, 기본 1시간) alias getToken='kubectl -n headlamp create token admin-user' master$ type getToken getToken is aliased to `kubectl -n headlamp create token admin-user' master$ getToken | cut -d. -f2 | python3 -c 'import sys,base64,json; p=sys.stdin.read().strip(); p+="="*(-len(p)%4); d=json.loads(base64.urlsafe_b64decode(p)); print(d["sub"], "유효시간", d["exp"]-d["iat"], "초")' system:serviceaccount:headlamp:admin-user 유효시간 3600 초

→ getToken 을 치면 셸이 kubectl -n headlamp create token admin-user 로 바꿔 실행하고, 그렇게 받은 토큰의 주인은 headlamp 네임스페이스의 admin-user, 유효 시간은 3600초라는 뜻이에요.

이번에는 --duration 을 주지 않았고, 토큰은 3600초짜리로 나왔어요. 이 숫자는 4절에서 다시 봐요. 별칭에 대해 기억해 둘 것이 두 가지 있어요. ~/.bashrc 는 셸이 시작할 때 읽는 파일이라, 이미 열려 있던 셸에서는 source ~/.bashrc 를 한 번 실행해야 별칭이 생겨요. 그리고 이 파일은 마스터 VM 안에 있어서 ./lab destroy 로 VM 을 지우면 별칭도 함께 사라져요.

4. --duration=0 은 "서버가 정하라"는 뜻이었다

토큰이 한 시간마다 만료되니 다시 받는 일이 귀찮았어요. 그래서 수명을 0 으로 받아 봤고, 결과는 글 첫머리에서 본 대로였어요. 전체 명령은 이래요.

master$ kubectl -n headlamp create token admin-user --duration=0 | cut -d. -f2 | python3 -c 'import sys,base64,json; p=sys.stdin.read().strip(); p+="="*(-len(p)%4); d=json.loads(base64.urlsafe_b64decode(p)); print("sub:", d["sub"]); print("exp:", d.get("exp", "(없음)"))' sub: system:serviceaccount:headlamp:admin-user exp: 1794226746

→ 수명 0 으로 받은 토큰에도 exp 가 있고, 그 값 1794226746 은 한국 시간 21시 19분 6초라는 뜻이에요. exp 가 없으면 "(없음)"을 찍도록 만든 명령인데 값이 나왔어요. 이 출력에는 exp 만 찍혔지만, 글을 쓰며 같은 명령으로 토큰을 하나 더 받아 iat 와 함께 꺼내 보니 exp - iat 가 3600초였어요(원자료 10-recheck.txt).

답은 kubectl 레퍼런스에 한 줄로 있었어요. kubectl create token 레퍼런스의 --duration 설명은 이래요.

--duration duration Requested lifetime of the issued token. If not set or if set to 0, the lifetime will be determined by the server automatically. The server may return a token with a longer or shorter lifetime.

→ 요청하는 토큰 수명이고, 지정하지 않거나 0 으로 주면 수명은 서버가 알아서 정하며, 서버는 요청보다 길거나 짧은 토큰을 돌려줄 수도 있다는 뜻이에요.

0 은 "만료 없음"이 아니라 "지정하지 않음"과 같은 값이었어요. kubectl 소스(create_token.go, v1.37.2)를 보면 이유가 보여요. --duration 이 0 보다 클 때만 요청의 expirationSeconds 를 채우고, 0 이면 비워 둔 채 보내요. 음수는 "--duration must be greater than or equal to 0" 으로 거절하고요. 그러니 옵션을 아예 주지 않은 요청(getToken)과 --duration=0 요청은 API 서버가 받기에 똑같아요.

비어 있는 expirationSeconds 를 채우는 쪽은 API 서버예요. API 의 기본값을 정하는 코드(defaults.go, v1.37.2)는 값이 없으면 60 * 60, 곧 3600초를 넣어요. ServiceAccount 관리 문서도 kubelet 이 파드에 넣어 주는 TokenRequest 토큰이 기본적으로 1시간 뒤 만료된다고 적어요. 남은 변수는 서버가 정한 상한이에요. kube-apiserver 에 --service-account-max-token-expiration 을 주면 그보다 긴 요청은 그 값으로 줄여서 발급해요. 글을 쓰면서 마스터의 kube-apiserver 정적 파드 매니페스트를 확인해 보니 이 플래그는 없었어요.

관찰과 해석을 나눠 두면 이래요. 관찰한 것은 옵션 없이 받은 토큰의 3600초, --duration=0 으로 받은 토큰의 exp 와, 글을 쓰며 다시 받아 본 같은 토큰의 exp - iat 3600초, --duration=10m 으로 받은 토큰의 600초예요. 그 3600초가 "비어 있는 요청에 API 가 넣는 기본값"이라는 것은 위의 레퍼런스와 소스로 확인한 해석이에요.

그림 4. 0 을 주든 안 주든 같은 요청이다. 만료가 없는 쪽은 Secret 토큰 하나뿐이다

한 시간이라는 수명은 불편이기만 한 것이 아니에요. ServiceAccount 관리 문서는 TokenRequest 로 받은 짧은 토큰에 대해 "발급 기록이 중앙에 없어서 토큰을 하나씩 폐기할 방법이 없다"고 적어요. 만료 전에 무효로 만들려면 ServiceAccount 를 지웠다가 다시 만들어 UID 를 바꾸는 수밖에 없고, 그러면 그 계정으로 발급한 토큰이 전부 무효가 돼요. 짧은 토큰에서 유출에 대비하는 수단은 사실상 만료 시각 하나예요. 수명을 늘리면 유출된 토큰을 쓸 수 있는 시간도 그만큼 늘어나요.

💡 실무에서는: 한 시간이 짧으면 기간을 적어서 받는다
만료 없는 토큰으로 가기 전에 예를 들어 --duration=12h 로 필요한 만큼 길게 요청하는 방법이 있어요. 레퍼런스는 실제 수명이 요청보다 짧거나 길 수 있다고 하니, 받은 뒤에는 이 글의 방식으로 exp 를 확인해야 해요. 검증 코드의 상한은 2^32초이고, kube-apiserver 에 --service-account-max-token-expiration 이 있으면 그 값이 실제 상한이 돼요. 이번 실습에서는 이 방법을 시험하지 않았어요.

5. 만료 없는 토큰은 Secret 에서 나온다

만료 없는 토큰을 만드는 방법은 따로 있어요. 1.23 까지 자동으로 생기던 토큰 Secret 을 이제는 손으로 만드는 거예요. ServiceAccount 설정 문서의 "Manually create a long-lived API token for a ServiceAccount" 절과, 1절에서 본 Dashboard 의 sample user 문서에 같은 방법이 실려 있어요.

📖 용어: service-account-token 타입 Secret
Secret 은 비밀번호나 토큰 같은 민감한 값을 담는 쿠버네티스 객체예요. 타입을 kubernetes.io/service-account-token 으로 하고 어노테이션 kubernetes.io/service-account.name 에 계정 이름을 적으면, 컨트롤 플레인이 그 계정의 토큰을 만들어 Secret 의 data.token 에 채워 넣어요. Secret 문서는 이것을 레거시 방식이라고 불러요.
master$ cat admin-user-token-secret.yaml | grep -v '^#' apiVersion: v1 kind: Secret metadata: name: admin-user-token namespace: headlamp annotations: kubernetes.io/service-account.name: admin-user type: kubernetes.io/service-account-token master$ kubectl apply -f admin-user-token-secret.yaml && sleep 2 && kubectl -n headlamp describe secret admin-user-token | sed -n '/^Type/,/^token/p' | sed -E 's/^(token: +).{12}.*/\1(가림)/' secret/admin-user-token created Type: kubernetes.io/service-account-token Data ==== ca.crt: 1107 bytes namespace: 8 bytes token: (가림)

→ Secret 을 만들고 2초 뒤에 보니 Data 에 ca.crt(1107바이트), namespace(8바이트), token 세 값이 채워져 있었다는 뜻이에요. 우리 YAML 에는 data 를 하나도 적지 않았어요.

세 값은 모두 컨트롤 플레인이 채운 거예요. ca.crt 는 API 서버 인증서를 확인할 때 쓰는 클러스터 CA 인증서이고, namespace 의 8바이트는 "headlamp" 여덟 글자예요. token 줄을 sed 로 가린 데는 이유가 있어요. kubectl describe secret 은 다른 값은 크기만 보여 주면서, 이 타입의 token 만은 원문을 그대로 출력해요(describe.go, v1.37.2). ServiceAccount 설정 문서도 이 Secret 의 내용을 남이 볼 수 있는 화면에 띄우지 말라고 따로 적어 둘 정도예요.

master$ kubectl -n headlamp get secret admin-user-token -o jsonpath='{.data.token}' | base64 -d | cut -d. -f2 | python3 -c 'import sys,base64,json; p=sys.stdin.read().strip(); p+="="*(-len(p)%4); d=json.loads(base64.urlsafe_b64decode(p)); print("sub:", d["sub"]); print("exp:", d.get("exp", "(없음)"))' sub: system:serviceaccount:headlamp:admin-user exp: (없음)

→ Secret 에 든 토큰을 꺼내(data.token 은 base64 로 저장돼 있어 base64 -d 로 한 번 푼 뒤) 가운데 부분을 보니, 주인은 같은 admin-user 인데 exp 항목 자체가 없다는 뜻이에요.

exp 가 없으니 만료 시각도 없어요. 이 토큰은 Secret 이 남아 있는 한 계속 유효해요. 그래서 getToken 도 매번 새 토큰을 발급하는 대신 이 Secret 에서 꺼내도록 바꿨어요.

master$ type getToken getToken is aliased to `kubectl -n headlamp get secret admin-user-token -o jsonpath="{.data.token}" | base64 -d; echo'

→ 이제 getToken 은 Secret 의 data.token 을 꺼내 base64 를 풀고 줄바꿈을 붙여 출력한다는 뜻이에요. 몇 번을 실행해도 같은 토큰이 나와요.

그림 5. 같은 admin-user 의 토큰인데, create token 으로 받은 것에는 exp 가 있고 Secret 에서 꺼낸 것에는 exp 가 없다

만료 없는 cluster-admin 토큰이 생겼다

편해진 만큼 감수할 것이 생겼어요. 이 토큰을 하나씩 따져 보면 이래요.

· 만료가 없어요. 유출되면 누군가 Secret 을 지울 때까지 계속 쓸 수 있어요.
· 권한이 cluster-admin 이에요. 토큰을 가진 사람은 클러스터의 모든 네임스페이스, 모든 리소스를 다룰 수 있어요.
· 클러스터 안에 저장돼 있어요. Secret 문서에 따르면 Secret 은 기본적으로 etcd 에 암호화 없이 저장되고, API 로 Secret 을 읽을 수 있는 사람과 etcd 에 접근할 수 있는 사람은 그 내용을 읽을 수 있어요. 글을 쓰며 확인한 우리 kube-apiserver 매니페스트에도 저장 시 암호화(Encryption at Rest) 설정인 --encryption-provider-config 는 없었어요. 인증 문서도 Secret 을 읽을 수 있는 사용자는 그 ServiceAccount 로 인증할 수 있다고 경고해요.
· 네임스페이스 경계가 다시 중요해져요. 2절에서 본 대로 headlamp 네임스페이스에 파드를 만들 수 있으면 이 Secret 을 읽을 수 있어요. admin-user 를 kube-system 에서 옮겨 둔 것이 여기서 한 번 더 의미가 있었어요.

만료 없는 토큰은 Secret 을 지우기 전까지 유효한 cluster-admin 자격 증명이에요. 문서들의 권고도 같아요. ServiceAccount 관리 문서는 "토큰 요청 방식이 맞지 않을 때만 장기 토큰을 만들라"고 하면서, 시간 제한이 있는 토큰은 만료되기 때문에 정보 보안 위험이 더 낮다고 설명해요. ServiceAccount 개념 문서도 클러스터 밖 애플리케이션이 Secret 에 저장한 장기 토큰으로 인증하는 방식을 피하라고 하고, 대신 잘 보호한 개인 키와 인증서, 인증 웹훅, TokenRequest 로 받은 짧은 토큰을 권해요.

그래도 이번에는 이 방식을 택했어요. 이 클러스터는 Mac 안에만 있는 VM 네트워크(3편) 위의 1인용 실습 환경이고, Headlamp 도 NodePort 를 닫고 port-forward 로만 열어요(9편). Secret YAML 의 첫 줄 주석에도 "로컬 실습 편의용"이라고 적어 두었어요. 같은 판단을 여러 사람이 쓰는 클러스터에 그대로 가져가면 안 돼요.

⚠️ 주의: 이 토큰을 무효로 만드는 방법
만료가 없으니 무효화는 손으로 해야 해요. ServiceAccount 관리 문서가 적은 방법은 Secret 을 지우는 것이고, 우리 환경에서는 kubectl -n headlamp delete secret admin-user-token 이에요. ServiceAccount 를 지우면 컨트롤 플레인이 그 Secret 의 토큰도 정리한다고 ServiceAccount 설정 문서는 적어요. 이번 실습에서는 두 방법 모두 실행해 보지 않았어요. 문서에는 주의가 하나 더 있어요. 손으로 만든 Secret 을 ServiceAccount 의 secrets 필드에 적으면 자동 생성 토큰으로 취급돼서, 오래 쓰지 않으면 정리 대상이 될 수 있다고요. 우리 YAML 은 어노테이션으로만 계정과 연결하고 그 필드는 건드리지 않았어요.
💡 실무에서는: 사람에게는 사람용 신원과 좁은 권한을
ServiceAccount 개념 문서는 ServiceAccount 를 워크로드와 자동화용으로, 사용자 계정을 사람용으로 구분해요. 여러 사람이 쓰는 클러스터라면 사람마다 클라이언트 인증서(5편의 kubeadm kubeconfig user)나 OIDC 같은 외부 인증으로 신원을 주고, 권한은 RBAC 모범 사례 문서대로 필요한 만큼만 줘요. 화면만 볼 사람이라면 기본 ClusterRole view 를 RoleBinding 으로 네임스페이스마다 주는 식이에요. RBAC 문서에 따르면 view 는 Secret 을 볼 수 없는데, Secret 을 읽으면 그 네임스페이스의 ServiceAccount 자격 증명을 얻을 수 있기 때문이라고 해요. Headlamp 차트도 clusterRoleBinding.clusterRoleName 에 좁은 역할을 넣거나 clusterRoleBinding.create=false 로 기본 cluster-admin 바인딩을 만들지 않게 할 수 있어요. 이 클러스터에는 아직 적용하지 않았어요.

6. whoami 는 토큰이 아니라 인증서의 주인을 보여 줬다

마지막으로 확인할 것이 남았어요. Secret 에서 꺼낸 토큰이 정말 admin-user 로 인증되는지예요. 1절의 can-i --as 는 관리자가 admin-user 인 척하고 권한을 물어본 것이라, 이 토큰 자체가 통하는지는 말해 주지 않아요. 토큰을 직접 보내서 API 서버가 누구로 받아들이는지 물어야 했어요.

📖 용어: kubectl auth whoami (SelfSubjectReview)
API 서버에 SelfSubjectReview 를 보내, 이 요청이 어떤 사용자 이름과 그룹으로 인증됐는지 돌려받는 명령이에요. SelfSubjectReview API 는 1.28 부터 정식 기능이고, 보통의 클러스터에서는 인증된 사용자 누구나 쓸 수 있어요. 인증 경로가 복잡할 때 "API 서버가 나를 누구로 보는가"를 확인하는 데 써요.

처음에는 마스터에서 평소처럼 kubectl auth whoami --token="$(getToken)" 을 실행했어요. 결과의 Username 은 admin-user 가 아니라 kubernetes-admin 이었어요. 5편에서 본 관리자 kubeconfig 의 클라이언트 인증서 주인이에요. 토큰을 줬는데 토큰이 무시된 것으로 보였어요. 이 첫 실행의 출력은 원자료 파일로 남기지 않았고, 결과만 작업 메모에 적었어요. 글을 쓰며 같은 명령을 다시 실행했을 때도 Username 은 kubernetes-admin, 그룹은 kubeadm:cluster-admins 였어요.

이유는 kubectl 이 자격 증명을 합치는 방식에 있었어요. client-go 의 kubeconfig 처리 코드(client_config.go, v1.37.2)는 --token 같은 명령줄 값을 kubeconfig 의 사용자 정보 위에 덧씌워요. 토큰 항목만 채워지고, kubeconfig 에 있던 클라이언트 인증서 항목은 그대로 남아요. 그래서 요청에는 TLS 연결의 클라이언트 인증서와, Authorization: Bearer 헤더(토큰을 실어 보내는 HTTP 헤더)의 토큰이 함께 실려요.

API 서버는 둘 중 하나로 사용자를 정해요. 인증 문서는 인증 모듈이 여럿 켜져 있으면 "요청을 처음으로 인증하는 데 성공한 모듈이 평가를 끝낸다"고 적고, 이어서 "API 서버는 인증 모듈이 도는 순서를 보장하지 않는다"고 적어요. 우리 클러스터에서는 인증서 쪽 신원이 나왔어요. 다만 문서가 순서를 보장하지 않으니, 다른 클러스터나 다른 버전에서도 늘 인증서 쪽이 선택된다고 말할 수는 없어요. 분명한 것은 하나예요. 자격 증명이 둘 실린 요청으로는 그중 하나가 누구인지 확인할 수 없어요.

그래서 kubeconfig 를 비우고 토큰만 보냈어요.

master$ kubectl --kubeconfig=/dev/null --server=https://192.168.104.1:6443 --certificate-authority=/etc/kubernetes/pki/ca.crt --token="$(getToken)" auth whoami ATTRIBUTE VALUE Username system:serviceaccount:headlamp:admin-user UID d877ee99-2bf1-4e82-a4a5-d13085444da1 Groups [system:serviceaccounts system:serviceaccounts:headlamp system:authenticated] master$ kubectl --kubeconfig=/dev/null --server=https://192.168.104.1:6443 --certificate-authority=/etc/kubernetes/pki/ca.crt --token="$(getToken)" get nodes NAME STATUS ROLES AGE VERSION k8s-master Ready control-plane 4d23h v1.37.2 k8s-worker1 Ready worker 4d22h v1.37.2 k8s-worker2 Ready worker 4d22h v1.37.2 k8s-worker3 Ready worker 4d22h v1.37.2

→ 빈 kubeconfig(/dev/null)를 쓰니 접속할 서버 주소와 서버 인증서를 확인할 CA 를 따로 줘야 했어요. 이번에는 Username 이 system:serviceaccount:headlamp:admin-user 로 나왔고, 같은 토큰으로 노드 4대도 조회됐다는 뜻이에요.

서버 주소는 마스터의 eth0 IP 이고, 5편에서 본 대로 API 서버 인증서에 이 IP 가 들어 있어 CA 확인을 통과해요. 그룹 셋은 인증 문서가 적은 그대로예요. ServiceAccount 는 system:serviceaccounts 와 system:serviceaccounts:<네임스페이스> 그룹에 들어가고, 인증된 요청은 모두 system:authenticated 그룹에 들어가요. UID 는 admin-user 라는 ServiceAccount 객체의 UID 예요. 4절에서 본 대로 ServiceAccount 를 지웠다 다시 만들면 이 UID 가 바뀌어요. get nodes 가 된 것은 cluster-admin 바인딩이 이 토큰의 신원에 실제로 적용된다는 확인이에요.

그림 6. 자격 증명이 둘 실리면 어느 쪽이 쓰일지 장담할 수 없다. 토큰을 확인할 때는 토큰만 보낸다
⚠️ 주의: --as 와 --token 은 다른 질문이다
kubectl auth can-i --as=... 는 지금 접속한 관리자가 "그 이름이라면 권한이 있나"를 묻는 거예요. 바인딩이 그 이름에 걸려 있는지는 알 수 있지만, 실제 토큰이 그 이름으로 인증되는지는 알 수 없어요. 토큰을 확인하려면 이번에 한 대로 다른 자격 증명이 없는 상태로 토큰만 보내야 해요. 관리자 kubeconfig 가 기본으로 잡혀 있는 곳(이번에는 마스터)에서는 --kubeconfig=/dev/null 이 가장 간단한 방법이었어요.

여기까지가 강의의 대시보드 실습이었어요. 9편에서 Headlamp 를 띄우고 접속 경로를 정했고, 이번 편에서 로그인할 신원과 토큰을 정리했어요. 화면에 노드와 파드가 보이게 됐으니, 그다음은 노드마다 수치를 시간에 따라 모으는 일이에요. Prometheus 는 11편에서 다뤄요.

강의의 admin-user 는 ServiceAccount 하나에 cluster-admin 을 묶은 ClusterRoleBinding 하나였어요. 권한은 네임스페이스와 상관없이 클러스터 전체에 미치므로, 네임스페이스는 누가 그 계정의 권한을 쓸 수 있는지를 정하는 경계로 골라야 했어요.

1.24 부터 ServiceAccount 에는 토큰이 따라오지 않고 TokenRequest 로 그때그때 발급받아요. --duration=0 은 "서버가 정하라"는 뜻이라 API 기본값인 3600초짜리 토큰이 나왔고, 만료 없는 토큰은 service-account-token 타입 Secret 으로 따로 만들어야 했어요. 그 토큰이 누구인지 확인할 때는 kubeconfig 의 인증서를 빼고 토큰만 보내야 했고요. 토큰의 수명을 정하는 일은 편의와 위험을 함께 정하는 일이에요.
