파드 9개를 한꺼번에 지웠어요. 모두 busybox나 nginx로 오래 도는 파드였고 다른 점은 컨테이너의 첫 프로세스 모양뿐이었어요. 결과는 두 무리로 깔끔하게 갈렸어요. 네 개는 30.8~31.0초 뒤에 exit 137로 사라졌고 네 개는 0.6~0.7초 만에 사라졌어요. grace를 5초로 준 나머지 하나는 5.7초였어요.

느린 쪽에 sh -c 'trap "exit 0" TERM; sleep infinity; echo bye'가 있었어요. SIGTERM을 받으면 exit 0을 하라고 trap까지 걸었는데 30.8초를 다 채우고 SIGKILL로 끝났어요. 빠른 쪽에는 같은 trap을 걸고 뒷부분만 sleep infinity & wait로 바꾼 파드가 있었고 0.7초에 exit 0으로 끝났어요.

64편에서는 핸들러가 없는 PID 1이 SIGTERM을 버린다는 커널 규칙을 봤어요. 그러면 셸로 감싸고 trap을 걸면 해결될 것 같은데 실제로는 그렇지 않았어요. sh -c로 감싼 컨테이너는 왜 SIGTERM에 반응하지 않을까요? 클러스터는 v1.37.2, containerd 2.4.1이고 셸은 busybox 1.37의 sh예요.

1. 아홉 가지 PID 1 모양은 31초와 0.7초로 갈렸다

실험은 파드 9개를 띄우고 Ready가 된 뒤 하나의 kubectl delete로 같이 지웠어요. watch로 각 파드가 사라진 시각과 컨테이너 종료 코드를 받고 노드의 containerd 로그에서 보낸 신호를 읽었어요. 원본은 labs/devops/k8s-study/out/65-delete-timing.txt와 같은 디렉터리의 65-delete-timing.sh예요. 같은 모양의 파드로 PID 1과 신호 마스크를 읽은 결과는 64편의 64-pid1-sigmask.txt에 있어요.

그림 1. containerd는 모든 파드에 +0.1초에 신호를 보냈고, 결과를 가른 것은 그 신호를 받은 PID 1이었어요.

containerd 로그를 보면 모든 파드가 삭제 요청 뒤 +0.1초에 정지 신호를 받았어요. 느린 다섯 개는 +30.1초(grace 5초 파드는 +5.1초)에 SIGKILL을 한 번 더 받았어요. nginx만 신호 이름이 quit였고 나머지는 terminated(SIGTERM)였어요. 종료 코드는 셋으로 나뉘었어요. 137은 SIGKILL로 죽은 것, 143은 SIGTERM의 기본 동작으로 죽은 것, 0은 프로세스가 스스로 exit 0을 한 거예요.

표에서 바로 보이는 것이 하나 있어요. grace를 5초로 줄인 파드는 빨리 끝났지만 종료 코드는 여전히 137이에요. 신호를 처리하게 된 것이 아니라 SIGKILL이 25초 앞당겨졌을 뿐이에요. 이 글은 표의 위쪽 다섯 줄, 그중에서도 셸이 끼어 있는 b, c, d, e를 따라가요. g와 h는 66편에서 다시 봐요.

2. sh -c 하나짜리는 셸이 남지 않았고 둘짜리는 셸이 PID 1로 남았다

Docker를 써 본 사람에게는 익숙한 경고가 있어요. Dockerfile의 ENTRYPOINT를 문자열로 쓰면 신호가 앱에 닿지 않는다는 경고예요. Dockerfile reference는 이렇게 적어요.

The shell form of ENTRYPOINT ... starts your ENTRYPOINT as a subcommand of /bin/sh -c, which does not pass signals. This means that the executable will not be the container's PID 1, and will not receive Unix signals. In this case, your executable doesn't receive a SIGTERM from docker stop <container>.

→ 문자열로 쓴 ENTRYPOINT는 /bin/sh -c의 하위 명령으로 실행되고, sh는 신호를 넘겨주지 않으므로 앱은 PID 1이 아니고 docker stop의 SIGTERM도 받지 못한다는 뜻이에요. 같은 문서의 예에서 ENTRYPOINT top -b는 PID 1이 /bin/sh -c top -b였고 docker stop에 10.19초가 걸렸어요. Docker의 기본 grace인 10초를 다 쓴 거예요. ENTRYPOINT exec top -b로 바꾸자 top이 PID 1이 됐고 0.20초에 멈췄어요.

📖 용어: shell form과 exec form
Dockerfile에서 CMD nginx -g "daemon off;"처럼 문자열로 쓰면 shell form이고 /bin/sh -c가 그 문자열을 실행해요. ["nginx", "-g", "daemon off;"]처럼 배열로 쓰면 exec form이고 그 프로그램이 셸 없이 바로 실행돼요. 쿠버네티스의 command와 args는 언제나 배열이라 exec form이에요.

쿠버네티스에는 shell form이 없어요. 그런데 셸 문법(파이프, &&, 변수)을 쓰고 싶으면 command: ["sh", "-c", "..."]로 쓰고, 이게 Docker의 shell form과 같은 모양이에요. 그러니 셸이 PID 1이 될 거라고 예상했어요. 실제로는 명령 개수에 따라 달랐어요.

📖 용어: busybox sh (ash)
busybox는 ls, sleep, sh 같은 유닉스 도구를 바이너리 하나에 모은 프로그램이에요. busybox 이미지의 /bin/sh는 busybox에 든 ash라는 셸이고, nginx:1.27-alpine 이미지에서도 /bin/sh는 /bin/busybox를 가리켰어요(labs/devops/k8s-study/out/65-alpine-sh.txt). bash나 dash와는 다른 구현이라서 아래에서 본 동작이 그 셸들에도 같다고 볼 수는 없어요.

b-sh-c(sh -c "sleep infinity")의 컨테이너 안 ps에는 sh가 없었어요. PID 1이 sleep infinity였어요. 셸이 sleep을 자식으로 띄우지 않고 자기 자신을 sleep으로 바꿨다는 뜻이에요. c-sh-c-2cmds(sh -c "sleep infinity; echo bye")에서는 PID 1이 sh였고 sleep은 PID 7, 부모가 1인 자식이었어요.

## b-sh-c command: ["sh","-c","sleep infinity"] PID PPID STAT COMMAND 1 0 S sleep infinity ## c-sh-c-2cmds command: ["sh","-c","sleep infinity; echo bye"] PID PPID STAT COMMAND 1 0 S sh -c sleep infinity; echo bye 7 1 S sleep infinity

→ 명령이 하나면 셸이 남지 않았고, 뒤에 실행할 명령이 남아 있으면 셸이 PID 1로 남았다는 뜻이에요.

📖 용어: exec (셸 내장 명령)
셸에서 exec 명령을 쓰면 셸이 새 프로세스를 만들지 않고 자기 프로세스를 그 명령으로 바꿔요. PID는 그대로이고 셸은 사라져요. PID 1인 셸이 exec를 하면 그 명령이 PID 1을 이어받아요. b-sh-c에서는 exec를 쓰지 않았는데도 같은 결과가 나왔어요.

두 파드는 모양이 달랐지만 결과는 같았어요. b는 sleep이 PID 1이니 64편의 규칙대로 SIGTERM이 버려져요. c는 PID 1인 sh가 TERM에 핸들러를 걸지 않았으니(SigCgt INT CHLD) sh에게 온 SIGTERM이 버려져요. 그리고 sh는 받은 신호를 자식에게 넘겨주지 않아요. 자식 sleep은 PID 1이 아니라서 SIGTERM을 받았다면 기본 동작으로 죽었을 텐데, 31.0초가 걸린 것을 보면 받지 못한 거예요. sleep이 죽었다면 sh는 다음 명령 echo bye를 실행하고 끝났을 거예요. 여기서 정지 신호가 컨테이너의 첫 프로세스 하나에만 간다고 읽었어요. containerd가 옵션 없이 task.Kill(ctx, sig)를 부르는 것까지는 소스에서 봤지만, 그 아래 shim과 runc가 첫 프로세스에만 보내는지는 소스로 확인하지 않았어요. 이 결론은 c의 결과에서 끌어낸 추론이에요.

그림 2. 셸이 남든 사라지든 PID 1이 SIGTERM을 처리하지 못하면 결과는 같았어요.

⚠️ busybox가 명령을 exec한 것은 관찰이지 확인된 규칙이 아니에요
b-sh-c의 PID 1이 sleep이었다는 것은 컨테이너 안 ps와 /proc/1/status로 본 사실이에요. busybox ash의 소스에서 이 동작을 찾아 확인하지는 않았고 dash와 bash에서는 시험하지 않았어요. 그러니 "sh -c에 명령 하나면 안전하다"고 일반화하면 안 돼요. 이미지의 셸이 바뀌거나 명령 뒤에 무언가 붙으면 결과가 달라질 수 있어요. 4절에서 실제로 그런 경우를 봐요.

3. trap을 걸어도 앞쪽 명령이 끝날 때까지 트랩이 미뤄졌다

셸이 PID 1로 남는다면 셸이 SIGTERM을 처리하게 하면 될 것 같아요. 셸에서 신호 핸들러를 거는 방법이 trap이에요.

📖 용어: trap
trap '명령' TERM은 셸이 SIGTERM을 받으면 그 명령을 실행하라고 등록하는 셸 내장 명령이에요. 셸은 이때 커널에 실제 신호 핸들러를 걸어요. 그래서 trap을 건 셸의 SigCgt에는 TERM 비트가 켜지고, PID 1이어도 커널이 SIGTERM을 버리지 않아요.

d-trap-fg의 PID 1 sh는 SigCgt가 INT TERM CHLD였어요. 64편의 그림 2로 보면 왼쪽 갈래, 즉 핸들러가 실행되는 쪽이에요. 신호는 분명히 sh에게 전달됐어요. 그런데도 30.8초 뒤 SIGKILL로 끝났어요. 이유는 셸 표준에 적혀 있어요. POSIX.1-2024 Shell Command Language 2.12절이에요.

When a signal for which a trap has been set is received while the shell is waiting for the completion of a utility executing a foreground command, the trap associated with that signal shall not be executed until after the foreground command has completed. When the shell is waiting, by means of the wait utility, for asynchronous commands to complete, the reception of a signal for which a trap has been set shall cause the wait utility to return immediately with an exit status >128, immediately after which the trap associated with that signal shall be taken.

→ 셸이 전경 명령이 끝나기를 기다리는 중에 trap을 건 신호가 오면 그 trap은 전경 명령이 끝난 뒤에야 실행된다는 뜻이에요. 반대로 wait 내장 명령으로 백그라운드 명령을 기다리는 중이면 wait가 128보다 큰 값으로 즉시 돌아오고 바로 trap이 실행돼요.

📖 용어: 전경 명령과 비동기 명령, wait
셸은 보통 명령 하나를 실행하고 끝날 때까지 기다린 뒤 다음 줄로 가요. 이게 전경(foreground) 명령이에요. 명령 끝에 &를 붙이면 셸은 기다리지 않고 다음으로 넘어가는데 이게 비동기(백그라운드) 명령이에요. wait는 백그라운드로 띄운 명령이 끝나기를 기다리는 셸 내장 명령이에요.

d에서 sh는 전경 명령 sleep infinity를 기다리고 있었어요. SIGTERM은 도착했지만 trap의 exit 0은 sleep이 끝날 때까지 미뤄졌고, sleep은 끝나지 않으니 30초 뒤 SIGKILL이 먼저 왔어요. e는 sleep infinity & wait로 sleep을 백그라운드로 보내고 wait로 기다렸어요. SIGTERM이 오자 wait가 바로 돌아오고 trap이 exit 0을 실행했어요. +0.7초, 종료 코드 0이에요.

그림 3. 같은 trap이라도 셸이 무엇을 기다리고 있었는지가 30초를 갈랐어요.

e에서 한 가지 더 볼 것이 있어요. 2절의 추론대로라면 SIGTERM은 PID 1인 sh에게만 갔고 백그라운드 sleep에는 가지 않았어요. 이 실험만으로는 sleep이 SIGTERM을 받았는지 가릴 수 없어요. 64편의 신호 마스크 출력에서 e의 PID 7 sleep은 SigIgn이 INT QUIT였어요. POSIX 2.12의 첫 문단이 작업 제어가 꺼진 셸에서 비동기 명령은 SIGINT와 SIGQUIT을 무시 상태로 물려받는다고 정한 그대로이고, TERM은 무시 목록에 없어요. 어느 쪽이든 sleep은 곧바로 끝났어요. PID 1인 sh가 exit 0으로 끝나면 커널이 그 네임스페이스의 나머지 프로세스에 SIGKILL을 보내기 때문이에요(64편의 zap_pid_ns_processes()). 컨테이너의 종료 코드 0은 sh의 것이에요.

이 점은 실제 앱에서 중요해요. sleep 자리에 정리 작업이 필요한 앱이 있다면 e의 모양은 앱을 정리 없이 SIGKILL로 끝내요. Dockerfile reference도 정리 작업이 필요하거나 여러 프로그램을 함께 돌린다면 진입점 스크립트가 "receives the Unix signals, passes them on, and then does some more work"해야 한다고 적어요. 신호를 받아서 자식에게 넘기고 그다음 일을 하라는 뜻이에요. tini를 만든 krallin도 tini 이슈 #8에서 Bash를 PID 1로 쓰면 신호가 Bash에게만 가고 "does not forward them anywhere (unless you code it yourself)"라고 했어요. 직접 코드로 짜지 않으면 어디에도 넘기지 않는다는 뜻이에요. trap으로 자식에게 신호를 넘기는 스크립트는 이 글에서 시험하지 않았어요.

네이티브 사이드카 실험에도 같은 규칙이 보여요. trap "exit 0" TERM; while true; do sleep 1; done을 쓴 사이드카는 앱이 끝난 11:31:23의 1초 뒤인 11:31:24에 exit 0으로 끝났어요(labs/devops/k8s-study/out/64-native-sidecar-finish.txt). 전경 명령이 sleep 1이라 trap이 미뤄져도 최대 1초라고 읽을 수 있어요. 이 해석은 끝난 시각의 초 단위 기록에서 끌어낸 것이고 trap이 실행된 순간을 따로 재지는 않았어요.

4. exec는 PID 1을 앱에게 넘기지만 nginx 앞에 셸이 남으면 SIGQUIT이 버려졌다

셸이 PID 1로 남아서 생기는 문제라면 가장 단순한 처방은 셸이 남지 않게 하는 거예요. Dockerfile reference가 진입점 스크립트의 마지막 줄에 exec "$@"나 exec gosu postgres "$@"를 쓰는 예를 드는 이유예요. 준비 작업은 셸이 하고 마지막에 앱으로 자신을 바꾸면 앱이 PID 1이 되고 정지 신호를 직접 받아요. f-nginx가 그 예예요. command는 /docker-entrypoint.sh라는 셸 스크립트로 시작했는데 PID 1은 nginx master였어요. 같은 PID 1 자리가 스크립트에서 nginx로 바뀌었으니 스크립트가 마지막에 exec로 자리를 넘긴 거예요.

다만 exec는 신호를 앱에게 보내는 길을 열 뿐이에요. b-sh-c도 결과적으로 sleep이 PID 1이었지만 sleep에는 핸들러가 없어서 30.9초가 걸렸어요. exec 뒤의 앱이 정지 신호에 핸들러를 걸어야 의미가 있어요.

실제 앱으로 확인해 봤어요. nginx:1.27-alpine 이미지로 네 가지 command를 띄우고 같이 지웠어요. 원본은 labs/devops/k8s-study/out/65-nginx-sh-wrapper.txt와 같은 디렉터리의 65-nginx-sh-wrapper.sh예요.

w-direct ["nginx","-g","daemon off;"] PID 1 = nginx master w-sh-exec ["sh","-c","echo prep; exec nginx -g \"daemon off;\""] PID 1 = nginx master w-sh-noexec ["sh","-c","echo prep; nginx -g \"daemon off;\""] PID 1 = nginx master w-sh-tail ["sh","-c","nginx -g \"daemon off;\"; echo bye"] PID 1 = sh -c nginx -g "daemon off;"; echo bye (w-sh-tail의 PID 1 sh: SigIgn = QUIT, SigCgt = INT CHLD)

→ 출력에서 command와 PID 1만 모은 거예요. exec를 쓰지 않은 w-sh-noexec도 PID 1이 nginx였어요. busybox sh가 마지막 명령을 exec한 것으로 보여요. 셸이 남은 것은 nginx 뒤에 echo bye가 붙은 w-sh-tail 하나였어요.

그림 4. 셸이 PID 1로 남은 w-sh-tail만 SIGQUIT을 버리고 30초를 기다렸어요.

containerd가 보낸 신호는 네 파드 모두 quit(SIGQUIT)이었어요. nginx 공식 이미지에 STOPSIGNAL SIGQUIT이 들어 있기 때문이에요. 64편의 신호 마스크 실험에서 노드의 containerd가 본 nginx:1.27-alpine 이미지 설정도 StopSignal=SIGQUIT이었어요.

📖 용어: STOPSIGNAL
이미지를 멈출 때 보낼 신호를 정하는 Dockerfile 지시어예요. 적지 않으면 SIGTERM이에요. containerd는 파드 스펙에 정지 신호가 없으면 이미지의 STOPSIGNAL을, 그것도 없으면 SIGTERM을 보내요. 쿠버네티스 파드 스펙으로 이 값을 바꾸는 필드는 67편에서 봐요.

nginx는 SIGTERM과 SIGINT를 빠른 종료(연결을 바로 끊음), SIGQUIT을 우아한 종료(처리 중인 요청을 마치고 끝남)로 다뤄요. 2019-11-15에 열린 docker-nginx 이슈 #377은 "when Docker or Kubernetes decide to stop a container, nginx will die immediately, closing any connections straight away"라고 문제를 적었어요. 컨테이너가 멈출 때 nginx가 연결을 바로 끊는다는 뜻이에요. nginx의 관련 버그(trac #753)가 1.19.1에서 고쳐진 뒤 2020-11-24의 커밋 3fb70ddd70이 이미지의 STOPSIGNAL을 SIGTERM에서 SIGQUIT으로 바꿨어요.

여기에 busybox sh가 끼면 문제가 하나 더 생겨요. w-sh-tail의 PID 1 sh는 SigIgn에 QUIT이 켜져 있었어요. 핸들러가 없는 것이 아니라 일부러 무시하는 상태예요. containerd가 보낸 SIGQUIT은 sh에서 버려졌고 +30.7초의 SIGKILL로 끝났어요. 사라진 시각은 +32.3초, 종료 코드는 137이에요. nginx가 PID 1이었던 세 파드는 SIGQUIT을 받아 우아한 종료를 하고 +3.2~3.4초에 exit 0으로 사라졌어요. 이번 실행에서 컨테이너 종료가 watch에 처음 보인 시각은 +2.3~2.4초였고 1절의 f-nginx는 +0.4초였어요. 그 차이는 따로 보지 않았어요.

⚠️ nginx 이미지를 sh -c로 감쌀 때는 TERM trap으로도 막을 수 없어요
nginx 이미지의 정지 신호는 SIGTERM이 아니라 SIGQUIT이에요. 셸이 PID 1로 남는 모양이면 containerd는 그 셸에 SIGQUIT을 보내고 busybox sh는 QUIT을 무시 상태로 두고 있어요. 그래서 trap ... TERM만 걸어서는 이 신호를 잡지 못해요(이 조합은 따로 시험하지 않았고 SigIgn과 STOPSIGNAL에서 끌어낸 결론이에요). nginx 앞에 설정 생성 같은 준비 작업을 넣는다면 마지막 명령을 exec nginx -g "daemon off;"로 쓰고 그 뒤에 아무것도 두지 마세요.

5. 셸로 감쌌다면 PID 1, 정지 신호, 마지막 명령 셋을 확인한다

지금까지의 결과를 순서로 묶으면 점검할 것은 세 가지예요. PID 1이 누구인지, 그 PID 1이 런타임이 보내는 정지 신호에 핸들러를 걸었는지, 셸이라면 앱이 마지막에 exec로 PID 1을 넘겨받는지예요.

그림 5. 셸을 없애는 것과 앱이 신호를 처리하는 것은 서로 다른 점검이에요.

💡 실무에서는
• 셸 문법이 필요 없으면 command: ["nginx", "-g", "daemon off;"]처럼 배열로 바로 써요. 그러면 셸이 끼지 않아요.
• 준비 작업이 필요하면 sh -c '준비 && exec 앱'처럼 마지막을 exec로 쓰고, 셸 동작에 기대지 말고 exec를 명시해요. 진입점 스크립트도 마지막 줄을 exec "$@"로 끝내요.
• 배포 뒤에 kubectl exec <파드> -- cat /proc/1/cmdline으로 PID 1을 보고 /proc/1/status의 SigIgn과 SigCgt를 같이 봐요.
• 이미지의 정지 신호는 노드에서 crictl inspecti <이미지> 출력의 info.imageSpec.config.StopSignal로 확인해요. 비어 있으면 SIGTERM이에요.
• grace를 줄이는 것은 해결이 아니에요. i-sleep-grace5와 같이 137이 빨리 올 뿐이에요.

✍️ 오늘의 요약

sh -c로 감싼 컨테이너가 SIGTERM에 반응하지 않는 이유는 둘 중 하나였어요. 셸이 PID 1로 남으면 셸은 TERM 핸들러가 없고 받은 신호를 자식에게 넘기지도 않아요. 셸이 남지 않더라도 PID 1이 된 프로그램에 핸들러가 없으면 결과는 같아요. 우리 실험에서 두 경우 모두 31초 근처에서 137로 끝났어요.

trap은 셸에 핸들러를 걸지만 POSIX 2.12에 따라 전경 명령이 끝날 때까지 실행이 미뤄져요. sleep infinity; ...는 30.8초, sleep infinity & wait는 0.7초였어요. busybox sh는 마지막 명령을 exec해서 셸이 남지 않는 것으로 관찰됐지만, nginx 뒤에 명령 하나를 붙이자 셸이 PID 1로 남아 이미지의 정지 신호 SIGQUIT을 무시했고 32.3초가 걸렸어요.

셸로 감쌀 때는 마지막을 exec로 명시해 앱에게 PID 1을 넘기고, 그 앱이 런타임이 보내는 정지 신호를 실제로 처리하는지 /proc/1/status로 확인해야 해요.
