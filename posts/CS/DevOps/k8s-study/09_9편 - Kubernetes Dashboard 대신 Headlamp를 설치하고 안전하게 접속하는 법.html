7편. 노드를 재시작한 직후의 Ready를 믿으면 안 되는 이유
8편. 쿠버네티스에서 관측성(옵저버빌리티)이 필요한 이유
9편. Kubernetes Dashboard 대신 Headlamp를 설치하고 안전하게 접속하는 법 ← 지금 이 글

강의 자료에 적힌 대시보드 링크를 열었어요. 주소는 github.com/kubernetes-retired/dashboard였습니다. 조직 이름에 retired가 붙어 있었고 README 맨 위에는 이 프로젝트가 아카이브되어 더 이상 관리되지 않는다는 문장이 굵은 글씨로 적혀 있었어요.

8편에서 정리한 관측 도구 가운데 강의에서 가장 먼저 다룬 것이 이 Kubernetes Dashboard예요. 파드·노드·이벤트 같은 클러스터 상태를 웹 화면으로 보여 주는 도구입니다. README에서 대신 쓰라고 권한 Headlamp를 설치하고 강의에서 말한 대로 API 서버를 거치는 경로로 열어 봤어요. 인증서 없이는 403, 관리자 인증서를 붙이면 200이 나왔고 로그인 창도 떴습니다. 그런데 토큰을 넣고 로그인하자 화면이 로딩 표시에서 더 넘어가지 않았어요.

클러스터는 1~7편에서 만든 실습 환경(Lima VM 4대, 쿠버네티스 v1.37.2, Calico v3.33.0)이고 이번 실습부터 마스터에 Helm v3.22.1을 설치해 썼어요. 이 글에서는 대시보드를 고르는 데서 시작해 Headlamp를 설치하고 어느 길로 접속할지 정하기까지를 다룹니다.

이 글에서 다룰 것
· 강의에서 쓰는 Kubernetes Dashboard는 왜 설치하지 않았고 무엇으로 바꿨을까?
· helm install 한 줄은 클러스터에 무엇을 만들었고 그중 무엇을 조심해야 할까?
· NodePort, API 서버 프록시, kubectl port-forward는 Headlamp에 닿기 전에 무엇이 다를까?
· API 서버 경로로 연 Headlamp는 왜 로그인 뒤에 멈췄을까?
· 같은 Mac에서 nc는 되는데 kubectl만 no route to host 오류를 낸 이유는 무엇일까?

1. 강의에서 쓰는 대시보드는 이미 은퇴해 있었다

설치 명령을 입력하기 전에 저장소 상태부터 확인했어요. GitHub API로 아카이브 여부, README 첫 부분, 릴리스 두 개, 그리고 README에서 대신 쓰라고 권한 Headlamp의 최신 릴리스를 차례로 조회했습니다.

그림 1. 저장소는 archived=true, 강의식 helm 저장소 주소는 404, 강사가 쓴 v2.7.0은 1.25에만 ✓였다

화면에서 볼 것은 네 가지예요. 첫째, 저장소는 archived=true였고 README에는 "활동하는 관리자와 기여자가 부족해 아카이브했고 더 이상 관리하지 않는다"라고 적혀 있었어요. 같은 README에는 Headlamp를 대신 쓰라는 권고와 Headlamp가 최근 sig-ui 아래로 옮겨졌다는 내용도 있었습니다. 둘째, Helm 저장소 주소 https://kubernetes.github.io/dashboard/index.yaml을 요청하자 404가 돌아왔어요. 저장소의 차트 목록 파일이 없으니 helm repo add로 이 저장소를 등록할 수 없습니다. 마지막 릴리스인 kubernetes-dashboard-7.14.0(2025-10-30)의 차트 파일은 릴리스 첨부 파일로 남아 있어서 내려받을 수는 있었어요. 하지만 받더라도 앞으로 고쳐 줄 사람이 없는 차트예요.

셋째는 강의에서 쓴 버전이에요. 강사는 Dashboard v2.7.0을 매니페스트 한 장으로 설치했는데, 이 릴리스는 2022-09-16에 나왔고 릴리스 노트의 호환표에는 쿠버네티스 1.25에만 ✓가 있고 1.22~1.24는 ?로 남아 있었어요. 우리 클러스터는 v1.37.2라서 표에 아예 없습니다. 그 매니페스트 주소는 지금도 200으로 응답해 내려받을 수 있지만 내려받을 수 있다는 것과 이 클러스터에서 제대로 동작한다는 것은 다른 문제였어요. 넷째, Headlamp의 최신 릴리스는 v0.46.0(2026-10-15)이었습니다.

쿠버네티스 공식 문서의 Deploy and Access the Kubernetes Dashboard 페이지 맨 위에도 같은 사실이 적혀 있어요. "Kubernetes Dashboard is deprecated and unmaintained." 이어서 새로 설치한다면 Headlamp를 고려하라고 권하고 Dashboard는 지금 Helm 설치만 지원한다고 설명합니다. 그런데 그 페이지 본문에서 안내하는 helm repo add kubernetes-dashboard https://kubernetes.github.io/dashboard/ 명령은 바로 위에서 404를 받은 그 주소를 쓰고 있어요(2026-11-09에 확인). 문서는 아직 설치 명령을 보여 주지만 그 명령이 가리키는 저장소는 이미 비어 있었어요.

"그러면 뭐 써?"라는 질문에 고를 수 있는 답은 하나였어요. Dashboard의 README와 쿠버네티스 문서가 둘 다 Headlamp를 권하고 있었어요. Headlamp는 kubernetes-sigs 조직의 저장소이고 쿠버네티스 프로젝트 안에서 UI를 맡는 분과(SIG UI) 아래에 있어요. Helm 저장소 https://kubernetes-sigs.github.io/headlamp/도 200으로 응답했습니다. 강의에서 Dashboard로 보여 주려던 것, 곧 파드·노드·이벤트를 웹 화면으로 보는 일은 Headlamp로 따라 하기로 했어요.

📖 용어: Helm (차트 · 릴리스 · 리비전)
쿠버네티스 매니페스트 묶음을 패키지 단위로 설치하고 고치는 도구예요. 묶음 하나를 차트라고 하고 이 차트를 클러스터에 한 번 설치한 단위를 릴리스라고 불러요. 같은 릴리스를 helm upgrade로 고칠 때마다 리비전 번호가 하나씩 올라가고 helm rollback으로 이전 리비전의 상태로 되돌릴 수 있습니다.

2. helm install 한 줄이 만든 것은 다섯 가지였다

마스터에서 Headlamp 차트를 설치했어요. 네임스페이스는 kube-system으로 했습니다. Headlamp의 클러스터 설치 문서 예시에서도 --namespace kube-system을 써요. 나중에는 전용 네임스페이스로 옮겼는데 그 이유는 10편에서 다룹니다. 서비스 타입은 Mac에서 바로 열어 보려고 NodePort로 정하고 포트 번호를 30466으로 고정했어요.

master$ helm install headlamp headlamp/headlamp --namespace kube-system --set service.type=NodePort --set service.nodePort=30466 NAME: headlamp LAST DEPLOYED: Mon Nov 9 19:56:26 2026 NAMESPACE: kube-system STATUS: deployed REVISION: 1 TEST SUITE: None NOTES: 1. Get the application URL by running these commands: export NODE_PORT=$(kubectl get --namespace kube-system -o jsonpath="{.spec.ports[0].nodePort}" services headlamp) export NODE_IP=$(kubectl get nodes --namespace kube-system -o jsonpath="{.items[0].status.addresses[0].address}") echo http://$NODE_IP:$NODE_PORT 2. Get the token using kubectl create token headlamp --namespace kube-system

→ 릴리스 headlamp의 리비전 1이 배포됐어요. 차트가 출력한 안내문(NOTES)에는 노드 IP와 노드 포트로 접속하고 로그인 토큰은 kubectl create token으로 받으라고 적혀 있어요.

롤아웃이 끝난 걸 확인하고 Mac에서 워커 노드의 NodePort로 요청을 보냈어요.

master$ kubectl -n kube-system rollout status deploy/headlamp --timeout=180s Waiting for deployment "headlamp" rollout to finish: 0 of 1 updated replicas are available... deployment "headlamp" successfully rolled out mac$ curl -s -o /dev/null -w "%{http_code}\n" http://192.168.64.3:30466/ 000 # 몇 초 뒤 다시 확인 mac$ curl -s -o /dev/null -w "%{http_code}" http://192.168.64.3:30466/ 200 mac$ curl -s -o /dev/null -w "%{http_code}" http://192.168.64.4:30466/ 200 mac$ curl -s -o /dev/null -w "%{http_code}" http://192.168.64.5:30466/ 200

→ 롤아웃 완료 직후의 첫 요청은 연결조차 맺지 못했고(000) 몇 초 뒤에는 워커 세 대의 30466 포트가 모두 200으로 응답했어요.

롤아웃 완료와 노드 포트의 실제 응답 사이에 몇 초 틈이 있었다는 사실만 기록해 둘게요. 원인은 확인하지 않았어요. 7편에서도 "준비 완료" 표시와 실제 응답이 어긋난 적이 있었는데, 이번에는 기다리면 저절로 맞춰지는 정도였습니다. 파드는 worker1에 하나만 떴는데도 worker2·3의 포트가 똑같이 응답했다는 점도 눈여겨볼 만해요. 이 성질은 8장에서 NodePort를 닫는 이유가 됩니다.

차트가 실제로 무엇을 만들었는지는 helm get manifest로 볼 수 있어요. 릴리스가 클러스터에 적용한 매니페스트 원문에서 종류와 이름만 골라냈습니다.

그림 2. 리비전 1이 만든 오브젝트는 ServiceAccount, Secret, ClusterRoleBinding, Service, Deployment 다섯 개였다

목록은 ServiceAccount headlamp, Secret oidc, ClusterRoleBinding headlamp-admin, Service headlamp, Deployment headlamp 다섯 개예요. ClusterRoleBinding 아래에 이름이 세 개(headlamp-admin, cluster-admin, headlamp) 나온 것은 그 오브젝트 안에 바인딩 자신의 이름, 묶는 역할의 이름, 묶이는 계정의 이름이 함께 들어 있기 때문이에요. ReplicaSet과 Pod는 목록에 없어요. 2편에서 본 대로 이 둘은 컨트롤러가 Deployment를 보고 만드는 오브젝트라서 차트가 직접 만들지 않습니다.

이번에는 클러스터에 실제로 생긴 것을 종류별로 조회했어요.

그림 3. headlamp-admin이 kube-system/headlamp 계정에 ClusterRole/cluster-admin을 묶고 있었다

위에서부터 읽으면 이래요. 서비스 headlamp는 NodePort 타입이고 클러스터 IP는 10.104.14.9, 포트는 80:30466/TCP예요. Deployment·ReplicaSet·Pod는 모두 1개씩 준비돼 있고 컨테이너는 ghcr.io/headlamp-k8s/headlamp:v0.46.0 이미지로 4466 포트를 엽니다. 서비스의 80 포트로 온 요청은 이 4466 포트로 전달돼요.

컨테이너 인자 네 개는 차트의 기본값에서 왔어요. -in-cluster는 클러스터 안에서 실행하는 모드를 켜요. Headlamp 문서에 따르면 이 모드에서는 파드의 ServiceAccount로 클러스터 컨텍스트를 메모리에 만들고 그 이름이 -in-cluster-context-name=main의 main입니다. -session-ttl=86400은 차트 values.yaml에 "세션 토큰 TTL(초), 기본 24시간"이라고 설명돼 있어요. -plugins-dir은 플러그인을 읽을 폴더를 정하는 인자예요.

Secret oidc는 타입이 Opaque이고 데이터가 하나도 없어요. 차트 템플릿을 보면 이 Secret은 OIDC 로그인 설정(clientID, issuerURL 같은 값)을 담는 자리이고 값이 주어진 항목만 채워져요. OIDC를 설정하지 않았으니 빈 채로 만들어진 거예요. 마지막 helm get values는 설치할 때 제가 직접 준 값만 보여 줍니다. service.nodePort: 30466과 service.type: NodePort 두 줄뿐이었어요.

📖 용어: ServiceAccount
사람이 아니라 프로그램을 위한 쿠버네티스 계정이고 네임스페이스에 속해요. API 서버는 이 계정의 토큰을 받으면 system:serviceaccount:<네임스페이스>:<이름>이라는 사용자로 요청을 처리해요. 여기서는 kube-system의 headlamp 계정이 만들어졌고 차트의 Deployment는 Headlamp 파드를 이 계정으로 띄웁니다.
📖 용어: ClusterRoleBinding과 cluster-admin
ClusterRoleBinding은 역할(ClusterRole)에 적힌 권한을 사용자·그룹·ServiceAccount에게 클러스터 전체 범위로 묶어 주는 오브젝트예요. cluster-admin은 쿠버네티스에 기본으로 들어 있는 역할이에요. RBAC 문서는 이 역할을 "모든 리소스에 모든 동작을 할 수 있는 슈퍼유저 권한"이라고 설명해요. ClusterRoleBinding으로 묶으면 모든 네임스페이스의 모든 리소스를 다룰 수 있게 됩니다.
📖 용어: NodePort
Service 타입 중 하나예요. 지정한 포트(기본 범위 30000~32767)를 클러스터의 모든 노드에 같은 번호로 열고 그 포트로 온 요청을 서비스의 파드로 보내요. 클러스터 밖에서 노드 IP만 알면 들어올 수 있게 하는 가장 간단한 방법입니다.

여기까지 내용을 그림 한 장에 모으면 이렇게 돼요. 위 두 줄은 화면을 띄우는 쪽이고 아래 줄은 권한을 주는 쪽이에요.

그림 4. 서비스 값 두 줄만 줬는데, 화면을 띄우는 쪽과 함께 cluster-admin을 묶는 쪽이 생겼다

값으로 준 것은 서비스 두 줄뿐인데, 클러스터 전체 관리자 권한이 있는 계정이 하나 생겼어요. helm install 한 줄의 결과를 알려면 제가 준 값이 아니라 helm get manifest를 봐야 했어요.

⚠️ 주의: 값 두 줄에 cluster-admin이 따라왔어요
차트의 values.yaml에는 clusterRoleBinding.create: true와 clusterRoleName: cluster-admin이 기본값으로 들어 있어요. 그 옆 주석에는 클러스터에 있는 "제한된 권한의 Cluster Role" 이름을 넣으라는 안내와 함께 user-ro가 예로 적혀 있어요. 기본값을 그대로 두면 headlamp 계정은 클러스터 전체 관리자가 되고 같은 values.yaml의 automountServiceAccountToken: true에 따라 이 계정의 토큰이 Headlamp 파드 안에도 마운트돼요. 쿠버네티스 RBAC good practices 문서에는 관리자라도 꼭 필요할 때가 아니면 cluster-admin 계정을 쓰지 말라고 적혀 있어요. 실습이라 이번에는 기본값을 그대로 두었어요. 운영 환경이라면 clusterRoleName에 더 좁은 역할을 넣는 일부터 검토하게 됩니다. 이 계정에 실제로 어느 권한까지 필요한지는 확인하지 않았어요.

3. 첫 로그인: 토큰 한 줄을 붙여 넣자 노드 4대가 보였다

브라우저에서 NodePort 주소 http://192.168.64.3:30466/을 열자 로그인 창이 떴어요.

그림 5. Headlamp는 첫 화면에서 토큰부터 요구했다

차트 values.yaml에는 모든 사용자를 파드의 ServiceAccount로 인증하게 바꾸는 unsafeUseServiceAccountToken이라는 값이 있어요. 설명에는 이 값을 켜면 사용자별 인증이 꺼지고 인증 프록시 뒤에서만 안전하다고 적혀 있습니다. 기본값은 false라서 Headlamp는 로그인한 사람마다 따로 인증해요. 화면은 열려도 토큰이 없으면 클러스터에서 아무것도 볼 수 없다는 뜻이에요.

토큰은 차트 안내문에 적힌 명령으로 발급했어요. 마스터에서 kubectl create token headlamp --namespace kube-system을 실행하면 긴 문자열 하나가 나와요. 이 문자열을 ID 토큰 칸에 붙여 넣고 인증을 누르자 개요 화면이 열렸습니다. 이 토큰은 그림 4에 나온 headlamp 계정의 토큰이라서 이 화면에서 하는 일은 cluster-admin 권한으로 처리돼요.

⚠️ 주의: 첫 캡처에 토큰 일부가 찍혔어요
이 글에 넣을 화면을 헤드리스 브라우저 스크립트로 찍었는데, 첫 시도에서 스크립트가 토큰을 로그인 입력칸이 아니라 숨어 있던 검색창에 입력했어요. 그 결과 찍힌 이미지에 토큰 일부가 보였습니다. 그 이미지는 바로 지우고 스크립트가 입력칸을 "ID 토큰"이라는 라벨로 찾도록 고쳐 다시 찍었어요. 토큰을 다루는 화면을 찍었다면 올리기 전에 이미지를 직접 열어 확인해야 해요. 그림 5와 그림 6에는 토큰이 없습니다.

로그인 직후의 개요 화면이에요.

그림 6. 노드 4/4와 파드 16/16이 100%였고 바로 아래에 경고 이벤트 13건이 있었다

숫자를 읽어 볼게요. CPU는 8 단위로 노드 4대 × 2 CPU와 같고 메모리는 15.25 GB로 표시됐어요. 파드는 16개 중 16개, 노드는 4대 중 4대가 준비됨 상태라서 두 원이 모두 100%였습니다. 왼쪽 위의 "Clusters main"은 앞에서 본 -in-cluster-context-name=main 인자에서 온 이름이에요.

아래쪽 이벤트 목록에는 경고만 걸러 13건이 보였어요. 맨 위 줄은 Headlamp 자신의 파드 headlamp-86c49cb4f4-8rv48이 2분 50초 전에 남긴 Unhealthy 이벤트예요. 준비 검사(readiness probe)가 http://10.244.194.78:4466/에 접속하다 connection refused를 받았다는 내용이고 횟수는 1이었어요. 컨테이너가 4466 포트를 열기 전에 첫 검사가 실행된 것으로 보여요. 그 아래 줄은 15분 전 calico-kube-controllers의 준비 검사 실패였습니다.

초록 원 두 개만 보면 클러스터는 완벽해 보여요. 하지만 같은 화면 아래에 경고가 13건 쌓여 있었고 그중 하나는 방금 설치한 Headlamp 자신의 것이었어요. 대시보드가 모두 초록이어도 실패가 숨어 있을 수 있다는 이야기는 추적과 디버깅 2편 - 모든 대시보드가 초록불인데, 주문은 실패하고 있었다에서 다뤘고 관측 도구 자체를 관측하는 문제는 8편에서 다뤘어요.

4. 강의는 API 서버를 거쳐 들어가라고 했다

여기까지는 NodePort로 들어왔어요. 강의에서는 다른 길을 안내했습니다. "접속하는 방법에는 프록시 포트, 노드포트, API 서버가 있는데, API 서버를 이용한 보안 접속을 해야 한다." 강의를 들으며 메모해 둔 문장이에요.

쿠버네티스 문서 Access Services Running on Clusters에서도 클러스터 밖에서 서비스에 닿는 방법을 비슷하게 나눠요. 첫째는 NodePort나 LoadBalancer로 서비스를 밖에 여는 방법이에요. 문서는 이 방법을 쓸 때 노출하는 서비스가 안전한지, 서비스가 스스로 인증을 하는지 생각해 보라고 적어 둡니다. 둘째는 API 서버의 프록시 기능(proxy verb)을 쓰는 방법이에요. 문서는 이 방법이 원격 서비스에 닿기 전에 API 서버의 인증과 인가를 거친다고 설명해요. 바로 아래에는 일부 웹 애플리케이션에서 프록시가 문제를 일으킬 수 있다는 경고도 있습니다. 셋째는 클러스터 안의 노드나 파드에 들어가서 접속하는 방법이에요.

Proxies in Kubernetes 문서는 두 번째 방법에 쓰이는 프록시를 둘로 나눠요. 하나는 kubectl proxy예요. 내 컴퓨터의 localhost 주소에서 받은 요청에 인증 헤더를 붙여 API 서버로 보내요. 다른 하나는 API 서버 프로세스 안에서 도는 API 서버 프록시예요. 저는 강의의 "프록시 포트"를 kubectl proxy로, "API 서버"를 API 서버 프록시 주소를 직접 여는 방법으로 이해했어요. 두 길 모두 결국 API 서버 프록시를 거쳐요.

📖 용어: API 서버 프록시 (apiserver proxy)
kube-apiserver 안에 들어 있는 프록시예요. /api/v1/namespaces/<네임스페이스>/services/[https:]<서비스>[:<포트>]/proxy/ 경로로 요청을 받으면, 인증과 인가를 마친 뒤 그 서비스로 요청을 넘겨요. 클러스터 밖에서는 닿지 않는 클러스터 IP에 API 서버를 거쳐 닿게 해 주는 기능입니다.

우리 서비스에 맞추면 경로는 /api/v1/namespaces/kube-system/services/http:headlamp:80/proxy/가 돼요. 서비스 이름 앞의 http:는 API 서버가 서비스에 HTTP로 연결하라는 표시(기본값도 HTTP)이고 뒤의 80은 서비스 포트예요. 세 길을 그림 한 장에 놓으면 이렇습니다. 세 번째 길은 6장에서 고르게 되는 방법이에요.

그림 7. 셋 다 같은 Headlamp 파드에 닿는다. 다른 점은 파드에 닿기 전에 누가 신원을 확인하느냐다

Mac에서 curl로 이 경로를 두 번 호출했어요. 한 번은 클러스터 CA만 주고 다른 한 번은 관리자 클라이언트 인증서까지 붙였습니다. 두 파일 모두 ./lab이 만든 kubeconfig에서 꺼낸 파일이에요.

그림 8. 같은 주소가 인증서 없이는 403, 관리자 인증서를 붙이면 200이었다. NodePort는 아무것도 없이도 200이었다

인증서 없이 보낸 요청은 403을 받았어요. 응답의 message를 옮기면 이렇습니다.

services "http:headlamp:80" is forbidden: User "system:anonymous" cannot get resource "services/proxy" in API group "" in the namespace "kube-system"

→ 이름 없는 사용자(system:anonymous)에게는 kube-system 네임스페이스에서 서비스 프록시를 쓸 권한이 없다는 뜻이에요.

쿠버네티스 인증 문서에 따르면 다른 인증 방법에서 거절되지 않은 요청은 익명 요청이 되고 사용자 이름 system:anonymous, 그룹 system:unauthenticated를 받아요. 그리고 RBAC은 익명 사용자에게 명시적으로 권한을 준 경우에만 허용합니다. 그러니까 이 403은 "누구인지 모르겠다"는 거절이 아니라 "익명 사용자에게는 이 일을 허락하지 않는다"는 거절이에요. 관리자 인증서를 붙이자 200과 5,061바이트짜리 HTML이 돌아왔어요. 5편에서 본 대로 이 인증서의 그룹은 kubeadm:cluster-admins이고 kubeadm이 이 그룹에 클러스터 관리자 권한을 묶어 둡니다.

받은 HTML에서 눈여겨볼 줄이 하나 있었어요. <base href="/api/v1/namespaces/kube-system/services/http:headlamp:80/proxy/">입니다. 이 태그를 Headlamp가 넣었는지 API 서버 프록시가 고쳐 넣었는지는 확인하지 않았어요. 응답에 이 태그가 있었다는 사실만 다음 장에서 씁니다.

📖 용어: base 태그 (<base href>)
HTML 문서에서 상대 경로를 해석할 때 기준이 되는 주소를 정하는 태그예요. base가 /a/b/이면 static/app.js는 /a/b/static/app.js로 해석돼요. 다만 /config와 같이 슬래시로 시작하는 경로는 base의 경로를 무시하고 그 서버의 맨 위(루트)에서부터 찾습니다.

마지막 줄은 비교용이에요. NodePort 30466은 인증서도 토큰도 없이 200으로 응답했어요. Headlamp가 로그인 창에서 토큰을 요구하긴 하지만 노드 IP에 닿는 사람은 누구나 그 화면까지는 들어올 수 있다는 뜻이에요. 강의에서 API 서버 경로를 쓰라고 한 이유를 저는 이 차이로 이해했어요. API 서버 경로에서는 Headlamp에 닿기 전에 API 서버가 신원과 권한을 먼저 확인합니다.

브라우저로 이 경로를 열려면 한 가지가 더 필요했어요. 같은 Access Services 문서에 따르면 브라우저는 보통 토큰을 넘기지 못해요. 그래서 관리자 클라이언트 인증서를 브라우저가 쓸 수 있는 형식(.p12)으로 묶어 Mac 키체인에 넣고 클러스터 CA도 함께 넣었습니다.

⚠️ 주의: 브라우저에 넣은 관리자 인증서는 관리자 권한 그 자체예요
키체인에 넣은 인증서는 사용자 kubernetes-admin, 그룹 kubeadm:cluster-admins의 인증서예요. 그 브라우저가 6443 포트로 보내는 요청은 Headlamp 화면을 거치든 거치지 않든 모두 클러스터 관리자로 인증돼요. 5편에서 본 대로 공식 문서도 admin.conf를 다른 사용자와 공유하지 말라고 합니다. 실습용 VM이라 이렇게 했지만 실습이 끝나면 키체인에서 지우는 편이 안전해요. .p12 파일과 CA 파일은 실습 저장소에 올라가지 않도록 Git 제외 목록에 넣어 두었어요.

5. 로그인하자 화면이 끝없이 돌았다

인증서를 넣은 브라우저로 API 서버 경로를 열었어요. 로그인 창까지는 NodePort 때와 똑같이 떴고 토큰을 넣고 인증 버튼을 누르는 데까지는 됐습니다. 그다음부터 화면이 로딩 표시만 띄운 채 넘어가지 않았어요.

무엇이 실패하는지 보려고 같은 상황을 헤드리스 크롬으로 재현했어요. 관리자 인증서를 쓰는 크롬으로 API 서버 경로를 열고 토큰으로 로그인한 뒤 12초 동안 상태 코드가 400 이상인 응답만 모았습니다. 이 기록은 나중에 Headlamp를 전용 네임스페이스 headlamp로 옮긴 뒤에 재현한 결과라서 경로의 네임스페이스가 kube-system이 아니라 headlamp예요.

그림 9. 로그인 뒤 12초 동안 /plugins가 19번, /config가 2번 404를 받았다

첫 페이지의 제목은 Headlamp였고 주소도 프록시 경로 그대로였어요. 문제 응답은 모두 21건이었고 전부 두 경로에서 나왔습니다. GET /plugins가 19번, GET /config가 2번이에요. 둘 다 프록시 경로가 아니라 /로 시작해요. 이 요청은 https://192.168.64.2:6443/plugins로 갔는데 API 서버에는 /plugins라는 경로가 없으니 404로 응답했어요. 같은 요청이 12초 동안 계속 반복된 것을 보면, 화면은 설정과 플러그인 목록을 받아야 다음으로 넘어가는데 그 요청이 계속 실패해서 재시도하고 있었던 것으로 보여요.

앞 장의 base 태그를 떠올리면 이 결과를 설명할 수 있어요. 첫 페이지를 비롯해 base 경로를 따른 요청은 프록시 경로 아래로 가서 Headlamp에 닿았어요. 400 이상 응답 목록에 다른 경로가 없었으니 그 요청은 실패하지 않았다는 뜻입니다. 반면 /config와 /plugins는 슬래시로 시작해서 base를 무시하고 API 서버의 루트로 갔어요. 로그인 뒤에 화면이 보낸 요청이었으니 페이지의 자바스크립트가 만든 주소로 보여요.

그림 10. 프록시 경로 아래로 간 요청은 Headlamp에 닿았고 루트로 간 /config와 /plugins에는 API 서버가 직접 404로 응답했다

쿠버네티스 문서에 이 증상이 그대로 적혀 있었어요. 같은 Access Services 문서의 브라우저 항목에서는 API 서버 프록시 주소를 브라우저 주소창에 넣을 수 있다고 설명하면서 이렇게 경고합니다. "Some web apps may not work, particularly those with client side javascript that construct URLs in a way that is unaware of the proxy path prefix." 프록시 경로 접두어를 모르는 채 주소를 만드는 자바스크립트가 있는 웹 앱은 동작하지 않을 수 있다는 뜻이고 이번 Headlamp가 그런 경우였어요.

kubectl proxy로 여는 방법은 시험하지 않았어요. 다만 그 길도 같은 /api/v1/.../proxy/ 접두어를 쓰기 때문에 같은 문제가 생길 것으로 봤습니다.

6. base URL을 맞추자 이번엔 첫 페이지부터 404였다

Headlamp에는 루트가 아닌 하위 경로에서 실행하는 옵션이 있어요. Base URL 문서에 따르면 Headlamp는 보통 도메인의 루트에서 동작하지만 -base-url 인자로 /headlamp 같은 경로 아래에서 동작하게 할 수 있어요. 차트에서는 config.baseURL 값이 이 인자가 됩니다. base URL을 프록시 경로로 맞추면 /config도 프록시 경로 아래로 갈 거라고 기대했어요.

master$ helm upgrade headlamp headlamp/headlamp -n kube-system --reuse-values --set config.baseURL=/api/v1/namespaces/kube-system/services/http:headlamp:80/proxy master$ kubectl -n kube-system get pod -l app.kubernetes.io/instance=headlamp -o jsonpath="{.items[0].spec.containers[0].args}" ["-in-cluster","-in-cluster-context-name=main","-plugins-dir=/headlamp/plugins","-session-ttl=86400","-base-url=/api/v1/namespaces/kube-system/services/http:headlamp:80/proxy"] # 같은 브라우저 재현: 이번에는 첫 페이지부터 404 1st page: /api/v1/namespaces/kube-system/services/http:headlamp:80/proxy/ 404 GET /api/v1/namespaces/kube-system/services/http:headlamp:80/proxy/

→ 컨테이너 인자 끝에 -base-url이 붙었지만 이번에는 프록시 경로의 첫 페이지 자체가 404였어요.

API 서버가 서비스에 어떤 경로를 넘기는지 보면 이유를 짐작할 수 있어요. 쿠버네티스 문서의 예시에서 .../services/elasticsearch-logging/proxy/_search?q=user:kimchy는 Elasticsearch의 _search 엔드포인트를 호출합니다. 프록시 경로 뒤에 붙인 부분이 서비스가 받는 경로가 된다는 뜻이에요. 그렇다면 .../proxy/로 들어온 첫 요청은 Headlamp에 /로 도착했을 것이고 base URL을 프록시 경로로 바꾼 Headlamp는 /api/v1/.../proxy/로 시작하는 요청만 자기 것으로 받았을 거예요. Headlamp 로그는 확인하지 않았으므로 이 설명은 문서 예시와 관찰 결과를 맞춰 본 해석입니다.

그래서 바로 되돌렸어요. Helm은 업그레이드할 때마다 리비전을 남기므로 설치 때의 리비전 1로 돌아가면 됩니다.

master$ helm rollback headlamp 1 -n kube-system Rollback was a success! Happy Helming! master$ helm history headlamp -n kube-system | tail -3 1 Mon Nov 9 19:56:26 2026 superseded headlamp-0.46.0 0.46.0 Install complete 2 Mon Nov 9 20:05:01 2026 superseded headlamp-0.46.0 0.46.0 Upgrade complete 3 Mon Nov 9 20:06:10 2026 deployed headlamp-0.46.0 0.46.0 Rollback to 1

→ 되돌린 작업도 새 리비전 3으로 기록돼요. base URL을 넣었던 리비전 2는 superseded로 남고 지금 배포된 것은 "Rollback to 1"인 리비전 3이에요.

되돌린 뒤 NodePort는 다시 200으로 응답했어요. 그리고 Headlamp의 Base URL 문서를 다시 읽다가 이 옵션 자체를 쓰지 말라는 문장을 찾았어요. 같은 출처(origin)에 여러 앱을 올리면 앱끼리 서로의 정보에 접근하고 요청을 보낼 수 있으니, 확신이 없으면 Headlamp를 별도 출처(도메인이나 포트)에 두고 -base-url 옵션을 쓰지 말라는 내용이에요. API 서버 프록시 경로로 연 Headlamp는 API 서버와 같은 출처 https://192.168.64.2:6443 위에 올라가요. 경로를 맞추는 데 성공했더라도 Headlamp 문서에서 피하라고 한 배치였던 셈이에요.

이 방식은 여기서 그만뒀어요. Headlamp는 API 서버의 서비스 프록시 경로로 여는 방식과 맞지 않았어요. 대신 강의에서 그 경로로 얻으려던 것을 다시 정리했습니다. 노드 포트를 아무에게나 열지 않아야 하고 Headlamp에 닿기 전에 API 서버가 신원과 권한을 확인해야 해요. 이 두 조건을 모두 만족하는 방법이 kubectl port-forward였어요.

📖 용어: kubectl port-forward
내 컴퓨터의 포트 하나를 클러스터 안 파드의 포트에 연결해 주는 kubectl 명령이에요. 서비스나 Deployment 이름을 주면 거기에 맞는 파드 하나를 골라 연결해요. 연결은 API 서버를 거치고 명령이 실행되는 동안만 유지됩니다.

쿠버네티스의 port-forward 문서에 따르면 이 명령의 접근은 RBAC으로 통제되고 인가는 kubectl이 아니라 API 서버가 해요. 이 명령을 쓰려면 보통 파드의 get 권한과 pods/portforward의 create 권한이 필요하다고 합니다. kubectl port-forward 레퍼런스를 보면 --address의 기본값이 localhost라서 따로 지정하지 않으면 명령을 실행한 컴퓨터의 127.0.0.1과 ::1에서만 연결을 받아요.

앞에서 본 Dashboard 문서에서도 지금은 접속 방법으로 kubectl -n kubernetes-dashboard port-forward svc/kubernetes-dashboard-kong-proxy 8443:443을 안내하면서 명령을 실행한 컴퓨터에서만 UI에 접근할 수 있다고 설명해요. Headlamp의 클러스터 설치 문서에도 kubectl port-forward -n kube-system service/headlamp 8080:80이 나옵니다. 두 도구의 공식 문서가 모두 이 길을 안내하고 있었어요.

💡 실무에서는: 별도 도메인, 인그레스, 그리고 OIDC
port-forward는 혼자 쓰는 실습에 맞는 방법이에요. 여러 사람이 쓰는 클러스터라면 사람마다 kubectl과 port-forward 권한을 나눠 줘야 해요. Headlamp의 클러스터 설치 문서는 흔한 구성의 예로 Headlamp를 클러스터 안에 두고 인그레스로 사용자에게 여는 방식을 소개해요. 접속은 ServiceAccount 토큰이나 OIDC 로그인으로 설정하라고 안내합니다. 이때도 Base URL 문서의 권고대로 Headlamp에는 전용 도메인을 따로 주는 편이 안전합니다. 2장에서 빈 채로 만들어진 Secret oidc가 이 OIDC 설정을 담는 자리예요.

7. port-forward는 Mac에서 no route to host로 막혔다

Mac 터미널에서 처음에는 8080 포트로 port-forward를 열었어요. Headlamp 문서 예시와 같은 번호예요. 그런데 포워딩이 시작되기도 전에 오류가 났습니다.

mac$ ./lab kubectl -n kube-system port-forward svc/headlamp 8080:80 Unable to connect to the server: dial tcp 192.168.64.2:6443: connect: no route to host

→ kubectl이 마스터의 API 서버(192.168.64.2:6443)에 TCP 연결을 맺으려 했는데 운영체제가 그 주소로 가는 경로가 없다고 응답했다는 뜻이에요.

몇 분 전까지 같은 Mac에서 curl로 6443에 잘 접속했으니 이상했어요. 같은 시각에 몇 가지를 한꺼번에 확인했습니다.

그림 11. 20:07:38, kubectl은 no route to host인데 nc는 같은 주소의 6443 연결에 성공했다

20:07:38에 ./lab kubectl get nodes도 같은 no route to host로 실패했어요. 그런데 바로 이어서 실행한 nc -z -G 3 192.168.64.2 6443은 연결에 성공했습니다. 라우팅 표에도 192.168.64.2로 가는 경로가 bridge100 인터페이스로 잡혀 있었어요. 경로가 있고 포트도 열려 있고 다른 프로그램은 연결되는데, kubectl만 막힌 거예요. macOS 버전은 26.6.2였어요.

이 증상은 macOS의 로컬 네트워크 개인정보 보호 기능으로 설명할 수 있었어요. Apple의 기술 노트 TN3179: Understanding local network privacy에서 확인한 내용은 이래요. 이 기능은 macOS 15부터 들어왔고 로컬 네트워크 주소로 나가는 TCP 연결에는 로컬 네트워크 접근 권한이 필요해요. 이 검사는 네트워크 스택 깊은 곳에서 이뤄져 BSD 소켓을 포함한 모든 네트워크 API에 적용됩니다. 권한이 없으면 시스템이 그 동작을 막고 사용자는 시스템 설정 > 개인정보 보호 및 보안 > 로컬 네트워크에서 앱별로 이 권한을 켜고 꺼요.

📖 용어: 로컬 네트워크 개인정보 보호 (local network privacy)
프로그램이 같은 네트워크의 기기에 접속하려면 사용자의 허락을 받도록 하는 Apple 운영체제의 권한이에요. macOS에는 15부터 들어왔어요. TN3179는 로컬 네트워크를 브로드캐스트가 가능한 인터페이스(Wi-Fi, 이더넷 등)에 연결된 IP 네트워크로 정의해요. 저는 Mac과 VM을 잇는 bridge100의 192.168.64.0/24도 여기에 들어간다고 봤어요.

어떤 프로그램이 자동으로 허용되는지도 문서에 나와 있어요. macOS는 launchd가 띄운 데몬, root로 실행되는 프로그램, 그리고 터미널(Terminal)이나 SSH에서 실행한 명령줄 도구와 그 자식 프로세스를 자동으로 허용해요. 그 밖의 프로그램은 사용자가 권한을 줄 때까지 막힌다고 적혀 있습니다. 또 macOS는 어떤 프로세스가 로컬 네트워크에 접속하면 책임 코드(responsible code)를 찾아요. 앱이 띄운 도우미 도구가 접속하면 그 앱을 책임 코드로 보고 사용자의 선택도 앱 단위로 기록해 시스템 설정에 보여 준다고 해요.

이 두 규칙을 제 상황에 적용해 보면 이렇게 돼요. 저는 macOS 기본 터미널 앱이 아니라 다른 앱 안에 들어 있는 터미널에서 kubectl을 실행했어요. 그러면 kubectl의 책임 코드는 그 앱이 되는데 그 앱에는 로컬 네트워크 권한이 없었어요. 실제로 시스템 설정 > 개인정보 보호 및 보안 > 로컬 네트워크에서 터미널을 띄운 앱을 켜자 같은 Mac에서 port-forward가 바로 열렸습니다.

mac$ ./lab kubectl -n kube-system port-forward svc/headlamp 18809:80 Forwarding from 127.0.0.1:18809 -> 4466 Forwarding from [::1]:18809 -> 4466 mac$ curl -s -o /dev/null -w "localhost:18809 %{http_code}\n" http://localhost:18809/ localhost:18809 200

→ Mac의 18809 포트가 IPv4와 IPv6 localhost 양쪽에서 Headlamp 파드의 4466 포트로 이어졌고 그 주소로 보낸 요청은 200을 받았어요.

포트 번호 18809는 다른 프로그램과 겹치지 않게 제가 정한 값이에요. 출력에 서비스 포트 80이 아니라 4466이 찍힌 점도 눈여겨볼 만해요. port-forward는 서비스 이름을 받으면 그 서비스에 맞는 파드 하나를 골라 파드의 포트로 바로 연결하기 때문에 서비스의 80이 가리키는 컨테이너 포트 4466이 출력에 나와요.

설명하지 못한 부분도 남았어요. 그림 11의 한 줄 명령 안에서 kubectl은 막히고 nc는 통과한 이유, 그리고 몇 분 전 curl이 통과한 이유는 TN3179의 내용만으로 알 수 없었어요. no route to host라는 오류가 이 권한 때문에 난다는 내용도 문서에 직접 적혀 있지는 않아요. 확인한 것은 앱을 허용하기 전에는 kubectl이 실패했고 허용한 뒤에는 성공했다는 사실까지예요.

그림 12. 경로도 포트도 그대로였다. 바뀐 것은 터미널을 띄운 앱의 로컬 네트워크 권한 하나였다
⚠️ 주의: no route to host가 늘 경로 문제는 아니에요
오류 문구만 보면 VM 네트워크가 끊긴 것으로 읽혀요. Mac에서 VM으로 가는 길(vzNAT)을 3편에서 따로 붙인 이 환경에서는 더욱 그렇게 보입니다. 하지만 이번에는 경로도 포트도 멀쩡했어요. macOS 15 이상에서 특정 프로그램만 이 오류를 낸다면, 같은 시각에 nc -z <IP> <포트>와 route -n get <IP>로 경로와 포트부터 확인해 보세요. 둘 다 정상인데 그 프로그램만 실패하면, 시스템 설정 > 개인정보 보호 및 보안 > 로컬 네트워크에서 그 프로그램을 띄운 앱이 꺼져 있지 않은지 확인합니다.

8. 쓸 일이 없어진 NodePort를 닫았다

port-forward로 접속되는 것을 확인했으니 NodePort를 더 열어 둘 이유가 없었어요. Service 문서에 따르면 NodePort에서는 모든 노드가 같은 포트 번호로 요청을 받아 서비스로 넘겨요. 2장에서 파드가 worker1에만 있는데도 worker2·3의 30466이 200으로 응답한 것이 바로 이 동작이에요. 노드 IP에 닿는 사람은 누구나 Headlamp 로그인 화면까지 올 수 있다는 뜻이기도 합니다.

master$ helm upgrade headlamp headlamp/headlamp -n kube-system --reuse-values --set service.type=ClusterIP --set service.nodePort=null >/dev/null && helm get values headlamp -n kube-system && kubectl -n kube-system get svc headlamp USER-SUPPLIED VALUES: service: type: ClusterIP NAME TYPE CLUSTER-IP EXTERNAL-IP PORT(S) AGE headlamp ClusterIP 10.104.14.9 <none> 80/TCP 12m mac$ curl -s -m5 -o /dev/null -w "NodePort 30466 (닫힌 뒤): %{http_code}\n" http://192.168.64.3:30466/ NodePort 30466 (닫힌 뒤): 000 mac$ curl -s -m5 -o /dev/null -w "port-forward localhost:18809: %{http_code}\n" http://localhost:18809/ port-forward localhost:18809: 200

→ 서비스 타입이 ClusterIP로 바뀌어 노드 포트가 사라졌고 30466은 응답하지 않게(000) 됐어요. port-forward로 연 localhost:18809는 그대로 200이에요.

명령에서 service.nodePort=null을 같이 준 데는 이유가 있어요. --reuse-values는 Helm 문서 설명대로 지난 릴리스의 값을 다시 쓰고 명령줄에서 준 값을 그 위에 합쳐요. 타입만 바꾸면 설치 때 준 nodePort: 30466이 값에 그대로 남습니다. Helm 문서는 값에서 키를 지우고 싶으면 그 키를 null로 덮어쓰라고 안내해요. 결과의 USER-SUPPLIED VALUES에 type: ClusterIP 한 줄만 남은 것이 그 덕분이에요. 서비스를 지우지 않고 고쳤기 때문에 클러스터 IP 10.104.14.9도 그대로 유지됐어요.

이제 Headlamp에 들어가는 길은 Mac에서 port-forward 명령이 실행 중인 동안 열리는 http://localhost:18809/ 하나예요. 그 주소를 열자 그림 5와 같은 로그인 화면이 떴고 토큰을 넣으니 개요 화면이 열렸습니다. 브라우저에서 보면 달라진 것은 주소 하나뿐이지만 그 사이에 API 서버의 인증과 인가가 들어갔어요.

남은 문제는 로그인 칸에 넣는 토큰이에요. 지금까지 쓴 토큰은 차트가 cluster-admin을 묶어 둔 headlamp 계정의 것이었어요. 이 토큰이 정확히 누구의 것이고 얼마 동안 유효한지, 강의의 admin-user 실습을 이 클러스터에 맞게 바꾸면서 무엇을 봤는지는 10편에서 다룹니다.

✍️ 오늘의 요약
강의의 Kubernetes Dashboard는 저장소가 아카이브돼 있었고 README와 쿠버네티스 문서가 함께 추천한 Headlamp로 바꿨어요.

Helm 차트는 서비스 값 두 줄만 받고도 NodePort 서비스와 함께 cluster-admin 바인딩까지 만들었어요. 강의대로 API 서버 프록시 경로로 열자 인증서 없이는 403, 관리자 인증서로는 200이 나왔지만 로그인 뒤 루트로 간 /config와 /plugins가 API 서버에서 404를 받으며 화면이 멈췄어요. base URL을 맞추자 첫 페이지부터 404가 나서 되돌렸어요. 그 뒤 API 서버를 거치면서 localhost에만 열리는 kubectl port-forward로 바꾸고 NodePort를 닫았습니다. 그 사이 macOS의 로컬 네트워크 권한이 kubectl만 막는 일도 있었어요. 웹 UI로 들어가는 길은 누가 먼저 신원을 확인하는지와 그 앱이 그 길의 경로 구조에서 동작하는지를 함께 따져 보고 골라야 해요.
