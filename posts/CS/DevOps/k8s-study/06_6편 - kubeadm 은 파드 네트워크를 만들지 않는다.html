kubeadm init 의 출력을 끝까지 내려가자 기다리던 문장이 나왔어요. Your Kubernetes control-plane has initialized successfully! 컨트롤 플레인이 다 떴다는 뜻입니다. 그런데 거기서 열두 줄을 더 내려가자 이런 문장이 있었어요. You should now deploy a pod network to the cluster. 이제 파드 네트워크를 클러스터에 배포하라는 안내예요.

성공 메시지 바로 뒤에 할 일이 하나 남아 있었던 거예요. kubeadm 은 API 서버와 etcd, 인증서까지 만들어 주지만, 파드에 IP 를 주거나 다른 노드의 파드까지 가는 경로를 만들지는 않아요. 그 일을 맡을 프로그램은 클러스터를 만드는 사람이 골라서 따로 설치해야 합니다. 이 실습 클러스터에서는 Calico v3.33.0 을 골랐어요. 이 글의 질문은 "파드 네트워크는 왜 따로 설치하고, 왜 Calico 였고, 기본 설정 그대로 두면 이 VM 노드에서 어디가 걸리는가"입니다.

이 글에서 다룰 것
· 파드 네트워크가 없으면 클러스터에서 무엇이 안 될까?
· Flannel·Calico·Cilium 중에서 강의 실습용으로 Calico 를 고른 이유는 무엇일까?
· NIC 가 둘인 노드에서 Calico 의 기본 설정은 어디서 문제가 될 수 있을까?
· worker1 의 파드가 worker3 의 파드에 요청을 보내면 패킷은 어느 경로로 갈까?
· NetworkPolicy 를 만들면 정말 트래픽이 막힐까?

1. 파드 네트워크가 없으면 CoreDNS 도 뜨지 않는다

master$ sudo kubeadm init --config /etc/kubernetes/kubeadm-config.yaml ... Your Kubernetes control-plane has initialized successfully! ... You should now deploy a pod network to the cluster. Run "kubectl apply -f [podnetwork].yaml" with one of the options listed at: https://kubernetes.io/docs/concepts/cluster-administration/addons/

→ 컨트롤 플레인 초기화는 성공했고, 파드 네트워크는 안내된 목록에서 하나를 골라 kubectl apply 로 직접 설치하라는 뜻이에요.

파드 네트워크가 없으면 무엇이 안 되는지부터 볼게요. kubeadm 문서는 이 단계를 이렇게 적고 있어요. 파드끼리 통신하려면 CNI 기반 파드 네트워크 애드온을 반드시 배포해야 하고, 네트워크를 설치하기 전에는 클러스터 DNS(CoreDNS)가 뜨지 않는다고요. 서비스 이름으로 다른 파드를 찾는 일부터 막힌다는 뜻입니다. 문서대로라면 1편에서 본 coredns 파드 두 개도 Calico 가 설치된 뒤에야 뜰 수 있었던 셈이에요.

그 네트워크가 지켜야 할 것도 문서에 정해져 있어요. 쿠버네티스 네트워크 모델은 두 가지를 요구합니다. 클러스터의 모든 파드는 클러스터 전체에서 고유한 IP 를 하나씩 받아요. 그리고 모든 파드는 같은 노드에 있든 다른 노드에 있든 프록시나 주소 변환(NAT) 없이 다른 파드와 직접 통신할 수 있어야 해요. 그런데 이 모델을 구현하는 코드는 쿠버네티스 안에 없어요. 문서는 그 일을 "파드 네트워크 구현체"가 맡고, 리눅스에서는 대부분의 컨테이너 런타임이 CNI 로 그 구현체와 연결된다고 설명합니다.

📖 용어: CNI (Container Network Interface)
파드가 만들어질 때 그 파드에 네트워크를 붙이는 방법을 정한 규격이에요. 컨테이너 런타임(이 클러스터에서는 containerd)이 이 규격을 따르는 플러그인을 써서 파드에 IP 를 주고 경로를 잡습니다. Calico·Flannel·Cilium 이 이 규격을 따르는 프로그램이라 "CNI 플러그인"이라고 불러요. 4편에서 containerd 설정에 CNI 플러그인 경로를 넣어 둔 것도 이 때문이에요.

그래서 이 클러스터에서 CNI 플러그인에게 맡긴 일은 세 가지예요. 파드에 IP 를 주는 일, 다른 노드에 있는 파드까지 가는 경로를 만드는 일, 그리고 NetworkPolicy 를 집행하는 일입니다. 앞의 두 가지는 위 네트워크 모델 자체라서 어떤 CNI 플러그인이든 해야 해요. 세 번째는 사정이 다릅니다. kubeadm 문서도 CNI 로 파드 네트워크를 제공하는 외부 프로젝트가 여럿 있고, 그중 일부가 NetworkPolicy 도 지원한다고 적고 있어요.

📖 용어: NetworkPolicy
어떤 파드로 들어오는(Ingress) 트래픽과 그 파드에서 나가는(Egress) 트래픽을 라벨 기준으로 허용하는 규칙을 적는 쿠버네티스 오브젝트예요. 네임스페이스에 정책이 하나도 없으면 모든 트래픽이 허용됩니다. 규칙을 실제로 집행하는 쪽은 쿠버네티스가 아니라 네트워크 플러그인이에요.

kubeadm 이 이 중 하나를 골라 주지 않는 이유도 문서에 있어요. kubeadm 은 특정 CNI 에 묶이지 않게 만들어졌고, 한 클러스터에는 파드 네트워크를 하나만 설치할 수 있습니다. 그래서 이 저장소의 scripts/master-init.sh 는 두 단계로 나뉘어 있어요. 먼저 kubeadm init 으로 컨트롤 플레인을 만들고, 이어서 Calico 매니페스트를 내려받아 두 곳을 고친 뒤 kubectl apply 합니다. 워커는 그다음에 조인해요. calico-node 는 DaemonSet(노드마다 파드를 하나씩 띄우는 리소스)이라서, 나중에 조인한 워커에도 하나씩 자동으로 뜹니다. 1편의 kube-system 목록에 calico-node 가 노드 수와 같은 4개 있었던 이유가 이것이에요.

2. Flannel·Calico·Cilium 중 Calico 를 고른 이유

후보는 Flannel, Calico, Cilium 세 개였어요. 셋 다 CNI 플러그인이라 파드 IP 와 노드 간 경로는 모두 만들어 줍니다. 차이는 그다음에 있어요. 각 프로젝트의 공식 문서에서 이 글에 필요한 부분만 확인했습니다.

Flannel 의 README 는 첫 문장에서 자신을 "쿠버네티스를 위해 설계된 L3 네트워크를 단순하고 쉽게 구성하는 방법"이라고 소개해요. 설치는 릴리스에 붙은 매니페스트 하나를 kubectl apply 하는 방식입니다. NetworkPolicy 에 대해서는 README 가 분명하게 적어 두었어요. flanneld 바이너리는 NetworkPolicy 를 스스로 집행하지 않는다고 합니다. 정책이 필요하면 Helm 차트의 netpol.enabled 옵션으로 쿠버네티스 SIG 의 network policy 컨트롤러를 함께 띄우거나, 연결은 Flannel 에 맡기고 정책은 Calico 같은 다른 프로젝트에 맡기라고 안내해요.

Calico 문서는 NetworkPolicy 를 집행하려면 Calico 같은 네트워크 플러그인이 있어야 한다고 적고 있어요. 노드 사이 경로는 IPIP 나 VXLAN 으로 감싸서 보낼 수도 있고, 감싸지 않고 BGP 로 경로를 주고받을 수도 있습니다. 문서는 일반적으로는 캡슐화 없이 쓰기를 권하고, 노드 네트워크가 파드 IP 를 알기 어려운 환경에서 캡슐화가 쓸모 있다고 설명해요. 설치 방법 중 하나가 매니페스트 하나를 받아 apply 하는 방식입니다.

Cilium 은 리눅스 커널 기술인 eBPF 를 바탕으로 해요. NetworkPolicy 를 L3 부터 L7 까지 집행하고, Hubble 이라는 네트워크·보안 관측 플랫폼을 갖고 있습니다. 서비스 트래픽 처리도 직접 맡을 수 있어요. kube-proxy 를 완전히 대체하는 설정이 있고, Helm 기본값(kubeProxyReplacement=false)에서도 클러스터 안의 ClusterIP 부하 분산은 Cilium 이 패킷 단위로 처리한다고 문서에 나와요.

📖 용어: eBPF
리눅스 커널 안에 보안·관측·네트워크 제어 로직을 동적으로 넣을 수 있게 해 주는 커널 기술이에요(Cilium 문서의 설명). Cilium 은 이 기술로 kube-proxy 가 iptables 규칙으로 하던 서비스 처리까지 대신할 수 있습니다.
그림 1. 셋 다 파드 IP 와 노드 간 경로를 만든다. 갈리는 곳은 정책 집행과 서비스 처리다

제가 Calico 를 고른 이유는 세 가지예요. 셋 다 "강의를 따라 하는 실습 클러스터"라는 조건에서 내린 판단이고, 다른 두 플러그인이 모자라다는 뜻은 아닙니다.

첫째, 강의 실습에 NetworkPolicy 가 나와도 그대로 돌아가게 하고 싶었어요. Flannel 로 같은 결과를 얻으려면 README 가 안내하는 정책 컨트롤러나 다른 프로젝트를 함께 붙여야 해요. 실습 클러스터의 구성 요소는 하나라도 적게 두고 싶었습니다.

둘째, kube-proxy 와 iptables 가 서비스를 처리하는 기본 구성을 그대로 보고 싶었어요. 2편에서 Service 하나를 만들자 worker3 의 iptables 에 그 서비스의 규칙이 생겼고, kube-proxy 로그에는 "Using iptables Proxier" 가 찍혀 있었습니다. Cilium 의 서비스 처리는 그 일을 eBPF 로 옮긴 것이라서, 쿠버네티스의 기본 동작부터 익히려는 지금은 한 단계 다음 내용이라고 봤어요.

셋째, 설치가 매니페스트 하나예요. 이건 Flannel 도 같아서 Calico 만의 장점은 아닙니다. 다만 앞의 두 조건을 만족하면서 설치 스크립트에 curl 한 줄과 sed 몇 줄로 넣을 수 있었어요. 정책 집행은 플러그인 하나로 끝내고 서비스 처리는 쿠버네티스 기본 그대로 두는 조합이 이 실습에는 Calico 였어요.

💡 실무에서는: Calico 문서는 새 클러스터에 operator 를 권해요
이 글은 매니페스트로 설치했지만, Calico 설치 문서는 매니페스트 방식을 업그레이드 호환을 위해 유지한다고 적고, 새 클러스터에는 클러스터 규모에 맞게 설정을 잡아 주는 operator 를 권해요. 매니페스트 방식 안내도 노드 50대 이하 기준입니다. 이 실습은 노드가 4대이고 설치를 매니페스트 파일 하나로 끝내고 싶어서 매니페스트를 골랐어요. 운영 클러스터를 만든다면 operator 쪽 문서부터 보는 것이 맞습니다.

3. 기본값 그대로면 걸리는 두 곳

매니페스트를 받은 그대로 apply 하지 않고 두 곳을 고쳤어요. 둘 다 이 클러스터 노드의 네트워크 사정과 부딪힐 수 있는 값이었습니다. 3편에서 만든 노드에는 NIC 가 둘 있어요. eth0 은 Lima user-v2 네트워크(192.168.104.0/24)라서 VM 끼리 통하고, lima1 은 vzNAT 네트워크(192.168.64.0/24)라서 Mac 에서는 닿지만 VM 끼리는 통하지 않아요.

파드 대역: 192.168.0.0/16 은 VM 네트워크를 통째로 품는다

v3.33.0 매니페스트를 열어 보면 파드 대역 설정은 주석으로 꺼져 있고, 예시 값으로 192.168.0.0/16 이 적혀 있어요. Calico 설치 문서도 "파드 CIDR 로 192.168.0.0/16 을 쓴다면 다음 단계로 넘어가라"는 문장으로 이 단계를 시작합니다.

# calico.yaml (v3.33.0) 에서 calico-node 컨테이너의 env 일부 # Auto-detect the BGP IP address. - name: IP value: "autodetect" ... # The default IPv4 pool to create on startup if none exists. Pod IPs will be # chosen from this range. Changing this value after installation will have # no effect. This should fall within `--cluster-cidr`. # - name: CALICO_IPV4POOL_CIDR # value: "192.168.0.0/16"

→ 노드 IP 는 자동으로 감지하고, 파드 IP 를 나눠 줄 풀은 처음 시작할 때 하나도 없으면 만들며, 그 대역은 설치한 뒤에 바꿔도 효과가 없다는 뜻이에요. 마지막 두 줄은 주석이라 이대로는 적용되지 않습니다.

📖 용어: 파드 CIDR (podSubnet)
CIDR 은 주소 범위를 "시작 주소/고정 비트 수"로 적는 표기예요. 10.244.0.0/16 은 앞 16비트(10.244)가 고정이라 10.244 로 시작하는 주소 65,536개를 뜻합니다. 파드 CIDR 은 파드 IP 를 나눠 줄 범위이고, 이 클러스터는 kubeadm 설정의 podSubnet 에 10.244.0.0/16 을 넣었어요(5편).

192.168.0.0/16 은 192.168 로 시작하는 주소 전부예요. 노드의 두 네트워크 192.168.104.0/24 와 192.168.64.0/24 가 통째로 이 안에 들어갑니다. kubeadm 문서는 파드 네트워크가 호스트 네트워크와 겹치면 문제가 생기기 쉽다고 경고하고, 겹친다면 다른 대역을 골라 kubeadm init 과 네트워크 플러그인 YAML 양쪽에 넣으라고 안내해요. 그래서 주석을 풀고 값을 kubeadm 의 podSubnet 과 같은 10.244.0.0/16 으로 바꿨습니다.

그런데 이 글을 쓰면서 Calico 문서를 다시 읽다가, 스크립트에 적어 둔 주석이 절반만 맞았다는 것을 알았어요. 스크립트에는 "기본값 192.168.0.0/16 은 VM 네트워크와 겹친다"고 적었어요. 하지만 calico-node 설정 문서를 보면 이 변수를 비워 둘 때의 기본값이 192.168.0.0/16 으로 고정돼 있지 않습니다. kubeadm-config ConfigMap 에 podSubnet 이 있으면 그 값을 먼저 쓴다고 적혀 있어요. 설치 문서에도 kubeadm 으로 다른 파드 CIDR 을 쓰고 있다면 고칠 것이 없고 Calico 가 알아서 찾는다고 나옵니다. 그러니 이 클러스터에서는 주석을 그대로 둬도 10.244.0.0/16 이 잡혔을 가능성이 커요. 주석을 둔 채로 설치해 보지는 않았습니다. 스크립트의 주석은 이 내용에 맞게 고쳐 두었어요.

그래도 값을 직접 적는 방식은 그대로 뒀어요. 겹치는 일은 주석 속 192.168.0.0/16 을 그대로 살리거나, 설치 문서가 전제한 192.168.0.0/16 을 kubeadm 의 파드 대역으로 쓸 때 생깁니다. 그리고 이 값은 설치한 뒤에는 바꿔도 소용이 없어요. 처음 설치할 때 한 번에 맞게 들어가야 하는 값이라, 감지에 맡기지 않고 kubeadm 설정과 같은 값을 직접 적었습니다.

⚠️ 주의: 파드 대역은 설치한 뒤에 고쳐도 바뀌지 않아요
매니페스트 주석대로 calico-node 는 IP 풀이 하나도 없을 때만 이 값으로 풀을 만들어요. 노드 네트워크와 겹친 대역으로 한 번 설치했다면, 매니페스트 값만 고쳐 다시 apply 해도 이미 만들어진 풀은 그대로 남습니다. kubeadm 의 podSubnet, Calico 의 풀 대역, 노드 네트워크 세 가지를 설치 전에 나란히 놓고 겹치지 않는지 먼저 확인하세요.

노드 IP: NIC 가 둘이면 Calico 가 고르는 주소가 달라질 수 있다

두 번째는 Calico 가 각 노드의 IP 를 무엇으로 볼지예요. calico-node 는 노드마다 자기 IP 를 하나 정하고, 다른 노드는 그 IP 로 파드 트래픽을 보냅니다. 위 매니페스트는 IP 를 autodetect 로 두고, 감지 방법을 정하는 IP_AUTODETECTION_METHOD 는 적지 않아요. 이때 기본 방법은 first-found 이고, 문서는 이것을 "첫 번째 인터페이스의 첫 번째 유효한 IP 주소(docker 브리지 같은 로컬 인터페이스는 제외)"라고 설명합니다.

이 노드에서는 eth0 과 lima1 이 둘 다 유효한 IP 를 가진 인터페이스예요. 둘 중 어느 쪽이 "첫 번째"인지 문서는 순서를 적어 두지 않았고, 저도 기본값으로 설치해서 확인하지는 않았어요. 만약 lima1 의 192.168.64.x 가 노드 IP 로 잡히면 다른 노드는 그 주소로 파드 트래픽을 보내게 됩니다. 3편에서 master 가 worker1 의 lima1 주소(192.168.64.3)로 보낸 ping 은 100% 손실이었어요. 같은 주소로 보내는 파드 트래픽도 도착하지 못할 거예요.

그래서 감지 방법을 kubernetes-internal-ip 로 지정했어요. 이 방법은 쿠버네티스 Node 오브젝트의 Status.Addresses 에 있는 첫 번째 내부 IP(InternalIP)를 씁니다. 그 InternalIP 는 kubelet 이 노드를 등록하면서 올린 값이고, 4편에서 kubelet 에 --node-ip=<eth0 IP> 를 넣어 eth0 주소로 고정해 두었어요. 3편의 ./lab up 출력에 찍힌 노드 목록에서도 INTERNAL-IP 는 네 노드 모두 192.168.104.x 였습니다. kubelet 에서 한 번 정한 노드 IP 를 Calico 가 그대로 따라 쓰게 해서, 노드 IP 를 정하는 설정을 kubelet 한 곳으로 모았어요.

그림 2. 같은 노드라도 lima1 주소로 잡히면 다른 노드에서 보낸 파드 트래픽이 닿지 않는다

고친 결과는 실행 중인 calico-node DaemonSet 에서 확인했어요.

master$ kubectl -n kube-system get ds calico-node -o yaml | grep -A1 -E 'name: (CALICO_IPV4POOL_CIDR|IP_AUTODETECTION_METHOD|CALICO_IPV4POOL_IPIP)$' - name: IP_AUTODETECTION_METHOD value: kubernetes-internal-ip - name: CALICO_IPV4POOL_IPIP value: Always -- - name: CALICO_IPV4POOL_CIDR value: 10.244.0.0/16

→ 노드 IP 는 kubelet 이 등록한 InternalIP 로, 파드 대역은 10.244.0.0/16 으로 잡혔고, 노드 사이 파드 트래픽은 항상 IPIP 로 감싸서 보낸다는 뜻이에요. CALICO_IPV4POOL_IPIP=Always 는 제가 고친 값이 아니라 매니페스트에 처음부터 적혀 있던 값입니다. calico-node 설정 문서에 적힌 이 변수의 기본값은 Never 인데, 매니페스트가 Always 로 적어 두었어요.

💡 실무에서는: sed 로 고친 매니페스트는 고쳐졌는지 확인해요
스크립트는 매니페스트를 받을 때마다 sed 식 세 개로 세 군데를 고쳐요. 파드 대역 주석 두 줄을 각각 풀어 값을 넣고, value: "autodetect" 바로 아래에 감지 방법 두 줄을 끼워 넣습니다. 그런데 Calico 버전이 바뀌어 주석 형식이 달라지면 sed 는 아무것도 바꾸지 못한 채 성공으로 끝나고, 그대로 apply 하면 고치지 않은 매니페스트가 설치돼요. 그래서 apply 전에 바뀐 줄이 실제로 들어갔는지 grep 으로 세 번 확인하고, 하나라도 없으면 스크립트를 멈춥니다. 이미 설치된 뒤라면 Calico 문서가 안내하는 kubectl set env daemonset/calico-node -n kube-system IP_AUTODETECTION_METHOD=... 로 감지 방법을 바꿀 수도 있어요.

4. 노드마다 /26 블록을 받고, 다른 노드로는 tunl0 으로 보낸다

설치가 끝난 뒤 Calico 가 파드 IP 를 어떻게 나눴는지 봤어요. 파드 대역이 /16 이라고 해서 노드 하나가 그 대역 전체를 쓰지는 않아요. Calico 는 대역을 작은 블록으로 잘라 노드마다 붙이고, 그 연결을 blockaffinities 라는 리소스로 남깁니다.

📖 용어: IPAM 블록과 BlockAffinity
IPAM(IP 주소 관리)은 어떤 파드에 어떤 IP 를 줄지 정하는 일이에요. Calico 는 기본으로 주소 64개(/26)짜리 블록 단위로 주소를 다루고, 블록과 노드 사이의 연결을 BlockAffinity 리소스로 남겨요. Calico 문서는 이 리소스를 Calico IPAM 이 알아서 만들고 관리하니 보통은 손댈 일이 없다고 적고 있어요.
그림 3. 노드마다 /26 블록 하나, 다른 노드의 블록으로 가는 경로는 모두 eth0 주소를 거친다

노드 네 대가 /26 블록을 하나씩 받았어요. k8s-master 는 10.244.235.192/26, k8s-worker1 은 10.244.194.64/26, k8s-worker2 는 10.244.126.0/26, k8s-worker3 은 10.244.100.192/26 입니다. worker1 의 라우팅 표에는 나머지 세 노드의 블록마다 경로가 한 줄씩 있어요. 10.244.100.192/26 은 192.168.104.5(worker3)로, 10.244.126.0/26 은 192.168.104.4(worker2)로, 10.244.235.192/26 은 192.168.104.1(master)로 보내고, 세 줄 모두 장치가 tunl0 입니다. 다음 홉이 전부 eth0 쪽 192.168.104.x 이고, lima1 의 192.168.64.x 는 한 줄도 없어요. 3절에서 노드 IP 를 InternalIP 로 지정한 결과가 이 경로표에 그대로 나온 거예요.

📖 용어: IPIP (IP-in-IP) 캡슐화
출발지와 목적지가 파드 IP 인 원래 패킷 앞에 IP 헤더를 하나 더 붙여, 바깥 주소를 노드 IP 로 바꿔 보내는 방식이에요. 노드 사이 네트워크는 10.244.x 파드 주소를 모르지만 192.168.104.x 노드 주소로는 패킷을 전달할 수 있어서, 파드 패킷을 노드끼리 주고받는 패킷 안에 넣어 보냅니다. 리눅스에서는 tunl0 이라는 터널 장치가 이 일을 맡아요.

경로 끝에 붙은 mtu 1480 도 이 방식에서 나온 숫자예요. Calico 의 MTU 문서에 따르면 IPIP 헤더는 20바이트이고, 네트워크 MTU 가 1500 일 때 IPIP 를 쓰는 Calico 의 MTU 는 1480 입니다. 바깥에 헤더를 하나 더 붙이니 그만큼 안쪽 패킷에 쓸 수 있는 크기가 줄어요. onlink 는 다음 홉 주소가 그 장치에 바로 붙어 있는 것으로 간주하라는 표시예요(ip-route 매뉴얼).

그림 4. worker1 의 파드가 worker3 의 파드로 보낸 패킷은 노드 주소가 적힌 헤더에 한 번 더 감싸여 eth0 으로 간다

경로가 실제로 쓰이는지는 파드 두 개로 확인했어요. 2편에서 만든 hello 파드는 worker3 에 있어요. 여기에 busybox 파드 client 를 worker1 에 고정해 띄웠습니다(nodeName 지정). 요청이 반드시 노드를 넘어가게 하려는 배치예요.

master$ kubectl run client --image=busybox:1.37 --restart=Never --overrides='{"spec":{"nodeName":"k8s-worker1"}}' -- sleep 3600 && kubectl wait --for=condition=Ready pod/client --timeout=120s >/dev/null pod/client created master$ kubectl get pods -o wide | awk '{print $1, $6, $7}' | column -t # client 는 worker1, hello 는 worker3 NAME IP NODE client 10.244.194.68 k8s-worker1 hello-6c444d6966-grmj4 10.244.100.193 k8s-worker3 master$ kubectl exec client -- wget -qO- -T5 http://10.244.100.193 | grep title <title>Welcome to nginx!</title> master$ kubectl exec client -- wget -qO- -T5 http://hello | grep title <title>Welcome to nginx!</title>

→ worker1 의 client 파드(10.244.194.68)가 worker3 의 hello 파드(10.244.100.193)에 IP 로도, 서비스 이름 hello 로도 접속해서 nginx 첫 페이지의 제목을 받아 왔다는 뜻이에요.

client 의 IP 는 worker1 의 블록(10.244.194.64/26) 안에, hello 의 IP 는 worker3 의 블록(10.244.100.192/26) 안에 있어요. IP 로 보낸 첫 번째 요청은 그림 4 의 경로를 그대로 탑니다. 서비스 이름으로 보낸 두 번째 요청은 단계를 몇 개 더 거쳐요. hello 라는 이름은 CoreDNS 가 서비스의 ClusterIP 로 바꿔 주고, 그 ClusterIP 로 간 패킷은 kube-proxy 가 만든 iptables 규칙을 지나며 파드 IP 로 목적지가 바뀝니다(2편). CoreDNS 도 파드라서, 이 이름 풀이가 된다는 것 자체가 파드 네트워크가 동작한다는 증거예요.

그림 3 에서 남은 한 줄은 worker1 자신의 블록에 걸린 blackhole 10.244.194.64/26 이에요. blackhole 은 그 대역으로 가는 패킷을 조용히 버리는 경로 종류입니다(ip-route 매뉴얼). 그런데 client 파드는 이 블록 안의 주소를 쓰면서도 응답을 잘 받았어요. 리눅스는 목적지에 맞는 경로가 여럿이면 범위가 가장 좁은(접두사가 가장 긴) 경로를 고르기 때문에, worker1 에는 client 로 가는 더 좁은 경로가 따로 있다는 뜻이에요. 이번 출력은 tunl0 과 blackhole 이 들어간 줄만 골랐기 때문에 그 줄이 보이지 않습니다. 결국 blackhole 은 이 노드의 블록인데 아무 파드도 쓰지 않는 주소로 온 패킷을 다른 경로로 내보내지 않고 버리는 줄이에요.

5. 정책 하나로 같은 요청이 막혔다가 다시 통했다

마지막은 Calico 를 고른 첫 번째 이유를 확인하는 실험이에요. 정책이 없는 지금은 바로 위에서 본 대로 client 가 hello 에 접속됩니다. 여기에 hello 로 들어오는 트래픽을 모두 막는 정책을 넣었어요.

master$ cat /lab/deny-hello.yaml apiVersion: networking.k8s.io/v1 kind: NetworkPolicy metadata: name: deny-hello spec: podSelector: matchLabels: app: hello policyTypes: - Ingress

→ app=hello 라벨이 붙은 파드를 고르고, 정책 종류에 Ingress 를 넣었지만 허용 규칙(ingress 목록)은 하나도 적지 않았다는 뜻이에요.

쿠버네티스 문서에 따르면 Ingress 로 격리된 파드에는 그 파드가 있는 노드에서 오는 연결과, 그 파드에 적용되는 정책의 ingress 목록이 허용한 연결만 들어갈 수 있어요. 허용 목록이 비어 있으니 다른 노드에 있는 client 의 연결은 들어갈 수 없습니다. 파일은 Mac 의 공유 폴더에 두었고, 노드에서는 /lab 경로로 보여요(자세한 건 7편에서 다뤄요).

그림 5. 같은 wget 이 정책을 넣자 5초를 기다린 뒤 끊겼고, 정책을 지우자 다시 nginx 제목을 받았다

정책을 적용하고 3초 뒤 같은 요청을 보내자 wget: download timed out 이 나오고 종료 코드 1 로 끝났어요. 거절 응답도 받지 못한 채 -T5 로 정한 5초를 다 기다리고 끝난 거예요. 정책을 지우고 3초 뒤 다시 보내자 <title>Welcome to nginx!</title> 이 돌아왔습니다. 노드도 파드도 그대로인데 정책 하나를 넣고 빼는 것만으로 결과가 바뀌었어요. 이 클러스터의 네트워크 플러그인은 Calico 하나뿐이니, 정책을 실제로 집행한 것은 Calico 입니다.

⚠️ 주의: created 가 떴다고 막힌 것은 아니에요
쿠버네티스 문서는 NetworkPolicy 를 구현하는 컨트롤러가 없으면 리소스를 만들어도 아무 효과가 없다고 적고 있어요. API 서버는 정책 오브젝트를 받아 저장할 뿐이라서, networkpolicy.networking.k8s.io/deny-hello created 는 정책을 집행하지 않는 플러그인 위에서도 똑같이 나옵니다. 그래서 정책을 넣은 뒤에는 막혀야 할 요청을 실제로 보내 봐야 해요. 이때 ping 은 판단 근거로 삼지 않는 것이 좋습니다. 같은 문서에 따르면 모든 연결을 거부하는 정책도 확실히 막는 것은 TCP·UDP·SCTP 연결이고, ICMP 같은 다른 프로토콜에서는 동작이 정해져 있지 않아요. 이 실험은 wget 으로 HTTP(TCP) 요청을 보냈습니다.
✍️ 오늘의 요약
kubeadm 은 컨트롤 플레인까지만 만들고, 파드 IP 와 노드 간 경로, NetworkPolicy 집행은 직접 고른 CNI 플러그인에게 맡겨요.

강의 실습에서 NetworkPolicy 가 그대로 되고 kube-proxy 와 iptables 를 기본 그대로 볼 수 있도록 Calico 를 매니페스트로 설치했어요. NIC 가 둘인 노드라서 파드 대역은 10.244.0.0/16 으로 직접 적고, 노드 IP 는 kubelet 이 등록한 InternalIP 를 따르게 했습니다. 그 결과 worker1 의 다른 노드행 경로는 모두 eth0 의 192.168.104.x 를 거쳐 tunl0 으로 나갔고, 정책 하나로 같은 요청이 막혔다가 다시 통했어요. 파드 네트워크는 노드 네트워크 위에서 동작하기 때문에, 노드에 NIC 가 몇 개이고 각각 어디로 통하는지를 먼저 알아야 설정할 수 있습니다.
