mysql:8.4 이미지로 파드를 하나 만들었는데 2초 만에 STATUS가 Error가 되고 재시작 횟수가 1로 올랐어요. 90초가 지나자 재시작은 4번이 됐어요. 로그에는 이렇게 남아 있었어요. Database is uninitialized and password option is not specified. 이어서 MYSQL_ROOT_PASSWORD를 포함한 환경 변수 세 개 가운데 하나를 지정하라는 안내가 붙어 있었어요.

매니페스트에 env: [{name: MYSQL_ROOT_PASSWORD, value: ...}]를 넣자 2초 만에 1/1 Running이 됐고 select version()은 8.4.13을 돌려줬어요. 문제는 그다음이었어요. 같은 방식으로 비밀번호를 넣은 파드에 kubectl describe pod를 실행하자 Environment 칸에 k8spass#가 그대로 찍혔어요.

이 글은 그 비밀번호가 어디에 남는지 하나씩 찾아봐요. env value, Secret을 가리키는 secretKeyRef, Secret 전체를 넣는 envFrom, Secret 볼륨을 같은 클러스터(Lima VM 4대, kubeadm v1.37.2)에서 비교하고, 권한을 나눈 ServiceAccount로 각각 무엇을 읽을 수 있는지 확인했어요.

이 글에서 다룰 것
· 필수 환경 변수를 안 넣으면 파드는 어떻게 끝날까?
· env value로 넣은 비밀번호는 어디에 남을까?
· secretKeyRef로 바꾸면 describe와 컨테이너 안에는 무엇이 보일까?
· describe에 비밀번호가 그대로 보이는데 괜찮을까?
· Secret 매니페스트를 kubectl apply로 올리면 무엇이 더 남을까?

1. 필수 환경 변수를 안 넣으면 컨테이너는 뜨자마자 끝나고 재시작을 반복한다

환경 변수 없이 띄운 mysql:8.4 파드의 상태를 2초 간격으로 읽어 바뀔 때만 적었어요(labs/devops/k8s-study/out/77-mysql-pod.txt의 B 절, 같은 이름의 .sh).

## B. mysql:8.4, 환경 변수 없음 + 0s 0/1 ContainerCreating restarts=0 + 2s 0/1 Error restarts=1 + 4s 0/1 CrashLoopBackOff restarts=1 + 13s 0/1 Error restarts=2 + 42s 0/1 Error restarts=3 + 90s 0/1 Error restarts=4 로그(마지막 실행 또는 직전 실행): 2026-11-21 03:13:20+00:00 [ERROR] [Entrypoint]: Database is uninitialized and password option is not specified You need to specify one of the following as an environment variable: - MYSQL_ROOT_PASSWORD - MYSQL_ALLOW_EMPTY_PASSWORD - MYSQL_RANDOM_ROOT_PASSWORD

→ 이미지를 받지 못한 것도 스케줄되지 못한 것도 아니에요. 2초 만에 재시작 횟수가 1이 됐다는 것은 컨테이너가 한 번 시작해서 끝났다는 뜻이에요. 이미지의 시작 스크립트가 비밀번호 설정이 없는 것을 보고 오류를 남긴 뒤 스스로 끝났어요. 파드의 restartPolicy를 적지 않으면 기본값은 Always라서 kubelet이 같은 파드 안에서 컨테이너를 다시 띄웠고 같은 이유로 또 끝났어요.

📖 용어: CrashLoopBackOff
컨테이너가 시작했다가 끝나기를 반복할 때 kubelet이 다음 재시작까지 기다리는 상태예요. STATUS 칸에 보이는 글자이고 파드의 phase는 아니에요. 재시작 횟수가 2, 3, 4가 된 것을 본 시점이 13초, 42초, 90초로 점점 벌어진 것이 이 기다림이에요. 간격이 정해지는 방식은 81편에서 다뤄요.

STATUS와 재시작 횟수만으로는 왜 끝났는지 알 수 없어요. 원인은 컨테이너가 남긴 로그에 있었어요. 실험 스크립트는 kubectl logs로 지금 실행의 로그를 읽고, 컨테이너가 이미 끝나 읽을 것이 없으면 kubectl logs --previous로 직전 실행의 로그를 읽었어요. 재시작 횟수가 오르는 파드를 만나면 이 두 명령이 먼저예요.

같은 이미지에 MYSQL_ROOT_PASSWORD를 env value로 넣은 C 절은 +2초에 1/1 Running이었고 mysql -uroot -p... -e 'select version();'이 8.4.13을 돌려줬어요. 필수 환경 변수 하나가 Error 반복과 정상 기동을 갈랐어요.

명령형으로 뼈대를 뽑아도 env는 spec에 남는다

매니페스트를 직접 쓰지 않고 kubectl run으로 만들어도 결과는 같아요. 59편에서 뼈대를 뽑을 때 쓴 --dry-run=client -o yaml을 붙여 보면 --env로 준 비밀번호가 그대로 env value가 돼요(77-run-env-dryrun.txt, 클러스터에는 아무것도 만들지 않았어요).

## kubectl run db --image=mysql:8.4 --port=3306 --env=MYSQL_ROOT_PASSWORD='k8spass#' --dry-run=client -o yaml spec: containers: - env: - name: MYSQL_ROOT_PASSWORD value: k8spass# image: mysql:8.4

선언형으로 쓰든 명령형으로 뼈대를 뽑든 비밀번호는 Pod 객체의 spec에 들어가요. kubectl run이 붙이는 라벨과 kubectl expose가 그 라벨을 셀렉터로 가져가는 과정은 78편에서 봐요.

2. env value는 Pod spec의 한 칸이라서 파드를 읽을 수 있으면 비밀번호도 읽힌다

busybox 파드 두 개에 같은 비밀번호를 넣었어요. env-plain은 env value로, env-secret은 Secret mysql-root를 가리키는 secretKeyRef로 넣고 describe, spec, 컨테이너 안을 비교했어요(labs/devops/k8s-study/out/77-env-vs-secret.txt, 같은 이름의 .sh).

## env-plain kubectl describe (Environment): Environment: MYSQL_ROOT_PASSWORD: k8spass# kubectl get -o jsonpath env: [{"name":"MYSQL_ROOT_PASSWORD","value":"k8spass#"}] 컨테이너 안 env: MYSQL_ROOT_PASSWORD=k8spass# ## env-secret kubectl describe (Environment): Environment: MYSQL_ROOT_PASSWORD: <set to the key 'password' in secret 'mysql-root'> Optional: false kubectl get -o jsonpath env: [{"name":"MYSQL_ROOT_PASSWORD","valueFrom":{"secretKeyRef":{"key":"password","name":"mysql-root"}}}] 컨테이너 안 env: MYSQL_ROOT_PASSWORD=k8spass#

→ env value로 넣은 비밀번호는 describe에도, API가 돌려준 spec에도, 컨테이너 안에도 평문이었어요. secretKeyRef로 넣은 쪽은 describe와 spec에 "어느 Secret의 어느 키"라는 참조만 있었고 컨테이너 안에서만 평문이었어요.

describe가 비밀번호를 찾아내 보여 준 것이 아니에요. v1.37.2 kubectl의 describe.go는 env 항목에 valueFrom이 없으면 value 문자열을 그대로 찍어요(77-k8s-v1.37.2-describe-kubelet-excerpts.txt).

for _, e := range container.Env { if e.ValueFrom == nil { ... w.Write(LEVEL_3, "%s:\t%s\n", e.Name, s) // value 를 그대로 continue } switch { case e.ValueFrom.SecretKeyRef != nil: w.Write(LEVEL_3, "%s:\t<set to the key '%s' in secret '%s'>\tOptional: %t\n", ...)

→ describe는 Pod 객체를 읽기 좋게 옮겨 적는 도구예요. env value는 Pod spec의 평범한 문자열 칸이니 Pod를 GET할 수 있는 사람과 프로그램은 누구나 그 값을 받아요. secretKeyRef는 키와 Secret 이름만 찍고 Secret을 따로 읽어 오지 않아요.

kubectl apply로 만들었다면 주석에도 남는다

비교를 넓혀 네 가지 방식으로 파드를 만든 실험(77-secret-visibility.txt, 네임스페이스 blog-77)에서는 env value 파드의 주석도 봤어요. 이 파드는 kubectl apply로 만들었고 kubectl.kubernetes.io/last-applied-configuration 주석에 비밀번호 문자열이 1번 나왔어요.

📖 용어: last-applied-configuration 주석
kubectl apply(클라이언트 쪽 apply)가 객체에 붙이는 주석이에요. 선언형 관리 문서는 "The annotation contains the contents of the object configuration file that was used to create the object"라고 해요. 다음 apply 때 무엇을 지웠는지 계산하려고 매니페스트 내용을 통째로 담아 두는 칸이라서 매니페스트에 적은 값이 그대로 들어가요.
⚠️ env value의 비밀번호는 적어도 세 곳에 평문으로 남아요
• Pod spec: kubectl get pod -o yaml, describe, 그리고 이 객체를 저장한 etcd(22편)
• kubectl apply로 만들었다면 last-applied-configuration 주석
• 컨테이너 안의 환경 변수
Deployment로 만들었다면 Deployment와 ReplicaSet의 파드 템플릿에도 같은 값이 들어가요. 매니페스트 파일을 저장소에 커밋했다면 그 파일도 한 곳이에요.

3. secretKeyRef로 바꾸면 spec에는 참조만 남고 값은 kubelet이 컨테이너에 넣는다

📖 용어: Secret과 secretKeyRef
Secret은 비밀번호 같은 값을 키와 값의 쌍으로 담는 API 객체예요. Pod와 따로 있어서 RBAC 권한도 따로 줄 수 있어요. secretKeyRef는 환경 변수 하나의 값을 "이 Secret의 이 키"로 가리키는 필드예요. Pod spec에는 이 참조만 저장돼요.

그렇다면 값은 누가 넣을까요? 컨테이너를 만드는 kubelet이에요. v1.37.2 kubelet_pods.go의 makeEnvironmentVariables는 env 항목이 secretKeyRef면 kl.secretManager.GetSecret(pod.Namespace, name)으로 Secret을 가져와 secret.Data[key]를 환경 변수의 값으로 써요. Pod 객체에는 끝까지 참조만 있고 평문은 노드의 kubelet을 거쳐 컨테이너에 들어가요.

env 말고도 Secret을 넘기는 방법이 둘 더 있어요. Secret의 모든 키를 한꺼번에 환경 변수로 넣는 envFrom과 Secret을 파일로 마운트하는 secret 볼륨이에요. 네 가지를 같은 Secret db-cred로 만들고 describe부터 봤어요.

그림 1. describe에서 평문이 보인 것은 env value 파드 하나였어요.

📖 용어: envFrom
Secret이나 ConfigMap의 모든 키를 환경 변수로 한꺼번에 넣는 필드예요. 키 이름이 그대로 변수 이름이 되고 prefix를 주면 앞에 붙어요. 이번 실험에서 키 password에 prefix DB_를 줬더니 변수 이름이 DB_password가 됐어요.

컨테이너 안에서는 결과가 달랐어요. 같은 실험의 3절이에요.

## 3. 컨테이너 안에서 (kubectl exec) env-value: DB_PASSWORD=k8spass# env-ref: DB_PASSWORD=k8spass# env-from: DB_password=k8spass# vol: env 에 DB_ 줄 수=0 cat /etc/db/password=k8spass# lrwxrwxrwx 1 root root 15 Nov 21 10:10 password -> ..data/password tmpfs on /etc/db type tmpfs (ro,relatime,size=3896024k,inode64,noswap)

→ 세 env 방식은 모두 컨테이너의 환경 변수에 평문이 있었어요. 볼륨 방식은 환경 변수에는 없었고 /etc/db/password 파일에 평문이 있었어요. 그 파일은 tmpfs(메모리 위의 파일 시스템)에 읽기 전용으로 마운트됐고 password는 ..data/password를 가리키는 심볼릭 링크였어요. Secret 문서에 따르면 kubelet은 볼륨에 쓰인 Secret의 키와 값을 캐시에 두고 Secret이 바뀌면 볼륨의 데이터를 갱신해요. 이번 실험에서 Secret을 바꿔 보지는 않았어요.

그림 2. 빨간 칸이 평문이 보이는 자리예요. 오른쪽 열은 네 방식 모두 빨간색이에요.

💡 실무에서는 Pod 객체에 평문을 남기지 않는 것부터 해요
• 비밀번호는 env value 대신 secretKeyRef, envFrom, secret 볼륨 가운데 하나로 넣어요. 셋 다 Pod spec에는 참조만 남아요
• 어느 방식이든 컨테이너 안에서는 평문이에요. 컨테이너에 들어갈 수 있는 사람에게서 값을 숨기는 장치가 아니에요
• 환경 변수는 env 한 번에 다 보이고 볼륨은 그 파일을 읽어야 보여요. 앱이 어느 쪽에서 값을 읽는지는 이미지가 정하니 이미지 문서부터 확인해요(mysql 이미지는 이번에 환경 변수로 읽었어요)

4. describe에 비밀번호가 보이는데 괜찮나: pods 권한과 secrets 권한을 나눌 때만 참조가 의미를 가진다

secretKeyRef로 바꿔도 클러스터 관리자 권한으로는 Secret을 열면 그만이에요. 참조가 실제로 무엇을 막는지는 권한이 다른 사용자로 봐야 보여요. 먼저 네임스페이스마다 자동으로 생기는 default ServiceAccount는 Secret도 Pod도 읽지 못했어요(77-env-vs-secret.txt).

can-i get secrets (default SA): no can-i get pods (default SA): no
📖 용어: ServiceAccount와 Role·RoleBinding
ServiceAccount는 파드 안의 프로그램이나 자동화 도구가 API 서버에 쓰는 계정이에요. Role은 한 네임스페이스에서 어떤 리소스에 어떤 동작(get, list, create...)을 허용할지 적은 규칙이고 RoleBinding은 그 규칙을 계정에 붙여요. pods와 secrets는 다른 리소스라서 따로 허용해요. 인가가 어디서 이뤄지는지는 32편에서 봤어요.

그다음 두 계정을 만들었어요. pod-reader에는 pods와 events의 get·list만, pod-maker에는 pods의 create·get·list와 pods/log의 get만 줬어요. 둘 다 secrets 권한은 없어요. 요청은 --as=system:serviceaccount:blog-77:pod-reader 같은 옵션으로 그 계정 이름을 달아 보냈어요.

그림 3. secrets 권한이 없어도 파드를 만들 수 있으면 비밀번호가 읽혔어요.

pod-reader부터 보면 secretKeyRef의 효과가 분명해요. env value 파드에서는 kubectl get pod -o jsonpath 한 번으로 k8spass#를 읽었어요. secretKeyRef 파드의 describe에서는 <set to the key 'password' in secret 'db-cred'>만 봤고 Secret을 직접 열려고 하자 거절됐어요.

Error from server (Forbidden): secrets "db-cred" is forbidden: User "system:serviceaccount:blog-77:pod-reader" cannot get resource "secrets" in API group "" in the namespace "blog-77"

→ 이 계정은 Pod는 읽을 수 있지만 Secret은 읽을 수 없다는 뜻이에요. 비밀번호를 env value로 넣으면 이 구분이 사라지고 secretKeyRef로 넣으면 남아요. 파드 목록만 읽으면 되는 대시보드나 모니터링 도구의 계정에 줄 권한이 이 정도예요.

pod-maker는 결과가 달랐어요. can-i get secrets는 no였는데 db-cred를 secretKeyRef로 가리키고 그 값을 출력만 하는 파드 peek을 만들 수 있었어요. 파드가 Succeeded로 끝난 뒤 pod-maker 권한으로 로그를 읽자 DB_PASSWORD=k8spass#가 나왔어요. Secret을 읽은 것은 pod-maker가 아니라 peek을 띄운 노드의 kubelet이었고 pod-maker는 그 결과를 로그로 받았어요.

Secret 문서의 주의 문구가 이 경우를 그대로 적고 있어요. "anyone who is authorized to create a Pod in a namespace can use that access to read any Secret in that namespace; this includes indirect access such as the ability to create a Deployment." 네임스페이스에 파드를 만들 수 있는 사람은 그 네임스페이스의 Secret을 모두 읽을 수 있고 Deployment를 만드는 권한 같은 간접 권한도 포함된다는 뜻이에요. 22편에서 이 문구를 etcd 저장 방식과 함께 봤어요.

그림 4. 아래 세 줄은 모두 평문까지 닿아요. 비밀번호를 지키는 경계는 첫 줄과 나머지 사이에 있어요.

그림의 셋째 줄은 관리자 권한으로 확인했어요. kubectl exec env-secret -- env에 평문이 나왔고 pod-reader는 can-i create pods/exec가 no였어요. exec 권한이 있는 계정으로 직접 해 보지는 않았지만 exec는 컨테이너 안에서 명령을 실행하는 권한이니 컨테이너 안의 평문이 그대로 보여요.

그러니 질문에 답하면 이래요. describe에 비밀번호가 보이는 것은 env value를 썼기 때문이고 괜찮지 않아요. 파드를 읽을 수 있는 모든 계정이 비밀번호를 읽게 되기 때문이에요. secretKeyRef로 바꾸면 pods만 읽는 계정에게서는 가려져요. 하지만 파드를 만들거나 exec할 수 있는 계정에게서는 가려지지 않아요.

💡 실무에서는 권한을 이렇게 나눠요
• 파드 목록만 필요한 도구에는 pods의 get·list만 주고 secrets는 주지 않아요. 이 경계가 의미를 가지려면 비밀번호가 env value에 없어야 해요
• pods/exec와 pods create(Deployment 같은 워크로드 생성 포함)는 secrets get과 같은 무게로 봐요. 이번 실험에서 secrets 권한이 없는 계정이 파드 하나로 비밀번호를 읽었어요
• 비밀번호를 쓰는 앱과 그렇지 않은 앱은 네임스페이스를 나누는 것이 가장 단순한 경계예요. 파드 생성 권한이 닿는 범위가 네임스페이스이기 때문이에요

5. Secret 자체는 base64일 뿐이고 apply로 만들면 주석에 평문이 남는다

참조가 가리키는 Secret 객체도 봤어요. describe는 값을 숨기고 바이트 수만 보여 줬지만 get -o jsonpath로 꺼낸 값은 base64를 한 번 풀면 그대로 비밀번호였어요(77-secret-visibility.txt 4절, 77-env-vs-secret.txt).

## 4. Secret 객체 자체 Data ==== password: 8 bytes get -o jsonpath data.password = azhzcGFzcyM= → base64 -d → k8spass#

→ describe.go의 describeSecret은 "%s:\t%d bytes\n"로 길이만 찍어요. 숨긴 것은 describe라는 출력 형식이지 API가 아니에요. secrets get 권한이 있으면 값을 받고 base64는 누구나 되돌릴 수 있어요. 저장 암호화를 켜지 않은 etcd에는 base64도 아닌 원래 글자로 저장된다는 것과 암호화를 켜는 방법은 22편에서 봤어요.

마지막으로 Secret을 만드는 방법을 바꿔 봤어요. 같은 비밀번호로 kubectl create secret, stringData를 적은 매니페스트의 kubectl apply, 같은 매니페스트의 kubectl apply --server-side를 썼어요(77-secret-apply-annotation.txt, 같은 이름의 .sh).

SECRET last-applied 주석에 평문 횟수 get -o yaml 전체에 평문 횟수 managedFields 작성자(동작) s-create 0 0 kubectl-create(Update) s-apply 1 1 kubectl-client-side-apply(Update) s-ssa 0 0 kubectl(Apply) s-ssa 의 managedFields 가 기록한 칸: {"f:stringData":{"f:password":{}}} kubectl describe secret s-apply 의 Annotations 줄: Annotations: <none>

→ 클라이언트 쪽 apply로 만든 s-apply만 get -o yaml에 비밀번호 평문이 1번 나왔어요. 2절에서 본 last-applied-configuration 주석에 stringData가 그대로 들어갔기 때문이에요(77-secret-visibility.txt 4절에서 같은 방식으로 만든 db-cred-applied의 주석 원문은 {"apiVersion":"v1","kind":"Secret",...,"stringData":{"password":"k8spass#"}}였어요). data의 base64를 풀 필요도 없이 평문이 객체에 붙어 있는 셈이에요. 그런데 describe의 Annotations는 <none>이었어요. describe.go가 이 주석을 skipAnnotations로 빼고 찍기 때문이에요. describe만 봐서는 이 평문을 알아챌 수 없어요.

📖 용어: 서버 사이드 apply와 managedFields
kubectl apply --server-side는 무엇을 지울지 계산하는 일을 API 서버에 맡기는 apply예요. 지난번에 적은 내용을 주석에 담는 대신 metadata.managedFields에 "누가 어느 칸을 관리하는지"를 칸 이름으로만 기록해요. 이번 s-ssa에서도 f:stringData, f:password라는 이름만 남았어요.
⚠️ Secret 매니페스트를 kubectl apply로 올리기 전에 확인할 것
• 클라이언트 쪽 apply는 매니페스트 전체를 last-applied-configuration 주석에 담아요. stringData로 적었다면 평문이, data로 적었다면 base64가 객체에 한 번 더 남아요
• describe는 이 주석을 보여 주지 않아요. 확인은 kubectl get secret 이름 -o yaml로 해요
• 이번 실험에서는 kubectl create secret과 kubectl apply --server-side로 만든 Secret에 평문이 0번이었어요
• 매니페스트 파일 자체도 비밀번호를 담고 있어요. 저장소에 커밋하기 전에 그 파일을 누가 읽을 수 있는지부터 봐요

✍️ 오늘의 요약

필수 환경 변수 없이 띄운 mysql:8.4는 2초 만에 Error로 끝나고 90초 동안 4번 재시작했어요. 원인은 컨테이너의 로그에 있었어요. MYSQL_ROOT_PASSWORD를 env value로 넣자 정상으로 떴지만 그 값은 Pod spec의 문자열 칸이라서 describe, get -o yaml, last-applied 주석에 평문으로 남았어요.

secretKeyRef, envFrom, secret 볼륨은 spec에 참조만 남기고 값은 kubelet이 컨테이너를 만들 때 Secret에서 채워요. 그래서 pods만 읽는 계정은 비밀번호를 못 봤고 Secret을 열면 Forbidden을 받았어요. 반면 secrets 권한이 없어도 파드를 만들 수 있는 계정은 Secret을 넣은 파드의 로그로 비밀번호를 읽었어요. Secret을 클라이언트 쪽 apply로 만들면 stringData가 주석에 평문으로 붙고 describe는 그 주석을 보여 주지 않았어요.

Secret과 secretKeyRef가 지키는 것은 "Pod를 읽을 수 있는 사람"과 "비밀번호를 읽을 수 있는 사람"의 경계예요. 그 경계는 비밀번호가 Pod 객체에 평문으로 없고 파드 생성·exec 권한을 Secret 읽기만큼 아껴서 줄 때만 유지돼요.
