우리 클러스터의 노드 네 대에서 docker, dockerd, cri-dockerd를 찾아보면 네 대 모두 "(없음)"이 나와요. /var/run/docker.sock도 없고 docker 서비스는 inactive예요. kubelet 설정의 containerRuntimeEndpoint는 containerd 소켓을 가리키고 API 서버가 아는 노드 런타임도 네 대 모두 containerd://2.4.1이에요. 노드 어디에도 Docker라는 이름이 붙은 프로그램이 없어요.

44편에서 본 노드당 파드 110개 중 사용자 파드 100개는 2016년에 kubelet과 docker 데몬의 CPU를 함께 재서 정한 값이었어요. 그 측정에 쓴 노드에는 docker 데몬이 있었고 kubelet은 그 데몬을 직접 불렀어요. 몇 년 사이에 kubelet과 런타임을 잇는 방식이 통째로 바뀐 거예요. 이번에는 쿠버네티스가 왜 kubelet에서 dockershim을 뺐는지 살펴봐요.

26편에서는 "도커 지원이 빠졌다는데 도커로 빌드한 이미지는 어떻게 도나"에 답했어요. 이미지 형식은 OCI 표준이라 어느 런타임에서나 그대로 읽혀요. 이번에는 그 앞의 질문을 따라가요. 쿠버네티스는 왜 kubelet 안에 Docker 전용 코드를 두었고 왜 1.24에서 지웠을까요? 근거는 CRI 설계 문서와 KEP, PR과 이슈 원문이고 마지막에는 우리 노드에 docker.sock을 기대하는 파드를 띄워 무엇이 깨지는지 확인해요. 클러스터는 Lima VM 4대에 kubeadm v1.37.2, containerd 2.4.1을 올린 실습 환경이에요.

이 글에서 다룰 것
· CRI가 생기기 전 kubelet은 런타임을 어떻게 불렀고 무엇이 곤란했을까?
· CRI를 만들었는데 왜 kubelet 안에 dockershim이 5년 넘게 남았을까?
· kubelet 안에 남은 Docker는 어떤 비용을 만들었을까?
· 떼어 내는 길로 무엇을 검토했고 경고에서 삭제까지 왜 1년 5개월이 걸렸을까?
· 지운 뒤에 무엇이 깨졌고 지금 우리 노드에서는 어떻게 보일까?

1. CRI 전에는 런타임마다 kubelet 안에 코드가 따로 있었다

초기 쿠버네티스가 지원한 런타임은 Docker Engine 하나였어요. 2022년 1월 쿠버네티스 블로그(Kubernetes is Moving on From Dockershim)는 그 시절을 "Docker support was hardcoded into Kubernetes"라고 적었어요. Docker 지원이 쿠버네티스 코드 안에 직접 들어가 있었다는 뜻이에요. 1.3(2016-07)에서는 rkt를 두 번째 런타임으로 붙였는데(rktnetes) 방식이 같았어요. kubelet 안에 rkt 전용 패키지를 하나 더 만든 거예요.

CRI를 발표한 2016년 12월 쿠버네티스 블로그는 이 구조를 이렇게 정리해요. "both Docker and rkt were integrated directly and deeply into the kubelet source code through an internal and volatile interface." Docker와 rkt가 둘 다 kubelet 소스에 직접 깊이 통합돼 있었고 둘이 붙은 접점은 내부용이라 자주 바뀌었다는 뜻이에요. 글은 이어서 이런 통합에는 kubelet 내부를 깊이 알아야 하고 그 유지 비용을 쿠버네티스 커뮤니티가 진다고 적었어요.

CRI가 처음 들어간 v1.5.0 태그에서 kubelet 패키지의 줄 수를 세어 보면 그 모양이 숫자로 보여요(테스트 파일 제외).

# v1.5.0 pkg/kubelet 아래 런타임별 패키지 (테스트 제외 줄 수) dockertools 5,718줄 (14파일) 옛 Docker 직결 구현 (DockerManager) rkt 3,382줄 ( 9파일) rkt 직결 구현 kuberuntime 3,944줄 (13파일) CRI를 부르는 쪽 공통 매니저 dockershim 2,549줄 (15파일) CRI용 Docker 어댑터 (1.5에서는 실험) # 같은 이름의 함수가 세 벌 dockertools/docker_manager.go:2103 func (dm *DockerManager) SyncPod(...) rkt/rkt.go:1709 func (r *Runtime) SyncPod(...) kuberuntime/kuberuntime_manager.go:569 func (m *kubeGenericRuntimeManager) SyncPod(...)

→ 파드를 원하는 상태로 맞추는 SyncPod 함수가 Docker용, rkt용, 새 CRI용으로 한 벌씩 있었다는 뜻이에요.

📖 용어: SyncPod
kubelet이 파드 하나를 원하는 상태에 맞추는 함수예요. 파드 스펙과 지금 상태를 받아 무엇을 새로 띄우고 무엇을 죽일지 정한 뒤 실행해요. CRI 전에는 이 함수 전체를 런타임마다 따로 구현했어요.

이 구조가 왜 곤란했는지는 CRI 설계 문서의 Motivation 절에 셋으로 정리돼 있어요. 첫째, 파드 개념을 기본으로 갖지 않은 런타임은 파드 기능을 모두 받쳐 줄 큰 shim을 따로 짜야 했어요. 둘째, SyncPod 같은 큰 함수가 런타임끼리 코드를 나눠 쓰지 못하게 했어요. 셋째는 파드 스펙이 빠르게 바뀐다는 점이었어요. 문서는 "Any pod-level change or addition requires changing of all container runtime shims."라고 적고 init 컨테이너를 예로 들어요. 파드 기능 하나를 더할 때마다 런타임 구현을 모두 고쳐야 했다는 뜻이에요.

런타임을 kubelet 밖으로 빼자는 이야기는 그보다 한 해 앞서 나왔어요. 2015년 9월 9일에 열린 이슈 #13768의 첫 문장은 "Currently, any container runtime has to be linked into the kubelet."이에요. 어떤 런타임이든 kubelet 바이너리에 함께 들어가야 해서 새 런타임을 시험하려면 쿠버네티스 본체에 코드를 넣어야 했다는 뜻이에요. 이슈는 런타임 인터페이스를 클라이언트와 서버로 나누면 런타임을 쿠버네티스 소스 트리 밖에서 만들고 유지할 수 있다고 제안했어요.

📖 용어: 트리 안(in-tree)과 트리 밖(out-of-tree)
쿠버네티스 저장소(kubernetes/kubernetes) 안에 있는 코드를 in-tree, 다른 저장소에서 따로 릴리스하는 코드를 out-of-tree라고 불러요. in-tree 코드는 쿠버네티스 릴리스 주기와 리뷰를 따라야 하고 쿠버네티스 메인테이너가 유지해요.

1.5의 CRI는 kubelet에 SyncPod를 하나만 두고 런타임에는 샌드박스와 컨테이너를 만들고 멈추고 지우는 작은 호출만 보내는 모양으로 정해졌어요. CRI 블로그의 "Why an imperative container-centric interface?" 절에 따르면 파드 객체를 통째로 런타임에 넘기는 방식도 검토했지만 재시작 백오프 같은 파드 수준 기능을 런타임마다 다시 짜야 하고 파드 스펙이 계속 바뀌어서 고르지 않았어요. 블로그는 CRI를 "a plugin interface which enables kubelet to use a wide variety of container runtimes, without the need to recompile"이라고 소개해요. kubelet을 다시 컴파일하지 않고 여러 런타임을 바꿔 쓸 수 있게 하는 인터페이스라는 뜻이에요.

그림 1. CRI는 런타임마다 따로 있던 SyncPod를 kubelet 쪽 하나로 모으고 런타임은 소켓 건너편에서 작은 호출만 받게 했다

2. Docker Engine이 CRI를 구현하지 않아서 kubelet 안에 dockershim이 생겼다

1.5(2016-12-13)에서 CRI v1alpha1이 알파로 들어왔어요. CRI 블로그는 연결 방식을 이렇게 적어요. "Kubelet communicates with the container runtime (or a CRI shim for the runtime) over Unix sockets using the gRPC framework, where kubelet acts as a client and the CRI shim as the server." kubelet은 유닉스 소켓 위에서 gRPC 클라이언트가 되고 런타임이나 런타임 앞의 CRI shim이 서버가 된다는 뜻이에요. 왜 하필 gRPC였는지는 46편에서 따로 봐요.

문제는 그때 노드 대부분이 쓰던 Docker Engine이 CRI 서버가 아니었다는 점이에요. Docker Engine은 CRI보다 먼저 있었고 자기 API(Docker Engine API)만 열었어요. 그래서 쿠버네티스는 CRI 서버 역할을 대신 맡아 Docker API를 부르는 어댑터를 만들었어요. 이 어댑터가 dockershim이고 시작은 2016년 7월 29일에 병합된 PR #29553 "Add a docker-shim package"였어요.

📖 용어: dockershim
kubelet에서 오는 CRI 호출(RunPodSandbox, CreateContainer 등)을 받아 Docker Engine API 호출로 바꿔 주던 어댑터예요. 쿠버네티스 저장소의 pkg/kubelet/dockershim에 있었고 kubelet 바이너리 안에 함께 빌드됐어요. 1.20에서 deprecated가 되고 1.24에서 지워졌어요.

dockershim은 따로 뜨는 프로세스가 아니었어요. 2020년 초에 나온 KEP-1547에는 "the Kubelet starts running the dockershim in a separate go routine within the main kubelet process"라고 적혀 있고 이어서 dockershim을 독립 실행 파일로 돌릴 수는 없다고 해요. kubelet 프로세스 안의 고루틴 하나가 CRI gRPC 서버를 띄우고 kubelet이 그 서버에 다시 클라이언트로 붙었던 거예요. CRI 블로그도 1.5의 내장 shim을 "This allows kubelet to start the gRPC server on Docker’s behalf."라고 설명해요. dockershim이 들어 있던 마지막 마이너인 v1.23.0의 kubelet 기본값을 보면 그 모양이 그대로 남아 있어요.

// cmd/kubelet/app/options/container_runtime.go (v1.23.0) 발췌 dockerEndpoint = "unix:///var/run/docker.sock" ContainerRuntime: kubetypes.DockerContainerRuntime, // cmd/kubelet/app/options/options.go (v1.23.0) 발췌 remoteRuntimeEndpoint = "unix:///var/run/dockershim.sock" // --container-runtime-endpoint 설명 중 "When using docker as container runtime this specifies the dockershim socket location which kubelet itself creates."

→ 1.23까지 kubelet의 기본 런타임은 docker였고 CRI 엔드포인트 기본값은 kubelet이 스스로 여는 dockershim.sock이었다는 뜻이에요(container_runtime.go, options.go). 플래그 설명에 "which kubelet itself creates"가 그대로 적혀 있어요.

그 뒤 CRI는 차례로 기본이 됐어요. 1.6(2017-03)에서 Docker-CRI 연동이 베타가 되면서 기본으로 켜졌고 1.7(2017-06)에서는 --enable-cri 플래그가 사라졌어요. CHANGELOG-1.7에는 "CRI is now the default, and the only way to integrate with Kubelet for the container runtimes."라고 적혀 있어요. rkt 직결 코드는 1.10에서 deprecated가 됐고 1.11(2018-06)에서 지워졌어요(PR #61432, 14,523줄 삭제). 이때부터 kubelet 안에 남은 런타임 예외는 Docker 하나였어요.

Docker 노드에서 컨테이너 하나가 뜨기까지 거치는 단계도 길었어요. Docker 1.11(2016-04-13)부터 Docker Engine 자체가 containerd와 runC 위에서 돌았어요. Docker 블로그는 "Docker Engine is now built on containerd"라고 발표했어요. 그러니 1.23까지의 Docker 노드는 kubelet 안의 dockershim이 docker.sock으로 dockerd를 부르고 dockerd가 다시 containerd를 부르는 구조였어요. 반대로 containerd는 CRI를 직접 받는 쪽으로 움직였어요. 2018년 5월 쿠버네티스 블로그에 따르면 containerd 1.0 시절에는 cri-containerd라는 데몬이 kubelet과 containerd 사이에 있었고 dockershim과 비교해 "eliminated one extra hop"이었어요. containerd 1.1에서는 그 데몬이 containerd 안의 CRI 플러그인이 되면서 "eliminates another grpc hop"이 됐어요. 우리 노드가 이 마지막 구조예요(26편).

그림 2. Docker 노드에서는 kubelet 안의 dockershim과 dockerd를 거쳐서야 containerd에 닿았다

단계 수 차이는 자원 사용량에도 나타났어요. 같은 2018년 글은 노드에 파드 105개를 띄운 안정 상태에서 containerd 1.1(CRI 플러그인)과 Docker 18.03 CE + dockershim을 비교했어요. containerd 쪽이 kubelet CPU 사용량은 30.89%, 컨테이너 런타임 CPU는 68.13%, kubelet 메모리(RSS)는 11.30%, 런타임 메모리(RSS)는 12.78% 낮았다고 해요. 우리 클러스터에서 dockershim과 containerd를 직접 비교해 재지는 않았어요.

3. kubelet 안에 남은 Docker가 쌓은 비용

dockershim은 처음부터 임시 해법이었어요. Dockershim: The Historical Context(2022-05)는 "this little software shim was never intended to be a permanent solution"이라고 적었어요. 그런데 이 임시 코드가 2016년부터 2022년까지 남으면서 비용이 쌓였어요. 제거를 결정한 KEP-2221과 그 전의 KEP-1547, PR 본문이 꼽은 이유를 묶으면 넷이에요.

kubelet의 수명과 Docker가 묶였다

KEP-2221의 Motivation 첫 문장은 "The design of CRI is to be able to run a CRI implementation as a separate binary."예요. CRI는 런타임 쪽을 별도 실행 파일로 돌리게 설계했다는 뜻이에요. 그런데 Docker용 CRI(dockershim)만 kubelet 코드의 일부로 kubelet과 함께 떴고 KEP는 이것을 "tightly coupled with kubelet's lifecycle"이라고 불렀어요. KEP는 이 결합 때문에 kubelet이 특정 런타임에 의존하게 됐고 runc CVE 같은 런타임 쪽 심각한 문제가 생기면 sig-node 개발자뿐 아니라 클러스터 관리자도 부담을 진다고 적었어요.

Docker 라이브러리가 kubelet을 무겁게 했다

KEP-1547은 docker/docker 클라이언트 라이브러리를 "a particularly painful dependency"라고 불렀어요. 이 라이브러리가 끌고 오는 오픈소스 의존성이 많아 따라가기 어렵고 그 의존성이 "bloat the Kubelet binary", 즉 kubelet 바이너리를 부풀린다고 해요. deprecation을 시작한 PR #94624(dims, 2020-11 병합)의 본문 첫 줄도 "dockershim has been part of kubelet for far too long."이에요. 이어서 moby/moby에서 많은 코드를 vendor로 들여와야 했다고 적었어요. 실제로 1년 뒤 dockershim을 지운 PR #97252는 372개 파일에서 53,713줄을 지웠는데 그중 27,391줄(210파일)이 vendor/github.com/docker, 17,166줄(85파일)이 pkg/kubelet/dockershim이었어요.

Docker에만 있는 분기가 생겼다

KEP-2221의 Pros에는 dockershim이 여러 이유로 "inconsistent integrations"를 누린다는 문장이 있고 예로 legacyLogProvider를 들어요. v1.23.0 소스의 주석은 "LegacyLogProvider gives the ability to use unsupported docker log drivers (e.g. journald)"이에요(kuberuntime_manager.go). Docker가 json-file이 아닌 로그 드라이버를 쓸 때만 kubelet이 다른 길로 로그를 읽었다는 뜻이에요. kubelet.go에도 런타임 종류가 docker일 때만 runDockershim을 부르는 분기가 있었어요. 같은 kubelet인데 Docker일 때만 다르게 움직이는 코드가 곳곳에 있었던 거예요.

새 기능이 dockershim에서 막혔다

2020년 12월 Dockershim Deprecation FAQ는 "features that were largely incompatible with the dockershim, such as cgroups v2 and user namespaces are being implemented in these newer CRI runtimes."라고 적었어요. cgroup v2나 user namespaces 같은 기능은 dockershim과 거의 맞지 않아서 새 CRI 런타임 쪽에서 만들어지고 있다는 뜻이에요. 쿠버네티스의 cgroup v2 지원을 정한 KEP-2254는 Non-Goals에 Dockershim을 넣고 본문에 "The dockershim implementation embedded in the Kubelet won't be supported on cgroup v2."라고 적었어요. 흥미로운 점은 Docker Engine 자체는 20.10.0(2020-12-08)에서 cgroup2를 지원했다는 거예요(Docker Engine 20.10 릴리스 노트). 같은 KEP에 따르면 containerd는 1.4.0부터 cgroup v2를 지원했어요. 막힌 곳은 Docker Engine이 아니라 kubelet 안의 dockershim이었어요. 우리 노드 네 대의 /sys/fs/cgroup은 모두 cgroup2fs예요. dockershim이 지원하지 않겠다고 한 바로 그 환경이에요.

KEP 승인자 dchen1107이 원안 리뷰에서 덧붙여 KEP-2221 Pros에 들어간 이유도 있어요. 내장 shim을 그대로 물려받는 편이 편해서 "there is less incentive to move to new container runtimes"라는 내용이에요. kubelet에 Docker가 들어 있는 한 사용자가 containerd나 CRI-O로 옮길 동기가 약했다는 뜻이에요. dims는 PR #97252 본문에 한 줄로 정리했어요. "dockershim has been a drag on sig-node and a huge technical debt." kubelet 안의 Docker 예외는 kubelet의 수명, 의존성, 코드 분기, 새 기능 모두에 걸려 있었어요.

⚠️ 주의: "쿠버네티스가 Docker를 버렸다"의 정확한 범위
• 지운 것은 kubelet 안의 Docker 전용 어댑터(dockershim)예요. Docker로 빌드한 이미지는 어느 CRI 런타임에서나 돌아요(26편)
• Docker Engine을 노드 런타임으로 계속 쓰려면 Mirantis와 Docker가 밖으로 옮겨 유지하는 cri-dockerd를 kubelet과 Docker Engine 사이에 둬요
• 깨지는 것은 노드의 docker 데몬과 docker.sock을 직접 부르던 스크립트, 에이전트, 설정이에요(5절)

4. 떼어 내는 길은 여럿이었고 경고에서 삭제까지 1년 5개월이 걸렸다

KEP-1547은 길을 둘로 정리했어요. "either Docker must begin implementing the CRI natively or the dockershim must be moved out-of-tree into a standalone component." Docker가 CRI를 직접 구현하거나 dockershim을 트리 밖의 독립 구성 요소로 옮기는 것이에요. 실제 논의에서는 여기에 "누가 유지하나"와 "언제 어떻게 지우나"가 더해졌어요. KEP-2221 자체의 Alternatives 절은 "None."이라서 아래 표는 KEP-1547, KEP 리뷰 댓글, PR 본문, 일정 변경 기록에서 모은 거예요.

검토한 길근거 원문결과
Docker Engine이 CRI를 직접 구현KEP-1547이 꼽은 두 길 중 하나일어나지 않았어요. Docker 쪽이 엔진에 CRI를 넣겠다고 한 원문은 찾지 못했어요

dims가 PR #94624에 적은 설명이 이 결정의 방향을 보여 줘요. "The correct split/architecture is to follow the same design as with containerd and cri-o namely a separate process that kubelet talks to via grpc that in turn talks to a runtime." kubelet이 gRPC로 부르는 별도 프로세스가 런타임을 부르는 구조, 즉 containerd·CRI-O와 같은 구조로 나누는 게 맞다는 뜻이에요. 다만 그 별도 프로세스를 쿠버네티스가 유지하지는 않겠다는 거였어요.

기본 빌드에서만 빼자는 원안에 문제를 제기한 liggitt의 댓글은 폐기 정책을 근거로 했어요. 폐기 정책은 deprecated 기간이 끝날 때까지 사용자가 쿠버네티스를 쓰는 방식을 바꾸지 않아도 되게 하려는 것인데 기본 빌드에서 빼 버리면 사용자가 kubelet을 직접 빌드해야 한다는 지적이었어요. 최종 KEP에는 "Deprecation should be for at least a year."라고 적혔고 deprecation이 2020년 12월에 발표됐으니 빌드에서 빼는 릴리스에 코드도 함께 지울 수 있다고 정리됐어요.

📖 용어: deprecated와 폐기 정책(deprecation policy)
기능을 바로 지우지 않고 "앞으로 지운다"고 먼저 알리는 단계가 deprecated예요. 쿠버네티스는 폐기 정책에 따라 이 기간에는 기능이 그대로 동작하게 두고 사용자가 옮겨 갈 시간을 줘요. dockershim은 1.20부터 kubelet이 시작할 때 경고를 남기기만 하고 그대로 동작했어요.

5. 지운 뒤에 깨진 것은 이미지가 아니라 노드의 docker에 기대던 도구였다

공식 문서 Check whether dockershim removal affects you는 이미지를 Docker로 빌드하는 것은 런타임 의존이 아니라고 먼저 짚어요. Docker로 이미지를 만드는 일은 그대로 되고 노드에서 docker 데몬을 부르던 일만 깨진다는 뜻이에요. 문서는 그런 의존을 찾을 곳을 이렇게 꼽아요.

· 특권 파드 안에서 docker ps 같은 Docker 명령을 실행하거나 docker 서비스를 재시작하거나 /etc/docker/daemon.json을 고치는 경우
· /etc/docker/daemon.json에 적어 둔 사설 레지스트리·이미지 미러 설정(다른 런타임 설정으로 옮겨야 해요)
· 노드에 SSH로 들어가 하는 문제 해결, 노드 시작 스크립트, 노드에 직접 설치한 모니터링·보안 에이전트
· 위 일을 하는 서드파티 도구
· Docker 고유의 메트릭이나 로그 문구에 맞춰 둔 경보 같은 간접 의존

같은 문서는 containerd로 바꾸면 컨테이너가 Docker에 보이지 않으니 docker ps, docker inspect, docker exec를 쓸 수 없다고 해요. docker로 빌드하거나 받은 이미지도 런타임에 보이지 않아서 레지스트리에 올려야 쿠버네티스가 쓸 수 있어요. 알려진 문제로는 kubelet /metrics/cadvisor의 컨테이너 이름 형식이 Docker 노드의 k8s_<container-name>_<pod-name>_...에서 containerd 노드의 <container-id>로 바뀌고 container_fs_usage_bytes 같은 파일시스템 메트릭 일부가 빠진다는 점이 적혀 있어요.

네트워크를 맡는 주체도 바뀌었어요. dockershim과 함께 kubelet의 --network-plugin, --cni-conf-dir, --cni-bin-dir 같은 플래그가 지워졌어요(PR #106907). 파드에 CNI를 부르는 일은 런타임 몫이 됐고 우리 노드에서도 CNI 경로는 kubelet이 아니라 containerd 설정에 있어요(6절). 34편에서 본 RunPodSandbox 안의 CNI ADD가 그 결과예요.

프로젝트도 대가를 치렀어요. 1.20에서 deprecation을 알리자 "Docker로 만든 이미지가 이제 안 도나" 하는 혼란이 퍼졌고 Historical Context 글은 "This was our fault"라고 적었어요. 혼란을 줄이려고 2020년 12월 2일에 Don't Panic: Kubernetes and Docker와 FAQ를 냈어요. Don't Panic 글은 "Docker isn’t compliant with CRI"라고 적고 Docker가 CRI를 따랐다면 shim이 필요 없었고 이런 일도 없었을 거라고 이어 가요. 이 일의 요점이 이 두 문장에 있어요.

트리 밖으로 나간 shim은 일정이 늦었어요. PR #97252가 병합된 2021-12-08에는 cri-dockerd 릴리스가 없었고 첫 릴리스 v0.2.0은 2022-01-04에 나왔어요. 1.26(2022-12-09)이 CRI v1alpha2 지원을 끊은 뒤 cri-dockerd가 v1을 지원한 v0.3.0은 11일 뒤인 2022-12-20에 나왔어요. 그 무렵 제거 피드백 이슈(#106917)에는 "the skeptics were right"라는 댓글이 달렸어요. 회의적이던 쪽이 옳았고 지원되는 런타임으로 옮기는 편이 낫겠다는 말이에요. KEP-2221의 Cons에도 이미 "Deployment pain with a new binary in addition to kubelet."이 적혀 있었어요. cri-dockerd는 지금도 릴리스를 이어 가서 2026-10-30에 v0.4.10이 나왔어요.

📖 용어: cri-dockerd
dockershim 코드를 쿠버네티스 밖으로 옮겨 독립 데몬으로 만든 CRI 서버예요. kubelet은 unix:///var/run/cri-dockerd.sock 같은 소켓으로 cri-dockerd에 CRI 호출을 보내고 cri-dockerd가 Docker Engine API를 불러요. Mirantis 저장소에서 따로 릴리스해요.
💡 실무에서는: 업그레이드 전에 노드의 Docker 의존을 이렇게 찾아요
• 공식 문서 Migrating telemetry and security agents from dockershim에 docker.sock을 hostPath로 마운트한 파드를 찾는 kubectl get pods --all-namespaces -o=jsonpath=... 명령이 있어요. 우리 클러스터에서는 범위를 넓혀 docker.sock, dockershim, cri-dockerd, containerd 소켓이나 /var/run 통째를 마운트한 파드를 찾았고 전체 32개 중 0개였어요(hostPath를 쓰는 파드는 12개)
• 노드에서 컨테이너를 볼 때는 docker ps 대신 crictl ps(CRI로 묻기)나 nerdctl -n k8s.io ps(containerd에 직접 묻기)를 써요
• daemon.json의 레지스트리 미러 같은 설정은 쓰는 런타임의 설정으로 옮기고 노드 스크립트와 에이전트 문서에서 docker 명령을 찾아봐요
• Docker Engine을 꼭 노드 런타임으로 써야 한다면 cri-dockerd를 설치하고 kubelet의 containerRuntimeEndpoint를 그 소켓으로 맞춰요

6. 우리 노드에서 확인한 것: Docker가 없는 노드와 docker.sock을 찾는 파드

노드 네 대를 조회만 하는 스크립트로 런타임 상태를 모았어요(2026-11-14 21:25). 아래는 API 서버가 아는 노드별 런타임과 마스터의 결과예요.

그림 3. 마스터에는 docker 계열 실행 파일과 소켓이 하나도 없고 kubelet은 containerd 소켓만 본다

워커 세 대도 같았어요. 다른 곳은 엔드포인트 경로의 앞부분뿐이었어요. 마스터는 unix:///run/containerd/containerd.sock이고 워커는 unix:///var/run/containerd/containerd.sock이에요. 마스터는 실습 저장소의 kubeadm init 설정에 criSocket을 직접 적었고 워커는 kubeadm 1.24부터 기본값이 된 containerd 소켓(CHANGELOG-1.24의 "default the kubeadm configuration to the containerd socket")을 받았어요. /var/run은 /run을 가리키는 심볼릭 링크라서 둘은 같은 소켓이에요(27편). kubelet 실행 인자에도 런타임 관련 플래그가 없었어요. 1.27에서 엔드포인트 설정이 플래그에서 kubelet 설정 파일로 옮겨진 것과 맞는 모습이에요.

그림 4. 1.24·1.27에서 지운 플래그는 kubelet v1.37.2에 없고 docker라는 낱말은 도움말 한 줄에만 남았다

--container-runtime은 1.27에서 지워졌고 --docker-endpoint·--network-plugin·--cni-bin-dir은 1.24에서 지워졌어요. 그래서 kubelet v1.37.2에는 넷 다 없어요. --container-runtime-endpoint는 남아 있지만 DEPRECATED 표시가 붙어 설정 파일로 옮기라고 하고 기본값은 containerd 소켓이에요. docker라는 낱말은 --serialize-image-pulls 도움말 한 줄에만 남아 있었어요. Docker 1.9 미만이나 Aufs 저장소를 쓰는 노드라면 기본값을 바꾸지 말라는 옛 안내예요.

kubelet이 부르는 CRI 서버는 containerd 안의 플러그인이에요. worker1에서 본 containerd의 플러그인 목록과 네임스페이스는 이래요.

# 45-runtime-no-docker.txt 4절 발췌 (worker1, containerd v2.4.1) --- ctr plugins ls 중 cri TYPE ID PLATFORMS STATUS io.containerd.cri.v1 images - ok io.containerd.cri.v1 runtime linux/arm64/v8 ok io.containerd.grpc.v1 cri - ok --- containerd namespaces NAME LABELS default k8s.io --- containerd config dump 중 CNI [plugins.'io.containerd.cri.v1.runtime'.cni] bin_dirs = ['/opt/cni/bin', '/usr/local/libexec/cni'] conf_dir = '/etc/cni/net.d' # 6절: worker1 에서 docker CLI 없이 보기 crictl pods (파드 샌드박스 수) = 14, crictl ps (앱 컨테이너 수) = 9 nerdctl -n k8s.io ps (pause 포함 전체) = 18 nerdctl -n default ps = 0

→ kubelet이 부르는 gRPC 서비스(io.containerd.grpc.v1 cri)가 containerd 프로세스 안의 플러그인이고 CNI 경로(bin_dirs, conf_dir)도 이 플러그인 설정에 있다는 뜻이에요. v1.23 kubelet의 기본값에 있던 /opt/cni/bin과 /etc/cni/net.d가 지금은 containerd 설정에 있어요. 쿠버네티스가 만든 컨테이너는 containerd의 k8s.io 네임스페이스에만 있었어요. crictl ps가 앱 컨테이너 9개를 보여 줄 때 nerdctl은 같은 네임스페이스의 pause 컨테이너까지 합쳐 18개를 보여 줬어요.

docker.sock을 마운트하는 파드를 Docker 없는 노드에 띄우면

문서가 첫 번째로 꼽은 의존은 노드의 docker.sock을 hostPath로 마운트하는 파드예요. 이런 파드가 Docker가 없는 우리 노드에서 어떻게 되는지 worker2에 두 개를 띄워 봤어요. sock-typed는 hostPath에 type: Socket을 줬고 sock-untyped는 type을 비웠어요. 실험은 전용 네임스페이스에서 하고 바로 지웠어요.

📖 용어: hostPath의 type
노드의 경로를 파드에 붙일 때 그 경로가 무엇이어야 하는지 정하는 칸이에요. 볼륨 문서에 따르면 Socket은 "A UNIX socket must exist at the given path"이고 빈 값(기본)은 하위 호환을 위한 값이라 마운트 전에 아무것도 확인하지 않아요.
그림 5. type: Socket을 준 파드는 FailedMount로 멈췄고 type을 비운 파드는 빈 디렉터리를 받은 채 Running이 됐다

· sock-typed는 12초 뒤에도 ContainerCreating이었고 이벤트에 FailedMount가 찍혔어요. 처음 이유는 경로가 없다는 것이었고 다음 이유는 "it's a Directory"였어요. 그사이 sock-untyped 때문에 같은 경로에 디렉터리가 생겼기 때문이에요.
· sock-untyped는 Running이 됐어요. 그런데 컨테이너 안의 /var/run/docker.sock은 소켓이 아니라 빈 디렉터리(drwxr-xr-x)였고 worker2 노드에도 같은 디렉터리가 생겨 있었어요. 이 파드 안에서 Docker 클라이언트를 돌리면 붙을 데몬이 없어요.

빈 디렉터리가 생긴 이유는 containerd의 CRI 코드에 있어요. containerd v2.4.1의 internal/cri/opts/spec_linux_opts.go는 마운트할 호스트 경로가 없으면 디렉터리를 만들어요.

// Create the host path if it doesn't exist. // TODO(random-liu): Add CRI validation test for this case. if _, err := osi.Stat(src); err != nil { if !os.IsNotExist(err) { return fmt.Errorf("failed to stat %q: %w", src, err) } if err := osi.MkdirAll(src, 0755); err != nil { return fmt.Errorf("failed to mkdir %q: %w", src, err) } }

→ 호스트 경로가 없으면 0755 권한의 디렉터리를 만든 뒤 마운트한다는 뜻이에요. type을 비운 hostPath는 kubelet이 아무것도 확인하지 않고 넘기니 containerd가 docker.sock이라는 이름의 빈 디렉터리를 만들었어요. 노드에 남은 디렉터리의 권한(drwxr-xr-x)도 0755와 같아요.

그림 6. 같은 docker.sock 마운트라도 type이 있으면 바로 멈추고 type이 없으면 Running인 채 Docker 호출만 실패한다
⚠️ 주의: type을 비운 hostPath는 Docker가 없어도 Running이 돼요
• 모니터링·보안 에이전트가 쓸 docker.sock을 마운트하면서 hostPath의 type을 비워 두면 Docker가 없는 노드에서도 파드는 Running이 되고 에이전트 안에서 Docker 호출만 실패해요. 파드 상태만 봐서는 고장을 알아차리기 어려워요
• 소켓을 기대하는 마운트에는 type: Socket을 줘요. 노드에 그 소켓이 없으면 FailedMount 이벤트로 바로 드러나요
• 런타임을 바꾼 뒤에는 hostPath로 런타임 소켓을 붙인 파드부터 찾아서 쓰는 소켓을 containerd나 CRI 쪽으로 바꿀 수 있는지 확인해요. 이번 실험 뒤에는 worker2에 생긴 빈 디렉터리도 지웠어요
✍️ 오늘의 요약
CRI는 런타임을 kubelet 밖의 gRPC 서버로 빼려고 만든 경계였는데 Docker Engine은 그 서버가 아니었어요. 그래서 kubelet 안에 dockershim이 남았고 1.24에서 지워졌어요.

2016년까지 kubelet 안에는 Docker용과 rkt용 SyncPod가 따로 있었고 파드 기능이 늘 때마다 런타임 구현을 모두 고쳐야 했어요. 1.5의 CRI는 파드 로직을 kubelet에 한 번만 두고 런타임은 유닉스 소켓 건너편에서 샌드박스와 컨테이너 단위의 작은 호출만 받게 했어요. Docker Engine은 CRI를 구현하지 않아서 kubelet이 자기 안에 CRI 서버(dockershim)를 띄워 Docker API로 바꿨어요. 이 예외는 kubelet의 수명을 Docker와 묶었고 docker 라이브러리와 Docker 전용 분기를 kubelet에 남겼으며 cgroup v2 같은 새 기능을 막았어요. 쿠버네티스는 shim을 직접 밖에서 유지하는 길도 기본 빌드에서만 빼는 길도 고르지 않았어요. 1.20에서 경고를 넣고 1년 5개월 뒤 1.24에서 지웠고 Docker Engine을 계속 쓰려는 사용자는 cri-dockerd를 둬요. 깨진 것은 이미지가 아니라 노드의 docker 데몬과 docker.sock에 기대던 도구였어요. 우리 노드에서 type: Socket으로 docker.sock을 요구한 파드는 FailedMount로 멈췄고 type을 비운 파드는 빈 디렉터리를 받은 채 Running이 됐어요. 쿠버네티스가 뺀 것은 Docker가 아니라 kubelet 안에 남아 있던 Docker 전용 예외였어요.
