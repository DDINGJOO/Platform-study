50편. 노드 장애 판단의 50초와 300초는 왜 그 값일까 ← 지금 이 글

worker3의 kubelet을 멈추자 Ready가 Unknown으로 바뀐 시각은 정지 후 약 42초였어요. 같은 노드에 있던 두 파드 중 30초 toleration을 준 파드의 대체 파드는 약 72초에 만들어졌고 기본값을 쓴 파드의 대체 파드는 약 342초에 만들어졌어요. 두 파드의 차이는 270초였어요. 300초에서 30초를 뺀 값과 같아요.

그런데 워커 세 대의 kubelet을 함께 멈추자 결과가 달라졌어요. 한 노드에는 unreachable:NoExecute taint가 붙었지만 다른 두 노드에는 붙지 않았어요. 약 7분 뒤에도 두 노드의 파드는 API에서 Running으로 남아 있었어요. 50초와 300초를 더하는 것만으로는 이 결과를 설명할 수 없어요.

49편에서는 하트비트가 Node 객체에서 Lease로 빠진 이유를 봤어요. 이번에는 신호가 끊긴 뒤 기다리는 시간을 봐요. 50초는 노드 상태 판단의 유예 시간이고 300초는 파드가 NoExecute taint를 견디는 기본 시간이에요. 두 숫자의 기원과 현재 코드의 기준점을 나눠 읽은 뒤 Lima VM 4대, kubeadm v1.37.2인 우리 클러스터의 실험과 대조해요.

1. 50초는 하트비트 유예 40초보다 긴 연결 장애 확인 시간을 고려한 값이다

📖 용어: node-monitor-grace-period
노드 컨트롤러가 새 하트비트를 관찰하지 못해도 정상 상태를 유지하는 유예 시간이에요. v1.37.2의 기본값은 50초예요. kubelet이 정지한 순간부터 재는 고정 타이머가 아니라 컨트롤러가 마지막으로 새 신호를 관찰한 시각을 기준으로 판단해요.

처음부터 50초는 아니었어요. 2015년 3월 PR #5399에서 kubelet의 NodeStatus 보고 주기는 2초였고 노드 컨트롤러의 유예 시간은 8초였어요. 코드 주석은 보고 주기의 N배를 기다려 kubelet이 보고를 재시도할 수 있게 하되 사용자에게 지나치게 긴 기다림을 주지 않으려는 취지를 적었어요. 기본값은 보고 주기의 네 배였어요.

같은 해 4월 PR #6535에서 보고 주기가 2초에서 10초로 늘었고 유예 시간도 8초에서 40초로 늘었어요. 네 배라는 관계를 함께 옮겼어요. PR 설명은 성능 불만을 일부 해소하기 위한 변경이라고 해요. 이 자료만으로 특정 부하 실험에서 10초가 최적이었다고 말할 근거는 없어요.

49편에서 본 Lease가 들어온 뒤에도 40초는 오래 남았어요. Lease의 기본 갱신 주기도 약 10초였기 때문에 정상적인 보고 간격만 보면 네 번의 여유가 있었어요. 문제는 kubelet의 보고 지연 밖에도 시간을 쓰는 구간이 있었다는 점이에요.

살아 있는 노드도 컨트롤러의 캐시에서는 멈춰 있을 수 있다

2023년 11월의 이슈 #121793은 HTTP/2 연결이 조용히 끊어진 경우를 다뤄요. 노드 컨트롤러는 매번 모든 Lease를 직접 GET하지 않고 informer가 watch로 받아 둔 캐시를 읽어요. kubelet이 API 서버에 Lease를 잘 갱신해도 컨트롤러 쪽 연결이 새 데이터를 받지 못하면 캐시는 옛 값을 유지할 수 있어요.

당시 문제가 된 HTTP/2 설정은 데이터를 받지 못한 상태로 30초를 기다린 뒤 ping을 보내고 응답을 15초 더 기다리는 구성이었어요. 합하면 45초예요. 연결 실패를 알아차리기 전에 40초 유예 시간이 끝날 수 있었어요. 이때 Unknown은 노드가 죽었다는 확정이 아니라 컨트롤러가 새 신호를 확인하지 못했다는 결과예요. 30초와 15초의 이름은 설명문에서 바뀌어 쓰인 곳도 있지만 전송 설정 코드는 ReadIdleTimeout을 30초, PingTimeout을 15초로 둬요.

📖 용어: informer 캐시
API 서버의 목록과 변경 스트림을 받아 로컬에 유지하는 객체 사본이에요. 컨트롤러는 이 사본으로 반복 판단을 해서 API 요청을 줄여요. 따라서 API 서버에 저장된 최신 값과 컨트롤러가 지금 보는 값 사이에는 지연이 생길 수 있어요.

그림 1. 40초를 넘는 HTTP/2 실패 확인 시간은 50초 변경의 직접 근거였어요.

2024년 8월 14일 병합된 PR #126287은 기본값을 40초에서 50초로 바꿨어요. v1.32에 들어간 변경이에요. HTTP/2 전송 설정을 바꾸면 client-go를 쓰는 다른 프로그램에도 영향이 가므로 이 문제에서는 노드 유예 시간을 늘리는 변경을 택했어요. 그 대가로 실제 노드 장애를 판단하는 기본 대기 시간도 10초 늘었어요.

50초가 모든 오판을 없애는 보장은 아니다

이슈에는 반례도 있어요. 마지막 Lease 관찰을 0초로 두고 연결이 9초 뒤에 끊기면 연결 실패를 확인하는 시각은 9 + 30 + 15 = 54초가 될 수 있어요. 50초 유예는 여전히 먼저 끝나요. 기본값을 55초로 더 늘리자는 이슈 #127352도 나왔지만 유지보수자는 API 서버가 40~50초 동안 응답하지 않는 환경의 원인을 고치는 쪽을 권했어요. 타임아웃을 계속 늘리는 것은 장애 대응을 그만큼 늦추는 선택이기도 해요.

우리 버전에는 별도 방어도 있어요. v1.37의 NodeControllerLeaseCircuitBreaker는 beta이며 기본으로 켜져 있어요. 노드 컨트롤러 코드는 캐시 기준으로 유예 시간이 끝났을 때 Lease를 API 서버에서 직접 확인해요. 캐시와 다른 resourceVersion이 보이면 캐시가 따라올 시간을 주고 Unknown 처리를 미뤄요. Lease가 없다는 오류를 제외한 GET 실패 때도 판단을 보류하는 경로가 있어요. 이 글의 kubelet 정지 실험은 이 기능의 오판 방지 효과를 따로 검증한 실험은 아니에요.

💡 Lease의 40초와 노드 유예 50초는 서로 다른 설정이에요
Lease의 leaseDurationSeconds가 40이라고 해서 40초 뒤에 자동으로 Node가 Unknown이 되는 것은 아니에요. kubelet은 그 값의 1/4을 기본 갱신 간격으로 쓰고 노드 컨트롤러는 별도의 node-monitor-grace-period로 판단해요. 현재 코드는 새 Lease 갱신을 관찰한 컨트롤러 자신의 시각을 기록해요. renewTime과 현재 시각을 단순히 빼서 50초와 비교하는 식으로 구현을 설명하면 기준점이 달라져요.

2. 300초는 재부팅을 기다리려던 2015년의 5분에서 왔다

50초의 직접 계기는 연결 장애였어요. 300초는 더 오래된 운영 판단에서 왔어요. 2015년 2월의 PR #4241은 응답하지 않는 노드의 파드를 언제 지울지 정하는 변경이었어요. 처음 제시된 1분에 대해 Brian Grant가 코드 리뷰에서 이렇게 적었어요.

I'd make this 5 minutes. We want to tolerate reboots, for example.

→ 예를 들어 재부팅은 견뎌야 하므로 5분으로 하자는 뜻이에요. 구현은 5분으로 바뀌어 병합됐어요. 이 대화가 확인해 주는 것은 재부팅 정도의 일시적 중단을 기다리려는 의도예요. 재부팅 시간을 대규모로 측정해 정확히 300초를 도출했다거나 모든 워크로드에 최적이라는 근거까지 담고 있지는 않아요.

📖 용어: NoExecute toleration과 tolerationSeconds
NoExecute taint는 그 노드의 파드를 내보내는 조건이에요. 파드에 맞는 toleration이 있으면 그 조건을 견딜 수 있고 tolerationSeconds는 견딜 시간을 초로 정해요. 맞는 toleration에 seconds를 쓰지 않으면 시간 제한 없이 견뎌요. NoSchedule은 새 배치를 막는 효과이고 기존 파드의 축출 타이머를 시작하는 효과는 아니에요.

노드 전체의 타임아웃에서 파드별 기다림으로 옮겼다

처음의 5분은 노드 컨트롤러의 공통 설정인 --pod-eviction-timeout이었어요. 그러나 다른 곳에서 빨리 복구해야 하는 서비스와 로컬 상태 때문에 재부팅을 더 오래 기다려야 하는 파드는 요구가 달라요. 2016년의 taint 기반 축출 제안 #34825은 기존 축출 동작을 NoExecute taint와 toleration으로 옮기면서 파드별로 시간을 정할 수 있게 했어요. 기존 기본 동작을 이어받으려고 5분이 그대로 새 기본값의 출발점이 됐어요.

v1.6의 PR #41414에서 DefaultTolerationSeconds admission 플러그인이 들어왔어요. 파드에 해당 toleration이 없으면 not-ready:NoExecute와 unreachable:NoExecute를 각각 300초로 채워요. 파드가 직접 지정한 값이 있으면 그 값을 존중해요. 따라서 매니페스트에 300을 쓰지 않아도 저장된 파드 객체에는 300이 나타날 수 있어요. 33편에서 확인한 어드미션 단계의 동작이에요.

tolerations: - key: node.kubernetes.io/not-ready operator: Exists effect: NoExecute tolerationSeconds: 300 - key: node.kubernetes.io/unreachable operator: Exists effect: NoExecute tolerationSeconds: 300

두 항목은 300초씩 더해서 600초 기다리라는 뜻이 아니에요. 노드가 명시적으로 비정상이라고 보고한 Ready=False에는 not-ready가 대응하고 신호를 확인할 수 없는 Ready=Unknown에는 unreachable이 대응해요. 여러 NoExecute taint를 견뎌야 할 때는 맞는 toleration 가운데 더 짧은 제한이 실제 축출 시각을 정해요. 하나라도 견디지 못하는 taint가 있으면 유예 없이 축출 대상이 돼요.

현재 값을 바꾸려면 파드의 tolerationSeconds를 보거나 새 파드에 기본값을 넣는 API 서버의 --default-not-ready-toleration-seconds와 --default-unreachable-toleration-seconds를 봐야 해요. 옛 --pod-eviction-timeout은 taint 기반 축출을 사용하는 동안 이 경로의 시간을 정하지 못했고 v1.26에 deprecated된 뒤 v1.27에 제거됐어요.

현재 공식 문서는 일반 파드의 기본 300초와 DaemonSet의 차이도 설명해요. DaemonSet 파드는 두 NoExecute taint에 시간 제한 없는 toleration을 자동으로 받아요. 노드마다 있어야 하는 구성 요소가 노드의 일시적인 단절만으로 축출되지 않게 하는 동작이에요. 300초는 모든 파드에 일괄 적용되는 종료 명령이 아니에요.

3. 같은 300초여도 어디서부터 세느냐가 달라졌다

과거 문서의 5분과 현재의 5분을 비교할 때 놓치기 쉬운 부분이에요. 2015년의 PR #17306은 응답이 끊긴 노드의 축출 기준점을 마지막 하트비트 쪽으로 잡았어요. v1.12의 노드 컨트롤러에도 기존 방식이 남아 있어요. Ready=Unknown인 노드는 probeTimestamp에 podEvictionTimeout을 더해서 축출 여부를 봐요. 반면 Ready=False 경로는 readyTransitionTimestamp를 사용했어요. 이 둘을 같은 기준이었다고 묶으면 안 돼요.

지금 기본인 taint 방식은 단계를 나눠요. 노드 컨트롤러가 유예 시간 뒤 Unknown을 기록하고 unreachable:NoExecute taint를 붙여요. taint-eviction-controller가 그 taint와 파드의 toleration을 보고 축출 작업을 예약해요. 이때 파드별 300초가 시작돼요. 이전 Unknown 경로의 300초에는 노드 장애를 판단하느라 기다린 시간이 포함됐지만 현재 기본 경로에서는 그 판단을 한 뒤의 기다림이 돼요.

그림 2. 현재 300초의 시작점은 kubelet을 멈춘 시각이 아니에요.

📖 용어: 축출과 대체 파드
이 글의 축출은 taint-eviction-controller가 기존 파드에 API 삭제를 요청하는 동작이에요. 대체 파드는 ReplicaSet 등 워크로드 컨트롤러가 새로 만드는 별개 객체예요. 기존 파드의 삭제 요청, 새 파드 생성, 스케줄링, 컨테이너 실행은 각각 다른 시각에 일어나요.

v1.37.2 코드의 최초 예약은 startTime := now와 triggerTime := startTime.Add(minTolerationTime)을 사용해요. 이미 예약한 작업이 있으면 기존 CreatedAt을 고려해서 객체 업데이트마다 기다림을 처음부터 다시 시작하지 않아요. 따라서 NoExecute의 TimeAdded에 무조건 정확히 300.000초를 더한 시각에 삭제된다고 설명하기보다 컨트롤러가 taint를 처리하면서 타이머를 예약한다고 설명하는 것이 정확해요.

평상시 10초 갱신, 50초 유예, 5초 감시 주기를 단순히 놓으면 kubelet 정지 후 Unknown까지 대략 40~55초를 생각할 수 있어요. 마지막 신호가 정지 전에 얼마나 일찍 왔는지와 다음 감시가 언제 도는지에 따라 달라져요. 이어 300초를 더하면 대략 340~355초예요. 이 계산은 정상적인 컨트롤러 진행과 taint 공급을 가정한 설명이며 API 지연과 큐 제한까지 포함한 복구 시간 보장은 아니에요.

💡 축출이 원래 프로세스의 종료를 증명하지는 않아요
이 경로는 파드에 DisruptionTarget 조건을 기록하고 Pods.Delete를 호출해요. drain에서 쓰는 Eviction API와 경로가 달라요. API의 삭제 요청을 단절된 kubelet이 받지 못하면 컨테이너가 원래 노드에서 계속 실행될 수 있어요. 26편과 34편에서 확인한 API 상태와 실제 실행 상태의 차이예요. 더 짧은 toleration은 대체 파드를 빨리 만들 기회를 주지만 이전 실행을 강제로 멈췄다는 보장은 주지 않아요.

4. 30초와 300초를 준 파드는 대체 시각이 270초 달랐다

첫 실험은 worker3에 pause 이미지를 쓰는 Deployment 두 개를 놓고 비교했어요. 하나는 toleration을 생략해서 어드미션이 두 NoExecute toleration을 300초로 채웠고 다른 하나는 같은 두 항목을 30초로 명시했어요. 나머지 워커 두 대는 정상으로 두었어요. 원본은 labs/devops/k8s-study/out/50-evict-30-vs-300.txt와 같은 디렉터리의 50-evict-30-vs-300.sh에 남겼어요.

정지 전에 Lease의 renewTime은 22:00:09.822, 22:00:19.893, 22:00:29.984였어요. 약 10초 간격이에요. 22:00:37에 kubelet을 멈췄을 때 마지막 Lease 갱신은 이미 약 8초 전이었어요. 그래서 정지 뒤 50초를 온전히 기다리지 않고 약 42초 뒤 Unknown이 된 관측이 유예 50초와 모순되지 않아요.

그림 3. 상태 전이와 생성 시각은 객체의 필드이고 왼쪽 소수점 시각은 스크립트가 관측한 시각이에요.

무엇을 봤나객체 필드의 상대 시각처음 관측한 시각
Ready=Unknown, unreachable taint약 +42초+43.3초
tol30 대체 파드 생성약 +72초+73.7초에 Pending
tol30 대체 파드 Running이 출력에 상태 전이 시각 없음+74.7초
default 대체 파드 생성약 +342초+343.3초에 Pending

Unknown과 taint의 약 42초에 30초를 더하면 대체 파드 생성 약 72초와 맞고 300초를 더하면 약 342초와 맞아요. 이것은 초 단위로 반올림한 객체 시각과 약 1초 주기의 관측을 비교한 결과예요. 정확한 30.000초와 300.000초의 지연을 측정했다고 해석하면 안 돼요. 확실히 구별되는 것은 두 대체 파드 생성 시각의 차이가 약 270초였다는 점이에요.

그림 4. 삭제 요청과 새 파드 생성이 같은 초에 기록됐고 실행 상태 관측은 그다음이었어요.

이벤트는 UTC라서 터미널의 한국 시각과 9시간 차이가 나요. 13:01:50에 tol30의 기존 파드에 TaintManagerEviction이 기록됐고 같은 초에 ReplicaSet이 대체 파드를 만들었어요. 기본값 파드의 같은 두 이벤트는 13:06:20이었어요. tol30은 worker2로 기본값 파드는 worker1로 배치됐어요. 컨트롤러가 관리하는 파드였고 정상 워커에 자원이 있었기 때문에 대체 실행까지 이어진 결과예요. 단독으로 만든 파드에는 ReplicaSet의 자동 대체를 기대할 수 없어요.

5. 55%와 50대는 재배치할 여유와 운영자의 대응 시간을 고려한 기준이다

한 노드의 장애를 빨리 처리하는 정책을 넓은 장애에 그대로 적용하면 문제가 커질 수 있어요. 많은 노드가 한꺼번에 연락을 끊은 것은 개별 VM 고장보다 네트워크나 컨트롤 플레인 문제일 수도 있어요. 정상 노드가 거의 남지 않았다면 파드를 지워도 실행할 곳이 충분하지 않을 수 있어요. 노드 컨트롤러가 장애 비율에 따라 축출 속도를 줄이는 이유예요.

📖 용어: zone과 PartialDisruption
여기서 zone은 노드의 topology zone 정보를 이용한 장애 판단 단위예요. 우리 실습 환경은 zone 정보가 없어 네 노드가 빈 이름의 같은 zone으로 묶였어요. PartialDisruption은 그 zone에서 일정 수와 비율 이상의 노드가 Ready가 아닌 상태를 뜻해요. 애플리케이션 파드의 가용 비율을 직접 계산한 상태는 아니에요.

zone을 고려한 동작은 2016년의 PR #28897에서 들어왔어요. 처음 제안된 부분 장애 비율은 33%였어요. 이어 v1.4에 들어간 PR #30138에서 현재까지 이어진 기본값들이 정리됐어요. 장애 비율 0.55, 소규모 기준 50대, 평상시 초당 0.1노드, 부분 장애 때 초당 0.01노드예요. 작은 규모의 부분 장애에는 축출 속도를 0으로 낮추는 선택도 포함됐어요.

리뷰는 이 숫자들을 수학적 정답으로 제시하지 않았어요. 55% 기준은 파드가 대체로 고르게 분포한다는 가정에서 더는 다른 곳에 옮기기 어렵다는 상황을 거칠게 판단하려는 것이었어요. 50대 논의에는 축출을 너무 느리게 해 작은 클러스터에서 장애 복구에 오랜 시간이 걸리는 문제와 운영자가 상황을 파악해 대응할 시간 사이의 절충이 나와요. 40대 대신 50대로 하자는 의견도 운영 대응 시간을 근거로 했어요. 55%는 Raft의 과반 합의 기준이 아니고 50대는 재배치 가능 용량을 정확히 계산한 경계도 아니에요.

현재 코드의 조건은 비율 하나보다 조금 더 구체적이에요. ComputeZoneState는 Ready 노드가 하나도 없으면 FullDisruption으로 보고 그렇지 않으면 Ready가 아닌 노드가 3대 이상이면서 비율이 55% 이상일 때 PartialDisruption으로 봐요. 이 조건에서 Ready가 아닌 노드는 False와 Unknown을 포함해요.

case readyNodes == 0 && notReadyNodes > 0: return notReadyNodes, stateFullDisruption case notReadyNodes > 2 && float32(notReadyNodes)/float32(notReadyNodes+readyNodes) >= nc.unhealthyZoneThreshold: return notReadyNodes, statePartialDisruption

따라서 네 노드 중 두 대가 Ready가 아니면 2/4 = 50%라서 이 조건에 들어가지 않아요. 세 대면 3/4 = 75%이고 최소 3대 조건도 만족해요. 남은 한 대가 Ready이므로 FullDisruption이 아니라 PartialDisruption이에요. 우리 클러스터의 나머지 한 대는 컨트롤 플레인 노드예요. 그 노드가 상태 계산의 분모에 들어간다는 사실과 일반 파드를 받아 줄 수 있는지는 다른 문제예요.

0으로 낮추는 대상은 NoExecute taint를 공급하는 노드 큐다

현재 구현의 ReducedQPSFunc는 부분 장애 상태에서 노드 수가 largeClusterSizeThreshold보다 크면 secondaryNodeEvictionRate를 반환하고 그 이하면 0을 반환해요. 이 호출에는 해당 zone의 노드 수가 전달돼요. 기본 50대인 환경에서 4노드인 우리 zone은 0이 돼요. 0.01노드/초라면 평균 100초에 한 노드인 속도예요. 이것은 파드 한 개당 100초를 기다리라는 설정이 아니에요.

특히 현재 구조에서는 노드 컨트롤러의 이 큐가 NoExecute taint를 붙이고 별도 taint-eviction-controller가 이미 붙은 taint의 파드 타이머를 처리해요. 공식 문서도 대규모 노드 장애 때 taint를 추가하는 속도를 제한한다고 설명해요. 부분 장애로 큐 속도가 0이 됐다는 사실만으로 이미 예약된 모든 파드 삭제 작업이 취소됐다고 결론 내릴 수 없어요. 다음 실험에서 이 구분이 실제로 드러났어요.

그림 5. v1.29부터 분리된 taint-eviction-controller와 노드 컨트롤러의 일을 나눠 봐야 해요.

6. 세 워커를 함께 멈추자 한 노드의 파드만 축출되고 다른 두 노드의 파드는 남았다

두 번째 실험은 워커마다 pause 파드를 하나씩 직접 만든 뒤 세 kubelet을 함께 멈췄어요. Deployment가 아닌 단독 파드라서 자동 대체를 관찰하는 실험은 아니에요. 세 파드는 기본 300초 toleration을 받았어요. 노드의 Ready 전이, 두 종류의 taint, 컨트롤러 로그를 함께 남겼어요. labs/devops/k8s-study/out/50-three-workers-down.txt와 같은 디렉터리의 50-three-workers-down.sh에서 확인할 수 있어요.

22:09:16을 정지 기준으로 잡았어요. 처음 관측할 때 세 노드의 마지막 Lease는 각각 약 8초, 7초, 8초 전이었어요. 약 +45.3초에 세 노드 모두 Unknown으로 관측됐고 객체의 상태 전이 시각은 약 +44초였어요. 여기까지는 세 노드가 같았어요. taint가 달랐어요.

그림 6. 세 노드의 Ready는 같았지만 NoExecute 유무는 같지 않았어요.

노드약 +44초에 붙은 taint약 7분 뒤 단독 파드
worker1unreachable:NoExecute와 NoSchedule약 +345초에 삭제 로그
worker2unreachable:NoScheduleAPI에서 Running
worker3unreachable:NoScheduleAPI에서 Running

컨트롤러는 13:10:02 UTC, 정지 기준 약 46초에 빈 이름의 zone이 PartialDisruption으로 바뀌었다고 기록했어요. 이후 수집한 지표는 zone 크기 4, 비정상 노드 3, 정상 비율 25%였어요. 3/4 = 75%이므로 앞에서 본 조건과 맞아요. 하지만 worker1에는 그 전 관측에서 이미 NoExecute가 붙어 있었어요.

그 뒤 13:15:01 UTC에 taint-eviction-controller가 w8-zone/on-worker1을 삭제하는 로그를 남겼어요. 정지 후 약 345초이고 taint 시각 약 +44초에서 약 301초 뒤예요. 초 단위 전이 시각과 로그를 비교한 근삿값이며 기본 300초 타이머와 맞는 결과예요. 같은 시점에 worker1의 다른 일반 파드들도 삭제 로그에 나타났어요.

그림 7. 부분 장애로 새 taint 공급이 멈춘 뒤에도 worker1의 타이머는 만료됐어요.

worker2와 worker3는 NoSchedule만 있어서 새 일반 파드의 배치는 막혔지만 이 장애의 NoExecute 타이머는 시작되지 않았어요. 약 7분 뒤에도 두 단독 파드는 API에서 Running이었어요. 이는 두 kubelet이 다시 보고했다는 뜻이 아니에요. kubelet은 계속 멈춰 있었고 API 상태가 남아 있었던 것이에요. 이 실험은 VM 전원을 끈 것이 아니라 kubelet 프로세스를 멈춘 실험이므로 컨테이너와 네트워크까지 동시에 정지했다고 해석해서도 안 돼요.

이 결과가 보여 준 것은 소규모 동시 장애에서 새 NoExecute taint 공급이 막힐 수 있다는 점과 이미 공급된 taint의 파드 타이머는 계속 진행할 수 있다는 점이에요. 모든 파드가 반드시 남는다고 단정하거나 모든 파드가 50 + 300초에 반드시 축출된다고 단정하면 둘 다 이 관측과 맞지 않아요. 어떤 노드가 상태 변경과 큐 처리 사이에서 먼저 taint를 받았는지까지 봐야 해요. 다음 실행에서도 항상 worker1만 먼저 처리된다고 보장할 수는 없어요.

마지막으로 kubelet을 다시 시작하자 세 노드는 모두 Ready로 돌아왔어요. 이 실험에서 남긴 원본은 한 번의 동시 정지에 대한 관측이에요. zone 전체가 Ready를 잃는 FullDisruption의 별도 처리나 다양한 네트워크 분할을 모두 검증한 결과는 아니에요.

📝 정리

50초는 2015년의 2초 보고·8초 유예가 10초 보고·40초 유예로 바뀐 뒤 HTTP/2 연결 실패 확인에 걸리는 45초를 고려해 2024년에 늘어난 기본값이에요. 노드 사망의 확정 시각이 아니라 새 신호를 관찰하지 못한 상태에서 판단을 유예하는 시간이에요.

300초는 2015년에 재부팅을 견디려던 5분을 파드별 toleration의 기본값으로 이어받은 결과예요. 현재는 Unknown 판정 뒤 NoExecute taint가 처리되면서 기다림이 시작돼요. 우리 단일 노드 실험에서 30초 파드와 300초 파드의 대체 생성은 약 72초와 342초로 270초 차이였어요.

동시 장애에서는 taint 공급 제한까지 봐야 해요. 4노드 중 3노드가 Unknown인 부분 장애에서 두 노드는 NoExecute를 받지 않았고 한 노드에는 먼저 붙어 그 노드의 파드가 약 345초에 축출됐어요. 장애를 읽을 때는 마지막 신호 관찰, Ready 전이, NoExecute 유무, 파드 toleration, 삭제와 대체 실행을 순서대로 확인해야 해요.
