44편. 노드당 파드 110개는 어디서 나온 숫자일까

21시 10분 58초에 Deployment web이 거느린 ReplicaSet에 설정된 파드 수를 직접 5로 바꿨어요(kubectl scale rs web-765494fbb4 --replicas=5). 0.1초 뒤 첫 조회에서 그 ReplicaSet의 spec.replicas는 이미 3이었고 Terminating 파드가 2개 보였어요. 2초쯤 지나자 Running 파드 3개만 남았어요. 제가 고친 숫자는 0.1초 안에 사라졌고 그사이 파드 두 개가 생겼다가 지워졌어요.

예전 구성도에 적힌 컨트롤러 목록을 현재 클러스터와 비교해 봤어요. 목록은 이랬어요. Deployment, ReplicaSet, DaemonSet, Job/CronJob, endpoints, namespace, Node, Service, Route, 그리고 "User define". 설명에는 컨트롤러 매니저가 "모든 컨트롤러를 관리한다"는 말도 있었어요. 우리 클러스터의 kube-controller-manager(KCM)와 대 보면 그대로인 이름도 있고 달라진 이름도 있어요. ReplicaSet과 Deployment 컨트롤러는 위 장면에서 본 대로 KCM 안에서 서로 맞물려 돌지만 Node 컨트롤러는 이름이 셋으로 나뉘어 있고 endpoints는 다른 API로 넘어가는 중이에요. Service와 Route 컨트롤러는 아예 없고 User define에 해당하는 컨트롤러는 KCM 밖에서 따로 돌아요.

KCM을 멈추면 무엇이 안 되는지는 20편에서, 컨트롤러 이름이 49개라는 것과 클라우드 컨트롤러 매니저(CCM)가 따로 있다는 것은 24편에서 봤어요. 이번 글에서는 KCM 안을 들여다봐요. 49개가 어떤 일을 나눠 맡는지, 한 프로세스에서 어떤 신원과 연결로 API 서버와 이야기하는지, 목록의 Service 컨트롤러는 어디로 갔고 그 일을 지금 누가 하는지를 실험 기록과 v1.37.2 소스로 확인해요. 클러스터는 Lima VM 4대에 kubeadm v1.37.2와 Calico v3.33.0을 올린 실습 환경이에요.

1. ReplicaSet을 5로 고치자 0.1초 만에 Deployment 컨트롤러가 3으로 되돌렸다

실험 전용 네임스페이스 cm-demo에 pause 이미지로 Deployment web(replicas 3)을 만들고 세 단계로 건드렸어요. 주인 관계를 보고 파드 하나를 지운 뒤 ReplicaSet에 설정된 파드 수를 직접 바꿨어요.

그림 1. 파드를 지우면 0.8초 만에 다시 3개였고 ReplicaSet을 5로 고치면 0.1초 만에 3으로 돌아왔다

파드의 주인은 ReplicaSet이고 ReplicaSet의 주인은 Deployment였어요. 둘 다 controller=true였어요. 파드 객체를 만든 쪽은 managedFields에 kube-controller-manager로 남아 있었어요. kubectl은 Deployment만 만들었고 ReplicaSet과 파드는 KCM이 만든 거예요.

📖 용어: ownerReferences
객체의 metadata에 "내 주인은 누구인가"를 적는 칸이에요. controller=true가 붙은 주인이 그 객체를 관리하는 컨트롤러 쪽 객체예요. Deployment가 ReplicaSet을, ReplicaSet이 파드를 이렇게 거느려요. 주인이 지워지면 KCM의 garbage-collector-controller가 이 칸을 보고 딸린 객체를 지워요.

파드 하나를 지우자 0.8초(조회 간격 0.3초 포함) 만에 Running 3개로 돌아왔고 replicaset-controller가 SuccessfulCreate 이벤트를 남겼어요. 20편에서 KCM을 멈췄을 때는 지운 파드가 다시 생기지 않았어요. 이번에는 KCM이 떠 있었으니 1초도 안 걸렸어요.

ReplicaSet을 5로 바꾼 3-b가 이 글의 도입 장면이에요. 이벤트를 보면 replicaset-controller가 파드 두 개(vnwxz, xbfdm)를 만들었다가 그 둘을 다시 지웠고 그사이 deployment-controller가 "Scaled down replica set web-765494fbb4 from 5 to 3"을 남겼어요. 이벤트와 맞는 순서로 풀면 이래요.

· 제가 ReplicaSet의 spec.replicas를 5로 고쳤어요.
· replicaset-controller는 "원하는 파드 5개, 실제 3개"를 보고 두 개를 만들었어요.
· deployment-controller는 "Deployment는 3인데 그 ReplicaSet은 5"를 보고 ReplicaSet을 3으로 되돌렸어요.
· replicaset-controller는 다시 "원하는 3개, 실제 5개"를 보고 두 개를 지웠어요.

deployment-controller가 되돌린 곳은 v1.37.2 소스의 pkg/controller/deployment/rolling.go에 있어요. 롤링 업데이트 전략을 쓰는 Deployment에서 새 ReplicaSet에 설정할 파드 수를 맞추는 함수예요.

func (dc *DeploymentController) reconcileNewReplicaSet(ctx context.Context, allRSs []*apps.ReplicaSet, newRS *apps.ReplicaSet, deployment *apps.Deployment) (bool, error) { if *(newRS.Spec.Replicas) == *(deployment.Spec.Replicas) { // Scaling not required. return false, nil } if *(newRS.Spec.Replicas) > *(deployment.Spec.Replicas) { // Scale down. scaled, _, err := dc.scaleReplicaSet(ctx, newRS, *(deployment.Spec.Replicas), deployment, false) return scaled, err }

→ ReplicaSet에 설정된 파드 수가 Deployment에 설정된 파드 수보다 크면 Deployment에 설정된 파드 수로 줄인다는 뜻이에요. 같은 패키지의 sync.go가 이때 "Scaled %s replica set %s from %d to %d" 형식의 이벤트를 남겨요. 제가 넣은 5는 이 비교에서 그냥 "틀린 값"이었어요.

그림 2. 원하는 상태는 층마다 따로 있고 위층 컨트롤러가 아래층의 원하는 상태를 쓴다

Deployment 문서 첫머리에도 "Do not manage ReplicaSets owned by a Deployment."라는 주의가 있어요. Deployment가 거느린 ReplicaSet을 직접 관리하지 말라는 뜻이에요. 원하는 상태는 Deployment, ReplicaSet, 파드 층마다 따로 있고 위층 컨트롤러가 아래층의 원하는 상태를 써요. 아래층을 직접 고치면 위층 컨트롤러가 되돌려요.

💡 실무에서는: 개수와 템플릿은 맨 위층에서 바꿔요
• 파드 수는 kubectl scale deploy나 Deployment 매니페스트의 replicas로 바꿔요. ReplicaSet이나 파드를 직접 고치거나 지워도 위층 컨트롤러가 곧 되돌려요
• HPA를 붙였다면 replicas를 고치는 주인은 HPA 컨트롤러예요. 사람이나 GitOps 도구가 같은 칸을 같이 고치면 서로 덮어써요
• 파드 하나를 지우는 것은 "같은 템플릿으로 새로 띄워 달라"는 뜻이 돼요. 문제 파드를 살려 두고 조사하려면 ReplicaSet 문서의 "You can remove Pods from a ReplicaSet by changing their labels."대로 라벨을 바꿔 떼어 내요. 떼어 낸 자리는 새 파드로 채워져요

흔한 목록에 이름이 있던 Deployment, ReplicaSet, DaemonSet, Job/CronJob, namespace는 그대로 있어요. 대신 목록에 없던 이름이 훨씬 많아요. 파드를 띄우는 일보다 신원과 인증서, 스토리지, 정리 작업을 맡은 컨트롤러가 더 많아요.

"KCM이 모든 컨트롤러를 관리한다"는 말은 고쳐 읽어야 해요. Controllers 문서는 "Kubernetes comes with a set of built-in controllers that run inside the kube-controller-manager."라고 써요. KCM에 든 것은 쿠버네티스에 기본으로 딸려 오는 내장 컨트롤러 묶음이에요. 같은 문서는 "You can find controllers that run outside the control plane, to extend Kubernetes."라고도 적어요. 컨트롤 플레인 밖에서 도는 컨트롤러도 있다는 뜻이고 그 예는 6절에서 봐요. 41편의 스케줄러, 28편의 kube-proxy, 노드의 kubelet도 API 서버를 지켜보며 차이를 메우는 프로그램이지만 KCM에는 들어 있지 않아요.

3. 공유 인포머로 함께 읽고 컨트롤러별 ServiceAccount를 쓴다

컨트롤러 45개가 한 프로세스에서 돈다면 API 서버와는 어떻게 이야기할까요? 마스터에서 KCM 프로세스의 TCP 연결을 세어 보니 이랬어요.

21:10:55 master$ ss -tnp 로 kube-controller-manager 프로세스의 TCP 연결 (상대 주소:포트별 개수) 2 192.168.104.1:6443 LISTEN: 127.0.0.1:10257

→ 바깥으로 나가는 연결은 API 서버(6443)로 가는 두 개뿐이고 받는 포트는 마스터 안에서만 여는 10257(메트릭과 상태 확인용 HTTPS, 레퍼런스의 --secure-port 기본값) 하나라는 뜻이에요. etcd(2379)로 가는 연결도, 컨트롤러끼리 주고받는 연결도 없어요. 구성도의 "컨트롤러 매니저 ↔ Kubernetes objects(Desired state)" 화살표도 실제로는 이 두 연결을 지나 API 서버를 거쳐요.

읽는 쪽과 쓰는 쪽은 신원이 달랐어요. v1.37.2 cmd/kube-controller-manager/app/controllermanager.go의 두 부분을 보면 이래요.

// CreateControllerContext creates a context struct containing references to resources needed by the // controllers such as the cloud provider and clientBuilder. rootClientBuilder is only used for // the shared-informers client and token controller. ... versionedClient, err := rootClientBuilder.Client("shared-informers") ... func createClientBuilders(c *config.CompletedConfig) (clientBuilder clientbuilder.ControllerClientBuilder, rootClientBuilder clientbuilder.ControllerClientBuilder) { rootClientBuilder = clientbuilder.SimpleControllerClientBuilder{ ClientConfig: c.Kubeconfig, } if c.ComponentConfig.KubeCloudShared.UseServiceAccountCredentials { clientBuilder = clientbuilder.NewDynamicClientBuilder( restclient.AnonymousClientConfig(c.Kubeconfig), c.Client.CoreV1(), metav1.NamespaceSystem)

→ kubeconfig(controller-manager.conf)의 신원은 공유 인포머와 메타데이터·디스커버리 조회, 토큰 컨트롤러 등에 쓰여요. 리더 선출도 이 신원을 사용해요. --use-service-account-credentials가 켜져 있으면 나머지 컨트롤러의 전용 클라이언트는 kubeconfig의 인증서를 뗀 설정에 kube-system 네임스페이스의 ServiceAccount를 붙여 써요. 인용한 주석보다 실제 rootClientBuilder의 쓰임이 넓은 것은 같은 함수의 metadata-informers와 controller-discovery 클라이언트 생성 코드에서 확인할 수 있어요.

📖 용어: 공유 인포머(shared informer)
41편에서 본 인포머를 여러 컨트롤러가 함께 쓰도록 묶은 것이에요. 파드 watch는 한 번만 열고 ReplicaSet 컨트롤러, 가비지 컬렉터, EndpointSlice 컨트롤러 같은 여러 컨트롤러가 같은 캐시를 읽어요. KCM은 메모리를 아끼려고 이 캐시에 넣을 때 managedFields를 지워요(같은 함수의 "Informer transform to trim ManagedFields for memory efficiency." 주석).
📖 용어: --use-service-account-credentials
kube-controller-manager 레퍼런스의 설명은 "If true, use individual service account credentials for each controller."예요. 컨트롤러마다 따로 ServiceAccount를 쓰게 하는 플래그이고 kubeadm이 켜 둬요. v1.37.2 clientbuilder는 그 ServiceAccount가 없으면 만들고(getOrCreateServiceAccount) 3600초짜리 토큰을 TokenRequest로 받아 갱신해요. 10편에서 본 1시간짜리 토큰과 같은 길이예요.

실제 신원을 조회만 해서 확인했어요.

그림 3. 공유 인포머와 리더 선출은 KCM 인증서로, 일반 컨트롤러의 전용 클라이언트는 ServiceAccount로 API 서버에 들어간다

controller-manager.conf의 인증서는 CN=system:kube-controller-manager였어요. 공유 인포머의 watch는 모두 이 신원으로 들어가요. kube-system의 ServiceAccount는 47개였고 그중 이름이 -controller로 끝나는 것이 30개였어요. 나머지 17개 가운데 calico-cni-plugin, calico-kube-controllers, calico-node, coredns, default, kube-proxy, kube-state-metrics 7개는 다른 구성 요소의 것이고 남은 10개(generic-garbage-collector, horizontal-pod-autoscaler, persistent-volume-binder 등)는 v1.37.2 KCM 소스에서 컨트롤러가 클라이언트를 만들 때 넘기는 이름과 같았어요. KCM이 쓰는 ServiceAccount는 40개인 셈이에요.

돌고 있는 컨트롤러 45개와 숫자가 다른 이유도 소스로 맞춰 볼 수 있어요. node-ipam, node-lifecycle, taint-eviction 세 컨트롤러는 node-controller 하나를 같이 쓰고(core.go) CSR을 다루는 세 컨트롤러는 certificate-controller 하나를 같이 써요(certificates.go). 여기서 네 개가 줄어 41개가 되고 토큰을 만드는 serviceaccount-token-controller는 ServiceAccount 대신 KCM 자신의 인증서로 돌아서(service_accounts.go의 rootClientBuilder) 하나가 더 줄어요. 45 − 4 − 1 = 40이에요.

deployment-controller와 replicaset-controller의 ServiceAccount에는 RBAC 기본 정책의 ClusterRole system:controller:<이름>이 연결돼요(32편의 RBAC). 모든 컨트롤러가 ClusterRole을 쓰는 것은 아니에요. bootstrap-signer와 token-cleaner처럼 네임스페이스 Role을 쓰는 경우도 있어요(namespace_policy.go). deployment-controller는 ReplicaSet은 만들고 고칠 수 있지만 파드를 만들 수는 없었어요(create pods: no). replicaset-controller는 파드를 만들고 지울 수 있지만 Deployment를 고칠 수는 없었어요(update deployments.apps: no). 1절의 장면을 권한으로 다시 보면 deployment-controller는 ReplicaSet의 숫자만 고칠 수 있었고 파드를 만들고 지운 것은 replicaset-controller였어요. 이벤트에도 두 이름이 따로 남았어요. 반면 파드의 managedFields에는 둘 다 kube-controller-manager 하나로 남아서 이벤트보다 덜 자세해요.

그림 4. 공유 인포머는 KCM 인증서로 읽고 일반 컨트롤러는 전용 ServiceAccount를 쓴다. 리더 선출과 토큰 컨트롤러는 KCM 신원을 쓰는 예외다

연결이 컨트롤러 수만큼 생기지 않는 데에는 클라이언트 쪽 사정도 있어요. client-go는 TLS 설정이 같은 클라이언트끼리 전송 계층을 같이 써요. v1.37.2 client-go/transport/cache.go의 tlsCacheKey에는 CA, 클라이언트 인증서, 서버 이름 같은 값만 있고 토큰은 들어가지 않아요. 그러니 토큰만 다른 ServiceAccount 클라이언트 40개는 같은 전송 계층을 쓸 수 있어요. 인증서를 붙인 인포머 쪽과 인증서를 뗀 컨트롤러 쪽은 TLS 설정이 달라요. 두 연결이 이 둘에 하나씩인지까지는 이번에 가르지 않았어요. KCM은 내장 컨트롤러 수십 개를 한 프로세스에 넣고 공유 인포머의 캐시를 함께 읽어요. 일반 컨트롤러의 전용 클라이언트는 ServiceAccount를 쓰지만 리더 선출과 토큰 컨트롤러는 KCM 신원을 써요.

💡 실무에서는: 감사 로그와 권한 문제는 컨트롤러 이름으로 찾아요
• ServiceAccount를 쓰는 컨트롤러의 요청은 감사 로그에 system:serviceaccount:kube-system:replicaset-controller 같은 사용자 이름으로 남아요. 어느 컨트롤러가 객체를 고쳤는지 이 이름으로 가를 수 있어요
• 컨트롤러가 403으로 막힌다고 의심되면 kubectl auth can-i <동사> <리소스> --as=system:serviceaccount:kube-system:<컨트롤러 SA>로 권한을 바로 확인해요. 실제로 아무것도 만들지 않는 검사예요
• RBAC 문서에 따르면 API 서버는 시작할 때마다 기본 ClusterRole에 빠진 권한을 다시 채워요("updates default cluster roles with any missing permissions"). 컨트롤러에 권한을 더 줘야 하면 system:controller:* 롤을 직접 고치기보다 별도 ClusterRole을 만들어 붙여요

4. 흔한 목록의 Node 컨트롤러는 셋으로 나뉘었고 endpoints는 EndpointSlice로 넘어가는 중이다

흔한 목록의 "Node 컨트롤러"라는 이름의 컨트롤러는 KCM 목록에 없어요. 그 일은 셋으로 나뉘어 있고 셋 모두 앞 절에서 본 ServiceAccount node-controller를 같이 써요.

· node-ipam-controller: --allocate-node-cidrs=true와 --cluster-cidr=10.244.0.0/16을 보고 노드마다 podCIDR을 /24로 나눠 적어요. 이 클러스터는 Calico IPAM을 써서 그 값이 파드 IP와 상관없다는 것을 31편에서 봤어요.
· node-lifecycle-controller: kubelet의 Lease 갱신이 끊긴 노드를 Unknown으로 바꾸고 taint를 붙여요(25편).
· taint-eviction-controller: NoExecute taint가 붙은 노드의 파드를 toleration 시간이 지나면 내보내요. 25편에서 300초 뒤 축출을 본 것이 이 컨트롤러예요.

노드와 관련된 정리도 하나 더 있어요. pod-garbage-collector-controller는 파드 수명 주기 문서에 따르면 끝난 파드가 임계값보다 많을 때 지우고 "orphan Pods - bound to a node which no longer exists", 곧 이미 없어진 노드에 묶인 파드도 지워요. 클라우드에서 서버가 지워졌는지 확인해 Node 객체를 지우는 cloud-node-lifecycle 컨트롤러는 24편에서 본 대로 CCM 쪽에 있어요.

endpoints 컨트롤러는 아직 있어요. 그런데 Endpoints를 조회하면 경고가 먼저 나와요.

mac$ kubectl get endpoints kubernetes -n default Warning: v1 Endpoints is deprecated in v1.33+; use discovery.k8s.io/v1 EndpointSlice NAME ENDPOINTS AGE kubernetes 192.168.104.1:6443 9d mac$ kubectl get endpointslices -n default -l kubernetes.io/service-name=kubernetes NAME ADDRESSTYPE PORTS ENDPOINTS AGE kubernetes IPv4 6443 192.168.104.1 9d

→ v1 Endpoints API는 v1.33부터 폐기 예정(deprecated)이고 대신 EndpointSlice를 쓰라는 뜻이에요. 28편에서 본 대로 kube-proxy가 규칙을 만들 때 보는 것도 EndpointSlice예요. 지금 Service 뒤의 파드 목록을 만드는 주인공은 endpointslice-controller이고 endpoints-controller는 예전 API를 쓰는 쪽을 위해 남아 있어요. 사용자가 직접 만든 Endpoints를 EndpointSlice로 옮겨 주는 endpointslice-mirroring-controller도 EndpointSlices 문서는 Endpoints API와 함께 폐기 예정으로 적어 두었어요.

누가 만든 EndpointSlice인지는 라벨로 가릴 수 있어요. 같은 문서에 따르면 "The endpoint slice controller sets endpointslice-controller.k8s.io as the value for this label"이고 그 라벨은 endpointslice.kubernetes.io/managed-by예요. default 네임스페이스를 조회해 보니 myweb의 슬라이스에는 endpointslice-controller.k8s.io가 있었고 kubernetes 서비스의 슬라이스에는 이 라벨이 비어 있었어요. API 서버 자신을 가리키는 이 슬라이스는 KCM이 아니라 API 서버가 Endpoints와 함께 직접 써요(v1.37.2 pkg/controlplane/reconcilers/endpointsadapter.go의 EnsureEndpointSliceFromEndpoints).

⚠️ 주의: Endpoints를 읽는 스크립트와 도구는 EndpointSlice로 옮겨요
• kubectl get endpoints는 아직 동작하지만 v1.33부터 경고가 붙어요. 모니터링 스크립트나 직접 만든 컨트롤러가 Endpoints를 본다면 discovery.k8s.io/v1 EndpointSlice로 바꿔요
• EndpointSlice는 Service 하나에 여러 개일 수 있어요. 이름이 아니라 kubernetes.io/service-name=<서비스> 라벨로 찾아요

5. Service와 Route 컨트롤러는 cloud-controller-manager로 옮겨 갔다

흔한 목록의 Service 컨트롤러와 Route 컨트롤러는 KCM 목록에 없어요. 24편에서 본 대로 둘은 클라우드 API를 불러야 하는 컨트롤러라서 cloud-controller-manager(CCM)로 옮겨 갔어요. Service 컨트롤러는 type LoadBalancer Service를 보면 클라우드에 로드밸런서를 만들고 Route 컨트롤러는 다른 노드의 파드끼리 닿도록 클라우드 네트워크에 경로를 넣어요. v1.31에서 마지막 in-tree 클라우드 연동 코드가 빠졌고 v1.37.0에서는 KCM에 남아 있던 이름(service-lb-controller, node-route-controller, cloud-node-lifecycle-controller)까지 빠졌어요. 우리 클러스터에는 CCM이 0개예요.

이번 조회에서 흔적을 하나 더 찾았어요. 3절의 system:controller: 롤 41개 가운데 route-controller와 service-controller가 있었어요. RBAC 기본 정책(controller_policy.go)에 두 롤이 아직 정의돼 있기 때문이에요. 현재 kube-system에는 그 이름의 ServiceAccount가 없고 v1.37.2 KCM의 컨트롤러 등록 목록에도 두 컨트롤러가 없어요. 롤이 왜 남아 있는지는 원문에서 이유를 찾지 못했어요.

그렇다면 이름이 Service인 컨트롤러가 없는데 Service는 누가 처리할까요? ClusterIP는 컨트롤러가 아니라 API 서버가 정해요. Virtual IPs and Service Proxies 문서는 "Kubernetes does that by allocating each Service its own IP address from within the service-cluster-ip-range CIDR range that is configured for the API Server."라고 써요. API 서버에 설정된 서비스 대역에서 Service마다 IP를 하나씩 할당한다는 뜻이에요. 같은 문서는 이 할당을 IPAddress와 ServiceCIDR 객체로 기록하는 방식도 설명해요.

그림 5. ClusterIP는 IPAddress 객체로 하나씩 기록돼 있었고 headless Service 하나만 IP가 없었다
📖 용어: ServiceCIDR와 IPAddress
ServiceCIDR는 Service에 줄 수 있는 IP 대역을 담은 객체이고 IPAddress는 그 대역에서 할당된 IP 하나를 "어느 Service 몫인지"와 함께 적은 객체예요. 문서에 따르면 클러스터가 처음 뜰 때 kube-apiserver의 --service-cluster-ip-range 값으로 kubernetes라는 이름의 ServiceCIDR가 만들어져요. KCM의 service-cidr-controller는 ServiceCIDR에 보호용 finalizer와 Ready 조건을 달고 아직 IPAddress가 남은 대역이 지워지지 않게 막아요(v1.37.2 servicecidrs_controller.go).

우리 클러스터의 ServiceCIDR는 kubernetes 하나(10.96.0.0/12)였어요. Service 9개 가운데 clusterIP가 None인 headless Service가 1개였고 IPAddress 객체는 정확히 8개였어요. 10.96.0.1의 주인(parentRef)은 services/default/kubernetes였고 managed-by 라벨은 ipallocator.k8s.io였어요. v1.37.2 pkg/registry/core/service/ipallocator/ipallocator.go의 ControllerName 값이에요. Service를 저장할 때 IP를 고르는 API 서버 안의 할당기가 이 라벨을 붙여요.

Service 하나의 일을 나눠 맡는 쪽을 모으면 그림 6과 같아요.

그림 6. Service의 일은 여러 구성 요소가 나눠 맡는다. CCM이 없는 이 실습에서 Calico는 LoadBalancer IP 할당과 파드 경로를 맡는다

이 실습에서 Calico가 맡는 일은 LoadBalancer IP 할당과 노드 사이 파드 경로 설정이에요. 외부 클라우드 로드밸런서를 만드는 것은 아니에요. LoadBalancer IP는 24편에서 calico-kube-controllers의 loadbalancer 컨트롤러가 IP 풀을 만들자 3초 안에 채웠고 노드 사이 파드 경로는 30편에서 본 BIRD와 Felix가 넣어요. "Service 컨트롤러"는 지금 클라우드 로드밸런서를 만드는 CCM의 컨트롤러를 가리키고 Service의 나머지 일은 API 서버, KCM의 EndpointSlice 컨트롤러, kube-proxy, CoreDNS가 나눠 맡아요.

6. 컨트롤러 매니저 밖의 컨트롤러와 kubectl apply가 보내는 요청

흔한 목록의 마지막 "User define"은 KCM 안에 없어요. 사용자가 설치한 컨트롤러는 보통 클러스터 안의 Deployment로 떠서 KCM과 똑같이 API 서버를 지켜봐요. 이 클러스터에서 가장 가까운 예가 calico-kube-controllers예요.

그림 7. KCM 밖에는 calico-kube-controllers가 있고 kubectl apply는 처음에는 POST, 다음에는 PATCH를 보냈다

calico-kube-controllers는 replicas 1인 Deployment이고 환경 변수 ENABLED_CONTROLLERS가 node,loadbalancer였어요. node 컨트롤러는 34편에서 본 IPAM 정리(새는 IP와 빈 블록 반납)를, loadbalancer 컨트롤러는 24편에서 본 LoadBalancer IP 할당을 맡아요. 이 컨트롤러는 KCM의 ServiceAccount가 아니라 자기 ServiceAccount(calico-kube-controllers)로 API 서버에 붙어요. CRD로 새 리소스를 정의하고 그 리소스를 지켜보는 컨트롤러를 함께 배포하는 오퍼레이터도 같은 자리예요.

📖 용어: 오퍼레이터(operator)
CRD로 새 객체 종류(예: 데이터베이스 클러스터)를 정의하고 그 객체를 지켜보며 실제 상태를 맞추는 컨트롤러를 함께 배포하는 방식이에요. 동작 원리는 KCM의 내장 컨트롤러와 같고 보통 클러스터 안의 Deployment로 떠서 자기 ServiceAccount와 RBAC으로 일해요.

구성도에서 kubectl과 API 서버 사이 화살표에는 "kubectl apply(create/update)"라고 적혀 있었어요. 같은 ConfigMap을 두 번 apply하며 -v=6으로 요청을 보니 처음에는 GET이 404 Not Found를 받은 뒤 POST로 만들었고(201 Created, "created") 값을 바꾼 두 번째에는 GET이 200을 받은 뒤 PATCH를 보냈어요(200, "configured"). kubectl apply가 "없으면 만들고 있으면 고친다"를 고르는 것은 맞지만 고칠 때 보내는 것은 객체 전체를 바꾸는 update(PUT)가 아니라 바뀐 부분만 보내는 PATCH였어요. 41편에서 managedFields에 kubectl-client-side-apply가 보인 것도 이 방식(클라이언트 쪽 apply) 때문이에요. 어느 쪽이든 kubectl은 API 서버의 원하는 상태를 고칠 뿐이고 나머지는 1절에서 본 컨트롤러들이 해요.

⚠️ 주의: KCM 밖의 컨트롤러는 KCM 로그와 메트릭에 나오지 않아요
• calico-kube-controllers나 오퍼레이터가 멈추면 KCM은 멀쩡해도 그 컨트롤러가 맡은 일(IP 정리, LoadBalancer IP, CRD 객체)이 멈춰요. 34편에서는 calico-kube-controllers 안의 다른 기능이 막혀 IPAM 정리가 23분 넘게 돌지 않았어요
• 클러스터에 어떤 컨트롤러가 있는지는 KCM 목록만으로 알 수 없어요. kubectl get deploy -A에서 controller나 operator가 들어간 이름과 CRD 목록(kubectl get crd)을 함께 봐요
• 장애 때는 그 컨트롤러의 파드 로그에서 "Waiting" 같은 대기 메시지가 계속 찍히는지부터 봐요
✍️ 오늘의 요약
컨트롤러 매니저는 쿠버네티스 내장 컨트롤러 49개를 묶은 프로세스이고 Service와 Route 컨트롤러는 클라우드 API가 필요해서 cloud-controller-manager로 옮겨 갔어요.

ReplicaSet을 직접 5로 고치자 replicaset-controller가 파드 둘을 만들었고 0.1초 안에 deployment-controller가 ReplicaSet을 3으로 되돌려 그 둘은 다시 지워졌어요. 원하는 상태는 층마다 있고 위층 컨트롤러가 아래층을 써요. KCM 안의 49개 가운데 45개가 시작됐고 워크로드보다 신원·인증서·스토리지·정리를 맡은 컨트롤러가 더 많았어요. 공유 인포머는 KCM 자신의 인증서로 읽고 일반 컨트롤러의 전용 클라이언트는 ServiceAccount 40개를 나눠 써요. 리더 선출과 토큰 컨트롤러는 KCM 신원을 써요. 역할별 권한이 달라서 deployment-controller는 파드를 만들 수 없고 replicaset-controller는 Deployment를 고칠 수 없어요. 연결은 API 서버로 가는 두 개뿐이었어요. 흔한 목록의 Node 컨트롤러는 node-ipam·node-lifecycle·taint-eviction으로 나뉘었고 endpoints는 EndpointSlice로 넘어가는 중이에요. ClusterIP는 API 서버가 정해 IPAddress 객체로 기록했고 이 클러스터의 Calico는 LoadBalancer IP 할당과 노드 사이 파드 경로 설정을 맡아요. KCM에 무엇이 있는지만큼 무엇이 없는지 알아야 장애 때 어느 컨트롤러를 볼지 고를 수 있어요.
