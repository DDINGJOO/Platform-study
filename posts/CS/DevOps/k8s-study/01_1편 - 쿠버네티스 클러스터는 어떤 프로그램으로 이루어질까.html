📚 k8s 스터디 · 1편
1편. 쿠버네티스 클러스터는 어떤 프로그램으로 이루어질까 ← 지금 이 글
2편. kubectl apply부터 파드가 뜨기까지 무슨 일이 일어날까
3편. VM으로 실습 노드를 만들 때 네트워크를 두 개 붙이는 이유
4편. kubeadm 설치 전에 swap을 꺼야 하는 이유
5편. kubeadm init이 만드는 인증서와 kubeconfig, 정적 파드

VM 네 대를 켜고 노드 4개가 모두 Ready가 된 것을 확인했어요. 이어서 kubectl get pods -n kube-system을 쳤더니 파드가 15개 나왔습니다. 저는 아직 파드를 하나도 만들지 않았는데 말이에요.

이름 몇 개는 익숙했어요. etcd, kube-apiserver, kube-scheduler가 보였습니다. 그런데 노드마다 있어야 할 kubelet은 목록 어디에도 없었고 calico-node와 kube-proxy는 네 개씩 있었어요. 어떤 파드는 이름이 -k8s-master로 끝나고 어떤 파드는 무작위 글자로 끝났습니다.

이 클러스터는 Apple Silicon Mac에서 Lima로 VM 4대를 만들고 kubeadm으로 묶은 실습 환경이에요. 마스터 k8s-master 1대와 워커 k8s-worker1~3 3대로 이뤄져 있어요. 쿠버네티스는 v1.37.2, 컨테이너 런타임은 containerd 2.4.1, 파드 네트워크는 Calico v3.33.0을 썼어요. 만드는 과정은 3편부터 다루고 이 글에서는 다 만든 클러스터를 들여다봅니다. 질문은 두 개예요. 마스터 1대와 워커 3대를 켜면 무엇이 어디서 돌고 있을까요? 그리고 각각이 없으면 무엇이 곤란할까요?

이 글에서 다룰 것
· kube-system의 파드 15개는 각각 무엇이고 어느 노드에 떠 있나?
· 구성 요소끼리는 정보를 어떻게 주고받나? 왜 전부 API 서버를 거치나?
· 구성 요소가 하나씩 빠지면 클러스터의 무엇이 멈추나?
· 같은 kube-system 파드인데 왜 주인이 Node, DaemonSet, ReplicaSet으로 갈리나?
· kubelet과 containerd는 왜 이 목록에 없나?

1. 아무것도 만들지 않았는데 파드가 15개 있었다

먼저 노드부터 봤어요. 아래는 마스터에 들어가 노드 목록을 조회한 출력입니다.

master$ kubectl get nodes NAME STATUS ROLES AGE VERSION k8s-master Ready control-plane 3m40s v1.37.2 k8s-worker1 Ready worker 3m26s v1.37.2 k8s-worker2 Ready worker 3m26s v1.37.2 k8s-worker3 Ready worker 3m26s v1.37.2

→ 노드 4대가 모두 Ready이고 버전은 v1.37.2라는 뜻이에요. ROLES의 control-plane은 kubeadm이 마스터에 붙인 라벨이고 worker는 실습 도구 ./lab이 워커에 따로 붙인 라벨이에요.

그다음 kube-system 네임스페이스의 파드를 조회했어요. 이름만으로는 누가 만든 파드인지 알 수 없어서 각 파드가 떠 있는 노드(.spec.nodeName)와 소유자의 종류(.metadata.ownerReferences[0].kind)를 열로 뽑았습니다.

📖 용어: 소유자 참조 (ownerReferences)
쿠버네티스 객체가 "나를 만든 객체는 이것이다"라고 적어 두는 필드예요. ReplicaSet이 만든 파드에는 그 ReplicaSet이 적혀 있어요. 이 글에서는 이 필드에 적힌 종류(kind)를 OWNER 열로 뽑아 파드를 누가 띄웠는지 구분하는 데 씁니다.
그림 1. kube-system의 파드 15개. OWNER가 Node, DaemonSet, ReplicaSet 세 종류로 갈린다

15개를 소유자별로 세면 Node 4개, DaemonSet 8개, ReplicaSet 3개예요. Node가 주인인 넷은 etcd, kube-apiserver, kube-controller-manager, kube-scheduler이고 모두 k8s-master에 있어요. DaemonSet이 주인인 여덟은 calico-node 4개와 kube-proxy 4개이고 노드 네 대에 하나씩 떠 있습니다. ReplicaSet이 주인인 셋은 coredns 2개와 calico-kube-controllers 1개이고 셋 다 k8s-worker1에 있었어요. 노드별로 세면 master 6개, worker1 5개, worker2 2개, worker3 2개입니다.

OWNER가 세 종류라는 것은 이 파드들이 서로 다른 세 경로로 만들어졌다는 뜻이에요. 그 경로는 5절에서 보기로 하고 먼저 이 프로그램들이 서로 정보를 어떻게 주고받는지부터 볼게요.

2. 구성 요소끼리는 서로를 부르지 않는다

파드 하나를 띄우는 일을 생각해 볼게요. 어느 노드에 띄울지 고르는 프로그램(kube-scheduler)과 실제로 띄우는 프로그램(kubelet)이 따로 있어요. 스케줄러가 고른 결과를 그 노드의 kubelet에게 직접 전한다고 해 봅시다. 그러면 스케줄러는 모든 노드의 kubelet 주소를 알아야 하고 마침 그 kubelet이 재시작 중이면 결정을 다시 보낼 방법도 스스로 마련해야 해요. 구성 요소가 늘수록 서로 알아야 하는 상대도 늘어납니다.

쿠버네티스는 이렇게 하지 않아요. 스케줄러는 결정을 API 서버에 기록하고(공식 문서는 이 과정을 binding이라고 불러요) kubelet은 자기 노드에 배정된 파드를 API 서버에서 가져갑니다. 둘은 서로의 주소를 몰라도 돼요. 공식 문서에는 노드와 컨트롤 플레인 사이의 통신이 이렇게 정리돼 있어요. "노드에서(또는 노드가 돌리는 파드에서) 나오는 모든 API 사용은 API 서버에서 끝난다. 다른 컨트롤 플레인 구성 요소는 원격 서비스를 내놓도록 설계되지 않았다."

📖 용어: 컨트롤 플레인 (control plane)
클러스터의 상태를 저장하고 결정을 내리는 구성 요소들을 묶어 부르는 이름이에요. 이 클러스터에서는 kube-apiserver, etcd, kube-scheduler, kube-controller-manager 넷이고 모두 k8s-master에 떠 있어요. 노드마다 도는 kubelet, kube-proxy, 컨테이너 런타임은 노드 구성 요소라고 불러요.
그림 2. kubelet과 containerd 사이를 빼면 모든 화살표가 API 서버로 간다. etcd에 붙는 것은 API 서버 하나뿐이다

이 구조에서는 구성 요소마다 할 일이 단순해져요. API 서버에서 자기가 맡은 종류의 객체를 지켜보다가 할 일이 생기면 API 서버에 쓰기만 하면 됩니다. 공식 문서의 컨트롤러 설명에도 같은 내용이 있어요. 컨트롤러는 원하는 상태에 가까워지도록 무언가를 바꾼 뒤 현재 상태를 API 서버에 보고하고 다른 컨트롤 루프가 그 보고를 받아 자기 일을 한다고 적혀 있어요. 구성 요소끼리는 서로를 부르지 않고 API 서버에 쓰고 API 서버를 지켜봐요.

Calico도 이 구조를 따랐어요. 설치한 Calico 매니페스트에는 DATASTORE_TYPE=kubernetes가 들어 있어서 Calico는 자기 데이터도 쿠버네티스 API를 거쳐 저장해요. 그래서 calico-node와 calico-kube-controllers도 etcd에 직접 붙지 않고 API 서버를 거칩니다.

⚠️ 주의: 반대 방향 연결도 있어요
"모두 API 서버를 거친다"는 말은 노드 쪽에서 시작하는 연결 이야기예요. 공식 문서에는 API 서버가 먼저 kubelet에 연결하는 경우도 나와 있어요. 파드 로그를 가져올 때, 실행 중인 파드에 attach할 때, port-forward를 할 때예요. 그래서 kubectl logs가 동작하려면 API 서버가 그 노드의 kubelet에 닿을 수 있어야 해요.

3. 컨트롤 플레인 넷: 하나씩 빠지면 생기는 일

이제 마스터에 있는 넷을 하나씩 볼게요. 각각 무엇을 하는지보다 빠지면 무엇이 멈추는지를 먼저 적었습니다.

kube-apiserver가 없으면 kubectl로 아무것도 조회하거나 바꿀 수 없어요. kubectl이 보내는 요청은 모두 API 서버로 가기 때문이에요. 스케줄러, 컨트롤러, kubelet도 새 정보를 받을 곳과 결과를 적을 곳을 함께 잃습니다. 공식 문서는 kube-apiserver를 "쿠버네티스 HTTP API를 내놓는 핵심 서버"라고 설명해요.

etcd가 없으면 API 서버가 상태를 저장하고 읽을 곳이 없어요. 파드, Deployment, 노드 정보가 모두 여기에 들어 있습니다.

📖 용어: etcd
쿠버네티스가 클러스터의 모든 데이터를 저장하는 키-값 저장소예요. 공식 문서에는 "etcd에 접근하는 것은 클러스터의 root 권한과 같으므로, 이상적으로는 API 서버만 접근해야 한다"고 적혀 있어요. 그래서 그림 2에서도 etcd에 닿는 화살표는 API 서버와 이어진 하나뿐이에요.

kube-scheduler가 없으면 새 파드가 노드를 배정받지 못해요. 스케줄러는 아직 노드가 정해지지 않은 파드를 찾아 알맞은 노드를 골라 주는 프로그램이에요. 고를 쪽이 없으면 파드는 노드 없이 Pending 상태로 남습니다.

kube-controller-manager가 없으면 Deployment를 만들어도 파드가 생기지 않아요. Deployment를 보고 ReplicaSet을 만드는 일과 ReplicaSet을 보고 파드 개수를 맞추는 일을 모두 이 안의 컨트롤러가 하기 때문이에요. 노드가 응답하지 않을 때 그 노드를 Ready가 아닌 상태로 바꾸는 일도 여기서 합니다. 기본값으로는 kubelet의 소식이 50초 동안 없으면 그 노드의 Ready 조건을 Unknown으로 바꿔요.

📖 용어: 컨트롤러 (controller)
클러스터의 현재 상태를 지켜보다가 원하는 상태와 다르면 그 차이를 줄이는 쪽으로 움직이는 루프예요. 대개 파드를 직접 띄우지 않고 "파드를 만들어 달라"고 API 서버에 요청하는 방식으로 일해요. 쿠버네티스에 기본으로 들어 있는 컨트롤러들은 kube-controller-manager라는 프로그램 하나 안에서 함께 돌아갑니다.

네 개는 모두 마스터 한 대에만 있어요. 이 실습 클러스터에서 마스터가 꺼지면 이 넷이 함께 멈춥니다. 워커가 세 대여도 클러스터에 새 일을 시키는 요청은 모두 마스터 한 대가 받아요.

4. 노드마다 도는 것과 애드온

노드 쪽은 네 대 모두 구성이 같아요. 공식 문서에서는 kubelet, 컨테이너 런타임, kube-proxy 셋을 노드 구성 요소로 꼽습니다.

kubelet이 없으면 그 노드에는 파드가 뜨지 않아요. kubelet은 자기 노드에 배정된 파드를 API 서버에서 받아 그 파드의 컨테이너가 실제로 돌고 있도록 지키는 프로그램이에요. 노드 상태를 API 서버에 보고하는 것도 kubelet입니다. 4편에서 worker3에 swap을 켜 kubelet이 시작하지 못하게 했더니 1분 뒤 노드 목록에서 worker3만 NotReady였어요. 보고하는 쪽이 사라지자 컨트롤 플레인이 그 노드를 준비되지 않은 상태로 본 거예요.

containerd가 없으면 컨테이너를 실행할 프로그램이 없어요. kubelet은 컨테이너를 직접 만들지 않고 CRI(Container Runtime Interface, kubelet이 컨테이너 런타임에게 일을 시키는 규격)로 containerd에게 이미지를 받고 컨테이너를 만들라고 요청합니다. containerd는 쿠버네티스 API를 모르고 같은 노드의 kubelet 요청만 받아요.

kube-proxy가 없으면 Service(파드 여러 개를 바뀌지 않는 주소 하나로 묶어 부르게 해 주는 객체)로 보낸 요청을 파드로 넘겨 줄 규칙이 노드에 없어요. kube-proxy는 Service 정보를 API 서버에서 받아 노드마다 네트워크 규칙을 넣어 두는 프로그램이에요. 이 클러스터에서는 iptables 규칙으로 넣어요(2편에서 다뤄요). 공식 문서에는 kube-proxy가 선택 구성 요소로 적혀 있어요. 일부 파드 네트워크 구현은 이 일을 자기 방식으로 대신하기 때문이에요.

여기까지가 공식 문서가 꼽는 노드 구성 요소예요. kube-system에 남은 셋은 애드온(클러스터에 기능을 더하려고 따로 설치하는 것)입니다. 쿠버네티스는 파드끼리 통신하는 경로를 직접 만들지 않아서 그 일을 하는 프로그램을 따로 설치해야 해요.

calico-node가 이 클러스터의 CNI 플러그인이에요. 이 플러그인이 없으면 파드끼리 통신할 방법이 없어요. kubeadm 문서에 따르면 CNI 기반 파드 네트워크 애드온은 직접 설치해야 하고 그 전에는 클러스터 DNS(CoreDNS)도 뜨지 않아요. calico-node는 노드 네 대에 하나씩 떠 있어요. Calico를 고른 이유와 바꾼 설정은 6편에서 다뤄요.

📖 용어: CNI 플러그인 (Container Network Interface)
파드에 IP를 붙이고 다른 노드에 있는 파드까지 가는 경로를 만들어 주는 프로그램이에요. 쿠버네티스는 이 부분의 규격만 정하고 실제 구현은 외부 프로그램에 맡겨요. Flannel, Calico, Cilium이 대표적이고 이 클러스터는 Calico를 씁니다.

calico-kube-controllers는 Calico용 컨트롤러 모음이에요. Calico 문서에 따르면 쿠버네티스 API를 지켜보다가 클러스터 상태에 맞춰 동작해요. 예를 들어 삭제된 노드의 Calico 데이터를 지웁니다. 이게 없으면 노드를 지워도 Calico 쪽에는 그 노드의 데이터가 남습니다. 매니페스트에는 "한 번에 하나만 돌 수 있다"는 주석과 함께 개수가 1개로 정해져 있어요.

coredns가 없으면 파드 안에서 Service를 이름으로 찾을 수 없어요. 쿠버네티스는 Service와 파드의 DNS 레코드를 만들어 IP 대신 이름으로 접근하게 하는데 그 이름 질의에 답하는 DNS 서버가 coredns예요. 이 클러스터의 coredns 2개는 둘 다 worker1에 떠 있었어요. 이 상태에서 worker1이 꺼지면 2개가 함께 멈춥니다.

5. 같은 kube-system인데 띄운 주체가 다르다

1절의 OWNER 열로 돌아가 볼게요. 컨트롤 플레인 넷의 주인은 Node였어요. 파드를 만든 객체가 Deployment도 DaemonSet도 아니고 노드라는 뜻입니다. 마스터와 worker1의 같은 폴더를 비교하면 이유를 알 수 있어요.

master$ ls /etc/kubernetes/manifests etcd.yaml kube-apiserver.yaml kube-controller-manager.yaml kube-scheduler.yaml worker1$ ls /etc/kubernetes/manifests

→ 마스터의 이 폴더에는 컨트롤 플레인 넷의 파드 정의 파일이 하나씩 있고 worker1의 같은 폴더는 비어 있다는 뜻이에요. kubelet은 이 폴더를 주기적으로 훑어서 파일이 생기면 그 파드를 띄우고 파일이 사라지면 파드를 지워요.

📖 용어: 정적 파드 (static Pod) · 미러 파드 (mirror Pod)
API 서버를 거치지 않고 특정 노드의 kubelet이 폴더의 파일을 읽어 직접 띄우는 파드가 정적 파드예요. kubelet은 정적 파드마다 API 서버에 미러 파드를 하나씩 만들어 kubectl에도 보이게 해요. 미러 파드 이름 끝에는 하이픈과 노드 이름이 붙습니다. etcd-k8s-master가 그런 이름이에요.

왜 컨트롤 플레인만 이렇게 띄울까요? 다른 방식을 떠올려 보면 답이 나와요. Deployment나 DaemonSet으로 API 서버를 띄우려면 먼저 그 객체를 API 서버에 만들어야 하는데 그 API 서버가 아직 없어요. 공식 문서에도 "정적 파드는 API 서버가 준비되기 전에 kubelet이 띄우므로 컨트롤 플레인 구성 요소를 처음 세우는 데 알맞고, DaemonSet은 돌고 있는 컨트롤 플레인이 있어야 한다"고 적혀 있어요. API 서버 자신은 API 서버 없이 떠야 하므로 파일에서 시작해요.

그림 3. 정적 파드는 파일에서 시작해 API 서버에는 보이기만 하고 나머지 파드는 API 서버에서 시작한다
⚠️ 주의: kubectl delete로는 정적 파드가 지워지지 않아요
미러 파드는 API 서버에서 보이기만 할 뿐, 거기서 제어할 수 없어요. 공식 문서에 따르면 kubectl delete pod로 미러 파드를 지워도 kubelet은 정적 파드를 지우지 않아요. 노드에서 컨테이너를 직접 멈춰도 kubelet이 알아채고 다시 띄웁니다. 정적 파드를 없애려면 그 노드의 /etc/kubernetes/manifests에서 파일을 치워야 해요.

나머지 두 종류는 API 서버를 거쳐 만들어진 파드예요. DaemonSet이 주인인 calico-node와 kube-proxy는 노드 네 대에 하나씩 떠 있었어요.

📖 용어: DaemonSet
조건에 맞는 모든 노드에 같은 파드를 하나씩 띄우는 객체예요. 노드가 새로 들어오면 그 노드에도 파드가 추가되고 노드가 빠지면 그 노드의 파드는 정리돼요. 노드마다 꼭 하나씩 있어야 하는 프로그램(네트워크 도구, 로그 수집기 등)을 띄울 때 씁니다.

DaemonSet이 없다면 워커를 한 대 늘릴 때마다 calico-node와 kube-proxy를 그 노드에 맞춰 따로 띄워야 해요. 실습 도구는 워커를 준비해 클러스터에 조인시킬 뿐, 이 둘을 노드마다 띄우는 일은 하지 않아요. 그 일은 DaemonSet이 합니다. 다만 DaemonSet 파드도 노드 배정은 스케줄러가 맡아요. DaemonSet 컨트롤러가 노드마다 파드를 만들면서 그 노드를 가리키는 조건(nodeAffinity)을 넣고 스케줄러가 그 노드에 배정합니다.

여기서 하나 더 볼 것이 있어요. kubeadm은 init 때 마스터에 node-role.kubernetes.io/control-plane:NoSchedule 표시(taint)를 붙여서 기본적으로 일반 파드가 마스터에 배정되지 않게 해요(5편에서 다뤄요). 그런데 calico-node와 kube-proxy는 마스터에도 떠 있었죠. 두 DaemonSet의 정의에 NoSchedule 표시를 모두 허용하는 설정(toleration)이 들어 있기 때문이에요. 특히 kube-proxy는 kubeadm이 만든 정의에 operator: Exists만 적혀 있어서 어떤 표시든 허용합니다.

ReplicaSet이 주인인 coredns 2개와 calico-kube-controllers 1개는 노드 수와 상관없이 개수가 정해진 파드예요. ReplicaSet(정해 둔 개수만큼 같은 파드를 유지하는 객체예요. 이 둘의 ReplicaSet은 모두 Deployment가 만들었어요)이 개수를 맞추고 어느 노드에 둘지는 스케줄러가 고릅니다. 셋 다 worker1에 있으니 마스터의 taint 때문이라고 짐작하기 쉬워요. 그런데 kubeadm의 CoreDNS 정의와 Calico v3.33.0 매니페스트를 열어 보면 둘 다 컨트롤 플레인 taint를 허용하는 설정이 들어 있어요. 그러니 마스터에 없는 이유를 taint로 단정할 수는 없고 셋이 모두 worker1에 모인 이유는 확인하지 않았습니다.

6. kubelet과 containerd는 이 목록에 없다

15개를 다 보고 나니 처음에 생긴 의문이 남았어요. kubelet과 containerd는 왜 목록에 없을까요? 이 둘은 파드가 아니기 때문이에요. 각 노드에서 systemd(리눅스에서 프로그램을 서비스로 띄우고 관리하는 시스템 프로그램)가 띄우는 서비스입니다. 실습 저장소의 노드 준비 스크립트에서도 systemctl enable kubelet, systemctl restart containerd로 이 둘을 다뤄요.

이 둘을 파드로 띄우지 않는 이유는 5절에서 본 정적 파드의 경우와 같아요. 파드를 띄우는 것이 kubelet이고 파드의 컨테이너를 실제로 실행하는 것이 containerd예요. 둘 중 하나라도 파드라면 그 파드를 띄워 줄 무언가가 먼저 있어야 합니다. 정적 파드는 API 서버 없이도 뜨지만 kubelet과 containerd는 있어야 떠요. 그래서 이 둘은 쿠버네티스 바깥에서 운영체제의 서비스 관리자가 맡아요. 공식 문서에도 리눅스 노드에서는 systemd로 노드의 구성 요소를 관리할 수 있다고 나와 있어요.

그림 4. 노드별로 무엇이 어떻게 떠 있나. kubectl로 보이는 것은 위의 세 층뿐이다

그림 4의 맨 아래 층이 없으면 위의 세 층도 없어요. 반대로 kubectl로 클러스터를 볼 때는 맨 아래 층이 보이지 않습니다. kubectl이 보여 주는 것은 API 서버에 기록된 내용뿐이에요.

💡 실무에서는: 노드 문제는 노드에 들어가서 본다
kubelet이 멈추면 정작 그 사실을 API 서버에 알릴 쪽이 없어요. 그래서 kubectl로 알 수 있는 것은 대개 "노드가 NotReady다"까지예요. 원인은 그 노드에 들어가 systemctl status kubelet, journalctl -u kubelet으로 봅니다. containerd도 같은 방법으로 systemctl status containerd를 봐요. 4편의 swap 실험에서도 kubelet이 뜨지 못한 이유는 kubectl이 아니라 journalctl -u kubelet에 찍힌 running with swap on is not supported 한 줄에 있었어요.
✍️ 오늘의 요약
kube-system의 파드 15개는 정적 파드 4개(컨트롤 플레인), DaemonSet 파드 8개(calico-node, kube-proxy), ReplicaSet 파드 3개(coredns, calico-kube-controllers)였어요. kubelet과 containerd는 파드가 아니라 노드의 systemd 서비스라서 목록에 없었습니다.

구성 요소끼리는 서로를 부르지 않고 API 서버에 쓰고 API 서버를 지켜봐요. etcd에 붙는 것은 API 서버 하나뿐이고 API 서버 자신은 kubelet이 파일을 읽어 띄워요. 각각이 빠지면 무엇이 멈추는지 알아 두면 클러스터가 이상할 때 어디부터 볼지가 정해집니다. 클러스터는 API 서버를 가운데 둔 프로그램 여러 개예요.
