1. 쓰는 사람과 업그레이드하는 사람이 달라서 경고 장치가 생겼다

1.19 전에는 deprecated API를 쓰고 있는지 알려면 릴리스 노트를 읽고 직접 찾아야 했어요. 2020년 4월 16일 liggitt가 작성한 KEP-1693의 Motivation이에요.

Kubernetes has many deprecations in flight at any given moment, in various stages, with various time horizons. Keeping track of all of them is difficult, and has historically required careful reading of release notes, and manually sweeping for use of deprecated features.

→ 진행 중인 deprecation이 늘 여러 개이고 단계와 시한이 제각각이라 따라가기 어려웠고, 지금까지는 릴리스 노트를 꼼꼼히 읽고 직접 뒤지는 수밖에 없었다는 뜻이에요. 같은 해 9월 liggitt는 소개 블로그에 두 가지 관찰을 적었어요. 하나는 "users often don't even realize they are depending on a deprecated API version until they upgrade to the release that stops serving it"이고, 다른 하나는 "the person using a deprecated API is often not the same person responsible for upgrading the cluster"예요. 사용자는 서빙이 끊기는 릴리스로 올라간 날에야 알게 되고, API를 쓰는 사람과 클러스터를 올리는 사람이 다른 경우가 많다는 뜻이에요. 그래서 요청한 사람에게 보이는 경고와 관리자용 도구 두 가지를 함께 넣었어요.

KEP가 정한 서버 쪽 동작은 세 가지예요. deprecated API가 쓰이면 응답에 Warning 헤더를 붙이고, group, version, resource, subresource, 제거 예정 릴리스를 레이블로 단 apiserver_requested_deprecated_apis gauge를 1로 만들고, 감사 이벤트에 "k8s.io/deprecated": "true" annotation을 남겨요. 1.19에 beta로 들어왔고 1.22에 WarningHeader가 GA, 메트릭이 stable이 됐어요. 1.19 CHANGELOG는 제거 예정 릴리스가 정해진 경우 "k8s.io/removal-release" annotation도 붙인다고 적어요.

📖 용어: Warning 헤더
HTTP 응답에 붙는 표준 헤더예요. KEP-1693은 코드 299, warn-agent -로 적게 했어요. 블로그는 이 방식을 고른 이유를 "it does not change the status code or response body in any way ... while remaining compatible with previous client versions"라고 설명해요. 상태 코드와 본문이 그대로라 옛 클라이언트는 헤더를 무시하고 지나가요.

그림 1. 세 장치는 보는 사람과 담는 정보가 서로 달라요.

2. Warning 헤더는 성공 응답에 붙고 kubectl은 stderr로 보여 준다

헤더를 직접 봤어요. 74편의 시험 CRD에서 v1을 deprecated: true로 표시한 뒤 마스터 노드에서 curl로 v1 목록을 요청했어요(labs/devops/k8s-study/out/74-crd-storage-migration-and-deprecation.txt 5절).

응답 헤더 (curl로 직접, 마스터의 admin.conf 인증서 사용): HTTP/2 200 content-type: application/json warning: 299 - "why-api.example.com/v1 Widget is deprecated; use why-api.example.com/v2 Widget"

→ 상태 코드는 200이고 본문도 평소대로 오며 경고는 헤더 한 줄로만 따라온다는 뜻이에요. kubectl로 같은 목록을 읽으면 이 헤더가 Warning:으로 시작하는 줄로 찍혔어요. 1.19 CHANGELOG에 따르면 kubectl은 이 줄을 stderr로 내보내요. v2로 읽을 때는 경고가 없었어요.

내장 API의 문구는 v1.37.2의 deprecation.go가 만들어요. 기본은 <group/version> <Kind> is deprecated in v1.X+이고, 제거 예정 릴리스가 있으면 , unavailable in v1.Y+를, 대체 API가 있으면 ; use ...를 덧붙여요. v1 Endpoints의 경고에는 unavailable 부분이 없어요. GA라서 제거 예정 릴리스가 없기 때문이에요. 원본은 labs/devops/k8s-study/out/75-deprecated-ga-endpoints.txt와 같은 디렉터리의 75-deprecated-ga-endpoints.sh예요.

그림 2. Endpoints 조회에만 경고가 붙었고 --warnings-as-errors를 주면 종료 코드가 1이었어요.

apply 단계에서도 같은 경고가 와요. 73편의 실험에서 v1 Endpoints 매니페스트 하나만 서버 dry-run으로 보냈어요(labs/devops/k8s-study/out/73-old-manifests-dry-run-scan.txt 3절).

$ kubectl apply --dry-run=server -f endpoints.yaml Warning: v1 Endpoints is deprecated in v1.33+; use discovery.k8s.io/v1 EndpointSlice endpoints/legacy-ep created (server dry run) 종료 코드: 0 $ kubectl apply --dry-run=server -f endpoints.yaml --warnings-as-errors Warning: v1 Endpoints is deprecated in v1.33+; use discovery.k8s.io/v1 EndpointSlice endpoints/legacy-ep created (server dry run) error: 1 warning received 종료 코드: 1

→ 서버는 두 번 다 요청을 받아들였고 kubectl이 받은 경고를 오류로 바꿔 종료 코드 1을 냈다는 뜻이에요. 저장하지 않는 dry-run에도 경고가 붙으니 CI에서 매니페스트를 서버 dry-run으로 돌리면 실제로 적용하지 않고도 경고를 모을 수 있어요.

📖 용어: --warnings-as-errors
kubectl이 서버에서 받은 경고를 오류로 취급해 0이 아닌 종료 코드로 끝내게 하는 옵션이에요. 1.19에 들어왔어요. 요청은 서버에서 그대로 처리되고 kubectl의 종료 코드만 달라져요.

경고가 보이는 곳은 요청한 클라이언트뿐이에요. 1.19 CHANGELOG에 따르면 kubectl은 stderr에 찍고 client-go도 기본으로 stderr에 남기지만 클라이언트마다 config.WarningHandler로, 프로세스 전체는 rest.SetDefaultWarningHandler()로 바꿀 수 있어요. KEP-1693은 kube-apiserver와 kube-controller-manager가 경고를 무시하도록 설정한다고 적었고, 블로그는 모든 리소스를 다루는 클라이언트에 경고를 끄는 예제까지 실었어요. 컨트롤러가 deprecated API를 불러도 그 경고가 로그에 남는다고 기대할 수 없다는 뜻이에요. KEP-1693은 내장 어드미션과 admission webhook도 같은 헤더로 경고를 보낼 수 있게 했어요. 33편에서 네임스페이스에 PodSecurity 라벨을 붙일 때 본 Warning: existing pods in namespace ... 줄도 내장 어드미션 플러그인이 보낸 경고예요.

⚠️ CI에 --warnings-as-errors를 걸면 무엇이 걸릴까
• 제거 예정이 없는 영구 deprecated도 걸려요. v1 Endpoints는 1.33부터 조회마다 경고가 오고 "The API will not be removed"인데도 종료 코드가 1이었어요
• deprecated API만 걸리는 것도 아니에요. KEP-1693은 검증, 어드미션, admission webhook도 경고를 보낼 수 있게 했어요. 어떤 경고든 실패로 바뀌어요
• 업그레이드를 막을 경고만 고르고 싶다면 경고 문구의 unavailable in v1.Y+나 아래 메트릭의 removed_release로 거르는 편이 맞아요

3. apiserver_requested_deprecated_apis는 무엇이 불렸는지만 알려 주고 지운 리소스의 줄도 1로 남아 있었다

관리자용 첫 번째 도구는 메트릭이에요. 블로그의 설명은 "when a request is made to a deprecated REST API endpoint, an apiserver_requested_deprecated_apis gauge metric is set to 1 in the kube-apiserver process"예요. 요청이 한 번이라도 오면 그 API 서버 프로세스 안에서 해당 레이블 조합의 값이 1이 된다는 뜻이에요.

📖 용어: gauge
Prometheus 지표 종류 가운데 올라가고 내려갈 수 있는 현재값이에요. apiserver_requested_deprecated_apis는 요청 횟수를 세지 않고 "불린 적이 있다"를 1로 표시해요. 횟수는 apiserver_request_total에서 봐야 해요.

우리 API 서버의 값이에요. 75-deprecated-ga-endpoints.txt 3절의 두 줄이에요.

apiserver_requested_deprecated_apis{group="",removed_release="",resource="endpoints",subresource="",version="v1"} 1 apiserver_requested_deprecated_apis{group="why-api.example.com",removed_release="",resource="widgets",subresource="",version="v1"} 1

endpoints 줄은 core 그룹(group이 빈 값)의 v1 Endpoints예요. removed_release가 비어 있어요. GA는 major 버전 안에서 지우지 않는다는 73편의 규칙과 맞아요. widgets 줄은 74편의 시험 CRD예요. 이 CRD는 21:14에 지웠는데 21:15의 측정에도, 약 30분 뒤인 21:43의 측정에도 남아 있었어요. 21:43에 확인한 kube-apiserver의 process_start_time_seconds는 19:58:25였어요(73-old-manifests-dry-run-scan.txt 4절). 한 번 1이 된 줄은 리소스를 지우고 30분 가까이 지나도 같은 API 서버 프로세스 안에서 그대로 남아 있었어요. 이것은 관측 결과예요. 재시작할 때까지 계속 남는지는 관측 범위를 넘고 코드로도 확인하지 않았어요.

그림 3. gauge는 그 프로세스가 뜬 뒤 한 번이라도 불렸는지를 보여 줬어요.

이 성질에서 두 가지가 따라와요. 하나는 관찰 기간이에요. 1이 된 줄은 그 API 서버 프로세스가 뜬 뒤의 기록이라서 재시작 직후에 보면 드물게 도는 작업이 부른 API는 아직 줄이 없을 수 있어요. 다른 하나는 API 서버가 여러 대일 때예요. 값은 프로세스마다 따로 있으니 각 API 서버의 /metrics를 모두 봐야 해요. 우리 클러스터는 마스터가 한 대라 한 곳만 봤어요.

몇 번 불렸는지는 같은 group, version, resource의 apiserver_request_total로 봐요. 블로그가 소개한 방법대로 두 지표를 묶었어요.

그림 4. 무엇을 어떤 동사로 몇 번 불렀는지는 보이지만 누가 불렀는지는 없어요.

core/v1/endpoints는 GET 470번, PUT 34번, WATCH 11번 등이었어요. 이 값은 프로세스가 뜬 뒤의 누적값이라 측정할 때마다 달라요. 우리가 친 kubectl get endpoints도 그 GET에 들어 있어요. 나머지를 누가 보냈는지는 이 지표로 알 수 없어요. 레이블에 클라이언트를 가리키는 값이 없기 때문이에요.

💡 다음 업그레이드에서 사라질 것만 고르는 질의
블로그는 removed_release로 거른 뒤 요청 수와 묶는 PromQL을 소개해요. 아래는 1.22 기준 예시예요.
apiserver_requested_deprecated_apis{removed_release="1.22"} * on(group,version,resource,subresource) group_right() apiserver_request_total
removed_release가 비어 있는 줄은 v1 Endpoints처럼 제거 예정이 없는 deprecated예요. 업그레이드를 막지는 않지만 대체 API로 옮길 대상이에요.

4. 요청한 주체는 감사 로그의 k8s.io/deprecated annotation으로 찾는다

남은 질문은 "누가"예요. 블로그는 메트릭의 한계를 이렇게 적어요.

Metrics are a fast way to check whether deprecated APIs are being used, and at what rate, but they don't include enough information to identify particular clients or API objects. Starting in Kubernetes v1.19, audit events for requests to deprecated APIs include an audit annotation of "k8s.io/deprecated":"true". Administrators can use those audit events to identify specific clients or objects that need to be updated.

→ 메트릭으로는 쓰이는지와 얼마나 자주인지만 알 수 있고, 특정 클라이언트나 객체를 찾으려면 이 annotation이 붙은 감사 이벤트를 봐야 한다는 뜻이에요. KEP-1693의 목표에도 "Allow a cluster administrator to programatically identify particular clients using deprecated APIs"가 있어요.

📖 용어: 감사 로그(audit log)
API 서버가 받은 요청을 정책에 따라 이벤트로 남기는 기록이에요. 요청한 사용자와 대상 객체가 이벤트에 함께 남아서 메트릭이 못 하는 "누가"를 답해요. 정책 파일을 주지 않으면 이벤트가 남지 않아요.

우리 API 서버는 --audit-policy-file 플래그 수가 0이었어요. 36편에서 인용한 감사 문서는 이 플래그가 없으면 이벤트를 남기지 않는다고 적어요. 그래서 우리 클러스터에서 v1 Endpoints를 GET 470번 부른 주체는 지금 찾을 수 없어요. 감사 로그를 켜는 것은 API 서버 설정을 바꾸는 일이라 이 실습에서는 하지 않았어요. 문서 기준의 순서만 적어요.

💡 감사 로그로 호출자를 찾는 순서 (문서 기준, 이 클러스터에서는 실행하지 않음)
• 감사 정책 파일을 만들어요. 감사 문서의 정책 예시처럼 요청 본문까지 남기지 않는 Metadata 수준으로 시작하면 기록량을 줄일 수 있어요
• kube-apiserver 정적 파드 매니페스트에 --audit-policy-file과 --audit-log-path를 넣고, 36편에서 본 대로 정책 파일과 로그 위치를 hostPath로 마운트해요
• 쌓인 이벤트에서 "k8s.io/deprecated":"true"가 붙은 것만 골라 요청한 사용자와 대상 객체를 봐요. 제거 예정이 정해진 API면 "k8s.io/removal-release"도 함께 붙어요
• 이행 가이드의 "Locate use of deprecated APIs" 절도 경고, 메트릭, 감사 정보를 함께 쓰라고 안내해요

5. 업그레이드 전 점검은 매니페스트, 실행 중인 요청, 요청한 주체 순서로 좁힌다

지금까지 본 도구를 한 표로 모았어요. 각 도구가 답하는 질문이 달라서 하나만으로는 부족해요.

업그레이드 전 순서로 정리하면 이래요. 먼저 올라갈 릴리스의 이행 가이드 항목과 CHANGELOG를 보고 손에 있는 매니페스트와 차트를 서버 dry-run으로 돌려요. 그다음 각 API 서버의 apiserver_requested_deprecated_apis에서 올라갈 릴리스와 같은 removed_release를 가진 줄을 찾고 apiserver_request_total로 얼마나 쓰이는지 봐요. 줄이 있으면 감사 이벤트에서 k8s.io/deprecated가 붙은 요청의 주체를 찾아 그 도구를 고쳐요. 이행 가이드는 API 서버에 --runtime-config=<group>/<version>=false를 줘서 빠질 버전을 미리 꺼 보는 시험도 안내해요. 이것도 API 서버 설정을 바꾸는 일이라 이번 실습에서는 하지 않았어요.

v1 Endpoints처럼 removed_release가 빈 줄은 업그레이드를 막지 않아요. 그래도 1.33 CHANGELOG가 "all users should use the EndpointSlice API instead"라고 적었으니 고칠 수 있는 클라이언트는 EndpointSlice로 옮기는 편이 맞아요. 다만 우리 클러스터에서 v1 Endpoints를 부르는 주체가 누구인지는 감사 로그가 없어서 확인하지 못했어요.

📝 정리

deprecated API를 부르면 서버는 요청을 그대로 처리하고 세 곳에 흔적을 남겨요. 요청한 클라이언트에게는 Warning 헤더가 가고, API 서버 프로세스에는 apiserver_requested_deprecated_apis가 1로 남고, 감사 로그가 켜져 있으면 k8s.io/deprecated annotation이 붙은 이벤트가 남아요. v1.37.2에서 v1 Endpoints는 조회마다 경고를 받았고 removed_release는 비어 있었어요.

메트릭은 무엇이 몇 번 불렸는지만 알려 줘요. 지운 CRD의 줄도 30분 가까이 1로 남아 있었고, GET 470번을 누가 보냈는지는 감사 로그가 없는 우리 클러스터에서 찾을 수 없었어요.

업그레이드 전에는 매니페스트를 서버 dry-run으로, 실행 중인 요청을 removed_release로 거른 메트릭으로, 요청한 주체를 감사 로그로 좁혀 가요. CI의 --warnings-as-errors는 제거 예정이 없는 경고에도 실패하니 막을 경고를 골라 거는 편이 맞아요.
