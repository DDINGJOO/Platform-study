20시 59분, etcd 파드 안에서 스냅숏을 뜨려고 예전 버전 기준으로 적힌 백업 명령을 그대로 쳤어요. kubectl exec etcd-k8s-master -- sh -c "ETCDCTL_API=3 etcdctl … snapshot save …" 모양의 명령이에요. 돌아온 것은 스냅숏이 아니라 이 줄이었어요.

OCI runtime exec failed: exec failed: unable to start container process: exec: "sh": executable file not found in $PATH

→ etcd 컨테이너 안에 sh라는 실행 파일이 없어서 명령을 시작하지도 못했다는 뜻이에요. 이어서 친 etcdctl snapshot restore도 복원은 하지 않고 도움말만 보여 줬어요.

바로 1분 전에는 제가 남긴 메모 "etcd 주기적 백업을 크론잡으로 돌리기도 한대"를 따라 CronJob으로 스냅숏을 한 번 떠 본 참이었어요. 스냅숏 저장은 성공했는데 되살리는 방법은 버전이 바뀌면서 달라져 있었던 거예요. 그래서 한 시간 뒤에 실제로 되살려 봤어요. 21:57:04에 ConfigMap before-snapshot을 만들고 스냅숏을 뜬 다음 ConfigMap after-snapshot을 하나 더 만들었어요. etcdutl로 복원하고 나니 after-snapshot은 사라졌고 etcd 리비전은 180005에서 1000180017이 돼 있었어요.

22편에서는 etcd 백업이 곧 API 객체로 관리하는 클러스터 상태의 백업이고 스냅숏 파일에 Secret이 평문으로 들어간다는 것을 봤어요. 이번 글에서는 그다음 질문인 "etcd 3.7에서는 어떤 명령으로 뜨고 어떤 순서로 되살리나"에 답해요. 클러스터는 Lima VM 4대에 kubeadm v1.37.2로 만든 실습 환경이고 etcd는 마스터 한 대에 멤버 하나로 떠 있어요(21편). etcd 이미지는 registry.k8s.io/etcd:3.7.0-0이에요.

· 예전 버전의 백업·복원 명령은 etcd 3.7에서 어디가 막힐까?

· 스냅숏으로 되살리면 클러스터는 정말 그 시점으로 돌아갈까? 어떤 순서로 해야 할까?
· 복원할 때 리비전을 10억이나 올리는 이유는 무엇일까?

1. 예전 백업 명령은 etcd 3.7에서 세 군데가 막힌다

20:59:35에 같은 etcd 파드에서 예전 형태와 지금 형태를 차례로 실행했어요. 운영 데이터는 건드리지 않으려고 스냅숏과 복원 결과는 모두 임시 경로에 두었다가 확인한 뒤 지웠어요.

그림 1. 셸로 감싼 명령은 시작도 못 했고 etcdctl을 바로 부르자 스냅숏이 저장됐다. 파일을 연 도구는 etcdutl이다

위에서부터 읽으면 이래요. sh -c로 감싼 명령은 컨테이너 안에서 sh를 찾지 못해 실패했어요. 같은 인증서 옵션으로 etcdctl을 바로 실행하자 Snapshot saved at /var/lib/etcd/snapshot.db가 나왔어요. 그 파일을 etcdutl로 열어 보니 리비전 143014, 키 514개, 크기 3.1 MB였어요. 예전 명령에서 달라진 곳은 세 군데예요.

이미지에 셸이 없다

예전 명령이 sh -c로 감싼 것은 컨테이너 안에서 ETCDCTL_API=3이라는 환경 변수를 붙여 etcdctl을 실행하려는 것이었어요. 그런데 지금 etcd 이미지에는 그 sh가 없어요. 마스터에서 이미지가 어떤 층으로 만들어졌는지 보면 바로 보여요.

# 40-restore-aftermath.txt 발췌 (마스터에서 crictl inspecti 로 본 이미지 history 의 끝부분) bazel build //common:cacerts_debian12_arm64 ADD etcd /usr/local/bin/ # buildkit ADD etcdctl /usr/local/bin/ # buildkit ADD etcdutl /usr/local/bin/ # buildkit WORKDIR /var/etcd/ WORKDIR /var/lib/etcd/ EXPOSE [2379/tcp 2380/tcp] CMD ["/usr/local/bin/etcd"]

→ 앞의 bazel build 줄 12개는 기본 이미지(distroless)가 만들어진 기록이고 그 위에 etcd, etcdctl, etcdutl 세 실행 파일만 얹었다는 뜻이에요. etcd 저장소 v3.7.0의 Dockerfile도 gcr.io/distroless/static-debian12 위에 같은 세 파일을 ADD하고 WORKDIR 두 줄, EXPOSE, CMD를 같은 순서로 둬요.

📖 용어: distroless 이미지
셸, 패키지 관리자 같은 운영체제 도구를 빼고 프로그램 실행에 필요한 파일만 담은 컨테이너 기본 이미지예요(GoogleContainerTools/distroless). 이런 이미지로 만든 컨테이너에는 kubectl exec 명령으로 sh나 ls를 부를 수 없고 이미지에 들어 있는 실행 파일만 이름으로 바로 실행할 수 있어요.

예전 이미지에는 셸이 있었어요. registry.k8s.io/etcd 이미지는 예전에 쿠버네티스 저장소의 빌드 파일로 만들었는데 v1.30.0 저장소의 cluster/images/etcd/Dockerfile을 보면 빌드 단계에서 bash-static을 설치해 /sh로 복사하고 실행 이미지의 /bin/ 아래에 넣어요. 이 빌드 코드는 2025년 12월 PR #135824에서 지워졌고 PR 설명에는 "Official `etcd` images are used instead."라고 적혀 있어요. 이제는 etcd 프로젝트가 낸 공식 이미지를 쓴다는 뜻이고 우리 3.7.0-0 이미지의 층도 위의 Dockerfile과 같았어요. 셸이 없으니 kubectl exec 명령 뒤에는 etcdctl을 바로 적어야 해요.

ETCDCTL_API=3은 3.4부터 기본값이다

ETCDCTL_API는 etcdctl에게 v2와 v3 가운데 어느 API를 쓸지 알려 주는 환경 변수예요. etcd 3.4 변경 기록의 v3.4.0(2019-08-30) 항목에 "Make `ETCDCTL_API=3 etcdctl` default"가 있고 이제 ETCDCTL_API=3 etcdctl put foo bar를 etcdctl put foo bar로 써도 된다는 설명이 붙어 있어요. 쿠버네티스의 etcd 운영 문서 예시에는 아직 ETCDCTL_API=3이 붙어 있지만 3.4 이상에서는 빼도 같은 명령이에요. 환경 변수를 붙일 일이 없으니 셸로 감쌀 이유도 사라져요. 그림 1의 2번에서 한 대로 etcdctl을 바로 실행하면 돼요.

복원은 etcdctl이 아니라 etcdutl이 한다

그림 1의 3번에서 스냅숏 파일을 연 도구는 etcdutl이었어요. 복원도 etcdutl의 일이에요. etcdctl 3.7.0의 snapshot 아래 하위 명령은 save 하나뿐이었고 etcdctl snapshot restore를 실행하자 복원은 하지 않고 snapshot 명령의 도움말(Manages etcd node snapshots)만 나왔어요.

📖 용어: etcdctl과 etcdutl
쿠버네티스의 etcd 운영 문서(Operating etcd clusters for Kubernetes)는 둘을 이렇게 나눠요. etcdctl은 네트워크로 etcd 클러스터와 주고받는 기본 클라이언트이고 키와 값 관리, 클러스터 관리, 상태 확인 같은 일상 작업에 써요. etcdutl은 etcd 데이터 파일을 직접 다루는 관리 도구이고 버전 사이의 데이터 이전, 조각 모음, 스냅숏 복원, 데이터 일관성 확인을 해요. 네트워크 작업에는 etcdctl을 쓰라고 적혀 있어요.
그림 2. 스냅숏을 뜨는 일은 돌고 있는 서버에 요청하는 일이라 etcdctl이, 복원은 새 data-dir을 만드는 일이라 etcdutl이 한다

이 분담은 한 번에 생기지 않았어요. etcd 변경 기록과 쿠버네티스 저장소를 시간순으로 놓으면 이래요.

버전 (날짜)바뀐 것예전 명령에 생긴 일
etcd v3.4.0 (2019-08-30)etcdctl이 기본으로 v3 API를 쓰게 됐다ETCDCTL_API=3을 빼도 된다
etcd v3.5.0 (2021-06)새 도구 etcdutl이 etcdctl snapshot status·restore, etcdctl backup, etcdctl defrag --data-dir의 기능을 넘겨받았다etcdctl로 하는 복원은 deprecated
etcd v3.5.10 (2023-10-27)etcdutl snapshot restore에 --bump-revision과 --mark-compacted가 생겼다4절에서 쓰는 옵션
etcd v3.6.0 (2025-05-15)etcdctl snapshot status와 snapshot restore를 지웠다etcdctl snapshot restore가 도움말만 낸다
쿠버네티스 PR #135824 (2025-12)registry.k8s.io/etcd를 만들던 빌드 코드를 지우고 etcd 공식 이미지를 쓴다이미지에 sh가 없다(우리 3.7.0-0에서 확인)
etcd v3.7.0 (2026-07-08)우리 클러스터가 쓰는 버전etcdctl snapshot 아래에는 save만 있다

출처는 etcd의 3.5 변경 기록, 3.6 변경 기록, 3.7 변경 기록이에요. 쿠버네티스 문서의 복원 절도 같은 내용을 탭 두 개로 나눠 보여 줘요. etcdutl 탭이 앞에 있고 etcdctl 탭에는 etcdctl로 하는 복원이 etcd v3.5.x부터 deprecated 상태이고 v3.6에서 지울 예정이라는 주의가 붙어 있어요. etcd v3.6 재해 복구 문서는 마지막 문단에서 v3.6부터는 etcdctl로 스냅숏을 뜨기만 하고 스냅숏에서 되살리는 일은 etcdutl로 한다고 정리해요. etcd 3.7에서 스냅숏은 etcdctl snapshot save로 뜨고 되살리는 일은 etcdutl snapshot restore로 해요.

⚠️ 주의: 돌고 있는 etcd 파드 안에서 restore만 하면 클러스터는 그대로예요
• etcdutl snapshot restore는 지금 쓰는 데이터를 바꾸지 않고 새 data-dir을 만들어요. etcd 복구 문서에 따르면 --data-dir을 주지 않으면 <name>.etcd가 생기고 v3.7.0 소스(snapshot_command.go)의 기본 이름은 default라서 현재 폴더에 default.etcd가 생겨요. 우리 이미지의 작업 폴더(WORKDIR)는 /var/lib/etcd/라서 kubectl exec 명령으로 실행하면 그 아래에 폴더 하나가 더 생길 것으로 보여요
• 실제로 되돌리려면 API 서버를 멈추고 etcd가 그 새 폴더를 쓰게 바꿔야 해요. 3절에서 그 순서대로 해 봐요
• 스냅숏을 /var/lib/etcd 아래에 두면 etcd 데이터와 같은 디스크에 있어서 그 디스크를 잃을 때 함께 잃어요. 그림 1의 스냅숏은 확인한 뒤 바로 지웠어요

2. CronJob으로 6시간마다 스냅숏을 뜨게 했다

제가 남긴 메모 중에 "etcd 주기적 백업을 크론잡으로 돌리기도 한대"가 있어요. 쿠버네티스 문서도 모든 컨트롤 플레인 노드를 잃는 재해에서 클러스터를 되살리려면 etcd 데이터를 주기적으로 백업하는 것이 중요하다고 해요. 그래서 1절의 스냅숏 명령을 CronJob에 넣어 봤어요. 매니페스트의 핵심은 이래요.

# 40-etcd-backup-cronjob.yaml 발췌 (Job 기록 개수, backoffLimit 줄은 뺐다) apiVersion: batch/v1 kind: CronJob metadata: {name: etcd-backup, namespace: kube-system} spec: schedule: "0 */6 * * *" # 6시간마다 concurrencyPolicy: Forbid jobTemplate: spec: template: spec: restartPolicy: Never hostNetwork: true nodeSelector: {node-role.kubernetes.io/control-plane: ""} tolerations: [{key: node-role.kubernetes.io/control-plane, operator: Exists, effect: NoSchedule}] containers: - name: snapshot image: registry.k8s.io/etcd:3.7.0-0 # 마스터에 이미 있는 이미지(etcdctl 포함) command: ["etcdctl","--endpoints=https://127.0.0.1:2379", "--cacert=/pki/ca.crt","--cert=/pki/server.crt","--key=/pki/server.key", "snapshot","save","/backup/etcd-snapshot.db"] volumeMounts: - {name: pki, mountPath: /pki, readOnly: true} - {name: backup, mountPath: /backup} volumes: - {name: pki, hostPath: {path: /etc/kubernetes/pki/etcd, type: Directory}} - {name: backup, hostPath: {path: /var/backups/etcd, type: DirectoryOrCreate}}

· hostNetwork: true etcd는 127.0.0.1:2379와 192.168.104.1:2379에서 요청을 받아요(etcd.yaml의 --listen-client-urls). 노드의 네트워크를 그대로 쓰면 Job 파드 안에서도 127.0.0.1:2379로 붙을 수 있어요.
· nodeSelector와 tolerations Job 파드에서 127.0.0.1로 마스터의 etcd에 접속할 수 있어야 하니 control-plane 라벨로 마스터를 고르고 마스터의 NoSchedule taint를 견디게 했어요(37편).
· command 이미지에 셸이 없으니 1절에서 성공한 etcdctl 명령을 그대로 배열로 적었어요.
· 볼륨 두 개 etcd 인증서 폴더는 읽기 전용으로, 백업을 쓸 마스터의 /var/backups/etcd는 쓰기용으로 붙였어요.
· concurrencyPolicy: Forbid CronJob 문서에 따르면 앞 Job이 끝나지 않았을 때 다음 차례가 오면 새 Job을 건너뛰어요. 스냅숏 두 개가 같은 파일에 동시에 쓰는 일을 막아요.

6시간을 기다릴 수 없어서 kubectl -n kube-system create job --from=cronjob/etcd-backup etcd-backup-now로 한 번 바로 돌렸어요.

그림 3. CronJob에서 만든 Job이 Complete 1/1로 끝났고 마스터에 root만 읽는 스냅숏 파일이 생겼다

Job은 Complete 1/1로 끝났고 로그에는 Snapshot saved at /backup/etcd-snapshot.db와 Server version 3.7.0이 찍혔어요. 마스터의 /var/backups/etcd에는 etcd-snapshot.db가 3,080,224바이트, -rw------- root 권한으로 생겼어요. 스냅숏에는 Secret이 평문으로 들어 있으니(22편) 확인한 뒤 CronJob, Job, 파일을 모두 지웠어요.

돌아가기는 하지만 이 매니페스트 그대로 운영에 쓰기에는 빈 곳이 있어요. 백업 파일이 etcd와 같은 마스터 디스크에만 있으면 마스터를 잃을 때 백업도 함께 잃어요.

💡 실무에서는: CronJob 백업에 더 챙길 것
• 파일 이름이 늘 etcd-snapshot.db라서 6시간마다 앞의 백업을 덮어써요. 이름에 시각을 붙이려면 이름을 만들 셸이 있어야 하는데 etcd 이미지에는 없어요. 셸이 있는 이미지에 etcdctl을 넣어 쓰거나 앞 단계 컨테이너에서 만든 이름을 넘겨줘야 해요
• 백업이 etcd와 같은 마스터 디스크에 있어요. 문서가 백업이 필요한 경우로 든 "컨트롤 플레인 노드를 모두 잃는 재해"에서는 백업도 함께 사라져요. 노드 밖 저장소로 옮기고 몇 개를 남길지 정해 오래된 것은 지워요
• 쿠버네티스 문서는 스냅숏 파일을 암호화하라고 해요. 22편에서 본 대로 Secret 원문이 들어 있어요
• /etc/kubernetes/pki/etcd 폴더를 통째로 붙이면 ca.key, peer.key까지 컨테이너에서 보여요. etcd CA 키가 있으면 etcd가 믿는 인증서를 새로 만들 수 있으니 필요한 인증서 파일만 붙이는 편이 좋아요
• 뜬 스냅숏은 etcdutl snapshot status로 리비전과 해시를 확인하고 3절에서 한 대로 실제로 되살려 보는 연습을 해 둬요

쿠버네티스 문서는 이 밖에 두 방법을 더 들어요. etcd 프로세스가 쓰지 않는 data-dir에서 member/snap/db 파일을 복사하는 방법과 백업을 지원하는 저장 볼륨(문서의 예는 Amazon EBS)에 etcd를 두고 볼륨 스냅숏을 뜨는 방법이에요. etcd 복구 문서에는 member/snap/db를 복사한 파일에 대한 주의가 두 가지 있어요. WAL(쓰기 로그)에는 있지만 아직 db 파일에 쓰이지 않은 데이터를 잃을 수 있고 무결성 해시가 없어서 복원할 때 --skip-hash-check를 줘야 한다고 해요. etcdctl snapshot save로 뜬 파일에는 해시가 들어 있어서 etcdutl이 복원할 때 확인해요.

3. 스냅숏 앞뒤에 표식을 두고 실제로 되살려 봤다

백업이 쓸모 있는지는 되살려 봐야 알 수 있어요. 21:57:04부터 마스터의 etcd를 실제로 스냅숏으로 되돌렸어요. 되돌아갔는지 눈으로 확인하려고 표식 두 개를 썼어요. 스냅숏 바로 앞에 ConfigMap before-snapshot을, 바로 뒤에 after-snapshot을 만들었어요. 복원이 제대로 됐다면 before-snapshot만 남아야 해요.

그림 4. 스냅숏은 리비전 180003에서 떴고 after-snapshot은 그 뒤 180005까지의 쓰기로 만들어졌다

스냅숏은 리비전 180003, 키 676개, 크기 29 MB였어요. after-snapshot을 만들고 라벨을 붙이는 두 번의 쓰기로 리비전은 180005가 됐어요. 38편에서 본 대로 etcd는 데이터를 바꾸는 트랜잭션이 성공할 때마다 리비전을 하나씩 올려요. 한 트랜잭션에서 여러 키를 바꿔도 리비전은 한 번만 올라요.

복원 순서는 쿠버네티스 문서의 "Restoring an etcd cluster" 절을 따랐어요. 그 절은 주의 문구로 시작해요. API 서버가 하나라도 떠 있으면 etcd 인스턴스를 복원하려 하지 말고 모든 API 서버를 멈추고 모든 etcd 인스턴스의 상태를 복원한 다음 모든 API 서버를 다시 시작하라고 해요. kube-scheduler, kube-controller-manager, kubelet도 다시 시작해 옛 데이터에 기대지 않게 하라는 권고와 복원하는 동안 중요한 구성 요소들이 리더 잠금을 잃고 스스로 재시작한다는 설명이 이어져요. 22편에서 이 문구를 소개만 했는데 이번에는 그 일이 실제로 일어나는지 봤어요.

API 서버부터 멈추라는 이유를 저는 이렇게 이해했어요. API 서버는 etcd 앞에서 watch 캐시를 들고 있고(39편) 그 캐시에는 스냅숏 뒤의 상태까지 들어 있어요. API 서버가 뜬 채로 etcd만 바뀌면 캐시와 etcd가 서로 다른 상태를 갖게 되고 복원 도중에 들어온 쓰기는 어느 쪽에 남을지 알 수 없어요.

📖 용어: data-dir과 멤버 정보
etcd가 데이터를 쓰는 폴더예요. 우리 etcd.yaml에는 --data-dir=/var/lib/etcd로 적혀 있고 그 아래에 member/snap/db(bbolt 파일, 38편)와 member/wal(쓰기 로그)이 있어요. 이 폴더에는 키와 값만이 아니라 "이 클러스터의 멤버는 누구이고 피어 주소는 무엇인가"라는 멤버 정보도 함께 들어가요. etcd 복구 문서는 복원이 이 멤버 정보를 새로 써서 새 논리 클러스터로 시작한다고 설명해요.

실제 순서와 시각은 이래요.

· 21:57:05 마스터에서 kube-apiserver.yaml을 /etc/kubernetes/manifests 밖으로 옮겼어요. 20편과 같은 방법으로 정적 파드를 내리는 거예요. 컨테이너가 0개가 되기까지 30초가 걸렸어요(21:57:35).
· 21:57:35 노드에서 crictl exec 명령으로 etcd 컨테이너 안의 etcdutl을 불러 스냅숏을 /var/lib/etcd/restored에 복원했어요. API 서버가 없으니 kubectl exec 명령은 쓸 수 없고 마스터 노드에는 etcdutl도 etcdctl도 설치돼 있지 않아서 이미지에 든 것을 썼어요. 복원은 1초 안에 끝났어요.
· 21:57:35 복원된 폴더를 노드의 /var/lib/etcd-restored로 옮기고 etcd.yaml에서 etcd-data 볼륨의 hostPath만 /var/lib/etcd에서 /var/lib/etcd-restored로 바꾼 뒤 kubelet을 재시작했어요.
· 21:57:48 새 etcd 컨테이너가 healthy가 되자 API 서버 매니페스트를 제자리에 돌려놓았어요.
· 21:57:50 API 서버의 /readyz가 ok를 돌려줬어요.

그림 5. etcdutl이 새 data-dir을 만들었고 etcd.yaml에서는 hostPath 한 줄만 바뀌었다

복원 명령의 옵션 값은 모두 etcd.yaml에서 옮겨 왔어요. 리허설 뒤에 다시 확인한 etcd.yaml의 해당 줄이에요.

# 40-restore-aftermath.txt 발췌 (마스터의 /etc/kubernetes/manifests/etcd.yaml) 18: - --data-dir=/var/lib/etcd 20: - --initial-advertise-peer-urls=https://192.168.104.1:2380 21: - --initial-cluster=k8s-master=https://192.168.104.1:2380 26: - --name=k8s-master 91: path: /var/lib/etcd --initial-cluster-token 줄 수: 0

· --name, --initial-cluster, --initial-advertise-peer-urls 복원본에 적힐 멤버 정보예요. 빼면 etcdutl 기본값인 이름 default, 피어 주소 http://localhost:2380으로 적혀요(v3.7.0 snapshot_command.go). etcd.yaml이 말하는 멤버(k8s-master, https://192.168.104.1:2380)와 같게 맞췄어요.
· --data-dir 새로 만들 폴더예요. 쿠버네티스 문서는 이 폴더가 복원하면서 만들어진다고 하고 예전과 같은 폴더에 복원하려면 그 폴더를 지우고 etcd 프로세스를 멈춘 뒤 복원하라고 해요. 원래 데이터를 남겨 두려고 다른 폴더를 골랐어요.
· --bump-revision 1000000000 --mark-compacted 리비전을 10억 올리고 그 지점까지를 컴팩션된 것으로 표시하는 옵션이에요. 이유는 4절에서 따로 봐요.

etcd.yaml에서 바뀐 것은 91번째 줄 하나예요. 컨테이너 안에서 보는 경로(mountPath)와 --data-dir은 그대로 /var/lib/etcd이고 그 자리에 붙는 노드 폴더만 /var/lib/etcd-restored로 바뀌었어요. 쿠버네티스 문서가 다른 폴더로 복원했을 때 안내하는 방법과 같아요. 문서는 그다음 etcd 파드를 kubectl delete로 지우거나 kubelet을 재시작하라고 하는데 API 서버가 꺼져 있어서 kubelet을 재시작했어요.

kubelet 재시작(21:57:35)부터 새 etcd가 healthy(21:57:48)가 되기까지 13초가 걸렸어요. 마스터의 containerd 기록을 보면 그사이에 이런 일이 있었어요.

그림 6. API 서버 매니페스트를 뺀 21:57:05부터 /readyz가 성공한 21:57:50까지 약 45초 걸렸고 etcd는 그사이에 바뀌었다

API 서버가 돌아온 21:57:50부터 확인한 결과예요.

그림 7. after-snapshot은 사라졌고 리비전은 10억 넘게 뛰었다. 컨트롤러 매니저와 스케줄러는 한 번씩 재시작했다

표식은 before-snapshot만 남았어요. 스냅숏 뒤에 만든 after-snapshot은 클러스터에서 사라졌어요. 클러스터의 상태가 21:57:04의 스냅숏 시점으로 돌아갔다는 뜻이에요. 리비전은 1000180017이었어요. --bump-revision으로 더한 10억 때문이에요. 21:58:10에는 노드 네 대가 모두 Ready였어요. Running이 아닌 파드가 1개 있었는데 약 1분 뒤(21:59:08)에는 0개였어요.

재시작 수도 바뀌었어요. 컨트롤러 매니저와 스케줄러가 1에서 2로 하나씩 늘었어요. 문서가 말한 "리더 잠금을 잃고 스스로 재시작"이 실제로 일어난 거예요. 마스터에 남은 로그를 보면 이래요.

# 40-restore-aftermath.txt 발췌 (마스터 /var/log/pods, KST) [kube-scheduler 1.log 끝] 21:57:17.140 leaderelection.go:304] "Failed to renew lease" lock="kube-system/kube-scheduler" err="context deadline exceeded" 21:57:17.141 server.go:337] "Leaderelection lost" [kube-controller-manager 2.log: 21:57:17 에 새로 시작한 컨테이너] 21:57:17.941 leaderelection.go:258] "Attempting to acquire leader lease..." lock="kube-system/kube-controller-manager" 21:58:08.567 leaderelection.go:272] "Successfully acquired lease" lock="kube-system/kube-controller-manager"

→ 스케줄러는 21:57:17에 Lease를 갱신하지 못해 리더 자리를 잃고 프로세스를 끝냈다는 뜻이에요. 리더는 갱신 기한 안에 Lease를 갱신하지 못하면 리더 자리를 내놓아요. v1.37.2의 리더 선출 기본값은 Lease 기간 15초, 갱신 기한 10초, 재시도 간격 2초예요(component-base defaults.go). 스케줄러는 API 서버를 내린 구간에 Lease 갱신에 실패했고 21:57:17에 리더 자리를 잃었어요. 매니페스트를 뺀 시각은 21:57:05, API 서버의 /readyz가 다시 성공한 시각은 21:57:50이었어요. 컨트롤러 매니저도 같은 시각에 새 컨테이너로 다시 떴고 API 서버가 돌아온 뒤 21:58:08에 Lease를 다시 얻었어요. 돌아온 Lease에는 스냅숏 시점의 옛 리더 기록이 들어 있었고 새 프로세스는 그 기록이 Lease 기간 동안 갱신되지 않는 것을 확인한 뒤 가져간 것으로 보여요. 그래서 API 서버가 돌아오고도 18초 동안 컨트롤러가 일하지 않았어요(컨트롤러 매니저가 없을 때의 모습은 20편). 스케줄러는 리허설 마지막 단계에서 API 서버를 한 번 더 내렸다 올린 뒤인 21:59:22에 리더가 됐어요.

복원한 멤버의 ID는 바뀌지 않았다

etcd 복구 문서에는 복원이 스냅숏 메타데이터 가운데 멤버 ID와 클러스터 ID를 덮어써서 멤버가 예전 정체성을 잃는다고 적혀 있어요. 새 멤버가 실수로 기존 클러스터에 끼어드는 것을 막기 위해서라고 해요. 그런데 복원 뒤의 멤버 ID는 c960bb57b7d36fea로 복원 전과 같았어요.

# 40-restore-aftermath.txt 발췌 복원 전 (shared/arch-exp/e6-etcd-ssot.txt, 15:17): ID=c960bb57b7d36fea RAFT_TERM=9 RAFT_INDEX=143152 지금: member_id=c960bb57b7d36fea cluster_id=3e50550e6ebc5cfd raftTerm=3 raftIndex=2436 revision=1000181854 계산: sha1(peer URL + 토큰 etcd-cluster) 앞 8바이트 = c960bb57b7d36fea, sha1(멤버 ID) 앞 8바이트 = 3e50550e6ebc5cfd

→ 이유는 ID를 만드는 방식에 있어요. etcd v3.7.0 member.go의 computeMemberID는 피어 URL과 클러스터 토큰을 이어 붙인 바이트의 SHA-1 해시에서 앞 8바이트를 멤버 ID로 써요. 같은 폴더의 cluster.go는 복원할 때 이 함수에 시각을 넘기지 않고(NewClusterFromURLsMap) 멤버 ID들의 SHA-1 앞 8바이트를 클러스터 ID로 써요(genID). etcd.yaml에는 --initial-cluster-token이 없어서 etcd와 etcdutl 모두 기본 토큰 etcd-cluster를 썼고 피어 URL도 etcd.yaml에서 그대로 옮겼으니 같은 ID가 다시 계산된 거예요. 직접 계산한 값도 멤버 ID, 클러스터 ID 모두 실제 값과 같았어요. 문서의 "덮어쓴다"는 복원할 때 넘긴 멤버 정보로 다시 쓴다는 뜻이고 같은 값을 넘기면 같은 ID가 나와요.

대신 Raft 기록이 처음부터 다시 시작했어요. 복원 직후 endpoint status는 이랬어요.

# 40-etcd-restore-rehearsal.txt 발췌 (21:57:48, 새 etcd 의 endpoint status 중 앞쪽 열) │ ENDPOINT │ ID │ VERSION │ STORAGE VERSION │ DB SIZE │ IN USE │ PERCENTAGE NOT IN USE │ QUOTA │ IS LEADER │ IS LEARNER │ RAFT TERM │ RAFT INDEX │ │ 127.0.0.1:2379 │ c960bb57b7d36fea │ 3.7.0 │ 3.7.0 │ 29 MB │ 2.4 MB │ 92% │ 2.1 GB │ true │ false │ 2 │ 4 │

→ 15:17에 term 9, index 143152였던 Raft 기록이 term 2, index 4가 됐다는 뜻이에요. v3.7.0 v3_snapshot.go의 saveWALAndSnap은 주석대로 초기 클러스터용 WAL을 새로 만들어요. 그래서 복원본의 etcd는 Raft 기록을 처음부터 쌓아요(48편). 같은 줄에서 DB SIZE 29 MB 가운데 실제로 쓰는 것(IN USE)은 2.4 MB였어요. 29 MB짜리 스냅숏 파일의 대부분이 38편에서 본 빈 페이지였다는 뜻이에요. 2절에서 CronJob으로 뜬 스냅숏이 3 MB 남짓이었던 것과 비교하면 같은 클러스터라도 그때그때 db 파일 크기에 따라 백업 크기가 크게 달라져요.

4. 복원할 때 리비전을 10억 올리고 컴팩션으로 표시하는 이유

복원은 클러스터의 시간을 되돌리는 일이라 리비전도 함께 되돌아가요. 스냅숏은 180003에서 떴는데 복원 직전 클러스터는 그보다 뒤의 리비전까지 와 있었어요. 옵션 없이 복원하면 etcd는 180003에서 다시 시작해 다음 변경 트랜잭션에 180004, 180005 같은 번호를 다시 붙여요. 이미 쓴 번호가 다른 내용으로 한 번 더 쓰이는 거예요.

📖 용어: 리비전과 컴팩션
리비전은 etcd 전체에 하나뿐인 변경 번호예요. 데이터를 바꾸는 트랜잭션이 성공할 때마다 1씩 오르고 한 트랜잭션에서 여러 키를 바꾸면 같은 리비전을 써요. 이 실습의 etcd 저장소 구현에서는 객체가 변경된 리비전을 그 객체의 resourceVersion으로 사용해요(22편). resourceVersion은 서버의 내부 버전을 나타내는 문자열이고 서버에 보낼 때는 그대로 돌려줘요. 현재 API 계약은 같은 API 그룹·리소스 종류의 값끼리 정수 순서를 비교하도록 허용하지만 서로 다른 종류의 값을 빼서 쓰기 횟수를 계산해도 된다는 뜻은 아니에요. 컴팩션은 지정한 리비전보다 옛 이력을 지우는 일이고 컴팩션된 리비전을 물으면 etcd는 답하지 않고 오류를 돌려줘요. API 서버가 5분마다 하는 컴팩션은 38편에서 봤어요.

쿠버네티스에서는 이것이 문제가 돼요. 39편에서 본 대로 컨트롤러와 kubelet은 API 서버에서 목록을 받아 두고 어느 리비전까지 봤는지 기억했다가 그다음부터 watch로 이어 받아요. etcd 복구 문서의 "Revision Difference" 절이 바로 이 경우를 다뤄요. 컨트롤러와 오퍼레이터는 informer라는 로컬 캐시를 쓰고 watch로 변경을 받는데 더 옛 리비전으로 복원하면 캐시가 제대로 새로 고쳐지지 않아 예측할 수 없고 일관되지 않은 동작이 생길 수 있다고 해요. 그래서 쿠버네티스에서 쓸 때는 "revision bump"로 복원하기를 강하게 권해요.

📖 용어: informer
client-go가 제공하는 캐시 장치예요. 초기 객체를 메모리에 채우고 이후 WATCH로 변경을 받아요. client-go v1.37.2에서는 초기 객체도 WATCH로 받는 WatchList가 기본이고 LIST 뒤 WATCH를 잇는 대체 경로도 있어요(39편). 컨트롤러 매니저, 스케줄러, kubelet은 여러 객체를 매번 조회하는 대신 이 캐시를 활용해요. 이어 받을 위치가 너무 옛것이면 410을 받고 초기 상태를 다시 받아요. calico-kube-controllers도 초기 상태와 이후 변경을 받는 자체 캐시(watchercache)를 써요.

이 문제를 막는 것이 etcdutl snapshot restore의 두 옵션이에요. 문서의 설명은 이래요.

· --bump-revision 문서는 "In order to ensure the revisions are never decreasing after a restore, you can supply the `--bump-revision` option."이라고 적어요. 복원 뒤 리비전이 줄어들지 않게 스냅숏의 리비전에 더할 값이라는 뜻이에요. 데이터를 바꾸는 트랜잭션마다 리비전이 1씩 오르니 초당 변경 트랜잭션이 1500번보다 적다면 1,000,000,000을 더해 일주일 된 스냅숏까지 덮을 수 있다고 계산해 줘요.
· --mark-compacted 더한 값까지 포함해 모든 리비전을 컴팩션된 것으로 표시해요. 문서는 그래서 모든 watch가 끝나고 스냅숏 뒤에 일어난 리비전을 묻는 요청에 etcd가 답하지 않게 되며 결과적으로 informer 캐시를 무효로 만든다고 설명해요.

etcdutl v3.7.0 소스(snapshot_command.go)는 두 옵션을 같이 줘야만 받아요. 하나만 주면 --mark-compacted required if --revision-bump > 0 오류로 끝나요. v3_snapshot.go의 RevisionBump 주석은 목적을 "to allow administrators to trick clients into thinking that revision never decreased"라고 적어요. 클라이언트가 보기에 리비전이 한 번도 줄지 않은 것으로 보이게 만든다는 뜻이에요.

그림 8. 리비전을 그대로 두면 같은 번호에 다른 기록이 붙는다. 10억을 더하고 그 아래를 컴팩션으로 표시하면 옛 번호를 든 클라이언트는 410을 받고 처음부터 다시 받는다

우리 복원본에서 실제로 그렇게 됐는지 etcd 로그로 확인했어요. 복원본으로 마지막에 다시 뜬 etcd(21:58:42 KST)의 시작 로그예요.

# 40-restore-aftermath.txt 발췌 (etcd 로그, 시각은 UTC) 12:58:42.738 restarting local member {"cluster-id": "3e50550e6ebc5cfd", "local-member-id": "c960bb57b7d36fea"} 12:58:42.740 restored last compact revision {"restored-compact-revision": 1000180003} 12:58:42.743 kvstore restored {"current-rev": 1000180176}

→ 컴팩션 지점이 1000180003이라는 뜻이에요. 스냅숏 리비전 180003에 1,000,000,000을 더한 값과 정확히 같아요. v3_snapshot.go의 modifyLatestRevision은 마지막 리비전에 bump 값을 더한 리비전으로 빈 기록 하나를 써서 리비전을 올리고 그 리비전을 예정된 컴팩션 지점으로 적어요. 그래서 etcd는 1000180003까지의 리비전을 모두 컴팩션된 것으로 다뤄요. API 서버가 다시 붙은 21:57:50에 리비전이 1000180017이었으니 그사이 데이터를 바꾼 트랜잭션이 14번 있었어요.

옛 리비전을 들고 있던 클라이언트는 어떻게 됐을까요? calico-kube-controllers는 08:28:26 UTC부터 마스터에서 한 번도 재시작하지 않고 돌던 파드라서 복원 전의 리비전을 기억하고 있었어요.

그림 9. 복원 전 리비전(179972~180013)으로 watch를 이으려 하자 API 서버가 too old resource version으로 거절했고 캐시 10개가 모두 목록을 다시 받았다

시각은 UTC라서 9시간을 더하면 21:58:54예요. 리허설 마지막 단계에서 API 서버가 다시 뜬 직후예요. calico-kube-controllers는 globalnetworkpolicies, ippools, nodes 같은 목록 10개를 각각 179972부터 180013 사이의 리비전에서 이어 받으려 했어요. 그중 180013은 스냅숏(180003)보다 뒤의 번호라서 복원으로 사라진 기록에 붙어 있던 번호예요. API 서버는 모두 too old resource version: 180013 (1000180186) 같은 오류로 거절했고 calico-kube-controllers는 "Full resync is required"를 남기고 목록을 처음부터 다시 받았어요.

이 메시지는 API 서버의 watch 캐시가 만들어요. v1.37.2 watch_cache_history.go를 보면 요청한 리비전이 캐시가 이어 줄 수 있는 가장 옛 위치보다 앞이면 "too old resource version: 요청한 값 (캐시의 경계)" 메시지로 410(Expired) 오류를 돌려줘요. 괄호 안의 1000180186이 그 경계예요. 복원본이 1000180003에서 시작했으니 복원 전의 어떤 번호도 이 경계보다 작아요. 리비전을 그대로 두고 복원했다면 180013은 복원본에서 아직 쓰이지 않은 번호가 됐을 거예요. 쓰기가 쌓여 그 번호를 지나면 calico-kube-controllers는 180013 다음부터 아무 일 없다는 듯 이어 받을 수 있었고 그사이 사라지거나 바뀐 객체는 캐시에 옛 모습으로 남았을 거예요. 문서가 경고한 "캐시가 제대로 새로 고쳐지지 않는" 경우예요. 39편의 410이 여기서는 캐시를 처음부터 다시 받게 하는 장치로 일했어요. 리비전을 10억 올리고 그 아래를 컴팩션으로 표시하면 옛 번호를 든 클라이언트는 이어 받지 못하고 목록부터 다시 받아요.

10억이 우리 클러스터에 충분한지도 계산해 봤어요. 20:59:35의 스냅숏은 리비전 143014였고(그림 1) 21:57:04의 스냅숏은 180003이었어요(그림 4). 약 57분 동안 데이터를 바꾼 트랜잭션이 36,989번, 초당 약 11번 있었던 셈이에요. 이 속도라면 10억은 약 3년 치예요. 더하는 값은 스냅숏을 뜬 뒤 복원하기까지 증가한 리비전 수보다 크기만 하면 되니 문서의 값을 그대로 써도 넉넉해요.

⚠️ 주의: 복원은 스냅숏 뒤의 변경을 모두 지워요
• 스냅숏 뒤에 만든 객체(이번의 after-snapshot), 바꾼 설정, 늘린 replicas는 모두 사라져요. 복원할 스냅숏이 언제 것인지와 그 뒤에 무엇을 바꿨는지 먼저 정리해 둬요
• 쿠버네티스 클러스터를 복원할 때는 --bump-revision과 --mark-compacted를 함께 줘요. 빼면 리비전이 뒤로 가서 컨트롤러 캐시가 옛 상태에 머물 수 있어요
• 복원 뒤에는 옛 리비전을 들고 있던 클라이언트가 모두 목록을 다시 받아요. 노드와 컨트롤러가 많은 클러스터라면 그만큼 LIST 요청이 API 서버에 몰려요

5. 복원한 뒤에는 경로를 원래대로 돌려 kubeadm 설정과 맞췄다

3절까지 하고 나면 etcd.yaml의 hostPath가 /var/lib/etcd-restored를 가리켜요. 쿠버네티스 문서는 kubeadm으로 관리하는 클러스터라면 이때 kubeadm-config ConfigMap의 etcd.local.dataDir도 새 경로로 바꾸라고 해요. 옛 경로가 남아 있으면 다음 kubeadm upgrade가 그 경로로 etcd 매니페스트를 다시 쓰기 때문이에요. 우리 kubeadm-config에는 21편에서 본 대로 dataDir: /var/lib/etcd가 적혀 있어요.

그래서 리허설 마지막 단계(21:58:41~21:58:47)에서는 설정을 바꾸지 않고 폴더를 옮겼어요. API 서버와 etcd 매니페스트를 모두 빼서 두 컨테이너가 내려간 것을 확인한 뒤 원래 /var/lib/etcd를 /var/lib/etcd-before-rehearsal로, 복원본 /var/lib/etcd-restored를 /var/lib/etcd로 이름을 바꾸고 원래 etcd.yaml을 돌려놓았어요. 이번에는 옛 etcd가 먼저 내려가 있었으니 etcd는 1초 만에(21:58:43) healthy가 됐어요. API 서버는 21:58:47에 다시 응답했고 리비전은 1000180202, 표식은 그대로 before-snapshot 하나였어요. 21:59:07에 노드 네 대가 Ready였고 21:59:08에는 Running이 아닌 파드가 0개였어요. 이제 etcd.yaml과 kubeadm-config는 리허설 전과 같고 데이터만 복원본으로 바뀐 상태예요. 원래 데이터는 /var/lib/etcd-before-rehearsal에 남겨 두었어요.

💡 실무에서는: 복원 순서를 이렇게 적어 둬요
• 스냅숏 파일을 etcdutl snapshot status로 확인하고 지금 data-dir을 다른 이름으로 남겨 둘 디스크 공간이 있는지 봐요
• 모든 API 서버를 멈춰요. 정적 파드라면 매니페스트를 /etc/kubernetes/manifests 밖으로 옮겨요
• etcd도 멈춰요. hostPath만 바꾸고 kubelet을 재시작하면 옛 etcd가 끝나기 전에 새 etcd가 뜨려다 실패할 수 있어요(3절)
• etcdutl snapshot restore에 --data-dir, --name, --initial-cluster, --initial-advertise-peer-urls를 etcd.yaml과 같게 주고 --bump-revision과 --mark-compacted를 함께 줘요. 멤버가 여럿이면 etcd 복구 문서대로 모든 멤버가 같은 스냅숏에서 각자 복원해요
• 새 폴더는 원래 경로로 옮겨요. hostPath를 바꿔 새 경로를 쓴다면 kubeadm-config의 etcd.local.dataDir도 함께 바꿔요
• etcd가 healthy인지 본 뒤 API 서버를 돌려놓고 문서의 권고대로 스케줄러, 컨트롤러 매니저, kubelet도 재시작해요. 리더 Lease를 다시 얻었는지, 노드가 Ready인지, 알고 있는 객체가 기대한 상태인지 확인해요

6. etcd를 컨트롤 플레인 밖에 두면 백업과 복원은 무엇이 달라질까

백업 이야기를 하다가 제가 물은 것은 "etcd 외부에서 관리하게 설치하는 곳도 있대, 뭐가 장점이야?"였어요. 우리 클러스터는 etcd가 마스터 안에서 정적 파드로 도는 stacked 구성이고 21편에서 external 구성과 표로 비교했어요. 그 표의 요점은 external etcd가 컨트롤 플레인 노드 하나나 etcd 멤버 하나를 잃어도 다른 쪽까지 함께 잃지 않는 대신 호스트가 stacked의 두 배 필요하다는 거예요.

쿠버네티스의 etcd 운영 문서가 드는 이유는 자원이에요. 클러스터의 성능과 안정성은 네트워크와 디스크 I/O에 민감하고 자원이 모자라면 하트비트 시간 초과로 클러스터가 불안정해질 수 있다고 해요. 그래서 etcd 클러스터를 전용 기계나 격리된 환경에서 돌려 필요한 자원을 보장하라고 권해요. stacked에서는 etcd가 API 서버, 컨트롤러 매니저, 스케줄러와 같은 기계의 CPU와 디스크를 나눠 써요.

이어서 물은 것은 "nginx conf 외부 관리하는 그런 느낌인가?"였어요. 답은 조금 달라요. nginx 설정 파일을 밖에서 관리하는 것은 프로세스가 시작할 때 읽는 설정을 프로세스와 따로 두는 일이에요. external etcd에서 밖으로 나가는 것은 설정이 아니라 API 서버가 계속 읽고 쓰는 데이터 저장소 자체예요. 4절에서 센 대로 우리 클러스터에서도 데이터를 바꾸는 트랜잭션이 초당 약 11번씩 있었어요. API 서버에 남는 것은 그 저장소의 주소와 인증서뿐이에요. 우리 API 서버의 --etcd-servers=https://127.0.0.1:2379(36편)가 external 구성에서는 etcd 호스트들의 주소 목록이 되고 --etcd-cafile, --etcd-certfile, --etcd-keyfile이 그 etcd와 주고받을 인증서를 가리켜요.

"조금 다르네" 하고 다시 보니 데이터베이스로 보는 편이 맞았어요. 그때 제가 남긴 말은 "DB 관점에서 보니까 알았음"이에요. API 서버는 상태를 디스크에 남기지 않는 서버이고(38편) etcd는 그 서버가 쓰는 데이터베이스예요. stacked는 그 데이터베이스를 API 서버와 같은 기계에 두고 external은 전용 서버들에 따로 둬요. 백업과 복원에서 달라지는 점은 이래요.

✍️ 오늘의 요약
etcd 3.7에서는 etcdctl로 스냅숏을 뜨고 etcdutl로 되살려요. 되살릴 때는 API 서버부터 멈추고 --bump-revision과 --mark-compacted로 리비전이 뒤로 가지 않게 해요.

예전 명령의 sh -c는 셸이 없는 distroless 이미지에서 시작도 못 했고 ETCDCTL_API=3은 3.4부터 기본값이라 필요 없었으며 etcdctl snapshot restore는 3.6에서 빠져 도움말만 냈어요. CronJob의 스냅숏은 저장됐지만 같은 이름으로 덮어쓰고 마스터 디스크에 남아서 시각이 붙은 이름, 노드 밖 보관, 암호화가 더 필요해요. 스냅숏 앞뒤에 표식을 두고 실제로 되살리니 API 서버 매니페스트를 뺀 뒤 준비 상태로 돌아오기까지 약 45초 걸렸고 그사이 etcd가 바뀌었으며 after-snapshot은 사라졌으며 컨트롤러 매니저와 스케줄러는 리더 Lease를 잃고 한 번씩 재시작했어요. 멤버 ID는 피어 URL과 토큰의 해시라서 그대로였고 Raft 기록만 처음부터 다시 시작했어요. 리비전은 180003에서 1000180003으로 뛰어 그 아래가 모두 컴팩션으로 표시됐고 복원 전 리비전으로 watch를 이으려던 calico-kube-controllers는 too old resource version을 받고 목록을 처음부터 다시 받았어요. 백업은 되살려 봐야 쓸모를 알 수 있고 되살릴 때는 데이터만이 아니라 클라이언트가 기억한 번호까지 함께 맞춰야 해요.
