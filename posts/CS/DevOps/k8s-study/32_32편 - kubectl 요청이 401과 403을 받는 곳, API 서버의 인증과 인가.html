worker1에서 API 서버(192.168.104.1:6443)의 /version 경로로 curl 요청을 두 번 보냈어요. 아무 자격 없이 보낸 첫 요청에는 200과 함께 버전 v1.37.2가 돌아왔어요. 두 번째 요청에는 Authorization 헤더에 not-a-real-token이라는 가짜 토큰을 붙였는데 이번에는 401 Unauthorized가 돌아왔어요. 자격을 하나 더 실었을 뿐인데 오히려 막힌 거예요. 이번에는 자격 없는 요청을 파드 목록 경로(/api/v1/namespaces/default/pods)로 보내자 401이 아니라 403 Forbidden이 나왔고 메시지에는 User "system:anonymous"라는 이름이 들어 있었어요.

이 실험은 아키텍처 그림 한 장에서 시작했어요. 그림 왼쪽에는 kubectl apply -f pod.yaml을 치는 개발자가 있었고 그 요청이 0) TLS 암호화로 전달되고 API 서버에 닿으면 1) Authentication check, 2) Authorization check, 3) Admission controller를 차례로 거친다고 적혀 있었어요. 그림을 보고 제가 남긴 말은 "해석 좀" 한마디였어요. 19편에서는 그림 전체를 읽으면서 이 네 칸을 한 절에서 다루고 지나갔어요. 이번 편과 33편에서는 네 칸을 하나씩 떼어 내 관문마다 우리 클러스터의 어떤 설정이 작동하는지, 무엇을 다음 관문에 넘기고 무엇을 거절하는지 실험으로 확인해요. 이번 편은 TLS, 인증, 인가 세 칸을 다루고 마지막 칸인 어드미션은 33편에서 따로 봐요.

클러스터는 1~7편에서 만든 실습 환경(Lima VM 4대, kubeadm으로 설치한 쿠버네티스 v1.37.2)이에요. 실험용 객체는 전용 네임스페이스 w32 안에만 만들었고 실험 하나가 끝날 때마다 네임스페이스째 지웠어요.

이 글에서 다룰 것
· kubectl 요청 하나는 API 서버 안에서 어떤 순서로 걸러지고 각 관문은 어떤 설정으로 돌까?
· 쿠버네티스에는 사용자 객체가 없는데 API 서버는 요청을 보낸 쪽이 누구인지 어떻게 알까?
· 자격이 없는 요청은 왜 401이 아니라 403을 받을까? 익명 요청은 왜 켜져 있을까?
· 권한은 어디서 오고 kubelet은 왜 자기 노드의 객체만 만질 수 있을까?
· 401이나 403을 만나면 메시지로 어느 관문에서 막혔는지 어떻게 가릴까?

1. kubectl 요청은 TLS, 인증, 인가, 어드미션을 차례로 지나야 저장된다

kubectl이 권한 문제로 실패하면 화면에 뜨는 낱말은 대개 Unauthorized 아니면 Forbidden이에요. 둘은 고칠 곳이 달라요. Unauthorized면 kubeconfig의 인증서나 토큰을, Forbidden이면 권한 규칙이나 네임스페이스의 정책을 봐야 해요. 어느 쪽인지 가르려면 요청이 API 서버 안에서 어떤 순서로 걸러지는지부터 알아야 해요.

공식 문서 Controlling Access to the Kubernetes API는 이 순서를 그림의 번호 그대로 설명해요. API 서버는 기본으로 6443 포트에서 TLS로 보호된 연결을 받고 클라이언트는 이 단계에서 TLS 클라이언트 인증서를 낼 수 있어요. 연결이 맺어지면 요청은 인증 단계로 가요. API 서버는 설정된 인증 모듈을 차례로 시도해서 하나가 성공하면 그 사용자 이름을 다음 단계로 넘기고 인증할 수 없는 요청은 HTTP 401로 거절해요. 인가 단계에서는 사용자 이름, 요청한 동작, 대상 객체를 보고 허락할지 정하고 거절하면 403이에요. 어드미션 단계의 모듈은 요청을 고치거나 거절할 수 있고 인가 모듈과 달리 만들거나 고치려는 객체의 내용까지 볼 수 있어요. 어드미션 모듈을 모두 통과한 요청은 객체 종류별 검증을 거쳐 저장소에 기록돼요. 이번 편은 그중 어드미션 앞의 세 관문까지 따라가고 어드미션은 33편에서 따로 봐요.

📖 용어: 인증과 인가 (authentication, authorization)
인증은 "요청을 보낸 쪽이 누구인가"를 정하는 단계이고 인가는 "그 사용자가 이 동작을 해도 되는가"를 정하는 단계예요. 인증이 끝나면 요청에는 사용자 이름과 그 사용자가 속한 그룹 목록이 붙어요. 그룹은 여러 사용자에게 같은 권한을 한꺼번에 주려고 쓰는 이름이에요. 인가는 이 사용자 이름과 그룹으로 규칙을 찾아요.
그림 1. 관문마다 넘기는 것과 막혔을 때 돌아오는 응답이 다르다. 403 하나만 보고는 인가인지 어드미션인지 알 수 없다

그림 1의 "우리 API 서버의 설정" 줄은 실행 플래그와 kube-apiserver --help, 웹훅 목록에서 확인한 값이에요(19편 원자료와 이번 원자료, 어드미션 칸은 33편 원자료). 관문별로 정리하면 이래요.

관문묻는 것우리 클러스터에서 작동하는 설정막히면
0. TLS이 서버가 진짜 API 서버인가, 연결이 암호화됐나--secure-port=6443, 서버 인증서(CN=kube-apiserver, 발급자 CN=kubernetes)연결 오류. 평문 http로 보내면 400
1. 인증요청을 보낸 쪽은 누구인가--client-ca-file(클라이언트 인증서), --service-account-key-file(ServiceAccount 토큰), 익명 요청 기본 허용401 Unauthorized
2. 인가그 사용자가 이 동작을 해도 되나--authorization-mode=Node,RBAC403 Forbidden
3. 어드미션이 객체를 이대로 저장해도 되나, 채울 칸은 없나바이너리 기본 플러그인 25개 + --enable-admission-plugins=NodeRestriction, 웹훅·정책 0개대개 403 Forbidden, 없는 네임스페이스면 404 NotFound(33편)
4. 저장(객체 종류별 검증 뒤 기록)--etcd-servers=https://127.0.0.1:237922편

관문 0은 다른 관문과 성격이 달라요. 인증보다 먼저 클라이언트가 서버를 확인하는 단계예요. worker1에서 CA 인증서를 주지 않고 curl로 요청을 보내 보면 차이가 보여요.

worker1$ curl -sS https://192.168.104.1:6443/version # CA 를 주지 않으면 curl: (60) SSL certificate problem: unable to get local issuer certificate worker1$ curl -sS http://192.168.104.1:6443/version # TLS 없이 평문으로 보내면 Client sent an HTTP request to an HTTPS server. worker1$ curl -sS --cacert /etc/kubernetes/pki/ca.crt https://192.168.104.1:6443/version | grep gitVersion "gitVersion": "v1.37.2", worker1$ openssl s_client -connect 192.168.104.1:6443 | openssl x509 -noout -subject -issuer # API 서버가 내민 인증서 subject=CN = kube-apiserver issuer=CN = kubernetes

→ CA를 주지 않으면 curl이 서버 인증서를 믿을 근거가 없어서 연결을 끊어요(종료 코드 60). 평문 http로 보내면 API 서버가 "HTTPS 서버에 HTTP 요청을 보냈다"고 답해요. 노드에 있는 CA 파일을 주자 같은 요청에 버전 정보가 돌아왔어요. 서버 인증서의 발급자 CN=kubernetes는 kubeadm init이 만든 클러스터 CA예요(5편).

문서에 따르면 사설 CA를 쓰는 클러스터에서는 클라이언트의 kubeconfig에 그 CA 인증서를 넣어 두어야 연결이 가로채이지 않았다고 믿을 수 있어요. kubectl은 같은 상황에서 Unable to connect to the server: tls: failed to verify certificate: x509: certificate signed by unknown authority를 출력했어요. TLS에서 막힌 요청은 401도 403도 받지 못해요. 그 두 코드는 연결이 맺어진 뒤에 API 서버가 직접 보내는 응답이에요.

2. 인증은 요청에 실린 자격을 사용자 이름과 그룹으로 바꾼다

쿠버네티스 API에는 사람 사용자를 나타내는 객체가 없어요. Authenticating 문서에 따르면 일반 사용자는 API 호출로 클러스터에 추가할 수 없고 대신 클러스터 CA가 서명한 유효한 인증서를 내는 사용자는 누구든 인증된 것으로 봐요. 그렇다면 API 서버는 kubectl을 친 사람이 누구인지 어디서 알아낼까요? 답은 요청에 실린 자격 안에 들어 있어요.

그림 2. 관리자의 이름도 kubelet의 이름도 인증서의 CN과 O에 적힌 글자였다

평소 쓰는 관리자 kubeconfig(admin.conf)에 든 인증서를 풀어 보면 인증서 주인을 적는 subject 칸이 O = kubeadm:cluster-admins, CN = kubernetes-admin이에요. kubectl auth whoami가 알려 준 사용자 이름 kubernetes-admin과 그룹 kubeadm:cluster-admins가 바로 이 두 칸에서 나왔어요. 문서의 X.509 절에 따르면 subject의 commonName은 사용자 이름으로, organization 칸은 그룹으로 쓰이고 인증에 성공한 요청은 자동으로 system:authenticated 그룹에도 들어가요. 그래서 whoami에 그룹이 두 개 나왔어요.

📖 용어: 인증서의 CN과 O
X.509 인증서의 subject에 들어가는 칸이에요. CN(commonName)은 이름, O(organization)는 소속이고 한 인증서에 O를 여러 개 넣을 수 있어요. API 서버는 --client-ca-file로 지정한 CA가 서명한 인증서만 받고 그 인증서의 CN을 사용자 이름으로, O를 그룹으로 읽어요.

kubernetes-admin이라는 사용자 객체는 클러스터 어디에도 없어요. 그런데도 이 이름이 관리자 권한을 받는 까닭은 kubeadm init이 만들어 둔 ClusterRoleBinding kubeadm:cluster-admins가 같은 이름의 그룹에 cluster-admin 역할을 묶어 두었기 때문이에요. ClusterRoleBinding은 역할(권한 규칙 묶음)을 사용자나 그룹에 클러스터 전체 범위로 연결하는 객체라서 이 그룹에 속한 사용자는 누구나 cluster-admin 권한을 받아요. kubeadm 구현 문서에도 admin.conf의 인증서 subject가 O = kubeadm:cluster-admins, CN = kubernetes-admin이고 이 그룹이 init 때 cluster-admin에 묶인다고 적혀 있어요. RBAC(역할 기반 접근 제어) 검사 자체를 건너뛰는 system:masters 인증서(super-admin.conf)는 5편에서 봤어요.

worker1의 kubelet도 같은 방식으로 이름을 얻어요. kubelet이 쓰는 인증서의 subject는 O = system:nodes, CN = system:node:k8s-worker1였고 그 인증서로 whoami를 실행하면 사용자 이름 system:node:k8s-worker1에 그룹 system:nodes가 나왔어요. 이 이름 형식은 4절에서 볼 Node 인가자(kubelet이 보낸 요청만 따로 판단하는 인가 모듈)와 이어져요.

ServiceAccount는 파드 안에서 도는 프로그램 같은, 사람이 아닌 쪽이 쓰는 계정이에요. 사람 사용자와 달리 API 객체로 만들고 인증서 대신 서명된 토큰을 써요. w32에 ServiceAccount reader를 만들고 kubectl create token으로 받은 토큰만 실어 worker1에서 whoami 요청을 보냈어요(클라이언트 인증서 없이 토큰만 보내야 하는 이유는 10편).

worker1$ kubectl --kubeconfig=/dev/null --server=https://192.168.104.1:6443 --certificate-authority=/etc/kubernetes/pki/ca.crt --token=$TOKEN auth whoami Username system:serviceaccount:w32:reader Groups ["system:serviceaccounts","system:serviceaccounts:w32","system:authenticated"]

→ API 서버가 토큰의 서명을 확인하고 이 요청을 w32 네임스페이스의 ServiceAccount reader로 인식했다는 뜻이에요. 그룹 세 개는 문서에 적힌 그대로 각각 모든 ServiceAccount, w32의 ServiceAccount, 인증된 사용자 전체를 뜻해요.

토큰의 서명을 확인하는 공개 키는 API 서버 플래그 --service-account-key-file=/etc/kubernetes/pki/sa.pub로 지정돼 있어요. 파드 안의 프로그램도 자기 ServiceAccount의 토큰을 들고 API 서버에 붙어요. 이때는 6443 대신 kubernetes Service의 주소 10.96.0.1:443을 쓰고 그 Service의 EndpointSlice는 192.168.104.1:6443을 가리켜요. 19편 원자료를 보면 CoreDNS 파드와 calico-kube-controllers 파드가 실제로 10.96.0.1:443에 연결돼 있었어요. 파드에 토큰이 어떻게 들어가는지는 33편에서 어드미션과 함께 봐요.

그림 3. 자격이 무엇이든 인증이 끝나면 이름과 그룹만 남는다. 틀린 자격만이 401로 끝난다

문서에 따르면 인증 모듈이 여럿 켜져 있을 때는 요청을 처음으로 인증해 낸 모듈에서 평가가 끝나고 API 서버는 모듈이 도는 순서를 보장하지 않아요. 그래서 인증서와 토큰을 함께 실은 요청은 어느 쪽 이름으로 인식될지 장담할 수 없어요(10편). 인증이 끝나면 요청에 남는 것은 사용자 이름과 그룹뿐이고 그다음 관문은 그 문자열만 봐요.

⚠️ 주의: 클라이언트 인증서는 중간에 폐기할 수 없어요
• 인증 문서에 따르면 쿠버네티스 1.37은 인증서 폐기(revocation)를 지원하지 않고 한 번 발급한 인증서는 만료될 때까지 유효해요
• 우리 admin.conf 인증서의 만료일은 2027년 11월 4일이었어요. 이 파일이 새 나가면 그날까지 cluster-admin 권한이 같이 새 나가요
• kubeadm 구현 문서도 admin.conf는 컨트롤 플레인 노드에 두고 다른 사용자와 공유하지 말고 추가 사용자의 kubeconfig는 kubeadm kubeconfig user로 만들라고 안내해요

3. 자격이 없으면 403, 틀린 자격이면 401이 나온다

도입에서 한 실험으로 돌아가 볼게요. worker1에서 CA 확인은 그대로 하면서 경로 여섯 개에 자격 없는 요청과 가짜 토큰 요청을 하나씩 보냈어요.

그림 4. 자격이 없으면 경로에 따라 200 또는 403이었고 가짜 토큰을 붙이면 공개 경로까지 모두 401이었다

자격 없는 요청은 /version, /livez, /readyz, /healthz에서 200을, /api와 파드 목록에서 403을 받았어요. 403 메시지에 찍힌 사용자 이름은 system:anonymous였어요. 가짜 토큰을 붙인 요청은 여섯 경로 모두 401이었어요. 누구나 열 수 있는 /version도 예외가 아니었어요.

이 결과는 Authenticating 문서의 Anonymous requests 절과 그대로 맞아요. 익명 요청이 켜져 있으면 다른 인증 방법이 거절하지 않은 요청은 익명 요청으로 취급되고 사용자 이름 system:anonymous와 그룹 system:unauthenticated를 받아요. 문서는 예도 하나 들어요. 토큰 인증과 익명 요청이 함께 켜진 서버에서 틀린 토큰을 낸 요청은 401을 받고 토큰을 내지 않은 요청은 익명 요청이 된다고요. 자격이 없는 요청은 인증에 실패한 것이 아니라 익명 사용자로 인증된 뒤 인가에서 거절됐어요. 틀린 토큰은 토큰 인증 모듈이 거절해 버리기 때문에 익명으로 넘어갈 기회가 없어요.

📖 용어: 익명 요청 (anonymous request)
인증서도 토큰도 없이 들어온 요청이에요. API 서버는 이 요청을 바로 거절하지 않고 사용자 이름 system:anonymous, 그룹 system:unauthenticated를 붙여 인가 단계로 넘겨요. 그래서 익명 요청이 무엇을 할 수 있는지는 인가 규칙이 정해요.

보낸 여섯 경로 가운데 익명 사용자가 공개 경로 네 곳만 열 수 있었던 이유는 기본 ClusterRoleBinding에 있어요. system:public-info-viewer는 system:authenticated와 system:unauthenticated 두 그룹에 묶여 있고 허용하는 규칙은 /healthz, /livez, /readyz, /version에 대한 get 하나뿐이었어요. API 목록(/api)을 읽게 하는 system:discovery와 자기 정보를 묻게 하는 system:basic-user는 system:authenticated에만 묶여 있었어요. RBAC 문서의 기본 역할 표를 보면 두 역할은 v1.14 전에는 system:unauthenticated에도 묶여 있었어요. 그래서 익명 사용자는 자기 권한 목록을 묻는 kubectl auth can-i --list조차 실행할 수 없었어요. 그 질문을 담은 SelfSubjectRulesReview를 만들 권한이 없다는 403이 돌아왔어요.

익명 요청은 왜 기본으로 켜져 있을까

문서에 따르면 인가 모드가 AlwaysAllow가 아니면 익명 요청이 기본으로 켜지고 --anonymous-auth=false로 끌 수 있어요. 우리 API 서버의 실행 플래그에는 --anonymous-auth가 아예 없었고 v1.37.2 바이너리의 --help에도 기본값이 true로 적혀 있었어요. Authenticating 문서에는 "그래서 켜 둔다"는 이유가 한 문장으로 적혀 있지 않았어요. 대신 RBAC 문서에는 기본 바인딩이 공개해도 안전하다고 판단한 API 정보를 인증하지 않은 사용자도 읽을 수 있게 한다는 설명이 있어요. 익명 요청에 기대는 쓰임새는 다른 문서에 적혀 있어요. kubeadm 구현 문서에 따르면 kubeadm init은 kube-public 네임스페이스의 cluster-info ConfigMap을 인증하지 않은 사용자도 읽게 해 두고 kubeadm join은 토큰 디스커버리 때 이 ConfigMap에서 CA 인증서를 자격 없이 받아 와요. 우리 클러스터에서도 RoleBinding(한 네임스페이스 안에서 권한을 주는 객체) kubeadm:bootstrap-signer-clusterinfo가 system:anonymous에게 이 ConfigMap 하나에 대한 get 권한을 주고 있었고 worker1에서 자격 없이 요청하자 200이 돌아왔어요(같은 네임스페이스의 ConfigMap 목록은 403). 익명 사용자가 읽을 수 있는 것이 위의 공개 경로 네 곳만은 아니라는 뜻이에요. v1.34 릴리스 블로그도 /healthz, /readyz, /livez 같은 헬스 체크·부트스트랩 경로에 익명 접근을 쓰는 클러스터를 언급해요. 우리 클러스터에서는 공개 경로를 실제로 쓰는 곳도 하나 보였어요.

master$ sudo grep -A6 -E 'livenessProbe|readinessProbe|startupProbe' /etc/kubernetes/manifests/kube-apiserver.yaml livenessProbe: host: 192.168.104.1 path: /livez port: probe-port scheme: HTTPS readinessProbe: host: 192.168.104.1 path: /readyz ... 프로브 정의 안의 httpHeaders 줄 수: 0

→ kubelet은 API 서버 정적 파드가 살아 있는지 6443 포트의 /livez와 /readyz로 확인하고 그 요청에 따로 넣는 헤더는 없다는 뜻이에요. probe-port는 같은 매니페스트에서 containerPort 6443에 붙인 이름이고 startupProbe도 /livez를 불러요.

kubelet의 HTTP 프로브 코드(pkg/probe/http/http.go, v1.37.2)는 HTTPS 프로브에 서버 인증서 확인을 건너뛰는 설정만 넣고 클라이언트 인증서는 싣지 않아요. 요청 헤더도 User-Agent와 Accept에 사용자가 적은 httpHeaders만 더해요(request.go). 그러니 이 프로브는 API 서버가 보기에 익명 요청이고 public-info-viewer 덕분에 200을 받아요. 우리 클러스터에서 익명 요청을 꺼 보지는 않았어요. 그래도 문서에 실린 익명 인증 설정 예시가 익명 요청을 딱 /livez, /readyz, /healthz에만 허용한다는 점은 이 쓰임새와 맞아떨어져요.

⚠️ 주의: 익명 요청을 막는 것은 인가 규칙뿐이에요
• 6443에 닿기만 하면 누구든 system:anonymous라는 이름을 받아 인가 단계까지 들어와요. 노드와 컨트롤 플레인의 통신 문서도 익명 요청이나 ServiceAccount 토큰을 허용한다면 특히 인가를 켜 두라고 적어요
• system:anonymous 사용자나 system:unauthenticated 그룹에 권한을 주는 바인딩을 만들면 그 권한은 6443에 닿을 수 있는 모든 곳에 열려요. 9편에서 인증서 없이 연 API 서버 프록시 경로가 403을 받은 것도 익명 사용자에게 그 권한이 없었기 때문이에요
• 익명 요청을 좁히고 싶다면 v1.34부터 정식 기능인 AuthenticationConfiguration의 anonymous 설정으로 익명 요청을 받을 경로만 지정할 수 있어요(이 설정은 --anonymous-auth 플래그와 함께 쓸 수 없어요)

kubelet은 같은 "자격 없는 요청"을 다르게 처리해요. worker1의 kubelet 설정에서는 authentication.anonymous.enabled가 false라서 10250 포트에 자격 없이 보낸 요청이 401을 받았어요(19편 원자료, 26편). API 서버는 익명 요청을 받아 준 뒤 인가에서 막았고 kubelet은 인증 단계에서 바로 막은 거예요.

4. 인가는 이름으로 규칙을 찾고 Node 인가자는 kubelet을 자기 노드에 묶는다

우리 API 서버의 인가 설정은 --authorization-mode=Node,RBAC이에요. Authorization 문서에 따르면 인가 모듈은 적힌 순서대로 판단하고 어느 모듈이든 허락이나 거부를 내리면 그 결정으로 곧바로 판단이 끝나요. 모든 모듈이 의견 없음(no opinion)을 내면 요청은 거절되고 HTTP 403을 받아요. RBAC에는 거부 규칙이 없어요. 권한을 더하는 규칙만 있으니 아무 규칙에도 걸리지 않은 요청은 의견 없음으로 끝나고 결국 403을 받아요. Node 인가자는 kubelet이 아닌 요청에는 의견 없음을 내기 때문에(node_authorizer.go, v1.37.2) 사람과 ServiceAccount의 요청은 사실상 RBAC 규칙이 판단해요.

RBAC: 권한 없는 토큰에 RoleBinding 하나를 붙인다

2절에서 만든 w32의 reader 토큰으로 파드 목록을 요청했어요. 같은 토큰에서 서명 부분만 뒤집은 토큰으로도 같은 요청을 보냈어요.

그림 5. 진짜 토큰은 이름을 얻고 403에서 막혔고 서명이 틀린 토큰은 이름도 얻지 못하고 401에서 막혔다

진짜 토큰은 403을 받았고 메시지에 User "system:serviceaccount:w32:reader"라는 이름이 찍혔어요. 인증은 통과했지만 인가에서 막혔다는 뜻이에요. 서명을 뒤집은 토큰은 모양이 같아도 서명 확인에 실패해서 401이었어요. 관리자 kubeconfig로 kubectl auth can-i ... --as=system:serviceaccount:w32:reader를 실행해 봐도 list, get, delete 모두 no였어요. can-i는 SelfSubjectAccessReview API로 인가 단계에 직접 묻는 명령이고 --as는 관리자가 다른 사용자 행세를 하며 묻게 해 주는 옵션(impersonation)이에요.

권한을 하나도 주지 않은 상태에서 can-i --list로 본 reader의 권한 목록에는 SelfSubjectReview·SelfSubjectAccessReview·SelfSubjectRulesReview 만들기와 /api, /apis, /openapi, /version, /healthz 같은 경로 읽기가 있었어요. 인증된 사용자라면 누구나 기본 바인딩으로 받는 권한이에요. 파드에 대한 권한은 없었어요. 이제 w32 안에서만 효력이 있는 Role과 RoleBinding을 만들었어요.

📖 용어: Role과 RoleBinding
Role은 한 네임스페이스 안에서 "어떤 리소스에 어떤 동작을 할 수 있다"는 규칙 묶음이고 RoleBinding은 그 묶음을 사용자, 그룹, ServiceAccount에게 주는 객체예요. 권한을 받는 쪽은 RoleBinding의 subjects 칸에 적어요(앞에서 본 인증서의 subject와는 다른 칸이에요). 둘 다 네임스페이스에 속해서 효력도 그 네임스페이스 안에만 미쳐요. 클러스터 전체에 미치는 ClusterRole과 ClusterRoleBinding은 10편에서 다뤘어요.
그림 6. RoleBinding 하나로 w32의 파드 읽기만 열렸다. 다른 동작, 다른 리소스, 다른 네임스페이스는 그대로 no였다

Role pod-reader는 파드에 get, list, watch만 허용하고 RoleBinding reader-can-read-pods는 그 Role을 w32/reader에게 줘요. 바인딩을 만든 뒤 같은 토큰으로 보낸 w32 파드 목록 요청은 200을 받았어요(파드가 없어서 items 0). 같은 토큰으로 default의 파드 목록을 요청했을 때는 여전히 403이었고 can-i로 물어본 delete pods와 list secrets도 no였어요. 토큰은 그대로였고 바뀐 것은 w32 안의 RoleBinding 하나였어요. 인증 결과는 같고 인가 결과만 바뀌었어요. can-i는 요청을 실제로 보내기 전에 권한을 확인하는 데 쓰고 토큰이 정말 그 이름으로 인증되는지는 토큰을 직접 실어 확인해요. 이번에는 두 가지를 다 했어요.

Node 인가자: kubelet은 자기 노드와 관련된 객체만 읽는다

kubelet은 자기 노드에 배정된 파드를 띄우려고 그 파드가 쓰는 Secret과 ConfigMap을 읽어야 해요. 모든 kubelet에게 모든 Secret을 읽을 권한을 주면 노드 한 대의 kubelet 자격이 새 나가는 순간 클러스터의 Secret도 전부 새 나가요. RBAC 문서의 기본 역할 표를 보면 system:node ClusterRole에는 모든 Secret 읽기와 모든 파드 status 쓰기가 들어 있어요. 문서는 이 역할 대신 Node 인가자와 NodeRestriction(kubelet이 고칠 수 있는 Node와 파드 객체를 자기 노드 것으로 좁히는 어드미션 플러그인)을 쓰라고 하고 이 역할은 v1.8 이전 버전에서 업그레이드한 클러스터와 호환하려고만 남겨 두었다고 적어요. 우리 클러스터의 ClusterRoleBinding system:node에는 subjects가 하나도 없었어요. 이 역할을 받은 사용자나 그룹이 없다는 뜻이에요.

📖 용어: Node 인가자 (Node authorizer)
kubelet이 보낸 요청만 판단하는 특수한 인가 모드예요. 사용자 이름이 system:node:<노드 이름>이고 그룹이 system:nodes인 요청을 kubelet의 요청으로 봐요. Secret, ConfigMap, PVC, PV는 그 노드에 배정된 파드가 쓰는 것만 읽게 하고 노드와 파드 객체는 자기 것만 읽게 해요. kubelet이 아닌 사용자의 요청에는 의견을 내지 않아요.

실험은 이렇게 짰어요. w32에 Secret s-w1과 s-w2를 만들고 s-w1을 쓰는 파드 p-w1은 worker1에, s-w2를 쓰는 파드 p-w2는 worker2에 nodeName으로 바로 배정했어요. 그리고 worker1에서 kubelet이 실제로 쓰는 kubeconfig(/etc/kubernetes/kubelet.conf)로 kubectl을 실행했어요. 쓰기 요청은 모두 --dry-run=server(API 서버가 인증부터 어드미션까지 다 처리하되 저장만 하지 않게 하는 옵션)로 보내서 아무것도 저장되지 않게 했어요.

그림 7. worker1의 kubelet은 자기 노드와 이어진 객체만 읽었고 인가가 허락한 쓰기도 남의 노드 파드에는 어드미션에서 막혔다

읽기는 Node 인가자가 판단했어요. p-w1이 쓰는 s-w1은 읽혔고 s-w2는 node: no relationship found between node 'k8s-worker1' and this object로 막혔어요. 노드 객체도 k8s-worker1만 읽혔고 k8s-worker2는 only its own Node object로 막혔어요. 파드는 p-w1만 읽혔고 목록은 spec.nodeName=k8s-worker1 필드 셀렉터를 붙였을 때만 나왔어요. Node Authorization 문서에 적힌 그대로예요. Node 인가자는 Service와 Endpoints 같은 객체의 읽기는 허락하지만 Secret, ConfigMap, PVC, PV는 자기 노드에 배정된 파드와 관련된 것만 읽게 하고 v1.34부터 정식 기능인 AuthorizeNodeWithSelectors에 따라 노드 객체와 파드도 자기 것만 읽게 해요. 문서는 이름 형식도 정해 둬요. 사용자 이름이 system:node:<노드 이름>이고 그룹이 system:nodes여야 Node 인가자가 판단해요. 2절에서 본 kubelet 인증서의 CN과 O가 정확히 그 모양이었어요.

쓰기는 달랐어요. kubelet 자격으로 물은 can-i create pods와 can-i delete pods는 둘 다 yes였어요. 문서에도 Node 인가자는 파드와 파드 status 쓰기를 허락하고 kubelet을 자기 노드의 파드로 좁히는 일은 NodeRestriction 어드미션 플러그인에 맡긴다고 적혀 있어요. 어드미션은 인가를 통과한 요청을 저장하기 전에 객체 내용까지 보고 고치거나 거절하는 단계예요(33편). 실제로 보통 파드를 만들려 하자 pod does not have "kubernetes.io/config.mirror" annotation, node "k8s-worker1" can only create mirror pods로, worker2에 배정된 p-w2를 지우려 하자 node "k8s-worker1" can only delete pods with spec.nodeName set to itself로 막혔어요. 자기 노드의 p-w1 삭제만 통과했어요(dry run). 미러 파드는 kubelet이 정적 파드를 API에서도 보이게 하려고 만드는 파드예요(26편).

그림 8. kubelet을 자기 노드에 묶는 일은 인가와 어드미션 두 관문이 나눠 맡는다

인가 단계에서 yes였던 쓰기 요청이 어드미션 단계에서 403으로 막혔어요. 인가는 사용자 이름, 동작, 리소스, 네임스페이스 같은 요청의 겉모습만 보고 판단해요. 지우려는 파드의 spec.nodeName이 무엇인지는 객체 내용을 봐야 알 수 있는데 그건 어드미션이 하는 일이에요. kubeadm이 API 서버에 --enable-admission-plugins=NodeRestriction을 넣어 두는 이유가 여기 있어요. 노드 객체에 쓰는 실험은 클러스터 전체에 영향을 줄 수 있어서 하지 않았어요. 문서에는 NodeRestriction이 kubelet에게 자기 Node 객체만 고치게 하고 taint를 고치거나 지우지 못하게 한다고 적혀 있어요.

5. 401과 403을 만나면 메시지로 어느 관문에서 막혔는지 가린다

여기까지 실험에서 나온 오류 문구를 관문별로 모았어요. 어드미션 줄은 33편의 실험과 이번 편 4절(NodeRestriction)에서 나온 것이고 나머지는 이번 편 원자료에 찍힌 문구예요.

이렇게 나오면막힌 곳먼저 볼 곳
Unable to connect to the server: tls: failed to verify certificate: x509: certificate signed by unknown authority0. TLSkubeconfig의 certificate-authority-data와 server 주소가 같은 클러스터의 것인지
Error from server (BadRequest): the server rejected our request for an unknown reason (https 포트에 http로 보냄)0. TLSserver 주소가 https://로 시작하는지
error: You must be logged in to the server (the server has asked for the client to provide credentials) = 4011. 인증토큰이 틀렸거나 서명이 맞지 않는지, 클라이언트 인증서가 만료됐는지. kubectl auth whoami가 되는지
User "system:anonymous" cannot list resource ... = 4032. 인가(자격이 안 실림)요청에 인증서나 토큰이 실렸는지
User "system:serviceaccount:w32:reader" cannot list resource "pods" ... = 4032. 인가(RBAC)kubectl auth can-i ... --as=, 그 이름에 걸린 RoleBinding
node: no relationship found between node ..., only its own Node object2. 인가(Node 인가자)kubelet 자격으로 다른 노드의 객체를 요청했는지
is forbidden: failed quota, exceeded quota, maximum memory usage per Container, violates PodSecurity, error looking up service account, node "..." can only ... = 4033. 어드미션ResourceQuota, LimitRange, 네임스페이스 라벨, ServiceAccount 이름, 컨트롤러가 만든 객체면 이벤트(33편)
Error from server (NotFound): namespaces "w32-none" not found3. 어드미션(NamespaceLifecycle)네임스페이스 이름

표를 만들고 보니 이번에 본 403은 두 가지 모양으로 나뉘었어요. 인가에서 막힌 403에는 User "..." cannot <동작> resource 문구가 붙었고 어드미션에서 막힌 403에는 그 문구 대신 플러그인이 적은 이유가 붙었어요. 그래서 Forbidden을 만나면 메시지에 User 이름이 있는지부터 확인해요. 이름이 있으면 그 이름이 내가 생각한 사용자인지 확인하고(system:anonymous라면 자격이 실리지 않은 거예요) 이름이 없으면 네임스페이스에 걸린 정책을 봐요.

💡 실무에서는: 관문 순서대로 하나씩 확인해요
• 연결부터 안 되면 kubectl config view --minify로 지금 컨텍스트의 server 주소와 CA를 봐요
• 401이면 kubectl auth whoami로 API 서버가 나를 누구로 보는지 확인해요. 토큰을 확인할 때는 다른 자격을 빼고 토큰만 보내요(10편)
• 인가 403이면 kubectl auth can-i <동작> <리소스> -n <네임스페이스>로 물어보고 관리자라면 --as로 그 사용자가 되어 물어봐요. --list를 붙이면 그 네임스페이스에서 할 수 있는 일 전체가 나와요
• 어드미션 403이면 --dry-run=server로 같은 요청을 저장 없이 다시 보내 봐요(33편). Deployment의 파드 같은 객체는 컨트롤러가 대신 만들기 때문에 이벤트를 확인해요

모든 관문을 통과한 요청은 객체 종류별 검증을 거쳐 etcd에 기록돼요. 그 뒤에 kubectl이 보여 주는 resourceVersion이 etcd 키의 리비전과 어떻게 이어지는지는 22편에서 봤어요.

✍️ 오늘의 요약
401은 인증에서 나오고 인가에서 막힌 403에는 User 이름이 찍혀요.

kubectl 요청은 TLS로 서버를 확인한 뒤 인증에서 사용자 이름과 그룹을 얻고 인가에서 그 이름으로 규칙을 찾아요. 이름은 클라이언트 인증서의 CN과 O, ServiceAccount 토큰의 서명된 내용에서 나왔어요. 자격이 없는 요청은 system:anonymous로 인증된 뒤 인가에서 403을 받았고 틀린 토큰은 익명으로 넘어가지 못해서 공개 경로인 /version에서도 401을 받았어요. 같은 ServiceAccount 토큰의 응답이 w32의 RoleBinding 하나로 403에서 200으로 바뀌었고 kubelet은 Node 인가자와 NodeRestriction 때문에 자기 노드의 객체만 읽고 고칠 수 있었어요. 403은 어드미션에서도 나오니(33편) Forbidden을 보면 메시지에 User 이름이 있는지부터 봐요. 401과 403을 만나면 관문을 앞에서부터 하나씩 짚어 가요.
