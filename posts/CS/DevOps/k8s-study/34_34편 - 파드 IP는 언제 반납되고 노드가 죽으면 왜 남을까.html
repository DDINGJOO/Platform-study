1. 파드 IP는 RunPodSandbox 안의 CNI ADD에서 정해진다

IP가 정해지는 순간을 잡으려고 worker1에 pause 이미지 파드 ipam-demo를 하나 띄웠어요(nodeSelector로 worker1 고정). 파드를 만들기 전 worker1의 블록 10.244.194.64/26은 64칸 중 8칸을 쓰고 있었고 IPAM 핸들(IP가 누구 몫인지 적어 둔 기록)은 23개, worker1의 cali 인터페이스(파드마다 노드 쪽에 생기는 veth)는 7개였어요. 파드 7개가 7칸을 쓰고 남은 한 칸은 노드의 tunl0 주소(10.244.194.64)로 보여요. 4절의 ipam check도 파드 IP와 별도로 노드 터널 IP를 세요.

📖 용어: IPAM 블록과 빈칸 목록
Calico IPAM은 IP 풀(이 클러스터는 10.244.0.0/16)을 64칸(/26)짜리 블록으로 잘라 노드마다 붙여 두고 파드가 뜰 때 그 노드 블록의 빈칸에서 IP를 하나씩 꺼내요. 블록마다 어느 칸을 누가 쓰는지와 아직 비어 있는 칸의 목록(unallocated)이 함께 기록돼요. 이 블록이 노드의 podCIDR과 상관없다는 점은 31편에서 봤어요.

그다음 containerd 로그와 Calico CNI 로그(/var/log/calico/cni/cni.log)에서 이 파드의 줄만 골라 시간순으로 합쳤어요.

그림 1. IP 할당과 veth 설정(.222~.242)은 모두 RunPodSandbox(.160~.283) 안에서 끝났고 앱 컨테이너는 그다음에 만들어졌다

IPAM 요청부터 기록까지는 약 20ms가, RunPodSandbox 전체는 123ms가 걸렸어요. 파드 IP는 앱 컨테이너를 만들기도 전에 RunPodSandbox 안에서 정해져요. 또 IPAM 핸들 이름에 들어가는 ID는 앱 컨테이너 ID(6200a7ce1f7a…)가 아니라 sandbox ID예요. 27편에서 본 대로 파드 IP는 컨테이너가 아니라 파드 안 컨테이너들이 함께 쓰는 샌드박스에 붙기 때문이에요.

📖 용어: CNI ADD와 DEL
CNI 스펙이 정한 명령이에요. 컨테이너 런타임이 플러그인 실행 파일을 ADD로 부르면 플러그인은 컨테이너 네트워크 네임스페이스에 인터페이스를 만들고 결과(IP 등)를 반환해요. DEL로 부르면 ADD가 한 일을 되돌려요. 스펙에는 "IPAM 플러그인을 알맞은 순간에 부르는 것은 런타임이 아니라 CNI 플러그인의 책임"이라고 적혀 있어요.

CNI를 부르는 쪽이 kubelet이 아니라 containerd인 것도 쿠버네티스 버전에 따라 달라진 부분이에요. 쿠버네티스 네트워크 플러그인 문서에 따르면 예전 버전에는 kubelet이 cni-bin-dir와 network-plugin 플래그로 CNI 플러그인을 관리할 수 있었고 이 플래그들은 1.24에서 빠졌어요. 지금은 컨테이너 런타임이 CNI 플러그인을 불러요.

그림 3. 블록의 칸 하나, 핸들 하나, 노드의 veth와 /32 경로 하나가 같이 생겼다

Calico 데이터스토어에는 블록의 사용 칸이 8에서 9로, 핸들이 23개에서 24개로 늘었어요. 10.244.194.103은 블록 시작 주소(.64)에서 39칸 떨어져 있어서 블록의 39번 칸에 기록됐고 그 칸에는 네임스페이스, 노드, 파드 이름, 시각이 함께 적혔어요. 핸들 k8s-pod-network.347b3b3ed2f4…에는 "이 블록에서 1개"라는 기록이 들어 있어요.

📖 용어: IPAM 핸들(IPAMHandle)
Calico IPAM이 "이 IP들은 누구 몫인가"를 적는 기록이에요. Calico CNI는 핸들 이름을 k8s-pod-network.<sandbox ID>로 짓고 반납할 때 이 이름으로 IP를 찾아 돌려줘요(DEL 로그의 "Releasing address using handleID"). 블록(IPAMBlock)은 칸마다 누가 쓰는지 적고 핸들은 주인마다 어떤 IP를 쓰는지 적어요.

파드 객체에는 cni.projectcalico.org/containerID, podIP, podIPs annotation이 붙었어요. 로그의 "Wrote updated endpoint to datastore"가 바로 이 annotation을 붙인 기록이에요. Calico가 쿠버네티스 API를 데이터스토어로 쓸 때 WorkloadEndpoint를 저장하는 동작은 파드에 annotation을 PATCH하는 거예요. v3.33.0 소스(workloadendpoint.go) 주석에는 PodStatus를 직접 고치면 kubelet의 변경과 경합하기 때문에 annotation에 둔다고 적혀 있어요. pod.status.podIP는 kubelet이 채워요. kubelet v1.37.2 소스(kuberuntime_sandbox.go의 determinePodSandboxIPs)를 보면 kubelet은 CRI의 PodSandboxStatus에 담긴 네트워크 정보에서 파드 IP를 읽어요.

worker1 노드에는 veth cali38cdd514d42와 10.244.194.103 dev cali38cdd514d42 scope link 경로가 생겼어요. 이 /32 경로는 6편과 30편에서 본 blackhole 10.244.194.64/26보다 범위가 좁아 먼저 선택되기 때문에 노드에서 보낸 ping이 파드에 닿았어요(1 received).

veth 이름은 네임스페이스와 파드 이름으로 정해진다

cali 뒤의 11글자는 무작위가 아니에요. v3.33.0 소스(workload_endpoint_default.go의 VethNameForWorkload)를 보면 이래요.

h := sha1.New() h.Write(fmt.Appendf(nil, "%s.%s", namespace, podname)) prefix := os.Getenv("FELIX_INTERFACEPREFIX") if prefix == "" { // Prefix is not set. Default to "cali" prefix = "cali" } ... return fmt.Sprintf("%s%s", prefix, hex.EncodeToString(h.Sum(nil))[:11])

→ "네임스페이스.파드이름"의 SHA-1 해시를 16진수로 바꿔 앞 11자를 잘라 내고 그 앞에 cali를 붙인다는 뜻이에요. 그래서 이름은 cali 4자와 해시 11자를 합쳐 15자예요. 직접 계산해 보면 실제 이름과 같아요.

$ python3 -c "import hashlib; print('cali' + hashlib.sha1(b'default.ipam-demo').hexdigest()[:11])" cali38cdd514d42 # worker1 의 실제 veth 이름도 cali38cdd514d42 $ python3 -c "import hashlib; print('cali' + hashlib.sha1(b'default.myweb-859c4764d4-scshl').hexdigest()[:11])" calicd0b7984a6e # worker1 의 실제 veth 이름도 calicd0b7984a6e

해시를 만들 때 노드나 시각은 들어가지 않으니 같은 네임스페이스에서 같은 이름으로 다시 만든 파드는 같은 veth 이름을 받아요. 실제로 default/ipam-demo를 두 번 만들었더니 IP는 처음에 .102, 두 번째에 .103으로 달랐지만 veth는 두 번 다 cali38cdd514d42였어요.

💡 실무에서는: 파드 이름으로 노드의 cali 인터페이스를 찾아요
• 노드에서 특정 파드의 패킷만 tcpdump로 보고 싶을 때 위 계산으로 인터페이스 이름을 바로 얻을 수 있어요. FELIX_INTERFACEPREFIX를 바꾼 클러스터라면 그 값의 첫 항목이 접두어예요
• 직접 계산하기 번거롭다면 calicoctl get workloadendpoints -n <네임스페이스> -o wide의 INTERFACE 열에 같은 이름이 나와요
• 노드에서 ip route get <파드 IP>를 실행해도 그 파드로 가는 cali 장치가 나와요

2. 파드를 지우면 StopPodSandbox 안의 CNI DEL이 IP를 돌려준다

15:26:38에 kubectl delete pod ipam-demo를 실행했어요. 같은 방법으로 모은 삭제 과정의 로그는 이래요.

15:26:39.250 [containerd] "StopContainer for "6200a7ce1f7a…" with timeout 30 (s)" 15:26:39.284 [containerd] "StopContainer for "6200a7ce1f7a…" returns successfully" 15:26:39.284 [containerd] "StopPodSandbox for "347b3b3ed2f4…"" 15:26:39.343 [calico-cni] cni-plugin/k8s.go 669: Releasing IP address(es) ContainerID="347b3b3ed2f4…" 15:26:39.382 [calico-cni] ipam/ipam_plugin.go 942: Released address using handleID ContainerID="347b3b3ed2f4…" HandleID="k8s-pod-network.347b3b3ed2f4… 15:26:39.386 [containerd] "StopPodSandbox for "347b3b3ed2f4…" returns successfully" 15:26:39.386 [containerd] "TearDown network for sandbox "347b3b3ed2f4…" successfully"

· .284 StopPodSandbox가 시작됐어요.
· .343~.382 calico가 DEL을 받아 "Releasing IP address(es)"를 찍었고 calico-ipam이 핸들 이름으로 IP를 반납했어요(Released address using handleID).
· .386 containerd가 "TearDown network for sandbox ... successfully"를 찍고 StopPodSandbox를 마쳤어요.

15:26:40에 다시 보니 블록은 8/64, 핸들은 23개, cali 인터페이스는 7개로 돌아와 있었어요. 핸들을 조회하자 NotFound가 나왔고 10.244.194.103으로 가는 경로도 사라졌어요. 삭제 명령부터 원래 상태로 돌아오기까지 2초가 채 걸리지 않았어요. IP가 반납되는 시점은 파드 객체가 지워질 때가 아니라 노드에서 StopPodSandbox가 CNI DEL을 실행할 때예요.

IP를 반납하는 시점이 StopPodSandbox라는 점은 CRI 정의에도 나와 있어요. cri-api의 api.proto에는 StopPodSandbox가 이렇게 설명돼 있어요.

// StopPodSandbox stops any running process that is part of the sandbox and // reclaims network resources (e.g., IP addresses) allocated to the sandbox. // ... // kubelet will call StopPodSandbox // at least once before calling RemovePodSandbox. It will also attempt to // reclaim resources eagerly, as soon as a sandbox is not needed. Hence, // multiple StopPodSandbox calls are expected.

→ StopPodSandbox가 샌드박스의 프로세스를 멈추고 IP 같은 네트워크 자원을 거둬들인다는 뜻이에요. kubelet은 RemovePodSandbox 전에 이 호출을 적어도 한 번 하고 여러 번 할 수도 있어요.

실제로 DEL은 한 번으로 끝나지 않았어요. 약 43초 뒤 kubelet이 샌드박스를 정리하면서 StopPodSandbox와 RemovePodSandbox를 다시 불렀고 그때마다 CNI DEL이 또 돌았어요.

15:27:21.886 [containerd] "StopPodSandbox for "347b3b3ed2f4…"" 15:27:21.921 [calico-cni] cni-plugin/k8s.go 669: Releasing IP address(es) ContainerID="347b3b3ed2f4…" 15:27:21.950 [calico-cni] ipam/ipam_plugin.go 940: Asked to release address but it doesn't exist. Ignoring ... 15:27:22.017 [containerd] "RemovePodSandbox "347b3b3ed2f4…" returns successfully"

→ 이미 반납한 IP를 또 반납하라는 요청을 받았지만 없는 주소라 무시하고 성공으로 끝냈다는 뜻이에요. CNI 스펙도 플러그인이 같은 컨테이너에 대한 DEL을 여러 번 받아들이고 지울 것이 이미 없으면 성공으로 응답해야 한다고 정해요. 스펙에는 DEL이 "할 수 있는 만큼 하는(best-effort)" 명령이라서 IPAM 플러그인은 네트워크 네임스페이스가 이미 없어도 IP를 반납하고 성공으로 끝내야 한다는 설명도 있어요.

반납한 칸은 빈칸 목록 맨 뒤로 간다

삭제 뒤 15:26:49에 블록의 빈칸 목록(unallocated) 앞뒤를 봤어요. 앞 다섯 칸은 40번(.104)부터 44번(.108)까지였고 뒤 다섯 칸은 24번(.88), 25번(.89), 34번(.98), 38번(.102), 39번(.103)이었어요. 방금 반납한 39번은 맨 끝에 있었어요.

이유는 v3.33.0 소스(libcalico-go/lib/ipam/ipam_block.go)에 있어요. 블록을 새로 만들 때 빈칸 목록에 0번부터 63번까지 차례로 넣어 두고 할당(autoAssign)할 때는 목록 앞에서부터 꺼내요. 반납한 칸은 garbageCollect가 목록 끝에 붙이는데 소스 주석에는 이곳이 "칸이 빈칸 목록에 들어가는 유일한 곳"이라고 적혀 있어요. 그래서 ipam-demo를 같은 이름으로 두 번 만들었을 때 처음에는 .102를, 두 번째에는 .102가 아니라 .103을 받았어요. 다음 차례는 목록 맨 앞의 .104예요.

그림 4. 할당은 목록 앞에서 꺼내고 반납은 목록 뒤에 붙이니 방금 돌려준 IP는 한동안 다시 나가지 않는다

다만 이 순서는 재사용을 막는 장치가 아니에요. IPAMConfiguration 문서의 ipCooldownSeconds는 "반납된 IP를 다시 쓰기 전까지의 최소 시간"이고 기본값 0은 "바로 다시 쓸 수 있다"는 뜻이에요. 블록에 빈칸이 몇 개 남지 않았다면 방금 돌려준 IP도 금방 다시 나가요.

⚠️ 주의: 지운 파드의 IP가 곧 다른 파드의 IP가 될 수 있어요
• 반납한 IP가 목록 뒤로 가서 한동안 다시 나가지 않는 것은 관찰한 순서일 뿐이고 기본 설정(ipCooldownSeconds 0)은 재사용을 막지 않아요
• 파드 IP를 방화벽 허용 목록이나 다른 시스템 설정에 그대로 적어 두면 그 IP를 나중에 받은 엉뚱한 파드가 같은 권한을 얻을 수 있어요. 파드 IP 대신 Service나 라벨 기반 정책으로 묶어요
• 반납 뒤 일정 시간 재사용을 막아야 한다면 IPAMConfiguration의 ipCooldownSeconds(0~1200초)를 검토해요

3. 파드 객체가 사라져도 IP는 몇 초 뒤에 돌아온다

파드 하나가 아니라 여러 개를 한꺼번에 지우면 순서가 더 잘 보여요. 31편에서 worker2의 블록 10.244.126.0/26(64칸 중 6칸 사용)을 채우려고 pause 파드 62개를 Deployment ipam-fill로 만들었어요. terminationGracePeriodSeconds를 0으로 준 Deployment예요. 다 뜬 뒤 첫 블록은 64/64, 새로 붙은 두 번째 블록 10.244.126.64/26은 4/64를 쓰고 있었어요. 이 Deployment를 지울 때의 기록은 이래요.

# 31-ipam-blocks.txt 발췌 (블록 표는 worker2 의 두 블록만) 15:29:49 kubectl delete deploy ipam-fill 15:29:54 ipam-fill 파드 0개 | worker2 블록: 10.244.126.0/26 10.244.126.64/26 | Block | 10.244.126.0/26 | 64 | 30 (47%) | 0 (0%) | 34 (53%) | | Block | 10.244.126.64/26 | 64 | 1 (2%) | 0 (0%) | 63 (98%) | 15:30:03 worker2 블록: 10.244.126.0/26 10.244.126.64/26 | 10.244.126.0/26 사용 6 (9%) , 10.244.126.64/26 사용 0 (0%) | …

15:29:49에 Deployment를 지웠어요. 15:29:54에는 ipam-fill 파드가 0개였는데 IPAM은 그 순간에도 첫 블록 30칸, 두 번째 블록 1칸을 쓰고 있었어요. 15:30:03에 확인했을 때에야 6칸과 0칸으로 돌아왔어요. 지운 지 약 14초 뒤예요.

그사이 Calico 데이터를 정리하는 calico-kube-controllers의 로그에도 흔적이 남았어요. 15:29:50.869부터 15:29:53.886까지 ipam-fill 파드 62개의 IP마다 Candidate IP leak(누수 후보) 로그가 한 줄씩 찍혔어요. 컨트롤러가 "이 IP의 주인 파드가 API에 없다"고 판단했다는 뜻이에요. 그 뒤 노드의 CNI DEL이 IP를 반납하면서 후보는 저절로 사라졌고 로그 전체에서 Confirmed IP leak(누수 확정)은 0줄이었어요.

terminationGracePeriodSeconds를 기본값(30초)으로 두고 지운 ipam-demo는 DEL을 마친 뒤에 삭제 명령이 끝났는데 이 값을 0으로 준 ipam-fill에서는 순서가 반대였어요. 파드 객체가 먼저 사라지고 IP는 노드가 샌드박스를 정리하는 속도대로 뒤따라 돌아왔어요. 파드 객체가 사라졌다고 IP 반납까지 끝난 것은 아니에요. 지우자마자 IPAM 사용량이나 IP 수를 세면 실제보다 많게 나와요.

그림 5. 점은 측정한 시각에 본 값이다. 반납된 IP가 모두 돌아와도 비어 버린 두 번째 블록은 15분 넘게 worker2에 붙어 있었다

4. 빈 블록과 새는 IP는 calico-kube-controllers가 치운다

IP가 다 돌아온 뒤에도 비어 버린 두 번째 블록 10.244.126.64/26은 worker2에 붙어 있었어요(15:31:56 확인까지). 이 블록이 반납된 것은 15:45:25였고 calico-kube-controllers 로그에 그 순간이 남아 있어요.

그림 6. 로그 시각은 UTC다. 06:45:25 UTC는 한국 시각 15:45:25이고 빈 블록이 된 지 약 15분 22초 뒤다
📖 용어: calico-kube-controllers의 node 컨트롤러와 leakGracePeriod
calico-kube-controllers는 쿠버네티스 API를 지켜보며 Calico 쪽 데이터를 정리하는 Deployment예요. kube-controllers 문서에 따르면 그 안의 node 컨트롤러가 IP 주소의 가비지 컬렉션(쓰지 않는 IP를 찾아 정리하는 일)을 맡아요. KubeControllersConfiguration 문서의 leakGracePeriod는 "누수로 의심되는 IP를 치울 때 쓰는 유예 시간"이고 기본값은 15m이에요.

빈 블록을 언제 반납하는지는 v3.33.0 소스(kube-controllers/pkg/controllers/node/ipam.go의 releaseUnusedBlocks)에 조건으로 적혀 있어요.

· 블록이 비어 있어야 해요.
· 그 노드에 다른 블록이 적어도 하나 더 있어야 해요. 그래서 노드의 마지막 블록은 비어도 반납하지 않아요.
· 그 노드가 Flannel에서 옮겨 오는 중이 아니어야 해요.
· 이 상태가 유예 시간(기본 15분)보다 오래 이어져야 해요. 주석에는 IP를 할당하는 동안 잠깐 빈 블록이 생길 수 있어서 바로 지우지 않는다고 적혀 있어요.

점검 주기는 leakGracePeriod의 절반이에요. 로그 첫머리의 Will run periodic IPAM sync every 7m30s가 그 값이고 실제로 전체 점검이 7분 30초 간격으로 찍혔어요. 그런데 반납 시각 15:45:25는 전체 점검 시각(15:41:58, 15:49:28)과 겹치지 않아요. 소스를 보면 releaseUnusedBlocks는 주기 점검 때만이 아니라 데이터스토어 변화 등으로 IPAM 동기화가 돌 때마다 불려요. 15분이 지난 뒤 처음 돈 동기화에서 반납된 것으로 보여요. worker2의 원래 블록 10.244.126.0/26은 노드의 마지막 블록이라 그대로 남았어요. 기본 설정에서 살아 있는 노드의 빈 블록은 15분 넘게 그대로 남고 그 노드에 다른 블록이 있을 때만 반납돼요.

노드가 갑자기 죽으면 DEL이 불리지 않는다

지금까지 본 반납은 모두 노드의 containerd가 CNI DEL을 실행해서 이뤄졌어요. 노드 전원이 갑자기 꺼지면 그 노드의 파드를 지워도 DEL을 실행할 주체가 없어서 IPAM에는 할당 기록이 남아요. 이렇게 남은 IP도 node 컨트롤러가 치워요. 같은 ipam.go의 checkAllocations 주석에 정리된 규칙은 이래요.

· 할당 기록이 가리키는 파드가 쿠버네티스 API에 없거나 파드의 IP가 다르면 누수 후보가 돼요.
· 후보 상태가 유예 시간(leakGracePeriod) 이상 이어지거나 그 노드가 API에서 지워졌으면 누수로 확정하고 IP를 반납해요.
· 노드가 API에서 지워졌고 그 노드에 유효한 할당이 남지 않았으면 노드의 블록 연결(affinity)도 풀어요.
· leakGracePeriod를 0으로 두면 유예 시간이 지나도 누수를 확정하지 않고 빈 블록도 반납하지 않아요. ipam_allocation.go의 주석에서는 이 설정을 "사용자가 IPAM GC를 끈 것"으로 봐요. 다만 API에서 지워진 노드의 IP는 그래도 확정 대상이에요.

3절의 62줄짜리 누수 후보 로그가 이 규칙의 첫 단계였어요. 그때는 DEL이 곧 와서 후보 단계에서 끝났어요. 위 규칙은 소스와 문서로 확인한 동작이에요. 노드를 실제로 멈춰 보니 이 규칙이 아예 돌지 않은 경우가 있었는데 그 이야기는 5절에서 이어 가요.

누수가 있는지는 calicoctl ipam check로 본다

그림 7. IPAM에 기록된 할당 23개가 노드 터널 IP 4개와 파드 IP 19개를 더한 값과 같았고 문제는 0개였다

ipam check 레퍼런스에서는 이 명령을 "Calico IPAM 자료 구조의 무결성을 확인하고 새거나 잘못 할당된 IP를 보고한다"라고 설명해요. 이 클러스터에서는 블록 4개에 기록된 할당이 23개였고 실제로 쓰는 IP도 노드 터널 IP 4개와 파드(workload) IP 19개를 더한 23개였어요. IPAM에 기록됐지만 쓰지 않는 IP, 쓰고 있지만 기록이 없는 IP, IP 없이 남은 핸들은 모두 0개였어요. 같은 시각 calicoctl ipam show로 보니 풀의 IP 65,536개 중 23개를 쓰고 있었어요.

누수가 나왔을 때 정리하는 절차도 레퍼런스에 있어요. 데이터스토어를 잠그고(calicoctl datastore migrate lock) calicoctl ipam check -o report.json으로 보고서를 만든 뒤 calicoctl ipam release --from-report report.json으로 IP를 반납한 다음 잠금을 풀어요(calicoctl datastore migrate unlock). 문서에는 잠근 동안 새 파드를 띄울 수 없다는 주의가 붙어 있어요.

5. 노드가 죽은 동안에는 20분이 지나도 누수가 정리되지 않았다

4절의 규칙대로라면 노드가 죽어 DEL이 오지 않아도 새는 IP는 leakGracePeriod(15분)가 지난 뒤 정리돼야 해요. 25편의 축출 실험과 같은 시간대에 이 장면을 직접 기록했어요. 17:22:41에 worker3의 kubelet을 멈췄고 17:23:26 확인부터 worker3은 Ready=Unknown이었어요. 파드의 toleration 300초가 지나자 17:28:26에 다른 노드에 myweb 파드 두 개가 새로 만들어졌어요. worker3에 있던 옛 파드 두 개(bn4k8의 10.244.100.228, zjdrs의 10.244.100.251)는 지울 kubelet이 없어서 Terminating으로 남았어요. 17:30:49에 이 둘을 --grace-period=0 --force로 강제 삭제했어요.

📖 용어: 파드 강제 삭제 (--grace-period=0 --force)
kubelet이 노드에서 파드를 멈췄다는 확인을 기다리지 않고 API에서 파드 객체를 바로 지우는 방법이에요. 쿠버네티스 파드 수명 주기 문서에 따르면 강제로 삭제하면 API 서버는 kubelet의 종료 확인을 기다리지 않고 파드를 API에서 바로 지워요. 이때 실제로 돌던 리소스는 클러스터에서 계속 돌 수도 있어요.
그림 8. 강제 삭제부터 17:50:57까지 약 20분 동안 ipam check는 매번 "쓰지 않는데 할당된 IP 2개"를 보고했다

강제 삭제로 파드 객체는 API에서 바로 사라졌지만 worker3에서는 그 IP를 쓰던 nginx 컨테이너 2개가 아직 돌고 있었어요. DEL을 실행할 kubelet이 없으니 IPAM 기록도 그대로였어요. ipam check는 강제 삭제 직후부터 약 1분 간격으로 17:50:57(+1207초)까지 매번 Found 2 IPs that are allocated in IPAM but not actually in use를 보고했어요. leakGracePeriod 15분을 넘긴 뒤에도 두 IP는 정리되지 않았어요.

원인은 calico-kube-controllers 쪽에 있었어요. 실험을 시작할 때 calico-kube-controllers 파드도 worker3에 있었고 myweb과 함께 쫓겨나 17:28:27에 마스터에서 새로 떴어요. 새 인스턴스의 로그는 이래요(시각은 UTC라서 9시간을 더하면 한국 시각이에요).

v3.33.0 소스를 따라가면 세 단계가 이어져요.

· kube-controllers는 데이터스토어의 상태 변화를 DataFeed 하나로 받아 등록된 컨트롤러들에 넘겨요. syncer.go의 OnStatusUpdated는 등록된 함수를 for 문으로 하나씩 호출하고 앞의 호출이 끝나야 다음 호출로 넘어가요. IPAM 정리를 맡은 node 컨트롤러, LoadBalancer 컨트롤러, 정책 이름 마이그레이터가 이 피드 하나를 함께 써요(run.go).
· 정책 이름 마이그레이터는 상태를 버퍼 없는 채널로 받아요. 그런데 policy_name_migrator.go의 run은 calico-node DaemonSet의 NumberUnavailable이 0이 될 때까지 5초마다 확인만 하고 그 채널을 읽지 않아요. 버퍼 없는 채널은 받는 쪽이 읽어야 보내는 쪽이 다음으로 넘어가니 OnStatusUpdated가 첫 상태를 넘기다 멈췄어요.
· IPAM 컨트롤러는 in-sync를 받지 못했어요. ipam.go의 syncIPAM은 상태가 InSync가 아니면 아무 일도 하지 않고 바로 끝나요. 4절에서 본 누수 확정과 빈 블록 반납은 모두 이 함수 안에서 돌아요.

// syncer.go: 상태 알림을 등록된 컨트롤러에 차례로, 동기로 넘긴다 func (d *DataFeed) OnStatusUpdated(status bapi.SyncStatus) { logrus.Infof("Node controller syncer status updated: %s", status) for _, f := range d.statusRegistrations { f(status) } } // policy_name_migrator.go: 버퍼 없는 채널로 보낸다 (statusUpdates: make(chan bapi.SyncStatus)) func (c *policyMigrator) onStatusUpdate(status bapi.SyncStatus) { c.statusUpdates <- status } // ipam.go: InSync가 아니면 IPAM 정리를 건너뛴다 if c.syncStatus != bapi.InSync { log.WithField("status", c.syncStatus).Debug("Syncer not currently InSync, skipping IPAM sync.") return nil }

→ 마이그레이터가 채널을 읽지 않는 동안 DataFeed는 그 자리에서 기다리고 IPAM 컨트롤러는 InSync를 받지 못해 정리를 건너뛴다는 뜻이에요. worker3의 calico-node가 unavailable인 동안 이 상태가 17:28:27부터 17:52:02까지 약 23분 35초 이어졌어요.

그림 9. 첫 상태(wait-for-ready)가 마이그레이터에서 막히자 같은 피드를 쓰는 IPAM 컨트롤러에는 in-sync가 오지 않았다

그럼 두 IP는 누가 돌려줬을까요? 17:51:57에 worker3의 kubelet을 다시 켜자 1초 뒤부터 worker3의 CNI 로그에 DEL이 찍혔어요.

# worker3 /var/log/calico/cni/cni.log 발췌 (KST, ContainerID 는 앞 12자) 17:51:58.477 cni-plugin/k8s.go 669: Releasing IP address(es) ContainerID="d3de25b89cca…" 17:51:58.542 ipam/ipam_plugin.go 942: Released address using handleID ContainerID="566f80d33a6c…" 17:51:58.643 ipam/ipam_plugin.go 942: Released address using handleID ContainerID="d3de25b89cca…" 17:51:59.469 ipam/ipam_plugin.go 942: Released address using handleID ContainerID="d471e622a915…" 17:51:59.570 ipam/ipam_plugin.go 942: Released address using handleID ContainerID="3f3d64dd4e0a…"

→ 다시 뜬 kubelet이 남아 있던 샌드박스를 정리했고 그때 2절에서 본 CNI DEL이 돌아 IP를 반납했다는 뜻이에요. 같은 CNI 로그에서 10.244.100.228은 15:48:44에 샌드박스 3f3d64dd4e0a…가 받은 IP였고 17:51:59.570에 반납됐어요. kube-controllers의 전체 점검은 그 뒤인 17:52:03에 시작됐고 누수나 반납 로그를 남기지 않았어요. 그 뒤 worker3의 nginx 컨테이너는 0개였고 10.244.100.228로 가는 경로도 없었으며 ipam check 결과는 found 0 problems였어요. 이번에 새던 IP를 돌려준 것은 kube-controllers의 누수 정리가 아니라 노드가 돌아온 뒤 kubelet이 부른 CNI DEL이었어요.

⚠️ 주의: 노드 장애 직후에는 누수 정리가 시작되지 않을 수 있어요
• 이 클러스터(Calico v3.33.0, 정책 이름 마이그레이터가 켜진 매니페스트 설치)에서는 죽은 노드에 있던 calico-kube-controllers가 다른 노드에서 새로 뜨자 죽은 노드의 calico-node가 돌아올 때까지 IPAM 정리가 한 번도 돌지 않았어요. 4절의 빈 블록 반납(15분 22초)은 kube-controllers가 정상일 때 본 동작이고 15분 누수 규칙도 IPAM 동기화가 in-sync일 때만 돌아요
• Node 객체를 지워 DaemonSet의 unavailable이 0이 되면 풀리는지는 확인하지 않았어요. 기본 브랜치(master)의 세 소스 파일도 2026-11-14 기준 구조가 같았고 IPAM 정리가 멈춘다는 GitHub 이슈는 찾지 못했어요. 마이그레이터의 기다림이 끝나지 않는다는 보고로는 canal 매니페스트에서 DaemonSet 이름이 달라 생긴 이슈(#13912)가 있었어요
• 노드 장애 뒤에는 kube-controllers 로그에 "Waiting for all calico-node pods to be available"이 계속 찍히는지, ipam check에 "allocated in IPAM but not actually in use"가 남는지 직접 봐요
• 죽은 노드의 파드를 강제로 지우면 API에서만 사라져요. 이번에도 그 노드에서는 nginx 컨테이너가 계속 돌았고 IP는 kubelet이 돌아와 DEL을 부른 뒤에야 반납됐어요
💡 실무에서는: IP 누수는 이렇게 점검해요
• 평소에는 calicoctl ipam check만 돌려 "found 0 problems"인지 봐요. 이 명령은 잠그지 않고 읽기만 해요
• 노드를 아예 없앴다면 Node 객체도 지워야 해요. 노드가 API에 남아 있는 동안에는 그 노드의 누수 후보가 leakGracePeriod(기본 15분)를 기다린 뒤에야 확정되고 노드의 마지막 블록도 그 노드에 남아요
• 문제가 나왔다면 레퍼런스의 lock, check -o, release --from-report, unlock 순서를 지켜요. 잠근 동안 파드 생성이 막히니 작업 시간을 잡고 해요
• KubeControllersConfiguration의 leakGracePeriod를 0으로 두면 살아 있는 노드의 누수 확정과 빈 블록 반납이 꺼져요
✍️ 오늘의 요약
파드 IP는 RunPodSandbox 안의 CNI ADD에서 정해지고 StopPodSandbox 안의 CNI DEL에서 반납돼요. DEL을 부를 노드가 죽으면 IP는 남아요.

containerd가 실행한 calico 플러그인이 calico-ipam에 IP 고르기를 맡겼고 calico-ipam은 노드 블록의 빈칸 하나와 핸들 하나로 그 IP를 기록했어요. IP는 앱 컨테이너보다 먼저 정해졌고 veth 이름은 네임스페이스와 파드 이름의 해시라서 같은 이름이면 같았어요. 파드를 지우자 StopPodSandbox 안의 CNI DEL이 핸들 이름으로 IP를 반납했고 DEL은 여러 번 와도 성공으로 끝났어요. 반납한 칸은 빈칸 목록 맨 뒤로 갔지만 기본 설정이 재사용을 막지는 않아요. 파드 객체가 먼저 사라져도 IP는 약 14초 뒤에 돌아왔고 비어 버린 블록은 약 15분 22초 뒤에 calico-kube-controllers가 반납했어요. 노드가 죽어 DEL이 오지 않는 IP는 규칙상 같은 컨트롤러가 leakGracePeriod를 기준으로 치워요. 다만 이 클러스터에서는 죽은 노드에 있던 kube-controllers가 다른 노드에서 다시 뜬 뒤 정책 이름 마이그레이터에 막혀 그 정리가 시작되지 않았고 IP 2개는 노드가 돌아와 kubelet이 부른 CNI DEL로 반납됐어요. 노드 장애 뒤에는 calicoctl ipam check로 누수를 직접 확인해요.
