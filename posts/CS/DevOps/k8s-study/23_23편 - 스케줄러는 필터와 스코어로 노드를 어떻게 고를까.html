1. 스케줄러는 파드의 노드 이름 한 칸을 채우고 끝난다

kube-scheduler 문서는 스케줄러를 이렇게 설명해요. "A scheduler watches for newly created Pods that have no Node assigned." 노드가 아직 정해지지 않은 새 파드를 지켜보다가 하나씩 맡아서 그 파드가 돌 노드를 고른다는 뜻이에요. 고른 결과를 API 서버에 알리는 과정을 문서에서는 바인딩(binding)이라고 불러요. 2편에서 본 대로 바인딩이 끝나면 파드의 spec.nodeName에 노드 이름이 들어가요. 스케줄러가 하는 일은 여기까지예요. 컨테이너를 띄우는 쪽은 그 노드의 kubelet이에요. kubelet은 API 서버를 지켜보다가 자기 노드 이름이 적힌 파드를 발견하면 컨테이너를 띄워요. 19편에서 본 허브 구조대로 스케줄러와 kubelet은 서로 직접 통신하지 않고 API 서버만 거쳐요.

노드를 고르는 방법은 같은 문서에 두 단계로 적혀 있어요.

kube-scheduler selects a node for the pod in a 2-step operation: 1. Filtering 2. Scoring

→ 필터링 단계는 "파드를 놓을 수 있는(feasible) 노드의 집합"을 찾고 스코어링 단계는 "남은 노드에 순위를 매겨" 가장 알맞은 곳을 고른다는 뜻이에요. 문서에 따르면 점수가 같은 노드가 여럿일 때 스케줄러는 그중 하나를 무작위로 고르고 알맞은 노드가 하나도 없으면 파드는 스케줄되지 않은 채(unscheduled) 남아요. 우리가 본 Pending이 바로 이 상태예요.

📖 용어: 스케줄링 프레임워크와 플러그인
스케줄러가 파드 하나를 처리하는 과정을 여러 단계로 나누고 단계마다 동작을 끼울 자리(확장 지점, extension point)를 정해 둔 구조예요. 필터 규칙도 점수 규칙도 모두 이 자리에 등록된 플러그인이에요. Scheduling Framework 문서에 따르면 이 구조는 v1.19부터 stable이고 플러그인은 스케줄러 안에 함께 컴파일돼 있어요.

두 단계라고 했지만 실제로는 그 앞뒤에도 단계가 더 있어요. Scheduling Framework 문서가 정한 순서를 그림으로 옮기면 이래요.

그림 1. 필터와 스코어는 스케줄링 사이클 가운데 두 칸이고 바인딩은 따로 돈다

문서의 설명을 단계별로 줄이면 이래요. PreEnqueue는 파드를 큐에 넣기 전에 검사하는 자리이고 QueueSort는 큐 안의 파드 순서를 정해요. PreFilter와 Filter는 노드를 걸러 내는 자리예요. Filter 단계에서는 노드마다 필터 플러그인을 정해진 순서로 부르다가 하나라도 "안 된다"고 하면 그 노드의 나머지 플러그인은 부르지 않아요. PostFilter는 통과한 노드가 하나도 없을 때만 불리는데 문서에서는 대표 구현으로 선점(preemption)을 들어요. PreScore·Score·NormalizeScore는 점수를 매기는 자리이고 Reserve는 바인딩이 끝나기 전에 그 노드의 자원을 이 파드 몫으로 잡아 두는 자리예요. Permit은 바인딩을 허락하거나 미루거나 거절할 수 있어요.

문서에서는 한 번의 시도를 스케줄링 사이클과 바인딩 사이클로 나누고 "Scheduling cycles are run serially, while binding cycles may run concurrently."라고 설명해요. 노드를 고르는 일은 한 번에 파드 하나씩 차례로 하고 고른 결과를 API 서버에 쓰는 일은 여러 파드 몫을 동시에 할 수 있다는 뜻이에요. Reserve 단계는 이 둘 사이의 틈을 메워요. Reserve 설명에는 "It exists to prevent race conditions while the scheduler waits for the bind to succeed."라는 문장이 있어요. 앞 파드의 바인딩이 끝나기를 기다리는 동안 다음 파드가 같은 자원을 또 차지하지 않게 미리 잡아 둔다는 뜻이에요.

필터는 "이 파드가 갈 수 있는 노드인가"만 보고 스코어는 "갈 수 있는 노드 가운데 어디가 나은가"를 정해요. 두 질문을 따로 떼어 보면 이벤트 메시지도 두 부분으로 나눠 읽을 수 있어요.

2. FailedScheduling 한 줄은 콜론과 쉼표로 끊어 읽는다

도입의 두 파드를 만들고 이벤트를 본 화면이에요.

그림 2. 두 파드 모두 필터에서 네 노드가 전부 빠졌고 라벨을 붙이자 nodeSelector 파드는 worker2로 갔다

CPU 3개짜리 파드(filter-cpu3)의 메시지를 조각내면 이래요.

0/4 nodes are available: 필터를 통과한 노드 0대 / 전체 4대 1 node(s) had untolerated taint(s), 마스터: 허용하지 않은 taint가 있다 (TaintToleration) 3 Insufficient cpu. 워커 3대: CPU가 모자란다 (NodeResourcesFit) preemption: 0/4 nodes are available: PostFilter(선점)가 다시 따져 본 결과 4 Preemption is not helpful for scheduling. 4대 모두 다른 파드를 내보내도 소용없다

→ 앞부분은 필터 단계의 결과이고 "preemption:" 뒤는 PostFilter 단계의 결과예요. 이유 앞의 숫자를 더하면 전체 노드 수와 같아요(1 + 3 = 4).

1 node(s) had untolerated taint(s): 마스터의 taint

📖 용어: taint와 toleration
taint는 노드에 붙이는 "이 조건을 견디는 파드만 오라"는 표시이고 toleration은 파드 쪽에 적는 "나는 그 표시를 견딘다"는 선언이에요. effect가 NoSchedule인 taint가 붙은 노드는 그 taint를 허용하지 않는 새 파드를 받지 않아요. kubeadm은 마스터에 node-role.kubernetes.io/control-plane:NoSchedule을 붙여요(5편).

노드 목록을 taint와 함께 찍어 보면 taint가 있는 노드는 k8s-master 하나예요(24편 실험 기록의 노드 목록). 우리 파드에는 그 taint를 허용하는 toleration이 없으니 마스터는 TaintToleration 플러그인에서 빠졌어요. 이 플러그인 이름은 Scheduler Configuration 문서의 기본 플러그인 목록에 있어요. 마스터는 CPU를 따져 보기도 전에 빠졌어요. Filter는 한 노드에서 플러그인 하나가 "안 된다"고 하면 거기서 멈추기 때문에 마스터가 CPU 3개를 받을 수 있는지는 이 메시지에 나타나지 않아요.

3 Insufficient cpu: requests의 합이 allocatable을 넘는다

워커 세 대는 NodeResourcesFit 플러그인에서 빠졌어요. 이 플러그인은 노드에 이미 배정된 파드의 requests 합에 새 파드의 requests를 더해 노드의 할당 가능량(allocatable)을 넘는지 봐요. 노드마다 allocatable CPU가 2이니 3을 요청한 파드는 빈 노드에도 들어갈 수 없어요.

preemption: 4 Preemption is not helpful: 내보내도 자리가 안 생긴다

📖 용어: 선점 (preemption)
Pod Priority and Preemption 문서에 따르면 파드에는 우선순위(priority)가 있고 파드를 놓을 노드를 찾지 못하면 스케줄러는 우선순위가 더 낮은 파드를 내보내(evict) 자리를 만들려고 해요. 기본 스케줄러에서는 DefaultPreemption 플러그인이 PostFilter 자리에서 이 일을 해요.

필터에서 노드가 모두 빠지자 PostFilter가 불렸고 선점 플러그인이 "다른 파드를 내보내면 들어갈 노드가 있나"를 다시 따졌어요. 네 노드 모두 소용없다는 결과가 나왔어요. 이유는 v1.37.2 소스에서 확인했어요. 필터 플러그인은 "안 된다"는 결과를 두 종류로 나눠 반환해요. 다른 파드가 빠지면 풀릴 수 있는 Unschedulable과 무엇을 내보내도 풀리지 않는 UnschedulableAndUnresolvable이에요. TaintToleration은 허용하지 않은 taint가 있으면 UnschedulableAndUnresolvable을 반환하고(taint_toleration.go) NodeResourcesFit은 파드의 요청이 노드의 allocatable 자체보다 크면 같은 값을 반환해요(fit.go의 Unresolvable: podRequest.MilliCPU > nodeInfo.GetAllocatable().GetMilliCPU()). 선점은 이런 노드를 "Preemption is not helpful for scheduling"으로 표시하고 건너뛰어요(preemption.go). 마스터는 taint가 이유였고 워커는 CPU 3이 노드 전체보다 커서 넷 다 이 표시를 받았어요.

nodeSelector 파드(filter-nodeselector)의 메시지에서는 둘째 조각만 "3 node(s) didn't match Pod's node affinity/selector"로 달라요. 기본 플러그인 목록을 보면 NodeAffinity 플러그인이 nodeSelector와 node affinity를 함께 구현해요. 그래서 nodeSelector를 썼는데도 메시지에는 "node affinity/selector"가 같이 나와요. 이 경우에도 라벨이 없는 노드는 다른 파드를 내보내도 라벨이 생기지 않으니 선점이 소용없다고 나왔어요(node_affinity.go도 UnschedulableAndUnresolvable을 반환해요).

⚠️ 주의: 한 노드에는 이유가 하나만 적힌다
• 노드 하나는 처음 걸린 필터 플러그인 하나의 이유로만 세어져요. 그래서 이번 메시지에서는 이유 앞 숫자의 합이 노드 수와 같았어요. 다만 NodeResourcesFit은 CPU와 메모리가 함께 모자라면 두 이유를 모두 적어서(fit.go) 그때는 합이 노드 수보다 커져요
• 그래서 메시지에 보이는 이유를 고쳐도 그 노드가 다음 필터에서 또 걸릴 수 있어요. 파드에 마스터의 taint를 허용하는 toleration을 넣어도 CPU 3은 여전히 마스터에 들어가지 않아요
• "preemption:" 뒤가 전부 not helpful이면 우선순위를 높여도 소용없다는 뜻이에요. 요청이나 노드 조건부터 고쳐야 해요

3. 조건을 맞추면 Pending 파드는 스케줄러가 다시 시도한다

다음으로 nodeSelector 파드의 조건을 맞춰 줬어요. 15:05:46에 kubectl label node k8s-worker2 disktype=ssd로 worker2에 라벨을 붙이고 10초 뒤인 15:05:56에 다시 보니 filter-nodeselector는 이미 worker2에서 Running이었어요(그림 2의 마지막 줄). 이벤트도 Created와 Started로 이어졌어요. 파드를 다시 만들거나 스케줄러에 따로 무언가를 시키지 않았는데도 스케줄러가 스스로 다시 시도한 거예요. 실험이 끝난 뒤 이 라벨은 지웠어요.

📖 용어: 스케줄링 큐
스케줄러 안에서 아직 노드를 받지 못한 파드가 기다리는 곳이에요. 바로 시도할 파드가 모인 active queue, 실패한 파드가 잠시 기다리는 backoff queue, 조건이 바뀌기 전까지는 시도해도 소용없는 파드를 모아 두는 unschedulable Pods 목록으로 나뉘어요. 이 이름들은 Scheduling Framework 문서의 PreEnqueue·QueueingHint 설명에 나와요.

Scheduling Framework 문서의 QueueingHint 절에 이 동작이 설명돼 있어요. 플러그인이 등록해 둔 종류의 변화가 클러스터에 생길 때마다 콜백이 불리고 그다음 동작은 "When the QueueingHint finds that the event might make the Pod schedulable, the Pod is put into the active queue or the backoff queue"라고 적혀 있어요. 그 변화로 파드가 노드에 들어갈 수 있게 됐을지도 모르면 파드를 다시 큐로 올린다는 뜻이에요. v1.37.2 소스의 NodeAffinity 플러그인은 노드 추가(Add)와 노드 라벨 변경(UpdateNodeLabel)을 이 이벤트로 등록해 두었어요(node_affinity.go의 EventsToRegister). worker2에 라벨이 붙는 순간이 바로 그 이벤트였어요.

다시 시도하기 전에 기다리는 시간은 스케줄러 설정에 정해져 있어요. 4절에서 쓸 실험 스크립트로 지금 돌고 있는 스케줄러의 설정(/configz)을 읽어 보니 podInitialBackoffSeconds: 1, podMaxBackoffSeconds: 10이었어요. 실패할 때마다 다음 시도까지 기다리는 시간이 1초에서 시작해 최대 10초까지 늘어난다는 뜻이에요.

💡 실무에서는: Pending 파드를 만나면
• kubectl describe pod <파드>의 Events나 kubectl get events --field-selector involvedObject.name=<파드>로 FailedScheduling 메시지를 먼저 봐요
• 이유별 숫자로 몇 대가 어떤 필터에서 빠졌는지 세고 "preemption:" 뒤가 전부 not helpful인지 확인해요
• 원인을 고친 뒤 파드를 지우고 다시 만들 필요는 없어요. 노드 라벨이나 다른 파드 등 플러그인이 지켜보는 대상이 바뀌면 스케줄러가 다시 시도해요

4. 통과한 노드가 여럿이면 플러그인 점수에 가중치를 곱해 더한다

여기까지는 갈 곳이 없던 경우였어요. 처음 실험에서는 통과한 노드가 0대였으니 스코어 단계는 한 번도 돌지 않았어요. 점수가 실제로 어떻게 매겨지는지 보려고 실험 전용 네임스페이스 w23에서 파드를 더 띄워 봤어요. 노드 라벨은 새로 붙이지 않고 모든 노드에 원래 있는 kubernetes.io/hostname 라벨만 썼어요. 먼저 지금 돌고 있는 스케줄러가 어떤 점수 플러그인을 어떤 가중치로 쓰는지부터 봤어요. 마스터에서 관리자 인증서로 스케줄러의 https://127.0.0.1:10259/configz를 읽었어요.

그림 3. 우리 스케줄러의 점수 플러그인 가중치와 NodeResourcesFit 전략(LeastAllocated)

점수에 관여하는 플러그인과 가중치는 TaintToleration 3, NodeAffinity·PodTopologySpread·InterPodAffinity·DynamicResources 2, NodeResourcesFit·NodeResourcesBalancedAllocation·ImageLocality 1이었어요. v1.37.2 소스의 기본값(default_plugins.go)과 같았어요. kubeadm이 띄운 스케줄러는 점수 설정을 기본값 그대로 쓰고 있었어요. 각 플러그인이 점수를 주는 기준을 Scheduler Configuration 문서의 플러그인 설명과 v1.37.2 소스로 확인해 간추리면 이래요.

플러그인 가중치 점수를 주는 기준 TaintToleration 3 PreferNoSchedule taint를 덜 가진 노드 NodeAffinity 2 preferred 규칙의 weight 합이 큰 노드 PodTopologySpread 2 분산 규칙(topologySpreadConstraints)을 덜 어기는 노드 InterPodAffinity 2 파드 간 affinity·anti-affinity 선호에 맞는 노드 NodeResourcesFit 1 LeastAllocated: requests가 덜 찬 노드 NodeResourcesBalancedAllocation 1 CPU와 메모리 requests 비율이 고르게 되는 노드 ImageLocality 1 컨테이너 이미지를 이미 가진 노드

→ DynamicResources는 ResourceClaim을 쓰는 파드에만 점수를 매기고 claim이 없으면 0을 반환해요(v1.37.2 dynamicresources.go). configz에서 가중치가 0으로 찍힌 플러그인 가운데 VolumeBinding은 점수 단계도 있어서 가중치가 비어 있으면 스케줄러가 1로 쳐요(framework.go의 getValidScoreWeights). 이 점수는 v1.37에서 기본으로 켜진 StorageCapacityScoring 기능에서 나오고 PVC를 쓰는 파드일 때만 노드마다 값이 달라져요. 볼륨이 없는 파드라면 모든 노드가 0이에요(volume_binding.go). 점수 플러그인이 노드마다 0~100 사이 값을 내면 NormalizeScore로 범위를 맞춘 뒤 가중치를 곱해 모두 더해요. 설정 문서에는 "The scheduler will then select the node with the highest weighted scores sum."이라고 적혀 있어요.

선호(preferred): 점수 200을 더 받아도 필터는 못 넘는다

📖 용어: node affinity의 required와 preferred
Assigning Pods to Nodes 문서에 따르면 requiredDuringSchedulingIgnoredDuringExecution은 규칙을 만족하지 않으면 스케줄하지 않는 조건(nodeSelector와 같은 역할)이고 preferredDuringSchedulingIgnoredDuringExecution은 맞는 노드를 찾아보고 없어도 스케줄하는 조건이에요. preferred 규칙마다 1~100의 weight를 적고 노드가 만족하는 규칙의 weight가 그 노드 점수에 더해져요.

첫 실험은 worker3을 weight 100으로 선호하는 파드였어요. CPU 500m(0.5코어)과 메모리 32Mi를 요청하는 pause 컨테이너 파드를 하나씩 네 개 만들면서 매번 만들기 직전에 노드별 점수를 계산해 실제로 간 노드와 나란히 찍었어요. worker3은 원래 CPU requests 합이 350m이었으니 500m짜리는 세 개까지(350 + 1500 = 1850m) 들어가고 네 번째(2350m)부터는 넘쳐요.

그림 4. 선호 점수 200을 받던 worker3도 CPU가 차자 필터에서 빠졌고 네 번째 파드는 worker2로 갔다

표의 열부터 읽을게요. requests 열은 노드에 이미 있는 파드의 requests 합이에요. 점수용 열은 NodeResourcesFit이 점수를 매길 때 쓰는 값이고 Balanced 점수에는 requests를 그대로 써요(둘이 왜 다른지는 6절에서 봐요). Fit은 NodeResourcesFit, Balanced는 NodeResourcesBalancedAllocation의 점수이고 둘 다 가중치가 1이에요. NodeAffinity 점수는 worker3만 weight 100을 받고 NormalizeScore가 가장 큰 값을 100으로 맞춘 뒤 가중치 2를 곱해서 200이 돼요. TaintToleration·PodTopologySpread·InterPodAffinity·ImageLocality·DynamicResources는 이 실험에서 세 워커가 모두 같은 값을 받아 순위에 영향을 주지 않으므로 계산에서 뺐어요. 워커에는 PreferNoSchedule taint가 없고 실험 파드는 Service나 ReplicaSet에 속하지 않아요. pause 이미지는 세 워커에 다 있고 ResourceClaim도 쓰지 않아요.

이 표는 스케줄러가 찍은 값이 아니라 제가 v1.37.2 소스의 공식(least_allocated.go, balanced_allocation.go)대로 계산한 값이에요. 스케줄러는 플러그인별 점수를 로그 레벨 10에서만 남기는데(resource_allocation.go의 logger.V(10)) 다른 실험과 함께 쓰는 클러스터라 스케줄러 플래그는 건드리지 않았어요. 대신 계산 결과를 실제 배치와 대조했어요. 이 절의 네 번과 5절의 여섯 번을 합해 열 번 모두 파드가 계산상 최고점인 노드(동점이면 그중 하나)로 갔어요.

pref-1부터 pref-3까지는 worker3이 계속 최고점이었어요. 파드가 하나씩 들어갈수록 worker3의 Fit은 43, 30, 29로 떨어졌지만 NodeAffinity 200점이 있어서 다른 노드가 따라잡지 못했어요. pref-3 직전에 Fit이 30에서 29로 1점만 내려간 이유는 CPU 점수가 이미 2점까지 떨어져 있다가 0이 됐기 때문이에요. 점수용 CPU 1950m에 500m을 더하면 2450m이 돼 할당 가능량 2000m을 넘는데 least_allocated.go에서는 요청이 할당 가능량보다 큰 자원을 0점으로 쳐요. 그래서 Fit은 (CPU 0 + 메모리 58) / 2 = 29이고 합은 297이에요. 필터는 점수용 값이 아니라 requests(1350m + 500m = 1850m)로 판단하니 worker3은 통과했어요. pref-4 직전에는 worker3의 requests가 1850m이었고 500m을 더하면 2000m을 넘어 필터에서 탈락했어요. 네 번째 파드는 남은 worker1(111점)과 worker2(112점) 가운데 1점 높은 worker2로 갔어요. 실험 스크립트는 앞 파드가 노드를 배정받은 것을 확인한 뒤에 다음 파드를 만들었으니 매번의 계산에는 앞 파드의 requests가 이미 들어가 있어요.

필수(required): 같은 조건을 필터로 바꾸면 Pending이 된다

이번에는 같은 조건을 required로 바꾼 파드 네 개를 만들었어요.

그림 5. required로 바꾸자 네 번째 파드는 갈 곳이 없어 Pending이 됐다

req-4의 메시지를 2절과 같은 방식으로 끊으면 1(worker3, CPU 부족) + 1(마스터, taint) + 2(worker1·2, affinity 불일치) = 4예요. "preemption:" 뒤는 달라졌어요. worker3의 CPU 부족은 요청한 500m이 노드 전체(2000m)보다 작으니 다른 파드가 빠지면 풀릴 수 있는 쪽이에요. 그래서 선점 플러그인이 worker3을 실제로 따져 봤고 "No preemption victims found for incoming pod"가 나왔어요. 내보낼 수 있는 파드는 우선순위가 더 낮아야 하는데 문서에 따르면 globalDefault인 PriorityClass가 없을 때 priorityClassName이 없는 파드의 우선순위는 0이에요. 19편에서 어드미션 플러그인이 파드에 priority = 0을 붙이는 것을 봤어요. req-4의 우선순위도 0이었어요. worker3에 있던 파드는 우선순위가 0이거나(req-1~3, myweb 등) PriorityClass가 system-node-critical이라 더 높았으니(calico-node·kube-proxy 등) 내보낼 대상이 없었어요.

그림 6. 같은 "worker3으로"도 preferred는 Score에, required는 Filter에 들어간다

preferred는 점수라서 갈 수 있는 노드 안에서 순위만 바꾸고 required와 nodeSelector는 필터라서 갈 수 있는 노드 자체를 줄여요. 그래서 "꼭 그 노드여야 하는가"와 "되도록 그 노드면 좋은가"를 먼저 정해야 해요. required로 쓰면 그 노드가 차는 순간 Pending이 생기고 preferred로 쓰면 파드가 다른 노드로 넘쳐 나가요.

5. 아무 조건이 없으면 requests가 덜 찬 노드로 하나씩 퍼진다

마지막으로 아무 조건 없이 CPU 300m·메모리 64Mi를 요청하는 파드 여섯 개를 하나씩 만들었어요. 이번에는 NodeAffinity 점수가 없으니 Fit과 Balanced 두 점수의 합만으로 순위가 정해져요.

그림 7. 파드가 들어간 노드는 점수가 내려가고 다음 파드는 다른 노드로 간다

여섯 개는 worker2, worker3, worker1, worker2, worker3, worker1 순서로 들어갔어요. 매번 계산상 최고점인 노드였고 spread-1(worker2·worker3 119점)과 spread-4(worker2·worker3 110점)는 동점이었는데 스케줄러는 두 번 다 worker2를 골랐어요. 동점일 때 무작위로 고른다는 문서의 설명과 어긋나지 않아요. 두 번만으로는 무작위인지 판단할 수 없으니 여기서는 "동점 노드 중 하나를 골랐다"까지만 말할게요.

LeastAllocated 점수의 공식은 least_allocated.go 주석에 있어요. 자원마다 (할당 가능량 − 요청 합) × 100 ÷ 할당 가능량을 구하고(요청 합이 할당 가능량보다 크면 그 자원은 0점) CPU와 메모리의 가중치(각 1)로 평균해요. spread-2 직전의 worker3으로 계산하면 이래요.

CPU: (2000m - (950m + 300m)) × 100 / 2000m = 37 메모리: (3896016Ki - (1470Mi + 64Mi)) × 100 / 3896016Ki = 59 (정수 나눗셈) Fit: (37 + 59) / 2 = 48

→ 덜 찬 노드일수록 점수가 높아요. 파드 하나가 들어가면 그 노드의 Fit이 8~9점씩 내려가서 다음 파드는 다른 노드로 가요. BalancedAllocation은 CPU 비율과 메모리 비율이 얼마나 비슷해지는지를 보는 점수이고 이번에는 노드끼리 1점 안팎밖에 차이가 나지 않았어요.

그림 8. 점수가 가장 높은 노드로 하나씩 들어가니 결과적으로 세 노드에 고르게 퍼졌다

이번 실험에는 일부러 소유자가 없는 파드를 썼어요. Pod Topology Spread Constraints 문서에 따르면 Service·ReplicaSet·StatefulSet·ReplicationController에 속한 파드에는 스케줄러가 기본 분산 규칙(같은 hostname에 maxSkew 3 등)을 자동으로 걸어요. Deployment로 만든 파드라면 PodTopologySpread 점수도 섞여서 LeastAllocated만의 효과를 보기 어려웠을 거예요. 실제 서비스 파드는 대개 Deployment에서 나오니 두 점수가 함께 작동한다고 보면 돼요.

6. 스케줄러가 보는 것은 실제 사용량이 아니라 requests다

그림 8의 아래 두 줄이 이번 실험에서 가장 뜻밖이었어요. worker1은 requests 합이 CPU 250m·메모리 0Mi로 세 워커 가운데 가장 적었어요. 그런데 첫 파드를 놓을 때 worker1은 118점이고 나머지 둘은 119점이었어요. 스케줄러가 점수를 매길 때 쓰는 값(점수용)이 950m·1600Mi였기 때문이에요.

v1.37.2 소스(pkg/scheduler/util/pod_resources.go)에 이유가 적혀 있어요. requests를 적지 않은 컨테이너는 "for the purpose of computing priority only", 즉 점수를 계산할 때만 CPU 100m·메모리 200Mi를 요청한 것으로 쳐요. 주석에 따르면 이 값은 requests가 0인 파드가 요청 합이 가장 적은 노드 한 곳에 몰리지 않게 하려고 넣은 거예요. worker1의 컨테이너는 하나도 메모리 requests를 적지 않아서 컨테이너마다 200Mi씩 쌓여 점수용 메모리가 1600Mi가 됐어요. 다른 두 워커(1470Mi)보다 많은 값이에요.

📖 용어: requests와 allocatable
requests는 컨테이너가 "이만큼은 보장해 달라"고 적는 CPU·메모리 양이에요. allocatable은 노드 전체 용량(capacity)에서 시스템 몫을 뺀 나머지로 파드에 나눠 줄 수 있는 양이에요. 우리 워커의 allocatable은 CPU 2, 메모리 3896020Ki(약 3.7GiB, worker3만 3896016Ki)예요. 필터는 "이미 있는 파드의 requests 합 + 새 파드 requests ≤ allocatable"인지 봐요.

Resource Management 문서에는 이 점이 분명히 적혀 있어요. "although actual memory or CPU resource usage on nodes is very low, the scheduler still refuses to place a Pod on a node if the capacity check fails." 노드의 실제 사용량이 아무리 낮아도 requests 합으로 계산한 용량 검사를 통과하지 못하면 스케줄러는 그 노드에 파드를 놓지 않는다는 뜻이에요. 2절의 CPU 3개짜리 파드가 바로 그 경우였고 워커가 실제로 CPU를 얼마나 쓰고 있었는지는 판단에 들어가지 않았어요.

반대 방향의 문제도 있어요. 필터는 requests 0을 그대로 0으로 계산해요. NodeResourcesFit의 필터는 requests를 그대로 쓰고(fit.go의 GetRequested()) 100m·200Mi 보정은 NodeResourcesFit의 점수 계산에서만 쓰이기 때문에(resource_allocation.go에서 useRequested가 false일 때 쓰는 GetNonZeroRequested()) requests를 적지 않은 파드는 자원 필터의 CPU·메모리 검사를 늘 통과해요. 걸리는 것은 노드당 파드 수 한도(우리 노드는 110)뿐이에요. 21편에서 본 대로 우리 클러스터에는 requests를 적지 않은 파드가 많아요. 그런 파드는 실제로 메모리를 많이 써도 필터 계산에서는 자원을 하나도 차지하지 않는 것으로 쳐요.

💡 실무에서는: requests를 적어야 스케줄러가 제대로 고른다
• 컨테이너마다 평소 사용량에 맞춘 CPU·메모리 requests를 적어요. 그래야 필터와 점수가 실제 부하에 가깝게 계산돼요
• 노드에 얼마나 배정됐는지는 kubectl describe node의 Allocated resources(requests 합)로 봐요. 실제 사용량을 보는 kubectl top(metrics-server 필요)과는 다른 숫자예요
• 특정 노드로 몰고 싶을 때는 required보다 preferred를 먼저 검토해요. 그 노드가 차도 파드가 Pending으로 남지 않아요
⚠️ 주의: requests가 없으면 필터는 막지 못한다
• requests가 0인 파드는 NodeResourcesFit 필터의 CPU·메모리 검사를 늘 통과해요(노드당 파드 수 한도만 걸려요). 한 노드에 몰려도 스케줄러는 막지 않아요
• 점수 계산에서만 CPU 100m·메모리 200Mi로 쳐 주니 몰림이 조금 줄어들 뿐이에요. 실제로 메모리가 모자라면 문제는 노드의 kubelet이 파드를 내보낼 때 드러나요
✍️ 오늘의 요약
kube-scheduler는 필터로 갈 수 있는 노드를 남기고 스코어로 그중 하나를 고른 뒤 spec.nodeName 한 칸을 API 서버에 적어요.

FailedScheduling 메시지를 콜론과 쉼표로 끊으면 "필터를 통과한 노드 수 / 전체", 노드별 탈락 이유, 선점이 도움이 되는지가 차례로 보여요. CPU 3개 요청은 워커 allocatable 2를 넘어서 선점으로도 풀리지 않았고 nodeSelector 파드는 라벨을 붙이자 스케줄러가 스스로 다시 시도해 worker2로 갔어요. 통과한 노드가 여럿이면 플러그인 점수에 가중치(TaintToleration 3, NodeAffinity 2, NodeResourcesFit 1 등)를 곱해 더해요. preferred affinity로 받은 200점도 필터는 넘지 못했고 required로 바꾸자 같은 파드가 Pending이 됐어요. 조건이 없을 때는 LeastAllocated 점수에 따라 덜 찬 노드로 하나씩 퍼졌어요. 이 모든 계산은 실제 사용량이 아니라 requests로 해요. requests를 정직하게 적는 것이 스케줄러를 제대로 쓰는 첫걸음이에요.
