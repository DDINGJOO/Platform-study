2편. kubectl apply 한 번이 파드가 되기까지
3편. 노드를 VM 으로 만들고 네트워크를 두 개 붙였다

6편. kubeadm 은 파드 네트워크를 만들지 않는다

worker3 에 512MB 짜리 swap 파일을 켜고 kubelet 을 재시작했어요. 15초 뒤 상태를 물어보니 active 가 아니라 activating 이 돌아왔습니다. 1분 뒤 마스터에서 kubectl get nodes 를 치자 네 줄 중 worker3 만 NotReady 였어요. swap 을 다시 끄고 kubelet 을 재시작하자 worker3 는 Ready 로 돌아왔습니다.

📖 용어: swap (스왑)
메모리가 모자랄 때 커널이 당장 쓰지 않는 메모리 페이지를 디스크로 내보내고, 비운 물리 메모리를 다른 곳에 쓰게 하는 공간이에요. 디스크의 파일이나 파티션을 swap 으로 지정해서 켭니다. 이 실험에서는 512MB 파일 하나를 swap 으로 켰어요.

일부러 깨 본 실험이었어요. 이 실습 클러스터를 만드는 스크립트의 첫 단계가 swapoff -a 인데, 그 한 줄을 빼면 정말 무엇이 깨지는지 보고 싶었습니다. kubeadm 설치 문서는 swap, 컨테이너 런타임 같은 준비를 kubeadm 을 돌리기 전에 노드마다 해 두라고 적고 있어요. 저는 그 준비를 scripts/node-setup.sh 한 파일에 모으고, ./lab up 이 노드 네 대에서 root 로 실행하게 했습니다.

이 글은 그 스크립트를 위에서부터 따라가며 질문 하나에 답해요. "kubeadm 전에 노드마다 무엇을 해 둬야 하고, 각각 빼면 무엇이 깨지나." swap 은 직접 켜서 확인했고, 나머지는 공식 문서가 말하는 이유와 노드에서 확인한 값으로 적었습니다. 직접 시험하지 않은 것은 시험하지 않았다고 적었어요.

이 글에서 다룰 것
· swap 이 켜진 노드에서 kubelet 은 어떻게 실패하고, 노드는 언제 NotReady 가 될까?
· v1.34 에 swap 지원이 GA 가 됐는데 왜 아직도 끄라고 할까?
· br_netfilter 와 ip_forward 는 각각 무엇을 위해 켜는 걸까?
· containerd 의 cgroup 드라이버와 pause 이미지는 왜 따로 맞춰야 할까?
· NIC 가 둘인 노드에서 kubelet 의 노드 IP 는 왜 고정해야 할까?

1. 스크립트 한 파일에 다섯 단계가 들어 있다

node-setup.sh 는 위에서부터 다섯 단계예요. swap 을 끄고, 커널 모듈과 sysctl(실행 중인 커널의 설정값을 읽고 바꾸는 명령)을 맞추고, kubeadm·kubelet·kubectl 을 설치하고, containerd 설정을 쓰고, kubelet 이 쓸 노드 IP 를 고정합니다. 여러 번 실행해도 결과가 같도록 짰어요. 패키지 설치와 설정 파일 쓰기는 이미 원하는 상태면 건너뛰기 때문에, ./lab up 을 다시 돌려도 설정이 같으면 containerd 와 kubelet 을 재시작하지 않습니다.

그림 1은 다섯 단계와 각 단계를 뺐을 때 생기는 일을 한 장에 모은 거예요. 오른쪽 칸의 꼬리표는 근거입니다. "실험"과 "겪음"은 이 클러스터에서 직접 본 것이고, "문서"는 공식 문서가 그렇게 설명하는 것이에요.

그림 1. 다섯 단계는 모두 kubeadm 보다 먼저 돈다. 빼면 깨지는 곳은 단계마다 다르다

다섯 단계 모두 kubeadm 을 돌리기 전에 노드마다 끝나 있어야 하는 일입니다. 이 중 제가 직접 깨 본 것은 swap 하나예요. 그 결과부터 볼게요.

2. swap 을 켜자 kubelet 이 10초마다 다시 떴다

worker3 에서 실행한 명령과 출력을 그대로 옮겼어요.

worker3$ sudo fallocate -l 512M /swapfile-test && sudo chmod 600 /swapfile-test && sudo mkswap /swapfile-test >/dev/null && sudo swapon /swapfile-test && echo ok ok worker3$ swapon --show NAME TYPE SIZE USED PRIO /swapfile-test file 512M 0B -2 worker3$ sudo systemctl restart kubelet; sleep 15; systemctl is-active kubelet activating

→ 512MB 파일을 swap 으로 켰고(아직 사용량 0B), kubelet 을 재시작하고 15초가 지나도 kubelet 이 실행 중(active)이 아니라 시작하는 중(activating)에 머물러 있다는 뜻이에요.

swap 을 켠 다음 kubelet 을 일부러 재시작한 데는 이유가 있어요. 공식 문서에 따르면 이미 떠 있는 kubelet 은 swap 이 새로 생긴 것을 재시작해야 알아챕니다. kubelet 이 swap 을 검사하는 때가 시작하는 순간이기 때문이에요. 그래서 swap 을 켜기만 해서는 바로 드러나지 않고, kubelet 이 다음에 시작할 때 걸립니다.

kubelet 이 activating 에 머문 이유는 로그에 있었어요.

worker3$ sudo journalctl -u kubelet --since -1min --no-pager -o cat | grep 'command failed' | tail -2 E1104 21:23:52.732059 10576 run.go:72] "command failed" err="failed to run Kubelet: running with swap on is not supported, please disable swap or set --fail-swap-on flag to false" E1104 21:24:02.958659 10600 run.go:72] "command failed" err="failed to run Kubelet: running with swap on is not supported, please disable swap or set --fail-swap-on flag to false"

→ swap 이 켜진 채로 실행하는 것은 지원하지 않으니 swap 을 끄거나 --fail-swap-on 을 false 로 두라며 kubelet 이 실행을 거부했다는 뜻이에요. 맨 앞의 E 는 오류 등급, 1104 는 11월 4일, 시각 뒤의 10576·10600 은 프로세스 번호입니다.

두 줄에서 두 가지를 읽을 수 있어요. 첫째, 프로세스 번호가 10576 에서 10600 으로 바뀌었습니다. 같은 kubelet 이 오류를 두 번 낸 것이 아니라, kubelet 이 새로 두 번 떴다가 두 번 다 거부한 거예요. 둘째, 두 시각의 차이가 약 10.2초입니다(21:23:52.73 → 21:24:02.96). 쿠버네티스 패키지의 kubelet.service 템플릿(kubernetes/release 저장소)에는 Restart=always 와 RestartSec=10 이 적혀 있어요. kubelet 이 실패로 끝나면 systemd 가 10초 기다렸다가 다시 띄우고, 다시 뜬 kubelet 은 또 swap 을 보고 거부합니다. 15초 뒤에 본 activating 은 이 반복의 한 순간이었어요.

그림 2. 프로세스 번호가 10576 에서 10600 으로 바뀌며 같은 오류가 10초 간격으로 찍혔고, 1분 뒤 worker3 만 NotReady 였다

그럼 노드는 왜 NotReady 가 됐을까요. 노드가 살아 있다는 소식은 kubelet 이 API 서버에 주기적으로 보고해요. kubelet 이 뜨지 못하면 그 보고를 할 프로그램이 노드에 없습니다. 컨트롤 플레인에서는 kube-controller-manager 의 노드 컨트롤러가 이 보고를 지켜보다가, 마지막 소식 뒤로 node-monitor-grace-period(기본 50초) 동안 아무 소식이 없으면 그 노드의 Ready 조건을 Unknown 으로 바꿔요. kubectl get nodes 의 STATUS 열은 Ready 조건이 True 가 아니면 NotReady 로 보여 줍니다.

1분 뒤에 확인했을 때 worker3 만 NotReady 였던 건 그래서예요. 마스터와 다른 워커의 kubelet 은 계속 보고하고 있었으니 Ready 로 남았습니다. 정확히 몇 초 시점에 Unknown 으로 바뀌었는지는 기록하지 않았어요. 그림 3은 이 흐름을 시간 순서로 놓은 것입니다.

그림 3. kubelet 이 10초마다 다시 떠서 거부하는 동안 상태 보고가 끊겼고, 50초 판정을 넘긴 뒤 본 worker3 는 NotReady 였다

되돌리는 건 간단했어요.

worker3$ sudo swapoff /swapfile-test && sudo rm -f /swapfile-test && sudo systemctl restart kubelet && echo ok ok master$ kubectl wait --for=condition=Ready node/k8s-worker3 --timeout=120s node/k8s-worker3 condition met

→ swap 을 끄고 파일을 지운 뒤 kubelet 을 재시작했더니, 120초 제한 안에 worker3 의 Ready 조건이 다시 True 가 됐다는 뜻이에요.

kubelet 이 뜨지 않으면 노드 상태를 보고할 프로그램이 없고, 마지막 보고 뒤 50초가 지나면 컨트롤 플레인은 그 노드를 Unknown 으로 판정합니다. 스크립트가 swap 을 끄는 부분은 두 줄이에요.

swapoff -a sed -i -E '/\sswap\s/ s/^([^#])/#\1/' /etc/fstab

→ 지금 켜진 swap 을 모두 끄고, /etc/fstab 에서 swap 이 들어 있는 줄 앞에 # 를 붙여 부팅할 때 다시 켜지지 않게 한다는 뜻이에요.

worker1$ swapon --show; free -h | grep -i swap Swap: 0B 0B 0B

→ 스크립트를 거친 worker1 에서는 swapon --show 가 아무것도 출력하지 않았고, swap 총량이 0B 라는 뜻이에요.

⚠️ 주의: swapoff -a 만으로는 재부팅을 넘기지 못해요
swapoff -a 는 지금 켜진 swap 만 꺼요. /etc/fstab 에 swap 줄이 남아 있으면 재부팅할 때 swap 이 다시 켜지고, 그 뒤 시작하는 kubelet 이 위와 똑같이 거부합니다. 공식 설치 문서도 swapoff -a 는 일시적이고, 재부팅 뒤에도 유지하려면 /etc/fstab 이나 systemd.swap 같은 설정에서 꺼야 한다고 적고 있어요. 이 스크립트는 fstab 만 다룹니다. systemd 의 swap 유닛으로 swap 을 켜는 시스템이라면 그쪽도 따로 확인해야 해요.

3. swap 지원이 GA 가 된 뒤에도 기본값은 "켜져 있으면 거부"다

여기서 의문이 하나 생겨요. 쿠버네티스는 노드 swap 지원을 v1.22 에 알파로 넣었고, v1.28 에 베타, v1.34 에 GA 로 올렸습니다(KEP-2400). 이 클러스터는 v1.37.2 예요. 그런데도 kubelet 은 왜 거부했을까요.

GA 가 된 것은 swap 을 허용할 수 있는 방법이고, 기본값은 그대로이기 때문이에요. kubelet 설정의 failSwapOn 은 "swap 이 켜져 있으면 시작에 실패하라"는 뜻이고, 기본값이 true 입니다. 오류 메시지가 가리킨 --fail-swap-on 플래그가 같은 설정이에요. 플래그 쪽에는 설정 파일로 지정하라는 deprecated 표시가 붙어 있습니다.

그럼 처음에는 왜 막았을까요. KEP-2400 은 첫머리에 이유를 적어 두었어요. swap 이 끼면 파드의 메모리 사용을 보장하고 계산하기가 어렵고, 그래서 초기 설계에서 swap 지원은 범위 밖이었다는 거예요. 공식 문서의 "위험과 주의" 절은 더 구체적입니다.

· 예측 가능성: swap 이 있으면 예측 가능성이 떨어져요. swap 으로 내보낸 데이터를 메모리로 다시 읽는 일은 때로 몇 자릿수 느려서, 예상하지 못한 성능 저하가 생길 수 있어요.
· 스케줄링: 파드는 memory 만 요청하고 swap 은 요청하지 않아요. 그래서 스케줄러는 파드를 노드에 배치할 때 swap 사용을 계산에 넣지 않습니다.
· 축출: swap 이 없으면 kubelet 의 축출(eviction, kubelet 이 노드 자원을 지키려고 파드를 끝내는 것) 기준을 노드 메모리보다 조금 낮게 잡을 수 있어요. 그러면 OOM killer(메모리가 바닥났을 때 커널이 프로세스를 골라 강제로 끝내는 기능)가 움직이기 전에 kubelet 이 먼저 파드를 내보냅니다. OOM killer 는 QoS 나 파드 우선순위를 모르기 때문이에요. swap 이 있으면 커널이 swap 으로 내보내기 시작하는 지점과 축출 기준이 엇갈려서, 이 값을 맞추기가 까다로워집니다.

📖 용어: QoS 클래스
쿠버네티스가 파드의 requests·limits 를 보고 붙이는 등급이에요. 모든 컨테이너가 CPU·메모리의 requests 와 limits 를 같게 두면 Guaranteed, 아무것도 두지 않으면 BestEffort, 그 사이는 Burstable 입니다. 노드 자원이 모자랄 때 어느 파드를 먼저 내보낼지 정하는 데 쓰여요.

KEP-2400 에는 이런 권고도 있어요. 노드에 swap 을 켜는 것은 커널 튜닝과 지식이 필요한 고급 기능이라 모든 노드에 권하지 않고, 대부분의 경우 --fail-swap-on=true 를 권한다고요. 공식 문서도 컨트롤 플레인 노드는 swap 없이 돌리라고 권합니다.

이 실습에서 swap 을 끈 이유도 여기에 있어요. 강의를 따라 하며 확인하고 싶은 것은 requests·limits, QoS, 축출이 문서에 적힌 대로 움직이는 모습이에요. swap 이 끼면 메모리가 모자랄 때의 동작부터 달라집니다. GA 가 된 것은 swap 을 허용하는 방법이고, 기본값은 여전히 "켜져 있으면 시작하지 않는다"입니다.

그래도 swap 을 켜야 하는 노드가 있다면 kubelet 설정 파일에서 두 값을 바꿔요. 공식 튜토리얼의 예시 그대로입니다.

# kubelet 설정 파일(KubeletConfiguration)의 일부 failSwapOn: false memorySwap: swapBehavior: LimitedSwap

→ failSwapOn: false 는 swap 이 켜진 노드에서도 kubelet 이 시작하게 하고, swapBehavior: LimitedSwap 은 파드도 swap 을 쓰게 한다는 뜻이에요. 바꾼 뒤에는 kubelet 을 재시작해야 적용됩니다.

여기서 헷갈리기 쉬운 점이 둘 있어요. 첫째, failSwapOn: false 만 바꾸면 kubelet 은 뜨지만 파드는 swap 을 쓰지 못합니다. swapBehavior 의 기본값이 NoSwap 이기 때문이에요. 다만 kubelet 자신을 포함해 쿠버네티스가 관리하지 않는 프로세스는 swap 을 쓸 수 있어요. 둘째, LimitedSwap 으로 바꿔도 모든 파드가 쓰지는 않습니다. Burstable 파드만 쓰고, Guaranteed·BestEffort 파드와 우선순위가 높은 파드는 쓰지 못해요. 컨테이너가 쓸 수 있는 양은 (메모리 request ÷ 노드 전체 메모리) × 파드에게 허용된 swap 총량으로 자동 계산됩니다.

💡 실무에서는: swap 을 켤 노드를 고른다
공식 문서가 권하는 것을 모으면 이래요.
• 컨트롤 플레인 노드에는 swap 을 두지 않아요.
• swap 공간은 암호화해요. secret 볼륨 같은 메모리 기반 볼륨의 내용은 디스크로 나가면 안 되기 때문이에요.
• 스케줄러가 swap 을 모르므로, swap 을 켠 노드에는 taint 를 걸어 swap 을 쓰려는 워크로드만 가게 해요.
이 실습 클러스터에서는 이 중 아무것도 하지 않고 swap 을 끄는 쪽을 골랐습니다.

4. 파드 패킷이 노드를 지나가려면: 커널 모듈과 sysctl

두 번째 단계는 커널 설정이에요. 스크립트는 이렇게 생겼습니다.

cat >/etc/modules-load.d/k8s.conf <<'EOF' overlay br_netfilter EOF modprobe overlay modprobe br_netfilter cat >/etc/sysctl.d/99-k8s.conf <<'EOF' net.bridge.bridge-nf-call-iptables = 1 net.bridge.bridge-nf-call-ip6tables = 1 net.ipv4.ip_forward = 1 EOF sysctl --system >/dev/null

→ 부팅할 때마다 올릴 커널 모듈 두 개를 파일에 적고 지금 바로 올린 다음, sysctl 값 세 개를 파일에 적고 바로 적용한다는 뜻이에요. 파일에 적는 것은 재부팅 뒤에도 유지하기 위해서입니다.

먼저 net.ipv4.ip_forward 예요. 공식 문서(컨테이너 런타임 설치 문서)는 이렇게 설명합니다. 리눅스 커널은 기본적으로 인터페이스 사이에서 IPv4 패킷을 라우팅하지 않는다. 대부분의 클러스터 네트워킹 구현은 필요하면 이 값을 직접 바꾸지만, 관리자가 해 두기를 기대하는 구현도 있다.

파드에서 나온 패킷은 노드 입장에서 파드 쪽 인터페이스로 들어와 eth0 같은 다른 인터페이스로 나가야 다른 노드에 닿아요. 이 값이 0 이고 CNI 플러그인도 켜 주지 않으면 그 길이 막힙니다. 지금 문서가 kubeadm 전 준비로 직접 적어 둔 커널 설정은 이것 하나예요.

다음은 br_netfilter 와 bridge-nf-call-iptables 예요.

📖 용어: br_netfilter
리눅스 브리지(한 노드 안의 여러 가상 인터페이스를 L2 로 잇는 커널 기능)를 지나는 패킷도 iptables 규칙을 거치게 해 주는 커널 모듈이에요. net.bridge.bridge-nf-call-iptables 는 이 모듈이 제공하는 설정이고, 1 이면 브리지를 지나는 IPv4 패킷이 iptables 를 거칩니다.

이 설정이 왜 필요한지는 지금 공식 문서에서 찾을 수 없었어요. v1.29 까지의 네트워크 플러그인 문서에는 이유가 적혀 있었습니다. kube-proxy 의 iptables 모드는 iptables 에 의존하므로, 플러그인이 컨테이너를 리눅스 브리지에 연결한다면 iptables 프록시가 제대로 동작하도록 이 값을 1 로 둬야 한다는 내용이었어요. 서비스 IP 를 파드 IP 로 바꾸는 DNAT 규칙(2편에서 다룬다)이 바로 이 iptables 규칙입니다. 브리지를 지나는 패킷이 iptables 를 거치지 않으면 그 규칙이 적용되지 않아요.

이 문장은 2024년 2월 문서 저장소의 한 커밋에서 빠졌어요. 커밋 메시지는 "필요한 플러그인은 스스로 설정하리라 기대한다. kubeadm 도 더는 이 값을 검사하지 않는다"였습니다. 그 뒤 v1.30 문서부터 노드 준비 예시에는 ip_forward 만 남았어요. 지금 문서는 다른 sysctl 값이나 커널 모듈을 요구하는 구현도 있으니 쓰는 네트워크 구현의 문서를 보라고만 적습니다.

제 스크립트의 이 블록은 v1.29 까지의 공식 문서 예시와 같은 내용이에요. 지우지 않고 남겨 뒀지만, Calico 를 쓰는 이 클러스터에서 br_netfilter 와 bridge 설정을 빼면 무엇이 달라지는지는 시험하지 않았습니다. 지금 공식 문서가 kubeadm 전 준비로 요구하는 커널 설정은 ip_forward 하나이고, br_netfilter 는 쓰는 네트워크 플러그인이 요구할 때 맞추는 설정이 됐어요.

남은 overlay 는 overlayfs 커널 모듈이고, v1.29 문서 예시에도 같이 있었어요. containerd 문서에 따르면 containerd 의 기본 스냅샷터(이미지 층을 겹쳐 컨테이너의 파일시스템을 만드는 부분)가 overlayfs 입니다. 노드에서 확인한 결과는 이랬어요.

worker1$ lsmod | grep -E "^(br_netfilter|overlay)" br_netfilter 32768 0 overlay 204800 10 worker1$ sysctl net.bridge.bridge-nf-call-iptables net.ipv4.ip_forward net.bridge.bridge-nf-call-iptables = 1 net.ipv4.ip_forward = 1

→ worker1 에 두 모듈이 올라와 있고, 두 sysctl 값이 1 로 적용돼 있다는 뜻이에요.

5. cgroup 드라이버는 이제 containerd 쪽 설정이 정한다

네 번째 단계는 containerd 설정이에요. containerd 2.4.1 은 Lima 가 VM 을 만들 때 설치했고, 스크립트는 쿠버네티스용 설정을 /etc/containerd/conf.d/k8s.toml 에 따로 적습니다. worker1 에 적힌 내용이에요.

worker1$ cat /etc/containerd/conf.d/k8s.toml version = 2 [plugins] [plugins."io.containerd.grpc.v1.cri"] sandbox_image = "registry.k8s.io/pause:3.10.2" [plugins."io.containerd.grpc.v1.cri".containerd] [plugins."io.containerd.grpc.v1.cri".containerd.runtimes] [plugins."io.containerd.grpc.v1.cri".containerd.runtimes.runc] runtime_type = "io.containerd.runc.v2" [plugins."io.containerd.grpc.v1.cri".containerd.runtimes.runc.options] SystemdCgroup = true [plugins."io.containerd.cri.v1.runtime".cni] bin_dirs = ["/opt/cni/bin", "/usr/local/libexec/cni"]

→ runc 로 컨테이너를 만들 때 systemd cgroup 드라이버를 쓰고, 파드 샌드박스 이미지로 registry.k8s.io/pause:3.10.2 를 쓰고, CNI 플러그인 실행 파일은 두 폴더에서 찾으라는 설정이에요.

📖 용어: cgroup 드라이버
cgroup 은 프로세스 묶음이 쓰는 CPU·메모리를 제한하는 리눅스 기능이에요. cgroup 드라이버는 kubelet 과 런타임이 이 cgroup 을 어떤 방식으로 만들고 고치는지를 정합니다. cgroup 파일시스템을 직접 다루는 cgroupfs 와 systemd 를 거쳐 다루는 systemd 두 가지가 있어요.

공식 문서는 kubelet 과 컨테이너 런타임이 같은 cgroup 드라이버를 쓰는 것이 매우 중요하다고 적어요. 다르면 어떻게 되는지는 v1.34 발표 글에 있습니다. 예전에는 kubelet 과 런타임에 같은 드라이버를 따로 설정해야 했고, 둘이 다르면 kubelet 이 분명한 오류 메시지 없이 이상하게 동작했다는 거예요.

v1.34 부터는 이 문제를 다른 방식으로 풀어요. kubelet 이 시작할 때 CRI 런타임에게 어떤 cgroup 드라이버를 쓰는지 물어서 그 답을 씁니다(v1.28 에 기능 게이트로 들어와 v1.34 에 GA). 이때 kubelet 설정의 cgroupDriver 값은 무시돼요. containerd 는 2.0 부터 이 질문에 답합니다. 우리 노드의 kubelet 로그에 그 흔적이 남아 있어요.

worker1$ sudo journalctl -u kubelet --no-pager -o cat | grep -i -m2 "cgroup driver" I1104 21:19:40.656302 8691 server.go:1502] "Using cgroup driver setting received from the CRI runtime" cgroupDriver="systemd"

→ kubelet 이 CRI 런타임(containerd)에게서 받은 cgroup 드라이버 값 systemd 를 쓰고 있다는 뜻이에요. 맨 앞의 I 는 정보 등급입니다.

그림 4. v1.34 부터 kubelet 은 런타임에게 cgroup 드라이버를 묻고, 자기 설정값은 쓰지 않는다

그럼 이제 맞출 필요가 없어졌을까요. 두 값이 어긋날 일은 사라졌지만, 어떤 값을 쓸지는 여전히 정해야 해요. containerd 문서에 따르면 containerd 의 기본값은 cgroupfs 입니다. SystemdCgroup = true 를 빼면 kubelet 도 containerd 의 답을 따라 cgroupfs 를 쓰게 돼요. 공식 문서는 systemd 가 init 인 시스템에서 cgroupfs 를 권하지 않습니다. systemd 는 시스템에 cgroup 관리자가 하나뿐이라고 기대하기 때문이에요. cgroup v2 를 쓴다면 systemd 드라이버를 쓰라고도 권하고요. Ubuntu 노드는 systemd 로 부팅하므로 systemd 로 맞췄어요.

이 구성에서 cgroup 드라이버를 실제로 정하는 값은 containerd 의 SystemdCgroup = true 하나예요. 5편에서 다룰 kubeadm 설정 파일에도 cgroupDriver: systemd 를 적었지만, 이 구성에서는 kubelet 이 그 값 대신 containerd 의 답을 씁니다.

⚠️ 주의: 설정 파일 모양이 공식 예시와 달랐어요
공식 문서의 containerd 2.x 예시는 머리가 version = 3 이고 플러그인 이름이 io.containerd.cri.v1.runtime 이에요. 제 파일은 containerd 1.x 형식인 version = 2 와 io.containerd.grpc.v1.cri 를 썼습니다. containerd 문서에 따르면 2.x 는 version 2 설정도 읽어서 version 3 으로 자동 변환해요. 그래도 파일만 봐서는 적용됐는지 알 수 없어서 위의 kubelet 로그로 확인했어요. 기본값이 cgroupfs 인데 systemd 라는 답이 왔으니 SystemdCgroup 이 읽힌 거예요. 반면 마지막 CNI 경로 줄은 2.x 이름으로 적혀 있어 한 파일에 두 형식이 섞여 있고, 이 줄이 실제로 반영됐는지는 따로 확인하지 않았습니다. 설정을 바꾼 뒤에는 파일이 아니라 그 설정을 읽은 프로그램의 로그로 확인하는 편이 확실해요.

두 번째 줄의 sandbox_image 는 pause 이미지예요.

📖 용어: pause 이미지 (샌드박스 이미지)
파드를 만들 때 앱 컨테이너보다 먼저 띄우는 "인프라 컨테이너"의 이미지예요. 파드를 이루는 cgroup 과 네임스페이스는 그 안에 프로세스가 하나는 있어야 유지되는데, pause 프로세스가 그 일을 합니다. 그래서 앱 컨테이너가 죽었다 다시 떠도 파드의 네트워크 설정이 사라지지 않아요.

이 이미지를 무엇으로 쓸지는 kubeadm 이 아니라 컨테이너 런타임 설정이 정해요. kubeadm 문서도 pause 이미지를 바꾸려면 런타임 쪽에서 설정하라고 적고 있습니다. 한편 kubeadm 은 쿠버네티스 버전마다 쓰는 이미지 목록을 갖고 있고, 그 목록에 pause 도 있어요. 그래서 스크립트는 kubeadm 에게 이 버전의 pause 이미지 이름을 물어서 containerd 설정에 그대로 적습니다.

PAUSE_IMAGE=$(kubeadm config images list --kubernetes-version "v${K8S_VERSION}" 2>/dev/null | grep pause)

→ kubeadm 이 v1.37.2 에 쓰는 이미지 목록에서 pause 가 들어간 줄만 골라 변수에 담는다는 뜻이에요. 이렇게 나온 값이 위 설정 파일의 registry.k8s.io/pause:3.10.2 입니다.

이렇게 하면 쿠버네티스 버전을 올릴 때 pause 이미지 버전을 손으로 따라 고칠 필요가 없어요. 두 값이 다를 때 실제로 무엇이 깨지는지는 이번에 시험하지 않았습니다.

마지막 줄은 CNI 플러그인 실행 파일을 찾을 폴더예요. 스크립트 주석에 적어 둔 대로 Calico 는 자기 플러그인을 /opt/cni/bin 에 두고, loopback 같은 기본 플러그인은 Lima 가 설치한 containerd 번들 쪽(/usr/local/libexec/cni)에 있어요. 쿠버네티스는 런타임이 파드 샌드박스마다 loopback 인터페이스 lo 를 마련하길 요구하고, 공식 문서는 CNI 의 loopback 플러그인을 재사용하는 방법을 예로 듭니다. 그래서 두 폴더를 모두 적었어요.

6. kubelet 이 등록할 IP 를 정해 주고, 빠진 crictl 을 채운다

마지막 단계는 노드 IP 예요. 이 VM 들에는 NIC 가 둘 있어요(3편에서 다룬다). eth0 은 VM 끼리 통하는 192.168.104.0/24, lima1 은 Mac 에서 VM 으로만 닿고 VM 끼리는 통하지 않는 192.168.64.0/24 입니다. kubelet 명령줄 문서에 따르면 --node-ip 를 주지 않으면 kubelet 은 노드의 기본 IPv4 주소로 노드를 등록해요. NIC 가 둘이면 그 기본 주소가 eth0 쪽이라는 보장이 없습니다.

이 값이 lima1 주소가 되면 노드가 VM 끼리 통하지 않는 주소로 등록돼요. Calico 는 kubelet 이 등록한 이 주소(InternalIP)로 노드 사이 경로를 놓게 설정했기 때문에(6편에서 다룬다), 노드 사이 파드 통신이 서로 닿지 않는 네트워크로 가게 됩니다. 공식 설치 문서도 NIC 가 여럿이고 기본 경로로 쿠버네티스 구성 요소에 닿지 않으면 경로를 추가하라고 권해요. 저는 경로를 건드리는 대신 kubelet 이 쓸 IP 를 직접 지정했습니다. 지정하지 않았을 때 이 VM 에서 실제로 어느 쪽이 골라지는지는 시험하지 않았어요.

worker1$ cat /etc/default/kubelet KUBELET_EXTRA_ARGS=--node-ip=192.168.104.3

→ worker1 의 kubelet 은 eth0 주소 192.168.104.3 으로 노드를 등록하라는 뜻이에요. kubeadm 이 까는 kubelet 의 systemd 설정이 이 파일을 읽어 KUBELET_EXTRA_ARGS 를 명령줄 맨 끝에 붙이고, 이 값은 충돌하는 다른 설정보다 우선합니다.

스크립트는 eth0 의 IP 를 읽어 이 파일을 쓰고, kubelet 이 이미 돌고 있으면 재시작해요. 결과는 첫 ./lab up 의 마지막 화면에서 확인했습니다. 네 노드의 INTERNAL-IP 가 192.168.104.1, .3, .4, .5 로 모두 eth0 대역이었어요.

이 파일에는 짚어 둘 점이 있어요. kubeadm 문서는 이 파일을 kubelet 인자를 덮어쓰는 최후의 수단으로 소개하고, 가능하면 kubeadm 설정 파일의 nodeRegistration.kubeletExtraArgs 를 쓰라고 권합니다. 이 스크립트는 kubeadm 보다 먼저, 마스터와 워커에서 똑같이 돌아요. 그래서 여기서는 이 파일을 골랐습니다.

마지막은 작업하다 발견한 빈칸이에요. 처음에는 kubeadm·kubelet·kubectl 패키지만 설치했는데, 노드에서 컨테이너를 보려고 crictl 을 치자 이렇게 나왔습니다.

sudo: crictl: command not found

→ 노드에 crictl 명령이 설치돼 있지 않다는 뜻이에요.

📖 용어: crictl
CRI 를 구현한 런타임(여기서는 containerd)에 직접 붙어 그 노드의 파드 샌드박스와 컨테이너를 보는 명령줄 도구예요. kubectl 이 API 서버에 묻는다면, crictl 은 노드의 런타임에 직접 묻습니다. 2편에서 worker3 의 컨테이너를 확인할 때도 이 도구를 써요.

설치 문서를 다시 보니 crictl 은 CRI 와 상호작용하려면 필요하지만 kubeadm 에는 선택 사항이라고 적혀 있고, apt 설치 명령도 kubelet, kubeadm, kubectl 세 개뿐이었어요. 그래서 crictl 이 없으면 cri-tools 패키지를 설치하는 단계를 넣었어요. crictl 이 붙을 런타임 주소는 스크립트가 원래 /etc/crictl.yaml 에 containerd 소켓으로 적어 두고 있었습니다.

if ! command -v crictl >/dev/null 2>&1; then echo "[node-setup] cri-tools(crictl) 설치" DEBIAN_FRONTEND=noninteractive apt-get install -y -qq cri-tools >/dev/null fi

→ crictl 명령이 없을 때만 cri-tools 패키지를 설치한다는 뜻이에요. 이미 있으면 아무것도 하지 않습니다.

swap 을 켠 worker3 에서 kubelet 은 10초마다 다시 떠서 매번 거부했고, 상태 보고가 끊긴 노드는 1분 뒤 NotReady 였어요. v1.34 에 swap 지원이 GA 가 됐어도 failSwapOn 의 기본값은 true 입니다. cgroup 드라이버는 이제 kubelet 이 containerd 에게 물어서 정하므로 효력이 있는 값은 containerd 의 SystemdCgroup 이고, br_netfilter 는 지금 문서에서 네트워크 플러그인이 요구할 때 맞추는 설정이 됐어요. 준비 단계마다 "빼면 무엇이 깨지나"를 알아 둬야, 깨졌을 때 어디부터 볼지 정할 수 있습니다.
