📚 k8s 스터디 · 7편
1편. 클러스터는 API 서버를 가운데 둔 프로그램 여러 개다
2편. kubectl apply 한 번이 파드가 되기까지
3편. 노드를 VM 으로 만들고 네트워크를 두 개 붙였다
4편. swap 을 켜면 kubelet 이 시작하지 않는다
5편. kubeadm init 은 인증서와 정적 파드를 만든다
6편. kubeadm 은 파드 네트워크를 만들지 않는다
7편. 껐다 켠 직후의 Ready 는 재부팅 전 상태일 수 있다 ← 지금 이 글

실습 클러스터를 ./lab stop 으로 끄고 ./lab up 으로 다시 켰어요. 출력 끝에 "클러스터 준비 완료"가 찍혔고, 같은 셸에서 바로 Mac 에서 워커 노드로 curl 을 보냈습니다. 같은 명령 줄에서 kubectl get deploy 는 nginx 3개가 모두 준비됐다고(READY 3/3) 답했는데, curl 이 받은 HTTP 상태 코드는 000 이었어요. 응답을 하나도 받지 못했다는 뜻입니다.

잠시 뒤 다시 부르자 워커 세 대 모두 200 을 돌려줬어요. 한 번 지나가는 일로 넘길 수도 있었지만, 이 클러스터는 강의를 따라가며 매일 켜고 끌 실습 환경이에요. 켜자마자 실습을 시작하면 첫 명령이 바로 이 틈에 걸릴 수 있어요.

이 글은 이 클러스터를 매일 쓰는 환경으로 다듬은 기록이에요. Mac 에서 고친 파일이 노드에 바로 보이게 하고, Mac 의 kubectl 을 클러스터 버전에 맞추고, 더블클릭 한 번으로 켜고 들어가게 했습니다. 그리고 질문 하나를 따라갑니다. "껐다 켠 직후의 '준비 완료'는 왜 믿을 수 없었나."

이 글에서 다룰 것
· Mac 에서 고친 index.html 을 세 노드의 nginx 가 재배포 없이 보여 주려면 무엇을 붙여야 할까?
· Mac 의 kubectl 이 클러스터보다 마이너 버전 3 낮으면 무엇이 문제일까?
· 노드가 모두 Ready 이고 rollout 이 끝났다는데 왜 요청이 실패했을까?
· 재현 시도에서 실패가 다시 나지 않았다면, 무엇까지 말할 수 있을까?
· 재부팅 전 값으로는 통과할 수 없는 대기 조건은 어떻게 만들까?

1. Mac 에서 고친 파일이 세 노드에 바로 보인다

강의 실습은 대부분 YAML 을 쓰고 적용하는 일이에요. 노드에 ssh 로 들어가 파일을 쓰면 Mac 의 에디터를 쓸 수 없고, 파일은 VM 안에만 남아서 VM 을 지우면 함께 사라져요. 그래서 저장소의 shared/ 폴더를 모든 노드의 /lab 에 붙였습니다. Lima 로 VM 을 만들 때 마운트 설정을 하나 넘긴 것이고, 노드에서 보면 이렇게 붙어 있어요.

worker2$ findmnt -n -o TARGET,SOURCE,FSTYPE /lab /lab lima-e8a9ec3b02612c27 virtiofs

→ worker2 의 /lab 이 virtiofs 파일 시스템으로 붙어 있다는 뜻이에요.

📖 용어: virtiofs
VM 안에서 호스트(여기서는 Mac)의 폴더를 디렉터리로 붙여 쓰게 해 주는 공유 파일 시스템이에요. Lima 문서에 따르면 vz 로 띄운 VM 에서는 이것이 기본 마운트 방식입니다. 이 글에서는 Mac 에서 파일을 고치면 VM 안의 /lab 에서도 같은 내용이 보이게 해 주는 장치예요.

폴더가 노드에 있다고 해서 컨테이너가 그 폴더를 보는 것은 아니에요. 컨테이너는 이미지로 만든 자기 파일 시스템만 봅니다. 도커라면 docker run -v 호스트경로:컨테이너경로 로 붙였을 일이에요. 쿠버네티스에서는 파드 설정에 hostPath 볼륨을 적어 같은 일을 합니다.

📖 용어: hostPath 볼륨
파드가 뜬 노드의 파일이나 디렉터리를 컨테이너 안에 붙이는 볼륨이에요. 공식 문서는 "호스트 노드의 파일 시스템에 있는 파일이나 디렉터리를 파드에 마운트한다"고 설명합니다. 경로는 파드가 뜬 그 노드를 기준으로 찾아요.
containers: - name: nginx image: nginx:1.29 volumeMounts: - name: html mountPath: /usr/share/nginx/html # 컨테이너 안 경로 readOnly: true volumes: - name: html hostPath: path: /lab/web # 노드 경로 (= Mac 의 shared/web) type: Directory --- kind: Service spec: type: NodePort ports: - port: 80 nodePort: 30081

→ 노드의 /lab/web 을 nginx 의 웹 루트에 읽기 전용으로 붙이고, 노드의 30081 번 포트로 여는 NodePort 서비스를 만든다는 뜻이에요(shared/examples/web-volume.yaml 에서 필요한 줄만 옮겼어요). type: Directory 는 그 경로에 디렉터리가 이미 있어야 한다는 조건입니다.

📖 용어: NodePort
모든 노드에서 같은 포트 번호(여기서는 30081)를 열어, 클러스터 밖에서 그 포트로 들어온 요청을 서비스로 넘기는 서비스 종류예요. 이 실습에서는 Mac 에서 워커의 Mac 접근용 IP(192.168.64.3~.5)와 이 포트로 nginx 를 부릅니다.

이 Deployment 를 적용하자 nginx 3개가 k8s-worker1·2·3 에 하나씩 떴어요. index.html 이 v1 인 상태에서 세 워커의 NodePort 를 부르면 세 곳 모두 v1 이 나옵니다. 그다음 Mac 에서 파일 내용을 v2 로 바꾸고 다시 불렀어요. 파드를 다시 만들거나 재시작하지 않았는데 세 곳 모두 v2 를 돌려줬습니다.

그림 1. Mac 에서 index.html 한 줄을 바꾸자 재배포 없이 세 워커(192.168.64.3~.5)의 응답이 v1 에서 v2 로 바뀌었다

파일이 바뀐 곳은 Mac 한 곳뿐이에요. 파일은 Mac 에 한 벌만 있고, 세 노드의 /lab 이 모두 그 한 벌을 가리킵니다. 그래서 어느 노드에 뜬 nginx 든 같은 파일을 읽어요.

그림 2. 세 노드의 /lab 이 모두 같은 Mac 폴더라서, 어느 노드에 뜬 nginx 든 같은 파일을 읽는다
⚠️ 주의: hostPath 는 원래 "그 노드의 디스크"예요
공식 문서는 같은 설정으로 만든 파드라도 노드마다 파일이 달라 다르게 동작할 수 있다고 적고 있어요. 실제 멀티노드 클러스터에서 hostPath 로 웹 루트를 붙이면 파드가 어느 노드에 뜨느냐에 따라 보이는 내용이 달라집니다. 이 실습에서 세 곳이 같은 v2 를 보여 준 것은 쿠버네티스가 맞춰 준 결과가 아니라, 세 노드의 /lab 이 모두 같은 Mac 폴더이기 때문이에요. 같은 문서는 hostPath 에 보안 위험이 많으니 피할 수 있으면 피하라고도 적고 있어요. 그래서 여기서는 읽기 전용으로만 붙였습니다.

노드 안에서 도커 방식 그대로 해 보고 싶을 때도 있어요. 노드에는 Lima 가 containerd 와 함께 설치한 nerdctl 이 있어서, sudo nerdctl run -v /lab/web:/usr/share/nginx/html nginx:1.29 형태로 같은 -v 문법을 쓸 수 있어요. 이렇게 띄운 컨테이너는 파드가 아니라서 kubectl 로는 보이지 않습니다. 이 방식은 이번 실행 기록에 남기지 않았어요.

2. Mac 의 kubectl 은 클러스터보다 마이너 버전 3 낮았다

Mac 에는 원래 kubectl 이 깔려 있었어요. 실습 클러스터에 붙이기 전에 버전부터 확인했습니다.

mac$ /usr/local/bin/kubectl version --client Client Version: v1.34.1 Kustomize Version: v5.7.1 mac$ ./lab kubectl version Client Version: v1.37.2 Kustomize Version: v5.8.1 Server Version: v1.37.2

→ Mac 에 있던 kubectl 은 v1.34.1 이고, ./lab kubectl 이 쓰는 kubectl 과 API 서버는 둘 다 v1.37.2 라는 뜻이에요.

📖 용어: 버전 차이 정책 (version skew policy)
쿠버네티스 구성 요소끼리 버전이 얼마나 달라도 되는지 정한 공식 규칙이에요. kubectl 은 kube-apiserver 와 마이너 버전 1 차이 안에서만 지원합니다. 공식 문서의 예가 마침 이 클러스터와 같아서, API 서버가 1.37 이면 kubectl 은 1.36·1.37·1.38 이 지원 범위예요.

1.34 는 1.37 과 마이너 버전이 3 차이 나서 지원 범위 밖이에요. 이 상태로 실제로 무엇이 깨지는지는 시험하지 않았어요. 다만 지원 범위 밖에서 강의를 따라가다 결과가 이상하게 나오면, 그게 버전 차이 때문인지 제 실수 때문인지 가를 수 없어요. 그래서 버전을 맞추기로 했습니다.

Mac 에 있던 kubectl 과 ~/.kube/config 는 그대로 두었어요. 실습 클러스터 때문에 Mac 의 기존 설정을 바꾸면, 실습 환경을 지운 뒤에도 그 변경이 남기 때문이에요. 대신 ./lab kubectl 을 처음 부르면 클러스터와 같은 v1.37.2 kubectl 을 dl.k8s.io 에서 받아 sha256 체크섬을 확인한 뒤 저장소 안 .lab/bin 에 둡니다. kubeconfig 도 .lab/kubeconfig 를 따로 써요. 이 kubeconfig 는 서버 주소를 마스터의 Mac 접근용 IP 로 바꾸고 tls-server-name: kubernetes 를 넣은 것인데, 그 이유는 5편에서 다룹니다.

💡 실무에서는: 터미널 하나만 실습 클러스터로 돌린다
매번 ./lab kubectl 이라고 치기 번거로우면 eval "$(./lab env)" 를 실행해요. 그 터미널에서만 KUBECONFIG 와 PATH 가 실습용으로 바뀌어서, 그냥 kubectl 이라고 쳐도 v1.37.2 가 실습 클러스터를 봅니다. 다른 터미널과 ~/.kube/config 는 영향을 받지 않아요.

3. "준비 완료" 다음 줄의 curl 이 000 이었다

이제 처음 장면으로 돌아갈게요. 수정 전의 ./lab up 은 VM 을 켜고 나서 아래 세 명령이 모두 끝나기를 기다린 뒤 "클러스터 준비 완료"를 출력했어요.

kubectl wait --for=condition=Ready nodes --all --timeout=300s kubectl -n kube-system rollout status daemonset/calico-node --timeout=300s kubectl -n kube-system rollout status deployment/coredns --timeout=300s

→ 노드 4대가 모두 Ready 가 되고, 노드마다 하나씩 도는 calico-node(DaemonSet)와 클러스터 DNS 를 맡는 coredns(Deployment)의 rollout 이 끝났다고 나오면 통과한다는 뜻이에요.

📖 용어: kubectl rollout status
Deployment 나 DaemonSet 의 상태 숫자를 지켜보다가 목표에 닿으면 끝나는 명령이에요. DaemonSet 이면 "4개 중 몇 개가 available 인가"를 보여 주는데, available 은 파드가 실행 중이고 Ready 인 상태를 뜻해요. 이 숫자는 컨트롤러가 API 서버에 적힌 파드 상태를 보고 계산한 값입니다.

처음 발견했을 때의 출력은 이랬어요. 그때 예제 앱은 nginx(NodePort 30080)였습니다.

mac$ ./lab kubectl get deploy nginx; curl -s -m 5 -o /dev/null -w "NodePort %{http_code}\n" http://192.168.64.4:30080 NAME READY UP-TO-DATE AVAILABLE AGE nginx 3/3 3 3 2m4s NodePort 000

→ 쿠버네티스는 nginx 3개가 모두 available 이라고 답했는데, 같은 줄의 curl 은 worker2(192.168.64.4)에서 5초 안에 HTTP 응답을 하나도 받지 못했다는 뜻이에요.

잠시 뒤 세 워커를 모두 불렀더니 이번에는 셋 다 200 이었어요. 같은 명령 묶음에서 kube-system 파드도 찍었는데, calico 줄만 옮기면 이렇습니다.

NAMESPACE NAME READY STATUS RESTARTS AGE NODE kube-system calico-kube-controllers-846669895c-flkv2 1/1 Running 1 (40s 5m16s kube-system calico-node-hkvnx 1/1 Running 1 (28s 5m16s kube-system calico-node-jwpcq 0/1 Running 1 (40s 5m16s kube-system calico-node-mwbxw 1/1 Running 1 (28s 5m16s kube-system calico-node-vp7t6 0/1 Running 1 (29s 5m16s

→ awk 로 열을 자르면서 RESTARTS 의 "(40s ago)" 가 쪼개져 다음 열로 밀렸어요. 그래서 오른쪽 끝 5m16s 는 NODE 가 아니라 AGE 입니다. 읽어 보면 calico 파드 5개가 모두 28~40초 전에 한 번씩 재시작했고, calico-node 4개 중 2개는 아직 준비되지 않았다(0/1)는 뜻이에요.

이 기록으로 확인되는 사실은 두 가지예요. 하나는 "준비 완료" 직후 쿠버네티스는 준비됐다고 답했는데 실제 요청은 실패했다는 점이에요. 다른 하나는 그 무렵 calico 파드들이 막 재시작한 상태였다는 점입니다. 000 의 직접 원인이 무엇이었는지는 이 출력만으로 가를 수 없어요. 이 실행은 작업 세션의 명령 기록에서 옮긴 것이라 ./lab up 의 원본 로그도 남아 있지 않습니다.

4. 재부팅 전에 적힌 Ready 가 잠깐 남아 있었다

노드 Ready 와 rollout status 는 왜 통과했을까요? 먼저 이 값을 누가 쓰는지 봐야 해요. 노드의 상태도, 파드의 Ready 도 그 노드의 kubelet 이 API 서버에 적습니다. VM 을 끄면 kubelet 도 함께 꺼지니, 마지막으로 적은 "Ready" 가 API 서버에 그대로 남아요. 노드의 Ready 가 바뀌는 길은 둘이에요. 다시 켜진 kubelet 이 새 상태를 덮어쓰거나, kube-controller-manager 가 그 노드에서 소식이 끊겼다고 판정하는 경우입니다.

📖 용어: node-monitor-grace-period
kube-controller-manager 가 노드를 응답 없음으로 판정하기 전에 기다리는 시간이에요. 기본값은 50초이고, 그동안 kubelet 소식이 없으면 노드의 Ready 를 Unknown 으로 바꿉니다. kubelet 은 기본 10초마다 Lease 라는 객체를 갱신해서 살아 있다고 알려요.

여기서부터는 기록이 아니라 제 해석이에요. kube-controller-manager 는 마스터 VM 안에서 도는 정적 파드라서(1편), 마스터를 끄면 판정을 내릴 쪽도 함께 꺼져요. 다시 켠 뒤에는 워커의 컨테이너들이 20초 안팎에 다시 떴습니다(아래 재현 기록). 50초 판정에 걸릴 일이 없었던 거예요. 끌 때도 ./lab stop 은 워커를 먼저 끄고 마스터를 마지막에 끄니, 그 사이가 50초를 넘지 않았다는 전제가 깔려 있어요. 그 간격은 재지 않았습니다. 그러니 컨트롤 플레인이 보기에는 노드가 꺼졌던 적이 없고, kubelet 이 새 상태를 덮어쓰기 전까지 API 서버에는 재부팅 전의 Ready 가 남아 있었다고 봅니다. 수정 전 대기 조건은 바로 이 값을 읽으니, kubelet 이 덮어쓰기 전에 확인하면 재부팅 전 상태를 보고도 통과할 수 있어요. kube-controller-manager 가 다시 켜질 때 노드마다 50초를 어디서부터 세는지는 확인하지 않았습니다.

이 해석을 확인하려고 같은 상황을 다시 만들었어요. ./lab stop 으로 4대를 끈 직후 VM 만 다시 켜고, 수정 전 대기 조건 세 개로 기다린 다음 바로 NodePort 를 불렀습니다. 예제 앱은 1절의 web(NodePort 30081)이에요.

mac$ date +%T; limactl start --tty=false k8s-master >/dev/null 2>&1; for n in k8s-worker1 k8s-worker2 k8s-worker3; do limactl start --tty=false $n >/dev/null 2>&1 & done; wait; date +%T 21:27:45 21:28:09

→ 마스터를 먼저 켜고 워커 세 대를 함께 켜는 데 21:27:45 부터 21:28:09 까지 24초가 걸렸다는 뜻이에요.

그림 3. 4대를 막 켠 직후 calico-node 가 3 of 4 에서 시작해 0 of 4 로 떨어졌다. 첫 숫자는 재부팅 전 값으로 보인다

노드 4대는 모두 condition met 이었고, calico-node 는 "3 of 4" 에서 시작해 "0 of 4" 로 떨어졌다가 1, 2, 3 을 거쳐 끝났어요. 대기는 21:28:32 에 끝났고, 같은 초에 부른 NodePort 3곳은 모두 200 이었습니다. 이때 파드 상태는 이랬어요.

NAME READY STATUS RESTARTS AGE calico-node-gc95j 1/1 Running 1 (27s ago) 8m52s calico-node-kn8n4 1/1 Running 1 (28s ago) 8m52s calico-node-lj6rx 1/1 Running 1 (27s ago) 8m52s calico-node-tvx2h 1/1 Running 1 (39s ago) 8m56s NAME READY STATUS RESTARTS AGE web-844546cf5c-9mqds 1/1 Running 1 (28s ago) 118s web-844546cf5c-kdbp9 1/1 Running 1 (27s ago) 118s web-844546cf5c-lsfz8 1/1 Running 1 (27s ago) 118s 21:28:32

→ 대기를 통과한 시점에 calico-node 4개와 web 3개가 모두 27~39초 전에 한 번씩 재시작해 준비된(1/1) 상태였다는 뜻이에요. 60초 뒤에 다시 불러도 세 곳 모두 200 이었어요.

실패는 재현되지 않았어요. 대기를 통과한 순간 이미 모든 파드가 재부팅 뒤에 다시 떠서 준비돼 있었으니, 이번에는 대기 조건이 실제 상태를 보고 통과한 셈이에요. 조건도 처음과 똑같지는 않았어요. 원래 ./lab up 은 VM 을 켠 뒤 노드 설정 확인과 마스터 스크립트를 한 번 더 돌리고 나서 기다리는데, 재현에서는 그 단계를 건너뛰었습니다. 기다리기 시작한 시점이 달랐다는 뜻이에요.

그래도 이 재현은 해석을 받쳐 주는 장면을 하나 남겼어요. 4대를 막 다시 켠 직후인데 rollout status 의 첫 줄이 "3 of 4 available" 이었고, 다음 줄에서 0 of 4 로 떨어졌어요. 처음의 3 은 재부팅 뒤의 실제 상태가 아니라, kubelet 이 아직 덮어쓰지 않은 재부팅 전 값이었다고 봅니다. 마스터를 먼저 켰으니 마스터의 calico-node 하나만 먼저 새 상태로 바뀌어 있었다고 보면 3 이라는 숫자와 맞아요. 다만 NODE 열을 찍지 않아서 그 하나가 어느 노드의 것인지는 확인하지 못했어요. 첫 숫자가 4 of 4 였다면 rollout status 는 그 자리에서 끝났을 수도 있어요. 통과하느냐 마느냐가 확인하는 순간에 따라 갈리는 조건이었던 거예요.

그림 4. 재현 기록의 시각을 한 줄에 놓았다. 모두 50초 안에 돌아왔고, 주황 구간은 측정이 아니라 해석이다

5. 재부팅 뒤에만 생기는 값을 기다린다

수정 전 조건은 "지금 Ready 인가"만 물었어요. 재부팅 전 값도 이 질문에는 "예"라고 답할 수 있습니다. 그래서 질문을 "VM 을 켠 뒤에 새로 시작해서 Ready 인가"로 바꿨어요. 이 질문에 답하려면 컨테이너가 언제 시작했는지 알아야 합니다.

📖 용어: startedAt
파드 상태의 containerStatuses[].state.running.startedAt 은 컨테이너가 마지막으로 (다시) 시작된 시각이에요. 공식 API 문서의 설명은 "Time at which the container was last (re-)started" 입니다. 재부팅 뒤 kubelet 이 컨테이너를 다시 띄우고 상태를 적어야 이 값이 바뀌어요.
# cmd_up (요지): 꺼져 있던 VM 이 하나라도 있으면, 켜기 직전 시각(UTC)을 기억한다 for n in $(nodes); do [ "$(vm_status "$n")" = "Running" ] || booted_at=$(date -u +%Y-%m-%dT%H:%M:%SZ) done # wait_ready (요지): 수정 전 조건 세 개를 통과한 다음, 켠 시각이 있으면 더 기다린다 for i in $(seq 1 60); do stale=$(kubectl -n kube-system get pods -o jsonpath='{range .items[*]}{range .status.containerStatuses[*]}{.ready}{" "}{.state.running.startedAt}{"\n"}{end}{end}' \ | awk -v since="$booted_at" '$1 != "true" || $2 == "" || $2 < since' | wc -l) [ "$stale" -eq 0 ] && exit 0 echo "kube-system 컨테이너 $stale 개가 아직 재기동 중" sleep 5 done exit 1

→ kube-system 의 모든 컨테이너에서 준비 여부(ready)와 시작 시각(startedAt)을 한 줄씩 뽑고, 준비가 안 됐거나, 실행 중이 아니어서 시작 시각이 비었거나, 켠 시각보다 먼저 시작한 줄을 센다는 뜻이에요. 그 수가 0 이 될 때까지 5초 간격으로 최대 60번 확인하고, 끝내 0 이 안 되면 실패로 끝납니다. 두 시각은 모두 UTC 의 YYYY-MM-DDThh:mm:ssZ 형태라 문자열 비교로 앞뒤를 가릴 수 있어요. 실제 파일에서는 이 부분이 마스터에서 도는 스크립트 안에 있어서 $ 일부가 \$ 로 이스케이프돼 있어요.

그림 5. 수정 전 조건은 재부팅 전 값으로도 채워질 수 있고, 수정 후 조건은 재부팅 뒤의 kubelet 만 채울 수 있다

재부팅 전 값에 적힌 시작 시각은 모두 VM 을 켜기 전이에요. 그러니 이 조건은 kubelet 이 재부팅 뒤에 컨테이너를 다시 띄우고 새 상태를 적어야만 채워집니다. 재부팅 전 값으로는 채울 수 없는 조건을 기다리면, 언제 확인하든 오래된 값을 보고 통과하는 일이 없어요. 고친 뒤 다시 껐다 켜 봤습니다.

mac$ ./lab stop >/dev/null; S=$(date +%s); ./lab up >/dev/null 2>&1; echo "up 소요: $(( $(date +%s) - S ))초" up 소요: 50초 mac$ grep '재기동 중' .lab/logs/k8s-master.log | tail -4 kube-system 컨테이너 13 개가 아직 재기동 중 kube-system 컨테이너 8 개가 아직 재기동 중 kube-system 컨테이너 7 개가 아직 재기동 중 kube-system 컨테이너 6 개가 아직 재기동 중 mac$ for ip in 192.168.64.3 192.168.64.4 192.168.64.5; do curl -s -m3 -o /dev/null -w "$ip:30081 %{http_code}\n" http://$ip:30081; done 192.168.64.3:30081 200 192.168.64.4:30081 200 192.168.64.5:30081 200

→ 꺼진 상태에서 켜는 데 50초가 걸렸고, 대기 로그의 마지막 네 줄에서 새 조건을 못 채운 컨테이너가 13, 8, 7, 6개로 줄었고, 끝난 뒤 NodePort 3곳이 모두 200 이었다는 뜻이에요.

이 로그에서 하나 더 읽을 수 있어요. 이 반복문은 수정 전 조건 세 개를 모두 통과한 뒤에야 돌기 시작합니다. 그러니 수정 전 코드였다면 "13 개" 줄이 찍히기 전에 이미 "클러스터 준비 완료"를 출력했을 거예요. "13 개" 줄과 "6 개" 줄 사이에만 5초 쉬기가 세 번 있었으니, 수정 전 조건이 통과한 뒤 적어도 15초 동안은 켠 뒤에 새로 떠서 준비된 상태가 아닌 컨테이너가 남아 있었다는 뜻입니다.

⚠️ 주의: 이 수정이 증명하지 못하는 것
• 수정 뒤 한 번 돌려 200 을 봤지만, 수정 전 조건으로 한 재현에서도 200 이 나왔어요. 확인하는 순간에 따라 갈리는 문제라 성공 한 번으로는 고쳐졌다고 증명할 수 없어요. 이 수정의 근거는 성공 횟수가 아니라, 재부팅 전 값으로는 조건을 채울 수 없다는 구조예요.
• kube-system 컨테이너만 봐요. web 같은 실습용 파드는 이 조건에 들어 있지 않아요.
• Mac 의 시계로 잰 켠 시각과 노드가 적은 시작 시각을 비교해요. 두 시계가 크게 어긋나면 판정이 틀어질 수 있는데, 이 실습에서 시계 차이를 재지는 않았어요.
• 처음 고친 이 버전은 4대를 함께 껐다 켜는 경우만 맞았어요. 한 대만 껐다 켜는 경우의 결함은 바로 아래에서 다룹니다.

한 대만 껐다 켜면 이 조건은 끝내 채워지지 않았다

이 글을 쓰면서 코드를 다시 읽다가 결함을 하나 더 찾았어요. 위 조건은 kube-system 의 모든 컨테이너가 켠 시각 뒤에 시작했기를 요구합니다. 4대를 함께 껐다 켤 때는 맞는 요구예요. 그런데 worker3 한 대만 꺼져 있던 상태에서 ./lab up 을 하면, 계속 켜져 있던 마스터와 worker1·worker2 의 컨테이너는 켠 시각보다 먼저 시작한 상태 그대로예요. 이 컨테이너들은 다시 시작할 일이 없으니 조건을 영영 채울 수 없고, 5분을 기다린 뒤 실패로 끝납니다. 재부팅 전 값을 걸러 내려고 만든 조건이, 재부팅하지 않은 노드까지 같은 잣대로 재고 있었어요.

그래서 "이번에 켠 노드"의 컨테이너만 보도록 바꿨어요. VM 을 켜기 전에 꺼져 있던 VM 이름을 모아 두고, 파드마다 어느 노드에 떠 있는지(spec.nodeName)를 함께 뽑아서 그 목록에 든 노드의 줄만 셉니다.

# cmd_up: 꺼져 있던 VM 이름을 모으고, 하나라도 있으면 켜기 직전 시각(UTC)을 기억한다 for n in $(nodes); do [ "$(vm_status "$n")" = "Running" ] || booted_nodes="$booted_nodes $n" done [ -z "$booted_nodes" ] || booted_at=$(date -u +%Y-%m-%dT%H:%M:%SZ) # wait_ready: 파드마다 "노드이름 ready,startedAt ..." 한 줄을 뽑아, 이번에 켠 노드의 줄만 센다 kubectl -n kube-system get pods -o go-template='{{range .items}}{{.spec.nodeName}}{{range .status.containerStatuses}} {{.ready}},{{with .state.running}}{{.startedAt}}{{end}}{{end}}{{"\n"}}{{end}}' \ | awk -v since="$booted_at" -v nodes=" $booted_nodes " ' index(nodes, " " $1 " ") == 0 { next } NF == 1 { n++; next } { for (i = 2; i <= NF; i++) { split($i, c, ","); if (c[1] != "true" || c[2] == "" || c[2] < since) n++ } } END { print n + 0 }'

→ 이번에 켠 노드가 아니면 그 파드는 건너뛰고, 켠 노드의 파드에서는 컨테이너 상태가 아직 없거나, 준비가 안 됐거나, 켠 시각보다 먼저 시작한 컨테이너를 하나씩 센다는 뜻이에요. jsonpath 대신 go-template 을 쓴 것은 파드의 노드 이름과 컨테이너 상태를 한 줄에 함께 뽑기 위해서예요.

이번에는 코드를 읽는 데서 멈추지 않고 실제로 돌려 봤어요. 나머지 3대는 켜 둔 채 worker3 만 끄고 ./lab up 을 실행했습니다.

mac$ limactl list --format '{{.Name}} {{.Status}}' k8s-master k8s-worker1 k8s-worker2 k8s-worker3 k8s-master Running k8s-worker1 Running k8s-worker2 Running k8s-worker3 Stopped mac$ S=$(date +%s); ./lab up >/dev/null 2>&1; echo "exit=$? up 소요: $(( $(date +%s) - S ))초" exit=0 up 소요: 39초 mac$ grep '재기동 중' .lab/logs/k8s-master.log | tail -3 kube-system 컨테이너 1 개가 아직 재기동 중 kube-system 컨테이너 1 개가 아직 재기동 중 kube-system 컨테이너 1 개가 아직 재기동 중 master$ kubectl -n kube-system get pods -o wide --field-selector spec.nodeName=k8s-worker3 | awk '{print $1, $2, $4, $5, $6, $7, $8}' | column -t NAME READY RESTARTS AGE IP NODE NOMINATED calico-node-kn8n4 1/1 3 (32s ago) 35m 192.168.104.5 kube-proxy-kc292 1/1 3 (32s ago) 35m 192.168.104.5

→ ./lab up 은 39초 만에 정상으로 끝났어요(exit=0). 대기 로그에는 worker3 에서 아직 다시 뜨지 않은 컨테이너 1개만 남아 있다가 사라졌고, 계속 켜져 있던 노드의 컨테이너는 세지 않았어요. worker3 의 calico-node 와 kube-proxy 는 32초 전에 다시 시작한 상태였습니다. 열은 awk 로 잘라서 RESTARTS 의 "(32s ago)" 가 두 칸으로 나뉘어 보여요.

고친 뒤 4대를 함께 껐다 켜는 경우도 다시 돌렸어요. 68초 만에 정상으로 끝났고, 이미 켜져 있을 때의 ./lab up 은 2초였습니다.

⚠️ 주의: VM 이 부팅 첫 단계에서 멈추기도 했어요
위 회귀 시험 중에 worker1 의 limactl start 가 10분 넘게 끝나지 않은 적이 있어요. 다른 3대는 15초 안에 떴고, worker1 은 Lima 로그에 "vm state change: running" 까지만 찍힌 채 VM 콘솔 로그 파일이 0바이트였습니다. 운영체제가 한 줄도 출력하지 않은 거예요. 강제로 끄고(limactl stop -f) 다시 켜자 17초 만에 정상으로 부팅했어요. 원인은 찾지 못했습니다. 그래서 ./lab up 이 VM 하나를 3분 기다려도 뜨지 않으면 강제로 끄고 한 번만 다시 켜도록 바꿨어요. 평소 부팅은 15~25초라 3분이면 여유가 충분합니다.
💡 실무에서는: rollout status 는 재부팅을 모른다
rollout status 는 이름 그대로 롤아웃(설정을 바꿔 파드를 새로 띄우는 과정)이 끝났는지를 보는 명령이에요. 재부팅은 설정을 바꾸지 않으니 새 롤아웃이 생기지 않고, 위 출력에서 보듯 available 숫자가 목표에 닿으면 끝나요. 재부팅이나 노드 복구 뒤의 준비 확인에 이 명령을 쓴다면, 그 숫자가 재부팅 전 값으로도 채워질 수 있는지 먼저 따져 봐야 해요.

6. 더블클릭 한 번으로 켜고 들어간다

매일 쓰는 데 마지막으로 걸린 것은 터미널을 열고 저장소 폴더로 가서 명령을 치는 일이었어요. 그래서 저장소에 Finder 에서 더블클릭하는 파일 세 개를 두었습니다. 확장자가 .command 인 셸 스크립트는 Finder 에서 더블클릭하면 터미널 창이 열리며 실행돼요.

#!/bin/bash # Finder 에서 더블클릭: 클러스터를 켜고 마스터 노드에 접속한다. cd "$(dirname "$0")" || exit 1 if ./lab up; then echo echo "마스터 노드에 접속합니다. 나가려면 exit (클러스터는 계속 켜져 있음)" ./lab ssh master else echo read -r -p "실패했습니다. 위 메시지를 확인하고 엔터를 누르면 창을 닫습니다... " _ fi

→ start.command 는 파일이 있는 폴더로 옮겨 ./lab up 을 돌리고, 성공하면 곧바로 마스터 노드 셸로 들어간다는 뜻이에요. 실패하면 엔터를 칠 때까지 기다리게 해서, 오류 메시지를 읽기 전에 스크립트가 끝나지 않게 했어요.

stop.command 는 ./lab stop 으로 4대를 끄고, files.command 는 공유 폴더 shared/ 를 VS Code(없으면 Finder)로 열어요. 처음 한 번은 VM 을 만들고 설치까지 하느라 368초가 걸렸고, 꺼진 상태에서 다시 켜는 데는 50초, 이미 켜져 있으면 약 2초면 끝나요.

start.command 는 "준비 완료"가 나오자마자 마스터 셸을 열어요. 사람이 따로 확인할 틈이 없습니다. 그 "준비 완료"가 재부팅 전 값을 보고 나온 것이라면, 들어가서 친 첫 명령이 바로 그 틈에 걸립니다. 켜는 일을 더블클릭 한 번으로 줄일수록 "준비 완료"라는 출력이 사실이어야 했어요.

✍️ 오늘의 요약
노드 Ready 와 rollout status 는 API 서버에 적힌 값을 읽어요. 4대를 함께 껐다 켜면 kubelet 이 새 상태를 적기 전까지 재부팅 전의 Ready 가 남아 있을 수 있고, 수정 전 대기 조건은 그 틈에 통과할 수 있었다고 봐요.

재현 시도에서 실패는 다시 나지 않았지만, rollout status 가 3 of 4 에서 0 of 4 로 떨어지는 장면은 남았어요. 그래서 VM 을 켠 그 노드에서 새로 시작해 준비된 kube-system 컨테이너만 세도록 바꿨습니다. 그 밖에 Mac 폴더를 virtiofs 와 hostPath 로 세 노드의 nginx 에 붙였고, kubectl 은 클러스터와 같은 v1.37.2 를 따로 받아 썼어요. 준비 확인은 "지금 Ready 인가"가 아니라 "그 일이 있은 뒤에 Ready 가 됐나"를 물어야 합니다.
