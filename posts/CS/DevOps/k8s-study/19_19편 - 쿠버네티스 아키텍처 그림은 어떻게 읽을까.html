21편. 컨트롤 플레인은 왜 3대 이상이고 워커 노드 수에는 왜 정답이 없을까

11월 14일 오후, 쿠버네티스 아키텍처 그림 한 장을 앞에 두고 제가 처음 적은 말은 "해석 좀"이었어요. 왼쪽에는 kubectl apply -f pod.yaml을 치는 개발자와 Dashboard가 있었고 여기서 나간 요청은 0) TLS, 1) Authentication, 2) Authorization, 3) Admission controller라고 번호가 붙은 칸을 차례로 지나 가운데의 API Server로 들어가게 그려져 있었어요. API Server 둘레에는 etcd(key-value, SSOT, gRPC), Controller Manager(Controller Loops), Scheduler(Bind Pod to Node), Cloud Controller Manager와 Cloud Provider API가 붙어 있었어요. 아래에는 워커 노드 세 대가 있었고 노드마다 kube-proxy, Networking(CNI), kubelet, containerd(runtime)와 그 밑의 OCI가 그려져 있었습니다. 구석에는 Calico의 BGP·BIRD·calicoctl이 있었고 바깥(External world)에서 들어오는 End User까지 그려져 있었어요.

상자 이름은 대부분 1편에서 한 번씩 본 것이었어요. 막힌 곳은 화살표였습니다. 누가 누구를 부르는지, 화살표 하나가 끊기면 무엇이 멈추는지는 그림만 봐서는 알 수 없었거든요. 그래서 그날 오후 내내 화살표를 하나씩 우리 클러스터에서 확인하고 몇 개는 직접 끊어 봤어요. 그림을 처음 보고 적은 말은 "이거 하나만 잘 이해해도 쿠버네티스 이해했다고 할 수 있겠다"였고 실험을 몇 개 하고 나서 적은 말은 "모든 리소스들이 API 서버만 보고 있으니까 선언형/명령어 구조가 되는구나"였어요. 이번 글에서는 이 두 문장 사이에서 확인한 것을 정리해요.

20편부터 33편까지는 이 그림의 상자나 화살표를 하나씩 골라 깊이 파고든 글이에요. 그래서 이번 편에서는 화살표마다 우리 클러스터에서 본 증거를 한 줄씩 붙이고 자세한 이야기는 해당 편으로 넘길게요. 실습 클러스터는 1~7편에서 만든 환경(Lima VM 4대, 쿠버네티스 v1.37.2, containerd 2.4.1, Calico v3.33.0)이에요.

1. 그림을 세 구역으로 나누고 상자마다 누가 띄우는지 본다

먼저 원래 그림을 우리 클러스터의 실제 이름으로 다시 그렸어요. 상자는 거의 그대로 두고 요청 하나가 지나가는 순서대로 ①~⑥ 번호를 붙였습니다.

그림 1. ①~⑥을 따라가면 kubectl 명령 한 줄이 노드의 컨테이너로 떠서 사용자 요청을 받기까지의 순서가 보인다

번호마다 이번 글의 몇 절과 몇 편에서 다루는지 함께 적으면 이래요. 이 순서는 2편에서 Deployment 하나를 만들면서 이벤트와 etcd 키로 한 번 따라가 봤어요.

① 개발자의 요청이 TLS, 인증, 인가, 어드미션을 차례로 지나 API 서버에 들어가요. (2절, 32·33편)
② API 서버가 객체를 etcd에 저장해요. 구성 요소 중에서 etcd에 직접 붙는 것은 API 서버뿐이에요. (2·3절, 22편)
③ 컨트롤러 매니저가 새로 저장된 객체를 보고 거기에 필요한 객체를 더 만들어 API 서버에 적어요. Deployment를 만들면 ReplicaSet과 파드가 이 단계에서 생기고 pod.yaml로 파드를 바로 만들면 이 단계에서 만들 ReplicaSet이 없어요. (3절, 20편)
④ 스케줄러는 아직 노드가 정해지지 않은 파드를 보고 노드를 고른 뒤 그 결과를 API 서버에 기록해요. (20·23편)
⑤ 그 노드의 kubelet이 자기 노드에 배정된 파드를 발견하고 containerd에 컨테이너를 만들라고 요청해요. 이때 CNI 플러그인이 파드에 IP를 붙여요. (4절, 26·27·31·34편)
⑥ kube-proxy와 CoreDNS가 Service를 보고 각각 iptables 규칙과 DNS 응답을 준비해 두면 사용자 요청이 파드에 닿아요. (4절, 28·29편)

원래 그림은 상자를 컨트롤 플레인, 워커 노드, 그 밖의 add-on 세 구역으로 나눠 놓았어요. 그런데 우리 클러스터에서 각 상자가 실제로 어떻게 떠 있는지 보니 구역보다 "누가 띄우나"로 나누는 편이 더 잘 들어맞았어요. 아래는 kube-system의 파드를 소유자(OWNER)와 함께 뽑고 노드의 systemd 서비스 상태를 같이 본 화면이에요.

그림 2. OWNER가 Node면 kubelet이 파일을 읽어 띄운 정적 파드이고 DaemonSet·ReplicaSet이면 컨트롤러가 API 객체를 보고 만든 파드다

OWNER가 Node인 파드 넷은 마스터의 /etc/kubernetes/manifests에 있는 파일 네 개와 이름이 같아요. 이 넷은 kubelet이 그 폴더의 파일을 읽어 직접 띄운 정적 파드이고 API 서버에서 보이는 것은 kubelet이 따로 만들어 둔 미러 파드예요(5편, 26편). kubelet과 containerd는 파드 목록에 아예 없어요. 이 둘은 노드의 systemd 서비스로 떠 있어요. 나머지는 DaemonSet이나 ReplicaSet이 만든 평범한 파드예요. 표로 정리하면 이래요.

표에서 눈여겨볼 곳은 kube-proxy와 CNI예요. 그림에서는 워커 노드 안에 그려져 있고 실제로도 노드마다 돌지만 설치 방식으로 보면 add-on이에요. 공식 문서인 Cluster Architecture는 add-on을 "DaemonSet, Deployment 같은 쿠버네티스 리소스로 클러스터 기능을 구현하는 것"이라고 설명하고 그 목록에 네트워크 플러그인(CNI)을 넣어 두었어요. kubeadm도 coredns와 kube-proxy를 add-on으로 따로 묶어 kubeadm init phase addon의 하위 명령으로 설치해요(29편). 같은 문서는 컨트롤 플레인을 kubelet이 관리하는 정적 파드로 띄우는 방식을 kubeadm 같은 도구가 흔히 쓰는 방식으로 소개해요. 그림의 구역은 역할을 나눈 것이고 실제로 상자를 띄우는 주체는 셋이에요. 파일을 읽는 kubelet, 노드의 systemd, 그리고 API 객체를 보는 컨트롤러예요.

그림에는 있는데 우리 클러스터에는 없는 상자도 하나 있어요. 클라우드 컨트롤러 매니저(CCM)예요. 이 상자를 보고 제가 물은 것은 "CCM인가 컨트롤러 매니저?"였어요. 둘은 다른 프로그램이에요. 우리 클러스터의 kube-controller-manager는 Deployment, ReplicaSet, 노드 수명 주기 같은 컨트롤러 49개를 바이너리 하나에 묶은 프로그램이에요. CCM은 클라우드 API가 있어야 일할 수 있는 컨트롤러만 따로 모은 프로그램이에요. Cluster Architecture 문서는 그 예로 노드, 라우트, 서비스(클라우드 로드밸런서) 컨트롤러를 들어요. 같은 문서에는 "온프레미스나 내 PC 안의 학습 환경에서 돌리는 클러스터에는 클라우드 컨트롤러 매니저가 없다"는 문장도 있어요. 우리 클러스터가 바로 그 경우였어요. cloud-controller-manager 파드는 0개였고 노드의 providerID는 모두 비어 있었어요. 그래서 type: LoadBalancer Service를 만들고 약 30초 동안 지켜보는 내내 EXTERNAL-IP는 <pending>이었고 이벤트도 하나 없었어요. 같은 Service라도 NodePort(worker1:32019)로 보낸 요청에는 바로 200이 왔어요. CCM이 없는 이 빈자리를 무엇으로 채울 수 있는지는 24편에서 다뤄요.

2. 요청 하나는 API 서버 안에서 관문 네 개를 지나 etcd에 저장된다

kubectl 요청이 권한 문제로 거절될 때 자주 보는 말은 "Unauthorized"와 "Forbidden"이에요. 둘은 고칠 곳이 달라서 어느 관문에서 막혔는지부터 알아야 해요. 그림 왼쪽의 0) TLS, 1) Authentication, 2) Authorization, 3) Admission controller는 공식 문서 Controlling Access to the Kubernetes API에 나오는 순서 그대로예요. 우리 클러스터에서 관문마다 본 결과를 한 장에 모았어요. 인증과 인가를 직접 시험해 본 실험은 32편에, 어드미션이 요청을 고치고 거절하는 모습은 33편에 자세히 적었어요.

📖 용어: 인증과 인가 (authentication, authorization)
인증은 "요청을 보낸 쪽이 누구인가"를 정하는 단계이고 인가는 "그 사용자가 이 일을 해도 되는가"를 정하는 단계예요. 쿠버네티스 API에는 사람 사용자를 나타내는 객체가 따로 없어요. 대신 인증 단계가 클라이언트 인증서나 토큰에서 사용자 이름과 그룹을 꺼내 오면 인가 단계가 그 이름과 그룹으로 RBAC 같은 규칙을 찾아봐요.
그림 3. 401은 인증에서 나온다. 자격 없이 보낸 요청은 익명 사용자로 인증을 통과한 뒤 인가에서 403으로 막혔다 (자세한 실험은 32·33편)

관문마다 핵심만 적으면 이래요.

0) TLS. API 서버는 6443 포트에서 TLS 연결을 받고 클라이언트가 낸 인증서는 kubeadm이 만든 CA(--client-ca-file=/etc/kubernetes/pki/ca.crt)로 확인해요(5편, 32편).

1) 인증. worker1에서 같은 GET 요청을 자격만 바꿔 보내 보니 가짜 토큰을 붙인 요청은 401 Unauthorized를 받았는데 자격을 아예 붙이지 않은 요청은 403 Forbidden을 받았어요. Forbidden 메시지에 찍힌 사용자 이름은 system:anonymous였어요. Authenticating 문서의 Anonymous requests 절에 따르면 익명 요청이 켜져 있을 때 다른 인증 방법이 거절하지 않은 요청은 system:anonymous라는 사용자의 요청으로 처리되고 틀린 토큰을 낸 요청은 401을 받아요. 익명 요청은 인가 모드가 AlwaysAllow가 아니면 기본으로 켜지고 우리 v1.37.2 바이너리의 --help에도 --anonymous-auth의 기본값이 true로 적혀 있었어요. 자격 없는 요청은 인증에 실패한 것이 아니라 익명 사용자로 인증에 성공한 뒤 인가에서 막혀서 403을 받았어요. 반대로 익명 요청을 꺼 둔 kubelet(10250 포트)은 자격 없이 보낸 요청에 401로 응답했어요(26편, 32편).

2) 인가. 우리 API 서버는 --authorization-mode=Node,RBAC로 떠 있었어요. --as로 default ServiceAccount를 가장해 파드 목록을 요청하자 Forbidden이 돌아왔어요. 관리자 kubeconfig의 사용자 kubernetes-admin(그룹 kubeadm:cluster-admins, system:authenticated)으로 같은 권한을 kubectl auth can-i로 물어보자 yes가 나왔어요(10편, 32편).

3) 어드미션. 이름과 이미지만 적은 파드를 --dry-run=server로 보내 보니 어드미션 플러그인 셋이 파드의 빈칸을 채워 넣었어요. ServiceAccount 플러그인은 serviceAccountName과 토큰 볼륨을, DefaultTolerationSeconds 플러그인은 not-ready·unreachable taint가 NoExecute로 붙어도 300초 동안 견디는 toleration 두 개를, Priority 플러그인은 priority 0을 넣었어요. 우리 바이너리에서 기본으로 켜지는 어드미션 플러그인은 25개였고 kubeadm이 NodeRestriction을 하나 더 켰어요. 어드미션이 거절할 때도 대개 Forbidden이 나와요. 17편에서 본 "exceeded quota"도 ResourceQuota 플러그인이 거절한 결과였어요(33편).

이 300초는 25편의 실험과 바로 이어져요. 25편에서 worker3의 kubelet을 300초 넘게 멈춰 두자 노드에 unreachable taint가 붙었고 그 시각(08:23:26Z)에서 정확히 300초 뒤인 08:28:26Z에 그 노드의 myweb 파드 두 개가 축출됐어요. 같은 시각에 다른 노드에서 새 파드 두 개가 만들어졌어요.

4) 저장. 모든 관문을 지난 요청은 객체 종류별 검증을 거쳐 --etcd-servers=https://127.0.0.1:2379의 etcd에 기록돼요. 그림의 etcd 옆에 적힌 gRPC는 이 연결의 프로토콜이고 etcd API 문서에도 "etcd 서버로 보내는 모든 API 요청은 gRPC 원격 프로시저 호출"이라고 적혀 있어요. kubectl이 보여 주는 resourceVersion은 etcd 키의 mod_revision과 같았고 실습용 Secret의 값은 etcd 원본에 평문으로 들어 있었어요(22편). 그래서 etcd는 API 서버 말고는 아무도 만지지 못하게 막아 둬야 해요.

3. 모든 구성 요소가 API 서버만 보기 때문에 쿠버네티스는 선언형으로 움직인다

원래 그림에서는 API 서버를 가운데 두고 여러 상자가 화살표로 이어져 있어요. 이것만 보면 스케줄러가 kubelet에게 "이 파드를 띄워라"라고 직접 말한다고 읽을 수도 있어요. 1편에서는 공식 문서의 hub-and-spoke 문장을 인용해 "구성 요소끼리는 서로를 부르지 않는다"고 정리했는데 이번에는 그 말이 실제 연결에서도 맞는지 확인했어요. 마스터와 worker1에서 ss로 맺어진(established) TCP 연결을 뽑아 프로세스마다 상대 포트별로 개수를 셌어요.

그림 4. 2379에 붙은 프로세스는 kube-apiserver 하나였고 나머지는 모두 6443을 향했다

etcd가 받은 연결 92개는 모두 kube-apiserver가 연 것이었어요. 컨트롤러 매니저(2개), 스케줄러(2개), kube-proxy, kubelet, kubectl은 모두 6443 포트, 곧 API 서버에 연결돼 있었어요. 스케줄러나 컨트롤러 매니저가 kubelet(10250)이나 etcd(2379)에 직접 맺은 연결은 하나도 없었어요.

이 표에 잡히지 않은 프로그램도 있었어요. calico-node와 CoreDNS, calico-kube-controllers예요. 이 셋은 6443이 아니라 10.96.0.1:443으로 연결돼 있었어요. 10.96.0.1은 default 네임스페이스에 있는 kubernetes Service의 주소이고 이 Service의 EndpointSlice가 가리키는 곳은 192.168.104.1:6443, 곧 API 서버예요. CoreDNS와 calico-kube-controllers는 파드 네트워크를 쓰기 때문에 그 파드의 네트워크 네임스페이스 안에 들어가서 확인했어요.

## 4. kubernetes Service: 파드·노드 안 프로그램이 API 서버를 찾는 주소 Service kubernetes 10.96.0.1 443/TCP EndpointSlice → 192.168.104.1:6443 ## 5. 6443 대신 10.96.0.1:443 으로 붙는 것들 (established, 프로세스별) [k8s-worker1 호스트 네트워크: calico-node] 10.96.0.1:443 ← pid 2513 calico component felix 10.96.0.1:443 ← pid 2517 calico component confd 10.96.0.1:443 ← pid 9100 calico component node node-services [k8s-worker2 의 CoreDNS 파드 네트워크 네임스페이스 안] 10.244.126.30:45532 → 10.96.0.1:443 users:(("coredns",pid=2907,fd=11)) (… 9153 포트 연결 1줄, worker3 CoreDNS 2줄 생략) [calico-kube-controllers 파드 네트워크 네임스페이스 안] 10.244.100.220:60320 → 10.96.0.1:443 users:(("calico",pid=2479,fd=24)) (calico-kube-controllers 가 뜬 노드: k8s-worker3)

그림 5. 숫자는 실제 연결 수다. 모든 화살표가 API 서버로 모이고 etcd와 kubelet 쪽으로 연결을 여는 것은 API 서버뿐이다

Communication between Nodes and the Control Plane 문서는 이 구조를 hub-and-spoke API 패턴이라고 불러요. 노드에서(또는 노드에서 도는 파드에서) 나오는 모든 API 사용은 API 서버에서 끝나고 다른 컨트롤 플레인 구성 요소는 원격 서비스를 내놓도록 설계되지 않았다고 적혀 있어요. 우리 클러스터에서 센 연결 수도 이 문장과 맞았어요.

방향이 반대인 연결도 있었어요. kube-apiserver가 10250 포트로 연 연결 4개예요. 10250은 노드마다 kubelet이 열어 두는 포트이고 마스터와 worker1의 kubelet은 이 포트로 연결을 1개씩 받고 있었어요. 같은 문서는 API 서버가 kubelet에 연결하는 경우로 파드 로그 가져오기, 실행 중인 파드에 attach하기, port-forward 세 가지를 들어요. 이날 이 연결 4개가 각각 무엇에 쓰였는지까지는 확인하지 않았어요. 대신 이 방향이 끊기면 어떻게 되는지는 25편 실험에서 봤어요. worker3의 kubelet을 멈추고 65초 뒤 kubectl logs를 실행하자 이렇게 실패했어요(원자료에도 줄 끝이 잘린 채 남아 있어요).

15:04:34 +65s kubectl logs (API 서버 → kubelet 경로): Error from server: Get "https://192.168.104.5:10250/containerLogs/default/myweb-859c4764d4-5xtpv/nginx?tailLines=1": dial tcp 192.168.104.5:10250: connect: conn

→ API 서버가 worker3의 kubelet(192.168.104.5:10250)에 로그를 달라고 연결하다 실패했다는 뜻이에요. 그 순간에도 파드 IP로 직접 보낸 curl에는 200이 왔어요. kubectl logs는 API 서버 안에서 답이 끝나는 명령이 아니라 API 서버가 다시 kubelet에 물어서 답을 받아 오는 명령이에요. 그래서 노드 방화벽을 정할 때는 컨트롤 플레인에서 노드의 10250으로 가는 연결도 열어 둬야 해요.

📖 용어: 선언형과 명령형 (declarative, imperative)
Kubernetes Object Management 문서는 kubectl로 객체를 다루는 방법을 셋으로 나눠요. 동작을 인자로 주는 명령형 커맨드(kubectl create deployment, kubectl scale), 동작과 파일을 함께 주는 명령형 오브젝트 구성(kubectl create -f), 파일만 주고 만들지 고칠지를 kubectl이 객체마다 판단하게 하는 선언형 오브젝트 구성(kubectl apply -f)이에요.

이 실험을 보고 제가 적은 말이 "모든 리소스들이 API 서버만 보고 있으니까 선언형/명령어 구조가 되는구나"였어요. 조금 다듬으면 이렇게 말할 수 있어요. kubectl 쪽에서 말하는 명령형과 선언형은 원하는 상태를 API 서버에 어떤 방식으로 적느냐의 차이예요. kubectl scale로 숫자 하나를 고치든 kubectl apply로 파일 전체를 맞추든 남는 결과는 API 서버에 기록된 원하는 상태예요. 그 기록을 실제 상태로 만드는 일은 모두 그 기록을 지켜보는 쪽이 해요. Controllers 문서는 쿠버네티스의 컨트롤러를 "클러스터의 상태를 지켜보다가 필요한 곳에 변경을 만들거나 요청하는 제어 루프"라고 하고 각 컨트롤러는 현재 상태를 원하는 상태에 더 가깝게 옮기려 한다고 설명해요. 스케줄러, kubelet, kube-proxy, Calico도 같은 방식으로 일해요. API 서버에 등록된 리소스 종류는 94개였고 그중 22개는 Calico가 CRD로 등록한 것이었어요(20편). Calico도 자기 설정을 같은 API 서버에 적어 두고 그것을 지켜보며 일해요. 노드 안의 CRI 호출, 노드끼리 주고받는 BGP, logs·exec 같은 몇 가지 예외를 빼면 구성 요소끼리 할 일을 주고받는 곳은 API 서버에 적힌 기록 하나예요.

원하는 상태는 API 서버 한 곳에 적히고 모든 구성 요소가 그곳을 지켜보며 자기 몫의 차이를 메우기 때문에 쿠버네티스는 선언형으로 움직여요. 같은 Controllers 문서에는 "컨트롤러는 실패할 수 있고 쿠버네티스는 그것을 견디도록 설계됐다"는 문장도 있어요. 컨트롤러가 잠깐 멈춰도 원하는 상태는 API 서버에 기록으로 남아 있으니 컨트롤러가 돌아오면 그 기록을 보고 다시 맞춰요. 위 실험에서 7/7이 된 것이 그 장면이고 5절의 실험들도 대부분 이 성질을 보여 줘요.

💡 실무에서는: 컨트롤 플레인을 여러 대로 늘리는 원리
이날 처음 구조를 볼 때 제가 "컨트롤 플레인도 여러 대가 될 수 있었구나"라고 적었어요. 허브 구조를 이해하고 나면 그 이유가 보여요. 모든 구성 요소가 API 서버의 주소 하나만 알면 되니 그 주소 뒤에 API 서버를 여러 대 두고 로드밸런서로 요청을 나눌 수 있어요. Cluster Architecture 문서도 kube-apiserver는 인스턴스를 늘려 수평으로 확장하도록 설계됐다고 적어요. 상태는 etcd에만 있으니 etcd는 여러 대로 묶어 서로 합의하게 하고 컨트롤러 매니저와 스케줄러는 리더 선출로 한 번에 한 대만 일하게 해요. 우리 클러스터는 kubeadm 설정에 controlPlaneEndpoint가 없고 etcd 멤버도 k8s-master 하나뿐인 단일 구성이에요. 그래도 컨트롤러 매니저는 --leader-elect=true로 떠 있었고 컨트롤러 매니저와 스케줄러의 Lease holder(지금 리더인 쪽)는 둘 다 lima-k8s-master_로 시작하는 자기 자신이었어요. 컨트롤 플레인이 몇 대, 왜 필요한지는 21편에서 다뤄요.

4. 워커 노드 안은 kubelet부터 커널까지 층으로 쌓여 있다

원래 그림의 워커 노드 상자에는 kube-proxy, Networking(CNI), kubelet, containerd가 나란히 들어 있었고 containerd 아래에 OCI가 따로 붙어 있었어요. 이 상자를 보고 제가 물은 것은 "OCI가 뭐의 약자야?"였어요. 답은 Open Container Initiative예요. OCI가 왜 containerd 아래에 있는지 따라가 보니 워커 노드 안의 상자들은 나란히 놓여 있는 게 아니라 위에서 아래로 층을 이루고 있었어요.

📖 용어: OCI (Open Container Initiative)
컨테이너 형식과 런타임에 관한 업계 표준을 만드는 리눅스 재단 산하 프로젝트예요. OCI 소개 페이지에 따르면 지금 OCI에는 런타임 규격(runtime-spec), 이미지 규격(image-spec), 배포 규격(distribution-spec) 세 가지가 있어요. runc는 OCI 규격에 따라 리눅스에서 컨테이너를 만들고 실행하는 CLI 도구예요. 우리 노드의 runc 1.5.2에 버전을 물어보니 따르는 runtime-spec이 1.3.0이라고 나왔어요.

📖 용어: shim (containerd-shim-runc-v2)
containerd와 컨테이너 사이에 파드마다 하나씩 뜨는 프로세스예요. 우리 마스터의 pstree에서 컨테이너 프로세스(pause와 본 프로세스)의 부모는 shim이었고 shim의 부모는 containerd가 아니라 systemd(PID 1)였어요.

이 부모 관계 덕분에 26편에서 worker1의 containerd와 kubelet을 차례로 재시작해도 nginx의 pid(10360, 10492)가 그대로였고 curl도 계속 200이었어요. kubelet이 하는 일과 컨트롤러가 하는 일의 경계도 이 층에서 보였어요. worker1에서 nginx 프로세스를 kill -9로 죽이자 약 1초 만에 같은 파드(같은 uid, 같은 IP) 안에서 컨테이너가 다시 떴고 restarts가 1로 올랐어요. 이렇게 컨테이너를 다시 띄우는 쪽은 kubelet이에요. 반면 파드 자체를 지웠을 때 새 이름과 새 IP로 파드를 다시 만드는 쪽은 컨트롤러 매니저 안의 ReplicaSet 컨트롤러예요. 그래서 3절 실험에서 컨트롤러 매니저가 멈춘 동안에는 지운 파드가 다시 생기지 않았어요(26편).

오른쪽 층의 kube-proxy는 트래픽이 지나가는 경로 위에 있지 않아요. worker1의 kube-proxy가 맺은 TCP 연결은 API 서버 192.168.104.1:6443 하나뿐이었어요. kube-proxy는 규칙만 써 두고 실제 패킷의 목적지는 커널의 iptables 규칙이 DNAT으로 바꿔요. ClusterIP에 ping은 안 되는데 curl은 되는 이유도 여기에 있어요(28편).

📖 용어: Felix와 BIRD
둘 다 calico-node 파드 안에서 도는 프로세스예요. Felix는 노드의 라우팅 표와 iptables에 경로와 NetworkPolicy 규칙을 써넣는 에이전트이고 BIRD는 다른 노드와 BGP 세션을 맺어 "이 /26 블록은 이 노드로 보내라"는 경로 정보를 주고받는 BGP 데몬이에요. calico-node의 readiness 검사에는 --felix-ready와 --bird-ready가 함께 들어 있어요.

원래 그림에는 Calico 옆에 BGP와 BIRD만 적혀 있어서 노드 사이의 경로를 BIRD가 커널에 넣는다고 읽기 쉬워요. 우리가 쓰는 Calico v3.33.0에서는 그렇지 않았어요. worker1의 BIRD 설정을 보니 커널로 경로를 내보내는 필터에 if (net ~ 10.244.0.0/16) then { reject; } # Cluster routes are handled by Felix. 한 줄이 있었어요. 클러스터 경로는 BIRD가 커널에 넣지 않고 Felix에 맡긴다는 설정이에요. FelixConfiguration의 programClusterRoutes도 EnabledIPIPOnly였어요. Calico 3.33 릴리스 노트에도 관련 항목이 둘 있어요. 하나는 IPIP IP 풀의 클러스터 경로를 이제 기본으로 BIRD가 아니라 Felix가 넣는다는 항목이고 다른 하나는 BIRD가 IPIP 클러스터 경로를 넣는 방식은 폐기 예정이며 v3.35에서 없앨 계획이라는 항목이에요. 예전 버전에서 BIRD가 넣던 경로를 3.33부터는 Felix가 넣는다는 뜻이에요. 그래서 30편에서 BIRD를 멈춰도 worker1의 경로는 그대로 남았어요. 그림 구석의 calicoctl은 마스터에 v3.33.0을 설치해서 IPPool과 IPAM 블록을 둘러볼 때 썼어요(30·31·34편).

CoreDNS는 원래 그림에 따로 그려져 있지 않지만 앞에서 본 ⑥에서 Service 이름을 IP로 바꾸는 일을 해요. kubelet 설정의 clusterDNS가 10.96.0.10이라서 파드의 resolv.conf도 이 주소를 DNS 서버로 가리키고 10.96.0.10으로 간 질의는 다시 kube-proxy가 만든 규칙을 거쳐 CoreDNS 파드 2개 중 하나로 가요(29편). kubelet, containerd, shim, runc는 위에서 아래로 일을 넘기는 층이고 컨테이너를 격리하고 패킷을 전달하는 실제 일은 맨 아래 커널이 해요.

5. 화살표 하나가 끊기면 변경은 멈추지만 트래픽은 대체로 계속된다

그림을 다 읽고 나서 마지막으로 궁금했던 것은 "이 화살표 하나가 끊기면 무엇이 안 될까"였어요. 그날 직접 끊어 본 결과를 표 하나로 모았어요. 구성 요소를 멈춘 실험은 대부분 3분 안에 원래대로 돌려놓았고 축출까지 보려고 kubelet을 약 29분 동안 멈춘 실험이 하나 있어요.

그림 7. 멈춰 본 것 대부분은 제어 경로 위에 있었고 데이터 경로를 직접 건드린 실험에서만 통신이 바로 끊겼다

표를 보면 공통점이 하나 보여요. API 서버는 원하는 상태를 보관하는 곳이고 스케줄러, 컨트롤러 매니저, kubelet, kube-proxy, BIRD는 그 상태를 지켜보며 차이를 메우는 쪽이에요. 이들이 멈추면 새로 생기는 차이를 메울 쪽이 없으니 변경이 멈춰요. 하지만 이미 만들어 둔 컨테이너, iptables 규칙, 커널 경로는 그 자리에 그대로 남아요. 그래서 구성 요소만 멈추고 파드는 그대로 둔 실험에서 보낸 curl은 모두 200이었어요. 구성 요소 대부분은 데이터 경로 위에 있지 않고 옆에서 그 경로를 고쳐 쓰는 프로그램이라서 잠깐 멈춰도 트래픽은 대체로 계속되고 변경만 멈춰요. 3절에서 인용한 "컨트롤러는 실패할 수 있고 쿠버네티스는 그것을 견디도록 설계됐다"는 문장을 실험으로 확인한 셈이에요.

⚠️ 주의: "잠깐 멈춰도 괜찮다"를 일반화하면 안 돼요
• kubelet이 멈추면 데이터 경로도 바뀌어요. 컨테이너는 멀쩡히 200으로 응답하는데도 65초 뒤에 보니 EndpointSlice에서 serving=False였어요. EndpointSlice 문서에 따르면 serving은 그 엔드포인트를 Service 트래픽 대상으로 써도 되는지를 나타내요. 그대로 두면 taint가 붙은 지 300초 뒤에 파드가 쫓겨나요. 25편에서는 실제로 08:23:26Z에 붙은 taint가 08:28:26Z의 축출로 이어졌어요
• kube-proxy가 없는 동안 파드가 바뀌면 그 노드의 규칙은 옛 상태로 남아요. kube-proxy가 살아 있을 때는 파드 수를 5에서 3으로 줄이자 1.3초 만에 규칙이 바뀌었어요. 그런데 28편에서 worker1의 kube-proxy만 없앤 채 myweb을 5개에서 2개로 줄이자 worker1의 규칙은 지워진 파드까지 다섯 개를 그대로 가리켰고 worker1에서 보낸 curl 30번 중 22번이 실패했어요. 같은 시각 마스터에서 보낸 curl은 30번 모두 200이었어요
• 데이터 경로를 직접 건드리면 바로 끊겨요. worker1에서 worker3 블록으로 가는 경로 한 줄을 지우자 바로 다음 curl이 000으로 실패했고 37초 안에 Felix가 경로를 다시 넣은 뒤에야 200으로 돌아왔어요(30편)
• 컨트롤러가 다른 노드로 옮겨 다시 떠도 곧바로 일하지 않을 수 있어요. 25편 실험에서는 worker3에 있던 calico-kube-controllers도 함께 축출돼 마스터에서 새로 떴어요. 그런데 worker3의 calico-node가 unavailable인 동안에는 IPAM 누수 정리를 약 23분 35초(08:28:27~08:52:02 UTC) 동안 시작하지 못했어요. 그사이 강제로 지운 옛 파드 두 개의 IP는 calicoctl ipam check에 "할당됐지만 쓰이지 않는 IP 2개"로 남았고 worker3의 kubelet이 돌아와 CNI DEL을 부른 뒤에야 반납됐어요(34편)
✍️ 오늘의 요약
쿠버네티스 아키텍처 그림의 화살표는 대부분 API 서버로 모여요. 그래서 쿠버네티스는 선언형으로 움직여요.

요청 하나는 TLS, 인증, 인가, 어드미션을 지나 etcd에 기록돼요. 자격 없는 요청이 401이 아니라 403을 받은 것은 익명 사용자로 인증된 뒤 인가에서 막혔기 때문이에요. 어드미션은 파드에 ServiceAccount와 300초 toleration 같은 칸을 채워 넣었어요. 실제 TCP 연결을 세어 보니 etcd에 붙은 프로세스는 API 서버 하나였고 나머지 구성 요소는 모두 API 서버를 향했어요. 워커 노드 안은 kubelet, containerd, shim, runc를 거쳐 커널에 닿는 층과 kube-proxy, Calico가 규칙과 경로를 써넣는 층으로 나뉘어요. 이 구조 덕분에 구성 요소 하나가 멈춰도 변경만 멈추고 이미 떠 있는 컨테이너와 이미 깔린 규칙을 지나는 트래픽은 대체로 계속됐어요. 아키텍처 그림은 상자보다 화살표를 읽어야 하는 그림이고 그 화살표는 거의 모두 API 서버로 모여요.
