파드 YAML에 imagePullPolicyy: Always라고 y를 하나 더 쳤어요. 기본 설정으로 kubectl apply --dry-run=server를 보내자 API 서버가 strict decoding error: unknown field "spec.containers[0].imagePullPolicyy"로 거절했어요. 그런데 같은 YAML에 --validate=false를 붙이자 결과는 pod/typo created (server dry run)였어요. 오타가 난 필드는 에러 없이 버려지고 파드는 만들어질 수 있는 상태였어요.

조용히 사라진 필드는 하나 더 있었어요. readinessProbe의 httpGet에 protocol: HTTP2를 넣고 server dry-run 결과를 보니 저장될 httpGet은 {"path":"/","port":80,"scheme":"HTTP"}였어요. kubectl explain에는 분명히 protocol 필드와 enum: HTTP1, HTTP2가 보였는데도 결과에서는 빠졌고 경고도 없었어요. 마지막으로 같은 오타 YAML을 --dry-run=client로 보내자 pod/typo created (dry run)가 나왔어요. 잘못된 restartPolicy 값도 client에서는 그대로 통과했어요.

쿠버네티스는 YAML을 받으면 apiVersion과 kind로 요청 주소를 정하고, 필드 이름과 값을 검사하고, 꺼진 기능의 필드를 지운 뒤 저장해요. 이 글은 그 과정에서 실수가 어디서 걸리고 어디서 그냥 지나가는지를 v1.37.2 실습 클러스터(Lima VM 4대, containerd 2.4.1, Calico v3.33.0)에서 확인한 기록이에요. 58편의 관계도에서 상자 하나하나가 실제로 어떤 YAML이 되는지를 따라가는 글이기도 해요.

· kind와 apiVersion은 왜 중요할까? api-versions와 api-resources는 무엇이 다를까?
· kubectl explain은 어떻게 쓸까?
· dry-run=client와 dry-run=server는 무엇을 잡고 무엇을 놓칠까?
· 스키마에 보이는 필드는 다 쓸 수 있을까?
· 결국 spec을 잘 쓰면 될까? 리스트의 순서는 상관없을까?
· strace로 kubectl의 API 호출을 볼 수 있을까?
· 명령형과 선언형 중 무엇으로 만들까?

1. apiVersion은 요청 주소가 되고 kind는 그 주소 아래의 종류다

매니페스트의 최상위에는 네 칸이 있어요. apiVersion과 kind는 이 오브젝트가 어느 API의 무슨 종류인지 정하고, metadata는 이름과 라벨을, spec은 원하는 상태를 담아요. 클러스터에서 다시 읽으면 다섯째 칸 status가 붙어요. status는 5절에서 따로 봐요.

📖 용어: API 그룹과 버전
apiVersion의 apps/v1에서 apps가 그룹, v1이 버전이에요. Pod, Service, ConfigMap처럼 오래된 종류는 이름 없는 core 그룹에 있어서 v1만 적어요. 같은 종류가 여러 버전으로 서빙될 수 있고 버전 이름의 alpha와 beta는 안정성 단계를 뜻해요.

kind와 apiVersion은 왜 중요할까요? kubectl은 이 두 칸으로 요청을 보낼 주소를 만들어요. -v=6으로 실제 요청을 찍어 보면 core 그룹과 다른 그룹의 주소가 다르게 생겼어요(labs/devops/k8s-study/out/58-kind-apiversion.txt).

## 요청 경로: core 그룹은 /api/v1, 나머지는 /apis/<그룹>/<버전> /api/v1/namespaces/ch05/pods?limit=500 /apis/apps/v1/namespaces/ch05/deployments?limit=500

→ 파드는 /api/v1 아래에, Deployment는 /apis/apps/v1 아래에 있어요. apiVersion을 틀리면 kubectl은 엉뚱한 주소를 만들거나 주소를 찾지 못해요. 옛 매니페스트의 apiVersion: extensions/v1beta1로 Deployment를 보내면 no matches for kind "Deployment" in version "extensions/v1beta1"로 보내기 전에 멈췄어요. 그 버전을 이 클러스터가 더는 서빙하지 않기 때문이에요(58편).

그림 1. apiVersion을 바꾸면 YAML 한 줄이 아니라 요청 주소가 바뀌어요.

api-versions는 그룹/버전 전부, api-resources는 종류마다 하나

kubectl api-versions와 api-resources는 무엇이 다를까요? 같은 클러스터에서 둘을 나란히 보면 autoscaling에서 차이가 드러나요.

## kubectl api-resources (일부) NAME SHORTNAMES APIVERSION NAMESPACED KIND horizontalpodautoscalers hpa autoscaling/v2 true HorizontalPodAutoscaler ## kubectl api-versions (일부) autoscaling/v1 autoscaling/v2

→ api-versions는 API 서버가 서빙하는 그룹/버전 쌍을 전부 나열해요. autoscaling은 v1과 v2가 둘 다 있어요. api-resources는 종류마다 대표 버전 하나만 보여 주고 HPA는 autoscaling/v2로 나와요. 그래서 HPA를 autoscaling/v1로 써서 보내도 받아 줘요. 같은 HPA를 두 버전으로 동시에 읽을 수 있는 원리는 72편에서 다뤄요.

버전 이름의 alpha와 beta는 기본으로 켜지느냐와 이어져요. 내장 alpha API 버전은 기본으로 꺼져 있고 API 서버의 --runtime-config로 켜야 해요. beta도 1.24부터 새로 나오는 것은 기본으로 꺼져요(KEP-3136). 그래서 v1.37.2를 기본 설정으로 띄운 우리 클러스터에서 서빙 중인 alpha·beta 버전을 찾자 하나만 나왔어요(labs/devops/k8s-study/out/59-alpha-beta-served.txt).

# 07 지금 서빙 중인 alpha·beta API 버전 policy.networking.k8s.io/v1alpha2 ← 내장 API 가 아니라 CRD(clusternetworkpolicies, Calico 가 설치) # kube-apiserver 의 --runtime-config / --feature-gates (지정 없음 → 기본값)

→ 유일한 v1alpha2는 Calico 매니페스트가 함께 설치한 CRD였고 내장 API의 alpha·beta 버전은 0개였어요. 옛 글의 예제에서 내장 종류의 v1beta1을 그대로 가져오면 우리 클러스터에서는 앞의 extensions/v1beta1처럼 거절될 수 있다는 뜻이에요. beta 규칙이 생긴 과정은 73편에서 봐요.

2. 필드 이름과 위치는 kubectl explain으로 찾는다

kubectl explain은 어떻게 쓸까요? 이 명령은 지금 접속한 API 서버가 내려 준 스키마를 읽어서 필드를 보여 줘요. 인터넷의 문서는 다른 버전일 수 있지만 explain은 내 클러스터 버전의 필드를 보여 준다는 점이 가장 큰 장점이에요. 실습에서 쓴 방법은 세 가지예요(labs/devops/k8s-study/out/59-explain-tips.txt).

📖 용어: OpenAPI 스키마
API 서버가 종류마다 필드 이름, 타입, 필수 여부, 허용 값을 기계가 읽을 수 있게 내보내는 명세예요. kubectl explain과 서버 쪽 필드 검증이 이 명세를 써요. CRD도 스키마를 적어 두면 같은 방식으로 explain과 검증이 돼요.
## 점으로 파고들기: pod.spec.containers.livenessProbe.httpGet host <string> httpHeaders <[]HTTPHeader> path <string> port <IntOrString> -required- protocol <string> enum: HTTP1, HTTP2 scheme <string> enum: HTTP, HTTPS ## CRD 도 스키마가 있으면 explain 된다 (Calico IPPool) assignmentMode <string> enum: Automatic, Manual cidr <string> -required-

→ 첫째, 점으로 경로를 이어 원하는 깊이까지 내려가요. -required-는 빠뜨리면 거절되는 필드이고 enum은 허용되는 값 목록이에요. httpGet의 port가 필수이고 scheme에는 HTTP와 HTTPS만 들어간다는 것을 YAML을 쓰기 전에 알 수 있어요. 둘째, Calico의 IPPool처럼 CRD로 들어온 종류도 같은 방식으로 볼 수 있어요. cidr가 필수라는 것도 explain이 알려 줬어요.

셋째, 필드가 어디에 있는지 모를 때는 --recursive로 전체 트리를 펼치고 줄 번호와 함께 찾아요. kubectl explain pod.spec --recursive | grep -n Probe로 probe를 찾자 livenessProbe, readinessProbe, startupProbe가 세 벌 나왔어요. 줄 번호 195~304, 440~549, 691~800이에요. pod.spec의 필드는 알파벳순으로 나오므로 차례대로 containers, ephemeralContainers, initContainers 아래에 있는 거예요. 디버깅용 ephemeralContainers에도 probe 필드가 있지만 그 필드의 설명 첫 줄은 이랬어요(labs/devops/k8s-study/out/59-explain-and-verbose.txt).

Probes are not allowed for ephemeral containers.

→ 타입을 컨테이너와 같이 쓰다 보니 필드는 있지만 쓸 수 없다는 뜻이에요. explain은 필드 목록만이 아니라 이런 제약도 DESCRIPTION에 적어 줘요.

💡 explain을 이렇게 써요
• 위치를 모를 때: kubectl explain pod.spec --recursive | grep -n 필드이름으로 줄 번호를 보고 들여쓰기로 부모를 찾아요.
• 위치를 알 때: kubectl explain deploy.spec.strategy.rollingUpdate처럼 점으로 내려가 -required-와 enum을 확인해요.
• 짧은 이름도 돼요: deploy, svc, hpa처럼 api-resources의 SHORTNAMES를 쓸 수 있어요.
• DESCRIPTION을 끝까지 읽어요. 기능 게이트(4절)가 필요한 필드나 쓸 수 없는 조합이 여기에 적혀 있어요.

3. dry-run=server는 저장 직전까지 검사하고 --validate=false는 오타를 버린다

도입의 오타 실험은 dry-run=server로만 했어요. 같은 YAML을 client 쪽 dry-run과 비교하려고 blog-59 네임스페이스에서 다시 돌렸어요. 필드 이름 오타와 값 오류를 각각 네 가지 옵션 조합으로 보냈어요(labs/devops/k8s-study/out/59-client-vs-server.sh, 원래 실험은 labs/devops/k8s-study/out/59-spec-typo.txt).

📖 용어: dry-run=client와 dry-run=server
--dry-run=client는 kubectl이 만들 오브젝트를 화면에만 보여 주고 서버에 보내지 않아요. --dry-run=server는 요청을 실제로 API 서버에 보내서 검증, 기본값 채우기, 어드미션까지 거친 뒤 etcd에 저장하는 단계만 건너뛰어요. 그래서 응답에 저장될 오브젝트의 모습이 돌아와요.

그림 2. client에서는 둘 다 통과했고 server에서는 둘 다 걸렸어요. --validate=false는 오타 검사만 껐어요.

보낸 방식필드 이름 오타(imagePullPolicyy)값 오류(restartPolicy: Sometimes)
--dry-run=clientcreated (dry run)created (dry run)
--dry-run=client --validate=falsecreated (dry run)created (dry run)
--dry-run=serverBadRequest: unknown fieldinvalid: Unsupported value
--dry-run=server --validate=falsecreated (server dry run)invalid: Unsupported value

client dry-run은 두 오류를 모두 놓쳤어요. kubectl의 기본 --validate는 strict인데도 그랬어요. kubectl 1.37.2의 도움말은 strict를 "서버에서 필드 검증을 하고, 서버가 지원하지 않을 때만 덜 믿을 만한 client 검증으로 대신한다"고 설명해요. 서버로 보내지 않는 client dry-run에서는 그 서버 검증이 일어나지 않았어요. 같은 도움말은 false를 이렇게 설명해요.

"false" or "ignore" will not perform any schema validation, silently dropping any unknown or duplicate fields.

→ false는 스키마 검증을 하지 않고 모르는 필드나 중복 필드를 조용히 버린다는 뜻이에요. 실제로 --dry-run=server --validate=false로 받은 오브젝트의 컨테이너에는 imagePullPolicyy가 없었고 대신 기본값 "imagePullPolicy":"IfNotPresent"가 들어 있었어요. 제가 원한 Always는 오타와 함께 사라지고 기본값으로 만들어지는 거예요.

📖 용어: 서버 쪽 필드 검증 (strict decoding)
API 서버가 요청 본문을 오브젝트로 바꿀 때 스키마에 없는 필드나 같은 필드가 두 번 나오면 거절하는 검사예요. 에러 문구는 strict decoding error: unknown field이고 400 BadRequest로 돌아와요. kubectl의 --validate 값이 이 검사를 켜고 끄는 요청 옵션이 돼요.

값 오류는 성격이 달랐어요. --validate=false여도 spec.restartPolicy: Unsupported value: "Sometimes": supported values: "Always", "OnFailure", "Never"로 거절됐어요. 필드 이름이 맞으면 디코딩은 통과하고 그다음에 종류마다 정해진 값 검증이 돌아요. 이 검증은 --validate로 끌 수 없었어요. 36편에서 컨테이너 이름 Bad_Name이 422 Unprocessable Entity로 거절된 것과 같은 종류의 검사예요.

그림 3. 필드 이름은 디코딩에서, 값은 검증에서 걸리고, 꺼진 기능의 필드는 그 사이에서 에러 없이 지워져요.

⚠️ --validate=false로 에러를 없애지 않아요
unknown field 에러가 귀찮아서 --validate=false를 붙이면 에러가 사라지는 대신 오타 난 설정이 사라져요. 이번처럼 imagePullPolicy 오타는 기본값으로 대체되고, 프로브나 리소스 제한 오타라면 그 설정 없이 파드가 떠요. apply 전 확인은 --dry-run=server로 하고, client dry-run은 YAML 뼈대를 뽑는 용도로만 써요.

4. 스키마에 있는 필드도 기능 게이트가 꺼져 있으면 조용히 사라진다

도입의 두 번째 장면으로 돌아가 볼게요. 2절에서 explain은 httpGet 아래에 protocol 필드와 enum: HTTP1, HTTP2를 보여 줬어요. 그래서 readinessProbe에 protocol: HTTP2를 넣고 server dry-run으로 저장될 httpGet만 뽑았어요(labs/devops/k8s-study/out/59-h2c-probe-alpha.sh).

그림 4. 보낸 protocol: HTTP2가 저장될 오브젝트에서 빠졌고 에러는 없었어요.

API 서버의 --feature-gates는 하나도 지정돼 있지 않았고 저장될 httpGet에는 path, port, scheme만 남았어요. 이유는 v1.37.2 소스에 있어요(labs/devops/k8s-study/out/59-k8s-v1.37.2-h2c-probe-excerpts.txt).

## staging/src/k8s.io/api/core/v1/types.go (HTTPGetAction.Protocol) // +featureGate=H2CContainerProbe Protocol *HTTPProtocol `json:"protocol,omitempty" ...` ## pkg/features/kube_features.go (H2CContainerProbe) // kep: https://kep.k8s.io/5999 H2CContainerProbe: { {Version: version.MustParse("1.37"), Default: false, PreRelease: featuregate.Alpha}, },

→ protocol 필드는 H2CContainerProbe라는 기능 게이트에 묶여 있고 이 게이트는 1.37에 alpha로 들어와 기본값이 false예요. CHANGELOG-1.37은 이 필드를 HTTP/2 cleartext(H2C)로 프로브를 보내기 위해 추가했다고 적었어요(PR #139429, KEP-5999). 게이트가 꺼진 API 서버는 새로 만드는 오브젝트에서 이 필드를 지우고 나머지를 저장해요. 오류로 알려 주지 않아요.

📖 용어: 기능 게이트 (feature gate)
구성 요소마다 새 기능을 켜고 끄는 스위치예요. alpha 기능은 기본으로 꺼져 있어서 --feature-gates=이름=true로 켜야 동작해요. 필드가 스키마와 explain에 보여도 게이트가 꺼져 있으면 그 필드에 넣은 값은 저장되지 않을 수 있어요.

스키마에 있다는 것과 켜져 있다는 것은 다른 말이에요. v1.37.2의 explain으로 생명주기 관련 필드를 확인했을 때 initContainers.restartPolicy, containers.restartPolicyRules, lifecycle.preStop.sleep, lifecycle.stopSignal, status.observedGeneration이 모두 "있음"이었어요(labs/devops/k8s-study/out/59-fields-1.37.txt). 그중 observedGeneration의 설명에는 The PodObservedGenerationTracking feature gate must be enabled to use this field.라고 게이트가 직접 적혀 있었어요. stopSignal도 우리 클러스터에서 같은 식으로 조용히 지워지는데 그 이야기는 67편에서 해요.

⚠️ 새 필드는 보낸 것과 저장된 것을 비교해요
최근 버전에 들어온 필드를 쓸 때는 kubectl apply --dry-run=server -o yaml의 결과에서 그 필드가 남았는지 확인해요. 빠졌다면 기능 게이트가 꺼진 거예요. 이미 만든 오브젝트라면 kubectl get -o yaml로 같은 비교를 해요. 에러가 없다는 것만으로 설정이 들어갔다고 판단하면 안 돼요.

5. 리스트는 순서가 의미 있고 status는 사람이 쓰는 칸이 아니다

결국 spec을 잘 쓰면 될까요? 잘 쓰는 것만큼 확인하는 습관이 필요했어요. 1~4절에서 본 실수는 모두 YAML만 봐서는 드러나지 않았고 explain, dry-run=server, 저장된 결과를 볼 때 드러났어요. 확인할 거리가 하나 더 있어요. YAML의 맵은 키 순서가 상관없지만 리스트는 순서가 의미를 가져요. blog-59에서 init 컨테이너 두 개와 env 세 개를 일부러 순서를 섞어 적은 파드를 띄웠어요(labs/devops/k8s-study/out/59-list-order.sh).

initContainers: - name: init-a # 먼저 적었고 2초 걸린다 command: ["sh", "-c", "sleep 2; echo init-a >> /work/order"] - name: init-b # 나중에 적었고 바로 끝난다 command: ["sh", "-c", "echo init-b >> /work/order"] containers: - name: app env: - {name: BEFORE, value: "hello-$(NAME)"} # NAME 보다 앞에서 참조 - {name: NAME, value: "k8s"} - {name: AFTER, value: "hello-$(NAME)"} # NAME 보다 뒤에서 참조 ## app 로그 order: init-a init-b BEFORE=hello-$(NAME) AFTER=hello-k8s ## initContainerStatuses (시작 · 끝) init-a started=2026-11-15T12:42:48Z finished=2026-11-15T12:42:50Z exit=0 init-b started=2026-11-15T12:42:51Z finished=2026-11-15T12:42:51Z exit=0

→ 바로 끝나는 init-b가 2초 걸리는 init-a보다 먼저 쓰지 못했어요. init-a가 끝난 다음 초에 init-b가 시작했어요. initContainers는 적힌 순서대로 하나씩 실행돼요. env에서는 NAME보다 아래에 있는 AFTER만 hello-k8s로 바뀌었고 위에 있는 BEFORE는 $(NAME) 글자가 그대로 남았어요. $(VAR) 참조는 리스트에서 앞에 정의된 변수만 풀려요(공식 문서).

같은 파드를 API에서 다시 읽으면 env의 세 값은 보낸 문자열 그대로였어요. API 서버는 이 참조를 풀지 않고 저장만 해요. 값이 바뀐 것은 컨테이너를 만들 때였어요. 그래서 dry-run=server는 이 실수를 잡아 주지 않아요. 순서는 YAML을 쓰는 사람이 챙겨야 해요.

그림 5. 맵은 순서가 상관없지만 initContainers와 env 같은 리스트는 적은 순서대로 동작했어요.

status는 컨트롤러와 kubelet이 쓰는 칸이다

spec은 사람이 원하는 상태를 적는 칸이고 status는 컨트롤러와 kubelet이 관찰한 상태를 적는 칸이에요. 58편에서 managedFields를 보면 파드의 status는 kubelet이, Deployment와 ReplicaSet의 status는 kube-controller-manager가 썼어요. 사람이 YAML에 status를 적으면 어떻게 될까요? status: {phase: Running, message: written-by-me}를 붙인 파드를 server dry-run으로 보내자 저장될 status는 {"phase":"Pending","qosClass":"BestEffort"}였어요(labs/devops/k8s-study/out/59-status-on-create.txt). 보낸 phase와 message는 버려졌고 API 서버가 정한 값만 남았어요. kubectl이 뽑아 주는 뼈대 YAML의 status: {}는 지워도 되는 칸이에요.

6. API 요청은 kubectl -v로 보고 빨리 만들 때는 명령형으로 뼈대를 뽑는다

strace에는 시스템 콜이, kubectl -v에는 HTTP 요청이 보인다

strace로 kubectl의 API 호출을 볼 수 있을까요? 마스터 노드에서 strace -f kubectl get pod -n ch05를 돌려 봤어요(labs/devops/k8s-study/out/59-strace-vs-verbose.txt). 명령 하나에 시스템 콜이 1,788번 나왔고 많은 순서로 fcntl 326번, read 318번, futex 269번, rt_sigaction 114번이었어요. API 서버의 6443 포트로 가는 connect는 보였지만 그 뒤에 오가는 바이트는 TLS로 암호화돼 있어서 평문 GET /api가 나오는 줄은 0줄이었어요. strace가 보여 주는 것은 커널에 들어간 호출이고 HTTP 요청의 내용은 아니에요.

HTTP 요청은 kubectl이 스스로 찍어 줘요. 같은 명령에 -v=6을 붙이면 verb="GET" url=".../api/v1/namespaces/ch05/pods?limit=500" status="200 OK"처럼 요청마다 메서드와 주소, 응답 코드가 나와요. -v=8은 요청 헤더와 응답 본문 일부를, -v=9는 같은 요청을 curl -v -XGET -H "Accept: …" -H "User-Agent: …" 'https://<API 서버>/api/v1/namespaces/default' 모양으로 보여 줘요(labs/devops/k8s-study/out/59-explain-and-verbose.txt, 헤더 값은 줄였어요).

Accept: application/json;as=Table;v=v1;g=meta.k8s.io,application/json;as=Table;v=v1beta1;g=meta.k8s.io,application/json User-Agent: kubectl/v1.37.2 (linux/arm64) kubernetes/c50e539 "Response Body" body="{\"kind\":\"Table\",\"apiVersion\":\"meta.k8s.io/v1\", ...

→ -v=8에서 하나 더 알 수 있었어요. kubectl get은 파드 오브젝트 자체가 아니라 as=Table 형식을 달라고 요청하고 서버는 "kind":"Table"로 답해요. kubectl get 화면의 NAME, READY, STATUS 같은 열은 kubectl이 아니라 서버가 정해서 보내 준 거예요.

📖 용어: Table 응답
API 서버가 오브젝트 목록을 사람이 읽을 열과 행으로 바꿔 주는 응답 형식(meta.k8s.io/v1 Table)이에요. 클라이언트가 Accept 헤더에 as=Table을 넣으면 이 형식으로 받아요. CRD도 정의에 출력할 열(additionalPrinterColumns)을 적어 두면 kubectl get에 그 열이 나와요.

명령형으로 뼈대를 뽑고 YAML을 고쳐서 apply한다

명령형과 선언형 중 무엇으로 만들까요? 20편과 58편에서 봤듯이 API 서버 쪽에서는 둘 다 원하는 상태를 적는 요청이에요. 차이는 그 상태를 파일로 남기느냐에 있어요. 운영에서는 파일을 Git에 두고 apply하는 쪽이 변경 기록을 남기기 좋아요. 다만 CKA 같은 시험처럼 빨리 만들어야 할 때는 명령형으로 뼈대를 뽑아 파일로 고치는 방법이 빨라요. v1.37.2 kubectl로 뽑은 Deployment 뼈대는 이랬어요(labs/devops/k8s-study/out/59-imperative-skeleton.txt).

$ kubectl create deployment web --image=nginx:1.27-alpine --replicas=2 --dry-run=client -o yaml apiVersion: apps/v1 kind: Deployment metadata: labels: app: web name: web spec: replicas: 2 selector: matchLabels: app: web strategy: {} template: metadata: labels: app: web spec: containers: - image: nginx:1.27-alpine name: nginx resources: {} status: {}

→ apiVersion, 셀렉터와 템플릿 라벨의 짝, 컨테이너 목록 같은 틀린 데 없이 써야 하는 부분을 kubectl이 채워 줘요. 컨테이너 이름이 이미지 이름에서 온 nginx라는 점과 빈 strategy, resources, status 칸은 고칠 거리예요. 파드는 kubectl run tmp --image=busybox:1.37 --restart=Never --dry-run=client -o yaml -- sleep 3600으로 뽑을 수 있어요.

명령이 없는 종류도 있어요. kubectl create의 하위 명령은 clusterrole, clusterrolebinding, configmap, cronjob, deployment, ingress, job, namespace, poddisruptionbudget, priorityclass, quota, role, rolebinding, secret, service, serviceaccount, token이었고 daemonset, statefulset, persistentvolumeclaim, networkpolicy는 없었어요. 프로브, 멀티 컨테이너, 볼륨 마운트도 명령 옵션으로는 넣을 수 없어요. 이런 것은 비슷한 종류의 뼈대를 뽑아 고치거나 explain을 보며 직접 써요. HPA를 만드는 kubectl autoscale은 kubectl 1.37.2에서 --cpu-percent가 deprecated로 나와요. 쓰면 Flag --cpu-percent has been deprecated, Use --cpu with percentage or resource quantity format 경고가 나오고, --cpu=50%로 바꿔도 같은 autoscaling/v2 HPA(averageUtilization 50)가 나왔어요.

💡 빨리 만들 때의 순서
• 뼈대: kubectl create deployment ... --dry-run=client -o yaml > web.yaml
• 고치기: 명령이 없는 필드(프로브, 볼륨, 두 번째 컨테이너)를 explain으로 위치를 찾아 넣어요.
• 검사: kubectl apply --dry-run=server -f web.yaml로 오타와 값 오류를 잡고, 넣은 필드가 결과에 남았는지 봐요.
• 적용과 확인: kubectl apply -f web.yaml 뒤에 status와 이벤트로 원하는 상태가 됐는지 봐요.
client dry-run은 뼈대를 뽑을 때만 써요. 3절에서 본 것처럼 client에서는 오타도 잘못된 값도 걸리지 않았어요.

📝 정리

apiVersion과 kind는 kubectl이 요청을 보낼 주소를 정해요. core 그룹은 /api/v1, 나머지는 /apis/그룹/버전이고, 서빙하지 않는 버전은 보내기 전에 거절돼요. v1.37.2 기본 설정에서 서빙 중인 내장 alpha·beta 버전은 0개였어요.

apply 전 검사는 explain으로 필드를 찾고 dry-run=server로 보내는 순서가 맞았어요. client dry-run은 오타 필드와 잘못된 값을 모두 통과시켰고, --validate=false는 오타 필드를 에러 없이 버렸어요. 기능 게이트가 꺼진 httpGet.protocol도 스키마에는 있었지만 저장될 오브젝트에서 조용히 빠졌어요.

initContainers와 env 같은 리스트는 적은 순서대로 동작하고 status는 사람이 써도 버려져요. 에러가 없다는 것은 저장될 수 있다는 뜻일 뿐이므로 보낸 것과 저장된 것을 비교해야 해요.
