Portainer에 admin으로 처음 로그인하자 대시보드에 숫자 일곱 개가 떴어요. Namespaces 8, Applications 13, Services 9, Ingresses 0, ConfigMaps 18, Secrets 3, Volume 1이었습니다. 16편에서 설치한 Portainer CE 2.45.3 LTS의 첫 화면이에요. 이 화면을 보다가 "결국에 관측성부터 확보하고 개발하자는 거네?"라는 말이 나왔어요. 강의 챕터가 Prometheus와 Grafana(11~12편)에서 시작해 Kubeshark(13~15편)를 거쳐 Portainer로 이어졌으니 그렇게 읽혔어요.

그런데 Portainer 문서의 첫 화면에는 Portainer가 컨테이너 관리의 복잡함을 쓰기 쉬운 UI 뒤로 숨겨 준다고 적혀 있어요. 대시보드의 숫자도 시간에 따라 쌓인 수치가 아니라 지금 클러스터에 있는 오브젝트의 개수였어요. Prometheus는 노드 수치를 시간 순서로 쌓고 Kubeshark는 파드 사이를 오가는 요청을 잡아요. Portainer는 지금 무엇이 어떤 상태로 있는지 보여 주고 그 자리에서 바꾸게 해 주는 관리 도구에 가까워요.

그래서 이번에는 Portainer를 관리 도구로 써 봤어요. kubectl로 앱을 넣고 빼면서 일부러 고장도 내고 Portainer 화면이 어떻게 바뀌는지 찍었어요. 그다음 Portainer 화면에서 메모리 한도를 건 네임스페이스를 만들고 앱 두 개를 배포했어요. 질문은 "Portainer 화면의 어디를 보면 배포가 멈춘 것과 자원 한도에 막힌 것을 알 수 있을까"예요.

이 글에서 다룰 것
· 대시보드의 숫자는 무엇을 센 것이고 앱을 넣고 빼면 어떻게 바뀔까?
· 없는 이미지로 바꾼 배포는 화면에 어떻게 보이고 옛 파드는 왜 3개가 남았을까?
· kubectl로 만든 앱과 Portainer로 만든 앱은 화면에서 어떻게 다를까?
· 메모리 한도 512M 네임스페이스에서 0/2와 3/5는 왜 나왔고 거절된 파드는 어디에 기록될까?
· 웹 화면 하나로 클러스터를 다룰 때 권한과 열린 포트는 어떻게 다뤄야 할까?

1. 대시보드의 숫자는 지금 있는 오브젝트의 개수다

실험 방법부터 적을게요. 명령은 마스터에서 kubectl로 실행하고 결과는 Portainer 화면에서 확인했어요. Portainer는 Mac 브라우저에서 worker1의 주소 192.168.64.3과 NodePort 30779(HTTPS)로 열었어요. 실험은 새로 만든 demo 네임스페이스 안에서만 했습니다. 실험 전 화면이 그림 1이에요.

그림 1. 실험 전 대시보드. 숫자 일곱 개는 모두 지금 클러스터에 있는 오브젝트의 개수다

Environment info의 URL은 kubernetes.default.svc예요. 클러스터 안에서 API 서버를 부를 때 쓰는 Service 이름이라서 Portainer가 클러스터 안에서 파드로 돌면서 API 서버에 직접 요청한다는 뜻이에요. 이 연결이 어떤 권한으로 이뤄지는지는 6절에서 다시 볼게요.

📖 용어: 애플리케이션 (Portainer의 Application)
Portainer에서는 Deployment, DaemonSet, StatefulSet, 그리고 컨트롤러 없이 만든 파드를 묶어 애플리케이션이라고 해요. 대시보드의 Applications는 이 오브젝트들의 개수예요. 목록 화면(그림 5)의 Application type 열에도 Deployment, DaemonSet, Pod, Helm이 나와요.

그다음 demo 네임스페이스를 만들고 그 안을 채웠어요. 순서는 이랬어요.

master$ kubectl create namespace demo master$ kubectl -n demo create deployment web --image=nginx:1.25.1-alpine --replicas=2 --port=80 master$ kubectl -n demo scale deploy/web --replicas=4 (2절의 고장 실험과 되돌리기) master$ kubectl -n demo expose deploy/web --type=NodePort --port=80 service/web exposed NAME TYPE CLUSTER-IP EXTERNAL-IP PORT(S) AGE web NodePort 10.109.189.209 <none> 80:31725/TCP 0s master$ cat <<'EOF' | kubectl apply -f - # PVC web-data(1Gi, local-path), ConfigMap web-config, Deployment web-data persistentvolumeclaim/web-data created configmap/web-config created deployment.apps/web-data created

→ demo에 Deployment 2개(web, web-data), NodePort Service 1개, ConfigMap 1개, PVC 1개를 만들었다는 뜻이에요.

그림 2. demo를 채운 뒤. Ingresses와 Secrets를 뺀 다섯 숫자가 올라갔다
Namespaces Applications Services ConfigMaps Secrets Volumes before (그림 1) 8 13 9 18 3 1 after demo (그림 2) 9 15 10 20 3 2 after delete demo 8 13 9 18 3 1

→ demo를 지우자 여섯 숫자가 모두 실험 전 값으로 돌아왔다는 뜻이에요.

늘어난 숫자는 하나씩 맞춰 볼 수 있어요. Namespaces는 demo 하나, Applications는 web과 web-data 둘, Services는 web 하나, Volumes는 web-data PVC 하나만큼 늘었어요. 제가 만든 ConfigMap은 web-config 하나인데 ConfigMaps는 2가 늘었어요. 쿠버네티스에서는 kube-controller-manager가 API 서버 연결을 검증할 때 쓰는 CA 묶음을 kube-root-ca.crt라는 ConfigMap으로 모든 네임스페이스에 만들어 둬요(제거된 기능 게이트 목록의 RootCAConfigMap 설명). 늘어난 나머지 하나는 demo에 생긴 이 ConfigMap으로 보여요. demo 안의 ConfigMap 목록은 열어 보지 않았어요. Volumes에 잡힌 web-data PVC에는 local-path가 PV를 자동으로 만들어 붙였고 그 PV는 demo를 지울 때 함께 사라졌어요. 이 이야기는 16편에서 했어요.

대시보드의 숫자는 개수라서 앱이 정상인지는 알려 주지 않아요. web이 고장 나도 web이라는 Deployment는 그대로 있으니 개수는 변하지 않아요. 상태는 앱 화면으로 들어가야 보여요.

⚠️ 주의: 목록 화면은 시스템 리소스를 숨겨요
Namespaces·Applications·Services 목록 위에는 "System resources are hidden, this can be changed in the table settings"라는 안내가 붙어 있어요. demo가 있을 때 대시보드의 Namespaces는 9였는데 Namespaces 목록에는 default, demo, headlamp, local-path-storage, monitoring 다섯 개만 나왔어요. 빠진 넷은 kube-node-lease, kube-public, kube-system, portainer예요. Portainer 자신이 든 portainer 네임스페이스도 숨겨져 있다는 점은 6절에서 다시 나와요.

2. 없는 이미지로 바꾸자 Replicated 3 / 4가 되고 옛 파드 3개가 남았다

web을 2개로 만들고 4개로 늘렸을 때 Portainer의 앱 상세 화면에서 Status는 Replicated 2 / 2, 그다음 4 / 4였어요. 그 상태에서 이미지를 존재하지 않는 태그 nginx:does-not-exist로 바꿨어요. 25초 뒤에 kubectl로 본 파드 목록이에요.

master$ kubectl -n demo set image deploy/web nginx=nginx:does-not-exist && sleep 25 && kubectl -n demo get pods deployment.apps/web image updated NAME READY STATUS RESTARTS AGE web-7b466b6cf6-mszr7 0/1 ImagePullBackOff 0 24s web-7b466b6cf6-twwb9 0/1 ImagePullBackOff 0 24s web-858dfd6ff8-7z79p 1/1 Running 0 47s web-858dfd6ff8-kd2lb 1/1 Running 0 47s web-858dfd6ff8-m546r 1/1 Running 0 30s

→ 이름 가운데가 7b466b6cf6인 새 파드 2개는 이미지를 받지 못해 재시도를 기다리는 중(ImagePullBackOff)이고 858dfd6ff8인 옛 파드 3개는 그대로 돌고 있다는 뜻이에요.

📖 용어: ReplicaSet (레플리카셋)
정해진 수의 파드가 떠 있도록 맞추는 오브젝트예요. Deployment는 파드 템플릿이 바뀔 때마다 새 ReplicaSet을 만들고 옛 ReplicaSet과 새 ReplicaSet의 파드 수를 조절하면서 업데이트를 진행해요. 파드 이름 가운데의 7b466b6cf6, 858dfd6ff8이 어느 ReplicaSet의 파드인지 가르는 해시예요.
그림 3. 없는 이미지로 바꾼 뒤의 web. 두 숫자가 달라졌고 Events 탭에 경고 6이 붙었다

Portainer 화면에서는 Status가 Replicated 3 / 4로 바뀌고 Events 탭에 ⚠ 6이 붙었어요. 두 숫자가 무엇인지는 Portainer 코드에서 확인했어요. 2.45.3 태그의 utils.ts를 보면 Deployment일 때 앞 숫자는 status.availableReplicas(쓸 수 있는 상태가 된 파드 수)이고 뒤 숫자는 spec.replicas(원하는 파드 수)예요. 그러니 3 / 4는 "4개를 원하는데 쓸 수 있는 파드는 3개"라는 뜻이에요. Events 탭의 경고 6개는 새 파드 2개가 이미지를 받지 못해 남긴 경고로 보여요. 탭 안은 이번에 열어 보지 않았어요.

그러면 옛 파드는 왜 3개가 남았을까요. 답은 Deployment의 업데이트 방식에 있어요.

📖 용어: 롤링 업데이트 (RollingUpdate)
Deployment의 기본 업데이트 방식이에요. 새 ReplicaSet의 파드를 늘리고 옛 ReplicaSet의 파드를 줄이는 일을 조금씩 번갈아 해요. 원하는 수보다 몇 개까지 더 띄울지를 maxSurge로, 몇 개까지 못 쓰는 상태를 허용할지를 maxUnavailable로 정하고 둘 다 기본값은 25%예요.

Deployment 문서에 따르면 비율을 개수로 바꿀 때 maxUnavailable은 내림하고 maxSurge는 올림해요. replicas가 4면 25%는 정확히 1이라서 둘 다 1이에요. 그러면 파드는 모두 합쳐 5개(4+1)까지만 띄울 수 있고 쓸 수 있는 파드는 3개(4-1) 아래로 줄일 수 없어요. 새 파드 2개가 준비되지 못하니 옛 파드를 하나 더 줄이면 쓸 수 있는 파드가 2개가 돼요. 그래서 옛 3개와 새 2개, 합계 5개에서 롤아웃이 더 나아가지 못했어요. 같은 문서의 롤백 예제에도 잘못된 롤아웃은 Deployment 컨트롤러가 자동으로 멈추고 새 ReplicaSet을 더 늘리지 않으며 이 동작은 maxUnavailable 값에 달려 있다는 설명이 있어요.

그림 4. 상한 5개와 하한 3개 사이에서 새 파드가 준비되지 않으면 롤아웃이 그 자리에서 멈춘다

이대로 두면 어떻게 될까요. Deployment 문서의 Failed Deployment 절에 따르면 진행이 멈춘 Deployment에는 progressDeadlineSeconds(기본 600초)가 지난 뒤 Progressing 조건이 False, 이유 ProgressDeadlineExceeded로 붙어요. 쿠버네티스는 이 조건을 표시할 뿐 다른 조치는 하지 않는다고 적혀 있어요. 되돌리는 일은 사람이나 상위 도구의 몫이에요. 이번에는 이미지를 바꾼 지 35초 만에 되돌렸어요.

master$ kubectl -n demo rollout undo deploy/web && kubectl -n demo rollout status deploy/web --timeout=120s && kubectl -n demo get pods deployment.apps/web rolled back Waiting for deployment "web" rollout to finish: 3 out of 4 new replicas have been updated... Waiting for deployment "web" rollout to finish: 3 of 4 updated replicas are available... Waiting for deployment "web" rollout to finish: 3 of 4 updated replicas are available... deployment "web" successfully rolled out NAME READY STATUS RESTARTS AGE web-7b466b6cf6-mszr7 0/1 Terminating 0 35s web-858dfd6ff8-7z79p 1/1 Running 0 58s web-858dfd6ff8-kd2lb 1/1 Running 0 58s web-858dfd6ff8-m546r 1/1 Running 0 41s web-858dfd6ff8-r9hd4 1/1 Running 0 0s

→ 이전 템플릿(858dfd6ff8)으로 되돌리자 그 ReplicaSet이 다시 4개로 늘었고(r9hd4가 새로 떴다) 실패한 새 파드는 지워지는 중이라는 뜻이에요. Portainer의 Status도 다시 Replicated 4 / 4로 돌아왔어요.

⚠️ 주의: 멈춘 롤아웃은 요청 쪽에서 잘 드러나지 않아요
옛 파드 3개가 계속 Running이었으니 이 앱 앞에 Service가 있었다면 요청은 준비된 옛 파드 3개가 받았을 거예요. 이때는 아직 Service를 만들기 전이라 직접 확인하지는 않았지만 앱을 쓰는 쪽에서 이상을 바로 알아채기 어려운 상태예요. Portainer에서는 Replicated의 두 숫자가 다르면 Events 탭부터 여세요. 배포 스크립트에서 기다린다면 kubectl rollout status가 진행 기한을 넘긴 Deployment에서 0이 아닌 종료 코드로 끝난다는 점(Deployment 문서)을 쓸 수 있어요.

3. kubectl로 만든 앱에는 External이 붙는다

그림 3의 web 이름 옆에는 External이라는 표시가 있었고 버튼도 Edit external application이었어요. 이 표시의 뜻은 Portainer 문서의 Inspect an application 페이지에서 찾지 못했어요. 그래서 Portainer 코드를 열어 봤어요.

// app/react/kubernetes/applications/utils.ts (portainer/portainer 2.45.3 태그, 31~34행) // the application is external if it has no owner label export function isExternalApplication(application: Application) { return !application.metadata?.labels?.[appOwnerLabel]; } // app/react/kubernetes/applications/constants.ts (8행) export const appOwnerLabel = 'io.portainer.kubernetes.application.owner';

→ io.portainer.kubernetes.application.owner 라벨이 없는 앱은 누가 어떻게 만들었든 External로 표시한다는 뜻이에요.

그림 5. kubectl과 Helm으로 만든 앱에는 External이 붙고 Portainer 웹 편집기로 배포한 두 앱에는 붙지 않았다

그림 5의 Applications 목록에서 External이 없는 앱은 4절에서 Portainer 웹 편집기로 배포한 no-limit과 with-limit 둘뿐이에요. 강의 저장소의 매니페스트를 kubectl로 적용한 grafana, node-exporter, prometheus-deployment와 15편의 myweb, loadgen에 모두 붙어 있고 Helm으로 설치한 headlamp에도 붙어 있어요. Portainer로 배포한 앱의 상세 화면에는 Creation 줄에 만든 사람 admin과 "Deployed from manifest"가 나오고 버튼도 Edit this application, Rollback to previous configuration, Create template from application으로 바뀌어요(그림 7). Portainer 화면에서 만든 네임스페이스 pt-lab에도 io.portainer.kubernetes.resourcepool.owner=admin 같은 Portainer 라벨이 붙었어요(4절).

실무에서는 이 표시를 "이 앱의 원본 매니페스트는 Portainer 밖에 있다"는 신호로 읽으면 돼요. 원본이 Git의 YAML이나 Helm 차트라면 Portainer 화면에서 고친 내용은 그 원본에 남지 않아요. 다음에 원본을 다시 적용하면 화면에서 고친 값이 원본의 값으로 되돌아갈 수 있어요. External이 붙은 앱은 화면에서 고치기 전에 원본이 어디 있는지부터 확인하세요.

4. 메모리 한도 512M 네임스페이스에서 0/2와 3/5가 나온 이유

이번에는 Portainer 화면에서 직접 만들었어요. Namespaces → Create a namespace에서 이름을 pt-lab으로 적고 Resource assignment를 켠 뒤 Memory limit을 512MB로, CPU limit은 unlimited로 뒀어요. 폼 아래 Summary에 Portainer가 실행할 쿠버네티스 작업 두 개가 나와요. pt-lab이라는 Namespace와 portainer-rq-pt-lab이라는 ResourceQuota를 만든다는 내용이에요.

그림 6. 메모리 한도를 켜자 Summary에 ResourceQuota를 하나 만들겠다는 줄이 생겼다
📖 용어: ResourceQuota (리소스 쿼터)
네임스페이스 하나가 쓸 수 있는 자원의 총량이나 오브젝트 개수에 상한을 거는 오브젝트예요. Resource Quotas 문서에 따르면 오브젝트를 만들거나 고치는 요청이 상한을 넘으면 API 서버가 그 요청을 403 Forbidden으로 거절해요. 이미 만들어진 리소스에는 영향을 주지 않아요.
📖 용어: requests와 limits
컨테이너마다 적는 자원 값이에요. requests는 스케줄러가 파드를 놓을 노드를 고를 때 쓰는 값이고 limits는 kubelet이 컨테이너가 넘지 못하게 막는 상한이에요. 메모리 limits를 넘긴 컨테이너는 커널이 종료할 수 있어요(Resource Management 문서).

kubectl로 확인하면 이렇게 나와요.

master$ kubectl get ns pt-lab --show-labels; kubectl -n pt-lab get resourcequota,limitrange -o yaml | grep -A6 spec: NAME STATUS AGE LABELS pt-lab Active 32s io.portainer.kubernetes.resourcepool.name=pt-lab,io.portainer.kubernetes.resourcepool.owner=admin,kubernetes.io/metadata.name=pt-lab NAME REQUEST LIMIT AGE resourcequota/portainer-rq-pt-lab requests.memory: 0/512M limits.memory: 0/512M 32s {"hard":{"limits.memory":"512M","requests.memory":"512M"}}

→ 폼에 메모리 512MB를 적은 결과 requests.memory와 limits.memory 두 항목에 512M 상한이 걸렸고 LimitRange는 만들어지지 않았다는 뜻이에요. 네임스페이스에는 Portainer의 resourcepool 라벨이 붙었어요.

Portainer의 네임스페이스 추가 문서에는 Resource assignment를 켜면 메모리와 CPU 한도를 정할 수 있다는 정도만 적혀 있어요. 어떤 쿠버네티스 오브젝트가 생기는지는 폼의 Summary와 kubectl 결과로 확인했어요.

그다음 Create from code → Web editor에 Deployment 두 개를 넣고 Deploy를 눌렀어요. 둘 다 nginx:1.25.1-alpine이고 no-limit에는 자원 값을 적지 않았고 with-limit에는 메모리 requests와 limits를 128Mi씩 적었어요.

# Portainer Web editor에 넣은 매니페스트 (selector·labels 줄은 뺐다) kind: Deployment metadata: name: no-limit namespace: pt-lab spec: replicas: 2 ... containers: - name: nginx image: nginx:1.25.1-alpine --- apiVersion: apps/v1 kind: Deployment metadata: name: with-limit namespace: pt-lab spec: replicas: 5 ... containers: - name: nginx image: nginx:1.25.1-alpine resources: requests: {memory: 128Mi} limits: {memory: 128Mi}

→ no-limit은 파드 2개, with-limit은 파드 5개를 원하고 with-limit의 파드 하나는 메모리 128Mi를 요청한다는 뜻이에요.

45초 뒤 kubectl로 본 결과예요.

master$ kubectl -n pt-lab get deploy,rs,pods; kubectl -n pt-lab get resourcequota NAME READY UP-TO-DATE AVAILABLE AGE deployment.apps/no-limit 0/2 0 0 45s deployment.apps/with-limit 3/5 3 3 45s NAME DESIRED CURRENT READY AGE replicaset.apps/no-limit-c85f9544 2 0 0 45s replicaset.apps/with-limit-7d58cbbcf 5 3 3 45s NAME READY STATUS RESTARTS AGE pod/with-limit-7d58cbbcf-h88cf 1/1 Running 0 45s pod/with-limit-7d58cbbcf-kf5dd 1/1 Running 0 45s pod/with-limit-7d58cbbcf-nfsvv 1/1 Running 0 45s NAME REQUEST LIMIT AGE portainer-rq-pt-lab requests.memory: 384Mi/512M limits.memory: 384Mi/512M 116s

→ no-limit은 원하는 파드 2개 중 하나도 만들지 못했고 with-limit은 5개 중 3개만 만들었으며 쿼터에는 384Mi가 쓰였다는 뜻이에요. 파드 목록에는 실패한 파드가 한 줄도 없어요.

no-limit: 자원 값을 적지 않은 파드는 아예 만들어지지 않는다

Deployment와 ReplicaSet은 만들어졌는데 파드는 하나도 없어요. Resource Quotas 문서에 이 경우가 그대로 나와요. 쓸 수 있는 자원보다 많이 쓰려는 Deployment를 만들면 Deployment 생성은 성공하지만 그 Deployment가 관리할 파드를 모두 만들지는 못할 수 있다고 적혀 있어요. 같은 문서에는 cpu나 memory에 쿼터가 걸린 네임스페이스에서는 파드를 정의할 때 그 자원의 requests나 limits를 적어야 하고 적지 않으면 쿼터 시스템이 파드 생성을 거절할 수 있다는 설명도 있어요.

그림 7. 파드가 하나도 없는 no-limit. 거절 이유는 화면 맨 위 빨간 상자에 나왔다
Failed to create application pods "no-limit-c85f9544-b9mgr" is forbidden: failed quota: portainer-rq-pt-lab: must specify limits.memory for: nginx; requests.memory for: nginx

→ portainer-rq-pt-lab 쿼터가 nginx 컨테이너에 limits.memory와 requests.memory를 적으라고 요구해서 이 파드를 만드는 요청이 거절됐다는 뜻이에요.

이 쿼터는 requests.memory와 limits.memory 두 항목에 모두 상한을 걸었기 때문에 오류에도 두 값이 함께 나와요. Placement 탭에도 ⚠ 1이 붙어 있었는데 이번에는 그 탭을 열어 보지 않았어요.

📖 용어: 어드미션 (admission)
API 서버가 요청을 인증·인가한 뒤 오브젝트를 저장하기 전에 그 요청을 검사하거나 고치는 단계예요. ResourceQuota 검사도 이 단계의 컨트롤러가 해요. 여기서 거절된 파드는 저장되지 않으니 Pending 상태로도 남지 않아요.

그래서 kubectl get pods에 no-limit 파드가 한 줄도 없었어요. 그런데 Portainer의 Events 탭도 조용했어요.

그림 8. 같은 앱의 Events 탭에는 거절 경고가 없고 Normal 이벤트 한 줄뿐이었다

Events 탭에는 21:41:57에 Deployment가 남긴 "Scaled up replica set no-limit-c85f9544 from 0 to 2" 한 줄만 있었어요. 거절 기록은 kubectl로 네임스페이스의 이벤트를 조회해야 나왔어요.

master$ kubectl -n pt-lab get events | grep quota 44s Warning FailedCreate replicaset/no-limit-c85f9544 Error creating: pods "no-limit-c85f9544-xd5qx" is forbidden: failed quota: portainer-rq-pt-lab: must specify limits.memory for: nginx; requests.memory for: nginx 44s Warning FailedCreate replicaset/no-limit-c85f9544 Error creating: pods "no-limit-c85f9544-bxc7p" is forbidden: failed quota: portainer-rq-pt-lab: must specify limits.memory for: nginx; requests.memory for: nginx 5s Warning FailedCreate replicaset/no-limit-c85f9544 (combined from similar events): Error creating: pods "no-limit-c85f9544-tw2bh" is forbidden: failed quota: portainer-rq-pt-lab: ... 2s Warning FailedCreate replicaset/with-limit-7d58cbbcf (combined from similar events): Error creating: pods "with-limit-7d58cbbcf-99tsx" is forbidden: exceeded quota: portainer-rq-pt-lab, ...

→ 경고가 붙은 대상이 Deployment가 아니라 ReplicaSet이라는 뜻이에요. ReplicaSet은 조회 44초 전에도 5초 전에도 파드 만들기를 다시 시도했고 비슷한 이벤트는 "(combined from similar events)"로 묶여 기록됐어요.

Events 탭이 조용했던 이유는 Portainer 코드에 있었어요. useApplicationEventsTableData.tsx를 보면 앱 Events 탭에는 네임스페이스의 이벤트 중 대상(involvedObject)이 그 앱 자신, 그 앱의 Service, 그 앱의 파드인 것만 들어가요. FailedCreate는 ReplicaSet에 붙는 이벤트라서 걸러지고 거절된 파드는 존재하지 않으니 파드 이벤트도 없어요. 반면 그림 7 맨 위의 빨간 상자는 다른 곳에서 와요. ApplicationSummaryWidget.tsx에서는 Deployment의 status.conditions에서 reason이 FailedCreate인 조건을 찾아 그 메시지를 "Failed to create application" 아래에 띄워요. Deployment 문서의 Failed Deployment 절에도 쿼터가 모자라면 Deployment 상태에 type이 ReplicaFailure, reason이 FailedCreate인 조건이 생기는 예가 나와요.

그림 9. 거절된 파드는 존재하지 않는다. 흔적은 Deployment의 조건과 ReplicaSet의 이벤트에 남는다

쿼터에 막힌 파드는 파드 목록에도 앱의 Events 탭에도 없어요. Portainer에서는 앱 화면 맨 위의 빨간 상자를 보고 kubectl에서는 get events의 FailedCreate를 봐야 해요.

with-limit: 128Mi 파드 4개는 512M 한도를 넘는다

그림 10. with-limit은 3개에서 멈췄다. 빨간 상자에 요청량, 사용량, 한도가 함께 나온다
Failed to create application pods "with-limit-7d58cbbcf-8hv9z" is forbidden: exceeded quota: portainer-rq-pt-lab, requested: limits.memory=128Mi,requests.memory=128Mi, used: limits.memory=384Mi,requests.memory=384Mi, limited: limits.memory=512M,requests.memory=512M

→ 이미 384Mi를 쓰는 중에 128Mi를 더 요청하면 한도(512M)를 넘기 때문에 넷째 파드를 거절했다는 뜻이에요.

처음에는 계산이 맞지 않아 보였어요. 128 × 4 = 512이니 4개까지는 들어가야 할 것 같았거든요. 차이는 단위에 있었어요.

📖 용어: Mi와 M (메모리 단위)
쿠버네티스 메모리 값에 붙는 접미사예요. M은 10의 6제곱(1,000,000)바이트이고 Mi는 2의 20제곱(1,048,576)바이트예요. Resource Management 문서에는 대소문자도 조심하라는 주의가 있어요. 소문자 m은 1/1000바이트라서 400m은 0.4바이트예요.

바이트로 바꾸면 512M 한도는 512,000,000바이트이고 128Mi는 134,217,728바이트예요. 파드 3개면 402,653,184바이트(384Mi)이고 4개면 536,870,912바이트(512Mi)라서 한도를 24,870,912바이트 넘어요. 3개를 띄운 뒤 남은 자리는 109,346,816바이트(약 104Mi)라서 128Mi 파드 하나가 들어갈 수 없었어요(그림 11). 폼에는 MB로 512를 적었고 매니페스트에는 Mi로 128을 적었어요. 숫자는 맞아떨어져 보여도 단위가 달라서 넷째 파드가 들어가지 못했어요.

그림 11. 같은 512라도 M과 Mi는 다르다. 128Mi 넷째 파드는 512M 한도를 넘는다

Portainer 화면 안에서도 단위가 섞여 있어요. 네임스페이스 폼의 Memory limit은 MB이고 앱 화면의 Resource reservations는 MiB(그림 10의 Memory 128 MiB)이며 클러스터 화면도 MiB예요(5절). 폼 슬라이더의 끝 값 15958MB는 클러스터 화면의 메모리 합계 15220MiB를 MB로 바꾼 값(약 15959MB)과 거의 같아요. 한도를 512Mi로 적었다면 계산상 128Mi 파드 4개가 들어갔을 거예요. 이번에는 해 보지 않았어요.

💡 실무에서는: 쿼터를 건 네임스페이스에 배포할 때
• 쿼터에 걸린 자원(이번에는 메모리의 requests와 limits)은 모든 컨테이너에 적으세요. 하나라도 빠지면 그 Deployment의 파드는 하나도 만들어지지 않아요
• 기본값을 강제하고 싶다면 LimitRange를 함께 두세요. Resource Quotas 문서도 자원 값을 적지 않은 파드에 기본값을 넣는 방법으로 LimitRange를 안내해요. 이번에 Portainer 폼은 ResourceQuota만 만들었어요
• 한도와 요청의 단위를 맞추세요. 512M 한도에는 128Mi 파드가 3개까지, 512Mi 한도에는 4개까지 들어가요(계산)
• 확인은 kubectl -n <네임스페이스> get resourcequota의 사용량/한도와 get events의 FailedCreate로 하세요. Portainer에서는 앱 화면 맨 위의 빨간 상자예요

5. 파드 로그의 시각은 UTC이고 클러스터 화면의 메모리는 요청량의 합이다

Portainer에서는 kubectl logs와 kubectl get nodes로 보던 내용도 화면으로 볼 수 있어요. Applications → myweb → Pods → myweb-859c4764d4-4tjzk → Containers → nginx → Logs로 들어가면 컨테이너 로그가 나와요. 15편의 서비스맵 실험에 쓴 myweb 파드예요.

그림 12. 마스터가 보낸 curl 요청이 nginx 접근 로그에 남아 있다. 시각은 UTC다

위쪽에는 Auto-refresh 스위치, 로그 안을 거르는 Search 칸, Download logs 버튼이 있어요. 로그에는 nginx/1.25.1과 OS: Linux 6.8.0-147-generic이 찍힌 시작 기록 뒤로 10.244.235.192에서 온 "GET / HTTP/1.1" 200 615 "curl/8.5.0" 요청이 1초 간격으로 이어져요. 출발지 10.244.235.192는 15편에서 확인한 마스터의 Calico tunl0 주소예요. 15편에서 파드별 요청 수를 세는 정답지로 쓴 nginx 접근 로그가 바로 이 로그예요.

시각은 조심해서 읽어야 해요. 접근 로그의 [11/Nov/2026:11:57:55 +0000]은 UTC라서 한국 시각으로는 20:57:55예요. 반면 Portainer 화면의 Creation 같은 시각은 한국 시각으로 나왔어요(그림 10의 2026-11-11 21:41:57). 두 화면의 시각을 맞춰 볼 때는 로그 쪽에 9시간을 더해야 해요.

그림 13. Resource reservation은 실제 사용량이 아니라 파드 requests의 합이다

Cluster → Details 화면에는 노드 4대가 모두 Ready로 나와요. 노드마다 CPU 2, 메모리 3805MiB, 버전 v1.37.2이고 IP는 192.168.104.1, .3, .4, .5예요. 3편에서 노드끼리 통하는 eth0(user-v2) 주소로 노드를 등록했으니 Mac에서 NodePort로 접속할 때 쓴 192.168.64.3과 다른 주소가 나오는 게 맞아요. Cached Images 열에는 12, 18, 20, 13이 나왔어요.

위쪽 Resource reservation은 Memory 624 / 15220 MiB(4%), CPU 1.85 / 8(23%)예요. 화면 설명에는 "클러스터 안 모든 애플리케이션에 할당된 자원의 총량"이라고 적혀 있어요. Portainer 코드를 보면 이 값은 클러스터의 모든 파드에서 컨테이너의 CPU·메모리 requests를 더한 값이고(applications.go) 분모는 노드 4대의 할당 가능량(allocatable)을 더한 값이에요(useClusterResourceLimitsQuery.ts). 3805MiB × 4 = 15220MiB, 2 CPU × 4 = 8이에요. 실제 사용량은 Portainer의 환경 설정에서 서버 메트릭(UseServerMetrics)을 켜야 따로 나오는데(useClusterResourceReservationData.tsx) 이번에는 켜지 않아서 요청량만 보였어요.

메모리 예약 4%는 메모리를 4%만 쓰고 있다는 뜻이 아니에요. requests를 적지 않은 파드는 이 합계에 들어가지 않으니 실제 사용량과 차이가 클 수 있어요. 이번에 연 Portainer 화면에는 시간에 따른 그래프도 없었어요. 실제 사용량과 그 변화는 11~12편의 Prometheus와 Grafana에서 봐야 해요.

6. NodePort로 연 Portainer 로그인 하나가 cluster-admin으로 이어진다

16편에서 적용한 공식 매니페스트(portainer.yaml)에는 이런 ClusterRoleBinding이 들어 있어요.

# portainer.yaml (downloads.portainer.io/ce-lts, 일부) kind: ClusterRoleBinding metadata: name: portainer roleRef: apiGroup: rbac.authorization.k8s.io kind: ClusterRole name: cluster-admin subjects: - kind: ServiceAccount namespace: portainer name: portainer-sa-clusteradmin ... # Deployment portainer serviceAccountName: portainer-sa-clusteradmin

→ portainer 네임스페이스의 ServiceAccount portainer-sa-clusteradmin에 cluster-admin을 묶고 Portainer 파드를 그 ServiceAccount로 띄운다는 뜻이에요.

쿠버네티스 RBAC 문서의 기본 역할 표에서 cluster-admin은 슈퍼유저 권한을 주는 역할이에요. ClusterRoleBinding으로 묶으면 클러스터와 모든 네임스페이스의 모든 리소스를 완전히 제어할 수 있다고 적혀 있어요. 10편에서 admin-user에 묶었던 바로 그 역할이에요. Portainer 설치 문서에도 Portainer가 ServiceAccount와 ClusterRoleBinding을 만들 수 있도록 클러스터 관리자 권한이 필요하다는 사전 조건이 적혀 있어요. 1절에서 본 Environment URL kubernetes.default.svc까지 합치면 Portainer가 클러스터에 하는 일은 이 ServiceAccount의 권한 안에서 이뤄진다고 볼 수 있어요.

이 권한을 쓰는 화면은 NodePort로 열려 있어요. 매니페스트의 Service에는 9000이 30777(HTTP), 9443이 30779(HTTPS), 30776이 같은 번호(edge)로 적혀 있어요. 설치 문서에도 30777은 HTTP, 30779는 HTTPS로 열린다고 적혀 있고 30779는 기본으로 자체 서명 인증서를 써요. NodePort는 모든 노드의 같은 포트로 열리니 192.168.64.3이 아닌 다른 워커 주소로도 닿을 수 있어요. 로그인한 뒤에는 사이드바의 kubectl shell 버튼으로 브라우저 안에서 kubectl과 helm이 든 셸을 열 수 있어요. kubectl shell 문서에는 그 셸에 로그인한 사용자의 권한에 맞춘 kubeconfig가 들어 있다고 적혀 있고 이번에 로그인한 계정은 Portainer 관리자 admin이었어요.

그림 14. 포트에 닿은 사람과 클러스터 전체 권한 사이에는 Portainer 로그인 하나만 있다
그림 15. NodePort로 열린 Service가 한 화면에 모인다. 다만 Portainer 자신의 Service는 목록에 없다

Networking → Services 목록은 열린 포트를 점검하기에 좋아요. 이 클러스터에서는 grafana 30004, prometheus-service 30003, node-exporter 31672, 그리고 demo의 web 31725가 NodePort였어요. 앞의 셋은 11편에서 강의 매니페스트를 적용하며 열린 포트예요. 그런데 이 목록에 Portainer 자신의 Service가 없어요. 1절에서 본 대로 portainer 네임스페이스가 시스템 리소스로 숨겨져 있기 때문으로 보여요. 표 설정에서 시스템 리소스를 보이게 하면 나올 것 같지만 이번에는 바꿔 보지 않았어요. 관리 화면으로 열린 포트를 점검할 때 그 관리 화면 자신의 포트가 목록에서 빠져 있을 수 있어요.

💡 실무에서는: 실습이 끝나면 Portainer의 NodePort를 닫아요
• 9편의 Headlamp와 같은 방식으로 Service를 ClusterIP로 두고 필요할 때만 kubectl port-forward로 여는 방법이 있어요. port-forward는 API 서버를 거치고 kubeconfig의 자격 증명이 있어야 열려요. Portainer에는 이번에 적용해 보지 않았어요
• NodePort를 열어 둬야 한다면 30777(HTTP)은 쓰지 말고 30779(HTTPS)로만 접속하세요. HTTP로 로그인하면 관리자 비밀번호가 암호화되지 않은 채 오가요
• 2.45.3에서는 첫 관리자를 만들 때 서버 로그에 찍힌 setup token이 있어야 했고 토큰 없이 보낸 요청은 403이었어요(16편). 그래도 관리자를 만든 뒤에는 비밀번호 하나가 cluster-admin 권한 앞에 남아요
• RBAC 모범 사례 문서에는 관리자라도 꼭 필요한 경우가 아니면 cluster-admin 계정을 쓰지 말라고 적혀 있어요. Portainer를 여러 사람이 쓴다면 관리자 계정 하나를 나눠 쓰지 말고 사용자마다 권한을 나눠야 해요. Portainer의 사용자 권한 기능은 이번에 확인하지 않았어요
✍️ 오늘의 요약
Portainer는 지금 클러스터에 무엇이 어떤 상태로 있는지 보여 주고 그 자리에서 바꾸게 해 주는 관리 도구였어요.

대시보드의 숫자는 오브젝트 개수라서 상태는 앱 화면의 Replicated n / m과 Events에서 읽어야 해요. 없는 이미지로 바꾼 web은 maxSurge·maxUnavailable 기본값 25% 때문에 옛 파드 3개와 새 파드 2개에서 멈췄고 화면에는 Replicated 3 / 4로 나왔어요. kubectl이나 Helm으로 만든 앱에는 Portainer의 owner 라벨이 없어서 External이 붙어요. 메모리 512M 쿼터를 건 네임스페이스에서는 자원 값을 적지 않은 no-limit이 0/2, 128Mi를 적은 with-limit이 3/5에서 멈췄어요. 거절된 파드는 존재하지 않아서 파드 목록과 앱 Events 탭에는 흔적이 없고 앱 화면 맨 위 빨간 상자와 ReplicaSet 이벤트에만 남았어요. Portainer 파드는 cluster-admin이 묶인 ServiceAccount로 돌기 때문에 NodePort로 연 화면은 실습이 끝나면 닫아야 해요. 화면에 숫자가 두 개 나오면 둘이 같은지부터 보고 다르면 그 차이가 어디에 기록됐는지 따라가야 해요.
