restartPolicy: Never인 파드에 컨테이너 두 개를 넣었어요. app은 10초 뒤 exit 0으로 끝나고 helper는 3초마다 exit 0으로 끝나요. helper에만 컨테이너 수준의 restartPolicy: Always를 줬어요. 사이드카처럼 app이 끝나면 helper도 정리되고 파드가 끝나기를 기대한 설정이에요.

76초 뒤 kubectl get pod는 0/2 Completed 3 (52s ago)를 보여 줬어요. STATUS 칸만 보면 끝난 파드예요. 그런데 phase는 Running이었어요. app은 오래전에 끝났고 helper는 계속 다시 뜨면서 재시작 횟수가 2에서 3으로 늘고 있었어요. 파드는 끝나지 않았어요.

70편까지 본 네이티브 사이드카는 initContainers 안의 restartPolicy: Always였어요. 69편에서 본 것처럼 2023년 KEP는 이 필드를 컨테이너 타입에 더하면서 "컨테이너별 restart policy라는 오랜 요청을 구현할 기회가 열린다"고 적었고 그 기회는 1.34의 KEP-5307로 보통 컨테이너에 열렸어요. 이번 글은 v1.37.2에서 그 필드가 보통 컨테이너에서 어떻게 동작하는지, 그리고 사이드카와 왜 다른지 확인해요.

· 같은 Always가 파드, init 컨테이너, 보통 컨테이너에서 각각 무엇을 뜻할까?
· restartPolicyRules는 어떤 문제를 풀려고 나왔을까?
· 2022년에 버린 컨테이너별 restartPolicy는 어떻게 돌아왔을까? 정책을 낮추면 어떻게 될까?
· 파드 종료 중에 죽은 사이드카는 왜 아직 다시 뜨지 않을까?
· 그래서 무엇을 어디에 쓰면 될까?

1. 보통 컨테이너의 Always는 파드를 끝내지 않는다

📖 용어: 컨테이너 수준 restartPolicy
파드의 spec.restartPolicy와 별개로 컨테이너마다 적는 restartPolicy예요. 값은 Always, Never, OnFailure이고 적으면 그 컨테이너에 한해 파드의 값을 덮어써요. 1.28부터 init 컨테이너의 Always(사이드카)에 쓰였고 1.34부터 보통 컨테이너에도 열렸어요.

도입의 실험은 labs/devops/k8s-study/out/71-restart-rules.txt의 always-pod예요. 같은 디렉터리의 71-restart-rules.sh로 다시 돌릴 수 있어요.

그림 1. always-pod의 STATUS는 Completed인데 phase는 Running이에요.

API 서버는 보통 컨테이너의 restartPolicy: Always를 그대로 받아들였어요. 생성 후 30초에 app은 exit 0으로 끝나 있었고 helper는 이미 두 번 재시작한 상태였어요. 75초에도 phase는 Running이었고 helper의 재시작은 3회로 늘었어요. 재시작 사이 간격은 점점 벌어졌어요. exit 0으로 끝나도 재시작이 반복되면 kubelet은 백오프를 적용해요. STATUS 칸의 Completed는 그 순간 helper도 끝나 있어서 두 컨테이너가 모두 terminated였기 때문에 보인 값이에요.

같은 helper를 initContainers에 넣었다면 결과는 달랐을 거예요. 68편의 job-native에서 initContainers의 사이드카는 work가 끝나자 SIGTERM을 받았고 파드는 Succeeded가 됐어요. 차이는 kubelet이 사이드카를 골라내는 기준에 있어요. kubelet은 IsRestartableInitContainer, 즉 "initContainers에 있고 restartPolicy가 Always인 컨테이너"만 사이드카로 다뤄요. 종료 순서, phase 계산 제외, "main이 다 끝나면 사이드카 재시작을 멈춘다"는 규칙 모두 이 판별을 거쳐요(70편). KEP-5307도 이 점을 분명히 적었어요.

This proposal does not change how Sidecar containers will be detected and their lifecycles.

→ 이 제안은 사이드카를 판별하는 방법과 사이드카의 생명주기를 바꾸지 않는다는 뜻이에요. 그래서 containers에 있는 helper는 Always를 받아도 보통 컨테이너예요. kubelet이 파드를 끝내는 조건은 남길 main 컨테이너도 시작할 main 컨테이너도 없을 때인데, helper는 끝날 때마다 다시 시작할 컨테이너가 되므로 이 조건이 오지 않아요. 관찰과 맞는 코드 해석이에요.

그림 2. 가운데 칸만 사이드카예요. 오른쪽 칸은 사이드카처럼 보이지만 파드를 붙잡아요.

2023년 KEP는 이 상황을 예상했어요. "Future use of restartPolicy field" 절은 보통 컨테이너에도 Always가 열리면 Never나 OnFailure 파드에서 그 컨테이너는 파드 종료를 막지 않을 것이고 "the container with restartPolicy:Always will effectively become a sidecar container similar to init container with the same field value"라고 적었어요. Always와 새 enum 값을 비교한 절에서는 이 경우를 두고 "needs to be carefully reviewed at the time this feature will be considered"라며 결정을 미뤘어요. 실제로 열린 1.34 이후의 동작은 우리 실험처럼 사이드카가 되지 않는 쪽이에요.

2023년 1월 KEP 리뷰에서 thockin은 보통 컨테이너의 조합표를 따로 그렸어요.

{ Pod: OnFail, Container: Always } = Either not-supported or API warning - pod can never terminate. See note2 { Pod: Never, Container: Always } = Either not-supported or API warning - pod can never terminate. See note2 ... Note2: Setting the per-container policy "greater than" the pod policy is semantically unclear and probably should be disallowed.

→ 파드가 OnFailure나 Never인데 컨테이너가 Always면 파드가 끝날 수 없으니 막거나 API 경고를 내야 한다는 의견이에요. v1.37.2에서 이 조합을 --dry-run=server로 보내고 stderr까지 남겼는데 경고는 없었어요(labs/devops/k8s-study/out/71-restart-combos.txt의 (1)). 검증 코드의 supportedContainerRestartPolicies는 Always, Never, OnFailure 셋을 모두 받아요. KEP-5307의 리뷰에서 이 조합을 따로 논의했는지는 리뷰 코멘트를 읽지 않아 확인하지 못했어요.

⚠️ STATUS가 Completed여도 phase를 봐요
always-pod는 kubectl get pod의 STATUS가 Completed였지만 phase는 Running이었어요. STATUS 칸은 컨테이너 상태에서 뽑은 요약이라 그 순간 막 끝난 컨테이너의 reason이 보일 수 있어요. 파드가 정말 끝났는지는 kubectl get pod 파드이름 -o jsonpath='{.status.phase}'로 확인해요. Job이었다면 이 파드는 끝나지 않아 Job도 완료되지 않아요.

2. restartPolicyRules는 비싼 재스케줄을 피하려고 나왔다

그렇다면 보통 컨테이너의 restartPolicy는 무엇을 하려고 열렸을까요? 2025년 5월 yuanwang04와 SergeyKanzhelev가 올린 KEP-5307의 Summary는 사이드카 이야기가 아니에요.

This will allow users to configure special exit codes of the container to be treated as non-failure and restart the container in-place even if the Pod has a restartPolicy=Never. This scenario is important for use cases, when rescheduling of a task is very expensive, and restarting in-place is preferable.

→ 특정 exit code를 실패로 보지 않고 파드가 Never여도 컨테이너를 제자리에서 다시 시작하게 하자는 뜻이에요. 작업을 다시 스케줄하는 비용이 클 때 필요하다고 했어요.

Motivation은 AI/ML 학습 Job을 예로 들었어요. Job 하나가 비싼 하드웨어를 쓰는 파드 수백 개로 이뤄지고 모든 파드가 같은 체크포인트에서 함께 한 단계씩 나아가요. 한 파드라도 실패하면 모든 파드를 다시 시작해 이전 체크포인트부터 함께 시작하는 것이 가장 빠르고, 파드를 다시 스케줄하는 비용이 크니 이 재시작을 제자리에서 하도록 따로 다뤄야 한다는 내용이에요. 파드를 OnFailure로 두면 안 되는 이유도 두 가지 적었어요. 하드웨어 고장은 파드를 실패시켜 다른 곳으로 옮겨야 하므로 제자리 재시작과 구별해야 하고 Job의 podFailurePolicy는 OnFailure 파드와 함께 쓸 수 없어요.

📖 용어: podFailurePolicy
Job이 실패한 파드를 어떻게 셀지 정하는 규칙이에요. 특정 exit code나 파드 조건이면 Job을 바로 실패시키거나 재시도 횟수에서 빼는 식으로 써요. Job 컨트롤러가 파드가 끝난 뒤에 평가하므로, KEP-5307은 컨테이너 수준 재시작이 이 정책과 겹치지 않는다고 적었어요.
📖 용어: restartPolicyRules
컨테이너가 끝날 때 순서대로 검사하는 규칙 목록이에요. 규칙은 조건(exit code)과 동작(Restart)으로 되어 있고 맞는 규칙이 없으면 컨테이너의 restartPolicy를 따라요. 규칙을 쓰려면 restartPolicy를 반드시 함께 적어야 해요. 규칙은 20개까지, exit code 값은 255개까지 넣을 수 있어요.

always-pod와 같은 파일의 rules-pod가 이 쓰임새예요. 파드는 Never이고 app은 처음 두 번 exit 42, 세 번째에 exit 0으로 끝나요.

spec: restartPolicy: Never containers: - name: app restartPolicy: Never restartPolicyRules: - action: Restart exitCodes: {operator: In, values: [42]} rules-pod phase=Succeeded app: restartCount=2 state=terminated(exit=0) lastExit=42

→ exit 42일 때만 제자리에서 두 번 다시 시작했고 세 번째 exit 0으로 파드가 Succeeded가 됐어요. 42가 아닌 다른 코드로 실패했다면 컨테이너의 restartPolicy인 Never를 따라 그대로 끝났을 거예요.

기능 게이트는 ContainerRestartRules예요. 1.34에 알파(#132642, 2025-07-24 병합), 1.35에 베타로 기본 켜짐(#134631, 2025-10-22 병합)이 됐어요. KEP의 kep.yaml은 GA 목표를 v1.36으로 적었지만 v1.37.2의 kube_features.go는 아직 1.35의 Beta 항목에서 멈춰 있어요. GA가 늦어진 이유는 확인하지 못했어요.

KEP-5307의 메모 몇 개는 사이드카와 이어져요. restartPolicy가 Never인 파드에서 재시작 횟수가 0보다 클 수 있다는 점은 "This is already possible for sidecar containers which have container-level restartPolicy=Always."라고 적었어요. 사이드카에 restartPolicyRules를 붙이는 것은 사이드카가 어차피 늘 다시 뜨므로 효과가 없다고 했어요.

💡 restartPolicyRules는 "다시 해도 되는 실패"를 구별할 때 써요
학습 코드가 "체크포인트부터 다시 하면 되는 실패"에 정해진 exit code를 쓰고 그 코드만 restartPolicyRules로 제자리 재시작하게 하면 파드를 새로 스케줄하지 않아도 돼요. 다른 실패는 파드를 끝내 podFailurePolicy가 판단하게 둬요. 재시작도 백오프를 따르므로 같은 코드로 계속 죽으면 간격이 늘어나요.

3. 2022년에 버린 컨테이너별 restartPolicy가 다른 목적으로 돌아왔다

이 필드는 2022년에 한 번 버려졌던 생각이에요. 69편에서 본 2022년 11월 15일 워킹 그룹 회의록의 "버린 설계" 2번이 "Not the per-container termination/restartPolicy control"이었어요. 사이드카를 컨테이너별 restartPolicy 덮어쓰기로 표현하는 안을 버렸다는 뜻이에요. 그 안이었던 SergeyKanzhelev의 2022년 문서 "Per Container Restart Policy override"는 덮어쓰기 방향을 한쪽으로 묶었어요.

Containers can only override to "higher" value. From Never to OnFailure or Always, from OnFailure to Always. And override from Always to Never is not allowed.

→ 컨테이너는 파드보다 "높은" 값으로만 덮어쓸 수 있고 Always에서 Never로 낮추는 것은 허용하지 않는다는 뜻이에요. 문서는 kubelet이 재시작했을 때 Never로 낮춘 컨테이너를 다시 띄워야 하는지 판단할 수 없는 상황을 피하려는 것이라고 적었어요. 2023년 KEP의 Future 절도 같은 방향을 적고 적어도 컨테이너 하나는 파드의 restartPolicy와 같아야 한다는 조건을 둘 가능성도 언급했어요.

2025년 KEP-5307의 Design Details는 파드의 restartPolicy가 컨테이너마다의 기본값이 되고 컨테이너의 restartPolicy가 그것을 덮어쓴다고만 적었어요. 우리 클러스터에서 양쪽 방향을 모두 돌려 봤어요. 원본은 labs/devops/k8s-study/out/71-restart-combos.txt와 같은 디렉터리의 71-restart-combos.sh예요.

그림 3. "낮추는" 덮어쓰기(Always 파드의 Never 컨테이너)도 v1.37.2는 받아요.

always-never 파드는 restartPolicy가 Always인데 once 컨테이너에만 Never를 줬어요. once는 3초 뒤 exit 0으로 끝났고 파드를 만들고 60초가 지나도 다시 뜨지 않았어요(restartCount 0). 파드는 Running이었지만 READY는 1/2, STATUS는 NotReady였어요. 2022년 문서와 2023년 KEP가 허용하지 않겠다던 방향이 지금은 동작해요. never-onfail 파드는 반대 방향이에요. 파드는 Never인데 app에 OnFailure를 줬고 app은 exit 1로 두 번 죽은 뒤 세 번째에 exit 0으로 끝나 파드가 Succeeded가 됐어요. never-onfail은 컨테이너가 app 하나뿐이라 파드의 restartPolicy와 같은 컨테이너가 하나도 없는 파드이기도 해요. 2023년 KEP가 둘 수도 있다고 한 "적어도 컨테이너 하나는 파드의 restartPolicy와 같아야 한다"는 조건도 v1.37.2는 요구하지 않았어요.

⚠️ Always 파드에서 한 번만 도는 컨테이너는 파드를 NotReady로 만들어요
Deployment 파드 안에 "한 번만 돌고 끝나는" 컨테이너를 restartPolicy: Never로 넣으면 그 컨테이너가 끝난 순간부터 파드는 READY 1/2, NotReady로 보여요. 한 번만 도는 준비 작업이라면 보통 init 컨테이너가 맞는 자리예요.

재시작 규칙은 한 걸음 더 나갔어요. KEP-5532는 restartPolicyRules에 컨테이너 하나가 끝나면 파드의 컨테이너 전체를 다시 시작하는 동작을 더해요. 1.35에 알파, 1.36에 베타(기본 켜짐)가 됐고 v1.37.2 검증 코드는 이 게이트가 켜져 있으면 RestartAllContainers 동작을 받아요. Summary는 이것을 이렇게 설명해요.

This "in-place" pod restart will terminate and then restart all of the pod's containers (including init and sidecar containers) while preserving the pod's sandbox, UID, network namespace, attached devices, and IP address.

→ 파드의 샌드박스, UID, 네트워크 네임스페이스, 붙은 장치, IP를 그대로 둔 채 init 컨테이너와 사이드카까지 모든 컨테이너를 내렸다 다시 올린다는 뜻이에요. 이 동작은 이번에 실험하지 않았어요.

그림 4. 2022년에 버린 것은 "사이드카를 이 방식으로 표현하는 것"이었고 재시작 제어 자체는 2025년에 돌아왔어요.

4. 종료 중에 죽은 사이드카는 아직 다시 뜨지 않는다

사이드카 쪽에 남은 일도 하나 있어요. KEP-753의 종료 절에는 1.29 베타를 준비하며 적은 이런 문장이 있고 지금 판에도 남아 있어요.

Sidecars continue to be restarted until they enter the `Terminated` state which they are notified by a `SIGTERM` signal. This is to ensure that sidecars that fail are restarted until the TGPS expires.

→ 사이드카는 SIGTERM으로 종료 통보를 받기 전까지는 계속 다시 시작되어, 실패한 사이드카도 유예 시간이 끝날 때까지는 다시 뜬다는 뜻이에요. 70편에서 본 것처럼 파드를 지우면 사이드카는 앱이 끝날 때까지 SIGTERM을 받지 않아요. 그 사이에 사이드카가 죽으면 다시 띄우겠다는 계획이었어요.

이 부분은 베타에서 빠졌어요. 2024년 1월 30일 병합된 enhancements PR #4324가 이를 KEP-4438로 떼어 냈어요. KEP-4438의 Motivation은 이유를 이렇게 적었어요.

restarting sidecar containers during Pod termination requires fundamental changes to the Pod lifecycle, and such changes cannot be introduced in beta (enabled by default) without risking disruption to users.

→ 파드 종료 중에 사이드카를 다시 시작하려면 파드 생명주기를 근본적으로 바꿔야 하고 기본으로 켜지는 베타에 그런 변경을 넣으면 사용자에게 장애를 줄 위험이 있다는 뜻이에요. 2020년의 반대 의견도 kubelet 생명주기 코드가 단단해지기 전에 기능을 넓히지 말자는 것이었어요.

2026년 11월 기준 KEP-4438의 kep.yaml은 상태 implementable, 단계 alpha, 알파 목표 v1.38, 게이트 이름 SidecarsRestartableDuringPodTermination이고 추적 이슈 #4438은 열려 있어요. Goals는 파드 종료 중에도 사이드카 재시작, liveness·readiness·startup 프로브, 생명주기 훅, 서비스 어카운트 토큰 갱신, Secret과 ConfigMap 볼륨 갱신을 유지하자는 것이에요. Summary의 첫 문장 "Sidecar containers should be restarted if they exit prematurely when a Pod is terminated"는 지금은 그렇지 않다는 것을 전제로 해요. 우리 클러스터에서 종료 중에 사이드카를 죽이는 실험은 하지 않았어요.

⚠️ 종료 중의 사이드카는 다시 뜬다고 가정하지 마세요
v1.37.2에서는 앱이 정리하는 동안 사이드카가 죽으면 다시 뜬다는 동작을 기대할 근거가 없어요. 프록시가 앱의 정리 트래픽을 맡는다면 사이드카가 SIGTERM 전에 스스로 죽지 않도록 메모리 한도와 liveness 설정을 보수적으로 잡는 편이 안전해요. 사이드카의 liveness 실패가 종료 중에 어떻게 처리되는지는 이번에 확인하지 않았어요.

5. 그래서 무엇을 어디에 쓸까

컨테이너마다 restartPolicy를 주면 사이드카가 될까라는 처음 질문의 답은 "아니요"예요. 사이드카를 정하는 것은 값이 아니라 initContainers라는 자리예요. 같은 필드 이름으로 할 수 있는 일을 우리 실험과 함께 정리하면 이래요.

하고 싶은 일쓸 자리v1.37.2에서 본 것
앱보다 먼저 떠서 끝까지 돌고 파드 종료는 막지 않는 도우미(프록시, 로그 수집기)initContainers + restartPolicy: AlwaysJob이 12초에 Complete(68편), 앱 뒤 역순 종료(70편)
그 도우미가 준비된 뒤에 앱 시작위 + startupProbestartupProbe 성공 뒤 init2와 app 시작, readiness는 안 막음(70편)
Never 파드에서 특정 exit code만 제자리 재시작containers[]의 restartPolicy: Never + restartPolicyRulesexit 42만 2회 재시작 뒤 Succeeded
Never 파드에서 실패한 컨테이너만 재시작containers[]의 restartPolicy: OnFailureexit 1 두 번 뒤 Succeeded
Never·OnFailure 파드의 보통 컨테이너를 계속 띄우기쓰지 않아요파드가 75초 넘게 Running, API 경고 없음
Always 파드에서 한 번만 도는 작업보통 init 컨테이너containers에 Never로 두면 READY 1/2 NotReady
컨테이너 하나의 실패에 파드째 제자리 재시작restartPolicyRules의 RestartAllContainers (KEP-5532)실험하지 않음
📖 용어: 베타 기능 게이트
베타 기능은 보통 기본으로 켜져 있지만 GA 전이라 동작이나 필드가 바뀔 수 있어요. ContainerRestartRules(1.35)와 RestartAllContainersOnContainerExits(1.36)는 v1.37.2에서 베타예요. 쓰기 전에 클러스터에서 게이트가 켜져 있는지 확인해요.

API 서버가 경고를 주지 않는다는 점이 이 표에서 가장 중요해요. 파드가 끝날 수 없는 조합도, 파드를 NotReady로 만드는 조합도 모두 그대로 받아들여졌어요. 매니페스트에 컨테이너 수준 restartPolicy를 적었다면 그 컨테이너가 containers에 있는지 initContainers에 있는지, 파드의 restartPolicy와 어느 쪽으로 다른지를 직접 확인해야 해요.

💡 리뷰할 때 확인할 두 줄
• containers[] 아래에 restartPolicy: Always가 있고 파드가 Never나 OnFailure라면, 사이드카를 의도한 것인지 묻고 initContainers로 옮겨요.
• restartPolicyRules가 있다면 같은 컨테이너에 restartPolicy가 함께 적혀 있는지, 재시작할 exit code를 앱이 실제로 그 의미로 쓰는지 확인해요.

📝 정리

보통 컨테이너에 restartPolicy: Always를 줘도 사이드카가 되지 않아요. kubelet은 initContainers에 있고 Always인 컨테이너만 사이드카로 다뤄요. Never 파드의 보통 컨테이너 helper에 Always를 주자 app이 10초에 끝났는데도 생성 75초 뒤까지 파드는 Running이었고 STATUS 칸만 Completed로 보였어요. API 서버는 이 조합에 경고를 주지 않았어요.

보통 컨테이너의 restartPolicy와 restartPolicyRules는 사이드카가 아니라 비싼 재스케줄을 피하려고 KEP-5307로 열렸어요. exit 42만 제자리 재시작한 파드는 Succeeded로 끝났어요. 2022년에 사이드카 표현으로는 버린 컨테이너별 restartPolicy가 재시작 제어로 돌아왔고 예전 문서가 막겠다던 "낮추는" 덮어쓰기도 지금은 동작해요. 종료 중 사이드카 재시작(KEP-4438)은 1.38 알파 목표로 아직 열려 있어요.

같은 restartPolicy: Always라도 파드에서는 끝나지 않음, initContainers에서는 사이드카, containers에서는 파드를 붙잡는 컨테이너예요. 무엇이 사이드카인지를 정하는 것은 필드의 값이 아니라 그 필드를 적은 자리예요.
