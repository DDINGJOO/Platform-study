1. OCI는 Open Container Initiative의 약자이고 스펙은 세 개다

첫 메모에 적은 "OCI가 뭐의 약자야?"라는 질문의 답은 Open Container Initiative예요. OCI 소개 페이지에 따르면 OCI는 컨테이너 형식과 런타임의 업계 표준을 만들려고 리눅스 재단 아래에 꾸린 프로젝트예요. 2015년 6월 22일에 Docker와 CoreOS 같은 회사들이 시작했고 Docker는 이때 자사의 컨테이너 형식과 런타임 runC를 OCI에 기증했어요. 이 runC가 지금의 runc 저장소이고 README 첫 줄에도 "runc는 OCI 스펙에 따라 리눅스에서 컨테이너를 만들고 실행하는 명령줄 도구"라고 적혀 있어요.

📖 용어: OCI (Open Container Initiative)
컨테이너를 어떻게 실행하는지, 이미지가 어떤 모양인지, 레지스트리와 이미지를 어떻게 주고받는지를 정한 표준 묶음이에요. 지금은 runtime-spec, image-spec, distribution-spec 세 스펙이 있어요. 이 표준만 맞추면 이미지를 만든 도구와 실행하는 도구가 달라도 됩니다.

세 스펙이 각각 무엇을 정하고 우리 노드의 어디에서 보였는지 표로 정리하면 이래요.

스펙정하는 것 (OCI 소개 페이지)worker1에서 보인 곳
runtime-spec디스크에 풀어 둔 "파일시스템 번들"을 어떻게 실행할지runc --version의 spec: 1.3.0, 컨테이너마다 있는 config.json(2절)
image-spec이미지 매니페스트, 레이어, 이미지 설정의 형식nginx:1.29 이미지의 mediaType application/vnd.oci.image.index.v1+json
distribution-spec컨테이너 이미지를 배포하는 API이번에는 따로 확인하지 않았어요

먼저 runtime-spec이에요. worker1에서 containerd와 runc의 버전을 확인했어요.

worker1$ containerd --version; runc --version containerd github.com/containerd/containerd/v2 v2.4.1 f2551031d7276a770f65f98c9b52e57e7dad07e8 runc version 1.5.2 commit: v1.5.2-0-g29dd3dc spec: 1.3.0 go: go1.26.8 libseccomp: 2.6.0

→ runc 1.5.2가 따르는 OCI runtime-spec의 버전이 1.3.0이라는 뜻이에요. runtime-spec v1.3.0은 2025-11-04에 나온 릴리스예요.

다음은 image-spec이에요. 노드에 받아 둔 이미지마다 매니페스트의 형식(mediaType)을 찍어 봤어요.

worker1$ sudo ctr -n k8s.io images ls # REF와 TYPE 열만 골라 봄 docker.io/library/nginx:1.25.1-alpine application/vnd.docker.distribution.manifest.list.v2+json docker.io/library/nginx:1.29 application/vnd.oci.image.index.v1+json quay.io/calico/node:v3.33.0 application/vnd.docker.distribution.manifest.list.v2+json registry.k8s.io/kube-proxy:v1.37.2 application/vnd.docker.distribution.manifest.list.v2+json registry.k8s.io/pause:3.10.2 application/vnd.docker.distribution.manifest.list.v2+json

→ 다섯 개 가운데 nginx:1.29만 OCI 형식의 이미지 인덱스였고 나머지 넷은 도커 형식의 매니페스트 리스트였다는 뜻이에요. 둘 다 여러 플랫폼(CPU 아키텍처)용 매니페스트를 묶은 목록이에요.

형식이 두 가지로 섞여 있었지만 containerd는 둘 다 받아 두었고 myweb 파드는 도커 형식인 nginx:1.25.1-alpine으로 돌고 있었어요. image-spec의 media-types.md 호환성 표에는 도커의 manifest list v2가 OCI 이미지 인덱스와 비슷한 형식으로 올라 있어요. 차이로 적힌 것은 annotations, urls 같은 몇몇 필드가 OCI 쪽에만 있다는 점뿐이에요.

dockershim이 빠졌는데 도커로 만든 이미지가 도는 이유

이 표를 보면 자주 듣는 질문 하나에 답할 수 있어요. "쿠버네티스 1.24에서 도커 지원이 빠졌다는데 도커로 빌드한 이미지는 어떻게 돌아요?" dockershim 제거 FAQ에 따르면 초기 쿠버네티스는 Docker Engine 하나만 런타임으로 썼어요. 그 뒤 여러 런타임을 지원하려고 CRI라는 규약을 만들었는데 Docker Engine은 CRI를 구현하지 않았어요. 그래서 쿠버네티스는 둘을 잇는 코드를 kubelet 안에 넣었는데 이 코드가 dockershim이에요. 처음부터 임시방편으로 만든 코드였고 v1.24에서 실제로 빠졌어요.

같은 FAQ의 "기존 컨테이너 이미지는 계속 동작하나요?"라는 항목에는 "Yes, the images produced from docker build will work with all CRI implementations."라고 적혀 있어요. 빠진 것은 kubelet과 Docker Engine을 잇던 코드이고 이미지 형식은 OCI 표준 덕분에 어느 런타임에서나 그대로 읽혀요. 우리 노드에서 도커 형식 매니페스트 리스트로 받은 nginx와 calico/node가 containerd 위에서 돌고 있는 것이 그 예예요.

2. kubelet에서 커널까지: CRI, shim, runc, OCI 번들

OCI가 정하는 것은 맨 아래 두 층이에요. 그 위에는 쿠버네티스와 containerd가 정한 규약이 따로 있어요. worker1에서 확인한 내용을 층으로 쌓아 그리면 그림 1과 같아요.

그림 1. 층마다 규약을 정한 쪽이 다르다. CRI는 쿠버네티스가, shim API는 containerd가, 번들 형식은 OCI가 정했다

맨 위의 kubelet은 컨테이너를 직접 만들지 않아요. CRI 문서에 따르면 kubelet은 gRPC 클라이언트로 컨테이너 런타임에 붙고 쿠버네티스 1.26부터는 런타임이 v1 CRI API를 지원하지 않으면 노드를 등록하지 않아요. 우리 kubelet이 붙는 곳은 설정에 적힌 containerRuntimeEndpoint: unix:///var/run/containerd/containerd.sock이에요. 이 소켓으로 어떤 호출이 어떤 순서로 오가는지는 27편에서 containerd 로그로 따라가요.

📖 용어: CRI (Container Runtime Interface)
kubelet과 컨테이너 런타임이 주고받는 gRPC 규약이에요. 쿠버네티스 프로젝트가 정했고 "파드 샌드박스를 만들어라", "이미지를 받아라", "컨테이너를 시작해라" 같은 호출이 들어 있어요. 이 규약을 지키는 런타임이면 containerd가 아니어도 kubelet과 함께 쓸 수 있어요.

containerd도 컨테이너를 직접 띄우지 않아요. containerd의 runtime v2 문서를 보면 둘째 문단 첫 문장이 "containerd 데몬은 컨테이너를 직접 띄우지 않는다"예요. containerd는 이미지를 받아 디스크에 펼치고 컨테이너의 루트 파일시스템과 설정을 준비한 다음 런타임을 불러요. 어떤 런타임을 부를지는 설정에 정해져 있어요.

worker1$ containerd config dump | grep -nE 'default_runtime_name|runtime_type|BinaryName|SystemdCgroup' 59: default_runtime_name = 'runc' 65: runtime_type = 'io.containerd.runc.v2' 81: BinaryName = '' 89: SystemdCgroup = true

→ 기본 런타임의 이름은 runc이고 그 종류(runtime_type)는 io.containerd.runc.v2라는 뜻이에요. 같은 문서에 따르면 이 종류에 해당하는 실행 파일이 containerd-shim-runc-v2이고 containerd는 이 shim을 띄워 ttRPC로 요청을 보내요. shim은 다시 runc 실행 파일을 불러 컨테이너를 만들어요. BinaryName이 비어 있으면 shim은 기본값인 runc를 써요(go-runc의 DefaultCommand). SystemdCgroup은 5절에서 다시 봐요.

📖 용어: 런타임 shim (containerd-shim-runc-v2)
containerd와 runc 사이에서 컨테이너를 맡는 작은 프로세스예요. containerd의 요청을 ttRPC로 받아 runc를 부르고 자신은 컨테이너 프로세스의 부모로 남아 컨테이너가 끝나면 종료 상태를 거둬요. runtime v2 문서에 따르면 쿠버네티스가 띄운 컨테이너는 파드 샌드박스 ID 라벨로 묶이기 때문에 한 파드의 컨테이너를 shim 하나가 모두 맡아요.

shim과 runc를 나눈 이유도 문서에 적혀 있어요. shim이 containerd와 통신하는 일을 맡고 실제 컨테이너 생성은 OCI runtime-spec을 구현한 별도 엔진에 맡기면 엔진을 바꾸기 쉽다는 거예요. containerd의 CRI 설정 문서에는 같은 runtime_type(io.containerd.runc.v2)에 BinaryName만 /usr/local/bin/crun으로 바꿔 crun이라는 다른 OCI 런타임을 쓰는 예가 실려 있어요.

runc가 읽는 OCI 번들

그럼 shim이 runc에게 넘기는 것은 무엇일까요? worker1의 myweb 컨테이너에 해당하는 디렉터리를 열어 봤어요.

그림 2. 컨테이너마다 config.json과 rootfs가 있고 config.json의 ociVersion은 runc가 따르는 스펙 버전과 같은 1.3.0이었다

runtime-spec의 bundle.md에 따르면 번들은 두 가지로 이루어져요. 하나는 번들 디렉터리 맨 위에 반드시 있어야 하는 config.json이고 다른 하나는 config.json의 root.path가 가리키는 컨테이너의 루트 파일시스템이에요. 화면의 config.json과 rootfs가 그 둘이고 나머지 파일(bootstrap.json, init.pid, log.json, options.json 등)은 OCI가 정한 것이 아니라 containerd와 shim이 쓰는 파일이에요.

📖 용어: OCI 번들 (filesystem bundle)
OCI 런타임이 컨테이너 하나를 실행하는 데 필요한 것을 모은 디렉터리예요. 실행할 명령, 나눌 네임스페이스, 자원 한도를 적은 config.json과 컨테이너의 루트 파일시스템이 들어 있어요. runc는 이 디렉터리만 보고 컨테이너를 만들어요.

config.json에 든 값도 저마다 출처가 있어요.

· ociVersion 1.3.0: runtime-spec의 config.md에 따르면 이 번들이 따르는 runtime-spec 버전이에요. runc의 spec: 1.3.0과 같아요.
· process.args: myweb Deployment에는 command와 args가 비어 있었어요. 그래서 nginx:1.25.1-alpine 이미지 설정의 Entrypoint(/docker-entrypoint.sh)와 Cmd(nginx -g daemon off;)가 이어 붙어 들어갔어요.
· namespaces: pid, ipc, uts, mount, network, cgroup 여섯 개를 따로 나눠요. 27편에서 컨테이너 안의 PID 1과 hostname으로 이 격리를 확인해요.
· cgroupsPath: runc의 systemd 문서가 정한 [slice]:[prefix]:[name] 형식이에요. 이 컨테이너는 kubepods-besteffort-pod265764f4….slice 아래 cri-containerd-<컨테이너 ID>.scope라는 systemd 단위에 들어가요. myweb에는 requests가 없어서 BestEffort 자리에 놓였고 CPU 가중치(shares)는 2로 들어갔어요.

OCI가 정한 것은 runc가 읽는 번들의 모양이고 그 번들을 만들어 runc에게 건네는 것은 containerd와 shim이에요. runc는 번들을 읽어 컨테이너를 만들고 시작한 뒤에는 상주하지 않아요. 다음 절의 pstree에 runc 프로세스가 하나도 없는 것이 그 흔적이에요.

3. pstree로 보면 컨테이너의 부모는 kubelet도 containerd도 아니다

"마스터 들어가서 pstree 쳐 보는 것도 중요할 듯"이라는 메모대로 마스터에서 pstree -T를 실행했어요. pstree는 프로세스를 부모와 자식 관계대로 나무 모양으로 그려 주고 -T는 스레드를 숨기는 옵션이에요.

그림 3. kubelet과 containerd 아래에는 아무것도 없고 컨테이너는 전부 containerd-shim 아래에 있었다

systemd 바로 아래에 containerd와 kubelet이 따로 있어요. 1편에서 본 대로 둘 다 systemd가 띄운 서비스예요. 그런데 etcd, kube-apiserver 같은 컨테이너 프로세스는 이 둘 아래가 아니라 containerd-shim 아래에 있고 shim은 다시 systemd 바로 아래에 있어요. 부모 PID(PPID)로 다시 확인하면 이래요.

containerd pid=808 부모 pid=1 (systemd) kubelet pid=1519 부모 pid=1 (systemd) kube-apiserver pid=8689 부모 pid=8636 (containerd-shim) etcd pid=1801 부모 pid=1589 (containerd-shim) kube-scheduler pid=9117 부모 pid=9068 (containerd-shim) kube-controller-manager pid=9677 부모 pid=9612 (containerd-shim) kube-proxy pid=2014 부모 pid=1906 (containerd-shim)

→ containerd와 kubelet의 부모는 PID 1(systemd)이고 컨테이너 프로세스 다섯 개의 부모는 모두 containerd-shim이라는 뜻이에요.

shim마다 자식 프로세스를 세어 보면 shim 하나가 파드 하나를 맡는다는 것도 알 수 있어요.

shim(1589) etcd-k8s-master 자식: pause(1695) etcd(1801) shim(1906) kube-proxy-xjg9n 자식: pause(1931) kube-proxy(2014) shim(1947) calico-node-tvx2h 자식: pause(1977) runsvdir(2402) shim(2966) node-exporter-47twj 자식: pause(2992) node_exporter(3033) shim(8636) kube-apiserver-k8s-master 자식: pause(8661) kube-apiserver(8689) shim(9068) kube-scheduler-k8s-master 자식: pause(9093) kube-scheduler(9117) shim(9612) kube-controller-manager-k8s-master 자식: pause(9639) kube-controller(9677)

→ 마스터의 파드 일곱 개에 shim이 일곱 개였고 shim마다 pause 하나와 본 컨테이너의 프로세스 하나가 자식으로 붙어 있다는 뜻이에요. calico-node만 본 프로세스가 runsvdir이고 그 아래에 calico 프로세스 셋과 BIRD가 있어요(30편).

📖 용어: pause 컨테이너
파드마다 본 컨테이너보다 먼저 뜨는 아주 작은 컨테이너예요. containerd는 이 컨테이너로 파드 샌드박스(파드 안 컨테이너들이 함께 쓰는 실행 환경, 27편)를 만들어요. 이 클러스터에서 쓰는 이미지는 registry.k8s.io/pause:3.10.2예요.

PID 번호에도 그날 있었던 일이 남아 있어요. etcd(1801)와 kube-proxy(2014)는 번호가 작아요. 마스터는 14:41:21에 부팅했고 두 프로세스는 14:41:37과 14:41:40에 뜬 뒤 그대로 돌고 있었어요. kube-apiserver(8689), kube-scheduler(9117), kube-controller-manager(9677)는 번호가 커요. 셋의 시작 시각은 14:56~14:57이었어요. 20편에서 이 셋의 정적 파드 파일을 옮겼다가 되돌리는 실험을 하면서 새로 뜬 프로세스예요. systemd 아래의 buildkitd와 containerd-star는 쿠버네티스와 상관없는 서비스였어요. 각각 buildkit.service와 stargz-snapshotter.service라는 systemd 단위였고 containerd-star는 실행 파일 containerd-stargz-grpc의 이름이 pstree에서 15자로 잘려 보인 것이에요. kube-controller-manager가 kube-controller로 보이는 것도 같은 이유예요.

systemd 쪽에서 봐도 같은 숫자가 나와요. 마스터의 systemd 단위 목록에는 cri-containerd-<컨테이너 ID>.scope가 14개 있었어요. shim 7개에 pause와 본 컨테이너가 하나씩 있으니 7 × 2 = 14로 맞아요. etcd 컨테이너의 cgroup은 /kubepods.slice/kubepods-burstable.slice/kubepods-burstable-pod5040…slice/cri-containerd-ee65….scope였어요.

shim의 부모가 systemd인 이유

runtime v2 문서에는 containerd가 shim을 띄우는 흐름이 이렇게 적혀 있어요. containerd가 shim 실행 파일을 start 명령으로 부르면 shim은 ttRPC 요청을 받을 새 프로세스를 하나 만들고 그 소켓 주소를 containerd에 알려 준 뒤 끝나요. containerd가 직접 띄운 프로세스는 끝나고 새로 만든 프로세스만 남는 셈이에요. 리눅스에서는 부모가 먼저 끝나면 그 프로세스의 부모가 PID 1로 바뀌어요. 조상 가운데 서브리퍼(고아가 된 자손 프로세스를 대신 거두겠다고 커널에 등록한 프로세스)가 있으면 그 프로세스가 새 부모가 되는데 containerd는 그런 등록을 하지 않았는지 shim은 systemd 아래로 넘어갔어요. pstree에서 shim이 systemd 바로 아래에 보인 것은 이 때문이에요.

컨테이너 프로세스의 부모가 shim인 이유도 문서에 나와 있어요. containerd-shim-runc-v2는 서브리퍼 역할을 맡아 끝난 컨테이너 프로세스를 거둬요. runc는 컨테이너를 만든 뒤 끝나기 때문에 컨테이너 프로세스의 부모 자리에는 shim이 남아요.

그림 4. 컨테이너는 kubelet이나 containerd의 자식이 아니다. shim의 자식이고 shim은 systemd의 자식이다

4. containerd와 kubelet을 재시작해도 nginx의 PID는 그대로였다

그림 4대로라면 kubelet이나 containerd가 내려가도 shim 아래에 있는 프로세스는 영향을 받지 않아야 해요. 마스터 대신 myweb 파드 두 개가 떠 있는 worker1에서 확인했어요. 먼저 이 노드에서도 shim의 부모가 PID 1(systemd)인지 확인했어요. 그런 다음 containerd와 kubelet을 차례로 재시작하면서 2초마다 nginx 마스터 프로세스의 PID, shim 수, containerd와 kubelet의 PID, 파드 IP로 보낸 curl 결과를 찍었어요.

그림 5. containerd와 kubelet의 PID만 바뀌고 nginx PID, shim 수, curl 200은 그대로였다

15:33:18에 containerd를 재시작하자 containerd의 PID가 877에서 26048로 바뀌었어요. 15:33:24에 kubelet을 재시작하자 kubelet의 PID가 1673에서 26209로 바뀌었어요. 그동안 2초마다 찍은 일곱 줄 내내 nginx 마스터의 PID 10360과 10492, shim 9개, curl 응답 200은 바뀌지 않았어요. 마지막에 확인한 myweb 파드 두 개의 RESTARTS도 0이었고 노드는 Ready였어요. 화면의 loadgen이 RESTARTS 1인 것은 이 실험과 상관없어요. loadgen도 worker1에 떠 있는데 마지막 종료 시각(finishedAt)이 05:41:40Z, 한국 시각으로 14시 41분 40초였어요. worker1이 부팅한 14시 41분 34초에서 6초 뒤예요.

이유는 두 가지예요. 첫째, containerd가 내려가도 shim과 컨테이너 프로세스는 containerd의 자식이 아니라서 같이 끝나지 않아요. runtime v2 문서에는 containerd가 부팅할 때 shim에 다시 연결한다는 문장이 있어요. 번들이 디스크에 남아 있는데 shim에 연결할 수 없을 때만 그 컨테이너의 자원을 정리하는 delete 명령을 부른다고 해요. 실제로 약 9분 뒤 같은 노드에서 myweb의 nginx를 죽였을 때 새로 뜬 containerd(26048)는 원래 샌드박스 안에 컨테이너를 다시 만들었어요(27편).

둘째, kubelet은 처음부터 어떤 컨테이너의 부모도 아니에요. kubelet은 CRI로 containerd에게 요청을 보내는 쪽이라서 kubelet 프로세스가 바뀌어도 이미 떠 있는 컨테이너에는 영향이 없어요. 약 9분 뒤(15:42)에 확인했을 때 kubelet의 10250 포트를 잡고 있던 프로세스도 재시작한 kubelet(26209)이었어요(5절).

컨테이너의 수명을 책임지는 것은 shim이고 kubelet과 containerd는 shim에게 일을 시키는 쪽이라서 둘이 잠깐 내려가도 컨테이너는 그대로 돌아요. 반대로 말하면 둘이 내려가 있는 동안에는 일을 시킬 쪽이 없어요. 이 한계는 6절에서 정리해요.

5. kubelet 설정과 포트, 그리고 미러 파드를 지워도 그대로인 정적 파드

"워커 노드 구성 요소 중에 kubelet도 있대"라는 메모를 남긴 뒤 worker1의 kubelet 설정 파일에서 몇 줄을 골라 봤어요.

worker1$ sudo grep … /var/lib/kubelet/config.yaml anonymous: enabled: false webhook: enabled: true mode: Webhook cgroupDriver: systemd clusterDNS: - 10.96.0.10 clusterDomain: cluster.local rotateCertificates: true staticPodPath: /etc/kubernetes/manifests

→ 위 다섯 줄은 kubelet API의 인증과 인가 설정이고 아래 줄들은 cgroup 드라이버, 클러스터 DNS, 인증서 갱신, 정적 파드 폴더 설정이라는 뜻이에요. 하나씩 풀면 이래요(kubelet 설정 레퍼런스).

· cgroupDriver: systemd: kubelet이 cgroup을 다룰 때 systemd를 거친다는 뜻이에요. 2절의 containerd 설정 SystemdCgroup = true와 짝을 이루는 설정이에요.
· clusterDNS, clusterDomain: kubelet은 모든 컨테이너가 노드의 DNS 서버 대신 10.96.0.10을 쓰고 cluster.local을 검색 도메인에 더하도록 설정해요. 10.96.0.10은 kube-dns Service의 주소예요(29편).
· rotateCertificates: true: kubelet이 자신의 클라이언트 인증서를 certificates.k8s.io API에 새로 요청해 바꾼다는 뜻이에요.
· staticPodPath: 정적 파드 파일을 읽는 폴더예요(1·5편). kubelet은 이 폴더를 주기적으로 훑고 그 간격(fileCheckFrequency)의 기본값은 20초예요.

📖 용어: cgroup 드라이버
kubelet과 컨테이너 런타임이 cgroup(프로세스 묶음마다 CPU·메모리 한도를 거는 리눅스 기능)을 만들고 고치는 방식이에요. cgroupfs와 systemd 두 가지가 있어요. 컨테이너 런타임 문서에서는 systemd를 init으로 쓰는 노드라면 둘 다 systemd 드라이버를 쓰라고 권하고 kubelet을 systemd로 정했다면 런타임도 반드시 systemd로 맞추라고 해요.

kubelet이 여는 포트도 봤어요.

worker1$ sudo ss -ltnp | grep kubelet 127.0.0.1:10248 users:(("kubelet",pid=26209,fd=19)) *:10250 users:(("kubelet",pid=26209,fd=16)) master$ curl -sk https://192.168.104.3:10250/pods → 401 worker1$ curl -s http://127.0.0.1:10248/healthz → ok

→ 10250은 모든 주소에서 요청을 받고 10248은 노드 자신(127.0.0.1)에서 온 요청만 받으며 인증서 없이 10250에 요청하면 401이 돌아온다는 뜻이에요. 두 포트를 잡은 프로세스는 4절에서 재시작한 kubelet(26209)이에요.

설정 레퍼런스에 따르면 10250(port)은 kubelet이 API를 제공하는 포트의 기본값이고 10248(healthzPort)은 localhost용 상태 확인 포트의 기본값이에요. 포트 문서에도 10250은 컨트롤 플레인과 노드 자신이 쓰는 Kubelet API로 적혀 있어요. 컨트롤 플레인과 노드 통신 문서에 따르면 API 서버는 파드 로그 가져오기, attach, port-forward를 할 때 이 포트로 kubelet에 붙어요(19편). 401이 나온 것은 anonymous.enabled: false 설정 때문이에요. kubelet 인증·인가 문서에 따르면 kubelet은 기본 설정에서 인증되지 않은 요청을 익명 사용자의 요청으로 받는데 익명 접근을 끄면 그런 요청에 401 Unauthorized로 응답해요. API 서버는 같은 상황에서 익명 사용자로 받아들인 뒤 인가에서 403으로 거절했어요(19편). 같은 "인증서 없는 요청"을 kubelet은 인증 단계에서 막았고 API 서버는 인가 단계에서 막았어요.

미러 파드를 지우면 무엇이 지워질까

1편에서 정적 파드와 미러 파드를 소개하면서 "미러 파드를 kubectl delete로 지워도 kubelet은 정적 파드를 지우지 않는다"는 공식 문서 문장을 옮겼어요. 이번에는 마스터의 kube-scheduler로 직접 확인해 봤어요. API 서버에 보이는 kube-scheduler 파드는 kubelet이 정적 파드를 API 서버에 보여 주려고 만든 미러 파드예요.

그림 6. API 서버의 파드는 지워졌다가 새 uid로 다시 생겼고 kube-scheduler 프로세스(9117)는 한 번도 바뀌지 않았다

지우기 전 파드에는 config.source=file(파일에서 온 파드), config.mirror=…(미러 파드 표시) annotation이 붙어 있었고 소유자(ownerReferences)는 Node/k8s-master였어요. 15:42:42에 지우자 파드는 Terminating이 됐고 deletionTimestamp는 30초 뒤인 06:43:12Z(grace 30)로 찍혔어요. 그런데 그 기한보다 먼저 15:43:03에 새 uid(c4e87283)의 파드가 Pending 상태로 나타났고 6초 뒤인 15:43:09에는 Running이었어요. 그동안 마스터의 kube-scheduler 프로세스는 처음부터 끝까지 PID 9117이었어요.

API 서버에서 지운 것은 미러 파드라는 객체 하나뿐이었어요. 이 프로세스를 띄우는 원본은 /etc/kubernetes/manifests/kube-scheduler.yaml 파일이고 kubelet은 그 파일이 있는 한 정적 파드를 계속 띄워 두면서 미러 파드만 다시 만들었어요. 20편에서 컨트롤 플레인 구성 요소를 멈출 때 kubectl delete가 아니라 매니페스트 파일을 폴더 밖으로 옮겨야 했던 것도 이 때문이에요.

6. 업그레이드할 때 믿어도 되는 것과 조심할 것

여기까지 관찰한 내용과 문서를 합치면 그림 7과 같아요.

그림 7. 재시작은 shim 덕분에 견디지만 kubelet이 오래 멈추거나 버전이 바뀌면 컨테이너도 영향을 받는다

믿어도 되는 것은 그림의 위쪽 세 줄이에요. containerd나 kubelet을 같은 버전으로 재시작했을 때도 미러 파드를 지웠을 때도 이미 떠 있는 컨테이너는 그대로였어요. 이 결과는 설정 한 줄을 바꾸고 systemctl restart를 하는 정도로는 워크로드가 끊기지 않는다는 근거가 돼요.

아래쪽 두 줄은 한계예요. 하나는 kubelet이 멈춰 있는 시간이에요. 컨테이너가 죽었을 때 다시 띄우는 것도 새 파드의 컨테이너를 만드는 것도 kubelet이 하는 일이라서 kubelet이 멈춘 동안에는 아무도 그 일을 하지 않아요. 25편에서 worker3의 kubelet을 멈췄을 때는 노드가 41초까지 Ready였다가 52초에 Ready=Unknown이 되고 unreachable taint가 붙었어요. 그동안 파드로 보낸 curl 요청은 계속 200 응답을 받았으니 컨테이너는 살아 있었어요. 하지만 taint 문서에 따르면 쿠버네티스가 파드에 기본으로 붙이는 toleration은 300초짜리라서 그 시간이 지나면 파드가 그 노드에서 쫓겨나요.

다른 하나는 버전을 올리는 경우예요. kubeadm 업그레이드 문서에 따르면 kubelet의 마이너 버전을 올릴 때는 그 노드를 먼저 drain해야 하고 업그레이드 뒤에는 컨테이너 명세의 해시 값이 바뀌어서 모든 컨테이너가 다시 시작돼요. 그래서 재시작을 견딘다는 관찰을 업그레이드에 그대로 적용하면 안 돼요.

💡 실무에서는: 노드 하나씩 비우고 올려요
• kubeadm의 리눅스 워커 노드 업그레이드 문서에 나온 순서는 kubeadm·kubectl 패키지 업그레이드 → sudo kubeadm upgrade node → kubectl drain <노드> --ignore-daemonsets → kubelet 패키지 업그레이드 → systemctl daemon-reload와 systemctl restart kubelet → kubectl uncordon <노드>예요
• drain으로 파드를 다른 노드로 옮겨 두면 업그레이드 중 컨테이너가 다시 시작돼도 서비스 요청은 다른 노드의 파드가 처리해요
• 설정만 바꾸는 재시작이라면 drain하지 않아도 컨테이너는 그대로였어요. 다만 kubelet이 내려가 있는 시간은 짧게 잡아요
⚠️ 주의: 재시작 타이밍과 shim
• 파드 수명 주기 문서에 따르면 파드가 종료 유예 시간을 기다리는 도중 kubelet이나 런타임의 관리 서비스가 재시작되면 유예 시간이 처음부터 다시 시작돼요. 지우는 중인 파드가 있으면 재시작을 미뤄요
• runtime v2 문서에는 실행 중인 컨테이너를 맡은 shim이 SIGKILL로 죽은 경우가 따로 적혀 있어요. containerd가 shim과 연결할 수 없으면 그 컨테이너의 자원을 정리해요. 노드에서 프로세스를 정리할 때 containerd-shim까지 죽이지 않도록 해요
• 컨테이너 런타임 문서는 이미 클러스터에 조인한 노드의 cgroup 드라이버를 바꾸는 일을 "민감한 작업"이라고 경고해요. 기존 파드의 샌드박스를 다시 만들 때 오류가 날 수 있고 kubelet을 재시작해도 안 풀릴 수 있다고 해요

containerd 쪽에도 업그레이드할 때 챙겨 볼 것이 하나 있었어요. 2절에서 containerd config dump를 실행했을 때 출력보다 먼저 이런 경고가 두 줄 찍혔어요.

level=warning msg="Configuration migrated from version 2, use `containerd config migrate` to avoid migration"

→ 설정 파일이 옛 형식(version 2)이라서 containerd가 읽을 때마다 최신 형식으로 바꿔서 쓰고 있다는 뜻이에요. containerd v2.4.1의 RELEASES.md에 따르면 최신 설정 형식은 version 4이고 containerd는 시작할 때마다 설정을 자동으로 변환하지만 파일은 그대로 둬요. containerd config migrate로 새 형식의 파일을 만들 수 있지만 그렇게 바꾼 파일은 옛 containerd에서 못 읽을 수 있으니 되돌릴 일이 없다고 확신할 때 바꾸라고 해요. 같은 문서에는 메이저 버전 사이의 업그레이드는 호환을 보장하지 않는다는 내용도 있어요.

✍️ 오늘의 요약
컨테이너의 부모는 kubelet도 containerd도 아니고 파드마다 하나씩 뜨는 containerd-shim이에요.

OCI는 Open Container Initiative의 약자이고 runtime-spec, image-spec, distribution-spec을 정해요. kubelet은 CRI로 containerd에 요청해요. containerd는 shim을 띄우고 shim은 runc에게 OCI 번들(config.json과 rootfs)을 넘겨요. shim의 부모는 systemd라서 worker1에서 containerd(877→26048)와 kubelet(1673→26209)을 재시작해도 nginx PID 10360·10492와 curl 응답 200은 그대로였어요. 미러 파드를 지워도 kube-scheduler(9117)는 그대로였고 원본은 매니페스트 파일이었어요. 다만 kubelet이 오래 멈춰 있으면 노드가 Unknown이 돼요. 또 kubeadm 문서에 따르면 업그레이드 뒤에는 모든 컨테이너가 다시 시작되니 kubelet 마이너 버전은 노드를 drain한 뒤 올려요. 재시작을 견디게 만든 것은 kubelet이 아니라 shim이에요.
