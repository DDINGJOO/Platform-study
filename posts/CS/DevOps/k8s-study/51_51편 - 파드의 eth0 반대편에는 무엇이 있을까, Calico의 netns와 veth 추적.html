파드 안에서는 eth0인데 노드에서는 cali0cbfd12677e예요. 둘 다 MTU는 1480이고, 노드에서 파드 IP로 가는 길도 이 cali 장치를 가리켜요. 그런데 노드에는 끝에 @if3가 붙은 cali 장치가 여러 개 있었어요. 이름 뒤의 숫자만 보고 어느 파드와 연결됐는지 고르면 틀릴 수 있어요.

worker1에 앱 컨테이너 두 개를 가진 일반 파드 pair와 hostNetwork 파드 host를 만들었어요. 프로세스가 속한 네트워크 네임스페이스부터 양쪽 인터페이스의 인덱스, 경로와 통신까지 대조했어요. 환경은 Lima VM 네 대, Kubernetes v1.37.2, containerd 2.4.1, Calico v3.33.0이에요.

43편에서 pause가 파드의 네트워크를 유지하는 이유를 봤다면 이번에는 그 안과 밖에 실제로 무엇이 만들어졌는지 확인해요. IPIP Always인 현재 Linux 구성에서 관측한 결과이며, 모든 CNI의 장치 구성이 같다는 뜻은 아니에요.

1. 컨테이너 세 개의 PID는 달라도 네트워크 네임스페이스는 같았어요

pair의 샌드박스 프로세스 PID는 232563, 앱 두 개는 232590과 232625였어요. 각 프로세스의 /proc/PID/ns/net을 readlink로 읽자 세 개 모두 net:[4026532560]이었어요. 호스트와 hostNetwork 파드는 net:[4026531840]이었어요. 이 비교는 같은 worker1 커널 안에서 했어요.

📖 용어: 네트워크 네임스페이스(netns)
리눅스가 네트워크 장치, 주소, 라우팅 테이블, 소켓의 포트 번호 등을 분리하는 단위예요. Kubernetes namespace는 API 자원을 구분하는 범위이므로 같은 이름의 개념이 아니에요.

Linux 문서가 설명하는 격리 단위를 프로세스에서 확인한 거예요. Kubernetes 문서도 같은 파드의 컨테이너들이 네트워크 네임스페이스를 공유한다고 설명해요. 앱 컨테이너 개수만큼 eth0와 Pod IP가 생기는 구조가 아니에요.

# worker1에서 샌드박스와 앱 PID를 조회한 뒤 실행했어요. sudo readlink /proc/232563/ns/net net:[4026532560] sudo readlink /proc/232590/ns/net net:[4026532560] sudo readlink /proc/232625/ns/net net:[4026532560]

PID 세 개가 같은 네트워크 공간을 사용한다는 뜻이에요. PID는 실행마다 달라지므로 그대로 복사하지 않고 CRI에서 현재 값을 찾아야 해요. 실험 스크립트는 crictl pods로 샌드박스 ID를 고른 뒤 inspectp의 PID, ps와 inspect의 앱 PID를 읽어요.

그림 1. 일반 파드와 hostNetwork 파드는 같은 방식으로 네트워크를 격리하지 않아요.

2. eth0의 상대 인덱스 64가 호스트의 cali 장치를 가리켰어요

샌드박스 PID로 nsenter -t 232563 -n ip -j -d link show를 실행했어요. 호스트에 설치된 ip 명령을 사용하되 네트워크 네임스페이스만 바꿔 조회하는 방법이에요. 컨테이너 이미지에 ip 명령이 없어도 조사할 수 있어요.

📖 용어: veth pair
서로 연결된 두 가상 네트워크 장치예요. 한쪽으로 보낸 패킷을 다른 쪽에서 받으며, 양 끝을 서로 다른 네트워크 네임스페이스에 둘 수 있어요.

실제 링크 종류도 양쪽 모두 veth였어요. veth 문서에서 설명하는 쌍을 이름 추측 대신 양쪽 인덱스로 찾았어요.

📖 용어: ifindex와 상대 인덱스
ifindex는 해당 네트워크 네임스페이스 안의 장치 번호예요. 이번 veth JSON의 link_index는 반대편 장치의 인덱스를 나타냈어요. 같은 숫자가 다른 netns에 반복될 수 있어요.
조회 위치 장치 ifindex link_index Pod netns eth0 3 64 worker1 호스트 cali0cbfd12677e 64 3 sudo ethtool -S cali0cbfd12677e NIC statistics: peer_ifindex: 3

표는 양쪽 ip JSON의 필드만 뽑은 것이고, ethtool은 출력 중 peer_ifindex를 발췌했어요. Pod에서 64를 가리키고 호스트의 64번 장치가 다시 Pod의 3을 가리켰어요. ethtool도 3을 확인했어요. 반면 다른 파드의 eth0도 자기 netns에서는 3번일 수 있어요. @if3가 같다는 이유만으로 같은 파드라고 판단하지 않아요.

그림 2. 서로 다른 이름의 장치 두 개가 같은 veth pair라는 근거예요.

실험 원본 verified.json에서 확인한 필드를 정리해 터미널 형태로 렌더링한 화면이에요. 실시간 화면이나 터미널 창을 직접 촬영한 이미지는 아니에요.

3. Pod의 게이트웨이는 노드 IP가 아니라 169.254.1.1이었어요

pair는 10.244.194.79/32를 받았고, 내부 라우팅 표에는 다음 두 줄이 있었어요.

default via 169.254.1.1 dev eth0 169.254.1.1 dev eth0 scope link

두 번째 경로는 169.254.1.1을 eth0 링크에서 찾게 하고 첫 번째 경로는 다른 목적지를 그 주소로 보내게 해요. 노드 IP 192.168.104.3을 게이트웨이로 적은 구성이 아니에요.

📖 용어: proxy ARP
자기 인터페이스에 붙은 주소가 아니더라도 다른 목적지에 대한 ARP 요청에 대신 응답하는 기능이에요. ARP는 같은 링크에서 IPv4 다음 홉의 MAC 주소를 찾을 때 사용해요.

호스트 쪽 cali의 proxy_arp와 forwarding 값은 모두 1이었어요. 통신 뒤 Pod의 이웃 테이블에서 169.254.1.1의 MAC은 ee:ee:ee:ee:ee:ee였고 호스트 cali의 MAC과 같았어요. 호스트 netns의 주소 목록에서 그 cali 장치에 169.254.1.1이 직접 붙어 있지는 않았어요.

Calico v3.33.0의 Linux CNI 코드는 IPv4 주소를 /32로 설정하고, 링크 범위의 169.254.1.1 경로와 기본 경로를 준비해요. 따라서 같은 /26 블록을 배정받았다는 사실을 파드들이 같은 이더넷 브리지에 붙어 있다는 뜻으로 읽으면 안 돼요.

⚠️ 상태 조회와 패킷 관측을 구분해요
여기서는 proxy_arp 설정·주소 목록·이웃 테이블을 코드와 대조했어요. ARP 요청과 응답 자체를 캡처한 실험은 아니므로 패킷을 봤다고 표현하지 않아요.

4. 호스트는 파드 IP를 cali 장치로 보내도록 경로를 골랐어요

호스트에서 ip route get 10.244.194.79를 실행한 결과는 10.244.194.79 dev cali0cbfd12677e src 192.168.104.3이었어요. 파드 안의 eth0 반대편으로 도착하는 경로예요. 이 명령은 커널의 경로 선택을 조회한 것이므로 패킷 전송에 성공했다는 뜻까지 포함하지는 않아요.

📖 용어: 최장 접두사 일치
같은 목적지에 맞는 경로가 여러 개면 더 구체적인 주소 범위를 우선 선택하는 원칙이에요. /32는 IPv4 주소 하나라서 그 주소를 포함하는 /26보다 구체적이에요.

6·30·34편에서 본 노드 블록의 blackhole /26과 개별 파드의 /32 경로는 이 원칙으로 함께 읽어요. 블록 전체의 blackhole이 있다고 그 안의 정상 파드까지 무조건 버리는 것이 아니에요. 이번 조회로도 이 파드의 목적지는 cali 장치가 선택됐어요.

전달 성공은 별도로 확인했어요. worker1에서 pair의 IP로 보낸 ping은 2 packets transmitted, 2 received, 0% packet loss였어요. 이 결과의 범위는 호스트에서 해당 파드로 보낸 ICMP 두 번이에요. 다른 노드 간 통신이나 NetworkPolicy의 모든 포트까지 확인한 결과는 아니에요.

💡 실무에서는 조회 위치부터 적어요
같은 ip route 명령도 Pod netns와 호스트 netns에서 다른 표를 읽어요. 장애 기록에는 노드 이름, 파드 이름·IP, 명령을 실행한 netns를 함께 남겨야 출발지와 경로를 혼동하지 않아요.

5. CNI는 연결을 만들고 Felix는 호스트 상태를 계속 관리해요

장치가 보인다고 그것을 계속 관리하는 프로세스까지 ip link 출력에서 알아낼 수는 없어요. 생성 작업은 설치 버전의 코드와 설정으로, 지속 동작은 구성 요소 문서와 30편의 별도 실험으로 구분해요.

📖 용어: CNI 플러그인
컨테이너 런타임이 호출해 네트워크 연결을 구성하거나 해제하는 실행 프로그램이에요. CNI는 이 호출과 결과의 규약이며, Calico는 이를 구현한 플러그인을 제공해요.

worker1의 CNI 설정에서 플러그인 type은 calico, 그 안의 IPAM type은 calico-ipam이었어요. 뒤에는 portmap도 있었어요. CNI ADD에서 실행되는 경로를 담은 v3.33.0 플러그인 코드와 CNI 규약을 대조하면 역할을 나눌 수 있어요.

  • 런타임과 CNI: containerd가 샌드박스를 준비하는 과정에서 CNI를 호출해요. Calico CNI는 IPAM에 주소 할당을 맡기고, 이번 Linux 코드 경로에서 veth·주소·컨테이너 경로와 호스트 경로를 구성해요. ADD/DEL의 실행 기록은 34편에서 다뤘어요.
  • Felix: 호스트의 인터페이스 설정, 경로, 정책 규칙을 원하는 상태로 관리해요. CNI가 처음 넣는 설정과 Felix가 지속해서 관리하는 설정이 있으므로 모든 경로를 한 프로세스의 일로 단정하지 않아요.
  • BIRD와 confd: BIRD는 BGP로 경로 정보를 교환하고 confd는 설정 변경을 BIRD 구성에 반영해요. BIRD가 일반 Pod 트래픽을 사용자 공간에서 중계하는 구조는 아니에요. 3.33의 IPIP 노드 간 경로 작성 주체와 설정은 30편에서 따로 검증했어요.
  • 리눅스 커널: 만들어진 장치·라우팅·정책에 따라 실제 패킷을 처리해요. 패킷이 매번 CNI 바이너리를 호출하면서 이동하지 않아요.

이 구분은 Calico 구성 요소 문서와 일치해요. 이번에는 BIRD나 Felix를 멈추지 않았고, 그 프로세스의 장애 효과를 새로 측정하지도 않았어요.

그림 3. 생성 시점의 작업과 계속 실행되는 관리, 패킷 전달을 나누면 구성 요소가 연결돼요.

6. 다시 실행할 때는 PID를 찾고, 끝난 뒤에는 장치까지 확인해요

재현 자료에는 파드 두 개의 매니페스트, 생성·조회·삭제를 수행하는 experiment.py, 각 명령의 시각·종료 코드·원문을 담은 commands.json, 양쪽 링크와 netns를 담은 verified.json을 함께 보관했어요. PID와 인터페이스 인덱스는 매번 찾아서 비교하며 글에 적힌 숫자를 상수로 쓰지 않아요.

원본과 재현 스크립트는 실습 자료 디렉터리에 모았어요. 개인 Mac의 Lima 실습 주소를 사용했으며 인증서·토큰·Secret·kubeconfig 내용은 수집하지 않았어요. 호스트 sudo는 netns와 CRI 조회에 필요해요.

마지막에는 이번에 만든 calico-blog-51 namespace만 지웠어요. API에서 NotFound를 확인했고 이후 호스트 링크 목록에 cali0cbfd12677e가 남아 있지 않은 것도 확인했어요. 노드의 경로나 Calico 설정을 직접 지우는 방식으로 정리하지 않았어요.

이 결과는 기본 Linux veth 구성의 관측이에요. 같은 파드에서 보인 DOWN 상태의 tunl0는 링크 목록에 존재한다는 사실만 기록했으며 트래픽에 사용된다고 해석하지 않았어요. hostNetwork, 다른 데이터플레인이나 다른 장치 종류에서는 같은 이름과 인덱스를 기대하지 않고 실제 목록부터 다시 확인해요.

정리
파드의 eth0와 호스트 cali 장치는 서로 다른 네트워크 네임스페이스에 놓인 veth의 양 끝이었어요. 양쪽 인덱스·경로·실제 통신을 각각 확인하니 파드 네트워크의 경계가 보였어요. 주소를 할당하고 연결을 만드는 작업, 호스트 상태를 유지하는 작업, 패킷을 전달하는 작업은 나누어 읽어요.
