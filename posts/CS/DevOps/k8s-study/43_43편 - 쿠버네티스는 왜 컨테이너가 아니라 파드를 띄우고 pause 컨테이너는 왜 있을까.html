1. 파드마다 IP를 주기로 한 것은 Borg의 포트 관리 경험 때문이었다

쿠버네티스를 설계한 사람들 가운데 여럿은 구글 안에서 Borg라는 클러스터 관리 시스템을 운영했어요. 2015년 Borg 논문(Large-scale cluster management at Google with Borg)은 8절에서 운영하며 배운 것을 좋은 것과 나쁜 것으로 나눠 적었는데 나쁜 쪽 첫 항목의 제목이 "One IP address per machine complicates things."예요. 기계마다 IP가 하나뿐이라 일이 복잡해졌다는 뜻이에요.

📖 용어: Borg와 alloc
Borg는 구글이 쿠버네티스보다 먼저 만들어 쓰던 클러스터 관리 시스템이에요. Borg에서 작업 하나를 task라고 부르고 한 기계에 자원을 미리 떼어 두고 그 안에서 task 여러 개를 함께 돌리는 묶음을 alloc(allocation)이라고 불러요. 논문은 웹 서버 task와 그 서버의 로그를 분산 파일 시스템으로 옮기는 logsaver task를 한 alloc에 넣는 예를 들어요.

Borg에서는 한 기계의 모든 task가 기계의 IP 하나를 함께 쓰고 포트 공간도 함께 써요. 논문은 여기서 생긴 일을 네 가지로 적었어요.

· Borg가 CPU·메모리와 함께 포트도 스케줄할 자원으로 다뤄야 했어요.
· task는 포트가 몇 개 필요한지 미리 밝히고 시작할 때 어느 포트를 쓸지 통보받아야 했어요.
· 기계마다 도는 Borglet이 포트 격리를 지켜야 했어요.
· 이름 서비스와 RPC 시스템이 IP뿐 아니라 포트까지 다뤄야 했어요.

2016년 ACM Queue 글(Borg, Omega, and Kubernetes)은 같은 경험을 "하지 말아야 할 것" 목록의 첫 줄로 옮겼어요. 제목은 "Don't make the container system manage port numbers"예요. 컨테이너가 다른 기계로 옮겨 가면 포트가 바뀌고 같은 기계에서 다시 시작할 때도 때로는 바뀌니 DNS 같은 표준 이름 서비스를 자체 구현으로 바꿔야 했고 URL에 포트를 넣을 수 없었고 IP만 다루던 도구를 IP:포트를 다루게 고쳐야 했다고 해요. 그리고 결론을 이렇게 적었어요.

Learning from our experiences with Borg, we decided that Kubernetes would allocate an IP address per pod, thus aligning network identity (IP address) with application identity.

→ Borg에서 배운 대로 쿠버네티스는 파드마다 IP를 하나씩 주기로 했고 그래서 네트워크 신원(IP)이 애플리케이션 신원과 맞아떨어진다는 뜻이에요. 같은 글은 이 덕분에 앱이 HTTP의 80 같은 잘 알려진 포트를 그대로 쓰고 네트워크 분리나 대역폭 제한에 기존 도구를 그대로 쓸 수 있다고 이어 가요.

그림 1. 포트를 나눠 주는 대신 IP를 나눠 주자 포트 충돌은 노드 단위가 아니라 파드 안의 문제가 됐다 (오른쪽 IP는 우리 worker1의 실제 값)

Borg에서 얻은 교훈이 하나 더 있어요. 같은 논문의 "좋은 것" 쪽 첫 항목이 "Allocs are useful."이에요. 주 프로그램 옆에 로그를 옮기거나 데이터를 주기적으로 갱신하는 도우미 task를 붙이는 방식이 널리 쓰였고 도우미를 다른 팀이 따로 만들 수 있어서 좋았다고 해요. 논문은 쿠버네티스의 파드를 alloc에 대응시키면서 파드를 "a resource envelope for one or more containers that are always scheduled onto the same machine and can share resources"로 설명해요. 늘 같은 기계에 함께 스케줄되고 자원을 나눠 쓰는 컨테이너 묶음이라는 뜻이에요.

컨테이너가 하나뿐인데도 파드로 감싸는 이유도 ACM Queue 글에 있어요. Borg는 task를 alloc 밖에서도 돌릴 수 있게 해 두었는데 그게 "much inconvenience"였고 그래서 쿠버네티스는 "always runs an application container inside a top-level pod, even if the pod contains a single container"라고 적었어요. 원문은 무엇이 불편했는지까지는 적지 않았어요. 실행 단위가 두 갈래면 스케줄러와 네트워크, 모니터링이 두 경우를 모두 다뤄야 하니 컨테이너가 하나여도 늘 파드 안에서 돌게 하나로 맞춘 것으로 보여요. 쿠버네티스는 포트를 스케줄하는 대신 파드마다 IP를 나눠 주는 쪽을 골랐고 컨테이너 하나짜리도 파드로 감싸 실행 단위를 하나로 맞췄어요.

2014년 Docker의 기본 네트워크와는 맞지 않았다

문제는 그때의 Docker였어요. 2014-06-09에 처음 들어간 쿠버네티스 설계 문서(DESIGN.md)의 핵심 개념 절은 "While Docker itself works with individual containers, Kubernetes works with a pod"로 시작해요. Docker는 컨테이너 하나하나를 다루지만 쿠버네티스는 파드를 다룬다는 선언이에요. 같은 문서는 파드 안의 컨테이너가 네트워크 네임스페이스와 IP를 함께 쓴다고 적었어요.

한 달 뒤 정리된 네트워크 문서(docs/networking.md, 2014-07-16)는 첫 문장부터 "Kubernetes deviates from the default Docker networking model."이에요. 문서에 따르면 Docker의 기본 모드에서는 컨테이너마다 172로 시작하는 사설 대역의 IP를 받고 그 IP는 다른 호스트에서 닿지 않아요. 그래서 문서는 "you can never self-register anything from a container, because a container can not be reached on its private IP"라고 적었어요. 컨테이너가 자기 IP를 etcd 같은 서비스 레지스트리에 등록해도 다른 호스트에서는 그 주소로 찾아올 수 없다는 뜻이에요. 그 무렵 쿠버네티스도 파드를 노드 밖에 내보낼 때는 Docker의 -p로 노드의 주 인터페이스 포트에 연결했는데 문서는 이 방식이 "disallowing two pods from exposing the same port"라는 부작용을 낳는다고 적었어요. 포트를 기계 단위로 나눠 쓰는 한 두 파드가 같은 포트를 내보낼 수 없었던 거예요.

⚠️ 주의: 파드 안 컨테이너끼리는 같은 포트를 쓸 수 없어요
• 같은 2014 문서가 대가도 적어 두었어요. "ports could conflict, and there couldn't be private ports across containers within a pod"라서 파드 안의 컨테이너끼리는 포트가 겹칠 수 있고 서로에게 숨긴 포트를 가질 수 없어요
• 사이드카를 붙일 때는 본 컨테이너와 사이드카가 같은 포트를 열지 않게 정해요. 둘 다 같은 네트워크 네임스페이스를 쓰므로 나중에 뜬 쪽이 bind에서 실패해요
• 같은 파드 안에서는 localhost로 서로 붙을 수 있고 localhost에만 연 포트는 파드 밖에서 보이지 않아요. 파드 밖에 열 필요가 없는 관리용 포트는 127.0.0.1에만 열어요

2. 검토했다가 버린 대안들

파드마다 IP를 주는 쪽으로 가기 전에 검토한 대안들이 2014년 문서 두 편과 이슈에 남아 있어요. 출처 문장을 요약하면 이래요.

대안버린 이유출처
동적 포트 할당 (Borg, Docker -p)정적 포트와 동적 포트를 함께 지원해야 하고 포트가 귀한 자원이라 스케줄링이 복잡해져요. 포트 충돌·재사용·고갈에 시달리고 DNS 대신 etcd 같은 비표준 이름 체계가 필요해요. NAT는 주소 공간을 쪼개 자기 등록을 깨뜨려요docs/networking.md (2014-07)
컨테이너마다 IP를 주고 파드 안에서만 보이게 한 겹 더파드마다 브리지와 split-horizon DNS가 필요해 구현이 복잡하고 주소 변환이 한 번 더 끼어 이해하기 어려워요. 자기 등록과 IP를 주고받는 프로그램도 깨져요같은 문서
파드마다 VM"The VM per pod model would negate the container efficiency gains". 컨테이너로 얻은 효율이 사라진다는 반론이었어요이슈 #188 (2014-06-20)
여러 프로그램을 Docker 컨테이너 하나에인프라가 컨테이너를 하나하나 볼 수 있어야 프로세스 관리와 자원 모니터링을 해 줄 수 있고 컨테이너를 따로 빌드·배포할 수 있어요. 사용자가 프로세스 관리자를 직접 돌리거나 신호와 종료 코드 전달을 걱정하지 않아도 돼요docs/pods.md (2014-10)
파드 없이 affinity로 같은 노드에 함께 스케줄같은 노드에 놓을 수는 있지만 "resource sharing, IPC, guaranteed fate sharing, and simplified management" 같은 파드의 장점 대부분을 얻지 못해요같은 문서

마지막 줄의 fate sharing은 파드 안의 컨테이너가 같은 노드에서 함께 뜨고 함께 정리된다는 뜻이에요. affinity로 같은 노드에 두기만 하면 한쪽이 다른 노드로 옮겨 가거나 한쪽만 지워지는 일을 막을 수 없어요.

표를 보면 이 결정은 Docker의 기본값을 따르다 생긴 것이 아니라 일부러 벗어난 것이었어요. DESIGN.md는 네트워크 절을 "Kubernetes expands the default Docker networking model."로 시작해요. 그렇다면 Docker로 어떻게 컨테이너 여러 개가 IP 하나를 쓰게 했을까요? 그 답이 pause예요.

3. Docker로 IP 하나를 나눠 쓰려면 네임스페이스를 붙잡을 프로세스가 필요했다

📖 용어: 리눅스 네임스페이스 (net, ipc, uts, pid, mnt)
프로세스가 보는 시스템 자원을 따로 떼어 주는 커널 기능이에요. net은 네트워크 인터페이스와 IP·포트, ipc는 공유 메모리 같은 프로세스 간 통신, uts는 호스트 이름, pid는 프로세스 번호, mnt는 파일시스템 마운트를 나눠요. 네임스페이스는 그 안에 프로세스가 하나라도 있거나 파일로 붙잡혀 있는 동안만 살아 있어요. 프로세스는 /proc/<PID>/ns/net 같은 경로로 다른 프로세스의 네임스페이스에 들어갈 수 있어요.

파드마다 IP 하나를 주려면 파드 안의 컨테이너들이 네트워크 네임스페이스 하나를 같이 써야 해요. 2014년 네트워크 문서의 "Current implementation" 절은 이걸 두 단계로 풀었어요.

· 먼저 최소한의 이미지로 컨테이너 하나를 만들고 그 안에서 영원히 대기하는 명령을 실행해요. 사용자가 정의한 컨테이너가 아니고 잘 알려진 특별한 이름을 받아요. 이 컨테이너가 새 네트워크 네임스페이스와 veth를 만들고 Docker 대역에서 IP를 받아요.
· 그다음 사용자 컨테이너를 만들면서 net 인자에 그 컨테이너 이름을 줘요. 문서는 이 단계를 "Docker finds the PID of the command running in the network container and attaches to the netns of that PID."로 설명해요.

→ Docker가 다른 컨테이너의 네트워크 네임스페이스에 붙는 길은 그 컨테이너 안에서 돌고 있는 프로세스의 PID였다는 뜻이에요. 그래서 네임스페이스를 쥐고 오래 살아 있을 프로세스가 하나 필요했어요.

그 자리를 처음 맡은 것은 busybox였어요. pause 이미지를 들여온 2014-07-19 커밋(88317efb42)의 지워진 줄을 보면 그전까지 kubelet은 net이라는 이름의 컨테이너를 busybox 이미지로 띄우고 sh -c "rm -f nap && mkfifo nap && exec cat nap"을 실행했어요. 아무도 쓰지 않는 FIFO 파일을 만들어 놓고 cat으로 영원히 읽기를 기다리는 명령이에요. 이 커밋이 그 자리를 pause로 바꿨고 커밋 메시지는 이래요.

The pause image is a 240KB image that simply pauses waiting on a signal. Use this for the net container which only needs to act as a placeholder. Current net image is ~2.5MB. From my tests, this reduces startup time for the net container from ~14s to ~6s.

→ pause 이미지는 신호를 기다리며 멈춰 있기만 하는 240KB 이미지이고 자리만 지키면 되는 net 컨테이너에 쓴다는 뜻이에요. 그때 쓰던 이미지는 약 2.5MB였고 net 컨테이너 시작 시간이 약 14초에서 약 6초로 줄었다고 적혀 있어요. 처음 pause.go의 본문은 syscall.Pause() 한 줄이었어요.

왜 앱 컨테이너 하나에 이 역할을 맡기지 않고 따로 띄웠을까요? 2014년 네트워크 문서의 "앞으로 할 일" 절에 실마리가 있어요.

Right now, if the network container dies, all the user containers must be stopped and restarted because the netns of the network container will change on restart, and any subsequent user container restart will join that new netns, thereby not being able to see its peers. Additionally, a change in IP address would encounter DNS caching/TTL problems.

→ 네트워크 컨테이너가 죽었다가 다시 뜨면 네임스페이스가 새로 생기니 나머지 컨테이너를 모두 멈추고 다시 띄워야 하고 IP가 바뀌면 DNS 캐시와 TTL 문제도 생긴다는 뜻이에요. 앱 컨테이너에 이 역할을 맡기는 안을 검토하고 버렸다는 원문은 찾지 못했어요. 다만 이 문단대로라면 앱이 죽을 때마다 파드 전체를 다시 띄워야 하니 아무 일도 하지 않아서 죽을 일이 거의 없는 프로세스에게 맡긴 것으로 보여요. 같은 절에는 "IP addresses can be made stable across network container restarts"도 앞으로 할 일로 적혀 있어요. 이 문장은 4절에서 다시 나와요.

Go에서 C로, 그리고 CRI의 PodSandbox로

pause는 그 뒤로 몇 번 바뀌었어요. 2015-10에 열린 이슈 #15140은 코드 곳곳에 pause 이미지 태그가 세 가지로 갈려 있던 문제를 정리하려던 이슈였는데 이야기가 pause 자체로 번졌어요. "The Go runtime wakes up a few times a minute to do nothing."(Go 런타임이 하는 일 없이 1분에 몇 번씩 깨어난다)라는 지적이 나왔고 thockin은 "I have seen the Go binary die."라고 적었어요. 결국 2016년 PR #23009에서 pause를 C로 다시 썼고 이게 pause 3.0이에요. PR 본문에 적힌 amd64 바이너리 크기는 3,560바이트예요.

2017-01에는 PR #36853이 SIGCHLD 처리기를 넣었어요(pause 3.1). PR 본문은 "This allows pause to reap orphaned zombies in a shared PID namespace."예요. 파드가 PID 네임스페이스를 공유할 때 pause가 부모 잃은 좀비 프로세스를 거두게 한다는 뜻이고 5절에서 실험으로 확인해요.

그 사이 2016년 12월에 kubelet과 런타임 사이의 규약인 CRI가 소개됐어요(45편). CRI는 파드가 도는 환경을 PodSandbox라고 부르고 컨테이너와 따로 만들고 지워요.

📖 용어: PodSandbox (파드 샌드박스)
CRI가 파드 안 컨테이너들이 함께 쓰는 실행 환경에 붙인 이름이에요. CRI 설계 문서는 "The PodSandbox's lifecycle is decoupled from the containers"라고 적었어요. 샌드박스는 어떤 컨테이너보다 먼저 만들어지고 안의 컨테이너가 모두 끝나도 남아 있을 수 있다는 뜻이에요. 리눅스 런타임에서는 네임스페이스 묶음이고 VM 기반 런타임에서는 VM 하나일 수 있어요. 27편에서 본 RunPodSandbox가 이걸 만드는 호출이에요.

2014년의 "net 컨테이너"가 이름만 바뀐 것이 아니라 규약의 한 단위가 된 거예요. CRI 소개 글은 RunPodSandbox가 "setting up networking for a pod (e.g., allocating an IP)"을 포함한다고 적었어요. 파드 IP가 컨테이너가 아니라 샌드박스에 붙는다는 것은 27편과 34편에서 로그로 본 그대로예요.

지금 쓰는 pause.c는 v1.37.2 태그와 master가 같아요. 핵심만 옮기면 이래요(build/pause/linux/pause.c).

static void sigdown(int signo) { psignal(signo, "Shutting down, got signal"); exit(0); } static void sigreap(int signo) { while (waitpid(-1, NULL, WNOHANG) > 0) ; } int main(int argc, char **argv) { ... if (getpid() != 1) /* Not an error because pause sees use outside of infra containers. */ fprintf(stderr, "Warning: pause should be the first process\n"); sigaction(SIGINT, ...sigdown...); sigaction(SIGTERM, ...sigdown...); sigaction(SIGCHLD, ...sigreap...); for (;;) pause(); }

→ SIGINT나 SIGTERM을 받으면 바로 끝나고 SIGCHLD를 받으면 끝난 자식 프로세스를 모두 거두고 그 밖에는 pause() 시스템 콜로 신호가 올 때까지 잠들어 있다는 뜻이에요(sigaction 줄은 인자를 줄여 옮겼어요). 우리 노드의 pause도 이 소스에서 나온 3.10.2예요(샌드박스 안의 /pause -v 출력이 pause.c v3.10.2-).

4. 우리 클러스터에서 pause가 붙잡는 것과 pause를 죽였을 때

worker1의 myweb 파드 하나(샌드박스 c134f148ae67e)에서 pause와 nginx의 네임스페이스를 비교했어요. 두 프로세스의 /proc/<PID>/ns/ 아래 링크를 읽어 inode 번호가 같은지 본 거예요.

그림 2. pause와 nginx는 net·ipc·uts 세 가지만 같았고 pid·mnt·cgroup은 따로였다

· net·ipc·uts가 같아요. 그래서 nginx와 같은 파드의 다른 컨테이너는 IP와 localhost, 호스트 이름을 함께 써요.
· pid·mnt가 달라요. NSpid 줄을 보면 pause(호스트 PID 10332)와 nginx(10360)가 각자 자기 PID 네임스페이스에서 PID 1이에요. 파일시스템도 컨테이너마다 따로예요.
· oom_score_adj가 pause는 -998, nginx는 1000이에요. 메모리가 모자랄 때 커널은 이 값이 클수록 그 프로세스를 먼저 죽이는 쪽으로 골라요. 이 nginx는 requests를 적지 않은 BestEffort 파드라서 1000을 받았고 pause는 거의 죽이지 않을 값을 받았어요. containerd 소스에서 -998이라는 상수가 정의된 곳은 찾지 못했고 이 값은 우리 노드에서 본 값이에요.

컨테이너를 만들 때 containerd가 runc에 넘긴 OCI 설정(26편)을 보면 어떻게 같은 네임스페이스를 쓰게 되는지 나와요.

# 43-pod-sandbox.txt 4절 발췌 (worker1) pause spec namespace: network /var/run/netns/cni-0099a4f1-67e2-12c5-5900-c6cd6da46675 ip netns identify 10332 → cni-0099a4f1-67e2-12c5-5900-c6cd6da46675 /var/run/netns 파일 수 7 / Ready 샌드박스 중 hostNetwork 아닌 것 7 CRI 가 본 파드 IP 10.244.194.100, 그 netns 안 eth0: 10.244.194.100/32 nginx 컨테이너 spec 의 네임스페이스 경로 (pause PID 의 /proc 경로로 들어간다): ipc /proc/10332/ns/ipc uts /proc/10332/ns/uts network /proc/10332/ns/net

→ pause는 /var/run/netns/ 아래 파일로 만들어 둔 네트워크 네임스페이스에 들어가 돌고 nginx는 pause의 PID 경로(/proc/10332/ns/...)로 net·ipc·uts에 들어간다는 뜻이에요. 2014년 문서의 "PID로 netns에 붙는다"가 containerd 2.4.1에서도 그대로 쓰여요. 다른 점은 네트워크 네임스페이스를 containerd가 먼저 만들어 파일로도 붙잡아 둔다는 거예요. containerd v2.4.1의 sandbox_run.go는 hostNetwork가 아니면 /var/run/netns에 네임스페이스를 만들고 CNI로 네트워크를 설정한 다음 pause를 띄워요. worker1에서 이 파일 수(7)는 hostNetwork가 아닌 Ready 샌드박스 수(7)와 같았어요. hostNetwork 파드인 kube-proxy에도 pause는 있었고 그 pause의 net 네임스페이스는 노드의 것과 같았어요.

그림 3. 앱 컨테이너는 pause의 PID 경로로 net·ipc·uts에 들어가고 네트워크 네임스페이스는 containerd가 만든 파일로도 붙잡혀 있다

앱을 죽이면 같은 샌드박스, pause를 죽이면 새 샌드박스

그럼 pause가 죽으면 어떻게 될까요? 실험용 네임스페이스 w1-pause에 nginx:1.25.1-alpine 파드 sb-demo를 worker1에 고정해 띄우고 노드에서 nginx 마스터 프로세스와 pause 프로세스를 차례로 kill -9 했어요. 매번 파드가 다시 Ready가 될 때까지 걸린 시간과 샌드박스 ID, attempt 번호, 파드 IP, 재시작 횟수를 기록했어요.

그림 4. nginx를 죽이면 같은 샌드박스에서 컨테이너만 다시 떴고 pause를 죽이면 attempt 1인 새 샌드박스가 생겼다

· nginx를 죽였을 때 파드는 1.3초 만에 다시 Ready였고 샌드박스는 6e1464df433e(attempt 0) 그대로, IP도 10.244.194.65 그대로, restartCount만 1이 됐어요.
· pause를 죽였을 때 파드가 다시 Ready가 되기까지 12.4초가 걸렸어요. 새 샌드박스 6c69b5d1cf56(attempt 1)이 생겼고 옛 샌드박스는 NOTREADY로 남았어요. 이벤트에는 SandboxChanged ... Pod sandbox changed, it will be killed and re-created.와 Killing ... Stopping container web가 찍혔어요.

12.4초가 어디에 쓰였는지 보려고 같은 시간대의 containerd, Calico CNI, kubelet 로그를 한 줄에 놓았어요.

그림 5. pause가 죽고 새 샌드박스가 준비되기까지 0.44초, 앱 컨테이너는 그 뒤 11초 넘게 재시작 백오프를 기다렸다

순서대로 읽으면 이래요.

· 17.128 → 17.885 nginx가 끝나고 약 0.76초 뒤에 같은 샌드박스(6e1464df433e) 안에서 컨테이너를 다시 만들기 시작했어요(attempt:1). StartContainer가 성공한 17.924까지는 약 0.80초였고 파드가 다시 Ready가 되기까지는 1.3초였어요. RunPodSandbox는 부르지 않았어요. 27편에서 OOM으로 죽은 컨테이너가 다시 뜰 때와 같아요.
· 18.687 containerd가 샌드박스 종료 이벤트를 받았어요. exit_status 137은 128 + 9, 즉 SIGKILL로 끝났다는 뜻이에요.
· 18.886 ~ 19.010 kubelet이 아직 돌던 web 컨테이너를 멈추고(StopContainer) StopPodSandbox를 불렀어요. 그 안에서 Calico CNI가 IP를 반납했고(Released address using handleID) 네트워크 정리(TearDown)가 끝났어요. 34편에서 본 반납 과정 그대로예요.
· 19.013 ~ 19.129 새 샌드박스(attempt:1)를 만들었어요. 그 사이 Calico CNI가 "Reassigning existing IP to new sandbox"를 찍고 10.244.194.65를 콕 집어 요청했어요.
· 19.130 → 30.708 kubelet이 back-off 10s restarting failed container=web를 찍고 기다렸다가 30.708에 새 샌드박스 안에 web 컨테이너를 만들었어요(attempt:2).

kubelet이 이렇게 움직이는 근거는 v1.37.2 소스에 있어요. util.go의 PodSandboxChanged는 최신 샌드박스가 SANDBOX_READY가 아니면 "No ready sandbox for pod can be found. Need to start a new one"을 남기고 attempt를 1 올린 새 샌드박스가 필요하다고 답해요. kuberuntime_manager.go의 computePodActions는 그 답을 받으면 KillPod와 CreateSandbox를 함께 켜요. 파드의 컨테이너를 모두 정리하고 샌드박스부터 다시 만든다는 뜻이에요.

그러니 12.4초의 대부분은 샌드박스를 다시 만드는 시간이 아니었어요. pause가 죽고 새 샌드박스가 준비되기까지는 0.44초(18.687 → 19.129)였고 그 뒤 web 컨테이너를 다시 만들기까지 기다린 약 11.6초(19.129 → 30.708)는 재시작 백오프였어요. 파드 수명 주기 문서는 첫 크래시에는 바로 재시작하고 "After the initial crash Kubernetes applies an exponential backoff delay for subsequent restarts"라고 적었어요. 앞에서 nginx를 죽인 재시작이 첫 번째였고 이번이 두 번째라서 10초를 기다린 거예요. pause가 죽으면 파드의 모든 컨테이너가 같이 정리되고 새 샌드박스 안에서 다시 떠요. 이때 컨테이너 재시작 백오프도 그대로 적용돼요.

📖 용어: 재시작 백오프 (CrashLoopBackOff)
kubelet이 컨테이너를 같은 파드 안에서 다시 띄울 때 기다리는 시간이에요. 첫 크래시에는 바로 다시 띄우고 그 뒤로는 10초, 20초, 40초 순서로 두 배씩 늘려 최대 300초까지 기다려요. 컨테이너가 10분 동안 문제없이 돌면 기다리는 시간이 처음으로 돌아가요. 기다리는 동안 kubectl의 STATUS 칸에 CrashLoopBackOff가 보일 수 있어요.
그림 6. 시각은 21:40 뒤의 초. 앱을 죽이면 컨테이너만, pause를 죽이면 샌드박스와 그 안의 컨테이너가 모두 다시 만들어졌다

새 샌드박스인데 IP가 같았던 이유

3절에서 본 2014년 문서는 네트워크 컨테이너가 다시 뜨면 IP가 바뀔 수 있다고 걱정했고 IP를 그대로 유지하는 것을 앞으로 할 일로 적었어요. 지금 kubelet은 새 샌드박스를 만들 때 CNI ADD를 다시 부르고 어떤 IP를 줄지는 CNI 플러그인이 정해요. 이번 실험에서 IP가 같았던 것은 Calico가 일부러 같은 IP를 다시 요청했기 때문이에요.

Calico v3.33.0의 CNI 플러그인 소스(cni-plugin/pkg/k8s/k8s.go)에 있는 assignPodIPs의 주석은 "allocates this pod's addresses, preferring the ones its existing endpoint already holds"예요. 같은 파드의 엔드포인트 기록에 IP가 남아 있으면 새 샌드박스에서 그 IP를 콕 집어 요청하고 실패할 때만 새로 받는다는 뜻이에요. 로그의 "Reassigning existing IP to new sandbox"가 이 경로예요. 이 코드는 2026-09에 들어갔어요(PR #14014, v3.33으로 옮긴 PR #14015). PR이 고친 문제는 IP 풀에 빈 주소가 없을 때 샌드박스를 다시 만들면 새 IP를 받지 못해 파드가 다시 뜨지 못하던 일이었고 릴리스 노트는 "reusing the address the pod already holds when its sandbox is rebuilt"로 정리했어요. 같은 파일을 v3.30.0, v3.31.0, v3.32.0 태그에서 열어 보면 이 경로가 없어요. 그 버전에서는 새 샌드박스도 처음 뜨는 파드와 같은 방식으로 34편에서 본 빈칸 목록에서 IP를 새로 할당받아요.

정리하면 샌드박스가 다시 만들어질 때 IP가 유지되는지는 쿠버네티스가 아니라 CNI 플러그인과 그 버전이 정해요. 쿠버네티스 쪽 문서에도 이 경우가 따로 적혀 있어요. init 컨테이너 문서는 init 컨테이너가 다시 실행되는 이유의 첫 번째로 "The Pod infrastructure container is restarted."를 들고 노드에 root로 접근한 사람이나 할 법한 드문 일이라고 적었어요. pause가 다시 뜨면 init 컨테이너도 처음부터 다시 돈다는 뜻이에요.

노드 자체가 재부팅될 때도 같은 일이 생겨요. worker1의 샌드박스 목록에는 재부팅 전의 샌드박스가 SANDBOX_NOTREADY로 남아 있었고 IP 칸이 비어 있었어요. 같은 파드 이름으로 attempt가 1 오른 새 샌드박스가 Ready였어요(portainer는 attempt 0 → 1, calico-node는 6 → 7).

💡 실무에서는: 컨테이너 재시작과 샌드박스 재생성을 나눠 읽어요
• RESTARTS만 오르고 SandboxChanged 이벤트가 없으면 같은 샌드박스에서 컨테이너만 다시 뜬 거예요. IP와 다른 컨테이너는 그대로예요
• SandboxChanged ... Pod sandbox changed, it will be killed and re-created. 이벤트가 보이면 파드의 모든 컨테이너가 정리되고 다시 떠요. init 컨테이너도 다시 돌고 IP는 CNI에 따라 바뀔 수 있어요
• 노드에서는 crictl pods --name <파드 이름>로 attempt 번호와 NOTREADY로 남은 옛 샌드박스를 봐요
• 1.37에서 GA가 된 PodReadyToStartContainers 조건이 샌드박스 준비 여부를 보여 줘요. CHANGELOG-1.37에 따르면 False일 때 메시지에 샌드박스가 준비되지 않은 이유(예: "pod sandbox has no IP address")가 담겨요

5. pause가 남긴 숙제: 좀비 수거, 이미지 관리, 없애자는 논의

좀비는 누가 거둘까

📖 용어: 좀비 프로세스와 PID 1
끝났지만 부모가 종료 상태를 읽어 가지 않아 프로세스 표에 남은 프로세스를 좀비라고 해요(ps의 STAT이 Z). 부모가 먼저 끝난 프로세스는 그 PID 네임스페이스의 PID 1이 넘겨받고 PID 1이 wait로 거둬야 사라져요. PID 1이 이 일을 하지 않는 프로그램이면 좀비가 쌓여요.

그림 2에서 봤듯 기본 설정에서는 컨테이너마다 PID 네임스페이스가 따로이고 앱이 자기 네임스페이스의 PID 1이에요. 그러면 고아 프로세스를 거두는 일도 앱 몫이에요. 두 파드로 확인했어요. 컨테이너 명령은 sh -c "(sleep 1 &); exec sleep 3600"이고 1초 뒤에 끝나는 sleep 1은 부모를 잃고 PID 1에게 넘어가요. 하나는 shareProcessNamespace를 false(기본값)로, 다른 하나는 true로 줬어요.

# 43-pause-vs-app-kill.txt 4절 21:40:36 zombie-false: ps -o pid,ppid,stat,comm PID PPID STAT COMMAND 1 0 S sleep 8 1 Z sleep # 부모 잃은 sleep 1 이 PID 1(sleep 3600) 아래 좀비로 남았다 9 0 R ps 21:40:36 zombie-true: ps -o pid,ppid,stat,comm PID PPID STAT COMMAND 1 0 S pause # 파드 전체의 PID 1 이 pause 6 0 S sleep 14 0 R ps # 좀비가 없다

→ false 파드에서는 PID 1인 sleep 3600이 자식을 거두지 않아 끝난 sleep 1이 STAT Z로 남았다는 뜻이에요. true 파드에서는 PID 1이 pause였고 좀비가 없었어요. pause.c의 SIGCHLD 처리기(sigreap)가 거둔 거예요.

📖 용어: shareProcessNamespace
파드 스펙의 필드로 true면 파드 안 모든 컨테이너가 PID 네임스페이스 하나를 같이 써요. 서로의 프로세스가 보이고 신호도 보낼 수 있어요. 이때 그 네임스페이스의 PID 1은 앱이 아니라 pause예요. 기본값은 false예요.

그럼 처음부터 PID 네임스페이스도 공유하면 되지 않았을까요? 실제로 1.7에서 Docker 파드의 PID 네임스페이스 공유를 기본으로 켰어요(PR #45236). CHANGELOG-1.7은 이때 kubectl exec {pod} kill 1이 컨테이너 하나가 아니라 파드 전체를 다시 시작하게 된다고 경고했고 1.8에서 기본값을 다시 껐어요(PR #51634). 대신 파드마다 고르는 shareProcessNamespace 필드가 1.10 알파, 1.12 베타, 1.17 GA를 거쳤어요. KEP-495의 대안 절은 기본 공유를 버린 이유로 "this would cause problems for container images that assume they will always be PID 1"과 "Many members of the community want to use the isolated namespaces as security boundary between containers in a pod"를 들어요. 자기가 PID 1이라고 가정하는 이미지(systemd 등)가 깨지고 컨테이너 사이의 보안 경계로 쓰고 싶은 사람이 많았다는 뜻이에요.

그래서 pause의 init 역할은 반쯤만 남았어요. KEP-495는 Non-Goals에 "Creating a general purpose container init solution"을 적었어요. 기본 설정의 파드에서는 pause가 좀비를 거두지 않으니 자식 프로세스를 많이 만드는 앱이라면 이미지 안에서 좀비를 거두는 작은 init 프로세스를 PID 1로 두는 방법을 검토해야 해요.

⚠️ 주의: shareProcessNamespace를 켜기 전에 확인할 것
• KEP-495의 위험 절 첫 줄대로 앱이 더는 PID 1이 아니에요. 공유 PID 파드에서 kill 1은 앱이 아니라 pause에 가고 "potentially restart the pod", 즉 파드 전체가 다시 만들어질 수 있어요(4절에서 본 SandboxChanged)
• 다른 컨테이너의 /proc이 보여요. 명령 인자나 환경 변수로 넘긴 비밀번호도 보이고 /proc/$pid/root로 파일시스템까지 들여다볼 수 있어요
• 이 클러스터에서 shareProcessNamespace가 true인 파드는 0개였어요. 디버깅용 사이드카가 필요할 때만 켜고 PID 1을 가정하는 이미지(systemd 등)에는 켜지 않아요

pause 이미지는 지워지면 안 된다

파드를 하나 띄우려면 노드에 pause 이미지가 먼저 있어야 해요. 2022-08의 이슈 #111796 제목은 "Kubelet removes pause container to free up disk space"예요. 디스크를 비우던 kubelet 이미지 GC가 실행 중인 파드가 쓰는 pause 이미지를 지운 일이에요. 지금은 런타임이 CRI로 이미지에 pinned 표시를 붙여 알려 주고 kubelet 이미지 GC가 그 이미지를 건너뛰어요(1.23의 PR #103299). worker1에서는 이미지 19개 가운데 pinned=true가 registry.k8s.io/pause:3.10.2 하나였어요. containerd 설정의 pinned_images.sandbox에 적힌 이미지가 이거예요.

pause 버전은 두 곳에서 정해져요. kubeadm v1.37.2 소스의 상수 PauseVersion = "3.10.2"와 containerd 설정의 pinned_images.sandbox예요. 4편에서 노드를 준비할 때 kubeadm이 알려 준 pause 이미지 이름을 containerd 설정에 그대로 적은 것도 이 때문이에요. 1.27부터 kubeadm은 둘이 다르면 경고를 내요(PR #115610). kubelet의 --pod-infra-container-image 플래그는 1.24에 deprecated, 1.35에 제거됐어요. pause 이미지를 고르는 일이 kubelet에서 런타임으로 완전히 넘어간 거예요.

💡 실무에서는: pause 이미지는 런타임 설정에서 관리해요
• 노드가 인터넷에 닿지 않아 사설 레지스트리를 쓴다면 pause 이미지도 미러하고 containerd의 pinned_images.sandbox(containerd 2.x)를 그 주소로 바꿔요. 이 이미지를 받지 못하면 RunPodSandbox부터 실패해요
• 쿠버네티스를 올릴 때 kubeadm config images list의 pause 버전과 런타임 설정이 같은지 보고 kubeadm의 불일치 경고를 무시하지 않아요
• crictl images -o json에서 pause 이미지가 "pinned": true인지 확인해요. pinned가 아니면 디스크가 찰 때 이미지 GC가 지울 수 있어요

pause를 없애자는 논의는 런타임으로 넘어갔다

pause를 없애고 싶다는 말은 일찍부터 나왔어요. 2015년 이슈 #15140에서 dchen1107은 "I really want to get rid of pause."라고 적고 런타임 구현과 자원 관리를 복잡하게 하고 부담을 더한다는 이유를 들었어요. 같은 이슈에서 thockin은 "It will be some time before runc is ready for us to use, and we have more than net namespaces to manage."라고 답했어요. runc를 바로 쓸 준비가 안 됐고 관리할 것이 네트워크 네임스페이스만이 아니라는 뜻이에요.

지금은 쿠버네티스가 아니라 런타임이 정해요.

· CRI-O는 drop_infra_ctr 설정의 기본값이 v1.22.0부터 true예요. sandbox_linux.go의 NeedsInfra를 보면 이 설정이 켜져 있으면 PID 네임스페이스를 파드 단위로 공유하는 파드(shareProcessNamespace: true)에만 infra 컨테이너(pause)를 띄워요. 파드 전체의 PID 1이 필요한 경우만 남긴 셈이에요.
· containerd는 기본 샌드박스 구현(sandboxer = 'podsandbox')이 지금도 pause 컨테이너를 띄워요. 우리 노드 설정도 이 값이에요. 샌드박스를 직접 구현하는 shim(sandboxer = "shim", 예: Kata Containers 같은 VM 기반 런타임)은 pause를 쓰지 않아서 2026-05에 머지된 PR #13424가 이 경우 pause 이미지를 받지 않게 했어요. 우리 노드 설정에 보이는 disable_pause_image_pull = false가 이 동작과 관련된 항목이에요. v2.4.1 소스에는 pause 이미지를 미리 받아 두는 이유를 설명하며 "This may be removed/deprecated in the distant future, if we decide to remove pause containers."라는 주석이 남아 있어요.

쿠버네티스 API는 이 구현을 일부러 드러내지 않아요. 1.37에서 GA가 된 파드 조건의 이름을 정한 KEP-3085는 SandboxReady라는 이름을 피한 이유를 "Kubernetes does not directly surface low level sandbox related concepts to all users"라고 적었어요. "파드 = pause + 앱 컨테이너"는 쿠버네티스 API가 약속한 것이 아니라 런타임이 PodSandbox를 구현하는 방식이에요. 우리 클러스터는 containerd의 기본 구현을 쓰니 파드마다 pause가 하나씩 뜨고 worker1에서는 그 비용이 파드 9개에 RSS 4,432KiB였어요.

✍️ 오늘의 요약
쿠버네티스는 포트를 스케줄하던 Borg의 고생 때문에 파드마다 IP를 주기로 했고 2014년 Docker에서 그 IP를 여러 컨테이너가 나눠 쓰려면 네임스페이스를 붙잡고 있을 프로세스가 필요했어요. 그게 pause예요.

Borg에서는 기계의 IP 하나를 task들이 나눠 쓰느라 포트를 자원으로 스케줄하고 이름 서비스가 IP:포트를 다뤄야 했어요. 쿠버네티스는 파드마다 IP를 주고 컨테이너 하나짜리도 파드로 감싸 실행 단위를 하나로 맞췄어요. 동적 포트, 파드 안 IP 한 겹, 파드마다 VM, 한 컨테이너에 다 넣기, affinity는 2014년 문서에서 이유와 함께 버려졌어요. Docker에서는 살아 있는 컨테이너의 PID로만 네트워크 네임스페이스에 붙을 수 있어서 busybox가 그 자리를 지키다 240KB pause로 바뀌었고 C로 다시 쓰인 뒤 좀비를 거두는 일도 맡게 됐어요. 이 자리는 CRI에서 PodSandbox라는 이름을 얻었어요. 우리 worker1에서 pause와 nginx는 net·ipc·uts만 같았고 nginx는 pause의 PID 경로로 그 네임스페이스에 들어갔어요. nginx를 죽이면 같은 샌드박스에서 종료 후 약 0.76초에 컨테이너를 다시 만들기 시작했고 종료 후 약 0.80초에 시작을 마쳤어요. 파드는 종료 후 1.3초 만에 Ready가 됐어요. pause를 죽이면 0.44초 만에 새 샌드박스가 생긴 뒤 재시작 백오프 10초를 기다려 컨테이너가 다시 떴어요. IP가 그대로였던 것은 Calico v3.33.0이 같은 IP를 다시 요청했기 때문이고 이건 CNI와 버전에 달린 동작이에요. PID 공유는 기본으로 켰다가 되돌려 선택 항목이 됐고 pause를 없애는 결정은 지금 런타임이 내려요.
