6편은 리뷰 질문 하나를 남겼어요. "같은 함수가 복사돼 여러 곳에 있나? 한 곳을 고치면 나머지는 누가 고치나?" 이번 실습은 그 질문을 실제 저장소의 1년치 이력에 던집니다. 한 릴리스에서 복사된 코드 묶음을 찾고, 다음 릴리스까지 어떤 커밋이 묶음의 어느 사본을 고쳤는지 셌어요. 숫자는 전부 이번에 돌린 결과이고, 직접 만든 예제 코드는 쓰지 않았습니다.

1. "불일치 변경"을 무엇으로 셀 것인가

먼저 셀 대상을 정해야 했어요. 복제 코드와 결함의 관계를 처음 크게 잰 연구는 Juergens 외의 ICSE 2009 논문이에요(Do Code Clones Matter?). 원문을 읽어 보니 생각과 방법이 달랐습니다. 이 논문은 이력을 보지 않아요. 한 시점의 코드에서 거의 같은 사본들을 찾고, 사본 사이에 편집 거리가 임계값 이하인 차이가 있으면 그 묶음을 불일치 복제 묶음이라고 불러요. 그다음 각 묶음을 그 시스템의 개발자에게 보여 주고 일부러 다르게 둔 것인지, 결함인지 판정받았습니다. 판정할 수 없으면 의도한 것이고 결함이 아니라고 쳤어요.

📖 용어: 복제 묶음 (clone group)
서로 같거나 거의 같은 코드 조각들의 모음이에요. 조각 하나하나를 사본이라고 부릅니다. 연구에서는 글자까지 같은 것을 type 1, 이름과 값만 다른 것을 type 2, 문장이 더해지거나 빠진 것을 type 3이라고 나눠요.

이력을 보지 않은 이유도 논문에 적혀 있어요(7.1절). 한 커밋 안에서 복사하고 바로 고친 경우도 세고 싶었고, 산업 시스템은 이력이 온전하지 않았다고요. 결과는 다섯 시스템 평균으로 복제 묶음의 52%가 불일치였고, 불일치 묶음을 분모로 28%가 의도하지 않은 것, 15%가 결함이었습니다(의도하지 않은 것 중에서는 절반이 결함). 개발자가 확인한 결함은 107개였어요. 유일한 오픈 소스이자 자바 시스템(Sysiphus)은 303개 묶음 중 146개가 불일치, 23개가 결함이었습니다.

이력으로 세는 방법은 Krinke의 WCRE 2007 연구가 대표적이에요(A Study of Consistent and Inconsistent Changes to Code Clones). Juergens 외는 관련 연구 절에서 이 결과를, 여러 오픈 소스 시스템에서 복제의 절반 정도만 일관되게 변했고 일관되지 않게 변한 복제가 나중에 다시 맞춰지는 경우는 드물었다고 요약해요. 그리고 이런 간접 측정에는 약점이 있다고 지적합니다. 개발자가 모르고 남긴 차이와 일부러 갈라 놓은 차이는 이력에서 똑같이 보인다는 거예요.

저는 개발자에게 물을 수 없으니 두 방법을 섞었어요. 사본을 고른 시점에는 같았던 묶음에서 일부 사본만 바꾼 커밋을 불일치 변경으로 세고(이력 기반), 그런 묶음은 원 논문처럼 하나씩 읽어 의도인지 판정했습니다. 판정하는 사람이 개발자가 아니라 저라는 점이 가장 큰 차이예요. 그래서 "빠뜨렸다"는 판정은 나중에 유지보수자가 다른 사본에 같은 수정을 넣었거나, 릴리스된 jar로 돌려 차이를 확인한 경우로만 한정했어요.

Juergens 외 2009 이 실습 검출 ConQAT, 문장 단위, 최소 10문장, PMD CPD 7.28.0, 토큰 단위, 최소 100 토큰 편집 거리 5 이하(type 3), (75, 150 으로도), 글자가 같거나 값만 다른 묶음 식별자·상수 정규화, 메서드 경계 안 (리터럴만 정규화, 이름이 다른 type 2 는 제외), 메서드 경계를 넘을 수 있음 불일치 한 시점에 사본끼리 다르다 기준 릴리스에서 같던 사본 중 일부만 바꾼 커밋이 있다 의도 판정 그 시스템 개발자 필자(커밋 메시지, 이슈, 이후 이력). 모르면 의도로 친다 결함 판정 개발자 유지보수자가 나중에 고쳤거나 jar 로 재현한 것만
📖 용어: CPD (Copy/Paste Detector)
PMD에 들어 있는 복제 검출기예요. 소스를 토큰으로 자르고 Karp-Rabin 문자열 검색으로 같은 토큰열을 찾습니다. 문서에 따르면 기본으로는 똑같은 중복만 찾고, --ignore-literals, --ignore-identifiers 같은 옵션을 주면 값이나 이름이 달라도 같은 것으로 봐요(PMD 문서, Finding duplicated code with CPD).
⚠️ 주의: 식별자 정규화 옵션은 이번에 쓰지 못했다
원 논문처럼 이름 차이를 무시하려고 --ignore-identifiers를 줬더니 CPD가 보고서 없이 멈췄어요.
[ERROR] Exception while running CPD.: Cannot invoke "String.equals(Object)" because "java.util.Deque.peek().name" is null
→ 생성자를 알아보는 내부 상태에서 null을 꺼냈다는 뜻이에요(출력 전체는 out/cpd-ignore-identifiers-error.txt). 파일 목록을 반씩 잘라 가며 세 파일까지 줄였는데, 세 파일 모두 하나씩 돌리면 멀쩡했습니다. 앞 파일이 남긴 상태가 다음 파일로 넘어가는 문제였고, 같은 증상이 이미 보고돼 7.29.0에서 고쳐질 예정이었어요(pmd/pmd#7133). 그래서 리터럴만 정규화했고, 이름만 바꾼 사본(type 2)은 이번 묶음에 들어오지 않았습니다.

2. 실습 환경: spring-framework의 1년

대상은 spring-projects/spring-framework예요. 서블릿(webmvc)과 리액티브(webflux), RestTemplate과 RestClient, jdbc와 r2dbc처럼 같은 일을 두 스택으로 하는 코드가 나란히 있어서, 복사해 붙일 이유가 구조에 있습니다. 그리고 커밋 메시지가 이슈 번호를 다는 습관이 있어 한쪽만 고친 이유를 확인하기 좋아요. 창 안의 머지 아닌 커밋 2,395개 중 1,661개(69%)가 메시지에 gh- 뒤에 숫자가 붙은 이슈 번호를 달고 있었습니다(대소문자 무시, scripts/count_issue_refs.sh).

기준은 v6.1.0(2023-11-16), 끝은 v6.2.0(2024-11-14)이에요. 7.0까지 가는 다음 1년은 쓰지 않았습니다. 7.0은 JSpecify null 표기로 거의 모든 파일을 한 번에 바꿔서, 그런 커밋이 "모든 사본을 함께 바꿨다"는 숫자를 부풀립니다. 검출 범위는 각 모듈의 src/main/java이고, 다른 프로젝트에서 가져와 넣은 코드(org.springframework.asm, cglib, objenesis, javapoet)는 뺐어요. 원 논문이 생성된 코드를 뺀 것과 같은 이유입니다.

그림 1. 기준 릴리스의 묶음을 끝 릴리스까지 줄 단위로 따라가고, 일부만 바뀐 묶음은 하나씩 읽었다
📖 용어: git log -L
파일의 줄 범위 하나를 주면 그 줄들을 바꾼 커밋만 거슬러 올라가며 보여 주는 git 옵션이에요. git log -L 57,120:파일 v6.1.0..v6.2.0처럼 쓰면 범위 밖 변경은 무시하고, 유지보수 브랜치에서 머지로 올라온 커밋도 실제로 고친 커밋으로 찾아 줍니다.
git clone https://github.com/DDINGJOO/Platform-study.git cd Platform-study/labs/devops/pc-02-clone-drift export WORK=/tmp/clone-drift # 저장소 밖 빈 디렉터리 ./scripts/fetch.sh v6.1.0 v6.2.0 # 클론, git archive 로 스냅숏, PMD 7.28.0 ./scripts/cpd.sh v6.1.0 100; ./scripts/cpd.sh v6.2.0 100 python3 scripts/track.py "$WORK" v6.1.0 v6.2.0 100 # 사본마다 git log -L python3 scripts/analyze.py v6.1.0 v6.2.0 100 # -> results/summary-*.md, events-*.tsv python3 scripts/dossier.py "$WORK" v6.1.0 v6.2.0 100 # 불일치 묶음별 diff 모음 (손 판정용) ./scripts/run_demos.sh # 릴리스 jar 로 세 묶음 확인 -> out/demo/

Docker는 쓰지 않았고 호스트의 OpenJDK 25.0.3, git, python3로 돌렸어요. 받은 저장소는 --no-checkout으로 클론한 뒤 git archive로 스냅숏만 풀었고, 그 안의 빌드 스크립트는 실행하지 않았습니다. 추적 한 번은 28초 걸렸어요(out/track-time.txt). 코드와 결과는 labs/devops/pc-02-clone-drift에 있고, 손 판정 40건은 results/review-v6.1.0-v6.2.0-t100.md에 근거와 함께 적어 뒀어요.

3. 숫자만 보면 절반은 따로 고쳐졌다

v6.1.0, 최소 100 토큰: 복제 묶음 256개 (사본 2개 245, 3개 7, 4개 3, 5개 1) 1년 동안 코드가 안 바뀐 묶음 175 모든 사본이 같은 커밋으로만 바뀐 묶음 39 일부 사본만 바꾼 커밋이 한 번이라도 있는 묶음 40 사본이 하나 이하로 줄어든 묶음 2 커밋 단위: 일관 변경 83, 불일치 변경 69 (주석·공백만 바꾼 (커밋, 사본) 쌍 55 는 뺐다) (묶음 65 를 손으로 고친 숫자. 스크립트 출력은 안 바뀐 묶음 176, 함께만 바뀐 묶음 38, 일관 변경 81)

→ 코드가 바뀐 묶음 79개 중 40개(51%)에서 적어도 한 번은 한쪽만 고쳐졌다는 뜻이에요. 묶음 하나는 손으로 고쳤습니다. webflux와 webmvc의 PathResourceLookupFunction 묶음은 두 사본이 같은 커밋(gh-33574)으로 각 스택의 공통 유틸리티로 옮겨졌는데, 지워진 줄이 사본 범위 가장자리에 있어서 git log -L이 끝 릴리스에 남은 여덟 줄만 보고 "변경 없음"으로 셌어요. 그 커밋의 부모까지만 범위를 옮겨 다시 돌리니, 두 사본을 함께 바꾼 커밋이 둘(정리 커밋 d86bf8b205와 옮긴 커밋 c6fa180602) 나와 일관 변경이 81에서 83이 됐습니다(out/recheck-g65.txt). 범위가 절반 아래로 줄어든 사본은 모두 10개였고, 나머지 8개는 남은 줄에서 바꾼 커밋이 잡혔지만, 같은 이유로 가장자리에서 지운 변경을 놓쳤을 수 있어요.

최소 토큰을 바꿔도 비율은 크게 움직이지 않았어요.

최소 토큰 묶음 코드가 바뀐 묶음 그중 불일치가 있던 묶음 불일치 커밋 / 전체 변경 커밋 75 450 128 70 (55%) 116 / 240 (48%) 100 256 79 40 (51%) 69 / 152 (45%) 150 127 49 23 (47%) 40 / 92 (43%) (100 은 묶음 65 를 고친 숫자, 75 와 150 은 스크립트 출력 그대로)

Krinke가 보고한 "절반 정도"는 묶음 수가 아니라 묶음에 생긴 변경 수의 비율이에요. 같은 단위인 오른쪽 열이 43~48%로, 거의 같은 자리에 떨어졌습니다(이쪽은 버전이 아니라 커밋 단위라 더 잘게 셌어요). 여기까지만 보면 바뀐 복제 코드의 절반은 함께 고쳐지지 않았습니다. 다만 전체 256개 묶음으로 보면 16%이고, 175개(68%)는 1년 동안 아예 바뀌지 않았어요. 그런데 이 숫자는 Juergens 외가 경고한 바로 그 간접 측정이에요. 40개를 하나씩 열어 봤습니다.

4. 40개를 하나씩 읽으니, 빠뜨린 것은 하나였다

판정은 다섯 가지로 했어요. 같은 변경이 창 안에서 다른 사본에도 들어갔으면 따라 고쳐짐, 이름·형식·주석·어노테이션만 바뀌었거나 같은 날 되돌렸거나 다른 사본이 이미 같은 동작이면 동작 차이 없음, 한쪽에만 필요한 변경이면 한쪽만의 요구, 다른 사본에도 필요했는데 빠졌고 그 증거가 있으면 빠뜨림, 빠뜨린 것 같지만 증거가 없으면 후보예요. 후보는 원 논문 규칙대로 집계에서 의도로 쳤습니다.

그림 2. 노란 칸 둘은 확인 못 한 후보, 빨간 칸 하나가 확인된 빠뜨림이다

따라 고쳐짐 9: 짝 커밋이 불일치로 잡혔다

가장 흔한 모양은 같은 날의 짝 커밋이었어요. "Add resource redirection to WebFlux functional router"와 "Add resource redirection to WebMVC functional router"가 같은 날 따로 들어갔고, 이 한 쌍이 세 묶음(라우터 빌더와 라우터 함수 두 곳)에서 불일치 변경 두 번씩으로 잡혔습니다. 모듈별로 나눠 넣은 null 안전성 커밋도 같은 모양으로 세 묶음을 만들었어요. 9개 묶음이 실제로는 변경 다섯 건이었고, 커밋 단위로 세면 이런 짝이 전부 "일부만 바뀜"이 됩니다. 커밋이 아니라 버전 단위로 셌다면 같은 날 짝은 일관 변경으로 보였을 거예요.

이틀 늦은 경우는 사람이 알아챈 경우였어요. 사용자가 NamedParameterJdbcTemplate이 MySQL 백틱 안의 &를 매개변수로 읽는다고 보고했고(#31944), 수정은 jdbc의 NamedParameterUtils에만 들어갔습니다. 다음 날 다른 유지보수자가 이슈를 다시 열며 "Reopening to provide analogous support in org.springframework.r2dbc.core.NamedParameterUtils"라고 적었고, r2dbc 사본은 별도 이슈(#32285)로 "for consistency with spring-jdbc" 고쳐졌어요. 190일 늦은 경우가 글머리의 OutputStreamPublisher입니다.

동작 차이 없음 11개의 한 예는 서블릿과 리액티브의 DefaultServerResponseBuilder예요. 서블릿 쪽만 eTag 따옴표 처리를 지우고 HttpHeaders.setETag에 맡기는 커밋이 들어갔는데, 리액티브 쪽은 원래 headers.setETag만 부르고 있었습니다. 한쪽만 바뀌었지만 결과는 오히려 두 사본이 같은 일을 하게 됐어요.

한쪽만의 요구 17: 대부분은 고친 쪽에만 문제가 있었다

17개 중 15개는 읽어 보면 이유가 분명했어요. 나머지 2개(Reactor 클라이언트 생명주기를 정리하다 앞쪽 클래스가 새 이름으로 바뀐 두 묶음)는 판단할 근거가 부족해서 원 논문 규칙대로 의도로 쳤습니다. Netty 5 응답 쪽은 Partitioned 쿠키를 구현하는 대신 "TODO: support Partitioned attribute when available in Netty 5 API"를 남겼고, RestClient가 쿠키와 요청 속성을 얻은 변경은 WebClient에 이미 있던 기능을 따라간 것이었습니다. 하나는 직접 돌려서 확인했어요. webflux의 PartEventHttpMessageReader는 허용한 부분 수만큼 보내도 "Too many parts"로 거절하는 off-by-one이 있었고(#32122), 수정은 그 클래스에만 들어갔습니다. 거의 같은 부분 세기 코드를 가진 DefaultPartHttpMessageReader는 그대로였는데, 릴리스된 jar로 같은 본문을 읽혀 보니 이렇게 나왔어요.

spring-web 6.1.3 parts=2 maxParts=2 DefaultPart: ok, 2 items PartEvent: error: Too many parts (3/2 allowed) parts=3 maxParts=2 DefaultPart: error: Too many parts (3/2 allowed) PartEvent: error: Too many parts (3/2 allowed) spring-web 6.2.0 parts=2 maxParts=2 DefaultPart: ok, 2 items PartEvent: ok, 2 items

→ 결함은 PartEvent 쪽에만 있었다는 뜻이에요. 두 사본은 스트림을 부분으로 자르는 방법이 달라서(PartEvent는 헤더 토큰 앞에서 자르는데, 수정 커밋의 설명대로 빈 조각까지 세고 있었어요), 세는 코드가 같아도 같은 결함이 생기지 않았습니다. 사본이 같다고 결함까지 같지는 않았어요.

5. 빠뜨린 한 벌은 1년 반 동안 남았다

확인된 하나는 헤더 클래스였어요. 2024년 5월 24일 커밋(903493e9a9, "Various MultiValueMap improvements")이 MultiValueMap에 asSingleValueMap()(값 목록마다 첫 값만 보여 주는 뷰)을 더하면서, HttpHeaders와 ReadOnlyHttpHeaders에 내부 맵으로 넘기는 구현을 넣었습니다. WebSocketHttpHeaders는 HttpHeaders를 상속하면서 자기 필드에 든 다른 HttpHeaders로 모든 메서드를 넘기는 클래스이고, 그 위임 메서드 블록이 HttpHeaders의 같은 블록과 복제 묶음으로 잡혀 있었어요. 새 메서드는 그쪽에만 빠졌습니다. 상속받은 구현은 부모의 빈 맵을 봐요.

spring-web 6.2.0 (6.2.19 도 같다) HttpHeaders get=[Basic abc] toSingleValueMap={Authorization=Basic abc} asSingleValueMap={Authorization=[Basic abc]} ReadOnlyHttpHeaders get=[Basic abc] toSingleValueMap={Authorization=Basic abc} asSingleValueMap={Authorization=[Basic abc]} WebSocketHttpHeaders get=[Basic abc] toSingleValueMap={Authorization=Basic abc} asSingleValueMap={} spring-web 7.0.0 WebSocketHttpHeaders get=[Basic abc] toSingleValueMap={Authorization=Basic abc} asSingleValueMap={Authorization=[Basic abc]}

→ 같은 헤더를 넣었는데 WebSocketHttpHeaders만 빈 뷰를 돌려준다는 뜻이에요. 뷰의 toString()은 원래 맵을 찍어서 헷갈리기 쉬워, get과 size로 확인했습니다. 바로 옆의 toSingleValueMap()은 예전부터 위임돼 있어서 멀쩡했습니다. 고쳐진 건 2025년 11월 11일이에요. 사용자가 WebSocketHttpHeaders를 다른 헤더에 putAll하면 값이 사라진다고 보고했고(#35792), 그 수정 커밋 메시지가 "Overrides addAll(String, List), asSingleValueMap(), and asMultiValueMap() in WebSocketHttpHeaders"라고 적었어요. 다음 날 커밋은 아예 위임 필드를 없애 사본 자체를 지웠습니다. 7.0.0에만 들어갔고, 이번에 받은 6.2 계열 최신판(6.2.19, 2026-06)은 여전히 빈 맵이었어요.

그림 3. 다른 사본을 따라 고치게 만든 건 매번 사람이었고, 사람이 늦으면 몇 달이 그냥 지나갔다

확인 못 한 후보 둘도 적어 둘게요. 하나는 @SessionAttributes를 타입으로 지정했을 때 알게 된 속성 이름을 세션에 저장해 분산 세션에서도 복원하게 한 수정(#30463)이에요. 서블릿 쪽 SessionAttributesHandler에만 들어갔고, webflux 쪽은 지금 main까지도 메모리에 든 이름만 봅니다. 돌려 보지는 않았어요. 다른 하나는 RestTemplate 오류 메시지에 HTTP 메서드와 URL을 넣은 변경(#28958)이에요. 같은 메시지 코드를 복사해 가진 RestClient의 기본 처리기에는 들어가지 않았고, 같은 500 응답에 두 클라이언트가 낸 메시지는 7.0.0에서도 달랐습니다.

RestTemplate: 500 Internal Server Error on GET request for "<url>": [no body] RestClient: 500 Internal Server Error: [no body]

→ RestClient의 메시지에는 어느 요청이 실패했는지가 없다는 뜻이에요. 그 PR에서 기여자가 "is there a chance that the behaviour stays consistent across WebClient, RestTemplate and RestClient?"라고 물었고, 그 질문에 대한 답은 달리지 않았습니다. 다만 사흘 전 리뷰에서 유지보수자가 메시지에 전체 URI를 넣으면 쿼리의 민감한 정보가 드러날 수 있다고 했고, RestClient는 요청과 응답을 함께 받는 자체 오류 처리기 인터페이스를 따로 제공한다고 적었어요(#28958 의 2023-11-24 리뷰). 그러니 일부러 둔 차이일 수도 있고, 빠뜨린 것인지는 판단하지 못했어요.

6. 원 논문과 왜 이렇게 다르게 나왔나

원 논문에서는 불일치 묶음 중 28%가 의도하지 않은 것이었고, 같은 불일치 묶음을 분모로 15%가 결함이었어요. 의도하지 않은 것만 분모로 하면 절반(50%)이 결함이라는 뜻이고, "의도하지 않은 차이는 둘 중 하나꼴로 결함"이라는 말이 이 비율입니다. 이번에는 불일치 묶음 40개 중 빠뜨림으로 확인된 것이 1개(2.5%), 후보를 넣어도 3개(7.5%)예요. 같은 질문에 대한 답이 다르다고 하기 전에, 잰 것이 달랐다는 점을 짚어야 합니다.

보는 시간이 달라요. 원 논문은 2~17년 된 시스템의 현재 코드를 봤으니, 그동안 쌓인 모든 차이가 한 번에 보여요. 이번 실습은 1년이고, 기준 시점에 글자까지 같았던 묶음만 봤습니다. 이미 갈라진 사본은 애초에 묶음으로 잡히지 않았어요. 그리고 이 1년 안에 빠뜨린 것도 대개 그 안에 드러나지 않았습니다. 헤더 사본은 17개월 뒤에야 드러났어요. 판정하는 사람이 달라요. 개발자가 아니라 제가 읽었고, 증거가 없으면 의도로 쳤으니 이번 숫자는 아래쪽 경계예요. 저장소가 달라요. 원 논문은 COBOL 시스템의 비의도 비율이 10%로 낮았던 이유를 둘로 봤어요. 첫째는 의도와 결함을 분명히 가릴 수 없으면 의도로 친 보수적 판정이고(원 개발자에게 물을 수 없던 시스템이라 더 그랬어요), 이번 실습도 같은 편향을 가져요. 둘째는 유지보수자들이 복제를 찾는 일을 유지보수 절차의 일부로 하고 있어 복제를 더 잘 알고 있었다는 점입니다. Spring의 짝 커밋, 이슈를 다시 여는 습관, "Align" 이슈는 같은 종류의 인식으로 보입니다. 원 논문의 검출 알고리즘으로 다른 회사의 자바 시스템 셋을 본 Wagner 외의 연구도 개발자들이 type 3 복제 대부분을 동시에 고쳤다고 보고했어요(On the Relationship of Inconsistent Software Clones and Faults, 2016).

⚠️ 주의: 이 실습이 놓치는 것
• 이름만 바꾼 사본(type 2)과 이미 갈라진 사본(type 3)은 묶음에 없다. 원 논문이 결함을 찾은 곳이 바로 갈라진 사본이다
• 줄 범위로 따라가서, 사본 가장자리에 끼워 넣은 새 메서드도 "그 사본을 바꿨다"에 섞인다. 반대로 범위 끝에서 통째로 지운 줄은 놓친다(3장의 한 건)
• 기준 릴리스 뒤에 사본 안에 새로 쓴 코드는 대상이 아니다. 2024년 9월 webflux 쪽 경로 검사 한 줄만 고친 커밋(gh-33568)은 그 줄이 v6.1.0에 없어서 세지 않았다
• 저장소 하나, 1년, 사람 하나의 판정이다

하나 더 눈에 띈 게 있어요. 공통 유틸리티로 옮겨 중복을 없앤 묶음이 넷 있었는데(ETag 처리, 정적 자원 처리), 정적 자원 쪽은 webflux와 webmvc에 ResourceHandlerUtils가 하나씩 새로 생겼고, v6.2.0의 CPD가 그 둘을 다시 복제 묶음 4개로 잡았습니다. 스택 안의 중복은 합쳐도, 스택 사이의 사본은 다시 두 벌이 됐어요.

💡 실무에서는
• 두 스택에 같은 코드를 둘 수밖에 없다면, 한쪽을 고치는 커밋이나 이슈에 다른 사본의 경로를 적는다. 이번에 따라 고쳐진 9개는 전부 사람이 다른 사본을 찾아 고친 경우였다
• 복제 묶음 목록은 경고로 내보내는 것보다 "이 파일을 고쳤으면 저 파일도 봤나"를 리뷰에서 묻는 데 쓴다. CPD 결과에 사본 위치가 다 있다
• 일부만 바뀐 비율(이번에 절반)은 위험의 크기가 아니다. 대부분은 일부러 갈라 놓은 것이었고, 숫자가 아니라 하나씩 읽어야 빠뜨린 것이 나온다
• CPD의 --ignore-identifiers는 고친 판(7.29.0, 이 글을 쓸 때 아직 SNAPSHOT)이 나오면 쓴다. 그 전에는 식별자 정규화를 끈다. 7.28.0은 큰 저장소에서 파일 순서에 따라 멈춘다
✍️ 오늘의 요약
spring-framework 6.1.0에서 찾은 복제 묶음 256개를 6.2.0까지 1년 따라가니, 코드가 바뀐 79개 중 40개(51%)에서 일부 사본만 바꾼 커밋이 나왔어요. 최소 토큰을 75나 150으로 바꿔도 47~55%였어요. 변경 단위로는 불일치가 43~48%로, 이력으로 센 선행 연구의 "절반 정도"와 같았습니다. 그런데 40개를 하나씩 읽으니 9개는 창 안에서 다른 사본도 따라 고쳐졌고, 11개는 동작 차이가 없었고, 17개는 고친 쪽에만 필요한 변경이거나(15개) 판단할 근거가 없어 의도로 친 것(2개)이었어요. 다른 사본에 필요했는데 빠진 것으로 확인된 건 WebSocketHttpHeaders.asSingleValueMap() 하나였고, 이 한 벌은 약 17개월 뒤 다른 버그 보고를 계기로 7.0에서 고쳐졌으며 6.2.19에서는 지금도 빈 맵을 돌려줘요.

바뀐 복제 코드의 절반은 따로 고쳐졌지만, 따로 고친 것의 대부분은 실수가 아니었어요. 실수였던 한 벌은 드물었고, 대신 오래 남았습니다.
