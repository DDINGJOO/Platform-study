실습-2. 복사해 붙인 코드가 바뀔 때 절반은 따로 고쳐지고, 놓친 한 벌은 오래 남는다

3편은 장애 회고에서 나온 결정 하나로 시작했어요. "하위 서비스 호출은 시도 하나를 0.5초에서 끊고, 첫 시도를 포함해 최대 3번까지 시도하자." 그리고 이 결정이 서비스 전부에 퍼지는 비용을 세 축으로 나눴습니다. 정책 값을 바꿀 때 무엇을 다시 띄우나(축 1), 구현을 올릴 때 무엇을 다시 띄우나(축 2), 그동안 옛 정책과 새 정책이 함께 응답하는 창(이 글에서는 줄여서 섞인 창이라고 부를게요)은 얼마나 긴가(축 3)입니다.

이번 실습은 그 세 축을 서비스 다섯 개로 셉니다. 같은 정책을 공통 스타터 jar에 넣은 판, 같은 스타터가 실행 중에 정책 파일을 읽는 판, 서비스마다 Envoy 사이드카를 붙인 판으로 각각 바꿔 봤고, 마지막으로 사이드카 Envoy 자체의 버전을 올려 봤어요. 각 방식을 세 번씩 돌렸고, 숫자는 전부 이번에 돌린 결과입니다. 값이 jar에 구워져 있을 때는 정말로 서비스 다섯 개가 다시 떴어요. 그런데 같은 스타터라도 값을 실행 중에 읽게 하자 아무것도 다시 뜨지 않았습니다. 그러니 이 실습의 축은 "라이브러리 대 사이드카"가 아니라 "빌드에 구운 값 대 실행 중에 읽는 값"이에요. 그리고 사이드카도 자기 버전을 올리는 날에는 다섯 번 다시 떴습니다.

🧭 이 글에서 확인할 것
• 정책이 스타터 jar 안에 있으면 값 하나 바꾸는 데 무엇이 몇 번 다시 뜨고, 그동안 요청은 몇 건 실패하나?
• 사이드카의 설정만 바꾸면 정말 아무것도 다시 뜨지 않나? 섞인 창은 얼마나 되나?
• 라이브러리라도 정책을 실행 중에 읽는 파일로 빼면 무엇이 달라지나? 그 파일이 틀리면?
• 사이드카 Envoy의 버전을 올리면 무엇이 다시 뜨나?
• 그 대신 사이드카 한 홉은 지연과 메모리를 얼마나 쓰나?

1. 실습 환경: 서비스 다섯, 정책이 사는 곳 셋

서비스 다섯 개(svc1~svc5)가 하위 서비스 backend 하나를 부릅니다. backend는 모든 요청에 5ms 뒤 응답하고, 그중 10%는 503, 나머지는 200이에요. 서비스는 Spring Boot 4.1.1 앱이고 GET /work를 받으면 backend의 /data를 한 번 부른 결과를 돌려줍니다. 바꾸는 정책은 3편 서두의 그것이에요.

정책 뜻 스타터(Resilience4j Retry) Envoy 라우트 v1 재시도 없음, 요청 하나에 2초 maxAttempts=1, 읽기 타임아웃 2000ms retry_policy 없음, timeout: 2s v2 최대 3번, 시도당 0.5초 maxAttempts=3, 읽기 타임아웃 500ms, 대기 25ms num_retries: 2, per_try_timeout: 0.5s retry_on: 5xx,reset,connect-failure

같은 "최대 3번"이 두 도구에서 숫자가 다르게 적혀요. Resilience4j의 maxAttempts는 문서 표현대로 첫 호출을 첫 시도로 포함한 최대 시도 횟수라 3이고(Resilience4j Retry), Envoy의 num_retries는 재시도 횟수라 2입니다. Envoy 문서는 per_try_timeout이 첫 시도를 포함한 시도마다의 타임아웃이라고 적어요(route_components.proto, RetryPolicy). Resilience4j의 재시도 대기 기본값은 500ms라서 25ms 고정으로 줄였어요. Envoy의 기본 백오프는 첫 재시도를 0~25ms 사이에서 고르게(평균 12.5ms) 뽑고 그다음부터 상한을 두 배씩 늘리는 지터 지수 백오프라(트래픽 관리 실습-5에서 잰 것), 두 판의 재시도 간격이 똑같지는 않아요. 이 실습은 간격이 아니라 무엇이 다시 뜨는지를 재므로 그 차이는 두었습니다.

이 정책을 세 군데에 두고 v1에서 v2로 바꿨어요. 네 번째 방식은 정책을 v2로 둔 채 사이드카 Envoy 버전만 올립니다.

그림 1. 같은 정책을 jar 안, 실행 중에 읽는 파일, 옆 프록시의 설정 파일에 두었다

lib는 플랫폼 스타터(platform-starter)가 자동 구성으로 재시도와 타임아웃이 걸린 HTTP 클라이언트 빈을 만들어 줍니다. 정책 값은 스타터를 빌드할 때 jar 안의 속성 파일에 구워져요. 정책을 바꾸려면 스타터 1.1.0을 내고, 서비스마다 의존성 버전을 1.1.0으로 올려 이미지를 다시 빌드하고, 한 대씩 다시 띄웁니다. dyn은 같은 스타터에 정책 파일 경로를 줘서, 스타터가 그 파일을 1초마다 읽고 바뀌면 클라이언트를 새로 만들어 바꿔 끼우게 했어요. sidecar는 앱이 재시도 없는 클라이언트로 127.0.0.1:15001을 부르고, 그 옆의 Envoy가 라우트 설정 파일에 적힌 정책대로 backend를 부릅니다.

📖 용어: 네트워크 이름공간 공유
컨테이너 둘이 같은 네트워크 인터페이스와 127.0.0.1을 쓰게 하는 설정이에요. Compose의 network_mode: service:sc-svc1이 그 일을 하고, 쿠버네티스 파드 안의 컨테이너들이 원래 이렇게 묶입니다. 그래서 앱이 127.0.0.1:15001을 부르면 옆 컨테이너의 Envoy가 받아요.

Envoy는 라우트 설정을 RDS로 받는데, 컨트롤 플레인 대신 파일에서 읽게 했어요(path_config_source). 컨트롤 플레인을 띄우지 않고도 "프록시를 재기동하지 않고 정책만 바꾼다"를 재현하려는 선택입니다. 새 파일로 바꿔치우는 일(rename)이 3편의 "xDS로 밀어 준다"를 대신해요.

📖 용어: RDS, path_config_source
RDS(Route Discovery Service)는 Envoy가 라우트 설정(어느 경로를 어느 클러스터로, 재시도와 타임아웃은 얼마로)을 실행 중에 받아 오는 xDS API 하나예요. 보통은 컨트롤 플레인에서 받지만, path_config_source를 쓰면 로컬 파일에서 읽고 그 파일이 바뀌면 다시 읽습니다.

요청마다 어느 정책이 적용됐는지는 응답 헤더로 셌어요. 스타터는 X-Policy(정책 이름)와 X-Attempts(시도 수)를 직접 붙이고, 사이드카 쪽은 Envoy가 라우트의 response_headers_to_add로 붙인 정책 이름과 x-envoy-attempt-count를 앱이 옮겨 줍니다. 부하기는 서비스마다 초당 20건(합 100건)을 일정하게 보내고, 요청마다 시각, 상태 코드, 정책 이름을 한 줄씩 남겨요. 한 번의 실행은 부하 20초, 바꾸기, 부하 20초입니다.

📖 용어: 열린 부하 (open-loop)
앞 요청의 응답을 기다리지 않고 정해진 간격으로 계속 보내는 부하예요. 서비스가 잠깐 죽어도 요청이 줄지 않으니, 그동안 몇 건이 실패했는지를 그대로 셀 수 있습니다. 응답을 기다린 뒤 다음 요청을 보내는 닫힌 부하라면 서비스가 죽은 동안 요청 수 자체가 줄어 실패가 작아 보여요.
git clone https://github.com/DDINGJOO/Platform-study.git cd Platform-study/labs/devops/pc-01-policy-rollout ./scripts/setup.sh # 스타터 1.0.0(v1)과 서비스 이미지 다섯 개 ./scripts/run_all.sh # lib, sidecar, dyn, upgrade 를 번갈아 세 번씩 (약 15분) python3 scripts/analyze.py lib-1 sidecar-1 dyn-1 upgrade-1 ./scripts/latency.sh # 사이드카 한 홉의 지연과 메모리

Spring Boot 4.1.1(Java 21), Resilience4j 2.4.0, Gradle 9.8.1, Envoy v1.39.2와 v1.39.3, k6 2.3.0을 썼고, Docker 29.5.3과 Compose v5.1.4, Docker Desktop VM(15 CPU, 7.7GiB), Apple M5 Pro에서 돌렸어요. 코드는 labs/devops/pc-01-policy-rollout에 있고, 실행별 요약은 results/summary.txt에 있습니다.

2. 스타터 안의 정책: 다섯 번 빌드하고 다섯 번 다시 떴다

lib의 두 번째 실행을 시각 순서로 보면 이래요. 바꾸기 시작을 0초로 둔 시각입니다.

0.0s 스타터 1.1.0 빌드 시작 (v2 를 jar 에 굽는다) 3.4s 스타터 1.1.0 발행 3.5s svc1 이미지 빌드 시작 (스타터 1.1.0 으로) 8.0s svc1 빌드 끝, docker compose up -d --no-deps lib-svc1 시작 (옛 컨테이너를 멈추고 새로 만든다) 8.2s svc1 에 v1 으로 응답한 마지막 요청 8.9s compose up 반환 10.0s svc1 에 v2 로 응답한 첫 요청 ← 여기서부터 섞인 창 ... svc2, svc3, svc4 반복 35.6s svc5 에 v1 으로 응답한 마지막 요청 ← 섞인 창 끝 37.3s svc5 에 v2 로 응답한 첫 요청 37.4s 스크립트가 svc5 의 v2 를 확인 ← 바꾸기 끝 (요청 시각은 부하기가 보낸 시각) 서비스 v2 첫 요청 v1 마지막 요청 재기동 중 실패 한 번에 이어진 실패 svc1 9.98s 8.18s 35건 1.70s svc2 17.43s 15.53s 37건 1.80s svc3 23.93s 22.23s 33건 1.60s svc4 30.74s 28.68s 40건 1.95s svc5 37.28s 35.58s 33건 1.60s 다시 시작한 컨테이너 5개, 섞인 창 25.6초

세 번의 숫자는 이렇습니다. 바꾸기 시작부터 끝까지 30.1초, 37.4초, 34.9초. 섞인 창은 20.1초, 25.6초, 23.5초. 다시 시작한 컨테이너는 매번 서비스 다섯 개였고, 바꾸는 동안 연결 실패로 끝난 요청은 162건, 178건, 176건이었어요. 서비스 하나가 재기동하는 동안 31~40건씩, 1.5~1.95초 동안 이어서 실패했습니다.

시간이 어디에 쓰였는지 나눠 보면, 스타터 빌드와 발행이 2.5~3.4초, 서비스 이미지 빌드가 하나에 3.4~5.2초, docker compose up이 0.8~1.2초, docker compose up이 돌아온 뒤 v2로 응답하기까지 1.0~1.4초였어요. 빌드가 이렇게 짧은 데는 이유가 있습니다. 서비스 코드가 클래스 세 개이고, Gradle 의존성 캐시가 이미 데워져 있었어요. CI 대기열도, 리뷰도, 배포 승인도 없고, 다섯 서비스를 한 스크립트가 쉬지 않고 차례로 처리했습니다. 3편이 말한 "서비스팀이 각자 자기 일정에 맞춰" 하는 부분이 통째로 빠진 거예요. 그래서 이 25초 안팎의 창은 하한이고, 실제 조직에서는 같은 창이 며칠에서 몇 주가 됩니다. 이 실습이 보여 주는 건 그 창의 길이가 아니라, 창이 서비스 수만큼의 빌드와 재기동으로 이뤄진다는 구조예요.

⚠️ 주의: 실패 건수는 서비스가 한 대씩이라서 나왔다
서비스마다 컨테이너가 한 대뿐이라, 재기동하는 1.5~2초 동안 그 서비스로 간 요청이 연결 실패로 끝났어요. 여러 대를 두고 준비 상태를 확인하며 한 대씩 바꾸는 롤링 배포라면 이 실패는 거의 없앨 수 있습니다. 그래도 재빌드 다섯 번, 재기동 다섯 번(대수가 늘면 그 배수), 그리고 그동안의 섞인 창은 그대로 남아요.

정책 효과도 숫자로 보였어요. 바꾸기 전 v1에서는 요청의 9~10%가 502(하위 503을 그대로 전달)였고, 바꾼 뒤 v2에서는 0~0.3%였습니다. 시도 세 번이 모두 10% 확률로 실패할 때의 이론값 0.1%(0.1의 세제곱)와 같은 자릿수예요. 그 대가로 backend가 받은 요청은 부하기가 보낸 요청보다 그만큼 늘었습니다. 재시도가 하위 부하를 늘리는 이야기는 트래픽 관리 실습-5에서 했어요.

3. 사이드카 설정: 다시 뜬 컨테이너 0개

같은 정책을 다섯 사이드카의 라우트 파일로 바꿨어요. 세 번의 결과입니다.

실행 바꾸기 시작~끝 섞인 창 다시 시작한 컨테이너 연결 실패 sidecar-1 0.8s 0.45s 0 0 sidecar-2 0.9s 0.50s 0 0 sidecar-3 0.8s 0.40s 0 0 sidecar-2 서비스별: svc1 v2 첫 요청 0.13s / v1 마지막 요청 0.08s svc5 v2 첫 요청 0.68s / v1 마지막 요청 0.63s

컨테이너의 시작 시각과 재시작 횟수를 바꾸기 전후로 떠 두었는데 하나도 바뀌지 않았어요. 연결 실패도 0건이었습니다. 3편의 예상대로 축 1에서는 설정만 바뀌었어요. Envoy 통계의 http.egress.rds.backend_route.version_text가 "v2"로 바뀐 것으로 각 프록시가 새 파일을 받은 걸 확인했습니다.

섞인 창이 0이 아닌 것도 3편이 말한 그대로예요. 사이드카 하나만 보면 v1으로 응답한 마지막 요청과 v2로 응답한 첫 요청 사이는 0.05초 안팎인데, 다섯 개 전체로는 0.40~0.50초였습니다. 이 0.4초는 스크립트가 다섯 사이드카에 차례로 docker exec를 부른 시간이에요. 컨트롤 플레인이 수백 개 프록시에 밀어 주는 실제 메시라면 이 창은 프록시가 몇 개인지, 컨트롤 플레인이 얼마나 빨리 보내는지에 달려 있고, 이 실습은 그 규모를 재지 않았어요.

⚠️ 주의: 호스트에서 바꾼 파일을 Envoy가 못 봤다
처음에는 호스트에서 새 파일을 만들어 mv했어요. 컨테이너에 바인드 마운트한 디렉터리라 컨테이너 안에서도 파일 내용은 바로 바뀌었는데, Envoy는 30초가 지나도 v1이었습니다. Envoy 문서는 path_config_source의 파일을 "옮겨짐(move)" 이벤트로 감시한다고 적어요. 원자적인 건 대개 move뿐이라서입니다(config_source.proto, PathConfigSource). Docker Desktop(macOS)의 바인드 마운트에서는 호스트 쪽 rename이 컨테이너 안에 그 이벤트로 오지 않았어요. 같은 rename을 docker exec로 컨테이너 안에서 하자 1초 안에 v2가 됐습니다.

최신 문서에는 알림이 믿을 만하지 않은 파일 시스템을 위한 poll_interval(일정 간격으로 읽기)이 있다고 나와요. 이 필드는 v1.39.4 문서에는 없고 v1.40.0(2026년 10월 13일 릴리스) 문서부터 있어요(v1.40.0, v1.39.4). 이 실습의 v1.39.3에 넣어 보니 no such field: 'poll_interval'로 기동부터 실패했습니다. 문서 "latest"는 지금 쓰는 버전보다 앞서 있을 수 있어요.
📖 용어: inotify
리눅스 커널이 파일이나 디렉터리에 생긴 변화(만들어짐, 고쳐짐, 옮겨짐)를 프로그램에 알려 주는 기능이에요. Envoy의 파일 감시가 이걸 씁니다. 변화가 그 커널 안에서 일어나야 이벤트가 생기니, 다른 커널(여기서는 macOS 호스트)에서 바꾼 파일은 공유 방식에 따라 이벤트가 안 올 수 있어요.

4. 라이브러리라도 값을 파일로 빼면

3편의 표는 라이브러리 경로의 비용이 "값이 어디에 있느냐"로 갈린다고 했어요. dyn이 그걸 잽니다. 같은 스타터, 같은 이미지(1.0.0)이고 정책을 서비스마다 마운트한 파일에서 1초마다 읽게만 했어요.

실행 바꾸기 시작~끝 섞인 창 다시 시작한 컨테이너 연결 실패 dyn-1 1.1s 0.90s 0 0 dyn-2 0.4s 0s (겹침 없음) 0 0 dyn-3 1.2s 0.95s 0 0

재빌드도 재기동도 없이 사이드카와 같은 자릿수로 끝났어요. 창이 0초에서 0.95초 사이로 흔들린 건 1초 폴링 때문입니다. 다섯 파일을 거의 동시에 바꿨는데, 세 번 중 두 번은 svc5만 다음 폴링까지 1초 가까이 늦게 읽었어요. 축 1에서 라이브러리와 사이드카의 차이는 "앱 안이냐 밖이냐"가 아니라 "값이 코드와 함께 빌드되느냐, 실행 중에 읽히느냐"였습니다.

그 대신 이 순간 정책 파일이 배포 대상이 돼요. 파일을 일부러 틀려 봤습니다.

(out/extra-badfile.txt 발췌. /policy 응답은 mode·svc·starter 필드를 뺐고, 로그는 시각과 로거 이름을 뺐다) ## maxAttempts=three 로 바꾼 뒤 {"policy":"v1", "maxAttempts":1, "timeoutMs":2000} WARN policy file unreadable, keeping CallPolicy[name=v1, ...]: java.lang.NumberFormatException: For input string: "three" ## maxAttempts=0 으로 바꾼 뒤 {"policy":"v1", "maxAttempts":1, "timeoutMs":2000} WARN policy file unreadable, keeping CallPolicy[name=v1, ...]: java.lang.IllegalArgumentException: maxAttempts must be greater than or equal to 1 ## maxAttempts=50, timeoutMs=1 로 바꾼 뒤 {"policy":"v9", "maxAttempts":50, "timeoutMs":1} X-Attempts: 50 X-Attempts: 50 X-Attempts: 50 INFO policy changed CallPolicy[name=v9, maxAttempts=50, timeoutMs=1]

→ 숫자가 아닌 값은 파싱에서, 0은 Resilience4j의 설정 검사("1 이상이어야 한다")에서 걸려 스타터가 옛 정책을 지켰다는 뜻이에요. 다만 파일을 고칠 때까지 같은 WARN이 1초마다 찍혔습니다. 그런데 형식은 맞지만 위험한 값(시도 50번, 시도당 1ms)은 1초 안에 적용됐고, 이어진 요청 세 개가 모두 50번씩 시도했습니다. 다섯 서비스 파일을 다 이렇게 바꿨다면 하위 서비스가 받는 요청은 순식간에 수십 배가 됐을 거예요. 재빌드가 사라지면서 빌드와 리뷰가 걸러 주던 기회도 같이 사라진 거예요. 5편이 설정 변경도 배포처럼 단계적으로 내보내고 검증해야 한다고 말하는 이유가 이 장면입니다.

5. 사이드카를 올리는 날: 다섯 개가 다시 떴다

이번에는 정책을 v2로 둔 채 사이드카 Envoy를 v1.39.2에서 v1.39.3으로 한 대씩 다시 만들었어요. 축 2입니다.

실행 바꾸기 시작~끝 다시 시작한 컨테이너 사이드카가 없어 실패한 요청 upgrade-1 2.4s Envoy 5개 (앱 0개) 503 20건 upgrade-2 2.1s Envoy 5개 (앱 0개) 503 19건 upgrade-3 1.9s Envoy 5개 (앱 0개) 503 18건 사이드카 하나당 3~5건, 한 번에 0.1~0.2초

정책을 바꿀 때 0이던 재기동이 여기서는 다섯 번이 됐어요. 사이드카가 내려가 있던 0.1~0.2초 동안 앱이 127.0.0.1:15001에 연결하지 못해 503을 냈습니다. 정책은 그대로 v2였어요. 라우트 파일이 호스트 디렉터리에 남아 있어서 새 Envoy도 v2로 떴습니다. 프록시를 다시 만들 때 마지막 설정을 누가 다시 주느냐는 실제 메시에서는 컨트롤 플레인의 몫이에요.

앞서 버린 두 바퀴(아래 6장)의 upgrade에서는 매번 1~4건이 앱의 500으로 끝났어요. 앱 로그는 이랬습니다.

RestClientException: Error while extracting response for type [java.lang.String] and content type [application/json] java.io.EOFException: EOF reached while reading

→ 앱이 사이드카에게서 응답 본문을 받는 도중에 사이드카 컨테이너가 멈춰 연결이 끊겼다는 뜻이에요. 컨테이너를 멈추는 신호를 받은 Envoy가 처리 중이던 응답을 마저 보내지 못하고 내려간 것으로 보여요(Envoy 쪽 로그로 확인하지는 않았어요). 그래서 Envoy를 운영 중에 내리는 제품들은 내리기 전에 할 일을 따로 둬요. 예를 들어 Envoy Gateway(쿠버네티스 Gateway API 구현) 문서를 보면, 종료 신호를 받은 관리 프로세스가 리스너 배수를 시작하고 헬스 체크를 실패로 돌려 새 트래픽이 오지 않게 한 뒤, 이미 받은 연결은 계속 처리하면서 연결 수를 지켜봅니다. 연결이 0이 되거나 배수 시한(기본 60초)이 지나면 끝내고, 그 전에 최소 대기 시간(기본 10초)은 채워요(Graceful Shutdown and Hitless Upgrades). 이 실습의 사이드카에는 그런 장치가 없었어요.

⚠️ 주의: 쿠버네티스였다면 앱도 같이 다시 떴다
이 실습에서는 Compose가 Envoy 컨테이너만 다시 만들고 앱 컨테이너는 그대로 두었어요(앱 재기동 0개). 쿠버네티스에 주입된 사이드카는 사정이 달라요. 3편이 인용한 Istio 카나리 업그레이드 문서대로 새 프록시를 받으려면 파드를 재시작해야 하고, 파드가 다시 뜨면 앱 컨테이너도 다시 뜹니다. 그 경우 축 2의 비용은 2장의 lib에서 빌드만 뺀 것, 즉 서비스 다섯 개의 재기동에 가까워요. 이 실습의 0.1~0.2초는 Envoy 하나가 뜨는 시간이지, 파드가 다시 뜨는 시간이 아닙니다.
그림 2. 같은 정책 변경이 lib에서는 35초 넘게 걸렸고, 그중 25초 넘게가 섞인 창이었다

6. 사이드카 한 홉의 값

사이드카가 축 1에서 이긴 값은 매 요청이 한 홉을 더 지나는 것으로 냅니다. 하위 실패를 0으로, 정책을 v1(재시도 없음)으로 두고 같은 네트워크 안의 k6로 초당 200건씩 60초를 세 경로에 두 바퀴 보냈어요.

경로 p50 p90 p99 k6 → backend (기준) 6.12ms 7.10ms 7.87ms 6.26ms 7.41ms 9.34ms k6 → lib-svc1 → backend 6.83ms 7.93ms 9.49ms 7.08ms 8.08ms 9.97ms (12,000건 중 1건 실패) k6 → sc-svc1 → Envoy → backend 7.33ms 8.68ms 10.16ms 7.35ms 8.38ms 10.32ms 메모리 (docker stats): Envoy 사이드카 17.2~23.5MiB씩, 앱 163~242MiB씩 (-Xmx160m)

같은 앱에 Envoy 한 홉을 더한 값은, 같은 바퀴의 lib와 sidecar끼리 빼면 p50에서 0.27~0.50ms, p99에서 0.35~0.67ms였어요. 사이드카 다섯 개의 메모리는 합쳐 100MiB에 조금 못 미쳤습니다. 앱 하나보다 작아요. 이 숫자는 같은 노트북 안, 초당 200건, TLS 없는 HTTP/1.1 평문에서 잰 것이라 운영 환경의 메시(상호 TLS, 텔레메트리 필터, 수천 개 엔드포인트의 설정)에 그대로 옮기면 안 됩니다. 이 실습에서 말할 수 있는 건 "정책 하나 바꾸는 데 아낀 재기동 다섯 번의 값을 요청마다 1ms가 안 되는 지연으로 냈다"까지예요.

사실 이 표는 한 번 틀렸어요. 처음 잰 표에서는 lib와 sidecar의 p50이 둘 다 48ms 근처에 몰려 있었고, k6가 바로 부른 backend만 6ms였습니다. 사이드카 비용을 재러 갔다가 엉뚱한 40ms를 잰 셈이에요. 원인은 backend였습니다. 파이썬 BaseHTTPRequestHandler는 헤더와 본문을 따로 쓰는데, Nagle 알고리즘이 켜져 있으면 둘째 쓰기가 첫째 쓰기의 ACK를 기다리고, 받는 쪽은 ACK를 모아 보내려고 잠깐 미룹니다. 연결을 재사용하는 클라이언트(JDK HttpClient, Envoy)에서 이 대기가 보였던 것으로 봐요. 다만 k6도 연결을 재사용하는데 k6가 backend를 바로 부를 때는 6ms였고, 그쪽이 왜 괜찮았는지는 확인하지 못했어요. backend의 소켓에서 Nagle을 끄자(disable_nagle_algorithm = True) 세 경로가 모두 6~7ms로 돌아왔고, 그 뒤 지연 비교와 1~5장의 실행을 전부 다시 했습니다.

📖 용어: Nagle 알고리즘, 지연 ACK
Nagle 알고리즘은 작은 패킷을 여러 번 보내지 않으려고, 앞서 보낸 데이터의 ACK가 오기 전에는 다음 작은 데이터를 모아 두는 TCP 동작이에요. 지연 ACK는 받는 쪽이 ACK를 곧바로 보내지 않고 잠깐 미뤄 다른 데이터와 같이 보내는 동작입니다. 둘이 만나면 작은 응답 하나가 수십 ms씩 늦어져요. 소켓에 TCP_NODELAY를 켜면 Nagle이 꺼집니다.

버린 실행

최종 결과는 세 번째 바퀴(방식 넷 × 세 번 = 12번, 지연 비교 두 바퀴)입니다. 그 앞에 시험 실행 4번과 두 바퀴 24번을 버렸어요. 첫 바퀴는 "바꾸기 시작" 표시를 컨테이너 상태를 떠 두는 docker inspect보다 먼저 찍어서 그 시간이 바꾸는 시간에 섞였고, 그중 dyn 하나는 그 명령이 5.8초 걸리는 동안 요청이 타임아웃으로 쏟아졌습니다(호스트 쪽이 잠깐 멈춘 것으로 보이고, 원인은 확인하지 못했어요). 두 번째 바퀴는 위의 Nagle 문제가 있던 판이에요. 버린 두 바퀴도 재기동 수와 걸린 시간의 흐름은 최종과 같았습니다. 바꾸기 시작부터 끝까지가 첫 바퀴는 lib 35.2~36.1초, sidecar 0.9초, 둘째 바퀴는 lib 39.4~42.0초, sidecar 0.8~0.9초였어요.

그림 3. 사이드카가 "설정만 바뀐다"는 건 축 1의 이야기였고, 축 2에서는 사이드카도 다섯 번 다시 떴다
💡 실무에서는
• 공통 스타터의 정책 기본값은 jar에 굽지 말고 속성으로 빼 둡니다. 이번 실습에서 같은 변경이 재빌드·재기동 다섯 번(30~37초)에서 재기동 0번(1초 안팎)으로 내려왔어요
• 대신 정책을 실행 중에 읽는다면 형식 검사만으로 멈추지 말고 값의 범위(시도 횟수 상한, 타임아웃 하한)를 검사하고, 한 서비스씩 내보냅니다. 형식이 맞는 시도 50번은 1초 만에 적용됐어요
• 어떤 정책이 적용됐는지 응답 헤더나 지표로 내보내 두면 섞인 창을 직접 셀 수 있어요. 이번에는 X-Policy 헤더 하나로 요청마다 셌습니다
• 사이드카를 쓰면 프록시 업그레이드 날을 따로 계산합니다. 정책 변경에서 아낀 재기동이 그날 한꺼번에 돌아오고, 프록시를 내리기 전에 배수(drain)하지 않으면 처리 중이던 응답이 끊겨요
• 파일로 설정을 받는 프록시를 컨테이너에서 쓴다면, 파일을 바꾼 쪽과 감시하는 쪽이 같은 커널인지 확인합니다. Docker Desktop에서는 호스트 쪽 rename이 Envoy에게 닿지 않았어요
✍️ 오늘의 요약
재시도 정책을 "재시도 없음, 2초"에서 "최대 3번, 시도당 0.5초"로 바꾸자, 정책이 스타터 jar 안에 있을 때는 스타터 빌드 한 번, 서비스 빌드 다섯 번, 재기동 다섯 번이 필요했어요. 데워진 캐시와 작은 코드로도 30~37초가 걸렸고, 그중 20~26초가 섞인 창이었으며, 서비스가 한 대씩이라 재기동마다 31~40건이 실패했어요. 같은 정책을 사이드카 Envoy의 라우트 파일로 바꾸자 다시 뜬 컨테이너는 0개, 실패는 0건, 섞인 창은 0.5초 안쪽이었어요. 같은 스타터라도 정책을 실행 중에 읽는 파일로 빼면 재기동 없이 1초 안팎에 끝났지만, 형식만 맞으면 시도 50번 같은 값도 그대로 들어갔어요.

사이드카 Envoy를 v1.39.2에서 v1.39.3으로 올리자 이번에는 사이드카 다섯 개가 다시 떴고 그동안 18~20건이 503으로 끝났어요. 그 대가로 낸 한 홉은 p50 0.3~0.5ms, 사이드카 하나 17~24MiB였습니다. 사이드카가 설정만 바뀌는 건 값을 바꿀 때까지이고, 무엇이 다시 뜨는지는 바꾸는 것이 값이냐 구현이냐가 정해요.
