🧭 플랫폼 엔지니어링, 3편
1편. 경고는 아무도 읽지 않고, 고쳐 주는 도구는 쓰인다
2편. SRE를 따로 둘지는 공통 문제를 맡을 사람이 있느냐가 정한다
3편. 공통 기능은 실어 보내는 경로가 업그레이드 값을 정한다 ← 지금 이 글
4편. 테스트는 아는 것을 증명하고, 모니터링은 모르는 것을 보여 준다
5편. 설정 변경도 배포다
6편. 임시방편은 빚이지만, 갚을지는 남은 수명이 정한다
실습-1. 재시도 값을 jar에 구우면 다섯 번 다시 뜨고, 사이드카에 두면 설정만 바뀐다
실습-2. 복사해 붙인 코드가 바뀔 때 절반은 따로 고쳐지고, 놓친 한 벌은 오래 남는다

장애 회고가 끝나고 결론이 하나 나왔습니다. "하위 서비스 호출은 시도 하나를 0.5초에서 끊고, 첫 시도를 포함해 최대 3번까지 시도하자." 지금까지는 재시도 없이 2초를 다 기다렸고, 느린 응답 몇 개가 요청 스레드를 붙잡아 장애를 키웠다는 분석이었어요. 결정은 10분 만에 났습니다. 그런데 이 결정이 운영 중인 서비스 전부에 실제로 반영되기까지는 얼마나 걸릴까요?

재시도 로직이 플랫폼팀이 만든 공통 라이브러리 안에 있다면, 라이브러리 새 버전을 내고 서비스마다 의존성 버전을 올리는 PR을 열고, 빌드하고, 배포해야 해요. 서비스가 마흔 개면 그 일이 마흔 번 일어납니다. 3주 뒤에도 일곱 개는 예전 버전일 수 있어요. 같은 정책이 서비스 메시의 사이드카 설정에 있다면, 설정 한 번 바꾸면 몇 초 안에 전체 프록시가 새 값을 받습니다. 여기까지만 보면 답이 정해진 것 같아요. 그런데 그 메시의 프록시 버전을 올리는 날에는 반대로 모든 파드를 한 번씩 다시 띄워야 합니다.

이번 편은 재시도, 메트릭, 트레이스 태그 같은 공통 기능을 서비스에 실어 보내는 경로를 다섯 가지로 나누고, 각 경로가 업그레이드 비용을 어떻게 다르게 매기는지 봅니다. 기능 자체를 앱에 둘지 메시에 둘지의 비교(언어 지원, 도메인 지식 같은 기준)는 트래픽 관리 7편의 "앱에 둘까, 서비스 메시에 둘까" 절에서 했어요. 여기서는 그 다음 질문, 정했다면 바꿀 때 얼마를 내느냐를 다룹니다.

🧭 이 글에서 확인할 것
• 공통 기능을 서비스에 실어 보내는 경로에는 무엇이 있나?
• "정책 값을 바꾸는 일"과 "구현을 업그레이드하는 일"은 왜 따로 재야 하나?
• 경로마다 무엇을 다시 띄우고, 버전이 섞인 상태는 얼마나 이어지나?
• 사이드카가 라이브러리보다 기능이 모자라다는 말은 지금도 맞나?
• 중앙화와 탈중앙화 사이를 오가는 유행 대신 무엇을 기준으로 고르나?

1. 공통 기능은 결국 어딘가에 실려 간다

플랫폼팀이 하는 일은 객체 지향의 캡슐화와 닮은 데가 있습니다. 재시도를 몇 번 할지, 메트릭에 어떤 태그를 붙일지, 트레이스 문맥을 어떻게 넘길지 같은 일을 서비스팀이 매번 알 필요가 없게 감추는 거예요. 목적은 통제가 아니라 서비스팀의 짐을 더는 데 있습니다. 서비스팀이 그 기능의 존재를 의식하지 않고 일할 수 있다면 플랫폼팀은 제 몫을 한 셈이에요. 1편에서 본 관문이 아니라 가드레일이라는 원칙도 같은 방향입니다.

그런데 감춘 기능도 어딘가에는 있어야 합니다. 서비스 프로세스 안에 들어가든, 옆에 붙든, 노드에 깔리든요. 어디에 실리느냐에 따라 경로를 다섯으로 나눌 수 있어요.

  • 의존성과 자동 구성: 플랫폼팀이 라이브러리를 만들고, 서비스가 빌드 파일에 의존성으로 넣습니다. Spring Boot라면 자동 구성(auto-configuration)이 붙어 의존성을 넣기만 해도 기능이 켜져요.
  • 서비스팀이 소유한 클라이언트: 주문 서비스를 만든 팀이 주문 서비스 호출용 클라이언트 라이브러리도 만들어 배포합니다. 재시도와 폴백을 그 서비스를 가장 잘 아는 팀이 넣는 방식이에요.
  • 런타임 주입: 서비스는 아무것도 넣지 않고, 배포 플랫폼이 실행 직전에 에이전트나 라이브러리를 끼워 넣습니다. Cloud Foundry의 빌드팩, 쿠버네티스의 OpenTelemetry Operator 자동 계측이 이 방식이에요.
  • 사이드카: 서비스 컨테이너 옆에 프록시를 붙여 들어오고 나가는 트래픽을 대신 처리합니다. Istio 같은 서비스 메시가 대표적입니다.
  • 사이드카 없는 길: 프록시를 파드마다 두지 않고 노드에 하나 두거나(Istio ambient 모드), 아예 프록시 없이 클라이언트 라이브러리가 메시의 설정을 직접 받습니다(proxyless gRPC).
📖 용어: 자동 구성 (auto-configuration)
Spring Boot가 클래스패스에 어떤 라이브러리가 있는지, 사용자가 이미 같은 빈을 만들었는지 같은 조건을 보고 설정을 알아서 켜는 기능이에요. 의존성 하나만 넣으면 기본 설정이 따라오고, 서비스팀이 직접 정의하면 그쪽이 이깁니다.
그림 1. 다섯 경로는 공통 기능이 서비스 코드에서 얼마나 떨어져 있느냐로 줄 선다

이 다섯을 비교할 때 흔히 기능표를 그립니다. 어느 쪽이 재시도 백오프를 지원하나, 어느 쪽이 서킷 브레이커가 있나. 이번 편은 축을 다르게 잡아요. 기능은 시간이 지나면 양쪽에 다 생기지만, 무엇을 바꿀 때 무엇을 다시 띄워야 하는지는 경로가 정해 버리기 때문입니다. 재는 축은 셋이에요.

축 1. 정책 값 하나(최대 시도 1 → 3, 시도당 타임아웃 2초 → 0.5초)를 바꿀 때 무엇을 다시 띄우나 축 2. 구현 자체(라이브러리, 에이전트, 프록시 버전)를 올릴 때 무엇을 다시 띄우나 축 3. 바꾸는 동안 옛 버전과 새 버전이 섞여 도는 창은 얼마나 길고, 그걸 누가 아나

축 1과 축 2를 나누는 게 이 글의 핵심이에요. 서두의 비교가 헷갈렸던 이유는 사이드카의 축 1과 라이브러리의 축 2를 나란히 놓았기 때문입니다.

2. 의존성과 자동 구성: 가장 단단하고, 값은 업그레이드 때 낸다

서비스마다 런타임 의존성으로 들어간 라이브러리는 가장 확실한 전달 수단입니다. 프로세스 안에 있으니 요청 하나하나의 문맥(어떤 엔드포인트인지, 멱등한지, 사용자가 누구인지)을 다 볼 수 있어요. Spring Boot에서는 플랫폼팀이 스타터를 만들고 자동 구성으로 기본값을 켭니다.

// 플랫폼팀의 platform-retry-spring-boot-starter @AutoConfiguration @ConditionalOnClass(Retry.class) @EnableConfigurationProperties(PlatformRetryProperties.class) public class PlatformRetryAutoConfiguration { @Bean @ConditionalOnMissingBean // 서비스팀이 직접 만들면 이 빈은 물러선다 RetryConfig platformRetryConfig(PlatformRetryProperties p) { return RetryConfig.custom() .maxAttempts(p.getMaxAttempts()) // 첫 시도를 포함한 횟수. 기본값 1(재시도 없음), 속성으로 덮을 수 있음 .waitDuration(p.getWaitDuration()) .build(); } } # src/main/resources/META-INF/spring/ # org.springframework.boot.autoconfigure.AutoConfiguration.imports com.example.platform.retry.PlatformRetryAutoConfiguration

Spring Boot 문서는 자동 구성 클래스를 이 AutoConfiguration.imports 파일에 적은 것으로만 불러오라고 하고, @ConditionalOnMissingBean을 "기본값이 마음에 들지 않는 개발자가 자동 구성을 덮어쓸 수 있게 하는" 흔한 예로 듭니다(Creating Your Own Auto-configuration). 이게 가드레일의 모양이에요. 기본으로 켜지지만, 서비스팀이 이유가 있으면 빠져나올 수 있습니다.

정책 값을 바꿀 때: 어디에 적었느냐가 갈린다

서두의 "최대 시도 1번을 3번으로"를 이 경로에서 해 볼게요. Resilience4j의 maxAttempts는 첫 시도를 포함한 횟수라, 1은 재시도 없음이고 3은 재시도 2번이에요. 결과는 그 값이 어디에 있느냐에 따라 갈립니다.

값이 있는 곳 바꾸는 방법 다시 띄우는 것 스타터 코드의 상수(기본값) 스타터 새 버전 → 서비스마다 버전 올림 서비스 전부 (재빌드 + 재배포) 서비스의 application.yml 서비스마다 설정 수정 서비스 전부 (재배포) 설정 서버 / 동적 설정 설정 한 곳 수정 + 갱신 설정 갱신 방식에 따라 0 ~ 전부

즉 라이브러리 경로라고 해서 값 하나 바꾸는 데 늘 재빌드가 필요한 건 아니에요. 값을 속성으로 빼 두고 동적 설정으로 내보내면 축 1의 비용은 사이드카와 비슷해집니다. 대신 그 순간 "설정 변경"이라는 별개의 배포가 생겨요. 설정 변경을 코드 배포처럼 다뤄야 하는 이유는 5편에서 봅니다.

구현을 올릴 때: 서비스 수만큼 내고, 꼬리가 길다

축 2에서는 피할 길이 없습니다. 라이브러리 버그를 고치거나 새 기능을 넣으면, 그 코드는 서비스가 다시 빌드되어야 실려 가요. 서비스 마흔 개면 PR 마흔 개, 빌드 마흔 번, 배포 마흔 번입니다. 그리고 그 마흔 번을 서비스팀이 각자 자기 일정에 맞춰 해요. 그래서 버전이 섞인 창(축 3)은 마지막 서비스가 배포될 때까지 이어지고, 그 끝은 플랫폼팀이 정하지 못합니다. 1편에서 다룬 받아들이지 않는 팀의 꼬리가 여기서 생겨요. 지금 운영에서 어느 서비스가 어느 버전을 쓰는지 아는 것도 일이에요. 빌드 파일이 아니라 떠 있는 바이너리를 봐야 한다는 이야기는 소스 코드 관찰 1편과 실습-2(SBOM)에서 했습니다.

가장 비싼 경우는 버전 올림이 아니라 라이브러리 교체예요. Hystrix는 README에 더 이상 활발히 개발하지 않는 유지 보수 모드라고 적었고, 새 프로젝트에는 Resilience4j 같은 활발한 프로젝트를 쓰겠다고 밝혔습니다(Netflix/Hystrix). Spring Cloud는 2020.0 릴리스 트레인의 호환성을 깨는 변경 목록에서, 미리 공지한 대로 spring-cloud-netflix-hystrix를 포함한 모듈들을 spring-cloud-netflix에서 제거했다고 밝혔어요(Spring Cloud 2020.0 Release Notes). Hystrix의 명령 객체와 Resilience4j의 데코레이터는 API 모양이 달라서, 이건 버전 숫자를 바꾸는 일이 아니라 호출부 코드를 다시 쓰는 일입니다. 코드 수정을 기계로 하는 방법은 소스 코드 관찰 4편에서 봤어요.

📖 용어: 하이럼의 법칙 (Hyrum's Law)
API 사용자가 충분히 많으면 계약서에 무엇을 약속했든 상관없이, 시스템에서 관찰할 수 있는 모든 동작에 누군가는 의존하게 된다는 경험칙이에요(hyrumslaw.com). 문서에 없는 기본값, 로그 형식, 예외 메시지까지 포함됩니다.

하이럼의 법칙은 공통 기능의 기본값에 그대로 걸립니다. 스타터의 기본값 "재시도 없음, 시도당 2초"는 문서상으로는 기본값일 뿐이지만, 어떤 서비스는 그 2초를 전제로 자기 쪽 타임아웃을 맞춰 놨을 수 있어요. 기본값을 "최대 3번, 시도당 0.5초"로 바꾸는 릴리스는 그 서비스에는 동작 변경입니다. 2초 걸려 성공하던 호출이 이제는 실패하고, 멱등하지 않은 호출이 세 번 나갈 수도 있어요. 그래서 라이브러리 경로의 업그레이드는 서비스 수만큼의 배포에 더해, 서비스 수만큼의 "혹시 이 값에 기대고 있었나"를 확인하는 비용까지 냅니다.

3. 서비스팀이 소유한 클라이언트: 아는 사람이 넣지만, 소비자가 업그레이드한다

재시도와 폴백은 호출받는 서비스의 사정에 따라 달라야 할 때가 많아요. 어떤 요청이 멱등한지, 어떤 오류는 다시 시도해도 소용없는지, 느려지면 무엇을 대신 내줄 수 있는지는 그 서비스를 만들고 운영하는 팀이 가장 잘 압니다. 그래서 서비스팀이 자기 서비스용 클라이언트 라이브러리를 만들어 배포하고, 소비자는 그걸 가져다 쓰게 하는 방식이 나와요.

장점이 분명한 만큼 반론도 오래됐습니다. 2016년 Ben Christensen은 모든 서비스가 같은 바이너리 라이브러리를 실어야 돌아가는 구조를 "분산 모놀리스"로 경고했어요. InfoQ의 정리에 따르면 공유 코드는 서비스 경계 안에서는 괜찮지만 경계 밖으로 새어 나가면 결합이 되고, 서비스는 데이터 계약과 네트워크 프로토콜만 드러내야 한다는 주장입니다(InfoQ, 2016).

업그레이드 비용으로 보면 이 경로의 특징이 더 잘 보입니다. 클라이언트를 고치는 건 제공자 팀인데, 버전을 올리는 건 소비자 팀이에요. 주문 서비스 팀이 폴백 버그를 고쳐도, 그 클라이언트를 쓰는 다른 서비스들이 버전을 올려 다시 배포해야 반영됩니다. 2장의 꼬리가 제공자마다 하나씩 생기는 셈이에요. 그리고 클라이언트에 업무 로직이 조금씩 들어가기 시작하면, 서버를 고칠 때 클라이언트도 같이 고쳐야 하는 일이 늘어납니다.

💡 서비스팀 클라이언트를 쓴다면
• 클라이언트에는 호출 방식(타임아웃, 재시도 가능 여부, 폴백)만 넣고 업무 규칙은 넣지 않아요. 업무 규칙은 서버에 둬야 서버 배포 한 번으로 바뀝니다
• 클라이언트를 쓰는 게 의무가 아니라 선택이어야 해요. 프로토콜만 지키면 직접 호출해도 되게 두면 결합이 계약 수준에 머뭅니다
• 클라이언트 버전별 사용 서비스 목록을 만들어 둬요. 고친 버전이 어디까지 퍼졌는지 모르면 고쳤다고 말할 수 없습니다

4. 런타임 주입: 빌드는 건너뛰지만, 재기동은 남는다

배포 절차가 표준화돼 있으면 플랫폼이 실행 직전에 기능을 끼워 넣을 수 있어요. Cloud Foundry의 자바 빌드팩은 앱을 올릴 때(스테이징) JRE를 고르는 것과 함께 여러 "프레임워크"를 붙입니다. README의 표준 프레임워크 목록에는 APM 에이전트들, JaCoCo 에이전트, Java CfEnv, Spring Auto Reconfiguration 같은 항목이 있어요(cloudfoundry/java-buildpack). 서비스팀은 의존성을 넣지 않았는데 앱에 메트릭 에이전트가 붙어서 뜹니다.

📖 용어: 빌드팩 (buildpack)
소스나 jar를 받아 실행 가능한 이미지로 만드는 플랫폼 쪽 단계예요. 어떤 런타임을 깔지, 어떤 에이전트를 붙일지, 어떤 시작 명령으로 띄울지를 빌드팩이 정합니다. 서비스팀의 빌드 파일 밖에서 일어나는 일이에요.

쿠버네티스에서도 같은 일을 할 수 있습니다. OpenTelemetry Operator는 파드 템플릿에 instrumentation.opentelemetry.io/inject-java: "true" 주석을 달면, 초기화 컨테이너를 추가해 자동 계측 에이전트를 앱 컨테이너에 넣어요. 문서는 이 동작이 파드가 시작될 때 일어난다고 적습니다(Injecting Auto-instrumentation).

이 경로가 바꾸는 건 누가 배포 버튼을 누르느냐예요. 에이전트를 새 버전으로 바꿀 때 서비스팀의 PR이 필요 없습니다. 플랫폼팀이 빌드팩이나 계측 설정을 갱신하면 돼요. 그러나 재기동까지 사라지지는 않습니다. cloud.gov 운영 문서는 플랫폼이 파일 시스템과 빌드팩을 갱신하면 앱을 다시 스테이징(cf restage)해야 새 것을 쓰고, 그러지 않으면 갱신을 놓친다고 적어요. 다시 스테이징하는 동안 앱을 쓸 수 없을 수 있다는 경고도 같이 있습니다(cloud.gov, App maintenance). OpenTelemetry Operator도 주입이 파드 시작 시점에 일어나니, 이미 떠 있는 파드가 새 에이전트를 받으려면 다시 떠야 한다고 보는 게 자연스러워요. 이 부분은 문서에 명시돼 있지 않아 제 추론입니다.

그래서 런타임 주입의 축 2는 "재빌드 없이 재기동"이에요. 플랫폼팀이 재기동 일정을 쥘 수 있으니 버전이 섞인 창은 라이브러리 경로보다 짧게 만들 수 있습니다. 대신 하이럼의 법칙은 더 아프게 걸려요. 서비스팀은 자기 앱 안에서 무엇이 바뀌었는지 PR로 보지 못합니다. 에이전트가 새로 잡기 시작한 스팬, 바뀐 메모리 사용량이 서비스팀 입장에서는 이유 없는 변화로 보여요. 이 경로를 쓰면 무엇이 언제 바뀌었는지를 서비스팀이 볼 수 있는 곳에 남기는 일이 플랫폼팀 몫이 됩니다.

5. 사이드카와 사이드카 없는 길: 값은 공짜에 가깝고, 버전은 파드를 다시 띄운다

사이드카는 서비스 프로세스 밖에 있으니 축 1에서 가장 쌉니다. 컨트롤 플레인(Istio라면 istiod)이 정책을 xDS라는 프로토콜로 각 프록시에 밀어 주고, 프록시는 재기동 없이 새 값을 씁니다. 서두의 "최대 3번, 시도당 0.5초"는 설정 한 번이에요. Envoy로 적으면 num_retries: 2(재시도 횟수라 첫 시도는 빠짐), per_try_timeout: 0.5s입니다.

📖 용어: 컨트롤 플레인, 데이터 플레인, xDS
메시에서 실제 트래픽을 처리하는 프록시들을 데이터 플레인, 그 프록시들에게 설정을 나눠 주는 쪽을 컨트롤 플레인이라고 불러요. 둘 사이에서 리스너, 라우트, 클러스터, 엔드포인트 설정을 주고받는 Envoy의 API 묶음이 xDS입니다.

다만 축 3이 0은 아닙니다. Envoy 문서는 xDS API가 결과적 일관성(eventually consistent)을 따르기 때문에 갱신하는 동안 트래픽이 잠깐 떨어질 수 있다고 적고, 클러스터를 먼저 보내고 라우트를 나중에 보내는 "만들고 나서 끊는" 순서를 권합니다(xDS REST and gRPC protocol). 프록시마다 새 설정을 받은 시점이 다르니 짧게나마 섞인 창이 생기고, 어떤 프록시가 못 받았는지는 istioctl proxy-status로 봐요. Istio 문서에서 STALE은 istiod가 갱신을 보냈는데 Envoy가 받았다는 응답이 오지 않은 상태입니다(Debugging Envoy and Istiod).

프록시 버전을 올릴 때

축 2로 가면 그림이 뒤집혀요. Istio 카나리 업그레이드 문서는 새 리비전의 컨트롤 플레인을 설치하는 것만으로는 기존 사이드카 프록시에 아무 영향이 없고, 네임스페이스를 새 리비전으로 바꾼 뒤 파드를 재시작해야 다시 주입된다고 적습니다(Canary Upgrades). 사이드카는 파드 명세에 주입되는 컨테이너라, 사이드카를 설치하거나 올리면 앱 파드를 다시 띄워야 한다는 점은 Istio 팀이 ambient 모드를 소개하며 직접 꼽은 단점이기도 해요(Introducing Ambient Mesh).

여기에 기한까지 붙습니다. Istio 지원 정책은 컨트롤 플레인이 데이터 플레인보다 한 버전까지만 앞설 수 있고, 데이터 플레인이 앞서는 건 안 된다고 적어요(Supported Releases). 컨트롤 플레인을 제자리에서(in-place) 1.N에서 1.N+1로 올린 뒤 다시 1.N+2로 올리려면, 그 사이에 모든 파드가 적어도 한 번은 다시 떠서 1.N+1 프록시를 받아야 한다는 뜻입니다. 같은 문서는 스큐를 아예 만들지 않도록 리비전을 쓰라고 권해요. 리비전으로 옛 컨트롤 플레인을 옆에 남겨 두면 파드는 옛 리비전에 붙은 채 버틸 수 있고, 그때 기한은 옛 리비전의 지원 종료가 정합니다. 어느 쪽이든 라이브러리 경로의 꼬리는 서비스팀 일정에 맡겨지지만, 사이드카 경로의 재기동은 메시의 릴리스 주기가 정한 기한 안에 끝내야 해요.

그림 2. 같은 경로도 값을 바꿀 때와 구현을 올릴 때 다시 띄우는 것이 다르다

사이드카 없는 길은 재기동을 어디로 옮겼나

Istio는 1.24(2024년 11월)에서 ambient 모드를 정식(GA)으로 발표했어요. 파드마다 프록시를 두는 대신 노드마다 L4(연결 단위: 암호화, 어느 서비스가 어느 서비스에 연결해도 되는지)를 맡는 공유 프록시 ztunnel을 두고, 라우팅이나 세밀한 인가처럼 HTTP 요청 내용을 봐야 하는 L7 기능은 앱 배포 밖에서 따로 늘리고 줄일 수 있는 waypoint 프록시가 맡습니다(Istio 1.24 발표). 프록시가 파드 명세 밖으로 나갔으니 프록시를 올린다고 앱 파드를 다시 띄울 일은 없어요.

그렇다고 업그레이드 비용이 사라진 건 아닙니다. ambient 업그레이드 문서는 ztunnel을 제자리에서 올리면 리비전을 써도 그 노드의 ambient 트래픽 전부가 잠깐 끊기고, 실제로는 짧은 창이라 오래 유지되는 연결이 주로 영향을 받는다고 적어요. 운영 환경에서는 노드를 격리(cordon)하거나 블루그린 노드 풀로 영향 범위를 줄이라고 권합니다(Upgrade with Helm). 재기동의 단위가 파드에서 노드로 옮겨 간 셈이에요.

proxyless gRPC는 반대 방향입니다. gRPC 클라이언트가 프록시 없이 xDS를 직접 받아요(gRFC A27). 정책 값은 메시 설정 한 번으로 바뀌니 축 1은 사이드카처럼 싸지만, 그 정책을 해석하는 건 서비스 안의 gRPC 라이브러리예요. gRPC의 xDS 기능 표를 보면 재시도는 Java 1.40.1, 이상치 탐지는 Java 1.49.0부터처럼 기능마다 필요한 라이브러리 버전이 다르고, 지원하지 않는 기능의 설정은 클라이언트가 로그도 남기지 않고 무시한다고 적혀 있어요(xDS Features in gRPC). 설정은 한 번에 나갔는데 실제로 적용됐는지는 서비스마다 라이브러리 버전에 달린 상태입니다. 축 2와 축 3은 2장의 라이브러리 경로로 돌아가요.

사이드카는 정말 기능이 모자란가

흔히 사이드카는 앱과 완전히 떨어져 있어서 여러 앱의 공통분모만 할 수 있고, 그래서 라이브러리보다 기능이 크게 모자란다고들 합니다. 이 말은 두 부분으로 나눠 봐야 해요.

기능 목록으로는 지금 맞지 않습니다. Envoy에는 헤지 요청(트래픽 관리 실습-4), 재시도 예산(트래픽 관리 5편), 임계값을 스스로 찾는 적응형 동시성 제한(트래픽 관리 7편)이 있어요. 오히려 라이브러리 쪽이 늦은 경우도 있습니다. Resilience4j의 적응형 벌크헤드 제안(이슈 #201)은 2018년에 열려 지금도 열려 있고, 구현 PR들은 기능 브랜치에만 합쳐졌어요. 이 글을 쓰는 시점에 기본 브랜치(master)와 최신 릴리스 v2.4.0(2026년 3월) 어디에도 적응형 벌크헤드 코드는 없습니다(resilience4j#201).

반면 도메인 지식이 필요한 판단은 여전히 앱 쪽에 있어요. 무엇을 먼저 버릴지, 이 요청을 다시 보내도 되는지는 프록시가 모릅니다. 이 부분은 트래픽 관리 7편에서 자세히 다뤘으니 여기서는 반복하지 않을게요. 이 글의 질문으로 옮기면 이렇습니다. 도메인 지식이 필요한 정책은 앱에 둘 수밖에 없고, 그 정책을 바꿀 때는 앱 배포의 비용을 냅니다. 메시로 옮길 수 있는 정책만 축 1의 이득을 봐요.

6. 시계추보다 표 한 장

신뢰성 기능을 누가 가져야 하느냐는 유행이 오간다는 관찰이 있어요. 넷플릭스 OSS 시절에는 라이브러리로 앱 안에 넣는 게 주류였고, 서비스 메시가 뜨면서 플랫폼이 중앙에서 쥐는 쪽으로 옮겨 갔다는 이야기입니다. 그리고 각 주기는 앞 주기에서 배운 것을 담아 간다고들 해요.

그런데 지금 보이는 모습은 한쪽으로 쏠리는 시계추보다는 한가운데로 모이는 쪽에 가깝습니다. ambient 모드는 프록시를 앱에서 더 떼어 냈고, proxyless gRPC는 메시의 설정 체계를 앱 라이브러리 안으로 들였어요. 적응형 동시성 제한은 넷플릭스의 자바 라이브러리와 Envoy 필터에 동시에 있습니다. 그러니 "요즘은 메시가 대세"라는 판단보다, 자기 조직의 변경 패턴에 맞는 경로를 고르는 편이 낫습니다.

그림 3. 버전이 섞인 창의 길이는 누가 재기동 버튼을 쥐었느냐가 정한다

고를 때는 기능표 대신 이런 표를 한 장 만들어 보세요. 지난 1년 동안 실제로 있었던 변경을 행으로 놓습니다.

지난 1년의 공통 기능 변경 종류 횟수 이 경로라면 다시 띄우는 것 재시도 횟수, 타임아웃 조정 정책 값 12 라이브러리: 값 둔 곳에 따라 / 사이드카: 없음 메트릭 태그 추가 구현 3 라이브러리: 전부 재빌드 / 주입: 전부 재기동 보안 패치 (라이브러리 or 프록시) 구현 4 라이브러리: 전부 재빌드 / 사이드카: 파드 전부 재시작 요청 종류별 폴백 규칙 정책 + 도메인 5 어느 경로든 앱 배포 (숫자는 표 쓰는 법을 보이기 위한 예시)

정책 값 변경이 대부분이면 축 1이 싼 경로(메시, 동적 설정)가 이득입니다. 구현 변경과 보안 패치가 잦으면 재기동을 플랫폼이 쥘 수 있는 경로(런타임 주입, 메시)가 버전이 섞인 창을 줄여요. 도메인 지식이 필요한 변경이 많으면 어느 경로를 골라도 앱 배포가 남으니, 라이브러리 경로를 쓰되 꼬리를 줄이는 쪽(1편의 자동 수정 PR, 버전 현황판)에 투자하는 편이 낫습니다. 같은 재시도 정책을 라이브러리 다섯 개와 사이드카 다섯 개로 실제로 바꿔 보며 무엇이 몇 번 다시 뜨는지는 실습-1에서 잽니다.

💡 실무에서는
• 공통 라이브러리의 기본값은 코드 상수보다 속성으로 둬요. 값 하나 바꾸는 일이 재빌드에서 설정 배포로 내려옵니다
• 기본값을 바꾸는 릴리스는 동작 변경으로 취급해요. 하이럼의 법칙대로 누군가는 그 값에 기대고 있습니다
• 어떤 경로든 "지금 어느 서비스가 어느 버전으로 떠 있나"를 답할 수 있어야 해요. 라이브러리는 SBOM과 떠 있는 바이너리로, 사이드카는 istioctl proxy-status로, proxyless gRPC는 라이브러리 버전과 기능 표를 같이 봅니다
• 메시를 쓴다면 프록시 업그레이드 기한(컨트롤 플레인은 한 버전까지만 앞섬)을 달력에 적어요. 파드 재시작 한 바퀴를 그 안에 끝내야 합니다
• 런타임 주입으로 바뀐 내용은 서비스팀이 볼 수 있는 곳(배포 이벤트, 변경 공지)에 남겨요. PR이 없으니 서비스팀은 따로 알 길이 없습니다
✍️ 오늘의 요약
공통 기능을 실어 보내는 경로는 의존성과 자동 구성, 서비스팀 클라이언트, 런타임 주입, 사이드카, 사이드카 없는 길의 다섯이고, 경로마다 정책 값을 바꿀 때와 구현을 올릴 때 다시 띄우는 것이 달라요. 사이드카는 값 변경이 xDS 갱신 한 번이지만 프록시 버전을 올리면 파드를 전부 다시 띄우고, 라이브러리는 값을 속성으로 빼면 설정 배포로 바뀌지만 구현을 올리면 서비스 수만큼 재빌드하고 꼬리가 길어집니다. ambient는 재기동을 노드로 옮겼고, proxyless gRPC는 설정을 메시로 보내도 적용은 라이브러리 버전에 맡겨요.

그래서 고르는 기준은 유행도 기능표도 아니라, 지난 1년 동안 무엇을 몇 번 바꿨는지입니다. 어느 경로든 바꾸는 값은 있고, 경로는 그 값을 언제 누가 내는지를 정할 뿐이에요.
