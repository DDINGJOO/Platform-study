📚 배포 관측과 A/B 실험 · 1편
1편. 오래된 A 대신 새 베이스라인 A′와 B를 비교한다 ← 지금 이 글

같은 v1 코드를 실행했는데, 먼저 띄워 둔 A는 약 13ms이고 새로 띄운 A′는 약 78ms였어요. 이 차이만으로 코드 변경에 따른 회귀라고 단정할 수 없어요. 이번에는 새 프로세스의 빈 캐시가 원인이었어요.

이 차이를 먼저 확인하고, 새 A′와 새 B를 같은 조건으로 실행했어요. 실제 HTTP 요청을 보내고 Prometheus로 수집한 값을 Netflix Kayenta에 넣었어요. Spinnaker Deck의 실제 판정 화면까지 연결하면서 무엇을 비교해야 배포 영향을 구분할 수 있는지 확인했어요.

📖 용어: 카나리 분석 (canary analysis)
변경본에 일부 요청을 보내고 기준 버전과 지표를 비교하는 절차예요. 이 실습에서는 로컬 요청을 별도로 보내며, 운영 트래픽 분할은 구현하지 않아요.

1. 같은 코드도 프로세스 상태가 다르면 느려져요

기존 A와 변경본 B를 바로 비교하면 코드 외의 차이도 함께 측정해요. A에는 캐시가 차 있고 B에는 없을 수 있어요. JVM 서비스라면 실행 중 최적화 상태도 달라질 수 있죠. 그래서 새 v1인 A′를 B와 함께 만들고, 주 판정은 A′와 B를 비교하도록 정했어요.

📖 용어: 베이스라인 (baseline)
변경본과 비교할 기준 실행이에요. 여기서는 기존 A와 같은 v1을 새로 시작한 A′가 베이스라인이고, 먼저 시작한 A는 재시작 영향을 확인하는 보조 대상이에요.

작은 Python HTTP 서비스를 세 개 띄웠어요. 요청 키 128개를 순환하며 실제 메모리 캐시를 채워요. 캐시가 없으면 65ms를 추가로 기다리고, 있으면 기본 10~14ms만 기다려요. 실제 데이터베이스 대신 대기 시간을 주입한 합성 부하이며, 지표는 해당 코드가 실제로 실행된 시간을 측정해요.

그림 1. 배포 변경과 새 프로세스의 영향을 나눠 확인해요.

첫 실행의 초기 20초 구간에서 A는 13.183ms, 같은 코드의 A′는 78.448ms였어요. 이는 시계열 11개 지점의 평균이며 진단용이에요. 이 값을 새 코드의 실패 판정이나 Kayenta의 오탐 결과로 제시하지 않았어요. 오래된 상태와 새로운 상태를 바로 비교했을 때 생기는 차이만 확인했어요.

2. A′와 B의 조건을 먼저 고정해요

먼저 같은 v1끼리 비교하고, 다음에는 B에만 40ms를 추가하는 v2 설정을 넣었어요. 두 경우 모두 같은 이미지와 서비스 코드를 사용해요. 변경 변수는 B의 버전 라벨과 지연 설정이에요. 실제 제품 코드 배포를 재현한 실험은 아니에요.

A′ / B 공통 조건 자원 제한: 각 0.5 CPU, 96MiB 시작: 두 프로세스의 기동 차이 3초 미만을 검사 요청: 같은 키 순서로 각 초당 4건 워밍업: 46초, 캐시 128개가 모두 찼는지 확인 관측: 동일한 절대 시각의 120초 수집 / 조회 간격: 2초 / 2초 → 각 61개 지점

요청은 양쪽의 별도 스레드에서 같은 일정으로 시작해요. 실제 처리 건수도 확인해서 목표 요청률만 맞다고 가정하지 않았어요. 이 작은 부하에서는 다음 요청 전까지 응답이 끝났어요. 과부하 상황에서 이 생성기가 같은 요청률을 유지한다고 보장하지는 않아요.

📖 용어: 워밍업 (warmup)
주 관측 전에 서비스를 실행해 캐시 등 초기 상태를 준비하는 구간이에요. 양쪽에 같은 46초를 주고, 지표의 최근 10초 조회에도 초기 느린 요청이 섞이지 않도록 했어요.

판정에는 실제 Kayenta를 사용했어요. 공식 Spinnaker 2026.1.3 이미지의 Deck·Gate·Kayenta·Front50과 Redis를 띄웠어요. 전체 배포 시스템을 구성한 것은 아니고, 실제 분석 실행과 보고서에 필요한 범위예요.

📖 용어: Kayenta와 judge
Kayenta는 두 실행의 지표를 가져와 비교 분석을 실행하는 도구예요. judge는 그 안에서 지표를 분류하고 점수를 계산하는 부분이며, 여기서는 공식 NetflixACAJudge-v1.0을 사용해요.
그림 2. 프로세스 재시작은 실습 스크립트가, 분석 단계는 Kayenta 내장 Orca가 실행해요.

Prometheus에는 처리 시간 누적값과 처리 건수를 수집해요. 아래 쿼리는 최근 10초의 건당 평균 처리 시간을 ms로 계산해요. Kayenta가 ${scope}를 baseline 또는 canary로 바꿔 같은 시작·종료 시각을 조회해요.

📖 용어: PromQL
Prometheus에 저장한 시계열을 조회하는 언어예요. 여기서는 누적 시간의 증가율을 누적 건수의 증가율로 나눠, 각 실행의 평균 처리 시간을 구해요.
1000 * sum(rate(orders_duration_seconds_sum{role="${scope}"}[10s])) / sum(rate(orders_duration_seconds_count{role="${scope}"}[10s]))

이는 서비스 내부에서 측정한 평균 시간이에요. 네트워크를 포함한 사용자 응답 시간이나 p99 지연을 대신하지 않아요. 상세 설정은 실습 디렉터리에 있어요.

3. 같은 버전은 통과하고 지연을 넣은 B는 실패했어요

실행 전 허용할 평균 지연 증가를 20%로 정했어요. meanRatio의 allowedIncrease와 criticalIncrease를 모두 1.20으로 설정하고 두 실행에 그대로 사용했어요. Kayenta의 통계 분류와 이 효과 크기 조건을 함께 적용하며, 관측 평균만 20%와 단순 비교하는 코드로 대체하지 않았어요.

📖 용어: 판정 점수 (score)
Kayenta가 지표별 분류와 그룹 가중치로 계산하는 점수예요. 여기서는 지연 지표 하나에 가중치 100을 줬어요. 점수 100은 신뢰도 100%나 배포 전체의 안전을 뜻하지 않아요.
비교A′ 평균B 평균실제 판정
v1 대 v113.001ms13.005msPass · 100
v1 대 v2 설정13.484ms53.807msFail · 0

각 주 관측 구간에서 A′와 B가 처리한 요청은 각각 480건이에요. judge에 들어간 값은 양쪽 각각 61개예요. 공식 가이드의 최소 50개 시계열 지점 권고를 넘기도록 정했지만, 이 61개는 독립 사용자 61명을 뜻하지 않아요. 최근 10초 구간이 겹치는 값이라 인접 지점끼리 상관이 있어요.

그림 3. 새 v1끼리의 비교는 실제 NetflixACAJudge에서 통과했어요.
그림 4. 같은 조건에서 B에만 지연을 추가하자 지표가 High로 분류되고 최종 판정은 실패했어요.

Grafana에는 평균 지연, 실제 요청률, 프로세스 나이, 캐시 개수를 함께 표시했어요. A′와 B의 나이가 함께 초기화되고 캐시가 같은 과정으로 채워지는지 확인할 수 있어요. 관측이 끝난 뒤 임의로 그린 그래프가 아니라 같은 Prometheus에 연결한 실제 화면이에요.

그림 5. 결과와 함께 실행 조건도 시각화해야 비교가 적절했는지 확인할 수 있어요.

4. 응답을 받은 것과 분석을 마친 것을 구분해요

첫 연결에서 Kayenta가 분석을 끝냈는데도 실습 스크립트가 기다리는 문제가 있었어요. 원인은 판정이 아니라 응답 처리였어요. 실제 상태 문자열은 소문자인데 대문자와 비교했어요.

실제 응답: {"complete": true, "status": "succeeded"} 수정한 종료 확인: str(result.get("status", "")).upper() == "SUCCEEDED" cd labs/devops/deployment-experiments/canary python3 run.py python3 verify.py cat out/results.txt

이 수정은 API 상태 확인만 바꿨어요. 완료된 첫 보고서를 보존하고 전체 실험을 다시 실행했으며, 표의 수치는 재실행 결과예요. run.py는 자기 Compose 프로젝트와 볼륨을 초기화하고 기존 out/은 history/에 보관해요. 같은 결과를 재검할 때는 초기화하지 않는 verify.py를 사용해요.

💡 저장한 값과 judge 입력을 대조해요
검증기는 양쪽 요청 수·기동 시점·이미지·자원 제한을 확인해요. Kayenta가 실제 사용한 각 61개 값도 저장한 Prometheus 조회 결과와 대조해요. Prometheus 쿼리 로그에서 Kayenta 컨테이너가 보낸 쿼리와 시각·간격을 확인하고, Gate의 실제 보고서 응답까지 다시 조회해요.
그림 6. 원자료와 실행 조건을 다시 확인한 결과예요.

Deck은 http://localhost:28100, Grafana는 http://localhost:28105/d/fresh-baseline에서 열어요. 각 실행의 Deck 보고서 전체 주소는 out/summary.json에 있어요. Playwright가 설치된 기존 환경에서는 capture.py로 화면을 다시 찍을 수 있어요.

5. 통과 결과의 적용 범위를 남겨요

이 실습에서 실제 실행한 것은 Docker Compose의 프로세스 재생성과 Kayenta 내장 Orca의 지표 수집·판정 단계예요. 외부 Orca의 배포 파이프라인, 클라우드 리소스 생성, 트래픽 승격, 자동 롤백까지 만들지는 않았어요. Deck은 실제 분석 보고서를 보여 주며, Grafana의 재시작 그래프가 Spinnaker 배포 파이프라인 화면을 뜻하지는 않아요.

⚠️ 데모 저장소와 화면의 한계가 있어요
Kayenta의 공식 memory 계정을 사용해서 컨테이너를 재시작하면 설정과 보고서가 사라져요. 호스트의 원자료는 남지만 해당 Deck 보고서는 재실행해야 해요. 생략한 Clouddriver·Echo·외부 Orca를 호출하는 일부 메뉴 요청은 실패해요. 가짜 응답을 붙이지 않았으며 실제 canary 보고서 API가 성공하는 범위만 확인했어요.

또한 짧은 합성 부하, 실행별 인스턴스 하나, 평균 지연 지표 하나만 사용했어요. 실제 서비스에서는 오류율과 꼬리 지연, 충분한 운영 관측 구간, 요청 특성의 균형도 확인해야 해요. A′와 B의 조건을 맞췄다는 사실만으로 모든 차이의 원인이 코드라고 확정할 수도 없어요.

비교 설계는 Netflix의 Kayenta 소개를 참고했어요. 실행 범위는 해당 버전의 standalone 문서, 판정 설정은 고정된 소스의 NetflixACAJudge와 대조했어요.

✍️ 오늘의 요약
오래된 A와 새 B의 차이에는 프로세스 초기 상태도 포함될 수 있어요.

새 A′와 새 B의 자원·워밍업·부하·관측 시각을 맞추고 실제 Kayenta 판정과 입력값을 함께 확인했어요. 판정 결과를 해석하기 전에 비교 대상의 조건부터 확인해야 해요.
