📚 배포 관측과 A/B 실험 · 2편
1편. 오래된 A 대신 새 베이스라인 A′와 B를 비교한다
2편. A/B 테스트 사용자는 새로고침해도 같은 그룹이어야 한다 ← 지금 이 글

가상 사용자 400명이 실험에 진입하는 작은 HTTP 서비스를 만들었어요. 새로고침과 재시도로 진입 요청은 1,600번이 됐지만 사용자는 여전히 400명이에요. 요청마다 그룹을 다시 뽑거나 요청 수를 분모로 쓰면 비교가 어떻게 달라질까요?

이번 실습은 같은 사용자가 같은 그룹에 남고, 노출된 사용자와 전환한 사용자를 한 번씩만 세는지 확인해요. Python 표준 라이브러리와 SQLite로 이벤트를 저장하고, Prometheus와 실제 Grafana 화면에서 수집값을 대조했어요. 모두 가상 식별자와 합성 전환이에요.

1. 사용자 할당과 기능 노출을 따로 기록해요

서비스가 사용자에게 A를 배정했다고 해서 해당 기능을 실제로 사용했다는 뜻은 아니에요. 사용자는 결제 화면에 오기 전에 나갈 수도 있어요. Netflix 엔지니어링 팀의 실험 플랫폼 소개도 실험에 할당된 구성원이 모두 대상 기능을 경험하는 것은 아니라고 설명해요. 이 글에서는 그 구분을 작은 서비스로 확인해요. Netflix 내부 플랫폼을 실행하는 실습은 아니에요.

세 가지 HTTP 이벤트를 만들었어요. /entry는 그룹을 배정하고 진입을 기록해요. /exposure는 기능을 노출했다는 확인을 받아요. /conversion은 노출 이후의 전환을 기록해요. 이 실습의 노출은 테스트 클라이언트가 보낸 확인이에요. 실제 브라우저에서 화면이 그려졌는지까지 검사하지는 않아요.

📖 용어: 할당과 노출 (Assignment / Exposure)
할당은 사용자가 속할 실험 그룹을 정하는 일이에요. 노출은 그 사용자가 실험 대상 경험을 접했음을 기록하는 일이에요. 두 사용자 집합이 다를 수 있어 따로 저장해요.
그림 1. 400명이 진입했지만 전환율의 노출 사용자 분모는 320명이에요.

이번 글의 집계값은 노출된 사용자 중 한 번 이상 전환한 사용자의 비율로 미리 정했어요. 할당된 전체 사용자를 기준으로 보는 분석과는 다른 값이에요. 노출이 실험 그룹의 영향을 받는 경우에는 노출 사용자만 비교하면 편향이 생길 수 있어요. 이 집계 정의만으로 제품 효과를 판단할 수는 없어요.

2. 그룹을 정하는 입력을 고정해요

같은 사용자 식별자에는 같은 A 또는 B를 돌려줘야 해요. 요청마다 난수를 뽑으면 한 사용자가 두 경험을 모두 보게 돼요. Unleash의 stickiness 문서는 사용자 문맥과 그룹 식별자를 함께 해시해 일관된 결과를 만드는 방식을 설명해요. Unleash는 MurmurHash를 사용해요. 이 실습에서는 구조를 직접 확인하기 위해 Python의 SHA-256을 사용했어요. Unleash를 설치한 것은 아니에요.

📖 용어: 고정 할당 (Stickiness)
같은 실험과 같은 사용자에게 같은 그룹을 계속 주는 성질이에요. 식별자나 실험 설정이 바뀌면 같은 사람이더라도 그룹이 달라질 수 있어요.
material = json.dumps( [experiment_id, salt, user_id], ensure_ascii=False, separators=(',', ':') ).encode('utf-8') bucket = int.from_bytes( hashlib.sha256(material).digest()[:8], 'big' ) % 10000 variant = 'A' if bucket < 5000 else 'B'

SHA-256 결과의 앞 8바이트를 정수로 읽고 10,000으로 나눈 나머지를 사용해요. 0~4,999는 A, 5,000~9,999는 B예요. 입력 문자열의 결합 방식도 결과의 일부라 JSON 배열과 UTF-8 직렬화 규칙을 함께 고정했어요. 50:50 설정이 실제 사용자 수도 정확히 반반으로 만든다는 뜻은 아니에요. 이번 실행의 할당은 A 202명, B 198명이었어요.

📖 용어: salt와 실험 식별자
salt는 이 실습에서 해시 입력을 구분하는 고정 설정값이에요. 실험 식별자는 어느 실험의 할당인지 구분해요. 이 값들은 비밀키나 개인정보 익명화 수단으로 쓰지 않아요.

salt를 바꿔 같은 400명을 다시 계산하니 182명의 그룹이 달라졌어요. DB에 저장된 사용자만 예전 그룹에 남고 새 사용자만 새 규칙을 따르면 한 실험 안에 서로 다른 할당 규칙이 섞여요. 그래서 기존 실험 식별자에 다른 salt를 넣으면 서비스 기동을 거부하도록 했어요. 바꿔야 한다면 새로운 실험 식별자로 시작해요. 사용자 식별자를 브라우저 세션마다 새로 만들거나 기기별로 다르게 주면 이 서비스도 같은 사람임을 알 수 없어요.

3. 재시도는 요청을 늘려도 사용자 수를 늘리지 않아요

SQLite에는 할당과 이벤트를 따로 저장해요. 할당의 고유 키는 실험과 사용자예요. 이벤트의 고유 키에는 이벤트 종류까지 들어가요. 전환을 두 번 보내도 같은 사용자의 전환 기록은 하나예요. 이 글에서 세는 것은 구매 건수가 아니라 전환한 사용자 수이기 때문이에요.

assignments: PRIMARY KEY(experiment_id, user_id) events: UNIQUE(experiment_id, user_id, event_type) BEGIN IMMEDIATE; -- 기존 할당 확인 또는 새 할당 저장 -- 노출 전 전환이면 HTTP 409 INSERT OR IGNORE INTO events (...); -- 수락된 제출 횟수는 별도로 증가 COMMIT;
📖 용어: 사용자 단위 중복 제거 (Deduplication)
같은 사용자가 같은 실험 이벤트를 여러 번 보내도 한 번만 세는 처리예요. 이 실습은 요청 ID가 달라진 재시도도 사용자 단위로 합쳐요. 결제 요청 자체의 중복 실행 방지와는 목적이 달라요.

첫 요청과 같은 요청 ID로 다시 보내는 경우, 새 요청 ID로 새로고침하는 경우를 모두 보냈어요. request_id는 진단 정보로 남기고 중복 제거의 기준으로 쓰지 않아요. 서버가 inserted:false를 돌려주면 요청은 수락했지만 새 사용자 이벤트를 추가하지 않았다는 뜻이에요. 첫 이벤트의 시각도 유지해요.

순서가 잘못된 이벤트도 실제 HTTP로 확인했어요. 진입 없이 노출하면 409, 노출 없이 전환해도 409예요. 사용자 식별자가 없거나 클라이언트가 직접 그룹을 지정하면 400이에요. 식별자가 없는 요청을 임의의 그룹으로 처리하지 않아요.

저장소는 Docker의 SQLite 볼륨이에요. 서비스 프로세스를 재시작한 뒤 할당과 이벤트 전체를 내보내 이전 값과 비교했어요. 재기동 직후와 이후 400명의 진입 재시도 뒤에도 export가 같았어요. 400명 모두 같은 그룹을 유지했어요. 트랜잭션과 고유 제약으로 이 단일 서비스의 쓰기를 정리했으며, 여러 서버에서 운영하는 분산 이벤트 저장소까지 구현한 것은 아니에요.

그림 2. 새 요청 ID와 서비스 재기동이 사용자 분모를 증가시키지 않아요.

4. Grafana에는 집계값을, DB에는 사용자 이벤트를 둬요

Prometheus는 서비스의 /metrics를 1초마다 수집해요. ab_users에는 그룹별 할당·진입·노출·전환 사용자 수를 내보내요. DB에서 읽은 현재 사용자 수라 gauge로 표시했어요. ab_event_attempts_total은 중복을 포함한 수락 요청 수예요. 거부된 400·409 요청은 이 값에 포함하지 않아요.

📖 용어: gauge와 counter
gauge는 현재 상태를 나타내는 값이에요. counter는 누적된 횟수를 나타내요. 여기서는 사용자 집합의 현재 크기와 수락한 제출 횟수를 구분하는 데 사용해요.

레이블은 실험 식별자, A/B 그룹, 이벤트 단계처럼 제한된 값만 사용해요. 사용자 ID나 요청 ID는 넣지 않아요. Prometheus 공식 지침도 사용자 ID처럼 많은 값을 갖는 레이블을 피하도록 안내해요. 사용자별 기록은 SQLite와 JSON export에서 확인해요. 새 실험마다 식별자 레이블도 늘어나므로 실험을 많이 운영할 때는 보관 기간과 집계 설계를 따로 정해야 해요.

# 그룹별 전환한 사용자 / 노출된 사용자 ab_users{stage="conversion"} / ignoring(stage) ab_users{stage="exposure"}

실측 결과는 A의 노출 160명 중 전환 46명, B의 노출 160명 중 전환 37명이에요. 각각 28.75%, 23.125%예요. Grafana는 B를 23.13%로 표시하고 Python 텍스트의 소수 둘째 자리 형식은 23.12%로 표시해요. 두 출력의 반올림 방식 차이이며 분자와 분모는 같아요. 노출 수가 양쪽 모두 160명이 된 것은 이번 입력과 할당에서 나온 결과예요. 그룹별 노출 수를 맞추는 코드는 없어요.

그림 3. 실제 Prometheus 수집값을 사용한 Grafana 대시보드예요.

진입 요청은 1,600번이지만 진입 사용자는 400명이에요. 노출 요청은 640번이지만 노출 사용자는 320명이에요. 전환 요청 166번은 전환 사용자 83명이에요. 요청 수로 사용자 분모를 대신하면 재시도가 많은 그룹의 비율이 달라져요. 화면에 비율을 그리기 전에 어떤 집합의 크기인지 확인해야 해요.

💡 이 숫자로 승자를 고르지 않아요
전환은 가상 사용자 번호에 적용한 조건으로 만들었어요. 제품을 사용한 사람의 반응을 관측한 결과가 아니에요. 표본 계획, 할당 비율 이상, 오류와 지연 같은 보호 지표도 여기서는 판정하지 않아요. 이 화면은 이벤트 집계와 연결이 맞는지 확인하는 자료예요.

5. 실제 실행과 실패 조건을 다시 확인해요

실습 경로는 저장소의 labs/devops/deployment-experiments/sticky-ab예요. 앱은 Python 3.12.15, Prometheus는 3.15.0, Grafana는 13.2.3을 사용했어요. Python 패키지는 추가하지 않았어요. Docker Compose와 Python 3.9 이상으로 검증을 실행할 수 있어요. Python 이미지는 이번 실행에 사용한 manifest digest를 Compose에 고정했어요.

cd labs/devops/deployment-experiments/sticky-ab python3 run.py # 실제 Grafana 화면: http://127.0.0.1:28200/d/sticky-ab/sticky-ab # DB 집계: http://127.0.0.1:28280/summary # 이벤트: http://127.0.0.1:28280/export cat out/results.txt cat out/summary.json

실행기는 400명의 진입·노출·전환 요청을 보내고 HTTP 응답을 검사해요. 이후 앱을 실제로 재시작해 전체 export를 대조하고, Prometheus의 노출 사용자 수가 DB 집계와 같은지도 확인해요. salt를 바꾼 별도 기동은 실패해야 통과해요. 실패 로그는 out/salt-rejection.txt에 남아요.

그림 4. 실제 실행 후 저장한 results.txt를 터미널 형식으로 렌더링한 이미지예요.

새 실행은 이전 out/을 history/ 아래로 옮기고 새로운 실험 식별자를 사용해요. 같은 실행 안에서는 salt와 식별자가 유지되지만 다른 실행의 그룹별 수치는 달라질 수 있어요. 기존 증거를 열 때는 저장된 실험 식별자로 다시 띄워야 해요. README에 재기동 명령과 Playwright 캡처 명령을 함께 적었어요.

400 오류는 식별자와 JSON 입력, 클라이언트가 보낸 그룹 필드를 먼저 확인해요. 409 오류는 진입→노출→전환 순서를 확인해요. 화면에 데이터가 없다면 앱의 /metrics, Prometheus의 수집 대상 상태, Grafana 데이터 소스 순서로 점검해요. 메모리 상한은 앱 128MiB, Prometheus 256MiB, Grafana 1GiB예요. 캡처를 마친 뒤에는 이 프로젝트만 docker compose down으로 종료하고 SQLite 볼륨은 유지했어요.

기록의 형태와 계산은 Python hashlib 문서, sqlite3 트랜잭션 문서, 앞서 연결한 Unleash·Netflix·Prometheus 공식 자료를 함께 참고했어요. 이 예제는 단일 노드의 합성 이벤트 실습이에요. 실제 개인정보나 운영 트래픽을 받는 서비스로 사용하지 않아요.

✍️ 오늘의 요약
같은 실험과 사용자는 같은 그룹을 유지하고, 같은 사용자의 반복 이벤트는 한 번만 세요.

할당 400명, 노출 320명, 전환 83명을 실제 HTTP와 SQLite, Prometheus, Grafana로 대조했어요. 사용자 분모를 먼저 고정해야 화면의 비율이 무엇을 뜻하는지 설명할 수 있어요.
