📚 배포 관측과 A/B 실험 · 3편
1편. 오래된 A 대신 새 베이스라인 A′와 B를 비교한다
2편. A/B 테스트 사용자는 새로고침해도 같은 그룹이어야 한다
3편. 전환율이 높아도 표본과 가드레일부터 확인한다 ← 지금 이 글

이번 실습에서 A의 전환율은 10%, B는 14%인 데이터를 세 가지 만들었어요. 전환율만 보면 같지만 분석 결과는 통과, 표본 비율 이상, 오류·지연 기준 위반으로 갈렸어요. 그룹당 100명인 데이터에서는 B가 15%p 높아도 표본 부족으로 보류했어요.

2편에서는 사용자에게 같은 A/B 버전을 계속 보여 주고 이벤트를 중복 없이 기록했어요. 이번에는 그다음 질문을 다뤄요. 전환율 차이를 해석하기 전에 어떤 조건을 확인해야 할까요? 고정한 합성 이벤트를 Python으로 분석하고, 실제 실행 결과를 자체 HTTP 보고서에서 확인해 볼게요.

1. 통과 조건을 먼저 정하고 다섯 경우를 비교해요

먼저 plan.json에 분석 조건을 적었어요. A와 B의 예정 비율은 50:50, 최소 표본은 각 그룹 2,000명이에요. 최초 노출을 모집하는 기간과 전환을 기다리는 기간도 고정했어요. 데이터가 나온 뒤 유리한 조건으로 고치지 않아요.

예정 비율 A 50% / B 50% 최초 노출 모집 2026-10-01 00:00 UTC 이상 2026-10-07 00:00 UTC 미만 전환 관찰 사용자별 최초 노출 이후 24시간 분석 시점 2026-10-08 00:00 UTC 이후 1회 최소 표본 그룹당 노출 사용자 2,000명 SRM 기준 p ≥ 0.001 요청 가드레일 각 그룹 오류율 ≤ 1%, p95 ≤ 250ms B p95 ≤ A p95 × 1.2 효과 기준 관측 차이 B−A ≥ 3%p 차이의 95% 구간 하한 > 0

실행에는 Python 표준 라이브러리만 사용했어요. 저장된 이벤트를 실제로 읽어 분석하고, 결과 JSON으로 만든 자체 보고서를 http://localhost:28300에서 제공해요. Netflix나 Grafana의 화면은 아니에요. 합성 사건의 10월 날짜는 분석 창을 검증하기 위한 입력값이며, 실제로 일주일 동안 제품 실험을 운영한 기록은 아니에요.

그림 1. 고정한 다섯 이벤트 세트를 분석한 실제 자체 보고서예요.

각 시나리오에서 확인한 핵심 결과는 아래와 같아요. PASS_FIXED_RULES는 이 실습의 고정 규칙을 충족했다는 뜻이에요. 실제 제품의 개선을 입증한 결과로 읽으면 안 돼요.

효과 크기는 비교하려는 변화의 크기예요. 여기서는 B 전환율에서 A 전환율을 뺀 값이에요. 10%에서 14%로 바뀌면 +4%p이고, 상대 증가율로는 40%예요. 두 표현의 분모가 달라서 구분해야 해요.

2. 요청 수 대신 처음 노출된 사용자를 세어요

전환율을 계산하려면 무엇을 한 번으로 셀지부터 고정해야 해요. 이번 분석은 기간 안에 처음 노출된 고유 사용자를 분모로 삼았어요. 분자는 그 사용자가 최초 노출 후 24시간 안에 전환했는지로 결정해요. 한 사람이 새로고침하거나 두 번 구매해도 사용자 전환은 한 번이에요.

📖 용어: 노출과 전환
노출은 사용자가 실험 버전을 실제로 본 사건이고, 전환은 구매처럼 미리 정한 목표 행동이에요. 진입 기록만 있거나 추적용 스팬이 많다는 이유로 노출 사용자 분모를 늘리지 않아요.
그림 2. 2편 HTTP 이벤트를 읽기 전용으로 독립 집계한 실제 사용자 수예요.

2편의 out/events.json도 독립 분석기로 읽었어요. 할당은 A 202명과 B 198명, 노출은 각각 160명, 전환은 46명과 37명이었어요. 따라서 노출 기준 전환율은 46/160 = 28.750%와 37/160 = 23.125%예요. 소수 둘째 자리 표시는 화면의 반올림 방식에 따라 23.12% 또는 23.13%가 될 수 있어서 분수도 함께 적었어요.

이 연결 결과는 DESCRIPTIVE_ONLY로 남겼어요. 2편 스크립트는 노출할 사용자 부분집합을 직접 골랐고, 이번 합성 데이터용 사전 계획에는 그 원자료의 관측 기간과 가드레일이 없어요. 날짜를 사후에 바꾸어 통과 판정에 끼워 넣지 않았어요.

💡 노출 기준의 분석 범위도 미리 정해요
B가 노출될 가능성 자체를 바꾸면 노출 사용자만 골라 비교하는 과정에서 선택 편향이 생길 수 있어요. 실제 무작위 실험에서는 배정된 전체 사용자 기준 분석인 ITT와 적격 노출의 정의를 사전에 검토해야 해요. 이 실습의 사용자 집계가 모든 제품 실험에 그대로 적용되는 것은 아니에요.

분석기는 같은 event_id 재시도와 서로 다른 ID의 반복 노출·전환을 따로 제거해요. 각 합성 세트에 의도적으로 재시도 20건, 반복 노출 20건, 반복 전환 10건, 요청 ID 중복 10건을 넣었어요. 노출 전 전환과 24시간을 넘긴 전환 4건도 분자에서 제외했어요. ID는 같지만 내용이 다른 이벤트, 한 사용자가 A와 B에 함께 속한 경우도 정상 입력으로 넘기지 않아요.

3. 전환율 차이보다 표본 비율 이상을 먼저 확인해요

예정 비율이 50:50인데 분석 대상이 A 2,800명, B 1,200명이라면 전환율 차이를 먼저 믿기 어려워요. 이번 SRM 사례의 전체 노출 사용자는 4,000명이므로 기대 수는 각 그룹 2,000명이에요. 수집 누락이나 노출 조건 차이부터 확인해야 해요. Microsoft도 SRM 진단 안내에서 효과를 해석하기 전 실험 데이터의 신뢰성을 점검하는 문제로 다뤄요.

📖 용어: SRM (Sample Ratio Mismatch)
사전에 예정한 그룹 비율과 실제 분석 대상의 비율이 통계적으로 맞지 않는 상태예요. 이번 기본 분석은 최초 노출 사용자 수를 검사하므로 정확히는 노출·모집 단계 SRM이에요. 사용자 배정 단계의 비율 검사와 구분해야 해요.
A B 관측 수 O 2,800 1,200 기대 수 E 2,000 2,000 χ² = Σ (O−E)² / E = 640 자유도 = 그룹 수 − 1 = 1 p ≈ 3.34 × 10⁻¹⁴¹ 사전 기준 p < 0.001 → INVALID_SRM

코드는 Pearson 카이제곱 통계량과 자유도 1의 상측 확률을 계산해요. 이 경우 p값은 erfc(sqrt(χ² / 2))로 구할 수 있어요. 연속성 보정은 사용하지 않았고, 기대 수가 5명 미만이면 이 근사로 비율 이상을 확정하지 않고 표본 부족으로 보류해요. NIST의 카이제곱 표에 있는 자유도 1, 통계량 3.841의 상측 확률 약 0.05도 테스트 기준으로 대조했어요.

📖 용어: p값
정한 모형과 가정 아래에서, 귀무가설이 맞을 때 관측값만큼 또는 그보다 더 극단적인 결과가 나올 확률이에요. 여기서는 예정 비율과 같은 비율이라는 가정을 검사해요. B가 좋을 확률이나 효과 크기를 뜻하지 않아요.

노출 수가 정확히 같아 p=1이 나와도 무작위 배정이 잘됐다는 증명은 아니에요. 2편 원자료는 배정 202/198명과 노출 160/160명을 각각 진단하도록 별도로 저장했어요. 노출을 의도적으로 선택한 데이터의 균형으로 무작위화나 인과 추론의 전제를 확인할 수는 없어요.

4. 표본과 분석 시점을 결과에 맞춰 바꾸지 않아요

표본 부족 사례는 A에서 100명 중 5명, B에서 100명 중 20명이 전환했어요. 관측 차이는 +15%p이고 차이의 구간도 약 +5.92~+24.33%p예요. 그래도 사전 최소 표본인 그룹당 2,000명에 못 미쳐 HOLD_SAMPLE로 남겨요. 차이가 커 보인다는 이유로 표본 조건을 없애지 않아요.

여기서 2,000명은 판정 경로를 보여 주기 위한 사전 임계값 예시예요. 검정력 계산으로 결정한 수가 아니고, 특정 효과를 충분히 탐지할 수 있다고 보장하지 않아요. 실제 표본 계획은 기존 전환율, 탐지할 차이, 유의수준, 원하는 검정력과 분석 방법에 맞춰 정해야 해요.

📖 용어: 고정 표본 설계와 선택적 중단
고정 표본 설계는 분석 전에 표본·기간과 판정 방법을 정하고 약속한 시점에 분석하는 방식이에요. 중간 결과를 반복해서 보다가 유리한 순간에만 종료하는 선택적 중단은 한 번 분석을 가정한 오탐률과 신뢰구간 해석을 바꿀 수 있어요.

이번에는 고정 모집 기간과 전환 창이 끝난 뒤 한 번 분석해요. 모든 적격 사용자를 포함하고 2,000명을 넘었다고 잘라내지 않아요. SRM 사례에서 군별 수를 2,000명에 맞추면 비율 이상 자체를 숨길 수 있기 때문이에요. 종료 시각 전이면 사용자 수가 많아도 HOLD_WINDOW로 보류하는 테스트를 넣었어요.

실습을 다시 실행하면 같은 고정 fixture로 코드와 규칙을 재검증해요. 승자가 나올 때까지 새로운 제품 데이터를 만들거나 유리한 결과만 남기는 반복은 하지 않아요. 실시간으로 실험을 중단해야 하는 운영 환경이라면 그 목적에 맞는 순차 분석과 중단 규칙을 사전에 설계해야 해요. 이 코드에는 그 방법이나 여러 지표에 대한 다중 검정 보정이 들어 있지 않아요.

5. 오류·지연을 확인한 뒤 효과와 구간을 읽어요

전환율이 올라가도 요청 실패와 응답 지연이 악화되면 실험을 통과시키지 않도록 했어요. 가드레일 사례에서는 A와 B의 전환율이 10%와 14%였지만, B의 오류율은 5%, p95는 447ms였어요. A의 오류율 0.5%, p95 147ms와 비교해도 악화가 커서 STOP_GUARDRAIL로 판정했어요.

📖 용어: 가드레일과 p95
가드레일은 주목표 지표가 좋아져도 함께 지켜야 하는 품질 기준이에요. p95는 요청 지연을 정렬했을 때 약 95%가 그 값 이하가 되는 지점이에요. 여기서는 중복 요청을 제거한 뒤 ceil(0.95 × 요청 수)번째 값을 사용해요.

전환율은 사용자 기준이고 오류율과 p95는 요청 기준이에요. 가드레일 집계에는 적격 사용자의 전환 관찰 창 안 요청을 사용하고, 같은 request_id를 한 번만 세요. 요청 데이터가 없으면 전환율만으로 통과시키지 않고 HOLD_GUARDRAILS로 보류해요. 이번 문턱은 관측값에 대한 운영 정책이며 통계적 비열등성이나 무해성을 증명한 것은 아니에요.

그림 3. 효과 해석 앞에 데이터·기간·표본·품질 조건을 두었어요.

조건을 충족한 사례에서도 +4%p만 적고 끝내지 않았어요. 각 군의 비율에는 Wilson 구간을, B−A 차이에는 두 Wilson 구간을 조합한 연속성 보정 없는 Newcombe 방법을 사용했어요. 계산 수식은 NIST의 Wilson 설명, Newcombe 원논문 초록, statsmodels의 공식 구현과 대조했어요. 실행 코드에는 해당 라이브러리 의존성을 추가하지 않았어요.

📖 용어: 신뢰구간
같은 설계와 가정으로 표본 추출을 반복할 때, 정한 비율만큼 실제 모수를 포함하도록 구성하는 구간이에요. 이번 Newcombe 95% 구간은 독립적인 두 이항 표본을 가정한 근사 방법이에요. 이 한 구간 안에 실제 값이 있을 확률을 95%로 읽거나 유한 표본의 정확한 포함률을 보장하면 안 돼요.
효과 기준 충족 사례 A = 200 / 2,000 = 10% B = 280 / 2,000 = 14% B−A = +4%p Newcombe 95% 구간 ≈ [+1.99, +6.02]%p 관측 차이 ≥ +3%p, 구간 하한 > 0 → 효과 조건 충족

이 규칙은 관측 차이가 최소 3%p이고 구간이 0을 넘는지 확인해요. 실제 효과가 3%p 이상임을 보장하는 규칙은 아니에요. 구간에는 3%p보다 작은 값도 포함돼요. 효과가 없을 때 오탐할 가능성과 실무적으로 필요한 최소 개선을 어떻게 함께 다룰지는 실험 목적에 맞게 설계해야 해요. ASA의 p값 성명도 p값 하나가 효과 크기를 뜻하거나 의사 결정을 대신하지 않는다고 설명해요.

6. 저장된 원자료로 판정 과정을 다시 확인해요

저장소 루트에서 아래 명령을 실행하면 컨테이너가 테스트와 분석을 수행하고 보고서를 제공해요. 실제 검증에는 Python 3.12.15를 사용했고, 표준 라이브러리 기반 회귀 테스트 14개가 통과했어요. compose의 python:3.12.15-slim 이미지는 실제 실행한 이미지와 같은 digest에 고정했고 별도 pip 설치는 없어요.

docker compose -f labs/devops/deployment-experiments/decision/compose.yaml up -d --force-recreate python3 labs/devops/deployment-experiments/decision/verify.py cat labs/devops/deployment-experiments/decision/out/results.txt open http://localhost:28300

verify.py는 실제 HTTP 결과가 준비될 때까지 기다린 뒤 다섯 판정과 테스트 통과 수를 assert해요. 테스트는 사용자 중복 제거, 시간 창, 표본 부족, SRM 기준값, Wilson 구간의 경계값, 교차 할당, 가드레일 결측과 ID 충돌을 확인해요. 예를 들어 24시간보다 1초 늦은 전환은 제외하고, 진입만 한 사용자는 전환율 분모에 넣지 않아요.

그림 4. 저장된 실행 출력에서도 보고서와 같은 판정을 확인했어요.

원자료는 out/events/*.json.gz, 계획과 전체 통계·중복 제외 수는 out/summary.json, 테스트 기록은 out/tests.txt에 있어요. 화면에서만 수치를 반올림하고 JSON에는 계산 정밀도를 유지해요. 다시 실행할 때는 이전 out을 실습 안 history로 이동해서 증거를 덮어쓰지 않아요. 2편의 실제 HTTP 원자료는 선택적으로 아래 명령으로 대조할 수 있어요.

python3 labs/devops/deployment-experiments/decision/integrate.py labs/devops/deployment-experiments/sticky-ab/out/events.json # 판정 로직만 재검증 python3 -m unittest discover -s labs/devops/deployment-experiments/decision -p 'test_*.py' # 이 실습의 컨테이너만 종료 docker compose -f labs/devops/deployment-experiments/decision/compose.yaml down

연결 실패는 docker compose ... ps에서 컨테이너 상태와 28300 포트를 먼저 확인해요. HOLD_GUARDRAILS가 나오면 요청 이벤트의 오류·지연 필드가 실제로 있는지 살펴봐요. INVALID_SRM은 유리한 전환율로 무시하지 말고 배정과 노출, 수집 누락을 단계별로 대조해야 해요. 고정 계획을 바꿔 판정만 통과시키는 방식으로 해결하지 않아요.

이 실습이 검증한 범위는 합성 이벤트의 집계·통계 계산과 고정된 판정 경로예요. 실제 사용자 효과, 무작위 배정의 인과성, 장기 지표, 순차 분석까지 검증한 것은 아니에요. 코드는 각 조건의 참·거짓을 함께 저장해서 최종 판정 한 단어만으로 원인을 숨기지 않도록 했어요.

✍️ 오늘의 요약
전환율을 해석하기 전에 사용자 분모와 관측 창, 표본 비율·최소 표본·오류·지연을 확인해요.

같은 +4%p도 SRM이나 가드레일에 따라 판정이 달라졌고, +15%p도 사전 표본 조건을 충족하지 못하면 보류했어요. 통과 결과에는 효과 크기와 구간, 적용한 규칙과 그 한계를 함께 남겨요.
