4편에서 사후 분석의 재료는 장애가 끝나기 전에 모아야 한다고 했어요. 말로는 쉽습니다. 그런데 막상 장애가 나면 명령을 치느라 바빠서 시각을 적을 틈이 없고, 다음 날 채팅 기록과 그래프를 맞춰 보며 "이게 몇 시였더라"를 되짚게 돼요.

이번 실습은 장애를 일부러 일으키고, 운영 절차서대로 대응하면서 명령을 치는 순간 시각이 자동으로 남게 해 봅니다. 그 기록에 Prometheus와 Alertmanager의 기록을 합쳐 타임라인을 만들고, 그 타임라인만으로 사후 분석 문서를 씁니다. 숫자와 화면은 전부 실제로 돌린 결과예요.

1. 실습 환경: 주문, 재고, 그 사이의 프록시

주문 서비스가 주문을 받으면 재고 서비스에 재고를 묻습니다. 그 사이에 Toxiproxy를 세워 경로에 지연을 넣을 수 있게 했어요. 주문 서비스는 재고 호출에 1초 타임아웃을 걸었고(2장에서 보듯 요청 전체의 상한은 아니에요), 타임아웃에 걸리면 503을 돌려줍니다. 서비스는 파이썬 표준 라이브러리만으로 짠 작은 서버라 Docker 메모리를 거의 쓰지 않아요. 부하기는 초당 20건씩 주문을 넣습니다.

그림 1. 장애는 Toxiproxy에서 나고, 타임라인은 세 곳의 기록에서 나온다
📖 용어: Toxiproxy
두 서비스 사이에 세우는 TCP 프록시입니다. HTTP API로 "독(toxic)"을 걸어 지연, 대역폭 제한, 연결 끊기 같은 장애를 경로에 넣고 뺄 수 있어요. 지연 독은 latency ± jitter 범위에서 고르게 뽑은 값만큼 데이터를 붙잡아 둡니다(toxics/latency.go).

경고는 두 개입니다. 주문 실패율이 1분 창에서 5%를 1분 넘게 넘으면 OrderErrorRatioHigh(page), 주문 p99가 500ms를 2분 넘게 넘으면 OrderLatencyHigh(ticket)예요. 둘 다 summary와 runbook_url 주석을 달아 알림에서 바로 운영 절차서로 갈 수 있게 했습니다. Alertmanager는 group_wait 30s, group_interval 5m 기본값을 그대로 썼어요.

Prometheus 3.15.0 (스크레이프 5s, 규칙 평가 10s) Alertmanager 0.34.1 (2026-09 최신 안정판) Toxiproxy 2.12.0 (2025-03 릴리스, 그 뒤 안정판 없음) Grafana 13.2.3 Python 3.13 alpine (서비스, 부하기, 웹훅 수신기) 실행 환경 Docker Desktop, Apple M5 Pro

실습 코드는 labs/devops/ir-02-gameday에 있어요. Docker와 파이썬 3만 있으면 됩니다.

git clone https://github.com/DDINGJOO/Platform-study.git cd Platform-study/labs/devops/ir-02-gameday mkdir -p raw # 웹훅 기록 자리. 없으면 Linux 에서 Docker 가 root 로 만들어 쓸 수 없다 docker compose up -d sleep 60 # 1분 창이 찰 때까지 python3 scripts/gd.py diag # 평상시: 재고 호출 p99 0.005s, ok 20/s # Grafana: http://localhost:28030/d/gameday

gd.py는 장애 주입, 진단, 완화, 복구 명령을 실행하면서 그 시각을 raw/events.jsonl과 Grafana 주석에 남기는 작은 도구예요. 사람이 내린 판단도 gd.py event decide "..."로 한 줄 남길 수 있습니다. 3편에서 말한 "결정과 변경은 한 줄씩 채널에 남긴다"를 명령 자체에 묶은 거예요.

2. 장애를 넣고 절차서대로 대응했다

실행 이름을 run-1로 정하고, 재고 경로에 600~1200ms 지연을 넣은 뒤 page 알림을 기다렸어요. 대응자는 저 혼자라 3편의 표현대로 지휘자이자 운영 담당이자 소통 담당입니다.

python3 scripts/gd.py event start run-1 python3 scripts/gd.py inject 900 300 python3 scripts/gd.py wait OrderErrorRatioHigh firing 22:07:58 알림 도착: OrderErrorRatioHigh firing python3 scripts/gd.py diag [diagnose] 주문 실패율(1m)=0.304, 주문 서버 p99(s)=1.489, order가 본 재고 호출 p99(s)=1.489, 재고 서버 자체 p99(s)=0.005, 재고 호출 결과/초={'ok': 13.86, 'timeout': 6.1, 'error': 0.0}

운영 절차서(RUNBOOK.md)의 2단계는 이 숫자 넷을 표 하나로 읽게 해 둡니다. 재고 서버 자체는 5ms인데 주문 쪽에서 본 재고 호출은 1.5초예요. 서버가 아니라 가는 길이 느리다는 뜻이고, 표는 이때 원인을 찾기 전에 3-A 완화(재고 확인을 보류하고 주문을 받는다)부터 하라고 적혀 있습니다.

python3 scripts/gd.py event declare "OrderErrorRatioHigh page 수신. 장애 선언, IC 겸 운영 담당 1인" python3 scripts/gd.py event decide "절차서 2단계 표 1행: 재고 서버는 5ms인데 order가 본 호출은 1.5s. 가는 길이 느림 → 3-A 완화" python3 scripts/gd.py fallback on python3 scripts/gd.py event comms "[조사 중] 주문 일부가 실패하고 있습니다. 재고 확인을 보류하는 완화를 적용했고, 주문은 '확인 보류' 상태로 접수됩니다. 다음 공지 15분 뒤." sleep 75 && python3 scripts/gd.py diag # 실패율 0 확인 (5장에서 다시 본다) python3 scripts/gd.py event note "완화 후 재고 호출이 0건이라 절차서 5단계의 'order가 본 재고 호출 p99' 를 볼 수 없음. 경로를 직접 찔러 확인하기로" # 원인 제거(지연 독 삭제)와 경로 직접 10회 호출. 결과가 probe 행으로 남는다 python3 scripts/gd.py heal && docker compose exec -T order python -c " import urllib.request,time r=[] for i in range(10): t=time.time(); urllib.request.urlopen('http://toxiproxy:28666/stock/A',timeout=3).read(); r.append(round((time.time()-t)*1000,1)) print('경로 직접 호출 10건(ms):',r)" | tee /dev/stderr | xargs -0 python3 scripts/gd.py event probe python3 scripts/gd.py fallback off # 정상 경로 복귀 sleep 90 && python3 scripts/gd.py diag python3 scripts/gd.py event resolved "fallback 끄고 90초간 실패율 0. 정상 경로 복귀"
그림 2. 빨간 점선이 명령 시각이다. 실패는 완화 직후 멈췄지만 경고는 1분 더 빨갛다

위 칸의 실패율은 1분 창이라 완화(22:08:05) 뒤에도 1분 가까이 천천히 내려옵니다. 가운데 칸에서 노란 선(주문이 본 재고 호출)은 1.5초 근처에 붙어 있고 파란 선(재고 서버 자체)은 바닥에 있어요. 아래 칸은 경고 상태입니다. page 경고는 pending(주황)을 1분 거쳐 firing(빨강)이 됐고, fallback(파랑)을 켠 뒤에도 실패율 창이 비워질 때까지 firing으로 남았어요. 패널의 시각 해상도는 15초 정도라 경계는 대략입니다.

p99 1.489초와 1초 타임아웃은 둘 다 보이는 그대로가 아니었다

진단 결과를 다시 보면 이상한 점이 있어요. 타임아웃이 1초인데 p99가 1.489초입니다. 주입 중 110초 동안의 버킷을 직접 세 봤어요.

응답 시간 건수 0.5 ~ 0.75초 282 0.75 ~ 1.0초 892 1.0 ~ 1.5초 1,020 1.5초 초과 0 합계 2,195 (increase 외삽으로 칸의 합과 1건 어긋나요), 같은 구간 503 = 약 673

1.5초를 넘은 응답은 0건이에요. p99 1.489초는 1.0~1.5초 버킷 안을 선형 보간한 값입니다. 그리고 1초를 넘긴 응답이 1,020건인데 실패는 약 673건이에요. 약 347건은 1초를 넘기고도 성공했습니다. 파이썬 urllib의 timeout은 "연결 시도 같은 블로킹 동작"에 거는 값이에요(Python 문서, urllib.request). 요청 전체의 상한이 아니라 소켓 동작 하나하나의 대기 한도예요. 재고 응답은 헤더와 본문이 따로 쓰이고, Toxiproxy는 데이터 조각마다 지연을 새로 뽑아요(toxics/latency.go). 그래서 첫 조각이 1초 안에 오면 전체가 1초를 넘어도 성공할 수 있다고 설명돼요. 사후 분석에 "타임아웃 1초"라고만 쓰면 사용자가 실제로 기다린 최대 시간을 잘못 적게 됩니다.

3. 탐지 113초 중 사람이 쓴 시간은 0초였다

대응이 끝나면 resolved 알림까지 받은 뒤 타임라인을 만듭니다. 알림을 다 받기 전에 돌리면 resolved 행이 빠져요.

python3 scripts/gd.py settle # 울린 경고가 모두 resolved 알림을 받을 때까지 (run-1 은 T+07:43.8) python3 scripts/timeline.py run-1 # results/run-1/timeline.md

명령 기록, 웹훅이 받은 알림, Prometheus의 ALERTS 시계열과 503 카운터를 시각순으로 합치고, 주입 시각을 0으로 둔 상대 시간으로 바꿔요. 앞부분을 옮기면 이렇습니다.

| T+00:00.0 | 명령 기록 | [inject] inventory 경로 latency=900ms jitter=300ms | T+00:02.8 | Prometheus | 503 카운터가 처음 늘어난 스크레이프(영향 시작) | T+00:22.8 | Prometheus | 실패율 기록 규칙이 5% 를 넘음, OrderErrorRatioHigh pending | T+01:22.8 | Prometheus | OrderErrorRatioHigh firing 시작 | T+01:53.3 | 웹훅 수신 | OrderErrorRatioHigh firing (page) startsAt=T+01:22.4 | T+01:57.0 | 명령 기록 | [declare] 장애 선언, IC 겸 운영 담당 1인 | T+02:01.0 | 명령 기록 | [mitigate] order fallback 켬(재고 확인 보류) | T+02:02.8 | Prometheus | 503 카운터가 마지막으로 늘어난 스크레이프(영향 끝)

4편에서 타임라인은 간격으로 읽어야 한다고 했어요. 탐지 113.3초를 간격으로 쪼개면 이렇습니다.

주입 → 첫 503 스크레이프 2.8초 스크레이프 간격 5초 첫 503 → 5% 초과, pending 20.0초 rate(...[1m]) 창이 실패를 쌓는 시간 + 평가 간격 10초 pending → firing 60.0초 for: 1m firing → 웹훅 수신 30.5초 group_wait: 30s ─────────────────────────────────────── 탐지 (TTD) 113.3초 90초는 고정 설정, 23.3초는 주기와 실패 비율
📖 용어: pending과 for
Prometheus 경고 규칙의 식이 처음 참이 되면 경고는 pending 상태가 되고, 식이 for에 적은 시간 동안 계속 참이어야 firing이 됩니다. firing이 된 경고만 Alertmanager로 가서 알림이 돼요. 잠깐 튀었다 사라지는 신호를 거르는 장치예요.

113초 중 90초(for 1m + group_wait)는 고정 설정이고, 나머지 23초는 스크레이프와 평가 주기, 실패 비율이 정했어요. 사람이 쓴 시간은 없습니다. 이 경고가 늦은 게 아니라 이렇게 설계된 겁니다. for: 1m과 group_wait는 잠깐 튀었다 사라지는 신호로 사람을 깨우지 않으려고 넣은 값이고, 그 대가가 90초예요. 탐지를 줄이고 싶다면 사람을 다그칠 게 아니라 이 세 값을 저울질해야 합니다. 그리고 그 저울질은 이미 SLO와 경고 시리즈에서 burn rate로 다룬 문제예요.

반대로 page를 받고 완화 명령까지는 7.7초였습니다. 이건 자랑할 숫자가 아니에요. 대응자가 절차서를 직접 쓴 사람이고, 진단과 완화가 스크립트로 준비돼 있었고, 이미 노트북 앞에 앉아 있었습니다. 새벽 3시에 깨어난 사람의 숫자가 아니라서, 사후 분석에서는 이걸 운이 좋았던 것 칸에 넣었어요.

4. 같은 장애를 반복해 보려다 실행을 버렸다

탐지 시간이 한 번 잰 값으로 충분한지 보려고 같은 장애를 여러 번 반복하는 스크립트(scripts/ttd-trials.sh)를 만들어 돌렸어요. 매 회 주입 전에 0~20초를 무작위로 쉬어 주입 시각이 평가 주기의 다른 위치에 떨어지게 하고, page를 받자마자 독을 걷고, 두 경고의 resolved 알림까지 받은 뒤 다음 회로 넘어갑니다.

그런데 이 반복 실행은 전부 버렸어요. 세 번씩 두 세트를 돌렸고, 세트 안에서 한 회차라도 호스트가 멈추면 그 세트를 통째로 버렸어요. 노트북 덮개가 닫힌 채 배터리로 돌면서 시스템이 잠들었고, 그동안 Docker VM도 같이 멈췄습니다. timeline.py가 실행마다 적는 점검 줄이 그걸 보여 줬어요. 한 회차는 기대한 스크레이프 460개 중 92개만 남았고, 다른 회차는 page 알림이 10분 안에 오지 않았습니다. 두 회차는 주입부터 page까지는 스크레이프가 빠짐없이 남아 있었지만, 그 뒤에 시계가 몇 분씩 건너뛰어서 같은 실행으로 묶기 어렵다고 보고 함께 버렸어요. 그래서 이 글의 탐지, 완화, 복구 숫자는 run-1 한 번뿐입니다(스크레이프 106/106, 부하 최저 19.0건/초).

한 번만 쟀으니, 탐지 시간이 얼마나 흔들릴 수 있는지는 설정에서 범위를 세워 보는 수밖에 없어요. 3장의 네 간격 중 for: 1m(60초)과 group_wait(30초)는 고정이고, 흔들리는 건 앞의 두 간격입니다. 앞의 두 간격을 이루는 것을 하나씩 더하면 이렇습니다.

첫 실패 응답이 나오기까지 (타임아웃) 약 1초 그 실패가 스크레이프되기까지 0~5초 rate 1분 창에서 실패율이 5%를 넘기까지 약 10초 (실패 비율 약 1/3 기준. 비율이 클수록 짧다) 다음 규칙 평가까지 0~10초 for 1m + group_wait 30s 90초 Alertmanager 가 보내기까지 약 1초 ───────────────────────────────────────── 합계 약 102~117초 (run-1: 113.3초)

흔들림의 폭은 주기 두 개(5초, 10초)가 만드는 15초 정도이고, 실패 비율이 달라지면 범위 자체가 옮겨 가요. 확인한 값은 113.3초 하나입니다. 반복 측정은 전원이 연결된 상태에서 같은 스크립트로 다시 돌려야 해요.

⚠️ 주의: 실행이 온전했는지부터 적는다
• 장애 시간을 재는 실습은 측정하는 쪽이 멈추면 장애가 길어진 것처럼 보여요. 이번엔 resolved 알림이 10분 넘게 늦거나 아예 오지 않은 회차가 있었는데, 원인은 Alertmanager가 아니라 잠든 호스트였어요
• 그래서 timeline.py는 실행마다 스크레이프 수와 기대값, 부하 최저치를 같이 적어요. 숫자를 쓰기 전에 그 두 줄부터 봐요
• 노트북에서 돌린다면 측정 전에 pmset -g batt로 전원을, ioreg -r -k AppleClamshellState로 덮개 상태를 확인해요. 덮개가 닫힌 배터리 상태에서는 caffeinate를 걸어도 잠들었어요
📖 용어: MTTR (mean time to recover)
여러 장애의 복구 시간을 평균 낸 값입니다. 운영 지표로 흔히 쓰지만, 무엇을 시작점과 끝점으로 잡는지가 조직마다 다르고, 장애 시간의 분포가 고르지 않아 평균이 대표값 노릇을 못 할 때가 많아요.

장애가 끝난 시각은 끝점을 어디에 찍느냐에 따라 약 3.4배 달라진다

분산은 반복해야 보이지만, 한 번의 실행으로도 확인할 수 있는 게 있어요. 정의입니다. run-1에서 "장애가 끝난 시각"을 네 가지로 재 봤어요.

끝점 주입부터 무엇을 본 것 완화 명령을 친 시각 121.0초 명령 기록 마지막 503 스크레이프 (사용자 영향 끝) 122.8초 503 카운터 경고 endsAt (실패율 창이 비워진 시각) 182.4초 Alertmanager 알림의 endsAt resolved 알림을 받은 시각 413.7초 웹훅 수신 시각

사용자가 아팠던 시간은 약 2분인데, 알림 수신 시각으로 재면 약 7분이에요. resolved 알림은 경고가 끝난 시각(endsAt)보다 3분 51초 늦게 왔습니다. group_interval은 group_wait가 끝나는 순간 시작하는 반복 타이머이고, 그 타이머가 돌아올 때 새로 울렸거나 해결된 경고가 있으면 알림을 보내요(Alertmanager 설정 문서). 실제로 firing 알림(T+01:53.3)에서 정확히 5분 뒤(T+06:53.7)에 resolved가 왔습니다. 알림 도구의 "해결" 시각을 모아 MTTR을 내는 대시보드가 있다면, 그 숫자에는 사람이 고친 시간이 아니라 group_interval이 섞여 있어요.

이건 4편에서 소개한 비판의 한 조각을 확인한 것뿐이에요. 구글의 Davidovič는 시뮬레이션으로 MTTR과 MTTM이 의사 결정과 추세 분석에 잘 맞지 않는다고 보였고, VOID 보고서는 장애 시간 데이터의 분산이 너무 커서 MTTR을 신뢰도 척도로 쓰기 어렵다고 결론 냈습니다. 여기서 보탤 수 있는 건 하나예요. 같은 장애 한 번 안에서도 끝점 정의만으로 숫자가 3.4배 달라진다는 것. 평균을 내기 전에 정의부터 적어야 합니다.

5. 절차서대로 했는데 막힌 곳

대응하면서 절차서가 맞지 않은 곳이 세 군데 나왔어요. 셋 다 사후 분석의 "잘 안 된 것"과 조치 항목이 됐습니다.

완화가 진단 신호를 지웠습니다. 절차서 5단계는 원인을 제거한 뒤 "주문이 본 재고 호출 p99가 평소로 돌아왔는지 본다"고 적혀 있었어요. 그런데 fallback을 켜자 주문 서비스가 재고를 부르지 않으니 그 지표가 비었습니다.

T+03:21.8 [diagnose] 주문 실패율(1m)=0.000, 주문 서버 p99(s)=0.005, order가 본 재고 호출 p99(s)=nan, 재고 서버 자체 p99(s)=nan, 재고 호출 결과/초={'ok': 0.0, 'timeout': 0.0, 'error': 0.0}

nan은 값이 없다는 뜻이에요. 완화는 사용자를 지켰지만, 그 대가로 고쳐졌는지 확인할 눈도 같이 감았습니다. 그 자리에서 경로를 직접 열 번 불러 확인하고(첫 호출 7.9ms, 나머지 0.5~2.1ms) 정상 경로로 되돌렸어요. 조치 항목에는 fallback 중에도 경로를 주기적으로 찌르는 합성 호출을 넣었습니다.

📖 용어: 합성 호출 (synthetic probe)
실제 사용자 요청과 상관없이 모니터링이 일정 간격으로 직접 보내는 요청입니다. 사용자 트래픽이 끊기거나 우회되는 동안에도 그 경로가 살아 있는지 알려 줘요.

ticket 경고는 영향이 끝난 뒤에 울렸습니다. OrderLatencyHigh는 T+02:12.8에 firing, T+02:43.4에 알림이 왔어요. 완화는 T+02:01.0이었습니다. p99를 1분 창으로 보고 for: 2m을 건 결과라 설계대로이긴 한데, 막 완화를 마친 대응자에게는 새 장애처럼 보여요. 같은 원인이면 page가 울리는 동안 ticket을 억제하는 규칙(실습-1의 inhibit)이 필요합니다.

해결 알림에 기준을 넘는 숫자가 적혀 있었습니다. resolved 알림의 summary가 "주문 실패율 5.719% (기준 5%)"였어요. Prometheus는 경고 식이 참인 평가에서만 값과 주석을 다시 계산하고, 식이 거짓이 되면 상태만 inactive로 바꿔요(Prometheus v3.15.0 소스, rules/alerting.go). 그래서 해결 알림에는 마지막으로 참이었던 평가의 값이 남아요. summary에 현재 값을 넣는 습관은 firing 알림에서는 유용하지만 resolved 알림에서는 오해를 만듭니다.

⚠️ 주의: 게임데이 도구가 먼저 멈출 수 있다
• 이 실습의 첫 시도에서 Toxiproxy에 독을 거는 API 호출이 10초 클라이언트 타임아웃(당시 도구 설정)까지 응답하지 않았어요. 그 뒤 독 목록은 비어 있는데 프록시 경유 경로만 5초 타임아웃이 났고(재고 직접 호출은 7ms), 프록시를 재시작해야 풀렸어요
• 같은 조건으로 독 추가와 삭제를 세 번 되풀이했을 때와 이후 실행에서는 다시 나지 않았어요. Toxiproxy 저장소에 열려 있는 이슈 #558(독 삭제 때 제어 포트가 멈춤), #428(죽은 출력에 마지막 버퍼를 쓰다 교착)과 같은 계열의 증상이에요
• 그래서 그 시도는 버리고 새로 돌렸어요. 게임데이 계획에는 "주입 도구가 말을 안 들으면 어떻게 끊나"(여기선 프록시 재시작)를 미리 적어 둬요. 5편의 자동 중단 조건이 이 경우까지 덮어야 해요

6. 타임라인만으로 사후 분석을 썼다

마지막으로 results/run-1/timeline.md만 보고 사후 분석(postmortem.md)을 썼어요. 꾸민 사건은 없고, 모든 시각과 숫자가 타임라인이나 Prometheus 쿼리에서 나왔습니다. 요약과 조치 항목만 옮깁니다.

요약 T+00:02.8부터 약 2분 동안 주문 요청의 약 30%(2,500건 중 747건)가 503으로 실패했다. 재고 서비스로 가는 경로가 0.6~1.2초로 느려지면서 응답 대기 1초를 넘는 요청이 실패했다. T+01:53 page를 받고 T+02:01 재고 확인 보류를 켜서 실패를 멈췄다(이후 1,825건 보류 접수). T+03:28 경로 지연을 제거하고 T+03:32 정상 경로로 되돌렸다. # 유형 우선 끝 상태 1 detect P1 fallback 중에도 재고 경로를 1초마다 찌르는 합성 호출 지표 2 mitigate P1 재고 호출 실패율이 기준을 넘으면 fallback 을 자동으로 켜는 차단기 검토 3 detect P2 같은 원인의 ticket 경고는 page 가 울리는 동안 inhibit 4 investigate P2 완화 시간은 503 카운터, 복구 시간은 정상 경로 복귀 명령 시각으로 정의하고 문서화 5 repair P2 summary 에 현재 값 대신 기준과 창을 적는다 6 investigate P3 Toxiproxy 경로 멈춤 기록, 게임데이 중단 절차에 프록시 재시작 추가

쓰면서 4편의 원칙이 저절로 지켜지는 걸 느꼈어요. 기록이 명령과 지표뿐이라 "누가"를 쓸 자리가 없고, 결정마다 그때 본 숫자가 붙어 있어서 "왜 그게 말이 됐는지"를 따로 기억해 낼 필요가 없었습니다. 예를 들어 "1.5초"라는 판단 근거가 사실은 버킷 보간값이었다는 것도, 판단을 탓하는 문장이 아니라 측정 메모로 적을 수 있었어요.

💡 실무에서는: 장애 중 기록을 자동으로 남기는 방법
• 완화 명령을 스크립트나 챗봇 명령으로 감싸고, 실행할 때 시각과 실행자를 장애 채널과 대시보드 주석에 남겨요. 이 실습의 gd.py가 그 최소형이에요
• 복구 시각은 알림 도구의 resolved 시각이 아니라 SLI 지표로 정의해요. 알림 시각에는 group_interval이 섞여요
• 실행마다 데이터가 온전한지 같이 적어요. 이 실습의 timeline.py는 스크레이프 수와 부하 최저치를 함께 써서, 호스트가 멈췄던 실행을 골라낼 수 있게 했어요
✍️ 오늘의 요약
재고 경로에 600~1200ms 지연을 넣자 주문의 약 30%가 실패했고, page는 주입 113초 뒤에 왔어요. 그중 90초는 for 1m과 group_wait 30s라는 고정 설정이었고, 나머지 23초는 수집·평가 주기와 실패 비율이 정했어요. 사람은 page 뒤 7.7초 만에 완화했어요.

명령 시각, 알림, 지표를 합친 타임라인으로 사후 분석을 쓰니 비난할 자리가 없었고, 대신 절차서의 빈칸(완화가 진단 지표를 지움), 늦게 우는 ticket, 기준을 넘는 숫자가 적힌 해결 알림이 드러났어요. 장애가 끝난 시각은 끝점 정의만으로 약 3.4배가 달라졌습니다. 장애의 숫자는 재기 전에 무엇을 재는지부터 적어야 해요.
