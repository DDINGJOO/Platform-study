CPU 사용률이 한 서비스에서만 늘 높은데, 지표 라이브러리는 없고 코드를 고쳐 배포하려면 다른 팀 일정을 기다려야 해요. 5편은 이런 상황의 답으로 커널에서 요청을 보는 eBPF와 콜스택을 통계적으로 찍는 상시 프로파일링을 들었습니다.

이번 실습에서는 둘을 실제로 붙여 봤어요. 관측 의존성이 없는 스프링 부트 앱에 실행 옵션으로 Pyroscope 자바 에이전트를 붙이고, 옆 컨테이너에 Grafana Beyla를 띄웠습니다. 숫자와 화면은 전부 이번에 돌린 결과입니다.

🧭 이 글에서 확인할 것
• Docker Desktop for Mac에서 eBPF 도구가 정말 도는가?
• eBPF는 URL 경로 템플릿(/price/{sku})을 어떻게 알았는가?
• 프로파일 서버가 받은 데이터는 실제 CPU 사용량의 몇 %였는가?
• 플레임 그래프가 가리킨 곳을 고치면 얼마나 달라지는가?

1. 실습 환경: 코드에는 아무것도 없다

앱에는 엔드포인트가 세 개 있습니다. /price/{sku}는 상품 200개에 할인 규칙을 돌리고(BigDecimal 계산), /report는 2,000줄짜리 보고서 문자열을 만들고, /checkout은 10% 확률로 503을 돌려줘요. build.gradle의 의존성은 spring-boot-starter-webmvc 하나뿐입니다.

그림 1. 앱 이미지에는 에이전트 jar만 넣었고, 나머지는 옆에서 붙였다
📖 용어: Pyroscope 자바 에이전트
JVM에 -javaagent로 붙어 async-profiler를 돌리는 jar입니다. 정해진 간격(기본 10ms)마다 실행 중인 스레드의 콜스택을 찍고, 일정량 이상 메모리를 할당한 지점도 기록해서 10초마다 Pyroscope 서버로 보내요.
📖 용어: Grafana Beyla
eBPF로 프로세스의 네트워크 시스템 콜과 함수에 후크를 걸어 HTTP·gRPC 요청을 관찰하고, 요청 수와 오류, 지연을 지표로 내보내는 도구입니다. 5편에서 본 것처럼 지금은 OpenTelemetry eBPF Instrumentation(OBI)의 배포판이에요.

Beyla 컨테이너는 pid: "service:app"로 앱 컨테이너와 PID 네임스페이스를 같이 쓰고, eBPF 프로그램을 커널에 올려야 해서 privileged로 띄웠어요. 쓴 버전과 돌리는 법입니다.

Spring Boot 4.1.1 (Java 21, Temurin 21.0.12) Pyroscope 자바 에이전트 2.9.2 Pyroscope 서버 2.3.2 Grafana Beyla 3.38.0 Prometheus 3.15.0 Grafana 13.2.3 k6 2.3.0 (VU 10개, 3분) 실행 환경 Docker Desktop (리눅스 6.12 linuxkit, arm64), Apple M5 Pro

2. eBPF는 Mac의 Docker에서도 돌았다

Docker Desktop for Mac은 리눅스 가상 머신(linuxkit) 위에서 컨테이너를 돌립니다. 그 커널에서 eBPF가 막혀 있을 수도 있다고 보고 시작했는데, Beyla는 첫 실행에 그대로 붙었어요.

msg="Grafana Beyla" Version=v3.38.0 msg="instrumenting process" cmd=/opt/java/openjdk/bin/java pid=1 type=java service=shop msg="creating or accessing OTEL namespace in bpffs failed ..." (경고)

→ 앱의 자바 프로세스를 찾아 계측을 시작했다는 뜻이에요. 경고는 /sys/fs/bpf가 없어 프로파일 연계 같은 일부 기능을 끈다는 것이고, HTTP 지표와는 상관이 없었어요.

이 VM의 커널은 6.12였고 BTF 정보(/sys/kernel/btf/vmlinux)도 있었어요. 5편에서 본 verifier가 있는 최신 커널이면 VM 위라도 eBPF는 동작합니다. 다만 앱 컨테이너를 재생성하면 PID 네임스페이스를 빌려 쓰던 Beyla가 Exited (137)로 같이 죽으니, 둘을 함께 다시 띄워야 해요.

요청 수는 k6와 맞았다

3분 부하 동안 Beyla가 센 요청 수를 k6가 보낸 수와 맞춰 봤어요. 아래 3절의 실행 A(초당 약 4천 건)와 5절의 실행 C(초당 약 1.5만 건)입니다.

k6가 보낸 요청 Beyla가 센 요청 실행 A 726,468 726,469 실행 C 2,769,149 2,769,143

A의 1건은 부하 전에 보낸 확인용 curl로 보이고, C는 277만 건 중 6건이 적었어요. 503 비율도 코드에 넣은 10% 근처였습니다(탐색 실행에서 /checkout 219,184건 중 21,923건).

📖 용어: RED 지표
요청 수(Rate), 오류 수(Errors), 처리 시간(Duration)입니다. 서비스가 사용자에게 어떻게 보이는지를 가장 짧게 요약하는 세 가지라서, 서비스 대시보드의 첫 줄에 많이 둬요.
그림 2. 왼쪽 구간이 실행 B, 오른쪽이 5절에서 고친 뒤의 실행 C다

오른쪽 아래 p99 패널은 5ms와 10ms 두 값에만 붙어 있어요. Beyla의 기본 버킷(0.005, 0.01, 0.025초…)이 거칠어 백분위가 버킷 경계로 보간되기 때문이에요.

eBPF가 어떻게 {sku}를 알았나

가장 의외였던 건 http_route="/price/{sku}"라는 라벨이었어요. 커널이 보는 건 GET /price/sku-17 같은 실제 요청 줄뿐이고, {sku}는 컨트롤러의 @GetMapping에만 있어요.

OBI 소스를 찾아보니 pkg/internal/transform/route/harvest/java에 답이 있었습니다. 실행 중인 프로세스의 jar에서 클래스 파일을 읽어 스프링 매핑 애노테이션과 JAX-RS @Path의 경로 템플릿을 모으고, 커널에서 본 실제 경로를 거기에 맞춰요. 경로를 템플릿으로 묶지 못했다면 sku 값마다 라벨이 생겨서 실습-1에서 본 카디널리티 문제가 됐을 겁니다.

하나 더 있었어요. 앱 프로세스가 연 파일 목록을 보니, 우리가 붙이지 않은 jar가 들어 있었습니다.

docker compose logs beyla | grep inject → msg="injecting OpenTelemetry eBPF instrumentation for Java process" docker compose exec app sh -c 'ls -l /proc/1/fd | grep jar' /app/zc.jar /pyroscope/pyroscope.jar /tmp/obi-java-agent.jar ← Beyla 가 실행 중인 JVM 에 붙인 자바 에이전트

Beyla가 HotSpot의 동적 attach로 자기 자바 에이전트를 JVM에 붙인 거예요. OBI 설정 문서는 이 에이전트를 TLS 추적, 가상 스레드 연결, JVM 런타임 지표용이라고 적어요. 자바는 OpenSSL이 아닌 자체 TLS 구현을 써서 5편의 "OpenSSL 함수에 uprobe를 거는" 방법이 통하지 않으니, 그 자리를 자바 에이전트로 메운 겁니다. 그래서 Beyla의 OTEL_EBPF_JAVAAGENT_ENABLED를 false로 넘겨 끄고 30초를 다시 돌려 봤어요.

OBI_JAVAAGENT=false docker compose --profile ebpf up -d app beyla # compose 가 OTEL_EBPF_JAVAAGENT_ENABLED 로 넘긴다 DURATION=30s ./run-load.sh

에이전트 jar는 붙지 않았고, 요청 77,646건이 k6와 정확히 같은 수로, /price/{sku} 라벨도 그대로 잡혔습니다. 평문 HTTP의 RED 지표는 eBPF만으로 나온 거예요.

⚠️ 주의: "eBPF라서 프로세스를 안 건드린다"는 기본값이 아니다
Beyla 3.38.0은 기본 설정으로 실행 중인 JVM에 자바 에이전트를 붙였어요. 앱 로그에는 JVM 경고(bootstrap classpath has been appended) 한 줄이 더 찍힐 뿐이에요. 운영 JVM에 무엇이 들어가는지 관리하는 곳이라면 OTEL_EBPF_JAVAAGENT_ENABLED 값을 명시적으로 정해 두세요. 이 주입 경로에는 OBI 0.4.0 이상 0.8.0 미만에 영향을 준 보안 취약점(CVE-2026-41433, 0.8.0에서 수정)이 있었어요. Beyla 3.38.0은 OBI 0.14.0 기반이라 해당하지 않습니다.

3. 프로파일 서버에는 14%만 들어왔다

이제 Pyroscope입니다. 탐색 실행의 플레임 그래프는 그럴듯했는데, 3분 부하의 CPU 합계가 95초였고 같은 부하를 다시 주니 182초가 나왔어요. 그래서 실행 A부터는 앱 컨테이너의 cgroup CPU 사용량(/sys/fs/cgroup/cpu.stat의 usage_usec)을 부하 앞뒤로 같이 쟀습니다(run-load.sh).

./run-load.sh http_reqs......................: 726468 4035.827389/s window 1791619101 1791619282 app_cpu_seconds=744.3 (4.11 cores) rejected_uploads=14

앱은 3분 동안 CPU를 744초(코어 4.1개) 썼는데, Pyroscope가 받은 CPU 프로파일의 합은 105.8초였어요. 14%입니다. 앱 로그에 답이 있었습니다.

[ERROR] Error uploading snapshot: 422 {"code":"unknown","message":"parsing IngestInput-pprof failed loadJFRFromForm failed to decompress jfr: decompressed size exceeds maximum allowed size of 4194304 bytes"}

→ 에이전트가 10초마다 보내는 JFR(JVM 이벤트 기록 형식) 묶음이 압축을 풀면 4MiB를 넘어서 서버가 422로 거절했다는 뜻이에요. 3분 동안 18번 정도의 업로드 중 14번이 버려졌어요. 서버의 -validation.max-profile-size-bytes 기본값이 4MiB이고, 2026년 1월 크기 제한 변경(#4734)으로 JFR 업로드에도 걸리게 됐어요. 초당 수 GB를 할당하는 이 앱은 문서가 권하는 할당 임계값(512k)으로도 10초치가 한도를 넘었습니다.

서버 한도를 16MiB로 올리고 같은 부하를 다시 돌렸어요(실행 B). Pyroscope 컨테이너를 새 값으로 다시 만들어야 하니 프로필 전체를 다시 올립니다. 거절은 0건이 됐어요.

PYROSCOPE_MAX_PROFILE_BYTES=16777216 docker compose --profile ebpf up -d PYROSCOPE_MAX_PROFILE_BYTES=16777216 ./run-load.sh
그림 3. 프로파일의 CPU 합계를 cgroup의 실제 CPU 초와 나란히 놓아 본 결과

B는 86%, 5절의 C는 97%였어요. B가 왜 C보다 낮은지는 확인하지 못했어요. 거절은 없었습니다.

무서운 점은 A의 플레임 그래프가 B와 거의 같은 모양이었다는 거예요. 보고서 함수가 차지하는 비율이 A 68.0%, B 74.2%로 비슷했습니다(모든 경로를 더한 값, top-frames.py). 비율은 비슷해도 "이 함수가 CPU를 몇 초 썼나"에는 7분의 1로 답해요. 프로파일도 수집 경로에서 말없이 버려질 수 있고, 플레임 그래프의 모양만으로는 그걸 알 수 없습니다.

4. 플레임 그래프는 예상과 다른 줄을 가리켰다

B 실행의 CPU 플레임 그래프입니다. 위에서 아래로 호출이 깊어지고, 가로 폭이 그 함수 아래에서 쓴 CPU 시간이에요. 검색창에 lab/zc를 넣어 앱 코드 프레임을 색으로 표시했습니다.

📖 용어: 플레임 그래프 (flame graph)
콜스택 표본을 합쳐서, 함수 하나를 막대 하나로 그린 그림입니다. 막대 폭이 그 함수와 그 아래 호출에 쓰인 몫이고, 막대 아래에 다른 막대가 없는 부분이 그 함수가 직접 쓴 몫이에요. Grafana는 위에서 아래로 내려가게 그립니다.
그림 4. 가장 넓은 막대는 보고서의 String.format, 그 아래는 정규식이었다

앱을 만들 때는 /price의 BigDecimal 복리 계산이 가장 무거울 거라고 생각했어요. 코드 주석에도 그렇게 적어 뒀습니다. 플레임 그래프는 달랐어요. 그림의 가장 넓은 막대는 보고서의 formatRow로 전체 11.0분 중 6.63분(60%)이었고, 그 아래 Formatter.parse가 4.01분(36%), 그 아래는 java.util.regex였습니다. 할인 계산은 8.5%였어요. 다른 비율은 top-frames.py로 모든 경로를 더한 값이라 그림의 막대보다 조금 커요(formatRow 66.5%).

String.format("%08d|%-20s|%12.2f|%s%n", i, "item-" + i, i * 1.5, "x".repeat(64))

JDK 21의 Formatter.parse 소스를 보면 이유가 나옵니다. % 바로 뒤가 s, d 같은 변환 문자 하나면 빠른 경로로 처리하지만, %08d, %-20s, %12.2f처럼 플래그나 폭이 붙으면 정규식 FORMAT_SPECIFIER_PATTERN으로 매칭해요. 줄 하나에 정규식 매칭이 세 번, 보고서 하나에 6,000번입니다.

할당 플레임 그래프는 같은 메서드 안의 다른 줄을 가리켰어요.

그림 5. 할당은 200줄짜리 문자열 이어 붙이기가 3분의 1을 차지했다
📖 용어: TLAB 할당 샘플
JVM은 스레드마다 작은 메모리 구역(TLAB)을 주고 그 안에서 객체를 할당합니다. 에이전트는 새 TLAB을 받거나 큰 객체를 바깥에 할당하는 순간을 표본으로 기록하고, 그 크기로 전체 할당량을 추정해요. 그래서 바이트 수는 정확한 합이 아니라 추정치입니다.

할당된 바이트의 87.9%가 보고서에서 나왔고, 그중 formatRow가 47.7%, out = out + l 반복(StringConcatHelper.simpleConcat)이 34.7%였어요. 이어 붙이기는 200줄뿐이지만 매번 길어지는 문자열 전체를 새 배열로 복사해요. CPU와 할당은 같은 메서드 안에서도 서로 다른 줄을 가리킵니다.

5. 고치고 다시 잰다

보고서를 StringBuilder 하나에 직접 쓰는 구현을 만들고(REPORT_IMPL=builder), 같은 부하를 3분 돌렸어요. 결과가 원래 구현과 같은지는 몇 줄을 골라 비교했어요.

PYROSCOPE_MAX_PROFILE_BYTES=16777216 REPORT_IMPL=builder docker compose --profile ebpf up -d app beyla REPORT_IMPL=builder PYROSCOPE_MAX_PROFILE_BYTES=16777216 ./run-load.sh B (String.format) C (StringBuilder) k6 처리량 4,494 req/s 15,384 req/s 앱 CPU (cgroup, 3분) 768초 734초 보고서 1건당 CPU 약 2.1ms 약 0.24ms 보고서 1건당 할당(추정) 약 6.4MB 약 0.77MB (보고서 1건당 값 = 프로파일의 render 합계 ÷ Beyla가 센 /report 수)

두 실행 모두 코어 4개 남짓을 썼으니 같은 CPU로 3.4배를 처리한 셈이에요. B의 건당 값은 집계가 끝 몇 초를 놓쳐 조금 클 수 있어요.

그림 6. 고치고 나니 처음에 가장 무겁다고 짐작했던 BigDecimal.pow가 1위로 올라왔다

고친 뒤의 그래프에서는 보고서가 CPU의 28.2%로 줄었고, PriceService.quote가 37.6%로 가장 넓어졌어요. 그 아래 BigDecimal.pow가 27.1%입니다. 짐작으로 BigDecimal부터 고쳤다면 CPU의 8.5%를 손봤을 거예요.

💡 실무에서는: 코드 없이 붙이는 관측을 쓸 때
• 프로파일러를 붙였으면 한 번은 프로파일 CPU 합계를 컨테이너의 실제 CPU 초와 맞춰 봐요. 에이전트 로그의 Error uploading snapshot도 알람 대상이에요
• 할당이 많은 서비스는 서버의 프로파일 크기 한도를 올리거나, 할당 임계값을 키우거나, 업로드 간격(PYROSCOPE_UPLOAD_INTERVAL)을 줄여요
• Beyla를 쓰면 히스토그램 버킷을 서비스 지연대에 맞추고, 자바 에이전트 주입 여부를 설정으로 정해 둬요

6. 5편과 맞춰 보면

5편은 eBPF가 "경계에서 일어나는 일"만 보고 비즈니스 맥락은 앱만 안다고 했어요. Beyla는 클래스 파일을 읽고 JVM에 에이전트를 붙여 그 경계를 조금 넘었지만, "이 주문이 어떤 사용자의 무엇인지"는 여전히 지표에 없었어요.

이번에 쓴 Pyroscope 자바 에이전트는 eBPF가 아니라 JVM 안의 async-profiler였고, 샘플 간격 10ms는 5편의 "초당 약 100번"과 같았어요. 에이전트와 Beyla가 얹은 비용은 따로 재지 않았습니다.

✍️ 오늘의 요약
의존성이 webmvc 하나뿐인 앱에서 Pyroscope 에이전트로 CPU·할당 플레임 그래프를, Beyla로 HTTP RED 지표를 얻었다. Beyla는 Docker Desktop의 6.12 커널에서 그대로 돌았고 요청 수는 k6와 거의 맞았다. 라우트 템플릿은 jar의 애노테이션에서 왔고, 기본 설정은 JVM에 자바 에이전트를 붙였다.

프로파일은 처음에 서버의 4MiB 한도에 걸려 실제 CPU의 14%만 저장됐는데, 그래프 모양은 멀쩡했다. 한도를 올린 뒤의 그래프는 짐작과 다른 줄(String.format의 정규식, 문자열 이어 붙이기)을 가리켰고, 그 줄을 고치자 같은 CPU로 3.4배를 처리했다. 코드 없이 얻은 관측도 수집 경로까지 맞춰 봐야 믿을 수 있다.
