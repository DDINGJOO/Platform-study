장애 회고에서 이런 말이 나옵니다. "어떤 사용자가 겪었는지 알 수가 없었어요. 다음부터는 지표에 user_id를 붙여 둡시다." 코드로는 .tag("user_id", user) 한 줄이에요. 리뷰에서도 잘 걸리지 않습니다. 그런데 1편은 이 한 줄이 시계열 수를 사용자 수만큼 곱한다고 했어요.

이번 글에서는 그 곱셈을 직접 해 봅니다. 스프링 부트 앱에 user_id 태그를 붙였다 떼면서 Prometheus의 시계열 수, 스크레이프 크기, 메모리를 쟀어요. 숫자와 화면은 전부 이번에 돌린 결과입니다.

🧭 이 글에서 확인할 것
• 사용자 1,000명이 한 번씩 주문하면 시계열은 몇 개가 되는가?
• 같은 태그를 카운터에 붙일 때와 타이머에 붙일 때는 얼마나 다른가?
• 태그를 떼고 앱을 다시 배포하면 Prometheus의 메모리는 바로 돌아오는가?
• 시계열 수 상한(sample_limit)을 걸면 넘쳤을 때 무슨 일이 생기는가?

1. 실습 환경: 앱 하나, Prometheus, Grafana

앱은 GET /checkout?user=u42 요청을 받으면 주문을 처리하는 척하고 지표 두 개를 남깁니다. 주문 수를 세는 카운터 shop.orders와 처리 시간을 재는 타이머 shop.checkout이에요. 둘 다 결과(result: ok 또는 declined)를 태그로 달고, 결과는 5% 확률로 declined가 됩니다. 환경변수 LAB_USER_TAG로 user_id 태그를 어디에 붙일지 고릅니다.

LAB_USER_TAG=none user_id 를 아무 데도 붙이지 않는다 LAB_USER_TAG=counter 카운터에만 붙인다 LAB_USER_TAG=timer 타이머에도 붙인다 LAB_USER_TAG=histogram 타이머에도 붙이고, 히스토그램 버킷까지 켠다

Prometheus는 앱을 5초마다 긁어 갑니다(기본값 1분을 실습 시간 때문에 줄였어요). k6로 사용자 u1부터 u1000까지 한 번씩 주문해서 user_id가 정확히 1,000가지 값이 되게 했어요.

📖 용어: 스크레이프 (scrape)
Prometheus가 대상의 HTTP 엔드포인트를 호출해서 지금 값을 텍스트로 받아 가는 일입니다. 한 번의 응답에 든 줄 하나가 시계열 하나의 값이에요. 2편에서 본 pull 방식이 이것입니다.
📖 용어: head 시계열 (prometheus_tsdb_head_series)
Prometheus는 최근 몇 시간치 데이터를 head라는 메모리 영역에 두고, 오래된 것만 디스크 블록으로 내립니다. prometheus_tsdb_head_series는 지금 head에 올라 있는 시계열 수예요. Prometheus 메모리 사용량을 가장 직접적으로 설명하는 숫자입니다.

쓴 버전은 아래와 같습니다.

Spring Boot 4.1.1 (Java 21, Micrometer 1.17.1) Prometheus 3.15.0 Grafana 13.2.3 k6 2.3.0 실행 환경 Docker Desktop, Apple M5 Pro

실습 코드는 GitHub 저장소의 labs/observability/metrics-01-cardinality에 있습니다. 앱은 이미지 안에서 빌드하니 Docker와 Python 3만 있으면 돼요. run-phases.sh는 태그 자리를 none, counter, timer, histogram, none 순서로 바꿔 가며 앱을 다시 띄우고, 부하를 준 뒤 30초 기다렸다가 measure.py로 숫자를 찍습니다.

git clone https://github.com/DDINGJOO/Platform-study.git cd Platform-study/labs/observability/metrics-01-cardinality docker compose up -d --build ./run-phases.sh # 단계마다 measure.py 한 줄씩. 5분쯤 걸린다 # Grafana: http://localhost:21000 → 대시보드 "카디널리티 실습"

2. 카운터에 user_id를 붙이면 1,000개가 늘어난다

태그 없이 돌린 기준선에서 앱이 내보낸 줄은 108개였어요. 대부분 JVM, 톰캣, HTTP 요청 지표입니다.

카운터에 user_id를 붙이고 같은 1,000명을 다시 보냈습니다. 앱 응답에서 사용자 한 명의 줄을 꺼내 보면 이렇게 생겼어요.

shop_orders_total{result="ok",user_id="u7"} 1.0 shop_orders_total{result="ok",user_id="u8"} 1.0 shop_orders_total{result="declined",user_id="u9"} 1.0 ... ← 이런 줄이 1,000개

값은 전부 1이지만 Prometheus 입장에서는 줄 하나하나가 따로 저장할 시계열이에요. 앱이 내보낸 줄은 108개에서 1,106개가 됐습니다. 태그 없던 카운터 두 줄(ok, declined)이 사라지고 사용자별 1,000줄이 생겨서 998개가 늘었어요.

📖 용어: 카디널리티 (cardinality)
태그가 가질 수 있는 값의 가짓수입니다. 지표 하나의 시계열 수는 그 지표에 달린 태그들의 카디널리티를 곱한 값까지 늘어날 수 있어요. result가 2가지, user_id가 1,000가지면 최대 2,000개입니다.

"최대"라는 말이 중요합니다. 한 사용자가 한 번만 주문했으니 처음엔 1,000개였지만, 다음 단계에서 같은 1,000명이 다시 주문하자 declined가 나온 사용자가 생겼어요. 세 단계를 거친 뒤 Prometheus가 본 shop_orders_total 시계열은 1,145개였어요. 같은 사용자라도 다른 태그의 값이 바뀌면 시계열이 또 하나 생깁니다. 곱셈의 상한은 태그 값이 섞일수록 실제 숫자에 가까워집니다.

3. 사용자 한 명당 줄 수가 1, 4, 73으로 늘어난다

다음은 타이머에도 user_id를 붙인 단계, 그리고 그 타이머에 히스토그램 버킷까지 켠 단계입니다. 히스토그램은 publishPercentileHistogram() 한 줄이고, p99를 그리려면 보통 이걸 켭니다.

LAB_USER_TAG 앱이 내보낸 시계열 스크레이프 본문 스크레이프 시간 Prometheus head 시계열 none 108 13.6 KB 9.8 ms 830 counter 1,106 62.6 KB 10.3 ms 1,853 timer 4,100 236.3 KB 20.9 ms 4,944 histogram 73,100 5,356.7 KB 68.1 ms 74,275 (사용자 1,000명이 한 번씩 주문, 스크레이프 주기 5초, 부하가 끝나고 30초 뒤에 잼)

타이머 단계에서는 사용자 한 명당 세 줄이 더 생겼어요. 타이머는 Prometheus로 나갈 때 _count, _sum, _max 세 시계열이 되기 때문입니다. 히스토그램 단계에서는 사용자 한 명당 73줄이 됐어요. 앱 응답에서 사용자 u7의 줄을 이름별로 세 보면 이렇습니다.

curl -s localhost:21080/actuator/prometheus | grep 'user_id="u7"' | awk -F'{' '{print $1}' | sort | uniq -c 69 shop_checkout_seconds_bucket ← le="0.001" 부터 le="30.0" 까지 68개 + le="+Inf" 1 shop_checkout_seconds_count 1 shop_checkout_seconds_max 1 shop_checkout_seconds_sum 1 shop_orders_total
📖 용어: 히스토그램 버킷 (le)
"처리 시간이 0.001초 이하인 요청 몇 건, 0.002초 이하 몇 건"처럼 경계별 누적 건수를 따로 내보내는 방식입니다. 경계 하나가 le 태그 값 하나이고, 그래서 시계열 하나가 됩니다. 서버에서 여러 인스턴스를 합쳐 백분위를 계산할 수 있게 하는 대가예요.

문서와 다른 점도 있었어요. Micrometer 문서는 타이머 기본 범위를 1밀리초~1분, 버킷 73개로 적지만, 실제로는 30초까지 68개에 +Inf를 더한 69개였습니다. 1.17.1 소스의 AbstractTimerBuilder 기본 최댓값이 Duration.ofSeconds(30)이에요. 버킷 수는 자기 앱의 엔드포인트에서 직접 세는 게 정확해요.

그림 1. 사용자 한 명이 남기는 줄은 붙인 자리에 따라 1줄, 4줄, 73줄이 된다

Grafana 대시보드로 보면 단계마다 선이 한 단씩 올라갑니다. 시계열 수 패널은 로그 눈금이라 한 칸이 10배예요.

그림 2. 마지막 단계에서 태그를 뗐는데, 초록 선(head)은 내려오지 않았다

노란 선이 단계 사이마다 떨어지는 건 앱을 다시 띄웠기 때문이에요. 오른쪽 아래 패널은 스크레이프 한 번의 응답 크기인데, 히스토그램 단계에서 5.2MB가 됐어요. 5초마다 긁으니 이 앱 하나에서만 초당 1MB 넘게 Prometheus로 들어갑니다. 스크레이프 시간도 10ms에서 68ms로 늘었어요.

Prometheus 웹 화면의 Status → TSDB status에서도 같은 결과를 볼 수 있습니다. 실무에서 시계열을 가장 많이 늘린 태그를 찾을 때 가장 먼저 여는 화면이에요.

그림 3. 시계열을 가장 많이 늘린 태그는 user_id, 가장 많은 지표는 버킷

4. Prometheus 메모리는 시계열 수를 따라간다

1편은 공개된 운영 사례를 들어 "활성 시계열 하나당 대략 3~4KB"라고 했어요. 이번 실행의 숫자로 나눠 보겠습니다. 히스토그램 단계에서 head 시계열이 830개에서 74,275개로 73,445개 늘었고, 그동안 Prometheus의 메모리는 이렇게 변했어요.

none 단계 histogram 단계 늘어난 양 시계열 하나당 Go heap in-use 25.0 MB 175.5 MB 150.5 MB 약 2.1 KB 프로세스 RSS 93.1 MB 247.5 MB 154.4 MB 약 2.2 KB
📖 용어: RSS (resident set size)
프로세스가 지금 실제 물리 메모리에 올려 둔 크기입니다. 컨테이너 메모리 한도와 OOM 판단에 쓰이는 숫자에 가까워요. Go heap in-use는 그중 Go 런타임이 객체를 담는 데 쓰고 있는 부분입니다.

2KB 남짓으로 1편의 숫자보다 작지만, 시계열이 생긴 지 1~2분 됐을 때 잰 값이라 샘플이 쌓일수록 커지고, 1편이 근거로 든 운영 사례의 3KB 남짓은 샘플까지 포함한 값이라 직접 비교하기는 어려워요. 시계열 하나의 값은 작아도, 1,000명 곱하기 73줄은 150MB입니다.

5. 태그를 떼도 head는 줄지 않는다

여기서 예상과 다른 일이 일어났습니다. 태그를 떼고(LAB_USER_TAG=none) 앱을 다시 띄우자 앱이 내보내는 줄은 바로 108개로 돌아왔는데, head 시계열은 3분을 더 기다려도 74,275개 그대로였어요. 그림 2의 초록 선이 내려오지 않은 게 이 장면이에요.

앱이 더 이상 내보내지 않는 시계열은 스크레이프 때 "끝났다"는 표시(stale 표시)를 받아서 쿼리 결과에서는 바로 빠집니다. 하지만 메모리에서 지워지는 건 다른 시점이에요. Prometheus는 head에 쌓인 데이터를 2시간 단위 블록으로 디스크에 내리는데(컴팩션), 기본 설정에서는 블록을 하나 내린 직후에 head를 정리하면서 그 뒤로 샘플이 없는 시계열을 지웁니다.

📖 용어: head 컴팩션 (head compaction)
head에 쌓인 오래된 구간을 잘라 디스크 블록으로 쓰고, 그 구간을 메모리에서 비우는 작업입니다. 이 직후에 "Head GC"가 돌면서 더는 샘플이 없는 시계열을 메모리에서 지워요.

Prometheus 3.15.0 소스(tsdb/head.go)를 보면 컴팩션 조건은 MaxTime - MinTime > chunkRange/2*3입니다. 블록이 기본 2시간이니 head에 3시간이 넘게 쌓여야 첫 2시간을 내리고, 끊긴 시계열이 지워지기까지는 블록 경계에 따라 1~3시간이 걸려요.

그림 4. 지워지는 시점은 태그를 뗀 시각이 아니라 블록 경계가 정한다

그래서 시험용 옵션 --storage.tsdb.min-block-duration으로 블록 길이를 5분으로 줄여 따로 돌려 봤어요.

docker compose down -v PROM_BLOCK=5m LAB_USER_TAG=histogram docker compose up -d ./wait-app.sh && docker compose --profile load run --rm -e USERS=1000 load LAB_USER_TAG=none docker compose up -d app # 1분 뒤 태그를 뗀다 python3 measure.py # 30초마다 다시 돌려 head_series 를 본다 docker compose logs prometheus | grep -E "write block|Head GC"
그림 5. 태그를 뗀 지 6분 뒤, 블록이 써지는 순간에야 head가 비워졌다
15:32:20 태그를 떼고 앱 재시작 head 73,868 앱 105 15:38:21 (6분 동안 그대로) head 73,868 15:38:27 msg="write block started" mint=15:30:54 maxt=15:35:00 15:38:28 msg="Head GC started" caller=truncateMemory 15:38:28 msg="Head GC completed" duration=69ms 15:38:51 head 865

head가 처음 샘플을 받은 15:30:54에서 7분 30초(5분의 1.5배)가 지난 15:38:27에 블록이 써졌고, 바로 이어진 Head GC에서 7만 3천 개가 지워졌어요. 소스에서 읽은 조건 그대로입니다. Go heap in-use도 이때 175MB에서 78MB로 내려왔어요(RSS는 191MB 그대로였어요).

⚠️ 주의: 태그를 뗀 배포가 메모리 문제를 바로 풀지는 않는다
카디널리티 폭발로 Prometheus가 OOM 직전이라면, 태그를 뗀 배포를 내보내도 기본 설정에서는 1~3시간 동안 메모리가 그대로예요. 그 사이 Prometheus가 재시작되면 WAL을 다시 읽으면서 같은 시계열을 다시 메모리에 올립니다. 급할 때는 metric_relabel_configs에서 문제 지표를 action: drop으로 통째로 버려요. 태그만 빼면(labeldrop) 사용자별 시계열 1,000개가 같은 라벨 조합으로 겹쳐 샘플이 거부되니 확인이 필요해요. Prometheus 3.15에는 stale 시계열 비율이 임계값을 넘으면 바로 컴팩션하는 실험적 설정(storage.tsdb.stale_series_compaction_threshold, 기본 0으로 꺼짐)과 prometheus_tsdb_head_stale_series 지표도 있는데, 이번 실습에서 시험하지는 않았어요. min-block-duration은 문서에 "For use in testing"이라고 적힌 옵션이라 운영에서 바꿀 값이 아닙니다.

6. 방어선을 걸었더니 타깃이 통째로 죽었다

1편은 방어선으로 스크레이프 한 번의 시계열 수 상한인 sample_limit을 들었어요. 한도를 2,000으로 걸고(prometheus-limited.yml) 시험했어요.

docker compose down -v PROM_CONFIG=prometheus-limited.yml LAB_USER_TAG=counter docker compose up -d ./wait-app.sh docker compose --profile load run --rm -e USERS=1000 load # 1,106개: 한도 안 docker compose --profile load run --rm -e USERS=2500 load # 2,705개: 한도 초과

2,500명이 되어 2,705개가 되자 다음 스크레이프부터 타깃이 DOWN이 됐습니다.

그림 6. 앱은 멀쩡한데 Prometheus는 이 타깃을 DOWN으로 본다
Error scraping target: sample limit exceeded

→ 줄 수가 한도를 넘어 그 스크레이프 전체를 버렸다는 뜻이에요(설정 문서: "스크레이프 전체를 실패로 취급한다"). 넘친 줄만이 아니라 JVM 지표, HTTP 지표까지 전부 버려요. 그리고 up이 0이 됩니다.

앱은 멀쩡한데 up == 0 알람이 울려요. prometheus_target_scrapes_exceeded_sample_limit_total이 늘고 있으면 앱이 죽은 게 아니라 한도에 걸린 겁니다.

한도에 걸린 직후 한도 전에 읽은 시계열 일부(이번에는 shop_orders_total 1,000개 중 339개와 JVM 지표)는 stale 표시 없이 lookback 5분 동안 마지막 값으로 남았어요(scrape/scrape.go에서 실패한 스크레이프를 처리하는 방식). 그래서 일부 패널이 마지막 값으로 몇 분 동안 멈춰 보이고, 그래프가 평평하다고 정상이라는 뜻은 아니에요.

💡 실무에서는: 카디널리티를 지킬 때
• sample_limit은 Prometheus를 지키는 마지막 방어선이에요. 걸 때는 prometheus_target_scrapes_exceeded_sample_limit_total 증가 알람을 같이 만들어요
• 한도에 닿기 전에 알 수 있게 extra_scrape_metrics: true를 켜고 scrape_samples_scraped / scrape_sample_limit 비율을 봐요
• 히스토그램은 꼭 필요한 타이머에만 켜고, minimumExpectedValue와 maximumExpectedValue로 범위를 좁히면 버킷 수가 줄어요
• 새 태그가 들어간 배포 뒤에는 TSDB status 화면의 상위 태그 목록을 한 번 열어 봐요
✍️ 오늘의 요약
user_id 태그 하나가 사용자 1,000명에 대해 카운터로는 1,000개, 히스토그램 타이머로는 7만 3천 개의 시계열을 만들었다. 곱해지는 대상은 지표 이름이 아니라 그 지표가 내보내는 줄 전부라서, 같은 태그도 어느 미터에 붙이느냐에 따라 사용자 한 명당 줄 수가 1줄에서 73줄까지 달라진다. 이번 실행에서 Prometheus 메모리는 시계열 하나당 2KB 남짓씩 늘었고, 스크레이프 한 번은 5.2MB가 됐다.

되돌리는 쪽은 더 느리다. 태그를 떼도 head의 시계열은 다음 블록 컴팩션까지, 기본 설정으로 1~3시간 메모리에 남는다. sample_limit은 Prometheus를 지키지만 넘치는 순간 그 타깃의 지표를 전부 버리고 up을 0으로 만든다. 카디널리티는 넣기 전에 막아야 하는 숫자다.
