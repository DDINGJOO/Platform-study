이번 실습에서는 StatsD 줄을 직접 수백만 개 보내서 받는 쪽 카운터가 보낸 수보다 적어지는 지점을 찾고, 그 차이가 어디에 기록되는지 확인합니다. 3편은 "통계는 대량이라 몇 개 유실돼도 경향은 그대로"라고 했는데, 그 말이 어디까지 맞는지도 숫자로 봤어요.

🧭 이 글에서 확인할 것
• UDP로 보낸 줄은 어디서 버려지고, 그 흔적은 어디에 남는가?
• 받는 프로세스가 잠깐 멈추면 몇 개까지 버티는가?

• 받는 쪽이 바쁘면 "경향"은 정말 그대로인가?
• 유닉스 도메인 소켓으로 바꾸면 무엇이 달라지는가?

1. 실습 환경: 보내는 쪽이 직접 센다

보내는 쪽은 Python 스크립트예요. lab.sent:1|c 한 줄(12바이트)을 UDP 패킷 하나에 담아 정해진 속도로 보내고, 보낸 개수를 스스로 셉니다. 받는 쪽은 Prometheus 프로젝트의 statsd_exporter예요. 받은 줄을 더해 lab_sent라는 카운터로 만들어 두고, Prometheus가 그걸 긁어 갑니다. 보낸 수와 lab_sent의 차이가 사라진 숫자예요.

📖 용어: statsd_exporter
StatsD 줄을 UDP(또는 TCP, 유닉스 소켓)로 받아 Prometheus 지표로 바꿔 내보내는 프로그램입니다. 원조 StatsD 데몬은 집계한 값을 Graphite로 보냈는데, statsd_exporter는 같은 줄을 받아 Prometheus가 긁어 갈 수 있는 형태로 내놓아요.

차이가 생기는 곳은 두 군데입니다. 하나는 커널이에요. 패킷은 먼저 받는 소켓의 수신 버퍼에 쌓이고, 프로그램이 꺼내 가기 전에 버퍼가 차면 커널이 버립니다. 다른 하나는 statsd_exporter 안쪽이에요. 소스(pkg/listener/listener.go)를 보면 소켓에서 읽은 패킷을 내부 큐(기본 10,000개)에 넣는데, 큐가 차 있으면 버리고 statsd_exporter_udp_packet_drops_total을 올립니다.

📖 용어: 소켓 수신 버퍼 (SO_RCVBUF)
커널이 소켓마다 잡아 두는, 아직 프로그램이 읽지 않은 데이터를 담는 공간입니다. 기본 크기는 net.core.rmem_default, 프로그램이 요청할 수 있는 최댓값은 net.core.rmem_max가 정해요. 이 실습의 Docker Desktop에서는 둘 다 212,992바이트(208KB)였습니다.

커널이 버린 수는 /proc/net/snmp의 Udp: RcvbufErrors에 쌓입니다. 이 숫자는 네트워크 네임스페이스마다 따로라서, statsd_exporter 컨테이너 안에서 봐야 해요. 그래서 node_exporter를 statsd 컨테이너와 같은 네임스페이스에 붙여(network_mode: service:statsd) 이 값을 Prometheus로 가져왔습니다.

📖 용어: 네트워크 네임스페이스 (network namespace)
리눅스가 컨테이너마다 네트워크 장치, 소켓, 통계를 따로 보이게 나누는 단위입니다. 호스트에서 netstat -su를 쳐도 컨테이너 안에서 버려진 패킷은 보이지 않아요.
그림 1. 줄 하나가 카운터가 되기까지 버려질 수 있는 곳은 두 군데다

쓴 버전과 돌리는 법입니다.

statsd_exporter 0.31.0 node_exporter 1.12.1 (netstat 수집기만 켬) Prometheus 3.15.0 Grafana 13.2.3 sender Python 3.13 (alpine 이미지) 실행 환경 Docker Desktop (리눅스 커널 6.12, linuxkit), Apple M5 Pro

실습 코드는 GitHub 저장소의 labs/observability/metrics-03-statsd에 있어요. run.sh는 statsd를 새로 띄워 카운터를 0으로 만든 뒤 보내고, count.sh로 받은 쪽 숫자를 한 줄로 찍습니다. 조건은 환경변수로 바꿔요.

git clone https://github.com/DDINGJOO/Platform-study.git cd Platform-study/labs/observability/metrics-03-statsd docker compose up -d RATE=1000 SECONDS_TO_SEND=30 ./run.sh # 초당 1,000개를 30초 RATE=0 SECONDS_TO_SEND=10 ./run.sh # 최대 속도로 10초 # Grafana: http://localhost:21300 → 대시보드 "StatsD UDP 유실"

2. 천천히 보내면 하나도 안 잃고, 빨리 보내면 4%를 잃는다

먼저 초당 1,000개를 목표로 30초 보냈습니다(실제로는 초당 912개가 나갔어요). 보낸 27,360개가 lab_sent에 그대로 27,360으로 찍혔어요. 커널 카운터도 0이었습니다.

다음은 보낼 수 있는 만큼 빨리 10초입니다. 같은 조건을 세 번 돌렸어요.

RATE=0 SECONDS_TO_SEND=10 ./run.sh sent=4772000 errors=0 seconds=10.0 rate=477,105/s udp_packets(exporter)=4589347 queue_drops(exporter)=0 lab_sent=4589347 RcvbufErrors=182653 보낸 수 받은 수(lab_sent) 커널이 버린 수 유실률 1회차 4,772,000 4,589,347 182,653 3.8% 2회차 4,814,000 4,620,289 193,711 4.0% 3회차 4,627,000 4,442,879 184,121 4.0%

세 가지가 눈에 띕니다. 첫째, 보낸 쪽 오류(errors)는 0이에요. sendto()는 패킷을 자기 쪽 네트워크 스택에 넘기면 성공을 돌려주니, 보낸 쪽은 18만 개가 사라진 걸 알 방법이 없습니다. 둘째, statsd_exporter 내부 큐 유실은 0이었어요. 셋째, 숫자가 정확히 맞아요. 1회차의 4,589,347 + 182,653은 4,772,000입니다. 사라진 줄은 하나도 빠짐없이 받는 쪽 커널의 RcvbufErrors에 기록됐습니다.

📖 용어: RcvbufErrors
수신 버퍼가 가득 차서 커널이 소켓에 넣지 못하고 버린 UDP 데이터그램 수입니다. /proc/net/snmp의 Udp: 줄에 있고, netstat -su에서는 "receive buffer errors"로 보여요. 리눅스 6.12 소스(net/ipv4/udp.c)에는 "ENOMEM 오류는 두 번 집계된다"는 주석이 있어서 InErrors도 같이 올라갑니다.

같은 숫자를 세 군데서 볼 수 있어요. 명령은 statsd 컨테이너의 네트워크 네임스페이스 안에서 실행해야 합니다.

docker compose exec statsd cat /proc/net/snmp | grep '^Udp:' Udp: InDatagrams NoPorts InErrors OutDatagrams RcvbufErrors SndbufErrors ... Udp: 11758318 0 16715482 0 16715482 0 ... # statsd 의 네트워크 네임스페이스에 붙인 임시 컨테이너에서(호스트에서 치면 안 보인다) docker run --rm --network container:$(docker compose ps -q statsd) alpine:3.20 \ sh -c "apk add -q iproute2 net-tools; netstat -su; ss -uamn sport = :9125" netstat -su → 16715482 receive buffer errors ss -uamn sport = :9125 → skmem:(r0,rb212992,...,d16715482) ← d 가 이 소켓이 버린 수

(이 출력은 4절의 단계별 시험이 끝난 뒤에 찍은 것이라 숫자가 커요. Grafana의 커널 수치는 compose의 kernel 서비스, 곧 statsd와 네트워크 네임스페이스를 같이 쓰는 node_exporter가 같은 /proc/net/snmp를 읽어 보낸 거예요.)

3. 수신 버퍼에는 238개가 들어간다

208KB면 12바이트짜리 줄이 1만 개 넘게 들어갈 것 같지만 그렇지 않았어요. 받는 프로세스를 docker pause로 멈춰 두고 초당 1,000개를 5초 보내 봤습니다(pause-test.sh).

./pause-test.sh sent=4570 errors=0 skmem:(r213248,rb212992,...,d4332) ← 버퍼에 213,248바이트가 찼고 4,332개를 버렸다 udp_packets(exporter)=238 lab_sent=238 ← 프로세스를 다시 깨우자 238개만 읽혔다

버퍼에 들어간 건 238개였어요. 213,248 ÷ 238이면 패킷 하나에 약 896바이트입니다. 커널은 버퍼를 데이터 길이가 아니라 패킷을 담는 구조체까지 포함한 실제 메모리 크기로 세기 때문이에요. 작은 줄을 많이 보내는 StatsD에서는 이 차이가 커집니다. 초당 1,000개를 받는 수집기라면 0.24초만 멈춰도 버리기 시작해요. GC 일시 정지, CPU 제한, 노드의 순간 부하 모두 이 정도 길이가 됩니다.

그럼 버퍼를 키우면 되겠죠. statsd_exporter에는 --statsd.read-buffer 옵션이 있습니다. 8MB를 요청하고 소켓을 보니 이렇게 나왔어요.

READ_BUFFER=8388608 docker compose up -d --force-recreate statsd kernel ss -uamn sport = :9125 → skmem:(r0,rb425984,...) ← 8MB 가 아니라 416KB READ_BUFFER=4096 ... → skmem:(r0,rb8192,...)

8MB를 요청했는데 416KB가 됐어요. statsd_exporter 로그에는 경고 한 줄 없었습니다. 리눅스 socket(7) 매뉴얼에 이유가 있어요. 커널은 요청값을 먼저 rmem_max로 자르고, 그 값을 두 배로 잡아요(관리용 공간 몫). 그래서 212,992의 두 배인 425,984에서 멈춰요. 4,096을 요청하면 두 배인 8,192가 됩니다. statsd_exporter의 옵션 설명에도 "net.core.rmem_max를 이 값보다 크게 설정하라"고 적혀 있어요.

세 가지 버퍼로 최대 속도 10초를 세 번씩 돌린 결과입니다.

RATE=0 SECONDS_TO_SEND=10 READ_BUFFER=4096 ./run.sh RATE=0 SECONDS_TO_SEND=10 ./run.sh RATE=0 SECONDS_TO_SEND=10 READ_BUFFER=8388608 ./run.sh
실제 버퍼 1회차 2회차 3회차 8KB 13.6% 22.0% 14.3% ← --statsd.read-buffer=4096 208KB 3.8% 4.0% 4.0% ← 기본값 416KB 1.2% 1.3% 1.1% ← 8MB 를 요청했지만 rmem_max 에 걸림 (초당 46~48만 개를 10초, statsd CPU 1개)
⚠️ 주의: rmem_max는 컨테이너에서 못 바꾼다
net.core.rmem_max는 네트워크 네임스페이스마다 따로 있는 값이 아니라 호스트(노드) 전체 값이에요. 컨테이너에 --sysctl net.core.rmem_max=16777216을 주면 이번 환경에서는 open sysctl net.core.rmem_max file: reopen fd 8: permission denied로 컨테이너가 아예 뜨지 않았습니다. 버퍼를 키우려면 노드의 sysctl부터 바꿔야 하고, 그러지 않으면 애플리케이션 옵션은 조용히 상한에 걸려요.

4. 받는 쪽이 바쁘면 경향도 사라진다

3편은 "통계는 어차피 대량이라 몇 개 유실돼도 경향은 그대로"라고 했어요. 무작위로 몇 개씩 빠진다면 맞는 말입니다. 그런데 버퍼 유실은 무작위가 아니에요. 받는 쪽이 따라가지 못할 때 몰려서 일어납니다. 이걸 보려고 statsd 컨테이너의 CPU를 0.25개로 묶고(cpus: 0.25), 보내는 속도를 30초마다 올렸어요(ramp.sh).

./ramp.sh # STATSD_CPUS=0.25, STEPS=20000:30,50000:30,100000:30,200000:30,0:30 # 실습을 마칠 때(프로필로 띄운 sender 까지 지운다) docker compose --profile send down -v
그림 2. 보낸 쪽이 세 배 넘게 늘어도 받은 쪽 선은 거의 그대로였다

단계별로 Prometheus가 5초마다 긁은 값을 나눠 보면 이렇습니다. 단계 경계는 긁은 시각이라, 마지막 단계는 보내기가 끝난 뒤의 커널 카운터를 덜 담았어요. 전체 합은 맨 아래 count.sh 값이 정확합니다.

보낸 속도(실제) 30초간 보낸 수 받은 수 버린 수 유실률 18,221/s 547,200 541,000 0 0.0% 45,517/s 1,366,000 1,353,943 2,706 0.2% 91,063/s 2,733,000 2,491,465 205,699 7.5% 181,964/s 5,458,986 3,286,120 1,966,113 36.0% 612,299/s 18,368,014 4,044,835 13,052,625 71.1% count.sh 최종 28,473,800 11,758,318 16,715,482 58.7% (11,758,318 + 16,715,482 = 28,473,800, 보낸 수와 정확히 같다)

받은 수를 30초로 나누면 초당 1.8만, 4.5만, 8.3만, 11만, 13.5만 개예요. 보낸 쪽이 18만에서 61만으로 3.4배가 되는 동안 받은 쪽은 11만에서 13.5만으로 23% 늘었습니다. 이 카운터로 그린 "초당 주문 수" 그래프였다면 트래픽이 세 배가 된 순간을 거의 평평한 선으로 보여 줬을 거예요. 유실은 경향을 보존하지 않고, 받는 쪽 처리량에서 위를 잘라 냅니다. 3편의 말은 받는 쪽에 여유가 있을 때에만 맞아요.

평균으로는 여유가 있어 보이는 초당 4.5만 개 단계에서도 2,706개가 버려졌어요. 받는 쪽은 초당 13만 개까지 처리하는데 왜 그럴까요? 같은 조건(초당 5만 개 목표, CPU 0.25개)을 따로 돌린 뒤 statsd 컨테이너의 cpu.stat을 보니, 100ms 주기 340번 중 14번 CPU 할당을 다 써서 멈췄고(nr_throttled 14), 멈춘 시간이 합쳐서 60ms였습니다. 그 실행에서 버려진 건 3,502개였어요. 초당 4.5만 개가 들어오는 중에 몇 ms씩 멈추면 238개짜리 버퍼는 금방 찹니다. 평균 처리량이 아니라 멈춤의 길이가 유실을 정하는 것으로 보여요.

📖 용어: CPU 스로틀링 (CPU throttling)
컨테이너에 CPU 한도(cpus: 0.25 이면 100ms마다 25ms)를 걸면, 그 주기 안에 할당을 다 쓴 프로세스를 다음 주기까지 멈추는 동작입니다. 평균 사용률이 낮아도 순간적으로 몰리면 멈춰요.

5. 같은 호스트라면 유닉스 도메인 소켓이 알려 준다

3편은 데이터독 Agent가 컨테이너 환경에서는 UDP 대신 유닉스 도메인 소켓(UDS)을 권한다고 했어요. 데이터독 문서는 UDS가 "네트워크 스택을 건너뛰어 트래픽이 많을 때 성능이 크게 좋아지고", UDP와 달리 "버려진 패킷과 연결 오류를 알 수 있다"고 적고 있습니다. statsd_exporter도 --statsd.listen-unixgram으로 유닉스 데이터그램 소켓을 받을 수 있어서, 같은 조건(statsd CPU 0.25개, 최대 속도 10초)으로 세 가지를 비교했어요.

RATE=0 SECONDS_TO_SEND=10 STATSD_CPUS=0.25 ./run.sh UNIX_SOCKET=/sock/statsd.sock RATE=0 SECONDS_TO_SEND=10 STATSD_CPUS=0.25 ./run.sh UNIX_SOCKET=/sock/statsd.sock NONBLOCK=1 RATE=0 SECONDS_TO_SEND=10 STATSD_CPUS=0.25 ./run.sh 보낸 속도 받은 수 잃은 수 보낸 쪽이 안 것 UDP 593,858/s 1,386,641 4,552,359 없음 (errors=0) UDS, 블로킹 200,313/s 2,006,000 0 없음 (대신 느려짐) UDS, 논블로킹 220,337/s 2,203,530 11,787,470* 전부 (EAGAIN 으로 셈) * 논블로킹은 버퍼가 찼을 때 보내기를 시도했다가 거절당한 횟수
그림 3. 받는 쪽이 못 따라갈 때 세 방식이 고르는 것

UDS 블로킹에서는 아무것도 잃지 않았지만, 보내는 속도가 초당 59만에서 20만으로 떨어졌어요. 받는 쪽 버퍼가 차면 sendto()가 자리가 날 때까지 기다리기 때문입니다(정확히는 받는 소켓의 큐 길이와 보내는 쪽 송신 버퍼가 조건인데, 여기서는 줄여 말했어요). 실제 앱이라면 요청을 처리하던 스레드가 지표 하나 때문에 멈춘다는 뜻이에요. 3편이 말한 "모니터링은 서비스를 해치면 안 된다"는 원칙과 정면으로 부딪혀요. 3편의 "'앱을 블로킹하지 않는다'는 원칙 자체는 그대로 남았다"는 말은 UDS를 논블로킹으로 쓸 때만 맞습니다. 데이터독 문서가 UDS의 장점을 말하면서 "논블로킹으로 쓸 수 있다"는 조건을 같이 붙이는 이유예요. 논블로킹에서는 버퍼가 차는 순간 오류가 돌아오고, 앱이 그 수를 셀 수 있습니다. 버리는 건 UDP와 같지만 버렸다는 사실을 보내는 쪽이 압니다.

하나 더 볼 점은 받은 수예요. 같은 CPU 0.25개로 UDP는 10초에 139만 개, UDS는 200만~220만 개를 받았습니다. 네트워크 스택을 거치지 않는 만큼 같은 CPU로 더 많이 처리했어요.

💡 실무에서는: StatsD 계열 수집기를 운영할 때
• 수집기 노드의 /proc/net/snmp RcvbufErrors(또는 node_exporter의 node_netstat_Udp_RcvbufErrors)에 알람을 걸어요. 앱 쪽에서는 유실을 볼 방법이 없어요
• 수신 버퍼 옵션을 바꿨으면 ss -uamn의 rb 값으로 실제 크기를 확인해요. rmem_max에 걸려 조용히 줄어 있을 수 있어요
• 수집기 컨테이너에 CPU 한도를 빡빡하게 걸지 않아요. 평균이 낮아도 스로틀링으로 멈추는 순간에 버려져요
• 같은 노드 안이라면 UDS를 논블로킹으로 쓰고, 클라이언트가 세는 전송 실패 수를 지표로 내보내요
✍️ 오늘의 요약
UDP StatsD는 받는 쪽이 따라가지 못하는 만큼 정확히 버렸고, 그 수는 받는 쪽 커널의 RcvbufErrors에만 남았다. 보낸 쪽 오류는 수천만 개를 보내는 동안 한 번도 0을 벗어나지 않았다. 기본 208KB 버퍼에 작은 줄은 238개만 들어갔고, 버퍼를 키우는 옵션은 노드의 rmem_max에 걸려 조용히 줄었다.

유실은 무작위가 아니라 받는 쪽 처리량에서 위를 잘라 내는 모양이라, 트래픽이 세 배가 돼도 그래프는 23%만 움직였다. 유닉스 도메인 소켓은 같은 상황에서 보내는 쪽에 오류로 알려 준다. 쏘고 잊는 대가는 잃는 것보다 잃은 줄 모르는 데 있다.
