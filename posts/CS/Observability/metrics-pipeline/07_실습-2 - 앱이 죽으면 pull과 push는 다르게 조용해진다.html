주문 서비스가 멈췄습니다. 대시보드의 주문 그래프는 마지막 값에서 평평하게 이어지고, 알람은 아직 울리지 않아요. 5분쯤 지나서야 그래프가 끊깁니다. 그 5분 동안 서비스가 정말 멈춘 건지, 주문이 없었던 건지, 지표 파이프라인이 고장 난 건지 알 수 없어요.

2편은 pull 방식이 "침묵을 정보로" 만든다고 했습니다. 긁으러 갔다가 실패하면 up이 0이 되니까요. push는 데이터가 오지 않아도 그게 무슨 뜻인지 모릅니다. 이번 실습에서는 kind 클러스터에 같은 앱을 두 번 띄워, 하나는 Prometheus가 긁게 하고 하나는 OTLP로 Collector에 밀게 했어요. 그리고 앱을 멈추고, 없애고, 재배포하면서 각각이 몇 초 만에 알아차리는지를 쟀습니다.

🧭 이 글에서 확인할 것
• 앱 프로세스가 멈추면 pull과 push는 각각 몇 초 만에 알아차리는가?
• 파드가 아예 사라지면 up == 0 알람은 울리는가?
• push로 받은 시계열은 왜 끊긴 뒤에도 5분 동안 쿼리에 나오는가?
• Collector를 한 번 더 거치면 무엇이 달라지는가?

1. 실습 환경: 같은 앱, 두 가지 경로

앱은 0.1초마다 주문 카운터 shop.orders를 1씩 올리는 스프링 부트 앱이에요. 같은 이미지를 두 Deployment로 띄웠습니다.

pull-app은 /actuator/prometheus를 열어 둡니다. Prometheus는 쿠버네티스 API에서 파드 목록을 받아(kubernetes_sd_configs, role: pod) prometheus.io/scrape: "true" 애노테이션이 붙은 파드를 10초마다 긁어요. push-app은 Micrometer OTLP 레지스트리로 10초마다 OTel Collector에 지표를 밉니다. Collector는 받은 지표를 두 곳으로 보내요. 하나는 Prometheus의 OTLP 수신 엔드포인트로 그대로 밀고(경로 1), 다른 하나는 Collector 자신의 :8889에 Prometheus 형식으로 걸어 두어 Prometheus가 긁게 합니다(경로 2). 현장에서 둘 다 흔히 쓰는 구성이에요.

그림 1. 같은 앱 하나를 긁기와 밀기로 나눠 띄웠다
📖 용어: 서비스 디스커버리 (service discovery)
Prometheus가 긁을 대상 목록을 설정 파일 대신 외부에서 받아 오는 기능입니다. 쿠버네티스에서는 API 서버를 지켜보다가 파드가 생기면 대상에 넣고, 사라지면 뺍니다. 2편에서 pull이 쿠버네티스에서 이긴 이유로 든 바로 그 기능이에요.
📖 용어: OTLP (OpenTelemetry Protocol)
OpenTelemetry가 정한 텔레메트리 전송 형식입니다. 앱이나 Collector가 이 형식으로 지표를 밀어 보내고, Prometheus 3는 --web.enable-otlp-receiver를 켜면 /api/v1/otlp/v1/metrics에서 직접 받아요.

알람은 Prometheus 규칙 네 개로 걸었어요. 몇 초 만에 울리는지 보려고 for는 두지 않았습니다.

PullTargetDown up{job="pull-app"} == 0 긁으러 갔는데 실패했다 PullTargetAbsent absent(up{job="pull-app"}) 긁을 대상 자체가 없다 PushSeriesAbsent absent(shop_orders_total{job="push-app"}) 밀어 넣던 시계열이 쿼리에서 사라졌다 PushNoSampleFor30s absent_over_time(shop_orders_total{job="push-app"}[30s]) 최근 30초 동안 새 샘플이 없다
📖 용어: absent()와 absent_over_time()
absent(식)은 그 식이 지금 아무 시계열도 돌려주지 않을 때 1을 돌려줍니다. "있어야 할 것이 없다"를 알람으로 만드는 함수예요. absent_over_time(식[30s])는 지난 30초 안에 샘플이 하나도 없을 때 1을 돌려줘요.

버전과 돌리는 법입니다. kind 클러스터는 이 실습 전용으로 만들고 끝나면 지워요.

kind 0.33.0 Spring Boot 4.1.1 (Micrometer 1.17.1) Prometheus 3.15.0 (--web.enable-otlp-receiver) OTel Collector 0.162.0 (contrib) Grafana 13.2.3 실행 환경 Docker Desktop, Apple M5 Pro git clone https://github.com/DDINGJOO/Platform-study.git cd Platform-study/labs/observability/metrics-02-pull-push ./up.sh # kind 클러스터 생성, 앱 이미지 빌드·적재, 배포 ./freeze.sh # 시나리오 1: 두 앱 프로세스를 400초 멈춘다. 시작·끝 유닉스초를 찍는다 python3 timeline.py <시작-20> <끝+60> # 무엇이 언제 바뀌었는지 ./scale-zero.sh # 시나리오 2: 두 Deployment 를 400초 동안 0개로 python3 timeline.py <시작-20> <끝+60> ./down.sh # 클러스터 삭제 # Prometheus http://localhost:21290, Grafana http://localhost:21200

실습 코드는 GitHub 저장소의 labs/observability/metrics-02-pull-push에 있습니다.

⚠️ 주의: 스프링 부트 4에서 OTLP 레지스트리만 넣으면 아무것도 안 나간다
처음에는 micrometer-registry-otlp만 의존성에 넣었어요. 앱은 잘 떴고 오류도 경고도 없었는데, Collector에는 한 줄도 오지 않았습니다. 스프링 부트 4.1.1의 OtlpMetricsExportAutoConfiguration은 @ConditionalOnClass({ OtlpMeterRegistry.class, OpenTelemetryProperties.class })로 걸려 있고, OpenTelemetryProperties는 spring-boot-opentelemetry 모듈에 있어요. 이 모듈을 추가하자 지표가 나갔습니다. push는 "안 나가고 있다"는 사실도 조용하다는 걸 시작부터 겪은 셈이에요.

2. 시나리오 1: 프로세스가 멈췄다

첫 번째는 앱이 응답하지 않는 상황입니다. kind 노드 안에서 두 앱의 자바 프로세스에 SIGSTOP을 보내 400초 동안 멈췄어요. 파드는 Running 그대로이고, 프로브를 두지 않았으니 쿠버네티스도 아무것도 하지 않습니다.

./freeze.sh # 18:24:42 에 SIGSTOP, 18:31:22 에 SIGCONT python3 timeline.py 1791624260 1791624742 (멈춘 시각 기준으로 다시 정리) +7초 pull up 1 → 0, pull 시계열이 쿼리에서 사라짐 +10초 ALERT PullTargetDown 발화 +25초 ALERT PushNoSampleFor30s 발화 +292초 push 시계열(OTLP)이 쿼리에서 사라짐 +295초 ALERT PushSeriesAbsent 발화 +296초 push 시계열(Collector :8889)이 사라짐 (그때까지 값 787 그대로)
그림 2. pull은 10초 만에 울렸고, push의 absent()는 5분을 기다렸다

pull 쪽은 2편이 말한 그대로예요. 멈춘 뒤 첫 스크레이프(타임아웃 5초)가 실패하자 up이 0이 됐고, 규칙 평가 한 번 뒤에 알람이 울렸습니다. 그리고 shop_orders_total{job="pull-app"}은 같은 순간 쿼리 결과에서 빠졌어요. 스크레이프에 실패하면 Prometheus가 직전까지 받던 시계열에 "끝났다"는 표시(stale 표시)를 쓰기 때문입니다.

📖 용어: stale 표시와 lookback
Prometheus는 쿼리 시각마다 최근 5분(lookback) 안의 마지막 샘플을 그 시계열의 값으로 씁니다. 다만 스크레이프나 규칙 평가가 "이 시계열은 끝났다"는 특수 값(stale 표시)을 써 두면 그 뒤로는 값을 돌려주지 않아요. 문서는 이 표시를 쓰는 주체를 스크레이프와 규칙 평가로 적고 있습니다.

push 쪽 OTLP 시계열에는 그 표시를 써 줄 주체가 없어요. 앱이 마지막으로 민 샘플이 18:24:34였는데, 쿼리는 그 값을 5분 뒤인 18:29:34까지 돌려줬습니다. 오른쪽 아래 패널의 초록 선이 그 "샘플 나이"예요. 0에서 5분까지 늘어나다가 끊깁니다. 그래서 absent() 알람은 멈춘 지 295초 뒤에야 울렸어요. push 시계열은 끊긴 뒤에도 lookback만큼 쿼리에 계속 나옵니다. 반면 absent_over_time(...[30s])는 25초 만에 울렸어요. "지금 값이 있나"가 아니라 "최근에 새 샘플이 왔나"를 물었기 때문입니다.

Collector를 한 번 더 거치면 값이 멈춘 채 살아 있다

경로 2는 더 헷갈렸어요. Prometheus가 긁는 대상은 Collector라서, Collector가 멀쩡하면 up{job="otel-collector"}은 계속 1입니다. 그리고 Collector는 마지막으로 받은 값 787을 계속 내놓아요. Prometheus는 그 값을 10초마다 새 샘플로 받아 적으니 샘플 나이는 늘 10초 이내였습니다(오른쪽 아래 패널의 노란 선). 대시보드만 보면 "값이 들어오는데 안 늘 뿐"이에요. 이 값은 296초 뒤에야 사라졌습니다. Collector의 prometheus exporter 문서가 말하는 metric_expiration 기본값 5분이 지나서 Collector가 내놓기를 멈춘 거예요.

2편은 Pushgateway의 함정으로 "한 번 밀어 넣은 시계열을 스스로 잊지 않는다"를 들었어요. Collector의 prometheus exporter는 5분 뒤에 잊긴 하지만, 그 5분 동안은 같은 함정이 그대로 나타났습니다. 끊긴 앱의 마지막 값이 새 샘플로 계속 저장돼요.

3. 시나리오 2: 파드가 사라졌다

두 번째는 앱이 아예 없어지는 상황입니다. 두 Deployment를 replicas=0으로 줄였다가 400초 뒤에 1로 되돌렸어요.

./scale-zero.sh # 18:16:32 에 0 으로, 18:23:12 에 1 로 up{job="pull-app"} 원본 샘플: 18:16:07 1 18:16:17 1 18:16:27 1 (그다음은 없음) +15초 ALERT PullTargetAbsent 발화 +35초 ALERT PushNoSampleFor30s 발화 +301초 push 시계열(OTLP)이 쿼리에서 사라짐 +305초 ALERT PushSeriesAbsent 발화 PullTargetDown 은 한 번도 울리지 않았다
그림 3. 파드가 사라지자 up은 0이 되지 않고 그냥 없어졌다

이번에는 up이 0이 된 적이 없어요. 1, 1, 1 다음에 아무것도 없습니다. 파드가 지워지자 서비스 디스커버리 목록에서 바로 빠졌고, 긁으러 갈 대상이 없으니 실패할 일도 없었던 거예요. Prometheus 문서도 "대상이 제거되면 이전 시계열은 곧 stale로 표시된다"고만 적고 있습니다. 2편은 "제거되기 전에 실패한 순찰은 up=0으로 남는다"고 했는데, 이번 실행에서는 그 실패한 순찰이 한 번도 없었어요. Prometheus는 대상이 빠지면 두 주기 남짓 기다렸다가 up을 포함한 그 대상의 시계열에 stale 표시를 써요(scrape.go의 endOfRunStaleness). 이번 앱처럼 빨리 종료되면 up == 0만 걸어 두어서는 알람이 울리지 않습니다. 종료가 느려 Terminating 동안 목록에 남아 있으면 up=0이 찍힐 수 있는데, 아래 재배포에서 한 번 그랬어요. 울린 건 absent(up{job="pull-app"})였어요.

push 쪽은 시나리오 1과 같았고, 하나가 달랐어요. 파드가 종료 신호를 받으면서 Micrometer가 마지막 값을 한 번 더 밀었습니다. 10초 주기 중간인 18:16:32에 값 5052가 들어왔어요. 그래서 마지막 샘플이 조금 늦게 찍혔고, 사라지기까지는 그 시각부터 다시 5분이었습니다.

재배포하면 어떻게 보이나

두 앱을 재배포해 봤어요.

kubectl --context kind-obs-lab-metrics-02 -n obs rollout restart deploy/pull-app deploy/push-app

pull 쪽은 실행마다 결과가 달랐습니다. 한 번은 옛 pull 파드에 up=0 샘플이 하나(17:20:10) 찍힌 뒤 대상에서 빠졌고, 다른 한 번(18:34:23)은 0 없이 빠졌어요. 종료 중인 파드를 스크레이프가 마침 건드렸는지에 따라 갈리는 것으로 보입니다. for 없는 up == 0 알람이라면 재배포 때 가끔 헛알람이 울린다는 뜻이에요.

push 쪽은 매번 같았어요. 옛 인스턴스의 시계열이 마지막 값(6697)을 단 채 18:39:24까지 5분 더 남아서, 새 인스턴스와 4분 52초 동안 겹쳤습니다. push-app은 service.instance.id를 파드 이름으로 보내서 옛 파드와 새 파드가 다른 인스턴스로 잡히고, 이 동안 count(shop_orders_total{job="push-app"})은 2였어요. 인스턴스를 합쳐 값을 더하는 쿼리라면 그동안 옛 값이 같이 더해집니다.

그림 4. 같은 장애, 같은 Prometheus인데 알아차리는 시간은 식이 정했다
💡 실무에서는: 조용해진 대상을 잡는 규칙
• pull 대상에는 up == 0과 함께 absent(up{job="..."})를 걸어요. 앞의 것은 "멈춤", 뒤의 것은 "사라짐"을 잡아요. 재배포 헛알람을 피하려면 up == 0에 for: 1m 정도를 줘요
• push 시계열에는 absent() 대신 absent_over_time(지표[주기의 2~3배])를 써요. absent()는 lookback(기본 5분)이 지나야 울려요
• Collector의 prometheus exporter를 거친다면 up은 앱이 아니라 Collector의 상태예요. 앱의 생사는 앱이 보낸 지표의 갱신 여부로 따로 봐요
• push 인스턴스를 합산하는 쿼리는 재배포 직후 몇 분 동안 옛 인스턴스가 함께 더해질 수 있어요
✍️ 오늘의 요약
앱이 멈추자 pull은 10초 만에 up=0으로 알렸고, push 시계열은 마지막 값을 단 채 5분 동안 쿼리에 계속 나왔다. 스크레이프 실패는 stale 표시를 남기지만, 밀어 넣은 샘플에는 그 표시를 써 줄 주체가 없어서 lookback이 끝날 때까지 남는다. Collector를 한 번 더 거치면 끊긴 앱의 마지막 값이 5분 동안 새 샘플로 저장됐다.

pull도 만능은 아니었다. 이번처럼 빨리 종료되는 파드는 서비스 디스커버리 목록에서 바로 빠져 up이 0이 아니라 없음이 됐고, up == 0 알람은 울리지 않았다. 침묵을 정보로 바꾸는 건 수집 방식이 아니라, 그 침묵을 묻는 식이다.
