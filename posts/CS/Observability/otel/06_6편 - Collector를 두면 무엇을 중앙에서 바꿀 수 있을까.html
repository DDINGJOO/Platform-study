4편. 샘플링하면 무엇이 남고 무엇이 빠질까
5편. 메트릭은 어디서 집계되고 누가 가져갈까
6편. Collector를 두면 무엇을 중앙에서 바꿀 수 있을까 ← 지금 이 글

여러 서비스가 같은 관측 백엔드로 데이터를 보내다가, 목적지를 추가해야 하는 상황을 가정해 봐요. SDK마다 exporter와 인증 정보를 바꾸는 방법이 있어요. 애플리케이션은 공통 수집 주소로 계속 보내고, 그 뒤의 전달 설정만 바꾸는 방법도 있어요. 두 번째 구성이 Collector를 생각하게 되는 출발점이에요.

그렇다고 중간 프로세스를 하나 추가하면 애플리케이션의 관측 문제가 모두 분리되는 것은 아니에요. Collector가 받기 전에 버려진 스팬은 되살릴 수 없고, 잘못된 계측의 의미도 임의로 알아내지 못해요. 대신 이미 만들어진 데이터를 어디로 보내고 어떻게 처리할지 앱 밖에서 관리할 수 있어요. 무엇을 중앙에서 바꿀 수 있게 되고, 그만큼 누가 무엇을 운영해야 할까요?

Collector v0.163.0의 소스에서 설정이 실행 경로로 연결되는 과정을 따라가고, 직접 전송·Prometheus Agent·Alloy와 책임이 어떻게 다른지 비교해 볼게요.

1. 전송 정책을 옮겨도 계측의 책임은 남아요

직접 전송에서는 앱의 exporter가 백엔드와 통신해요. Collector를 경유하면 앱의 전송 상대를 Collector로 바꾸고, Collector의 exporter가 다음 목적지와 통신하게 해요. 공식 소개도 개발·소규모 환경의 직접 전송을 유효한 출발점으로 설명하면서, Collector에서 재시도·배치·암호화·민감정보 필터링 같은 처리를 맡길 수 있다고 안내해요. Collector는 사용 전제 조건이라기보다 운영 경계를 고르는 선택이에요. Collector를 사용하는 경우에서 이 구분을 확인할 수 있어요.

공통 목적지가 있다는 이점은 변경 범위에서 드러나요. 백엔드의 주소나 전송 인증을 바꿀 때 앱마다 새 설정을 배포할 필요를 줄일 수 있어요. 두 백엔드로 동시에 보내며 결과를 비교하거나, 특정 속성을 전달 전에 제거하는 정책도 수집 계층에서 관리할 수 있어요. 다만 새로운 목적지가 요구하는 데이터가 원래 계측에 없었다면 전송 설정만으로 해결되지 않아요. 목적지 교체가 대시보드·질의·데이터 의미까지 그대로 옮겨 준다는 뜻도 아니에요.

예를 들어 앱의 head sampling에서 제외된 요청, SDK의 꽉 찬 큐에서 거절된 스팬, 기록되지 않은 업무 속성은 Collector에 도착하지 않아요. Collector의 필터를 풀어도 이미 없는 데이터가 생기지는 않아요. 저는 이 경계를 데이터를 만드는 정책과, 받은 데이터를 처리하는 정책의 분리로 이해했어요. 이는 구현을 읽은 해석이며, Collector의 모든 기능이 무상으로 분리된다는 보장은 아니에요.

2. YAML에 정의했다고 실행되지는 않아요

Collector 설정을 처음 읽으면 receivers, processors, exporters가 나란히 보이니 그 자체로 순서가 정해진 것처럼 느껴질 수 있어요. 하지만 위쪽은 사용할 컴포넌트의 설정을 정의하는 곳이에요. 실제 사용 관계는 service.pipelines에서 참조해야 해요. 아래 예제는 이 차이를 설명하기 위한 미실행 구성이고, 수치도 운영 권장값이 아니라 임의의 예시예요.

📖 용어: receiver · processor · exporter
receiver는 데이터를 받아들이거나 가져오고, processor는 받은 데이터를 처리하며, exporter는 다음 대상으로 전달해요. receiver가 항상 수신 서버인 것은 아니에요. Prometheus receiver처럼 대상을 주기적으로 읽는 구성도 있어요.
receivers: otlp: protocols: grpc: endpoint: 127.0.0.1:4317 processors: memory_limiter: check_interval: 1s limit_mib: 128 spike_limit_mib: 32 batch: timeout: 1s exporters: otlp_grpc/backend: endpoint: telemetry-backend.example.com:4317 sending_queue: enabled: true sizer: items queue_size: 20000 retry_on_failure: enabled: true debug/unused: verbosity: basic service: pipelines: traces: receivers: [otlp] processors: [memory_limiter, batch] exporters: [otlp_grpc/backend]

이 구성에서 debug/unused는 정의만 있고 traces 파이프라인에 없으므로 활성화되지 않아요. 반대로 otlp_grpc/backend는 목적지 설정과 참조가 모두 있어요. memory_limiter 다음에 batch를 적은 순서도 의미가 있어요. 예제의 수신 주소는 같은 네트워크 공간의 로컬 클라이언트를 가정해요. 다른 Pod에서 접근하는 gateway 설정으로 그대로 쓸 수 없고, 외부 노출에는 접근 제어·TLS·인증 구성이 별도로 필요해요.

otlp_grpc/backend의 앞부분은 컴포넌트 종류이고 뒤쪽은 구별하기 위한 이름이에요. backend라는 플러그인을 내려받는 지시가 아니에요. 공식 설정 문서는 이 식별자를 type[/name]으로 설명해요. 해당 종류의 컴포넌트가 선택한 실행 파일에 들어 있어야 하고, 다루려는 신호를 지원하는지도 확인해야 해요. Collector 구성 문서에 정의와 활성화의 차이가 나와 있어요.

📖 용어: 배포판(distribution)
Collector의 코어와 선택한 컴포넌트들을 묶은 실행 가능한 구성이에요. 같은 Collector 계열이라도 포함된 receiver·processor·exporter와 지원 신호, 안정성 수준이 다를 수 있어요. YAML에 이름을 적는 것만으로 없는 구현이 추가되지는 않아요.
소스 캡처 1. receiver·processor·exporter의 참조 목록을 검사해요. 원문 50~66행

PipelineConfig 원문에는 세 종류의 참조 목록이 있어요. 이어지는 검사는 receiver와 exporter가 각각 비었는지 확인해요. 이 부분에서 processor는 필수가 아니며, 아래쪽에는 같은 파이프라인에서 processor를 중복 참조하는지도 확인해요. 이 검사가 통과했다고 endpoint 연결이나 처리 결과까지 검증된 것은 아니에요. 설정의 구조와 실제 환경의 동작은 따로 확인해야 해요.

3. 참조 목록이 실제 호출 그래프로 바뀌어요

이제 설정이 동작으로 바뀌는 곳을 봐요. graph.Build()는 컴포넌트 노드를 만들고, 그 사이의 연결을 만든 뒤, 실제 컴포넌트를 구성해요. processor 노드는 설정 목록을 순회하며 slice에 추가해요. 따라서 처음 설정에 적은 순서가 다음 연결 단계에서도 유지돼요.

소스 캡처 2. 설정 순서대로 처리 경로를 연결해요. 원문 267~290행

createEdges()는 receiver를 capabilities 노드에 연결하고, processor를 하나씩 이어 붙인 다음, fanout과 exporter를 연결해요. capabilities 노드는 데이터 변경 가능성 같은 consumer의 성질을 전달하는 내부 구성이고, 사용자가 YAML에 적는 처리 정책 하나가 추가된다는 뜻은 아니에요. exporter가 하나여도 fanout 노드는 만들어지며, 그 경우 통과 역할을 한다는 주석도 있어요.

📖 용어: fan-out
한 입력을 여러 전달 대상으로 나누는 구성이에요. exporter 목록에 두 목적지를 넣으면 두 목적지로 보내는 경로가 생겨요. 두 저장소의 결과를 하나의 원자적 작업으로 묶거나, 둘 다 성공할 때만 저장된다는 뜻은 아니에요.
그림 1. 처리 순서는 선형으로, 목적지는 분기로 구성돼요.

선이 만들어지면 buildComponents()가 뒤쪽 컴포넌트부터 만들면서 다음 consumer를 넘겨줘요. receiver가 데이터를 받아 consumer를 호출하면 이 연결을 따라 처리가 진행되는 구조예요. 그림의 화살표마다 독립 네트워크 요청이나 비동기 큐가 하나씩 있다는 뜻은 아니에요. 큐나 배치는 해당 컴포넌트가 실제로 구현하고 설정한 곳에서 생겨요.

시작과 종료 순서에도 같은 관계가 반영돼요. StartAll()과 ShutdownAll()은 뒤쪽을 먼저 시작하고 앞쪽부터 종료하도록 구성돼 있어요. 받는 쪽을 준비한 후 입력을 열고, 입력을 멈춘 후 다음 쪽으로 남은 데이터를 보낼 기회를 주는 순서예요. 다만 이 순서가 강제 종료·디스크 오류·종료 제한 시간까지 없애는 것은 아니에요.

4. 순서와 인스턴스를 잘못 이해하면 정책도 달라져요

processor의 순서는 설정을 보기 좋게 정렬하는 문제가 아니에요. 가정으로, 특정 속성을 가진 스팬을 제외하는 필터와 그 속성을 지우는 처리가 있다고 해 봐요. 필터를 먼저 실행하면 그 값을 보고 판단할 수 있어요. 먼저 지워 버리면 다음 필터가 기대한 조건을 읽을 수 없어요. 반대로 어떤 민감한 속성을 뒤의 처리기에 남기면 안 되는 상황이라면 제거 시점 자체가 우선 조건이에요. 같은 두 처리라도 요구사항에 따라 맞는 순서가 달라져요.

배치도 앞의 처리를 무효로 만들지 않아요. 필요 없는 데이터를 거르는 일을 배치 앞에 두면 나중에 버릴 데이터까지 오래 모아 둘 필요를 줄일 수 있어요. 다만 실제 메모리와 지연 변화는 선택한 processor와 입력 형태에 따라 측정해야 해요. 위 예제의 memory_limiter와 batch 순서를 모든 처리기의 보편적 정답으로 확장하면 안 돼요. 메모리 제한이 거절한 데이터에 앞단이 어떻게 반응하는지도 함께 봐야 해요.

여러 파이프라인에서 같은 processor ID를 쓰는 경우도 주의가 필요해요. 공식 문서는 파이프라인별 processor 인스턴스가 따로 만들어진다고 설명해요. 이 버전의 노드 생성도 processor에는 pipeline ID를 함께 넘겨요. 같은 batch 설정을 참조한다고 서로 다른 traces 파이프라인의 대기 데이터가 하나로 합쳐진다고 가정하면 안 돼요. 설정 재사용과 실행 상태 공유는 다른 문제예요.

따라서 파이프라인을 나눌 때는 YAML 줄 수뿐 아니라 생기는 실행 상태도 세어 봐야 해요. 별도 배치 상태, 정책별 대기 데이터, 목적지별 전송 큐가 어떤 컴포넌트에 생기는지 확인하는 거예요. 반대로 receiver나 exporter까지 전부 무조건 pipeline별 별도 인스턴스라고 일반화할 수도 없어요. 이 소스는 종류와 신호에 따라 노드 재사용을 다르게 처리해요. 공유 여부를 확인하지 않은 채 파이프라인 수만으로 자원 사용량을 계산하지 않는 편이 좋아요.

5. 중앙 관리는 반드시 한 대를 뜻하지 않아요

Collector의 배포 위치는 처리 기능과 별도로 선택해요. 공식 agent 배포는 앱 옆이나 같은 호스트에 Collector를 두는 구성을 설명해요. gateway 배포는 앱이나 다른 Collector가 공통 OTLP 주소로 보내는 구성이에요. 이 주소 뒤에는 하나 이상의 인스턴스가 있을 수 있어요. 공통 정책을 관리한다는 것과 물리적으로 한 프로세스만 운영한다는 것은 같지 않아요.

📖 용어: agent 배포와 gateway 배포
여기서 agent는 앱 가까이에 둔 Collector의 배포 역할이에요. JVM에 넣는 Java instrumentation agent와 다른 뜻이에요. gateway는 여러 생산자의 데이터를 받는 공통 수집 계층을 뜻하며, 반드시 단일 인스턴스인 것은 아니에요.

앱 가까운 Collector는 호스트의 로그·메트릭을 함께 수집하거나 로컬 전달 지점을 두고 싶을 때 생각할 수 있어요. 앱마다 원격 저장소 인증 정보를 배포하는 범위도 줄일 수 있어요. 하지만 노드마다 Collector를 배포·업데이트·관찰해야 하고, 호스트 자원을 함께 사용해요. 로컬 전달이 빨라져도 이후 네트워크 장애가 사라지는 것은 아니에요. 같은 노드의 장애로 앱과 로컬 수집기가 함께 사라질 가능성도 고려해야 해요.

공유 gateway는 목적지 인증과 처리 정책을 관리할 배포 단위를 앱과 분리하기 편해요. 대신 앱에서 gateway까지의 네트워크가 새 의존성이 되고, 한 번의 잘못된 필터 배포가 여러 서비스에 영향을 줄 수 있어요. 인스턴스를 복제해도 모든 인스턴스가 같은 잘못된 설정을 읽으면 정책 오류에는 도움이 되지 않아요. 가용성과 변경 안전성을 별도로 설계해야 하는 이유예요.

agent와 gateway를 함께 둘 수도 있어요. 가까운 쪽에서 수집하고 공통 계층에서 정책을 적용하는 방식이에요. 이때는 홉·인증·큐·관측 지점도 늘어요. 저는 배포 형태를 고를 때 “중앙화할 수 있나”보다 “호스트 접근이 필요한가, 실패를 어디까지 분리할 것인가, 누가 각 계층을 운영할 것인가”를 먼저 묻는 편이 더 구체적이라고 봤어요. 작은 환경에 두 계층을 추가하고 아무도 큐와 인증 만료를 보지 않는다면, 직접 전송보다 좋은 운영이 된다고 단정할 수 없어요.

6. 받았다는 응답은 어디까지의 성공일까요?

Collector를 사이에 넣으면 성공의 경계도 나뉘어요. 앱이 Collector에 보낸 요청이 성공한 것, exporter의 대기 큐에 들어간 것, 백엔드의 수신 요청이 성공한 것, 백엔드가 데이터를 보관해 질의할 수 있는 것은 서로 다른 사건이에요. OTLP 사양도 응답이 한 client/server 쌍 사이의 확인이며 여러 중간 노드를 거치는 전체 경로의 보장을 정의하지 않는다고 명시해요. OTLP의 전달 범위를 큐의 동작과 함께 읽어야 해요.

📖 용어: 확인 응답(acknowledgement)
요청을 받은 쪽이 정해진 조건까지 처리했다고 돌려주는 응답이에요. 무엇을 확인하는지는 프로토콜과 구현에 달려 있어요. 중간 수집기의 수락 응답을 최종 데이터베이스의 저장 완료로 읽지 않는 것이 중요해요.

이 버전의 exporterhelper는 큐·배치·재시도 같은 공통 기능을 제공해요. QueueBatch.Send()는 queue의 Offer()를 호출해요. 고정 버전의 설정 설명에서 wait_for_result 기본값은 false예요. 이 helper의 큐를 쓰는 구성에서는 큐에 수락하는 시점과 뒤에서 전송을 처리하는 시점을 구분해야 해요. 모든 exporter가 항상 같은 큐나 같은 응답 시점을 가진다는 뜻은 아니에요.

그림 2. 비동기 큐를 쓰는 경로의 개념도예요. 다른 버퍼링·대기 설정에서는 응답 시점이 달라질 수 있어요.

큐 앞에서 거절된 요청과, 큐에서 꺼내 전송하다 실패한 요청도 달라요. exporterhelper 설명은 enqueue 실패가 그 exporter의 재시도 로직에 도달하지 않는다고 구분해요. 앞단이 오류를 받고 재전송할 수 있는지는 앞단의 구현·오류 분류·남은 재시도 예산에 달려 있어요. 그러므로 “재시도를 켰으니 큐가 차도 다시 전송된다”는 결론은 성립하지 않아요. block_on_overflow를 켜면 기다리는 선택도 가능하지만, 그 대기는 앞단 요청의 지연과 제한 시간 문제로 이어질 수 있어요.

두 exporter로 보내는 상황도 같은 방식으로 봐요. 한 목적지가 성공하고 다른 쪽이 실패할 수 있어요. 재시도 중 같은 데이터가 다시 도착할 가능성을 포함해 각 저장소의 처리 의미를 확인해야 해요. 저는 이 구조를 정확히 한 번의 공통 저장 작업으로 취급하지 않았어요. 데이터 유입·큐 수락·전송 성공의 숫자를 같은 이름의 성공으로 합치지 않는 편이 실패 위치를 찾는 데 더 도움이 돼요.

7. 디스크와 복제 수를 늘려도 남는 경계가 있어요

메모리 큐는 프로세스 종료와 함께 없어질 수 있어요. 공식 복원력 문서는 exporter sending queue에 file_storage 같은 저장 확장을 연결해 재시작 후 전송을 이어가는 구성을 설명해요. 확장을 정의하는 것뿐 아니라 service.extensions에서 켜고, exporter의 큐가 그 storage ID를 참조해야 해요. 이 경우 디스크 공간·권한·볼륨의 수명도 수집 시스템의 운영 항목이 돼요.

📖 용어: 영속 큐(persistent queue)
프로세스 메모리에만 두지 않고 저장 장치에 데이터를 남겨 재시작 후 다시 읽을 수 있게 한 큐예요. 저장 장치 장애, 용량 초과, 재시도 정책의 종료까지 없애지는 않아요. 장기 질의를 위한 관측 데이터베이스와도 역할이 달라요.

여기서 디스크에 남는 범위를 정확히 봐야 해요. exporter의 영속 큐는 그 큐까지 도달한 데이터를 대상으로 해요. 앞의 processor가 메모리에 대기시키던 데이터, Collector에 도착하지 못한 데이터, SDK가 버린 데이터까지 보호하지는 않아요. 종료도 자동 복구의 예외가 아니에요. 이 버전 exporterhelper의 종료 순서는 재시도 sender를 먼저 멈추고 큐를 종료해요. 큐 종료 주석도 남은 요청을 내보낼 때 재시도는 멈춘 상태임을 설명해요. 종료 처리가 있다는 사실을 장애 중 전량 전달 보장으로 읽을 수 없어요.

gateway 복제 수를 늘리는 일에도 반례가 있어요. 목적지의 처리 한도가 이미 꽉 찼는데 수집기와 전송 worker만 늘리면 목적지 압력이 더 커질 수 있어요. 큐 크기를 늘리는 선택은 더 오래 대기할 여지를 주지만, 지속적인 입력 초과를 없애지는 않아요. 소요 디스크·메모리와 대기 데이터의 나이도 늘 수 있어요. 원인이 입력 처리 CPU인지, 목적지의 거절인지, 네트워크인지 구분한 후 확장해야 해요. 공식 확장하지 말아야 할 경우도 이 상황을 따로 다뤄요.

상태를 모아 판단하는 처리는 아무렇게나 분산할 수 없어요

tail sampling은 도착한 스팬들을 일정 시간 모아 trace의 처리 여부를 정해요. 같은 trace의 일부는 gateway A로, 다른 일부는 B로 보내면 각 인스턴스는 불완전한 입력으로 판단할 수 있어요. 단순히 복제 수를 늘리거나 요청별로 분산하는 것만으로 처리 의미가 유지되지 않는 이유예요. 공식 문서는 trace ID를 기준으로 같은 처리기로 보내는 load-balancing 계층을 설명해요. 상태가 있는 Collector 확장이 근거예요.

📖 용어: trace affinity
같은 trace ID에 속한 데이터를 같은 처리 인스턴스로 보내려는 배치 원칙이에요. trace를 모아 판단하는 처리에 중요해요. 인스턴스 변경 시의 재분배와 늦게 도착하는 데이터까지 자동 해결한다는 뜻은 아니에요.

scrape 수집도 복제하면 끝나는 종류가 아니에요. 모든 복제본이 같은 target을 그대로 읽으면 중복 수집이 생길 수 있어요. 어떤 인스턴스가 어떤 대상을 읽을지 나누는 정책이 필요해요. 메트릭 변환이나 집계가 상태를 가진다면 그 상태의 식별 기준도 확인해야 해요. “Collector는 상태가 없다”라는 하나의 문장으로 전체 구성을 판단하기보다 실제로 넣은 컴포넌트별로 확장 조건을 검토해야 해요.

8. 중앙에서 지우기 전에 이미 지나온 경로가 있어요

민감정보 제거는 중앙 관리의 유용한 예지만, 제거 위치를 잘못 해석하기 쉬워요. 앱이 민감한 값을 스팬에 넣어 gateway까지 전송했다면, gateway에서 지워도 그 값은 이미 앱의 메모리와 SDK 처리 경로, gateway까지의 전송을 거쳤어요. TLS는 전송 중 보호와 관련되지만, 애초에 수집하지 않았다는 뜻은 아니에요. gateway의 수신 지점에서도 원본 데이터를 다루게 돼요.

그래서 “저장소로 보내면 안 된다”와 “프로세스 밖으로 내보내면 안 된다”는 다른 요구사항이에요. 전자는 Collector에서의 제거 정책이 방어 수단이 될 수 있어요. 후자는 계측 시점의 데이터 선택을 먼저 바꿔야 해요. 공식 민감정보 처리 가이드도 필요한 데이터만 수집하는 원칙과 계측 출력 검토를 강조해요. Collector에 processor가 있다는 사실만으로 모든 값의 민감한 의미를 자동 판별하는 것은 아니에요.

이 관점은 영속 큐와도 연결돼요. 제거 전 데이터를 어느 경로에서 파일로 남기는지, 디버깅 exporter가 원문을 출력하는지, 다른 파이프라인이 같은 입력을 우회해서 내보내는지 확인해야 해요. 제거 processor 하나를 넣었다는 확인보다, 민감한 데이터가 만들어진 곳에서 각 저장·출력 지점까지 실제 경로를 따라가 보는 편이 정확해요. 정책을 중앙에 모으면 일관성을 높일 수 있지만, 잘못된 허용 정책의 영향 범위도 넓어져요.

9. 직접 전송·Prometheus Agent·Alloy를 같은 기준으로 봐요

이제 다른 선택지를 수집 계층이라는 기준에서 비교해 봐요. OTel SDK와 Prometheus 저장 서버, Collector를 이름만 다른 대체품으로 놓으면 역할이 섞여요. 아래 표는 무엇을 만드는지보다 “앱 밖의 수집·처리·전달을 어디서 운영하는가”를 맞춰 본 것이에요. 개별 컴포넌트의 전체 기능이나 성능 순위표는 아니에요.

선택중심 역할별도로 남는 책임
SDK 직접 전송앱의 exporter가 목적지와 통신해요.앱별 전송 설정과 목적지 운영이 남아요.
OTel Collector포함된 컴포넌트로 수집·처리·전달해요.수집 계층의 배포·용량·전달 실패를 운영해요.
Prometheus AgentPrometheus 메트릭 scrape와 remote write에 집중해요.질의·규칙 평가·장기 저장은 다른 쪽이 맡아요.
Grafana AlloyOTel Collector 배포판으로 여러 수집 파이프라인을 조합해요.선택한 엔진·컴포넌트 구성과 저장 백엔드를 운영해요.

Prometheus Agent는 Prometheus 바이너리의 운영 모드예요. scrape와 서비스 발견 같은 메커니즘을 유지하며 remote write 전달에 집중하고, 질의·알림·규칙 평가와 통상적인 로컬 TSDB 역할을 끄는 구성이에요. 대신 전송용 WAL을 사용하므로 “저장 서버가 아니니 디스크를 전혀 쓰지 않는다”는 설명은 틀려요. 메트릭을 수집해 원격 저장소로 보내려는 목적이면 비교할 수 있지만, 이 모드만으로 OTel trace의 처리까지 대신한다고 볼 수는 없어요.

Grafana Alloy는 OTel Collector 배포판이며 Prometheus 파이프라인과 Loki·Pyroscope 지원 등을 함께 제공해요. Collector와 완전히 무관한 별도 계층이라고 보기보다 수집 컴포넌트의 조합과 운영 방식이 다른 선택으로 보는 편이 맞아요. 공식 구조 문서도 데이터 소스와 저장 백엔드 사이의 수집 계층으로 설명해요. 구성 문법만으로 단순 구분하지 않고, 선택한 버전과 엔진이 실제로 지원하는 컴포넌트를 확인해야 해요.

Alloy에는 컴포넌트 상태를 확인하는 디버깅 UI도 있어요. 따라서 “Alloy는 UI가 없고 Grafana만 UI가 있다”는 비교는 부정확해요. 다만 이 UI가 있다는 사실과, 수집한 모든 신호를 장기간 보관하고 질의하는 백엔드라는 주장은 달라요. 수집기에서 디스크 버퍼나 진단 화면을 제공해도 관측 저장소의 책임을 모두 맡는 것은 아니에요.

선택이 달라지는 두 가지 경우를 가정해 봐요

첫째, 개발용 서비스 몇 개가 단일 OTLP 백엔드로 보내고 공통 처리 정책도 없다면 직접 전송은 운영 대상을 줄이는 선택이 될 수 있어요. SDK의 전송 한계를 확인하고 목적지 인증을 안전하게 관리할 수 있다는 조건이 붙어요. 반대로 조직 공통의 필터와 여러 목적지 전송을 자주 바꿔야 한다면 Collector 계층을 따로 두는 가치가 커져요. 서비스 수만으로 결정하기보다 변경 빈도와 정책 소유자가 어디에 있는지를 보는 거예요.

둘째, 요구사항이 기존 Prometheus scrape 설정과 발견 규칙을 유지하면서 중앙 remote-write 저장소로 메트릭을 보내는 것이라면 Prometheus Agent를 검토할 이유가 있어요. 여기에 OTLP trace·로그 수집과 여러 전처리를 같은 운영 단위에 모아야 한다면 Collector나 Alloy의 해당 컴포넌트 구성이 비교 대상이 돼요. 이미 익숙한 설정·필요한 컴포넌트·업데이트 정책을 확인해야 해요. 어느 쪽이 더 빠르고 싸다는 결론은 같은 입력과 배포 조건의 측정 없이 낼 수 없어요.

10. 추가한 수집 계층도 관측 대상이에요

Collector를 넣은 뒤 앱의 exporter 오류만 본다면 새로 생긴 실패 구간을 놓칠 수 있어요. 수신 거절, processor의 의도적 제외, 큐 진입 실패, 전송 실패, 저장 장치 부족을 구분해 봐야 해요. 공식 확장 문서는 otelcol_exporter_queue_size, otelcol_exporter_queue_capacity, otelcol_exporter_enqueue_failed_spans, otelcol_exporter_send_failed_spans 같은 신호를 설명해요. 실제 이름·단위·노출 설정은 선택한 버전과 컴포넌트의 내부 텔레메트리 문서를 맞춰 확인해야 해요.

특히 위 예제는 큐의 sizer를 items로 명시했어요. 그 수를 기본 requests 큐의 크기나 바이트 한도와 그대로 비교하면 안 돼요. 요청 하나에 담기는 데이터 수와 데이터 크기가 다르면 같은 queue_size라도 자원 비용이 달라져요. 큐가 낮게 유지된다는 사실 하나로 손실이 없다고 판단할 수도 없어요. 앞단에서 이미 거절하거나 필터가 버리는 경우에는 큐가 비어 있어도 관측 데이터가 줄 수 있어요.

변경 검증도 설정 문법 검사와 동작 검사를 나누는 편이 좋아요. 사용할 배포판의 validate 명령으로 참조와 설정을 검사한 뒤, 민감정보가 없는 작은 입력으로 각 목적지의 도착 여부와 처리 결과를 확인하는 식이에요. 그다음 큐 초과·목적지 중단·재시작·정상 종료에서 기대한 범위만 보존되는지 별도 시험할 수 있어요. 이는 앞으로 배포할 때의 확인 항목이고, 이 글에서 실행했다는 결과는 아니에요.

여기서는 고정 소스의 구성·연결·시작과 종료 경로, exporterhelper의 큐 경계, 공식 문서의 배포·확장·제품 역할을 읽었어요. YAML 배포나 장애 주입, 처리량 비교는 실행하지 않았어요. 소스 PNG의 줄 범위와 파일 해시는 별도 manifest로 남겼고, 제품 간 런타임 성능이나 모든 exporter의 보장을 확인한 것으로 확장하지 않았어요.

소스 기준: OpenTelemetry Collector v0.163.0. 코드 이미지는 해당 공개 소스를 렌더링했어요.

✍️ 오늘의 요약
Collector를 두면 받은 데이터의 처리·전달 정책을 앱과 분리할 수 있어요. 그 대신 수집 계층 자체의 배포·용량·실패·변경 안전성을 운영해야 해요.

정의와 활성화, processor의 순서, 파이프라인별 상태가 실제 동작을 결정해요. 큐 수락은 최종 저장 확인이 아니며, 영속 큐와 복제본도 이미 버려진 입력이나 잘못된 정책을 복구하지 못해요. 도구를 고를 때는 이름보다 어느 경계의 책임을 옮기는지부터 확인해야 해요.
