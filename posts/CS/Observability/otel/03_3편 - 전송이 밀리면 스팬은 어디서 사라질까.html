📚 OpenTelemetry 구조와 설계 읽기
1편. API와 SDK는 왜 나뉘어 있을까
2편. 스레드가 바뀌면 컨텍스트는 어떻게 이어질까
3편. 전송이 밀리면 스팬은 어디서 사라질까 ← 지금 이 글

스팬을 끝낸 뒤 조회 화면에서 찾지 못했다고 가정해 볼게요. span.end()를 호출했으니 전송도 끝났을까요? OpenTelemetry Java의 BatchSpanProcessor를 읽어 보면, 스팬 종료와 외부 전송 사이에 아직 여러 단계가 남아 있어요.

📖 용어: 스팬 (span)
요청 처리나 데이터베이스 호출 같은 작업 하나의 시작·종료와 속성을 기록한 데이터예요. 작업이 끝났다는 사실과 그 기록이 저장소에 도착했다는 사실은 달라요.

이번에는 Java SDK v1.67.0에서 전송을 별도 스레드로 넘기면서 무엇을 얻고, 어디서 기록을 잃을 수 있는지 호출 경로를 따라가 볼게요.

1. span.end()는 어디까지 실행한 뒤 돌아올까

첫 출발점은 SdkSpan.end()예요. 인자 없는 메서드는 현재 시간을 구해 endInternal()을 호출합니다. 이 내부 메서드는 종료 상태와 시간을 기록하고, 필요한 종료 직전 처리를 거쳐 스팬을 종료 상태로 바꿔요. 그다음 spanProcessor.isEndRequired()가 참이면 spanProcessor.onEnd(this)를 호출합니다.

여기까지는 별도 작업으로 제출하는 코드가 아니에요. end()를 호출한 스레드가 처리기의 onEnd()도 실행합니다. 처리기를 여러 개 등록한 경우에는 MultiSpanProcessor가 필요한 처리기의 콜백을 차례로 불러요. 따라서 “OTel은 비동기니까 종료 호출에서 무슨 일을 해도 요청과 무관하다”는 결론은 성립하지 않아요.

스팬을 끝낼 때마다 원격 서버의 응답까지 기다리면 전송 지연이 애플리케이션 실행에 영향을 줄 수 있어요. 공식 오류 처리 원칙은 계측 때문에 애플리케이션 동작이 크게 바뀌는 것보다 관측 데이터 손실을 선호한다고 설명해요. 영향이 전혀 없다는 약속과는 달라요.

배치 처리는 여러 스팬을 모아 전송 함수에 건네는 방식이에요. 배치 처리기 사양도 최대 대기 개수와 전송 조건을 따로 정해요. 호출을 묶는 대신 메모리와 대기 시간이 필요합니다.

📖 용어: SpanProcessor와 SpanExporter
처리기인 SpanProcessor는 스팬 종료를 받아 배치 등의 처리를 해요. 전송기인 SpanExporter는 전달받은 스팬 데이터를 외부로 보내는 역할을 맡아요.

생성자에는 크기가 제한된 큐와 별도 작업 스레드가 나옵니다. 큐를 무제한 늘리면 지속적인 전송 지연이 메모리 증가로 이어질 수 있고, 빈자리가 날 때까지 기다리면 호출 스레드도 지연돼요. 이 구현은 대기 공간에 한도를 두고, 공간이 없으면 새 스팬을 받지 않아요.

호출 스레드 SdkSpan.end() → endInternal() → SpanProcessor.onEnd() → BatchSpanProcessor의 sampled 여부 확인 → Worker.addSpan() → 큐 삽입 성공 또는 폐기 작업 스레드 Worker.run() → drain() → exportCurrentBatch() → SpanExporter.export() → 결과 대기 → 현재 배치 정리

이 목록은 위 고정 소스를 따라 정리한 호출 순서이지 실행 로그가 아니에요. onEnd() 앞쪽은 호출 스레드에서, 배치 변환과 전송은 작업 스레드에서 일어난다는 경계를 먼저 잡아야 합니다.

2. SimpleSpanProcessor라면 전부 동기 전송일까

비교 대상은 같은 SDK의 SimpleSpanProcessor예요. 이 구현은 onEnd() 안에서 스팬 하나를 SpanData로 바꾸고, synchronized (exporterLock) 안에서 곧바로 spanExporter.export(spans)를 불러요. 배치 작업 스레드와 대기 큐를 거치지 않아요.

하지만 호출이 끝날 때 네트워크 전송까지 끝났다고 말할 수는 없어요. export()가 반환한 CompletableResultCode를 pendingExports에 넣고 완료 콜백을 등록할 뿐, 이 onEnd()에는 join()이 없습니다. 동기인 것은 export 메서드의 호출 위치예요. exporter가 내부에서 비동기 네트워크 작업을 시작하면 완료는 나중일 수 있어요.

반대로 exporter가 메서드 안에서 오래 처리하면 호출 스레드도 그 시간만큼 지연됩니다. 락을 잡은 상태에서 호출하므로 여러 스레드의 스팬 종료가 같은 락에서 기다릴 가능성도 있어요. 그러니 Simple의 비용을 판단하려면 exporter의 직렬화, 메모리 할당, 동기 처리와 비동기 완료 방식을 함께 읽어야 해요. 이름만 보고 항상 네트워크 완료까지 기다린다고 하거나, 항상 즉시 돌아온다고 하면 둘 다 과장이에요.

어떤 선택이 나을까요? 단일 스팬을 로그에 바로 출력하는 작은 디버깅 exporter라면 Simple의 짧은 경로가 읽기 쉬울 수 있어요. 다만 로그 출력 자체의 비용은 남습니다. 원격 목적지로 많은 스팬을 보내는 경우라면 Batch가 exporter 호출을 묶고 실행 위치도 분리해요. 그 대신 큐 메모리, 전달 지연, 종료 시 처리해야 할 데이터가 생깁니다. 소스의 클래스 설명도 단일 스팬 전송 부담을 언급하며 일반적인 원격 전송에는 Batch를 고려하라고 해요.

반례도 있어요. 프로세스가 아주 짧게 실행되고 정상 종료 절차가 없다면, Batch 큐에 넣고 바로 종료하는 것만으로는 전송을 기대하기 어려워요. 그렇다고 Simple로 교체하면 해결된다고 단정할 수도 없습니다. Simple의 exporter도 비동기일 수 있기 때문이에요. 처리기 선택과 완료를 기다리는 수명주기 처리는 서로 다른 문제예요.

3. 큐에 넣지 못한 스팬은 다시 시도하지 않아요

전송이 늦어지는 동안에도 스팬은 계속 끝날 수 있어요. 이때 먼저 볼 곳은 addSpan()입니다.

📖 용어: 크기가 제한된 큐 (bounded queue)
처리 전 데이터를 일정 개수까지만 보관하는 대기 공간이에요. 개수 제한이 있으므로, 들어오는 속도가 처리 속도보다 계속 빠르면 새 데이터를 모두 보관할 수는 없어요.
코드 1. queue.offer 실패 뒤에는 재삽입이 아니라 폐기 기록이 있어요

원문: BatchSpanProcessor.java 228~242줄, v1.67.0

229줄은 처리기가 이미 종료됐는지 검사해요. 234줄의 queue.offer(span)는 큐에 빈자리가 생길 때까지 기다리는 호출이 아니에요. 실패하면 235~236줄에서 폐기 계측과 경고용 카운터를 갱신합니다. 이 경로에는 해당 스팬을 다시 넣는 코드가 없어요.

여기서 버리는 것은 새로 넣으려던 스팬이에요. 기존 스팬을 큐에서 하나 빼고 최신 스팬으로 교체하지도 않고, 나중에 재시도할 별도 목록에 보관하지도 않아요. 이미 종료된 처리기에 전달된 경우에는 큐 삽입을 시도하기도 전에 dropSpansAlreadyShutdown(1)을 부르고 돌아와요. 큐 포화와 종료 후 전달은 다른 폐기 이유입니다.

그보다 앞선 onEnd()는 기본적으로 샘플링에서 내보내도록 선택된(sampled) 스팬만 addSpan()에 넘겨요. exportUnsampledSpans 설정을 바꾸면 범위가 달라져요. 애초에 전송 대상으로 선택하지 않은 스팬과 전송하려다가 큐에서 잃은 스팬을 같은 유실 카운터로 해석하면 원인을 잘못 찾게 돼요.

그림 1. 큐 포화 때 버리는 것은 새로 넣으려던 스팬이에요
⚠️ 비동기 전송도 비용은 있어요
큐가 찼을 때 기다리지 않는 것과 애플리케이션에 영향이 없는 것은 달라요. 스팬 생성, 속성 기록, 큐 처리에도 CPU와 메모리가 필요합니다. 여기서는 성능 수치를 측정하지 않았어요.

실행해 보기: 첫 전송을 보류한 상태에서 다섯 스팬을 더 끝내요

코드의 분기를 읽는 것과 실제 설정에서 같은 결과를 확인하는 것은 다른 일이에요. 공개 Maven 아티팩트 1.67.0으로 큐 크기 2, 배치 크기 1을 설정하고, 첫 전송의 완료만 제어하는 메모리 exporter를 연결해 실행했어요. 공개 JAR 다섯 개는 SHA-256을 검증했고, 상위 소스를 수정하거나 전체 프로젝트를 빌드하지는 않았습니다.

먼저 in-flight 스팬을 끝내고 flush를 요청해요. exporter의 첫 export()는 아직 완료되지 않은 CompletableResultCode를 반환하도록 했어요. 호출 자체를 붙잡는 것이 아니라, Batch 작업 스레드가 그 결과를 기다리는 상태를 만든 거예요. 실행 순서는 CountDownLatch라는 스레드 간 완료 신호로 제어했어요. 첫 전송에 진입했다는 신호를 확인한 뒤에만 다음 단계로 진행하므로 “충분히 오래 sleep하면 전송 중일 것”이라고 추측하지 않아요.

첫 결과가 여전히 미완료인 동안 queued-a, queued-b, overflow-c, overflow-d, overflow-e 다섯 스팬을 차례로 끝냈어요. 작업 스레드는 첫 결과를 기다리므로 큐를 비우지 못하고, 두 칸에 들어간 뒤의 세 스팬은 큐에 들어갈 수 없어요. 이후 첫 결과를 완료시켜 작업 스레드가 진행하게 하고, 남은 데이터의 flush 완료까지 확인했습니다.

batch queue-capacity=2 batch-size=1 first-export-pending=true batch spans-ended-while-export-pending=5 batch recording-spans-ended=6 exported=3 not-exported=3 batch exported-names=in-flight,queued-a,queued-b batch PASS

실제 표준 출력이에요. recording 상태로 끝낸 스팬은 여섯 개였고, 메모리 exporter에 남은 이름은 첫 스팬과 큐에 들어간 두 스팬뿐이었어요. SDK가 남긴 표준 오류도 별도로 확인했어요.

BatchSpanProcessor dropped 3 span(s) since the last export because the queue is full (maxQueueSize=2)

경고의 세 개와 exporter에 전달되지 않은 세 개가 일치해요. 이 설정과 제어 순서로 각 실험을 별도 JVM에서 다섯 번 반복했고, 같은 출력과 경고가 나왔습니다. 이 결과는 큐 포화 때 새 스팬을 버리는 분기를 확인한 것이지, 일반적인 유실률이 절반이라는 뜻은 아니에요. exporter 결과를 언제 완료할지도 실험이 제어했으므로 처리량·레이턴시 벤치마크나 실제 네트워크 장애의 재현으로 해석할 수는 없어요.

재현은 저장소 루트에서 python3 labs/observability/otel-runtime-probes/verify.py --repeat 5로 할 수 있어요. 실험 소스, 실행 조건, 아티팩트 해시·반복 횟수·표준 오류 기록을 함께 남겼어요. 여기서 exported는 메모리 exporter에 남았다는 뜻이며, OTLP 전송이나 백엔드 저장 성공을 뜻하지 않습니다.

4. 큐 크기를 늘리면 왜 결국 다시 찰까

전송 장애를 가정해 볼게요. 큐의 유효 수용량을 Q, 현재 대기 개수를 q₀, 전송 대상으로 끝나는 스팬의 유입 속도를 λ, 작업 스레드가 큐에서 꺼내 처리하는 평균 속도를 μ라고 두겠습니다. 아래는 두 속도가 일정하고 배치 단위의 변동을 무시한 설명용 근사예요. 실측값이나 이 구현의 정확한 지연 상한은 아니에요.

λ > μ인 동안의 대기량 증가 속도 ≈ λ - μ 큐가 찰 때까지의 시간 ≈ (Q - q₀) / (λ - μ) 전송 완료를 기다리며 큐를 못 비우는 구간: μ ≈ 0 그 구간에서 새로 쌓이는 스팬 수 ≈ λ × 대기 시간

첫 식은 들어온 개수에서 처리한 개수를 빼면 대기 개수가 남는다는 뜻이에요. 큐를 두 배로 늘리면 한동안 더 보관할 수는 있지만, 유입 속도가 처리 속도보다 계속 빠르다면 증가 원인은 그대로예요. 큐 용량은 일시적인 지연을 흡수할 양을 바꾸지, 지속 가능한 전송 처리량 자체를 보장하지 않아요.

이 구현에서는 네트워크 전송 결과를 기다리는 동안 같은 작업 스레드가 다음 큐 데이터를 꺼내지 못해요. 따라서 exporter의 재시도가 오래 계속되면 그 배치의 성공 가능성을 높이는 대신 SDK 큐의 후속 스팬은 더 오래 기다릴 수 있어요. 재시도 횟수를 늘리는 것이 전체 스팬의 손실까지 항상 줄인다는 결론은 나오지 않습니다. 한 배치의 복구와 뒤에서 증가하는 대기량을 함께 봐야 해요.

큐를 늘리는 것이 오히려 불리한 조건도 있어요. 메모리 여유가 적은 프로세스가 전송 병목을 지속해서 겪는다고 가정해요. 더 큰 큐는 더 많은 스팬 객체를 오래 유지하고, 새로 들어온 기록이 전송될 때까지의 시간을 늘릴 수 있어요. 결국 프로세스가 메모리 한계를 넘으면 기존 큐에 있던 데이터도 잃을 수 있습니다. 이 위험은 큐 포화 시 일부 새 스팬을 버리는 위험과 종류가 달라요. 여기서는 메모리나 GC의 구체 수치를 측정하지 않았어요.

대안은 세 가지로 나눠 볼 수 있어요. 무제한 큐는 폐기 결정을 미루지만 메모리 한도를 해결하지 못해요. 빈자리가 날 때까지 호출을 막는 큐는 유입을 늦출 수 있지만 그 지연이 스팬 종료를 호출한 애플리케이션 스레드로 전달돼요. 현재 Batch 구현은 용량을 제한하고 새 스팬을 버리는 쪽이에요. 이 비교는 가능한 설계 선택을 이해하기 위한 것이며, 세 가지 모드가 모두 이 처리기의 옵션으로 제공된다는 뜻은 아니에요.

5. 작업 스레드는 언제 무엇을 exporter에 넘길까

큐에 들어간 다음에는 작업 스레드의 run()을 따라갑니다. 먼저 flush 요청이 있으면 처리하고, 남은 배치 공간만큼 drain()으로 꺼내요. drain()은 ReadableSpan을 SpanData로 바꿔 배치에 담고 큐 개수를 줄여요. 큐에 넣을 때 이미 직렬화된 네트워크 요청이 완성된 것은 아니에요.

배치가 최대 크기에 도달하거나 다음 전송 시간이 지나면 exportCurrentBatch()를 불러요. 큐가 비었다면 별도의 신호 큐에서 다음 전송 시점까지 기다립니다. 스팬을 넣는 쪽은 필요한 개수가 모였을 때 신호를 보낼 수 있어요. 신호는 “새 처리 기회가 있다”는 알림이고, 실제 스팬 저장 공간은 앞에서 본 스팬 큐예요.

📖 용어: 배치 (batch)
여러 스팬을 한 번의 전송 호출에 넘기기 위해 모은 목록이에요. 최대 배치 크기와 큐 전체의 최대 대기 개수는 서로 다른 설정입니다.
maxQueueSize 큐에서 기다릴 수 있는 최대 스팬 수 maxExportBatchSize 한 전송 호출에 모을 최대 스팬 수 scheduleDelay 배치 전송 시점을 정하는 시간 설정 exporterTimeout 전송 결과를 기다리는 시간 설정

위 목록은 설정 역할을 구분한 것이에요. 큐를 크게 하는 것만으로 전송 처리량이 늘어나지는 않아요. 지연을 더 오래 흡수할 수 있지만 메모리 사용과 대기 데이터가 늘어납니다.

배치 크기와 전송 간격도 같은 조절기가 아니에요. 큰 배치가 빨리 만들어지는 상황에서는 시간 조건 전에 전송을 시작할 수 있어요. 반대로 유입이 적다면 정해진 개수까지 계속 기다리는 것이 아니라 시간 조건으로 작은 배치를 보낼 수 있어요. 이 구현의 다음 전송 시각은 전송 함수가 돌아온 뒤 갱신돼요. 그러므로 간격 설정을 모든 스팬의 최장 도착 지연이나 백엔드 응답 제한으로 읽으면 안 됩니다.

코드 2. 결과 대기가 끝나면 처리기의 현재 배치는 비워져요

원문: BatchSpanProcessor.java 355~370줄, v1.67.0

359줄에서 exporter를 호출하고, 360줄에서 결과를 기다려요. 실패하면 로그를 남기지만 367~368줄의 finally에서는 배치를 비웁니다. 이 처리기에는 실패 배치를 다시 큐에 넣는 경로가 없어요. 그렇다고 모든 전송이 한 번만 시도된다는 뜻은 아니에요. 재시도는 사용하는 exporter와 전송 설정을 따로 확인해야 합니다.

전달하는 값도 조금 더 읽어 볼 필요가 있어요. Collections.unmodifiableList(batch)는 exporter 쪽에서 목록을 수정하지 못하게 만든 뷰예요. 별도의 영구 저장 사본을 만든다는 뜻이 아니고, 처리기가 가진 원래 목록과 무관한 복사본이라는 뜻도 아닙니다. 비동기 exporter가 데이터를 유지하는 방법과 exporter 계약은 별도로 확인해야 해요. “불변 목록을 넘겼으니 나중에 실패해도 재사용할 수 있다”는 보장은 이 코드에서 나오지 않아요.

⚠️ 대기 제한이 전송 작업의 강제 중단은 아니에요
이 코드의 join(timeout)은 결과를 기다리는 시간을 제한해요. 실행 중인 네트워크 작업을 반드시 취소한다는 뜻은 아닙니다. 그 앞의 동기 export() 호출 자체가 오래 걸리는 구현이라면, 아직 join()에 도달하지 않았을 수도 있어요. exporter의 시간 제한도 확인해야 해요.

CompletableResultCode.join()까지 들어가면 이유가 보여요. 완료 콜백에 연결한 CountDownLatch를 제한 시간만큼 기다린 뒤 돌아옵니다. 시간이 다 됐다고 결과 자체를 실패 상태로 바꾸거나 취소하는 호출은 없어요. 따라서 처리기가 기다리기를 끝낸 뒤에도 exporter의 작업은 완료되지 않았거나 나중에 성공할 수 있어요. 여기서 확실히 알 수 있는 것은 “현재 배치를 처리기 큐로 되돌리지 않는다”는 점이지, 시간 초과한 모든 데이터가 반드시 원격에서도 사라졌다는 점은 아니에요.

6. 정상 종료와 강제 종료의 차이는 어디서 생길까

이 처리기의 작업 스레드는 데몬 스레드예요. 이 스레드만 남았다고 JVM 종료가 보류되지는 않습니다. 큐와 배치도 메모리에 있으므로 프로세스 강제 종료 뒤에 자동으로 복구할 기록은 없어요.

📖 용어: forceFlush
다음 정기 전송 시점까지 기다리지 말고 남은 스팬의 전송을 진행해 달라는 호출이에요. 이미 버린 스팬을 되살리거나 외부 저장소의 영구 저장을 보장하는 호출은 아닙니다.

종료 코드는 flush를 진행한 뒤 exporter 종료를 호출해요. 다만 이 버전의 flush()는 전송 함수를 호출한 뒤 flush 결과를 성공으로 표시합니다. 반환 성공을 백엔드의 영구 저장 확인으로 해석하면 안 돼요. 정상 종료 시간을 주는 것은 손실을 줄이기 위한 조건이지, 모든 실패 상황의 전송 완료를 보장하는 조건은 아닙니다.

진행 순서를 더 나누면 shutdown()은 먼저 isShutdown을 바꿔 이후 스팬의 수신을 막고, forceFlush() 완료 뒤 작업 루프를 멈추고 exporter의 shutdown()을 불러요. 반환되는 결과는 비동기 완료를 나타내요. 호출문을 실행하는 것만으로 끝난 것이 아니라, 애플리케이션의 정상 종료 절차에서 완료를 기다릴 시간을 확보해야 해요.

forceFlush()는 flush 요청을 등록하고 작업 스레드를 깨웁니다. 실제 flush()는 시작 시점의 큐 개수를 기준으로 스팬을 배치에 옮겨 전송 함수를 불러요. 애플리케이션이 계속 새 스팬을 만드는 도중의 flush와, 새 스팬을 더 받지 않도록 한 뒤 진행하는 shutdown을 같은 상태로 보면 안 돼요. 이미 큐에서 버렸거나 아직 끝나지 않아 처리기에 도달하지 않은 스팬도 flush가 새로 만들어 주지 않아요.

“flush 성공”과 “외부 보관 성공”도 분리해서 읽어야 해요. 이 버전은 exportCurrentBatch() 내부의 실패를 flush 결과에 하나씩 합산하지 않아요. 작업 진행을 확인하는 결과와 원격 서버가 수신한 데이터, 조회용 저장소가 보관한 데이터는 같은 확인이 아니에요. 종료 절차에서는 처리기 결과만 보지 말고 exporter 오류와 목적지의 수신 상태도 함께 확인해야 합니다.

7. Collector의 디스크 큐와 Kafka는 무엇이 다를까

Collector에 보내는 구조여도 SDK 큐에서 이미 버린 스팬은 도착하지 않아요. Collector 복원력 문서가 설명하는 전송 큐, 재시도, 디스크 저장은 Collector가 받은 데이터를 이후 목적지로 보내는 구간의 대책입니다.

📖 용어: Collector의 WAL (write-ahead log)
Collector 전송 큐의 데이터를 디스크에 기록해 재시작 뒤에도 전송을 이어가도록 하는 방식이에요. SDK 메모리 큐의 디스크 사본은 아니며, 디스크 장애나 재시도 한도 같은 제약도 남아요.
그림 2. 복구 기능이 어느 단계의 데이터를 대상으로 하는지 구분해요

프로세스 안의 Batch 큐는 원격 전송 때문에 애플리케이션 스레드가 지연되는 일을 줄이는 데 도움이 돼요. 하지만 저장 위치는 애플리케이션 메모리예요. Collector의 exporter 전송 큐에 file_storage를 연결하면 그 구간의 데이터를 디스크에 기록하고 Collector 재시작 후 다시 보낼 수 있어요. 이쪽은 애플리케이션 내부의 큐 용량 문제가 아니라 별도 수집 프로세스가 가진 데이터의 재시작 내구성 문제를 다룹니다.

대가도 달라요. 디스크 공간과 입출력, 보관 위치의 수명, 재시도 한도를 운영해야 해요. 전송 큐를 메모리에서 디스크로 바꿔도 SDK가 Collector에 연결하지 못한 구간이나 Collector 수신 이전의 데이터를 복구해 주지는 않아요. 문서도 디스크 고장·공간 부족·재시도 한도에 따른 손실 가능성을 설명해요. 그러므로 “Collector가 있으니 SDK 큐는 신경 쓰지 않아도 된다”는 선택은 안전하지 않아요.

Kafka를 가운데 두는 방식은 또 다른 계층의 선택이에요. 같은 문서는 Collector 사이에 Kafka 같은 메시지 큐를 둘 수 있다고 설명해요. 여기서 Kafka는 SpanProcessor 교체품이 아니라 데이터를 전달받은 뒤 보관하고 다음 소비자가 읽게 하는 별도 브로커예요. SDK→Collector→Kafka→소비 Collector 같은 구성이면 앞의 SDK 큐와 전송 실패 지점도 그대로 남아요.

Kafka 4.1의 producer 문서에서 acks=all은 당시의 in-sync replica 집합의 확인을 기다리는 설정이에요. 이 확인도 최종 트레이스 저장소가 저장했다는 뜻은 아니에요. 같은 문서의 buffer.memory 설명은 producer 버퍼가 부족하면 max.block.ms 동안 기다린 뒤 실패할 수 있다고 해요. SDK의 queue.offer() 폐기와 달리 호출 지연을 허용하는 지점이 있으니, “둘 다 비동기 큐니까 같은 동작”이라고 비교하면 안 됩니다.

여기의 버퍼 설정은 Kafka Java producer를 비교한 예예요. Collector의 Kafka exporter가 같은 Java 클라이언트나 옵션을 쓴다는 뜻은 아닙니다. 브로커의 수신 확인과 클라이언트 버퍼 정책을 구분하려고 문서 버전을 4.1로 고정했으며, 새 설치에 이 버전을 권장하는 것은 아니에요.

선택 기준은 보장하려는 구간이에요. 짧은 원격 지연 동안 앱의 스팬 전송을 분리하려면 SDK 배치 큐를 먼저 봅니다. Collector 재시작 후에도 이미 수신한 데이터를 다시 보내야 한다면 디스크 전송 큐가 후보예요. 수집 계층 사이의 보관과 소비 분리가 필요하다면 Kafka가 후보가 될 수 있지만, 브로커의 저장·복제·보존 기간·소비 상태라는 운영 책임이 추가돼요. 어떤 구조도 아직 전달받지 못한 앞 단계의 기록을 복구하지는 못해요.

8. 유실을 확인하는 메트릭도 같은 보장일까

큐 포화가 있어도 조회 화면에 나타나는 것은 “일부 스팬이 없다”는 결과예요. 왜 없는지 알아보려면 처리기 자체의 상태가 필요해요. 앞의 addSpan()에는 큐 포화와 종료 후 전달을 구분하는 계측 호출이 있고, 전송 전에 폐기 개수를 경고 로그로 남기는 경로도 있어요. 하지만 코드에 카운터 호출이 있다고 실제 메트릭이 자동으로 수집된다고 단정할 수는 없습니다.

이 버전의 빌더 기본값은 MeterProvider::noop이고 내부 계측 방식은 LEGACY예요. 직접 빌더로 구성했다면 MeterProvider 연결을 먼저 확인해야 해요. 에이전트나 자동 설정이 어떤 값을 주는지는 또 별도 구성이에요. 모든 사용 방식에서 아래 표준 이름이 그대로 나온다고 가정하면 안 됩니다.

표준 계측 구현을 사용할 때 확인할 이름 otel.sdk.processor.span.queue.size otel.sdk.processor.span.queue.capacity otel.sdk.processor.span.processed processed에 붙는 폐기 이유 error.type = queue_full error.type = already_shutdown

표준 계측 구현은 위 두 폐기 이유를 구분하고 큐 크기·용량도 기록해요. 반면 기존 계측 구현은 processedSpans와 queueSize를 사용하고 종료 후 폐기 수나 용량 메트릭을 같은 방식으로 제공하지 않아요. 메트릭이 없다는 사실을 폐기가 0이라는 증거로 읽어서는 안 돼요.

마지막으로 finishSpans()를 호출하는 시점도 중요해요. 캡처의 358줄은 exporter 결과가 나오기 전입니다. 그러므로 오류 속성이 없는 처리 개수를 최종 백엔드 저장 성공 개수로 대입할 수 없어요. 큐 길이가 줄었다는 사실도 작업 스레드가 배치로 옮겼다는 의미일 수 있지 원격 저장 완료를 의미하지는 않아요.

코드를 읽고 나니 유실을 확인할 질문도 나뉘어요. SDK 큐 포화인지, exporter 실패인지, 종료 시점인지 먼저 구분하고 Collector 큐와 재시도 상태를 이어서 봐야 해요. 전송 경로가 여러 단계라면 손실과 복구의 범위도 단계별로 확인해야 합니다.

💡 이번에 확인한 범위
공개 Java SDK의 호출 경로와 공식 문서를 대조하고, 메모리 exporter의 첫 완료를 제어해 큐 포화를 실행해 확인했어요. 유입·처리 속도의 식은 가정을 둔 설명이며 성능 측정값이 아니에요. exporter별 재시도, 강제 종료 시 유실량, 큐 크기에 따른 지연과 메모리는 실측하지 않았어요.

소스 기준: OpenTelemetry Java v1.67.0. 코드 이미지는 해당 공개 소스를 렌더링했어요.

✍️ 오늘의 요약
스팬 종료, 큐 보관, 전송 시도, 외부 저장 완료는 서로 다른 단계예요.

BatchSpanProcessor는 크기가 제한된 큐와 별도 작업 스레드를 사용하고, 큐 포화 시에는 새 스팬을 버려요. Collector의 복구 기능도 SDK가 이미 버린 기록까지 되살릴 수는 없습니다.
