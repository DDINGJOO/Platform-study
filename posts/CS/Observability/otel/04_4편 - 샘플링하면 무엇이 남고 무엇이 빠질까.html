요청이 시작할 때는 정상으로 보였는데, 마지막 데이터베이스 호출에서 실패했다고 가정해 볼게요. 수집 비율을 낮춘 뒤라면 이 요청의 트레이스가 없을 수 있습니다. 나중에 에러라는 사실을 알았다고 해서, 시작할 때 기록하지 않은 내용을 되돌릴 수 있을까요?

샘플링은 수집량을 줄이는 설정인 동시에, 어느 시점에 가진 정보로 무엇을 남길지 결정하는 일이에요. “10%만 보내자”는 한 문장 안에도 생성 시점의 기록 결정, 부모 정책, 종료 후 전송 필터, Collector의 선택이 섞일 수 있습니다. 같은 수집량이라도 이 선택들을 어디에 놓았는지에 따라 애플리케이션 비용과 실패를 찾을 가능성이 달라져요.

OpenTelemetry Java v1.67.0의 스팬 생성부터 프로세서 전달까지 따라가고, Collector tail sampling과 Jaeger의 원격·적응형 샘플링을 같은 질문으로 비교해 볼게요. 공개 소스 분석에 더해, 동일 버전의 공개 Maven 아티팩트로 부모 정책과 RECORD_ONLY를 최소 실행해 확인했어요. 뒤의 확률 계산은 가정에 따른 계산이며, 실제 서비스 부하나 수집 성능을 측정한 결과는 아닙니다.

1. 요청이 끝나기 전에 결정하면 무엇을 모를까

모든 스팬을 기록하고 보내면 처리량에 따라 데이터도 늘어나요. 스팬은 요청이나 작업 한 구간의 시작·종료와 속성을 담고, 같은 trace ID로 연결된 스팬들이 트레이스를 이룹니다. 수집량을 줄이려면 이들 중 일부를 선택해야 해요.

📖 용어: 샘플러 (sampler)
새 스팬을 만들 때 기록 여부와 sampled 플래그를 결정하는 SDK 구성 요소예요. 단순히 전송 직전에 일부 데이터를 지우는 기능만을 뜻하지는 않습니다.

공식 문서의 head sampling은 가능한 이른 시점에 결정하는 방식이에요. 이 글에서 읽는 Java 샘플러도 스팬 생성 시점에 호출됩니다. 아직 끝나지 않은 자식 호출의 최종 에러나 전체 소요 시간은 이 시점의 입력에 없어요.

📖 용어: 헤드 샘플링 (head sampling)
트레이스 전체 결과를 기다리지 않고 이른 시점에 선택하는 방식이에요. 미리 아는 속성은 쓸 수 있지만, 뒤에 발생할 실패까지 보고 결정하지는 못합니다.

그래서 수집 비율이 충분해 보인다는 판단과 모든 실패 요청을 보관한다는 보장은 달라요. 드문 실패를 반드시 남겨야 한다면, 비율 하나만으로 그 요구를 충족한다고 보면 안 됩니다.

그림 1. 일찍 선택할수록 나중에 생기는 정보는 판단에 쓸 수 없어요

2. 샘플러는 스팬 생성 경로의 어디에 있을까

샘플러 함수만 보면 false를 반환하는 필터로 생각하기 쉬워요. 하지만 실제 호출자는 이미 보내려던 스팬을 버리는 것이 아니라, 어떤 스팬 객체를 만들지 결정합니다. SdkSpanBuilder.startSpan 182~228행을 보면 먼저 부모 문맥을 얻고, 유효한 부모가 있으면 그 trace ID를 사용해요. 부모가 없으면 새 ID를 만듭니다. 이 ID와 스팬 이름·종류·초기 속성·링크가 shouldSample의 입력이에요.

이 경로에는 전제가 있어요. 같은 버전의 SdkTracerProvider는 등록된 프로세서가 없으면 no-op TracerBuilder를 반환하는 최적화를 합니다. SDK 객체와 샘플러를 만들었다는 사실만으로 이 경로가 실행되거나 기록 스팬이 생긴다고 단정하지 않아요. 아래는 실제 SDK tracer가 생성되어 스팬을 시작하는 경우를 읽는 것입니다.

SdkSpanBuilder.startSpan() 1. 부모 문맥과 trace ID를 결정해요. 2. Sampler.shouldSample(부모, ID, 이름, 종류, 초기 속성, 링크)을 호출해요. 3. SamplingResult에서 결정·tracestate·추가 속성을 받아요. 4. 결정으로 sampled 플래그와 기록 여부를 정해요. 5. DROP이면 비기록 스팬, 나머지는 SdkSpan을 만들어요. 6. 기록 스팬이 끝나면 필요한 SpanProcessor.onEnd를 호출해요.

위 순서는 219~277행과 SdkSpan.endInternal을 읽어 정리한 흐름이에요. 원문을 그대로 옮긴 코드나 실행 로그는 아닙니다. DROP도 문맥을 가진 비기록 스팬은 반환하므로, “스팬이 null이다”나 “trace ID도 없다”는 뜻이 아니에요.

호출 시점은 정책의 표현력을 제한해요. 예를 들어 스팬을 시작한 뒤에야 라우터가 HTTP 경로를 알아내서 속성을 추가한다면, 그 속성은 처음 shouldSample에 넘긴 초기 속성에 없을 수 있어요. 샘플러에 경로별 규칙을 작성했더라도 계측 코드가 언제 이름과 속성을 제공하는지 확인해야 합니다. 최종 예외·최종 상태·최종 지연은 더 분명하게 나중 정보예요.

반대로 시작 전에 이미 아는 요청 종류나 신뢰할 수 있는 초기 속성을 쓰는 선택은 가능해요. 문제는 head sampling이 “아무 정보도 못 쓴다”가 아니라 결정 당시 주어진 정보만 쓸 수 있다는 데 있습니다. 종료 시점에 recordException을 호출해도, 비기록 스팬이 과거 이벤트를 보관해 두었다가 기록 스팬으로 바뀌지는 않아요.

📖 용어: tracestate
trace ID와 별도로 전파할 수 있는 추적 상태예요. 샘플러가 돌려주는 결과는 단순한 참·거짓뿐 아니라, 다음 구성 요소가 해석할 상태와 추가 속성도 포함할 수 있습니다.

3. 비율 샘플러는 실패 대신 ID를 읽어요

TraceIdRatioBasedSampler의 입력에는 이름·속성·부모 문맥도 있지만, 이 버전의 실제 반환식은 trace ID에서 읽은 값과 임계값을 비교해요. 37~53행에서 ratio를 임계값으로 바꾸고, 111~112행에서 ID 뒤쪽 64비트를 읽습니다.

코드 캡처 1. 매번 난수를 새로 뽑는 대신 이 버전은 trace ID와 임계값을 비교해요

원문 61~80행에서 77행의 비교가 참이면 recordAndSample, 거짓이면 drop 결과입니다. 성공·실패를 예측하는 조건은 없어요.

ID의 해당 부분이 무작위로 분포한다는 전제에서 원하는 비율을 기대하는 구조예요. 열 번 요청하면 그중 정확히 한 번을 고르는 식의 순번 제어는 아닙니다. 또 Java API 문서는 구체 알고리즘을 계약으로 고정하지 않아요. 같은 ID가 언어·버전을 넘어 언제나 같은 결과를 낸다고 확대하면 안 됩니다.

여기서 “스팬마다 10%를 새로 뽑는다”는 해석도 맞지 않아요. 이 구현과 같은 ratio에 같은 trace ID를 넣으면 같은 비교를 반복합니다. 자식 스팬은 부모와 trace ID를 공유하므로, 매번 독립 난수를 뽑는 샘플러와 다르게 동작해요. 반면 이 구현은 부모의 sampled 플래그 자체를 결정 조건으로 쓰지 않으니, 서로 다른 ratio를 쓰는 서비스의 결정을 자동으로 따르지는 않습니다.

예를 들어 앞 서비스의 비율을 높이고 뒤 서비스의 비율을 낮추면, 앞에서 선택된 ID가 뒤의 더 좁은 선택 범위에는 들지 않을 수 있어요. 뒤에서 비율을 올린다고 해도 이미 앞에서 기록하지 않은 스팬은 생겨나지 않습니다. 그래서 같은 ID를 활용한다는 사실만으로 완전한 트레이스가 보장되지는 않아요. 부모 선택을 따르게 할지는 별도 정책이고, 언어·버전 간 구현 일치 여부도 별도 조건입니다.

4. 부모 결정은 다섯 가지 경우로 나뉘어요

서비스마다 자기 기준만으로 결정하면 부모를 남겼는데 자식은 없는 모양이 생길 수 있어요. ParentBasedSampler는 유효한 부모가 없을 때의 정책과, 부모가 있을 때의 정책을 나눕니다.

📖 용어: sampled 플래그
스팬 문맥에 포함되는 샘플링 선택 표시예요. 부모의 선택을 다음 스팬에 전달하는 데 쓰지만, 이미 전송이나 저장에 성공했다는 확인은 아닙니다.
코드 캡처 2. 부모 없음, 원격 부모, 로컬 부모에 따라 위임할 샘플러를 골라요

원문 58~76행에서 59행은 부모가 유효하지 않으면 root로 가요. 그 외에는 원격·로컬 여부와 sampled 플래그로 위임 대상을 선택합니다.

여기서 원격 부모는 다른 프로세스에서 전달된 정보를 추출해 원격으로 표시한 부모예요. 단순히 다른 스레드에서 실행됐다는 뜻은 아닙니다. 기본 위임 설정은 sampled 부모라면 alwaysOn, 아니라면 alwaysOff예요. builder로 각 위임 정책을 바꿀 수도 있으므로, ParentBased라는 이름만으로 모든 구성을 단정하면 안 됩니다.

// v1.67.0 기존 API의 조합 예시예요. 실행 결과가 아닙니다. Sampler sampler = Sampler.parentBased( Sampler.traceIdRatioBased(0.1));

이 조합은 유효한 부모가 없을 때 비율 샘플러를 쓰고, 부모가 있으면 기본 부모 정책을 사용해요. 샘플링 선택을 이어 가는 설정이지, 문맥 유실이나 전송 실패까지 없애는 설정은 아닙니다.

유효한 부모 원격 여부 부모 sampled 기본 위임 없음 해당 없음 해당 없음 root 있음 remote true alwaysOn 있음 remote false alwaysOff 있음 local true alwaysOn 있음 local false alwaysOff

이 표의 기본값은 root 비율을 모든 자식에 다시 곱하지 않아요. root가 10%라는 설정에서 부모가 sampled인 자식도 매번 10%만 남는다면, 세 단계의 요청이 완전하게 남을 확률을 0.1의 세제곱으로 계산하게 될 거예요. 하지만 위 기본 ParentBased 구성은 그런 독립 선택을 하지 않습니다. root에서 선택하고 이후 기본 위임으로 선택을 따르게 하는 구조예요. 이것은 정책 설명이지, 네트워크 손실까지 포함한 실제 완전 수집률 계산은 아닙니다.

반례도 있어요. 원격 부모가 sampled가 아니더라도 특정 서비스에서 새 문제를 추적하려고 remoteParentNotSampled를 다르게 구성할 수 있습니다. 그러면 뒤쪽 일부 스팬만 남을 수 있어요. SDK는 그 선택을 허용하지만, 그 결과를 완전한 요청 트레이스로 해석할 책임까지 대신 지지는 않습니다.

부모 문맥이 유실된 경우는 또 달라요. 실제로는 한 요청의 연속이어도 유효한 부모를 못 찾으면 표의 첫 줄, root 정책으로 들어갑니다. 수집 비율만 조사해서는 “같은 요청의 일부가 없다”는 문제를 설명하지 못하는 이유예요. 먼저 trace ID가 유지됐는지, 원격 표시가 어떻게 붙었는지, 어떤 분기의 위임 설정이 실행됐는지 순서대로 봐야 합니다.

이 기본값을 공개 아티팩트로 실행해서도 확인했어요. Java 1.67.0 JAR를 고정 해시로 검증하고, 자동 구성 없이 SdkTracerProvider.builder()를 사용했습니다. 앞의 10% root 예제와 달리 이 실험은 프로그램 기본 sampler를 사용해요. 프로세서가 없으면 no-op이 되는 최적화를 피하려고, 종료 호출만 세는 프로세서를 연결했습니다. 원격 부모는 실제 네트워크 호출이 아니라 유효한 SpanContext를 원격으로 표시해 직접 만들었어요.

sampling default-root recording=true sampled=true sampling default-remote-sampled-parent recording=true sampled=true sampling default-remote-unsampled-parent recording=false sampled=false sampling always-on-remote-unsampled-parent recording=true sampled=true sampling always-off-remote-sampled-parent recording=false sampled=false

labs/observability/otel-runtime-probes/actual.txt에서 샘플링 출력 다섯 줄을 그대로 가져왔어요. 기본 설정에서는 root와 sampled 부모의 자식을 기록하고, unsampled 부모의 자식은 기록하지 않았습니다. 마지막 두 줄은 ParentBased의 위임 설정을 바꾼 실험이 아니라, provider의 sampler 자체를 alwaysOn 또는 alwaysOff로 바꾼 결과예요. 부모의 표시와 관계없이 결과가 바뀌므로 “어떤 sampler라도 부모 결정을 따른다”는 일반화의 반례입니다.

실험 환경과 5회 반복 결과는 같은 디렉터리의 validation.json, 구성은 RuntimeProbes.java에 남겼어요. OpenJDK 25.0.3에서 Java 11 대상으로 컴파일했고, 반복 출력은 동일했습니다. 로컬·원격 모든 분기의 조합이나 실제 서비스 간 전파까지 실행한 것은 아니므로, 확인한 다섯 사례를 넘어 완전한 통합 검증이라고 하지는 않겠습니다.

5. 기록, sampled, export는 서로 다른 단계예요

여기서 “남긴다”는 말을 나눠야 해요. SDK 사양의 SamplingResult는 기록 여부와 sampled 여부를 별도로 정의합니다. 비율 샘플러는 두 결과만 쓰지만, 샘플러 인터페이스 전체에는 세 가지 결정이 있어요.

📖 용어: RECORD_ONLY
속성·이벤트를 기록할 수 있지만 sampled 플래그는 설정하지 않는 결정이에요. “기록 가능하다”와 “샘플링 대상으로 선택됐다”를 분리합니다.
결정 isRecording sampled 플래그 DROP false false RECORD_ONLY true false RECORD_AND_SAMPLE true true

이 표는 스팬 생성 시점의 기록과 플래그를 비교한 것이지, 백엔드에 도착한 결과표가 아니에요. 실제 builder는 결정으로 SpanContext의 sampled 비트를 설정하고, DROP이면 그 문맥을 감싼 비기록 스팬을 반환해요. RECORD_ONLY와 RECORD_AND_SAMPLE은 SdkSpan을 생성하고, 샘플러가 추가한 속성도 합칩니다. 즉 기록 가능성과 전파하는 선택 표시는 처음부터 다른 값이에요.

이후 기록 스팬이 끝나면 필요한 프로세서의 onEnd가 호출됩니다. 여기서 프로세서는 종료한 스팬을 받아 집계하거나 전송하도록 구성한 처리 요소예요. 모든 프로세서가 동일한 전송 정책을 갖지는 않습니다. RECORD_ONLY도 기록 스팬이므로 프로세서가 관찰할 수 있지만, 그것이 곧 exporter로 전달된다는 뜻은 아니에요.

이 버전 BatchSpanProcessor.onEnd는 exportUnsampledSpans || span.getSpanContext().isSampled() 조건을 통과한 스팬만 worker에 추가해요. builder 기본값은 exportUnsampledSpans가 false이므로 기본 배치 전송에서는 RECORD_ONLY가 제외됩니다. 이 옵션을 켜거나 다른 프로세서를 쓰면 결론이 달라질 수 있어요.

이 차이가 중요한 반례는 “트레이스는 적게 보내되 요청 수를 로컬에서 집계하고 싶다”는 요구예요. 기록을 아예 하지 않는 DROP과, 기록한 내용을 특정 프로세서가 활용하되 기본 전송에서는 제외하는 RECORD_ONLY는 비용도 사용 가능 정보도 달라요. 다만 RECORD_ONLY를 선택한 순간 별도 메트릭이 자동 생성되지는 않습니다. 실제로 집계하는 구성 요소를 두어야 하고, 기록 비용은 이미 들고 있다는 점도 확인해야 해요.

전송 여부가 별도라는 점은 사용자 정의 sampler가 항상 SamplingResult.recordOnly()를 반환하도록 만들어 확인했습니다. 이 실행에는 앞서 소스로 읽은 배치 프로세서가 아니라 SimpleSpanProcessor와 메모리 exporter를 사용했어요. 종료 후 forceFlush를 기다리고 exporter가 받은 스팬 이름의 수를 검사했습니다.

sampling record-only include-unsampled=false recording=true sampled=false exported=0 sampling record-only include-unsampled=true recording=true sampled=false exported=1 sampling PASS

같은 실제 실행 로그에서 가져온 세 줄이에요. include-unsampled는 실험이 setExportUnsampledSpans에 넘긴 값을 출력한 이름입니다. 기록 상태와 sampled 플래그는 같은데, 이 설정만 바꾸자 메모리 exporter에 도착한 수가 0에서 1로 바뀌었어요. 메모리 exporter의 콜백을 확인한 결과이므로 실제 OTLP 네트워크 전송이나 백엔드 영구 저장까지 확인했다는 뜻은 아닙니다.

💡 실무에서는 선택과 유실을 나눠 확인해요
트레이스가 없을 때는 샘플링 정책으로 제외됐는지, 문맥이 끊겼는지, 큐나 전송에서 손실됐는지 구분해야 해요. sampled 플래그 하나가 전체 수집 경로의 성공 여부를 설명하지는 않습니다.

6. 10%라면 드문 실패를 얼마나 놓칠까

비율만 보고 “충분히 많이 보냈다”고 말할 수 있는지 계산해 볼게요. 여기서는 서로 다른 요청의 trace ID가 독립적으로 충분히 무작위이고, 실패 여부와 샘플링 선택이 독립이며, 각 트레이스가 확률 p로 선택된다고 가정합니다. 전송 손실은 없다고 놓을게요. 이 조건은 설명용 확률 모델이지, 앞의 유한 정수 비교가 모든 입력에서 정확한 베르누이 시행을 보장한다는 주장은 아닙니다.

이미 n건의 실패가 발생했다는 조건에서, 각각의 실패를 선택하지 않을 확률은 1-p예요. 서로 독립이라는 가정 아래 이 실패들을 한 건도 선택하지 못할 확률은 다음과 같습니다.

가정: 트레이스별 선택 확률 p = 0.1, 실패와 선택은 독립 P(실패 n건을 전부 놓침 | 실패 n건 발생) = (1-p)^n n = 1 → 0.9 = 90% n = 5 → 0.9^5 ≈ 59.05% n = 20 → 0.9^20 ≈ 12.16% n = 50 → 0.9^50 ≈ 0.52%

입력 전체가 많아도 특정 원인의 실패가 한 번뿐이면, 10% 선택으로 그 한 번을 놓칠 확률은 이 모델에서 90%예요. “하루 요청이 많다”는 사실과 “하루 한 번의 희귀 실패를 확보한다”는 목표는 같지 않습니다. 반대로 자주 발생하는 동일 유형의 원인을 몇 건만 확인하면 되는 조사라면, 낮은 비율이 합리적일 수 있어요. 어떤 질문에 답할 데이터가 필요한지에 따라 판단이 달라집니다.

이 계산을 스팬 수에 그대로 적용하면 안 돼요. 기본 ParentBased에서 같은 트레이스의 자식 선택은 부모 선택과 연결되어 있으니, 스팬을 독립 표본으로 셌다는 가정이 깨집니다. 실패가 특정 요청 종류에 집중되어 있거나 사용자 정의 ID와 상관이 있어도 단순 모델은 맞지 않을 수 있어요. 낮은 비율이 항상 나쁘다는 결론이 아니라, 비율의 목적을 평균 대표성과 희귀 사례 보존으로 나눠야 한다는 결론입니다.

7. Tail은 최종 결과를 기다리는 대신 상태를 유지해요

최종 에러나 지연을 보고 고르려면 tail sampling을 고려할 수 있어요. 지금까지 읽은 것은 Java SDK의 생성 시점 결정이고, tail sampling은 Collector의 별도 처리 단계 등에서 구성해요. 앞의 SDK Sampler만 바꾸면 같은 동작을 얻는 것은 아닙니다. 여러 스팬이 도착한 뒤 그 정보를 기준으로 결정하므로, 시작 시점에는 없던 조건을 쓸 수 있습니다.

📖 용어: 테일 샘플링 (tail sampling)
도착한 트레이스의 스팬들을 모아 더 늦게 선택하는 방식이에요. 기다리는 동안 상태를 저장하고 처리할 자원이 필요하며, 들어오지 않은 정보까지 알 수는 없습니다.
그림 2. 더 많은 결과를 보고 고르려면 데이터를 먼저 받아 보관해야 해요

여기서는 Collector Contrib의 고정 커밋 README가 설명하는 기본 trace-complete 전략을 기준으로 읽을게요. 이 전략은 모은 데이터를 타이머 경로에서 평가하며, 기다리는 동안 스팬을 상태로 보관해요. 같은 문서에는 도착한 배치를 기준으로 더 일찍 결정하는 span-ingest도 있으니, “tail이면 언제나 완전한 전체 트레이스가 끝난 뒤 결정한다”고 일반화하지는 않겠습니다.

기다리는 시간을 늘리면 늦은 결과를 볼 가능성은 높아질 수 있지만, 그동안 유지할 트레이스도 많아져요. 용량을 넘기면 선택 전에 데이터가 제거될 수 있다고 문서는 설명합니다. 입력률이 일정하다고 가정할 때 동시 대기 트레이스 수가 대략 “초당 새 trace 수 × 기다리는 시간”에 비례한다는 계산은 용량을 생각하는 출발점이지만, 큰 트레이스·캐시·내부 구조까지 포함한 실제 메모리 사용량의 측정값은 아니에요.

분산 배치도 상태와 연결돼요. 같은 trace의 스팬들은 같은 Collector 인스턴스로 가야 유효한 판단을 할 수 있습니다. 일반적인 부하 분산으로 스팬들을 여러 인스턴스에 나눠 보내면, 한쪽은 정상 스팬만 보고 다른 쪽은 에러 스팬만 볼 수 있어요. 프로세서 옵션만 추가하는 것으로 끝나지 않고, trace ID를 고려한 라우팅과 확장 방식을 같이 검토해야 하는 이유입니다.

선택한 뒤 도착하는 스팬도 있어요. 해당 README의 늦은 스팬 처리를 보면, 결정이 아직 남아 있으면 늦은 스팬은 그 결정을 따르고 그 정보로 과거 결정을 다시 바꾸지는 않아요. 결정이 제거됐고 별도 캐시도 없으면 처음 보는 trace인 것처럼 처리될 수 있습니다. 선택 결정을 얼마나 기억할지까지 설정과 자원 사용의 문제예요.

📖 용어: 결정 캐시 (decision cache)
스팬 본문을 해제한 뒤에도 어떤 trace를 남길지 결정한 정보를 기억하는 공간이에요. 늦게 도착한 스팬에 같은 결정을 적용하는 데 쓰지만, 기다리기 전에 없어진 스팬을 복원하는 공간은 아닙니다.

tail이 판단하는 범위는 자신에게 실제로 도착한 데이터예요. 앞 SDK에서 10%만 기록하고 tail에서 그중 모든 에러를 남기면, 결과는 “도착한 10% 안의 에러를 남김”이지 “전체 서비스의 모든 에러를 남김”이 아닙니다. head와 tail을 함께 쓰는 것은 가능하지만, 앞 단계가 어떤 정보를 없앴는지를 뒤의 규칙으로 취소할 수는 없어요.

또 tail에서 비율 조건만 사용할 예정이라면 기다림이 필요한지도 물어야 합니다. 같은 README의 확률 프로세서 비교는 trace ID만으로 정하는 정책은 더 많은 스팬이 도착해도 결정이 달라지지 않는다고 설명해요. 이미 다른 조건 때문에 tail을 운영한다면 정책을 합칠 수 있지만, 비율 선택 하나를 위해 상태와 대기를 추가하는 선택은 따로 검토할 가치가 있습니다.

8. Jaeger의 원격·적응형 정책은 언제 결정할까

“Collector tail sampling과 Jaeger 중 무엇이 더 좋을까”라는 비교는 범위가 맞지 않아요. Jaeger는 저장·조회뿐 아니라 여러 샘플링 구성을 제공하고, Java SDK도 여러 정책을 사용할 수 있습니다. 따라서 여기서는 제품 전체가 아니라 선택을 언제·어디서 하고, 어떤 정보를 쓰는가로 비교합니다.

Jaeger 2.22의 remote sampling은 SDK가 백엔드에서 정책을 받아 쓰는 head 방식이에요. 정책을 운영자가 한곳에서 바꾸는 것과, 각 요청의 최종 결과를 기다린 뒤 고르는 것은 다른 일입니다. 원격이라는 단어도 앞의 remote parent와 뜻이 달라요. 여기서는 정책 설정을 외부에서 받아 온다는 의미예요.

📖 용어: 적응형 샘플링 (adaptive sampling)
관측한 트래픽에 따라 선택 확률을 다시 계산하는 방식이에요. Jaeger의 해당 기능은 서비스·엔드포인트별 목표 샘플 수에 맞추도록 정책을 조정하며, 이미 빠진 실패 trace를 사후 복구하는 기능은 아닙니다.

같은 문서의 adaptive sampling은 받은 스팬에서 트래픽을 관측해 target_samples_per_second에 맞는 확률을 계산하고, 이를 원격 정책으로 제공해요. 목표는 초당 확보할 트레이스 수를 관리하는 쪽에 가깝습니다. 실패를 전부 보관한다는 정책과 같지도 않고, 각 trace의 바이트 크기가 다른데 네트워크 바이트가 일정하게 고정된다는 보장도 아닙니다.

비교 기준 SDK 비율 + 기본 ParentBased Collector tail Jaeger remote/adaptive 개별 trace 선택 시점 생성할 때 수신 데이터로 판단할 때 SDK가 생성할 때 활용 정보 초기 문맥·정책·ID 도착한 스팬·상태·지연 초기 정보 + 배포받은 정책 주된 관리 대상 비율과 부모 선택의 일관성 내용에 따른 보존 조건 정책 배포·목표 샘플 수 추가 운영 조건 SDK 설정·문맥 전파 상태·대기·trace별 라우팅 정책 서버·갱신·관측 상태

표는 기본 구성을 비교한 것이며 모든 옵션을 열거한 표는 아니에요. 예를 들어 트래픽이 많이 다른 엔드포인트에서 일정 수준의 사례를 확보하고 싶은데, 매번 SDK 설정을 재배포하기는 어렵다면 원격·적응형 정책을 검토할 수 있습니다. 하지만 종료 직전의 오류를 조건으로 보관하고 싶다면, 비율 갱신만으로는 그 요청의 결과를 알 수 없어요. 받은 내용으로 선택하는 tail 정책과 목적을 구분해야 합니다.

반대로 애플리케이션이 기록하고 보내는 비용부터 줄여야 한다면, 뒤쪽 tail에서 버리기만 해서는 앞단 기록·전송 비용은 남아요. SDK head 정책을 쓰되 희귀 오류를 놓칠 수 있다는 조건을 받아들이거나, 별도 오류 로그·메트릭 경로를 함께 설계하는 쪽이 맞을 수 있습니다. 공식 Jaeger 문서도 OTel SDK의 head 기능과 tail sampling processor를 함께 설명해요. OTel과 Jaeger를 서로 배타적인 기술로 고를 문제는 아닙니다.

9. 선택된 스팬으로 만든 오류율은 전체 오류율일까

에러를 우선 보관하는 정책은 원인 분석에 유용하지만, 그 결과를 그대로 전체 트래픽 통계로 읽으면 다른 문제가 생겨요. 설명을 위해 요청 하나가 스팬 하나로 기록되고 전체 요청은 100건, 그중 실패는 1건이라고 가정해 볼게요. tail 정책을 통과한 결과에 성공 9건과 실패 1건만 남았다면, 받은 스팬에서 단순 계산한 실패 비율은 10%예요. 실제 입력의 실패 비율 1%와 다릅니다.

이 숫자는 어떤 정책에서 반드시 나온다는 실측값이 아니라, 선택과 통계의 관계를 보여 주는 반례예요. 실패를 더 잘 남기는 정책은 성공과 실패의 포함 확률이 달라질 수 있으므로, 받은 집합에서 실패 수를 전체 스팬 수로 나눈 값을 원래 요청의 오류율로 단정할 수 없습니다. 모든 스팬에 무작정 10을 곱하는 보정도, 실제로 모든 요청이 같은 10% 확률로 들어온 것이 아니라면 정당화되지 않아요.

따라서 trace에서 메트릭을 만들려면 어느 선택 단계의 앞과 뒤에서 집계했는가를 확인해야 해요. 처음부터 별도 요청 메트릭을 기록한 것인지, 기록된 스팬을 SDK 내부에서 집계한 것인지, head 선택이 끝나 Collector에 도착한 스팬만 집계한 것인지, tail 선택까지 끝난 결과를 집계한 것인지가 다릅니다. Collector에서 tail 앞에 집계기를 두어도, 앞 SDK에서 이미 DROP한 요청까지 자동으로 포함되지는 않습니다.

이 구분은 RECORD_ONLY의 의미와도 연결돼요. 모든 요청에 기록 비용을 들여 로컬 집계에 활용하고 전송만 줄이는 방식과, 일찍 DROP해서 그 비용까지 줄이는 방식은 얻는 데이터가 달라요. 전체 요청의 비율을 설명할 데이터가 필요한지, 실패 원인 몇 건을 읽을 trace가 필요한지를 분리하면 서로 다른 경로를 두는 이유가 명확해집니다.

10. ProbabilitySampler 전환이 왜 호환성 문제일까

지금까지 분석한 Java 클래스는 존재하는 기존 구현이에요. 하지만 2026-10-21 확인한 현재 TraceIdRatioBased 사양은 이 샘플러를 deprecated로 표시합니다. 원래 동작은 최소 2027-01-01까지 제거·변경하지 않도록 요구해요. 이는 그날 모든 언어에서 API가 없어지거나, 모든 배포 환경이 동시에 전환된다는 일정표는 아닙니다.

핵심은 이름보다 공유 규칙이에요. Java API 자체가 구체 ID 알고리즘을 보장하지 않았는데, 여러 언어가 이름과 비율만 같다는 이유로 독립적으로 선택하면 같은 trace에서 다른 결과가 날 수 있어요. 새 ProbabilitySampler 문서는 56비트 무작위성, 거절 임계값 비교, tracestate의 임계값 전달을 구체적으로 설명합니다. 이 절은 확인 시점에 Development 상태이며, 여기서 읽은 Java 기존 클래스와 같은 구현이라고 섞어 설명하지 않겠습니다.

앞의 구현은 절댓값과 상한을 비교하지만, 새 문서는 무작위 값이 거절 임계값 이상인지 비교해요. 둘 다 “10%”라고 설정하더라도 동일한 ID 집합을 선택한다는 뜻은 아닙니다. 특히 새 사양은 trace ID 무작위성을 확인할 플래그와, 오래된 전파 구현을 거쳤을 때의 호환 경고도 다룹니다. 단순히 클래스 이름을 바꾸고 끝낼 문제가 아니라 ID 생성·문맥 전파·다른 SDK의 정책을 함께 보는 문제예요.

Java 1.67.0 안에서도 안정 API와 실험 API를 구별해야 해요. 앞서 읽은 core의 Sampler 팩터리와 별도로, incubator 모듈의 ComposableSampler.probability()와 이를 SDK Sampler로 감싸는 CompositeSampler.wrap()이 존재합니다. 따라서 “Java에는 새 방식이 없다”도, “기존 안정 팩터리 이름만 바꾸면 된다”도 맞지 않아요. 여기서는 그 실험 API의 전환·호환 동작을 실행 검증하지 않았으므로, 사용 예제로 대신 제시하지는 않겠습니다.

⚠️ 기존 코드 분석을 최신 설정 예제로 복사하지 않아요
위 Java 예제는 v1.67.0의 동작을 설명하기 위한 조합이에요. 새 배포의 권장 API와 지원 상태는 사용하는 SDK 버전에서 다시 확인해야 합니다. 사양의 전환 설명만으로 특정 Java 버전에 새 구현이 이미 들어 있다고 가정하지 않아요.

11. 남기려는 질문부터 정한 뒤 위치를 골라요

샘플링 정책을 검토할 때는 먼저 “전체 비율을 추정하려는가”, “희귀 실패의 구체 내용을 반드시 보려는가”, “특정 엔드포인트의 사례 수를 확보하려는가”를 나눠야 해요. 이 질문들은 같은 비율 설정으로 모두 충족되지 않을 수 있습니다. 그다음 시작 시점에 필요한 속성이 있는지, 부모 선택을 어떻게 이어 갈지, 뒤쪽 선택에 보낼 데이터가 실제로 기록·전송되는지를 봅니다.

Collector tail을 넣는다면 같은 trace를 같은 인스턴스로 모을 수 있는지, 오래 걸린 요청의 늦은 스팬을 어느 범위까지 기다리고 기억할지도 확인해야 해요. Jaeger 원격 정책을 쓴다면 정책을 어디서 만들고 SDK가 언제 갱신하는지를 살펴봐야 합니다. 어떤 방식이든 sampled 플래그는 영구 저장 확인이 아니므로, 선택 정책으로 제외된 양과 처리 경로에서 잃은 양도 나눠 관찰해야 해요.

여기서 확인한 것은 고정 버전의 생성·위임·전송 진입 경로, 최소 실행의 부모 정책과 RECORD_ONLY 결과, 공식 문서의 운영 조건입니다. 실제 수집 비율, 서비스 간 분산 전파, 지연·메모리·처리 비용은 측정하지 않았어요. 설계의 비용을 읽는다는 것은 “정보를 포기했다”로 끝내는 대신, 어떤 정보가 어느 단계에서 빠지고 그 대가로 어떤 비용을 줄였는지 구분하는 일이라고 정리했습니다.

소스 기준: OpenTelemetry Java v1.67.0. 코드 이미지는 해당 공개 소스를 렌더링했어요.

✍️ 오늘의 요약
일찍 결정하면 기록량을 앞에서 줄일 수 있지만, 나중에 발생할 실패는 판단에 쓸 수 없어요.

ParentBased의 기본 정책은 부모의 선택을 이어 가고, tail sampling은 받은 결과를 더 늦게 살펴봐요. 선택 정책과 실제 도착 여부를 구분해야 무엇이 빠졌는지 설명할 수 있습니다.
