결제 API가 HTTP 200을 반환했는데 응답 본문에는 승인 거절이 들어 있다고 가정해 볼게요. HTTP 클라이언트의 요청 시간과 상태 코드를 기록한 스팬만으로 결제가 성공했다고 판단해도 될까요? 통신은 정상적으로 끝났지만 업무 결과는 다를 수 있어요.

Java agent를 붙이면 직접 startSpan()을 쓰지 않은 곳에서도 스팬이 생겨요. 그래서 자동 계측이 프로그램의 모든 실행과 의미를 이해한다고 생각하기 쉬워요. 실제로는 어느 라이브러리의 어떤 메서드를 관찰하고, 그 경계에서 얻은 정보를 어떤 수명으로 기록하는지가 정해져 있어요. 이 조건을 알아야 자동 계측에 맡길 부분과 애플리케이션에서 명시할 부분을 나눌 수 있어요.

Java 자동 계측 v2.32.0의 HTTP Client 구현에서 대상을 고르는 조건과 동기·비동기 작업을 끝내는 경로를 읽어 볼게요.

1. 자동이라는 말에는 지원하는 실행 경계가 들어 있어요

Java agent 공식 소개는 지원하는 라이브러리와 프레임워크에 바이트코드를 동적으로 주입하여 HTTP, 데이터베이스 등의 경계에서 데이터를 수집한다고 설명해요. 애플리케이션 소스에 계측 호출을 직접 추가하지 않아도 된다는 뜻이에요. 모든 메서드의 업무적 중요도를 자동으로 판별한다는 뜻은 아니에요.

📖 용어: 계측 (Instrumentation)
실행 중인 작업의 시작·종료·오류·속성을 관측 데이터로 기록하도록 연결하는 코드예요. agent가 추가한 코드도 계측이고, 개발자가 직접 작성한 스팬 코드도 계측이에요.

이 차이는 수집 범위에서 드러나요. HTTP 계측은 요청 객체와 응답 객체를 받는 지점을 알아요. 반면 그 응답을 읽은 뒤 적립금을 취소하는지, 대체 결제 수단을 선택하는지, 거절을 정상적인 업무 결과로 취급하는지는 애플리케이션이 정해요. 통신 스팬이 정확해도 업무 설명이 충분하지 않을 수 있어요. 이것은 곧바로 계측 버그를 뜻하지 않아요. 처음부터 관찰한 경계가 다른 경우예요.

반대로 지원한다고 명시한 HTTP 호출에서 응답이 올 때까지의 시간을 잘못 기록하거나 애플리케이션 예외를 바꾼다면 다른 문제예요. 관찰 범위의 한계와 구현 결함을 같은 이유로 설명하면 안 돼요. 전자는 필요한 정보를 추가할 계측 위치를 정하는 문제이고, 후자는 지원 계약과 구현을 검증할 문제예요.

2. matcher를 읽으면 무엇을 자동으로 아는지 보여요

이번에 읽는 파일은 HttpClientInstrumentation.java예요. 타입을 고르는 typeMatcher()와 메서드에 advice를 연결하는 transform()이 나란히 있어요. 추상적인 설명보다 이 두 조건을 읽는 편이 자동 계측의 범위를 구체적으로 보여 줘요.

📖 용어: matcher와 advice
matcher는 계측할 클래스와 메서드를 고르는 조건이고, advice는 선택한 메서드의 진입·반환·예외 경계에서 실행하는 코드예요. 이 파일에서는 Byte Buddy의 API로 두 부분을 연결해요.
소스 1. 타입과 메서드 조건으로 send·sendAsync의 계측 대상을 골라요

소스 1 원문: 타입·메서드 선택 조건

타입 조건은 이름이 java.net. 또는 jdk.internal.로 시작하고, java.net.http.HttpClient를 상속하며, 특정 HttpClientFacade 타입은 아닌 경우예요. 따라서 단순히 “HttpClient를 상속한 모든 클래스”라고 요약하면 이름 조건과 제외 조건을 빠뜨리게 돼요. 이 파일 하나를 보고 임의 패키지의 사용자 정의 HTTP 클라이언트까지 동일하게 계측된다고 결론 내릴 수도 없어요.

메서드 조건도 구체적이에요. 동기 호출은 이름이 send이고 public이며 인자가 두 개이고 첫 인자가 HttpRequest인 메서드를 선택해요. 비동기 호출은 public sendAsync이고 첫 인자가 HttpRequest인 메서드를 선택해요. 그리고 둘에 서로 다른 advice를 연결해요. 반환 시점과 작업 완료 시점이 다르기 때문이라는 해석은 뒤의 종료 코드를 읽으면 확인할 수 있어요.

지원 여부를 선언하는 것과 실제로 계측할 대상을 고르는 조건은 구분해야 해요. 런타임의 실제 타입 구조와 메서드 모양을 조건으로 사용해요. 라이브러리나 JDK 구현이 바뀌면 그 조건에 맞는지, advice가 기대하는 인자와 반환값을 여전히 제공하는지 확인해야 해요. “HTTP를 쓴다”라는 사실만으로 모든 HTTP 구현에 이 코드가 적용되지는 않아요.

3. 동기 호출에서도 Context와 Scope의 수명을 관리해요

다음은 동기 send의 수명이에요. 진입 advice는 AdviceScope.start(request)를 호출해요. 이 함수가 현재 Context를 얻고, 시작해도 되는지 확인하고, instrumenter를 시작해요. 새 Context를 현재 실행에 연결한 Scope와 요청 객체도 함께 보관해요.

소스 2. Scope를 닫아 이전 문맥을 복원한 뒤 작업 종료를 기록해요. 원문 80~94행

소스 2 및 호출자 원문: start에서 methodExit까지

📖 용어: Scope와 Span의 종료
Scope를 닫는 일은 현재 실행에 연결한 Context를 복원하는 일이에요. Span을 끝내는 일은 관측한 작업의 종료를 기록하는 일이며, 두 동작이 항상 같은 시점에 일어나는 것은 아니에요.

shouldStart(parentContext, request)가 false면 null을 반환해요. 메서드 종료 advice도 보관한 scope가 있을 때만 종료 처리를 해요. 시작하지 않은 계측을 무조건 끝내는 구조가 아니에요. 다만 이 함수 이름만으로 “이미 비슷한 스팬이 있으면 모든 경우에 중복이 제거된다”라고 확대해서 읽을 수는 없어요. 구체적인 판단은 instrumenter의 구성과 억제 정책까지 봐야 해요.

정상 반환이나 예외 종료가 발생하면 scope.close()를 먼저 호출하고, instrumenter.end(context, request, response, throwable)에 보관한 Context와 결과를 전달해요. 현재 Context를 복원한 뒤에도 작업을 끝낼 Context를 직접 전달할 수 있다는 점이 중요해요. 종료 함수가 그때의 Context.current()만 다시 읽어야 하는 구조가 아니에요.

이 파일은 계측 대상을 고르고 수명을 연결하는 부분이에요. HTTP 속성을 어떻게 추출하는지, 전파 헤더를 어디에 넣는지, 최종 스팬 상태를 어떻게 정하는지의 전체 구현은 이 짧은 범위 안에 없어요. 진입 advice를 읽었다는 사실과 HTTP 계측의 모든 동작을 검증했다는 사실은 달라요. 이 글도 화면에 나온 몇 줄을 전체 보장으로 해석하지 않아요.

4. sendAsync는 반환할 때 Scope만 닫고 완료를 기다려요

비동기 호출에서 메서드 반환을 작업 종료로 기록하면 요청 시간을 잘못 해석하게 돼요. sendAsync는 응답 자체가 아니라 이후에 완료될 CompletableFuture를 반환해요. 이 구현은 별도 AsyncAdviceScope로 그 차이를 처리해요.

비동기 start/end 원문 L138-L167을 보면 현재 부모 Context뿐 아니라 계측을 시작한 Context와 Scope를 따로 저장해요. 반환 경계에서는 Scope를 닫아요. 그리고 메서드 자체가 예외를 던졌다면 즉시 instrumenter를 끝내지만, Future를 정상적으로 반환했다면 완료 콜백을 연결해요.

// v2.32.0의 비동기 종료 분기를 요약한 의사 코드예요. // 원문의 중첩 호출 검사와 null 처리는 생략했어요. scope.close(); if (methodThrew) { instrumenter.end(context, request, null, throwable); return originalFuture; } return wrap(originalFuture, parentContext) .whenComplete(responseConsumer(context, request));

이 콜백의 끝도 확인할 필요가 있어요. 같은 릴리스의 ResponseConsumer.accept()는 완료된 응답 또는 Throwable을 받아 instrumenter.end()를 호출해요. 즉, Future를 반환한 경로에서는 메서드 반환이 아니라 완료 통지를 통해 계측을 끝내요. 요청이 빨리 반환되었다는 사실을 요청 전체가 빨리 끝났다는 사실로 바꾸지 않아요.

그림 1. 반환 직후에도 작업은 진행될 수 있어요. 이 경로에서 Scope와 Span의 종료 시점이 나뉘어요.

Context 처리도 현재 값을 계속 유지하는 방식이 아니에요. CompletableFutureWrapper.wrap()은 원래 Future의 완료를 전달할 때 인자로 받은 Context를 현재로 연결해요. 이 advice에서 넘기는 값은 HTTP 계측 Context가 아니라 parentContext예요. 이 차이를 놓치면 모든 후속 실행이 HTTP 클라이언트 스팬을 현재 부모로 계속 사용한다고 잘못 설명하게 돼요. 별도 비동기 실행자로 옮겨진 애플리케이션 코드까지 모두 이 한 함수로 검증되는 것은 아니에요.

또 시작 부분의 CallDepth는 중첩된 HttpClient 호출을 구분해요. 내부 호출에서도 같은 계측을 계속 시작하지 않도록 분기하는 코드예요. 이것도 이 경로의 중첩 처리이지, 다른 SDK나 수동 계측이 만든 모든 스팬의 중복을 전역적으로 제거한다는 약속은 아니에요.

💡 비동기 계측은 콜백 하나로 끝나는 문제가 아니에요
이 구현은 반환 Future를 감싸고 취소를 원본 Future에 전달하는 코드도 가지고 있어요. 따라서 응답·예외·취소·반환 객체의 사용 방식은 검증 대상이에요. 소스에 취소 처리가 있다는 사실만으로 모든 라이브러리 조합의 취소 동작과 콜백 문맥이 동일하다고 보증할 수는 없어요.

5. 수동 계측은 자동 계측을 다시 쓰는 일이 아니에요

앞의 결제 예시로 돌아가 볼게요. HTTP 스팬에 결제 업무 전체라는 이름을 붙이면 네트워크 호출 시간과 업무 처리 시간을 혼동할 수 있어요. 승인 요청 전의 검증, 응답을 읽은 뒤의 상태 변경, 보상 처리까지 포함하려면 애플리케이션이 아는 업무 경계를 따로 정하는 편이 의미를 분리하기 좋아요. 아래는 이 차이를 설명하는 가상 동기 코드예요. 실행한 샘플은 아니며 Tracer를 이미 주입받았다고 가정해요.

Span span = tracer.spanBuilder("payment.authorize").startSpan(); try (Scope ignored = span.makeCurrent()) { // 내부 HTTP 호출은 지원되는 자동 계측에 맡기는 구성이에요. Authorization result = paymentService.authorize(command); span.setAttribute("app.payment.outcome", result.outcomeName()); return result; } catch (RuntimeException error) { span.recordException(error); span.setStatus(StatusCode.ERROR); throw error; } finally { span.end(); }

이 예시가 직접 정하는 것은 payment.authorize라는 업무 구간, 정해진 결과 분류, 예외 발생 시의 기록이에요. 같은 HTTP 호출을 수동으로 한 번 더 계측할 필요는 없어요. HTTP 계측이 활성화되고 같은 Context가 전달되는 구성이라면 업무 구간 아래의 통신을 함께 볼 수 있어요. 정확한 부모 관계는 실제 조합에서 확인해야 하고, 예시 코드만으로 설치나 전송 설정까지 완성되지는 않아요.

app.payment.outcome은 여기서 정한 예시용 속성이지 OTel이 보편적으로 규정한 결제 표준 속성이 아니에요. 결과 이름도 제한된 분류를 사용한다는 가정이에요. 주문 전문이나 고객 정보를 그대로 넣는 방식을 권하는 예시가 아니에요. HTTP 200으로 전달된 승인 거절을 ERROR로 표시할지, 정상적인 업무 결과로 구분할지도 업무와 운영 기준이 결정해야 해요. 이 코드가 임의의 결과를 자동으로 오류로 바꾸지는 않아요.

agent에 API 계측을 추가하는 공식 가이드도 두 방식을 함께 사용하는 구성을 안내해요. 계측 API를 쓰기 위해 애플리케이션마다 독립 SDK와 exporter를 하나씩 더 만들 필요는 없어요. agent가 구성한 OTel과 연결해 추가 작업을 기록하는 경로가 있어요. 별도 Provider를 의도적으로 구성한다면 연결과 전송 책임이 어디에 생기는지 따로 확인해야 해요.

📖 용어: 보강과 새 작업 구간
보강은 이미 기록하는 작업에 필요한 속성이나 이벤트를 추가하는 일이고, 새 작업 구간은 별도 시작·종료가 있는 Span을 만드는 일이에요. 정보가 하나 더 필요하다는 이유만으로 항상 새로운 Span이 필요한 것은 아니에요.

업무 작업이 기존 서버 요청과 수명이 같고 속성만 필요한 경우에는 현재의 적절한 스팬을 보강하는 선택도 있어요. 반대로 같은 요청에서 업무 작업이 여러 번 실행되거나 여러 외부 호출을 포함한다면 별도 구간이 구별에 도움이 돼요. 다만 보강하려는 시점에 어떤 스팬이 현재인지, 이미 종료되지는 않았는지부터 확인해야 해요. Span.current()를 호출했다고 원하는 업무 스팬이 자동으로 선택되지는 않아요.

수동 코드의 비용은 책임이 명확해진다는 점과 함께 생겨요. 새 업무 이름의 안정성, 성공과 실패의 정의, 속성의 민감성, 예외 재전파, 반드시 한 번 끝나는 수명을 코드 소유자가 관리해요. 위의 try/finally를 그대로 비동기 반환 메서드에 붙이면 Future 완료 전에 스팬을 끝낼 수 있어요. 자동 계측에서 읽은 Scope와 Span의 수명 분리가 수동 계측에서도 필요한 이유예요.

6. Micrometer Observation은 어떤 지점을 추상화할까요

이미 Micrometer Observation을 쓰는 코드에서는 업무 작업의 시작과 종료가 Observation으로 표현되어 있을 수 있어요. 여기서 OTel을 선택한다는 이유만으로 같은 위치에 계측 API를 다시 붙이는 것이 유일한 경로는 아니에요. 먼저 기존 계측 호출과 실제 Span을 만드는 구현을 구분해야 해요.

📖 용어: Observation과 Handler
Observation은 작업의 수명과 메타데이터를 표현하고, Handler는 그 수명 이벤트에 반응하여 타이머나 스팬 등의 기록을 만드는 구성 요소예요. 실제로 무엇이 만들어지는지는 Registry에 등록한 Handler와 연결된 구현에 달려 있어요.

Micrometer 1.17.1의 소개에서 observe(() -> ...)는 시작, Scope 열기, 코드 실행, 발생한 오류 기록, Scope 닫기, 종료를 수행한다고 설명해요. 각 Handler는 자신이 지원하는 Observation.Context에서 해당 수명 이벤트를 받아요. 이름과 태그의 규칙을 ObservationConvention으로 분리하는 경로도 있어요.

따라서 이 추상화에서 애플리케이션은 “이 작업을 관측한다”라는 위치를 표현하고, 어떤 기록을 만들지는 Handler 구성을 통해 연결할 수 있어요. Handler 없이 API 호출만 추가한 것을 저장소에서 스팬이 보이는 상태와 동일하게 취급할 수는 없어요. 계측 위치의 재사용과 실제 전송의 완료는 다른 단계예요.

Micrometer Tracing 1.7.1 문서는 OTel 또는 Brave를 사용하는 bridge와 exporter/reporter 구성을 설명해요. OTel bridge를 쓰면 Observation 기반 계측과 OTel 기반 처리가 연결될 수 있어요. 그래서 “Micrometer냐 OTel이냐”만 묻기보다 계측 호출을 어느 API로 표현하고, Tracing 구현과 exporter는 누가 구성하는지를 나누는 편이 정확해요.

주의할 이름도 있어요. Micrometer의 Observation.Context는 Handler 사이에서 상태를 공유하는 변경 가능한 맵이고, 2편에서 읽은 OTel Context는 불변 문맥 객체예요. 둘 다 Scope와 함께 등장해도 같은 타입이나 변경 모델이 아니에요. bridge의 존재가 두 Context 객체를 아무 곳에서나 서로 대입할 수 있다는 뜻은 아니에요.

선택 기준도 달라져요. 기존 Observation으로 업무 경계가 잘 표현되어 있고 설정을 조직적으로 관리한다면 그 계측을 연결하는 방향을 먼저 검토할 수 있어요. 반대로 OTel API를 직접 사용하는 모듈에서는 OTel Span과 Context로 경계를 표현하는 쪽이 직접적일 수 있어요. 어느 쪽이든 동일한 HTTP 작업을 agent, 프레임워크 Handler, 별도 수동 코드가 각각 기록하지 않는지 확인해야 해요. bridge를 추가했다는 사실만으로 구성 전체의 중복이 없어지지는 않아요.

7. eBPF와 비교할 때는 관찰 지점과 요구 권한을 봐야 해요

코드 변경 없이 데이터를 얻는 또 다른 경로로 eBPF 기반 도구가 있어요. 여기서는 eBPF 전체의 공통 기능을 단정하지 않고 공식 프로젝트인 OpenTelemetry eBPF Instrumentation, OBI의 현재 문서를 기준으로 볼게요. 문서는 지원하는 Linux 워크로드의 실행 파일과 운영체제 네트워크 계층을 관찰한다고 설명해요. eBPF는 오직 커널 패킷만 읽는다고 요약하면 사용자 공간 관찰을 빠뜨려요.

📖 용어: probe와 관찰 가능 정보
probe는 실행 경로에 연결하여 그 지점의 정보를 읽는 관측 수단이에요. 어떤 위치에 붙고 어떤 런타임과 프로토콜을 해석하는지가 얻을 수 있는 정보의 범위를 제한해요.

현재 OBI 문서는 Linux의 amd64·arm64, BTF, 지원 커널과 필요한 권한을 요구해요. 커널은 일반적으로 5.8 이상이며 필요한 기능이 백포트된 RHEL 계열 4.18 이상 예외를 따로 설명해요. root 또는 활성화한 기능이 요구하는 Linux capability가 필요해요. 애플리케이션 소스를 고치지 않는다는 설명을 운영환경과 권한을 바꾸지 않아도 된다는 설명으로 바꾸면 안 돼요.

더 중요한 한계는 의미예요. OBI 문서도 probe에서 얻을 수 없는 애플리케이션 전용 속성, 업무 이벤트, 사용자 정의 스팬에는 언어 계측이나 수동 계측이 필요할 수 있다고 명시해요. HTTP 통신이 보인다는 것과 승인 거절 뒤의 재시도 정책을 업무 이름으로 설명할 수 있다는 것은 달라요. 분산 전파나 비동기 요청 연결, 프로토콜 지원도 기능별 문서를 확인해야 해요.

그림 2. 세 행은 정보를 얻는 위치의 비교예요. 위에서 아래로 거치는 처리 pipeline이나 호출 순서가 아니에요.

이 비교에서 Java agent는 이미 알려진 JVM 라이브러리 경계를 세밀하게 다루는 구현을 제공하고, OBI는 지원 환경에서 애플리케이션 수정 없이 관측을 시작하는 경로를 제공해요. 수동 계측과 Observation은 코드가 아는 의미를 명시할 위치를 제공해요. 자동 수집의 두 경로와 계측 API를 동급 제품 네 개의 순위로 비교하면 책임의 차이가 사라져요.

조건에 따라 선택도 달라져요. 수정하기 어려운 여러 Linux 서비스의 지원 프로토콜 흐름을 먼저 파악하려는 경우에는 OBI의 배포 조건과 기능 범위를 검토할 수 있어요. 반면 업무 구간의 실패 원인을 코드의 분기와 연결해야 한다면 네트워크 관찰만으로는 부족할 수 있어요. JVM 앱에서 라이브러리별 비동기 수명과 Context가 중요한 경우에는 agent의 지원 구현을 확인하는 일이 먼저일 수 있어요. 이것은 요구 정보에 따른 판단이지 여기서 측정한 성능 순위가 아니에요.

특히 “eBPF이므로 항상 더 저렴하다”나 “바이트코드를 바꾸므로 항상 더 느리다”라는 결론은 이 자료에서 나오지 않아요. 이벤트 빈도, probe와 추출 로직, 활성화한 계측 범위, 스팬 수, 전송 경로에 따라 측정 대상이 달라져요. 이 글에서는 CPU·메모리·지연을 비교 실행하지 않았어요. 수집 방식의 명칭을 보편적인 비용 수치로 대체하지 않아요.

8. 중복 스팬과 호환성은 조합 단위로 확인해요

한 번의 HTTP 호출이 여러 라이브러리를 거칠 수 있어요. 상위 클라이언트와 내부 하위 클라이언트를 모두 계측하면 의미가 같은 중첩 스팬이 생길 수 있어요. 공식 Java agent의 억제 문서는 이런 상황을 설명하고, 현재 기본 semconv 기반 정책과 다른 선택지를 안내해요. “agent는 중복을 전혀 처리하지 않는다”라고 쓰는 것도 맞지 않아요.

동시에 이 정책을 임의의 조합에 대한 보장으로 넓히면 안 돼요. 독립 SDK를 하나 더 만들었는지, Observation Handler가 어느 구현에 연결되는지, 수동 Span이 같은 통신을 다시 표현하는지에 따라 결과가 달라져요. 앞서 본 CallDepth와 shouldStart는 특정 구현과 Context 안에서 동작해요. 스팬 이름이 비슷하다는 이유만으로 전체 pipeline이 그 둘을 같은 작업으로 자동 판단한다고 기대할 수는 없어요.

중복 여부를 볼 때는 단순한 개수보다 경계를 먼저 봐요. “결제 승인”과 그 안의 HTTP 호출은 서로 다른 작업일 수 있어요. 반대로 동일한 원격 요청을 HTTP client span 두 개가 같은 역할로 반복해서 나타내는 것은 중복일 수 있어요. 수집량을 줄이려고 무조건 자식 스팬 하나를 지우면 유효한 업무 구간을 없앨 수도 있어요. 원래 기대한 작업 모델을 먼저 정해야 비교가 가능해요.

호환성도 agent 버전 하나만으로 판단할 수 없어요. 공식 지원표는 라이브러리와 버전, 제공하는 데이터 종류를 구분해요. Java agent 자체의 실행 요구사항과 이번 예제인 Java HTTP Client의 Java 11 이상 조건은 같은 범위가 아니에요. 현재 지원표를 과거 모든 agent 버전의 출력 보증으로 소급하지도 않아야 해요.

현실의 검증 단위는 JDK, 프레임워크, 클라이언트 라이브러리, agent, 다른 계측 구성의 조합이에요. 빌드가 성공했다는 사실은 변환된 실행 코드의 반환값·예외·Future 취소가 기존 계약을 지켰다는 증거가 아니에요. 특히 런타임 내부 타입을 선택하는 구현을 읽었으므로 실제로 사용하는 JDK와 라이브러리에서 확인하는 절차가 필요해요.

9. 애플리케이션의 동작을 바꾸지 않는 것은 검증할 요구예요

관측을 추가하면서 원래 업무 동작을 크게 바꾸지 않아야 한다는 요구는 공식 OTel 오류 처리 사양에도 나타나요. 사양은 업무 동작을 크게 바꾸는 것보다 관측 데이터를 잃는 쪽을 선호한다는 전제와, 실행 중 처리되지 않은 예외를 내보내지 말아야 한다는 원칙을 설명해요. 초기화 실패나 사용자 지정 오류 처리 같은 구체적인 예외 조건은 문서에서 따로 구분해요.

읽은 동기·비동기 advice에도 suppress = Throwable.class가 있어요. 이 설정은 advice에서 발생한 오류가 업무 메서드로 전파되는 것을 억제하는 장치예요. 원래 HTTP 메서드의 Throwable은 종료 advice가 결과로 받아 전달해요. “애플리케이션 예외를 숨기기 위해 모든 예외를 무시한다”라는 설명과는 달라요.

그렇다고 이 어노테이션 하나가 모든 부작용을 제거하지는 않아요. Context를 잘못 복원하거나 완료 콜백을 잘못 연결하거나 수집 작업이 과도한 자원을 사용하면 예외 전파 외의 문제가 생길 수 있어요. 투명하게 동작해야 한다는 요구를 구현이 이미 완벽하게 충족했다는 증명으로 취급하지 않아야 해요. 실제로 동작이 바뀌었다면 그것을 자동 계측의 자연스러운 비용이라고 넘기기보다 결함인지 검토해야 해요.

또 “코드 수정 없음”과 “변경 위험 없음”은 다르다는 해석이 가능해요. 수정되는 소스 파일이 없더라도 런타임에는 새로운 코드와 상태, 배경 작업, 전송이 생겨요. 검토해야 할 변경의 위치가 저장소 diff에서 실행환경까지 넓어지는 거예요. 반대로 수동 계측도 소스에 명시되어 있다는 이유만으로 누락된 종료나 민감정보 수집 위험에서 자유롭지는 않아요.

🔎 적용 전에 정할 검증 경계
같은 입력에서 원래 반환값과 예외를 유지하는지, 동기·비동기·취소 경로의 수명이 맞는지, 부모 관계와 의도한 Span 수가 맞는지, exporter 장애가 업무 요청에 어떤 영향을 주는지 확인해요. 수집 성공 여부와 애플리케이션 계약 유지 여부는 별도로 검사해야 해요.

10. 무엇을 자동으로 모을지보다 무엇이 필요한지 먼저 정해요

검증 시나리오는 필요한 정보에서 출발할 수 있어요. 가령 정상 응답 하나, 예외로 끝나는 호출 하나, 나중에 실패하는 Future 하나를 구분해요. 각 경우에 업무 결과와 Span 종료 시점이 맞는지 비교해요. 이어서 HTTP 성공과 업무 거절이 다른 입력을 넣으면 통신 스팬만으로 무엇이 설명되지 않는지도 확인할 수 있어요. 여기서 적은 입력들은 실제로 실행한 결과가 아니라 적용 전 확인할 가상 사례예요.

이 과정을 거쳐 라이브러리 경계 정보만으로 목적을 달성한다면 수동 스팬을 넓게 추가할 이유는 적어져요. 업무 의미가 빠져 있다면 필요한 구간이나 속성을 제한적으로 추가할 수 있어요. 기존 Observation이 이미 그 구간을 표현한다면 같은 작업을 한 번 더 만들기보다 연결된 Handler를 확인하는 편이 먼저예요. 배포 환경이 언어 agent보다 외부 관찰 도구에 적합하다면 지원 probe와 권한을 확인한 뒤 부족한 의미를 어떻게 보강할지 정할 수 있어요.

개인정보와 비밀값도 별도 검증 대상이에요. 자동 계측이 추출한 속성과 직접 추가한 업무 속성을 모두 살펴야 해요. 개발용 가짜 식별자와 가짜 민감값을 사용해 SDK 출력, 중간 처리, 저장소에 도착한 데이터를 비교할 수 있어요. 헤더나 본문을 넓게 수집한 뒤 나중에 지우는 것을 기본값으로 삼기보다, 목적에 필요한 값만 수집하도록 정하는 것이 우선이에요. 이 원칙과 Collector에서의 추가 삭제·변환은 공식 민감정보 처리 가이드에서 함께 다뤄요.

마지막으로 이 소스 분석에서 확인한 것과 아직 확인하지 않은 것을 나눠 둘게요. 고정 릴리스의 타입 선택, 동기 Scope 정리, 비동기 Future 완료 연결과 보조 클래스를 읽었어요. 그러나 특정 서비스에서 agent를 실행하여 추적 연결, 취소, 전파, 민감정보, 성능을 검증하지는 않았어요. OBI나 Micrometer bridge 조합도 실행하지 않았어요. 코드를 읽고 얻은 설계 이해가 그 실행 검증을 대신하지는 않아요.

소스 기준: OpenTelemetry Java 자동 계측 v2.32.0. 코드 이미지는 해당 공개 소스를 렌더링했어요.

✍️ 오늘의 요약
자동 계측은 알려진 실행 경계에 계측 코드를 연결해요. 업무 의미 전체를 자동으로 추론하는 기능과는 달라요.

Java HTTP Client의 구현에서도 matcher가 대상을 고르고 Context와 Scope를 관리하며, 비동기 호출은 Future 완료까지 Span 종료를 미뤄요. 수동 API와 Observation은 애플리케이션이 아는 작업을 표현하고, OBI는 지원하는 probe와 환경에서 정보를 얻어요.

조합의 기준은 필요한 정보와 책임의 위치예요. 같은 작업을 중복 기록하지 않는지, 원래 동작을 유지하는지, 필요한 의미와 민감정보 경계가 맞는지를 실제 구성에서 확인해야 해요.
