📚 OpenTelemetry 운영 실습 · 2편
1편. Collector가 받았다고 한 스팬은 정말 저장됐을까
2편. 에러 트레이스만 남기면 장애를 놓치지 않을까 ← 지금 이 글

에러 요청을 10번 보냈는데 Tempo에 남은 트레이스는 3개였어요. 애플리케이션은 10번 모두 HTTP 500을 반환했고, 요청 로그도 남았습니다. 저장 비용을 줄이려고 SDK에서 25%만 선택했더니, 실패한 요청의 기록도 함께 줄었어요.

그러면 Collector에서 에러를 확인한 뒤 남기면 될까요? 작은 주문 서비스를 만들어 정상·오류·느린 요청을 보냈어요. 오류를 알아보는 시점과 스팬이 도착하는 시점을 바꾸며, 어떤 장애 기록이 남고 어떤 기록이 빠지는지 확인해요.

🧭 이 글에서 확인할 것
• 시작할 때 25%를 선택하면 오류 요청은 몇 개 남을까요?
• 오류와 느린 요청을 Collector에서 골라 남길 수 있을까요?
• 앞에서 버린 요청과 늦게 도착한 오류 스팬은 어떻게 될까요?

1. 오류가 나기 전에 이미 선택이 끝났어요

한 요청에 checkout과 그 안에서 실행하는 inventory.lookup을 기록해요. 정상은 약 15ms, 오류는 같은 정도의 작업 뒤 HTTP 500, 느린 요청은 재고 조회에서 실제로 320ms를 기다리게 했어요. 회사 서비스나 운영 데이터는 쓰지 않았습니다.

📖 용어: 트레이스와 스팬
트레이스는 한 요청의 실행 기록이고, 스팬은 그 안의 작업 하나예요. 이 실습은 요청마다 부모 작업과 자식 작업, 두 스팬을 만들어요.

SDK에서 ParentBased(TraceIdRatioBased(0.25))를 설정하면 요청을 시작할 때 trace ID를 기준으로 선택해요. 자식 스팬은 부모의 결정을 따릅니다. 이때는 재고 조회가 실패할지, 320ms가 걸릴지 아직 알 수 없어요.

📖 용어: Head sampling
스팬을 시작할 때 수집 여부를 정하는 방식이에요. 이 실습에서는 0.25를 확률로 지정하지만, 작은 요청 집합의 결과가 정확히 25%일 필요는 없어요.

확률 선택 자체가 잘못된 것은 아니에요. 애플리케이션에서 내보내는 데이터를 줄이는 데 쓸 수 있습니다. 다만 요청을 시작할 때 미래의 오류 여부까지 판단할 수는 없어요. 선택되지 않은 요청도 실제로 실행되고, 서비스의 응답 로그에는 남습니다.

그림 1. 확률 선택은 오류가 드러나기 전에 이뤄져요.

2. 작은 서비스를 세 경로로 보냈어요

Python 표준 HTTP 서버에 OpenTelemetry Python SDK 1.38.0을 직접 붙였어요. Collector contrib 0.162.0, Tempo 2.10.8, Grafana 13.2.3을 Docker Compose로 띄웁니다. 자동 계측이 무엇을 만드는지 비교하는 실험은 아니고, 두 스팬과 선택 조건을 직접 통제하는 실험이에요.

같은 코드에 세 모드를 두었어요. head는 SDK에서 25%를 선택하고 저장소로 바로 보내요. tail은 SDK에서 모두 기록한 뒤 Collector가 선택해요. head-tail은 SDK의 25% 선택 뒤 Collector의 조건을 적용합니다.

📖 용어: Tail sampling
Collector가 일정 시간 모은 스팬을 보고 보관할 트레이스를 정하는 방식이에요. 오류 상태와 관측된 실행 시간을 판단에 쓸 수 있어요.
cd labs/observability/otel-practice/tail-sampling python3 run.py --build cat out/results.txt # 실행한 요청의 trace ID와 SDK 선택 여부 python3 -m json.tool out/requests.json # 화면과 관측 데이터는 이 실습 전용 포트를 써요 # Grafana: http://127.0.0.1:27200 # Tempo: http://127.0.0.1:27201

실행기는 이 Compose 프로젝트만 재생성하고 이전 실행의 생성 파일을 교체해요. 서비스의 준비 상태를 확인한 뒤 모드마다 정상 40건·오류 10건·느린 요청 10건을 보냅니다. 뒤에서 사용할 지연 전송 두 건까지 실제 HTTP 요청은 182건이에요. 실행이 끝나면 화면을 확인할 수 있도록 스택을 유지합니다.

⚠️ 개수를 먼저 정해 둬야 해요
실행한 요청 목록을 분모로 삼고, SDK의 선택 여부·Collector 전후의 파일·Tempo의 trace ID를 대조해요. 화면의 검색 결과 개수만으로 유실을 판단하면 아직 검색되지 않은 기록과 선택하지 않은 기록을 구분하기 어려워요.

3. 에러와 지연을 조건으로 남겨 봤어요

Collector에는 ERROR 상태이거나, 관측된 트레이스 시간이 200ms를 초과하면 남기는 정책을 넣었어요. 아래 두 정책 중 하나라도 충족하면 선택하는 구성이에요. 일반 경로의 판단 대기는 2초로 지정했습니다.

tail_sampling/short: decision_wait: 2s num_traces: 1000 decision_cache: sampled_cache_size: 1000 non_sampled_cache_size: 1000 policies: - name: keep-errors type: status_code status_code: {status_codes: [ERROR]} - name: keep-slow type: latency latency: {threshold_ms: 200}

status_code는 HTTP 응답 코드가 아니라 스팬에 기록된 OTel 상태를 읽어요. 서비스 코드가 오류 요청에 set_status(Status(StatusCode.ERROR, ...))를 직접 호출합니다. HTTP 500을 반환했다는 사실만으로 이 정책이 작동했다고 판단하지 않았어요.

📖 용어: 스팬 상태
스팬이 성공·오류 등의 결과를 표현하는 값이에요. 이 실습의 오류 정책은 OTel의 ERROR 상태를 검사해요.

지연 정책은 모은 스팬의 가장 이른 시작부터 가장 늦은 종료까지를 봐요. 부모 320ms와 자식 320ms를 더해서 640ms로 보지는 않습니다. 실제 저장 화면에서 느린 요청 한 건은 약 323ms였어요.

화면 1. Collector가 남긴 느린 요청을 실제 Grafana Explore에서 열었어요.

기본 실행 ID sampling-seed-a로 실행한 결과예요. 표의 숫자는 Tempo에 저장된 트레이스 수를 요청 수로 나눈 값입니다.

경로정상오류느린 요청
Head 25%10 / 403 / 101 / 10
Tail만 적용0 / 4010 / 1010 / 10
Head 25% → Tail0 / 405 / 101 / 10

이번 입력에서는 Tail만 적용한 경로가 오류와 느린 요청 20건을 모두 남겼어요. 정상 기록은 남기지 않았습니다. 조건에 필요한 스팬이 판단 전에 도착했을 때의 결과예요. 모든 장애를 항상 보존한다는 뜻은 아니에요.

4. 앞에서 버린 오류는 Tail도 되살리지 못해요

head-tail의 오류 요청 10건 중 SDK가 기록한 것은 5건이었어요. Collector는 이 5건을 모두 남겼지만, SDK가 기록하지 않은 나머지 5건은 입력 자체가 없었습니다. 느린 요청도 SDK가 선택한 1건만 남았어요. 정상 요청은 SDK가 선택한 13건도 Collector에서 제외됐습니다.

여기서 Head 단독의 오류 3건과 Head→Tail의 5건을 비교해 "Tail이 2건을 추가로 살렸다"고 읽으면 안 돼요. 모드 사이에 트레이스가 합쳐지지 않도록 서로 다른 ID를 사용했어요. 각 경로의 확률 선택 결과는 달라요. 복구할 수 없다는 근거는 한 경로 안에서 SDK가 기록하지 않은 ID가 Collector와 Tempo에도 없다는 대조입니다.

화면 2. 서비스 응답·Collector 파일·Tempo 조회를 대조한 실제 출력이에요.

전체 저장 결과는 고유 트레이스 41개, 스팬 82개였고 Collector 출력과 Tempo가 일치했어요. 요청 로그에는 선택 여부와 무관하게 응답이 남습니다. 오류율을 계산하려면 이 표의 저장된 기록만 분모로 쓰면 안 돼요. 특히 이번 Tail 정책은 정상 요청을 모두 제외하므로, 수집된 트레이스의 오류 비율을 서비스 오류율로 해석할 수 없습니다.

💡 실무에서는
선택된 트레이스는 오류 원인과 호출 경로를 살펴보는 데 쓰고, 전체 요청 수·오류 수·지연 지표는 별도로 수집해요. 이 실습은 전체 요청 응답과 로그를 보존했지만, 요청 지표를 위한 Prometheus까지 추가하지는 않았어요.

5. 오류 스팬이 5초 늦으면 결과가 달라져요

마지막 두 요청은 조금 다르게 만들었어요. 부모와 오류 자식의 작업을 약 15ms로 기록해요. 부모를 먼저 전송하고, 자식은 종료 시각을 기록해 둔 다음 전송만 5초 지연시킵니다. 트레이스에 기록된 실행 시간이 5초인 것은 아니므로, 지연 정책이 대신 남기는 경우를 피할 수 있어요. 이 조건을 통제하려고 부모 스팬을 수동으로 먼저 끝냈고, HTTP 응답은 지연 전송 뒤 반환하므로 약 5초가 걸려요. 실제 비동기 서버의 자동 계측을 재현한 코드는 아닙니다.

📖 용어: decision_wait
첫 스팬을 받은 뒤 Collector가 판단하기까지 기다리는 시간이에요. 이번 비교에서는 2초와 8초로 설정해요.

2초 대기 경로는 오류 자식이 오기 전에 정상 부모만 보고 제외했어요. 8초 대기 경로는 오류 자식까지 받은 뒤 두 스팬을 남겼습니다. 지연 전송 요청의 저장 결과는 각각 0/1, 1/1이었어요.

📖 용어: 결정 캐시 (decision cache)
이미 선택하거나 제외한 trace ID의 결정을 기억하는 곳이에요. 이 실습은 두 캐시 크기를 각각 1,000으로 지정해, 늦은 스팬에도 앞서 내린 결정을 적용했어요.
그림 2. 기다리는 동안 어떤 스팬이 도착했는지가 정책의 입력을 바꿔요.

Collector의 비선택 결정 캐시 적중 지표도 1이었어요. 이번 설정에서 늦은 오류 자식이 기존 제외 결정을 바꾸지 못했다는 결과와 맞습니다. 기대한 기록이 도착한 뒤 10초를 더 관찰해 추가 기록이 없는지도 확인했어요. 캐시를 끄거나, 수용량·종료·재시작 조건을 바꾸면 다른 실험이 필요합니다.

6. 보관 조건과 관측의 한계를 같이 정해요

판단 대기를 늘리면 이번 지연 전송은 보존할 수 있었어요. 대신 아직 판단하지 않은 트레이스를 더 오래 유지해야 합니다. 이 실습은 메모리나 처리량을 측정하지 않았으므로 8초가 운영 환경의 적정값이라고 제안하지는 않아요.

오류 조건도 서비스의 실패 정의와 맞아야 해요. 예외를 처리하고 정상 응답을 주는 코드가 ERROR 상태를 남기는지, 다른 서비스가 전송을 늦추는지 확인해야 합니다. 여러 Collector로 나누는 환경에서는 같은 트레이스의 스팬이 같은 판단 인스턴스에 모이는지도 별도로 확인해야 해요. 이번 실험은 서비스 하나와 Collector 하나에서 실행했습니다.

재현 코드는 labs/observability/otel-practice/tail-sampling에 있고, 원자료는 그 아래 out/에 있어요. 확인을 마치면 같은 디렉터리에서 docker compose down으로 이 실습만 종료할 수 있습니다.

기술 근거는 Collector 0.162.0 Tail sampling 문서, 같은 버전의 지연 계산 코드, Python SDK 1.38.0 샘플러를 확인했어요. 앞단 선택과 뒷단 선택의 관계는 OpenTelemetry 공식 샘플링 설명도 함께 볼 수 있어요.

✍️ 오늘의 요약
Tail sampling은 판단 전에 받은 오류·지연 정보를 기준으로 기록을 남겨요. SDK에서 기록하지 않은 스팬은 되살릴 수 없고, 이번 설정에서는 판단 뒤 도착한 오류 스팬도 제외됐어요.

보관할 조건뿐 아니라, 그 조건을 판단할 데이터가 언제 어디까지 도착하는지도 확인해야 해요.
