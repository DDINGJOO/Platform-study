1편. Collector가 받았다고 한 스팬은 정말 저장됐을까 ← 지금 이 글

로컬 서비스가 스팬 20개를 보냈어요. Collector는 20개 모두에 성공을 응답했는데, 전송 대기 중인 Collector를 강제 종료하자 저장 결과는 0개였어요. 같은 조건의 디스크 큐에서는 20개가 돌아왔습니다.

Collector의 수신 성공과 백엔드의 저장 완료 사이에는 무엇이 있을까요? 간단한 주문 테스트 서비스를 만들고, 장애 복구·프로세스 종료·큐 포화·성공 응답 실패를 차례로 넣어 봤어요. 여기서 나온 숫자는 모두 2026년 10월 23일 실행한 로컬 실험 결과예요.

1. 성공 응답을 세 번 나누어 확인해요

화면에 트레이스가 안 보일 때 전송 실패인지, 수신 후 대기 중인지부터 구분해야 해요. 그래서 주문 테스트 서비스 뒤에 Collector 두 개를 두었어요. 하나는 메모리 큐, 하나는 디스크 큐를 사용해요.

📖 용어: Collector
애플리케이션의 관측 데이터를 받아 가공하고 다른 저장소로 보내는 프로그램이에요. 수신과 최종 전송은 서로 다른 단계입니다.

백엔드 앞에는 수신 기록용 게이트웨이를 넣었어요. 이 게이트웨이는 받은 스팬의 ID를 SQLite에 커밋한 다음 같은 스팬을 Tempo로 전송해요. Tempo는 트레이스를 보관하고 조회하는 도구이고, Grafana는 그 결과를 화면에 보여 줍니다.

📖 용어: 스팬과 트레이스
스팬은 작업 하나의 기록이고, 트레이스는 연결된 작업 기록의 묶음이에요. 이번에는 스팬마다 별도 트레이스 ID를 만들고, 트레이스 ID와 스팬 ID의 쌍으로 누락·중복을 비교해요.
그림 1. 성공 응답 하나로 뒤의 모든 단계를 확인할 수는 없어요

측정은 세 단계예요. 첫째는 서비스가 받은 OTLP 전송의 HTTP 200, 둘째는 게이트웨이에 커밋된 고유 ID, 셋째는 Tempo에서 같은 ID를 다시 조회한 결과입니다. 주문 테스트 API 자체의 HTTP 200은 실행 보고서를 돌려준 응답이므로 별도로 봐야 해요.

📖 용어: OTLP 수신 응답
OpenTelemetry 데이터를 전송한 요청에 대한 응답이에요. 수신 측 큐에 들어갔다는 응답과, 최종 저장소가 디스크 장애에도 견딘다는 보장은 같지 않아요.

서비스는 SDK나 Java agent를 쓰지 않고 유효한 OTLP JSON을 직접 만들어요. 요청 하나에 스팬 하나를 넣고, Collector의 batch processor도 뺐어요. SDK 큐와 묶음 처리의 영향을 제외하고 Collector의 큐만 비교하려는 구성입니다. 화면의 1ms는 테스트 데이터에 넣은 고정 길이이며 실제 주문 지연을 잰 값이 아니에요.

2. 같은 전송 설정에서 저장 위치만 바꿔요

버전은 Collector contrib 0.162.0, Tempo 2.10.8, Grafana 13.2.3, Python 3.12-slim이에요. Docker Compose와 Python 3.10 이상이 있으면 아래 명령으로 실행해요. Python 패키지를 추가로 설치할 필요는 없어요.

cd labs/observability/otel-practice/collector-loss python3 run.py cat out/results.txt # Grafana: http://localhost:27120 # 같은 실행의 저장 결과만 다시 확인하기 python3 verify.py

run.py는 이 실습의 otel-practice-01 프로젝트만 초기화해요. 그 프로젝트의 기존 큐·SQLite·Tempo 볼륨을 지우고, 이전 결과 파일은 history/실행시각/으로 옮겨요. 다른 프로젝트는 건드리지 않습니다. 저장된 결과를 유지하려면 verify.py를 쓰세요.

📖 용어: 전송 큐와 영속 큐
전송 큐는 아직 전송을 마치지 못한 요청을 보관해요. 메모리 큐는 프로세스와 함께 사라질 수 있고, 영속 큐는 지정한 저장 공간에 기록해 재시작 후 다시 읽어요.

두 Collector 모두 큐 크기는 요청 100개, 전송 작업자는 1개예요. 큐에 넣은 뒤 백엔드 결과를 기다리지 않고 응답하도록 wait_for_result: false를 명시했어요. 실패한 전송은 계속 재시도하게 설정했어요.

# disk.yaml의 핵심 부분, 전체 실행 설정은 실습 디렉터리에 있어요. exporters: otlp_http: endpoint: http://backend:8080 encoding: json compression: none retry_on_failure: initial_interval: 1s max_interval: 2s max_elapsed_time: 0s sending_queue: sizer: requests queue_size: 100 num_consumers: 1 wait_for_result: false block_on_overflow: false storage: file_storage extensions: file_storage: directory: /queue create_directory: true fsync: true

storage: file_storage가 있는 쪽은 프로젝트 전용 Docker 볼륨을 사용해요. 메모리 쪽은 이 연결을 빼요. 재시작 때 같은 볼륨을 유지하는 것이 실험 조건입니다. 전체 파일에는 receiver, health_check, service 연결도 들어 있어요.

설정 이름과 재시도 동작은 0.162.0 exporter helper 문서, 디스크 동기화는 같은 버전의 file_storage 문서로 확인했어요. 이 버전에서는 예전 별칭인 otlphttp 대신 otlp_http를 사용합니다.

3. 저장소 연결만 실패하면 둘 다 돌아와요

먼저 정상 상태에서 10개를 보내 모두 저장되는지 확인했어요. 다음에는 수신 게이트웨이가 HTTP 503을 반환하게 바꾸고, 각 Collector에 20개씩 보냈어요. 이때 게이트웨이는 기록을 커밋하지 않아요. Tempo 프로세스 자체는 계속 실행되며, Collector와 백엔드 사이의 전송 실패만 재현합니다.

두 Collector는 20개 모두에 수신 성공을 응답했어요. 하지만 장애를 복구하기 전, 게이트웨이의 해당 ID 기록은 양쪽 모두 0개였어요. 수신 성공 응답을 받은 시점에도 최종 전송은 끝나지 않았어요.

게이트웨이를 정상으로 바꾸자 메모리와 디스크 양쪽에서 정확히 20개의 고유 ID가 도착했어요. 짧은 연결 장애만으로 메모리 큐가 항상 유실되는 것은 아니에요. 아직 실행 중인 프로세스에 대기 요청과 재시도 상태가 남아 있었어요.

완료 여부는 몇 초 기다린 뒤 추측하지 않아요. run.py가 생성·수락 ID 집합을 보관하고, 게이트웨이에 같은 ID가 도착할 때까지 제한 시간 안에서 반복 조회해요. 장애가 실제 발생했는지도 게이트웨이의 503 응답 카운터로 확인해요.

4. 강제 종료 뒤에는 20개와 0개로 갈렸어요

다시 전송을 막고 양쪽에 20개를 보냈어요. 모두 수신 성공을 받았고 게이트웨이 기록이 비어 있는 것을 확인한 다음, 두 Collector에 SIGKILL을 보냈어요. 정상 종료의 전송 마무리를 기다리지 않고 프로세스를 끝내는 신호입니다.

동일한 볼륨으로 Collector를 다시 올리고 게이트웨이를 복구했어요. 디스크 쪽에서는 20개가 도착했고 메모리 쪽은 0개였어요. 메모리 쪽에 새로운 확인용 스팬을 보내 도착하는 것도 확인했어요. 재시작한 전송 경로는 동작하지만, 종료 전의 메모리 큐는 돌아오지 않았습니다.

그림 2. 같은 전송 실패라도 프로세스 종료가 겹치면 큐 저장 위치가 중요해져요

아래는 디스크 큐에서 복구한 스팬을 실제 Grafana Explore에서 연 화면이에요. 속성의 lab.run=kill-disk로 해당 실험에서 나온 데이터임을 구분해요.

그림 3. 디스크 큐에서 복구한 실제 스팬을 Tempo에서 다시 조회했어요

화면 한 장만 확인한 것은 아니에요. 결과 표의 저장된 고유 스팬 173개 전부를 Tempo API로 다시 조회하고 스팬 ID까지 대조했어요. 이 숫자에는 별도로 보낸 경로 확인용 스팬 1개를 넣지 않았어요. 조회 성공은 현재 Tempo의 가시성을 확인한 결과이며, Tempo가 고장 나도 보존된다는 검증은 아닙니다.

5. 디스크 큐도 꽉 차고, 재전송은 중복을 만들어요

디스크 큐를 사용하더라도 백엔드가 계속 실패하면 용량 한계에 도달해요. 이번에는 장애 상태에서 140개를 보냈어요. 이 실행에서는 100개를 수락했고 40개를 거절했어요. 복구 뒤에는 수락한 100개만 도착했습니다. 요청별 응답을 저장하므로 단순히 생성 수에서 추측한 결과가 아니에요.

📖 용어: 큐 포화
큐가 새 요청을 받을 수 없을 정도로 찬 상태예요. 이 실습은 기다리지 않고 거절하도록 설정했으며, 큐에 못 들어간 요청에는 exporter의 재시도도 시작되지 않아요.

queue_size가 언제나 스팬 개수인 것은 아니에요. 여기서는 sizer: requests이고 전송 요청마다 스팬 하나를 넣었어요. 여러 스팬을 묶거나 전송 작업자 수를 바꾸면 수락·거절 개수도 달라질 수 있어요. 이번 서비스는 거절된 전송을 재시도하지 않습니다.

마지막에는 게이트웨이가 저장과 Tempo 전송을 마친 뒤, 각 고유 트레이스의 첫 응답만 503으로 돌려주게 했어요. 네트워크 패킷을 실제로 버린 실험이 아니라, 처리는 끝났지만 성공 응답은 받지 못한 상황을 넣은 거예요. Collector가 재시도하자 고유 스팬 3개에 수신 기록 6개가 생겼어요.

📖 용어: 중복 전달
같은 ID의 데이터를 수신 측이 두 번 이상 받는 상황이에요. 전송 측은 실패 응답만 보고 이미 저장됐는지 알 수 없어서, 재시도 중 중복이 생길 수 있어요.

Grafana에서 스팬이 한 번 보인다고 전달도 한 번이었다고 결론 내릴 수는 없어요. 수신 게이트웨이는 모든 수신 시도를 별도 행으로 남기고, 고유 ID 개수와 전체 수신 행 수를 나누어 셉니다.

그림 4. 생성·수락·거절·고유 저장·중복·누락을 따로 세었어요

출력의 stored는 SQLite에 커밋된 고유 ID 수, duplicates는 추가 수신 행 수, missing은 Collector가 수락했지만 게이트웨이에 도착하지 않은 ID 수예요. overflow-disk의 누락이 0이어도 생성한 140개가 모두 도착했다는 뜻은 아니에요. 거절된 40개는 수락 집합에 포함하지 않아요.

6. 무엇을 복구했고 무엇은 확인하지 않았나요

이번 결과로 확인한 범위는 백엔드 경로의 HTTP 503, Collector 프로세스 강제 종료, 동일 볼륨의 재사용, 큐 포화, 저장 후 응답 실패예요. 호스트 전원 장애·디스크 고장·볼륨 삭제·Tempo 장애 복구·영구 오류는 시험하지 않았어요. 디스크 큐가 모든 유실을 막거나 정확히 한 번 전달한다는 결론은 낼 수 없습니다.

fsync: true는 디스크 동기화를 요청하지만, 디스크가 없어지거나 더 쓰지 못하는 조건까지 해결하지는 않아요. max_elapsed_time: 0s도 재시도할 수 있는 실패의 시간 제한을 없앤 설정이지 큐 거절을 복구하는 설정이 아니에요. 적용 시에는 디스크 여유·큐 사용량·enqueue 실패·전송 실패를 함께 확인해야 해요. 가능한 실패 조건은 공식 Collector 복원력 문서에도 정리돼 있어요.

💡 재현이 막히면 여기부터 확인해요
health check 연결 실패는 docker compose ps와 docker compose logs disk memory tempo로 확인해요. file_storage 권한 오류는 큐 디렉터리 쓰기 권한을 확인하고, 초기 상태가 필요하면 이 프로젝트의 run.py로 다시 실행해요. 테스트용 Collector는 전용 볼륨 권한을 단순화하려고 root로 실행했으며 운영에서는 볼륨 소유권과 제한된 실행 계정을 맞춰야 해요. Grafana에 데이터가 없다면 out/summary.json의 kill-disk 항목에서 example_trace를 골라 Explore의 trace ID 조회로 열어 보세요.

전체 재현 코드는 labs/observability/otel-practice/collector-loss, 기계 판독 결과는 out/summary.json에 있어요. 생성 ID와 응답은 *-generated.json, 수신 기록은 capture-receipts.json, Tempo에서 대조한 ID는 tempo-confirmed.json에 남겨요. 검증을 마쳤으면 해당 디렉터리에서 docker compose down으로 이 실습만 종료할 수 있어요.

✍️ 오늘의 요약
Collector가 스팬을 수락했다는 응답과, 백엔드에 저장됐다는 증거는 구분해야 해요. 이번 강제 종료에서는 메모리 큐의 수락 20개가 남지 않았고, 같은 볼륨의 디스크 큐는 20개를 복구했어요.

하지만 디스크 큐도 꽉 차면 거절하고, 저장 후 응답 실패에는 중복 전송이 생겼어요. 성공 응답만 세지 말고 수락한 ID, 저장한 ID, 다시 받은 ID를 함께 확인해야 해요.
