1편. 로드 밸런서 셋이 각자 가장 한가한 서버를 고르면
2편. 빨리 실패하는 서버는 한가해 보인다
3편. 갓 뜬 인스턴스에게는 보호관찰이 필요하다
4편. 요청을 한 번 더 보내면 빨라진다
5편. 재시도는 공짜가 아니다

7편. 임계값을 정하지 않는 동시성 제한

주문 서비스가 결제, 재고, 추천 목록 세 곳을 호출합니다. 어느 날 추천 목록 서비스의 응답이 0.1초에서 3초로 늘어납니다. 몇 분 뒤 결제 버튼까지 응답하지 않습니다. 결제 서비스는 멀쩡한데요. 주문 서비스의 스레드가 전부 추천 목록 응답을 기다리느라 묶여 있었기 때문입니다.

회의에서 처방이 세 개 나옵니다. "추천 호출에 비율 제한을 걸자." "벌크헤드로 떼어 내자." "서킷 브레이커를 달자." 셋 다 Resilience4j로 한 줄씩 감쌀 수 있고, 코드도 거의 똑같이 생겼습니다. 그럼 셋 중 아무거나 골라도 될까요? 이번 편은 셋이 각각 무엇을 세는지, 그래서 각자 무엇을 막지 못하는지를 봅니다.

1. 세 줄의 코드가 거의 똑같다

Resilience4j 2.x에서 세 패턴을 거는 코드를 나란히 놓아 보면 차이가 잘 안 보입니다.

Supplier<List<Item>> call = () -> recommendClient.fetch(userId); RateLimiter.decorateSupplier(rateLimiter, call); Bulkhead.decorateSupplier(bulkhead, call); CircuitBreaker.decorateSupplier(circuitBreaker, call);

셋 다 "호출 앞에서 통과시킬지 말지 판단하고, 안 되면 예외를 던진다"는 같은 모양입니다. 던지는 예외 이름만 달라요(RequestNotPermitted, BulkheadFullException, CallNotPermittedException). 차이는 판단에 쓰는 숫자에 있습니다. 비율 제한은 이번 기간에 내준 허가 수를, 벌크헤드는 지금 실행 중인 호출 수를, 서킷 브레이커는 최근 호출의 실패율을 셉니다.

그림 1. 셋은 같은 자리에 서서 서로 다른 숫자를 본다

그림 아래 회색 줄이 이 글의 뼈대입니다. 각 패턴은 자기가 세는 숫자 바깥의 일을 모릅니다. 하나씩 보겠습니다.

2. 비율 제한은 기간당 허가 수를 센다

정각마다 배치 작업이 추천 서비스를 초당 수천 번 호출하는데, 추천 서비스는 초당 몇백 번만 감당한다고 해 볼게요. 호출하는 쪽이 "초당 이만큼만 보낸다"는 상한을 지키지 않으면 받는 쪽은 넘치는 요청을 다 받아 놓고 같이 느려집니다.

📖 용어: 허가 (permission)
Resilience4j의 RateLimiter와 Bulkhead는 호출을 통과시킬 때 허가를 하나 내줍니다. 허가가 남아 있으면 통과, 없으면 기다리거나 거부예요. 둘의 차이는 허가를 언제 돌려받느냐입니다. RateLimiter는 기간이 바뀔 때 한꺼번에 채우고, Bulkhead는 호출이 끝날 때 하나씩 돌려받습니다.

RateLimiter의 설정은 세 개입니다. Resilience4j 문서의 설명과 기본값을 그대로 옮기면 이렇습니다.

limitRefreshPeriod 기본 500ns 허가 수를 되돌리는 주기 limitForPeriod 기본 50 한 주기 동안 쓸 수 있는 허가 수 timeoutDuration 기본 5s 허가를 기다리는 최대 시간

문서는 limitForPeriod를 "한 갱신 주기 동안 쓸 수 있는 허가 수"라고 적습니다. 그리고 주기마다 허가 수를 다시 limitForPeriod로 되돌린다고 설명하죠. 이 값은 흔히 "동시에 처리할 수 있는 작업 수"로 소개되지만 문서상 의미는 동시 실행 수가 아니라 주기당 개수입니다. 기본 구현 AtomicRateLimiter는 시간을 주기로 잘라 주기마다 허가를 다시 채울 뿐, 허가를 받아 간 호출이 끝났는지는 보지 않아요.

숫자로 확인해 보겠습니다. 주기 1ms에 허가 10개로 설정하면 1초에 주기가 1,000번 돌아서 초당 10,000개를 통과시키는 설정이 됩니다. 기본값은 더 극단적이에요. 500ns 주기는 1초에 2,000,000번이고, 여기에 50을 곱하면 초당 1억 개입니다. 기본값 그대로는 사실상 제한이 없는 것과 같으니, 쓸 때는 두 값을 직접 정해야 합니다.

비율 제한이 막지 못하는 것: 느려진 다운스트림

서두의 장면으로 돌아가 보죠. 추천 호출에 초당 100개 비율 제한이 걸려 있었다고 해 볼게요. 응답 시간이 0.1초일 때 동시에 떠 있는 호출은 평균 100 × 0.1 = 10개입니다(동시 실행 수 = 도착률 × 체류 시간, 2편에서 본 리틀의 법칙이에요. 7편에서 다시 다룹니다). 응답이 3초로 늘면 비율은 그대로 초당 100개인데 동시에 떠 있는 호출은 100 × 3 = 300개가 됩니다. 비율 제한은 하나도 거부하지 않았고, 스레드 300개가 추천 응답을 기다리며 묶입니다. 비율 제한을 걸었어도 결제 버튼은 멈췄을 거예요.

범위의 한계도 있습니다. RateLimiter는 한 JVM 안의 객체라서 인스턴스마다 따로 셉니다. 인스턴스 10대가 각자 초당 100개를 지키면 받는 쪽에는 초당 1,000개가 가고, 오토스케일링으로 대수가 바뀌면 총량도 같이 바뀝니다.

⚠️ 주의: 기본 timeoutDuration은 기다리게 한다
기본값 5초는 허가가 없을 때 호출 스레드를 최대 5초 세워 둔다는 뜻입니다. 빨리 거부하려고 건 비율 제한이 스레드를 묶는 원인이 될 수 있어요. 기다리지 않고 바로 RequestNotPermitted를 받으려면 timeoutDuration(Duration.ZERO)로 둡니다.

메트릭은 남은 허가 수(resilience4j.ratelimiter.available.permissions)와 허가를 기다리는 스레드 수(resilience4j.ratelimiter.waiting_threads, 이것만 밑줄입니다) 두 개입니다. 남은 허가가 0 근처인데 대기 스레드가 없으면 한계에 다가가는 중이고, 대기 스레드가 몇 분째 0보다 크면 사용자 응답이 이미 늦어지는 중이에요. 소스 코드 주석은 남은 허가 수가 음수가 될 수 있다고 적어 둡니다(다음 주기 허가를 미리 예약한 호출이 있을 때). 경고를 "0과 같다"로 쓰면 이 경우를 놓칩니다.

(Prometheus) 허가 대기가 5분 내내 이어지면 min_over_time(resilience4j_ratelimiter_waiting_threads{name="recommend"}[5m]) > 0

timeoutDuration이 0이면 대기 스레드는 늘 0이라 첫 경고는 울리지 않고, 거부된 호출도 두 게이지에 남지 않습니다. 이때는 호출하는 쪽에서 RequestNotPermitted를 직접 세야 해요.

3. 벌크헤드는 지금 실행 중인 수를 센다

서두의 장면을 정확히 막는 건 벌크헤드입니다. 문제는 주문 서비스가 결제, 재고, 추천 호출을 하나의 스레드 풀에서 처리했다는 데 있었어요. 추천 호출은 전체 트래픽 중 일부였지만, 그 일부가 느려지자 풀 전체가 추천 응답을 기다리는 스레드로 채워졌습니다.

📖 용어: 벌크헤드 (bulkhead)
다운스트림마다 동시에 실행할 수 있는 호출 수에 따로 상한을 두는 패턴입니다. 추천 호출이 상한(예: 20개)을 다 쓰면 21번째 추천 호출은 거부되지만, 결제와 재고 호출은 자기 몫이 남아 있어서 계속 나갑니다. 장애를 한 의존성 안에 가둬 두는 게 목적이에요.
그림 2. 같은 12개 자리라도 나눠 두면 한 곳의 장애가 다른 곳으로 넘어가지 않는다

Resilience4j는 벌크헤드를 두 가지로 제공합니다.

SemaphoreBulkhead (Bulkhead) maxConcurrentCalls 기본 25 동시에 실행할 수 있는 최대 호출 수 maxWaitDuration 기본 0 자리가 없을 때 호출 스레드를 세워 둘 최대 시간 FixedThreadPoolBulkhead (ThreadPoolBulkhead) maxThreadPoolSize 기본 CPU 코어 수 coreThreadPoolSize 기본 CPU 코어 수 - 1 (코어가 1개면 1) queueCapacity 기본 100 keepAliveDuration 기본 20ms

둘의 차이는 누가 호출을 실행하느냐입니다. 세마포어(남은 자리 수를 세는 카운터) 방식은 호출한 스레드가 직접 실행하고 개수만 셉니다. 동기 코드에 그대로 쓸 수 있어요. 스레드 풀 방식은 전용 풀이 실행하고 결과를 CompletionStage로 돌려줍니다. 호출한 스레드는 바로 풀려나지만, 코어 스레드가 모두 바쁘면 요청은 큐(기본 100칸)에서 기다리고 그 시간도 사용자에게는 응답 시간이에요. 내부가 자바 ThreadPoolExecutor라서 스레드를 최대 크기까지 늘리는 건 큐가 가득 찬 뒤이고, 큐와 스레드가 모두 차야 BulkheadFullException이 납니다.

벌크헤드가 막지 못하는 것: 빨리 실패하는 다운스트림

벌크헤드는 자리가 비었는지만 봅니다. 그래서 다운스트림이 5ms 만에 500을 돌려주면 자리는 금방금방 비고, 벌크헤드는 그 실패 호출들을 아무 문제 없이 통과시킵니다. 동시 20개 상한이라면 20 / 0.005초 = 초당 4,000개의 실패 호출이 나갈 수 있어요. 2편에서 본 "빨리 실패하는 서버는 한가해 보인다"가 여기서도 똑같이 나타납니다. 실패를 세는 쪽은 서킷 브레이커예요.

메트릭은 세마포어 방식이 resilience4j.bulkhead.available.concurrent.calls(남은 자리)와 max.allowed.concurrent.calls(전체 자리) 두 개, 스레드 풀 방식이 queue.depth, queue.capacity, thread.pool.size 등입니다. 남은 자리는 다운스트림이 느려지는 순간 줄어드는 선행 신호예요. 순간적으로 0을 찍는 일은 흔하니 지속 시간을 붙이고, 스레드 풀 방식이면 큐 깊이 대비 용량도 같이 봅니다.

(Prometheus) 남은 자리가 전체의 10% 미만으로 5분 resilience4j_bulkhead_available_concurrent_calls{name="recommend"} / resilience4j_bulkhead_max_allowed_concurrent_calls{name="recommend"} < 0.1 for: 5m

4. 서킷 브레이커는 최근 실패율을 센다

추천 서비스가 완전히 죽어서 호출마다 3초 뒤 타임아웃으로 실패한다고 해 볼게요. 벌크헤드 덕에 결제는 살아 있지만, 추천 호출 20개는 결과가 뻔한데도 3초씩 기다렸다 실패하길 반복하고 죽은 서비스에 부담도 계속 줍니다. 최근 실패가 많으면 아예 호출하지 않고 바로 실패를 돌려주는 장치가 서킷 브레이커입니다.

📖 용어: 서킷 브레이커와 폴백 (fallback)
서킷 브레이커는 최근 실패율을 보고 CLOSED(정상 호출), OPEN(즉시 거부), HALF_OPEN(몇 개만 시험 통과)을 오가는 상태 기계입니다. 폴백은 거부됐을 때 대신 돌려주는 응답이에요. 개인화 추천 대신 인기 상품 목록을 보여 주는 식입니다.
그림 3. 열리는 조건과 닫히는 조건이 서로 다른 숫자를 본다

옛 예제의 ringBuffer는 지금 없다

서킷 브레이커 예제를 찾다 보면 이런 코드를 자주 만납니다.

// 옛 API (2.0.0에서 삭제됨) CircuitBreakerConfig.custom() .failureRateThreshold(50) .waitDurationInOpenState(Duration.ofMillis(1000)) .ringBufferSizeInHalfOpenState(2) .ringBufferSizeInClosedState(2) .build();

Resilience4j의 이력을 보면 1.0.0에서 링 버퍼 구현이 슬라이딩 윈도(실패율을 계산할 범위, "최근 N건" 또는 "최근 N초")로 바뀌었고, 1.x 동안 deprecated로 남아 있던 옛 메서드는 2.0.0 소스에서 지워졌습니다(릴리스 노트에는 이 삭제가 2.0.1 항목 아래 적혀 있어요). ringBufferSizeInClosedState(n)은 1.x에서 창 크기와 최소 호출 수를 둘 다 n으로 넣는 메서드였으니 slidingWindowSize와 minimumNumberOfCalls 둘로, ringBufferSizeInHalfOpenState는 permittedNumberOfCallsInHalfOpenState로 대체됐어요. 2.x 문서 기준 기본값과 함께 쓰면 이렇습니다.

// 2.x CircuitBreakerConfig.custom() .slidingWindowType(SlidingWindowType.COUNT_BASED) // 기본 COUNT_BASED .slidingWindowSize(50) // 기본 100 .minimumNumberOfCalls(20) // 기본 100 .failureRateThreshold(50) // 기본 50 (%) .waitDurationInOpenState(Duration.ofSeconds(30)) // 기본 60초 .permittedNumberOfCallsInHalfOpenState(5) // 기본 10 .build();

옛 예제를 그대로 옮기면 생기는 일을 계산해 보겠습니다. 창 크기 2에 임계값 50%면, 개수 기준 창에서는 최소 호출 수가 창 크기를 넘을 수 없어서(소스 코드가 둘 중 작은 값으로 맞춥니다) 2건만 쌓이면 판정합니다. 2건 중 1건만 실패해도 실패율 50%이고, 비교가 "이상"이라 바로 OPEN이에요. 실패 한 번에 열리는 서킷입니다. 반대로 기본값(창 100, 최소 100)은 트래픽이 적은 서비스에서 100건을 채우는 데 한참 걸려서, 그동안은 실패율이 아무리 높아도 열리지 않아요.

옛 설명은 "링 버퍼가 가득 차면 실패율을 비교한다"고 합니다. 옛 메서드가 두 값을 같게 넣었으니 그때는 맞는 말이었지만, 지금은 창이 가득 찰 때가 아니라 minimumNumberOfCalls를 채운 때부터 계산합니다. 두 값을 따로 정하면 둘의 차이가 보여요.

서킷 브레이커가 막지 못하는 것: 실패가 쌓이기 전의 동시성, 그리고 세지 않는 실패

서킷 브레이커는 결과가 돌아와야 셉니다. 응답이 3초에서 30초로 늘면 결과가 하나도 안 돌아오는 30초 동안 실패율은 변하지 않고, 그사이 동시 호출은 계속 쌓여요. 느린 호출도 셀 수는 있지만(slowCallDurationThreshold) 기본값이 60초에 비율 100%라 정하지 않으면 사실상 꺼져 있고, 결과가 돌아오기 전의 동시성은 어차피 벌크헤드 몫이에요.

무엇을 실패로 세는지도 봐야 합니다. 기본 설정은 모든 예외를 실패로 기록해서, 요청 형식이 틀려 생긴 400 계열 예외도 실패율을 올립니다. 호출하는 쪽 버그가 멀쩡한 다운스트림을 향한 서킷을 열 수 있어요. recordExceptions, ignoreExceptions로 다운스트림 상태를 나타내는 예외만 세게 정해 둡니다. 서킷 브레이커도 인스턴스마다 따로 판단해서, 10대 중 일부만 열려 있는 상태가 흔히 생깁니다.

5. 폴백이 없는 기능은 어떻게 하나

추천 목록은 서킷이 열려도 인기 상품 목록으로 대신할 수 있습니다. 사용자는 조금 덜 맞춤인 화면을 보지만 페이지는 뜹니다. 결제는 다릅니다. "결제 서비스가 응답하지 않으니 대신 결제된 것으로 하자"는 폴백은 있을 수 없어요. 그럼 결제에는 서킷 브레이커가 쓸모없을까요?

쓸모가 있습니다. 서킷이 열렸을 때 얻는 것은 대체 응답이 아니라 빠르고 분명한 거부예요. 서킷이 없으면 결제 요청마다 타임아웃까지 기다렸다가 실패하고, 사용자는 30초 동안 돌아가는 화면을 보다가 새로고침을 누릅니다. 서킷이 열려 있으면 CallNotPermittedException이 즉시 돌아오니 "결제를 잠시 처리할 수 없어요. 결제되지 않았습니다"라고 바로 말할 수 있어요. 결제 여부가 분명하다는 점이 중요합니다. 타임아웃은 "결제가 됐는지 안 됐는지 모르는" 상태를 남기거든요.

결제를 나중에 확정해도 되는 업무라면 다른 길도 있습니다. 요청을 저장해 두고 다운스트림이 회복되면 처리하는 방식이에요. 조건이 둘 붙습니다. 같은 요청이 두 번 처리돼도 한 번만 결제되도록 멱등성 키가 있어야 하고(추적과 디버깅 시리즈 4편의 주제예요), 사용자에게 "결제 완료"가 아니라 "접수됨, 결제 확인 중"으로 안내해야 합니다. 어느 쪽을 고르든 판단 근거는 도메인 지식이라 라이브러리 설정이 대신 정해 주지 않아요.

💡 실무에서는: 폴백을 기능별로 적어 둔다
• 대체 가능 (추천, 리뷰 요약): 캐시된 값, 인기 목록, 빈 영역 숨기기
• 지연 가능 (주문 접수 후 결제 확인, 알림 발송): 저장 후 재처리. 멱등성 키 필수
• 대체도 지연도 불가 (결제 승인 자체): 즉시 거부와 분명한 안내. 성공한 척하는 폴백은 쓰지 않는다

6. 배압: 셋을 겹쳐 거는 순서와 경고

세 패턴을 묶는 말이 배압입니다. Jeff Hodges는 2013년 글 「Notes on Distributed Systems for Young Bloods」에서 배압을 위한 설계를 "과부하와 장애 동안 자원 사용에 상한을 두는 것"이라 정의하고, 배압 장치가 없으면 연쇄 장애나 메시지 유실이 일어나기 쉽다고 적습니다.

📖 용어: 배압 (backpressure)
받는 쪽이 "지금은 더 못 받는다"는 신호를 보내고, 보내는 쪽이 그 신호를 보고 덜 보내거나 빨리 포기하는 구조입니다. 신호를 받고도 계속 보내면 과부하가 보내는 쪽으로 번집니다.

비율 제한은 보내는 양에, 벌크헤드는 동시에 기다리는 양에, 서킷 브레이커는 실패가 확인된 뒤에도 계속 보내는 것에 상한을 둡니다. 세는 것이 다르니 하나가 다른 하나를 대신하지 못하고, 실제로는 겹쳐 겁니다. 이때 순서가 결과를 바꿉니다. Resilience4j 스프링 부트 문서가 밝힌 애너테이션 기본 적용 순서는 바깥에서 안쪽으로 이렇습니다(TimeLimiter는 호출 시간에 상한을 거는 모듈이에요).

Retry ( CircuitBreaker ( RateLimiter ( TimeLimiter ( Bulkhead ( 실제 호출 ) ) ) ) )

여기서 두 가지가 따라 나옵니다. 첫째, Retry가 가장 바깥이라 재시도마다 서킷 브레이커를 다시 지납니다. 열린 서킷이 던진 CallNotPermittedException까지 재시도하면 횟수만 소모합니다. Retry는 기본으로 모든 예외를 재시도하니, 5편처럼 retryExceptions로 대상을 좁혀 이 예외가 빠지게 둡니다. 둘째, 서킷 브레이커가 비율 제한과 벌크헤드를 감싸고 있어서, 기본 설정이면 RequestNotPermitted와 BulkheadFullException도 실패로 기록됩니다. 우리 쪽 상한에 걸린 거부가 다운스트림 실패율로 잡히는 거죠. 이 거부를 "다운스트림이 감당 못 한다는 신호"로 볼지 "우리 설정 문제"로 볼지 정하고, 후자라면 ignoreExceptions에 넣습니다.

마지막으로 경고입니다. 서킷 브레이커의 메트릭은 resilience4j.circuitbreaker.state(상태별 게이지, 현재 상태만 1), failure.rate, slow.call.rate, calls(kind 태그로 successful, failed, ignored를 나누는 타이머), not.permitted.calls(거부된 호출 수 카운터) 등이에요.

(Prometheus) 열린 서킷이 하나라도 있으면 max(resilience4j_circuitbreaker_state{state="open"}) == 1 (Prometheus) 열리기 전 선행 신호: 실패율이 임계값(50)의 80%를 넘음 resilience4j_circuitbreaker_failure_rate{name="payment"} >= 40

상태 경고가 울릴 때는 이미 사용자가 폴백이나 거부를 받고 있으니 선행 신호는 아닙니다. 잠깐 열렸다 닫히는 일이 잦다면 열린 상태가 몇 분 이어질 때만 울리게 하거나 resilience4j_circuitbreaker_not_permitted_calls_total 증가율을 보는 편이 덜 시끄러워요. 실패율 게이지에는 함정이 있습니다. 소스 코드와 인터페이스 주석을 보면 기록된 호출이 minimumNumberOfCalls보다 적을 때 failure.rate는 -1을 돌려줍니다. 트래픽이 적은 새벽에 이 값으로 "실패율이 떨어졌다"를 판단하면 안 되고, 평균을 내면 -1이 섞여 값이 내려갑니다.

셋 다 미리 정해 둔 숫자로 판단한다는 점은 같습니다. 초당 100개, 동시 20개, 실패율 50%. 이 숫자는 다운스트림이 증설되거나 코드가 바뀌면 낡아요. 숫자를 미리 정하지 않고 관측으로 상한을 찾아가는 방법은 7편에서 봅니다.

✍️ 오늘의 요약
비율 제한은 기간당 허가 수를, 벌크헤드는 지금 실행 중인 수를, 서킷 브레이커는 최근 실패율을 셉니다. 그래서 비율 제한은 느려진 다운스트림을, 벌크헤드는 빨리 실패하는 다운스트림을, 서킷 브레이커는 결과가 돌아오기 전에 쌓이는 동시성을 막지 못해요. limitForPeriod는 동시 실행 수가 아니라 주기당 허가 수이고, 옛 ringBuffer 설정은 slidingWindowSize, minimumNumberOfCalls, permittedNumberOfCallsInHalfOpenState로 바뀌었습니다.

폴백이 없는 기능에서 서킷 브레이커가 주는 것은 대체 응답이 아니라 빠르고 분명한 거부입니다. 어떤 패턴을 고를지는 무엇을 셀지를 고르는 일이에요.
