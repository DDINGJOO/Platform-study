6편에서는 비율 제한, 벌크헤드, 서킷 브레이커가 각각 다른 숫자를 센다고 정리했습니다. 비율 제한은 기간당 허가 수를, 벌크헤드는 지금 실행 중인 호출 수를, 서킷 브레이커는 최근 호출의 실패율을 세요. 그래서 비율 제한은 느려진 하위 서비스(6편의 다운스트림)를, 벌크헤드는 빨리 실패하는 하위 서비스를 막지 못한다고 했습니다. 표로 정리하면 그럴듯한데, 정말 그렇게 움직일까요?

이번 글은 같은 하위 서비스 앞에 세 패턴을 따로 걸고, 같은 부하를 주면서 하위 서비스를 먼저 느리게, 다음에는 빨리 실패하게 만들었습니다. 6편의 예상은 대부분 맞았어요. 그런데 예상하지 못한 것도 셋 나왔습니다. 하위가 느려지자 비율 제한의 거절이 오히려 0건으로 줄었고, 서버가 잰 결제 호출 p99는 9ms인데 클라이언트에서는 수천 건이 5초 타임아웃이었고, 서킷 브레이커로 벌크헤드를 감싸자 한 건도 실패하지 않은 하위 서비스에 서킷이 3분 동안 16번 열렸어요. 화면과 숫자는 전부 직접 돌린 결과입니다.

1. 실습 환경: 호출하는 쪽 네 대와 하위 서비스 하나

하위 서비스(downstream)는 엔드포인트가 둘이에요. /recommend는 실행 중에 지연과 실패율을 바꿀 수 있고, /pay는 늘 5ms 만에 성공합니다. 호출하는 쪽(order)은 같은 이미지로 네 대를 띄우고 /recommend 호출을 감싸는 방법만 다르게 했어요. /pay 호출은 네 대 모두 아무것도 감싸지 않았습니다. 추천 목록의 장애가 결제 호출까지 번지는지를 보려는 장치예요.

그림 1. 같은 하위 서비스 앞에 감싸는 방법만 다른 호출자 네 대를 세웠다
📖 용어: 요청 처리 스레드 (Tomcat worker thread)
스프링 MVC 앱에서 들어온 요청 하나를 맡아 응답을 보낼 때까지 붙잡고 있는 스레드입니다. 개수에 상한이 있어서(기본 200, 이 실습은 25), 다 차면 새 요청은 스레드가 빌 때까지 기다려요. 하위 호출을 기다리는 동안에도 스레드는 묶여 있습니다.

스레드를 25개로 줄인 이유는 스레드가 다 차는 장면을 작은 부하로 만들기 위해서예요. k6는 호출자마다 /recommend 초당 40건, /pay 초당 20건을 11분 동안 보냅니다. 하위 서비스 상태는 스크립트가 시간에 맞춰 바꿔요.

구간 하위 /recommend 세 패턴 설정 (Resilience4j 2.4.0 코어) 0~2분 50ms, 실패 0 RateLimiter 1초마다 허가 30개, timeoutDuration 0 2~5분 1000ms, 실패 0 Bulkhead maxConcurrentCalls 10, maxWaitDuration 0 5~6분 50ms, 실패 0 CircuitBreaker COUNT_BASED 창 20, 최소 10건, 6~9분 50ms, 실패 100% 실패율 50%, OPEN 10초, HALF_OPEN 시험 5건 9~11분 50ms, 실패 0 하위 호출 읽기 타임아웃 3초, k6 는 5초까지 기다림

호출하는 쪽은 거절 이유를 응답 코드로 구분해요. 비율 제한과 벌크헤드 거절은 429, 서킷 OPEN은 503, 하위 실패는 502입니다. 실습 코드는 GitHub 저장소의 labs/traffic/tm-06-resilience4j에 있어요.

git clone https://github.com/DDINGJOO/Platform-study.git cd Platform-study/labs/traffic/tm-06-resilience4j docker compose up -d --build ./scripts/phases.sh # k6 11분 + 시간에 맞춘 장애 주입 python3 scripts/summarize.py # 구간별 숫자를 Prometheus 에서 뽑는다 # Grafana: http://localhost:28000 → 대시보드 「실습-6 …」 docker compose --profile load down -v # 끝나면 정리

장애 주입은 curl -X POST 'localhost:28082/admin/fault?delayMs=1000&errorRate=0' 한 줄이에요. phases.sh는 이 명령을 2분, 5분, 6분, 9분에 값만 바꿔 보냅니다.

resilience4j-spring-boot3는 스프링 부트 4에서 일부러 멈춘다

앱은 스프링 부트 4.1.1입니다. 처음에는 익숙한 resilience4j-spring-boot3 스타터를 붙여 봤는데 기동하자마자 멈췄어요.

APPLICATION FAILED TO START Description: Module 'io.github.resilience4j:resilience4j-spring-boot3' is only compatible with Spring Boot 3.x Action: Update your project to use 'io.github.resilience4j:resilience4j-spring-boot4'
📖 용어: 스프링 부트 스타터와 자동 구성
의존성 하나만 넣으면 필요한 빈을 알아서 등록해 주는 묶음이 스타터입니다. Resilience4j 스타터는 application.yml의 설정을 읽어 레지스트리를 만들고, @CircuitBreaker 같은 애너테이션을 애스펙트로 처리해요. 스프링 부트 메이저 버전마다 자동 구성 API가 달라서 모듈도 버전별로 따로 나옵니다.

클래스를 못 찾아서 깨진 게 아니라 모듈이 스스로 거부한 거예요. 2.4.0 소스의 SpringBoot3Verifier가 스프링 부트 메이저 버전을 읽어서 4면 이 예외를 던집니다. 같은 2.4.0(2026년 3월 14일 릴리스)에 resilience4j-spring-boot4 모듈이 새로 들어왔고(릴리스 노트의 "Add support for Spring Boot 4 / Spring Cloud 5"), 이 모듈로 바꾸자 같은 앱이 떠서 @CircuitBreaker 애너테이션과 /actuator/circuitbreakers가 동작했어요. 두 경우 모두 저장소의 compat/로 다시 확인할 수 있습니다.

그래도 본 실습은 스타터 없이 코어 모듈(resilience4j-ratelimiter, -bulkhead, -circuitbreaker, -micrometer)을 직접 썼어요. 무엇을 세는지 보려는 실습이라, 설정값과 감싸는 순서가 YAML과 애스펙트 순서 뒤가 아니라 자바 코드 한 파일에 그대로 보이는 편이 낫다고 판단했습니다.

// Guards.java 일부. 서킷 브레이커가 벌크헤드를 감싸는 조합(order-cbbh) case "cb-over-bulkhead" -> CircuitBreaker.decorateSupplier(circuitBreaker, Bulkhead.decorateSupplier(bulkhead, call));

2. 하위가 느려지면: 비율 제한은 거절을 멈췄다

2분 시점에 하위 /recommend를 1000ms로 늦췄습니다. 아래 표의 앞 세 열은 서버가 센 응답(http_server_requests)을 구간마다 앞뒤 20초를 빼고 초당으로 평균 낸 값이에요. 마지막 열은 k6가 실제로 받은 200을 어림한 값입니다. k6는 11분 전체의 합계만 남겨서, 정상 구간 5분 동안 받은 몫(초당 30건 또는 40건 × 300초)을 빼고 느려짐 180초로 나눴어요. 빨리 실패 구간에는 200이 없었습니다.

/recommend (초당) 서버가 센 응답 스레드 k6 가 받은 200 200 429 503 최대 (어림) 정상(50ms) order-rl 30.0 10.0 0 2 order-bh 40.0 0 0 2 order-cb 40.0 0 0 2 느려짐(1000ms) order-rl 24.9 0 0 25 약 2.3 (9,419 - 9,000) order-bh 9.8 30.2 0 10 약 9.7 (13,750 - 12,000) order-cb 24.9 0 0 25 약 1.5 (12,269 - 12,000)

서버가 센 숫자와 클라이언트가 받은 숫자가 크게 다릅니다. 비율 제한과 서킷 브레이커 쪽은 서버가 초당 24.9건을 200으로 끝냈는데 k6가 5초 안에 받은 건 초당 2건 안팎이었어요. 나머지는 k6가 5초에 연결을 끊은 뒤에야 서버가 처리를 마친 요청입니다. 이유는 3절에서 봐요. 벌크헤드 쪽만 두 숫자가 맞았습니다.

정상 구간의 비율 제한은 설정대로 움직였어요. 초당 40건 중 30건을 통과시키고 10건을 429로 돌려보냈습니다. 그런데 하위가 느려지자 429가 0건이 됐어요. 6편은 "비율 제한은 하나도 거부하지 않고 스레드가 묶인다"고 예상했는데, 실제로는 평소에 하던 거절까지 멈췄습니다.

그림 2. 하위가 느려지자 거절(노랑)은 사라지고 스레드가 25개로 찼다

오른쪽 그래프가 이유를 보여 줘요. 요청 하나가 1초씩 스레드를 잡으니 스레드 25개로는 초당 25건만 처리할 수 있습니다. 나머지 요청은 비율 제한에 닿기도 전에 스레드를 기다려요. 비율 제한에 도착하는 요청이 초당 25건이 되니 허가 30개가 남아돌고, 거절할 이유가 없어진 거예요. 비율 제한은 자기 앞까지 들어온 요청만 셀 수 있습니다. 병목이 앞단의 스레드 풀로 옮겨 가면 비율 제한 지표는 오히려 평온해 보여요.

서킷 브레이커도 서버 쪽 숫자가 똑같았습니다(성공 24.9, 스레드 25). 응답은 1초로 늦어졌지만 3초 타임아웃 안에 성공으로 돌아왔으니 실패율은 0%였고 서킷은 닫혀 있었어요. 6편의 "결과가 돌아오기 전에 쌓이는 동시성은 서킷 브레이커가 막지 못한다"가 그대로 나왔습니다. slowCallDurationThreshold(기본 60초)를 정했다면 느린 호출을 실패로 볼 수 있었겠지만, 이번 실행에서는 기본값을 그대로 둬서 확인하지 않았어요.

벌크헤드만 다르게 움직였어요. 동시 10개 상한에 걸려 초당 9.8건만 하위로 보내고 30.2건을 바로 429로 돌려보냈습니다. 스레드는 10개 이상 쓰지 않았어요.

그림 3. 벌크헤드는 스레드를 10개까지만 내주고 나머지는 바로 거절했다

3. 서버 p99는 9ms, 클라이언트는 5초 타임아웃

스레드가 다 찼다면 결제 호출(/pay)은 어땠을까요? 서버 쪽 지표부터 봤습니다. 스프링이 내보내는 http_server_requests로 계산한 /pay p99예요.

그림 4. 서버가 잰 결제 호출 p99는 몇 번 튄 것 말고는 11분 내내 10ms 안팎이었다

네 대 모두 몇 번 50ms 남짓 튄 것 말고는 10ms 안팎이에요. 느려짐 구간 전체로 계산한 p99도 9ms였습니다. 그런데 같은 시간에 k6는 전혀 다른 숫자를 셌어요.

k6 가 센 5초 무응답 (11분 전체, 스레드가 다 찬 건 느려짐 구간뿐) /pay /recommend order-rl 3,134 6,397 order-cb 3,247 6,619 order-bh 0 0 order-cbbh 0 0

느려짐 구간 3분 동안 /pay는 대마다 3,600건쯤 나갔으니, 비율 제한과 서킷 브레이커 쪽 결제 호출은 대부분 5초 안에 응답을 받지 못한 셈이에요. 서버 지표가 이걸 못 본 이유는 측정이 시작되는 지점에 있습니다. 스프링의 관측 필터는 요청이 스레드를 잡은 뒤에야 시간을 재기 시작해요. 스레드를 기다린 시간은 서버 쪽 지표 어디에도 기록되지 않아요. 클라이언트인 k6만 그 시간을 셉니다. Tomcat은 연결을 최대 8,192개(maxConnections 기본값)까지 받아 두고 스레드가 비기를 기다리게 하니, 그 대기는 꽤 길어질 수 있어요. 벌크헤드를 건 두 대만 무응답이 0건이었습니다. 추천 호출이 스레드를 10개까지만 쓰니 결제 호출이 나머지 15개를 쓸 수 있었어요.

📖 용어: maxConnections
Tomcat이 동시에 받아 둘 수 있는 연결 수입니다(NIO 기본 8,192). 요청 처리 스레드보다 훨씬 커서, 스레드가 다 찬 뒤에도 연결은 계속 받아 두고 요청은 스레드가 빌 때까지 기다려요. 클라이언트 입장에서는 연결은 됐는데 응답이 안 오는 상태입니다.
📖 용어: 스크레이프 (scrape)
Prometheus가 일정 간격(이 실습은 2초)으로 앱의 /actuator/prometheus를 HTTP로 불러 지표를 가져가는 동작입니다. 앱 입장에서는 이것도 요청 하나라서 요청 처리 스레드가 있어야 응답할 수 있어요.
⚠️ 주의: 스레드가 다 차면 지표도 사라진다
첫 실행은 지표 엔드포인트를 앱과 같은 8080 포트에 뒀습니다. 느려짐 구간이 시작되자 order-rl과 order-cb의 스크레이프가 context deadline exceeded로 실패했고, up이 0이 됐어요. 느려짐 시작 후 1분이 안 되는 사이에 대마다 22~23번 실패했습니다. 지표가 가장 필요한 순간에 그 두 대의 그래프가 비었습니다. management.server.port로 지표를 별도 포트(9090)에 띄우자 해결됐어요. 별도 포트는 커넥터가 달라서 요청 처리 스레드 풀도 따로 씁니다. 이 글의 그래프와 숫자는 전부 이렇게 바꾼 두 번째 실행에서 나왔어요.

느려짐이 끝나는 순간에도 볼 것이 있었습니다. 그림 2에서 5분 무렵 429가 순간 초당 300건 넘게 튀었어요. 서킷 브레이커 쪽은 같은 순간에 200이 초당 270건 가까이 튀었습니다. Tomcat이 받아 두었던 요청이 스레드가 풀리자 한꺼번에 처리된 거예요. 5초 넘게 기다린 요청이라면 k6는 이미 연결을 끊은 뒤였으니, 서버는 아무도 기다리지 않는 응답을 만들고 있었습니다.

4. 하위가 빨리 실패하면: 벌크헤드는 초당 40건의 실패를 통과시켰다

6분 시점에 하위를 50ms로 되돌리고 실패율을 100%로 올렸습니다.

빨리 실패(100%) 200 429 502 503 스레드 최대 order-rl 0 10.0 30.0 0 2 order-bh 0 0 40.0 0 2 order-cb 0 0 0.5 39.5 0 하위 서비스가 받은 /recommend: 초당 71.0 (네 대 합)

벌크헤드는 초당 40건을 그대로 하위로 보내 40건의 502를 받았어요. 실패가 50ms 만에 돌아오니 자리 10개는 거의 비어 있었고, 벌크헤드가 보기에는 아무 문제가 없었습니다. 비율 제한은 정상 때와 똑같이 30건을 통과시키고 10건을 거절했어요. 두 패턴 모두 실패율을 보지 않으니 실패한 하위 서비스에 정상 때와 같은 양을 계속 보낸 겁니다.

서킷 브레이커만 하위로 가는 호출을 끊었어요. 실패율이 50%에 닿자 OPEN이 됐고, 그 뒤로는 초당 39.5건을 하위에 보내지 않고 503으로 돌려보냈습니다. 남은 0.5건은 HALF_OPEN의 시험 호출이에요. 10초마다 5건을 보내 보고, 전부 실패하니 다시 OPEN으로 돌아갔습니다. 3분 동안 이 왕복이 17번 있었어요.

그림 5. 빨리 실패하는 구간(13:49 이후)에는 두 서킷이 함께 열렸다. 그 앞의 주황 구간은 5절의 이야기다
📖 용어: HALF_OPEN 시험 호출
OPEN 상태로 정해진 시간(이 실습은 10초)이 지나면 서킷은 HALF_OPEN이 되어 정해진 수(5건)만 하위로 보내 봅니다. 그 결과의 실패율이 임계값 아래면 CLOSED로, 아니면 다시 OPEN으로 갑니다. 하위가 살아났는지 확인하는 유일한 통로예요.

하위가 회복된 13:52:33(한국 시간)에서 3초 뒤 다음 HALF_OPEN 시험이 성공하면서 서킷이 닫혔어요. 6편이 짚은 대로 실패율 게이지가 판정 전에는 -1이라는 것도 확인했습니다. 기동 직후 resilience4j_circuitbreaker_failure_rate는 -1이었고, 서킷 전이 로그에도 HALF_OPEN으로 넘어간 직후의 실패율이 -1.0으로 찍혔어요.

5. 서킷이 벌크헤드를 감싸면 실패하지 않은 하위에 서킷이 열린다

네 번째 호출자 order-cbbh는 서킷 브레이커가 벌크헤드를 감싸게 했습니다. 스프링 부트 애너테이션의 기본 적용 순서(서킷 브레이커가 벌크헤드보다 바깥)와 같은 모양이에요. 6편은 이 순서에서 벌크헤드 거절(BulkheadFullException)이 서킷의 실패로 기록된다고 했습니다. 느려짐 구간의 결과는 이랬어요.

느려짐(1000ms) 200 429 503 스레드 최대 order-bh 9.8 30.2 0 10 order-cbbh 1.3 0.9 37.8 11
그림 6. 하위는 한 건도 실패하지 않았는데 응답 대부분이 503(서킷 OPEN)이었다

하위 서비스는 느렸을 뿐 한 건도 실패하지 않았어요. 그런데 서킷이 열렸습니다. 벌크헤드가 초당 30건을 거절했고, 서킷은 그 거절을 실패로 셌기 때문이에요. 전이 로그를 보면 지연을 넣은 바로 그 초에 열렸습니다. 로그 시각은 UTC라서 한국 시간으로는 9시간을 더해요(04:45:33은 13:45:33).

04:45:33 State transition from CLOSED to OPEN 50.0 ← 지연 주입과 같은 초 04:45:43 State transition from OPEN to HALF_OPEN -1.0 04:45:44 State transition from HALF_OPEN to CLOSED -1.0 ← 시험 5건은 자리 10개 안이라 성공 04:45:45 State transition from CLOSED to OPEN 100.0 ← 닫히자마자 다시 벌크헤드가 차서 열림 ... 3분 동안 CLOSED → OPEN 16번

HALF_OPEN의 시험 호출 5건은 벌크헤드 자리 10개 안에 들어가니 1초 뒤 성공으로 돌아오고, 서킷은 닫힙니다. 닫히는 순간 초당 40건이 다시 몰려 벌크헤드가 차고, 거절이 실패로 쌓여 0.5초 만에 다시 열려요(로그 04:45:44.948 닫힘 → 04:45:45.447 열림). 결과적으로 벌크헤드만 걸었을 때 초당 9.8건이던 성공이 1.3건으로 줄었습니다. 우리 쪽 상한에 걸린 거절을 하위 서비스의 실패로 세면, 서킷은 하위가 아니라 우리 설정에 반응합니다.

그럼 벌크헤드 거절을 실패에서 빼면 어떻게 될까요? 서킷 설정에 ignoreExceptions(BulkheadFullException.class)만 더한 호출자(order-cbbh-ign)를 기본 설정 호출자와 나란히 띄우고 4분짜리 확인을 따로 돌렸어요. 1분 정상, 2분 느려짐, 1분 정상입니다. 이 실행은 다른 실습이 같은 장비에서 함께 돌던 때라 잡음이 큽니다. 기본 호출자의 서킷은 지연을 넣기 18초 전(14:37:39, 지연 주입은 14:37:57)에 이미 한 번 열렸고, 실행 끝 무렵에는 Docker가 몇 분간 응답하지 않아 k6가 10분 넘게 끝나지 못했어요. 그래서 서버 쪽 숫자를 느려짐 구간의 뒤쪽 100초로만 비교했습니다.

느려짐 100초 200/s 429/s 503/s 서킷 OPEN 횟수 order-cbbh (기본) 1.4 0.9 38.8 9 order-cbbh-ign (벌크헤드 무시) 8.8 32.8 0 0

벌크헤드 거절을 무시하자 서킷은 한 번도 열리지 않았고, 서버 쪽 숫자는 벌크헤드만 건 order-bh(초당 9.8건 성공, 30.2건 거절)와 비슷해졌어요. 다만 같은 실행의 k6는 order-cbbh-ign에서도 /recommend 1,160건, /pay 644건의 5초 무응답을 셌습니다(Docker가 멈춘 시간을 포함한 합계라 구간을 나눌 수 없어요). 본 실행의 order-bh는 0건이었으니, 이 확인은 "서킷이 열리지 않는다"까지만 보여 준다고 봐야 합니다. 6편이 권한 대로 우리 쪽 거절은 ignoreExceptions에 넣으면 서킷이 그 거절에 반응하지 않아요. 다시 해 보려면 docker compose --profile ignore up -d --build 뒤에 ./scripts/ignore-check.sh를 돌립니다. 이 호출자는 프로필로만 뜨니 기본 실행에서는 Prometheus 대상 order-cbbh-ign:9090이 down으로 보여요. 다만 이건 "벌크헤드가 찬 것은 하위 상태와 무관하다"고 판단했을 때의 선택이에요. 벌크헤드가 차는 원인이 늘 하위의 지연이라면 그 신호를 서킷이 받게 둘 수도 있습니다.

⚠️ 주의: 2초마다 긁는 게이지로는 서킷 전이를 다 못 본다
로그에는 3분 동안 CLOSED → OPEN이 16번 있었지만 그림 5의 주황 선은 다섯 덩어리로만 보여요. CLOSED와 HALF_OPEN이 1초 남짓씩이라 2초 간격 스크레이프와 그래프의 점 간격 사이로 빠집니다. 서킷이 얼마나 자주 오가는지는 상태 게이지가 아니라 onStateTransition 이벤트(로그나 카운터)로 세야 해요.

6. 지표로 볼 수 있었던 것과 없었던 것

마지막으로 라이브러리 지표를 정리했어요. resilience4j-micrometer 2.4.0을 그대로 등록하면 RateLimiter는 available_permissions와 waiting_threads 게이지 둘, 세마포어 Bulkhead는 available_concurrent_calls와 max_allowed_concurrent_calls 게이지 둘만 나옵니다. 거절 건수 카운터는 없어요. 이번 실습에서 초당 30건의 벌크헤드 거절은 라이브러리 지표가 아니라 호출하는 쪽이 돌려준 429로 셌습니다. 서킷 브레이커만 not_permitted_calls_total 카운터가 있어요.

대기 스레드 게이지(waiting_threads)는 실행 내내 0이었습니다. timeoutDuration을 0으로 둬서 허가를 기다리는 스레드가 생기지 않으니까요. 6편이 경고 예시로 든 "대기 스레드가 5분 내내 0보다 크면" 규칙은 이 설정에서 울릴 일이 없습니다.

💡 실무에서는: 장애 중에도 보이게 계측한다
• 지표 엔드포인트는 management.server.port로 앱 포트와 떼어 둬요. 스레드가 다 찬 순간이 가장 보고 싶은 순간이에요
• 비율 제한과 벌크헤드의 거절은 호출하는 쪽에서 직접 세요. 예외 종류별 카운터나 응답 코드면 충분해요
• 서버 지연 지표에는 스레드를 기다린 시간이 없어요. 사용 중 스레드 수(tomcat_threads_busy_threads)를 같이 보고, 가능하면 호출하는 쪽이나 로드 밸런서에서 잰 지연도 함께 봐요
• 서킷 브레이커가 다른 패턴을 감싼다면 RequestNotPermitted와 BulkheadFullException을 실패로 셀지부터 정해요
✍️ 오늘의 요약
같은 장애에 세 패턴을 걸어 보니 6편의 예상은 대부분 맞았다. 하위가 느려지자 비율 제한과 서킷 브레이커는 아무것도 거절하지 않은 채 스레드 25개를 다 내줬고, 벌크헤드만 10개로 묶었다. 하위가 빨리 실패하자 비율 제한과 벌크헤드는 실패를 그대로 통과시켰고, 서킷 브레이커만 호출을 끊었다.

예상 밖의 결과는 전부 "어디서 세느냐"에서 나왔다. 비율 제한은 앞단에서 막힌 요청을 셀 수 없어 거절이 0이 됐고, 서버 지표는 스레드를 기다린 시간을 몰라 결제 p99 9ms와 성공 24.9건을 보였지만 클라이언트가 받은 성공은 초당 2건 안팎이었고, 벌크헤드를 감싼 서킷은 우리 쪽 거절을 하위의 실패로 셌다. 패턴을 고르는 일은 무엇을, 어디서 셀지를 고르는 일이다.
