서버 세 대가 초당 150건을 나눠 받고 있습니다. 한 대를 더 붙였어요. 스프링 부트는 5초 만에 떴고, 헬스 체크도 바로 통과했습니다. 로드 밸런서는 새 서버에 4분의 1을 보내기 시작했어요. 그 순간부터 5초 동안 새 서버로 간 요청의 중앙값이 8초였습니다.

3편은 헬스 체크 통과가 준비 완료가 아니고, 그래서 신규 인스턴스에는 slow start 같은 보호관찰이 필요하다고 했어요. 이번 글은 그 장면을 직접 만들어 봅니다. 부하 중에 인스턴스를 새로 띄우고, Envoy의 slow start를 켜고 끄고, 라운드로빈과 LEAST_REQUEST를 바꿔 가며 첫 2분을 비교했어요. 결과 하나는 예상과 달랐습니다.

🧭 이 글에서 확인할 것
• 갓 뜬 JVM은 부하를 바로 받으면 얼마나 느린가?
• slow start를 켜면 새 인스턴스의 몫이 정말 식대로 오르나?
• slow start 없이 LEAST_REQUEST만 쓰면 어떻게 되나?
• 둘을 같이 켜면 Envoy 안에서 무엇이 바뀌나?

1. 실습 환경: 세 대가 일하는 중에 네 번째가 뜬다

실습-1, 2와 같은 앱인데 이번에는 잠자는 대신 CPU 일을 시켰어요. 요청마다 객체 40개를 만들고, 정렬하고, 문자열로 만들고, 정규식으로 훑고, SHA-256을 계산하는 일을 100번 반복합니다. 데워진 뒤에는 요청 하나에 3~4ms 걸려요. 컨테이너마다 CPU는 0.5개로 묶었습니다. CPU를 많이 주면 JIT 컴파일이 금방 끝나서 차이가 잘 안 보이기 때문이에요. 쿠버네티스에서 CPU 한도를 500m로 두는 경우와 비슷한 조건입니다.

그림 1. 같은 실행을 Envoy 설정만 바꿔 네 번 돌렸다

Envoy는 네 설정 모두 액티브 헬스 체크를 겁니다. app-4 컨테이너가 뜨면 Docker DNS에 이름이 생기고, Envoy가 1초 안에 그 주소를 호스트로 추가해요(dns_refresh_rate: 1s, 기본값은 5초). 하지만 첫 헬스 체크를 통과하기 전에는 요청을 보내지 않습니다.

📖 용어: 액티브 헬스 체크 (active health check)
로드 밸런서가 실제 요청과 별개로 서버에 검사 요청을 주기적으로 보내 상태를 판정하는 방식입니다. 이 실습은 1초마다 /actuator/health를 부르고, 1초 안에 200이 안 오면 실패로 셉니다. 두 번 연속 실패하면 빼고, 한 번 성공하면 다시 넣어요.
# envoy/rr-ss.yaml (일부) type: STRICT_DNS dns_refresh_rate: 1s # 새 컨테이너 이름을 1초마다 다시 조회(기본 5초) load_balancing_policy: policies: - typed_extension_config: name: envoy.load_balancing_policies.round_robin typed_config: "@type": type.googleapis.com/envoy.extensions.load_balancing_policies.round_robin.v3.RoundRobin slow_start_config: slow_start_window: 60s aggression: { default_value: 1.0, runtime_key: lab.aggression } # 1.0 = 선형 min_weight_percent: { value: 10 } # 바닥 10% (기본값) health_checks: - timeout: 1s interval: 1s no_traffic_interval: 1s # 기본 60초. 아래 주의 상자 참고 unhealthy_threshold: 2 healthy_threshold: 1 http_health_check: { path: /actuator/health }
📖 용어: slow start 창 (slow_start_window)
새 호스트의 가중치를 깎아 주는 기간입니다. Envoy 문서에 따르면 액티브 헬스 체크가 있으면 호스트가 헬스 체크로 healthy가 된 순간부터 세고, 없으면 클러스터에 들어온 순간부터 셉니다. 창이 끝나면 원래 가중치로 돌아가요.
Envoy 1.39.3 · Spring Boot 4.1.1 (Java 21) · Prometheus 3.15.0 · Grafana 13.2.3 · k6 2.3.0 실행 환경: Docker Desktop, Apple M5 Pro, 앱 컨테이너당 CPU 0.5개 git clone https://github.com/DDINGJOO/Platform-study.git cd Platform-study/labs/traffic/tm-03-slow-start docker compose up -d --build ./run.sh rr && mv out/rr out/warmup-rr # app-1~3을 데우는 첫 실행 ./run.sh rr # 각 150초, 30초에 app-4 기동 ./run.sh rr-ss ./run.sh lr ./run.sh lr-ss docker compose --profile load down -v

실습 코드는 GitHub 저장소(DDINGJOO/Platform-study)의 labs/traffic/tm-03-slow-start에 있어요. run.sh는 app-4를 내리고 Envoy를 새 설정으로 띄운 뒤, 부하를 시작하고 30초 뒤에 docker compose up -d app-4를 실행합니다. 표는 join-report.py가 Envoy 접근 로그에서 app-4 기동 후 120초만 잘라 계산해요.

⚠️ 주의: 요청이 없는 클러스터는 헬스 체크를 60초마다 한다
처음에는 Envoy를 띄우고 요청을 안 보낸 상태에서 호스트가 전부 failed_active_hc로 한참 남아 있었어요. 통계를 보니 헬스 체크를 4번만 하고 멈춰 있었습니다. Envoy API 문서에 따르면 트래픽을 받은 적 없는 클러스터는 interval 대신 no_traffic_interval(기본 60초) 간격으로 검사해요. 그동안 호스트가 전부 unhealthy라 Envoy는 panic 모드로 전부에 보냈고, lb_healthy_panic 카운터가 올라갔습니다. 실습에서는 1초로 줄였어요.

2. slow start 없는 라운드로빈: 새 서버가 빠졌다 돌아왔다

ROUND_ROBIN, app-4 기동 후 120초 (Envoy 접근 로그) app-4 첫 요청: 컨테이너 시작 5.7초 뒤 (스프링 기동 4.3초) app-4 몫 22.3% (4006건) app-4 첫 요청부터 5초 구간별 구간 app-4 몫 app-4 p50 app-4 p99 전체 p99 0~5초 19.2% 8128ms 9988ms 9954ms 5~10초 0.0% - - 42ms 10~15초 18.1% 741ms 1573ms 1364ms 15~20초 25.1% 4ms 279ms 224ms 20초~ 25.0% 3ms 4~7ms 4~7ms 200ms 넘은 요청 292건 (그중 app-4 287건), 1초 넘은 요청 171건, 최대 10.0초 200이 아닌 응답 5건 (504 두 건, 클라이언트 연결 끊김 세 건)

처음 5초 동안 app-4로 간 144건의 중앙값이 8.1초였어요. 데워진 뒤 3ms짜리 일입니다. 명목상 몫은 초당 37.5건이지만, 이 5초 안에 실제로 시작된 요청은 초당 28.8건이었어요(아래에서 볼 헬스 체크 제외 때문에 4초쯤만 받았습니다). 그 정도 속도도 막 뜬 JVM이 처리하지 못해 줄이 쌓였고, 줄이 쌓인 만큼 늦어졌어요.

그림 2. 수집이 잡힌 뒤 약 7초 동안 새 JVM은 1초마다 1초 넘게 JIT 컴파일을 했다

그림 2는 같은 실행에서 Micrometer가 내보내는 jvm_compilation_time_ms_total의 증가 속도예요. app-4 선은 15시 2분 14초에 처음 나타납니다. 컨테이너를 띄운 지 20초, 첫 요청을 받은 지 약 14초 뒤예요. 그 전 구간은 값이 비어 있어서, 가장 밀렸던 처음 몇 초의 컴파일량은 이 그래프로 알 수 없어요(과부하로 수집이 실패한 것으로 보이지만, 스택을 내린 뒤라 확인하지 못했습니다). 잡힌 구간에서는 1초에 1,000ms 넘게 컴파일을 하다가 약 7초 뒤 50ms 아래로 떨어졌어요. 컴파일러 스레드가 여럿이라 벽시계 시간보다 클 수 있습니다. CPU 0.5개 중 상당 부분을 컴파일러가 쓰는 동안 요청이 들어왔다는 뜻이에요. 컴파일이 잦아든 시점과 지연이 정상으로 돌아온 시점(첫 요청 후 15~20초 구간)이 비슷했어요.

📖 용어: JIT 워밍업
JVM이 자주 실행되는 메서드를 골라 기계어로 컴파일할 때까지 느리게 도는 구간입니다. 실제로 코드가 돌아야 무엇을 컴파일할지 정해지기 때문에, 보통은 들어오는 요청이 이 구간을 지나가게 만들어요.

밀린 새 서버는 헬스 체크에서 빠졌다

표의 5~10초 구간에 app-4가 요청을 하나도 받지 않았어요. 접근 로그로 보면 app-4는 컨테이너 시작 5.7초 뒤부터 9.6초까지 요청을 받다가 끊겼고, 17.1초에 다시 받기 시작했어요. 실행 당시 Envoy 지표 membership_healthy를 2초 간격으로 조회했을 때도 12~18초 표본에서 healthy 호스트가 4대가 아니라 3대였어요(조회 결과는 out/rr/membership-healthy.txt). 헬스 체크 요청도 같은 줄에 서서 1초 타임아웃을 넘겼고, 두 번 연속 실패해서 빠진 겁니다. 이 실행의 헬스 체크 실패는 10번이었고, 스프링이 뜨기 전 실패만 있었던 LEAST_REQUEST 실행은 4번이었어요.

빠진 동안 app-4는 쌓인 줄을 처리할 시간을 얻었어요. 다시 들어온 뒤에도 10~15초 구간은 p50 741ms로 느렸습니다. 헬스 체크가 우연히 보호관찰 역할을 했지만, 그 대가로 사용자 요청 292건이 200ms를 넘었고, 그중 171건은 1초 넘게 기다렸습니다.

3. slow start를 켜면 몫이 식대로 오른다

같은 라운드로빈에 slow start 60초를 켰습니다.

그림 3. 새 서버의 몫이 1분에 걸쳐 직선으로 오르고, 기존 세 대의 몫이 그만큼 내려온다

Envoy 문서의 식은 "새 가중치 = 원래 가중치 × max(바닥, 경과 시간 ÷ 창)"이에요(aggression 1.0일 때). 라운드로빈에서 원래 가중치가 모두 같으니 app-4의 몫은 f ÷ (3 + f)가 됩니다. f는 깎인 비율이에요. 5초 구간의 가운데 시각을 넣어 계산한 값과 실측을 나란히 놓았습니다.

ROUND_ROBIN + slow start 60s, app-4 첫 요청부터 5초 구간별 몫 구간 계산 f 계산 몫 실측 몫 app-4 p99 0~5초 0.10 3.2% 4.0% 1070ms 10~15초 0.21 6.5% 6.7% 7ms 20~25초 0.38 11.1% 11.2% 7ms 30~35초 0.54 15.3% 15.5% 6ms 40~45초 0.71 19.1% 19.3% 10ms 50~55초 0.88 22.6% 22.5% 4ms 60초~ 1.00 25.0% 25.0% 4~35ms (f = max(0.1, t ÷ 60), t는 구간 가운데 시각. app-4만 slow start 중이라고 본 계산)

10초 이후는 소수점 한 자리까지 거의 맞아요. 첫 구간만 실측 4.0%가 계산 3.2%보다 높았습니다. 창이 첫 요청보다 1~2초 먼저 시작됐다고 해도 설명되지 않아요. 창 시작 후 6초까지는 바닥 10%가 정하기 때문에 계산값이 그대로 3.2%거든요.

원인은 기존 세 대 쪽에 있었어요. Envoy 소스(health_checker_base_impl.cc)는 호스트가 액티브 헬스 체크로 unhealthy에서 healthy가 될 때마다 그 시각을 기록하고, slow start 가중치(applySlowStartFactor)는 그 시각이 창 안에 있는 모든 호스트에 걸려요. run.sh가 실행마다 Envoy를 새로 띄우니, app-1~3도 Envoy 시작 직후 첫 헬스 체크를 통과한 순간부터 자기 slow start 창 안에 있었던 거예요. app-4의 첫 요청은 Envoy를 띄우고 약 47초 뒤였으니 그때 app-1~3의 가중치는 0.8 안팎이었습니다. 세 대 모두 깎인 상태로 계산을 다시 하면 2초 구간별 몫이 맞아떨어져요.

ROUND_ROBIN + slow start, app-4 첫 요청부터 2초 구간 (구간마다 약 300건) 구간 실측 app-4만 slow start로 본 계산 app-1~3도 창 안이라고 본 계산 0~2초 4.3% 3.2% 4.0% 2~4초 3.7% 3.2% 3.9% 4~6초 3.7% 3.2% 3.7% 6~8초 4.3% 4.0% 4.5% (app-1~3의 창은 Envoy 시작 약 1초 뒤에 열렸다고 가정. Envoy 시작 시각은 run.sh 의 8초 대기로 추정)

라운드로빈 + slow start는 가중치 스케줄러가 차례를 정해서 무작위 표본 오차가 끼어들 여지가 적어요. 그래서 이 차이는 표본 수가 적어서가 아니라 기존 호스트의 가중치 때문으로 봤습니다. app-1~3의 창은 app-4 첫 요청 후 13초쯤 끝나서 그 뒤 계산에는 영향이 없어요. 처음 5초에 app-4는 30건만 받았고, 그중 가장 느린 요청이 1.07초였어요. 그 뒤로는 p99가 대부분 10ms 안팎이었습니다.

한 가지 조건이 달랐던 점도 적어 둘게요. slow start를 켠 두 실행에서는 app-4의 스프링 기동이 6.1~6.5초, 켜지 않은 두 실행에서는 4.1~4.3초 걸렸어요. 같은 이미지라 기동 시간 차이는 실행 시점의 호스트 상태 때문으로 보이고, slow start와는 관계가 없어요. 다만 두 그룹을 비교할 때 이 차이가 섞여 있다는 건 감안해야 합니다.

app-4 기동 후 120초 ROUND_ROBIN + slow start 200ms 넘은 요청 292건 12건 1초 넘은 요청 171건 1건 최대 10.0초 1.07초 200이 아닌 응답 5건 0건 헬스 체크로 빠진 적 있음 없음

slow start가 한 일은 JIT를 빨리 데운 게 아니에요. 새 서버가 감당할 수 있을 만큼만 보내서, 컴파일이 끝날 때까지 줄이 쌓이지 않게 했습니다. 3편의 계산(열 대 중 한 대, 바닥 10%면 몫이 1.1%)과 같은 원리가 네 대에서 3.2%로 나타난 거예요.

4. 예상 밖: LEAST_REQUEST만으로도 거의 같았다

여기까지는 3편이 말한 그대로였어요. 그런데 slow start를 끄고 LEAST_REQUEST로만 바꿨더니 결과가 더 좋았습니다.

처음 5초 구간의 몫은 라운드로빈과 LEAST_REQUEST 모두 19.2%로 같았어요. 그런데 결과는 전혀 달랐습니다. 5초 구간으로는 차이가 안 보여서 0.5초 단위로 쪼개 봤어요.

처음 0.5초에는 app-4가 6.6%만 받았고 그 요청들은 77ms씩 걸렸어요. 1.5초쯤 지나 지연이 5ms로 내려오자 몫도 제 몫 근처로 올라갔습니다. 라운드로빈은 처음부터 25%를 보냈고(위 2장 표의 0~5초 구간은 헬스 체크 제외로 중간에 끊겨 19.2%가 됐어요), LEAST_REQUEST는 요청을 보낼 때마다 활성 요청을 봐서 느린 동안 덜 보낸 거예요. app-4가 데워져 빨라지면 다시 몫이 늘고요. 실습-1에서 느린 서버를 피한 것과 같은 일이 새 서버에도 일어난 겁니다.

3편은 ALB에서 slow start를 least outstanding requests와 함께 쓸 수 없다는 점을 "점진 증가냐 요청 수 기반 분배냐 하나를 포기해야 한다"고 설명했어요. 이번 조건(따뜻한 서버 셋에 새 서버 하나, 초당 150건)에서는 요청 수 기반 분배 쪽이 새 서버 보호까지 해냈습니다. 다만 이 결과를 넓게 믿으면 안 되는 조건이 있어요. 새 서버가 대부분이면 피할 곳이 없고, 트래픽이 적어 활성 요청이 늘 0 근처면 느린 서버를 알아보지 못합니다. 1편이 말한 한산할 때의 약점이 그대로 적용돼요.

5. 둘을 같이 켜면 P2C가 잠시 다른 알고리즘이 된다

LEAST_REQUEST에 slow start를 켠 실행은 몫이 라운드로빈 + slow start와 거의 같은 직선으로 올랐어요(구간별 4.0%, 4.7%, 6.5%, 8.7%...). 왜 P2C인데 직선이 나오는지 Envoy 1.39.3 소스(load_balancer_impl.cc)를 봤습니다.

EdfLoadBalancerBase::refresh는 "모든 호스트의 가중치가 같고, slow start 중인 호스트가 없을 때"만 가중치 스케줄러를 만들지 않고 P2C 같은 비가중 선택을 씁니다. 새 호스트가 slow start에 들어가면 이 조건이 깨져서 가중치 스케줄러로 고르게 돼요. 이때 LEAST_REQUEST의 호스트 가중치는 "원래 가중치 ÷ (활성 요청 + 1)"에 slow start 비율을 곱한 값입니다(least_request_lb.cc의 hostWeight). 무작위 둘을 비교하는 P2C가 아니라, 활성 요청과 slow start 비율을 함께 반영한 가중치 순서로 돌아가는 거예요.

📖 용어: EDF 스케줄러 (earliest deadline first)
호스트마다 가중치에 반비례하는 다음 차례 시각을 두고, 가장 이른 호스트부터 고르는 방식입니다. Envoy는 가중치가 서로 다른 라운드로빈과 LEAST_REQUEST에 이걸 써요. 가중치가 두 배인 호스트는 차례가 두 배 자주 옵니다.

하나 더 눈에 띈 게 있어요. 창이 끝난 뒤 LEAST_REQUEST + slow start 실행의 몫은 5초 구간마다 24.7~25.1%(대부분 24.9~25.1%)로 매우 고르게 나왔어요. slow start 없는 LEAST_REQUEST 실행은 같은 시기에 21.7~27.2%로 출렁였고요(그림 4). 소스에서 스케줄러는 호스트 목록이 바뀔 때 다시 만들어지는데, 창이 끝났다는 이유만으로 다시 만드는 코드는 찾지 못했습니다. 그래서 창이 끝난 뒤에도 한동안 가중치 스케줄러가 남아 있는 것으로 보여요. 이 부분은 소스를 읽고 몫의 모양을 본 것이지, Envoy 내부 상태를 직접 확인한 건 아닙니다.

💡 실무에서는
• 먼저 새 인스턴스가 감당할 수 있는 양을 재요. 이 실습의 앱은 CPU 0.5개에서 초당 30건 안팎도 처음 몇 초를 못 버텼고, 지연이 정상으로 돌아오기까지 첫 요청 후 15~20초가 걸렸어요
• 라운드로빈을 쓴다면 slow start 창은 그 워밍업보다 넉넉하게 잡아요. 60초 창에서 바닥 10%로 시작해 처음 5초에 받은 30건 중 최대가 1.07초였어요
• LEAST_REQUEST를 쓰고 트래픽이 충분하면 slow start 없이도 새 인스턴스의 지연이 크게 늘지 않을 수 있어요. 켜기 전에 이 실습처럼 두 경우를 재 보고 정해요
• 헬스 체크 타임아웃이 짧으면 밀린 새 인스턴스가 빠졌다 들어오기를 반복해요. slow start를 켰다면 Envoy 문서대로 헬스 체크에 실패한 순간 slow start도 끝나고, 다시 healthy가 되면 창을 처음부터 다시 세요. 둘을 같이 설계해요
✍️ 오늘의 요약
CPU 0.5개로 갓 뜬 JVM에 라운드로빈이 바로 4분의 1을 보내자, 처음 5초 요청의 중앙값이 8.1초였고 새 서버는 헬스 체크에서 한 번 빠졌다 돌아왔어요.

slow start 60초를 켜자 새 서버의 몫이 Envoy 문서의 식대로 4% 안팎에서 25%까지 직선으로 올랐고, 200ms를 넘은 요청이 292건에서 12건이 됐어요. 예상과 달리 slow start 없는 LEAST_REQUEST는 1건으로 더 나았어요. 활성 요청을 보고 고르는 방식이 느린 새 서버를 그때그때 피했기 때문이에요. 둘을 같이 켜면 Envoy는 창 동안 P2C 대신 가중치 스케줄러로 고릅니다. 새 인스턴스를 보호하는 방법은 정해진 시간 동안 덜 주거나, 느린 동안 덜 주거나 둘 중 하나이고, 어느 쪽이 맞는지는 재 봐야 압니다.
