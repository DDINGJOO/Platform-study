🚦 트래픽 관리, 5편
1편. 로드 밸런서 셋이 각자 가장 한가한 서버를 고르면
2편. 빨리 실패하는 서버는 한가해 보인다
3편. 갓 뜬 인스턴스에게는 보호관찰이 필요하다
4편. 요청을 한 번 더 보내면 빨라진다
5편. 재시도는 공짜가 아니다 ← 지금 이 글
6편. 비율 제한, 벌크헤드, 서킷 브레이커는 서로 다른 것을 센다
7편. 임계값을 정하지 않는 동시성 제한

오후 2시, 재고 서비스의 DB가 30초쯤 느려집니다. 흔한 일이에요. 인덱스 통계가 갱신됐거나 무거운 배치가 잠깐 겹쳤겠죠. 평소라면 30초 뒤에 저절로 풀립니다. 그런데 이날은 풀리지 않습니다. DB에 들어오는 쿼리 수가 평소의 몇십 배로 뛰어 있고, 느려진 원인이 사라진 뒤에도 그 숫자가 내려오지 않아요.

쿼리를 보낸 쪽을 따라가 보면 새로 들어온 사용자 요청은 거의 늘지 않았습니다. 늘어난 건 재시도예요. 게이트웨이도, 주문 서비스도, 재고 서비스도 "일시적인 오류니까 세 번까지 다시 해 보자"는 설정을 각자 갖고 있었습니다. 하나하나는 합리적인 설정이었어요. 그럼 무엇이 30초짜리 지연을 멈추지 않는 장애로 바꿨을까요?

이번 편에서 볼 질문은 이렇습니다. 어떤 실패를 다시 보내도 되나? 계층마다 세 번씩 재시도하면 맨 아래는 몇 배를 받나? 왜 기다리는 시간에 무작위를 섞나? 재시도 총량은 어떻게 묶나? 재시도가 장애를 가리고 있다는 건 어떻게 알아보나?

1. 다시 보내면 되는 실패, 다시 보내도 같은 실패

다운스트림은 생각보다 자주, 아주 짧게 아픕니다. 커넥션이 리셋되고, 스레드 풀이 잠깐 꽉 차고, 배포 중인 인스턴스가 요청을 하나 놓쳐요. 이런 실패는 몇백 밀리초 뒤에 다시 보내면 대개 성공합니다. 그대로 사용자에게 에러로 돌려주면 원인보다 큰 장애가 돼요.

📖 용어: 일시 장애 (transient fault)
원인이 짧은 시간 안에 저절로 사라지는 실패입니다. 같은 요청을 조금 뒤에 다시 보내면 성공할 가능성이 높아요. 반대로 요청 자체가 잘못됐거나 권한이 없는 실패는 몇 번을 다시 보내도 결과가 같습니다.

그래서 재시도를 넣기 전에 세 가지를 정해야 합니다. 다시 보내도 되는 요청인가(2장), 몇 번까지, 얼마 간격으로(3장, 4장), 그리고 다시 보내 봐야 소용없는 응답은 무엇인가. 마지막 것은 기준이 비교적 분명합니다.

HTTP로 보면 4xx는 대체로 "요청이 잘못됐다"는 뜻입니다. 입력 형식이 틀려 400을 받았다면 같은 입력을 다시 보내도 400이 돌아와요. AWS Builders' Library의 타임아웃·재시도 글도 클라이언트 오류는 나중에 보내도 성공하지 않으니 같은 요청으로 재시도하지 말라고 적어 둡니다. 재시도 후보는 5xx, 그중에서도 502·503·504와 응답 자체를 못 받은 경우(연결 리셋, 연결 실패)예요.

예외가 둘 있습니다. 하나는 429(Too Many Requests)입니다. 요청이 틀린 게 아니라 "지금은 너무 많다"는 뜻이라 기다리면 성공할 수 있어요. 다른 하나는 Retry-After 헤더입니다. HTTP 명세(RFC 9110)는 503과 함께 보낸 Retry-After를 "서비스가 얼마 동안 이용 불가로 예상되는지"로 정의해요. 서버가 언제 다시 오라고 말해 줬다면 그 값이 내 백오프 계산보다 우선이에요.

Envoy의 retriable-4xx 조건이 다루는 409도 조심해야 합니다. 문서는 409가 낙관적 잠금의 버전을 갱신해야 한다는 뜻일 때가 있고, 그런 경우 그대로 다시 보내면 매번 또 409로 실패하니 최신 값을 다시 읽은 뒤 쓰기를 시도해야 한다고 경고해요. 라이브러리가 대신해 줄 수 없는 재시도입니다.

2. 타임아웃은 실패가 아니라 "모름"이다

재시도를 처음 붙일 때 가장 흔히 놓치는 건 타임아웃의 의미예요. 500을 받았다면 서버가 처리하다 실패했다는 걸 압니다. 그런데 응답이 3초 안에 안 와서 끊었다면, 우리가 아는 건 "응답을 못 받았다"뿐입니다. 서버가 요청을 못 받았을 수도, 처리 중일 수도, 이미 처리를 끝내고 응답을 보내다 끊겼을 수도 있어요.

조회는 두 번 해도 결과가 같습니다. 결제는 다릅니다. 첫 요청이 실제로는 승인됐는데 응답만 늦었다면 재시도는 두 번째 결제가 돼요. 추적과 디버깅 시리즈 4편의 중복 결제를 이번엔 호출하는 쪽이 스스로 만드는 셈입니다.

📖 용어: 멱등성 (idempotency)
같은 요청을 여러 번 보내도 한 번 보낸 것과 결과가 같은 성질입니다. 재시도해도 되는지는 응답 코드가 아니라 이 성질로 정해져요.

RFC 9110은 PUT, DELETE와 GET 같은 안전한 메서드를 멱등하다고 정의하고, 응답을 읽기 전에 연결이 끊기면 이런 요청은 자동으로 다시 보낼 수 있다고 적어요. 멱등하지 않은 요청은 실제로 멱등하다는 것이나 원래 요청이 적용되지 않았다는 것을 알 방법이 없으면 자동 재시도하지 말라(SHOULD NOT)고 하고요.

결제 같은 POST는 그 "알 방법"을 만들어 주면 됩니다. 클라이언트가 요청마다 고유한 멱등성 키를 붙이고, 서버는 같은 키의 두 번째 요청에 첫 번째 결과를 돌려주는 방식이에요. AWS Builders' Library도 부수 효과가 있는 API는 멱등성을 제공하지 않는 한 재시도에 안전하지 않다고 적어 둡니다.

이 판단은 도메인을 아는 쪽만 할 수 있습니다. 프록시는 요청이 POST라는 건 알아도 그게 장바구니 담기인지 결제인지는 몰라요. Envoy의 5xx 조건은 응답이 5xx이거나 없으면 재시도할 뿐 메서드를 가려 주지 않고(retriable_request_headers로 메서드를 직접 걸러야 해요), Finagle 문서는 요청이 멱등한지 알 수 없어서 타임아웃을 기본으로 재시도하지 않는다고 적습니다. 4편의 헤지 요청처럼, 메시에 재시도를 켜는 건 쉽지만 어느 경로에 켤지는 사람이 정해야 해요.

3. 계층마다 세 번이면 맨 아래는 스물일곱 번

서두의 구조는 게이트웨이 → 주문 서비스 → 재고 서비스 → DB였고, 세 계층이 각자 "최대 세 번 시도"를 갖고 있었습니다. DB 쿼리가 타임아웃 나면 어떻게 될까요?

계층마다 최대 3번 시도 (처음 1번 + 재시도 2번) 게이트웨이 → 주문 서비스 : 3번 주문 서비스 → 재고 서비스 : 3 × 3 = 9번 재고 서비스 → DB : 3 × 3 × 3 = 27번 사용자 요청 1개 = DB 쿼리 최대 27개

계층이 n개이고 각자 시도가 k번이면 맨 아래는 최대 kn배를 받습니다.

그림 1. 재시도는 더해지지 않고 곱해진다

"재시도 3번"은 두 가지로 읽힙니다. Resilience4j의 maxAttempts는 처음 호출을 포함한 횟수라 3은 재시도 2번이에요. "실패하면 세 번 더"로 읽으면 계층당 4번이고 세 계층이면 43 = 64배입니다. AWS Builders' Library도 이 두 읽기가 섞여 있습니다. 다섯 단계 호출에서 "계층마다 재시도 세 번"이면 DB 부하가 243배라고 쓰는데, 243은 35, 즉 계층당 세 번 시도로 센 값이에요. 글자 그대로 재시도 세 번(시도 네 번)이면 45 = 1024배입니다.

더 나쁜 건 타이밍입니다. 재시도는 다운스트림이 이미 힘들 때 몰려와요. AWS 글의 표현대로 과부하로 생긴 실패에 부하를 늘리는 재시도를 얹으면 상황은 훨씬 나빠집니다. 원인이 사라져도 쌓인 재시도가 DB를 붙잡고, 또 타임아웃이 나고, 또 재시도가 생겨요. 처음 원인과 상관없이 재시도가 재시도를 만드는 상태, 흔히 재시도 폭풍(retry storm)이라고 부르는 상태예요.

가장 단순한 처방은 한 곳에서만 재시도하는 겁니다. AWS 글은 비용이 낮은 작업에 대해 "스택의 한 지점에서만 재시도"를 모범 사례로 들어요. 재고 서비스만 재시도하고 위 계층은 실패를 그대로 올리면 27이 3이 됩니다. 다만 모든 계층이 이 약속을 지켜야 해요. 라이브러리 기본값이나 메시 설정이 어딘가에서 재시도를 켜 두면 곱셈은 다시 시작되고, 그래서 5장의 예산이 필요합니다.

4. 얼마나 기다릴까: 백오프만으로는 부족하다

실패하면 늘 100ms 뒤에 다시 보낸다고 해 볼게요. 과부하로 실패하는 중이라면 100ms 뒤에도 과부하일 가능성이 높습니다. 그래서 실패할수록 기다리는 시간을 늘려요.

📖 용어: 지수 백오프 (exponential backoff)
재시도할 때마다 대기 시간에 일정한 배수를 곱해 늘리는 방식입니다. 100ms, 200ms, 400ms처럼요. 보통 상한(cap)을 둬서 대기 시간이 끝없이 길어지지 않게 합니다.

그런데 같은 순간에 실패한 클라이언트 100개는 같은 공식으로 같은 시간을 기다렸다가 같은 순간에 다시 보냅니다. 부하가 덩어리째 뒤로 옮겨 갈 뿐이에요. AWS 아키텍처 블로그의 2015년 글 "Exponential Backoff And Jitter"(Marc Brooker)가 시뮬레이션으로 보여 준 것도 이겁니다. 상한 있는 지수 백오프만으로는 개선이 작았고, 경합을 흩뜨리지 못하고 다른 시점으로 옮기기만 했어요.

📖 용어: 지터 (jitter)
대기 시간에 일부러 섞는 무작위 값입니다. 같은 순간에 실패한 클라이언트들이 서로 다른 시각에 재시도하게 만들어서, 재시도가 한 시점에 몰리지 않게 해요.

그 글이 비교한 세 가지 방식을 공식으로 적으면 이렇습니다. base는 첫 대기 시간, cap은 상한, attempt는 몇 번째 재시도인지예요.

상한 있는 지수 백오프: sleep = min(cap, base × 2^attempt) Full Jitter: sleep = random(0, min(cap, base × 2^attempt)) Equal Jitter: t = min(cap, base × 2^attempt) sleep = t/2 + random(0, t/2) Decorrelated: sleep = min(cap, random(base, 이전 sleep × 3))

지터를 넣자 클라이언트 100개 기준 호출 수가 절반 넘게 줄고 완료 시간도 크게 줄었습니다. 셋 중 Equal Jitter가 가장 약했고, Full과 Decorrelated의 우열은 분명하지 않다고 적혀 있어요. 결론은 지터를 섞은 백오프를 원격 클라이언트의 표준으로 삼자는 것이었습니다.

그림 2. 백오프는 간격을 벌리고, 지터는 클라이언트끼리 어긋나게 만든다

같은 "지터"라도 도구마다 섞는 방식이 꽤 다릅니다.

Envoy 라우터 : Full Jitter. N번째 재시도는 [0, (2^N - 1) × 25ms) 중 무작위 기본 base 25ms, 상한은 base의 10배(250ms) gRPC (gRFC A6) : min(initialBackoff × multiplier^(n-1), maxBackoff) × random(0.8, 1.2) 계산값의 ±20% Resilience4j : ofExponentialRandomBackoff, 계산값의 ±randomizationFactor 기본 0.5, 즉 ±50%

gRPC는 특히 볼 만합니다. gRPC의 재시도 설계 문서인 gRFC A6는 원래 random(0, 계산값)의 Full Jitter였는데 2024년 8월 개정에서 ±20%로 바뀌었어요. 그래서 실제 대기가 maxBackoff를 조금 넘을 수 있다고 문서가 따로 적어 둡니다. "지터를 넣었다"만으로는 분포를 알 수 없으니 쓰는 라이브러리의 공식을 확인해야 해요.

그리고 백오프와 지터는 재시도의 시점을 바꿀 뿐 횟수를 줄이지 않습니다. 3장의 27배는 지터를 넣어도 고르게 퍼진 27배예요.

5. 재시도에 예산을 건다

"최대 3번"은 요청 하나의 상한입니다. 정상일 때는 거의 안 쓰이지만, 다운스트림이 통째로 실패하면 모든 요청이 상한까지 채워 재시도해요. 실패가 1%일 때 약 1.01배이던 부하가, 다운스트림이 가장 약할 때 3배가 됩니다. 그래서 나온 발상이 "재시도는 전체 요청의 일정 비율까지만"이라는 재시도 예산입니다.

📖 용어: 재시도 예산 (retry budget)
최근 요청량에 비례해 허용되는 재시도 총량입니다. 요청이 성공하거나 들어올 때마다 조금씩 쌓이고, 재시도할 때마다 꺼내 씁니다. 바닥나면 재시도하지 않고 실패를 바로 돌려줘요. 구현은 대개 토큰 버킷(일정량을 쌓아 두고 꺼내 쓰는 카운터)입니다.

공개된 구현 셋은 같은 발상을 다르게 셉니다.

Finagle RetryBudget은 요청 비율로 셉니다. 소스의 기본값은 ttl 10초, 초당 최소 재시도 10회, 비율 0.2예요. 요청마다 예금(deposit)이 쌓이고 재시도할 때 인출(withdraw)하며, 예금은 ttl이 지나면 사라집니다. 그래서 최근 10초 요청의 약 20%만큼 재시도할 수 있고, 요청이 적은 클라이언트를 위해 초당 최소 횟수를 바닥으로 깔아 둬요.

Envoy retry_budget은 동시성으로 셉니다. 클러스터의 서킷 브레이커 설정 안에 있고, budget_percent(기본 20%)는 처리 중·대기 중 요청의 합 대비 동시에 진행 중인 재시도의 상한이에요(budget_interval을 주면 그 기간 안에 시작된 요청까지 셉니다). 바닥은 min_retry_concurrency(기본 3)이고, 예산을 설정하면 동시 재시도 수를 고정값으로 묶는 서킷 브레이커의 max_retries 대신 예산이 적용됩니다.

gRPC retry throttling은 실패와 성공의 균형으로 셉니다. 서버 이름마다 token_count를 maxTokens로 시작해, 실패마다 1을 빼고 성공마다 tokenRatio를 더해요. maxTokens의 절반 이하로 떨어지면 재시도와 헤지를 멈춥니다. 실패로 세는 건 재시도 대상(헤지라면 nonFatalStatusCodes) 상태 코드와 서버의 재시도 거부(pushback) 응답뿐이라 INVALID_ARGUMENT 같은 요청 오류는 빠져요. AWS Builders' Library가 말하는 로컬 토큰 버킷도 같은 계열입니다.

그림 3. 재시도 예산은 "최근에 얼마나 실패했나"로 재시도 자격을 정한다

9%는 직접 계산한 값입니다. 실패율이 p면 호출당 토큰 변화의 기댓값은 −p + (1−p) × 0.1이고, 이게 0이 되는 p는 0.1 / 1.1 ≈ 9.1%예요. tokenRatio를 정하는 건 "실패율 몇 %부터 재시도를 그만할지"를 정하는 일입니다.

다운스트림이 전부 실패하는 최악의 경우, 계층 3개 요청마다 최대 3번 시도 : 3 × 3 × 3 = 27배 재시도 예산 20% (계층마다) : 1.2 × 1.2 × 1.2 ≈ 1.73배

계층마다 받은 요청의 20%까지만 재시도하면 세 계층을 곱해도 약 1.73배예요(Finagle처럼 요청 수의 비율로 예산을 세고 최소 바닥은 0으로 둔 단순 모델 기준입니다. Envoy의 예산은 동시 요청 수의 비율이라 타임아웃이 길면 배수가 달라져요). 정상일 때의 경험은 거의 그대로 두고, 가장 나쁠 때의 증폭만 크게 깎습니다.

⚠️ 주의: 예산이 막지 못하는 경우
• 최소 재시도 바닥은 클라이언트 수만큼 더해집니다. 요청이 적은 클라이언트가 수백 개면 초당 10회, 동시 3개 같은 바닥만으로도 큰 양이 돼요.
• 20%도 공짜는 아닙니다. 한계에서 버티는 다운스트림에는 1.2배가 마지막 한 걸음일 수 있어요. 예산은 증폭을 줄일 뿐 부하를 덜어 주지 않고, 그건 6편의 서킷 브레이커 몫입니다.
• 예산이 바닥나면 사용자는 에러를 봅니다. 의도된 동작이니, 예산 소진은 장애 신호로 따로 봐야 해요.

6. Resilience4j로 쓰고, 재시도가 가린 장애를 지표로 본다

자바에서 직접 재시도를 짠다면 Resilience4j가 흔한 선택입니다. 지금까지의 원칙을 현재 API로 옮기면 이래요.

RetryConfig config = RetryConfig.custom() .maxAttempts(3) // 처음 호출 포함 3번 = 재시도 2번 .intervalFunction(IntervalFunction.ofExponentialRandomBackoff( Duration.ofMillis(200), // 첫 대기 2.0, // 배수 0.5, // 지터 ±50% Duration.ofSeconds(2))) // 상한 .retryExceptions(ResourceAccessException.class, RetryableApiException.class) .ignoreExceptions(BadRequestException.class) .build(); RetryRegistry retryRegistry = RetryRegistry.of(config); Retry retry = retryRegistry.retry("inventory"); Supplier<Stock> call = Retry.decorateSupplier(retry, () -> inventoryClient.get(sku));

ofExponentialBackoff에는 지터가 없으니 이름에 Random이 들어간 쪽을 고르고, 상한을 받는 오버로드를 씁니다. 재시도 대상은 retryExceptions로 좁히고(여기서는 연결 실패나 읽기 타임아웃 때 Spring의 HTTP 클라이언트가 던지는 unchecked 예외 ResourceAccessException을 예로 들었어요. Supplier 람다는 checked 예외를 던질 수 없어서, ConnectException을 직접 받으려면 decorateCheckedSupplier를 써야 합니다) 4xx에 해당하는 예외는 ignoreExceptions로 적어서 1장과 2장의 판단을 코드에 남겨요.

이제 관측입니다. 재시도는 잘 동작할수록 장애를 가립니다. 다운스트림이 첫 시도의 30%를 실패해도 재시도가 다 살려 내면 사용자 에러율은 0에 가까워요. 대신 레이턴시가 늘고 다운스트림 부하는 약 1.3배가 돼 있습니다(재시도가 한 번에 성공한다고 칠 때고, 재시도도 같은 비율로 실패하면 더 늡니다).

TaggedRetryMetrics.ofRetryRegistry(retryRegistry).bindTo(meterRegistry)로 붙이는 지표는 resilience4j.retry.calls 하나이고, kind 태그가 결과를 네 갈래로 나눕니다.

kind="successful_without_retry" 한 번에 성공 kind="successful_with_retry" 재시도 끝에 성공 ← 재시도가 가린 실패 kind="failed_with_retry" 재시도했지만 끝내 실패 kind="failed_without_retry" 재시도 대상이 아닌 예외로 실패

함정이 하나 있습니다. Resilience4j 문서의 마이크로미터 페이지는 이 값을 successful.with.retry처럼 점으로 적고 게이지라고 소개하는데, 현재 소스(AbstractRetryMetrics)는 밑줄 값을 FunctionCounter(라이브러리가 쌓아 둔 누적값을 읽어 가는 카운터)로 등록해요. 프로메테우스로 내보내면 resilience4j_retry_calls_total{kind="successful_with_retry"} 모양이 됩니다. 점 표기를 경고 쿼리에 옮기면 아무것도 걸리지 않으니 실제로 노출된 값을 확인하고 씁니다.

카운터는 누적값이라 "failed_with_retry가 100을 넘으면" 같은 고정 임계값은 오래 떠 있을수록 언젠가 반드시 넘습니다. 걸어야 하는 건 증가율의 비율이에요.

재시도 의존도 = rate(successful_with_retry + failed_with_retry) / rate(모든 kind 합) 최종 실패율 = rate(failed_with_retry + failed_without_retry) / rate(모든 kind 합)

최종 실패율은 사용자가 겪는 증상이라 SLO와 경고 시리즈 1편의 burn rate 경고로 다룹니다. 재시도 의존도는 그보다 먼저 움직이는 원인 쪽 신호예요. 평소 1%이던 값이 20%가 되면 다운스트림이 아프고 내 재시도가 그 부하를 키우고 있다는 뜻이니, 사람을 깨우기보다 티켓으로 넘기는 경고가 맞습니다. Envoy라면 upstream_rq_retry와 예산이나 서킷 브레이커 상한 때문에 재시도하지 못한 upstream_rq_retry_overflow가 같은 역할을 해요.

💡 실무에서는
• 재시도는 한 계층에서만. 나머지 계층은 실패를 빨리 위로 올립니다
• 멱등하지 않은 호출(결제, 주문 생성)은 멱등성 키가 확인되기 전까지 재시도 대상에서 뺍니다
• 백오프에는 상한과 지터를 함께 두고, 쓰는 라이브러리의 지터 공식을 확인합니다
• 요청당 횟수 상한 위에 재시도 예산을 하나 더 겁니다
• 재시도 전체가 상위 타임아웃 안에 드는지 봅니다(Envoy 라우트 타임아웃은 모든 재시도를 포함)
• 경고는 누적 횟수가 아니라 재시도 의존도의 비율에 겁니다
✍️ 오늘의 요약
재시도는 일시 장애를 가려 주는 대가로 다운스트림에 부하를 더 얹는 장치입니다. 다시 보내도 되는지는 멱등성이 정하고, 계층마다 재시도하면 부하는 kn배로 곱해져요(세 번씩 세 계층이면 27배).

백오프와 지터는 재시도의 시점을 흩뜨릴 뿐 양을 줄이지 않으니, 총량은 재시도 예산으로 묶고 재시도 의존도를 비율로 지켜봅니다. 재시도로 얻은 성공은 공짜가 아니라 다운스트림의 여유를 써서 얻은 성공이에요.
