게이지 하나를 등록하고 /actuator/prometheus를 열었어요. queue_size 42.0이 보입니다. 2초 뒤에도 42, 4초 뒤에도 42였어요. 6초 뒤에 다시 여니 NaN이었습니다. 그 사이에 코드는 아무것도 하지 않았어요. 바뀐 건 JVM의 GC 횟수 하나였습니다.

2편과 3편에서 게이지는 관측 대상을 약한 참조로 쥐고, 그 대상이 GC로 사라지면 값이 NaN이 된다고 했어요. 이번 글은 그 NaN을 일부러 만듭니다. 같은 값 42를 내는 게이지 여러 개를 띄우되 "관측 대상을 누가 쥐고 있나"만 다르게 하고, GC 횟수를 같이 찍으면서 어느 것이 언제 NaN이 되는지 지켜봤어요. NaN이 그래프와 쿼리에서 어떻게 보이는지도 확인했습니다.

🧭 이 글에서 확인할 것
• 지역 객체를 넘긴 게이지는 정확히 언제 NaN이 되는가?
• NaN이 된 게이지를 다시 등록하면 살아나는가?
• NaN은 Prometheus, OTLP, Grafana에서 어떻게 보이고, 알람은 울리는가?
• 강한 참조를 거는 세 가지 방법은 전체 GC를 버티는가?

1. 실습 환경: 값은 같고 주인만 다른 게이지들

기동할 때 게이지 다섯 개를 등록해요. 모두 AtomicInteger(42)를 읽습니다. 다른 점은 그 AtomicInteger를 누가 강하게 쥐고 있느냐 하나예요.

QueueGauges(MeterRegistry registry) { // ① 지역 객체를 넘긴다. 생성자가 끝나면 아무도 강하게 쥐지 않는다 AtomicInteger local = new AtomicInteger(42); Gauge.builder("queue.size", local, AtomicInteger::get) .tag("case", "local").register(registry); // ② registry.gauge(...) 의 반환값을 버린다(2편 버그 코드와 같은 모양) registry.gauge("queue.size.shortcut", new AtomicInteger(42)); // ③ 필드로 보관한다 Gauge.builder("queue.size", held, AtomicInteger::get) .tag("case", "field").register(registry); // ④ 지역 객체지만 strongReference(true) Gauge.builder("queue.size", strong, AtomicInteger::get) .tag("case", "strong").strongReference(true).register(registry); // ⑤ Supplier 형태. 람다가 지역 객체를 붙잡는다 Gauge.builder("queue.size", captured::get) .tag("case", "supplier").register(registry); } // 기동이 끝난 뒤 ①과 같은 코드를 한 번 더 도는 엔드포인트 @PostMapping("/register") // case="late-local"

GC를 관찰하는 엔드포인트도 두 개 만들었어요. POST /gc는 System.gc()를 부르고, POST /alloc?mb=N은 쓰레기만 만듭니다. 둘 다 그 시점까지의 GC 횟수를 돌려줘요. mb=0으로 부르면 아무것도 안 하고 횟수만 읽습니다.

그림 1. 게이지는 같은 약한 참조다. 차이는 다른 누군가가 강하게 쥐고 있느냐뿐이다
📖 용어: 약한 참조 (WeakReference)
가리키고는 있지만 GC가 객체를 치울지 판단할 때 세지 않는 참조입니다. 다른 강한 참조가 하나도 없으면 GC가 객체를 가져가고, 그 뒤로 get()은 null을 돌려줘요. Micrometer의 DefaultGauge는 이때 Double.NaN을 냅니다.
Spring Boot 4.1.1 (Micrometer 1.17.1, Java 21, -Xmx256m, 컨테이너 메모리 512MB) OTel Collector 0.162.0 (contrib, debug 익스포터) Prometheus 3.15.0 (5초마다 스크레이프) Grafana 13.2.3 실행 환경 Docker Desktop, Apple M5 Pro

실습 코드는 GitHub 저장소의 labs/observability/instr-03-gauge에 있어요. 레지스트리는 Prometheus와 OTLP 두 개를 넣어서, NaN이 두 길에서 어떻게 나가는지도 같이 봤습니다.

git clone https://github.com/DDINGJOO/Platform-study.git cd Platform-study/labs/observability/instr-03-gauge docker compose up -d --build curl -s localhost:22280/actuator/prometheus | grep ^queue_size curl -s -XPOST localhost:22280/register # late-local 게이지 등록 curl -s -XPOST 'localhost:22280/alloc?mb=0' # GC 횟수만 읽기 curl -s -XPOST localhost:22280/gc # 전체 GC 부탁 # 2초마다 late-local 값과 GC 횟수를 같이 읽는다(3절) for i in $(seq 1 30); do v=$(curl -s localhost:22280/actuator/prometheus | grep 'case="late-local"' | awk '{print $2}') echo "$(date +%T) late-local=$v $(curl -s -XPOST 'localhost:22280/alloc?mb=0' | tail -1)" [ "$v" = "NaN" ] && break; sleep 2 done # OTLP 로 나간 원문(5절) docker compose logs otel-collector --no-log-prefix | python3 show-otlp.py queue.size # Prometheus http://localhost:22290, Grafana http://localhost:22230

2. 기동 직후, 둘은 이미 NaN이었다

처음 띄운 실행(실행 1)에서 앱이 뜨자마자 읽은 값이에요.

queue_size{case="field"} 42.0 queue_size{case="local"} NaN queue_size{case="strong"} 42.0 queue_size{case="supplier"} 42.0 queue_size_shortcut NaN GC 횟수: Copy=81, MarkSweepCompact=3

지역 객체를 넘긴 ①과 반환값을 버린 ②는 한 번도 42를 보여 주지 않았어요. 앱이 뜬 직후에 읽은 GC 횟수가 이미 84번(젊은 GC 81, 전체 GC 3)이었어요. 첫 스크레이프 전에 지역 객체가 수거된 거예요. 2편의 버그 코드 registry.gauge("queue.size", new AtomicInteger(0))는 "어느 날부터 NaN"이 아니라, 이 조건에서는 처음부터 NaN이었어요.

GC 이름이 낯설 수 있어요. Copy와 MarkSweepCompact는 Serial GC의 두 수집기 이름입니다. 컨테이너 안에서 JVM 플래그를 찍어 보니 UseSerialGC = true {ergonomic}이었어요. 우리가 고른 게 아니라 JVM이 컨테이너의 메모리 한도(512MB)를 보고 스스로 고른 값입니다. 운영 환경이 G1이라면 횟수와 시점은 달라질 수 있어요.

📖 용어: 젊은 GC와 전체 GC
새로 만든 객체는 힙의 젊은 영역에 놓이고, 자주 도는 젊은 GC(여기서는 Copy)가 이 영역만 치웁니다. 몇 번 살아남은 객체는 올드 영역으로 옮겨지고, 그곳은 드물게 도는 전체 GC(MarkSweepCompact)가 치워요. 약한 참조만 남은 객체도 자기가 있는 영역이 수집될 때 사라집니다.

3. 등록하고 몇 초, 젊은 GC 한 번

기동 중의 GC에 휩쓸리지 않게, 앱이 다 뜬 뒤에 /register로 ①과 같은 코드를 한 번 더 돌렸어요. 실행 2는 이 /register 엔드포인트를 넣으려고 이미지를 다시 빌드해 스택을 새로 띄우고, 앱 컨테이너를 한 번 재시작한 뒤의 실행이에요. 기동 직후 GC 횟수(Copy=81, MarkSweepCompact=3)가 실행 1과 같았는데, 같은 앱이 같은 조건으로 떴기 때문으로 보여요. 그리고 2초마다 값과 GC 횟수를 같이 읽었습니다.

curl -s -XPOST localhost:22280/register 시각 late-local GC 횟수 15:34:51 42.0 Copy=81, MarkSweepCompact=3 15:34:53 42.0 Copy=81, MarkSweepCompact=3 15:34:55 42.0 Copy=82, MarkSweepCompact=3 ← 젊은 GC 한 번 15:34:57 NaN Copy=82, MarkSweepCompact=3

System.gc()를 부르지 않았는데도 첫 확인 6초 뒤에 NaN이 됐어요. 실행 3에서도 15:36:32에 등록한 게이지가 15:36:37에 NaN이었고, 그 사이 Copy가 81에서 82로 하나 늘었어요. 이 앱은 스크레이프 요청을 받고 OTLP로 지표를 보내는 것만으로도 객체를 계속 만들고, 그래서 젊은 GC가 몇 초에 한 번씩 돕니다. 약한 참조만 남은 새 객체는 다음 젊은 GC 한 번이면 사라졌어요.

다시 등록하면 살아날까

같은 코드를 한 번 더 부르면 새 AtomicInteger로 바뀔 것 같지만, 그대로 NaN이었어요. 앱 로그에 이런 경고가 남았습니다.

WARN i.m.core.instrument.MeterRegistry : This Gauge has been already registered (MeterId{name='queue.size', tags=[tag(case=late-local)]}), the registration will be ignored. Note that subsequent logs will be logged at debug level.

레지스트리는 이름과 태그 조합 하나에 미터를 하나만 둡니다. 같은 ID로 다시 등록하면 이미 있는 게이지, 곧 죽은 객체를 가리키는 게이지를 돌려주고 새 객체는 버려요. Micrometer 문서도 같은 이름·태그의 게이지를 다시 등록하면 무시된다고 적고 있어요. 경고는 첫 번째만 WARN이고, 그다음부터는 DEBUG로 내려가서 기본 설정에서는 다시 보이지 않습니다. NaN이 된 게이지를 살리려면 그 미터를 registry.remove()로 지우고 다시 등록해야 하는데, 이번 실습에서 그 방법까지 돌려 보지는 않았어요. 처음부터 강한 참조를 거는 쪽이 간단합니다.

4. 같은 코드인데 실행마다 달랐다

스택을 새로 띄운 실행 3에서는 결과가 달랐어요. 기동 직후에 ①이 42로 살아 있었습니다.

15:35:42 기동 직후 local=42.0 shortcut=NaN Copy=80, MarkSweepCompact=3 15:36:32 /register 호출 local=42.0 Copy=81 15:36:37 late-local=NaN local=42.0 Copy=82 15:36:46 /gc 호출 local=NaN Copy=82, MarkSweepCompact=4

①은 젊은 GC 두 번(81, 82번째)을 버티고, System.gc()가 부른 전체 GC에서 NaN이 됐어요. 기동 중에 만든 객체라서 올드 영역으로 옮겨진 뒤였던 것으로 보입니다. 올드 영역은 젊은 GC가 손대지 않으니, 약한 참조만 남아도 전체 GC가 돌 때까지 살아 있어요. 3편이 "다음 GC에 바로 사라진다고 외우면 곤란하다, 올드 영역에 올라가 있으면 한참 뒤에야 정리되기도 한다"고 한 그 경우를 실제로 만났습니다. 이 객체가 정말 올드 영역에 있었는지는 힙을 덤프해서 확인하지 않았어요.

⚠️ 주의: 테스트에서 42가 나왔다고 안심하면 안 된다
실행 1에서는 처음부터 NaN, 실행 3에서는 1분 넘게 42였어요. 같은 코드가 GC 시점에 따라 다르게 보여요. 로컬에서 몇 번 확인하고 넘어간 게이지가 운영에서 며칠 뒤 전체 GC를 만나 NaN이 될 수 있습니다. 지역 객체를 게이지에 넘기는 코드는 리뷰 단계에서 막는 게 확실해요.

5. NaN은 어떻게 보이나

앱의 두 레지스트리는 NaN을 그대로 내보냈어요. Prometheus 출력에는 NaN이라는 글자로, OTLP에서는 Gauge 데이터 포인트의 값으로 실렸습니다(실행 3, Collector debug 출력).

-> Name: queue.size -> DataType: Gauge Data point attributes: -> case: Str(local) Value: NaN Data point attributes: -> case: Str(late-local) Value: NaN

Micrometer 문서는 객체가 수거되면 레지스트리 구현에 따라 "NaN을 보고하거나 아무것도 보고하지 않는다"고 적어요. 이번에 쓴 Prometheus와 OTLP 레지스트리는 둘 다 NaN을 보냈습니다. 시계열이 사라지지 않고 NaN 값으로 계속 들어와요. 이 차이가 쿼리에서 중요해집니다.

그림 2. 게이지 하나가 NaN이 되자 합계 선이 통째로 사라졌다

그림 2는 실행 3의 Grafana 화면이에요. 42에 있는 선들은 겹쳐서 하나로 보입니다(전체 GC 전에는 넷, 15:36:46의 전체 GC 뒤로는 셋). 보라색 sum(queue_size)는 168(42×4)로 그려지다가, late-local이 등록되고 NaN이 된 뒤로 그려지지 않아요. Grafana는 NaN 점을 선으로 잇지 않습니다. 실행 3이 끝날 무렵 같은 데이터에 몇 가지 쿼리를 더 던졌어요.

sum(queue_size) → NaN count(queue_size) → 5 count(queue_size == queue_size) → 3 (NaN 은 자기 자신과 같지 않다) sum(queue_size == queue_size) → 126 queue_size < 1 → 결과 없음 absent(queue_size{case="local"}) → 결과 없음

여기서 알람 쪽 문제가 보여요. "큐 크기가 1 미만이면 알린다"는 규칙은 NaN에 대해 아무것도 반환하지 않습니다. NaN과의 비교는 늘 거짓이거든요. 그렇다고 "지표가 없어지면 알린다"는 absent()도 울리지 않아요. 시계열은 멀쩡히 있고 값만 NaN이니까요. 게이지가 죽어도 어떤 알람도 울리지 않는 상태가 됩니다. 반대로 대시보드의 합계 패널은 다른 게이지 넷이 멀쩡한데도 비어 버려요.

📖 용어: NaN (Not a Number)
부동소수점에서 "값이 정의되지 않음"을 나타내는 특별한 값입니다. NaN이 섞인 덧셈은 결과도 NaN이고, NaN과의 비교(<, >, ==)는 늘 거짓이에요. 그래서 x == x는 NaN만 걸러 내는 조건이 됩니다.
📖 용어: absent()
주어진 조건에 맞는 시계열이 하나도 없을 때 1을 돌려주는 PromQL 함수입니다. "지표가 끊겼다"는 알람에 써요. 시계열이 NaN 값으로 계속 들어오는 경우는 "없음"이 아니라서 잡지 못합니다.

6. 고치는 세 가지는 전체 GC를 버텼다

실행 2와 실행 3에서 System.gc()로 전체 GC를 일으킨 뒤에도 세 게이지는 42였어요.

curl -s -XPOST localhost:22280/gc Copy=82, MarkSweepCompact=4 queue_size{case="field"} 42.0 ← 빈의 final 필드가 쥔다 queue_size{case="strong"} 42.0 ← .strongReference(true) queue_size{case="supplier"} 42.0 ← Supplier 람다가 쥔다 queue_size{case="local"} NaN queue_size{case="late-local"} NaN queue_size_shortcut NaN

세 방법이 살아남은 이유는 각각 달라요. 필드 보관은 스프링 빈이 살아 있는 동안 그 필드가 강한 참조라서예요. strongReference(true)는 Micrometer가 게이지 함수를 StrongReferenceGaugeFunction으로 감싸 객체를 직접 쥐게 합니다. Supplier 형태는 Gauge.builder(String, Supplier)가 내부에서 strongReference(true)를 켜 두고 있어요(Micrometer 1.17.1 Gauge.java). 람다가 지역 변수를 붙잡고, 그 람다를 레지스트리가 강하게 쥐는 구조예요.

3편이 권한 순서는 필드 보관이 먼저였어요. 측정 대상의 주인은 비즈니스 코드여야 하고 게이지는 구경만 해야 한다는 이유였죠. 실측으로도 셋 다 같은 결과였으니, 고르는 기준은 동작이 아니라 수명 관리예요. 뒤의 둘은 그 객체를 레지스트리가 살아 있는 한 붙잡아 둡니다.

💡 실무에서는: 게이지를 등록할 때
• 관측 대상은 필드나 빈으로 소유해요. 큐, 캐시, 풀처럼 원래 오래 사는 객체를 넘기면 약한 참조여도 문제가 없어요
• 지역 객체를 넘기는 코드는 리뷰에서 막아요. registry.gauge(..., new ...)의 반환값을 버리는 줄이 대표 신호예요
• 합계 쿼리는 NaN을 걸러요. sum(x == x)처럼 쓰면 게이지 하나가 죽어도 나머지 합은 보여요. 대신 죽은 게이지는 count(x != x) > 0 같은 규칙으로 따로 알려요
• WARN 로그를 놓치지 않아요. "already registered" 경고는 첫 번째만 WARN이에요
✍️ 오늘의 요약
지역 객체를 넘긴 게이지는 등록 후 첫 젊은 GC에서 NaN이 됐다. 이번 환경에서는 등록하고 5~6초 안이었다. 기동 중에 등록한 게이지는 실행에 따라 처음부터 NaN이기도 했고, 올드 영역으로 옮겨진 뒤에는 전체 GC가 올 때까지 42를 유지하기도 했다. 죽은 게이지는 같은 ID로 다시 등록해도 살아나지 않았다.

NaN은 조용하다. 시계열이 남아 있어 absent()도, NaN과의 비교도 알람을 울리지 않고, 합계 패널만 통째로 비운다. 필드 보관, strongReference(true), Supplier 셋은 모두 전체 GC를 버텼다. 게이지가 살아 있는지는 게이지가 아니라 그 객체의 주인이 정한다.
