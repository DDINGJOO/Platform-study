2편에서 이상한 버그를 하나 만났었죠. 게이지로 큐 길이를 쟀는데 어느 날부터 메트릭이 조용히 NaN이 되는 것이었어요. 게이지가 관측 대상을 "약한 참조"로만 쥔다는 게 원인이었죠. 그런데... 참조에 강하고 약한 게 있다고요?

있어요. 자바의 참조는 사실 4단계고 이건 GC와 대화하는 언어예요. 게이지의 각주에서 시작해서 JVM의 방 하나를 여는 게 이번 편입니다.

1. 강한 참조: 이름 없는 기본값

먼저 놀라운 사실부터 말하면, 여러분이 지금까지 쓴 모든 참조가 강한 참조입니다.

Order order = new Order(); // ← 이게 강한 참조 this.repository = repo; // ← 이것도 list.add(item); // ← 이것도 (리스트가 item을 강하게 쥠)

StrongReference라는 클래스는 없어요. 강한 참조가 기본값이고 나머지 셋만 이름이 붙은 거죠. "일반 볼펜"이라는 특수 볼펜이 없는 것과 같아요. 특이한 것들(지워지는 펜, 형광펜)만 이름을 얻는 법이니까요.

GC의 규칙은 이래요. GC 루트(스택의 지역변수, static 필드, 활성 스레드)에서 출발해 강한 참조 사슬을 따라가서, 도달 가능하면 생존, 아니면 수거. 그래서 자바의 메모리 누수란 "안 쓰는 객체를 누군가 강한 참조로 계속 쥐고 있는 상태"예요. static 컬렉션에 넣고 안 빼는 경우가 전형이죠.

2. 약한 참조: 투표권 없는 구경꾼

이제 게이지의 그 "약한 참조(WeakReference)"예요. 계약이 명확합니다: "나는 이 객체를 가리키지만, 살릴지 말지 투표에서 나를 세지 마."

Object obj = new Object(); WeakReference<Object> ref = new WeakReference<>(obj); ref.get(); // → 객체 (아직 obj라는 강한 참조가 있으니까) obj = null; // 강한 참조 소멸. 이제 약한 참조"만" 남음 System.gc(); // 어디까지나 "부탁", 실행 보장은 없다 ref.get(); // → 대개 null (수거가 일어났다면)

약한 참조만 남은 객체는 수거 대상이 돼요. 다만 "다음 GC에 바로 사라진다"고 외우면 곤란해요. 명세는 수거 시점을 GC 재량에 맡기고, 세대별 수집기에서 그 객체가 이미 올드 영역에 올라가 있으면 한참 뒤에야 정리되기도 하거든요. 언젠가는 사라진다, 언제인지는 모른다. 이게 정확한 계약이에요. Micrometer 게이지의 구현이 이 계약 위에 서 있습니다:

public class DefaultGauge<T> implements Gauge { private final WeakReference<T> ref; // ← 약하게만 쥔다 public double value() { // 발행 시점마다 호출 T obj = ref.get(); if (obj != null) return f.applyAsDouble(obj); return Double.NaN; // ← 그 NaN의 출처! } }

왜 이렇게 설계했을까요? 관측 도구가 관측 대상의 수명을 연장하면 안 되니까요. 감시 카메라가 피사체를 못 떠나게 붙잡으면 이상하잖아요. 앱이 버린 객체는 게이지가 있든 말든 GC가 치울 수 있어야 해요. 그 대가가 바로 그 버그입니다. 게이지"만" 아는 객체는 수거되고, 메트릭은 NaN이 되거나 그래프에서 조용히 사라지죠.

그래서 한 가지는 정확히 말해둬야 해요. "게이지는 약한 참조"는 기본값이지 전부가 아니에요. 강하게 쥐는 길이 공식적으로 열려 있고, 실무에서 쓰는 모양이 셋입니다.

// ⓐ 가장 흔한 해법: 관측 대상을 내 필드로 소유한다 this.queueSize = registry.gauge("queue.size", new AtomicInteger(0)); // ⓑ 빌더에 명시적으로 요구한다 Gauge.builder("queue.size", queue, Queue::size) .strongReference(true) // registry 쪽이 대상을 강하게 쥔다 .register(registry); // ⓒ Supplier 형태는 애초에 강한 참조가 기본값 Gauge.builder("queue.size", () -> queue.size()) .register(registry); // 내부에서 strongReference(true)로 세팅됨

그래도 ⓐ가 1순위예요. 관측 대상의 소유권은 비즈니스 코드에 있는 게 자연스럽고 게이지는 구경꾼으로 남는 편이 맞으니까요. ⓑ와 ⓒ는 소유할 주체가 마땅치 않을 때 꺼내는 탈출구인데, 쥐는 쪽이 registry로 바뀐다는 뜻이기도 해요. 즉 그 객체는 registry가 살아 있는 한 수거되지 않습니다. 편한 대신 수명 관리를 떠넘기는 거라, 람다 안에 무거운 객체를 통째로 가둬두진 않았는지 한 번은 봐야 해요.

그리고 이건 게이지만의 사정이 아니에요. 2편에서 "스냅샷 모델"로 묶었던 FunctionCounter와 FunctionTimer도 구현을 열어 보면 똑같이 WeakReference로 대상을 쥐고 있어요. 남의 상태를 읽어가는 미터는 그 남을 붙잡지 않는다. Micrometer가 일관되게 지키는 계약인 셈이죠.

같은 철학의 대표 사용처가 WeakHashMap이에요. 키를 약하게 쥐는 맵인데 주 객체(키)가 앱 어디에서도 안 쓰이게 되면 엔트리가 자동으로 사라져요. "본체가 죽으면 부가 정보도 따라 죽는" 구조라서 수동 remove() 없이 누수를 막죠. 여기서 파생된 유명한 함정이 ThreadLocal 누수예요: 내부 맵의 키(ThreadLocal)는 약한데 값은 강해서 키만 수거되고 값이 좀비로 남을 수 있어요. 스레드풀처럼 스레드가 안 죽는 환경에서 remove()를 부르라는 잔소리의 근원이 이 비대칭이에요.

3. 소프트 참조: 메모리가 궁할 때만 버려라

강함과 약함 사이에 SoftReference가 있어요. 계약: "GC가 돌아도 살려두되, 메모리가 부족해지면 버려도 좋다." 명세가 보장하는 건 딱 한 줄이에요. OutOfMemoryError를 던지기 전에는 소프트 참조가 전부 비워져 있어야 한다. "남는 메모리를 캐시로 쓰다가 필요하면 반납"인 셈이니 이론상 캐시에 완벽해 보이죠.

그런데 "메모리가 궁할 때"라는 말이 생각보다 허술해요. 명세는 그 시점을 정의하지 않고 GC 재량에 맡기거든요. 실제 기준은 구현이 정합니다. 핫스팟에는 -XX:SoftRefLRUPolicyMSPerMB라는 옵션이 있어서 "남은 힙 1MB당 몇 밀리초까지 봐주느냐"를 정하는데, 기본값이 1000이에요. 여유 힙이 10MB면 마지막으로 쓴 지 10초가 넘은 소프트 참조부터 버린다는 뜻이죠. 바꿔 말하면 소프트 참조의 수명은 코드가 아니라 그날의 힙 여유가 정해요. 할당이 정말 막다른 곳에 몰리면 이 정책조차 무시하고 전부 수거한 뒤에야 OOM을 던지고요.

그래서 실무 쪽 반전이 나와요. 주류 캐시 라이브러리들은 소프트 참조를 기능으로 갖고 있으면서도 쓰지 말라고 말려요. Guava도 Caffeine도 softValues()를 제공하지만, 문서에 똑같이 "대부분의 경우 소프트 참조보다 최대 크기를 지정하는 편이 낫다"는 경고를 붙여뒀어요. 이유는 방금 본 그대로예요. 수거 시점을 힙 사정이 정하니 캐시 동작이 비결정적이 되거든요. 힙 크기를 바꾸면 히트율이 변하고, GC 설정을 건드리면 캐시가 통째로 날아갑니다.

그 결과 현실의 기본 설정은 명시적 크기 제한과 축출 정책 쪽으로 기울었어요. 참고로 Caffeine이 쓰는 건 LRU가 아니라 W-TinyLFU고요. 좋아 보이는 메커니즘도 예측 가능성이 없으면 운영 도구로는 실격이라는, 꽤 보편적인 교훈이에요.

4. 팬텀 참조: 장례식 알림 서비스

마지막 하나는 기괴합니다. PhantomReference는 get()이 항상 null이에요. 객체에 접근하는 용도가 아예 아니라는 뜻이죠. 그럼 어디에 쓰느냐면, "그 객체, 수거됐어요"라는 통지를 받는 용도예요.

ReferenceQueue<Resource> queue = new ReferenceQueue<>(); PhantomReference<Resource> ref = new PhantomReference<>(resource, queue); // 별도 스레드에서 Reference<?> dead = queue.remove(); // 수거가 일어나면 깨어남 ⚰️ // → "죽었어요" 통지 수신 → 연관 네이티브 메모리 해제 등 뒷정리

참조가 수거되면 그 껍데기가 ReferenceQueue에 들어와요. 장례식 알림인 셈이죠. 용도는 finalize()의 대체품입니다. finalize의 죄목은 셋이었어요. 부활 가능(안에서 this를 어딘가 담으면 되살아남!), 실행 보장 없음, 그리고 성능. 팬텀은 get()이 늘 null이라 부활이 원천 불가능해서 그 첫 번째 구멍부터 막혀요. 자바 9에서 들어온 Cleaner API가 이 팬텀 참조로 구현돼 있고, DirectByteBuffer의 네이티브 메모리 해제가 대표 사용처예요.

그런데 "finalize는 퇴출됐다"고 뭉뚱그리기 쉬운데, 날짜를 세워두면 이렇습니다. Object.finalize()는 자바 9에서 deprecated가 됐고, 18에서 제거 예정 deprecation으로 수위가 올라가면서 --finalization=disabled라는 스위치가 생겼어요. 다만 기본값은 지금도 "켜짐"이에요. "언젠가 기본을 끄고, 그 뒤에 제거한다"가 공식 계획이고 그 "언젠가"는 아직 오지 않았어요. 쓰면 안 되는 건 맞지만 이미 사라졌다고 말하면 틀린 셈이죠.

5. 한 장으로 정리

그림 1. 참조 4단계 스펙트럼: GC에 보내는 네 가지 신호
🧠 기억법
강 = 소유("내 거야, 치우지 마") / 소프트 = 여유("공간 남으면 놔둬") / 약 = 구경("보고만 있을게, 치워도 돼") / 팬텀 = 조문("가면 알려만 줘")
✍️ 오늘의 요약
자바 참조는 GC에 보내는 4가지 신호다. 강한 참조는 이름조차 없는 기본값(도달 가능 = 생존)이고, 약한 참조는 "관찰하되 수명에 개입하지 않겠다"는 선언이라 게이지와 WeakHashMap의 재료가 되며, 소프트는 이론상 캐시용이지만 수명을 그날의 힙 여유가 정하는 비결정성 때문에 밀려났고, 팬텀은 부활 불가능한 finalize의 후계자다.

게이지의 NaN 버그 하나를 따라왔을 뿐인데 GC의 방까지 왔다. 좋은 도구의 설계 결정은 이렇게 그 아래 층의 문을 열어주는 법이다. 마지막 4편은 반대 방향이다. 설계가 아래가 아니라 위쪽, 조직의 판단 쪽으로 문을 비워둔 경우를 본다.
