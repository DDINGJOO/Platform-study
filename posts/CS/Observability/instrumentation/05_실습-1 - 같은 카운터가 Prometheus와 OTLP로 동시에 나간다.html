Prometheus 쿼리 창에 orders_created_total을 쳤어요. 결과가 나옵니다. 그런데 같은 앱을 Prometheus가 직접 긁은 쪽 시계열을 찾으려고 {job="app-scrape"}를 붙이니 아무것도 안 나와요. 같은 앱의 같은 카운터인데, 그쪽 이름은 orders_total이었습니다. created라는 단어가 사라져 있었어요.

1편에서 Micrometer는 파사드라고 했어요. 코드는 registry.counter("orders.created")라는 중립 API만 알고, 백엔드가 무엇인지는 의존성이 정한다고요. 이번 글은 그 말을 그대로 시험합니다. 스프링 부트 앱 하나에 레지스트리를 두 개 넣고, 같은 카운터와 타이머가 Prometheus 스크레이프와 OTLP push 두 길로 동시에 나가게 만든 뒤 도착한 이름을 나란히 놓고 봤어요. 숫자와 출력은 전부 이번에 돌린 결과예요.

🧭 이 글에서 확인할 것
• 레지스트리가 둘이면 코드에 주입되는 MeterRegistry는 무엇인가?
• 같은 카운터가 두 길을 거치면 Prometheus에서 이름이 같은가?
• 타이머의 단위와 max는 두 길에서 같은 값을 말하는가?
• 대시보드와 알람 쿼리를 쓸 때 무엇을 먼저 정해야 하나?

1. 실습 환경: 레지스트리 두 개, 길 두 개

앱은 주문을 받는 엔드포인트 하나뿐이에요. 주문이 들어오면 카운터 orders.created를 지역 태그와 함께 올리고, 20~80ms 걸리는 작업을 타이머 checkout.latency로 재고, 요청 본문 크기를 order.payload(단위 bytes)에 기록합니다. 이 세 미터가 두 길로 나가요.

그림 1. 같은 미터가 두 레지스트리를 거쳐 한 Prometheus에 두 번 들어온다

경로 A는 Prometheus가 앱의 /actuator/prometheus를 10초마다 긁어 가는 길이에요. 경로 B는 앱이 10초마다 OTLP로 지표를 Collector에 밀고, Collector가 받은 그대로 Prometheus의 OTLP 수신 엔드포인트로 넘기는 길입니다. Collector에는 받은 지표를 로그로 찍는 debug 익스포터를 같이 걸어서, 앱이 OTLP로 보낸 원문도 볼 수 있게 했어요.

📖 용어: OTLP (OpenTelemetry Protocol)
OpenTelemetry가 정한 텔레메트리 전송 규약입니다. 지표 하나에 이름, 단위, 종류(Sum, Gauge, Histogram)를 따로 실어 보내요. Prometheus 3은 --web.enable-otlp-receiver 옵션을 켜면 이 형식을 직접 받습니다.

의존성은 레지스트리 구현체 두 개가 핵심이에요. spring-boot-opentelemetry는 스프링 부트의 OTLP 지표 내보내기 자동 구성이 조건으로 거는 클래스(OpenTelemetryProperties)가 들어 있는 모듈이라 같이 넣었습니다.

dependencies { implementation 'org.springframework.boot:spring-boot-starter-webmvc' implementation 'org.springframework.boot:spring-boot-starter-actuator' implementation 'io.micrometer:micrometer-registry-prometheus' // pull: /actuator/prometheus implementation 'io.micrometer:micrometer-registry-otlp' // push: OTLP/HTTP implementation 'org.springframework.boot:spring-boot-opentelemetry' }
Spring Boot 4.1.1 (Micrometer 1.17.1, Prometheus Java client 1.7.0) OTel Collector 0.162.0 (contrib) Prometheus 3.15.0 (--web.enable-otlp-receiver) 실행 환경 Docker Desktop, Apple M5 Pro

실습 코드는 GitHub 저장소의 labs/observability/instr-01-composite에 있어요. 앱은 이미지 안에서 Gradle로 빌드하니 Docker만 있으면 됩니다. 아래는 이 글의 숫자를 만든 명령 그대로예요. 서울 주문 10건, 부산 주문 5건을 넣었습니다.

git clone https://github.com/DDINGJOO/Platform-study.git cd Platform-study/labs/observability/instr-01-composite docker compose up -d --build curl -s localhost:22080/registries # 주입된 레지스트리 확인(2절) for i in $(seq 1 10); do curl -s -XPOST 'localhost:22080/orders?region=seoul' >/dev/null; done for i in $(seq 1 5); do curl -s -XPOST 'localhost:22080/orders?region=busan' >/dev/null; done sleep 20 # OTLP push(10초)와 스크레이프(10초)를 기다린다 curl -s localhost:22080/actuator/prometheus | grep -E '^(orders|checkout|order_payload)' docker compose logs otel-collector --no-log-prefix | python3 show-otlp.py # Prometheus: http://localhost:22090 에서 {__name__=~"orders.*"} 를 표로 조회(그림 2)

2. 주입받는 레지스트리는 하나다

컨트롤러 생성자는 MeterRegistry 하나만 받아요. 어느 백엔드로 갈지는 이 코드가 모릅니다.

OrderController(MeterRegistry registry) { this.registry = registry; this.checkout = Timer.builder("checkout.latency").register(registry); this.payload = DistributionSummary.builder("order.payload") .baseUnit("bytes").register(registry); } @PostMapping("/orders") String order(@RequestParam(defaultValue = "seoul") String region) { Counter.builder("orders.created").tag("region", region) .register(registry).increment(); long ms = ThreadLocalRandom.current().nextLong(20, 80); checkout.record(() -> sleep(ms)); // 실제로 20~80ms 걸리는 작업을 잰다 payload.record(ThreadLocalRandom.current().nextInt(200, 1200)); ... }

그 하나가 실제로 무엇인지 찍어 보는 엔드포인트 /registries를 하나 만들어 두었어요.

$ curl -s localhost:22080/registries org.springframework.boot.micrometer.metrics.autoconfigure.AutoConfiguredCompositeMeterRegistry └ io.micrometer.prometheusmetrics.PrometheusMeterRegistry └ io.micrometer.registry.otlp.OtlpMeterRegistry

스프링 부트가 클래스패스에서 레지스트리 구현체 두 개를 찾아 각각 빈으로 만들고, 그 둘을 묶은 복합 레지스트리를 @Primary로 내놓았어요. 부트 소스의 CompositeMeterRegistryConfiguration은 "MeterRegistry 빈이 없지도 않고 하나뿐이지도 않을 때"라는 조건으로 이 빈을 만듭니다.

📖 용어: CompositeMeterRegistry
다른 레지스트리 여러 개를 묶는 레지스트리입니다. 미터를 등록하면 묶인 레지스트리마다 같은 이름의 미터를 하나씩 만들고, increment() 한 번을 전부에 전달해요. 자기는 값을 저장하지도 내보내지도 않습니다.

여기까지는 1편이 말한 그대로예요. 코드는 레지스트리 하나만 보고, 그 뒤에서 두 벌로 갈라집니다. 문제는 갈라진 두 벌이 각자 자기 백엔드의 관례대로 이름을 바꾼다는 데서 시작해요.

3. 같은 카운터, 이름이 둘

먼저 경로 A, Prometheus가 긁어 가는 원문이에요.

# TYPE orders_total counter orders_total{region="busan"} 5.0 orders_total{region="seoul"} 10.0

다음은 경로 B, 앱이 OTLP로 보낸 것을 Collector의 debug 익스포터가 찍은 원문입니다.

-> Name: orders.created -> Unit: -> DataType: Sum -> IsMonotonic: true -> AggregationTemporality: Cumulative Data point attributes: -> region: Str(seoul) Value: 10.000000 Data point attributes: -> region: Str(busan) Value: 5.000000

OTLP 쪽은 코드에 쓴 이름 orders.created를 점까지 그대로 보냈어요. 종류는 단조 증가하는 Sum, 시간성은 누적(Cumulative)입니다. 이 둘이 같은 Prometheus에 도착한 모습이 아래예요.

그림 2. 값은 같은데 이름이 다르다. 한 쿼리로는 둘 중 하나만 잡힌다
📖 용어: 시간성 (aggregation temporality)
카운터 값을 "시작부터 지금까지의 합계"(Cumulative)로 보내느냐, "지난 보고 이후 늘어난 만큼"(Delta)으로 보내느냐입니다. Prometheus는 누적 값을 받아 rate()로 증가율을 계산해요. 스프링 부트의 OTLP 내보내기 기본값은 Cumulative입니다.

created는 어디로 갔나

OTLP 경로의 orders_created_total은 예상대로예요. Prometheus가 점을 밑줄로 바꾸고, 카운터라서 _total을 붙였습니다. 이상한 건 스크레이프 쪽이에요. Micrometer의 Prometheus 이름 규칙(PrometheusNamingConvention)을 열어 보면 마지막 줄이 이렇습니다.

return PrometheusNaming.sanitizeMetricName(conventionName);

이 함수는 Micrometer가 아니라 Prometheus 자바 클라이언트(1.7.0)에 있어요. 소스에 예약 접미사 목록이 있습니다.

static final String[] RESERVED_METRIC_NAME_SUFFIXES = { "_total", "_created", "_bucket", "_info", ".total", ".created", ".bucket", ".info" };

이름이 이 중 하나로 끝나면 떼어 내요. OpenMetrics 형식에서 카운터는 이름_total과 함께 "언제 0부터 세기 시작했나"를 뜻하는 이름_created를 같이 쓸 수 있어서, 사용자가 지은 이름에 _created가 남아 있으면 그 줄과 헷갈린다는 이유입니다. 그래서 orders.created → orders_created → orders가 되고, 카운터 출력기가 _total을 붙여 orders_total이 됐어요.

같은 앱에 있던 톰캣 지표가 이 설명을 확인해 줍니다. 스프링 부트가 등록하는 tomcat.sessions.created는 단위가 sessions라서 이름 규칙이 먼저 _sessions를 붙여요. 그러면 _created가 끝에 있지 않으니 떼이지 않고 tomcat_sessions_created_sessions_total로 그대로 나왔습니다. 떼이느냐 마느냐는 단어가 아니라 그 단어가 이름 끝에 오느냐로 갈려요.

⚠️ 주의: 1편의 예시 이름이 바로 이 경우다
1편은 파사드를 설명하며 registry.counter("orders.created", "region", "seoul")을 예로 들었어요. 이 이름은 Prometheus 레지스트리로 내보내면 orders_total이 됩니다. 1편이 말한 "계측 코드는 한 글자도 안 바뀜"은 맞지만, 백엔드를 바꾸면 쿼리 쪽 이름은 바뀔 수 있다는 것까지 같이 기억해야 해요. 카운터 이름을 .created, .total, .info, .bucket으로 끝내지 않는 편이 안전합니다.

4. 타이머는 단위부터 다르다

카운터는 이름만 달랐는데, 타이머는 값 자체가 달라요. 같은 15건을 두 길로 본 결과입니다.

# 경로 A: 스크레이프 checkout_latency_seconds_count 15 checkout_latency_seconds_sum 0.723872208 checkout_latency_seconds_max 0.077636083 # 경로 B: OTLP 원문 (Collector debug) -> Name: checkout.latency -> Name: checkout.latency.max -> Unit: milliseconds -> Unit: milliseconds -> DataType: Histogram -> DataType: Gauge Count: 15 Value: 77.636083 Sum: 723.872208

합계가 한쪽은 0.7239, 다른 쪽은 723.87이에요. Prometheus 레지스트리는 시간을 초로 내보내고, OTLP 레지스트리는 밀리초로 내보냅니다. Micrometer의 OtlpConfig.baseTimeUnit() 기본값이 MILLISECONDS이고, 스프링 부트의 management.otlp.metrics.export.base-time-unit 기본값도 밀리초예요.

이 둘이 Prometheus에 도착하면 이름이 이렇게 갈립니다.

경로 A (스크레이프) 경로 B (OTLP → Prometheus) checkout_latency_seconds_count checkout_latency_milliseconds_count checkout_latency_seconds_sum checkout_latency_milliseconds_sum (없음) checkout_latency_milliseconds_bucket{le="+Inf"} checkout_latency_seconds_max checkout_latency_max_milliseconds order_payload_bytes_count / _sum order_payload_bytes_count / _sum order_payload_bytes_max order_payload_max_bytes

세 가지가 달라요. 첫째, 단위 접미사가 _seconds와 _milliseconds입니다. 같은 rate(..._sum[5m]) / rate(..._count[5m]) 쿼리가 한쪽에서는 0.048, 다른 쪽에서는 48을 돌려줘요. 둘째, OTLP 쪽은 Histogram이라서 버킷 줄이 생기는데, 히스토그램 옵션을 켜지 않았으니 버킷이 +Inf 하나뿐입니다. 셋째, max는 Micrometer가 OTLP로 보낼 때 .max를 붙인 별도 Gauge로 보내고, Prometheus가 그 뒤에 단위를 붙여서 _max_milliseconds가 됐어요. 스크레이프 쪽은 _seconds_max라 순서가 반대입니다.

스프링이 자동으로 만드는 HTTP 지표도 똑같아요. 같은 Prometheus 안에 http_server_requests_seconds_count와 http_server_requests_milliseconds_count가 같이 있었습니다. 그리고 하나 더, Micrometer 공식 문서의 이름 규칙 페이지는 http.server.requests 타이머의 Prometheus 이름을 http_server_requests_duration_seconds라고 적고 있지만, 이번 실행에서 나온 이름은 http_server_requests_seconds였어요. PrometheusNamingConvention의 기본 타이머 접미사가 빈 문자열이기 때문입니다. 문서의 예시와 실제 출력이 다르면 실제 출력을 믿어요.

📖 용어: 네이밍 컨벤션 (NamingConvention)
Micrometer가 점으로 구분한 이름(checkout.latency)을 백엔드 관례에 맞는 이름으로 바꾸는 규칙입니다. 레지스트리마다 하나씩 있어요. Prometheus용은 밑줄로 바꾸고 단위 접미사를 붙이고, OTLP용은 이름을 거의 그대로 두는 대신 단위를 별도 필드로 보냅니다.

5. max는 기억하는 시간이 다르다

단위를 맞춰서 보면 max는 같은 값이었어요. 0.077636083초와 77.636083밀리초입니다. 그런데 주문을 멈추고 몇 분 지켜보니 둘이 다르게 움직였어요. 마지막 주문은 15시 22분 16초쯤이었습니다.

시각 checkout_latency_seconds_max checkout_latency_max_milliseconds (스크레이프, 초) (OTLP, 밀리초) 15:22:26 0.077636083 77.636083 15:22:36 0.077636083 77.636083 15:22:46 0.077636083 0 15:23:26 0.077636083 0 15:24:36 0.077636083 (이 시각은 스크레이프 쪽만 조회) 15:25:16 0 ← 앱의 /actuator/prometheus 에서 0 을 처음 본 시각

OTLP 쪽은 30초 안에 0이 됐고, 스크레이프 쪽은 약 3분을 버텼어요. Micrometer의 max는 전체 기간의 최댓값이 아니라 최근 시간 창 안의 최댓값이에요. 두 레지스트리는 같은 방식으로 이 창을 정해요. 둘 다 defaultHistogramConfig()에서 창의 길이(expiry)를 자기 step으로 바꿉니다(Micrometer 1.17.1 PrometheusMeterRegistry와 OtlpMeterRegistry). 다른 건 step 값뿐이에요. Prometheus 레지스트리의 step은 기본 1분이고, OTLP는 이 실습에서 10초로 줄였어요. max를 담는 TimeWindowMax는 칸 3개짜리 고리를 expiry마다 한 칸씩 넘기기 때문에, 기록된 값이 step의 2~3배 동안 남아요. 실측 약 3분(1분의 3배)과 30초 안(10초의 3배 안)이 그 범위에 들어요. 같은 "max" 패널이라도 OTLP 경로의 값은 최근 수십 초, 스크레이프 경로의 값은 최근 몇 분의 최댓값입니다.

📖 용어: step
레지스트리가 시간 단위로 값을 묶는 주기입니다. push 방식인 OTLP 레지스트리에서는 지표를 모아 보내는 주기이기도 해요. 기본 60초인데 이 실습은 management.otlp.metrics.export.step: 10s로 줄였어요. Prometheus 레지스트리에도 step이 있고(기본 1분), 두 레지스트리 모두 max와 백분위의 시간 창 길이를 이 값으로 정해요.

6. 라벨도 다르게 붙는다

그림 2를 다시 보면 라벨이 달라요. 스크레이프 쪽은 job="app-scrape", instance="app:8080"이 붙었습니다. Prometheus 설정의 잡 이름과 긁은 주소예요. OTLP 쪽은 job="instr-01"이고 instance가 없습니다. Prometheus 문서는 OTLP로 받은 지표의 job을 리소스 속성 service.name에서, instance를 service.instance.id에서 만든다고 설명해요. 스프링 부트는 spring.application.name을 service.name으로 보냈고, Micrometer OTLP 레지스트리는 인스턴스 ID를 보내지 않았습니다. 대신 리소스 정보를 담은 target_info가 하나 생겼어요.

target_info{job="instr-01", telemetry_sdk_language="java", telemetry_sdk_name="io.micrometer", telemetry_sdk_version="1.17.1"}

인스턴스가 여러 대인 서비스를 OTLP로 보내면서 인스턴스 속성을 따로 주지 않으면, 같은 job과 같은 태그를 가진 시계열이 여러 대에서 한 이름으로 들어와요. 누적 카운터 여러 개가 한 시계열로 섞이면 값이 오르락내리락해서 rate()가 망가집니다. 이번 실습은 한 대라서 이 증상까지는 재현하지 않았어요. OTLP 경로를 쓴다면 management.opentelemetry.resource-attributes 같은 설정으로 service.instance.id를 넣어 줘야 하는지 먼저 확인하세요.

📖 용어: target_info
Prometheus가 OTLP로 받은 리소스(서비스 이름, SDK 정보 등) 하나마다 만드는 정보용 시계열입니다. 값은 늘 1이고, 라벨에 리소스 속성이 들어 있어요. 다른 지표와 조인해서 속성을 끌어올 때 씁니다.
💡 실무에서는: 두 길을 같이 쓸 때
• 한 백엔드에는 한 길로만 넣어요. 같은 Prometheus에 스크레이프와 OTLP를 같이 넣으면 같은 사건이 이름만 다른 두 시계열이 되고, 저장 비용도 두 배가 돼요
• OTLP를 쓰면 시간 단위를 먼저 정해요. 기존 대시보드가 _seconds를 기대한다면 management.otlp.metrics.export.base-time-unit=seconds로 맞추는 방법이 있어요. 이번 실습에서 이 값을 바꿔 돌리지는 않았어요
• 이름 끝 단어를 조심해요. .created, .total, .info, .bucket으로 끝나는 미터 이름은 경로마다 다르게 잘려요
• 대시보드를 옮길 때는 쿼리보다 원문을 먼저 봐요. /actuator/prometheus와 Collector debug 로그를 한 번씩 찍어 보면 이름 차이가 바로 보여요

정리하면 파사드는 약속을 지켰어요. 코드 한 줄 안 바꾸고 두 백엔드로 나갔습니다. 다만 파사드가 막아 주는 건 계측 코드의 변경이고, 쿼리는 그 뒤 레지스트리와 수신 측의 이름 규칙을 따라 바뀝니다. 이름, 단위, max의 시간 창, 라벨이 모두 달랐어요.

✍️ 오늘의 요약
레지스트리 두 개를 넣자 스프링 부트가 CompositeMeterRegistry를 주입했고, 같은 카운터와 타이머가 두 길로 나갔다. 그런데 Prometheus에 도착한 이름은 달랐다. orders.created는 스크레이프 쪽에서 예약 접미사 _created가 떼여 orders_total, OTLP 쪽에서 orders_created_total이 됐고, 타이머는 초와 밀리초로 갈렸다.

max도 같은 말이 아니었다. 스크레이프 쪽은 약 3분, OTLP 쪽은 30초 안에 0으로 돌아갔다. 파사드는 계측 코드를 지켜 주지만, 쿼리가 보는 이름은 레지스트리가 정한다.
