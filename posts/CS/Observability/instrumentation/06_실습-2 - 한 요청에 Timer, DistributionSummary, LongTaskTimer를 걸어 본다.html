20초 걸리는 보고서 요청을 하나 보냈어요. 5초 뒤에 지표를 열어 봅니다. 요청 처리 시간을 재는 타이머의 count는 그대로예요. 지금 서버가 20초짜리 일을 하고 있다는 흔적이 타이머에는 하나도 없습니다. 같은 순간 다른 미터 하나는 "1개 진행 중, 5초째"라고 말하고 있었어요.

2편에서 미터 다섯 종류를 데이터 모델로 나눴어요. 타이머는 끝난 이벤트를 접어서 저장하고, LongTaskTimer는 진행 중인 작업의 명부를 들고 있다고요. 이번 글은 한 엔드포인트에 Timer, DistributionSummary, LongTaskTimer를 같이 걸고, Prometheus가 긁어 가는 출력 원문을 나란히 놓고 봅니다. 백분위를 앱이 계산하게 할 때와 버킷을 내보내 Prometheus가 계산하게 할 때가 어떻게 다른지도 같이 쟀어요.

🧭 이 글에서 확인할 것
• 미터 네 개를 건 요청 하나가 /actuator/prometheus에 몇 줄을 만드는가?
• 끝나지 않은 요청은 어느 미터에 보이는가?
• stop()을 빼먹은 LongTaskTimer는 어떻게 보이는가?
• 앱이 계산한 p99와 버킷으로 계산한 p99는 무엇이 다른가?

1. 실습 환경: 보고서 엔드포인트 하나

POST /reports?ms=N은 N 밀리초 동안 보고서를 만들고, 만든 행 수를 돌려줍니다. 여기에 미터 네 개를 걸었어요. 타이머가 둘인 건 백분위를 내는 방식 두 가지를 비교하려고서예요.

this.duration = Timer.builder("report.duration") .publishPercentileHistogram() // 버킷을 내보낸다 → PromQL 로 백분위 계산 .register(registry); this.durationPct = Timer.builder("report.duration.pct") .publishPercentiles(0.5, 0.99) // 앱이 백분위를 계산해 값으로 내보낸다 .register(registry); this.rows = DistributionSummary.builder("report.size") .baseUnit("rows").register(registry); this.active = LongTaskTimer.builder("report.active").register(registry); @PostMapping("/reports") String report(@RequestParam long ms) { LongTaskTimer.Sample task = active.start(); // 시작하자마자 명부에 올라간다 Timer.Sample sample = Timer.start(); try { sleep(ms); rows.record(ThreadLocalRandom.current().nextInt(100, 5000)); ... } finally { long nanos = sample.stop(duration); // 끝나야 기록된다 durationPct.record(nanos, TimeUnit.NANOSECONDS); task.stop(); // 명부에서 지운다 } }
📖 용어: DistributionSummary
시간이 아닌 크기(바이트, 행 수, 금액)의 분포를 재는 미터입니다. 타이머와 구조가 같아서 건수, 합계, 최댓값을 내보내요. 단위는 baseUnit으로 붙입니다.
📖 용어: LongTaskTimer
start()부터 stop()까지 진행 중인 작업을 명부로 들고 있다가, 지표를 읽는 순간 "지금 몇 개가 몇 초째 돌고 있나"를 계산하는 미터입니다. 끝난 작업의 기록은 남기지 않아요.
Spring Boot 4.1.1 (Micrometer 1.17.1) Prometheus 3.15.0 (5초마다 스크레이프) k6 2.3.0 실행 환경 Docker Desktop, Apple M5 Pro

실습 코드는 GitHub 저장소의 labs/observability/instr-02-meters에 있어요.

git clone https://github.com/DDINGJOO/Platform-study.git cd Platform-study/labs/observability/instr-02-meters docker compose up -d --build curl -s -XPOST 'localhost:22180/reports?ms=100' curl -s localhost:22180/actuator/prometheus | grep report_ # Prometheus: http://localhost:22190

2. 요청 하나가 만든 출력

100ms짜리 요청을 하나 보낸 직후의 출력이에요. 버킷 줄은 처음과 끝만 남기고 줄였습니다.

# TYPE report_duration_seconds histogram report_duration_seconds_bucket{le="0.001"} 0 report_duration_seconds_bucket{le="0.001048576"} 0 ... (68개 + "+Inf") report_duration_seconds_bucket{le="30.0"} 1 report_duration_seconds_bucket{le="+Inf"} 1 report_duration_seconds_count 1 report_duration_seconds_sum 0.101498625 report_duration_seconds_max 0.101498625 # TYPE report_duration_pct_seconds summary report_duration_pct_seconds{quantile="0.5"} 0.100663296 report_duration_pct_seconds{quantile="0.99"} 0.100663296 report_duration_pct_seconds_count 1 report_duration_pct_seconds_sum 0.101498625 report_duration_pct_seconds_max 0.101498625 # TYPE report_size_rows summary report_size_rows_count 1 report_size_rows_sum 2804.0 report_size_rows_max 2804.0 # TYPE report_active_seconds summary report_active_seconds_count 0 report_active_seconds_sum 0.0 report_active_seconds_max 0.0

읽을 거리가 네 가지 있었어요.

첫째, 버킷을 켠 타이머 하나가 72줄입니다. 버킷 69줄(68개 + +Inf)에 count, sum, max까지요. 백분위 두 개를 앱이 계산하는 쪽은 5줄이에요. 버킷 경계는 1ms에서 30초까지였는데, Micrometer 문서의 히스토그램 페이지는 타이머 기본 범위를 "1ms~1분, 버킷 73개"라고 적고 있어요. Micrometer 1.17.1 소스의 AbstractTimerBuilder는 기본 최댓값을 Duration.ofSeconds(30)으로 두고 있어서, 문서보다 소스와 실제 출력이 맞습니다. 30초를 넘는 요청은 전부 +Inf 버킷에만 들어가요.

둘째, 앱이 계산한 백분위는 정확한 값이 아닙니다. 기록한 값은 101.50ms 하나뿐인데 p50, p99가 100.66ms로 나왔어요. Micrometer는 값을 다 들고 있지 않고 정밀도를 정한 히스토그램에 넣은 뒤 백분위를 근사합니다. 기본 정밀도(percentilePrecision 1)에서는 이 정도 오차가 나요.

셋째, DistributionSummary의 단위는 이름 끝에 붙습니다. report.size에 baseUnit("rows")를 주니 report_size_rows가 됐어요. 이름을 report.rows로 지었다면 단위를 다시 붙이지 않고 report_rows가 됩니다.

넷째, LongTaskTimer가 summary 타입으로 나옵니다. 이번 실습과 같이 publishPercentileHistogram을 켜지 않은 기본 상태의 이야기예요. 켜면 버킷이 붙은 gauge histogram으로 나간다는 것을 소스(PrometheusMeterRegistry)에서 확인했지만, 그렇게 돌려 보지는 않았어요. 그래서 report_active_seconds_count라는 이름이 생겼는데, 이 값은 누적 건수가 아니라 지금 진행 중인 작업 수예요. 오르내리는 값이라 rate()를 씌우면 안 됩니다. 2편이 말한 active, duration, max는 Prometheus에서 각각 _count, _sum, _max로 나와요.

3. 20초짜리 요청이 도는 동안

이제 처음 장면을 재현해요. 20초짜리 요청을 백그라운드로 보내고 5초, 12초 뒤에 지표를 읽었습니다.

curl -s -XPOST 'localhost:22180/reports?ms=20000' & sleep 5; curl -s localhost:22180/actuator/prometheus | grep -E '^report_(active|duration_seconds_(count|sum|max))'
--- 5초 뒤 (15:26:34) report_active_seconds_count 1 report_active_seconds_sum 5.01697967 report_active_seconds_max 5.016983086 report_duration_seconds_count 1 ← 앞서 보낸 100ms 요청 하나뿐 report_duration_seconds_sum 0.101498625 --- 12초 뒤 (15:26:41) report_active_seconds_count 1 report_active_seconds_sum 12.03843663 report_active_seconds_max 12.038439422 report_duration_seconds_count 1 --- 요청이 끝난 뒤 (15:26:55) report_active_seconds_count 0 report_active_seconds_sum 0.0 report_active_seconds_max 0.0 ← 20초 작업의 흔적이 남지 않는다 report_duration_seconds_count 2 report_duration_seconds_sum 20.102231425 report_duration_seconds_max 20.0007328
그림 1. 진행 중인 20초는 LongTaskTimer만 안다

2편이 말한 그대로예요. 타이머는 끝나야 기록하고, LongTaskTimer는 끝나면 잊습니다. 둘을 같이 걸어야 "지금 문제 있나"와 "평소 얼마나 걸리나"를 둘 다 볼 수 있어요. 타이머의 max는 20초로 남았지만 이건 실습-1에서 본 대로 시간 창이 지나면 0으로 돌아가는 값입니다.

스프링은 이미 하나를 걸어 두었다

같은 출력에 우리가 만들지 않은 LongTaskTimer가 하나 더 있었어요.

http_server_requests_active_seconds_count{exception="none",method="POST",outcome="SUCCESS",status="200",uri="UNKNOWN"} 1 http_server_requests_active_seconds_sum{...,method="POST",...,uri="UNKNOWN"} 5.017155086 http_server_requests_active_seconds_count{...,method="GET",...,uri="UNKNOWN"} 1 ← 이 스크레이프 요청 자신

스프링의 HTTP 서버 계측이 요청마다 http.server.requests.active라는 LongTaskTimer를 같이 돌려요. 그런데 uri가 UNKNOWN입니다. 이 LongTaskTimer는 요청이 시작될 때 태그를 정하는데, 그 시점에는 스프링이 아직 요청을 어느 핸들러로 보낼지 정하기 전이라 경로 템플릿을 모르기 때문이에요. 그래서 이 지표로는 "어느 엔드포인트가 오래 걸리고 있나"를 구분할 수 없었어요. 특정 작업의 진행 상황을 보고 싶으면 이번 실습과 같이 그 작업에 직접 LongTaskTimer를 거는 편이 낫습니다.

4. stop()을 빼먹으면 끝난 요청이 명부에 남는다

/reports/leaky는 active.start()만 부르고 끝나는 엔드포인트예요. 세 번 부르고 30초 뒤에 읽었습니다.

for i in 1 2 3; do curl -s -XPOST localhost:22180/reports/leaky; done sleep 30; curl -s localhost:22180/actuator/prometheus | grep '^report_active' report_active_seconds_count 3 report_active_seconds_sum 90.103343706 report_active_seconds_max 30.042878764

요청은 이미 200을 받고 끝났는데 명부에는 세 개가 남았어요. 같은 실행에서 1분쯤 더 지난 뒤(15:28:34)에는 _sum이 285.8초, _max가 95.3초까지 자라 있었습니다. report_active_seconds_max > 90 같은 알람을 걸어 두었다면 이 남은 항목 때문에 울리고, 앱을 재시작하기 전까지 계속 울려요.

스택을 새로 띄우고 같은 일을 한 번 더 해서 그래프로 그렸습니다. 30초짜리 요청 하나를 보낸 뒤, 끝나고 15초 뒤에 leaky를 세 번 불렀어요(그래프 시각은 UTC라서 06:31이 한국 시각 15:31이에요).

docker compose down -v && docker compose up -d curl -s -XPOST 'localhost:22180/reports?ms=30000' # 30초짜리 요청, 끝날 때까지 기다린다 sleep 15 for i in 1 2 3; do curl -s -XPOST localhost:22180/reports/leaky; done sleep 60 # Prometheus http://localhost:22190 → Graph, 3m # {__name__=~"report_active_seconds_count|report_duration_seconds_count"}
그림 2. 진행 중일 때만 1이던 선이, stop()을 빼먹자 3에서 내려오지 않는다
⚠️ 주의: LongTaskTimer는 finally에서 멈춘다
예외가 나도 stop()이 불리게 try/finally로 감싸요. 타이머에서 stop()을 빼먹으면 데이터 하나가 빠지지만, LongTaskTimer에서 빼먹으면 값이 영원히 남아 알람이 됩니다. 비동기 작업이면 콜백의 성공과 실패 경로 양쪽에서 멈추는지 확인해요.

5. 백분위: 앱이 계산할까, 버킷을 보낼까

k6로 60초 동안 보고서 요청을 보냈어요. 동시 사용자 5명이고, 요청의 98%는 50~150ms, 2%는 1~2초짜리 느린 보고서입니다. 이 절의 숫자는 스택을 새로 띄워 이 부하 하나만 준 실행에서 나왔어요.

docker compose down -v && docker compose up -d docker compose --profile load run --rm load http_req_duration: avg=129.17ms med=101.94ms p(90)=142.3ms p(99)=1.55s max=1.99s http_reqs........: 2341

부하가 끝난 직후(15:29:53) 두 타이머와 PromQL 결과를 비교했습니다.

p50 p99 k6가 잰 응답 시간 101.94ms 1.55s 앱이 계산 (report_duration_pct) 102.76ms 1.676s 버킷으로 계산 histogram_quantile [1m] 102.39ms 1.578s histogram_quantile(0.99, rate(report_duration_seconds_bucket[1m]))

둘 다 근사값이고, 이 실행에서는 버킷 쪽이 k6에 더 가까웠어요. 1~2초 구간의 버킷 경계는 1.07초, 1.43초, 1.79초로 0.36초 간격이고, p99가 1.43~1.79초 버킷 안에서 보간됐어요. 두 방식의 차이는 부하가 끝난 뒤에 드러났어요.

📖 용어: histogram_quantile
버킷별 누적 건수(_bucket{le="..."})에서 백분위를 추정하는 PromQL 함수입니다. 목표 백분위가 들어 있는 버킷을 찾고, 그 버킷 안에서는 값이 고르게 퍼져 있다고 가정해 선형으로 보간해요.

부하가 끝난 뒤

요청을 더 보내지 않고 앱이 계산한 p99를 10초마다 읽었어요.

15:29:53 p50=0.102760448 p99=1.675624448 ← 부하 종료 직후 15:30:05 p50=0.102760448 p99=1.474297856 15:30:25 p50=0.09437184 p99=1.742733312 15:30:45 p50=0.0 p99=0.0

새 요청이 없는데도 p99가 1.68 → 1.47 → 1.74로 바뀌다가 52초 뒤 0이 됐어요. Prometheus 레지스트리는 백분위의 시간 창 길이(expiry)를 자기 step(기본 1분)으로 두고, 그 창을 3칸으로 나눠 20초마다 한 칸씩 넘겨요(AbstractTimeWindowHistogram). 창이 한 칸 밀릴 때마다 계산 대상이 바뀌고, 마지막 기록은 40~60초 뒤에 창에서 빠집니다. 실측 52초가 그 범위에 들어요. 그리고 한 번 지나간 창은 다시 계산할 수 없어요.

버킷은 누적 건수라서 지나간 구간도 다시 셀 수 있습니다. 같은 시각(15:31:03)에 두 쿼리를 던졌어요.

histogram_quantile(0.99, rate(report_duration_seconds_bucket[1m])) → NaN (최근 1분에 요청 없음) histogram_quantile(0.99, increase(report_duration_seconds_bucket[10m])) → 1.534

최근 1분에는 요청이 없으니 NaN이 맞고, 범위를 10분으로 넓히면 부하 구간 전체의 p99를 다시 계산해 줘요. 창의 길이를 쿼리하는 사람이 정할 수 있다는 점이 버킷의 장점입니다. Micrometer 문서도 publishPercentiles의 값은 "차원 사이에서 합칠 수 없다(non-aggregable)"고 적고, 합칠 수 있는 근사가 필요하면 publishPercentileHistogram을 쓰라고 해요. 여러 인스턴스의 p99를 평균 내면 왜 틀리는지는 「집계와 분포」 시리즈의 실습에서 따로 다룹니다.

📖 용어: 클라이언트 백분위 (client-side percentile)
앱 안에서 백분위를 미리 계산해 quantile="0.99" 같은 라벨을 단 값으로 내보내는 방식입니다. 줄 수가 적은 대신, 정한 백분위와 정한 시간 창 밖의 질문에는 답하지 못해요.

한 가지 더, 스프링이 만드는 http.server.requests는 기본으로 버킷을 내보내지 않아요. 이번 실행에서 http_server_requests_seconds_bucket으로 histogram_quantile을 돌리니 결과가 비어 있었습니다. 켜려면 management.metrics.distribution.percentiles-histogram.http.server.requests=true를 줘야 해요.

💡 실무에서는: 미터를 고를 때
• 지연 백분위는 버킷으로 내보내요. 인스턴스를 합치거나 지난 구간을 다시 보려면 버킷이 있어야 해요. 대신 타이머 하나, 태그 조합 하나마다 약 70줄이 늘어요
• 버킷 범위를 서비스에 맞춰요. 기본 상한이 30초라서 그보다 긴 작업은 +Inf에만 쌓여요. maximumExpectedValue로 늘리거나 serviceLevelObjectives로 필요한 경계만 지정해요
• 오래 걸리는 작업에는 LongTaskTimer를 같이 걸어요. 알람은 _max(가장 오래 돈 작업의 경과 시간)에 걸고, _count는 진행 중인 개수라서 rate()를 씌우지 않아요
✍️ 오늘의 요약
한 요청에 미터 넷을 걸자 각자 다른 시점을 기록했다. 타이머는 요청이 끝나는 순간 한 번 기록했고, LongTaskTimer는 진행 중인 동안만 "1개, 12초째"를 보여 주고 끝나면 잊었다. stop()을 빼먹은 작업 셋은 명부에 남아 계속 자랐다.

백분위는 앱이 계산한 쪽이 5줄, 버킷 쪽이 72줄이었다. 대신 앱 쪽 p99는 부하가 끝나고 52초 뒤 0이 됐고, 버킷은 10분 뒤에도 그 구간의 p99를 다시 계산했다. 줄 수를 아끼면 나중에 던질 수 있는 질문이 줄어든다.
