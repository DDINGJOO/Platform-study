서비스 대시보드에 "전체 p99" 패널이 하나 있다고 해 볼게요. 쿼리를 열어 보니 avg(...{quantile="0.99"})예요. 인스턴스마다 자기 p99를 보고하고, 대시보드는 그걸 평균 내서 보여 주고 있었습니다. 숫자는 200ms 근처에서 얌전히 움직이고, 아무도 이상하다고 느끼지 않아요.

1편에서 백분위는 합칠 수 없는 완성품이고, 합치려면 버킷을 재료째 보내야 한다고 했습니다. 이번 글은 그 말을 숫자로 확인합니다. 지연 분포가 다른 인스턴스 세 대에 부하를 주고, p99의 평균, 버킷을 합쳐 계산한 p99, k6가 모든 요청을 보고 잰 실제 p99를 나란히 놓았어요. 화면과 숫자는 전부 이번에 돌린 결과입니다.

🧭 이 글에서 확인할 것
• p99 세 개를 평균 내면 실제 p99와 얼마나 차이 나는가?
• 트래픽 비중이 바뀌면 그 오차는 어느 방향으로 움직이는가?
• 버킷을 합친 p99는 정확한가, 아니면 운이 좋았던 것인가?
• 같은 타이머에 백분위와 버킷을 둘 다 켜면 무엇이 나오는가?

1. 실습 환경: 빠른 두 대와 가끔 느린 한 대

스프링 부트 앱 하나를 세 번 띄웁니다. /work 엔드포인트는 요청마다 20~60ms 사이에서 무작위로 잠들었다가 응답해요. 세 번째 인스턴스 app-c에만 환경변수 LAB_SLOW_RATIO=0.1을 줘서, 요청의 10%를 300~500ms로 늦췄습니다. GC가 자주 도는 노드나 이웃 컨테이너가 시끄러운 노드 하나를 흉내 낸 거예요.

그림 1. 같은 코드 세 대, 느린 꼬리는 한 대에만 있다

세 대가 같은 양을 받으면 느린 요청은 전체의 약 3.3%가 됩니다. 실제 실행에서는 3.6%였어요(아래). 전체 p99는 "빠른 쪽에서 99%째 요청"이니 느린 요청 무리 안쪽 어딘가에 있어야 합니다. 그런데 p99를 셋 평균 내면 빠른 두 대의 60ms가 세 값 중 두 자리를 차지해요. 1편의 "평균의 평균" 함정이 백분위에서 어떻게 나타나는지 보려는 설정입니다.

쓴 버전은 아래와 같아요.

Spring Boot 4.1.1 (Java 21, Micrometer 1.17.1) Prometheus 3.15.0 Grafana 13.2.3 k6 2.3.0 실행 환경 Docker Desktop, Apple M5 Pro

실습 코드는 GitHub 저장소의 labs/observability/agg-01-percentile-avg에 있습니다. 다른 실습과 동시에 띄워도 겹치지 않게 호스트 포트를 23000번대로 잡았어요.

git clone https://github.com/DDINGJOO/Platform-study.git cd Platform-study/labs/observability/agg-01-percentile-avg docker compose up -d --build docker compose --profile load run --rm load # 초당 60건, 3분, 세 대에 차례로 # Grafana: http://localhost:23000 → 대시보드 「실습-1 p99 평균 vs 버킷 합산」

2. 버킷을 켜자 p99가 사라졌다

처음에는 스프링 부트의 자동 타이머 http.server.requests 하나에 두 가지를 다 켰어요. 인스턴스가 직접 계산하는 p99와, 백엔드가 합칠 수 있는 버킷입니다.

management: metrics: distribution: percentiles: http.server.requests: 0.99 # 앱이 계산한 p99 를 내보낸다 percentiles-histogram: http.server.requests: true # 버킷을 내보낸다
📖 용어: 클라이언트 백분위 (client-side percentile)
앱 프로세스 안에서 최근 요청들의 분포를 들고 있다가 p99 같은 값을 직접 계산해 내보내는 방식입니다. Prometheus에는 quantile="0.99" 라벨이 붙은 숫자 하나로 도착해서, 다른 인스턴스 값과 다시 합칠 재료가 남지 않아요.

그런데 /actuator/prometheus를 열어 보니 quantile 줄이 하나도 없었습니다. 버킷 줄과 _count, _sum, _max만 있었어요. 버킷 설정만 끄고 다시 띄우자 그제야 나왔습니다.

# 버킷을 켰을 때 # TYPE http_server_requests_seconds histogram http_server_requests_seconds_bucket{...,uri="/work",le="0.001"} 0 ... (버킷 68개 + le="+Inf") http_server_requests_seconds_count{...,uri="/work"} 1 # 버킷을 껐을 때 # TYPE http_server_requests_seconds summary http_server_requests_seconds{...,uri="/work",quantile="0.99"} 0.082837504

원인은 Micrometer의 Prometheus 레지스트리 코드에 있었어요. Micrometer 1.13부터 쓰는 새 레지스트리(io.micrometer.prometheusmetrics.PrometheusMeterRegistry)는 타이머에 버킷이 하나라도 있으면 Prometheus의 histogram 타입으로 내보내고, 버킷이 없을 때만 summary 타입으로 만들면서 quantile 값을 넣습니다. 한 이름이 histogram이면서 summary일 수는 없으니, 버킷을 켜는 순간 앱이 계산한 백분위는 조용히 빠져요. 설정 오류 경고도 없었습니다. 1.12까지 쓰던 예전 레지스트리 소스에는 "Prometheus는 한 지표가 histogram이면서 summary여도 거부하지 않는다"는 주석과 함께 quantile 줄과 버킷 줄을 같이 내보내는 코드가 있었어요. 버전을 올리면서 동작이 바뀐 겁니다.

📖 용어: Prometheus의 summary와 histogram
지연 분포를 내보내는 두 가지 지표 타입입니다. summary는 앱이 계산한 백분위 값(quantile 라벨)을 보내고, histogram은 "이 시간 이하가 몇 건"인 누적 버킷(le 라벨)을 보내요. 여러 인스턴스를 합칠 수 있는 쪽은 histogram입니다.

그래서 비교용 p99는 lab.work라는 타이머를 따로 만들어, 같은 요청에서 잠드는 구간만 따로 재게 했어요. 자동 타이머에는 버킷만, lab.work에는 클라이언트 p99만 켰습니다.

management: metrics: distribution: percentiles-histogram: http.server.requests: true # 버킷: 인스턴스를 합칠 수 있다 percentiles: lab.work: 0.99 # 앱이 계산한 p99: 합칠 수 없다

출력을 보다가 하나 더 걸렸어요. 설정에는 http.server.requests라고만 썼는데, 진행 중인 요청을 재는 http.server.requests.active(LongTaskTimer)에도 버킷 29줄이 따라 나왔습니다. 스프링 부트는 미터 이름을 점 단위로 하나씩 잘라 가며 맞는 설정을 찾기 때문이에요. http.server.requests.active에 대한 설정이 없으면 http.server.requests의 설정을 씁니다. 이름 앞부분이 같은 미터가 있다면 버킷 수가 그만큼 같이 늘어요.

⚠️ 주의: 대시보드의 quantile 패널이 비어 있다면
Micrometer 1.13 이상(스프링 부트 3.3 이상)으로 올린 뒤 {quantile="0.99"} 패널이 빈칸이 됐다면, 같은 타이머에 percentiles-histogram이 켜져 있는지 확인해요. 버킷을 켰다면 패널 쿼리를 histogram_quantile로 바꾸는 게 맞습니다. 버킷 없이 백분위만 쓰던 타이머는 그대로 나와요.

3. 세 대가 같은 양을 받을 때: 평균은 실제의 절반이 안 됐다

k6로 초당 60건을 3분 동안 세 대에 차례로 보냈습니다. 10,801건이 나갔고, 인스턴스마다 3,600건 안팎(app-a 3,601건)을 받았어요. 300ms를 넘은 요청은 392건(전체의 3.6%)이었고 전부 app-c에서 나왔습니다. 부하가 끝난 시각에 Prometheus에서 값을 읽었어요.

그림 2. 평균(초록)만 혼자 아래에 떨어져 있다
값 실제 p99 대비 인스턴스별 p99 app-a / app-b / app-c 59.8 / 59.8 / 485.5 ms p99 세 개의 평균 avg(...) 201.7 ms -55% p99 세 개의 최댓값 max(...) 485.5 ms +8% 버킷 합산 p99 histogram_quantile [3m] 447.8 ms -0.1% 실제 p99 k6, 10,801건 전체 448.3 ms

표의 버킷 합산 값은 부하 구간 3분 전체를 창으로 잡아 다시 계산한 것이고, 그래프 선은 1분 창이라 범례의 마지막 값(446ms)과 조금 달라요.

📖 용어: histogram_quantile
Prometheus 함수입니다. 버킷별 누적 건수를 받아서, 원하는 백분위가 어느 버킷에 떨어지는지 찾고 그 버킷 안을 직선으로 나눠 값을 추정해요(선형 보간: 버킷 안에 값이 고르게 퍼져 있다고 보고 비례로 위치를 정하는 계산). sum by (le)로 인스턴스의 버킷을 먼저 더해 넣으면 전체 요청의 백분위가 됩니다.

평균은 201.7ms로 실제 p99 448.3ms의 절반도 안 됐어요. 사용자 100명 중 1명이 450ms 가까이 기다리는데, 대시보드는 200ms라고 말한 셈입니다. 빠른 두 대의 60ms가 느린 한 대의 485ms를 끌어내린 결과예요. 세 숫자에는 각 인스턴스가 몇 건을 처리했는지도, 꼬리가 얼마나 두꺼운지도 남아 있지 않아서 이 계산을 바로잡을 방법이 없습니다.

최댓값 485.5ms는 실제보다 8% 높았어요. 이번처럼 느린 인스턴스가 3분의 1을 받는 경우에는 "제일 나쁜 인스턴스의 p99"가 그럴듯한 상한이 됩니다. 1편에서 말한 범위, 곧 "전체 p99는 가장 작은 p99와 가장 큰 p99 사이"가 그대로 성립했어요. 59.8ms와 485.5ms 사이에 448.3ms가 있습니다.

4. 느린 인스턴스가 5%만 받으면: 평균이 이번엔 세 배 높았다

평균이 늘 낮게 나온다면 "평균보다 조금 높게 보면 된다"로 넘어갈 수도 있어요. 그래서 트래픽 비중만 바꿔 한 번 더 돌렸습니다. 앱을 재시작해 클라이언트 백분위 창을 비운 뒤, 20건 중 1건만 app-c로 보냈어요.

docker compose restart app-a app-b app-c docker compose --profile load run --rm -e C_EVERY=20 load

10,801건 중 app-c가 541건을 받았고, 300ms를 넘은 요청은 54건(0.5%)이었습니다. 느린 요청이 1%보다 적으니 전체 p99는 빠른 쪽 분포 안에 있어야 해요.

그림 3. 이번엔 버킷 합산(파랑)이 바닥에 있고 평균이 붕 떠 있다
값 실제 p99 대비 인스턴스별 p99 app-a / app-b / app-c 59.8 / 59.8 / 502.3 ms p99 세 개의 평균 avg(...) 207.3 ms +236% p99 세 개의 최댓값 max(...) 502.3 ms +714% 버킷 합산 p99 histogram_quantile [3m] 61.4 ms -0.5% 실제 p99 k6, 10,801건 전체 61.7 ms

표는 이번에도 3분 창으로 다시 계산했고, 그래프 범례(61.3ms)는 1분 창 값이에요. 인스턴스별 p99는 첫 실행과 거의 같아요. 각 인스턴스 안의 분포는 바뀌지 않았으니까요. 그런데 실제 p99는 448ms에서 62ms로 내려갔고, 평균은 207ms로 오히려 조금 올랐습니다. p99의 평균은 트래픽 비중을 모르기 때문에, 틀리는 방향조차 정해져 있지 않습니다. 첫 실행에서는 절반 아래로, 두 번째에서는 세 배 위로 틀렸어요. 최댓값도 상한 노릇만 할 뿐, 두 번째 실행에서는 실제의 8배였습니다.

두 실행을 한 줄에 놓으면 이렇습니다.

그림 4. 인스턴스 안의 분포는 그대로고, 바뀐 건 트래픽 비중뿐이다
📖 용어: k6의 constant-arrival-rate
응답이 늦든 빠르든 정해진 초당 요청 수를 유지하는 k6 실행 방식입니다. 응답이 느려지면 가상 사용자를 더 꺼내 써요. 느린 인스턴스 때문에 요청 수가 줄어드는 일이 없어서, 두 실행의 총건수가 10,801건으로 같았습니다.

5. 버킷 합산도 추정이다: 이번엔 경계 운이 좋았다

버킷 합산 p99가 실제와 0.5ms 차이로 맞아서 "histogram_quantile은 정확하다"고 쓰고 싶어지는데, 숫자를 뜯어보면 그렇게 쓸 수 없어요. 첫 실행의 3분 버킷을 열어 봤습니다.

sum by (le) (increase(http_server_requests_seconds_bucket{uri="/work"}[3m])) le(초) 누적 건수 0.268435456 10399.1 0.357913941 10514.5 0.447392426 10684.1 0.536870911 10792.4 ← 전체 p99 순번 = 0.99 × 10792.4 = 10684.5 (0.447 경계까지 10684.1건) → 0.447 ~ 0.537 버킷에 0.4건만 들어간 지점 = 447.8ms

Micrometer가 미리 정한 버킷 경계 중 하나(0.447초)가 마침 실제 p99 바로 아래에 있었습니다. 99%째 요청이 경계에서 0.4건 떨어진 곳에 있으니 보간할 거리가 거의 없었던 거예요. 건수가 소수인 이유는 increase가 외삽을 하기 때문입니다. 창 양 끝에 샘플이 딱 맞지 않으면, 창 안에서 늘어난 속도대로 창 끝까지 늘었다고 보고 값을 늘려 잡아요.

같은 버킷으로 app-c 한 대의 p99를 구하면 사정이 달라요.

histogram_quantile(0.99, sum by (instance, le) (increase(...[3m]))) app-c 507.2 ms ← k6 가 잰 app-c 의 실제 p99 는 482.1ms, 최댓값은 501.4ms

버킷 추정이 실제로 관측된 최댓값보다 큰 값을 내놓았습니다. 0.447~0.537초 버킷 안에 값이 고르게 퍼져 있다고 가정하고 직선으로 나눴기 때문이에요. 실제 요청은 0.447~0.50초, 곧 그 버킷의 아래쪽 약 60%에만 있었습니다(버킷 중점은 492ms, 실제 최댓값은 501.4ms). 1편에서 말한 대로 histogram_quantile은 추정값이고, 오차의 상한은 그 백분위가 떨어진 버킷의 폭입니다. 이 구간에서는 90ms예요.

클라이언트 백분위와 k6 값도 그대로 비교할 수는 없어요. app-a의 p99를 k6는 61.5ms로, 앱은 59.8ms로 봤는데, 재는 범위가 다릅니다. lab.work는 앱 안에서 잠든 구간만 재고, k6는 HTTP 왕복 전체를 잽니다. 거기에 근사도 섞여 있어요. Micrometer는 클라이언트 백분위를 HdrHistogram으로 계산하는데, 정밀도 기본값이 유효숫자 1자리라 값이 계단 모양으로 떨어집니다. 두 실행에서 app-a와 app-b가 둘 다 정확히 59.768832ms를 보고한 건 그 계단 때문이에요. 계산 창도 최근 2분(3칸을 돌려 쓰는 원형 버퍼)이라 3분 전체와는 기준이 조금 달라요.

📖 용어: HdrHistogram
값의 범위를 로그 눈금으로 나눠 세는 자료구조입니다. 메모리를 고정해 두고 백분위를 빠르게 구하는 대신, 정밀도(유효숫자 자릿수)만큼만 값을 구분해요.
💡 실무에서는: 여러 인스턴스의 지연 백분위를 볼 때
• 전체 p99는 histogram_quantile(0.99, sum by (le) (rate(..._bucket[5m])))로 구해요. by (le)에 남길 라벨(서비스, 엔드포인트)만 더하고 instance는 빼요
• avg, max로 묶인 quantile 패널이 있으면 지워요. 이번 실험처럼 맞아 보이는 순간도 있지만, 트래픽 비중이 바뀌면 방향도 크기도 예측할 수 없어요
• 지켜야 할 지연 목표가 있으면 그 값에 버킷 경계를 직접 두어요(management.metrics.distribution.slo). 경계 위의 비율은 추정이 아니라 셈이에요
• 인스턴스 한 대만 보고 싶을 때만 by (instance, le)로 묶어요. 그 값도 버킷 폭만큼 틀릴 수 있어요

6. 개념 글과 다르게 나온 것: 기본 버킷 수

1편에는 타이머가 버킷 범위를 1밀리초에서 1분으로 좁혀 차원 하나당 73개를 쓴다고 적혀 있어요. 이번 출력에서 /work 하나의 버킷 줄은 1ms부터 30s까지 68개, 그리고 +Inf까지 69줄이었습니다. Micrometer 1.17.1 소스의 AbstractTimerBuilder도 기본 최솟값을 1ms, 최댓값을 30초로 두고 있었어요. 1.9.0 소스도 30초였습니다. 마지막 경계 30.0은 미리 만든 눈금에 있는 값이 아니라, 최댓값 30초를 경계로 하나 더 넣은 것이에요.

숫자는 조금 달라도 1편의 결론은 그대로예요. 버킷을 켜면 태그 조합 하나마다 시계열이 69개씩 생기고, 이번 앱에서는 이름 앞부분이 같은 LongTaskTimer까지 29개가 따라 붙었습니다. 버킷을 켤 타이머는 골라서 켜야 해요.

✍️ 오늘의 요약
인스턴스 세 대의 p99를 평균 내자 실제 p99 448ms가 202ms로, 트래픽 비중만 바꾼 두 번째 실행에서는 62ms가 207ms로 나왔다. p99의 평균은 각 인스턴스가 몇 건을 처리했는지 모르기 때문에, 얼마나 틀릴지는 물론 어느 쪽으로 틀릴지도 정해져 있지 않다. 버킷을 sum by (le)로 합친 histogram_quantile은 두 번 모두 실제와 0.5ms 이내였지만, 그건 경계가 가까웠던 덕이고 오차의 상한은 버킷 폭이다.

그리고 Micrometer 1.13 이후로는 같은 타이머에 버킷을 켜는 순간 앱이 계산한 백분위가 출력에서 빠진다. 합칠 수 있는 재료를 보내기로 했다면, 합칠 수 없는 완성품은 처음부터 대시보드에 올리지 않는 편이 낫다.
