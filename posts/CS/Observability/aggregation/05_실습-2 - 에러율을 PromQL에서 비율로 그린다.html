오후 피크 시간에 초당 5xx 건수 그래프가 평소의 7배로 올라갑니다. 30분 뒤 트래픽이 빠지자 그래프도 내려가요. 그날 저녁, 한산한 시간에 결제 모듈이 요청의 30%를 실패시키는데 건수 그래프는 오후 피크보다 조금 높을 뿐입니다. 어느 쪽이 진짜 장애였는지 건수 그래프만 보고는 말하기 어려워요.

2편에서 에러는 건수가 아니라 비율로 그려야 한다고 했습니다. 이번 글에서는 그 말을 대시보드로 확인하고, 비율을 PromQL로 쓸 때 실제로 부딪히는 문제를 다룹니다. 분자가 아직 없는 시계열일 때, 분모가 0일 때, 인스턴스별 비율을 평균 낼 때, 그리고 트래픽이 끊기는 마지막 몇 초에 무슨 값이 나오는지 직접 돌려서 봤어요.

🧭 이 글에서 확인할 것
• 트래픽이 출렁일 때 건수 그래프와 비율 그래프는 얼마나 다르게 보이는가?
• 에러가 한 번도 안 났을 때 비율 쿼리는 0을 돌려주는가?
• 트래픽이 0이 되면 비율은 무엇이 되고, 끊기기 직전에는 무엇이 찍히는가?
• 인스턴스별 비율을 평균 내면 왜 틀리는가?

1. 실습 환경: 9분 30초짜리 시나리오

스프링 부트 앱을 두 대 띄우고, k6로 요청 열 건 중 아홉 건은 app-a, 한 건은 app-b로 보냅니다. 앱은 모든 요청의 3%를 400(잘못된 요청)으로 돌려주고, 별도로 정한 비율만큼 500을 돌려줘요. 500 비율은 POST /admin/fail-rate로 실행 중에 바꿀 수 있게 했습니다. run.sh가 k6를 띄우고 시각에 맞춰 이 값을 바꿉니다.

그림 1. 파란 선이 초당 요청 수, 아래 띠가 그 시각의 500 비율이다

모든 요청의 3%는 시나리오 내내 400입니다. 4:30에 시작하는 장애 구간은 실패율 30%를 2분 동안 유지하고, 6:30부터 1분 30초 동안은 트래픽의 10%만 받는 app-b만 절반을 실패시켜요. 8:00에 k6가 끝나면 90초 동안 아무 요청도 보내지 않습니다.

쓴 버전은 아래와 같아요. Prometheus는 5초마다 긁고, rate 창은 2편의 권장대로 스크레이프 간격의 네 배인 20초로 잡았습니다.

Spring Boot 4.1.1 (Micrometer 1.17.1) Prometheus 3.15.0 (scrape 5s, rate 창 20s) Grafana 13.2.3 k6 2.3.0 실행 환경 Docker Desktop, Apple M5 Pro

실습 코드는 GitHub 저장소의 labs/observability/agg-02-error-ratio에 있습니다.

git clone https://github.com/DDINGJOO/Platform-study.git cd Platform-study/labs/observability/agg-02-error-ratio docker compose up -d --build ./run.sh # 9분 30초. 실패율을 바꾸는 시각이 화면에 찍힌다 # Grafana: http://localhost:23100 → 대시보드 「실습-2 에러 건수와 에러 비중」

k6는 8분 동안 17,850건을 보냈습니다. 그중 400이 573건, 500이 727건이었어요. Prometheus에 쌓인 카운터를 인스턴스와 결과별로 더한 값도 같았습니다.

2. 건수로 그리면 피크가 장애처럼 보인다

스프링 부트는 http.server.requests 타이머에 outcome 태그를 자동으로 붙여요. 값은 SUCCESS, CLIENT_ERROR, SERVER_ERROR 같은 결과 묶음입니다. 2편의 쿼리를 그대로 썼어요.

# 초당 5xx 건수 (2편의 용어로 '에러율') sum(rate(http_server_requests_seconds_count{uri="/orders", outcome="SERVER_ERROR"}[20s])) # 5xx 비중 (같은 분자에 분모만 추가) sum(rate(http_server_requests_seconds_count{uri="/orders", outcome="SERVER_ERROR"}[20s])) / sum(rate(http_server_requests_seconds_count{uri="/orders"}[20s]))
📖 용어: rate()
카운터가 창(여기서는 20초) 안에서 늘어난 양을 초당 값으로 바꿔 주는 PromQL 함수입니다. 창 양 끝에 샘플이 딱 맞지 않으면 끝까지 늘려서 추정해요. 그래서 건수가 정수가 아닌 값으로 나오기도 합니다.
그림 2. 가운데 그래프에서는 산이 둘이고, 아래 그래프에서는 하나다

구간마다 한 시점씩 값을 뽑았습니다.

시각 상황 요청/초 5xx/초 5xx 비중 1:50 평소 (500 2%) 20.0 0.27 1.3% 3:30 피크 (500 2%) 100.1 1.93 1.9% 5:30 장애 (500 30%) 10.0 3.27 32.7%

피크에서 5xx 건수는 평소의 7배가 됐어요. 서비스의 실패 확률은 그대로였는데요. 건수 그래프만 봤다면 2:30 무렵 "초당 1건 이상"짜리 경고가 울렸을 겁니다. 장애 구간의 5xx 건수는 피크의 1.7배에 불과해서, 그래프 모양만으로는 두 산이 같은 종류의 사건으로 보여요. 비중 그래프에서는 피크가 2% 근처에 머물고 장애만 30%대로 솟았습니다. 분모를 넣으면 트래픽이 만든 산은 사라지고, 서비스 상태가 만든 산만 남습니다.

📖 용어: outcome 태그
스프링 부트가 HTTP 응답 코드를 1xx~5xx 묶음(INFORMATIONAL, SUCCESS, REDIRECTION, CLIENT_ERROR, SERVER_ERROR)과 UNKNOWN으로 나눠 붙이는 태그입니다. 상태 코드를 정규식으로 고르는 대신 이 값 하나로 서버 잘못만 셀 수 있어요.

2편이 경고한 status!~"2.."도 같은 시점에 재 봤어요. 400까지 에러로 세니 평소 구간이 4.7%, 피크가 5.1%로 나왔습니다. 서버는 2%만 실패하는데 늘 3%포인트가 얹혀 있는 셈이에요. 400이 늘어나는 날(잘못된 클라이언트 배포, 비밀번호를 거듭 틀리는 사용자)에는 이 선만 올라갑니다.

그림 3. 노란 선은 처음부터 끝까지 400 몫만큼 떠 있다

3. 에러가 한 번도 안 났을 때: 0이 아니라 빈 결과

그림 2의 5xx 비중 선과 그림 3의 초록 outcome="SERVER_ERROR" 선은 첫 1분 동안 아무것도 그려지지 않았어요. 400까지 세는 노란 선만 처음부터 있습니다. 그 구간에는 500이 한 번도 없었습니다. 비중이 0%라고 그려질 거라 예상했는데 아예 빈칸이었어요.

Micrometer는 태그 조합이 처음 기록될 때 시계열을 만듭니다. 500이 한 번도 나지 않았으면 outcome="SERVER_ERROR"인 시계열 자체가 없어요. 없는 시계열의 sum(rate(...))은 0이 아니라 빈 결과이고, 빈 결과를 무엇으로 나눠도 빈 결과입니다. 그림 2의 가운데 패널에서 5xx 건수 선이 1:00 직후부터 시작하는 것도 같은 이유예요.

이건 대시보드보다 경고 규칙에서 더 위험해요. "5xx 비중이 30분 동안 0.1% 미만이면 정상" 같은 조건이나 다른 지표와 and로 묶은 조건은 빈 결과 앞에서 아무 일도 하지 않습니다. 분자에 or vector(0)을 붙이면 빈 결과 대신 0을 씁니다.

(sum(rate(..._count{uri="/orders", outcome="SERVER_ERROR"}[20s])) or vector(0)) / sum(rate(..._count{uri="/orders"}[20s]))
📖 용어: vector(0)
라벨 없이 값이 0인 시계열 하나를 만드는 PromQL 식입니다. A or vector(0)은 A가 비어 있을 때만 0을 대신 내놓아요. 분자를 sum으로 라벨 없이 합쳐 둬야 분모와 짝이 맞습니다.

4. 트래픽이 0이면 NaN, 끊기는 순간엔 50%

8:00에 k6가 끝난 뒤 같은 식을 다시 봤습니다. 이번에는 분자와 분모 시계열이 모두 있지만 둘 다 늘지 않아요. 0을 0으로 나누니 PromQL은 NaN을 돌려줬고, Grafana는 그 구간을 빈칸으로 그렸습니다.

시각 식 결과 0:40 A. 기본 식 (빈 결과) 0:40 B. 분자 or vector(0) 0 8:40 A. 기본 식 NaN 8:40 B. 분자 or vector(0) NaN 8:40 C. B / (분모 > 0) (빈 결과)
📖 용어: NaN (Not a Number)
0을 0으로 나눈 것처럼 값을 정할 수 없을 때 나오는 부동소수점 값입니다. 어떤 수와 크기를 비교해도 참이 되지 않아서, 비율 > 0.05 같은 조건이 참이 되지 않고 경고도 울리지 않아요.

C처럼 분모에 > 0 필터를 걸면 분모가 0인 시점이 결과에서 빠져서 NaN 대신 빈 결과가 됩니다. NaN은 크기 비교(>, <)에서 늘 거짓이라 경고 규칙에서 조용히 넘어가기 쉬운데, 빈 결과는 absent()로 따로 잡을 수 있어요. 어느 쪽이든 "트래픽이 없다"는 별도로 경고해야 할 상태입니다.

여기서 예상하지 못한 값이 하나 나왔어요. 비중 그래프의 범례 Max가 50%였습니다. 장애 구간 최고치는 38.7%였는데요. 그림 2의 맨 아래 패널 오른쪽 끝을 보면 트래픽이 끊기는 순간 선이 위로 치솟고 끝납니다. 1초 간격으로 다시 조회했어요.

k6 시작 후 5xx 비중 493초 9.3% 494~497초 3.9% 498초 50.0% ← 이 한 칸 499초~ NaN 498초 시점 20초 창 안의 증가량 app-a 모든 결과 0 (마지막 증가가 창 밖으로 나갔다) app-b SUCCESS +2, SERVER_ERROR +2 분모 = 0.27 요청/초

원인은 두 타깃의 스크레이프 시각이 달랐던 데 있어요. Prometheus는 타깃마다 긁는 시각을 흩어 둡니다. 이번에는 app-a가 매 5초의 x.2초에, app-b가 x.0초에 긁혔어요. 498초에 본 20초 창은 478초 초과 498초 이하입니다. Prometheus 3부터 범위 창은 왼쪽 끝을 포함하지 않아요. app-a의 카운터는 477.2초와 482.2초 샘플 사이에서 마지막으로 늘었는데, 477.2초 샘플이 창 밖이라 창 안의 샘플은 전부 같은 값이었어요. app-b는 479.0초와 484.0초 사이에서 마지막으로 늘었고 두 샘플이 모두 창 안에 있었습니다. 그래서 창 안에는 app-b의 마지막 스크레이프 구간(479.0~484.0초)에 들어온 요청 4건만 남았어요. 그때 app-b는 실패율 50% 구간이 막 끝난 참이었어요. 4건 중 2건이 500이라 전체 비중이 50%로 찍혔습니다. 같은 시나리오를 처음 돌렸을 때(트래픽 0 구간을 k6 안에서 주던 판)는 이 칸이 83%(6건 중 5건)였어요.

그림 4. 타깃마다 스크레이프 시각이 달라서, 끝나는 순간 창 안에 한 대만 남는다

2편은 처리량이 아주 낮은 엔드포인트에서는 비중이 크게 출렁인다고 했어요. 그게 엔드포인트 단위가 아니라 시간 단위로도 일어난다는 걸 이번에 봤습니다. 트래픽이 줄어드는 몇 초 동안은 어떤 서비스든 저처리량 엔드포인트가 돼요. 그래서 분모에 > 0 대신 최소 트래픽을 걸어 봤습니다.

D. (분자 or vector(0)) / (분모 >= 1) # 초당 1건 미만이면 비율을 내지 않는다
그림 5. 최소 트래픽을 건 D만 마지막 한 칸을 그리지 않았다

D는 498초 시점의 분모 0.27 요청/초를 걸러서 그 칸을 그리지 않았고, 범례 Max도 장애 구간 최고치인 38.7%가 됐어요. 기준값 1은 이 실습의 트래픽(초당 10~100건)에 맞춰 고른 값입니다. 서비스마다 "이 정도 건수면 비율을 믿을 수 있다"는 값이 달라요.

⚠️ 주의: 범례의 Max는 이런 한 칸이 정한다
대시보드 범례에 Max를 띄워 두고 "지난 1시간 최고 에러 비중"으로 읽는 경우가 많아요. 이번처럼 트래픽이 끊기거나 배포로 인스턴스가 빠지는 순간의 한 칸이 그 값을 차지할 수 있어요. 경고 규칙도 같아서, 비중 조건에는 for:로 지속 시간을 걸고 분모에 최소 트래픽 조건을 같이 거는 편이 안전해요.

5. 인스턴스별 비중을 평균 내면

마지막은 1편의 "평균의 평균" 문제를 비율로 다시 확인한 거예요. 6:30부터 app-b만 요청의 절반을 실패시켰습니다. app-b는 트래픽의 10%만 받아요. 인스턴스별 비중을 먼저 구하고 평균 낸 값과, 전체 5xx를 전체 요청으로 나눈 값을 같이 그렸습니다.

# 인스턴스별 비중의 평균 avg( sum by (instance) (rate(..._count{outcome="SERVER_ERROR"}[20s])) / sum by (instance) (rate(..._count[20s])) ) # 전체 5xx ÷ 전체 요청 sum(rate(..._count{outcome="SERVER_ERROR"}[20s])) / sum(rate(..._count[20s]))
그림 6. 초록 평균선은 아무 인스턴스의 값도, 전체의 값도 아니다

7:30 시점에 전체 비중은 7.0%였고, 인스턴스별 비중의 평균은 29.1%였어요. 평균은 초당 2건을 받는 app-b와 초당 18건을 받는 app-a에 같은 한 표씩을 줬습니다. 사용자가 겪은 실패율은 7%예요. 그림 6에서 app-b 선이 다른 구간에서도 유난히 출렁이는 것도 같은 이유입니다. 초당 2건이면 20초 창에 40건뿐이라 한두 건에 비중이 몇 %포인트씩 움직여요.

💡 실무에서는: 에러 비중 쿼리를 쓸 때
• 분자와 분모를 각각 sum으로 먼저 합치고 마지막에 나눠요. avg로 비율을 합치지 않아요
• 분자에는 or vector(0)을 붙여요. 아직 에러가 없는 새 서비스도 0으로 그려져요
• 분모에는 최소 트래픽 조건(>= 1 같은)을 걸고, 트래픽이 없는 상태는 따로 경고해요
• 서버 잘못만 세려면 outcome="SERVER_ERROR"를 써요. 4xx 비중은 다른 패널, 다른 임계값으로 봐요
• 인스턴스 한 대가 문제인지 보고 싶으면 by (instance) 비율을 따로 그리되, 처리량이 적은 인스턴스는 출렁인다는 걸 감안해요

같은 카운터를 건수로 그리면 실패 확률이 그대로인 피크가 7배짜리 산이 되고, 비율로 그리면 그 산은 사라지고 32.7%짜리 장애만 남았다. 다만 비율 쿼리는 경계에서 약하다. 에러가 한 번도 없으면 빈 결과, 트래픽이 0이면 NaN이 나오고, 트래픽이 끊기는 순간에는 스크레이프 시각이 다른 인스턴스 한 대의 마지막 4건이 50%로 찍혔다. 인스턴스별 비율을 평균 내면 7%가 29%가 됐다.

분자는 or vector(0), 분모는 최소 트래픽 조건, 합치기는 sum으로 먼저 하고 나눗셈은 마지막에. 비율은 분모가 믿을 만할 때만 비율이다.
