📐 집계와 분포, 실습-3
1편. 집계의 함정
2편. 에러는 건수가 아니라 비율로 그린다
3편. 히스토그램 위의 점을 클릭하면
실습-1. 인스턴스 세 대의 p99를 평균 내면 틀린다
실습-2. 에러율을 PromQL에서 비율로 그린다
실습-3. 히스토그램 점을 눌러 트레이스로 넘어간다 ← 지금 이 글

부하를 3분 걸고 대시보드를 열었더니 p99가 1.3초였습니다. 코드에 1~2초 걸리는 경로가 있긴 해요. 요청의 1%만 그쪽으로 가게 만들어 뒀으니 p99가 그 근처에 있는 건 이상하지 않았습니다. 그대로 넘어갈 뻔했는데, 그래프 위에 찍힌 점 하나를 눌러 보고 나서야 그 1.3초가 코드 탓이 아니었다는 걸 알았어요.

3편에서 히스토그램 버킷에 trace ID를 하나씩 매달아 두는 exemplar를 설명했습니다. 이번 글은 그걸 실제로 잇습니다. 앱이 exemplar를 달고, Prometheus가 저장하고, Grafana가 점으로 그리고, 점을 누르면 Tempo의 트레이스가 열리기까지 네 단계가 전부 맞아야 해요. 단계를 하나씩 빼 보면 무엇이 보이는지도 확인했습니다. 화면과 숫자는 전부 이번에 돌린 결과예요.

🧭 이 글에서 확인할 것
• exemplar가 점으로 뜨기까지 무엇이 맞물려야 하는가?
• 점 하나를 눌러서 히스토그램이 말해 주지 않는 무엇을 알게 됐는가?
• 단계 하나를 빼면 어떤 오류가 나는가? (답: 확인한 세 경우 모두 오류가 없었다)
• 버킷마다 exemplar는 얼마나 자주 바뀌는가?

1. 실습 환경: 단계 네 개

스프링 부트 앱 하나가 /work 요청을 받습니다. 요청의 89%는 20~60ms(fast), 10%는 300~500ms(slow), 1%는 1~2초(very_slow) 동안 잠들어요. 잠드는 구간은 lab.work라는 Observation(Micrometer가 지표와 스팬을 한 번에 만드는 측정 단위)으로 감싸서, 트레이스에 자식 스팬이 생기고 어느 경로였는지가 kind 속성으로 남게 했습니다.

그림 1. 지표와 트레이스는 따로 가고, trace_id 하나가 둘을 잇는다
📖 용어: exemplar
히스토그램 버킷 한 줄 옆에 붙이는 견본 하나입니다. 그 버킷에 들어간 요청 중 하나의 trace ID와 실제 측정값, 시각이 들어 있어요. 집계된 숫자에서 개별 요청 하나로 건너갈 때 씁니다.

쓴 버전은 아래와 같아요. 이전 실습들은 OTel 자바 에이전트로 트레이스를 만들었지만, 이번에는 에이전트를 쓰지 않았습니다. exemplar를 다는 쪽이 Micrometer라서, Micrometer가 지금 요청의 trace ID를 알 수 있어야 하거든요. 스프링 부트는 Micrometer Tracing이 클래스패스에 있을 때만 그 연결을 자동으로 만듭니다.

📖 용어: Micrometer Tracing
스프링 부트 3부터 들어온 트레이싱 파사드입니다. 요청마다 스팬을 만들고 trace ID를 들고 다니며, 실제 내보내기는 OTel이나 Brave 같은 구현체에 맡겨요. 이번 실습은 OTel 브리지로 Tempo에 OTLP로 보냈습니다.

실습 코드는 GitHub 저장소의 labs/observability/agg-03-exemplar에 있습니다.

git clone https://github.com/DDINGJOO/Platform-study.git cd Platform-study/labs/observability/agg-03-exemplar docker compose up -d --build docker compose --profile load run --rm load # 초당 20건, 3분 # Grafana: http://localhost:23300 → 대시보드 「실습-3 exemplar」

2. 앱이 exemplar를 달게 하기

의존성은 스타터 세 개와 Prometheus 레지스트리입니다. spring-boot-starter-opentelemetry가 Micrometer Tracing, OTel 브리지, OTLP 내보내기를 한 번에 가져와요.

implementation 'org.springframework.boot:spring-boot-starter-webmvc' implementation 'org.springframework.boot:spring-boot-starter-actuator' implementation 'org.springframework.boot:spring-boot-starter-opentelemetry' runtimeOnly 'io.micrometer:micrometer-registry-prometheus'

설정에서 세 가지를 바꿨어요.

management: metrics: distribution: percentiles-histogram: http.server.requests: true # 버킷이 있어야 exemplar 를 매달 곳이 생긴다 tracing: sampling: probability: 1.0 # 기본값 0.1 opentelemetry: tracing: export: otlp: endpoint: http://tempo:4318/v1/traces # 이 값이 있어야 OTLP 내보내기가 켜진다 otlp: metrics: export: enabled: false # 스타터에 딸려 온 OTLP 지표 내보내기는 끈다

마지막 줄은 돌려 보고 넣었어요. OpenTelemetry 스타터에는 지표를 OTLP로 미는 레지스트리도 딸려 옵니다. 지표를 Prometheus로만 볼 거라면 꺼 두는 게 맞아요.

앱을 띄우고 /actuator/prometheus를 두 가지 형식으로 받아 봤습니다. 같은 엔드포인트인데 요청 헤더만 다릅니다.

curl -H 'Accept: application/openmetrics-text; version=1.0.0' localhost:23381/actuator/prometheus http_server_requests_seconds_bucket{...,uri="/work",le="0.050331646"} 5 # {span_id="88cbd98c31b35c70",trace_id="cddfafb7d7ecdb92bbfdfd287e0d6da7"} 0.045385542 1791615698.018 ↑ 여기부터 exemplar: trace_id, 실제 측정값(초), 기록 시각 curl localhost:23381/actuator/prometheus | grep 'uri="/work"' | grep -c ' # ' 0 ← 예전 텍스트 형식(0.0.4)에는 exemplar 가 한 줄도 없다
📖 용어: OpenMetrics
Prometheus 텍스트 형식을 다듬어 표준으로 만든 노출 형식입니다. 버킷 줄 뒤에 #를 찍고 exemplar를 붙이는 문법이 여기에만 있어요. 예전 텍스트 형식 0.0.4로 받으면 같은 앱이라도 exemplar가 빠집니다.

값 0.045초는 그 줄의 버킷 경계 0.050초 안에 들어 있어요. 3편에서 말한 규칙 그대로입니다. Prometheus 3.15는 따로 설정하지 않아도 OpenMetrics를 먼저 요청했어요. 실행 중인 설정을 /api/v1/status/config로 보면 협상 순서가 OpenMetricsText1.0.0부터 시작합니다.

3. 점을 눌러 본다

대시보드에는 패널을 두 개 만들었어요. 위는 histogram_quantile로 그린 p99와 p50이고, 아래는 버킷별 건수를 색으로 그린 히트맵입니다. 두 패널 모두 쿼리에 exemplar: true를 켰어요. 다른 컨테이너가 조용할 때 돌린 3분짜리 실행입니다.

그림 2. 히트맵의 세 띠가 코드의 세 경로다. 점은 각 띠에서 뽑힌 견본이다

히트맵에 띠가 세 줄로 나왔어요. 40ms 근처 진한 띠가 fast, 450ms 근처가 slow, 1.4초 근처의 옅은 띠가 very_slow입니다. 위 패널의 p99는 530ms와 1.25초 사이를 오갔어요. 1분 창 안에 very_slow 요청이 1%를 넘게 들어오면 p99가 위 띠로 올라가고, 1%보다 적으면 slow 띠의 끝에 머뭅니다. 분포 경계에 걸린 백분위는 이렇게 계단처럼 뛰어요.

점에 마우스를 올리면 그 exemplar의 라벨이 뜨고, 맨 아래에 Query with Tempo 링크가 붙습니다. 이 링크는 Prometheus 데이터 소스 설정의 exemplarTraceIdDestinations가 만들어요. "trace_id 라벨 값을 Tempo 데이터 소스로 넘겨라"라는 한 줄입니다.

jsonData: exemplarTraceIdDestinations: - name: trace_id # exemplar 라벨 중 trace ID 가 든 이름 datasourceUid: tempo # 이 데이터 소스에서 연다

4. 첫 실행에서 점이 알려 준 것

사실 그림 2는 두 번째 실행이에요. 첫 실행에서는 p99가 1.32초였고, 위쪽에 2초를 넘는 점이 두 개 있었습니다. 코드상 가장 느린 경로가 2초 미만인데요. 그중 하나에 마우스를 올렸습니다.

그림 3. 2.5초 버킷에 들어간 요청 하나. 히스토그램은 여기까지만 안다

히스토그램이 아는 건 "2.15~2.51초 버킷에 요청이 있었다"까지예요. 링크를 누르자 그 요청의 트레이스가 열렸습니다.

그림 4. kind가 slow인데 2.08초. slow 경로는 500ms를 넘을 수 없다

kind가 slow였어요. 코드에서 slow는 300~500ms 사이로만 잠드는데, 이 스팬은 2.08초였습니다. 가장 위에 있던 3.39초짜리 점도 열어 봤어요.

trace bc4afcf6... http get /work 3403.9ms lab.work 377.7ms kind=fast ← 20~60ms 여야 하는 경로 (lab.work 가 끝난 뒤 응답까지 약 3.0초)

빠른 경로가 378ms 걸렸고, 그 뒤로 3초 동안 응답이 나가지 않았어요. 코드 경로가 아니라 실행 환경을 의심할 근거입니다. TraceQL로 첫 실행 전체를 셌습니다.

첫 실행 조용할 때 다시 { name = "lab.work" } 3,507 3,601 { name = "lab.work" && span.kind = "fast" && duration > 100ms } 457 0 { name = "lab.work" && span.kind = "slow" && duration > 600ms } 19 0 histogram_quantile(0.99, ...) 실행 구간 전체 1.32s 0.53s

첫 실행 열의 3,507은 목표 3,601건보다 적어요. k6가 CPU 경합 속에서 45건을 못 보냈고(dropped_iterations), k6 컨테이너가 늦게 뜨면서 생긴 빈 구간을 피해 집계 시작을 30초 뒤로 잡았는데 그 경계에서 앞부분 2초 남짓이 잘린 것으로 보여요.

첫 실행에서는 100ms를 넘은 fast 요청이 전체 요청의 13%였어요. fast가 요청의 89%이니 fast만 놓고 보면 약 15%입니다. 그 시간대에 같은 Docker Desktop VM에서는 다른 실습 컨테이너들과 kind(Docker 안에 띄운 쿠버네티스) 클러스터가 같이 돌고 있었어요. Prometheus의 스크레이프 한 번이 3.6초까지 걸렸고, 앱 기동에 103.85초가 걸렸습니다. 조용해진 뒤에는 같은 이미지가 1.1초 만에 떴어요. 잠든 시간이 늘어난 것과 스레드가 CPU를 기다린 것이 원인으로 가장 그럴듯하지만, 어느 쪽이 얼마인지 스케줄러 수준까지 확인하지는 않았습니다. 확실한 건 하나예요. 히스토그램만 봤다면 "1~2초 경로가 늘었다"고 읽었을 겁니다. 점 하나를 눌러 본 덕에 느린 요청이 느린 경로가 아니었다는 걸 알았어요.

5. 단계를 하나씩 빼 본다

네 단계 중 하나가 빠지면 어떻게 되는지 확인했습니다. 본 Prometheus 옆에 Prometheus 두 대를 더 붙여 같은 앱을 동시에 긁게 했어요. 한 대는 --enable-feature=exemplar-storage 없이, 한 대는 플래그는 켜되 텍스트 형식으로만 긁게 했습니다.

docker compose -f compose.yaml -f experiments/compose.yaml up -d prom-noflag prom-text docker compose --profile load run --rm -e DURATION=1m load # 본 Prometheus 23390, 플래그 없음 23391, 텍스트 형식 23392 # experiments/prometheus-text.yml global: scrape_protocols: [PrometheusText0.0.4]

1분 부하(1,201건)가 끝난 직후, k6 시작부터 끝까지를 구간으로 세 Prometheus의 exemplar를 셌어요.

for p in 23390 23391 23392; do curl -s -G localhost:$p/api/v1/query_exemplars \ --data-urlencode 'query=http_server_requests_seconds_bucket{uri="/work"}' \ --data-urlencode start=$(($(date +%s)-90)) --data-urlencode end=$(date +%s); echo; done
exemplar 응답 본 Prometheus (플래그 + OpenMetrics) 72 success 플래그 없음 0 success 텍스트 형식(0.0.4)으로만 긁음 0 success

두 경우 모두 오류가 없었습니다. 타깃은 up이고, 버킷 지표도 정상으로 쌓였고, exemplar API는 성공 응답에 빈 목록을 돌려줬어요. Grafana 패널에서는 점이 안 뜰 뿐입니다. 플래그를 빠뜨렸는지, 형식 협상이 텍스트로 떨어졌는지는 화면만 봐서는 구분할 수 없어요.

⚠️ 주의: 점이 안 보이면 앞 단계부터 확인한다
• 앱: curl -H 'Accept: application/openmetrics-text; version=1.0.0'로 받아서 버킷 줄 뒤에 # {trace_id=...}가 있는지 봐요
• Prometheus: 실행 인자에 exemplar-storage가 있는지, scrape_protocols를 텍스트 형식으로 고정하지 않았는지 봐요
• Grafana에서 점이 안 보이면: 패널 쿼리의 Exemplars 스위치가 켜져 있는지 봐요
• 점은 보이는데 Tempo 링크가 없으면: 데이터 소스의 exemplarTraceIdDestinations를 봐요(이 경우는 직접 실험하지 않았고 Grafana 문서의 설정 설명을 따랐어요)

세 번째로 샘플링을 낮췄어요. 스프링 부트의 트레이스 샘플링 기본값은 10%이고, exemplar는 샘플링된 요청에만 붙습니다(management.tracing.exemplars.include 기본값이 샘플링된 트레이스만). 같은 1분 부하를 10%로 다시 줬습니다.

TRACING_PROBABILITY=0.1 docker compose up -d app docker compose --profile load run --rm -e DURATION=1m load Tempo 트레이스 exemplar exemplar 가 달린 버킷 샘플링 100% 1,201 79 14 ← 위 표와 같은 실행 샘플링 10% 124 38 10

Tempo 트레이스 수는 TraceQL { name = "http get /work" }로 /work 요청만 센 값이에요. 샘플링 100%에서는 Prometheus의 스크레이프 요청도 트레이스로 남기 때문에 걸러서 셌습니다. 100% 줄의 exemplar 79개는 위 표의 72개와 같은 실행인데, 셀 구간을 k6가 끝난 뒤 6초까지 넓혀 마지막 스크레이프까지 넣은 값이에요.

📖 용어: 샘플링 확률 (sampling probability)
요청이 시작될 때 트레이스를 남길지 정하는 확률입니다. 3편의 head 샘플링이에요. 남기지 않기로 한 요청도 지표에는 그대로 집계되지만, 그 요청의 trace ID는 어디에도 저장되지 않아요.

트레이스는 10분의 1로 줄었는데 exemplar는 절반으로만 줄었어요. 10%로 낮춰도 버킷마다 견본을 채울 만큼은 샘플링된 요청이 들어오기 때문입니다. 대신 드문 버킷이 비었어요. 그리고 10%일 때 저장된 exemplar 38개의 trace ID를 Tempo에 하나씩 조회했더니 38개 모두 있었습니다. 샘플링된 요청에만 exemplar를 다니까, 샘플링 때문에 트레이스 없는 점이 생기지는 않아요. 다만 Tempo 보존 기간이 지났거나 스팬 내보내기가 실패했다면 링크를 눌러도 트레이스가 비어 있을 수 있어요. 참고로 스프링 부트는 management.tracing.exemplars.include=all(샘플링 여부와 상관없이 전부 달기)을 Prometheus와 함께 쓰면 "Prometheus doesn't support including 'all' traces as exemplars"라는 설정 오류로 기동을 막아요.

6. 버킷마다 하나, 7초에 한 번

3편에는 버킷마다 최근 요청 하나를 견본으로 둔다고 적혀 있어요. 조용한 실행에서 3분 동안 3,601건을 보냈고, Prometheus에 저장된 버킷 줄 exemplar는 228개였습니다. 다만 이 숫자만으로는 "최근 것 하나"인지 다른 규칙인지 가릴 수 없어요. Prometheus는 5초마다 긁으니 어느 규칙이든 비슷한 수가 나올 수 있습니다. 그래서 선택 규칙은 소스에서 확인했어요.

Micrometer는 exemplar 선택을 Prometheus 자바 클라이언트의 ExemplarSampler에 맡깁니다. 규칙은 세 겹이에요.

1. 버킷마다 칸이 하나다. 한 번 채운 칸은 최소 7초 동안 바꾸지 않는다 (DEFAULT_MIN_RETENTION_PERIOD_SECONDS = 7) 2. 시계열 하나(타이머의 태그 조합 하나)에 문이 하나 있다. 요청 하나를 후보로 받으면 문을 닫고, 90ms 뒤에 다시 연다(DEFAULT_SAMPLE_INTERVAL_MILLISECONDS = 90). 모든 칸이 차 있으면 가장 오래된 견본이 7초를 넘길 때까지 닫아 둔다 (rateLimitedObserve, durationUntilNextExemplarExpires) 3. 70초가 넘은 견본은 내보낼 때 뺀다 (DEFAULT_MAX_RETENTION_PERIOD_SECONDS = 70)

2번 때문에 문이 닫혀 있는 동안 들어온 요청은 후보조차 되지 않아요. 초당 20건이면 요청 간격이 평균 50ms라 절반 남짓은 90ms 문에 걸러집니다. 그래서 견본은 "그 버킷의 가장 최근 요청"도, "7초 지난 뒤 처음 온 요청"도 정확히는 아니에요. 문이 열려 있을 때 들어왔고, 그 버킷 칸이 7초 넘게 묵어 있었던 요청이 됩니다. 요청이 몰리는 버킷일수록 견본 하나가 대표하는 요청 수가 많아져요.

Prometheus 쪽 저장소도 확인했어요. 실행 중인 설정에서 storage.exemplars.max_exemplars가 100,000이었고, 공식 문서는 이 저장소를 모든 시계열이 같이 쓰는 고정 크기 원형 버퍼라고 설명합니다. 오래된 exemplar부터 밀려나니, 알람을 받고 바로 따라가야 한다는 3편의 말이 그대로예요.

돌려 보며 하나 더 보였어요. exemplar는 버킷 줄뿐 아니라 _count 줄에도 붙었고, 샘플링 100%에서는 Prometheus가 5초마다 긁는 /actuator/prometheus 요청까지 트레이스로 남았습니다. Tempo 검색 결과가 스크레이프 트레이스로 채워지니 운영에서는 헬스체크와 함께 걸러 두는 편이 좋아요.

💡 실무에서는: exemplar를 켤 때
• exemplar를 넣으려고 샘플링을 100%로 올릴 필요는 없어요. 이번 실험에서 10%로도 견본은 절반이 남았고, 남은 견본은 전부 트레이스가 있었어요
• 드문 꼬리 버킷의 견본은 샘플링에 같이 깎여요. 느린 요청을 꼭 잡아야 하면 tail 샘플링이나 느린 요청 우대 규칙을 같이 봐요
• 링크를 연 트레이스에서 "어느 경로였는지"를 바로 알 수 있게, 코드 경로가 갈리는 곳에는 스팬 속성을 달아 둬요. 이번엔 kind 하나가 원인을 코드 밖으로 돌려놨어요
• 원형 버퍼라서 오래된 견본은 사라져요. 과거 장애를 되짚을 때는 exemplar 대신 Tempo에서 시간과 조건으로 검색해요
✍️ 오늘의 요약
앱이 버킷에 trace_id를 달고, Prometheus가 OpenMetrics로 긁어 저장하고, Grafana가 그 라벨을 Tempo 링크로 바꿔야 히스토그램의 점이 트레이스로 이어졌다. 저장 플래그를 빼거나 텍스트 형식으로 긁으면 exemplar가 0개가 되는데, 어디서도 오류가 나지 않았다. 샘플링을 10%로 낮추자 트레이스는 10분의 1이 됐지만 exemplar는 절반이 남았고, 남은 견본은 전부 트레이스가 있었다.

첫 실행에서 2.23초짜리 점 하나를 눌렀더니 300~500ms여야 할 slow 경로가 2.08초 걸려 있었다. 히스토그램은 느린 요청이 몇 건인지를 알려 주고, 점 하나는 그 요청이 왜 느렸는지를 묻게 해 준다.
