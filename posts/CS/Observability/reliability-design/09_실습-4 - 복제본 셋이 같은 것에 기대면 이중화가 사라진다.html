실습-3에서 90%짜리 복제본 셋은 99.9%를 냈습니다. 다만 그 환경은 병렬식이 맞도록 만든 것이었어요. 복제본의 실패는 각자의 난수로 정해서 서로 독립이었고, 앞단은 실패 응답을 받자마자 다른 복제본을 불렀습니다. 5편은 이 두 가정, 독립 고장과 즉시 전환이 운영에서는 깨진다고 했어요. 이번 글은 HAProxy와 공유 Redis를 붙여 두 가정을 하나씩 깨 보고, 숫자가 얼마나 바뀌는지 잽니다.

🧭 이 글에서 확인할 것
• 복제본 고장 중 공통 원인 비율 β를 0, 10%, 50%, 100%로 바꾸면 가용성은 얼마인가?
• 액티브가 죽은 뒤 백업으로 넘어가기까지 inter와 fall 조합별로 몇 초, 몇 건이 실패하나?
• 포트는 열려 있고 앱만 죽은 서버를 TCP 검사, HTTP 검사, observe는 각각 얼마나 놓치나?

1. 실습 환경: listen 하나가 실험 하나

복제본은 표준 라이브러리만 쓰는 파이썬 HTTP 서버예요. /work 요청마다 공유 Redis에서 설정 키 mode를 읽고, 값이 bad면 500을 돌려줍니다. 공유 설정 하나가 복제본 전부를 같이 망가뜨리는 공통 원인이에요. 복제본 하나만 고장 내는 건 각자의 POST /admin/state로 합니다.

상태 /work /health 뜻 up 200 (Redis 확인) 200 정상 down 503 503 프로세스와 포트는 살아 있고 앱만 죽음 gray 500 200 헬스 체크로는 안 보이는 고장 hang 30초 동안 응답 없음 30초 동안 응답 없음

HAProxy에는 실험마다 listen을 따로 만들었어요. 여러 listen이 같은 복제본을 가리켜도 서버 상태와 헬스 체크는 listen마다 따로라서, 고장 한 번에 설정 일곱 가지의 반응을 동시에 잴 수 있습니다.

그림 1. 같은 복제본을 실험마다 다른 listen이 각자의 설정으로 본다
HAProxy 3.4.6 (LTS) Redis 8.10.2 Python (이미지) 3.14.8-slim 측정 같은 이미지의 experiment.py. listen마다 초당 100~150건을 일정 간격으로 보내고 HAProxy 통계 CSV(/stats;csv)를 50ms마다 읽어 DOWN 판정 시각을 남긴다 실행 환경 Docker Desktop, Apple M5 Pro

버전은 HAProxy의 최신 LTS인 3.4를 골랐어요(2026년 6월 출시, 지원 종료 2031년 2분기). 설정 매뉴얼도 3.4 판을 기준으로 읽었습니다. 코드는 labs/observability/rel-04-redundancy에 있어요.

2. 공통 원인 비율을 0에서 100%까지 올린다

복제본 r1~r3를 라운드로빈으로 받는 listen 두 개를 썼어요. 하나(aa_noretry)는 아무 장치 없이 요청을 돌리고, 다른 하나(aa_retry)는 실패 응답을 받으면 다른 복제본으로 다시 보냅니다. 헬스 체크는 일부러 끄고 요청 단위로만 비켜 가게 했어요. 병렬식의 "즉시 전환"에 가장 가까운 설정이에요.

listen aa_retry balance roundrobin retries 2 retry-on conn-failure 500 503 # 연결 실패와 500, 503에 재시도 option redispatch 1 # 재시도마다 다른 서버를 고른다 server r1 r1:8080 server r2 r2:8080 server r3 r3:8080

고장 일정은 5편의 베타 인자 모형대로 만들었습니다. 시간을 100ms 슬롯으로 자르고, 슬롯마다 확률 βQ로 공통 원인 사건을 일으켜 Redis의 mode를 bad로 바꿔요. 그러면 세 복제본이 모두 500을 냅니다. 나머지는 복제본마다 독립적으로 down(503)으로 만들었고, 한 대의 비가용성 Q는 10%로 고정했어요. β = 0은 슬롯 6,000개(10분), 나머지는 3,000개(5분)를 돌렸고 listen마다 초당 150건을 보냈습니다. 복제본 상태를 바꾸는 몇 ms 사이에 보낸 요청은 어느 슬롯 상태로 볼지 애매해서 성공률에서 뺐어요(실행과 listen마다 19~740건).

📖 용어: retry-on, redispatch
HAProxy의 retry-on은 어떤 실패에 요청을 다시 보낼지 정하는 지시어예요. 기본값은 연결 실패(conn-failure)뿐이라 500이나 503 응답에는 재시도하지 않습니다. option redispatch는 재시도할 때 다른 서버를 고르게 하는 옵션이고, 인자 1은 매 재시도마다를 뜻해요.
β 이론 가용성 실제 일정에서 하나라도 재시도 없음 retry-on + redispatch 살아 있던 슬롯 비율 성공률 성공률 하나라도 살아 있던 동안 0 99.900% 99.900% 89.944% 99.895% 99.994% 10% 98.926% 99.433% 90.560% 99.449% 99.993% 50% 94.986% 94.767% 89.922% 94.855% 99.993% 100% 90.000% 89.533% 89.537% 89.773% 100.000%

읽을 것이 세 가지예요.

첫째, 비켜 가는 장치가 없으면 복제본 셋은 한 대와 같습니다. 재시도 없는 listen은 β와 상관없이 90% 근처였어요. 라운드로빈은 요청을 순서대로 나눌 뿐이라, 지금 죽어 있는 복제본에 걸린 요청은 그대로 실패합니다. 병렬식의 99.9%는 "살아 있는 복제본에 요청이 간다"는 가정에서 나온 숫자라는 게 이 줄에서 보여요.

둘째, 재시도로 비켜 가면 성공률은 "하나라도 살아 있던 시간"을 그대로 따라갑니다. 오른쪽 열을 보면 하나라도 살아 있던 동안의 성공률은 β와 상관없이 99.99% 이상이었어요. 그러니 전체 성공률을 정하는 건 HAProxy가 아니라 고장 일정, 곧 세 대가 함께 죽은 시간이었습니다. β = 0에서 99.895%로 이론값 99.900%를 재현했고, β = 50%에서는 94.855%, β = 100%에서는 89.773%로 한 대짜리와 같아졌어요. 공통 원인 몫만큼은 재시도도 이중화도 되돌리지 못했습니다.

셋째, β = 10% 줄은 이론값보다 높게 나왔어요(99.449%, 이론 98.926%). 슬롯 3,000개에서 공통 원인 슬롯이 기대값 30개(1.0%)가 아니라 16개(0.53%)만 뽑혔기 때문입니다. 실제 일정으로 계산한 "하나라도 살아 있던 비율" 99.433%와 측정값은 맞았어요. 공통 원인처럼 드문 사건은 5분짜리 실험 한 번으로는 비율이 크게 흔들린다는 걸 그대로 보여 준 줄이라, 다시 돌리지 않고 남겼습니다. 5편의 "β는 측정하기 어렵다"는 주의가 실험 안에서도 나타난 셈이에요.

⚠️ 주의: 모두 죽은 동안에도 1~2%가 성공했다
• 표에는 없지만, β 10~100% 실행에서는 세 대가 모두 죽어 있던 슬롯에 보낸 요청도 재시도 listen에서 1.45~2.42%가 성공했어요(β = 0에서는 0.00%).
• 요청은 보낸 시각으로 슬롯에 붙였는데, 재시도를 두 번 거치는 몇 ms 사이에 슬롯이 바뀌어 다음 슬롯의 살아 있는 복제본에 닿은 요청으로 보입니다. 재시도 없는 listen도 β = 10%에서 0.40%가 성공했으니, 슬롯 경계에 걸린 몫이 섞여 있어요. redispatch 1이라 재시도는 매번 다른 서버로 가서, 같은 서버 재시도 앞의 대기는 여기서 걸리지 않습니다.
• 매뉴얼은 같은 서버로 다시 보낼 때 min(timeout connect, 1초)를 기다린다고 적고 있어요. 이 실습은 timeout connect를 50ms로 줄여 두었지만, 흔히 쓰는 5초 같은 값으로 두면 같은 서버 재시도 한 번에 1초를 기다리니 요청 지연이 그만큼 늘 수 있습니다.

3. 액티브가 죽은 뒤 백업으로 넘어가기까지

이번에는 서버 a를 액티브로, b를 backup으로 둔 listen 일곱 개를 만들었어요. 헬스 체크는 option httpchk GET /health로 하고, listen마다 inter와 fall만 다르게 줬습니다. a를 down(모든 응답 503)으로 바꾼 순간부터 15초 동안 listen마다 초당 100건을 보내고, HAProxy 통계에서 a가 DOWN이 된 시각을 50ms 간격으로 읽었어요. 고장 시점이 검사 주기의 아무 데나 떨어지도록 시행마다 0.5~2.5초를 무작위로 쉬고 8번 반복했습니다.

📖 용어: 백업 서버 (backup)
HAProxy 서버 줄에 backup을 붙인 서버입니다. 평소에는 요청을 받지 않고, 백업이 아닌 서버가 모두 쓸 수 없게 됐을 때만 부하 분산에 들어가요. 액티브-스탠바이를 HAProxy 설정 한 줄로 만드는 방법입니다.

헬스 체크만으로 넘어가는 다섯 줄은 모두 5편의 계산 범위 안에 들었어요(통계를 50ms마다 읽어서 수십 ms 늦게 잡힌 몫이 있습니다). 실패 요청 수는 "초당 100건 × 판정까지 걸린 초"와 거의 같았습니다. 기본값 inter 2s fall 3에서는 고장 한 번에 중앙값으로 5.27초 동안, 요청 526건이 죽은 서버로 갔어요.

📖 용어: observe layer7
헬스 체크와 별개로, 실제 요청의 응답을 지켜보다가 연속 오류가 error-limit(기본 10)에 이르면 on-error에 정한 동작을 하는 HAProxy 서버 옵션입니다. mark-down이면 그 자리에서 서버를 DOWN으로 내려요. 100~499, 501, 505 말고는 오류로 칩니다.

예상과 달랐던 줄이 둘 있어요. 하나는 재시도를 켠 fo_i2f3_redispatch가 기본값과 똑같이 실패했다는 겁니다. 503에 재시도하고 매번 다른 서버를 고르게 했는데도 실패가 줄지 않았어요. 매뉴얼에 따르면 backup 서버는 백업이 아닌 서버가 모두 쓸 수 없을 때만 부하 분산에 들어갑니다. a가 아직 UP으로 남아 있는 동안에는 재시도할 "다른 서버"가 없어서, 재시도가 전부 같은 a로 갔다고 봐요. 요청마다 어느 서버로 갔는지는 남기지 않았고, 실패 건수가 기본값과 같게 나온 데서 짐작한 것입니다. 요청 단위 재시도는 액티브-액티브에서만 이중화를 대신합니다.

다른 하나는 observe layer7이 모든 시행에서 정확히 10건 만에 넘겼다는 거예요. 헬스 체크 주기와 상관없이 실제 요청 10건이 연달아 실패한 순간(초당 100건이니 0.1초) DOWN이 됐습니다. 감지 시간이 검사 주기가 아니라 트래픽 양으로 정해지는 장치예요.

응답하지 않고 멈춘 서버는 더 늦게 잡힌다

a를 hang(응답 없이 30초 멈춤)으로 바꿔 4번 더 돌렸어요. 이 설정의 timeout check는 1초라, 검사 하나가 실패로 끝나기까지 1초를 기다립니다.

listen down일 때 DOWN 판정(중앙) hang일 때 DOWN 판정(최소 / 중앙 / 최대) fo_i2f3 5.27초 7.05 / 7.74 / 8.76 fo_i1f3 2.65초 5.36 / 5.68 / 6.05 fo_i1f2 1.58초 3.30 / 3.59 / 3.94 fo_i2f3_fast 1.66초 4.48 / 5.29 / 5.83 fo_i500f3 1.15초 4.21 / 4.32 / 4.48 fo_i2f3_observe 0.11초 7.11 / 7.65 / 8.13

헬스 체크로만 넘어가는 다섯 줄은 2~4초씩 늦어졌고, 가장 빠르던 inter 500ms가 배수로는 가장 크게 밀렸어요(1.15초에서 4.32초, 3.8배). 검사 간격을 500ms로 줘도 검사 하나가 타임아웃 1초를 다 기다려야 실패로 끝나니, 간격을 줄인 효과가 사라진 겁니다. observe도 이번에는 도움이 안 됐어요. 응답이 아예 오지 않으면 HAProxy가 timeout server(5초)를 기다린 뒤에야 오류로 셀 수 있어서, 오류 10건이 쌓이기 전에 헬스 체크가 먼저 DOWN을 냈습니다.

hang 시행의 실패 요청 수는 표에 넣지 않았어요. listen마다 스레드 4개로 보냈는데, 멈춘 서버로 간 요청이 5초씩 붙잡혀서 그동안 스레드가 다음 요청을 못 보냈기 때문입니다. 실패가 4~8건으로 찍혔지만 실제로 보내려던 요청은 수백 건이었어요. 실습-3에서 본 것과 같은 부하 생성기의 착시라, 이 경우는 DOWN 판정 시각만 믿을 수 있는 숫자로 봤습니다.

4. 포트는 열려 있는데 앱은 죽어 있다

마지막으로 복제본 셋을 라운드로빈으로 받는 listen 셋을 비교했어요. 검사 간격은 모두 inter 1s fall 3 rise 2로 같고, 검사 방식만 다릅니다.

chk_tcp check TCP 연결만 본다(HAProxy 기본) chk_http option httpchk GET /health HTTP 응답 2xx/3xx만 정상 chk_observe chk_http + observe layer7 error-limit 10 on-error mark-down

r1 하나를 30초 동안 고장 내고, listen마다 초당 150건을 보냈어요. 고장은 두 가지입니다.

r1 = down (모든 응답 503, 포트는 열림) listen 보냄 실패 실패율 HAProxy가 r1을 DOWN으로 판정 chk_tcp 4,505 1,501 33.32% 판정 안 함 (30초 내내 UP) chk_http 4,505 131 2.91% 2.64초 chk_observe 4,505 10 0.22% 0.22초 r1 = gray (/work는 500, /health는 200) chk_tcp 4,511 1,503 33.32% 판정 안 함 chk_http 4,510 1,503 33.33% 판정 안 함 chk_observe 4,510 160 3.55% 0.22초에 처음 판정, 이후 UP과 DOWN을 반복
📖 용어: TCP 검사와 HTTP 검사
TCP 검사는 서버 포트로 연결이 맺어지는지만 봅니다. HTTP 검사는 연결 뒤에 정해진 경로로 HTTP 요청을 보내 응답 코드까지 봐요. 프로세스는 살아 있고 앱만 고장 난 서버는 TCP 검사를 통과합니다.

TCP 검사는 두 고장 모두 30초 내내 r1을 UP으로 봤고, 요청의 정확히 3분의 1이 실패했어요. 포트가 열려 있는 한 TCP 검사에게 그 서버는 정상입니다. 5편의 표에서 TCP 검사가 못 잡은 회색 고장을 사람이 20분 뒤에 발견하면 한 달 예산의 154%를 쓴다고 계산한 게 이 상태예요.

HTTP 검사는 down을 2.64초 만에 잡았지만 gray는 TCP 검사와 똑같이 놓쳤어요. /health가 200을 주는 한 HTTP 검사도 그 서버를 정상으로 봅니다. 앱 검사도 결국 검사 경로가 실제 요청 경로를 얼마나 닮았느냐만큼만 봐요.

observe를 붙인 listen이 두 고장 모두에서 가장 적게 실패했는데, gray에서는 모양이 특이했어요. 실패 160건을 시각순으로 묶어 보니 정확히 10건씩 16묶음이었고, 묶음 사이 간격이 2.0초였습니다. 실제 요청 10건이 실패하면 mark-down으로 내려가고, 그다음 헬스 체크(/health는 200)가 rise 2번 성공하면 2초 뒤 다시 UP으로 올라와 또 10건을 실패하는 순환이에요. 헬스 체크와 실제 요청이 서로 다른 답을 내는 동안 서버는 계속 들락날락하고, 그 사이 실패는 줄었지만 0이 되지는 않았습니다.

💡 실무에서는
• 이중화 가용성을 잴 때는 "하나라도 살아 있던 시간"과 "그 동안의 성공률"을 나눠 보면, 고장 일정의 문제(공통 원인)와 전환 장치의 문제가 따로 보여요.
• 라운드로빈만으로는 복제본을 늘려도 가용성이 오르지 않습니다. 헬스 체크든 요청 단위 재시도든 죽은 복제본을 비켜 가는 장치가 있어야 해요.
• 액티브-스탠바이에서 retry-on과 redispatch는 백업으로 가지 않습니다. 전환은 헬스 체크의 DOWN 판정이 정해요.
• inter를 줄일 때는 timeout check도 같이 봅니다. 멈춘 서버 앞에서는 타임아웃이 감지 시간을 정해요.
• 헬스 체크 경로가 실제 요청 경로와 다르게 답할 수 있으면 observe layer7을 함께 걸고, 서버가 들락날락하는지 통계 화면에서 확인합니다.
✍️ 오늘의 요약
복제본 셋에 공통 원인 고장을 섞자 가용성은 β = 0에서 99.895%, 10%에서 99.449%, 50%에서 94.855%, 100%에서 89.773%로 떨어졌고, 하나라도 살아 있던 동안의 성공률은 늘 99.99% 이상이었어요. 재시도는 독립 고장만 비켜 갔고, 함께 죽은 시간은 그대로 실패였습니다. 비켜 가는 장치가 없는 라운드로빈은 β와 상관없이 90%였어요.

액티브-스탠바이 전환은 inter와 fall로 계산한 범위 안에서 일어났고(기본값에서 4.2~5.9초, 요청 416~581건 실패), 멈춘 서버 앞에서는 검사 타임아웃 때문에 2~4초 더 늦어졌어요. TCP 검사는 앱만 죽은 서버를 30초 내내 놓쳤고, HTTP 검사도 헬스 경로만 살아 있는 서버는 놓쳤습니다. 이중화는 복제본 수가 아니라, 무엇을 함께 쓰고 무엇으로 고장을 알아채느냐로 정해져요.
