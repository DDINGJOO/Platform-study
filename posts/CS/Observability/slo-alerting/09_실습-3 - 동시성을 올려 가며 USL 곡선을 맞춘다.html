동시 요청 16개에서 초당 705건을 처리하던 앱이 24개에서는 615건, 64개에서는 275건을 처리했습니다. 에러는 한 건도 없었어요. 늘린 만큼 처리량이 줄어드는, 5편의 셋째 모양 그대로입니다.

이번 실습은 그 곡선을 일부러 만듭니다. 경합과 일관성 비용의 크기를 설정값으로 정확히 알고 있는 앱을 하나 만들고, 동시성을 1부터 64까지 올리며 처리량을 잰 뒤, 범용 확장성 법칙(USL)을 맞춰 봤어요. 답을 아는 상태에서 맞추니, 맞춘 계수가 답을 되찾는지 바로 확인할 수 있습니다. 결과는 기대와 꽤 달랐어요.

🧭 이 글에서 확인할 것
• 경합만 넣은 앱, 경합과 일관성 비용을 같이 넣은 앱에서 맞춘 σ와 κ는 넣은 값을 되찾나?
• 처리량이 꺾이기 전의 점만으로 정점을 미리 알 수 있나?
• 리틀의 법칙은 실측에서 맞나? 평균 대신 p99를 넣으면?
• 다른 컨테이너와 같은 도커를 나눠 쓰는 환경에서 측정은 얼마나 흔들리나?

1. 실습 환경: 설정값 둘로 비용을 정하는 앱과 닫힌 부하

앱은 스프링 부트 엔드포인트 하나(GET /work)입니다. 요청마다 먼저 20ms를 잠들어요. 다른 서비스나 DB를 기다리는 시간을 흉내 낸 병렬 구간이라 요청끼리 서로 막지 않습니다. 그다음 전역 락 하나를 잡고 직렬 구간을 지나요. 이 구간 길이가 경합의 설정값(S)이고, 락을 잡은 채로 지금 서버 안에 있는 다른 요청 수 × C만큼 더 머무는 것이 일관성의 설정값(C)입니다. 공유 상태를 바꿀 때 같이 일하는 다른 요청 모두와 맞추는 비용을 흉내 낸 거예요.

그림 1. 경합과 일관성 비용을 설정값으로 정하는 앱 하나에 닫힌 부하를 건다

부하는 k6로 겁니다. 가상 사용자(VU) N개가 응답을 받자마자 다음 요청을 보내는 닫힌 부하라서, 서버 안의 동시성은 N을 넘지 않아요. USL의 N을 직접 손에 쥐는 방법입니다. 단계 하나는 워밍업 5초와 측정 20초이고, 측정 구간의 요청 수를 20으로 나눠 처리량을 냅니다. N은 1, 2, 4, 6, 8, 12, 16, 24, 32, 48, 64의 열한 단계이고, 열한 단계를 한 바퀴로 세 바퀴를 돌렸어요. 같은 단계를 시간을 두고 세 번 잰 셈입니다.

📖 용어: 가상 사용자 (VU, virtual user)
k6가 띄우는 독립된 실행 단위예요. 각 VU가 스크립트의 기본 함수를 반복 실행합니다. constant-vus 실행기로 VU 수를 고정하고 스크립트에 쉬는 시간을 두지 않으면, VU 수가 곧 동시에 서버에 걸려 있는 요청 수의 상한이 돼요.

쓴 버전은 아래와 같아요. 맞추기는 파이썬 컨테이너에서 scipy의 curve_fit으로 했습니다. σ와 κ는 0~1, λ는 0 이상으로 범위를 묶었어요.

2. 1ms라고 적었는데 락은 1.8ms 동안 잡혀 있었다

처음에는 직렬 구간도 잠으로 채웠어요. 락을 잡고 LockSupport.parkNanos로 1ms 자는 식이었습니다. 동시성 32를 걸어 보니 처리량이 초당 504건에서 멈췄어요(scripts/sleep-serial.sh, sleep-serial.csv). 직렬 구간이 1ms면 1초에 1,000번은 지나가야 하는데 절반입니다. 서버가 센 락 보유 시간을 보니 평균 1.96ms였어요(동시성 1에서도 1.92ms).

요청 길이를 바꿔 가며 동시성 1로 300번씩 쟀습니다.

직렬 구간 설정 잠으로 채움(parkNanos) CPU 를 돌려 채움 50µs 774µs 51µs 500µs 1,281µs 504µs 1,000µs 1,824µs 1,000µs

잠은 1ms 단위로 반올림된 것처럼 깼어요. 컨테이너 안에서 커널 설정(/proc/config.gz)을 보니 CONFIG_HZ=1000이고 CONFIG_HIGH_RES_TIMERS가 꺼져 있었습니다. 이 Docker Desktop의 리눅스 커널 빌드는 고해상도 타이머 없이 1ms 틱으로 잠을 깨운다는 뜻이에요. 그래서 직렬 구간은 CPU를 돌려서 정확히 채우게 바꿨습니다. 락을 잡은 스레드 하나만 도니 코어는 하나만 써요. 병렬 구간 20ms는 그대로 잠이라 실제로는 약 22ms가 됐고, 이건 λ에만 영향을 주니 두었습니다.

작은 일이지만 이번 실습 전체에 걸리는 교훈이 여기서 먼저 나왔어요. 설정한 값과 시스템이 실제로 한 일은 다를 수 있고, 그건 재 봐야 압니다. 서버 쪽 락 보유 시간을 따로 세지 않았다면 1.8ms로 돈 실험을 1ms 실험으로 기록했을 거예요.

3. 경합만 넣었는데 맞춘 곡선은 κ를 내놓았다

첫 시나리오는 병렬 20ms, 락 안에서 1ms, 일관성 비용 0입니다. 답은 분명해요. 락은 1초에 최대 1,000번 지나갈 수 있으니 천장은 초당 1,000건이고, κ = 0이니 처리량이 줄어들 이유가 없습니다.

처리량은 직선으로 오르다가 24에서 초당 980건에 닿고 그대로 누웠어요. 그 뒤로 동시성을 늘린 만큼은 전부 락 앞의 대기로 갔습니다. 64에서 평균 응답 65.5ms 중 43.7ms가 락 대기예요. 여기까지는 예상대로입니다.

이 33개 점(11단계 × 3회)에 USL을 맞췄더니 이렇게 나왔어요.

모든 점으로 맞춤 λ = 49.71 σ = 0.00000 κ = 0.000587 R² = 0.9912 → 정점 N* = 41.3, 그때 처리량 1,039, 그 뒤로 감소 κ = 0 으로 묶은 암달 λ = 72.92 σ = 0.05205 R² = 0.9467 → 천장 λ/σ = 1,401 (실측 980)
그림 2. 실측은 수평으로 누웠는데, 맞춘 곡선은 꺾여 내려간다

경합만 넣었는데 σ는 0이고 κ가 나왔어요. 맞춘 곡선은 41에서 정점을 찍고 내려가는데, 실제 처리량은 64까지 980에서 한 치도 내려가지 않았습니다. 이 계수를 그대로 읽으면 "일관성 비용이 문제다, 동시성 41을 넘기지 마라"가 되는데 둘 다 틀렸어요.

원인은 곡선의 무릎 모양입니다. 이 앱은 처리 시간이 거의 일정해서, 처리량이 직선으로 오르다 천장에서 갑자기 꺾여요. 5편 5장에서 본 대로 USL과 암달은 모든 요청이 한꺼번에 줄을 서는, 처리량이 가장 낮게 나오는 경우의 경계에서 나왔고, 그 경계가 그리는 무릎은 훨씬 둥글어요. 실제로 κ를 0으로 묶은 암달 맞춤은 λ를 73(실측 44.5)으로, 천장을 1,401(실측 980)로 엉뚱하게 잡고도 R²가 0.95에 그쳤어요. USL 회귀는 σ 대신 κ를 키워 날카로운 무릎을 흉내 내는 쪽을 골랐고, 그게 점들에는 더 잘 맞았습니다(R² 0.99). 맞춘 계수는 원인이 아니라 곡선의 모양을 말해요.

📖 용어: 결정계수 (R²)
맞춘 곡선이 측정값의 흩어짐을 얼마나 설명하는지를 0~1로 나타낸 값이에요. 1에 가까울수록 곡선이 점들을 잘 지나갑니다. 다만 R²가 높다고 계수의 해석까지 맞다는 뜻은 아니라는 게 이 절의 결과예요.

처리 시간이 흔들리는 시스템이면 무릎이 둥글어져서 다를까 싶어, 병렬 구간과 직렬 구간의 길이를 같은 평균의 지수 분포에서 뽑도록 바꿔 다시 쟀습니다(설정에 expRandom=true를 넣고 bash scripts/sweep.sh contention-exp 3, 결과는 contention-exp.csv. scripts/run-rest.sh에 이 실행과 4절의 같은 실행, 6절의 첫 CPU 실행이 들어 있어요). 24에서 처리량이 980 대신 911로 조금 둥글어졌지만, 맞춘 결과는 σ = 0, κ = 0.000536으로 같았어요. 이 정도 흔들림으로는 결론이 바뀌지 않았습니다.

N ≤ 8 점만으로 맞춘 빨간 점선도 볼 만해요. 직선 구간에서는 꺾임의 정보가 없으니, 64에서 1,962건(실측 978)을 예측했습니다. 두 배예요.

σ = 0이라는 값에는 단서가 하나 붙습니다. fit.py는 기본으로 σ와 κ를 0~1 범위로 묶고 맞춰요. σ = 0은 그 하한에 붙은 값입니다. 제약을 풀면(--free-sigma) σ = −0.004, κ = 0.00062, N* = 40.2로 거의 같았어요. 경합만 넣은 앱에서 κ가 나온다는 결론은 제약 때문이 아닙니다.

4편과 비교해 두면 이렇습니다. 4편은 "σ만 있으면 어느 선에서 수평으로 눕고, κ까지 붙으면 어느 지점부터는 더 넣을수록 오히려 느려진다"고 했고, 실측은 그 모양 구분과 맞았어요. 경합만 넣은 앱은 980에서 수평이었고, 다음 절의 일관성 비용을 넣은 앱은 정점 뒤로 줄었습니다. 맞지 않은 건 그 구분을 거꾸로 읽는 일, 곧 관측값에 맞춘 계수로 어느 모양인지 판정하는 쪽이었어요.

그림 3. 꺾이기 직전까지의 점으로는 꺾임을 예측하지 못했다

모든 점으로 맞추면 λ = 58.6, σ = 0, κ = 0.00264, 정점 N* = 19.5에 처리량 585건이 나와요(R² 0.92). 이 실행에서 잰 최대값 705(16)보다 낮습니다. 다만 여기서도 σ = 0은 제약의 하한에 붙은 값이에요. 제약을 풀면 σ = −0.055, κ = 0.0030, R² 0.99로 훨씬 잘 맞고, 정점은 N* = 18.8에 674건이 됩니다. 곡선이 정점 높이를 크게 놓친 건 상당 부분 σ ≥ 0 제약 때문이었어요. 대신 제약을 풀면 σ가 음수로 나옵니다. 5편이 "σ가 음수면 측정부터 의심하라"고 한 그 값인데, 여기서는 측정 오류가 아니라 무릎이 날카로운 곡선을 USL 모양에 맞추다 나온 값이에요.

κ는 자릿수가 맞았어요. 처리량이 줄어드는 구간에서 이 앱은 1 / (C × N) 꼴로 내려가고, USL은 λ / (κN) 꼴로 내려가니 κ ≈ λ × C로 기대할 수 있습니다. λ를 동시성 1의 처리량 43.5건/초로 두면 43.5 × 0.00005초 ≈ 0.0022예요. 맞춘 값 0.0026(제약 있음), 0.0030(제약 없음)과 같은 자릿수입니다. 반면 넣은 경합(직렬 0.5ms)은 어느 쪽 맞춤에서도 양의 σ로 나타나지 않았어요.

처리 시간을 지수 분포로 흔든 같은 시나리오(coherency-exp.csv, bash scripts/sweep.sh coherency-exp 3)에서는 조금 달랐어요. 16에서 락 대기가 0.58ms 대신 1.95ms로 먼저 오르기 시작했고, 16까지의 점으로 맞춘 예측 정점이 158 대신 51로 나왔습니다. 처리 시간이 흔들리니 앞쪽 점에 꺾임이 조금 드러났지만, 실제 정점(16~24 사이)과는 여전히 멀어요.

📖 용어: 일관성 비용 설정값 (C)
이 실습에서 락을 잡은 요청이 "지금 서버 안에 있는 다른 요청 하나마다" 더 머무는 시간이에요. 요청이 많을수록 락 한 번이 길어지니, 5편에서 본 κN(N−1) 항을 코드로 옮긴 셈입니다. 같이 있던 요청 수는 서버가 락을 잡는 순간 센 값이에요.

5. 리틀의 법칙은 맞았고, p99를 넣으면 틀렸다

닫힌 부하에서 VU가 쉬지 않으니 생각 시간 Z는 0에 가깝고, 리틀의 법칙대로라면 처리량 × 평균 응답 시간이 VU 수와 같아야 해요. 일관성 시나리오의 숫자로 확인했습니다.

N 처리량 평균 응답 p99 응답 처리량×평균 처리량×p99 1 43.5 22.8ms 26.8ms 0.99 1.2 16 704.6 22.7ms 25.2ms 15.99 17.8 32 494.0 64.8ms 68.8ms 32.03 34.0 64 274.6 234.0ms 365.4ms 64.27 100.3

평균으로 계산한 값은 모든 단계에서 N과 1% 안으로 맞았어요. 측정이 제대로 됐다는 확인이기도 합니다. p99를 넣으면 64에서 100이 나와요. 동시에 걸린 요청이 100개였다는 뜻이 아니라, p99는 리틀의 법칙이 다루는 값이 아니라는 뜻입니다. 이 앱은 처리 시간이 일정해서 p99가 평균과 가까운 편인데도 64에서는 1.6배 차이가 났어요. 처리 시간이 흔들리는 시나리오에서는 동시성 1에서도 p99가 94ms로 평균 22ms의 네 배가 넘었습니다.

⚠️ 주의: USL이 예측하는 응답 시간은 평균입니다
USL의 R(N) = N/X(N)은 리틀의 법칙에서 나오니 평균 응답 시간이에요. SLO가 p99라면 USL로 고른 동시성에서 p99를 따로 재야 합니다. 이번 실습에서 처리 시간이 흔들리는 시나리오는 평균이 22ms일 때 p99가 이미 94ms였어요.

6. 같은 도커를 나눠 쓰면 측정은 얼마나 흔들리나

이 실습은 다른 실습 두 개가 같은 Docker Desktop VM(CPU 15개, 메모리 8GB)을 함께 쓰는 동안 돌렸어요. 단계마다 VM의 1분 로드 애버리지를 같이 기록했는데, 4에서 26 사이를 오갔습니다. 그래서 같은 단계를 세 번씩 시간을 두고 재서 흔들림을 봤어요.

3~4절의 앱은 거의 흔들리지 않았습니다. 처리량을 정하는 게 잠(병렬 구간)과 락을 잡은 스레드 하나의 계산(직렬 구간)뿐이라 코어를 두고 남과 다툴 일이 적었기 때문이에요. 세 번 측정의 (최대 − 최소)/평균이 경합 시나리오의 직선 구간에서 1.7~4.5%, 천장에서 0.3~0.5%, 일관성 시나리오에서 0~1.8%였습니다. 처리 시간을 지수 분포로 흔든 시나리오는 N = 1, 2에서 7%대까지 흔들렸는데, 동시성 1이면 단계 하나의 요청이 900건 남짓이라 무작위로 뽑은 길이의 편차가 평균에 그대로 남은 거예요.

흔들림이 크게 나온 건 CPU를 실제로 쓰는 시나리오였어요. 병렬·직렬 구간을 끄고 요청마다 약 2ms의 계산만 하게 한 뒤, 컨테이너를 CPU 2개로 묶었습니다. 세 가지로 쟀어요. 첫 실행은 scripts/run-rest.sh의 마지막 부분이고, 둘째는 scripts/run-extra.sh, 셋째는 scripts/cpu-cpuset.sh입니다. 그래프는 docker compose --profile fit run --rm --entrypoint python fit /fit/plot_cpu.py로 그렸어요.

# 첫째: 벽시계로 2ms (APP_CPUS=2 docker compose up -d app 뒤) curl -XPOST 'localhost:22080/config?parallelUs=0&serialUs=0&coherencyUs=0&cpuUs=2000&cpuLoops=0' bash scripts/sweep.sh cpu 3 # 둘째: 계산 180만 번 curl -XPOST 'localhost:22080/config?parallelUs=0&serialUs=0&coherencyUs=0&cpuUs=0&cpuLoops=1800000' bash scripts/sweep.sh cpu-fixed 3 # 셋째: 둘째와 같은 계산, 할당량 없이 코어 두 개에 고정 bash scripts/cpu-cpuset.sh
그림 4. 같은 "CPU 2개"인데 묶는 방식에 따라 곡선 모양이 셋으로 갈렸다

첫째, 벽시계로 2ms를 돌게 했더니 천장을 넘었어요(주황, cpu.csv). 64에서 평균 1,269건, 가장 높은 회차는 1,372건입니다. 2코어 ÷ 2ms = 초당 1,000건(그림 4의 점선)이 이 방식의 이론 천장인데 그걸 넘었어요. 코드가 "2ms가 지날 때까지 돈다"였기 때문이에요. 스레드가 코어를 뺏긴 동안에도 시계는 가니까, 동시성이 높을수록 요청 하나가 실제로 한 계산은 2ms보다 적어집니다. 그 회차의 VM 로드 애버리지는 10.4~26.1로, 다른 두 회차(4.9~9.9)보다 높았어요. 옆 컨테이너가 바쁠수록 처리량이 올라간 셈인데, 일을 덜 하고 끝냈기 때문입니다. 5편에서 초선형 결과가 나오면 측정부터 의심하라고 했던 경우가 이렇게 나왔어요.

둘째, 일의 양을 고정하자 처리량이 줄었어요(빨강, cpu-fixed.csv). 계산 180만 번(동시성 1에서 약 1.8ms)으로 바꿨더니 2에서 1,079건으로 정점을 찍고 24부터 720건대로 내려앉았습니다. 이 방식의 이론 천장은 2코어 ÷ 1.8ms ≈ 초당 1,110건이에요. 일관성 비용을 넣지 않았는데 5편의 셋째 모양이 나온 거예요. 동시성별로 컨테이너의 cgroup 통계(/sys/fs/cgroup/cpu.stat)를 25초씩 따로 다시 쟀습니다. 위 그래프와는 다른 실행이고, 원문 출력은 results/cpu-throttle.txt에 남겼어요.

📖 용어: CFS 할당량 (CFS quota)
리눅스 스케줄러가 cgroup에 주기마다 쓸 수 있는 CPU 시간을 정해 주는 방식이에요. 할당량을 다 쓰면 다음 주기까지 그 cgroup의 스레드 전체가 멈춥니다. Docker의 --cpus와 쿠버네티스의 CPU limit이 이 방식으로 동작해요.

셋째, 할당량 대신 코어 두 개에 고정하자 하락이 사라졌어요(파랑, cpu-cpuset.csv). 같은 계산을 할당량 없이 cpuset: "0,1"로만 묶었더니(compose.cpuset.yaml), 처리량이 6부터 64까지 1,110~1,130건에서 수평이었습니다. 앞에서 계산한 이론 천장 1,110 근처예요. 하락은 앱이 아니라 CPU를 나눠 주는 방식에서 왔다는 게 이걸로 갈렸어요. 쿠버네티스의 CPU limit도 CPU 스로틀링으로 강제되는 상한이에요(쿠버네티스 문서). 컨테이너에 CPU limit을 건 채로 USL을 맞추면, 앱의 κ와 할당량의 효과가 한 계수에 섞여 나올 수 있어요.

할당량 시나리오는 흔들림도 컸습니다. 16에서 세 번 측정이 730~1,072건으로 40%가 벌어졌어요. 첫 회차는 16까지 1,070건대를 유지했고 둘째·셋째 회차는 6부터 줄기 시작했습니다. 첫 회차의 VM 로드 애버리지(11.6~19.5)가 다른 회차(3.6~9.3)보다 높았는데, 옆이 바쁠 때 오히려 처리량이 높았던 이유는 확인하지 못했어요. 이 시나리오의 USL 맞춤은 R² 0.47로 의미 있는 곡선이 나오지 않았습니다. 코어를 고정한 시나리오에서도 맞춤은 다시 σ = 0.51, κ = 0.0014(N* 18.8)를 내놓았어요. 실측은 수평이었는데요. 3절과 같은 무릎 문제입니다.

⚠️ 주의: 이 숫자들을 일반화하지 마세요
• 이 실습의 앱은 처리 시간이 거의 일정하고 공유 자원이 락 하나뿐인 인공적인 앱이에요. 실제 서비스의 곡선은 이보다 둥글 수 있고, 그만큼 USL이 더 잘 맞을 수 있어요
• CPU 시나리오의 하락과 흔들림은 Docker Desktop VM과 CFS 할당량, 그리고 같은 VM을 쓰던 다른 작업의 조합에서 나온 결과예요. 다른 환경에서는 크기가 다를 수 있어요
• 모든 단계는 측정 20초, 회차는 2~3번이에요. 정점 근처는 더 촘촘히, 더 오래 재야 해요
💡 실무에서는: USL을 맞출 때
• 서버 쪽에서 락·풀 대기 시간과 보유 시간을 같이 재요. 계수가 κ를 가리켜도 원인이 일관성인지는 이 값으로 확인해요
• 동시성 단계는 정점을 넘어서까지 잡고, 정점이 보이면 그 근처를 다시 촘촘히 재요
• 리틀의 법칙(처리량 × 평균 응답 ≈ 동시성)으로 측정이 제대로 됐는지 먼저 확인해요
• CPU limit이 걸린 컨테이너라면 cgroup의 스로틀링 통계를 같이 기록해요. limit을 빼거나 코어를 고정한 측정과 비교하면 할당량의 몫이 갈려요
• 일을 "시간"으로 흉내 내는 부하 앱은 쓰지 않아요. 코어를 뺏기면 일의 양이 줄어 처리량이 부풀어요
✍️ 오늘의 요약
경합과 일관성 비용을 정확히 아는 앱에 동시성 1~64의 닫힌 부하를 걸었더니, 일관성 비용을 넣은 쪽은 64에서 초당 275건까지 줄었고, 정점 근처를 촘촘히 다시 잰 별도 실행에서 정점은 18(초당 748건)이었어요. 리틀의 법칙은 평균으로는 모든 단계에서 1% 안으로 맞았고, p99를 넣으면 맞지 않았어요.

맞춘 USL 계수는 κ의 자릿수는 맞혔지만(기대 0.0022, 맞춘 값 0.0026~0.0030), 넣은 경합은 σ에 나타나지 않았어요. σ는 제약의 하한 0에 붙거나, 제약을 풀면 음수로 나왔습니다. 경합만 넣은 앱에서도, 코어에 고정한 CPU 앱에서도 κ가 나왔고, 꺾이기 직전까지의 점으로는 정점을 158(제약을 풀면 65)로 예측했어요. CPU 할당량은 일관성 비용 없이도 처리량을 끌어내렸습니다. USL은 곡선의 모양을 요약해 줄 뿐이고, 원인은 서버 안에서 직접 잰 값이 알려 줍니다.
