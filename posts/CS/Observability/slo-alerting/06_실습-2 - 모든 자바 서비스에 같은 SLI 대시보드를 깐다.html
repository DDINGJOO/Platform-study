주문 서비스에 요청을 몰아넣었습니다. 지연 패널의 p99는 224ms에서 움직이지 않았는데, 같은 시각 k6는 응답 하나를 6.5초씩 기다렸어요. 가장 심했던 15초 동안은 대시보드 전체가 비었습니다.

3편의 공통 지표 목록을 Grafana 대시보드 JSON 한 장으로 만들어 서비스 두 개에 깔고, 스레드 풀 포화와 GC 압박을 넣어 어느 패널이 먼저 반응하는지 5초 단위로 기록했어요. 3편에 없던 함정도 하나 나왔습니다.

🧭 이 글에서 확인할 것
• 서비스 이름만 바꿔 같은 대시보드를 쓰려면 지표와 쿼리를 어떻게 맞춰야 하나?
• 톰캣 스레드가 다 차면 어느 패널이 움직이고, 어느 패널이 끝까지 모르나?
• 할당 폭주, 남는 데이터 증가, Full GC 연발 중 사용자 지연은 어디서부터 나빠지나?
• GC가 가장 심할 때 GC 패널은 무엇을 보여 줬나?

1. 실습 환경: 같은 코드, 다른 서비스 둘

실습-1의 앱으로 설정만 다른 orders와 payments를 띄웠어요. Prometheus가 5초마다 긁고, k6는 서비스마다 초당 30건을 보내며 자기가 잰 응답 시간을 원격 쓰기로 넣습니다(서버 타이머 비교용).

orders 톰캣 작업 스레드 20개(기본 200), 요청마다 200ms 지연(curl로 주입, 재기동하면 0으로 초기화) GC는 지정하지 않음 → JVM이 Serial GC를 골랐다(2절) payments 톰캣 기본값, 요청 처리 5~14ms(평균 약 10ms) -XX:+UseG1GC 로 G1을 직접 지정 공통 -Xmx256m, 컨테이너 메모리 한도 512MB
그림 1. 파일 하나, 변수 하나, 서비스 몇 개든 같은 화면

쓴 버전은 실습-1과 같아요(Spring Boot 4.1.1, Micrometer 1.17.1, Java 21.0.12, Prometheus 3.15.0, Grafana 13.2.3, k6 2.3.0). 실습 코드는 GitHub 저장소의 labs/observability/slo-02-jvm-sli에 있습니다. 앱은 실습-1 폴더의 코드를 같이 빌드해요.

cd Platform-study/labs/observability/slo-02-jvm-sli docker compose up -d --build docker compose --profile load run -d --rm -e TARGET=orders -e RATE=30 -e DURATION=90m load docker compose --profile load run -d --rm -e TARGET=payments -e RATE=30 -e DURATION=90m load curl -X POST 'localhost:24180/chaos?latencyMs=200' # orders 요청마다 200ms python3 scripts/panel-log.py orders > orders.csv # 패널 대표값을 5초마다 기록(30초 창) python3 scripts/panel-log.py payments > payments.csv bash scripts/gc-steps.sh # 4절의 GC 압박 세 단계 # 5절의 GC 로그: compose 의 payments JAVA_TOOL_OPTIONS 끝에 -Xlog:gc:stdout 을 붙이고 # docker compose up -d payments 로 재기동한 뒤 docker compose logs -t payments # Grafana: http://localhost:24130 → SLI / 자바 서비스 공통 SLI

2. 대시보드는 JSON 한 장, 서비스 구분은 태그 하나

화면에서 만든 대시보드는 서비스마다 복사되고 복사본끼리 달라져요. 그래서 JSON 파일로 두고 Grafana가 기동할 때 읽게 했습니다.

📖 용어: 프로비저닝 (provisioning)
Grafana가 기동할 때 정해진 폴더의 파일을 읽어 데이터 소스와 대시보드를 만드는 기능입니다. 대시보드를 코드 리뷰로 바꿀 수 있어요.
# grafana/provisioning/dashboards/dashboards.yaml providers: - name: java-sli folder: SLI type: file allowUiUpdates: false # 화면에서 고친 내용은 저장되지 않는다. 정본은 JSON options: path: /var/lib/grafana/dashboards

같은 쿼리를 쓰려면 모든 지표에 서비스 이름이 있어야 해요. 설정 한 줄로 Micrometer가 application 태그를 달고, 대시보드는 label_values(jvm_info, application)로 선택 변수를 만들어 모든 쿼리에 넣었습니다.

management: metrics: tags: application: ${spring.application.name} distribution: percentiles-histogram: http.server.requests: true # 서버 지연을 히스토그램 버킷으로도 내보낸다 server: tomcat: mbeanregistry: enabled: true # 이게 없으면 tomcat_threads_* 지표가 안 나온다

패널은 3편의 여섯 지표 순서에 톰캣 스레드 패널을 더했어요. 그림 1의 배치이고, 주요 쿼리는 이렇습니다.

가용성 1 - (sum(rate(http_server_requests_seconds_count{application="$application", uri!~"/actuator.*", status=~"5.."}[$__rate_interval])) or vector(0)) / sum(rate(http_server_requests_seconds_count{...}[$__rate_interval])) 지연 p99 histogram_quantile(0.99, sum by (le) (rate(http_server_requests_seconds_bucket{...}[...]))) GC 비중 sum(rate(jvm_gc_pause_seconds_sum{application="$application"}[$__rate_interval])) 힙 sum(jvm_memory_used_bytes{..., area="heap"}) / sum(jvm_memory_max_bytes{..., area="heap"} > 0) GC 직후 jvm_memory_usage_after_gc{application="$application"} 스레드 tomcat_threads_busy_threads, tomcat_threads_config_max_threads

같은 이미지인데 GC가 달랐다

처음 힙 쿼리는 G1을 가정해 분모를 id=~".*Old Gen"으로 골랐는데 orders 패널이 비었어요. 영역 이름이 Tenured Gen, GC 이름이 Copy와 MarkSweepCompact인 Serial GC였습니다.

GC를 지정하지 않으면 JVM이 기계를 보고 고릅니다. OpenJDK 21 소스(os::is_server_class_machine)의 주된 조건은 CPU 2개 이상, 메모리 2GB에서 256MB를 뺀 1,792MB 이상이에요(패키지당 논리 프로세서가 여럿이면 물리 패키지 수도 따지는 단서가 붙어요). 이걸 만족하면 "서버급"으로 보고 G1을, 아니면 Serial을 씁니다. 컨테이너 안에서는 메모리 한도를 기계 메모리로 읽어서, 한도 512MB와 2GB로 띄운 -XX:+PrintFlagsFinal은 각각 UseSerialGC = true {ergonomic}, UseG1GC = true {ergonomic}였어요.

📖 용어: GC 에르고노믹스 (ergonomics)
JVM이 CPU 수와 메모리를 보고 GC 종류, 힙 크기 같은 기본값을 스스로 정하는 동작입니다. {ergonomic} 표시가 붙은 값이 그렇게 정해진 값이에요.
⚠️ 주의: 공통 대시보드는 GC 종류를 가정하면 안 된다
G1은 Eden과 Survivor 영역의 max를 -1로 내보내고 Old Gen에만 힙 최대값을 실어요. Serial은 영역마다 max가 있습니다. 그래서 분모를 "0보다 큰 max의 합"으로 바꿨어요. 한도 1,792MB 미만 컨테이너는 GC를 지정하지 않으면 Serial이 되고, 3편의 G1 거대 할당 신호도 나오지 않아요.

3. 스레드가 다 차자, 서버 타이머는 끝까지 몰랐다

orders는 요청당 약 210ms, 스레드 20개라 초당 약 95건이 한계예요. 평소 30건(스레드 7개쯤)에 45초 동안 초당 90건을 더 보냈습니다.

docker compose --profile load run --rm -e TARGET=orders -e RATE=90 -e DURATION=45s -e MAX_VUS=1000 load

panel-log.py가 5초마다 30초 창으로 계산해 기록한 값이에요. 그림의 패널은 Grafana의 $__rate_interval로 계산해서 처리량 꼭대기가 108처럼 조금 다르게 보여요. 08:14:03에 주입을 시작했습니다.

그림 3. 사용자가 기다린 6초 중 서버가 잰 것은 마지막 0.21초

진행 중 요청 수(LongTaskTimer인 http.server.requests.active)도 20에서 멈췄어요. 이 값도 스레드를 얻어 처리를 시작한 요청만 세기 때문에, 큐에서 기다리는 요청은 보이지 않습니다(서버 p99가 0.224초로 고정된 건 버킷 경계 0.2013초와 0.2237초 사이 보간값이라서예요).

가장 심한 15초 동안 대시보드가 비었다

08:14:45부터 세 번의 스크레이프가 실패해 up이 0이 됐어요. /actuator/prometheus도 같은 스레드 20개로 처리되니 지표 요청도 큐에서 기다렸고, 5초를 넘자 Prometheus가 포기했습니다.

📖 용어: 스크레이프 타임아웃 (scrape_timeout)
Prometheus가 한 번 긁을 때 기다리는 최대 시간입니다. 설정이 없으면 10초와 스크레이프 간격 중 작은 값이라(Prometheus 소스), 이 실습은 5초였어요.

그림 2의 모든 패널이 같은 자리에서 끊긴 이유예요. 가장 나쁜 순간에 데이터가 없고, 그 지표에 건 경고도 평가할 값이 없습니다.

💡 실무에서는: 스레드 포화를 보려면
• 서버 지연 옆에 호출하는 쪽의 지연(http.client.requests, 게이트웨이)을 두세요. 3편의 권고예요
• 사용 중 스레드 / 최대 스레드가 1에 붙는 시간을 경고 후보로 보세요. 이번에 가장 빨랐어요
• 액추에이터를 별도 포트(management.server.port)로 빼면 지표 요청이 업무 요청 뒤에 줄을 서지 않아요. 이번에는 해 보지 않았어요
• up == 0도 신호예요. "지표 없음"을 정상으로 읽지 마세요

4. GC 압박 세 단계: 지연은 마지막 단계에서야 움직였다

payments(G1)에 세 단계로 압박을 넣었어요. 백그라운드 스레드가 64KB 배열을 초당 지정량만큼 만들어 버리고(할당), 1MB 배열을 지정 개수만큼 붙잡습니다(남는 데이터).

09:19:00 1) 버려지는 객체만 초당 300MB allocMbPerSec=300 09:21:00 2) 붙잡아 두는 데이터 90MB 추가 retainMb=90 09:23:00 3) 붙잡는 데이터 118MB, 초당 600MB retainMb=118&allocMbPerSec=600 09:26:00 4) 되돌림

이 첫 실행(09:19~09:26)에서 단계마다 패널 값이 처음 바뀐 시각과 크기를 적었어요(panel-log.py 5초 기록, 30초 창, 주입 전 1분 평균 대비).

1) 할당만 2) 남는 데이터 3) 꽉 찬 힙 + 할당 GC 횟수/초 0.08 → 7.7 (6초) 변화 없음 7.4 → 30~57 (11초) GC 일시정지 비중 0 → 1.1% 변화 없음 1.2% → 10~21% GC 직후 힙 7.8% 그대로 7.8% → 77% (6초) 77% → 98~99.9% CPU(15코어 기준) 0.2% → 1% 안팎 1% 안팎 1% → 19% (6초) → 25% 서버 p99 20ms 그대로 20ms 그대로 20ms → 77ms (6초) → 149ms k6 p99 18ms 그대로 18ms 그대로 18ms → 86ms → 164ms 가용성 100% 100% 100%
그림 4. 힙은 계단으로 오르고, 지연은 마지막 계단에서만 오른다

1단계는 GC 횟수가 100배 가까이 늘었지만 한 번에 1~2ms라 비중은 1%, 지연은 그대로였어요. 3편의 "볼 것은 횟수가 아니라 비중" 그대로입니다.

2단계에서는 GC 직후 힙(jvm_memory_usage_after_gc, 마지막 GC 뒤 오래 사는 영역 사용량을 그 영역 최대로 나눈 값. G1에서는 Old 영역 최대 = 힙 최대)만 다음 기록에서 7.8%에서 77%로 뛰었어요. 붙잡은 건 90MB인데 256MB 힙의 약 69%, 곧 177MB만큼 올랐습니다. G1 영역이 1MB(G1HeapRegionSize = 1048576)라 1MB 배열은 배열 머리 몇 바이트 때문에 거대 객체로 영역 두 개를 차지하고, 마지막 영역의 남는 공간은 쓰지 못한다고 보면 숫자가 맞아요(Oracle G1 문서의 거대 객체 설명, 실제로 cause="G1 Humongous Allocation" GC가 기록됨). 그래도 지연은 그대로였어요. 힙이 차 있는 것만으로는 장애가 아니었습니다.

📖 용어: Full GC (G1 Compaction Pause)
힙 전체를 멈춘 채 정리하는 수집입니다. G1은 공간을 확보하지 못하면 여기로 넘어가요. Micrometer에서는 gc="G1 Old Generation"으로 보입니다.

3단계에서 힙이 99%에 붙자 Full GC가 연달아 일어났고, 6초 뒤 서버 p99와 CPU가 같이 뛰었어요. 이번에는 서버 타이머와 k6가 같이 움직였습니다. GC 멈춤은 처리 중인 요청 안에서 일어나니까요.

5. GC가 가장 심할 때, GC 패널은 10분의 1만 보여 줬다

그림 4의 GC 패널에는 이상한 게 하나 있어요. 첫 실행에서 압박을 되돌린 09:26:06에 GC 일시정지 비중이 533%, GC 횟수가 초당 1,516번으로 튀었습니다(기록 스크립트의 30초 창 기준. 그림은 계산 창이 짧아 약 830%, 1.5K까지 보여요). 1초에 5초를 멈출 수는 없으니, payments를 GC 로그(-Xlog:gc:stdout)를 켠 채 다시 띄워 재실행했어요. 이번에는 3단계만 2분 동안 넣었다가 되돌린 뒤 로그와 Micrometer 카운터를 10초 단위로 맞대 봤습니다.

10초 구간 끝 GC 로그의 Full GC 로그의 멈춤 합 Micrometer 누적 Full GC 09:31:10 943 6,244ms 108 09:31:40 882 7,314ms 328 09:32:10 886 7,305ms 722 09:32:40 926 7,202ms 1,214 09:33:00 941 7,209ms 1,565 ← 09:33:01 되돌림 09:33:10 190 1,489ms 11,159 ← 10초 만에 9,594 증가 합계 11,159 87,449ms 11,159

JVM은 10초마다 Full GC를 900번 안팎 하며 약 7.2초를 멈춰 있었는데, Micrometer 카운터는 같은 10초에 56~184번만 늘었어요. 되돌리자 밀린 9,594번이 10초 안에 들어왔고 합계는 로그와 같았습니다. 1단계를 60초 넣었을 때는 로그 536번, Micrometer 493번으로 거의 맞았어요.

📖 용어: GC 알림 (GarbageCollectionNotification)
JVM이 GC 한 번이 끝날 때마다 JMX로 보내는 이벤트로, 종류·원인·걸린 시간이 들어 있어요. Micrometer는 이 알림을 받아 jvm_gc_pause_seconds와 jvm_gc_overhead를 갱신합니다.

Micrometer GC 지표는 이 알림을 받아서 셉니다(JvmGcMetrics 소스). 처리가 GC 속도를 못 따라가면 밀리는데, 어느 스레드가 왜 밀렸는지는 확인하지 못했어요. GC가 가장 심한 동안 GC 패널은 실제의 10분의 1 정도를 보여 줬고, 나머지는 압박이 끝난 뒤에 도착했습니다.

jvm_gc_overhead는 더 늦었어요. 이 게이지는 알림이 올 때마다 멈춘 시간을 바로 더하지만, 분모가 5분으로 고정이라 원래도 천천히 오릅니다(JvmHeapPressureMetrics 기본 lookback 5분. 1분 단위로 움직이는 건 오래된 값이 빠지는 쪽뿐이에요). 3단계 3분 동안 0.009에서 0.097까지만 올랐고, 되돌린 직후 밀린 알림이 들어오자 0.526으로 뛰어 그 뒤로도 한동안 높게 남았어요. 이 값에만 건 경고는 장애가 끝난 뒤에 울렸을 거예요. 3편은 이 값을 "GC에 쓴 CPU 시간의 근사치"라고 소개했는데, 1.17.1 소스를 보면 실제로 더하는 값은 동시 수행 단계를 뺀 GC 이벤트의 소요 시간(벽시계)이에요. 지표 설명(description) 문구가 CPU 시간이라고 적고 있을 뿐입니다.

💡 실무에서는: GC 경고는 GC 지표 하나에만 걸지 않는다
• 압박 직후 GC 비중이 100%를 넘게 튀면 밀린 알림일 수 있어요. 장애 시작으로 읽지 마세요
• 정확한 GC 시간은 GC 로그(-Xlog:gc)로 보세요. 이번에 로그는 밀리지 않았어요

6. 어느 패널이 먼저 반응했나

"먼저"는 주입 뒤 처음 값이 바뀐 5초 기록 기준이에요.

장애 제일 먼저(주입 뒤) 늦거나 끝까지 모른 패널 스레드 풀 포화 톰캣 스레드 20/20 (4초) 서버 p99(끝까지 평평), 가용성(100%), 진행 중 요청(20에서 멈춤) k6 p99 (4초, 실습 전용) 모든 패널: 가장 심한 15초는 스크레이프 실패로 공백 할당만 증가 GC 횟수 (6초) 사용자 지표는 변화 없음(정상) 남는 데이터 증가 GC 직후 힙 (6초) 사용자 지표는 변화 없음(정상) 힙 포화 + Full GC 지연, CPU, GC 직후 힙 (6초) GC 횟수·비중(재실행에서 실제의 약 10분의 1), jvm_gc_overhead(가장 늦음)
✍️ 오늘의 요약
대시보드 JSON 한 장과 application 태그 하나로 서로 다른 GC를 쓰는 두 서비스에 같은 SLI 화면을 깔았고, 패널 하나하나는 3편이 말한 대로 움직였다. 다만 자원 쪽 패널이 증상을 설명하려면 증상과 같은 시각에 값이 있어야 한다.

스레드가 다 찼을 때는 지표 엔드포인트도 같은 스레드를 기다려 가장 심한 15초가 비었고, Full GC가 초당 90번일 때 Micrometer는 그 10분의 1만 셌다가 압박이 끝난 뒤 한꺼번에 받았다. 증상이 심할수록 그것을 설명할 숫자가 늦거나 빌 수 있다. 공통 대시보드는 같은 자리를 보여 주지만, 그 자리의 숫자가 언제 도착하는지는 따로 확인해야 한다.
