주문 API가 갑자기 300ms씩 느려졌습니다. 주문 서비스 코드는 바뀐 게 없고, CPU도 메모리도 평소와 같아요. 느려진 곳은 주문 서비스가 아니라 그 뒤 어딘가입니다. 이번 글은 그 "어딘가"를 일부러 만들어 놓고 트레이스로 찾아봅니다.

두 가지를 해요. 먼저 재고 서비스와 DB 사이에 네트워크 지연을 넣고 트레이스에서 원인 스팬을 찾습니다. 그다음 6편의 실험을 직접 만들어요. W3C baggage에 chaos 깃발을 실은 요청만 결제에서 실패시키는 서블릿 필터를 짜고, 다른 요청은 멀쩡한지 확인합니다. 6편이 경고한 "들어오는 baggage를 그대로 믿으면 안 된다"도 실제로 확인했어요. 바깥에서 헤더 한 줄만 붙이면 결제가 실패했습니다.

🧭 이 글에서 확인할 것
• DB 경로에 300ms를 넣으면 트레이스의 어느 스팬이 늘어나나?
• 같은 300ms가 어떤 요청에서는 왜 600ms가 되나?
• baggage 깃발로 특정 요청만 실패시키면, 나머지 요청은 정말 멀쩡한가?
• 바깥에서 온 baggage를 믿으면 무슨 일이 생기고, 어떻게 막나?

1. 실습 환경: 재고 DB 앞에 Toxiproxy를 세웠다

실습-1의 세 서비스를 그대로 쓰되, 재고 서비스의 DB를 H2에서 Postgres로 바꿨어요. H2는 같은 JVM 안의 메모리 DB라서 네트워크가 없고, 지연을 끼울 자리도 없습니다. 재고 서비스는 Postgres에 직접 붙지 않고 Toxiproxy를 거쳐요.

📖 용어: Toxiproxy
두 프로그램 사이에 끼워 넣는 TCP 프록시입니다. HTTP API로 "toxic"을 걸면 지연, 대역폭 제한, 연결 끊기 같은 장애를 그 경로에만 만들어요. 앱은 Postgres 대신 Toxiproxy 주소로 접속할 뿐이라 코드는 그대로입니다.
그림 1. 하나는 경로 전체를 느리게 하고, 하나는 깃발 꽂힌 요청만 실패시킨다

버전은 실습-1에 아래를 더했어요. 실습 코드는 GitHub 저장소의 labs/observability/tracing-04-chaos에 있습니다.

2. 300ms를 넣고 원인 스팬을 찾는다

Toxiproxy의 inventory-db 경로에 latency toxic을 걸었어요. Postgres에서 재고 서비스로 돌아오는 데이터(downstream)를 300ms씩 늦춥니다.

# ① 지연 없음: 부하를 주고 스팬별 시간 보기 docker compose --profile load run --rm -e DURATION=30s load && sleep 12 && python3 breakdown.py 50 # ② 지연 넣고 같은 순서로 curl -XPOST localhost:25005/proxies/inventory-db/toxics \ -d '{"name":"db-latency","type":"latency","stream":"downstream","attributes":{"latency":300,"jitter":0}}' docker compose --profile load run --rm -e DURATION=30s load && sleep 12 && python3 breakdown.py 50 # ③ 지연 빼기 curl -XDELETE localhost:25005/proxies/inventory-db/toxics/db-latency # breakdown.py 50 은 최근 50초 주문 트레이스의 스팬별 중앙값, p90 을 낸다

지연이 없을 때와 있을 때 k6로 30초씩 이어서 주문을 넣었어요(VU 5개, 요청 사이 0.2초). k6가 잰 주문 응답 시간과, 같은 구간의 트레이스를 모아 스팬별로 걸린 시간을 낸 결과(breakdown.py)입니다.

지연 없음 300ms 지연 k6 주문 응답 (중앙값 / p90) 36.9ms / 53.0ms 342.2ms / 358.1ms k6 처리량 21.3건/초 8.9건/초 스팬별 중앙값 order POST /orders 36.6ms 341.9ms order GET (재고 호출) 2.3ms 304.2ms inventory GET /stock/{sku} 1.4ms 303.1ms inventory SELECT shop.stock 0.5ms 301.6ms ← 여기서 늘었다 order POST (결제 호출) 36.3ms 37.7ms payment POST /payments 35.4ms 36.1ms (스팬 집계에 쓴 트레이스: 지연 없음 558개, 300ms 지연 275개. Tempo 검색이 돌려준 만큼)

트레이스를 위에서부터 따라 내려가면 늘어난 시간이 어디서 왔는지 보여요. 주문 전체가 305ms 늘었고, 재고 호출이 302ms, 재고 서버 스팬이 302ms, 그 안의 SELECT shop.stock이 301ms 늘었습니다. 결제 쪽은 그대로예요. 늘어난 시간이 사라지지 않고 내려가는 마지막 스팬이 원인 자리입니다. 이번에는 JDBC 스팬이었고, 그 스팬의 server.address 속성이 toxiproxy였으니 DB 자체보다 그 앞 경로를 의심할 수 있어요.

스팬 하나하나를 열지 않고 TraceQL 메트릭으로 한 번에 좁히는 방법도 있어요. 별도로 30초 돌린 지연 구간에서 CLIENT 스팬의 중앙값을 서비스와 이름별로 냈습니다.

{ kind = client } | quantile_over_time(duration, .5) by (resource.service.name, name) inventory SELECT shop.stock 0.380s inventory shop 0.380s order GET 0.383s order POST 0.041s

어느 서비스의 어느 호출이 느린지는 바로 보이지만 값은 0.380초예요. 스팬을 직접 모아 낸 중앙값은 0.30초 남짓이었습니다. 실습-1에서 본 것과 같은 일로 보여요. 이 함수는 원래 값이 아니라 버킷으로 근사한 분포에서 백분위를 냅니다. 어디가 느린지 고르는 데 쓰고, 얼마나 느린지는 스팬에서 확인하는 게 안전해요.

📖 용어: TraceQL 메트릭
TraceQL로 고른 스팬에서 개수, 비율, 백분위 같은 시계열을 바로 계산하는 Tempo 기능입니다. | quantile_over_time(duration, .5) by (...)는 고른 스팬의 길이 중앙값을 묶음별로 냅니다. 이 실습은 Tempo의 local-blocks 설정을 켜 둬서 쓸 수 있었어요.

3. 300ms를 넣었는데 600ms가 걸렸다

부하를 끄고 지연을 건 채 주문을 2초 간격으로 세 건 넣었더니 1.22초, 0.72초, 0.68초가 걸렸어요. 첫 건은 트레이스를 열어 보지 않아 이 글에서는 설명하지 않습니다. 나머지 두 건도 300ms를 넣었는데 두 배가 넘어요. 마지막 건(0.68초)을 열어 봤어요.

그림 2. SELECT 앞에 이름이 "shop"뿐인 스팬이 하나 더 있고, 그것도 300ms다

재고 서버 스팬 아래에 JDBC 스팬이 두 개 있었어요. SELECT shop.stock(304ms) 앞에 이름이 shop뿐인 스팬(302ms)이 하나 더 있습니다. 속성을 보니 db.statement가 빈 문자열이었어요. 빈 SQL을 누가 보냈을까요.

원인은 커넥션 풀의 검증이었습니다. HikariCP는 풀에서 커넥션을 꺼낼 때, 그 커넥션이 마지막으로 쓰인 지 500ms(aliveBypassWindowMs 기본값)가 넘었으면 살아 있는지 확인해요. 확인 방법은 JDBC의 Connection.isValid()이고, Postgres 드라이버는 이 호출에서 빈 쿼리를 서버에 보냅니다. 두 소스를 실습에 쓴 버전으로 확인했어요.

📖 용어: 커넥션 풀 (HikariCP)
DB 연결을 미리 몇 개 열어 두고 요청마다 빌려 쓰고 돌려받는 장치입니다. 스프링 부트의 기본 풀이 HikariCP예요. 빌려줄 때 그 연결이 아직 살아 있는지 확인하는 단계가 있습니다.
// HikariCP 7.0.2 HikariPool.java aliveBypassWindowMs = Long.getLong("com.zaxxer.hikari.aliveBypassWindowMs", MILLISECONDS.toMillis(500)); ... elapsedMillis(poolEntry.lastAccessed, now) > aliveBypassWindowMs && isConnectionDead(...) // pgjdbc 42.7.13 PgConnection.isValid() ((PgStatement)checkConnectionQuery).executeWithFlags("", QueryExecutor.QUERY_EXECUTE_AS_SIMPLE);

빈 쿼리도 DB까지 다녀오는 왕복이라 300ms가 한 번 더 붙었어요. 에이전트는 이걸 SQL이 비어 있는 JDBC 스팬으로 남겼고, SQL에서 연산과 테이블을 뽑을 수 없으니 이름이 DB 이름 shop만 남은 겁니다.

그래서 같은 지연이 트래픽에 따라 다르게 보였어요. 2절의 지연 구간(부하 30초)에서는 이 스팬이 275개 트레이스 중 13개에만 있었습니다. 요청이 0.2초마다 들어오니 커넥션이 500ms 안에 다시 쓰여서 검증을 건너뛴 거예요. 한가할 때 띄엄띄엄 오는 요청은 매번 검증을 거쳐 DB 왕복 지연을 두 번 냅니다. "새벽에만 API가 느리다"는 현상이 이런 모양일 수 있어요.

💡 실무에서는: DB 경로가 느릴 때 트레이스에서 볼 것
• 이름이 DB 이름뿐인 JDBC 스팬이 있으면 db.statement를 확인해요. 비어 있으면 커넥션 검증일 가능성이 커요
• 한가한 시간대 지연이 바쁜 시간대보다 크면 풀의 검증을 의심해요. keepaliveTime(HikariCP 7.0.2 기본 2분)으로 쉬는 커넥션을 미리 확인해도 꺼낼 때의 500ms 검증은 그대로예요. 소스상 keepalive 확인은 마지막 사용 시각을 갱신하지 않거든요. 검증 간격은 JVM 시스템 속성 com.zaxxer.hikari.aliveBypassWindowMs로 바꿀 수 있지만, 늘리면 죽은 커넥션을 늦게 알아채요(이번 실습에서는 바꿔 보지 않았어요)
• 지연 실험은 부하가 있을 때와 없을 때 둘 다 해요. 이번처럼 결과가 두 배 차이 날 수 있어요

4. baggage 깃발로 요청 하나만 실패시킨다

6편은 결제 서버를 통째로 죽이는 대신, baggage에 chaos=payment-timeout 같은 깃발을 실은 요청에만 장애를 일으키면 폭발 반경이 요청 하나가 된다고 했어요. 그 미들웨어를 결제 서비스에 서블릿 필터로 만들었습니다. 6편의 타임아웃 대신, 결과를 세기 쉬운 503 실패(chaos=payment-fail)로 바꿨어요.

📖 용어: W3C baggage
요청에 임의의 키-값을 실어 하위 서비스까지 전달하는 HTTP 헤더 규격입니다. baggage: chaos=payment-fail,tier=gold처럼 씁니다. traceparent와 별개의 규격이지만, OTel 에이전트는 기본 전파 방식(tracecontext,baggage)에 둘 다 넣어 같이 실어 나릅니다.
// payment 서비스 ChaosFilter (요약) String flag = Baggage.current().getEntryValue("chaos"); // 에이전트가 헤더를 풀어 둔 컨텍스트에서 꺼낸다 if (flag != null) Span.current().setAttribute("chaos.flag", flag); if ("payment-fail".equals(flag)) { Span.current().setAttribute("chaos.injected", true); res.setStatus(503); // 깃발이 있을 때만 실패 return; } chain.doFilter(req, res);

결제 서비스는 헤더를 직접 파싱하지 않아요. 에이전트가 들어온 baggage 헤더를 풀어 현재 컨텍스트에 넣어 두고, 필터는 Baggage.current()로 꺼내기만 합니다. 주문 서비스는 아무것도 하지 않았어요. 주문의 에이전트가 받은 baggage를 결제 호출에 다시 실어 보냈습니다. 깃발을 단 주문과 안 단 주문을 하나씩 넣었어요.

curl -XPOST localhost:25003/orders -H 'Content-Type: application/json' \ -H 'baggage: chaos=payment-fail' -d '{"sku":"C-300","qty":1}' {"result":"payment_failed"} 502 curl -XPOST localhost:25003/orders -H 'Content-Type: application/json' -d '{"sku":"C-300","qty":1}' {"result":"ok"} 200
그림 3. 실패를 주입한 스팬에 깃발 값을 남겨 두면, 진짜 장애와 실험을 트레이스에서 구분할 수 있다

"나머지 요청은 정말 멀쩡한가"를 보려고, k6로 30초 동안 평범한 주문을 넣는 사이에 깃발 단 주문 10건을 2초 간격으로 섞었어요. 그 1분 구간을 TraceQL로 셌습니다.

깃발 단 curl 10건 → 10건 모두 502 k6 642건 → 실패 129건, 전부 재고 없는 상품(B-200)의 409. 502 는 0건 { resource.service.name="payment" && kind=server } 523 { resource.service.name="payment" && kind=server && status=error } 10 { resource.service.name="payment" && span.chaos.flag="payment-fail" } 10

결제까지 간 523건(k6 513건 + 깃발 10건) 중 에러는 깃발 단 10건뿐이었어요. 6편이 말한 대로 폭발 반경이 요청 단위로 줄었습니다.

📖 용어: 폭발 반경 (blast radius)
장애나 실험이 영향을 주는 범위입니다. 서버를 통째로 내리면 그 서버를 거치는 모든 요청이 반경 안에 들고, 깃발로 고른 요청에만 주입하면 그 요청들만 반경 안에 들어요.

실패한 스팬마다 chaos.flag가 남아 있으니, 대시보드의 에러가 실험 때문인지 진짜 장애인지 TraceQL 조건 하나로 가를 수 있어요.

5. 바깥에서 온 깃발도 그대로 통과했다

4절의 첫 curl을 다시 보세요. 우리는 주문 서비스의 공개 주소에 헤더 한 줄을 붙였을 뿐이에요. 바깥의 누구든 같은 헤더로 결제를 실패시킬 수 있다는 뜻입니다. 6편이 "들어오는 baggage는 남이 쓴 값"이라고 경고한 그대로였어요. 주문 서비스의 에이전트는 바깥에서 온 baggage를 우리 것과 구분하지 않고 하위로 넘겼습니다. 깃발 말고 다른 값도 마찬가지였어요.

# 결제 서비스가 받은 값은 ChaosFilter 가 찍은 로그로 본다 docker compose logs payment | grep "받은 baggage" # 로그의 바이트 수는 받은 항목을 key=value 로 이어 붙인 문자열의 길이다 보낸 헤더 (주문 서비스로) 결제 서비스가 받은 baggage user.email=someone%40example.com,tier=gold → tier=gold,user.email=someone@example.com pad=x...x (값 4,000바이트) → 1건, 4,004바이트 그대로 pad=x...x (값 7,000바이트) → 1건, 7,004바이트 그대로 pad=x...x (값 9,000바이트) → 주문 서비스가 400 으로 거절 k0=v,...,k99=v (100개) → 64건만 도착

이메일 같은 값도, 7KB짜리 값도 결제까지 그대로 실려 갔어요. 이 값은 주문 서비스가 부르는 모든 하위 호출에 붙어 다닙니다. 9,000바이트에서 막힌 건 baggage 규칙이 아니라 톰캣의 요청 헤더 크기 제한(스프링 부트 기본 8KB)이었어요. 100개를 보냈는데 64개만 도착한 건 OTel 자바 SDK의 baggage 전파기가 W3C 권고 한도(항목 64개, 8,192바이트)로 잘랐기 때문입니다. 헤더 하나에 100개가 들었을 때는 파서가 64개째에서 멈추고 나머지를 로그 한 줄 없이 버려요(SDK 1.66.0 소스. FINE 로그는 헤더 여러 개를 합쳐 한도를 넘을 때만 남깁니다). 6편이 "넘치면 구현이 항목을 버릴 수 있다"고 한 부분이 이렇게 나타났습니다.

입구에서 깃발을 걸러 낸다

그래서 입구인 주문 서비스에 필터를 하나 더 넣었어요. X-Chaos-Token 헤더가 정해 둔 값과 맞을 때만 chaos 깃발을 살려 두고, 아니면 깃발을 뺀 baggage를 현재 컨텍스트로 바꿔 끼운 채 다음으로 넘깁니다. 하위 호출은 에이전트가 현재 컨텍스트의 baggage를 싣고 나가니, 바꿔 끼운 쪽이 나가요.

// order 서비스 BaggageGuard (요약) Baggage baggage = Baggage.current(); boolean trusted = !token.isEmpty() && token.equals(req.getHeader("X-Chaos-Token")); if (baggage.getEntryValue("chaos") != null && !trusted) { Span.current().setAttribute("chaos.rejected", baggage.getEntryValue("chaos")); Baggage cleaned = baggage.toBuilder().remove("chaos").build(); try (Scope ignored = Context.current().with(cleaned).makeCurrent()) { chain.doFilter(req, res); // 깃발 뺀 baggage 로 계속 } return; } chain.doFilter(req, res);
BAGGAGE_GUARD=true CHAOS_TOKEN=lab-token docker compose up -d order curl -XPOST localhost:25003/orders -H 'Content-Type: application/json' \ -H 'baggage: chaos=payment-fail,tier=gold' -d '{"sku":"C-300","qty":1}' curl -XPOST localhost:25003/orders -H 'Content-Type: application/json' -H 'X-Chaos-Token: lab-token' \ -H 'baggage: chaos=payment-fail,tier=gold' -d '{"sku":"C-300","qty":1}' 토큰 없이 'baggage: chaos=payment-fail,tier=gold' → 200, 200, 200 결제가 받은 baggage: tier=gold 토큰과 함께 같은 헤더 → 502, 502, 502 결제가 받은 baggage: chaos=payment-fail,tier=gold
그림 4. 같은 헤더라도 토큰이 없으면 깃발만 떼고 나머지 baggage는 넘긴다

토큰 없이 온 깃발은 입구에서 떨어지고, 주문 스팬에는 chaos.rejected가 남았어요. 다만 이 필터는 chaos 키만 봅니다. tier=gold나 이메일 같은 다른 키는 여전히 하위로 흘러가요. 6편이 인용한 W3C 스펙의 프라이버시 절은 신뢰 경계에서 baggage를 벗겨 내라고 권합니다. 운영이라면 입구에서 허용 목록에 있는 키만 남기는 쪽이 맞아요.

⚠️ 주의: baggage로 분기하는 코드는 입구에서 키를 거르는 코드와 한 묶음이에요
• 서비스 안쪽에 baggage로 동작을 바꾸는 코드(실패 주입, 라우팅, 기능 플래그)를 넣는 순간, 입구에 그 키를 걸러 내는 코드가 같이 있어야 해요
• 게이트웨이나 입구 서비스에서 허용한 키만 남기고, 실험용 키는 서명이나 토큰으로 자격을 확인해요
• 주입한 스팬에는 깃발 값을 속성으로 남겨요. 실험 중에 에러율 알람이 울려도 바로 가를 수 있어요
✍️ 오늘의 요약
DB 경로에 300ms를 넣자 트레이스의 늘어난 시간이 주문, 재고 호출, 재고 서버를 거쳐 JDBC 스팬에서 멈췄고, 거기가 원인 자리였다. 한가할 때는 커넥션 풀의 검증용 빈 쿼리가 왕복을 하나 더 만들어 같은 지연이 두 배로 보였다. baggage 깃발로 만든 실패 주입은 깃발 단 10건만 실패시키고 나머지 513건은 건드리지 않았다.

그런데 그 깃발은 바깥에서도 꽂혔다. 에이전트는 들어온 baggage를 가리지 않고 실어 나르니, baggage로 동작을 바꾸는 코드는 입구에서 그 키를 거르는 코드와 함께 들어가야 한다.
