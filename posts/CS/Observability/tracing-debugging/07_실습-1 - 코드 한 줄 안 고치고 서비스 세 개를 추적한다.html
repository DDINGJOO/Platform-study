분산 추적이 필요하다는 데는 다들 동의합니다. 그런데 막상 우리 서비스에 붙이려고 하면 첫 질문에서 멈춰요. "그래서 코드 어디를 고쳐야 하지?" 컨트롤러마다 스팬을 열고, HTTP 클라이언트마다 헤더를 넣고, DB 호출마다 감싸야 할 것 같아서요.

이번 글은 반대 방향에서 시작합니다. 스프링 부트 서비스 세 개를 띄우는데, 애플리케이션 코드에는 OpenTelemetry 의존성을 하나도 넣지 않아요. 실행할 때 자바 에이전트만 붙이고, 그것만으로 트레이스가 어디까지 나오는지, 어디서부터는 안 나오는지를 직접 돌려서 확인합니다. 화면과 숫자는 전부 실제로 돌린 결과예요.

🧭 이 글에서 확인할 것
• 코드를 안 고치면 트레이스에 무엇이 남는가?
• 서비스 사이에 trace ID는 누가 실어 보내는가?
• 결제가 실패하면 트레이스는 어떻게 보이고, 재고 부족은 왜 안 보이는가?
• 에이전트를 붙이는 값은 얼마인가?

1. 실습 환경: 주문, 재고, 결제

주문 서비스가 주문을 받으면 재고 서비스에 재고를 묻고, 재고가 있으면 결제 서비스를 호출합니다. 재고 서비스는 H2 인메모리 DB에서 재고를 읽어요. 세 서비스는 같은 스프링 부트 코드에서 프로필만 바꿔 띄웁니다. 트레이스는 OTel Collector를 거쳐 Tempo에 쌓이고, Grafana로 봅니다.

그림 1. 앱 세 개는 그대로, 관측 쪽 부품만 옆에 붙였다
📖 용어: OTel 자바 에이전트 (OpenTelemetry Java agent)
JVM이 클래스를 읽어 들일 때 바이트코드를 고쳐 끼우는 jar 파일입니다. 톰캣, HTTP 클라이언트, JDBC 같은 라이브러리의 입구와 출구에 스팬을 여닫는 코드를 넣어서, 앱 코드를 고치지 않고도 트레이스가 나와요.
📖 용어: OTel Collector
앱이 보낸 텔레메트리를 받아 묶고, 거르고, 저장소로 보내는 중간 프로세스입니다. 앱은 Collector 주소만 알면 되고, 저장소를 Tempo에서 다른 것으로 바꿔도 앱 설정은 그대로예요.

쓴 버전은 아래와 같아요. Tempo만 한 단계 이전 라인인 2.10을 골랐습니다. 3.x는 분산 배포에서 Kafka를 거치는 구조로 바뀌었고, 단일 컨테이너(monolithic) 모드는 Kafka 없이도 뜹니다. 다만 설정 예시와 자료가 2.x 쪽에 훨씬 많아서 실습은 2.10으로 맞췄어요.

Spring Boot 4.1.1 (Java 21) OTel Java agent 2.32.0 OTel Collector 0.162.0 (contrib) Grafana Tempo 2.10.8 Prometheus 3.15.0 Grafana 13.2.3 k6 2.3.0 실행 환경 Docker Desktop, Apple M5 Pro

앱의 build.gradle 의존성은 이게 전부입니다. OpenTelemetry라는 글자가 주석에만 있어요.

// OpenTelemetry 의존성은 하나도 없다. 트레이스는 실행할 때 붙이는 자바 에이전트가 만든다. dependencies { implementation 'org.springframework.boot:spring-boot-starter-webmvc' implementation 'org.springframework.boot:spring-boot-starter-restclient' implementation 'org.springframework.boot:spring-boot-starter-jdbc' runtimeOnly 'com.h2database:h2' }

실습 코드는 GitHub 저장소(DDINGJOO/Platform-study)의 labs/observability에 있습니다. 앱 빌드까지 이미지 안에서 하니 Docker만 있으면 돼요. 아래 명령은 실패도 지연도 없는 기본 상태를 띄웁니다. 3절과 4절의 지연과 실패는 4절의 명령으로 넣어요.

git clone https://github.com/DDINGJOO/Platform-study.git cd Platform-study/labs/observability/tracing-01-zero-code docker compose up -d --build docker compose --profile load run --rm load # k6로 60초 동안 주문 # Grafana: http://localhost:3000 → Explore → Tempo

2. 에이전트는 환경변수로 붙는다

에이전트 jar는 이미지 안에 넣어 두기만 했어요. 켜는 건 compose 파일의 환경변수입니다. compose 파일에서는 세 서비스가 공통 값을 YAML 앵커로 나눠 쓰는데, order 서비스에 실제로 들어가는 값을 합쳐 보면 이렇습니다.

environment: SPRING_PROFILES_ACTIVE: order # 앱 쪽 설정. 어떤 컨트롤러를 띄울지 정한다 JAVA_TOOL_OPTIONS: -javaagent:/otel/opentelemetry-javaagent.jar OTEL_SERVICE_NAME: order OTEL_EXPORTER_OTLP_ENDPOINT: http://otel-collector:4318 OTEL_METRICS_EXPORTER: none # 이번 실습은 트레이스만 본다 OTEL_LOGS_EXPORTER: none
📖 용어: JAVA_TOOL_OPTIONS
JVM이 시작할 때 읽어서 명령줄 옵션에 덧붙이는 환경변수입니다. 이미지의 ENTRYPOINT를 고치지 않고 -javaagent를 넣을 수 있어서, 같은 이미지로 에이전트를 켜고 끌 수 있어요.

Dockerfile의 실행 명령은 java -jar /app/shop.jar 그대로예요. 에이전트를 빼고 싶으면 JAVA_TOOL_OPTIONS 한 줄만 지우면 됩니다. 6절에서 기동 시간을 비교할 때도 같은 이미지를 docker run으로 띄우면서 이 값만 비워서 껐어요.

⚠️ 주의: 서비스 이름을 꼭 준다
OTEL_SERVICE_NAME을 빼면 OpenTelemetry 규약상 서비스 이름이 unknown_service:java가 됩니다. 이 실습처럼 같은 이미지를 세 번 띄우면 세 서비스가 한 이름으로 섞여서, 트레이스에서 누가 누구를 불렀는지 구분할 수 없어요.

3. 주문 한 건이 스팬 여섯 개가 됐다

주문을 하나 넣고 Tempo에서 그 트레이스를 꺼냈습니다. 스팬을 시작 시각 순으로 찍는 작은 스크립트로 본 결과예요. 이때는 결제에 250ms 지연을 넣어 둔 상태였습니다(넣는 명령은 4절에 있어요).

python3 ../scripts/show-trace.py # Python 3 필요. 인자가 없으면 결제까지 간 최근 트레이스
시작 걸린 시간 서비스 종류 이름 계측 모듈 + 0.0ms 297.9ms order SERVER POST /orders io.opentelemetry.tomcat-10.0 + 0.9ms 2.7ms order CLIENT GET io.opentelemetry.java-http-client + 1.6ms 1.6ms inventory SERVER GET /stock/{sku} io.opentelemetry.tomcat-10.0 + 2.5ms 0.1ms inventory CLIENT SELECT shop.stock io.opentelemetry.jdbc + 3.9ms 293.3ms order CLIENT POST io.opentelemetry.java-http-client + 5.0ms 291.8ms payment SERVER POST /payments io.opentelemetry.tomcat-10.0
그림 2. Grafana에서 본 같은 트레이스. 300ms 중 290ms가 결제였다

오른쪽 열의 계측 모듈 이름을 보면 에이전트가 무엇을 했는지 보여요. 톰캣이 요청을 받는 자리, JDK HttpClient가 요청을 보내는 자리, JDBC가 쿼리를 보내는 자리에 스팬이 생겼습니다. 우리가 쓴 컨트롤러 클래스 이름은 어디에도 없어요. 에이전트는 우리 코드가 아니라 우리 코드가 쓰는 라이브러리를 계측합니다.

📖 용어: 스팬 종류 (span kind)
스팬이 요청을 받는 쪽인지(SERVER), 보내는 쪽인지(CLIENT)를 나타냅니다. 서비스 하나를 건널 때마다 보내는 쪽 CLIENT 스팬과 받는 쪽 SERVER 스팬이 한 쌍으로 생겨요.

돌려 보기 전에는 예상하지 못한 점이 세 가지 있었어요.

첫째, 클라이언트 스팬 이름이 그냥 GET, POST입니다. 서버 스팬은 GET /stock/{sku}처럼 경로 템플릿이 붙는데 클라이언트 쪽은 메서드뿐이에요. 버그가 아니라 HTTP 시맨틱 규약이 정한 동작입니다. 규약은 카디널리티가 낮은 대상 이름을 쓸 수 없으면 스팬 이름을 {method}로 하라고 해요. 서버는 스프링이 라우트 템플릿을 알려 주지만, 클라이언트는 /stock/A-100처럼 값이 들어간 URL밖에 몰라서 그걸 이름에 넣으면 sku마다 이름이 달라집니다. 대상은 스팬 속성 url.full과 server.address에서 보면 돼요.

둘째, 컨트롤러 스팬이 없습니다. 에이전트가 스프링 MVC를 지원하는데도 OrderController.order 같은 스팬이 안 생겼어요. 스프링 MVC 계측은 기본으로 서버 스팬에 라우트 정보만 채우고, 컨트롤러 스팬은 otel.instrumentation.common.experimental.controller-telemetry.enabled를 켜야 만듭니다. 이름에 experimental이 붙은 옵션이라 기본값이 꺼져 있어요.

셋째, RestClient가 JDK HttpClient로 나갔습니다. 아파치 HttpClient 같은 라이브러리를 클래스패스에 넣지 않았기 때문이에요. 계측 모듈 이름이 java-http-client인 걸 보고 알았습니다. 운영 서비스에서 HTTP 클라이언트 라이브러리를 바꾸면 이 줄이 바뀌고, 에이전트가 그 라이브러리를 지원하지 않으면 CLIENT 스팬이 통째로 빠져요.

trace ID는 누가 실어 보냈나

재고 서비스 컨트롤러에는 들어온 traceparent 헤더를 로그로 찍는 줄을 하나 넣어 뒀어요. 앱은 이 헤더를 만들지 않았습니다. 주문 서비스의 에이전트가 JDK HttpClient의 요청에 붙여 보낸 거예요.

INFO lab.shop.InventoryController : traceparent=00-913d35de3e0e379ccb3e647a0472b515-68965e053ce1d08f-03 00 버전 913d35de3e0e379ccb3e647a0472b515 trace ID (트레이스 전체에서 같다) 68965e053ce1d08f 부모 스팬 ID (order 의 CLIENT 스팬) 03 플래그

3편에서 본 헤더와 끝자리가 달라요. 3편 예시는 01이었는데 여기는 03입니다. W3C Trace Context Level 2가 플래그의 두 번째 비트에 random-trace-id라는 이름을 붙였어요. trace ID의 오른쪽 7바이트 이상을 무작위로 만들었다는 표시입니다. 01(샘플링됨)과 02(무작위 ID)가 둘 다 켜져서 03이 됐어요.

4. 결제를 일부러 망가뜨려 본다

결제 서비스는 환경변수로 실패율과 지연을 받게 만들어 뒀어요. 결제의 20%를 500으로 실패시키고 250ms씩 늦춘 뒤 부하를 줬습니다.

PAYMENT_FAIL_RATE=0.2 PAYMENT_SLOW_MS=250 docker compose up -d payment docker compose --profile load run --rm load

실패한 주문 하나를 열면 이렇게 보입니다.

그림 3. 실패 하나에 빨간 표시가 셋. 재고 쪽 가지는 멀쩡하다

에러 표시는 결제 서버 스팬(500), 주문의 결제 호출 스팬(500), 주문 서버 스팬(502) 세 곳에 붙었어요. 재고 쪽 가지는 정상이라서 원인이 결제 쪽이라는 게 바로 보입니다. 로그만 있었다면 세 서비스의 로그를 시각으로 맞춰 봐야 알 수 있는 내용이에요.

여기서 숫자를 세 보면 함정이 하나 나옵니다. 이보다 먼저, 지연 없이 실패율만 30%로 둔 실행(PAYMENT_FAIL_RATE=0.3, k6 40초, 846건)이 있었어요. 그 실행 구간에서 TraceQL로 조건에 맞는 스팬 수를 세고, 구간 전체를 더했습니다.

{ status = error } | count_over_time() → 612 스팬 { span.http.response.status_code = 409 } | count_over_time() → 158 스팬 (재고 부족) k6가 센 실패 응답 → 362 건
📖 용어: TraceQL
Tempo의 트레이스 질의 언어입니다. { 조건 } 안에 스팬 속성 조건을 적으면 조건에 맞는 스팬이 든 트레이스를 찾아 줘요. | count_over_time()을 붙이면 맞는 스팬 수를 시계열로 셉니다.

k6가 센 실패 362건은 재고 부족(409) 158건과 결제 실패(502) 204건을 합친 수예요. 결제 실패 하나에 에러 스팬이 세 개씩 생기니 204 × 3 = 612입니다. 에러 스팬 수는 실패한 요청 수가 아닙니다. 실패가 지나간 스팬 수만큼 늘어나요.

반대로 재고 부족 158건은 에러 스팬에 하나도 안 잡혔어요. 409를 돌려준 주문 서버 스팬의 상태가 비어 있었습니다. 이것도 HTTP 시맨틱 규약대로예요. 규약은 4xx 응답일 때 SERVER 스팬의 상태는 비워 두고, CLIENT 스팬은 에러로 하라고 정합니다. 4xx는 호출한 쪽이 잘못 요청한 것이지 서버가 고장 난 게 아니라는 판단이에요. 그런데 "재고가 없어서 주문이 안 됐다"가 사업상 실패라면, 그건 트레이스의 에러 집계로는 안 보입니다.

💡 실무에서는: 에러율을 트레이스로 셀 때
• 요청 단위 에러율은 진입점 SERVER 스팬만 세요. TraceQL이면 { resource.service.name = "order" && kind = server && status = error }
• 4xx 중 사업상 실패로 볼 것(재고 부족, 한도 초과)은 따로 세요. 상태 코드 조건을 쓰거나, 코드에서 스팬에 사업 결과 속성을 달아야 해요
• k6, 로드밸런서, 트레이스는 실패를 세는 기준이 서로 달라요. 숫자가 안 맞으면 기준부터 확인해요

5. 서비스 지도는 따라 나온다

Tempo에는 받은 스팬으로 지표를 만들어 내는 metrics-generator라는 기능이 있어요. 이 실습은 stack/tempo.yaml의 metrics_generator와 overrides에서 켰습니다. 켜 두면 Tempo가 스팬의 CLIENT/SERVER 짝을 맞춰 "누가 누구를 몇 번, 얼마나 걸려 불렀나"를 지표로 만들어 Prometheus로 보냅니다. Grafana는 그 지표로 서비스 그래프를 그려요.

그림 4. 아무도 그리지 않은 아키텍처 그림이 스팬에서 나왔다

노드 두 개는 우리가 띄운 서비스가 아니에요. user는 부모 CLIENT 스팬이 없는 요청, 곧 바깥에서 들어온 요청을 뜻합니다. shop은 H2 데이터베이스 이름이에요. JDBC 스팬의 DB 정보로 가상 노드를 만든 겁니다. 처음에는 결제 서비스에서 shop으로 가는 선도 하나 보였어요. 처음 설정에서는 세 서비스가 모두 기동할 때 스키마 초기화 SQL을 돌렸기 때문입니다. 초기화를 재고 서비스에서만 돌게 바꾸자 선이 사라졌어요. 주문 서비스도 같은 SQL을 돌렸는데 왜 그쪽 선은 안 보였는지는 확인하지 못했습니다. 서비스 그래프는 설계도가 아니라 실제로 일어난 호출을 그립니다.

결제 p90이 486ms? k6는 주문 전체가 305ms라고 했는데

서비스 그래프 화면에는 노드 그림 위에 엔드포인트별 표도 같이 나옵니다.

그림 5. 결제 p90이 486ms라고 나온다

결제의 Duration (p90)이 486ms예요. 그런데 k6가 잰 주문 전체의 p90은 305ms 안팎이었습니다. 결제가 주문 전체보다 느릴 수는 없어요. Prometheus에서 결제 지연 히스토그램의 버킷을 직접 봤습니다. 스택을 새로 띄우고 실패율 20%, 지연 250ms로만 돌린 실행(1,029건)이 끝난 시점의 값이에요.

le(초) 누적 건수 0.128 0 0.256 0 0.512 828 ← 828건 전부가 256~512ms 버킷 하나에 1.024 828 histogram_quantile(0.9, ...) = 0.256 + 0.9 × (0.512 − 0.256) = 0.4864

Tempo의 span-metrics 기본 버킷은 2ms부터 두 배씩 늘어나서 0.256초 다음이 0.512초예요. 결제는 모두 270ms에서 300ms 남짓 사이였는데, 버킷 안에서 값이 고르게 퍼져 있다고 가정하고 선형 보간을 하니 486ms가 나왔습니다. 버킷 하나에 몰린 분포에서 백분위는 버킷 경계가 정합니다. 「집계와 분포」 시리즈에서 다룬 문제가 그대로 나타난 거예요. 표에 찍힌 주문의 p90 479ms도 같은 버킷에 걸려서 커진 값이에요. 이 범위를 정확히 보고 싶으면 Tempo 설정의 histogram_buckets에 서비스 지연대에 맞는 경계를 넣어야 합니다.

📖 용어: 히스토그램 버킷 (histogram bucket)
지연 시간을 "0.256초 이하 몇 건, 0.512초 이하 몇 건"처럼 구간별 누적 건수로 저장한 것입니다. 원래 값은 버리기 때문에, 백분위는 구간 안을 추정해서 계산해요.

6. 공짜는 아니다: 기동 시간과 에이전트가 모르는 것

같은 이미지를 에이전트를 켜고 끄며 세 번씩 띄워 기동 시간을 쟀습니다(scripts/startup-time.sh). 스프링 로그의 두 숫자를 같이 봤어요.

스프링 컨텍스트 기동 JVM 시작부터 기동 완료까지 에이전트 끔 0.76 / 0.76 / 0.88초 0.93 / 0.93 / 1.06초 에이전트 켬 1.16 / 1.02 / 1.13초 2.46 / 2.33 / 2.39초

JVM 기준으로 약 1.4초가 늘었고, 그중 스프링 컨텍스트 구간에서 늘어난 건 0.3초 정도예요. 나머지 1초 남짓은 스프링이 시작하기 전, 에이전트가 계측 모듈을 준비하는 데 썼습니다. 오래 떠 있는 서버에서는 문제가 안 되지만, 짧게 떴다 내려가는 배치나 빠른 스케일 아웃이 중요한 서비스라면 계산에 넣어야 해요. 요청당 지연이나 CPU 비용은 이번 실습에서 재지 않았습니다.

그리고 에이전트가 모르는 것이 있어요. 트레이스에는 POST /orders가 300ms 걸렸다는 건 있지만, 어떤 상품을 몇 개 주문했는지, 재고 부족으로 거절됐는지는 없습니다. 에이전트는 라이브러리 경계만 보기 때문에 사업 로직 안쪽의 의미는 알 수 없어요. 그 정보를 남기려면 결국 코드에서 스팬에 속성을 달아야 합니다.

💡 실무에서는: 에이전트를 운영에 넣을 때
• 에이전트 버전을 고정해요. Dockerfile에서 받는 버전이 바뀌면 스팬 이름과 속성이 바뀔 수 있고, 그 위에 만든 알람과 쿼리가 깨져요
• 필요 없는 계측은 꺼요. OTEL_INSTRUMENTATION_<이름>_ENABLED=false로 모듈 단위로 끌 수 있어요. 헬스체크처럼 요청이 잦은 경로가 있으면 먼저 확인해요
• 샘플링을 정해요. 이번 실습은 전부 저장했어요. 운영 트래픽을 전부 저장하면 저장 비용이 요청 수에 비례해서 늘어요
✍️ 오늘의 요약
환경변수 몇 줄로 붙인 자바 에이전트만으로 서비스 세 개를 잇는 트레이스, 에러 위치, 서비스 그래프까지 나왔다. 에이전트는 톰캣, HTTP 클라이언트, JDBC 같은 라이브러리 경계를 계측하고, 서비스 사이의 traceparent 헤더도 대신 실어 보낸다.

다만 숫자를 읽을 때는 기준을 확인해야 한다. 에러 스팬은 실패가 지나간 스팬 수만큼 늘어나고, 서버 스팬은 4xx를 에러로 표시하지 않으며, 버킷 하나에 몰린 백분위는 경계값을 따라간다. 에이전트는 경계까지만 보고, 경계 안쪽의 의미는 코드가 알려 줘야 한다.
