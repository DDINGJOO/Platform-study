주문 API는 202를 돌려줬고 로그에도 에러가 없습니다. 그런데 결제 기록이 하나 비어요. 트레이스를 열어 보니 주문 서비스가 Kafka에 메시지를 넣은 데서 끝나 있습니다. 결제 컨슈머가 그 메시지를 받았는지, 받았다면 어디서 멈췄는지는 이 화면에 없어요.

3편에서 트레이스는 메시지 헤더에 실려 큐를 건너고, 이을 때는 부모-자식과 span link 두 가지 고리가 있다고 했습니다. 이번 글은 그 말을 실제로 확인합니다. 실습-1처럼 앱 코드에는 계측 코드를 넣지 않고 OTel 자바 에이전트만 붙인 뒤, 에이전트가 Kafka 양쪽 스팬을 어떤 고리로 잇는지 Tempo에서 봤어요. 설정 하나에 따라 고리가 바뀌었고, 규약 문서가 권하는 기본값과 에이전트의 기본값이 달랐습니다.

🧭 이 글에서 확인할 것
• 에이전트는 producer 스팬과 consumer 스팬을 부모-자식으로 잇는가, span link로 잇는가?
• 메시징 시맨틱 규약이 권하는 모양과 에이전트 기본값은 같은가?
• 메시지를 묶음으로 받으면 트레이스는 어떻게 되나?
• 컨슈머가 다른 스레드로 일을 넘기면 어디서 끊기나?

1. 실습 환경: 주문, Kafka, 결제

주문 서비스는 주문을 받으면 결제를 HTTP로 부르지 않고 orders 토픽에 메시지를 넣은 뒤 바로 202를 돌려줍니다. 결제 서비스는 그 토픽을 구독하는 컨슈머예요. 메시지를 받으면 H2 DB에 결제 기록을 한 줄 넣습니다. Kafka는 브로커 하나로 띄웠어요.

그림 1. 주문과 결제 사이에 HTTP 대신 토픽이 있다
📖 용어: KRaft
Kafka가 클러스터 메타데이터를 ZooKeeper 없이 자체 합의 프로토콜로 관리하는 방식입니다. Kafka 4.0부터는 이 방식만 남았어요. 이번 실습은 한 프로세스가 브로커와 컨트롤러를 겸하는 단일 노드로 띄웠습니다.

2. 기본값: 결제가 주문의 자식으로 붙었다

아무 설정도 바꾸지 않고 주문을 하나 넣었습니다. 결과는 한 트레이스였어요.

시작 걸린 시간 서비스 종류 이름 + 0.0ms 8.0ms order SERVER POST /orders + 0.6ms 7.1ms order PRODUCER orders publish offset=2135 + 8.8ms 1.1ms payment CONSUMER orders process offset=2135 + 9.3ms 0.4ms payment CLIENT INSERT shop.payments
그림 2. 결제 컨슈머의 process 스팬이 주문의 publish 스팬 바로 아래에 붙었다

주문 쪽에는 PRODUCER 스팬 orders publish가, 결제 쪽에는 CONSUMER 스팬 orders process가 생겼어요. 계측 모듈 이름은 각각 kafka-clients-0.11과 spring-kafka-2.7이었습니다. 프로듀서는 Kafka 클라이언트 라이브러리에서, 컨슈머는 Spring의 리스너 컨테이너에서 잡았다는 뜻이에요. 그리고 process 스팬의 부모가 publish 스팬입니다. 링크는 하나도 없었어요.

📖 용어: PRODUCER / CONSUMER 스팬
메시지를 보내는 쪽과 받아 처리하는 쪽을 나타내는 스팬 종류입니다. HTTP의 CLIENT/SERVER와 달리, 보낸 쪽이 끝난 뒤에 받는 쪽이 한참 지나서 시작할 수 있어요. 그래서 두 스팬을 어떻게 이을지가 따로 정해져 있습니다.

헤더에 실려 간 traceparent를 컨슈머 쪽 에이전트가 꺼내 부모로 삼은 거예요. 3편에서 그린 그림 그대로입니다. 그런데 3편에는 이런 문장도 있었어요. "OpenTelemetry의 메시징 규약은 기본값을 link 쪽에 둔다." 규약 문서를 다시 열어 봤습니다.

For each message it accounts for, the "Process" or "Receive" span SHOULD link to the message's creation context. These conventions use spans links as the default mechanism to correlate producers and consumer(s). Exclusively for single messages scenarios, the "Process" span MAY use the message's creation context as its parent. It is NOT RECOMMENDED to use the message creation context as the parent of "Process" spans (by default) if processing happens in the scope of another span.

규약은 링크를 기본 수단으로 두고, process 스팬은 처리한 메시지마다 그 메시지를 만든 컨텍스트에 링크를 걸어야 한다(SHOULD)고 합니다. 부모로 삼는 건 메시지 한 건을 처리할 때만 허용(MAY)하고, 처리가 다른 스팬 안에서 일어나는 경우에는 기본으로 하지 말라(NOT RECOMMENDED)고 해요. 이번 리스너는 다른 스팬 안에서 돌지 않고 메시지도 한 건씩 받으니, 부모로 삼은 것 자체는 규약이 허용하는 범위예요. 어긋나는 곳은 링크입니다. 규약은 링크를 걸라고 하는데 에이전트 기본값에는 링크가 하나도 없었어요. 3편의 "규약은 link가 기본"은 규약 기준으로 맞고, 에이전트 기본값은 그 링크를 빠뜨린 모양이었습니다.

📖 용어: span link
스팬과 스팬을 부모-자식이 아닌 관계로 잇는 참조입니다. 부모는 하나뿐이지만 링크는 여러 개를 걸 수 있고, 다른 트레이스의 스팬도 가리킬 수 있어요. Grafana에서는 스팬 상세의 References 칸에 나옵니다.

규약 버전이 하나 뒤처져 있었다

속성을 보면 이유를 짐작할 수 있어요. 스팬 이름이 orders publish이고 속성이 messaging.operation=publish, messaging.kafka.consumer.group=payment였습니다. 지금 규약은 이름을 {operation.name} {destination} 순서로, 동작 종류는 messaging.operation.type에 send, process 같은 값으로 적게 해요. 에이전트 소스의 SemconvStability를 보니 메시징은 기본으로 v1.24.0 규약을 내고, 새 규약은 opt-in으로만 켜집니다. 메시징 규약이 아직 Development 단계라서, 규약 문서도 계측 쪽에 "안정판이 되기 전에는 기본으로 내는 버전을 바꾸지 말라"고 적어 뒀어요.

opt-in을 켜고 다시 넣어 봤습니다.

SEMCONV_OPT_IN=messaging docker compose up -d order payment # OTEL_SEMCONV_STABILITY_OPT_IN=messaging
+ 0.0ms 345.3ms order SERVER POST /orders (재시작 직후 첫 요청이라 느리다) + 227.6ms 95.1ms order PRODUCER send orders type=send + 354.5ms 25.4ms payment CONSUMER process orders type=process link→ 34ae3a8f../e14a23bd13b0a357 + 377.1ms 0.6ms payment CLIENT INSERT shop.payments

이름과 속성이 새 규약대로 바뀌었어요. 그리고 process 스팬에 링크가 하나 생겼습니다. 링크가 가리키는 e14a23bd13b0a357은 바로 위의 send orders 스팬이에요. 부모이면서 동시에 링크로도 걸린 겁니다. 규약이 권하는 "링크로 잇는다"를 지키면서 기존의 부모-자식 모양도 유지한 절충으로 보여요. 이 글의 나머지 실험은 기본값(opt-in 끔)으로 되돌려 돌렸습니다.

docker compose up -d order payment # SEMCONV_OPT_IN 없이 두 서비스를 다시 띄워 기본값으로

3. 새 트레이스가 시작되는 두 경우

에이전트 문서에는 이런 설정이 있어요. otel.instrumentation.messaging.experimental.receive-telemetry.enabled. 2.32.0에서는 이 이름이 deprecated가 됐고 otel.instrumentation.common.messaging.experimental.receive-telemetry.enabled로 바뀌었어요(에이전트 저장소 docs/instrumentation-list.yaml). 실습 compose는 옛 이름의 환경변수를 썼고 2.32.0에서는 그대로 동작했습니다. 설명은 "컨슈머 쪽이 새 트레이스를 시작하고, 프로듀서 트레이스와는 span link 하나로만 이어진다"입니다. 켜고 주문 세 건을 2초 간격으로 넣었어요.

RECEIVE_TELEMETRY=true docker compose up -d payment # 주문 세 건을 넣은 뒤 python3 show-trace.py # 주문 트레이스 python3 show-trace.py '{name="orders receive"}' # 결제 쪽 트레이스(TraceQL 로 골라 가장 최근 것)
# 주문 트레이스: publish 에서 끝난다 + 0.0ms 13.2ms order SERVER POST /orders + 2.6ms 9.4ms order PRODUCER orders publish offset=2148 # 결제 쪽은 다른 트레이스 + 0.0ms 2027.8ms payment CONSUMER orders receive message_count=1 (부모 없음) + 2028.3ms 1.6ms payment CONSUMER orders process link→ d26064b2../59d1f34584a727bf + 2029.1ms 0.4ms payment CLIENT INSERT shop.payments

문서대로 결제 쪽은 orders receive를 뿌리로 하는 새 트레이스가 됐고, process 스팬이 링크로 주문 트레이스의 publish 스팬을 가리켰어요. 주문 세 건에 주문 트레이스 3개, receive 트레이스 3개가 생겼습니다.

눈에 띈 건 receive 스팬의 길이예요. 2,027.8ms입니다. 메시지가 큐에서 2초를 기다린 게 아니에요. 주문을 2초 간격으로 넣었으니, 컨슈머가 poll()을 부르고 다음 메시지가 올 때까지 기다린 시간이 그대로 receive 스팬이 된 겁니다. receive 스팬의 길이는 메시지의 대기 시간이 아니라 poll이 기다린 시간이에요. 이걸 "큐 지연"으로 읽으면 한가할수록 큐가 느려 보이는 이상한 그래프가 나옵니다.

📖 용어: poll
Kafka 컨슈머가 브로커에 "새 메시지 있으면 달라"고 묻는 호출입니다. 메시지가 없으면 정해진 시간까지 기다렸다가 돌아와요. 한 번에 여러 건을 받아 올 수 있습니다.

묶음으로 받으면 링크만 남는다

두 번째 경우는 배치 리스너예요. @KafkaListener(batch = "true")로 poll 한 번에 온 메시지를 리스트로 받게 바꿨습니다(receive 설정은 다시 끔). 메시지가 여러 건 쌓이게 하려고 결제 서비스를 멈춘 채 주문 10건을 넣고, 결제를 다시 띄웠어요.

BATCH=true docker compose up -d payment # 배치 리스너로 띄워 두고 docker compose stop payment for i in $(seq 1 10); do curl -s -XPOST localhost:25003/orders -H 'Content-Type: application/json' -d '{"sku":"A-100","qty":1}' & done; wait docker compose start payment python3 show-trace.py '{resource.service.name="payment" && name="orders process"}'
그림 3. 메시지 10건이 process 스팬 하나가 됐고, 부모 대신 링크 10개가 달렸다

process 스팬 하나가 부모 없이 새 트레이스를 시작했고, messaging.batch.message_count=10과 링크 10개가 붙었어요. 링크의 TraceID가 전부 다릅니다. 주문 10건이 각자 다른 트레이스였으니까요. 부모는 하나만 둘 수 있으니 10건을 다 이으려면 링크밖에 없습니다. 3편이 링크를 설명하며 든 이유가 그대로 나왔어요.

대가도 있었습니다. 이 트레이스 안에 INSERT 스팬 10개가 나란히 붙었는데, 어느 INSERT가 어느 주문 것인지는 스팬만 봐서는 알 수 없어요. 결제 로그 10줄도 전부 같은 trace_id를 달고 찍혔습니다. 주문 하나를 따라가려면 링크를 눌러 주문 트레이스로 건너가야 해요.

그림 4. 같은 코드, 같은 Kafka인데 트레이스 모양이 셋으로 갈렸다
⚠️ 주의: 트레이스가 끊겼다고 단정하기 전에
receive 설정을 켰거나 배치 리스너를 쓰면 주문 트레이스는 publish에서 끝나는 게 정상이에요. 이때 "Kafka 뒤로 전파가 안 된다"고 결론 내리면 틀립니다. 결제 쪽 스팬의 References(링크)를 먼저 확인하세요. 링크가 있으면 전파는 된 거고, 트레이스를 나눠 그렸을 뿐이에요.

4. 같은 JVM 안에서 끊기는 곳

3편 마지막 절은 컨슈머가 처리 속도를 높이려고 일을 스레드풀로 넘기면, MDC가 ThreadLocal이라 워커 스레드에서는 traceId가 안 찍힌다고 했어요. 결제 처리를 세 가지 방법으로 넘겨 보고, 각각 k6로 30초 동안 주문을 넣었습니다(VU 5개, 요청 사이 0.2초).

executor : Executors.newFixedThreadPool(4) 에 submit queue : 직접 만든 LinkedBlockingQueue 에 메시지만 넣고, 워커 스레드 4개가 꺼내 처리 queue-ctx : 같은 큐에 OTel Context 를 같이 넣고, 워커가 꺼낼 때 복원
HANDOFF=queue docker compose up -d payment docker compose --profile load run --rm load ./count.sh 75 # 최근 75초 트레이스를 뿌리 스팬 이름별로 센다
방식 k6 주문 주문 트레이스 INSERT가 뿌리인 트레이스 executor 710 710 0 queue 695 695 695 queue-ctx 710 710 0

예상과 달랐던 건 executor예요. 직접 만든 스레드풀로 넘겼는데 끊기지 않았습니다. INSERT 스팬 710개가 전부 주문 트레이스 안에 들어갔고, 워커 스레드(pool-4-thread-1)가 찍은 로그에도 trace_id가 있었어요. 에이전트가 java.util.concurrent의 execute, submit, schedule을 계측해서 넘기는 순간의 컨텍스트를 작업에 실어 주기 때문입니다. 에이전트 지원 목록에도 Java Executors가 "Context propagation"으로 올라가 있어요.

+ 0.0ms 12.9ms order SERVER POST /orders + 1.9ms 9.2ms order PRODUCER orders publish + 51.5ms 5.3ms payment CONSUMER orders process (56.8ms에 끝남) + 92.1ms 0.8ms payment CLIENT INSERT shop.payments thread=pool-4-thread-1

이 트레이스에서 INSERT는 부모인 process 스팬이 끝나고 35ms 뒤에 시작했어요. 리스너는 일을 넘기자마자 돌아왔으니 process 스팬은 "처리"가 아니라 "넘기기"까지만 잰 겁니다. 컨슈머 처리 시간을 process 스팬으로 보고 있었다면 실제보다 짧게 보여요.

끊긴 건 queue였습니다. 메시지를 담은 객체만 큐에 넣으면 에이전트가 끼어들 자리가 없어요. 주문 695건마다 주문 트레이스는 process에서 끝났고, INSERT는 부모 없는 트레이스 695개로 따로 떨어졌습니다. 로그도 그대로 갈라졌어요.

INFO [trace_id=c0e4e26ddb9b72eee636b48c0e6860a8 span_id=625ef462b361a370] [ntainer#0-0-C-1] 주문 수신 052dabc7-... INFO [trace_id= span_id=] [ pay-worker-0] 결제 완료 order=052dabc7-...

같은 주문인데 "수신" 줄에는 trace_id가 있고 "완료" 줄에는 비어 있어요. 결제가 실패했다면 그 예외 로그를 trace_id로 찾을 수 없었을 겁니다. 에이전트는 스레드풀은 알아도, 우리가 만든 큐 안의 객체는 모릅니다.

📖 용어: Context (OpenTelemetry)
지금 실행 중인 스팬과 baggage 같은 값을 담은 불변 객체입니다. 스레드에 "현재 컨텍스트"로 붙어 있고, Context.current()로 꺼내 makeCurrent()로 다른 스레드에 다시 붙일 수 있어요.

고친 방법은 3편의 캡처, 복원, 정리 그대로예요. 큐에 넣을 때 Context.current()를 같이 넣고, 워커가 꺼낼 때 그 컨텍스트를 붙였다가 블록이 끝나면 떼어 냅니다. 이 부분만 opentelemetry-api 의존성을 넣었어요. 에이전트가 이 API 호출을 자기 컨텍스트로 이어 줍니다.

// 넘길 때 (컨슈머 스레드) queue.add(new Job(payload, Context.current())); // 캡처 // 꺼낼 때 (워커 스레드) try (Scope ignored = job.ctx().makeCurrent()) { // 복원 pay(job.payload()); } // 정리: close 가 원래 컨텍스트로 되돌린다

queue-ctx로 돌린 710건은 부모 없는 트레이스 없이 전부 주문 트레이스 안으로 돌아왔어요. 워커 로그에도 trace_id가 다시 찍혔습니다.

💡 실무에서는: 컨슈머 쪽 트레이스를 점검할 때
• 주문 수와 "DB나 HTTP 클라이언트 스팬이 뿌리인 트레이스" 수를 같이 세 보세요. 후자가 늘면 어딘가에서 컨텍스트를 안 싣고 넘기는 코드가 있어요
• 에이전트가 이어 주는 건 Executor 계열까지예요. 직접 만든 큐, 링 버퍼, 메시지를 객체로 넘기는 이벤트 버스는 Context.current()를 같이 실어야 해요
• 컨슈머가 일을 넘기는 구조라면 process 스팬 길이를 처리 시간으로 쓰지 마세요. 넘긴 뒤의 실제 처리 스팬을 따로 봐야 해요

5. 3편과 다르게 나온 두 가지

정리하면 3편의 설명과 실측이 어긋난 곳이 두 군데 있었어요. 둘 다 3편이 틀렸다기보다, 3편은 규약과 맨 MDC를 기준으로 말했고 이번 실습은 에이전트를 붙인 결과라서 생긴 차이입니다.

첫째, 링크가 기본이 아니었습니다. 규약은 링크를 기본으로 권하지만 에이전트 2.32.0의 기본값은 부모-자식이었어요. 규약이 걸라고 한 링크가 생긴 건 receive 설정을 켰을 때, 배치 리스너일 때(이 둘은 컨슈머 쪽이 새 트레이스), 새 규약을 opt-in 했을 때(부모는 그대로 두고 링크를 더 검)였습니다.

둘째, 스레드풀로 넘겨도 끊기지 않았습니다. 3편의 executor.submit 예시는 에이전트가 없을 때 이야기예요. 에이전트가 있으면 Executor로 넘기는 작업에 컨텍스트가 따라가고, MDC의 trace_id도 찍힙니다. 끊기는 건 에이전트가 볼 수 없는 자리, 이번 실습에서는 직접 만든 작업 큐였어요. 3편이 말한 CompletableFuture 기본 풀은 이번에 시험하지 않았어요. 에이전트의 Executor 계측 대상에 ForkJoinTask를 받는 execute, submit, invoke도 들어 있어서 이어질 가능성이 높지만, 직접 확인한 결과는 아닙니다.

✍️ 오늘의 요약
에이전트는 Kafka 헤더로 traceparent를 실어 나르고, 기본값으로는 결제 컨슈머의 process 스팬을 주문의 publish 스팬 자식으로 붙였다. 규약이 걸라고 하는 span link는 receive 설정을 켜거나 배치로 받을 때 나타났고, 그때 컨슈머 쪽은 새 트레이스가 됐다. 새 규약을 opt-in 하면 부모는 그대로 두고 링크를 하나 더 걸었다.

같은 JVM 안에서는 Executor로 넘긴 작업까지 에이전트가 이어 줬고, 직접 만든 큐로 넘긴 메시지에서 트레이스와 로그의 trace_id가 함께 끊겼다. 트레이스가 끊긴 것처럼 보이면 링크부터 확인하고, 링크도 없으면 컨텍스트를 싣지 않은 채 넘기는 곳을 찾으면 된다.
