결제 실패 로그 한 줄을 찾았습니다. WARN 결제 실패 sku=C-300 status=500. 이 주문이 재고 조회에서 얼마나 걸렸는지, 결제 서비스는 무슨 에러를 냈는지 알고 싶어요. 1편에서 말한 "디버깅 릴레이"가 필요한 순간입니다. 로그에서 트레이스로 건너가고, 트레이스에서 다시 다른 서비스의 로그로 건너가야 해요.

1편은 이렇게 정리했어요. 모든 로그에 traceId를 심고, 대시보드에서 트레이스와 로그 사이 이동이 클릭으로 되는지 확인하라. 이번 실습은 그 이동을 실제로 설정해 봅니다. 앱 코드는 실습-1과 같고 로그 몇 줄만 더했어요. 링크는 설정했는데, 트레이스에서 로그로 건너가는 버튼이 빈 화면을 띄웠습니다. 설정이 틀린 게 아니었어요. 원인은 1ms보다 작은 시각 차이였습니다.

1. 실습 환경: 로그는 Loki로, 트레이스는 Tempo로

실습-1의 주문, 재고, 결제 서비스를 그대로 띄우고 로그 수집 쪽을 더했어요. 앱은 로그를 표준 출력에 찍기만 합니다. Grafana Alloy가 도커 소켓으로 컨테이너 로그를 읽어 Loki로 보내요. 트레이스는 실습-1처럼 Collector를 거쳐 Tempo로 갑니다.

그림 1. 로그와 트레이스는 따로 저장되고, Grafana 설정 두 개가 그 사이를 잇는다
📖 용어: Loki
Grafana Labs의 로그 저장소입니다. 로그 본문은 색인하지 않고 service_name 같은 라벨만 색인해요. 그래서 "이 서비스의 로그 중 이 글자가 든 줄"처럼 라벨로 범위를 좁히고 본문을 훑는 식으로 찾습니다.
📖 용어: Grafana Alloy
로그, 지표, 트레이스를 모아 보내는 Grafana의 수집기입니다. 이번 실습에서는 도커 소켓을 읽어 컨테이너 로그를 Loki로 보내는 일만 맡겼어요.

Grafana 데이터소스는 실습-1의 것에 Loki를 더하고 이동 설정을 넣어야 해서, 이 실습만 Grafana 프로비저닝 파일을 따로 뒀어요. 실습 코드는 GitHub 저장소의 labs/observability/tracing-03-logs에 있습니다.

Grafana Loki 3.7.8 (단일 바이너리, 파일시스템 저장) Grafana Alloy 1.20.1 Spring Boot 4.1.1, OTel Java agent 2.32.0, Tempo 2.10.8, Grafana 13.2.3, k6 2.3.0 (실습-1과 같음) cd Platform-study/labs/observability/tracing-03-logs PAYMENT_FAIL_RATE=0.3 docker compose up -d --build # 결제 30% 실패 docker compose --profile load run --rm -e DURATION=20s load # Grafana: http://localhost:25000 → Explore → Loki

2. trace_id를 로그 줄에 찍는다

에이전트는 로그백의 MDC에 trace_id, span_id, trace_flags를 넣어 줍니다. 넣어 주기만 하고 찍지는 않아요. 로그 패턴에 넣는 건 우리 몫입니다. 에이전트 문서는 스프링 부트라면 logging.pattern.level 하나만 덮어쓰라고 안내해요. 레벨이 찍히는 자리 앞뒤에 값을 끼워 넣는 설정이라, 나머지 기본 패턴은 그대로 둘 수 있습니다.

# application.yml logging: pattern: level: "%5p trace_id=%X{trace_id:-} span_id=%X{span_id:-}"

결제가 실패하면 주문과 결제 서비스가 각각 이렇게 찍어요. 두 줄의 trace_id가 같습니다.

order WARN trace_id=3771b55990d66c093ca8e6d047004633 span_id=adda62e5028afb95 ... 결제 실패 sku=C-300 status=500 payment ERROR trace_id=3771b55990d66c093ca8e6d047004633 span_id=259c63cc7ecc6582 ... PG 승인 거절 sku=C-300 code=PG_TIMEOUT
📖 용어: MDC (Mapped Diagnostic Context)
로깅 라이브러리가 스레드마다 들고 있는 작은 키-값 맵입니다. 여기 넣은 값은 로그 패턴의 %X{키} 자리에 찍혀요. 에이전트는 현재 스팬의 trace_id와 span_id를 여기 넣어 줍니다.

재고 서비스에는 실습-1부터 들어온 traceparent 헤더를 찍는 줄이 있었어요. 같은 줄에 MDC 값이 같이 찍히니 둘을 비교할 수 있었습니다.

INFO trace_id=912398645615be65758910eb6444a6f7 span_id=f251210ca2b398cf ... traceparent=00-912398645615be65758910eb6444a6f7-5ad4d27bcb70763f-03

trace_id는 같고 span_id는 달라요. 헤더의 5ad4d27bcb70763f는 주문 서비스의 CLIENT 스팬이고, MDC의 f251210ca2b398cf는 재고 서비스가 요청을 받으며 만든 SERVER 스팬입니다. 로그의 span_id는 "그 줄을 찍을 때 열려 있던 스팬"이에요.

Loki에 쌓인 앱 로그 1,047줄(30분)을 세어 보면, 32자리 trace_id가 있는 줄이 970줄, trace_id=가 비어 있는 줄이 37줄이었어요. 빈 줄은 전부 main 스레드가 기동할 때 찍은 로그였습니다. 요청을 처리하는 중이 아니니 열린 스팬이 없어요. 나머지 40줄은 JVM과 에이전트의 기동 메시지처럼 로그백 패턴을 거치지 않는 줄입니다.

⚠️ 주의: Alloy가 다른 컨테이너 로그까지 가져왔다
도커 소켓은 그 데몬의 모든 컨테이너를 보여 줍니다. 처음에는 loki.source.docker의 relabel_rules에 서비스 이름 keep 규칙을 넣었는데, 이 실습 설정에서는 Loki 자신의 로그가 unknown_service로 같이 들어왔어요. 왜 keep 규칙이 거르지 않았는지 원인까지는 확인하지 못했습니다. 문서는 relabel_rules를 "로그 항목에 적용하는 라벨 규칙"으로만 설명해요. discovery.relabel의 output을 targets로 넘기는 방식으로 바꾸자 앱 로그만 들어왔어요. compose 프로젝트 라벨로 먼저 거르는 필터도 넣었습니다.

3. 로그에서 트레이스로: derived field

로그 줄에 trace_id가 있어도 Grafana는 그게 trace ID인지 모릅니다. Loki 데이터소스의 derived field가 "이 정규식에 맞는 글자를 뽑아 Tempo 링크로 만들라"고 알려 줘요.

# grafana/provisioning/datasources/datasources.yaml (Loki 부분) derivedFields: - name: TraceID matcherType: regex matcherRegex: "trace_id=(\\w+)" datasourceUid: tempo url: "$${__value.raw}" # 뽑은 값을 그대로 Tempo 쿼리로. $$ 는 프로비저닝 파일의 이스케이프 urlDisplayLabel: Tempo에서 트레이스 열기
📖 용어: derived field
Loki 로그 줄이나 라벨에서 값을 뽑아 새 필드로 보여 주는 Grafana 설정입니다. 다른 데이터소스를 연결해 두면 그 필드가 링크가 돼요.

Explore에서 {service_name="order"} |= "결제 실패"로 찾은 줄을 펼치면 Links 칸에 버튼이 생깁니다.

그림 2. 정규식 한 줄이 로그 속 32자리 문자열을 링크로 바꿨다

버튼을 누르면 화면이 둘로 나뉘고 오른쪽에 그 트레이스가 열려요.

그림 3. 로그 한 줄에서 주문 전체의 여정으로 건너왔다

재고 조회는 1.71ms에 끝났고 결제가 38.19ms 걸려 500을 돌려준 게 바로 보입니다. 로그만으로는 세 서비스의 로그를 시각으로 맞춰 봐야 알 수 있던 내용이에요.

4. 트레이스에서 로그로: 빈 화면이 떴다

반대 방향은 Tempo 데이터소스의 trace to logs 설정이 맡아요. 스팬의 service.name을 Loki 라벨 service_name으로 바꿔 끼우고, trace ID로 줄을 거르게 했습니다.

tracesToLogsV2: datasourceUid: loki filterByTraceID: true tags: - key: service.name value: service_name

같은 트레이스에서 결제 서버 스팬을 펼치고 "Logs for this trace"를 눌렀어요. 결제 서비스가 찍은 PG 승인 거절 줄이 나와야 합니다.

그림 4. 쿼리는 맞게 만들어졌는데 결과가 없다

Grafana가 만든 쿼리를 Loki API로 직접 돌리면, 시간 범위를 넉넉히 줬을 때 그 줄이 나왔어요. 쿼리 내용은 문제가 아니었습니다. 그래서 Grafana가 Loki에 보낸 요청을 헤드리스 브라우저로 가로채 시간 범위를 봤어요.

Grafana 가 보낸 범위 from 1791614303998 to 1791614304036 (밀리초) 결제 서버 스팬 1791614303998692675 ~ 1791614304036878925 (나노초) Loki 에 찍힌 로그 시각 1791614304036220758 (나노초)

Grafana는 스팬의 시작과 끝을 밀리초로 잘라서 보냈어요. 스팬은 ...036.878ms에 끝났는데 범위의 끝은 ...036ms가 됐습니다. 로그는 ...036.220ms에 찍혀 있었어요. 스팬 안에서 찍힌 로그가, 잘려 나간 마지막 1ms 안에 있었던 겁니다.

그림 5. 스팬 끝을 밀리초로 내림하면 마지막 1ms 안의 로그가 범위 밖으로 떨어진다

우연한 한 건이었는지 보려고, 그 실행에서 쌓인 결제 에러 로그 101줄을 전부 그 로그를 남긴 스팬과 대조하는 스크립트(log-vs-span.py)를 돌렸어요.

python3 log-vs-span.py 900 결제 에러 로그 101줄 스팬 구간 안 101 / 스팬이 끝난 뒤 0 / 시작 전 0 스팬 끝을 밀리초로 내림하면 구간 밖이 되는 줄 38 Loki 시각 - 앱 로그 시각: 중앙값 0.99ms, 최대 1.81ms Loki 시각 - 스팬 끝: 중앙값 -0.59ms, 최소 -1.35ms, 최대 -0.06ms

101줄 모두 스팬 안에서 찍혔지만, 스팬 끝을 밀리초로 내린 경계와 실제 끝 사이에 찍힌 줄이 38줄이었어요. 이 설정 그대로면 결제 에러 로그 10개 중 4개 가까이를 트레이스에서 찾지 못합니다. 결제 컨트롤러가 실패 로그를 응답 직전에 찍기 때문이에요. 에러 로그는 대개 처리의 맨 끝에서 찍히니, 하필 제일 보고 싶은 줄이 잘 빠집니다.

Loki에 찍힌 시각은 앱이 본문에 쓴 시각보다 중앙값 0.99ms 늦게 나왔어요. 다만 본문 시각은 밀리초로 잘려 있어서 평균 0.5ms쯤은 그 절단 오차예요. 실제 차이는 이보다 작습니다. Loki 쪽 시각은 나노초 단위라, 앱 본문이 아니라 도커가 기록한 로그 시각으로 보여요. 결국 이 실습에서 로그를 놓친 원인은 수집 지연이 아니라 Grafana가 범위를 밀리초로 내린 것이었어요.

📖 용어: span time shift
trace to logs 설정의 spanStartTimeShift, spanEndTimeShift입니다. 로그를 찾을 시간 범위를 스팬의 시작과 끝에서 앞뒤로 넓혀요. 기본값은 0이라 스팬 구간만 찾습니다.

Grafana 문서도 이 경우를 적어 뒀어요. "기본값 0은 타임스탬프가 정확히 맞지 않으면 로그를 하나도 돌려주지 않을 수 있다." 앞뒤로 1초씩 넓히자 같은 버튼에서 그 줄이 나왔습니다. 가로챈 요청의 범위도 from ...302998 to ...305036으로 바뀌었어요. trace ID로 거르기 때문에 범위를 넓혀도 다른 트레이스의 로그는 섞이지 않습니다.

tracesToLogsV2: ... spanStartTimeShift: "-1s" spanEndTimeShift: "1s"

저장소의 grafana/provisioning/datasources/datasources.yaml에는 고친 뒤의 이 두 줄이 이미 들어 있어요. 그림 4의 빈 화면을 직접 보려면 두 줄을 지우고 docker compose restart grafana로 Grafana를 다시 띄우면 됩니다.

그림 6. 범위를 1초 넓히자 빠졌던 에러 로그가 나왔다
💡 실무에서는: 로그와 트레이스를 이을 때
• trace to logs에는 spanStartTimeShift와 spanEndTimeShift를 꼭 넣어요. 0이 아니기만 해도 밀리초 절단 문제는 사라지고, trace ID로 거르니 넉넉히 잡아도 다른 요청 로그는 섞이지 않아요
• 링크가 빈 화면을 띄우면 쿼리보다 시간 범위를 먼저 의심해요. Query inspector에서 요청의 from/to를 보면 바로 보여요
• 로그 패턴의 trace_id 이름을 서비스마다 통일해요. derived field 정규식 하나로 전부 잡혀야 해요

5. 로그를 OTLP로 보내면

패턴과 정규식 없이 잇는 길도 있어요. 에이전트가 로그를 OTLP로 직접 보내게 하면 로그 레코드에 trace ID가 필드로 붙어 갑니다. 결제 서비스만 OTEL_LOGS_EXPORTER=otlp로 바꾸고, Collector에 로그 파이프라인을 더해 Loki의 OTLP 수신 주소(/otlp)로 보냈어요.

LOGS_EXPORTER=otlp PAYMENT_FAIL_RATE=0.3 docker compose up -d

Loki에 들어온 모양이 달랐어요. 본문에는 메시지만 있고, trace ID와 span ID, 심각도는 structured metadata로 붙었습니다. 색인 라벨은 service_name과 service_instance_id 둘뿐이었어요.

본문 PG 승인 거절 sku=A-100 code=PG_TIMEOUT 라벨 service_name=payment, service_instance_id=9441413b-... 메타데이터 trace_id=8eff79e6de5cb19bd4943dd41e7f11d8, span_id=..., severity_text=ERROR, flags=3, ...
📖 용어: structured metadata (Loki)
로그 줄마다 붙지만 색인 라벨은 아닌 키-값입니다. trace ID처럼 값 종류가 무한히 많은 정보를 라벨로 만들면 스트림이 폭발하니, 검색은 되되 색인은 하지 않는 자리에 둬요.

여기서 두 가지를 봤어요. 하나는 중복입니다. Alloy의 도커 로그 수집을 켜 둔 채라 같은 로그가 두 길로 들어왔어요. 결제 실패 5건에 Loki 줄은 10개(도커 경로 5, OTLP 경로 5)였습니다. 하나만 남겨야 해요.

다른 하나는 정규식이 안 맞는다는 점이에요. OTLP로 온 본문에는 trace_id=라는 글자가 없으니 3절의 derived field가 링크를 못 만듭니다. 정규식 대신 메타데이터 이름으로 값을 고르는 derived field 설정이 따로 필요한데, 이번 실습에서는 그 설정을 시험하지 않았어요. 반대 방향은 대비가 돼 있는 것으로 보여요. 그림 4의 쿼리 끝에 or trace_id="..."가 붙어 있었는데, 본문이 아니라 이 메타데이터를 거르는 조건입니다. 이 경로로 trace to logs를 눌러 보는 것도 이번에는 하지 않았어요.

⚠️ 주의: 두 길을 동시에 열지 않아요
stdout 수집과 OTLP 로그 내보내기를 함께 켜면 로그 저장량이 두 배가 되고, 건수로 알람을 걸었다면 두 배로 울려요. OTLP로 옮길 때는 그 서비스의 stdout 수집을 끄는 것까지 한 번에 해요.
✍️ 오늘의 요약
에이전트가 MDC에 넣어 준 trace_id를 로그 패턴 한 줄로 찍고, Loki의 derived field와 Tempo의 trace to logs로 로그와 트레이스 사이를 클릭으로 오갈 수 있었다. 로그에서 트레이스로는 바로 됐지만, 트레이스에서 로그로는 처음에 빈 화면이 떴다. Grafana가 스팬 끝을 밀리초로 내림해서 물었고, 결제 에러 로그 101줄 중 38줄이 그 마지막 1ms 안에 있었다.

링크가 설정돼 있어도 시간 범위가 어긋나면 결과는 빈 화면이다. 링크가 빈 화면을 띄우면 쿼리보다 범위를 먼저 본다.
