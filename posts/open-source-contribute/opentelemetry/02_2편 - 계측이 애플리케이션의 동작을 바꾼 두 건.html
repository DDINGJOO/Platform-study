📚 오픈소스 기여 회고 · OpenTelemetry
1편. 서버 주소가 비고 에러 타입이 BLPOP.이 된 이유
2편. 계측이 애플리케이션의 동작을 바꾼 두 건 ← 지금 이 글

비동기로 값을 반환하는 @KafkaListener가 있는 Spring Boot 앱에 OpenTelemetry 에이전트 2.32.0을 붙였더니, 레코드 3건에 process 스팬이 6개 생겼어요. 다른 모듈에서는 @WithSpan을 붙인 메서드가 Flux를 반환하면, 구독자가 1개만 요청해도 원본 Flux가 32개를 요청받았습니다.

두 건 모두 계측이 기록만 하는 것이 아니라 애플리케이션이 하는 일의 양을 바꾸고 있었어요. 이 글은 open-telemetry/opentelemetry-java-instrumentation에 낸 PR 네 건 가운데 #20658(Spring Kafka)과 #20659(Reactor)의 회고예요. 네 건은 모두 머지됐고, 시각은 따로 적지 않으면 UTC입니다.

1. 레코드 하나에 process 스팬이 둘

PR 본문에 따르면 2.32.0부터, 비동기 ack를 쓰는 Spring Kafka 리스너 컨테이너에서 레코드마다 process 스팬이 두 개 만들어졌어요. 하나는 spring-kafka-2.7 계측이 만든 스팬이고, 다른 하나는 kafka-clients-0.11 계측이 만든 약 0ms짜리 스팬이며, 둘 다 프로듀서 스팬의 자식이었습니다. 비동기 ack는 AckMode.MANUAL에 ContainerProperties.setAsyncAcks(true)를 켠 경우, 또는 @KafkaListener가 CompletableFuture나 Mono를 반환하는 경우예요.

📖 용어: process 스팬과 비동기 ack
Kafka 컨슈머가 메시지(레코드)를 받아 처리하는 구간을 process 스팬 하나로 기록해요. ack(acknowledge)는 "이 레코드까지 처리했다"고 오프셋을 확정하는 호출입니다. 이 모드에서는 Spring Kafka가 폴링한 배치의 오프셋을 captureOffsets()에서 먼저 기록해요.

PR 본문의 설명은 이랬어요. 이 모드에서 Spring Kafka는 ListenerConsumer.captureOffsets() 안에서 폴링한 배치의 레코드를 돌며 오프셋을 기록하는데, 이 순회가 doPoll()이 반환되기 전에 일어납니다. 그런데 #20139 이후에는 이 배치가 Spring Kafka 소유라는 표시를 doPoll()이 끝날 때 붙였어요. 표시가 붙기 전에 순회가 시작되니, 그 순회가 Kafka 클라이언트의 순회 계측을 그대로 거쳐서 레코드마다 process 스팬을 시작하고 끝냈습니다. 2.31.1에서는 실행 루프 전체의 래핑이 꺼져 있어서 이 현상이 보이지 않았다고 적혀 있어요.

📖 용어: 소유 표시와 순회 계측
Kafka 클라이언트 계측은 ConsumerRecords를 순회(iterate)할 때 레코드마다 process 스팬을 만들어요. Spring Kafka 계측이 이미 같은 일을 하는 배치라면 중복되니까, 그 배치에 "Spring Kafka가 맡았다"는 표시를 붙여서 클라이언트 쪽 계측이 건너뛰게 합니다. 표시를 붙이는 시점이 순회보다 늦으면 건너뛰기가 작동하지 않아요.
그림 1. 소유 표시를 붙이는 위치가 순회보다 앞이어야 해요

2. 고친 곳은 표시를 붙이는 위치였다

수정은 표시를 붙이는 위치를 앞당기는 것이었어요. 배치가 Spring Kafka로 들어오는 시점은 pollConsumer()가 반환되는 때이므로, 거기서 표시를 붙입니다. 다만 doPoll()의 계측은 그대로 남겨야 했어요. PR 본문에 따르면 pollConsumer()가 없는 spring-kafka 2.7과, subBatchPerPartition 설정에서 doPoll()이 직접 만드는 하위 배치가 아직 doPoll()에서 표시를 받아야 하기 때문이에요. 본 코드 변경은 7줄 추가, 1줄 삭제입니다.

- transformer.applyAdviceToMethod(named("doPoll"), getClass().getName() + "$PollAdvice"); + // pollConsumer() (2.8+) returns the batch inside doPoll(), which may iterate it before + // returning, e.g. captureOffsets() when acks are async. Mark it there so that iteration doesn't + // create Kafka client process spans; doPoll() covers older versions and the sub-batches it + // creates. + transformer.applyAdviceToMethod( + namedOneOf("doPoll", "pollConsumer"), getClass().getName() + "$PollAdvice");

같은 어드바이스(PollAdvice)를 doPoll과 pollConsumer 두 메서드에 모두 적용했어요. 테스트는 새 스위트 testAsyncAcks(build.gradle.kts에 9줄 등록, 테스트 파일 95줄)로 추가했습니다. 비동기 ack는 spring-kafka 2.8에서 생겨서, 이 스위트는 기본으로 2.8.0을 쓰고 최신 의존성에서는 최신 버전을 씁니다. 테스트는 Kafka 브로커 없이 MockConsumer로 레코드를 하나 넣고, AckMode.MANUAL과 setAsyncAcks(true)를 켠 컨테이너를 레코드 리스너와 배치 리스너로 각각 실행해요. kafka-clients-0.11 스코프의 스팬이 하나도 없는지, CONSUMER 스팬이 spring-kafka-2.7 스코프의 하나뿐인지 확인합니다.

📖 용어: MockConsumer
Kafka 클라이언트가 테스트용으로 제공하는 가짜 컨슈머예요. 브로커를 띄우지 않고도 addRecord로 레코드를 넣고 schedulePollTask로 폴링 시점에 일어날 일을 예약할 수 있어서, 이 테스트처럼 Docker 없이 컨테이너 동작을 검사할 때 써요.

3. 머지 커밋에서 통과하고, 본 코드를 되돌리면 두 케이스 모두 실패

머지 커밋 811c17a4f2를 받아 이 스위트만 돌렸어요. 1편과 같은 설정으로, Gradle은 Corretto 21로 띄우고 컴파일과 테스트는 프로젝트 toolchain인 JDK 25로 실행됐습니다. 이 글에서는 기본 의존성(spring-kafka 2.8.0)만 돌렸고 최신 의존성 실행은 하지 않았어요.

Expecting empty but was: [...]은 "비어 있어야 할 목록에 항목이 남아 있다"는 AssertJ의 메시지예요. kafka-clients-0.11 스코프의 process orders 스팬이 남아 있다는 뜻이고, PR 본문의 "extra process orders span from kafka-clients-0.11"과 같은 모양입니다. 레코드 리스너와 배치 리스너 두 케이스가 모두 실패했어요. 수정 후 상태에서는 두 케이스 모두 통과했습니다.

PR 본문에 적은 Spring Boot 앱의 실험(레코드 3건에 process 스팬 6개)은 다시 만들지 않았어요. 앱과 브로커가 필요하고, 그 앱의 코드는 PR 기록에 없기 때문입니다. 이 글에서 확인한 것은 MockConsumer로 만든 단일 레코드에서 클라이언트 스팬이 남는지 여부까지예요.

4. 리뷰와 현재 상태 (#20658)

PR은 10-17 06:37에 열었고 자동 리뷰 봇의 첫 리뷰가 6분 뒤에 달렸어요. 지적 사항은 없다는 내용이었습니다. trask가 10-18 19:29에 승인했고, 10-19 06:59:23에 laurit이 직접 커밋 c017ad75(메시지 "use namedOneOf")를 올렸어요. 머지된 코드가 위 diff처럼 namedOneOf("doPoll", "pollConsumer")로 두 메서드를 한 번에 지정하는 것은 이 커밋 뒤의 모습이에요. 20초 뒤인 06:59:43에 laurit이 승인했습니다. 07:20:23에 laurit이 머지했어요. 지금 상태는 MERGED이고 머지 커밋은 811c17a4f2입니다.

리뷰어가 코드의 방향을 두고 질문하거나 변경을 요청한 코멘트는 없었어요. 리뷰어가 올린 커밋은 이 하나였어요.

5. @WithSpan을 붙였더니 소스가 32개를 요청받았다 (#20659)

두 번째 건은 Reactor 계측이에요. PR 본문에 따르면 @WithSpan을 붙인 메서드가 Flux를 반환하면, 반환된 Flux가 소스에서 끌어오는 양이 달라집니다. 구독자가 몇 개를 요청하든 소스는 32개를 요청받아요.

📖 용어: 수요(demand), 프리페치, 퓨전
Reactor에서 구독자는 request(n)으로 "n개 더 보내라"고 상류에 요청하고, 상류는 요청받은 만큼만 보내요. 이 요청량이 수요(demand)입니다. 프리페치는 연산자가 요청받지 않은 만큼을 미리 상류에서 가져오는 것이고, 퓨전은 상류와 하류가 큐를 직접 공유해서 request 호출 없이 값을 주고받는 최적화예요. @WithSpan은 메서드 실행을 스팬 하나로 감싸는 어노테이션입니다.

원인은 ContextPropagationOperator.runWithContext(Flux, Context)의 구현에 있었어요. 이 메서드는 ReactorAsyncOperationEndStrategy가 @WithSpan 메서드의 Flux를 감쌀 때 쓰고, 내부에서 ScalarPropagatingFlux(source).flatMap(unused -> source)를 만듭니다. ScalarPropagatingFlux는 Callable이 아니라서 이 호출은 완전한 FluxFlatMap이 되고, 그 안쪽 구독자가 Queues.XS_BUFFER_SIZE(32)만큼 소스에서 프리페치해요.

모든 소스에서 문제가 되는 것은 아니었어요. range나 fromIterable처럼 값을 동기로 내보내고 퓨전되는 소스는 프리페치를 알아채지 못합니다. 요청이 올 때 값을 만드는 소스, 예를 들어 Flux.generate, onRequest를 쓰는 Flux.create, 큐나 커서를 폴링하는 Flux에서 차이가 나요. PR 본문의 예시는 이렇습니다. 작업 100개가 든 큐를 폴링하는 Flux.generate에 .flatMap(job -> process(job), 1).take(1)을 이으면, 에이전트가 없을 때는 큐에 99개가 남고 @WithSpan을 붙였을 때는 68개가 남아요. 31개가 큐에서 꺼내진 채 취소 때 버려진 거예요. 이 100개 큐 예시는 PR 본문의 기록이고, 이번에는 다시 돌리지 않았습니다.

그림 2. flatMap은 프리페치하고 flatMapMany는 요청량을 그대로 넘겨요

6. flatMap을 flatMapMany로 바꾸면 되는 이유

수정은 ScalarPropagatingFlux가 Flux 대신 스칼라 Mono를 상속하게 하고, flatMap 대신 flatMapMany를 쓰는 것이었어요. Mono.flatMapMany는 하류의 요청량을 소스에 그대로 전달합니다. PR 본문에 따르면 컨텍스트 전파는 그대로예요. 소스는 여전히 스칼라 값의 onNext에서, 저장된 컨텍스트 안에서 구독됩니다. flatMapMany는 Reactor 3.1부터 있어서 이 모듈이 지원하는 하한 버전에서도 쓸 수 있어요. 본 코드 변경은 4줄 추가, 2줄 삭제였습니다.

- static class ScalarPropagatingFlux extends Flux<Object> implements Scannable { + static class ScalarPropagatingFlux extends Mono<Object> implements Scannable { static <T> Flux<T> create(Flux<T> source) { - return new ScalarPropagatingFlux(source).flatMap(unused -> source); + // flatMapMany passes downstream demand to the source unchanged, while Flux.flatMap would + // prefetch from it + return new ScalarPropagatingFlux(source).flatMapMany(unused -> source);

테스트 fluxPassesDownstreamDemandToSource는 14줄이에요. Flux.range(0, 100).hide().doOnRequest(requests::add)를 소스로 쓰고, runWithContext로 감싼 Flux를 StepVerifier.create(flux, 1)로 요청 1개만 구독해서 첫 값을 받은 뒤 취소해요. 마지막에 소스가 받은 요청이 [1L] 하나뿐인지 확인합니다. 퓨전되는 소스에서는 request 호출이 보이지 않기 때문에 hide()로 퓨전을 막았어요.

$ ./gradlew --no-daemon --max-workers=2 -Dorg.gradle.jvmargs=-Xmx2g \ :instrumentation:reactor:reactor-3.1:library:test --tests '*ReactorCoreTest*' # (1) 머지 커밋 2d0957e0bd 36 tests, 0 failed BUILD SUCCESSFUL in 1m 54s # (2) ContextPropagationOperator.java 만 직전 커밋으로 되돌림 36 tests completed, 1 failed BUILD FAILED in 11s ReactorCoreTest > fluxPassesDownstreamDemandToSource() FAILED org.opentest4j.AssertionFailedError: Expecting actual: [32L] to contain exactly (and in same order): [1L]

[32L]은 소스가 받은 요청이 1개가 아니라 32개 하나였다는 뜻이에요. PR 본문에 적힌 fails without this change ([32L])과 같은 값이 나왔습니다. 되돌린 상태에서도 다른 35개 테스트는 통과했어요. 머지 커밋에서는 기존 테스트를 포함한 36개가 모두 통과했으니, 수정 뒤에도 기존 테스트가 그대로 통과하는 것은 확인한 셈입니다.

7. 리뷰와 현재 상태 (#20659)

PR은 10-17 06:51에 열었고 커밋은 하나였어요. 자동 리뷰 봇은 지적 사항 없이 승인을 권했고, trask가 10-17 18:30에 "Thanks!"라는 코멘트와 함께 승인했습니다. laurit이 10-20 07:11:28에 승인하고 07:11:37에 머지했어요. 코드 변경을 요청한 코멘트는 없었고, 열 때의 커밋이 그대로 머지됐습니다. 지금 상태는 MERGED이고 머지 커밋은 2d0957e0bd예요.

PR 본문에는 열려 있던 #20643이 세 인자짜리 runWithContext 오버로드를 추가하지만 두 인자 경로는 바꾸지 않는다는 설명이 있었어요. 두 PR은 서로 다른 경로를 건드립니다.

8. 남은 한계

첫째, Spring Kafka 건의 앱 실험(레코드 3건, 스팬 6개)과 Reactor 건의 큐 100개 예시는 PR 본문의 기록만 옮겼고 이번에 다시 만들지 않았어요. 둘째, Kafka 스위트는 spring-kafka 2.8.0 기준으로만 돌렸습니다. 최신 의존성 실행과 2.7 경로는 확인하지 않았어요. 셋째, Reactor 테스트는 라이브러리 모듈의 단위 테스트이고, @WithSpan을 붙인 메서드를 에이전트로 실행하는 경로는 이번에 돌리지 않았습니다.

💡 확인한 것
• 두 PR 모두 머지 커밋에서 통과하고, 본 코드만 되돌리면 새 테스트가 실패하는 것을 직접 돌려서 확인했어요.
• Kafka는 2.8.0 기본 의존성에서만, Reactor는 모듈 단위 테스트에서만 확인했어요.

두 건에서 공통으로 배운 점이 있어요. 계측이 감싸는 위치와 시점이 애플리케이션이 하는 일의 양을 바꿀 수 있다는 것입니다. Kafka는 표시를 붙이는 시점이 순회보다 늦어서 스팬이 늘었고, Reactor는 감싸는 연산자가 프리페치를 해서 소스에서 가져오는 양이 늘었어요. 두 테스트 모두 결과 데이터가 아니라 스팬의 개수와 소스가 받은 요청량처럼 계측이 만든 부수 효과를 직접 검사합니다.

소스 기준: #20658(머지 커밋 811c17a4f2), #20659(머지 커밋 2d0957e0bd). 재현 명령과 출력은 labs/open-source-contribute/opentelemetry/repro.md에 남겼어요.

Spring Kafka 비동기 ack에서는 소유 표시가 순회보다 늦어 process 스팬이 둘씩 생겼고, @WithSpan을 붙인 Flux는 flatMap의 프리페치 때문에 소스가 32개를 요청받았어요. 둘 다 머지됐습니다.

Kafka는 표시를 배치가 들어오는 pollConsumer() 반환 시점으로 앞당겼고, Reactor는 flatMap을 요청량을 그대로 넘기는 flatMapMany로 바꿨어요. 두 PR 모두 본 코드만 되돌리면 새 테스트가 실패해서(스팬 잔존, [32L]), 테스트가 버그를 실제로 잡는다는 것을 확인했습니다. 계측의 위치는 기록의 정확도뿐 아니라 애플리케이션이 하는 일의 양까지 정해요.
