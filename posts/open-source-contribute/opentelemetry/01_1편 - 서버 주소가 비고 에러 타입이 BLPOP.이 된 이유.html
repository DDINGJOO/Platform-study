1편. 서버 주소가 비고 에러 타입이 BLPOP.이 된 이유 ← 지금 이 글
2편. 계측이 애플리케이션의 동작을 바꾼 두 건

JDBC URL이 jdbc:mysql://address=(host=db.example.com)(port=3307)/orders인 애플리케이션을 OpenTelemetry Java 계측으로 기록하면, 데이터베이스 호출의 스팬에 서버 주소가 기록되지 않았어요. 같은 서버를 jdbc:mysql://db.example.com:3307/orders로 적으면 주소와 포트가 정상으로 기록됐는데도요. 다른 모듈에서는 Redis 명령이 타임아웃으로 실패하면 error.type 값이 BLPOP.이나 GET.처럼 명령 이름에 마침표가 붙은 문자열로 기록됐어요.

이 글은 open-telemetry/opentelemetry-java-instrumentation에 제가 낸 PR 네 건 가운데, 기록된 값이 틀렸던 두 건의 회고예요. 하나는 #20660(JDBC)이고 다른 하나는 #20661(Lettuce)입니다. 이 저장소에는 2026-10-17에 모듈마다 PR을 하나씩 열었어요. 네 건은 모두 머지됐고, 두 건은 주제가 비슷해서 이 글에, 나머지 두 건은 다른 글에 나눠 적었습니다. 시각은 따로 적지 않으면 모두 UTC예요.

📖 용어: 계측(instrumentation)과 스팬(span)
OpenTelemetry Java Instrumentation은 자바 애플리케이션의 라이브러리 호출(JDBC 쿼리, Redis 명령 등)을 가로채서 호출 하나당 스팬 하나를 만드는 프로젝트예요. 스팬은 시작과 끝 시각, 이름, 속성(server.address, error.type 같은 키와 값)을 가진 기록 단위입니다. 라이브러리마다 이 기록을 만드는 모듈이 따로 있어서, PR도 모듈마다 하나씩 열었어요.

1. 주소 없이 기록되는 JDBC URL (#20660)

MySQL Connector/J와 MariaDB Connector/J 문서에는 호스트와 포트를 address=(host=...)(port=...) 블록으로 적는 URL 형식이 있어요. 서브프로토콜 없이 jdbc:mysql://address=(host=db.example.com)(port=3307)/orders처럼 쓰는 경우가 이 글에서 다루는 형식입니다. PR 본문에는 로컬에서 빌드한 main으로 확인한 결과가 적혀 있어요. 이 형식의 URL이 하나의 주소만 가질 때는 server.address와 server.port가 아예 기록되지 않았고, 2.x 기본 시맨틱 컨벤션 설정에서는 localhost:3306이 보고됐습니다. 같은 서버를 jdbc:mysql://db.example.com:3307/orders로 쓰면 정확하게 기록됐고요.

📖 용어: server.address, server.port
스팬이 어느 서버를 향한 호출인지 알려 주는 속성이에요. 데이터베이스 호출이면 접속한 DB 서버의 호스트와 포트가 들어갑니다. 이 값이 비면 트레이스 화면에서 어느 DB로 간 쿼리인지 구분할 수 없고, 값이 잘못되면 다른 서버의 쿼리로 보여요.

원인은 URL을 어느 파서에 넘기느냐에 있었어요. MysqlUrlParser는 address= 블록을 서브프로토콜이 있는 경로(mysql:replication://address=...)에서만 읽었습니다. 서브프로토콜이 없는 URL은 GenericUrlParser로 넘어가는데, 이 파서가 쓰는 java.net.URI는 address=(host=...)(port=...)에서 호스트를 찾지 못해요. 그래서 설정된 서버 정보가 아무것도 기록되지 않았습니다. 데이터베이스 이름, 사용자, 쿼리 파라미터는 GenericUrlParser가 계속 읽을 수 있어서 이 부분은 문제가 없었어요.

그림 1. 서브프로토콜 없는 address= URL만 호스트를 읽을 곳이 없었어요

3. 고친 코드와 리뷰에서 두 번 바뀐 곳

첫 커밋(1871d1ec)은 서브프로토콜이 없는 address= URL을 서브프로토콜이 있는 경로와 같은 파서로 넘기는 방식이었어요. 열고 4분 뒤에 자동 리뷰 봇이 인라인 코멘트를 남겼습니다. 이 경로로 보내면 데이터베이스 이름의 퍼센트 디코딩이 사라진다는 지적이었어요. jdbc:mysql://address=(host=db.example.com)(port=3307)/orders%2darchive는 원래 GenericUrlParser가 URI.getPath()로 디코딩해서 db.namespace=orders-archive가 되는데, 서브프로토콜 파서는 원문 orders%2darchive를 그대로 저장한다는 설명이었어요.

📖 용어: 퍼센트 인코딩(%2d)
URL에서 특별한 문자를 %와 16진수 두 자리로 적는 방식이에요. %2d는 하이픈(-)입니다. 데이터베이스 이름이 orders%2darchive로 적혀 있어도 실제 이름은 orders-archive라서, 디코딩을 빠뜨리면 db.namespace 속성 값이 실제 DB 이름과 달라져요.

맞는 지적이어서 방향을 바꿨어요. 이 URL들을 GenericUrlParser에 그대로 두고, 호스트와 포트만 address= 블록에서 추가로 읽도록 했습니다. 14:38에 커밋 ec194948로 올리고 봇의 코멘트에 답글을 달았어요. 이때 jdbc:mysql://address=(host=mdb.host)(port=33)/mdb%2ddb → mdb-db 케이스를 추가했고, 이 케이스는 이전 커밋에서 실패합니다.

그 직후 봇의 다음 리뷰(14:42)가 이미 있던 코드에서 두 번째 문제를 짚었어요. parseMariaAddress가 호스트와 포트를 찾을 때 address= 블록만이 아니라 URL의 나머지 전체를 훑는다는 내용이었습니다. 예를 들어 jdbc:mysql://address=(host=db.example.com)/orders?password=(port=3307)에서는 포트를 적지 않았는데도, 쿼리 문자열의 password=(port=3307)에서 포트 3307을 읽게 돼요. 위 (2)의 두 번째 실패 메시지가 이 현상이에요. 서브프로토콜이 있는 mysql:replication:// 형식에서도 되돌린 코드는 port=33을 읽었습니다. 이 PR이 새로 만든 문제가 아니라 원래 있던 문제였지만, 새 경로가 같은 함수를 쓰게 되므로 함께 고쳤어요. 23:35에 커밋 b7f5249a를 올리고 PR에 이 내용을 코멘트로 남겼습니다.

최종 본 코드 변경은 10줄 추가, 2줄 삭제였어요.

첫 블록은 GenericUrlParser가 먼저 데이터베이스 이름, 사용자, 쿼리 파라미터를 처리한 뒤에 address=로 시작하는 URL만 호스트와 포트를 따로 읽는 부분이에요. 둘째 블록은 처음 /나 ?가 나오는 곳에서 자르고, 그 앞부분에서만 주소를 찾는 부분입니다. 호스트가 여러 개인 ,address= 형식은 PR 본문에 따르면 기존의 다중 대상 처리로 이미 동작했고, 새 경로에서도 계속 동작하는지 보이려고 테스트에 넣었어요.

PR은 10-17 07:03에 열었고, 사람 리뷰어의 승인은 두 번이었어요. trask가 10-18 19:26에, laurit이 10-19 14:28:02에 승인했고, 같은 14:28:18에 laurit이 머지했습니다. 사람 리뷰어가 코드를 고쳐 달라고 요청한 코멘트는 없었어요. 바뀐 부분은 모두 자동 리뷰 봇의 두 지적에서 나왔습니다. gh로 다시 조회한 지금 상태는 MERGED이고, 머지 커밋은 c0a9e91262예요.

5. 명령 이름이 error.type이 된 Lettuce (#20661)

두 번째 건은 Redis 클라이언트 Lettuce의 계측이에요. PR 본문에 따르면 Lettuce 라이브러리 계측(LettuceTelemetry)과 Lettuce 6.6 이상에서, TimeoutOptions로 명령 타임아웃을 설정했을 때처럼 클라이언트 쪽에서 실패한 명령의 error.type이 BLPOP., GET., SET.처럼 명령 이름으로 기록됐어요.

📖 용어: error.type과 db.client.operation.duration
error.type은 호출이 실패했을 때 실패 종류를 짧게 적는 속성이에요. 예외가 있으면 보통 예외 클래스 이름이 들어가고, Redis가 에러 응답을 보냈으면 WRONGTYPE 같은 에러 코드가 들어갑니다. db.client.operation.duration은 DB 호출 시간을 모아 두는 메트릭이고, error.type이 그 메트릭을 나누는 기준(차원)의 하나예요.

스팬 속성만 이상한 것이 아니었어요. error.type은 db.client.operation.duration 메트릭의 차원이기도 해서, 명령 종류마다 새로운 error.type 값이 하나씩 생깁니다. 타임아웃이라는 같은 실패가 명령 개수만큼 다른 값으로 갈라져 기록되는 셈이에요.

원인은 Lettuce가 명령을 예외로 끝낼 때 동작에 있었어요. PR 본문에 따르면 Command.completeExceptionally는 output.setError(throwable.getMessage())를 호출해서, Redis의 에러 응답뿐 아니라 클라이언트 쪽 예외의 메시지도 명령의 출력(output)에 복사합니다. 계측은 output.getError()에서 첫 번째 공백 앞의 대문자 단어를 Redis 에러 접두어로 읽었어요. Lettuce 6.6 이상의 타임아웃 메시지는 "%s. Command timed out after %s" 형식이고 맨 앞에 명령 종류가 와서, 접두어가 BLPOP.이 된 거예요.

6. 5.1에서는 통과하고 최신 버전에서만 실패했다

이 PR의 회귀 테스트는 AbstractLettuceAsyncClientTest에 추가한 testCommandTimeoutDoesNotReportRedisErrorType 하나예요. 명령 타임아웃을 100ms로 설정하고 존재하지 않는 리스트에 blpop(1, "TIMEOUT_LIST")을 보내면, 3초 안에 RedisCommandTimeoutException이 오는지 확인한 뒤 스팬과 메트릭의 error.type을 검사해요. 머지 커밋 b1fcd7954b에서 먼저 돌렸습니다. Redis는 Testcontainers의 redis:6.2.3-alpine 컨테이너를 썼어요.

$ ./gradlew --no-daemon --max-workers=2 -Dorg.gradle.jvmargs=-Xmx2g \ :instrumentation:lettuce:lettuce-5.1:library:test \ --tests '*LettuceAsyncClientTest*' --tests '*LettuceDbAttributesGetterTest*' # (1) 머지 커밋, 기본 의존성(Lettuce 5.1 계열) 9 + 2 tests, 0 failed BUILD SUCCESSFUL in 1m 8s

다음에 본 코드(library/src/main의 다섯 파일)를 직전 커밋으로 되돌리고 같은 명령을 다시 돌렸어요. 결과는 통과였습니다. 되돌렸는데도 테스트가 실패하지 않은 거예요. PR 본문에 이 결과를 설명하는 내용이 있었어요. Lettuce 5.1의 타임아웃 메시지에는 명령 이름이 붙지 않고, 5.1의 트레이싱 어댑터는 예외 없이 에러 태그만 넘깁니다. 그래서 기본 의존성에서는 이 테스트가 error.type이 없다는 것을 기대하고, 최신 의존성에서는 예외 클래스 이름을 기대해요. 5.1에서는 버그가 드러나지 않으니 테스트도 통과하는 것이 맞았습니다.

그래서 최신 의존성으로 같은 되돌린 상태를 다시 돌렸어요.

but was: "BLPOP."이 이슈에서 말한 값 그대로예요. 이 실행에서 Gradle 캐시에 lettuce-core-7.9.0.RELEASE가 새로 내려받아졌어요. 최신 의존성이 이 버전으로 해석된 것으로 보이지만, 해석된 버전을 로그에서 직접 읽지는 않았습니다. 수정 전에는 BLPOP.이 기록되고 수정 후에는 예외 클래스 이름이 기록된다는 것까지가 이번에 확인한 범위예요. 5.1과 6.6 사이의 버전은 돌리지 않았습니다.

7. 고친 코드와 리뷰어가 바꾼 구조

첫 커밋(9f5ad194)의 수정은 출력의 에러 메시지를 쓰는 조건을 좁히는 것이었어요. 예외가 없거나 예외가 RedisCommandExecutionException일 때, 즉 Redis가 실제로 에러 응답을 보냈을 때만 메시지를 에러 접두어로 읽습니다. 그 밖의 실패는 #19075 이전처럼 예외 클래스 이름(io.lettuce.core.RedisCommandTimeoutException)으로 폴백하고, 스팬 상태는 계속 error로 설정해요.

10-18 03:52에 리뷰어 trask가 코멘트를 남겼어요. "I had trouble following the (existing) code around this change, so pushed a bit of refactoring"이라며 리팩터링 커밋 672c7572를 직접 올렸다는 내용이었습니다. 기존 코드는 응답 객체(LettuceResponse)에 에러 메시지와 예외를 그대로 담아 넘기고, getErrorType이 나중에 메시지를 해석했어요. 리팩터링은 이 분류를 응답을 만드는 시점으로 앞당겼습니다.

// LettuceResponse: 실패 여부와 Redis 에러 타입을 만들 때 정해 둔다 static LettuceResponse fromErrorMessage(@Nullable String errorMessage) { return new LettuceResponse(errorMessage != null, extractRedisErrorPrefix(errorMessage)); } // OpenTelemetryTracing private void finishFromOutput(@Nullable String errorMessage, @Nullable Throwable error) { // Lettuce also copies the message of client-side failures, such as command // timeouts, into the output, so only treat it as a Redis error reply when there is // no client-side failure if (error instanceof RedisCommandExecutionException) { end(LettuceResponse.fromErrorMessage(errorMessage), error); } else if (error != null) { end(null, error); } else { end(LettuceResponse.fromErrorMessage(errorMessage), null); } }

예외가 Redis 에러 응답이면 메시지에서 접두어를 만들고, 그 밖의 예외면 응답 없이 예외만 넘겨요. 예외가 없으면 출력의 메시지를 그대로 Redis 에러 응답으로 봅니다. 테스트도 같이 바뀌어서, 타임아웃 테스트가 스팬의 모든 속성과 메트릭의 error.type을 함께 검사해요. 최종 PR은 파일 6개, 110줄 추가와 46줄 삭제입니다.

리팩터링 커밋을 확인한 뒤 04:30에 저는 이렇게 답했어요. "Classifying the response up front (failed vs. Redis error type) is much easier to follow than passing the raw message and throwable around." 제가 낸 수정은 조건문을 좁히는 변경이었는데, 머지된 PR에서는 응답 객체가 실패 여부와 Redis 에러 타입을 먼저 정해 두는 구조로 바뀌었어요.

8. Lettuce PR의 결과와 남은 한계

PR은 10-17 07:10에 열었어요. trask가 10-18 19:24에, laurit이 10-19 07:00:49에 승인했고, laurit이 07:00:57에 머지했습니다. 지금 상태는 MERGED이고 머지 커밋은 b1fcd7954b예요. PR 본문에는 Java 에이전트가 영향을 받지 않는다는 설명도 있었어요. 에이전트는 이제 모든 버전에서 Lettuce 5.0 모듈을 쓰기 때문이고(#20533), 이 수정은 다른 Redis 클라이언트 계측이 같은 getter를 참고하려는 #20457과 관련이 있다고 적혀 있습니다.

이 글에서 확인하지 못한 것도 적어 둘게요.

첫째, JDBC는 파서 단위 테스트의 null까지만 확인했고, 실제 앱에서 스팬의 server.address가 어떻게 보이는지는 이번에 다시 만들지 않았어요. 둘째, Lettuce는 라이브러리 계측 모듈의 테스트로만 확인했습니다. Java 에이전트로 붙인 앱에서는 PR 본문의 설명대로 영향이 없다고 하지만, 이번에 실행해 보지는 않았어요. 셋째, Lettuce 최신 의존성 실행에서 해석된 버전을 로그에서 읽지 않았고, Lettuce의 BLPOP. 재현은 최신 의존성 한 가지 조합에서만 확인했어요.

두 건에서 같은 모양의 원인이 있었어요. 둘 다 문자열 하나에서 값을 꺼내는 코드였고, 읽어야 할 부분 밖의 내용까지 읽어서 값이 틀렸습니다. JDBC에서는 쿼리 문자열의 괄호 표기가, Lettuce에서는 클라이언트 예외의 메시지가 그 내용이었어요.

소스 기준: #20660(머지 커밋 c0a9e91262), #20661(머지 커밋 b1fcd7954b). 재현 명령과 출력은 labs/open-source-contribute/opentelemetry/repro.md에 남겼어요.

✍️ 오늘의 요약
서브프로토콜 없는 JDBC address= URL은 서버 주소가 기록되지 않았고, Lettuce 타임아웃의 error.type은 BLPOP.처럼 명령 이름이 됐어요. 둘 다 머지됐습니다.

JDBC는 URL을 어느 파서에 넘기느냐가 원인이었고, 리뷰에서 퍼센트 디코딩과 쿼리 문자열 오독 두 가지가 더 드러나 호스트와 포트만 address= 블록에서 읽도록 고쳤어요. Lettuce는 예외 메시지를 Redis 에러 접두어로 읽은 것이 원인이었고, Redis가 보낸 에러 응답일 때만 접두어를 쓰도록 바꿨습니다. 테스트가 통과한다고 수정이 검증된 것은 아니라서, 두 번째 건은 최신 의존성으로 다시 돌려서야 실패를 볼 수 있었어요.
