2. 이슈 #8207: 같은 모양의 쓰기를 한곳에 모았다

#8174를 머지한 다음 날인 10월 16일 12:48에 #8207을 열었어요. 승인 코멘트의 항목 5와 6이 요청한 이슈예요. 항목 6에서 리뷰어는 "머지 전에" 열어 달라고 썼는데 실제로는 머지 뒤에 열었어요. 3분 뒤 코멘트가 나중에 해도 된다고 덧붙이기는 했어요. 이슈 본문은 핸들러가 실행을 읽고, 판단하고, repository.updateStatus(execution)로 되쓰는 모양이 여러 곳에 있다는 점에서 시작해요. SQL 저장소에서 이 호출이 상태만이 아니라 실행 본문 전체와 canceled 열을 핸들러의 복사본으로 쓰기 때문에, 읽은 뒤 쓰기 전에 다른 쪽이 한 일(사용자의 취소나 재시작)이 덮어쓰인다는 설명이에요. 실행 단위 쓰기는 잠금이 없고, RetriableLock은 스테이지 id를 키로 쓰기 때문에 시작 경로를 빼면 보호되지 않는다고 적었어요.

📖 용어: 취소(cancel)와 CompleteExecution
사용자가 파이프라인을 취소하면 실행 상태가 CANCELED가 되고 canceled=true가 저장돼요. CompleteExecution은 마지막 스테이지가 끝난 뒤 실행의 최종 상태(SUCCEEDED 등)를 저장하는 큐 메시지예요. 둘이 같은 실행에 거의 동시에 쓰면 나중에 쓴 쪽이 이겨요.

이슈에는 재현 세 건이 적혀 있어요. 실제 핸들러(CompleteExecutionHandler, RestartStageHandler, CancelExecutionHandler, StartExecutionHandler)를 MySQL 8.0.40(Testcontainers)의 SqlExecutionRepository 위에서 돌리고, 첫 핸들러가 실행을 읽은 직후에 멈춘 사이 두 번째 핸들러를 돌린 결과예요. 케이스마다 같은 단계에서 끼어들기만 뺀 대조군이 있어요. 아래는 이슈 본문에 있는 텍스트 출력 중 둘이에요.

(2)는 마지막 스테이지가 성공한 뒤 CompleteExecution이 실행을 읽었는데 사용자가 취소한 경우예요. 취소가 저장한 CANCELED를 핸들러의 복사본(SUCCEEDED, canceled=false)이 덮어써서, 취소한 기록이 사라지고 ExecutionComplete 이벤트도 CANCELED와 SUCCEEDED 두 개가 나가요. (1)은 같은 CompleteExecution의 오래된 복사본이 스테이지 재시작을 되돌려서 실행이 TERMINAL에 영구히 남는 경우이고, (3)은 3장에서 다룰 롤백이에요. 이 글을 쓰면서 이 세 건 중 (3)만 #8208의 테스트로 다시 돌렸고, (1)과 (2)는 이슈 본문의 출력을 인용했어요. 이 둘을 돌리는 테스트는 열린 PR에 들어 있지 않아서, 로컬에 받은 저장소에서는 실행할 수 없었어요.

이슈에는 실행 단위 쓰기를 전부 훑은 표도 있어요. 시작 경로는 #8174가 고쳤고, 롤백은 #8208이 고치고, CompleteExecutionHandler와 RestartStageHandler는 같은 모양이라고 적었어요. SqlExecutionRepository의 cancel, pause, resume은 트랜잭션 안에서 읽고 쓰지만 행 잠금이 없어요(승인 코멘트의 항목 2). 기본 구현(Redis)이 원자적이지 않다는 항목 5는 이 이슈를 추적 이슈로 삼는다고 적었어요. 초기 스테이지가 없는 TERMINAL 경로와 ConfigurationErrorHandler는 실행이 시작되기 전의 쓰기라서 위험이 낮다고 분류했어요. 스테이지 단위 쓰기(storeStage, 호출 지점 약 30곳)는 범위에서 뺐어요. 스테이지별로 메시지 흐름이 순서를 지키고 RunTask가 스테이지 잠금을 잡기 때문이라고 적었어요.

이슈 끝에는 해결 방향 세 가지를 적고 리뷰어에게 물었어요. 하나는 핸들러마다 읽었던 상태를 기대값으로 updateStatusIfExpected를 쓰는 것이에요. 다른 하나는 저장소의 doForeignAware에서 행을 잠가서 cancel, pause, resume도 원자적으로 만드는 것이에요. 마지막은 비교가 status만 보고 쓰기는 본문 전체를 한다는 점을 줄이는 방법(상태만 갱신하거나 canceled도 비교)이에요. 리뷰어가 큐 시스템을 더 크게 바꿀 계획을 비친 적이 있어서, 더 진행하기 전에 어느 방향을 원하는지 물었어요. 같은 날 12:51에 "롤백 수정과 잠금에 의존하는 테스트부터 하고, 방향이 정해지면 다른 핸들러를 이어서 하겠다"고 코멘트를 남겼어요. 2026-10-22 02:03에는 리뷰어를 지목해서 두 PR이 올라와 있다고 알리고 방향을 다시 물었어요. 2026-10-22 현재 이 이슈의 코멘트는 제 것 두 개뿐이고, 리뷰어의 답은 없어요.

3. #8208: 롤백이 취소를 되돌리던 경로

항목 1은 승인 코멘트에서 가장 작은 항목이었어요. 리뷰어가 구간이 아주 좁다고 쓴 이 대상은, StartStage 푸시가 실패했을 때 StartExecutionHandler가 실행을 NOT_STARTED로 되돌리는 롤백이에요. 이 롤백이 있는 이유는, 큐가 같은 StartExecution을 다시 배달했을 때 NOT_STARTED 검사에서 메시지가 버려지지 않게 하려는 것이에요. 문제는 이 롤백이 #8174 이후에도 무조건 updateStatus로 핸들러의 복사본을 쓴다는 점이었어요.

PR 본문이 취소를 예로 들어 적은 순서는 다섯 단계예요. 핸들러가 실행을 RUNNING으로 바꾸고, StartStage 푸시가 연결 오류 같은 이유로 실패하고, 그 사이에 사용자가 취소하면 아직 스테이지가 시작되지 않았으니 CANCELED, canceled=true가 저장돼요. 그다음 롤백이 핸들러의 복사본(NOT_STARTED, canceled=false)을 쓰고, 다시 배달된 StartExecution은 취소되지 않은 NOT_STARTED 실행을 보고 시작해요. 취소한 파이프라인이 그대로 실행되는 결과가 돼요. 구간이 좁다고 해도 결과가 이렇게 나쁘니 닫을 가치가 있다고 판단했어요.

그림 2. 롤백이 실행 전체를 되쓰기 때문에 취소(canceled=true)가 지워져요

수정은 롤백을 #8174에서 쓴 같은 방법으로 바꾸는 것이에요. 저장된 상태가 아직 RUNNING일 때만 NOT_STARTED로 되돌리고, 아니라면 저장된 상태를 로그에 남기고 쓰기를 건너뛰어요. 예외는 그대로 던져서 메시지가 다시 배달되게 해요. 다시 배달된 핸들러는 CANCELED를 보고 실행을 끝내요.

execution.updateStatus(NOT_STARTED) - repository.updateStatus(execution) + if (!repository.updateStatusIfExpected(execution, RUNNING)) { + log.warn( + "Not restoring execution (type ${execution.type}, id {}, application: {}) to NOT_STARTED: {}.", + value("executionId", execution.id), + value("application", execution.application), + describeStoredStatus(execution) + ) + } throw e

PR 본문이 스스로 적은 한계가 있어요. 비교는 status만 보기 때문에, 초기 스테이지가 여러 개이고 일부가 이미 푸시된 뒤에 실패하면 취소가 상태를 RUNNING인 채로 canceled=true만 바꿀 수 있어요. 그 경우 롤백은 여전히 canceled를 덮어써요. 이건 이슈의 세 번째 방향(비교는 상태, 쓰기는 본문 전체)이라서 이 PR에서는 건드리지 않았어요. 같은 PR의 두 번째 커밋은 updateStatusIfExpected의 TODO가 "추적 이슈가 없다"고 적은 문장을 #8207을 가리키는 문장으로 고쳤어요. 승인 코멘트의 항목 5가 요청한 것이에요.

테스트는 두 곳이에요. StartExecutionHandlerTest에 두 케이스를 더해서, 롤백이 updateStatusIfExpected(pipeline, RUNNING)를 쓰고 updateStatus를 부르지 않는 것을 확인해요. 새 파일 StartExecutionHandlerSqlTest는 실제 StartExecutionHandler와 CancelExecutionHandler를 MySQL의 SqlExecutionRepository 위에서 돌려요. 큐를 감싼 객체가 StartStage 푸시를 막아 두고, 그 사이에 테스트가 취소하고, 푸시를 실패시킨 뒤 StartExecution을 다시 배달해요.

4. #8209: 잠금이 있어야만 통과하는 테스트

항목 3은 1편에서 제가 스스로 적어 둔 한계이기도 했어요. #8174의 SQL 테스트는 오래된 복사본을 순서대로 재생하는 것이라, FOR UPDATE를 빼도 통과한다는 점이에요. 리뷰어는 "I'd ask for it, since atomicity is the whole point"라고 적고, 행을 잡은 트랜잭션을 열어 둔 채 조건부 저장이 막히는지 보거나, 여러 스레드를 경쟁시켜서 true가 정확히 하나만 나오는지 보는 방법을 제안했어요.

#8209는 첫 번째 방법을 따랐어요. 테스트가 하는 일은 세 단계예요.

1) 다른 트랜잭션이 실행의 행을 SELECT ... FOR UPDATE로 잠그고 붙잡는다 2) NOT_STARTED로 읽어 둔 오래된 복사본이 다른 스레드에서 updateStatusIfExpected(copy, NOT_STARTED)를 호출한다. 1초 뒤에도 끝나지 않고 막혀 있는지 확인한다 (TimeoutException) 3) 다른 트랜잭션이 SUCCEEDED를 저장하고 커밋한다. 그러면 조건부 저장은 false를 돌려주고, 저장된 값은 SUCCEEDED로 남아야 한다

순서는 행 잠금과 래치로 정해지므로, 타이밍에 기대지 않는 결정적인 테스트예요. 2단계의 "1초 뒤에도 막혀 있다"는 확인이 핵심이에요. 이 확인이 있어야 잠금을 기다리지 않고 자기가 먼저 읽은 상태를 쓰는 구현이 걸러져요. FOR UPDATE가 없으면 조건부 저장은 쓰는 시점에는 행 잠금 때문에 막히지만, 비교는 잠금 전에 읽은 NOT_STARTED로 이미 끝나 있어서 true를 돌려주고 커밋된 SUCCEEDED를 덮어써요. 이것이 잠금이 막는 갱신 손실(lost update)이에요.

📖 용어: 갱신 손실(lost update)
두 트랜잭션이 같은 값을 읽고 각자 고쳐서 저장할 때, 나중에 저장한 쪽이 먼저 저장한 쪽의 변경을 모르고 덮어써서 변경 하나가 없어지는 현상이에요. 행을 잠그고 읽으면 나중 트랜잭션이 먼저 커밋된 값을 읽게 돼서 생기지 않아요.
