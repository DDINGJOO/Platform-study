1편. 검증 코드가 있는데 null이 통과한 이유
2편. 같은 실수를 저장소 전체에서 찾아보니 ← 지금 이 글

1편의 버그는 모양이 단순했어요. LettuceAssert.notNull(clientOptions, ...)가 연달아 두 번 나오고, 두 번째 줄의 메시지만 다른 인자를 가리켰습니다. 사람이 읽을 때는 놓치기 쉽지만, 기계로 찾기에는 좋은 모양이에요. "같은 변수를 두 번 검증하는 곳"은 문자열 패턴으로 표현할 수 있으니까요.

#3952가 머지되고 이틀 뒤인 2026-10-16에, 같은 실수가 저장소의 다른 곳에도 있는지 스크립트로 훑었어요. 결과는 #3954(자바독 오탈자)와 #3955(단언 메시지) 두 PR이 됐고, 둘 다 같은 날 머지됐습니다. 이 글에서는 아래 질문들에 답해 볼게요.

• 스크립트가 낸 58건과 77건 가운데 왜 대부분이 버그가 아니었을까요?
• 오탐을 거를 때 무엇을 기준으로 삼았을까요?
• 한 번의 탐색에서 나온 수정을 왜 PR 두 개로 나눴을까요?
• CI가 실패했는데 왜 이 변경과 무관하다고 봤을까요?

탐색 과정은 당시의 작업 기록을 따랐어요. 당시 스크립트는 남아 있지 않아서, 2026-10-22에 기록된 규칙대로 스크립트를 다시 짜서 같은 커밋에 돌려 봤습니다. 재실행 결과는 그렇다고 밝혀 두고 적을게요.

1. 같은 변수를 두 번 검증하는 곳: 58블록

첫 번째 규칙은 1편의 버그 모양을 그대로 옮긴 것이에요. LettuceAssert 호출이 연속으로 이어지는 블록 안에서, 첫 번째 인자로 같은 식별자가 두 번 이상 나오면 후보로 잡았습니다. 당시 이 규칙은 58블록을 찾았어요.

그런데 58블록을 열어 보니 대부분이 의도된 코드였어요. 예를 들면 이런 모양입니다.

// RedisCommandBuilder.java 819-821 LettuceAssert.notNull(commands, "Commands " + MUST_NOT_BE_NULL); LettuceAssert.notEmpty(commands, "Commands " + MUST_NOT_BE_EMPTY); LettuceAssert.noNullElements(commands, "Commands " + MUST_NOT_CONTAIN_NULL_ELEMENTS);

같은 commands를 세 번 검사하지만, 검사 내용이 null 여부, 비어 있는지 여부, null 원소 포함 여부로 각각 다르다는 뜻이에요. 앞 단계를 통과해야 다음 단계를 검사할 수 있는 순서라서, 같은 변수가 반복되는 것이 정상입니다.

📖 용어: 오탐 (false positive)
탐색 규칙에는 걸렸지만 실제로는 문제가 아닌 결과예요. 규칙을 넓게 잡을수록 놓치는 것은 줄지만 오탐이 늘어서, 사람이 걸러야 할 양이 많아집니다.

여기서 거르는 기준이 나왔어요. 같은 변수를 여러 번 검사하는 것은 문제가 아니고, 같은 변수를 같은 방식으로 두 번 검사하는 것이 문제입니다. 1편의 버그는 notNull을 같은 변수에 두 번 호출한 경우였어요. 두 번째 호출은 첫 번째 호출이 이미 통과시킨 값을 다시 검사하므로, 어떤 입력에서도 실패하지 않습니다.

이 기준이 실제로 갈라지는지 2026-10-22에 다시 확인했어요. 기록된 규칙대로 짠 스크립트에 "같은 검증 메서드가 같은 식별자에 두 번" 조건을 추가해, #3952 직전 커밋과 이후 커밋에서 돌렸습니다.

$ python3 -I scan-dup-assert.py <repo> <rev> # src/main/java 대상 rev 같은 식별자 반복 블록 그중 같은 메서드 두 번 be963b39 59 1 DefaultEndpoint.java 141,142 (clientOptions) a761616a 58 0 (#3954·#3955의 기준 커밋) 3da7a61f 58 0 (#3955 머지 후)

#3952 직전에는 59블록이 잡히고, 그중 같은 메서드를 두 번 쓴 곳은 1편의 DefaultEndpoint 하나뿐이었어요. 기준 커밋에서는 당시 기록과 같은 58블록이 나왔고, 같은 메서드를 두 번 쓴 곳은 0건이었습니다. 즉 1차 탐색의 58블록은 모두 단계적 검증이었고, 같은 실수가 남은 곳은 없었어요.

2. 메시지와 변수가 어긋난 곳: 77건 중 2건

1편의 버그는 다른 방향에서 보면 "메시지가 말하는 인자와 실제로 검사하는 인자가 다른 경우"이기도 해요. 그래서 두 번째 규칙은 단언 메시지의 첫 단어(주어)와 검사 대상 변수 이름을 비교했습니다. 당시 이 규칙은 77건을 냈어요.

77건 대부분은 메시지가 변수 이름 대신 개념이나 타입 이름을 쓴 정상 코드였어요. 변수 이름은 type인데 메시지는 "Class must not be null"이라고 쓰는 식입니다.

2026-10-22에 다시 돌려 보니 이 경향이 숫자로 보였어요. 대소문자만 무시하고 완전히 일치하지 않으면 후보로 잡는 가장 느슨한 규칙은 380건을 냈습니다. 한쪽 이름이 다른 쪽에 포함되면 제외하는 규칙(codec과 RedisCodec)으로 좁혀도 145건이 남았어요. 당시의 77건과 숫자가 다른 것은 당시 규칙의 세부 필터가 기록에 남지 않았기 때문입니다.

$ python3 -I scan-msg-subject.py <repo> a761616a 규칙 A (완전 일치가 아니면 후보) 380건 규칙 B (포함 관계면 제외) 145건 B의 상위 패턴: type → "Command" 9, name → "Parameter" 7, value → "Parameter" 6, seconds → "Timeout" 4, script → "Lua" 4 두 규칙 모두에서 잡힌 실제 결함: ClientOptions.java:329 reauthenticateBehavior → "ReuthenticatBehavior must not be null" CompressionCodec.java:156 to → "From must not be null"

상위 패턴은 모두 메시지가 개념을 가리키는 정상 표현이라는 뜻이에요. 규칙을 어떻게 잡아도 실제 결함 두 건은 빠지지 않았고, 차이는 사람이 걸러야 할 오탐의 양이었습니다.

두 건이 결함인 이유는 서로 달라요. ClientOptions.Builder#reauthenticateBehavior의 메시지는 타입 이름 ReauthenticateBehavior를 잘못 쓴 것이에요. 이 빌더는 공개 API라서, null을 넘긴 사용자가 오탈자가 섞인 메시지를 직접 보게 됩니다. CompressionCodec#copy는 from과 to를 차례로 검사하는데, 두 메시지가 모두 From must not be null이었어요. 출력 스트림이 null이어도 입력 스트림이 null이라고 보고하는 셈입니다.

💡 오탐을 거른 기준
• 메시지가 변수 대신 개념·타입 이름을 쓴 경우(type에 "Class")는 정상으로 봤어요.
• 메시지가 같은 메서드의 다른 인자를 가리키는 경우(to에 "From")는 결함으로 봤어요.
• 메시지 속 이름에 오탈자가 있는 경우("Reuthenticat")도 결함으로 봤어요.
• 결함이 아니거나 너무 사소한 후보(SslOptions의 메시지 차이, 소문자 주어 2곳)는 제외했어요.
그림 1. 두 규칙 모두 후보 대부분은 정상 코드였어요

3. 같은 김에 본 오탈자: 여섯 갈래의 API

메시지를 읽는 김에 자주 틀리는 영어 단어 몇 개도 저장소 전체에서 찾았어요. lenght가 12곳(6파일), overriden이 8곳, occured가 1곳 나왔습니다.

lenght 12곳은 모두 스트림 명령 XACK와 XLEN의 자바독 @return 설명이었어요. 같은 파일 안의 다른 자바독은 @param count length of the stream처럼 올바르게 쓰고 있어서, 한 파일 안에서도 표기가 엇갈린 상태였습니다.

6파일이 된 이유는 Lettuce가 같은 명령을 여러 API 형태로 제공하기 때문이에요. 동기, 비동기, 리액티브, 클러스터 동기·비동기, Kotlin 코루틴 인터페이스가 각자 같은 문서 주석을 가지고 있습니다. 저장소의 아키텍처 문서는 이 API 인터페이스들이 코드 생성물이 아니라 손으로 쓰는 파일이라고 설명해요. 그래서 한 곳만 고치면 나머지 다섯 곳에는 오탈자가 그대로 남습니다. 여섯 갈래를 모두 고쳤어요.

--- a/src/main/java/io/lettuce/core/api/sync/RedisStreamCommands.java +++ b/src/main/java/io/lettuce/core/api/sync/RedisStreamCommands.java - * @return simple-reply the lenght of acknowledged messages. + * @return simple-reply the length of acknowledged messages. ... - * @return simple-reply the lenght of the stream. + * @return simple-reply the length of the stream. (같은 변경을 async, reactive, cluster async, cluster sync, Kotlin coroutines 인터페이스에도)
📖 용어: 자바독 (Javadoc)
Java 소스의 /** ... */ 주석으로 작성하는 API 문서예요. IDE의 자동 완성 설명과 배포되는 API 문서에 그대로 나타나기 때문에, 공개 인터페이스의 자바독 오탈자는 사용자가 직접 보게 됩니다.

4. 한 번의 탐색, 두 개의 PR

찾은 수정은 두 종류였어요. A는 자바독과 주석의 오탈자(10파일), B는 런타임에 던지는 단언 메시지(2파일)입니다. 둘 다 동작을 바꾸지 않는 문자열 수정이라 한 PR로 묶을 수도 있었어요.

먼저 이 저장소가 이런 PR을 어떻게 받아 왔는지 머지 이력을 봤어요. 파일 하나에 1~3줄을 고친 오탈자 PR이 꾸준히 머지됐습니다(#2213, #1826, #1632, #1497). 여러 오탈자를 묶은 PR도 머지된 적이 있어요(#3423 "docs: Fix various typos in documentation"). 작은 PR도, 묶은 PR도 받는 저장소였습니다.

그래서 크기가 아니라 리뷰어가 할 판단을 기준으로 나눴어요. 자바독 오탈자는 철자만 보면 되지만, 예외 메시지는 "이 문자열에 기대는 코드가 없나"라는 질문이 붙습니다. 테스트나 사용자 코드가 메시지를 비교하고 있다면, 메시지 수정은 동작 변경이 될 수 있어요. 두 질문을 한 PR에 섞으면 오탈자 열 곳을 보는 동안 메시지 두 곳의 위험도 함께 판단해야 합니다.

B 안의 두 메시지 수정은 다시 쪼개지 않았어요. 둘 다 "메시지가 잘못된 이름을 말한다"는 같은 성격이고, 리뷰어가 던질 질문도 같기 때문이에요.

#3954 Fix typos in Javadoc and comments 10파일 +21/-21 #3955 Fix incorrect argument names in assertion messages 2파일 +2/-2

5. 올리기 전에 확인한 것

B를 올리기 전에 메시지 문자열에 의존하는 테스트를 검색했어요. RedisCommandBuilderUnitTests가 "From must not be null"을 단언하고 있었지만, 이는 RedisCommandBuilder#geodist의 from 검사를 위한 테스트였습니다. CompressionCodec과는 관계가 없어서 깨지는 테스트는 없었어요. 그리고 geodist는 from과 to에 각각 From, To 메시지를 쓰고 있어서, #3955의 수정은 이 표기를 따른 것이 됐습니다.

형식도 확인했어요. 이 저장소의 포매터 줄 길이 한도는 128자이고, 바뀐 줄 가운데 가장 긴 줄은 126자였습니다. ./mvnw formatter:validate는 두 브랜치 모두 통과했어요.

메시지가 실제로 바뀌는지는 이번에 다시 확인했어요. CompressionCodec#copy는 private static 메서드이고, 공개 경로에서는 내부에서 만든 스트림만 넘기므로 null이 들어갈 수 없습니다. 그래서 내려받은 사본에서 리플렉션으로 직접 호출하는 임시 테스트를 만들어 수정 전후에 돌렸어요. 같은 테스트에서 공개 빌더 reauthenticateBehavior(null)도 호출했습니다.

# 수정 전 (abcc00ef 버전) PROBE copy(from, null) -> java.lang.IllegalArgumentException: From must not be null PROBE reauthenticateBehavior(null) -> java.lang.IllegalArgumentException: ReuthenticatBehavior must not be null # 수정 후 (3da7a61f 버전) PROBE copy(from, null) -> java.lang.IllegalArgumentException: To must not be null PROBE reauthenticateBehavior(null) -> java.lang.IllegalArgumentException: ReauthenticateBehavior must not be null

수정 전에는 null인 출력 스트림을 입력 스트림 From으로 보고했고, 수정 후에는 To로 보고한다는 뜻이에요. 공개 빌더의 메시지도 타입 이름과 같아졌습니다. JDK 11로 실행했고, 한 번에 31~36초가 걸렸어요.

6. CI 실패를 무관하다고 본 근거

두 PR은 같은 시각에 올렸는데, #3955의 첫 CI만 실패했어요. CI는 Redis 6개 버전(7.2, 7.4, 8.2, 8.8, 8.10, 8.12)에서 전체 테스트를 돌리는데, 그중 Redis 8.10 잡 하나에서 테스트 한 개가 실패했습니다.

📖 용어: 매트릭스 빌드 (matrix build)
같은 테스트를 조건만 바꿔 여러 잡으로 나눠 돌리는 CI 구성이에요. 여기서는 Redis 서버 버전마다 잡이 하나씩 있어서, 한 잡만 실패하면 다른 잡의 결과와 비교할 수 있습니다.
[ERROR] io.lettuce.core.search.RediSearchIntegrationTests.testFtAlterAddingNewFields <<< FAILURE! org.opentest4j.AssertionFailedError: expected: 2L but was: 1L at io.lettuce.core.search.RediSearchIntegrationTests.testFtAlterAddingNewFields(RediSearchIntegrationTests.java:695) ... [ERROR] Tests run: 4784, Failures: 1, Errors: 0, Skipped: 88

4,784개 중 하나가 실패했고, 그 테스트는 이름이 가리키듯 인덱스에 필드를 추가하는 경우를 다루고, 기대값은 2인데 실제 값은 1이었다는 뜻이에요. 이 실패를 #3955와 무관하다고 본 근거는 세 가지였습니다.

📖 용어: 간헐 실패 (flaky test)
코드가 같아도 실행할 때마다 통과하거나 실패하는 테스트예요. 실제 서버와 통신하는 통합 테스트에서 타이밍이나 서버 상태 때문에 자주 생깁니다.

첫째, #3955가 바꾼 것은 ClientOptions.java와 CompressionCodec.java의 메시지 문자열 두 개였어요. 실패한 테스트는 검색 모듈의 통합 테스트이고, 실패 내용은 예외 메시지가 아니라 숫자 비교(expected: 2L but was: 1L)였습니다.

둘째, 같은 기준 커밋을 쓴 #3954는 통과했어요. 두 PR의 head 커밋(10686c5d, 0c6eebe1)은 부모가 같은 a761616a이고, #3954의 CI는 여섯 버전 모두 성공했습니다. #3954는 자바독만 바꿨으니, 같은 기준 코드에서 이 테스트가 통과한 실행이 하나 있는 셈이에요.

셋째, 같은 #3955 커밋에서도 Redis 8.10을 제외한 다섯 버전의 잡은 모두 성공했어요.

그래서 간헐 실패로 판단했습니다. 실패한 잡을 다시 돌려 확인하려면 관리자 권한이 필요해서, 재실행은 하지 못했어요.

이후의 기록은 GitHub에 남아 있어요. 2026-10-16 08:50:10(UTC)에 유지보수자 Aleksandar Todorov(a-TODO-rov)가 main을 #3955 브랜치에 병합한 커밋 77ddd8a8을 올렸고, 18초 뒤 08:50:28에 #3955를 머지했어요. #3954는 그보다 27초 앞선 08:50:01에 같은 유지보수자가 머지했습니다. 77ddd8a8에서 돈 CI는 여섯 버전 모두 성공했어요. 다만 머지가 커밋 18초 뒤였으니, 이 CI 결과는 머지 판단보다 늦게 나온 것입니다.

⚠️ 주의
"내 변경과 무관해 보인다"만으로는 간헐 실패의 근거가 약해요. 이번에는 같은 기준 커밋에서 통과한 실행(#3954)과 같은 커밋의 다른 버전에서 통과한 실행이 있었기 때문에 판단할 수 있었습니다. 재실행 권한이 없다면 이런 비교 대상을 먼저 찾아 두는 것이 좋아요.

7. 결과와 남은 한계

두 PR은 2026-10-16에 머지됐어요. 사람의 리뷰 코멘트나 수정 요청은 없었고, 제가 올린 커밋은 PR마다 처음 올린 하나였습니다. #3955에는 유지보수자의 main 병합 커밋이 하나 더해졌어요. 지금 main에서 lenght, overriden, occured는 src 아래에 한 곳도 남아 있지 않아요.

남은 한계도 적어 둘게요.

첫째, 사전 검사로는 실제 단어인 오탈자를 찾지 못했어요. 이번에 다시 확인하다가, 같은 스트림 자바독의 XLEN 설명 첫 줄이 지금도 여섯 파일 모두 Get the length of a steam.으로 남아 있는 것을 봤습니다. steam은 영어 사전에 있는 단어라 철자 목록에 걸리지 않아요. #3954에서 같은 자바독 블록의 @return 줄을 고쳤는데도 이 줄은 놓쳤습니다.

둘째, 두 탐색 규칙은 LettuceAssert 호출만 봤어요. Objects.requireNonNull이나 직접 쓴 if 검사는 대상이 아니었습니다. 같은 실수가 그런 형태로 남아 있는지는 확인하지 않았어요. 실제로 같은 모양의 실수가 다른 프로젝트에도 있었습니다. Keycloak의 AccessTokenContext는 Objects.requireNonNull로 grantType을 두 번 검사하고 rawTokenId는 검사하지 않았는데, 이 부분은 keycloak #53990에서 고쳤어요.

셋째, 탐색 결과를 거른 것은 사람의 판단이었어요. 당시의 77건 규칙은 세부 필터가 남지 않아서 이번에 같은 숫자를 다시 만들지 못했습니다. 1차 탐색의 58블록은 다시 돌려 같은 숫자를 얻었어요.
