2편. 같은 실수를 저장소 전체에서 찾아보니

Lettuce의 DefaultEndpoint 생성자 첫머리에는 인자 검증이 두 줄 있어요. 첫 줄은 ClientOptions must not be null, 둘째 줄은 ClientResources must not be null이라는 메시지를 가집니다. 메시지만 읽으면 두 인자를 모두 검사하는 코드예요. 그런데 둘째 줄이 검사하는 변수는 clientResources가 아니라 첫 줄과 같은 clientOptions였습니다.

그래서 clientResources에 null을 넣어도 생성자는 아무 말 없이 끝났어요. 이 글은 redis/lettuce #3952의 회고입니다. 검증 코드가 있는데 왜 null이 통과했는지, 그 null이 실제로 어디서 터지는지, 그리고 어떻게 재현하고 고쳤는지를 차례로 적었어요.

📖 용어: Lettuce
Java용 Redis 클라이언트 라이브러리예요. Netty 위에서 동기·비동기·리액티브 API를 함께 제공합니다. 이 글에서 다루는 DefaultEndpoint는 명령을 채널에 쓰고 응답을 기다리는 명령 큐를 관리하는 클래스예요.

이 PR은 2026-10-14에 열고 같은 날 머지됐어요. 다만 작업할 때의 과정 기록은 PR 본문과 커밋 메시지만 남아 있습니다. 그래서 이 글을 쓰기 전에 2026-10-22에 저장소를 새로 받아 재현을 다시 돌렸고, 글에 적은 출력은 모두 그때 얻은 것이에요.

1. 메시지는 맞는데 변수가 틀렸다

수정 전 생성자는 아래와 같았어요. 생성자의 자바독에는 두 인자 모두 must not be {@code null}이라고 적혀 있습니다.

/** * @param clientOptions client options for this connection, must not be {@code null}. * @param clientResources client resources for this connection, must not be {@code null}. */ public DefaultEndpoint(ClientOptions clientOptions, ClientResources clientResources) { LettuceAssert.notNull(clientOptions, "ClientOptions must not be null"); LettuceAssert.notNull(clientOptions, "ClientResources must not be null"); this.clientOptions = clientOptions; this.clientResources = clientResources; ...

두 번째 줄이 문제예요. 메시지는 ClientResources를 말하는데 첫 번째 인자는 clientOptions입니다. clientOptions가 null이면 첫 줄에서 이미 예외가 나므로, 둘째 줄은 어떤 입력에서도 실패하지 않는 검사가 됐어요.

📖 용어: LettuceAssert
Lettuce 내부의 인자 검증 유틸리티예요. notNull(값, 메시지)는 값이 null이면 그 메시지로 IllegalArgumentException을 던집니다. 검사 대상과 메시지를 따로 받기 때문에, 둘이 서로 다른 것을 가리켜도 컴파일러는 알려 주지 않아요.

두 줄은 길이와 들여쓰기가 같고, 메시지는 기대한 내용을 그대로 말해요. 검증 코드가 존재한다는 사실과 그 검증이 동작한다는 사실은 별개라는 점을 이 두 줄이 보여 줘요.

이 줄이 언제 들어왔는지 git log -L로 확인했어요. 2016년에 파일이 생길 때는 clientOptions 검사 한 줄만 있었고, 2018-06-09의 커밋 b53dc554(Add tracing support using Brave (OpenZipkin) #782)에서 지금의 둘째 줄이 추가됐습니다. 그 뒤 8년 넘게 같은 모양으로 남아 있었어요.

$ git log -L141,142:src/main/java/io/lettuce/core/protocol/DefaultEndpoint.java 26d42549 2026-10-14 Fix DefaultEndpoint client resources argument validation (#3952) - LettuceAssert.notNull(clientOptions, "ClientResources must not be null"); + LettuceAssert.notNull(clientResources, "ClientResources must not be null"); b53dc554 2018-06-09 Add tracing support using Brave (OpenZipkin) #782 + LettuceAssert.notNull(clientOptions, "ClientResources must not be null"); 30bbbbdf 2016-08-10 Decouple CommandHandler #317 + LettuceAssert.notNull(clientOptions, "ClientOptions must not be null");

세 커밋이 이 두 줄을 차례로 만들었다는 뜻이에요. 맨 아래가 파일을 처음 만든 커밋이고, 가운데 커밋이 잘못된 줄을 추가했습니다.

2. 통과한 null은 어디서 터지나

생성자를 통과한 null이 바로 문제를 일으키지는 않아요. 생성자 본문은 clientResources를 필드에 저장만 하고, 그 값을 쓰지 않습니다. 값은 getClientResources()로 다른 클래스에 넘어가요. PR 본문에는 이 값을 쓰는 곳으로 RedisChannelHandler와 ClusterDistributionChannelWriter 등을 적었습니다.

📖 용어: ClientResources
이벤트 루프, 타이머, 트레이싱 설정처럼 여러 연결이 함께 쓰는 자원을 담는 객체예요. 연결 객체는 만들어질 때 이 객체에서 트레이싱 사용 여부 같은 설정을 꺼내 갑니다.

PR 본문에는 "생성 지점과 먼 곳에서 NPE로 드러난다"고 적었지만, 실제 스택을 남기지는 않았어요. 그래서 재현할 때 수정 전 코드에서 짧은 임시 테스트를 하나 더 돌렸습니다. null로 DefaultEndpoint를 만들고, 그 엔드포인트로 연결 객체 StatefulRedisConnectionImpl을 만드는 테스트예요. 이 테스트는 내려받은 사본에서만 돌리고 지웠어요.

DefaultEndpoint endpoint = new DefaultEndpoint(ClientOptions.create(), null); System.out.println("PROBE constructed endpoint, getClientResources()=" + endpoint.getClientResources()); new StatefulRedisConnectionImpl<>(endpoint, endpoint, StringCodec.UTF8, Duration.ofSeconds(1)); PROBE constructed endpoint, getClientResources()=null java.lang.NullPointerException at io.lettuce.core.RedisChannelHandler.<init>(RedisChannelHandler.java:81) at io.lettuce.core.StatefulRedisConnectionImpl.<init>(StatefulRedisConnectionImpl.java:100) at io.lettuce.core.StatefulRedisConnectionImpl.<init>(StatefulRedisConnectionImpl.java:85)

엔드포인트는 null을 품은 채 정상적으로 만들어졌고, 예외는 다른 클래스의 생성자에서 났다는 뜻이에요. RedisChannelHandler.java 81행은 this.tracingEnabled = clientResources.tracing().isEnabled();입니다. 이 NPE에는 메시지가 없어서, 스택만 보고는 null이 어디서 들어왔는지 알 수 없어요.

그림 1. 같은 입력이 수정 전에는 다른 클래스의 생성자까지 흘러갔어요
📖 용어: 빠른 실패 (fail-fast)
잘못된 입력을 받는 즉시, 받은 자리에서 실패하게 만드는 방식이에요. 예외의 위치와 메시지가 원인을 직접 가리키므로, 나중에 다른 곳에서 터진 NPE를 거꾸로 추적할 필요가 없어집니다.

생성자의 null 검사는 빠른 실패를 위한 장치예요. 이 장치가 동작하지 않으면 실패는 사라지지 않고, 원인과 떨어진 곳으로 옮겨 갑니다. 이번 경우에는 DefaultEndpoint를 만든 코드가 아니라 RedisChannelHandler에서 메시지 없는 NPE가 났어요.

3. 수정은 한 단어, 테스트는 두 개

본 코드의 수정은 검사 대상 변수 하나를 바꾸는 것이었어요.

--- a/src/main/java/io/lettuce/core/protocol/DefaultEndpoint.java +++ b/src/main/java/io/lettuce/core/protocol/DefaultEndpoint.java @@ -139,7 +139,7 @@ public DefaultEndpoint(ClientOptions clientOptions, ClientResources clientResources) { LettuceAssert.notNull(clientOptions, "ClientOptions must not be null"); - LettuceAssert.notNull(clientOptions, "ClientResources must not be null"); + LettuceAssert.notNull(clientResources, "ClientResources must not be null");

테스트는 기존 DefaultEndpointUnitTests에 두 개를 추가했어요. 하나는 clientOptions가 null일 때, 다른 하나는 clientResources가 null일 때 각자의 메시지로 IllegalArgumentException이 나는지 확인합니다. 원래 맞게 동작하던 첫 번째 검사에도 테스트가 붙어 있어요. 두 테스트가 각자의 메시지까지 단언하기 때문에, 어느 쪽이든 검사 대상과 메시지가 다시 어긋나면 테스트가 실패합니다.

@Test void shouldRejectNullClientOptions() { assertThatThrownBy(() -> new TestableEndpoint(null, clientResources)).isInstanceOf(IllegalArgumentException.class) .hasMessage("ClientOptions must not be null"); } @Test void shouldRejectNullClientResources() { assertThatThrownBy(() -> new TestableEndpoint(ClientOptions.create(), null)) .isInstanceOf(IllegalArgumentException.class).hasMessage("ClientResources must not be null"); }
📖 용어: 회귀 테스트 (regression test)
고친 버그가 나중에 다시 생기지 않는지 확인하려고 남기는 테스트예요. 수정 전 코드에서는 실패하고 수정 후 코드에서는 통과해야 의미가 있습니다.

4. 다시 돌려 본 재현

회귀 테스트가 정말 이 버그를 잡는지는 두 상태에서 같은 테스트를 돌려 보면 알 수 있어요. 머지 커밋 26d42549에서 한 번, 본 코드 파일만 직전 커밋으로 되돌리고 테스트 파일은 그대로 둔 상태에서 한 번 돌렸습니다.

Lettuce의 통합 테스트 워크플로는 JDK 8(temurin)을 쓰는데, 로컬에는 JDK 8이 없었어요. 그래서 저장소의 다른 CI 워크플로(doctests)가 쓰는 JDK 11로 실행했습니다. Redis 서버가 필요 없는 단위 테스트 클래스 하나만 골라 돌렸어요.

$ export JAVA_HOME=$(/usr/libexec/java_home -v 11) MAVEN_OPTS=-Xmx2g $ ./mvnw -B test -Dtest=DefaultEndpointUnitTests \ -Dsurefire.failIfNoSpecifiedTests=false -Djacoco.skip=true # (1) 머지 커밋 26d42549 [INFO] Tests run: 25, Failures: 0, Errors: 0, Skipped: 0 [INFO] BUILD SUCCESS (01:10 min, 첫 컴파일 포함) # (2) 본 코드만 되돌림 $ git checkout 26d4254^ -- src/main/java/io/lettuce/core/protocol/DefaultEndpoint.java [ERROR] Tests run: 25, Failures: 1, Errors: 0, Skipped: 0 [ERROR] io.lettuce.core.protocol.DefaultEndpointUnitTests.shouldRejectNullClientResources java.lang.AssertionError: Expecting code to raise a throwable. [INFO] BUILD FAILURE (35.698 s)

Expecting code to raise a throwable은 예외가 나야 하는 코드가 예외 없이 끝났다는 AssertJ의 실패 메시지예요. 수정 전 코드에서 null을 넣은 생성자 호출이 그대로 통과했다는 뜻입니다.

결과는 PR 본문에 남긴 기록과 같았어요. 본문에는 before: Tests run: 25, Failures: 1, after: Tests run: 25, Failures: 0이라고 적혀 있습니다. 되돌린 상태에서 실패한 테스트는 shouldRejectNullClientResources 하나뿐이었어요. shouldRejectNullClientOptions는 두 상태 모두 통과했는데, 첫 번째 검사는 원래 맞았으니 기대한 결과입니다.

이 숫자에서 한 가지를 더 읽을 수 있어요. 되돌린 상태에서도 기존 테스트 23개는 전부 통과했습니다. 기존 테스트 가운데 clientResources에 null을 넣고 예외를 기대하는 테스트는 없었다는 뜻이에요. 잘못된 검사는 실패해야 하는 입력이 들어왔을 때만 드러나는데, 그 입력을 넣는 테스트가 없었어요.

수정 후 코드에서 2장의 임시 테스트를 다시 돌리면 예외 위치가 바뀌어요.

java.lang.IllegalArgumentException: ClientResources must not be null at io.lettuce.core.internal.LettuceAssert.notNull(LettuceAssert.java:56) at io.lettuce.core.protocol.DefaultEndpoint.<init>(DefaultEndpoint.java:142)

이제는 DefaultEndpoint 생성자 142행에서, 어떤 인자가 문제인지 말하는 메시지와 함께 실패합니다.

💡 실무에서는
• 인자 검증 테스트는 예외 타입만이 아니라 메시지까지 단언하면, 검사 대상과 메시지가 어긋나는 실수를 함께 잡을 수 있어요.
• 버그 수정 PR의 회귀 테스트는 본 코드만 되돌린 상태에서 실패하는지 한 번 확인해 두면, 테스트가 수정과 무관하게 항상 통과하는 경우를 걸러낼 수 있습니다.

5. 리뷰와 머지

PR은 2026-10-14 13:07(UTC)에 열었고, 같은 날 14:56에 유지보수자 a-TODO-rov가 머지했어요. 커밋은 처음 올린 4f3e144a 하나였고, 저장소에 설정된 자동 리뷰 봇의 상태 코멘트 외에 사람의 리뷰 코멘트나 수정 요청은 없었습니다. 리뷰 과정에서 바뀐 판단도 없었어요.

PR 본문에는 세 가지를 적었어요. 같은 생성자의 자바독이 clientResources를 null 불가로 명시한다는 점, 이 값이 getClientResources()로 다른 클래스에 넘어간다는 점, 그리고 수정 전후의 테스트 결과입니다.

6. 결과와 남은 한계

머지 커밋은 26d42549이고, 지금 DefaultEndpoint는 clientResources가 null이면 생성자에서 바로 실패합니다. 2018년부터 있던 검사가 이제 의도대로 동작해요.

남은 한계도 적어 둘게요.

첫째, 이 PR은 DefaultEndpoint 한 곳만 고쳤어요. 같은 모양의 실수가 저장소의 다른 곳에도 있는지는 이 PR의 범위 밖이었습니다.

둘째, 재현은 CI와 다른 JDK 11에서 했어요. 생성자 인자 검증이라 JDK 버전에 따라 결과가 달라질 부분은 아니라고 판단했지만, JDK 8에서 직접 돌려 보지는 않았습니다.

셋째, null이 실제 사용자 코드에서 어떤 경로로 들어올 수 있는지는 조사하지 않았어요. 이번 재현은 생성자를 직접 호출해서 null이 통과하고 다른 클래스에서 NPE가 나는 것까지만 확인했습니다.

소스 기준: redis/lettuce #3952, 머지 커밋 26d42549. 재현 명령과 출력은 labs/open-source-contribute/lettuce/repro.md에 남겼어요.

✍️ 오늘의 요약
검증 두 줄 중 둘째 줄이 첫째 줄과 같은 변수를 검사하고 있어서, clientResources의 null은 생성자를 통과했어요.

통과한 null은 연결 객체를 만들 때 RedisChannelHandler에서 메시지 없는 NPE로 터졌고, 변수 하나를 바로잡자 생성자에서 원인을 말하며 실패하게 됐습니다. 검증 코드는 존재하는 것만으로는 부족하고, 실패하는 입력으로 한 번은 확인해야 해요.
