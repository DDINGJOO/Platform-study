1편. 검증 버그를 고쳤는데 리뷰가 오지 않던 이유 ← 지금 이 글

Keycloak에 PR을 열고 이틀이 지났는데, 알림이 하나도 오지 않았어요. 사람의 코멘트도, 라벨도, 리뷰 요청도 없었습니다. PR 아래의 CI 워크플로 6개는 전부 action_required 상태로 멈춰 있었고, 누군가 승인해 주기를 기다리고 있었어요.

이 글은 keycloak/keycloak #53990의 회고예요. 고친 버그는 생성자의 검증 한 줄이었고, 코드 변경은 한 줄이었습니다. 그런데 머지까지 걸린 시간의 대부분은 코드가 아니라 리뷰가 시작되기를 기다리는 데 쓰였어요. 그 원인으로 PR에 이슈가 연결되어 있지 않다는 점을 짚었습니다. 버그가 무엇이었는지, 어떻게 재현했는지, 그리고 리뷰가 오지 않던 이유를 어떻게 확인하고 풀었는지를 차례로 적었습니다. 시각은 따로 적지 않으면 모두 UTC예요.

📖 용어: Keycloak, AccessTokenContext
Keycloak은 로그인과 토큰 발급을 맡는 오픈소스 인증 서버예요. AccessTokenContext는 발급한 액세스 토큰이 어떤 세션과 어떤 방식으로 만들어졌는지(세션 종류, 토큰 종류, 그랜트 타입, 원본 토큰 id)를 담는 작은 클래스입니다. 이 값들은 토큰 id 문자열 앞부분에 약어로 인코딩돼요.

1. 메시지는 rawTokenId를 말하는데 검사는 grantType을 했다

AccessTokenContext의 생성자는 인자 네 개를 받고, 첫머리에서 네 개가 null이 아닌지 검사해요. 수정 전 코드는 아래와 같았습니다.

@JsonCreator public AccessTokenContext(@JsonProperty("sessionType") SessionType sessionType, @JsonProperty("tokenType") TokenType tokenType, @JsonProperty("grantType") String grantType, @JsonProperty("rawTokenId") String rawTokenId) { Objects.requireNonNull(sessionType, "Null sessionType not allowed"); Objects.requireNonNull(tokenType, "Null tokenType not allowed"); Objects.requireNonNull(grantType, "Null grantType not allowed"); Objects.requireNonNull(grantType, "Null rawTokenId not allowed"); this.sessionType = sessionType; ... this.rawTokenId = rawTokenId; }

네 번째 줄의 메시지는 rawTokenId를 말하지만, 검사하는 변수는 바로 윗줄과 같은 grantType이에요. grantType이 null이면 윗줄에서 이미 예외가 나기 때문에, 네 번째 줄은 어떤 입력에서도 실패하지 않습니다. 결국 rawTokenId는 아무도 검사하지 않는 인자였어요.

📖 용어: @JsonCreator
JSON을 객체로 바꿀 때 Jackson이 호출할 생성자를 지정하는 어노테이션이에요. 이 생성자에는 @JsonProperty로 JSON 필드 이름이 붙어 있어서, 직렬화된 토큰 컨텍스트 JSON을 읽을 때도 같은 생성자를 거칩니다. 그래서 코드에서 직접 호출하는 경로와 JSON을 읽는 경로가 같은 검증을 공유해요.

네 줄은 길이와 들여쓰기가 같고, 메시지는 기대한 내용을 말해요. 검증 코드가 있다는 사실과 그 검증이 동작한다는 사실은 별개라서, 실패해야 하는 입력으로 한 번은 실행해 봐야 알 수 있었어요.

이 버그가 어느 버전에 있는지도 확인했어요. 세션 기록에는 최신 릴리스 26.8.1과 main 양쪽에 같은 줄이 있다는 점을 소스에서 확인한 내용이 남아 있습니다. 재현 코드에 쓴 열거형 상수(SessionType.ONLINE, TokenType.REGULAR)와 생성자 시그니처도 이때 실제 소스와 대조했어요.

2. 통과한 null은 어디로 가나

null이 생성자를 통과해도, 그 순간에는 아무 일도 일어나지 않아요. 문제는 그 객체가 쓰이는 곳에서 생깁니다. PR 본문에는 DefaultTokenContextEncoderProvider에서 토큰 id에 이어 붙을 때 문자열 null이 그대로 들어간다고 적어 두었어요. 이 글을 쓰려고 2026-10-22에 저장소를 새로 받아, 수정 전 상태에서 이 경로를 직접 실행해 봤습니다. 사본에서만 돌린 임시 테스트가 출력한 내용이에요.

// 되돌린 상태(rawTokenId 검사 없음) PROBE constructor: accepted, getRawTokenId()=null PROBE encodeTokenId=onrtro:null PROBE json: accepted, encodeTokenId=onrtro:null

첫 줄은 rawTokenId가 null인 채로 생성자가 끝났다는 뜻이에요. 둘째 줄은 그 객체로 encodeTokenId를 호출한 결과이고, 토큰 id 뒷부분이 :null이라는 문자열이 됐어요. 앞의 onrtro는 세션 종류(on, 온라인), 토큰 종류(rt, 일반), 그랜트 타입(ro, 임시 테스트가 password에 붙인 약어)를 이어 붙인 문자열입니다. 셋째 줄은 "rawTokenId":null이 들어 있는 JSON을 읽어도 똑같이 통과한다는 확인이에요.

수정 후 상태에서 같은 임시 테스트를 돌리면 결과가 달라져요.

// 머지 커밋 상태 PROBE constructor: java.lang.NullPointerException: Null rawTokenId not allowed PROBE json: ValueInstantiationException root=java.lang.NullPointerException: Null rawTokenId not allowed

생성자가 바로 Null rawTokenId not allowed 메시지의 NPE를 던지고, JSON을 읽는 쪽은 Jackson이 이 예외를 ValueInstantiationException으로 감싸서 올려요. 수정 전에는 이 null이 아무 예외 없이 onrtro:null이라는 문자열로 바뀌어 토큰 id에 섞였고, 수정 후에는 값을 만드는 자리에서 실패합니다.

그림 1. 같은 입력이 수정 전에는 문자열 null이 되었고, 수정 후에는 생성자에서 멈춰요

3. 고친 한 줄과 네 개의 테스트

본 코드의 수정은 검사 대상을 바로잡는 한 줄이었어요.

--- a/services/src/main/java/org/keycloak/protocol/oidc/encode/AccessTokenContext.java +++ b/services/src/main/java/org/keycloak/protocol/oidc/encode/AccessTokenContext.java @@ -111,7 +111,7 @@ public class AccessTokenContext { Objects.requireNonNull(tokenType, "Null tokenType not allowed"); Objects.requireNonNull(grantType, "Null grantType not allowed"); - Objects.requireNonNull(grantType, "Null rawTokenId not allowed"); + Objects.requireNonNull(rawTokenId, "Null rawTokenId not allowed");

테스트는 AccessTokenContextTest를 새 파일로 추가했어요(54줄). 네 인자를 하나씩 null로 바꿔서, 각각 NullPointerException이 나는지 확인하는 테스트 네 개입니다. 이 이름의 테스트 클래스는 원래 없었어요.

@Test public void shouldRejectNullRawTokenId() { Assert.assertThrows(NullPointerException.class, () -> new AccessTokenContext( AccessTokenContext.SessionType.ONLINE, AccessTokenContext.TokenType.REGULAR, OAuth2Constants.AUTHORIZATION_CODE, null)); }

다만 이 테스트는 예외의 타입만 확인하고 메시지는 확인하지 않아요. 검사 대상 변수가 바뀌었는지는 잡지만, 메시지가 엉뚱한 변수를 말하는 실수는 잡지 못합니다. 이번 PR에서 이 부분은 바꾸지 않았어요.

4. 재현: 머지 커밋에서 통과, 본 코드만 되돌리면 실패

PR 본문에는 테스트 결과가 적혀 있었어요. 이 글을 쓰기 전에 머지 커밋 082ead23을 얕게 받아서 같은 결과가 나오는지 다시 돌렸습니다. CI의 기본 JDK가 25(.github/actions/java-setup의 기본값, temurin)여서 로컬의 OpenJDK 25.0.4로 실행했고, 배포판만 달라요. 데이터베이스나 컨테이너는 필요 없는 단위 테스트라서 services 모듈과 그 의존 모듈만 컴파일했어요.

$ export JAVA_HOME=/opt/homebrew/Cellar/openjdk@25/25.0.4/libexec/openjdk.jdk/Contents/Home MAVEN_OPTS=-Xmx2g $ ./mvnw -B -pl services -am test -Dtest='AccessTokenContextTest,*TokenContext*' \ -Dsurefire.failIfNoSpecifiedTests=false -Dcheckstyle.skip -Dlicense.skip # (1) 머지 커밋 082ead23 Tests run: 4, Failures: 0 (AccessTokenContextTest) Tests run: 6, Failures: 0 (DefaultTokenContextEncoderProviderTest) Tests run: 10, Failures: 0 BUILD SUCCESS (35.3 s, 첫 컴파일 포함) # (2) 본 코드만 직전 커밋으로 되돌림, 테스트는 그대로 $ git checkout HEAD^ -- services/src/main/java/org/keycloak/protocol/oidc/encode/AccessTokenContext.java Tests run: 4, Failures: 1 (AccessTokenContextTest) AccessTokenContextTest.shouldRejectNullRawTokenId:49 java.lang.AssertionError: expected java.lang.NullPointerException to be thrown, but nothing was thrown BUILD FAILURE (11.9 s)

expected ... to be thrown, but nothing was thrown은 예외가 나야 하는 코드가 아무 일 없이 끝났다는 JUnit의 실패 메시지예요. 수정 전 코드에서 rawTokenId에 null을 넣은 생성자 호출이 그대로 통과했다는 뜻입니다.

결과는 PR 본문의 기록과 같았어요. 본문에는 before: Tests run: 4, Failures: 1과 after: Tests run: 4, Failures: 0, 그리고 *TokenContext* 패턴으로 돌린 Tests run: 10, Failures: 0이 적혀 있습니다. 되돌린 상태에서 실패한 테스트는 shouldRejectNullRawTokenId 하나뿐이고, 나머지 세 인자의 테스트는 두 상태 모두 통과했어요. 세 인자의 검사는 원래 맞았기 때문에 예상한 결과입니다.

💡 확인한 것
• 수정 전 코드에서 null 한 줄이 통과하는 것은 단위 테스트와 임시 프로브로 직접 확인했어요.
• 이 null이 실제 서버 코드의 어느 경로에서 들어오는지는 조사하지 않았어요. 확인한 범위는 생성자와 JSON 역직렬화, 그리고 encodeTokenId까지예요.

5. 리뷰가 오지 않은 이유를 CONTRIBUTING에서 찾았다

코드는 한 줄이었고 테스트도 통과했는데 이틀 동안 사람의 반응이 없었어요. PR을 열고 2분 안에 자동 리뷰 봇이 코멘트를 남기긴 했지만, 사람의 코멘트나 라벨, 담당자는 없었고 CI 워크플로 6개는 모두 action_required였습니다.

📖 용어: 첫 기여자 워크플로 승인 (action_required)
GitHub는 처음 기여하는 사람의 PR에서는 CI 워크플로를 자동으로 돌리지 않아요. 저장소 쓰기 권한이 있는 사람이 승인 버튼을 눌러야 돌아가고, 그 전에는 action_required 상태로 멈춰 있습니다. 승인할 사람이 PR을 보지 않으면 CI가 영원히 시작되지 않아요.

원인을 찾으려고 저장소의 CONTRIBUTING.md를 읽었어요. 거기에 이런 문장이 있었습니다.

Each PR, no matter how small, should have a GitHub issue associated with it. Issues are important for administrative purposes such as generating a changelog and handling backports.

앞 단락에는 작은 변경이면 디스커션 없이 바로 PR을 보내도 된다는 문장이 있어요. 그 문장은 디스커션을 생략해도 된다는 뜻이고, 이슈는 크기와 상관없이 필요하다는 규칙이 바로 아래에 따로 있었습니다. 커밋 메시지의 마지막 줄에는 Closes #이슈번호를 넣으라는 안내도 있었고요.

이 규칙이 왜 필요한지는 이슈의 이벤트 기록으로 확인했어요. 이슈에 라벨을 붙이는 주체와 시각을 조회하니 이런 순서였습니다.

2026-10-16T03:45:19Z 이슈 #54051 생성 (웹 양식, Bug Report) 03:45:20 labeled kind/bug (DDINGJOO, 양식이 붙임) 03:45:21 labeled status/triage (DDINGJOO, 양식이 붙임) 03:45:22 labeled area/oidc (keycloak-github-bot) 03:45:24 labeled team/core-protocols (keycloak-github-bot) ... 2026-10-19T13:42 mposolda 가 action/priority-low, 봇이 status/triage 제거 후 priority/low 부착
📖 용어: 이슈 양식(템플릿)과 영역 라벨
Keycloak의 이슈 만들기 화면에는 Bug Report 같은 양식이 있어요. 양식으로 이슈를 열면 kind/bug와 status/triage 같은 라벨이 자동으로 붙고, 양식에서 고른 영역(Area)에 따라 봇이 area/oidc 같은 영역 라벨과 담당 팀 라벨(team/core-protocols)을 이어서 붙입니다.

이슈를 만들고 5초 안에 영역 라벨과 팀 라벨이 붙었어요. 반면 PR 자체에는 지금도 라벨이 하나도 없습니다. Keycloak에서 담당 팀을 정하는 라벨은 PR이 아니라 이슈에 붙는다는 점이 보였어요. 이슈가 없던 제 PR은 어느 팀에도 분류되지 않았고, 그래서 이슈 목록을 보고 일하는 사람의 눈에 들어올 자리가 없었다고 판단했습니다. 승인 대기 중인 워크플로를 누가 열어 줄지도 같은 이유로 정해지지 않았을 것이라고 봤어요. 다만 유지보수자들의 내부 분류 절차는 제가 볼 수 없어서, 이 부분은 공개된 규칙과 이벤트 기록에서 세운 판단이에요.

6. 이슈를 두 번 만든 이유

먼저 이슈를 연결하기로 하고 10-16 03:39에 GitHub API로 이슈 #54050을 만들었어요. PR에도 이 이슈를 연결했어요. 그런데 #54050에는 라벨이 하나도 없었어요. API로 만든 이슈는 이슈 양식을 거치지 않기 때문에 kind/bug와 status/triage가 붙지 않았고, 외부 기여자인 저는 라벨을 직접 붙일 권한이 없었어요. 유지보수자가 붙여 달라는 코멘트를 이슈에 남겼지만, 곧 웹의 Bug Report 양식으로 같은 내용을 다시 열기로 했습니다. 이때 Area를 oidc로 골랐어요. AccessTokenContext가 org.keycloak.protocol.oidc.encode 패키지에 있기 때문입니다. 이렇게 만든 이슈가 #54051이고, 위 이벤트 기록처럼 라벨이 곧바로 붙었어요. 03:45:37에 커밋 메시지를 Closes #54051로 바꿔 올렸고(코드 변경 없음), PR 본문도 고쳤습니다. #54050에는 #54051의 중복이라고 적고 닫았어요.

그림 2. 같은 PR이 이슈 연결 뒤에는 라벨, 담당자, 머지 순서로 이어졌어요

7. 담당자 지정부터 머지까지

이슈가 연결된 뒤 반응은 10-19에 왔어요. 13:41에 유지보수자 mposolda가 PR의 담당자로 지정됐고, 같은 시각에 사람의 첫 리뷰로 "Thanks!"가 남았습니다. 이슈에는 13:42에 status/triage가 빠지고 priority/low 라벨이 붙었어요.

그 사이 CI가 한 번 실패했어요. 새로 추가한 테스트 파일의 import 순서가 Spotless 규칙에 맞지 않았기 때문입니다.

📖 용어: Spotless
코드 서식을 검사하고 자동으로 고쳐 주는 Maven 플러그인이에요. CI가 이 검사를 포함하고 있어서, import 순서나 공백이 규칙과 다르면 테스트와 상관없이 빌드가 실패합니다. mvn spotless:apply를 실행하면 규칙대로 고쳐 줘요.

14:01에 mvn spotless:apply로 서식을 고치고, 커밋 하나를 amend해서 다시 올렸어요. 바뀐 내용은 org.keycloak import를 파일 맨 위로 옮긴 것뿐이고 커밋은 여전히 하나였습니다. 이 사실은 PR에 코멘트로 남겼어요. 그런데 force push로 커밋이 바뀌자, 방금 받은 mposolda의 승인이 dismissed 처리됐습니다. 17:05에 승인이 다시 달렸고, 17:06에 머지됐어요.

리뷰어가 코드의 설계나 구현을 고치라고 요청한 적은 없었어요. 코드 리뷰 코멘트(인라인 코멘트)는 0개였고, 리뷰 과정에서 바뀐 것은 import 위치 하나였습니다. 이 PR에서 시간을 쓴 쪽은 리뷰 내용이 아니라 리뷰가 시작되기까지의 대기였어요.
