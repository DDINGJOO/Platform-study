설정 저장소에 커밋을 푸시합니다. Git 호스팅 서비스가 Config Server의 /monitor로 웹훅을 보내고, Config Server는 그 설정을 쓰는 애플리케이션들에게 "설정이 바뀌었으니 다시 받아 가라"고 알립니다. 애플리케이션은 곧바로 설정을 다시 요청해요. 그런데 돌려받은 설정이 방금 푸시한 커밋이 아니라 그 이전 커밋일 수 있습니다.

spring.cloud.config.server.git.refresh-rate를 켜 둔 서버에서 생기는 일이에요. 이 글은 spring-cloud/spring-cloud-config #3342의 회고 1편입니다. 웹훅을 받으면 refresh-rate를 만료시키는 첫 구현을 어떻게 만들었고, "모든 저장소를 만료시키지 말라"는 설계 지적을 받아 웹훅이 가리킨 저장소만 고르도록 어떻게 바꿨는지를 적었어요.

📖 용어: Spring Cloud Config Server
여러 애플리케이션의 설정 파일을 Git 저장소 같은 곳에 모아 두고 HTTP로 나눠 주는 서버예요. 애플리케이션은 기동할 때나 갱신 알림을 받았을 때 이 서버에 설정을 요청합니다.

이 PR은 이슈 gh-2249와 관련된 작업이고, 2026-10-09에 열었어요. 이 글을 쓰는 2026-10-22 현재 아직 열려 있고 머지되지 않았습니다. 글에 적은 과정은 PR의 커밋·본문·리뷰 기록과, 리뷰에 대응한 날 남긴 작업 기록에서 가져왔어요.

1. 웹훅은 왔는데 설정은 이전 커밋

Config Server가 Git 저장소를 쓰면, 설정 요청이 올 때마다 원격 저장소에서 fetch할지를 먼저 판단해요. refresh-rate를 0보다 크게 주면 마지막 fetch 뒤로 그 시간이 지나기 전에는 원격에 가지 않습니다. 요청이 많은 서버에서 원격 호출을 줄이려는 설정이에요.

📖 용어: refresh-rate
spring.cloud.config.server.git.refresh-rate, 초 단위예요. 마지막 fetch 이후 이 시간이 지나야 다음 요청에서 원격 저장소를 다시 fetch합니다. 음수면 fetch를 아예 하지 않아요.

판단은 JGitEnvironmentRepository.shouldPull()이 해요. 마지막 fetch 시각을 담은 필드가 lastRefresh입니다.

protected boolean shouldPull(Git git) throws GitAPIException { boolean shouldPull; if (this.refreshRate < 0 || (this.refreshRate > 0 && System.currentTimeMillis() - this.lastRefresh < (this.refreshRate * 1000))) { return false; } ...

여기에 웹훅이 끼어들면 순서가 어긋나요. 푸시 직후 웹훅이 오면 Config Server는 애플리케이션에 갱신 알림을 보내지만, 자기 자신은 아직 refresh-rate 안에 있어서 원격을 fetch하지 않습니다. 알림을 받고 설정을 다시 요청한 애플리케이션은 서버가 가진 이전 커밋을 받아요. 첫 커밋 메시지에 적은 문제가 바로 이것이었습니다.

When spring.cloud.config.server.git.refresh-rate is set, the config server does not fetch from the remote until the refresh rate has elapsed. A webhook sent to /monitor notifies the applications, which then fetch their configuration from the config server, but the config server may still serve the previous commit to them.
📖 용어: /monitor 엔드포인트
spring-cloud-config-monitor 모듈이 여는 웹훅 수신 주소예요. GitHub·GitLab·Bitbucket 같은 서비스가 보낸 푸시 페이로드에서 바뀐 파일 경로를 뽑고, 그 경로로 영향을 받는 애플리케이션 이름을 추정해 갱신 알림을 보냅니다. 코드에서는 PropertyPathEndpoint 클래스예요.

2. 첫 구현: lastRefresh를 0으로

해결 방향은 단순했어요. 웹훅을 받으면 lastRefresh를 0으로 되돌려서, 다음 요청의 shouldPull()이 refresh-rate가 지났다고 판단하게 만들면 됩니다. 2026-10-09 첫 커밋 3d9beb42의 핵심은 아래와 같아요.

// JGitEnvironmentRepository + public void expireRefreshRate() { + this.lastRefresh = 0; + } // MultipleJGitEnvironmentRepository + @Override + public void expireRefreshRate() { + super.expireRefreshRate(); + this.repos.values().forEach(JGitEnvironmentRepository::expireRefreshRate); + new ArrayList<>(this.placeholders.values()).forEach(JGitEnvironmentRepository::expireRefreshRate); + } // PropertyPathEndpoint: 알림을 보내기 전에 + for (JGitEnvironmentRepository repository : this.gitRepositories) { + repository.expireRefreshRate(); + }

만료를 알림보다 먼저 호출한 것은 의도한 순서예요. 애플리케이션이 알림을 받고 설정을 요청할 때 서버는 이미 만료된 상태여야 하기 때문입니다. 커밋 메시지에는 Fixes gh-2249를 달았어요.

3. "모든 저장소를 만료시키지 마라"

2026-10-20에 메인테이너 ryanjbaxter가 코드를 보기 전에 설계부터 이야기하자는 코멘트를 남겼어요. 요지는 이 한 문장이었습니다.

We should really only be expiring the refresh for the repo that was updated.

첫 구현에서는 웹훅 한 건이 들어오면 Config Server에 설정된 Git 저장소를 전부 만료시켜요. Config Server는 기본 저장소 하나만 쓰는 게 아니라, 애플리케이션 이름 패턴마다 다른 저장소를 붙이거나 URI에 {application} 같은 자리표시자를 넣어 저장소를 여러 개 다룰 수 있습니다. 저장소 A에 푸시가 들어왔는데 B와 C까지 다음 요청에서 원격을 fetch하게 되는 셈이에요. refresh-rate를 켠 이유가 원격 호출을 줄이려는 것이니, 웹훅이 잦은 환경에서는 웹훅이 올 때마다 그 설정과 상관없는 저장소까지 원격을 다시 fetch하게 됩니다.

📖 용어: 패턴 저장소와 자리표시자 저장소
MultipleJGitEnvironmentRepository가 다루는 두 가지 추가 저장소예요. 패턴 저장소(repos)는 애플리케이션 이름이 패턴에 맞을 때 쓰는 저장소이고, 자리표시자 저장소(placeholders)는 {application} 같은 자리표시자가 든 URI를 요청마다 실제 값으로 풀어서 만든 저장소예요. 자리표시자 저장소는 요청이 올 때마다 새로 생길 수 있습니다.
그림 1. 웹훅 한 건이 만료시키는 범위를 "전부"에서 "페이로드가 가리킨 저장소"로 줄였어요

지적이 맞았어요. 그래서 2026-10-21 커밋 3ba94c12에서 방향을 바꿨습니다. 웹훅 페이로드에 들어 있는 저장소 URL을 꺼내고, 그 URL이 각 저장소에 설정된 원격 URL과 같을 때만 만료시킵니다. 메서드 시그니처도 expireRefreshRate(String repositoryUri)로 바뀌었어요.

4. 웹훅마다 저장소 URL이 다른 곳에 있다

"페이로드에서 저장소 URL을 꺼낸다"는 말은 쉽지만, 서비스마다 그 URL을 두는 자리가 달랐어요. /monitor는 이미 GitHub, GitLab, Bitbucket, Gitea, Gitee, Gogs의 페이로드를 각각 해석하는 추출기를 갖고 있습니다. 그런데 기존 추출기들은 바뀐 파일 경로만 뽑았고 저장소 URL은 보지 않았어요. 3ba94c12에서 읽도록 만든 위치는 아래와 같습니다.

GitHub, Gitea, Gitee, Gogs repository.clone_url / ssh_url / git_url GitLab project.git_http_url / git_ssh_url (레거시 페이로드) repository.url Bitbucket Cloud repository.links.html.href (clone 링크 없음) Bitbucket Server pr:merged pullRequest.toRef.repository.links.clone[].href Bitbucket Server 푸시 저장소 URL 없음

까다로운 지점이 두 군데 있었어요. 첫째는 repository.url이에요. 레거시 GitLab 페이로드에서는 이 필드가 clone URL이지만, GitHub 페이로드에서는 같은 이름의 필드가 API 주소입니다. 그래서 이 필드는 X-Gitlab-Event: Push Hook 헤더가 있을 때만 읽었어요. 둘째는 Bitbucket이에요. Bitbucket Cloud는 clone URL 대신 저장소 웹 페이지 주소만 주고, Bitbucket Server의 기본 푸시 페이로드에는 저장소 URL이 아예 없습니다.

📖 용어: 웹훅 페이로드 (webhook payload)
Git 호스팅 서비스가 푸시 같은 이벤트가 일어났을 때 지정한 주소로 POST하는 JSON 본문이에요. 어떤 저장소의 어떤 커밋에서 어떤 파일이 바뀌었는지가 들어 있지만, 필드 이름과 위치는 서비스마다 다릅니다.

URL이 없는 페이로드를 어떻게 다룰지가 실제 결정이었어요. 선택지는 두 가지였습니다. URL을 못 찾으면 예전처럼 전부 만료시키거나, 아무것도 만료시키지 않거나요. 앞쪽을 고르면 리뷰에서 지적받은 동작이 Bitbucket Server에서는 그대로 남아요. 그래서 뒤쪽을 골랐습니다. 저장소를 식별할 수 없으면 만료는 하지 않고, 애플리케이션 알림은 예전대로 보냅니다. 애플리케이션 이름이나 저장소 이름의 끝부분으로 저장소를 짐작하는 방식도 쓰지 않았어요.

그러면 원래 이슈에 들어 있던 Bitbucket Server 사례는 이 PR로 해결되지 않아요. 그래서 커밋과 PR 본문의 이슈 연결을 Fixes gh-2249에서 Related to gh-2249로 바꾸고, 문서에 이 한계를 적었습니다. 리뷰어에게 남긴 답에도 같은 내용을 쓰고, 저장소 정보가 부족한 서비스를 어떻게 다루면 좋을지 의견을 물었어요.

One limitation worth calling out is that native Bitbucket Server push payloads do not include a repository URL. I documented that limitation and changed the issue link from "Fixes" to "Related to" ...

5. 저장소 쪽: 기본, 패턴, 자리표시자

받는 쪽에서는 MultipleJGitEnvironmentRepository가 자기 자신(기본 저장소)과 패턴 저장소, 이미 만들어진 자리표시자 저장소에 같은 URL을 넘겨요. 각 저장소는 자기 원격 URL과 비교해서 맞을 때만 lastRefresh를 0으로 만듭니다.

- private Map<String, JGitEnvironmentRepository> placeholders = new LinkedHashMap<>(); + private Map<String, JGitEnvironmentRepository> placeholders = new ConcurrentHashMap<>(); + public void expireRefreshRate(String repositoryUri) { + super.expireRefreshRate(repositoryUri); + this.repos.values().forEach(repository -> repository.expireRefreshRate(repositoryUri)); + this.placeholders.values().forEach(repository -> repository.expireRefreshRate(repositoryUri)); + } - if (!this.placeholders.containsKey(key)) { - this.placeholders.put(key, getRepository(repository, key)); - } - return this.placeholders.get(key); + return this.placeholders.computeIfAbsent(key, uri -> getRepository(repository, uri));

자리표시자 저장소 맵을 ConcurrentHashMap으로 바꾼 이유도 여기서 생겼어요. 웹훅을 처리하는 스레드가 이 맵을 순회하는 동안 설정 요청을 처리하는 스레드가 새 항목을 넣을 수 있기 때문입니다. PR 본문에는 이 변경을 "설정 요청이 항목을 만드는 동안에도 자리표시자 캐시를 안전하게 순회할 수 있게 했다"고 적었어요. 이 커밋에서 lastRefresh도 volatile로 선언해서 웹훅 스레드가 쓴 0을 요청 스레드가 보게 했습니다.

📖 용어: volatile
Java 필드에 붙이는 키워드예요. 한 스레드가 쓴 값을 다른 스레드가 바로 읽을 수 있도록 보장합니다. 여기서는 웹훅을 처리하는 스레드가 쓴 lastRefresh = 0을 설정 요청을 처리하는 스레드가 놓치지 않게 하려고 썼어요.

6. 무엇으로 확인했나

3ba94c12에는 회귀 테스트를 여럿 붙였어요. 저장소가 여러 개일 때 맞는 것만 만료되는지, 기본·패턴·자리표시자 저장소 각각에서 동작하는지, 만료가 알림보다 먼저 일어나는지, 페이로드에 저장소 정보가 없거나 형식이 깨졌을 때 아무것도 만료하지 않는지를 확인합니다. 서비스별 URL 필드와 무시 경로, 음수 refresh-rate도 테스트에 넣었어요.

실제 Git 저장소를 쓰는 통합 테스트도 하나 추가했어요. refresh-rate를 60초로 둔 상태에서 원격에 새 커밋을 만든 뒤, 다른 저장소 URL로 만료를 부르면 이전 커밋이 그대로 나오고 같은 URL로 부르면 새 커밋을 가져오는지 봅니다.

+ repository.expireRefreshRate(repository.getUri() + "-other"); + environment = repository.findOne("bar", "staging", "master"); + assertThat(environment.getVersion()).isEqualTo(startingRemoteVersion); + + repository.expireRefreshRate(repository.getUri());

PR 본문에 남긴 이 시점의 검증 결과는 Java 21에서 client·server·monitor 모듈을 함께 돌려 1,370개 테스트 통과(스킵 16), 이어서 Git 저장소·엔드포인트·추출기 관련 테스트만 골라 다시 돌려 282개 통과(스킵 5)였어요. 두 번 모두 실패와 오류는 0건이었고, 포맷과 Checkstyle 검사도 통과했습니다. 같은 날(UTC 기준) 저녁에 리뷰가 다시 왔어요. 이번에는 변경 요청 여섯 건이었습니다.

✍️ 오늘의 요약
refresh-rate 안에서는 웹훅 알림을 받은 애플리케이션이 이전 커밋을 받을 수 있어서, 알림 전에 lastRefresh를 0으로 만드는 만료를 넣었어요.

첫 구현은 웹훅 한 건에 모든 저장소를 만료시켰고, 리뷰를 받아 페이로드가 가리킨 저장소만 만료하도록 바꿨습니다. 저장소 URL이 서비스마다 다른 자리에 있고 아예 없는 경우도 있어서, 찾지 못하면 만료하지 않는다는 원칙을 세우고 그 한계를 문서와 이슈 연결에 그대로 적었어요. 만료 범위를 좁히는 일은 결국 "어떤 저장소가 바뀌었는지를 누가 확실히 아는가"를 정하는 일이었습니다.
