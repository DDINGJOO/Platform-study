웹훅이 가리킨 저장소만 만료시키도록 고친 커밋을 올린 날, 메인테이너 ryanjbaxter가 변경 요청(CHANGES_REQUESTED) 리뷰를 두 번 남겼어요. 코드 줄에 단 인라인 코멘트가 다섯 건, 리뷰 본문이 한 건이었습니다.

다섯 건은 받아들였어요. 그중 저장소 URL 매칭 규칙에 대한 지적은 규칙의 방향 자체를 바꾸게 만들었습니다. 리뷰 본문의 한 건은 따르지 않았어요. 왜 매칭을 엄격에서 관대로 뒤집었는지, 그리고 lastRefresh를 fetch가 성공한 뒤에 쓰자는 제안을 따르면 왜 오히려 그 제안이 막으려던 상황이 생기는지를 이 글에 적었어요. 대상 PR은 spring-cloud/spring-cloud-config #3342입니다.

📖 용어: CHANGES_REQUESTED
GitHub 리뷰의 상태 중 하나로, 리뷰어가 "이대로는 머지하기 어렵고 수정이 필요하다"고 표시한 것이에요. 작성자가 수정을 올려도 리뷰어가 다시 승인하거나 리뷰를 해제하기 전까지 이 상태가 남습니다.

1. 변경 요청 여섯 건

처음 받은 여섯 건을 먼저 정리하면 아래와 같아요. 이때 받아들인 다섯 건의 수정과 6번에 대한 테스트는 2026-10-22 커밋 53b59abc에 모았습니다. 1~7절의 코드와 실행 결과는 이 시점 기록이고, 이후 받은 세 건과 최신 대응은 8절에 구분했어요.

1 PropertyPathEndpoint URI 추출 로직을 PropertyPathNotificationExtractor 구현으로 옮겨라 2 JGitEnvironmentRepository NPE가 날 수 있다 3 JGitEnvironmentRepository 경로를 대소문자 구분으로 비교한다, ssh://git@host/org/repo.git 과 git@host:org/repo.git 이 다르게 정규화된다 4 PropertyPathEndpoint 만료가 notifyApplications 보다 먼저라, 예외가 나면 알림이 안 나간다 5 PropertyPathEndpoint repositoryUris 가 없을 때 debug 로그를 남겨라 6 리뷰 본문 lastRefresh 를 fetch 전에 now 로 써서, fetch 도중 들어온 만료가 덮어써진다. fetch 성공 뒤에 써라

1번은 구조에 대한 지적이었어요. 1편의 구현은 PropertyPathEndpoint가 페이로드 원문과 헤더를 직접 뒤져 저장소 URL을 찾았습니다. 그런데 서비스별로 페이로드를 해석하는 추출기가 이미 따로 있었어요. 그래서 PropertyPathNotification에 repositoryUris 필드를 추가하고, 각 추출기가 자기 서비스의 페이로드에서 그 필드를 채우게 옮겼습니다. 기본 구현은 repository와 project의 clone URL 필드를 읽고, GitLab은 레거시 repository.url을, Bitbucket은 Cloud의 HTML 링크와 Server의 clone 링크를 추가로 읽어요. 엔드포인트는 이제 notification.getRepositoryUris()만 부릅니다.

📖 용어: 추출기 (PropertyPathNotificationExtractor)
/monitor가 받은 웹훅 페이로드를 서비스별로 해석하는 인터페이스예요. GitHub, GitLab, Bitbucket 등 서비스마다 구현이 하나씩 있고, 헤더를 보고 자기 서비스의 요청인지 판단한 뒤 바뀐 파일 경로를 담은 PropertyPathNotification을 돌려줍니다.

2번의 NPE는 실제로 있었어요. 1편에서 만든 정규화 메서드는 parsed.getPath()의 결과에 바로 endsWith를 불렀는데, https://github.com처럼 경로가 없는 URI에서는 이 값이 null입니다. 새 코드는 경로가 없으면 비교 키를 만들지 않고 null을 돌려줘요. 테스트 입력에 https://github.com과 https://github.com/을 추가했습니다.

4번과 5번은 지적대로 고쳤어요. 저장소마다 만료 호출을 try/catch로 감싸서, 하나가 실패해도 warn 로그를 남기고 나머지 저장소와 알림은 계속 진행합니다. 페이로드에 저장소 URL이 없으면 debug 로그를 남기는데, Git 저장소가 설정돼 있을 때만 남겨요. Git 저장소가 없으면 애초에 만료할 대상이 없기 때문입니다.

for (String repositoryUri : repositoryUris) { for (JGitEnvironmentRepository repository : this.gitRepositories) { try { repository.expireRefreshRate(repositoryUri); } catch (RuntimeException ex) { log.warn("Could not expire the refresh rate for " + repositoryUri, ex); } } }

2. 엄격했던 매칭을 관대하게 바꾼 이유

3번은 두 가지 예를 들었어요. 하나는 설정에 https://github.com/Org/Repo라고 적었는데 페이로드가 https://github.com/org/repo를 주면 맞지 않는다는 것이고, 다른 하나는 같은 저장소의 두 SSH 표기가 서로 다르게 정규화된다는 것이었습니다.

📖 용어: scp 표기
git@github.com:org/repo.git처럼 ssh:// 없이 사용자@호스트:경로로 쓰는 SSH 저장소 주소예요. 같은 저장소를 ssh://git@github.com/org/repo.git로도 쓸 수 있는데, JGit의 URIish로 파싱하면 앞쪽은 경로가 org/repo.git, 뒤쪽은 /org/repo.git으로 나옵니다.

1편에 적은 대로 처음 규칙은 일부러 엄격했어요. 대소문자를 구분했고, scp 표기의 상대 경로는 다른 저장소로 취급했고, 프로토콜이나 포트, SSH 사용자가 다르면 불일치로 봤습니다. 기존 테스트의 CSV에도 이런 쌍이 "불일치"로 들어 있었어요. 지적받은 두 사례만 예외로 풀어 줄 수도 있었지만, 엄격하게 잡은 이유를 다시 따져 봤습니다.

만료는 "다음 요청에서 한 번 더 fetch하라"는 신호일 뿐이에요. 잘못 맞으면 상관없는 저장소가 fetch를 한 번 더 합니다. 반대로 같은 저장소를 못 알아보면 그 저장소의 설정은 refresh-rate가 지날 때까지 이전 커밋에 머물러요. 이 기능이 고치려던 증상이 바로 그것입니다. 틀린 일치의 비용은 fetch 한 번이고, 놓친 일치의 비용은 refresh-rate만큼 낡은 설정이라서, 관대한 쪽으로 기울이는 것이 맞다고 판단했어요.

새 규칙은 호스트와 저장소 경로만 비교해요. 대소문자를 무시하고, 프로토콜·자격 증명·SSH 사용자·포트도 무시하며, 경로 앞뒤의 /와 끝의 .git을 떼어 냅니다.

static String repositoryKey(String uri) { ... String path = parsed.getPath(); if (path == null) { return null; // 2번: 경로 없는 URI는 키 없음 } path = StringUtils.trimTrailingCharacter(StringUtils.trimLeadingCharacter(path, '/'), '/'); if (path.endsWith(".git")) { path = StringUtils.trimTrailingCharacter(path.substring(0, path.length() - 4), '/'); } if (path.isEmpty()) { return null; } String host = (parsed.getHost() != null) ? parsed.getHost().toLowerCase(Locale.ROOT) : ""; return host + "/" + path.toLowerCase(Locale.ROOT); }

테스트 CSV에서는 불일치로 적혀 있던 기대값 8개를 일치로 뒤집고, HTTPS와 scp 표기에 대소문자가 섞인 경우를 추가해서 모두 20개 쌍이 됐어요. 호스트가 다른 쌍은 여전히 불일치입니다.

- "git@git.example.com:team/config.git, ssh://git@git.example.com/team/config.git, false", - "alice@git.example.com:team/config.git, bob@git.example.com:team/config.git, false", + "git@git.example.com:team/config.git, ssh://git@git.example.com/team/config.git, true", + "https://github.com/Team/Config, git@github.com:team/config.git, true", + "ssh://git@git.example.com:2222/team/config.git, git@git.example.com:team/config.git, true", + "alice@git.example.com:team/config.git, bob@git.example.com:team/config.git, true", "https://github.com/team/config.git, https://gitlab.com/team/config.git, false"

문서도 같이 고쳤어요. push-notifications-and-bus.adoc가 이전의 엄격한 규칙을 그대로 설명하고 있었기 때문입니다. 그중 Bitbucket Cloud 문장은 규칙이 바뀌면서 틀린 말이 됐어요. 예전에는 "HTML 링크로는 HTTPS 저장소만 식별할 수 있다"고 적었지만, 이제는 HTML 링크의 호스트와 경로만으로 SSH로 설정한 저장소도 맞출 수 있습니다.

3. lastRefresh를 fetch 성공 뒤에 쓰자는 제안

리뷰 본문의 6번은 이렇게 시작했어요.

lastRefresh is set to now (line 573) before the fetch runs, so a webhook that calls expireRefreshRate during an in-flight fetch has its reset overwritten, and the new window starts from before the push was visible. It could be fixed by setting lastRefresh after a successful fetch.

요지는 이래요. fetch가 진행 중일 때 웹훅이 와서 lastRefresh를 0으로 만들어도, 그 값이 덮어써지니 fetch를 성공한 뒤에 시각을 쓰자는 것입니다. 이 지적은 이번 PR이 새로 만든 코드가 아니라 원래 있던 코드에 대한 것이었고, 만료를 저장소별로 좁히면서 더 중요해졌다는 맥락이었어요.

📖 용어: 경쟁 조건 (race condition)
둘 이상의 스레드가 같은 값을 읽고 쓸 때, 실행 순서에 따라 결과가 달라지는 상황이에요. 여기서는 fetch를 하는 요청 스레드와 웹훅을 처리하는 스레드가 둘 다 lastRefresh에 씁니다.

먼저 lastRefresh에 쓰는 곳을 main 소스 전체에서 찾았어요. 쓰는 곳은 JGitEnvironmentRepository.fetch() 안, fetch.call() 바로 앞 한 곳뿐이었습니다. 만료(expireRefreshRate)는 이 쓰기보다 나중에 일어날 수 있는 별도의 쓰기예요.

protected FetchResult fetch(Git git, String label) { FetchCommand fetch = git.fetch(); ... if (this.refreshRate > 0) { this.setLastRefresh(System.currentTimeMillis()); // 유일한 now 쓰기 } configureCommand(fetch); try { FetchResult result = fetch.call(); // 원격과 통신, 시간이 걸린다 ... return result; } catch (Exception ex) { ... warn(message, ex); return null; } }

리뷰가 말한 "fetch 도중"은 fetch.call()이 원격과 통신하는 구간이에요. 이 구간은 now를 쓴 다음에 시작합니다. 그러니 그 사이에 들어온 만료의 0이 마지막 쓰기가 되어야 해요. 두 순서를 시간순으로 나란히 놓아 보면 차이가 보입니다.

4. 순서대로 따라가 보기

상황은 같아요. refresh-rate가 켜진 서버에서 요청 하나가 refresh-rate가 지난 것을 보고 fetch를 시작했고, fetch가 원격과 통신하는 동안 누군가 푸시해서 웹훅이 들어옵니다. 진행 중이던 fetch는 이미 원격의 ref 목록을 받은 뒤일 수 있어서, 방금 들어온 푸시를 못 봤을 수 있어요.

그림 1. 시각을 fetch 앞에서 쓰면, fetch 도중 들어온 만료(0)가 마지막 쓰기로 남아요

현재 코드에서는 ②에서 T1을 쓰고, ③에서 fetch가 원격과 통신하는 동안 ④의 웹훅이 0을 써요. ⑤에서 fetch가 끝나도 lastRefresh를 다시 쓰는 코드는 없습니다. 그래서 ⑥의 다음 요청은 0을 보고 refresh-rate가 지났다고 판단해서 다시 fetch하고, 이번 fetch는 웹훅 뒤에 시작했으니 푸시를 가져와요. 리뷰가 걱정한 "만료가 덮어써지는" 일은 이 순서에서 일어나지 않습니다.

이제 제안대로 시각을 fetch가 성공한 뒤에 쓴다고 해 볼게요. 상황은 그대로입니다.

그림 2. 시각을 fetch 뒤에서 쓰면, 진행 중이던 fetch가 끝나며 만료를 덮어써요

②에서 fetch가 시작될 때는 아무것도 쓰지 않아요. ③에서 웹훅이 0을 씁니다. 그런데 ④에서 진행 중이던 fetch가 성공으로 끝나면서 now(T2)를 써요. 이 fetch는 ③의 푸시를 못 봤을 수 있는데도 그렇습니다. ⑤의 다음 요청은 T2를 보고 아직 refresh-rate 안이라고 판단해서 fetch하지 않아요. 애플리케이션은 웹훅 알림을 받고 설정을 다시 요청했지만 이전 커밋을 받습니다. 제안대로 옮기면, 리뷰가 막으려던 "fetch 도중 들어온 만료가 덮어써지는" 상황이 오히려 생깁니다.

현재 코드에도 만료가 덮어써지는 구간이 하나 남아 있어요. ①의 shouldPull 판단과 ②의 쓰기 사이에 웹훅이 들어오면, 0을 쓴 직후에 T1이 덮어씁니다. 다만 이때 시작하는 fetch는 웹훅보다 뒤에 시작하므로 푸시를 이미 볼 수 있어요. PR 코멘트에도 이 구간을 그대로 적었습니다.

5. 실패한 fetch의 back-off

제안에는 하나가 더 걸렸어요. 시각을 "성공한 뒤에만" 쓰면, fetch가 실패했을 때는 아무것도 쓰지 않게 됩니다.

📖 용어: back-off
실패한 작업을 바로 다시 시도하지 않고 일정 시간 기다리는 동작이에요. 현재 코드에서는 fetch가 실패해도 시작 전에 쓴 lastRefresh가 남아 있어서, refresh-rate 동안은 원격에 다시 가지 않습니다.

현재 fetch()는 fetch.call()에서 예외가 나면 경고를 남기고 null을 돌려줘요. 시각은 이미 앞에서 썼으니 다음 refresh-rate 동안은 shouldPull()이 false를 돌려줍니다. 원격 저장소가 응답하지 않을 때 요청마다 원격에 다시 fetch하지 않는 것은 이 순서 덕분이에요. 시각을 성공 뒤로 옮기면 원격이 죽어 있는 동안에는 lastRefresh가 갱신되지 않으니, 설정 요청이 올 때마다 fetch를 다시 시도하게 됩니다.

6. 두 동작을 테스트로 고정하기

말로만 설명하지 않으려고, 지금의 두 동작을 테스트로 남겼어요. 첫 번째 테스트는 fetch.call()을 흉내 내는 mock 안에서 만료를 호출해서, "fetch 도중에 웹훅이 온" 상황을 그대로 만듭니다.

@Test public void expireRefreshRateDuringFetchIsNotOverwritten() throws Exception { ... properties.setRefreshRate(1000); properties.setUri("https://github.com/team/config.git"); ... // A webhook for a push that the in-flight fetch did not see arrives mid-fetch. when(fetchCommand.call()).thenAnswer(invocation -> { repo.expireRefreshRate("https://github.com/team/config.git"); return fetchResult; }); repo.fetch(git, "master"); assertThat(repo.getLastRefresh()).isZero(); }

두 번째 테스트는 fetch.call()이 TransportException을 던지게 하고, 실패한 뒤에도 lastRefresh가 0보다 크고 shouldPull()이 false인지 확인해요.

@Test public void failedFetchKeepsRefreshRateBackoff() throws Exception { ... when(fetchCommand.call()).thenThrow(new TransportException("remote unavailable")); ... repo.setLastRefresh(0); assertThat(repo.fetch(git, "master")).isNull(); // An unreachable remote is not retried on every request. assertThat(repo.getLastRefresh()).isPositive(); assertThat(repo.shouldPull(git)).isFalse(); }

두 테스트는 지금의 동작을 고정하는 테스트예요. 제안대로 코드를 옮긴 상태에서 이 테스트들이 실패하는지까지 돌려 본 기록은 없어서, 여기서는 현재 코드에서 통과한 결과만 적습니다.

7. JDK 17로 돌린 결과와 기대값 실수

첫째, URI 공통 헬퍼를 별도 클래스 대신 인터페이스에 두자는 요청을 받아들였어요. WebhookRepositoryUris를 삭제하고 addCloneUris와 addUri를 PropertyPathNotificationExtractor의 정적 메서드로 옮겼습니다. 추출기들은 자신들이 구현하는 인터페이스의 메서드를 호출해요.

둘째, URI는 있는데 설정 저장소와 하나도 맞지 않을 때도 debug 로그를 남기라는 요청이었어요. expireRefreshRate(String)가 일치 여부를 boolean으로 반환하도록 바꿨습니다. MultipleJGitEnvironmentRepository는 기본·패턴·이미 만들어진 자리표시자 저장소를 모두 순회하며 |=로 결과를 누적해요. 하나가 일치했다고 뒤쪽 호출을 생략하면 같은 원격을 쓰는 다른 저장소가 만료되지 않을 수 있기 때문입니다. 엔드포인트는 하나도 일치하지 않았고 예외도 없었을 때만 미매칭 debug를 남겨요. 예외가 나면 기존 warn을 남기고, 그 실패를 미매칭이라고 단정하는 debug는 추가하지 않습니다.

셋째, Bitbucket Server 문서와 추출기 코드가 어긋난다는 지적이었어요. 당시 샘플에 clone 링크가 없었던 것을 Server 푸시 전체의 성질로 일반화한 문서가 잘못됐습니다. Atlassian 지원 Jenkins 플러그인 샘플에는 clone 링크가 있어요. 문서를 링크 유무에 따라 설명하도록 고치고, repo:refs_changed에 HTTP·SSH clone 링크가 있는 경우를 검사하는 테스트를 추가했습니다. 기존의 링크 없는 샘플은 빈 URI 배열을 기대하는 테스트로 남겼어요. pr:merged는 대상 저장소인 pullRequest.toRef.repository의 clone 링크를 읽고, 링크가 없으면 역시 만료 없이 알림만 보냅니다. 이 변경은 링크 처리 전체를 처음 구현한 것이 아니라 기존 처리에 맞게 문서를 정정하고 테스트를 보강한 것입니다.

DCO는 기여 권리를 선언하는 Signed-off-by 표기를 확인하는 검사예요. 코드 테스트나 암호학적 서명 검증 결과는 아닙니다. 7절의 테스트 수치는 53b59abc 당시 결과이고, 새 head에서 전체 테스트를 직접 다시 돌린 기록은 이번 확인에 포함하지 않았어요. PR 본문에는 예전의 엄격한 URL 비교 설명이 남아 있어서, 현재 동작은 최신 코드와 위 수정 커밋을 기준으로 적었습니다.

✍️ 오늘의 요약
변경 요청 여섯 건 중 다섯 건은 고쳤고, 매칭 규칙은 지적받은 두 사례를 넘어 "호스트와 경로만, 대소문자 무시"로 방향을 바꿨어요. 틀린 일치는 fetch 한 번의 비용이지만 놓친 일치는 refresh-rate만큼 낡은 설정이기 때문입니다.

lastRefresh를 fetch 성공 뒤에 쓰자는 제안은 따르지 않았어요. 시간순으로 따라가 보면 그렇게 옮길 때 진행 중이던 fetch가 끝나며 만료를 덮어쓰고, 실패한 fetch의 back-off도 사라진다는 결론이 나왔어요. 코드를 제안대로 옮겨 돌려 보지는 않았습니다. 지금 코드의 두 동작을 테스트로 고정해 근거와 함께 답했고, 놓친 경로가 있으면 바꾸겠다고 남긴 채 응답을 기다리고 있어요. 리뷰 제안을 따르지 않을 때는 그 제안이 지키려던 것을 제 코드가 이미 지키고 있다는 것을 순서와 테스트로 보여 줘야 했습니다.
