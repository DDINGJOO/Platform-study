2편. DEFAULT를 데이터베이스 이름으로 읽던 문법

ALTER DATABASE CHARACTER SET utf8mb4; 는 MySQL 이 받아 주는 문장이에요. 데이터베이스 이름을 빼면 지금 선택된 데이터베이스에 적용됩니다. 그런데 Debezium MySQL 커넥터의 새 DDL 문법은 이 문장을 파싱하지 못했고, 파싱 예외가 나면 커넥터가 멈췄어요. Debezium 이슈 dbz#2829 가 이 문제였습니다.

고친 코드는 문법 파일의 토큰 하나와 리스너 한 줄이었어요. 시간이 걸린 부분은 다른 곳에 있었습니다. 리뷰어가 "이 문법은 상류 ANTLR 문법과 맞춰 두려고 한다"고 했기 때문에, 같은 변경을 grammars-v4 저장소에도 올려 머지된 뒤에야 Debezium PR 이 머지됐어요. 이 글은 그 과정과, 이번에 두 저장소에서 직접 다시 돌린 재현 결과를 정리한 기록입니다.

1. 커넥터가 왜 DDL 을 파싱할까

Debezium 은 MySQL 의 binlog 를 읽어 테이블 변경을 이벤트로 내보내요. binlog 에는 행 변경뿐 아니라 CREATE TABLE, ALTER DATABASE 같은 DDL 도 문장 그대로 들어 있습니다. 커넥터는 이 문장을 직접 파싱해서 테이블 구조와 데이터베이스의 문자셋을 메모리에 따라 적어 둬요. 그래야 이후 행 이벤트의 컬럼을 올바른 타입과 문자셋으로 해석할 수 있습니다.

📖 용어: DDL 파서
Debezium 이 binlog 로 들어온 DDL 문장을 읽어 커넥터 안의 스키마 정보를 갱신하는 부분이에요. 파싱에 실패하면 이후 이벤트를 해석할 근거가 없어지므로 기본 설정에서는 예외를 내고 멈춥니다.

파서는 ANTLR 로 만들어요. 문법 파일(.g4)에 규칙을 적으면 빌드할 때 Java 파서 코드가 생성되고, Debezium 은 파싱 트리를 따라 내려가는 리스너에서 스키마를 갱신합니다.

📖 용어: ANTLR 문법과 리스너
ANTLR 은 .g4 문법 파일에서 렉서·파서 코드를 생성하는 도구예요. 리스너는 파싱 트리의 각 규칙에 들어가고 나올 때 호출되는 콜백이고, Debezium 의 실제 동작은 여기에 있습니다.

MySQL 쪽에는 문법이 두 벌 있어요. 예전부터 쓰던 legacy 문법과, Oracle 이 관리하는 MySQL 문법을 바탕으로 새로 들인 문법입니다. 이 PR 에서 "생성된 문법"이라고 부른 것이 뒤쪽이에요. 두 문법의 ALTER DATABASE 규칙은 아래처럼 달랐습니다.

// legacy MySQL 문법: 이름이 선택 alterDatabase : ALTER dbFormat = (DATABASE | SCHEMA) uid? createDatabaseOption+ # alterSimpleDatabase // 생성된 MySQL 문법 (Oracle 문법 기반): 이름이 필수 alterDatabase : DATABASE_SYMBOL schemaRef alterDatabaseOption+ ;

legacy 문법은 이름(uid?)을 생략할 수 있었고, legacy 리스너는 이름이 없으면 parser.currentSchema() 로 대신했어요. 새 문법으로 옮기면서 이 허용이 빠졌으니 회귀였습니다.

📖 용어: 회귀 (regression)
예전에는 되던 동작이 변경 후에 안 되는 버그예요. 여기서는 legacy 문법이 받아 주던 문장을 새 문법이 거부하게 된 경우입니다.

2. MySQL 은 정말 이름 없이 받아 줄까

문법을 고치기 전에 확인할 것은 "MySQL 이 이 문장을 받아 주는가"였어요. 공식 문서의 문법은 ALTER {DATABASE | SCHEMA} [db_name] alter_option ... 이고 이름이 대괄호 안에 있습니다. 문서만으로는 부족하다고 보고 공식 mysql 이미지 8.0.46, 8.4.11, 9.4.0 에서 같은 문장을 실행해 PR 본문에 붙였어요.

$ mysql -NB -e "ALTER DATABASE CHARACTER SET utf8mb4;" ERROR 1046 (3D000) at line 1: No database selected $ mysql -NB -e "CREATE DATABASE db1 CHARACTER SET latin1; USE db1; ALTER DATABASE CHARACTER SET utf8mb4; SHOW CREATE DATABASE db1; ..." db1 CREATE DATABASE `db1` /*!40100 DEFAULT CHARACTER SET utf8mb4 COLLATE utf8mb4_0900_ai_ci */ ...

선택된 데이터베이스가 없을 때 서버는 문법 오류가 아니라 No database selected 를 돌려줘요. 이름이 빠졌으니 현재 데이터베이스를 쓰겠다는 뜻이고, 현재 데이터베이스가 있으면 문자셋이 실제로 바뀝니다. 세 버전 모두 결과가 같았어요. 이름은 선택 사항이고, 생략하면 현재 데이터베이스에 적용된다는 것을 서버 응답으로 확인한 셈입니다.

3. 고친 것: 토큰 하나와 리스너 한 줄

문법에서는 schemaRef 를 선택으로 바꿨어요. 이름이 없으면 ctx.schemaRef() 가 null 이 되므로, 리스너는 legacy 리스너처럼 현재 스키마로 대신합니다.

--- a/debezium-ddl-parser/.../mysql/generated/MySqlParser.g4 +++ b/debezium-ddl-parser/.../mysql/generated/MySqlParser.g4 alterDatabase - : DATABASE_SYMBOL schemaRef alterDatabaseOption+ + : DATABASE_SYMBOL schemaRef? alterDatabaseOption+ ; --- a/debezium-connector-mysql/.../CreateAndAlterDatabaseParserListener.java +++ b/debezium-connector-mysql/.../CreateAndAlterDatabaseParserListener.java public void enterAlterDatabase(MySqlParser.AlterDatabaseContext ctx) { - databaseName = parser.parseName(ctx.schemaRef().identifier()); + // The database name is optional and defaults to the current database + databaseName = ctx.schemaRef() == null ? parser.currentSchema() : parser.parseName(ctx.schemaRef().identifier()); charsetSpecified = false;

테스트는 두 개를 넣었어요. BinlogAntlrDdlParserTest#shouldParseAlterDatabaseWithoutDatabaseName 은 MySQL 과 MariaDB 테스트 클래스가 함께 상속하는 공통 테스트이고, ALTER DATABASE CHARACTER SET ... 과 ALTER SCHEMA CHARSET ... 뒤에 현재 데이터베이스의 문자셋을 확인합니다. MySqlAntlrDdlParserTest#shouldParseAlterDatabaseWithDefaultCharsetWithoutDatabaseName 은 DEFAULT CHARACTER SET 과 DEFAULT CHARSET ... DEFAULT COLLATE ... 형태를 다뤄요.

리스너 한 줄에는 사연이 하나 있어요. main 에 rebase 할 때 dbz#373 의 변경이 같은 메서드(enterAlterDatabase)에 charsetSpecified = false; 를 넣어 두어서 충돌이 났습니다. 두 변경이 서로 다른 일을 하므로 둘 다 남겼고, 위 diff 의 마지막 줄이 그 결과예요.

4. 다시 돌려 본 재현

이번 회고를 쓰면서 머지된 커밋(8787caaa)을 받아 같은 테스트를 다시 돌렸어요. CI 의 Java 설정 기본값이 Temurin 21 이라 JDK 21 을 썼고, 통합 테스트는 Docker 가 필요해서 빼고 DDL 파서 단위 테스트만 골랐습니다. 처음 한 번은 의존 모듈을 함께 설치해야 해서 17분 38초가 걸렸고, 그 뒤 테스트 실행은 9초였어요.

$ ./mvnw -B -pl debezium-connector-mysql test ... \ -Dtest='MySqlAntlrDdlParserTest#shouldParseAlterDatabaseWithoutDatabaseName+shouldParseAlterDatabaseWithDefaultCharsetWithoutDatabaseName' [INFO] Tests run: 2, Failures: 0, Errors: 0, Skipped: 0 [INFO] BUILD SUCCESS

다음에는 .g4 의 schemaRef? 만 schemaRef 로 되돌렸어요. 리스너와 테스트는 그대로 두고 debezium-ddl-parser 모듈을 다시 설치해 파서 코드를 새로 생성했습니다.

$ ./mvnw -B -pl debezium-ddl-parser clean install -Dquick -DskipTests ... $ ./mvnw -B -pl debezium-connector-mysql test ... (같은 테스트) [ERROR] Tests run: 2, Failures: 0, Errors: 2, Skipped: 0 io.debezium.text.ParsingException: DDL statement couldn't be parsed. ... with the statement 'ALTER DATABASE CHARACTER SET utf8mb4;' mismatched input 'CHARACTER' expecting {ACCOUNT_SYMBOL, ACTION_SYMBOL, ADDDATE_SYMBOL, ...

파서는 DATABASE 다음에 이름이 될 수 있는 토큰을 기다리는데 CHARACTER 가 와서 멈췄다는 뜻이에요. 두 번째 테스트도 mismatched input 'DEFAULT' 로 같은 자리에서 실패했습니다. PR 본문에 적은 "문법 변경이 없으면 두 테스트가 이슈의 ParsingException 으로 실패한다"와 같은 결과예요.

⚠️ 문법을 되돌릴 때는 clean 부터
처음에는 clean 없이 install 만 했어요. 그랬더니 테스트가 ALTER 가 아니라 첫 줄인 CREATE DATABASE db1 ... 에서 mismatched input 'CREATE' 로 실패했습니다. 생성된 코드가 바뀐 문법과 어긋난 상태였어요. clean install 로 다시 만들고 나서야 의도한 문장에서만 실패했습니다. 문법을 바꾼 실험에서 실패한 위치가 바꾼 규칙과 맞는지 먼저 봐야 하는 이유예요.

5. 리뷰: "상류 문법과 맞춰 두고 싶다"

첫 리뷰는 Naros 가 남겼어요. 두 테스트에 @FixFor("debezium/dbz#2829") 를 붙이라는 제안과 main 에 rebase 해 달라는 요청이었고, 반영 뒤 "LGTM, I'd like to get feedback from @vsantonastaso before merging." 으로 승인했습니다.

vsantonastaso 는 질문 두 개를 남겼어요. 실제 MySQL 에서 시험한 증거가 있는지, 그리고 이 문법을 상류 ANTLR 문법과 맞춰 두려 하니 상류에서도 이 문제를 논의할 수 있는지였습니다. 첫 번째는 2장의 세 버전 실행 결과를 PR 본문에 붙여 답했어요. 두 번째를 위해 상류 문법을 열어 보니 sql/mysql/Oracle/MySQLParser.g4 의 규칙도 DATABASE_SYMBOL schemaRef alterDatabaseOption+ 로 같은 제약을 갖고 있었습니다.

📖 용어: 상류 (upstream)와 vendored 문법
Debezium 의 debezium-ddl-parser/README.md 는 MySQL 문법 파일을 grammars-v4 에서 복사해 왔고, 올릴 때는 다시 내려받아 덮어쓴다고 적어 둬요. 이렇게 다른 저장소의 파일을 자기 저장소에 복사해 두는 것을 vendoring 이라고 하고, 원본 저장소를 상류라고 부릅니다.

그래서 grammars-v4 에 이슈 #5036 을 열고, 같은 한 토큰 변경을 PR #5037 로 올렸어요. Debezium PR 에는 이 README 내용을 들어 "상류에서 고쳐야 다음 동기화 때 이 변경이 덮어써지지 않는다"고 남겼습니다. 이 PR 이 먼저 머지돼도 같은 한 토큰이라 상류가 머지되면 그대로 맞춰진다는 점도 적었어요. vsantonastaso 는 상류 피드백을 며칠 기다려 보고, 없으면 먼저 머지한 뒤 상류 리뷰를 따라 필요하면 조정하자고 답했습니다.

6. 상류 PR 에서 확인한 것

grammars-v4 는 문법 폴더마다 examples/ 의 SQL 파일을 모두 파싱해 보는 방식으로 시험해요. 그래서 #5037 에는 문법 한 토큰과 함께 examples/ddl_alter.sql 에 세 줄을 넣었습니다.

alter database character set = utf8; alter database default character set = utf8; alter schema default character set = utf8;

PR 본문에는 모호성에 대한 설명도 넣었어요. 이름을 선택으로 만들면 DEFAULT 가 식별자로 쓰일 수 있는 문법에서는 ALTER DATABASE DEFAULT CHARACTER SET x 의 DEFAULT 를 이름으로 읽을 위험이 있습니다. Oracle 문법에서는 schemaRef 가 identifier 로 내려가고 DEFAULT_SYMBOL 이 identifierKeyword 에 없어서 그 위험이 없다는 내용이에요. 반대로 legacy MySQL 과 MariaDB 문법은 DEFAULT 를 식별자로 허용했고, 이 차이가 2편의 출발점입니다.

이번에 grammars-v4 의 머지 커밋(a5802dc9)에서 MySQL Oracle 문법 폴더 하나만 시험해 봤어요. 그대로는 예제 24개 파일이 모두 파싱돼 10초 만에 통과했고, 문법만 schemaRef 로 되돌리자 추가한 세 줄에서 정확히 실패했습니다.

$ ./mvnw -B -f sql/mysql/Oracle/pom.xml clean test line 61:15 mismatched input 'character' expecting {ACCOUNT_SYMBOL, ... line 62:15 mismatched input 'default' expecting {ACCOUNT_SYMBOL, ... line 63:13 mismatched input 'default' expecting {ACCOUNT_SYMBOL, ... [INFO] BUILD FAILURE

상류에는 리뷰 코멘트 없이 10월 20일에 teverett 이 머지하고 "thanks!" 한 줄을 남겼어요.

7. 결과와 남은 것

상류 머지 다음 날 Debezium PR 에 "상류 #5037 이 머지됐고 문법 변경이 이 PR 의 schemaRef? 와 같으니 복사본이 상류와 맞춰졌다, 리스너 대체 처리와 회귀 테스트는 Debezium 쪽 변경으로 남는다"고 알렸습니다. vsantonastaso 가 같은 날(10월 21일) "Applied 🚀" 와 함께 머지했어요. PR 을 연 10월 10일부터 11일이 걸렸고, 그중 대부분은 상류를 기다린 시간이었습니다.

CI 에서는 MariaDB 12.3 잡 하나가 실패한 상태였어요. 실패한 것은 ReadOnlyIncrementalSnapshotIT, MariaDbConnectorIT 같은 통합 테스트였고, 다른 35개 체크는 통과했습니다. 이 PR 은 그 상태로 머지됐어요. 같은 패턴이 2편의 PR 에서 다시 나와서, 이 PR 탓인지 가리는 과정은 2편에 적었습니다.

💡 이번 재현이 말해 주지 않는 것
• 이번에는 파서 단위 테스트만 돌렸고, 실제 MySQL 서버를 띄운 binlog 처리는 돌리지 않았어요. 서버 동작의 근거는 PR 에 붙인 세 버전 실행 결과입니다.
• 리스너의 현재 스키마 대체는 Debezium 이 추적하는 현재 스키마 값에 의존해요. USE 없이 이 문장이 들어오는 경우를 따로 시험하지는 않았습니다.
✍️ 오늘의 요약
생성된 MySQL 문법이 데이터베이스 이름을 필수로 요구해서 ALTER DATABASE CHARACTER SET ... 가 커넥터를 멈췄고, schemaRef? 한 토큰과 현재 스키마 대체로 고쳤어요.

되돌려 보면 같은 테스트가 ParsingException 으로 실패하고, 상류 예제 세 줄도 같은 자리에서 실패합니다. 복사해 온 문법을 고칠 때는 상류에도 같은 변경이 들어가야 다음 동기화 뒤에도 수정이 남아요.
