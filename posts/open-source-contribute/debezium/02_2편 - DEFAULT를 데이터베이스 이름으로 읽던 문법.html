1편의 PR 을 시험하던 중에 이상한 결과가 하나 나왔어요. MariaDB 문법에서 ALTER DATABASE DEFAULT CHARSET latin2 는 오류 없이 파싱되는데, 현재 데이터베이스의 문자셋이 바뀌지 않았습니다. 같은 문장에서 DEFAULT 를 빼거나 이름을 붙이면 제대로 바뀌었어요. DEFAULT 가 데이터베이스 이름으로 소비되는 것처럼 보였습니다.

원인이 1편과 달라서 그 PR 에는 넣지 않고 본문에 따로 적어 두었어요. Naros 가 별도 이슈와 PR 로 이 차이를 닫아 주면 좋겠다고 해서 시작한 것이 dbz#2842 와 PR #8225 입니다. 이 글은 오류 없이 틀리게 파싱되는 문제를 어떻게 확인하고 고쳤는지, 상류가 한 문법만 받아 준 이유, 그리고 머지 충돌과 CI 실패를 이 PR 탓인지 가린 과정을 적은 기록이에요. 이 PR 은 2026-10-23 현재 아직 열려 있습니다. 날짜와 시각은 따로 적지 않으면 모두 UTC예요.

1. 파싱은 성공했는데 값이 틀린 문제

1편의 문제는 파서가 예외를 내고 멈추는 것이었어요. 적어도 무언가 잘못됐다는 것은 바로 드러납니다. 이번 문제는 반대였어요. 파싱이 성공하니 커넥터는 계속 돌고, 문자셋은 DEFAULT 라는 이름의 데이터베이스에 기록되며, 실제 현재 데이터베이스는 예전 문자셋으로 남습니다. 이후 그 데이터베이스에서 문자셋을 따로 지정하지 않은 테이블을 만들면 커넥터가 추적하는 기본 문자셋이 서버와 달라질 수 있어요.

MariaDB 문법과 legacy MySQL 문법의 규칙은 같았습니다.

alterDatabase : ALTER dbFormat = (DATABASE | SCHEMA) uid? createDatabaseOption+ # alterSimpleDatabase | ALTER dbFormat = (DATABASE | SCHEMA) uid UPGRADE DATA DIRECTORY NAME # alterUpgradeName ;

문제는 DEFAULT 가 keywordsCanBeId 목록에 들어 있다는 점이에요. 이 목록에 있는 키워드는 식별자 자리에도 올 수 있어서 uid 가 DEFAULT 를 받아들입니다. DEFAULT CHARSET latin2 는 "옵션 하나"로도, "이름 DEFAULT + 옵션 CHARSET latin2"로도 읽을 수 있고, 두 읽기가 모두 문법에 맞아요. ANTLR 은 이 경우 uid? 를 먼저 시도하는 쪽을 골랐습니다.

📖 용어: keywordsCanBeId
MySQL·MariaDB 문법에서 키워드지만 테이블·컬럼 이름 같은 식별자로도 쓸 수 있는 단어를 모아 둔 규칙이에요. 여기에 들어 있는 단어는 uid 자리에서도 매칭됩니다.
📖 용어: 파스 트리 (parse tree)
파서가 문장을 어떤 규칙으로 읽었는지 나무 모양으로 남긴 결과예요. 같은 문장이 파싱에 성공해도 트리가 다르면 리스너가 받는 값이 달라집니다.

이번에 grammars-v4 의 MariaDB 문법으로 두 경우의 파스 트리를 직접 뽑아 봤어요. ANTLR 의 TestRig 에 -tree 를 주고 ALTER DATABASE DEFAULT CHARSET latin2; 를 넣었습니다.

// 변경 전 문법 (alterDatabase ALTER DATABASE (uid (simpleId (keywordsCanBeId DEFAULT))) (createDatabaseOption (charSet CHARSET) (charsetName (charsetNameBase latin2)))) // 변경 후 문법 (alterDatabase ALTER DATABASE (createDatabaseOption DEFAULT (charSet CHARSET) (charsetName (charsetNameBase latin2))))

변경 전에는 DEFAULT 가 uid 아래에 있고, 변경 후에는 createDatabaseOption 의 첫 토큰이에요. 두 트리 모두 파싱에는 성공하므로, 이 차이는 트리를 읽는 쪽에서만 드러납니다.

2. 서버는 DEFAULT 를 무엇으로 읽을까

문법을 고치기 전에 서버가 이 문장을 어떻게 해석하는지 확인했어요. 이번 PR 은 legacy MySQL 문법도 건드리므로 MariaDB 11.4.13, 11.8.9, 12.0.2 와 MySQL 5.7.44, 8.0.46 공식 이미지에서 같은 문장을 실행해 PR 본문에 붙였습니다.

$ mariadb -NB -e "ALTER DATABASE DEFAULT CHARSET utf8mb4;" ERROR 1046 (3D000) at line 1: No database selected -- USE db1 뒤 ALTER DATABASE DEFAULT CHARSET utf8mb4; -- db1 이 utf8mb4 로 바뀜 ALTER DATABASE db2 DEFAULT CHARSET latin2; -- db2 만 latin2, db1 은 그대로

현재 데이터베이스가 없을 때 서버의 답은 Unknown database 'DEFAULT' 가 아니라 No database selected 였어요. 이름이 생략됐고 DEFAULT 는 옵션의 시작으로 읽혔다는 뜻입니다. 다섯 버전 모두 같았어요. DEFAULT 는 MariaDB 와 MySQL 의 예약어라 따옴표 없이는 데이터베이스 이름이 될 수 없다는 점도 이 결과와 맞습니다.

3. 고친 것: 이름 없는 쪽을 먼저

두 읽기가 모두 가능할 때 ANTLR 은 앞에 적힌 대안을 고릅니다. 그래서 규칙을 "옵션만"과 "이름 + 옵션" 두 대안으로 나누고 옵션만 있는 쪽을 앞에 두었어요.

alterDatabase - : ALTER dbFormat = (DATABASE | SCHEMA) uid? createDatabaseOption+ # alterSimpleDatabase + // Options without a database name come first: DEFAULT is also allowed as an identifier, so with + // "uid?" first, 'ALTER DATABASE DEFAULT CHARSET x' would take DEFAULT as the database name. + : ALTER dbFormat = (DATABASE | SCHEMA) (createDatabaseOption+ | uid createDatabaseOption+) # alterSimpleDatabase | ALTER dbFormat = (DATABASE | SCHEMA) uid UPGRADE DATA DIRECTORY NAME # alterUpgradeName ;

같은 변경을 mariadb/generated/MariaDBParser.g4 와 mysql/legacy/MySqlParser.g4 에 넣었어요. 이름이 있는 문장(ALTER DATABASE db2 ...)은 첫 대안이 일반 식별자로 시작할 수 없으므로 예전처럼 두 번째 대안으로 파싱됩니다. 이름이 없으면 uid() 가 여전히 null 이고 리스너는 이미 현재 스키마로 대신하고 있었으므로 리스너는 바꾸지 않았습니다.

테스트는 MariaDbOnlyAntlrDdlParserTest 와 MySqlPtAntlrDdlParserTest 에 같은 두 개를 넣었어요. 이름 없이 DEFAULT CHARACTER SET 을 바꾸는 경우와, 이름을 주면 그 데이터베이스만 바뀌는 경우입니다. 1편의 공통 테스트 클래스(BinlogAntlrDdlParserTest)에 넣지 않은 이유도 PR 에 적었어요. 그 클래스는 생성된 MySQL 문법으로도 돌기 때문에 1편 PR 이 머지되기 전에는 실패하게 됩니다. 두 PR 을 서로 독립적으로 머지할 수 있게 하려는 선택이었어요.

5. 상류가 받아 준 문법, 받지 않는 문법

두 문법도 상류에서 복사해 온 파일이었어요. legacy MySQL 문법은 파일 머리말에 grammars-v4 의 sql/mysql/Positive-Technologies/MySqlParser.g4 에서 왔다고 적혀 있고, MariaDB 문법은 sql/mariadb/MariaDBParser.g4 와 줄 단위로 같았습니다. 1편과 같은 이유로 상류에 이슈 #5038 과 PR #5039 를 같은 규칙 순서로 올렸어요.

📖 용어: deprecated 문법
상류가 더 이상 관리하지 않기로 정한 문법이에요. grammars-v4 에서 Positive-Technologies MySQL 문법이 여기에 해당하고, 이 문법에 대한 PR 은 받지 않기로 #4429 에서 정했습니다.

같은 날 kaby76 이 #4429 를 가리켰어요. Positive-Technologies 문법은 deprecated 이고 그 문법에 대한 PR 은 거절한다는 내용이었습니다. 그래서 그 파일의 변경을 되돌리는 커밋을 올리고 제목과 이슈 범위를 MariaDB 로 좁혔어요. MariaDB 서버 세 버전의 실행 결과가 남은 범위를 그대로 뒷받침한다는 점도 코멘트로 남겼습니다.

#5039 에는 예제를 일부러 넣지 않았어요. grammars-v4 의 시험은 예제 파일이 파싱되는지만 보는데, 이 문장은 고치기 전에도 파싱되므로 예제가 아무것도 지키지 못하기 때문입니다. 이번에 MariaDB 문법 폴더를 머지 커밋(84b3dca1)과 되돌린 상태에서 각각 돌려 보니, 예제 23개 파일이 두 경우 모두 통과했어요. 차이는 1장에서 본 파스 트리에만 있었습니다.

그림 1. 상류에 들어간 문법과 Debezium 에만 남는 문법

#5039 는 10월 20일에 teverett 이 머지했어요. 다음 날 Debezium PR 에 상황을 정리해 남겼습니다. MariaDB 문법은 상류와 같은 옵션 우선 규칙으로 맞춰졌고, Positive-Technologies 문법은 상류에서 deprecated 라 일부러 빠졌으며, Debezium 은 legacy 복사본을 아직 쓰고 시험하므로 같은 수정을 Debezium 쪽 유지보수 패치로 남긴다는 내용이었어요.
