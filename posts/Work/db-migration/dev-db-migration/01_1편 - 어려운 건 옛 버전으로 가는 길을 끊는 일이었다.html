📚 dev DB 메이저 버전 이관, 1편
1편. MySQL 8.0 이관 후 부팅 설정의 5.7 참조 정리하기 ← 지금 이 글

새로 만든 테이블의 DDL(테이블 구조를 정의하는 SQL)을 dev에 적용하다가 다음 오류가 났어요.

ERROR 1273 (HY000): Unknown collation: 'utf8mb4_0900_ai_ci'

표준으로 정한 콜레이션을 dev DB가 지원하지 않는다는 뜻이에요. 콜레이션은 문자열을 비교하고 정렬하는 규칙이에요. dev는 MySQL 5.7이었고, 이 콜레이션은 8.0부터 지원했어요. 반면 이 서비스의 prod는 Aurora MySQL 3.10.3, 즉 MySQL 8.0.42 호환 버전이었어요.

몇 달 동안 dev의 DDL 실행 결과만으로는 prod에서도 같은 결과가 날지 판단하기 어려운 상태였어요. 그래서 dev DB를 5.7에서 8.0.42로 옮겼어요. 작업을 5단계로 나누고 각 단계에서 되돌리는 데 필요한 백업과 기존 볼륨을 보존했어요.

1. dev에서 검증하지 못한 콜레이션과 예약어

버전 차이는 같은 DDL과 쿼리를 검증하는 데 영향을 줬어요. 처음 오류가 난 콜레이션부터 확인했어요.

5.7에서는 utf8mb4_general_ci 나 utf8mb4_unicode_ci 등을 써요. 8.0에서 기본값이 된 utf8mb4_0900_ai_ci는 5.7에서 지원하지 않아요. 신규 테이블에 표준 콜레이션을 적용하려 해도 기존 dev DB에서는 해당 DDL을 테스트할 수 없었어요. prod에 적용하기 전에 같은 버전에서 검증할 환경이 필요했어요.

예약어도 늘었어요. 8.0에서 rank, groups, system, lead 같은 단어가 예약어가 됐어요. 5.7에서 실행되던 쿼리도 8.0에서는 문법 오류가 날 수 있다는 뜻이에요. dev가 5.7이면 이런 차이를 미리 확인하기 어려워요.

그래서 dev·CI·prod 세 곳의 호환 기준을 8.0.42로 맞추는 것을 목표로 잡았어요. CI는 테스트용 DB 컨테이너를 실행하는 Testcontainers를 쓰고 있어서 이미지 태그를 mysql:8.0.42로 고정하면 됐어요. 기존 데이터가 있는 dev는 이관 절차가 필요했어요.

2. 덤프 완료 여부와 테이블 수 확인하기

먼저 데이터를 SQL 파일로 내보내는 논리 백업을 만들었어요. 이때 시스템 DB를 포함하지 않도록 옵션을 골랐어요.

# --all-databases 가 아니라 --databases mysqldump --databases app_db --single-transaction > backup.sql # 검증 1) 중간에 끊기지 않았나 tail -1 backup.sql # -- Dump completed on ... 이 나와야 정상 # 검증 2) 테이블이 다 들어왔나 grep -c 'CREATE TABLE' backup.sql
💡 --databases로 이관할 DB를 지정해요
--all-databases 는 mysql 시스템 DB까지 함께 덤프해요. 이 덤프를 8.0에 복원하면 5.7의 권한 테이블과 8.0의 시스템 테이블 구조 차이로 문제가 생길 수 있어요.
이번 이관에서는 애플리케이션 데이터만 옮기고 새 버전의 시스템 DB는 유지했어요.

44MB 백업 파일이 생긴 뒤에는 덤프가 끝까지 실행됐는지 확인했어요. 파일이 있어도 디스크 부족 등으로 중간에 끊겼을 수 있기 때문이에요. 덤프 말미에 -- Dump completed on이 있는지, CREATE TABLE 개수가 원본 테이블 수와 같은지 확인했어요. 덤프 완료 여부와 테이블 수를 먼저 확인하고, 실제 복원 결과는 다음 단계에서 검증했어요.

3. 기존 DB를 유지한 채 8.0을 병행 기동하기

5.7 컨테이너를 먼저 내리고 8.0을 올리면 복원이 실패한 동안 dev 서비스를 쓸 수 없어요. 그래서 기존 DB를 유지한 채 새 DB를 준비하는 블루그린 방식으로 진행했어요.

8.0을 3307 포트에 따로 띄우고 3306의 5.7은 계속 서비스하게 뒀어요. 새 DB에 데이터를 복원하고 검증을 통과한 뒤 포트를 바꿨어요. 아래 코드는 목표 패치 버전으로 고정한 흐름 예시예요. 당시 최초 컨테이너의 정확한 태그는 확인하지 못했어요. 초기 인증·비밀번호 전달·데이터 볼륨 설정도 생략했으므로, 이 명령만으로 새 MySQL 컨테이너를 기동할 수는 없어요.

# 8.0 을 3307 에 띄운다 — 3306 의 5.7 은 그대로 서비스 중 docker run -d --name app-dev-mysql8 -p 3307:3306 mysql:8.0.42 # "ready for connections" 로그를 믿지 말고 실제 쿼리로 확인 until docker exec app-dev-mysql8 mysql -uroot -p"$PW" -e 'SELECT 1' &> /dev/null; do sleep 2 done
⚠️ 로그와 함께 SQL 응답도 확인해요
MySQL 컨테이너 로그에는 이 문장이 두 번 나왔어요. 하나는 X Plugin(33060), 다른 하나는 실제 SQL 포트의 로그였어요. 앞의 로그만 보고 복원을 시작하면 SQL 접속이 거부될 수 있어요.
로그 문자열만 확인하는 대신 위 코드처럼 SELECT 1이 응답할 때까지 기다리는 루프로 SQL 접속 가능 여부를 확인했어요. 이 코드는 준비 여부 확인 부분만 보여 줘요. 접속 실패가 계속되면 대기를 중단하고 컨테이너 상태·초기화 로그·인증 정보를 확인해야 해요.

앱 DB 덤프에는 계정·권한 이관이 포함되지 않아요. 새 서버에서 사용할 계정과 권한은 별도로 준비할 대상이며, 당시 어떤 절차로 준비했는지는 확보한 자료로 확인하지 못했어요. 검증 항목은 세 개였어요. 전체 테이블의 행 수 차이(diff)가 0인지, mysql.user의 계정이 유지됐는지, 앱이 접속해 API가 200을 반환하는지 확인했어요. 5.7에서 8.0으로 바뀌면서 인증 플러그인 기본값도 달라지므로 계정 확인이 필요했어요.

그림 1. 목표 패치 버전을 표시한 전환 구성. 실제 최초 컨테이너 태그와 인증 준비 절차는 미확인이에요

4. 부팅 설정에 남아 있던 5.7 참조 정리하기

포트를 바꾼 뒤 API가 200을 반환하는 것까지 확인했어요. 다만 현재 실행 중인 컨테이너와 재부팅할 때 실행될 컨테이너가 같은지는 별도로 확인해야 했어요.

dev 서버에서는 systemd 유닛이 헬스체크 스크립트를 호출하고, 헬스체크가 start 스크립트를 거쳐 Compose를 실행했어요. 이 호출 순서를 따라가 보니 두 곳에 5.7 참조가 남아 있었어요.

8.0이 실행 중이어도 재부팅 때 기존 설정을 실행하면 5.7 컨테이너가 다시 올라올 수 있었어요. 그러면 3306 포트를 두 컨테이너가 경쟁하거나, 예전 볼륨을 연결한 5.7에 앱이 접속할 수 있어요. 이관 뒤 변경한 데이터가 보이지 않는 문제로 이어질 수 있는 설정이었어요.

그림 2. systemd부터 Compose까지 호출 순서를 따라 5.7 참조를 확인했어요

부팅 설정의 호출 순서를 따라가며 5.7 참조를 지웠어요. Compose의 db 서비스는 mysql:8.0.42와 새 볼륨, 표준 기동 플래그를 쓰도록 바꿨어요. 헬스체크와 유틸 스크립트의 컨테이너명도 교체했어요. 별도 crontab이 없는지도 확인해, 조사한 설정에서는 systemd를 통해 기동하는 구조임을 확인했어요.

다만 실제 재부팅 검증은 하지 않았어요. 설정을 수정하고 호출 관계를 확인한 것까지가 이번 검증 범위예요. 재부팅한 뒤에도 8.0이 기동하는지는 확인이 남았어요.

5. 기존 데이터 볼륨과 목표 패치 버전 보존하기

기존 데이터 디렉터리를 새 버전으로 직접 변환하는 인플레이스 업그레이드에도 주의가 필요해요. MySQL 8.0은 새 이미지로 기동하면서 데이터 디렉터리를 자동으로 업그레이드해요. 한번 변환한 디렉터리를 그대로 5.7에 다시 연결할 수는 없어요.

그래서 5.7에서 쓰던 물리 볼륨을 따로 보존했어요. 44MB SQL 파일은 새 DB에 논리 복원할 때 쓰고, 기존 볼륨은 5.7 컨테이너를 다시 기동할 때 쓰는 용도였어요. 되돌리는 방식이 달라 두 백업을 함께 보관했어요.

⚠️ 목표 패치 버전을 처음부터 고정하지 않았어요
Phase 2에서 "8.0" 컨테이너에 복원한 뒤 Phase 4에서 이미지를 8.0.42로 교체하는 2단계로 진행했어요. 만약 Phase 2에서 mysql:8.0 태그를 썼다면 8.0.43 이상을 받았을 수 있어요. 그러면 Phase 4는 다운그레이드가 돼요. 다만 MySQL 8.0.35부터는 같은 8.0 계열 안의 인플레이스 하향을 지원하므로, 8.0.43에서 8.0.42로 바꾼다는 이유만으로 기존 디렉터리를 사용할 수 없다고 한 설명은 맞지 않아요. 8.0에서 5.7로 되돌리는 메이저 버전 하향과는 구분해야 해요. 여기서 확인한 문제는 태그를 고정하지 않아 실제 복원·검증 버전이 목표와 달라질 수 있었다는 점이에요.
당시 이 단계에서 문제는 없었지만, 첫 컨테이너부터 prod의 호환 패치 버전에 맞췄다면 Phase 4의 이미지 교체는 필요 없었어요. 단계만 추가하면서 버전이 달라질 여지를 남긴 셈이에요.

6. 신규 6개 테이블에 적용한 스키마 표준

버전을 맞춘 뒤 처음 적용하려던 스키마 표준을 반영했어요. 이미 데이터가 들어 있던 신규 테이블 6개를 대상으로 데이터를 보존하면서 변경했어요.

-- ① 콜레이션 — 테이블을 재구성해요 (데이터는 보존) ALTER TABLE landing_page CONVERT TO CHARACTER SET utf8mb4 COLLATE utf8mb4_0900_ai_ci; -- ② 시간 컬럼 정밀도 — 초 단위로는 이벤트 순서가 깨져요 ALTER TABLE landing_page MODIFY created_at DATETIME(6) NOT NULL DEFAULT CURRENT_TIMESTAMP(6); -- ③ 인덱스 명명 — 메타데이터만 바뀌어서 즉시 끝나요 ALTER TABLE landing_page RENAME INDEX uq_lp_slug TO uk_lp_slug;

각 변경에 필요한 작업은 달라요. ①은 테이블을 다시 구성하므로 데이터가 크면 오래 걸릴 수 있고, ③은 인덱스 이름을 바꾸는 메타데이터 수정이에요. 같은 ALTER TABLE이라도 작업량이 다르므로 prod에 적용할 때는 변경 종류를 구분해서 시간을 예상해야 해요.

⚠️ 기존 테이블의 콜레이션은 남아 있어요
Phase 2에서 5.7 덤프를 논리 복원했기 때문에 나머지 수십 개 테이블은 기존 콜레이션(general_ci)을 유지했어요. 표준 콜레이션으로 바꾼 대상은 신규 6개뿐이에요.
한 DB 안에 콜레이션이 두 종류 섞인 상태였지만, 당시에는 "표준화 완료"라고 기록했어요. 신규 테이블에만 적용했다는 범위를 빠뜨린 기록이었어요.

이 차이는 문자열을 비교할 때 문제가 될 수 있어요. 문자 집합이 같다면 콜레이션이 달라도 저장되는 바이트는 같아요. 같은 '한글'을 넣어도 콜레이션에 따라 비교와 정렬 결과는 달라질 수 있어요.

서로 다른 콜레이션의 문자열 컬럼을 비교하면 다음과 같은 오류가 날 수 있어요.

그림 3. 다른 콜레이션의 문자열 컬럼을 비교할 때 오류가 날 수 있어요

당시 신규 테이블에서 기존 테이블을 참조하는 컬럼은 모두 BIGINT였어요. 숫자를 비교하는 JOIN에는 콜레이션이 개입하지 않아 이 오류가 나지 않았어요. 다만 문자열 비교가 추가되면 콜레이션 충돌이나 인덱스 사용에 영향이 없는지 확인해야 해요.

문서에는 "혼재 상태: 경계를 넘는 문자열 비교 금지"로 남기고 전체 테이블의 콜레이션 변환은 별도 과제로 분리했어요. 데이터 크기에 따라 변환 시간이 달라지므로 이번 버전 이관과 함께 진행하지 않았어요.

✍️ 이관 결과와 남은 검증
5단계로 이관하면서 백업을 확인하고, 5.7을 유지한 채 8.0을 준비한 뒤 행 수·계정·앱 응답을 검증했어요. 부팅 설정의 5.7 참조도 정리했지만 실제 재부팅 검증은 남았어요.

목표 패치 버전을 첫 단계부터 고정하지 않아 복원·검증 버전이 달라질 여지를 남겼고, 콜레이션 표준은 신규 6개 테이블에만 적용했어요. 기존 테이블과의 콜레이션 혼재는 별도 과제로 남겼어요.
