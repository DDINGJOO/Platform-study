3편. MySQL 이관 검증표에서 빠진 파라미터와 데이터 내용 확인 ← 지금 이 글

dev DB를 MySQL 8.0으로 이관한 뒤 검증표를 만들었어요. 항목마다 기대값을 적고, 실제 쿼리 결과와 비교해 통과 여부를 표시했습니다.

| 검증 항목 | 기대값 | 결과 | |----------------------|-----------------------|-----------| | 서버 버전 | 8.0.42 | ✅ | | 테이블 콜레이션 | utf8mb4_0900_ai_ci | ✅ 6/6 | | _at 시간 컬럼 | datetime(6) | ✅ 9/9 | | 인덱스 프리픽스 | uk_ 6개 / idx_ 5개 | ✅ 11/11 | | 데이터 보존 | 변동 없음 | ✅ | | 앱 기동 · API | HTTP 200 | ✅ |

그리고 아래에 이렇게 적었어요. 여기서 prod 상신본은 운영 적용을 위해 제출한 DDL 파일을 뜻해요. 실제 운영 DB를 조회한 결과와는 구분해야 해요. "dev 스키마 = 레포 마이그레이션 파일 = prod 상신본, 3자 일치."

여섯 항목이 모두 통과해서 이관이 끝났다고 판단했어요. 하지만 타임존 파라미터와 데이터 내용은 대조하지 않았고, 인덱스 개수를 비교한 문서도 구버전이었습니다. 검사 결과만으로 세 대상이 일치한다고 결론 내리기에는 확인 범위가 부족했어요.

그림 1. 기존 검증표로 확인하지 못한 세 가지 항목

1. 버전 외의 파라미터는 비교하지 않았어요

검증표 첫 줄이 SELECT VERSION() = 8.0.42 였어요. 이걸로 "dev 와 prod 의 DB 규격이 같아졌다"고 적었습니다. 그런데 버전 숫자는 DB 를 동등하게 만드는 여러 요소 중 하나일 뿐이에요.

타임존부터 확인할 필요가 있었어요. 신규 테이블의 시간 컬럼에는 다음과 같이 주석과 기본값을 넣었습니다.

published_at DATETIME(6) NULL COMMENT '최근 publish 시각(KST 벽시계)', created_at DATETIME(6) NOT NULL DEFAULT CURRENT_TIMESTAMP(6),

DATETIME 은 타임존 정보를 저장하지 않는 타입이에요. 따라서 시간을 만드는 쪽에서 어떤 기준을 사용하는지 확인해야 해요. 여기서 두 가지를 놓쳤습니다.

첫째, DEFAULT CURRENT_TIMESTAMP(6) 을 계산하는 건 앱이 아니라 DB 서버입니다. 정확히는 그 INSERT 를 처리하는 세션의 time_zone 이고, 기본값이 SYSTEM 이라 결국 서버 설정을 따라가요. 앱의 타임존 설정만으로 DB가 계산하는 기본값까지 확인했다고 볼 수 없어요.

둘째, dev 는 compose 에 TZ=Asia/Seoul 을 넣어뒀는데 prod는 Aurora여서 같은 방법으로 서버를 설정할 수 없었어요. SSH 도 없고 my.cnf 도 직접 수정할 수 없어요. 파라미터 그룹을 확인해야 했는데, 당시에는 대조하지 않았습니다.

⚠️ dev와 Aurora는 설정 방법이 달라요
Docker에서 사용한 설정을 Aurora에 그대로 적용할 수는 없어요. 버전뿐 아니라 각 환경에서 설정을 바꾸는 방법도 확인해야 합니다.
Aurora 파라미터 그룹은 클러스터 범위와 인스턴스 범위로 나뉘고, 설정값에 따라 재시작이 필요할 수 있어요.

앱과 DB가 서로 다른 타임존을 사용한다면 같은 행에도 기준이 다른 시간이 들어갈 수 있어요. 예를 들어 앱이 채우는 published_at 은 KST, 서버 DEFAULT 가 채우는 created_at 은 UTC로 저장되는 경우예요.

그림 2. 앱과 DB가 다른 타임존으로 값을 만드는 경우

같은 행 안에서 created_at 과 published_at 이 같은 순간을 뜻해도, 타임존 정보가 없는 숫자만 비교하면 00:00과 09:00으로 보여요. 이 예시에서 생성 시각 숫자는 발행 시각보다 작아요. 생성 전에 발행됐다는 방향의 설명은 잘못됐고, 문제는 서로 다른 기준의 벽시계 값을 같은 기준처럼 비교하는 데 있어요.

이 차이를 확인하려면 dev와 prod 양쪽에서 다음 쿼리를 실행해 결과를 대조해야 했어요. 당시 검증표에는 빠져 있던 항목입니다.

-- dev / prod 양쪽에서 각각 돌려서 대조한다 SELECT @@global.time_zone, @@session.time_zone, NOW(6), UTC_TIMESTAMP(6);

그리고 타임존만 문제가 아니었어요. 같이 대조했어야 하는 게 더 있습니다. sql_mode 는 8.0 에서 기본 구성이 달라졌고, lower_case_table_names 는 Aurora 에서 인스턴스를 만들 때 정하면 나중에 못 바꿔요. wait_timeout 은 커넥션 풀의 max-lifetime 을 정하는 근거값이고요.

이 설정들은 검증표에 없었어요. 서버 버전이 같다는 확인만으로 DB 규격 전체가 일치한다고 적은 셈입니다.

2. 행수 비교로는 데이터 내용을 확인할 수 없어요

이관 검증에서는 "전 테이블 행수 diff = 0"을 데이터 보존의 근거로 삼았어요. 원본과 복원본의 행수가 같으니 내용도 그대로일 것이라고 판단했습니다.

하지만 5.7에서 8.0으로 옮길 때 이중 인코딩(double encoding)처럼 내용이 달라지는 경우는 행수로 확인할 수 없어요. 컬럼이 latin1 인데 애플리케이션이 UTF-8 바이트를 그대로 저장한 경우입니다.

한 이라는 글자는 UTF-8 로 3바이트예요. 이걸 latin1 컬럼에 넣으면 DB 는 latin1 문자 3개로 받아들입니다. 저장은 됩니다. 에러도 안 나요. 그리고 덤프를 뜨면 그 바이트가 그대로 옮겨가고, 복원해도 그대로 들어갑니다.

그림 3. 문자열이 달라져도 행수는 3개로 같을 수 있어요

그림은 행수는 같지만 문자열이 달라진 경우를 보여 줘요. COUNT(*) 만 비교하면 이 차이를 찾을 수 없어요. 행수 검사가 통과해도 문자열 내용은 별도로 확인해야 합니다.

💡 "무결성 검증"이라고 부르려면 내용을 봐야 해요
최소한 이 정도는 있어야 합니다.
• 주요 텍스트 컬럼의 SUM(CRC32(col)) 대조: 입력의 문자셋·바이트 표현·NULL 처리를 맞춘 보조 검사예요. 충돌과 합계 상쇄 가능성이 있어, 합계가 같아도 모든 행·컬럼이 같다는 증명은 아니에요
• --single-transaction 은 InnoDB 만 보장하니 MyISAM 테이블이 있는지 먼저 확인하세요
• --source-data 는 백업과 일치하는 binlog 좌표를 남기는 한 방법이에요. 구버전 도구에서는 --master-data라는 이름을 써요. 이 옵션이 없다는 이유만으로 시점 복구(PITR)가 불가능하다고 단정할 수는 없어요. 별도로 확보한 좌표나 GTID, 이후 binlog가 있는지 확인해야 하며 이번 백업에서 그 자료를 확보했는지는 확인하지 못했어요

3. 인덱스 개수를 구버전 문서와 비교했어요

인덱스는 개수를 직접 조회했지만 비교 기준을 잘못 골랐어요. 검사 항목이 있어도 기대값이 최신 스키마와 다르면 차이를 놓칠 수 있었습니다.

인덱스 항목에 "uk_ 6개 / idx_ 5개 = 11/11 ✅"라고 적었어요. 실제로 dev DB에서 11개를 확인한 결과였어요. 하지만 최종 스키마의 기대 개수는 10개였습니다.

작업 도중에 상신본을 한 번 더 다듬으면서 중복 인덱스를 하나 뺐거든요. 유니크 키 uk_lpv_page_version (page_id, version) 이 있는데 idx_lpv_page (page_id, id) 를 당시에는 중복으로 판단했어요. InnoDB는 세컨더리 인덱스에 PK를 암묵적으로 붙이므로 앞의 키 구성을 (page_id, version, id) 로 설명했지만, 열의 포함 관계만으로 뒤 인덱스를 완전히 대체한다고 볼 수는 없어요. 중간의 version 때문에 page_id 조건에서 id 범위나 정렬을 이용하는 방식이 달라질 수 있어요. 실제 쿼리와 EXPLAIN을 확인하지 않은 상태에서 읽기 이득이 0이라고 단정한 설명은 정정해야 해요.

그래서 상신본과 레포 마이그레이션 파일에서는 뺐는데, dev DB 에서는 DROP 을 안 했습니다. 그리고 검증할 때 제가 기준으로 삼은 작업 문서는 인덱스를 빼기 전 버전이었어요.

-- 작업 문서 기준 (구버전): uk_ 6 + idx_ 5 = 11 → dev 는 11개 → ✅ -- 실제 최종본 (r6): uk_ 6 + idx_ 4 = 10 → dev 는 11개 → ❌ SHOW INDEX FROM landing_page_version; -- idx_lpv_page 가 남아있음 ALTER TABLE landing_page_version DROP INDEX idx_lpv_page;

조회한 개수는 맞았지만 기대 개수가 틀렸어요. 따라서 "3자 일치"라는 결론도 맞지 않았습니다. 구버전 문서만 기준으로 삼았다면 dev에 남은 인덱스를 놓쳤을 거예요.

💡 기준 문서의 버전부터 확인하기
작업 문서를 오전에 쓰고, 한 시간 뒤인 오후에 스키마를 한 번 더 고쳤어요. 검증할 때는 이전 문서를 그대로 사용했습니다.
기준 문서에 버전을 명시하고 실제 적용할 스키마와 같은 버전인지 확인해야 했어요.

문서와 스키마 파일을 따로 수정하다 보니 한쪽 변경을 다른 쪽에 반영하지 못했어요. 이 차이를 사람이 기억해서 확인하는 방식으로는 같은 누락이 생길 수 있습니다.

검증 스크립트가 저장소의 최종 마이그레이션 파일에서 기대값을 읽도록 하면 문서 간 대조를 줄일 수 있어요. 인덱스 개수뿐 아니라 컬럼 타입도 같은 기준으로 비교해야 합니다. 이는 보완 방향이고, 여기서 스크립트를 구현하거나 실행한 결과를 확인한 것은 아니에요.

4. 통과한 검사 옆에 미확인 범위를 적기

세 항목 모두 실제로 확인한 범위보다 넓은 결론을 내린 경우였어요.

① 버전은 맞췄는데 파라미터는 안 봤다: Docker 에서 되던 TZ 설정이 Aurora 에도 있을 거라고 가정했어요.
② 행수가 같으면 데이터도 같다고 봤다: 제가 아는 손상 방식(행이 사라짐)만 실패 모드로 상상했어요.
③ 문서가 최신일 거라고 봤다: 한 시간 전 문서와 최종 스키마의 차이를 확인하지 않았어요.

버전과 행수, 인덱스 개수라는 결과 자체는 확인했어요. 다만 그 결과가 파라미터 일치나 내용 보존, 최종 스키마 일치까지 뜻하지는 않았습니다. 검증표에는 이 차이를 구분할 설명이 없었어요.

그래서 요즘은 검증표를 쓸 때 칸을 하나 더 둡니다. "이 항목이 ✅ 여도 남는 위험" 이라는 칸이요.

| 검증 항목 | 결과 | 이 항목이 ✅ 여도 남는 위험 | |-------------|------|-----------------------------------| | 서버 버전 | ✅ | 파라미터(time_zone, sql_mode) 미대조 | | 행수 diff 0 | ✅ | 내용 손상(인코딩)은 못 잡음 | | 인덱스 11개 | ✅ | 기준 문서가 최신인지 미확인 |

검사마다 확인하지 못하는 내용을 적으면 추가로 비교할 항목을 정하기 쉬워요. 아직 판단할 수 없는 부분은 "모르겠음"으로 남겨 두고, 확인된 결과와 구분할 수 있습니다.

이 칸을 적으면서 Aurora 파라미터 그룹의 클러스터 범위와 인스턴스 범위도 제대로 구분하지 못하고 있었다는 점을 알게 됐어요. 버전 조회가 통과했다는 사실만으로는 떠올리지 못한 확인 사항이었습니다.

검증 결과에는 통과 여부와 함께 비교 기준, 실행 범위, 남은 확인 사항을 적기로 했어요. 그래야 다른 사람이 표를 읽을 때도 어디까지 확인한 결과인지 알 수 있습니다.

✍️ 오늘의 요약
버전은 맞췄지만 파라미터를 대조하지 않았고, 행수는 셌지만 내용을 비교하지 않았어요. 인덱스 개수는 구버전 문서와 비교해 최종 스키마와의 차이를 놓쳤습니다.

이후 검증표에는 각 항목이 통과해도 남는 위험을 함께 적었어요. 여기 제시한 추가 쿼리와 검증 자동화 방향을 실제로 실행해 확인한 결과는 포함하지 않았습니다.
