1편. MySQL 8.0 이관 후 부팅 설정의 5.7 참조 정리하기
2편. 백업 보관 뒤에도 확인해야 할 MySQL 롤백 조건 ← 지금 이 글

이관을 마친 뒤 작업 문서에는 5.7로 돌아갈 때 쓸 백업을 두 가지 적어뒀어요.

## 롤백 수단 (보관 중) | 수단 | 위치 | 비고 | |---------------|---------------------------------|--------------------| | 5.7 논리 백업 | ~/backup-20260803.sql (44MB) | 이관 직전 시점 | | 5.7 데이터 볼륨 | Docker volume (해시명) | 유일한 물리 롤백 |

논리 백업과 물리 볼륨을 보관했으니 복구 수단은 준비됐다고 생각했어요. 하지만 백업을 보관하는 것과 그 백업으로 서비스를 다시 기동하는 것은 확인할 내용이 달랐어요.

실제로 롤백 절차를 실행해 본 적은 없었어요.

절차를 검토하면서 볼륨 연결 외에도 앱 호환성과 전환 이후 데이터의 보존을 확인해야 한다는 점이 드러났어요.

1. 논리 백업과 물리 볼륨의 용도가 달랐어요

MySQL 8.0으로 기존 데이터 디렉터리(datadir)를 업그레이드하면 변환된 디렉터리를 그대로 5.7에 다시 연결할 수는 없어요. 새 버전 기동에 성공했더라도 이전 버전에서 쓸 데이터는 별도로 남겨야 해요.

논리 백업은 SQL을 실행해 데이터를 복원하는 데 쓰고, 물리 볼륨은 기존 데이터 디렉터리로 5.7을 기동하는 데 써요. 복원 방식이 달라 두 수단을 함께 보관했어요.

# 수단 A) 논리 백업 — 텍스트 SQL. 복원에 시간이 걸린다 mysql app_db < backup-20260803.sql # 수단 B) 물리 볼륨 — 붙이면 바로 뜬다 docker run -d -v app-mysql57-data:/var/lib/mysql mysql:5.7
⚠️ 변환된 datadir을 5.7에 다시 연결할 수는 없어요
새 버전에서 변환한 데이터 디렉터리를 이전 버전으로 다시 쓰는 방식은 지원하지 않아요.
그래서 5.7에서 쓰던 볼륨을 별도로 남겼어요. 논리 백업을 쓰는 경우에는 SQL을 복원하는 시간도 복구 절차에 포함해야 해요.

2. 이전 스키마와 현재 앱의 호환성 확인하기

보관한 볼륨으로 DB를 기동한 뒤 앱이 접속하는 단계까지 검토해 봤어요.

5.7 볼륨을 다시 연결하면 DB는 이관 직전 상태가 돼요. 반면 애플리케이션 코드는 배포된 상태를 유지하므로, 예전 스키마와 현재 코드가 호환되는지 따로 확인해야 해요.

이관 당시에는 표준 콜레이션과 시간 컬럼의 DATETIME(6), 인덱스 이름 규칙을 검토했어요. 다만 1편에서 구분한 것처럼 표준 콜레이션을 적용한 것은 신규 테이블이고, 덤프로 복원한 기존 테이블은 이전 설정을 유지했어요. 따라서 모든 테이블이 같은 규격으로 바뀌었다고 볼 수는 없어요.

5.7 볼륨에는 general_ci와 초 단위 DATETIME을 쓰는 테이블이 남아 있었어요. 이전 스키마와 현재 코드의 조합은 별도로 검증해야 해요. 이 차이가 실제 기동 실패로 이어지는지는 롤백 리허설에서 확인할 내용이에요.

그림 1. 이전 스키마에 현재 앱을 연결하는 조합도 확인해야 해요
⚠️ DB 기동과 앱 기동은 따로 확인해야 해요
운영 설정에서 spring.jpa.hibernate.ddl-auto는 validate예요. 이 설정은 앱 기동 시 엔티티와 테이블 매핑을 검증해요.
검증에서 불일치가 발견되면 앱 기동이 실패할 수 있어요. 다만 앞서 적은 콜레이션과 시간 정밀도 차이만으로 실제 실패를 확인한 것은 아니에요.

인증 설정도 함께 확인할 대상이에요. 8.0으로 옮길 때 구형 클라이언트 호환을 위해 mysql_native_password 기동 플래그를 사용했어요. 5.7로 돌아갈 때는 그쪽 계정 설정과 현재 클라이언트의 접속 조합을 확인해야 해요. 버전이 바뀐다는 이유만으로 인증 방식까지 반드시 달라진다고 단정할 수는 없어요.

볼륨 보관 여부만으로는 이 확인을 대신할 수 없었어요. DB 기동, 스키마 호환성, 인증과 앱 응답까지 절차에 포함해야 했어요.

3. 전환 이후 변경분을 확인해야 해요

데이터도 따로 확인해야 해요. 이관 직전의 5.7 볼륨에는 8.0 전환 뒤 추가하거나 수정한 데이터가 반영돼 있지 않아요. 그 볼륨으로 접속 대상을 바꾸면 사용자는 전환 이후 변경분을 볼 수 없어요.

dev 환경이라 그동안 변경이 없었을 가능성도 있지만, 그 가능성만으로 데이터 손실이 없다고 판단할 수는 없어요.

5.7을 3306 포트로 기동하는 것 자체가 8.0 볼륨을 삭제하는 것은 아니에요. 다만 8.0 볼륨을 정리하거나 덮어쓰면 전환 이후 변경분을 대조할 기준을 잃게 돼요. 롤백 전에 어떤 데이터를 남길지 정해 둬야 해요.

앱이 다시 응답하더라도 데이터 손실 여부까지 확인된 것은 아니에요. 롤백 완료를 판단할 때는 서비스 응답과 데이터 대조 결과를 구분해야 해요.

dev도 팀이 함께 쓰는 환경이에요. 다른 개발자가 만든 테스트 데이터나 연동 테스트에 필요한 데이터가 전환 이후에 추가됐을 수 있어요.

변경분을 확인하지 않고 이전 볼륨으로 전환하면 나중에 테스트가 실패했을 때 데이터 차이가 원인인지 추적하기 어려워요. 그래서 두 시점의 데이터를 남기고 비교할 필요가 있었어요.

4. 롤백 직전 데이터를 따로 보존하기

검토한 방법은 5.7을 연결하기 전에 8.0을 중지하고, 현재 볼륨을 별도 볼륨에 복사해 두는 것이었어요. 아래 명령은 이 절차를 설명하는 예시이며, 롤백을 실제로 실행한 결과는 아니에요.

# ❌ 이렇게 시작하면 비교 대상이 사라진다 docker stop app-dev-mysql8 docker run -d -v app-mysql57-data:/var/lib/mysql -p 3306:3306 mysql:5.7 # ✅ 첫 줄은 "지금 것을 봉인" 이다 docker stop app-dev-mysql8 docker volume create app-mysql8-preRollback docker run --rm -v app-mysql8-data:/from -v app-mysql8-preRollback:/to \ alpine sh -c 'cp -a /from/. /to/' # 이제 5.7 을 붙여도 비교 대상이 남아있다

위 예시의 첫 주석과 달리 중지와 다른 볼륨 연결만으로 기존 볼륨이 사라지지는 않아요. 별도 복사본을 만드는 목적은 롤백 직전의 상태를 비교 대상으로 보존하는 데 있어요. 복사했다고 변경분이 자동으로 합쳐지거나 손실 내역이 바로 확인되는 것은 아니에요.

보존한 볼륨을 나중에 식별할 수 있어야 해요. 당시 5.7 볼륨은 Docker가 자동으로 붙인 해시명으로 남아 있어, 이름만 보고 용도를 알기 어려웠어요.

문서에는 안정화 후 "1주 후 청소"라고 적어뒀어요. 정리할 때 백업 볼륨을 잘못 지우지 않으려면 용도를 알 수 있는 이름을 붙이거나 볼륨 ID를 문서에 명시해야 해요. 보관 기간과 삭제 대상을 함께 남기는 것도 필요했어요.

그림 2. 별도 보존본이 있으면 롤백 전후의 데이터를 대조할 수 있어요

5. 복제 관계가 없는 두 DB의 데이터 대조하기

두 볼륨을 보존한 다음에는 각각의 데이터를 읽어 차이를 확인해야 해요. 비교 방법도 롤백 전에 준비할 대상이었어요.

처음 검토한 방법은 데이터를 일정 범위씩 나눠 체크섬을 비교하는 것이었어요. 체크섬은 데이터에서 계산한 값으로, 두 결과가 다른지 확인하는 데 써요. Percona Toolkit의 pt-table-checksum도 후보였지만, 이 환경에는 도구가 전제하는 복제 관계가 없었어요.

💡 pt-table-checksum은 복제 관계를 이용해요
이 도구는 master에서 실행한 체크섬 쿼리가 binlog를 통해 replica로 전파되면, 각 서버가 자기 데이터로 계산한 결과를 대조해요. 이 과정에서 binlog_format=STATEMENT를 사용해요.
여기서 비교할 대상은 복제 관계가 없는 두 볼륨이었어요. 따라서 이 도구의 복제 기반 비교 방식을 그대로 적용할 수는 없었어요.
그림 3. pt-table-checksum의 비교 방식은 두 볼륨의 구성과 맞지 않았어요

그래서 두 DB에서 각각 쿼리를 실행하는 방법을 검토했어요. CHECKSUM TABLE은 row format, 즉 행의 물리적 저장 형식에도 영향을 받으므로 5.7과 8.0의 논리적 데이터 대조 수단으로 그대로 믿기 어려웠어요.

아래는 양쪽에서 행 수와 일부 컬럼의 CRC32 합계를 구하는 예시예요. 비교할 값을 같은 방식으로 계산하려는 접근이며, 이 쿼리만으로 모든 컬럼의 일치나 손실 내역까지 확정할 수는 없어요.

-- 양쪽에서 각각 돌려서 결과를 대조한다 SELECT COUNT(*), SUM(CRC32(slug)), SUM(CRC32(IFNULL(s3_key, ''))) FROM landing_page_version;

도구 이름만 정해 두는 것으로는 부족했어요. 보존한 두 DB에 적용할 수 있는지, 비교 대상 컬럼과 결과 해석이 맞는지도 미리 확인해야 해요.

🧪 보관한 백업으로 복구되는지 확인하기
문서의 두 줄은 백업을 보관한 위치를 보여 줘요. 그 백업으로 DB와 앱이 정상 동작하는지까지 확인한 결과는 아니에요.
실제 롤백 가능 여부를 판단하려면 기동 결과와 데이터 차이를 남기는 리허설이 필요해요.

리허설에서는 8.0 데이터 보존, 5.7 기동, 앱 접속과 응답 확인, 데이터 대조, 8.0 복귀까지 실행해 볼 필요가 있어요. 문제가 생긴 뒤 처음 시도하면 절차를 확인하는 시간까지 복구에 더해져요.

이 글의 검토 시점에는 롤백 리허설을 실행하지 않았어요. 공용 dev 환경에 미칠 영향을 조율하고, 실패했을 때 복귀할 절차까지 준비한 뒤 확인해야 할 작업으로 남아 있었어요.

✍️ 확인한 범위와 남은 작업
5.7 논리 백업과 물리 볼륨은 보관했지만, 실제 롤백 리허설은 하지 않았어요. 이전 스키마와 현재 앱의 호환성, 인증과 앱 응답을 확인해야 해요.

8.0 전환 이후 변경분을 대조할 수 있도록 롤백 직전 데이터를 별도로 보존하는 절차를 검토했어요. 두 DB에는 복제 관계가 없어 직접 쿼리로 비교하는 방법을 살펴봤으며, 예시 체크섬만으로 전체 데이터가 같다고 판단하지는 않았어요.
