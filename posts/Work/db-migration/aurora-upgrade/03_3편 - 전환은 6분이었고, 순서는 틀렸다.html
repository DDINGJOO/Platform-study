📚 Aurora 5.7 → 8.0, 5부작
1편. 파라미터 설정을 확인한 뒤 Blue/Green으로 바꾼 이유
2편. 전환 전에 파라미터와 green 복제본을 확인한 순서
3편. 전환 완료를 기다리기 전에 앱을 기동한 이유 ← 지금 이 글

복제본 준비를 마치고 Aurora MySQL 8.0으로 전환할 차례였어요. 정해둔 순서는 앱을 정지하고, DB 전환을 마친 다음 다시 기동하는 것이었습니다.

당시 기록에는 중단 약 6분, 데이터 유실 0으로 적었어요. 다만 아래 타임라인의 앱 정지부터 health UP까지는 4분 40초이며, 두 기록의 집계 범위 차이는 확인하지 못했어요. 데이터는 여섯 테이블의 행 수와 전환 후 전송 결과를 확인한 범위예요. 전환이 끝나기 전에 앱을 먼저 기동하는 실수도 있었습니다. 전환 명령이 반환되는 시점과 실제 완료 시점을 구분하지 않은 체크리스트를 다시 살펴봤어요.

1. 운영 접속 방식으로 8.0 연결 확인하기

2편의 준비 작업을 마친 뒤에도 운영이 쓰는 접속 방식으로 8.0에 연결하는 검증은 남아 있었어요.

개발 환경에서는 미리 검증했지만, 개발은 일반 접속 모드였고 운영은 페일오버를 지원하는 전용 모드였어요. 페일오버는 DB 장애 때 접속 대상을 바꾸는 동작이에요. 두 모드에서 드라이버가 실행하는 코드 경로가 달라 운영 방식도 확인해야 했습니다.

그래서 기록해둔 이미지 다이제스트로 컨테이너 하나를 따로 띄웠어요. 다이제스트는 실행할 이미지 버전을 정확히 지정하는 값이에요. 운영 이미지와 운영 프로필, 운영 환경변수를 그대로 사용했습니다.

compose 에 추가하지 않고 단독으로 ← 남의 배포가 라이브를 재시작하는 것을 막는다 프로필은 앱만, 배치 프로필 제외 ← 배치 프로필은 파기 스케줄러를 켠다 스키마 자동 초기화 never ← 읽기전용인 복제본에 쓰기 위험 제거

첫 시도는 테스트 실행 환경에 인증 관련 환경변수를 넘기지 않아 실패했어요. 실행 중인 컨테이너의 환경변수를 그대로 받아 다시 시도했습니다.

커넥션 풀 기동 완료 Started ... in 27.099 seconds health(40s): {"status":"UP"} 에러 스캔: (비어 있음)

운영 드라이버의 전용 모드로 8.0에 접속했고, 커넥션 풀 기동과 헬스체크 성공을 확인했어요.

⚠️ 접속 검증과 쿼리 검증의 범위
API 7개는 모두 401 응답으로 끝났어요. 인증 필터 뒤의 비즈니스 로직은 실행해보지 못했습니다.

확인된 것: 드라이버 접속 · 풀 기동 · ORM 초기화 · 헬스체크(데이터소스 검사 포함이라 복제본 왕복 쿼리 성공).
확인 안 된 것: ORM이 생성하는 엔티티 쿼리.

보완 검증으로 문자열 조인 3건(최대 52만 행)과 GROUP BY 2건을 실제 데이터에서 직접 실행해 에러 0을 확인했어요.

직접 실행한 SQL에서는 에러가 없었지만, 애플리케이션의 엔티티 쿼리까지 확인한 것은 아니었어요.

접속 로그에서는 ORM 방언 설정도 확인했어요.

Using dialect: org.hibernate.dialect.MySQL57Dialect

DB는 8.0인데 ORM은 5.7용 방언을 쓰고 있었어요. 방언은 ORM이 DB에 맞는 SQL을 만들 때 사용하는 설정이에요. 복제본에는 8.0 기본값에 있는 엄격 모드 하나도 빠져 있었습니다.

이번 전환에서는 기존 쿼리와의 호환성을 우선했어요. 목적은 확장 지원 비용을 없애는 것이었고, 엄격 모드를 켜서 5.7에서 통과하던 쿼리가 실패할 위험까지 이번 작업에 포함하지는 않기로 했습니다.

엄격 모드 적용은 별도 작업으로 남겼어요. 비용을 먼저 없애기로 한 결정이며, 호환성 설정까지 모두 8.0 기준으로 바꾼 것은 아니었습니다.

2. 여섯 테이블의 행 수 대조하기

전환 직전에는 원본과 복제본의 행 수를 비교했어요.

A B C D E F 원본 (5.7): 158897 138240 288997 62535 437744 190 복제본(8.0): 158897 138240 288997 62535 437744 190

여섯 테이블 모두 원본과 복제본의 행 수가 일치했어요. 이 행 수 대조를 전환 전 마지막 확인 항목으로 삼았지만, 행의 내용과 모든 쓰기의 보존까지 입증한 검사는 아니었어요.

3. 전환 완료 전에 앱을 기동한 이유

작업 시각은 원래 밤 10시에서 오후 5시로 옮겼어요. 야간 작업을 정한 이유가 트래픽이 적은 시간에 실행하기 위해서였고, 오후 5시에도 트래픽이 적다는 점을 보고 변경했습니다.

체크리스트에는 정지 → 전환 → 기동으로 적혀 있었어요.

그런데 전환이 진행 중인 상태에서 앱을 기동했어요. 앱과 커넥션 풀은 정상적으로 시작했지만, 그 시점의 접속 주소는 아직 옛 클러스터를 가리키고 있었습니다.

그림 1. 전환 명령 전송과 완료 확인을 별도 단계로 구분해야 해요

앱을 먼저 기동한 실수와 함께 체크리스트의 누락도 확인했어요. 전환 명령은 작업이 끝나기 전에 반환돼요. 완료 여부는 상태를 반복 조회하는 폴링으로 확인해야 합니다. 체크리스트에는 이 대기 단계가 빠져 있어서 명령을 보낸 직후 다음 단계로 넘어갈 수 있었어요.

앱을 바로 다시 정지하고, 전환 완료를 기다린 뒤 기동했어요.

⚠️ 트래픽이 없던 구간에서 발생한 실수
당시 기록상 해당 구간에 트래픽이 없었고, 확인한 범위에서 이 실수로 인한 오류나 유실 징후는 없었어요.

운영 드라이버는 전용 모드에서 인스턴스 엔드포인트를 캐시해요. 앱을 그대로 둔 채 요청을 받았다면 커넥션이 옛 클러스터를 계속 향해 읽기 전용 오류나 재연결 실패가 날 수 있었어요. 성공한 전환 뒤에는 옛 blue가 기본적으로 읽기 전용이므로, 두 클러스터에 각각 쓰기가 된다고 단정한 기존 설명은 맞지 않아요. 그런 쓰기 분기는 옛 DB를 다시 쓰기 가능하게 만드는 별도 조치가 있어야 하며, 이번에 그 조치를 한 것은 아니에요.

피해가 없었다는 결과만으로 이 순서를 다시 사용해도 된다고 판단할 수는 없었어요.

4. 정지·기동 시각과 연결·알람 확인하기

17:20 앱·배치 정지 → 앱 서버 커넥션이 사라진 것 확인 전환 명령 → 진행 중 → 완료 17:23:30 컨테이너 기동 17:24:40 health UP (70초)

앱 정지 확인 조건도 바꿨어요. 처음에는 전체 커넥션이 0이어야 진행하도록 정했지만, 관리용 내부 커넥션 7개가 남아 있었어요. 이 조건으로는 진행할 수 없어 앱 서버 주소에서 온 커넥션이 사라졌는지를 확인하도록 고쳤습니다.

전환 후에는 복제본이 기존 이름을 이어받았어요.

복제본 클러스터 → 원래 이름을 물려받는다 복제본 인스턴스 → 원래 인스턴스 이름을 물려받는다 옛 클러스터 → 이름에 -old 가 붙는다

앱 접속 URL은 바꾸지 않아도 됐어요. 알람 16개는 인스턴스 식별자로 이름을 구성하므로 자동으로 새 클러스터를 보게 됐습니다. 이 개수는 1편에서 확인한 10개에 2편에서 8.0 클러스터용으로 추가한 알람을 더한 수예요. 기존 접속 정보와 알람을 유지하려고 신규 클러스터 방식 대신 선택한 전환 방식이었습니다.

5. 옛 클러스터에는 전환 이후 데이터가 없다

후속 작업 계획에는 관측 3영업일 뒤 옛 클러스터를 삭제하고, 그때까지 롤백 자산으로 남긴다고 적었어요.

옛 클러스터는 남아 있었지만 복제는 전환 시점에 끊겼어요. 옛 클러스터에는 컷오버, 즉 접속 대상을 전환한 순간까지의 데이터만 남아 있었습니다.

반면 새 클러스터에는 전환 직후부터 데이터가 추가됐어요. 전송 17건이 성공했고 데이터 증가 추이도 확인했습니다.

그림 2. 기존 클러스터로 복귀하면 전환 이후 데이터가 빠져요

옛 클러스터로 복귀하려면 Blue/Green 배포 리소스 삭제와 읽기 전용 해제 조건, 앱 접속 경로를 별도로 확인해야 해요. 그 절차를 밟아도 전환 이후 변경분이 옛 DB에 생기지는 않아요. 클러스터가 남아 있다는 이유만으로 즉시 무손실 복귀가 가능한 것은 아니었습니다.

개발 DB를 옮길 때 쓴 "롤백은 되감기가 아니다"에서도 같은 문제를 다뤘어요. 이번 계획을 작성할 때는 그 내용을 참조하지 못하고, 옛 클러스터를 다시 롤백 자산이라고만 적었습니다.

3영업일 동안 얼마나 많은 데이터가 쌓이든 롤백 조건에는 그 데이터의 유실을 감수할지 판단하는 과정이 포함돼야 해요. 후속 계획에도 옛 클러스터로 복귀할 때 전환 이후 데이터가 빠진다는 제약을 함께 적어야 했습니다.

6. 8.0 기준 알람 임계값 재측정이 남았다

전환 뒤 관찰에서는 전송 17건이 모두 성공했고, 커넥션은 전환 직후 101에서 3으로 줄었어요. SQL 에러는 0이었으며 헬스체크는 5회 연속 200이었습니다.

중단 구간에는 정상 호스트가 0이어서 알람 1건이 발생했어요. 기동 후 타깃 상태는 직접 확인해 정상이었고, 알람은 새 데이터포인트가 들어오면 자동 복귀하는 상태였습니다.

다만 후속 작업에는 알람 임계값 재측정이 남아 있었어요.

알람 임계값 5종 재측정 — 전부 5.7 · 옛 인스턴스 기준 실측값이었다

당시에는 8.0 클러스터를 5.7 시절의 임계값으로 감시하고 있었어요. Aurora 3는 메모리 사용 패턴이 달라 임계값이 맞지 않으면 이상을 놓치거나 불필요한 알람이 발생할 수 있었습니다.

전환 직후의 관찰에 의존해 안정성을 판단하는 만큼, 새 버전에서 임계값이 적절한지도 함께 확인해야 했어요.

💡 변경 후 관찰 기준도 함께 준비하기
앞선 작업에서도 조치 후 관찰 수단을 마련하는 일이 늦어졌어요.

• 야간 축소: 조치했는데 남는 쪽을 보는 알람이 없었다
• 메모리 고갈: 조치했는데 상한에 닿은 걸 알 수단이 없었다
• 이번 작업: 버전을 올렸는데 알람은 옛 버전 기준이다

이번에도 버전 전환과 별개로 알람 임계값을 확인하는 일이 남았습니다. 전환 완료 여부와 관찰 준비 여부를 나눠 확인해야 했어요.
✍️ 전환 결과와 남은 확인
당시 기록의 중단 약 6분과 제시한 타임라인의 4분 40초는 집계 범위 차이를 확인하지 못했어요. 여섯 테이블의 행 수, 전환 뒤 전송과 헬스체크를 확인했지만 전체 데이터 무손실까지 입증한 것은 아니에요. 이름이 승계돼 앱 접속 URL과 알람 설정은 유지했습니다.

전환 완료 전에 앱을 기동한 뒤 다시 정지하고 완료를 기다렸어요. 체크리스트에는 비동기 명령의 완료 대기를 별도 단계로 적어야 했습니다. 옛 클러스터로 복귀하면 전환 이후 데이터가 빠진다는 제약이 있었고, 8.0 기준 알람 임계값 재측정도 남아 있었어요.
