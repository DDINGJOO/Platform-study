📚 Aurora 5.7 → 8.0, 5부작
1편. 파라미터 설정을 확인한 뒤 Blue/Green으로 바꾼 이유
2편. 전환 전에 파라미터와 green 복제본을 확인한 순서 ← 지금 이 글

1편에서 업그레이드는 Blue/Green으로 진행하기로 했어요. 운영 DB를 유지한 채 8.0 복제본인 green을 만들고, 전환할 때 이름을 맞바꾸는 방식이에요.

전환 전에 실제 DB 설정을 읽고, 복원에 쓸 스냅샷을 만든 뒤, 운영 DB에 붙이지 않은 리소스부터 검증했어요. 준비 중 문제가 생겨도 운영 DB에 영향을 주지 않는 순서로 진행하려고 했습니다.

1. 운영 DB에 영향이 적은 작업부터 진행하기

설정 조회부터 시작해 스냅샷과 미부착 리소스를 준비하고, green 생성과 검증을 마친 뒤 전환하기로 했어요.

그림 1. 운영 DB를 전환하기 전에 조회와 별도 리소스 검증을 마치는 순서예요

준비 과정에서 파라미터 반영과 검증 문제가 생겼지만 모두 ①~③ 단계의 작업이었어요. 해당 작업으로 운영 클러스터를 변경하지는 않았습니다.

2. 게이트 0: DB에 실제 적용된 파라미터 확인하기

1편에서 판단을 바꾼 근거는 필요한 파라미터가 이미 켜져 있다는 것이었어요. 하지만 그때 확인한 것은 파라미터그룹의 설정값이었고, 실제 DB에 적용된 값과 다를 수 있다는 지적을 받았습니다.

그래서 운영 DB에 직접 접속해 값을 조회했어요.

log_bin ON binlog_format ROW binlog_row_image FULL read_only OFF @@version 5.7.12-log ← 접미사 -log 가 바이너리 로깅 활성 증거

조회한 값으로 바이너리 로깅 활성 상태를 확인했어요. 이와 함께 다음 네 가지도 확인했습니다.

스키마 기본 문자셋이 이미 목표값 → 변환 작업 항목 삭제 앱·배치 이미지 다이제스트 기록 → 롤백 때 정확히 같은 이미지로 복귀 접속 URL 이 환경변수에 없다 → 이미지에 하드코딩됐다는 사실 확인 앱 서버 역할에 DB 권한 없음 → 권한이 좁다는 좋은 신호
그림 2. 설정 조회를 앞에 두고 파라미터그룹 값과 실제 적용값을 대조했어요
💡 설정값을 확인한 뒤 적용 여부도 조회해요
정적 파라미터는 재부팅 전까지 적용되지 않을 수 있어요. 파라미터그룹에 원하는 값이 있어도 DB에서 그 값을 쓰고 있는지는 따로 확인해야 합니다.

이 단계는 설정을 바꾸지 않고 조회만 하므로 전환 준비의 맨 앞에 뒀어요.

3. 복원에 쓸 수동 스냅샷 만들기

1편에서 확인했듯 백업 보존기간을 늘려도 이전 시점의 백업이 새로 생기지는 않아요. 복원에 쓸 수동 스냅샷은 0개였기 때문에 먼저 만들었습니다.

스냅샷에는 태그를 붙이지 않았어요. 당시 계정에는 환경 태그에 따라 접근을 제한하는 정책이 있었고, 태그를 비워두면 나중에 개발 환경으로 복원해 조사할 때도 사용할 수 있었습니다.

4. 미부착 파라미터그룹 검증에 걸린 시간

8.0용 파라미터그룹은 새로 만들어야 했어요. 아직 아무 DB에도 붙이지 않았기 때문에 생성이나 설정 적용이 실패해도 운영 DB에는 영향이 없었습니다.

아래 기록에는 세 차례 시도가 있고, 마지막은 성공으로 적혀 있어요.

1차 파라미터 8개 중 7개만 반영 2차 존재하지 않는 파라미터를 지우려 해서 실패 3차 성공

첫 두 시도에서 드러난 문제는 조사 과정에서 빠뜨린 확인 때문이었어요. 원자료에는 세 번 실패했다는 설명도 있지만 개별 실행 로그를 확보하지 못해, 이 표만으로 총 실패 횟수를 확정하지는 않았어요. 파라미터 목록을 뽑을 때 수정 가능 여부를 보지 않았고, 페이지네이션을 끈 상태에서 앞쪽 100개만 조회했는데도 나머지 목록을 확인하지 않았습니다.

⚠️ 파라미터 유효성을 CI 실행 전에 확인했어야 했어요
코드를 올리고 CI 파이프라인을 실행한 뒤에야 파라미터 유효성을 확인했어요. 한 번에 25~40분이 걸리는 과정을 세 번 반복했습니다.

이후 임시 파라미터그룹을 만들어 같은 값을 검증했을 때는 30초가 걸렸어요. 이 검증을 먼저 했다면 파라미터 오류를 확인하려고 CI가 끝날 때까지 기다릴 필요는 없었습니다.
그림 3. CI 실행마다 기다리던 파라미터 검증을 임시 리소스에서 먼저 할 수 있었어요

이 준비 작업에서 겪은 파라미터 오류가 운영 서비스에 영향을 주지는 않았어요. DB에 연결하기 전인 리소스에서 검증했기 때문입니다.

5. 알람과 앱 쪽 준비

DB 리소스와 함께 알람과 앱 설정도 준비했어요.

8.0 클러스터용 알람 3종 추가 로그 수신함 정리 — 안 쓰는 리소스를 미리 치워 전환 후 혼선을 줄인다 앱: 대용량 전송 청크 임계 조정 + DB 접속 설정을 환경변수로 분리

앱의 DB 접속 URL은 이미지 안에 하드코딩돼 있었어요. 롤백하면서 URL을 바꾸려면 이미지를 다시 빌드해야 했습니다. 환경변수로 분리하면 compose 파일의 설정을 바꿔 URL을 되돌릴 수 있어요.

이 변경을 저장소의 compose 파일에만 넣고, 실제 운영 호스트가 사용하는 파일에는 반영하지 않았어요.

저장소 infrastructure/compose 파일 ← 여기에 넣었다 호스트 운영 서버의 compose 파일 ← 여기가 실제로 도는 것. 빼먹었다

나중에 빠진 설정을 발견해 운영 호스트 파일에도 반영했어요. 이 확인을 놓쳤다면 URL을 되돌릴 수단이 운영 서버에 없는 상태로 전환했을 겁니다. 저장소의 변경과 실제 호스트 파일의 반영 여부를 각각 확인해야 했어요.

6. 전환 후에도 감시와 드리프트 검사를 유지하기

마지막으로 체크리스트에 전환 후에도 유지할 검사와 추가하지 않을 예외 설정을 적었어요.

전환 후 옛 클러스터는 -old가 붙은 이름으로 남아요. 감시 누락을 검사하는 커버리지 가드가 이를 "감시 밖 리소스"로 탐지할 예정이었지만, 이름 패턴에 따른 예외는 추가하지 않기로 했습니다.

⚠️ 롤백에 쓸 클러스터도 감시 대상이에요
전환 후 -old는 운영 태그를 유지한 5.7 클러스터예요. 별도 복구 절차를 거쳐 다시 운영에 사용할 가능성을 검토하는 대상이에요. 성공한 전환 뒤에는 읽기 전용이므로, 클러스터가 남아 있다는 사실만으로 즉시 복귀할 수는 없어요.

-old를 검사에서 제외하면 롤백 후 운영 DB의 감시 누락도 탐지하지 못해요. 예외를 추가하는 대신 이전 클러스터의 보존 기간을 짧게 잡고, 탐지된 이슈는 삭제 시점을 확인하는 데 쓰기로 했습니다.

코드와 실제 리소스의 차이인 드리프트를 무시하는 옵션도 넣지 않기로 했어요. 콘솔로 전환하면 한동안 코드에는 이전 버전이 남습니다. 이 불일치를 무시하도록 설정하면 스택 전체가 계속 검사 대상에서 빠질 수 있어요. 저장소에는 과거에 넣은 예외 설정이 남아 있었기 때문에 같은 방식을 추가하지 않기로 했습니다.

대신 전환 후 실제로 달라진 부분을 코드에 반영하고, 검사에서 남은 차이가 0인지 확인하기로 했어요.

7. 53분 걸린 green 생성과 가용영역 확인

준비를 마친 뒤 green 복제본을 만들었어요.

소스 읽기 복제본 생성 → 엔진 버전 업그레이드 → 인스턴스 생성 53분 후 사용 가능 그동안 운영 클러스터는 계속 서비스했다. 영향 0

생성 후에는 사전 검토에서 확인이 필요하다고 본 가용영역을 조회했어요. green 인스턴스가 코드에 적힌 가용영역에 생성됐는지 확인했습니다.

다른 가용영역에 생성되면 전환 후 코드와 실제 리소스가 달라져요. 해당 리소스에는 삭제 방지가 걸려 있어서 차이를 해소하는 작업이 실패하면 스택 전체의 변경이 막힐 수 있었습니다.

조회 결과는 코드와 일치했어요. 사전 검토의 세 관점에서 모두 우려했던 가용영역 불일치는 발생하지 않았습니다.

가용영역은 쓰기 인스턴스와 읽기 인스턴스, 두 개를 확인해야 했어요. 1편에서는 읽기 인스턴스의 일정한 부하를 검증 쿼리로 해석했어요. 실제 사용자 조회가 없다는 점까지 확정한 것은 아니었어요. 미리 삭제했다면 이번에 가용영역을 확인할 대상도 절반이었을 거예요.

💡 조회 중 확인한 다른 8.0 클러스터
조회 필터에 다른 팀이 운영하는 8.0 클러스터도 포함됐어요. 같은 계정에 8.0 운영 사례가 있었지만 이번 준비 전에는 알지 못했습니다.

그 클러스터의 버전은 장기 지원 계열이 아니었어요. 이 차이를 확인한 뒤 이번 업그레이드에는 장기 지원 계열을 선택했습니다.
✍️ 준비 결과와 놓친 확인
실제 파라미터 조회, 스냅샷, 미부착 리소스 검증을 거쳐 green을 생성했어요. 준비 중 파라미터 반영 문제는 운영 DB 변경 없이 처리했고, 53분 뒤 사용 가능해진 green의 가용영역이 코드와 일치하는지 확인했습니다.

파라미터 유효성은 한 번에 25~40분이 걸리는 CI를 세 번 실행한 뒤에야 별도로 검증했어요. 임시 리소스에서는 30초가 걸렸습니다. 앱 접속 설정도 저장소에만 반영했다가 운영 호스트 파일의 누락을 발견해 채웠어요. 전환 후에는 감시 예외를 추가하지 않고 실제 변경을 코드에 반영하기로 했습니다.
