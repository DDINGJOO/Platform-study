📚 Aurora 5.7 → 8.0, 5부작
1편. 파라미터 설정을 확인한 뒤 Blue/Green으로 바꾼 이유 ← 지금 이 글

운영 DB를 Aurora MySQL 5.7 호환 버전에서 8.0으로 옮겼어요. 표준 지원이 끝난 버전에 붙는 확장 지원 요금을 없애기 위한 메이저 업그레이드였어요.

확장 지원 단가가 오르기 전에 전환해야 했기 때문에, 방식 비교에서도 기한 안에 전환할 수 있는지와 되돌릴 방법을 먼저 살폈어요. 처음에는 in-place를 골랐지만 실제 파라미터 설정을 확인한 뒤 Blue/Green으로 바꿨고, 실행 전 검토에서도 백업과 감시 조건을 다시 확인했어요.

1. 지원이 끝나면 요금이 붙는다

당시 Aurora MySQL 2(5.7 호환)는 표준 지원이 끝나 확장 지원 요금이 붙고 있었어요. 기존 버전을 계속 사용할 수는 있지만, 인스턴스 컴퓨트 요금에 확장 지원 요금이 추가되는 구조예요.

단가는 가격 API로 조회했어요.

확장 지원 1~2년차 단가 지수 1 / vCPU-hour 확장 지원 3년차부터 단가 지수 2 / vCPU-hour 인스턴스 컴퓨트 요금 월 비용 비교 기준 100

확장 지원은 vCPU-시간 단위로 과금하므로 인스턴스 대수와 코어 수에 비례해요. 이 클러스터는 쓰기·읽기 인스턴스 두 대여서 다음과 같이 계산했어요.

1대 2 vCPU × 해당 연차의 단가 × 730h = 월 확장 지원료 2대 같은 구성 1대의 월 확장 지원료 × 2 연간 2대의 월 확장 지원료 × 12
⚠️ 읽기 인스턴스 제거를 미룬 이유
같은 클러스터의 읽기 인스턴스는 앞서 제거 가능성을 검토했어요. 당시 확인한 결과는 "쓰기가 92일간 정확히 0이고, 일정한 읽기 부하는 커넥션 풀 검증 쿼리로 보인다"는 판단이었어요. 다만 실제 SQL과 풀 설정을 대조해 사용자 조회가 없다고 확정한 것은 아니에요. 배치 최적화를 먼저 하고 효과를 확인한 뒤 제거 여부를 판단하기로 했어요.

업그레이드를 준비할 때도 이 인스턴스는 남아 있었어요. 먼저 제거했다면 확장 지원료는 절반이 되고, 가용영역 확인 대상도 하나로 줄었을 거예요. 다만 배치 최적화라는 선행조건이 남아 있었고 업그레이드 마감도 정해져 있어, 이번에는 인스턴스를 유지한 상태로 진행했어요.

인스턴스 한 대의 월 비용에서 컴퓨트와 확장 지원을 비교하면 다음과 같아요.

컴퓨트 월 비용을 100으로 둔 비교 전환 전 컴퓨트 100 + 확장지원 약 200 ≈ 300 전환 후 컴퓨트 100 확장 지원료가 컴퓨트의 약 2배

확장 지원 요금이 컴퓨트 요금의 약 2배였고, 3년차에는 확장 지원 단가가 다시 2배로 올라요.

그림 1. 인스턴스 1대의 월 비용 비교. 3년차에는 확장 지원 단가가 2배로 올라요
💡 방식 비교에서 먼저 본 조건
업그레이드를 미루는 동안에는 매달 확장 지원 요금이 붙고, 3년차에는 단가도 올라요. 그래서 전환 중 중단 시간을 줄이는 것과 함께, 기한 안에 실행할 수 있는지와 실패할 때 되돌릴 수 있는지를 먼저 비교했어요.

2. 세 가지 방식

메이저 버전을 올리는 방법은 세 가지를 비교했어요. in-place는 기존 클러스터를 직접 업그레이드하는 방식이고, Blue/Green은 업그레이드한 복제본을 준비한 뒤 전환하는 방식이에요.

A. in-place 클러스터를 그 자리에서 업그레이드 B. Blue/Green 8.0 복제본을 만들어두고 이름을 맞바꾼다 C. 신규 클러스터 새로 만들고 앱을 옮긴다

중단 시간, 식별자와 알람 유지, 코드에서의 실행 가능 여부, 롤백 방법을 함께 비교했어요.

그림 2. 중단 시간과 함께 식별자·코드·롤백 조건을 비교했어요

신규 클러스터를 만드는 C는 먼저 제외했어요. 알람 이름을 인스턴스 식별자로 조립하는 구조라 클러스터를 새로 만들면 알람 10개가 삭제·재생성되고 이력도 사라지는 조건이었어요. 또 기존 클러스터를 지우려면 삭제 방지를 해제해야 했고, 코드 주석에서도 그 과정의 위험을 경고하고 있었어요.

이후에는 in-place와 Blue/Green을 비교했어요.

3. 첫 검토에서는 in-place를 골랐어요

플랫폼, SRE(서비스 신뢰성 운영), 배포 파이프라인의 세 관점으로 나눠 각각 검토했어요.

플랫폼 in-place. B 는 공유 파라미터그룹을 건드려야 한다. 다른 팀 DB 의 변경이 PR 도 plan 도 없이 나간다 SRE in-place. B 의 그 파라미터는 정적이라 즉시 효과가 없다. 다른 팀 DB 가 언젠가 재부팅되는 날 켜진다 — 시한폭탄 파이프라인 Blue/Green. in-place 는 이 파이프라인에서 실행 자체가 어렵다 (즉시 적용 옵션 부재 · 유지보수 창 어긋남 · 의존 간선 없음)

처음에는 in-place를 선택했어요. 파이프라인에서 제기한 문제는 코드를 통해 실행할 때의 제약이라 콘솔에서 실행하면 피할 수 있었어요. 반면 Blue/Green에 필요한 공유 파라미터 그룹 변경은 다른 팀의 DB에도 영향을 준다고 봤어요. 다른 팀에 변경을 요구하지 않는다는 조건에 맞지 않는다고 판단한 거예요.

콘솔 실행에도 주의할 점은 있었어요. 실제 DB를 업그레이드한 뒤 코드를 갱신하기 전까지는 코드에 더 낮은 버전이 남아요. 이때 드리프트 감지, 즉 코드와 실제 설정의 차이를 찾는 검사는 코드에 맞추라고 안내할 수 있어요. 코드에 남은 5.7을 다시 적용하려는 요청이 생길 수 있다는 지적도 반영했어요. Aurora가 이 메이저 버전 하향을 허용한다는 뜻은 아니며, 잘못된 변경 요청과 적용 실패를 막기 위해 코드를 실제 버전에 맞춰야 했어요.

4. 실제 파라미터를 확인한 뒤 Blue/Green으로 변경

공유 파라미터 그룹에서 확인한 것은 Blue/Green 복제에 필요한 바이너리 로그 설정이었어요. 해당 설정은 이미 들어 있어서 새로 바꿀 필요가 없다고 판단했어요. 그룹의 설정값과 DB에 실제 적용된 값은 다를 수 있어, 적용값은 2편에서 따로 조회했어요.

다른 팀 DB에 변경을 요구하게 된다는 판단은 이 설정을 확인하지 않은 채 내린 것이었어요.

플랫폼과 SRE 관점의 검토에서 같은 지적이 나와 신뢰할 만하다고 생각했어요. 하지만 두 검토 모두 같은 코드를 보고 있었고, 실제 설정은 확인하지 않았어요.

⚠️ 같은 코드를 검토하면서 놓친 설정
두 검토가 같은 결론을 냈어도 코드에 드러나지 않은 실제 설정까지 확인한 것은 아니었어요. 이번 결정에는 코드 검토와 별도로 실제 파라미터 그룹을 조회한 결과가 필요했어요.

설정을 확인한 뒤 Blue/Green으로 바꿨어요. 다른 팀의 리소스를 수정하지 않고 진행할 수 있었고, 전환 후 기존 DB를 복구 검토 대상으로 남길 수 있다는 점을 더 중요하게 봤어요. 다만 기존 DB에는 전환 이후 변경분이 복제되지 않아요. 성공한 전환 뒤 기존 blue는 Blue/Green 배포 리소스를 삭제할 때까지 강제로 읽기 전용이며, 복귀하려면 읽기 전용 해제 조건과 앱 접속 경로, 이후 데이터의 처리 방법을 별도로 확인해야 해요. 전환 도중 실패했을 때 서비스가 수행하는 자동 롤백과는 다른 절차예요.

데이터가 작아 in-place 다운타임도 짧다 → 무중단의 값어치는 크지 않다 그래도 B 가 나은 이유는 → 롤백 대상이 살아 있다는 것 그리고 그 파라미터가 이미 켜져 있으니 → 다른 팀 리소스를 하나도 안 건드린다 전환 시 이름·엔드포인트 승계 → 앱 변경 불필요

데이터가 작아 in-place의 중단 시간도 짧을 것으로 봤기 때문에, 중단 시간 차이가 최종 선택을 가르지는 않았어요. 이 비교에서는 기존 DB를 남겨 복구를 검토할 수 있다는 점이 Blue/Green을 선택한 이유였어요. 위 인용의 롤백 대상은 즉시 무손실 복귀를 뜻하지 않아요.

5. 실행 전에 다시 확인한 백업과 드라이버

방식을 바꾼 뒤에는 당일 밤 실행할 수 있는지 다시 검토했어요. 이 과정에서 제가 세운 전제 여섯 개를 정정했고, 그중 백업과 드라이버에 관한 두 항목은 다음과 같아요.

먼저 롤백에 대비해 백업 보존기간을 늘리는 PR을 머지하려 했어요. 하지만 보존기간을 늘려도 과거 시점 복구 데이터가 소급해서 생기지는 않아요. 오후 3시에 보존기간을 늘린다고 밤 10시에 이전보다 더 과거로 복구할 수 있는 것은 아니었어요.

내가 믿은 것 보존기간을 늘리면 롤백 자산이 생긴다 실제 과거는 소급되지 않는다. 늘어나는 건 앞으로뿐 실제 롤백 자산 수동 스냅샷 그 개수 0개

보존기간 상향만으로 당일 롤백 준비가 되는 것은 아니었어요. 별도로 확보해야 할 수동 스냅샷은 당시 0개였어요.

드라이버 검증에도 빠진 조건이 있었어요. dev에서 8.0 접속을 확인했지만, dev 접속 URL은 일반 모드였고 운영은 장애 시 다른 인스턴스로 전환하는 페일오버를 지원하는 Aurora 모드였어요. 드라이버 내부에서 실행하는 코드 경로가 달라 운영과 같은 모드로 검증한 상태는 아니었어요.

6. 롤백 대상은 감시에서 제외하지 않기

세 관점의 결론을 서로 대조해 하나의 실행 일정으로 정리했어요. 그 과정에서 기존 판단 셋을 수정했고, 그중 하나가 전환 후 기존 클러스터의 감시 여부였어요.

전환 후에는 기존 클러스터가 -old가 붙은 이름으로 남아요. 감시 대상에서 빠진 리소스를 찾는 검사가 이 클러스터를 잡으면 불필요한 알림이 생긴다고 생각해, 해당 이름 패턴을 예외 처리하려 했어요.

다시 검토하면서 이 예외 처리는 하지 않기로 했어요.

⚠️ 롤백하면 다시 운영 DB가 되는 클러스터
전환 후 -old는 운영 태그를 유지한 채 실행되는 5.7 클러스터예요. 별도 복구 절차를 거쳐 다시 운영에 사용할 가능성을 검토하는 대상이므로, 이름만으로 검사에서 제외하면 복구 시 감시가 빠질 수 있어요.

-old를 검사에서 제외하는 대신 기존 클러스터를 유지하는 기간을 짧게 하고, 탐지된 항목은 삭제 시점을 다시 확인하는 용도로 쓰기로 했어요.

처음에는 불필요한 알림으로 봤지만, 롤백에 쓸 수 있는 클러스터가 감시에서 빠졌음을 알리는 유효한 탐지였어요.

✍️ 정리
확장 지원 요금과 3년차 단가 인상을 고려해 업그레이드 기한을 정했어요. 처음에는 공유 파라미터 그룹 변경이 필요하다고 보고 in-place를 골랐지만, 실제 값이 이미 설정돼 있음을 확인한 뒤 Blue/Green으로 바꿨어요.

실행 전 검토에서는 백업 보존기간 상향이 수동 스냅샷을 대신하지 못한다는 점과 운영 드라이버 모드가 아직 검증되지 않았다는 점을 확인했어요. 롤백 대상으로 남기는 기존 클러스터는 감시 검사에서도 제외하지 않기로 했어요.
