📚 Aurora 5.7 → 8.0, 5부작
2편. 전환 전에 파라미터와 green 복제본을 확인한 순서
3편. 전환 완료를 기다리기 전에 앱을 기동한 이유
4편. 단일 호스트 JDBC URL을 먼저 배포하고 DB를 전환한 이유 ← 지금 이 글

앞선 작업 하루 뒤에 다른 Aurora 클러스터도 업그레이드했어요. 이번에는 앱을 멈추지 않고 전환했습니다.

DB 쓰기는 약 5초 동안 중단됐고, 앱을 정지한 횟수는 0회였어요. 1초 간격으로 HTTP 응답을 확인한 폴러의 1,195개 샘플에서는 200이 아닌 응답이 0건이었습니다.

설계 문서에는 앱 정지가 필수 단계로 적혀 있었어요. 읽기 전용 DB로 재연결될 수 있는 접속 설정 때문이었습니다. 그 설정을 먼저 바꾸고 배포한 뒤 전환했고, 롤백 스크립트가 이전 설정을 다시 적용할 수 있다는 문제도 확인했어요.

1. 공유 파라미터그룹을 쓰는 클러스터가 하나 남았다

1편에서는 Blue/Green을 한 번 기각했던 이유를 다뤘어요. 가장 큰 근거는 공유 파라미터그룹을 변경하면 다른 팀 DB도 영향을 받는다는 것이었는데, 당시 확인한 내용과는 달랐습니다.

이번 작업에서는 공유 여부를 따질 조건도 달라졌어요. 3편에서 앞선 클러스터를 8.0으로 옮긴 뒤, 그 파라미터그룹을 쓰는 클러스터는 하나만 남았습니다. 따라서 이번에는 다른 클러스터와의 공유를 고려하지 않고 설정을 바꿀 수 있었어요.

업그레이드 전까지는 확장 지원료가 계속 발생하고 있었어요.

4대 × 2 vCPU × 해당 연차 단가 × 730h = 월 확장 지원료 현재 월 지원료를 1로 두면 2027-03-01부터 단가 2배 = 월 지원료도 2배

위 블록의 날짜는 당시 계획에 적힌 값이에요. Aurora 공식 지원 일정에서 Aurora MySQL 2의 확장 지원 3년차 시작은 2026-12-01이므로, 원자료에서 가져온 2027-03-01은 잘못된 일정으로 정정해요. 비용 비교의 배수와 지원 연차의 실제 시작일은 나눠 확인해야 했어요.

이 클러스터를 전환하면 5.7에 남는 클러스터는 하나예요. 남은 클러스터에는 아직 전용 파라미터그룹이 없어서, 그 설정을 준비하는 단계가 추가로 필요했습니다.

2. 접속 URL 때문에 앱 정지를 계획했다

설계 문서에 적힌 순서는 다음과 같았어요.

... 4. Blue/Green 생성 → 검증 5. 알람 3종 추가 6. 앱 정지 → 스위치오버 → 기동 ← 필수라고 적어둔 단계 7. 관측 후 옛 클러스터 삭제

앱 정지를 필수로 잡은 이유는 운영 JDBC 접속 URL에 호스트가 두 개 들어 있었기 때문이에요. 두 번째 호스트는 쓰기를 할 수 없는 읽기 전용 엔드포인트였습니다.

jdbc:mysql://<클러스터>.cluster-... ← 쓰기 <클러스터>.cluster-ro-... ← 읽기 전용 /<DB>?autoReconnect=true

당시 설정에서 우려한 것은 스위치오버로 첫 호스트의 연결이 끊긴 뒤 드라이버가 두 번째 호스트로 재연결되는 경우였어요. autoReconnect=true인 상태에서 읽기 전용 호스트와의 연결이 유지되면 쓰기가 실패하고, 앱을 재기동해야 하는 상황을 예상했습니다.

앞선 클러스터는 URL에 호스트가 하나만 있어서, 이번 설정과 같은 재연결 경로는 없었어요.

그림 1. 두 번째 호스트가 읽기 전용이면 재연결 후 쓰기가 실패할 수 있어요

3. 단일 호스트 설정을 먼저 배포했다

앱을 정지하려던 이유가 접속 설정에 있다면, 전환 전에 그 설정부터 바꿀 수 있었어요. 읽기 전용 엔드포인트를 URL에서 빼기로 했습니다.

호스트의 compose 설정에 데이터소스 URL 환경변수를 추가했어요. 이미지 안의 설정 파일 대신 이 환경변수에 적은 URL을 사용하도록 했습니다.

SPRING_DATASOURCE_URL=jdbc:mysql://<단일 호스트>/<DB>?... ↑ 읽기 전용 엔드포인트를 목록에서 뺐다

그다음 같은 이미지로 무중단 배포를 한 번 실행해, 실행 중인 앱에 단일 호스트 URL을 적용했어요. 앱 코드는 바꾸지 않고 읽기 전용 호스트로 재연결되는 경로를 없앴습니다.

이 배포를 마친 뒤 DB를 전환했어요.

1. 앱 배포 (단일 호스트 URL) → 무중단. DB 는 아직 5.7 2. 스위치오버 → 커넥션이 끊기고 writer 로 재연결

접속 설정을 바꾼 앱을 먼저 배포해야 했어요. 전환부터 하면 기존의 두 호스트 설정을 쓰는 앱이 연결 단절을 겪게 됩니다.

그림 2. 접속 설정을 먼저 배포한 뒤 앱 정지 없이 전환했어요

수정한 곳은 호스트의 compose 설정 한 곳이었어요. 저장소의 코드와 이미지는 바꾸지 않았습니다.

💡 전환 뒤에도 단일 호스트 설정을 유지했어요
단일 호스트 URL을 임시로 적용했다가 되돌릴 수도 있었지만, 이후에도 기본값으로 유지했어요.

읽기 전용 호스트로의 재연결은 스위치오버 외에도 writer 페일오버나 순간적인 연결 단절 때 문제가 될 수 있다고 봤습니다. DB 역할이 바뀌는 페일오버 때도 같은 설정을 쓰기 때문이에요.

전환 작업을 계기로 접속 설정을 확인했고, 작업이 끝난 뒤에도 변경한 설정을 사용했습니다.

4. 생성 시간과 전환 전 검증

Blue/Green 생성 시간은 예상과 달랐어요.

앞선 클러스터 1.30 GiB → Blue/Green 생성 53분 이번 클러스터 48.25 GiB → Blue/Green 생성 32분

데이터는 37배 많았지만 생성 시간은 더 짧았어요. 이 두 작업에서는 데이터 크기와 생성 시간이 비례하지 않았습니다. 다만 이 비교만으로 생성 시간의 주된 원인을 확정할 수는 없어요. 생성하는 32분 동안에는 기존 클러스터가 계속 서비스했습니다.

실제 쓰기 중단은 스위치오버 때 발생했고, 약 5초였어요.

전환 전 검증은 스키마 비교와 운영 이미지 기동으로 나눴어요.

스키마 비교 (기존 vs 새 클러스터) 테이블 수 104 = 104 테이블 콜레이션 general_ci 101 / unicode_ci 3 양쪽 동일 컬럼 콜레이션 general_ci 541 / unicode_ci 8 양쪽 동일 VIEW · 함수 · 트리거 · 이벤트 전부 0 = 0 달라진 값 sql_mode 에서 8.0 이 없앤 항목 하나가 빠짐

스키마 비교에서는 개발 환경의 Docker 실험과 다른 결과가 나왔어요. 실험할 때는 콜레이션, 즉 문자열을 비교하는 규칙이 8.0 기본값으로 바뀌어 기존 컬럼과 비교할 때 오류가 났습니다. 이번 Blue/Green에서는 그 문제가 재현되지 않았어요.

💡 기존 테이블과 새 테이블의 콜레이션을 구분했어요
이번 비교에서는 Blue/Green으로 옮긴 기존 테이블의 콜레이션이 유지된 것을 확인했어요.

전환 후 새로 만드는 테이블의 콜레이션은 별도로 관리해야 했습니다. 기존 테이블을 옮기는 절차와 앞으로 사용할 DDL, 즉 테이블 생성·변경 구문의 규칙을 나눠 정할 필요가 있었어요.

개발 환경에서 본 오류가 이번 이관에서도 발생한다고 가정하지 않고, 실제 스키마 비교 결과에 따라 점검 범위를 구분했습니다.

운영 이미지도 그대로 새 클러스터에 연결해 기동했어요. nginx에 연결하지 않은 로컬 포트를 사용해서 운영 요청이 들어오지 않도록 했습니다.

스키마 검증 오류 0 기동 실패 0 기동 시간 기존 32.596초 → 새 클러스터 32.36초 (회귀 없음) 드라이버 의도한 드라이버가 잡힌 것을 로그로 확인

이때 새 클러스터는 아직 읽기 전용이었어요. 스케줄 작업을 실행하려면 DB에서 분산 락을 잡아야 했는데, 그 쓰기를 할 수 없어 작업이 실행되지 않았습니다. 다만 이는 이번 기동에서 확인한 조건이므로, 다른 작업에서도 같은 격리가 된다고 보장할 수는 없어요.

5. 롤백하면 이전 접속 설정이 복구됐다

접속 설정을 바꾼 뒤에는 롤백했을 때도 그 설정을 유지하는지 확인했어요.

롤백 스크립트는 컨테이너를 새로 만드는 대신 멈춰 둔 컨테이너를 다시 시작하고 있었습니다.

기존 컨테이너를 다시 시작하면 생성 당시의 환경변수를 그대로 사용해요. 대기 컨테이너는 이틀 전에 기동한 것이어서, 오늘 추가한 단일 호스트 URL 환경변수가 없었습니다.

롤백을 누르면 → 이틀 전 컨테이너가 그대로 다시 시작 → 환경변수 없음 → 호스트 두 개짜리 URL 로 복귀 ← 방금 없앤 함정 → 그런데 DB 는 이미 8.0 으로 넘어간 상태

전환 후 롤백 스크립트를 실행하면 두 호스트를 쓰던 접속 설정으로 돌아가게 되어 있었어요.

대기 컨테이너와 활성 컨테이너는 같은 이미지를 사용하고 있었어요. 대기 컨테이너로 되돌려도 앱 버전은 같고 접속 설정만 이전 상태가 되므로 삭제했습니다. 이후에는 롤백 스크립트가 대상을 찾지 못해 실패하고, 되돌릴 때는 새로 배포해야 해요. 새로 배포하면 단일 호스트 기본값을 사용합니다.

⚠️ 롤백이 적용하는 설정도 확인했어요
앞서 다룬 3부작에서도 롤백 스크립트 문제가 있었어요. 조회 실패를 대상 없음으로 잘못 해석해서 아무것도 하지 않고 성공한 것처럼 끝났습니다.

이번에는 스크립트가 다시 시작하는 컨테이너에 어떤 환경변수가 들어 있는지 확인했어요. 앱 이미지가 같아도 컨테이너를 만든 시점에 따라 접속 설정은 다를 수 있었습니다.

이전 설정으로 복구하는 대신 대상이 없어 실패하도록 바꾸고, 필요한 경우 새 설정으로 배포하는 방식을 택했어요.

대기 컨테이너를 삭제하면서 메모리 3.7GB도 회수됐어요. 호스트 여유 메모리는 9.6GB에서 13.5GB로 늘었습니다.

이 호스트에서는 사흘 전에도 대기 컨테이너와 활성 컨테이너의 JVM 힙이 메모리를 채우면서 49분 동안 전면 중단이 발생했어요. 이번 삭제 후에는 대기 컨테이너가 없어 두 컨테이너의 힙이 함께 메모리를 차지하던 조건이 해소됐습니다. 메모리 회수는 업그레이드 과정에서 함께 얻은 결과였어요.

6. 교체 직후의 CPU 크레딧 알람을 조정했다

전환 전 점검에서는 앞선 클러스터의 CPU 크레딧 알람 두 개가 울리고 있었어요. CPU 크레딧은 인스턴스가 기준 사용률을 넘는 동안 사용하는 잔량이에요. 3편에서는 전환 직후 이 알람이 상태를 정확히 구분하지 못했다고 적었습니다.

크레딧 추이를 보니 잔량은 줄지 않고 늘고 있었어요.

12시간 전 현재 방향 writer 117 189 오르는 중 (시간당 +6) reader 160 255 오르는 중 (시간당 +8) 알람 임계값 < 400 400 도달까지 writer 약 35시간

크레딧이 줄어든 것이 아니라 아직 임계값까지 쌓이지 않아 울린 알람이었어요. 당시 Blue/Green으로 만든 인스턴스는 크레딧 0에서 시작한 것으로 확인했습니다. 임계값이 400이면 그만큼 채워지는 동안 계속 알람 상태가 됩니다.

잔량이 증가하는 추이를 보면 이 시점의 알람을 용량 부족으로 해석하기는 어려웠어요. 교체할 때마다 며칠씩 같은 알람이 울리면 실제 크레딧 소진과 구분하기도 어려워집니다.

그림 3. 교체 직후 크레딧이 쌓이는 동안에도 잔량 알람이 울렸어요

이번 클러스터는 실측값을 기준으로 알람을 나눠 설정했어요.

CPU 사용률 > 30% 기준선 그 자체. 넘으면 크레딧이 빠지기 시작하니 선행 지표이고, 교체 직후에 울릴 이유가 없다. 실측 최대 23.3% 대비 여유 1.3배 크레딧 잔량 < 100 쓰로틀링 임박을 알리는 후행 지표. 0 에서 100 까지는 약 3시간이라 교체 후 오탐 구간이 짧다 여유 메모리 < 800MB 실측 최소 2,420MB 의 약 1/3

CPU 사용률은 크레딧 소모 조건을 먼저 보고, 잔량은 감소 추세를 확인하도록 나눴어요. 다만 위 표의 “쓰로틀링 임박”이라는 설명은 정정해야 해요. 이 Aurora T4g 사양은 Unlimited 모드이므로 적립 크레딧 잔량이 0이 된다는 이유만으로 Standard 모드처럼 CPU를 자동 제한한다고 볼 수는 없어요. 초과 크레딧과 추가 비용을 함께 봐야 하며, 이번 관측에서 추가 요금이 발생했다고 확인한 것은 아니에요.

“0에서 100까지 약 3시간”도 무부하에 가까운 적립 가정이에요. 해당 t4g.large의 시간당 적립량 36개로 계산하면 약 2.8시간이지만, 앞서 관측한 writer의 순증가량은 시간당 6개였어요. 그 증가율이 유지된다면 약 16.7시간이므로, 실제 알람 기간을 3시간으로 정할 수는 없어요.

전환 후 측정값은 다음과 같았어요.

writer CPU 평균 5.7 구간 17.0% → 8.0 구간 18.5% (+1.5%p) writer CPU 최대 23.3% → 20.7% (증가 없음) 여유 메모리 최소 2,420MB → 2,430MB (동일)

측정한 CPU 사용률은 기준선 30%보다 낮았고, 크레딧은 쌓이는 방향이었어요. 이 구간에서는 8.0 전환 후 CPU나 메모리 사용이 뚜렷하게 증가하지 않았습니다. 인스턴스 등급을 올려야 할 징후도 이번 측정에서는 보이지 않았어요.

⚠️ 측정은 트래픽이 낮은 시간대에 했어요
전환 시점의 트래픽은 초당 0.1건 수준이었어요.

따라서 위 결과는 부하가 낮을 때의 8.0 동작을 확인한 것입니다. 업무시간의 부하에서도 같은지는 추가로 관측해야 했어요.

이번 결과로 업무시간의 성능까지 확인했다고 판단하지는 않았습니다.
✍️ 전환 결과와 남은 확인
두 번째 클러스터는 단일 호스트 URL을 먼저 배포한 뒤 앱 정지 없이 전환했어요. DB 쓰기 중단은 약 5초였고, 폴러 1,195개 샘플에서 200이 아닌 응답은 0건이었습니다.

기존 테이블의 콜레이션이 유지됐고 운영 이미지도 기동했습니다. 롤백 스크립트는 이전 접속 설정을 가진 컨테이너를 다시 시작하므로, 해당 대기 컨테이너를 삭제하고 새로 배포하도록 정리했어요.

CPU와 메모리는 낮은 트래픽에서 측정했고, 크레딧 알람은 사용률과 잔량을 나눠 조정했어요. 업무시간의 부하에서 같은 결과가 나오는지는 추가 확인이 필요했습니다.
