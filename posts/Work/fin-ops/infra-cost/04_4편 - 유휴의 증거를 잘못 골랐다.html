4편. 유휴 자원 삭제 전에 트래픽과 참조 관계 확인하기 ← 지금 이 글

로드밸런서 목록을 요금 기준으로 정렬해 세어 봤어요. 38개 중 33개의 사용량 단위 요금이 0이었고, 청구액은 최소 요금과 같았습니다.

처음에는 33개 모두 삭제 후보로 보였지만, 실제로 지운 것은 4개였어요. 요금만으로는 사용 여부를 판단할 수 없어서 타깃과 요청, 연결 경로를 더 확인했습니다.

확인하는 과정에서 같은 0이라도 의미가 달랐어요. 조회 기간에 트래픽이 없었던 경우도 있었고, 지표 자체가 발행되지 않은 경우도 있었습니다.

1. 사용량 요금이 0이어도 연결 경로를 확인했어요

로드밸런서 요금에는 켜져 있는 시간에 붙는 요금과 처리량에 붙는 요금이 있어요. 처리량을 계산하는 단위가 LCU예요. 당시에는 이 사용량 요금이 0인 것을 보고, 시간 요금만 내는 자원이라고 분류했습니다.

여기서 LCU 요금이 0이라는 사실을 요청이 없다는 뜻으로 해석한 게 문제였어요. 요금이 낮다는 것만으로 사용하지 않는다고 판단할 수는 없었습니다.

그래서 삭제 여부를 판단할 때는 연결된 타깃과 요청을 함께 봤어요. 타깃은 로드밸런서가 요청을 전달할 대상이에요. 타깃 0과 요청 0으로 분류한 자원도 지표의 발행 방식과 연결 경로를 추가로 확인해야 했습니다.

로드밸런서 38개 사용량 단위 요금 0 33개 "청구액이 최소 요금과 같다" 타깃 0 · 요청 0 4개 -> 실제 삭제 33 - 4 = 29 는 "요청이 적은 것" 이었다
💡 타깃과 요청을 함께 확인한 이유
• 타깃은 없는데 요청이 있다면, 요청이 전달되지 않거나 배포 중인 상태인지 확인해야 해요.
• 타깃은 있는데 요청이 없다면, 조회 기간 밖에 사용이 있는지 확인해야 해요.
• 둘 다 없더라도, 현재 연결 경로와 향후 재배포 가능성까지 확인한 뒤 삭제를 판단했어요.

2. 30일간 없던 연결이 90일 조회에서 보였어요

한 네트워크 로드밸런서를 30일 범위로 조회했어요. 활성 연결을 나타내는 ActiveFlowCount, 새 연결을 나타내는 NewFlowCount, 처리 바이트를 나타내는 ProcessedBytes가 모두 정확히 0이었습니다. 이 결과만 보면 사용하지 않는 것 같았어요.

그런데 조회 범위를 90일로 늘리자 서로 다른 두 날에 연결이 각 1건씩 있었습니다.

조회 창 30일 ActiveFlowCount 0 NewFlowCount 0 ProcessedBytes 0 전부 정확하게 0 조회 창 90일 연결 1건 + 연결 1건 서로 다른 두 날

앞의 29개는 33개에서 삭제한 4개를 뺀 나머지 개수예요. 그 29개 모두가 요청이 적었다는 분류를 입증하는 개별 요청량 원본은 확인하지 못했어요.

30일간 0이었다는 결과는 그 기간에 사용이 없었다는 뜻이에요. 분기에 한 번 실행하는 배치나 대체 경로, 재해 때만 쓰는 경로라면 평소의 짧은 조회 기간에는 사용이 드러나지 않을 수 있어요.

이 자원 뒤에는 회사 주요 웹사이트를 서비스하는 다른 로드밸런서가 연결돼 있었고, 그 로드밸런서의 90일 요청은 1천만 건을 넘었어요. 앞단의 네트워크 로드밸런서는 고정 IP로 접속하는 경로였습니다. DNS 레코드 없이 IP로 직접 접속하는 구조였어요.

이 경우에는 삭제 후 복구도 고려해야 했어요. 지운 뒤 같은 IP를 다시 확보할 수 없었기 때문입니다. 몇 분 안에 같은 구성으로 다시 만들 수 있는 자원과는 삭제 기준을 다르게 잡아야 했어요.

그래서 되돌리기 어려운 자원은 조회 기간을 더 길게 잡았어요. 최근 사용 여부뿐 아니라 삭제 판단이 틀렸을 때 같은 경로를 복구할 수 있는지도 확인 기준에 포함했습니다.

조회 기간을 늘릴 때는 집계 간격과 통계도 함께 확인했어요. 90일 범위에서는 데이터가 시간 단위 이상으로 합쳐져 나왔습니다. 드문 연결을 평균으로 보면 값이 0에 가까워져 놓치기 쉬워요. 이번에 두 건을 찾은 것은 합계와 최댓값으로 봤기 때문입니다.

그림 1. 30일간 없던 연결이 90일 범위에서는 두 건 확인됐어요

3. 지표가 발행되지 않은 것과 값이 0인 것은 다르다

NAT 게이트웨이를 확인할 때는 값이 0인 경우와 데이터가 없는 경우를 나눠 봐야 했어요.

NAT 게이트웨이 두 개를 지우기 전에는 라우팅 테이블의 참조가 없는지 확인했어요. 라우팅은 트래픽이 어느 자원을 거쳐 나갈지 정하는 설정이에요. 빠뜨린 경로가 없는지 확인하려고 30일 트래픽도 함께 조회했습니다.

아래 바이트 지표 두 개는 조회 결과가 비어 있던 것이 아니라 30일 내내 값이 0으로 발행돼 있었어요. 반면 활성 연결 수에는 데이터가 없었습니다.

라우팅 테이블 참조 없음 BytesOutToDestination 30일 합계 0 · 일최대 0 <- 발행된 0 BytesInFromSource 30일 합계 0 · 일최대 0 <- 발행된 0 ActiveConnectionCount 데이터 없음 <- 증거로 쓸 수 없다 Transit Gateway 없음 우회 경로 배제

같은 표 안에서도 두 결과의 의미가 달라요. 데이터 포인트가 없다는 것만으로는 측정이 이뤄졌는지 알 수 없지만, 발행된 0은 해당 기간과 지표에서 측정한 값이 0이라는 뜻이에요.

앞 편에서도 조회 실패와 실제 0을 혼동한 적이 두 번 있었어요. 다만 이 구분을 적용할 때는 모든 지표가 값이 0일 때도 발행되는 것은 아니라는 점을 고려해야 했습니다.

이번 NAT의 바이트 지표는 트래픽이 없어도 0을 발행했어요. 반대로 요청이 있을 때만 데이터 포인트가 생기는 요청 수 지표에서는 요청이 없으면 0이 아니라 데이터 없음으로 보였습니다. 이런 경우에는 발행된 0을 삭제 조건으로 요구할 수 없어요.

그래서 요청 수 데이터가 없는 자원은 연결 경로를 더 확인했어요. 5절의 로드밸런서가 그 경우입니다. 타깃이나 요청 중 하나만 보고 판단하지 않고, 실제로 요청이 들어오고 전달될 수 있는 구성을 함께 봤어요.

그림 2. 발행된 0과 데이터 없음을 구분하고 참조 관계도 확인했어요

4. 알람 주석에 트래픽이 없는 원인을 적었어요

그 NAT를 삭제하기 전에 알람 코드도 읽어 봤어요. 아래 주석은 지표가 없는 상태와 활동이 생겼을 때의 동작을 설명하고 있었습니다.

# 이 NAT 는 아직 이 지표를 발행한 적이 없다. 포트 할당 활동이 생기면 # 자동으로 감시가 시작된다. 그 전까지 이 알람은 데이터를 받지 못한다.

지표가 없고 활동이 생기면 감시가 시작된다는 설명은 맞았어요. 다만 왜 활동이 없는지는 적혀 있지 않았습니다.

확인한 원인은 라우팅 참조가 없다는 것이었어요. NAT로 들어올 트래픽이 없으니 포트를 할당할 활동도 없었습니다. 단순히 사용량이 적은 상태로 읽기에는 빠진 전제가 있었어요.

주석만 보면 연결 경로는 있지만 아직 활동이 없는 상태로 이해할 수 있었어요. 다음에 읽는 사람이 같은 확인을 반복하지 않도록, 라우팅 참조가 없고 30일간 바이트 지표가 0이었다는 원인과 측정 결과를 함께 적었습니다.

# 이 NAT 는 라우팅 테이블 어디에서도 참조되지 않아 30일간 0 바이트를 # 처리했다. 지표를 발행한 적이 없는 것은 트래픽이 없어서다.
⚠️ 지표가 없는 이유도 주석에 남겨요
활동이 생기면 지표가 발행된다는 설명만으로는 현재 활동이 없는 이유를 알 수 없어요. 트래픽이 드문 상태인지, 라우팅 참조가 없어 도달할 수 없는 상태인지 확인한 결과를 함께 적어 두면 다음 사람이 전제를 다시 조사하지 않아도 됩니다.

5. 보류한 로드밸런서의 진입 경로를 확인했어요

반대로 삭제 후보를 보류한 경우도 있었어요. 개발용 로드밸런서 하나가 "타깃 0, 30일 요청 0"을 근거로 확정 목록에 들어 있었지만, 관련 기록을 읽고 세 가지를 더 확인하기로 했습니다.

이름은 외부 연동을 시사했고, 비고에는 선행 조건이 적혀 있었어요. 관련 이미지 저장소를 남기기로 한 판단도 있었습니다. 다시 배포할 가능성이 있다면 이 로드밸런서도 필요한지 확인해야 했어요.

이 계정에는 외부 파트너가 사용한다는 이유로 남긴 자원이 이미 있었어요. 요청이 드물게 오는 경로일 수 있어서 삭제를 멈추고 상위 로드밸런서와 DNS, 리스너 등을 조회했습니다.

이 LB 를 타깃으로 가진 타깃그룹 1개, 그런데 상위 LB 목록이 비어 있다 그 타깃그룹을 쓰는 상위 LB 없음 (이미 삭제됨, 타깃그룹만 고아) DNS 별칭 레코드 없음 (호스팅 영역 전수 조회) 리스너 평문 1개 · 인증서 없음 리스너 기본 액션의 타깃그룹 없음 -> 요청이 와도 갈 곳이 없다 알람 (수동 생성 포함) 없음 코드 참조 없음 RequestCount 30일 데이터 없음 -> 발행된 0 이 아니다

조회해 보니 상위 로드밸런서는 이미 삭제됐고 타깃그룹만 남아 있었어요. 확인한 진입 경로가 없었고, 요청을 받아도 리스너의 기본 액션이 전달할 타깃그룹이 없었습니다.

맨 아래의 RequestCount는 30일간 0을 측정한 결과가 아니라 데이터 없음이었어요. 이 지표는 로드밸런서가 타깃을 선택할 수 있었던 요청을 집계하고, 타깃 선택 전에 거절된 요청은 포함하지 않아요. 따라서 타깃이 없는 상황에서는 데이터 없음이나 0만으로 실제 유입까지 없었다고 볼 수 없어요. 이 결과를 트래픽 부재의 직접 근거로 쓰지 않고, 그 위 일곱 줄의 조회 결과를 함께 보고 판단했습니다.

이름과 비고에서 예상했던 사용 경로는 확인되지 않았어요. 비고의 선행 조건도 현재 도달 경로가 있다는 뜻은 아니었습니다. 이미지 저장소를 남기는 판단은 유지했고, 다시 배포할 때는 로드밸런서를 새로 연결하면 된다고 봤어요.

보류했던 이유와 조회 결과를 함께 남겼어요. 이름이 외부 연동을 시사한다는 이유만으로 계속 남겨 두기보다는, 실제 연결 관계를 확인한 결과로 판단을 갱신한 것입니다.

6. 같은 가용영역의 인스턴스도 다른 NAT를 사용했어요

삭제 대상 NAT와 같은 가용영역에서 운영 인스턴스가 실행 중인 경우도 있었어요.

같은 영역에 있다는 것만으로는 그 NAT를 사용하는지 알 수 없었어요. 인스턴스가 속한 서브넷의 라우팅 테이블을 확인해야 했습니다.

같은 영역 운영 인스턴스가 돌고 있다 삭제 대상 NAT 도 같은 영역 라우팅 테이블 기본 경로 -> 다른 영역 NAT 즉 삭제와 무관하다

그 인스턴스의 기본 경로는 다른 가용영역의 NAT를 가리켰어요. 삭제 대상 NAT와 같은 영역에 있었지만 실제로는 다른 NAT를 사용하고 있었습니다. 자원의 위치와 트래픽이 나가는 경로를 따로 확인해야 하는 경우였어요.

이번에 삭제 근거로 쓰려던 정보는 최소 요금과 같은 청구액, 30일간의 0, 발행되지 않은 지표, 같은 가용영역에 있는 자원이었어요. 각각 추가 조회의 출발점은 됐지만, 단독으로는 사용 여부를 확정하지 못했습니다.

삭제 판단에는 참조 관계와 트래픽을 함께 확인한 결과를 사용했어요. 조회 기간과 통계는 드문 사용을 놓치지 않도록 정했고, 잘못 삭제했을 때의 복구 가능성도 같이 검토했습니다.

✍️ 확인한 결과
로드밸런서 38개 중 33개의 사용량 요금이 0이었지만, 연결 관계와 트래픽을 확인한 뒤 실제로 지운 것은 4개였어요. 30일간 사용이 없어 보인 자원도 90일 조회에서는 연결이 두 건 확인됐습니다.

NAT는 라우팅 참조와 30일간 발행된 바이트 지표의 0을 함께 확인했어요. 요청 수가 발행되지 않은 로드밸런서는 그 결과를 측정된 0으로 취급하지 않고, 상위 자원과 DNS·리스너·코드 참조를 추가로 조회해 판단했습니다. 삭제 전에는 조회 기간과 통계뿐 아니라 같은 경로로 복구할 수 있는지도 고려했어요.
