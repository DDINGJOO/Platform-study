11편. Terraform state 잠금 충돌과 PR 라벨 재검사를 구분하기 ← 지금 이 글

정리 대상으로 확정한 목록에서 마지막으로 남은 것은 사용이 끝난 서비스의 자원이었어요. 7편에서 확인한 삭제 순서에 따라 먼저 알람을 코드에서 빼는 PR을 올렸습니다. 검사가 통과한 뒤 머지하고, 곧바로 plan을 수동 실행했어요.

그런데 Error acquiring the state lock 오류로 plan이 실패했어요. Terraform이 상태 파일에 대한 잠금을 얻지 못했다는 뜻이에요.

자원을 지우기 전에 확인할 일이 세 가지 생겼어요. 자동 실행과 수동 실행의 잠금 충돌, 삭제 허용 라벨을 붙인 뒤에도 남아 있는 실패 결과, 그리고 제가 잘못 의심한 파괴적 변경 가드였어요. 앞의 둘은 실제로 실행을 막았고, 마지막 하나는 실패 원인을 찾는 과정에서 생긴 오해였습니다.

1. 사용 여부는 신고 대신 요청 수와 타깃 수로 확인했어요

당시 정리 대상으로 기록한 자원은 운영과 개발 로드밸런서 하나씩, 타깃그룹 둘, DNS 레코드 둘, 컨테이너 클러스터 하나, 용량 공급자 하나, 자동 확장 그룹 하나, 시작 템플릿 둘, 이미지 저장소 둘, 배포용 버킷 둘이에요. 당시 확인한 목록에서 과금되던 것은 로드밸런서와 이미지 저장소뿐이었고, 나머지는 요금이 0이었어요. 다음 사람이 용도를 다시 조사하지 않도록 함께 정리 대상으로 잡았어요. 다만 클러스터 하나는 이후 남아 있는 것으로 확인됐고, 실제 최종 삭제 결과는 확보하지 못했어요. 삭제 순서와 그 이유는 7편에서 다뤘어요.

이 가운데 DNS 레코드 둘은 사용 여부를 판단할 때 무엇을 확인해야 하는지 보여줬어요.

도메인 두 개가 여전히 로드밸런서를 가리키고 있었어요. 연결된 타깃은 0이었고, 그 주소로 접속하면 오류 응답을 받았습니다. 생성 시점을 확인하니 열다섯 달이 지나 있었어요.

그동안 접속 오류에 대한 신고는 없었어요. 7편에서는 DNS를 먼저 정리해야 연결할 수 없는 주소가 남지 않는다는 점을 다뤘는데, 여기서는 신고가 없다는 사실을 어떻게 해석할지가 더 걸렸어요.

신고가 없다는 사실만으로 사용자가 없다고 단정할 수는 없어요. 사용하려다 실패했어도 신고하지 않을 수 있으니까요. 이번에는 요청 지표와 타깃 수, DNS와 리스너의 연결 관계를 함께 보고 미사용으로 판단했어요. 다만 RequestCount는 타깃을 선택할 수 있었던 요청만 집계하므로 실제 유입이 없었다는 증거로 단독 사용하지는 못해요.

청구서와 기존 알람만으로도 이 상태를 파악하기 어려웠어요. DNS 레코드는 과금이 거의 없었고, 로드밸런서에는 시간당 요금이 계속 청구됐습니다. 청구서에는 뒤에 연결된 타깃이 없다는 정보가 없어요. 당시 조회한 요청 지표에는 처리된 요청이 드러나지 않았고 오류율이나 응답 시간 알람에서도 이 자원을 찾지 못했어요. 타깃 선택 전 거절된 요청이나 전체 유입까지 없었다고 확인한 것은 아니에요.

🔎 기존 청구서와 감시에서 확인하기 어려웠던 점
• 접속 오류에 대한 신고는 없었어요. 신고 여부만으로 사용하지 않는 자원이라고 판단하지는 않았습니다.
• 청구서에는 로드밸런서 요금이 있었지만, 연결된 타깃이 없다는 정보는 없었어요.
• 당시 오류율과 응답 시간 알람에서 이 자원을 찾지 못했어요. 이것만으로 모든 요청의 부재가 확인된 것은 아니에요.
• 정리 과정에서 DNS 연결 관계와 요청 수, 타깃 수를 함께 확인해 사용 여부를 판단했습니다.

2. 머지 직후 자동 실행과 수동 plan이 겹쳤어요

실행 과정에서 먼저 살펴볼 것은 머지 직후의 잠금 오류예요. 알람 제거 PR을 머지하고 plan을 수동 실행했더니 다음 오류가 나왔어요.

Error acquiring the state lock 코드는 방금 검사를 다 통과했다. 같은 plan 이 PR 에서 이미 성공했다. 그런데 머지한 뒤에 같은 것을 돌리니 실패한다.

처음에는 방금 머지한 변경에 문제가 있다고 생각했어요. 하지만 실행 목록을 확인하니 다른 잡이 같은 상태 파일을 사용하고 있었습니다.

이 파이프라인에는 실행을 시작하는 트리거가 두 개 있어요. 기본 브랜치에 push가 들어오면 자동으로 실행되고, 사람이 workflow_dispatch로 수동 실행할 수도 있어요. 두 경로는 같은 Terraform 상태 파일을 사용합니다. 상태 파일은 Terraform이 관리하는 자원 정보를 저장하는 파일이에요.

PR 머지로 자동 잡이 시작됐고, 그 잡이 상태 파일의 잠금을 사용하고 있었어요. 제가 누른 수동 실행은 잠금을 얻지 못해 실패했습니다. 이번 실패는 변경 내용보다 두 실행이 겹친 시점과 관련이 있었어요.

그날은 자동 실행이 끝날 때까지 기다린 뒤 다시 실행했어요. 진행 중이거나 대기 중인 잡은 다음 명령으로 확인할 수 있었습니다.

// 지금 도는 것이 있는지 먼저 본다 gh run list --limit 5 --json databaseId,name,status,event \ --jq '.[] | select(.status=="in_progress" or .status=="queued")' 결과가 비어 있을 때 dispatch 한다. 머지 -> (자동 잡 종료 확인) -> 수동 실행 이 셋이 한 세트다.

위 명령은 최근 다섯 실행을 살펴보는 예시예요. 빈 결과만으로 같은 상태 파일을 사용하는 모든 실행이 없다고 보장하지는 못해요. 실제 실행 전에는 자동·수동 경로의 진행·대기 실행을 충분한 조회 범위에서 확인해야 해요. 당시 그 전체 범위를 확인한 실행 원본은 확보하지 못했어요.

당시 구조에서는 머지 직후 수동 실행을 누르기 전에 자동 잡의 종료를 확인해야 했어요. 머지가 자동 실행도 시작한다는 점을 놓치면 같은 잠금 충돌이 생길 수 있었습니다.

매번 사람이 실행 목록을 조회하고 기다려야 하는지도 확인해 봤어요. 워크플로 자체에서 같은 상태 파일을 사용하는 실행이 겹치지 않게 조정할 수 있는지 보려던 거예요.

두 경로 모두 동시 실행을 제한하는 그룹을 갖고 있었지만 그룹 이름이 달랐어요. 같은 그룹에 속한 실행을 조정하는 설정이므로, 이 설정으로는 자동 경로와 수동 경로 사이의 충돌을 막지 못했습니다.

같은 상태 파일을 사용하는 두 경로를 공통 동시 실행 그룹으로 묶는 방안을 생각했어요. 다만 그룹을 합쳤을 때 대기와 취소가 어떻게 동작할지는 함께 확인해야 합니다.

그날 적용한 대응은 자동 잡이 끝나기를 기다린 것까지예요. 그룹을 합치는 변경은 하지 않았고, 충돌 방지 효과도 시험하지 않았습니다.

잠금 충돌을 확인했지만, 당시에는 파괴적 변경 가드의 입력 설명도 잘못됐다고 의심했어요. 워크플로를 다시 읽어 보니 그 의심은 맞지 않았습니다.

그림 1. 머지로 시작된 자동 잡과 수동 plan이 같은 상태 파일의 잠금을 요청했어요

3. 수동 적용 가드와 PR 가드를 혼동했어요

이 저장소에는 삭제나 재생성이 포함된 plan을 제한하는 파괴적 변경 가드가 있어요. 수동 적용 경로에서는 별도 입력으로 허용 여부를 지정합니다. 그날은 알람 넷을 지우려던 상황이라 이 입력을 의심했어요.

입력 설명은 “적용 단계에서만 의미가 있다”였어요. 그래서 plan을 실행할 때는 켜지 않았는데 실패하자 설명과 실제 동작이 다른지 확인했습니다.

확인할 부분은 두 가지였어요. 이 입력이 plan 실패에 영향을 줬는지, 그리고 입력 설명 자체가 잘못됐는지였어요.

워크플로를 읽어 보니 입력 설명과 동작이 일치했어요. 이 입력으로 허용 여부를 판단하는 가드는 적용 잡에만 있었습니다. plan 잡에서는 삭제와 재생성 건수를 요약하고, 적용할 때 입력을 켜야 한다고 안내할 뿐이에요. 이 입력을 켜지 않았다는 이유로 plan을 멈추지는 않았습니다.

혼동한 이유는 같은 이름의 가드가 PR 경로에도 있었기 때문이에요. PR 쪽 가드는 plan 단계에서 실제로 검사를 실패시켰고, 저는 머지 전에 이미 이 가드에 한 번 걸린 상태였어요.

두 가드는 허용 여부를 확인하는 방법이 달랐어요. 수동 적용 경로에서는 실행 입력을 보고, PR 경로에서는 삭제 허용 라벨을 봅니다. 저는 PR에서 겪은 동작을 수동 plan 입력에도 적용해 생각했어요.

실패는 하나인데 후보가 둘이었다 후보 A state 잠금 충돌 실제 원인. 기다리면 풀린다 후보 B 파괴적 변경 가드 원인이 아니었고, 다시 읽어보니 결함도 아니었다 A 를 해소하니 plan 이 돌았다. B 는 켜지 않은 채로 통과했다. => 그 통과가 이미 답이었다. 안 켜도 도는 것이 정상이었으니까. 이름이 같은 가드가 둘이다 plan 단계에서 막는 것 PR 쪽. 라벨로 통과시킨다 (4장) 적용 단계에서 막는 것 실행 입력으로 통과시킨다

3편에서도 원인 후보를 확인하지 않은 채 받아들인 문제를 다뤘어요. 이번에도 입력 설명이 잘못됐다고 판단하면서, 실제로 어느 잡에서 그 입력을 읽는지 확인하지 않았습니다.

그날 메모에는 이 내용을 실패 원인과 별개의 문서 불일치로 적어뒀어요. 이후 워크플로를 다시 읽고 나서야 그 판단도 틀렸다는 것을 알았습니다. 입력 설명은 수정할 필요가 없었어요.

자동 잡이 끝난 뒤 입력을 켜지 않고도 plan이 통과했으므로, 입력 미설정이 이번 실패의 원인은 아니었어요. 여기에 워크플로에서 확인한 가드의 위치까지 대조하니 문서 불일치라는 판단도 바로잡을 수 있었습니다.

🔬 원인 후보를 확인할 때 구분한 것
• 이번에는 읽기 단계인 plan에서 실패했기 때문에 자동 잡이 끝난 뒤 같은 입력으로 다시 실행할 수 있었어요.
• 입력을 켜지 않아도 plan이 통과했다는 결과로, 입력 미설정이 실패 원인이 아니라는 점을 확인했습니다.
• 입력 설명이 잘못됐는지는 별도로 워크플로에서 가드의 위치와 조건을 읽고 확인했어요.
• 되돌릴 수 없는 변경에서는 후보를 시험하려고 실행하지 않고, 실행 전에 코드와 문서로 범위를 좁혀야 해요.

4. 라벨을 붙인 뒤에는 검사를 다시 실행해야 했어요

시간상 가장 먼저 겪은 문제는 머지 전 PR 검사였어요. 삭제가 있는 PR에는 삭제 허용 라벨이 필요하고, 없으면 검사가 실패해 머지할 수 없었습니다. 실패 메시지는 라벨을 붙인 뒤 해당 잡을 다시 실행하라고 안내했어요.

라벨을 붙였지만, 이미 끝난 검사는 실패 상태로 남아 있었어요.

PR 화면에서는 라벨이 붙은 현재 상태와 라벨이 없을 때 계산한 검사 결과가 함께 보였어요. 라벨을 붙였다는 것만 확인해서는 해결되지 않는 이유였습니다.

라벨은 현재 PR의 상태이고, 검사 결과는 해당 실행에서 확인한 상태의 스냅샷이에요. 여기서 스냅샷은 검사 시점의 값을 남긴 결과를 뜻합니다. 라벨을 바꿔도 이미 완료된 실행의 결과가 바뀌지는 않아요. 당시에는 라벨을 붙인 뒤 실패한 잡을 재실행해야 새 판정이 반영됐습니다.

라벨을 붙였는데 왜 안 되나 라벨 PR 에 붙어 있는 지금의 상태 붙이면 즉시 바뀐다 검사 결과 그 실행이 끝난 시점의 스냅샷 다시 돌려야 바뀐다 필수 검사는 "마지막으로 완료된 실행" 만 본다. => 라벨을 붙인 뒤 실패한 실행을 재실행하는 것까지가 한 세트다.

위 인용의 마지막으로 완료된 실행만 본다는 표현은 당시 실패 결과를 갱신해야 했던 상황을 단순화한 것이에요. 일반적으로는 최신 관련 커밋 SHA에 지정된 필수 체크와 상태, 브랜치 보호 설정이 머지 가능 여부를 결정해요. 아무 실행이나 마지막으로 성공하면 된다는 뜻은 아니에요.

가드가 라벨을 읽는 방법도 확인했어요. 이벤트에 담긴 과거 값을 그대로 쓰지 않고 실행 시점에 API로 조회하고 있었습니다. 이벤트 값만 읽었다면 재실행해도 라벨을 붙이기 전의 값을 다시 읽었을 거예요. 코드 주석에도 재실행이 가능하도록 이렇게 조회한다는 이유가 적혀 있었어요.

라벨을 제거하는 방향도 고려돼 있었어요. 검사가 통과한 뒤 라벨을 떼더라도 완료된 실행의 성공 결과는 그대로 남습니다. 그래서 당시 워크플로는 라벨 제거 이벤트에도 새 검사를 실행하도록 설정돼 있었어요. 제가 직접 겪은 것은 라벨 추가 후 재실행이 필요한 경우이고, 제거 시 재검사 설정은 코드를 읽어 확인했습니다.

라벨을 붙이는 것과 그 라벨로 검사하는 것은 별도 단계였어요. 안내된 대로 실패한 잡을 다시 실행해야 현재 라벨을 기준으로 판정할 수 있었습니다.

그림 2. 라벨 변경은 새 검사에서 반영돼요. 당시에는 추가 후 수동 재실행이 필요했어요

5. 삭제 순서와 함께 실행 조건도 남기기

잠금 충돌, 라벨 검사, 가드 입력의 혼동을 나란히 정리해 봤어요.

막은 것 내가 의심한 곳 실제 원인 ----------------------------------------------------------------- state 잠금 내 코드 다른 실행이 진행 중이었다 삭제 허용 라벨 라벨을 잘못 붙였나 판정이 과거 시점에 끝나 있었다 (파괴적 변경 가드) (내 입력값) 아무것도 아니었다. 이름이 같은 가드를 헷갈린 것이다 둘 다 코드는 옳았고, 셋째는 애초에 막은 것이 아니었다. 어긋난 것은 "지금 무엇이 참인가" 와 "그 판정이 언제 어디서 일어났나" 사이의 간격이다.

잠금 문제는 다른 실행의 진행 상태를, 라벨 문제는 검사가 실행된 시점을 확인해야 했어요. 가드 입력의 오해는 워크플로에서 같은 이름의 가드가 각각 어디에 있는지 읽고 풀었습니다. 변경한 자원 코드와 함께 실행 상태와 검사 위치도 확인해야 했어요.

당시에는 알람을 먼저 제거하고 참조하는 쪽부터 삭제한 뒤 목록 조회로 완료를 기록했어요. 하지만 7편에서 정정했듯이 서비스 정의가 남은 클러스터 하나는 삭제가 거부된 상태였어요. 이 목록 확인을 최종 삭제 완료의 근거로 볼 수는 없고, 후속 최종 삭제 결과는 확보하지 못했어요.

삭제 순서와 순서를 바꿨을 때 생기는 문제가 코드 주석에 적혀 있어서 그대로 따를 수 있었어요. 이 두 가지 이유와 plan 기대값을 한 번 잘못 잡은 일은 7편에서 다뤘습니다.

삭제 절차에는 이유가 남아 있었지만, 자동 잡을 기다리거나 라벨 검사 결과를 갱신하는 절차는 작업할 때 바로 파악하지 못했어요.

삭제 순서를 틀리면 감시 대상이 사라진 뒤에도 경보 상태가 이어지거나 스택의 plan이 멈춰 복구가 필요할 수 있어요. 반면 이번 잠금 충돌과 라벨 재실행 문제는 자원 변경 전에 멈췄습니다. 자원에 영향이 없었더라도 실행 조건을 확인하는 데 든 과정은 남길 필요가 있었어요.

다음 작업에는 세 가지를 함께 확인할 수 있게 남기려 해요. 머지 후 자동 잡의 종료 여부, 라벨 추가 후 실패한 잡의 재실행 여부, 그리고 PR 가드와 수동 적용 가드가 요구하는 조건의 차이예요.

6. 절감액과 함께 남길 판단 근거와 실행 제약

첫 열한 편을 돌아보니 비용을 줄이는 명령보다 측정과 사용 여부 판단, 실행 조건을 확인하는 과정이 많이 나왔어요.

이 시리즈가 실제로 다룬 것 측정이 틀린 이야기 청구서가 이미 틀렸다 · 그럴듯한 숫자 · 유휴의 증거를 잘못 골랐다 · 평균은 근거가 못 된다 · 이름이 거짓말했다 막힌 이야기 삭제 순서 · 못 줄인 항목들 · 잠금과 가드와 라벨 실제로 줄인 이야기 선행 조건으로 알람을 만든 편 · 요금 모델만 바꾼 편

이번 작업에서는 무엇을 줄여도 되는지 판단하는 데 많은 시간이 들었어요. 청구 항목 이름이 실제 역할과 다르거나, 평균만으로 최댓값을 파악하기 어렵거나, 조회한 0이 정말 사용량이 없는 것인지 확인해야 하는 경우가 있었기 때문이에요.

그래서 절감액과 함께 판단에 사용한 근거, 실행 중 확인한 제약도 남기려고 해요.

근거가 있으면 다음 사람이 같은 자원을 검토할 때 무엇을 확인했는지 알 수 있어요. 삭제 순서를 따른 이유가 주석에 남아 있었던 것도 이번 작업에 도움이 됐습니다.

잠금과 라벨에서 멈춘 과정도 같은 용도로 남길 수 있어요. 삭제 대상의 판단과 실제 실행 조건을 함께 적어두면 다음 정리 작업에서 확인할 항목이 분명해집니다.

✍️ 확인한 내용
머지로 시작된 push 자동 잡과 수동 plan이 같은 상태 파일을 사용하면서 잠금 충돌이 났어요. 그날은 자동 잡이 끝난 뒤 다시 실행했습니다. 두 경로의 동시 실행 그룹 이름은 달랐고, 공통 그룹으로 묶는 방안은 적용하거나 시험하지 않았어요.

PR에 삭제 허용 라벨을 붙인 뒤에는 실패한 잡을 재실행해야 했어요. 당시 가드는 실행 시점의 라벨을 조회했고, 라벨을 제거할 때도 새 검사를 시작하도록 설정돼 있었습니다. 수동 실행 입력으로 허용 여부를 판단하는 가드는 적용 잡에만 있었어요. PR plan의 라벨 가드와 혼동해 입력 설명을 의심했지만, 워크플로를 다시 읽고 그 판단을 바로잡았습니다.

도메인 둘이 가리키던 로드밸런서에는 타깃이 없었고, 생성 후 열다섯 달 동안 오류 신고도 없었어요. 사용하지 않는 자원이라는 판단에는 요청 수와 타깃 수를 확인한 결과를 썼습니다. 삭제는 기록된 순서로 진행했지만 완료 기록 뒤에 클러스터 잔존이 확인됐어요. 최종 삭제 결과는 확인하지 못했고, 다음 작업에서 참고할 수 있도록 실행 전 확인한 잠금과 라벨 조건도 함께 남기려 해요.
