5편. 복제 인스턴스 다운사이징 전에 최저 여유 메모리 확인하기 ← 지금 이 글

AWS DMS에서 소스의 데이터 변경분을 대상에 반영하는 복제 인스턴스의 목표 등급을 확정하고 중단 시간을 계산해 작업 시간까지 잡아둔 상태였어요. 적용 직전에 같은 지표를 다시 열되, 이번에는 통계를 바꿔 봤어요.

조회한 지표와 기간은 같았지만 목표 등급은 한 단계 높여야 했어요. 평균으로 봤을 때는 충분해 보이던 메모리가 최저값으로 보니 부족했기 때문이에요.

이후 컨테이너 CPU도 조회 차원을 바꿔 확인했어요. 클러스터 평균만 보고 예약량을 줄이려던 판단을 서비스별 지표를 확인한 뒤 수정했어요. 두 경우 모두 숫자를 구한 뒤에야 그 숫자로 용량을 정해도 되는지 다시 따져 본 셈이에요.

1. 여유는 최저값으로, 사용률은 최고값으로

사이징, 즉 필요한 자원 용량을 정할 때는 "이 자원을 절반으로 줄여도 운영에 문제가 없을까"를 확인해야 해요. 평상시 평균뿐 아니라 여유가 가장 적었거나 사용량이 가장 높았던 순간을 살펴봤어요.

보려는 것 통계 이유 ──────────────────────────────────────────────────────────── 메모리 · 스토리지 여유 Minimum 여유가 가장 없던 순간이 한계다 CPU · 지연 Maximum 가장 몰린 순간이 한계다 사이징 근거 Average 쓰지 않는다

여유를 나타내는 지표는 값이 낮을수록 한계에 가까우니 Minimum(최저값)을 확인해요. 반대로 사용률이나 지연은 높은 값이 문제가 되므로 Maximum(최고값)을 봐요. 어느 방향으로 값이 변할 때 용량이 부족한지를 먼저 정해야 통계를 고를 수 있어요.

그렇다고 최고값만으로 등급을 정할 수는 없어요. 이번에도 더 작은 클래스를 선택하지 못한 근거가 CPU 최고값 하나였는데, 다시 보니 여러 대 중 한 대의 특정 하루에 나온 값이었어요. 그 값을 모든 인스턴스에 적용하고 있었어요.

최고값이 높다면 어느 자원에서 얼마나 오래 발생했는지 함께 봐야 해요. 한 대의 일시적인 사용량으로 여러 대의 상시 용량을 정할 수는 없으니까요. CPU를 낮게 쓰는 동안 크레딧을 적립하고 필요할 때 기준 성능을 넘겨 쓰는 버스터블 계열은 지속 시간이 특히 중요해요. 기준선을 몇 분 넘겼는지 몇 시간 넘겼는지는 최고값 하나로 알 수 없어요.

평균만으로는 여유가 얼마나 적었고 사용률이 얼마나 높았는지 알 수 없어요. 여유 메모리의 평균이 높아도 짧은 시간에는 메모리가 부족할 수 있어요. 사용률 평균이 낮은 경우에도 최대 사용량은 별도로 확인해야 해요.

콘솔에서 지표를 열면 통계가 평균으로 선택돼 있는 경우가 많아요. 용량을 정하려고 조회했다면 선택된 통계부터 확인해야 해요.

2. 적용 직전에 등급이 한 단계 올라갔다

처음에는 복제 인스턴스의 여유 메모리 지표인 FreeableMemory를 평균으로 보고 등급을 확정했어요. 여유가 계속 충분해 보여 메모리 4GB 등급으로 내려도 된다고 판단했어요.

적용 전에 같은 지표를 Minimum으로 다시 조회했어요.

FreeableMemory Average → 여유가 넉넉해 보인다 → 4GB 등급으로 확정 FreeableMemory Minimum → 실사용이 5GB 남짓 → 4GB 등급의 용량을 넘는다 판정: 한 단계 위(8GB)로 정정. 적용 전에 잡았다.

전체 메모리에서 여유를 뺀 값이 목표 등급의 전체 용량보다 컸어요. 그대로 적용하면 스왑 사용이나 복제 지연, 프로세스 종료가 생길 수 있다고 보고 목표를 8GB로 정정했어요. 4GB로 변경한 뒤 문제가 난 것은 아니에요.

평균의 계산이 틀린 것은 아니었어요. 다만 줄인 용량으로 최대 사용량을 감당할 수 있는지 확인하는 데 평균만 쓴 것이 문제였어요. 계산을 다시 하는 것보다 통계 선택을 다시 확인해야 했어요.

그림 1. 같은 여유 메모리 지표라도 평균과 최저값으로 판단한 목표 등급이 달랐어요

3. 변경 후 실측으로 다음 등급을 판단했어요

정정한 등급으로 두 대를 줄였어요. 8 vCPU에서 2 vCPU로 바꾸고 메모리는 절반으로 낮췄어요. 복제가 실제로 중단된 시간은 5분 48초였고, 두 대의 비용은 합쳐 67% 줄였어요.

전환 후 다시 측정해 보니 메모리와 CPU 사용량도 이전보다 낮았어요.

변경 전 (16GB) 변경 후 (8GB) ────────────────────────────────────────────────────── 메모리 실사용 5GB 남짓 2GB 아래 CPU 피크 0.59 vCPU 0.09 vCPU SwapUsage 0 0

워크로드는 그대로였는데 실사용으로 계산한 메모리가 절반 아래로 줄었어요. 변경 전의 "5GB 남짓"을 고정된 필요 메모리로 볼 수 없다는 결과였어요.

다만 무엇 때문에 줄었는지는 이 지표만으로 확인할 수 없어요. 여유 메모리에는 필요하면 회수할 수 있는 캐시도 포함되므로 "전체 용량에서 여유를 뺀 값"이 곧 작업에 필요한 메모리라고 단정할 수 없어요. 원인을 확인하려면 인스턴스 내부에서 별도로 측정해야 했지만 그렇게 하지는 않았어요.

다음 등급은 변경 전의 측정값만으로 정하지 않기로 했어요. 같은 워크로드에서도 인스턴스 크기를 바꾼 뒤 값이 달라졌으니, 변경 후 측정값으로 다시 검토할 필요가 있었어요.

CPU 사용량도 낮아졌어요. 변경 후 실사용은 버스터블 계열 기준선의 몇 분의 일 수준이어서 크레딧이 적립되는 상태였어요. 관측한 사용량으로는 더 작은 등급에서도 기준선 안에 들어간다고 판단했어요.

이후에는 한 단계 줄인 뒤 다시 측정하고, 그 결과로 다음 변경을 판단하는 방식으로 검토했어요. 처음 측정한 사용량만으로 최종 등급까지 정하기 어려웠기 때문이에요.

4. 같은 CPU 사용률인데 분모가 다르다

다음은 Amazon ECS의 CPU 지표를 비교한 사례예요. 컨테이너 CPU는 조회 차원을 확인한 뒤 판단을 바꿨어요. 여기서 차원은 클러스터 전체를 볼지 개별 서비스를 볼지 구분하는 조회 기준이에요.

먼저 컨테이너 클러스터 전체의 CPU 지표를 열었어요.

클러스터 차원 CPUUtilization 평균 2% 클러스터 차원 CPUReservation 97%

예약은 97%인데 평균 사용률은 2%였어요. 처음에는 태스크, 즉 컨테이너 실행 단위에 설정한 CPU 예약량이 과하다고 해석했어요. 예약량을 줄이면 같은 노드에 더 많은 태스크를 배치해 노드 수를 줄일 수 있다고 보고 절감 항목으로 적었어요.

하지만 서비스 차원으로 조회하니 CPU 사용률의 최대가 100%를 넘었어요.

두 조회 모두 이름은 CPUUtilization이지만 사용률을 계산하는 분모가 달라요.

차원 CPUUtilization 의 분모 ──────────────────────────────────────── 클러스터 클러스터에 등록된 총 CPU 서비스 태스크가 예약한 CPU

클러스터 차원의 2%는 등록된 노드의 총 CPU 대비 사용률이에요. 서비스 차원의 100% 초과는 태스크가 예약한 CPU보다 많이 쓴 구간이 있었다는 뜻이에요. 클러스터 평균이 낮아도 개별 서비스가 예약량 안에서만 실행됐다고 볼 수는 없어요.

당시에는 예약 97%와 평균 사용 2%만으로 개별 태스크의 예약량도 과하다고 판단했어요. 하지만 클러스터 전체 평균만으로는 어느 서비스가 언제 예약량을 초과했는지 알 수 없었어요. 서비스별 사용량을 함께 확인해야 할 부분을 빠뜨렸어요.

서비스 지표까지 확인한 뒤에는 예약을 줄이려던 판단을 보류하고 용량을 늘릴지 검토하는 항목으로 옮겼어요. 예약량을 초과한 서비스에도 클러스터 평균만 근거로 예약 축소를 적용할 수는 없었어요.

그림 2. 클러스터 평균이 낮아도 서비스 사용률은 예약량을 넘을 수 있어요
⚠️ 예약 축소를 보류한 항목도 있어요
메모리도 서비스 차원에서 다시 확인했어요. 예약분 대비 여유가 한 자릿수 퍼센트인 곳이 있어, 예약량을 줄이기보다 용량을 검토해야 한다고 판단했어요.

메모리 사용량이 늘어나면 컨테이너가 메모리 부족으로 종료될 수 있으므로, 해당 항목은 절감 목록에서 빼고 용량 검토 항목으로 옮겼어요. 다만 당시 글을 작성한 시점까지 예약량을 실제로 늘리지는 않았어요.

5. 변경 직후에는 지표와 완료 조건을 함께 확인해요

인스턴스 클래스를 바꾼 직후에는 지표가 나오는 시점과 변경 완료 조건도 확인해야 했어요.

CPU 지표는 변경 직후부터 나왔지만 FreeableMemory와 SwapUsage 같은 메모리 계열 지표는 20분쯤 늦게 나왔어요.

당시 메모리 여유 알람은 지표가 나오지 않는 결측 구간을 임계값 위반으로 취급하도록 설정돼 있었어요. 인스턴스에 문제가 생겨 지표가 끊기는 상황을 감지하려는 설정이었지만, 계획된 변경으로 지표가 비는 동안에도 알람이 발생했어요.

이때는 평가 기간을 늘려 20분짜리 공백 때문에 알람이 발생하지 않도록 조정하는 방안을 후속 과제로 남겼어요. 이 작업에서 알람 설정까지 바꾼 것은 아니에요.

변경 완료를 기다리던 반복문도 첫 조회에서 종료됐어요. 상태값만 검사했기 때문이에요.

# 틀렸다 status=$(describe-instance ... --query 'Status') [ "$status" = "available" ] && break # 변경 직후엔 아직 이전 상태다 # 고쳤다 [ "$status" = "available" ] && [ "$class" = "$TARGET_CLASS" ] && break

변경을 요청한 직후에는 상태 전이가 시작되기 전이라 기존의 available이 남아 있을 수 있어요. 반복문은 그 값을 변경 완료로 해석해 종료됐어요.

상태값만으로는 변경 시작 전과 완료 후를 구분할 수 없었어요. 상태가 available이고 인스턴스 클래스도 목표 클래스와 일치할 때만 종료하도록 고쳤어요.

6. 복제 중단 전에 변경 로그 보존 기간을 확인했어요

복제 중단에 대비하려면 현재 사용량 외에 소스의 변경 로그 보존 기간도 확인해야 했어요.

클래스를 바꾸는 동안 복제는 몇 분간 멈춰요. 그 사이 소스에서 일어난 변경이 로그에 남아 있어야 재개 후 이어서 반영할 수 있어요. 보존 기간이 중단 시간보다 짧아 필요한 로그가 사라지면 전체 재적재가 필요해지고, 시간 단위의 작업이 될 수 있어요.

처음에는 복제가 계속 실행 중이니 로그 보존 기간도 충분히 설정돼 있을 것이라고 생각했어요.

하지만 복제가 지연 없이 실행 중이라는 사실만으로는 중단 후에도 필요한 로그가 남는지 알 수 없어요. 보존 기간이 0에 가까워도 계속 읽는 동안에는 문제가 드러나지 않을 수 있어요. 중단 후 재개할 수 있는지는 별도로 확인해야 했어요.

실제 설정값을 확인하니 보존 기간은 중단 시간의 수십 배에서 천 배 넘게였어요. 이 값을 확인한 뒤에야 계획한 중단 시간에 비해 충분하다고 판단했어요.

조회한 값과 그 값으로 판단하려던 조건을 함께 정리했어요.

Average 로 여유를 봤다 → 가장 없던 순간이 가려졌다 큰 인스턴스에서 메모리를 쟀다 → 크기에 딸린 양이 섞여 보였다 클러스터 차원으로 CPU 를 봤다 → 분모가 달라 결론이 뒤집혔다 상태만으로 완료를 판정했다 → 시작 전과 완료가 같아 보였다 "돌고 있으니" 로 보존을 봤다 → 중단 후를 안 본 값이었다

위 메모리 행의 크기에 딸린 양이라는 설명은 당시 해석이며, 감소 원인을 확인한 결과는 아니에요. CPU 행도 클러스터 CPUReservation과 CPUUtilization의 분모가 서로 다르다는 뜻으로 읽으면 잘못이에요. 두 클러스터 지표의 분모는 등록된 총 CPU로 같고, 서비스 차원의 사용률과 비교할 때 분모가 달라져요.

지표와 상태값은 있었지만, 용량 축소나 변경 완료를 판단하는 데 필요한 조건을 모두 확인하지 못했어요. 통계, 조회 대상, 변경 전후의 상태를 함께 확인하면서 판단을 수정했어요.

💡 지표를 조회할 때 함께 확인한 조건
• 값이 낮을 때 문제가 되는 여유 지표는 Minimum을, 높을 때 문제가 되는 사용률 지표는 Maximum을 확인해요.
• 사용률은 조회 차원과 분모를 확인하고, 개별 서비스의 상황을 전체 평균만으로 판단하지 않아요.
• 변경 완료나 복제 재개 조건은 현재 상태값만으로 확인할 수 있는지 따져 봐요.

모든 전제를 따로 실측하지는 않았어요. 로그 보존 기간은 잘못 판단하면 전체 재적재가 필요할 수 있어 실제 설정값을 확인했어요.

이번 작업에서는 여유 메모리의 최저값을 확인해 목표 등급을 높였고, 서비스별 CPU 사용률을 확인해 예약 축소를 보류했어요. 자원을 줄이기 전에 조회한 통계와 범위가 그 판단에 맞는지 확인할 필요가 있었어요.

✍️ 확인한 결과와 남은 작업
여유 메모리를 평균에서 최저값으로 바꿔 확인한 뒤 목표 등급을 4GB에서 8GB로 정정했어요. 두 대를 변경한 뒤 복제 중단 시간과 메모리·CPU 사용량을 다시 측정했지만, 사용 메모리가 줄어든 원인까지 확인한 것은 아니에요.

컨테이너 CPU는 클러스터 평균만으로 예약량을 줄이려던 판단을 서비스별 지표를 본 뒤 보류했어요. 변경 완료 반복문은 상태와 목표 클래스를 함께 검사하도록 고쳤고, 당시 알람 조정과 예약량 증설은 후속 검토로 남겼어요.
