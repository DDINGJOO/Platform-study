3편. WAF ACL 삭제 전후, 빈 조회 결과를 검증한 방법 ← 지금 이 글

삭제 명령을 돌리기 전, 계정의 웹 방화벽 ACL 44개 중 배포가 연결되지 않은 것을 고르고 있었어요. ACL은 요청의 허용·차단 규칙을 묶은 설정이에요. 대부분은 CDN 배포를 콘솔에서 만들 때 자동 생성된 것으로, 이름이 CreatedByCloudFront-로 시작했어요. 판정 스크립트의 결과는 유지 5개, 삭제 후보 39개였습니다.

이후 실제로 39개를 삭제했고 건너뜀 0, 실패 0, 사고 0으로 끝났어요. 다만 삭제 전에 조회 쿼리를 고쳐야 했습니다.

처음 쿼리는 배포 51개 전부에 null을 반환하고 있었어요. 배포와 ACL의 연결 관계를 제대로 읽지 못했는데도 삭제 후보 수는 맞게 나온 거예요.

삭제를 되돌릴 수 없어서 후보 개수만 보고 실행할 수는 없었어요. 연결 집계를 확인한 뒤 삭제했고, 삭제 후에도 빈 지표 조회 결과를 차단 0건으로 해석한 오류를 다시 확인했습니다.

1. 삭제 후보 수와 연결 집계가 별도로 계산됐다

삭제 대상을 고르려면 배포별로 어떤 ACL이 연결돼 있는지 확인해야 해요. 배포가 참조하는 ACL은 남기고 참조가 없는 ACL만 삭제하려고 다음과 같이 조회했습니다.

# 틀렸다 aws cloudfront list-distributions \ --query 'DistributionList.Items[].{ACL:DistributionConfig.WebACLId}' # 결과 [ {"ACL": null}, {"ACL": null}, {"ACL": null}, ... ] 배포 51개 전부 null

원인은 API 응답 구조를 잘못 읽은 데 있었어요. 목록 API가 반환하는 항목은 전체 설정이 아닌 요약 객체예요. 상세 설정 블록은 없고, ACL 식별자는 요약 객체의 최상위 필드에 있습니다. 없는 경로를 조회했지만 오류가 나지 않고 null이 반환됐어요.

# 맞다 --query 'DistributionList.Items[].{ACL:WebACLId}' # 목록 API 의 항목 = 요약 객체 # 상세 설정 블록이 없다 # WebACLId 는 최상위 필드다 # 그래서 상세 설정 안을 파면 오류가 아니라 null 이 돌아온다

그런데 삭제 후보 개수는 잘못된 조회와 별도로 계산하고 있었어요.

전수 44 에서 유지 5 를 뺀다 = 39 <-- 산수. 측정하지 않았다 배포별 연결 수를 세어 집계한다 = 0 <-- 측정. 통째로 죽어 있었다

전체 ACL 개수는 ACL 목록에서, 유지 대상은 저장소의 코드 참조에서 구했어요. 둘 다 배포별 연결 조회 없이 알 수 있는 값이라 44에서 5를 뺀 39가 나왔습니다.

후보 수가 맞아도 각 ACL의 연결 상태를 확인했다는 뜻은 아니었어요. 삭제 39건을 실행하려면 배포를 조회한 결과가 유효한지부터 확인해야 했습니다.

그림 1. 삭제 후보 39개는 배포별 연결 조회와 별도로 계산됐다

2. 연결 조건을 대조해 조회 오류를 찾았다

삭제 후보 39는 예상과 같아서 그 숫자만으로는 조회 오류를 알아차리기 어려웠어요.

대신 판정 단계에 넣어둔 가드가 걸렸습니다. 가드는 미리 정한 조건을 만족하지 않으면 작업을 멈추는 검사예요.

가드: 코드가 참조하는 유지 대상 5개는 연결된 배포가 1개 이상이어야 한다 (참조되지 않는 ACL 을 코드가 붙들고 있을 수는 없다) 결과: 5개 전부 연결 0 가드 위반 5건

위 발췌의 유지 대상 다섯 개별 검사와 위반 다섯 건은 당시 회고의 설명이에요. 고정 커밋에서 확인한 가드는 공용 ACL의 연결 수가 0이거나 기대 하한인 30보다 작으면 중단하는 검사였어요. 개별 가드의 원 임시 코드는 찾지 못했으므로 두 검사를 같은 구현으로 볼 수는 없어요.

당시에는 유지 대상 중 공용 ACL에 수십 개의 배포가 연결돼 있어야 했어요. 삭제할 ACL 39개에 있던 배포를 이미 공용 ACL로 옮긴 뒤였기 때문이에요. 이 전제와 연결 0이라는 조회 결과가 맞지 않았습니다.

쿼리를 고친 뒤에는 연결 수가 다음과 같이 나왔어요.

유지 대상별 연결 수 (수정 후) 공용 ACL 39 두 번째 3 세 번째 2 네 번째 1 다섯 번째 1 ──────────────── 39 + 3 + 2 + 1 + 1 = 46 = ACL 이 붙어 있는 배포 수

공용 ACL에 연결된 배포 39개와 삭제 후보 ACL 39개가 같은 수인 이유도 확인됐어요. 통합 작업으로 배포 39개를 옮겨 기존 ACL 39개가 비어 있었던 거예요. 수정 전에는 한쪽이 단순 뺄셈이고 다른 쪽이 null이라 두 결과를 대조할 수 없었습니다.

후보 수와 독립적인 연결 조건을 확인한 덕분에 조회 오류를 찾았어요. 삭제 대상 개수만 맞춰 보는 검사로는 이 오류를 확인하지 못했을 겁니다.

3. 삭제 후 지표도 빈 결과를 0으로 읽었다

39개를 삭제한 뒤에는 방화벽 차단이 생기지 않았는지 확인하려고 지표를 조회했어요. 삭제 대상에 실제 연결이 남아 있었다면 배포에 영향을 줄 수 있으므로, 삭제 전 판정과 별도로 동작을 확인하려던 거예요.

AllowedRequests 0 BlockedRequests 0

처음에는 차단 요청이 0이라는 결과를 보고 문제가 없다고 판단했어요.

하지만 허용 요청도 0이었어요. 이 계정에는 월 천만 단위 요청을 받으며 방화벽을 거치는 도메인이 있어서, 그 트래픽을 받는 ACL의 몇 시간치 허용 요청이 모두 0인 결과는 다시 확인해야 했습니다. 지표의 차원 값을 잘못 지정해 데이터가 없는 시계열을 조회한 것이었어요.

차원은 지표를 자원이나 범위별로 구분하는 값이에요. ACL 이름과 적용 범위, 지표가 발행되는 리전을 맞춰야 원하는 시계열을 조회할 수 있습니다. 하나가 어긋나도 오류 없이 빈 결과가 나올 수 있어요. CDN 앞에 연결한 전역 범위 ACL의 지표 리전은 평소 쓰는 리전과 다를 수 있어 함께 확인해야 했습니다.

이 판단은 해당 도메인의 트래픽을 받는 ACL을 조회했을 때만 유효해요. 트래픽이 없는 다른 ACL이라면 허용 요청 0이 정상일 수 있으니, 어떤 자원에 대한 조건인지까지 정해야 합니다.

허용 요청 조회가 유효하지 않았다면 같은 조회에서 얻은 차단 0도 차단이 없었다는 근거로 쓸 수 없어요. 두 값이 모두 잘못 지정한 차원에서 나온 결과였기 때문입니다.

삭제 전에는 없는 응답 경로를 조회했고, 삭제 후에는 잘못된 차원으로 지표를 조회했어요. 두 경우 모두 빈 결과를 원하던 값인 0으로 해석했습니다.

1장 상세 설정 안을 뒤졌다 -> null 51개 -> "붙은 배포 0개" 3장 차원을 틀리게 줬다 -> 데이터 없음 -> "차단 0건" 둘 다 조회가 실패했는데 실패로 보이지 않았다 둘 다 원하는 결론과 모양이 같았다

4. 0이 나올 수 없는 조건을 함께 확인한다

그래서 0이나 빈 결과를 근거로 삼기 전에, 이미 알고 있는 조건과 모순되지 않는지 함께 확인했어요.

이번에는 공용 ACL에 수십 개가 연결돼 있어야 한다는 조건과, 알려진 트래픽의 허용 요청이 0일 수 없다는 조건이 있었어요. 이 조건들을 대조해야 조회가 잘못된 것인지, 실제로 해당 항목이 없는 것인지 구분할 수 있었습니다.

다만 사전 정보가 있어야 이런 조건을 정할 수 있어요. 처음 보는 자원이나 관측한 적 없는 지표라면 0이 잘못된 결과인지 판단하기 어렵습니다. 그때는 0만으로 결론을 내리지 않고 직접 요청을 보내거나 참조 관계를 확인해야 해요. 이번 작업에서도 두 방법을 함께 썼습니다.

연결 수가 7인데 예상이 39라면 차이가 바로 보여요. 반면 차단 0이나 참조 0은 작업에서 기대하던 결과이기도 해서, 조회 자체가 잘못됐다는 사실을 놓치기 쉽습니다.

그림 2. 잘못된 조회와 실제 0을 구분하려면 사전 조건이 필요하다

알람 검사에는 빈 결과를 확인하는 자기검사가 있었다

알람 커버리지 검사 스크립트에도 같은 문제를 다룬 주석이 있었어요. 코드에 적힌 리소스와 실제 목록을 대조해 알람이 없는 자원을 찾는 스크립트인데, 자기검사 절에 다음과 같이 적혀 있었습니다.

# 파서가 조용히 빈 목록을 내면 "감시 밖 0개" 로 보이고, 그건 통과와 구분되지 않는다. # 그 경우가 이 검사에서 가장 나쁜 실패다.

이 스크립트에는 정상 입력에서 파서가 실제 값을 추출하는지 확인하는 자기검사가 있어요. 입력을 읽지 못해 빈 목록이 나온 경우를 정상 통과와 구분하려는 검사입니다.

그런데 한 번 실행할 조회 명령에는 같은 확인을 적용하지 않았어요. 검사 스크립트는 CI에서 실패를 알릴 수 있지만, 수동 조회의 빈 결과는 기대한 답과 같으면 그대로 근거로 받아들이기 쉬웠습니다.

삭제 전 조회 오류를 찾은 가드도 이번 작업용 1회성 판정 스크립트에 넣은 것이었어요. 당시 삭제를 확인하는 데는 썼지만, 다음 삭제 작업에서도 같은 조건을 확인하도록 절차에 반영한 상태는 아니었습니다. 불가능 조건을 삭제 절차의 필수 입력으로 만드는 일은 남아 있었어요.

🧪 0을 근거로 쓰기 전에
• 어떤 자원에서 어떤 값이 0일 수 없는지 적어요. 사전 정보가 없다면 0만으로 결론 내리지 않아요.
• 같은 조회에서 함께 확인할 값을 정해요. 이번에는 해당 ACL의 허용 요청도 0인지 확인했습니다.
• 최종 답이 다른 계산에서 나온 것은 아닌지 확인해요. 후보 수가 맞아도 연결 조회가 유효하다는 증거는 되지 않아요.

5. 배포 51개를 두 경로로 확인했다

지표 조회를 근거로 쓸 수 없어서 배포에 직접 요청을 보내 응답을 확인했어요. 처음에는 대표 3곳만 골랐습니다.

그중 한 곳이 403을 반환했어요. 방화벽이 새로 막은 것인지 기존 응답인지 이 표본만으로는 구분하기 어려웠습니다. 삭제한 ACL은 39개라 나머지 배포의 상태도 확인해야 했어요.

확인 범위를 배포 51개 전체로 넓히고 각각 두 경로에 요청을 보냈어요.

51개 · 2경로 = 102회 cloudfront.net 기본 도메인 DNS 를 배제하고 CDN 과 방화벽만 본다 별칭 도메인 실제 사용자가 타는 경로 차단 판별: 응답 본문에 방화벽의 차단 문구가 있는지 결과: 102회 전부에서 0건

경로를 나눈 이유는 실패 지점을 구분하기 위해서예요. 별칭 도메인만 보면 DNS나 인증서 문제를 방화벽 문제로 오해할 수 있고, 기본 도메인만 보면 사용자가 실제 접근하는 경로를 확인하지 못합니다.

차단 여부는 상태 코드 대신 응답 본문의 차단 문구로 판별했어요. 403은 방화벽 차단뿐 아니라 실제 콘텐츠를 제공하는 오리진에서도 나옵니다. 없는 키를 요청하거나 버킷 정책에 거부돼도 403이어서, 상태 코드만으로는 원인을 구분할 수 없었어요.

차단 문구를 쓰려면 실제 차단 응답 설정을 먼저 확인해야 해요. 기본 응답의 문구는 커스텀 응답을 설정하면 바뀔 수 있고, 정상 화면과 비슷한 HTML을 내보낸다면 본문으로 구분하기도 어렵습니다. 이번에는 기본 응답이어서 그 문구를 판별 기준으로 썼어요.

삭제 대상 39개의 연결 수가 모두 0이라는 사실도 함께 확인했어요. 삭제 후에도 연결된 ACL은 5종류이고 연결 수 합계는 46으로 삭제 전과 같았습니다. 102회 응답 검사와 이 연결 집계를 함께 근거로 삼았어요.

🔍 삭제 후 응답과 연결 집계를 함께 확인하기
배포 51개 각각의 기본 도메인과 별칭 도메인에 요청을 보내 총 102회 응답을 확인했어요. 상태 코드만으로 차단 원인을 정하지 않고, 실제 차단 응답 설정에 맞는 본문 문구를 검사했습니다. 삭제 후 연결 집계도 삭제 전과 대조했어요.
그림 3. 전수 응답과 차단 문구를 함께 확인해 403의 원인을 구분했다

6. 화면은 표시되지만 403인 배포도 확인했다

전수 확인에서는 방화벽과 무관한 응답도 나왔어요. 활성 배포의 루트 경로 중 403이 아홉 개, 404가 다섯 개였습니다. 처음 표본에서 본 403도 이 분포에 포함돼 있었어요.

그중 한 배포에서 요청 경로별 응답을 비교했어요.

/ 403 그런데 본문은 정상 화면의 HTML 이다 /index.html 200 /favicon.ico 200

다음 세 설정이 함께 작용하고 있었습니다.

1. default_root_object 가 "/index.html" 이다 앞에 슬래시가 붙어 있다 -> 루트 요청이 오리진에서 없는 키를 찾는다 2. 프론트 버킷에 s3:ListBucket 권한이 없다 -> 없는 키의 응답이 404 가 아니라 403 이 된다 3. 이 배포의 custom_error_response 가 403 을 403 으로 내보낸다 -> 오리진의 403 이 상태 코드 그대로 사용자에게 나간다

세 번째인 오류 응답 설정은 배포마다 달랐어요. 어드민 배포와 dev 배포는 403을 200으로 바꾸도록 설정돼 있어 같은 원인에도 정상 상태 코드로 응답했습니다. 화면만 확인하면 이 차이를 알아차리기 어려웠어요.

확인한 배포는 정상 화면의 HTML을 본문에 담으면서 상태 코드는 403을 반환했어요. 브라우저에는 화면이 표시돼도 상태 코드를 기준으로 판단하는 도구는 다르게 처리할 수 있습니다.

사람 화면이 보인다 -> 아무도 신고하지 않는다 크롤러 4xx 로 읽는다 -> 색인에서 뺀다 업타임 실패로 읽는다 -> 가동률 지표가 깎인다 헬스체크 비정상으로 읽는다 -> 경로에 따라 트래픽을 끊는다

앞서 DNS 문제로 15개월간 503을 반환했지만 신고가 없었던 사례도 있었어요. 화면 표시나 사용자 신고 여부만으로 정상 동작을 판단하기 어렵다는 점에서 함께 볼 수 있는 사례였습니다.

이 현상은 방화벽 삭제로 생긴 것이 아니었어요. 비용 과제에서는 서비스 동작을 바꾸지 않기로 했으므로 이번 작업에서 수정하지 않고 별건으로 남겼습니다. 배포 51개 전체의 응답을 모으면서 여러 배포에 걸친 패턴이라는 점까지 확인할 수 있었어요.

✍️ 작업 결과와 남은 확인
삭제 후보 39개는 전체 44개에서 유지 5개를 뺀 값이었어요. 연결 조회는 배포 51개 전부를 null로 읽고 있었고, 공용 ACL에 배포가 연결돼 있어야 한다는 조건을 대조해 오류를 찾았습니다.

삭제 후에도 데이터가 없는 지표 조회를 차단 0으로 해석했어요. 이 결과는 근거에서 빼고 배포 51개에 두 경로로 요청을 보내 102회 응답을 확인했습니다. 차단 문구는 나오지 않았고, 연결된 ACL 5종류와 연결 수 합계 46도 삭제 전과 같았어요.

당시 가드는 1회성 판정 스크립트에 있었습니다. 다음 삭제에도 같은 조건을 확인하도록 절차에 반영하는 일은 남아 있었어요.
