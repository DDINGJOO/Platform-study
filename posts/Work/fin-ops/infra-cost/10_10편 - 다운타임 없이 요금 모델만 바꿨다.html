10편. Aurora I/O-Optimized를 Standard로 전환하기 전 확인한 비용과 원복 제약 ← 지금 이 글

요금 모델 필드 하나를 바꾸자 클러스터 목록의 상태가 잠깐 「수정 중」으로 바뀌었다가 「사용 가능」으로 돌아왔어요. 인스턴스 재시작은 없었고, 확인한 범위에서 앱 커넥션이 끊긴 흔적도 없었어요.

인스턴스 클래스와 대수, 스토리지는 그대로였어요. 자원을 줄이지 않고 요금 모델만 전환한 작업이었어요.

8편에서는 사용 패턴에 맞지 않는 최적화 상품이 오히려 비용을 늘릴 수 있다는 점을 다뤘어요. 이번에는 실제 입출력량과 청구 단가를 확인한 뒤 Standard로 전환했어요. 전환은 몇 분이었지만, 전환 근거를 확인하는 데는 그보다 오래 걸렸어요.

1. 클러스터 일곱 개의 요금 모델을 비교했어요

이 항목은 지표를 분석하다가 발견한 것이 아니었어요. 같은 종류의 자원 설정을 나란히 놓고 비교하다가 찾았어요.

DB 클러스터 일곱 개에서 스토리지 요금 모델을 지정하는 필드를 조회했어요.

클러스터별 StorageType 조회 클러스터 A aurora 클러스터 B aurora 클러스터 C aurora 클러스터 D aurora 클러스터 E aurora 클러스터 F aurora 클러스터 G aurora-iopt1 ← 혼자 다르다

여섯 개와 달리 한 클러스터만 I/O-Optimized를 쓰고 있었어요. 다른 설정을 쓸 이유가 있을 수 있으니, 곧바로 바꾸기보다 사용량에 맞는 선택인지 확인하기로 했어요.

인스턴스 클래스나 대수, 엔드포인트만 봐서는 요금 모델의 차이를 알기 어려웠어요. 청구서에서도 인스턴스 요금 항목의 단가 차이로 나타났고요. 클러스터별 요금 모델 필드를 모아 보니 차이가 분명해졌어요.

설정이 다르다는 사실만으로 비용이 낭비되고 있다고 판단할 수는 없어요. 입출력이 많은 클러스터라면 I/O-Optimized가 유리할 수 있어서, 다음으로 손익분기를 계산했어요.

2. 당시 손익분기 계산에는 스토리지 차액이 빠져 있었어요

당시 비교한 I/O-Optimized는 입출력 요금을 따로 내지 않는 대신 인스턴스 요금이 약 30% 높았어요. 총비용에서 유리하려면 절약하는 입출력 비용이 인스턴스와 스토리지 요금 증가분의 합보다 커야 해요.

당시에는 인스턴스 요금 증가분과 입출력 비용이 같아지는 지점을 손익분기로 잡았어요. 아래는 그 불완전한 계산을 보존한 것이에요. 스토리지 요금 차이를 빠뜨렸으므로 수백 배라는 값을 총비용 손익분기로 읽으면 안 돼요.

이 상품이 이득이 되는 조건 없어지는 입출력 과금 > 늘어나는 인스턴스 요금 (약 30%) 이 클러스터의 실측 실제 입출력량 : 손익분기 입출력량 = 1 : 수백 → 입출력이 수백 배 늘어나야 비로소 이득이 생긴다 다른 클러스터들 (전환 후보로 검토한 쪽) 입출력 비용 / 인스턴스 비용 < 0.1% → 없어질 비용이 거의 없고 인스턴스 요금만 오른다

당시 계산은 인스턴스 요금 증가분만으로도 입출력 절약액보다 크다고 본 비교였어요. 다만 당시 저장량과 원 계산을 확보하지 못해 스토리지를 포함한 총비용 기준의 정확한 배수는 재검증하지 못했어요.

다른 클러스터에도 같은 계산을 적용했어요. 입출력 비용이 인스턴스 비용의 0.1% 미만이라 I/O-Optimized로 바꾸면 비용이 늘어나는 것으로 나왔어요. 이미 쓰던 한 곳은 Standard로 전환하고, 나머지는 기존 모델을 유지하기로 했어요.

그림 1. 당시 계산은 스토리지 요금 차이를 빠뜨린 인스턴스·I/O 비교였어요

3. 청구 금액을 시간당 단가로 역산했어요

손익분기를 계산한 뒤에는 청구 단가를 확인했어요. 전환에 따른 절감 예상액과 현재 실제로 청구되는 요금이 일치하는지 따로 대조할 필요가 있었어요.

3편에서는 계산으로 구한 값과 측정값을 구분하지 않아 판단을 잘못했어요. 이번에는 청구 항목 금액을 실제 조회 기간의 시간 수로 나눠 시간당 단가를 구하고, 같은 인스턴스 클래스의 정가표와 비교했어요.

청구 항목 금액 ÷ 조회 기간의 시간 수 = 시간당 단가 ↓ 정가표와 대조 그 인스턴스 클래스의 I/O-Optimized 정가 와 일치 ✓ 같은 클래스의 Standard 정가 이 차이가 절감액 주의: 조회 기간은 「한 달」이 아니라 실제 조회된 일수다 (2편)

역산한 단가는 I/O-Optimized 정가와 일치했어요. 해당 청구 항목이 최적화 상품 단가로 매겨지고 있음을 확인하고, Standard 정가와의 차이를 인스턴스 요금 절감 예상치로 잡았어요.

이 대조로 확인한 것은 현재 청구 단가예요. 전환 후 총청구액이 정가 차이만큼 줄었다고 확인한 것은 아니에요. 당시에는 별도 입출력 비용까지 비교했지만 스토리지 요금 차이를 빠뜨렸어요. 총비용 절감액은 세 항목을 함께 계산해야 해요.

2편에서 부분월 청구를 확인할 때도 같은 방식으로 역산했어요. 그때는 금액과 단가로 조회 기간을 확인했고, 이번에는 금액과 조회 기간으로 단가를 구해 적용된 요금 모델을 확인했어요.

4. 전환 후 상태와 변경 범위를 확인했어요

전환은 필드 값을 aurora-iopt1에서 aurora로 바꾸는 작업이었어요.

이번 변경은 온라인으로 적용됐어요. 인스턴스 재시작과 다운타임은 없었고, 엔드포인트와 인스턴스 클래스, 파라미터그룹도 그대로였어요. 커넥션이 끊긴 흔적도 확인되지 않았어요.

이 결과를 모든 인스턴스 계열에 적용할 수는 없어요. 당시 확인한 공식 문서에는 로컬 저장장치를 함께 쓰는 계열에서 같은 전환에 엔진 재시작과 짧은 중단이 필요하다고 되어 있었어요. 이번 클러스터는 그 계열에 해당하지 않았어요.

변경 범위가 작더라도 적용 결과는 확인했어요. 예상한 동작과 실제 결과를 구분하기 위해 아래 항목을 남겼어요.

전환 후 확인한 것 StorageType aurora-iopt1 → aurora 실제로 바뀌었는지 클러스터 상태 available 로 복귀 인스턴스 재시작 없음 이벤트 목록으로 확인 엔드포인트 변경 없음 커넥션 끊긴 흔적 없음 인스턴스 클래스 변경 없음 파라미터그룹 변경 없음 다운타임 없음

StorageType이 바뀌고 클러스터가 available 상태로 돌아왔는지 확인했어요. 이벤트 목록에서는 재시작 여부를 봤고, 나머지 항목은 변경 전후에 차이가 없는지 확인했어요. 이 기록은 이후 문제가 생겼을 때 이번 변경의 범위를 확인하는 데 쓸 수 있어요.

별도의 성능 검증은 하지 않았어요. 당시 비교한 두 상품의 스펙 표에서 차이를 확인한 항목은 요금이었고, 클래스나 파라미터그룹도 바꾸지 않았어요. 성능이 같다는 것을 부하 테스트로 입증한 결과는 아니라는 점은 구분해야 해요.

📄 가격 대비 성능과 실제 성능 변화를 구분했어요
당시 공식 문서의 「가격 대비 성능 향상」이라는 표현을 처음에는 성능 자체가 오른다는 뜻으로 읽었어요. 입출력이 많은 워크로드에서 같은 성능을 더 낮은 비용으로 쓸 수 있다는 설명과는 구분해야 했어요.

처리량 증가와 지연 감소를 설명한 문구도 있었지만, 당시 확인한 내용은 특정 인스턴스 계열의 별도 읽기 최적화 기능에 관한 것이었어요. 요금 모델 필드만 바꿨을 때의 효과로 적용하지 않았어요.

이번에는 상품의 요금 차이와 변경한 설정 범위를 비교했어요. 성능 벤치마크를 실행하지 않았으므로 전환 전후 성능 수치를 제시하지는 않아요.

5. 원복에는 최대 30일 대기 제약이 있었어요

전환 제약도 확인했어요. Standard와 I/O-Optimized 사이의 변경 주기는 방향에 따라 달랐어요.

방향 이 방향으로 갈 때 Standard → I/O-Optimized 30일에 한 번만 된다 (최대 30일 대기) I/O-Optimized → Standard 언제든 된다 (즉시) 우리가 간 방향은 아래쪽이다. 즉 가는 길이 즉시이고, 되돌아오는 길이 위쪽 = 최대 30일 대기다.

I/O-Optimized에서 Standard로 바꾸는 것은 즉시 가능했지만, 다시 I/O-Optimized로 바꾸려면 최대 30일을 기다릴 수 있었어요. 이번 변경은 적용보다 원복에 제약이 있는 쪽이었어요.

그래서 원복이 필요할 상황을 먼저 검토했어요. 입출력이 크게 늘어나 I/O-Optimized가 더 저렴해지는 경우였어요. 당시 단순 계산에서는 수백 배 증가가 필요하다고 봤어요. 하지만 스토리지 차액을 빠뜨린 비교였으므로 그 배수를 정확한 원복 판단선으로 쓸 수는 없어요. 당시에는 예상 증가 폭을 근거로 전환을 선택했다고 남겼어요.

7편에서는 되돌릴 수 있는 작업부터 진행한다고 정했어요. 이번에는 원복 가능 여부에 더해, 원복까지 기다려야 하는 기간도 판단에 포함했어요.

기존 모델을 유지하면 인스턴스 요금 증가분을 계속 내야 했어요. 반대로 전환 후 입출력이 크게 늘어나 다시 최적화 모델이 유리해져도 즉시 원복하지 못할 수 있었고요. 당시 사용량과 예상 증가 폭을 비교한 뒤 Standard로 전환하기로 했어요.

I/O-Optimized로 전환하는 방향에 30일 제약이 있으므로 요금 모델을 수시로 바꾸는 운영에는 제한이 있어요. 당장 측정된 입출력량뿐 아니라, 제약 기간에 사용량이 얼마나 달라질 수 있는지도 함께 봐야 했어요.

6. 과금 단위가 자원 개수가 아닐 때

이 밖에도 자원 개수만으로 절감액을 계산하기 어려운 항목이 세 가지 있었어요. 각각 무엇을 기준으로 과금하는지 확인했어요.

사용자 단위로 과금되는 것

쓰지 않는 관리형 대시보드 워크스페이스를 삭제했어요. 이 항목은 워크스페이스 수보다 활성 사용자 수가 요금을 결정했고, 편집자와 뷰어의 단가도 달랐어요.

Amazon Managed Grafana는 활성 사용자 기준 과금과 별개로 워크스페이스마다 최소 Editor 라이선스 하나가 필요해요. 로그인한 사용자가 없다고 요금이 0이 되는 것은 아니에요. 당시에는 남은 편집자 한 명분으로 비용을 설명했지만, 최소 라이선스와 실제 청구 내역을 분리한 원본은 확보하지 못했어요. 따라서 그 사용자 때문에만 요금이 생겼다거나 삭제 절감액을 직접 검증했다고 볼 수는 없어요.

공유 조건에 따라 최소 과금이 유지되는 것

서버리스 검색 인덱스는 컬렉션이 세 개였어요. 당시에는 세 컬렉션이 같은 OCU 최소 과금 풀을 공유한다고 계산했어요. 공유는 유형과 KMS 키 같은 조건에 따라 달라지고, 당시 공유 구성을 대조할 원본은 확보하지 못했어요. 둘만 지울 때 절감이 거의 없다는 산정도 이 미확인 전제에 의존해요. 삭제 과정은 7편에서 다뤘어요.

떼어낸 뒤에도 과금이 남는 것

네트워크 자원을 정리할 때는 연결된 고정 IP도 함께 반납해야 했어요.

저는 고정 IP가 자원에 연결된 동안에는 무료이고 분리하면 요금이 붙는 것으로 알고 있었어요. 하지만 작업 당시 공용 IPv4 주소는 연결 여부와 무관하게 시간당 과금되고 있었어요. 연결된 주소도 이미 비용에 포함돼 있었어요.

자원을 지우고 IP를 남겨두면 기존 IP 요금이 계속 나와요. 그래서 자원 삭제와 IP 반납을 함께 확인해야 했어요. 예전 규칙을 그대로 적용하면 연결된 IP를 비용 계산에서 빠뜨릴 수 있었어요.

그림 2. 사용자 수, 최소 처리 단위, IP 사용 시간으로 과금돼요
🧾 절감액을 계산하기 전에 확인한 항목
과금 기준이 자원 수인지, 사용자 수인지, 처리 단위인지, 사용 시간인지 확인했어요. 자원 개수가 기준이 아니면 삭제 비율만으로 절감액을 계산할 수 없어요.

삭제 뒤에도 남는 요금이 있는지도 확인했어요. 연결된 IP가 별도로 과금되는 경우에는 그 주소까지 반납해야 했어요. 8편에서 스냅샷을 검토할 때도 개수만으로 절감액을 판단하지 않았어요.

요금 모델 전환은 운영 중인 인스턴스의 용량과 클래스를 유지한 채 진행했어요. 대시보드와 검색 항목은 사용하지 않는 자원을 삭제한 것이므로, 이 작업들을 모두 자원 변경이 없는 작업으로 묶을 수는 없어요.

요금 모델 전환에도 원복 주기와 인스턴스 계열별 재시작 여부를 확인하는 과정이 필요했어요. 삭제 항목은 과금 단위와 함께 남는 자원을 따로 확인해야 했고요.

이런 항목은 운영 자원의 사이징을 바꾸기 전에 검토할 만했어요. 다만 예상 절감액만으로 순서를 정하기보다, 사용 여부와 변경 범위, 원복 제약까지 확인한 뒤 실행 순서를 정하는 편이 적절했어요.

✍️ 정리
Aurora 클러스터 일곱 개의 요금 모델을 비교해 하나만 I/O-Optimized를 쓰는 것을 찾았어요. 당시 인스턴스·I/O 비교에서는 입출력량이 계산상 손익분기의 수백 분의 일이었지만 스토리지 차액은 빠져 있었어요. 총비용 기준의 배수는 재검증하지 못했고, 청구 금액을 시간당 단가로 역산해 적용된 요금 모델을 확인했어요.

Standard 전환 뒤에는 상태와 이벤트, 커넥션 등을 확인했어요. 이번 인스턴스 계열에서는 재시작과 다운타임이 없었지만 모든 계열에 같은 결과를 적용할 수는 없어요. 별도의 성능 검증은 하지 않았고, 원복에는 최대 30일 대기 제약이 있다는 점을 검토했어요.

대시보드 사용자, 검색 처리 단위, 고정 IP도 각각의 과금 기준을 확인했어요. 자원 개수나 삭제 개수만으로 절감액을 계산하지 않고, 삭제 후 남는 비용까지 확인하는 데 초점을 뒀어요.
