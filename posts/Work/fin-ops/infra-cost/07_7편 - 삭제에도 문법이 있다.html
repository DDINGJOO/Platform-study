확정 목록에 올려둔 개발용 로드밸런서 하나에 삭제 명령을 실행했어요. 타깃은 없었고, 30일 RequestCount 조회에는 데이터가 없었어요. 이를 요청 0으로 취급하지 않고 DNS와 리스너 등 연결 경로를 추가 확인한 상태였어요. 타깃 선택 전에 거절된 요청은 이 지표에 포함되지 않으므로 실제 유입 부재까지 확인한 것은 아니에요.

그런데 ResourceInUse 오류로 거부됐어요. 뒤에는 "이 자원은 하나 이상의 타깃그룹에 타깃으로 등록되어 있으므로 삭제할 수 없습니다."라는 설명이 붙어 있었어요.

등록이 남아 있다는 설명을 보고 사용 여부를 다시 확인해야 할지 망설였어요. 앞서 미사용으로 판단했지만, 그 등록 관계가 실제 트래픽을 전달하는지는 따로 확인해야 했어요.

그날은 로드밸런서, NAT 게이트웨이, 사용이 끝난 서비스의 잔재 열한 종, 검색 인덱스, 이미지와 스냅샷을 정리했어요. 자원마다 참조 관계를 해제하는 순서가 달랐고, 알람과 코드도 먼저 정리해야 했어요. 완료로 적은 항목 중에는 나중에 삭제되지 않은 것으로 확인된 것도 있었어요.

1. ResourceInUse가 발생한 참조 관계 확인하기

이번 오류는 실제 사용 여부와 별개로, 남아 있는 타깃 등록 때문에 발생한 삭제 순서 제약이었어요.

어떤 타깃그룹이 이 로드밸런서를 타깃으로 등록해두고 있었어요. 하지만 그 타깃그룹을 쓰던 상위 로드밸런서는 이미 삭제됐고, 연결 목록도 비어 있었어요. 트래픽이 전달될 경로 없이 등록 관계만 남은 상태였어요.

AWS는 등록이 남아 있는 동안 로드밸런서 삭제를 거부해요. 오류 문장에도 삭제 전에 모든 타깃그룹에서 등록을 해제하라고 적혀 있었어요.

받은 오류 ResourceInUse: 이 자원은 하나 이상의 타깃그룹에 타깃으로 등록되어 있으므로 삭제할 수 없습니다. 삭제하려면 모든 타깃그룹에서 등록을 먼저 해제해야 합니다. 내가 읽은 것 "누가 쓰고 있다" -> 멈춘다 실제 의미 "앞의 것을 먼저 지워라" -> 순서를 바꾼다 delete-target-group // 상위가 없는 고아 타깃그룹. 바로 지워진다 -> delete-load-balancer // 등록이 사라졌으므로 이제 지워진다

등록만 해제할 수도 있었지만, 그 타깃그룹을 남길 이유가 없어 타깃그룹 자체를 지웠어요. 등록도 함께 없어졌고, 그다음 로드밸런서 삭제가 성공했어요.

다른 작업에서도 참조 관계 때문에 삭제가 거부됐어요. 방화벽 규칙 묶음에 배포가 연결돼 있으면 WAFAssociatedItemException이 발생했고, 컨테이너 클러스터도 용량 공급자를 먼저 분리해야 했어요. 삭제할 자원을 참조하는 쪽부터 확인해야 했어요.

이 오류로 알 수 있는 건 참조가 남아 있다는 점까지예요. 실제 트래픽을 전달하는 참조인지, 상위 자원이 사라진 뒤 남은 참조인지는 구분해주지 않아요. 그래서 타깃그룹의 연결 목록과 상위 자원의 존재 여부를 직접 확인했어요.

작업 문서의 선행 조건을 잘못 읽었어요

작업 문서의 비고에는 이미 "상위 로드밸런서 타깃 등록 해제 선행"이라고 적혀 있었어요. 읽었지만 그 의미를 잘못 이해해 순서를 지키지 않았어요.

저는 그 문장을 보고 해당 경로가 필요해서 의도적으로 구성해둔 것으로 받아들였어요. 이름에 외부 연동을 시사하는 문자열이 있었고, 그 서비스의 이미지 저장소는 남기기로 한 상태였어요. 다시 배포할 가능성이 있다면 로드밸런서도 필요할 수 있다고 생각해 삭제를 한 번 보류했어요.

그래서 진입 경로를 확인했어요. 이 로드밸런서를 타깃으로 가진 타깃그룹은 하나였고 연결 목록은 비어 있었어요. 전체 호스팅 영역에 DNS 레코드가 없었고, 리스너는 평문 하나에 기본 액션이 가리키는 타깃그룹도 없었어요. 알람과 코드 참조도 찾지 못했어요.

세 가지 우려를 해소한 뒤 삭제를 다시 시도했고, 그때 오류를 만났어요. 비고에 적힌 한 줄을 설계 의도로 읽었지만, 실제로는 삭제 API의 선행 조건이었어요.

비고: "상위 로드밸런서 타깃 등록 해제 선행" 설계 의도로 읽으면 누군가 이 경로를 만들었다 -> 삭제를 보류한다 API 제약으로 읽으면 지우는 순서가 이렇다 -> 순서대로 지운다 판단이 정반대로 갈린다. 그런데 확인하는 데 걸린 시간은 조회 한 번이었다.

이후에는 비고에 선행 조건이 있으면 그 이유를 함께 확인하기로 했어요. 이번에는 조회 한 번으로 등록 관계를 확인할 수 있었어요. 그 관계가 현재도 필요한지와, 삭제하려면 무엇을 먼저 해야 하는지를 구분해야 했어요.

그림 1. 등록이 남아 있다는 오류만으로는 실제 사용 여부를 구분할 수 없어요

2. 자원보다 알람을 먼저 제거해야 하는 이유

자원을 지우기 전에는 알람 코드부터 정리했어요. 감시 대상을 먼저 지우면 Terraform 변경 계획인 plan이 실패하거나, 지표가 끊긴 알람이 계속 경보 상태에 남을 수 있었어요. 둘 다 과거 작업에서 겪은 문제였어요.

데이터소스 조회 실패로 스택 전체의 plan이 막혀요

알람 코드는 감시 대상을 data 소스로 조회했어요. 데이터소스는 이미 존재하는 자원의 정보를 읽어오는 설정이에요. 로드밸런서 지표 차원에는 이름 뒤에 무작위 16진수 접미사가 붙는데, 이를 잘못 옮기면 알람이 지표를 받지 못해요. 그래서 이름만 목록으로 관리하고 접미사는 조회하도록 구성했어요.

대상이 사라지면 데이터소스 조회가 실패하고 plan도 실패해요. 감시 대상이 목록에서 조용히 빠지는 것보다 오류로 확인하는 편이 낫다고 판단한 설계였어요. 그만큼 실제 자원보다 알람 코드를 먼저 정리해야 했어요.

과거에 로드밸런서 하나를 코드보다 먼저 지웠을 때, 그 자원과 관계없는 PR 둘의 plan도 함께 실패했어요. 두 PR 모두 같은 Terraform 스택을 변경하고 있어서 영향을 받았어요.

지표가 끊긴 알람이 경보 상태로 남아요

알람에는 지표가 들어오지 않을 때 판정하는 방식도 설정돼 있어요. missing_data 설정으로 결측을 위반으로 볼지, 정상으로 볼지, 판정을 보류할지 정해요.

결측을 위반으로 취급하면 감시 대상이 사라진 뒤에도 경보 상태가 이어져요. 대상이 없으니 정상 지표가 다시 들어오지 않기 때문이에요. 이런 알람은 대상 삭제에 맞춰 함께 정리해야 해요.

자동 확장 그룹의 인스턴스 수를 보는 일부 알람은 의도적으로 결측을 위반으로 처리했어요. 지표 수집이 중단되거나 그룹이 사라진 상황을 알아야 했기 때문이에요. 이 설정을 유지하면서 자원을 삭제하려면 알람을 먼저 제거해야 했어요.

매일 실행하는 알람 커버리지 검사도 고려했어요. 코드에 정의돼 있지만 실제 대상이 없는 항목을 찾는 검사예요. 실제 자원만 먼저 지우면 이후 검사에서 계속 불일치가 보고되므로 코드와 함께 정리해야 했어요.

그래서 순서가 이렇게 고정된다 1. 코드에서 알람을 제거한다 (PR 하나. 다른 변경을 섞지 않는다) 2. apply plan 기대값과 실제를 대조한다 3. 알람 0건 확인 지운 자원의 접두사로 조회한다 4. 남아야 하는 알람 생존 확인 옆 자원의 알람까지 지우지 않았나 5. 실물 삭제 6. 삭제 확인 + 그 자원을 쓰던 것들이 정상인지 확인 4번을 빠뜨리기 쉽다. 목록에서 한 줄 지울 때 옆 줄이 같이 지워지는 일이 실제로 일어나고, 그건 알람 0건 확인으로는 잡히지 않는다.

2번 단계에서는 예상한 삭제 다섯 건과 실제 plan의 네 건이 달랐어요. 목록을 for_each로 펼치는 곳이 두 군데라 둘 다 알람으로 셌는데, 하나는 module이 아닌 data 소스였어요. 데이터소스는 관리 리소스 삭제 건수에 포함되지 않아요. for_each 개수뿐 아니라 대상이 module인지 data인지도 봐야 했어요.

예상보다 삭제가 적다는 이유만으로 안전하다고 판단할 수는 없었어요. 대상을 잘못 골랐을 수도 있으니까요. 이번에는 데이터소스를 삭제 건수에 포함한 것이 원인임을 확인한 뒤 apply를 진행했어요.

3. 참조를 해제한 뒤 자원 삭제하기

알람을 제거한 다음에도 자원 사이의 참조를 따라 순서를 정했어요. 참조를 먼저 해제하거나, 참조하는 자원을 먼저 지웠어요.

그날은 다음 세 가지 관계를 확인했어요.

검색 인덱스와 상위 지식 베이스. 지식 베이스가 인덱스 컬렉션을 참조하고 있어 상위 지식 베이스부터 지웠어요. 컬렉션부터 지우면 참조 대상이 없는 지식 베이스가 남고, 삭제 요청도 오류로 거부되는 문제가 있었어요.

DNS 레코드와 로드밸런서. 여기서는 API 제약보다 접속 경로를 고려했어요. 로드밸런서부터 지우면 DNS 레코드가 더 이상 존재하지 않는 대상을 가리키게 돼요. 그래서 레코드를 먼저 지웠어요.

정리 대상 중에는 이미 그런 상태인 서비스도 있었어요. DNS 레코드는 남아 있고 로드밸런서에 타깃이 없어 접속하면 오류 응답이 돌아왔어요. 삭제하면서도 유효하지 않은 접속 경로가 남지 않도록 순서를 정했어요.

컨테이너 클러스터와 용량 공급자. 용량 공급자는 이 구성에서 ECS 클러스터와 자동 확장 그룹의 실행 용량을 연결하는 설정이에요. 먼저 서비스의 희망 실행 수를 0으로 내리고 태스크 종료를 확인한 뒤, 서비스의 용량 공급자 참조와 서비스 정의를 정리해야 해요. 등록된 컨테이너 인스턴스도 정리해야 클러스터를 삭제할 수 있어요. 그 뒤 클러스터에서 공급자 연결을 분리하고, 공급자 자체와 자동 확장 그룹, 시작 템플릿, 클러스터를 지우는 순서예요. 연결 분리와 공급자 삭제는 별도 작업이며, 아래 표는 서비스 정리 후 기반 자원의 순서를 요약한 것이에요. 공급자 분리부터 시작 템플릿까지의 네 단계는 알람 파일 주석에 이미 적혀 있었어요. 이전에 비슷한 자원을 정리하며 남긴 순서를 따랐어요.

사용이 끝난 어떤 서비스의 잔재 열한 종을 지운 순서 코드에서 알람 제거 -> apply // 알람 넷이 사라진다 -> DNS 레코드 // 로드밸런서보다 먼저. 죽은 구간을 안 만든다 -> 로드밸런서 // 운영·개발 각 하나 -> 타깃그룹 -> 클러스터에서 용량 공급자 떼기 -> 용량 공급자 -> 자동 확장 그룹 -> 시작 템플릿 -> 컨테이너 클러스터 -> 이미지 저장소 · 배포용 버킷 // 참조하는 것이 다 사라진 뒤 마지막에 로드밸런서 · 클러스터 · 확장 그룹 · 저장소 · 버킷 조회가 전부 0 으로 나오는 것까지 확인한다.

이 목록에서 직접 절감으로 이어지는 건 로드밸런서 둘과 이미지 저장소 둘이었어요. 확장 그룹, 클러스터, 시작 템플릿, 타깃그룹 자체에는 과금이 없었어요. 이 항목들은 남은 참조와 운영상 혼동을 정리하려고 함께 삭제 대상으로 잡았어요.

목록 조회만으로 남은 클러스터를 놓쳤어요

이후 별건 목록을 다시 확인하다가 컨테이너 클러스터 하나가 남아 있는 걸 발견했어요. 작업 기록에는 삭제 완료로 적혀 있던 항목이었어요.

그 클러스터에는 서비스 정의 하나가 실행 수 0인 채로 활성 상태로 남아 있었어요. 실행 중인 태스크는 없었지만 서비스 정의가 남아 있어 클러스터 삭제가 거부됐어요.

마지막 확인을 목록 조회 결과가 0인지로만 한 게 문제였어요. 0을 보고 완료로 적었지만 실제 자원은 남아 있었어요. 과금이 없는 자원이라 청구서에서도 발견할 수 없었고요. 조회 결과가 비어 있다는 것과 삭제 대상이 없어졌다는 것은 별도로 확인해야 했어요.

그래서 삭제 완료를 기록하기 전에 자원 이름으로 직접 조회하는 절차를 추가했어요. 목록 조회의 필터 때문에 누락된 자원이 없는지 확인하려는 목적이었어요.

그림 2. 삭제 순서에 따라 조회 실패, 경보, 연결 오류가 생길 수 있어요

4. 관리 주체에 맞는 삭제 API 사용하기

이미지와 스냅샷을 정리할 때는 관리 주체 때문에 삭제가 거부됐어요. 오래된 이미지 하나를 등록 해제하려고 하자 다음 오류가 나왔어요.

AuthFailure: 이 이미지는 백업 서비스가 관리하고 있으며 EC2 API 로 삭제할 수 없습니다. 삭제하려면 백업 서비스의 API 나 CLI 또는 콘솔을 사용하세요. deregister-image -> 거부 delete-recovery-point -> 볼트 이름과 복구지점 식별자를 넘긴다

그 이미지는 백업 계획이 만든 복구지점으로, 백업 서비스가 관리하고 있었어요. 같은 계정과 리전에 있는 이미지여도 EC2 API 대신 관리 주체인 백업 서비스의 API를 사용해야 했어요.

오류 이름은 AuthFailure여서 권한 문제로 읽기 쉬웠어요. 하지만 이번 오류의 설명은 백업 API를 사용하라는 것이었어요. 역할에 권한을 추가하기 전에 오류 본문에서 관리 주체와 사용할 API를 확인해야 했어요.

백업 계획 자체는 이미 삭제됐지만 복구지점 다섯 개는 남아 용량을 차지하고 있었어요. 상위 설정을 지운 뒤에도 그 설정이 만든 자원이 남아 있는지 별도로 확인해야 했어요.

이미지를 지울 때는 두 곳을 본다

이미지 삭제 전에는 런북도 확인했어요. "이미지가 삭제됨 → 시작 템플릿 이전 버전으로 되돌림"이라는 복구 절차가 적혀 있었어요. 삭제 후보를 고를 때 복구에 필요한 이미지도 고려해야 한다는 근거였어요.

시작 템플릿이 참조하는 이미지를 지우면 자동 확장 그룹이 새 인스턴스를 띄우지 못해요. 시작 템플릿에는 여러 버전이 있으므로 최신 버전만 확인해서는 부족했어요. 이전 버전으로 되돌릴 때 필요한 이미지까지 확인했어요.

🔎 이미지 삭제 전에 확인한 두 목록
• 목록 하나: 시작 템플릿의 모든 버전이 참조하는 이미지. 이전 버전으로 되돌릴 때 필요한 이미지도 확인해요
• 목록 둘: 실행 중과 정지 중 인스턴스가 쓰는 이미지. 정지 중인 인스턴스도 목록에 포함해요
• 둘 다에 없는 것만 삭제 대상이에요
이 확인으로 삭제 후보 하나를 제외했어요. 시작 템플릿 조회에서는 찾지 못했지만 실행 중인 인스턴스가 쓰던 이미지였어요. 참조가 없어도 다른 이미지의 기반으로 보여 판단을 보류한 항목도 있었어요.

실제로 지운 것은 다시 받을 수 있는 공용 이미지의 복사본, 참조가 없는 오래된 이미지, 남아 있던 복구지점 다섯 개와 연결되지 않은 볼륨 하나였어요. 자동 보존 정책이 만드는 스냅샷은 남겼어요. 보존 기간이 닷새와 이레로 이미 짧아 더 줄이면 복구 가능한 기간도 짧아지기 때문이에요.

5. 청구 내역과 조회 API의 범위 확인하기

검색 서비스는 삭제 대상을 찾는 데 시간이 걸렸어요.

청구서에는 검색 서비스 요금이 있었지만 도메인 목록 조회 결과는 0개였어요. 다른 리전에서도 찾지 못했어요. 청구 내역과 조회 결과가 맞지 않아 조회 범위를 다시 확인했어요.

기존 도메인 방식과 서버리스 방식의 조회 API가 달랐어요. 서버리스 자원은 기존 도메인 조회 API에 나오지 않았어요. 서버리스 컬렉션을 조회하자 세 개가 나왔어요.

💡 청구는 있는데 자원이 안 보일 때
• 먼저 다른 리전에 자원이 있는지 확인해요
• 같은 서비스라도 도메인 방식과 서버리스 방식의 조회 API가 다른지 확인해요
• 3편에서처럼 조회 결과를 다른 관측과 대조해요. 여기서는 청구가 계속 발생한다는 점과 맞지 않았어요
조회 결과가 0이어도 API와 필터가 대상을 포함하는지 확인해야 해요.

상위 지식 베이스가 사라진 컬렉션 하나가 남았어요

컬렉션은 셋이고 상위 지식 베이스는 둘이었어요. 상위 지식 베이스가 삭제된 뒤 컬렉션 하나만 남아 있었고, 열한 달 동안 과금된 상태였어요.

그 컬렉션으로 접근하던 상위 지식 베이스가 없어 기존 사용 경로가 끊겨 있었어요. 도메인 목록만 확인해서는 남은 컬렉션을 찾을 수 없었고요. 사용 경로가 사라진 뒤에도 컬렉션 요금은 계속 발생하고 있었어요.

부분 삭제의 절감액은 최소 과금 풀 공유 여부에 달려 있어요

일부만 남길지도 검토했지만, 당시 계산은 컬렉션 셋이 같은 최소 처리 용량 과금 풀을 공유한다는 전제였어요. 처리 단위인 OCU의 공유 여부는 컬렉션 유형과 KMS 키 같은 조건에 따라 달라져요. 그 공유 구성을 직접 대조할 당시 원본은 확보하지 못했어요.

같은 최소 과금 풀을 공유했다면 하나를 남겨도 최소 처리 단위가 유지돼, 둘만 삭제할 때의 절감은 작을 수 있어요. 청구액이 거의 그대로였다는 당시 산정은 공유 전제를 확인하지 못해 재검증하지 못했어요. 해당 항목의 과금을 없애려면 전부 삭제할 수 있는지 확인해야 했어요.

그래서 일부 컬렉션을 삭제할지보다 셋을 모두 지워도 되는지를 먼저 확인했어요. 일부 삭제에도 작업 위험은 있어요. 다만 부분 정리의 절감액을 판단하려면 당시 컬렉션별 과금 풀부터 확인해야 해요.

모델 사용료만으로 검색 기능의 미사용을 판단할 수 없었어요

처음에는 상위 모델 사용료가 거의 0이라는 점을 미사용 근거로 삼았어요. 하지만 이 요금만으로 지식 베이스를 쓰지 않는다고 단정할 수는 없었어요.

검색용 조회 API는 상위 모델 사용료를 발생시키지 않아요. 검색 결과를 다른 모델에 전달하는 다음 구성도 가능했어요.

검색만 하고 생성은 다른 모델로 하는 구성 앱 -> 지식 베이스 조회 API (검색 결과를 받는다) 상위 모델 요금 0 앱 -> 다른 모델 (그 결과로 답을 만든다) 다른 항목으로 청구 => 상위 모델 요금이 0 이면서 지식 베이스를 매일 쓰고 있을 수 있다. "요금 0 = 미사용" 이 성립하지 않는다.

그래서 요금만으로 확정하지 않고 담당자에게 사용 여부를 확인한 뒤 진행했어요. 확인한 요금 지표만으로는 검색에만 사용하는 구성을 구분할 수 없었기 때문이에요.

상위 모델 사용료가 거의 0이라는 관측은 그 모델의 생성 기능 사용량에 관한 근거였어요. 지식 베이스의 검색 기능까지 미사용이라는 근거로 넓혀 해석한 것이 잘못이었어요.

6. 과금이 없는 자원을 지운 이유

3장에 나온 확장 그룹, 시작 템플릿, 컨테이너 클러스터, 타깃그룹 자체에는 과금이 없었어요. 이 항목을 정리한 목적은 직접적인 절감과 달랐어요.

로드밸런서 삭제 중 ResourceInUse를 받았을 때도 타깃그룹의 역할부터 조사해야 했어요. 이름에 상위 유형을 시사하는 문자열이 있어 관련 자원을 찾았고, 연결 목록을 확인한 뒤에야 상위는 이미 삭제됐고 타깃그룹만 남았다는 걸 알았어요.

이번에는 조회 두세 번으로 확인했지만, 조사 전에는 얼마나 걸릴지 알 수 없었어요. 상위 자원이 남아 있을 가능성을 확인해야 했고, 그 판단이 끝나야 로드밸런서를 지울 수 있었어요.

상위가 사라진 타깃그룹을 그대로 두면 다음 정리 때도 같은 확인이 필요해요. 청구서에는 나타나지 않아도 자원 목록에는 남고, 이름만으로는 현재 사용 여부를 알 수 없기 때문이에요.

정리하는 이유는 둘이다 과금이 있는 자원 지우면 청구서가 줄어든다 과금이 없는 자원 지우면 다음 사람의 조사 시간이 줄어든다 두 번째를 안 하면 계정에 "정체를 조사해야 하는 것" 이 계속 쌓인다. 그 재고는 청구서에 안 나오고, 다음 정리 작업의 비용으로 나온다.

반대로 데이터 분석 플랫폼의 네트워크 구성에서는 과금되는 항목만 지우고 가상 네트워크, 서브넷, 라우팅, 피어링은 남겼어요. 6편에서 확인한 것처럼 실험 잔재가 아니었고, 역할과 다시 사용할 경로가 문서에 정리돼 있었어요. 재사용할 때 필요한 구성을 남긴 결정이었어요.

과금 여부와 함께 자원의 역할, 남은 참조, 재사용 계획을 봤어요. 역할이 끝나 불필요한 확인을 반복하게 하는 항목은 정리하고, 재사용할 근거가 있는 항목은 기록과 함께 남겼어요.

7. 참조 해제와 삭제 완료를 따로 확인하기

이번 정리에서는 삭제 대상뿐 아니라 이를 참조하는 코드와 다른 자원도 확인했어요. 참조 관계를 그래프로 정리하면, 어떤 참조를 먼저 해제해야 삭제할 수 있는지 순서를 정하기 쉬웠어요.

확인한 참조는 세 종류였어요.

참조 그래프의 세 층 코드와 감시 알람 정의 · 데이터소스 조회 · 커버리지 검사 목록 => 실물을 참조한다. 그래서 가장 먼저 걷어낸다 사용자 경로 DNS 레코드 => 실물을 참조한다. 죽은 구간을 만들지 않으려면 먼저 지운다 자원 사이 타깃그룹 -> 로드밸런서 · 지식 베이스 -> 컬렉션 클러스터 -> 용량 공급자 · 시작 템플릿 -> 이미지 => 참조하는 쪽부터. 안 지키면 API 가 거부한다

알람과 코드도 실제 자원을 참조한다는 점을 빼놓기 쉬웠어요. 데이터소스 조회가 실패하면 같은 스택의 plan이 막히고, 결측을 위반으로 보는 알람은 대상 삭제 뒤에도 경보를 유지했어요. 그래서 자원 사이의 연결을 정리하기 전에 이 부분부터 처리했어요.

참조 해제와 자원 삭제는 별도 작업이었어요. 클러스터와 용량 공급자처럼 클러스터를 남겨둔 상태에서 먼저 연결만 분리해야 하는 경우도 있었어요. 자원 목록의 삭제 순서만 정하지 말고, 중간에 필요한 참조 해제 작업까지 포함해야 했어요.

이번 ResourceInUse와 방화벽 규칙 묶음의 삭제 거부는 남은 참조를 확인할 계기였어요. AuthFailure는 관리 주체에 맞는 API가 필요한 경우였고요. 오류 이름만으로 사용 중이거나 권한이 부족하다고 판단해서는 원인을 구분하기 어려웠어요.

삭제가 거부되면 오류 본문에 나온 참조를 조회하고, 실제 사용 경로가 남아 있는지 확인했어요. 참조만 남았는지 현재도 사용 중인지를 구분한 다음 등록 해제나 삭제를 진행했어요.

이 순서로 확인해도 삭제 명령의 실행만으로 완료를 판단할 수는 없었어요. 남은 클러스터를 발견한 뒤에는 대상 이름으로 직접 조회하는 절차까지 추가했어요.

✍ 정리
삭제가 거부되면 오류 본문에 나온 참조와 관리 주체부터 확인했어요. 알람 코드와 실제 알람을 먼저 제거하고, DNS와 자원 간 참조를 정리한 뒤 삭제를 진행했어요.

이미지와 검색 컬렉션은 복구 경로와 사용 여부를 별도로 확인했어요. 목록 조회가 0이라는 이유로 완료를 적었다가 클러스터 하나가 남은 사실도 발견했어요. 이후에는 삭제 대상 이름으로 직접 조회하는 절차를 추가했어요.
