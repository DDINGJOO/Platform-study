복제 인스턴스 두 대를 절반 이하 등급으로 낮추기로 했어요. 목표 등급과 예상 중단 시간을 정한 뒤, 실제 변경에 앞서 알람부터 만들었어요.

이 파이프라인은 열 달째 CDC로 데이터 변경분을 복제하고 있었어요. 그런데 해당 서비스 지표가 모이는 네임스페이스에는 알람이 0개였어요. 다른 자원 종류에는 많으면 스무 개 넘게 붙어 있었지만, 이 파이프라인에는 태스크 중단을 알릴 알람이 없었어요.

등급을 정할 때 쓴 통계는 5편에서 살펴봤어요. 실제 변경에서는 감시를 먼저 추가하고, 한 대씩 바꾼 뒤 복제 상태를 확인했어요. 변경 이벤트를 확인하면서 전체 작업 시간과 실제 복제 중단 시간도 구분할 수 있었어요.

1. 변경 후 상태를 확인할 알람부터 추가했어요

등급을 낮추면 메모리가 부족해지거나 복제가 밀릴 수 있어요. 변경 후 이런 문제가 생겼는지 확인할 수 있어야 원래 등급으로 되돌릴지도 판단할 수 있어요.

문제가 발생했다면 먼저 현재 상태를 확인하고, 변경 전후 지표를 비교해 다운사이징과 관련이 있는지 살펴봐야 해요. 알람이 없던 상태에서는 그 확인부터 어려웠어요.

그래서 알람을 추가한 뒤 소스 로그 보존 기간을 확인하고, 한 대씩 변경하는 순서로 진행했어요.

1. 알람 8종 신설 → apply (+8 ~0 -0) 2. 소스의 변경 로그 보존 기간 확인 ← 추론을 실제 값으로 바꾼다 3. 한 대 변경 ← 15분 남짓 4. 메모리 · CPU · 스왑 · 복제 지연 실측 ← 여기서 멈추고 확인한다 5. 다른 한 대 변경

위 순서의 8종은 알람 종류와 Terraform 리소스 개수를 섞은 표현이에요. 고정 구성은 인스턴스마다 세 지표 알람을 둬 총 여섯 개이며, 두 인스턴스를 개별 필터링하지 않는 DMS 공통 이벤트 규칙 하나와 타깃 하나를 함께 정의해요. 실제 apply 출력은 확보하지 못해 생성 결과를 새로 확인한 것은 아니에요. 같은 지표 공백을 감지하는 메모리 알람은 인스턴스마다 하나씩 두는 구성이에요.

다운사이징을 하지 않더라도 필요한 알람이었어요. 이번 변경을 준비하면서 기존 감시에 빠진 부분을 확인하게 됐어요.

2. 결측을 위반으로 보는 알람은 하나만 남겼어요

여러 알람이 같은 지표 공백에 동시에 반응하면 알림이 중복돼요. 각 알람이 무엇을 감지할지 나누고, 데이터가 들어오지 않을 때의 처리도 함께 정했어요.

알람 지표 · 임계값 근거 결측 처리 ──────────────────────────────────────────────────────────────────────── swap-used SwapUsage > 0 14일간 정확히 0 notBreaching memory-low FreeableMemory < 1.5GB 8GB 의 19% · Minimum breaching cdc-latency CDCLatencyTarget > 300초 평시 3초 · 14일 최대 36초 notBreaching event 태스크 중단 · 실패 EventBridge 규칙 해당 없음 알람 이름은 {환경}-{서비스}-dms-{인스턴스}-swap-used 형태로 붙였다.

결측은 지표 데이터가 들어오지 않는 상태예요. 이를 임계값 위반으로 처리하는 알람은 메모리 여유 알람 하나만 두기로 했어요. 인스턴스 이상으로 지표가 끊겼을 때 알림을 받되, 같은 공백에 알람 세 개가 동시에 반응하는 것은 피하려고 했어요.

나머지 지표 알람은 결측을 정상으로 처리했어요. 스왑은 평시에 데이터포인트가 없을 수 있고, 태스크가 멈추면 복제 지연 지표 발행도 끊겨요. 태스크 중단은 별도의 이벤트 규칙으로 감지하도록 했어요.

임계값은 실측을 기준으로 정했어요. 스왑은 14일간 정확히 0이어서 0 초과를 위반으로 뒀어요. 복제 지연은 평시 몇 초, 14일 최대 수십 초였고, 임계값은 300초로 정했어요. 관측한 최대값의 여덟 배가 넘는 값으로, 당시 확인한 정상 변동과 구분하려는 설정이었어요.

3. 태스크가 실행 중이어도 복제가 지연될 수 있어요

처음에는 태스크 중단을 이벤트로 감지하면 지표 알람은 없어도 되는지 생각했어요. 하지만 태스크 설정을 확인하니 상태 변경 이벤트만으로는 감지하기 어려운 경우가 있었어요.

당시 기록은 RecoverableErrorCount가 -1이라는 이유로 무제한 재시도라고 해석했어요. 하지만 이 값은 오류 유형에 따라 동작이 달라요. 공식 문서에서 실행 중 연결 소실이나 대상 적용 실패는 9회, 시작 중 복구 가능 오류는 6회 재시도로 구분해요. 모든 오류가 무기한 반복된다는 해석은 정정해야 해요.

재시도하거나 일부 테이블만 중단된 동안에는 태스크가 실행 중이어도 복제가 지연될 수 있어요. 테이블 오류는 정책에 따라 해당 테이블만 중단하거나 태스크를 멈출 수 있어요. 당시 전체 오류 정책과 이벤트 원본은 확보하지 못했으므로, 어떤 오류가 실제로 상태 변경 없이 반복됐는지는 확인하지 못했어요. 그래서 상태 이벤트와 복제 지연 지표를 함께 보도록 구성했어요.

그림 1. 재시도 중에는 상태 변경 이벤트 없이 복제 지연만 늘어날 수 있어요

그래서 이벤트와 지표를 함께 감시했어요. 이벤트는 태스크 중단을, 복제 지연 지표는 태스크가 실행 중이어도 변경분 처리가 지연되는 경우를 감지하도록 역할을 나눴어요.

💡 아직 설정하지 않은 감시도 문서에 남겼어요
이 시점에는 다음 두 가지를 설정하지 않았어요.

• 이벤트 규칙을 종류별로 좁히지 않았어요. 이 계정에서 해당 서비스의 이벤트 페이로드를 실측한 적이 없어 필드 값을 단정하기 어려웠어요. 인스턴스 수정 중 태스크가 자동으로 중지·재개될 때 알림 카드가 오는지 확인하려고 했어요.

• CPU 알람은 전환 뒤로 미뤘어요. 당시 실측값은 8 vCPU 기준으로 피크가 한 자릿수 퍼센트였어요. 2 vCPU에서 같은 부하를 처리하면 30% 수준으로 계산되므로, 전환 후 실측을 보고 임계값을 정하려고 했어요.

설정하지 않은 항목과 이유를 남겨 두어 후속 작업에서 확인할 수 있게 했어요.

4. 한 대씩 변경했고, 첫 작업에서 알람이 오탐했어요

변경 전에는 소스의 변경 로그 보존 기간을 확인했어요. 복제가 몇 분간 끊겨도 그사이의 변경이 소스 로그에 남아 있어야 재개 후 처리할 수 있어요. 보존 기간이 중단 시간보다 짧으면 전체 재적재가 필요해요. 설정 여부를 추측하지 않고 실제 값을 조회했고, 두 소스는 각각 하루와 닷새 수준이었어요.

로그 보존 기간은 작업 시작 여부를 정하는 조건이었어요. 예상 중단 시간을 감당하지 못한다면 변경을 미뤄야 하므로, 인스턴스를 수정하기 전에 실제 값을 확인했어요.

두 대를 동시에 변경하지도 않았어요. 첫 대를 바꾸고 메모리·CPU·스왑·복제 지연을 확인한 뒤 두 번째로 넘어갔어요.

막 만든 알람이 예상대로 동작하는지 확인해야 했고, 문제가 생겼을 때 두 파이프라인이 함께 멈추는 것도 피하려고 했어요. 첫 대의 변경 결과를 보고 다음 작업을 진행할지도 판단할 수 있었어요.

다만 두 파이프라인의 부하는 달랐어요. 6절에서 다룰 전체 재적재 시간도 다섯 배 차이가 났어요. 첫 대에서 확인한 것은 변경 절차가 예상대로 진행되는지까지였고, 두 번째 인스턴스의 자원 여유는 별도로 측정해야 했어요.

첫 작업에서 메모리 알람이 오탐했어요. 클래스가 바뀐 직후 메모리 계열 지표가 한동안 발행되지 않았고, 결측을 위반으로 처리한 알람이 이 공백에 반응했어요.

평상시의 지표 소실을 감지하려고 둔 설정이 예정된 변경에도 반응한 거예요. 당시 설정은 변경 중 지표가 발행되지 않는 구간을 충분히 고려하지 못했어요. 이 시점에는 평가 기간을 늘려 해당 공백을 허용하는 방안이 후속 과제로 남았어요.

알람을 먼저 추가했지만, 실제 변경 중에도 설정이 적절한지는 별도로 확인해야 했어요. 이번 작업에서 그 보완 지점을 찾았어요.

5. 15분 중 실제 중단은 5분 48초였어요

당시 기록상 작업 전체는 15분 남짓, 복제 중단은 5분 48초였어요. 아래 이벤트별 시각과 전후 지표의 원본은 확보하지 못해 이 수치를 독립적으로 재검증하지는 못했어요.

+00:00 클래스 변경 시작 +08:51 Replication application shutdown ← 실제 중단 시작 +14:39 Replication application restarted ← 실제 중단 끝 +14:52 변경 완료 실제 중단 = 14:39 - 8:51 = 5분 48초

중단과 재개 시점은 시간순으로 남은 이벤트에서 확인했어요. 콘솔에서는 작업 전체가 변경 중 상태로 표시됐지만, 앞의 약 9분 동안은 복제가 계속 진행됐어요.

그림 2. 전체 변경 시간과 실제 복제 중단 시간을 구분해 확인했어요

다음 작업에서 허용할 중단 시간을 정할 때도 두 시간을 구분할 필요가 있어요. 전체 15분을 모두 복제 중단 시간으로 보면 이번에 확인한 영향보다 크게 평가하게 돼요. 작업 일정에는 전체 소요 시간을, 복제 중단 영향에는 실제 중단 시간을 따로 참고할 수 있어요.

소스 로그 보존 기간이 이번 복제 중단 시간의 몇 배인지 계산할 때도 5분 48초를 기준으로 비교했어요. 전체 작업 시간으로 나누면 두 값의 비율이 달라지므로, 어떤 시간을 비교했는지 함께 남겨야 해요.

6. 재시작과 이어서 처리를 구분하도록 안내했어요

복제 재개 방법도 주의해야 했어요. 당시 태스크는 전체 로드 시 대상 테이블을 지우고 다시 만드는 모드로 설정돼 있었어요.

이 설정에서 콘솔의 "재시작"으로 전체 로드를 다시 실행하면 대상 데이터를 지우게 돼요. 재적재에는 한쪽이 두 시간, 다른 한쪽이 열 시간 넘게 걸려요. 기존 변경분 복제를 재개할 때는 이어서 처리하는 옵션을 선택해야 했어요.

🚨 재개 방법을 알람 카드 본문에도 넣었어요
파이프라인이 멈췄을 때는 알림을 보고 바로 콘솔을 열 수 있어요. 실행 문서 외에 알람 카드에서도 재개 방법을 확인할 수 있도록 했어요.

이벤트 알람 카드 본문에 "재시작을 쓰면 데이터가 지워집니다. 이어서 처리하는 옵션을 쓰십시오"라는 안내를 넣었어요.

알림을 확인하는 화면에 주의사항을 함께 표시하려는 선택이었어요.

다만 안내 문구만으로 잘못된 실행을 막을 수는 없어요. 실제 호출을 제한하는 조치와는 구분해야 해요.

해당 동작은 관리 콘솔에서 실행하는 것이어서 코드 수정으로 버튼을 제한할 수는 없었어요. 권한으로 호출을 제한하면 필요한 재적재까지 막을 수 있어, 이번에는 카드에 경고 문구를 추가하는 수준으로 대응했어요.

후속 작업자가 실행 자체를 차단한 것으로 오해하지 않도록, 안내에 의존하는 대응이라는 한계도 남겼어요.

변경 후에는 태스크 상태와 진행률 외에 대상 테이블 수가 유지됐는지도 확인했어요. 전체 로드 후에도 상태와 진행률이 정상으로 표시될 수 있으므로, 여러 항목을 함께 살펴봤어요.
