읽기 전용 인스턴스를 한 대 줄였을 때의 절감액을 계산하려고 DB 인스턴스 목록을 뽑았어요. 이름에 writer가 있으면 쓰기를 받는 쪽이라고 보고 후보에서 빼고, 나머지를 축소 후보로 올렸어요.

역할을 확인하니 분류가 거꾸로였어요. 이름에 writer가 있던 인스턴스는 reader였고, 후보로 올린 다른 인스턴스가 실제 writer였어요.

이번 과제에서 이름과 실제 구성이 달라 판단을 잘못한 사례는 다섯 건이었어요. DB 인스턴스의 역할과 클래스, 네트워크 자원, 게이트웨이, 서버 네 대를 확인하면서 자원 종류에 따라 봐야 하는 필드가 다르다는 점을 확인했어요.

예전에 서비스를 코드로 편입할 때도 이름만으로 소유 범위를 정하지 않고 참조를 확인했어요. 잘못 분류하면 필요한 자원이 코드 밖에 남거나 다른 서비스의 자원을 가져올 수 있었기 때문이에요. 이번에는 분류 결과로 삭제나 축소까지 진행할 수 있어 실제 용도를 확인하는 일이 더 중요했어요.

1. writer라는 이름과 실제 역할이 달랐어요

클러스터 안에서 writer와 reader 역할은 바뀔 수 있어요. 페일오버로 다른 인스턴스가 쓰기를 넘겨받아도 생성할 때 붙인 이름은 그대로 남아요. 이름에 적힌 역할과 현재 역할이 달라질 수 있는 이유예요.

현재 쓰기를 받는 인스턴스는 RDS가 반환하는 IsClusterWriter 필드로 확인했어요. 이름으로 나눈 목록과 이 값을 대조하니 차이가 드러났어요.

이름이 말하는 역할 IsClusterWriter 실제 역할 ───────────────────────────────────────────────────── writer false reader reader (번호가 붙음) true writer

이렇게 잘못 분류하면 삭제 위험과 절감 누락이 함께 생겨요.

실제 writer가 축소 후보에 올라가면 쓰기를 받는 인스턴스를 잘못 건드릴 수 있어요. 반대로 실제 reader는 이름 때문에 후보에서 빠져요. 유지해야 할 대상을 확인하는 일과 줄일 수 있는 대상을 찾는 일이 모두 필요했어요.

2. 인스턴스 클래스는 이미 낮춘 상태였어요

두 번째도 DB 인스턴스였지만 확인할 값은 클래스였어요. 이름 끝에 최신 세대 계열을 가리키는 문자열이 있어, 처음에는 그 세대의 단가를 기준으로 클래스를 낮췄을 때의 절감액을 계산했어요.

실제 클래스는 버스터블 계열(db.t4g.medium)이었어요. 이미 클래스를 낮춘 상태에서 이름만 그대로 남아 있었어요.

이름에 박힌 것 DBInstanceClass 가 말하는 것 ──────────────────────────────────────────────────── 최신 세대 접미사 버스터블 계열 클래스 = 이미 낮춰져 있다 이름으로 잡은 절감 최신 세대 단가에서 깎는 만큼 실제 절감 0

첫 사례는 잘못된 축소 대상을 고른 경우였고, 여기서는 이미 반영된 변경을 앞으로의 절감으로 계산한 셈이에요. 이 항목을 목표에 넣으면 계획한 만큼 비용을 줄일 수 없어요.

코드 편입 작업 때도 같은 인스턴스의 이름과 클래스가 다르다는 사실을 적어뒀어요. 절감액을 계산할 때도 이 확인이 필요했어요. 이름에 적힌 세대의 단가로 계산한 추가 절감은 실제로는 0이었어요.

그림 1. 이름만으로 분류하면 삭제 대상과 유지 대상을 잘못 고를 수 있어요

3. VPC의 연결과 소속을 확인했어요

세 번째는 데이터 분석 플랫폼을 연결하면서 만든 VPC였어요. 안에 있는 자원 이름에 실험용 접두사가 붙어 있었고, 생성 후 아홉 달이 지난 상태였어요. NAT 하나와 인터페이스 엔드포인트 둘에서 계속 비용이 발생하고 있었어요.

처음에는 이름과 생성 후 지난 기간을 보고 실험이 끝난 뒤 남은 자원으로 분류했어요.

피어링, 즉 VPC 사이의 연결을 확인하니 운영 환경과의 관계가 보였어요. 피어링 연결 이름에는 그 플랫폼의 운영 환경을 가리키는 문자열이 있었어요. 엔드포인트 둘도 하나는 역할 위임에 쓰는 sts, 하나는 로그 전송에 쓰는 스트리밍 서비스가 대상이었어요.

이름이 말한 것 실험용 접두사가 붙은 VPC 와 그 안의 자원들 피어링 연결 이름 그 데이터 플랫폼의 운영 환경을 가리킨다 엔드포인트 대상 역할 위임 · 로그 전송 라우팅 운영 VPC 쪽으로 열려 있다 정체 실험 잔재가 아니라 그 플랫폼의 운영 컴퓨트용 네트워킹

이 VPC는 플랫폼의 컴퓨트를 실행하고 피어링을 통해 운영 자원에 접근하도록 만든 네트워크였어요. 실험용이라는 이름만으로 용도를 정할 수 없었고, 피어링·라우팅·엔드포인트의 대상과 사용 주체를 함께 확인해야 했어요.

개발용 이름의 NAT가 운영 VPC에 있었어요

네 번째는 이름이 개발 환경을 가리키는 NAT 게이트웨이였어요. 실제로는 운영 API 서버와 DB 복제 인스턴스가 있는 운영 VPC에 속해 있었어요.

이 게이트웨이의 소속 환경은 VPC로 확인했어요. 어떤 자원이 NAT를 통해 나가도록 구성돼 있는지는 라우팅 테이블의 참조를 확인해야 했어요.

이름만으로 개발 자원으로 분류했다면 정지 스케줄이나 통합을 검토했을 수 있어요. 하지만 변경이 적용되는 곳은 운영 VPC이므로 소속과 참조를 먼저 확인해야 했어요.

4. 실제 사용 여부를 확인한 뒤 삭제했어요

앞서 확인한 분석 플랫폼의 VPC는 운영 컴퓨트용 네트워크였어요. 용도를 알게 된 뒤에도 삭제 대상으로 판단했지만, 이번에는 실제 사용 여부를 확인한 뒤 내린 결정이었어요.

당시 그 플랫폼은 서버리스 방식만 쓰고 있었어요. 청구 사용량의 SKU, 즉 사용 항목 구분이 모두 서버리스 계열이었고 클래식 계열은 없었어요. VPC 안의 서버도 0대였고, 네트워크 인터페이스 다섯 개는 모두 엔드포인트와 NAT의 것이었어요.

1차 판정 이름에 실험 접두사가 있다 → 삭제 (근거 없음) 정체 확인 피어링 이름 · 엔드포인트 대상 → 운영 컴퓨트용 네트워킹 2차 판정 그 방식을 쓰는 컴퓨트가 0대 → 삭제 (근거 있음)

처음과 같은 삭제 결론이 나왔어도 확인 과정에는 차이가 있어요. 처음에는 실험용 이름을 근거로 삼았고, 나중에는 원래 용도와 당시 사용량을 확인했어요. 3편에서 절감 계산의 숫자를 대조했듯이, 여기서도 후보를 고른 근거를 다시 확인해야 했어요.

엔드포인트를 삭제한 뒤에는 다른 서비스가 사용했을 가능성도 확인했어요. 같은 계정의 DB 복제 인스턴스 역시 역할 위임을 사용하고 있었기 때문이에요.

💡 삭제 후 다른 VPC의 사용 가능성도 확인했어요
복제 인스턴스는 피어링 상대 VPC에 있었어요. 당시에는 엔드포인트의 네트워크 인터페이스와 사설 DNS가 해당 VPC에 속한다는 이유로 다른 VPC의 복제 인스턴스가 사용하지 않는다고 판단했어요. 이 근거는 잘못됐어요. 인터페이스 엔드포인트는 라우팅·보안그룹·DNS 구성이 맞으면 VPC 피어링을 통해서도 접근할 수 있어요. 상대 VPC의 DNS 해석이나 명시적 엔드포인트 URL, 사용 기록을 실제 확인했는지는 원자료가 없어 확인하지 못했어요. 당시 자료만으로 다른 VPC의 비사용까지 입증됐다고 볼 수는 없어요.

NAT 게이트웨이 역시 피어링 상대 VPC에서 사용할 수 없다고 판단했어요. 라우팅과 보안그룹 참조는 VPC를 넘어 영향을 줄 수 있어 별도로 확인해야 할 항목으로 봤어요.

VPC·서브넷·라우팅 테이블·피어링은 남겼어요. 당시 과금이 없는 구성으로 분류했고, 나중에 클래식 방식으로 돌아갈 때 엔드포인트 둘과 NAT를 다시 만들 수 있도록 기본 구성을 유지했어요.

NAT에 연결돼 있던 탄력적 IP는 함께 반납했어요. NAT만 지우고 IP를 남기면 미연결 상태의 IP 비용이 계속 발생하기 때문이에요.

5. 컨테이너 호스트 이름의 개발 서버 네 대

다섯 번째는 EC2 인스턴스 네 대였어요. 이름은 콘솔이 컨테이너 호스트에 자동으로 붙이는 형식이었고, 끝에는 개발 환경 표시가 붙어 있었어요.

이름으로 보면 개발용 컨테이너 클러스터의 호스트였어요. 개발 클러스터를 쓰지 않는다면 호스트도 정리할 수 있다고 생각했지만, 실제 구성은 달랐어요.

부팅 스크립트와 계정의 클러스터 목록을 확인했어요.

부팅 스크립트 컨테이너 에이전트에 넘길 ECS_CLUSTER 지정이 없다 = 이 서버는 어떤 클러스터에도 등록하지 않는다 클러스터 목록 이름이 가리키는 그 개발 클러스터가 계정에 없다 = 등록할 대상 자체가 존재하지 않는다

위 인용의 클러스터 미등록 결론은 정정해야 해요. ECS 에이전트는 클러스터를 따로 지정하지 않으면 기본 클러스터인 default에 등록할 수 있고, 설정은 ecs.config 등 다른 경로에서도 전달할 수 있어요. 특정 개발 클러스터가 없다는 사실도 모든 클러스터의 미등록을 뜻하지 않아요. 여기서 확인한 것은 부팅 스크립트의 명시적 지정 부재이며, 실제 전체 등록 상태는 당시 에이전트와 등록 목록 원본이 없어 확인하지 못했어요.

사용 지표에서는 CPU 최댓값이 90%를 넘고 네트워크 사용량이 수십 GB였어요. 사용량을 봐도 유휴 서버로 분류할 수 없었어요.

이 네 대는 개발자들이 원격 접속으로 쓰는 개발 서버였어요. 컨테이너 호스트 형식의 이름이 실제 용도와 맞지 않았어요.

부팅 스크립트에서는 클러스터를 명시한 설정이 없다는 점만 확인했고, 지표에서는 실제 사용 중이라는 점을 확인했어요. 둘을 함께 봐야 클러스터 호스트라는 추정과 유휴 서버라는 추정을 구분해서 점검할 수 있었어요.

⚠️ 등록 인스턴스가 없는 클러스터도 확인했어요
등록 인스턴스는 0인데 태스크가 실행 중인 클러스터도 있었어요. 컴퓨트 환경 설정을 확인하니 서버리스 계열만 사용하고 있었어요. 이번에 확인한 이런 클러스터는 넷이었어요.

이 클러스터들을 EC2 서버 절감 항목으로 세면 실제로 줄일 서버가 없는데도 절감액을 넣게 돼요. 그래서 클러스터의 등록 인스턴스 수를 먼저 확인했어요. 0이면 서버 절감 대상에서 제외하고, 인스턴스가 있으면 부팅 스크립트를 확인했어요.

6. 자원 종류에 따라 확인할 값을 정했어요

다섯 사례를 자원 종류별로 정리하면 아래와 같아요. RDS 두 사례는 같은 행에 묶었지만, 하나는 역할 플래그를, 다른 하나는 클래스를 확인해야 했어요.

자원 종류 이름 진짜 용도가 나오는 곳 ────────────────────────────────────────────────────────── RDS 인스턴스 X IsClusterWriter · DBInstanceClass 네트워크 자원 X 피어링 · 라우팅 · 엔드포인트를 쓰는 주체 게이트웨이 X 속한 VPC · 라우팅 테이블 참조 EC2 인스턴스 X user-data · 실사용 지표 컨테이너 클러스터 X 등록 인스턴스 수 · 컴퓨트 환경

자원 종류를 먼저 확인하고 그 자원의 역할·소속·사용 여부를 나타내는 값을 찾아야 해요. 모든 자원을 같은 필드로 판단할 수는 없었어요.

그림 2. 역할·소속·사용 여부를 확인할 값은 자원 종류마다 달라요

역할 플래그는 현재 쓰기를 받는 인스턴스를, 라우팅은 트래픽이 향하는 곳을, 부팅 스크립트는 시작할 때 실행하는 설정을 보여줘요. 이름과 달리 실제 동작에 관련된 값이어서 판단 근거로 확인했어요.

다만 이 표로 모든 자원을 판단할 수 있는 것은 아니에요. 다른 종류의 자원을 조사할 때는 그 자원에서 어떤 설정과 참조가 용도를 결정하는지 추가로 확인해야 해요.

이후 로드밸런서를 정리하면서 여섯 번째 사례도 나왔어요. 이름에는 상위 로드밸런서 종류가 있었지만, 실제 상위 목록이 비어 있는 타깃그룹이었어요. 이미 삭제된 로드밸런서에 연결돼 있던 자원이었고, 여기서는 연결 목록이 판단 근거였어요.

절감 작업에서 이런 분류는 단순한 문서 작성으로 끝나지 않아요. 잘못된 분류를 실행 단계로 넘기면 사용 중인 자원이 삭제될 수 있으므로, 후보 목록과 실행 대상을 구분해 검토해야 했어요.

이름은 후보를 찾을 때 참고하되, 실행 대상으로 확정하기 전에는 역할과 참조를 확인했어요. 이번 다섯 사례에서는 그 과정에서 이름과 실제 구성의 차이가 드러났어요.

✍️ 확인한 내용
RDS의 이름과 실제 역할·클래스가 달랐고, 네트워크 자원의 이름도 소속과 용도를 정확히 나타내지 않았어요. 컨테이너 호스트 형식으로 이름 붙인 서버 네 대는 개발자가 쓰는 서버였어요. 역할 플래그, 클래스, VPC와 라우팅, 부팅 스크립트와 사용 지표를 대조해 판단을 수정했어요.

분석 플랫폼의 네트워크는 원래 용도를 확인한 뒤 당시 컴퓨트와 사용량을 근거로 정리했어요. NAT와 엔드포인트를 삭제하고 탄력적 IP를 반납했으며, VPC·서브넷·라우팅 테이블·피어링은 유지했어요. 이름으로 찾은 후보를 실행 대상으로 확정하기 전에 실제 구성을 확인하는 과정이 필요했어요.
