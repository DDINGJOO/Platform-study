12편. ECR 수명주기 정책의 개수 규칙이 이전 삭제를 막지 못한 이유 ← 지금 이 글

컨테이너 이미지 저장소를 확인했을 때 한 곳에는 이미지가 657개, 다른 곳에는 104개 있었어요. 쌓인 이미지를 정리하려고 조건에 맞는 이미지를 자동으로 삭제하는 수명주기 정책을 적용했어요. 한 번 설정하면 이후에도 같은 기준으로 정리될 거라고 생각했어요.

657개에서 1개, 104개에서 8개로 바뀐 수치는 당시 정리값이에요. 당시 이미지 목록과 정책 평가·삭제 실행 원본은 확보하지 못해 이번에 그 결과를 재검증하지는 못했어요.

규칙은 두 개였어요. 태그 없는 오래된 이미지를 지우고, 최근 이미지 20개는 남기려는 의도였어요. 두 번째 규칙이 첫 번째 규칙의 삭제 범위를 제한해 줄 거라고 이해했어요.

다음 날 확인하니 657개가 1개로, 104개가 8개로 줄어 있었어요. 두 저장소 모두 최신 20개를 남기려고 설정했는데 그보다 적게 남았어요. 개수 규칙이 앞선 규칙의 삭제 대상을 제외해 줄 거라고 해석한 것이 잘못이었어요.

1. 최신 20개를 남기려고 추가한 규칙

그날 두 저장소에 적용한 정책은 다음과 같아요.

{"rules": [ { "rulePriority": 1, "description": "untagged 1 day", "selection": { "tagStatus": "untagged", "countType": "sinceImagePushed", "countUnit": "days", "countNumber": 1 }, "action": { "type": "expire" } }, { "rulePriority": 2, "description": "keep latest 20", "selection": { "tagStatus": "any", "countType": "imageCountMoreThan", "countNumber": 20 }, "action": { "type": "expire" } } ]}

첫 번째 규칙은 태그가 없고 푸시한 지 하루가 지난 이미지를 삭제해요. 두 번째 규칙에는 최신 20개를 초과하는 이미지를 삭제하는 조건을 넣었어요. 저는 이 두 조건을 합쳐서 읽으면 최신 20개가 보존된다고 생각했어요.

저장 요금을 줄이는 데는 첫 번째 규칙으로 충분해 보였어요. 두 번째 규칙은 최근 이미지까지 지워지는 일을 막으려고 추가했어요. 삭제한 이미지로 되돌릴 수 없으니 최근 스무 개는 남기려는 목적이었어요.

하지만 두 번째 규칙이 첫 번째 규칙에 어떻게 작용하는지는 확인하지 않았어요. 규칙을 추가했다는 이유만으로 삭제 범위도 제한됐다고 판단했어요.

이 정책을 개발용 저장소 두 곳에 동일하게 적용했어요. 각기 다른 서비스에서 쓰던 저장소였어요.

2. 적용 다음 날 657개 중 1개만 남았어요

당시에는 수명주기 정책을 적용하면 24시간 안에 첫 평가가 끝날 것으로 보고 기다렸어요. 다음 날 이미지 목록을 다시 세어봤어요.

저장소 적용 전 적용 후 남은 비율 ------------------------------------------------------ {서비스}/dev 657개 1개 0.2% {다른서비스}/dev 104개 8개 7.7% 두 곳 다 "최신 20개는 남긴다" 가 적혀 있는 정책이었다. 그런데 남은 것이 둘 다 20개보다 적다.

처음에는 두 번째 규칙이 실행되지 않았다고 생각했어요. 남은 개수가 20보다 적었기 때문이에요. 정책 문법이나 우선순위 설정에 문제가 없는지부터 확인했어요.

정책을 다시 조회했지만 문법 오류는 없었어요. 우선순위는 1과 2였고, 규칙 2의 countNumber도 20으로 들어가 있었어요.

남은 비율은 각각 0.2%와 7.7%로 서른 배 넘게 차이 났어요. 같은 정책을 넣었는데 왜 결과가 달랐는지 확인하려면 각 저장소에서 어떤 이미지가 규칙 1의 조건에 해당했는지도 봐야 했어요. 남은 개수만으로 규칙 2의 실행 여부를 판단할 수는 없었어요.

설정값을 다시 읽은 뒤에는 두 규칙의 적용 방식을 확인했어요. 제가 기대한 보존 동작이 이 정책에서 가능한지를 살펴봤어요.

3. 뒤의 개수 규칙은 앞의 삭제를 취소하지 않아요

수명주기 정책은 모든 규칙을 평가한 다음 우선순위 번호가 작은 규칙부터 적용해요. 제가 잘못 이해한 부분은 뒤의 규칙이 앞의 규칙에서 선택한 삭제 대상을 취소할 수 있느냐였어요.

저는 규칙 1이 삭제 후보를 고르면 규칙 2가 그중 최신 20개를 제외해 준다고 생각했어요. 하지만 앞 규칙이 이미 선택한 이미지에 뒤 규칙이 다시 적용되지 않는다는 것은, 그 이미지가 삭제 대상에서 빠진다는 뜻이 아니에요. 뒤 규칙은 앞 규칙의 삭제 결정을 취소하지 않아요.

규칙 1 tagStatus: untagged, 푸시 후 1일 경과 해당하는 이미지: 656개 -> 656개 전부에 삭제 표시 (이 규칙에는 "몇 개까지" 라는 조건이 없다) 규칙 2 tagStatus: any, imageCountMoreThan 20 이 규칙도 657개를 전부 본다 최신 20개를 뺀 637개에 삭제 표시를 하려 한다 그 637개는 규칙 1 이 이미 전부 찍어둔 것이다 -> 규칙 2 가 새로 찍는 것: 0개 규칙 2 는 실패하지 않았다. 자기 조건을 정확히 지켰다. 다만 이 규칙은 "20개를 남긴다" 가 아니라 "20개를 넘는 것을 지운다" 였다. 남기는 규칙이 아니었다.

규칙 1에는 개수 조건이 없어요. tagStatus: untagged에 sinceImagePushed 1 day를 붙였으니 태그가 없고 푸시한 지 하루가 지난 이미지는 개수에 관계없이 삭제 대상이에요. 다른 규칙에 최신 20개를 초과하는 이미지를 삭제하라고 적어도 이 조건에 보존 예외가 추가되지는 않아요.

이 정책에서는 우선순위 1번 규칙이 조건에 맞는 이미지를 모두 삭제 대상으로 선택해요. 뒤의 개수 규칙으로 그 범위를 줄일 수 없으니, 각 규칙의 삭제 조건을 따로 확인했어야 했어요.

그림 1. 두 번째 규칙은 첫 번째 규칙이 선택한 이미지의 삭제를 취소하지 않아요
⚠️ 규칙을 함께 쓸 때 확인할 내용
• 앞 규칙에 sinceImagePushed만 있고 imageCountMoreThan이 없다면 이미지 개수를 제한하는 조건이 없어요.
• 뒤 규칙은 앞 규칙이 선택한 삭제 대상을 취소하지 않아요.
• 이 정책의 두 규칙은 모두 삭제 규칙이에요. imageCountMoreThan 20은 20개를 초과하는 이미지를 삭제하는 조건이에요. tagStatus: any 규칙은 우선순위 번호가 가장 커야 하므로 순서를 앞으로 옮길 수도 없어요.
• 규칙을 여러 개 쓴다면 각 규칙이 선택하는 대상과 우선순위를 함께 확인해야 해요.

4. 태그 없는 656개에는 이전 배포본이 포함됐어요

이제 삭제된 656개가 왜 모두 태그 없는 이미지였는지도 확인했어요. 저장소의 99.8%가 여기에 해당했어요.

이 저장소는 빌드한 이미지를 푸시할 때 latest 태그 하나만 사용했어요. 태그를 덮어쓸 수 있는 저장소에서 같은 태그를 새 이미지에 붙이면 이전 이미지는 그 태그를 잃어요. 이미지 자체는 남아 있고, 이미지 내용을 식별하는 해시인 digest로 조회할 수 있어요.

push #1 digest aaa... 태그: latest push #2 digest bbb... 태그: latest aaa 는 태그를 잃는다 push #3 digest ccc... 태그: latest bbb 는 태그를 잃는다 ... push #657 digest zzz... 태그: latest 앞의 656개가 전부 untagged 이 저장소에서 untagged 는 "버린 이미지" 를 뜻하지 않았다. "지난 배포본" 과 같은 말이었다.

저는 태그가 없는 이미지를 더 이상 필요 없는 이미지로 간주했어요. 하지만 태그 유무만으로 삭제해도 되는지를 판단하려면 먼저 그 저장소의 태그 사용 방식을 확인해야 했어요.

이 저장소에서는 가장 최근에 푸시한 이미지에만 태그가 붙고 이전 배포본은 태그 없이 남았어요. 따라서 하루가 지난 태그 없는 이미지를 정리하는 규칙은 이전 배포본도 삭제 대상으로 선택했어요.

104개에서 8개로 줄어든 저장소는 여러 태그를 나눠 쓰고 있었어요. 태그가 붙어 있던 이미지 8개가 남았고, 규칙 2가 추가로 삭제할 대상은 없었어요. 같은 정책이어도 태그를 운영하는 방식에 따라 삭제 범위가 달랐어요.

그림 2. 같은 태그를 다시 사용하면 이전에 푸시한 이미지에는 태그가 남지 않아요

5. latest가 남은 이유와 정책 수정

남은 이미지 1개의 태그는 latest였고 푸시 시각은 2026-08-21이었어요. 당시에는 이 이미지를 현재 배포본으로 판단했어요. 그 시점에 이 저장소를 참조하는 컨테이너 서비스가 없다는 것도 확인했고, 그 범위에서는 서비스 영향이 없다고 봤어요.

이 이미지가 남은 이유는 규칙 1의 태그 없음 조건에 해당하지 않았기 때문이에요. 최근 배포본인지 확인해서 보존한 결과는 아니었어요. 규칙 2 역시 현재 배포 여부를 기준으로 예외를 두는 규칙은 아니에요.

예를 들어 새 이미지를 푸시하면서 latest가 옮겨가도 실행 중인 컨테이너가 이전 이미지를 계속 참조할 수 있어요. 그 이미지는 태그를 잃은 상태이고, 푸시한 지 하루가 지났다면 규칙 1의 삭제 조건에 해당해요. 이전 배포본을 삭제하면 롤백에 쓸 이미지도 함께 없어질 수 있어요.

이번에는 개발용 저장소였고 조회한 컨테이너 서비스 중 참조하는 서비스가 없었어요. 이 결과만으로 다른 저장소에서도 서비스 영향이 없을 거라고 판단할 수는 없었어요.

태그 없는 이미지의 경과 일수 규칙을 빼고, 개수 조건을 가진 규칙 하나로 줄였어요.

{"rules": [ { "rulePriority": 1, "description": "keep latest 20", "selection": { "tagStatus": "any", "countType": "imageCountMoreThan", "countNumber": 20 }, "action": { "type": "expire" } } ]}

tagStatus: any는 태그 유무와 관계없이 이미지를 선택해요. 여기에 개수 조건을 붙여 푸시 시각이 최신인 순서로 20개를 남기고 나머지를 삭제하도록 했어요. 당시에는 새 이미지가 푸시될 때마다 latest가 옮겨가니 이 태그도 반드시 20개 안에 포함된다고 생각했어요. 하지만 그 판단에는 태그가 항상 가장 최근에 푸시한 이미지를 가리킨다는 전제가 있었어요.

규칙을 하나로 줄여 두 규칙의 우선순위 때문에 의도보다 많이 삭제되는 문제는 피할 수 있었어요. 다만 개수 조건만으로 현재 배포본을 보존하는 것까지 보장할 수는 없었어요. 그 부분은 태그를 붙이는 방식과 함께 확인해야 했어요.

💡 tagStatus에 따라 달라지는 선택 대상
• untagged는 태그 없는 이미지를 선택해요. 여기에 제가 쓴 sinceImagePushed를 조합하면 푸시 시각을 기준으로 판단하고 개수는 제한하지 않아요.
• tagged는 지정한 태그의 이미지를 선택해요. 태그 접두사 목록이나 패턴 목록 중 하나가 필요해요.
• any는 태그 유무에 관계없이 선택해요. 이번 정책에서는 개수 조건과 조합해 푸시 시각 최신순으로 남길 대상을 정했어요.
• any 규칙의 우선순위 번호는 다른 규칙보다 커야 해요. 이번 수정에서는 any 규칙 하나만 사용했어요.

6. preview로 삭제 대상을 먼저 확인해요

새 정책을 put한 뒤 조회했을 때는 다음 값이 나왔어요.

aws ecr get-lifecycle-policy --repository-name {저장소} "lastEvaluatedAt": "1970-01-01T00:00:00+00:00" 잘못 넣었나 싶은 값이지만 이상이 아니다. 정책을 갈아 끼울 때마다 이 값이 초기값으로 돌아왔다. 새 정책에는 아직 평가 이력이 없다는 뜻으로 읽었다.

처음에는 1970년이라는 값 때문에 정책 저장에 문제가 생겼다고 생각했어요. 당시에는 정책을 교체한 뒤 아직 평가 이력이 없다는 뜻으로 해석했어요. 이 값만으로 삭제 대상 계산 결과를 확인할 수는 없었어요.

정책 적용 후 24시간 안에 평가될 것으로 예상하고 5분 간격으로 목록을 다시 세어봤지만 변화는 없었어요. 당시에는 즉시 실제 삭제를 실행시키는 API를 찾지 못했어요. 목록을 반복 조회해도 평가 시점을 앞당길 수는 없었어요.

적용 전에 삭제 대상을 계산해 보는 명령은 start-lifecycle-policy-preview였어요. 정책을 실제로 적용하지 않고 예상 삭제 목록을 조회할 수 있어서, 이 단계에서는 이미지가 삭제되지 않아요.

aws ecr start-lifecycle-policy-preview --repository-name {저장소} \ --lifecycle-policy-text file://policy.json aws ecr get-lifecycle-policy-preview --repository-name {저장소} \ --query 'previewResults[].imageTags' 이 결과에 latest 가 들어 있으면 그 정책은 적용하지 않는다. 정책을 저장하지 않고 판정만 받아보는 방법은 이것 말고 못 찾았다.

기존 두 규칙을 적용하기 전에 preview를 확인했다면 656개가 삭제 대상으로 선택되는지를 살펴볼 수 있었을 거예요. 다만 당시 상태로 preview를 실행한 결과는 없어요. 실제로 확인한 삭제 결과와 미리 실행했을 경우의 예상은 구분해야 해요.

이후에는 preview를 먼저 실행하고 결과 목록에 latest가 있으면 적용하지 않는 절차를 두었어요. 보존하려는 태그가 삭제 대상에 포함되는지를 확인하려는 목적이었어요. 이 검사는 나중에 다른 저장소에서도 적용을 중단시켰지만, 당시에는 그 원인까지 예상하고 만든 것은 아니었어요.

이번에 추가한 두 번째 규칙도 삭제 규칙이었어요. 최신 20개를 보존하려는 의도와 달리, 앞 규칙의 삭제 대상을 제한하는 기능은 없었어요.

11편에서는 절감 과제에서 확인한 근거와 진행을 막은 조건을 남겼어요. 이번 정책에서는 각 규칙이 선택하는 삭제 목록과 실제로 남겨야 하는 배포본을 대조하는 절차가 필요했어요.

✍️ 정책 수정과 확인 범위
tagStatus: untagged에 경과 일수 조건을 붙인 규칙이 656개를 삭제 대상으로 선택했어요. 뒤의 개수 규칙은 그 삭제를 취소하지 못했어요. tagStatus: any 규칙은 우선순위 번호가 가장 커야 한다는 제약도 있었어요.

이 저장소는 latest 태그 하나를 다시 사용했기 때문에 이전 배포본이 태그 없이 남아 있었어요. 수정한 정책은 tagStatus: any와 imageCountMoreThan 20을 조합한 규칙 하나예요. 다만 latest라는 태그 자체를 보존하는 규칙은 아니에요. latest가 최신 20개에 포함되는지는 태그를 붙이는 방식에도 달려 있어요.

이후에는 start-lifecycle-policy-preview로 삭제 대상을 먼저 조회하고 보존하려는 태그가 포함되면 적용을 중단했어요. lastEvaluatedAt 값이나 이미지 목록만 반복 조회하는 대신, 정책이 선택한 삭제 목록을 확인하는 절차를 추가한 거예요.
