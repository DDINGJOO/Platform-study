12편. ECR 수명주기 정책의 개수 규칙이 이전 삭제를 막지 못한 이유
13편. ECR 수명주기 정책 적용 전 latest와 배포본 순위 확인하기 ← 지금 이 글

12편에서 ECR 이미지 수명주기 규칙 두 개를 하나로 줄였어요. 규칙이 겹치면서 이미지 657개 중 1개만 남은 뒤라, 규칙 간 순서를 고려하지 않아도 되는 구성을 택했어요. tagStatus: any로 최신 20개를 유지하고, 태그 유무에 관계없이 21번째부터 삭제하는 규칙이에요. 이번에는 다른 저장소에도 같은 규칙을 적용하려고 했어요.

아래 48곳의 태그 순위와 배포본 위치는 당시 조사 기록의 수치예요. 원래 이미지 목록과 배포 설정 조회 출력은 확보하지 못해 같은 결과를 다시 대조하지는 못했어요.

적용 전에 preview를 돌렸어요. 정책을 저장하지 않고 삭제 예정 이미지 목록을 확인하는 API예요. 12편에서 정한 대로 삭제 목록에 latest가 있으면 적용을 중단하는 검사도 실행했어요. 네 저장소 중 세 곳은 통과했고, 네 번째에서는 latest가 삭제 대상에 포함됐어요.

해당 저장소의 latest는 푸시 시각순으로 56번째였어요. 최신 20개 안에 있을 거라는 제 예상과 달랐어요. 같은 규칙을 적용하려면 저장소마다 태그를 어떻게 붙이는지부터 확인해야 했어요.

1. 같은 규칙을 적용하려면 태그 방식도 확인해야 했다

12편에서 만든 규칙이에요. 다른 저장소에도 이 구성을 그대로 적용할 계획이었어요.

{ "rules": [{ "rulePriority": 1, "description": "최신 20개만 남긴다", "selection": { "tagStatus": "any", "countType": "imageCountMoreThan", "countNumber": 20 }, "action": { "type": "expire" } }] } tagStatus: any => 태그가 있든 없든 전부 대상이다 21번째부터 지운다. 예외 조항은 없다.

당시에는 새 이미지를 푸시할 때마다 latest 태그도 새 이미지로 옮기므로, 항상 최신 1번째이고 20개 안에서 제외되지 않을 거라고 생각했어요. 제가 확인한 저장소 대부분이 그렇게 동작했거든요. 같은 태그를 새 이미지에 붙이면 이전 이미지에서는 그 태그가 제거돼요. 이전 이미지 자체가 삭제되는 것은 아니에요.

하지만 태그를 옮기는 동작은 수명주기 정책이 보장하는 조건이 아니었어요. 정책은 같은 코드로 적용해도 태그를 붙이는 방식은 저장소별 배포 파이프라인이 정해요. 각 파이프라인은 다른 사람이 다른 시기에 만들었고, 제가 수정한 적도 없었어요.

규칙을 통일하려면 그 규칙이 안전하게 동작하는 조건도 저장소마다 확인해야 했어요. 보존 개수를 하나로 맞추기 전에 각 저장소가 같은 방식으로 태그를 갱신하는지 확인했어야 해요.

preview에서는 새 규칙을 넘겨 삭제 예정 이미지를 확인할 수 있어요. 여기서는 그 목록에 latest가 포함되는지를 검사했어요.

💡 preview로 확인할 수 있는 범위
• 정책을 저장하지 않고 삭제 예정 결과만 확인해요.
• 삭제 대상이 된 이미지에 어떤 규칙이 적용됐는지 확인할 수 있어요.
• 조회 시점의 이미지 목록을 기준으로 계산해요. 이후 새 이미지가 추가되면 결과가 달라질 수 있어요.
• 이미지의 실제 배포 여부는 알려주지 않아요. 5장에서는 배포 설정도 따로 조회했어요.

2. 네 곳 중 한 곳에서 latest가 삭제 대상이었다

네 저장소의 검사 결과는 다음과 같았어요.

preview · 삭제 목록에 latest 가 들어 있는가 {서비스}/dev 안전 latest 순위 1 {서비스}/prod-web 안전 latest 순위 2 {소량 서비스}/dev 안전 latest 순위 1 {배치 서비스}/dev 위험 latest 순위 56 <=== 여기 앞의 셋은 전제가 참이었고, 넷째는 거짓이었다.

네 번째 저장소의 상위 20개는 모두 커밋 SHA 태그를 사용하고 있었어요. 빌드한 커밋의 해시를 태그로 쓰므로 커밋마다 다른 태그가 붙어요. 같은 이름을 재사용하는 latest와 달리 {커밋SHA} 형식으로만 새 이미지를 푸시하고 있었어요. latest가 붙은 이미지의 마지막 푸시 시각은 다섯 달 전이었어요.

조회한 상태로 보면 과거에 붙인 latest를 갱신하지 않은 채 SHA 태그 이미지만 추가한 것으로 보였어요. 파이프라인이 중간에 바뀌었는지, 처음부터 그랬는지는 이 조회로 알 수 없어요. latest가 갱신되지 않는 동안 새 이미지가 55개 추가되면 1번째였던 이미지도 56번째가 될 수 있어요.

제가 놓친 것은 태그 이름과 갱신 동작의 차이였어요. 레지스트리의 수명주기 규칙은 latest도 다른 태그와 같은 방식으로 처리해요. 태그를 생략하면 latest를 붙이는 것은 클라이언트의 기본 동작이에요. latest가 최신 이미지를 가리키려면 파이프라인이 매번 그 태그를 갱신해야 해요.

앞선 세 저장소의 결과만 봤다면 네 번째도 같다고 판단했을 거예요. 3편에서 숫자의 근거를 따졌던 것처럼, 이번에도 일부 저장소에서 확인한 조건을 다른 저장소에 그대로 적용해서는 안 됐어요.

3. 저장소 48곳의 태그 사용 방식을 조사했다

다른 예외도 확인하려고 이번 정리 범위에 있던 저장소 48곳을 모두 조회했어요. 계정 전체를 조사한 것은 아니에요. 이미지 목록을 푸시 시각 내림차순으로 정렬한 뒤 latest의 순위를 읽었어요. 여기서 확인한 것은 순위뿐이고, 실제 사용 여부는 알 수 없었어요.

// 저장소 하나에서 latest 의 순위를 센다 aws ecr describe-images --repository-name "$REPO" \ --query 'sort_by(imageDetails,&imagePushedAt)[*].imageTags' \ --output json \ | jq -r 'reverse | to_entries[] | select(.value != null and (.value | index("latest"))) | .key + 1' 출력이 비어 있다 => latest 자체가 없는 저장소다 출력이 1 또는 2 => 개수 규칙으로 지켜진다 출력이 21 이상 => 개수 규칙으로는 못 지킨다

48곳의 태그 사용 방식은 네 유형으로 나뉘었어요. 아래는 이번 정책 적용 대상 네 저장소를 유형별로 하나씩 보여준 결과예요. 숫자는 저장소 수가 아니라 각 저장소의 이미지 개수예요.

유형 전체 태그 있음 태그 없음 latest 순위 ------------------------------------------------------------------ latest 만 쓴다 4,408 905 3,503 1 혼합 307 78 229 2 커밋 SHA 만 68 58 10 56 소량 141 1 140 1 태그 없는 이미지가 많은 곳일수록 정리 여지가 크다. 세 번째 줄만 반대다. 68개 중 58개가 태그를 갖고 있다.

위 표의 “latest만 쓴다”는 분류와 태그된 이미지 905개는 단일 latest 태그만으로 설명되지 않아요. 다른 과거 태그가 있었는지, 집계 범위가 달랐는지는 원본 목록이 없어 확인하지 못했어요. 따라서 이 유형 이름을 실제 태그 구성의 검증 결과로 읽어서는 안 돼요.

다른 세 저장소에는 태그 없는 이미지가 많아 이를 정리할 여지가 컸어요. 반면 커밋 SHA 태그를 쓰는 저장소는 커밋마다 태그가 붙으니 이미지 대부분에 태그가 남아 있었어요.

이 차이에 따라 당시 적용 기준을 나눴어요.

latest 가 1~2번째 => 개수 규칙(tagStatus: any) 안전 latest 가 20 밖 => untagged 규칙만 건다 latest 가 아예 없음 => 위와 같음. 개수 규칙을 걸 근거가 없다 첫 줄의 안전은 무조건이 아니라 조건부다. 지금 순위가 1~2 라는 사실 하나에만 걸려 있다. 그 저장소가 태그 없이 푸시하거나 SHA 태그로 갈아타는 순간 latest 는 그날부터 한 칸씩 뒤로 밀린다. 정책은 그대로인 채로. untagged 규칙의 성질 대상 태그가 없는 이미지만 조건 규칙 하나에도 countType 은 반드시 하나 있어야 한다 경과일로 자를지 개수로 자를지는 따로 정해야 한다 결과 태그된 것은 개수와 무관하게 전부 보존된다 => latest 를 절대 건드리지 않는다. 대신 태그된 것도 절대 못 지운다.

tagStatus: untagged는 태그 없는 이미지만 대상으로 삼아요. latest가 붙은 이미지는 순위가 56이든 560이든 삭제 대상에서 제외돼요.

대신 태그가 붙은 이미지는 오래되거나 사용하지 않아도 이 규칙으로 삭제할 수 없어요. 따라서 정리할 수 있는 용량은 태그 없는 이미지로 한정돼요.

그림 1. 같은 정책이라도 latest의 순위에 따라 삭제 여부가 달라져요

4. 태그된 58개를 보존하기로 했다

해당 저장소에서는 개수 규칙을 빼고 untagged 규칙 하나만 남겼어요. 태그가 붙은 58개는 이 규칙의 선택 대상에서 빠져요. 다만 태그 없는 이미지 10개가 만료 예정이었다는 종전 설명은 22편의 최종 정책과 맞지 않아요. 그 정책은 태그 없는 이미지를 20개 초과 보유할 때만 초과분을 선택하므로, 10개만 있다면 선택하지 않아요. 당시 다른 중간 정책을 썼는지는 확인하지 못했고, 10개의 만료·삭제 결과도 확정할 수 없어요.

이 선택으로 기대할 수 있는 절감은 사실상 0으로 봤어요. 태그가 붙은 이미지가 선택되지 않아 오래된 SHA 이미지의 용량을 줄이는 효과는 기대하기 어려웠어요. 태그 없는 10개가 실제 삭제됐다는 뜻은 아니에요. 다섯 달 전 이미지처럼 오래된 SHA 태그 이미지도 이번 규칙으로는 정리할 수 없었어요.

이 저장소의 용량은 전체 이미지 저장 용량의 0.5% 수준이었어요. 정리 효과는 작은 반면, 오래된 배포 이미지를 잘못 삭제할 위험이 있었어요. 그래서 태그된 58개를 보존하고 이 저장소의 절감은 사실상 0으로 두기로 했어요.

8편의 절감 0은 조사한 항목을 절감으로 계산할 수 없어서 나온 결과였어요. 이미 자동화로 정리 중이거나, 약정 때문에 자원을 꺼도 청구가 줄지 않는 경우였어요. 이번에는 정리 가능한 이미지가 있어도 보존을 택한 것이어서, 예외를 둔 이유를 함께 적었어요.

🧾 이 저장소를 예외로 둔 이유
• 용량 비중이 전체의 0.5% 수준이라 정리 효과가 작았어요.
• 태그된 이미지가 배포 중일 가능성을 배제하지 못했어요. 용량을 줄이기 위해 이를 삭제하지 않기로 했어요.
• 나중에 latest를 다시 갱신하면 이미지 순위와 삭제 예정 목록을 확인해 개수 규칙을 재검토할 수 있어요.
• 다른 저장소와 규칙이 다른 이유를 적어뒀어요. 이후 정책을 통일할 때도 이 조건을 확인할 수 있게 했어요.

5. 운영 배포본은 781번째에 있기도 했다

이어서 순위를 조사한 운영 저장소 네 곳은 커밋 SHA 태그만 사용했어요. 다만 운영 저장소가 모두 같은 방식을 쓰는 것은 아니에요. 2장의 {서비스}/prod-web은 운영 저장소지만 latest도 함께 갱신하고 있었고, 당시 순위는 2였어요. 개발·운영 구분만으로 태그 방식을 판단할 수는 없었어요.

SHA 태그를 쓰는 네 저장소는 거의 모든 이미지에 태그가 붙어 있어서 untagged 규칙으로 정리할 수 있는 이미지가 거의 없었어요.

개수 기준으로 정리하려면 실제 배포본이 보존 범위 안에 있는지 확인해야 했어요. 이 네 곳에는 latest가 없었으므로, 대신 현재 배포 중인 SHA 태그의 순위를 조사했어요.

배포 중인 이미지는 레지스트리의 이미지 목록만으로 알 수 없어요. ECS 태스크 정의, 즉 컨테이너 실행 설정에서 이미지 태그를 추출하고 저장소 안의 순위를 다시 계산했어요. 이때 확인한 참조는 태스크 정의뿐이에요. 이미지가 참조되는 다른 위치까지 확인한 결과는 아니에요.

// 1) 지금 쓰이는 태스크 정의에서 이미지 태그를 뽑는다 aws ecs describe-task-definition --task-definition "$TD" \ --query 'taskDefinition.containerDefinitions[*].image' => {계정}.dkr.ecr.{리전}.amazonaws.com/{저장소}:{커밋SHA} 여기서 필요한 것은 콜론 뒤 한 조각뿐이다. // 2) 그 태그가 저장소에서 몇 번째인지 센다 describe-images 결과를 imagePushedAt 내림차순 정렬 그 태그의 인덱스 + 1 = 배포본 순위

배포본의 순위와 전체 이미지 수를 함께 확인했어요.

저장소 배포본 순위 전체 이미지 판정 -------------------------------------------------------------- {서비스 A}/prod 1~2번째 개수 규칙 안전 {서비스 B}/prod 21~50번째 개수를 늘려야 한다 {배치 서비스}/prod 781번째 1,964 보류 {서비스 C}/prod 112번째 196 보류 위 둘의 순위가 범위인 것은 한 저장소를 여러 태스크 정의가 참조해서다. 배포본이 여럿이면 순위도 여럿 나온다. 앞의 둘은 숫자를 정하면 끝난다. 뒤의 둘은 숫자를 정할 수가 없다.

781번째인 저장소는 마지막 배포 이후에도 CI에서 커밋별 이미지를 계속 추가한 경우였어요. 배포본이 바뀌지 않는 동안 새 이미지가 쌓여 순위가 780칸 내려간 거예요. 커밋이 잦고 배포 간격이 길수록 이런 차이가 커질 수 있어요.

보존 개수를 781보다 크게 잡으면 1,964개 중 1,100개 남짓을 정리할 수는 있었어요. 하지만 900개를 보존해도 새 커밋 이미지가 120개 추가되면 같은 배포본이 다시 삭제 대상이 돼요. 보존 개수를 늘리는 것만으로는 배포본의 장기 보존을 보장할 수 없었어요. 그래서 순위가 오래된 두 저장소의 정책 적용을 보류했어요.

두 저장소는 배포 일정도 함께 고려해야 했어요. 배포본이 갱신되면 순위를 다시 확인하고 개수 규칙 적용을 검토할 수 있어요. 당시에는 정책을 적용하지 않고 보류 이유를 남겼어요.

그림 2. 배포 설정에서 이미지 태그를 찾은 뒤 저장소 안의 순위를 확인했어요

6. 삭제 대상과 배포 참조를 함께 확인해야 했다

특정 태그를 삭제에서 제외할 수 있다면 순위를 계속 확인할 필요가 줄어들어요. 그래서 정책에 latest를 보존하는 조건을 직접 적을 수 있는지도 살펴봤어요.

당시 사용한 수명주기 정책에는 특정 태그를 삭제에서 제외하는 조항이 없었어요. 삭제 대상과 규칙 우선순위, 보존 개수 또는 기간을 정하는 방식이었어요. tagPrefixList도 삭제할 태그의 접두사를 고르는 설정이지, 그 접두사를 제외하는 설정은 아니었어요.

당시 검토한 방법은 삭제 대상 자체를 좁히거나, 보존할 이미지가 최신 N개에 포함되도록 개수를 정하는 것이었어요.

방법 1 대상에서 뺀다 tagStatus: untagged 만 걸거나, tagged + 접두사 목록으로 지울 태그를 좁힌다 어느 쪽이든 latest 는 규칙의 시야 밖이라 안전하다 대가: 시야 밖에 둔 것은 무엇이든 영구 보존된다 접두사로 좁히려면 지울 태그에 공통 접두사가 있어야 하는데 커밋 SHA 에는 그런 게 없다 방법 2 개수 안에 넣는다 "최신 N개 안에 든다" 는 사실에 기댄다 대가: 그 사실이 언제든 변할 수 있다 둘 다 정책이 태그를 알아보는 게 아니다. 정책은 태그 이름에 아무 의미도 두지 않는다.

위 방법 1에서 태그 없는 이미지만 고르는 규칙은 태그가 붙은 이미지를 선택하지 않아요. 하지만 태그된 이미지에 접두사로 조건을 걸 때는 latest와 삭제 접두사 태그가 같은 이미지에 함께 붙을 수 있어요. 선택과 만료는 이미지 단위이므로 접두사만으로 latest 보호를 보장할 수는 없어요. 보존할 이미지의 모든 태그와 전체 정책의 preview 결과를 함께 확인해야 해요.

개수 기준을 택하면 안전 여부는 실제 이미지 순위에 달려 있어요. 파이프라인이나 커밋 빈도, 배포 간격이 바뀌면 정책 파일을 수정하지 않아도 보존 범위를 벗어날 수 있어요.

12편에서 만든 검사는 삭제 예정 목록에 latest가 있으면 적용을 중단하는 방식이었어요. 처음에는 규칙 순서를 잘못 정하는 상황을 생각해서 넣었는데, 이번에는 태그를 갱신하지 않는 파이프라인도 찾아냈어요.

preview 결과를 확인한 덕분에 네 저장소에 같은 정책을 적용하기 전에 차이를 발견했어요. 그대로 적용했다면 다섯 달 전 latest 이미지도 삭제 대상이었어요. 다만 이 검사만으로 그 이미지의 실제 사용 여부까지 확인한 것은 아니에요.

이 검사는 latest를 갱신하거나 배포본을 최신으로 바꿔주지는 않아요. 이번에 확인한 것은 삭제 예정 목록에 보존하려던 이미지가 포함된다는 점이었고, 이를 근거로 정책을 바꿨어요.

따라서 공통 규칙을 적용할 때는 저장소별 태그 사용 방식과 삭제 예정 목록을 함께 확인하기로 했어요. 배포 중인 이미지는 별도로 참조를 확인해야 하고, 이번 작업에서 조회한 범위는 ECS 태스크 정의까지였어요.

✍️ 적용 결과와 확인 범위
처음 확인한 네 저장소 중 한 곳에서는 latest가 56번째였어요. latest를 갱신하지 않고 SHA 태그만 추가하고 있어서 최신 20개 보존 규칙의 삭제 대상이 됐어요.

조사 범위는 저장소 48곳이었어요. latest가 최신 1~2번째인 저장소와 그렇지 않은 저장소를 구분했고, 후자에는 untagged 규칙을 검토했어요. 문제를 발견한 저장소는 untagged로 바꿔 태그된 58개를 보존했어요. 전체 용량의 0.5% 수준이라 절감은 사실상 0으로 두기로 했어요. 운영 여부만으로 태그 방식을 판단하지는 않았어요. prod-web처럼 latest를 갱신하는 운영 저장소도 있었어요.

SHA 태그를 쓰는 운영 저장소 네 곳은 태스크 정의에서 배포 이미지를 추출해 순위를 확인했어요. 전체 1,964개 중 배포본이 781번째인 곳도 있었고, 순위가 오래된 두 저장소는 적용을 보류했어요. 이때 확인한 참조는 ECS 태스크 정의까지이며, 모든 이미지 사용처를 확인한 결과는 아니에요. 공통 규칙을 적용하기 전에 태그 사용 방식과 preview 결과를 확인하고, 배포본은 별도로 조회할 필요가 있었어요.
