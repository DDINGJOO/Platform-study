14편. ECR 이미지 삭제 전 ECS·Batch·Lambda 참조 확인하기 ← 지금 이 글

이미지 저장소를 정리하려고 오래된 태그와 용량을 살펴봤어요. 지울 후보를 고르기 전에, 각 이미지를 어떤 서비스나 작업이 참조하는지부터 확인해야 했어요.

아래 참조 개수와 삭제된 저장소를 가리킨 세 설정은 당시 조사 결과로 남은 값이에요. 그때의 전체 API 응답과 실행 로그는 확보하지 못해 실제 참조 상태를 새로 검증한 결과는 아니에요.

저장소 목록과 이미지 참조 목록을 대조하는 것부터 시작했어요.

이미지를 지워도 이미 실행 중인 컨테이너는 계속 동작할 수 있어요. 문제는 재배포나 태스크 추가 때 이미지를 다시 내려받으면서 드러날 수 있어요. 서비스에서 찾은 참조는 12개였는데, 태스크 정의를 따로 조회하니 17개로 늘었어요. 배치 잡과 서버리스 함수에서도 추가 참조를 찾았고요. 네 경로를 확인한 뒤에도 참조를 설명하지 못한 저장소가 남았어요.

1. 삭제 직후 정상이어도 다음 배포는 확인할 수 없어요

오래된 이미지가 쌓인 저장소부터 정리하려고 했어요. 용량과 태그 목록으로 후보를 고를 수 있었지만, 오래됐다는 이유만으로 삭제할 수는 없었어요. 7편에서 다른 자원을 지우기 전에 참조를 확인했던 것처럼, 여기서도 사용하는 쪽을 찾아야 했어요.

이미지는 삭제 직후의 상태만 보고 문제가 없다고 판단하기 어려워요.

이미 실행 중인 컨테이너는 매번 저장소에서 이미지를 다시 받지 않아요. 그래서 저장소의 이미지를 지워도 현재 프로세스는 계속 동작할 수 있어요.

재배포, 스케일아웃, 노드 교체로 이미지를 다시 받아야 할 때 다운로드가 실패할 수 있어요. 삭제와 장애 발생 시점이 며칠 떨어질 수도 있는 거예요. 삭제 직후 헬스체크를 통과했다는 사실만으로 다음 배포까지 안전하다고 볼 수는 없어요.

🕓 삭제 직후 상태만으로 확인할 수 없는 것
• 이미 실행 중인 컨테이너와 헬스체크가 정상이어도 다음 이미지 다운로드 성공 여부까지 알 수는 없어요
• 재배포, 스케일아웃, 노드 교체 때 삭제한 이미지를 다시 요청하면 실패할 수 있어요
• 삭제 전에 이미지 참조를 확인하고, 현재 프로세스의 정상 여부와 구분해서 봐야 해요

먼저 클러스터마다 서비스 목록을 받고, 각 서비스가 참조하는 태스크 정의에서 이미지를 모았어요. 태스크 정의에는 컨테이너의 이미지와 실행 설정이 들어 있어요. 서비스는 사용할 태스크 정의와 유지할 태스크 수 등을 지정해요.

1차 조회 · 지금 배포되어 돌고 있는 것 클러스터 목록 -> 클러스터마다 list-services -> 서비스마다 태스크 정의를 읽는다 -> 컨테이너 정의의 image 를 모은다 결과: 이미지 12개 이 12개는 지우면 안 된다. 나머지는 지워도 된다 ... 고 그때는 생각했다.

첫 결과는 12개였어요. 모든 클러스터의 서비스를 순회했고 오류도 없어서, 당시에는 이 목록으로 충분하다고 생각했어요. 하지만 스크립트가 성공했다는 것만으로 서비스 밖의 참조까지 확인한 것은 아니었어요. 저장소 목록과 대조하면서 그 한계를 알게 됐어요.

2. 이미 지운 저장소를 가리키는 참조가 셋 있었다

12개 중 세 개는 이미 삭제한 저장소를 가리키고 있었어요.

그중 하나는 예전에 사용 종료로 판단해 정리했던 서비스에서 나왔어요. 저장소를 지운 뒤에도 서비스와 이미지 참조가 남아 있었어요.

그 상태로 태스크를 새로 띄우면 삭제된 이미지를 내려받을 수 없어요. 당시 desiredCount 는 0이었고, 실행하려는 태스크가 없어 문제가 드러나지 않았어요.

저장소 삭제는 끝났지만 그 저장소를 가리키는 서비스까지 정리한 상태는 아니었어요.

"정리 완료" 라고 적혀 있던 것의 실제 상태 저장소 지웠다 ✅ 목록에 적힌 것 서비스 남아 있다 ❌ 목록에 없던 것 참조 남은 서비스가 지운 것을 가리킨다 desiredCount = 0 이라서 아무 일도 안 일어난다. 그리고 아무 일도 안 일어나니까 아무도 모른다. 같은 모양이 셋이었다.

삭제 대상 목록만 확인하면 이런 참조를 놓칠 수 있어요. 저장소가 사라졌는지는 알 수 있지만, 다른 자원에 남아 있는 이미지 설정은 별도로 읽어야 해요.

11편에서는 도메인 둘이 대상 그룹의 등록 대상이 0개인 로드밸런서를 가리키고 있었어요. 로드밸런서 자체가 사라진 것은 아니었고, 열다섯 달은 생성 후 기간이라 그동안 내내 대상이 없었다는 뜻도 아니에요. 이번 서비스 설정은 이미 삭제된 저장소를 가리킨 경우였어요. 대상 자원의 삭제 여부와 참조 설정의 정리 여부를 함께 확인해야 했어요.

🧹 남아 있는 참조 세 개도 기록했어요
• 저장소 삭제 여부와 별도로 다른 자원에 남은 이미지 설정을 확인했어요
• desiredCount 가 0이라 실행하지 않고 있었지만, 다시 태스크를 띄우려 하면 삭제된 이미지를 요청하게 돼요
• 이 셋은 발견 목록에만 적었어요. 서비스 정리는 이번 조사 범위 밖이었고, 이 글에서 완료한 작업도 발견까지예요

12개는 실행 중인 이미지의 목록이 아니라 서비스 설정에서 읽어 낸 이미지 참조 목록이었어요. 존재하지 않는 저장소를 가리키는 항목도 들어 있었고요. 그렇다면 반대로, 서비스 설정 밖에 있는 이미지 참조도 빠졌을 수 있었어요.

3. 서비스에 붙지 않은 태스크 정의가 다섯 개 더 있었다

다음으로 태스크 정의를 직접 조회했어요. 첫 조회는 서비스에 연결된 태스크 정의만 읽었어요. 태스크 정의는 서비스 없이도 등록할 수 있고, 일회성 작업이나 예약 실행, 수동 실행에도 쓸 수 있어요.

같은 이름의 태스크 정의는 패밀리로 묶이고, 변경할 때마다 리비전 번호가 붙어요. 2차에서는 패밀리 목록을 받아 각각의 최신 리비전에서 이미지를 추출했어요.

같은 질문, 다른 범위 1차 클러스터 -> 서비스 -> 태스크 정의 이미지 12개 2차 패밀리별 최신 리비전 전수 이미지 17개 차이 5개는 전부 "서비스에 붙어 있지 않은" 태스크 정의였다. 1차의 범위는 "계속 떠 있도록 선언된 것" 이었다. 가끔 뜨는 것은 애초에 볼 수 없는 조회였다.

이미지가 다섯 개 더 나왔어요. 추가된 다섯 개는 모두 서비스에 연결되지 않은 태스크 정의에 있었어요. 1차 조회에서 서비스를 빠뜨린 문제가 아니라, 서비스만 읽도록 정한 조회 범위의 문제였어요.

서비스와 태스크 정의 양쪽을 확인해 17개가 됐지만, 저장소 목록과 대조하니 여전히 참조를 찾지 못한 항목이 있었어요.

용량이 큰 저장소 몇 곳이 두 조회 결과에 없었고, 그중 하나에는 전날 새 이미지가 푸시돼 있었어요.

최근 푸시는 그 저장소에 이미지를 올리는 작업이 있었다는 뜻이에요. 다만 푸시 기록만으로 실제 배포나 실행까지 확인할 수는 없어요. 이미지를 올린 경로와 사용하는 곳을 더 살펴볼 필요가 있었어요.

조회 결과에 없다는 이유로 정리 후보로 삼기는 어려웠어요. 최근 푸시는 사용 중이라는 확정 증거가 아니라, 조회 범위를 다시 확인할 단서로 봤어요.

그림 1. 조회 범위를 넓히며 추가 참조를 찾았지만 미확인 저장소도 남았어요

4. 클러스터 이름에 접두사가 붙어 있었다

1차에서 받아 둔 클러스터 목록을 다시 읽었어요. 그때는 서비스 목록을 순회하는 데만 썼는데, 클러스터 둘의 이름에 AWSBatch- 접두사가 붙어 있었어요.

이 환경에서는 배치 잡도 컨테이너 클러스터에서 실행하고 있었어요. 그래서 배치용 클러스터가 처음 받은 목록에 포함돼 있었어요.

배치 잡의 이미지 참조는 잡 정의에 있었어요. 해당 클러스터에 list-services 를 호출해도 서비스가 0개로 나왔고, 제가 수행한 최신 태스크 정의 조회에서도 그 이미지를 찾지 못했어요. 배치가 컨테이너 실행에 쓰는 태스크 정의와 별개로, 잡 정의의 이미지 설정을 직접 확인해야 했어요.

클러스터 조회가 실패한 것은 아니었어요. 배치 잡이 참조하는 이미지를 서비스 목록만으로 확인하려 했던 게 문제였어요.

3차로 배치 잡 정의를 조회해 저장소 두 곳의 참조를 찾았어요. 다만 처음에는 응답에서 이미지를 제대로 추출하지 못했어요.

첫 조회 · 이미지가 전부 None 이었다 describe-job-definitions --status ACTIVE containerProperties.image -> None containerProperties.image -> None 잡 정의가 신형 ecsProperties 구조를 쓰고 있었다. ecsProperties 는 containerProperties 안쪽이 아니라 그 옆에 나란히 있는 별개의 키다. 이미지까지는 두 겹 더 들어간다. containerProperties.image (구) ecsProperties.taskProperties[].containers[].image (신) 중첩 어디에 있든 찾는 방식으로 다시 조회했다 jq -r '.. | .image? // empty' -> {저장소}/prod

API 응답은 정상적으로 왔지만, 제가 지정한 필드 경로에 이미지 값이 없었어요. 응답 구조에 맞지 않는 경로를 읽어서 빈 값이 나온 거예요.

응답 원문을 확인하지 않았다면 이 빈 값을 참조가 없다는 뜻으로 받아들였을 수 있어요. 잡 정의가 사용하는 구조를 먼저 확인하고, 그 구조 안에서 이미지 필드를 다시 추출했어요.

🕳️ 빈 값이 나오면 확인할 것
• 응답 원문과 필드 경로를 대조해 사용하는 구조에 이미지가 어디에 있는지 확인해요
• 상태·리전 등 조회 조건으로 제외한 범위도 적어 둬요
• 최근 푸시가 있으면 사용 여부를 단정하지 말고 추가로 확인해요
• 이번에는 jq -r '.. | .image? // empty' 로 중첩된 이미지 필드를 찾았어요. 이 결과도 조회한 잡 정의 범위에서 해석했어요

찾은 참조에는 태그가 없었어요. {저장소}/prod 로 끝나고 뒤에 태그가 붙어 있지 않았어요.

태그를 생략한 참조는 latest 를 사용해요. 따라서 이 잡 정의가 참조하는 latest 는 보존해야 했어요. 다른 태그가 이 잡 정의에 필요하지 않다는 뜻이지, 다른 실행 주체도 쓰지 않는다는 뜻은 아니에요. 또 13편에서 확인했듯이 latest 가 가장 최근에 푸시된 이미지에 붙어 있다는 보장도 없어요. 개수 기준 정책을 적용할 때 이 참조가 삭제 대상에 들어가지 않는지 따로 확인해야 해요.

5. ARM64 이미지 두 곳은 서버리스 함수가 쓰고 있었어요

조사 초반에 저장소별 이미지 아키텍처도 확인했어요. 대부분은 x86이었고, 두 곳만 ARM64였어요.

당시 제가 살펴본 컨테이너 노드는 모두 x86이었어요. 그래서 처음에는 ARM64 이미지를 잘못 빌드했거나 실험용으로 올렸을 수 있다고 생각하고 기록만 해 뒀어요. 다른 곳에서 실행할 가능성은 확인하지 않은 상태였어요.

Lambda 이미지 참조를 읽으려면 list-functions로 목록과 PackageType을 확인한 뒤 get-function의 Code.ImageUri·ResolvedImageUri를 조회해야 해요. 목록 응답만으로 이미지 URI를 얻는 경로는 아니에요. 당시 모든 함수 버전까지 조회했는지는 원본 호출 로그가 없어 확인하지 못했어요.

4차로 컨테이너 이미지로 배포한 서버리스 함수를 확인했어요. 함수 둘이 나왔고, 각각 앞서 본 ARM64 저장소 두 곳을 참조하고 있었어요.

설명이 안 되던 데이터가 이미 답이었다 아키텍처 조사 결과 저장소 대부분 x86_64 컨테이너 노드가 x86 이니까 저장소 2곳 arm64 ??? 이걸 어디서 띄우지 4차 조회 결과 컨테이너 이미지로 배포된 서버리스 함수 2개 -> 참조하는 저장소가 그 2곳이었다 서버리스 쪽은 ARM64 를 지원하고, 같은 성능에서 x86 보다 싸다. 그래서 그렇게 빌드한 것이었다. 아키텍처는 결함의 흔적이 아니라 실행 주체의 지문이었다.

그 두 이미지는 x86 컨테이너 노드용이 아니라 서버리스 함수용이었어요. 서버리스 환경은 ARM64를 지원하므로, x86 노드만 살펴봤을 때의 의문이 풀렸어요. 다만 아키텍처별 실제 비용을 비교하려면 요금뿐 아니라 해당 함수의 성능도 측정해야 해요.

처음에 아키텍처가 다르다는 점을 기록했을 때 실행 환경도 함께 확인했으면 좋았을 거예요. ARM64라는 값은 오류로 분류하기 전에 다른 실행 환경이 있는지 확인할 단서였어요.

6편에서는 자원 이름과 실제 구성을 대조했어요. 이번에는 이미지 아키텍처를 실행 환경과 대조하면서, 서비스와 배치 외에 서버리스 함수의 참조도 찾았어요.

6. 네 경로로도 안 나온 것이 남았다

조회 결과를 경로별로 정리했어요. 아래의 API 세 개는 개별 호출 세 번이 아니라, 컨테이너·배치·서버리스의 서비스 API 세 종류를 뜻해요.

최종 참조 경로 목록 경로 조회 방법 찾은 것 -------------------------------------------------------------------- 컨테이너 서비스 클러스터 / 서비스 / 태스크 정의 이미지 12개 태스크 정의 전수 패밀리별 최신 리비전 이미지 17개 (5개 추가) 배치 잡 정의 describe-job-definitions 저장소 2곳 서버리스 함수 컨테이너 이미지로 배포된 함수 저장소 2곳 -------------------------------------------------------------------- ❓ 모른다 몇 곳이 남았다 경로는 넷인데 물어본 API 는 셋이다. 1차와 2차는 같은 컨테이너 API 의 다른 입구였고, 배치와 서버리스가 각자 자기 API 를 하나씩 더 붙였다. 첫 조회 하나로 끝날 줄 알았는데 API 가 두 개 더 붙었고, 그러고도 다 못 찾았다.

이렇게 확인한 뒤에도 용량이 큰 저장소 몇 곳의 참조는 찾지 못했어요.

인스턴스에서 직접 컨테이너를 실행하거나 별도 배포 도구가 이미지를 가져가는 경우를 생각해 봤어요. 다만 이 저장소들이 실제로 어느 쪽에서 쓰이는지는 확인하지 못했어요.

그 저장소들은 삭제하지 않고 남겼어요. 용량은 컸지만 사용 여부를 판단할 근거가 부족했어요. 참조를 놓친 채 지우면 이후 이미지 다운로드가 실패할 수 있었어요.

8편에서도 사용 여부를 확인하지 못한 자원을 남겼어요. 이번에도 조회 경로와 결과, 미확인 저장소를 기록했어요. 다만 다음 조사에서 새 경로만 보면 되는 것은 아니에요. 이미 확인한 경로에도 리비전 등 누락한 범위가 있었어요.

그림 2. 네 조회 경로에 세 종류의 서비스 API를 사용했어요

이번에 확인한 경로는 서비스가 참조하는 태스크 정의, 패밀리별 최신 태스크 정의, 배치 잡 정의, 서버리스 함수의 네 가지예요. 앞의 둘은 같은 컨테이너 서비스 API를 사용했고, 배치와 서버리스는 각각의 API를 조회했어요.

참조를 한 건 찾으면 그 설정이 남아 있다는 것은 확인할 수 있어요. 반면 조회 결과에 없다는 이유만으로 모든 실행 경로에서 쓰지 않는다고 판단할 수는 없어요. 처음 얻은 12개도 서비스 설정이라는 범위에서 찾은 결과였어요.

2차에서 실제로 읽은 범위는 패밀리별 최신 리비전 하나씩이에요. 앞의 코드와 표에 있는 태스크 정의 전수는 모든 리비전을 조회했다는 뜻은 아니에요. 서비스가 참조하는 리비전은 1차에서 확인했지만, 이전 리비전을 지정해 직접 실행하는 경우는 남아 있어요. 7편에서 시작 템플릿의 모든 버전을 확인했던 것처럼 리비전 범위도 따로 확인해야 했어요.

남은 참조를 찾으려면 먼저 이미지를 실행할 수 있는 주체와 조회 범위를 정리해야 해요. 서비스·일회성 태스크·배치·함수별로 참조를 읽고, 리비전이나 조회 조건 때문에 빠진 범위도 확인해야 해요. 직접 실행과 별도 배포 도구는 아직 확인하지 못한 경로로 남겼어요.
