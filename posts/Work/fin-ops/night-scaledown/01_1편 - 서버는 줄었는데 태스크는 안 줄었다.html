📚 야간 스케일 다운, 2부작
1편. ASG 야간 축소 뒤 ECS 태스크 배치가 실패한 이유 ← 지금 이 글

당시 기록에는 새벽 0시 8분에 Slack으로 ECS 태스크 배치 실패 알림을 받은 것으로 남아 있어요.

ECS 태스크 배치 실패 부족: RESOURCE:CPU 서비스: 웹 서비스 (운영) 클러스터: prod

전날 배포한 감지 규칙 중 하나가 보낸 알림이었어요. 당시에는 배포 16시간 만에 처음으로 실제 배치 실패를 감지한 것으로 정리했어요.

확인한 범위에서는 5xx나 사용자 신고가 없었고 대시보드에도 이상이 나타나지 않았어요. 하지만 매일 밤 6시간씩 목표 태스크 수의 2/3로 운영되고 있었어요. ASG 활동 로그로 확인한 기간만 최소 4일이었어요.

1. 야간 서버 수만 줄어든 설정

야간 EC2 비용을 줄이려고 ASG(서버 수를 조절하는 Auto Scaling Group)에 예약 작업을 설정해 둔 상태였어요. 자정에 서버를 3대에서 2대로 줄이고 아침 6시에 다시 3대로 늘리는 일정이었어요.

예약 작업은 서버 수만 바꿨고 ECS의 목표 태스크 수는 3개로 남아 있었어요. 이 서비스는 서버 한 대에 태스크 하나만 배치할 수 있어서, 서버가 2대로 줄면 3번째 태스크를 실행할 수 없었어요.

그림 1. 서버는 2대인데 목표 태스크 수는 3개인 야간 설정

ECS 스케줄러는 목표인 태스크 3개를 맞추려고 배치를 재시도했어요. 서버가 부족해 실패가 반복됐고, 아침 6시에 서버를 늘린 뒤에야 나머지 태스크를 배치할 수 있었어요.

💡 배치 실패가 반복된 이유
ECS는 설정된 목표 수를 맞추려고 재시도했어요. 당시 서버 수로는 목표를 충족할 수 없었으므로 재시도를 멈추기보다 서버 수와 목표 태스크 수를 함께 조정해야 했어요.

실행 중인 태스크 2개가 요청을 처리해서, 응답 오류만 확인해서는 목표보다 적은 수로 운영된다는 점을 놓치기 쉬웠어요. 이번에는 태스크 배치 실패 알림으로 그 상태를 확인했어요.

당시 조사에서 정리한 야간 타임라인은 아래와 같아요. 초 단위 원본 로그는 재확인하지 못했으므로 당시 정리본으로 봐야 해요.

00:00:05 ASG 예약 작업 실행 00:00:15 인스턴스 종료 시작 00:06:15 그 위의 태스크 중단 00:06:25 연결 드레이닝 00:08:48 ⚠️ 배치 실패 — CPU 부족 ← 알람이 여기서 울렸다 ... 6시간 동안 태스크 2개로 운영 ... 06:00:02 ASG 예약 작업 실행 06:00:14 인스턴스 시작 06:10:13 태스크 1개 시작 06:37:29 정상 상태 도달

조회한 ASG 활동 로그에서는 같은 패턴이 최소 4일 반복됐어요. 이 조회 범위만으로는 그 이전에도 같은 일이 있었는지 확인할 수 없었어요.

⚠️ 부팅 시간과 재시도 대기를 구분하기
위 기록에서는 인스턴스 시작(06:00:14)부터 태스크 시작(06:10:13)까지 약 10분이 걸렸어요. 처음에는 이를 부팅 시간으로 보고 아침 전환에 10분 여유를 잡았어요.

이후 조사에서는 부팅을 2분, 남은 8분을 ECS 스케줄러의 재시도 백오프, 즉 실패 뒤 다음 시도까지 기다리는 시간으로 구분했어요. 6시간 동안 배치가 실패하며 재시도 간격이 길어졌다는 해석이었어요.

다만 이 세부 측정 기록은 이번 대조에서 확인하지 못했어요. 당시의 10분을 정상 전환에도 그대로 필요한 시간으로 단정하지 않고, 부팅과 태스크 배치 시간을 나누어 확인해야 해요.

2. CPU 설정상 서버 한 대에 태스크 하나만 배치할 수 있었어요

남은 서버에 태스크를 추가로 배치할 수 있는지 CPU 설정을 확인했어요.

서버 등록 CPU 8192 태스크 요구 CPU 7936 (97%) ───── 남는 CPU 256 → 두 번째 태스크는 절대 못 들어감

7936 = 8192 - 256으로, 태스크 하나가 서버에 등록된 CPU의 대부분을 요구했어요. 남는 CPU로는 같은 태스크를 추가 배치할 수 없어서 이 서비스는 태스크 1개당 서버 1개가 필요했어요.

따라서 서버 수를 바꿀 때 목표 태스크 수도 함께 검토해야 했어요.

그림 2. 서버 한 대에 배치할 수 있는 태스크 수에 따른 차이

서버 한 대에 여러 태스크를 배치할 수 있다면 남은 서버의 여유 용량을 활용할 수 있어요. 다만 실제 재배치 가능 여부는 남은 자원과 배치 조건에 따라 달라져요. 이 서비스의 1:1 구조에서는 목표 태스크 수만큼 서버가 필요하므로 서버와 태스크를 바꾸는 순서를 맞춰야 했어요.

CPU 요구량 외에도 태스크를 서로 다른 서버에 배치하는 제약이 있었어요. 서버 한 대가 중단되었을 때 여러 태스크가 함께 중단되지 않도록 한 가용성 설계였으므로, 이번 조정에서도 이 조건은 유지하기로 했어요.

3. 서버 축소가 태스크 목표 수를 바꾸지는 않았어요

당시 설정에는 ECS의 용량 수요를 ASG에 반영하는 경로가 있었지만, ASG 예약 작업에 맞춰 ECS의 목표 태스크 수를 바꾸는 설정은 없었어요.

그림 3. 당시 설정에서 ASG 예약 작업과 ECS 목표 수는 연동되지 않았어요

ECS의 용량 공급자는 태스크 배치에 필요한 서버 용량을 관리형 스케일링에 반영해요. 하지만 서버 수를 줄이는 ASG 예약 작업이 ECS의 목표 태스크 수까지 줄여 주지는 않았어요.

서버 수와 태스크 수는 서로 다른 서비스의 화면과 API에서 관리했어요. ASG 설정만 변경할 때 ECS의 목표 수를 함께 확인하도록 하는 장치가 없었어요.

ASG는 예약된 수로 서버를 줄였고 ECS는 설정된 수의 태스크를 유지하려고 했어요. 개별 동작보다 두 설정을 함께 조정하지 않은 점에서 배치 실패의 원인을 찾았어요.

4. 야간 상한 때문에 관리형 스케일링도 늘릴 수 없었어요

관리형 스케일링이 부족한 서버를 늘릴 수 있는지도 확인했어요. 야간 예약 작업에는 상한이 설정돼 있었어요.

ASG 예약 작업 (밤) MinSize 2 MaxSize 2 ← 상한이 2 로 고정 Desired 2 관리형 스케일링: "서버를 더 달라" ASG: "상한이 2 다"

예약 작업이 MinSize = MaxSize로 서버 수를 고정해서 관리형 스케일링이 필요 용량을 계산해도 상한을 넘겨 서버를 늘릴 수 없었어요.

확인한 구성에서는 야간 6시간 동안 서버 부족을 해소할 자동 조정 경로가 없었어요.

5. 두 설정을 함께 검토하고 수량 차이를 확인하기

이 서비스의 안정된 운영 상태에서는 서버 수와 목표 태스크 수를 아래처럼 맞춰야 했어요. 전환 중에는 서버 준비와 태스크 배치가 순차적으로 진행되므로, 이 등식이 순간마다 성립해야 한다는 뜻은 아니에요.

ASG 서버 수 == ECS 태스크 수

당시에는 이 수량 차이를 직접 검사하거나 두 설정을 함께 변경하도록 강제하지 않았어요. 그래서 서버 수만 바뀐 상태가 며칠간 이어졌어요.

두 수량의 관계를 유지하는 방법으로는 수동 확인, IaC에서 설정을 함께 관리하는 방식, 수량 차이를 감지하는 검증을 비교했어요.

최소 사람이 기억해서 양쪽을 같이 고친다 ← 여기였고, 깨졌다 중간 양쪽 설정을 같은 IaC 파일에 둔다 (한쪽을 고치려면 다른 쪽이 눈에 보인다) 강 검증 장치가 등식 위반을 감지한다

당시에는 양쪽 설정을 IaC로 관리하지 않아 변경 내용을 코드 diff로 비교하거나 함께 리뷰하기 어려웠어요. 사람이 두 설정을 모두 확인하는 데 의존하고 있었어요.

🔍 설정 생성 시점은 확인하지 못했어요
당시에는 CloudTrail의 90일 조회 범위에서 예약 작업 생성 기록을 찾지 못했다고 정리했어요. 이 결과만으로 90일보다 오래된 설정이라고 확정하거나 생성자를 특정할 수는 없어요.

야간 서버 수를 2대로 정한 뒤 목표 태스크 수가 3개로 바뀌었을 가능성은 있지만, 변경 순서와 당시 의도는 확인하지 못했어요.
✍️ 정리
야간 ASG 예약 작업은 서버만 줄였고 ECS의 목표 태스크 수는 유지됐어요. 태스크와 서버가 1:1로 배치되는 조건에 야간 서버 상한까지 겹쳐 배치 실패가 반복됐어요.

서버 수와 목표 태스크 수를 함께 검토하고, 수량 차이가 지속되는지 확인해야 한다고 판단했어요. 당시 타임라인과 부팅·재시도 시간의 세부 원본은 이번에 다시 확인하지 못했고, 설정 변경 순서도 추정으로 남겨 두었어요.
