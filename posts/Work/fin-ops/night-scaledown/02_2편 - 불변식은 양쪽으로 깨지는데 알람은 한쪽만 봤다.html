1편. ASG 야간 축소 뒤 ECS 태스크 배치가 실패한 이유
2편. ECS 야간 축소 후 남는 서버를 ASG 지표로 감지하기 ← 지금 이 글

서버에만 걸려 있던 야간 예약을 ECS 태스크에도 추가했어요. 자정에 태스크를 2개로 줄이고 아침에 3개로 되돌리되, 서버가 줄고 늘어나는 시각과 순서를 맞춰야 했어요.

태스크 예약, 서버 예약, 종료 보호의 세 가지를 적용했어요. 다만 종료 보호가 예상대로 해제되지 않으면 서버가 줄지 않을 수 있었어요. 기존 배치 실패 알람으로는 이 상황을 감지할 수 없어 별도 알람을 추가했어요.

1. 밤에는 태스크부터, 아침에는 서버부터 조절하기

이 구성에서는 태스크 예약과 서버 예약 사이에 간격을 뒀어요. 밤에는 태스크를 먼저 줄이고 서버를 줄여요. 아침에는 서버를 먼저 늘려 태스크가 실행될 용량을 준비해요.

그림 1. 태스크 종료와 서버 준비에 필요한 시간을 예약 사이에 둬요

밤에는 태스크가 종료된 뒤 빈 서버를 줄여야 실행 중인 태스크가 함께 종료되는 일을 피할 수 있어요. 아침에는 서버가 준비되기 전에 태스크를 늘리면 배치할 용량이 부족해 알람이 발생할 수 있고요. 두 예약 사이에 둔 간격은 각각 10분이에요.

2. 태스크와 서버의 종료 대상이 다를 수 있어요

예약 시각을 맞춰도 종료 대상이 일치한다는 보장은 없었어요. 자정에 태스크가 줄어 서버 하나가 비더라도, ASG(Auto Scaling Group)가 그 서버를 종료 대상으로 고르는지는 별도 문제예요.

처음에는 "1/3 확률로 맞고 2/3 확률로 틀리겠네"라고 생각했어요. 하지만 서버를 무작위로 고르는 구성이 아니어서 그런 확률을 적용할 근거가 없었어요.

ECS와 ASG는 서로 다른 기준으로 종료 대상을 골라요.

ECS 종료할 태스크를 고른다 AZ 균형 등 자체 판단 ASG 종료할 서버를 고른다 종료 정책 — 가장 최근에 뜬 것

아래는 아침 이후 서버 교체나 태스크 재배치가 없었다고 본 구성이에요. 가장 최근에 시작된 서버는 아침에 추가한 3번째 서버예요. 서버마다 같은 서비스의 태스크를 하나씩만 놓는 배치 제약 때문에, 기존 두 대에 태스크가 있는 상태라면 아침에 추가한 태스크는 새 서버에 배치돼요.

그림 2. 태스크를 추가한 서버와 ASG 종료 후보가 겹칠 수 있어요

이 상태에서 ECS가 다른 서버의 태스크를 종료하면, ASG의 종료 후보에는 여전히 태스크가 있어요. 그대로 서버를 종료하면 불필요한 태스크 재시작이 발생하고 몇 분간 태스크가 하나 부족해질 수 있어요. 매일 같은 일이 발생한다고 단정할 수는 없지만, 두 종료 대상이 일치하도록 할 방법은 필요했어요.

그래서 세 번째 조치로 종료 보호를 적용했어요. 태스크가 있는 서버를 ASG 축소 대상에서 제외하고, 태스크가 없는 서버의 보호는 ECS가 해제하도록 하는 구성이에요. 이 동작이 확인돼야 빈 서버만 종료 후보로 남길 수 있어요.

3. 종료 보호가 해제되지 않으면 서버가 남아요

적용 당시에는 ECS가 이 서비스의 태스크 상태에 따라 서버 보호를 관리하는지 확실하지 않았어요. 보호 설정을 켜는 것과 빈 서버의 보호가 자동으로 해제되는 것은 따로 확인해야 했어요.

보호 해제가 동작하지 않으면 서버 축소 자체가 막힐 수 있어요.

인스턴스 축소 보호는 ASG의 기능이에요. 조치할 때 서버 3대에 보호를 수동으로 설정했어요. ECS가 그 플래그를 관리하지 않으면 태스크가 사라진 뒤에도 보호가 남을 수 있어요.

00:00 태스크 3 → 2 ① 동작한다 00:10 ASG 축소 시도 → 전부 보호됨 ② 차단된다 서버 3대 유지 결과: 태스크 2 / 서버 3 절감액 전액 소멸. 그리고 Slack 은 조용하다

이 경우 태스크 예약은 실행돼도 서버 예약이 목표한 축소는 완료되지 않아요. 야간 서버 한 대를 줄여 얻으려던 절감 효과도 없어져요. 종료 보호를 추가한 뒤에는 서버 수가 실제로 줄었는지까지 확인해야 했어요.

4. 배치 실패 알람으로는 남는 서버를 감지하지 못해요

1편에서 문제를 감지한 알람은 태스크 배치 실패를 확인해요. 서버가 부족할 때는 알림이 오지만, 태스크보다 서버가 많이 남는 상황은 감지 대상이 아니에요.

배치 실패가 없다는 이유만으로 조치 성공을 판단할 수는 없었어요. 조치 문서에 적었던 다음 문장도 그 구분이 부족했어요.

⚠️ 알림이 없다는 것만으로는 부족해요
"Slack 이 조용하면 알람도 해결된 것이다."

알림이 없다는 것만으로 배치 실패가 없다고 확정하거나 서버 축소가 성공했다고 판단할 수는 없어요.
목표한 서버 수와 실제 서버 수를 별도로 확인해야 해요.

1편에서는 태스크에 비해 서버가 부족했어요. 이번에 추가한 종료 보호는 반대로 서버가 남는 상황을 만들 수 있었고, 당시 배치 실패 알람으로는 그 차이를 확인할 수 없었어요.

그림 3. 서버 부족과 서버 초과는 감지 조건이 달라요

5. ASG 목표 용량과 실제 인스턴스 수를 비교했어요

서버가 목표 수보다 많이 남는 상황을 감지하는 알람을 추가했어요.

처음에는 태스크 수와 서버 수를 비교하려고 컨테이너 단위 지표를 제공하는 유료 모니터링 기능의 도입 결정을 기다렸어요. 하지만 ASG가 목표 용량까지 줄지 못한 상황은 ASG 지표만으로 확인할 수 있었어요.

IF( 실제 서버 수 - 목표 서버 수 > 0, 1, 0 ) 30분 이상 지속되면 알림

ASG의 GroupDesiredCapacity는 목표 용량이고, GroupInServiceInstances는 서비스 중인 인스턴스 수예요. 두 값으로 목표보다 서버가 많이 남았는지 비교했어요. 사용한 그룹 지표는 별도 요금 없이 제공되며, 며칠 전에 이미 활성화해 둔 상태였어요.

이 알람은 배치 실패 알람에 더해 서버 축소가 끝나지 않은 상황을 감지해요. 다만 태스크 수를 직접 비교하지 않으므로 서버 수와 태스크 수가 항상 같다는 보장은 아니에요. 종료나 시작을 기다리는 정상 전환 구간을 제외하려고 30분 동안 초과 상태가 이어질 때 알리도록 했어요. 당시 전환 시간은 약 6분으로 기록했지만, 이를 뒷받침할 실측 로그는 확인하지 못했어요.

6. 첫날 관찰 결과와 남은 확인 범위

당시에는 세 가지 조치를 모두 적용했고, 설정 변경에 따른 재시작은 0회, 다운타임은 0초였다고 기록했어요. 첫날 야간 축소와 아침 복귀 결과는 아래와 같이 남겼어요.

00:05 보호 플래그 하나가 False ← ECS 가 빈 서버의 보호를 풀었다 서버 2 / 태스크 2 성공 00:30 최종 상태 일치 06:00 서버 3 / 태스크 3 · 알람 0건 아침 복귀도 정상

이 기록에서는 빈 서버의 보호 플래그가 해제된 것을 ECS의 보호 관리가 동작한 근거로 봤어요. 다만 이 결과를 뒷받침할 시각별 실행 로그는 확인하지 못했어요. 특히 00:05에 서버 2대라고 적힌 결과와 00:10 서버 축소 예약 사이의 시점 차이는 추가 확인이 필요해요.

🌙 보호 해제에 실패할 때의 롤백 준비
보호 해제가 동작하지 않을 가능성에 대비해 수동으로 보호를 해제하는 롤백 절차를 적어뒀어요. ASG가 목표 용량으로 다시 조정할 수 있도록 하는 절차였어요. 당시 야간 태스크 2개는 처리량보다 이중화를 위한 구성으로 판단해, 롤백 시 몇 분간의 태스크 재시작도 함께 검토했어요.

당시 기록에 따르면 이 절차는 쓰지 않았어요. 0시 5분 관찰 시점에 새로 판단하지 않도록 준비한 절차이며, 실패 시 5분 안에 끝난다는 실제 검증 결과는 아니에요.

종료 보호가 동작했다는 관찰은 용량 공급자, 즉 ECS가 태스크에 필요한 서버 용량을 관리하는 연결도 살펴볼 이유가 됐어요. 다만 보호 해제 결과만으로 자동 용량 조절까지 정상 동작한다고 확정할 수는 없어요.

예약으로 상한을 고정한 상태에서는 자동 조절 동작을 충분히 관찰하기 어려웠어요. 예약 없이 자동 조절에 맡기는 구성은 별도 관찰 대상으로 남겼고, 이번 야간 예약 조치로 그 검증까지 끝났다고 보지는 않았어요.

✍️ 오늘의 요약
태스크와 서버의 예약 순서를 맞추고, 실행 중인 태스크가 있는 서버에는 종료 보호를 적용했어요. 보호가 해제되지 않아 서버가 남는 상황은 ASG 목표 용량과 실제 인스턴스 수를 비교하는 알람으로 감지하도록 했어요.

첫날 축소와 아침 복귀는 정상이라고 기록했지만, 시각별 실행 로그와 약 6분이라는 실측 시간의 근거는 확인하지 못했어요. 자동 용량 조절도 별도 검증 대상으로 남아 있어요.
