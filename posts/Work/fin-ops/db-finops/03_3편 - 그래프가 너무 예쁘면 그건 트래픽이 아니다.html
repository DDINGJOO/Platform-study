3편. 평평한 DB 지표에서 커넥션 풀 검증 쿼리를 의심한 이유 ← 지금 이 글

DB 읽기 전용 인스턴스의 92일치 지표를 조회했는데, 쿼리 수와 CPU 사용률의 변동 폭이 작았어요.

reader Queries p10 6.86 p50 6.97 p95 7.25 p99 7.34 reader SelectThroughput p10 2.91 p50 2.94 p95 3.01 p99 3.05 reader CPUUtilization p10 12.94 p50 13.55 p95 14.18 p99 14.32

p10과 p99는 측정값을 낮은 순서로 나열했을 때 각각 10%, 99% 지점의 값이에요. 이 두 값의 차이가 SELECT에서는 초당 0.14건, CPU 사용률에서는 약 1.4%p였어요.

처음에는 부하가 안정적이라고 생각했어요. 그러다 사용자 요청에 따라 변하는 쿼리보다 일정하게 실행되는 쿼리가 많은 건 아닌지 확인해 보기로 했어요. 변동 폭만으로 둘을 구분할 수는 없으니 시간대별 차이부터 살펴봤습니다.

1. 업무시간과 야간의 차이가 작았어요

사용자 요청이 부하의 대부분이라면 새벽 4시와 오전 10시 사이에도 차이가 있을 거라고 예상했어요. 그 예상과 실제 지표가 맞는지 보려고 업무시간과 야간을 나눴습니다.

업무시간은 09~18시, 야간은 18~09시로 나눠 쿼리 수를 비교했어요.

reader 업무 09-18 7.09 / 야간 18-09 6.94 → 차이 2.2%

업무시간의 값이 야간보다 2.2% 높았어요. 시간대에 따른 차이가 크지 않았습니다.

이 결과를 보고 사용자 요청과 무관하게 반복되는 쿼리가 있는지 살펴봤어요. 다만 하루 주기가 뚜렷하지 않다는 관측만으로 사용자 요청이 없다고 결론 내리지는 못합니다.

그림 1. 하루 주기가 있는 부하와 관측한 지표의 차이

2. 커넥션 풀의 검증 쿼리를 의심했어요

커넥션 풀은 DB 연결을 미리 유지해 두었다가 요청에 재사용하는 기능이에요. 유지 중인 연결이 끊겼을 수 있으므로, 연결을 사용할 수 있는지 확인하는 검증 과정이 필요합니다.

당시에는 풀이 연결을 점검할 때 보내는 가벼운 검증 쿼리가 이 부하를 만들었다고 판단했어요. 유휴 연결을 주기적으로 점검한다면 사용자 요청이 없어도 일정한 쿼리 수가 관측될 수 있다고 본 거예요.

애플리케이션 요청 없어도 풀이 유휴 커넥션을 주기적으로 점검 → 일정 간격 쿼리 풀 크기가 고정이면 그 빈도도 고정 → 낮과 밤이 같다

당시 확인한 접속 URL은 쓰기·읽기 두 엔드포인트를 모두 참조하고 있었어요. 이를 보고 드라이버가 양쪽에 커넥션 풀을 유지하지만 애플리케이션 쿼리는 쓰기 쪽으로 보내고, 읽기 쪽에는 검증 쿼리만 보낸다고 해석했습니다.

이 해석에 따르면 읽기 인스턴스에서 관측한 쿼리는 사용자 요청을 처리하는 부하보다 연결을 유지하기 위한 상시 부하에 가까워요. 읽기 인스턴스의 쓰기 지표가 92일 내내 0이었던 점도 함께 확인했지만, 그 값만으로 조회 쿼리의 용도를 구분할 수는 없어요.

💡 쓰기 노드의 시간대별 차이도 비교했어요
쓰기 노드도 업무시간의 부하 증가가 3.7%였어요. 사용자 요청에 따른 증가분이 크지 않다고 보고 상시 부하의 비중을 함께 살펴봤습니다. 다만 이 비율만으로 검증 쿼리의 비중까지 계산한 것은 아니에요.

3. 확인한 근거와 빠뜨린 설정 비교

검증 쿼리가 원인이라는 판단에는 추가 확인이 필요했어요. 아래는 당시 근거로 정리했던 항목입니다.

① 쓰기가 92일 내내 정확히 0 사용자 트래픽이면 읽기 전용 노드라도 0 이 나오기 어렵다 검증 쿼리는 SELECT 하나뿐이므로 0 이 자연스럽다 ② 접속 URL 이 두 엔드포인트를 모두 참조한다 드라이버가 양쪽에 풀을 유지하는 구조 → 검증 쿼리만 흘러가는 경로가 설명된다 ③ 분포 폭이 SELECT 0.14/초 기계적 신호의 특징

쓰기 지표와 접속 URL은 각각 확인한 항목이지만, 둘이 있다는 이유만으로 가설이 확정되지는 않아요. 특히 ①의 쓰기 0은 사용자 조회가 없다는 직접 증거가 되기 어렵습니다. ③의 좁은 분포도 쿼리의 출처를 직접 확인한 결과는 아니므로, 세 항목을 확정 근거로 세는 데에는 한계가 있어요.

그림 2. 쓰기 지표와 접속 URL을 확인했지만 가설은 남았어요

다음으로 할 수 있었던 확인은 풀 설정과 관측값을 비교하는 일이었어요. 아래는 연결 수와 검증 주기로 예상 쿼리 수를 계산하는 예시입니다. 실제 풀 설정을 확인한 결과는 아니에요.

상시 QPS ≈ 유지하는 커넥션 수 ÷ 검증 주기(초) 관측값 SELECT 2.94/초 를 이 식에 넣으면 커넥션 30개 / 10초 주기 → 3.0/초 거의 일치 커넥션 10개 / 10초 주기 → 1.0/초 안 맞는다

관측값인 초당 SELECT 2.94건이 설정에서 예상한 빈도와 비슷한지 비교하려던 계산이에요. 값이 비슷하면 가설을 뒷받침할 수 있고, 차이가 크면 검증 쿼리 외의 부하나 계산 조건을 다시 확인해야 합니다.

당시에는 이 설정 비교를 하지 않았어요. 그래프와 접속 URL을 보고 검증 쿼리를 의심한 단계까지 확인했고, 풀 설정으로 예상 빈도를 계산해 대조하지는 못했습니다.

4. 그래프를 해석하기 전에 집계 조건을 확인해요

이후에는 아래 특징을 발견하면 일정하게 실행되는 쿼리가 있는지 살펴보기로 했어요. 다만 각 항목을 사용자 요청의 유무를 확정하는 기준으로 쓰기에는 부족합니다.

1. 하루 주기로 출렁이는가 아니오 → 사람이 만든 부하가 아닐 가능성 2. 분위수 폭이 비정상적으로 좁은가 p10~p99 가 소수점 두 자리 안 → 기계적 신호 3. 업무시간 / 야간 비율이 1에 가까운가 가깝다 → 사용자와 무관한 부하

변동이 작다는 사실만 보고 부하가 안정적이라고 판단하면 상시 쿼리의 비중을 놓칠 수 있어요. 반대로 위 특징만으로 읽기 인스턴스가 필요 없다고 판단해서도 안 됩니다. 먼저 실제로 어떤 쿼리를 처리하는지 확인할 필요가 있어요.

기존에 요청을 처리하던 노드의 그래프가 갑자기 평평해진 경우에도 원인을 따로 확인해야 해요. 요청이 전달되는 경로나 앞단 캐시의 처리 여부가 달라졌을 가능성도 함께 살펴볼 수 있습니다.

⚠️ 평균값으로 집계하면 변동이 작아 보일 수 있어요
집계 해상도는 지표를 얼마 간격으로 묶어 보는지를 뜻해요. 1시간 평균에서는 그 안의 짧은 변동이 잘 드러나지 않을 수 있습니다.

당시에는 일부 지표를 1시간 평균으로 해석했지만, 실제 조회의 Period·Statistic은 확인하지 못했어요. 따라서 좁은 분포를 검증 쿼리의 근거로 삼기 전에 조회 조건을 확인할 필요가 있었어요. 짧은 구간을 세밀한 해상도로 다시 조회하는 확인도 필요합니다.
✍️ 확인한 내용과 남은 검증
읽기 인스턴스의 시간대별 차이와 좁은 분포, 접속 URL을 보고 커넥션 풀의 검증 쿼리가 주된 부하라고 판단했어요. 다만 쓰기 0이나 평평한 그래프만으로 사용자 조회가 없다고 확정할 수는 없습니다.

풀 설정으로 예상 쿼리 수를 계산해 대조하지 않았고, 일부 지표를 1시간 평균으로 해석했지만 실제 Period·Statistic은 확인하지 못했어요. 가설을 더 확인하려면 실제 풀 설정과 지표의 집계 조건을 함께 확인해야 합니다.
