1편. Aurora 리더 삭제 전 CloudWatch 판정 기준을 다시 확인한 이유 ← 지금 이 글

Aurora 클러스터에 쓰기를 처리하는 writer 하나와 읽기용 reader 하나가 있었어요. 두 인스턴스는 같은 사양이었고, 각각 같은 비용이 들고 있었습니다.

92일치 지표에서 reader의 쓰기는 계속 0이었어요. 읽기 부하도 거의 일정해서 실제 서비스 쿼리를 처리하는지 확인하고, reader를 삭제할 수 있을지 검토했습니다.

삭제 판단을 위해 CloudWatch 지표를 모아 판정표를 만들었어요. 그런데 표를 다시 확인하면서 CPU 기준선, 지표 해상도, 지연 단위를 잘못 해석한 부분을 찾았습니다. 부하가 낮아 보인다는 것만으로 삭제해도 된다고 판단하기는 어려웠어요.

1. reader의 일정한 쿼리를 검증 쿼리로 해석했어요

먼저 reader의 지표 분포를 봤어요. 아래의 p10, p50, p95, p99는 측정값을 작은 순서로 놓았을 때 각각 10%, 50%, 95%, 99% 지점의 값입니다.

reader Queries p10 6.86 p50 6.97 p95 7.25 p99 7.34 reader SelectThroughput p10 2.91 p50 2.94 p95 3.01 p99 3.05 reader CPUUtilization p10 12.94 p50 13.55 p95 14.18 p99 14.32 reader DMLThroughput 92일 내내 0.00

SELECT 처리량의 p10과 p99 차이는 0.14/초였어요. 시간대에 따른 서비스 사용량이 이 분포에 드러나지 않는다고 보고, 쿼리가 어느 인스턴스로 가는지 설정을 확인했습니다.

커넥션 URL에서 드라이버는 writer와 reader의 접속 주소인 엔드포인트를 둘 다 참조하고 있었어요. 이를 보고 서비스 쿼리는 writer가 처리하고 reader에는 커넥션 풀의 연결 상태 확인 쿼리가 간다고 해석했어요. 다만 두 호스트를 참조하는 URL과 쓰기 0만으로 사용자 SELECT가 없다고 확정할 수는 없어요. 실제 드라이버 라우팅과 SQL 출처, 풀 설정을 대조하는 확인은 남아 있었어요.

그림 1. URL과 지표로 세운 쿼리 경로 가설. 실제 서비스 쿼리의 전체 경로를 확인한 결과는 아니에요

2. 판정표의 기준선에는 근거가 없었어요

CloudWatch에서 writer와 reader의 측정값을 나눠 보고, 월별 추세와 분위수, 최댓값도 따로 정리했어요. 문제는 측정값에 안전 여부를 판단할 기준을 붙이는 과정에 있었습니다.

판정표의 오른쪽 열에는 CPU 70% 미만, 크레딧 500 초과, 커넥션 1500 미만, 지연 50ms 미만이라고 적었어요. 모든 항목을 통과로 표시했지만, 이 기준값들은 근거를 확인하지 않고 제가 정한 숫자였습니다.

표에 빈칸을 두기 싫어서 넣은 기준이었어요. 그런데 삭제해도 되는지를 판단하려면 현재 측정값과 비교할 기준에 근거가 있어야 합니다. 그 근거를 확인하지 않은 채로는 그래프가 낮아 보인다는 인상을 넘어서기 어려웠어요.

기준값과 해석을 하나씩 다시 확인했어요. 그중 세 가지는 같은 문서의 다른 수치와 맞춰 보거나 단위와 집계 조건을 확인했어야 할 오류였습니다.

3. CPU 베이스라인은 30%가 아니라 20%였어요

버스터블 인스턴스(t 계열)는 CPU 사용량이 정해진 베이스라인보다 낮으면 크레딧을 쌓고, 높으면 크레딧을 소모해요. 부하를 더 받아도 되는지 판단하려면 이 사양의 베이스라인부터 알아야 했습니다.

저는 근거를 확인하지 않고 30%라고 썼어요. 같은 문서에 적어 둔 크레딧 상한과 vCPU 수로 다시 계산하면 다른 값이 나옵니다.

CPUCreditBalance 최대 576 (92일간 min 569.33) 576 = 시간당 적립 크레딧 x 24시간 -> 시간당 24 크레딧 크레딧 1개 = vCPU 1개를 100%로 1분 돌릴 권리 이 사양 = 2 vCPU 1시간 예산 = 2 x 60 = 120 vCPU분 베이스라인 = 24 / 120 = 20%

이 사양의 베이스라인은 20%였고, 제가 쓴 30%는 한 단계 위 사양의 값이었어요. 10%p 차이를 반영하니 reader를 제거한 뒤의 크레딧 추정도 달라졌습니다.

내 가정(30%) 실제(20%) 현재 avg 16.4% 여유 있음 여유 3.6%p (크레딧 만점의 이유) 현재 p99 20.85% 여유 9%p 거의 베이스라인 위 제거 후 avg 18~20% 여유 있음 적립이 0에 수렴 제거 후 p99 23~25% "베이스라인 아래" 베이스라인 초과 -> 소모

당시에는 "베이스라인 30% 아래를 유지하므로 크레딧 소모가 계속 발생하지 않습니다"라고 적었어요. 베이스라인이 20%라면 같은 추정치로 그 결론을 낼 수 없습니다.

92일간 크레딧 잔량이 576에서 569까지만 내려갔다는 실측은 남아 있었어요. 관찰한 잔량이 상한 근처를 유지했다는 근거입니다. 다만 reader 제거 후에도 같을지는 별도로 확인해야 해서, 잘못된 베이스라인에 기대어 삭제 가능 여부를 확정할 수는 없었어요.

그림 2. 베이스라인을 바로잡으니 제거 후 크레딧 소모를 다시 검토해야 했어요

4. 92일치 지표의 해상도와 단위를 다시 봤어요

문서에 이런 문장을 썼어요. "2,208시간 동안 p10~p99의 차이가 SELECT 0.14/초입니다."

2,208 = 92 x 24예요. 당시에는 시간당 데이터포인트로 해석했지만, 이 곱셈만으로 실제 반환 개수나 Average 집계를 확인할 수는 없어요. 원래 조회의 Period·Statistics와 원본 시계열을 확보하지 못해 정확한 집계 조건은 확인하지 못했어요.

CloudWatch는 오래된 데이터를 원본 해상도로 보관하지 않아요.

1분 해상도 15일까지 5분 해상도 63일까지 1시간 해상도 455일까지 92일치를 한 번에 조회하면 -> 구간이 세 조각으로 쪼개진다 [-------- 1시간 평균 --------][--- 5분 ---][- 1분 -] 92일 전 63일 전 15일 전 오늘

위 인용에서 조회 결과가 자동으로 세 구간으로 나뉜다는 설명은 정정해야 해요. 보존 가능한 해상도와 요청한 Period는 다른 조건이에요. GetMetricStatistics는 요청 Period로 집계하며 63일보다 오래된 시작 시각에는 3600초의 배수가 필요해요. 최근 구간을 세밀하게 보려면 별도 조회 조건을 정해야 해요.

집계 조건에 따라 두 가지 해석도 달라져요.

첫째, 시간별 평균 중 가장 큰 값을 "절대 최댓값"이라고 부르면 안 됐어요. 1시간 평균 62%만으로는 그 시간 안의 최고 CPU 사용률을 알 수 없습니다. 순간 CPU가 90%까지 올라갔다가 낮아졌어도 평균은 62%일 수 있어요. 따라서 당시 값이 시간별 Average의 최댓값이었다면, 그것을 원래 측정값의 최고점으로 볼 수는 없어요. 실제 Statistic을 확인해야 해요.

둘째, reader의 분포가 일정하게 보이는 데에는 집계 간격도 영향을 줄 수 있어요. 1시간 평균에서는 짧은 부하 변화가 잘 드러나지 않습니다. 분포만 보고 서비스 트래픽이 아니라고 단정했던 판단은 근거가 부족했어요.

reader의 쓰기가 0이라는 측정값과 URL 설정 확인 결과는 남아 있었어요. 하지만 분포 모양까지 별도의 근거로 세기는 어려웠습니다. URL에서 추정한 쿼리 경로와 실제 SQL 출처 확인, 집계된 지표의 해석을 구분해야 했어요.

⚠️ WriteLatency의 단위를 잘못 적었어요
판정표에 WriteLatency max 0.01ms vs 기준 50ms 라고 쓰고 "여유 5000배"라며 넘겼어요.

그런데 CloudWatch의 ReadLatency · WriteLatency 단위는 밀리초가 아니라 초입니다.
• 제 해석: 0.01ms = 10마이크로초
• 실제 단위로 환산한 값: 0.01초 = 10ms

제가 정한 50ms 기준과 비교하면 5000배가 아니라 5배 차이예요. 단위를 고쳐도 표의 통과 표시는 같았지만, 차이의 크기를 잘못 설명하고 있었습니다. 이 비교만으로 50ms라는 기준 자체가 타당해지는 것도 아니에요.
그림 3. 초를 밀리초로 잘못 읽어 기준과의 차이를 1000배 크게 계산했어요

5. 배치를 최적화한 뒤 reader 삭제를 판단하기로 했어요

짧게 부하가 높아지는 구간도 확인해야 했어요. writer Queries(초당 쿼리 수)의 p99는 약 11, 최댓값은 약 102로 차이가 컸어요. 이 값의 집계 Period와 Statistic은 확인하지 못했어요. 처음에는 "1% 미만이니 예외"라고 썼지만, 92일의 1%가 얼마인지 시간으로 계산해 봤어요.

92일 x 24시간 x 60분 = 132,480분 1% = 1,324.8분 = 약 22시간 = 하루 14.4분

1%는 약 22시간이고 하루 평균으로 나누면 약 15분에 해당해요. 이는 전체 기간의 비율을 환산한 규모이며, 높은 부하가 매일 그 시간만큼 지속됐다는 뜻은 아니에요. 당시에는 매일 실행되는 배치와 관련된 부하로 해석했지만, 이 요약 통계만으로 반복 시각이나 원인을 확정할 수는 없어요. 실제 시계열과 배치 로그 대조가 필요했어요.

배치 최적화와 인스턴스 축소를 동시에 적용하면, 변경 후 CPU가 예상과 다를 때 어느 변경의 영향인지 구분하기 어려워요. 두 작업을 나누어 진행하기로 했습니다.

배치의 부하를 먼저 줄이고, 결과를 확인한 다음 reader 삭제 여부를 판단하기로 했어요. reader를 먼저 제거하면 배치 최적화 효과를 확인하기 전에 인스턴스 용량부터 줄어듭니다. 두 작업 사이의 관찰 기간에는 최근 15일 이내의 1분 해상도 지표를 확인할 계획이었어요. 이미 확보한 92일 추세에 더해 짧은 부하 변화도 살펴보려는 목적이에요. CPU처럼 1분 주기로 제공되는 지표와 5분 주기인 Aurora CPU 크레딧 지표는 나눠 봐야 해요. 15일 넘는 관찰 구간 전체를 분 단위로 보려면 오래된 값이 집계되기 전에 별도로 저장해야 하지만, 그 수집을 실행한 결과는 여기에 포함하지 않았어요.

관찰 결과에 따라 삭제 여부를 판단할 수 있도록 당시 통과 조건도 숫자로 적었어요. 크레딧 회복 추세를 주로 보고, CPU와 배치 실행 시간, 쿼리 수를 함께 확인하는 계획이었습니다.

관찰 기간 최소 15일 1분 해상도 보존 한계. 배치 주기 1회 이상 포함 통과 지표 CPUCreditBalance 추세 절대값이 아니라 기울기. 배치 드레인 후 24시간 내 만점 복귀 보조 지표 writer CPU avg <= 15% 베이스라인 20% - 리더 흡수분 2~4%p = 제거 후 17~18% 검증 지표 배치 실행 시간 + 쿼리수 최적화가 실제로 됐는지. 안 줄면 게이트 자체가 무의미

위 인용의 관찰 기간 최소 15일은 당시 계획이에요. 1분 해상도의 보존 한계가 실험의 최소 기간을 정해 주지는 않으므로, 실제 관찰 길이는 배치와 업무 주기를 기준으로 정해야 해요. CPU 보조 산식도 잘못됐어요. writer 평균 15%를 조건으로 reader 흡수분 2~4%p를 단순히 더하면 17~19%예요. 현재 실측 평균 16.4%에 같은 가정을 적용하면 18.4~20.4%가 되므로 두 시나리오를 구분해야 해요. 어느 값도 제거 후 실측이 아니며, 기준선에서 흡수분을 빼는 인용 식으로 통과를 확정할 수는 없어요.

크레딧 잔량을 1차 지표로 고른 이유는 CPU 사용률이 베이스라인을 얼마나 오래 넘었는지 함께 보려는 것이었어요. CPU 사용률의 특정 분위수만 비교하는 대신, 배치 실행 후 크레딧이 감소하고 회복하는 추세를 확인하기로 했습니다.

⚠️ 통과 조건을 적용하기 전에 확인할 것
일반적인 버스터블 인스턴스 설명에서 나오는 standard와 달리, 여기서 다룬 Aurora T계열은 unlimited 모드예요. 이 상품의 unlimited 동작을 기준으로 크레딧을 해석해야 해요.

unlimited면 크레딧을 소진한 뒤의 초과 사용분이 요금으로 청구될 수 있어요. 크레딧 조건을 볼 때 성능뿐 아니라 비용도 고려해야 합니다.
잔량이 0이라는 이유만으로 CPU가 자동 제한된다고 판단하지 말고, 삭제로 줄어드는 비용과 초과 크레딧 사용 비용을 함께 봐야 해요. 이번 분석에서 초과 요금이 실제 발생했는지는 확인하지 않았어요.
그림 4. 배치 최적화 효과를 확인한 뒤 reader 삭제 여부를 판단해요

6. 판정표에 남겨야 할 확인 항목

판정표를 다시 보면서 찾은 오류는 아래 세 가지였어요. 측정값을 옮기는 데 그치지 않고 사양, 집계 조건, 단위를 대조했어야 했습니다.

베이스라인 30% -> 20% 문서 안의 576 으로 검산 가능했다 2,208 데이터포인트 -> 1시간 그 숫자 자체가 해상도의 증거였다 WriteLatency 0.01ms -> 0.01초 10마이크로초는 물리적으로 불가능했다

위 인용의 “2,208개 자체가 해상도의 증거”와 “10마이크로초는 물리적으로 불가능”이라는 설명도 근거가 부족해요. 실제 집계 간격은 조회 조건으로 확인해야 하고, 지연 단위 정정의 근거는 공식 지표 정의예요. 이 지표의 0.01초가 10ms라는 환산을 확인한 것이지 보편적인 최소 지연을 검증한 것은 아니에요.

크레딧 상한과 vCPU 수는 베이스라인 계산을 확인할 단서였어요. 조회 기간과 집계 간격, 지연 지표의 단위도 판정표에 함께 적어야 했습니다. 그래야 수치가 달라졌을 때 같은 조건으로 비교할 수 있어요.

기준값을 적었다면 그 값을 어디서 확인했는지도 남겨야 했어요. 이번에는 측정값은 모았지만, 비교 기준의 근거를 확인하는 과정이 빠져 있었습니다.

판정표의 지표 여덟 개가 모두 CPU, 메모리, 커넥션 같은 자원 지표였다는 점도 부족했어요. 예를 들어 배치 실행 시간이 40분에서 60분으로 늘면 CPU가 18%라는 이유만으로 통과시켜서는 안 됩니다. 1.5배 느려졌다는 결과를 놓치지 않으려면 애플리케이션에서 배치 실행 시간도 수집해야 해요. 당시 표에는 그 항목이 빠져 있었습니다.
