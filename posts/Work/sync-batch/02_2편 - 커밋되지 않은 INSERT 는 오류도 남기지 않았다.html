1편. 9건이 전부 21시 3분에서 9분 사이였다
2편. 커밋되지 않은 INSERT 는 오류도 남기지 않았다 ← 지금 이 글

운영 담당자에게서 질문이 하나 왔어요. 건 하나를 가리키면서, 출금을 시도하고 실패한 이력이 상세 화면에 코멘트로 남아야 하는데 아무것도 없다는 거였습니다. 2026년 10월 8일이었어요.

처음엔 그 한 건만 이상한 줄 알았습니다. 그래서 같은 종류의 코멘트를 날짜순으로 뽑아 봤어요. 마지막이 9월 28일 오후 2시 44분이었습니다. 그 뒤로는 한 건도 없었어요. 확인하던 당일 낮에 정상으로 끝난 출금 건에도 코멘트가 없었고요. 한 건이 빠진 게 아니라 열흘째 전량이 빠지고 있었습니다.

그런데 오류 로그는 0건이었어요. 저장에 실패하면 에러 로그를 남기도록 코드에 적혀 있는데도요. 쓰기가 실패한 게 아니라, 실패하지도 않은 채로 사라지고 있었습니다. 이 글은 그 열흘 동안 아무도 모를 수 있었던 이유와, 그날 오후에 고친 방법을 적은 기록이에요. 이 글의 시각은 모두 한국시간(KST) 기준입니다.

1. 단서가 사람 한 명이었어요

버그를 쫓을 때는 보통 남은 기록부터 모읍니다. 로그, 실패한 요청, 깨진 행. 늘어놓고 모양을 보면 공통점이 원인을 지목해 주거든요. 그런데 이번엔 늘어놓을 데이터가 아예 없었습니다. 없어진 것은 그래프에 그려지지 않습니다.

모니터링이 보는 건 대부분 "일어난 일"이에요. 오류율이 올라갔다, 응답이 느려졌다, 큐가 쌓였다, 재시도가 늘었다. 이번 실패는 그중 어디에도 걸리지 않았습니다. 예외가 안 났으니 오류율은 평소 그대로였고, 쓰기 한 번이 빠진다고 응답이 느려지지도 않았어요. 알림을 걸 수 있는 신호 자체가 만들어지지 않았습니다.

그래서 유일하게 남은 감지기가 사람이었어요. 그 화면을 매일 보는 사람이 "있어야 할 게 없다"고 느낀 것이 시작이었습니다. 그리고 이 종류의 감지기는 지연이 깁니다. 운영 담당자가 하필 코멘트가 필요한 건을 만나야 하고, 비어 있는 게 원래 그런 건지 고장인지 의심해야 하고, 그걸 물어봐 줘야 하거든요. 열흘이 걸린 이유가 거기에 있었어요.

처음 로그를 뒤졌을 때는 0건이라는 결과를 "코멘트를 남기는 쪽이 잘 돌았다"는 뜻으로 읽을 뻔했습니다. 저장 코드에 예외를 잡아 에러 로그를 남기는 처리가 들어 있었으니까요. 그런데 0건에는 뜻이 두 개 있어요. 아무 문제가 없었거나, 예외라는 사건 자체가 일어나지 않았거나. 롤백은 예외가 아닙니다. 커밋되지 않은 트랜잭션이 정리되는 건 데이터베이스 입장에서 정상 동작이라, 애플리케이션에 아무 말도 하지 않아요.

⚠️ 로그 0건을 무죄로 읽기 전에
"에러 로그가 없다"는 "에러가 없었다"가 아니라 "예외가 던져지지 않았다"만 뜻해요. 이 둘이 갈라지는 지점이 몇 군데 있습니다. • 커밋되지 않고 끝난 쓰기: 이 글의 경우예요. SQL 은 성공하고 반영만 안 됩니다. • 잡아서 삼킨 예외: 빈 catch 블록이나 로그 수준이 debug 로 내려간 자리. • 조건문으로 건너뛴 경로: 분기에 걸려 애초에 실행되지 않은 코드는 실패하지도 않아요. 셋 다 "성공 로그도 없다"는 공통점이 있으니, 실패 로그가 아니라 성공 건수를 세는 지표가 있어야 보입니다.

2. 커밋되지 않은 INSERT 는 어디로 갔나

1편은 트랜잭션이 너무 길어서 생긴 일이었어요. 이번은 반대로 트랜잭션이 아예 없어서 생긴 일입니다. 코드는 이런 모양이었어요.

// {출금 코멘트 저장소} @Repository public class CommentWriter { private final JdbcTemplate jdbc; // 엔티티를 못 써서 JDBC 로 직접 쓴다 public void insert(Long id, Long userId, String content) { // <- 트랜잭션이 없다 jdbc.update(INSERT_SQL, id, userId, content, now, now); } } // 출금 결과를 받아 코멘트를 남기는 리스너 @Async("commentEventExecutor") @EventListener public void handle(CommentEvent event) { try { writer.insert(event.id(), event.userId(), event.content()); } catch (Exception e) { log.error("출금 코멘트 저장 실패 - id: {}", event.id(), e); // <- 한 번도 찍히지 않았다 } }

위 코드를 한 줄로 풀면 이래요. 출금 처리가 끝나면 이벤트를 하나 던지고, 리스너가 그걸 받아 다른 스레드에서 코멘트 한 행을 넣는다. 실패하면 로그를 남기도록 되어 있고요.

왜 하필 JDBC 로 직접 쓰고 있었을까요. 9월 7일 이후로 배치에서 돌 때만 코멘트가 누락되는 문제가 따로 있었어요. 리스너가 다른 모듈에 있었고 배치가 그 모듈을 읽지 않았거든요. 9월 28일에 그걸 고치려고 리스너를 공용 모듈로 옮겼습니다. 그런데 코멘트 테이블의 엔티티는 옮겨 올 수 없는 쪽에 있어서, 엔티티를 저장하는 방식 대신 SQL 을 직접 실행하는 방식으로 바꿨어요. 코멘트는 그때부터 배치에서도 남게 됐지만, 엔티티 저장이 대신 해 주던 커밋까지 같이 사라졌습니다.

📖 용어: 트랜잭션 (transaction)
데이터베이스에 보내는 여러 개의 쓰기를 "전부 반영" 아니면 "전부 취소" 중 하나로 묶는 단위예요. 커밋을 해야 반영되고, 커밋 없이 끝나면 되돌려집니다. 이 글의 사고는 그 커밋을 아무도 부르지 않아서 생겼어요.

남은 조건은 운영 환경에 있었어요. 운영 커넥션 풀 설정에 autoCommit: false 가 들어 있습니다. 자동 커밋이 꺼져 있으면 빌려 온 커넥션에서 쓰기를 한 번 날리는 순간 트랜잭션이 열려요. 그 행은 열린 트랜잭션 안에 머물고, 누군가 커밋을 불러야 확정됩니다. 그런데 이 메서드에는 트랜잭션 경계가 없으니 커밋을 부를 주체가 없었어요. 그대로 커넥션이 풀로 반납되고, 풀은 다음 사람에게 깨끗한 커넥션을 주려고 반납 시점에 롤백합니다.

📖 용어: 자동 커밋 (autoCommit)
켜져 있으면 쿼리 한 줄을 실행할 때마다 그 자리에서 커밋됩니다. 꺼져 있으면 커밋을 직접 불러야 반영돼요. 커넥션 풀은 보통 이 값을 켠 상태로 시작하지만, 여기서는 설정 파일에서 꺼 두었습니다.

그래서 두 문장이 동시에 참이었어요. INSERT 는 성공했습니다. 그리고 그 행은 데이터베이스에 남지 않았습니다. 둘 사이에 예외가 끼어들 자리가 없어요. 조용한 건 운이 나빠서가 아니라 구조가 그랬던 겁니다.

그림 1. 예외가 없으면 감시 장치가 볼 것도 없다

3. 테스트도 리뷰도 통과했는데 안 걸렸어요

9월 28일 변경은 테스트를 통과했고 리뷰도 거쳤어요. 그런데도 열흘을 갔습니다. 안 걸린 이유는 단순했어요. 그 테스트들이 커밋을 보지 않았거든요. 전부 가짜 객체로 "무엇을 호출했나"를 확인하는 종류였고, 코멘트를 쓰는 저장소에는 테스트가 아예 없었습니다. 리뷰도 마찬가지예요. 쓰기 메서드 한 줄은 그 자체로는 멀쩡해 보이고, 커밋이 빠졌다는 건 그 코드가 어느 풀 위에서 도는지를 같이 봐야 보입니다.

그리고 여기서 제가 한 번 틀린 것도 적어 둘게요. 작업 문서에 "로컬은 자동 커밋이라 재현되지 않았다"고 한 줄을 적었는데, 나중에 환경별 설정 파일을 전부 열어 보니 로컬 프로필에도 자동 커밋이 꺼져 있었습니다. 환경마다 값이 갈려서 못 잡은 게 아니라, 이 경로를 실제 데이터베이스에 붙여 돌려 본 적이 한 번도 없어서 못 잡은 거였어요. 설정은 기억으로 말하면 안 되는 종류의 정보였습니다.

📖 용어: 커넥션 풀 (connection pool)
데이터베이스 연결을 미리 몇 개 만들어 두고 빌려 주고 돌려받는 창고예요. 연결을 그때그때 새로 맺는 비용이 커서 씁니다. 자동 커밋 여부, 최대 개수, 수명 같은 걸 여기서 정하기 때문에, 같은 코드의 동작이 이 설정에 따라 달라져요.

그래서 원인을 못 박으려고 재현을 따로 돌렸어요. 같은 리스너를 자동 커밋이 꺼진 풀과 켜진 풀에서 각각 실행하고 테이블을 세어 봤습니다. 꺼진 쪽은 0, 켜진 쪽은 1. 이 비교가 나오고 나서야 "트랜잭션 없는 쓰기"가 가설이 아니라 원인이 됐어요. 운영 로그에서는 확인할 길이 없었으니, 조건을 직접 만들어 재현하는 것 말고는 방법이 없었습니다.

그림 2. 커밋이 없을 때 결과를 가르는 건 코드가 아니라 풀 설정 한 줄이다

4. 비동기 리스너는 호출한 쪽의 트랜잭션을 따라가지 않아요

여기서 한 번 더 걸리기 쉬운 전제가 있어요. 출금 처리 자체는 트랜잭션 안에서 돕니다. 그 안에서 이벤트를 발행했으니 리스너의 쓰기도 같은 트랜잭션에 묶일 것 같거든요. 그렇지 않습니다.

트랜잭션은 스레드에 묶여 있어요. 스프링은 지금 열린 트랜잭션과 커넥션을 스레드별 저장소에 넣어 두고, 같은 스레드에서 쓰기가 일어날 때만 그걸 꺼내 씁니다. 리스너에 비동기 처리가 붙어 있으면 그 작업은 다른 스레드에서 돌고, 그 스레드에는 아무것도 들어 있지 않아요. 호출한 쪽의 트랜잭션은 경계를 넘어오지 않습니다.

📖 용어: 비동기 이벤트 리스너 (@Async + @EventListener)
어떤 일이 끝났다는 알림을 받아 뒷처리를 하는 코드인데, 알린 쪽을 기다리게 하지 않으려고 별도 스레드에서 실행해요. 코멘트 저장이 느리거나 실패해도 출금 처리는 그대로 끝나게 하려고 이렇게 떼어 놓았습니다.

그리고 이 분리는 실수가 아니라 의도였어요. 코멘트 한 줄 때문에 출금 처리가 되돌아가면 안 되니까 일부러 떼어 놓은 겁니다. 문제는 떼어 놓은 쪽에 트랜잭션을 따로 주지 않은 것이었어요. 분리의 대가를 반만 치른 셈입니다.

고칠 때는 @Transactional 을 리스너가 아니라 쓰기 메서드 쪽에 붙였어요. 리스너에 붙이면 나중에 다른 호출 경로가 생겼을 때 또 빠집니다. 쓰기 지점에 두면 호출한 쪽에 트랜잭션이 있으면 거기 합류하고, 없으면 새로 열어요. 경계는 호출하는 쪽이 아니라 반드시 지나가는 쪽에 둡니다.

💡 실무에서는 세 군데를 같이 봅니다
• 운영 풀의 자동 커밋 값: 환경별 설정 파일을 전부 열어 값을 직접 확인해요. 갈려 있으면 그 코드는 환경마다 다르게 동작하고, 전부 꺼져 있으면 트랜잭션 없는 쓰기는 어디서 돌든 사라집니다. • 엔티티를 거치지 않는 쓰기: SQL 을 직접 실행하는 자리는 프레임워크가 커밋을 대신 해 주지 않아요. 저장소 클래스 중 엔티티를 안 쓰는 것부터 트랜잭션 경계를 확인합니다. • 별도 스레드에서 도는 쓰기: 비동기 처리, 스케줄러, 직접 만든 스레드 안의 쓰기는 전부 호출자의 트랜잭션 밖이에요. 풀 설정을 통째로 자동 커밋으로 바꾸는 선택지도 있었지만, 그 설정을 공유하는 서비스 전체에 영향이 가서 접었습니다.
그림 3. 트랜잭션은 스레드 경계를 넘지 못한다

5. 결과가 아니라 커밋 호출을 보는 테스트

회귀 테스트를 짜려는데 바로 막혔어요. 가장 먼저 떠오르는 건 "코멘트를 저장하고 테이블에서 다시 읽어 한 행이 있는지 본다"입니다. 그런데 그 테스트는 이 버그를 못 잡아요. 테스트가 쓰는 데이터베이스는 보통 자동 커밋이고, 설령 아니어도 같은 트랜잭션 안에서는 커밋하지 않은 행이 그대로 보입니다. 고치기 전 코드로 돌려도 통과해 버려요.

그래서 보는 대상을 바꿨습니다. 저장 결과 대신 커밋이 불렸는지를 봤어요.

@Configuration @EnableTransactionManagement @Import(CommentWriter.class) static class Config { static final JdbcTemplate JDBC = mock(JdbcTemplate.class); static final PlatformTransactionManager TX = mock(PlatformTransactionManager.class); // ... 두 개를 빈으로 등록한다 } @Test @DisplayName("코멘트 insert 는 트랜잭션 안에서 실행되고 커밋된다" + " (운영 풀은 자동 커밋이 꺼져 있어 커밋이 없으면 롤백되어 코멘트가 사라진다)") void insert_commitsTransaction() { when(TX.getTransaction(any())).thenReturn(mock(TransactionStatus.class)); writer.insert(1L, 2L, "출금 실패 (2026-10-08) [2/3]"); verify(JDBC).update(anyString(), any(Object[].class)); verify(TX).commit(any(TransactionStatus.class)); // <- 이 한 줄이 회귀를 막는다 }

풀어 쓰면 이래요. 진짜 데이터베이스 대신 가짜 트랜잭션 관리자를 끼워 넣고, 쓰기 메서드를 한 번 부른 다음, 그 가짜가 커밋을 받았는지 확인합니다. 테이블은 쳐다보지도 않아요.

📖 용어: 목 객체 (mock)
진짜 객체 대신 끼워 넣는 가짜예요. 미리 정한 값을 돌려주고, 어떤 메서드가 몇 번 불렸는지 기록합니다. 그래서 "무슨 결과가 나왔나" 대신 "무엇을 호출했나"를 검증할 때 씁니다.
📖 용어: 회귀 테스트 (regression test)
한 번 고친 버그가 나중에 되살아나는지 감시하는 테스트예요. 그래서 "기능이 되는가"보다 "그 버그의 조건이 다시 생겼는가"를 겨냥해 짭니다.

이 테스트가 보는 건 데이터가 아니라 경계의 존재예요. 쓰기 메서드에 트랜잭션 경계가 걸려 있으면 커밋이 불리고, 누가 애너테이션을 지우면 커밋이 안 불려서 테스트가 깨집니다. 실제로 수정을 떼어 내고 돌려서 실패하는 것까지 확인했어요. 회귀 테스트가 지켜야 할 건 결과가 아니라 그 결과를 만든 조건입니다.

그리고 이 테스트는 사람에게 말을 거는 자리이기도 해요. 테스트 이름 옆에 "운영 풀은 자동 커밋이 꺼져 있어서 커밋이 없으면 코멘트가 사라진다"는 설명을 붙여 뒀습니다. 몇 달 뒤에 이 테스트가 깨진 사람이 verify(TX).commit(...) 한 줄만 보고 "왜 이런 걸 검사하지" 하며 지우는 일을 막으려고요.

6. 돌아오지 않는 것을 배포 노트에 적었어요

고치면 앞으로는 남습니다. 하지만 9월 28일 오후 2시 44분부터 배포 전까지는 돌아오지 않아요. 그 구간의 쓰기는 데이터베이스까지 갔다가 되돌려진 거라 복구할 원본이 테이블 어디에도 없습니다. 지워진 걸 되살리는 문제가 아니라 처음부터 기록되지 않은 것이라서요.

그래서 배포 노트에 두 문장을 나란히 적었어요. 코멘트가 다시 남는다는 문장과, 그 기간의 누락분은 복구되지 않는다는 문장이요. 수정 내용만 적으면 읽는 사람은 "이제 다 정상"으로 읽습니다. 그 화면을 근거로 일하는 사람에게는 그 열흘이 여전히 비어 있고, 비어 있다는 걸 모르면 "기록이 없으니 그런 일이 없었다"고 판단하게 돼요. 그게 이 사고의 진짜 잔여 위험입니다.

작업 문서의 "남은 일"에도 한 줄을 남겼어요. 다른 경로의 로그에 흔적이 남아 있는지, 남아 있다면 어디까지 복원할지 운영 쪽과 협의하는 일이요. 그 로그에도 보관 기한이 있어서 이건 기한이 있는 숙제입니다.

그리고 오늘은 배포 당일이에요. 그래서 확인 절차를 문서에 미리 적어 뒀습니다. 출금이 도는 시각들 뒤에 코멘트 행이 실제로 생기는지 조회해서 보는 거예요. 원인을 알아낸 것과 운영에서 확인한 것은 아직 다른 일입니다. 애초에 이 사고가 열흘을 간 이유가 "확인하지 않아도 되는 줄 알았던 것"이었으니까요.

✍️ 오늘의 요약
자동 커밋이 꺼진 커넥션 풀에서 트랜잭션 없이 쓰면, SQL 은 성공하고 행은 남지 않습니다. 예외가 없으니 로그도 없고요.

비동기 리스너는 호출한 쪽의 트랜잭션을 따라가지 않아요. 떼어 놓았으면 그쪽에도 경계를 줘야 하고, 그 경계는 호출 지점이 아니라 반드시 지나가는 쓰기 지점에 둡니다. 회귀 테스트는 저장 결과가 아니라 커밋 호출을 봐야 이 조건이 다시 생기는 걸 잡아낼 수 있어요.

실패가 조용하면 감지기는 사람 한 명으로 줄어듭니다. 그러니 성공 건수를 세는 지표를 두고, 고친 사실과 돌아오지 않는 사실을 같은 문서에 적어 두세요.
