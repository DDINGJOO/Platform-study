📚 어느 백엔드 저장소의 기록, 2편
1편. 중복 파일 9건의 발생 시각으로 정리 배치를 추적하기
2편. 비동기 JDBC 쓰기에서 빠진 커밋과 회귀 테스트의 검증 범위 ← 지금 이 글

운영 담당자가 상세 화면에 출금 실패 코멘트가 남지 않았다고 알려 줬어요. 출금을 시도한 이력이 코멘트로 보여야 하는데 비어 있다는 내용이었어요. 2026년 10월 8일이었어요.

처음에는 그 한 건만 빠진 줄 알고 같은 종류의 코멘트를 날짜순으로 조회했어요. 마지막 저장 시각은 9월 28일 오후 2시 44분이었고, 그 뒤로는 한 건도 없었어요. 확인 당일 낮에 정상으로 끝난 출금 건에도 코멘트가 없었어요. 조회한 범위에서는 열흘 동안 이 종류의 코멘트가 모두 누락된 상태였어요.

관련 오류 로그는 0건이었어요. 저장 중 예외가 발생하면 오류 로그를 남기도록 되어 있었지만, 로그만으로는 저장 여부를 알 수 없었어요. INSERT 실행 뒤 커밋이 이뤄졌는지 확인해야 했어요. 아래 시각은 모두 한국시간(KST) 기준이에요.

1. 화면의 누락과 오류 로그를 함께 확인했어요

이번에는 누락된 코멘트 자체에서 조사할 데이터를 얻을 수 없었어요. 저장된 코멘트의 마지막 시각과 관련 로그를 함께 확인해야 했어요.

저장 코드에는 예외를 기록하는 처리가 있었지만, 코멘트가 실제로 남았는지를 확인하는 것과는 달랐어요. INSERT가 예외 없이 끝난 뒤 커밋되지 않으면, 그 예외 처리만으로는 누락을 감지할 수 없어요.

조사는 화면을 사용하던 담당자의 제보로 시작됐어요. 코멘트가 필요한 건을 확인하다가 누락을 발견한 경우였어요. 다만 제보가 늦어진 이유를 이 사실 하나로 설명할 수는 없어요.

처음에는 오류 로그가 0건이라는 결과를 저장 코드가 정상 동작했다는 뜻으로 읽을 뻔했어요. 하지만 커밋되지 않은 쓰기가 커넥션 반납 때 롤백되는 과정은 INSERT 호출의 예외로 나타나지 않을 수 있어요. 오류 로그 유무와 저장 결과를 따로 확인해야 했어요.

⚠️ 오류 로그와 저장 성공은 따로 확인해요
오류 로그가 0건이면 해당 로그가 기록되지 않았다는 사실만 알 수 있어요. 커밋되지 않은 쓰기, 로그를 남기지 않고 처리한 예외, 조건문으로 실행을 건너뛴 경로를 구분해야 해요. 쓰기 누락까지 감지하려면 처리 대상 건수와 실제 저장 건수를 비교하는 방법도 필요해요. 당시 그런 지표를 추가했다는 의미는 아니에요.

2. INSERT 뒤에 커밋이 없었어요

1편에서는 배치의 긴 트랜잭션과 중복 저장 문제를 살펴봤어요. 발생 시각이 겹친다는 사실만으로 원인을 확정하거나, 롤백만으로 최종 중복을 설명할 수는 없어요. 이번에는 비동기 쓰기 메서드에 스프링이 관리하는 트랜잭션 경계가 없었던 문제를 확인했어요. 당시 코드의 형태는 다음과 같아요.

// {출금 코멘트 저장소} @Repository public class CommentWriter { private final JdbcTemplate jdbc; // 엔티티를 못 써서 JDBC 로 직접 쓴다 public void insert(Long id, Long userId, String content) { // <- 트랜잭션이 없다 jdbc.update(INSERT_SQL, id, userId, content, now, now); } } // 출금 결과를 받아 코멘트를 남기는 리스너 @Async("commentEventExecutor") @EventListener public void handle(CommentEvent event) { try { writer.insert(event.id(), event.userId(), event.content()); } catch (Exception e) { log.error("출금 코멘트 저장 실패 - id: {}", event.id(), e); // <- 한 번도 찍히지 않았다 } }

출금 결과 이벤트를 발행하면 리스너가 별도 스레드에서 코멘트 한 행을 INSERT해요. 이 호출에서 예외가 발생하면 오류 로그를 남기도록 되어 있었어요.

JDBC로 직접 쓰게 된 배경에는 앞선 누락 문제가 있었어요. 9월 7일 이후 배치에서 실행할 때만 코멘트가 누락됐는데, 리스너가 있는 모듈을 배치가 읽지 않았기 때문이었어요. 9월 28일 리스너를 공용 모듈로 옮겼지만 코멘트 테이블의 엔티티까지 옮길 수는 없어서, 엔티티 저장을 SQL 실행으로 바꿨어요. 배치에서도 리스너를 호출할 수 있게 됐지만, 기존 저장 방식에 있던 트랜잭션 경계를 새 쓰기 메서드에 두지 않았어요. 리스너가 호출되는 문제를 고친 뒤에도 저장을 확정하는 커밋은 빠져 있었어요.

📖 용어: 트랜잭션 (transaction)
데이터베이스의 작업을 함께 확정하거나 취소하는 단위예요. 여기서 트랜잭션 경계가 없었다는 말은 스프링이 시작과 커밋을 관리하지 않았다는 뜻이에요. 데이터베이스에서는 자동 커밋이 꺼진 커넥션의 쓰기가 커밋을 기다리고 있었어요.

당시 운영 커넥션 풀에는 autoCommit: false 설정이 있었어요. 자동 커밋이 꺼진 커넥션에서는 INSERT가 실행돼도 커밋 전까지 저장이 확정되지 않아요. 하지만 이 쓰기 메서드에는 커밋을 수행할 트랜잭션 경계가 없었어요. 사용한 커넥션은 풀로 반납됐고, 그때 커밋되지 않은 쓰기가 롤백됐어요.

📖 용어: 자동 커밋 (autoCommit)
켜져 있으면 SQL 문 실행을 마칠 때 자동으로 커밋해요. 꺼져 있으면 애플리케이션이나 트랜잭션 관리자가 커밋을 호출해야 해요. 당시에는 설정 파일에서 꺼 둔 상태였어요.

이 경로에서는 INSERT가 예외 없이 실행됐어도 행이 최종적으로 남지 않을 수 있었어요. 커밋 누락에 따른 롤백을 저장 호출의 예외 처리만으로 감지하지 못한 경우였어요.

그림 1. 이 경로에서는 커밋 누락이 INSERT 호출의 예외로 나타나지 않았어요

3. 기존 테스트는 실제 커밋을 확인하지 않았어요

9월 28일 변경은 테스트와 리뷰를 거쳤지만 누락을 발견하지 못했어요. 당시 테스트는 목 객체로 메서드 호출을 확인하는 방식이었고, 코멘트를 쓰는 저장소 자체에는 테스트가 없었어요. 실제 풀 설정에서 커밋되는지는 확인하지 않았어요. 코드 한 줄의 실행 여부와 그 쓰기의 커밋 여부가 다른 검사였던 셈이에요.

작업 문서에는 처음에 로컬은 자동 커밋이라 재현되지 않았다고 적었어요. 나중에 환경별 설정을 확인하니 로컬 프로필에도 자동 커밋이 꺼져 있었어요. 환경 차이 때문이라는 설명은 잘못됐어요. 이 저장 경로를 실제 데이터베이스에 연결해 확인하지 않은 것이 빠진 검사였어요.

📖 용어: 커넥션 풀 (connection pool)
데이터베이스 연결을 만들고 재사용하도록 관리하는 기능이에요. 자동 커밋 여부나 연결 최대 개수 등을 설정해요. 이 글에서는 커넥션 반납 때 커밋되지 않은 쓰기가 어떻게 처리되는지가 관련돼 있어요.

당시에는 같은 리스너를 자동 커밋이 꺼진 풀과 켜진 풀에서 각각 실행하고 행 수를 비교했어요. 기록된 결과는 꺼진 쪽이 0, 켜진 쪽이 1이었어요. 이 비교로 자동 커밋 설정과 커밋 누락이 저장 결과에 미치는 영향을 확인했어요. 운영에서 누락된 각 INSERT의 실행 과정을 로그로 추적한 것은 아니에요.

그림 2. 당시 재현에서는 자동 커밋 설정에 따라 저장된 행 수가 달랐어요

4. 비동기 리스너는 호출한 쪽의 트랜잭션을 따라가지 않아요

출금 처리는 트랜잭션 안에서 실행됐어요. 그 안에서 이벤트를 발행하더라도 별도 스레드에서 실행되는 리스너의 쓰기까지 같은 트랜잭션에 참여하는 것은 아니에요.

여기서 사용하는 스프링 트랜잭션은 스레드에 연결돼 있어요. 같은 스레드에서는 연결된 트랜잭션과 커넥션을 사용하지만, 비동기 리스너가 실행되는 별도 스레드에는 호출자의 트랜잭션이 전달되지 않아요. 따라서 리스너의 저장 경로에서 별도의 트랜잭션 경계를 확인해야 해요.

📖 용어: 비동기 이벤트 리스너 (@Async + @EventListener)
이벤트를 받아 별도 스레드에서 후속 작업을 실행하는 코드예요. 여기서는 코멘트 저장을 출금 처리와 분리하기 위해 사용했어요.

코멘트 저장이 실패해도 출금 처리까지 되돌리지 않으려고 비동기로 분리한 것이었어요. 문제는 별도 스레드에서 수행하는 쓰기에 트랜잭션 경계를 두지 않은 점이었어요.

수정할 때는 @Transactional을 리스너 대신 쓰기 메서드에 붙였어요. 다른 경로에서 이 저장 메서드를 호출하더라도 트랜잭션 처리를 적용하기 위해서였어요. 이 메서드가 스프링의 트랜잭션 처리를 통해 호출되면, 기존 트랜잭션이 있을 때는 참여하고 없을 때는 새로 시작해요.

💡 풀 설정과 쓰기 경로를 함께 확인해요
• 자동 커밋 설정: 로컬과 운영의 값을 직접 확인해요. 설정에 따라 트랜잭션 경계 누락이 드러나는 방식이 달라질 수 있어요.
• JDBC 쓰기의 트랜잭션 경계: SQL을 직접 실행하더라도 기존 트랜잭션에 참여할 수 있어요. 호출 경로에서 누가 커밋을 관리하는지 확인해야 해요.
• 별도 스레드의 쓰기: 호출자의 트랜잭션이 전달된다고 가정하지 않고, 해당 작업에 트랜잭션 처리가 적용되는지 확인해요.
풀 전체의 자동 커밋을 켜는 방법도 검토했지만, 설정을 공유하는 서비스 전체에 영향을 주므로 선택하지 않았어요.
그림 3. 호출자의 트랜잭션은 비동기 리스너에 전달되지 않아요

5. 커밋 호출을 검증하는 회귀 테스트

코멘트를 저장한 뒤 테이블에서 다시 읽는 테스트도 조회 조건을 살펴야 해요. 자동 커밋이 켜져 있거나, INSERT와 조회가 같은 커넥션의 같은 트랜잭션 안에서 실행되면 커밋 경계가 빠져도 행이 보일 수 있어요. 따라서 행이 조회됐다는 결과만으로 커밋까지 검증했다고 볼 수는 없어요. 반대로 운영과 같은 설정에서 쓰기를 마친 뒤 별도 커넥션으로 조회하는 테스트는 저장 결과를 검증할 수 있어요.

이번 회귀 테스트에서는 쓰기 메서드의 트랜잭션 경계에 집중했어요. 실제 저장 결과 대신 트랜잭션 관리자의 커밋 메서드가 호출되는지 확인했어요.

@Configuration @EnableTransactionManagement @Import(CommentWriter.class) static class Config { static final JdbcTemplate JDBC = mock(JdbcTemplate.class); static final PlatformTransactionManager TX = mock(PlatformTransactionManager.class); // ... 두 개를 빈으로 등록한다 } @Test @DisplayName("코멘트 insert 는 트랜잭션 안에서 실행되고 커밋된다" + " (운영 풀은 자동 커밋이 꺼져 있어 커밋이 없으면 롤백되어 코멘트가 사라진다)") void insert_commitsTransaction() { when(TX.getTransaction(any())).thenReturn(mock(TransactionStatus.class)); writer.insert(1L, 2L, "출금 실패 (2026-10-08) [2/3]"); verify(JDBC).update(anyString(), any(Object[].class)); verify(TX).commit(any(TransactionStatus.class)); // <- 이 한 줄이 회귀를 막는다 }

실제 데이터베이스 대신 목 트랜잭션 관리자를 등록한 뒤 쓰기 메서드를 호출하고 커밋 호출을 검증해요. 이 테스트는 실제 테이블의 행을 조회하지 않아요.

📖 용어: 목 객체 (mock)
실제 객체 대신 미리 정한 응답을 돌려주고 메서드 호출을 기록하는 테스트용 객체예요. 이 테스트에서는 SQL 실행과 커밋 요청 여부를 검증하는 데 사용했어요.
📖 용어: 회귀 테스트 (regression test)
수정한 버그가 이후 변경으로 다시 발생하지 않는지 확인하는 테스트예요. 여기서는 쓰기 메서드의 트랜잭션 처리가 빠지는 변경을 확인하도록 만들었어요.

이 테스트는 쓰기 메서드에 트랜잭션 처리가 적용되는지 확인해요. 당시에는 수정을 제거한 상태에서 테스트가 실패하는 것까지 확인했어요. 다만 목 객체의 커밋 호출 검증이 실제 데이터베이스의 저장 결과까지 입증하는 것은 아니에요.

테스트 이름에도 운영 풀의 자동 커밋이 꺼져 있어 커밋이 필요하다는 설명을 붙였어요. verify(TX).commit(...)을 검사하는 이유를 나중에 코드를 읽는 사람도 알 수 있도록 한 거예요.

6. 누락 기간과 배포 후 확인 계획을 남겼어요

수정은 이후의 쓰기를 커밋하도록 바꾸는 것이었어요. 9월 28일 오후 2시 44분부터 배포 전까지의 누락분을 되살리는 작업은 아니었어요. 해당 쓰기는 커밋되지 않았으므로 코멘트 테이블에는 복원할 행이 남아 있지 않았어요.

배포 노트에는 코멘트 저장을 고쳤다는 내용과 그 기간의 누락분은 이 수정으로 복구되지 않는다는 내용을 함께 적었어요. 화면에 기록이 없다는 이유로 출금 시도 자체가 없었다고 판단할 수 있어, 누락 기간도 알려야 했어요.

다른 경로의 로그에 흔적이 있는지, 있다면 어디까지 복원할지를 운영 담당자와 협의하는 일은 작업 문서의 남은 항목이었어요. 그 로그의 보관 기한도 고려해야 했어요. 복원이 완료됐다는 의미는 아니에요.

당시 글을 작성한 날은 배포 당일이었어요. 출금이 실행되는 시각 뒤에 코멘트 행이 실제로 생기는지 조회하는 확인 절차를 문서에 적어 뒀어요. 이 기록에 포함된 것은 수정과 테스트, 배포 후 확인 계획까지예요. 운영에서 저장이 재개됐다는 확인 결과는 포함하지 않았어요.

✍️ 정리
자동 커밋이 꺼진 풀에서 비동기 리스너가 JDBC 쓰기를 수행했지만, 쓰기 메서드에 커밋을 관리할 트랜잭션 경계가 없었어요. INSERT 호출의 오류 로그만으로는 이 누락을 감지하지 못했어요.

쓰기 메서드에 트랜잭션 처리를 추가하고 목 객체로 커밋 호출을 검증했어요. 실제 저장 결과와는 검사 범위가 달라요. 누락 기간의 복원 협의와 배포 후 코멘트 조회는 당시 남아 있던 작업이었어요.
