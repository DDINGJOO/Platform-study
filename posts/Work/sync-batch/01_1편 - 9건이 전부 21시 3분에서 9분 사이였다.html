1편. 중복 파일 9건의 발생 시각으로 정리 배치를 추적하기 ← 지금 이 글

넉 달 남짓 동안 파일 중복 저장이 아홉 번 발생했어요. 파일이 하나만 있어야 하는 자리에 똑같은 파일이 두 벌 저장돼 있었어요. 재현하지는 못했고, 사용자나 브라우저, 요청 본문에서도 공통점을 찾지 못했어요.

발생 시각을 비교하자 아홉 건이 전부 21시 3분에서 9분 사이에 있었어요. 시각은 모두 한국시간(KST) 기준이에요. 그 시간에 실행되는 정리 배치를 살펴봤고, 배치의 트랜잭션 범위와 파일 저장 순서를 원인 후보로 검토했어요. 변경을 되돌렸다가 다시 반영하는 과정에서는 머지 커밋 revert의 동작도 확인하게 됐어요.

1. 발생 시각으로 정리 배치를 추적했어요

처음에는 어떤 입력과 조작 순서, 실행 환경에서 문제가 생겼는지 찾았어요. 공통점이 나오지 않아 발생 시각을 비교했더니, 확인한 아홉 건이 6분 폭 안에 모여 있었어요. 다른 시간대의 발생 기록은 찾지 못했어요.

이 분포만으로 원인을 정할 수는 없지만, 같은 시간에 반복 실행되는 작업을 살펴볼 이유는 있었어요. 당시 매일 21시에 오래된 파일을 정리하는 배치가 있었어요.

배치 실행 시간을 21시로 바꾼 커밋도 찾았어요. 당시 기록상 그 커밋은 넉 달 반 전의 것이었고, 첫 발생 날짜와는 일주일 차이였어요. 배치를 우선 조사할 단서였지만, 날짜와 시각이 가깝다는 사실만으로 중복 생성 과정까지 입증되지는 않았어요.

그림 1. 발생 시각의 분포를 보고 같은 시간의 정리 배치를 조사했어요

2. 배치와 업로드 사이에서 검토한 네 단계

당시에는 배치가 실행되는 동안 업로드가 실패하고, 재시도 과정에서 중복이 생겼을 가능성을 검토했어요. 아래 코드는 배치와 저장 로직을 간추린 예시예요. 운영에서 발생한 아홉 건의 실행 순서를 그대로 재현한 결과는 아니에요.

단계 1: 배치의 트랜잭션 안에 외부 파일 삭제가 있었어요

정리 배치는 스프링 배치의 태스크릿 스텝 하나로 구성돼 있었어요. 이 구조에서는 스텝의 트랜잭션 안에서 대상 수백 건을 순회하며 외부 스토리지의 파일을 하나씩 삭제했어요. 네트워크 통신이 끝날 때까지 트랜잭션도 길어질 수 있는 구조였어요.

// {정리 배치} 의 스텝. 태스크릿 스텝은 기본이 트랜잭션 하나다. // = 이 블록이 끝날 때까지 커넥션 하나가 반납되지 않는다. tasklet { _, _ -> val targets = findExpired().take(dailyLimit) // 수백 건 targets.forEach { t -> cleanupService.destroy(t) // @Transactional 이지만 REQUIRED 라 바깥에 합류한다 } RepeatStatus.FINISHED } @Transactional fun destroy(t: Target) { // 건마다, 파일마다, 네트워크 왕복 하나씩. 전부 트랜잭션 안이다. filesOf(t).forEach { storage.remove(it.path) } fileRepository.deleteByOwner(t.key) // ... 나머지 정리 }

destroy에 붙은 @Transactional의 전파 속성은 REQUIRED였어요. 기존 트랜잭션이 있으면 거기에 참여하는 설정이라, 이 예시에서는 건마다 커밋하지 않고 바깥 스텝의 트랜잭션을 함께 사용해요. 애너테이션이 있다는 이유만으로 건별 트랜잭션이라고 볼 수 없었어요.

단계 2: 약 9분의 배치 실행과 커넥션 사용을 살펴봤어요

외부 스토리지의 파일 삭제에는 건마다 네트워크 왕복이 필요했어요. 수백 건에 파일이 여러 개씩 있으면 호출 횟수도 늘어나요. 당시 기록에는 이 구간이 약 9분 걸린 것으로 남아 있어요.

배치가 커넥션 하나를 오래 사용하는 점을 확인할 필요가 있었어요. 다만 커넥션 하나를 사용한다는 사실만으로 풀 전체가 고갈됐다고 판단할 수는 없어요. 배치 실행 시간과 사용자 요청의 지연을 연결하려면 같은 구간의 커넥션 사용량과 요청 실패 기록이 필요해요.

단계 3: 같은 시간대의 업로드 실패를 검토했어요

21시는 사용자가 파일을 올리는 시간이기도 했어요. 당시에는 약 9분의 배치 실행 중 업로드 요청이 커넥션을 기다리거나 처리에 시간이 걸려 실패했을 가능성을 봤어요. 아홉 건 모두가 같은 이유로 실패했다고 확정할 만큼의 요청별 기록은 여기서 제시하지 못해요.

단계 4: 조회·삭제·삽입 순서만으로는 중복을 막지 못했어요

파일 저장 로직은 기존 파일을 조회하고, 스토리지와 테이블에서 삭제한 뒤 새 파일을 올리고 행을 저장하는 순서였어요.

@Transactional fun saveFiles(ownerKey: String, files: List<UploadedFile>) { val prev = fileRepository.findByOwner(ownerKey) // 1) 지금 있는 것을 찾고 storage.removeAll(prev.map { it.path }) // 2) 스토리지에서 지우고 fileRepository.deleteAll(prev) // 3) 테이블에서 지우고 files.forEach { val path = storage.upload(it) // 4) 새로 올리고 fileRepository.save(FileRow(ownerKey, it.slot, path)) // 5) 새로 넣는다 } } // 3) 이 아무것도 못 지운 채로 5) 만 실행되면 행이 두 개가 된다.

이 코드에서 지키려던 규칙은 "이 사용자의 이 슬롯에는 행이 하나만 있어야 한다"였어요. 앞에서 조회한 행을 삭제한 뒤 새 행을 넣는 순서로 구현했어요.

당시에는 재시도한 요청에서 앞 요청의 행이 보이지 않아 삭제를 건너뛰고 삽입했을 가능성을 생각했어요. 다만 앞 요청이 롤백됐다면 그 요청의 삽입 행도 남지 않으므로, 롤백만으로 두 행이 남는 과정은 설명되지 않아요. 앞 요청이 아직 커밋되지 않은 경우도 조회 시점과 두 요청의 최종 커밋 결과를 함께 봐야 해요. 이 부분은 당시 가설이며, 중복 생성의 정확한 순서를 확인한 재현 결과는 없어요.

그림 2. 당시 검토한 흐름이에요. 각 요청의 실행 순서를 입증한 결과는 아니에요

3. 테이블에는 유니크 제약이 없었어요

조회와 삭제가 예상한 대로 동작하지 않더라도 같은 소유자와 슬롯의 중복 삽입을 거부하려면 테이블에도 그 규칙이 있어야 해요. 당시 테이블에는 유니크 제약, 즉 지정한 컬럼 조합의 중복을 거부하는 제약이 없었어요.

애플리케이션의 조회·삭제·삽입 순서는 DB가 중복을 거부하는 조건과는 달라요. 규칙에 맞는 유니크 제약이 있었다면 중복 삽입 시 오류로 드러났을 거예요. 다만 오류를 언제 발견했을지는 당시 알림과 확인 방식에 달려 있으므로 첫날 발견했을 것이라고 단정할 수는 없어요.

같은 스키마의 다른 테이블에는 소유자와 유형을 묶은 유니크 키가 있었어요. 이 테이블에도 컬럼 변경과 함께 중복 허용 범위를 다시 검토할 필요가 있었어요.

💡 유니크 제약을 추가하기 전에 확인할 것
기존 중복: 중복이 남아 있으면 제약 추가가 실패할 수 있어요. 어느 행을 남길지 먼저 정해야 해요.

소프트 삭제: 지워진 행을 deleted 플래그로 남기는 구조라면, 삭제된 행까지 제약에 포함되는지 확인해야 해요. 삭제 플래그를 제약 컬럼에 넣는 방식도 실제로 허용할 데이터 조합과 맞는지 검토해야 해요.

NULL 취급: NULL을 포함한 유니크 키의 처리 방식은 사용하는 DB에서 확인해야 해요. 슬롯 구분 컬럼이 nullable이면 의도한 중복을 거부하는지 함께 살펴봐야 해요.

4. 실행 시간 변경은 임시 조치였어요

당시에는 배치 실행 시간을 사용자 활동이 적은 새벽으로 옮겼어요. 사용자 요청과 배치가 겹칠 가능성을 줄이려는 조치였어요. 배포한 날부터 증상이 사라졌다거나, 재발하지 않았다고 확인할 후속 기록은 여기서 제시하지 못해요.

실행 시간을 옮겨도 외부 I/O가 트랜잭션 안에 있는 구조와 유니크 제약의 부재는 그대로예요. 새벽에도 요청이나 다른 작업이 있을 수 있어서 시간 변경만으로 중복 방지가 보장되지는 않아요.

당시 후속 검토 대상으로 남긴 방향은 다음 세 가지예요. 각각 해결하려는 문제가 달라서 어느 하나만 적용하면 전체 문제가 해결된다고 볼 수는 없어요.

🔧 후속 검토 대상으로 남긴 세 가지
외부 I/O를 트랜잭션 밖으로 옮기기: 대상 조회와 DB 변경의 트랜잭션 범위를 정하고, 실제 파일 삭제를 커밋 뒤로 옮기는 방향이에요. 외부 시스템의 응답을 기다리는 시간을 DB 트랜잭션에서 줄이려는 목적이에요.

배치를 건 단위로 나누기: 전체 대상을 한 트랜잭션으로 처리하는 대신 건별로 짧게 커밋하는 방향이에요. 중간 실패 시 어디까지 반영됐는지도 이 단위에 맞춰 확인해야 해요.

유니크 제약 추가하기: 허용할 소유자·슬롯 조합을 정하고 DB에서 중복 삽입을 거부하도록 하는 방향이에요. 기존 데이터 정리와 제약 설계가 먼저 필요해요.

당시 기록에는 이 세 방향을 배포 문서의 "남은 후속 과제"로 적었다고 남아 있어요. 이 글에서 설명한 실행 시간 변경과 후속 수정의 완료 여부는 구분해서 봐야 해요.

5. 머지 커밋을 되돌린 뒤 같은 브랜치를 다시 머지했어요

운영 영향이 있는 변경이라 배포 직후 확인하는 과정에서 일단 되돌리기로 했어요. 되돌린 대상은 머지 커밋이었어요.

git revert -m 1로 기준 부모를 지정해 머지 내용을 되돌렸어요. 이후 같은 브랜치의 변경을 다시 반영하려고 머지했지만 변경이 들어오지 않았어요. 아래는 그 이력을 간추린 예시예요.

$ git log --oneline --graph main * R Revert "Merge ..." <- 머지 커밋을 revert 했다 * M Merge (원래 변경) |\ | * C2 ... <- 이 커밋들은 여전히 main 의 조상이다 | * C1 ... # 그래서 같은 브랜치를 다시 머지하면 $ git merge feature-branch Already up to date. # git 은 "이미 다 들어와 있다" 고 본다. 코드에는 없는데.

이 예시에서 기능 브랜치의 커밋은 머지를 되돌린 뒤에도 main의 조상으로 남아 있어요. 그래서 브랜치에 새 커밋이 없는 상태에서 다시 머지하면 가져올 커밋이 없다는 결과가 나와요. revert는 머지 커밋을 이력에서 삭제하지 않고, 그 내용을 되돌리는 새 커밋을 추가해요.

당시에는 revert 커밋을 다시 revert해서 변경을 복원했어요. 이력에는 머지 → 되돌리기 → 되돌리기의 되돌리기가 남았어요. 복원 방법이 이것뿐인 것은 아니지만, 기존 머지의 변경을 다시 반영하려고 선택한 방식이었어요.

⚠️ 되돌리기 전에 재반영 방법도 확인해요
설정 한 줄만 되돌릴지, 브랜치의 변경 전체를 되돌릴지 먼저 범위를 정해요. 머지 커밋을 revert한다면 나중에 같은 브랜치를 다시 머지하는 것만으로 변경이 복원되지는 않는다는 점도 함께 확인해야 해요. 재반영할 때는 revert를 다시 revert할지, 필요한 변경을 새 커밋으로 만들지 상황에 맞춰 정해요.

6. 확인한 범위와 남은 검증

아홉 건의 발생 시각이 6분 안에 모여 있다는 점과 21시 정리 배치의 존재는 조사 범위를 좁히는 단서였어요. 다만 커넥션 사용, 업로드 실패, 재시도와 최종 중복 행을 연결한 요청별 기록이나 재현 결과는 제시하지 못했어요. 당시의 원인 후보와 확인한 사실을 구분해야 해요.

실행 시간을 바꾸는 조치와 트랜잭션·제약을 수정하는 작업도 구분했어요. 변경을 되돌렸다가 다시 반영하는 과정에서는 파일 내용과 커밋 조상 관계가 다르게 남는다는 점을 확인했어요.

✍️ 정리
파일 중복 저장 아홉 건이 모두 21시 3분에서 9분 사이에 발생해 21시 정리 배치를 조사했어요. 배치 안의 외부 I/O와 파일 저장 순서를 원인 후보로 봤지만, 시각의 일치만으로 중복 생성 과정을 확정하지는 못해요.

실행 시간은 임시 조치로 변경했고, 트랜잭션 범위와 유니크 제약은 후속 검토 대상으로 구분했어요. 머지 커밋을 되돌린 뒤에는 같은 브랜치를 다시 머지해도 변경이 복원되지 않아 revert를 다시 revert하는 방식을 사용했어요.
