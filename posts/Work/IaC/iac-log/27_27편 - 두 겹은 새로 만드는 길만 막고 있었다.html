27편. IAM 그룹과 자격증명 변경을 apply 역할에서 차단한 이유 ← 지금 이 글

오늘 아침에는 사람이 콘솔에서 자원을 만들 때 규약 태그를 빠뜨리지 못하게 하는 정책을 설계하고 있었어요. 닷새 전에 시크릿 하나에 적용한 제한을 다른 서비스로 넓히려던 작업이었습니다. 이를 위해 사람이 이 계정에 접근하는 방식을 다시 정리했어요. 사람은 IAM 사용자로 접근하고 그룹에 속해 있어서, 태그를 강제하는 정책도 그룹에 붙어 있습니다.

그룹에 정책을 붙이는 일을 파이프라인의 apply 역할도 할 수 있는지 확인했어요. 이미 차단했다고 생각했지만, 해당 액션은 허용돼 있었습니다.

두 달 전에는 이 역할의 권한 상승 경로를 두 가지 정책으로 차단하는 ADR을 썼어요(6편). 액션이나 리소스를 열거해서 차단하면 목록에 빠진 대상이 남는다는 점도 적어 뒀습니다. 하지만 당시 설계는 역할이나 사용자를 새로 만드는 시나리오를 중심으로 검토했어요.

이 판단으로 오전에 ADR을 보강하고 커밋 메시지를 썼는데, 차단되지 않았다고 적은 액션 중 두 개는 이미 두 달 전에 차단한 상태였어요. 같은 파일 아래쪽의 Deny 문을 읽지 않아 잘못 분류했습니다. 그룹 변경 권한이 남아 있다는 판단은 맞았지만, 자격증명 액션은 기존 정책과 다시 대조해야 했어요.

1. 태그 정책을 설계하다 그룹 변경 권한을 확인했다

📖 용어: apply 역할
CI가 terraform apply 를 실행할 때 사용하는 AWS 역할이에요. 이 저장소에서는 환경마다 하나씩 두고 파이프라인에 필요한 권한을 부여합니다.

당시에는 권한 상승 경로를 점검하려던 것이 아니었어요. 기존 정책을 다시 볼 때도 정책이 있는지와 의도대로 동작하는지에 집중했고, 어떤 액션을 제한하지 못하는지까지 따로 검토하지 않았습니다.

태그 정책을 설계하려면 그룹에 정책을 붙일 수 있는 주체부터 확인해야 했어요. apply 역할이 그룹에 수행할 수 있는 액션을 살펴보면서, 그룹 변경을 차단하는 정책이 빠져 있다는 것을 확인했습니다.

그래서 아침 10시 25분에는 그룹 변경 권한을 제한하는 보안 수정이 먼저 들어갔어요. 원래 하려던 태그 강제 확장은 오후에 머지됐습니다.

2. 기존 두 정책이 제한하던 액션

기존 두 겹을 짧게 다시 볼게요. apply 역할에는 iam:* 가 열려 있습니다. Terraform 이 스택마다 역할을 만들어야 해서 회수할 수가 없었어요. 대신 두 가지를 걸었습니다. 1겹은 sts:AssumeRole 전면 Deny 예요. 역할을 만들어도 그 역할을 맡아 실행할 수 없도록 한 거예요. 2겹은 역할이나 사용자를 만들 때, 그리고 거기에 정책을 붙일 때, 정해진 permissions boundary 가 지정돼 있지 않으면 Deny 하는 것입니다.

📖 용어: permissions boundary (권한 경계)
역할이나 사용자가 가질 수 있는 권한의 상한을 정하는 정책이에요. 자체적으로 권한을 부여하지는 않습니다. AdministratorAccess를 붙여도 권한 경계가 허용하지 않는 작업은 할 수 없어요.
📖 용어: 조건 키 (condition key)
IAM 정책이 "요청이 이런 모양일 때만"이라고 단서를 달 때 보는 값이에요. iam:PermissionsBoundary 는 "이 요청이 지정한 권한 경계가 무엇인가"를 담는 조건 키입니다. 그 값을 애초에 담지 않는 액션도 있어서, 그런 액션에는 이 조건으로 단서를 달 수가 없어요.

두 정책이 대상으로 삼은 시나리오는 역할을 새로 만들고, 정책을 붙인 뒤 그 역할을 맡아 실행하는 순서였어요. 하지만 이 계정에는 이미 높은 권한을 가진 사용자와 그 사용자가 속한 그룹이 있습니다. 기존 그룹이나 자격증명을 변경하는 액션은 역할 생성이나 AssumeRole 없이도 실행할 수 있었어요.

그림 1. 새 역할을 사용하는 방식과 기존 사용자·그룹을 변경하는 방식의 차이

3. 그룹 변경에는 권한 경계 조건을 쓸 수 없었다

저는 권한 경계를 강제하는 두 번째 정책이 apply 역할의 IAM 동작 전반을 제한한다고 생각했어요. 하지만 그 정책은 지정된 액션에만 적용됐고, 그룹과 자격증명 변경 액션은 목록에 없었습니다.

권한 경계는 역할과 사용자에만 붙는 속성이에요. 그룹에는 붙지 않고, 비밀번호나 액세스 키 같은 자격증명에도 붙지 않습니다. 그래서 2겹의 Deny 는 역할·사용자를 만드는 요청과 그 둘에 정책을 붙이는 요청에만 조건을 걸 수 있었어요. 그룹에 정책을 붙이는 요청에는 그 조건이 들어갈 칸 자체가 없습니다.

그림 2. 권한 경계를 지정할 수 있는 대상과 그렇지 않은 대상
⚠️ 주의: 조건과 액션 목록을 함께 확인하기
• 조건부 Deny 를 쓰면 "이 조건을 어기는 모든 요청"이 막힌다고 읽기 쉬운데, 실제로 막히는 건 그 정책이 나열한 액션 중에서 조건을 어긴 것뿐이에요
• 이 정책에서는 조건 키를 지원하는 액션으로 목록을 제한했어요. 조건 키를 지원하지 않는 액션을 같은 문에 넣으면 해당 액션이 항상 거부되는 문제가 있었기 때문입니다(이 동작은 28편에서 따로 다뤘어요)
• 목록에 없는 액션은 이 정책으로 제한되지 않아요. 권한 상승을 막는 문서에는 적용 대상과 함께, 제한하지 못하는 액션군도 적어 둘 필요가 있습니다

오전에는 아래 액션들이 허용돼 있다고 정리했어요.

그룹 AttachGroupPolicy 권한이 센 그룹에 관리자 정책을 붙인다 AddUserToGroup 아무 사용자를 그 그룹에 넣는다 RemoveUserFromGroup 태그 강제 대상에서 사람을 빼낸다 자격증명 UpdateLoginProfile 사람의 로그인 비밀번호를 바꾼다 CreateAccessKey 사람의 액세스 키를 새로 만든다 EnableMFADevice MFA 장치를 새로 등록한다

이 중 비밀번호 변경과 액세스 키 생성을 가장 위험한 액션으로 분류했어요. 새 역할 없이도 기존 사용자의 권한을 사용할 수 있다고 봤기 때문입니다. ADR 보강과 커밋 본문에도 이 두 액션을 먼저 적었습니다.

그 두 줄은 이미 막혀 있었다

bootstrap/iam.tf 를 위에서 아래까지 다시 읽으며 기존 Deny 문을 확인했어요. 같은 파일 끝부분에 DenyLongLivedCredsAndServiceAssume 라는 문이 있습니다. 2026년 8월 6일에는 액션 여섯 개로 추가했고, 후속 변경에서 둘을 제외했어요. 10월에 다시 확인한 목록은 다음과 같았습니다. 조건 없이 * 에 Deny 를 걸고, 액션 네 개를 적어 뒀는데 그중 셋이 CreateAccessKey · CreateLoginProfile · UpdateLoginProfile 입니다. 이 Deny 문을 이번 확인에서 빠뜨렸어요.

하지만 그 두 액션은 이미 차단돼 있었어요. 그룹과 자격증명 액션을 기존 정책과 다시 대조한 결과는 아래와 같습니다.

정말 열려 있던 것 그룹 AttachGroupPolicy 권한이 센 그룹에 관리자 정책을 붙인다 DetachGroupPolicy 붙어 있던 정책을 뗀다 AddUserToGroup 아무 사용자를 그 그룹에 넣는다 RemoveUserFromGroup 태그 강제 대상에서 사람을 빼낸다 자격증명 UploadSSHPublicKey 사람 계정에 공개키를 올린다 EnableMFADevice MFA 장치를 새로 등록한다 DeactivateMFADevice 붙어 있던 MFA 를 뗀다 UpdateAccessKey 비활성 상태의 키를 다시 켠다 이미 막혀 있던 것 ← 두 달 전에 조건 없는 Deny 로 막아 둔 자리 자격증명 CreateAccessKey · CreateLoginProfile · UpdateLoginProfile

그룹 쪽은 통째로 비어 있었던 게 맞아요. 자격증명 쪽은 통째가 아니라 목록 밖이 비어 있었습니다. 10월에 확인한 목록에는 네 개가 있었고 "장기 자격증명은 막았다"고 판단했는데, 같은 목적을 가진 액션이 그 네 개 말고도 있었어요. 사람 계정에 공개키를 올리는 길, 서비스 전용 자격증명을 다시 발급받는 길, MFA 를 떼고 다시 붙이는 길 같은 것들입니다.

액션을 열거하면 누락이 생길 수 있다는 점을 ADR에 적었지만, 뒤이어 만든 자격증명 Deny 목록은 두 달 동안 다시 검토하지 않았어요. 이번 ADR 보강 문서와 커밋 본문에도 이미 차단된 액션을 허용된 것으로 적은 내용이 남아 있습니다.

4. 그룹과 자격증명 변경을 조건 없이 거부했다

apply 역할에 조건 없는 Deny 문 두 개를 추가했어요.

조건 없는 Deny는 두 달 전에도 사용한 방식이에요. 기존 문 위에는 조건 키를 지원하지 않는 액션을 조건부 Deny에 넣으면 항상 거부되므로, 의도를 명시하기 위해 조건을 빼 뒀다는 주석도 있습니다. 이번에는 그 방식을 그룹과 나머지 자격증명 변경 액션까지 확대했어요.

statement { sid = "DenyHumanGroupAndCredentialChanges" effect = "Deny" actions = [ "iam:AddUserToGroup", "iam:RemoveUserFromGroup", "iam:AttachGroupPolicy", "iam:DetachGroupPolicy", "iam:CreateGroup", "iam:UpdateGroup", "iam:DeleteGroup", "iam:CreateLoginProfile", "iam:UpdateLoginProfile", "iam:DeleteLoginProfile", "iam:CreateAccessKey", "iam:UpdateAccessKey", "iam:DeleteAccessKey", "iam:UploadSSHPublicKey", "iam:UploadSigningCertificate", "iam:EnableMFADevice", "iam:DeactivateMFADevice", "iam:ResyncMFADevice", # 그 밖에 자격증명을 새로 쥐여 주는 액션들 ] resources = ["*"] }

위 액션 중 일부는 8월의 Deny 문에도 있어요. 중복은 그대로 뒀습니다. 사용자와 자격증명 변경에 관한 제한을 한 문에서 확인할 수 있게 하려는 선택이었어요. Deny 는 겹쳐도 결과가 달라지지 않습니다.

리소스를 * 로 둔 게 핵심이에요. 이름으로 대상을 고르면 다시 목록 방어가 됩니다. 이렇게 전면 Deny 를 걸 수 있었던 건 확인 하나 덕분이었어요. 이 액션들을 쓰는 스택이 하나도 없었습니다. 사람 계정과 그룹 구성은 코드가 아니라 사람이 콘솔에서 하는 일이고, 그게 이 저장소의 규칙이에요.

예외는 딱 하나였습니다. 아침에 넓히려던 그 태그 강제 정책이 그룹의 인라인 정책으로 들어가 있거든요.

📖 용어: 인라인 정책 (inline policy)
독립된 정책 자원을 따로 만들지 않고, 특정 사용자나 그룹에 직접 써 넣는 정책이에요. 이름은 그 대상 안에서만 의미가 있고 주소(ARN)가 따로 생기지 않습니다. 그래서 정책 이름을 가리켜 권한을 가를 수가 없어요.
statement { sid = "DenyGroupInlinePolicyOutsideTagEnforcement" effect = "Deny" actions = ["iam:PutGroupPolicy", "iam:DeleteGroupPolicy"] # 운영: 태그 강제 정책이 들어가는 그룹만 빼고 전부 Deny # 개발: 존재하지 않는 그룹 ARN 하나를 넣어 전부 Deny not_resources = ... }

not_resources 는 "여기 적힌 것 말고 전부"라는 뜻이에요. 운영 환경에서는 태그 강제 정책이 들어갈 그룹만 적어 두면 나머지는 전부 막힙니다. 개발 환경 apply 역할은 그룹을 건드릴 일이 아예 없어서 빼 둘 것이 하나도 없는데, 그렇다고 칸을 비울 수는 없었어요. 역할에 붙는 IAM 정책은 문마다 대상을 적는 칸이 있어야 하거든요. 그래서 존재하지 않는 그룹 주소를 하나 적었습니다. 세상에 없는 것만 빼고 막으면 결과적으로 전부 막히니까요.

허용한 그룹의 인라인 정책에는 제한이 남았다

이 예외는 그룹 단위까지만 제한할 수 있었어요. 인라인 정책 이름으로 범위를 좁힐 수 없어서, 허용한 그룹에는 태그 강제 정책 이외의 내용도 넣을 수 있습니다.

태그 강제 정책을 사람이 직접 apply하는 영역으로 옮기면 이 예외를 제거할 수 있어요. 다만 태그 규칙을 바꿀 때마다 사람이 apply해야 합니다. 당시에는 그 운영 부담을 더 크게 보고 예외를 유지했어요. 머지된 변경만 apply되므로, 해당 그룹에 어떤 정책을 넣는지는 PR 리뷰에서 확인하기로 했습니다.

ADR에는 이 내용을 "남는 위험"으로 적었어요. 이후에 정책을 검토할 때도 제한한 액션과 유지한 예외를 함께 확인할 수 있도록 했습니다.

그림 3. 이번에 누락했던 기존 Deny 문과 새로 추가한 제한

5. 이 변경은 파이프라인이 적용하지 못한다

이 Deny 두 개는 apply 역할 자체에 붙는 정책이라서, apply 역할로는 변경할 수 없어요. 이 저장소에서는 이런 자원을 bootstrap이라는 별도 영역에 두고 사람이 직접 apply합니다.

📖 용어: bootstrap
파이프라인이 돌기 위해 먼저 있어야 하는 것들을 모아 둔 영역이에요. state 를 보관하는 버킷, apply 역할과 그 권한 같은 것들입니다. 이것들을 파이프라인으로 만들려면 파이프라인이 먼저 있어야 하니, 순서상 사람이 손으로 만들 수밖에 없어요.

그런데 오늘은 로컬에 Terraform 을 돌릴 세션이 없었어요. 그래서 IAM 관리자가 CloudShell 에서 정책을 직접 넣었습니다. 코드로 관리하는 저장소에서 콘솔 작업을 한 거라, 그대로 두면 코드와 실물이 어긋난 상태가 돼요.

# 1. 사람이 CloudShell 에서 Deny 문 두 개를 넣는다 aws iam put-role-policy --role-name {apply 역할} \ --policy-name {정책} --policy-document file://policy.json # 2. 적용 기록을 올리는 PR 의 bootstrap plan 으로 대조한다 No changes. Your infrastructure matches the configuration.

적용 기록을 올리는 PR의 bootstrap plan에서 변경 사항이 없다는 결과를 확인했어요. 수동으로 적용한 정책과 Terraform 설정 사이에 plan이 감지한 차이가 없었다는 뜻입니다. bootstrap/README.md 의 적용 기록 표에는 날짜와 변경 내용, 적용 방법, 검증 결과를 남겼어요.

• 콘솔이나 CLI로 적용한 변경은 바로 plan으로 설정과 대조해 두는 게 좋아요. 확인이 늦어지면 그 사이에 다른 apply가 실행됐을 수 있습니다
• 수동 변경을 코드에 반영하지 않으면 다음 apply에서 Deny가 제거될 수 있어요. plan의 정책 변경 내용도 함께 확인해야 합니다
• 적용 기록은 README처럼 이후 작업자가 확인하기 쉬운 곳에도 남겨 둡니다
✍️ 오늘의 요약
기존 두 정책은 새 역할·사용자 생성과 역할 전환을 제한했지만, 그룹 변경과 일부 자격증명 액션은 제한하지 않았어요. 해당 액션에 조건 없는 Deny 두 개를 추가하고, 태그 강제에 필요한 그룹 인라인 정책은 예외로 남겼습니다. 정책 이름으로 제한할 수 없는 위험은 ADR에 적고 PR 리뷰에서 확인하기로 했어요.

처음에 허용된 것으로 분류한 자격증명 액션 두 개는 이미 차단돼 있었어요. 파일 전체를 다시 읽어 이를 정정했습니다. 정책은 IAM 관리자가 CloudShell에서 적용했고, 적용 기록 PR의 bootstrap plan에서 변경 사항이 없다는 결과를 확인했어요.
