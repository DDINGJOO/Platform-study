22편. AWS 인벤토리를 Terraform state 식별자로 대조하기 ← 지금 이 글

9월 27일 오후, 새로 만든 CI 잡의 두 번째 실행 결과를 확인했어요. 탄력적 IP 60, 보안그룹 67, S3 버킷 131, IAM 역할 154, 로그그룹 112, CloudFront 51, Lambda 24로, 열하루 전에 손으로 셌던 개수와 모두 같았습니다. 수집 실패와 모르는 종류도 각각 0이었어요.

저는 이 결과를 근거로 결정 기록의 상태를 "승인됨"으로 바꿨습니다. 커밋 제목에도 그렇게 적었어요. "두 번째 실행이 9/16 전수와 일치했다."

같은 날 저녁에 항목을 하나씩 확인하니 추가로 구분할 것이 있었어요. 탄력적 IP 60개 중 54개는 우리가 관리할 대상이 아니었고, 실물이 없는 버킷 하나가 state 안에 남아 있었습니다. 종류별 총개수만 비교해서는 알 수 없던 내용이에요.

1. 손으로 만든 표를 갱신하지 못한 이유

리소스를 몇 주째 편입하고 있었지만, AWS 계정에 있는 모든 리소스가 이 저장소에서 관리되는지는 확인하지 못한 상태였어요.

9월 16일에는 터미널에서 종류별 개수를 뽑고, 저장소의 resource 블록 수와 나란히 놓은 표를 만들었어요. 그 표로 편입 순서를 정하고 다음 날 첫 배치를 끝냈습니다. 다만 이후 배치를 몇 개 더 편입한 결과는 표에 반영하지 못했어요.

📖 용어: Terraform state
Terraform이 관리하는 리소스와 실물의 ID를 기록하는 JSON 파일이에요. 이 저장소에는 스택마다 하나씩, 모두 33개가 S3에 있어요. 코드의 블록 수와 달리 state에는 실제 관리되는 인스턴스가 각각 기록됩니다.

멈춘 이유를 적어 보니 세 가지였어요.

9/16 표의 한계 1. 다시 셀 수 없다 출력을 손으로 붙여 넣어 만든 표라 갱신 비용이 조사 비용과 같다 2. 개수로 비교했다 "S3 131 vs 92" 는 39개가 빠졌다는 것만 말한다. 어느 39개인지는 다시 찾아야 한다 코드 쪽은 resource 블록을 셌는데 for_each 블록 하나가 N 개를 만든다 3. 판정이 표 안의 문장이었다 "보안그룹 60: 공유, 소유 안 함" 은 다음 조사에 기계적으로 적용되지 않는다

두 번째가 가장 근본적이에요. for_each(목록을 받아 같은 리소스를 항목 수만큼 만드는 문법)를 쓰면 블록 하나가 버킷 열 개를 만들 수 있어요. 그러니 "실물 131, 코드 92"는 처음부터 같은 단위로 잰 숫자가 아니었습니다. 차이 39도 정확한 값이 아니라 짐작이었던 거예요.

개수를 먼저 세게 된 계기도 있었어요. 이미지 저장소를 편입할 때 36개짜리 목록으로 시작했다가 실제로는 47개라는 것을 뒤늦게 알았습니다. 이후 종류별 개수부터 확인하도록 했지만, 전체 개수를 아는 것만으로는 어느 리소스를 관리하고 있는지까지 알 수 없었어요.

2. 실물과 state의 식별자를 대조하기

ADR-0052에서 정한 방식으로 CI 잡을 만들었어요. 실물은 종류별 목록 조회 API로 식별자를 모으고, state 33개에서도 식별자를 뽑아 대조합니다.

📖 용어: 식별자와 ARN
식별자는 리소스 하나를 정확히 가리키는 값이에요. AWS 에서는 보통 ARN(arn:aws:서비스:리전:{계정ID}:종류/이름 형식의 전체 주소)이고, 버킷같이 이름이 곧 식별자인 종류도 있어요. 대조의 핵심은 종류마다 "실물의 어느 값"과 "state 의 어느 속성"이 같은 값인지 정해 두는 것입니다.

예를 들어 로드밸런서는 ARN 끼리, 버킷은 버킷 이름끼리 맞춰요. state 를 보는 이유도 분명합니다. for_each 가 펼쳐진 뒤의 실제 인스턴스가 거기 있으니까요. state 에는 민감한 값도 평문으로 들어 있어서, 식별자만 뽑고 원문은 출력하지도 남기지도 않습니다.

대조가 끝나면 규칙 파일에 따라 분류해요. 9/16 표에 문장으로만 적혀 있던 판정을 다음 실행에도 적용할 수 있도록 데이터로 옮겼습니다.

분류 뜻 managed state 에 있다 aws-managed AWS 가 만든 것 (서비스 연결 역할, 기본 VPC, 자동 확장 그룹이 띄운 서버) excluded 개별 규칙으로 "담지 않는다" 가 정해졌다. 근거 ADR 을 같이 적는다 excluded-kind 종류 통째로 담지 않는다 (시크릿, 공유 보안그룹 등) orphan? 삭제 후보로 보이는 것. 물음표는 판정이 아니라 신호라는 뜻 candidate 어디에도 안 걸린다. 편입 대상

그리고 두 가지 장치를 붙였어요. 하나는 수집이 하나라도 실패하면 잡 전체를 실패시키는 것입니다. 권한이 없어서 0개가 나온 것과 실제로 0개인 것을 구분하려고요. 다른 하나는 "state 에만 있는 것" 목록이에요. state 에는 있는데 실물 쪽에서 못 찾은 식별자를 따로 모읍니다. 콘솔에서 누가 지웠을 수도 있고, 제가 식별자 매핑을 틀렸을 수도 있어요. 어느 쪽이든 여기로 나옵니다.

그림 1. 총개수가 같아도 여섯 주소는 별도로 판정해야 해요

3. 첫 실행에서 확인한 수집기 결함

첫 실행에서는 수집 범위, 예외 처리, 지원하는 리소스 종류에 문제가 있었어요. 계정에서 리소스가 사라진 것이 아니라 수집기를 보완해야 하는 경우였습니다.

"state 에만 있는 것" 24건이 전부 us-east-1 이었다

state에는 있는데 실물이 없다는 항목이 24건 나왔어요. 처음에는 콘솔에서 삭제된 리소스일 수 있다고 생각했지만, 모두 us-east-1에 있어 수집 범위를 확인했습니다.

📖 용어: us-east-1 과 글로벌 서비스
IAM 과 CloudFront 는 리전이 없는 서비스예요. 이런 서비스를 글로벌 서비스라고 해요. 그런데 이런 서비스에 딸린 리소스 중 일부는 미국 동부(us-east-1)에만 만들 수 있습니다. CloudFront 에 붙일 인증서와 웹 방화벽이 대표적이에요.

첫 버전은 서울 리전을 전부 보고, us-east-1 에서는 CloudFront 용 웹 방화벽과 인증서만 봤어요. 그 둘만 거기 있다고 생각했거든요. 그런데 24건을 열어 보니 이런 것들이었습니다.

state 에만 있는 것 24건 (전부 us-east-1) 인증서 만료 알람 · 그 알람이 보내는 SNS 토픽 · 실패한 메시지를 받는 DLQ 루트 계정 · IAM 보안 이벤트를 잡는 이벤트 규칙 CloudFront 웹 방화벽의 로그그룹 -> 실물은 다 있었다. 수집기가 그 리전에서 이 종류들을 안 봤을 뿐이다

CloudFront용 인증서는 us-east-1에 있으니 만료 지표와 이를 감시하는 알람도 그 리전에 있었어요. 알람이 메시지를 보내는 토픽도 함께 있었고요. IAM 보안 이벤트를 받는 이벤트 규칙과 CloudFront 웹 방화벽의 로그그룹도 us-east-1에 만들었습니다. 저장소에서는 이미 관리하고 있던 리소스인데 수집 범위에서 빠져 있었어요.

고치면서 하나를 더 발견했어요. 알람, 로그그룹, 이벤트 규칙은 이름이 리전 안에서만 유일합니다. 서울과 us-east-1 에 같은 이름의 알람이 따로 있을 수 있어요. 그런데 첫 버전은 이름만 키로 썼습니다. 그러면 us-east-1 의 알람이 서울의 같은 이름 알람과 "일치"로 처리돼요. 실물은 둘인데 하나로 셈이 맞아 버리는 거죠. 그래서 이런 종류는 키 앞에 리전을 붙였습니다.

고친 뒤의 키 리전 안에서만 유일한 종류 ap-northeast-2|{알람 이름} (알람 · 로그그룹 · 규칙 · Lambda 등) us-east-1|{알람 이름} <- 이제 서로 다른 것 ARN 이나 전역 유일 ID 로 맞추는 종류 그대로 (리전이 이미 값 안에 있다) 글로벌 종류 (IAM · CloudFront · 버킷) 서울에서 한 번만 센다

us-east-1도 수집기가 지원하는 전 종류를 조회하도록 넓혔어요. 일부 서비스만 있을 것이라고 가정하지 않고 계정에 실제로 있는 리소스를 확인하기로 했습니다.

KMS 키 하나 때문에 키 종류 전체가 빠졌다

두 번째는 수집 실패였어요. KMS 키 수집기가 통째로 실패했습니다. 키 목록은 받아왔는데, 키마다 상세를 묻는 호출에서 하나가 거부됐어요.

수집 실패 kms_key list_keys 성공 (키 목록은 다 받았다) describe_key 키 하나에서 AccessDenied

→ 잡의 역할로는 그 키 하나의 상세를 볼 수 없었다는 뜻이에요. 다른 키들은 다 보였습니다.

잡이 쓰는 역할에는 AWS 의 읽기 전용 관리형 정책이 붙어 있어요. 거의 모든 서비스의 조회가 허용됩니다. 그런데도 막힌 이유는 KMS 의 권한 구조에 있어요.

📖 용어: KMS 키 정책
KMS 키마다 붙는 권한 문서예요. 다른 서비스와 달리 KMS 는 키 정책이 먼저입니다. 키 정책이 "이 계정의 IAM 정책도 따른다"고 허용해 두지 않으면, IAM 역할에 아무리 넓은 권한을 붙여도 그 키에는 적용되지 않아요.

그 키의 키 정책은 잡의 역할에 상세 조회를 허용하지 않았어요. 역할에 붙인 IAM 정책만으로는 이 키를 조회할 수 없었습니다.

수집기는 종류 단위로 예외를 잡고 있었어요. 키 하나에서 예외가 나도 KMS 키 수집 전체가 실패로 기록됐습니다. 나머지 키도 결과에서 빠졌고, 수집 실패를 리소스가 없다는 뜻으로 처리하지 않도록 "state 에만 있는 것" 판정도 이 종류는 건너뛰었어요.

예외를 키 단위로 처리하도록 고쳤어요. 상세 조회가 거부된 키는 목록에서 빼지 않고 "상세 조회 거부"라고 표시했습니다. 이러면 목록에서 확인한 키의 존재와 상세 조회 가능 여부를 구분할 수 있어요.

이 키에 접근할 수 없다는 사실은 열하루 전인 9/16 표의 "담지 않기로 정한 것" 절에도 적혀 있었고, 규칙 파일로도 옮겨 둔 상태였어요. 다만 그 규칙은 수집이 끝난 뒤 분류할 때만 적용됐습니다. 수집 단계에서는 조회 거부를 별도로 처리하지 않아, 이미 알고 있던 제약 때문에 전체 수집이 실패한 거예요.

모르는 종류 15개

태그 조회 API로 확인한 리소스 주소 중 수집기가 없는 종류도 따로 셌어요. 첫 실행에서 VPN 게이트웨이, 네트워크 방화벽, 키페어, 배포 서비스의 앱 등 15종이 나왔습니다. 수집기를 추가해 지원 범위를 79종에서 94종으로 늘렸어요. 미지원 종류가 수집 결과에서 0개처럼 보이지 않도록 둔 보조 점검이었습니다.

4. 두 번째 실행: 숫자가 정확히 맞았다

셋을 고치고 다시 돌렸어요. 결과는 도입에 적은 그대로입니다.

두 번째 실행 수집기 94종 · 규칙 37개 · 수집 실패 0 · 모르는 종류 0 managed candidate excluded-kind aws-managed excluded orphan? 전체 802 638 172 113 41 36 1,802 9/16 손으로 센 개수와 비교 EIP 60 · SG 67 · S3 131 · IAM 역할 154 · 로그그룹 112 · CloudFront 51 · Lambda 24 -> 일곱 종류 전부 같다

당시에는 수집 결과의 개수가 손으로 센 값과 같다는 점을 수집 범위를 검증한 근거로 삼았어요. 첫 실행에서 있었던 종류 누락이나 목록 잘림을 점검하려는 비교였습니다. 다만 개수가 같다는 결과만으로 그런 결함이 전혀 없다고 단정할 수는 없었어요.

9/16에는 터미널에서, 9/27에는 CI에서 같은 목록 조회 API를 불렀어요. 개수 비교는 수집 결과를 점검하는 데 쓸 수 있지만, 각 항목의 식별자를 올바르게 대조하고 분류했는지까지 확인해 주지는 않습니다.

더 걸리는 게 하나 있어요. 같은 날 로드맵 문서에 이런 문장도 적었거든요. us-east-1 에 이 저장소가 만든 것 24건이 있고, 9/16 표는 그것을 세지 않았다. 두 번째 실행은 us-east-1 을 전부 봅니다. 그리고 거기에는 웹 방화벽 로그그룹이 있어요. 그런데 로그그룹은 112 로 똑같았습니다. 리전별로 나눠서 비교했는지, 범위가 달랐는데 우연히 맞았는지, 지금 남은 기록으로는 가릴 수 없어요. 승인 근거로 삼은 개수조차 같은 범위에서 수집한 값인지 확인되지 않은 상태였어요.

16편에서도 이미지 저장소의 부품 수가 120 = 60 × 2로 맞는다는 것만으로 고아 리소스가 0이라고 할 수 없다고 적었어요. 이번에는 계정 전체를 조사하면서 개수 일치를 충분한 검증으로 판단한 셈입니다.

• 개수는 수집 결과를 비교한 근거지만, 리소스별 소유 판정이나 누락 여부를 확정하는 근거로는 부족했어요
• 승인 근거에는 비교한 범위와 아직 확인하지 못한 항목을 함께 적어야 했어요

5. 항목별로 확인한 주소의 소유와 남은 state

승인 커밋을 올린 몇 시간 뒤에는 결과의 각 항목을 다시 살펴보고, 확인이 필요한 것은 터미널에서 직접 조회했어요. 이 과정에서 주소의 소유와 state에 남은 버킷 기록을 확인했습니다.

탄력적 IP 60개 중 54개는 로드밸런서 것이었다

9/16 표는 탄력적 IP 60개를 한 줄로 정리했어요. "ALB 가 관리한다. 담지 않는다." (ALB 는 애플리케이션 로드밸런서예요.) 그런데 그건 확인한 사실이 아니라 짐작이었습니다. 60개를 하나하나 열어 본 적은 없었어요. 이번에는 주소마다 어디에 붙어 있는지를 봤습니다.

📖 용어: ENI (네트워크 인터페이스)
VPC 안에서 IP 를 갖는 가상 네트워크 카드예요. 서버뿐 아니라 로드밸런서, NAT 게이트웨이도 서브넷마다 ENI 를 하나씩 만들어 씁니다. ENI 에는 "누가 만들었나"를 뜻하는 요청자 값이 남아요.

탄력적 IP 가 서버가 아니라 ENI 에 붙어 있으면, 그 ENI 의 요청자를 물어봤어요. 결과는 이랬습니다.

탄력적 IP 60개 ENI 요청자가 로드밸런서 서비스 54 = ALB 27개 × 가용영역 2 그 밖 6 -> 54개는 로드밸런서가 서브넷마다 만든 ENI 에 붙은 주소다 우리가 할당하고 붙인 것이 아니다. 편입하면 남의 자원을 소유하게 된다

27 × 2 라는 등식이 이유를 말해 줘요. 로드밸런서는 가용영역마다 서브넷에 ENI 를 하나씩 둡니다. 27개가 두 영역씩 쓰니 54개예요. 21편에서 이런 주소 하나를 "우리가 붙였다가 잃은 고정 IP"로 오해했다가, 감사 기록을 보고 로드밸런서 서비스가 주체라는 걸 알았다고 썼죠. 그 오해의 범위가 계정 전체로는 54개였던 겁니다.

9/16 표의 "ALB 가 관리한다"는 설명은 54개에만 해당했어요. 나머지 6개는 로드밸런서가 만든 것이 아니어서 별도로 판정해야 했습니다. 60개를 한 줄로 정리한 개수 표에는 이 차이가 드러나지 않았어요.

고친 방식은 규칙 한 줄이에요. 이름이나 태그가 아니라 "ENI 요청자가 로드밸런서 서비스다"라는 사실로 aws-managed 를 판정합니다. 새 로드밸런서가 생기면 그 주소도 자동으로 같은 분류에 들어가요. 나머지 여섯은 이 규칙에 걸리지 않으니 연결 상태에 따라 각자 분류를 받아요. 60개를 일괄 제외하던 방식과 달리 항목별 판정이 남습니다.

404 인 버킷이 state 에 있는데 plan 은 No changes 였다

두 번째는 "state 에만 있는 것" 목록에 남은 버킷 하나였어요. 개발 환경의 한 스택이 쓰던 버킷입니다. 실물에 직접 물어보니 404 가 왔어요.

HeadBucket {버킷 이름} -> 404 Not Found

이 작업에서는 해당 응답을 부재 후보로 분류했어요. 다만 HeadBucket은 버킷이 없거나 권한이 부족할 때 400·403·404 같은 일반 오류를 반환할 수 있어요. 404 하나만으로 권한 문제를 배제하거나 버킷이 없다고 확정할 수는 없으므로, 권한과 목록 조회 등 다른 근거를 함께 확인해야 합니다.

이력을 거슬러 가 보니 8월 중순에 그 스택의 구성을 바꾼 커밋이 있었어요. 버킷이 필요 없는 방식으로 옮기면서 코드에서 버킷 블록이 통째로 빠졌습니다. 그런데 state 에서는 빠지지 않았어요. 그리고 그 스택의 plan 은 No changes 였어요.

코드에서 빠졌고 state에 남았다면 plan에 삭제가 나올 것으로 예상했어요. 이 경우에 변경이 없었던 이유는 plan의 변경 계산 전에 수행하는 refresh에 있었습니다.

📖 용어: refresh
plan 이 변경을 계산하기 전에, state 에 적힌 리소스마다 실물을 다시 조회해 최신 값으로 맞추는 단계예요. 이 결과는 그 plan 의 계산에만 쓰이고, plan 은 state 파일을 고쳐 쓰지 않습니다.
그림 2. 이 버킷은 plan에 변경이 없어도 state 파일에 기록이 남았어요

이 사례의 plan 처리 순서로 보면 이래요. refresh가 state의 버킷을 조회하고 404를 받은 뒤, 프로바이더가 이번 plan에서 "이미 사라진 것"으로 처리했어요. 이 처리는 앞에서 설명한 HeadBucket 상태코드만으로 실제 부재를 확정하는 것과 구분해야 합니다. 코드에도 블록이 없으니 원하는 상태도 "없음"입니다. 없음과 없음 사이에 할 일이 없으니 No changes 예요. 그리고 plan 은 state 파일을 고쳐 쓰지 않으니, 다음 plan 에서도 똑같은 일이 반복됩니다.

매일 plan을 돌리는 drift 점검에서도 이 버킷은 나오지 않았어요. state를 직접 읽어 실물의 식별자와 대조하면서 처음 확인했습니다. plan에 변경이 없어도 state 파일에는 실물이 없는 리소스 기록이 남을 수 있었어요.

이 줄을 정리하는 방법은 removed 블록이에요.

📖 용어: removed 블록
"이 주소의 리소스를 state 에서 빼라"고 코드로 적는 Terraform 문법이에요. destroy = false 를 같이 쓰면 실물은 건드리지 않고 기록만 지웁니다. 명령줄에서 state 를 직접 고치는 대신 PR 로 리뷰를 받을 수 있어요.
removed { from = aws_s3_bucket.root lifecycle { destroy = false } }

이 주소의 기록을 state에서 제거하고 실물은 삭제하지 않도록 지정한 예시예요.

그런데 이 블록을 쓰려면 주소가 필요합니다. 버킷 이름만으로는 어느 스택의 어느 모듈, 어느 for_each 키인지 알 수 없어요. 그래서 "state 에만 있는 것" 목록에 Terraform 주소를 같이 적도록 바꿨습니다. 목록에서 줄을 복사해 그대로 from 에 넣을 수 있게요.

다만 이 글을 쓰는 시점에 그 removed 블록은 아직 커밋하지 않았어요. 로드맵에서 정리 배치는 "삭제 보류, 근거 수집과 판정표까지만"으로 정해 둔 상태였습니다. 이번에 한 일은 남은 기록을 찾고 주소를 결과에 추가한 것까지예요.

6. 검증 범위를 구분해서 남기기

이날은 개수와 식별자를 비교하고, state에만 남은 항목도 따로 확인했어요. 각 비교에서 확인하려던 문제를 표로 나누면 다음과 같습니다. 다만 앞서 확인했듯, 개수 일치만으로 첫 행의 누락 가능성을 모두 배제할 수 있는 것은 아니에요.

검증 배제하는 실패 배제하지 못하는 실패 개수가 9/16 과 같다 종류가 통째로 빠짐 · 목록 잘림 어느 항목이 누구 것인지 틀림 같은 이름의 다른 리소스 식별자 대조 위의 둘 + 항목 단위 소유 오판 state 에만 있는 기록 (state 를 따로 읽어야 보인다) state 에만 있는 것 코드에서 빠졌는데 state 에 남음 - 식별자 매핑 실수

위 표의 둘째 행도 조건부 요약이에요. 수집된 항목의 식별자를 대조한다고 해서 수집 범위 자체가 완전해지는 것은 아닙니다. 종류 전체의 누락이나 목록 잘림, 항목별 조회 실패는 별도 확인이 필요하고, 식별자 구성과 소유 판정의 근거도 각각 검토해야 해요.

첫 실행에서 us-east-1의 24건은 수집 범위가 빠진 문제였고, KMS 키는 한 항목의 조회 실패를 종류 전체의 실패로 처리한 문제였어요. 리전 없는 이름 키는 서로 다른 리소스를 같은 것으로 대조하게 했습니다. 총개수와 함께 수집 범위, 조회 실패, 식별자 키 구성을 각각 확인해야 했어요.

💡 실무에서는: 인벤토리 수집기를 짤 때
• 예외는 항목 단위로 잡으세요. 하나의 권한 거부가 종류 전체를 지우면, 그 종류는 "0개"가 아니라 "모름"이 됩니다. 거부된 항목은 사실로 남기세요
• 이름이 리전 안에서만 유일한 종류는 키에 리전을 붙이세요. 알람, 로그그룹, 이벤트 규칙, Lambda 가 그렇습니다
• 글로벌 서비스와 관련된 리소스의 리전도 확인하세요. 이 계정에서는 us-east-1의 알람과 이벤트 규칙 등이 수집 범위에서 빠졌어요
• state 쪽 결과에는 Terraform 주소를 같이 적으세요. 찾은 다음 단계가 removed 블록이라면 주소가 없을 때 다시 찾아야 합니다
• 이 잡은 새 권한 없이 만들었어요. plan 역할이 이미 읽기 전용 권한과 state 버킷 읽기를 갖고 있었습니다

잡은 매주 월요일 아침, drift 점검 30분 뒤에 돌도록 했어요. 콘솔에서 새로 만든 리소스는 다음 주 수집 범위에 포함되면 규칙에 따라 분류됩니다. 수작업 표를 다시 만드는 대신 같은 절차를 반복 실행할 수 있게 됐지만, 결과를 볼 때는 총개수와 함께 항목별 분류와 수집 범위도 확인해야 해요.

✍️ 오늘의 요약
실물과 state를 식별자로 대조하면서 us-east-1 수집 누락과 KMS 키의 예외 처리를 고쳤고, 탄력적 IP 60개 중 54개를 로드밸런서 관리 대상으로 분류했어요. 실물이 404인 버킷의 state 기록도 찾았지만, 정리 블록은 아직 커밋하지 않았습니다.

두 번째 실행의 개수는 9/16 조사와 같았고 이를 승인 근거로 썼어요. 다만 로그그룹의 리전별 집계 범위는 남은 기록으로 확인하지 못했으므로, 개수 일치만으로 수집과 항목별 판정이 모두 맞았다고 결론 내릴 수는 없습니다.
