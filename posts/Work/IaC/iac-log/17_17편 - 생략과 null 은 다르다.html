17편. Terraform import 후 첫 apply 전에 기본값과 변경 속성 확인하기 ← 지금 이 글

여러 해째 운영 중인 서비스 하나를 Terraform으로 관리하기로 했어요. 로드밸런서와 리스너, 타깃그룹, 데이터베이스, 서버를 가져오는 작업이었고, 모두 사용 중인 리소스였습니다. 작업 문서 첫 줄에는 이렇게 적었어요. "import 는 실물을 건드리지 않는다. state 에만 쓴다."

terraform import 는 AWS 리소스를 읽고, Terraform의 리소스 주소와 실제 리소스의 연결을 state 파일에 저장해요. 이 단계에서는 실제 리소스의 설정값을 바꾸지 않습니다.

하지만 그다음 apply 는 실제 설정을 바꿀 수 있어요. 저는 import 가 설정을 바꾸지 않는다는 이유로 직접 작성한 코드를 써도 안전하다고 판단했는데, 첫 plan 에서 코드와 실제 설정의 차이가 드러났습니다.

확인해야 할 것은 변경 개수만이 아니었어요. 삭제 보호를 끄는 변경도 태그 하나를 수정하는 변경도 요약에는 ~ 1 로 표시됐습니다. 생략한 속성과 null 이 어떻게 처리되는지 확인하고, 바뀌는 속성까지 대조해야 했어요.

1. 생략한 속성이 첫 apply 에서 바뀔 수 있어요

import 는 state 에 리소스를 등록하는 명령이고, 설정 코드를 만들어주지는 않아요. import 직후 state 에는 읽어온 실제 속성이 있지만, 코드(.tf)에는 제가 작성한 속성만 있었습니다.

이후 apply 는 코드에 적힌 설정을 실제 리소스에 반영해요. 일부 속성은 코드에 생략하면 프로바이더 기본값으로 계획되기 때문에, 기존 설정이 기본값으로 바뀔 수 있습니다. 리소스가 삭제되지 않아도 운영에 필요한 기능이 꺼질 수 있는 거예요.

생략한 속성이 모두 바뀌는 것은 아니에요. 기존 값을 유지하는 속성도 있고, 그 차이는 4장에서 설명할 스키마에 따라 달라집니다. 따라서 생략해도 되는지는 속성별로 확인해야 해요.

가져오려던 데이터베이스에서는 최소 네 가지 설정이 바뀔 수 있었어요.

코드에 안 적으면 첫 apply 가 이렇게 되돌린다 deletion_protection true -> false 삭제 보호가 꺼진다 enabled_cloudwatch_logs_exports 4종 -> 전부 해제 감사 로그가 내려간다 monitoring_interval 60 -> 0 향상된 모니터링이 멈춘다 performance_insights_enabled true -> false 성능 통계가 꺼진다

네 가지 모두 실제 리소스에서는 켜져 있었지만 제 코드에는 없었어요. 이 속성들은 생략하면 기존 값을 유지하지 않고 기본값으로 바뀌는 경우였습니다.

감사 로그와 성능 통계는 꺼진 뒤 다시 켜더라도 그 사이에 수집하지 못한 기록을 복구할 수 없어요. 삭제 보호를 다시 켜는 것과는 영향이 달랐습니다. apply 전에 확인해야 하는 이유였어요.

공유 보안그룹이 제거되면 타깃 연결에 영향이 생겨요

로드밸런서의 security_groups 도 확인해야 했어요.

해당 로드밸런서에는 계정의 퍼블릭 로드밸런서 30여 개가 함께 쓰는 공유 보안그룹 하나만 연결돼 있었어요. 코드에 이 속성을 적지 않으면 apply 가 그 연결을 제거하려 했고, 이때는 로드밸런서에서 타깃으로 가는 트래픽에 영향이 생깁니다.

타깃 쪽 보안그룹은 로드밸런서의 보안그룹을 참조해서 트래픽을 허용하고 있었어요. 로드밸런서에서 해당 보안그룹이 제거되면 그 허용 조건을 충족하지 못합니다. 외부 요청은 로드밸런서까지 도착해도 서버로 전달되지 못하고, 헬스체크도 실패할 수 있어요. 다만 healthy 타깃이 0이라는 사실만으로 응답을 503으로 확정할 수는 없습니다. ALB는 등록된 타깃이 모두 unhealthy이면 fail-open으로 그 타깃에 전달을 시도하므로, 실제 응답은 등록 상태와 연결 실패 양상을 함께 확인해야 해요.

같은 계정의 {다른 서비스}에서 이 원인으로 연결이 끊긴 이력이 있었어요. 그 기록을 보고 이번 import 점검 항목에도 포함했습니다.

⚠️ in-place 변경도 별도로 확인해야 해요
• 당시 삭제와 재생성을 막는 장치는 prevent_destroy, 라벨 게이트, 리뷰였어요.
• 이 중 삭제·재생성 판정이 보는 것은 - 와 ± 이고, 기존 리소스를 수정하는 ~(in-place)는 그 대상이 아니었어요.
• apply 가 실제 설정을 코드에 맞춘 결과라면 직후 드리프트도 0 으로 나와요. 드리프트 감지는 코드와 실제 설정의 차이를 찾기 때문입니다.
• 공유 보안그룹 제거로 healthy 타깃이 0 이 되면 알람이 오지만, 연결에 영향이 생긴 뒤의 알림이에요.
• 따라서 - 와 ± 외에 ~ 안에서 어떤 속성이 바뀌는지도 확인해야 했어요.
그림 1. import 는 state 에 등록하고, 첫 apply 는 실제 설정을 바꿀 수 있어요

2. 직접 작성한 설정에서 태그 외 변경 7건이 나왔어요

설계 리뷰에서는 "사람이 손으로 쓴 설정으로 import 하지 마라"는 권고가 나왔어요. 직접 옮겨 적다가 값을 빠뜨리거나 잘못 적으면 실제 설정과 다른 코드로 apply 할 수 있기 때문이었습니다.

저는 리소스가 몇 개 안 되니 콘솔에서 읽은 값을 직접 옮기는 편이 빠르다고 판단했어요. 대신 첫 plan 에서 태그 외의 변경이 나오면 직접 작성한 코드를 버리고 생성 도구로 전환하겠다는 조건을 정했습니다.

손으로 쓴다. 대신 갈아탈 조건을 미리 못 박는다. 첫 plan 에서 tags 밖의 변경이 하나라도 뜨면 -> 손으로 쓴 것을 버리고 생성 도구로 갈아탄다 -> apply 하지 않는다

첫 plan 에서는 태그 외의 변경이 7건 나왔어요. 그중에는 운영 중인 443 리스너에 수정 API 를 보내는 변경도 있었습니다.

직접 작성한 코드와 실제 설정을 대조하니 네 군데가 달랐어요.

손으로 쓴 것 실물 그대로 apply 했다면 ------------------------------------------------------------------------------------------------ Name = {서비스}-prod-alb-https {서비스}-api-prod-alb-listener-2 없는 이름으로 태그를 덮어씀 forward 블록 생략 (축약형으로 씀) ForwardConfig 명시 운영 443 리스너에 ModifyListener lambda_multi_value_headers 생략 = null ModifyTargetGroupAttributes stickiness / target_group_health 실물에 블록이 있음 그 블록을 지우려 함

리스너의 Name 태그는 실제 값을 확인하지 않고 예상한 이름으로 적은 것이었어요. 그대로 apply 했다면 실제 태그를 제가 추측한 값으로 바꾸게 됩니다. 태그 변경도 원래 값을 확인해야 한다는 점을 놓쳤어요.

직접 작성하기로 한 판단에는 누락 위험을 충분히 반영하지 못했어요. 다만 전환 조건을 미리 정해 두었기 때문에 7건을 확인한 뒤에는 apply 하지 않고 생성 도구로 바꿀 수 있었습니다.

💡 직접 작성하기 전에 중단 조건을 정했어요
이번에는 첫 plan 에 태그 외 변경이 하나라도 나오면 apply 하지 않고 생성 도구로 바꾸기로 했어요. "위험해 보이면 중단한다"는 표현 대신 plan 에서 확인할 수 있는 조건을 적었습니다.

3. 자동 생성한 설정에도 검증 오류가 있었어요

직접 작성한 코드 대신 terraform plan -generate-config-out 을 사용했어요. 실제 리소스를 읽어 .tf 설정을 생성하는 기능이라, 값을 사람이 옮겨 적는 과정은 줄일 수 있었습니다.

하지만 생성된 설정도 프로바이더 검증에 걸려 validate 부터 실패했어요. 아래에 모은 사례만 열일곱 가지입니다. 리소스 종류를 늘릴 때마다 다른 오류가 나왔고, 커밋 메시지에도 "일곱 번째다"라고 적을 정도로 반복됐어요.

생성된 설정이 프로바이더 자기검증에 걸린 것들 [A] 값이 허용 범위 밖이다 target_control_port = 0 1-65535 만 받는다 default_action.order = 0 1-50000 만 받는다 forward.stickiness.duration = 0 1-604800 만 받는다 tunnel1_rekey_margin_time_seconds = 0 60-1800 만 받는다 tunnel1_replay_window_size = 0 64-2048 만 받는다 tunnel1_dpd_timeout_seconds = 0 하한 미달 tunnel1_ike_versions = [] 빈 집합은 받지 않는다 root_block_device 의 iops · throughput 실물이 gp2 인데 gp3/io1/io2 전용 [B] 함께 쓸 수 없는 것을 같이 뱉는다 mutual_authentication mode 가 off 인데 ignore_client_certificate_expiry 를 같이 낸다 subnet_mapping subnets 와 충돌 launch_template id 와 name 을 동시에 낸다 ipv6_address_count + ipv6_addresses 0 과 [] 를 둘 다 낸다 (상호 배타) primary_network_interface associate_public_ip_address 와 상호 배타 [C] 다른 타입 전용 속성을 붙인다 tunnel_bandwidth = "standard" vpn_gateway_id 와 conflicts with (Transit Gateway 연결 전용 속성) enable_acceleration = false transit_gateway_id 와 함께만 쓸 수 있다 [D] 필수 인자 없이 빈 블록을 낸다 target_failover {} target_health_state {}

생성된 설정의 속성 조합이 프로바이더 규칙에 맞지 않는다는 오류였어요.

Error: Invalid Attribute Combination Attribute "mutual_authentication[0].ignore_client_certificate_expiry" cannot be specified when "mutual_authentication[0].mode" is "off".

미설정 값과 스키마 검증이 맞지 않았어요

여러 오류는 AWS API 응답, 설정 생성 결과, 프로바이더 스키마가 "값이 없음"을 다르게 처리하는 데서 나왔어요. 스키마는 각 속성의 타입과 허용 범위 등을 정한 규칙입니다.

여기서 문제가 된 AWS API 는 미설정 속성을 0 이나 [] 로 반환했어요. 생성 결과에도 = 0 과 = [] 가 들어갔습니다. 그런데 프로바이더 스키마에는 "1 이상만 허용한다", "빈 집합은 허용하지 않는다"는 검증이 있었어요. API 에서는 미설정 상태를 나타내던 값이 설정 코드에서는 검증 오류가 된 거예요.

모든 AWS API 가 같은 방식으로 응답하는 것은 아니에요. 미설정 필드가 응답에서 빠져 생성 결과에 = null 이 들어가는 경우도 있었고, 그 경우에는 위와 같은 범위 검증 오류가 나지 않았습니다. 리소스 종류를 늘리면서 생성 결과를 각각 확인해야 했어요.

[C] 는 다른 연결 유형에만 쓸 수 있는 속성이 생성된 경우예요. Transit Gateway 연결 전용 속성이 Virtual Private Gateway 연결의 설정에도 포함됐고, 프로바이더가 그 조합을 허용하지 않아 실패했습니다.

💡 생성 설정도 검증한 뒤 사용했어요
직접 작성한 설정에서는 실제와 다른 값을 빠뜨리기 쉬웠고, 생성한 설정에서는 허용 범위나 속성 조합 오류가 나왔어요. 후자는 validate 에서 확인할 수 있었습니다. 열일곱 가지 오류를 정리하는 작업이 필요했지만, 값을 직접 옮기는 방식으로 돌아가지는 않았어요.

4. null 을 적어도 기본값이 적용되는 속성이 있어요

기존 값을 유지하려면 실제 설정을 코드에 반영해야 해요. 값이 없는 속성은 = null 로 남겨 두면 될 것 같았습니다.

그런데 일부 속성은 = null 로 적어도 스키마 기본값이 적용돼 plan 의 ~ 가 남았어요. 실제로 코드를 작성하고 CI plan 을 확인하면서 알게 된 차이였습니다.

생략한 경우뿐 아니라 null 을 명시한 경우에도 기본값이 적용되는지 확인해야 했어요.

겹 1. 생략하면 -> 프로바이더 기본값이 실물을 덮는다 겹 2. = null 로 적어도 -> 프로바이더 스키마 기본값이 이긴다 즉 "명시적으로 비움" 이 통하지 않는 속성이 있다.

스키마의 Optional 과 Computed 를 확인했어요

속성마다 결과가 다른 이유는 스키마의 optional 과 computed 설정에 있어요. 각각 사용자가 값을 생략할 수 있는지, 프로바이더가 값을 결정할 수 있는지를 나타냅니다.

Optional + Computed 속성은 생략했을 때 이전 state 의 값을 계획에 사용할 수 있어요. 3장의 target_control_port 는 생략해도 기존 값이 유지되는 경우였습니다.

이 설명은 이전 state 에 값이 있는 import 상황을 기준으로 해요. 새 리소스를 만들 때는 이어받을 기존 값이 없으므로 같은 상황으로 볼 수 없습니다.

반면 기본값이 있는 Optional 속성은 생략하거나 null 로 적어도 기본값이 적용될 수 있어요. 1장에서 본 설정 변경은 이런 경우였고, = null 을 적어도 막을 수 없었습니다.

리스너의 고정 세션 블록은 다른 처리가 필요했어요. 실제 지속 시간은 0 인데 프로바이더가 1 이상만 허용했고, 블록을 통째로 제거하면 운영 리스너에서 해당 블록을 없애는 변경이 생겼습니다. 그래서 허용 범위의 값을 적고 그 속성의 변경만 무시했어요. 고정 세션이 꺼진 상태라 지속 시간은 사용되지 않았습니다.

3장에는 같은 속성을 제거한 사례도 있어요. 그 스택에서는 실제 리소스에 블록이 없어 제거할 수 있었습니다. 같은 속성이라도 리소스의 기존 설정에 따라 처리 방법이 달라졌어요.

당시 참고한 문서에는 Optional 이라는 설명만 있고 Computed 여부가 드러나지 않는 경우가 있었어요. 문서의 선택 속성이라는 설명만으로는 기존 값이 유지될지 판단하기 어려웠습니다.

terraform providers schema -json 으로 두 플래그를 확인할 수는 있지만, 기본값까지 나오지는 않아요. 이 작업에서는 코드를 적고 plan 을 돌려 ~ 가 사라지는지 확인하는 방법을 썼습니다.

그림 2. 미설정 속성의 처리는 스키마와 기존 블록에 따라 달라져요

변경 무시와 기본값 명시를 나눠 적용했어요

= null 로도 변경이 사라지지 않을 때는 변경을 무시할지, 기본값을 명시할지 정했어요. 실제로 여섯 속성을 다음과 같이 처리했습니다.

속성 AWS 호출 미래 의미 확인 비용 처방 --------------------------------------------------------------------------------------- proxy_protocol_v2 있다 없다 - ignore_changes lambda_multi_value_headers_enabled 있다 없다 - ignore_changes enable_global_write_forwarding 있다 없다 운영 라이터 ignore_changes enable_local_write_forwarding 있다 없다 운영 라이터 ignore_changes force_destroy (DB 인스턴스) 없다 없다 - ignore_changes user_data_replace_on_change 없다 있다 - 기본값 명시 무시하는 쪽도 코드에는 = null 을 그대로 남겼다. 동작은 ignore_changes 가 정하고, null 은 "AWS 가 이 값을 안 줬다" 는 사실을 코드에 남긴다.

타깃그룹에서는 다른 유형에만 사용하는 속성이 문제가 됐어요. proxy_protocol_v2 는 네트워크 로드밸런서 쪽 속성이어서 애플리케이션 로드밸런서의 타깃그룹에 수정 요청을 보내면 거부될 수 있었습니다. 관리 대상이 아닌 속성은 ignore_changes 에 명시했어요.

이 목록을 다른 유형의 리소스에 그대로 적용하면 안 돼요. 같은 계정의 네트워크 로드밸런서 타깃그룹에서는 proxy_protocol_v2 가 실제 값(false)으로 읽혔고, 무시 목록에는 lambda_multi_value_headers_enabled 만 넣었습니다. 속성 이름과 함께 리소스 유형도 확인했어요.

데이터베이스의 write forwarding 플래그 둘은 당시 엔진 버전이 지원하지 않아 API 응답에 값이 없었어요. 하지만 apply 하면 운영 중인 라이터에 클러스터 수정 API 를 보내게 됐습니다. 미지원 기능에 대한 요청이 어떻게 처리될지 확인되지 않았고, 운영 라이터에서 시험할 수는 없어 변경을 무시하기로 했어요.

며칠 뒤 엔진을 올리면서 해당 기능을 지원하는 버전이 됐어요. 기능은 사용하지 않았으므로 무시 설정을 유지하되, 주석의 이유를 "미지원"에서 "지원하지만 사용하지 않음"으로 고쳤습니다.

DB 인스턴스의 강제 삭제 스위치는 Terraform 전용 필드여서 AWS 호출은 없었지만 변경을 무시했어요. 이 리소스는 태그 외 변경이 없어야 한다는 중단 조건을 두고 있었기 때문입니다. 무해한 변경이라도 항상 표시되면 예외로 넘겨 읽게 될 수 있다고 판단했어요.

서버의 user_data_replace_on_change 는 기본값을 명시했어요. 이 속성도 Terraform 전용 필드라 AWS 호출은 없지만, 나중에 부팅 스크립트를 바꿀 때 인스턴스를 재생성할지 결정합니다. ignore_changes 에 넣으면 이후에도 변경을 무시하게 되므로, 기본값을 적어 첫 apply 후 state 에 반영했습니다.

💡 변경을 무시할지 정할 때 확인한 항목
• AWS 호출이 생기는지, 호출의 영향을 확인할 수 있는지 살폈어요.
• 나중에 관리할 속성인지도 확인했어요. ignore_changes 에 남기면 이후 변경도 무시하게 됩니다.
• AWS 호출이 없어도 태그 외 변경을 금지한 중단 조건을 유지하기 위해 무시한 속성이 있었어요.
• 운영 라이터에서 시험할 수 없어 확인하지 않은 경우에는 그 이유를 주석에 남겼고, 엔진 버전이 바뀐 뒤에는 이유도 갱신했어요.

미설정 상태의 의미도 확인해야 해요

필드 부재와 명시적 null 을 구분하는 규약은 부분 갱신 API 에도 있어요. 일부 규약에서는 필드가 없으면 기존 값을 유지하고 null 이면 값을 지우도록 정합니다.

다만 Terraform 에서는 미설정 상태를 어떻게 처리할지 프로바이더 스키마도 확인해야 해요. 이 작업에서는 Optional + Computed 속성의 기존 값이 유지되는 경우와, 기본값이 적용되는 경우를 나눠 확인했습니다.

생성 결과의 null 줄은 어떤 상태에서 생성됐는지 확인하고 다뤘어요. = null 을 남겨도 기본값에 따른 변경이 계획되는 속성이 있었고, 그중 변경을 보내면 안 되는 속성에는 null 과 별도로 ignore_changes 가 필요했습니다.

5. plan 요약의 "~1" 만으로는 판단하기 어려워요

이런 변경은 plan 의 요약에서 다음과 같이 표시돼요.

Plan: 0 to add, 1 to change, 0 to destroy.

태그 하나를 바꿔도 같은 요약이 나옵니다. 삭제 보호를 끄는 변경도 ~ 1, 라벨 오타를 고치는 변경도 ~ 1 이라서 요약만으로는 영향을 구분할 수 없어요.

코드로 관리하지 않던 인스턴스에서도 기본값과 실제 값이 다른 두 속성을 확인했어요.

source_dest_check = false (프로바이더 기본값 true) disable_api_termination = true (프로바이더 기본값 false) 둘 다 코드에서 빠지면 첫 apply 가 기본값으로 되돌린다. 전자는 그 인스턴스를 통한 라우팅을 끊고, 후자는 종료 보호를 푼다.

태그와 같은 리소스에서 바뀌면 ~ 1 이 그대로 ~ 1 일 수 있고, 다른 리소스가 함께 바뀌면 ~ 2 로 보일 수 있어요. 변경 개수와 속성의 위험은 따로 확인해야 합니다.

변경되는 속성 경로를 출력했어요

판정 스크립트는 바뀌는 속성의 경로를 출력하도록 만들었어요. 스택 README 의 중단 조건도 처음부터 허용할 속성 이름으로 적혀 있었습니다.

스택 README 의 중단 조건 (첫 판부터 이 문장이었다) "tags 와 tags_all 밖의 속성이 하나라도 바뀌면 apply 하지 않는다" python3 scripts/plan-verdict.py plan.json --expect tags,tags_all 기대 밖 속성이 하나라도 있으면 실패한다. ::error:: 코드가 실제와 다릅니다. apply 하지 말고 코드를 실제에 맞춘 뒤 plan 부터 다시 하세요.

변경 1건까지 허용한다는 조건만으로는 그 리소스 안에서 태그와 삭제 보호가 함께 바뀌는 경우를 구분하지 못해요. 속성 이름으로 비교하면 태그 100개가 바뀌어도 허용할 수 있고, 태그 외 속성이 하나라도 나오면 중단할 수 있습니다.

출력에는 속성의 값 없이 경로만 넣었어요. plan JSON 에는 민감값이 평문으로 들어갈 수 있고, 결과가 PR 코멘트로 나가기 때문입니다. 허용한 속성이 맞는지 비교하는 데는 경로만 사용했어요.

속성 비교는 아직 수동 확인이었어요

다만 당시 CI 는 --expect 를 자동으로 실행하지 않았어요. 매 PR 에 적용되는 것은 뒤에서 설명할 import 블록 수 대조였고, PR 코멘트에는 여전히 +0 ~0 -0 ±0 · 파괴적 변경 없음 처럼 개수가 표시됐습니다. 워크플로 네 파일 여섯 지점에 복제된 판정을 스크립트로 합치는 작업이 남아 있었어요.

--expect 는 스택 README 를 보고 사람이 직접 실행하는 명령이었어요. 15편에서 다뤘던 수동 확인과 같은 한계가 있었습니다. 제가 실행하지 않고 머지해도 이 속성 비교가 자동으로 막아주지는 않았어요.

스택마다 기대 목록도 달랐어요. 어떤 스택은 tags,tags_all 만 허용하고, 다른 스택은 속성을 하나 더 허용했습니다. 목록을 README 문장으로만 관리하면 스택이 다섯일 때 다섯 문서를 각각 확인해야 해요. 자동 검사로 만들려면 스택 옆에 기대 목록을 데이터로 두고 워크플로가 읽도록 하는 작업이 필요했습니다.

계산 예정인 값은 변경 목록에서 제외했어요

속성을 비교할 때는 실제 변경과 아직 계산되지 않은 값을 구분해야 했어요. 그렇지 않으면 정상 import 도 변경으로 잘못 판정할 수 있습니다.

생성 코드에서 불필요한 기본값 블록을 제거하면 plan JSON 의 after 에서 그 값이 빠질 수 있어요. 프로바이더가 apply 때 계산할 값은 after_unknown 에 따로 표시됩니다. 실제로 기본값 블록 넷을 제거한 plan 에서도 0 to change 가 나왔어요.

그래서 스크립트는 after_unknown 에 표시된 속성을 변경 목록에서 제외했어요. 이를 구분하지 않으면 정상 import 에도 경고가 반복되고, --expect 목록을 불필요하게 넓히거나 검사를 생략하게 될 수 있습니다.

no-op 으로 표시되는 import 도 확인했어요

반대로 import 를 놓치는 문제도 있었어요. 이 문제 때문에 판정 스크립트를 만들기 시작했습니다.

설정 변경이 없는 import 는 액션이 no-op 이고, import 라는 표시가 따로 붙어요. 당시 저장소의 판정은 no-op 을 모두 건너뛰고 있었습니다. 며칠 전 데이터 소스 읽기 세 건이 "기타"로 집계돼 파괴적 변경 가드가 오탐한 뒤 넣은 필터였는데, import 도 함께 제외된 거예요.

이 때문에 판정 결과와 실제로 적용할 작업이 어긋났어요.

운영 중인 prod 리소스가 state 로 들어오는 PR 에서 PR 코멘트 +0 ~0 -0 ±0 · "파괴적 변경 없음" apply 변경 없음으로 판단 → 통째로 스킵 드리프트 clean 미적용 변경 점검 clean → 열려 있던 이슈까지 닫는다 즉 사람이 보는 화면 전부가 "아무 일도 없음" 이었다.

이 경우에는 경고가 반복되는 것과 달리 검사 결과가 정상처럼 보여요. import 가 누락됐다는 사실을 PR 코멘트와 후속 점검에서 모두 놓칠 수 있었습니다.

설정 변경이 없어도 import 가 있으면 apply 대상이라고 판정하도록 고쳤어요. 코드의 import 블록 수와 plan 의 import 건수를 비교하는 단언도 넣었고, 이 검사는 당시 CI 에서 매 PR 에 실행됐습니다. import 블록이 0개일 때는 대조할 대상이 없고, 블록이 추가되면 plan 에 반영된 건수와 비교해요.

속성 비교에서는 update 안의 값이 계산 예정인지 확인해야 했고, import 판정에서는 no-op 옆의 import 표시를 확인해야 했어요. 액션 이름만으로 작업 내용을 판단할 수는 없었습니다.

일회성 예외가 상시로 남은 곳도 있었어요

서버를 가져오는 PR 에서는 user_data_replace_on_change 가 null 에서 false 로 함께 바뀌었어요. AWS 호출이 없고 첫 apply 후 반영되는 값이므로, 그 PR 에서 실행하는 확인 명령에만 허용 속성으로 추가했습니다.

# 평소 python3 scripts/plan-verdict.py plan.json --expect tags,tags_all # 서버를 가져오는 그 PR 에서만 python3 scripts/plan-verdict.py plan.json \ --expect tags,tags_all,user_data_replace_on_change

한 번만 필요한 예외를 기본 목록에 추가하면 이후에도 계속 허용하게 돼요. 이 경우에는 해당 PR 의 확인 명령에만 남겼습니다.

하지만 같은 서비스의 dev 스택에서는 같은 예외가 README 의 중단 조건에 상시로 적혀 있었어요. 한쪽에서는 PR 한 번의 예외였고 다른 쪽에서는 계속 허용되는 상태였습니다. 예외의 적용 범위를 맞추는 작업도 남아 있었어요.

그림 3. 태그 수정과 삭제 보호 해제는 같은 ~1 로 요약돼요

6. 첫 apply 전 확인과 남은 자동화

직접 작성한 설정에서 시작했지만, 첫 plan 을 확인한 뒤 생성 도구로 전환하고 속성별 처리까지 검토하게 됐어요.

import 자체가 설정을 바꾸지 않는다는 사실만으로 이후 apply 까지 안전하다고 판단할 수는 없었습니다. 직접 작성한 코드의 첫 plan 에 태그 외 변경이 7건 나왔고, 그 결과를 보고 apply 를 중단했어요.

이 작업에서는 import 와 첫 apply 를 나눠 확인했어요. 특히 생략했거나 null 로 남긴 속성이 기존 값으로 유지되는지, 기본값으로 바뀌는지를 plan 에서 확인해야 했습니다.

같은 ~ 1 이 태그 수정과 삭제 보호 해제를 모두 나타낼 수 있어 속성 경로를 비교하는 검사도 만들었어요.

다만 import 블록은 멱등적이에요. 같은 주소가 이미 state에 있으면 다시 편입하지 않으므로, apply 뒤 블록을 남겨도 다음 plan은 성공하면서 import 건수가 0이 될 수 있어요. 블록 수와 편입 건수가 다르면 실패하도록 한 것은 이 저장소의 추가 검사이며, Terraform 자체가 기존 블록을 거부하는 동작은 아닙니다. 따라서 이 검사에 오탐이 없다고 단정할 수는 없어요.

"경고 5건 이하", "커버리지 80% 이상", "실패 테스트 0건" 같은 수치가 각 검사의 내용을 모두 설명하지는 않듯이, 이 plan 에서도 변경 개수 외에 어떤 속성이 바뀌는지 읽어야 했습니다.

당시 자동화된 것은 import 건수 대조까지였어요. 속성 경로를 비교하는 명령은 사람이 직접 실행해야 했고, 기대 목록 관리와 워크플로 통합은 남아 있었습니다.

✍️ 정리
직접 작성한 설정의 첫 plan 에서 태그 외 변경 7건을 확인하고 apply 를 중단했어요. 생성 도구로 바꾼 뒤에도 열일곱 가지 검증 오류가 있었고, 생략하거나 null 로 남긴 속성은 스키마에 따라 기존 값 유지와 기본값 적용을 구분해야 했습니다.

설정 변경은 - 를 확인하는 장치만으로 막을 수 없었어요. 생성 결과의 0, [], = null 을 검토하고, 기본값으로 바뀌면 안 되는 속성에는 별도 처리를 했습니다. plan 요약의 ~ 1 만 보지 않고 속성 경로를 비교하는 명령도 만들었어요.

당시 CI 에서 자동 실행한 것은 import 건수 대조까지였습니다. 속성 경로 비교는 사람이 직접 실행해야 했고, 기대 목록의 관리 방식과 워크플로 통합은 남아 있었어요.
