이미 돌고 있는 리소스를 Terraform 관리 아래로 데려올 때는 import 블록을 씁니다. "이 주소는 저 실물이다"라고 코드에 한 줄 적어두면 다음 apply 가 그 실물을 state 에 등록해요. 한 번 등록되면 그 블록은 할 일이 끝납니다. 그 자리에서는 아무 일도 안 하니까 죽은 문장처럼 보이죠.

그런데 지우지 않으면 그 스택의 다음 PR 이 막힙니다. 잘못한 그 PR 이 아니라요. 며칠 뒤에, 완전히 무관한 작업을 들고 온 다음 PR 이 막혀요. 제가 실제로 본 것 중 제일 억울한 사례는 문서 파일 하나만 고친 PR 이 로드밸런서도 버킷도 건드리지 않았는데 plan 단계에서 통째로 막힌 것이었습니다.

이 실수를 여섯 번 했어요. 다섯 번은 이사가 몰려 있던 며칠 안에 났고, 여섯 번째는 그 뒤에 편입한 서비스에서 나왔습니다. 그리고 네 번째에 고친 것은 가드가 아니라 작업 지시서의 문장 한 줄이었어요. 이 글은 그 문장이 무엇을 고쳤다고 제가 믿었고, 그 믿음이 왜 틀렸는지에 대한 이야기입니다.

1. 왜 잘못한 PR 은 통과하고 다음 PR 이 막히나

가드 자체는 아주 단순합니다. 두 숫자를 대조해요.

A. 코드에 적힌 import 블록의 개수 (.tf 파일을 grep 해서 센다) B. plan 이 "이번에 가져오겠다"고 말한 건수 (plan JSON 의 importing) A != B -> 실패

이 가드가 왜 생겼는지부터 짚어야 뒤가 이해돼요. Terraform 은 import 를 plan JSON 에 actions: ["no-op"] 로 표시하고, 진짜 정보는 change.importing 이라는 옆자리에 담습니다. 그런데 파이프라인의 판정 로직 여섯 지점이 전부 no-op 을 "볼 것 없음"으로 건너뛰고 있었어요. 그래서 운영 중인 리소스가 state 로 들어오는 PR 이 PR 코멘트에 +0 ~0 -0 ±0 · 파괴적 변경 없음 으로 보였습니다. 머지해도 아무것도 안 옮겨지는 것처럼 보이는데, 실제로는 운영 리소스의 소유권이 옮겨오는 중이었죠. 11편의 "설정했다와 적용됐다는 다른 말이다"와 같은 가족입니다. 화면이 거짓말을 한 게 아니라, 화면이 그걸 보는 눈이 없었던 거예요.

여섯 지점을 통합하는 건 폭발 반경이 큰 작업이라 뒤로 미루고, 대신 비어 있는 창을 막는 단언 하나를 plan 워크플로에 끼웠습니다. 이게 전부예요.

- name: import 단언 run: | set -euo pipefail n=$(cat "$DIR"/*.tf 2>/dev/null | grep -cE '^[[:space:]]*import[[:space:]]*\{' || true) echo "코드의 import 블록: ${n}개" python3 scripts/plan-verdict.py "$DIR/plan.json" --import-blocks "$n" >/dev/null

여기서 이 가드의 좋은 성질 두 개를 먼저 인정하고 갈게요.

첫째, 평소에는 없는 것과 같습니다. import 블록이 0 개인 스택에서는 0 == 0 으로 무해하게 통과해요. 그리고 첫 import 블록이 들어오는 순간 자동으로 무장됩니다. 누가 켜주지 않아도요.

둘째, 어긋남의 원인이 사실상 하나뿐입니다. 이유는 Terraform 의 동작에 있어요. import 블록이 가리키는 주소가 이미 state 에 있으면 Terraform 은 그 블록을 에러 없이 건너뜁니다. plan 은 성공하고, 그 블록만 importing 에서 빠져요. 그러니 "코드 블록 수가 plan 의 import 건수보다 많다"는 부등식은 역할을 다한 블록이 남아 있다는 것과 사실상 같은 말입니다. 매번 우는 가드는 꺼지지만, 이 가드는 여섯 번 울고 여섯 번 다 진짜였어요.

이 두 번째 성질은 처음 쓸 때 "오탐이 구조적으로 안 난다"고 적어뒀는데, 15편을 쓴 뒤에 그 문장을 다시 보니 너무 셌어요. 15편에서 물어야 한다고 정한 질문이 "이 사고가 속한 클래스의 나머지는 무엇인가"였는데, 그걸 이 가드에 적용하면 반례가 하나 나옵니다.

🎯 이 가드가 오탐을 내는 조건
가드는 grep 으로 import { 로 시작하는 줄을 셉니다. 즉 블록의 개수를 세요. 그런데 Terraform 은 import 블록에 for_each 를 붙일 수 있고, 그러면 블록 하나가 여러 건의 import 를 만듭니다. 이 저장소가 고정해둔 Terraform 은 1.15 대라서 문법이 이미 열려 있어요.

블록 1 개가 import 5 건을 만들면 1 != 5 로 정상 작업이 실패합니다. 그러니까 이 가드가 무오탐인 근거는 구조가 아니라 이 저장소가 그 문법을 안 쓴다는 관례예요. 누군가 반복 편입을 for_each 로 쓰는 날, 이 가드는 옳은 PR 을 막습니다.

그런데 우는 자리가 원인에서 한 칸 떨어져 있다

문제는 시점이에요. 이미 state 에 들어간 리소스는 다음 plan 에서 더 이상 "가져온다"로 잡히지 않습니다. 등록이 끝났으니까 당연하죠. 그래서 이런 순서가 만들어집니다.

[ PR A ] import 블록 7 개를 쓰고 plan -> 7 건 잡힌다. 7 == 7 통과 ✅ apply. 7 개가 state 에 들어간다. 블록을 지우지 않고 머지한다. <-- 어긋남이 생기는 자리 [ PR B ] 전혀 다른 작업. 문서 한 줄만 고쳤다. plan -> import 는 0 건. 코드에는 블록이 7 개. 7 != 0 -> 이 스택의 모든 plan 이 실패 ❌ <-- 어긋남이 드러나는 자리

어긋남을 만든 PR 은 그것을 만드는 순간에는 완벽하게 옳습니다. 그 시점에 두 숫자는 정확히 같아요. 어긋남은 apply 가 성공한 뒤에, 그러니까 그 PR 이 이미 머지되고 CI 가 끝난 뒤에 비로소 생깁니다. 그리고 그걸 처음 밟는 사람은 그 스택을 다음에 건드리는 사람이에요. 자기가 뭘 잘못했는지 알 방법이 없는 사람이요.

남은 블록은 죽은 문장이 아니다

글 처음에 "죽은 문장처럼 보인다"고 썼는데, 정확히는 잠들어 있는 문장입니다. 이걸 알려준 건 이 가드가 아니라 훨씬 전의 다른 정리 작업이었어요.

알림 스택에 이미 state 에 들어간 구독의 import 블록이 남아 있었습니다. 지금은 건너뛰어지니 아무 일도 안 하죠. 그런데 누군가 콘솔에서 그 구독을 지우면 refresh 가 state 에서 그것을 잃고, 그 순간 잔여 블록이 되살아납니다. 이제는 실재하지 않는 대상을 가리키니 plan 이 통째로 실패해요. 그러면 plan 과 apply 와 드리프트 감시가 그 스택에서 전부 멈춥니다. 알림 경로가 끊어진 바로 그 순간에, 그것을 고칠 파이프라인도 함께 멈추는 거예요.

그러니 잔여 블록의 대가는 "다음 PR 이 불편해진다" 하나가 아닙니다. 실제로 청구된 것은 앞의 것이고, 구조적으로 열려 있는 것은 뒤의 것이에요.

그림 1. 가드는 정확히 울었다: 다만 원인에서 한 칸 떨어진 자리였다

2. 며칠 안에 다섯 번

가드를 넣은 날 오후에 벌써 처음 울었어요. 그건 접근 제어 스택이었습니다. 그리고 며칠 뒤 서비스 하나를 이사하면서 네 번 더 울렸어요. 매번 다른 리소스 종류였고, 매번 잘못한 PR 이 아니라 다음 작업이 걸렸어요.

서수를 먼저 정하고 갈게요. 이 글의 "몇 번째"는 전부 아래 표의 행 번호입니다. 저장소 커밋들은 서수를 다르게 셉니다. 스택마다 따로 세기도 하고, 서비스의 편입 단계 번호로 세기도 해요. 그래서 저장소 문장을 인용할 때는 그게 저장소의 셈이라는 걸 그 자리에서 밝히겠습니다. 그리고 여섯 번째는 이 표에 없습니다. 다른 서비스에서 일어났고, 그건 6 장의 주제예요.

남긴 블록 그것을 넣은 apply 막힌 "다음 작업" 가드가 뱉은 숫자 ---------------------------------------------------------------------------------------------- 1. 웹 방화벽 1 개 접근 제어 스택 편입 무관한 CI 변경 PR 1 개 vs 0 건 2. 로드밸런서 4 개 서비스 스택 1 단계 DB 클러스터 편입 PR 7 개 vs 3 건 3. DB 3 개 서비스 스택 2 단계 버킷 편입 PR 10 개 vs 7 건 4. 버킷 7 개 서비스 스택 3 단계 문서만 고친 PR 7 개 vs 0 건 5. dev 14 개 dev 스택 첫 apply 파일을 나누는 리팩터 PR 14 개 vs 0 건

두 번째와 세 번째를 보면 숫자가 왜 저렇게 이상한지 알 수 있어요. 로드밸런서 블록 4 개가 남은 상태에서 DB 편입 PR 이 새 블록 3 개를 들고 오면 코드에는 7 개인데 plan 은 3 건입니다. 그다음 버킷 PR 이 7 개를 들고 오면 코드 10 개에 plan 7 건이에요. 잔여 블록이 다음 PR 의 정상적인 숫자에 그대로 얹혀서 어긋남을 만듭니다. 그러니 화면의 숫자만 보면 "내가 쓴 블록 개수도 안 맞나?" 싶고 실제로 이 두 번은 로그를 뒤져서 원인을 찾았습니다.

가장 억울한 건 네 번째입니다. 그 PR 은 이사하면서 발견한 고아 리소스와 어긋남 목록을 문서에 정리한 것이 전부였어요. .tf 파일을 한 글자도 고치지 않았습니다. 그런데도 그 스택의 plan 이 실패했어요. 가드는 PR 의 diff 를 보는 게 아니라 그 스택의 현재 코드 전체를 보니까요.

다섯 번째가 특히 나쁘다: 정리 PR 이 사라졌다

표의 마지막 줄은 성질이 달라요. 이번엔 잊지 않았습니다. apply 직후에 블록을 지우는 커밋을 만들어서 정리 PR 까지 올렸어요. 그런데 그 PR 이 머지되지 않고 닫혔습니다. 그래서 블록 14 개가 기본 브랜치에 그대로 남았고, 43 분 뒤 다른 리팩터 PR 이 그걸 밟았습니다.

커밋 그래프에서 확인해보면 그 정리 커밋은 지금도 자기 브랜치에만 남아 있어요. 기본 브랜치의 조상이 아닙니다. 일은 다 해놨는데 도착하지 않은 겁니다.

여기서 교훈 하나가 나와요. 정리를 다음 PR 로 미루면 그 PR 은 유실될 수 있습니다. 그리고 이건 "PR 관리를 잘하자"로 끝날 문제가 아니라 진짜 트레이드오프예요.

⚖️ 정리를 어디에 담을 것인가
• 같은 PR 에 넣는다. 유실되지 않는다. 대신 리뷰어가 읽을 diff 가 지저분해진다. import 블록을 추가하는 줄과 지우는 줄이 한 diff 에 같이 있어서 리뷰어는 "결국 뭐가 남는 거지"를 머릿속으로 계산해야 한다. 그리고 애초에 블록을 지우려면 apply 가 이미 끝나 있어야 하니, apply 전에 리뷰받은 diff 와 최종 머지되는 diff 가 달라진다
• 다음 PR 로 나눈다. 각 PR 이 한 가지만 한다. 편입 PR 은 "가져오기", 정리 PR 은 "죽은 문장 치우기". 리뷰가 쉽고 되돌리기도 쉽다. 대신 그 PR 이 닫히거나 잊히면 잔여 블록이 그대로 남는다

저는 나누는 쪽을 계속 택했고 실제로 한 번 유실됐습니다. 그러니 나누는 게 틀렸다기보다, 나눌 때는 "그 PR 이 머지됐는지"를 확인하는 단계까지가 한 세트라는 뜻이에요. 계획을 세울 때 정리를 담을 자리를 정했다면 그 자리에 실제로 도착했는지도 봐야 계획이 끝납니다.

3. 잊는 이유가 매번 같았다

표의 네 번째를 밟은 날, 커밋 본문에 이렇게 적었어요. 저장소는 이걸 "세 번" 이라고 셉니다. 그 서비스 스택에서 잊은 횟수만 세니까요. 표의 첫 번째는 다른 스택 일이었고, 다섯 번째는 아직 오지 않았을 때예요.

세 번 잊었으니 스킬의 지시를 강하게 고쳤다. 잊는 이유가 매번 같기 때문이다. apply 가 끝나면 다음 리소스로 넘어가고 싶어진다.

이 문장이 이 글에서 제일 중요한 관찰입니다. 부주의가 아니라 작업 흐름의 구조거든요. 이사 작업의 한 단계는 이렇게 생겼어요.

1. 실물의 설정을 읽어 코드로 옮긴다 (지루하고 조심스럽다) 2. import 블록을 쓴다 (한 줄, 사실 확인) 3. plan 을 읽는다 (긴장한다. 여기서 사고가 난다) 4. 사람이 확인하고 apply 를 누른다 (제일 긴장한다) 5. apply 성공. 리소스가 코드 아래로 들어왔다 ★ 성취감이 여기서 터진다 6. 역할을 다한 import 블록을 지운다 <- 성취감이 0 인 단계

5 번에서 보상이 전부 지급됩니다. 운영 중인 실물이 이제 코드 아래로 들어왔고, plan 이 초록이고, 되돌릴 수 없는 것도 없어요. 이 순간 머릿속에 남는 문장은 "다음 리소스"입니다. 6 번은 이미 끝난 일의 뒤처리고 아무것도 만들어내지 않아요.

그리고 결정적인 게 하나 더 있어요. 6 번을 건너뛰어도 그 순간에는 아무 일도 안 일어납니다. 지금 열려 있는 PR 은 이미 통과했고, CI 는 초록이고, 화면 어디에도 빨간 줄이 없어요. 처벌이 다음 PR 로 미뤄져 있으니, 그 자리에서는 잘못한 신호가 전혀 없습니다. 잊을 조건이 완벽하게 갖춰진 셈이죠.

이게 저 혼자만의 게으름이 아니라는 근거가 하나 있어요. 이 규칙은 이사 훨씬 전부터 말로는 존재했습니다. 파이프라인 설계를 협의하면서 이미 이렇게 적혀 있었어요. "import 블록은 apply 성공 직후 지운다. 사람 기억에 맡기면 남으므로 기계로 강제한다." 알고 있었고, 문장으로 남겨뒀고, 기계로 강제하자고 스스로 적어놓고도 여섯 번 같은 자리에 걸렸습니다.

4. 문장으로 고쳤고, 그 판단은 절반만 옳았다

네 번째를 밟은 뒤에 무엇을 고쳤나. 가드가 아니라 작업 지시서였습니다. 정확히는 이 저장소의 "서비스 편입" 절차서인데, 세 단계에 걸쳐 이렇게 변했어요.

[1단계] 이사 시작 시점: 절차서에 그 단계가 아예 없었다 편입 절차 어디에도 "블록을 지운다" 가 없다. 협의 기록에만 있었고, 손이 보는 문서로는 옮겨지지 않았다. [2단계] 표의 두 번째를 밟은 뒤: 단계를 추가했다 제목 "apply 가 끝나면 그 import 블록을 지운다" 부제 "다음 PR 이 막힌다" [3단계] 표의 네 번째를 밟은 뒤: 시점을 못 박았다 제목 "apply 가 끝나면 **그 자리에서** import 블록을 지운다" 본문 "**stage=apply 성공을 확인한 직후, 다른 일을 시작하기 전에 지운다.**" "잊는 이유는 매번 같다. apply 가 끝나면 다음 리소스로 넘어가고 싶어진다."

2 단계와 3 단계의 차이가 작지 않아요. "apply 후에 지운다"는 언제든지입니다. 오늘 안에 지우면 후고, 내일 지워도 후고, 다음 주에 지워도 후예요. 그 문장은 순서를 말하지만 시점을 말하지 않습니다.

"apply 성공을 확인한 직후, 다른 일을 시작하기 전에"는 다릅니다. 그 사이에 끼어들 틈을 없앤 문장이에요. 위반했는지 아닌지가 스스로 판정 가능해집니다. 다른 일을 시작했으면 이미 위반이니까요. 그리고 이 문장은 3 장에서 본 그 구조를 정면으로 겨눕니다. 성취감이 터지는 5 번과 성취감 0 인 6 번 사이를 붙여서 6 번을 5 번의 일부로 만드는 겁니다.

가드에 들어간 변경은 다섯 줄이었다

같은 기간에 가드 쪽 코드도 손댔어요. 표의 세 번째를 밟은 날입니다. 전부 이만큼이에요.

print(f"::error::코드에 import 블록이 {args.import_blocks}개인데 " f"plan 의 import 는 {len(v['imports'])}건입니다.", file=sys.stderr) + if args.import_blocks > len(v["imports"]): + # 압도적으로 흔한 원인이다. 두 번 겪었다 (편입 2·3단계). + print("::error::apply 로 역할을 다한 import 블록이 남아 있을 수 있습니다. 판정은 한 글자도 안 바뀌었습니다. 규칙도, 임계도, 검사 범위도 그대로예요. 바뀐 건 에러 메시지가 원인과 조치를 말하게 된 것뿐입니다.

주석의 "편입 2·3단계"가 저장소의 셈이에요. 그 서비스의 편입 단계 번호이고, 표로 옮기면 두 번째와 세 번째입니다.

그리고 실제로 저 다섯 줄은 값을 했어요. 네 번째와 다섯 번째에는 로그 한 줄로 끝났습니다. 두 번째와 세 번째는 숫자만 보고 원인을 짐작하느라 CI 를 왕복했는데, 메시지가 들어간 뒤로는 실패 로그가 곧 조치 안내였어요. 다만 정확히 말하면 이건 재발을 줄인 게 아니라 재발의 비용을 줄인 것입니다. 여섯 번 중 세 번이 메시지가 들어간 뒤에 일어났으니까요.

왜 그 다섯 줄이 전부였나. 그때 제 추론은 이랬어요. 판정 규칙에는 늘릴 자리가 없다. 15편에서 저는 "사고 하나에 규칙 하나를 붙이면 막히는 건 정확히 겪은 만큼"이라고 썼고, 그때 처방은 규칙을 늘리는 것이었습니다. 검사 범위 밖에 남은 원인이 다섯 개나 있었으니까요. 그런데 이 가드는 상황이 반대입니다. 어긋남을 만드는 경로가 사실상 하나고 그 하나를 이미 정확히 잡고 있어요. 게다가 이 판정 스크립트는 lint 가 --selftest 를 돌려주는 네 스크립트 중 하나입니다. 15편에서 "자체 검사기가 넷인데 그중 어느 것에도 테스트가 없다"고 쓴 그 넷은 워크플로·태그·IAM 경계를 보는 다른 넷이고, 지금도 테스트가 없어요. 그러니까 이 저장소의 검사기는 자기검사가 있는 넷과 없는 넷으로 갈리는데, 이건 있는 쪽입니다. 여기에 판정 규칙을 더 붙일 자리는 정말 없었습니다.

그런데 "규칙을 늘릴 자리가 없다"와 "코드가 할 일이 없다"는 다른 말이다

여기가 제 추론이 미끄러진 지점입니다. 앞 문장은 참이고, 뒤 문장은 거짓이에요. 그리고 저는 앞 문장을 근거로 뒤 문장을 결론 삼아서 문장 한 줄로 이 일을 끝냈습니다.

가드의 한계를 세 줄로 적으면 이렇게 됩니다.

첫째, 탐지는 있고 예방은 없습니다. 블록이 남는 것 자체를 막는 장치는 하나도 없어요. 블록을 남긴 채로 머지하는 데는 아무 저항이 없습니다.

둘째, 탐지 시점이 한 PR 늦습니다. 가드는 어긋남을 만든 PR 을 통과시키고 다음 PR 에서 웁니다. 그러니까 이 가드는 잘못을 막는 장치가 아니라, 잘못이 이미 저장돼 있다는 걸 다음 사람에게 알려주는 장치예요.

셋째, 문장은 강제가 아니라 규약입니다. 준수 여부가 어디에도 기록되지 않고, 위반해도 그 자리에서 아무 일이 안 일어나요. 그러니까 3 장에서 진단한 그 구조를 문장은 하나도 바꾸지 못합니다. 시점을 못 박은 것은 사람이 스스로 판정할 근거를 준 것이고, 판정할 사람이 잊으면 판정도 안 일어납니다.

예방을 코드로 만들 수 있나. 생각해보면 만들 수 있어요. 후보가 셋 정도 됩니다.

A. apply 워크플로가 apply 성공 직후 그 디렉터리의 블록을 센다 0 이 아니면 Job Summary 에 경고를 찍는다 -> 가장 싸다. 사람이 지우게 하되 잊을 자리에서 알려준다 B. 같은 자리에서 정리 PR 을 자동으로 열어준다 블록을 지우고 주석으로 옮긴 diff 를 봇이 만든다 -> 유실 위험까지 없어진다. 대신 워크플로에 쓰기 권한이 필요하다 C. 블록에 "이 apply 로 소비됨" 표시를 강제하고 CI 가 대조한다 -> 가장 확실하고 가장 무겁다. 규약을 하나 더 만드는 일이다

당시에 안 한 이유는 이랬어요. A 는 결국 알림이라 지우는 건 여전히 사람이고 잊으면 그대로 남습니다. B 는 폭발 반경이 늘어납니다. apply 워크플로에 저장소 쓰기 권한을 주는 일인데, 이 시리즈에서 파이프라인 권한을 좁히려고 여러 번 고쳤으니(2편·6편) 그 방향과 정면으로 반대예요. C 는 지우는 일에 사람 판단이 섞여 있어서 봇에 온전히 맡기기 어렵습니다. 이 저장소의 관례는 블록을 지우되 내용을 주석으로 남기는 것인데, 어떤 실물이 어느 주소로 들어왔는지가 기록으로 남아야 하니까요. 실제로 한 번, 파일을 용도별로 나누면서 어떤 버킷의 import 기록이 그 버킷을 쓰지 않는 파일에 남게 됐습니다.

그런데 이 목록에 없는 후보가 하나 있었습니다. A 를 경고가 아니라 실패로 만드는 것이에요. 이 일을 다시 들여다보면서 제가 떠올린 게 그거였고 근거를 이렇게 적었습니다.

A'. apply 워크플로가 apply 성공 직후 그 디렉터리의 블록을 센다 0 이 아니면 그 잡을 실패시킨다 - 새 판정 규칙이 아니다. 같은 규칙을 다른 자리에서 재는 것이다 - 저장소 쓰기 권한이 필요 없다. B 의 폭발 반경 문제가 없다 - 주석을 어디에 둘지 봇이 안 정한다. C 의 사람 판단 문제가 없다 - apply 는 이미 끝났으니 실물은 안전하다. 실패하는 것은 "정리를 안 했다" 는 사실 하나뿐이다 - 우는 자리가 원인과 같은 자리다. 다음 사람이 아니라 내가 받는다

다섯 줄이 다 맞아 보였어요. A·B·C 를 기각한 세 이유 중 어디에도 걸리지 않으니까요. 알림이 아니라 강제고, 권한을 늘리지 않고, 사람 판단을 봇에 넘기지 않습니다.

그런데 A' 는 그대로는 성립하지 않는다

판정 자체가 성립하지 않습니다. apply 성공 직후의 코드에는 import 블록이 반드시 있어요. 방금 끝난 그 apply 가 바로 그 블록을 소비했으니까요. 그러니 "0 이 아니면 실패"는 조건이 아니라 상수입니다. 모든 편입 apply 가 예외 없이 실패해요.

이게 왜 치명적인가. 이 시리즈가 반복해서 경계한 것에 정면으로 걸리기 때문이에요. 17편 5장에 "매번 우는 가드는 꺼진 가드"라고 썼고, 같은 문장이 이 판정 스크립트의 주석에도 들어 있습니다. 제가 A' 를 붙이려던 자리가 하필 그 주석이 있는 파일이에요. A' 는 "같은 규칙을 다른 자리에서 재는 것"이 아니라 무조건 켜지는 빨간불입니다.

발동 시점을 미루면 되나 싶었어요. "apply 성공을 기록해두고, 그 스택의 다음 PR 이 열릴 때 이전 apply 의 블록이 남아 있으면 실패"로 옮기면 무조건 발동은 피해집니다. 그런데 그게 지금 있는 가드예요. 다음 PR 의 plan 에서 우는 것, 정확히 그겁니다. 한 바퀴 돌아서 제자리입니다.

거기서 왜 안 되는지가 보였습니다. 원인 자리에서는 판정이 축퇴합니다. "역할을 다한 블록"과 "코드에 있는 블록"이 그 순간에는 같은 집합이라서 둘을 가르는 정보가 그 자리에 없어요. 구분이 처음 생기는 시점은 그 스택의 다음 변경이고, 거기엔 이미 가드가 서 있습니다.

그러면 원인 자리에서 할 수 있는 일은 판정이 아니라 둘뿐이에요.

기계가 블록을 직접 지운다 -> B 다. 저장소 쓰기 권한을 값으로 낸다 어떤 apply 가 어떤 블록을 소비했는지 기록에 남긴다 -> C 다. 규약과 기록을 하나 더 만드는 값을 낸다

둘 다 제가 무겁다고 기각한 그 값입니다. 그러니 정정도 한 칸 물러나야 해요. 붙일 자리가 없었던 게 아니라, 값을 안 내고 자리를 옮기는 방법이 없었습니다. "규칙을 늘릴 자리가 없다"에서 "코드가 할 일이 없다"로 넘어간 게 잘못된 추론이라는 건 그대로예요. 코드가 할 일은 있습니다. 다만 그 일이 공짜가 아니었어요.

그리고 이게 이 문제의 알려진 오답이라는 근거가 있어요. 쓰고 나서 지우는 일을 사람에게 맡긴 선언은 대체로 남습니다. 폐기 예정으로 표시해둔 API, 켰다 끄고 안 걷어낸 임시 기능 플래그, 다 적용된 마이그레이션 스크립트가 다 같은 모양이에요. 그리고 이 문제를 오래 겪은 도구들은 전부 사람 손을 뺐습니다. 폐기 예정 표시는 컴파일러가 매번 경고하게 만들었고, 임시 플래그에는 만료일을 넣어 만료되면 빌드를 깨뜨리게 했고, 마이그레이션은 파일을 지우는 대신 적용 여부를 상태로 기록하는 쪽을 택했어요.

여기서 봐야 할 게 하나 더 있습니다. 셋 다 값을 냈어요. 만료일은 규약을 하나 더 만든 것이고, 적용 여부 기록은 상태를 하나 더 둔 것입니다. 제가 C 라고 부르며 무겁다고 기각한 게 정확히 그 값이에요. 그러니 결론을 이렇게 고쳐야 합니다. 처방이 코드 밖에 있었던 게 아니라, 제가 코드 밖에서 끝냈습니다. 예방 장치를 못 만든 게 아니라 만들 형태를 아직 못 찾은 것이고, 찾는 걸 멈춘 이유는 다음 장에 있어요.

💡 가드가 정확한데도 재발할 때 물어볼 것
• 이 가드가 놓치는 케이스가 있나? 없다면 판정 규칙을 늘리는 건 헛수고다
• 이 가드가 우는 자리와 원인이 생긴 자리가 같은가? 다르면 고칠 것은 규칙이 아니라 재는 위치다. 그리고 위치를 옮기는 것도 코드다
• 원인 자리에서 그 판정이 성립하나? 원인이 생긴 순간에 "잘못된 상태"와 "정상 상태"가 구분되지 않으면 그 자리의 판정은 무조건 발동한다. 그때는 판정 대신 기계가 직접 치우게 하거나 기록을 남기게 해야 하고, 둘 다 값을 낸다
• 실패 로그를 읽고 다음 행동을 알 수 있나? 이건 규칙과 무관하게 항상 값을 한다. 가드를 정확하게 만드는 일과 가드를 친절하게 만드는 일은 다른 작업이다

네 번째는 재발 비용을 줄이고, 재발 건수를 줄이는 건 두 번째와 세 번째예요. 그리고 두 번째의 답이 "다르다"일 때 "그럼 코드로 할 게 없다"로 넘어가면 안 됩니다. 그게 제가 한 실수예요.

5. 가드 이야기 세 유형: 이 글이 어디에 있나

이 시리즈가 가드 실패를 세 번 다뤘어요. 셋이 다 다른 유형이고, 처방이 서로 다릅니다. 여기서 정리해두면 좋겠어요.

가드가 못 본 것 (15편). 워크플로 파일을 통째로 무효로 만드는 조건이 최소 일곱 가지인데, 검사기는 둘만 봤어요. 그 둘은 하필 제가 겪은 사고 두 개였고요. 규칙은 정상 동작했고 그냥 범위 밖이었습니다. 처방은 규칙을 늘리는 것이고, 정확히는 클래스에 이름을 붙이고 원인 집합을 먼저 세는 것이었죠.

가드가 죽은 것 (10편). IAM 정책의 Deny 조건이 참조하는 태그 키와 프로바이더가 실제로 붙이는 태그 키가 어긋났어요. 그러면 그 Deny 는 에러 없이, 경고 없이, 영원히 안 걸립니다. 규칙은 존재하는데 발동하지 않는 상태고, 화면은 초록입니다. 처방은 규칙을 늘리는 게 아니라 규칙의 전제를 검사하는 정합성 검사였어요.

가드가 옳게 울렸는데 반복되는 것 (이 글). 규칙도 맞고 발동도 했습니다. 여섯 번 모두 정확히 울렸어요. 그런데도 여섯 번 반복됐습니다. 우는 자리가 원인에서 한 칸 떨어져 있기 때문입니다. 여기서는 판정 규칙을 늘려도 아무것도 안 고쳐져요. 고칠 것은 재는 위치입니다. 다만 4 장에서 본 대로, 이 사례에서 그 위치를 옮기려면 쓰기 권한이나 새 기록 중 하나를 값으로 내야 해요.

그림 2. 규칙을 늘려서 고쳐지는 건 첫 번째뿐이다

세 번째 유형의 처방이 사람의 작업 순서라고 쓰고 싶었는데, 그렇게 쓰면 안 됩니다. 그건 "결국 사람 문제였다"와 한 글자 차이고, 아무것도 안 하겠다는 말과 같으니까요. 정확히 쓰면 이렇게 돼요. 작업 순서를 고쳐야 하는 상황에서 코드가 할 일은, 판정 규칙을 늘리는 게 아니라 재는 위치를 원인 쪽으로 옮기는 것입니다. 그리고 그 위치가 판정이 성립하지 않는 자리라면 기계가 직접 치우게 하거나 무엇이 소비됐는지 기록에 남기게 해야 합니다. 어느 쪽이든 값을 내고, 그 값을 안 내겠다고 정하는 것까지가 결정이에요. 저는 그 결정을 안 하고 자리를 비워뒀습니다.

6. 작동했다고 믿었고, 다음 서비스에서 또 걸렸다

문장을 강화한 뒤로 편입을 여러 건 더 했습니다. 같은 서비스의 남은 단계들과, 그다음 이틀 동안 붙인 작은 스택 둘이요. 전부 깨끗했어요. 정리 커밋 이름들이 이렇게 생겼습니다.

chore: 역할을 다한 EC2 import 블록을 치운다 chore: 역할을 다한 VPN import 블록을 지운다 chore: 역할을 다한 import 블록 9 개를 내린다

커밋 본문도 전부 같은 모양이에요. "남겨두면 import 단언이 어긋나 이 스택의 모든 plan 을 막는다." 막힌 뒤에 쓴 문장이 아니라 막히기 전에 쓴 문장입니다. apply 와 정리 사이도 짧아요. 대부분 삼십 분 안쪽입니다.

그래서 이 장은 원래 이렇게 끝나 있었습니다. "문장은 작동했다. 표의 다섯 번째는 잊음이 아니라 유실이었으니, 문장이 못 겨눈 것은 유실 하나뿐이다."

그 결론은 반증됐습니다. 나흘 뒤, 그다음에 편입한 서비스에서 같은 일이 또 일어났어요.

코드에 import 블록이 5개인데 plan 의 import 는 0건입니다.

이번에도 문서만 고친 PR 이 막혔습니다. README 를 쓴 PR 이었고 .tf 는 한 글자도 안 건드렸어요. 표의 네 번째와 완전히 같은 모양이죠. 그리고 저장소 커밋 본문이 그 사건을 이렇게 적어뒀습니다.

앞 서비스의 README 가 "세 번 잊었고 세 번 다 다음 PR 이 막혔다" 고 적어둔 함정이고 여기서 네 번째로 걸렸다.

저장소의 "네 번째"는 앞 서비스에서 잊은 세 번에 이걸 더한 셈이에요. 표로 세면 여섯 번째입니다. 어느 쪽으로 세든 성질은 같아요. 유실이 아니라 순수한 잊음이고, 문장을 강화한 뒤에 일어났습니다.

그러니 "문장은 잊음을 겨눴고 유실만 못 겨눴다"는 성립하지 않습니다. 문장은 겨눈 것도 못 막았어요. 4 장에 "그 판단은 절반만 옳았다"고 썼는데, 이 사건을 넣으면 그 문장이 약해지는 게 아니라 세집니다. 절반도 아니었던 거예요.

그럼 저는 무엇을 보고 작동했다고 판단했나

깨끗했던 그 여러 건에는 공통 조건이 하나 있었습니다. 전부 방금 밟아서 기억이 살아 있는 상태에서 한 것이었어요. 같은 서비스의 남은 단계들은 세 번 연속으로 막힌 그날 저녁에 이어서 한 것이고, 작은 스택 둘은 그 이틀 뒤였습니다. 커밋 본문이 저장소 관례를 인용하는 대신 "앞에서 세 번 막혔다"를 인용하고 있어요.

그리고 서비스가 바뀌자 그 조건이 사라졌습니다. 새 서비스는 편입 단계가 일곱 개였고, 실물을 처음 데려온 단계에서 바로 걸렸습니다. 그러니 제가 "그 뒤로 안 막혔다"로 본 것은 처방의 성질이 아니라 관찰 범위가 기억의 유효 기간보다 짧았다는 사실이었습니다.

걸린 뒤에 그 서비스의 남은 단계들은 다시 전부 깨끗했어요. 그런데 그걸 만든 것도 문장이 아닙니다. 두 번째 정리 커밋의 본문이 이렇게 적혀 있어요.

앞 단계에서 한 번 걸렸던 것이라 이번에는 apply 직후 걷어낸다.

근거가 절차서가 아니라 두 시간 전에 밟았다는 기억입니다. 같은 경로가 한 번 더 돈 거예요. 앞 서비스에서 세 번 밟고 나머지가 깨끗해졌고, 새 서비스에서 한 번 밟고 나머지가 깨끗해졌습니다. 재발을 막은 것은 매번 문장이 아니라 방금 밟았다는 기억이었습니다.

그리고 손으로 지우는 일에 새 위험도 생겼어요. 주석 구분선을 뒤로 찾으며 블록을 잘라내던 중에 import 블록과 함께 리소스 블록까지 잘라낸 일이 실제로 있었습니다. 그래서 그다음부터는 잘라내기 전후로 리소스 블록 수가 같은지 세는 단언을 붙이고 있어요. 그 단언도 손으로 붙입니다. 사람에게 맡긴 정리 작업이 정리 작업을 검사할 일거리를 또 사람에게 만들어준 셈이죠.

그러니 이 장의 답은 하나입니다. 문장은 재발을 막지 못했습니다. 4 장의 A' 를 만들지 않은 것이 게으름이었다면, 만들 필요가 없다고 믿은 것은 표본 몇 개짜리 판단이었어요. 그리고 그 표본은 편입할 서비스가 하나 늘자마자 반례를 냈습니다.

그림 3. 관찰 범위가 기억의 유효 기간보다 짧으면 처방이 작동한 것처럼 보인다
✍️ 오늘의 요약
가드가 어긋남을 만든 PR 을 통과시키고 다음 사람 앞에서 우는 구조면 판정 규칙을 늘려도 재발한다. import 블록 단언은 여섯 번 모두 정확히 울렸다. 어긋남을 만드는 PR 은 그 순간 완벽하게 옳고, 어긋남은 apply 가 끝난 뒤에 생기고, 그걸 밟는 사람은 며칠 뒤 무관한 작업을 들고 온 다음 사람이다. 고칠 것은 규칙이 아니라 재는 위치다.

그래서 그때 고른 처방은 코드가 아니라 문장이었다. "apply 후에 지운다"를 "apply 성공을 확인한 직후, 다른 일을 시작하기 전에 지운다"로 바꾼 것이 네 번 밟은 뒤의 유일한 수리였고, 가드에 들어간 변경은 에러 메시지 다섯 줄뿐이었다. 그 다섯 줄은 재발 건수가 아니라 재발 비용을 줄였다. 그리고 문장은 재발을 막지 못했다. 강화한 나흘 뒤 다음 서비스에서 또 잊었고, 또 문서만 고친 PR 이 막혔다.

"판정 규칙을 늘릴 자리가 없다"에서 "코드가 할 일이 없다"로 넘어간 것은 잘못된 추론이었다. 다만 그 자리를 채우는 일도 공짜가 아니다. apply 성공 직후에 잔여 블록을 세어 실패시키는 것은 성립하지 않는다. 그 순간의 코드에는 방금 소비된 블록이 반드시 있어서 모든 편입 apply 가 실패하고, 그건 이 시리즈가 경계해온 "매번 우는 가드"다. 원인 자리에서는 "역할을 다한 블록"과 "코드에 있는 블록"이 같은 집합이라 판정이 축퇴한다. 그 자리에 설 수 있는 것은 기계가 직접 지우는 것과 어떤 apply 가 무엇을 소비했는지 기록에 남기는 것뿐이고, 둘 다 권한이나 규약을 값으로 낸다.

쓰고 나서 지우는 일을 사람에게 맡긴 선언은 대체로 남는다. 폐기 예정 표시, 임시 기능 플래그, 다 적용된 마이그레이션이 다 같은 모양이고, 이 문제를 오래 겪은 도구들은 전부 사람 손을 빼는 대신 그 값을 냈다. 그러니 처방이 문장으로 끝나면 그건 처방이 안 끝난 것이다. 그리고 문장이 작동하는 것처럼 보인다면, 먼저 내가 본 표본이 몇 개인지 세어야 한다.
