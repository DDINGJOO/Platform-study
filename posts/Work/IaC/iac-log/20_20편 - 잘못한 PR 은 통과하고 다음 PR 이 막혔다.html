20편. apply 후 남은 import 블록이 다음 PR을 막는 이유 ← 지금 이 글

문서 파일 하나만 고친 PR이 plan 단계에서 막혔어요. 로드밸런서도 버킷도 건드리지 않았는데, 이전 PR에서 남긴 import 블록이 원인이었습니다. 이 블록은 운영 중인 리소스를 Terraform의 state, 즉 관리 상태에 등록할 때 써요. 등록할 리소스의 주소와 실제 대상을 적어두면 다음 apply가 state에 등록합니다.

등록이 끝난 블록을 지우지 않으면 이 저장소의 import 개수 가드가 다음 PR을 차단해요. 편입 PR의 plan에서는 개수가 맞지만, apply가 끝난 뒤에는 코드에 남은 블록 수와 새로 import할 건수가 달라지기 때문입니다. 그래서 며칠 뒤 무관한 작업을 하던 사람이 실패를 확인하게 됐어요.

이 문제가 여섯 번 생겼어요. 다섯 번은 리소스 편입이 몰려 있던 며칠 안에, 여섯 번째는 그 뒤에 편입한 서비스에서 일어났습니다. 네 번째에는 작업 지시서에 블록을 지울 시점을 더 구체적으로 적었어요. 한동안 정리가 잘돼 효과가 있다고 판단했지만, 다음 서비스에서 다시 블록을 남겼습니다.

1. import 블록 수가 다음 plan에서 달라지는 이유

가드는 코드에 적힌 import 블록 수와 plan에 나타난 import 건수를 대조해요.

A. 코드에 적힌 import 블록의 개수 (.tf 파일을 grep 해서 센다) B. plan 이 "이번에 가져오겠다"고 말한 건수 (plan JSON 의 importing) A != B -> 실패

처음 이 가드를 넣은 이유는 PR 코멘트에서 import를 구분하지 못했기 때문이에요. Terraform은 import를 plan JSON에 actions: ["no-op"]로 표시하고, import 정보는 change.importing에 담습니다. 파이프라인의 판정 로직 여섯 지점은 모두 no-op을 변경 없음으로 보고 건너뛰었어요. 그래서 운영 중인 리소스를 state에 등록하는 PR도 코멘트에는 +0 ~0 -0 ±0 · 파괴적 변경 없음으로 표시됐습니다. 실제로는 Terraform 관리 대상으로 편입하는데도 요약에서는 그 사실을 알 수 없었어요. 11편에서 설정 여부와 적용 여부를 구분했던 것처럼, 여기서도 plan 정보와 화면의 요약을 구분해야 했습니다.

여섯 지점의 판정 로직을 통합하는 작업은 영향 범위가 커서 뒤로 미뤘어요. 대신 plan 워크플로에 import 개수를 확인하는 단언을 추가했습니다.

- name: import 단언 run: | set -euo pipefail n=$(cat "$DIR"/*.tf 2>/dev/null | grep -cE '^[[:space:]]*import[[:space:]]*\{' || true) echo "코드의 import 블록: ${n}개" python3 scripts/plan-verdict.py "$DIR/plan.json" --import-blocks "$n" >/dev/null

기존 작업에 미치는 영향과 실제 실패 원인은 다음과 같았어요.

import 블록이 0개인 스택은 0 == 0으로 통과해요. 첫 import 블록을 추가하면 별도 설정 없이 그 블록부터 검사합니다.

import 블록이 가리키는 주소가 이미 state에 있으면 Terraform은 그 블록을 에러 없이 건너뛰어요. plan은 성공하지만 해당 블록은 importing에 나타나지 않습니다. 그래서 코드의 블록 수가 plan의 import 건수보다 많을 때 잔여 블록을 의심할 수 있었어요. 실제로 확인한 여섯 번은 모두 등록을 마친 블록이 남아 있던 경우였습니다.

처음에는 이를 두고 오탐이 구조적으로 나지 않는다고 적었어요. 하지만 15편에서처럼 같은 문제에 속하는 다른 조건까지 살펴보면, 정상 작업도 실패시킬 수 있는 경우가 있습니다.

⚠️ 블록 수와 import 건수가 달라지는 조건
가드는 grep으로 import {로 시작하는 줄을 세요. 그런데 Terraform의 import 블록에 for_each를 붙이면 블록 하나가 여러 건의 import를 만들 수 있습니다. 이 저장소가 고정한 Terraform은 1.15대여서 이 문법을 사용할 수 있어요.

블록 1개가 import 5건을 만들면 1 != 5로 정상 작업도 실패합니다. 당시 저장소에서는 for_each를 쓰지 않았기 때문에 여섯 번 모두 잔여 블록을 찾았어요. 가드가 정확히 동작한 범위는 이 관례 안으로 한정해야 합니다.

불일치는 다음 PR에서 드러난다

다만 검사가 실패하는 시점은 블록을 남긴 직후가 아니에요. 이미 state에 등록한 리소스는 다음 plan에서 import 건수에 포함되지 않으므로, 다음 순서로 문제가 드러납니다.

[ PR A ] import 블록 7 개를 쓰고 plan -> 7 건 잡힌다. 7 == 7 통과 ✅ apply. 7 개가 state 에 들어간다. 블록을 지우지 않고 머지한다. <-- 어긋남이 생기는 자리 [ PR B ] 전혀 다른 작업. 문서 한 줄만 고쳤다. plan -> import 는 0 건. 코드에는 블록이 7 개. 7 != 0 -> 이 스택의 모든 plan 이 실패 ❌ <-- 어긋남이 드러나는 자리

편입 PR의 plan을 실행할 때는 두 숫자가 정확히 같아요. apply가 성공하고 CI가 끝난 뒤에도 블록을 남겨두면, 그 스택의 다음 plan에서 개수가 달라집니다. 다음 작업자는 자신의 변경과 관계없이 실패하게 되므로 이전 PR의 정리 여부까지 확인해야 해요.

남은 블록이 다시 import를 시도할 수도 있다

이미 등록한 import 블록이 이후에도 영향을 줄 수 있다는 점은 더 앞선 정리 작업에서도 확인했어요.

알림 스택에는 state에 등록을 마친 구독의 import 블록이 남아 있었습니다. 이때 Terraform은 블록을 건너뛰어요. 하지만 누군가 콘솔에서 구독을 지워 refresh가 state에서도 그 구독을 제거하면, 잔여 블록이 다시 import를 시도합니다. 실재하지 않는 대상을 가리키므로 plan이 실패하고, 그 스택의 plan·apply·드리프트 감시도 진행할 수 없어요. 알림 경로를 복구할 때 파이프라인부터 정리해야 하는 상황이 생길 수 있습니다.

이번에 실제로 겪은 것은 다음 PR의 차단이었어요. 외부에서 리소스를 삭제했을 때 import가 다시 시도되는 문제는 잔여 블록이 만들 수 있는 별도의 위험입니다.

그림 1. 편입 PR의 plan은 통과하고 다음 PR에서 잔여 블록을 탐지했다

2. 며칠 안에 다섯 번

가드를 넣은 날 오후에 접근 제어 스택에서 첫 실패가 났어요. 며칠 뒤 서비스 하나를 편입하면서 네 번 더 실패했습니다. 리소스 종류는 달랐지만, 모두 블록을 추가한 PR 이후의 작업에서 발견됐어요.

아래 표는 처음 다섯 번을 발생 순서대로 정리한 것이에요. 본문의 서수도 이 표를 기준으로 합니다. 저장소 커밋에는 스택별 횟수나 서비스 편입 단계 번호가 쓰여 있어, 인용할 때는 따로 구분할게요. 다른 서비스에서 생긴 여섯 번째 사례는 6장에서 다룹니다.

남긴 블록 그것을 넣은 apply 막힌 "다음 작업" 가드가 뱉은 숫자 ---------------------------------------------------------------------------------------------- 1. 웹 방화벽 1 개 접근 제어 스택 편입 무관한 CI 변경 PR 1 개 vs 0 건 2. 로드밸런서 4 개 서비스 스택 1 단계 DB 클러스터 편입 PR 7 개 vs 3 건 3. DB 3 개 서비스 스택 2 단계 버킷 편입 PR 10 개 vs 7 건 4. 버킷 7 개 서비스 스택 3 단계 문서만 고친 PR 7 개 vs 0 건 5. dev 14 개 dev 스택 첫 apply 파일을 나누는 리팩터 PR 14 개 vs 0 건

두 번째에는 로드밸런서 블록 4개가 남은 상태에서 DB 편입 PR이 새 블록 3개를 추가했어요. 코드에는 7개지만 plan에는 3건만 나타납니다. 세 번째에는 버킷 PR이 7개를 추가해 코드 10개, plan 7건이 됐어요. 잔여 블록 수만큼 차이가 나지만, 실패 로그의 숫자만으로는 이번 PR의 블록이 잘못됐는지 구분하기 어려웠습니다. 이 두 번은 로그를 더 찾아 원인을 확인했어요.

네 번째 PR은 편입 중 발견한 고아 리소스와 설정 불일치 목록을 문서에 정리한 것이었어요. .tf 파일은 고치지 않았는데도 plan이 실패했습니다. 가드는 PR의 diff가 아니라 그 스택의 현재 코드 전체를 검사하기 때문이에요.

다섯 번째는 정리 PR이 머지되지 않았다

다섯 번째는 정리를 잊은 경우와 달랐어요. apply 직후 블록을 지우는 커밋을 만들고 정리 PR까지 올렸지만, PR이 머지되지 않고 닫혔습니다. 블록 14개가 기본 브랜치에 남았고, 43분 뒤 다른 리팩터 PR의 plan이 실패했어요.

커밋 그래프에서도 정리 커밋은 자기 브랜치에만 있고 기본 브랜치에는 포함되지 않았어요. 정리 코드를 작성하고 PR을 올리는 것만으로는 기본 브랜치의 잔여 블록이 없어지지 않았습니다.

정리를 별도 PR로 나누면 리뷰는 쉬워지지만, 머지까지 확인하지 않으면 작업이 반영되지 않을 수 있어요. 같은 PR에서 정리하는 방식과 각각의 부담을 비교해야 했습니다.

⚖️ 정리를 같은 PR에 담을지 나눌지
• 같은 PR에서 정리해요. 별도 정리 PR이 닫히는 문제는 피할 수 있지만, apply 전에 리뷰한 diff와 정리 후 최종 머지할 diff가 달라집니다. import 블록 추가와 삭제 과정도 함께 확인해야 해요.
• 다음 PR로 나눠요. 편입과 정리의 목적이 분명해 리뷰하거나 되돌리기 쉬워요. 대신 정리 PR을 머지하지 않으면 잔여 블록이 남습니다.

저는 별도 PR로 나눴고, 실제로 한 번은 정리가 기본 브랜치에 반영되지 않았어요. 이 방식을 쓰려면 PR을 올린 뒤 머지됐는지 확인하는 단계까지 필요했습니다.

3. apply 성공 직후에는 정리 누락을 알 수 없었다

표의 네 번째 사례를 처리한 날에는 커밋 본문에 아래 내용을 적었어요. 저장소가 세 번이라고 센 것은 그 서비스 스택에서 잊은 횟수입니다. 표의 첫 번째는 다른 스택에서 생겼고, 다섯 번째는 아직 일어나기 전이었어요.

세 번 잊었으니 스킬의 지시를 강하게 고쳤다. 잊는 이유가 매번 같기 때문이다. apply 가 끝나면 다음 리소스로 넘어가고 싶어진다.

apply가 끝나면 다음 리소스로 넘어가고 싶어진다는 내용이 반복됐어요. 블록 삭제를 빠뜨리는 지점을 살펴보면 작업 순서와도 관련이 있었습니다.

1. 실물의 설정을 읽어 코드로 옮긴다 (지루하고 조심스럽다) 2. import 블록을 쓴다 (한 줄, 사실 확인) 3. plan 을 읽는다 (긴장한다. 여기서 사고가 난다) 4. 사람이 확인하고 apply 를 누른다 (제일 긴장한다) 5. apply 성공. 리소스가 코드 아래로 들어왔다 ★ 성취감이 여기서 터진다 6. 역할을 다한 import 블록을 지운다 <- 성취감이 0 인 단계

5번에서 리소스 편입이 끝나면 주된 작업을 마쳤다고 느끼고 다음 리소스로 넘어갔어요. 반면 6번의 블록 삭제는 새 리소스를 등록하는 일이 아니어서 뒤로 미루기 쉬웠습니다.

6번을 건너뛰어도 그 순간에는 CI가 실패하지 않아요. 열려 있는 PR의 검사는 이미 통과한 상태입니다. 다음 plan이 실행돼야 잔여 블록이 드러나므로, apply 직후에는 정리가 빠졌다는 신호가 없었어요.

이 규칙을 몰랐던 것은 아니에요. 편입 작업 전 파이프라인 설계 협의에도 "import 블록은 apply 성공 직후 지운다. 사람 기억에 맡기면 남으므로 기계로 강제한다"고 적혀 있었습니다. 하지만 실제 절차에서 정리를 완료하게 만드는 장치까지 연결하지 못했고, 같은 문제가 여섯 번 생겼어요.

4. 절차서와 에러 메시지를 고친 뒤에도 남은 문제

네 번째 사례를 처리한 뒤에는 저장소의 서비스 편입 절차서를 고쳤어요. 절차서는 다음 세 단계를 거쳐 바뀌었습니다.

[1단계] 이사 시작 시점: 절차서에 그 단계가 아예 없었다 편입 절차 어디에도 "블록을 지운다" 가 없다. 협의 기록에만 있었고, 손이 보는 문서로는 옮겨지지 않았다. [2단계] 표의 두 번째를 밟은 뒤: 단계를 추가했다 제목 "apply 가 끝나면 그 import 블록을 지운다" 부제 "다음 PR 이 막힌다" [3단계] 표의 네 번째를 밟은 뒤: 시점을 못 박았다 제목 "apply 가 끝나면 **그 자리에서** import 블록을 지운다" 본문 "**stage=apply 성공을 확인한 직후, 다른 일을 시작하기 전에 지운다.**" "잊는 이유는 매번 같다. apply 가 끝나면 다음 리소스로 넘어가고 싶어진다."

2단계의 "apply 후에 지운다"는 작업 순서만 정해요. 그날 지울지, 다음 주에 지울지는 정하지 않습니다. 그래서 정리를 미루더라도 문장 자체를 어겼는지 판단하기 어려웠어요.

3단계에는 "apply 성공을 확인한 직후, 다른 일을 시작하기 전에"라고 적었어요. 다른 작업을 시작하기 전에 블록을 지워야 한다는 기준을 둔 것입니다. 3장의 6번 정리를 5번 apply 완료 확인에 이어서 하도록 순서를 더 구체적으로 정했어요.

가드에 들어간 변경은 다섯 줄이었다

가드 코드에도 변경이 있었어요. 표의 세 번째 사례를 처리한 날 에러 메시지 다섯 줄을 추가했습니다.

판정 규칙과 임계값, 검사 범위는 그대로예요. 에러 메시지에 잔여 블록이 원인일 수 있다는 설명과 삭제 방법을 추가한 변경입니다.

코드 주석의 "편입 2·3단계"는 저장소에서 쓰던 서비스 편입 단계 번호예요. 이 글의 표에서는 두 번째와 세 번째에 해당합니다.

네 번째와 다섯 번째에는 메시지 한 줄을 보고 조치를 알 수 있었어요. 두 번째와 세 번째처럼 숫자를 보고 원인을 찾느라 CI 로그를 여러 번 확인할 필요가 줄었습니다. 다만 여섯 번 중 세 번은 메시지를 추가한 뒤에 일어났어요. 에러 메시지는 원인 파악을 도왔지만 재발을 막지는 못했습니다.

당시에는 잔여 블록을 이미 판별하니 판정 규칙을 더할 필요가 없다고 판단했어요. 검사 범위 밖의 원인이 다섯 개 남았던 15편과는 상황이 달랐습니다. 이 판정 스크립트는 lint가 --selftest를 실행하는 네 스크립트 중 하나이기도 해요. 15편에서 테스트가 없다고 쓴 네 검사기는 워크플로·태그·IAM 경계를 검사하는 별도 스크립트들이었습니다. 두 집합을 구분해야 하지만, 자기검사가 있다는 이유만으로 정리 누락을 예방할 수 있는 것은 아니었어요.

판정이 정확해도 예방 장치는 따로 필요하다

저는 판정 규칙에 변경이 필요 없다는 판단을 코드로 더 할 일이 없다는 결론으로 이어갔어요. 그래서 절차서 수정으로 대응을 마쳤습니다. 하지만 판정의 정확성과 정리 누락의 예방은 따로 살펴봐야 했어요.

당시 남은 한계는 세 가지였어요.

잔여 블록을 탐지할 수는 있지만, 블록을 남긴 채 머지하는 것을 막지는 못했어요.

실패도 한 PR 늦게 드러났어요. 편입 PR은 통과하고 다음 PR이 실패하므로, 원인을 만든 작업자에게 바로 정리를 요구할 수 없었습니다.

절차서는 사람이 따라야 하는 규약이었어요. 준수 여부를 기록하거나 위반 직후 실패시키지는 않았습니다. 지울 시점을 명확히 해도 작업자가 정리를 잊으면 다음 PR까지 발견하지 못하는 구조는 그대로였어요.

예방을 돕는 코드 변경으로는 다음 세 가지를 검토했어요.

A. apply 워크플로가 apply 성공 직후 그 디렉터리의 블록을 센다 0 이 아니면 Job Summary 에 경고를 찍는다 -> 가장 싸다. 사람이 지우게 하되 잊을 자리에서 알려준다 B. 같은 자리에서 정리 PR 을 자동으로 열어준다 블록을 지우고 주석으로 옮긴 diff 를 봇이 만든다 -> 유실 위험까지 없어진다. 대신 워크플로에 쓰기 권한이 필요하다 C. 블록에 "이 apply 로 소비됨" 표시를 강제하고 CI 가 대조한다 -> 가장 확실하고 가장 무겁다. 규약을 하나 더 만드는 일이다

A는 경고를 보여줘도 삭제를 사람이 해야 하므로 블록이 남을 수 있어요. B는 apply 워크플로에 저장소 쓰기 권한이 필요합니다. 2편·6편에서 파이프라인 권한을 좁혀온 방향과도 함께 검토해야 했어요. C는 블록을 지울 때 사람 판단이 필요하다는 점이 부담이었습니다. 이 저장소는 어떤 리소스를 어느 주소로 편입했는지 알 수 있도록 블록 내용을 주석으로 남겨요. 실제로 파일을 용도별로 나누는 과정에서 버킷의 import 기록이 그 버킷을 쓰지 않는 파일에 남은 적도 있었습니다.

이후 A의 경고를 실패로 바꾸는 안도 생각했어요. apply가 끝난 자리에서 강제하면 다음 작업까지 정리가 미뤄지지 않을 거라고 보고, 다음과 같이 적었습니다.

A'. apply 워크플로가 apply 성공 직후 그 디렉터리의 블록을 센다 0 이 아니면 그 잡을 실패시킨다 - 새 판정 규칙이 아니다. 같은 규칙을 다른 자리에서 재는 것이다 - 저장소 쓰기 권한이 필요 없다. B 의 폭발 반경 문제가 없다 - 주석을 어디에 둘지 봇이 안 정한다. C 의 사람 판단 문제가 없다 - apply 는 이미 끝났으니 실물은 안전하다. 실패하는 것은 "정리를 안 했다" 는 사실 하나뿐이다 - 우는 자리가 원인과 같은 자리다. 다음 사람이 아니라 내가 받는다

처음에는 기존 후보들의 부담을 피할 수 있다고 봤어요. 저장소 쓰기 권한을 늘리지 않고, 주석을 둘 위치도 봇이 정하지 않으면서 작업자에게 정리를 요구할 수 있다고 생각했습니다.

apply 직후 블록 수를 검사하면 항상 실패한다

하지만 apply 성공 직후의 코드를 그대로 검사하면 방금 사용한 import 블록이 여전히 있어요. 이 시점에 "0이 아니면 실패"를 적용하면 import 블록으로 편입한 apply가 모두 실패하게 됩니다. 정리를 누락한 작업만 구분할 수 없는 조건이에요.

17편 5장과 이 판정 스크립트의 주석에는 매번 실패하는 가드는 쓰이지 않게 된다는 취지의 문장이 있어요. A'도 같은 문제를 만들었습니다. 정리 누락 여부와 관계없이 실패하므로, 실패한 작업을 구분하는 데 도움이 되지 않아요.

실행 시점을 다음 PR로 미루면 항상 실패하는 문제는 피할 수 있어요. 하지만 이전 apply의 블록이 남았는지 다음 PR의 plan에서 확인하는 것은 현재 가드가 하는 일입니다. 탐지 시점을 앞당기려던 목적은 이루지 못해요.

apply 직후의 블록 수만으로는 사용을 마친 블록과 아직 정리 중인 블록을 구분할 정보가 없었어요. 다음 변경에서 불일치를 확인할 수 있을 때는 이미 기존 가드가 검사하고 있었습니다.

검토한 후보 중 apply 직후에 정리를 진행하게 만들려면 다음 두 방식이 남았어요.

기계가 블록을 직접 지운다 -> B 다. 저장소 쓰기 권한을 값으로 낸다 어떤 apply 가 어떤 블록을 소비했는지 기록에 남긴다 -> C 다. 규약과 기록을 하나 더 만드는 값을 낸다

두 방식 모두 앞서 부담 때문에 채택하지 않은 안이었어요. 자동 삭제에는 쓰기 권한이, 적용 여부 기록에는 별도의 규약과 상태 관리가 필요합니다. 코드로 할 일이 없었던 것은 아니지만, 검사 시점만 바꾸는 작은 변경으로 해결할 수 있는 문제도 아니었습니다.

폐기 예정 API의 경고, 임시 기능 플래그의 만료일 검사, 마이그레이션의 적용 여부 기록도 정리 시점을 놓치는 문제와 관련이 있어요. 사람이 정리할 때까지 기다리는 대신 도구가 경고하거나 적용 상태를 관리하는 방식으로 비교할 수 있습니다.

이런 방식도 만료일 규약이나 적용 상태처럼 관리할 정보를 추가해야 해요. C를 검토하면서 부담으로 본 부분과 같습니다. 이 사례에서는 예방 장치의 형태를 정하지 못한 채 절차서 수정으로 대응을 마쳤고, 뒤이은 몇 건에서 문제가 없다는 이유로 효과가 있다고 판단했어요.

• 검사에서 놓치는 조건이 있는지 확인해요. 현재 문제를 이미 판별한다면 같은 판정 규칙을 추가해도 정리 누락은 줄지 않습니다.

• 실패 로그가 조치를 설명하는지 확인해요. 원인과 삭제할 대상을 안내하면 재발 시 조사 부담을 줄일 수 있어요. 이번에 추가한 메시지가 한 일도 여기에 해당합니다.

5. 검사 범위, 조건 불일치, 탐지 시점을 구분하기

이 시리즈에서 다룬 세 사례는 실패한 이유가 달랐어요. 필요한 변경도 구분해서 봐야 했습니다.

검사 범위가 부족했던 경우(15편). 워크플로 파일을 무효로 만드는 조건이 최소 일곱 가지였지만 검사기는 제가 겪은 둘만 확인했어요. 기존 규칙은 동작했으나 다른 원인은 범위 밖에 있었습니다. 같은 유형의 원인을 먼저 정리하고 검사 범위를 늘려야 했어요.

조건이 맞지 않아 발동하지 않았던 경우(10편). IAM 정책의 Deny 조건이 참조하는 태그 키와 프로바이더가 붙이는 키가 달랐어요. 그 상태에서는 오류나 경고 없이 조건이 성립하지 않았습니다. 규칙을 추가하기에 앞서 조건에 쓰는 값이 서로 맞는지 검사해야 했어요.

탐지가 늦어 재발했던 경우(이 글). 여섯 번 모두 잔여 블록을 정확히 탐지했지만 다음 PR에서 실패했어요. 같은 판정 규칙을 더해도 블록 삭제를 빠뜨리는 과정은 바뀌지 않습니다. 4장에서 검토했듯 apply 직후의 정리를 자동화하거나 적용 기록을 남기려면 쓰기 권한 또는 별도의 상태 관리가 필요했어요.

그림 2. 범위를 넓힐지, 조건을 확인할지, 탐지 시점을 바꿀지 구분해야 한다

세 번째 사례에서 절차서로 작업 순서를 안내하는 것과 코드로 정리를 요구하는 것은 달랐어요. 원인이 생긴 시점에 정상 상태와 누락 상태를 구분할 수 없다면 검사 위치만 옮길 수는 없습니다. 자동 정리나 적용 기록의 부담까지 검토해야 했지만, 당시에는 그 선택을 끝내지 않았어요.

6. 다음 서비스에서 다시 남은 import 블록

절차서 문장을 구체화한 뒤 같은 서비스의 남은 편입 단계들과, 그다음 이틀 동안 추가한 작은 스택 둘에서는 잔여 블록 문제 없이 진행했어요. 정리 커밋은 다음과 같았습니다.

chore: 역할을 다한 EC2 import 블록을 치운다 chore: 역할을 다한 VPN import 블록을 지운다 chore: 역할을 다한 import 블록 9 개를 내린다

커밋 본문에도 "남겨두면 import 단언이 어긋나 이 스택의 모든 plan을 막는다"고 적혀 있어요. 실패한 뒤가 아니라 실패하기 전에 정리했습니다. apply와 정리 사이의 간격도 대부분 삼십 분 안쪽이었어요.

이 결과만 보았을 때는 절차서가 정리를 잊는 문제에 효과가 있다고 판단했어요. 표의 다섯 번째는 정리 PR을 만들고도 머지하지 않은 경우였으므로, 남은 문제는 PR의 반영 여부라고 생각했습니다.

하지만 나흘 뒤 다음에 편입한 서비스에서 같은 일이 다시 생겼어요.

코드에 import 블록이 5개인데 plan 의 import 는 0건입니다.

이번에도 문서만 고친 PR이 막혔어요. README를 작성한 PR이었고 .tf 파일은 수정하지 않았습니다. 표의 네 번째와 같은 경우예요. 저장소 커밋 본문에도 그 경위가 남아 있습니다.

앞 서비스의 README 가 "세 번 잊었고 세 번 다 다음 PR 이 막혔다" 고 적어둔 함정이고 여기서 네 번째로 걸렸다.

인용문의 네 번째는 앞 서비스에서 잊은 세 번에 이번 일을 더한 횟수예요. 이 글에서 처음부터 세면 여섯 번째입니다. 이번에는 정리 PR이 닫힌 것이 아니라 블록 삭제를 빠뜨렸고, 절차서 문장을 구체화한 뒤에 일어났어요.

따라서 절차서로 정리를 잊는 문제는 해결했고 PR 반영 여부만 남았다는 판단은 맞지 않았어요. 지울 시점을 구체적으로 적는 것만으로는 삭제 누락을 막지 못했습니다.

재발하지 않았던 작업의 공통 조건

문제없이 정리했던 작업들은 실패를 겪은 직후에 몰려 있었어요. 같은 서비스의 남은 단계들은 세 번 연속으로 막힌 그날 저녁에 진행했고, 작은 스택 둘은 그 이틀 뒤였습니다. 커밋 본문도 저장소 관례보다 "앞에서 세 번 막혔다"는 경험을 근거로 들고 있어요.

새 서비스는 편입 단계가 일곱 개였고, 리소스를 처음 편입한 단계에서 바로 잔여 블록이 발견됐어요. 앞선 몇 건에서 재발하지 않았다는 관찰만으로는 절차서가 재발을 막는다고 판단할 수 없었습니다.

실패를 겪은 뒤 그 서비스의 남은 단계들은 다시 문제없이 정리했어요. 두 번째 정리 커밋 본문은 다음과 같습니다.

앞 단계에서 한 번 걸렸던 것이라 이번에는 apply 직후 걷어낸다.

이 커밋도 두 시간 전의 실패 경험을 근거로 들고 있어요. 앞 서비스에서 세 번 실패한 뒤, 새 서비스에서 한 번 실패한 뒤에는 정리가 이어졌습니다. 적어도 이 기록에서는 절차서의 효과와 최근 실패를 기억한 영향을 분리하기 어려웠어요.

수동 삭제 과정에서는 import 블록과 함께 리소스 블록까지 잘라낸 일도 있었어요. 주석 구분선을 뒤로 찾으며 삭제 범위를 정하다가 생긴 일입니다. 이후에는 삭제 전후의 리소스 블록 수가 같은지 확인하는 단언을 붙이고 있어요. 이 확인도 사람이 직접 해야 했습니다.

절차서를 고친 뒤에도 재발했고, 자동 예방을 검토한 A'는 그대로 구현하면 모든 편입 apply를 실패시키는 안이었어요. 문장 수정의 효과도 자동화 방안의 타당성도 각각 확인해야 했습니다. 몇 건의 정리 성공만으로 예방 문제가 해결됐다고 판단한 범위가 너무 좁았어요.

그림 3. 최근 실패 이후의 작업만으로 절차서의 효과를 판단했다
✍️ 정리
import 개수 가드는 여섯 번 모두 잔여 블록을 탐지했지만, 실패는 다음 PR에서 드러났어요. 절차서에 삭제 시점을 구체적으로 적고 에러 메시지 다섯 줄을 추가해 조치 방법을 안내했지만, 나흘 뒤 다음 서비스에서 블록 삭제를 다시 빠뜨렸습니다.

apply 직후 블록 수가 0인지 검사하는 안은 방금 사용한 블록까지 실패시키므로 그대로 적용할 수 없었어요. 검토한 자동 정리와 적용 기록 방식에는 각각 쓰기 권한이나 별도의 상태 관리가 필요했습니다. 당시에는 예방 방식을 정하지 못했고, 몇 건의 정리 성공만으로 절차서의 효과를 판단한 점을 바로잡아야 했어요.
