7편. Terraform 드리프트와 점검 오류의 알림 경로 나누기 ← 지금 이 글

테라폼으로 AWS 인프라를 관리하는 저장소에 매일 실행하는 점검 워크플로를 붙였어요. 이때 인프라 변경을 발견한 경우와 점검을 실행하지 못한 경우를 구분해야 했어요. 둘 다 Terraform Drift Detection 실패로 알리면, 콘솔 변경을 확인해야 하는지 plan 역할의 자격증명을 확인해야 하는지 알림만으로 판단하기 어려워요.

그래서 plan에서 확인한 결과는 GitHub 이슈에 남기고, plan에 도달하기 전의 실패는 워크플로 실패 알림으로 받도록 나눴어요. 이슈에는 변경 내용이나 plan 오류를 확인할 로그를 붙여서, 받은 사람이 확인할 대상을 구분하도록 했어요.

1. 콘솔 변경을 다음 apply 전에 확인하기

드리프트는 코드에 정의한 인프라와 실제 인프라가 달라진 상태예요. 예를 들어 장애 대응 중에 콘솔에서 보안그룹 규칙 하나를 추가했는데 코드에는 반영하지 않았다고 해볼게요. 코드가 그 규칙을 관리하고 있다면 다음 apply에서 콘솔 변경이 되돌려질 수 있어요. 반영 전에 차이를 확인해야 임시 변경을 유지할지 되돌릴지 판단할 수 있어요.

이런 변경을 놓치면 다음 apply 뒤에 통신이 안 될 때 콘솔 변경 이력까지 다시 확인해야 해요. 원인을 찾는 데 몇 시간이 걸릴 수 있다는 점을 고려해, 코드와 실제 설정의 차이를 매일 한 번 확인하도록 했어요.

2. 변경 감지와 plan 오류를 이슈로 남기기

확인 수단은 terraform plan이에요. 초기 설계에서는 -detailed-exitcode 플래그로 변경 없음, 변경 있음, 실행 오류를 구분했어요. 이 옵션을 붙였을 때의 종료 코드는 다음과 같아요.

terraform plan -detailed-exitcode 0 변경 없음 코드 == 실제 인프라 2 변경 있음 드리프트 (또는 아직 반영 안 된 코드) 1 오류 plan 자체가 실패 (state 잠금, 문법, 권한 부족)

이 설계에서는 plan의 종료 코드가 2이거나 1이어도 잡을 실패시키지 않아요. 2는 변경 내용을 확인할 이슈를 만들고, 1은 같은 제목과 같은 drift 라벨의 이슈에 plan이 오류로 끝났다는 본문을 남겨요. 오류일 때는 "파이프라인 자체가 깨져 있을 수 있습니다"라는 안내와 실행 로그를 확인해야 해요.

반면 체크아웃, 역할 위임, init 단계에서 실패하면 plan을 실행하지 못해요. 이 경우 잡이 실패하고 슬랙의 workflows 구독으로 알림을 받아요. plan에서 변경을 발견했을 때와 plan이 오류로 끝났을 때는 이슈 본문을 구분하고, plan 이전의 실패는 워크플로 알림에서 확인하는 방식이에요.

그림 1. plan 결과와 plan 이전의 실패를 구분해 알림을 받아요

3. GitHub Slack 앱 구독으로 받기

알림을 받기 위해 웹훅 시크릿이나 알림 전용 워크플로를 추가하지는 않았어요. GitHub Slack 앱에서 이슈, 워크플로, PR 관련 이벤트를 구독했어요. 각 구독에서 확인할 대상은 다음과 같아요.

📮 구독별로 확인할 내용
• issues: 드리프트 이슈가 생겼다 → 콘솔 변경을 코드에 반영하거나 되돌리는 PR 을 올린다
• workflows: 워크플로 실행이 실패했다 → 러너·자격증명·apply 실행 오류를 확인한다
• pulls / reviews: 리뷰 요청이 왔다 → 머지에 승인 1인이 필요하니 PR 을 검토한다

별도 알림 구현을 추가하면 시크릿을 관리하고 알림 워크플로의 실행 상태도 확인해야 해요. 알림 전송이 실패했는데 이를 확인하지 못하면, 문제가 없어서 알림이 없는 것인지 전송이 멈춘 것인지 구분하기 어려워요. 기존 GitHub Slack 앱 구독을 사용해 추가로 관리할 설정을 줄였어요.

4. 정기 점검은 업무 시작 시간에 맞추기

후속 변경에서는 cron을 0 0 * * *로 바꿨어요. GitHub Actions의 cron은 UTC 기준이므로 UTC 00:00, 한국시간 오전 9시입니다. 같은 변경에서 상세 종료코드 옵션을 제거하고 plan JSON으로 변경 여부를 판정하도록 바꿨어요. 위 종료코드 설명은 초기 설계이고, 오전 9시 스케줄과 JSON 판정은 후속 구현이므로 같은 시점의 코드로 읽으면 안 됩니다. 업무 시작 무렵에 결과를 확인하려고 실행 시각도 조정한 것이에요.

이 정기 점검은 발견한 차이를 업무 시간에 검토하고 PR로 처리하는 용도예요. 변경을 확인할 사람이 대응할 수 있는 시간에 결과를 받도록 했어요. 즉시 대응할 장애 알림과 같은 방식으로 야간에 확인을 요구하지 않으려는 선택이었어요.

5. 중복 이슈를 줄이고 처리 후 닫기

이슈로 알림을 받으면 처리한 항목을 닫는 방법도 정해야 해요. 이 저장소에서는 main 머지 시 dev만 자동 반영하고, prod는 사람이 plan 요약을 읽은 뒤 수동으로 실행해요. 머지와 prod 반영 사이에 남은 변경은 apply 워크플로의 prod-pending 잡이 확인해요. 미반영 변경이 있으면 이슈를 열고, 다음 머지에서 반영을 확인하면 코멘트를 남기고 자동으로 닫아요.

드리프트 이슈는 같은 제목의 열린 이슈가 있으면 새로 만들지 않고 코멘트만 덧붙여요. 같은 변경을 이슈 30개로 반복해서 만들면 처리해야 할 변경이 몇 개인지 파악하기 어려워지기 때문이에요. 당시 드리프트 이슈는 자동으로 닫지 않고 PR로 처리한 사람이 직접 닫도록 했어요. 미반영 알림과 드리프트 알림의 종료 방식이 다르므로, 처리한 이슈가 계속 열려 있지 않은지도 확인해야 해요.

6. 알림에서 다음 확인 대상을 구분하기

이렇게 나누면 콘솔 변경은 코드에 반영할지 되돌릴지 검토하고, plan 오류는 이슈에 첨부된 실행 로그를 확인하게 돼요. plan 이전의 실패는 워크플로에서 러너나 자격증명을 확인해요. 변경이 없는 exit 0은 따로 알리지 않도록 했어요.

그림 2. 이슈 내용과 워크플로 실패를 나눠 확인할 대상을 구분해요

다만 plan 오류도 드리프트와 같은 제목과 라벨의 이슈에 남으므로 이슈 본문까지 읽어야 구분할 수 있어요. 알림을 나눴더라도 실행 로그를 확인하는 과정은 필요해요.

✍️ 적용한 알림 구분
초기에는 plan의 변경 감지(exit 2)와 오류(exit 1)를 이슈 본문으로 구분하고, plan 이전의 실패는 잡 실패로 받도록 했어요. GitHub Slack 앱 구독을 사용했습니다. 후속 변경에서 정기 점검을 KST 09시로 옮기면서 변경 판정도 종료코드에서 plan JSON으로 바꿨어요.

prod 미반영 이슈는 다음 머지에서 반영을 확인하면 자동으로 닫고, 당시 드리프트 이슈는 PR로 처리한 사람이 닫도록 했어요. 변경을 발견한 경우와 점검하지 못한 경우를 구분하되, 구체적인 대응은 이슈 본문과 실행 로그를 확인해서 정하도록 했어요.
