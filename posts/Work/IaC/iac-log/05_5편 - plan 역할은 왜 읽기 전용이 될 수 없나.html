📌 정정: 다음 날 3장의 권한 범위가 바뀌었어요
다음 날 잠금 파일 이름을 하나로 제한했던 정책을 두 번 넓혔어요. 읽기와 잠금 파일 접근 범위가 버킷 전체로 바뀌어서, 3장의 코드블록과 그림 2는 현재 코드와 달라요.

잠금 파일 외의 state 본문까지 쓸 수 있게 해서는 안 된다는 제약은 유지했어요. 확장자 .tflock 제한과 apply 역할의 쓰기 경계도 그대로 남겼습니다. 바뀐 부분은 잠금 파일을 이름 하나로 제한한 범위이고, 1·2·4·5장의 설명은 그대로 적용돼요.

이 범위를 유지하기 어려웠던 이유는 9편에 적었어요. 아래 3장은 변경 전 설계입니다.

Terraform CI에서 plan 역할에 ReadOnlyAccess만 주면 첫 PR부터 state 잠금 획득에 실패해요. 환경마다 실제 리소스를 바꾸는 apply 역할과 PR에서 변경 계획을 계산하는 plan 역할을 나눴는데, plan에도 일부 쓰기 권한이 필요했던 거예요.

state는 Terraform이 관리하는 리소스의 상태를 저장하는 파일이고, 우리는 그걸 S3 버킷에 둬요. plan이 변경 계획을 계산하는 동안 이 파일이 다른 실행에 의해 갱신되지 않도록 잠금을 사용합니다. S3 네이티브 잠금은 별도 객체를 만들고 지우기 때문에, plan 역할에도 그 객체에 대한 쓰기 권한이 필요해요.

1. plan도 state 잠금 파일을 만들어요

plan은 코드가 원하는 상태, state에 적힌 상태, 실제 리소스의 현재 상태를 읽어요. 이들을 비교해 변경 계획을 계산하기 전에 state 잠금을 획득합니다.

계산하는 동안 다른 실행이 같은 state를 갱신하면, plan이 비교한 기준과 실제 state가 달라질 수 있어요. 이를 막기 위해 plan도 기본적으로 잠금을 사용해요.

Terraform 1.10+의 S3 네이티브 잠금(use_lockfile = true)은 state 파일 옆에 <state 키>.tflock 객체를 만들었다가 지워요. 만들 때는 s3:PutObject, 지울 때는 s3:DeleteObject가 필요합니다. ReadOnlyAccess에는 이 두 권한이 없어서, 이 잠금 설정을 쓰는 plan 역할에는 별도로 추가해야 해요.

그림 1. plan 계산 전후에 잠금 파일을 만들고 지워요

2. 잠금을 끄는 대신 권한을 고쳐요

잠금 획득에서 실패할 때 -lock=false를 붙이면 잠금을 생략하고 plan을 실행할 수 있어요. 다만 워크플로에 이 옵션이 남으면 이후에도 잠금 없이 실행됩니다. 이 설정을 apply에도 복사하면 동시 실행이 같은 state를 갱신하면서 손상될 위험이 있어요.

이 경우에는 잠금을 유지하면서 plan이 필요한 작업을 할 수 있도록 IAM 정책을 고치는 편이 맞아요. 잠금 오류를 없애려고 옵션을 추가하기 전에, 잠금 파일 생성과 삭제 권한이 빠졌는지 확인해야 합니다.

⚠️ 워크플로의 잠금 옵션 확인
워크플로에 -lock=false가 있다면 추가한 커밋에서 이유를 확인해 보세요. 우리 워크플로는 그 옵션 없이 -lock-timeout=5m를 사용해요. 잠금을 생략하지 않고 최대 5분까지 기다린 뒤 실패하도록 했습니다.

3. 당시에는 잠금 파일 하나에만 쓰기를 허용했어요

state는 환경별로 env/dev/, env/prod/ 프리픽스에 나눠 두었어요. 당시에는 dev plan 역할이 자기 환경의 state만 읽으면 된다고 판단했습니다. 그래서 인프라 전반을 읽되, 쓰기는 자기 프리픽스 안의 잠금 파일 하나에만 허용했어요.

ReadOnlyAccess # 인프라 전반 읽기 (실제 리소스 상태) s3:GetObject env/dev/* # 자기 환경 state 읽기 s3:ListBucket prefix=env/dev/* # 자기 프리픽스만 s3:PutObject + s3:DeleteObject env/dev/terraform.tfstate.tflock ^ 와일드카드가 아니라 파일 이름

마지막 줄은 쓰기 대상을 잠금 파일로 제한해요. 쓰기 범위를 env/dev/*로 넓히면 같은 프리픽스의 terraform.tfstate까지 덮어쓸 수 있습니다. state 본문을 읽는 권한과 잠금 파일을 쓰는 권한을 구분한 정책이에요.

그림 2. 당시에는 쓰기 대상을 잠금 파일 하나로 제한했어요

4. DynamoDB 없이 S3에서 잠금을 관리해요

DynamoDB를 쓰는 기존 방식에서는 부트스트랩에 테이블이 하나 더 필요하고, S3와 DynamoDB 양쪽의 권한을 설정해야 해요. 1.10의 S3 네이티브 잠금을 선택하면 별도 테이블 없이 S3 권한으로 잠금을 구성할 수 있습니다.

대신 잠금용 S3 객체에 필요한 권한을 함께 설정해야 해요. use_lockfile = true를 적용할 때 어떤 객체가 생성되고 삭제되는지 확인하면, state 본문에 쓰기 권한을 주지 않고도 잠금을 허용할 수 있습니다.

5. 명령이 생성하는 객체까지 확인해요

조회나 미리보기 용도로 쓰는 명령도 별도 객체를 생성할 수 있어요. Athena의 SELECT는 결과를 S3에 저장하므로 s3:PutObject가 필요하고, CloudFormation 변경 집합도 실제 변경을 적용하기 전이지만 집합 생성 자체는 쓰기 API입니다.

역할에 줄 권한을 정할 때는 실행할 명령이 읽는 대상과 생성하거나 삭제하는 대상을 함께 확인해야 해요. 우리 plan 역할도 이 기준에 따라 리소스 조회 권한에 잠금 파일 쓰기를 추가했습니다. 다만 파일 하나로 고정했던 범위는 앞의 정정처럼 다음 날 넓혔어요.

✍️ 오늘의 요약
S3 네이티브 잠금을 쓰는 plan은 잠금 파일을 생성하고 삭제하므로 ReadOnlyAccess 외에 해당 객체의 쓰기 권한도 필요해요. -lock=false로 잠금을 생략하는 대신, state 본문과 잠금 파일의 권한을 나눴습니다.

당시에는 잠금 파일 이름 하나로 쓰기를 제한했지만 다음 날 범위를 넓혔어요. state 본문은 쓰지 못하게 하고 잠금 파일만 생성·삭제하도록 허용하는 구분은 유지했습니다.
