13편. 알림 경로를 감시하는 알람의 SNS·KMS 의존성 확인하기 ← 지금 이 글

알람이 발생하면 티어별 SNS 토픽으로 메시지를 보내고, 토픽을 구독한 외부 모니터링 서비스가 온콜 담당자에게 전화하도록 구성했어요. 티어는 이 구성에서 알림을 보낼 경로를 구분하는 값입니다.

구독 배달 실패를 감시하는 알람도 추가했는데, p2 경로의 실패 알람을 다시 p2로 보내고 있었어요. 감시 대상과 알람이 같은 경로에 의존하니, 경로가 고장났을 때 감시 알람도 도착하지 않을 수 있었습니다. DLQ 라우팅을 고친 뒤에는 카드 변환과 암호화 키 감지 룰에도 같은 의존성이 있는지 살펴봤어요.

1. 구독 배달 실패 알람은 다른 경로로 보내기

SNS가 구독자에게 메시지를 배달하지 못하면 재시도 정책에 따라 처리해요. 외부 모니터링 서비스가 401을 돌려주거나 엔드포인트가 응답하지 않는 경우, DLQ가 없으면 실패한 메시지를 별도로 보관하지 못합니다. CloudWatch 알람이 ALARM 상태가 되고 SNS 발행까지 끝나도 담당자는 전화를 받지 못할 수 있어요.

그래서 구독마다 DLQ(배달 실패 큐)를 붙였어요. 최종적으로 배달하지 못한 메시지를 큐에 남기고, 큐 깊이가 늘어나면 알람을 보내도록 했습니다.

처음에는 이 알람을 모두 p2(채팅 카드)로 보냈어요. p2 구독의 배달이 실패하면, 그 실패를 알리는 알람도 같은 구독을 거쳐야 했습니다. 코드 주석에는 알림 체계 자체를 감시한다고 적혀 있었지만, 액션의 티어는 p2로 고정돼 있었어요.

감시하는 경로와 다른 경로를 쓰도록 티어별 목적지를 정했어요.

locals { # 감시 대상 경로를 피해서 보낼 곳을 정한다. dlq_alarm_tier = { p1 = "p2" # 전화 경로가 끊겼으니 채팅으로 p2 = "p1" # 채팅이 끊겼으니 전화로 p3 = "p2" # 하트비트 배달 실패는 급하지 않다 } } tier = local.dlq_alarm_tier[each.key]

이 저장소에서는 tier 값으로 발행할 토픽을 선택해요. 그래서 별도의 예외 분기를 만들지 않고 tier 값만 바꿔서 라우팅을 수정할 수 있었습니다. p1 배달 실패는 p2로, p2 배달 실패는 p1로 보내도록 했어요.

⚠️ 채팅 배달 실패도 전화로 알리게 돼요
p2의 DLQ 알람은 p1으로 보내므로 채팅 배달 문제로도 담당자를 호출할 수 있어요. p2로 다시 보내면 같은 배달 실패를 겪을 수 있고, p3는 사람이 확인하는 경로가 아니어서 p1을 택했습니다.
DLQ 메시지의 보존 기간은 14일이에요. 메시지가 남아 있는 동안에는 큐 깊이 알람으로 실패 사실을 확인할 수 있습니다.

2. 카드 변환 실패는 변환을 거치지 않는 알람으로 알리기

DB 페일오버와 컨테이너 배포 실패 같은 이벤트 기반 알림은 전화가 와도 채팅에는 내용이 남지 않았어요. 당시 CloudWatch 알람 32개는 표시됐지만, 이벤트 넷은 AWS Chatbot에서 원본 JSON을 카드로 표시하지 못했습니다.

EventBridge의 input_transformer로 이벤트를 Chatbot의 커스텀 카드 JSON 형식으로 바꿨어요. Lambda를 따로 두면 그 함수의 실패까지 감시해야 하므로, EventBridge의 변환 기능을 사용했습니다.

다만 변환 결과가 유효한 JSON이 아니면 배달이 실패할 수 있어요. DB 메시지나 컨테이너 실패 사유에 따옴표가 들어가는 경우가 문제였습니다. 룰과 타깃이 존재한다는 것만 확인해서는 이런 배달 실패를 알 수 없어요.

그래서 AWS/Events의 FailedInvocations에 메타 알람을 걸었어요. 메타 알람은 알림 체계 자체의 실패를 감시하는 알람입니다. 카드 변환을 거친 배달이 실패했는지 확인하고 p2로 알리도록 했어요.

이 경우에는 카드와 실패 알람이 같은 p2 토픽을 써도 감시 대상인 변환 과정은 공유하지 않아요. 실패 알람은 CloudWatch에서 SNS 토픽으로 직접 가므로 EventBridge의 카드 변환을 거치지 않습니다. 확인할 대상은 티어가 같은지보다 실패한 구성 요소를 감시 알람도 거치는지였어요.

카드를 추가하면서 기존 전화 경로도 유지했어요. 원본은 p1으로 보내고, 룰에 별도 타깃을 추가해 카드만 p2로 보내도록 했습니다. 아직 실제 배달을 검증하지 못한 변환이 실패하더라도 전화 경로에 영향을 주지 않게 하려는 선택이었어요.

3. KMS 감지 룰과 알림 토픽이 같은 키에 의존했어요

침해 탐지 룰을 살펴보니, KMS 키를 비활성화하거나 삭제 예약하는 API 호출을 감지하고 있었어요.

# 암호화 키를 무력화하는 API 호출을 잡는다 eventSource = ["kms.amazonaws.com"] eventName = ["DisableKey", "ScheduleKeyDeletion"] # 타깃 target = {p1 토픽} # 원본 target = {p2 토픽} # 카드 (input_transformer)

코드 주석에도 이 계정의 고객 관리형 KMS 키(CMK)에 알림 토픽 암호화 키가 포함된다고 적혀 있었어요. 그 키가 비활성화되면 SNS 발행이 실패할 수 있으므로, 이 룰은 침해 탐지와 알림 체계 감시를 함께 맡는다는 설명이었습니다.

그런데 SNS 토픽 설정을 보면, 룰이 알림을 보낼 토픽도 감시 대상 키로 암호화돼 있었어요.

resource "aws_sns_topic" "alerts" { for_each = toset(local.tiers) name = "{티어별 알럿 토픽}" kms_master_key_id = aws_kms_key.alerts.id # 바로 그 키 }

키를 비활성화하면 CloudTrail 이벤트가 생기고 룰이 매칭되더라도, 타깃 토픽에 발행하는 단계에서 같은 키가 필요합니다. 키 비활성화를 감지하는 룰과 그 사실을 전달하는 토픽이 같은 키에 의존하고 있었어요.

아래는 당시의 잘못된 비교예요. 삭제 예약 대기 중에도 KMS 키를 암호화 작업에 사용할 수 없으므로, 삭제 예약이면 알림이 전달된다는 결론은 맞지 않습니다. 당시 인용은 정정 이유를 보여주기 위해 남겼어요.

ScheduleKeyDeletion 삭제 예약 7~30일 대기 → 키는 아직 살아 있다 → 알림 나간다 DisableKey 즉시 비활성화 키가 지금 죽는다 → 알림 못 나간다

삭제 예약에는 최소 7일의 대기 기간이 있지만, 그 7일 동안 키를 계속 사용할 수 있다는 뜻은 아니에요. 키가 삭제 대기 상태로 바뀌면 암호화 작업에 사용할 수 없습니다. SNS에 캐시된 데이터 키가 있으면 영향이 즉시 나타나지 않을 수도 있지만, 삭제 예약 알림이 전달된다고 보장할 수는 없어요.

DisableKey는 키를 즉시 비활성화해요. 이 경로에서는 비활성화된 키로 암호화한 토픽에 알림을 보내야 한다는 의존성 문제가 드러납니다. 이벤트를 감지하는 것과 그 결과가 담당자에게 도착하는 것은 따로 확인해야 했어요.

DLQ 라우팅에서는 감시 대상 경로를 피하도록 수정했지만, KMS 감지 룰에서는 같은 기준을 적용하지 못했어요. 개별 파일의 주석을 확인하는 데서 그치지 않고, 감지 룰부터 토픽과 구독까지 연결해서 살펴볼 필요가 있었습니다.

그림 1. KMS 감지 룰도 알림 토픽의 암호화 키에 의존해요

4. 별도 경로와 외부 감시를 검토하기

실패를 감시하는 알람을 더해도 그 알람이 같은 자원에 의존하면 함께 전달되지 않을 수 있어요. 그래서 알람을 추가하는 것과 별개로 공유하는 자원을 확인하고, 다음 두 방식을 검토했습니다.

방법 1: 감시 알림에 별도 경로 쓰기

감시 대상과 토픽·키를 공유하지 않는 경로를 두는 방식이에요. 여기서는 해당 KMS 키의 암호화에 의존하지 않는 비상용 경로(break-glass)도 검토했습니다. 키를 사용할 수 없을 때도 알림을 보낼 수 있어야 하기 때문이에요.

관리할 자원이 늘고 암호화를 적용하지 않는 발행 경로가 생긴다는 부담이 있어요. 평소에 쓰지 않는 비상 경로가 실제로 동작하는지도 주기적으로 확인해야 합니다.

방법 2: 파이프라인 밖에서 실패 지표 보기

발행·배달 실패 지표를 외부 모니터링 서비스에서 확인하는 방식도 검토했어요. 다만 변환 실패, 키 비활성화, 구독 배달 실패가 모두 같은 지표에 남는지는 별도 확인이 필요합니다. 지표가 감지하는 실패 범위부터 구분해야 해요.

실패 횟수만으로 원인을 모두 알 수 있는 것도 아니에요. 그리고 지표 알람을 같은 토픽으로 보내면 알림이 함께 실패할 수 있으므로, 파이프라인 외부에서 확인해야 합니다.

살펴보던 시점에는 EventBridge 배달 실패와 DLQ 큐 깊이 알람이 있었어요. 반면 계획 문서에 적힌 발행·배달 실패 지표 감시는 코드에서 찾지 못했습니다. 별도 경로와 외부 지표 감시는 검토한 방안이며, 여기서 구현이나 동작 검증까지 마쳤다는 뜻은 아니에요.

그림 2. 별도 경로는 점검이 필요하고, 외부 지표는 감지 범위를 확인해야 해요

5. 복구 알림을 받지 못하면 다음 장애 호출도 놓칠 수 있어요

복구 알림에서도 수신 경로를 끝까지 확인하지 못한 문제가 있었어요. 알람 모듈은 P1 알람의 복구를 한 단계 낮은 p2로 보내도록 구성했습니다.

# modules/cw-alarm ok_tier = var.tier == "p1" ? "p2" : var.tier alarm_actions = [var.topic_arns[var.tier]] # 발생 → p1 (전화) ok_actions = [var.topic_arns[local.ok_tier]] # 복구 → p2 (기록만)

발생 알림은 전화로 받고, 복구는 기록만 남기려는 의도였어요. 예를 들어 장애 알림 뒤 15분 만에 자동 복구됐을 때, 복구로 다시 호출하지 않도록 한 것입니다.

그런데 외부 모니터링 서비스 구독을 코드로 가져올 때 p1과 p3만 만들었어요. p2는 사람을 호출하지 않으므로 구독도 필요 없다고 판단했습니다. 그 결과 약 18시간 동안 발생 알림은 전달돼도 복구 알림은 해당 서비스에 전달되지 않는 구성이었어요.

복구 신호를 받지 못하면 외부 모니터링 서비스의 인시던트가 열린 채로 남을 수 있어요. 그러면 다음 발생 알림이 기존 인시던트로 처리돼 새 호출을 놓칠 수 있습니다. 복구 여부를 모르는 데서 끝나는 문제가 아니었어요.

그 18시간 동안 발생과 복구를 오간 알람이 없어 실제 피해는 없었습니다. 그래도 구독 누락은 고쳐야 했어요. p2 구독을 추가하되 온콜 라우팅 파라미터를 빼서, 복구는 전달하고 전화는 걸지 않게 했습니다. p2 구독이 필요한 이유도 코드 옆 주석에 남겼어요.

비슷한 확인이 보안 룰에서도 필요했어요. P3로 먼저 관찰하려 했지만 p3에는 채팅 구독이 없어 관찰할 수 없다는 것을 확인하고 계획을 바꿨습니다. 티어를 낮추거나 관찰용으로 쓰려면, 먼저 그 티어에서 누가 어떤 방식으로 알림을 받는지 확인해야 했어요.

6. 감지부터 수신까지 의존성 확인하기

룰이 존재하고 타깃이 연결돼 있다는 것만으로 담당자가 알림을 받는다고 볼 수는 없었어요. DLQ 알람은 배달 경로를, 카드 실패 알람은 변환 과정을, KMS 감지 룰은 암호화 키를 함께 확인해야 했습니다.

알림 경로를 감시할 때는 감시 대상과 같은 토픽·키·변환기·구독을 쓰는지 살펴보려고 해요. 같은 토픽을 쓰더라도 카드 변환을 거치지 않는 경로는 구분할 수 있고, 토픽을 나눠도 같은 키를 쓰면 함께 영향을 받을 수 있습니다.

복구 알림도 수신 서비스까지 도착해야 인시던트를 닫을 수 있어요. 발생 알림의 호출 여부와 복구 알림의 전달 여부를 각각 확인하는 것이 필요한 이유입니다.

✍️ 정리
DLQ 알람은 p1 → p2, p2 → p1로 라우팅을 바꿨고, 카드 변환 실패 알람은 변환을 거치지 않는 CloudWatch 경로로 보냈어요. KMS 감지 룰에서는 감시 대상과 토픽의 암호화 키가 같다는 의존성을 확인했습니다. 삭제 예약 대기 중에도 KMS 키를 암호화 작업에 사용할 수 없으므로, 예약 알림이 전달된다는 당시 비교도 정정했어요. 실패 지표의 감지 범위는 추가 확인이 필요합니다.

복구 알림은 p2 구독을 추가해 외부 모니터링 서비스에 전달하도록 고쳤어요. 별도 비상 경로와 외부 지표 감시는 검토한 방안이며, 이 글에서 구현과 배달 검증까지 확인한 결과로 쓰지는 않았습니다.
