10편. 태그 키 변경에서 빠뜨린 IAM boundary 조건을 검사로 찾기 ← 지금 이 글

태그 키를 env에서 Environment로 바꿨어요. 조직에서 이미 PascalCase로 된 태그 키를 쓰고 있어서, 새로 만든 스택만 소문자를 쓰면 태그로 리소스를 조회할 때 결과가 나뉘었거든요. plan에는 문제가 없었고 PR 검사도 모두 통과했어요.

이 태그 키는 단일 계정 안에서 dev와 prod의 접근 권한을 구분하는 IAM Deny 조건에도 쓰였어요. 어제 6편에서 설명한 두 겹의 차단 중, 하위 역할에 적용되는 permissions boundary의 조건을 수정하지 못했습니다. 태그 이름 변경에 문제가 없어도 IAM 조건이 맞는지 따로 확인해야 했어요.

태그를 바꾼 커밋은 815de6b이고, 다음 날 c6226ae에서 누락된 조건을 고쳤어요. 수정할 때는 태그 선언과 IAM 참조를 함께 검사하는 스크립트도 추가했습니다.

1. 조건 키가 없으면 Deny에 매치되지 않아요

IAM 정책의 StringEquals는 비교할 조건 키가 요청 컨텍스트에 있고 값도 같아야 참이 돼요. 키가 없으면 조건은 거짓이 되고, 해당 Deny 문은 적용되지 않아요.

리소스에는 Environment 태그가 붙어 있는데 Deny가 aws:ResourceTag/env를 참조하면, 그 조건으로는 요청을 거부하지 못해요.

리소스에 붙은 태그 Environment = prod Deny 조건 StringEquals aws:ResourceTag/env = ["prod"] 조건 키 env 가 리소스에 없다 → 비교가 성립하지 않는다 → 조건 false → Deny 문이 발동하지 않는다 → 요청은 그냥 성공한다

위 발췌의 마지막 줄은 다른 권한 평가를 생략한 설명이에요. 이 Deny가 적용되지 않아도 별도의 허용이 없거나 다른 명시적 Deny가 있으면 요청은 거부될 수 있어요.

이 경우는 AccessDenied로 요청이 실패하는 상황과 달라요. Deny 조건에 매치되지 않았다는 이유만으로 오류가 발생하지는 않아요. 요청 실패를 확인하는 것만으로는 태그 키와 IAM 조건이 어긋난 상태를 찾기 어려워요.

🔑 조건 키가 없을 때 무슨 일이 일어나나
6편 4장에서 StringNotEquals는 키가 없을 때도 참이라 boundary 강제가 성립한다고 썼어요. 이번에는 반대로 키가 없으면 거짓이 되는 조건을 사용했어요.
• StringEquals: 키가 없으면 거짓이 됩니다. Deny에 쓰면 키가 사라졌을 때 해당 조건으로 거부하지 못해요
• StringNotEquals: 키가 없으면 참이 됩니다. Deny 에 쓰면 키가 없는 요청까지 막아요
• ...IfExists: 키가 없으면 조건 결과를 참으로 평가해요. Deny에서 부정 연산자와 함께 쓰면 키가 없는 요청도 거부하므로, 조건을 무시해 허용한다는 뜻은 아니에요
긍정형 조건으로 만든 Deny는 태그가 붙어 있어야만 동작해요. 그래서 태그 키를 바꿀 때는 정책에 미치는 영향도 확인해야 해요.

2. 적용 순서만 정해서는 공백을 없앨 수 없어요

태그와 IAM 조건을 따로 적용할 때 생기는 위험은 알고 있었어요. 그래서 커밋 메시지에 다음 순서를 적었습니다.

적용 순서가 중요하다: 1) bootstrap apply - IAM Deny 가 Environment 를 보게 만든다 2) stacks/alerting apply - 리소스 태그를 Environment 로 바꾼다 반대로 하면 태그는 바뀌었는데 Deny 는 옛 키를 보는 구간이 생긴다.

하지만 이 순서로도 Deny가 적용되지 않는 기간을 없애지는 못해요.

bootstrap을 먼저 apply하면 Deny는 Environment를 참조하지만, 기존 리소스에는 아직 env 태그만 있어요. 이때도 조건에 매치되지 않아요. 순서를 반대로 하면 리소스 태그가 먼저 바뀌므로, 어느 쪽이든 태그와 조건이 맞지 않는 기간이 생깁니다.

이 공백을 피하려면 전환 기간에 두 키를 함께 사용해야 해요. Deny도 두 조건을 OR로 유지하고, 새 태그가 모두 적용된 뒤 옛 키를 제거하는 3단계로 나눌 수 있어요.

🪜 태그 키를 무중단으로 바꾸는 3단계
1단계: default_tags 에 env 와 Environment 를 둘 다 달고 apply 합니다. 이 사이 리소스는 두 키를 모두 가져요
2단계: IAM Deny 조건을 두 개로 늘립니다. 옛 키 조건과 새 키 조건을 각각 별도 statement 로 두면, Deny 는 하나만 맞아도 거부되니 자연스럽게 OR 이 돼요
3단계: 모든 리소스에 새 키가 붙은 걸 확인한 뒤, 옛 키 태그와 옛 키 조건을 같은 PR 에서 떼어냅니다
전환 기간에는 옛 키와 새 키 어느 쪽으로도 Deny가 적용되도록 유지해요.

당시에는 실제 AWS 리소스가 거의 없어 피해 가능성은 낮았어요. 그래도 적용 순서만으로 공백을 피할 수 있다는 판단은 잘못됐습니다.

3. boundary 파일의 조건을 빠뜨렸어요

전환 과정의 공백과 별개로, 코드에도 누락이 있었어요. 태그 키를 조건으로 참조하는 파일은 두 개였는데 한 파일만 고쳤습니다.

bootstrap/iam.tf ← 고쳤다 DenyOtherEnvironmentResources aws:ResourceTag/Environment DenyTaggingAsOtherEnvironment aws:RequestTag/Environment bootstrap/iam-boundary.tf ← 빠뜨렸다 DenyOtherEnvironmentResources aws:ResourceTag/env

빠뜨린 파일은 permissions boundary를 정의해요. apply 역할이 새 IAM 역할을 만들 때 반드시 붙이도록 한 권한 상한입니다. 6편의 두 겹 차단 중 첫 번째는 apply 역할 자신의 권한을 제한하고, 두 번째는 그 역할이 만드는 하위 역할에도 같은 환경 격리를 적용해요.

태그 변경 뒤 이 저장소에서 만드는 리소스에는 env 태그가 없었어요. boundary의 Deny는 계속 옛 키를 참조했으므로 하위 역할의 환경 격리에 쓰던 조건이 적용되지 않았습니다. 이 누락은 다음 날 발견했어요.

태그를 바꾼 커밋 메시지에도 이 위험을 적어 두었어요.

"주의: env 태그는 장식이 아니라 IAM Deny 조건이 참조하는 값이다. 키만 바꾸면 그 가드가 조용히 무력화되므로 함께 교체한다."

위험을 알고도 참조 파일 하나를 빠뜨렸어요. 같은 설명을 다시 읽는 것보다, 선언한 태그 키와 IAM에서 참조하는 키를 함께 확인할 방법이 필요했습니다.

그림 1. 태그 이름을 바꾼 뒤 boundary에 남은 옛 키는 조건에 매치되지 않아요

4. 변경 목록 밖에 남은 참조도 확인해야 해요

grep -rn "aws:.*Tag/" .로 찾으면 세 곳 중 하나만 소문자라는 걸 확인할 수 있었어요. 하지만 이번 리뷰에서는 그 참조를 찾지 못했습니다.

리뷰에서 주로 확인한 것은 diff였어요. 누락된 iam-boundary.tf는 PR의 변경 파일 목록에 없었기 때문에, 바뀐 줄만 검토해서는 찾기 어려웠습니다.

diff에는 실제 바뀐 내용이 표시돼요. 함께 바뀌어야 하는 참조가 남았는지 확인하려면 변경 목록 밖의 파일도 검색해야 합니다.

이 확인을 PR마다 반복할 수 있도록 저장소 전체를 읽는 스크립트를 CI에 추가했어요.

5. 옛 키를 넣어 검사기가 실패하는지 확인했어요

수정 PR에 scripts/check-tag-key-consistency.py를 추가했어요.

provider의 default_tags에 선언된 환경 태그 키를 기준으로 삼았어요. 저장소의 .tf 파일에서 aws:ResourceTag/와 aws:RequestTag/ 참조를 모아 선언된 키와 비교하고, 다르면 실패하게 했습니다. AWS 자격증명 없이 실행할 수 있어서 PR의 static 검사 잡에 넣었어요.

::error::IAM 조건이 참조하는 태그 키가 실제 태그 키(Environment)와 다르다. ::error::이 Deny 는 매치되지 않아 조용히 무력화된다 - 거부되지 않은 요청은 로그를 남기지 않는다. bootstrap/iam-boundary.tf: aws:...Tag/env -> aws:...Tag/Environment 여야 한다

위 검사 메시지의 로그 설명도 범위를 좁혀 읽어야 해요. IAM 조건이 일치하지 않았다는 별도 오류가 생기지 않는다는 뜻이며, 허용된 API 요청이 CloudTrail 등에 기록되지 않는다는 뜻은 아니에요. API별 기록 설정은 따로 확인해야 합니다.

검사기를 만든 뒤에는 일부러 옛 키로 되돌려 검사가 실패하는지 확인했어요. 정규식이 실제 선언과 참조를 찾지 못하면 검사 실행 자체는 성공할 수 있기 때문이에요. 8편에서도 네 개의 검사가 통과했지만 apply 잡이 실행되지 않았으므로, 통과 결과만으로 의도한 동작을 확인했다고 볼 수는 없었어요.

태그 선언을 하나도 찾지 못할 때도 실패하도록 했어요. 파일 구조가 바뀌어 정규식이 맞지 않는 경우를 위반 0건으로 처리하지 않기 위해서예요.

6. 여러 파일에 있는 설정을 함께 검사해요

이날 확인한 세 문제는 모두 같은 설정이 여러 곳에 있었는데 일부만 고쳤다는 공통점이 있었어요.

8편에서는 재사용 워크플로 호출부 두 곳 중 하나만 권한을 고쳐, 검사에 통과한 PR의 apply 잡이 실행되지 않았어요. 9편에서는 backend의 state 키를 바꾸고 IAM 정책의 잠금 파일 이름을 그대로 두어 읽기는 되고 잠금만 거부됐습니다. 이번에는 태그 키를 참조하는 파일 둘 중 하나만 고쳤고요.

세 문제 모두 변경한 파일만 확인해서는 다른 파일에 남은 설정을 찾기 어려웠어요. 이번 태그 키 검사는 여러 파일에 나뉜 선언과 참조를 비교하는 방식으로 그 누락을 확인해요.

환경 태그 키는 아래처럼 파일 여섯 개의 여덟 곳에 있었어요. 선언과 참조를 먼저 찾아 놓으면 수정 범위와 검사 범위를 함께 정할 수 있어요.

그림 2. 태그 선언뿐 아니라 IAM 조건에서 참조하는 키까지 함께 확인해요

다만 고친 파일은 bootstrap/에 있어요. 9편에서 설명했듯 CI의 apply 대상이 아니므로, 머지 뒤에 자격증명을 가진 사람이 로컬에서 apply해야 실제 정책에 반영됩니다. 코드 수정과 실제 적용은 구분해서 확인해야 해요.

✍️ 오늘의 요약
태그 키를 바꾸면서 boundary의 IAM 조건 한 곳을 빠뜨렸고, 다음 날 옛 키를 새 키로 고쳤어요. 재발을 막기 위해 태그 선언과 IAM 참조를 비교하는 CI 검사를 추가하고, 옛 키를 넣었을 때 실패하는지도 확인했습니다.

bootstrap 정책은 머지만으로 적용되지 않아요. 실제 환경에 반영하려면 로컬 apply가 필요합니다.
