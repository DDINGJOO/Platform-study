10월 8일 오전은 Lambda 함수를 코드로 담는 일로 지나갔어요. 알림 함수들, 로그 포워더, 리뷰 봇, 청구서를 만드는 함수까지 차례로요. plan 은 깨끗했고 apply 도 조용했습니다.

그런데 12시 58분에 올린 PR 의 제목은 이랬어요. "C-2 Lambda 의 트리거를 편입한다." 함수는 이미 state 안에 들어와 있는데 할 일이 또 남아 있었던 거예요.

함수를 가져왔더니 그 함수를 깨우는 것들이 코드 밖에 남아 있었습니다. 그리고 그건 한 종류가 아니었어요.

1. 함수를 담았는데 깨우는 쪽이 왜 남았나 2. 트리거는 몇 갈래였고 무엇을 담았나 3. 왜 트리거 쪽이 아니라 함수 쪽에서 찾았나 4. 그 방법이 놓친 것 하나 5. 담으면서 걸린 것 둘

1. 함수는 담았는데 깨우는 쪽이 남았다

📖 용어: 트리거
함수를 호출하는 쪽을 통틀어 부르는 말이에요. 사람이 버튼을 누르는 게 아니라, 정해진 시각이 되거나 메시지가 오거나 파일이 생겼을 때 AWS 가 대신 함수를 불러 줍니다. 함수와는 별개의 자원이고, 대개 함수가 아니라 다른 서비스에 속해 있어요.

함수만 담으면 무엇이 곤란한지는 25편과 같은 이야기예요. 매일 도는 drift 잡은 코드가 소유한 자원만 봅니다. 함수의 메모리나 타임아웃이 콘솔에서 바뀌면 다음 날 잡히지만, 그 함수를 매시 정각에 부르던 규칙이 꺼져도 아무 말을 하지 않아요.

다만 이날 더 신경 쓴 건 고장이 나는 방식이었어요. 이날 쓴 코드 주석 두 곳에 같은 경고를 적어 뒀습니다. 한쪽은 "규칙", 한쪽은 "트리거" 라고만 달리 썼어요.

⚠️ 권한이 끊기면 트리거는 발화하지만 호출이 거부된다. 조용히 실패한다.

트리거와 함수 사이에는 한 겹이 더 있어요. 부르는 쪽이 멀쩡히 살아 있어도, 함수 쪽에 "너는 나를 불러도 된다"가 적혀 있지 않으면 호출은 거부됩니다. 규칙은 제시간에 발화하고 발화 횟수 지표도 올라가는데 함수는 한 번도 안 깨어나요. 트리거 쪽 화면만 보면 정상으로 보입니다.

📖 용어: 호출 권한 (함수의 리소스 정책)
함수에 붙어 있는 정책 문서예요. "events 서비스가, 이 규칙으로부터 올 때, 나를 호출해도 된다" 같은 문장이 한 줄씩 들어 있습니다. 한 줄을 statement 라고 부르고 각 줄에는 이름(statement id)이 붙어요. Terraform 에서는 이 한 줄이 aws_lambda_permission 리소스 하나에 대응합니다.

2. 세어 보니 여섯 갈래였다

이날 담은 것은 열넷이에요. 종류별로 세면 이렇습니다.

호출 권한 8 Lambda 리소스 정책의 한 줄씩 스케줄 1 EventBridge Scheduler 이벤트 규칙 · 타깃 2 EventBridge 토픽 구독 1 SNS 로그 구독 필터 1 CloudWatch Logs 버킷 알림 설정 1 S3 ──── 14

표의 이름 둘은 짧게 풀어 둘게요. 토픽 구독은 "이 토픽에 메시지가 오면 저 함수로 보내라" 를 토픽 쪽에 적어 둔 것이고, 로그 구독 필터는 "이 로그 그룹에 줄이 쌓이면 저 함수로 넘겨라" 를 로그 그룹 쪽에 적어 둔 거예요. 버킷 알림은 5장에서 따로 봅니다.

열넷 중 여덟이 호출 권한이에요. 트리거 자체보다 트리거에게 내준 허가가 더 많습니다. 하나의 트리거마다 허가가 하나씩 붙고, 어떤 함수는 부르는 쪽이 둘이라 허가만 둘이거든요.

부르는 쪽을 기준으로 다시 세면 여섯 갈래였어요. 스케줄, 이벤트 규칙, 토픽 구독, 로그 구독, 버킷 알림, 그리고 ALB 의 람다 타깃그룹입니다. 커밋 제목에도 여섯이 적혀 있는데 그건 담은 자원의 종류 이름이라 이 여섯과 같지 않아요. 거기엔 트리거가 아닌 호출 권한이 들어가 있고 ALB 는 빠져 있습니다.

그림 1. 함수는 하나의 스택에 있지만, 그 함수를 부르는 것들은 서비스가 전부 다르다

3. 트리거 쪽에서는 셀 수 없었다

편입 작업에서 대상을 찾는 1차 수단은 태그 조회예요. 이름으로 훑으면 반드시 놓치거나 남의 것을 끌어온다는 걸 앞선 편입에서 겪었거든요. 그런데 이번 열넷은 태그 조회에 하나도 걸리지 않습니다. 열넷 중 열하나는 애초에 자기 ARN 이 없거든요.

📖 용어: ARN
AWS 자원 하나하나에 붙는 전역 식별자예요. arn:aws: 로 시작하는 긴 문자열이고, 서비스·리전·계정·자원 이름이 콜론으로 이어져 있습니다. 태그를 거는 단위이자 태그로 찾아낼 때 돌려받는 단위이기도 해요.

호출 권한은 독립된 자원이 아니라 함수에 붙은 정책 문서 안의 한 문장이에요. 이벤트 타깃도, 로그 구독 필터도, 버킷 알림 설정도 자기 ARN 이 없습니다. 태그 API 는 ARN 목록을 돌려주는 창구라서 ARN 이 없는 것은 나올 자리가 아예 없어요. 남은 셋(스케줄 · 규칙 · 토픽 구독)은 ARN 이 있지만 태그가 하나도 안 붙어 있어서 결과는 같았습니다. 빠진 것을 보완하려고 만들어 둔 참조 그래프 스크립트도 ARN 을 따라가는 방식이라 사정은 같아요.

그러면 트리거 쪽에서 직접 세는 수밖에 없는데, 그 길이 이렇게 생겼어요.

# 트리거 쪽에서 세려면: 서비스마다 다른 창구를 두드린다 aws scheduler list-schedules aws events list-rules → list-targets-by-rule (규칙마다) aws sns list-subscriptions-by-topic (토픽마다) aws logs describe-subscription-filters (로그그룹마다) aws s3api get-bucket-notification-configuration (버킷마다) aws elbv2 describe-target-groups → describe-target-health (타깃그룹마다) # 함수 쪽에서 거꾸로: 한 번 aws lambda get-policy --function-name {함수}

위쪽 길의 문제는 창구가 여섯이라는 것보다 괄호 안에 있어요. 토픽과 로그 그룹과 버킷은 대상을 하나씩 넣어야 답을 줍니다. 어느 토픽인지, 어느 로그 그룹인지, 어느 버킷인지 모르는 상태에서 찾는 작업인데, 그걸 이미 알아야 물어볼 수 있는 구조예요. 계정의 토픽과 로그 그룹과 버킷을 전부 돌면 답은 나오지만 그건 전수 조사입니다.

아래쪽 길은 함수 이름 하나만 있으면 돼요. 함수의 리소스 정책에는 그 함수를 부르려면 허가가 필요한 상대가 모두 적혀 있습니다. 누가 부르는지(서비스), 어느 실물에서 오는 호출인지(source ARN), 무슨 동작을 허가받았는지가 한 줄에 같이 들어 있어요.

앞에서 ARN 을 따라간다고 적은 그 참조 그래프 스크립트도 Lambda 앞에서는 이미 이 방향으로 움직이고 있었어요. 함수 설정과 이벤트 소스 매핑을 읽고, 거기에 리소스 정책을 더해 그 안의 ARN 을 통째로 긁어 옵니다. 허가 자체는 ARN 이 없어 그래프의 점이 되지 못하지만, 허가가 가리키는 실물은 그렇게 드러나요. 트리거가 함수를 가리키는 게 아니라, 함수가 트리거를 허가합니다. 그래서 목록은 함수 쪽에 있어요.

그림 2. 흩어진 것을 모으려면 모여 있는 쪽에서 출발하는 게 싸다

import 식별자까지 그 안에 있었다

리소스 정책을 읽어야 하는 이유가 하나 더 있었어요. 호출 권한을 Terraform 으로 가져올 때 쓰는 식별자가 함수 이름과 statement id 를 슬래시로 이은 것이거든요. 그리고 콘솔이 만든 statement id 는 이렇게 생겼습니다.

{ "Sid": "lambda-{콘솔이 붙인 UUID}", ← import id 의 뒷부분 "Principal": { "Service": "events.amazonaws.com" }, ← 누가 부르나 "Condition": { "ArnLike": { "AWS:SourceArn": "arn:aws:events:{리전}:{계정ID}:rule/{규칙 이름}" } } ← 어느 실물인가 } import { to = aws_lambda_permission.{이름} id = "{함수 이름}/lambda-{콘솔이 붙인 UUID}" }

이 UUID 에는 규칙이 없어요. 콘솔에서 트리거를 추가할 때 자동으로 붙은 이름이라 추측할 수가 없습니다. 함수의 정책을 읽기 전에는 import 블록의 id 줄을 쓸 수조차 없어요. 리소스 정책은 트리거를 찾아내는 길이면서 동시에 그걸 가져올 열쇠였습니다.

4. 거꾸로 찾기에도 구멍이 하나 있었다

이 방법에는 전제가 하나 있어요. 트리거가 호출 권한을 쓴다는 겁니다. 그런데 이날 담은 여섯 갈래 중 하나는 안 썼어요.

매일 오전 9시에 도는 스케줄이 그랬습니다. 그 파일에 이렇게 적어 뒀어요.

스케줄러는 역할로 호출하므로 Lambda 권한이 없다. 역할은 소유하지 않는다.

EventBridge 규칙이 Lambda 를 부를 때는 함수 쪽 리소스 정책만으로 충분해요. 저장소의 다른 스택에도 같은 설명이 주석으로 남아 있습니다. Lambda 를 부르는 타깃의 역할 항목이 비어 있는 이유가 그거예요. 반면 EventBridge Scheduler 는 호출할 때 IAM 역할을 맡아서 부릅니다. 권한이 함수가 아니라 역할 쪽에 있으니, 함수의 허가 목록을 아무리 뒤져도 자취가 없어요.

이름에 둘 다 EventBridge 가 들어가는데 호출 경로가 다르고, 그래서 찾는 방법도 달라집니다. 거꾸로 찾기는 "허가가 필요한 트리거" 만 찾아 줘요. 허가가 필요 없는 트리거는 다른 방법으로 찾아야 하고, 그게 이 방법의 경계였습니다.

이번 스케줄은 그 다른 방법이 비쌀 게 없었어요. 3장의 목록에서 스케줄 창구만은 대상을 미리 넣지 않아도 되거든요. 계정의 스케줄을 통째로 받을 수 있으니 전수 조사라고 부를 만큼 넓지도 않습니다. 창구가 그런 모양이 아니었으면 이 하나는 목록에서 그냥 빠졌을 거예요.

그림 3. 방법의 경계를 아는 것이 방법을 아는 것만큼 중요하다

그 역할 자체는 소유하지 않기로 했어요. 콘솔이 스케줄을 만들 때 자동으로 붙여 준 서비스 역할이고, IAM 편입은 따로 떼어 둔 단계라서요. 코드에는 역할 ARN 을 문자열로 두고 "이건 다른 단계에서 담는다"를 주석에 적었습니다.

5. 담으면서 걸린 것 둘

한 경로의 양쪽이 서로 다른 스택에 갈렸다

토픽 구독 둘은 이미 다른 스택이 코드로 갖고 있었어요. 그런데 그 구독이 호출할 때 쓰는 허가는 아무도 안 갖고 있었습니다. 구독은 저쪽 스택에, 허가는 이쪽 스택에 남는 모양이 된 거예요.

소유 경계가 자원 단위라서 생기는 일인데, 둘 중 하나만 지워져도 결과는 똑같이 "조용히 실패" 입니다. 그래서 파일 맨 위에 여기 없는 구독 둘이 어느 스택 어느 파일에 있는지를 경로까지 적어 뒀어요. 나중에 이 파일만 보고 "구독이 빠졌네" 하고 다시 담으면 같은 구독이 두 벌이 되니까요.

토픽 하나는 소유가 아직 안 정해졌어요. 규약 태그가 없어서 어느 팀 것인지 판단할 근거가 없었거든요. 그래서 그 토픽의 구독만은 토픽 쪽이 아니라 함수 쪽 파일에 뒀습니다. 임시 배치라는 것도 같이 적었어요.

버킷 알림은 버킷 전체를 쥔다

📖 용어: 버킷 알림 설정
"이 버킷에 파일이 생기면 저기로 알려라" 를 적어 두는 설정이에요. 접두어로 범위를 좁힐 수 있습니다. 중요한 건 이게 버킷마다 하나라는 점이에요. 알림 세 줄이 있어도 설정 덩어리는 하나고, Terraform 리소스도 하나가 그 덩어리 전체를 소유합니다.

그래서 코드에 적지 않은 알림은 apply 가 지워요. 이번에 담은 건 CDN 접근 로그가 쌓이는 버킷의 알림 한 줄인데, 그 버킷 자체는 코드 밖에 있습니다. 남의 버킷 설정 전체를 우리 코드가 쥐는 모양이 되는 거예요.

같은 제약 때문에 9월 9일에는 반대로 결정한 적이 있어요. 다른 버킷의 알림 세 줄은 콘솔에 두고 IaC 는 호출 권한만 갖기로 했습니다. 그 버킷에는 우리 파이프라인과 무관한 접두어가 여럿 섞여 있어서, 모르는 알림을 지울 위험이 더 컸거든요.

이번에는 담았어요. 대신 커밋 본문에 확인 절차를 같이 적었습니다. "버킷 알림은 버킷의 알림 설정 전체를 소유하므로 plan 에서 다른 알림이 지워지는지 본다." 바뀌는 개수를 세는 게 아니라 지워지는 항목이 있는지를 보는 거예요. 그리고 파일에는 "알림을 더하려면 이 블록에 더한다"를 남겼습니다. 다음 사람이 콘솔에서 한 줄 더하면 그다음 apply 가 그걸 지우니까요.

⚠️ 트리거를 담을 때 밟기 쉬운 것
• 권한만 끊겨도 트리거는 발화한다. 트리거 쪽 지표만 보면 정상으로 보인다
• 역할로 부르는 트리거는 함수의 허가 목록에 나오지 않는다
• 버킷 알림은 버킷당 하나다. 코드에 없는 알림은 apply 가 지운다
• 호출 권한의 import 식별자는 콘솔이 붙인 UUID 라서 추측할 수 없다
• ALB 뒤에 붙은 함수의 호출 권한이 끊기면 사용자가 502 를 받는다

마지막 줄이 이날 가장 조심한 부분이에요. 청구서를 만드는 함수는 ALB 의 람다 타깃그룹 뒤에 붙어 있어서, 허가가 끊기면 내부 작업이 멈추는 게 아니라 요청이 오류로 돌아옵니다. 그 타깃그룹은 아직 코드 밖이라 ARN 을 문자열로 두고, 그 사실과 끊겼을 때 벌어지는 일을 주석에 적었어요.

12시 58분에 올린 편입 PR 은 14시 1분에 import 블록을 지우는 PR 로 닫혔습니다. 63분이에요. 블록을 왜 그 자리에서 지워야 하는지는 25편에 적어 뒀습니다.

✍️ 오늘의 요약
함수를 코드로 담았다는 말이 그 함수가 깨어나는 방식까지 담았다는 뜻은 아니었어요. 트리거는 한 종류가 아니라 여섯 갈래였고, 스케줄러부터 ALB 까지 서비스가 전부 달랐습니다. 열넷을 담았는데 그중 여덟은 트리거 자체가 아니라 트리거에게 내준 호출 허가였어요.

트리거 쪽에서는 셀 수가 없었습니다. 창구가 서비스마다 다른 것보다, 허가와 타깃과 구독 필터에는 ARN 이 없어서 태그 조회에도 참조 그래프에도 뜨지 않는 게 결정적이었어요. 그래서 함수의 리소스 정책에서 출발해 거꾸로 찾았습니다. 거기에는 누가 부르는지, 어느 실물에서 오는지, 그리고 그걸 가져올 import 식별자까지 한 줄에 같이 들어 있었어요.

다만 이 방법은 "허가가 필요한 트리거" 만 찾아 줍니다. 역할을 맡아서 부르는 스케줄러는 함수 쪽에 자취를 남기지 않아 따로 찾아야 했어요. 찾는 방법을 정할 때 같이 정해 둬야 하는 건, 그 방법이 무엇을 못 찾는지입니다.
