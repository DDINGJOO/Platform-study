10월 8일 오전에는 알림 함수, 로그 포워더, 리뷰 봇, 청구서를 만드는 Lambda 함수를 차례로 코드에 편입했어요. plan과 apply에서는 문제가 없었습니다.

12시 58분에는 "Lambda의 트리거를 편입한다"는 PR을 올렸어요. 함수는 이미 Terraform이 관리하는 자원 목록인 state에 들어와 있었지만, 함수를 호출하는 트리거와 호출 권한은 별도로 가져와야 했습니다.

스케줄과 이벤트 규칙부터 ALB 타깃그룹까지 호출 경로는 여섯 종류였어요. 서비스마다 따로 조회하는 대신, 먼저 함수의 리소스 정책에서 호출 권한과 연결된 자원을 확인했습니다.

1. 함수를 담았는데 깨우는 쪽이 왜 남았나 2. 트리거는 몇 갈래였고 무엇을 담았나 3. 왜 트리거 쪽이 아니라 함수 쪽에서 찾았나 4. 그 방법이 놓친 것 하나 5. 담으면서 걸린 것 둘

1. 함수와 트리거는 따로 편입해야 했다

📖 용어: 트리거
정해진 시각이 되거나 메시지·파일이 도착했을 때 함수를 호출하는 설정이나 자원을 통틀어 부르는 말이에요. 함수와 별도로 관리하며, 대개 다른 서비스에 속해 있어요.

25편에서도 다뤘듯이, 매일 실행하는 drift 잡은 코드로 관리하는 자원의 변경만 검사해요. 함수의 메모리나 타임아웃을 콘솔에서 바꾸면 다음 날 감지하지만, 코드 밖에 있는 시간별 호출 규칙을 꺼도 감지하지 못합니다.

이날은 호출 권한이 사라졌을 때 생길 실패도 고려했어요. 코드 주석 두 곳에 아래 경고를 남겼습니다. 한쪽에서는 "트리거" 대신 "규칙"이라고 적었어요.

⚠️ 권한이 끊기면 트리거는 발화하지만 호출이 거부된다. 조용히 실패한다.

트리거 설정이 정상이어도 함수 쪽에 호출 권한이 없으면 요청은 거부돼요. 규칙은 정해진 시각에 실행되고 실행 횟수 지표도 올라가지만, 함수는 실행되지 않습니다. 트리거의 실행 횟수만 확인해서는 이 실패를 알기 어려워요.

📖 용어: 호출 권한 (함수의 리소스 정책)
함수에 연결된 정책 문서로, 어느 서비스의 어떤 자원이 함수를 호출할 수 있는지 적혀 있어요. 각 권한 항목을 statement라고 부르고 이름(statement id)을 붙입니다. Terraform에서는 이 항목 하나가 aws_lambda_permission 리소스 하나에 대응해요.

2. 호출 경로 여섯 종류와 편입 자원 열넷

이날 편입한 자원은 열넷이에요. 종류별 개수는 다음과 같습니다.

호출 권한 8 Lambda 리소스 정책의 한 줄씩 스케줄 1 EventBridge Scheduler 이벤트 규칙 · 타깃 2 EventBridge 토픽 구독 1 SNS 로그 구독 필터 1 CloudWatch Logs 버킷 알림 설정 1 S3 ──── 14

토픽 구독은 토픽에 도착한 메시지를 지정한 함수로 보내는 설정이에요. 로그 구독 필터는 로그 그룹에 들어온 로그를 함수로 전달하는 설정이고요. 버킷 알림은 5장에서 따로 설명할게요.

열넷 중 여덟은 호출 권한이었어요. 트리거 설정 외에 함수 쪽 권한도 따로 관리해야 했고, 어떤 함수는 호출하는 자원이 둘이라 권한 항목도 둘이었습니다.

함수를 호출하는 쪽을 기준으로는 스케줄, 이벤트 규칙, 토픽 구독, 로그 구독, 버킷 알림, ALB의 람다 타깃그룹까지 여섯 종류였어요. 커밋 제목에 나열한 여섯 가지는 편입 자원의 종류라서 이 분류와는 달라요. 호출 권한을 포함하는 대신, 타깃그룹 자체를 가져오지 않은 ALB는 빠져 있습니다.

그림 1. 함수는 한 스택에서 관리하지만 호출 설정은 여러 서비스에 있어요

3. 태그 조회를 함수의 리소스 정책으로 보완했다

편입 대상을 찾을 때는 먼저 태그를 조회했어요. 앞선 작업에서 이름만으로 찾으면 대상을 놓치거나 다른 소유자의 자원을 포함할 수 있다는 걸 확인했거든요. 그런데 이번 열넷은 태그 조회 결과에 나오지 않았습니다. 그중 열하나는 독립된 ARN이 없었어요.

📖 용어: ARN
AWS 자원 하나하나에 붙는 전역 식별자예요. arn:aws: 로 시작하는 긴 문자열이고, 서비스·리전·계정·자원 이름이 콜론으로 이어져 있습니다. 태그를 거는 단위이자 태그로 찾아낼 때 돌려받는 단위이기도 해요.

호출 권한은 함수에 연결된 정책 문서의 항목이에요. 이벤트 타깃, 로그 구독 필터, 버킷 알림 설정도 독립된 ARN이 없습니다. 사용하던 태그 API는 ARN 목록을 반환하므로 이 항목들을 직접 찾을 수 없었어요. 남은 셋인 스케줄·규칙·토픽 구독도 태그 조회 결과에는 없었습니다. 태그 조회를 보완하려고 만든 참조 그래프 스크립트 역시 ARN을 따라가므로, 이 항목들을 직접 표시하지는 못했어요.

트리거가 속한 서비스에서 직접 찾으려면 다음 조회가 필요했어요.

# 트리거 쪽에서 세려면: 서비스마다 다른 창구를 두드린다 aws scheduler list-schedules aws events list-rules → list-targets-by-rule (규칙마다) aws sns list-subscriptions-by-topic (토픽마다) aws logs describe-subscription-filters (로그그룹마다) aws s3api get-bucket-notification-configuration (버킷마다) aws elbv2 describe-target-groups → describe-target-health (타깃그룹마다) # 함수 쪽에서 거꾸로: 한 번 aws lambda get-policy --function-name {함수}

서비스별 API를 쓰면 토픽·로그 그룹·버킷을 하나씩 지정해야 해요. 어떤 자원이 함수를 호출하는지 찾으려는 단계에서, 조회 대상을 먼저 알아야 하는 셈이었어요. 계정의 자원을 전부 순회할 수는 있지만 조회 범위가 넓어집니다.

함수의 리소스 정책은 이미 알고 있는 함수 이름으로 조회할 수 있었어요. 여기에는 서비스 이름, 호출 출처의 ARN(source ARN), 허용한 동작이 권한 항목별로 들어 있습니다.

참조 그래프 스크립트도 Lambda를 조회할 때는 이 방식을 사용하고 있었어요. 함수 설정과 이벤트 소스 매핑, 리소스 정책에서 ARN을 추출합니다. 호출 권한 자체는 그래프의 자원으로 표시하지 못해도, 정책에 적힌 호출 출처는 찾을 수 있었어요.

그림 2. 함수의 리소스 정책을 읽으면 서비스별 조회 대상을 좁힐 수 있어요

호출 권한의 import 식별자도 확인했다

호출 권한을 Terraform으로 가져올 때는 함수 이름과 statement id를 슬래시로 이은 식별자가 필요해요. 콘솔이 만든 statement id도 리소스 정책에서 확인했습니다.

{ "Sid": "lambda-{콘솔이 붙인 UUID}", ← import id 의 뒷부분 "Principal": { "Service": "events.amazonaws.com" }, ← 누가 부르나 "Condition": { "ArnLike": { "AWS:SourceArn": "arn:aws:events:{리전}:{계정ID}:rule/{규칙 이름}" } } ← 어느 실물인가 } import { to = aws_lambda_permission.{이름} id = "{함수 이름}/lambda-{콘솔이 붙인 UUID}" }

콘솔에서 트리거를 추가할 때 자동으로 붙인 UUID는 이름만 보고 추측할 수 없었어요. 함수 정책에서 이 값을 읽어 import 블록의 id에 넣었습니다. 호출 출처를 찾는 조회로 import에 필요한 값까지 얻은 거예요.

4. Scheduler는 별도로 조회해야 했다

함수 정책에서 호출 출처를 찾으려면 그 트리거의 권한이 정책에 있어야 해요. 이날 다룬 여섯 종류 중 Scheduler는 이 조건에 해당하지 않았습니다.

매일 오전 9시에 도는 스케줄이 그랬습니다. 그 파일에 이렇게 적어 뒀어요.

스케줄러는 역할로 호출하므로 Lambda 권한이 없다. 역할은 소유하지 않는다.

EventBridge 규칙이 Lambda를 호출할 때는 함수의 리소스 정책으로 권한을 부여해요. 저장소의 다른 스택에도 이 설명이 주석으로 남아 있고, Lambda 타깃의 역할 항목은 비어 있습니다. 반면 EventBridge Scheduler는 IAM 역할을 맡아 호출하므로, 그 호출 권한을 함수의 리소스 정책에서 찾을 수 없었어요.

이름에 모두 EventBridge가 들어가지만 권한을 부여하는 위치가 달랐어요. 함수의 리소스 정책에 권한을 두는 트리거는 정책에서 찾고, 역할로 호출하는 Scheduler는 별도로 조회해야 했습니다.

Scheduler는 스케줄을 하나씩 지정하지 않고도 목록을 받을 수 있어서 별도 조회가 간단했어요. 계정의 스케줄 목록을 조회해 이번 함수로 연결된 스케줄을 찾았습니다.

그림 3. 규칙은 함수 정책에서, 스케줄은 Scheduler에서 조회했어요

스케줄의 역할 자체는 이번에 편입하지 않았어요. 콘솔에서 스케줄을 만들 때 자동으로 연결한 서비스 역할이고, IAM 편입은 별도 단계로 정해 두었기 때문이에요. 역할 ARN은 문자열로 참조하고 이 범위를 주석에 적었습니다.

5. 구독과 버킷 알림의 관리 범위를 정했다

구독과 호출 권한을 서로 다른 스택에서 관리했다

토픽 구독 둘은 이미 다른 스택에서 관리하고 있었지만, 구독이 사용할 호출 권한은 코드로 관리하지 않고 있었어요. 기존 구독은 그대로 두고 호출 권한만 함수 쪽 스택에 편입했습니다.

구독이나 권한 중 하나가 삭제되면 함수 호출이 끊길 수 있어요. 파일 상단에 구독 둘을 관리하는 스택과 파일 경로를 적어, 호출 경로를 함께 확인할 수 있게 했습니다. 이 파일에 구독이 없다는 이유로 중복 편입하는 것도 피하려고요.

토픽 하나는 규약 태그가 없어 어느 팀에서 관리하는지 판단하기 어려웠어요. 그 토픽의 구독은 함수 쪽 파일에 두고 임시 배치임을 적었습니다.

버킷 알림 리소스는 전체 알림 설정을 관리한다

📖 용어: 버킷 알림 설정
버킷에 파일이 생성되는 등의 이벤트를 다른 서비스로 전달하는 설정이에요. 접두어로 대상 범위를 좁힐 수 있어요. 알림이 세 줄이어도 버킷당 설정은 하나이며, Terraform 리소스 하나가 그 설정 전체를 관리합니다.

이 리소스를 apply하면 코드에 없는 알림은 삭제돼요. 이번에는 CDN 접근 로그가 쌓이는 버킷의 알림 한 줄을 가져왔습니다. 버킷 자체는 코드 밖에 있지만 알림 설정 전체는 이 코드로 관리하게 되는 거예요.

같은 제약 때문에 9월 9일에는 다른 결정을 했어요. 다른 버킷의 알림 세 줄은 콘솔에 두고 IaC에서는 호출 권한만 관리하기로 했습니다. 그 버킷에는 해당 파이프라인과 무관한 접두어가 여럿 섞여 있어, 파악하지 못한 알림을 지울 위험이 컸거든요.

이번 버킷 알림은 편입하되, plan에서 다른 알림이 삭제되는지 확인하도록 커밋 본문에 적었어요. 파일에도 알림을 추가하려면 이 블록을 수정하라는 주석을 남겼습니다. 콘솔에서만 알림을 추가하면 다음 apply에서 삭제될 수 있기 때문이에요.

⚠️ 트리거 편입 시 확인할 항목
• 호출 권한이 없어도 규칙의 실행 횟수는 늘 수 있어요. 함수 호출 결과도 확인해야 해요
• IAM 역할로 호출하는 스케줄은 함수의 리소스 정책에 나오지 않아요
• 버킷 알림은 버킷당 하나의 설정이에요. 코드에 없는 알림이 삭제되는지 확인해야 해요
• 콘솔이 만든 호출 권한의 UUID는 정책에서 읽어 import 식별자에 넣어야 해요
• ALB 뒤에 연결된 함수의 호출 권한이 끊기면 사용자가 502 오류를 받아요

청구서를 만드는 함수는 ALB의 람다 타깃그룹에 연결돼 있어 호출 권한을 특히 주의해서 다뤘어요. 권한이 끊기면 사용자 요청에 오류가 반환되기 때문입니다. 타깃그룹은 당시 코드 밖에 있어 ARN을 문자열로 참조하고, 관리 범위와 권한 삭제의 영향을 주석에 적었습니다.

12시 58분에 편입 PR을 올리고, 63분 뒤인 14시 1분에는 import 블록을 삭제하는 PR을 올렸어요. 편입 뒤 블록을 바로 지운 이유는 25편에서 다뤘습니다.

✍️ 편입 결과와 확인 범위
Lambda 함수 편입 뒤 트리거와 호출 권한 열넷을 추가로 가져왔어요. 여덟은 호출 권한이었고, 함수의 리소스 정책에서 호출 출처와 import 식별자를 확인했습니다. IAM 역할로 호출하는 Scheduler는 별도로 조회했어요.

기존 구독을 관리하는 스택은 주석으로 연결하고, 버킷 알림은 plan에서 다른 알림이 삭제되는지 확인하도록 했어요. 스케줄의 IAM 역할과 ALB 타깃그룹은 이번 편입 범위에서 제외하고 ARN으로 참조했습니다.
