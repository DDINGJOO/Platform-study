6편. permissions boundary로 생성되는 IAM 역할의 권한 상한 정하기 ← 지금 이 글

GitHub Actions가 terraform apply를 실행할 때 쓰는 역할(이하 apply 역할)에 iam:*를 허용해야 했어요. 이 역할에 붙인 PowerUserAccess에는 IAM 권한이 빠져 있지만, Terraform은 대부분의 스택에서 역할을 만들어야 했기 때문이에요. 대신 파이프라인 자체 역할들(platform-iac-* 접두사)에 대한 iam:*를 Deny로 막았고, 처음에는 이 제한으로 충분하다고 봤어요.

설계 리뷰에서는 다른 이름으로 관리자 역할을 만들면 이 Deny의 적용을 받지 않는다는 지적이 나왔어요. 아래 네 단계로 기존 제한을 우회할 수 있었어요.

1. 새 관리자 역할로 환경 제한을 우회하는 경로

이 저장소는 단일 AWS 계정에서 dev와 prod를 세 가지 장치로 분리했어요. 환경별 state 파일 경로를 나누고, 리소스의 env 태그가 자기 환경과 다르면 접근을 막는 IAM Deny를 두고, prod 리소스에는 prevent_destroy를 설정했어요. 하지만 iam:*를 가진 역할이 새 관리자 역할을 만들고 그 역할로 전환하면 이 제한을 우회할 수 있었어요.

리뷰에서 확인한 시나리오는 이래요. ① iam:CreateRole로 totally-normal-app-role이라는 새 역할을 만들어요. 이 이름은 접두사 목록에 없어서 Deny 대상이 아니에요. ② 여기에 AdministratorAccess를 붙이고 신뢰 정책에 자기 자신을 넣어요. ③ sts:AssumeRole로 새 역할을 사용해요. 새 역할은 기존 apply 역할의 identity 정책에 있던 태그 Deny를 자동으로 물려받지 않아요. 새 역할 자체에 env 태그가 없어서 생긴 문제가 아니라, 새 주체에 기존 제한이 적용되지 않는 문제였습니다. ④ 그러면 state 버킷 정책을 바꾸거나 반대 환경 리소스를 삭제할 수 있어요.

모듈을 잘못 사용하거나 관리형 정책을 잘못 붙여도 이런 권한 구성이 생길 수 있어요. 역할 이름 목록을 늘려도 새 이름을 쓰면 같은 문제가 반복되므로, 목록을 넓히는 방법은 선택하지 않았어요.

그림 1. 새 이름의 관리자 역할로 기존 제한을 우회하는 경로

2. apply 역할의 sts:AssumeRole 차단

먼저 apply 역할에 sts:AssumeRole을 명시적으로 Deny했어요. 그러면 시나리오의 ③번 단계에서 다른 역할로 전환할 수 없어요. 당시 provider에는 assume_role 설정이 없었으므로 정상 동작에 쓰지 않는 권한을 회수한 것이에요.

이 설정만으로 새 관리자 역할의 생성을 막지는 못해요. 만들어진 역할이 다른 경로로 사용될 수 있어서, 생성되는 역할 자체에도 권한 제한이 필요했어요.

3. 생성되는 역할에 permissions boundary 적용

permissions boundary는 역할에 부여할 수 있는 권한의 상한을 정하는 정책이에요. boundary 자체가 권한을 주지는 않아요. boundary가 붙은 역할은 붙인 정책과 boundary가 둘 다 Allow한 작업만 할 수 있고, 어느 한쪽에서 Deny하면 거부돼요. AdministratorAccess를 붙여도 이 상한이 유지돼요. 다만 그 역할을 principal로 지목한 리소스 기반 정책 같은 예외는 있어요.

앞의 Deny는 정해 둔 이름에만 적용됐어요. boundary를 강제하면 역할 이름과 관계없이 같은 권한 상한을 적용할 수 있어요.

그림 2. 붙인 정책과 boundary가 함께 허용하는 권한

4. boundary 누락과 변경을 막는 조건

boundary 정책을 만들어도 역할에 붙이지 않으면 적용되지 않아요. apply 역할에서 다음 다섯 곳에 제한을 두어 boundary를 강제했어요.

🔒 boundary를 유지하기 위한 다섯 가지 제한
• 역할 생성 → CreateRole/CreateUser 를 iam:PermissionsBoundary 조건부로만 허용
• 정책 부착 → AttachRolePolicy/PutRolePolicy 에 같은 조건
• boundary 제거 → DeleteRolePermissionsBoundary 전면 Deny
• boundary 교체 → PutRolePermissionsBoundary 도 같은 조건부로만
• boundary 정책 수정 → 그 정책 ARN 의 CreatePolicyVersion 등 Deny
Deny iam:CreateRole, iam:CreateUser, iam:AttachRolePolicy, iam:AttachUserPolicy, iam:PutRolePolicy, iam:PutUserPolicy on * Condition StringNotEquals iam:PermissionsBoundary = arn:aws:iam::<계정ID>:policy/<env>-created-role-boundary

여섯 액션 모두 이 조건 키를 지원해요. 생성할 때는 요청에 담긴 boundary를, 정책을 붙일 때는 대상 역할에 이미 붙어 있는 boundary를 확인해요. 그래서 역할을 먼저 만들고 정책을 나중에 붙이는 방법으로도 이 제한을 피할 수 없어요.

이 조건에는 StringNotEquals를 사용했어요. 요청 컨텍스트에 조건 키가 없어도 true가 되므로, boundary를 지정하지 않은 CreateRole 요청도 Deny에 걸려요. 부정형 연산자는 비교할 키가 없는 경우에도 조건을 만족한다는 점을 고려해야 해요.

이전에 이 글에서 StringNotEqualsIfExists처럼 ...IfExists를 붙이면 조건 키가 없는 요청이 통과한다고 설명한 것은 오류였어요. Deny와 이 부정형 연산자를 함께 쓰면 키가 없어도 요청을 거부해요. 따라서 이 정책에 IfExists를 붙이는 것으로는 누락된 키를 허용할 수 없어요.

5. boundary에서 제한한 권한과 남긴 권한

boundary는 Allow * on *를 기본으로 두고 제한할 작업에 Deny를 추가했어요. 실제 권한은 역할에 붙인 정책이 정하고, boundary는 그 권한의 범위를 제한해요.

IAM 쓰기는 액션 이름의 접두사로 막았어요. 대상은 iam:Add* Attach* Create* Delete* Detach* Put* Remove* Set* Update* Upload*예요. 개별 액션을 열거하면 AWS가 새 액션을 추가할 때 누락될 수 있어요. 접두사로 지정하면 같은 동사로 시작하는 새 액션도 제한에 포함돼요.

접두사도 목록이므로 새로운 동사로 시작하는 쓰기 액션까지 막지는 못해요. 다만 액션 이름은 AWS가 정하고, 역할 이름은 역할을 만드는 쪽이 정해요. 앞의 이름 기반 Deny는 새 이름을 고르는 것만으로 피할 수 있었지만, 액션 접두사는 그런 방식으로 바꿀 수 없어요.

읽기(Get*/List*)와 iam:PassRole은 남겼어요. 이 파이프라인이 만드는 역할에는 boundary가 필수라서, PassRole로 다른 서비스에 전달해도 권한 상한이 유지돼요. 계정에 이미 있던 boundary 없는 역할은 예외예요. PassRole까지 막으면 ECS 태스크 역할 같은 정상적인 사용도 실패해요. 여기에 sts:AssumeRole Deny, state 버킷 전면 Deny, 반대 환경 태그 Deny를 더해 생성되는 역할에도 같은 격리 제한을 적용했어요.

생성된 역할이 다시 역할을 만들려 해도 boundary의 iam:Create* Deny에 막혀요.

6. 모듈에서 지킬 설정과 재검토 조건

이 설정을 적용한 뒤에는 모든 aws_iam_role에 permissions_boundary를 넣어야 해요. 빠뜨리면 apply가 CreateRole 단계에서 AccessDenied로 실패해요. boundary 없이 생성되는 것보다는 낫다고 판단했지만, 첫 모듈을 작성하는 사람이 이 조건을 모르면 실패 원인을 찾는 데 시간이 걸릴 수 있어요.

나중에 정상적인 기능을 위해 제한을 조정해야 할 수도 있어요. 크로스 계정 접근이 필요해지면 sts:AssumeRole Deny의 적용 범위를 좁혀야 해요. 설계 당시에는 실제 리소스가 0개였으므로, 엄격한 제한으로 시작하고 필요가 생길 때 조정하기로 했어요.

✍️ 오늘의 요약
apply 역할의 sts:AssumeRole을 막고, 생성되는 역할에는 permissions boundary를 강제했어요. AdministratorAccess를 붙이더라도 boundary의 권한 상한을 적용받도록 한 설정이에요.

boundary가 없는 역할의 생성과 정책 부착, boundary 제거·교체·수정도 제한했어요. 모듈에서는 permissions_boundary를 빠뜨리면 apply가 실패하고, 크로스 계정 접근이 필요해지면 관련 Deny를 다시 검토해야 해요.
