28편. 규약 태그가 없는 생성 요청을 IAM Deny로 거부하기 ← 지금 이 글

10월 2일, 운영 계정에 시크릿 하나가 새로 생겨 있었어요. 콘솔에서 사람이 만든 것이었습니다. 규약 태그 셋 중 하나도 붙어 있지 않았고, 대신 그 자리에서 즉석으로 지은 태그 둘이 붙어 있었어요. 이름에는 개발용이라는 표시가 들어 있었는데, 이 계정은 운영 계정입니다.

계정에 흩어져 있던 자원을 코드로 옮기는 편입 작업은 거의 끝나가고 있었어요. 그런데 작업하는 동안에도 코드 밖에서는 새 자원이 계속 생겼습니다. 기존 자원을 옮기는 것과 함께, 새로 만드는 자원에도 규약을 적용할 방법이 필요했어요.

그래서 사람이 규약 태그 없이 자원을 만들지 못하도록 할 방법 넷을 비교했어요. 조직 차원의 정책을 쓸 수 있는지, 태그 누락을 생성 시점에 막는지 확인한 뒤 사람의 IAM 권한에 거부 정책을 추가하기로 했습니다. 적용할 때는 액션의 조건 키 지원 여부와 그룹의 정책 개수 한도를 확인해야 했어요.

이 글에서 다룰 것은 이렇습니다.

1. 규약 태그가 없으면 무엇이 곤란한가 2. 막을 수 있는 자리 넷을 비교한 결과 3. 왜 한 번에 다 넓히지 않았나 4. 관리형 정책이 아니라 인라인 정책이어야 했던 이유 5. 막는 것과 세는 것을 함께 넣었다

1. 태그 하나가 빠지면 무엇이 곤란한가

다섯째 날에 만든 주간 인벤토리(22편)는 계정의 자원을 수집해 코드가 관리하는 것과 그렇지 않은 것으로 분류하는 스크립트예요. 태그는 그 분류에 쓰는 근거 중 하나입니다. 어느 팀과 서비스의 자원인지, 운영용인지 개발용인지 확인할 때 참고해요.

📖 용어: 규약 태그
이 저장소가 모든 자원에 붙이기로 정한 세 개의 태그 키예요. Team(어느 팀 것인가), Application(어느 서비스에 딸린 것인가), Environment(운영인가 개발인가)입니다. 코드로 만드는 자원에는 Terraform 이 자동으로 붙여 줘요.

다만 16편에서는 이름과 태그만으로 서비스의 자원을 판단하지 않기로 했어요. 이름에는 개발용이라고 적혀 있어도 운영 트래픽을 받고 있을 수 있습니다. 당시 태그 필터와 이름 검색으로는 필요한 자원을 놓치거나 이미 지워진 자원을 찾기도 했어요. 그래서 자원 사이의 실제 참조를 따라가며 서비스의 범위를 확인했습니다.

이번에 태그를 강제한다고 해서 태그만으로 자원의 용도를 확정하겠다는 뜻은 아니에요. 참조 추적과 태그를 어디에 쓸지 나누어 생각했습니다.

16편의 참조 추적은 서비스 하나를 세 번 살펴보며 범위를 직접 확인한 작업이었고, 며칠이 걸렸어요. 이 작업을 계정 전체에 매주 반복하기는 어렵습니다. 주간 인벤토리에서는 태그로 수백 개의 자원을 분류하고, 용도가 의심스러운 자원은 참조를 따로 확인하기로 했어요.

또 태그의 내용이 틀린 경우와 태그가 아예 없는 경우는 구분해야 해요. 16편에서 본 자원에는 태그가 있었지만 실제 용도와 어긋났습니다. 태그가 맞는지는 따로 확인해야 해도, 적힌 팀이나 서비스는 문의할 대상을 찾는 단서가 될 수 있어요.

이 정책이 보장하는 범위도 거기까지예요. 적용 대상인 생성 요청에는 규약 태그가 있어야 하지만, 그 내용이 실제 용도와 맞는지는 별도로 확인해야 합니다. 25편에서 했던 확인을 태그 강제가 대신해 주지는 않아요.

이번에 생긴 시크릿도 이름에는 개발용이라고 적혀 있었지만 운영 계정에 있었어요. 운영용인데 이름이 잘못됐는지, 개발용인데 계정을 잘못 골랐는지 확인이 필요했습니다. 규약 태그가 하나라도 있었다면 담당 팀이나 용도를 문의할 단서가 됐을 텐데, 세 태그가 모두 빠져 있어 만든 사람을 찾는 일부터 해야 했어요.

담당 팀이나 용도를 확인할 정보가 빠져 있어, 자원을 정리하기 전에 추가 확인부터 해야 하는 상황이었어요.

2. 태그 누락을 막을 방법 넷을 비교했다

ADR 에 선택지 넷을 적고 하나씩 봤어요.

첫째, 조직 정책입니다. 계정 전체에 권한의 상한을 씌우는 방법이에요. 가장 확실한 자리인데, 우리 계정에는 걸 수가 없었습니다.

📖 용어: SCP (서비스 제어 정책)
AWS Organizations 에서 조직의 관리 계정이 멤버 계정들에게 거는 권한 상한이에요. 멤버 계정 안에서 아무리 강한 권한을 줘도 이 상한을 넘지 못합니다. 다만 거는 쪽이 관리 계정이라, 멤버 계정에서는 자기 자신에게 걸 수 없어요.

우리 계정은 조직의 멤버 계정이었고, 관리 계정의 권한은 없었어요. 직접 SCP를 적용할 수 없어 이 방법은 제외했습니다.

둘째, 태그 정책입니다. 이름이 비슷해서 이게 답인 줄 알았어요. 조직이 제공하는 태그 표준화 기능인데, 실제로 하는 일은 태그 값의 형식을 맞추는 것이에요. 대소문자를 통일하고, 허용한 값 목록 밖의 값을 걸러 줍니다.

이번에 막으려던 것은 규약 태그를 빠뜨린 생성 요청이었어요. 검토한 태그 정책은 태그의 형식을 다루지만 태그 없이 만드는 요청은 막지 못해서 제외했습니다.

셋째, AWS Config의 설정 검사입니다. 규칙에 맞지 않는 자원을 찾는 기능으로, 필수 태그 규칙도 있어요. 다만 자원이 만들어진 뒤에 탐지하고 평가 건수에 따라 요금이 붙습니다. 생성 자체를 막을 수는 없어서 사후 점검 방법으로 검토했어요. 이번에는 새 서비스를 켜는 대신 기존 주간 인벤토리에서 누락 태그를 찾도록 했습니다(5절).

이 세 방법으로는 우리가 원하는 생성 시점의 제한을 적용하기 어려웠어요. 생성 전에는 대상 자원에 정책을 붙일 수도 없어서, 생성 요청을 보내는 쪽의 권한을 확인했습니다.

그래서 넷째 방법인 사람 IAM 그룹에 Deny 정책을 추가하기로 했어요. 사람이 콘솔이나 CLI로 보내는 생성 요청에 규약 태그가 빠졌으면 거부하는 방식입니다.

명시적인 Deny는 Allow보다 우선해요. 태그 누락 조건에 해당하면 관리자 권한이 있어도 해당 요청은 거부됩니다. 기존에 허용한 권한을 일일이 수정하는 대신 거부 정책을 추가할 수 있었어요.

6편에서 역할에 적용한 권한 상한과는 방식이 달라요. 그때는 역할에 붙은 정책과 권한 상한이 모두 허용하는 작업만 할 수 있게 했습니다. 이번에는 사람 IAM 그룹에 태그 조건에 따른 명시적인 거부를 추가했어요.

그림 1. 권한과 적용 시점을 비교해 사람 IAM 그룹의 Deny를 선택했어요

3. 조건 키를 지원하는 생성 액션만 추가했다

정책의 모양은 단순해요. 생성 요청에 Team 태그가 담겨 있지 않으면 거부합니다. 세 태그를 각각 따로 적었어요. 한 조건 블록 안에 여러 변수를 넣으면 전부 만족해야 걸리는 조건이 되는데, 우리는 하나라도 없으면 거부해야 하니까요.

statement { sid = "RequireTagTeamOnCreate" effect = "Deny" actions = ["secretsmanager:CreateSecret", ...] condition { test = "Null" variable = "aws:RequestTag/Team" values = ["true"] # 이 키가 비어 있으면 거부 } }

"이번 요청에 Team 이라는 태그가 담겨 있지 않으면 거부한다"는 뜻이에요.

📖 용어: aws:RequestTag
지금 보낸 요청에 담겨 온 태그를 가리키는 IAM 조건 키예요. 조건 키는 정책이 요청을 허용할지 판단할 때 들여다보는 값의 이름이에요. 이미 붙어 있는 태그(aws:ResourceTag)와 다릅니다. 자원이 아직 없는 생성 시점에 쓸 수 있는 건 이쪽뿐이에요.
📖 용어: Null 조건 연산자
조건 키가 요청에 들어 있는지 아닌지만 보는 연산자예요. 그 키가 아예 없으면 true, 값이 뭐라도 담겨 있으면 false 입니다. 값이 무엇인지는 보지 않아요.

여기서는 액션이 조건 키를 지원하는지 확인해야 했어요. 두 달 전 파이프라인 권한을 작성할 때도 같은 문제를 겪어 정책 파일에 주석을 남겼습니다. 액션이 제공하지 않는 조건 키로 거부 여부를 판단하면, 사용자가 조건을 충족할 방법이 없어 해당 작업을 계속 거부할 수 있다는 내용이었어요.

모든 액션이 aws:RequestTag 를 받는 건 아니에요. 생성할 때 태그를 같이 받도록 만들어진 액션만 이 키에 값을 채워 줍니다. 받지 않는 액션은 사용자가 태그를 아무리 잘 붙여 보내도 이 키가 비어 있어요.

조건 키가 제공되지 않으면 Null 조건은 항상 참이 됩니다. 사용자가 태그를 보완해도 이 정책의 거부를 피할 수 없어요. 이 상태로 정책을 적용하면 태그 입력을 강제하는 대신 해당 액션을 사용할 수 없게 됩니다.

두 달 전에는 StringNotEquals, 이번에는 Null 연산자를 썼어요. 두 경우 모두 조건 키가 요청에 없을 때 거부 조건이 참이 된다는 점을 확인해야 했습니다.

그림 2. 조건 키를 받지 않는 액션을 넣으면 Null 조건이 늘 참이 된다

그래서 액션을 한 번에 넓히지 않았어요. 10월 2일 1차에는 시크릿 생성 하나만 넣었습니다. 그리고 오늘 2차로 다섯 서비스를 더했어요. 하나씩 공식 문서에서 조건 키 지원 여부를 확인하면서요.

1차 (10-02) secretsmanager:CreateSecret 2차 (10-07) ecr:CreateRepository sns:CreateTopic sqs:CreateQueue logs:CreateLogGroup lambda:CreateFunction 뺀 것 s3:CreateBucket 생성 시 태그 조건을 받는지 확인하지 못했다

S3는 당시 생성 액션의 태그 조건 지원 여부를 확인하지 못해 제외했어요. 제외하면 태그 없이 버킷이 만들어질 수 있지만, 잘못 포함하면 정책 적용 대상자는 태그를 보완해도 버킷을 만들지 못할 수 있습니다. 생성 요청을 보내기 전까지 문제가 드러나지 않을 수도 있어서, 지원 여부를 확인한 액션만 추가했어요.

💡 실무에서는
• 액션마다 어떤 조건 키를 받는지는 AWS 의 Service Authorization Reference 에 서비스별로 적혀 있어요. 추측하지 말고 거기서 확인합니다
• 태그를 붙이고 떼는 액션 이름이 서비스마다 달라요. 어떤 서비스는 TagResource 한 개지만, 어떤 서비스는 큐 전용 이름을 따로 쓰고, 어떤 서비스는 두 이름을 둘 다 받습니다. 하나만 막으면 나머지로 지나갑니다
• 생성만 막으면 만들고 나서 태그를 떼면 그만이에요. 그래서 떼는 액션도 같이 막았고, Environment 값이 규약 밖이면 거부하는 조건도 넣었습니다

그리고 Terraform 의 apply 역할과 서비스 역할에는 이 정책을 붙이지 않았어요. 코드로 만드는 자원에는 이미 규약 태그가 자동으로 붙으니까요. 사람이 쓰는 경로에만 걸면 됩니다.

4. 관리형 정책이 아니라 인라인 정책이어야 했다

1차 apply 는 중간에 멈췄어요. 정책 문서는 만들어졌는데, 그걸 그룹에 붙이는 단계에서 이 오류가 났습니다.

Error: LimitExceeded: Cannot exceed quota for PoliciesPerGroup: 10

그룹 하나에 붙일 수 있는 관리형 정책이 열 개까지인데 이미 꽉 차 있었다는 뜻이에요.

📖 용어: 관리형 정책과 인라인 정책
관리형 정책은 독립된 문서로 한 번 만들어 여러 곳에 붙여 쓰는 방식이고, 인라인 정책은 그 그룹이나 사용자 안에 직접 적어 넣는 방식이에요. 관리형은 "몇 개까지 붙일 수 있나"의 한도가 있고, 인라인은 그 한도에 들지 않는 대신 글자 수 한도가 있습니다.

이때 apply는 앞서 성공한 작업을 되돌리지 않았어요. 정책 문서는 만들어졌고 일부 그룹에는 붙었지만, 나머지 그룹에는 붙지 않은 상태로 멈췄습니다. 따라서 apply가 실패했다는 결과와 함께, 어느 그룹까지 정책이 적용됐는지도 확인해야 했어요.

대상 그룹 전부를 인라인 정책으로 통일했어요. 인라인 정책은 관리형 정책의 부착 개수 한도에 포함되지 않고, 이 문서는 그룹당 글자 수 한도보다 작았습니다. 중복으로 관리하지 않도록 기존 관리형 정책과 부착 설정은 제거했어요.

그 전환 apply 에도 공백이 있었어요. 관리형 쪽을 지우고 인라인 쪽을 만드는 사이 몇 초 동안은 강제가 없습니다. 그래서 PR 에 기대하는 plan 의 모양을 미리 적었어요. 무엇이 새로 생기고 무엇이 지워지는지, 그리고 그 사이에 몇 초의 공백이 있다는 것까지요.

⚠️ 주의: 계정 한도는 plan 에 뜨지 않는다
plan 은 코드의 문법과 참조 관계를 확인하고, 실물과 비교해 무엇이 바뀔지를 보여 줍니다. 그런데 "이 그룹에 정책을 하나 더 붙일 자리가 남았는가" 같은 계정 쪽 한도는 실제로 붙여 봐야 압니다. 그래서 apply 에서 처음 드러나요. 가드를 거는 PR 일수록 apply 가 중간에 멈추면 어떤 상태가 남는지를 먼저 적어 두는 편이 좋습니다.

5. 정책 적용 범위 밖의 누락은 인벤토리에서 찾았다

이 정책이 다루지 못하는 범위는 ADR의 「반대 의견」에 적어 뒀어요.

그룹 단위로 적용하므로 대상 그룹 밖의 사람에게는 이 정책이 적용되지 않아요. 조건 키 지원 여부를 확인하지 못해 제외한 액션도 있고, 정책 적용 전에 만들어진 자원의 태그도 그대로입니다.

그래서 같은 날 주간 인벤토리에도 조건을 추가했어요. 코드가 관리하지 않는 것으로 분류된 자원 중 규약 태그가 하나라도 빠진 것을 요약 표와 결과 파일에 표시하도록 했습니다.

다만 인벤토리는 자원 종류마다 수집하는 정보가 달라요. 태그를 가져오지 않는 종류까지 포함하면 실제 태그 유무와 관계없이 전부 "태그 없음"으로 분류됩니다. 그래서 태그가 수집된 적 있는 종류만 검사하도록 했어요.

# 태그가 한 건이라도 수집된 적이 있는 종류만 본다 tagged_kinds = {종류 | 그 종류에서 태그가 하나라도 수집됐다} for 자원 in 전체: if 자원.분류 not in (코드 밖) : 건너뛴다 if 자원.종류 not in tagged_kinds: 건너뛴다 # 수집 안 하는 종류 빠진 태그가 있으면 → 목록에 담는다 # 그래서 이 숫자는 상한이 아니라 하한이다

태그를 수집하는 종류만 보기 때문에, 이 목록은 실제보다 적게 나옵니다. 그래서 요약 표의 설명에 "태그를 수집하지 않는 종류는 빠져 있어 실제는 이보다 많을 수 있다"고 적었어요. 10월 5일자 인벤토리에 돌려 보니 61건이 나왔습니다. 시작 템플릿이 가장 많았고, 그다음이 게이트웨이와 키페어였어요.

21편에서 점검 목록과 실제 수정 결과를 구분했던 것처럼, 이번에도 집계 범위를 함께 적었어요. 61건은 전체 누락 건수를 확정한 값이 아니라, 검사 대상에서 확인된 최소 건수입니다.

그림 3. 생성 시 제한과 기존 자원의 사후 점검을 함께 적용했어요

IAM 정책은 적용 대상자의 생성 요청을 제한하고, 인벤토리는 이미 존재하는 자원의 태그 누락을 보여 줍니다. 생성 제한만으로는 기존 자원을 점검할 수 없고, 사후 점검만으로는 태그 없는 새 자원의 생성을 막지 못해서 함께 적용했어요.

⚠️ 주의: 권한 오류만으로는 태그 누락을 알기 어렵다
콘솔에서 태그를 빠뜨리고 생성을 요청하면 「권한이 없습니다」라는 메시지가 나와요. 이 메시지만으로는 태그를 보완해야 한다는 것을 알기 어렵습니다. ADR의 반대 의견에 이 점을 적고, 정책 이름과 태그 입력 안내를 미리 알려 두기로 했어요.
✍️ 적용 결과와 점검 범위
사람 IAM 그룹에 규약 태그가 없는 생성 요청을 거부하는 정책을 적용했어요. 조건 키를 지원하는 액션만 포함했고, 관리형 정책은 그룹당 부착 개수 한도에 걸려 인라인 정책으로 전환했습니다.

태그가 있다는 것과 내용이 맞다는 것은 별도로 확인해야 해요. 대상 그룹 밖의 사람, 제외한 생성 액션, 기존 자원은 이 정책만으로 다룰 수 없어 주간 인벤토리에서 태그 누락을 찾도록 했습니다. 10월 5일자 자료에서 확인한 61건은 태그 수집이 가능한 종류에 한정한 하한이에요.
