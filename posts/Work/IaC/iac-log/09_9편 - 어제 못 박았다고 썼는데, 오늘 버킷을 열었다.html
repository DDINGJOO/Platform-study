9편. 새 스택의 잠금 오류로 plan IAM 권한을 넓힌 이유 ← 지금 이 글

어제 이 시리즈 5편에서는 잠금 파일 이름을 IAM 정책에 직접 지정했어요. "파일 이름 한 개 차이로 계획만 세우는 역할과 바꿀 수 있는 역할이 갈려요."라고 설명하며, 이 정책을 최종 형태라고 적었습니다.

그 글을 올린 다음 날, 같은 정책을 두 번 넓혔어요. 낮 12시 54분에는 프리픽스 단위로 넓혔고, 오후 3시 30분에는 버킷 전체로 넓혔습니다. 두 커밋 사이는 두 시간 반 남짓입니다.

잠금 파일에만 쓰기를 허용한다는 의도는 유지했어요. 다만 파일명을 하나로 고정한 정책은 새 스택을 추가할 때마다 수정해야 했고, 그 수정은 수동 apply가 필요했어요. 접근 범위와 정책을 유지하는 절차를 함께 검토하게 됐습니다.

1. 잠금 파일 하나에만 쓰기를 허용한 정책

5편에서는 terraform plan도 state 잠금 파일(<state 키>.tflock)을 만들고 지우므로 읽기 전용 권한만으로 실행할 수 없다고 설명했어요. ReadOnlyAccess만 부여하면 잠금에서 실패하고, 이를 피하려고 -lock=false를 계속 사용할 우려가 있었어요. 그래서 인프라 전반은 읽되, 쓰기는 잠금 파일에만 허용했습니다.

당시에는 쓰기 권한의 대상을 잠금 파일 하나로 지정했어요. 프리픽스를 env/{환경}/*로 지정하면 같은 경로의 terraform.tfstate까지 덮어쓸 수 있으니, 쓰기를 허용할 파일 이름을 직접 적었습니다. 프리픽스는 S3 객체 키에서 경로 앞부분을 뜻해요.

이 정책은 state 본문에 대한 쓰기를 막았어요. 하지만 환경마다 잠금 파일 이름이 하나라는 전제도 함께 두고 있었고, 새 스택을 추가하면서 그 제약이 드러났습니다.

2. 새 스택에서 잠금 파일 생성이 거부됐어요

알럿 감지 체계를 별도 스택으로 추가하면서 state도 따로 만들었어요. 새 state 키는 env/{환경}/alerting.tfstate였고 잠금 파일 이름은 alerting.tfstate.tflock이 됐어요. 정책에 허용한 terraform.tfstate.tflock과 달라서 잠금 파일을 만들지 못했습니다.

Error acquiring the state lock Error message: operation error S3: PutObject, api error AccessDenied

state 읽기는 env/{환경}/*에 허용돼 있어 통과했지만, 잠금 파일을 만드는 요청은 거부됐어요. 첫 줄의 Error acquiring the state lock만 보면 다른 실행이 잠금을 사용 중이거나 이전 잠금이 남았는지부터 확인하기 쉬워요. 여기서는 아래에 나온 PutObject AccessDenied가 진단에 필요했습니다. S3 객체 생성 권한이 거부됐다는 뜻이에요.

그전에 state 경로를 정할 때도 확인을 빠뜨렸어요. 원래 설계 문서의 알럿 state 키는 alerting/terraform.tfstate였는데, 이 프리픽스는 기존 권한 범위 밖이었어요. 그래서 env/{환경}/ 아래로 옮기면서 프리픽스가 같으면 기존 권한을 그대로 쓸 수 있다고 판단했습니다.

읽기 권한은 프리픽스 단위였지만 잠금 파일의 쓰기 권한은 파일명 단위였어요. 읽기와 쓰기에 서로 다른 제한이 있다는 점을 놓쳤습니다. 알럿 스택 ADR의 결정 2에도 "프리픽스만 보고 권한 변경 없이 된다고 판단한 것이 틀렸다."라고 남겼어요.

⚠️ 잠금 에러를 만나면 볼 순서
Error acquiring the state lock 은 잠금 획득에 실패했다는 뜻이에요. 아래 API 오류로 원인을 확인해요.
• ConditionalRequestConflict / Lock Info 가 붙어 있다면 잠금 경합이나 기존 잠금 정보를 확인해요
• PutObject AccessDenied 가 붙어 있다면 객체 생성 권한이 거부된 것이므로 IAM 정책을 확인해요
• 이 사례처럼 읽기는 되는데 잠금만 안 된다면 잠금 파일 리소스 ARN의 허용 범위도 확인해요

3. 정책을 바꿀 때마다 로컬 apply가 필요했어요

잠금 파일 권한은 정책 한 줄을 수정해 해결할 수 있었어요. 하지만 이 정책을 실제 환경에 반영하는 절차는 자동화돼 있지 않았습니다.

이 저장소의 bootstrap/은 CI가 쓸 OIDC 역할과 IAM 정책을 담고 있어요. 1편에서 정한 설계에 따라 CI의 apply 대상에서는 제외했어요. CI가 자기 권한과 state 버킷을 직접 변경할 수 있으면, CI가 침해됐을 때 그 권한과 버킷까지 변경할 수 있기 때문이에요.

따라서 IAM 정책을 바꾸면 자격증명을 가진 사람이 로컬에서 apply해야 해요. PR 검사를 통과해도 정책은 반영되지 않아요. 당시 이 작업을 할 자격증명을 가진 사람은 사실상 한 명이었습니다.

그게 하루에 다섯 번 발생했어요.

1) 최초 생성 — 2) IAM description 에 한글 → CreateRole 거부 작성 실수 3) OIDC sub 가 불변 ID 형식이라 신뢰 정책 불일치 사전 확인 부족 4) 잠금 파일 권한이 파일명으로 고정 프리픽스를 좁게 박음 5) 태그 키를 조직 스키마로 바꾸며 IAM Deny 도 교체 태그와 IAM 결합 6) bootstrap 을 drift 감지에 넣으려면 plan 역할이 bootstrap/ 프리픽스를 읽어야 함 프리픽스를 좁게 박음 ← 오려던 참

4번과 6번은 state 접근 대상을 제한한 방식에서 생겼어요. 새 잠금 파일명이나 프리픽스를 사용할 때마다 정책 수정과 수동 apply가 필요했습니다. stacks/network, stacks/data도 추가할 예정이어서 같은 절차가 반복될 수 있었어요.

반복 작업 중에는 최신 코드를 받지 않고 apply한 일도 있었어요. ADR 원문에는 이렇게 적었습니다.

"오늘 실제로 옛 코드로 apply 해서 0 changed 가 나왔고, 그걸 알아채는 데 왕복 세 번이 걸렸다."

당시에는 옛 코드로 apply해서 0 changed를 보고도 변경이 반영되지 않은 이유를 바로 알아채지 못했어요. CI를 다시 실행해 실패를 확인하고 로컬 apply로 돌아오는 일을 세 번 반복했습니다.

정책의 접근 범위뿐 아니라 변경을 반영할 횟수와 수동 작업에서 생기는 실수도 고려해야 했어요.

4. plan의 읽기와 잠금 권한을 넓혔어요

변경한 권한은 plan 역할의 state 읽기와 잠금 파일 쓰기예요.

# plan 역할 — 넓힘 s3:GetObject env/{환경}/* → {버킷}/* s3:PutObject + s3:DeleteObject env/{환경}/*.tflock → {버킷}/*.tflock s3:ListBucket prefix 조건 → 조건 없음 # apply 역할 — 그대로 s3:PutObject + s3:DeleteObject env/{환경}/* (안 건드림)

정책 문의 이름도 바꿨어요. ReadOwnState는 ReadAnyState로, WriteOwnLockfile은 WriteLockfiles로, ListOwnPrefix는 ListBucket으로 변경했습니다. 각 환경의 프리픽스에 한정하던 plan 접근을 버킷 전체로 넓힌 것에 맞춘 이름이에요.

state 본문에 대한 쓰기 제한은 유지했어요.

apply 역할의 쓰기는 여전히 env/{환경}/* 안에 제한했어요. dev apply 역할이 prod state를 덮어쓰지 못하도록 한 경계예요.

plan의 쓰기 대상도 {버킷}/*.tflock으로 제한했어요. {버킷}/* 전체에 쓰기를 허용하지 않았으므로 .tflock으로 끝나지 않는 state 본문은 plan 역할로 변경할 수 없어요. 5편에서 우려한 state 덮어쓰기를 막기 위한 제한이에요.

📌 5편의 설명에서 바뀐 부분
무효 • "쓰기 권한의 대상이 잠금 파일 하나다" → 이제 버킷 안의 모든 .tflock 이에요
무효 • "자기 프리픽스 안에서만 읽는다" → plan 은 이제 버킷 전체를 읽어요
무효 • "최종 형태는 …입니다" → 다음 날 정책을 수정했어요
유효 • state 본문 덮어쓰기 권한까지 넓히지 않도록 확장자 제한을 남겼어요
유효 • "plan 은 순수 ReadOnly 가 될 수 없다" → 이 구성은 잠금 파일 쓰기 권한도 필요해요

쓰기 대상을 잠금 파일로 제한한다는 원칙은 유지했고, 그 대상을 파일명 하나에서 확장자가 같은 파일들로 바꿨어요.

읽기 범위를 넓힌 데 따른 위험도 ADR에 남겼어요. 당시에는 state에 시크릿을 넣지 않는다는 전제에 의존했고, 이를 강제할 수단은 없었어요. 이 전제가 지켜지지 않으면 plan 역할이 전 환경의 state를 읽을 수 있는 만큼 시크릿의 노출 범위도 커집니다.

5. 접근 범위와 함께 검토한 유지 절차

처음에는 허용 범위를 얼마나 좁힐 수 있는지에 집중했어요. 파일명까지 지정하면 새 스택을 추가할 때 어떤 절차가 필요한지는 충분히 고려하지 않았습니다.

아래 식은 이 사례의 유지 부담을 설명하기 위해 정리한 것이에요.

경계의 실제 비용 = 그 경계를 유지하는 데 드는 수정 횟수 × 그 수정을 할 수 있는 사람의 수의 역수 수정 횟수 : 스택이 늘 때마다 1회 (앞으로 network, data 예정) 고칠 수 있는 사람 : 1명 (bootstrap 은 CI apply 대상이 아님) 1회당 비용 : 로컬 apply 왕복 + 그 안에서 실수할 확률

이 사례에서는 정책을 반영할 사람이 한 명이었고, 새 접근 대상이 생길 때마다 수동 apply가 필요했어요. 반복 중에 옛 코드를 적용한 일도 있었으니, 수정 횟수를 줄일 방법을 검토할 이유가 있었습니다. 5편에서 우려했던 -lock=false 사용처럼 절차를 우회할 가능성도 함께 고려했어요.

정책을 검토하면서 누가 변경을 반영할 수 있는지, 스택이 늘 때마다 정책도 수정해야 하는지를 함께 확인했어요.

apply 역할의 env/{환경}/*는 새 스택을 같은 프리픽스에 추가해도 수정할 필요가 없었어요. 그래서 이 제한은 유지했습니다. 권한을 넓힐지는 수동 작업의 빈도와 추가로 허용되는 접근 범위를 함께 비교해 결정했어요.

6. ADR에 재검토 조건을 남겼어요

5편에서는 정책을 최종 형태라고 설명했지만, 다음 날 새 스택을 추가하면서 수정했어요.

파일명을 하나로 고정한 정책에는 환경마다 스택이 하나라는 전제가 있었어요. 당시에는 그 전제를 따로 적지 않았습니다. 스택이 늘어날 가능성을 고려했다면 잠금 파일의 허용 범위도 함께 검토할 수 있었어요.

이번 결정은 ADR에 남기고, 다시 검토할 조건도 아래와 같이 적었어요.

재검토해야 할 조건 - state 에 시크릿을 넣어야 하는 요구가 생길 때 → 되돌리거나 해당 스택만 별도 버킷으로 분리 - 저장소 기여자가 admin 5명을 넘어설 때 → plan artifact 노출 범위를 다시 계산 - bootstrap 변경 빈도가 월 1회 이하로 안정될 때 → 굳이 넓게 둘 이유가 줄어든다

시크릿 저장 요구나 기여자 범위, bootstrap 변경 빈도가 달라지면 접근 범위를 다시 판단할 수 있도록 조건을 명시했어요.

계정을 dev/prod로 분리하는 경우에도 권한 경계와 bootstrap 변경 절차를 다시 검토해야 해요. 이 글의 판단은 당시 한 계정에서 운영하던 구성과 수동 apply 절차를 전제로 했어요.

✍️ 오늘의 요약
새 스택의 잠금 파일 이름이 기존 정책과 달라 S3 객체 생성이 거부됐어요. 정책 수정에는 bootstrap의 수동 apply가 필요했고, 반복 과정에서 옛 코드를 적용해 0 changed를 보고도 반영 누락을 알아채지 못한 일이 있었어요.

plan의 읽기는 버킷 전체로, 쓰기는 버킷 안의 .tflock 파일로 넓혔어요. apply의 환경별 state 쓰기 제한은 유지하고, 읽기 범위를 넓힌 위험과 재검토 조건은 ADR에 남겼습니다.
