23편. PR 라벨로 plan을 생략하지 않고 호출 관계로 범위를 정한 이유 ← 지금 이 글

일요일 오후에 계정의 리소스를 전수로 세는 인벤토리 스크립트를 추가하고, 린트 스크립트에 세 줄을 더한 PR을 올렸어요. Terraform 코드는 바꾸지 않았는데 체크 목록에는 plan이 서른세 개 나타났습니다. 저장소에 있는 스택 전부였어요.

나흘 전에도 파이썬 스크립트 한 줄을 고친 PR에서 체크 서른일곱 개가 실행됐어요. 그때는 .github/ 디렉터리, 이번에는 scripts/ 디렉터리가 원인이었습니다. plan 대상을 고르는 스크립트는 두 경로 모두 영향 범위를 알 수 없는 것으로 분류하고 있었어요.

처음에는 PR에 plan:skip을 붙이면 plan을 건너뛰게 하려 했어요. 하지만 라벨을 잘못 붙였을 때 Terraform 변경까지 검증에서 빠질 수 있어서 만들지 않았습니다. 대신 워크플로에서 스크립트를 호출하는 잡을 읽어 영향 범위를 구분했어요. 같은 판정 스크립트는 머지 뒤 점검에도 사용했는데, 그쪽은 취소된 plan이 남긴 잠금 파일 때문에 drift 점검까지 멈춘 것이 계기였습니다.

🧭 이 글에서 다룰 것
• 스크립트만 고친 PR에서 왜 전 스택 plan이 실행됐을까요?
• plan을 생략하는 라벨은 왜 제외했을까요?
• 별도 목록 없이 스크립트를 어떻게 분류했을까요?
• 취소된 plan의 잠금 파일은 후속 점검에 어떤 영향을 줬을까요?

1. 경로만 보고는 스크립트가 무엇을 하는지 모른다

이 저장소의 PR 검사는 바뀐 파일 목록을 보고 plan을 실행할 스택을 골라요. select-plan-stacks.py가 이 판정을 맡습니다.

📖 용어: plan (terraform plan)
코드와 실제 클라우드 상태를 비교해서 "적용하면 무엇이 생기고 바뀌고 지워지는지"를 미리 계산하는 명령입니다. 이 저장소에서는 PR 마다 plan 결과가 필수 체크로 붙고, 리뷰어는 그 결과를 보고 머지를 판단해요.
📖 용어: 스택 (stack)
state 파일 하나를 공유하는 Terraform 디렉터리 하나입니다. plan 과 apply 는 스택 단위로 돌아요. 이 글의 시점에 저장소에는 스택이 서른셋 있었습니다.

스택 디렉터리 안의 파일이 바뀌면 그 스택만 실행하고, 문서만 바뀌면 plan을 실행하지 않아요. 어느 스택에도 속하지 않는 파일이 바뀌면 전 스택을 실행합니다. 공용 모듈이 대표적이에요. 모듈 하나를 고치면 그 모듈을 쓰는 여러 스택의 plan이 달라질 수 있으니까요.

바뀐 파일 고른 스택 stacks/<서비스>/prod/main.tf 그 스택 하나 docs/adr/x.md 없음 modules/cw-alarm/main.tf 전 스택 (영향 범위를 모른다) scripts/아무거나 전 스택 (영향 범위를 모른다)

마지막 줄처럼 scripts/ 아래 파일은 모두 영향 범위를 알 수 없는 것으로 분류됐어요.

영향 범위를 모르면 전부 실행한다는 규칙은 한 달 반 전에 결정 기록(ADR)으로 남겼어요. 범위를 줄이지 못하면 plan 실행 비용이 더 들지만, 잘못 줄이면 검증되지 않은 변경이 main에 들어갈 수 있습니다. 후자의 위험이 더 크다고 판단해서 근거가 부족할 때는 전 스택을 선택하도록 했어요.

이 원칙을 유지하면서도 scripts/ 안의 파일을 구분할 필요가 있었어요. plan 대상을 고르는 스크립트는 모든 스택의 plan에 영향을 줄 수 있지만, 린트 잡에서만 쓰는 검사 스크립트나 인벤토리 스크립트는 역할이 다릅니다. 기존 판정은 이 차이를 반영하지 않았어요.

나흘 전 .github/의 분류 문제는 이름 규약으로 해결했어요. Terraform을 실행하는 워크플로에는 terraform- 접두사를 붙이고, 나머지는 plan과 무관한 것으로 보는 규칙입니다. apply에서 호출하는 공용 워크플로 하나만 예외로 명시했어요. 이름과 내용이 어긋나면 린트에서 확인하도록 했습니다. scripts/에도 같은 방식이 맞는지 검토하다가 라벨을 사용하는 안이 나왔어요.

2. plan을 생략하는 라벨을 만들지 않은 이유

📖 용어: PR 라벨 (label)
GitHub PR에 사람이 붙이는 분류 표시예요. 워크플로가 라벨을 읽고 동작을 바꿀 수 있습니다. 이 저장소는 이미 삭제를 허용하는 allow-destroy 라벨을 쓰고 있었어요(3편).

결정 기록에는 검토한 선택지가 셋 남아 있어요.

1) scripts/ 에서 plan 과 무관한 파일을 목록으로 적는다 -> 탈락. 목록은 파일이 늘면 낡고, 낡은 목록은 조용히 틀린다 2) 라벨로 plan 범위를 정한다 (plan:skip, plan:stacks=... 포함) -> 좁히는 라벨은 탈락. plan:skip 을 잘못 붙이면 Terraform 변경이 plan 없이 초록불이 된다 3) 파일이 바닥을 정하고, 라벨은 넓히기만 한다 scripts/ 는 워크플로를 읽어서 부르는 잡으로 가른다 -> 채택

두 번째 안은 라벨을 잘못 붙였을 때의 결과를 보고 제외했어요. 사람이 붙이는 라벨에는 실수가 생길 수 있으니, 그 실수가 검증 범위에 어떤 영향을 주는지 비교했습니다.

예를 들어 스택 하나만 바뀐 PR에 plan:all을 잘못 붙이면 plan 서른세 개가 실행돼요. 몇 분이 더 걸리고 러너(CI 잡을 실행하는 머신) 사용 시간이 늘지만, 검증이 빠지지는 않습니다.

반대로 스택 파일을 고친 PR에 plan:skip을 잘못 붙이면 plan이 실행되지 않은 채 필수 체크가 통과할 수 있어요. 리뷰어 화면에서는 실제로 변경이 없는 경우와 구분하기 어렵습니다. plan으로 확인하지 않은 변경이 main에 들어가고 apply에서야 드러날 수 있어서, 이 방식은 채택하지 않았어요.

그림 1. 범위를 넓히면 실행 시간이 늘고, 잘못 줄이면 검증이 빠져요

결정 기록에 남긴 라벨은 셋이에요. plan:all은 파일과 상관없이 전 스택을 실행하고, inventory는 해당 PR에서 계정 인벤토리를 실행합니다. 편입 PR(콘솔로 만든 자원을 코드로 가져오는 PR)에서 코드 밖의 자원 목록이 실제로 줄었는지 확인할 때 써요. 기존의 삭제 허용 라벨 allow-destroy도 유지했습니다. plan 범위를 줄이는 라벨은 두지 않았어요.

결정 기록에는 범위를 줄이는 라벨이 필요해지면 이 ADR부터 재검토하도록 적었어요. 라벨 하나를 추가하는 일이 검증 범위에 대한 정책 변경이라는 점을 명시한 것입니다.

3편에서 뺀 트리거를 다시 넣었다

3편에서는 라벨을 붙일 때마다 plan을 다시 실행하는 비용 때문에 워크플로 트리거에 labeled를 넣지 않았어요. 이번에는 plan:all을 붙이는 것만으로 전 스택 실행을 요청할 수 있도록 추가했습니다. 별도로 Re-run 버튼을 눌러야 한다면 그 단계를 빠뜨렸을 때 요청이 실행되지 않기 때문이에요.

이 설정에서는 어떤 라벨을 붙여도 plan이 다시 실행돼요. 같은 PR의 이전 실행은 동시 실행 설정으로 취소하고, 라벨을 붙이는 빈도가 낮다는 점을 고려해 추가 실행을 받아들이기로 했습니다.

💡 라벨로 검증 범위를 바꿀 때 확인한 기준
• 라벨을 잘못 붙인 경우와 필요한 라벨을 빠뜨린 경우를 함께 검토했어요
• 이 저장소에서는 라벨 때문에 파일 변경에 필요한 검증이 빠지지 않도록 했어요
• 범위를 줄일 때는 바뀐 파일 목록처럼 자동으로 확인할 수 있는 근거를 사용하고, 판단할 수 없으면 전 스택을 선택해요

3. 워크플로의 호출 관계로 스크립트를 분류하기

라벨로 생략하지 않는다면 인벤토리 스크립트의 영향 범위를 다른 방식으로 확인해야 했어요. 나흘 전 .github/를 고칠 때도 별도 목록은 파일이 늘어날 때 갱신을 빠뜨릴 수 있다는 이유로 쓰지 않았습니다.

워크플로 파일에는 어느 잡이 어떤 스크립트를 실행하는지 이미 적혀 있었어요. 이 호출 관계를 읽어 plan 결과에 영향을 주는 스크립트를 구분하기로 했습니다.

판정 조건 plan --------- -------------------------------------------------- ------- 파이프라인 plan · apply 잡이 부른다 전 스택 (terraform-plan 의 lint · security 잡은 제외) 자기검증 그 밖의 잡이나 lint.sh 만 부른다 없음 모름 어느 잡도 부르지 않는다 전 스택

가운데의 자기검증 분류를 새로 추가했어요. 린트와 보안 잡은 모든 PR에서 실행되므로, 그 잡에서만 호출하는 스크립트는 변경한 PR 안에서 검증됩니다. 해당 스크립트는 plan 결과에 영향을 주지 않아 스택별 plan을 생략하도록 했어요.

plan 쪽 잡이 호출하는 스크립트는 넷이었어요. plan 결과 판정, 스택 선택, 스택 목록 생성, 진행 상황 표시를 각각 맡습니다. 인벤토리 스크립트는 인벤토리 잡에서, IAM 경계와 알람 누락 검사는 drift 잡에서 호출했어요. 이들은 plan 결과에 영향을 주지 않는 것으로 분류했습니다.

호출 관계를 읽을 때는 다음 조건도 구분했어요.

먼저 잡 정의에 적힌 경로만 읽어요. 진행 상황 스크립트 안에는 "scripts/lint.sh를 만든 이유와 같다"라는 주석이 있는데, 이런 문장까지 참조로 읽으면 린트 스크립트를 파이프라인으로 잘못 분류하게 됩니다. 그 결과 린트 스크립트만 고쳐도 전 스택이 다시 실행될 수 있어요.

하위 디렉터리의 파일에는 같은 분류를 적용해요. 인벤토리 디렉터리의 분류 규칙 데이터는 잡에서 직접 호출하지 않지만, 인벤토리 스크립트와 함께 사용하는 파일이기 때문입니다. 반면 scripts/ 바로 아래 파일은 각각 판정해요. 그곳의 태그 기준 파일은 여전히 "모름"으로 남아서, 수정하면 전 스택을 실행합니다.

두 분류에 모두 해당하면 파이프라인으로 분류해요. plan 판정 스크립트처럼 린트 잡에서 자기 검사도 받는 경우에 적용됩니다. 워크플로를 읽지 못하면 기존 동작대로 scripts/ 전체를 "모름"으로 처리해요.

다만 워크플로 파싱이 틀리면 필요한 plan을 빠뜨릴 수 있어요. 잡 정의에서 스크립트 호출 위치를 바꿨을 때 파이프라인 스크립트가 자기검증으로 잘못 분류될 가능성입니다. 이를 확인하려고 판정 스크립트의 자기 검사가 실제 저장소의 워크플로를 읽도록 했어요. 앞의 네 스크립트가 파이프라인으로 분류되지 않으면 린트가 실패합니다. 인벤토리와 린트 스크립트가 자기검증으로 분류되는지도 함께 확인해요.

⚠️ 주의: 이 판정이 깨지는 조건
• plan · apply 잡이 공용 액션 등 잡 정의 밖에서 스크립트를 호출하면 이 방식으로는 확인하지 못해요. 결정 기록에 재검토 조건으로 남겼습니다
• 자기검증 스크립트만 고친 PR에서는 스택별 tflint · validate를 0개 실행해요. 해당 스크립트의 자기 검사와 전역 가드는 스택 선택과 무관하게 실행되므로 받아들인 범위입니다

영향 범위를 알 수 없으면 전 스택을 실행한다는 규칙은 유지했어요. 워크플로에서 역할을 확인할 수 있는 파일만 별도로 분류해 불필요한 plan을 줄인 것입니다.

4. 같은 판정을 머지 뒤에도 붙인 이유: 남겨진 잠금 파일

같은 스택 선택 스크립트는 일주일쯤 앞서 머지 뒤 파이프라인에도 적용했어요. 그때는 취소된 plan이 남긴 잠금 파일 때문에 점검이 실패한 것이 계기였습니다.

main에 머지되면 "prod 미반영 확인" 잡이 실행돼요. prod는 사람이 수동으로 apply하므로, 머지 후에도 반영되지 않은 변경이 있으면 이슈로 알려 줍니다(7편). 이 잡은 푸시 내용과 상관없이 prod 스택 열여덟 개 전부에 plan을 실행하고 있었어요. 스택 하나를 고친 머지에서도 나머지 열일곱 개를 함께 확인했습니다.

여기에 동시 실행 설정이 겹쳤어요.

📖 용어: concurrency 와 cancel-in-progress
GitHub Actions 에서 같은 그룹 이름을 가진 실행이 겹칠 때 어떻게 할지 정하는 설정입니다. cancel-in-progress: true 이면 새 실행이 시작될 때 진행 중이던 이전 실행을 취소해요. 이 잡은 스택마다 그룹을 따로 두고 이 옵션을 켜 두었습니다.

머지 두 개가 짧은 간격으로 들어오면 뒤 머지의 실행이 앞선 plan을 취소해요. 다음 실행이 같은 스택을 다시 확인하지만, 앞선 plan이 잠금을 얻은 뒤 취소되면 잠금 파일을 지우지 못한 채 종료될 수 있었습니다. 잠금을 얻기 전에 취소되면 파일은 남지 않으므로 취소 시점에 따라 결과가 달랐어요.

📖 용어: state 잠금과 .tflock
두 실행이 같은 state 를 동시에 고치지 못하게 막는 장치입니다. 이 저장소는 S3 에 state 를 두고 use_lockfile = true 를 쓰는데, 그러면 plan · apply 가 시작할 때 state 옆에 <키>.tflock 객체를 만들고 끝날 때 지워요. 그 객체가 있는 동안 다른 실행은 기다립니다.

정상 실행에서는 몇 분 안에 잠금 객체가 생성됐다 삭제되지만, 프로세스가 강제로 종료되면 삭제 단계가 실행되지 않아 객체가 남을 수 있어요. 처음 겪은 8월 말의 작업 기록에는 "S3 lockfile은 만료가 없어 재시도로 풀리지 않는다. .tflock 객체를 지워야 한다"라고 적었습니다. 그날은 다른 작업 세션의 머지 두 개가 44초 간격으로 겹쳤어요.

다만 잠금 파일을 지우기 전에는 잠금을 만든 원래 실행이 실제 종료됐는지, 같은 state를 사용하는 다른 실행도 없는지 확인해야 해요. 기다린 시간이 길다는 이유만으로 살아 있는 실행의 잠금을 지우면 동시 쓰기가 생길 수 있습니다. 종료된 실행이 남긴 자기 잠금인지 확인한 뒤 잠금 ID를 지정하는 해제를 우선 검토해야 해요.

후속 실행은 잠금 객체가 남아 있으면 기다려요. 이 저장소는 plan마다 -lock-timeout=5m을 지정했기 때문에 5분 뒤에도 잠금을 얻지 못하면 실패합니다. 잠금을 만든 실행이 이미 종료되어 파일을 지우지 못하므로 재실행해도 같은 이유로 실패해요.

남은 잠금은 미반영 확인뿐 아니라 같은 스택의 state를 사용하는 후속 실행에도 영향을 줘요. 매일 실행하는 drift 점검도 잠금을 얻지 못하면 실패합니다.

📖 용어: drift 점검
코드와 실제 클라우드가 어긋났는지(누가 콘솔에서 손으로 바꿨는지) 매일 plan 을 돌려 확인하는 잡입니다. 어긋남을 찾으면 이슈를 열어요. plan 자체가 실패하면 "drift" 가 아니라 "error" 상태로 이슈를 남깁니다(7편).
그림 2. 실행이 종료돼도 남은 잠금 객체 때문에 후속 점검이 실패해요

성공 기록과 남은 잠금 기록의 차이

9월 16일 작업 기록에는 머지 두 개를 16초 간격으로 하면서 미반영 확인 잡 열일곱 개가 취소됐다고 적혀 있어요. 당시에는 잠금을 얻기 전에 취소돼 다음 실행에서 열여덟 개가 전부 성공했다고 기록했습니다. 연속으로 머지할 때는 main 잡이 끝날 때까지 기다리겠다는 운영 방침도 남겼어요.

닷새 뒤 수리 커밋에는 그날 고아 잠금이 셋 생겨 해당 스택들의 drift 감시가 하루 넘게 실패했다고 적혀 있어요. 그 셋이 앞서 성공했다고 기록한 머지에서 생겼는지, 기록 이후 다른 머지에서 생겼는지는 자료만으로 구분할 수 없습니다. 다음 실행이 성공했다는 기록만으로 그날 다른 잠금도 남지 않았다고 판단할 수는 없었어요. 연속 머지를 조심하겠다는 운영 방침 외에 실행 범위도 줄일 필요가 있었습니다.

PR의 선택 스크립트로 바뀐 스택만 확인하기

이 잡도 해당 푸시에서 바뀐 prod 스택만 확인하도록 고쳤어요. PR에서 사용하던 스택 선택 스크립트를 그대로 사용했습니다. 자기 검사가 있고 린트에서 매번 확인하는 로직이라 같은 판정을 새로 구현하지 않았어요.

실측 (수리 당일) 바뀐 파일 고른 prod 스택 stacks/<서비스>/dev/alb-legacy.tf 없음 (전에는 18개 전부) stacks/<서비스>/prod/alb-legacy.tf 그 스택 하나 docs/adr/x.md 없음 modules/cw-alarm/main.tf 18개 전부 (모르면 좁히지 않는다) .github/workflows/*.yml 18개 전부

바뀐 스택이 한두 개라면, 머지가 겹칠 때 취소될 수 있는 plan도 열여덟 개에서 한두 개로 줄어요.

⚠️ 주의: prod 목록만 넘기면 오히려 넓어진다
처음에는 판정 스크립트에 prod 스택 목록만 넘기려 했어요. 그러면 dev 스택만 바뀐 머지에서 바뀐 파일이 어느 prod 디렉터리에도 속하지 않습니다. 이 파일을 스택 밖의 변경으로 판정해 prod 전체를 실행하게 돼요. 그래서 전체 스택 목록으로 판정한 뒤 prod만 추립니다. dev 변경도 스택 내부 변경으로 판정할 수 있도록 전체 스택 목록이 필요했어요.

생략한 대상을 실행 요약에 표시해서 전체를 확인한 것으로 오해하지 않도록 했어요. 또 이전 커밋을 찾지 못해 diff를 구할 수 없으면 범위를 줄이지 않도록 했습니다.

이전에는 다른 사람의 머지가 들어올 때도 미반영 상태를 다시 알려 줬지만, 범위를 줄이면 그런 재알림은 사라져요. 해당 변경이 머지될 때 알리는 것을 이 잡의 역할로 정하고, 이후 상태는 매일 실행하는 drift 점검에서 확인하기로 했습니다.

이 변경으로 고아 잠금이 생기지 않게 된 것은 아니에요. 미반영 확인 잡은 여전히 스택별로 cancel-in-progress: true를 사용합니다. 같은 스택을 고친 머지 두 개가 겹치면 잠금이 남을 수 있어요. 매 머지마다 열여덟 개였던 대상이 실제로 바뀐 스택 몇 개로 줄었다는 범위의 개선입니다.

5. 범위를 줄일 때 남긴 근거와 한계

PR 라벨, 스크립트 분류, 머지 뒤 점검에서 공통으로 확인한 것은 검증 범위를 줄이는 근거였어요.

범위를 줄이는 라벨은 잘못 붙여도 필요한 plan이 빠졌다는 사실을 알아내기 어려워 제외했어요. 대신 스크립트 분류는 워크플로의 호출 관계를 읽고, 읽지 못하면 전 스택을 선택하도록 했습니다. 분류가 바뀌는 문제는 실제 워크플로를 읽는 자기 검사로 확인해요. 미반영 확인에도 같은 판정을 적용하고 생략한 대상을 표시했습니다.

서른세 개 plan의 실행 비용과 prod 열여덟 개 plan에서 생길 수 있는 잔여 잠금 문제를 줄이면서도, 영향 범위를 알 수 없는 변경은 계속 전체 검증 대상으로 남겼어요. 다만 워크플로의 호출 방식이 달라지면 분류를 재검토해야 하고, 같은 스택의 실행이 겹칠 때 잠금이 남을 가능성도 유지됩니다.

✍️ 적용한 변경과 남은 한계
스크립트만 고친 PR에서도 전 스택 plan이 실행된 것은 scripts/ 전체를 영향 범위가 불명확한 경로로 분류했기 때문이에요. plan:skip 라벨 대신 워크플로의 호출 관계로 스크립트를 분류하고, plan · apply 잡에서 사용하는 파일과 역할을 알 수 없는 파일은 계속 전 스택을 검증하도록 했습니다.

머지 뒤 미반영 확인에도 같은 선택 스크립트를 적용해 바뀐 prod 스택만 확인하도록 했어요. 취소된 plan의 .tflock이 drift 점검까지 막은 문제를 줄이기 위한 변경입니다. 생략한 대상은 실행 요약에 표시하지만, 같은 스택의 연속 머지에서 잠금이 남을 가능성까지 제거하지는 못했어요.
