3편. 라벨을 붙여 재실행해도 이전 이벤트를 읽던 삭제 가드 수정하기 ← 지금 이 글

Terraform 코드를 관리하는 저장소에서 PR을 올리면 dev/prod plan을 실행하고 요약을 코멘트로 남겨요. 삭제나 재생성이 포함돼 있으면 allow-destroy 라벨 없이는 체크를 실패시키는 가드를 추가해 뒀어요. 동료가 오래된 dev 리소스를 정리하는 PR을 올렸을 때도 plan 요약에 삭제 3건이 표시됐습니다. 의도한 변경이었지만 가드가 실패하면서 이렇게 안내했어요. "의도한 변경이라면 PR 에 allow-destroy 라벨을 붙이고 다시 실행하세요." 안내대로 라벨을 붙이고 Actions에서 Re-run failed jobs를 눌렀는데, 다시 실행해도 계속 실패했어요.

라벨은 붙어 있는데 가드는 계속 없다고 판단했어요. 제가 작성한 안내대로 재실행해도 바뀐 라벨을 읽지 못하는 이유를 확인해야 했습니다.

1. 문제의 한 줄

기존 가드는 이벤트에 담긴 PR 라벨 목록을 조건으로 사용했어요.

- name: 파괴적 변경 가드 run: | if [ "${{ contains(github.event.pull_request.labels.*.name, 'allow-destroy') }}" != "true" ]; then echo "::error::라벨을 붙이고 다시 실행하세요." exit 1 fi

이 코드는 라벨 목록에 allow-destroy가 없으면 오류를 출력하고 종료해요. 저는 이 목록이 실행할 때마다 현재 PR에서 가져온 값이라고 생각했어요. 그래서 라벨을 붙이고 다시 실행하면 통과할 것으로 예상했습니다. 하지만 재실행에서는 라벨 변경이 반영되지 않아 안내한 절차대로 해도 통과할 수 없었어요.

2. github.event에는 이벤트 당시 정보가 남아요

github.event는 실행 시점에 GitHub API로 조회한 값이 아니에요. 워크플로 실행을 시작한 이벤트의 webhook payload JSON, 즉 당시 전달된 데이터가 들어 있어요. 이때는 마지막 커밋을 push하면서 synchronize 이벤트가 발생했고, 그 시점의 PR에는 라벨이 없었어요.

Re-run은 기존 이벤트의 payload로 job을 다시 실행해요. 라벨은 그 이벤트가 발생한 뒤에 붙였으니, 재실행이 읽는 labels 배열은 여전히 비어 있어요. 재실행을 반복해도 같은 조건에서 실패한 이유예요.

기존 코드에서 통과하려면 라벨을 붙인 뒤 새 이벤트가 필요했어요. 빈 커밋을 push해서 synchronize를 일으키거나, PR을 닫고 다시 열어 reopened를 발생시키는 방법이 있어요. 하지만 에러 메시지에는 이런 조건이 없어서, 사용자가 안내만 보고 필요한 조치를 알기는 어려웠어요.

그림 1. Re-run은 라벨을 붙이기 전 이벤트의 payload를 다시 읽어요

3. 라벨을 제거해도 성공한 체크가 남았어요

라벨을 제거하는 경우에도 문제가 있었어요. 트리거는 on: pull_request만 지정해서 기본값 세 종류(opened, synchronize, reopened)에만 반응했어요. unlabeled가 없으니 체크가 성공한 뒤에 라벨을 떼도 워크플로가 다시 실행되지 않았습니다. 필수 상태 체크는 그 커밋에 같은 이름으로 마지막에 보고된 결과를 보므로, 새 run이 없으면 이전 성공 결과가 남아요. 라벨을 제거했는데도 머지 가능한 상태를 유지할 수 있었어요.

4. 트리거 추가와 실행 시점 조회를 비교했어요

방법 A는 트리거를 types: [opened, synchronize, reopened, labeled, unlabeled]로 늘리는 거예요. 라벨을 붙이거나 떼면 변경된 라벨이 담긴 payload로 워크플로가 실행돼요. 다만 라벨을 하나 붙일 때마다 dev/prod plan 전체를 다시 실행하고, AWS와 통신하는 plan 작업도 두 번 더 실행돼요.

방법 B는 실행 시점에 API로 라벨을 조회하는 거예요. 재실행할 때 현재 라벨을 읽으므로 안내대로 라벨을 붙이고 Re-run하면 가드를 통과할 수 있어요.

env: GH_TOKEN: ${{ github.token }} PR_NUMBER: ${{ github.event.pull_request.number }} run: | labels=$(gh pr view "$PR_NUMBER" --repo "$GITHUB_REPOSITORY" \ --json labels --jq '.labels[].name') if ! printf '%s\n' "$labels" | grep -qx 'allow-destroy'; then exit 1 fi

위 코드는 PR의 현재 라벨을 조회하고, 목록에 allow-destroy가 없으면 실패해요. 이 방식인 B를 사용하고 types에는 unlabeled만 추가했어요. 라벨을 붙일 때는 수동으로 재실행하고, 제거할 때는 워크플로가 자동으로 다시 검사하도록 했습니다. labeled는 넣지 않았어요. 실행 시점 조회로 Re-run이 동작하므로, 라벨 추가만으로 dev/prod plan을 자동 실행하지 않기로 한 거예요.

5. 검사 대상과 현재 상태를 구분해요

모든 값을 실행 시점에 다시 조회할 필요는 없어요. 위 코드에서도 PR 번호는 github.event에서 읽어요. 라벨을 조회할 PR은 해당 실행을 시작한 이벤트의 github.event로 식별하고, 바뀔 수 있는 라벨 목록만 새로 가져오는 방식이에요.

커밋 SHA, PR 번호, 브랜치명은 해당 이벤트의 검사 대상을 식별하는 데 사용해요. 실행 중에 PR에 새 커밋이 올라와도 이 run이 검사하는 대상은 t1의 SHA이기 때문이에요. 반면 라벨, 리뷰 승인 상태, 코멘트, assignee, PR 제목은 이벤트 이후에 바뀔 수 있어요. 현재 상태를 조건으로 검사하려면 이벤트 당시 값과 구분해서 조회해야 해요.

그림 2. 검사 대상은 이벤트에서 읽고, 바뀌는 상태는 실행 시점에 조회해요
🔎 가드 코드를 확인할 때
• 조건에 사용하는 값이 이벤트 이후에 바뀔 수 있는지 확인해요.
• 에러 메시지가 안내하는 복구 절차대로 실행하면 통과하는지 확인해요.
• 라벨 제거 등으로 통과 조건을 되돌렸을 때 체크가 다시 실행되는지 확인해요.
✍️ 오늘의 요약
github.event에는 이벤트 당시 라벨이 남아 있어서, 라벨을 붙인 뒤 재실행해도 가드가 계속 실패했어요. 실행 시점에 API로 라벨을 조회하도록 바꿔 안내한 절차가 동작하게 했습니다.

라벨을 제거할 때도 다시 검사하도록 unlabeled를 트리거에 추가했어요. 라벨 추가 시 자동으로 dev/prod plan 전체를 실행하는 대신 수동 재실행을 사용하기로 했어요.
