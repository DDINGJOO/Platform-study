18편. 기존 퍼블릭 S3 편입에서 Checkov skip을 허용한 기준 ← 지금 이 글

서비스의 프론트 S3 버킷을 Terraform으로 관리하기 위해 PR을 열었어요. 실물에서 추출한 값을 고치지 않고 옮겼는데, CI의 2 · 보안 잡이 종료코드 1로 실패했습니다. 기존 버킷의 퍼블릭 설정이 보안 차단 규칙에 걸렸어요.

이 저장소는 정적 분석 결과 대부분을 참고용으로 남기지만, 퍼블릭 S3 관련 규칙은 오탐이 사실상 없다고 판단해 머지를 막도록 설정했어요. 한편 기존 자원을 편입할 때는 실물과 같은 값을 코드에 적고, 낡은 설정이나 잘못된 태그도 다음 PR에서 고치기로 했습니다.

편입할 버킷은 2023년부터 퍼블릭이었어요. 기존 상태를 그대로 적으면 CI가 실패하고, CI를 통과하려고 값을 바꾸면 편입 원칙을 어기게 됩니다. 정책을 코드에 남기면서 필요한 검사만 skip하는 방식을 택했고, 이후 CDN까지 편입하며 퍼블릭 읽기를 바로 차단할 수 없는 이유도 확인했어요.

1. 기존 퍼블릭 버킷 편입이 보안 검사에 걸렸어요

편입 시점에 확인한 버킷 설정과 CI 차단 규칙은 다음과 같아요.

프론트 버킷의 실물 (편입 시점 실측) 퍼블릭 액세스 차단 4개 전부 false 버킷 정책 Allow Principal: * ["s3:GetObject", "s3:GetObjectVersion"] 린트 스크립트의 하드 차단 목록 (CI `2 · 보안` 잡이 이 스크립트를 그대로 부른다) CKV_AWS_24 / 25 / 260 0.0.0.0/0 인바운드 (SSH / RDP / 80) CKV_AWS_20 S3 퍼블릭 읽기 CKV_AWS_53 ~ 56 S3 퍼블릭 액세스 차단 4종 실물 그대로 쓰면 -> 종료코드 1 -> 머지 불가 게다가 plan 잡은 린트·보안 잡을 needs 로 기다린다. 둘 중 하나라도 실패하면 plan 은 아예 태어나지 않고, 정적 검사로 잡히는 실패에 AWS 자격증명도 발급되지 않는다.

하드 차단 목록을 정할 때는 이 저장소의 코드로 새 자원만 만든다고 전제했어요. 그 조건에서는 퍼블릭 S3가 코드에 추가되는 것을 막으면 됐습니다.

스택이 알림·접근제어·데이터 플랫폼 셋뿐일 때는 이 전제가 맞았어요. 기존 퍼블릭 버킷을 편입하면서 처음으로 보안 규칙에 걸리는 설정을 그대로 코드에 적어야 했습니다.

기존 퍼블릭 버킷을 코드에 옮기는 작업은 새 버킷을 만드는 작업과 달라요. 실물은 바꾸지 않고 Terraform 관리 대상으로 등록합니다. 하지만 여기서 쓰는 정적 분석은 리소스 설정을 보기 때문에 두 작업을 구분하지 못해요. 기존 자원을 가져오는 import 블록은 plan 단계에서 처리되고, 이 보안 검사는 그 결과로 편입 여부를 판단하지 않습니다.

따라서 퍼블릭 설정을 정확히 탐지했다는 사실만으로 이 PR이 새 퍼블릭 버킷을 만든다고 판단할 수는 없었어요. 기존 상태를 편입하는 PR에는 별도의 예외 기준이 필요했습니다.

2. 정책을 코드에서 제외하지 않은 이유

버킷만 가져오고 정책과 퍼블릭 액세스 차단 설정은 코드에서 제외하는 방법도 검토했어요. 문제 되는 설정을 검사 대상에서 빼면 해당 규칙으로 CI가 실패하는 상황은 피할 수 있습니다.

하지만 그렇게 하면 기존 설정을 확인하고 변경을 추적하기가 더 어려워져요.

우선 버킷의 퍼블릭 상태는 그대로 남아요. 검사 대상에서 빼거나 skip을 붙이거나 해당 설정을 검사하지 않는다는 점은 같아서, 정책을 생략한다고 보안 상태가 개선되지는 않습니다.

skip을 붙이면 리포트에 건너뛴 검사가 표시되고 코드에는 사유가 남아요. 정책 자체를 생략하면 그 정보도 없습니다. 6개월 뒤 파일을 읽는 사람은 코드만으로 버킷의 공개 여부와 그 이유를 확인하기 어려워요.

정책이 Terraform 관리 아래 있어야 매일 실행하는 드리프트 감지도 변경을 확인할 수 있어요. 드리프트는 코드와 실제 설정이 달라진 상태를 뜻합니다. 정책을 관리 대상에서 빼면 콘솔에서 쓰기 권한을 추가해도 이 잡으로는 확인할 수 없습니다.

하드 차단 목록에서 S3 규칙을 빼는 방법도 제외했어요. 그러면 이 버킷뿐 아니라 저장소에서 새로 만드는 퍼블릭 버킷도 같은 규칙으로 막을 수 없게 됩니다. 실물을 먼저 비공개로 바꾼 뒤 편입하는 방법은, 당시 어떤 경로로 이 버킷을 읽는지 확인하지 못해 선택하지 않았어요.

정책을 코드에 남겨야 공개 상태와 변경 이력을 확인할 수 있다고 판단했어요. 그래서 하드 차단 목록은 유지하고, 해당 리소스에만 skip 주석과 사유를 붙였습니다.

그림 1. 정책을 코드에 남기고 skip 사유와 드리프트 감지 범위를 확인했어요

3. 퍼블릭 허용이 실제 CDN 읽기 경로였어요

예외를 정할 때는 퍼블릭 읽기 허용을 나중에 제거할 수 있다고 생각했어요. CDN 배포와 접근 주체를 편입하며 이 판단을 다시 확인하게 됐습니다.

처음에는 Principal: *가 과거 설정의 잔재라고 봤어요. 이 버킷 앞에는 CDN이 있었고, 버킷 정책에도 전용 접근 주체 네 개가 적혀 있었습니다. CDN이 오리진인 S3를 읽도록 허용하는 OAI·OAC 설정이 있는 것으로 생각했어요. 예전에 공개하던 버킷에 CDN을 붙인 뒤 퍼블릭 허용만 남겨 둔 상태라고 추정했습니다.

CDN 배포와 접근 주체를 코드로 가져와 대조하니 실제 연결 관계는 달랐어요.

실제로 버킷을 읽는 CDN 배포의 접근 주체가 버킷 정책에 없었습니다. 이 배포는 Principal: * 허용으로 버킷을 읽고 있었어요. 불필요하다고 생각한 설정이 당시 서비스의 유일한 읽기 경로였으므로, 먼저 지우면 서비스가 중단될 수 있었습니다.

정책에 적힌 접근 주체 넷은 전부 다른 서비스의 것이었어요. 그 서비스의 CDN 배포는 이 버킷을 오리진으로 쓰지 않아, 권한만 허용되어 있고 실제로 이 경로로 읽지는 않는 상태였습니다. 개발 환경 버킷의 정책에도 운영과 같은 넷이 적혀 있었어요. 두 환경에 같은 접근 주체 허용이 남아 있었습니다.

퍼블릭 허용은 서비스에 필요했고, 정상적인 접근 설정이라고 생각한 네 주체는 이 버킷의 배포와 관계가 없었어요. 실제 읽기 주체를 추가하지 않은 채 먼저 비공개로 바꾸면 서비스 접근이 끊기는 구성이었습니다.

버킷 정책과 CDN 배포를 각각 볼 때는 이 불일치를 놓쳤어요. 둘을 같은 코드베이스로 가져와 배포가 참조하는 접근 주체와 정책에서 허용한 주체를 대조한 뒤에야 확인할 수 있었습니다.

그림 2. 배포의 실제 접근 주체가 정책에 없어 퍼블릭 허용으로 읽고 있었어요

4. skip 이후에도 남는 검사 범위의 한계

skip은 리소스 단위로 붙이고, 사유와 제거할 조건을 주석에 함께 적었어요.

resource "aws_s3_bucket_public_access_block" "front" { # checkov:skip=CKV_AWS_53:2023년부터 퍼블릭인 것을 실물 그대로 편입한다 (결정 기록 참조). 잠그는 것은 별도 PR # checkov:skip=CKV_AWS_54:위와 같음 # checkov:skip=CKV_AWS_55:위와 같음 # checkov:skip=CKV_AWS_56:위와 같음 bucket = aws_s3_bucket.front.id block_public_acls = false block_public_policy = false ignore_public_acls = false restrict_public_buckets = false skip_destroy = null } resource "aws_s3_bucket_policy" "front" { # checkov:skip=CKV_AWS_20:2023년부터 퍼블릭인 것을 실물 그대로 편입한다 (결정 기록 참조). 잠그는 것은 별도 PR bucket = aws_s3_bucket.front.id policy = jsonencode({ ... }) # Principal: * 가 첫 Statement }

규칙 다섯 개를 리소스 둘에 나누어 skip했습니다. 퍼블릭 액세스 차단 4종은 차단 설정 리소스에, 퍼블릭 읽기 규칙은 정책 리소스에 붙였어요. 2023년부터 있던 퍼블릭 상태를 바꾸지 않고 코드와 CI 리포트에 남기기 위한 예외였습니다.

주의할 점은 skip이 이후 변경에도 계속 적용된다는 것이에요. 당시 설정은 s3:GetObject 읽기를 허용하고 있었어요. Principal: *에 s3:PutObject를 추가하면 CKV_AWS_20이 탐지한다고 ADR에 적혀 있었지만, 이 설명은 잘못됐어요. 이 규칙은 S3 ACL의 퍼블릭 읽기를 검사하므로 임의의 버킷 정책 쓰기 권한 추가까지 탐지한다고 볼 수 없습니다. skip은 해당 규칙의 적용을 생략하는 것이며, 그 규칙이 원래 검사하지 않는 변경까지 막아주지는 않아요. 특정 리소스의 현재 설정만 허용하는 예외가 아니라 해당 규칙의 검사를 계속 생략하는 방식이에요.

대신 정책을 Terraform 관리 아래 두어 콘솔에서 바뀐 설정을 드리프트 잡으로 확인하기로 했어요. 매일 코드와 실물을 대조해 diff를 확인하는 방식입니다.

드리프트는 코드와 실물이 다른 경우를 확인해요

다만 드리프트 감지로 확인할 수 있는 범위는 한정돼 있어요. 코드와 실물을 비교하므로, 코드에 반영하지 않은 변경은 확인하지만 코드와 함께 바뀐 설정은 차이가 나지 않습니다.

아래는 당시 적어 둔 변경 경로 비교예요. 여기서 쓰기 권한 변경을 "skip이라 안 본다"고 한 인과도 앞서 정정한 옛 설명입니다. 이 규칙이 원래 검사하지 않는 변경은 skip을 제거해도 탐지한다고 보장할 수 없어요. 콘솔 변경을 드리프트로 찾는 것과 PR의 정책 내용을 리뷰하는 범위만 구분해서 봐야 해요.

콘솔에서 정책에 s3:PutObject 를 얹었다 -> 코드와 실물이 어긋난다 -> 드리프트 잡이 diff 를 본다 -> 이슈가 열린다 PR 로 코드에 s3:PutObject 를 얹고 apply 했다 -> checkov 는 skip 이라 안 본다 -> 실물과 코드가 같아졌으므로 드리프트도 볼 것이 없다 -> 남은 것은 리뷰뿐이다

드리프트 감지는 skip한 보안 검사를 대신하지 못해요. 7편에서 설명한 것처럼 잡을 실패시키는 대신 이슈를 열기 때문에 사람이 내용을 확인해야 합니다. PR로 코드에 반영한 변경은 드리프트로도 확인할 수 없어 리뷰가 필요해요.

이 한계를 전제로 skip을 붙이는 리소스는 Terraform 관리 아래 두기로 했어요. 정책을 코드에서 제외하면 정적 분석뿐 아니라 드리프트 감지로도 해당 정책을 확인할 수 없기 때문입니다.

ADR(설계 결정 기록)에는 skip이 3개 스택을 넘으면 하드 차단 목록 자체를 재설계한다는 재검토 조건도 넣었어요. 예외가 늘어날 때 개별 skip을 계속 추가해도 되는지 다시 판단하기 위한 기준입니다.

💡 skip을 붙일 때 남긴 기준
• 사유에 실물 그대로 편입한다는 점과 제거할 조건을 적고, 사유 없는 skip은 리뷰에서 제외하기로 했어요.
• 스택 README에 상태의 의미를 적었어요. 이 경우에는 CDN과 WAF를 우회해 버킷을 직접 읽는 경로가 있다는 내용입니다.
• skip은 리소스 단위로만 붙이고, 범위가 넓어지는 파일·디렉터리 단위 skip은 쓰지 않기로 했어요.
다만 이 조건을 자동으로 강제하는 검사는 없었습니다. 필수 승인 수가 0인 저장소여서, 다음 작업자가 사유를 확인하도록 요구하는 근거는 문서에 남아 있어요.

공개 여부를 검토하기 쉽게 파일을 나눴어요

편입 초기에는 S3 리소스가 모두 s3.tf 한 파일에 있었고, 분량은 211줄이었어요. 리소스 종류별로 파일을 나누는 저장소 규약을 따랐지만, 공개 배포물을 담는 프론트 버킷과 개인정보를 담는 비공개 버킷이 섞여 있었습니다.

파일 이름만으로는 skip이 어느 용도의 버킷에 붙었는지 알기 어려웠어요. 200줄이 넘는 파일에서 리소스와 예외 사유를 찾아 대조해야 하므로, 리뷰할 때 공개가 허용되는 버킷인지 확인하는 데도 더 많은 문맥이 필요했습니다.

그래서 용도에 따라 파일을 나눴어요.

s3-front.tf 프론트 서빙용. 퍼블릭이 정상일 수 있는 것 s3-data.tf 보관용. 절대 퍼블릭이면 안 되는 것

파일 이름에서 용도를 알 수 있으면 예외를 검토할 기준도 분명해져요. s3-data.tf에 퍼블릭 skip이 있으면 비공개 보관 용도와 맞는지 바로 확인해야 합니다. 규약에도 같은 종류의 리소스가 성격이 다른 용도로 쓰이면 용도별로 한 번 더 나눈다고 적었어요.

프론트와 백엔드를 디렉터리로 나누는 방법은 택하지 않았어요. 현재 스택 탐색 규칙에서 하위 디렉터리의 코드를 검사하지 못하기 때문입니다.

🚧 파일을 나눌 때 스택 탐색 깊이를 확인해요
stacks/{서비스}/prod/front/로 나누면 파일 분리가 아닌 스택 분리가 됩니다.

이 저장소의 탐색 스크립트는 stacks/*/*/versions.tf 중 backend 선언이 있는 것만 스택으로 셉니다. 한 단계 더 깊은 디렉터리의 코드는 탐색하지 않아 plan·validate·린트·드리프트 감지가 모두 실행되지 않아요.

이때는 오류가 나지 않고 대상이 0개인 채 통과합니다. 15편에서 다룬 것처럼 검사 성공 여부와 함께 검사 대상도 확인해야 해요.

용도가 다르면 파일을 나누고, 잠금·변경 영향 범위·롤백을 따로 관리해야 할 때 스택 분리를 검토하기로 했습니다.

5. 읽기 경로를 확인한 뒤 퍼블릭 허용을 제거해요

Principal: *를 제거하려면 먼저 실제 CDN 접근 주체로 읽을 수 있어야 해요. 당시 확인한 읽기 경로를 유지하면서 비공개로 전환하기 위한 순서는 다음과 같습니다.

잠그는 순서 (운영) 1. 버킷 정책에 실제로 쓰이는 접근 주체를 추가한다. `*` 는 아직 유지 추가만으로 넘어가지 않고, 그 주체로 실제로 읽히는지 확인한다 2. `Principal: *` 와 다른 서비스 접근 주체 4줄을 제거한다 3. 퍼블릭 액세스 차단 4개를 on 으로. 이때 checkov skip 도 함께 지운다 무엇이 순서를 강제하나 1 -> 2 아무것도 강제하지 않는다. 문서와 사람뿐이다 2 -> 3 S3 가 강제한다. 차단을 켜면 퍼블릭 정책 등록이 거부되고 이미 있는 퍼블릭 정책의 익명 접근도 차단된다 개발 환경은 단계가 하나 더 있다 4. 정적 웹사이트 호스팅을 어떻게 할지 먼저 정한다 웹사이트 엔드포인트는 접근 주체 방식으로 보호할 수 없다. 퍼블릭이 아니면 그 엔드포인트가 죽는다

이 순서 중 시스템이 제약하는 구간은 2번과 3번 사이예요. 차단을 먼저 켜면 S3가 퍼블릭 정책 등록을 거부하거나 익명 읽기를 차단합니다. 반면 1번을 확인하기 전에 2번을 실행하는 것은 자동으로 막지 못해요. *를 먼저 지우면 새 접근 주체를 허용할 때까지 읽기가 중단될 수 있으므로, 작업자가 문서의 순서를 확인해야 합니다. 15편에서 다룬 검사 범위의 한계와 같은 문제예요.

버킷 정책 변경이 즉시 효력을 갖는다고 가정해서도 안 됩니다. 1번은 설정 적용뿐 아니라 새 주체로 실제 읽기가 되는지 확인하는 단계까지 포함해요. 적용만 확인하고 2번으로 넘어가면 읽기가 중단될 수 있습니다.

같은 계정의 어드민 프론트 버킷은 배포를 조건으로 지정하는 OAC 방식으로 비공개 접근을 구성해 둔 상태였어요. 위 순서의 1번은 기존 OAI를 먼저 허용해 중단을 피하는 단계이고, 최종적으로는 어드민과 같은 OAC 형태로 옮기는 방향입니다.

개발 환경은 4번도 별도로 검토해야 해요. 이 버킷에는 정적 웹사이트 호스팅이 켜져 있어 HTTP로 직접 서빙하는 경로가 있습니다. 웹사이트 엔드포인트는 접근 주체 방식으로 보호할 수 없으므로, 비공개로 바꾸기 전에 서비스 방식을 정해야 해요. DNS 레코드나 다른 배포의 커스텀 오리진 중 무엇이 이 엔드포인트를 가리키는지 먼저 확인해야 합니다.

CDN 접근 주체도 Terraform으로 관리하게 되어 1번의 정책을 리소스 참조로 표현할 수 있었어요.

policy 안에서 aws_cloudfront_origin_access_identity.front.iam_arn <- 참조 소유하지 않았다면 "arn:aws:iam::cloudfront:user/CloudFront Origin Access Identity {식별자}" 문자열을 손으로 박아야 한다

접근 주체를 관리하지 않으면 식별자를 문자열로 직접 적어야 해요. 문자열로 적힌 식별자의 오타나 참조 대상 삭제는 plan과 apply에서 확인하지 못하는 한계가 있어요. 리소스 참조를 쓰면 정책과 접근 주체의 관계를 코드에 명시할 수 있어요.

6. import 블록으로는 편입 이력을 판정할 수 없어요

편입에만 skip을 허용한다는 조건은 여전히 사람이 확인해야 했어요. 새 퍼블릭 버킷에 같은 형식의 주석을 붙일 수도 있으므로, ADR에는 다음과 같은 재검토 조건을 적었습니다.

재검토 조건 중 하나 "skip 이 편입이 아닌 곳에 처음 붙는 것이 발견되면 -> 린트 스크립트에 `import` 블록이 없는 파일의 skip 을 거부하는 검사를 넣는다" 즉, 판정 기준을 이렇게 두겠다는 것이다 파일에 import 블록이 있다 -> 편입 작업이다 -> skip 허용 파일에 import 블록이 없다 -> 새로 만드는 것 -> skip 거부

import 블록의 존재로 편입 여부를 구분하려는 계획이었어요. 하지만 이 저장소의 편입 절차와 함께 적용할 수 없는 조건이었습니다.

이 저장소에서는 apply가 끝난 import 블록을 제거해야 해요. CI가 코드의 import 블록 수와 plan의 import 건수를 대조하기 때문입니다. 이미 state에 등록한 블록을 남겨 두면 다음 PR에서 "코드에 import 블록이 7개인데 plan의 import는 3건입니다"라는 불일치로 해당 스택의 plan이 막혀요. 이 편입에서 실제로 세 번 제거를 잊었고, 세 번 모두 다음 PR이 막혔습니다.

편입이 끝나면 import 블록은 주석으로만 남고 실행할 코드에서는 사라져요. 따라서 블록이 없다는 이유로 skip을 거부하면 편입 때 추가한 예외도 거부하게 됩니다. 편입 후 블록을 지우라는 규칙과, 그 블록으로 예외를 인정하겠다는 계획이 충돌하는 셈이에요.

ADR의 반대 의견에도 이미 이 한계가 적혀 있었어요. import 블록은 apply 후 제거되므로 6개월 뒤에는 skip이 편입 때문인지 주석으로만 확인할 수 있다는 내용입니다. 그런데 다음 섹션에서는 사라질 블록을 검사 입력으로 쓰겠다고 계획했어요.

워크플로 권한, state 키 레이아웃, 태그 키를 검토할 때처럼 같은 사실을 설명하는 두 부분을 함께 확인하지 못했습니다. 이번에는 ADR 안의 반대 의견과 재검토 조건이 서로 맞지 않았어요.

따라서 이 재검토 조건은 그대로 구현할 수 없는 계획으로 남아 있습니다. 자동으로 판정하려면 skip 사유 형식을 검사하거나 편입된 리소스 목록을 따로 유지하는 등, 편입 후에도 남는 기록이 필요해요. import 블록은 apply 뒤 제거하는 지시이므로 그 기록으로 쓸 수 없습니다.

skip 사유에는 예외가 필요한 이유와 다른 검사로 확인할 범위, 사람이 검토해야 할 범위를 함께 남겨야 했어요. 이번에는 콘솔에서 바뀐 설정을 드리프트로 확인하고, 코드에 반영한 변경은 리뷰로 확인하는 한계까지 적었습니다.

✍️ 정리
기존 퍼블릭 버킷을 그대로 편입하기 위해 리소스별 Checkov skip을 붙이고, 정책과 예외 사유를 코드에 남겼어요. 드리프트 감지는 코드와 다른 설정을 확인하지만, 코드에 함께 반영한 변경은 리뷰가 필요합니다.

CDN과 버킷 정책을 대조해 퍼블릭 허용이 실제 읽기 경로임을 확인했어요. 이를 제거하기 전에 실제 접근 주체로 읽을 수 있는지 확인해야 하고, 개발 환경의 웹사이트 엔드포인트는 별도로 검토해야 합니다.

편입 후 지우는 import 블록으로 skip의 편입 이력을 판정하겠다는 ADR 조건은 기존 절차와 맞지 않았어요. 예외를 자동으로 검사하려면 편입 후에도 남는 기록이 필요하며, 그 검사는 아직 구현한 것으로 보지 않았습니다.
