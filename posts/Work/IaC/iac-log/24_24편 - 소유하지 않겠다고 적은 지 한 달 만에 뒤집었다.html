8월 27일, 메일 발송 파이프라인을 코드로 옮기면서 lambda.tf 맨 위에 빨간 동그라미를 단 주석을 적었어요. 제목은 이랬습니다. "함수 본체는 소유하지 않는다." 큐와 트리거는 가져오되, Lambda 함수 자체는 Terraform 밖에 두겠다는 결정이었어요. 근거도 길게 적었고, 그때는 그 근거가 단단해 보였습니다.

9월 21일, 같은 저장소에 ADR-0049 가 들어갔어요. 제목은 "Lambda 함수 본체를 편입한다." 같은 사람이 같은 파일의 같은 주석을 뒤집은 거예요. 그날 하루에만 함수 넷이 코드로 들어왔고, 다음 날 하나가 더 들어왔습니다.

결정을 뒤집는 일은 자주 있어요. 이 글에서 적고 싶은 건 무엇이 바뀌어서 뒤집을 수 있었는가예요. 답은 파일 하나의 해시값이었습니다. 그리고 그렇게 들여온 함수 하나가, 한 달 넘게 매주 실패하면서도 지표에는 한 번도 실패로 찍히지 않았다는 이야기도 같이 적을게요.

이 글에서 다룰 것은 이렇습니다.

1. 8월 27일에는 왜 함수 코드를 소유하지 않기로 했나 2. 무엇이 바뀌었고, 해시가 맞는다는 게 왜 그렇게 중요했나 3. zip 만 커밋하면 왜 리뷰가 안 되나 4. 죽은 함수의 실패를 Errors 지표는 왜 못 봤나 5. 같은 주에 있었던 작은 일 셋

1. 소유하지 않기로 한 이유

먼저 상황을 볼게요. 계정에 Lambda 함수가 24개 있었고, Terraform 이 소유한 건 다른 파이프라인 하나에 딸린 넷뿐이었어요. 9월 18일에 전수로 다시 확인했을 때 운영 함수 본체는 한 개도 코드에 없었습니다. 런타임, 메모리, 타임아웃, 환경변수가 전부 코드 밖이라 누가 콘솔에서 바꿔도 아무도 모르는 상태였어요.

📖 용어: 편입 (import)
이미 클라우드에 떠 있는 자원을 Terraform state 에 등록해 코드로 관리하기 시작하는 일이에요. 이 시리즈의 원칙은 "편입은 실물을 바꾸지 않는다"입니다. 들여오는 순간 설정이 하나라도 바뀌면 그건 편입이 아니라 변경이에요.

그런데 함수는 다른 자원과 결정적으로 다른 점이 하나 있어요. 설정만 있는 게 아니라 코드가 있습니다. Terraform 의 aws_lambda_function 리소스는 그 코드가 어디 있는지를 반드시 적으라고 요구해요. 로컬 zip 파일 경로, 컨테이너 이미지 주소, S3 버킷과 키 중 하나입니다. 하나도 안 적으면 검증에서 바로 죽어요.

Error: "filename": one of `filename,image_uri,s3_bucket` must be specified

셋 중 하나는 꼭 적어야 한다는 뜻이에요. 그리고 import 를 해도 이 값은 돌려받지 못합니다. 자동 생성한 설정에는 filename = null 로 나와요.

문제는 이 파이프라인 주변의 함수 다섯 중 셋이 사람이 콘솔에서 zip 을 올려서 만든 것이었다는 점이에요. 콘솔에서 올린 코드는 AWS 내부 저장소로 들어갑니다. 우리 버킷에 남지 않아요. 함수 조회 API 가 코드 위치를 알려주긴 하는데, 그 주소는 잠깐만 유효한 서명 URL 입니다.

📖 용어: 프리사인 URL (presigned URL)
인증 정보 없이도 정해진 시간 동안만 파일을 내려받을 수 있게 서명을 붙인 주소예요. 시간이 지나면 같은 주소로는 더 이상 받을 수 없어서, 코드에 "여기서 가져오라"고 적어 둘 수 없습니다.

그래서 8월 27일의 판단은 이랬어요. 저장소가 가리킬 버킷과 키가 없다. 그러면 남는 길은 하나인데, 아무 내용 없는 더미 zip 을 두고 Terraform 이 코드 차이를 못 보게 가리는 거예요.

resource "aws_lambda_function" "worker" { filename = "dummy.zip" # 실제 코드가 아니다 source_code_hash = filebase64sha256("dummy.zip") lifecycle { ignore_changes = [filename, source_code_hash] # 차이를 보지 마라 } }
📖 용어: ignore_changes
Terraform 에게 "이 속성은 코드와 실물이 달라도 고치지 마라"고 적어 두는 설정이에요. plan 에 차이가 안 뜨게 만들 뿐, 차이 자체를 없애지는 않습니다.

8월 27일의 주석은 바로 이 길을 거절했어요. 이유가 정확했습니다. 그 lifecycle 블록이 한 번 지워지면, 다음 apply 가 운영 함수의 코드를 더미로 덮어씁니다. 누군가 "이 ignore_changes 는 왜 있지?" 하고 정리하는 순간이에요. 그리고 되돌릴 방법이 없어요. 원본 zip 이 저장소에 없으니까요.

그래서 결론은 "본체는 두고 부속만 가져온다"였습니다. 트리거와 권한은 함수 이름을 문자열로 받으니까 본체 없이도 소유할 수 있었어요. 함수를 제대로 들여오려면 배포 방식부터 바꿔서, 코드를 우리 S3 키에 올리고 그 키를 가리키게 해야 한다고 적었습니다. 그건 편입이 아니라 배포 파이프라인 작업이라 범위 밖이었고요.

2. 바뀐 것은 해시 하나였다

9월 21일에 한 일은 단순했어요. 그 "잠깐만 유효한" URL 로 원본 zip 을 실제로 내려받았습니다. 만료되기 전에 받으면 되는 거였어요. 8월 27일의 근거는 "코드에 적어 둘 수 없다"였지, "한 번도 받을 수 없다"가 아니었습니다. 저는 그 둘을 한 문장으로 묶어 읽고 있었어요.

그런데 받았다는 것만으로는 아무것도 증명되지 않아요. 내려받은 파일이 지금 돌고 있는 코드와 같은 바이트인지는 따로 확인해야 합니다. 여기서 해시를 대조했어요.

📖 용어: CodeSha256 / source_code_hash
CodeSha256 은 AWS 가 기억하는, 지금 배포된 zip 의 SHA-256 해시(base64)예요. source_code_hash 는 Terraform 코드 쪽에서 같은 방식으로 계산한 값입니다. 둘이 같으면 Terraform 은 "코드가 바뀌지 않았다"고 판단해요.
# 커밋할 zip 의 해시 openssl dgst -sha256 -binary {함수}.zip | base64 # 지금 운영 중인 함수의 해시 aws lambda get-function-configuration --function-name {함수} \ --query CodeSha256 --output text 1차 대상 여섯 여섯 모두 일치

두 줄의 출력이 같은 문자열이면 바이트까지 같은 파일이에요. 1차 대상 여섯 개 전부가 일치했습니다.

이게 왜 결정적이었는지가 이 글의 중심이에요. 8월 27일의 걱정을 다시 꺼내 볼게요. "lifecycle 이 지워지면 apply 가 운영 코드를 덮는다." 이 문장은 지금도 참입니다. 달라진 건 덮는 내용이에요. 더미였다면 운영 함수가 빈 코드로 바뀌는 사고가 되고, 원본이면 같은 코드를 같은 코드로 덮는 일이 됩니다. 위험이 사라진 게 아니라, 위험이 실현돼도 아무 일도 일어나지 않게 된 거예요.

그래서 ignore_changes 를 쓰지 않았어요. 가릴 차이가 없으니까요. 오히려 쓰면 해롭습니다. 나중에 누가 콘솔에서 코드를 고쳤을 때 그 차이까지 가려 버려요. 매일 도는 drift 잡(코드와 실물이 어긋났는지 매일 plan 을 돌려 확인하는 잡)이 잡아야 할 신호를 우리 손으로 지우게 됩니다.

그림 1. 해시 대조는 위험을 지운 게 아니라 위험의 결과를 무해하게 만들었다

그래도 첫 apply 는 무언가를 호출한다

하나 짚어 둘 게 있어요. 해시가 같으니 apply 가 아무것도 안 할 거라고 생각하기 쉬운데, 실제로는 코드 갱신 API 를 한 번 호출합니다. import 직후 state 에는 filename 이 비어 있으니, 코드에 경로를 적은 것을 Terraform 이 변경으로 읽는 것으로 보여요. 9월 21일에 첫 함수로 실측했을 때 결과는 이랬어요. 같은 바이트를 다시 올리니까 코드는 그대로이고, 마지막 수정 시각만 갱신됐습니다. 코드를 올리는 호출일 뿐이라 함수를 실행하거나 스케줄을 당기는 일도 아니에요.

그러니까 해시 대조가 지켜 준 건 "apply 가 아무것도 안 한다"가 아니라 "apply 가 무엇을 하든 코드는 같다"예요. 이 둘은 다릅니다. 해시가 하나라도 어긋났다면 그 한 번의 호출이 운영 코드를 다른 버전으로 바꿨을 거예요. 예를 들어 누군가 로컬에 갖고 있던 조금 더 새 버전의 zip 을 "원본"이라고 커밋했다면, plan 은 태그 하나 바뀌는 것과 구분하기 어려운 모양으로 뜨고 apply 는 조용히 배포를 해 버립니다.

💡 실무에서는
• 함수를 편입할 때 zip 을 어디서 구했는지보다 해시가 맞는지를 먼저 봅니다. 맞지 않으면 그 zip 은 원본이 아니에요
• 해시는 PR 본문과 README 에 함께 적어 둡니다. 나중에 "이 zip 이 정말 그때 그 코드인가"를 다시 물을 때 기준이 돼요
• 소스에서 zip 을 새로 만드는 방식(archive_file)은 이 단계에서 쓰지 않았어요. 압축할 때 들어가는 타임스탬프 때문에 해시가 달라져서, 첫 apply 가 코드를 재배포합니다. 그 전환은 2차로 미뤘어요

ADR 은 다른 선택지 둘도 적었어요. 배포 파이프라인을 먼저 바꾸는 정석은 범위가 너무 커서 탈락했습니다. 여섯 중 셋은 코드를 갖고 있는 저장소조차 없었거든요. 그걸 기다리는 동안 함수 설정은 계속 코드 밖에 남아요. 그리고 원본 zip 을 커밋하는 방식에도 분명한 비용이 있어서, 그게 다음 장의 이야기입니다.

결과만 정확히 적을게요. 1차 대상 여섯 중 다섯을 이틀에 걸쳐 편입했어요. 나머지 하나는 편입 전에 해야 할 선행 작업이 드러나서 뒤로 미뤘습니다. 해시가 맞는다고 다 들여오는 건 아니었어요.

3. zip 만 있으면 리뷰가 안 된다

첫 함수를 편입한 PR 을 열자마자 문제가 보였어요. 함수 코드에 대해 리뷰어가 볼 수 있는 diff 가 이것뿐이었습니다.

Binary files /dev/null and b/stacks/{스택}/prod/lambda/{함수}.zip differ

"바이너리 파일이 다르다"는 한 줄이에요. 이 함수가 무엇을 하는지, 어디에 쓰는지, 예외를 어떻게 다루는지 PR 에서 하나도 안 보입니다. 앞으로 이 함수의 코드를 바꾸는 PR 도 전부 이 한 줄로만 보일 거고요. 코드를 저장소로 가져온 이유가 리뷰와 이력인데, 가져온 코드가 읽히지 않는 거예요.

그래서 두 시간쯤 뒤에 PR 하나를 더 올렸어요. 같은 zip 을 푼 소스를 바로 옆에 함께 커밋했습니다.

lambda/ {함수}.zip Terraform 이 가리키는 것. 실물에서 회수한 원본 src/{함수}/ 사람이 읽는 것. 위 zip 을 푼 것 README.md 왜 둘인지, 어긋났는지 확인하는 법 filename 이 가리키는 것은 zip 뿐이다. src/ 는 Terraform 이 읽지 않는다. apply 영향 0, plan 은 No changes 여야 한다.

이렇게 두면 리뷰는 src/ 의 diff 로 하고, 배포는 여전히 바이트가 검증된 zip 으로 합니다. 편입의 전제인 "실물을 바꾸지 않는다"를 건드리지 않고 읽을 수 있는 소스를 얻은 거예요.

⚠️ 주의: 같은 코드가 두 군데 적혀 있다
src/ 를 고쳐도 zip 은 그대로라서 배포되지 않습니다. 반대로 zip 만 바꾸면 src/ 가 낡아요. 같은 사실을 두 곳에 적으면 언젠가 어긋난다는 건 이 시리즈 둘째 날의 주제였어요. 그래서 README 에 "코드를 고쳐야 하면 소스에서 zip 을 만드는 2차 전환을 먼저 한다"고 적어 두었습니다. 지금의 zip 은 state 를 채우기 위한 임시 수단이에요.

그리고 소스를 풀어 둔 덕에 바로 다음 날 하나가 읽혔어요.

4. 한 달 넘게 실패했는데 Errors 는 0 이었다

1차의 마지막 묶음은 DB 클러스터를 매주 한 번 정지시키는 함수와 그 트리거였어요. 쓰지 않는 시간에 DB 를 꺼 두려고 만든 자동화로 보였어요. 그런데 조사해 보니 멈추려는 대상 클러스터가 이미 없었어요. 8월 초에 DB 엔진을 올리면서 구 클러스터를 스냅샷을 뜬 뒤 삭제했는데, 그 클러스터 이름이 함수 코드 안에 직접 적혀 있었습니다.

그 뒤로 이 함수는 매주 깨어나서 이 로그 한 줄을 남기고 끝났어요.

[ERROR] 클러스터 {구 클러스터}를 찾을 수 없습니다.

지정한 이름의 DB 클러스터가 없어서 정지 요청이 실패했다는 뜻이에요. 8월 9일 로그도, 8월 23일 로그도 같았습니다.

이상한 건 여기부터예요. 이 함수에는 실패 알람이 걸려 있었습니다. 스케줄로 도는 함수들을 모아 둔 목록에 이름이 있었고, 조건은 Errors > 0 이었어요. 그런데 한 달 넘게 매주 실패하는 동안 그 알람은 계속 OK 였습니다.

📖 용어: Errors 지표
Lambda 가 함수 호출마다 자동으로 올리는 CloudWatch 지표 중 하나예요. 함수가 처리되지 않은 예외로 끝나거나 타임아웃 같은 실행 오류가 나면 1 씩 늘어납니다. 함수가 값을 반환하고 정상적으로 끝나면 늘지 않아요.

원인은 풀어 둔 소스에서 바로 보였어요. 예외를 잡은 뒤에 다시 던지지 않고, 반환값으로 바꿔서 돌려주고 있었습니다.

except rds_client.exceptions.DBClusterNotFoundFault: logger.error(error_msg) return { 'statusCode': 404, # 실패를 "값"으로 돌려준다 'body': json.dumps({'error': error_msg, ...}) } except Exception as e: logger.error(error_msg) return {'statusCode': 500, ...} # 다른 예외도 같다

코드만 보면 404 와 500 을 돌려주니까 실패를 알리는 것으로 읽혀요. 그런데 Lambda 입장에서 보면 이 함수는 매번 값을 반환하고 정상 종료했습니다. Errors 지표는 "함수가 예외로 끝났는가"를 세는 것이지, 반환값 안에 무슨 숫자가 들어 있는지는 보지 않아요. statusCode 는 HTTP 응답을 만들 때나 의미가 있는 필드인데, 이 함수를 부르는 건 스케줄 규칙이라 그 응답을 읽는 쪽도 없었습니다.

📖 용어: EventBridge 규칙
정해진 시각이나 이벤트가 오면 지정한 대상을 호출하는 AWS 의 스케줄러예요. 이 글의 함수들은 모두 이 규칙이 cron 식으로 깨웁니다. 규칙은 함수를 비동기로 부르기 때문에, 함수가 돌려준 값을 받아서 들여다보지 않아요.
그림 2. Errors 는 "함수가 실패로 끝났나"를 센다. "함수가 실패를 말했나"는 세지 않는다

정리하면 실패를 반환값으로 삼키는 함수는 Errors 지표로 감시할 수 없어요. 로그는 정직하게 [ERROR] 를 남겼는데, 알람은 로그가 아니라 지표를 보고 있었습니다. 감시 목록에 이름이 올라 있다는 사실이 감시되고 있다는 뜻은 아니었어요.

이 함수의 코드는 고치지 않았어요. 편입은 실물을 바꾸지 않는다는 원칙 그대로입니다. 고칠 수 있었지만 두고 온 것이 셋이에요. 콘솔 기본 템플릿의 핸들러가 파일 안에 남아 있는 것, 타임아웃이 3초인 것, 그리고 위의 예외 삼키기입니다. 이 함수는 고쳐 쓸 대상이 아니라 지울 대상이라고 판단했어요.

⚠️ 주의: 고쳐서 살리면 더 위험하다
"대상 클러스터 이름만 지금 것으로 바꾸면 되지 않나" 싶을 수 있어요. 그런데 지금 같은 계열의 클러스터는 운영 트래픽을 받는 DB 입니다. 이름을 바꿔 살리면 매주 그 시각에 운영 DB 가 정지해요. 그래서 코드 주석에 "고칠 것이 아니라 지울 것이다"라고 적어 두었습니다.

아직 끝나지 않은 부분도 적을게요. 같은 감시 목록에 스케줄 함수가 다섯 개 더 있어요. 그중에도 예외를 삼키고 statusCode 로 돌려주는 함수가 있으면, 그 알람도 똑같이 아무것도 못 봅니다. 그 다섯의 코드는 아직 확인하지 않았어요. zip 을 받아 코드를 읽어 봐야 알 수 있는 일입니다.

5. 같은 주에 있었던 작은 일 셋

지우려고 들여오고, 들여온 뒤 삭제를 보류했다

같은 날 아침, 이미 아무 일도 안 하는 구형 앞단 자원 여덟을 편입했어요. 운영과 개발의 로드밸런서, 타깃그룹, 리스너입니다. 등록된 타깃이 0이었고 최근 7일 요청 지표에 데이터포인트가 없었어요.

지울 거면 콘솔에서 바로 지우면 되지 않나 싶지요. 그런데 콘솔에서 지우면 무엇이 사라졌는지 기록이 남지 않아요. 코드로 한 번 담아 두면 삭제 PR 의 plan 에 리소스 하나하나가 드러나고, 사람이 읽은 뒤에 apply 할 수 있습니다. 그 PR 의 diff 가 그대로 삭제 기록이 되고요. PR 제목에 "지우기 위해서다"라고 적었고, 삭제는 다음 PR 로 예정했어요.

다음 날 그 다음 PR 대신 문서 수정 PR 이 들어갔어요. 삭제는 보류한다. 자원을 코드에 담는 것과 지우는 것은 별개의 결정이라는 판단이었습니다. README 의 "다음 PR 이 지운다"는 문장이 곧 실행할 일로 읽혀서, 절차는 그대로 두되 지금 할 일이 아니라고 명시했어요. 편입해 둔 덕에 서두를 이유도 없었습니다. 무엇이 남아 있는지는 저장소만 보면 알 수 있고, 지울 때가 오면 plan 이 전부 보여 주니까요.

연휴 동안의 dev 기동 중지를 CLI 가 아니라 코드로 했다

편입한 함수 중 둘은 dev 서버 일곱 대를 평일 아침 9시에 켜고 매일 밤 9시에 끄는 쌍이었어요. 9월 24일, 연휴 동안 아침 기동을 멈춰야 했습니다. 가장 빠른 방법은 CLI 로 아침 규칙을 끄는 명령 한 줄이에요.

그렇게 하지 않았어요. 그 규칙은 사흘 전에 편입했기 때문에, CLI 로 끄면 코드에는 켜짐, 실물은 꺼짐인 드리프트가 생깁니다. 연휴 중에 누가 그 스택에 다른 일로 apply 하면 규칙이 조용히 다시 켜지고, 아무도 없는 사무실에서 서버 일곱 대가 아침마다 떠요. 그래서 코드에서 규칙 상태를 DISABLED 로 바꿔 apply 했습니다.

resource "aws_cloudwatch_event_rule" "dev_start" { schedule_expression = "cron(...)" # 평일 09:00 KST state = "DISABLED" # 연휴 동안. CLI 로 끄지 않는다 } 밤 9시 정지 규칙은 ENABLED 그대로 둔다. 누가 손으로 켜도 그날 밤에 꺼진다.

밤 정지 규칙을 그대로 둔 것도 이유가 있어요. 연휴 중에 누가 필요해서 서버를 손으로 켜도 그날 밤에 꺼지니까, 켜 둔 채 잊어버리는 일이 막힙니다. 9월 27일에 다시 ENABLED 로 되돌렸어요. 되돌리는 걸 잊었더라도 첫 출근일 아침에 dev 가 안 떠서 바로 드러났을 거예요. 되돌리는 PR 에는 "다시 끌 때도 CLI 가 아니라 코드로 바꾼다"는 규칙만 주석으로 남겼습니다.

dev 배포 실패가 P1 전화로 울렸다

9월 21일에는 전화가 한 번 울렸어요. 배치 서버의 dev 서비스 배포가 실패한 건데, ECS 배포 실패 규칙이 계정의 모든 클러스터를 덮고 환경을 가리지 않아서 운영 장애와 같은 P1 경로(담당자에게 바로 전화가 가는 최고 등급)를 탔습니다. dev 는 즉시 대응할 대상이 아니에요.

그래서 dev 서비스를 전화 대상에서 뺐어요. 다만 알림을 없애지는 않았습니다. 같은 사건을 P2 카드로 #{알림 채널} 에 보내는 규칙을 따로 만들었어요. 완전히 빼면 dev 가 깨져도 아무도 모르니까요. 거르는 기준은 이름의 -dev 가 아니라 서비스 ARN 목록으로 잡았습니다. 이 계정에는 이름과 환경이 어긋나는 자원이 여럿 있었거든요(16편의 주제였어요). 목록에 새 dev 서비스를 빠뜨리면 전화가 한 번 더 오는 쪽으로 실패하니까, 틀려도 안전한 방향입니다.

✍️ 오늘의 요약
8월 27일의 "함수 코드는 소유하지 않는다"는 틀린 판단이 아니었어요. 원본을 구할 수 없다는 전제 위에서는 정확했습니다. 9월 21일에 원본 zip 을 회수하고 그 해시가 실물의 CodeSha256 과 같다는 걸 확인하자 전제가 사라졌고, 그래서 뒤집었어요. 해시 대조가 지켜 준 건 "apply 가 아무것도 안 한다"가 아니라 "apply 가 무엇을 하든 코드는 같다"였고, 그래서 ignore_changes 도 필요 없었습니다.

읽을 수 없는 코드는 소유한 게 아니어서 zip 옆에 푼 소스를 두었고, 그 소스에서 한 달 넘게 매주 실패하던 함수가 보였어요. 그 함수는 예외를 반환값으로 삼켜서 Errors 지표를 한 번도 올리지 않았습니다. 감시 목록에 이름이 있다는 것과 실패가 보인다는 것은 다른 이야기예요.

결정을 뒤집을 때 물을 것은 "그때 내가 틀렸나"가 아니라 "그때의 전제가 아직 참인가"입니다.
