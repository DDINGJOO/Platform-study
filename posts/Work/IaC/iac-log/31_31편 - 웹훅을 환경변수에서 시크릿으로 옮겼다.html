31편. Slack 웹훅을 Secrets Manager로 옮긴 순서 ← 지금 이 글

10월 8일 아침 9시 32분에 값이 없는 시크릿 하나를 만들었어요. 알림 함수들의 환경변수에 평문으로 있던 Slack 웹훅 주소를 옮기기 위해서였습니다.

Slack 웹훅 주소를 알면 연결된 대화방에 메시지를 보낼 수 있어요. 비밀로 관리해야 하는 값인데 함수 설정을 조회하면 그대로 보이는 환경변수에 들어 있었습니다.

29편에서 함수를 Terraform으로 가져올 때 환경변수는 관리 대상에서 제외했어요. 비밀 값을 코드에 적으면 저장소에 평문이 남고, 적지 않은 채 환경변수를 관리하면 plan 출력에 기존 값이 찍힐 수 있었기 때문입니다.

이날은 시크릿을 만들고 함수가 그 값을 읽게 바꾼 뒤, 이전 환경변수를 지우는 순서로 작업했어요. 9시 32분부터 12시 40분까지 진행했고, 마지막 커밋에는 앱 코드 수정이 필요해 이전을 보류한 서비스도 기록했습니다.

1. 왜 값이 없는 그릇부터 만들었나 2. 읽기 권한을 함수가 아니라 시크릿에 적은 이유 3. 런타임에 읽게 바꾸면 무엇을 치르나 4. 그제서야 환경변수를 코드로 가져왔다 5. 하나는 못 옮기고 보류로 적었다

1. 시크릿 생성과 값 등록을 나눈 이유

먼저 시크릿을 생성해 값을 등록하고, 함수가 시크릿에서 읽도록 배포한 다음, 이전 환경변수를 삭제했어요. 알림을 유지하면서 값을 옮기려면 이 순서를 지켜야 했습니다.

📖 용어: Secrets Manager
비밀번호나 API 키 같은 비밀 값을 보관하는 AWS 서비스예요. 값을 암호화해 저장하고, 읽기 권한이 있는 프로그램이 실행 중에 조회할 수 있습니다.

Terraform으로는 시크릿 자원과 읽기 권한만 만들었어요. 비밀 값은 사람이 명령줄로 직접 등록했습니다. 이렇게 나눠야 값이 Terraform 코드와 상태 파일에 남지 않아요.

시크릿 값은 함수별 키를 가진 JSON으로 구성했어요. 각 함수는 자기 키에 해당하는 웹훅을 사용하므로, 한 함수의 웹훅을 재발급해 교체할 때 다른 키는 바꾸지 않아도 됩니다. 다만 읽기 권한은 시크릿 단위로 주기 때문에 키를 나눴다고 접근 권한까지 분리되는 것은 아니에요.

값을 등록하기 전에 함수 코드를 바꾸면 조회할 값이 없어 알림 전송이 실패해요. 기존 함수가 환경변수를 읽는 동안 그 값을 먼저 지워도 마찬가지입니다. 새 경로로 값을 읽을 수 있게 만든 뒤 이전 값을 지웠어요.

그림 1. 값 등록과 함수 배포를 마친 뒤 이전 환경변수를 삭제했어요

2. 읽기 권한을 함수가 아니라 시크릿에 적은 이유

함수가 시크릿을 읽으려면 권한도 필요해요. 함수의 실행 역할에 읽기를 허용하는 정책을 붙일 수 있지만, 당시 apply 역할로는 이 작업을 할 수 없었습니다.

📖 용어: 실행 역할 (execution role)
Lambda가 AWS 자원에 접근할 때 사용하는 IAM 역할이에요. 로그를 쓰거나 시크릿을 읽을 수 있는지는 이 역할에 적용되는 권한에 따라 정해집니다.
📖 용어: 권한 경계 (permissions boundary)
역할에 부여할 수 있는 권한의 상한을 정하는 정책이에요. 이 저장소에서는 자동화가 만드는 역할에 권한 경계를 설정하도록 했습니다.

이 함수들은 콘솔에서 만들었고 실행 역할에는 권한 경계가 없었어요. 6편에서 설정한 제한 때문에 apply 역할은 경계가 없는 역할에 정책을 붙일 수 없었습니다. 시크릿 읽기 권한을 추가하려면 이 제한 안에서 다른 방법을 찾아야 했어요.

실행 역할을 수정하는 대신 시크릿의 리소스 정책에 읽기를 허용할 역할을 명시했어요. 시크릿 자원에 정책을 붙이는 방식입니다.

📖 용어: 리소스 정책 (resource policy)
자원에 붙여서 접근을 허용할 대상과 작업을 정하는 정책이에요. 여기서는 시크릿을 읽을 수 있는 실행 역할을 지정했습니다.
⚠️ 주의: 계정 루트 지정만으로 역할에 읽기 권한이 생기지는 않는다
리소스 정책의 허용 대상에는 실행 역할의 ARN을 각각 적었어요. 계정 루트를 지정하면 계정 안의 역할에 읽기 권한을 직접 주는 것이 아니라, IAM 정책으로 권한을 부여하도록 계정에 위임합니다. 당시에는 apply 역할이 실행 역할에 그 정책을 붙일 수 없었으므로, 계정 루트만 지정해서는 대상 함수가 시크릿을 읽을 수 없었어요.
그림 2. 실행 역할을 수정하지 않고 시크릿의 리소스 정책으로 허용했어요

3. 시크릿 조회에 맞춰 제한 시간과 오류 처리를 바꿨다

읽기 권한을 설정한 뒤 다섯 함수의 코드를 고쳤어요. 기존 웹훅 값을 사용하던 부분을 시크릿 조회로 바꿨습니다.

_cache = None def webhook_url(): global _cache if _cache is None: r = boto3.client("secretsmanager").get_secret_value( SecretId=os.environ.get("SECRET_ID", "{시크릿}")) _cache = json.loads(r["SecretString"])["{이 함수의 키}"] return _cache

한 번 읽은 값을 전역 변수에 저장하고 다음 호출부터 재사용해요. 같은 실행 환경에서는 시크릿을 반복해서 조회하지 않습니다. 이 예제에는 캐시 만료나 재조회가 없으므로 Secrets Manager에서 웹훅을 바꿔도 기존 실행 환경에는 바로 반영되지 않아요. 교체할 때는 캐시를 갱신하거나 실행 환경이 새 값을 읽는 시점을 함께 관리해야 해요. 이전 웹훅을 폐기하기 전에는 새 값을 읽고 있는지 확인해야 해요. 이번 기록만으로 그 전환까지 자동화됐다고 볼 수는 없습니다.

📖 용어: 콜드스타트 (cold start)
Lambda가 호출을 처리할 새 실행 환경을 초기화하는 것이에요. 처음 호출하거나 동시 실행이 늘 때처럼 새 환경이 필요한 경우에 발생합니다. 이때는 코드를 올리고 연결을 맺는 시간이 추가로 듭니다. 이미 떠 있는 환경이 재사용되면 이 비용이 없어요.

시크릿 조회 시간은 콜드스타트에 추가돼요. 파이썬으로 된 셋은 기존 제한 시간이 3초였는데, 조회까지 마치기에는 빠듯해 10초로 올렸습니다.

⚠️ 주의: 시크릿을 못 읽었을 때 조용히 지나가면 안 된다
다섯 중 하나는 로그 여러 건을 순회하며 보내고, 한 건이 실패해도 다음 건으로 넘어가게 짜여 있었어요. 조회를 그 반복문 안에 두면 시크릿을 읽지 못해 모든 전송이 실패해도 함수는 정상 종료할 수 있습니다. 알림이 오지 않아도 오류 지표는 0으로 남는 경우예요. 그래서 반복문에 들어가기 전에 조회하고, 실패하면 예외를 던져 함수 오류로 집계되게 했습니다.

다섯 중 하나는 환경변수가 아니라 코드 안에 웹훅이 직접 적혀 있었어요. 배포용 압축 파일을 그대로 저장소에 넣는 방식이어서, 이 값이 포함된 상태로는 편입할 수 없었습니다. 그래서 29편에서 다룬 오전 9시 15분의 첫 편입에서는 제외했어요. 코드에서 웹훅을 지운 뒤 같은 날 낮 12시 13분에 편입한 과정과 구분해야 합니다.

이번에 코드의 웹훅을 삭제하고 시크릿에서 읽도록 바꾸면서 그 함수도 처음 편입했어요. 시크릿을 지운 zip으로 편입과 재배포를 함께 진행한 과정은 29편에 적었어요. 다른 함수에서는 목록으로 오는 값을 사전처럼 읽는 버그도 발견해 수정했어요. 기존 코드는 해당 값을 처리할 때 형 오류가 나는 구조였습니다.

4. 이전 웹훅을 지운 뒤 환경변수를 관리했다

12시 13분에 다섯 함수가 시크릿을 읽도록 바꿨어요. 함수가 더는 사용하지 않는 이전 웹훅 값은 아직 환경변수에 남아 있었습니다.

이 상태에서 환경변수를 바로 Terraform 관리 대상으로 바꾸면 안 됐어요. 29편에서 설정한 변경 무시를 해제하면 실제 환경변수와 코드를 비교합니다. 코드에 이전 웹훅이 없으므로 삭제 계획을 세우면서 plan 출력에 그 값이 나올 수 있어요. 출력이 PR에 첨부되면 평문도 함께 남습니다.

그래서 사람이 명령줄로 이전 웹훅 값을 먼저 지웠어요. 남은 환경변수에 비밀 값이 없는 것을 확인한 뒤 변경 무시를 해제하고, 관리할 값들을 코드에 적었습니다.

# 전환 전: 환경변수에 평문 웹훅이 있어 코드가 손대지 않았다 lifecycle { ignore_changes = [environment] } # 전환 후: 평문을 먼저 지우고, 남은 값만 코드가 소유한다 environment { variables = { DEFAULT_INTERVAL_DAYS = "365" NOTIFY_LEAD_DAYS = "14" } }

전환 전에는 환경변수 변경을 무시했고, 전환 후에는 코드에 적은 값을 기준으로 비교해요. 이후 콘솔에서 값을 바꾸면 drift, 즉 코드와 실제 설정의 차이로 확인할 수 있습니다.

다섯 중 넷은 환경변수 변경 무시를 해제했어요. 그중 하나는 웹훅을 지우고 나니 남은 변수가 없어 환경변수 블록을 두지 않았습니다. 지연 쿼리를 알리는 나머지 하나는 임계값 변수의 실제 값을 아직 확인하지 못해 변경 무시를 유지했어요. 비밀 값은 아니지만 추측해서 코드에 적으면 기존 설정이 바뀔 수 있었습니다.

5. 앱 코드 수정이 필요한 서비스는 보류했다

이날 작업의 마지막 커밋은 12시 40분이었어요. 문서 한 줄을 바꿔 별도 서비스의 시크릿 이전을 보류했다고 적었습니다.

이 서비스는 애플리케이션 코드가 환경변수를 직접 읽고 있어 설정 변경만으로는 이전할 수 없었어요. 먼저 앱 코드를 수정해야 했고, 해당 저장소는 다른 팀이 관리하고 있었습니다.

💡 실무에서는: 보류 사유도 같은 표에 남긴다
완료한 항목과 보류한 항목을 같은 표에 적었어요. 보류한 이유와 먼저 필요한 앱 코드 수정을 남겨, 다른 팀의 작업이 필요하다는 것을 구분했습니다.

알림 함수 다섯은 런타임에 시크릿에서 웹훅을 읽게 됐고, 함수 설정의 이전 웹훅 값은 삭제했어요. 로그를 전달하는 함수의 API 키도 같은 시크릿으로 옮겼으며, 문서에는 오류 없이 동작한 것으로 남아 있습니다. 환경변수 관리로 전환하지 못한 임계값 변수 하나와, 앱 수정이 필요한 서비스 하나는 별도로 남겼어요.

그림 3. 완료한 이전과 후속 작업을 구분했어요
✍️ 작업 정리
시크릿 자원과 권한은 Terraform으로 만들고 값은 명령줄로 등록했어요. 함수가 시크릿을 읽도록 바꾼 뒤 이전 웹훅 환경변수를 삭제해, 평문이 plan 출력에 남지 않도록 했습니다.

실행 역할에는 정책을 붙일 수 없어 시크릿 리소스 정책에 역할 ARN을 각각 지정했어요. 조회 시간이 추가되는 파이썬 함수 셋은 제한 시간을 3초에서 10초로 늘렸고, 조회 실패는 반복문 전에 예외로 처리했습니다.

다섯 함수의 웹훅 조회를 전환했지만 환경변수 관리는 넷만 전환했어요. 임계값 확인이 필요한 함수와 앱 코드 수정이 먼저인 별도 서비스는 후속 작업으로 남겼습니다.
