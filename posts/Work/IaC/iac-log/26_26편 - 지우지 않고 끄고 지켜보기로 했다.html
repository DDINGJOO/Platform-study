26편. CloudFront 배포 넷을 삭제 대신 비활성화한 이유 ← 지금 이 글

10월 7일 아침 10시 19분, CloudFront 배포 두 개를 비활성화했어요. 운영용과 개발용 한 쌍입니다. 둘 다 활성 상태였고 도메인도 연결돼 있었지만, 그 주소로 들어온 요청은 90일 동안 모두 404였어요. 파일을 제공해야 할 오리진 저장소가 없었거든요.

그날 오후 3시 33분에는 배포 두 개를 더 비활성화했어요. 넷 다 삭제하지 않고, 설정 한 줄을 되돌려 다시 활성화할 수 있는 상태로 남겼습니다.

삭제할 때 필요한 순서를 지키면 비활성화와 마찬가지로 해당 위험을 없앨 수 있었어요. 다만 사용 여부를 잘못 판단했을 때는 배포를 다시 만드는 것보다 비활성화 설정을 되돌리는 편이 간단했습니다. 같은 날 Datadog 쿼리 오류도 로컬에서 검사하도록 바꿨어요. 배포는 복구하기 쉽게 남기고, 쿼리 오류는 CI에 올리기 전에 확인하도록 한 작업입니다.

먼저 배포 상태와 사용 여부를 확인한 근거, 삭제 대신 비활성화를 선택한 이유를 살펴볼게요. 이어서 Datadog 쿼리 린트를 추가하고 검증한 과정을 설명합니다.

1. 켜져 있는데 아무것도 못 주는 배포 2. 지우는 대신 끈 이유 3. 같은 16건이 반대 결론을 냈다 4. CI 에서 처음 죽던 것을 로컬에서 죽게 했다

1. 오리진 없이 활성 상태로 남은 배포

먼저 비활성화한 것은 제휴용 프런트 배포 한 쌍이었어요. 운영용과 개발용 모두 도메인이 연결돼 있었고 인증서도 유효했습니다.

📖 용어: CloudFront 배포와 오리진
CloudFront 배포는 엣지에서 파일을 제공하는 설정이에요. 원본 파일을 가져오는 대상을 오리진이라고 하고, 여기서는 S3 버킷이었습니다. 오리진 버킷이 삭제돼도 배포 설정은 남아 있을 수 있어요.

이 배포들의 오리진 버킷이 없었습니다. 접근 권한 문제가 아니라 버킷 자체가 존재하지 않았어요. 9월 초 조사에서 이런 배포를 다섯 개 찾았고, 그중 셋이 활성 상태였습니다. 당시에는 서비스가 계속 필요한지 담당자가 판단해야 한다고 적어 두고 코드를 변경하지 않았어요.

한 달 뒤, 그중 한 쌍의 사용 여부를 확인했습니다. 판단에 쓴 근거는 네 가지였어요.

🔍 "쓰이지 않는다"를 무엇으로 판정했나
• 오리진 버킷이 존재하지 않았어요. 현재 상태로는 파일을 제공할 수 없었어요
• 배포처를 찾았어요. 프런트 저장소에 2025년 11월에 만든 POC(되는지만 확인해 보는 시험 구현) 앱이 있었고, 그 작업 브랜치는 main 에 머지되지 않은 채로 남아 있었습니다
• 지금의 연동 경로가 달랐어요. 그 제휴는 당시 백엔드 API와 본 서비스 도메인으로 처리하고 있었어요
• 요청 수가 90일 합계 16건이었고 전부 404 였어요. 봇과 스캐너의 요청으로 보였어요

이 가운데 앞의 세 가지로 배포의 용도와 현재 연동 경로를 확인했어요. 요청이 적다는 이유만으로 중단하지 않고, 생성 이력과 대체 경로까지 확인한 뒤 비활성화했습니다.

오리진이 없는 상태로 배포를 계속 활성화해 두는 데에는 위험도 있었어요.

📖 용어: 서브도메인 탈취
도메인이 가리키는 자원이 삭제된 뒤 제3자가 같은 이름의 자원을 만들어, 기존 도메인으로 자신의 내용을 제공하는 일이에요. 이 사례에서는 오리진 버킷 이름이 비어 있는 상태가 문제였습니다.

오리진 버킷 이름이 비어 있으면 제3자가 같은 이름의 버킷을 만들 수 있어요. 그 버킷의 내용이 기존 도메인과 인증서를 통해 제공될 위험이 있었습니다. 배포를 비활성화해 그 경로를 차단했어요. 도메인은 남아 있지만 배포가 요청을 받지 않는 상태입니다.

2. 지우는 대신 끈 이유

삭제도 가능한 선택이었어요. 비활성화한 배포와 삭제한 배포 모두 요청을 받지 않으므로, 해당 위험을 없애는 효과는 같습니다. 다만 삭제할 때는 도메인 레코드를 먼저 제거해야 해요. 그 이유는 3절에서 설명합니다.

차이는 복구 과정에 있어요. 비활성화한 배포는 설정을 true로 바꿔 apply하면 됩니다. 삭제하면 배포 ID가 사라지고 별칭과 인증서 연결도 끊어지므로, 다시 사용하려면 배포를 새로 만들어야 해요.

resource "aws_cloudfront_distribution" "{제휴 POC 배포}" { aliases = ["{도메인}"] # 2026-10-07 비활성. 오리진 버킷이 없어 모든 요청이 404 였다. # 되돌리기: enabled = true enabled = false lifecycle { prevent_destroy = true } } 삭제 순서: Route53 레코드(코드 밖) → 이 배포. 오리진 버킷은 이미 없다. 인증서 · OAC · 방화벽처럼 다른 배포와 공유하는 것은 남긴다.

넷 모두 삭제 순서를 남겼지만, 함께 제거할 자원은 배포마다 달랐어요. 위 운영용 배포는 오리진 버킷이 이미 없고 OAC를 다른 배포와 공유하므로 레코드와 배포만 삭제하면 됩니다. 개발용 배포에는 전용 OAC가 하나 있고, 오후에 끈 둘에는 각각 OAI와 OAC가 하나씩 있어 함께 삭제해야 해요. 공유 자원은 남기고 전용 자원만 삭제하도록 배포별로 확인했습니다. OAC·OAI는 배포가 버킷을 읽을 때 사용하는 신원으로, 25편에서 다뤘어요.

📖 용어: prevent_destroy
Terraform 에게 "이 자원을 지우는 plan 이 나오면 계획 단계에서 실패시켜라"고 적어 두는 설정이에요.

삭제 방지 설정은 네 배포에 모두 적용된 것으로 생각했지만, 확인해 보니 넷 중 셋에만 있었어요. 비활성 배포를 모아 둔 파일의 둘과 개발용 배포에는 있었고, 활성 배포와 같은 파일에 있는 하나에는 빠져 있었습니다. 같은 파일의 다른 배포에는 설정이 있었어요. 실물 설정을 코드로 옮기는 데 집중하다 lifecycle 블록을 빠뜨렸고, 당시에는 아직 추가하지 않은 상태였습니다.

설정이 있는 셋에도 한계는 있어요. prevent_destroy가 막는 것은 해당 설정이 구성에 남아 있을 때 Terraform이 만드는 destroy 계획이에요. 리소스 블록 자체를 제거하거나 콘솔에서 직접 삭제하는 작업, state에서 자원을 제외한 뒤 삭제하는 작업은 막지 못합니다. 콘솔 변경도 다뤄 온 만큼 삭제 방지 설정의 범위를 구분해야 했습니다. 의도한 삭제는 별도 PR과 삭제 대상이 표시된 plan으로 확인해야 해요. 리소스 블록 삭제처럼 이 설정으로 보호하지 못하는 변경도 리뷰해야 하고, 콘솔 등 다른 경로는 권한과 감시로 관리해야 합니다.

비활성화해 둔 배포에도 제약은 남아요. 요금은 거의 없지만 별칭과 오리진 설정이 유지됩니다. 같은 도메인을 다른 배포에 연결하려면 기존 배포에서 별칭을 먼저 제거해야 해요.

그림 1. 비활성화하면 배포 설정을 유지한 채 다시 활성화할 수 있어요

3. 요청 수가 같아도 사용 여부는 달랐어요

오후에 비활성화한 두 배포는 아침과 상황이 달랐어요. 둘 다 그날 낮 12시대에 Terraform 관리 대상으로 편입한 B2B 배포였습니다. 편입은 코드 밖에 있던 실물을 Terraform으로 관리하도록 옮기는 작업이고, 25편에서 다뤘어요. 세 시간 뒤 둘 다 비활성화했지만, 편입할 때 남긴 판단은 달랐습니다. 한쪽에는 담당자가 중단 여부를 판단해야 한다고, 다른 쪽에는 트래픽은 미미하지만 사용 중으로 본다고 적었어요.

담당자 판단이 필요하다고 적은 쪽은 오리진 버킷이 없는 배포였어요. 코드 주석에 남긴 실측은 90일 요청 130건 중 81%가 4xx였습니다. 나머지 19%는 http 요청을 https로 보내는 301 리다이렉트였고, 그 경로를 따라가면 다시 404였어요. 최종적으로 정상 응답을 받은 요청은 없었습니다.

사용 중으로 본 쪽은 응답이 정상 200이었어요. 조직 내 저장소를 찾아봤지만 배포에 사용한 저장소는 찾지 못했고, 90일 요청은 16건이었습니다.

아침에 비활성화한 배포도 요청이 16건이었지만 모두 404였어요. 요청 수는 같아도 한쪽은 오류만 반환했고, 다른 쪽은 정상 응답을 반환했습니다. 사용 여부를 판단하려면 요청 수와 함께 응답 코드도 봐야 했어요.

그림 2. 요청 수에 응답 코드와 담당자 판단을 함께 고려했어요

그림의 세 번째 배포는 요청 수와 응답만으로 사용하지 않는다고 판단하기 어려웠어요. 이 배포를 네 번째로 비활성화한 것은 사용하는 쪽의 결정이었습니다. 그래서 주석에도 자료상으로는 사용 중으로 보였지만 비활성화하기로 결정했다고 남겼어요. 나중에 읽는 사람이 트래픽만 보고 내린 판단으로 오해하지 않도록 했습니다.

네 배포 모두 되돌리는 방법과 삭제 순서를 함께 적었어요. 배포부터 삭제하면 도메인 레코드가 없어진 배포를 가리키게 되고, 서브도메인 탈취 위험이 생깁니다. 그래서 레코드를 먼저 제거한 뒤 배포를 삭제하도록 했어요.

⚠️ 코드와 맞지 않는 주석도 있었어요
주석을 다시 읽어 보니 코드와 맞지 않는 곳도 있었어요. 비활성 배포를 모아 둔 파일은 배포가 다섯 개인데 머리말에는 넷으로 적혀 있었습니다. 아침에 비활성화한 배포의 날짜는 하루 앞이었고, 오후에 비활성화한 배포는 머리말에 없었어요. 블록을 추가하면서 머리말을 갱신하지 않은 상태였습니다. 린트 스크립트도 주석에는 보간 부분을 같은 길이의 자리표시자로 바꾼다고 적혀 있지만, 실제 코드는 한 글자로 바꿔요. 4절은 코드 동작에 맞춰 설명했습니다. 이 주석들의 수정은 별도 PR로 남아 있었어요.

다만 관찰 기준은 정하지 못했어요. 지켜본 뒤 삭제한다고만 적고, 어떤 신호를 얼마 동안 확인할지는 남기지 않았습니다. 다른 작업에는 관찰 기간을 1~2주로 적어 두었지만, 이 배포에는 기간이 없었어요. 비활성화 후 문제가 보고되지 않더라도 언제 삭제해도 되는지 판단하려면 관찰 종료일과 확인 기준이 더 필요합니다.

4. Datadog 쿼리 오류를 로컬 린트에서 확인하기

그날은 Datadog 쿼리 정적 검사도 추가했어요. 계기는 오후 1시 반쯤 실패한 PR이었습니다. 제휴 인증 모니터 넷을 새로 만드는 PR에서 CI의 plan이 다음 오류를 반환했어요.

monitor/validate 400 "query is invalid" 나쁨 sum:m{env:prod,result:fail,error_type IN (a,b)} 좋음 sum:m{env:prod AND result:fail AND error_type IN (a,b)}
📖 용어: 태그 필터
Datadog 쿼리에서 중괄호 안에 적는 조건 묶음이에요. env:prod,result:fail 처럼 쉼표로 이으면 전부 만족하는 것만 고릅니다. IN, AND, OR 같은 연산자를 쓸 수도 있는데, 쉼표와 연산자를 한 중괄호 안에 섞으면 안 돼요. 연산자를 쓰기로 했으면 전부 AND 로 이어야 합니다.

같은 쿼리는 지표 조회 도구에서 결과를 반환했어요. 임계값을 정할 때도 문제가 보이지 않았고 기존 로컬 린트도 통과했습니다. 모니터를 만드는 CI의 plan 단계에서야 쿼리가 유효하지 않다는 오류를 확인할 수 있었어요.

해당 PR에서는 쿼리를 모두 AND로 연결해 통과시켰고, 모니터 파일 상단에도 주의사항을 남겼어요. 하지만 다른 파일에 모니터를 추가하는 사람은 그 주석을 보지 못할 수 있습니다. 주석을 읽고 기억하는 데에만 의존하지 않도록 로컬 검사에도 같은 조건을 추가하기로 했어요.

그림 3. CI plan에서 확인하던 오류를 로컬 린트에서도 검사해요

검사 스크립트는 모니터 쿼리의 중괄호 안을 확인해요. 괄호 밖에 쉼표와 불리언 연산자가 함께 있으면 위반으로 처리합니다. 필터와 다른 구문은 제외해야 했어요. 그룹을 나누는 by {a,b}와 알림 문구의 {{#is_alert}}는 검사 대상이 아니고, 대시보드 위젯도 검증 경로가 달라 제외했습니다.

${...}로 값을 넣는 쿼리도 검사해요. 이번에 실패한 쿼리가 변수에 들어 있던 보간 문자열이었기 때문입니다. 보간 부분은 한 글자 자리표시자로 바꿔 중괄호 경계를 유지한 채 확인합니다.

# scripts/lint.sh check "Datadog 쿼리 필터 검사" python3 scripts/check-dd-query-filters.py check "Datadog 쿼리 필터 자기검사" python3 scripts/check-dd-query-filters.py --selftest 자기검사 13건 · 현재 저장소 위반 0건 실패했던 옛 커밋을 넣으면 29행을 정확히 잡는다

현재 저장소에서 위반 0건이 나오는지만으로는 검사 규칙이 동작한다고 보기 어려워요. 그래서 실제로 실패했던 커밋을 입력해 29행의 오류를 찾아내는지 확인했습니다. 자기검사 13건에는 위반 사례와 정상 사례를 함께 넣었어요.

✍️ 정리
CloudFront 배포 넷은 삭제하지 않고 비활성화했어요. 요청 수에 응답 코드와 담당자 판단을 함께 고려했고, 되돌리는 방법과 삭제 순서를 코드 주석에 남겼습니다. prevent_destroy는 넷 중 셋에만 있었으며, 블록과 설정이 구성에 남아 있는 경우의 Terraform destroy 계획을 막아요. 블록 자체를 제거하는 변경은 이 보호 범위에 들어가지 않습니다. 별칭은 계속 유지되고, 삭제 전 관찰 기간과 기준은 정하지 못했습니다.

Datadog 쿼리 오류는 CI plan 전에 로컬 린트에서 확인하도록 했어요. 현재 저장소의 위반 여부뿐 아니라 정상·위반 사례를 넣은 자기검사와 과거 실패 커밋으로도 검사 규칙을 확인했습니다.
