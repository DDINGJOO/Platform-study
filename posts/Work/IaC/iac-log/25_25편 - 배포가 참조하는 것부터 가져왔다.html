25편. CloudFront OAC·OAI를 편입해 배포의 ID 참조를 바꾸기 ← 지금 이 글

10월 7일 오전 10시 43분에 머지한 PR 의 제목은 이랬어요. "배포가 참조하는 CloudFront OAC 23 · OAI 4 를 편입한다." CDN 배포 자체는 한 달 전인 9월 4일에 이미 코드로 담았습니다. 그런데 그 배포 블록을 열어 보면 이런 줄이 있었어요.

origin_access_control_id = "{OAC ID}" # 열네 글자짜리 문자열

이 ID 문자열만으로는 Terraform이 참조 대상의 설정까지 관리하지 않아요. 배포는 코드에 있어도 OAC의 설정은 별도로 확인해야 했습니다.

이날은 엣지 자원 38개를 Terraform 관리 대상으로 편입했어요. 다섯 묶음 모두 import 블록을 추가하고 apply한 뒤 블록을 삭제했습니다. 편입 PR과 삭제 PR 사이의 간격은 9분에서 48분이었어요. 블록을 바로 삭제한 이유는 이 저장소의 CI 검사에 있었습니다.

참조를 바꾸는 과정에서 import 검사, CLI 조회값과 plan의 차이, 공용 방화벽의 관리 범위를 함께 확인했어요.

1. 배포는 코드에 있는데 왜 부속은 밖에 있었나 2. import 블록은 왜 apply 하자마자 지워야 하나 3. CLI 출력과 plan 이 어긋났을 때 무엇을 믿었나 4. 함수 코드가 한 바이트 다르면 무슨 일이 일어나나 5. ALB 열다섯이 공유하는 방화벽을 어떻게 담았나 6. "소유를 정할 근거가 없다"던 셋은 어떻게 됐나

1. 배포가 참조하는 OAC·OAI도 관리하기

CDN 배포가 S3 버킷을 오리진으로 쓸 때, 버킷을 인터넷에 열지 않고도 배포만 읽게 하려면 전용 신원이 필요해요. 그게 OAC 와 OAI 입니다.

📖 용어: OAC · OAI
오리진 접근 제어(Origin Access Control)와 오리진 접근 신원(Origin Access Identity)이에요. S3 오리진에 대한 CloudFront의 접근을 설정하는 데 쓰는 자원입니다. OAI가 먼저 나온 방식이고 OAC가 뒤에 나온 방식인데, 오래된 배포에는 아직 OAI가 붙어 있어요. 배포 설정에는 해당 자원의 ID가 들어갑니다.

drift 잡은 코드와 실제 설정이 어긋났는지 매일 plan으로 확인해요. 점검 범위는 코드가 관리하는 자원입니다. 배포 설정의 변경은 감지할 수 있지만, 배포가 참조하는 OAC의 서명 방식이 콘솔에서 바뀌어도 그 OAC가 관리 대상이 아니면 감지하지 못해요. 배포에 적힌 ID 문자열은 그대로이기 때문입니다.

그래서 27개를 한 PR 로 담았어요. 운영 18개, 개발 9개입니다. 담으면서 배포 쪽 참조도 문자열에서 리소스 속성으로 바꿨어요.

# 전 origin_access_control_id = "{OAC ID}" origin_access_identity = "origin-access-identity/cloudfront/{OAI ID}" # 후 origin_access_control_id = aws_cloudfront_origin_access_control.{이름}.id origin_access_identity = aws_cloudfront_origin_access_identity.{이름}.cloudfront_access_identity_path

배포에 전달하는 값은 전과 같아요. 이제 Terraform이 배포와 OAC·OAI 사이의 의존 관계도 파악합니다. OAC는 ID를 그대로 쓰고, OAI는 origin-access-identity/cloudfront/가 앞에 붙은 경로 형식을 요구해서 전용 속성을 썼어요.

그림 1. 배포의 ID 참조만으로는 OAC·OAI 설정의 변경을 감지하지 못해요

2. apply 뒤 import 블록을 삭제한 이유

이날 다섯 묶음은 모두 편입 PR 뒤에 import 블록을 삭제하는 PR을 머지했어요.

10:43 OAC 23 · OAI 4 편입 → 11:05 import 블록 27개 삭제 (22분) 11:19 CDN 함수 2 편입 → 11:30 import 블록 삭제 (11분) 11:42 공용 WebACL · IP 집합 편입 → 11:51 import 블록 삭제 ( 9분) 12:19 배포 2 편입 → 12:34 import 블록 삭제 (15분) 12:48 배포 2 · OAC 2 · OAI 1 편입 → 13:36 import 블록 삭제 (48분)

편입 PR 과 삭제 PR 이 늘 짝으로 붙어 있어요. 삭제 PR 의 본문은 한 줄짜리가 대부분입니다. "apply 완료."

📖 용어: import 블록
이미 존재하는 자원을 Terraform의 관리 상태인 state에 등록하도록 코드에 적는 블록이에요. 어느 리소스 주소로(to) 어떤 식별자를(id) 가져올지 둘만 적습니다. 명령어로 하던 편입을 코드로 적게 만든 방식이라, PR 리뷰와 plan을 거쳐 편입할 수 있어요.

블록을 바로 삭제한 이유는 plan 잡의 import 단언 때문이에요. 코드의 import 블록 수와 plan의 편입 건수가 같은지 검사합니다. 코드에 import 블록이 N개면 plan에도 import가 N건이어야 해요.

apply가 끝나면 그 자원들은 이미 state에 있어요. 다음 plan의 import는 0건인데 코드에는 블록 27개가 남아 있으니 검사가 실패합니다. 같은 스택을 변경하는 다른 PR도 이 단계에서 실패하기 때문에, 편입이 끝나면 블록을 삭제해야 했어요.

::error::코드에 import 블록이 27개인데 plan 의 import 는 0건입니다. ::error::apply 로 역할을 다한 import 블록이 남아 있을 수 있습니다. 이미 state 에 있는 리소스는 plan 에 import 로 잡히지 않습니다. 해당 블록을 지우고 주석으로 남기세요.

CI 가 실패하면서 원인과 조치까지 같이 말해 주는 메시지예요. 두 번 겪고 나서 스크립트에 적어 둔 문구입니다.

이 단언이 왜 필요했나

이 검사가 생긴 이유는 편입을 판별하던 방식에 있었어요. 자원의 설정을 바꾸지 않는 편입은 plan에서 no-op으로 표시됩니다. 설정 변경이 없다는 뜻이고, 편입 여부는 importing이라는 별도 표시에 담겨요.

문제는 이 저장소의 판정 지점 여섯 곳이 전부 no-op 을 건너뛰고 있었다는 점입니다. 그래서 운영 자원이 state 로 들어오는 PR 인데 사람이 보는 화면은 이랬어요.

PR 코멘트 +0 생성 · ~0 변경 · -0 삭제 · ±0 재생성 · 파괴적 변경 없음 apply 잡 변경 없음 → 스킵 drift 잡 clean 미반영 점검 clean (머지됐는데 apply 안 된 변경을 찾는 잡. 열려 있던 이슈까지 닫힌다)

운영 중인 자원 27개를 편입하는 PR인데 네 화면 모두 편입을 표시하지 못했어요. 이 누락을 막으려고 import 여부를 따로 판별하고, 코드의 블록 수와도 대조하게 했습니다. 당시 검사 주석에는 이미 state에 있는 주소를 import하면 plan이 실패하므로 오탐이 없다고 적혀 있었어요. 하지만 import 블록은 멱등적이라 같은 주소가 state에 있으면 다시 편입하지 않습니다. apply 뒤 블록을 남겨도 다음 plan은 성공하면서 편입 건수가 0이 될 수 있으므로, 이 주석을 오탐이 없다는 근거로 쓸 수는 없어요.

그림 2. 코드의 import 블록 수와 plan의 편입 건수를 대조해요
⚠️ 주의: apply에는 먼저 머지된 변경도 포함돼요
OAC 묶음의 개발 환경 apply에 다른 PR의 변경 하나가 함께 반영됐어요. 미사용 배포를 비활성화하는 변경이 그날 아침에 머지됐지만 아직 적용되지 않은 상태였습니다. 이 저장소의 apply는 기본 브랜치의 현재 상태를 적용하므로 plan 전체를 확인해야 해요. 함께 적용된 변경은 커밋에 적어 두었습니다.

3. CLI 조회값과 plan의 차이를 확인하기

편입하면서 기존 자원의 설정을 유지하려면 코드의 값도 실제 설정과 맞아야 해요. 그래서 CloudShell(브라우저에서 AWS 명령을 실행하는 터미널)에서 값을 조회해 옮겼습니다.

그런데 이날 하루에 세 번, 조회 결과를 그대로 옮겼는데 plan 이 차이를 띄웠습니다.

OAC 하나의 설명 공백이 둘인 줄 알았는데 실물은 하나였다 배포 하나의 설명 CLI 화면에서 한글이 깨져 보였다 다른 배포의 설명 비어 있는 값이었는데 그렇게 보이지 않았다

세 경우 모두 CLI의 텍스트 출력을 읽고 값을 옮기는 과정에서 차이가 생겼어요. 텍스트 화면의 정렬용 공백과 실제 값의 공백을 구분해야 했고, 한글이 깨져 보이는 출력도 확인해야 했습니다.

plan은 프로바이더가 API로 받아 온 값과 코드를 비교해요. ~로 표시된 차이를 확인하면서 옮겨 적은 값이 실제 설정과 다른 부분을 찾았습니다.

📖 용어: plan 의 ~
Terraform 이 plan 에서 쓰는 기호예요. + 는 새로 만듦, - 는 지움, ± 는 지우고 다시 만듦, ~ 는 기존 자원의 속성을 바꿈입니다. 편입 PR 에서 ~ 가 뜨면 "코드가 실물과 다르다"는 신호예요.

세 번 모두 실제 자원의 설정은 유지하고 코드를 고쳤어요. 편입 중이었으므로 plan에 나타난 차이를 그대로 apply하지 않았습니다.

같은 "비어 있음"을 반대로 적어야 했다

값이 비어 있을 때가 특히 까다로웠어요. 두 자원이 정반대였거든요.

OAC 의 description 실물이 빈 문자열 → description = "" 라고 적어야 한다 생략하면 프로바이더 기본값이 들어가 ~ 가 뜬다 IP 집합의 description 실물이 빈 문자열 → 그 줄을 아예 생략해야 한다 "" 를 프로바이더가 받지 않는다

실제 값은 둘 다 비어 있었지만, 프로바이더가 요구하는 표기는 달랐어요. 두 자원 모두 plan을 실행해 차이가 없어지는지 확인했습니다.

그림 3. 빈 description도 자원마다 표기가 달라 plan으로 확인했어요
💡 실무에서는
• 편입 PR 에서 plan 의 기대값은 "import N건, 변경 0건" 입니다. 태그가 바뀌는 것만 예외로 허용했어요
• 태그 외의 속성에 ~가 뜨면 머지하지 않아요. apply하면 해당 설정이 바뀌기 때문입니다
• 판정 스크립트에는 기대 밖 속성이 바뀌면 막는 --expect 기능도 있어요. 사람이 기대 목록을 tags 로 지정해 실행하면 태그 외의 변화는 실패합니다. 다만 당시 CI 호출은 import 블록 수 대조까지였고, 이 속성 검사를 자동 실행한 것은 아니에요
• apply 뒤에는 같은 스택으로 plan 을 한 번 더 돌려 변경 없음을 확인했어요. 첫 묶음은 그 결과를 삭제 PR 본문에 적었습니다

4. 함수 코드의 줄바꿈도 변경으로 잡혔어요

11시 19분에는 CDN 함수 둘을 담았어요. 하나는 광고 식별 파일 두 개를 외부 주소로 돌려보내는 함수고, 하나는 확장자 없는 경로에 .html 을 붙이는 함수입니다.

📖 용어: CloudFront Function
CloudFront에서 요청과 응답을 처리하는 JavaScript 함수예요. 요청이 오리진에 닿기 전에 주소를 바꾸거나 다른 주소로 돌려보내는 용도로 씁니다. 함수 코드도 자원의 속성이라 코드가 다르면 plan에 변경으로 표시돼요.

여기서 24편과 같은 문제를 다시 만났어요. 설정뿐 아니라 코드가 자원의 일부라는 점입니다. 코드를 조회해서 파일로 옮겼는데, 첫 plan 이 차이를 띄웠어요. 원인은 줄바꿈 하나였습니다. 실물에는 파일 끝 줄바꿈이 없는데, 편집기가 저장하면서 붙인 거예요.

resource "aws_cloudfront_function" "{이름}" { name = "{함수 이름}" runtime = "cloudfront-js-2.0" code = trimsuffix(file("${path.module}/cloudfront-functions/{파일}.js"), "\n") publish = true }

trimsuffix 가 파일 끝의 줄바꿈 하나를 떼고 읽는다는 뜻이에요. 저장소에는 줄바꿈이 있는 평범한 파일을 두고, Terraform 에 넘길 때만 뗍니다.

이 차이를 없애야 했던 이유는 publish = true 설정이에요. 코드가 다르면 apply가 새 버전을 운영 단계로 올리므로, 편입 과정에서 함수 코드까지 배포하게 됩니다. 그래서 파일 머리에 plan에 code 변경이 보이면 머지하지 않는다고 적었어요.

⚠️ 주의: 태그 변경은 편입과 함께 허용했어요
이 저장소는 ADR-0013에 따라 규약 태그를 붙이기로 했고, 함수 편입에도 같은 규칙을 적용했어요. 함수 하나의 Service 태그 값이 연결된 배포의 값과 달라서 배포 쪽 값으로 맞췄습니다. 따라서 편입 PR은 import N건과 태그 변경만 허용하는 조건으로 확인했어요. 태그 규약은 28편에서 더 다룹니다.

5. ALB 열다섯이 공유하는 WebACL 편입하기

11시 42분의 PR 은 성격이 좀 달랐어요. 지금까지는 배포 하나에 딸린 작은 부속이었는데, 이번엔 ALB 열다섯 개가 공유하는 웹 방화벽 하나였습니다.

📖 용어: WebACL · 관리형 룰 그룹 · Count
WebACL은 요청의 차단과 허용을 결정하는 규칙 묶음이에요. 관리형 룰 그룹은 AWS가 제공하는 규칙 모음입니다. 개별 규칙의 동작을 Count로 바꾸면 해당 규칙은 요청을 차단하지 않고 집계만 해요.

실제 WebACL에는 규칙이 7개 있었고, 그중 여섯이 관리형 룰 그룹이었어요. 그룹 안의 개별 규칙에 지정한 동작은 46개였습니다. 그중 27개는 Count, 나머지 19개는 Block이었어요.

46개 설정의 이유는 코드에 남아 있지 않았어요. 이번 PR에서는 규칙의 적절성을 다시 판단하지 않고 기존 설정을 그대로 옮겼습니다. 동작 하나를 다르게 적어도 운영 트래픽의 차단 여부에 영향을 줄 수 있기 때문이에요.

파일 머리의 주석은 제가 잘못 적었어요. 46개를 다 세기 전에 Count 설정만 보고 "관리형 룰 그룹의 조정은 콘솔에서 하나씩 Count로 내려 둔 것"이라고 썼습니다. 27개에만 해당하는 설명이고, Block으로 지정한 19개는 설명하지 못해요. 다음 사람이 이 19개를 관리형 룰 그룹의 기본값으로 오해할 수 있어 주석도 수정해야 합니다.

⚠️ 주의: 공용 자원은 변경의 폭이 다르다
이 방화벽은 ALB 열다섯 개에 연결돼 있어요. 규칙 하나를 고치면 연결된 ALB 모두의 차단과 허용에 영향을 줄 수 있습니다. 그래서 파일 머리에 "이 ACL의 규칙을 바꾸는 PR은 대상 ALB의 최근 차단 로그를 먼저 확인한다"고 적어 두었어요. 코드로 관리하면서 변경하기 쉬워진 만큼, 변경 전에 확인할 조건도 함께 적었습니다.

소유 위치도 같이 정했어요. 서비스 스택은 "이 ALB 에 저 방화벽을 붙인다"는 연결만 가지고, 방화벽 본체는 계정 보안을 담당하는 스택이 가집니다. 규칙은 특정 서비스의 사정이 아니라 계정 전체의 보안 정책이니까요.

다만 연결까지 코드로 관리하는 ALB는 열다섯 중 둘뿐이었어요. 두 연결은 이전에 다른 스택에서 편입한 것이고, 이날 편입한 대상은 방화벽 본체였습니다. 나머지 열셋의 연결은 아직 코드 밖에 있었어요.

방화벽 본체와 ALB의 연결은 별도의 관리 대상이에요. 본체를 편입해도 코드에 없는 연결의 해제까지 plan으로 감지할 수는 없습니다. 나머지 연결은 각 스택의 후속 작업 목록에 남겼고, 이날 편입 범위에는 포함하지 않았어요.

6. 소유가 불분명한 배포는 잠정 스택에 편입했어요

마지막 두 묶음은 부속이 아니라 배포 본체 넷이었어요. 그중 셋은 한 달 전에 편입하지 않기로 결정했던 것들입니다.

9월 4일에 각 배포의 관리 스택을 정할 때 기준은 "누가 배포하는가"였어요. 배포 워크플로를 역추적해 그 저장소를 가진 팀의 스택에 넣는 방식입니다. 16편에서 확인한 것처럼 태그와 실제 사용처가 어긋나는 사례가 있어서, 태그만으로 정하지 않았어요.

그런데 셋은 배포 워크플로를 찾지 못했어요. 버킷 이름으로도 배포 ID 로도 조직 전체 코드 검색에 걸리는 것이 문서뿐이었습니다. 수동 배포이거나, 비공개 저장소이거나, 검색 밖이거나요. 그때 문서에 이렇게 적었어요.

소유를 정할 근거가 없으므로 편입하지 않는다. 사람에게 물어야 하는 항목이다.

10월 7일에는 그 셋을 담았어요. 기준을 바꿨기 때문입니다. 하나는 오리진 버킷의 소유로 정했어요. 버킷을 가진 스택이 그 버킷을 쓰는 배포도 갖는다는 규칙입니다.

나머지 둘은 버킷의 관리 스택으로 정할 수 없었어요. 한쪽은 오리진 버킷이 아직 코드 밖이었고, 다른 한쪽은 버킷 자체가 없었습니다. 이 둘은 태그를 근거로 잠정 스택을 정했어요. 태그만으로 소유자를 확정할 수 없다는 이전 판단은 유지했습니다.

두 배포의 근거 수준은 달랐어요. 버킷이 코드 밖에 있는 쪽은 배포 태그와 버킷 태그를 비교할 수 있었습니다. 버킷이 없는 쪽은 배포 자체의 태그만 확인할 수 있었어요.

그런데 커밋 메시지와 코드 주석에는 둘을 합쳐 "배포와 버킷 태그가 모두 같은 곳을 가리킨다"고 적었어요. 버킷이 없는 배포에도 버킷 태그를 확인한 것처럼 쓴 오류입니다. 배포 태그만으로 정한 쪽은 그 한계를 따로 적어야, 나중에 잠정 소유를 재검토할 때 근거를 구분할 수 있어요.

배포 워크플로로 소유자를 확인하지 못한 상태라, 파일 머리에 "소유는 잠정이다", "소유자가 확인되면 옮긴다"고 적었어요. 나중에 이전할 수 있도록 state에서 뺀 뒤 다른 스택으로 다시 넣는 방법도 남겼습니다.

소유자를 확정할 때까지 기다리면 이 배포들은 계속 drift 점검에서 빠져요. 이번에는 소유가 잠정이라는 조건을 남기고 먼저 편입해서, 매일 설정 변경을 점검할 수 있게 했습니다. 소유자가 확인되면 해당 스택으로 옮기기로 했어요.

버킷이 없던 배포는 조회 시 "그런 버킷 없음"이 돌아왔지만, 배포는 켜져 있고 도메인도 살아 있었어요. 이번 편입에서는 그 설정을 그대로 유지했습니다. 주석에 비활성화 여부는 사람이 판단할 항목으로 남겼고, 세 시간 뒤의 판단은 다음 편에서 다뤄요.

편입 순서와 별개로 남은 스택 간 참조

12시 19분에 담은 배포 하나는 자기 OAC 가 아직 코드 밖이었어요. 실측을 안 했거든요. 그래서 그 줄만 ID 문자열로 남겨 두고, 29분 뒤 다음 PR 에서 OAC 를 담으면서 리소스 참조로 바꿨습니다.

이번에는 배포를 먼저 편입한 뒤 OAC를 편입해도 같은 리소스 참조로 바꿀 수 있었어요. 다만 직접 리소스 속성을 참조하려면 같은 state에서 관리해야 한다는 제약이 있습니다. 개발 환경 배포 하나는 운영 스택의 OAC를 공유하고 있어서 ID 문자열을 유지했어요. 이 참조는 편입 순서만 바꿔서는 해결되지 않고 스택 사이에서 값을 전달하는 방법을 따로 정해야 합니다.

9월 4일에 "편입하지 않는다"고 적은 문서는 아직 수정하지 않았어요. 변경한 판단은 코드 주석과 커밋 메시지에만 남아 있어서, 당시 문서와 설명이 어긋나 있습니다.

✍️ 편입 결과와 남은 범위
엣지 자원 38개를 편입하고, 같은 state에 있는 OAC·OAI는 배포에서 리소스 속성으로 참조하게 바꿨어요. CLI에서 옮긴 값은 plan으로 다시 확인했고, 함수 코드의 끝 줄바꿈도 실제 코드와 맞췄습니다.

apply가 끝난 import 블록은 CI의 편입 건수 검사에 맞춰 삭제했어요. 첫 묶음은 두 환경에서 재plan한 결과가 변경 없음인 것도 확인했습니다.

공용 WebACL을 편입했지만 ALB 연결 열셋은 후속 작업으로 남았어요. 잠정 소유의 근거를 잘못 적은 주석과 이전 편입 제외 문서도 정정이 필요한 상태입니다.
