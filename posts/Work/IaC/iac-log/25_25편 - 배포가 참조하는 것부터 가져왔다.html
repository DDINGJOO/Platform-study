10월 7일 오전 10시 43분에 머지한 PR 의 제목은 이랬어요. "배포가 참조하는 CloudFront OAC 23 · OAI 4 를 편입한다." CDN 배포 자체는 한 달 전인 9월 4일에 이미 코드로 담았습니다. 그런데 그 배포 블록을 열어 보면 이런 줄이 있었어요.

origin_access_control_id = "{OAC ID}" # 열네 글자짜리 문자열

Terraform 은 이 값을 그대로 옮겨 적을 뿐이에요. 그 ID 가 실재하는지, 가리키는 대상이 어떤 설정인지, 어제와 같은지는 보지 않습니다. 배포는 코드 안에 있었는데, 배포가 가리키는 것은 코드 밖에 있었어요.

이날 한 일은 그 바깥을 안으로 들이는 작업이었어요. 엣지 자원 38개입니다. 그리고 다섯 묶음 전부가 같은 리듬으로 돌았습니다. import 블록을 넣고, apply 하고, 9분에서 48분 뒤에 그 블록을 지웠어요. 왜 지워야 하는지가 이 글의 중간 이야기예요.

이 글에서 다룰 것은 이렇습니다.

1. 배포는 코드에 있는데 왜 부속은 밖에 있었나 2. import 블록은 왜 apply 하자마자 지워야 하나 3. CLI 출력과 plan 이 어긋났을 때 무엇을 믿었나 4. 함수 코드가 한 바이트 다르면 무슨 일이 일어나나 5. ALB 열다섯이 공유하는 방화벽을 어떻게 담았나 6. "소유를 정할 근거가 없다"던 셋은 어떻게 됐나

1. 배포는 코드에 있는데 부속은 밖에 있었다

CDN 배포가 S3 버킷을 오리진으로 쓸 때, 버킷을 인터넷에 열지 않고도 배포만 읽게 하려면 전용 신원이 필요해요. 그게 OAC 와 OAI 입니다.

📖 용어: OAC · OAI
오리진 접근 제어(Origin Access Control)와 오리진 접근 신원(Origin Access Identity)이에요. 둘 다 "이 배포가 이 버킷을 읽어도 된다"를 증명하는 작은 자원입니다. OAI 가 먼저 나온 방식이고 OAC 가 뒤에 나온 방식인데, 오래된 배포에는 아직 OAI 가 붙어 있어요. 배포 쪽에는 그 자원의 ID 만 적힙니다.

부속을 코드 밖에 두면 무엇이 곤란한지부터 볼게요. 매일 도는 drift 잡(코드와 실물이 어긋났는지 매일 plan 으로 확인하는 잡)은 코드가 소유한 자원만 봅니다. 배포는 소유했으니 배포의 설정이 바뀌면 잡혀요. 그런데 그 배포가 참조하는 OAC 의 서명 방식이 콘솔에서 바뀌어도 drift 는 아무 말도 하지 않아요. 코드에 있는 건 ID 문자열뿐이고, 문자열은 바뀌지 않았으니까요.

그래서 27개를 한 PR 로 담았어요. 운영 18개, 개발 9개입니다. 담으면서 배포 쪽 참조도 문자열에서 리소스 속성으로 바꿨어요.

# 전 origin_access_control_id = "{OAC ID}" origin_access_identity = "origin-access-identity/cloudfront/{OAI ID}" # 후 origin_access_control_id = aws_cloudfront_origin_access_control.{이름}.id origin_access_identity = aws_cloudfront_origin_access_identity.{이름}.cloudfront_access_identity_path

값은 양쪽이 똑같아요. 달라진 건 Terraform 이 둘 사이의 의존 관계를 알게 됐다는 점입니다. 두 줄의 끝이 다른 것도 보실 거예요. OAC 는 ID 를 그대로 쓰고, OAI 는 origin-access-identity/cloudfront/ 가 앞에 붙은 경로 형식을 요구해서 전용 속성을 써야 했습니다.

그림 1. 배포만 소유하면 배포가 기대는 것은 계속 사각지대에 남는다

2. 넣고, apply 하고, 바로 지운다

이날 다섯 묶음의 시각을 나란히 놓으면 리듬이 보여요.

10:43 OAC 23 · OAI 4 편입 → 11:05 import 블록 27개 삭제 (22분) 11:19 CDN 함수 2 편입 → 11:30 import 블록 삭제 (11분) 11:42 공용 WebACL · IP 집합 편입 → 11:51 import 블록 삭제 ( 9분) 12:19 배포 2 편입 → 12:34 import 블록 삭제 (15분) 12:48 배포 2 · OAC 2 · OAI 1 편입 → 13:36 import 블록 삭제 (48분)

편입 PR 과 삭제 PR 이 늘 짝으로 붙어 있어요. 삭제 PR 의 본문은 한 줄짜리가 대부분입니다. "apply 완료."

📖 용어: import 블록
이미 떠 있는 자원을 state 로 데려오라고 코드에 적는 블록이에요. 어느 리소스 주소로(to) 어떤 식별자를(id) 가져올지 둘만 적습니다. 명령어로 하던 편입을 코드로 적게 만든 방식이라, PR 리뷰와 plan 을 거쳐 편입할 수 있어요.

왜 바로 지워야 하는지는 이 저장소의 CI 가 정했어요. plan 잡에 import 단언이라는 단계가 있습니다. 하는 일은 한 문장이에요. 코드에 import 블록이 N개면 plan 에도 import 가 N건이어야 한다.

apply 가 끝나면 그 자원들은 이미 state 에 있어요. 그러면 다음 plan 에서 import 는 0건으로 나옵니다. 그런데 코드에는 블록이 27개 그대로 남아 있죠. 27 과 0 이 다르니 단언이 깨지고, 그 스택의 모든 plan 이 막혀요. 내 PR 뿐 아니라 그 스택을 건드리는 다음 사람의 PR 까지요.

::error::코드에 import 블록이 27개인데 plan 의 import 는 0건입니다. ::error::apply 로 역할을 다한 import 블록이 남아 있을 수 있습니다. 이미 state 에 있는 리소스는 plan 에 import 로 잡히지 않습니다. 해당 블록을 지우고 주석으로 남기세요.

CI 가 실패하면서 원인과 조치까지 같이 말해 주는 메시지예요. 두 번 겪고 나서 스크립트에 적어 둔 문구입니다.

이 단언이 왜 필요했나

단언이 있다는 사실보다, 이게 왜 생겼는지가 더 중요해요. Terraform 은 편입을 plan 에서 no-op 으로 표시합니다. "아무것도 바꾸지 않음"이라는 뜻이에요. 실제로 자원의 설정은 안 바뀌니까 거짓말은 아닙니다. 편입이라는 사실은 importing 이라는 별도 표시에 담겨요.

문제는 이 저장소의 판정 지점 여섯 곳이 전부 no-op 을 건너뛰고 있었다는 점입니다. 그래서 운영 자원이 state 로 들어오는 PR 인데 사람이 보는 화면은 이랬어요.

PR 코멘트 +0 생성 · ~0 변경 · -0 삭제 · ±0 재생성 · 파괴적 변경 없음 apply 잡 변경 없음 → 스킵 drift 잡 clean 미반영 점검 clean (머지됐는데 apply 안 된 변경을 찾는 잡. 열려 있던 이슈까지 닫힌다)

운영 중인 자원 27개가 코드의 관리 아래로 들어오는데 네 화면 전부가 "아무 일도 없음"이에요. 단언은 그 빈 창을 막으려고 붙인 겁니다. 그리고 오탐이 날 수 없는 구조예요. 이미 state 에 있는 주소를 import 하려 하면 plan 자체가 실패하니까, "plan 은 성공했는데 import 가 모자라다"는 상황은 블록이 남아 있을 때뿐이거든요.

그림 2. 편입 PR 이 "아무 일도 없음"으로 보이기 때문에, 블록 수를 따로 센다
⚠️ 주의: apply 는 내 PR 만 들고 가지 않는다
OAC 묶음의 개발 환경 apply 결과에 다른 PR 의 변경 하나가 같이 반영됐어요. 미사용 배포를 비활성화하는 변경이 그날 아침에 머지돼 있었고, 아직 apply 되지 않은 상태였거든요. apply 는 내 브랜치가 아니라 기본 브랜치의 현재 상태를 적용합니다. 그래서 plan 을 읽을 때 "내가 쓴 줄"이 아니라 plan 전체를 읽어야 해요. 결과는 커밋에 그대로 적어 두었습니다.

3. CLI 출력이 틀리고 plan 이 맞았다

편입의 전제는 이 시리즈 내내 같아요. 실물을 바꾸지 않는다. 그러려면 코드에 적는 값이 실물과 한 글자도 다르면 안 됩니다. 그래서 값은 전부 CloudShell(브라우저에서 바로 AWS 명령을 돌리는 터미널)에서 조회해 옮겼어요.

그런데 이날 하루에 세 번, 조회 결과를 그대로 옮겼는데 plan 이 차이를 띄웠습니다.

OAC 하나의 설명 공백이 둘인 줄 알았는데 실물은 하나였다 배포 하나의 설명 CLI 화면에서 한글이 깨져 보였다 다른 배포의 설명 비어 있는 값이었는데 그렇게 보이지 않았다

세 번 다 범인은 같아요. CLI 의 텍스트 출력은 사람이 읽기 좋게 정리된 화면이지, 저장된 값 그 자체가 아니었습니다. 공백을 정렬에 쓰기도 하고, 터미널 인코딩에 따라 한글이 깨지기도 해요.

반면 plan 은 프로바이더가 API 로 받아 온 값과 코드를 직접 비교합니다. 그래서 ~ 한 줄이 뜨면 그게 실물의 진짜 값이에요.

📖 용어: plan 의 ~
Terraform 이 plan 에서 쓰는 기호예요. + 는 새로 만듦, - 는 지움, ± 는 지우고 다시 만듦, ~ 는 기존 자원의 속성을 바꿈입니다. 편입 PR 에서 ~ 가 뜨면 "코드가 실물과 다르다"는 신호예요.

그래서 세 번 다 코드를 고쳤어요. 실물을 plan 에 맞춘 게 아니라, 코드를 plan 이 보여 준 실물에 맞췄습니다. 이 순서가 반대가 되면 편입이 아니라 변경이에요.

같은 "비어 있음"을 반대로 적어야 했다

값이 비어 있을 때가 특히 까다로웠어요. 두 자원이 정반대였거든요.

OAC 의 description 실물이 빈 문자열 → description = "" 라고 적어야 한다 생략하면 프로바이더 기본값이 들어가 ~ 가 뜬다 IP 집합의 description 실물이 빈 문자열 → 그 줄을 아예 생략해야 한다 "" 를 프로바이더가 받지 않는다

실물의 상태는 똑같이 "비어 있음"인데, 적는 법은 반대예요. 외워서 맞출 수 있는 종류가 아니라서, 둘 다 plan 을 돌려 보고 알았습니다.

그림 3. 빈 값은 자원마다 표기법이 달라서, 외우지 말고 plan 으로 확인한다
💡 실무에서는
• 편입 PR 에서 plan 의 기대값은 "import N건, 변경 0건" 입니다. 태그가 바뀌는 것만 예외로 허용했어요
• ~ 가 뜨면 머지하지 않습니다. apply 하면 그 차이만큼 운영 자원이 바뀌니까요
• CI 에는 "기대 밖 속성이 바뀌면 막는" 검사도 같이 있어요. 기대 목록을 tags 로 주면 태그 외의 변화는 전부 실패로 떨어집니다
• apply 뒤에는 같은 스택으로 plan 을 한 번 더 돌려 변경 없음을 확인했어요. 첫 묶음은 그 결과를 삭제 PR 본문에 적었습니다

4. 코드가 한 바이트 다르면 배포가 된다

11시 19분에는 CDN 함수 둘을 담았어요. 하나는 광고 식별 파일 두 개를 외부 주소로 돌려보내는 함수고, 하나는 확장자 없는 경로에 .html 을 붙이는 함수입니다.

📖 용어: CloudFront Function
CDN 가장자리에서 요청과 응답을 손보는 아주 작은 JavaScript 예요. 요청이 오리진에 닿기 전에 주소를 바꾸거나 돌려보내는 용도로 씁니다. 함수 코드 자체가 자원의 속성이라, 코드를 바꾸면 자원이 바뀝니다.

여기서 24편과 같은 문제를 다시 만났어요. 설정뿐 아니라 코드가 자원의 일부라는 점입니다. 코드를 조회해서 파일로 옮겼는데, 첫 plan 이 차이를 띄웠어요. 원인은 줄바꿈 하나였습니다. 실물에는 파일 끝 줄바꿈이 없는데, 편집기가 저장하면서 붙인 거예요.

resource "aws_cloudfront_function" "{이름}" { name = "{함수 이름}" runtime = "cloudfront-js-2.0" code = trimsuffix(file("${path.module}/cloudfront-functions/{파일}.js"), "\n") publish = true }

trimsuffix 가 파일 끝의 줄바꿈 하나를 떼고 읽는다는 뜻이에요. 저장소에는 줄바꿈이 있는 평범한 파일을 두고, Terraform 에 넘길 때만 뗍니다.

왜 이렇게까지 맞췄는지는 publish = true 에 있어요. 코드가 다르면 apply 가 새 버전을 만들어 운영 단계로 올립니다. 그러니까 편입 PR 하나가 배포 행위가 되는 거예요. 그래서 이 파일 머리에 규칙을 적어 두었습니다. plan 에 code 변경이 보이면 머지하지 않는다.

⚠️ 주의: 편입이 실물을 바꾼 항목이 하나 있다
"편입은 실물을 바꾸지 않는다"에 예외를 하나 뒀어요. 태그입니다. 이 저장소는 모든 자원에 규약 태그를 붙이기로 했고(10편과 28편의 주제예요), 편입하면 그 규칙이 함수에도 걸려요. 함수 하나는 실물의 Service 태그 값이 그 함수가 붙어 있는 배포의 값과 달랐는데, 배포 쪽 값으로 맞췄습니다. 그래서 편입 PR 의 plan 은 "import N건, 변경은 태그뿐" 이 기대값이에요. 태그 밖의 변경이 섞이면 그건 편입이 아닙니다.

5. ALB 열다섯이 공유하는 방화벽 하나

11시 42분의 PR 은 성격이 좀 달랐어요. 지금까지는 배포 하나에 딸린 작은 부속이었는데, 이번엔 ALB 열다섯 개가 공유하는 웹 방화벽 하나였습니다.

📖 용어: WebACL · 관리형 룰 그룹 · Count
WebACL 은 "어떤 요청을 막고 어떤 요청을 통과시킬지" 규칙을 모아 둔 묶음이에요. 관리형 룰 그룹은 AWS 가 만들어 파는 규칙 꾸러미고요. 꾸러미 안의 개별 규칙은 Count 로 내릴 수 있는데, 차단하지 않고 세기만 한다는 뜻입니다. 정상 요청까지 막는 규칙을 꺼 두는 흔한 방법이에요.

실물을 읽어 보니 규칙이 7개였고, 그중 여섯이 관리형 룰 그룹이었어요. 꾸러미 안쪽 개별 규칙 조정은 46개였고, 그중 27개가 Count 로 내려져 있었습니다. 절반이 넘어요.

이 46개는 누군가 콘솔에서 하나씩 내린 판단이에요. 왜 내렸는지는 코드 어디에도 없고요. 그래서 이 PR 이 한 일은 그 판단을 평가하지 않고 그대로 옮겨 적는 것이었어요. 46줄 중 한 줄이라도 다르게 적으면 운영 트래픽의 차단 여부가 바뀝니다.

⚠️ 주의: 공용 자원은 변경의 폭이 다르다
이 방화벽은 ALB 열다섯 개에 한꺼번에 걸려 있어요. 규칙 한 줄을 고치면 열다섯 개 서비스의 차단과 허용이 동시에 바뀝니다. 그래서 파일 머리에 "이 ACL 의 규칙을 바꾸는 PR 은 대상 ALB 의 최근 차단 로그를 먼저 확인한다"고 적어 두었어요. 소유를 가져왔다는 건 고치기 쉬워졌다는 뜻이기도 해서, 쉬워진 만큼 앞에 문장을 하나 세워 둔 겁니다.

소유 위치도 같이 정했어요. 서비스 스택은 "이 ALB 에 저 방화벽을 붙인다"는 연결만 가지고, 방화벽 본체는 계정 보안을 담당하는 스택이 가집니다. 규칙은 특정 서비스의 사정이 아니라 계정 전체의 보안 정책이니까요.

6. "소유를 정할 근거가 없다"던 셋을 담았다

마지막 두 묶음은 부속이 아니라 배포 본체 넷이었어요. 그중 셋은 한 달 전에 편입하지 않기로 결정했던 것들입니다.

9월 4일에 배포들의 소유를 한 벌씩 정할 때 기준은 "누가 배포하는가"였어요. 배포 워크플로를 역추적해 그 저장소를 가진 팀의 스택에 넣는 방식이에요. 태그를 믿지 않는 이유는 16편에 적었습니다. 태그와 실물이 어긋나는 사례가 실제로 나왔거든요.

그런데 셋은 배포 워크플로를 찾지 못했어요. 버킷 이름으로도 배포 ID 로도 조직 전체 코드 검색에 걸리는 것이 문서뿐이었습니다. 수동 배포이거나, 비공개 저장소이거나, 검색 밖이거나요. 그때 문서에 이렇게 적었어요.

소유를 정할 근거가 없으므로 편입하지 않는다. 사람에게 물어야 하는 항목이다.

10월 7일에는 그 셋을 담았어요. 기준을 바꿨기 때문입니다. 하나는 오리진 버킷의 소유로 정했어요. 버킷을 가진 스택이 그 버킷을 쓰는 배포도 갖는다는 규칙입니다.

나머지 둘은 버킷으로 정할 수 없었어요. 한쪽은 오리진 버킷이 아직 코드 밖이었고, 다른 한쪽은 버킷 자체가 없었습니다. 그래서 배포와 오리진 버킷에 붙은 태그가 같은 곳을 가리킨다는 것을 근거로 삼았어요. 16편에서 믿지 않겠다고 적은 그 태그입니다. 소유를 확정하는 근거로는 못 쓰지만, 잠정으로 둘 자리를 고르는 근거로는 쓰기로 했어요.

이게 기준을 낮춘 게 맞아요. 그래서 낮춘 만큼을 코드에 적었습니다. 파일 머리에 "소유는 잠정이다", "소유자가 확인되면 옮긴다"를 쓰고, 옮기는 방법까지 적어 뒀어요. state 에서 뺀 뒤 다른 스택으로 다시 넣는 두 단계입니다.

바뀐 판단의 핵심은 이거예요. 편입은 소유를 확정하는 일이 아니라 자원을 코드가 보이는 곳으로 옮기는 일입니다. 소유 결정을 기다리는 동안 그 배포들은 계속 코드 밖에 있었고, 그동안은 누가 무엇을 바꿔도 아무도 몰랐어요. 잠정으로 담아 두면 적어도 매일 돌아가는 drift 가 봅니다. 나중에 소유자가 확인되면 옮기는 비용은 PR 하나예요.

버킷이 없던 그 배포는 담고 나서 더 분명해졌어요. 조회하면 "그런 버킷 없음"이 돌아오는데, 배포는 켜져 있고 도메인도 살아 있습니다. 그래도 고치지 않고 그대로 담았어요. 편입은 실물을 바꾸지 않으니까요. 주석에는 "끌지 말지는 사람이 판단한다"만 적어 두었고, 세 시간 뒤에 그 판단을 한 이야기는 다음 편의 주제예요.

부속이 먼저라는 순서가 늘 지켜지지는 않았다

12시 19분에 담은 배포 하나는 자기 OAC 가 아직 코드 밖이었어요. 실측을 안 했거든요. 그래서 그 줄만 ID 문자열로 남겨 두고, 29분 뒤 다음 PR 에서 OAC 를 담으면서 리소스 참조로 바꿨습니다.

순서를 뒤집어 본 셈인데, 결과는 똑같았어요. 중요한 건 "부속을 먼저"가 아니라 참조하는 쪽과 참조되는 쪽이 같은 state 안에 있어야 리소스로 이을 수 있다는 제약이었습니다. 실제로 개발 환경 배포 하나는 운영 스택의 OAC 를 공유하고 있어서, 스택이 달라 지금도 문자열로 두었어요. 이건 순서의 문제가 아니라 스택 경계의 문제라 다른 해법이 필요합니다.

그리고 아직 안 한 것도 적어 둘게요. 9월 4일의 "편입하지 않는다"가 적힌 문서는 그대로입니다. 뒤집힌 판단은 코드 주석과 커밋 메시지에만 남아 있어요. 같은 사실이 두 군데 적혀 있을 때 한쪽만 고치면 어떻게 되는지는 이 시리즈 둘째 날의 주제였는데, 지금 제가 그 상태를 만들어 둔 겁니다.

✍️ 오늘의 요약
배포를 코드로 담았다는 말이 배포가 기대는 것까지 담았다는 뜻은 아니었어요. 배포 블록 안의 ID 문자열은 어제와 오늘이 늘 같아서, 그 문자열이 가리키는 자원이 콘솔에서 바뀌어도 drift 는 아무 말을 하지 않습니다. 이날 담은 38개는 거의 다 그런 부속이었어요.

편입마다 import 블록을 넣고 apply 한 뒤 바로 지운 건 정리벽이 아니라 CI 때문입니다. Terraform 은 편입을 "아무것도 바꾸지 않음"으로 표시하고, 그래서 운영 자원이 들어오는 PR 이 빈 PR 처럼 보여요. 그 빈 창을 막으려고 코드의 블록 수와 plan 의 편입 건수를 대조하는 단언을 붙였고, 블록이 남으면 그 스택의 모든 plan 이 멈춥니다.

그리고 값은 CLI 화면이 아니라 plan 이 알려 줬어요. 공백 하나, 깨진 한글, 빈 문자열까지 세 번 다 그랬습니다. 코드를 실물에 맞추는 일에서 믿을 것은 사람이 읽기 좋게 꾸민 출력이 아니라, 기계가 실물과 코드를 직접 비교한 결과입니다.
