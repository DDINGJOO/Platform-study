15편. 권한 검사기가 놓친 needs 참조와 actionlint의 검사 범위 ← 지금 이 글

어제 워크플로 파일이 무효가 되면서 잡이 하나도 생성되지 않았어요. 실행 로그가 없었고 인프라 변경도 반영할 수 없었습니다. 같은 결함을 파일만 읽고 확인할 수 있도록 검사기를 만들어 PR 체크에 추가했어요.

그런데 오늘도 잡 0 개인 실행이 생겼어요. 화면에는 어제와 같은 문장이 나왔습니다. This run likely failed because of a workflow file issue. 워크플로 파일에 문제가 있어 실행하지 못했다는 뜻이에요.

PR 체크와 어제 만든 검사기는 모두 통과했어요. 검사기는 권한만 확인하도록 만들었고, 오늘의 원인은 그 범위에 없었습니다. 어떤 조건을 빠뜨렸는지 확인하면서 자체 검사기로 어디까지 검사해야 하는지도 다시 살펴봤어요.

1. 어제 만든 검사기가 무엇을 봤나

첫 사고는 재사용 워크플로의 권한 문제였어요. 이 저장소의 apply 파이프라인은 환경별 절차를 _apply-env.yml 하나에 정의하고, 호출부에서 uses:로 불러 씁니다. 재사용 워크플로가 선언한 permissions는 호출 잡이 준 권한의 부분집합이어야 해요. 이를 초과하면 워크플로 파일 전체가 무효가 됩니다. 호출부 두 곳 중 한 곳에 issues: write를 빠뜨려서, 같은 파일의 수동 실행용 dispatch 잡까지 실행할 수 없었어요. 자세한 경위는 8편에 적었습니다.

이때 만든 check-workflow-permissions.py는 호출부와 재사용 워크플로의 권한을 비교해요. 검사 절차는 다음과 같습니다.

1. 워크플로 디렉터리의 모든 .yml 을 연다 2. `uses: ./.github/workflows/...` 로 로컬 재사용 워크플로를 부르는 잡을 찾는다 3. 불려가는 파일의 permissions 각 scope 를 호출 잡이 준 것과 none < read < write 순위로 비교한다 4. 하나라도 모자라면 종료 코드 1

검사기는 워크플로 파일을 전부 파싱하고 모든 잡을 순회했어요. 하지만 잡 사이의 실행 의존성을 지정하는 needs는 읽지 않았습니다. 파일에 정보는 있었지만, 권한 사고를 재발 방지하는 데만 범위를 맞췄기 때문이에요.

2. 문법은 맞고 의미가 틀렸다

오늘은 워크플로에 적어 둔 스택 목록을 디렉터리 스캔으로 바꾸는 작업을 했어요. 스택 하나를 추가할 때마다 워크플로 다섯 곳에 이름을 등록해야 했고, 빠뜨려도 알 수 없었습니다. plan 매트릭스에서 빠지면 validate·tflint·plan이 실행되지 않아도 PR 체크는 통과했어요. 그래서 backend가 있는 디렉터리를 찾아 실행 대상을 매트릭스로 만드는 스크립트를 두었습니다. 디렉터리를 만들면 목록에도 등록되도록 바꾼 거예요.

워크플로 세 파일에 각각 두 부분을 수정해야 했어요. 스캔을 실행하는 discover 잡을 정의하고, 직접 적어 둔 매트릭스를 needs.discover의 출력으로 바꾸는 작업입니다. 세 파일에 두 부분씩, 모두 여섯 군데였어요.

커밋에는 다섯 군데만 반영됐고 한 군데가 빠졌습니다.

커밋 메시지에 적어둔 계획 실제로 커밋에 들어간 것 terraform-plan.yml discover 잡 + 매트릭스 잡 O 참조 O terraform-drift.yml discover 잡 + 매트릭스 잡 O 참조 O terraform-apply.yml discover 잡 + 매트릭스 잡 X 참조 O <-- 여기

세 파일 중 apply 파일에 잡 정의가 빠졌어요. 출력 참조만 추가돼서, 정의되지 않은 잡을 기다리는 상태가 됐습니다.

# terraform-apply.yml — 이 커밋이 남긴 상태 jobs: # discover 잡의 정의가 여기 있어야 했다. 없다. prod-pending: needs: discover # 참조는 들어갔고 strategy: matrix: include: ${{ fromJSON(needs.discover.outputs.prod) }} # 여기도 들어갔다

커밋 메시지에는 세 파일 모두 "discover 잡 +"라고 적었어요. 하지만 실제 diff에 잡 정의가 들어갔는지는 확인하지 못했습니다.

세 검사가 누락을 발견하지 못한 이유

YAML 파서, 자체 검사기, PR 체크에서 각각 무엇을 확인했는지 따져봤어요.

YAML 파서는 needs: discover를 문자열 값으로 읽을 수 있어요. YAML 문법은 맞으므로 파싱에 성공합니다. 하지만 그 이름의 잡이 있는지까지 확인하지는 않아요.

자체 검사기도 needs를 읽지 않아서 통과했어요. 이 커밋에서는 권한 관계가 바뀌지 않았으니, 권한 검사 결과에는 문제가 없었습니다.

8편에서도 확인했듯, 이 저장소의 PR 체크로는 Terraform Apply의 실행을 검증하지 못했어요. GitHub은 워크플로로 run을 만들 때 파일을 파싱하고 잡 그래프를 만듭니다. Terraform Apply의 트리거는 push와 workflow_dispatch뿐이라 pull_request 이벤트에서는 실행되지 않았고, 이 파일의 잡 그래프를 검증한 횟수는 0 회였어요.

누락은 머지 뒤 첫 push에서 드러났습니다. 없는 잡을 needs로 가리켜 잡 그래프를 만들 수 없었고, 해당 파일의 잡은 모두 생성되지 않았어요. 권한 문제였던 어제와 원인은 달랐지만, 실행되지 않는 범위와 화면의 오류 문구는 같았습니다.

3. 무효가 되는 조건 일곱 가지를 대조하다

빠진 discover 잡을 추가하고 검사기에 needs 참조 검사를 넣었습니다. 이름도 check-workflow-permissions.py에서 check-workflows.py로 바꿨어요. 권한 부분집합 위반과 잘못된 needs 참조가 모두 파일 전체를 무효로 만들기 때문에 한 검사기에 두기로 했습니다.

# check-workflows.py 에 추가한 부분 for path in sorted(WF_DIR.glob("*.y*ml")): jobs = (load(path).get("jobs") or {}) for job_name, job in jobs.items(): needs = job.get("needs") or [] if isinstance(needs, str): needs = [needs] for dep in needs: if dep not in jobs: problems.append(f"{path} 의 `{job_name}` 잡이 없는 잡 `{dep}` 을 참조합니다.")

커밋 메시지에 "파일 전체를 무효로 만드는 조건"이라고 쓰다가, 이 조건이 몇 개인지 확인하지 않았다는 걸 알게 됐어요. 권한과 잡 참조 외에 무엇이 남아 있는지 세어봤습니다.

세어봤더니 최소 일곱 개였습니다.

워크플로 파일 하나를 통째로 무효로 만드는 조건 [검사됨] 재사용 워크플로의 permissions 가 호출자가 준 것을 초과한다 (사고 1) [검사됨] needs 가 존재하지 않는 잡을 가리킨다 (사고 2) [ 열림 ] needs 가 순환한다 (A 가 B 를, B 가 A 를 기다린다) [ 열림 ] 재사용 워크플로가 요구하는 필수 입력을 호출부가 안 준다 [ 열림 ] 표현식 문법이 깨졌다 (닫는 중괄호 누락, 없는 함수 호출) [ 열림 ] 같은 파일 안에 잡 ID 가 중복된다 [ 열림 ] needs 에 없는 잡의 출력을 표현식에서 참조한다

일곱 가지 중 검사하는 것은 둘이었어요. 둘 다 실제로 겪은 사고에 대응하며 추가한 조건이었습니다.

특히 재사용 워크플로의 필수 입력 누락을 빠뜨린 점이 아쉬웠어요. 첫 사고와 마찬가지로 호출부와 피호출부 사이의 계약 위반이고, 파일을 정적으로 읽어 확인할 수 있는 조건입니다. 검사기는 이미 두 파일을 열어 둔 상태였으므로 permissions와 함께 inputs도 비교할 수 있었어요. 비교를 추가하는 데 필요한 코드는 열 줄 정도였습니다.

하지만 처음 검사기를 만들 때는 필수 입력 누락까지 확인할 생각을 하지 못했어요. 권한 문제와 관련된 다른 실패 조건을 함께 검토하지 않은 겁니다.

이번에는 사고를 겪을 때마다 해당 규칙만 추가하면서 나머지 조건을 놓쳤어요. 검사기를 추가했더라도 어떤 조건이 아직 검사되지 않는지 함께 확인해야 했습니다.

4. actionlint와 자체 검사기의 범위

처음에는 나머지 다섯 개도 직접 검사하려고 했어요. 하지만 순환 참조를 확인하려면 그래프 탐색이 필요하고, 표현식 문법을 검사하려면 파서가 필요합니다. 모두 구현하면 워크플로 린터를 별도로 만들고 유지하는 일이 돼요.

개별 규칙을 추가하기 전에 다음 순서로 검토했어야 했습니다.

1. 이 실패가 어떤 "클래스"인지 이름을 붙인다 -> "워크플로 파일이 통째로 무효가 되는 것" 2. 그 클래스의 원인 집합을 먼저 열거한다 -> 한 번 겪은 것 하나가 아니라, 알려진 것 전부 3. 그 집합을 이미 아는 도구가 있는지 찾는다 -> 대개 있다. 이건 우리만 겪는 문제가 아니다 4. 도구가 모르는 "우리만의 규칙"에만 자체 검사기를 남긴다

저는 실패 유형과 다른 원인을 살피지 않고 자체 검사기부터 만들었어요. check-workflow-permissions.py라는 이름에서 보듯, 권한 문제 하나만 검사 범위로 잡았습니다.

GitHub Actions 워크플로를 정적으로 검사하는 공개 린터로 actionlint가 있어요. 당시 문서에 적힌 검사 목록을 앞의 일곱 가지와 대조해봤습니다.

actionlint 문서에 명시된 검사 vs 우리가 센 7 개 needs 가 없는 잡을 가리킴 -> 있다 ("undefined jobs in needs") needs 순환 참조 -> 있다 ("cyclic dependencies") 잡 ID 중복 -> 있다 (job/step ID 유일성) 표현식 문법 오류 -> 있다 (${{ }} 렉싱·파싱·타입 검사) 재사용 워크플로 필수 입력 누락 -> 있다 (uses 의 inputs/secrets 검사) 없는 잡의 출력 참조 -> 있다 (컨텍스트 프로퍼티 검사) 재사용 워크플로 permissions 부분집합 -> 문서화된 목록에 없다

문서의 검사 목록에는 일곱 가지 중 여섯 가지가 있었고, 오늘 발생한 없는 잡 참조도 포함됐어요. 기존 린터를 먼저 검토했다면 직접 참조 검사를 추가할 필요가 없었습니다. 저는 코드 열 줄을 더 쓰고도 나머지 다섯 조건은 검사하지 않은 상태였어요.

재사용 워크플로의 권한 부분집합 검사는 당시 문서화된 목록에서 찾지 못했어요. 이 비교를 기준으로 하면 권한 검사는 자체 검사기에 남기고, 오늘 추가한 잡 참조 검사는 기존 린터에 맡길 수 있었습니다.

또 자체 검사기에 남길 것은 저장소의 설계 결정에 따른 규칙이에요. 다음 조건은 일반적인 워크플로 문법만으로 판단할 수 없고, 저장소의 ADR, 즉 설계 결정 문서를 함께 알아야 합니다.

🔧 저장소의 설계 결정에 따른 검사
• 환경 태그 키 정합성: IAM 조건이 참조하는 태그 키와 provider의 default_tags 키가 같아야 해요. 다르면 해당 Deny 조건이 의도대로 적용되지 않을 수 있습니다. (10편)
• 알람 모듈 경계: 알람은 raw 리소스를 직접 선언하지 않고 모듈을 통해 만들도록 정했어요. 직접 선언하면 모듈이 강제하는 규칙을 적용받지 않습니다.
• OIDC 토큰의 top-level 금지: id-token: write를 파일 최상단에 두면 서드파티 코드를 실행하는 잡에도 토큰 발급 권한이 적용돼요.

이 세 조건은 ADR에 적힌 의도를 코드와 대조하는 검사로 남길 수 있어요.
그림 2. 기존 린터의 검사 범위와 자체 검사기에 남길 조건을 나눠봤어요

5. 수동 확인을 반복 가능한 테스트로 남기기

자체 검사기의 유지 비용에는 테스트도 포함돼요. 당시 저장소를 확인했을 때는 검사기 코드는 있었지만, 이를 검증하는 테스트나 픽스처 파일은 없었습니다.

$ ls scripts/ check-alarm-module-boundary.py check-tag-key-consistency.py check-workflows.py discover-stacks.sh verify-iam-boundaries.py $ find . -iname "*test*" -o -iname "*fixture*" (아무것도 없다)

자체 검사기 넷 중 어느 것에도 테스트가 없었어요. 없는 잡 참조를 검사하는 기능은 수동으로 확인했고, 커밋 메시지에 "일부러 없는 잡을 참조하게 만들어 잡히는 것을 확인했다"라고 남겼습니다.

8편에서도 잘못된 입력을 넣어 검사기가 실패하는지 확인해야 한다고 썼고, 이번에도 그렇게 했어요. 다만 수동 확인 결과를 문장으로만 남겨서 다음 변경 때 반복할 수 없었습니다. 예를 들어 리팩터링 중 jobs 대신 빈 딕셔너리를 순회하도록 바뀌어도, 검사기는 종료 코드 0과 "워크플로 검사 통과"를 출력할 수 있어요.

10편에서는 태그 키 변경으로 IAM Deny가 적용되지 않았어요. 알람 문제를 조사할 때는 처음에 432일 단절로 해석했지만, 12편에서 지표 보존 시작일을 단절일로 잘못 읽었다고 정정했습니다. 검사기도 잘못된 입력을 놓치면서 정상 종료하면 문제를 알아채기 어렵습니다. 이번에 그런 오작동이 발생했다는 뜻은 아니고, 이를 확인할 테스트가 없다는 점을 구분해야 해요.

실패 입력과 정상 입력을 함께 보관하기

수동 확인에 쓴 잘못된 입력을 픽스처, 즉 테스트용 입력 파일로 남기면 반복 실행할 수 있어요. 정상 입력은 통과하고 잘못된 입력은 실패하는지 확인하는 테스트를 다음처럼 구성할 수 있습니다. 아래는 당시 구현한 결과가 아닌 제안이에요.

tests/ fixtures/ needs-undefined-job.yml # 없는 잡을 needs 로 참조하는 파일 permissions-superset.yml # 호출자보다 큰 권한을 요구하는 재사용 워크플로 ok.yml # 정상 파일 (거짓 양성 방지) test_check_workflows.sh # 깨진 픽스처엔 종료 코드 1, 정상엔 0 을 요구한다 # static 잡에 스텝 한 줄 - name: 검사기 자체 검사 run: bash tests/test_check_workflows.sh

이를 적용하려면 당시 검사기의 경로 지정 방식도 바꿔야 했어요.

WF_DIR = Path(".github/workflows") # 상수다

검사 대상 디렉터리가 상수라서 인자로 픽스처 디렉터리를 지정할 수 없어요. 다른 검사기들도 저장소 루트를 상수로 두고 있었습니다. 대상 경로를 인자로 받도록 바꾸면, 저장소 파일을 수정하지 않고 별도 입력으로 검사기를 실행할 수 있어요.

🧪 검사기를 만들 때 같이 커밋할 것
• 잘못된 입력 픽스처: 수동으로 실패를 확인한 입력을 파일로 남겨요
• 정상 입력 픽스처: 정상 파일은 통과하는지도 함께 확인해요
• 검사 대상 경로를 인자로: 저장소 파일 대신 픽스처를 지정할 수 있게 해요

수동으로 확인한 입력과 기대하는 종료 코드를 함께 남겨 두면, 검사기 수정 후에도 같은 조건을 다시 확인할 수 있어요.

6. 검사 범위와 남은 작업

이번에는 누락된 잡과 참조 검사를 수정한 뒤, 워크플로 무효의 다른 원인까지 검토했어요.

그전에는 방금 겪은 사고를 재발 방지할 수 있는지만 확인했습니다. 그 확인도 필요하지만, 권한 검사만 통과해도 워크플로 전체가 유효하다고 판단하기에는 범위가 좁았어요.

그래서 같은 실패 유형에 속하는 다른 조건을 먼저 열거하고, 기존 도구가 검사하는 범위와 비교하기로 했습니다.

권한 사고 하나를 수정했을 때는 일곱 조건 중 여섯이 남아 있었고, 오늘 잡 참조 검사를 추가한 뒤에도 다섯은 검사하지 않았어요. actionlint 문서와의 대조는 기존 도구에 맡길 검사와 자체 코드로 남길 검사를 나누는 근거가 됐습니다.

다만 문서 목록을 대조한 것과 린터를 도입해 실행한 것은 구분해야 해요. 여기서 확인한 실행은 누락된 잡을 추가하고, 없는 잡 참조를 수동으로 검사한 데까지입니다. 린터 도입과 픽스처 테스트는 이 기록만으로 완료했다고 할 수 없어요.

✍️ 오늘의 요약
워크플로가 무효가 되는 조건 일곱 가지를 살펴보니, 당시 자체 검사기가 확인하는 것은 권한 부분집합과 없는 잡 참조 두 가지였어요. 두 번째 사고는 권한 검사 범위 밖의 누락 때문에 발생했습니다.

actionlint 문서에서는 여섯 조건을 확인했고, 권한 부분집합 검사는 문서화된 목록에서 찾지 못했어요. 이를 기준으로 기존 린터와 자체 검사기의 역할을 나눌 수 있었습니다. 다만 린터 도입 완료를 확인한 기록은 아니에요.

자체 검사기에는 정상·오류 입력을 남겨 반복 검증할 필요가 있었어요. 대상 경로를 인자로 받고 픽스처를 실행하는 테스트는 당시 구현 결과와 구분해 제안으로 남겼습니다.
