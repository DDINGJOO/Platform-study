19편. CloudWatch 알람 스택 이동 뒤 태그 정정 apply가 필요했던 이유 ← 지금 이 글

CloudWatch 알람 13개를 기존 알람 스택에서 서비스 스택으로 옮겼어요. 알람 정의를 새 스택에 추가하고 기존 스택에서 제거하는 작업이었지만, 두 스택이 서로 다른 state를 사용한다는 점을 고려해야 했습니다.

Terraform의 state는 각 스택이 관리하는 리소스와 속성을 기록해 둔 상태 파일이에요. 이 작업은 한 번의 apply로 끝낼 수 없었고, 기존 알람을 먼저 지우면 새 스택에서 만들 때까지 감시가 비게 됩니다. 그래서 새 스택에 추가하는 1단계와 기존 스택의 관리에서 제외하는 2단계로 나눴어요.

두 단계를 마친 뒤 같은 스택의 다음 PR을 확인하다가, 옮긴 알람 13개가 다시 변경 대상으로 나온 것을 발견했어요. 알람 정의는 그대로였지만 태그가 이전 스택의 값으로 남아 있었습니다. 새 스택에서 태그를 정정하는 세 번째 apply가 필요했어요.

1. 알람을 서비스 스택으로 옮기려는 이유

이 저장소 규약은 알람을 감시 대상의 소유 팀 스택에 두도록 정하고 있어요. 알람 스택과 서비스 스택은 둘 다 플랫폼팀 소유였으므로, 기존 배치가 규약 위반인 것은 아니었습니다.

이동의 근거는 스택 레이아웃 결정에 있었어요. 잠금 단위와 변경의 영향 범위, 롤백 단위를 같게 둔다는 원칙입니다.

서비스 리소스는 이미 서비스 스택으로 옮겼지만 알람은 기존 스택에 남아 있었어요. 임계값을 바꿀 때 두 스택을 확인해야 했고, 파괴적 변경 라벨도 각각 검토해야 했습니다. 리소스와 알람을 함께 관리하도록 잠금과 소유 경계를 맞추려는 작업이었어요.

기존 알람 파일에도 이동 조건이 주석으로 남아 있었어요. 공유 리소스는 data로 읽기만 하고, 서비스별 스택이 생기면 로드밸런서와 알람을 함께 옮긴다는 내용이었습니다.

이번에는 그 조건에 맞는 서비스 스택이 생겼어요. 주석에 적어 둔 조건을 근거로 이동을 진행할 수 있었고, 기존 스택에 계속 둘지를 처음부터 다시 판단할 필요는 없었습니다.

이동 후 기존 스택에는 공통 알림 인프라와 아직 소유 스택이 없는 서비스의 알람이 남았어요.

알람 인프라 스택이 계속 소유하는 것 서비스 스택으로 가는 것 SNS 토픽 · KMS 키 · 구독 · DLQ 특정 리소스 하나를 보는 알람 계정 전체를 덮는 이벤트 규칙 런북 URL 맵 소유 스택이 아직 없는 서비스의 알람 공통 알람 모듈은 그대로 공통 부품이다. 서비스 스택이 그것을 호출한다.

SNS 토픽과 KMS 키처럼 계정 전체가 사용하는 리소스는 알람 인프라 스택이 계속 소유해요. 특정 리소스를 감시하는 알람은 그 리소스와 같은 서비스 스택에서 관리하도록 나눴습니다.

서로 다른 state와 수동 이동의 제약

다만 서로 다른 state 사이에서는 리소스 주소를 그대로 옮기기 어려웠어요. 이 저장소의 권한 구조도 수동 이동에 제약이 있었습니다.

Terraform의 moved 블록은 리소스를 다시 만들지 않고 state 안의 주소를 바꿔줘요. 하지만 한 state 안에서만 동작하므로 스택 A의 리소스를 스택 B의 state로 넘길 수는 없습니다.

상태 이동 명령을 직접 실행하는 경로도 사용할 수 없었어요. 이 저장소의 apply 역할은 환경 이름이 포함된 OIDC 클레임으로만 맡을 수 있고, 사람이 그 자격증명을 받을 경로는 없었습니다. 1편과 4편에서 구성한 신뢰 정책에 따른 제약이에요.

이 조건에서 선택한 방법은 새 스택에서 알람을 만든 뒤 기존 스택의 관리에서 제외하는 것이었어요. 두 PR에서 각각 apply하되, 감시가 끊기지 않도록 순서와 제거 방식을 정해야 했습니다.

2. 먼저 삭제하면 알람이 없는 시간이 생겨요

기존 스택에서 먼저 삭제하면 새 스택이 알람을 다시 만들 때까지 알람이 존재하지 않아요. PR을 연달아 병합하더라도 리뷰와 apply에 걸리는 시간이 있으므로, 공백이 몇 분에서 몇 시간까지 이어질 수 있습니다.

알람이 없으면 감시 대상에 이상이 생겨도 해당 알람으로 통지할 수 없어요. 알람 자체가 사라진 상태를 다른 검사가 제때 찾아주는지도 확인해야 했습니다.

14편에서도 비슷한 문제를 다뤘어요. 알람의 데이터 없음 판정은 알람이 존재할 때만 동작하므로, 알람을 삭제한 상태까지 알려주지는 않습니다.

알람이 사라진 몇 시간 동안, 어디에서 신호가 나오나 데이터 없음 알람 -> 알람이 없으니 데이터 없음도 판정할 것이 없다 파이프라인 심장박동 검사 -> 파이프라인만 본다. 알람 존재 여부는 안 본다 알람 커버리지 검사 -> "감시 밖" 으로 보고할 것이다. 다만 하루 한 번 돈다 terraform plan -> 의도한 변경이니 정상 종료 아무 곳에서도 아무 소리가 나지 않는다. 그리고 그 시간에 실제로 장애가 나면, 아무도 모른다.

커버리지 검사는 목록에서 빠진 대상이 AWS에 남아 있으면 "감시 밖"으로 보고해요. 다만 AWS를 조회하는 일일 드리프트 잡에 붙어 있어서, 몇 시간짜리 공백보다 실행 주기가 길 수 있습니다. 알람을 다시 만든 뒤 검사가 실행되면 이미 복구된 상태만 확인하게 돼요.

4장에서는 같은 검사의 입력 경로도 고쳤어요. 여기서 살펴본 문제는 실행 주기 때문에 공백을 놓치는 것이고, 4장의 문제는 이동한 목록을 읽지 못해 오탐하는 것입니다.

옮길 13개 중에는 정상 타깃 수가 0이 되는 상태를 감시하는 알람도 있었어요. 해당 타깃그룹은 최근 한 달 사이에 실제로 세 번 그 상태가 됐지만, 당시에는 알람이 없어 통지받지 못했습니다. 나중에 지표 이력을 조회해 발견했어요.

그 이력을 보고 만든 알람이었으므로, 스택을 옮기는 동안에도 감시를 유지해야 했습니다.

3. 중복 구간에 필요한 두 조건

그래서 새 스택에 먼저 추가한 뒤 기존 스택에서 제외하기로 했어요. 1단계와 2단계 사이에는 같은 이름의 알람이 양쪽 코드와 state에 함께 존재합니다.

알람 생성 API인 PutMetricAlarm은 같은 이름의 알람이 있으면 갱신하고, 없으면 생성하는 upsert 방식이에요. 따라서 1단계 apply는 실물 알람을 하나씩 더 만든 것이 아니라, 기존 알람 13개에 같은 정의를 다시 적용한 작업이었습니다.

이 중복 구간을 안전하게 유지하려면 생성과 관리 제외 양쪽에 조건이 필요했어요.

먼저 같은 이름과 같은 정의를 반복해서 보내도 알람이 추가로 생기거나 동작이 달라지지 않아야 합니다. 이번에는 upsert 방식이 이 조건에 맞았어요.

기존 스택에서 제외할 때는 삭제 API를 호출하지 않아야 해요. Terraform은 자기 state와 코드를 비교하므로, 코드에서 알람을 지우면 다른 스택도 같은 알람을 관리하는지와 관계없이 삭제를 계획합니다. 양쪽에 정의가 남아 있다는 사실만으로 삭제를 막을 수는 없어요. 5장에서 state에서만 제외한 이유입니다.

따라서 이번 절차는 동일한 정의를 다시 적용하는 1단계와 실물을 삭제하지 않는 2단계를 함께 전제로 했어요. 순서와 두 단계의 동작을 모두 확인해야 했습니다.

상태 갱신 시각으로 확인한 범위

1단계 apply 결과는 13 added였어요. 새 스택의 state에 없던 알람을 등록한 결과이므로, 이 숫자만으로 AWS 알람이 실제로 유지됐는지까지 알 수는 없었습니다.

실물에서는 StateUpdatedTimestamp를 확인했어요. 알람 상태가 마지막으로 바뀐 시각이며, 알람이 리셋되면 갱신되는 값입니다.

1단계 apply 후, 계정의 알람 13개를 조회했다. StateUpdatedTimestamp 전부 엿새에서 열하루 전 사이의 날짜 그대로. apply 시각으로 갱신된 것이 하나도 없다. 이 관측이 배제하는 것 그 구간에 알람이 리셋되어 감시가 빈 일 이 관측이 배제하지 못하는 것 정의가 덮어써지면서 상태만 유지되는 경우

조회 결과에서 확인한 범위는 알람이 리셋되지 않았다는 것까지예요. "파라미터가 하나라도 다르면 CloudWatch가 리셋한다"는 전제는 값을 일부러 바꿔 검증하지 않았습니다. 따라서 이 시각만으로 정의가 같다고 판단하지는 않았어요.

정의는 1단계에서 파라미터를 바꾸지 않았다는 점과, 나중에 나온 plan의 23 unchanged attributes를 함께 확인했어요. 후자는 6장의 태그 정정 apply에서 나온 결과로, 정의가 유지됐다는 사후 근거였습니다.

상태 갱신 시각과 plan은 서로 다른 부분을 확인해 줬어요. 상태가 유지됐다는 관측과 정의가 같다는 근거를 구분해서, 각각 확인한 범위 안에서 판단했습니다.

이름과 정의를 유지하고 중복 구간을 짧게 두기

같은 알람을 갱신하려면 이름도 유지해야 해요. 이름을 바꾸면 기존 알람을 덮어쓰는 절차가 성립하지 않고, 삭제 후 생성 과정에서 히스토리를 잃을 수 있습니다. 실물 알람이 둘인 구간에는 같은 사건이 중복 통지될 수도 있어요. 반대로 이름은 같아도 임계값을 바꾸면 기존 알람의 동작이 달라집니다. 새 스택의 plan은 여전히 1 to add로 보이고 apply도 성공할 수 있어요.

중복 구간에는 두 state가 같은 실물 알람을 관리하지만 잠금은 각 state 안에서만 걸려요. 한쪽 정의가 바뀌면 어느 스택을 나중에 apply했는지에 따라 최종 설정이 달라질 수 있습니다. 그래서 중복 구간을 짧게 유지하고, 그동안 알람 정의를 바꾸는 다른 PR은 섞지 않도록 했어요.

다른 자원에는 같은 절차를 바로 적용하기 어려워요. 이름 충돌, 실물 중복, 중복 통지 여부를 먼저 확인해야 합니다.

⚠️ 다른 자원에 적용하기 전에 확인할 점
• 이름이 유일해야 하는 자원은 같은 이름으로 새로 만들 때 실패할 수 있어요. 버킷, IAM 역할 이름, CDN 도메인 이름은 유일성 범위가 다르므로 각각 확인해야 합니다. 16편의 도메인 이름처럼 중복할 수 없는 경우에는 새 이름으로 만든 뒤 전환하고 기존 이름을 해제하는 별도 절차가 필요해요
• 개수로 과금되거나 쿼터가 있는 자원은 실물을 중복 생성하면 비용과 한도에 영향을 줍니다. 이번 알람은 같은 이름으로 갱신해 개수가 늘지 않았어요
• 이름을 바꾸며 알람을 옮기면 같은 사건을 중복 통지할 수 있어요. 이동 작업에는 이름 규칙 변경을 섞지 않는 편이 안전합니다
같은 이름으로 다시 요청했을 때 기존 객체가 갱신되는지, 오류가 나는지, 별개 객체가 생기는지부터 확인해야 해요.

"감시 공백 0"은 이번에 옮긴 13개에 한정한 말이에요. 이동 작업과 별도로 감시 범위를 검토할 항목도 있었습니다.

해당 판단을 다시 확인할 수 있도록 양쪽 파일에 재검토가 필요하다는 주석을 남겼어요. 검토 사항을 기록한 것이며, 이를 해결했다는 뜻은 아닙니다.

그림 1. 동일한 정의를 먼저 적용하고, 기존 state에서 삭제 없이 제외하는 순서

4. 커버리지 검사도 여러 스택의 목록을 읽도록 수정했어요

알람 위치를 바꾸려면 14편의 커버리지 검사도 수정해야 했어요. 이 검사는 코드의 감시 대상 목록을 모아 AWS 실물과 대조하는데, 종류별로 목록을 읽을 파일 경로를 하나씩 지정하고 있었습니다.

검사가 종류마다 들고 있던 명세 "vpn": { 파일 = 옛 스택의 알람 파일 , 목록 = 이름 -> ID 맵 } ^^^^^^^^^^^^^^^^^^ 경로가 한 개다 이 한 줄이 전제하는 것 이 종류의 감시 대상 목록은 세상에 한 파일로만 존재한다

목록이 기존 스택에 모여 있을 때는 충분한 입력 범위였지만, 서비스 스택으로 나누면 새 위치도 읽어야 했어요.

기존 경로를 그대로 두면 단계별 판정은 다음과 같아요.

경로가 한 개인 검사가 이사를 어떻게 보나 1단계 후 (양쪽 코드에 목록이 다 있다) 옛 스택 파일만 읽는다 -> 옮긴 대상이 거기 그대로 있다 -> 통과 2단계 후 (새 스택에만 목록이 있다) 옛 스택 파일만 읽는다 -> 옮긴 대상이 목록에서 빠졌다 실물은 멀쩡히 돌고 있다 -> "감시 밖" 보고 검사가 못 넘긴 것은 중복 구간이 아니라, 이사가 끝난 뒤의 상태였다

중복 구간에는 기존 파일에 목록이 남아 있어 검사를 통과해요. 문제가 생기는 시점은 2단계 이후입니다. 새 스택에서 알람이 동작해도 검사는 그 목록을 읽지 못해, 매일 "감시 밖"으로 잘못 보고하게 됩니다.

그래서 종류별 파일 경로를 glob 패턴으로 바꿨어요. 패턴에 맞는 알람 파일을 여러 스택에서 찾고, 감시 대상 목록을 합집합으로 모으게 했습니다. 기존에는 VPN만 대조했지만, 옮기는 13개에 포함된 로드밸런서와 DB도 검사하도록 두 종류를 추가했어요.

여러 파일을 합치면서 같은 키가 두 파일에 있을 때의 판정도 필요해졌어요. 이전에는 입력 파일이 하나여서 처리하지 않던 경우입니다.

합치는 함수는 같은 키의 값이 다르면 오류로 중단하고, 같으면 중복 경고만 내도록 만들었어요. 값이 다르면 어느 리소스가 감시 대상인지 확정할 수 없지만, 같은 값의 중복은 이동 중에 의도적으로 생기는 상태이기 때문입니다.

이 판정은 기존 오류 규칙을 완화한 것이 아니라, 합집합 기능과 같은 PR에서 처음 추가한 규칙이에요. "중복이면 오류"로 처리하면 1단계와 2단계 사이의 정상적인 이동 상태를 허용할 수 없다는 점을 구현 전에 검토했습니다. 이후 입력을 의도적으로 바꿔 값이 같은 중복은 경고만 내고, 다른 값은 종료 코드 2로 중단하는지 확인했어요.

오탐의 원인은 입력이 한 파일에만 있다는 전제였어요. 여러 스택에서 관리하는 상태에 맞춰 입력을 넓히고, 새로 생긴 값 충돌은 오류로 구분했습니다.

14편에서 정한 전수 목록과 실물을 대조하는 방식은 유지했어요. 달라진 부분은 전수 목록을 얻는 위치입니다. 한 파일 대신 여러 스택의 목록을 합쳐 대조하도록 바꿨습니다.

다만 이 검사는 알람 리소스 자체가 아니라 목록을 읽어요. 목록에 이름만 선언하고 그 목록으로 알람을 만들지 않으면, 실제 알람이 없어도 감시 중으로 판단할 수 있습니다. 입력을 합쳐도 이 한계는 남아요.

1단계에서 처음에는 새 스택에 목록을 선언하고 알람 이름은 따로 적었어요. 이때 린터가 사용하지 않는 목록을 지적했습니다. 목록을 for_each에 사용하도록 바꿔 알람 이름도 목록에서 나오게 했어요. 커버리지 검사가 확인하지 못하는 목록과 리소스의 연결을 린터가 점검한 경우였습니다.

🔧 정상적인 이동을 오탐한 원인 확인하기
이 검사는 감시 대상 목록이 한 파일에 있다고 가정했어요. 서비스 스택으로 나누면서 입력 범위를 여러 파일의 합집합으로 바꿨습니다.
같은 키가 다른 값을 가리키면 오류로 중단하고, 값이 같으면 이동 중의 중복으로 경고해요. 검사를 끄지 않고 새 배치를 판정할 수 있도록 처리한 것입니다.
다만 같은 값의 중복 경고에는 기한을 강제하는 장치가 없어요. 2단계를 마치면 사라지지만, 작업을 끝내지 않으면 경고가 계속 남는 한계가 있습니다.

5. 기존 state에서 제외하되 실물은 유지하기

1단계를 마쳐도 기존 스택의 state에는 같은 알람이 남아 있어요. 이 상태에서 코드만 지우고 apply하면 기존 스택이 실물 알람을 삭제합니다. 새 스택에 등록됐다는 사실만으로 기존 스택의 삭제 계획이 바뀌지는 않아요.

실물은 두고 state에서만 제외하려고 removed 블록에 destroy = false를 지정했어요. plan에도 더는 관리하지 않지만 삭제하지 않는다는 문구가 나옵니다.

# module.forget_... will no longer be managed by Terraform, # but will not be destroyed # (destroy = false is set in the configuration) Plan: 0 to add, 0 to change, 0 to destroy.

plan의 결과는 0 to destroy예요. destroy = false를 빠뜨리면 삭제 13건이 되지만, 파괴적 변경 라벨은 PR 단위라 그 삭제까지 승인될 수 있습니다. 대상을 구분해 검토할 수 있도록 이 PR에는 다른 파괴적 변경을 섞지 않기로 했어요.

삭제 0건, 재생성 0건인 이 plan도 파괴적 변경 라벨을 요구했어요. 처음에는 "라벨이 필요하면 destroy = false를 빠뜨렸다는 신호"라고 임시 파일에 적었습니다.

그 설명은 잘못됐어요. 2편에서 plan JSON을 읽도록 바꾼 가드는 처음에 생성·변경·삭제·재생성 네 종류만 집계했는데, 이후 그 밖의 액션도 승인 대상으로 보도록 이미 수정해 둔 상태였습니다. 관리 이탈은 네 종류에 포함되지 않아, 수정 전에는 plan 코멘트와 가드가 파괴적 변경이 없다고 판단했어요.

관리 이탈 후에는 실물이 남아도 해당 스택의 코드와 state에서 빠지므로 그 스택의 드리프트 검사가 추적하지 못해요. 이 위험을 검토하려고 네 종류 밖의 액션을 "기타"로 집계하고, 0이 아니면 파괴적 변경으로 취급하도록 한 것입니다.

따라서 라벨 요구는 의도한 동작이었어요. 13개를 기존 스택의 관리에서 제외한다는 점을 명시적으로 승인받도록 한 것이었습니다. 이를 다시 확인한 뒤 코드 주석과 PR 본문에 판정 기준을 정정했어요.

이 PR 의 plan 을 어떻게 읽나 삭제나 재생성이 하나라도 있으면 -> 중단. destroy = false 가 안 먹은 것이다 기타만 13건이면 -> 정상. 관리에서만 빠지는 것이 맞다 숫자가 13 이 아니면 -> 중단. 대상이 잘못 잡혔다는 뜻이다

3편 이후 가드가 실패하면 작업에서 빠뜨린 조건부터 확인하곤 했어요. 이번에는 가드의 구현과 수정 근거를 다시 읽어, 작업 오류가 아니라 관리 이탈에 필요한 승인임을 확인했습니다.

결정 문서의 코드가 인스턴스 주소를 받지 못했어요

2단계에 사용할 코드는 결정 문서에 미리 적어 뒀지만, 실제로 실행하자 주소 문법 오류가 났어요.

# 결정 문서가 처방한 것 removed { from = module.alb_elb_5xx["{서비스}-alb"] lifecycle { destroy = false } } # 실제 결과 Error: Module address must be a module (e.g. "module.foo"), not a module instance (e.g. "module.foo[1]").

당시 관리 이탈 블록은 모듈 주소를 받을 수 있었지만, 인덱스가 붙은 모듈 인스턴스 주소는 받지 못했습니다.

기존 스택은 계정 전수 목록을 for_each로 반복해 알람을 만들고 있었어요. 알람 이름을 목록과 일치시키려는 구조였지만, for_each로 만든 모듈에서 한 서비스에 해당하는 것만 제외하려면 인덱스를 지정해야 했습니다. 그 주소가 거부된 거예요.

인덱스를 받을 수 있는 moved로 임시 주소를 만든 뒤 관리에서 제외했어요. moved와 removed를 다음과 같이 함께 사용했습니다.

# 1) 인덱스 없는 임시 주소로 옮긴다 (state 안에서만, 실물은 그대로) moved { from = module.alb_elb_5xx["{서비스}-alb"] to = module.forget_alb_elb_5xx } # 2) 그 임시 주소를 관리에서 뺀다 removed { from = module.forget_alb_elb_5xx lifecycle { destroy = false } } 알람 13개마다 이 짝을 하나씩. 두 종류 블록 26개짜리 파일이 나온다. 이 파일은 임시다. apply 가 끝나면 지운다. import 블록과 같다.

1장에서는 moved로 서로 다른 state 사이를 옮길 수 없었어요. 여기서는 기존 state 안의 주소만 바꾸므로 사용할 수 있습니다. 인덱스가 없는 임시 주소로 바꾼 뒤 그 주소를 관리에서 제외하는 방식이에요.

이 파일에는 apply 후 지울 임시 파일이라는 설명도 첫 줄에 적었어요. import 블록처럼 한 차례의 작업을 위한 파일이므로, 완료 후 남겨서 이전 대상의 상태를 다시 조사하게 하지 않으려는 목적입니다.

실행이 실패한 뒤 결정 문서에도 정정을 추가했어요. 처음 제시한 코드, 실제 오류 메시지, 임시 주소를 거치는 방법과 그 이유를 함께 남겼습니다. 4편에 이어 이번에도 문서에 적힌 코드를 실행하면서 제약을 확인한 경우예요.

6. 다음 plan에서 발견한 태그 변경 13건

2단계 결과는 0 added / 0 changed / 0 destroyed, 관리 이탈 13건이었어요. 임시 파일을 정리하고 결정 문서도 고친 뒤 두 단계가 끝났다고 판단했습니다.

이후 같은 스택에서 다른 종류의 리소스를 코드로 가져오는 PR을 진행했어요. 그런데 plan에는 예정에 없던 알람 13건의 변경도 포함돼 있었습니다.

원인은 PutMetricAlarm의 태그 처리였어요. 이 API의 태그 파라미터는 알람을 새로 만들 때만 적용됩니다.

기존 알람에 같은 이름으로 요청하면 임계값·주기·차원 같은 정의는 갱신하지만 태그 파라미터는 무시해요. 태그 변경에는 붙이기와 떼기 API를 별도로 호출해야 합니다.

1단계에서 Terraform은 알람 13개를 추가했다고 표시했지만, AWS에서는 기존 알람 정의만 다시 적용됐어요. 태그는 기존 스택의 값으로 남았고 새 스택의 기본 태그는 적용되지 않았습니다.

1단계 plan에서는 아직 이 알람이 새 스택의 state에 없었기 때문에 실제 태그와 비교하지 못했어요.

이사 PR 의 plan (1단계) state 에 그 알람이 없다 -> refresh 할 대상이 아니다 -> 실물 태그를 읽지 않는다 -> 코드와 비교할 것이 없다 -> "13 added" · 태그는 코드에 적힌 대로 새로 붙는다고 표시된다 -> 아무 이상 없음 apply 후, 실제로는 정의는 덮어써졌다 · 태그는 옛 값 그대로 남았다 이제 state 는 "새 태그가 붙어 있다" 고 기록하고 있다 <- 사실과 다르다 같은 스택의 다음 PR 의 plan 이제 state 에 있으므로 refresh 가 실물 태그를 읽어온다 -> 코드와 다르다 -> 알람 13건이 변경으로 뜬다 -> 23 unchanged attributes (정의는 정말 안 바뀌었다는 증거)

이번 생성 계획은 state에 없던 알람의 실물 태그를 refresh하지 않았어요. 따라서 생성 시 지정한 태그가 기존 알람에 적용되지 않았다는 차이는, 알람이 state에 등록된 뒤의 plan에서 드러났습니다.

이 차이는 알람을 등록한 state를 읽는 plan에서 확인할 수 있어요. 다른 스택의 PR이었다면 나오지 않았을 변경이며, 그 경우에는 일일 드리프트 잡이 탐지해야 했습니다.

다음 PR의 변경 17건을 읽다가 발견했어요. CDN 변경은 4건이었고 나머지 13건이 알람 태그였습니다. 드리프트 잡도 같은 차이를 확인할 수 있지만, 다음 날 아침 실행 전까지는 state에 기록된 태그와 실물이 달랐어요.

이번 변경은 알람 동작에 관여하지 않는 태그에 한정됐고, 정정 apply도 태그만 썼어요. plan의 23 unchanged attributes로 정의가 유지됐다는 점도 확인했습니다. 상태 갱신 시각만으로 판단하지 못했던 부분을 함께 대조한 것입니다.

소유 스택과 감시 대상에 맞춰 태그 정하기

태그를 정정하면서 결정 문서의 미결 항목도 판단해야 했어요. 서비스 태그를 기존 값으로 유지할지, 감시 대상 서비스에 맞춰 바꿀지였습니다.

우선 소유 스택을 판별하는 태그는 바꿔야 했어요. 이 저장소는 그 태그로 계정 리소스를 조회해 스택별 인벤토리를 만들어요. 기존 값이 남으면 새 스택 인벤토리에서는 알람 13개가 빠지고, 기존 스택 인벤토리에는 넘긴 알람 13개가 계속 포함됩니다.

10편에서도 태그 키를 바꾼 뒤 IAM 가드가 대상을 찾지 못한 일을 다뤘어요. 이런 조회에 쓰이는 태그는 변경할 때 참조하는 코드도 함께 확인해야 합니다.

미결이었던 서비스 태그는 감시 대상의 컴포넌트와 맞추기로 했어요. 로드밸런서와 VPN 알람에는 백엔드 컴포넌트, DB 알람에는 DB 컴포넌트 값을 사용했습니다.

규약의 <application>-<component> 형식에 맞춰 새 서비스의 컴포넌트를 적는 것이 첫 번째 근거였어요. 기존 값이 나타내던 "플랫폼팀의 L4 감시"는 팀 태그와 계층 태그에 이미 포함돼 있었습니다. 또 저장소의 스크립트·워크플로·대시보드에서 기존 값 참조가 0건이고 .tf 파일에만 있음을 확인했어요. 조회 로직 변경 없이 인벤토리와 비용 분류용 태그만 바꾸는 작업으로 판단했습니다.

값을 바꾸기 전에는 그 값을 읽는 곳을 확인했어요. 참조하는 코드가 있으면 함께 바꿔야 하고, 이번처럼 없으면 태그 정정만 진행할 수 있습니다. 10편에서 누락했던 확인을 이번에는 먼저 한 셈이에요.

그림 2. 기존 알람의 태그는 다음 plan의 refresh에서 차이가 드러났어요
