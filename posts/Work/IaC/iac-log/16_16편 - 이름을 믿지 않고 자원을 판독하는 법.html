16편. 자원 참조로 Terraform 편입 범위와 삭제 대상을 확인하기 ← 지금 이 글

이미 운영 중인 서비스 하나를 IaC 관리로 옮겼어요. 콘솔에서 만든 AWS 자원을 새로 생성하지 않고 Terraform 코드로 관리하는 작업입니다. 코드를 쓰기 전에 어떤 자원이 있는지, 어디까지가 이 서비스 것인지부터 확인해야 했어요.

계정에는 자원이 수백 개 있었어요. 필요한 자원을 빠뜨리면 Terraform 관리 밖에 남고, 다른 서비스가 쓰는 자원을 함께 가져오면 이후 변경이 그 서비스에도 영향을 줄 수 있습니다.

처음에는 태그와 이름으로 검색했어요. 그런데 실제 사용하는 자원을 놓치기도 하고, 이미 삭제된 자원을 조회 결과에서 찾기도 했습니다.

그래서 자원 사이의 참조를 따라 목록을 만들고, 공유 자원인지 다시 확인했어요. S3와 이미지 저장소는 앱 소스와 참조 관계까지 대조해야 했고, DNS는 참조 대상만 보고 잘못 판단한 경우도 있었습니다. 조사 뒤 코드를 정리할 때는 운영 DB 삭제가 plan에 나타나는 실수도 했어요.

1. 이름과 현재 설정이 다른 자원들

계정을 훑으면서 모은 반례가 이렇습니다.

이름이 말하는 것 실제 ───────────────────────────────────────────── NLB 이름에 internal 인터넷에서 접근 가능 NLB 이름에 표시 없음 내부용 · 리스너 0개 ECR 태그 Environment=prod dev 이미지 저장소 리더 이름에 r7g 실제 클래스는 t4g ECS 클러스터 이름에 이 서비스의 옛 런타임 이 서비스 문자열 없음 태그 ManagedBy=manual 이제 Terraform 이 소유 EIP 태그 색인 조회 결과의 70%가 유령

리더 인스턴스는 등급을 낮춰 비용을 줄인 뒤에도 이름을 그대로 쓰고 있었어요. 이름을 바꾸면 그 이름에 연결된 지표와 알람, 대시보드도 영향을 받으니 설정이 바뀔 때마다 맞춰 바꾸기는 어려웠습니다. 이름에 적힌 클래스와 실제 클래스가 달랐던 이유예요.

이름과 태그로 필터링했을 때 놓친 자원과 잘못 포함한 자원은 다음과 같아요.

못 찾는다 서비스 이름으로 ECS 를 찾다가 "클러스터 없음" 이라고 결론냈다 클러스터 이름이 옛 런타임 이름이었다 없는 걸 찾는다 이 계정에서 EIP 태그 조회 결과의 70% 가 이미 삭제된 자원이었다

두 번째 사례에서 사용한 태그 조회는 자원 자체가 아닌 태그 색인을 보고 있었어요. 이 색인이 즉시 갱신되지 않아 삭제한 자원이 한동안 목록에 남았습니다. 이번에 확인한 지연은 1~2주였어요.

이름과 태그가 현재 설정을 반영하는지는 별도로 확인해야 했어요.

2. 감사 로그로 관리 주체를 확인하기

다음으로 자원 구성을 바꾼 관리 API 호출을 감사 로그에서 확인했어요. 태그에 적힌 관리 주체가 실제로 자원을 변경했는지 알아보려는 것이었습니다.

앞서 같은 계정의 다른 서비스를 편입할 때도 이 조회로 판단을 바꾼 적이 있어요. 로드밸런서와 타깃그룹에는 배포 파이프라인이 관리한다고 적힌 태그가 있었습니다. 실제로 파이프라인이 구성을 바꾼다면 Terraform과 변경이 충돌할 수 있어 편입 대상에서 제외하려고 했어요.

태그가 말한 것 ManagedBy = github-actions "배포 파이프라인이 관리한다" 감사 조회 결과 로드밸런서 · 타깃그룹 · DB 클러스터 · 인스턴스 2대 90일 관리 API 호출 0건 "배포는 이걸 만진 적이 없다"

90일 동안 그 자원들의 구성을 바꾼 호출이 하나도 없었습니다. 그 태그는 이미지를 빌드하고 밀어넣는 파이프라인의 규약이었고 인프라 구성과는 무관했어요. 태그와 실제 관리 API 호출을 구분해서 볼 필요가 있었습니다.

이벤트 이름으로 최근 호출 몇 건만 조회해서는 특정 자원에 변경이 없었다고 판단할 수 없어요. 이때는 자원 이름을 지정해 해당 자원에 대한 이벤트를 조회했습니다.

다만 감사 로그만으로 편입할 자원의 목록을 만들 수는 없었어요. 조회 방식과 기록 범위에 다음 제약이 있었습니다.

열거를 못 한다 자원 이름으로 지목해야 나온다 즉 무엇이 있는지 이미 알아야 조회할 수 있다 창이 90일이다 분기에 한 번 도는 배포는 0건으로 보인다 읽기는 안 남는다 자원 안의 데이터를 누가 읽었는지는 기본 설정으로 기록되지 않는다

우선 무엇이 있는지 알아야 자원 이름을 지정할 수 있어요. 감사 기록은 이미 찾은 후보의 관리 주체를 확인하는 데 쓰고, 후보 목록은 따로 만들어야 했습니다.

조회된 변경이 0건이어도 확인한 범위는 90일뿐이에요. 그때는 서버가 15개월째 같은 인스턴스였다는 점도 함께 보고 위험이 낮다고 판단했지만, 다른 서비스에도 같은 판단을 적용할 수는 없습니다.

데이터 읽기 기록을 미리 켜두지 않았다면 과거의 접근 여부도 확인할 수 없어요. 그래서 4장의 S3 버킷 사용 여부는 앱 소스로 확인했습니다.

3. 참조를 따라 찾고 공유 여부를 확인하기

자원 목록은 이미 알고 있는 자원에서 시작해 연결된 대상을 따라가며 만들었어요. 이때 대상의 존재가 보장되는 참조와 이름만 남을 수 있는 참조를 구분했습니다.

강제되는 참조 ID 로 가리키고, 대상이 없으면 동작하지 않는다 로드밸런서 → 타깃그룹, 인스턴스 → 보안그룹 → 존재가 보장되므로 늙지 않는다 문서적 참조 이름으로 가리키고, 대상이 없어도 그대로 남는다 DNS 레코드 → 별칭 대상 → 태그와 같은 성질이다

로드밸런서와 타깃그룹처럼 대상이 있어야 동작하는 연결은 실제 자원을 찾는 데 썼어요. 반면 DNS처럼 대상이 삭제되어도 설정이 남을 수 있는 연결은 대상의 존재부터 확인했습니다.

DNS의 연결을 해석하다가 잘못 판단한 사례는 6장에서 살펴볼게요.

세 번 훑었습니다. 방향이 각각 다릅니다.

1차 씨앗을 잡는다 확실히 아는 자원 하나에서 시작한다 2차 참조를 펼친다 그 자원이 가리키는 것을 따라 밖으로 넓힌다 3차 경계를 좁힌다 찾은 것마다 "이걸 누가 참조하나" 를 거꾸로 되짚는다

연결된 자원을 찾기만 하면 공유 자원까지 목록에 포함돼요. 3차에서는 찾은 자원을 다른 서비스도 참조하는지 역으로 조회해, 이 서비스가 단독으로 관리할 수 있는 범위를 좁혔습니다.

그림 1. 연결된 자원을 찾은 뒤 다른 서비스의 참조를 확인한다

이 확인 과정에서 보안그룹 여섯 개와 DB 서브넷그룹, 인증서, KMS 키를 편입 대상에서 제외했어요. 공유 여부와 소유 가능 여부를 확인해 다른 서비스에 영향을 줄 수 있는 변경을 피하려는 판단이었습니다.

참조 대상을 확인하다가 더 이상 사용하지 않는 DNS 레코드도 찾았어요.

DNS 레코드 하나 → 별칭 대상이 …-nlb-prod-<해시> 그 해시의 NLB 가 계정에 없다

이름으로는 운영 레코드처럼 보였지만, 가리키는 NLB는 이미 삭제되어 있었습니다. 태그와 이름 검색만으로는 알 수 없었던 상태예요.

앞서 구분한 문서적 참조의 사례예요. 대상이 없어도 DNS 레코드 자체는 남아 있으므로, 레코드가 있다는 것만으로 대상 자원이 존재한다고 판단하면 안 됐습니다.

4. S3 사용 여부를 앱 소스와 대조하기

S3 버킷 여덟 개 중 어떤 것을 실제로 사용하는지도 확인해야 했어요. IAM 정책과 요청 지표로는 판단할 수 없어 앱 소스의 호출 지점을 확인했습니다.

1차 (실패) 인스턴스 역할의 IAM 정책을 본다 → 정책이 s3:* on * 였다. 아무 정보가 없다 2차 (실패) 버킷 요청 지표로 접근 여부를 본다 → 기본으로 안 켜져 있고, 켜면 그때부터 쌓인다. 과거를 볼 수 없다 3차 (성공) 앱 소스를 읽는다 → 버킷 이름 상수를 grep 하고 호출 지점을 센다

소스의 호출 지점과 AWS 자원 상태를 대조하니 다음과 같은 차이가 있었어요.

버킷 소스 호출 객체 판정 ────────────────────────────────────────── A 9곳 0개 현역 B 0곳 0개 죽은 상수 C 4곳 — 버킷이 없다

A 버킷은 객체가 0개였지만 코드 아홉 곳에서 호출하고 있었어요. 아직 사용자가 그 기능을 쓰지 않아 비어 있었던 것이므로 삭제 대상에서 제외했습니다.

B는 버킷 이름 상수만 남아 있고 호출하는 곳이 없었어요.

C는 객체를 넣고 꺼내고 지우는 호출이 네 곳 있었지만 계정에 버킷이 없었어요. 인프라를 조사하는 과정에서 앱의 호출 대상이 존재하지 않는 문제도 확인했습니다.

💡 새 로그를 켜기 전에 기존 앱 로그 확인하기
DNS 레코드 하나가 이상해 보였어요. dev 라는 이름이 붙은 도메인이 운영 로드밸런서를 가리키고 있었습니다.

판정하려면 액세스 로그를 켜서 어떤 이름으로 요청이 들어오는지 봐야 한다고 적고 보류했어요. 로그는 저장 버킷과 정책이 필요하고 요금도 붙습니다.

그런데 다른 일로 앱 컨테이너 로그를 보다가 답이 나왔습니다. 앱이 요청 URL 을 그대로 찍고 있었고, 그 dev 이름으로 실사용자 요청이 들어오고 있었어요. 실제로 사용하는 경로여서 정리 대상에서 제외했어요.

추가 로그를 켜지 않아도 기존 앱 로그에서 필요한 요청을 확인할 수 있었습니다.

5. 태그 없는 이미지도 참조될 수 있다

처음에는 태그 없는 이미지를 배포가 참조할 수 없는 삭제 대상으로 봤어요. 다른 이미지 저장소에서는 그 판단으로 15GB 를 지웠고, 당시에는 인덱스와 자식의 개수를 대조하지 않았습니다. 이번 저장소를 확인하면서 그 판단만으로는 충분하지 않다는 걸 알게 됐어요.

이 저장소에서는 배포가 사용하는 태그가 인덱스에 붙어 있었어요. 인덱스는 이미지 정보를 담은 매니페스트 여러 개를 묶는 상위 매니페스트입니다. 인덱스가 가리키는 자식에는 태그가 없었어요.

전체 813개 (아래 셋은 서로 겹치지 않는다) 단독 매니페스트 633 인덱스 60 ← 태그가 붙어 있다 인덱스의 자식 120 ← 태그가 없다 합계 813

태그 없는 이미지 수 120은 인덱스 수 60에 2를 곱한 값과 같았어요.

앱 CI 가 쓰는 빌드 액션이 빌드 출처 증명(이 이미지가 어느 커밋·어느 워크플로에서 나왔는지를 적은 별도 아티팩트)을 기본으로 만듭니다. 그래서 푸시마다 인덱스 하나에 자식 둘, 즉 이미지와 출처 증명이 생깁니다.

이 구조에서는 태그 없는 120개가 태그 붙은 인덱스 60개의 자식일 수 있어요. 그래서 태그 유무만으로 미참조 이미지라고 판단하지 않았어요. ECR 수명주기의 참조 보호 동작과 별개로, 삭제 후보의 참조 관계를 확인해야 했습니다.

그림 2. 인덱스가 참조하는 자식에도 태그가 없을 수 있다

다만 이 등식이 고아 0을 증명하는 건 아닙니다. 두 인덱스가 같은 자식을 공유하면 참조되는 자식 수가 줄고, 그만큼 고아가 섞여 있어도 총계는 그대로 120 이에요. 등식은 "부모당 자식 수가 일정하다"는 전제 아래에서만 고아 0과 맞아떨어집니다.

따라서 이 개수 대조만으로는 미참조 이미지가 없다고 확정하지 않았어요. 대량 삭제 규칙을 적용하기 전에 인덱스가 가리키는 자식 다이제스트, 즉 콘텐츠 식별값을 실제로 나열해 대조해야 했습니다.

같은 계정의 다른 이미지 저장소에는 태그 없는 최상위 인덱스가 15개 있었어요. 이쪽은 삭제할 수 있는 미참조 인덱스가 있었지만 자식의 구성을 함께 봐야 했습니다.

태그 없는 인덱스 15 ← 진짜 고아. 지워도 된다 자식 32 = 고아 인덱스의 자식 30 + 살아 있는 인덱스의 자식 2 "태그 없음" 규칙은 47개를 한꺼번에 지운다 → 살아 있는 것의 부품 2개가 섞인다

위 메모의 "47개를 한꺼번에 지운다"는 당시 우려였고, 실제 수명주기 삭제 결과는 아니에요. ECR은 매니페스트 목록이 참조하는 이미지를 해당 목록이 먼저 삭제되기 전에는 수명주기로 만료시키지 못합니다. 살아 있는 인덱스의 자식까지 이 규칙으로 삭제된다는 단정은 잘못됐어요. 다만 태그가 없다는 이유만으로 미참조 이미지라고 볼 수는 없으므로, 삭제 후보는 참조 관계와 다이제스트로 확인해야 해요.

6. CDN의 DNS 대상과 요청 처리 배포 구분하기

참조를 확인할 때도 자원 종류에 따른 동작을 알아야 했어요. DNS의 별칭 대상만으로 실제 응답한 CDN 배포를 판단했다가 잘못 진단한 적이 있습니다.

아래 레코드와 배포는 공용 DNS 존을 함께 쓰는 다른 서비스의 자원이었어요. 편입 범위를 확인하는 과정에서 함께 살펴봤습니다.

그리고 용어를 갈라둘게요. 방향이 반대인 두 가지가 둘 다 "별칭"으로 불립니다.

DNS 쪽 별칭 대상 이 도메인이 어디를 가리키나 CDN 쪽 받아주는 도메인 목록 이 배포가 어떤 이름의 요청을 받나

DNS가 가리키는 배포와 도메인 요청을 받는 배포를 구분해서 확인해야 했어요.

apex 도메인 → 별칭 대상: CDN 배포 X (배포 X 가 받아주는 도메인: dev 도메인 하나뿐) dev 도메인 → 별칭 대상: CDN 배포 Y (배포 Y 가 받아주는 도메인: apex 도메인 하나뿐)

서로 엇갈려 있었어요. CDN 은 요청의 호스트 이름이 그 배포가 받아주는 도메인 목록에 없으면 거부합니다. 그래서 "레코드가 뒤바뀌어 둘 다 깨졌다"고 단정했어요. apex 를 실제로 호출해보니 403 이 왔습니다. 이 응답을 보고 제 판단이 맞다고 생각했어요.

하지만 응답 헤더를 보니 403을 반환한 곳은 CDN 자체가 아니었어요.

HTTP/2 403 server: AmazonS3 ← 오리진이 403 을 냈다 x-cache: Error from cloudfront ← CDN 은 중계했을 뿐이다 via: 1.1 ….cloudfront.net ← 즉 요청을 받아들였다

호스트 불일치였다면 CDN 자기 오류 페이지가 오고 오리진 헤더는 붙지 않습니다. 즉 CDN 은 이 요청을 정상으로 처리했고, 403 을 낸 건 그 뒤에 있는 오리진 버킷이었어요.

apex 요청을 처리한 쪽은 그 도메인을 목록에 가진 Y 배포였어요. 하나의 도메인 이름은 계정 전체에서 배포 하나만 가질 수 있습니다. DNS는 X를 가리키고 있었지만 응답한 배포는 Y였습니다.

왜 버킷이 403 을 내냐면, 없는 키를 요청하면 그렇게 답하도록 되어 있기 때문입니다. apex 로 들어온 요청이 그 배포의 오리진에서 찾을 수 없는 경로였던 거죠.

그림 3. 참조처럼 보이지만 트래픽을 결정하지 않는 참조가 있다

이유는 이랬습니다. CDN 엣지 주소는 모든 배포가 공유하고, 어느 배포가 응답할지는 DNS 가 가리킨 대상이 아니라 요청이 들고 온 이름(TLS 핸드셰이크의 SNI 와 Host 헤더)이 결정합니다. 그래서 별칭 대상이 엉뚱한 배포를 가리켜도, 계정 어딘가에 그 이름을 가진 배포가 있으면 정상 동작해요.

이 사례에서는 DNS 별칭 대상과 실제 요청을 처리하는 배포가 달랐어요. 별칭 대상만 읽어서는 요청 경로를 판단할 수 없었습니다.

범위를 정확히 적어둘게요. 모든 별칭이 그런 건 아닙니다. 로드밸런서를 가리키는 별칭은 그 대상이 곧 트래픽 목적지라서 3장에서 끊긴 레코드를 유휴로 판정한 것은 지금도 유효합니다. 참조가 실제 동작에 어떤 영향을 주는지는 자원 종류마다 확인해야 해요.

그리고 403 이 사용자에게까지 나가는 이유는 또 따로 있었습니다. 프론트가 단일 페이지 앱이라 없는 경로를 앱 화면으로 넘겨주는 설정이 걸려 있는데, 그때 응답 코드를 200 으로 되돌리는 칸이 비어 있었어요.

그래서 본문은 정상 화면이고 상태 코드만 403 입니다. 브라우저로 열면 아무 문제가 없어서 헬스체크와 검색엔진에서만 드러납니다. 셋을 정리하면 원인·중계·노출이 각각 다른 층에 있었어요.

원인 오리진에 없는 경로였다 → 버킷이 403 중계 CDN 은 그걸 그대로 전달했다 → 거부한 게 아니다 노출 폴백이 코드를 안 고쳤다 → 403 이 사용자에게 나간다
⚠️ 같은 DNS 존을 여러 서비스가 공유할 때
CDN 배포 51개 중 이 서비스 것을 찾을 때 "별칭이 우리 도메인 하위인 배포"로 필터를 잡았어요. 13개가 걸렸고 전부 오탐이었습니다. 그 존을 다른 서비스 여러 개가 함께 쓰고 있었거든요. 레코드 27개 중 이 서비스 것은 4개였습니다.

이 서비스의 배포인지는 오리진으로 판별했어요. 배포가 어디서 콘텐츠를 가져오는지는 그 배포가 무엇을 서비스하는지와 같은 것이고, 그것으로 세면 0개였습니다. 이 서비스는 CDN 을 안 씁니다. 프론트가 없는 서버 대 서버 중계 서비스였어요.

같은 존에서 이런 것도 나왔습니다. 하이픈이 하나 있고 없는 두 이름이 완전히 다른 곳으로 갑니다. 장애 대응 중에 둘을 혼동하면 엉뚱한 서비스를 끊어요.

7. 코드 정리 중 운영 DB 삭제 계획을 발견하다

자원 조사를 마친 뒤 코드를 정리하는 과정에서는 제 실수로 운영 DB 삭제가 plan에 포함됐어요.

리소스 블록 하나만 걷어내려고 블록이 끝나는 지점을 스크립트로 다음 주석 구분선까지 훑었어요. 그랬더니 운영 DB 클러스터와 writer 까지 함께 잘렸습니다. plan 에 -3 이 떴어요.

여기서 장치 하나를 설명해야 합니다. 이 저장소에서는 삭제나 재생성이 섞인 plan 을 CI 가 막습니다. 의도한 삭제일 때만 PR 에 라벨을 붙여 그 가드를 끄고 통과시켜요. 3편에서 재실행 시 라벨 반영 문제를 다뤘던 가드예요.

그리고 두 가지가 겹쳐서 위험했습니다.

① 블록이 사라지면 그 안의 삭제 방지 설정도 사라진다 코드 안의 안전장치는 코드를 지우는 실수로부터 자신을 지키지 못한다 ② allow-destroy 라벨을 미리 붙여뒀다 그 라벨은 파괴적 변경을 "허용" 하는 게 아니라 가드를 끄는 스위치다 그래서 -3 이 떠도 CI 는 통과시킨다

삭제 대상을 확인하기 전에 라벨을 붙인 탓에, 의도하지 않은 삭제가 포함돼도 해당 가드는 CI를 막지 못하는 상태였어요.

이번에는 PR 본문에 미리 적어둔 기대 변경 개수와 비교해 실수를 발견했어요. "이 스택에 -1 이나 +1 이 뜨면 중단" 이라고 써둔 내용과 실제 plan이 달랐습니다.

⚠️ 삭제 라벨과 기대 변경 개수 확인하기
allow-destroy 는 plan 의 삭제 대상을 이름으로 확인한 뒤에 붙인다. 미리 붙이면 의도하지 않은 삭제도 가드를 통과할 수 있어요.

기대 카운트를 먼저 쓴다. 숫자만 보면 무엇이 지워지는지 알 수 없어요. 몇 개가 지워질지 먼저 적어두면 실제 숫자가 다를 때 작업을 중단하고 확인할 수 있습니다.

다만 기대 변경 개수를 적고 비교한 것은 사람이 한 일회성 확인이에요. 15편에서 다룬 자동 검증의 한계가 해결된 것은 아닙니다. 본문에 이 내용을 적지 않은 PR에는 적용되지 않으므로, PR 본문에 기대 카운트가 있는지를 CI가 확인하도록 만드는 일이 남아 있었어요.

편입 과정에서는 권한, 생성 가능한 속성, 실제 삭제 시점을 각각 따로 확인해야 하는 사례도 세 개 더 있었어요.

권한이 있는 것 ≠ 쓰는 것 역할에 리스너 수정 권한이 남아 있어서 예외 처리가 필요한지 판단해야 했다 90일 감사 로그를 보니 그 API 호출이 1건이고 행위자가 그 역할이 아니었다 권한만 남은 옛 방식의 흔적이었다 읽을 수 있는 속성 ≠ 만들 수 있는 속성 편입할 때 AWS 가 백업 시간대를 돌려주므로 코드에 들어가고 계획도 통과한다 그런데 그건 클러스터 속성이라 인스턴스 생성 API 가 거부한다 실물이 있는 동안은 안 드러나고, 다시 만들려는 순간에만 터진다 계획에 삭제가 없음 ≠ 아무것도 안 지움 이미지 수명주기 정책은 "추가 1건" 으로만 보인다 apply 뒤에 이미지 저장소가 비동기로 지운다

가운데 사례는 기존 자원이 있을 때의 plan과 apply만으로 발견하기 어려웠어요. 자동 생성된 설정에 인스턴스 생성 API가 받지 않는 속성이 남아 있으면, 나중에 인스턴스를 재생성할 때 실패할 수 있습니다.

✍️ 확인한 내용
이름과 태그로 후보를 찾은 뒤 자원 간 참조, 감사 로그, 앱 소스를 대조했어요. 감사 로그는 확인한 90일의 관리 API 호출을 판단하는 데 썼고, 공유 자원은 다른 서비스의 참조를 역으로 조회해 편입 대상에서 제외했습니다.

빈 S3 버킷에도 코드 아홉 곳의 호출이 있었고, 태그 없는 이미지 120개와 인덱스 60개의 관계는 60 × 2라는 개수만으로 확정할 수 없었어요. DNS 별칭 대상과 실제 요청을 처리하는 CDN 배포도 구분해야 했습니다.

코드 정리 중에는 운영 DB 삭제 계획을 PR 본문의 기대 변경 개수와 비교해 발견했어요. 삭제 대상을 확인한 뒤 라벨을 붙이기로 했지만, 기대 카운트 확인 자체를 CI에서 강제하는 일은 남아 있었습니다.
