1편. Terraform 초기 파이프라인의 환경 분리와 prod apply 설계 ← 지금 이 글

커밋 1개짜리 저장소를 받았어요. Terraform 코드는 0줄이고 워크플로도 브랜치 보호도 없었습니다. 이 저장소에 인프라 변경을 코드로 검토하고 적용할 파이프라인을 구성해야 했어요.

먼저 Terraform을 선택한 이유와 환경 분리 방식을 정했어요. 구현 중에는 OIDC 신뢰 정책과 GitHub 플랜 제약 때문에 설정과 설계를 수정했고, 설계 리뷰에서는 plan 확인 절차와 권한, 재실행 방식에서 네 가지 문제가 나왔습니다.

1. Terraform을 선택한 이유부터 문서화하기

도구 선택의 근거는 뒤늦게 정리했어요. 설계 결정을 남기는 문서인 ADR을 0001부터 썼지만, 정작 Terraform을 고른 이유는 빠져 있었습니다. 리뷰에서 이 부분을 지적받고 다른 후보와 비교해 적었어요.

후보는 Pulumi(범용 언어), CloudFormation(AWS 네이티브), Terraform이었어요. Pulumi는 범용 언어로 추상화를 자유롭게 만들 수 있지만, 작성자마다 표현 방식이 달라질 수 있다는 점이 부담이었어요. 코드에서 계정의 리소스 구성을 바로 파악할 수 있기를 원했기 때문에, 표현 방식을 제한하는 선언형 HCL을 선택했습니다.

다만 이 기준만으로는 CloudFormation을 제외할 수 없어요. CloudFormation도 선언형이고 리소스 상태를 AWS가 관리해 줍니다. 처음에는 "멀티 클라우드 대비"를 이유로 들었지만 충분한 설명은 아니었어요. aws_s3_bucket이 GCP 리소스로 자동 변환되지는 않기 때문이에요. Terraform으로 여러 클라우드를 다룰 수 있어도 클라우드를 바꿀 때 코드를 그대로 쓸 수 있는 것은 아닙니다. 최종 근거는 이미 파이프라인에 넣은 tflint·checkov 검증, 모듈 생태계, 오류를 조사할 때 참고할 수 있는 사례였어요. "업계 표준"이라는 표현 대신 실제 운영에서 필요한 조건을 적었습니다.

2. develop 브랜치를 만들지 않기로 했다

당시 서비스 저장소에서는 master + develop 모델을 쓰고 있었어요. develop에 머지하면 dev에, master에 머지하면 운영에 배포하고, 배포가 성공하면 봇이 master를 develop으로 자동 역머지했습니다. 운영에 반영된 코드를 개발 브랜치에도 맞추는 절차였고, IaC 저장소에도 같은 모델을 쓸지 검토했어요.

같은 워크플로를 가져오면 봇의 역머지 커밋이 dev apply를 시작하게 돼요. 사람이 그 커밋의 인프라 변경을 확인하지 않은 채 적용할 수 있다는 점이 문제였습니다. Terraform에서는 코드를 이전 상태로 돌려도 리소스 변경이나 삭제가 발생할 수 있어요. 환경별 코드와 state를 브랜치로 나눠 관리할 때는 서로 다른 리소스 구성이 plan에 어떻게 반영되는지도 검토해야 했습니다.

그래서 환경은 브랜치 대신 디렉터리로 나눴어요. 기본 브랜치 main에 envs/dev, envs/prod, 그리고 공유 modules/를 뒀어요. 환경 차이는 모듈에 넘기는 값으로 표현하므로 dev와 prod의 차이를 한 PR에서 볼 수 있습니다. 운영에 반영할 때도 값을 바꾸는 PR을 만들어 검토하도록 했어요.

그림 1. 역머지 봇이 dev apply를 시작하는 경로를 피하려고 디렉터리를 나눴어요

3. state 버킷과 CI 역할은 bootstrap에서 먼저 만들기

Terraform을 CI에서 실행하려면 리소스 상태를 저장할 S3 버킷과 CI용 IAM 역할이 먼저 필요해요. 이 리소스들도 Terraform으로 관리하되, bootstrap/ 디렉터리만 사람이 로컬에서 1회 apply하도록 했어요. 이 디렉터리는 CI apply 대상에서 영구 제외해 CI가 자신의 state 버킷을 삭제하지 못하도록 구성했습니다.

역할은 환경×용도로 4개(dev/prod × plan/apply)를 만들었어요. plan 역할은 인프라를 읽고 변경 계획을 계산하지만, 잠금 파일에는 쓰기 권한이 필요합니다. Terraform 1.10의 네이티브 잠금(use_lockfile)이 .tflock 객체를 만들고 지우기 때문이에요. ReadOnly만 붙이면 plan이 실패해요. 이를 피하려고 -lock=false를 붙여 잠금을 끄지 않도록, 전체 읽기 권한에 해당 역할의 잠금 파일 쓰기 권한만 추가했습니다.

단일 AWS 계정에 dev/prod가 공존하는 조건이라 격리는 3중 방어로 구성했어요. state 키 프리픽스 분리, default_tags로 env 태그를 강제하고 apply 역할에 반대 환경 태그 리소스에 대한 명시적 Deny, 그리고 prod 리소스의 prevent_destroy입니다. 태그 조건을 지원하지 않는 서비스(IAM, Route53 등)는 이 방식으로 막을 수 없다는 한계도 ADR의 "감수하는 것"에 적었어요.

4. 구현 중 확인한 문자 제한과 인증·승인 제약

구현 중 첫 번째로 수정한 것은 IAM 역할의 description이었어요. 한글로 작성했더니 CreateRole이 ValidationError로 거부됐습니다. description에 허용되는 문자 범위는 사실상 ASCII + Latin-1이라 한글이나 em-dash를 쓸 수 없었어요.

두 번째는 OIDC 신뢰 정책이었어요. 문서에 나온 repo:org/repo:... 형식을 썼는데 AssumeRole이 계속 거부됐어요. 당시 조직에는 불변 주체 클레임이 켜져 있어 인증 주체를 나타내는 sub에 조직·저장소 ID도 들어가고 있었습니다.

기대한 sub: repo:{조직}/{저장소}:ref:refs/heads/main 실제 sub: repo:{조직}@{조직ID}/{저장소}@{저장소ID}:ref:refs/heads/main 확인 방법: gh api repos/<org>/<repo>/actions/oidc/customization/sub --jq .sub_claim_prefix

세 번째는 prod apply의 승인 방식이었어요. 원래는 GitHub Environment의 required reviewer를 사용하려고 했습니다. 승인을 받아야 job이 시작되므로 그 전에는 OIDC 자격증명도 발급되지 않는다는 설계였어요. 하지만 구현하려고 API를 호출하자 다음 응답이 돌아왔습니다.

PUT /repos/{조직}/{저장소}/environments/prod {"reviewers": [{"type": "User", "id": ...}]} → 422 "Please ensure the billing plan supports the required reviewers protection rule."

당시 조직 플랜은 GitHub Team이었어요. private 저장소에서 Environment를 만들 수는 있었지만, 필요한 required reviewer 보호 규칙은 쓸 수 없다는 응답이었습니다. 실제로 생성된 Environment의 protection_rules도 빈 배열이었어요. environment: prod만 지정하면 main 머지 후 승인 없이 prod apply가 실행될 수 있었습니다. ADR-0002에서 이 전제를 정정하고 prod 트리거를 workflow_dispatch 수동 실행으로 바꿨어요. 코드에는 브랜치 보호의 필수 승인 1인(+관리자 예외 없음)을 적용하는 설계였습니다.

⚠️ 구현 중 확인한 제약 3개
• IAM description의 문자 제한 때문에 한글과 em-dash를 수정했어요
• OIDC 신뢰 정책을 맞추려면 실제 발급되는 sub 형식을 확인해야 해요
• Environment 생성 가능 여부와 required reviewer 지원 여부는 따로 확인해야 해요
그림 2. 리뷰 전 구성한 흐름이에요. prod는 수동 실행하지만 plan 확인 절차는 빠져 있었어요

5. 설계 리뷰에서 확인한 네 가지 문제

초기 구성을 마친 뒤 설계 리뷰를 받았어요. 정상 실행만 고려하면서 놓친 부분이 지적 4건으로 나왔습니다. 여러 변경이 누적됐을 때의 plan, 다른 역할을 통한 권한 상승, 라벨 변경 후 재실행, 수동 입력의 적용 범위를 다시 확인했어요.

① prod plan을 읽을 단계가 없었어요. 수요일에 dispatch 버튼을 누르면, 월요일에 다른 사람이 머지해 둔 변경까지 함께 계산된 plan이, 아무도 그 전체를 확인하지 않은 채 같은 run 안에서 바로 apply됩니다. 자동 가드가 있긴 하지만 destroy만 잡아요. 삭제가 없는 변경은 이 가드로 막히지 않습니다. 수정 방향은 저장된 plan을 사용하는 것이었어요. 저장된 plan은 그 사이 state가 변하면 apply가 stale 에러로 거부되므로, plan과 apply를 나누고 그 사이에 plan 요약을 확인하는 절차를 둘 수 있습니다. dispatch도 두 단계로 분리하기로 했어요.

② 새 역할을 통해 태그 기반 제한을 우회할 수 있었어요. apply 역할에 iam:*를 열어주면서 파이프라인 역할(platform-iac-*)만 Deny로 보호했는데, 그 목록 밖 이름으로 관리자 역할을 만들고 해당 역할을 사용하면 태그 Deny도 우회할 수 있었습니다. sts:AssumeRole의 명시적 Deny와 "permissions boundary 없이는 역할 생성 불가" 조건을 조합하기로 했어요. permissions boundary는 역할에 허용할 권한의 상한을 정하는 정책입니다.

③ 라벨을 붙여도 재실행이 실패했어요. 파괴적 변경 가드는 "allow-destroy 라벨을 붙이고 다시 실행하세요"라고 안내했습니다. 하지만 github.event에는 이벤트 발생 당시의 payload가 들어 있어 Re-run에서도 라벨을 붙이기 전 값을 읽어요. 같은 실행을 반복해도 통과하지 못하므로 라벨은 실행 시점에 API로 조회해야 했습니다.

④ 삭제 허용 입력이 dev와 prod에 함께 적용됐어요. dispatch에 환경 선택 입력이 없어서 allow_destroy를 켜고 실행하면 dev와 prod가 함께 돌아요. env 입력을 추가해 선택한 환경에서만 실행되도록 바꾸기로 했어요.

🔧 리뷰 후 수정할 목록 (PR 두 개 분량)
• prod를 2단계 dispatch로 분리 + env 선택 입력 추가
• 머지 직후 "prod 미반영 변경" 이슈 자동 생성: 24시간 drift 대기를 즉시 알림으로
• sts:AssumeRole Deny + permissions boundary 강제
• 라벨 가드를 실행 시점 API 조회로 교체 + unlabeled 트리거 추가
그림 3. 보호 대상 밖의 역할을 만들어 태그 Deny를 우회할 수 있었어요

6. 리뷰 결과와 추가로 확인할 내용

리뷰 점수는 10점 만점에 7.5점이었어요. 감점 2.5점은 위의 4건에 해당했고, 패치 반영 후 재채점 예상은 8.5~9점이었습니다. 이 수치는 수정 후 검증 결과가 아니라 리뷰 당시의 예상이에요.

단일 계정의 태그 기반 격리가 IAM 같은 서비스에는 적용되지 않는다는 한계는 ADR에 적어둔 내용이었어요. 리뷰에서도 이를 알고 선택한 제약으로 설명할 수 있었습니다. 반면 dispatch의 plan 확인 절차와 iam:*의 권한 상승 경로는 검토가 빠져 있어 수정 대상으로 남았어요.

추가 검토에서는 정상 실행 외에도 버튼을 잘못 눌렀을 때의 대상 환경, 입력이 전달되는 범위, 이벤트 값이 만들어진 시점을 확인해야 했어요. 수정할 항목은 정했지만, 이 시점에는 패치 반영과 실행 검증이 남아 있었습니다.

✍️ 작업 요약
Terraform과 디렉터리 기반 환경 분리를 선택하고, state 버킷과 CI 역할은 bootstrap에서 먼저 구성했어요. GitHub 플랜 제약으로 prod apply는 수동 실행으로 바꿨습니다.

설계 리뷰에서는 prod plan 확인 단계, IAM 권한 상승, 재실행 시 라벨 조회, 삭제 허용 입력의 환경 범위에서 문제를 찾았어요. 수정 방향을 정한 단계이며, 패치 적용과 실행 검증은 아직 남아 있었습니다.
