11편. S3 기본 암호화를 바꿔도 Terraform state 객체가 그대로였던 이유 ← 지금 이 글

state 버킷의 기본 암호화를 AWS에서 관리하는 키에서 직접 만든 키로 바꿨어요. 키와 키 정책을 만들고, 파이프라인 역할 네 개에 복호화 권한을 준 뒤 버킷 설정을 변경했습니다. plan에서 변경 내용을 확인했고 apply도 성공했어요. 변경은 커밋 하나와 ADR 하나에 남겼습니다.

그런 다음 새로 올라간 state 객체의 속성을 열어봤어요. 버킷 설정은 바뀌었는데 객체의 암호화 방식은 이전과 같았습니다.

에러나 경고는 없었고, 콘솔의 버킷 속성 화면도 새 키를 가리키고 있었어요. 버킷 설정을 바꾸는 작업은 성공했지만, 그 설정이 새 객체에 적용되는지는 별도로 확인해야 했습니다.

1. 시크릿을 직접 만들지 않아도 state에 값이 남는다

첫날에는 시크릿을 콘솔에서 만들고 코드에는 ARN만 참조하기로 했어요. 시크릿 값이 코드와 state에 들어오는 것을 피하려는 규칙이었습니다.

하지만 시크릿을 직접 생성하지 않아도 state에 값이 저장될 수 있어요. 데이터 소스와 리소스가 반환하는 속성도 확인해야 했습니다.

파라미터 스토어의 값을 data로 읽으면 그 값이 state에 평문으로 기록돼요. 리소스가 반환한 초기 비밀번호, 인증서, 연결 문자열이나 프로바이더가 저장하는 필드도 대상이 될 수 있습니다. sensitive = true는 화면 출력을 가리는 설정이고, state 파일에 저장되는 값을 암호화하지는 않아요.

이번에는 알럿을 외부 모니터링 서비스로 보내는 구독이 계기였어요. 엔드포인트가 URL 안에 API 키를 포함하는 형식이고 실제 값을 넣어야 하므로, 참조만 남기는 방식으로는 구독을 정의할 수 없었습니다. 구독을 코드로 관리하면 state에도 키가 들어와요. 그래서 state에 시크릿이 들어올 수 있다는 전제로 바꾸고, state 자체의 보호 방법을 검토했습니다.

9편에서 넓힌 읽기 권한과 함께 검토하기

9편에서는 plan 역할의 state 읽기 권한을 버킷 전체로 넓혔어요. 파일 이름으로 범위를 지정하니 스택이 늘 때마다 권한을 추가하고, 로컬에서 bootstrap을 apply해야 했기 때문입니다. 운영 부담은 줄었지만 읽을 수 있는 범위가 넓어진 점도 함께 고려해야 했어요.

당시에는 기존 SSE-S3 객체를 s3:GetObject 권한으로 읽을 수 있으므로, 읽기 권한을 넓힌 뒤 시크릿이 들어오면 plan 역할의 열람 범위도 함께 넓어진다고 봤어요.

직접 만든 키를 쓰면 S3 읽기 권한 외에 키 정책으로도 접근을 제한할 수 있다고 판단했어요. 아래 비교도 키 정책을 S3 권한과 독립적으로 감사하고 회수할 수 있다고 본 당시의 판단입니다.

AWS 관리형 키 (SSE-S3) 복호화 조건 : s3:GetObject ← 관문 1개 회수 방법 : IAM 정책만 우리 키 (CMK) 복호화 조건 : s3:GetObject AND kms:Decrypt (키 정책 통과) ← 관문 2개 회수 방법 : IAM 정책, 또는 키 정책에서 역할 하나만 빼기

다만 실제 키 정책에는 계정 root를 통해 IAM 정책에 권한 부여를 위임하는 항목도 있었어요. 그 경로로 허용되는 역할은 키 정책의 개별 역할 목록에서 빼는 것만으로 차단되지 않습니다. 따라서 위 비교의 "역할 하나만 빼기"는 독립적인 회수를 보장하지 못했고, 키 정책의 위임과 역할의 IAM 권한을 함께 확인해야 했어요.

2. 키 생성과 backend 변경을 두 단계로 나눈 이유

첫날에는 Terraform으로 state 버킷을 만들려면 state를 저장할 버킷이 먼저 필요하다는 문제가 있었어요. bootstrap/ 디렉터리만 로컬 state로 1회 apply한 뒤 원격 버킷을 쓰는 방식으로 시작했습니다.

이번에는 키 생성과 backend 설정의 순서가 문제였어요. 키를 만드는 코드가 bootstrap/에 있는데, bootstrap/의 backend가 아직 없는 키를 가리키면 init이 실패합니다. init이 실패하면 키를 생성할 apply도 실행할 수 없어요. 모든 스택이 같은 버킷을 쓰므로 backend를 먼저 바꾸면 저장소의 CI 체크가 함께 막힙니다.

로컬에서 실행하더라도 backend가 요구하는 키가 먼저 있어야 해요. 그래서 변경을 두 개의 PR로 나눴습니다. 첫 PR에서 키를 생성하고 apply한 뒤, 두 번째 PR에서 backend가 그 키를 사용하도록 바꿨어요.

1단계 (PR 하나) 키 생성 + 별칭 키 정책 : 루트 + 파이프라인 역할 4개만 IAM : plan·apply 역할에 kms:Decrypt / GenerateDataKey / DescribeKey 버킷 기본 암호화를 우리 키로 변경 ※ backend 는 손대지 않는다 2단계 (1단계 apply 이후, 별도 PR) backend 블록 4곳에 kms_key_id 추가
⚠️ 키 정책과 IAM 권한을 함께 변경하기
• IAM에 kms 권한이 반드시 별도로 필요하다는 뜻은 아니에요. 같은 계정에서는 키 정책이 역할을 직접 허용할 수도 있고, 계정 root를 통한 IAM 위임 경로를 사용할 수도 있어요. 이번 변경은 키 정책과 IAM 양쪽에 권한을 추가했지만, 실패 여부는 실제 허용 경로와 작업을 대조해야 합니다.
• 당시에는 역할이 늘 때 키 정책에도 추가해야 한다고 봤어요. 역할의 state 접근 권한과 함께 확인할 항목으로 남겼습니다.
• 로컬에 .terraform/ 캐시가 있으면 2단계에서 재구성 프롬프트가 떠요. init -reconfigure로 재구성합니다. CI는 매번 새 체크아웃을 사용하므로 해당하지 않아요.
그림 1. 버킷은 로컬 state로 생성하고, 키는 backend를 변경하기 전에 생성해요

3. 버킷 기본값을 바꿔도 객체는 이전 방식으로 저장됐다

1단계를 apply한 뒤에도 새 state 객체는 이전 방식으로 암호화돼 있었어요. 버킷의 기본값을 바꾸면 backend가 올리는 객체에도 적용될 것이라고 생각한 게 원인이었습니다.

S3의 버킷 기본 암호화는 요청이 암호화 방식을 지정하지 않았을 때 사용하는 값이에요. 버킷에 올라오는 모든 객체의 암호화 방식을 강제하는 설정은 아닙니다.

Terraform의 S3 backend에는 encrypt = true가 설정돼 있었어요. 이 설정으로 backend가 업로드 요청의 헤더에 암호화 방식을 명시하고 있었습니다. 요청에 암호화 방식이 있으면 버킷 기본값보다 그 값이 우선해요.

그래서 버킷 기본값을 직접 만든 키로 바꿔도 새 객체의 방식은 그대로였어요. backend가 계속 이전 방식을 요청하고 있어 버킷 기본값이 사용되지 않았습니다.

버킷 설정과 객체 속성을 각각 확인하기

plan과 apply는 버킷 설정 변경을 확인해 줬고, 버킷 속성 조회도 바뀐 키를 보여줬어요. 다만 이 결과만으로는 실제 객체가 그 키로 저장되는지 알 수 없었습니다.

요청한 방식으로 저장됐으므로 에러나 경고도 없었어요. 실제 적용 여부는 저장된 객체의 암호화 속성을 조회해서 확인해야 했습니다.

# 버킷 설정 — 바뀌었다 aws s3api get-bucket-encryption --bucket {state 버킷} "SSEAlgorithm": "aws:kms" ✅ 우리 키 # 그 뒤에 새로 쓰인 state 객체 — 안 바뀌었다 aws s3api head-object --bucket {state 버킷} \ --key env/prod/terraform.tfstate "ServerSideEncryption": "AES256" ❌ 옛 방식 그대로

2단계에서 backend에 키를 명시한 뒤에야 새 객체가 그 키로 저장됐어요. 버킷 기본값 변경에 더해, 업로드 요청의 암호화 방식도 바꿔야 했던 것입니다.

그림 2. backend가 요청에 명시한 암호화 방식이 버킷 기본값보다 우선해요

4. 시크릿이 들어오기 전에 전환한 이유

당시 state에는 아직 시크릿이 없었어요. 그 상태에서 암호화 전환을 먼저 끝내기로 한 이유는 버킷의 버저닝 설정 때문이었습니다.

state 버킷에는 이전 버전으로 복구할 수 있도록 버저닝이 켜져 있어요. 버킷 설정이나 backend를 바꿔도 이미 저장된 버전은 바뀌지 않습니다. S3가 기존 객체를 자동으로 재암호화하지 않기 때문에, 과거 버전에는 이전 암호화 방식이 남아요.

시크릿이 들어간 다음에 암호화를 전환하면, 시크릿을 담은 과거 버전은 이전 방식으로 남습니다. 당시에는 그 버전이 9편에서 넓힌 s3:GetObject 권한으로 읽힌다는 점을 우려했어요. 새 버전의 암호화 설정만 확인해서는 과거 버전의 접근 범위를 판단할 수 없었습니다.

그래서 1단계에서 키를 만들고, 2단계에서 backend를 변경한 뒤 시크릿을 담는 리소스를 코드로 관리하기로 했어요. 이 순서를 지키지 않으면 설정 변경 후에도 이전 버전에 시크릿이 남습니다.

⏳ 설정 변경이 기존 데이터에도 적용되는지 확인하기
• 태그 정리, 모듈 리팩터링, 문서 보강은 이후 변경으로 보완할 수 있어요.
• 버저닝 · 감사 로그 · 암호화 · 보존 정책은 설정 이전의 데이터가 어떻게 처리되는지 따로 확인해야 해요.
• 이번 state 암호화 전환은 시크릿이 저장되기 전에 backend 변경까지 끝내기로 했습니다.

5. 키 ID 대신 별칭을 사용할 때의 관리 범위

2단계에서 backend에 넣은 값은 키 ID 대신 별칭이에요. 별칭은 사람이 읽을 수 있는 키 이름이고, 다른 키를 가리키도록 바꿀 수 있습니다.

backend "s3" { bucket = "{state 버킷}" key = "env/prod/terraform.tfstate" region = "{리전}" encrypt = true # 별칭 ARN 이라 키를 재생성해도 이 값은 안 바뀐다. # 대신 이 별칭이 사라지면 모든 스택의 init 이 깨진다. kms_key_id = "arn:aws:kms:{리전}:{계정ID}:alias/{state 키 별칭}" use_lockfile = true }

키를 교체할 때 backend 설정을 바꾸는 곳을 줄이려는 선택이었어요. 키 ID를 직접 적으면 backend 블록 네 곳을 모두 고치고 각 스택을 재구성해야 합니다. 하나를 빠뜨리면 해당 스택은 이전 키를 계속 가리켜요. 별칭을 쓰면 키를 교체해도 backend에 적힌 문자열은 유지할 수 있습니다.

대신 그 별칭이 사라지면 같은 별칭을 쓰는 모든 스택의 init이 실패해요. backend 네 곳의 수정은 줄일 수 있지만, 모든 스택이 의존하는 별칭을 관리해야 합니다.

키 삭제에도 주의해야 해요. 삭제 유예를 최대치인 30일로 뒀지만, 삭제 예약으로 키가 PendingDeletion 상태가 되면 그때부터 암호화 작업에 사용할 수 없어요. 유예가 끝나 실제 키가 삭제되면 그 키로 암호화한 state의 복호화도 영구적으로 불가능해집니다. 백업도 같은 키로 암호화돼 있다면 읽을 수 없어요. bootstrap에서 terraform destroy를 실행하지 않는다는 기존 규칙에 state 복호화 키를 보존한다는 이유가 추가됐습니다.

6. 전환 완료는 새 객체의 속성으로 확인하기

이번 전환에서는 버킷 설정과 객체 속성을 따로 확인해야 했어요. 버킷 기본값 변경만 확인했다면 backend가 이전 방식을 계속 요청한다는 사실을 놓쳤을 겁니다.

기본 태그, 보존 기간, 리소스 요청량, 타임아웃도 기본값과 명시한 값의 관계를 확인할 필요가 있어요. 설정 화면의 값과 실제 생성된 결과를 함께 확인하기로 했습니다.

버킷 설정만 보고 전환을 끝냈다고 판단하지 않도록, 새로 저장한 객체를 골라 암호화 속성도 조회해야 해요.

버저닝과 감사 로그, 암호화처럼 설정 이전의 데이터에 영향을 주는 항목은 적용 순서도 검토해야 해요. 나중에 설정을 바꿨을 때 기존 데이터까지 달라지는지, 별도 처리가 필요한지 확인해야 합니다.

이번에는 시크릿을 담은 리소스를 추가하기 전에 키 생성과 backend 변경을 끝내는 순서로 정리했어요. 새 객체에 적용되는 암호화 방식과 과거 버전에 남는 방식을 구분한 결정입니다.

✍️ 전환 결과
state 버킷의 기본 암호화를 바꾸고 apply도 성공했지만, 새 객체는 이전 방식으로 저장됐어요. backend의 encrypt = true가 업로드 요청에 암호화 방식을 명시하고 있었기 때문입니다. backend에 사용할 키를 지정한 뒤 새 객체의 암호화 방식이 바뀌었어요.

키를 만드는 bootstrap의 backend가 아직 없는 키를 가리키면 init이 실패하므로, 키 생성과 backend 변경을 두 PR로 나눴습니다. 과거 버전은 설정 변경만으로 재암호화되지 않아, 시크릿을 담는 리소스를 추가하기 전에 두 단계를 끝내는 순서로 진행했어요.
