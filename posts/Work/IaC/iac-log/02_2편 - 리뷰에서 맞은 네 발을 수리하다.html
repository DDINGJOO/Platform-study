2편. prod apply 승인 절차와 변경 가드 수정 ← 지금 이 글

설계 리뷰에서 7.5점을 받은 뒤, 지적받은 내용을 고칠 브랜치를 만들었어요. 이름은 IAC-0008/fix-apply-gate-and-label-guard로 정했어요. 지적 4건 중 두 건이 같은 워크플로 파일에 있었으니까요.

워크플로를 고치면서 리뷰에 없던 문제도 하나 더 찾았어요. plan과 apply를 분리하니 기존 가드가 읽던 값이 없어졌고, 라벨을 붙인 뒤 재실행하는 절차도 이벤트 처리 방식과 맞지 않았어요. 각 가드가 어떤 값을 언제 읽는지 확인하면서 수정했어요.

1. prod plan과 apply를 별도 실행으로 나눴어요

첫 번째 지적은 prod apply 절차였어요. 기존 구조에서는 수요일에 dispatch 버튼을 누르면 월요일에 머지된 변경까지 함께 계산한 plan이 같은 run 안에서 곧바로 apply돼요. 실행한 사람이 알고 있던 변경 외에도, 아직 plan을 확인하지 않은 변경이 함께 반영될 수 있었어요.

처음에는 plan과 apply 사이에 state가 바뀔 수 있다는 점이 걱정됐어요. 확인한 시점과 사용하는 시점의 값이 달라지는 TOCTOU 문제 때문에 둘을 한 run에 두었거든요. 확인해 보니 Terraform이 이미 이를 검사하고 있었어요. -out=tfplan으로 저장한 plan에는 lineage와 serial이 포함돼서, apply 전에 state가 바뀌면 Saved plan is stale로 거부해요.

이 검사를 이용하면 plan과 apply 사이에 사람이 내용을 확인하는 단계를 둘 수 있어요. 그래서 dispatch 입력에 stage를 넣고 재사용 워크플로에 mode(auto / plan / apply)를 만들었어요. dev는 기존처럼 auto로 한 번에 실행하고, prod만 plan과 apply를 각각 실행하도록 나눴어요.

workflow_dispatch: inputs: env: [dev, prod] # 선택한 환경 하나에만 적용된다 stage: [plan, apply] # prod 는 버튼을 두 번 눌러야 나간다 plan_run_id: '' # stage=apply 일 때 어느 plan 을 적용할지 allow_destroy: false

plan_run_id는 적용할 plan을 사람이 직접 지정하기 위한 입력이에요. stage=plan으로 실행한 run의 Job Summary에는 "이 plan을 적용하려면 plan_run_id = 12345로 넣으세요"라는 안내가 나와요. 최신 plan을 자동으로 찾는 대신 이 값을 입력하게 해서, 요약 화면을 확인하고 적용할 run을 고르는 단계를 두었어요.

그림 1. prod plan을 확인한 뒤 run ID를 지정해서 apply해요

2. 가드가 실제 적용할 plan 파일을 검사하게 했어요

파괴적 변경 가드는 1단계를 고치다가 추가로 발견한 문제예요. 기존에는 plan 잡이 삭제·재생성 건수를 세어 job output으로 넘기고, apply 잡이 그 숫자로 통과 여부를 정했어요.

그 구조에는 두 가지 문제가 있었어요. 건수를 전달하는 경로와 artifact로 내려받는 tfplan 파일이 달라서 숫자와 파일이 어긋날 수 있었어요. 또 mode=apply에서는 plan 잡을 실행하지 않으므로 그 건수 자체가 없어요. plan과 apply를 분리한 뒤에도 가드가 판단하려면 근거를 바꿔야 했어요.

그래서 가드를 apply 잡 안으로 옮겼어요. 내려받은 tfplan을 terraform show -json으로 열어 삭제·재생성 건수를 직접 세도록 했어요. 앞 잡의 output 대신 실제로 적용할 파일을 검사하는 방식이에요.

⚠️ 래퍼를 거친 종료 코드도 확인해야 했어요
변경 유무를 판정할 때도 전달되는 값을 확인해야 했어요. terraform plan -detailed-exitcode는 변경이 있으면 2를 반환해요. 하지만 setup-terraform 액션의 래퍼를 거치면 그 코드가 그대로 전달되지 않았어요. 변경이 있는데도 has_changes=false가 되어 apply를 건너뛰었어요. terraform_wrapper: false로 래퍼를 껐고, 변경 내용은 plan JSON을 기준으로 확인하도록 했어요.

3. 재실행할 때 최신 PR 라벨을 읽게 했어요

다음은 1편에서 지적받은 라벨 가드의 안내였어요. PR에 파괴적 변경이 있으면 "의도한 변경이라면 PR에 allow-destroy 라벨을 붙이고 다시 실행하세요"라고 안내하고 있었어요.

하지만 github.event에는 이벤트가 발생한 순간의 webhook payload가 들어 있어요. 안내대로 라벨을 붙이고 Re-run을 눌러도 가드는 라벨을 붙이기 전의 값을 다시 읽어서 실패해요. 재실행으로는 최신 라벨을 읽을 수 없는데, 안내문에서는 그 절차를 권하고 있었어요.

라벨을 제거할 때도 문제가 있었어요. 라벨이 있는 상태에서 검사를 통과한 뒤 라벨을 떼면 재검사가 실행되지 않았어요. 허용 근거가 사라져도 이전 성공 결과가 남았어요.

// before — 이벤트 발생 순간의 박제를 읽는다 ${{ contains(github.event.pull_request.labels.*.name, 'allow-destroy') }} // after — 실행 시점에 직접 조회한다 gh pr view "$PR" --json labels --jq '.labels[].name' | grep -qx allow-destroy on: pull_request: types: [opened, synchronize, reopened, labeled, unlabeled]

두 경우를 나눠 고쳤어요. 라벨은 실행 시점에 API로 조회해서 현재 붙어 있는지 확인해요. 또 types에 unlabeled를 추가해 라벨을 제거하면 재검사가 실행되게 했어요. 실제 수정에서는 라벨 추가 후 Re-run을 이용하고, 제거할 때 자동으로 다시 계산했어요. 바로 위 발췌에는 labeled도 들어 있지만, 3편에서 확인한 구현에는 이 트리거를 추가하지 않았어요. 발췌와 실제 구현을 구분해서 봐야 합니다.

그림 2. 재실행해도 이벤트 당시의 라벨을 읽어 실패했어요

4. 삭제 허용 입력이 선택한 환경에만 적용되게 했어요

환경 선택 입력은 십 분 만에 고쳤지만, 영향 범위가 큰 문제였어요. 기존 dispatch 입력에는 allow_destroy만 있고 환경 선택이 없었어요. dev 잡과 prod 잡은 이 입력을 똑같이 전달받고 있었어요.

dev 리소스를 삭제하려고 allow_destroy를 켜도 prod의 파괴적 변경 가드까지 함께 해제된 채 prod apply가 실행되는 구조였어요. 의도한 대상은 dev 하나여도 실제로는 두 환경에 모두 영향을 줬어요.

env choice 입력을 추가해서 실행할 환경을 하나 고르게 했어요. allow_destroy도 선택한 환경에만 적용돼요. 환경을 고르는 입력이 없던 탓에 생긴 문제라, 실행 대상과 삭제 허용 범위를 함께 제한했어요.

5. iam:* 권한 상승 경로를 두 겹으로 제한했어요

가장 오래 걸린 작업은 IAM 권한 상승 경로를 막는 일이었어요. apply 역할에는 PowerUserAccess에 빠진 IAM 권한을 보충하려고 iam:*를 허용했어요. 자기 권한을 확대하지 못하게 파이프라인 역할 이름 패턴(platform-iac-*)에는 Deny를 걸어 둔 상태였어요.

하지만 그 패턴과 다른 이름의 역할은 만들 수 있었어요. 새 역할에 AdministratorAccess를 붙이고 그 역할을 사용하면 dev/prod 태그 격리 3중 방어를 우회할 수 있었어요. 파이프라인 역할의 이름만 제한해서는 이 경로를 막지 못했어요.

먼저 sts:AssumeRole을 명시적으로 Deny했어요. 새 역할을 만들더라도 apply 역할이 그 역할을 사용하는 단계에서 차단하려는 조치예요.

여기에 permissions boundary도 강제했어요. 역할 생성과 정책 부착은 iam:PermissionsBoundary 조건을 만족할 때만 허용해요. boundary를 제거하거나 boundary 정책 자체를 수정하는 작업은 Deny했어요.

statement { sid = "RoleWriteRequiresBoundary" effect = "Allow" actions = ["iam:CreateRole", "iam:AttachRolePolicy", "iam:PutRolePolicy"] condition { test = "StringEquals" variable = "iam:PermissionsBoundary" values = [aws_iam_policy.tf_boundary.arn] } } # + iam:DeleteRolePermissionsBoundary Deny (떼는 것 금지) # + boundary 정책의 iam:CreatePolicyVersion Deny (내용 수정 금지) # + sts:AssumeRole Deny (갈아타기 차단)

이렇게 하면 Terraform이 AdministratorAccess를 붙인 역할을 만들어도 실효 권한은 붙인 정책과 boundary의 교집합으로 제한돼요. AdministratorAccess라는 이름과 관계없이 boundary에서 허용하지 않는 작업은 할 수 없어요. 새 역할에서 다시 역할을 만들려는 경로에도 boundary 제약이 적용되도록 해서, 역할 이름과 무관하게 권한의 상한을 유지하는 방식이에요.

그림 3. 역할의 실효 권한은 붙인 정책과 boundary의 교집합이에요

6. 수정 후 다시 확인한 항목

diff를 다시 읽어 보니, 처음 설계에서 고려하지 못한 실행 경로들이 있었어요. 한 run에서만 쓰던 값을 별도 run에서도 읽으려 했고, 이벤트 당시의 값을 현재 PR 상태로 취급했어요. IAM 정책도 기존 역할 이름만 제한해서는 새 역할을 통한 권한 상승을 막지 못했어요.

다음에 워크플로나 IAM 정책을 작성할 때 확인할 항목을 세 가지로 정리했어요.

🧭 워크플로와 IAM 정책을 작성할 때 확인할 것
• 이 실행이 어느 변경과 환경에 영향을 주는가: 패치 ①(확인하지 않은 plan도 적용됨), 패치 ④(dev 실행이 prod에도 적용됨)
• 이 입력과 권한이 어디까지 적용되는가: 패치 ④(allow_destroy가 두 잡에 적용됨), 패치 ⑤(iam:*로 새 역할을 만듦)
• 이 값은 언제 만들어졌는가: 패치 ②(앞 잡이 센 숫자), 패치 ③(이벤트 당시의 payload)

특히 값이 만들어지는 시점을 구분할 필요가 있었어요. github.event는 이벤트 당시의 값이고, job output은 앞 잡에서 계산한 값이에요. 종료 코드도 래퍼를 거치면 기대한 대로 전달되지 않을 수 있었어요. 현재 상태를 판단하는 데 쓸 수 있는지 각각 확인해야 했어요.

plan과 apply를 같은 run에 두어야 한다는 전제도 다시 확인했어요. Terraform이 stale plan을 거부하므로 state 변경 검사 때문에 두 단계를 붙여 둘 필요는 없었어요. 그 동작을 확인한 뒤 prod plan을 사람이 읽는 단계를 추가할 수 있었어요.

이 다섯 패치는 워크플로 쪽(①~④)과 IAM 쪽(⑤)으로 나눠 PR 두 개로 올렸고, 당시에는 리뷰 대기 중이었어요. IAM 패치는 bootstrap/에 있어서 머지 후에도 사람이 로컬에서 한 번 apply해야 반영돼요. CI가 자기 state 버킷을 파괴할 수 있는 경로를 만들지 않기로 했기 때문이에요.

✍️ 수정 내용과 당시 상태
prod는 plan과 apply를 별도로 실행하고, 파괴적 변경 가드는 실제 tfplan 파일과 실행 시점의 PR 라벨을 검사하도록 고쳤어요. 삭제 허용은 선택한 환경에만 적용하고, IAM에는 AssumeRole Deny와 permissions boundary 제약을 추가했어요.

다섯 패치를 담은 PR 두 개는 당시 리뷰 대기 중이었고, bootstrap의 IAM 변경은 머지 후 로컬 apply가 필요했어요.
