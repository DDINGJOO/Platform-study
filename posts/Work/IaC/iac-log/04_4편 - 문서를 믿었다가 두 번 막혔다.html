같은 워크플로를 세 번 실행했는데 모두 같은 오류로 실패했어요. Not authorized to perform sts:AssumeRoleWithWebIdentity라는 오류였어요. GitHub Actions에서 AWS 액세스 키 없이 인증하려고 OIDC를 사용했어요. 이를 위해 AWS 역할에는 신뢰 정책(이 역할을 사용할 수 있는 주체를 정하는 문서)이 필요해요. 공식 문서 예제를 그대로 옮겼고 오타도 없었어요. OIDC 프로바이더(AWS가 GitHub 토큰을 검증하도록 등록하는 항목)도 계정에 이미 있었는데 역할 사용이 거부됐어요.

Terraform 저장소에 CI/CD를 붙이던 그날, 이 신뢰 정책을 고친 뒤에는 GitHub Environment 설정에서도 실패했어요. 신뢰 정책에서는 문서 예제와 실제 sub 형식이 달랐고, Environment에서는 객체 생성과 보호 규칙 설정의 지원 범위를 구분하지 못했어요.

1. 신뢰 정책과 실제 sub 형식 비교

신뢰 정책은 GitHub 토큰의 sub(주체) 클레임이 내가 적어둔 문자열과 같은지를 봐요. 문서 예제의 조건은 repo:<org>/<repo>:ref:refs/heads/main 이렇게 생겼어요. 저장소 이름과 브랜치로 주체를 제한하는 조건이에요. 예제대로 작성해도 거부돼서, 정책에 적은 문자열과 실제 발급되는 문자열이 같은지 API로 확인했어요.

$ gh api repos/<org>/<repo>/actions/oidc/customization/sub --jq .sub_claim_prefix 기대한 sub: repo:{조직}/{저장소}:ref:refs/heads/main 실제 sub: repo:{조직}@{조직ID}/{저장소}@{저장소ID}:ref:refs/heads/main (@ 뒤 숫자 ID 두 개가 끼어든다 — 실제 값은 가렸어요)

프리픽스에 숫자 ID 가 들어가는 이 형식을 불변 주체 클레임(immutable subject claim)이라고 불러요. 이름은 바뀔 수 있어도 숫자 ID는 바뀌지 않으니, 저장소를 지우고 같은 이름으로 다시 만들더라도 이전 역할을 사용할 수 없게 하는 형식이에요. 제가 참고한 문서 예제는 이 옵션을 사용하지 않는 기본 형식이어서 실제 값과 달랐어요.

위 명령의 응답에는 use_immutable_subject라는 필드도 함께 있어요. 제 저장소는 그 값이 false인데도 프리픽스에 ID가 들어 있었어요. 이 값만으로 형식을 판단할 수 없어서 응답의 프리픽스를 그대로 사용했어요.

2. 와일드카드 대신 실행별 sub 허용

형식 차이를 확인한 뒤에는 와일드카드로 조건을 넓히는 방법도 생각했어요. repo:{조직}/{저장소}:*는 조직·저장소 ID를 생략한 개념 예시예요. 이 문자열 그대로는 앞에서 확인한 ID 포함 sub와 매칭되지 않습니다. 실제 sub 형식에 맞춰 브랜치 부분만 와일드카드로 넓히면 브랜치별 조건을 따로 쓰지 않아도 되지만, 그 저장소의 아무 브랜치에서나 역할을 사용할 수 있어요. 저장소 이름 자리까지 넓히면 조직의 다른 저장소도 허용돼요. 실제 인프라를 바꾸는 apply 역할에는 허용 범위가 너무 넓어서 변수 validation으로 와일드카드를 금지했어요.

허용할 sub를 구체적으로 정할 때는 실행 경로도 살펴봐야 했어요. plan 역할(변경을 미리 계산만 하는 쪽)을 쓰는 곳은 세 군데(PR, main push, 코드와 실제 인프라가 어긋났는지 보는 야간 점검)인데 발급되는 sub 는 세 가지가 아니라 두 가지예요. 호출 지점 수와 sub 개수가 1:1로 대응하지 않아요. 한쪽만 허용하면 다른 실행이 거부되므로 PR뿐 아니라 스케줄 실행에 쓰이는 sub도 포함해야 했어요.

⚠️ 역할별로 허용한 sub
• 와일드카드 금지를 !strcontains(var.github_subject_prefix, "*") validation으로 변수에 명시했어요
• plan 역할은 :pull_request 와 :ref:refs/heads/main 두 개를 함께 허용해요 (스케줄 실행은 main ref로 발급돼요)
• apply 역할은 :environment:<env> 하나만 허용해요

3. Environment 보호 규칙 설정의 422 오류

OIDC 인증 문제를 해결한 뒤에는 prod apply의 승인 절차를 설정하려고 했어요. GitHub Environment는 배포 대상마다 보호 규칙을 설정하는 기능이에요. 여기에 required reviewer(필수 승인자)를 지정하면 승인 전에는 job이 시작되지 않아 OIDC 자격증명도 발급되지 않아요. 이 방식을 사용하려고 API를 호출했지만 아래 오류가 나왔어요.

PUT /repos/{조직}/{저장소}/environments/prod {"reviewers": [{"type": "User", "id": ...}]} 422 Failed to create the environment protection rule. Please ensure the billing plan supports the required reviewers protection rule.

wait_timer 도 같은 422 였어요. 당시 조직 플랜은 GitHub Team이었어요.

4. Environment 생성과 보호 규칙의 지원 범위

문서에는 이렇게 적혀 있어요. Organizations with GitHub Team can configure environments for private repositories. 저는 이 문장을 "보호 규칙까지 쓸 수 있다"로 읽었는데 실제 범위는 Environment 객체를 만들 수 있다까지였어요. 보호 규칙은 별개였고요.

Environment 생성 자체는 성공해서 보호 규칙이 적용됐는지 따로 확인해야 했어요. dev 와 prod Environment 는 정상 생성되고 워크플로에 environment: prod 를 써도 에러가 나지 않아요. 다만 protection_rules 가 빈 배열이라 승인 절차 없이 실행돼요. 이 상태를 그대로 뒀다면 main 머지 후 승인 없이 prod apply가 실행됐을 거예요.

그래서 설계를 바꿨어요. prod 트리거를 workflow_dispatch 수동 실행으로 바꾸고, 다른 사람의 검토는 브랜치 보호의 필수 승인으로 받게 했어요. 기여자가 전원 admin인 조직이어서 관리자에게도 보호 규칙을 적용했어요. GitHub은 작성자의 자기 승인을 허용하지 않으므로 작성자와 승인자가 달라져요. 다만 수동 실행은 혼자 할 수 있어서 apply 단계마다 두 사람의 승인을 강제하지는 못했어요.

5. 확인한 제약과 설계 변경을 ADR에 남기기

신뢰 정책은 기본 예제만으로 작성할 수 없었고, Environment도 생성 가능하다는 설명만으로 보호 규칙 지원 여부를 판단할 수 없었어요. 실제 sub와 API 응답을 확인한 뒤에야 신뢰 정책과 승인 절차를 수정할 수 있었어요.

이번에는 gh api로 프리픽스를 조회하고 PUT으로 보호 규칙 설정을 시도해 차이를 확인했어요. 둘 다 명령 한 줄로 확인할 수 있는 제약이었어요. 파이프라인을 모두 구현하기 전에 확인해서 설계를 바꿀 수 있었어요.

설계를 바꾼 이유는 ADR(설계 결정을 남기는 문서)에도 적었어요. 원래 설계를 담은 ADR-0001을 지우지 않고 "이 부분은 ADR-0002로 대체됐다"고 표시했어요. 재검토 조건에는 "Enterprise로 올라가면 원래 설계로 복귀"를 적어 두어, 승인 방식을 바꾼 이유와 다시 검토할 조건을 함께 남겼어요.

✍️ 오늘의 요약
실제 sub 프리픽스를 조회해 신뢰 정책을 맞췄고, GitHub Team에서 Environment 보호 규칙 설정이 422로 거부돼 prod apply를 수동 실행으로 바꿨어요. 다른 사람의 검토는 브랜치 보호의 필수 승인으로 받되, apply 단계마다 두 사람의 승인을 강제하지는 못했어요.

이 제약과 설계 변경은 ADR-0002에 남기고, Enterprise 업그레이드 시 원래 승인 방식으로 돌아갈 수 있도록 재검토 조건을 적었어요.
