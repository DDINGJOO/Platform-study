29편. Lambda 편입에서 환경변수와 배포 코드의 관리 범위 나누기 ← 지금 이 글

10월 8일 오전 9시 15분에 머지한 PR 제목은 "알림 함수 셋을 편입한다. 환경변수는 코드 밖"이었어요. 함수를 Terraform으로 관리하되, 환경변수 값은 HCL에 적지 않기로 했습니다.

알림 함수 셋의 환경변수에는 메신저 웹훅 주소가 평문으로 들어 있었어요. 청구서 생성 함수와 로그 전달 함수, 리뷰 봇에도 환경변수 시크릿이 있었습니다. 운영 설정을 그대로 HCL에 옮기면 이 값들까지 저장소에 남게 돼요. 한편 이날 편입한 블로그 렌더 함수에는 환경변수가 없었어요.

이날 오전 9시 15분부터 오후 2시 14분까지 함수 9개를 편입했어요. 함수별로 Terraform이 관리할 속성과 환경변수·배포 코드처럼 별도로 관리할 속성을 구분했습니다.

1. 함수를 담으면 그 안의 시크릿도 같이 담긴다 2. 가릴 수 있는 시크릿과 가릴 수 없는 시크릿 3. 배포 파이프라인이 코드를 바꾸는 함수 둘 4. 지난달에 "쓰지 않는다"고 적어 둔 그 lifecycle 5. 9개가 들어왔고, 들어오면서 드러난 것

배포 파이프라인이 코드를 관리하는 함수는 청구서 생성 함수 둘과 블로그 렌더 함수 하나, 합계 셋이에요. 위 작업 메모의 "함수 둘"은 수가 맞지 않아 정정합니다. 뒤에서 셋의 관리 범위를 나눠 설명할게요.

1. 환경변수 값을 저장소에 남기지 않고 편입하기

함수를 편입하지 않으면 런타임 버전, 메모리, 타임아웃, 환경변수의 콘솔 변경을 IaC로 확인할 수 없어요. 1차 편입 조사에서도 지원이 끝난 런타임으로 실행 중인 함수와, 이미 지워진 DB를 매주 멈추려 하던 함수를 처음 확인했습니다.

📖 용어: drift 와 drift 잡
drift는 코드에 적힌 상태와 실제 상태가 다른 것이에요. drift 잡은 매일 정해진 시각에 plan을 실행하고, 차이가 있으면 이슈를 여는 자동화입니다. 다만 코드가 관리하는 자원만 비교하므로, 편입하지 않은 함수의 변경은 확인할 수 없어요.

함수 설정을 관리하려면 편입이 필요했지만, 환경변수의 시크릿을 어떻게 처리할지 먼저 정해야 했어요. 세 가지 방법을 검토했습니다.

첫째는 값을 그대로 HCL에 적는 방법이에요. 웹훅 주소와 비밀번호가 저장소 이력에 남기 때문에 선택하지 않았습니다.

둘째는 환경변수 블록만 생략하는 방법이에요. Terraform은 코드에 적지 않은 속성을 프로바이더 기본값으로 되돌릴 수 있어요. 환경변수 생략이 "환경변수 없음"으로 반영되면 첫 apply에서 운영 환경변수가 지워질 수 있으므로, 생략만으로 기존 값이 유지된다고 판단하지 않았습니다.

셋째는 환경변수 블록을 생략하면서 해당 속성을 변경 비교에서 제외하는 방법이에요. 기존 값을 유지할 수 있도록 이 방법을 선택했습니다.

resource "aws_lambda_function" "알림_함수" { function_name = "..." runtime = "python3.12" memory_size = 128 timeout = 3 # environment 블록을 쓰지 않는다 lifecycle { # 환경변수에 시크릿(메신저 웹훅)이 있다. 코드 밖에 둔다. ignore_changes = [environment] } }
📖 용어: ignore_changes
지정한 속성의 변경을 Terraform이 반영하지 않도록 하는 설정이에요. 여기서는 기존 환경변수의 변경을 plan에 표시하지 않고 apply에서도 유지하도록 썼습니다. 함수 전체를 제외하지 않고 속성별로 관리 범위를 나눌 수 있어요.

이렇게 하면 런타임, 메모리, 타임아웃, 태그, 코드를 Terraform으로 관리하고 매일 drift를 확인할 수 있어요. 대신 환경변수의 콘솔 변경은 plan으로 확인하지 못합니다. 환경변수 값은 state에는 남아요. state를 전용 키로 암호화하고 역할별로 접근을 제한하는 조건에서 이 범위를 받아들이기로 했습니다.

그림 1. 환경변수 블록을 생략할 때는 기존 값의 유지 여부도 확인해야 해요

2. 코드에 들어 있는 시크릿은 먼저 수정하기

같은 날 아침, 느린 쿼리 알림 함수는 편입 대상에서 제외했어요. 커밋 본문에도 "코드에 웹훅이 하드코딩돼 있어 넣지 않았다"고 이유를 남겼습니다.

환경변수와 달리 함수 코드에 들어 있는 값은 HCL에서 생략할 수 없었어요. 1차 편입에서 운영 함수로부터 회수한 zip을 바이트 그대로 커밋하고, Terraform이 그 파일을 참조하기로 정했기 때문입니다.

📖 용어: 코드 해시 (source_code_hash)
Terraform 이 "지금 떠 있는 함수 코드"와 "저장소에 있는 zip"이 같은지 비교할 때 쓰는 값이에요. 둘이 다르면 apply 가 저장소의 코드를 올려 함수를 재배포합니다. 편입은 실물을 바꾸지 않는다는 전제를 지키려면 이 값이 처음부터 일치해야 해요.

웹훅만 지우고 커밋하면 해시가 달라져요. 첫 apply에서 운영 함수의 코드가 재배포되므로, 기존 상태를 바꾸지 않고 편입한다는 전제를 지킬 수 없었습니다.

나머지 여덟은 시크릿 제거를 위한 코드 수정 없이 편입할 수 있었지만, 이 함수는 코드를 고쳐야 저장소에 넣을 수 있었어요. 오전 9시 15분 편입에서 제외했던 함수를 낮 12시 13분에 편입했습니다.

이 함수는 기존 코드를 유지한 채 편입하는 방식을 따르지 않았어요. 웹훅을 제거하고 다시 묶은 zip의 해시가 운영 코드와 달라, 한 번의 apply에서 import와 재배포를 함께 진행했습니다. 코드 수정 내용은 31편에서 다룹니다.

💡 시크릿이 어디 있느냐로 처리가 갈려요
• 환경변수에 있는 경우: HCL에 값을 적지 않고 변경 무시를 지정해 편입했어요.
• 함수 코드에 있는 경우: 회수한 zip에도 시크릿이 들어 있으므로 먼저 코드를 수정해야 했어요.
환경변수는 HCL에서 제외할 수 있지만, zip 안의 시크릿은 함수 코드를 수정해야 제거할 수 있다는 차이입니다.
그림 2. 시크릿의 위치가 편입 순서를 정했다

3. 배포 코드와 함수 설정의 관리 범위 나누기

이 저장소에서는 8월에 배포 파이프라인이 변경하지 않는 자원만 관리하기로 정했어요. 편입 전에 CloudFormation 소유 여부, 배포 파이프라인의 변경 여부, 공유 자원 여부를 확인합니다. 파이프라인의 변경 여부는 지난 90일의 감사 로그에서 관리 API 호출 주체가 사람인지 자동화인지 구분해 판단해요.

📖 용어: 배포 파이프라인
앱 코드를 빌드해서 운영에 배포하는 자동화예요. 인프라 저장소와 별도로 실행되며 함수 코드나 컨테이너 이미지 주소를 바꿉니다. Terraform도 같은 속성을 관리하면 배포된 값을 저장소에 적힌 값으로 되돌릴 수 있어요.

1차 편입 때는 여섯 함수 전부 호출 주체가 사람이었어요. 그런데 이날 담은 9개 중 셋은 달랐습니다. 청구서 생성 함수 둘(운영·개발)은 컨테이너 이미지로 도는데 앱 파이프라인이 배포할 때마다 이미지 주소를 바꾸고, 블로그 렌더 함수는 프론트 저장소의 배포 워크플로가 update-function-code 로 새 코드를 올리고 버전을 발행합니다.

이 규칙을 함수 전체에 적용하면 셋 다 편입 대상에서 빠져요. 그러면 런타임, 메모리, 타임아웃, 호출 경로 설정을 계속 코드 밖에서 관리해야 합니다.

그래서 속성별로 관리 주체를 나눴어요. 함수 설정은 Terraform이 관리하고, 코드나 이미지 같은 배포 산출물은 파이프라인이 계속 변경하도록 했습니다.

알림 함수 · 느린 쿼리 알림 함수 · 로그 전달 함수 · 리뷰 봇 ignore_changes = [environment] → 설정과 코드는 저장소가 소유. 환경변수만 코드 밖 청구서 생성 함수 (컨테이너 이미지) ignore_changes = [image_uri, environment] → 이미지 주소는 앱 파이프라인이 바꾼다 블로그 렌더 함수 (파이프라인이 zip 을 올린다) ignore_changes = [filename, source_code_hash, publish] → 코드는 파이프라인, 설정과 호출 경로는 저장소

Terraform이 배포 코드까지 관리하면 앱팀이 배포할 때마다 운영 상태와 저장소 사이에 차이가 생겨요. drift 잡은 차이가 하나만 있어도 이슈를 열기 때문에 매일 배포하면 매일 이슈가 열립니다. 정상 배포도 인프라 채널에 drift로 알려지면, 확인해야 할 설정 변경을 구분하기 어려워져요.

⚠️ 변경 무시를 지정한 이유도 남기기
변경 무시를 지정한 속성은 설정을 제거할 때까지 drift 감시에서 제외돼요. 그래서 "파이프라인이 변경하는 속성", "시크릿이 들어 있는 속성"처럼 이유를 주석으로 남겼습니다. 다음 사람이 변경 무시를 유지할지 판단하는 데 필요한 정보예요.

4. ignore_changes를 쓰지 않기로 했던 이유 다시 확인하기

1차 편입을 정한 결정 문서에는 "ignore_changes를 쓰지 않는다"고 적혀 있어요. 9월 21일에 적은 이 결정과 이번 설정이 다른 이유를 확인해야 했습니다.

당시 우려는 더미 zip과 변경 무시를 함께 쓰는 방식에 있었어요. 코드 출처를 재현할 수 없어서 더미 zip을 지정하고 그 변경을 무시하자는 안이었습니다. 리팩터링 중 lifecycle 블록이 지워지면 다음 apply가 운영 함수에 더미 코드를 배포해요. 저장소에 원본이 없으면 되돌리기도 어렵습니다.

이번에 zip 코드 관련 속성에 변경 무시를 지정한 블로그 렌더 함수는 조건이 달랐어요. 저장소에 운영 함수에서 회수한 원본 zip이 있었고, 편입 시점에 해시도 일치했습니다. lifecycle이 지워져 apply가 실행되면 저장소에 보관한 코드가 배포됩니다. 파이프라인의 다음 배포에서는 최신 코드를 다시 올릴 수 있어요.

원본 zip을 확보하면서 더미 배포 후 복구할 수 없다는 우려는 해소됐어요. 이번에는 파이프라인과의 충돌을 피하려고 변경 무시를 지정했습니다. 이전 결정에 이유가 남아 있었기 때문에 달라진 조건을 확인하고 적용 여부를 다시 판단할 수 있었어요.

그림 3. 결정 문서에 이유를 적어 두면 조건이 바뀔 때 다시 판단할 수 있다

5. 함수 9개의 편입 결과와 조사에서 확인한 점

함수 9개의 편입 시각은 다음과 같아요. 편입 PR마다 적용을 마친 뒤 import 블록을 삭제하는 PR이 이어졌습니다.

09:15 알림 함수 3 → 09:24 블록 삭제 ( 9분) 09:54 청구서 생성 함수 2 (운영·개발) → 10:07 블록 삭제 (13분) 10:26 로그 전달 함수 1 · 리뷰 봇 1 → 10:41 블록 삭제 (15분) 12:13 느린 쿼리 알림 함수 1 → 12:21 블록 삭제 ( 8분) 14:14 블로그 렌더 함수 1 → 14:22 블록 삭제 ( 8분) 합계 9개

실행 역할은 IAM 편입 단계에서 다루기로 해서 이날은 주소로만 참조했어요. 트리거는 이날 오후에 별도로 편입했습니다. 함수 본체와 트리거를 한 PR에 넣으면 되돌릴 범위가 커지기 때문이에요.

조사에서는 두 가지를 추가로 확인했어요. 하나는 태그가 없는 함수였습니다. 소유자나 서비스를 구분하는 태그 없이 매시 정각에 실행됐고, 30일 동안 730번 가까이 호출됐어요. 이번 apply에서 태그를 처음 붙였습니다. 다른 하나는 로그 전달 함수의 코드 해시가 제작사 공식 배포판 최근 다섯 버전 어느 것과도 맞지 않는다는 점이에요. 직접 묶어 올린 코드로 보고, 업그레이드할 때 공식 배포판으로 교체해야 한다는 메모를 .tf 주석에 남겼습니다. 1차 조사에서 확인했던 지원 종료 런타임도 이날 편입하면서 올렸어요.

편입한 함수 9개의 런타임, 메모리, 타임아웃, 태그는 코드로 관리하고 매일 drift를 확인하게 됐어요. 시크릿이 든 환경변수는 편입할 때 HCL에 적지 않고 변경 무시를 지정했습니다. 환경변수가 없는 블로그 렌더 함수에는 이 조치가 필요하지 않았어요. 시크릿 이전도 병행했고, 낮 12시 34분에는 알림 함수 넷의 환경변수를 코드로 옮기면서 변경 무시를 제거했습니다. 이 순서와 시크릿 이전 내용은 31편에서 다룹니다.

✍️ 편입 결과
함수 9개를 편입하면서 설정과 배포 코드의 관리 주체를 속성별로 나눴어요. 시크릿이 든 환경변수와 파이프라인이 바꾸는 배포 산출물에는 변경 무시를 지정했습니다. 환경변수는 시크릿 이전 후 다시 관리할 수 있는 임시 제외였고, 배포 산출물은 파이프라인이 계속 관리하는 속성이었어요.

변경 무시를 지정한 이유는 주석으로 남겼고, 알림 함수 넷은 같은 날 시크릿을 옮긴 뒤 환경변수 관리를 시작했습니다. 실행 역할과 트리거는 함수 본체의 편입과 별도로 다뤘어요.
