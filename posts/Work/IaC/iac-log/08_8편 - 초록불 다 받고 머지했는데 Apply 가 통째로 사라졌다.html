8편. 재사용 워크플로 권한 누락으로 Apply 잡이 생성되지 않은 이유 ← 지금 이 글

PR 체크 네 개가 모두 통과했어요. fmt / validate / tflint, checkov, plan (dev), plan (prod)였고, 리뷰 승인을 받은 뒤 머지했어요.

main 에 push 가 들어오자 Terraform Apply 워크플로가 잡을 하나도 만들지 못하고 끝났어요. 잡 목록이 비어 있었고, 화면에는 다음 메시지가 남았어요.

Terraform Apply · main · push status: failure jobs: 0 개 message: This run likely failed because of a workflow file issue.

잡이 생성되지 않아 실행 로그도 없었어요. 화면의 메시지만으로는 어느 파일의 어느 줄이 문제인지 알 수 없었고요. dev 자동 apply 와 수동 dispatch 모두 잡 0 개로 끝나서, 두 경로로 인프라 변경을 반영할 수 없었어요.

1. 호출 잡의 권한을 넘을 수 없어요

이 저장소의 apply 파이프라인은 환경마다 같은 절차를 반복해요. init, plan, 파괴적 변경 검사, apply 를 실행하고, 반영이 끝나면 이슈를 닫아요. 이 절차를 _apply-env.yml 이라는 재사용 워크플로로 분리했고, 호출부에서는 uses: 에 같은 파일을 지정해 환경만 바꿔 실행하도록 했어요.

이 구조에서는 호출부와 재사용 워크플로의 권한 선언을 함께 확인해야 해요. 호출 잡이 선언한 permissions 가 상한이고, 재사용 워크플로가 선언한 permissions 는 그 범위 안에 있어야 해요.

저는 요구한 권한이 부족하면 실행 중 해당 스텝이 403 으로 실패할 거라고 생각했어요. 하지만 이번 오류는 스텝 실행 전에 발생했어요. GitHub 이 워크플로 파일을 읽고 잡 그래프를 만드는 단계에서 권한 검증에 실패한 거예요.

잡이 실행된 뒤 실패했다면 어느 잡에서 오류가 났는지 확인할 수 있었을 거예요. 이번에는 잡 생성 전 검증이 실패해서 같은 파일에 정의된 모든 잡이 만들어지지 않았어요. 권한이 맞는 다른 호출부도 실행되지 않은 이유예요.

2. 두 호출부 중 dev-auto 에 권한이 빠졌어요

하루 전 커밋에서 두 호출부 모두에 잡 단위 permissions 를 지정했어요. id-token: write, contents: read, actions: read 세 권한이 양쪽에 같았고, 재사용 워크플로가 요구하는 권한도 그 셋이었어요.

다음 커밋에서 prod 반영 후 prod-pending 이슈를 자동으로 닫는 스텝을 _apply-env.yml 에 추가했어요. 이때 issues: write 도 필요해졌어요. 호출부 두 곳을 함께 수정해야 했지만, 수동 dispatch 잡에만 추가하고 push 트리거로 실행되는 dev-auto 잡에는 빠뜨렸어요.

# _apply-env.yml — 불려가는 쪽이 요구하는 권한 permissions: id-token: write contents: read actions: read issues: write # apply 성공 시 이슈를 닫는다 ← 이번에 추가한 줄 # terraform-apply.yml — 부르는 쪽, 호출부가 둘이다 jobs: dev-auto: # push 트리거 permissions: id-token: write contents: read actions: read # issues 가 없다 ← 여기를 빠뜨렸다 uses: ./.github/workflows/_apply-env.yml dispatch: # workflow_dispatch 트리거 permissions: id-token: write contents: read actions: read issues: write # 여기만 맞췄다 uses: ./.github/workflows/_apply-env.yml

이 상태에서는 dev-auto 가 제공하는 권한보다 재사용 워크플로가 요구하는 권한이 더 커요. 워크플로 파일 전체가 무효로 처리되면서 권한을 맞게 선언한 dispatch 잡도 생성되지 않았고, 수동 반영도 할 수 없었어요.

이 변경은 리뷰 승인을 받은 뒤 추가한 커밋에 들어 있었어요. 블로그 글을 쓰다가 발견한 결함 두 개를 같은 PR 에 추가하면서, 승인 후 변경분을 다시 검토받지 않은 채 머지했어요. 기존 PR 체크에서도 이 권한 불일치를 확인하지 못했어요.

그림 1. dev-auto 의 권한 누락으로 같은 파일의 dispatch 도 실행되지 않았어요

3. PR 체크에는 워크플로 권한 검사가 없었어요

두 YAML 파일을 비교하면 요구 권한과 제공 권한의 차이를 확인할 수 있었어요. 그런데 당시 PR 체크 네 개에는 이 비교가 없었어요.

fmt / validate / tflint 와 checkov 는 Terraform 코드를 검사해요. plan (dev) 와 plan (prod) 는 AWS 에 연결해 변경 계획을 만들어요. 네 체크는 .tf 파일을 대상으로 했고, .github/workflows/ 아래 파일의 권한 관계를 검사하지 않았어요.

이번 권한 오류는 GitHub 이 해당 워크플로의 실행을 만들려는 시점에 드러났어요. 이벤트를 받아 워크플로 파일을 읽고 잡 그래프와 권한 관계를 검증하는 단계였어요. 다른 워크플로의 PR 체크가 통과했다는 결과만으로는 이 파일의 검증 여부를 알 수 없었어요.

Terraform Apply 워크플로의 트리거는 push 와 workflow_dispatch 두 개였어요. 따라서 pull_request 이벤트에서는 이 파일이 실행되지 않았고, 기존 PR 체크에는 별도 권한 검사도 없었어요. 머지 전 PR 에서는 이 오류를 확인하지 못한 상태였어요.

당시 PR 체크가 통과했다는 것은 Terraform 코드 검사와 변경 계획 생성이 성공했다는 뜻이었어요. 제가 바꾼 Apply 워크플로의 권한 관계까지 검증한 결과는 아니었는데, 그 범위를 확인하지 않고 머지했어요.

그림 2. PR 체크 네 개에는 Apply 워크플로의 권한 검증이 없었어요

4. PR 단계에서 권한 선언을 비교해요

직접적인 수정은 dev-auto 에 issues: write 를 추가하는 한 줄이었어요. 다만 호출부가 여러 곳에 있는 구조에서는 같은 누락이 다시 생길 수 있어서, 요구 권한과 제공 권한을 비교하는 검사도 추가했어요.

스크립트는 워크플로 파일을 읽어 로컬 재사용 워크플로를 호출하는 잡을 찾아요. 호출된 파일이 요구하는 각 scope 를 호출 잡의 권한과 none < read < write 순서로 비교해요.

RANK = {"none": 0, "read": 1, "write": 2} for caller_path in sorted(WF_DIR.glob("*.yml")): for job_name, job in (load(caller_path).get("jobs") or {}).items(): uses = str(job.get("uses", "")) if not uses.startswith("./.github/workflows/"): continue # 로컬 호출만 본다 # lstrip("./") 은 문자 집합을 지우므로 쓰면 안 된다. # "./.github/..." 가 "github/..." 로 뭉개진다. called = Path(uses.removeprefix("./")) required = load(called).get("permissions") or {} granted = job.get("permissions") or {} for scope, need in required.items(): have = granted.get(scope, "none") # 선언이 없으면 none 이다 if RANK[str(have)] < RANK[str(need)]: problems.append( f"{caller_path} 의 `{job_name}` 잡이 " f"`{scope}: {need}` 를 주지 않습니다 (현재: {have})" )

위 코드는 권한을 비교하는 핵심 부분만 발췌했어요. 실제 스크립트에는 비교 전에 권한 선언의 타입을 확인하는 코드가 따로 있어요. 그 부분이 스칼라 선언을 제외하므로, 이 발췌만 그대로 실행하면 아래에서 설명하는 제외 동작이 완성되는 것은 아닙니다.

이 검사는 pull_request 에서 실행되는 static 잡에 넣었어요. 기존 fmt / validate / tflint 와 같은 잡이에요. 로컬 파일의 권한 선언을 비교하므로 AWS 자격증명이나 OIDC 토큰 없이 PR 단계에서 실행할 수 있어요.

호출부에서 권한을 하나 지운 뒤 검사기를 실행해 오류를 잡는지도 확인했어요. 정상 설정이 통과하는 것과 누락된 설정이 실패하는 것을 확인한 뒤 커밋했어요.

⚠️ 이 검사가 못 보는 것 두 가지
• 스칼라 권한 선언: permissions: write-all 이나 read-all 처럼 딕셔너리가 아닌 형태로 쓰면 비교 대상에서 제외해요.
• 원격 재사용 워크플로: org/repo/.github/workflows/x.yml@ref 형태는 파일이 로컬에 없어서 이 스크립트로 요구 권한을 읽을 수 없어요. ./ 로 시작하는 호출만 검사해요.

당시 저장소에는 두 형태가 없어서 검사 범위에 포함하지 않았어요. 이후 도입한다면 이 검사만으로 권한 관계를 확인할 수 없으므로 검사 범위도 함께 바꿔야 해요.

5. PR 에서 실행되지 않는 경로도 확인해요

이번 수정에서 추가한 것은 issues: write 한 줄과 PR 단계의 권한 검사예요. 같은 문제가 생길 수 있는 다른 실행 경로도 확인할 필요가 있었어요.

월간 크론 잡, 릴리스 태그를 붙일 때만 실행되는 배포 파이프라인, 재해복구 스크립트도 PR 에서 실행되지 않을 수 있어요. 이런 경로는 평소 PR 체크와 별개로, 실행 전에 확인할 수 있는 설정과 의존성이 무엇인지 살펴봐야 해요.

PR 에서 실행되지 않는 파일을 먼저 확인하고, 그중 정적으로 검사할 수 있는 항목을 PR 체크에 추가하는 방식이에요. 이번에는 인프라를 실제로 변경하지 않고도 두 파일의 권한 선언을 비교할 수 있었어요.

체크 개수와 변경 파일의 검사 범위도 함께 봐야 해요. 이번 네 체크는 .tf 파일을 대상으로 했고 제가 수정한 것은 .yml 파일이었어요. 워크플로 권한 관계에 대한 기존 검사 커버리지는 0% 였어요.

머지 전에는 변경한 파일을 어느 체크가 검사하는지 확인해야 해요. 승인 후 커밋을 추가했다면 그 변경분도 검토 대상에 포함됐는지 함께 확인하고요. 이번에는 두 확인이 모두 빠져 있었어요.

💡 머지 전에 확인할 항목
• 변경한 파일 종류가 PR 체크의 검사 대상에 포함돼 있는지 확인해요.
• 여러 곳에서 선언한 설정은 서로 일치하는지 검사해요.
• 승인 후 추가한 커밋의 변경분도 다시 검토했는지 확인해요.
✍️ 수정 내용과 확인 범위
재사용 워크플로의 permissions 가 호출 잡의 권한을 초과해 Apply 워크플로 파일 전체가 무효로 처리됐어요. dev-auto 에 빠진 권한을 추가했고, 같은 파일의 dispatch 도 실행되지 않았던 원인을 확인했어요.

기존 PR 체크 네 개는 Apply 워크플로의 권한 관계를 검사하지 않았어요. 로컬 재사용 워크플로의 권한 선언을 비교하는 검사를 PR 단계에 추가하고, 호출부 권한을 하나 뺐을 때 실패하는 것까지 확인했어요. 스칼라 권한 선언과 원격 재사용 워크플로는 이 검사의 범위에 포함하지 않았어요.
