9편. 쿼리를 고친 P1의 음소거가 plan에 나타나지 않은 이유 ← 지금 이 글

10월 1일 오후, 마일스톤 M2 를 확인하고 있었어요. M2 의 기준은 "콘솔에만 있는 Datadog 운영 설정 0"이었어요. 모니터 90개, 파이프라인, 아카이브, 인덱스, AWS 연동을 차례로 실물과 맞춰 보니 전부 코드에 있었어요. 남은 것은 두 줄이었습니다. 일부러 남긴 대시보드 7개, 그리고 일회성 다운타임 1개.

일회성 다운타임은 코드 밖에 두기로 한 대상이에요. 바로 전날 ADR(설계 결정과 이유를 적는 문서)로 다시 확인한 결정이기도 합니다. 그래서 그 한 줄은 "결정대로 남긴 예외"로 읽혔어요. 그런데 대상을 확인해 보니 그 다운타임이 음소거하고 있던 것은 배치 서버의 배치 Job 실패 P1 이었습니다. 9월 23일부터 종료 시각 없이 걸려 있었어요.

전날 쿼리를 고친 모니터인데 알림은 여전히 꺼져 있었어요. 음소거는 코드 리뷰와 plan, 매일 도는 drift 검사에서 확인할 수 없는 설정이었습니다. 왜 약 9일 동안 해제되지 않았는지 앞선 작업 기록을 확인했어요.

이 글에서 다룰 것
· P1 모니터가 왜 재시작할 때마다 울렸을까?
· "지우지 말고 다시 켠다"고 적어 둔 모니터는 왜 다시 켜지지 않았을까?
· 일회성 다운타임을 코드 밖에 둔 결정은 무엇을 보이지 않게 했을까?
· 코드 밖에 일부러 둔 것은 누가, 어떻게 확인해야 할까?

1. 재시작할 때마다 울리는 P1

배치 서버는 정해진 시각에 Job 을 돌리는 서버예요. 이 서버의 Job 이 실패하면 온콜(그 시간 장애 대응을 맡은 당번)을 부르는 P1 모니터가 하나 있었습니다. 지표가 아니라 로그를 보는 모니터였어요.

📖 용어: 로그 모니터 (log alert)
Datadog 에 들어온 로그 중 검색 조건에 맞는 줄을 일정 시간 동안 세어서, 그 수가 임계를 넘으면 알리는 모니터예요. 이 글의 모니터는 "최근 5분 동안 맞는 로그가 1줄이라도 있으면" 경보를 냅니다.
name = "[P1] {배치 서비스} Job 실패" query = logs("service:{배치 서비스} (status:error OR \"실행 실패\" OR \"status=FAILED\")") .rollup("count").last("5m") > 0

→ 배치 서비스 로그 가운데 상태가 error 이거나, "실행 실패" 또는 "status=FAILED" 라는 문구가 들어간 줄이 5분 안에 한 줄이라도 있으면 P1 을 울린다는 뜻이에요.

📖 용어: 로그 status
Datadog 이 로그 한 줄마다 붙이는 심각도 속성이에요(info, warn, error 등). 앱이 로그에 레벨을 적어 보내면 그 값을 쓰고, 적지 않은 줄은 수집 경로에 따라 정해집니다. 컨테이너의 표준 에러 출력(stderr)으로 나간 줄은 error 로 분류될 수 있어요.

문제는 status:error 쪽에 있었어요. 컨테이너가 뜰 때 stderr 로 두 줄이 나갑니다. 하나는 Datadog 트레이서가 자기 설정을 출력하는 줄이고, 하나는 JVM 이 내는 경고였어요. 둘 다 오류가 아닌데 stderr 로 나갔기 때문에 error 로 분류됐고, 배치 서버를 재시작할 때마다 이 P1 이 울렸습니다. 이 현상은 9월 28일 18시 7분 compose(여러 컨테이너를 한 번에 띄우는 도구) 재기동 때도 그대로 재현됐어요.

이 모니터는 실제 Job 실패와 컨테이너 재시작을 구분하지 못하고 있었어요. 오탐을 줄이려고 음소거했다면, 쿼리를 고치는 작업과 알림을 다시 켜는 작업을 함께 확인해야 했습니다.

2. 9월 23일, 종료 시각 없는 음소거

9월 23일에 누군가 이 모니터를 음소거했어요. 종료 시각을 정하지 않았고, 사유도 남기지 않았습니다. Datadog 에서 모니터를 음소거하면 그 모니터를 대상으로 하는 일회성 다운타임이 하나 만들어져요.

📖 용어: 일회성 다운타임 (음소거)
정해진 기간 동안 특정 모니터의 알림을 멈추는 Datadog 설정이에요. 콘솔에서 "Mute" 를 누르면 만들어지고, 종료 시각을 비워 두면 누가 취소할 때까지 계속 유지됩니다. 매일 같은 시각에 되풀이되는 반복 다운타임과는 다른 설정이에요.

음소거는 모니터의 평가를 멈추지 않아요. 모니터는 계속 로그를 세고 상태도 바뀝니다. 멈추는 것은 알림뿐이에요. 그래서 9월 29일 배치 서버를 다시 배포한 뒤 관련 모니터 6개를 확인했을 때도, 이 모니터는 다른 모니터와 함께 OK 로 보였습니다. 그날 남긴 확인 기록에도 음소거 이야기는 없었어요.

9월 23일부터는 배치 Job 이 실패해도 이 P1 을 통한 호출을 받을 수 없는 상태였어요. 그 기간에 배치가 실제로 실패했는지는 참고한 기록에 남아 있지 않습니다. 확인한 것은 배치 실패 여부가 아니라 이 P1 의 알림이 꺼져 있었다는 점이에요.

3. "지우지 말고 다시 켠다"고 적었다

9월 28일, 코드 편입을 시작하면서 모니터 68개를 읽기 전용으로 전수 점검했어요. 개발팀 회신을 기다리지 않고 플랫폼팀이 직접 판정한 표였습니다. 이 모니터는 그 표의 "삭제 후보" 칸에 들어 있었어요.

삭제 후보 (약 20) - 바로 삭제: ... 대행 v2 (9개월 음소거) ... - 9/22 P1 계열로 대체된 구 인증 모니터 15종 - ⚠️ 배치 Job 실패 P1 - 9/23 사유 없이 음소거. 지우지 말고 조건을 좁혀 다시 켠다

→ 오래 음소거된 모니터들을 삭제 후보로 모았지만, 이 모니터는 여전히 감시가 필요하니 지우지 말고 고쳐서 다시 켜라는 메모예요.

점검표에서 음소거된 모니터는 대개 더 이상 쓰지 않는 것으로 분류됐어요. 9개월 동안 음소거된 모니터가 바로 삭제 목록에 있었던 것도 그래서입니다. 다음 날(9월 29일) 중복되거나 고장 난 모니터 26개를 지웠고, 당시 음소거용 다운타임 20건 중 19건이 그 모니터들과 함께 사라졌어요. 기록을 맞춰 보면 남은 1건이 이 배치 P1 의 음소거였습니다. 지우지 않기로 한 모니터라서, 음소거도 함께 남은 거예요.

같은 날 서비스별 점검(모니터 89개, 7일 발화 이력)에서 1절의 원인을 찾았고, 9월 30일 오전에 쿼리를 고쳤어요(#772).

# 전 (status:error OR "실행 실패" OR "status=FAILED") # 후 ((status:error -"DATADOG TRACER CONFIGURATION" -"OpenJDK 64-Bit Server VM warning") OR "실행 실패" OR "status=FAILED")

→ 기동 때 나오는 두 줄을 status:error 쪽에서만 빼고, "실행 실패"와 "status=FAILED" 문구는 그대로 잡는다는 뜻이에요.

두 문구를 status:error 쪽에서만 뺀 점이 중요해요. 검색 전체에서 뺐다면 "실행 실패"가 적힌 줄에 그 문구가 함께 들어간 경우까지 제외할 수 있어요. 실제 실패를 나타내는 문구는 계속 탐지하도록 제외 범위를 좁혔습니다.

그리고 커밋 메시지의 이 항목 끝에 이렇게 적었어요. "적용 후 콘솔에서 음소거를 푼다(다운타임은 코드 밖, ADR-0054)." 같은 날 작업 기록에도 "콘솔 음소거 해제 필요"라고 남겼습니다. 후속 작업은 커밋 메시지와 작업 기록에 남겼지만, 해제 여부를 다시 확인하는 절차로 연결되지는 않았어요. 쿼리는 고쳐졌지만 알림은 그 뒤로 이틀 더 꺼져 있었습니다.

그림 1. 음소거부터 해제까지. 쿼리를 고친 날과 알림이 돌아온 날이 달랐다

4. 코드 밖에 둔 음소거는 plan에 나타나지 않았다

4편에서는 다운타임의 관리 범위를 정했어요. 매일 되풀이되는 알림 억제 시간(반복 다운타임)은 모니터의 알림 조건이니 코드로 옮기고(ADR-0057), 일회성 다운타임은 계속 코드 밖에 둔다(ADR-0054). 이유도 분명했어요. 종료 시각이 있는 다운타임을 코드가 들고 있으면, 끝난 뒤 매일 drift 로 뜨고 누가 apply 를 다시 돌리면 끝난 음소거가 되살아납니다.

📖 용어: state 와 plan
state 는 Terraform 이 "내가 관리하는 자원"과 실물 ID 를 적어 둔 파일이에요. plan 은 코드와 state, 실물을 비교해 반영하면 무엇이 바뀌는지 보여 주는 명령입니다. 코드에 새로 정의한 자원도 생성 대상으로 계획하지만, 코드와 state 밖의 자원을 모두 찾아내지는 않아요.
📖 용어: drift 검사
코드와 실물이 어긋났는지 정기적으로 확인하는 작업이에요. 이 저장소에서는 매일 오전 9시에 모든 스택의 plan 을 돌려, 차이가 있으면 이슈를 올립니다. 이 잡은 코드와 state에 정의된 관리 대상을 확인하며, 그 밖에서 콘솔로 만든 자원을 자동으로 발견하지는 않아요.

일회성 다운타임을 코드 밖에 두는 이유는 있었어요. 다만 그렇게 제외한 설정을 어떻게 확인할지는 구현하지 않았습니다. 모니터는 코드에 있었어요. 모니터 리소스는 음소거 관련 필드를 소유하지 않도록 정했고(ADR-0054), 음소거는 모니터와 별개인 다운타임 객체로 존재합니다. 그래서 9월 30일 #772 에서 이 모니터의 변경은 쿼리 한 줄이었고, plan 의 비교 대상에는 음소거가 없었어요. 리뷰어가 본 코드에는 이름에 [P1] 이 붙고 메시지에 @oncall-{온콜 팀} 이 적힌 P1 모니터만 있었습니다.

그림 2. plan은 모니터 변경을 보여 줬지만, 음소거용 다운타임은 비교 대상이 아니었어요

9월 30일에 관리 범위를 다시 정할 때는 일회성 다운타임을 코드 밖에 두어도 괜찮다고 판단했어요. 일회성이니 언젠가 끝나고, 끝나면 사라진다고 생각했습니다. 그 전제는 종료 시각이 있는 다운타임에만 맞았어요. 종료 시각이 없는 일회성 다운타임은 끝나지 않으니, 실제로는 기한 없는 설정이었습니다. 이 설정으로 P1 의 알림이 계속 멈춰 있었어요.

⚠️ 주의: 같은 날 코드 안에 있던 일회성 다운타임은 제때 사라졌다
9월 30일에는 일회성 다운타임이 하나 더 있었어요. 전환 작업용 P3 모니터에 건 것으로, "코드 밖" 규칙을 어기고 코드로 만들어졌어요. 그 탓에 한 스택의 plan 과 drift 가 403 으로 멈췄고, ADR-0057 이 뒤늦게 이것을 예외로 적으면서 끝나는 시각(10월 1일 새벽 3시)과 "끝나면 코드에서 지운다"는 후속 작업을 같이 남겼어요. 이 다운타임은 종료 시각이 있어서 새벽 3시에 스스로 끝났고, 코드에 남은 정의는 그날 아침 PR 로 지웠어요(#813). 배치 P1 의 음소거에는 종료 시각도, ADR 에 적힌 후속 작업도 없었어요.

5. M2 실물 대조에서 해제되지 않은 음소거를 확인했다

📖 용어: 마일스톤 M2
이 프로젝트에서 정한 중간 목표 중 두 번째예요. "콘솔에만 있는 Datadog 운영 설정 0" 이 기준이고, 처음 계획은 10월 23일이었는데 10월 1일에 확인했습니다.

음소거는 9월 28일 점검표에도, 9월 30일 커밋에도 적혀 있었지만 해제는 빠져 있었어요. 10월 1일 M2 를 확인하려고 실물 전체를 코드와 맞춰 보면서 이 상태를 다시 확인했습니다. 그때 남긴 기록은 이래요.

M2 실물 대조 (10-01) 모니터 90/90 코드 커스텀 파이프라인 2 코드 아카이브 7 코드 스팬 지표 1 코드 (대조 중 발견) 인덱스 · AWS 연동 코드 남은 것 대시보드 7 빈 것 · 샘플 · 복제, 일부러 남김 일회성 다운타임 1 ADR-0057 로 코드 밖

→ 코드 밖에 남은 것은 두 종류였고, 둘 다 "일부러 남긴 것"으로 분류돼 있었다는 뜻이에요.

이 대조가 음소거를 찾을 수 있었던 이유는 기준이 "state 에 있는가"가 아니라 "실물에 있는 것 중 코드에 없는 것은 무엇인가"였기 때문이에요. plan 과 drift 는 코드와 state 에 정의한 자원을 실물과 비교해요. 이번 대조에서는 실물 목록을 먼저 가져왔기 때문에 코드 밖에 있는 다운타임도 확인할 수 있었습니다.

다만 대조 기록의 그 줄은 "ADR-0057 로 코드 밖"이라고만 적혀 있어요. 결정대로 남긴 예외로 읽히는 문구입니다. 그 다운타임이 배치 실패 P1 을 끄고 있다는 사실은 그 아래 하위 항목에 따로 적혔어요. 실제로 M2 는 그날 이 줄을 남긴 채 "달성"으로 적혔어요. "코드 밖"이라는 분류와 별개로, 어떤 모니터를 음소거하는지도 확인해야 하는 항목이었어요.

10월 2일, 다운타임을 취소해 음소거를 풀었어요. 모니터가 OK 상태일 때 풀었기 때문에 해제와 함께 나가는 알림은 없었습니다. 9월 23일부터 10월 2일까지 약 9일 동안 꺼져 있던 배치 실패 P1 이 그날부터 다시 온콜을 부를 수 있게 됐어요. M2 의 "코드 밖 설정" 목록에서 일회성 다운타임은 0 이 됐습니다.

6. 다운타임을 따로 보고한다는 결정은 구현되지 않았다

ADR-0054 를 다시 읽어 보니, 다운타임을 코드 밖에 두기로 한 결정 바로 아래에 이런 줄이 있었어요.

### 6. 다운타임 - 코드 밖, 감사는 한다 - 다운타임·음소거는 코드로 관리하지 않는다. - 종료 시점이 없는 다운타임을 주기적으로 보고한다. 음소거 19개가 해제 시점 없이 쌓인 것이 이 공백의 결과다

→ 코드 밖에 두는 대신, 종료 시점이 없는 다운타임은 따로 찾아서 보고하겠다고 결정해 두었다는 뜻이에요.

다운타임을 코드에서 제외하는 것과 별도로 감사하는 것이 함께 결정돼 있었어요. 하지만 10월 2일까지 저장소에서 다운타임을 보고하는 스크립트나 워크플로는 찾을 수 없었습니다. 코드로 관리하지 않는 설정을 정기적으로 확인하는 작업은 구현되지 않은 상태였어요.

이 글을 쓰는 10월 3일 기준으로 새로 추가한 검사나 규칙은 아직 없어요. 이번에는 음소거 하나를 수동으로 해제했어요. 같은 상태를 정기적으로 확인하는 작업은 남아 있었고, 다음과 같은 검사를 생각했습니다.

💡 실무에서는: 코드 밖에 둔 다운타임을 확인하는 최소한의 장치 (아직 만들지 않음)
• 매일 drift 검사 옆에서 Datadog API 로 활성 다운타임을 전부 조회한다. state 를 거치지 않고 실물에서 출발한다
• 종료 시각이 없는 일회성 다운타임은 무조건 보고한다. 대상 모니터가 P1 이면 이슈의 우선순위도 올린다
• 음소거를 걸 때 사유와 종료 시각을 적게 한다. 사유 없는 음소거는 보고서에서 따로 표시한다
• 쿼리를 고친 PR 에 "음소거를 푼다"는 후속 작업이 있으면, 커밋 메시지가 아니라 추적되는 이슈로 남긴다

돌아보면 ADR-0054 에는 같은 구조의 결정이 하나 더 있어요. 콘솔에서 새로 만든 모니터는 state 밖이라 drift 가 보지 못하니, 계정 인벤토리 잡에 Datadog 모니터 수집기를 더해 state 밖 모니터를 매일 센다는 결정입니다. 코드 밖 자원은 인벤토리에서 확인하겠다는 취지예요. 다만 10월 2일 기준 저장소의 인벤토리 잡에도 그 수집기는 아직 없어요. M2 의 실물 대조에서는 이를 수동으로 한 번 확인했지만, 두 결정에 필요한 정기 수집은 아직 구현되지 않았어요.

⚠️ 주의: 예외 목록에도 대상과 종료 시각을 적어야 해요
M2 대조 목록에서 대시보드 7개와 다운타임 1개는 둘 다 "일부러 남김"으로 분류됐어요. 두 종류는 운영에 미치는 영향이 달랐어요. 예외 목록을 만들 때는 각 항목이 무엇을 대상으로 하는지와 언제 끝나는지를 함께 적어야 해요. P1 을 종료 시각 없이 음소거하는 항목이라면, 알림을 다시 켤 후속 작업도 확인해야 합니다.
✍️ 오늘의 요약
배치 서버의 Job 실패 P1 은 기동 로그를 오류로 분류해 재시작마다 울렸고, 9월 23일 종료 시각과 사유 없이 음소거됐어요. 9월 28일 점검표에 재활성화를 적고 9월 30일 쿼리도 고쳤지만, 코드 밖의 다운타임은 plan과 drift 검사에 나타나지 않았습니다.

10월 1일 M2 실물 대조에서 남아 있던 음소거를 확인해 10월 2일 해제했어요. ADR-0054 에 적힌 종료 시점 없는 다운타임 보고는 10월 3일 작성 시점에도 구현되지 않아, 정기 확인은 후속 작업으로 남았습니다.
