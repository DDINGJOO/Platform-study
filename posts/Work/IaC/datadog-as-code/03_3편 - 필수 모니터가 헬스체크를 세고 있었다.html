9월 28일 오후 4시 18분, #{인프라 채널} 에 P2 알림이 하나 떴어요. "배치 서버 응답 지연". 그날 낮에 새로 만든 필수 모니터 가운데 하나였습니다. 그런데 배치 서버에는 느려진 곳이 없었어요. 느린 요청은 2주 내내 같은 속도로 느렸고, 그날 특별히 달라진 것은 없었습니다.

원인을 따라가 보니 이 모니터가 "요청이 충분히 들어오는가"를 판단할 때 센 요청의 70%가 헬스체크와 OPTIONS 요청이었어요. 이틀 뒤에는 CPU 모니터가 앱 컨테이너가 아니라 옆에 붙은 Datadog 에이전트 컨테이너를 재고 있었다는 것도 알게 됐습니다. 두 쿼리 모두 문법은 맞았고, Datadog 의 validate 도 통과했어요.

이 글은 서비스마다 똑같이 붙는 필수 모니터 세트를 만들고, 만든 직후 드러난 결함을 고친 기록이에요. 질문은 하나입니다. "모니터가 재는 값이 정말 재고 싶었던 값인지, 무엇으로 확인하는가."

이 글에서 다룰 것
· 서비스마다 모니터가 다르면 무엇이 곤란할까?
· 새벽에 요청 세 건 중 한 건이 실패하면 에러율 모니터는 울려야 할까?
· 요청 수를 셀 때 헬스체크를 빼면 무엇이 달라질까?
· 컨테이너를 태그로 골랐는데 엉뚱한 컨테이너가 잡힌 이유는 무엇일까?
· 알림을 받은 사람이 메시지만 보고 움직이려면 무엇이 적혀 있어야 할까?

1. 서비스마다 모니터가 들쭉날쭉했다

9월 28일, 콘솔에 있던 모니터를 코드로 옮기면서(1편) 스택별로 개수를 세어 봤어요. 메인 API 스택으로 옮긴 모니터가 45개였고, 에이전트 API 는 9개, 배치 서버는 파일럿 4개에 1개를 더해 5개였습니다. 문서 팩스 서비스와 메시지 발송 서비스 스택에는 Datadog provider 설정이 아예 없었어요. 코드로 관리하는 Datadog 모니터가 그 두 스택에는 없었다는 뜻입니다.

개수보다 곤란한 건 무엇을 재는지가 서비스마다 달랐다는 점이에요. 예를 들어 메인 API 와 에이전트 API 에는 이름에 "ERROR%"가 붙은 옛 모니터가 있었는데, 이 모니터는 서비스가 받은 요청이 아니라 서비스가 밖으로 보낸 호출(trace.http)을 1분 창으로 보고 있었어요. 90일 동안 1,686번 울렸습니다. 이 모니터는 다음 날 정리 작업에서 지웠어요. 서비스 하나가 죽었을 때 "무엇이 울리는가"라는 질문에 서비스마다 답이 달랐고, 어떤 서비스는 답이 없었습니다.

그래서 모든 서비스가 같은 질문 네 개에 답하게 하기로 했어요. 요청이 들어오는가, 실패하는가, 느린가, 자원이 차 가는가. 이 네 가지를 흔히 골든 시그널이라고 부릅니다.

📖 용어: 골든 시그널 (golden signals)
Google SRE 책이 "사용자에게 닿는 서비스라면 최소한 이것은 보라"고 꼽은 네 가지 신호예요. 지연(latency), 트래픽(traffic), 에러(errors), 포화(saturation)입니다. 이 글의 필수 모니터는 이 네 칸을 서비스마다 채우는 것을 목표로 했어요.

2. 모듈 하나를 아홉 번 부른다

같은 모니터 세트를 서비스마다 손으로 복사하면, 한 서비스에서 고친 것이 다른 서비스에는 반영되지 않아요. 1절의 들쭉날쭉함이 코드 안에서 다시 생기는 거예요. 그래서 모니터 세트를 Terraform 모듈로 만들었습니다(#688).

📖 용어: 모듈 (Terraform module)
여러 리소스 정의를 한 폴더에 묶고, 서비스 이름이나 임계값을 변수로 받게 만든 것이에요. 쓰는 쪽은 module 블록 하나로 부르면서 변수만 바꿉니다. 모듈 안의 쿼리를 한 번 고치면 그 모듈을 부르는 모든 서비스에 같이 반영돼요.

모듈 dd-service-baseline 이 만드는 모니터는 이렇습니다.

트래픽 서비스 다운 10분 요청 0 + 데이터 없음도 알림 P1 · 온콜 호출 에러 에러율 서비스가 받은 요청 기준 P2 · #{인프라 채널} 지연 p95 서비스별 임계 P2 포화 메모리 컨테이너 또는 호스트, 15분 평균 P2 (배치) 실행 침묵 정해진 시간 동안 실행 흔적 없음 P2

→ 골든 시그널 네 칸에 모니터를 하나씩 두고, 요청을 받지 않는 배치에는 "돌았는가"만 보는 모니터를 따로 둔다는 뜻이에요.

이 모듈을 메인 API, 에이전트 API, 배치 서버, 문서 팩스 서비스, 메시지 발송 서비스, 제휴 서비스와 그 중계 서버에 붙였어요. 커밋 제목은 "7개 서비스"라고 적었고, 코드에서는 모듈을 아홉 번 부릅니다. 배치 서버에 딸린 배치 작업과 에이전트 API 에 딸린 배치 작업을 따로 한 번씩 부르기 때문이에요. 이 커밋의 모듈 호출을 세면 모니터가 43개 나오고, 그중 2개는 제휴 서비스에 있던 모니터를 모듈 안으로 옮긴 것이라 새로 생긴 모니터는 41개였어요. 3절에서 설명할 알림 없는 하위 모니터까지 센 숫자입니다. 이미 다운 모니터가 있던 세 서비스에는 다운을 만들지 않았어요. 같은 장애에 온콜 전화가 두 번 오기 때문입니다.

임계는 7일 실측으로 정했습니다. p95(응답 100건을 빠른 순으로 세웠을 때 95번째 응답시간)의 정상 범위가 서비스마다 100배 넘게 달랐기 때문이에요. 문서 팩스 서비스와 메시지 발송 서비스는 500ms, 에이전트 API 는 1.5초, 메인 API 와 배치 서버는 3초로 잡았어요. 제휴 서비스는 평소 p95 중앙값이 2.96초라서 15초로 잡았는데, 이 값은 느린 상태를 정상으로 인정한 값이라고 코드 주석에 적어 뒀습니다.

💡 실무에서는: 넣지 않은 이유도 코드에 적는다
실측을 해 보면 넣으려던 신호가 쓸모없다는 것도 드러나요. JVM 힙은 에이전트 API 가 평소 99%까지 차서(GC 가 정상적으로 도는 상태) 경보로 쓸 수 없어 뺐습니다. 배치 서버의 호스트 메모리는 평소 90%대 초반이라서 임계를 97%로 두고, 여유가 거의 없다는 사실 자체를 발견 사항으로 남겼어요. 그날 저녁 배치 서버의 힙을 줄인 설정이 반영되자 사용률이 절반 아래로 내려갔고, 다음 날 임계를 90%로 되돌렸습니다(#729). 컨테이너 CPU 는 사용량과 한도의 단위가 맞지 않아 그날 측정을 무효로 보고 보류했습니다. 뺀 이유를 적어 두지 않으면 다음 사람이 같은 신호를 다시 넣고 같은 소음을 겪게 돼요.

3. 새벽의 요청 세 건 중 한 건이 실패하면

에러율 모니터를 그대로 두면 곤란한 시간대가 있어요. 새벽 3시에 10분 동안 요청이 3건 들어왔고 그중 1건이 실패했다고 해 볼게요. 에러율은 33%입니다. 임계 5%를 한참 넘지만, 이걸로 사람을 깨울 일은 아니에요. 요청이 적을 때는 한두 건 실패만으로 비율이 크게 튑니다.

그래서 에러율과 지연은 요청이 충분할 때만 판정하게 했어요. 10분 요청이 20건 미만이면 판정하지 않습니다. 이 조건을 저트래픽 가드라고 불렀고, 복합 모니터로 구현했어요.

📖 용어: 복합 모니터 (composite monitor)
다른 모니터 여러 개의 상태를 &&, ||, ! 로 엮어서 판정하는 Datadog 모니터예요. 재료가 되는 모니터는 알림을 보내지 않게 두고, 복합 모니터만 알림을 보내게 할 수 있습니다.

여기서 논리를 한 번 뒤집어야 했어요. 처음 떠오르는 방식은 "요청 20건 이상"을 조건 모니터로 만드는 것이에요. 그런데 그렇게 만들면 이 조건 모니터는 평소에 늘 경보 상태가 됩니다. 요청이 많은 게 정상인데 모니터 화면에는 빨간 불이 켜져 있게 돼요. 그래서 "요청 20건 미만"을 조건으로 만들고, 복합 모니터에서 그 조건이 아닐 때만 판정하게 했습니다.

그림 1. 저트래픽 조건은 평소 OK 이고, 요청이 적을 때 켜져 에러율·지연 판정을 막는다

그럼 서비스가 통째로 죽으면 어떻게 될까요. 요청이 0건이라는 값이 찍히는 게 아니라, 요청 수 시계열 자체가 끊깁니다. 이때 B 는 데이터 없음 상태가 되고, 모듈은 이때를 저트래픽으로 보고 판정을 막도록 두었어요. 모듈 코드에서 B 는 on_missing_data = "show_no_data" 로 두고, "신호가 없으면 다운 모니터가 본다"고 주석을 달았습니다. 에러율은 분모인 요청 수가, 지연은 재료가 되는 요청이 사라져서 판정할 값이 없어요(지연 조건은 데이터가 없으면 OK 로 돌아가게 뒀습니다). 그래서 두 복합 모니터는 울리지 않고, 신호가 끊긴 것은 데이터 없음에도 알리게 설정한 다운 모니터가 받습니다. 가드는 요청이 적을 때 튀는 비율을 막고, 죽은 서비스의 호출은 다운 모니터가 합니다.

📖 용어: 데이터 없음 (No Data)
모니터가 판정할 값 자체를 받지 못한 상태예요. 경보(Alert)도 정상(OK)도 아닌 별도 상태입니다. 앱이 죽으면 값이 0 으로 찍히는 게 아니라 시계열이 사라지기 때문에, 이 상태를 알릴지 말지는 모니터마다 따로 정해야 해요. 살아 있는 앱에는 헬스체크 요청이 늘 트레이스로 들어오니, 다운 모니터가 이 상태가 되면 앱이 응답하지 않는다는 뜻입니다.

가드는 "언제 판정하지 않을지"를 정하는 장치이고, 그래서 가드가 세는 숫자가 틀리면 판정 전체가 틀립니다. 이 문장이 바로 그날 오후에 확인됐어요.

4. 가드가 헬스체크를 세고 있었다

9월 28일 오후 4시 18분의 배치 서버 지연 알림으로 돌아가 볼게요. 원인은 두 가지였습니다(#719).

첫째는 지연이에요. 배치 서버에는 파일 업로드 엔드포인트가 두 개 있는데, 하나는 p95 가 40~70초, 다른 하나는 5~20초였어요. 2주 내내 이 속도였습니다. 배치 서버는 요청이 적어서, 업로드 한 건만 10분 창에 끼어도 서비스 전체 p95 가 3초를 넘었어요. 업로드는 원래 느린 작업이라 이 두 엔드포인트를 지연 판정에서 뺐습니다.

둘째가 더 중요했어요. 요청이 적은 서비스인데 왜 저트래픽 가드가 판정을 막지 않았을까요. 가드가 헬스체크와 OPTIONS 요청까지 세고 있었기 때문입니다. 배치 서버는 10분 요청의 70%가 이것이었어요. 실제 사용자가 거의 없는 시간에도 가드 기준 20건을 넘겼고, 그래서 판정이 켜졌습니다.

📖 용어: 헬스체크 (health check)
로드밸런서나 오케스트레이터가 "이 앱이 살아 있는가"를 확인하려고 몇 초마다 보내는 요청이에요. Spring 앱에서는 보통 /actuator/health 를 부릅니다. 사용자가 없어도 일정하게 들어오기 때문에, 요청 수에 섞이면 사용자가 없는 시간에도 요청이 있는 것으로 세어져요. OPTIONS 는 다른 도메인으로 보내는 일부 요청(사용자 정의 헤더를 붙이거나 PUT 을 쓰는 경우 등) 앞에 브라우저가 보내는 사전 확인 요청(CORS preflight)이에요.

그래서 가드와 에러율(분자와 분모 모두)에서 둘을 뺐어요.

traffic_scope = join(",", [ local.scope, "!resource_name:get_/actuator/health", "!resource_name:head_/actuator/health", "!resource_name:options_*", ])

→ 요청 수를 세는 범위에서 GET·HEAD 헬스체크와 모든 OPTIONS 요청을 뺀다는 뜻이에요. ! 가 붙은 태그는 "이것은 제외"입니다.

어디서 빼고 어디서는 빼지 않을지도 따로 정했어요. 헬스체크를 빼는 곳은 "사용자가 있는가"를 묻는 가드와 에러율뿐입니다. 다운 모니터는 헬스체크를 그대로 셉니다. 헬스체크에 응답한다면 앱은 살아 있는 것이니까요. 지연 p95 에서도 헬스체크를 빼지 않았어요. 빠른 요청을 빼면 p95 가 올라가서, 2절에서 실측으로 정한 임계를 다시 봐야 하기 때문입니다.

⚠️ 주의: 와일드카드 *health* 는 쓰지 않았다
헬스체크를 뺀다고 *health* 로 쓰면 편해 보여요. 그런데 메인 API 에는 경로에 /api/v1/health/ 가 들어가는 업무 API 가 있었습니다. 와일드카드를 쓰면 그 API 의 실제 사용자 요청까지 사라져요. 그래서 7일 동안 실제로 들어온 resource 이름 목록을 확인하고, 정확한 이름으로만 뺐습니다.

고친 뒤의 영향도 7일 실측으로 확인했어요. 배치 서버와 메시지 발송 서비스는 업무 시간에는 가드 기준을 넘지만, 야간과 주말에는 거의 0건이라 그 시간에는 판정하지 않습니다. 의도한 결과예요. 메인 API, 에이전트 API, 제휴 서비스는 늘 가드 기준을 크게 넘어서 영향이 없었습니다. 문서 팩스 서비스는 APM 에 잡힌 요청이 전부 헬스체크여서 에러율과 지연이 아예 판정되지 않게 됐어요. 이 서비스는 그날 로그와 큐 지표로 세운 대체 감시가 따로 봅니다.

5. 받은 사람이 바로 움직이게, 그리고 빠진 두 칸

9월 29일에는 두 가지를 더했어요. 먼저 알림 메시지입니다(#746). 처음 메시지에는 "무엇이 몇인지"만 있었어요. 새벽에 메시지를 받은 사람은 거기서부터 무엇을 볼지 스스로 정해야 했습니다. 그래서 모든 필수 모니터의 메시지를 같은 순서로 다시 썼어요.

⚠️ [P2] {서비스} 에러율 증가 : 10분 에러율이 5% 를 넘었습니다 요청이 10분에 20건 이상일 때만 판정합니다(헬스체크 제외). 먼저 볼 것 1. 어느 엔드포인트에서 나는가 : APM 의 Resources 를 에러 순으로 정렬 2. 에러 로그의 예외 종류 : 한 종류면 코드·외부 연동, 흩어지면 인프라 3. 직전 배포 여부 📈 에러율 그래프(판정 조건) · APM · 에러 로그 링크

→ 무슨 일인가(값·임계·판정 창), 영향, 먼저 볼 것 세 가지, 바로 가기 링크 순서예요. 복구 메시지에는 무엇을 확인해야 하는지도 적었습니다.

작은 함정도 두 개 있었어요. 복합 모니터는 Slack 알림에 그래프가 붙지 않아서, 그래프가 있는 조건 모니터 화면으로 가는 링크를 따로 넣었습니다. 그리고 에러율을 %로 보여 주려고 메시지 안에서 0.05*100 을 그대로 찍었더니 5.00…01(소수점 아래 열다섯째 자리에 1 이 붙은 값)이 나왔어요. Terraform 이 숫자를 계산해 문자열로 바꾸는 과정에서 붙은 끝자리라서, format 으로 출력 형식을 지정해 정수로 찍게 했습니다.

같은 날 오후에는 모듈을 기준표와 대조했어요(#753). 골든 시그널 네 칸, 그리고 USE 세 칸입니다.

📖 용어: USE (Utilization · Saturation · Errors)
서비스가 아니라 CPU, 메모리, 디스크 같은 자원 하나하나를 볼 때 쓰는 점검표예요. 얼마나 쓰고 있는가(사용률), 처리하지 못하고 밀린 일이 있는가(포화), 자원 자체가 오류를 내는가(에러)를 봅니다. 골든 시그널이 사용자 쪽에서 본 증상이라면, USE 는 그 증상의 원인이 될 자원 쪽을 봐요.

대조해 보니 빠진 칸이 둘 있었어요. CPU 포화, 그리고 0건은 아닌데 급격히 줄어든 트래픽입니다. 다운 모니터는 요청이 0건이거나 신호가 끊길 때만 울리므로, 요청이 평소의 10분의 1로 줄어도 울리지 않아요. 그래서 30분 요청이 지난주 같은 시각의 20% 미만이면 울리는 트래픽 급감 모니터를 더했어요. 추석 연휴에도 에이전트 API 는 지난주의 35~40%였으니, 20%는 명절에 울리지 않는 기준입니다. 야간(20시~08시)은 반복 다운타임이 판정을 막아요. 메시지 발송 서비스는 같은 2시간 창에서도 요청이 거의 없는 때와 몰리는 때의 차이가 커서, 지난주 대비 비율을 기준으로 쓸 수 없었어요. 그래서 이 모니터를 켜지 않았습니다.

CPU 포화는 임계 90%(경고 80%)로 잡았어요. ECS 서비스는 컨테이너 한도 대비 비율로, EC2 에서 docker 로 도는 서비스는 호스트 CPU 로 봅니다. docker 에 CPU 한도를 주지 않아서 컨테이너 비율이 87~95%로 나오는데, 같은 때 호스트는 최대 8.6%였기 때문이에요. 문서 팩스 서비스의 호스트 CPU 는 일주일 동안 16%에서 28%로 한 번도 내려가지 않고 올랐는데, 자바 에이전트를 뗀 재배포 뒤 5%로 내려갔습니다. 이 모니터는 그 증상이 다시 생기는지 봐요.

이때 커밋에 적은 7일 최대 CPU 에는 에이전트 API 5%도 있었어요. 임계 90%와 한참 떨어져 있으니 노이즈가 없다고 판단했습니다. 이 숫자가 다음 날 틀린 것으로 드러났어요.

6. 반전: 모니터는 사이드카를 재고 있었다

9월 30일 아침, 모니터 쿼리를 하나씩 실측 데이터와 대조했어요. 모니터가 보고 있는 값과, 같은 대상을 다른 경로로 직접 잰 값을 나란히 놓는 작업입니다. 에이전트 API 의 앱 컨테이너 CPU 는 7일 최대 약 70%였어요. 그런데 모니터가 보고 있던 값은 1% 미만이었습니다(#779).

원인은 컨테이너를 고르는 조건에 있었어요. 모듈은 service:<서비스> 태그로 컨테이너를 골랐는데, 그 태그는 앱 컨테이너가 아니라 같은 태스크에 붙은 Datadog 에이전트 사이드카에만 붙어 있었습니다. 앱 컨테이너에는 service 태그가 없었어요.

📖 용어: 사이드카 (sidecar)
앱 컨테이너와 같은 태스크(또는 파드)에 함께 떠서 로그 수집, 지표 전송 같은 보조 일을 맡는 컨테이너예요. ECS 에서는 Datadog 에이전트를 사이드카로 두는 경우가 많습니다. 같은 호스트에 있으니 호스트 단위 지표는 섞이고, 태그가 어느 컨테이너에 붙는지는 설정에 따라 달라져요.
그림 2. 태그가 붙어 있던 컨테이너는 앱이 아니라 에이전트였다

앱이 CPU 를 다 써도 이 모니터는 울리지 않았을 거예요. 5절의 "에이전트 API 5%"도 결국 앱을 잰 숫자가 아니었습니다. 그래서 고친 것은 다음과 같아요.

· 모듈에 container_scope 변수를 더하고, 기본값에서 Datadog 에이전트와 ECS 에이전트 이미지를 뺐어요.
· 메인 API 와 에이전트 API 는 이미지 이름(short_image)으로 앱 컨테이너를 골랐습니다. 두 앱에는 메모리 하드 한도가 없어서 "한도 대비 비율"을 계산할 수 없었어요. 그래서 컨테이너 메모리 모니터는 지우고, 호스트 메모리를 보는 공용 모니터에 맡겼습니다.
· 에이전트 API 에 딸린 배치 작업(2절에서 따로 부른 배치 둘 중 하나)의 컨테이너는 CPU 2코어, 메모리 3.75GB 한도가 있어서 CPU·메모리 모니터를 새로 붙였어요.
· 제휴 서비스는 앱 컨테이너 이미지로 골랐고, 그 중계 서버의 CPU·메모리 모니터는 지웠습니다. 제휴 서비스와 같은 컨테이너를 중복으로 보고 있었고, nginx 컨테이너까지 섞여 있었어요.

이 방식으로 옛 CPU 모니터 두 개도 다시 봤어요(#786). 필수 모듈이 앱 컨테이너를 제대로 재게 되면서 둘은 중복이 됐는데, 실측으로 보니 둘 다 앱 포화를 잡지 못하고 있었습니다. 메인 API 의 옛 모니터는 사용량과 한도를 호스트 단위 최댓값으로 나눠서 7일 최대 2.8%로 읽혔어요. 같은 기간 앱 컨테이너는 최대 45.8%였습니다. 에이전트 API 의 옛 모니터는 호스트의 모든 컨테이너(앱, Datadog 에이전트, ECS 에이전트)를 평균해서 24시간 최대 9.9%로 읽혔고, 같은 기간 앱은 68.4%였어요. 둘 다 지웠습니다.

옛 모니터에서 쓸 만한 설정이 하나 있었어요. 복구 임계입니다. 이것은 모듈의 CPU·메모리 모니터로 옮겼어요.

📖 용어: 히스테리시스 (복구 임계)
경보가 켜지는 값과 꺼지는 값을 다르게 두는 설정이에요. CPU 가 90%에서 울렸다면 85% 아래로 내려와야 복구로 봅니다. 15분 평균이 임계 부근에서 오르내릴 때 "경보, 복구, 경보, 복구" 알림이 반복되는 것을 막아요. Datadog 에서는 critical_recovery 로 지정합니다.

임계에서 5%p(메모리는 0.05) 아래로 내려와야 복구하게 했는데, 이것도 한 번에 끝나지 않았어요. Terraform 에서 메모리 0.90 - 0.05 가 0.8499… 로 계산돼서 소수 둘째 자리로 맞췄습니다. 그랬더니 이번에는 경고 쪽 복구 임계 "0.80"(경고 0.85 에서 0.05 를 뺀 값)을 Datadog 이 0.8 로 저장해서, plan 을 돌릴 때마다 차이가 났어요. 끝자리 0 을 떼서 해결했습니다.

⚠️ 주의: 저도 여기서 틀렸어요. 태그로 고르면 그 태그가 붙은 것이 잡혀요
service:<서비스> 로 고르면 그 서비스의 컨테이너가 잡힐 거라고 생각했어요. 실제로 잡히는 것은 "그 태그가 붙은 컨테이너"입니다. 앱에 태그가 없고 사이드카에만 있으면 사이드카만 잡혀요. 쿼리 결과에 by {container_name} 을 붙여 어떤 컨테이너가 잡히는지 한 번 펼쳐 보면 바로 드러나는 문제였습니다.

돌아보면 만든 직후의 필수 모니터 두 곳에서 같은 일이 있었어요. 가드는 "사용자가 보낸 요청"을 세고 싶었지만 세기 쉬운 "들어온 요청 전부"를 셌고, CPU 모니터는 "앱의 CPU"를 재고 싶었지만 고르기 쉬운 "service 태그가 붙은 컨테이너"를 쟀습니다. 만든 직후의 모니터는 재고 싶은 것이 아니라 재기 쉬운 것을 재고 있었어요. 문법 검사와 validate 는 이 차이를 잡지 못합니다. 쿼리가 올바른 형식인지만 보기 때문이에요.

💡 실무에서는: 모니터 쿼리를 다른 경로로 잰 값과 나란히 놓는다
9월 30일에 쓴 방식은 단순해요. 모니터 쿼리의 결과를 먼저 그대로 뽑고, 같은 대상을 다른 경로(컨테이너 단위 지표, 이미지 이름, 호스트 원본)로 직접 잰 값과 비교합니다. 둘이 크게 다르면 쿼리가 다른 대상을 보고 있는 거예요. 같은 날 로그 모니터 설계안도 같은 구조의 쿼리를 기존 로그로 먼저 돌려 봤고, 태그 누락과 status 매핑 때문에 절대 울리지 않는 구조라는 것을 배포 전에 찾았습니다.
✍️ 오늘의 요약
서비스마다 들쭉날쭉하던 모니터를 골든 시그널 모듈 하나로 맞췄고, 저트래픽 가드로 요청이 적은 시간대의 오탐을 막았다. 죽은 서비스는 데이터 없음에도 알리는 다운 모니터가 맡는다.

그런데 만든 직후의 모니터는 가드가 헬스체크를 세고 CPU 가 사이드카를 재는, 재기 쉬운 값을 재고 있었다. 이를 잡은 것은 validate 가 아니라 모니터가 보는 값을 다른 경로로 잰 실측과 나란히 놓는 대조였다. 모니터를 만드는 일은 쿼리를 쓰는 데서 끝나지 않고, 그 쿼리가 무엇을 잡는지 확인하는 데서 끝난다.
