10편. 지연 오탐 68건은 느린 게 정상인 요청이 만들었다 ← 지금 이 글

10월 2일 오전, 메인 API 의 지연 모니터를 지난 14일 데이터에 그대로 대 봤어요. 임계는 3편에서 7일 실측으로 정한 3초였습니다. 14일 동안 이 임계를 넘은 횟수는 68번이었어요. 그런데 그 68번 중에 실제로 서비스가 느려진 때는 한 번도 없었습니다. 전부 원래 느린 요청이 평소 속도로 느렸을 뿐이었어요.

3편에서 배치 서버의 업로드 두 개를 지연 판정에서 뺀 적이 있어요. 그때는 서비스 하나의 엔드포인트 두 개였습니다. 메인 API 와 에이전트 API 를 열어 보니 같은 성격의 요청이 훨씬 많았고, 종류도 여러 가지였어요. 사용자가 휴대폰에서 버튼을 누를 때까지 기다리는 인증 요청, 신분증 사진을 분석하는 요청, 5분 동안 연결을 열어 두는 스트림이 서비스 p95 하나에 섞여 있었습니다.

이 글은 그 68번을 0으로 만든 과정과, 서비스 p95 하나로는 보이지 않던 것을 따로 보게 만든 과정이에요. 그리고 열 편째인 만큼 이 시리즈가 지금까지 무엇을 했고 무엇이 남았는지도 짧게 정리합니다.

이 글에서 다룰 것
· 장애가 없었는데 지연 임계를 68번 넘은 이유는 무엇일까?
· 3편에서 "지연 p95 에서는 헬스체크를 빼지 않는다"고 한 판단은 왜 뒤집었을까?
· 서비스 전체 p95 가 멀쩡해도 로그인만 느려질 수 있을까?
· 오래 기다리는 API 는 왜 따로 감시하지 않기로 했을까?
· 조금씩 나빠지는 지연은 무엇으로 잡을까?

1. 68번 넘었는데 전부 정상이었다

서비스 단위 지연 모니터는 그 서비스가 받은 요청 전체의 p95 를 봐요. 요청 100건을 빠른 순으로 세웠을 때 95번째 응답시간입니다. 이 값이 하나의 숫자로 의미가 있으려면 섞인 요청들이 대체로 비슷한 속도여야 해요. 메인 API 는 그렇지 않았습니다.

메인 API 와 에이전트 API 에서 원래 느린 요청을 성격별로 묶으면 이렇게 나뉘었어요.

· 외부 기관이나 사용자를 기다리는 요청: 본인 인증 요청은 사용자가 휴대폰 앱에서 확인을 누를 때까지 응답하지 않아요. 외부 기관의 응답을 받아 넘기는 단계도 그쪽 속도를 따릅니다.
· 안에서 무거운 일을 하는 요청: 신분증·서명 이미지 분석(OCR), 상담 초안 작성, 관리자의 회원 탈퇴 처리가 있었어요.
· 스트리밍: 에이전트 API 의 관리자 문의 화면은 연결을 5분 동안 열어 둡니다.
· 헬스체크와 CORS 사전 요청: 반대로 아주 빠른 요청들이에요.

📖 용어: 스트리밍 응답 (SSE)
서버가 응답을 한 번에 끝내지 않고 연결을 열어 둔 채 데이터를 조금씩 보내는 방식이에요. APM 은 이 연결이 닫힐 때까지를 한 요청으로 재기 때문에, 정상 동작인데도 응답시간이 몇 분으로 찍힙니다.

메인 API 는 10분 창으로 p95 를 봤어요. 10분 동안 들어온 요청 중 인증이나 OCR 같은 느린 요청이 5%를 넘으면, 그 창의 p95 는 그 요청들의 응답시간이 됩니다. 임계를 넘긴 것은 서비스가 느려져서가 아니라, 원래 느린 요청이 그 10분 창에 많이 들어와서였어요. 그래서 이 모니터가 울려도 받은 사람이 할 수 있는 일은 없었습니다. 인증 요청을 빠르게 만들 방법은 사용자에게 버튼을 빨리 누르라고 하는 것뿐이니까요.

2. 일반 요청만 재고, 3편의 판단 하나를 뒤집었다

그래서 지연 판정을 "일반" 요청으로 좁혔어요(#851). 3편에서 모듈에 넣어 둔 latency_exclude_resources 목록을 메인 API 와 에이전트 API 에도 채운 거예요.

latency_p95_ms = 1000 # 지연은 「일반」 요청만 본다. # 외부 기관 · 사용자 대기 : 인증 요청, 외부 기관 중계 단계 # 내부 무거운 처리 : 신분증 · 서명 분석(OCR), 상담 초안 # 헬스체크 · CORS 사전요청 # 핵심 업무(신청 접수 등)는 빼지 않는다. 느려지면 잡아야 한다. latency_exclude_resources = [ "get_/actuator/health", "head_/actuator/health", "options_*", "post_/api/{버전}/{인증 경로}/*", "post_/api/v1/user/{OCR 분석 경로}", ... ]

→ APM 의 resource 이름(메서드_경로)으로 판정에서 뺄 요청을 적고, 같은 성격의 새 API 가 생겨도 덮이도록 경로 끝은 와일드카드로 묶었다는 뜻이에요. 다만 3편에서 적은 대로 *health* 같은 넓은 패턴은 쓰지 않았습니다.

이 목록에서 눈여겨볼 줄은 맨 위 두 줄이에요. 3편에서는 "지연 p95 에서는 헬스체크를 빼지 않는다"고 정했습니다. 빠른 요청을 빼면 p95 가 올라가서 임계를 다시 봐야 하기 때문이었어요. 그 판단을 이번에 뒤집었습니다. 메인 API 에서 헬스체크는 전체 요청의 11%였고 응답시간은 1ms 였어요. 이 요청들이 p95 를 실제 사용자가 겪는 값보다 낮게 보이게 하고 있었습니다. 3편의 판단은 요청이 적은 서비스를 기준으로 한 것이었고, 메인 API 와 에이전트 API 는 헬스체크를 빼도 판정할 요청이 충분했어요.

두 방향으로 뺀 결과를 14일 시뮬레이션(10분 p95)으로 확인했어요.

p95 중앙 14일 최대 임계(전) 임계(후) 초과(후) 메인 API 182ms 756ms 3000ms 1000ms 0 에이전트 API 51ms 638ms 1500ms 1000ms 0

→ 느린 요청을 빼니 남은 요청의 14일 최댓값이 1초 아래로 내려왔고, 그래서 임계를 오히려 조일 수 있었다는 뜻이에요. 메인 API 는 3초에서 1초로, 에이전트 API 는 1.5초에서 1초로 낮췄습니다. 메인 API 의 14일 초과 횟수는 68번에서 0번이 됐어요. 이 0은 같은 14일 데이터에 새 조건을 대 본 결과이고, 운영에서 앞으로도 0이라는 뜻은 아닙니다.

⚠️ 주의: 느리다고 다 빼면 안 된다
에이전트 API 의 신청 접수 API 는 평소 p95 가 약 3초예요. 이 API 를 빼면 임계를 더 조일 수 있었지만 빼지 않았습니다. 제외 기준은 "느린가"가 아니라 "느린 게 정상이고, 느려져도 우리가 할 일이 없는가"였어요. 신청 접수가 느려지면 사용자가 그 화면에서 기다리고 있는 것이니 잡아야 합니다. 이런 API 는 4절의 핵심 경로 모니터가 자기 평소 값으로 따로 봐요.

3. 가드도 판정과 같은 요청을 세야 했다

같은 날 제휴 서비스와 메시지 발송 서비스를 같은 방식으로 들여다봤어요(#854). 여기서 3편의 저트래픽 가드가 다시 문제를 일으키고 있었습니다.

3편에서 가드는 /actuator/health 와 OPTIONS 를 빼고 셌어요. 그런데 제휴 서비스는 헬스체크 경로가 따로 있었습니다. 그 경로는 3편의 제외 목록에 없었으니 가드가 그대로 셌어요. 이 서비스는 요청의 71%가 그 헬스체크였습니다. 그래서 실제 요청이 3건뿐인 10분에도 가드 기준 20건을 넘겼고, 모니터는 그 3건의 p95 로 판정했어요. 3편에서 막으려던 "몇 건의 비율로 사람을 깨우는 일"이 경로 이름 하나 때문에 그대로 남아 있었던 거예요.

고친 방법은 지연 판정 전용 가드를 하나 더 두는 것이었어요. 기존 가드는 에러율 판정에 그대로 쓰고, 새 가드는 지연 제외 목록까지 반영해서 셉니다.

latency_guard_scope = join(",", concat( [local.traffic_scope], [for r in var.latency_exclude_resources : "!resource_name:${r}"] )) # [sub] 지연 판정 대상 적음 : 10분 동안 위 범위의 요청이 20건 미만 # [P2] 응답 지연 : latency_raw && !low_traffic_latency

→ 가드가 세는 범위와 p95 를 재는 범위를 같은 목록에서 만들게 했다는 뜻이에요. 지연 판정에서 뺀 요청은 가드에서도 빠집니다.

제휴 서비스는 자기 헬스체크와 CORS 사전 요청, 외부 기관 중계 두 종류를 지연 판정에서 뺐어요. p95 중앙값이 3,511ms 에서 490ms 로 내려가서 임계를 15초에서 2초로 낮췄습니다. 3편에서 느린 상태를 정상으로 인정한 값이라고 소개한 그 15초예요. 새 조건으로 14일을 다시 보면, 판정 대상이 20건 이상인 구간에서 2초를 넘은 것은 1번이었어요.

메시지 발송 서비스 쪽은 더 곤란한 상태였어요. 요청의 86%가 헬스체크였고, 지연 모니터가 보던 p95 는 헬스체크의 응답시간인 7ms 였습니다. 이 모니터는 발송 API 가 아니라 헬스체크의 속도를 재고 있었어요. 헬스체크를 빼고 발송 API 만 재니 p95 중앙값은 62ms 였고, 임계 500ms 는 그대로 뒀습니다.

그림 1. 서비스 p95 하나에 섞여 있던 요청을 셋으로 갈랐다

4. 서비스 p95 가 멀쩡해도 로그인은 느릴 수 있다

2절까지 하고 나면 오탐은 사라져요. 그런데 반대쪽 문제가 남습니다. 로그인 API 가 평소 0.2초에서 0.8초로 느려졌다고 해 볼게요. 사용자는 확실히 느끼는 변화예요. 하지만 서비스 p95 는 다른 수많은 요청과 섞여 있어서, 이 정도 변화로는 임계 1초를 넘지 않을 수 있습니다. 서비스 p95 는 성격이 다른 API 를 섞어 놓아서, 특정 API 하나가 나빠지는 것에는 둔해요.

그래서 업무에서 중요한 API 는 서비스 p95 와 별도로, API 마다 자기 평소 값을 기준으로 보게 했어요(#862). 모듈에 critical_endpoints 입력을 두고, 여기 적은 API 마다 모니터를 하나씩 만듭니다.

📖 용어: 핵심 경로 (critical path)
이 글에서는 "사용자가 이 화면에서 실제로 기다리고 있고, 느려지면 업무가 바로 영향을 받는 API"를 뜻해요. 서비스 하나에 API 가 수백 개 있어도 이런 API 는 몇 개 안 됩니다.

메인 API 에서 5개, 에이전트 API 에서 3개를 골라 모두 8개예요. 역할로 나누면 로그인 2개, 신청 접수 2개, 그 밖의 업무 핵심 API 4개입니다.

critical_endpoints = { "{메서드}_{로그인 경로}" = { label = "로그인", latency_ms = {임계} } "{메서드}_{업무 경로}" = { label = "{업무 이름}", latency_ms = {임계} } ... } # 모니터 쿼리 (API 하나에 하나) avg(last_1h):p95:trace.servlet.request{service:{서비스},env:prod, resource_name:{API}} > {임계}

→ 서비스 전체가 아니라 resource 이름 하나로 범위를 좁히고, 1시간 창의 p95 를 그 API 의 임계와 비교한다는 뜻이에요.

창을 10분이 아니라 1시간으로 잡은 데는 이유가 있어요. 이 API 들은 호출이 시간당 몇 건에서 몇백 건이었습니다. 10분 창으로 보면 몇 건짜리 p95 가 되고, 그건 3절에서 겪은 "3건의 p95" 문제와 같아요. 호출이 없는 시간에는 데이터 없음이 되는데, 이때는 알리지 않게 뒀습니다.

임계는 API 마다 따로 계산했어요. 14일 동안의 1시간 p95 중 상위 1%에 1.5를 곱하고, 최소 300ms, 100ms 단위로 올림했습니다. 이 기준으로 14일을 시뮬레이션해 보니 8개 중 7개는 초과가 0번이었어요. 에이전트 API 의 신청 접수 하나만 2번 넘었습니다. 평소 꼬리가 긴 API 라 임계가 22.7초로 나왔고, 이 값은 첫 기준으로 두고 운영하면서 다시 보기로 했어요. 알림은 P2 로 #{알림 채널} 에 갑니다.

5. 오래 기다리는 API 의 감시는 만들지 않았다

2절에서 뺀 API 들은 이제 어떤 지연 모니터도 보지 않아요. 그래서 "이 API 들의 에러는 따로 봐야 하지 않을까"를 확인했습니다. 결론은 만들지 않는 것이었어요. 근거는 14일 실측입니다.

· 메인 API 의 인증·OCR 요청은 약 56만 건 중 5xx 가 0건이었어요.
· 에이전트 API 의 서류 발급 요청은 5xx 가 0.3% 이하였습니다.
· 인증 실패는 5xx 가 아니라 업무 코드가 담긴 정상 응답으로 돌아가요. 그리고 외부 인증 연동은 이미 P1 모니터가 timeout 까지 보고 있었습니다.
· 에이전트 API 의 스트림은 요청의 42%가 에러로 기록됐는데, 연결 종료가 에러로 남은 것이었어요. 10분에 많아야 8건이라 같은 시간 요청 450건 이상인 서비스 에러율에는 영향이 없었습니다.

새로 만들 모니터가 잡을 사건이 14일 동안 거의 없었고, 있을 법한 실패는 이미 다른 모니터가 보고 있었어요. 이 상태에서 모니터를 더하면 늘어나는 것은 관리할 코드와 스트림 끊김 같은 소음뿐입니다.

💡 실무에서는: "만들지 않음"도 결정으로 남긴다
3편에서 JVM 힙 모니터를 뺀 이유를 코드 주석에 적었듯이, 이번에도 만들지 않은 이유를 작업 기록에 숫자와 함께 남겼어요. 나중에 누군가 "느린 API 는 아무도 안 보네" 하고 모니터를 더하려 할 때, 그 사람이 먼저 확인할 것은 이 숫자가 아직 맞는가입니다.

6. 조금씩 나빠지는 지연은 SLO 로 본다

4절의 핵심 경로 모니터는 1시간 p95 가 임계를 넘을 때 울려요. 그러면 매일 한두 번씩 잠깐 느려지는 API 는 어떨까요. 한 번 한 번은 1시간 평균을 끌어올리지 못해서 모니터가 울리지 않아요. 그런데 한 달을 모으면 사용자가 느린 화면을 본 횟수는 적지 않아요. "지금 나쁜가"를 묻는 모니터로는 "이번 달에 얼마나 나빴나"를 답할 수 없어요.

📖 용어: SLO 와 에러 예산
SLO(Service Level Objective)는 "30일 중 99%는 괜찮아야 한다"는 식의 목표예요. 나머지 1%가 에러 예산입니다. 그만큼은 나빠도 된다고 미리 정해 둔 양이에요. 예산이 남아 있으면 괜찮은 달이고, 빨리 줄어들면 무언가 나빠지고 있다는 뜻입니다.

8개 핵심 경로마다 지연 SLO 를 하나씩 만들었어요(#870). 방식은 time-slice 입니다.

📖 용어: time-slice SLO
시간을 일정한 조각(여기서는 5분)으로 나눠, 조각마다 조건을 만족했는지 "좋은 5분 / 나쁜 5분"으로 판정하는 SLO 예요. 여기서는 그 5분의 p95 가 핵심 경로 임계 이하면 좋은 5분입니다. 호출이 하나도 없는 5분은 Datadog 기본값에 따라 좋은 것으로 세요. 그래서 밤에 호출이 없는 API 가 예산을 쓰지 않습니다.

목표는 30일 중 좋은 5분 99%, 경고는 99.5%로 뒀어요. time-slice SLO 는 만들자마자 과거 데이터로 지난 30일 실적을 계산해 줍니다. 그래서 알림을 붙이기 전에 목표가 맞는지 먼저 볼 수 있었어요. 8개 모두 99.84%에서 100% 사이였고, 남은 예산은 가장 적은 것도 84%였습니다. 지난 30일 실적이 목표 안에 있었으므로 99%를 그대로 뒀어요.

그다음에 예산이 줄어드는 속도로 알림을 붙였습니다(#873).

📖 용어: 번 레이트 (burn rate)
에러 예산을 쓰는 속도를 "딱 30일에 다 쓰는 속도"와 비교한 배수예요. 번 레이트 1이면 30일째에 예산이 정확히 바닥나고, 6이면 그 6배 속도라서 5일 만에 바닥납니다.
burn_rate("{SLO}").over("30d").long_window("6h").short_window("30m") > 6 6시간 × 6배 = 30일 예산의 5% (6 × 6h ÷ 720h) 이 속도가 이어지면 예산은 약 5일 안에 바닥난다

→ 최근 6시간 동안 예산을 평소의 6배 속도로 썼고, 최근 30분도 여전히 그 속도라면 알린다는 뜻이에요. 30분 확인 창은 이미 끝난 문제에 뒤늦게 울리지 않게 하는 장치입니다.

이 알림은 P3 로, 사람을 부르지 않고 Slack 에만 보내요. 급한 장애는 4절의 핵심 경로 모니터(P2)가 이미 잡습니다. 번 레이트를 빠른 소진용으로도 하나 더 걸면 같은 장애에 알림이 두 번 와요. 그래서 번 레이트는 "모니터가 울리지 않을 만큼 조금씩, 그러나 계속 나빠지는" 경우만 맡게 했어요.

그림 2. 임계를 넘는 급성 지연은 모니터가, 임계 아래에서 반복되는 지연은 번 레이트가 맡는다

7. 자동으로 쌓이기만 한 인시던트 538건

같은 날 Datadog 의 인시던트 목록도 정리했어요. 열어 보니 538건이 쌓여 있었습니다.

📖 용어: 인시던트 (Datadog Incident Management)
장애 하나를 기록 단위로 만들어 담당자, 진행 상황, 타임라인을 모아 두는 Datadog 기능이에요. 사람이 직접 열 수도 있고, 모니터가 울릴 때 자동으로 만들게 설정할 수도 있습니다.

538건 중 533건은 사람이 연 것이 아니었어요. 옛 로그인 에러 모니터와 옛 신청 API 에러 모니터가 울릴 때마다 자동으로 만든 것이었습니다. 자동 생성은 9월 14일 이후 멈춰 있었고, 그 뒤로는 새 기록 없이 옛 기록만 남아 있었어요. 나머지 5건은 테스트로 만든 것이었습니다.

538건을 모두 지우고, 같은 날 Incident 좌석 1개도 해제했습니다. 콘솔에만 남아 있던 정리 대상을 하나 줄인 일이기도 해요. On-Call 좌석 8개는 그대로 뒀습니다. P1 알림이 온콜 담당자에게 전화를 거는 데 쓰는 좌석이기 때문이에요.

⚠️ 주의: 인시던트는 기본 설정으로는 지울 수 없다
인시던트 유형(여기서는 General Incident) 설정의 allow_incident_deletion 을 켜야 삭제가 됩니다. 켜고 지운 뒤 다시 껐어요. 켜 둔 채로 두면 진짜 장애 기록도 실수로 지워질 수 있으니, 정리가 끝나면 원래대로 돌려 두는 것이 안전합니다.

같은 날 다운 모니터의 알림 대상도 하나 맞췄어요(#865). 다른 서비스의 P1 다운 알림은 플랫폼팀 온콜이 받는데, 메인 API 와 에이전트 API 의 다운 모니터는 서버개발 온콜만 불렀습니다. 같은 등급의 장애인데 받는 사람이 서비스마다 달랐던 거예요. 두 모니터에 플랫폼팀 온콜을 더하고, 서버개발 온콜은 그대로 두었습니다.

8. 열 편을 돌아보며: 한 것과 남은 것

이 시리즈는 9월 28일에 시작했어요. 계획은 13단계, 약 6주였습니다. 10월 2일까지 5일 동안 0~10단계와 12단계(SLO)를 끝냈어요. 열 편을 묶으면 대략 이런 흐름이었습니다.

· 옮기기 (1·2편): 콘솔에 흩어진 모니터를 실물 변경 없이 코드로 옮겼고, 태그의 뜻(service 는 앱, team 은 호출 단위)을 정했어요.
· 제대로 재기 (3~6편, 10편): 필수 모니터를 모듈로 맞추고, 그 모니터가 재고 싶은 값을 재는지 실측으로 대조했어요. 헬스체크를 세던 가드, 사이드카를 재던 CPU, 데이터 없음의 의미, APM 을 떼는 순서, 로그 유실이 여기서 나왔습니다. 이번 편의 지연 판정 범위도 같은 질문의 연장이에요.
· 알림이 닿는지 확인하기 (7~9편): 없는 채널로 가는 알림을 PR 단계에서 막고, 서비스 카탈로그를 실제로 데이터를 보내는 11개 앱에 맞추고, 음소거된 채 잊힌 P1 을 되살렸어요.

10월 1일 실물 대조에서 모니터 90개가 전부 코드에 있다는 것을 확인했어요. 코드 밖에 일부러 남긴 것은 빈 대시보드와 샘플 대시보드 같은 정리 후보, 그리고 원칙상 코드 밖에 두는 일회성 다운타임 하나였습니다. 9편에서 적었듯이 그 다운타임은 배치 실패 P1 을 끄고 있던 음소거였고, 10월 2일에 풀어서 코드 밖 일회성 다운타임도 0이 됐어요.

남은 것은 세 가지예요. 하나는 11단계인 서비스 표준 모듈입니다. 서비스 목록(CMDB)에 한 줄을 등록하면 카탈로그, 모니터, 대시보드, SLO 가 함께 만들어지게 하는 단계예요. 이건 날짜가 아니라 CMDB 쪽 결정(원본을 어디에 둘지, 어떤 항목을 둘지, 어떻게 옮길지, 누가 쓸지)에 달려 있어서 아직 시작하지 않았습니다. 둘째는 9편에서 적은 종료 시점 없는 다운타임을 찾아 보고하는 장치로, 아직 만들지 않았어요. 셋째는 이번 편에서 정한 숫자들이에요. 핵심 경로 임계와 SLO 목표는 14일, 30일 실측으로 정한 첫 기준이라, 1~2주 운영한 뒤 실제로 울린 알림을 보고 다시 맞출 예정입니다.

✍️ 오늘의 요약
메인 API 의 지연 모니터가 14일 동안 임계를 68번 넘은 것은 인증 대기, OCR, 스트림 같은 원래 느린 요청 때문이었다. 이 요청과 헬스체크를 판정과 가드에서 함께 빼니 68번이 0번이 됐고, 임계는 오히려 3초에서 1초로 조일 수 있었다.

대신 서비스 p95 가 놓치는 로그인·신청 접수 같은 핵심 경로 8개는 경로마다 자기 평소 값으로 보고, 임계 아래에서 반복되는 지연은 SLO 번 레이트가 Slack 으로만 알린다. 오래 기다리는 API 의 감시는 14일 실측을 보고 만들지 않았다. 지연 모니터를 고친다는 것은 임계를 바꾸는 일이 아니라, 그 숫자에 어떤 요청이 섞여 있는지부터 가르는 일이다.
