6편. JSON 로그 수집 규칙과 모니터 검색 조건 고치기 ← 지금 이 글

배치 서버 호스트의 로그 파일에는 있는 줄이 Datadog 로그 화면에서는 보이지 않았어요. 일부 줄만 보이지 않아 처음에는 샘플링을 의심했습니다.

9월 29일, 호스트의 원본 로그와 Datadog에 들어온 로그를 줄 단위로 맞춰 보니 여러 줄이 한 건으로 합쳐져 있었어요. 같은 주에는 로그 관련 문제를 네 개 더 확인했습니다. 에러가 info로 분류됐고, 새 모니터에 쓰려던 태그와 status 조건에 맞는 로그가 없었어요. 백업 필터는 서비스 이름 하나에 의존했고, 옛 서비스 이름으로 검색하던 지표와 모니터는 몇 달째 0을 세고 있었습니다. 로그가 수집됐는지와 설정 조건에 맞게 검색되는지를 나눠 확인해야 했어요.

확인한 항목
· 원본 로그와 수집된 로그의 줄 단위 대조
· ERROR가 info로 분류된 원인과 파이프라인 수정
· 배포 전 실제 로그로 모니터 조건 확인
· 태그 변경에 앞선 아카이브 편입
· 옛 서비스 이름을 참조하는 지표와 모니터 정리

1. 여러 JSON 로그가 한 건으로 합쳐진 이유

📖 용어: 샘플링 (sampling)
데이터의 일부만 골라 보내거나 저장하는 방식이에요. 무작위 비율로 고를 수도 있고 조건에 따라 고를 수도 있어요. 누락 패턴만으로 샘플링을 배제할 수는 없으므로, 여기서는 원본 로그와 실제 수집·필터 설정을 대조했어요.

호스트의 원본 로그 파일과 같은 시간대에 Datadog에 들어온 로그를 한 줄씩 대조했어요. 빠진 줄은 흩어져 있지 않고, 바로 앞 줄과 1초 안에 연달아 찍힌 줄이었어요. 앞 줄과 1초 넘게 떨어져 찍힌 줄은 따로 들어왔고, 1초 안에 이어진 줄만 보이지 않았습니다.

연달아 찍힌 줄은 Datadog에서 로그 한 건으로 합쳐져 있었습니다. 원인은 배치 서버 컨테이너에 붙어 있던 multi_line 규칙이었어요.

📖 용어: multi_line (로그 수집 규칙)
Datadog 에이전트가 여러 줄을 한 로그로 묶게 하는 처리 규칙이에요. "새 로그는 이런 모양으로 시작한다"는 패턴을 주면, 그 패턴에 맞지 않는 줄은 앞 로그의 뒷부분으로 붙입니다. 한 에러가 수십 줄로 찍히는 자바 스택 트레이스 같은 평문 로그를 위해 쓰는 설정이에요. 이 규칙은 컨테이너 라벨로 붙어 있었습니다.

문제는 이 서비스의 로그가 평문이 아니라 한 줄에 JSON 하나씩 찍는 형식이었다는 점이에요. 새 로그의 시작을 알아보는 패턴이 JSON 줄의 첫머리와 맞지 않았습니다. 그러면 에이전트 기준으로는 어떤 줄도 "새 로그의 시작"이 아니에요. 에이전트는 줄을 계속 이어 붙이다가, 일정 시간(기본 1초) 동안 다음 줄이 오지 않으면 모아 둔 것을 한 건으로 보냅니다. 그래서 1초 안에 이어진 줄은 전부 로그 한 건이 됐어요.

# 호스트의 로그 파일 (형태를 보이려고 만든 예시) {"time":"09:12:03.101","level":"INFO","msg":"요청 처리 시작"} {"time":"09:12:03.240","level":"ERROR","msg":"외부 호출 실패"} {"time":"09:12:03.388","level":"INFO","msg":"재시도 예약"} # Datadog 에 들어온 것: 로그 1건 status: info message: 요청 처리 시작 (뒤의 두 줄은 이 한 건의 뒷부분으로 붙음)

→ 합쳐진 로그를 원본과 대조해 보니 맨 앞 JSON 의 값만 속성으로 잡혀 있었어요. 레벨도 첫 줄 것만 남아서, 가운데의 ERROR 는 에러로 세어지지 않았습니다.

그림 1. 시작 패턴에 맞는 줄이 없으면, 1초 안에 이어진 줄은 한 건이 된다

조치는 9월 30일에 했어요. JSON 로그는 한 줄이 이미 완결된 로그 하나라 여러 줄을 묶을 필요가 없습니다. 그래서 multi_line 라벨을 지우고, 앱 컨테이너와 배치 컨테이너를 다시 만들었어요. 컨테이너 라벨은 컨테이너를 만들 때 정해지는 값이라, 설정 파일만 고치고 재시작하면 옛 라벨이 그대로 남습니다.

수정에 앞서 숫자를 다시 셌어요. 이 서비스의 status:error 로그는 3일에 27건이었는데, 합쳐져 있던 줄을 풀어 세면 같은 3일 기준 약 142건이 될 것으로 봤어요. 수집 수정 뒤에 같은 에러를 개별 로그로 세게 될 것을 고려한 예상치였어요.

⚠️ 주의: 수집을 고치면 임계값도 다시 확인해요
이 서비스에는 5편에서 APM 을 대신하려고 세운 "에러 로그 10분 4건 이상" 모니터가 있었어요. 기준은 에러가 합쳐져 있던 시절의 평소값(9월 28일에 센 값, 3일에 10건)으로 잡은 것이었습니다. 합쳐진 줄을 풀어 센 예상 분포를 보니 10분 최댓값이 8, 5, 3 순이었고, 4건 이상 기준이면 3일에 두 번 넘어요. 그래서 수집 수정과 같은 날 기준을 "10분 6건 이상"으로 올렸습니다(#803). 에러를 개별 로그로 세게 되므로 기존 임계값도 함께 조정했어요.

2. 모니터 조건은 쌓인 로그에 먼저 돌렸다

9월 30일 낮에는 제휴 API 에 로그 모니터를 새로 만들고 있었어요. 이 서비스는 APM 이 없고, CloudWatch 알람은 호스트와 로드밸런서 상태만 봐서, 앱이 외부 연동에 실패해도 그걸 세는 감시가 없었습니다. 그래서 조건을 정하기 전에 이 서비스의 로그가 어떤 태그와 status 로 들어오는지부터 이미 쌓인 로그로 확인했어요(#799).

📖 용어: status (Datadog 로그의 레벨)
Datadog 이 로그마다 매기는 심각도 값이에요(error, warn, info 등). 로그 화면의 색과 status:error 같은 검색이 이 값을 씁니다. 로그 원문에 ERROR 라고 적혀 있어도, 수집하면서 그 글자를 읽어 status 로 옮기지 않으면 기본값 info 가 붙어요.

확인한 것은 두 가지였어요. 첫째, 이 서비스의 로그에는 env 태그가 아예 없었습니다. 둘째, 원문에 ERROR 라고 찍힌 줄도 status 는 info 였어요. 7일 동안 들어온 로그가 한 줄도 빠짐없이 info 였습니다. 운영 환경(env:prod)과 에러(status:error)로 거르는 흔한 조건을 이 서비스에 그대로 쓰면, 장애가 나도 0건이 됩니다.

확인한 로그를 기준으로 조건을 정했어요. 없는 env와 에러를 제대로 반영하지 못하는 status는 쓰지 않고, 실패 문구로 세었어요. 실패 1건에 ERROR 줄이 약 4줄 찍히는 것도 확인해서, 요청마다 한 번만 찍히는 문구를 골랐습니다. 줄 수를 그대로 세면 실패 1건을 4건으로 집계하게 됩니다.

logs("service:{제휴 API} \"{요청당 한 번 찍히는 실패 문구}\"").last("10m") >= 3

→ 최근 10분 동안 이 서비스의 로그 중 그 실패 문구가 들어간 것이 3건 이상이면 알림을 보낸다는 뜻이에요. 같은 조건을 9월 28일부터 30일까지의 로그에 돌려 보니 27건이 잡혔습니다.

이런 쿼리는 문법이 맞으면 Datadog의 검증을 통과해요. 하지만 그 조건에 맞는 로그가 실제로 있는지까지 확인해 주지는 않습니다. 배포 전에 기존 로그로 검색해 본 이유예요.

💡 실무에서는: 모니터 조건을 로그 검색창에서 확인해요
• 모니터에 넣을 조건을 로그 검색창에 그대로 넣고, 지난 며칠 동안 몇 건이 잡히는지 먼저 봅니다
• 0 이면 조건을 하나씩 빼 보며 어느 조건이 0 을 만드는지 찾아요. 이번에는 태그 누락과 status 분류가 원인이었어요
• 반대로 너무 많이 잡히면 한 사건이 몇 줄로 찍히는지 세어 보고, 한 번만 찍히는 문구를 고릅니다

3. ERROR 라고 찍혀도 info 였던 이유

오후에 다른 서비스에서도 ERROR 로그의 status를 확인했어요. 메인 API 는 3일 동안 ERROR 줄이 수만 개였는데 status:error 는 23건이었습니다. 약 0.05% 만 에러로 분류된 거예요. status로 거르는 로그 모니터에는 대부분의 에러가 집계되지 않았어요.

원인은 로그의 줄 모양이었어요. Datadog 이 자바 로그에 기본으로 적용하는 해석 규칙은 "날짜, 스레드, 레벨, 로거, 메시지" 순서를 기대합니다. 그런데 앱들의 로그는 레벨이 맨 앞에 오고 날짜가 없는 모양이었어요. 문서 팩스 서비스와 메시지 발송 서비스는 Spring Boot 기본 모양이라 역시 맞지 않았습니다.

기대하는 모양 2026-09-30 13:58:15.783 [exec-1] ERROR … - 메시지 (날짜, 스레드, 레벨) 앱 logback ERROR 13:58:15.783 [exec-1] … - 메시지 (레벨, 시각) Spring Boot 2026-09-30T11:04:40.003+09:00 ERROR 1 --- [app] …

→ 첫 줄의 모양을 기대하는 규칙에 아래 두 모양이 들어오면 해석에 실패하고, 레벨을 뽑지 못한 로그에는 info 가 붙어요.

앱의 로그 형식을 바꾸거나 수집 쪽에서 현재 형식을 해석하도록 고칠 수 있었어요. 앱 저장소는 각 팀이 소유하고 있어서 앱을 바꾸려면 여러 팀의 배포가 필요합니다. 그래서 앱은 그대로 두고, 수집 쪽에 로그 파이프라인을 하나 만들어 코드로 두었어요(#803).

📖 용어: 로그 파이프라인 (log pipeline)
Datadog 이 로그를 받아 저장하기 전에 거치는 처리 단계의 묶음이에요. 원문에서 값을 뽑아 속성으로 만들거나(파서), 뽑은 값을 status 같은 표준 속성으로 옮기는(리매퍼) 처리를 차례로 둡니다. 앱을 고치지 않고도 로그를 읽는 방식을 바꿀 수 있는 곳이에요.
app_logback %%{regex("(TRACE|DEBUG|INFO|WARN|ERROR|FATAL)"):level}\s+%%{regex("[0-9]{2}:[0-9]{2}:[0-9]{2}[.][0-9]{3}")}\s+%%{data} spring_boot %%{notSpace}\s+%%{regex("(TRACE|DEBUG|INFO|WARN|ERROR|FATAL)"):level}\s+%%{integer}\s+---\s+%%{data}

→ 줄 머리에서 레벨 단어를 뽑아 level 속성에 담는 규칙 두 개예요(%% 는 Terraform 문자열 안에서 % 를 쓰려고 겹친 것). 뒤이어 둔 리매퍼가 이 level 을 status 로 옮깁니다.

규칙이 줄 머리만 보고 나머지를 %{data} 로 받는 데는 이유가 있어요. Datadog 의 해석 규칙은 로그 한 줄 전체가 규칙에 맞아야 적용되기 때문에, 메시지 부분까지 형식을 제한하면 그 형식과 다른 로그는 해석하지 못해요. 적용 전에 서비스마다 하루치 로그에서 500건을 뽑아 맞춰 보니, 규칙에 맞는 비율이 76.8%에서 100% 사이였어요. 맞지 않은 줄은 스택 트레이스의 이어지는 줄과 기동 배너였습니다. 이런 줄에는 원래 레벨이 없으니 info 로 남는 게 맞아요.

이 파이프라인이 켜지면 status:error 로 거르는 로그 모니터 넷이 영향을 받는다는 것도 코드 주석에 적어 두었습니다. 여러 줄이 합쳐진 JSON 로그와 레벨을 해석하지 못한 평문 로그는 원인이 달랐어요. 두 경우 모두 로그가 수집돼도 에러 건수에는 제대로 반영되지 않았습니다.

⚠️ 주의: 검색 결과 0건은 "로그가 없다"는 뜻이 아니다
이 조직의 로그 인덱스(검색할 수 있게 로그를 담아 두는 저장 공간)는 3일만 보관돼요. 인덱스 제외 필터(수집은 하되 인덱스에는 넣지 않을 로그를 고르는 조건)로 검색에서 빠지는 로그도 있습니다. 그래서 검색이 0건이라고 수집이 끊겼다고 판정하면 틀릴 수 있어요. 수집이 되는지는 검색이 아니라 로그 수집량 지표로 봐야 합니다.

4. 태그를 바꾸기 전에 백업부터

로그 아카이브는 원본 로그를 대조하기 하루 전인 9월 28일에 확인했어요. 2편의 태그 규약을 정리하면서 서비스 이름이 바뀌면 기존 이름을 쓰는 검색 조건에 로그가 맞지 않게 된다는 점을 확인했습니다. 아카이브의 필터도 같은 영향을 받았어요.

📖 용어: 로그 아카이브 (log archive)
Datadog 에 들어온 로그를 조건에 맞춰 S3 같은 외부 저장소에 계속 복사해 두는 설정이에요. 인덱스 보관 기간이 지나 검색에서 사라진 로그도 여기서 다시 불러올 수 있습니다.

인덱스 보관이 3일이라, 그보다 오래된 로그는 아카이브에만 남아요. 사실상 유일한 백업입니다. 그런데 아카이브 다섯 개의 필터가 전부 service:<이름> 이었어요. 서비스 이름이 바뀌면 기존 필터에 맞지 않아 그 서비스의 로그가 백업되지 않을 수 있어요. 그래서 태그를 바꾸기 전에 아카이브부터 코드로 옮기기로 했습니다.

첫 PR(#698)은 콘솔에 있던 아카이브 다섯 개를 설정 그대로 코드로 가져왔어요. plan 결과는 가져오기 5건, 변경 0건이었습니다. 이제 누가 콘솔에서 필터를 바꿔도 다음 plan 에서 코드와의 차이로 드러나요. 두 번째 PR(#701)에서는 백업되지 않던 문서 팩스 서비스와 메시지 발송 서비스의 아카이브를 새로 만들었습니다. 필터에는 실제 수집된 로그의 서비스 이름을 사용했어요. 그 이름의 로그가 어디서 나오는지 하루치 로그로 먼저 확인한 뒤였습니다.

아카이브 조건을 확인하다가 오전의 판단도 수정했어요. 문서 팩스 서비스를 "수집량 상위권"으로 보고 백업이 급하다고 적었는데, 그 서비스 이름으로 잡히던 수집량은 개발 서버 로그였습니다. 그래서 세 번째 PR(#703)에서 필터를 운영 로그(env:prod)로 좁혔어요. 당시에는 해당 서비스의 운영 로그 수집이 없어 운영 로그용 필터만 준비한 상태였어요. 운영 로그를 수집하기 시작한 뒤부터 보관되므로, 이 PR만으로 운영 로그 백업이 시작된 것은 아닙니다. 아카이브 필터에도 실제 로그를 대조해 보니 개발·운영 환경의 차이를 확인할 수 있었습니다.

5. 옛 이름을 보던 지표와 모니터

9월 30일 오후, 아직 콘솔에만 있던 로그 설정을 훑다가 로그 기반 지표 네 개를 찾았어요.

📖 용어: 로그 기반 지표 (log-based metric)
조건에 맞는 로그의 건수 등을 세어 시계열 지표로 만들어 두는 설정이에요. 로그는 검색 보존 기간이 지나 사라져도, 지표는 더 오래 남아 대시보드와 모니터에 쓸 수 있습니다.

네 개 모두 메인 API 의 옛 서비스 이름으로 로그를 거르고 있었어요. 로그의 서비스 이름은 6월 말에 바뀌었고, 그날부터 이 지표들은 0 을 셌습니다. 모니터와 대시보드에서 이 지표를 참조하는 곳이 있는지 전부 찾아봤는데 없었어요. 그래서 지웠습니다.

지우는 방법은 두 단계였어요. #806 에서 네 지표를 코드로 가져오고, 바로 다음 #807 에서 코드에서 지웠습니다. 코드로 가져온 뒤 삭제하면 지표의 기존 설정과 삭제 이유를 커밋에 남길 수 있어요.

# 지우기 전 필터 (네 개 모두 같은 모양) filter { query = "service:{옛 이름} \"{연동} 에러 발생\"" }

→ 서비스 이름이 바뀐 뒤로는 이 조건에 맞는 로그가 들어오지 않아서, 지표는 에러가 나도 0 이었다는 뜻이에요.

그날 오후에는 배치 실패 알림 모니터도 고쳤어요(#809). 배치 서버에서 매일 새벽 3시에 도는 배치를 감시하는 모니터였는데, 옛 서비스 이름을 보고 있었습니다. 배치의 로그 서비스 이름이 7월에 바뀌면서 조건에 맞는 로그가 사라졌고, 옛 조건에 맞는 로그는 0건이었어요. 배치가 실패해도 울리지 않는 상태였다는 뜻이에요. 먼저 최근 로그로 배치가 매일 새벽 정상 완료되고 있음을 확인했고, 그런 다음 조건을 새 이름으로 바꾸면서 실패 문구를 셋(작업 전체 실패, 건 단위 실패, 실패 기록)으로 넓혔어요.

그리고 조건에서 status:error 를 뺐습니다. 이 수정은 같은 날 저녁 1절의 multi_line 라벨을 지우기 전이었어요. 그때까지 배치 서버 로그의 status가 에러를 제대로 반영하지 못해 문구로만 거르게 했습니다.

그림 2. 서비스 이름 변경은 기존 이름을 참조하는 모니터·지표·아카이브에 영향을 줘요

이미 쓰이는 service 이름을 바꾸지 않기로 한 2편의 규약은 이런 문제를 막기 위한 것이었어요. 규약 문서에는 이름이 바뀌어 데이터가 갈라진 일을 "세 번 겪었다"고 적었는데, 이 지표 네 개와 새벽 배치의 실패 알림 모니터는 그중 두 번에서 생긴 것이었습니다. 이름이 바뀐 날에도 조건 불일치를 알리는 알림이나 오류는 없었어요.

💡 실무에서는: 삭제할 설정도 먼저 코드로 가져와요
콘솔에만 있는 설정을 지울 때도 한 번 코드로 가져오고(import), 다음 PR 에서 코드에서 지웠어요. 그러면 지운 설정의 원래 모양과 지운 이유가 커밋에 남고, 지우는 변경도 plan 과 리뷰를 거칩니다.

6. 설정 조건과 실제 로그를 대조한 결과

9월 마지막 주에 콘솔의 Datadog 설정을 Terraform으로 옮기면서 수집된 데이터도 함께 확인했어요. 콘솔 변경을 허용하는 운영 방식과 태그의 관리 주체를 정했고, 헬스체크를 세던 필수 모니터와 데이터가 끊겨도 알림을 내지 않던 다운 감시를 확인했습니다. APM을 제거하는 순서를 정하는 과정에서는 로그의 에러 분류도 확인해야 했어요.

로그에서는 원본과 수집 결과를 대조하고, 모니터와 아카이브의 조건을 실제 로그로 검색해 문제를 확인했어요. 당시 모니터 대부분과 로그 아카이브, 반복 다운타임은 코드로 옮긴 상태였고, 알림 경로와 서비스 카탈로그, 대시보드, 로그 파이프라인 전체의 편입은 11월까지의 로드맵에 남아 있었습니다.

✍️ 오늘의 요약
JSON 로그가 한 건으로 합쳐진 원인은 multi_line 규칙과 로그 형식의 불일치였어요. 1초 안에 이어진 줄이 합쳐지고 첫 JSON의 레벨만 남아, 수집 설정과 에러 모니터 임계값을 함께 고쳤습니다.

평문 로그에는 레벨을 status로 옮기는 파이프라인을 만들고, 모니터와 아카이브 조건은 실제 로그로 검색해 확인했어요. 옛 서비스 이름을 참조하던 지표 네 개는 참조 여부를 확인한 뒤 삭제했고, 배치 실패 모니터는 새 이름과 실패 문구로 조건을 바꿨습니다. 파이프라인 규칙은 서비스별 하루치 로그 중 500건을 뽑아 대조했으며, 합쳐진 배치 로그를 분리한 뒤의 약 142건은 같은 3일 기준의 예상치였어요.
