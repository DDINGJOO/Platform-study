10월 1일 오전, 알림 경로를 코드로 가져오는 PR 의 plan 을 돌렸어요. 결과는 가져오기 33건, 변경 0건이었습니다. 콘솔에 있던 설정을 하나도 바꾸지 않고 코드 관리 아래로 옮겼다는 뜻이라, 받고 싶었던 결과 그대로였어요. 그런데 가져온 목록을 세어 보니 Slack 채널이 15개였습니다. 계획서에는 11개라고 적혀 있었어요.

숫자 하나가 틀린 건 작은 일이었습니다. 그날 오후에 붙잡은 문제가 더 컸어요. 모니터 메시지에 채널 이름을 한 글자 틀리게 적어도 plan 과 apply 는 둘 다 통과하고, Datadog 도 그 메시지를 받아 줍니다. 알림만 아무 데도 가지 않아요. 6편 끝에서 "알림 경로는 11월까지의 로드맵에 남아 있다"고 적었는데, 이 글은 그다음 날의 기록입니다. 질문은 이것이에요. "알림이 사람에게 닿는지는 언제, 무엇으로 확인하는가."

1. 모니터는 코드에 있는데, 알림이 가는 길은 콘솔에 있었다

9월 마지막 주까지 모니터는 거의 다 코드로 옮겼어요. 그런데 모니터가 하는 일은 조건을 보고 메시지를 만드는 데까지입니다. 그 메시지가 누구에게 가는지는 메시지 안에 적힌 핸들이 정해요.

📖 용어: 핸들 (알림 대상 표기)
모니터 메시지 안에 @ 로 시작하는 문자열을 적으면, Datadog 은 알림이 울릴 때 그 대상에게 메시지를 보내요. @slack-<채널> 은 Slack 채널로, @oncall-<팀> 은 그 팀의 온콜 당번에게 갑니다. 메시지 본문의 일부라서, 겉보기에는 그냥 글자예요.

핸들이 실제로 사람에게 닿으려면 그 뒤에 설정이 더 있어야 해요. @slack- 쪽은 Datadog 의 Slack 연동에 그 채널이 등록돼 있어야 하고, @oncall- 쪽은 팀, 라우팅 규칙, 에스컬레이션 정책, 스케줄이 차례로 이어져 있어야 합니다.

📖 용어: Slack 채널 연동
Datadog 이 메시지를 보낼 수 있는 Slack 채널 목록이에요. 채널마다 알림에 그래프 스냅샷이나 음소거 버튼을 붙일지도 여기서 정합니다. 이 목록에 없는 채널 이름을 핸들로 적으면 보낼 곳이 없어요.
📖 용어: 온콜 경로 (라우팅 규칙 · 에스컬레이션 정책 · 스케줄)
@oncall-<팀> 이 울리면 팀 라우팅 규칙이 어떤 에스컬레이션 정책을 쓸지 고르고, 정책은 "먼저 당번에게, 5분 안에 응답이 없으면 팀 전체에게" 같은 순서를 정하며, 스케줄은 오늘의 당번이 누구인지를 정해요. 하나라도 끊기면 호출이 사람에게 닿지 않습니다.

이 설정들이 전부 콘솔에만 있었어요. 모니터 코드는 리뷰를 거치는데, 그 모니터가 부르는 채널과 팀은 누가 언제 바꿔도 기록이 남지 않는 상태였습니다. 계획서의 4단계가 이것을 가져오는 일이었고, 일정은 10월 6~7일이었는데 앞당겨 10월 1일에 했어요(#818).

방법은 앞선 편들과 같았어요. Terraform 의 설정 생성 기능으로 콘솔의 실물을 코드로 뽑고, import 블록을 붙여 plan 을 돌린 뒤, 변경이 0 이 될 때까지 코드를 맞췄습니다.

📖 용어: 설정 생성 (-generate-config-out)
import 블록만 적어 두고 plan 에 이 옵션을 주면, Terraform 이 실물을 읽어 그 리소스의 코드를 파일로 써 줘요. 손으로 옮겨 적다 생기는 오타를 줄일 수 있지만, 나온 코드는 ID 가 문자열로 박힌 날것이라 다듬어야 합니다.

다듬은 것은 ID 였어요. 생성된 코드에는 팀, 스케줄, 정책이 서로를 긴 ID 문자열로 가리키고 있었습니다. 이것을 리소스 참조로 바꿨어요. 가리키는 값이 같으니 plan 의 차이는 0 으로 유지됩니다.

resource "datadog_on_call_team_routing_rules" "platform" { id = datadog_team.platform.id # 예전: "{팀 ID}" rule { escalation_policy = datadog_on_call_escalation_policy.platform.id # 예전: "{정책 ID}" urgency = "dynamic" } }

→ "플랫폼팀이 호출되면 플랫폼팀 정책을 쓴다"는 규칙이에요. ID 문자열 대신 참조를 쓰면 코드만 읽어도 무엇이 무엇에 이어지는지 보이고, 팀을 지우려 할 때 그 팀을 쓰는 규칙이 있으면 Terraform 이 먼저 알려 줍니다. 사람(사용자) ID 는 사용자 편입 단계(10단계)까지 문자열로 남겼어요.

하나 더 확인한 게 있어요. 4편에서 다운타임을 코드로 다루다가 읽기 키에 권한이 없어 plan 과 drift 점검이 403 으로 멈춘 적이 있습니다. 그래서 이번에는 가져올 리소스 전부가 읽기 키로 조회되는지를 먼저 봤어요. 결과는 팀 6, 온콜 스케줄 2, 에스컬레이션 정책 5, 팀 라우팅 규칙 5, Slack 채널 15, 합쳐서 가져오기 33건, 변경 0건이었습니다. 다음 PR(#819)에서 import 블록을 지웠어요.

2. 계획서의 11 은 실물의 숫자가 아니었다

9월 27일에 API 로 전수 조회해 세운 계획서에는 "Slack 채널 (모니터가 참조) 11"이라고 적혀 있었어요. 가져와 보니 연동에 등록된 채널은 15개였습니다. 그럼 모니터가 쓰는 채널은 11개였을까 싶어 코드의 핸들을 세어 보니 그것도 아니었어요.

연동에 등록된 채널 15 모니터 코드에 나오는 핸들 8가지 그중 같은 채널을 두 형식으로 @slack-{채널} / @slack-{워크스페이스}-{채널} 채널로 묶으면 7개 계획서 (9월 27일) 11

→ 핸들은 채널 이름만 쓰는 형식과 워크스페이스 이름을 앞에 붙이는 형식이 둘 다 통해요. 그래서 핸들 문자열로 세면 8가지, 가리키는 채널로 세면 7개입니다. 11 은 둘 중 어느 쪽과도 맞지 않았어요.

11 이 어떻게 나온 숫자인지는 기록에 남아 있지 않아요. 그래서 원인을 짐작해 적지는 않겠습니다. 분명한 건 이쪽이에요. 계획서의 개수는 그날 누군가가 센 값이고, plan 이 보여 주는 개수는 지금 실물에 있는 값입니다. 이번에 믿을 수 있었던 숫자도 실물을 읽어 들인 import plan 이 세어 준 15 였어요.

모니터가 쓰지 않는 채널 8개도 지우지 않고 그대로 가져왔어요. 가져오는 PR 과 바꾸는 PR 을 나눈다는 1편의 원칙 때문입니다. 같은 이유로, 가져오면서 눈에 띈 것도 바로 고치지 않고 코드 주석에 남겼어요. 팀 6개 가운데 둘이 하이픈 하나만 다른 이름이었고, 그중 하나에는 라우팅 규칙이 없었습니다. 2편에서 "온콜 재편 단계로 미뤘다"고 적은 그 중복이에요. 이건 5절에서 다시 나옵니다.

⚠️ 주의: 변경 0 은 "경로가 맞다"는 뜻이 아니다
import plan 의 변경 0 은 코드와 실물이 같다는 뜻일 뿐이에요. 실물이 틀려 있으면 틀린 그대로 같아집니다. 쓰지 않는 채널 8개와 라우팅 없는 팀 하나도 변경 0 으로 코드에 들어왔어요. 가져오기는 정리의 시작점이지, 정리가 끝났다는 증거가 아닙니다.

3. 없는 채널로 보낸 알림은 plan 을 통과한다

채널 목록을 코드로 가져오고 나니 오래 걸려 있던 질문 하나를 다시 볼 수 있었어요. 모니터 메시지에 이렇게 적으면 무슨 일이 생길까요.

# 형태를 보이려고 만든 예시. 등록된 채널 이름은 app-alert 이다 message = <<-EOT 🔴 [P1] 메인 API 다운 @oncall-{플랫폼팀 핸들} @slack-app-alret EOT

→ 채널 이름의 철자가 뒤집혔어요. plan 은 메시지 문자열이 바뀐다고만 보여 주고, apply 는 성공하며, Datadog 은 이 모니터를 저장합니다. 경고는 어디에서도 나오지 않아요.

Terraform 입장에서 메시지는 그냥 문자열입니다. 문자열 안의 @slack- 뒤에 무엇이 오든 문법은 맞아요. Datadog 도 모니터를 저장할 때 쿼리의 모양은 검사하지만, 메시지 속 핸들이 등록된 채널인지는 막지 않았습니다. 그래서 이 모니터는 평소에 아무 문제가 없어 보여요. 문제가 드러나는 건 장애가 나서 알림이 울려야 하는 순간이고, 그때 채널에는 아무것도 오지 않습니다. 알림이 가지 않는다는 사실은 알림이 가야 할 때에야 드러나요.

이 시리즈에서 이미 같은 모양을 두 번 봤어요. 1편에서 정리한 고장 목록에는 알림 대상이 "@slack-당신의-온콜-채널-이름" 이라는 템플릿 문구 그대로인 RDS CPU 모니터가 있었습니다. 두 번째는 9월 30일 저녁에 인증 모니터의 채널을 옮긴 PR(#811)이에요. 그 커밋 메시지에는 이런 문장을 적어 두었습니다.

선행 조건: Datadog Slack 연동에 #{인증 알림 채널} 이 등록되어 있어야 한다. 등록 전에 apply 하면 알림이 조용히 배달되지 않는다.

→ 위험을 알고 있었지만, 막는 장치는 커밋 메시지 한 줄과 apply 하는 사람의 기억뿐이었다는 뜻이에요.

그림 1. 핸들이 등록된 채널인지는 저장할 때가 아니라 알림을 보낼 때 갈린다

@oncall-<팀> 도 같아요. 없는 팀 핸들을 적어도 모니터는 저장되고, 호출은 어디에도 닿지 않습니다. 그리고 2편에서 정한 규약대로 모니터의 team 태그도 Datadog 팀 핸들이어야 하는데, 여기에 없는 팀 이름을 적어도 역시 아무 오류가 나지 않아요.

4. 가드는 API 를 부르지 않고 코드만 읽는다

계획서에서 이 검사는 9단계(10월 26~27일)였어요. 알림 경로를 가져온 날 오후에 바로 만들었습니다(#837). 그 순서에는 이유가 있었어요. 검사하려면 "등록된 채널과 팀의 목록"이 있어야 하는데, 그 목록이 오전에 코드로 들어왔기 때문입니다.

📖 용어: 가드와 린트 잡
이 저장소에서 가드는 PR 이 머지되기 전에 도는 검사 스크립트예요. 여러 가드를 한 스크립트로 묶어 CI 의 린트 잡이 돌리고, 하나라도 실패하면 PR 이 막힙니다. 린트 잡은 클라우드 자격증명 없이 도는 것이 전제예요.

검사 규칙은 셋이에요.

1. 모니터 메시지의 @slack-<채널> 은 코드에 등록된 Slack 채널이어야 한다 (@slack-{워크스페이스}-<채널> 형식도 같은 채널로 본다) 2. @oncall-<팀> 과 team:<핸들> 태그는 코드에 있는 Datadog 팀의 핸들이어야 한다 3. 서비스 카탈로그 정의에는 소유 팀(owner)이 있어야 하고, 그 값도 팀 핸들이어야 한다

→ "코드에 등록된"이 핵심이에요. 검사 대상인 모니터 코드와 비교 기준인 채널·팀 목록이 같은 저장소 안에 있으니, 파일만 읽으면 됩니다.

방법은 두 가지를 놓고 볼 수 있었어요. 하나는 Datadog API 로 지금 등록된 채널 목록을 받아 와서 비교하는 것, 다른 하나는 저장소 안의 채널 리소스 정의와 비교하는 것입니다. 코드를 읽는 쪽을 택했어요. 그 결과로 생기는 차이는 셋이었습니다.

첫째, 자격증명이 필요 없어요. 린트 잡에는 Datadog 키가 없고, 키를 주는 순간 린트가 외부 상태에 따라 결과가 달라지는 검사가 됩니다. 코드만 읽는 검사는 같은 커밋이면 언제 돌려도 같은 결과가 나와요. 개발자 노트북에서도 키 없이 바로 돌릴 수 있습니다.

둘째, 새 채널을 쓰는 순서가 강제돼요. API 로 비교하면 누군가 콘솔에서 채널을 먼저 등록해 두었을 때 검사가 통과합니다. 코드와 비교하면 새 채널을 쓰려는 PR 이 그 채널의 등록 코드도 함께 담아야 통과해요. #811 의 커밋 메시지에 적었던 "등록 전에 apply 하면 조용히 배달되지 않는다"는 주의가, 사람이 기억할 문장에서 PR 이 통과해야 할 조건으로 바뀐 거예요.

셋째, 코드의 등록부가 실물과 어긋나는 경우는 다른 장치가 맡습니다. 누가 콘솔에서 채널 연동을 지우면 매일 도는 drift 점검이 코드와의 차이로 잡아요. 그래서 이 가드는 "코드끼리 맞는가"만 보면 됐습니다.

그림 2. 비교 기준이 같은 저장소에 있으니 키 없이 PR 단계에서 막을 수 있다

범위도 정했어요. 메시지 안의 ${var.slack} 같은 보간값은 건너뜁니다. 모듈 안에서는 값이 변수라 알 수 없고, 실제 값은 모듈을 부르는 쪽 코드에 문자열로 적히니 거기서 검사돼요. 대시보드는 대상에서 뺐습니다. 대시보드 정의에는 위젯 쿼리 속에 team: 이 데이터를 거르는 조건으로 섞여 있어서, 소유 표시와 구분하기 어렵기 때문이에요.

검사 규칙 자체가 틀리면 검사는 조용히 아무것도 잡지 않아요. 그래서 자기검사도 같이 넣었습니다.

📖 용어: 자기검사 (selftest)
저장소 파일을 읽지 않고, 스크립트 안에 적어 둔 예시 문자열에 규칙을 돌려 기대한 개수만큼 위반이 나오는지 보는 검사예요. 정규식을 고치다 규칙이 무너지면 실제 코드가 아니라 이 단계에서 먼저 실패합니다.

자기검사에는 맞는 핸들, 철자가 틀린 채널, 없는 팀, 보간값, 주석 속 핸들, 쿼리 속 팀 조건 같은 경우를 넣어 각각 위반 개수를 정해 두었어요. 처음 돌렸을 때 실제 코드의 위반은 0건이었습니다. 철자를 틀린 채널 핸들을 일부러 넣어 보니 잡혔어요.

💡 실무에서는: 새 채널로 알림을 보내려면
• 같은 PR 에 채널 등록 코드와 그 채널을 쓰는 모니터 수정을 함께 담습니다. 등록 없이 핸들만 바꾸면 린트가 막아요
• 린트 실패 메시지에는 등록된 채널과 팀 목록이 함께 찍혀서, 오타인지 미등록인지 바로 구분할 수 있습니다
• 팀 핸들을 바꿀 때도 같아요. 그 핸들을 쓰는 @oncall- 과 team: 이 같은 PR 에서 바뀌지 않으면 통과하지 못합니다
⚠️ 주의: 등록부는 Datadog 의 기록이지 Slack 의 실물이 아니다
이 가드가 확인하는 건 "Datadog 연동에 등록된 이름인가"까지예요. Slack 쪽에서 채널 이름이 바뀌거나 채널이 보관 처리된 것은 모릅니다. 실제로 가져온 15개 안에는 Slack 에서 이름을 바꾸기 전의 옛 채널 이름도 그대로 들어 있었어요. 알림이 정말 도착하는지는 결국 실제로 한 번 울려 보는 것으로만 확인됩니다.

5. 없는 팀을 가리키는 태그와 아무도 쓰지 않는 팀

가드를 만들면서 코드 전체의 team: 값을 훑었어요. 그러다 대시보드 하나의 소유 태그가 team:{없는 팀 이름} 인 것을 봤습니다. 그런 이름의 Datadog 팀은 없었어요. 대시보드는 가드의 범위 밖이라 검사로 잡힌 건 아니고, 가드 PR 의 커밋 메시지에 별건 발견으로 적어 두었어요.

같은 날 저녁에 이것과 2절에서 미뤄 둔 중복 팀을 함께 정리했어요(#841).

- tags = ["team:{없는 팀 이름}"] # 인증 지표 대시보드 + tags = ["team:{인증 담당 팀 핸들}"] - resource "datadog_team" "server_dev_hyphen" { - handle = "{서버-팀}" # "{서버팀}" 과 하이픈 하나 차이 - }

→ 없는 팀을 가리키던 소유 태그를 실제 팀으로 바꾸고, 중복 팀 하나를 지웠다는 뜻이에요.

중복 팀은 어느 쪽을 지울지가 문제였어요. 이름만 보면 둘 다 그럴듯했습니다. 그래서 참조를 셌어요. 하이픈이 있는 쪽은 모니터, 온콜 라우팅 규칙, 에스컬레이션 정책, 대시보드 어디에서도 쓰이지 않았습니다. 라우팅 규칙이 5개뿐이고 팀이 6개였던 이유도 이 팀이었습니다. 라우팅 규칙이 없으니 이 팀으로 호출을 걸어도 정책으로 이어지지 않는 상태였죠. 지우기 전에 걸린 것이 하나 있었어요. 이 팀에만 있고 남는 팀에는 없는 멤버가 한 명 있었습니다. 그때 팀 멤버십은 코드 밖이라, 필요하면 콘솔에서 남는 팀에 추가하라고 커밋에 적어 두었어요.

이름이 맞는지는 사람이 보면 그럴듯하고, 기계로 대조해야 틀린 것이 나옵니다. 없는 팀 이름도, 하이픈 하나 차이의 팀도, 콘솔 화면에서는 멀쩡해 보였어요.

6. 사람의 대화와 기계의 알림을 가른다

가드가 생기기 전 이틀 동안, 채널을 옮기는 PR 두 개가 이미 메시지 속 핸들을 손봐 두었어요. 둘 다 가드 없이 사람이 확인한 작업이었습니다.

9월 29일의 #739 는 플랫폼팀이 임시로 받는 알림을 둘로 갈랐어요. 3편에서 만든 필수 모니터 모듈은 알림 채널 변수가 하나뿐이라 다운, 에러율, 지연, 메모리가 모두 인프라 채널 하나로 갔습니다. 여기에 인프라용 변수를 하나 더 두었어요.

#{앱 알림 채널} 앱 계층: 다운 · 에러율 · 지연 · 실행 침묵, 앱 에러 로그 #{인프라 채널} 인프라 계층: 메모리 포화 · 컨테이너 CPU · DB 커넥션

→ 앱이 이상한지, 앱이 올라선 자원이 이상한지에 따라 받는 채널을 나눴다는 뜻이에요. 담당 팀으로 넘길 때는 앱 채널 쪽 변수만 바꾸면 됩니다.

이때 옛 핸들도 정리했어요. 배치 실패 P1 과 DB 커넥션 P1 두 모니터가 Slack 에서 채널 이름을 바꾸기 전의 옛 이름을 핸들로 쓰고 있었습니다. 둘을 각각 앱 채널과 인프라 채널로 옮겼어요. DB 커넥션은 RDS 의 문제라 인프라 쪽입니다.

9월 30일의 #811 은 인증 쪽이었어요. 인증 모니터 10개가 인증 담당자들이 대화하는 채널로 알림을 보내고 있었습니다. 메시지 안의 멘션 17곳을 인증 알림 전용 채널로 바꿨어요. 같은 날 인증 리포트도 웹훅을 바꿔 이 채널로 옮겼습니다. 조건과 임계값은 그대로 두고 메시지만 바꿨어요.

- @slack-{인증 대화 채널} # 사람이 대화하는 채널 + @slack-{인증 알림 채널} # 기계 알림만 받는 채널 (모니터 10개, 멘션 17곳)

→ 알림이 대화 사이에 섞이면 대화가 알림에 밀려 올라가고, 알림은 대화 사이에서 놓칩니다. 채널을 가르면 알림 채널은 "울린 것"의 기록이 되고, 대화 채널은 대화만 남아요.

두 PR 은 모두 핸들 문자열을 고치는 일이었어요. 다음 날 가드가 위반 0 을 냈으니, 고친 핸들이 전부 등록된 채널을 가리킨다는 확인은 됐습니다. 다만 이건 이틀 늦은 확인이에요. #811 을 apply 할 때는 그 확인을 커밋 메시지의 "선행 조건" 한 줄이 대신하고 있었습니다.

거꾸로는 성립하지 않아요. 옮기기 전의 옛 핸들, 그러니까 이름을 바꾸기 전의 채널과 인증 담당자들의 대화 채널도 연동 목록 15개 안에 그대로 남아 있었습니다. 두 PR 이 없었더라도 가드는 위반 0 을 냈을 거예요. 가드가 보는 건 "보낼 곳이 있는가"이고, "맞는 곳으로 가는가"는 사람이 정합니다.

💡 실무에서는: 채널을 가르는 기준
• 받는 사람이 다르면 채널을 가릅니다. 앱 알림과 인프라 알림은 먼저 볼 화면이 달라요
• 사람이 대화하는 채널에는 기계 알림을 보내지 않습니다. 대화와 알림이 서로를 묻어요
• 채널을 옮기는 PR 에서는 조건·임계값을 건드리지 않습니다. 메시지만 바뀐 diff 여야 리뷰가 쉬워요

이날 알림 경로를 가져오면서 계획서의 마일스톤 하나도 같이 넘었어요. "알림이 안 가거나 태그가 사전 밖인 모니터는 PR 에서 차단"이라는 M3 는 10월 27일이 목표였는데, 작업 기록에는 10월 1일에 이 가드로 달성했다고 적었어요. 알림 경로를 먼저 코드로 가져온 덕분에 가능한 순서였습니다. 다만 이 가드가 사전과 대조하는 태그는 team 하나뿐이에요. service 같은 다른 태그가 규약 안에 있는지는 이 가드가 보지 않습니다.

✍️ 오늘의 요약
모니터 메시지의 채널·팀 핸들은 그냥 문자열이라, 없는 이름을 적어도 plan, apply, Datadog 저장을 모두 통과하고 알림만 아무 데도 가지 않는다.

알림 경로(팀 6, 스케줄 2, 정책 5, 라우팅 규칙 5, Slack 채널 15)를 변경 0 으로 코드로 가져온 뒤, 같은 날 그 목록과 모니터 코드를 대조하는 가드를 붙였다. API 대신 코드를 읽어서 키 없이 돌고, 새 채널은 등록 코드와 함께 들어와야 통과한다. 계획서의 개수도, 그럴듯한 팀 이름도, 대조해 보기 전에는 맞는지 알 수 없었다. 알림이 닿는지는 울려야 할 때 확인하면 늦다.
