2편. 8주치 82,918건을 전부 셌다

보안 설정 파일을 다시 열었습니다. 보호할 경로들이 위에 줄줄이 적혀 있고, 그 아래에 /api/** 를 통과시키는 줄이 하나 있었어요. 규칙은 위에서부터 읽히니까, 위에 걸리지 않은 요청은 전부 그 줄에서 통과됩니다. 읽는 순서로는 "막을 것만 골라 막고, 나머지는 열어 둔다" 였어요.

이 구조에서 새 경로를 하나 추가하면 어떻게 될까요. 아무것도 적지 않아도 잘 동작합니다. 테스트도 통과하고, 호출도 되고, 리뷰에서도 걸릴 이유가 없어요. 인증을 한 번도 떠올리지 않아도 열린 채로 배포까지 갑니다.

1편에서 넣어 둔 관찰 필터가 25일 동안 기록을 쌓아 줬습니다. 그 기록을 집계해 공개 목록 밖으로 들어온 익명 요청이 0건인 걸 확인한 뒤에 기본값 자체를 뒤집었어요. 그리고 되돌릴 스위치를 같이 넣었습니다.

🧭 이 글에서 다룰 것
• "인증을 빠뜨렸다"는 사실은 왜 아무 데도 드러나지 않나?
• 기본값을 뒤집기 전에 무엇을 세야 했나?
• 기본 거부로 바꾸면 같은 실수가 어디로 떨어지나?
• 되돌림 스위치는 무엇을 되돌리고, 무엇은 되돌리지 못하나?
• 호출하는 쪽의 기본값도 바꿀 수 있나?

1. 빠뜨렸다는 사실이 아무 데도 남지 않았어요

기본 허용의 진짜 문제는 "열려 있는 경로가 있다" 가 아니에요. 빠뜨렸다는 사실이 어디에도 기록되지 않는다 는 겁니다.

경로를 하나 추가하면서, 그 경로가 인증을 요구하는지는 아무도 묻지 않아요. 묻지 않아도 되니까요. 그래서 이건 사람이 꼼꼼하지 못해서 생기는 일이 아니라, 구조가 질문을 만들어 내지 않아서 생기는 일이었어요.

📖 용어: 익명 요청 (anonymous request)
로그인 정보나 토큰을 하나도 달고 오지 않은 요청이에요. 기본 허용 설정에서는 이런 요청도 그냥 통과하기 때문에, 응답만 봐서는 정상 호출과 구분되지 않습니다.

1편에서 본 것도 같은 모양이었어요. /api/** 아래가 통째로 열려 있는데, 누가 판단해서 연 건지 기본값이 남은 건지 아무도 설명하지 못했습니다. 설명할 기록이 애초에 만들어지지 않으니까요. 설정을 더 꼼꼼히 읽는 것으로는 줄지 않는 종류예요. 같은 실수가 닫히는 쪽으로 떨어지게 만들어야 했습니다.

2. 뒤집기 전에 먼저 셌어요

기본값을 거부로 바꾸는 작업 자체는 설정 몇 줄이에요. 어려운 건 지금 들어오는 호출 중 무엇이 끊기는지 모른다 는 점입니다.

공개로 열려 있던 경로 중에는 실제로 공개여야 하는 것도 섞여 있습니다. 상태 점검 호출이나 토큰을 받기 전에 부르는 경로 같은 것들이요. 목록을 눈으로 만들어 뒤집으면, 빠뜨린 경로는 그 순간 끊깁니다.

그래서 1편에서 관찰 필터를 먼저 넣었어요. 요청을 막지 않고 통과시키면서, 인증 정보 없이 들어왔다는 사실만 기록하는 장치입니다. 차단하지 않으니 동작은 그대로인데, "바꾸면 무엇이 끊기는가" 는 미리 알 수 있어요.

세는 태도는 2편과 같았어요. 표본이 아니라 전부를 봅니다. 다만 출처도 기간도 다릅니다. 2편이 센 것은 리버스 프록시의 접근 로그라 보관본까지 꺼내 8주를 덮었어요. 여기서 세는 건 애플리케이션에 넣은 관찰 필터의 태그라, 필터가 들어간 날부터만 쌓입니다. 필터를 넣고 기본값을 뒤집기까지가 25일, 약 3주 반, 그게 제가 볼 수 있었던 전부였어요.

25일치 집계 · 관찰 필터 태그 기준 (필터를 넣은 날 ~ 기본값을 뒤집은 날. 2편의 8주와는 출처가 다릅니다) 공개 목록 안으로 들어온 익명 요청 .... 태그가 붙은 전량 공개 목록 밖으로 들어온 익명 요청 .... 0 건 -> 이 25일 안에서는, 기본값을 거부로 바꿔도 끊기는 호출이 없다

→ 익명 호출이 모두 "공개여도 되는 경로" 안에서만 들어온다는 뜻이에요. 목록 밖에서 한 건이라도 있었다면, 그건 전환하는 순간 끊길 호출이었습니다. 다만 이 0건은 25일치 0건이에요.

⚠️ 적어 놓고 제가 못 지킨 기준
이 글 끝에 저는 "관찰 기간은 업무 주기를 덮어야 한다" 고 적어 뒀어요. 그런데 실제 관찰 창은 25일, 한 달도 안 됩니다. 월 1회 배치가 있었다면 이 창 밖이었을 거예요
25일이 충분해서 전환한 게 아니에요. 되돌리는 비용을 먼저 낮춰 놓고 모자란 기간을 감수한 겁니다. 되돌림 스위치는 덤이 아니라, 이 짧은 창으로 전환하려면 먼저 갖춰야 했던 조건이었어요
그림 1. 관찰이 먼저이고 전환은 그 결과다

3. 기본값을 거부로 뒤집었어요

근거가 생겼으니 바꿨습니다. 바뀐 건 두 줄의 역할이에요.

전환 전 기본 허용 보호할 경로 목록 authenticated <- 따로 적는다 (위) "/api/**" permitAll <- 걸러지지 않은 나머지 새 경로를 추가하고 아무것도 적지 않으면 -> permitAll 전환 후 기본 거부 공개할 경로 목록 permitAll <- 따로 적는다 (위) anyRequest() authenticated <- 걸러지지 않은 나머지 새 경로를 추가하고 아무것도 적지 않으면 -> authenticated

→ 목록에 적는 대상이 "막을 것" 에서 "열 것" 으로 바뀌었어요. 길이는 비슷한데 의미가 반대입니다.

📖 용어: anyRequest().authenticated() 와 permitAll
Spring Security 의 경로별 접근 규칙이에요. 규칙은 위에서부터 읽히고, 먼저 걸리는 규칙이 이깁니다. permitAll 은 "이 경로는 인증 없이 통과" 고, 맨 마지막의 anyRequest().authenticated() 는 "위에서 아무 규칙에도 걸리지 않은 나머지 전부는 인증이 필요하다" 예요. 즉 마지막 한 줄이 기본값 역할을 합니다.

이제 새 경로를 만들면서 인증을 생각하지 않으면 호출이 401로 막힙니다. 만든 사람이 바로 알게 돼요. 같은 실수인데 떨어지는 곳이 반대가 된 겁니다.

다만 그 경로가 공개 목록에 걸리지 않았을 때만 그렇습니다. 전환 뒤에도 공개 목록은 위에 남아 있고, 넓은 패턴으로 적힌 줄이 덮는 범위 안에서는 기본 허용이 살아 있어요. 새 경로가 하필 그 안으로 들어가면 401은 뜨지 않습니다. 저희도 예외로 남긴 공개 경로가 네 개였고, 일부는 검토 끝에 지우지 않기로 정했어요.

그러니 기본값을 뒤집어도 공개 목록은 여전히 사람이 읽고 줄여야 하는 목록입니다. 바뀐 건 "안 적으면 열린다" 가 "안 적으면 막힌다" 로 된 데까지예요.

📖 용어: 401 과 403
401은 "누구인지 모르겠다" 고, 403은 "누구인지는 알겠는데 권한이 없다" 예요. 기본 거부로 바꾼 뒤 설정을 빠뜨린 경로는, 인증 정보가 없는 익명 요청에 401을 돌려줘요. 로그인은 했는데 권한이 모자란 경우라면 403이고요. 조용히 통과하는 대신 응답 코드로 말해 주는 겁니다.
그림 2. 기본값이 바뀌면 빠뜨림의 결과가 공개에서 차단으로 바뀐다

4. 되돌림 스위치를 같이 넣었어요

0건이라고 해서 안전하다고 단정할 수는 없었어요. 25일을 비켜 간 배치가 있을 수도 있고, 공개 목록을 옮겨 적으면서 한 줄을 흘렸을 수도 있습니다. 둘 다 전환한 뒤에야 드러나요.

그래서 되돌아갈 길을 같이 만들었습니다. 설정값 하나로요.

security.api-default-authenticated=true 기본 거부 (기본값, 현재 값) security.api-default-authenticated=false 이전 동작 (기본 허용) 참이면 anyRequest().authenticated() 거짓이면 "/api/**" 을 permitAll -> 두 모양을 코드에 둘 다 남겨 두고 설정값으로 고른다

→ 이 값이 false 면 전환 전 구성으로 돌아갑니다. 규칙은 기동할 때 짜이니까 다시 띄워야 하지만, 코드를 되돌려 빌드와 배포를 다시 태울 필요는 없어요.

📖 용어: 되돌림 스위치
새 동작과 옛 동작을 코드에 둘 다 남겨 두고, 설정값 하나로 어느 쪽을 쓸지 고르게 만드는 방식이에요.
그림 3. 되돌리는 비용이 전환을 결정할 수 있는 범위를 정한다
⚠️ 주의: 스위치는 시간을 벌어 줄 뿐이에요
• false 로 내리면 끊긴 호출은 되살아나지만, 열려 있던 상태로 같이 돌아갑니다. 되돌림은 해결이 아니라 조사할 시간을 버는 수단이에요
• 되돌린 사실이 눈에 띄게 남아야 해요. 값이 조용히 false 인 채로 몇 주가 지나면 전환을 한 적이 없는 것과 같아집니다
• 스위치는 임시 상태예요. 안정이 확인되면 옛 경로를 지우는 것까지가 한 작업입니다

5. 호출하는 쪽의 기본값도 바꿨어요

같은 생각을 서버 간 호출 쪽에도 적용했습니다. {연동 서버}로 나가는 호출에는 API 키 헤더를 실어야 했는데, 그동안은 호출하는 코드가 매번 붙이는 구조였어요. 새 호출을 추가하는 사람이 키를 기억해야 했습니다. 그래서 호출 클라이언트를 고쳐, 모든 호출에 키 헤더를 기본으로 싣게 했어요.

앞의 전환과 방향은 반대예요. 받는 쪽은 "안 적으면 막힌다" 로, 거는 쪽은 "안 적어도 붙는다" 로 바꿨습니다. 기준은 같아요. 사람이 기억해야 동작하는 자리를 기본값으로 옮긴다.

6. 바뀐 것은 실수의 양이 아니라 방향이에요

인증 설정을 빠뜨리는 일이 사라지지는 않아요. 사람은 계속 빠뜨립니다. 바뀐 건 빠뜨렸을 때 어디로 떨어지느냐예요. 전에는 공개로, 지금은 차단으로 떨어집니다.

이 전환에서 제일 오래 걸린 건 설정을 고치는 일이 아니었어요. 무엇이 들어오고 있는지 세는 일이었습니다. 먼저 뒤집고 나서 끊기는 걸 하나씩 찾았다면, 그건 전환이 아니라 사고였을 겁니다.

💡 실무에서는: 기본값을 뒤집기 전에
• 관찰부터 넣으세요. 막지 않고 기록만 하는 단계가 있어야 "바꾸면 무엇이 끊기는가" 에 숫자로 답할 수 있어요
• 관찰 기간은 업무 주기를 덮어야 해요. 월말에만 도는 호출이 있다면 한 달로는 부족합니다. 저는 25일로 끊었으니 이 기준을 못 지킨 셈이고, 그래서 되돌림 스위치가 선택이 아니라 전제 조건이었어요
• 되돌림 비용을 먼저 정하세요. 재배포가 필요하면 전환을 미루게 됩니다
• 공개 목록은 짧게 쓰세요. 넓은 범위로 한 줄 적어 두면 그 줄 안에서 기본 허용이 되살아납니다
✍️ 오늘의 요약
기본값을 허용에서 거부로 뒤집으면 실수의 방향이 바뀝니다. 인증 설정을 빠뜨렸을 때 전에는 열린 채로, 지금은 닫힌 채로 배포되고 401이 떠서 바로 드러나요. 다만 공개 목록에 걸리는 경로는 예외라, 그 목록은 여전히 사람 몫이에요.

뒤집을 수 있었던 건 먼저 셌기 때문이에요. 1편의 관찰 필터가 25일 동안 쌓은 기록을 집계해 공개 목록 밖 익명 요청이 0건인 걸 확인한 뒤에 바꿨고, 설정값 하나로 되돌아갈 길을 남겼어요. 25일은 제가 이 글에 적은 "업무 주기를 덮어라" 는 기준에 못 미칩니다. 모자란 만큼은 되돌림 스위치가 메웠어요.

안전한 기본값은 용기로 정하는 게 아니라 숫자로 정합니다. 무엇이 들어오는지 모르는 상태에서 기본값을 바꾸는 건 전환이 아니라 장애예요.
