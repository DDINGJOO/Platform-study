당시 보안 설정에는 인증이 필요한 경로가 먼저 적혀 있고, 그 아래에 /api/**를 허용하는 규칙이 있었어요. 앞선 규칙에 일치하지 않은 API 요청은 마지막 허용 규칙을 따르는 구성이었어요.

이 구성에서는 새 API 경로를 추가하면서 인증 규칙을 빠뜨려도 익명 요청이 통과할 수 있어요. 호출 성공만 확인하는 테스트로는 인증 설정이 빠졌다는 사실을 알아보기 어려워요.

기존 작업 기록에는 1편에서 넣은 관찰 필터의 25일치 로그를 집계해 공개 목록 밖 익명 요청이 0건인 것을 확인한 뒤 기본값을 바꿨다고 남아 있어요. 설정값으로 이전 동작을 선택하는 되돌림 스위치도 함께 뒀어요. 아래의 집계와 전환은 당시 기록을 기준으로 설명하며, 이번 문체 수정에서 원본 로그나 운영 설정을 다시 확인한 결과는 아니에요.

🧭 전환할 때 확인한 항목
• 기본 허용에서 인증 설정 누락을 알아보기 어려운 이유
• 기본값을 바꾸기 전에 집계한 요청과 관찰 기간
• 인증을 기본으로 요구할 때 달라지는 동작과 예외
• 되돌림 스위치의 동작과 제약
• 서버 간 호출의 API 키 헤더 기본값

1. 호출 성공만으로는 인증 누락을 알기 어려웠어요

공개 경로 중에는 인증 없이 호출할 수 있어야 하는 경로도 있어요. 문제는 공개 여부를 검토한 경로와 인증 설정을 빠뜨린 경로가 같은 허용 규칙을 따를 수 있다는 점이었어요.

새 경로가 정상 응답을 보냈다는 사실만으로 인증 필요 여부도 검토했다고 볼 수는 없어요. 개별 설정을 확인하는 것과 함께, 설정을 빠뜨렸을 때 익명 요청이 통과하는 기본 동작을 바꿀 필요가 있었어요.

📖 용어: 익명 요청 (anonymous request)
여기서는 로그인 정보나 토큰 없이 들어온 요청을 뜻해요. 기본 허용 규칙을 따르는 경로라면 이런 요청도 통과할 수 있어, 성공 응답만으로 인증 여부를 구분하기 어려워요.

1편에서 살핀 /api/** 허용 규칙도 같은 문제였어요. 이 규칙에 도달한 요청이 통과한다는 것은 알 수 있었지만, 각 경로를 공개한 이유까지 설정에서 알 수는 없었어요. 공개할 경로를 따로 적고, 나머지는 인증을 요구하도록 바꾸려 했어요.

2. 전환 전에 익명 요청을 집계했어요

설정은 몇 줄만 바꾸면 됐지만, 먼저 기존 호출 중 어떤 요청이 차단될지 확인해야 했어요.

상태 점검이나 토큰을 받기 전에 호출하는 경로는 인증 없이 접근해야 할 수 있어요. 공개 목록을 설정만 보고 작성하면 이런 경로를 빠뜨려 전환 후 호출을 차단할 수 있었어요.

그래서 1편에서는 요청을 차단하지 않고 익명 요청을 기록하는 관찰 필터를 먼저 넣었어요. 그 기록으로 공개 목록 밖에서 들어오는 익명 호출이 있는지 살폈어요.

2편과 마찬가지로 집계 대상 기록 전체를 봤지만, 출처와 기간은 달랐어요. 2편은 당시 단일 리버스 프록시 접근 로그에 남아 있던 약 8주를 살폈어요. 여기서는 애플리케이션 관찰 필터의 태그를 집계했기 때문에 필터를 넣은 날부터 기록이 있었어요. 기본값을 바꾸기까지 관찰한 기간은 25일, 약 3주 반이었어요.

25일치 집계 · 관찰 필터 태그 기준 (필터를 넣은 날 ~ 기본값을 뒤집은 날. 2편의 8주와는 출처가 다릅니다) 공개 목록 안으로 들어온 익명 요청 .... 태그가 붙은 전량 공개 목록 밖으로 들어온 익명 요청 .... 0 건 -> 이 25일 안에서는, 기본값을 거부로 바꿔도 끊기는 호출이 없다

위 블록은 당시 글에 남은 집계 설명이에요. 다만 1편의 관찰 필터는 공개 목록 안 요청을 기록 대상에서 제외한다고 설명해요. 따라서 같은 목록을 기준으로 했다면 위의 “목록 안 요청에 태그가 붙은 전량”과 맞지 않아요. 관찰 당시 목록과 전환 시점 목록의 관계, 집계 조건을 확인할 원본이 없어 이 차이는 해소하지 못했어요. 이 태그만으로 전체 익명 요청이나 공개 목록 안 요청 전량을 셌다고 볼 수는 없으며, 목록 밖 0건도 기존 기록의 결과로 한정해 읽어야 해요. 관찰 기간 이후에도 차단될 호출이 없다는 뜻은 아니에요.

⚠️ 25일로는 한 달 주기를 확인할 수 없었어요
25일은 한 달보다 짧아서 월 1회 배치가 실행되지 않은 기간일 수 있어요. 업무 주기 전체를 확인하기에 충분했다고 볼 수는 없어요.
당시에는 설정값으로 이전 동작을 선택할 수 있게 한 뒤 전환했어요. 되돌림 수단을 준비했어도 관찰하지 못한 기간의 호출까지 확인한 것은 아니에요.
그림 1. 관찰 필터의 25일치 집계를 확인한 뒤 전환했어요

3. 공개 목록 밖 요청은 인증을 요구하도록 바꿨어요

당시 집계 결과를 확인한 뒤 접근 규칙을 바꿨어요. 기존에 보호할 경로를 따로 적던 구성을, 공개할 경로를 따로 적는 구성으로 바꿨어요.

전환 전 기본 허용 보호할 경로 목록 authenticated <- 따로 적는다 (위) "/api/**" permitAll <- 걸러지지 않은 나머지 새 경로를 추가하고 아무것도 적지 않으면 -> permitAll 전환 후 기본 거부 공개할 경로 목록 permitAll <- 따로 적는다 (위) anyRequest() authenticated <- 걸러지지 않은 나머지 새 경로를 추가하고 아무것도 적지 않으면 -> authenticated

명시한 공개 경로에는 익명 접근을 허용하고, 나머지는 인증을 요구하는 구성이에요. 여기서 말하는 기본 거부는 모든 요청을 거절한다는 뜻이 아니라 익명 접근을 기본으로 허용하지 않는다는 뜻이에요.

📖 용어: anyRequest().authenticated()와 permitAll
Spring Security의 경로별 접근 규칙이에요. 선언 순서대로 비교해 처음 일치하는 규칙을 적용해요. permitAll은 해당 인가 규칙에서 인증을 요구하지 않고, 마지막의 anyRequest().authenticated()는 앞선 규칙에 일치하지 않은 나머지 요청에 인증을 요구해요.

당시 구성에서는 새 경로가 공개 목록에 일치하지 않으면 인증 정보가 없는 호출에 401을 반환하도록 했어요. 인증 규칙을 빠뜨려도 익명 접근을 허용하던 기본 동작을 바꾼 거예요.

다만 공개 목록의 패턴에 일치하는 경로에는 그 허용 규칙이 먼저 적용돼요. 넓은 패턴에 새 경로가 포함되면 마지막 인증 요구 규칙으로 차단되지 않아요. 당시 기록에는 공개 예외가 네 개였고, 일부는 검토 뒤 유지하기로 했다고 남아 있어요. 현재 예외 목록을 다시 확인한 결과는 아니에요.

그래서 전환 후에도 공개 목록의 범위를 검토해야 해요. 기본 인증 요구만으로 공개 예외의 적절성이나 경로별 세부 권한까지 확인되는 것은 아니에요.

📖 용어: 401과 403
401은 인증이 필요한 요청에 유효한 인증 정보가 없음을, 403은 접근이 거부됐음을 나타내요. 당시 API에서는 익명 요청의 인증 실패를 401로 설명했어요. 다만 인증을 요구하는 설정 한 줄만으로 응답 코드가 항상 401이 되는 것은 아니며, 실제 응답은 인증 실패 처리 설정에도 달려 있어요.
그림 2. 공개 목록 밖의 익명 요청은 인증 규칙을 따르게 돼요

4. 되돌림 스위치를 같이 넣었어요

관찰 결과가 0건이어도 전환 뒤 모든 호출이 정상일 것이라고 단정할 수는 없었어요. 25일 동안 실행되지 않은 배치가 있거나, 공개 목록을 옮기는 과정에서 필요한 경로를 빠뜨렸을 수 있었어요.

그래서 이전 접근 규칙을 코드에 남겨 두고 설정값으로 선택할 수 있게 했어요. 아래 블록의 현재 값 표기는 당시 기록 기준이에요.

security.api-default-authenticated=true 기본 거부 (기본값, 현재 값) security.api-default-authenticated=false 이전 동작 (기본 허용) 참이면 anyRequest().authenticated() 거짓이면 "/api/**" 을 permitAll -> 두 모양을 코드에 둘 다 남겨 두고 설정값으로 고른다

이 값을 false로 바꾸면 전환 전 규칙을 선택해요. 당시 구현은 시작할 때 접근 규칙을 구성하므로 설정을 반영하려면 애플리케이션을 다시 시작해야 했어요. 이전 코드를 복구해 다시 빌드하는 절차는 줄일 수 있지만, 재시작까지 없어지는 방식은 아니에요.

📖 용어: 되돌림 스위치
새 동작과 이전 동작을 코드에 남겨 두고 설정값으로 선택하는 방식이에요. 이 구현에서는 설정 변경 후 재시작이 필요했어요.
그림 3. 설정값으로 새 규칙과 이전 규칙을 선택할 수 있게 했어요
⚠️ 되돌리면 이전 허용 규칙도 적용돼요
• false로 바꾸면 이전 허용 규칙도 다시 적용돼요. 전환으로 차단된 호출을 복구하기 위한 임시 조치이며, 공개 목록 누락의 원인을 고치는 일은 따로 필요해요.
• 되돌렸다면 그 사실과 적용 값을 기록해야 해요. 값이 false인 동안은 새 기본 규칙을 적용한 상태가 아니에요.
• 안정화 뒤에는 이전 규칙과 스위치의 제거 여부를 검토해야 해요. 당시 이 후속 정리까지 끝났는지는 여기서 확인하지 못했어요.

5. 호출하는 쪽의 기본값도 바꿨어요

당시 기록에는 서버 간 호출도 함께 바꿨다고 남아 있어요. {연동 서버}에 필요한 API 키 헤더를 호출 코드마다 붙이던 방식에서, 해당 연동 클라이언트가 기본으로 붙이는 방식으로 바꿨어요. 이 변경의 구현이나 실제 배포를 이번에 다시 확인한 것은 아니에요.

요청을 받는 쪽에서는 인증을 기본으로 요구하고, 해당 연동 클라이언트에서는 필요한 키를 기본으로 붙이게 한 거예요. 두 변경 모두 새 경로와 호출을 추가할 때 매번 같은 설정을 기억해야 하는 부분을 줄이려는 선택이었어요.

6. 관찰 범위와 공개 예외는 별도로 확인해야 해요

기본값을 바꿔도 설정 누락 자체가 없어지지는 않아요. 다만 공개 목록 밖에서는 익명 요청을 허용하지 않도록 바꿀 수 있었어요. 공개 목록 안의 경로와 별도의 권한 검사는 계속 살펴야 해요.

당시에는 설정 수정에 앞서 어떤 호출이 들어오는지 집계하는 데 시간을 썼어요. 그래도 관찰 기간 밖의 호출은 알 수 없었고, 되돌림 수단을 준비했다는 이유만으로 그 한계가 사라지지는 않았어요.

💡 전환 전에 정리할 항목
• 차단 없이 기록하는 단계에서 공개 목록 밖 익명 요청이 있는지 확인해요.
• 관찰 기간에 월말·정기 배치 등 필요한 업무 주기가 포함됐는지 확인해요. 당시의 25일로는 한 달 주기를 확인할 수 없었어요.
• 되돌릴 때 필요한 설정 변경·재시작·빌드 절차를 구분하고, 적용 값을 기록해요.
• 공개 목록의 패턴이 필요한 경로보다 넓지 않은지 검토해요.
✍️ 전환 내용과 확인 범위
당시에는 관찰 필터의 25일치 기록에서 공개 목록 밖 익명 요청이 0건인 것을 확인한 뒤, 공개 경로 외에는 인증을 요구하도록 바꿨어요. 이전 규칙도 남겨 설정값과 재시작으로 선택할 수 있게 했어요.

25일은 한 달 주기를 확인하기에 짧았고, 되돌림 스위치가 그 관찰 한계를 없애지는 않았어요. 공개 예외의 범위와 되돌린 뒤 적용 값도 별도로 관리해야 했어요. 이 설명은 기존 작업 기록을 기준으로 하며, 원본 로그·당시 배포·현재 운영 설정과 후속 정리 완료 여부는 이번에 다시 확인하지 못했어요.
