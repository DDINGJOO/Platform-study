5편. 생성자 추가로 실패한 기동과 블루그린 배포의 공유 자원 부하 ← 지금 이 글

배포 후 새 버전이 건강검사를 통과하지 못하고 재시작을 반복했어요. 기존 버전이 요청을 처리하는 동안에도, 같은 호스트의 CPU 사용률은 올라갔어요.

그 배포에는 두 변경이 함께 들어 있었어요. 4편에서 계획한 분기별 호출 측정 로그와, 제휴 로그인에 쓰는 암호화 키를 코드 대신 시크릿 저장소에서 읽도록 바꾼 변경이에요. 이때 암복호화 유틸리티의 생성자가 늘었고, 새 버전은 요청을 받기 전에 기동에 실패했어요.

당시에는 생성자 선택을 명시해 기동 실패를 복구했어요. 배포 과정을 살피면서 실패 처리 경로의 결함도 발견했고요. 이보다 먼저 진행한 로그 마스킹에서는 직렬화 결과가 비어 있는 객체를 확인했어요. 아래 내용은 그때의 기록이며, 현재 운영 상태를 다시 점검한 결과는 아니에요.

🧭 확인할 지점
• 생성자 추가가 빈 생성에 미치는 영향
• 재시작하는 컨테이너가 공유 호스트에 주는 부하
• 정상 배포만으로 확인할 수 없는 실패 처리 경로
• 마스킹 전후 출력을 비교하다 발견한 직렬화 문제

1. 호출을 측정하려던 배포에서 새 버전이 기동하지 못했어요

측정 로그는 분기마다 호출이 들어올 때 한 줄씩 남겼어요. branch=PLAIN인지 branch=ENCRYPTED인지를 적고 식별자는 가렸어요. 4편의 45분 동안 17~31건은 실패한 배포에서 얻은 수치가 아니라, 복구 후 다시 배포해 얻은 값이에요.

로그는 값을 읽어 기록하는 변경이고, 키도 읽어 오는 위치만 바뀐다고 생각했어요. 암복호화 로직이 같으니 동작도 같을 거라고 보고 배포했지만, 객체 생성 방식이 달라지는 점을 놓쳤어요.

새 애플리케이션은 요청을 받기 전에 기동 도중 종료됐어요. 암복호화 연산을 실행하다 실패한 것이 아니라, 유틸리티 객체를 만드는 단계에서 멈췄어요.

2. 생성자 둘 중 사용할 것을 지정하지 않았어요

키를 코드 상수 대신 시크릿에서 읽도록 바꾸면서 시크릿 객체를 받는 생성자를 추가했어요. 문자열 키를 받던 기존 생성자는 테스트에서 쓰고 있어 남겨 뒀고요. 같은 클래스에 생성자가 두 개가 됐지만, 스프링이 사용할 생성자는 지정하지 않았어요.

📖 용어: 빈(bean)과 생성자 주입
스프링 컨테이너가 생성하고 관리하는 객체를 빈이라고 해요. 필요한 다른 객체를 생성자 인자로 전달하는 방식이 생성자 주입이에요. 생성자가 하나면 표시 없이도 사용할 수 있지만, 여러 개이고 우선 사용할 생성자나 기본 생성자도 없으면 @Autowired로 사용할 생성자를 지정해야 해요.

이 클래스에는 생성자가 둘이었고, @Autowired 표시도 인자 없는 기본 생성자도 없었어요. 로그에는 No default constructor found가 남았어요. 이 빈을 생성하지 못하면서 애플리케이션 기동도 실패했어요.

@Component class CryptoUtil { // 키를 받아 암복호화하는 유틸 // 운영용. 키를 시크릿에서 읽게 되면서 새로 생긴 생성자 CryptoUtil(KeySecrets secrets) { ... } // 테스트용. 문자열 키를 그대로 받던 원래 생성자 CryptoUtil(String key) { ... } } -> @Autowired 표시도, 인자 없는 기본 생성자도 없다 No default constructor found 로 빈 생성이 멈추고, 애플리케이션은 기동하지 못한다

암복호화 로직은 그대로였지만, 스프링이 이 클래스를 생성하는 조건은 달라졌다는 뜻이에요.

그림 1. 생성자가 둘이 된 뒤 사용할 생성자를 지정하지 못해 기동에 실패했어요

3. 트래픽을 넘기지 않아도 공유 호스트에는 부하가 생겼어요

블루그린 배포여서 처음에는 새 버전의 기동 실패가 기존 서비스에 영향을 주지 않을 거라고 생각했어요.

📖 용어: 블루그린 배포
기존 버전을 유지한 채 새 버전을 따로 실행하고, 정상 동작을 확인하면 트래픽을 넘기는 방식이에요. 이 배포에서는 새 버전이 건강검사를 통과하지 못해 기존 버전이 계속 요청을 처리했어요.

요청은 기존 버전이 계속 처리했어요. 다만 새 컨테이너는 종료되면 다시 시작하도록 설정돼 있어, 같은 지점에서 기동에 실패하고 재시작하는 동작이 반복됐어요.

애플리케이션은 기동할 때 클래스를 읽고 빈을 만들어요. 실패할 때까지 수행한 초기화 작업이 분 단위로 반복되면서 기존 버전과 공유하는 호스트의 CPU 사용률이 올라갔어요. 트래픽 전환이 없었다는 사실만으로 자원 영향까지 없다고 볼 수는 없었어요.

운영용 생성자에 @Autowired를 붙여 스프링이 사용할 생성자를 지정했어요. 테스트용 생성자는 남겨 문자열 키를 직접 넣을 수 있도록 했고요. 생성자가 둘이어서 표시를 명시했다는 주석도 남겼어요. 당시 기록에서는 이 수정 후 재배포했을 때 새 버전이 정상 기동했고, 재시작 반복이 멈췄어요.

그림 2. 새 버전의 재시작이 기존 버전과 공유하는 호스트에 부하를 줬어요
⚠️ 주의: 로그 추가와 함께 바뀐 생성자도 확인해요
• 기록할 값만 읽더라도 빈을 생성하는 방식이 달라졌는지 확인해요
• 이번에는 암복호화 연산이 그대로라는 이유로 생성자 변경의 영향을 놓쳤어요
• 로그를 추가하는 배포에도 기동 확인과 실패 시 절차가 필요해요

4. 되돌림 경로에는 실행 인자가 빠져 있었어요

복구 과정에서 배포 스크립트를 읽다가 실패 처리 경로도 확인했어요. 건강검사에 실패하면 기존 컨테이너를 다시 실행하는 부분인데, 실행에 필요한 인자 몇 개가 빠져 있었어요.

정상 배포에서는 이 경로를 실행하지 않아 누락이 드러나지 않았어요. 정상 경로가 동작했다는 결과만으로 되돌림 경로까지 확인됐다고 생각하면 안 되는 상황이었어요.

이후 다른 시스템의 배포 스크립트를 살피다가 비슷한 결함을 봤어요. 스크립트가 참조하는 컨테이너 이름이 실제 이름과 달라, 멈출 대상을 찾지 못하는 문제였어요. 이 발견은 위 기동 실패를 복구하던 작업과는 별개예요.

배포 스크립트 (단순화) 정상 경로 컨테이너 실행 + 환경변수 + 포트 전달 # 배포마다 실행된다 실패 경로 컨테이너 실행 # 거의 실행되지 않는다 ^ 환경변수와 포트가 빠져 있었다 다른 시스템 실제와 다른 컨테이너 이름을 참조 # 멈출 대상을 못 찾는다

두 결함 모두 평소 배포에서는 잘 실행하지 않는 경로에 있었어요.

배포가 성공할 때마다 정상 경로를 관찰할 기회는 있었지만, 그 결과가 실패 경로의 동작을 보장하지는 않았어요. 되돌림이 필요한 때에 인자 누락을 처음 발견하지 않도록 별도로 확인해야 했어요.

그림 3. 정상 배포가 성공해도 실패 처리 경로에 누락이 있을 수 있어요
💡 실패 경로를 확인할 때
• 운영과 분리된 환경에서 건강검사 실패와 되돌림 절차를 확인해요
• 정상 경로와 실패 경로에 필요한 실행 인자가 같은지 비교해요
• 복사한 스크립트가 실제 컨테이너 이름을 참조하는지도 확인해요
위 항목은 확인 기준이며, 여기서 추가 시험을 완료했다는 뜻은 아니에요.

5. 마스킹 전후 직렬화 결과가 모두 비어 있었어요

로그 마스킹을 적용할 때는 다른 문제가 드러났어요.

이 작업은 위 기동 실패보다 먼저였어요. 요청 본문과 민감한 값이 로그에 남는 것을 보고, 출력 전에 해당 값을 가리는 유틸리티를 적용했어요. 분기별 호출 측정 로그가 늘어나서 시작한 작업은 아니었어요.

마스킹 전후 출력을 확인하던 중 취소 요청 객체만 양쪽 모두 비어 있는 것을 봤어요.

마스킹 전후를 같이 찍어 본 결과 마스킹 전 CancelRequest{} 마스킹 후 CancelRequest{} -> 가릴 값이 없었던 것이 아니라, 꺼낼 방법이 없었다
📖 용어: 직렬화와 접근자(getter)
직렬화는 객체를 문자열이나 JSON 같은 형태로 바꾸는 일이에요. 접근자는 getXxx()처럼 객체의 값을 읽는 메서드예요. 어떤 속성을 읽을 수 있는지는 직렬화 라이브러리와 설정에 따라 달라져요.

이 객체에는 접근자가 없었어요. 당시 직렬화 방식에서 읽을 속성을 찾지 못해, 마스킹 전후 결과가 모두 비어 있었던 거예요. 접근자가 없다는 이유만으로 모든 직렬화 방식이 같은 결과를 낸다고 볼 수는 없어요.

6. 관찰 코드도 기동과 실패 경로를 확인해야 해요

앞선 작업에서는 접근을 제한하기 전에 실제 호출과 사용자를 확인하려고 했어요.

1편에서는 위험이 큰 경로부터 제한했고, 2편에서는 약 8주치 호출을 집계했어요. 3편에서는 기본값을 거부로 바꾸면서 되돌림 스위치를 남겼고, 4편에서는 삭제하려던 분기에 실제 사용자가 있다는 것을 확인했어요. 사용 현황은 제한 범위를 정할 때 필요한 근거였어요.

이번에는 그 현황을 확인하려고 넣은 코드도 기동에 영향을 줄 수 있다는 점을 놓쳤어요. 로그 추가와 함께 생성자가 달라졌으므로, 읽기 위주의 변경이라도 애플리케이션이 실제로 생성되고 시작하는지 확인해야 했어요.

생성자 변경은 새 버전의 기동 실패로 이어졌고, 실패 처리 경로와 마스킹 결과를 확인하는 과정에서는 별도의 결함이 드러났어요. 각 항목을 발견한 기록만으로 후속 수정까지 끝났다고 볼 수는 없어요.

당시 기록과 현재 확인의 범위

📌 전체 조치 완료와는 구분해요
당시에도 후속 검토 항목이 남아 있었어요. 이후 조치와 현재 운영 상태를 확인한 자료가 없어, 전체 점검이 끝났다고 결론 내리지는 않아요.
✍️ 확인한 내용
로그 추가와 키 읽기 방식 변경을 함께 배포하면서 암복호화 유틸리티의 생성자가 둘이 됐어요. 사용할 생성자가 지정되지 않아 No default constructor found로 새 버전이 기동하지 못했고, 재시작이 공유 호스트의 CPU 부하로 이어졌어요. 당시에는 운영용 생성자에 @Autowired를 명시한 뒤 재배포해 기동을 복구했어요.

배포 스크립트의 실패 처리 경로에서도 누락을 발견했고, 이보다 앞선 마스킹 작업에서는 접근자가 없는 객체의 직렬화 결과가 비어 있는 것을 봤어요. 이 발견들의 후속 수정과 현재 운영 상태까지 확인한 것은 아니에요. 기동 실패를 복구한 기록과 전체 조치 완료 여부는 구분해서 봐야 해요.
