1편. Spring Security 포괄 허용을 줄이기 전 관리자 인가와 익명 요청 관찰하기 ← 지금 이 글

당시 기록을 보면 2026년 8월 10일 보안 감사에서 이 서버의 URL 단위 인가가 지적됐어요. /api/**에 permitAll이 적용돼 있었고, 등급은 HIGH, 조치 기한은 "단기 1주 이내"였어요. 아래의 점검·변경 경위는 당시 기록을 바탕으로 한 것이며, 이번 편집에서 운영 상태를 다시 확인한 것은 아니에요.

8월 18일 점검 페이지에는 완료로 표시돼 있었지만, 9월 11일 설정을 살펴봤을 때는 해당 규칙이 남아 있었다고 해요. 기한은 1주였는데 실제로 설정을 확인하기까지 한 달 넘게 걸린 셈이에요. 완료 표시와 설정이 일치하지 않았던 이유까지는 이 기록으로 알 수 없어요.

당시 살펴본 파일은 224줄이었고, 인가 블록에 permitAll이 스무 줄 넘게 나열돼 있었어요. 마지막에는 /api/**를 허용하는 규칙도 있었어요. 앞에서 별도로 제한하지 않은 어드민 API와 엑셀 내려받기 같은 경로도 이 포괄 허용 범위에 포함돼 있었어요.

기본값을 바로 거부로 바꾸려면 먼저 기존 호출을 파악해야 했어요. 어떤 경로를 누가 호출하는지 모르는 상태에서는 정상 호출까지 차단할 수 있으니까요. 당시에는 관리자성 경로에 먼저 인가를 적용하고, 나머지는 익명 호출 기록을 모은 뒤 전환하는 순서를 택했어요.

🧭 이 글에서 다룰 것
• 점검 완료 표시와 실제 설정은 어떻게 달랐나요?
• 개별 허용 규칙과 마지막 포괄 규칙은 어떻게 적용되나요?
• 관리자성 경로부터 인가를 적용한 이유는 무엇인가요?
• 요청을 차단하지 않는 관찰 필터는 왜 함께 넣었나요?

1. 개별 허용 목록 밖의 요청도 통과했어요

당시 인가 블록의 요지는 아래와 같아요.

// 점검하기 전의 인가 블록 (요지, 224줄 파일의 일부) .authorizeHttpRequests(reg -> reg .requestMatchers(정적 리소스).permitAll() .requestMatchers("/api/v1/batch/**").permitAll() .requestMatchers("/api/v1/{연동}/**").permitAll() // 이 경로는 인증 없이 접근 가능 .requestMatchers("/api/v1/{연동}/v3/00660/** ").permitAll() ... permitAll 이 스무 줄 넘게 이어짐 ... .requestMatchers("/api/v1/payment/**").authenticated() .requestMatchers("/api/**", 문서 화면).permitAll() )

앞쪽의 permitAll 목록에 없는 요청도 마지막 /api/** 규칙에 도달하면 허용돼요. 다만 Spring Security는 선언된 순서에서 처음 일치한 규칙을 적용하므로, 마지막 규칙이 앞선 규칙을 덮어쓰는 것은 아니에요. 이 예시에서 앞에 선언된 결제 경로의 인증 요구는 그대로 적용돼요.

설정에 허용 경로가 길게 나열돼 있어도 허용 범위가 그 목록으로 제한되지는 않았어요. 마지막 포괄 규칙까지 함께 읽어야, 명시하지 않은 경로가 어떤 판정을 받는지 알 수 있었어요.

인증은 요청한 주체가 누구인지 확인하는 과정이고, 인가는 그 요청을 허용할지 정하는 과정이에요. 익명 요청도 공개 규칙으로 허용할 수 있어요. 여기서 검토할 대상은 인증 자체의 유무만이 아니라, 관리자성 기능까지 익명 접근을 허용할 이유가 있는지였어요.

📖 용어: permitAll
Spring Security에서 해당 규칙에 일치한 요청을 인증 여부와 관계없이 허용하는 설정이에요. 앞에서 일치한 규칙이 있으면 그 규칙이 먼저 적용돼요. 이 설정만으로 앞선 인증 필터의 동작까지 생략되는 것은 아니에요.

제휴 연동 서버에는 외부 서버가 호출하도록 일부러 공개한 경로도 있었어요. 그래서 각 경로의 공개 목적과 호출 주체를 구분해야 했어요. 당시 기록에서는 마지막 포괄 허용 규칙을 둔 이유를 찾지 못했다고 해요.

공개 목적이 있는 경로는 그 필요성을 검토하고, 근거가 없는 포괄 허용은 호출 영향을 확인해야 했어요. 개별 공개 경로를 추가하는 일과 기본 허용 범위를 정하는 일을 구분할 필요가 있었어요.

그림 1. 앞선 제한 규칙에 일치하지 않으면 포괄 허용 규칙이 적용돼요

2. 기본값을 바꾸려면 기존 호출을 알아야 했어요

포괄 허용 규칙을 지우는 수정 자체는 간단해 보여도, 그 결과까지 알 수 있었던 것은 아니에요. 제휴 서버가 호출하는 경로, 사내 도구의 연동, 오래된 배치의 사용 여부를 먼저 확인해야 했어요.

기본값 거부는 명시적으로 허용한 요청만 통과시키고 나머지를 거부하는 방식이에요. 허용 목록에서 정상 호출이 빠지면 전환 뒤에 실패할 수 있어요. 당시에는 익명 호출의 주체를 인증 정보로 구분하기 어려워, 경로와 호출 횟수부터 확인하기로 했어요.

⚠️ 주의: 인가 변경의 영향을 확인해요
• 악용 흔적을 확인하지 못했다는 이유로 관찰 기간이 안전하다고 판단할 수는 없어요
• 당시에는 관리자성 경로에 먼저 인가를 적용하고, 나머지는 호출 기록을 모은 뒤 전환하기로 했어요

3. 관리자성 경로부터 URL 단위 인가를 적용했어요

먼저 인가를 적용할 대상을 나눴어요. 관리자 기능이나 상세 정보 조회처럼, 익명 접근을 허용했을 때 영향을 크게 볼 필요가 있는 경로를 우선했어요.

당시 정한 대상은 관리자성 경로 열 묶음과 API 문서 화면이었어요. 운영자나 내부 서버 등 정해진 주체가 사용하는 기능으로 보고, 제휴 연동을 위한 공개 경로와 구분했어요.

URL 단위 인가를 건 경로 (관리자성) /api/v1/admin/** 어드민 /api/v1/excel/** 엑셀 내려받기 /api/v1/assignment/** 배정 /api/v1/admin-proxy-receipt/** 대행 접수 /api/v1/{연동}-admin/** 제휴사 어드민 /api/v1/proxy-person-detail/** 대행인 상세 /api/v1/hospital-visit-work/** 방문 업무 /api/v1/user-detail/** 사용자 상세 /api/v1/{사내}/payment/** 결제 /api/v1/document-checklist/test-auto-create/** /swagger-ui/** 등 API 문서 화면

중괄호는 실제 이름을 가린 부분이에요. 마지막 문서 화면 경로만 /api/ 밖에 있고, 포괄 API 규칙과 별도로 허용돼 있어 함께 검토했어요. 이 단계의 변경 대상은 위 목록이었어요.

판정은 전용 AuthorizationManager에 맡긴 것으로 기록돼 있어요. 요청을 허용할지 결정하는 코드를 따로 두고, 사용자 권한과 요청 헤더를 함께 확인하는 방식이에요.

AdminApiAuthorizationManager.check(인증정보, 요청) 관리자 권한을 가진 사용자인가 -> 통과 요청 헤더의 서버 간 API 키가 맞는가 -> 통과 요청 헤더의 제휴사 어드민 키가 맞는가 -> 통과 셋 다 아니다 -> 거부

세 조건 중 하나를 충족하면 통과하는 방식이에요. 운영자는 관리자 권한으로, 내부 서버는 서버 간 API 키로, 제휴사 운영 도구는 별도 키로 호출하도록 구분했어요. 호출 방식을 하나로 통일하려면 호출자도 함께 고쳐야 해서, 이 단계에서는 기존 방식에 맞춰 관리자성 경로의 접근 조건을 추가했어요.

거부 응답도 구분했어요. 당시 구현 설명은 인증 정보가 없으면 401, 로그인했지만 관리자 권한이 없으면 403을 반환한다는 내용이에요. 호출자가 인증 정보 누락과 권한 부족을 구분하도록 한 것이에요.

다만 이 목록 안에서도 내부 서버가 토큰 없이 호출하던 경로 네 개는 예외로 남겼다고 해요. 호출하는 쪽을 함께 바꾸지 않고 차단하면 정상 연동이 실패하기 때문이었어요. 이 숫자는 당시 변경 범위의 예외 수이며 현재 허용 목록을 뜻하지 않아요.

당시 배포 기록에는 알림톡 경로에서 401이 발생했고, 토큰 없이 호출하던 내부 API 서버의 경로를 같은 날 예외에 추가해 복구했다고 남아 있어요. 예외 네 개는 이 한 건을 포함한 수치예요. 이번 편집에서 배포나 복구 결과를 새로 검증한 것은 아니에요.

그림 2. 관리자성 경로에 먼저 접근 조건을 추가했어요

4. 같은 날 익명 요청을 기록하는 필터도 적용했어요

같은 날 익명 요청을 기록하는 서블릿 필터도 별도 커밋으로 함께 배포했다고 해요. 이 필터의 목적은 접근 차단이 아니라 관찰이에요. 공개 목록에 없는 API 경로로 들어온 익명 요청에 전용 태그를 붙여 로그를 남기고, 요청 처리는 계속하도록 했어요.

인증 없이 들어온 요청에 붙이는 태그 [ANON-API] method=GET path=/api/v1/{상세}/... ip=... ua=... origin=... -> 공개로 적어 둔 목록에 없는 /api/** 익명 요청만 이 태그를 받는다 요청은 막지 않는다. 응답도 바뀌지 않는다

이 태그가 붙은 로그를 집계하면 관찰 대상에 포함된 익명 요청의 경로와 횟수를 확인할 수 있어요. 공개 목록에 있어 관찰에서 제외된 요청까지 모두 센다는 뜻은 아니에요.

인가 변경과 함께 관찰을 시작하면 다음 전환을 준비하는 동안 호출 기록을 모을 수 있어요. 나중에 관찰을 시작하면 그만큼 기록을 모으는 기간도 늦어지기 때문에 같은 날 적용한 것으로 설명돼 있어요.

💡 실무에서는: 관찰 필터를 넣을 때
• 관찰 필터가 요청을 차단하거나 응답을 바꾸지 않는지 확인해야 해요
• 검색으로 구분할 수 있는 태그를 쓰면 집계할 때 다른 로그가 섞이는 일을 줄일 수 있어요
• 본문과 인증 헤더 값은 남기지 않도록 주의해야 해요. 익명 요청에도 개인정보가 들어 있을 수 있어요

로그에 남길 항목도 검토해야 했어요. 당시 기록에는 2024년 3월 추가된 JWT 토큰 전문의 INFO 로그가 2년 넘게 유지됐고, 감사 이후 제거됐다고 남아 있어요. 여기서는 이미 남아 있던 과거 조치 경위만 다루며, 현재 로그 설정을 새로 확인한 것으로 보지는 않아요.

기록상 토큰 로그는 보고서를 받은 뒤 이틀 만에 제거됐지만, permitAll 검토는 한 달을 넘겼어요. 로그 한 줄을 제거하는 변경과 기존 호출에 영향을 주는 인가 변경은 확인할 범위가 달랐어요. 다만 이 차이만으로 실제 지연 원인을 모두 설명할 수는 없어요.

5. 기본값 전환에 앞서 호출 기록을 모았어요

호출 기록 없이 전환하는 경우와 먼저 관찰하는 경우를 비교하면 아래와 같아요.

그림 3. 관찰 기록으로 기본값 전환에 영향을 받을 호출을 검토해요

이 단계에서는 기본값을 거부로 바꾸는 작업까지 마친 것은 아니에요. 당시 기록상 관리자성 경로에 인가를 먼저 적용하고, 나머지 익명 호출은 관찰 대상으로 남겼어요. 관찰을 선택했다는 사실만으로 남은 범위가 안전하다거나 기다려도 된다고 결론 내릴 수는 없어요.

6. 개별 변경과 포괄 허용 규칙의 이력을 구분했어요

당시에는 변경 이후 저장소 이력을 살펴보며 포괄 허용 규칙이 언제부터 있었는지도 추적했어요. 검토한 커밋 두 개는 아래와 같아요.

범인으로 지목했던 두 커밋 2024-04-23 "시스템 토큰 적용 완" + "/api/v1/{연동}/v3/00660/** " 를 permitAll 에 추가 (끝에 공백) 2024-06-27 "잘못된 security config matcher 수정" - /api/v1/{연동}/**/hometax/info + /api/v1/{연동}/**

두 번째 변경은 좁은 경로 하나를 더 넓은 경로 패턴으로 바꾼 것이에요. 커밋 제목만으로 허용 범위가 좁아졌다고 판단할 수는 없었어요.

다만 당시 이력 분석에서는 두 커밋보다 먼저 포괄 허용 규칙이 존재했다고 해요. 앞선 허용 목록에 추가된 경로가 이미 포괄 규칙으로 허용됐다면 접근 허용 결과는 같을 수 있어요. 앞에 인증을 요구하는 규칙이 있는 경우까지 같은 결과라고 일반화할 수는 없어요.

기록에는 포괄 규칙이 저장소 첫 커밋인 2023-11-29의 로컬용 설정에 있었고, 운영용 설정의 같은 위치에는 인증 요구가 있었다고 남아 있어요. 이후 2024년 3월 환경별 설정 블록을 주석 처리하면서 로컬용 블록 하나가 남았다는 분석이에요. 해당 저장소 이력은 이번 편집에서 직접 대조하지 못했어요.

2024-04-23에 추가한 패턴의 끝에는 공백도 있었어요. 당시에는 이 패턴이 일반적인 요청 경로와 맞지 않더라도 뒤의 포괄 허용 때문에 호출이 통과할 수 있다고 분석했어요. 다만 2년 동안 한 건도 일치하지 않았다는 결론은 요청 기록을 전수 확인하지 않고 확정할 수 없어요.

이력을 확인하는 일과 함께 현재 읽고 있는 설정의 최종 허용 범위도 살펴봐야 했어요. 앞선 명시 규칙이 계속 효력을 갖는다는 점을 지키면서, 거기에 일치하지 않은 요청을 마지막 규칙이 어떻게 처리하는지 확인하는 것이 이 설정을 이해하는 데 필요했어요.

개별 허용 경로가 길게 나열돼 있어도, 마지막에 포괄 허용 규칙이 있으면 목록 밖의 요청까지 허용될 수 있어요. 다만 앞에서 처음 일치한 규칙이 우선하므로, 기존 결제 경로의 인증 요구까지 무효가 되는 것은 아니에요.

당시 기록에서는 관리자성 경로 열 묶음과 API 문서에 접근 조건을 추가하고, 같은 날 익명 요청을 관찰하는 필터를 적용했어요. 예외 네 개에는 배포 당일 401이 발생한 뒤 추가한 한 건도 포함돼 있어요. 이 단계는 기본값 거부 전환의 완료가 아니며, 배포·복구·과거 이력은 이번 편집에서 독립적으로 재확인하지 못했어요.
