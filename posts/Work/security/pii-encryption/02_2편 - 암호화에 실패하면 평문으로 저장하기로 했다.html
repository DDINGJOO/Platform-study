계좌번호를 저장할 때 암호화하도록 바꾸면서, 암호화에 실패한 요청을 어떻게 처리할지도 정해야 했어요. 당시에는 대행인 정보 수정과 로그인에서도 이 저장 경로를 사용하고 있었어요.

예외를 던져 저장을 거절하는 방법과, 암호화에 실패한 값을 평문으로 저장하는 방법을 비교했어요. 전자는 해당 요청이 실패하고, 후자는 저장은 이어지지만 개인정보가 암호화되지 않은 채 남는다는 문제가 있었어요.

당시에는 암호화 실패 시 평문 저장을 선택했고, 설계 문서에도 그 판단을 적었어요. 평문이 남는 위험을 감수한 전환 기간의 선택이었어요. 아래 설명은 당시 기록에 한정하며, 평문 저장을 일반적인 보안 권장안으로 제시하는 것은 아니에요.

🧭 이 글에서 다룰 것
• 암호화 실패 시 저장을 거절하거나 평문을 남기면 각각 어떤 문제가 있었나?
• 실패 로그와 채우기 배치는 무엇을 담당했고, 어디까지 확인했나?
• 왜 읽기 호환성과 쓰기 암호화를 나눠 배포했나?
• 암호문 전용 컨버터로 바꾸는 조건은 무엇이었나?

1. 암호화 실패를 저장 실패로 처리할 때의 영향

암호화 처리는 엔티티와 DB 사이에서 값을 변환하는 컨버터에 넣었어요. 저장할 때 암호화하고, 읽을 때 복호화하는 구조였어요.

📖 용어: 컨버터 (attribute converter)
엔티티의 필드 하나와 DB 컬럼 하나 사이에서 값을 변환하는 코드예요. 당시에는 조회·수정 코드에서 암호화를 직접 호출하지 않고, 컨버터에서 저장 형식을 바꾸도록 했어요.

당시에는 키를 읽지 못하거나 암호 모듈에서 문제가 생기는 경우를 고려했어요. 키는 기동할 때 검증했지만, 이것만으로 실행 중의 암호화 실패까지 배제할 수는 없었어요. 같은 원인이 이어지면 후속 저장도 실패하고, 이 경로를 사용하는 대행인 수정과 로그인에도 영향을 줄 수 있다고 봤어요.

평문 저장을 허용하면 기존 평문을 암호화하는 전환 도중에도 평문 행이 새로 생길 수 있었어요. 요청 실패를 줄이는 선택이 암호화 누락을 허용하는 것이기도 해서, 저장 성공만으로 전환이 잘 되고 있다고 판단할 수 없었어요.

2. 평문 읽기를 허용하던 전환 기간의 선택

이 선택의 전제는 읽기 쪽이 평문도 처리한다는 점이었어요. 같은 컬럼에 평문 행과 암호문 행이 섞이는 전환 기간을 위해 별도의 컨버터를 사용하고 있었어요.

📖 용어: {관대한 컨버터}와 {암호문 전용 컨버터}
당시 {관대한 컨버터}는 암호문 접두어가 있으면 복호화하고, 없으면 평문으로 보고 그대로 반환했어요. {암호문 전용 컨버터}는 암호문이 아니면 읽기에 실패했어요. 앞쪽은 전환 기간에 쓰고, 뒤쪽은 평문이 없는지 확인한 뒤 적용하려던 구현이에요.
{관대한 컨버터} 읽기 (DB -> 엔티티) null -> null 암호문 접두어로 시작 -> 복호화 (실패하면 예외, 모니터가 잡는다) 그 밖 -> 그대로 (아직 암호화 안 된 행) 쓰기 (엔티티 -> DB) null -> null 쓰기 암호화 꺼짐 -> 그대로 (1차 배포) 쓰기 암호화 켜짐 -> 암호화 (2차 배포) 암호화 실패 -> 평문 그대로 저장 + WARN (이 글의 결정)

이 의사코드는 당시 기록에 있던 처리 흐름이에요. 평문으로 저장한 값도 읽기 컨버터가 그대로 반환하므로, 그 값을 사용하는 화면과 지급 계산의 호환성을 유지하려던 설계였어요. 다만 이 동작은 개인정보가 암호화되지 않은 문제를 해결해 주지는 않아요.

남은 평문은 별도의 채우기 배치로 암호화하도록 했어요.

📖 용어: 채우기 배치 (fill)
컬럼에서 평문인 행을 찾아 저장 형식을 암호문으로 바꾸는 일회성 배치예요. 당시 기록상 배치는 암호화 직후 한 번 복호화해 원문과 같은지 확인한 뒤 커밋하도록 했어요.

배치가 남은 평문을 암호화할 것이라고 예상했지만, 배치가 있다는 사실만으로 완료가 보장되지는 않아요. 배치 실행 결과와 남은 평문 수를 확인해야 하는 선택이었어요. 그 확인 전까지는 평문이 남을 수 있다는 한계가 있었어요.

3. 암호화 실패 로그와 확인 범위

평문이 남는 것에 더해, 요청이 성공하면 암호화 실패를 알아차리기 어렵다는 문제도 있었어요. 화면에 표시되는 값이 같아도 DB의 저장 형식까지 같은 것은 아니었어요.

당시에는 암복호 유틸이 남기는 ERROR 로그를 모니터가 감시하도록 했어요. 컨버터에서는 암호화 실패 뒤 평문을 저장했다는 WARN 로그를 추가로 남겼어요.

📖 용어: P1 모니터
당시 사용한 모니터 중 가장 높은 우선순위의 알림 규칙이에요. 암복호 유틸의 실패 로그가 한 건만 발생해도 담당자에게 알리도록 설정했다고 기록했어요.

실패한 값을 로그에 남기면 개인정보가 로그에도 복사돼요. 그래서 컨버터의 WARN에는 값 없이 입력 길이만 남겼어요. 계좌번호 사본을 담은 지급 내역 스냅샷에도 별도의 컨버터가 있었는데, 아래 {스냅샷 컨버터}는 길이도 빼고 원문 저장 여부만 기록했어요.

실패했을 때 남는 줄 (실제 발췌가 아니라 모양) [ERROR] 암복호 유틸 암호화 실패 [WARN ] {관대한 컨버터} 대행인 계좌번호 암호화 실패로 평문 저장. 입력 길이=13 [WARN ] {스냅샷 컨버터} 지급 내역 계좌번호 암호화 실패로 원문 저장 JSON 이 깨져 암호화를 아예 걸지 못한 경우 [ERROR] {스냅샷 컨버터} JSON 형식이 아니어서 계좌번호를 암호화하지 못하고 원문 저장

위 로그는 실제 발췌가 아닌 형식 예시예요. 계좌번호·암호문·예외 원인 문구를 넣지 않고 실패 위치와 일부 입력 길이만 남기는 의도였어요. 암복호 유틸의 ERROR는 알림 대상으로, WARN 두 줄은 평문 저장에 대한 추가 기록으로 구분했어요.

JSON 형식 오류는 암복호 유틸 호출 전에 생기는 실패라 따로 다뤘어요. 당시 기록에는 컨버터가 직접 ERROR를 남기도록 바꿨다고 적혀 있어요. 다만 로그 수준을 바꾼 사실과 실제 알림이 발생한 사실은 구분해야 해요. 당시 확인 범위만으로는 모든 실패 경로의 알림 동작까지 입증할 수 없었어요.

⚠️ 당시 설계의 보완책과 한계
• 실패 로그와 알림은 암호화 누락을 알아차리기 위한 수단이었어요. 평문 저장 자체를 막지는 못해요.
• 채우기 배치를 두었지만, 실행 성공과 남은 평문 수를 따로 확인해야 했어요.
• 로그에도 개인정보가 복사되지 않도록 값 대신 처리 결과만 남겼어요.

4. 배포를 둘로 나눈 이유

읽기 호환성과 쓰기 암호화는 두 차례에 나눠 배포했어요. 롤링 배포 중에는 구버전과 신버전이 같은 DB를 사용하기 때문이에요.

📖 용어: 롤링 배포 (rolling deploy)
새 버전 컨테이너를 실행하고 구버전을 순서대로 종료하는 방식이에요. 여기서는 컨테이너 하나를 "태스크"라고 불러요. 당시 배포 기록에서는 두 버전이 공존하는 시간이 약 15분이었어요.

읽기와 쓰기를 한 번에 바꾸면 새 태스크가 저장한 암호문을 구버전 태스크가 읽을 수 있어요. 구버전에는 복호화 처리가 없으니 암호문을 계좌번호 값으로 사용하게 돼요. 두 버전이 공존하는 약 15분 동안 화면과 지급 계산에 영향을 줄 수 있는 조건이었어요.

그래서 1차 배포에서는 평문과 암호문을 모두 읽도록 바꾸고, 쓰기는 평문으로 유지했어요. 모든 태스크가 1차 버전으로 교체된 뒤 2차 배포에서 쓰기 암호화를 켜는 순서였어요. 2차 배포 중 남아 있는 이전 태스크도 1차 버전이므로 암호문을 읽을 수 있게 한 거예요.

그림 2. 모든 태스크가 암호문을 읽을 수 있게 된 뒤 쓰기 암호화를 적용한 순서

기존 {암호문 전용 컨버터}는 접두어가 없는 값을 읽을 때 예외를 던졌어요. 평문이 섞인 컬럼에 바로 적용하면 평문 행을 읽는 요청이 실패하므로, 전환 기간에는 별도의 컨버터가 필요했어요.

⚠️ 암호문 접두어와 평문 입력의 충돌
1차 배포에서는 암호문 접두어로 시작하는 입력도 평문으로 저장될 수 있었어요. 읽기 쪽은 접두어를 기준으로 복호화를 시도하므로 이 값은 읽기에 실패할 수 있었어요.

목록은 행을 페이지 단위로 읽기 때문에 해당 행이 포함된 페이지와 일괄 지급 계산, 해당 대행인의 로그인까지 영향을 받을 수 있었어요. 당시에는 생성·수정 입력에서 이 접두어를 대소문자 구분 없이 거부하도록 했고, 사전 조회에서도 해당 값이 0건이었다고 기록했어요.

5. 암호문 전용 컨버터로 바꾸려던 조건

평문과 암호문을 모두 읽는 컨버터는 전환 기간에 쓰려던 구현이었어요. 이를 계속 사용하면 평문이 새로 저장돼도 읽기는 성공하기 때문에, 읽기 성공 여부로 암호화 완료를 확인할 수 없었어요.

당시 계획은 일괄 암호화 후 남은 평문이 없는지 확인하고, {암호문 전용}으로 바꾸면서 {관대한 컨버터}와 채우기 배치를 삭제하는 것이었어요. 전환 뒤에는 평문을 읽을 때 복호화가 실패하도록 해, 평문이 남은 상태를 정상적인 읽기로 처리하지 않으려 했어요.

처음에는 암호문을 평문으로 되돌리는 배치 모드를 남겨 두려 했어요. 하지만 암호문 전용 컨버터로 바꾼 뒤에는 되돌린 평문을 읽지 못해요. 당시 독립 리뷰에서 "전환된 코드에 되돌리기 버튼만 살아 있다"고 지적받아, 컨버터 전환과 배치 삭제를 같은 배포에 포함했어요. 원래 기록은 이 지적과 설계 문단이 전환을 되돌릴 때 함께 삭제됐다고 설명해요. 이번 편집에서는 해당 과거 커밋을 별도 원자료로 재확인하지 못했어요.

그림 3. 전환 기간의 처리와 암호문 전용 전환 계획을 구분했어요

암호문 전용 컨버터로 바꾼 배포는 한 번 되돌렸어요. 당시 기록에 따르면 쓰기 암호화 설정이 운영에서 읽히지 않은 상태였고, 암호문 전용 컨버터가 평문 행을 읽으면서 복호화에 실패했어요. 1편에서 다룬 사건이에요. 배포를 되돌리면서 {관대한 컨버터}와 채우기 배치도 다시 포함됐다고 기록했어요.

글을 처음 작성한 날 저녁에도 채우기 배치가 예정돼 있었지만, 당시 기록에는 결과를 확인하지 못했다고 남아 있어요. 남은 평문이 0인지 확인한 뒤 재전환하려던 계획까지가 이 글의 범위예요. 이후 배치 결과와 전환 완료 여부, 현재 운영 상태는 이번 편집에서 확인하지 못했어요.

✍️ 정리
당시에는 암호화 실패가 수정·로그인 요청의 실패로 이어지는 영향을 줄이려고 평문 저장을 선택했어요. 읽기 호환성은 유지할 수 있었지만, 개인정보가 평문으로 남는 위험을 감수한 선택이었어요. 실패 로그와 채우기 배치는 이 위험을 확인하고 후속 처리하려던 수단이었고, 암호화 완료를 보장하지는 않았어요.

롤링 배포에서 약 15분 동안 두 버전이 공존했기 때문에 읽기 호환성을 먼저 배포하고 쓰기 암호화를 적용하는 순서를 정했어요. 남은 평문이 0인지 확인한 뒤 암호문 전용 컨버터로 바꾸려 했지만, 그 배포는 한 번 되돌렸어요. 이후 배치 결과와 재전환 완료 여부는 당시 기록만으로 확인하지 못했어요.
