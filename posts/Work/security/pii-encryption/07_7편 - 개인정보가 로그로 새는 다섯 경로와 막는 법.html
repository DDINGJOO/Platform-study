7편. 개인정보 로그 마스킹: 다섯 출력 경로와 대응책의 적용 범위 ← 지금 이 글

주민번호 컬럼을 암호화해도 로그에 같은 값이 남을 수 있어요. 컬럼에 저장하기 전의 DTO를 출력하거나 입력값을 예외 메시지에 넣으면, 저장된 암호문과 별개로 평문이 로그에 찍히기 때문이에요.

이를 확인하려고 작은 Java 프로그램에서 다섯 경로를 재현했어요. 가짜 이름·주민번호·전화번호 한 벌을 사용했는데 로그에 값 22개가 남았어요. 대응책을 하나씩 적용한 실행에서는 다섯 경로를 모두 막는 방법이 없었고, 실습에서 조합한 대응책을 함께 적용해도 2개가 남았어요.

경로별로 대응 전후의 로그를 비교하고, 대응책 열 가지의 적용 범위와 한계를 정리했어요. 아래 결과는 가짜 값을 넣은 실습에서 확인한 것이며, 실제 서비스의 전체 로그 경로나 현재 보안 상태를 검증한 결과는 아니에요.

🧭 이 글에서 확인할 것
• Lombok @ToString.Exclude 를 붙였는데 왜 값이 또 찍히나?
• 형식 검사 예외는 왜 마스킹 정규식을 피해 가나?
• Logback %replace(%msg) 를 걸었는데 Caused by: 줄은 왜 그대로인가?
• HTTP 클라이언트 덤프에서 이름은 왜 정규식으로 못 가리나?
• 정규식을 넓혀도 남는 입력은 무엇인가?
• 코드와 로깅 설정에서 각각 무엇을 확인해야 하나?

1. 실습: 가짜 값 한 벌로 다섯 경로를 재현하기

실습 코드는 labs/security/pii-07-log-leaks/ 에 있어요. Java 25, Lombok 1.18.48, SLF4J 2.0.17 과 Logback 1.5.18, H2 2.3.232, Apache HttpClient 5.6.5, ArchUnit 1.5.1 을 쓰고 Docker 는 쓰지 않아요. 넣는 값은 전부 가짜예요. 이름 김가짜, 주민번호 000000-9876543, 전화번호 010-0000-0000예요.

프로그램은 다섯 경로를 차례로 실행해요. 가입 요청 DTO 를 통째로 로깅하고(①), 형식이 틀린 주민번호로 검사 예외를 던지고(②), 같은 전화번호를 두 번 넣어 DB 유니크 제약을 깨고(③), 외부 본인확인 API 를 흉내 낸 로컬 서버에 HTTP 요청을 보내고(④), 마지막으로 검색어 열 개를 그대로 로깅해요(⑤). 대응책은 시스템 속성으로 하나씩 적용해요.

그림 1. 다섯 경로는 모두 Logback 을 사용하지만 전달하는 값의 형태가 달라요

남은 값은 scripts/leaks.py 가 세어요. 같은 값이 다른 모양으로 남아도 잡아야 하니까 줄마다 HttpClient 의 바이트 표기([0xffffffea])를 바이트로 되돌리고, URL 인코딩을 풀고, NFKC 정규화로 전각 숫자를 반각으로 바꾸고, 공백·점·대시를 지운 뒤 가짜 값을 찾아요. 한 줄에 이름과 전화번호가 같이 있으면 2개로 세어요. 아무것도 켜지 않은 실행에서 ①이 6개, ②가 1개, ③이 1개, ④가 4개, ⑤가 10개로 합계 22개였어요. 아무것도 켜지 않은 기준 실행, 막는 법을 하나씩 켠 아홉 번, 전부 켠 한 번까지 11번을 한 묶음으로 세 번 돌렸는데 세 번 모두 숫자가 같았어요.

아래는 대응책을 적용하지 않은 실행과 실습의 조합을 모두 적용한 실행을 경로별로 비교한 화면이에요. 전자는 값이 남은 줄만, 후자는 스택 줄을 뺀 전체 출력을 보여 줘요.

그림 2. 실습의 대응책을 함께 적용해도 ⑤의 두 줄에는 가짜 값이 남았어요

2. ① DTO 전체 출력과 새 필드의 포함 여부

가장 흔한 줄은 이거예요. log.info("가입 요청 {}", request). Lombok @Data 가 만든 toString 은 모든 필드를 찍으니, 이 한 줄에 이름·주민번호·전화번호 3개가 실려요. 같은 값을 record 로 받은 줄도 3개였어요.

INFO app - 가입 요청 SignupData(name=김가짜, rrn=000000-9876543, phone=010-0000-0000, channel=web) INFO app - 가입 요청(record) SignupRecord[name=김가짜, rrn=000000-9876543, phone=010-0000-0000, channel=web]

Lombok 문서에는 세 가지 설정이 나와 있어요. 필드를 빼는 @ToString.Exclude, 인자 없는 인스턴스 메서드의 결과를 넣는 @ToString.Include(name 으로 표시 이름을 바꿀 수 있어요), 그리고 @ToString(onlyExplicitlyIncluded = true) 예요. 마지막 설정은 문서 표현대로 "표시한 것 말고는 아무것도 넣지 않는다"는 뜻이에요(Lombok @ToString).

주민번호에만 @ToString.Exclude 를 붙인 판은 6개에서 5개로 줄었어요. 이름과 전화번호는 그대로였어요. 처음 만들 때 주민번호만 민감하다고 보고 빼 두면, 나중에 붙은 필드는 기본값대로 포함돼요. 제외 목록에 적지 않은 필드는 계속 출력되는 거예요.

@Data @ToString(onlyExplicitlyIncluded = true) // 허용 목록: 새 필드는 기본으로 빠진다 public class SignupAllow { @Pii private String name; @Pii private String rrn; @Pii private String phone; @ToString.Include private String channel; } @Data public class SignupMasked { // 원본은 빼고 같은 이름으로 마스킹 값을 넣는다 @Pii @ToString.Exclude private String rrn; @ToString.Include(name = "rrn") String maskedRrn() { return Masking.rrn(rrn); } // 000000-******* ... }

마스킹 메서드 판과 허용 목록 판은 둘 다 3개가 남았어요. 남은 3개는 전부 record 줄이었어요. record 에는 @Data 를 붙이지 않으니 컴파일러가 만든 toString 이 모든 구성 요소를 찍어요. DTO 를 record 로 바꾸면 기존 Lombok 설정이 적용되지 않는다는 점도 함께 확인해야 해요.

📖 용어: TurboFilter
Logback 이 로그 요청마다 부르는 필터예요. 문서는 "원칙적으로 LoggingEvent 객체를 만들기 전에 불린다", "한 appender 가 아니라 로깅 컨텍스트 전체에 묶인다"고 설명해요(Logback Filters). 형식 문자열과 인자 배열을 보고 통과·중립·거부를 돌려줘요. 넘어오는 인자 배열이 원본이라 기술적으로는 고쳐 쓸 여지가 있지만, API 가 의도한 일은 판정이라 이 실습에서는 거부만 썼어요.

record 줄까지 막은 건 TurboFilter 였어요. 인자 가운데 @Pii 를 단 필드나 record 구성 요소가 있는 객체가 오면 그 줄을 버리고, 무엇을 버렸는지만 따로 남기게 했어요. ①이 0개가 됐어요. 이때는 그 로그 줄 자체가 사라져요. 가입 요청이 왔다는 사실도 함께 없어지므로, 필터와 별개로 로깅하는 코드에서 남길 정보를 정해야 해요.

WARN pii-guard - @Pii 객체를 인자로 받은 로그를 버림: logger=app format="가입 요청 {}" type=SignupData WARN pii-guard - @Pii 객체를 인자로 받은 로그를 버림: logger=app format="가입 요청(record) {}" type=SignupRecord

당시 업무에서도 객체의 출력 형식을 먼저 제한했어요. 암호화 배치에서 한 행을 담는 객체의 출력 형식을 id 만 찍게 해 두고, 로그와 예외에는 id 와 건수만 남겼어요(4편). 이 방식은 해당 객체를 출력하는 경로에 대한 대응이에요. 다른 로그 경로까지 확인했다는 뜻은 아니에요.

3. ② 형식 검사 예외에 입력값이 포함되는 경우

두 번째는 입력값을 예외 메시지에 넣는 코드예요. throw new IllegalArgumentException("주민번호 형식이 아닙니다: " + v). 전역 예외 처리기가 log.warn("요청 거부", e) 로 받으면 메시지가 그대로 찍혀요.

WARN app - 요청 거부 java.lang.IllegalArgumentException: 주민번호 형식이 아닙니다: 000000 9876543

형식 검사에서 거부한 값은 마스킹 정규식이 예상한 형식과도 다를 수 있어요. 이번에는 구분자가 공백이었고, 그래서 \d{6}-\d{7} 같은 흔한 마스킹 정규식에 걸리지 않았어요. 실제로 메시지만 가리는 판도, 예외까지 가리는 판도 ②는 1개 그대로였어요. 정규식을 넓힌 판에서야 0개가 됐어요.

실습에서는 메시지에 값 대신 필드 이름과 길이를 넣었어요. 입력 형식 문제를 확인하는 데 필요한 정보를 남기면서 원본 값은 제외한 거예요.

throw new IllegalArgumentException("주민번호 형식이 아닙니다 (field=rrn, length=" + v.length() + ")"); // WARN app - 요청 거부 // java.lang.IllegalArgumentException: 주민번호 형식이 아닙니다 (field=rrn, length=14)

당시 업무에서도 같은 방식으로 예외 로그를 제한했어요. 암호화에 실패한 값을 로그에 찍으면 원인 찾기는 쉬워지는데, 그 값이 바로 지키려던 개인정보예요. 그래서 컨버터는 값 없이 입력 길이만 WARN 으로 남기게 했어요(2편).

4. ③ 원인 예외에 포함된 DB 오류 메시지

저장소 계층에서 드라이버 예외를 감싸 다시 던지는 코드도 흔해요. throw new IllegalStateException("회원 저장 실패", e). 바깥 메시지에는 값이 없지만, 로그에는 원인 체인이 Caused by: 로 따라 찍혀요. H2 의 유니크 제약 위반 메시지는 겹친 값을 그대로 담고 있었어요.

ERROR app - 가입 실패 java.lang.IllegalStateException: 회원 저장 실패 Caused by: org.h2.jdbc.JdbcSQLIntegrityConstraintViolationException: Unique index or primary key violation: "PUBLIC.UK_MEMBER_PHONE_INDEX_8 ON PUBLIC.MEMBER(PHONE NULLS FIRST) VALUES ( /* 1 */ '010-0000-0000' )"; SQL statement: INSERT INTO member (rrn_enc, phone) VALUES (?, ?) [23505-232]

→ 바인딩 변수는 ? 로 가려져 있지만, 제약 위반 문구가 겹친 값을 직접 보여 줘요.

실습에서는 암호화한 컬럼의 제약 위반 메시지도 비교했어요. 같은 주민번호를 두 번 넣었을 때의 위반 메시지에는 실습용 암호문(LABENC:...)만 찍혔고, 전화번호 중복 메시지에는 평문 값이 나타났어요. 따라서 전화번호나 이메일 등 유니크 제약이 있는 평문 컬럼도 확인해야 해요. MySQL 도 오류 1062(ER_DUP_ENTRY)의 메시지가 Duplicate entry '%s' for key ... 모양이라 겹친 값을 문구에 넣어요(MySQL Server Error Reference).

📖 용어: 원인 예외 (cause)
예외를 다시 던질 때 안쪽에 달아 보내는 "무엇 때문에 실패했나"예요. 로거에 예외를 넘기면 Logback 은 바깥 예외와 원인 체인을 모두 찍어요. 디버깅에 도움이 되지만 안쪽 메시지의 값도 로그에 포함될 수 있어요.

실습에서는 원인 예외를 제외하고 SQLState 와 오류 코드만 담았어요. 원본 값을 남기지 않고 오류 종류를 구분하기 위한 선택이에요.

} catch (SQLException e) { throw new MemberSaveException("회원 저장 실패 (sqlState=" + e.getSQLState() + ", errorCode=" + e.getErrorCode() + ")"); // 원인을 달지 않는다 } // lab.repo.SafeMemberRepo$MemberSaveException: 회원 저장 실패 (sqlState=23505, errorCode=23505)

대신 드라이버 내부의 스택 정보가 사라져 처음 보는 오류는 별도로 재현해야 할 수 있어요. 그래서 이 처리는 저장소 계층에서 값이 포함될 수 있는 예외를 다시 던지는 지점에 적용했어요.

당시 업무에서는 이 처리가 빠진 코드를 리뷰에서 발견했어요. "쓰기 예외는 원인을 떼고 다시 던진다"는 방침이 문서에 있었는데, 새로 만든 배치 코드는 원인 예외를 그대로 달아 던지고 있었고 독립 리뷰에서 그 차이를 찾았어요. 해당 예외를 그대로 전달하면 배치 스케줄러 로그와 실패 알림에도 원인 메시지가 포함될 수 있었어요(5편). 아래 실습에서는 원인 예외를 전달하는 코드를 정적 검사로 찾는 방법도 확인했어요.

%replace(%msg) 의 적용 범위와 Caused by 줄

📖 용어: PatternLayout, 변환어
Logback 이 로그 이벤트를 문자열로 출력하는 규칙이에요. %msg(메시지), %ex(예외와 원인 체인), %level 같은 변환어를 이어 붙여 출력 형식을 정해요. 메시지와 예외는 서로 다른 변환어로 따로 출력해요.

로깅 층에서 정규식으로 가리는 방법도 같이 봤어요. Logback 의 %replace(p){r, t} 는 "하위 패턴 p 가 만든 문자열에서" 정규식 r 에 일치하는 부분을 t 로 바꿔요. 그리고 PatternLayout 은 패턴에 예외용 변환어가 없으면 "스택 정보가 중요하므로" 그것을 맨 끝에 자동으로 붙여요(Logback Layouts). 그러니 %replace(%msg) 만 걸면, 자동으로 붙은 예외 부분은 replace 바깥에서 찍혀요.

그림 3. 정규식 마스킹은 replace 안에 포함된 문자열에만 적용돼요
<!-- 메시지만: ③ 이 그대로 샌다 --> <pattern>%-5level %logger{0} - %replace(%msg){'\d{6}-\d{7}', '[주민번호]'}%n</pattern> <!-- 메시지와 예외를 함께. %nopex 는 "예외는 이미 위에서 그렸다"는 의도를 적어 두는 안전장치 --> <pattern>%-5level %logger{0} - %replace(%msg%n%ex){'\d{6}-\d{7}', '[주민번호]'}%nopex</pattern>

위 설정은 주민번호 형식 한 가지로 예외를 감싸는 범위를 보여 준 축약 예시예요. 전화번호 패턴은 포함하지 않으므로 이 설정만으로 그림의 전화번호를 가릴 수는 없어요. 실습의 측정 설정에는 주민번호와 전화번호 패턴을 함께 넣었어요. 그 구성에서 메시지만 가린 판은 ③의 전화번호가 1개 남았고, 예외까지 감싼 판은 0개였어요. 그림의 결과를 얻으려면 예외를 포함하는 범위와 전화번호를 찾는 패턴이 모두 필요해요. %nopex 는 꼭 있어야 하는 건 아니었어요. Logback 1.5.18 은 %replace 안에 든 %ex 도 예외 변환어로 인정해 자동 %ex 를 붙이지 않았고, %nopex 만 뺀 설정으로 다시 돌려도 예외는 한 번만 찍히고 결과도 13개로 같았어요. 필수 설정은 아니지만 의도가 드러나도록 남겼어요.

5. ④ HTTP 클라이언트 덤프는 본문을 통째로 찍는다

외부 API 의 오류를 확인하려고 요청·응답 로그를 켤 때도 본문 출력 여부를 봐야 해요. Apache HttpClient 5 는 org.apache.hc.client5.http.wire 로거를 DEBUG 로 켜면 오가는 바이트를, ...http.headers 를 켜면 헤더를 찍어요. 요청 본문과, 받은 전화번호를 되돌려 주는 응답 본문이 둘 다 찍혀 값 4개가 남았어요.

📖 용어: wire 로그
HTTP 클라이언트가 소켓에 쓰고 읽은 바이트를 그대로 남기는 로그예요. >> 는 보낸 것, << 는 받은 것이에요. 헤더 로그와 달리 본문이 들어가요.
DEBUG wire - http-outgoing-0 >> "{"name":"[0xffffffea][0xffffffb9][0xffffff80][0xffffffea]...","rrn":"000000-9876543","phone":"010-0000-0000"}" DEBUG wire - http-outgoing-0 << "{"result":"MATCH","phone":"010-0000-0000"}"

→ 이름은 UTF-8 바이트가 [0xffffffea] 꼴로 한 바이트씩 찍혔어요. 사람 눈으로도, 로그 검색으로도 이름이라는 걸 알아보기 어려워요.

정규식 마스킹을 켜면 주민번호와 전화번호는 가려졌지만 이름 1개는 끝까지 남았어요. 실습에서 사용한 정규식에는 이름 패턴이 없고, 이 줄의 이름은 바이트 표기로 출력됐기 때문이에요. 이름도 개인정보예요. OWASP Logging Cheat Sheet 는 로그에 직접 남기지 말고 지우거나 가리거나 해시·암호화할 것들 가운데 "개인 이름, 전화번호, 이메일 주소 같은 민감하지 않은 개인정보"를 따로 적어 둬요(OWASP Logging Cheat Sheet).

실습에서 ④를 0개로 만든 설정은 wire·headers 로거 수준을 INFO 로 명시하는 것이었어요. 루트 로그 수준을 DEBUG 로 바꿨을 때도 해당 덤프가 함께 켜지지 않도록 별도로 지정했어요. 요청·응답을 확인할 때는 본문 덤프 대신 상태 코드, 걸린 시간, 응답 길이 등 원본 값이 없는 정보를 남기는 방법을 사용할 수 있어요. 실습의 막은 쪽은 본인확인 응답 수신 length=42 한 줄이었어요.

6. ⑤ 정규식이 처리하지 못한 입력 형식

앞선 코드 규칙에서 개인정보로 다루지 않은 자유 입력에도 값이 포함될 수 있어요. 실습에서는 검색어를 그대로 로깅하는 코드를 두고, 정규식 마스킹이 처리하는 범위를 열 가지 입력으로 확인했어요.

흔한 정규식(주민번호 \d{6}-\d{7}, 전화번호 010-\d{4}-\d{4})은 열 개 중 하나만 가렸어요. 전각 숫자를 놓친 이유는 Java 정규식의 기본 설정과 관련이 있어요. Java 의 \d 는 UNICODE_CHARACTER_CLASS 가 꺼져 있으면 [0-9] 이고, 이 플래그는 패턴 안에 (?U) 로도 켤 수 있어요(java.util.regex.Pattern).

넓힌 정규식은 열 개 중 여덟을 가렸고, 둘이 남았어요. 뒷자리 일곱 자리만 따로 쓴 값은 아무 일곱 자리 숫자와 구별되지 않고, URL 인코딩된 값은 디코딩하기 전에는 숫자 사이에 %20 이 끼어 있어요. 처리 범위를 넓힐 때의 영향도 있어요. 구분자 없는 13자리를 가리게 넓히면 13자리 주문번호나 거래 번호도 같이 가려져요. 처리 범위를 넓히면 개인정보가 아닌 값도 가릴 수 있고, 좁히면 개인정보가 남을 수 있어요. 그래서 원본 값을 로그에 넣지 않는 코드 규칙을 우선하고, 정규식 마스킹을 보완책으로 적용했어요.

7. 대응책 열 가지의 적용 범위 비교

막는 법을 하나씩만 켜고 다섯 경로를 돌려 남은 값을 셌어요. 기준은 아무것도 켜지 않은 실행의 6·1·1·4·10, 합계 22개예요. 정적 검사(ArchUnit)는 로그를 바꾸지 않으니 따로 돌려 위반 건수로 봤어요.

실습의 코드 규칙은 ①~③에만 적용했고, ⑤의 검색어 로깅은 비교를 위해 그대로 두었어요. 따라서 이 결과는 코드 규칙 자체가 자유 입력을 처리할 수 없다는 뜻이 아니라, 실습에서 지정한 적용 범위를 보여 줘요.

ArchUnit 규칙은 처음에 두 개를 넣었어요. 하나는 "@Pii 필드를 가진 클래스의 toString 이 그 필드나 getter 를 직접 부르면 위반"이고, 다른 하나는 "저장소 패키지에서 Throwable 을 받는 예외 생성자를 부르면 위반"이에요. 첫 규칙은 @Data 판과 @ToString.Exclude 판에서 위반 5건을 찾았고, 마스킹 메서드 판과 허용 목록 판은 통과시켰어요. 그런데 record 는 못 잡았어요.

record 의 toString 은 invokedynamic 한 줄로 ObjectMethods.bootstrap 을 부르고, 필드는 그 부트스트랩 인자에 REF_getField 핸들로만 들어 있어요. ArchUnit 은 그 인자를 필드 접근으로 세지 않았어요. 그래서 record 는 isRecord() 와 toString 재정의 여부를 보는 규칙을 따로 둬야 해요. 세 번째 규칙으로 "@Pii 구성 요소를 가진 record 의 toString 에 필드 접근도 메서드 호출도 없으면 위반"을 넣자, 컴파일러가 만든 toString 을 그대로 쓰는 SignupRecord 1건이 잡혔고 toString 을 직접 쓴 SignupRecordSafe 는 통과했어요. 세 규칙의 위반은 합쳐 7건이었어요.

@Data 는 소스 보존이라 클래스 파일에 남지 않지만, Lombok 이 만든 메서드에는 @lombok.Generated 가 붙어 있어 "생성된 toString 인가"는 바이트코드에서도 알 수 있어요.

이 규칙은 toString 이 직접 읽는 것만 확인해요. 마스킹 메서드 판이 통과한 것도 toString 이 maskedRrn() 을 부르고, 원본 필드는 그 메서드 안에서 읽기 때문이에요. 마스킹 메서드가 실수로 원본을 그대로 돌려줘도 이 규칙으로는 찾지 못해요. 그 부분은 실제 로그 출력을 확인하는 단언 테스트로 보완해야 해요.

둘째 규칙은 첫 실행에서 오탐을 냈어요. 막은 쪽 예외 클래스가 super(m, null, false, false) 를 불렀는데, 인자 값은 null 이어도 시그니처에 Throwable 이 있어서 걸렸어요. super(m) 으로 바꾸자 원인 예외를 그대로 전달하는 저장소 1건만 남았어요. 이 규칙은 실제 인자 값이 아니라 생성자 시그니처를 검사하므로, 그 범위를 고려해 코드 관례를 정해야 해요.

⚠️ 이 숫자로 말할 수 있는 것과 없는 것
• 경로마다 대표 코드와 가짜 값 한 벌로 잰 결과예요. 실제 코드베이스의 비율이 아니라 "이 방법이 이 모양을 막느냐"의 확인이에요
• HTTP 덤프는 Apache HttpClient 5.6.5 의 wire 로거 하나만 봤어요. 다른 클라이언트의 로깅 인터셉터는 형식이 달라요
• DB 메시지는 H2 2.3.232 에서 재현했고, MySQL 은 오류 문서의 메시지 형식만 확인했어요
• 다루지 않은 경로도 있어요. Hibernate 의 바인딩 파라미터 로깅(org.hibernate.orm.jdbc.bind 를 TRACE 로 켤 때), 접근 로그와 MDC 에 실리는 쿼리스트링은 이번 실습에서는 확인하지 않았어요

8. 코드·로깅 설정·테스트에서 확인할 항목

실습에서 확인한 대응은 소스 코드, 로깅 설정, 검사로 나눌 수 있어요. DTO 와 예외를 만드는 코드에서 출력할 값을 제한하고, 라이브러리 로거와 패턴을 설정한 뒤, 정적 규칙과 로그 단언 테스트로 확인하는 방식이에요.

💡 체크리스트
• DTO·엔티티 전체를 로그 인자로 넘기기보다 식별자와 건수만 남겨요. 객체를 넘겨야 하면 @ToString(onlyExplicitlyIncluded = true) 로 허용 목록을 사용해요. 실습의 제외 목록은 지정하지 않은 필드를 그대로 출력했어요
• record 로 바꾼 DTO 는 toString 을 직접 재정의하거나 로그 인자에서 제외해요. 실습에서 Lombok 설정과 toString 필드 접근 규칙은 record 의 출력을 제한하지 못했어요. 정적 검사로 찾으려면 record 용 규칙이 따로 필요해요
// 실습 PiiRules 의 규칙 3 (ArchCondition 안쪽) if (c.isRecord() && hasPiiField(c)) { c.tryGetMethod("toString").ifPresent(m -> { if (m.getFieldAccesses().isEmpty() && m.getMethodCallsFromSelf().isEmpty()) events.add(SimpleConditionEvent.violated(c, c.getSimpleName() + " 는 컴파일러가 만든 toString 을 그대로 쓴다")); }); } • 검사 예외 메시지에는 값 대신 필드 이름과 길이를 넣어요. 거부된 입력값은 마스킹 정규식의 예상 형식과 다를 수 있어요
• 저장소 계층에서 드라이버 예외를 감쌀 때는 원본 값이 담기는지 확인하고, 원인을 제외한 SQLState·오류 코드·식별자 등으로 제한해요. 실습의 평문 컬럼 유니크 위반 메시지에는 값이 들어 있었어요
• HTTP 클라이언트의 wire·본문 로거 수준을 설정 파일에 명시해요. 루트 로그 수준을 DEBUG 로 바꿀 때 함께 켜지는지 확인해요
• 정규식 마스킹은 %replace(%msg%n%ex){…} 처럼 예외까지 포함하고(%nopex 는 의도를 적어 두는 용도), (?U) 와 여러 구분자를 포함해요. 실습에서는 그래도 뒷자리만 쓴 값과 URL 인코딩된 값이 남았어요
• 테스트에 가짜 값을 넣고 로그 출력에 그 값이 없는지 단언해요. 바이트 표기·URL 인코딩·전각 숫자 등 실습에서 확인한 변형도 정규화한 뒤 검색해요

마지막 항목에서 필요한 잔여 값 집계는 이 실습의 leaks.py 로 확인했어요. 이 스크립트는 다섯 경로에서 지정한 가짜 값이 몇 개 남았는지 세며, 값이 없다고 단언하거나 로그 발생을 막지는 않아요. 테스트가 실행한 경로와 지정한 가짜 값만 확인해요. 당시 업무에서도 로컬 DB 실측 후 "로그에 이름·계좌번호 0건"을 확인 항목으로 남겼어요(5편).

✍️ 오늘의 요약
컬럼 암호화와 별개로 DTO 출력, 예외 메시지, DB 원인 예외, HTTP 클라이언트 덤프, 자유 입력의 로그를 확인해야 해요. 실습에서는 가짜 값 한 벌이 22개로 집계됐고, 개별 대응책 중 가장 적게 남은 결과도 5개였어요. 여러 대응책을 조합한 실행에서는 ①~④가 0개였지만, ⑤의 뒷자리만 쓴 값과 URL 인코딩된 값 2개는 남았어요. @ToString.Exclude 는 지정하지 않은 필드를, Lombok 과 toString 필드 접근 규칙은 record 를, %replace(%msg) 는 Caused by 줄을 처리하지 못했어요.

실습에서는 출력할 값을 코드에서 제한하고, 라이브러리 로거 수준과 예외를 포함한 마스킹 패턴을 설정했어요. 가짜 값을 넣은 로그 검사로 남은 값을 확인했으며, 이 결과의 범위는 실습에 포함한 코드와 입력이에요. 실제 서비스의 전체 경로를 확인하거나 현재 조치 완료를 판단한 결과로 확대할 수는 없어요.
