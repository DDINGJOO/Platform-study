주민번호 컬럼을 암호화했고, DB 를 열어 보면 암호문만 보입니다. 그런데 로그 검색창에 주민번호 뒷자리 일곱 자리를 넣으면 결과가 나와요. DB 는 지켰는데 같은 값이 다른 길로 로그에 내려앉은 겁니다.

그 길이 몇 개인지 세어 보려고 작은 Java 프로그램 하나에 흔한 코드 다섯 줄을 넣고 돌렸어요. 가짜 이름·주민번호·전화번호 한 벌이 지나가자 로그에 값 22개가 남았습니다. 막는 법을 하나씩 켜 보니 어느 것도 혼자서는 다섯 경로를 다 막지 못했고, 전부 켠 뒤에도 2개가 남았어요.

이 글은 컬럼은 암호화했는데 개인정보가 로그에 남는다면 어디로 새고, 무엇으로 막나에 답합니다. 경로마다 새는 화면과 막은 화면을 나란히 보이고, 막는 법 열 가지가 다섯 경로 가운데 무엇을 막고 무엇을 못 막는지 실제로 센 표로 정리했어요.

• 내 코드에서 오늘 바꿀 것은 무엇인가?

1. 실습: 값 한 벌을 다섯 길로 흘려 보낸다

실습 코드는 labs/security/pii-07-log-leaks/ 에 있어요. Java 25, Lombok 1.18.48, SLF4J 2.0.17 과 Logback 1.5.18, H2 2.3.232, Apache HttpClient 5.6.5, ArchUnit 1.5.1 을 쓰고 Docker 는 쓰지 않습니다. 넣는 값은 전부 가짜예요. 이름 김가짜, 주민번호 000000-9876543, 전화번호 010-0000-0000 입니다.

프로그램은 다섯 경로를 차례로 지나갑니다. 가입 요청 DTO 를 통째로 로깅하고(①), 형식이 틀린 주민번호로 검사 예외를 던지고(②), 같은 전화번호를 두 번 넣어 DB 유니크 제약을 깨고(③), 외부 본인확인 API 를 흉내 낸 로컬 서버에 HTTP 요청을 보내고(④), 마지막으로 검색어 열 개를 그대로 로깅해요(⑤). 막는 법은 시스템 속성으로 하나씩 켭니다.

그림 1. 다섯 길은 모두 Logback 을 지나지만, 지날 때의 모양이 서로 다릅니다

남은 값은 scripts/leaks.py 가 셉니다. 같은 값이 다른 모양으로 남아도 잡아야 하니까 줄마다 HttpClient 의 바이트 표기([0xffffffea])를 바이트로 되돌리고, URL 인코딩을 풀고, NFKC 정규화로 전각 숫자를 반각으로 바꾸고, 공백·점·대시를 지운 뒤 가짜 값을 찾아요. 한 줄에 이름과 전화번호가 같이 있으면 2개로 셉니다. 아무것도 켜지 않은 실행에서 ①이 6개, ②가 1개, ③이 1개, ④가 4개, ⑤가 10개로 합계 22개였어요. 아무것도 켜지 않은 기준 실행, 막는 법을 하나씩 켠 아홉 번, 전부 켠 한 번까지 11번을 한 묶음으로 세 번 돌렸는데 세 번 모두 숫자가 같았습니다.

아래는 아무것도 켜지 않은 실행과 전부 켠 실행을 경로별로 붙여 본 화면이에요. 새는 쪽은 값이 남은 줄만, 막은 쪽은 스택 줄을 뺀 전부를 보여 줍니다.

그림 2. 새는 로그와 막은 로그. 전부 켜도 ⑤에서 두 줄이 남습니다

2. ① DTO 를 통째로 찍으면 새로 붙은 필드부터 샌다

가장 흔한 줄은 이거예요. log.info("가입 요청 {}", request). Lombok @Data 가 만든 toString 은 모든 필드를 찍으니, 이 한 줄에 이름·주민번호·전화번호 3개가 실립니다. 같은 값을 record 로 받은 줄도 3개였어요.

INFO app - 가입 요청 SignupData(name=김가짜, rrn=000000-9876543, phone=010-0000-0000, channel=web) INFO app - 가입 요청(record) SignupRecord[name=김가짜, rrn=000000-9876543, phone=010-0000-0000, channel=web]

Lombok 문서가 주는 장치는 셋입니다. 필드를 빼는 @ToString.Exclude, 인자 없는 인스턴스 메서드의 결과를 넣는 @ToString.Include(name 으로 표시 이름을 바꿀 수 있어요), 그리고 @ToString(onlyExplicitlyIncluded = true) 예요. 마지막 것은 문서 표현대로 "표시한 것 말고는 아무것도 넣지 않는다"는 뜻입니다(Lombok @ToString).

주민번호에만 @ToString.Exclude 를 붙인 판은 6개에서 5개로 줄었어요. 이름과 전화번호는 그대로였습니다. 실제 코드에서도 이 모양이 흔해요. 처음 만들 때 주민번호만 민감하다고 보고 빼 두면, 나중에 붙은 필드는 기본값대로 포함됩니다. 제외 목록은 잊은 필드를 막지 못해요.

@Data @ToString(onlyExplicitlyIncluded = true) // 허용 목록: 새 필드는 기본으로 빠진다 public class SignupAllow { @Pii private String name; @Pii private String rrn; @Pii private String phone; @ToString.Include private String channel; } @Data public class SignupMasked { // 원본은 빼고 같은 이름으로 마스킹 값을 넣는다 @Pii @ToString.Exclude private String rrn; @ToString.Include(name = "rrn") String maskedRrn() { return Masking.rrn(rrn); } // 000000-******* ... }

마스킹 메서드 판과 허용 목록 판은 둘 다 3개가 남았어요. 남은 3개는 전부 record 줄입니다. record 에는 @Data 를 붙이지 않으니 컴파일러가 만든 toString 이 모든 구성 요소를 찍어요. DTO 를 record 로 바꾸는 리팩터링 하나가 Lombok 설정을 통째로 비껴갑니다.

📖 용어: TurboFilter
Logback 이 로그 요청마다 부르는 필터예요. 문서는 "원칙적으로 LoggingEvent 객체를 만들기 전에 불린다", "한 appender 가 아니라 로깅 컨텍스트 전체에 묶인다"고 적습니다(Logback Filters). 형식 문자열과 인자 배열을 보고 통과·중립·거부를 돌려줘요. 넘어오는 인자 배열이 원본이라 기술적으로는 고쳐 쓸 여지가 있지만, API 가 의도한 일은 판정이라 이 실습에서는 거부만 썼습니다.

record 줄까지 막은 건 TurboFilter 였어요. 인자 가운데 @Pii 를 단 필드나 record 구성 요소가 있는 객체가 오면 그 줄을 버리고, 무엇을 버렸는지만 따로 남기게 했습니다. ①이 0개가 됐어요. 대신 그 로그 줄 자체가 사라집니다. 가입 요청이 왔다는 사실도 같이 없어지니, 이 필터는 안전망이고 고칠 곳은 여전히 로깅하는 코드예요.

WARN pii-guard - @Pii 객체를 인자로 받은 로그를 버림: logger=app format="가입 요청 {}" type=SignupData WARN pii-guard - @Pii 객체를 인자로 받은 로그를 버림: logger=app format="가입 요청(record) {}" type=SignupRecord

제 회사 작업에서도 이 경로는 객체의 출력 형식부터 막았어요. 암호화 배치에서 한 행을 담는 객체의 출력 형식을 id 만 찍게 해 두고, 로그와 예외에는 id 와 건수만 남겼습니다(4편). 객체를 찍는 줄이 아예 없으면 Lombok 설정이 틀려도 샐 곳이 없어요.

3. ② 형식 검사 예외는 정규식이 못 알아보는 값을 들고 온다

두 번째 줄도 흔합니다. throw new IllegalArgumentException("주민번호 형식이 아닙니다: " + v). 전역 예외 처리기가 log.warn("요청 거부", e) 로 받으면 메시지가 그대로 찍혀요.

WARN app - 요청 거부 java.lang.IllegalArgumentException: 주민번호 형식이 아닙니다: 000000 9876543

이 경로가 까다로운 이유가 있어요. 형식 검사가 실패하는 값은 정의상 형식이 틀린 값입니다. 이번에는 구분자가 공백이었고, 그래서 \d{6}-\d{7} 같은 흔한 마스킹 정규식에 걸리지 않았어요. 실제로 메시지만 가리는 판도, 예외까지 가리는 판도 ②는 1개 그대로였습니다. 정규식을 넓힌 판에서야 0개가 됐어요.

막는 법은 메시지에 값 대신 필드 이름과 길이를 싣는 겁니다. 원인 찾기에는 "어느 필드가, 몇 글자로 왔나"면 대개 충분해요.

throw new IllegalArgumentException("주민번호 형식이 아닙니다 (field=rrn, length=" + v.length() + ")"); // WARN app - 요청 거부 // java.lang.IllegalArgumentException: 주민번호 형식이 아닙니다 (field=rrn, length=14)

제 회사 작업에서 같은 판단을 한 자리가 있습니다. 암호화에 실패한 값을 로그에 찍으면 원인 찾기는 쉬워지는데, 그 값이 바로 지키려던 개인정보예요. 그래서 컨버터는 값 없이 입력 길이만 WARN 으로 남기게 했습니다(2편).

4. ③ 원인 예외는 DB 가 붙인 값을 함께 데려온다

저장소 계층에서 드라이버 예외를 감싸 다시 던지는 코드도 흔해요. throw new IllegalStateException("회원 저장 실패", e). 바깥 메시지에는 값이 없지만, 로그에는 원인 체인이 Caused by: 로 따라 찍힙니다. H2 의 유니크 제약 위반 메시지는 겹친 값을 그대로 담고 있었어요.

ERROR app - 가입 실패 java.lang.IllegalStateException: 회원 저장 실패 Caused by: org.h2.jdbc.JdbcSQLIntegrityConstraintViolationException: Unique index or primary key violation: "PUBLIC.UK_MEMBER_PHONE_INDEX_8 ON PUBLIC.MEMBER(PHONE NULLS FIRST) VALUES ( /* 1 */ '010-0000-0000' )"; SQL statement: INSERT INTO member (rrn_enc, phone) VALUES (?, ?) [23505-232]

→ 바인딩 변수는 ? 로 가려져 있지만, 제약 위반 문구가 겹친 값을 직접 보여 줘요.

여기서 컬럼 암호화가 한 일이 보입니다. 같은 주민번호를 두 번 넣었을 때의 위반 메시지에는 실습용 암호문(LABENC:...)만 찍혔어요. 암호화한 컬럼은 에러 메시지에서도 암호문이지만, 같은 테이블의 평문 컬럼은 그렇지 않습니다. 전화번호나 이메일처럼 유니크 제약을 거는 일이 많은 컬럼이 바로 그쪽이에요. MySQL 도 오류 1062(ER_DUP_ENTRY)의 메시지가 Duplicate entry '%s' for key ... 모양이라 겹친 값을 문구에 넣습니다(MySQL Server Error Reference).

📖 용어: 원인 예외 (cause)
예외를 다시 던질 때 안쪽에 달아 보내는 "무엇 때문에 실패했나"예요. 로거에 예외를 넘기면 Logback 은 바깥 예외와 원인 체인을 모두 찍습니다. 디버깅에는 좋은데, 안쪽 메시지가 그대로 바깥으로 흘러가요.

막는 법은 원인을 떼고, 원인에서 값이 아닌 것만 골라 담는 겁니다. SQLState 와 오류 코드면 중복인지, 연결 문제인지는 구분돼요.

} catch (SQLException e) { throw new MemberSaveException("회원 저장 실패 (sqlState=" + e.getSQLState() + ", errorCode=" + e.getErrorCode() + ")"); // 원인을 달지 않는다 } // lab.repo.SafeMemberRepo$MemberSaveException: 회원 저장 실패 (sqlState=23505, errorCode=23505)

대가는 스택이에요. 드라이버 안쪽 스택이 사라지니 처음 보는 오류라면 재현이 필요해집니다. 그래서 원인을 떼는 자리를 저장소 계층처럼 값이 실리는 경계로 좁히는 편이 낫습니다.

이 경로는 제 회사 작업에서도 한 번 놓쳤어요. "쓰기 예외는 원인을 떼고 다시 던진다"는 방침이 문서에 있었는데, 새로 만든 배치 코드는 원인 예외를 그대로 달아 던지고 있었고 독립 리뷰가 그걸 잡았습니다. 그 예외는 배치 스케줄러 로그와 실패 알림으로 그대로 나가는 길이었어요(5편). 방침만으로는 코드가 따라오지 않으니, 뒤에서 볼 정적 검사가 필요해집니다.

%replace(%msg) 는 Caused by 줄을 가리지 않는다

📖 용어: PatternLayout, 변환어
Logback 이 로그 이벤트 하나를 글자 한 줄로 그리는 규칙이에요. %msg(메시지), %ex(예외와 원인 체인), %level 같은 변환어를 이어 붙여 모양을 정합니다. 메시지와 예외는 서로 다른 변환어가 따로 그려요.

로깅 층에서 정규식으로 가리는 방법도 같이 봤어요. Logback 의 %replace(p){r, t} 는 "하위 패턴 p 가 만든 문자열에서" 정규식 r 을 t 로 바꿉니다. 그리고 PatternLayout 은 패턴에 예외용 변환어가 없으면 "스택 정보가 중요하므로" 그것을 맨 끝에 자동으로 붙여요(Logback Layouts). 그러니 %replace(%msg) 만 걸면, 자동으로 붙은 예외 부분은 replace 바깥에서 찍힙니다.

그림 3. 정규식은 자기가 감싼 글자만 봅니다
<!-- 메시지만: ③ 이 그대로 샌다 --> <pattern>%-5level %logger{0} - %replace(%msg){'\d{6}-\d{7}', '[주민번호]'}%n</pattern> <!-- 메시지와 예외를 함께. %nopex 는 "예외는 이미 위에서 그렸다"는 의도를 적어 두는 안전장치 --> <pattern>%-5level %logger{0} - %replace(%msg%n%ex){'\d{6}-\d{7}', '[주민번호]'}%nopex</pattern>

측정도 그대로 나왔어요. 메시지만 가린 판은 ③이 1개 남았고, 예외까지 감싼 판은 0개였습니다. %nopex 는 꼭 있어야 하는 건 아니었어요. Logback 1.5.18 은 %replace 안에 든 %ex 도 예외 변환어로 인정해 자동 %ex 를 붙이지 않았고, %nopex 만 뺀 설정으로 다시 돌려도 예외는 한 번만 찍히고 결과도 13개로 같았습니다. 그래도 버전이 바뀌어도 의도가 남도록 적어 두는 편을 권해요.

5. ④ HTTP 클라이언트 덤프는 본문을 통째로 찍는다

외부 API 를 부르는 쪽은 장애가 나면 요청·응답을 보고 싶어집니다. Apache HttpClient 5 는 org.apache.hc.client5.http.wire 로거를 DEBUG 로 켜면 오가는 바이트를, ...http.headers 를 켜면 헤더를 찍어요. 요청 본문과, 받은 전화번호를 되돌려 주는 응답 본문이 둘 다 찍혀 값 4개가 남았습니다.

📖 용어: wire 로그
HTTP 클라이언트가 소켓에 쓰고 읽은 바이트를 그대로 남기는 로그예요. >> 는 보낸 것, << 는 받은 것입니다. 헤더 로그와 달리 본문이 들어가요.
DEBUG wire - http-outgoing-0 >> "{"name":"[0xffffffea][0xffffffb9][0xffffff80][0xffffffea]...","rrn":"000000-9876543","phone":"010-0000-0000"}" DEBUG wire - http-outgoing-0 << "{"result":"MATCH","phone":"010-0000-0000"}"

→ 이름은 UTF-8 바이트가 [0xffffffea] 꼴로 한 바이트씩 찍혔어요. 사람 눈으로도, 로그 검색으로도 이름이라는 걸 알아보기 어렵습니다.

정규식 마스킹을 켜면 주민번호와 전화번호는 가려졌지만 이름 1개는 끝까지 남았어요. 정규식은 이름 모양을 모르고, 이 줄의 이름은 글자가 아니라 바이트 표기라서요. 이름도 개인정보예요. OWASP Logging Cheat Sheet 는 로그에 직접 남기지 말고 지우거나 가리거나 해시·암호화할 것들 가운데 "개인 이름, 전화번호, 이메일 주소 같은 민감하지 않은 개인정보"를 따로 적어 둡니다(OWASP Logging Cheat Sheet).

④를 0개로 만든 건 wire·headers 로거 수준을 설정 파일에 INFO 로 명시하는 것 하나였어요. 루트 수준에 기대지 않고 적어 두는 이유가 있습니다. 장애 때 누군가 루트를 DEBUG 로 내리는 순간 이 덤프가 같이 켜지거든요. 본문이 꼭 필요하면 덤프 대신 상태 코드, 걸린 시간, 응답 길이 같은 값이 아닌 것을 직접 찍으면 됩니다. 실습의 막은 쪽은 본인확인 응답 수신 length=42 한 줄이었어요.

6. ⑤ 마스킹 정규식은 모양이 하나 다르면 놓친다

로깅 층의 정규식은 마지막 안전망입니다. 검색어, 메모, 상담 내용처럼 개발자가 개인정보라고 생각하지 못한 자유 입력은 여기서만 걸러져요. 그래서 그 그물이 무엇을 놓치는지 열 가지 입력으로 봤습니다.

흔한 정규식(주민번호 \d{6}-\d{7}, 전화번호 010-\d{4}-\d{4})은 열 개 중 하나만 가렸어요. 전각 숫자를 놓친 이유는 Java 정규식에 있습니다. Java 의 \d 는 UNICODE_CHARACTER_CLASS 가 꺼져 있으면 [0-9] 이고, 이 플래그는 패턴 안에 (?U) 로도 켤 수 있어요(java.util.regex.Pattern).

넓힌 정규식은 열 개 중 여덟을 가렸고, 둘이 남았어요. 뒷자리 일곱 자리만 따로 쓴 값은 아무 일곱 자리 숫자와 구별되지 않고, URL 인코딩된 값은 디코딩하기 전에는 숫자 사이에 %20 이 끼어 있습니다. 반대쪽 대가도 있어요. 구분자 없는 13자리를 가리게 넓히면 13자리 주문번호나 거래 번호도 같이 가려집니다. 정규식은 넓힐수록 정상 로그를 망가뜨리고, 좁힐수록 새요. 그래서 정규식은 앞의 막는 법들이 놓친 것을 줍는 마지막 단계로만 씁니다.

7. 막는 법 열 가지가 막는 것과 못 막는 것

막는 법을 하나씩만 켜고 다섯 경로를 돌려 남은 값을 셌어요. 기준은 아무것도 켜지 않은 실행의 6·1·1·4·10, 합계 22개입니다. 정적 검사(ArchUnit)는 로그를 바꾸지 않으니 따로 돌려 위반 건수로 봤어요.

코드 규칙이 ⑤를 못 막는 건 일부러 그렇게 짰어요. 검색어를 로깅하는 개발자는 그것이 개인정보라고 생각하지 않습니다. 규칙은 사람이 개인정보라고 알아본 곳에만 걸려요.

ArchUnit 규칙은 처음에 두 개를 넣었어요. 하나는 "@Pii 필드를 가진 클래스의 toString 이 그 필드나 getter 를 직접 부르면 위반"이고, 다른 하나는 "저장소 패키지에서 Throwable 을 받는 예외 생성자를 부르면 위반"입니다. 첫 규칙은 @Data 판과 @ToString.Exclude 판에서 위반 5건을 찾았고, 마스킹 메서드 판과 허용 목록 판은 통과시켰어요. 그런데 record 는 못 잡았습니다. record 의 toString 은 invokedynamic 한 줄로 ObjectMethods.bootstrap 을 부르고, 필드는 그 부트스트랩 인자에 REF_getField 핸들로만 들어 있어요. ArchUnit 은 그 인자를 필드 접근으로 세지 않았습니다. 그래서 record 는 isRecord() 와 toString 재정의 여부를 보는 규칙을 따로 둬야 해요. 세 번째 규칙으로 "@Pii 구성 요소를 가진 record 의 toString 에 필드 접근도 메서드 호출도 없으면 위반"을 넣자, 컴파일러가 만든 toString 을 그대로 쓰는 SignupRecord 1건이 잡혔고 toString 을 직접 쓴 SignupRecordSafe 는 통과했습니다. 세 규칙의 위반은 합쳐 7건이었어요. @Data 는 소스 보존이라 클래스 파일에 남지 않지만, Lombok 이 만든 메서드에는 @lombok.Generated 가 붙어 있어 "생성된 toString 인가"는 바이트코드에서도 알 수 있습니다.

이 규칙에는 한계가 하나 더 있어요. toString 이 직접 읽는 것만 봅니다. 마스킹 메서드 판이 통과한 것도 toString 이 maskedRrn() 을 부르고, 원본 필드는 그 메서드 안에서 읽기 때문이에요. 마스킹 메서드가 실수로 원본을 그대로 돌려줘도 이 규칙은 모릅니다. 그 부분은 로그 단언 테스트가 맡아야 해요.

둘째 규칙은 첫 실행에서 오탐을 냈습니다. 막은 쪽 예외 클래스가 super(m, null, false, false) 를 불렀는데, 인자 값은 null 이어도 시그니처에 Throwable 이 있어서 걸렸어요. super(m) 으로 바꾸자 새는 저장소 1건만 남았습니다. 정적 검사는 값이 아니라 모양을 보니, 규칙이 잡는 모양을 코드 관례로 맞춰 두어야 해요.

⚠️ 이 숫자로 말할 수 있는 것과 없는 것
• 경로마다 대표 코드 한 줄, 가짜 값 한 벌로 잰 것입니다. 실제 코드베이스의 비율이 아니라 "이 방법이 이 모양을 막느냐"의 확인이에요
• HTTP 덤프는 Apache HttpClient 5.6.5 의 wire 로거 하나만 봤어요. 다른 클라이언트의 로깅 인터셉터는 형식이 다릅니다
• DB 메시지는 H2 2.3.232 에서 재현했고, MySQL 은 오류 문서의 메시지 형식만 확인했어요
• 다루지 않은 경로도 있어요. Hibernate 의 바인딩 파라미터 로깅(org.hibernate.orm.jdbc.bind 를 TRACE 로 켤 때), 접근 로그와 MDC 에 실리는 쿼리스트링은 이번 실습 밖입니다

8. 내 코드에서 오늘 바꿀 것

다섯 경로를 막는 자리는 하나가 아니라 셋입니다. 소스(DTO 와 예외를 만드는 코드), 로깅 설정(라이브러리 로거와 패턴), 그리고 검사(정적 규칙과 로그 단언 테스트)예요.

💡 체크리스트
• DTO·엔티티는 로그 인자로 넘기지 않는다. 식별자와 건수만 찍는다. 넘겨야 하는 객체는 @ToString(onlyExplicitlyIncluded = true) 로 허용 목록을 쓴다. 제외 목록은 새 필드를 막지 못했다
• record 로 바꾼 DTO 는 toString 을 직접 재정의하거나 로그 인자에서 뺀다. Lombok 설정과 toString 필드 접근 규칙이 둘 다 record 를 비껴갔다. 규칙으로 막으려면 아래처럼 record 용을 따로 둔다
// 실습 PiiRules 의 규칙 3 (ArchCondition 안쪽) if (c.isRecord() && hasPiiField(c)) { c.tryGetMethod("toString").ifPresent(m -> { if (m.getFieldAccesses().isEmpty() && m.getMethodCallsFromSelf().isEmpty()) events.add(SimpleConditionEvent.violated(c, c.getSimpleName() + " 는 컴파일러가 만든 toString 을 그대로 쓴다")); }); } • 검사 예외 메시지에는 값 대신 필드 이름과 길이를 싣는다. 틀린 값은 정규식이 알아보지 못하는 모양으로 온다
• 저장소 계층에서 드라이버 예외를 감쌀 때 원인을 떼고 SQLState·오류 코드·식별자만 담는다. 평문 컬럼의 유니크 위반 메시지에 값이 들어 있었다
• HTTP 클라이언트의 wire·본문 로거 수준을 설정 파일에 명시한다. 루트를 DEBUG 로 내리는 날 같이 켜지지 않게
• 정규식 마스킹은 %replace(%msg%n%ex){…} 처럼 예외까지 감싸고(%nopex 는 의도를 적어 두는 용도), (?U) 와 여러 구분자를 넣는다. 그래도 뒷자리만 쓴 값과 URL 인코딩된 값은 남는다
• 테스트에서 가짜 값을 흘린 뒤 로그 출력에 그 값이 없는지 단언한다. 바이트 표기·URL 인코딩·전각을 정규화하고 찾아야 숨은 값까지 보인다

마지막 항목은 이 실습의 leaks.py 가 하는 일이에요. 막는 법 가운데 다섯 경로 모두에서 쓸 수 있는 건 이 단언 하나였습니다. 다만 테스트가 지나간 경로에서만 동작해요. 제 회사 작업에서도 로컬 DB 실측 끝에 "로그에 이름·계좌번호 0건"을 확인 항목으로 남겼습니다(5편).

✍️ 오늘의 요약
컬럼을 암호화해도 개인정보는 DTO 의 toString, 예외 메시지, 원인 예외에 실린 DB 메시지, HTTP 클라이언트 덤프, 정규식이 못 알아보는 자유 입력으로 로그에 닿습니다. 실습에서 가짜 값 한 벌이 값 22개로 남았고, 막는 법을 하나만 켰을 때는 가장 적게 남은 판도 5개였으며, 전부 켜도 2개가 남았어요. @ToString.Exclude 는 잊은 필드를, Lombok 과 toString 필드 접근 규칙은 record 를, %replace(%msg) 는 Caused by 줄을, 정규식은 이름과 URL 인코딩된 값을 놓쳤습니다.

그래서 값을 로그 인자로 넘기지 않는 코드 규칙을 먼저 두고, 라이브러리 로거를 설정에 명시하고, 정규식은 마지막 그물로만 씁니다. 그리고 가짜 값을 흘려 로그에 남지 않았는지 세어 보는 테스트로 확인해요. 로그 유출은 한 곳에서 막는 게 아니라, 값이 글자로 바뀌는 자리마다 따로 막아야 합니다.
