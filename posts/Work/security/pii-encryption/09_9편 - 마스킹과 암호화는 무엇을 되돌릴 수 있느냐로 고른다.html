개인정보 컬럼을 보호하라는 요청을 받으면 보통 세 가지가 후보로 오릅니다. 마스킹, 암호화, 그리고 키 있는 해시(HMAC)로 바꾼 토큰이에요. 셋은 강도 순서로 줄 세울 수 있는 것이 아니라 무엇을 되돌릴 수 있게 남기느냐가 서로 다릅니다. 이 글은 같은 가짜 계좌번호 여섯 행에 세 방식을 실제로 적용해 그 차이를 숫자로 보고, 고르는 기준을 정리해요.

1. 네 방식은 원문을 어디에 남기나

마스킹을 하나로 묶어 부르면 판단이 꼬입니다. 별표를 언제 치느냐에 따라 원문이 살아남는지가 정반대로 갈리거든요.

📖 용어: 표시용 마스킹 / 저장용 마스킹
표시용 마스킹은 원문(또는 암호문)을 그대로 저장해 두고, 화면·응답·로그로 내보낼 때만 일부를 가리는 방식이에요. 저장용 마스킹은 가린 값을 저장하고 원문을 버립니다. 앞쪽은 권한만 있으면 원문을 다시 볼 수 있고, 뒤쪽은 누구도 볼 수 없어요.

암호화는 키가 있으면 원문으로 돌아오는 방식입니다. 여기서는 AES-GCM 을 기준으로 삼았어요. 행마다 새 IV 를 뽑기 때문에 같은 값도 매번 다른 암호문이 되고, IV·본문·태그 바이트나 함께 인증한 값(이 실습에서는 AAD 로 넣은 키 ID)을 바꾸면 복호화가 실패로 끝납니다. OWASP Cryptographic Storage Cheat Sheet 는 인증 모드를 쓸 수 있으면 항상 쓰고, 그중 GCM 과 CCM 을 먼저 고르라고 적어요(OWASP Cryptographic Storage).

📖 용어: AES-GCM (인증 암호화)
AES 블록 암호를 GCM 모드로 쓰는 방식이에요. 암호문 끝에 위조 검사용 태그가 붙어서, 키가 틀렸거나 값이 바뀌었으면 엉뚱한 평문 대신 예외를 던집니다. 같은 키로 IV 가 한 번이라도 겹치면 안전성이 무너지므로 IV 를 매번 새로 뽑아야 해요.

NIST SP 800-38D 는 이 조건을 "같은 IV 와 같은 키로 서로 다른 입력을 암호화할 확률이 2-32 를 넘으면 안 된다" 로 적고, 실무에서는 이 요구가 키를 비밀로 지키는 것과 거의 같은 만큼 중요하다고 덧붙입니다(NIST SP 800-38D, 8절). 그래서 같은 값이 같은 암호문이 되게 하려고 GCM 의 IV 를 고정하는 것은 선택지가 아닙니다. 등치 조회가 꼭 필요할 때의 방법은 6편에서 따로 다뤄요.

📖 용어: HMAC 토큰 (키 있는 해시)
비밀 키와 값을 함께 해시해서 고정 길이 토큰을 만드는 방식이에요. 같은 키, 같은 값이면 항상 같은 토큰이 나와서 등치 조회 열로 쓸 수 있습니다. 복호화 연산은 없어요. 원문을 아는 쪽이 다시 계산해 비교만 할 수 있습니다.
그림 1. 같은 계좌번호가 네 방식에서 DB 와 화면에 남기는 것

그림에서 표시용 마스킹만 성격이 다릅니다. 나머지 셋은 "무엇을 저장하나" 의 답이고, 표시용 마스킹은 "무엇을 내보내나" 의 답이에요. 그래서 실제 설계는 대개 둘을 겹칩니다. 저장은 AES-GCM 으로 하고, 출구에서 표시용 마스킹을 거는 식이에요. 고를 것은 저장 방식이고, 표시용 마스킹은 그 위에 얹는 출구 규칙입니다.

2. 실습: 같은 여섯 행에 세 방식을 적용했다

입력은 가짜 계좌번호 세 개를 섞은 여섯 행입니다. A 가 세 번, B 가 두 번, C 가 한 번이에요. C 는 일부러 A 와 끝 여섯 자리가 같게 골랐습니다. 마스킹은 앞 세 자리와 끝 두 자리만 남기고, AES-GCM 은 AES-256 에 행마다 새 96비트 IV, HMAC 은 HMAC-SHA256 입니다. 키는 실습용 문자열에서 만든 고정 키이고, 암호문 앞의 lab9$k1$ 도 이 실습에서만 쓰는 표시예요.

git clone https://github.com/DDINGJOO/Platform-study.git cd Platform-study/labs/security/pii-09-mask-vs-encrypt java src/MaskVsEncrypt.java # JDK 11 이상, 외부 라이브러리 없음

OpenJDK 25.0.3 에서 돌렸고, 코드는 labs/security/pii-09-mask-vs-encrypt 에 있습니다. 세 번 돌렸고, AES-GCM 암호문 줄(IV 가 매번 달라서 실행마다 다릅니다)을 뺀 나머지 출력은 세 번 모두 같았어요. 아래 캡처 두 장은 그 세 번과 별도로 다시 돌려 같은 숫자가 나온 실행의 화면이고, 출력 앞부분([1]~[4], 1~27줄)과 뒷부분([5]~[7], 28~48줄)을 나눠 찍었습니다.

그림 2. (출력 1~27줄) 되돌리기, 같은 값의 출력, 등치 조회를 한 화면에서 비교했다

숫자를 하나씩 읽어 볼게요.

저장용 마스킹 AES-GCM HMAC 원문으로 되돌린 행 0/6 6/6 (복호화 없음) 서로 다른 출력 (입력 3) 2 6 3 WHERE = f(A) (정답 1,3,5) 1,3,4,5 없음 1,3,5 가장 많이 나온 출력의 빈도 4 1 3

저장용 마스킹은 되돌리지 못하는 것만이 문제가 아니었어요. 서로 다른 입력 세 개가 출력 두 개로 줄었습니다. A 와 C 가 같은 999-**-****01 이 됐거든요. 그래서 마스킹한 값으로 A 를 찾으면 C 가 있는 4행까지 걸립니다. 마스킹 값은 식별자가 아니에요. 이 열을 조회 키나 중복 판정에 쓰면 엉뚱한 사람의 행이 섞입니다.

AES-GCM은 여섯 행이 모두 다른 암호문이 됐어요. 같은 A 세 번도 서로 다릅니다. 그래서 암호문만 본 사람은 몇 행이 같은 계좌인지 알 수 없고(최다 빈도 1), 같은 이유로 WHERE 암호문 = 새로 암호화한 A 는 아무것도 찾지 못해요. 대신 키가 있으면 6행 전부가 원문으로 돌아왔습니다.

HMAC은 정확히 원문의 구조를 따라갑니다. 출력이 세 개이고 A 를 찾으면 1,3,5행만 걸려요. 등치 조회가 되는 대신, 토큰만 본 사람도 "이 토큰이 세 번 나온다" 는 사실을 압니다. 원문을 몰라도 같은 사람의 행끼리 묶을 수 있다는 뜻이에요.

⚠️ 주의: 등치 조회와 빈도 노출은 같은 성질입니다
같은 값이 같은 출력이 되어야 WHERE 로 찾을 수 있고, 같은 값이 같은 출력이 되면 몇 번 나왔는지가 드러나요. 둘 중 하나만 갖는 방식은 없습니다. 그래서 HMAC 토큰 열을 둘지는 "그 컬럼을 값으로 찾는 조회가 정말 있나" 를 먼저 확인하고 정하세요. 등치 조회가 남아 랜덤 IV 를 쓸 수 없었던 이야기는 3편에 있습니다(3편).

부분 검색과 정렬은 셋 다 잘 안 됩니다

"끝 네 자리로 찾기", "이름 앞글자로 찾기", "번호순 정렬" 은 세 방식 어느 쪽도 그대로는 못 해요. AES-GCM 과 HMAC 의 출력은 원문의 앞뒤 순서나 부분을 전혀 담지 않고, 저장용 마스킹은 남긴 자리로만 찾을 수 있는데 그마저 위에서 본 대로 겹칩니다. 부분 검색이 꼭 필요하면 "끝 네 자리" 같은 조각을 별도 열로 따로 저장하게 되는데, 그 조각은 경우의 수가 1만 개뿐이에요. 조각 하나를 HMAC 으로 바꿔도 아래 3절의 키 유출 문제가 그대로 커집니다. 정렬은 대상 행을 먼저 다른 조건으로 좁힌 뒤, 애플리케이션에서 복호화해서 하는 수밖에 없어요.

3. 키를 잃을 때와 키가 샐 때

암호화와 HMAC 의 보호는 전부 키에서 나옵니다. 그러니 키에 생길 수 있는 두 사고, 잃어버리는 것과 새어 나가는 것을 따로 봐야 해요. 실습의 마지막 부분이 키를 k1 에서 k2 로 바꾼 결과입니다.

그림 3. (출력 28~48줄) 키를 바꾸면 GCM 은 다시 암호화해야 하고, HMAC 은 원문이 있어야 다시 계산된다

AES-GCM 행 여섯 개를 k2 로 풀면 6/6 이 AEADBadTagException 으로 실패합니다. 키가 틀리면 태그 검증에서 걸리니 틀린 평문이 조용히 나오지는 않아요. 저장할 때 앞에 붙여 둔 키 ID(k1)로 옛 키를 골라 풀고 k2 로 다시 암호화하자 6/6 이 k2 로 복호화됐습니다. OWASP 도 키를 바꾼 뒤 기존 데이터는 새 키로 다시 암호화하는 쪽을 먼저 권하고, 그게 어려우면 항목마다 쓴 키의 ID 를 표시해 두라고 적어요(OWASP Cryptographic Storage, Key Lifetimes and Rotation). 반대로 말하면 옛 키는 마지막 행을 다시 암호화할 때까지 버리면 안 됩니다. OWASP 는 은퇴한 키도 옛 백업을 풀 수 있도록 한동안 보관하라고 적어요. 그 키로 암호화된 백업이 보존 기간 안에 남아 있다면 키도 그때까지 있어야 합니다. 이 순서를 운영 중에 지키는 방법은 8편의 전환 순서와 같아요.

HMAC 은 다른 방식으로 곤란해집니다. k2 로 계산한 A 의 토큰으로 기존 행을 찾으면 아무것도 걸리지 않아요. 기존 토큰은 k1 으로 만든 것이니까요. 토큰을 k2 로 다시 계산하려면 원문이 있어야 하는데, 토큰에서 원문을 꺼낼 방법은 없습니다. 실습에서는 같은 행의 AES-GCM 열을 풀어 원문을 얻고 다시 계산했고, 그제야 1,3,5행이 찾아졌어요. HMAC 토큰만 저장한 컬럼은 원문이 다시 들어오기 전까지 키를 바꿀 수 없습니다. 사용자가 같은 값을 다시 입력할 때마다 새 키로 바꿔 쓰는 점진 교체는 가능해요. OWASP Password Storage Cheat Sheet 도 같은 구조를 적어요. pepper 는 사용자의 비밀번호를 모르면 바꿀 수 없어서 이전 pepper 로 보호된 사용자에게 비밀번호를 다시 정하게 해야 하고, 작업 계수를 올릴 때는 사용자가 다음에 인증할 때 다시 해시하라고 합니다. 어느 쪽이든 원문이 다시 들어와야 바뀝니다. 다만 그 값이 다시 들어오지 않는 행은 끝까지 옛 키에 묶여요. 한 번에 바꿔야 할 가능성이 있다면 원문을 얻을 경로(암호문 열)를 함께 두어야 합니다.

키가 새는 쪽은 실습으로 재지 않았습니다. 원리만 공개 자료로 적을게요.

키 없는 해시(SHA-256 한 번)는 누구나 같은 계산을 할 수 있습니다. ENISA 의 가명처리 보고서는 해시 함수가 무결성에는 도움이 되지만 가명처리 기법으로는 대입(brute force)과 사전 공격에 약하다고 보고, 식별자의 경우의 수가 작으면 대입이 "trivially feasible" 하다고 적어요. 반면 MAC(HMAC)은 키가 노출되지 않는 한 되돌리기가 불가능해서 견고한 기법으로 분류합니다(ENISA, Pseudonymisation techniques and best practices, 2019, 4.4.1절·5.1.3~5.1.4절). 계좌번호, 전화번호, 주민등록번호는 자릿수와 형식이 정해진 값이라 경우의 수가 작은 쪽에 속해요. OWASP Password Storage Cheat Sheet 도 SHA-256 같은 빠른 해시는 공격자가 짧은 시간에 아주 많은 추측을 해 볼 수 있게 한다고 경고하고, DB 와 따로 보관하는 비밀값(pepper)을 HMAC 의 키로 쓰는 구성을 소개합니다(OWASP Password Storage).

📖 용어: 솔트와 페퍼 (salt, pepper)
솔트는 값마다 다르게 붙이는 공개 난수예요. 미리 계산해 둔 표를 무력화하지만, 행마다 달라서 같은 값이 같은 출력이 되지 않으니 등치 조회 열로는 못 씁니다. 페퍼는 DB 밖에 따로 두는 비밀값이고, HMAC 의 키가 바로 이 자리예요.

여기서 HMAC 의 한계도 같이 나옵니다. HMAC 이 키 없는 해시보다 안전한 이유는 키 하나뿐이에요. 키가 새면 HMAC 토큰은 키 없는 해시와 같은 처지가 됩니다. 경우의 수가 작은 식별번호라면 그 키로 후보를 계산해 보는 일을 막을 것이 없어요. 그래서 HMAC 키는 암호화 키와 같은 수준으로 보관하고, 분석용 사본을 만드는 사람이 그 키에 닿지 못하게 해야 합니다.

그림 4. 키를 잃는 사고와 키가 새는 사고는 방식마다 결과가 다르다

4. 고시는 어떤 항목에 암호화를 요구하나

법적 요구는 개인정보보호위원회 고시 「개인정보의 안전성 확보조치 기준」 제7조에 있습니다. 2026-10-17 에 국가법령정보센터에서 확인한 현행본은 개인정보보호위원회고시 제2026-9호(2026. 7. 1. 시행)이고, 이 글과 관련된 항은 이렇게 적혀 있어요(국가법령정보센터).

제7조(개인정보의 암호화) ① 개인정보처리자는 비밀번호, 생체인식정보 등 인증정보를 저장 또는 정보통신망을 통하여 송ㆍ수신하는 경우에 이를 안전한 암호 알고리즘으로 암호화하여야 한다. 다만, 비밀번호를 저장하는 경우에는 복호화되지 아니하도록 일방향 암호화하여 저장하여야 한다. ② 개인정보처리자는 다음 각 호의 해당하는 이용자의 개인정보에 대해서는 안전한 암호 알고리즘으로 암호화하여 저장하여야 한다. 1. 주민등록번호 2. 여권번호 3. 운전면허번호 4. 외국인등록번호 5. 신용카드번호 6. 계좌번호 7. 생체인식정보 ③ 개인정보처리자는 이용자가 아닌 정보주체의 개인정보를 다음 각 호와 같이 저장하는 경우에는 암호화하여야 한다. 1. 인터넷망 구간 및 인터넷망 구간과 내부망의 중간 지점(DMZ : Demilitarized Zone)에 고유식별정보를 저장하는 경우 2. 내부망에 고유식별정보를 저장하는 경우(다만, 주민등록번호 외의 고유식별정보를 저장하는 경우에는 (...) 암호화의 적용여부 및 적용범위를 정하여 시행할 수 있다)

읽을 때 걸리는 지점이 셋 있어요.

첫째, ②와 ③은 대상이 다릅니다. ②의 "이용자" 는 같은 고시 제2조에서 정보통신망법상 정보통신서비스 제공자의 서비스를 이용하는 자로 정의돼요. 그 경우에는 계좌번호와 신용카드번호까지 저장 시 암호화 대상입니다. 이용자가 아닌 정보주체에 대한 ③은 고유식별정보를 기준으로 하고, 주민등록번호 외의 고유식별정보를 내부망에 저장하는 경우에는 적용 여부와 범위를 정할 수 있게 열어 둡니다. 근거는 영향평가 대상 공공기관이면 그 영향평가 결과, 그 밖에는 암호화를 적용하지 않을 때의 위험도 분석 결과예요. 내 서비스가 어느 쪽에 해당하는지는 고시 문언만으로 정하기 어려운 경우가 있으니, 개인정보위가 공개한 이 기준의 안내서(해설서)와 법무 검토로 확인하세요.

둘째, ①의 일방향 암호화는 비밀번호에 대한 요구입니다. 원문을 되돌릴 필요가 없고 되돌려서도 안 되는 값이라 이렇게 정했어요. 계좌번호를 HMAC 토큰으로만 저장하는 것이 ②의 "암호화하여 저장" 을 채우는지는 고시가 직접 말하지 않습니다. 저는 이 판단을 문언에서 끌어내지 못했고, 실무에서는 앞 절의 이유(키 교체에 원문이 필요하다)로 어차피 암호문 열을 같이 두게 됩니다.

셋째, 마스킹은 제7조가 아니라 제12조 ① 쪽에 가까워요. "개인정보의 출력시(인쇄, 화면표시, 파일생성 등) 용도를 특정하여야 하며, 용도에 따라 출력 항목을 최소화하여야 한다." 표시용 마스킹은 이 출력 최소화를 구현하는 흔한 방법이지만, 저장 시 암호화를 대신하지는 않습니다.

5. 내 컬럼에는 무엇을 고르나

지금까지 본 것을 질문 순서로 묶으면 그림 5가 됩니다. 처음 질문이 가장 무거워요. 업무상 원문을 되돌려야 하는가, 다시 말해 그 값으로 실제로 무언가를 하는 사람(송금, 본인 확인, 법정 제출)이 있는가입니다.

그림 5. 첫 질문은 "되돌려야 하나" 이고, 조회 필요는 그다음에 토큰 열을 붙일지만 정한다

사례: 이력 문장 속 계좌번호를 문장째 암호화했다

4편의 대상은 업무 이력 문구였습니다. 사람 이름과 계좌번호가 한 문장 안에 들어 있었고, 그 문장은 어드민 화면의 이력 탭에 그대로 출력돼요. 4편은 그 컬럼을 통째로 암호화하지 않고 특정 문구만 골라 문장 전체를 암호화했습니다. 같은 컬럼을 조건으로 쓰는 조회 두 곳이 통째 암호화로 깨지기 때문이었어요. 암호화한 문장은 읽을 때 복호화되어, 이력 화면과 같은 조회로 원래 문장이 그대로 나오는 것까지 확인했습니다. 원문이 화면에 그대로 나가는 자리이니, 그림 5로 옮기면 첫 질문에 "예" 인 경우에 해당합니다.

실습의 [6]은 이름과 번호가 섞인 가짜 메모 한 줄로 마스킹과 문장째 암호화를 비교합니다. 계좌번호 형식을 찾는 정규식으로 문장을 마스킹하면 계좌번호는 가려지지만 홍길동 은 패턴에 없으니 그대로 남습니다. 자유 문장에서 개인정보를 골라 가리려면 그 위치를 먼저 정확히 찾아야 하는데, 정규식은 형식이 정해진 값만 찾아요. 문장째 암호화하면 무엇이 어디 있는지 몰라도 문장 전체가 보호되고, 권한자 화면에서는 복호화한 원문을, 다른 화면에서는 복호화 뒤 표시용 마스킹을 건 문장을 보여 줄 수 있습니다. 대가도 숫자로 나왔어요. 원문 38자(UTF-8 70바이트) 문장이 암호문으로 140자가 됐습니다. 계좌번호 13자는 AES-GCM 으로 64자, HMAC 으로 44자였어요. 컬럼 길이를 이만큼 늘려야 합니다.

⚠️ 주의: 문장째 암호화에도 대가가 있었습니다
• 같은 컬럼을 조건으로 쓰는 조회가 있으면 암호화 범위를 좁혀야 하고, 그러면 한 컬럼에 평문과 암호문이 섞입니다(4편)
• 읽는 쪽이 값의 생김새로 암호문을 가리면, 사람이 쓴 글이 우연히 그 생김새로 시작할 때 복호화가 실패합니다(5편)

노출 지점마다 다시 묻기

저장 방식을 정해도 값은 여러 출구로 나갑니다. 출구마다 무엇이 보이는지 한 번씩 확인하세요.

출구 AES-GCM 저장일 때 보이는 것 해야 할 일 화면·API 응답 복호화한 원문 역할별 표시용 마스킹, 출력 항목 최소화 로그 코드가 찍는 그대로 원문·복호화 값을 찍지 않는다 (7편) 백업 암호문 키를 백업과 같은 곳에 두지 않는다 분석 사본 암호문 또는 HMAC 토큰 분석가가 키에 닿지 않게. 토큰은 빈도와 연결이 보인다

로그와 분석 사본에서는 HMAC 토큰도 조심해야 해요. 토큰은 원문은 아니지만 같은 사람의 기록끼리 이어 붙일 수 있는 값입니다. 로그로 새는 경로는 7편에서 따로 다뤄요.

코드로 옮기면 저장은 두 열, 출구는 한 함수가 됩니다. 아래는 계좌번호 하나를 기준으로 한 모양이에요.

-- 저장: 원문은 암호문 열에만, 조회가 있을 때만 토큰 열 account_enc VARCHAR(80) -- {표시}${키ID}$Base64(IV || 암호문 || 태그), 13자 계좌번호 기준 64자 account_hmac CHAR(44) -- HMAC-SHA256 Base64. 등치 조회가 없으면 이 열을 만들지 않는다 -- 저장용 마스킹 열은 따로 두지 않는다. 화면에 필요한 별표는 출구에서 만든다 // 출구: 응답 DTO 를 만들 때 역할로 갈라 표시용 마스킹 String accountForView(String plain, Role role) { return role.canSeeAccount() ? plain : mask(plain); // mask 는 앞 3자리, 끝 2자리만 남김 }
💡 실무에서는: 고르기 전 체크리스트
• 이 값을 원문으로 되돌려 쓰는 업무가 있나? 없으면 원문을 저장하지 않는다
• 있다면 AES-GCM 같은 인증 암호화로, 행마다 새 IV, 저장값에 키 ID
• 이 값으로 WHERE 를 거는 조회가 실제로 있나? 있을 때만 HMAC 토큰 열. 키 없는 해시는 쓰지 않는다
• HMAC 키를 바꿀 때 원문을 어디서 얻을지 정했나?
• 옛 키는 마지막 행을 다시 암호화하고, 그 키로 암호화된 백업의 보존 기간이 끝날 때까지 남겨 두나?
• 화면·API·로그·백업·분석 사본마다 누가 무엇을 보나? 표시용 마스킹은 그 출구에 걸었나?
• 마스킹 값을 식별자나 조회 키로 쓰는 코드는 없나?
• 이 항목이 고시 제7조 ②·③의 대상인지 해설서와 법무로 확인했나?
✍️ 오늘의 요약
저장용 마스킹은 아무것도 되돌릴 수 없고, AES-GCM 은 키가 있으면 전부 되돌리고, HMAC 은 되돌리지 못하는 대신 찾을 수 있습니다. 같은 여섯 행으로 재 보니 서로 다른 출력이 2, 6, 3개였고, A 를 찾으면 마스킹은 남의 행까지 1,3,4,5행을, HMAC 은 정확히 1,3,5행을 돌려줬어요.

키 사고는 되돌릴 수 있게 남긴 만큼 커집니다. GCM 은 키를 잃으면 원문을 영영 못 읽고, HMAC 은 원문이 다시 들어오기 전까지 키를 바꾸기 어려우며, 키가 새면 키 없는 해시와 같아져요. 표시용 마스킹은 저장 방식이 아니라 출구마다 거는 규칙입니다.

고르는 순서는 "얼마나 세게 감출까" 가 아니라 "누가 원문을 다시 써야 하나" 부터입니다.
