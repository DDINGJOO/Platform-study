관리 화면에 계좌번호가 999-**-****01로 보인다고 해 볼게요. 끝자리 01을 확인하는 데는 이 표시만으로 충분할 수 있어요. 하지만 그 번호로 실제 이체를 하려면 가려진 숫자도 필요해요. 화면에서만 가렸다면 저장된 원문을 다시 읽을 수 있지만, 가린 값만 저장하고 원문을 버렸다면 그 저장값에서 전체 번호를 복원할 수는 없어요.

개인정보 컬럼의 저장 방식을 정할 때는 마스킹, 암호화, 키 있는 해시(HMAC)로 만든 토큰을 비교할 수 있어요. 각 방식은 원문을 다시 읽을 수 있는지, 같은 값을 찾을 수 있는지에서 차이가 나요. 같은 가짜 계좌번호 여섯 행에 세 방식을 적용한 결과를 보면 업무에 필요한 기능과 저장 방식의 제약을 함께 비교할 수 있어요.

1. 네 방식은 원문을 어디에 남기나

마스킹을 비교할 때는 화면에서 가리는지, 가린 값만 저장하는지부터 구분해야 해요. 원문을 보관하는지가 다르기 때문이에요.

📖 용어: 표시용 마스킹 / 저장용 마스킹
표시용 마스킹은 원문(또는 암호문)을 저장해 두고 화면·응답·로그로 내보낼 때 일부를 가리는 방식이에요. 여기서 저장용 마스킹은 가린 값만 저장하고 원문을 버리는 방식을 뜻해요. 후자는 저장값만으로 가린 부분을 복원할 수 없지만, 남긴 정보나 다른 자료로 원문을 추측할 가능성까지 없어지는 것은 아니에요.

암호화는 올바른 키로 원문을 복원할 수 있는 방식이에요. 여기서는 AES-GCM 을 기준으로 삼았어요. 행마다 새 IV(암호화할 때 쓰는 초기값)를 생성해 같은 값도 다른 암호문으로 저장해요. IV·본문·태그 바이트나 함께 인증한 값(이 실습에서는 AAD 로 넣은 키 ID)이 달라지면 태그 검증을 통과하지 못해요. OWASP Cryptographic Storage Cheat Sheet 는 인증 모드를 쓸 수 있으면 항상 쓰고, 그중 GCM 과 CCM 을 먼저 고르라고 적어요(OWASP Cryptographic Storage).

📖 용어: AES-GCM (인증 암호화)
AES 블록 암호를 GCM 모드로 쓰는 방식이에요. 암호문 끝에 위조 검사용 태그가 붙어서, 이 실습의 복호화 코드는 키가 틀렸거나 인증 대상 값이 바뀌면 예외를 던져요. 같은 키에서 IV를 재사용하면 기밀성과 무결성이 손상될 수 있어 IV가 겹치지 않도록 관리해야 해요.

NIST SP 800-38D 는 이 조건을 "같은 IV 와 같은 키로 서로 다른 입력을 암호화할 확률이 2-32 를 넘으면 안 된다" 로 적고, 이 요구가 키의 비밀 유지에 거의 비견될 만큼 중요하다고 설명해요(NIST SP 800-38D, 8절). 같은 값에서 같은 암호문을 얻으려고 GCM의 IV를 고정해서는 안 돼요. 등치 조회가 꼭 필요할 때의 방법은 6편에서 따로 다뤄요.

📖 용어: HMAC 토큰 (키 있는 해시)
비밀 키와 값을 함께 해시해서 고정 길이 토큰을 만드는 방식이에요. 같은 키와 같은 값으로는 같은 토큰이 나와 등치 조회(같은 값인지 비교하는 조회) 열로 쓸 수 있어요. 복호화 연산은 없고, 원문 후보로 토큰을 다시 계산해 비교할 수 있어요.
그림 1. 같은 계좌번호가 네 방식에서 DB 와 화면에 남기는 것

그림의 표시용 마스킹은 출력 시 적용하는 규칙이고, 나머지 셋은 저장할 값을 정하는 방식이에요. 따라서 AES-GCM으로 저장한 뒤 화면이나 API 응답에서 표시용 마스킹을 적용할 수 있어요. 저장 방식과 출력 시 마스킹을 각각 정해야 해요.

2. 실습: 같은 여섯 행에 세 방식을 적용했다

입력은 가짜 계좌번호 세 개를 섞은 여섯 행이에요. A 가 세 번, B 가 두 번, C 가 한 번이에요. C는 A와 끝 여섯 자리가 같도록 골랐어요. 마스킹은 앞 세 자리와 끝 두 자리만 남기고, AES-GCM 은 AES-256 에 행마다 새 96비트 IV, HMAC 은 HMAC-SHA256을 사용해요. 키는 실습용 문자열에서 만든 고정 키이고, 암호문 앞의 lab9$k1$ 도 이 실습에서만 쓰는 표시예요.

git clone https://github.com/DDINGJOO/Platform-study.git cd Platform-study/labs/security/pii-09-mask-vs-encrypt java src/MaskVsEncrypt.java # JDK 11 이상, 외부 라이브러리 없음

당시 OpenJDK 25.0.3 에서 실행했고, 코드는 labs/security/pii-09-mask-vs-encrypt 에 있어요. 기존 기록에는 세 번 실행해 AES-GCM 암호문 줄(IV가 달라 실행마다 달라져요)을 뺀 나머지 출력이 같았다고 남아 있어요. 이번에 직접 대조한 저장 출력은 한 벌이라, 세 실행과 추가 캡처 실행을 각각 재확인하지는 못했어요. 아래 캡처 두 장은 그 세 번과 별도로 다시 돌려 같은 숫자가 나온 실행의 화면이고, 출력 앞부분([1]~[4], 1~27줄)과 뒷부분([5]~[7], 28~48줄)을 나눠 찍었어요.

그림 2. (출력 1~27줄) 원문 복원과 출력 개수, 등치 조회 결과를 비교했어요

각 방식의 조회 결과는 다음과 같았어요.

저장용 마스킹 AES-GCM HMAC 원문으로 되돌린 행 0/6 6/6 (복호화 없음) 서로 다른 출력 (입력 3) 2 6 3 WHERE = f(A) (정답 1,3,5) 1,3,4,5 없음 1,3,5 가장 많이 나온 출력의 빈도 4 1 3

저장용 마스킹은 되돌리지 못하는 것만이 문제가 아니었어요. 서로 다른 입력 세 개가 출력 두 개로 줄었어요. A 와 C 가 같은 999-**-****01 이 됐거든요. 마스킹한 값으로 A를 찾으니 C가 있는 4행도 조회됐어요. 이 마스킹 규칙은 서로 다른 원문을 구분하지 못하므로, 전체 번호의 일치 여부나 중복을 판정하는 키로 쓸 수 없어요.

AES-GCM은 여섯 행이 모두 다른 암호문이 됐어요. 같은 A 세 번도 서로 달랐어요. 암호문의 일치 여부만으로는 같은 계좌의 행을 묶을 수 없었고(최다 빈도 1), 같은 이유로 WHERE 암호문 = 새로 암호화한 A 는 아무것도 찾지 못해요. 대신 올바른 키로 6행 전부를 원문으로 복원했어요.

HMAC은 이 입력에서 원문의 중복 관계를 유지했어요. 출력이 세 개이고 A를 찾으면 1,3,5행만 조회됐어요. 등치 조회가 되는 대신, 토큰만 본 사람도 "이 토큰이 세 번 나온다" 는 사실을 알 수 있어요. 원문을 몰라도 같은 계좌번호를 토큰화한 행끼리 묶을 수 있다는 뜻이에요.

⚠️ 주의: 같은 토큰의 빈도도 드러나요
같은 값이 같은 출력이 되어야 WHERE 로 찾을 수 있고, 같은 값이 같은 출력이 되면 몇 번 나왔는지가 드러나요. 이 실습의 HMAC 토큰 열에서는 조회 기능과 빈도 노출이 함께 생겨요. 그래서 HMAC 토큰 열을 둘지는 "그 컬럼을 값으로 찾는 조회가 정말 있나" 를 먼저 확인하고 정하세요. 등치 조회가 남아 랜덤 IV 를 쓸 수 없었던 이야기는 3편에서 다뤘어요(3편).

부분 검색과 정렬에는 별도 설계가 필요해요

"끝 네 자리로 찾기", "이름 앞글자로 찾기", "번호순 정렬" 은 세 방식 어느 쪽도 그대로는 못 해요. AES-GCM 과 HMAC 의 출력은 원문의 앞뒤 순서나 부분을 검색 가능한 형태로 보존하지 않고, 저장용 마스킹은 남긴 자리로만 찾을 수 있는데 그 값도 위에서 본 것처럼 겹칠 수 있어요. 부분 검색이 꼭 필요하면 "끝 네 자리" 같은 조각을 별도 열로 따로 저장하게 되는데, 그 조각은 경우의 수가 1만 개뿐이에요. 조각 하나를 HMAC 으로 바꿔도 아래 3절의 키가 노출되면 후보를 비교하기가 더 쉬워져요. 원문 기준 정렬이 필요하면 대상 행을 다른 조건으로 좁힌 뒤 애플리케이션에서 복호화해 정렬하는 방법을 검토할 수 있어요.

3. 키를 잃을 때와 키가 샐 때

암호화와 HMAC은 모두 비밀 키를 관리해야 해요. 키를 잃었을 때와 키가 노출됐을 때의 영향은 달라요. 실습에서는 키를 k1에서 k2로 바꿨을 때 기존 저장값을 읽거나 조회할 수 있는지 확인했어요.

그림 3. (출력 28~48줄) GCM 재암호화와 HMAC 재계산에 기존 원문을 사용했어요

AES-GCM 행 여섯 개를 k2 로 풀면 6/6 이 AEADBadTagException 으로 실패했어요. 키가 틀려 태그 검증을 통과하지 못했다는 뜻이에요. 저장할 때 앞에 붙여 둔 키 ID(k1)로 옛 키를 골라 풀고 k2 로 다시 암호화하자 6/6 이 k2 로 복호화됐어요. OWASP 도 키를 바꾼 뒤 기존 데이터는 새 키로 다시 암호화하는 쪽을 먼저 권하고, 그게 어려우면 항목마다 쓴 키의 ID 를 표시해 두라고 적어요(OWASP Cryptographic Storage, Key Lifetimes and Rotation). 기존 행을 다시 암호화하기 전에는 옛 키가 필요해요. OWASP 는 은퇴한 키도 옛 백업을 풀 수 있도록 한동안 보관하라고 적어요. 그 키로 암호화된 백업을 보존 기간 안에 복호화해야 한다면 키도 그때까지 필요해요. 이 순서를 운영 중에 지키는 방법은 8편의 전환 순서와 같아요.

HMAC은 키를 바꾸면 기존 토큰과의 비교가 달라져요. k2 로 계산한 A 의 토큰으로 기존 행을 찾으면 아무것도 걸리지 않아요. 기존 토큰은 k1 으로 만든 것이니까요. 토큰을 k2 로 다시 계산하려면 원문이 있어야 하는데, 토큰에서 복호화로 원문을 얻을 수는 없어요. 실습에서는 같은 행의 AES-GCM 열을 풀어 원문을 얻고 다시 계산했고, 그제야 1,3,5행이 찾아졌어요. HMAC 토큰만으로는 새 키의 토큰을 다시 계산할 수 없어요. 사용자가 같은 값을 다시 입력할 때마다 새 키로 바꿔 쓰는 점진 교체는 가능해요. OWASP Password Storage Cheat Sheet 도 같은 구조를 적어요. pepper 는 사용자의 비밀번호를 모르면 바꿀 수 없어서 이전 pepper 로 보호된 사용자에게 비밀번호를 다시 정하게 해야 하고, 작업 계수를 올릴 때는 사용자가 다음에 인증할 때 다시 해시하라고 설명해요. 두 예시 모두 새로 계산할 원문이 필요해요. 그 값이 다시 입력되지 않는 행은 이 방법으로 새 키의 토큰으로 전환할 수 없어요. 일괄 교체가 필요하다면 원문을 얻을 경로(암호문 열 등)를 설계할 때 정해 두어야 해요.

키 노출의 영향과 후보 대입 공격은 이 실습에서 확인하지 않았어요. 아래 설명은 공개 자료를 기준으로 해요.

키 없는 해시(SHA-256 한 번)는 누구나 같은 계산을 할 수 있어요. ENISA 의 가명처리 보고서는 해시 함수가 무결성에는 도움이 되지만 가명처리 기법으로는 대입(brute force)과 사전 공격에 약하다고 보고, 식별자의 경우의 수가 작으면 대입이 "trivially feasible" 하다고 적어요. MAC(HMAC)은 비밀 키를 이용해 이런 후보 대입을 어렵게 하는 기법으로 설명해요(ENISA, Pseudonymisation techniques and best practices, 2019, 4.4.1절·5.1.3~5.1.4절). 계좌번호, 전화번호, 주민등록번호처럼 형식이 정해진 식별자는 가능한 후보의 범위와 공격자가 이미 아는 정보가 대입 비용에 영향을 줘요. OWASP Password Storage Cheat Sheet 도 SHA-256 같은 빠른 해시는 공격자가 짧은 시간에 아주 많은 추측을 해 볼 수 있게 한다고 경고하고, DB 와 따로 보관하는 비밀값(pepper)을 HMAC 의 키로 쓰는 구성을 소개해요(OWASP Password Storage).

📖 용어: 솔트와 페퍼 (salt, pepper)
솔트는 값마다 다르게 붙이는 공개 난수예요. 미리 계산한 해시 표의 재사용을 어렵게 하지만, 행마다 다르면 같은 입력도 같은 출력이 되지 않아 이 방식의 등치 조회 열로는 쓸 수 없어요. 페퍼는 DB 밖에 따로 두는 비밀값이에요. 인용한 비밀번호 저장 구성에서는 HMAC 키가 이 역할을 해요.

HMAC 키가 노출되면 공격자도 후보 값의 토큰을 계산해 저장된 토큰과 비교할 수 있어요. 후보의 범위가 작을수록 원문을 추측하는 비용도 줄어들어요. 따라서 HMAC 키도 암호화 키처럼 보호하고, 분석용 사본의 접근 권한과 키 접근 권한을 분리해야 해요.

그림 4. 키를 잃었을 때와 키가 노출됐을 때의 영향을 나눠 봐요

4. 고시는 어떤 항목에 암호화를 요구하나

법적 요구는 개인정보보호위원회 고시 「개인정보의 안전성 확보조치 기준」 제7조에서 확인할 수 있어요. 2026-10-17에 확인한 것으로 당시 글에 적은 판본은 개인정보보호위원회고시 제2026-9호(2026. 7. 1. 시행)이고, 이 글과 관련된 항은 이렇게 적혀 있어요(국가법령정보센터).

제7조(개인정보의 암호화) ① 개인정보처리자는 비밀번호, 생체인식정보 등 인증정보를 저장 또는 정보통신망을 통하여 송ㆍ수신하는 경우에 이를 안전한 암호 알고리즘으로 암호화하여야 한다. 다만, 비밀번호를 저장하는 경우에는 복호화되지 아니하도록 일방향 암호화하여 저장하여야 한다. ② 개인정보처리자는 다음 각 호의 해당하는 이용자의 개인정보에 대해서는 안전한 암호 알고리즘으로 암호화하여 저장하여야 한다. 1. 주민등록번호 2. 여권번호 3. 운전면허번호 4. 외국인등록번호 5. 신용카드번호 6. 계좌번호 7. 생체인식정보 ③ 개인정보처리자는 이용자가 아닌 정보주체의 개인정보를 다음 각 호와 같이 저장하는 경우에는 암호화하여야 한다. 1. 인터넷망 구간 및 인터넷망 구간과 내부망의 중간 지점(DMZ : Demilitarized Zone)에 고유식별정보를 저장하는 경우 2. 내부망에 고유식별정보를 저장하는 경우(다만, 주민등록번호 외의 고유식별정보를 저장하는 경우에는 (...) 암호화의 적용여부 및 적용범위를 정하여 시행할 수 있다)

아래는 당시 글에 적힌 조항 해석이에요. 이번 검수에서는 해당 판본의 조항 문언과 해당 서비스에 대한 적용을 독립적으로 다시 확인하지 못했어요. 현행 요구를 판단할 때는 원문과 최신 안내서를 다시 확인해야 해요. 인용한 조항은 적용 대상과 목적을 구분해서 읽어야 해요.

첫째, ②와 ③은 대상이 달라요. ②의 "이용자" 는 같은 고시 제2조에서 정보통신망법상 정보통신서비스 제공자의 서비스를 이용하는 자로 정의돼요. 그 경우에는 계좌번호와 신용카드번호까지 저장 시 암호화 대상이에요. 이용자가 아닌 정보주체에 대한 ③은 고유식별정보를 기준으로 하고, 주민등록번호 외의 고유식별정보를 내부망에 저장하는 경우에는 적용 여부와 범위를 정할 수 있도록 하고 있어요. 근거는 영향평가 대상 공공기관이면 그 영향평가 결과, 그 밖에는 암호화를 적용하지 않을 때의 위험도 분석 결과예요. 내 서비스가 어느 쪽에 해당하는지는 고시 문언만으로 정하기 어려운 경우가 있으니, 개인정보위가 공개한 이 기준의 안내서(해설서)와 법무 검토로 확인하세요.

둘째, ①은 비밀번호를 복호화할 수 없는 방식으로 저장하도록 요구해요. 계좌번호를 HMAC 토큰으로만 저장하는 것이 ②의 "암호화하여 저장" 을 채우는지는 이 인용 조항만으로 단정할 수는 없어요. 기술적으로도 토큰을 일괄 교체하려면 원문이 필요하므로, 법적 판단과 별도로 원문을 얻을 경로를 검토해야 해요.

셋째, 마스킹은 제7조가 아니라 제12조 ① 쪽에 가까워요. "개인정보의 출력시(인쇄, 화면표시, 파일생성 등) 용도를 특정하여야 하며, 용도에 따라 출력 항목을 최소화하여야 한다." 표시용 마스킹은 이 출력 최소화를 구현하는 흔한 방법이지만, 저장 시 암호화를 대신하지는 않아요.

5. 내 컬럼에는 무엇을 고르나

그림 5는 업무상 원문을 다시 읽어야 하는지부터 확인하는 순서예요. 송금, 본인 확인, 법정 제출처럼 전체 값이 필요한 업무가 있는지 살펴보고, 그다음 등치 조회가 필요한지 판단해요.

그림 5. 원문 복원이 필요한지 확인한 뒤 조회용 토큰 열을 검토해요

사례: 이력 문장 속 계좌번호를 문장째 암호화했다

4편에서 다룬 대상은 업무 이력 문구였어요. 당시 기록에 따르면 사람 이름과 계좌번호가 한 문장에 들어 있었고, 어드민 화면의 이력 탭에서 원래 문장을 읽어야 했어요. 같은 컬럼을 조건으로 쓰는 조회 두 곳이 있어 컬럼 전체를 암호화하지 않고, 특정 문구에 해당하는 문장 전체를 암호화했어요. 기존 기록의 확인 범위는 암호화한 문장을 복호화해 이력 화면과 같은 조회에서 읽는 데까지예요. 이 과거 확인 결과로 현재 화면의 권한이나 마스킹 적용 상태까지 판단할 수는 없어요.

실습의 [6]에서는 이름과 번호가 섞인 가짜 메모 한 줄로 마스킹과 문장째 암호화를 비교했어요. 계좌번호 형식을 찾는 정규식으로 문장을 마스킹하면 계좌번호는 가려지지만 홍길동 은 패턴에 없으니 그대로 남았어요. 자유 문장에서 개인정보를 골라 가리려면 그 위치를 먼저 정확히 찾아야 하는데, 정규식은 형식이 정해진 값만 찾아요. 문장 전체를 암호화하면 저장 시 문장 안의 개인정보 위치를 개별적으로 찾을 필요는 없어요. 다만 복호화한 뒤의 출력에서는 필요한 항목을 다시 가려야 해요. 이 실습의 표시용 마스킹도 계좌번호만 가리므로 이름까지 가려지는 것은 아니에요. 저장 길이도 늘었어요. 원문 38자(UTF-8 70바이트) 문장이 암호문으로 140자가 됐어요. 계좌번호 13자는 AES-GCM 으로 64자, HMAC 으로 44자였어요. 이 수치는 실습의 암호문 형식에서 나온 값이므로, 실제 컬럼 길이는 입력 길이와 저장 형식을 기준으로 정해야 해요.

⚠️ 주의: 조회 조건과 암호문 판별도 확인해요
• 4편에서는 같은 컬럼을 조건으로 쓰는 조회 때문에 암호화 범위를 좁혔고, 그 결과 한 컬럼에 평문과 암호문이 섞였어요(4편)
• 5편에서는 값의 시작 부분으로 암호문을 판별해, 같은 형태로 시작하는 일반 문장을 복호화하다 실패한 경우를 다뤘어요(5편)

노출 지점마다 다시 묻기

저장 방식과 별도로 화면·API·로그·백업·분석 사본에서 어떤 값이 보이는지 확인해야 해요.

출구 AES-GCM 저장일 때 보이는 것 해야 할 일 화면·API 응답 복호화한 원문 역할별 표시용 마스킹, 출력 항목 최소화 로그 코드가 찍는 그대로 원문·복호화 값을 찍지 않는다 (7편) 백업 암호문 키를 백업과 같은 곳에 두지 않는다 분석 사본 암호문 또는 HMAC 토큰 분석가가 키에 닿지 않게. 토큰은 빈도와 연결이 보인다

로그와 분석 사본에서는 HMAC 토큰도 조심해야 해요. 토큰은 원문은 아니지만 같은 입력 값의 기록끼리 연결할 수 있는 값이에요. 로그로 새는 경로는 7편에서 따로 다뤄요.

아래는 계좌번호를 암호문으로 저장하고 등치 조회가 필요할 때만 토큰 열을 추가하는 예시예요. 응답 DTO를 만들 때는 역할에 따라 표시용 마스킹을 적용해요.

-- 저장: 원문은 암호문 열에만, 조회가 있을 때만 토큰 열 account_enc VARCHAR(80) -- {표시}${키ID}$Base64(IV || 암호문 || 태그), 13자 계좌번호 기준 64자 account_hmac CHAR(44) -- HMAC-SHA256 Base64. 등치 조회가 없으면 이 열을 만들지 않는다 -- 저장용 마스킹 열은 따로 두지 않는다. 화면에 필요한 별표는 출구에서 만든다 // 출구: 응답 DTO 를 만들 때 역할로 갈라 표시용 마스킹 String accountForView(String plain, Role role) { return role.canSeeAccount() ? plain : mask(plain); // mask 는 앞 3자리, 끝 2자리만 남김 }
💡 실무에서는: 고르기 전 체크리스트
• 원문을 다시 써야 하는 업무가 있나요? 없다면 원문을 저장할 필요가 있는지 확인해요
• 원문이 필요하다면 AES-GCM 같은 인증 암호화와 IV 관리, 저장값의 키 ID를 검토해요
• 이 값으로 WHERE 조회를 하나요? 필요할 때 HMAC 토큰 열을 검토하고, 키 없는 해시의 후보 대입 위험을 구분해요
• HMAC 키를 교체할 때 원문을 어디서 얻을지 정했나요?
• 기존 행과 보존 기간 안의 백업을 복호화하는 데 필요한 옛 키를 보관하나요?
• 화면·API·로그·백업·분석 사본마다 접근 권한과 출력할 값을 정했나요?
• 마스킹 값을 원문 식별자나 중복 판정 키로 쓰는 코드가 있나요?
• 해당 항목이 고시 제7조 ②·③의 대상인지 해설서와 법무 검토로 확인했나요?
✍️ 오늘의 요약
같은 여섯 행에서 서로 다른 출력은 저장용 마스킹 2개, AES-GCM 6개, HMAC 3개였어요. A를 조회하면 마스킹은 C까지 포함한 1,3,4,5행을, HMAC은 1,3,5행을 반환했어요. AES-GCM은 올바른 키로 6행을 모두 복호화했어요.

저장용 마스킹 값만으로는 가린 부분을 복원할 수 없지만, 그것만으로 재식별 위험이 없어지는 것은 아니에요. HMAC도 원문 후보를 비교할 수 있고 같은 토큰의 빈도가 드러나요. 키 교체 실습에서는 AES-GCM을 옛 키로 풀어 다시 암호화했고, HMAC도 그 원문으로 다시 계산했어요.

업무에 원문 복원과 등치 조회가 필요한지 각각 확인해 저장 방식을 정하고, 표시용 마스킹은 출력 지점마다 적용해요. 이 비교는 가짜 데이터 실습과 공개 자료에 근거하며 현재 운영의 안전 상태를 확인한 결과는 아니에요.
