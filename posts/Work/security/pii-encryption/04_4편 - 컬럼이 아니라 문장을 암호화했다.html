4편. 기존 조회를 유지하며 업무 이력 문구를 선택적으로 암호화하기 ← 지금 이 글

계좌번호 컬럼을 암호화한 뒤, 같은 값이 다른 테이블에도 있는지 확인했어요. 업무 이력 화면에 나오는 문구를 몇 건 조회해 보니 사람 이름과 계좌 정보가 한 문장 안에 그대로 들어 있었어요.

당시 조회한 건수는 35,802건이었어요. 2024-08-15부터 쌓였고, 확인 시점에도 매일 수십 건씩 추가되고 있었어요. 계좌번호 컬럼을 암호화했어도 다른 테이블의 설명 문장에 복사된 값은 별도로 처리해야 했어요.

같은 컬럼에 여러 종류의 업무 이력이 저장되기 때문에 어떤 문구를 암호화할지 먼저 정해야 했어요. 대상 문구만 암호화하면 한 컬럼에 평문과 암호문이 섞이므로, 읽을 때 두 값을 구분하는 방법도 필요했어요.

🧭 선택적 암호화에서 정한 것
• 컬럼 전체를 암호화하면 기존 조회는 어떻게 달라지는가?
• "이 문장이 암호화 대상인가"를 무엇으로 판정했는가?
• 한 컬럼에 평문과 암호문이 섞이면 읽는 쪽은 어떻게 가리는가?
• 35,802건을 고치는 배치에 왜 진행 위치를 저장해야 했는가?
• 되돌리려면 무엇을 먼저 꺼야 하는가?

아래 설계와 로컬 확인 결과는 독립 리뷰 이전 시점을 기준으로 설명해요. 코드를 올린 뒤 받은 리뷰는 변경요청이었고, 지적은 9건(변경요청 5건, 권고 4건)이었어요. 리뷰 뒤 정정된 내용은 해당 절에서 구분하고, 전체 대응은 5편에서 다뤄요. 당시의 선택과 제약을 설명하는 내용이며, 현재 운영 환경의 보안 상태를 확인한 결과는 아니에요.

1. 기존 조회가 사용하는 문구는 유지해야 했어요

업무 이력의 설명 컬럼에는 44가지 사건 종류에 따른 문구가 저장되고 있었어요. 그중 한 종류에 사람 이름과 계좌번호가 함께 들어 있었어요. 이름만 들어 있는 종류도 따로 하나 있었지만, 당시 작업 범위에서는 제외했어요.

📖 용어: 업무 이력 문구
업무 처리 과정에서 생긴 일을 한 줄씩 쌓아 두는 기록이에요. 관리자 화면의 이력 탭에 출력하며, JSON 같은 구조화된 데이터 대신 사람이 읽는 일반 문자열로 저장해요.

컬럼에 암호화 컨버터를 붙여 모든 값을 암호화하는 방법도 있어요. 컨버터는 저장하고 읽을 때 값을 자동으로 변환하며, 3편에서도 사용한 방식이에요. 그런데 같은 컬럼을 조회 조건으로 사용하는 곳이 두 곳 있었어요. 하나는 처리 소요 시간 지표를 계산하는 네이티브 SQL이 문구 앞부분을 잘라 다른 테이블 값과 비교하는 곳이었어요. 다른 하나는 특정 문구와 값이 같은 행을 찾는 등치 조회였어요.

컬럼 전체를 암호화하면 두 조회에서 사용하는 평문 비교가 맞지 않게 돼요. 3편에서는 등치 조회를 유지하려고 같은 입력이 같은 암호문이 되는 방식을 선택했어요. 이번에는 기존 조회에서 비교하는 문구를 암호화 대상에서 제외하는 방법을 골랐어요.

그림 1. 조회 조건에 쓰는 문구는 유지하고 대상 문구만 암호화했어요

2. 공유한 접두어로 암호화 대상을 판정했어요

문구는 사건 종류마다 정해진 접두어로 시작했어요. 접두어는 문자열 맨 앞에 붙는 공통 부분이에요. 이를 기준으로 대상 접두어로 시작하는 문장은 암호화하고, 나머지는 평문으로 유지하도록 했어요.

문구를 만드는 코드와 암호화 대상을 판정하는 코드에 접두어를 따로 적으면, 문구를 바꿀 때 한쪽을 빠뜨릴 수 있어요. 그래서 접두어를 이벤트 코드의 상수로 정의하고 두 코드가 함께 쓰게 했어요.

// 문장을 만드는 쪽 (이벤트) static final String 대상_접두어 = "…이 사건을 알리는 문구 앞부분…"; String 문구() { return 대상_접두어 + "…사람 이름과 계좌 정보가 이어집니다(형식은 가렸어요)…"; } // 암호화 대상인지 판정하는 쪽 (컨버터와 배치가 같이 쓴다) static boolean 대상인가(String 문구) { return 문구 != null && 문구.startsWith(대상_접두어); }

이 구조에서는 상수의 접두어를 바꾸면 문구 생성과 대상 판정에 함께 반영돼요.

⚠️ 문구 생성과 대상 판정이 같은 접두어를 써야 해요
문구만 바꾸고 판정에 쓰는 접두어를 그대로 두면 암호화 대상에서 빠질 수 있어요. 대상이 아닌 값으로 처리되므로 오류 없이 평문으로 저장될 수 있고, 화면만 봐서는 구분하기 어려워요. 그래서 이벤트가 만드는 문구가 판정 상수로 시작하는지 테스트로 확인하도록 했어요.

3. 읽을 때는 값 앞의 암호문 표시를 확인해요

선택적 암호화를 적용하면 같은 컬럼에서 평문과 암호문을 모두 읽게 돼요. 모든 값에 복호화를 시도할 수는 없으므로, 읽은 값이 어느 쪽인지 먼저 구분해야 해요.

컨버터는 변환할 컬럼 값 하나만 받아요. 같은 행의 사건 종류 컬럼은 전달받지 않으므로, 사건 종류를 기준으로 복호화 여부를 정할 수 없었어요.

📖 용어: 컨버터 (AttributeConverter)
엔티티 필드와 DB 컬럼 사이에서 값을 바꾸는 인터페이스예요. 저장하거나 읽을 때 변환할 값 하나를 전달받으며, 같은 행의 다른 컬럼 값은 전달받지 않아요.

그래서 값 앞에 붙은 암호문 표시로 복호화 여부를 정했어요. 표시가 있으면 복호화하고, 없으면 저장된 값을 그대로 반환해요. 배치가 처리하기 전의 평문 행과 암호화 대상이 아닌 43종 문구는 그대로 반환하도록 했어요.

쓰기 : 스위치가 켜져 있고 + 대상 접두어로 시작 → 문장 전체를 암호화 그 밖의 문구 → 평문 그대로 저장 읽기 : 값이 암호문 표시로 시작 → 복호화해서 원래 문장 아니면 → 저장된 값 그대로

저장할 때 암호화하는 대상은 한 종류지만, 컬럼에 붙은 컨버터는 44종 문구를 모두 읽을 때 호출돼요. 따라서 대상 외의 평문도 읽기 판정의 영향을 받아요.

그림 2. 읽기 컨버터는 전달받은 값에서 암호문 표시를 확인해요

4. 기존 35,802건을 처리할 배치에 진행 위치를 저장했어요

컨버터를 추가해도 이미 저장된 35,802건이 자동으로 바뀌지는 않아요. 기존 데이터를 암호화하려고 일회성 배치를 따로 만들었어요.

당시에는 사건 종류 컬럼에 인덱스가 없었어요. 배치는 기본키(PK) 순서로 행을 읽으면서 대상 종류를 골라내도록 했어요. 사전 조회에서 확인한 규모는 테이블 전체 486만 행, 약 1GB였어요.

처음에는 대상이 35,802건이니 하룻밤이면 끝날 것으로 예상했어요. 이를 바탕으로 새벽 04:05부터 04:55까지 5분 간격으로, 다른 배치가 실행되는 04:45만 제외해 열 번 실행하도록 설정했어요. 하지만 대상 한 페이지를 채우기 위해 읽어야 할 행 수는 계산하지 않았어요.

독립 리뷰에서 이 읽기 비용을 계산했어요. 대상 비율이 0.74%라 한 페이지(200건)를 채우려면 평균 2.7만 행을 읽어야 하고, 한 실행이 끝까지 진행되면 테이블 전체를 한 번 읽는 셈이었어요. 이 계산은 실측 실행 시간이 아니에요. 리뷰를 반영하면서 설계 문서에 수치를 추가하고, 배치의 중복 실행을 막는 분산 락의 보유 시간도 늘렸어요(5편).

한 실행에서 처리할 양에도 상한을 뒀어요. 채우기는 페이지당 200행씩 250페이지까지(5만 행), 쓰기가 없는 검증은 페이지당 500행씩 200페이지까지예요. 상한에서 멈춘 다음 실행이 같은 구간을 다시 읽지 않도록 진행 위치를 저장해야 했어요.

📖 용어: 진행 위치 (커서)
마지막으로 처리한 행의 id예요. 다음 실행은 그보다 큰 id부터 읽어요. 페이지 번호 대신 id를 저장하면, 앞쪽 행이 추가되거나 삭제돼 페이지 구성이 바뀌더라도 저장한 id 이후부터 이어서 읽을 수 있어요.

진행 위치는 배치 실행을 제어하는 스위치 행에 함께 저장하도록 했어요. 실행이 끝날 때 마지막으로 본 id를 기록하고, 대상을 끝까지 읽으면 스위치 행을 삭제해요. 이 행이 없으면 다음 실행 시각에 배치 작업을 시작하지 않아요.

-- 배치 설정 테이블에 이 행이 있을 때만, 그 모드로 돕니다 {"mode":"FILL"} -- 처음부터 채우기 {"mode":"FILL","진행위치":1234567} -- 멈춘 자리 (키 이름과 숫자는 가렸어요) {"mode":"VERIFY"} -- 남은 평문·복호화 실패 건수만 센다 {"mode":"RESTORE"} -- 암호문을 평문으로 되돌린다 -- 대상 끝에 닿으면 이 행을 지운다 = 더 이상 돌지 않는다
그림 3. 처리량 상한에서 멈추면 저장한 진행 위치 다음부터 이어서 읽어요
💡 이력의 수정 시각을 유지하려고 SQL로 갱신했어요
• 당시 엔티티로 저장하면 수정 시각 컬럼도 함께 갱신됐어요. 암호화 작업으로 이력의 수정 시각이 배치 실행 시각으로 바뀌지 않게 해야 했어요
• 엔티티 조회에는 삭제 표시된 행을 제외하는 조건이 있었어요. 소프트 삭제된 행에도 계좌번호가 있어서 배치 대상에 포함해야 했어요
• 그래서 배치는 직접 SQL로 읽고 쓰도록 했어요. UPDATE에는 읽었던 값과 같은 경우에만 갱신하는 조건을 넣어, 그 사이 앱이 같은 행을 고쳤으면 갱신이 0건으로 끝나게 했어요
• 로그와 예외에는 id와 건수만 남기도록 설계했고, 행 객체를 출력할 때도 id만 나오게 했어요
• 다만 리뷰 전 코드에서는 쓰기 예외에 원인 예외를 그대로 첨부하고 있었어요. DB 오류 메시지에 값이 포함될 수 있으므로 원인 예외를 제거하라는 지적을 받았어요(5편)

5. 채우기·검증·복원을 나누고 되돌림 순서를 정했어요

배치는 채우기, 검증, 복원의 세 모드로 나눴어요. 채우기는 평문을 암호문으로 바꾸고, 검증은 데이터를 쓰지 않고 남은 평문과 복호화에 실패하는 행을 세도록 했어요. 복원은 암호문을 평문으로 되돌리는 모드예요.

채우기 모드에서는 이미 암호문인 행을 건너뛰어요. 대상 사건 종류인데 문구가 판정 접두어로 시작하지 않으면, 수정하지 않고 확인할 수 있도록 id만 남겨요. 대상 문구이면 암호화한 뒤 다시 복호화해 원문과 같은지 확인하고 UPDATE를 실행하도록 했어요.

📖 용어: 소프트 삭제 (soft delete)
행을 실제로 지우지 않고 삭제 표시만 남기는 방식이에요. 화면에 나오지 않아도 테이블에는 남아 있으므로, 평문 개인정보를 찾을 때 함께 확인해야 해요.
⚠️ 복원 전에 새 암호문이 저장되지 않게 해야 해요
리뷰 전 설계 문서에는 되돌림 순서를 "복원 완료 → 이전 버전"으로 적어 뒀어요. 3편에서 다룬 쓰기가 중단된 레거시 테이블의 절차를 그대로 옮겼기 때문이에요. 이번 테이블은 계속 새 이력이 들어오므로 복원 중에도 암호문이 추가될 수 있다는 차이를 놓쳤어요.

독립 리뷰의 지적을 받고 다음 순서로 정정했어요(5편).

① 쓰기 스위치를 끄고 재배포해요. 암호화 쓰기가 꺼져도 컨버터의 복호화는 유지되므로 화면 문구는 그대로예요
② 복원을 실행하고, 복원해야 할 전체 범위에서 잔여 암호문을 별도로 집계해 0건인지 확인해요
③ 그다음 이전 버전으로 되돌려요

여기서 필요한 것은 복원 대상 전체의 잔여 암호문 확인이에요. 앞서 설명한 남은 평문·복호화 실패 집계만으로는 복원 완료를 판단할 수 없고, 해당 검증 모드가 이 별도 집계를 지원했는지는 당시 원본이 없어 확인하지 못했어요. 배치 대상만 0건이어도 쓰기 판정 범위가 더 넓다면 누락된 암호문이 있을 수 있어요.

암호화 쓰기를 먼저 중단하지 않으면 복원 중이나 이전 버전 배포 전까지 새 암호문이 저장될 수 있어요. 이전 버전에서는 이를 복호화하지 못하므로 화면에 암호문이 남을 수 있어요. 복원 배치가 없는 버전으로 먼저 되돌리면 복원도 실행할 수 없어요.

6. 로컬 확인 결과와 운영 미실행 상태를 구분했어요

리뷰 전까지 구현한 것은 선택적 컨버터, 접두어 상수 공유, 쓰기 스위치와 기동 로그 표시, 일회성 배치와 테스트였어요. 로컬 DB에 넣고 꺼내 보며 대상 문구가 암호문으로 저장되고 저장 컬럼에 사람 이름과 계좌 정보가 남지 않는지 확인했어요. 관리자 이력 화면과 같은 조회로 원래 문장이 나오는지, 읽기만 했을 때 평문 행이 다시 저장되지 않는지도 확인했어요.

⚠️ 테스트 주석에 적은 조회를 모두 실행하지는 않았어요
테스트 클래스 주석에는 문구를 조건으로 쓰는 조회도 확인한다고 적었어요. 하지만 문구 앞부분을 잘라 비교하는 네이티브 조회는 호출하지 않았어요. 등치 조회도 실제 메서드 대신 같은 조건의 쿼리를 따로 작성해 실행했어요. 당시 확인한 범위는 비교에 쓰는 값이 컨버터를 거쳐도 유지되는지까지였어요.

독립 리뷰에서 주석과 실제 테스트 범위가 다르다는 지적을 받았어요. 리뷰 뒤에는 앞부분 비교 조회를 직접 호출하는 테스트를 추가했어요. 등치 조회는 실제 메서드 대신 별도 질의로 같은 조건을 확인한 범위를 유지했어요(5편).

당시 운영 채우기 배치는 예정 단계였고 실행 전이었어요. 스위치 행을 넣기 전에는 배치 작업을 시작하지 않도록 했어요. 따라서 남은 평문이 0건인지, 486만 행을 읽는 데 실제로 몇 분이 걸리는지, 접두어가 다른 행이 몇 건인지는 이 시점의 결과에 없어요.

여기서 확인한 범위는 문구별 암호화 판정과 배치·복원 코드의 구현, 로컬 테스트 결과예요. 운영 데이터의 암호화 완료나 배치의 실제 처리 시간까지 확인한 결과로 볼 수는 없어요.

✍️ 정리
같은 컬럼을 조건으로 사용하는 조회 두 곳을 유지하려고, 특정 사건의 문구만 골라 문장 전체를 암호화했어요. 문구 생성과 대상 판정은 같은 접두어 상수를 쓰게 했고, 읽을 때는 값 앞의 암호문 표시로 복호화 여부를 정했어요.

기존 35,802건을 바꿀 일회성 배치에는 진행 위치 저장, 검증, 복원을 넣었어요. 되돌릴 때는 새 암호문 저장을 먼저 중단한 뒤 복원과 검증을 거치도록 순서를 정정했어요.

당시 확인은 구현과 로컬 테스트까지였고 운영 배치는 실행 전이었어요. 앞부분 비교 조회의 직접 호출 테스트와 읽기 비용 계산은 리뷰를 반영하면서 보완했어요. 등치 조회는 별도 질의로 같은 조건을 확인한 결과였어요.
