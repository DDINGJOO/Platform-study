주민번호 컬럼에 AttributeConverter 를 붙여 AES-GCM 으로 암호화했습니다. 저장도 되고, 화면에서 읽으면 평문으로 잘 나와요. 그런데 다음 날 고객 조회 화면이 아무것도 찾지 못합니다. repo.findBySsn("000000-0002500") 이 예외도 없이 빈 목록을 돌려줘요. 그 사람의 행이 다섯 개 있는데도요.

처음에는 JPA 가 조회 인자에는 컨버터를 안 거치나 보다 생각하기 쉽습니다. 실제로는 반대예요. 인자도 컨버터를 거칩니다. 그래서 평문 인자가 새 난수로 다시 암호화되어 넘어가고, 저장된 암호문과 한 글자도 맞지 않아요. 이 글은 이 상황에서 고를 수 있는 세 방법을 같은 테이블에서 재 봅니다. 결정적 암호화, 랜덤 IV 를 유지하고 전부 복호화해서 앱에서 거르기, 블라인드 인덱스예요. 각각 등치 조회가 되는지, 인덱스를 타는지, 키 없이 무엇이 보이는지, 키를 바꿀 때 무엇이 깨지는지를 숫자로 봅니다.

1. findBy 가 빈 목록인 이유: 인자도 암호화된다

📖 용어: AttributeConverter
엔티티 필드 값과 컬럼 값을 서로 바꿔 주는 JPA 인터페이스예요. 저장할 때 convertToDatabaseColumn, 읽을 때 convertToEntityAttribute 가 불립니다. 컬럼 암호화를 엔티티 코드 한 줄(@Convert)로 붙일 수 있어서 많이 써요.

Jakarta Persistence 명세는 이 동작을 정해 두었어요. 3.2 판 3.9절(Type Conversion of Basic Attributes)은 변환이 걸린 속성을 질의에서 리터럴이나 파라미터와 비교하면, 비교 대상인 그 리터럴이나 파라미터 값도 변환해야 한다고 적습니다(Jakarta Persistence 3.2). Spring Data 의 findBySsn 은 결국 JPQL 비교라서, Hibernate 가 인자를 컨버터에 넣고 나온 값을 바인딩해요. 실습에서 Hibernate 의 바인딩 로그를 켜고 돌린 화면입니다.

그림 1. 인자도 컨버터를 거친다. GCM 은 새 IV 로 암호화된 인자를 넘겨 0행이 된다

→ 5만 행에 정답이 5행인 사람을 찾았어요. 결정적 컬럼(ssn_det)은 바인딩된 값이 저장된 암호문과 같아서 5행이 나왔습니다. GCM 컬럼(ssn_gcm)도 인자가 암호화되어 넘어갔지만, 매번 새 IV 를 쓰니 저장된 어느 행과도 같지 않아 0행이었어요. 마지막 줄이 더 조용한 함정입니다. StartingWith 는 Spring Data 가 인자 뒤에 % 를 붙이는데, Hibernate 가 그 "000000-00025%" 전체를 컨버터에 넣어 암호화했어요. % 가 암호문 안으로 들어가 버려서 평문 기준 707행이어야 할 결과가 0행이 됐습니다. 예외는 어디에도 없었어요.

정리하면 질문은 "어떻게 하면 인자가 컨버터를 안 거치나"가 아니에요. "같은 평문이 DB 안에서 같은 무언가로 보이게 할 것인가, 그렇다면 그 무언가는 무엇인가"입니다. 세 방법이 이 질문에 각각 다르게 답해요.

2. 실습: 같은 가짜 주민번호를 세 방식으로 한 행에

MySQL 8.4 컨테이너 하나와 Spring Boot 앱 하나로 돌렸어요. 테이블 하나에 같은 값을 네 형태로 넣고 컬럼마다 인덱스를 걸었습니다. 비교하려고 한 테이블에 모은 것이고, 실제로는 ① 한 컬럼이나 ③ 두 컬럼 한 쌍만 둡니다.

컬럼 방식 인덱스 ssn_det ① 결정적 암호화 (Tink AES256_SIV), 컨버터 idx_det ssn_gcm ② 랜덤 IV (AES-256-GCM, 12바이트 IV 매번 새로), 컨버터 idx_gcm ssn_bidx ③ 블라인드 인덱스: HMAC-SHA256(별도 키, 정규화한 평문) idx_bidx ssn_bidx12 ③' 같은 HMAC 의 앞 12비트만 (일부러 충돌을 낸다) idx_bidx12 데이터 1만 / 5만 / 10만 행, 사람 수 = 행 수 / 10 일부 사람이 아주 자주 나오게 치우친 분포 (5만 행에서 1등이 719행) 주민번호는 생년월일 자리가 000000 인 가짜

Spring Boot 4.1.1(Hibernate ORM 7.4.5, Spring Data JPA 4.1.1), MySQL Connector/J 9.7.0, Tink 1.23.0, Java 25, Docker 29.5.3 의 Docker Desktop, Apple M5 Pro 에서 돌렸어요. 전체를 세 바퀴 돌렸고 숫자는 전부 이 세 바퀴에서 나왔습니다. 키는 실습용으로 실행마다 새로 만들어요.

코드는 labs/security/pii-06-encrypted-lookup, 세 바퀴 요약은 results/summary.txt 에 있어요. 같은 평문이 두 행에 있을 때 DB 에 무엇이 남는지부터 그림으로 보면 이렇습니다.

3. ① 결정적 암호화: 그대로 되지만 빈도가 그대로 보인다

📖 용어: 결정적 암호화 (deterministic encryption)
같은 키, 같은 입력이면 항상 같은 암호문이 나오는 암호화예요. 암호문끼리 비교할 수 있어서 WHERE 와 인덱스가 그대로 동작합니다. 대신 키가 없는 사람도 두 행이 같은 값인지는 알 수 있어요.

컨버터 안의 암호화만 결정적으로 바꾸면 코드는 하나도 안 바뀌어요. 1장의 화면처럼 findBySsnDet 가 5행을 찾았고, EXPLAIN 은 세 바퀴 내내 type=ref key=idx_det 였습니다. 조회 시간도 행 수와 거의 상관이 없었어요. 1만 행에서 p50 0.77~0.87ms, 10만 행에서 0.69~0.76ms 였습니다.

대가는 키 없이 SQL 만 쓸 수 있는 사람에게 보이는 것입니다. DB 계정을 가진 사람, 백업 파일을 손에 넣은 사람이 그 예예요. 5만 행에서 평문 기준 빈도와, 키 없이 GROUP BY 만 돌린 결과를 나란히 놓았어요.

(results/freq-r1.txt, 5만 행) 서로 다른 값 가장 많은 다섯 값의 행 수 평문 (키로 전부 복호화) 4,996 719 297 214 183 150 ssn_det (키 없이 SQL 만) 4,996 719 297 214 183 150 ssn_gcm (키 없이 SQL 만) 50,000 1 1 1 1 1

→ 결정적 컬럼의 빈도 분포가 평문과 한 자리도 다르지 않다는 뜻이에요. 세 바퀴 모두 같았습니다(키는 바퀴마다 새로 만들었으니 키와 무관하게 그렇다는 뜻이에요). "719행을 가진 사람이 한 명 있다"는 사실은 암호를 풀지 않아도 보여요. 여기에 바깥 정보가 하나만 붙으면 값이 드러납니다. 예를 들어 그 사람의 평문과 암호문 한 쌍을 알면, 같은 암호문을 가진 719행이 전부 그 사람이에요. Google Tink 의 문서도 결정적 AEAD 에 대해 "평문에 대해서는 길이와 반복되는 평문의 동일성 말고는 아무것도 알려지지 않는다"고 적고, 같은 메시지를 두 번 보내면 공격자가 같다는 걸 알아챌 수 있으니 그게 의도가 아니면 일반 AEAD 를 쓰라고 합니다(Tink, Deterministic AEAD).

그래서 결정적 방식은 값의 종류가 많고 한 값이 여러 행에 반복되지 않는 컬럼에서 대가가 작아요. 사람마다 한 행인 회원 테이블의 주민번호라면 빈도로 얻을 게 적습니다. 같은 사람이 수백 번 나오는 접수 테이블이나, 값이 몇 개 안 되는 컬럼(성별, 은행 코드)이라면 결정적 암호화는 거의 평문만큼 많이 보여 줘요.

GCM 의 IV 를 고정하면 결정적이 되지 않나요

코드 한 줄로 결정적 암호화를 만드는 가장 쉬운 길이 이거라서 따로 적어요. AES-GCM 에 매번 같은 IV 를 넣으면 같은 평문에서 같은 암호문이 나오기는 합니다. 그런데 GCM 의 암호문은 평문에 키와 IV 로 만든 키스트림을 XOR 한 것이라, IV 가 같으면 다른 평문 두 개도 같은 키스트림으로 XOR 됩니다. 실습에서 IV 를 0 으로 고정하고 서로 다른 두 값을 암호화해 봤어요.

(results/ivreuse.txt) GCM, 키와 IV 고정, 평문 둘: 000000-0000001 / 000000-0735218 암호문1 XOR 암호문2 = 00 00 00 00 00 00 00 00 07 03 05 02 01 09 평문1 XOR 평문2 = 00 00 00 00 00 00 00 00 07 03 05 02 01 09 평문1을 아는 사람이 키 없이 복원한 평문2 = 000000-0735218

→ 암호문 두 개를 XOR 하면 평문 두 개를 XOR 한 값이 그대로 나와요. 평문 하나를 알면 다른 하나가 키 없이 풀립니다. 앞 8바이트가 00 인 것도 누출이에요. 앞부분이 같은 평문이면 암호문 앞부분도 같아서, 키 없이 "앞자리가 같다"까지 보입니다. 결정적 암호화는 "같은 값인가"만 드러내는데, 고정 IV GCM 은 다른 값끼리의 관계까지 드러내요. NIST SP 800-38D 는 8절에서 같은 키로 IV 가 한 번이라도 반복되면 위조 공격에 취약해질 수 있고 이 요구가 실무에서 키의 비밀 유지와 거의 같은 정도로 중요하다고 적고, 부록 A 에서 IV 가 반복되면 공격자가 해시 부분키를 알아내 인증이 사실상 사라진다고 설명합니다(NIST SP 800-38D). 결정적 암호화가 필요하면 처음부터 그렇게 설계된 방식을 씁니다. RFC 5297 의 SIV 는 쓰는 방식에 따라 결정적 인증 암호화가 되도록 만든 모드이고(RFC 5297), Tink 는 그 AES-SIV 를 AES256_SIV 로 권합니다. 실습의 ① 도 이것을 썼어요. 같은 두 평문을 AES-SIV 로 암호화하면 XOR 결과는 아무 관계 없는 바이트였습니다.

📖 용어: AES-SIV
평문과 연관 데이터로 IV 를 계산해 쓰는 암호화 모드예요(Synthetic IV). IV 가 입력에서 나오니 같은 입력이면 같은 암호문이고, 다른 입력이면 IV 도 달라져서 고정 IV GCM 같은 XOR 누출이 없습니다.

4. ② 랜덤 IV + 전부 복호화해서 거르기: 맞지만 행 수에 비례한다

📖 용어: 랜덤 IV
암호화할 때마다 새 난수 IV 를 섞는 방식이에요. 같은 평문도 매번 다른 암호문이 되어 키 없이는 같은 값인지조차 모릅니다. AES-GCM 의 기본 사용법이고, 대부분의 권고가 이쪽입니다.

랜덤 IV 를 그대로 두고 찾을 방법은 하나예요. 후보 행을 전부 읽어 복호화한 뒤 앱에서 비교합니다. 코드는 repo.findAll().stream().filter(...) 한 줄이라 쉽게 들어가요. 정답도 나옵니다. 문제는 시간이에요.

조회 한 번의 p50 (ms, 세 바퀴 최소~최대) 1만 행 5만 행 10만 행 ① findBySsnDet 0.77~0.87 0.76~0.78 0.69~0.76 ② findBySsnGcm 0.46~0.51 0.45~0.55 0.45~0.59 ← 항상 0행 ② findAll + 앱 filter 27.78~28.89 126.72~134.04 266.86~290.77 ② JDBC 한 컬럼 + 복호화 10.99~11.68 53.44~55.38 111.26~115.49 ③ findBySsnBidx 0.44~0.47 0.45 0.45~0.75

→ 전부 복호화하는 쪽만 행 수에 정비례해서 늘었다는 뜻이에요. 1만 행에서 28ms 였던 조회가 10만 행에서 270ms 안팎이 됐습니다. 엔티티를 만들지 않고 JDBC 로 암호문 한 컬럼만 읽어 복호화한 최선의 경우도 1만 행 11ms 에서 10만 행 113ms 안팎으로 같은 기울기였어요. 엔티티 생성을 빼도 기울기는 그대로고, 줄어든 건 상수뿐입니다. 이 숫자는 DB 와 앱이 한 노트북 안에 있을 때 값이라 실제 망에서는 행을 옮기는 시간이 더 붙어요. 조회가 동시에 여러 개 들어오면 그만큼 DB 와 앱의 메모리, CPU 를 같이 씁니다.

그림 3. 조회 한 번의 p50. 인덱스를 타는 두 방식은 평평하고, 전부 복호화는 직선으로 오른다

EXPLAIN 이 이 함정을 알려 주지 않는다는 점도 적어 둘게요. findBySsnGcm 이 실제로 보내는 WHERE ssn_gcm = ? 의 EXPLAIN 은 type=ref key=idx_gcm rows=1 이었습니다. 인덱스를 잘 타는 빠른 쿼리로 보이고, 실제로 0.5ms 안팎으로 끝났어요. 다만 결과가 항상 0행이었습니다. 느린 쿼리 로그에도, 실행 계획 점검에도 걸리지 않고 기능만 틀려요. 랜덤 IV 컬럼에 걸린 findBy 는 빠르고 틀리고, 그걸 고친 findAll 은 맞고 느립니다. 느린 쪽은 테스트 데이터 몇 행으로는 드러나지 않고, 틀린 쪽은 찾은 행 수를 정답과 맞춰 보는 테스트가 있어야 드러나요.

그래도 이 방식이 맞는 자리가 있어요. 그 컬럼을 조건으로 찾는 일이 관리자 화면의 드문 검색처럼 가끔이고, 대상 행을 다른 조건(날짜, 지점)으로 먼저 수백 행까지 줄일 수 있다면 복호화 비용은 그 수백 행에만 듭니다. 기준은 "전체 행 수"가 아니라 "복호화해야 하는 후보 행 수 × 조회 빈도"예요.

5. ③ 블라인드 인덱스: 인덱스는 타지만 빈도는 똑같이 보인다

📖 용어: 블라인드 인덱스 (blind index)
평문의 키 있는 해시(HMAC)를 암호문과 별도 컬럼에 저장해 두고, 찾을 때는 그 해시로 찾는 방식이에요. 원래 값은 랜덤 IV 로 암호화한 채 둡니다. Paragon 의 글은 이 인덱스 키를 암호화 키와 다르게, DB 서버가 모르게 두라고 적어요.

Paragon Initiative 의 글이 이 방식을 정리했어요. 평문의 키 있는 해시를 별도 컬럼에 저장하는 것이 기본 생각이고, 인덱스 키는 암호화 키와 달라야 하며 DB 서버가 몰라야 한다고 적습니다(Building Searchable Encrypted Databases with PHP and SQL). JPA 로 옮기면 이렇게 됩니다.

@Convert(converter = GcmConverter.class) // 원래 값: 랜덤 IV 그대로 @Column(name = "ssn_gcm") private String ssnGcm; @Column(name = "ssn_bidx") // 찾기용: 컨버터 없음, 인덱스 있음 private String ssnBidx; public void setSsn(String ssn) { this.ssnGcm = ssn; this.ssnBidx = Crypto.bidx(ssn); // HMAC-SHA256(인덱스 키, "claim.ssn|" + 정규화(ssn)) } // 저장소: 평문이 아니라 인덱스 값을 넘긴다 List<Claim> findBySsnBidx(String bidx); repo.findBySsnBidx(Crypto.bidx(ssn));

두 군데가 중요해요. 첫째, 인덱스 컬럼에는 컨버터를 붙이지 않고 호출하는 쪽에서 HMAC 을 계산해 넘깁니다. 그래서 1장의 "인자가 다시 암호화되는" 일이 생기지 않아요. 둘째, HMAC 에 넣기 전에 값을 정규화합니다(실습은 하이픈과 공백 제거). 정규화하지 않으면 하이픈이 있는 값과 없는 값, 뒤에 공백이 붙은 값이 전부 다른 인덱스가 돼요. "같은 값인가"를 누가 판정하는지 정해 두는 일이고, 판정을 DB 의 비교 규칙에 맡겼다가 뒤 공백을 구분하지 않아 놀란 일은 3편에 적었습니다. 이 판정을 코드에서 고정하는 게 블라인드 인덱스의 장점이기도 해요.

결과는 ① 과 같은 자리에 섰어요. findBySsnBidx 는 5행을 찾았고 EXPLAIN 은 type=ref key=idx_bidx, p50 은 행 수와 상관없이 0.44~0.75ms 였습니다. 그런데 빈도도 같은 자리에 섰어요.

그림 4. 블라인드 인덱스의 GROUP BY 는 결정적 암호문의 GROUP BY 와 한 자리도 다르지 않다

→ ssn_bidx 의 서로 다른 값 4,996개, 상위 다섯 값의 행 수 719, 297, 214, 183, 150 이 결정적 컬럼과 평문과 전부 같았어요. Paragon 의 글도 DB 서버만 털린 경우 공격자가 알 수 있는 건 여러 행이 같은 값을 공유하는지라고 적습니다. 등치 조회가 되는 한 "같은 값인가"는 어딘가에 드러나고, 블라인드 인덱스는 그 노출을 암호문에서 인덱스 컬럼으로 옮길 뿐이에요.

그럼 ③ 이 ① 보다 나은 점은 무엇일까요. 셋이에요. 원래 값의 암호문은 랜덤 IV 라서 그 컬럼만 빠져나가면 아무것도 안 보입니다. 찾기용 키와 복호화 키가 갈려서 복호화 권한과 검색 권한을 나눌 수 있어요(두 키의 보호 수준은 같아야 합니다, 바로 아래 이유로). 그리고 다음 절에서 볼 짧은 인덱스로 디스크를 아끼면서 빈도도 조금 흐릴 수 있습니다.

다만 인덱스 키가 "덜 중요한 키"는 아니에요. 인덱스 키만 가진 쪽은 암호문을 복호화하지는 못하지만, 주민번호처럼 경우의 수가 작은 값은 후보를 하나씩 HMAC 해 보고 인덱스와 맞춰 보는 것만으로 원래 값이 찾아집니다. Paragon 의 글도 같은 자리에서, 아주 민감한 정보라면 단순 HMAC 대신 키 스트레칭 알고리즘(PBKDF2-SHA256, scrypt, Argon2)을 써서 열거 시도를 늦추라고 적어요. 인덱스 키는 암호화 키만큼 지키고, 값의 경우의 수가 작고 민감하면 키 스트레칭을 검토합니다. 그 대가로 인덱스 계산이 느려지니 쓰기와 조회마다 그만큼 시간이 붙어요.

인덱스를 자르면 빈도가 흐려질까

Paragon 의 글은 블라인드 인덱스를 16, 32, 64비트 정도로 잘라 블룸 필터처럼 다루라고 제안해요. 동기는 디스크예요. 검색이 조금 느려지는 대신 디스크를 많이 아낄 수 있는 경우가 있다고 적습니다. 자르면 서로 다른 값이 같은 인덱스를 갖게 되어, 인덱스로 찾은 행은 "아마 맞는" 후보가 되고 앱이 복호화해서 확인합니다. 그러면 부수적으로 빈도도 흐려지는데, 얼마나 흐려지는지 재 봤어요. 실습은 효과가 잘 보이게 12비트(4,096칸)까지 잘랐어요. 5만 행의 서로 다른 값 4,996개를 4,096칸에 넣은 셈입니다.

(5만 행, 세 바퀴. 인덱스 키가 바퀴마다 달라 충돌도 달라진다) r1 r2 r3 서로 다른 인덱스 값 2,865 2,901 2,889 (평문 4,996) 가장 많은 인덱스 값 727 730 719 (평문 1등 719) 조회 후보 / 진짜 37 / 5 14 / 5 22 / 5 조회 p50 (복호화 확인 포함) 0.47ms 0.40ms 0.43ms

→ 자르면 꼬리는 흐려졌어요. 서로 다른 값 수가 평문의 절반 남짓이 되어, 한두 번 나오는 값끼리는 구별이 안 됩니다. 조회도 후보 14~37행을 복호화해 걸러도 0.5ms 안쪽이었어요. 그런데 머리는 그대로 보였습니다. 1등 인덱스 값은 727, 730, 719행으로, 평문 1등 719행에 다른 값 몇 행이 섞였을 뿐이에요. 자르는 건 드물게 나오는 값을 숨기지, 자주 나오는 값을 숨기지는 않습니다. 머리까지 흐리려면 칸당 평균 행 수가 1등 값의 행 수(719)에 가까워질 만큼, 5만 행이면 대략 70칸까지 줄여야 해요. 그때는 조회 한 번의 후보가 수백 행이 되어 4장의 전부 복호화 쪽으로 다가갑니다. 자르기는 디스크를 아끼는 장치이고, 빈도를 숨기는 장치로 기대하면 안 돼요.

6. 키 회전: 셋 다 전 행을 다시 쓰지만, 조회가 깨지는 건 둘이다

키를 바꿀 때 비용은 두 가지예요. 전 행을 다시 쓰는 시간, 그리고 다시 쓰는 동안 조회가 맞는 답을 내는가입니다. 5만 행을 1,000행씩 커밋하며 다시 쓰고, 절반을 옮긴 시점에 정답 5행인 사람을 찾아봤어요.

(results/rotate-r1~r3.txt, 5만 행) 전부 다시 쓰기 (r1 / r2 / r3) 절반 옮긴 시점의 조회 ① 결정적 키 회전 1.6s / 2.0s / 1.8s 새 키로 3행, 옛 키로 2행, IN(새, 옛) 5행 ② GCM 키 회전 1.7s / 2.0s / 1.8s 전 행 복호화 성공, 조회와 무관 ③ 블라인드 인덱스 키 회전 1.9s / 2.2s / 2.0s 새 키 HMAC 3행, 옛 키 HMAC 2행

→ 다시 쓰는 시간은 셋 다 비슷했어요. 행마다 복호화하고 다시 만들어 쓰는 일이라 연산이 거의 같습니다. ② 의 숫자에는 확인용으로 전 행을 두 번 복호화한 시간이 들어 있어서, 다시 쓰기만 따지면 그보다 조금 짧아요. 차이는 오른쪽 칸이에요. ① 에서 컨버터가 새 키로 인자를 암호화하자 아직 옛 키로 남은 2행을 못 찾았습니다. 세 바퀴 모두 3행이었어요. 회전하는 동안은 키마다 암호문을 만들어 컨버터를 거치지 않는 네이티브 쿼리나 JDBC 로 IN (새 키 암호문, 옛 키 암호문) 을 써서 찾아야 5행이 다 나왔고, 이건 findBy 한 줄이 아니라 직접 쓴 쿼리가 됩니다. 이때 컨버터가 걸린 필드에 JPQL IN :list 를 쓰면 안 돼요. 목록의 원소도 컨버터를 거쳐 주 키로만 암호화되니, 새 값과 옛 값을 넣어도 둘 다 새 키 암호문이 됩니다. 실습도 컨버터를 거치지 않는 JDBC 쿼리로 찾았어요. ③ 도 인덱스 키를 바꾸면 똑같이 3행이었어요.

그림 5. 회전 도중에 조회가 깨지는 건 "찾는 값"이 키에 묶인 방식이다

② 는 반대였어요. 암호문 맨 앞 1바이트에 키 번호를 넣어 두었기 때문에, 절반을 옮긴 시점에도 전 행 5만 개가 복호화됐고 정답 5행도 그대로 찾았습니다. 찾는 값이 암호문이 아니니 회전과 조회가 서로 엮이지 않아요. 그래서 ② 의 회전은 서두를 필요가 없고, 행을 읽거나 고칠 때 조금씩 옮겨도 됩니다(옛 키는 마지막 행을 옮길 때까지 남겨야 해요). ③ 은 두 키를 따로 돌릴 수 있다는 게 이점이에요. 암호화 키를 바꾸는 건 ② 와 같아서 조회에 영향이 없고, 깨지는 건 인덱스 키를 바꿀 때뿐입니다. 결정적 암호화는 하나의 키가 두 일을 같이 하므로 언제 돌려도 조회가 같이 깨져요.

7. 고르는 법

제 회사의 레거시 테이블 한 곳에서는 한 테이블 안에서 방식이 둘로 갈렸어요. 값을 조건으로 찾는 조회가 남아 있는 컬럼은 결정적 방식으로, 그런 조회가 없는 컬럼은 랜덤 IV 로 갔습니다. 보안 기준이 달라서가 아니라 남아 있는 조회가 달라서였어요(3편). 이 글의 숫자로 다시 보면 그 판단의 축은 하나입니다. 그 컬럼을 값으로 찾는 조회가 있는가, 있다면 얼마나 자주, 몇 행을 대상으로 하는가예요.

① 결정적 ② 랜덤 IV + 앱 필터 ③ 랜덤 IV + 블라인드 인덱스 등치 조회 (findBy) 그대로 된다 0행 (조용히 틀림) 인덱스 값으로 된다 인덱스 탄다 (ref) 못 쓴다 (전 행 ALL) 탄다 (ref) p50, 10만 행 0.7ms 안팎 270ms 안팎 (JPA) 0.5ms 안팎 키 없이 보이는 빈도 평문과 같다 없다 평문과 같다 (자르면 꼬리만 흐림) 키 회전 중 조회 IN(새, 옛) 필요 영향 없음 인덱스 키 회전 때만 IN 필요 LIKE / 부분 검색 안 된다 (0행) 앱에서만 안 된다 코드 변경 컨버터만 조회마다 필터 컬럼 하나 + 호출부 HMAC

LIKE 는 셋 다 DB 에서는 안 돼요. 뒷자리 네 개로 찾는 화면이 꼭 필요하면 그 부분값에 블라인드 인덱스를 따로 하나 더 둡니다. 다만 그 인덱스는 "뒷자리가 같은 행"을 드러내니, 둘 수 있는 부분 인덱스의 수가 곧 노출의 크기예요. 앞 글자 검색처럼 길이가 여러 개인 부분 검색은 길이마다 인덱스가 하나씩 늘어나서 대개 감당이 안 됩니다. 이럴 때는 검색 범위를 다른 조건으로 줄이고 ② 로 거르는 쪽이 현실적이에요.

💡 내 코드에서 바꿀 것
• 암호화 컨버터가 붙은 필드를 쓰는 findBy, @Query, StartingWith/Containing 부터 세세요. 랜덤 IV 컬럼에 걸린 것은 지금 0행을 돌려주고 있습니다
• 테스트는 "찾은 행 수가 정답과 같다"로 쓰세요. 예외가 없다는 것, EXPLAIN 이 ref 라는 것으로는 못 잡습니다
• 등치 조회가 필요하면 ③ 을 먼저 보세요. 인덱스 키를 암호화 키와 따로 두되 암호화 키만큼 지키고, HMAC 전에 정규화하고, 인덱스 컬럼에는 컨버터를 붙이지 마세요. 주민번호처럼 경우의 수가 작은 값이면 키 스트레칭도 검토하세요
• ① 을 고른다면 IV 를 고정한 GCM 이 아니라 AES-SIV 같은 결정적 AEAD 를 쓰고, 한 값이 여러 행에 반복되는 컬럼인지 먼저 GROUP BY 로 확인하세요
• ② 로 버틴다면 기준은 전체 행 수가 아니라 "후보 행 수 × 조회 빈도"입니다. 다른 조건으로 먼저 줄일 수 있는지 보세요
• 키 회전 계획에 "도중에는 키마다 값을 만들어, 컨버터를 거치지 않는 쿼리의 IN 으로 찾는다"를 적어 두세요. ① 과 ③ 의 인덱스 키에 해당합니다
✍️ 오늘의 요약
JPA 는 변환이 걸린 컬럼과 비교하는 인자도 컨버터로 바꿉니다. 랜덤 IV 컬럼의 findBy 가 예외 없이 0행인 이유이고, LIKE 는 % 까지 암호화되어 0행이 됩니다.

결정적 암호화는 코드 변경 없이 인덱스를 타지만 5만 행의 빈도 분포가 평문과 한 자리도 다르지 않게 보였어요. 전부 복호화해서 거르면 정답은 나오지만 1만 행 28ms 에서 10만 행 270ms 로 행 수를 따라 늘었습니다. 블라인드 인덱스는 인덱스를 타고 키를 나눌 수 있지만 빈도는 결정적 방식과 똑같이 보였고, 12비트로 잘라도 1등 값은 그대로 보였어요. 키 회전 도중에 조회가 깨지는 건 찾는 값이 키에 묶인 ① 과 ③ 이었습니다.

암호화한 컬럼을 WHERE 로 찾을 수 있다는 건, 같은 값인지를 누군가에게 보여 준다는 뜻이에요. 고를 것은 방식이 아니라 그걸 어디에, 누구에게 보여 줄지입니다.
