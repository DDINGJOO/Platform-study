가짜 주민번호 컬럼에 AttributeConverter를 붙여 AES-GCM으로 암호화한 실습에서는 저장과 읽기가 모두 됐어요. 그런데 repo.findBySsn("000000-0002500")은 예외 없이 빈 목록을 돌려줬어요. 해당 값으로 저장한 행이 다섯 개 있는데도 조회 결과는 0행이었어요.

JPA는 조회 인자도 컨버터에 전달해요. 랜덤 IV를 쓰면 같은 평문 인자를 다시 암호화해도 저장된 암호문과 달라져서 일치하는 행을 찾지 못해요. 이를 해결할 세 방식으로 결정적 암호화, 랜덤 IV를 유지한 채 복호화 후 앱에서 비교하기, 블라인드 인덱스를 같은 테이블에서 비교했어요. 등치 조회와 인덱스 사용 여부, 키 없이 보이는 정보, 키를 바꾸는 동안의 조회 결과를 확인했어요.

• 키를 바꾸는 도중에 검색 결과가 누락되는 방식은 무엇인가요?

1. findBy 가 빈 목록인 이유: 인자도 암호화된다

📖 용어: AttributeConverter
엔티티 필드 값과 컬럼 값을 서로 바꿔 주는 JPA 인터페이스예요. 저장할 때 convertToDatabaseColumn, 읽을 때 convertToEntityAttribute가 호출돼요. 컬럼 암호화를 엔티티 필드의 @Convert로 적용할 수 있어요.

Jakarta Persistence 명세는 이 동작을 정해 두었어요. 3.2 판 3.9절(Type Conversion of Basic Attributes)은 변환이 걸린 속성을 질의에서 리터럴이나 파라미터와 비교하면, 비교 대상인 그 리터럴이나 파라미터 값도 변환해야 한다고 설명해요(Jakarta Persistence 3.2). Spring Data 의 findBySsn 은 결국 JPQL 비교라서, Hibernate 가 인자를 컨버터에 넣고 나온 값을 바인딩해요. 실습에서 Hibernate 의 바인딩 로그를 켜고 돌린 화면이에요.

그림 1. 실습의 GCM 조회 인자는 새 IV로 암호화돼 저장된 값과 일치하지 않았어요

5만 행에 정답이 5행인 사람을 찾았어요. 결정적 컬럼(ssn_det)은 바인딩된 값이 저장된 암호문과 같아서 5행이 나왔어요. GCM 컬럼(ssn_gcm)도 인자가 암호화되어 넘어갔지만, 매번 새 IV 를 쓰니 저장된 어느 행과도 같지 않아 0행이었어요. 부분 검색도 기대한 결과를 찾지 못했어요. StartingWith 는 Spring Data 가 인자 뒤에 % 를 붙이는데, Hibernate 가 그 "000000-00025%" 전체를 컨버터에 넣어 암호화했어요. % 가 암호문 안으로 들어가 버려서 평문 기준 707행이어야 할 결과가 0행이 됐어요. 이 실행에서 예외는 발생하지 않았어요.

조회에 필요한 값의 비교를 어디서 할지 정해야 해요. DB에서 암호문이나 별도 인덱스를 비교할 수도 있고, 앱에서 복호화한 평문을 비교할 수도 있어요. 이 선택에 따라 DB에 드러나는 정보와 조회 비용이 달라져요.

2. 실습: 같은 가짜 주민번호를 세 방식으로 한 행에

MySQL 8.4 컨테이너 하나와 Spring Boot 앱 하나로 돌렸어요. 테이블 하나에 같은 값을 네 형태로 넣고 컬럼마다 인덱스를 걸었어요. 비교하려고 한 테이블에 모은 것이고, 실제 설계에서는 필요한 방식만 두면 돼요. 예를 들어 ①은 암호문 한 컬럼, ③은 암호문과 인덱스 두 컬럼을 사용해요.

컬럼 방식 인덱스 ssn_det ① 결정적 암호화 (Tink AES256_SIV), 컨버터 idx_det ssn_gcm ② 랜덤 IV (AES-256-GCM, 12바이트 IV 매번 새로), 컨버터 idx_gcm ssn_bidx ③ 블라인드 인덱스: HMAC-SHA256(별도 키, 정규화한 평문) idx_bidx ssn_bidx12 ③' 같은 HMAC 의 앞 12비트만 (일부러 충돌을 낸다) idx_bidx12 데이터 1만 / 5만 / 10만 행, 사람 수 = 행 수 / 10 일부 사람이 아주 자주 나오게 치우친 분포 (5만 행에서 1등이 719행) 주민번호는 생년월일 자리가 000000 인 가짜

Spring Boot 4.1.1(Hibernate ORM 7.4.5, Spring Data JPA 4.1.1), MySQL Connector/J 9.7.0, Tink 1.23.0, Java 25, Docker 29.5.3 의 Docker Desktop, Apple M5 Pro 에서 돌렸어요. 전체를 세 실행 돌렸고 숫자는 전부 이 세 실행에서 나왔어요. 키는 실습용으로 실행마다 새로 만들어요.

코드는 labs/security/pii-06-encrypted-lookup, 세 실행 요약은 results/summary.txt 에 있어요. 같은 평문이 두 행에 있을 때 DB 에 무엇이 남는지부터 그림으로 보면 아래와 같아요.

그림 2. 결정적 암호문과 블라인드 인덱스는 DB에서 같은 값을 비교할 수 있어요

3. ① 결정적 암호화: 등치 조회와 빈도 노출

📖 용어: 결정적 암호화 (deterministic encryption)
같은 키, 같은 입력이면 항상 같은 암호문이 나오는 암호화예요. 암호문끼리 비교할 수 있어서 WHERE 와 인덱스가 그대로 동작해요. 대신 키가 없는 사람도 두 행이 같은 값인지는 알 수 있어요.

컨버터의 암호화 구현을 결정적 방식으로 바꾸면 조회 호출부는 유지할 수 있어요. 1장의 화면처럼 findBySsnDet 가 5행을 찾았고, EXPLAIN 은 세 실행 내내 type=ref key=idx_det 였어요. 측정한 범위에서는 조회 시간도 비슷했어요. p50은 조회 시간의 중앙값이에요. 1만 행에서 p50 0.77~0.87ms, 10만 행에서 0.69~0.76ms 였어요.

대신 복호화 키 없이도 같은 값의 반복 횟수가 보여요. DB 계정을 가진 사람, 백업 파일을 손에 넣은 사람이 그 예예요. 5만 행에서 평문 기준 빈도와, 키 없이 GROUP BY 만 돌린 결과를 나란히 놓았어요.

(results/freq-r1.txt, 5만 행) 서로 다른 값 가장 많은 다섯 값의 행 수 평문 (키로 전부 복호화) 4,996 719 297 214 183 150 ssn_det (키 없이 SQL 만) 4,996 719 297 214 183 150 ssn_gcm (키 없이 SQL 만) 50,000 1 1 1 1 1

결정적 컬럼의 빈도 분포가 평문과 같았어요. 키를 실행마다 새로 만들었지만 세 실행의 분포는 같았어요. "719행을 가진 사람이 한 명 있다"는 사실은 암호를 풀지 않아도 보여요. 외부 정보와 결합하면 값이 드러날 수 있어요. 예를 들어 그 사람의 평문과 암호문 한 쌍을 알면, 같은 암호문을 가진 719행이 전부 그 사람이에요. Google Tink 의 문서도 결정적 AEAD 에 대해 "평문에 대해서는 길이와 반복되는 평문의 동일성 말고는 아무것도 알려지지 않는다"고 적고, 같은 메시지를 두 번 보내면 공격자가 같다는 걸 알아챌 수 있으니 그게 의도가 아니면 일반 AEAD 를 권해요(Tink, Deterministic AEAD).

값의 종류가 많고 반복이 적은 컬럼에서는 빈도로 추론할 수 있는 정보가 상대적으로 적어요. 사람마다 한 행인 회원 테이블과 같은 사람이 수백 번 나오는 접수 테이블의 차이예요. 성별이나 은행 코드처럼 값의 종류가 적은 컬럼은 빈도와 외부 정보를 결합해 값을 추론할 위험을 더 신중하게 봐야 해요. 반복이 적다는 이유만으로 안전하다고 판단할 수는 없어요.

GCM 의 IV 를 고정하면 결정적이 되지 않나요

GCM의 IV를 고정해서 결정적 암호화를 구현하면 안 돼요. AES-GCM 에 매번 같은 IV 를 넣으면 같은 평문에서 같은 암호문이 나와요. 그런데 GCM 의 암호문은 평문에 키와 IV 로 만든 키스트림을 XOR 한 것이라, IV 가 같으면 다른 평문 두 개도 같은 키스트림으로 XOR돼요. 실습에서 IV 를 0 으로 고정하고 서로 다른 두 값을 암호화해 봤어요.

(results/ivreuse.txt) GCM, 키와 IV 고정, 평문 둘: 000000-0000001 / 000000-0735218 암호문1 XOR 암호문2 = 00 00 00 00 00 00 00 00 07 03 05 02 01 09 평문1 XOR 평문2 = 00 00 00 00 00 00 00 00 07 03 05 02 01 09 평문1을 아는 사람이 키 없이 복원한 평문2 = 000000-0735218

암호문 두 개를 XOR 하면 평문 두 개를 XOR 한 값이 그대로 나와요. 평문 하나를 알면 다른 하나가 키 없이 복원돼요. 앞 8바이트가 00 인 것도 누출이에요. 앞부분이 같은 평문이면 암호문 앞부분도 같아서, 키 없이 "앞자리가 같다"까지 보여요. AES-SIV에서 드러나는 동일성과 달리 고정 IV GCM은 서로 다른 평문 사이의 관계도 노출해요. NIST SP 800-38D 는 8절에서 같은 키로 IV 가 한 번이라도 반복되면 위조 공격에 취약해질 수 있고 이 요구가 실무에서 키의 비밀 유지와 거의 같은 정도로 중요하다고 적고, 부록 A 에서 IV 가 반복되면 공격자가 해시 부분키를 알아내 인증이 사실상 사라진다고 설명해요(NIST SP 800-38D). 결정적 암호화가 필요하면 처음부터 그렇게 설계된 방식을 사용해야 해요. RFC 5297 의 SIV 는 쓰는 방식에 따라 결정적 인증 암호화가 되도록 만든 모드이고(RFC 5297), Tink 는 그 AES-SIV 를 AES256_SIV 로 권해요. 실습의 ① 도 이것을 썼어요. 같은 두 평문을 AES-SIV 로 암호화하면 앞서 본 XOR 일치가 나타나지 않았어요.

📖 용어: AES-SIV
평문과 연관 데이터로 IV를 계산하는 암호화 모드예요(Synthetic IV). 이 실습처럼 결정적으로 사용하면 같은 입력에서 같은 암호문이 나와요. 고정 IV GCM과 다른 방식으로 설계됐어요.

4. ② 랜덤 IV + 앱 필터: 후보 행 수에 따른 복호화 비용

📖 용어: 랜덤 IV
암호화할 때마다 새 난수 IV를 사용하는 방식이에요. 같은 평문에서도 다른 암호문이 나오므로 암호문을 단순 비교해서 평문이 같은지 판단하기 어려워요. AES-GCM은 같은 키에서 IV가 중복되지 않도록 관리해야 해요.

②는 랜덤 IV를 유지한 채 앱에서 값을 비교하는 방식이에요. 후보 행을 전부 읽어 복호화한 뒤 앱에서 비교해요. 코드는 repo.findAll().stream().filter(...) 로 구현할 수 있고, 실습에서도 정답을 찾았어요. 다만 복호화할 후보 행 수에 따라 시간이 더 걸려요.

조회 한 번의 p50 (ms, 세 바퀴 최소~최대) 1만 행 5만 행 10만 행 ① findBySsnDet 0.77~0.87 0.76~0.78 0.69~0.76 ② findBySsnGcm 0.46~0.51 0.45~0.55 0.45~0.59 ← 항상 0행 ② findAll + 앱 filter 27.78~28.89 126.72~134.04 266.86~290.77 ② JDBC 한 컬럼 + 복호화 10.99~11.68 53.44~55.38 111.26~115.49 ③ findBySsnBidx 0.44~0.47 0.45 0.45~0.75

전 행을 복호화하는 조회는 행 수와 함께 시간이 늘었어요. 1만 행에서 28ms 였던 조회가 10만 행에서 270ms 안팎이 됐어요. 엔티티를 만들지 않고 JDBC 로 암호문 한 컬럼만 읽어 복호화한 경우에도 1만 행 11ms 에서 10만 행 113ms 안팎으로 행 수와 함께 시간이 늘었어요. 엔티티 생성을 제외하면 시간은 줄었지만 행 수에 따라 비용이 늘어나는 경향은 같았어요. DB와 앱을 같은 노트북에서 실행한 수치이므로 실제 네트워크의 전송 비용까지 측정한 결과는 아니에요. 조회가 동시에 여러 개 들어오면 그만큼 DB 와 앱의 메모리, CPU를 함께 사용해요.

그림 3. 실습에서 전 행 복호화 비용은 행 수와 함께 늘었어요

실행 계획만으로는 결과의 정확성을 확인할 수 없었어요. findBySsnGcm 이 실제로 보내는 WHERE ssn_gcm = ? 의 EXPLAIN 은 type=ref key=idx_gcm rows=1 이었어요. 인덱스를 잘 타는 빠른 쿼리로 보이고, 실제로 0.5ms 안팎으로 끝났어요. 다만 결과가 항상 0행이었어요. 조회가 빨리 끝나고 인덱스를 사용해도 기대한 행을 찾는지 따로 확인해야 해요. 랜덤 IV 컬럼에 걸린 findBy 는 기대한 행을 찾지 못했고, findAll 후 필터는 정답을 찾는 대신 더 오래 걸렸어요. 느린 쪽은 테스트 데이터 몇 행으로는 드러나지 않고, 틀린 쪽은 찾은 행 수를 정답과 맞춰 보는 테스트가 있어야 드러나요.

그래도 이 방식이 맞는 자리가 있어요. 그 컬럼을 조건으로 찾는 일이 관리자 화면의 드문 검색처럼 가끔이고, 대상 행을 다른 조건(날짜, 지점)으로 먼저 수백 행까지 줄일 수 있다면 복호화 비용은 그 수백 행에만 들어요. 기준은 "전체 행 수"가 아니라 "복호화해야 하는 후보 행 수 × 조회 빈도"예요.

5. ③ 블라인드 인덱스: 검색 키 분리와 빈도 노출

📖 용어: 블라인드 인덱스 (blind index)
평문의 키 있는 해시(HMAC)를 암호문과 별도 컬럼에 저장해 두고, 찾을 때는 그 해시로 찾는 방식이에요. 원래 값은 랜덤 IV 로 암호화해 저장해요. Paragon 의 글은 이 인덱스 키를 암호화 키와 다르게, DB 서버가 모르게 두라고 적어요.

Paragon Initiative 의 글이 이 방식을 정리했어요. 평문의 키 있는 해시를 별도 컬럼에 저장하는 것이 기본 생각이고, 인덱스 키는 암호화 키와 달라야 하며 DB 서버가 몰라야 한다고 설명해요(Building Searchable Encrypted Databases with PHP and SQL). JPA 로 옮기면 다음과 같이 구성할 수 있어요.

@Convert(converter = GcmConverter.class) // 원래 값: 랜덤 IV 그대로 @Column(name = "ssn_gcm") private String ssnGcm; @Column(name = "ssn_bidx") // 찾기용: 컨버터 없음, 인덱스 있음 private String ssnBidx; public void setSsn(String ssn) { this.ssnGcm = ssn; this.ssnBidx = Crypto.bidx(ssn); // HMAC-SHA256(인덱스 키, "claim.ssn|" + 정규화(ssn)) } // 저장소: 평문이 아니라 인덱스 값을 넘긴다 List<Claim> findBySsnBidx(String bidx); repo.findBySsnBidx(Crypto.bidx(ssn));

인덱스 컬럼에는 컨버터를 붙이지 않고, 호출부에서 HMAC을 계산해 전달해요. 그러면 검색 인자가 다시 암호화되지 않아요. HMAC을 계산하기 전에는 값을 정규화해야 해요. 실습 코드는 하이픈과 앞뒤 공백을 제거해서 같은 값으로 처리했어요. 이 규칙이 없으면 하이픈 유무나 뒤 공백에 따라 다른 인덱스가 나와요. DB 비교 규칙 때문에 뒤 공백을 구분하지 못했던 사례는 3편에 적었어요. 블라인드 인덱스를 쓸 때는 어떤 입력을 같은 값으로 볼지 코드에서 명시해야 해요.

findBySsnBidx는 5행을 찾았고 EXPLAIN은 type=ref key=idx_bidx였어요. p50은 측정한 행 수 범위에서 0.44~0.75ms로 결정적 방식과 비슷했어요. 빈도 분포도 결정적 방식과 같았어요.

그림 4. 실습의 블라인드 인덱스와 결정적 암호문은 같은 빈도 분포를 보였어요

ssn_bidx 의 서로 다른 값 4,996개, 상위 다섯 값의 행 수 719, 297, 214, 183, 150 이 결정적 컬럼과 평문과 전부 같았어요. Paragon 의 글도 DB 서버가 침해된 경우 공격자가 알 수 있는 건 여러 행이 같은 값을 공유하는지라고 설명해요. 이 실습의 블라인드 인덱스는 암호문 대신 인덱스 컬럼에서 동일성과 빈도를 드러냈어요.

③에서는 원래 값을 랜덤 IV로 암호화하므로 그 암호문만으로 평문의 반복 여부를 비교하기 어려워요. 또 검색용 키와 복호화 키를 분리해 각각의 권한을 관리할 수 있어요. 다만 인덱스가 함께 노출되면 앞서 본 빈도가 드러나고, 검색용 키도 암호화 키와 같은 수준으로 보호해야 해요. 짧은 인덱스를 쓸 때의 저장 공간과 조회 비용도 따로 확인했어요.

인덱스 키를 가진 사람은 후보 값을 HMAC으로 계산해 저장된 인덱스와 비교할 수 있어요. 주민번호처럼 후보를 열거할 수 있는 값은 이 방법으로 원래 값이 드러날 수 있어요. Paragon의 글은 민감한 정보에 PBKDF2-SHA256, scrypt, Argon2 같은 키 스트레칭 알고리즘을 적용해 열거 시도를 늦추는 방안도 안내해요. 적용하면 쓰기와 조회 때 인덱스를 계산하는 비용도 늘어나므로 함께 검토해야 해요.

짧은 인덱스의 충돌과 빈도 노출

Paragon의 글은 블라인드 인덱스를 16, 32, 64비트 정도로 줄여 저장 공간을 아끼는 방안을 제안해요. 비트 수를 줄이면 서로 다른 평문이 같은 인덱스에 대응하는 충돌이 생겨요. 조회 결과를 후보로 받아 앱에서 복호화해 확인해야 하는 이유예요. 실습에서는 충돌이 잘 드러나도록 12비트(4,096개 인덱스 값)를 사용했어요. 5만 행의 서로 다른 평문 4,996개가 4,096개 인덱스 값 중 하나에 대응하도록 만든 구성이에요.

(5만 행, 세 바퀴. 인덱스 키가 바퀴마다 달라 충돌도 달라진다) r1 r2 r3 서로 다른 인덱스 값 2,865 2,901 2,889 (평문 4,996) 가장 많은 인덱스 값 727 730 719 (평문 1등 719) 조회 후보 / 진짜 37 / 5 14 / 5 22 / 5 조회 p50 (복호화 확인 포함) 0.47ms 0.40ms 0.43ms

서로 다른 인덱스 값 수는 평문의 절반 남짓으로 줄었어요. 후보 14~37행을 복호화해 확인한 조회 시간은 0.5ms 안쪽이었어요. 하지만 가장 많은 인덱스 값의 행 수는 727, 730, 719로, 가장 흔한 평문 719행에 다른 값 몇 행이 합쳐진 정도였어요. 드문 값 사이에 충돌이 생겨도 자주 나오는 값의 빈도까지 충분히 감춰지지는 않았어요. 5만 행에서 인덱스 값 하나에 평균 719행 정도가 대응하려면 가능한 인덱스 값을 대략 70개까지 줄여야 해요. 이는 단순 평균 계산이며, 해당 구성의 검색 성능을 측정한 결과는 아니에요. 후보가 수백 행으로 늘면 복호화 확인 비용도 커지므로 인덱스 단축으로 빈도 노출을 없애기는 어려워요.

6. 키 회전 중 옛 키와 새 키의 검색 값을 함께 조회하기

키를 바꿀 때 비용은 두 가지예요. 전 행을 다시 쓰는 시간, 그리고 다시 쓰는 동안 조회가 맞는 답을 내는지예요. 5만 행을 1,000행씩 커밋하며 다시 쓰고, 절반을 옮긴 시점에 정답 5행인 사람을 찾아봤어요.

(results/rotate-r1~r3.txt, 5만 행) 전부 다시 쓰기 (r1 / r2 / r3) 절반 옮긴 시점의 조회 ① 결정적 키 회전 1.6s / 2.0s / 1.8s 새 키로 3행, 옛 키로 2행, IN(새, 옛) 5행 ② GCM 키 회전 1.7s / 2.0s / 1.8s 전 행 복호화 성공, 조회와 무관 ③ 블라인드 인덱스 키 회전 1.9s / 2.2s / 2.0s 새 키 HMAC 3행, 옛 키 HMAC 2행

다시 쓰는 시간은 셋 다 비슷했어요. 다만 갱신 외에 포함된 확인 시간이 달라 순수 갱신 시간끼리의 비교는 아니에요. ②의 숫자에는 추가 전 행 조회와, 정답 행을 찾으려고 각 행을 복호화·비교한 시간이 포함돼요. 별도로 복호화 뒤 행 수를 세는 스트림은 자바가 변환 연산을 생략할 수 있어, 그 개수 출력만으로 전 행 복호화를 확인했다고 볼 수는 없어요. 오른쪽의 복호화·조회 결과는 별도의 전 행 복호화·비교 경로를 기준으로 읽어야 해요. 차이는 오른쪽 칸이에요. ① 에서 컨버터가 새 키로 인자를 암호화하자 아직 옛 키로 남은 2행을 못 찾았어요. 세 실행 모두 3행이었어요. 회전하는 동안은 키마다 암호문을 만들어 컨버터를 거치지 않는 네이티브 쿼리나 JDBC 로 IN (새 키 암호문, 옛 키 암호문) 을 써서 찾아야 5행이 다 나왔고, 이건 findBy 한 줄이 아니라 직접 쓴 쿼리가 필요해요. 이때 컨버터가 걸린 필드에 JPQL IN :list 를 쓰면 안 돼요. 미리 만든 암호문을 전달해도 목록의 각 원소가 다시 컨버터를 거치므로, 컨버터를 우회하는 조회와 같지 않아요. 실습도 컨버터를 거치지 않는 JDBC 쿼리로 찾았어요. ③ 도 인덱스 키를 바꾸면 똑같이 3행이었어요.

그림 5. 결정적 암호화와 인덱스 키 회전 중에는 두 키의 검색 값을 함께 조회해야 해요

②는 암호문 맨 앞 1바이트에 키 번호를 넣고 그 번호로 복호화 키를 골랐어요. 옛 키와 새 키를 모두 보유한 상태에서는 절반을 옮긴 시점에도 5만 행을 복호화했고, 정답 5행을 찾았어요. 이 구현은 행을 읽거나 고칠 때 순차적으로 전환할 수도 있지만, 전환이 끝날 때까지 옛 키가 필요해요. 실제 회전 일정은 키 교체 사유와 정책에 맞춰 정해야 해요. ③은 암호화 키와 인덱스 키를 따로 바꿀 수 있어요. 암호화 키만 바꾸고 인덱스를 유지하면 검색 값은 그대로지만, 인덱스 키를 바꿀 때는 전환 중인 두 인덱스 값을 함께 조회해야 해요. ①도 옛 키와 새 키로 만든 검색 값을 함께 다뤄야 누락을 막을 수 있어요.

7. 조회 빈도와 후보 행 수로 비교하기

앞서 다룬 레거시 테이블에서는 등치 조회가 필요한 컬럼에 결정적 방식을, 그런 조회가 없는 컬럼에 랜덤 IV를 선택했어요(3편). 당시 선택의 배경은 남아 있는 조회의 차이였어요. 이번 실습 결과를 적용할 때도 값으로 검색해야 하는지, 얼마나 자주 조회하는지, 후보가 몇 행인지부터 확인하고 빈도 노출과 키 관리 요구를 함께 비교해야 해요.

① 결정적 ② 랜덤 IV + 앱 필터 ③ 랜덤 IV + 블라인드 인덱스 등치 조회 (findBy) 그대로 된다 0행 (조용히 틀림) 인덱스 값으로 된다 인덱스 탄다 (ref) 못 쓴다 (전 행 ALL) 탄다 (ref) p50, 10만 행 0.7ms 안팎 270ms 안팎 (JPA) 0.5ms 안팎 키 없이 보이는 빈도 평문과 같다 없다 평문과 같다 (자르면 꼬리만 흐림) 키 회전 중 조회 IN(새, 옛) 필요 영향 없음 인덱스 키 회전 때만 IN 필요 LIKE / 부분 검색 안 된다 (0행) 앱에서만 안 된다 코드 변경 컨버터만 조회마다 필터 컬럼 하나 + 호출부 HMAC

실습의 세 구성은 암호문에 SQL LIKE를 적용해 평문 부분 검색을 할 수 없어요. 뒷자리 네 개로 찾아야 한다면 해당 부분값에 대한 블라인드 인덱스를 따로 두는 방법을 검토할 수 있어요. 대신 뒷자리가 같은 행이 드러나므로 추가 노출을 평가해야 해요. 여러 길이의 접두어를 검색하려면 각 부분값의 인덱스가 필요해 저장 공간과 관리 비용도 늘어요. 다른 조건으로 후보를 줄인 뒤 ②로 비교하는 방법과 함께 검토할 수 있어요.

💡 적용 전에 확인할 것
• 암호화 컨버터가 붙은 필드를 쓰는 findBy, @Query, StartingWith/Containing을 먼저 확인해요. 실습과 같은 랜덤 IV 등치 조회에서는 기대한 행을 찾지 못할 수 있어요
• 테스트에서 조회 행 수를 정답과 비교해요. 예외 발생 여부와 EXPLAIN만으로는 결과의 정확성을 확인할 수 없어요
• ③을 검토한다면 인덱스 키를 암호화 키와 분리해 보호하고, HMAC 전에 정규화 규칙을 정해요. 인덱스 컬럼에는 컨버터를 붙이지 않아요. 후보를 열거할 수 있는 값은 키 스트레칭의 비용도 비교해요
• ①에는 AES-SIV처럼 결정적 암호화를 제공하는 방식을 사용해요. GCM의 IV를 고정하면 안 돼요. 같은 값의 반복 정도는 GROUP BY로 확인해요
• ②는 복호화할 후보 행 수와 조회 빈도를 함께 살펴봐요. 다른 조건으로 후보를 줄일 수 있는지도 확인해요
• ①과 ③의 인덱스 키를 회전할 때는 옛 키와 새 키의 검색 값을 함께 조회할 계획을 세워요. ①은 컨버터가 인자를 다시 변환하지 않도록 조회 경로도 확인해야 해요
✍️ 조회 방식별 확인 결과
JPA는 변환이 걸린 속성과 비교하는 인자도 컨버터에 전달해요. 실습의 랜덤 IV 컬럼은 findBy가 0행을 반환했고, LIKE도 %까지 암호화돼 기대한 행을 찾지 못했어요.

결정적 암호화와 블라인드 인덱스는 빠른 등치 조회가 가능했지만 빈도 분포가 드러났어요. 전 행을 복호화해 비교하면 정답을 찾는 대신 조회 시간이 1만 행 28ms에서 10만 행 270ms 안팎으로 늘었어요. 인덱스를 12비트로 줄여도 가장 흔한 값의 빈도는 충분히 감춰지지 않았어요.

결정적 키나 인덱스 키를 회전하는 동안에는 두 키의 검색 값을 함께 조회해야 누락을 막을 수 있었어요. 이 수치는 가짜 데이터와 실습 환경에서 측정한 결과이며, 실제 선택에는 후보 행 수·조회 빈도와 함께 빈도 노출 및 키 관리 요구를 반영해야 해요.
