10월 7일, 4편에서 다룬 변경을 올리고 독립 리뷰를 받았어요. 변경요청 5건과 권고 4건으로, 모두 9건의 지적이 나왔습니다.

첫 지적은 관리자가 직접 쓴 코멘트가 암호문 접두어와 같은 모양으로 시작하면, 해당 건의 이력 조회 전체가 실패할 수 있다는 내용이었어요. 운영에서 발생한 장애 사례가 아니라 리뷰에서 찾은 회귀였습니다.

📖 용어: 독립 리뷰
이 작업에서는 코드를 고친 사람과 다른 리뷰어가 설계 문서와 구현을 대조했어요. 변경요청에는 문제가 있는 위치와 이유, 수정 제안이 붙었습니다.

4편에서 붙인 컨버터는 쓸 때 대상 문구인지 확인하고, 읽을 때는 저장값의 앞머리를 보고 복호화를 시도했어요. 같은 컬럼에 사람이 자유롭게 쓴 코멘트도 들어오는데, 읽기에서는 이 차이를 구분하지 못했습니다. 이 때문에 생긴 회귀와 같은 리뷰에서 지적받은 롤백·로그·테스트 문제를 함께 수정했어요.

1. 사람이 쓴 글이 암호문 모양으로 시작할 때

당시 업무 이력에는 44종의 이벤트 문구가 한 컬럼에 쌓였어요. 4편에서 암호화 대상으로 고른 건 그중 한 종류, 계좌 정보가 도착했다는 고정 문구뿐이었습니다. 나머지 43종은 4편에서 본 조회 두 곳이 평문으로 읽어야 해서 그대로 뒀어요.

쓰기에서는 대상 문구를 구분했지만, 읽기 컨버터는 44종 모두에 적용됐어요. 이벤트 종류를 받지 않고 저장값의 앞머리만 보고 복호화할지 정했습니다.

그 44종 중에 관리자가 자유롭게 입력하는 코멘트 이벤트가 하나 있었어요. 사람이 쓴 문장이 그대로 문구가 됩니다. 그 문장이 우연히 암호문 접두어와 같은 모양으로 시작하면, 컨버터는 암호문이라고 보고 복호화를 시도해요.

📖 용어: 복호화 실패
이 방식에서는 복호화할 때 암호문에 붙은 검증값도 확인해요. 필요한 형식이나 검증값이 맞지 않으면 복호화가 실패합니다. 앞머리가 같다는 사실만으로 정상 암호문이라고 판단할 수는 없어요.

수정 전에는 복호화가 실패하면 예외를 던졌어요. 이력 조회는 해당 건의 이벤트를 한 번에 읽는 경로라, 한 행의 복호화 실패가 조회 전체의 실패로 이어질 수 있었습니다. 같은 조회를 반복하면 스택이 붙은 ERROR 로그도 반복되는 구조였어요.

그 코멘트는 암호화를 붙이기 전에는 화면에 표시할 수 있는 평문이었어요. 읽기 컨버터를 추가하면서 기존 입력을 처리하지 못하게 된 회귀였습니다.

그림 1. 쓰기는 종류를 보고 갈랐지만, 읽기는 모양 하나로 판정했습니다

2. 복호화 실패 시 저장값을 반환하도록 바꿨어요

고친 방향은 접두어 판정을 정교하게 만드는 쪽이 아니었어요. 어떤 접두어를 골라도 사람이 그 모양으로 시작하는 문장을 쓸 수 있으니까요.

당시에는 복호화를 시도한 뒤 실패하면 예외를 던지지 않고 저장값을 그대로 반환하도록 바꿨어요. 이 코멘트는 암호화를 붙이기 전과 같이 원문으로 읽을 수 있게 됐습니다. 실패 시 WARN에는 입력 길이만 남기고 값은 쓰지 않도록 했어요.

읽기 (수정 전) 앞머리가 {접두어} → 복호화 # 실패하면 예외 아니면 → 그대로 관리자 코멘트 "{접두어}로 시작하는 아무 문장" → 복호화 실패 → 예외 → 그 건의 이력 조회 전체 실패 + ERROR 로그 읽기 (수정 후) 앞머리가 {접두어} → 복호화 시도 성공 → 복호화한 문구 실패 → 저장값 그대로 (길이만 WARN) 아니면 → 그대로

평문을 암호문으로 오인해도 조회를 계속할 수 있게 한 선택이에요. 다만 복호화 실패 시 저장값을 반환한다는 것만으로 평문과 암호문을 완전히 구분하거나, 반환한 값이 정상이라고 보장할 수는 없습니다.

2편에서는 암호화 실패 시 평문으로 저장했고, 이번에는 복호화 실패 시 저장값을 반환했어요. 둘 다 기존 기능의 중단을 피하려고 선택한 동작이었습니다. 다만 2편에서는 평문이 0건이 되면 암호문만 읽는 컨버터로 바꾸기로 했어요. 이번 컬럼은 43종을 평문으로 남기는 설계라 같은 전환 조건을 적용할 수 없었습니다.

회귀 테스트에는 암호문 모양으로 시작하는 텍스트를 넣고, 예외 없이 원문이 반환되는지 확인하는 케이스를 추가했어요. 리뷰 기록에도 이 입력을 읽는 테스트가 없다는 지적이 따로 있었습니다. 이 테스트가 확인한 범위는 해당 입력의 반환 동작이에요.

⚠️ 주의: 읽기 회귀 수정과 판별의 한계
당시 설계에는 쓰기 판정과 배치 대상 범위가 일치하지 않는 한계도 남아 있었어요. 이 점은 설계 문서와 코드 주석에 기록했습니다. 읽기 회귀를 수정했다는 사실을 평문·암호문 판별이나 복원 범위 전체가 검증됐다는 뜻으로 해석할 수는 없어요.

3. 쓰기가 계속되는 테이블의 롤백 순서를 고쳤어요

두 번째 변경요청은 코드가 아니라 설계 문서의 한 줄이었어요. 롤백 순서가 "복원 완료 → 이전 버전"으로 적혀 있었고, 괄호로 "앞 대상과 같은 이유"라고 달려 있었습니다. 3편에서 다룬 레거시 테이블의 절차를 그대로 옮겨 적은 거예요.

3편의 테이블은 쓰기가 1년 반 넘게 멈춰 있었어요. 옛 데이터만 남아 있어 복원 뒤에 새 암호문이 생기지 않는 조건이었습니다. 반면 이번 테이블에는 하루에 수십 건씩 새 이력이 쌓이고 있었어요.

쓰기 스위치가 켜진 상태라면 복원 중에도, 복원 완료 뒤 이전 버전으로 전환하기 전에도 새 암호문이 생길 수 있어요. 이전 버전에는 복호화 컨버터가 없으므로, 그 사이에 쌓인 암호문은 롤백 뒤 화면에 그대로 표시될 수 있었습니다.

롤백 순서 (수정 전 · 3편 대상의 절차를 그대로 옮겨 적음) 1. 복원 배치 실행 완료 2. 이전 버전으로 되돌리기 ^ 1 이 도는 동안과 1~2 사이에도 새 이력은 계속 암호화된다 이전 버전에는 복호화할 코드가 없다 → 암호문이 화면에 남는다 롤백 순서 (정정) 1. 쓰기 스위치를 끄고 재배포 (운영 API · 배치) 컨버터는 꺼져도 읽기는 복호화한다 → 화면 정상, 새 이력은 평문으로 쌓임 2. 복원 실행 → 쓴 건수 확인 → 검증 모드로 암호문 0건 확인 3. 이전 버전으로 되돌리기 배치까지 먼저 되돌리면 복원을 실행할 코드가 없다

4편에 적은 순서는 이 지적을 반영한 결과예요. 새 암호문이 생기지 않도록 쓰기 스위치를 먼저 끄고, 복원한 뒤 잔여 암호문을 별도로 집계해야 해요. 위의 보존된 절차에는 “검증 모드로 암호문 0건”이라고 적혀 있지만, 이 글의 검증 출력은 남은 평문과 복호화 실패를 집계해요. 당시 구현이 복원 후 잔여 암호문 집계를 지원했는지는 원본이 없어 확인하지 못했어요.

이전 버전으로 전환하기 전에는 복원해야 할 전체 범위를 기준으로 암호문이 남지 않았는지 확인해야 해요. 배치 대상에서만 0건이어도 컬럼 전체의 암호문 부재를 보장하지는 않아요. 쓰기 판정과 복원·집계 대상이 다를 수 있으므로 누락된 범위를 별도로 확인해야 해요. 아래 그림의 0건 확인도 이 전체 범위 확인을 뜻하는 절차이며, 당시 구현의 검증 완료 결과는 아니에요.

당시에는 설정 변경을 읽히려면 재배포가 필요했어요. 스위치를 끄는 절차에도 1편에서 다룬 설정 로딩 조건이 적용됐습니다. 위 순서는 정정한 절차이며, 여기서 실제 운영 롤백을 실행했다는 뜻은 아니에요.

그림 2. 쓰기가 계속되는 테이블에서는 복원보다 스위치가 먼저입니다
💡 실무에서는: 롤백 절차를 복사하기 전에
• 테이블에 쓰기가 계속되는지 확인하고, 새 암호문이 생기는 조건을 복원보다 먼저 해제해요
• 복원 도구가 새 버전에 있다면 복원과 검증을 마칠 때까지 그 버전을 유지해야 해요
• 문서에는 절차뿐 아니라 각 단계가 필요한 이유도 적어 두는 편이 좋아요

4. 기동 로그와 쓰기 예외에 담는 내용을 고쳤어요

권고 두 건은 오류가 났을 때 로그와 알림에 어떤 정보가 남는지에 관한 내용이었어요.

첫째는 기동 로그입니다. 1편의 장애 뒤에 운영에서 쓰기 스위치가 꺼져 있으면 ERROR를 남기는 장치를 붙여 뒀어요. 이번에 스위치가 하나 늘었는데, 판정 조건에는 새 스위치를 넣고 ERROR 메시지에는 넣지 않았습니다. 그래서 새 스위치만 꺼지면 ERROR는 뜨지만 메시지에 찍힌 값 세 개가 모두 참이에요. 알림을 보고도 무엇이 꺼졌는지 알 수 없습니다. 테스트도 로그 수준만 보고 있었어요. 메시지에 항목을 넣고, 테스트가 메시지 문자열까지 확인하게 바꿨습니다.

둘째는 배치의 쓰기 예외였어요. 4편에 "쓰기 예외는 원인을 떼고 다시 던진다"고 적어 뒀죠. 앞선 대상의 배치에서 세운 방침인데, 이번 배치는 원인 예외를 그대로 다시 던지고 있었어요. 문서의 방침과 구현이 달랐습니다.

📖 용어: 원인 예외
예외를 다시 던질 때 "무엇 때문에 실패했는지"를 안쪽에 달아 보내는 걸 말해요. 디버깅에는 좋습니다. 대신 안쪽 예외의 메시지가 바깥으로 같이 흘러가요.

원인 예외를 분리한 이유는 안쪽 메시지에 쓰려던 값이 포함될 수 있기 때문이에요. 당시 검토에서는 문자 인코딩 오류처럼 값 일부가 바이트로 표시되는 경우를 고려했습니다. 예외가 배치 스케줄러 로그와 실패 알림까지 전달되는 경로도 함께 봤어요.

특히 복원 모드는 암호문을 평문으로 쓰므로, 쓰기 실패 메시지에 값이 섞이면 평문이 알림에 남을 수 있었어요. 그래서 원인 예외를 분리하고 행 식별자와 "쓰기 실패로 페이지를 되돌렸다"는 사실만 담아 다시 던지도록 바꿨습니다. 복구에 필요한 행 정보는 남기되, 값이 포함될 수 있는 원인 메시지는 이 예외에 연결하지 않도록 한 조치였어요.

그림 3. 디버깅에 좋은 원인 연결이 평문 유출 경로가 되기도 합니다

5. 테이블 읽기 비용에 맞춰 락 보유 시간을 늘렸어요

4편에서 계산한 배치 비용은 한 번 실행할 때 테이블을 사실상 한 번 다 읽는 수준이었어요. 하지만 설계 문서에는 이 계산이 빠져 있었습니다.

리뷰에서 페이지당 읽는 행 수를 계산하면서 분산 락 설정도 함께 확인했어요. 여러 인스턴스 중 한 대만 배치를 실행하도록 설정했는데, 락 보유 시간은 10분이었습니다.

📖 용어: 분산 락 보유 시간
여러 인스턴스가 같은 배치를 동시에 실행하지 않도록 공유 저장소에 락을 설정해요. 그 락을 언제까지 유효하게 볼지 정한 값이 보유 시간입니다. 실제 실행이 그보다 길어지면 락이 만료돼 다른 인스턴스도 실행을 시작할 수 있어요.

테이블을 한 번 다 읽는 실행이 10분 안에 끝난다는 보장은 없었어요. 당시에는 4편의 조건부 갱신으로 같은 행의 중복 변경을 피하는 설계였지만, 여러 인스턴스가 동시에 읽는 비용까지 줄여 주지는 못했습니다. 중복 실행 가능성을 줄이려고 보유 시간을 10분에서 30분으로 늘렸어요.

한 페이지에 몇 행을 읽는지, 한 실행이 테이블을 몇 번 읽는지도 설계 문서에 적었어요. 락 보유 시간을 정할 때 참고할 수 있도록 계산 근거를 남겼습니다.

6. 누락된 테스트를 보완하고 로컬 DB에서 확인했어요

남은 지적은 넷이었어요. 셋은 테스트고, 하나는 설계 문서의 근거 한 줄이었습니다. 이 배치는 앞서 같은 틀로 만든 다른 대상의 배치에서 구조를 거의 그대로 가져왔습니다. 페이지 크기와 지표 이름 하나를 빼면 같았어요. 그런데 테스트는 가져오지 않았습니다.

앞 배치에는 진행 위치 저장, 끝에 닿았을 때 스위치 삭제, 페이지 실패 시 직전 위치 저장 같은 동작을 보는 테스트가 10개 있었고 스케줄러 테스트도 있었어요. 이번 배치에는 서비스 계층 테스트와 SQL 문자열을 맞춰 보는 테스트만 있었고, 진행 위치가 실제로 저장되는지 보는 테스트는 한 개도 없었습니다.

그래서 앞 배치의 테스트를 기준으로 채웠어요. 종류 필터 때문에 0행 페이지가 나와도 진행 위치가 제자리에 머물며 종료 판정이 되는지 보는 케이스를 하나 더 넣었습니다. 인덱스가 없어 훑는 구조라 0행 페이지가 실제로 나올 수 있어요.

마지막은 로컬 DB 실측이었습니다. 배치 SQL 테스트가 가짜 객체로 문자열만 비교하고 있어서, 조건부 갱신이 실제 DB에서 어떻게 도는지, 소프트 삭제된 행도 포함되는지, 수정 시각이 정말 그대로인지가 확인되지 않았어요. 그래서 로컬 DB에 테스트 행을 넣고 세 모드를 차례로 돌렸습니다.

첫 시도에서는 셸 클라이언트의 문자셋을 지정하지 않아 한글이 깨진 바이트로 저장됐어요. 채우기는 그 2건을 "모르는 문구"로 보고하고 변경하지 않았습니다. 해당 입력에서는 접두어가 맞지 않는 값을 제외하는 조건이 동작했어요. 문자셋을 맞춰 다시 넣은 뒤 위 결과를 얻었습니다.

주석에만 적혀 있던 확인

기존 테스트가 설명한 범위와 실제로 실행한 범위가 다른 문제도 있었어요.

4편에서 돌린 로컬 DB 테스트에는 설명 주석이 붙어 있었어요. 평문으로 읽어야 하는 그 조회 두 곳이 이번 변경 뒤에도 그대로 찾는지 본다고 적혀 있었습니다. 그런데 리뷰가 그 클래스의 메서드를 하나씩 세어 보니, 그 조회를 실제로 부르는 메서드가 한 개도 없었어요. 테스트는 네 개였고, 같은 조건을 다른 질의 방식으로 대신 확인하고 있었습니다.

4편의 "조건으로 쓰는 조회가 그대로 찾는지 확인했다"는 설명은 주석에 적힌 범위를 그대로 받아들인 것이었어요. 실제 테스트는 유사한 조건을 다른 질의로 확인했으므로, 해당 조회 자체를 검증했다고 말하기에는 부족했습니다.

⚠️ 주의: 테스트의 설명과 테스트가 하는 일은 다를 수 있어요
테스트 이름이나 주석만으로 검증 범위를 판단하기는 어려워요. 실제로 호출한 메서드와 질의, 결과를 비교하는 코드를 함께 봐야 설명과 실행 범위가 일치하는지 알 수 있습니다.

그래서 네이티브 SQL로 문구 앞부분을 잘라 비교하는 조회를 직접 부르는 케이스를 추가하고, 주석을 테스트가 실제로 하는 범위로 고쳤어요. 등치로 비교하는 쪽은 다른 테이블을 묶고 전날을 기준으로 삼는 구조라, 같은 조건을 다른 질의 방식으로 보는 기존 케이스를 그대로 뒀습니다. 직접 호출해 확인한 범위는 앞부분 비교 조회이고, 등치 조회는 여전히 다른 질의로 같은 조건을 확인한 결과였어요.

배치 구조를 가져오면서 테스트를 빠뜨린 문제와, 테스트 주석의 범위를 실제 실행으로 확인하지 않은 문제를 각각 수정했어요.

사본 테이블이 없는 이유를 정정했어요

마지막 한 건은 코드도 테스트도 아니고 설계 문서였어요. 이 테이블은 변경 이력을 자동으로 따로 복사해 두는 기능의 대상이 아니라 사본 테이블이 없는데, 문서에는 그 이유가 "부모 클래스에 그 표시가 없어서"라고 적혀 있었습니다. 실제로는 부모에 표시가 있었고, 엔티티 쪽에 없어서 대상이 아니었어요.

사본 테이블이 없다는 결론은 같아서 코드 변경은 필요하지 않았어요. 문서의 이유는 엔티티 쪽에 표시가 없기 때문이라고 고쳤습니다. 부모 클래스 변경의 영향을 판단할 때 잘못된 근거를 사용하지 않도록 한 정정이었어요.

수정 뒤 재리뷰는 받지 않았어요. 당시에는 진행을 막는 지적이 없다고 판단했지만, 수정 내용에 대한 재승인까지 받은 것은 아닙니다.

이번 수정에서는 같은 컬럼에 들어오는 자유 입력, 쓰기가 계속되는 동안의 복원 순서, 로그에 연결되는 예외와 테스트의 실제 호출 범위를 다시 확인했어요. 로컬 DB 실행과 추가한 테스트로 확인한 범위가 있으며, 이를 운영 전환 전체나 보안 검증의 완료로 볼 수는 없습니다.

✍️ 정리
평문 코멘트를 암호문으로 오인했을 때 조회가 실패할 수 있어, 복호화 실패 시 저장값을 반환하도록 바꾸고 회귀 테스트를 추가했어요. 이 변경은 기존 입력의 조회를 유지하기 위한 선택이었으며, 평문과 암호문을 완전히 구분하는 해결책은 아닙니다.

같은 리뷰에서 롤백 순서, 기동 로그, 쓰기 예외, 분산 락 보유 시간과 테스트를 보완했어요. 로컬 DB에서는 테스트 행 4건으로 채우기·검증·복원을 실행했지만, 수정 뒤 재리뷰는 받지 않았습니다. 남은 판별 한계와 테스트가 직접 확인하지 않은 조회 범위를 구분해서 봐야 해요.
