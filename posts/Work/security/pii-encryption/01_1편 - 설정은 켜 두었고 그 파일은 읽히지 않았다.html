1편. 운영 프로필에 적용되지 않은 암호화 설정과 설정 테스트의 한계 ← 지금 이 글

당시 작업 기록에 따르면, 2026년 10월 2일 오전 9시 39분에 어드민의 대행인 목록에서 오류가 났어요. 문의 채팅에서도 같은 오류가 올라왔어요. 그날 아침에는 컬럼 값을 읽고 쓸 때 거치는 변환기(컨버터)에서 평문 처리 경로를 지우고, 암호문만 읽도록 배포한 상태였어요.

복호화 실패: 암호문 형식이 아님

→ 컬럼에서 읽은 값이 암호문 접두어로 시작하지 않는다는 뜻이에요. 당시 조사에서는 평문이 남아 있는 것으로 확인했어요.

하루 전에는 쓰기 암호화를 켜는 배포를 내보냈어요. 17시 45분에 실행한 일회성 배치 로그에는 대상 전체를 암호화했다고 나왔고, 설정 테스트도 통과했어요. 배치가 끝난 뒤 DB를 직접 집계한 결과도 평문 0행, NULL 0행이었어요.

배포와 테스트가 끝났다는 사실만으로 운영 API에 쓰기 암호화가 적용됐는지는 알 수 없었어요. 배치 로그와 DB 집계는 배치 직후의 데이터를 확인한 결과였고, 이후 API가 어떤 값을 쓰는지까지 확인한 것은 아니었어요.

배치 직후에는 평문이 없었지만, 이후에도 쓰기는 계속됐어요. 원인을 조사하면서 집계 이후 일부 값이 다시 평문으로 저장됐다는 것을 확인했어요.

직전 배포 버전으로 롤백하고 코드도 되돌렸어요. 조사 결과, 전날 추가한 쓰기 암호화 설정이 운영에서 읽히지 않는 파일에 들어 있었어요.

1. 그 시점에 평문이 없어야 했던 이유

암호화 대상은 대행인 계좌번호 컬럼의 2,113행이었어요. 새 컬럼을 만들지 않고 평문이 있던 컬럼에 암호문을 덮어쓰는 방식이었어요.

📖 용어: 관대한 컨버터 (lenient converter)
JPA 가 컬럼 값을 읽고 쓸 때 거치는 변환기예요. 읽을 때 값이 암호문 접두어로 시작하면 복호화하고, 아니면 평문으로 보고 그대로 넘깁니다. 평문과 암호문이 한 컬럼에 섞여 있는 전환 기간에 사용하는 방식이에요.

배포는 둘로 나눴어요. 당시에는 교체 중에 이전 버전 컨테이너(태스크)와 새 버전이 15분쯤 함께 실행됐어요. 그래서 1차에서는 평문과 암호문을 모두 읽게 하고, 2차에서 쓰기 암호화를 켰어요. 이 배포 순서는 2편에서 다뤄요.

오류가 난 아침은 2차 배포와 일괄 암호화를 마친 다음 날이었어요. 쓰기 암호화까지 적용됐다면 이후에도 평문이 새로 저장되지 않을 것으로 예상했어요.

2. 운영이 읽는 파일은 그 파일이 아니었다

쓰기 암호화 여부를 정하는 설정값을 API 모듈의 운영 프로필 설정 파일에 넣었어요. 파일 이름을 보고 운영에서 읽는 파일이라고 판단했어요.

당시 기록에 남긴 설정 예시는 아래와 같아요. 실제 파일과 변경 커밋은 이번에 다시 대조하지 못했어요.

[ API 모듈의 운영 프로필 설정 파일 ] # 스위치를 여기 넣었다 spring: config: activate: on-profile: dev # 2025-10-24 부터 이렇게 되어 있었다 ... encryption: {대행인 계좌번호}: encrypt-on-write: true # 운영에서는 이 줄이 읽히지 않는다 [ 공용 모듈의 운영 설정 파일 ] # 운영 API 가 실제로 읽는 쪽 # 파일 이름에 활성 프로필을 끼워 넣어 불러온다 # 이 파일에는 커넥션 풀, 외부 서비스 주소, 점검 시간 등이 들어 있다

→ on-profile: dev는 dev 프로필일 때 이 설정 문서를 적용하는 조건이에요. 당시 운영 태스크의 활성 프로필은 prod였고, 작업 기록에서는 이 조건 때문에 해당 설정이 적용되지 않은 것으로 정리했어요.

📖 용어: 프로필 (profile)
환경마다 다른 설정을 선택할 때 쓰는 이름이에요. 실행할 때 prod 같은 프로필을 활성화하며, 여러 프로필을 함께 활성화할 수도 있어요. 파일 이름에 따라 선택하는 방식과 파일 안의 on-profile 조건을 사용하는 방식이 함께 쓰여요.

당시 조사 기록에는 이 조건이 2025년 10월 24일 커밋에서 바뀌었다고 나와요. 커밋 제목은 "운영 설정 파일을 두 모듈에서 중복 사용하고 있음"이었어요. 중복된 설정을 정리하면서 API 모듈 쪽에 dev 조건을 두었고, 이후 운영 API는 공용 모듈 쪽 설정 파일을 사용한 것으로 파악했어요.

그림 1. 운영 프로필에서 적용 조건을 만족하는 설정 파일

3. 배치와 개발 환경에서는 설정이 적용됐다

같은 쓰기 암호화 설정을 세 곳에 넣었지만, 조사한 범위에서 적용되지 않은 곳은 운영 API였어요.

배치 모듈의 운영 설정 파일에는 on-profile: prod가 있어 쓰기 암호화가 적용됐어요. 개발 환경에서도 dev 프로필 파일의 설정이 적용됐고요. 운영 API와 설정 로딩 조건이 달라 개발 환경에서는 같은 증상을 재현하지 못했어요.

일회성 배치가 17시 45분에 전 행을 암호화한 뒤, 대행인이 로그인하면서 다시 쓰기가 발생했어요.

📖 용어: 부분 갱신 (@DynamicUpdate)
하이버네이트에서 변경된 컬럼만 UPDATE 문에 포함하도록 하는 설정이에요. 당시 기록상 이 엔티티에는 그 설정이 없었고, 로그인 시각을 바꾸는 UPDATE 문에 계좌번호 컬럼도 포함됐어요.

로그인하면 마지막 로그인 시각을 갱신해요. 이때 생성된 UPDATE 문에는 계좌번호 컬럼도 포함됐어요. 조사 기록에서는 쓰기 암호화가 적용되지 않은 태스크가 복호화된 값을 그대로 저장하면서, 로그인한 대행인 61명의 계좌번호가 평문으로 되돌아간 것으로 정리했어요.

배치는 매일 새벽 4시 휴면 전환 작업에서 같은 엔티티를 수정했어요. 배치에는 쓰기 암호화가 적용돼 있어 수정한 값을 암호화해 저장했어요. 같은 엔티티를 사용해도 모듈별 설정 적용 여부에 따라 저장 결과가 달랐어요.

그림 2. 당시 로그인 시각 갱신의 UPDATE 문에 계좌번호도 포함된 경로

4. 파일 검사에서 프로필별 적용값 검사로 바꾸기

기존 설정 테스트는 이 문제를 발견하지 못했어요. yml 파일에 설정 키가 있는지 검사했기 때문에, 운영 프로필에서 파일을 읽지 않아도 통과했어요.

[ 고치기 전 ] yml 파일을 직접 열어서 "encrypt-on-write" 키가 있는가 -> 있다 -> 통과 [ 고친 뒤 ] 활성 프로필을 운영 태스크와 똑같이 prod 로 지정하고 운영과 같은 설정 소스로 스프링 환경을 올린 다음 Environment 에서 꺼낸 값이 true 인가 -> 단언 dev · local 프로필도 같은 방식으로 단언

→ 기존 테스트는 파일에 설정이 적혀 있는지 확인했어요. 수정한 테스트는 지정한 프로필과 설정 소스로 스프링 환경을 구성한 뒤 실제 적용값을 확인해요. 파일 선택 조건을 검사 범위에 포함한 거예요.

다만 테스트가 설정 소스를 직접 지정하므로 실제 실행 환경과 차이가 남아요. 운영에서 활성 프로필을 다르게 주거나 환경변수로 값을 덮어쓰는 경우까지 이 테스트로 확인할 수는 없어요. 실제 기동 시 적용값을 로그에 남긴 이유예요.

설정 위치를 옮기기 전에 새 테스트부터 실행했고, 기존 설정에서 실패하는 것을 확인했어요. 이후 설정을 옮겨 통과 여부를 봤어요. 이 순서로 이번 적용 조건 오류를 테스트가 발견하는지 확인했어요.

💡 실무에서는
• 파일에 키가 있는지 확인하는 검사만으로는 프로필별 파일 선택 오류를 발견하기 어려워요
• 프로필과 설정 소스를 실행 환경에 맞춰 구성하고 실제 적용값을 검사해요
• 수정 전 실패와 수정 후 통과를 함께 확인하면 이번 결함을 검사하는지 알 수 있어요
그림 3. 파일의 키 존재 여부와 프로필별 적용값을 검사하는 범위

5. 전환 직전 검증을 건너뛴 과정

암호문만 읽는 3차 작업에는 검증 배치 통과를 머지 조건으로 적어 뒀어요. 이 배치는 데이터를 바꾸지 않고 평문으로 남은 행과 복호화에 실패한 행을 세도록 했어요.

📖 용어: 검증 모드 (VERIFY)
일회성 배치를 채우기와 검증 두 모드로 나눠 뒀어요. 채우기는 평문 행을 암호화하고, 검증은 아무것도 쓰지 않고 평문으로 남은 행 수와 그 행의 식별자만 로그로 남깁니다. 암호문 전용으로 전환해도 되는지 판단하기 위한 검사예요.

당시 기록에는 당일 17시 45분 실행분의 검증을 조건으로 두었지만, 3차 작업이 그 전에 머지됐다고 나와요. 이후 확인한 평문은 61행이었어요. 다만 예정된 검증 시각에 몇 행이었을지는 별도로 확인하지 못했어요.

전날 저녁의 평문 0행은 그 시각에 확인한 결과였어요. 이후에도 쓰기가 계속되므로 암호문 전용으로 전환하기 전에 다시 검증하려던 것이었어요. 이전 집계만으로 전환을 결정하면서, 직전 상태를 확인하는 절차를 건너뛰었어요.

⚠️ 주의: 문서의 머지 조건은 자동으로 강제되지 않아요
• 당시에는 검증 조건과 이유를 문서에 적었지만, 미충족 시 머지를 막는 장치는 없었어요
• 문서에 적은 검증 순서를 실제 머지 과정에서 지키지 못했어요
• 쓰기가 계속되는 동안에는 이전 집계 이후 데이터가 달라질 수 있어요

6. 설정 파일 전체 대신 필요한 값만 옮기기

수정안은 두 가지였어요. 쓰기 암호화 설정 두 개를 공용 모듈의 운영 설정 파일로 옮기거나, API 모듈 파일의 적용 조건을 운영 프로필로 바꾸는 방법이었어요.

API 모듈 파일은 1년 가까이 운영에 적용되지 않은 상태였어요. 적용 조건을 바꾸면 쓰기 암호화 설정 두 개 외의 설정도 함께 적용돼요. 당시 비교한 결과 함께 바뀌는 운영 설정은 13개였어요. 커넥션 풀 크기, 엔티티 이름 짓기 규칙, 점검 시간 등이 포함됐어요.

장애 수정 배포에서 변경 범위를 넓히지 않으려고 쓰기 암호화 설정만 옮겼어요. 기존 파일 맨 위에는 "이 파일은 운영에 적용되지 않는다"는 주석을 달았고, 파일 삭제는 별도 작업으로 남겼어요.

같은 날 기동이 끝날 때 쓰기 암호화 설정값을 로그에 남기도록 했어요. 파일에 적힌 값과 실제 적용값을 구분해서 확인하려는 변경이었어요.

같은 로그에는 키 지문도 남기도록 했어요. 암호화 키 해시의 앞 4바이트를 16진수로 표시한 값으로, API와 배치의 키 설정을 대조하려고 넣었어요. 당시 조치 내용은 이 비교값을 추가한 것이며, 그 값만으로 키 일치를 확정했다는 뜻은 아니에요.

당시 수정은 독립 리뷰에서 통과 판정을 받았고, 권고 7건 중 다섯 개를 반영했다고 기록돼 있어요. 그중 배치에도 실제 적용값 테스트를 추가하고, 운영 프로필에서 쓰기 암호화가 꺼져 있으면 ERROR 로그를 남기고, 모든 태스크 교체 후 채우기 배치를 실행하도록 절차를 정리했어요. 기동을 실패시키는 방식은 택하지 않았어요. 설정 오류로 서비스 기동까지 막기보다는 오류 로그를 남기는 쪽을 선택했어요.

당시 후속 계획은 되돌아간 61행을 다시 암호화하고 검증한 뒤 암호문 전용 컨버터를 배포하는 것이었어요. 저녁 배치는 예정만 확인한 상태였고 실행 결과는 확인하지 못했어요. 현재 데이터나 후속 배포 상태를 확인한 결과는 포함하지 않아요.

당시에는 3차 작업을 되돌리면서 전날 집계가 적힌 설계 문서의 해당 절과 3차 작업 점검 문서도 함께 삭제됐다고 기록했어요. 이전 판단의 근거를 보려면 되돌리기 전 커밋을 확인해야 했어요. 이번에는 그 원본 커밋과 실행 로그를 확보하지 못해, 사고 시각·수치·원인·조치 결과는 당시 작업 기록의 범위로 한정해요.

✍️ 요약
당시 기록에서는 운영 프로필에 적용되지 않는 파일에 쓰기 암호화 설정을 넣은 것이 원인이었어요. 배치 직후 평문은 0행이었지만, 이후 로그인 시각을 갱신하면서 61명의 계좌번호가 다시 평문으로 저장됐어요.

필요한 설정을 실제 적용되는 파일로 옮기고, 프로필별 적용값 테스트와 기동 로그를 추가했어요. 기존 파일 전체를 활성화하면 운영 설정 13개가 함께 바뀌어 그 방법은 택하지 않았어요. 수정 전 테스트 실패를 확인한 과정과 전환 직전 검증을 건너뛴 점도 남겼어요.

사고 수치와 조치 내용은 당시 작업 기록에 근거해요. 원본 코드와 실행 로그를 다시 확보하지 못했으며, 후속 배치의 실행 결과나 현재 운영 상태는 확인하지 않았어요.
