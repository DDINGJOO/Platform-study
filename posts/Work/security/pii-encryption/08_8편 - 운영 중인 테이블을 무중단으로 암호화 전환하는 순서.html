8편. 운영 테이블 암호화에서 읽기·쓰기·검증을 나눠 배포하기 ← 지금 이 글

실습에서 주민번호 형식의 가짜 평문 30만 행을 넣고, 앱 두 대가 계속 읽고 쓰게 했어요. 읽기 전환과 쓰기 암호화를 한 버전으로 묶어 롤링 배포했더니, 배포가 진행된 약 20초 동안 5,773건 중 164건이 200 응답에 암호문을 담아 돌아왔어요. 요청 오류는 한 건도 없어서, 오류 건수만 보는 모니터링으로는 응답 값이 달라진 사실을 알 수 없었어요.

기존 평문을 암호화로 바꾸는 동안에는 옛 버전도 새 버전이 쓴 값을 읽을 수 있어야 해요. 그래서 컬럼을 넓히고, 평문과 암호문을 모두 읽는 컨버터를 배포한 뒤, 쓰기 암호화를 켜는 순서로 나눴어요. 이후 진행 위치를 저장하는 배치로 남은 평문을 바꾸고, "암호문 형식이 아닌 값"과 복호화 실패가 0인지 확인한 뒤 암호문만 읽는 컨버터로 전환했어요. 되돌릴 때는 쓰기 암호화를 먼저 껐어요. 아래 수치는 MySQL 8.4 컨테이너와 작은 Java 앱에서 측정한 결과예요. 운영 사례는 당시의 선택을 설명하며, 현재 운영 상태를 확인한 결과는 아니에요.

• 쓰기 암호화가 "켜졌다"는 건 무엇으로 확인하나?
• 채우기 배치가 중간에 종료되면 어디서부터 재개하나?
• 검증 COUNT 는 왜 "평문 모양"이 아니라 "암호문 형식이 아닌 값"을 세야 하나?
• 되돌릴 때는 왜 쓰기 암호화를 먼저 끄나?

1. 읽기와 쓰기를 한 번에 바꾸면 응답 값이 달라져요

롤링 배포로 교체하는 동안에는 옛 버전과 새 버전이 같은 DB를 함께 써요. 이 구간에 두 버전이 어떤 형식을 읽고 쓰는지에 맞춰 전환 순서를 정해야 해요.

📖 용어: 롤링 배포 (rolling deploy)
새 버전 인스턴스가 요청을 받게 한 뒤 옛 버전을 하나씩 내리는 방식이에요. 교체가 끝날 때까지 두 버전이 동시에 요청을 받아요. 당시 운영 환경에서는 이 구간이 약 15분이었어요(2편).

읽기 전환과 쓰기 암호화를 한 버전에 담으면 새 버전이 저장한 암호문을 아직 교체되지 않은 옛 버전이 읽어요. 옛 버전에는 복호화 코드가 없어 그 문자열을 주민번호 값으로 그대로 응답해요. 예외가 나지 않으니 실패 요청에도 포함되지 않아요. 실습의 164건은 모두 이 경로였고, 옛 버전(v0)이 돌려준 응답이었어요.

이 전환에서는 읽기와 쓰기를 배포 단계로 나누고, 모든 인스턴스가 해당 버전으로 교체된 뒤 다음 단계로 진행했어요. 각 단계에서 확인할 조건은 아래와 같아요.

단계배포 내용확인할 문제다음으로 넘어가는 조건
0컬럼 넓히기길이에 따라 테이블 복사, 그동안 쓰기 대기암호문 최대 길이가 들어간다
1관대한 읽기, 쓰기는 평문암호문 접두어로 시작하는 평문모든 대가 1단계 버전
2쓰기 암호화 켜기스위치가 안 읽힌 대가 평문을 되돌려 씀모든 대가 2단계 버전, 기동 로그로 스위치 값 확인
3채우기 배치중간 종료, 앱이 수정한 행 덮어쓰기마지막 행까지 처리

그림 1. 읽기와 쓰기를 나눠 배포하고 모든 인스턴스의 교체를 확인한 뒤 진행해요

MySQL 8.4 컨테이너에 가짜 데이터 30만 행을 넣고, 앱 두 대를 호스트에서 실행했어요. 부하 생성기는 작업자 8개가 초당 약 320건을 목표로 요청을 보냈어요. 한 건 조회, 20행 목록 조회, 로그인(모든 컬럼을 다시 쓰는 UPDATE), 값 변경 뒤 다른 인스턴스에서 다시 읽기를 섞었어요. 응답마다 시작 시점 값과 비교해 "실패"(5xx·연결 오류)와 "값 틀림"(200인데 다른 값)을 따로 셌어요. 500번째 행마다 비정상 형식 6종을 100행씩, 997번째 행마다 NULL을 넣어 운영 데이터에 섞일 수 있는 형식을 포함했어요. 롤링 배포는 한 대씩 교체하고 두 버전이 함께 요청을 받는 구간을 8초로 뒀어요. 실습 앱은 JPA를 쓰지 않고 JDBC로 두 방향 변환(convertToDatabaseColumn, convertToEntityAttribute)을 구현했어요. 로그인 요청은 부분 갱신이 없는 엔티티처럼 모든 컬럼을 다시 써요. 코드와 원자료는 저장소의 labs/security/pii-08-online-migration/에 있어요.

2. 0~1단계: 컬럼을 넓히고, 읽기부터 관대하게

⚠️ 0단계 전에: 이 컬럼을 컨버터 밖에서 누가 읽고 쓰나
• 컨버터는 그 엔티티를 거치는 경로에만 적용돼요. 같은 컬럼을 다른 서비스, 네이티브 SQL, ETL·CDC·BI 추출, 뷰·트리거, DB 관리 도구가 직접 읽고 쓰면, 그쪽은 2단계부터 암호문을 받거나 평문을 써 넣어요. 각 경로를 찾아 어느 단계에서 함께 바꿀지 정해야 해요
• 그 컬럼을 WHERE 조건이나 UNIQUE 인덱스로 쓰는 곳이 있으면, 난수 IV 암호문으로 바뀌는 순간 같은 값을 찾지 못하고 유일성도 지켜지지 않아요. 이 경우에는 암호화 방식과 조회 방식을 함께 검토해야 해서 6편에서 따로 다뤄요

먼저 암호문이 들어갈 컬럼 길이를 확인해야 해요. 실습 형식(접두어 + base64(IV 12바이트 + 암호문 + 태그 16바이트))에서는 14자 평문이 64자가 되고, 전각 숫자 값은 100자가 돼요. 평문에 맞춰 만든 VARCHAR(20) 컬럼에는 들어가지 않아요.

컬럼 확장 중 쓰기가 대기하는지는 길이 조건에 따라 달라져요. MySQL 문서의 온라인 DDL 절은 VARCHAR를 늘릴 때 "길이를 담는 바이트 수가 같아야 한다"고 설명해요. 0~255바이트는 1바이트, 256바이트 이상은 2바이트여서 이 경계를 넘는 확장은 테이블 복사(ALGORITHM=COPY)가 필요해요. utf8mb4는 글자당 최대 4바이트로 계산하므로 VARCHAR(63)까지가 252바이트로 1바이트 구간에 해당해요.

-- VARCHAR(20) 에서 넓히기, 부하를 건 채로 (results/ddl.txt) ALTER ... MODIFY rrn VARCHAR(63) ..., ALGORITHM=INPLACE, LOCK=NONE -- 0.10초, 성공 ALTER ... MODIFY rrn VARCHAR(255) ..., ALGORITHM=INPLACE, LOCK=NONE ERROR 1846 (0A000): ALGORITHM=INPLACE is not supported. Reason: Cannot change column type INPLACE. Try ALGORITHM=COPY. ALTER ... MODIFY rrn VARCHAR(255) ..., ALGORITHM=COPY -- 0.37초 그동안 들어온 쓰기 29건 중 최대 224ms (앞뒤 구간은 최대 5~6ms)

실습에서는 64자 암호문을 저장할 크기로 넓히면 이 경계를 넘어 테이블을 복사해야 했어요. 좁은 30만 행 테이블에서는 0.37초에 끝났지만, 그동안 쓰기는 대기했어요. 이 측정값으로 큰 운영 테이블의 소요 시간을 추정할 수는 없어요. 새 길이를 바이트로 계산해 255 이하라면 ALGORITHM=INPLACE, LOCK=NONE으로 가능한지 확인하고, 256 이상으로 경계를 넘는다면 COPY를 실행할 점검 시간이나 온라인 스키마 변경 도구를 검토해야 해요. ALTER에 알고리즘을 명시하면 지원되지 않는 경우 다른 방식으로 실행되는 대신 오류로 멈춰요.

기존 컬럼을 넓히는 대신 암호문 전용 컬럼을 추가할 수도 있어요. 실습에서 측정한 것은 기존 컬럼을 바꾸는 방식이고, 아래 표의 새 컬럼 방식은 당시 MySQL 8.4 문서로 확인한 내용이에요.

스키마 변경기존 컬럼 넓히기. 255바이트 이하에서 256바이트 이상으로 늘리면 COPYADD COLUMN. MySQL 8.4 기본 알고리즘은 INSTANT (행 크기 한도, 테이블당 행 버전 64개, 압축 행 형식·FULLTEXT 인덱스 테이블 불가 같은 제약)
섞인 기간의 판정접두어로 판정. 접두어로 시작하는 평문은 복호화 실패 가능어느 컬럼에 값이 있는지로 판정

컬럼 길이를 확보한 뒤에는 읽기를 바꿔요. 1단계 배포에서는 쓰기를 평문으로 유지하고, 읽기만 두 형식을 처리하게 해요.

📖 용어: 관대한 컨버터 (lenient converter)
JPA AttributeConverter 의 읽기 쪽에서 값이 암호문 접두어로 시작하면 복호화하고, 아니면 아직 바뀌지 않은 평문으로 보고 그대로 돌려주는 컨버터예요. 평문과 암호문이 한 컬럼에 섞여 있는 기간에 두 형식을 모두 읽기 위한 코드예요. 반대로 접두어가 없으면 예외를 던지는 쪽을 엄격한 컨버터라고 부를게요.
@Converter public class LenientRrnConverter implements AttributeConverter<String, String> { private final boolean encryptOnWrite; // 1단계 false, 2단계 true public LenientRrnConverter() { // JPA 가 인자 없는 생성자로 만들 때 this(CryptoSwitch.encryptOnWrite()); // 기동 때 설정값을 담아 둔 정적 홀더 } public LenientRrnConverter(boolean encryptOnWrite) { this.encryptOnWrite = encryptOnWrite; } @Override public String convertToDatabaseColumn(String attr) { if (attr == null) return null; return encryptOnWrite ? Crypto.encrypt(attr) : attr; } @Override public String convertToEntityAttribute(String db) { if (db == null) return null; return db.startsWith(Crypto.PREFIX) ? Crypto.decrypt(db) : db; } }

쓰기 스위치를 컨버터에 전달하는 방법도 정해야 해요. 위 코드처럼 기동 시 설정을 정적 홀더에 저장하고 인자 없는 생성자가 읽거나, 컨테이너가 관리하는 빈으로 컨버터를 생성해 생성자로 주입할 수 있어요. Hibernate 문서는 Jakarta Persistence가 AttributeConverter를 관리 빈으로 해석하는 것을 지원하고, 외부 컨테이너는 BeanContainer로 연결한다고 설명해요. 어느 방식을 쓰든 3절에서 설명할 기동 로그로 실제 적용값을 확인해요.

실습에서 v0 → v1 롤링 동안 5,787건, v1 두 대만 남은 구간 1,567건은 모두 실패 0, 값 틀림 0이었어요. 아직 암호문이 없는 단계라, 이 결과만으로 혼재 상태의 읽기까지 검증한 것은 아니에요. 다음 단계에서 생길 암호문을 읽을 코드를 모든 인스턴스에 미리 배포한 상태예요.

⚠️ 주의: 접두어로 시작하는 평문
• 관대한 읽기는 접두어로 형식을 판정해요. 사람이 우연히 암호문 접두어로 시작하는 값을 넣으면, 그 값은 평문으로 저장되고 읽을 때는 암호문으로 보여 복호화가 실패해요
• 당시에는 이 조건을 두 컬럼에서 검토했어요. 계좌번호 컬럼에서는 1단계 기간에 그런 입력을 대소문자 구분 없이 거부했고(2편), 사람이 자유롭게 쓰는 문구가 섞인 컬럼에서는 리뷰에서 "관리자 코멘트가 접두어로 시작하면 이력 조회가 통째로 실패한다"는 지적을 받아 복호화 실패 시 저장값을 그대로 돌려주게 바꿨어요(5편)
• 당시에는 컬럼에 허용하는 값의 형식에 따라 방식을 달리했어요. 주민번호처럼 형식이 정해진 값에서는 접두어 입력을 거부하는 쪽을 검토할 수 있어요

3. 2단계: 쓰기 암호화를 켜고 프로세스의 적용값 확인하기

모든 인스턴스가 1단계 버전으로 교체되면 쓰기 암호화를 켠 2단계를 롤링 배포해요. 두 버전이 함께 요청을 받아도 1단계 버전이 암호문을 읽을 수 있어요. 실습의 v1 → v2 롤링에서는 5,813건 중 실패 0, 값 틀림 0이었어요.

이때는 설정 파일에 쓴 값이 실제로 적용됐는지도 확인해야 해요. 파일이 운영 프로필에서 읽히지 않으면 2단계 버전을 배포해도 평문을 계속 써요. 당시 운영 사례에서는 스위치를 넣은 파일에 dev 프로필 조건이 있어 운영 API에 적용되지 않았고, 배치 쪽에만 켜져 있었어요(1편).

이 상황을 재현하려고 2단계 두 대 중 한 대를 스위치가 꺼진 상태(v2-off)로 실행했어요. 채우기 배치를 돌린 뒤에는 10초마다 "암호문 형식이 아닌 값"을 셌어요.

채우기 직후 not_cipher = 499 +10초 not_cipher = 965 +20초 not_cipher = 1,407 +30초 not_cipher = 1,810 채우기 뒤 30초 재측정 구간 요청 9,664건: 실패 0, 값 틀림 0 시나리오 전체 요청 27,763건: 실패 0, 값 틀림 0 (results/config-miss.txt)

채우기가 끝난 뒤에도 평문이 계속 늘었어요. 스위치가 꺼진 인스턴스가 로그인을 처리하면서 행 전체를 다시 써, 암호문으로 바뀐 값도 평문으로 덮었기 때문이에요. 읽기는 두 형식을 처리하므로 요청 실패나 값 틀림은 없었어요. 이 실습에서는 요청 지표에 나타나지 않은 문제를 테이블의 평문 개수로 확인했어요.

📖 용어: 부분 갱신 (@DynamicUpdate)
Hibernate User Guide 는 "기본적으로 엔티티를 수정하면 식별자를 뺀 모든 컬럼이 UPDATE 에 실린다(By default, when you modify an entity, all columns but the identifier are being set during update)"고 적고, 이 애너테이션은 "실제로 바뀐 컬럼만 담는다"고 설명해요. 이 설정이 없는 엔티티는 로그인 시각만 바꿔도 다른 컬럼까지 함께 다시 쓰는 UPDATE를 보내요. 당시 운영 사례에서 평문으로 되돌아간 61행이 이 경로였어요(1편).

따라서 2단계 배포 완료를 확인할 때는 버전뿐 아니라 각 프로세스가 기동할 때 남긴 실제 스위치 값도 봐야 해요. 실습 앱은 시작할 때 아래 한 줄을 남겨요.

INFO started label=v2 port=38082 read=lenient encryptOnWrite=true WARN started label=v2-off port=38086 read=lenient encryptOnWrite=false

이 로그는 프로세스가 실제로 사용하는 값을 보여 줘요. 운영 프로필에서 false가 나오면 오류로 다루고, 모든 인스턴스의 값을 확인한 뒤 채우기를 시작하는 절차가 필요해요. 당시 운영 사례에서도 장애 뒤에 기동 로그와 "모든 태스크가 교체된 뒤에 채우기를 돌린다"는 조건을 절차에 추가했어요(1편).

쓰기 암호화에 실패하면 저장을 거부할지도 이 단계에서 정해야 해요. 키를 읽지 못하는 상태가 계속되면 쓰기 기능 전체가 영향을 받을 수 있어요. 당시에는 평문 저장을 허용하고 실패를 ERROR 로그와 호출 등급 모니터로 집계하며, 남은 평문을 채우기 배치로 다시 처리하는 방식을 선택했어요(2편). 평문이 남는 것을 허용하는 선택이므로 관대한 읽기와 후속 채우기를 함께 고려했던 것이며, 현재 운영 상태나 일반적인 안전성을 뜻하지는 않아요.

4. 3단계: 진행 위치를 저장하는 채우기 배치

2단계부터 새 값은 암호문으로 쓰지만, 기존 평문은 남아 있어요. 이를 바꾸는 일회성 작업이 채우기 배치예요. 운영 중에 실행하므로 중간 종료 뒤 재개할 수 있어야 하고, 배치가 읽은 뒤 앱이 수정한 값을 덮어쓰지 않아야 해요.

📖 용어: 진행 위치 (커서)
마지막으로 처리한 id예요. 중간에 종료됐다가 다시 실행하면 이 id보다 큰 행부터 읽어요. 페이지 번호를 저장하는 방식과 달리, 앞쪽 행이 추가되거나 삭제돼도 저장한 id를 재개 기준으로 쓸 수 있어요.
loop: rows = SELECT id, rrn FROM t WHERE id > :cursor ORDER BY id LIMIT 1000 if rows 가 비었으면: DELETE FROM batch_state WHERE job='fill'; COMMIT; 끝 for (id, v) in rows: if v is null or v 가 암호문 형식: 건너뛴다 c = encrypt(v); decrypt(c) == v 인지 확인 UPDATE t SET rrn = :c WHERE id = :id AND rrn = :v -- 읽은 값 그대로일 때만 UPSERT batch_state(job='fill', cursor_id = 마지막 id) -- 같은 트랜잭션 COMMIT; 잠깐 쉰다(20ms)

페이지 쓰기와 진행 위치 저장을 같은 트랜잭션으로 처리해, 커밋된 페이지 다음부터 재개하게 했어요. 그사이 앱이 값을 바꾸면 조건부 UPDATE는 0행으로 끝나요. 이 행은 앱이 이미 암호문으로 저장했을 수 있고, 평문이 남았다면 다음 검증에서 확인해야 해요.

실습에서는 부하를 주면서 배치를 실행하고 4초 뒤 kill -9로 종료했어요. 저장된 커서는 82000이었고, 다시 실행하자 start cursor=82000부터 이어서 21만 8천 행을 10.6초에 처리했어요. 채우기 구간의 요청 4,804건은 실패 0, 값 틀림 0이었고, 재개한 실행에서 조건부 UPDATE가 0행으로 끝난 충돌은 1건이었어요. 완료하면 배치 상태 행을 삭제해요. 이 코드에서 완료 뒤 다시 실행하면 처음부터 읽으며 이미 암호문인 값은 건너뛰어요.

💡 실무에서는
• 한 번에 읽을 페이지 수를 제한한다면 다음 실행의 재개 위치가 필요해요. 매번 처음부터 읽으면 같은 구간만 반복할 수 있어요. 당시 486만 행 이력 테이블에서도 실행마다 상한을 두었기 때문에 커서를 배치 스위치 행에 함께 저장했어요(4편)
• 조건부 UPDATE에서 "같은 값"인지는 DB 콜레이션에 따라 달라져요. PAD SPACE 콜레이션은 뒤 공백만 다른 두 값을 같다고 봐요. 실습 컬럼에는 NO PAD인 utf8mb4_0900_bin을 사용했어요
• 당시 채우기에서는 SQL로 직접 갱신했어요. 엔티티로 저장할 때 수정 시각이 배치 시각으로 바뀌거나 소프트 삭제 조건 때문에 삭제된 행을 건너뛰는 문제를 피하려는 선택이었어요(4편)

5. 4단계: "암호문 형식이 아닌 값" 세기

채우기가 끝나면 엄격한 컨버터로 바꿔도 되는지 검증해요. "평문 모양이 남았나"를 세는 쿼리와 "암호문 형식이 아닌 값이 남았나"를 세는 쿼리를 비교했어요.

-- 평문 모양을 센다 (틀린 쪽) SELECT COUNT(*) FROM t WHERE rrn REGEXP '^[0-9]{6}-?[0-9]{7}$'; -- 암호문 형식이 아닌 값을 센다 (맞는 쪽) SELECT COUNT(*) FROM t WHERE rrn IS NOT NULL AND rrn NOT LIKE 'LABENC1:%';

위 쿼리는 예상한 형식의 평문만 세고, 아래 쿼리는 NULL이 아닌 값 중 암호문 접두어가 없는 값을 세요. 아래 조건도 복호화 성공까지 보장하지는 않아요. 비정상 형식의 값을 하나씩 넣고 각 조건이 무엇을 세는지 확인했어요.

값평문 모양 [0-9]평문 모양 \d암호문 아님 IS NOT NULL<> '' NO PAD<> '' PAD SPACE
정상, 하이픈 없음 (각각)11111
뒤에 문자 붙음00111
자릿수 틀림00111
전각 숫자01111
빈 문자열 ''00100
공백 한 칸 ' '00110
뒤 공백00111
합계 (평문 8개 중)23876

NULL과 암호문 행은 다섯 조건 모두 세지 않았어요(results/count-demo.txt). 평문 모양 쿼리는 평문 8개 중 2개만 셌어요. 정규식을 \d로 쓰면 실습의 MySQL 8.4 정규식이 전각 숫자도 받아들여 3개가 됐지만, 다른 형식은 빠졌어요. <> ''로 빈 값을 제외하면 빈 문자열이 빠지고, PAD SPACE 콜레이션에서는 공백 한 칸도 빈 문자열과 같다고 보고 제외돼요. MySQL 문서에서도 PAD SPACE 콜레이션은 비교할 때 뒤 공백을 무시하며, utf8mb4_bin은 PAD SPACE, utf8mb4_0900_bin은 NO PAD라고 설명해요. 실습의 엄격한 컨버터는 빈 문자열과 공백도 "암호문 아님"으로 보고 실패하므로, 검증 대상에 포함하려면 IS NOT NULL 조건을 써야 해요.

30만 행 테이블에서도 같은 차이를 확인했어요. 채우기 대상을 "평문 모양인 값"으로 제한하고 다른 형식은 건너뛰는 시나리오를 실행한 뒤, 두 COUNT를 비교했어요.

실행 화면. 평문 모양 COUNT는 0이지만 암호문 아님 COUNT는 597이었고, 엄격한 컨버터 배포 뒤 42건이 실패했어요

평문 모양 COUNT는 0, 암호문 형식이 아닌 값은 597, <> ''로 세면 498이었어요. 평문 모양 COUNT 0만 보고 엄격한 컨버터를 롤링하자 배포 구간과 그 뒤 8초 동안 요청 42건이 500으로 실패했어요. 그중 31건이 목록 조회였어요. 한 번에 20행을 읽는 목록에서는 한 행의 변환 실패가 페이지 전체의 요청 실패로 이어졌어요. 당시 운영 사례에서도 암호문만 읽는 컨버터를 배포한 뒤 목록 화면에 "복호화 실패: 암호문 형식이 아님" 오류가 났어요(1편). 운영 사례에서는 설정 문제로 평문이 다시 생긴 것이 원인이었고, 배포 직전 검증을 생략해 이를 확인하지 못했어요.

그림 2. 채우기와 검증 조건이 다르면 COUNT가 0이어도 미처리 값이 남을 수 있어요

접두어 비교만으로는 복호화가 가능한지도 알 수 없어요. 모든 행을 암호화한 실습 테이블에 'LABENC1:hello' 한 행을 넣자 암호문 아님 COUNT는 0이었지만, 복호화 검증 배치는 decryptFailed=1과 해당 id를 남겼어요(results/fake-prefix.txt). 더 엄격한 형식 검사로 이 예시를 걸러낼 수는 있어도, 최종 확인에는 실제 복호화 검증이 필요해요.

대소문자 비교도 SQL과 코드의 조건을 맞춰야 해요. MySQL 문서는 "SQL 패턴은 기본적으로 대소문자를 구분하지 않는다"고 설명해요. 컬럼이 _ci 콜레이션이면 NOT LIKE 'LABENC1:%'는 소문자 labenc1:로 시작하는 값을 암호문으로 보고 세지 않아요. 반면 Java의 startsWith는 대소문자를 구분해 엄격한 컨버터가 해당 행에서 실패해요. 실습 컬럼은 utf8mb4_0900_bin이라 이 차이를 재현한 것은 아니에요. _ci 콜레이션에서는 rrn COLLATE utf8mb4_0900_bin LIKE 'LABENC1:%'처럼 대소문자를 구분해 세고, 복호화 검증도 함께 해야 해요.

💡 검증 조건과 실행 시점
• 채우기와 검증의 조건을 "NULL 이 아니고 암호문 형식이 아니다"로 맞춰요. 형식이 다른 값도 그대로 암호화하고, 데이터 정리는 별도로 정해요
• SQL로 IS NOT NULL AND NOT LIKE '접두어%'를 세고, 쓰기 없이 전 행을 복호화하는 검증 모드로 실패 수와 id를 남겨요. 값 자체는 남기지 않아요
• 이 숫자는 측정한 시점의 상태예요. 엄격한 컨버터 배포 직전에 다시 세고, 0이 아니면 전환을 멈춰요. 당시 운영 사례에서는 문서에 적어 둔 이 검증을 건너뛰었어요(1편)
• COUNT는 주 DB에서 세야 해요. 읽기 복제본은 복제 지연 때문에 주 DB와 다른 값을 셀 수 있어요. 복제본을 읽는 앱이 있다면 엄격한 컨버터로 전환하기 전에 채우기 결과가 복제본에 반영됐는지도 확인해야 해요

6. 5단계: 엄격한 컨버터 배포와 되돌림 순서

암호문 형식이 아닌 값과 복호화 실패가 모두 0이면 엄격한 컨버터를 롤링 배포해요. 아래는 이 순서로 실행한 로컬 실습 결과예요.

실행 화면. 세 번의 롤링 배포와 채우기 중단·재개를 거친 요청 29,401건에서 실패 0, 값 틀림 0을 확인했어요

v0에서 v3까지 전환하는 동안 요청 29,401건 중 실패 0, 값 틀림 0이었어요. 엄격한 컨버터로 바꾼 뒤 다시 센 암호문 아님 COUNT도 0이었어요. 이 결과는 앞서 설명한 두 인스턴스와 부하 조건에서 확인한 범위예요.

엄격한 컨버터로 전환할 때는 관대한 컨버터와 채우기 배치를 제거하는 절차도 정해야 해요. 평문을 그대로 읽는 코드가 남아 있으면 평문이 다시 들어와도 조회 오류로 드러나지 않을 수 있어요. "암호문을 평문으로 되돌리는" 복원 모드도 정리 대상이에요. 엄격한 컨버터가 배포된 상태에서 복원하면 해당 행을 읽지 못하기 때문이에요. 당시 운영 사례의 독립 리뷰에서도 이 조합을 지적했어요(2편).

컨버터를 거치지 않는 쓰기는 별도로 확인해야 해요. 데이터 이관 import나 직접 실행하는 SQL은 전환 뒤에도 평문을 넣을 수 있어요. DB에서 형식을 제한하려면 CHECK (rrn IS NULL OR rrn COLLATE utf8mb4_0900_bin LIKE 'LABENC1:%') 같은 제약을 검토할 수 있어요. MySQL 문서에 따르면 CHECK 제약은 8.0.16부터 실제로 적용되고, INSERT, UPDATE, REPLACE, LOAD DATA에서 평가되며, NULL처럼 결과가 UNKNOWN이면 통과해요. 다만 이 식은 실습에서 실행하지 않았고, 큰 테이블에 추가할 때 기존 행을 검사하는 비용도 확인하지 못했어요. 적용하려면 같은 크기의 사본에서 먼저 확인해야 해요.

⚠️ 주의: 테이블 밖에 남는 것
• 캐시: 해당 값을 캐시한다면 저장 형식을 확인하고, 엄격 전환과 되돌림 시 비울 대상을 정해야 해요. 옛 형식이 남으면 변경한 코드가 그 값을 읽을 수 있어요
• 백업, binlog, 추출본: 테이블을 암호문으로 바꿔도 전환 이전의 백업과 binlog, 추출본에 있던 평문까지 바뀌지는 않아요. 보존 기간과 파기는 전환과 별도로 정해야 해요

엄격한 컨버터를 배포하기 전인 2단계 상태에서 되돌려야 할 수도 있어요. 쓰기가 계속되는 테이블에서 "복원 배치를 돌리고 옛 버전으로"라는 순서를 따르면, 복원 중에도 새 암호문이 생겨요. 당시에도 쓰기가 멈춘 레거시 테이블의 절차를 계속 데이터가 쌓이는 테이블에 적용하려다가 리뷰에서 순서를 정정했어요(5편).

틀린 순서: 쓰기 켠 채 복원 → v0 (results/rollback-wrong.txt) 복원 직후 남은 암호문 663 행 v0 롤링 끝난 뒤 암호문 1,130 행 요청 28,897건: 실패 0, 값 틀림 223 바른 순서: 쓰기 끈 판(v2-off) 롤링 → 복원 → 암호문 0 확인 → v0 (results/rollback-right.txt) 복원 직후 남은 암호문 0 행 v0 롤링 끝난 뒤 암호문 0 행 요청 34,935건: 실패 0, 값 틀림 0

쓰기 암호화를 켠 채 복원한 실습에서는 복원 완료 시 암호문이 663행 남았어요. v0 롤링 중에도 남아 있던 v2 인스턴스가 암호문을 써서 1,130행으로 늘었고, 옛 버전은 이를 암호문 그대로 응답했어요. 반대로 쓰기 스위치를 끈 버전을 먼저 모든 인스턴스에 배포한 뒤 복원했을 때는 복원 직후와 v0 전환 뒤 모두 암호문이 0이었어요. 쓰기를 끈 버전도 두 형식을 읽으므로 읽기 변환은 유지되고 새 값은 평문으로 저장돼요. 이 상태에서 복원하고 0을 확인한 뒤 옛 버전으로 바꿨어요. 복원 배치는 새 버전에 들어 있으므로 버전을 먼저 내리면 사용할 수 없어요.

그림 3. 쓰기 암호화를 끈 버전으로 교체한 뒤 복원하고 옛 버전으로 되돌려요
💡 배포 전 확인할 항목
• 컨버터 밖에서 같은 컬럼을 읽고 쓰는 경로(다른 서비스, 네이티브 SQL, ETL·CDC·BI, 뷰·트리거, 관리 도구)와 WHERE·UNIQUE 사용처를 확인해요
• 암호문 최대 길이를 바이트로 계산해요. 255 이하에서는 ALGORITHM=INPLACE, LOCK=NONE이 가능한지 확인하고, 256 이상으로 경계를 넘으면 COPY 점검 시간이나 온라인 스키마 변경 도구, 새 컬럼 추가를 검토해요
• 1단계(두 형식 읽기, 평문 쓰기)가 모든 인스턴스에 배포된 뒤 2단계를 시작해요
• 2단계 뒤 모든 프로세스의 기동 로그에서 쓰기 스위치의 실제 값을 확인해요
• 채우기의 페이지 쓰기와 커서 저장을 같은 트랜잭션에 넣고, UPDATE에는 읽은 값과 같다는 조건을 사용해요
• 채우기와 검증 대상을 같은 조건으로 맞춰요: IS NOT NULL AND NOT 암호문 형식
• 엄격한 컨버터 배포 직전에 주 DB에서 SQL COUNT(대소문자 구분 비교)와 복호화 검증을 다시 실행해 둘 다 0인지 확인해요. 복제본을 읽는 앱이 있다면 채우기 결과의 복제도 확인해요
• 엄격 전환과 되돌림 때 비울 캐시를 정해요
• 엄격한 컨버터 배포 시 관대한 컨버터, 채우기, 복원 모드의 제거 절차를 정해요
• 되돌릴 때는 쓰기 암호화를 끈 버전을 먼저 배포해요
• 앱 밖의 import·수작업 SQL 경로를 제한할 방법을 정하고, 백업·binlog·추출본에 남은 평문은 따로 다뤄요
✍️ 전환 순서와 확인 범위
컬럼 길이를 확보한 뒤 두 형식을 읽는 버전, 쓰기 암호화를 켠 버전 순으로 배포하고, 채우기와 검증을 거쳐 엄격한 읽기로 전환했어요. 로컬 실습에서는 이 순서로 요청 29,401건 중 실패 0, 값 틀림 0을 확인했어요. 읽기 단계를 건너뛴 실행에서는 오류 없이 암호문 164건이 응답에 포함됐어요.

쓰기 스위치가 꺼진 인스턴스를 남기면 채우기 뒤 30초 동안 평문이 499행에서 1,810행으로 늘었고, 평문 모양 COUNT가 0이어도 암호문 형식이 아닌 597행이 남았어요. 따라서 각 프로세스의 설정과 배포 직전의 데이터 상태를 함께 확인해야 해요. 되돌림도 쓰기 암호화를 먼저 끈 뒤 복원해야 하며, 쓰기를 켠 채 복원한 실습에서는 완료 직후 암호문 663행이 남았어요.

여기서 확인한 완료 조건은 해당 실습 시점의 암호문 형식 검사와 복호화 검증이 모두 0이었다는 것이에요. 컬럼 확장 시 쓰기 대기와 백업·추출본에 남는 평문은 별도로 다뤄야 해요.
