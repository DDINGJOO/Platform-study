9편. 마스킹과 암호화는 무엇을 되돌릴 수 있느냐로 고른다

주민번호 형식의 평문이 30만 행 쌓인 테이블이 있고, 그 테이블을 읽고 쓰는 앱 두 대가 쉬지 않고 요청을 받고 있어요. 암호화 컨버터를 하나 만들어 붙이고 평소처럼 롤링 배포를 내보내면 끝날 것 같습니다. 실습에서 그렇게 해 봤더니, 배포가 진행된 약 20초 동안 5,773건 중 164건이 200 응답에 암호문을 담아 돌려줬어요. 오류는 한 건도 없었습니다. 그래서 모니터링에도 아무것도 뜨지 않아요.

이 글은 그 질문에 답합니다. 이미 평문이 쌓인 운영 테이블을 서비스 중단 없이 암호화로 바꾸려면 어떤 순서로 배포하나. 답부터 적으면, 컬럼을 넓히고, 평문과 암호문을 둘 다 읽는 컨버터를 먼저 깔고, 그다음에 쓰기 암호화를 켜고, 진행 위치를 저장하는 배치로 남은 평문을 채우고, "암호문 형식이 아닌 값"이 0인지 센 뒤에야 암호문만 읽는 컨버터로 넘어갑니다. 되돌릴 때는 쓰기 암호화부터 끕니다. 각 단계에서 무엇이 깨질 수 있는지는 MySQL 8.4 컨테이너와 작은 Java 앱으로 부하를 흘리면서 직접 쟀어요.

• 쓰기 암호화가 "켜졌다"는 건 무엇으로 확인하나?
• 채우기 배치가 중간에 죽으면 어디서부터 다시 하나?
• 검증 COUNT 는 왜 "평문 모양"이 아니라 "암호문 형식이 아닌 값"을 세야 하나?
• 되돌릴 때는 왜 거꾸로가 아니라 쓰기부터 끊나?

1. 한 번에 바꾸면 무엇이 깨지나

무중단 배포에서는 옛 버전과 새 버전이 같은 DB를 함께 쓰는 시간이 반드시 생깁니다. 이 사실 하나가 순서 전체를 정해요.

📖 용어: 롤링 배포 (rolling deploy)
새 버전 인스턴스를 하나 띄워 트래픽을 받게 한 다음 옛 버전을 하나 내리는 일을 대수만큼 되풀이하는 방식이에요. 서비스는 끊기지 않지만, 교체가 끝날 때까지 두 버전이 동시에 요청을 받습니다. 제 회사 환경에서는 이 구간이 약 15분이었어요(2편).

읽기 전환과 쓰기 암호화를 한 버전에 담아 내보낸다고 해 볼게요. 새 버전이 저장한 암호문을 아직 안 내려간 옛 버전이 읽습니다. 옛 버전에는 복호화 코드가 없으니 그 문자열을 그대로 주민번호로 알고 화면에 내보내요. 예외가 나지 않으니 실패로 세어지지도 않습니다. 위에서 말한 164건이 정확히 이 경로였고, 전부 옛 버전(v0)이 돌려준 응답이었어요.

그래서 한 배포에는 한 가지 변화만 담고, 모든 인스턴스가 그 버전이 된 뒤에 다음 변화를 내보냅니다. 단계와 각 단계에서 깨질 수 있는 것을 표로 먼저 보여 드릴게요.

단계배포 내용깨질 수 있는 것다음으로 넘어가는 조건
0컬럼 넓히기길이에 따라 테이블 복사, 그동안 쓰기 대기암호문 최대 길이가 들어간다
1관대한 읽기, 쓰기는 평문암호문 접두어로 시작하는 평문모든 대가 1단계 버전
2쓰기 암호화 켜기스위치가 안 읽힌 대가 평문을 되돌려 씀모든 대가 2단계 버전, 기동 로그로 스위치 값 확인
3채우기 배치중간에 죽음, 앱이 고친 행 덮어쓰기커서가 끝에 닿음
4검증 (쓰지 않음)잘못 센 0암호문 형식 아닌 값 0, 복호화 실패 0
5엄격한 읽기, 채우기 배치 삭제남은 평문 한 행이 목록 페이지 전체를 깨뜨림(끝)
그림 1. 단계마다 바꾸는 것은 하나이고, 넘어가는 조건은 "모든 대가 그 버전"이다

실습 환경은 이렇게 꾸렸어요. MySQL 8.4 컨테이너에 30만 행을 넣고, 앱은 호스트에서 두 대로 띄웠습니다. 부하 생성기는 작업자 8개가 초당 약 320건을 목표로 보내요. 한 건 조회, 20행 목록 조회, 로그인(모든 컬럼을 다시 쓰는 UPDATE), 값 변경 뒤 다른 대에서 다시 읽기를 섞었고, 응답마다 시작 시점 값과 비교해 "실패"(5xx·연결 오류)와 "값 틀림"(200인데 다른 값)을 따로 셉니다. 데이터에는 500번째 행마다 이상한 값 6종을 100행씩, 997번째 행마다 NULL을 넣었어요. 운영 테이블에 실제로 섞여 있는 종류들입니다. 롤링은 두 대를 한 대씩 갈고, 두 버전이 함께 받는 구간을 8초로 뒀어요. 실습 앱은 JPA 를 쓰지 않고 JDBC 로 같은 두 방향 변환(convertToDatabaseColumn, convertToEntityAttribute)을 흉내 냈어요. 로그인 요청은 부분 갱신이 없는 엔티티처럼 모든 컬럼을 다시 씁니다. 코드와 원자료는 저장소의 labs/security/pii-08-online-migration/ 에 있습니다.

2. 0~1단계: 컬럼을 넓히고, 읽기부터 관대하게

⚠️ 0단계 전에: 이 컬럼을 컨버터 밖에서 누가 읽고 쓰나
• 컨버터는 그 엔티티를 거치는 경로만 바꿉니다. 같은 컬럼을 다른 서비스, 네이티브 SQL, ETL·CDC·BI 추출, 뷰·트리거, DB 관리 도구가 직접 읽고 쓰면, 그쪽은 2단계부터 암호문을 받거나 평문을 써 넣어요. 하나씩 찾아 순서표의 어느 단계에서 같이 바꿀지 정합니다
• 그 컬럼을 WHERE 조건이나 UNIQUE 인덱스로 쓰는 곳이 있으면, 난수 IV 암호문으로 바뀌는 순간 같은 값을 찾지 못하고 유일성도 지켜지지 않아요. 이건 순서 문제가 아니라 방식 문제라 6편에서 따로 다룹니다

코드보다 먼저 확인할 것이 컬럼 길이예요. 암호문은 평문보다 깁니다. 실습 형식(접두어 + base64(IV 12바이트 + 암호문 + 태그 16바이트))이면 14자 평문이 64자가 되고, 전각 숫자 값은 100자가 돼요. 평문에 맞춰 VARCHAR(20) 으로 만든 컬럼에는 안 들어갑니다.

넓히는 ALTER 가 무중단인지는 길이에 달려 있어요. MySQL 문서의 온라인 DDL 절은 VARCHAR 를 늘릴 때 "길이를 담는 바이트 수가 같아야 한다"고 적고 있습니다. 0~255바이트는 1바이트, 256바이트 이상은 2바이트라서, 그 경계를 넘는 확장은 테이블 복사(ALGORITHM=COPY)로만 된다고요. utf8mb4 는 글자당 최대 4바이트로 잡으니 VARCHAR(63) 까지가 252바이트로 1바이트 구간입니다.

-- VARCHAR(20) 에서 넓히기, 부하를 건 채로 (results/ddl.txt) ALTER ... MODIFY rrn VARCHAR(63) ..., ALGORITHM=INPLACE, LOCK=NONE -- 0.10초, 성공 ALTER ... MODIFY rrn VARCHAR(255) ..., ALGORITHM=INPLACE, LOCK=NONE ERROR 1846 (0A000): ALGORITHM=INPLACE is not supported. Reason: Cannot change column type INPLACE. Try ALGORITHM=COPY. ALTER ... MODIFY rrn VARCHAR(255) ..., ALGORITHM=COPY -- 0.37초 그동안 들어온 쓰기 29건 중 최대 224ms (앞뒤 구간은 최대 5~6ms)

→ 64자 암호문이 들어갈 크기로 넓히려는 순간 1바이트 구간을 벗어나 복사가 됩니다. 실습 테이블은 좁은 30만 행이라 0.37초로 끝났지만, 복사가 도는 동안 쓰기는 기다렸어요. 이 시간은 테이블 크기를 따라가니, 큰 테이블이면 이 단계만 따로 점검 시간을 잡거나 온라인 스키마 변경 도구를 씁니다. 판단 기준은 이렇습니다. 새 길이를 바이트로 계산해 255 이하로 남으면 ALGORITHM=INPLACE, LOCK=NONE, 256 이상이 되면 COPY 를 점검 시간에 돌리거나 온라인 스키마 변경 도구로 넓힙니다. 어느 경우든 ALTER 에 알고리즘을 적어 두면, 기대와 다를 때 조용히 복사로 떨어지지 않고 위처럼 오류로 멈춰요.

제자리에서 넓히는 대신 암호문 전용 컬럼을 새로 붙이는 방법도 있어요. 둘은 대가가 다릅니다. 이 글의 실습은 제자리 변환만 쟀고, 아래 표의 새 컬럼 쪽은 MySQL 8.4 문서로 확인한 범위예요.

제자리 변환 (이 글의 순서)새 암호문 컬럼 추가
스키마 변경기존 컬럼 넓히기. 새 길이가 256바이트를 넘으면 COPYADD COLUMN. MySQL 8.4 기본 알고리즘은 INSTANT (행 크기 한도, 테이블당 행 버전 64개, 압축 행 형식·FULLTEXT 인덱스 테이블 불가 같은 제약)
섞인 기간의 판정값의 생김새(접두어)로 가린다. 접두어로 시작하는 평문이 위험어느 컬럼에 값이 있느냐로 가린다. 생김새 판정이 필요 없다
앱 코드컨버터 하나 + 쓰기 스위치두 컬럼 동시 쓰기, 읽기 전환, 옛 컬럼 정리까지 단계가 더 많다

검증 COUNTIS NOT NULL 이고 암호문 형식이 아닌 값옛 컬럼은 값이 있는데 새 컬럼은 NULL 인 행

그다음이 읽기 쪽입니다. 1단계 배포는 쓰기를 평문 그대로 두고, 읽기만 두 형식을 받게 바꿔요.

📖 용어: 관대한 컨버터 (lenient converter)
JPA AttributeConverter 의 읽기 쪽에서 값이 암호문 접두어로 시작하면 복호화하고, 아니면 아직 바뀌지 않은 평문으로 보고 그대로 돌려주는 컨버터예요. 평문과 암호문이 한 컬럼에 섞여 있는 기간을 버티는 장치입니다. 반대로 접두어가 없으면 예외를 던지는 쪽을 이 글에서는 엄격한 컨버터라고 부를게요.
@Converter public class LenientRrnConverter implements AttributeConverter<String, String> { private final boolean encryptOnWrite; // 1단계 false, 2단계 true public LenientRrnConverter() { // JPA 가 인자 없는 생성자로 만들 때 this(CryptoSwitch.encryptOnWrite()); // 기동 때 설정값을 담아 둔 정적 홀더 } public LenientRrnConverter(boolean encryptOnWrite) { this.encryptOnWrite = encryptOnWrite; } @Override public String convertToDatabaseColumn(String attr) { if (attr == null) return null; return encryptOnWrite ? Crypto.encrypt(attr) : attr; } @Override public String convertToEntityAttribute(String db) { if (db == null) return null; return db.startsWith(Crypto.PREFIX) ? Crypto.decrypt(db) : db; } }

→ 스위치를 컨버터에 넣는 길은 둘이에요. 위처럼 기동 때 설정을 읽어 정적 홀더에 담아 두고 인자 없는 생성자가 꺼내 쓰거나, 컨버터를 컨테이너가 만드는 빈으로 받아 생성자로 주입받습니다. Hibernate 문서는 Jakarta Persistence 가 AttributeConverter 를 관리 빈으로 해석하는 것을 지원하고, 외부 컨테이너는 BeanContainer 로 연결한다고 적고 있어요. 어느 쪽이든 3장의 기동 로그로 실제 값을 찍습니다.

실습에서 v0 → v1 롤링 동안 5,787건, v1 두 대만 남은 구간 1,567건이 실패 0, 값 틀림 0이었어요. 이 단계에서는 아직 암호문이 하나도 없으니 당연한 결과입니다. 이 단계가 하는 일은 다음 단계에서 섞일 암호문을 읽을 수 있는 코드를 미리 모든 대에 깔아 두는 것이에요.

⚠️ 주의: 접두어로 시작하는 평문
• 관대한 읽기는 값의 생김새만 봅니다. 사람이 우연히 암호문 접두어로 시작하는 값을 넣으면, 그 값은 평문으로 저장되고 읽을 때는 암호문으로 보여 복호화가 실패해요
• 제 회사에서는 두 번 걸렸습니다. 계좌번호 컬럼에서는 1단계 기간에 그런 입력을 대소문자 구분 없이 거부했고(2편), 사람이 자유롭게 쓰는 문구가 섞인 컬럼에서는 리뷰가 "관리자 코멘트가 접두어로 시작하면 이력 조회가 통째로 실패한다"고 짚어서 복호화 실패 시 저장값을 그대로 돌려주게 바꿨어요(5편)
• 어느 쪽을 고를지는 그 컬럼에 사람이 쓴 값이 들어오느냐로 정합니다. 주민번호처럼 형식이 정해진 값이면 입력 거부가 단순해요

3. 2단계: 쓰기 암호화를 켜고, 켜졌는지를 프로세스에게 묻는다

모든 대가 1단계 버전이 된 뒤에 쓰기 스위치를 켠 2단계를 롤링합니다. 이 구간에는 1단계 대와 2단계 대가 섞이지만, 1단계 대도 암호문을 읽을 수 있으니 값 틀림이 생기지 않아요. 실습의 v1 → v2 롤링은 5,813건, 실패 0, 값 틀림 0이었습니다.

이 단계에서 가장 흔하게 깨지는 것은 코드가 아니라 설정이에요. 스위치를 설정 파일에 적었는데 그 파일이 운영 프로필에서 읽히지 않으면, 그 대는 2단계 버전 이름을 달고 1단계처럼 평문을 씁니다. 제 회사에서 실제로 이렇게 됐어요. 스위치를 넣은 파일 맨 위가 dev 프로필 조건이라 운영 API 에서는 한 줄도 적용되지 않았고, 배치 쪽은 켜져 있었습니다(1편).

그 상태가 왜 위험한지는 실습으로 보는 게 빠릅니다. 2단계 두 대 중 한 대를 스위치가 꺼진 채로 띄우고(v2-off) 채우기 배치를 돌린 뒤, 10초마다 "암호문 형식이 아닌 값"을 셌어요.

채우기 직후 not_cipher = 499 +10초 not_cipher = 965 +20초 not_cipher = 1,407 +30초 not_cipher = 1,810 채우기 뒤 30초 재측정 구간 요청 9,664건: 실패 0, 값 틀림 0 시나리오 전체 요청 27,763건: 실패 0, 값 틀림 0 (results/config-miss.txt)

→ 채우기는 끝났는데 평문이 계속 늘어요. 스위치가 꺼진 대가 로그인을 처리할 때마다 그 행 전체를 다시 쓰면서, 방금 암호문이 된 값을 평문으로 덮기 때문입니다. 읽기는 관대하니 사용자 화면은 멀쩡하고, 요청은 하나도 실패하지 않았어요. 이 결함은 요청 지표로는 보이지 않고, 테이블을 다시 세야만 보입니다.

📖 용어: 부분 갱신 (@DynamicUpdate)
Hibernate User Guide 는 "기본적으로 엔티티를 수정하면 식별자를 뺀 모든 컬럼이 UPDATE 에 실린다(By default, when you modify an entity, all columns but the identifier are being set during update)"고 적고, 이 애너테이션은 "실제로 바뀐 컬럼만 담는다"고 설명해요. 이 설정이 없는 엔티티는 로그인 시각 한 칸만 바꿔도 다른 컬럼까지 함께 다시 쓰는 UPDATE 를 보냅니다. 제 회사에서 평문으로 되돌아간 61행이 이 경로였어요(1편).

그래서 2단계를 "다 깔렸다"로 판정하는 근거는 배포 성공이 아니라 각 프로세스가 기동할 때 남긴 실제 스위치 값이어야 해요. 실습 앱은 뜰 때 이렇게 한 줄을 찍습니다.

INFO started label=v2 port=38082 read=lenient encryptOnWrite=true WARN started label=v2-off port=38086 read=lenient encryptOnWrite=false

→ 설정 파일에 무엇이 적혀 있는지가 아니라, 그 프로세스가 지금 쓰는 값이에요. 운영 프로필인데 false 면 경고가 아니라 오류로 올리고, 채우기 배치는 모든 대의 이 줄을 확인한 뒤에 돌립니다. 제 회사도 장애 뒤에 이 로그와 "모든 태스크가 교체된 뒤에 채우기를 돌린다"는 조건을 절차에 넣었어요(1편).

쓰기 암호화가 실패할 때 저장을 막을지도 이 단계에서 정해야 해요. 키를 못 읽는 종류의 실패는 한 건이 아니라 그 시점 이후가 전부 실패하니, 막으면 쓰기 기능 전체가 멈춥니다. 제 회사는 평문으로 저장하고 실패를 ERROR 로그와 호출 등급 모니터로 세게 했고, 남은 평문은 채우기 배치가 다시 치우게 했어요(2편). 관대한 읽기와 채우기 배치가 있는 동안에만 고를 수 있는 선택지입니다.

4. 3단계: 진행 위치를 저장하는 채우기 배치

2단계부터 새로 쓰는 값은 암호문이 되지만, 이미 쌓인 평문은 그대로예요. 이걸 바꾸는 일회성 배치가 채우기입니다. 운영 중에 도는 배치라 두 가지를 견뎌야 해요. 중간에 죽는 것, 그리고 배치가 읽은 뒤 앱이 같은 행을 고치는 것.

📖 용어: 진행 위치 (커서)
"여기까지 처리했다"는 마지막 id 하나예요. 다음 실행은 그 id 보다 큰 행부터 읽습니다. 몇 번째 페이지인지로 기억하면 그 사이 행이 들어오거나 빠질 때 어긋나지만, id 기준이면 어긋나지 않아요.
loop: rows = SELECT id, rrn FROM t WHERE id > :cursor ORDER BY id LIMIT 1000 if rows 가 비었으면: DELETE FROM batch_state WHERE job='fill'; COMMIT; 끝 for (id, v) in rows: if v is null or v 가 암호문 형식: 건너뛴다 c = encrypt(v); decrypt(c) == v 인지 확인 UPDATE t SET rrn = :c WHERE id = :id AND rrn = :v -- 읽은 값 그대로일 때만 UPSERT batch_state(job='fill', cursor_id = 마지막 id) -- 같은 트랜잭션 COMMIT; 잠깐 쉰다(20ms)

→ 페이지를 쓴 것과 진행 위치를 저장한 것이 한 트랜잭션이라, 어느 순간에 죽어도 "쓴 데까지"가 정확히 남습니다. 조건부 UPDATE 는 그 사이 앱이 값을 바꿨으면 0행으로 끝나고, 그 행은 앱이 이미 암호문으로 썼거나 다음 검증에서 다시 세어져요.

실습에서는 부하를 건 채로 배치를 띄우고 4초 뒤 kill -9 로 죽였어요. 저장된 커서는 82000이었고, 다시 띄우자 start cursor=82000 으로 이어서 21만 8천 행을 10.6초에 마쳤습니다. 채우기가 돈 구간의 요청 4,804건은 실패 0, 값 틀림 0이었고, 다시 띄운 실행에서 조건부 UPDATE 가 0행으로 끝난 충돌은 1건이었어요. 끝나면 배치 상태 행을 지워서, 다음 실행은 할 일이 없음을 알고 바로 끝납니다.

💡 실무에서는
• 한 번 실행에 상한(페이지 수)을 두면 커서는 선택이 아니라 필수예요. 매번 처음부터 훑으면 앞쪽 구간만 다시 읽고 뒤쪽에 닿지 못합니다. 제 회사의 486만 행 이력 테이블도 실행마다 상한을 뒀기 때문에 커서를 배치 스위치 행에 함께 저장했어요(4편)
• 조건부 UPDATE 의 "같은 값" 판정은 DB 콜레이션이 합니다. PAD SPACE 콜레이션은 뒤 공백만 다른 두 값을 같다고 봐요. 실습 컬럼은 NO PAD 인 utf8mb4_0900_bin 으로 뒀습니다
• 엔티티로 저장하지 말고 SQL 로 직접 쓰세요. 엔티티로 저장하면 수정 시각이 배치 시각으로 덮이고, 소프트 삭제 조건 때문에 지운 행을 건너뜁니다(4편)

5. 4단계: "암호문 형식이 아닌 값"을 센다

채우기가 끝나면 엄격한 컨버터로 넘어가도 되는지 셉니다. 여기서 많이 쓰는 쿼리가 "평문 모양이 남았나"예요.

-- 평문 모양을 센다 (틀린 쪽) SELECT COUNT(*) FROM t WHERE rrn REGEXP '^[0-9]{6}-?[0-9]{7}$'; -- 암호문 형식이 아닌 값을 센다 (맞는 쪽) SELECT COUNT(*) FROM t WHERE rrn IS NOT NULL AND rrn NOT LIKE 'LABENC1:%';

둘은 같은 질문처럼 보이지만 0이 되는 조건이 다릅니다. 위쪽은 "내가 예상한 모양의 평문"만 세고, 아래쪽은 엄격한 컨버터가 실패할 값을 전부 세요. 이상한 값 하나씩을 넣고 조건마다 걸리는지 봤습니다.

값평문 모양 [0-9]평문 모양 \d암호문 아님 IS NOT NULL<> '' NO PAD<> '' PAD SPACE
정상, 하이픈 없음 (각각)11111
뒤에 문자 붙음00111
자릿수 틀림00111
전각 숫자01111
빈 문자열 ''00100
공백 한 칸 ' '00110
뒤 공백00111
합계 (평문 8개 중)23876

→ NULL 과 암호문 행은 다섯 조건 모두 세지 않았어요(results/count-demo.txt). 평문 모양 쿼리는 평문 8개 중 2개만 셉니다. 정규식을 \d 로 쓰면 실습의 MySQL 8.4 정규식이 전각 숫자도 숫자로 받아 3개가 되는데, 그래도 나머지는 못 세요. <> '' 로 "빈 값은 빼자"고 쓰면 빈 문자열이 빠지고, 컬럼이 PAD SPACE 콜레이션이면 공백 한 칸도 빈 문자열과 같다고 보고 함께 빠집니다. MySQL 문서도 PAD SPACE 콜레이션은 비교할 때 뒤 공백을 무시하고, utf8mb4_bin 이 PAD SPACE, utf8mb4_0900_bin 이 NO PAD 라고 적고 있어요. 그런데 엄격한 컨버터는 빈 문자열도 공백도 "암호문 아님"으로 보고 실패합니다. 세는 조건은 IS NOT NULL 이어야 해요.

이 차이가 실제로 무엇을 만드는지 30만 행 테이블에서 돌려 봤습니다. 채우기 배치가 대상을 "평문 모양인 값"으로 골랐다고 해 볼게요. 이상한 값은 사람이 봐야 한다며 건너뛰는, 흔한 설계예요. 그 배치가 끝난 뒤 두 COUNT 는 이렇게 나왔습니다.

실행 화면. 평문 모양 COUNT 는 0, 암호문 아님 COUNT 는 597. 그 상태로 엄격한 컨버터를 올리자 42건이 실패했다

평문 모양 COUNT 는 0, 암호문 형식이 아닌 값은 597, <> '' 로 세면 498이었어요. 0을 믿고 엄격한 컨버터를 롤링하자 그 구간과 그 뒤 8초 동안 요청 42건이 500으로 실패했습니다. 31건이 목록 조회였어요. 목록은 20행을 한 번에 읽으니, 이상한 값 한 행이 그 페이지 전체를 깨뜨립니다. 제 회사의 장애도 이 모양이었어요. 암호문만 읽는 컨버터를 올린 날 아침 목록 화면이 "복호화 실패: 암호문 형식이 아님"으로 깨졌습니다(1편). 그때 남은 평문은 앞 장의 설정 문제로 다시 생긴 것이었지만, 넘어가기 직전에 세기로 한 검증을 건너뛴 것이 마지막 기회였다는 점은 같아요.

그림 2. 채우기가 고르는 조건과 검증이 세는 조건이 다르면, 그 차이만큼이 0 뒤에 숨는다

SQL COUNT 로도 못 세는 값이 하나 더 있어요. 접두어만 암호문처럼 생기고 풀리지 않는 값입니다. 모든 행을 암호화한 테이블에 'LABENC1:hello' 한 행을 넣자, 암호문 아님 COUNT 는 0이었고 복호화까지 해 보는 검증 배치는 decryptFailed=1 과 그 id 를 찍었어요(results/fake-prefix.txt). 형식을 정규식으로 더 엄격하게 세면 이 값도 걸리지만, 최종 판정은 실제로 풀어 보는 쪽이 맞습니다.

대소문자도 SQL 과 코드가 다르게 봐요. MySQL 문서는 "SQL 패턴은 기본적으로 대소문자를 구분하지 않는다"고 적고 있습니다. 컬럼이 _ci 콜레이션이면 NOT LIKE 'LABENC1:%' 는 소문자 labenc1: 로 시작하는 값을 암호문으로 보고 세지 않는데, Java 의 startsWith 는 대소문자를 구분하니 엄격한 컨버터는 그 행에서 실패해요. 실습 컬럼은 utf8mb4_0900_bin 이라 이 차이가 드러나지 않았습니다. 콜레이션이 _ci 라면 rrn COLLATE utf8mb4_0900_bin LIKE 'LABENC1:%' 처럼 대소문자를 구분하는 비교로 세고, 복호화 검증을 최종 판정으로 둡니다.

💡 실무에서는: 검증을 이렇게 짠다
• 채우기가 고르는 조건과 검증이 세는 조건을 같은 술어로 둡니다: "NULL 이 아니고 암호문 형식이 아니다". 이상한 값도 값 그대로 암호화하고, 데이터 정리는 따로 정합니다
• SQL 로 IS NOT NULL AND NOT LIKE '접두어%' 를 세고, 쓰기 없이 전 행을 복호화해 보는 검증 모드로 실패 수와 id 를 남깁니다(값은 남기지 않아요)
• 이 숫자는 센 시각까지만 참이에요. 엄격한 컨버터 배포 직전에 한 번 더 세고, 0이 아니면 멈춥니다. 제 회사는 이 조건을 문서에 적어 두고 건너뛰었어요(1편)
• COUNT 는 주 DB 에서 셉니다. 읽기 복제본은 지연만큼 이전 상태라, 복제본에서 센 0 은 주 DB 의 0 과 다를 수 있어요. 복제본을 읽는 앱이 있다면 엄격한 컨버터로 넘기기 전에 복제 지연이 0인지도 봅니다. 채우기가 쓴 행이 복제본에 아직 안 닿았으면 그 앱은 평문을 읽어요

6. 5단계: 엄격한 컨버터로, 되돌릴 때는 쓰기부터

검증이 0이면 엄격한 컨버터를 롤링합니다. 바른 순서를 끝까지 밟은 실행의 결과예요.

실행 화면. 세 번의 롤링 배포와 중간에 죽인 채우기를 거치는 동안 요청 29,401건, 실패 0, 값 틀림 0

v0 에서 시작해 v3 가 될 때까지 요청 29,401건 중 실패 0, 값 틀림 0이었어요. 엄격한 컨버터로 넘긴 뒤 다시 센 암호문 아님 COUNT 도 0이었습니다.

엄격한 컨버터를 배포할 때 관대한 컨버터와 채우기 배치도 함께 지웁니다. 평문을 받아 주는 코드가 살아 있으면 평문이 다시 들어와도 아무 일도 일어나지 않아, 들어왔다는 사실을 알 수 없기 때문이에요. 그리고 배치의 "암호문을 평문으로 되돌리는" 모드도 같이 지워요. 엄격한 컨버터는 되돌린 평문을 읽지 못하니, 그 모드는 안전장치가 아니라 가장 위험한 버튼이 됩니다. 제 회사에서는 이걸 독립 리뷰가 짚었어요(2편).

엄격한 컨버터가 지키는 건 앱을 거치는 쓰기뿐이에요. 데이터 이관 import 나 사람이 직접 돌리는 SQL 은 컨버터를 거치지 않으니, 전환 뒤에도 평문이 들어올 수 있습니다. DB 쪽에서 막고 싶다면 CHECK (rrn IS NULL OR rrn COLLATE utf8mb4_0900_bin LIKE 'LABENC1:%') 같은 제약이 선택지예요. MySQL 문서에 따르면 CHECK 제약은 8.0.16 부터 실제로 적용되고, INSERT, UPDATE, REPLACE, LOAD DATA 에서 평가되며, NULL 처럼 결과가 UNKNOWN 이면 통과합니다. 이 식을 실습에서 돌려 보지는 않았고, 큰 테이블에 제약을 추가할 때 기존 행을 검사하는 비용도 확인하지 못했어요. 점검 시간에 같은 크기의 사본으로 먼저 재 보세요.

⚠️ 주의: 테이블 밖에 남는 것
• 캐시: 이 값을 담는 캐시가 있으면 무엇을 담는지 확인하고, 엄격 전환과 되돌림 때마다 비웁니다. 옛 형식이 담긴 항목이 남아 있으면 바뀐 코드가 그 항목을 읽어요
• 백업, binlog, 추출본: 테이블을 전부 암호문으로 바꿔도 전환 이전에 만든 백업과 binlog, 내려받아 둔 추출본에는 평문이 그대로 있습니다. 보존 기간과 파기는 전환과 따로 정해야 해요

엄격한 쪽으로 넘기기 전, 2단계 상태에서 되돌려야 할 때도 있어요. 이때 흔한 실수가 "복원 배치를 돌리고 옛 버전으로"라는 순서입니다. 쓰기가 멈춘 테이블이면 맞는 순서인데, 쓰기가 계속되는 테이블에서는 틀려요. 제 회사도 쓰기가 멈춘 레거시 테이블의 절차를 매일 쌓이는 테이블에 그대로 옮겨 적었다가, 리뷰에서 정정했습니다(5편).

틀린 순서: 쓰기 켠 채 복원 → v0 (results/rollback-wrong.txt) 복원 직후 남은 암호문 663 행 v0 롤링 끝난 뒤 암호문 1,130 행 요청 28,897건: 실패 0, 값 틀림 223 바른 순서: 쓰기 끈 판(v2-off) 롤링 → 복원 → 암호문 0 확인 → v0 (results/rollback-right.txt) 복원 직후 남은 암호문 0 행 v0 롤링 끝난 뒤 암호문 0 행 요청 34,935건: 실패 0, 값 틀림 0

→ 틀린 순서에서는 복원이 도는 동안에도 v2 가 계속 새 암호문을 써서, 복원이 끝난 순간 이미 663행이 암호문이었어요. v0 롤링 중에도 남은 v2 대가 계속 써서 1,130행으로 늘었고, 옛 버전은 그 행들을 암호문 그대로 돌려줬습니다. 바른 순서는 쓰기 스위치를 끈 판을 먼저 롤링해요. 이 판도 읽기는 관대하니 화면은 그대로고, 새 값은 평문으로 쌓입니다. 암호문이 더 생기지 않는 상태에서 복원하고 0을 확인한 뒤에야 옛 버전으로 내려가요. 복원 배치는 새 버전에 들어 있으니, 버전을 먼저 내리면 되돌릴 수단도 같이 사라집니다.

그림 3. 쓰기가 계속되는 테이블에서 되돌림의 첫 걸음은 복원이 아니라 쓰기 스위치다
💡 배포 전 체크리스트
• 컨버터 밖에서 같은 컬럼을 읽고 쓰는 경로(다른 서비스, 네이티브 SQL, ETL·CDC·BI, 뷰·트리거, 관리 도구)와 WHERE·UNIQUE 사용처를 찾았다
• 암호문 최대 길이를 바이트로 계산했다. 255 이하면 ALGORITHM=INPLACE, LOCK=NONE, 256 이상이면 COPY 점검 시간이나 온라인 스키마 변경 도구(또는 새 컬럼 추가)로 정했다
• 1단계(관대한 읽기, 평문 쓰기)가 모든 대에 깔린 뒤 2단계를 내보낸다
• 2단계 뒤 모든 프로세스의 기동 로그에서 쓰기 스위치 실제 값을 확인했다
• 채우기는 커서와 페이지 쓰기를 한 트랜잭션에 담고, UPDATE 에 "읽은 값 그대로" 조건을 건다
• 채우기 대상과 검증 대상이 같은 술어다: IS NOT NULL AND NOT 암호문 형식
• 엄격한 컨버터 배포 직전에 주 DB 에서 SQL COUNT(대소문자 구분 비교)와 복호화 검증을 다시 돌려 둘 다 0이고, 복제 지연도 0이다
• 엄격 전환과 되돌림 때 비울 캐시를 정했다
• 엄격한 컨버터와 함께 관대한 컨버터, 채우기, 복원 모드를 지운다
• 되돌림 절차의 첫 줄이 "쓰기 스위치 끄고 재배포"다
• 앱 밖의 import·수작업 SQL 경로를 어떻게 막을지(CHECK 제약 등) 정했고, 백업·binlog·추출본의 평문은 따로 다룬다
✍️ 오늘의 요약
무중단 암호화 전환은 컬럼 넓히기, 관대한 읽기, 쓰기 암호화, 채우기, 검증, 엄격한 읽기의 순서로, 한 배포에 한 가지만 바꾸고 모든 대가 그 버전이 된 뒤에 넘어갑니다. 실습에서 이 순서는 요청 29,401건 동안 실패 0, 값 틀림 0이었고, 읽기 단계를 건너뛰면 오류 없이 암호문 164건이 응답에 실렸어요.

깨지는 지점은 대개 숫자를 읽는 쪽이었습니다. 스위치가 안 읽힌 한 대는 요청을 하나도 실패시키지 않으면서 채우기가 끝난 뒤 30초 동안 평문을 499행에서 1,810행으로 늘렸고, 평문 모양 COUNT 0 은 암호문 형식이 아닌 597행을 가렸으며, 쓰기를 켠 채 돌린 복원은 끝난 순간 이미 663행이 암호문이었어요. 그래서 검증은 "암호문 형식이 아닌 값"을 배포 직전에 다시 세고, 되돌림은 쓰기 스위치부터 끕니다.

전환이 끝났다는 것은 배포가 성공했다는 뜻이 아니라, 엄격한 컨버터가 실패할 값이 0이라는 것을 직전에 다시 셌다는 뜻입니다.
