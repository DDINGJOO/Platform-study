애플리케이션 로그에 Deadlock found when trying to get lock; try restarting transaction 이 찍혔습니다. DB 에 들어가 SHOW ENGINE INNODB STATUS 를 치면 LATEST DETECTED DEADLOCK 아래에 SQL 두 개와 lock_mode X locks rec but not gap waiting 같은 줄이 나와요. 두 SQL 이 모두 SELECT … FOR UPDATE 라서 "FOR UPDATE 를 빼면 되겠다"고 결론 내리기 쉽습니다.

그 결론은 자주 틀려요. 출력에 찍힌 SQL 은 교착 순간에 기다리던 문장이고, 상대를 막고 있던 잠금을 잡은 문장은 출력 어디에도 없을 수 있습니다. 이 글은 MySQL 8.4 에서 교착 두 종류를 일부러 내고, 같은 사건을 STATUS, 에러 로그, performance_schema.data_locks 세 군데서 본 결과로 다음을 정리합니다.

1. 실습: 교착 두 종류를 세 바퀴

MySQL 8.4.11 컨테이너 하나에 mysql 클라이언트 세션을 여러 개 붙여 돌렸어요. 격리 수준은 기본값 REPEATABLE-READ 입니다. 한 바퀴에 교착을 두 번 냅니다.

A. 1편과 같은 교착 (첫 방문 동시 요청 3개) visit(id PK, user_key UNIQUE, cnt) 세션 1, 2, 3 모두: BEGIN; INSERT IGNORE INTO visit (user_key) VALUES ('u-1'); SELECT * FROM visit WHERE user_key='u-1' FOR UPDATE; UPDATE visit SET cnt = cnt + 1 WHERE user_key='u-1'; COMMIT; 세션 1 만 INSERT 뒤 4초 쉰다 (그동안 2, 3 이 중복 검사에서 기다린다) B. 두 행을 서로 반대 순서로 갱신 acct(id PK, bal), 행 1, 2, 10 세션 1: UPDATE … WHERE id = 1; (1초) UPDATE … WHERE id = 2; 세션 2: UPDATE … WHERE id = 2; (3초) UPDATE … WHERE id = 1; C. 교착 없이 갭 잠금, 삽입 의도 잠금을 만들어 표기만 대조

교착이 나기 전 대기 상태에서 data_locks 를 찍고, 교착 직후 STATUS 를 저장하고, 바퀴가 끝나면 에러 로그를 저장해요. 세 바퀴 모두 A 와 B 에서 교착이 한 번씩 났고, 아래 숫자와 원문은 전부 이 세 바퀴에서 나왔습니다.

git clone https://github.com/DDINGJOO/Platform-study.git cd Platform-study/labs/db/dl-03-read-deadlock scripts/run_all.sh # MySQL(127.0.0.1:39030) + 세 바퀴, 약 1분 docker compose down -v

코드는 labs/db/dl-03-read-deadlock, 세 바퀴 요약은 results/summary.txt 에 있어요.

2. LATEST DETECTED DEADLOCK 한 줄씩 읽기

A 교착 직후의 STATUS 입니다. 첫 바퀴(r1) 원문이고, 레코드 덤프의 큰 숫자와 OS 스레드 핸들만 자리표시자로 바꿨어요.

그림 1. A 교착 직후의 STATUS. 두 트랜잭션이 같은 레코드에 S 를 쥐고 X 를 기다린다

같은 원문을 블록마다 주석을 달아 다시 놓을게요.

*** (1) TRANSACTION: TRANSACTION 1941, ACTIVE 3 sec starting index read ← 트랜잭션 번호, 시작한 지 3초 LOCK WAIT 5 lock struct(s), heap size 1128, 3 row lock(s) ← 잠금을 기다리는 중 MySQL thread id 127, … localhost root statistics ← 접속 번호 (CONNECTION_ID, processlist Id) SELECT * FROM visit WHERE user_key='u-1' FOR UPDATE ← 교착 순간 실행 중이던 문장 하나 *** (1) HOLDS THE LOCK(S): ← 이미 쥐고 있는 잠금 RECORD LOCKS … index uk_user_key of table `lab`.`visit` trx id 1941 lock mode S 0: len 3; hex 752d31; asc u-1;; ← 보조 인덱스 값 'u-1' 1: len 8; hex {생략}; asc ;; ← 붙어 있는 PK (id = 1) *** (1) WAITING FOR THIS LOCK TO BE GRANTED: ← 지금 기다리는 잠금 RECORD LOCKS … index uk_user_key … trx id 1941 lock_mode X locks rec but not gap waiting *** (2) TRANSACTION: TRANSACTION 1942, … MySQL thread id 128 … SELECT * FROM visit WHERE user_key='u-1' FOR UPDATE *** (2) HOLDS THE LOCK(S): … uk_user_key … lock mode S (같은 레코드) *** (2) WAITING FOR THIS LOCK: … uk_user_key … lock_mode X locks rec but not gap waiting *** WE ROLL BACK TRANSACTION (2) ← 희생자. thread id 128 의 세션이 1213 을 받는다

→ 두 트랜잭션이 uk_user_key 의 같은 레코드('u-1', id 1)에 S 잠금을 쥔 채로, 같은 레코드의 X 잠금을 기다렸다는 뜻이에요. S 끼리는 같이 쥘 수 있지만 X 는 다른 쪽 S 가 풀려야 받을 수 있으니 둘 다 영원히 기다리게 됩니다. 세 바퀴 모두 WE ROLL BACK TRANSACTION (2) 였고, 실제로 1213 을 받은 세션의 접속 번호가 (2) 의 MySQL thread id 와 같았어요.

여기서 가장 중요한 건 S 잠금을 잡은 문장이 출력에 없다는 점이에요. 두 트랜잭션 모두 SQL 줄에는 SELECT … FOR UPDATE 가 찍혔지만, FOR UPDATE 는 X 를 요청하는 문장입니다. S 는 그 앞의 INSERT IGNORE 가 중복 키를 만났을 때 잡은 거예요(이유는 1편). STATUS 의 SQL 줄은 트랜잭션이 그 순간 실행 중이던 문장 하나일 뿐이고, 트랜잭션이 앞에서 실행한 문장들은 보여 주지 않습니다. 물론 SQL 줄의 문장이 HOLDS 의 잠금을 잡은 문장인 경우도 있어요. UPDATE … WHERE id IN (1, 2) 처럼 한 문장이 여러 행을 차례로 잠그다 막히면 쥔 잠금과 기다리는 잠금이 같은 문장에서 나옵니다. 그래서 "SQL 줄은 범인이 아니다"가 아니라 "SQL 줄이 범인이라는 보장이 없다"로 읽어야 해요. 매뉴얼의 교착 예시(17.7.5.1)도 두 SQL 이 모두 UPDATE 인데, HOLDS 에 찍힌 S 잠금은 그 전에 실행한 SELECT … FOR SHARE 가 잡은 것이에요.

그림 2. STATUS 의 SQL 줄은 기다리는 문장이다. 쥐고 있는 잠금을 잡은 문장은 따로 찾아야 한다

잠금 줄 말고도 읽을 것

TRANSACTION 블록의 앞 몇 줄도 원인을 좁히는 데 써요. A 와 B 에서 실제로 나온 값으로 정리했습니다.

줄 A (r1) B (r1) 읽는 법 ACTIVE N sec 3 sec 4 sec / 3 sec 트랜잭션이 시작한 지 얼마나 됐나. 길면 중간에 다른 일(외부 호출 등)을 한다 LOCK WAIT … N row lock(s) 3 row lock(s) 2 row lock(s) 쥐고 기다리는 행 잠금 수 undo log entries N (없음) undo log entries 1 이미 바꾼 행이 있다. 없으면 아직 아무것도 안 바꿨다 MySQL thread id …, … root 상태 statistics updating 교착 순간의 스레드 상태 starting index read 둘 다 둘 다 인덱스로 행을 찾기 시작한 문장에서 막혔다

→ A 에 undo log entries 가 없다는 건 두 트랜잭션 모두 아직 아무 행도 바꾸지 않았다는 뜻이에요. INSERT IGNORE 는 중복이라 넣지 못했고, FOR UPDATE 에서 막혔으니까요. 그런데도 S 잠금은 쥐고 있었습니다. "아무것도 안 바꾼 트랜잭션이 왜 잠금을 쥐고 있나"가 1편 패턴을 알아보는 단서예요. B 는 둘 다 한 행씩 바꾼 뒤(undo log entries 1) 두 번째 행에서 막혔습니다. 매뉴얼은 희생자를 고를 때 삽입, 갱신, 삭제한 행 수로 트랜잭션 크기를 잰다고 적어요. B 는 두 트랜잭션의 크기가 같았어요. 실습에서는 세 바퀴 모두 (2) 가 희생됐지만, 크기가 같을 때 누구를 고르는지는 문서가 정해 두지 않았습니다. 애플리케이션은 양쪽 경로 모두 1213 을 받을 수 있다고 보고 재시도를 준비해야 해요.

드물게 이 절에 TOO DEEP OR LONG SEARCH IN THE LOCK TABLE WAITS-FOR GRAPH, WE WILL ROLL BACK FOLLOWING TRANSACTION 이 찍히기도 해요. 매뉴얼(17.7.5.2)에 따르면 대기 목록의 트랜잭션이 200개에 이르렀거나 살펴봐야 할 잠금이 100만 개를 넘은 경우입니다. 이때는 실제 순환이 없어도 교착으로 처리돼요. 그러니 이 메시지를 보면 잠금 순서보다 한 행에 대기가 몰린 핫스팟을 먼저 의심합니다.

📖 용어: next-key 잠금과 REC_NOT_GAP
InnoDB 의 행 잠금은 인덱스 레코드에 걸려요. 레코드만 잠그면 "rec but not gap", 레코드 앞의 빈 구간(갭)만 잠그면 "gap", 둘 다 잠그면 next-key 잠금입니다. 갭까지 잠그면 그 구간에 다른 트랜잭션이 새 행을 넣지 못해요. STATUS 에서 아무 꼬리표 없이 lock mode S 나 lock_mode X 라고만 나오면 next-key 잠금이에요.

3. STATUS 표기와 data_locks.LOCK_MODE 대응표

같은 잠금을 STATUS 와 data_locks 는 다르게 적어요. 실습 A, B, C 에서 두 출력을 같은 순간에 찍어 맞춰 본 결과입니다. C 는 innodb_status_output_locks=ON 으로 켜서 교착 절이 아닌 TRANSACTIONS 절에서도 잠금 줄이 나오게 했어요.

STATUS 표기 data_locks.LOCK_MODE 실습에서 나온 곳 lock mode S S A: INSERT IGNORE 가 중복을 만나 잡음 lock mode S locks rec but not gap S,REC_NOT_GAP C: 유니크 등치 FOR SHARE lock_mode X X C: id BETWEEN 1 AND 2 FOR UPDATE 의 id 2 lock_mode X locks rec but not gap X,REC_NOT_GAP B: PK 등치 UPDATE / A: FOR UPDATE 가 기다림 lock_mode X locks gap before rec X,GAP C: 없는 id = 5 FOR UPDATE, 다음 레코드 10 앞 lock_mode X locks gap before rec insert intention X,GAP,INSERT_INTENTION C: INSERT id 6 이 그 갭에서 기다림 TABLE LOCK … lock mode IX / IS IX / IS (LOCK_TYPE=TABLE) 행을 잠그기 전에 테이블에 거는 의도 잠금 … waiting (줄 끝) LOCK_STATUS = WAITING 기다리는 쪽

→ 두 가지를 기억해 두면 검색할 때 덜 헤매요. 첫째, STATUS 는 레코드 잠금의 S 를 lock mode S(띄어쓰기), X 를 lock_mode X(밑줄)로 적습니다. 세 바퀴와 매뉴얼 예시가 모두 그랬어요. 테이블 잠금은 X 계열이어도 lock mode IX 처럼 띄어 씁니다. 로그에서 grep 할 때 lock.mode 처럼 둘 다 잡히게 씁니다. 둘째, data_locks 문서(29.12.13.1)는 InnoDB 의 LOCK_MODE 값으로 S[,GAP], X[,GAP], IS[,GAP], IX[,GAP], AUTO_INC, UNKNOWN 만 적어 두었는데, 실제로는 REC_NOT_GAP 과 INSERT_INTENTION 이 붙어 나왔어요. 문서 목록에 없다고 이상한 값으로 보지 않아도 됩니다.

어느 행인지는 data_locks.LOCK_DATA 가 바로 보여 줘요. 보조 인덱스 잠금이면 'u-1', 1 처럼 인덱스 값 뒤에 PK 가 붙습니다. STATUS 에서는 레코드 덤프의 asc 칸을 읽는데, 문자열은 그대로 보이지만 정수는 바이트로만 보여요. B 의 PK 1 은 hex 80000001, PK 2 는 hex 80000002 로 나왔습니다. 부호 있는 정수의 맨 앞 비트가 뒤집혀 저장되기 때문이라, 앞의 8 을 0 으로 바꿔 읽으면 돼요. 같은 이유로 음수는 7 로 시작하고(-1 은 7fffffff), UNSIGNED 컬럼은 뒤집지 않아 1 이 0 으로 시작하는 00…01 로 보입니다. BIGINT 는 16자리라 A 의 visit.id 1 은 8 다음에 0 이 14개, 끝이 1 이었어요.

번호도 셋이 섞여요. STATUS 의 MySQL thread id 는 CONNECTION_ID(), SHOW PROCESSLIST 의 Id, INNODB_TRX.trx_mysql_thread_id 와 같은 접속 번호입니다. data_locks.THREAD_ID 는 performance_schema 의 스레드 번호라 값이 달라요. r1 에서 접속 127 의 THREAD_ID 는 167 이었어요. 둘은 performance_schema.threads 의 PROCESSLIST_ID 로 이어집니다.

4. STATUS 는 마지막 1건만, 에러 로그는 설정 두 개가 필요하다

A 다음에 B 를 내고 STATUS 를 다시 봤어요. 세 바퀴 모두 A 직후 STATUS 에는 visit 이 있었고, B 직후에는 acct 교착만 남고 visit 은 한 글자도 없었습니다. 매뉴얼도 이 절이 마지막 교착만 보여 준다고 적어요. 알람을 받고 몇 분 뒤에 들어가면 이미 다른 교착이 덮어쓴 뒤일 수 있습니다.

그래서 innodb_print_all_deadlocks 를 켜요. 매뉴얼의 변수 설명은 기본값 OFF, 전역, 동적 변경 가능이고, 켜면 모든 교착 정보를 mysqld 에러 로그에 남긴다고 적습니다(innodb_print_all_deadlocks). 기본값 OFF 는 매뉴얼 기준이에요. 실습 컨테이너는 앞선 시험 실행에서 이미 SET GLOBAL 로 켜 둔 상태였고, 세 바퀴 내내 켜져 있었습니다. 그런데 에러 로그를 열어 보니 A 의 기록이 이랬습니다.

(results/r1-errorlog.txt, A: log_error_verbosity = 2, 기본값) TRANSACTION 1941, ACTIVE 3 sec starting index read … SELECT * FROM visit WHERE user_key='u-1' FOR UPDATE RECORD LOCKS … uk_user_key … trx id 1941 lock mode S RECORD LOCKS … uk_user_key … trx id 1941 lock_mode X locks rec but not gap waiting TRANSACTION 1942, ACTIVE 3 sec starting index read … ← "WE ROLL BACK" 줄이 없다 (B: log_error_verbosity = 3) … [Note] [MY-012468] [InnoDB] Transactions deadlock detected, dumping detailed information. … [Note] [MY-012469] [InnoDB] *** (1) TRANSACTION: TRANSACTION 1949, ACTIVE 4 sec starting index read … [Note] [MY-012469] [InnoDB] *** (1) HOLDS THE LOCK(S): … [Note] [MY-012469] [InnoDB] *** (1) WAITING FOR THIS LOCK TO BE GRANTED: … … [Note] [MY-012469] [InnoDB] *** WE ROLL BACK TRANSACTION (2)

→ 기본값에서는 [MY-012468] … Transactions deadlock detected 머리말, *** (1) HOLDS THE LOCK(S): 같은 소제목, WE ROLL BACK 희생자 줄과 시각이 빠지고 트랜잭션·잠금 본문만 남았다는 뜻이에요. 세 바퀴 모두 같았습니다. 머리말과 소제목은 Note 등급으로 찍히는데, log_error_verbosity 의 기본값 2 는 ERROR 와 WARNING 만 통과시키기 때문이에요(log_error_verbosity, 3 이어야 INFORMATION 까지). 본문은 등급 필터를 거치지 않고 stderr 로 바로 쓰여서 남았어요. 소스로 확인한 경로는 4편에 있습니다. 이 상태로는 어느 잠금이 쥔 것이고 어느 것이 기다린 것인지를 줄 끝 waiting 으로만 짐작해야 하고, 누가 희생됐는지와 언제 났는지는 알 수 없어요. 교착을 조사하는 동안에는 두 변수를 같이 켭니다. 3 은 다른 Note 도 모두 남기니 조사가 끝나면 되돌려요.

SET GLOBAL innodb_print_all_deadlocks = ON; -- 모든 교착을 에러 로그로 SET GLOBAL log_error_verbosity = 3; -- 머리말, 소제목, 희생자 줄, 시각까지 남기려면 -- 재시작 뒤에도 유지하려면 SET PERSIST 나 설정 파일에. 관리형 DB 는 파라미터 그룹에서 바꾼다

교착이 몇 번 났는지 세는 것은 별개예요. INFORMATION_SCHEMA.INNODB_METRICS 의 lock_deadlocks 는 바퀴마다 정확히 2 씩 늘었습니다(교착 두 번). 같은 8.4.11 에서 SHOW GLOBAL STATUS LIKE 'Innodb_deadlocks' 는 행이 하나도 나오지 않았어요. 카운터로 알람을 걸 때 어느 쪽을 읽는지는 4편에서 다룹니다.

5. 교착 전 대기 상태는 data_locks 로 잡는다

STATUS 와 에러 로그는 교착이 난 뒤의 기록이에요. 반면 data_locks 와 data_lock_waits 는 지금 이 순간의 잠금이라, 교착이 끝나면 비어 있습니다. 대신 교착 직전에 누가 누구를 기다리는지 볼 수 있어요. A 에서 세션 1 이 INSERT 뒤 4초를 쉬는 동안, 세션 2, 3 이 중복 검사에서 기다리던 순간을 찍었습니다.

그림 3. 대기 중의 data_locks. 첫 세션의 X 와 나머지 둘의 S 대기가 보인다

→ 트랜잭션 1940(접속 126)이 INSERT 한 행의 유니크 인덱스 레코드에 X,REC_NOT_GAP 을 쥐었고, 1941 과 1942 가 같은 레코드에 S 를 기다렸어요. 1940 이 커밋하면 두 S 가 함께 허락되고, 둘이 FOR UPDATE 로 X 를 요청하는 순간 2장의 교착이 됩니다. 교착이 나기 전 단계를 이렇게 직접 볼 수 있어요.

그런데 그림 3 에 함정이 하나 있어요. 1940 의 X,REC_NOT_GAP 줄의 THREAD_ID 가 166(접속 126)이 아니라 167, 기다리는 접속 127 의 스레드로 찍혔습니다. 세 바퀴 모두 이렇게 기다리는 쪽 스레드 번호가 찍혔어요. 흔히 쓰는 대로 THREAD_ID 로 조인하면 결과가 이렇게 나옵니다.

-- THREAD_ID 기준 조인 (r1) req_thr req_mode blk_thr blk_mode req_sql_now / blk_sql_now 167 S 167 X,REC_NOT_GAP INSERT IGNORE … / INSERT IGNORE … ← 자기가 자기를 막는다? 168 S 167 X,REC_NOT_GAP INSERT IGNORE … / INSERT IGNORE … ← 막는 쪽이 엉뚱한 세션

→ 막는 쪽이 실제 주인(접속 126)이 아니라 같이 기다리는 세션으로 나왔다는 뜻이에요. data_locks 문서를 보면 두 칸의 뜻이 달라요. ENGINE_TRANSACTION_ID 는 잠금을 요청한 트랜잭션이고 "잠금의 주인(owner of the lock)으로 볼 수 있다"고 적혀 있습니다. 반면 THREAD_ID 는 그 잠금을 만든 세션의 스레드이고, EVENT_ID 와 함께 "잠금 데이터 구조가 메모리에 만들어진 이벤트"를 가리키며 "그 이벤트는 이 잠금 요청보다 먼저 일어났을 수 있다"고 적혀 있어요. 즉 THREAD_ID 는 주인이 아니라 잠금 구조를 만든 쪽입니다. INSERT 한 행의 잠금 구조를 기다리는 쪽 세션이 만들었기 때문에 이렇게 보인 것으로 짐작해요. 내부 구현은 이 실습으로 확인하지 못했지만, 결과는 세 바퀴 모두 같았습니다. 주인은 문서대로 트랜잭션 번호로 찾으면 정확해요. ENGINE_TRANSACTION_ID 는 1940 으로 맞게 나왔어요.

SELECT rx.trx_mysql_thread_id AS req_conn, rl.LOCK_MODE AS req_mode, rl.LOCK_DATA AS data, bx.trx_mysql_thread_id AS blk_conn, bl.LOCK_MODE AS blk_mode, rx.trx_query AS req_sql_now, IFNULL(bx.trx_query, '(idle)') AS blk_sql_now FROM performance_schema.data_lock_waits w JOIN performance_schema.data_locks rl ON rl.ENGINE_LOCK_ID = w.REQUESTING_ENGINE_LOCK_ID JOIN performance_schema.data_locks bl ON bl.ENGINE_LOCK_ID = w.BLOCKING_ENGINE_LOCK_ID JOIN information_schema.INNODB_TRX rx ON rx.trx_id = w.REQUESTING_ENGINE_TRANSACTION_ID JOIN information_schema.INNODB_TRX bx ON bx.trx_id = w.BLOCKING_ENGINE_TRANSACTION_ID; -- 결과 (r1) req_conn req_mode data blk_conn blk_mode req_sql_now blk_sql_now 127 S 'u-1', 1 126 X,REC_NOT_GAP INSERT IGNORE … SELECT SLEEP(4) 128 S 'u-1', 1 126 X,REC_NOT_GAP INSERT IGNORE … SELECT SLEEP(4)

→ 막는 쪽이 접속 126 으로 바로잡혔어요. 그런데 그 세션이 지금 실행 중인 문장은 SELECT SLEEP(4) 입니다. 실제 서비스라면 다른 조회나 외부 API 호출 중이거나 아무것도 안 하는(idle) 상태일 거예요. 막고 있는 잠금을 잡은 문장은 여기서도 안 보입니다. 그 문장은 events_statements_history 에서 찾아요. 스레드마다 끝난 문장을 최근 N개 남기는 표이고, N 은 서버가 시작할 때 자동으로 정합니다(29.12.6.2). 실습에서는 설정을 따로 바꾸지 않고 바로 조회됐어요. 내 서버의 N 은 SHOW VARIABLES LIKE 'performance_schema_events_statements_history_size' 로 확인합니다.

SELECT t.PROCESSLIST_ID AS conn, h.EVENT_ID, h.SQL_TEXT FROM performance_schema.events_statements_history h JOIN performance_schema.threads t USING (THREAD_ID) WHERE t.PROCESSLIST_ID = 126 -- 위에서 찾은 blk_conn ORDER BY h.EVENT_ID; -- 결과 (r1): BEGIN / INSERT IGNORE INTO visit (user_key) VALUES ('u-1') / SELECT NOW(6) …

→ 막는 세션의 이력에 INSERT IGNORE 가 있었어요. B 에서도 같은 방법으로, id 2 를 막던 세션의 이력에 UPDATE acct … WHERE id = 2 가 남아 있었습니다. 세 바퀴 모두 이력에서 잠금을 잡은 문장이 나왔어요. 단, 이력은 스레드마다 최근 N개뿐이라 문장이 많은 트랜잭션이면 앞 문장이 밀려날 수 있고, 커넥션 풀은 같은 접속을 계속 재사용하니 트랜잭션 경계를 같이 봐야 합니다. 풀이 접속을 빌려줄 때마다 보내는 검증 쿼리(SELECT 1 같은 것)도 이력 칸을 하나씩 차지해요.

운영에서는 교착이 난 다음에 보면 이미 늦어요. 잠금 대기가 생겼을 때만 이 조인을 몇 초 간격으로 찍어 남기는 작업을 두면, 다음 교착 직전의 대기 상태가 남습니다. 교착 자체는 순환이 닫히는 순간 감지되니 그 순간까지 찍히지는 않아요. 하지만 A 처럼 앞 단계에서 몇 초씩 기다리는 패턴은 잡힙니다. 최소한의 모양은 이렇습니다(실습에서 쓴 조인을 그대로 파일로 남기는 형태이고, 운영 적용 전에는 조회 권한과 부하를 따로 확인하세요).

# 잠금 대기가 있을 때만 대기 관계와 막는 쪽 이력을 남긴다 (2초 간격) while true; do n=$(mysql -N -e "SELECT COUNT(*) FROM performance_schema.data_lock_waits") if [ "$n" -gt 0 ]; then { date '+%F %T'; mysql -t < lock_waits_by_trx.sql; mysql -t < blocker_history.sql; } >> lockwait.log fi sleep 2 done

→ lock_waits_by_trx.sql 는 위의 트랜잭션 기준 조인이고, blocker_history.sql 은 그 결과의 blk_conn 으로 문장 이력을 찾는 쿼리예요(실습의 scripts/run.sh 에 둘 다 있습니다). 막는 쪽 이력은 그 세션이 다음 문장을 실행하면 밀려나니, 대기를 발견한 그 순간에 같이 찍어야 해요.

6. 원인 확정 순서: SQL, 잠금 종류, 인덱스, 순서

B 의 STATUS 도 같은 방식으로 읽어 보면 A 와 모양이 다릅니다.

(results/r1-B-status.txt, 요약) (1) thread 138 SQL: UPDATE acct SET bal = bal + 10 WHERE id = 2 HOLDS PRIMARY lock_mode X locks rec but not gap hex 80000001 (id 1) WAITING PRIMARY lock_mode X locks rec but not gap waiting hex 80000002 (id 2) (2) thread 139 SQL: UPDATE acct SET bal = bal + 10 WHERE id = 1 HOLDS PRIMARY lock_mode X locks rec but not gap id 2 WAITING PRIMARY lock_mode X locks rec but not gap waiting id 1 WE ROLL BACK TRANSACTION (2)

→ A 는 두 트랜잭션이 같은 레코드에 S 를 쥐고 X 를 기다렸어요(업그레이드형). B 는 (1) 이 쥔 행을 (2) 가 기다리고 (2) 가 쥔 행을 (1) 이 기다렸습니다(순서형). HOLDS 와 WAITING 의 레코드가 같은지, 엇갈리는지만 보면 둘이 갈려요. B 도 HOLDS 의 id 1 잠금을 잡은 WHERE id = 1 문장은 (1) 의 SQL 줄에 없습니다.

그림 4. 같은 레코드에서 S 를 X 로 올리려다 막히는 교착과, 두 행을 반대 순서로 잠그는 교착

이제 원인을 확정하는 순서를 정리할게요. 순서가 중요합니다. 1번을 건너뛰면 나머지가 다 맞아도 엉뚱한 코드를 고치게 돼요.

✅ 교착 원인 확정 체크리스트
1. 출력의 SQL 이 지금 배포된 코드에 있는가. STATUS 의 SQL 문자열을 운영에 떠 있는 빌드의 커밋에서 찾습니다. main 브랜치가 아니라 배포된 아티팩트의 커밋이에요. 컨테이너 이미지 태그, 빌드 정보 엔드포인트(Spring Boot 라면 git 정보를 넣어 둔 /actuator/info), 배포 이력 중 하나로 확인합니다. 그 커밋에 문장이 없다면 다른 서비스나 배치가 낸 문장이거나, 고친 코드가 아직 배포되지 않은 거예요. ORM 이 만든 SQL 이면 문자열이 코드에 그대로 없으니 테이블과 WHERE 컬럼으로 찾습니다.
2. 잠금 종류. HOLDS 가 lock mode S 계열이면 앞에서 S 를 잡은 문장(중복 검사를 하는 INSERT 와 INSERT IGNORE, FOR SHARE, 외래 키 검사)을 찾습니다. X 계열이면 UPDATE, DELETE, FOR UPDATE 예요. 갭이나 insert intention 이 보이면 범위 조건이나 없는 값을 잠근 문장을 의심해요.
3. 인덱스. index PRIMARY 인지 보조 인덱스(uk_…)인지 봅니다. 보조 유니크 인덱스면 그 컬럼으로 넣거나 찾는 문장이 범인 후보예요. 인덱스가 없는 조건으로 UPDATE 하면 훑은 레코드 전부가 잠겨 후보가 늘어납니다. 원래 쓰려던 인덱스인지 EXPLAIN 으로 확인해요.
4. 순서. HOLDS 와 WAITING 의 레코드가 같으면 업그레이드형, 엇갈리면 순서형입니다. 앞의 것은 잠금을 처음부터 X 로 잡거나 S 를 잡지 않는 쪽으로, 뒤의 것은 두 경로가 같은 순서(예: PK 오름차순)로 잠그도록 고쳐요. 업그레이드형을 고치는 구체적인 방법은 6편에 모았습니다. 이때 INSERT IGNORE 를 ON DUPLICATE KEY UPDATE 로 바꾸고 반환값으로 중복을 판정하면 2편의 함정에 빠지니 주의하세요.
5. 잠금을 잡은 문장 확정. STATUS 의 SQL 줄이 그 문장이라는 보장이 없으니 코드에서 같은 트랜잭션의 앞 문장을 찾거나, 재현 환경에서 events_statements_history 로 확인합니다.

1번이 왜 맨 앞인지는 실제로 겪은 일로 설명할게요. 1편의 교착(INSERT IGNORE 다음 같은 행에 FOR UPDATE)을 고친 PR 이 머지됐는데도 교착 알람이 계속 왔습니다. "수정했는데 안 고쳐진다"에서 시간을 썼는데, 운영 빌드를 확인해 보니 수정 전 커밋이었어요. 미배포였던 겁니다. STATUS 의 SQL 이 수정 뒤 코드에 더는 없는 문장이라는 걸 먼저 대조했다면 바로 알 수 있었어요. 배포 뒤에 남은 교착은 같은 패턴이 다른 테이블에서 난 것이었고, 그중 하나가 B 처럼 두 행을 서로 반대 순서로 잠그는 모양이었습니다. B 와 같은 모양이었어요.

하나 더 볼 것이 있어요. A 는 세 세션이 얽힌 교착인데 STATUS 에는 트랜잭션이 두 개만 나옵니다. 커밋해서 두 S 를 한꺼번에 풀어 준 트랜잭션 1940(접속 126)은 교착 순간 이미 끝났기 때문에 출력 어디에도 없어요. 교착을 촉발한 세 번째 요청이 있었는지는 STATUS 만으로는 알 수 없고, 5장의 대기 상태 기록이나 애플리케이션 로그로 확인해야 합니다.

STATUS 만 보고 내리기 쉬운 결론 세 가지

"SQL 줄이 FOR UPDATE 니까 FOR UPDATE 를 빼면 된다." A 에서 S 잠금은 FOR UPDATE 가 아니라 INSERT IGNORE 가 잡았어요. FOR UPDATE 를 빼도 바로 다음 문장인 UPDATE … WHERE user_key = 'u-1' 이 같은 유니크 인덱스 레코드에 X 를 요청합니다. 상대가 쥔 S 와 부딪히는 건 그대로예요. 고칠 곳은 X 를 요청하는 문장이 아니라 S 를 잡게 만든 흐름입니다.

"격리 수준을 READ COMMITTED 로 내리면 된다." 매뉴얼의 교착 개요(17.7.5)는 격리 수준이 바꾸는 것은 읽기 동작이고 교착은 쓰기 때문에 생기므로, 교착 가능성은 격리 수준의 영향을 받지 않는다고 적어요. 하지만 1편 실측에서는 격리 수준에 따라 교착이 생기기도 하고 사라지기도 했습니다. 행이 이미 있을 때 대리 키 테이블은 RR 에서 대기로 끝나던 것이 RC 에서 교착이 됐고, 행이 없을 때 FOR UPDATE 를 먼저 하는 판은 RR 에서 세 바퀴 모두 교착, RC 에서 0번이었어요. 같은 장의 대처법(17.7.5.3)은 잠그는 읽기를 쓴다면 READ COMMITTED 를 검토하라고 권하는데, 갭 잠금이 줄어들기 때문으로 보여요. 다만 A 패턴의 중복 키 S 잠금은 RC 에서도 잡히니 RC 는 해법이 아닙니다. 1편에서도 RC 는 A 패턴을 없애지 못했어요.

"교착은 재시도하면 끝이다." 매뉴얼도 교착은 위험하지 않으니 다시 시도하라고 적어요. 다만 A 같은 패턴은 첫 방문이 동시에 들어올 때마다 납니다. 1편 실측에서 행이 없을 때 세 요청이면 키 구조와 격리 수준에 상관없이 열두 번 모두 교착이 났어요. 재시도는 증상을 흡수할 뿐이라, 같은 SQL 이 STATUS 에 반복해서 나온다면 체크리스트로 구조를 고칠 대상이에요.

📖 용어: 희생자 (victim)
InnoDB 가 교착을 풀려고 롤백하는 트랜잭션이에요. 매뉴얼은 삽입, 갱신, 삭제한 행 수로 크기를 재서 작은 쪽을 고르려 한다고 적어요. STATUS 의 WE ROLL BACK TRANSACTION (N) 이 그것이고, 그 트랜잭션의 세션이 1213 을 받습니다. 1213 을 받은 뒤 트랜잭션이 어디까지 되돌아가는지는 5편에서 봐요.

STATUS 는 세 바퀴 모두 다음 교착에 덮어써졌고, innodb_print_all_deadlocks 만 켠 에러 로그는 기본 log_error_verbosity 2 에서 머리말, 소제목, 희생자 줄이 빠졌습니다. 교착 전 대기는 data_locks 로 볼 수 있지만, INSERT 한 행의 잠금은 THREAD_ID 가 기다리는 쪽으로 찍혀서 트랜잭션 번호로 주인을 찾아야 했어요. 원인은 배포된 코드의 SQL 인지, 잠금 종류, 인덱스, 레코드가 같은지 엇갈리는지 순서로 확정합니다.

교착 출력은 잠금이 어디서 엇갈렸는지를 보여 주지만, 그 잠금을 잡은 문장까지 보여 준다는 보장은 없습니다. 그 문장은 배포된 코드와 문장 이력에서 찾아야 해요.
