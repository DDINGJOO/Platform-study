1편. INSERT IGNORE 뒤 SELECT … FOR UPDATE에서 교착이 발생하는 조건 ← 지금 이 글

회원의 첫 방문 행을 만들고 방문 횟수를 갱신하는 코드를 예로 볼게요. 같은 회원의 행이 두 번 생기지 않도록 유니크 키를 두고, 중복이면 삽입을 건너뛰도록 INSERT IGNORE 를 써요. 이어서 같은 행을 SELECT … FOR UPDATE 로 잠근 뒤 방문 횟수를 고치는 순서예요. 첫 방문 요청 세 개가 동시에 이 코드를 실행하면 아래 교착 오류가 날 수 있어요.

ERROR 1213 (40001): Deadlock found when trying to get lock; try restarting transaction

→ 두 트랜잭션이 서로 보유한 잠금을 기다리면서 순환이 생겨 MySQL 이 한쪽 트랜잭션을 되돌렸다는 뜻이에요. 문장은 두 개이고 대상 행도 하나지만, 공유 잠금을 보유한 채 배타 잠금을 요청하면 교착이 생길 수 있어요. 당시에는 첫 방문 요청 세 개가 겹쳤고, INSERT IGNORE 다음에 같은 행을 SELECT … FOR UPDATE 로 조회한 것으로 파악했어요. 다만 운영 장애의 원본 로그와 요청 이력은 이번에 대조할 수 없어서, 아래에서는 로컬 실습으로 확인한 조건과 결과를 설명해요.

1편에서는 두 문장이 행 하나를 다루는데도 교착이 나는 조건을 MySQL 8.4 실습으로 살펴봐요. 이어지는 글에서는 ON DUPLICATE KEY UPDATE 의 반환값(2편), 교착 로그와 data_locks 분석(3편), 알람의 관찰 범위(4편), 1213 과 1205 의 롤백 범위(5편), "없으면 넣기"의 구현 선택지(6편), 동시성 테스트의 실행 여부(7편)를 다뤄요. 여기서는 세션을 순서대로 실행하고 data_locks 에 나타난 잠금을 비교할게요.

• 행이 이미 있을 때와 없을 때, 교착에 필요한 요청 수는 왜 다른가?
• READ COMMITTED 로 내리면 사라지나?

• 내 코드에서 무엇을 바꾸면 되나?

1. INSERT IGNORE 는 중복일 때도 잠금을 건다

먼저 잠금 두 종류부터 짚을게요.

📖 용어: 공유 잠금(S)과 배타 잠금(X)
여기서는 행 잠금을 공유 잠금(S)과 배타 잠금(X)으로 구분해요. 같은 레코드의 S 는 여러 트랜잭션이 함께 보유할 수 있어요. 다른 트랜잭션이 S 나 X 를 보유한 레코드의 X 요청은 기다려야 해요.

MySQL 8.4 매뉴얼의 InnoDB Locking 절은 이 규칙을 그대로 적어 둡니다. T1 이 행 r 에 S 를 쥐고 있을 때 다른 트랜잭션 T2 가 S 를 요청하면 바로 허용되고, X 를 요청하면 바로 허용되지 않아요(InnoDB Locking). SELECT … FOR UPDATE 와 UPDATE 는 찾은 행에 X 를 겁니다.

그럼 INSERT 는 중복을 만났을 때 무엇을 할까요. 매뉴얼의 Locks Set by Different SQL Statements 절에 답이 있습니다. "중복 키 오류가 나면 중복된 인덱스 레코드에 공유 잠금이 걸린다"고 적고, 바로 이어서 이 공유 잠금 때문에 여러 세션이 같은 행을 넣으려 할 때 교착이 날 수 있다고 경고해요(Locks Set by Different SQL Statements).

이 절에는 INSERT IGNORE 의 잠금 동작이 별도로 설명되어 있지 않아요. INSERT … ON DUPLICATE KEY UPDATE 는 중복이면 S 대신 X 를, REPLACE 는 X next-key 를 건다고 설명하지만 IGNORE 는 따로 구분하지 않아요. INSERT 문서의 IGNORE 설명도 "무시 가능한 오류를 무시하고, 중복 행은 버리고 경고를 남긴다"는 동작을 설명하며 잠금은 언급하지 않아요(INSERT Statement). 오류가 경고로 바뀐 뒤에도 잠금이 남는지 실습에서 확인했어요.

📖 용어: performance_schema.data_locks
지금 InnoDB 가 들고 있거나 기다리는 잠금을 한 행씩 보여 주는 테이블이에요. 어느 인덱스의 어느 값에(INDEX_NAME, LOCK_DATA), 어떤 모드로(LOCK_MODE), 받았는지 기다리는지(LOCK_STATUS)가 나옵니다. 어떤 잠금 때문에 요청이 기다리는지 확인할 때 사용해요.

실습에는 테이블 두 개를 사용했어요. (가)는 별도 기본 키인 대리 키와 보조 유니크 키를 두고, (나)는 member_id 를 기본 키로 사용해요. 둘 다 같은 회원 행의 중복을 막지만, 3장에서 보듯 잠금 동작에는 차이가 있었어요.

-- (가) first_visit: 대리 키 + 보조 유니크 키 CREATE TABLE first_visit ( id BIGINT AUTO_INCREMENT PRIMARY KEY, member_id BIGINT NOT NULL, visit_count INT NOT NULL DEFAULT 1, UNIQUE KEY uk_member (member_id) ); -- (나) first_visit_pk: member_id 가 기본 키 CREATE TABLE first_visit_pk (member_id BIGINT PRIMARY KEY, visit_count INT NOT NULL DEFAULT 1);

member_id = 1 행을 미리 넣어 두고, READ COMMITTED 세션에서 INSERT IGNORE 로 같은 값을 넣은 직후의 data_locks 입니다(레코드 잠금만 추렸어요).

S1> INSERT IGNORE INTO first_visit (member_id) VALUES (1); Query OK, 0 rows affected, 1 warning | sess | idx | mode | status | data | | S1 | uk_member | S | GRANTED | 1, 1 |

→ 0행이 들어갔고 경고 하나로 끝났지만, 중복이 난 유니크 인덱스 레코드(uk_member 의 값 1, 기본 키 1)에 S 를 받아 들고 있다는 뜻이에요. 이 S 는 문장이 끝나도 풀리지 않고 트랜잭션이 끝날 때까지 남습니다. INSERT IGNORE 는 오류를 경고로 바꿀 뿐, 중복 검사가 건 S 잠금은 그대로 남겨요. 모드가 S,REC_NOT_GAP 이 아니라 S 인 것도 눈여겨볼 만해요. 레코드와 그 앞 간격을 같이 잠그는 next-key 잠금이라는 뜻이고, READ COMMITTED 에서도 그렇습니다((나) 테이블처럼 기본 키에서 중복이 나면 S,REC_NOT_GAP, 레코드만 잠갔어요). 매뉴얼의 격리 수준 절이 READ COMMITTED 에서 갭 잠금은 "외래 키 제약 검사와 중복 키 검사에만" 쓰인다고 적은 그 예외예요(Transaction Isolation Levels).

2. S 를 쥔 채 X 로 올리려는 두 트랜잭션

두 번째 세션도 같은 삽입을 실행해요. READ COMMITTED 이거나 유니크 키가 기본 키인 테이블에서는 S 끼리 충돌하지 않아 S2 도 S 를 받아요. REPEATABLE READ 의 대리 키 테이블에서 달라지는 동작은 3장에서 살펴볼게요. 이 상태에서 두 세션이 다음 문장으로 같은 행의 X 를 요청하면 서로의 S 를 기다리게 돼요.

그림 1. 잠금을 올리려는 쪽이 둘이면, 각자 쥔 S 가 상대의 X 를 막는다 (RC 이거나 유니크 키가 기본 키일 때)
📖 용어: 잠금 업그레이드 (S→X)
이미 S 를 쥔 트랜잭션이 같은 행에 X 를 요청하는 것이에요. 자기 S 는 문제가 안 되지만 다른 트랜잭션의 S 가 하나라도 있으면 X 는 기다려야 합니다. 두 트랜잭션이 동시에 업그레이드하려 하면 서로의 S 가 서로를 막아요.

매뉴얼의 교착 예제(An InnoDB Deadlock Example)도 같은 구조예요. 예제에서는 SELECT … FOR SHARE 로 S 를 보유한 뒤 UPDATE 로 X 를 요청해요. 이번 실습에서는 INSERT IGNORE 가 FOR SHARE 대신 S 를 남겨요. 명시적인 잠금 조회가 없어도 공유 잠금을 보유하게 된다는 점을 아래 실행 화면에서 볼 수 있어요.

그림 2. READ COMMITTED, 대리 키 테이블. [04] 에서 S 가 둘, [05] 에서 S1 의 X 가 대기, [06] 에서 S2 가 1213

→ [04] 에서 같은 레코드에 S1 과 S2 의 S 가 나란히 GRANTED 예요. [05] 에서 S1 의 FOR UPDATE 가 X,REC_NOT_GAP 을 요청했고 S2 의 S 때문에 WAITING 입니다. [06] 에서 S2 도 X 를 요청하는 순간 순환이 생겨서 InnoDB 가 S2 를 되돌렸어요. S2 는 1213 을 받았고, 기다리던 S1 의 FOR UPDATE 는 그제야 끝났습니다. 교착 카운터(INNODB_METRICS 의 lock_deadlocks)도 1 올랐어요.

FOR UPDATE 대신 UPDATE … SET visit_count = visit_count + 1 을 써도 실습 결과는 같았어요. UPDATE 도 같은 행의 X 가 필요하기 때문이에요. 당시에는 1차 수정 뒤 다른 테이블에서도 INSERT IGNORE 다음에 UPDATE 하는 코드에서 교착이 남은 것으로 판단했어요. 다만 이 경위 역시 운영 원자료는 대조하지 못했어요. 실습으로 확인한 범위에서는 FOR UPDATE 조회뿐 아니라 뒤따르는 갱신도 함께 확인해야 해요.

3. 행이 이미 있을 때: 키 구조와 격리 수준에 따른 차이

행이 이미 있어도 키 구조와 격리 수준에 따라 결과가 달랐어요. 같은 순서를 두 테이블과 두 격리 수준에서 세 번씩 반복했어요.

(행 member_id = 1 이 있다. 두 요청. 칸 = 세 바퀴 중 1213 이 난 횟수) (가) = 대리 키 + 보조 유니크 키, (나) = member_id 가 기본 키 RR (가) RR (나) RC (가) RC (나) INSERT IGNORE → FOR UPDATE 0/3 (대기) 3/3 3/3 3/3 INSERT IGNORE → UPDATE 0/3 (대기) 3/3 3/3 3/3

→ 실습한 네 조합 중 기본 격리 수준인 REPEATABLE READ 의 대리 키 테이블(가)에서만 교착이 나지 않았어요. 이때의 잠금 대기를 data_locks 에서 확인할 수 있어요.

REPEATABLE READ, first_visit (가). S1 의 INSERT IGNORE(중복) 직후 | sess | idx | mode | status | data | | S1 | PRIMARY | X | GRANTED | supremum pseudo-record | | S1 | uk_member | S | GRANTED | 1, 1 | S2 의 INSERT IGNORE 직후 | S2 | PRIMARY | X,INSERT_INTENTION | WAITING | supremum pseudo-record |

→ RR 에서는 중복 난 INSERT IGNORE 가 유니크 인덱스의 S 말고도 기본 키 인덱스 맨 끝(supremum, 인덱스의 마지막 값보다 큰 자리를 나타내는 가상 레코드)에 X 를 하나 더 남겼어요. supremum 은 실제 레코드가 아니라서, 여기 걸린 잠금은 인덱스의 가장 큰 값 뒤 간격만 막습니다(InnoDB Locking 의 Next-Key Locks 절). 즉 레코드를 독점하는 잠금이 아니라 "새 행을 맨 끝에 넣는 것"만 막는 간격 잠금이에요. 매뉴얼은 간격 잠금끼리는 충돌하지 않고 함께 쥘 수 있다고 적는데, 실제로 4장의 [07] 에서는 S2 와 S3 가 같은 supremum X 를 동시에 GRANTED 로 쥐고 있었습니다. 중복 난 INSERT IGNORE 가 왜 이 잠금을 남기는지는 매뉴얼에 없어서, 여기서는 MySQL 8.4.11 과 이 스키마에서 관찰한 사실로만 적어요. AUTO_INCREMENT 로 만든 새 id 는 늘 맨 끝에 들어가니, S2 의 INSERT IGNORE 는 중복 검사에 닿기도 전에 그 자리에 넣으려다 막혔습니다(X,INSERT_INTENTION 대기). S2 가 S 를 받지 못하니 S→X 를 올리려는 쪽이 하나뿐이고, 교착 대신 S1 이 커밋할 때까지 줄을 서는 것으로 끝났어요.

📖 용어: insert intention 잠금
INSERT 가 행을 넣기 직전에 "이 간격에 넣겠다"고 거는 갭 잠금의 한 종류예요. 같은 간격의 다른 위치에 넣는 INSERT 끼리는 서로 기다리지 않지만, 누가 그 간격에 갭 잠금이나 next-key 잠금을 쥐고 있으면 기다립니다.

이 결과를 RR 에서 교착이 나지 않는다는 뜻으로 일반화할 수는 없어요. (나)처럼 유니크 키가 기본 키인 테이블에서는 RR 에서도 교착이 났고, 중복 검사가 기본 키에서 일어나 supremum 잠금은 생기지 않았어요. 또 다음 장의 행이 없는 경우에는 (가)도 RR 에서 교착이 나요. supremum 잠금이 다른 회원의 삽입에도 영향을 주는지 보려고, S1 의 중복 INSERT IGNORE 가 커밋되기 전에 S2 가 다른 회원(member_id = 2)을 삽입하는 경우도 확인했어요.

(행 member_id = 1 이 있다. S1 이 1 을 INSERT IGNORE 하고 커밋하기 전에, S2 가 2 를 넣는다) RR (가) RR (나) RC (가) RC (나) S2 의 INSERT IGNORE S1 커밋까지 대기 (3/3) 바로 끝 바로 끝 바로 끝

→ RR 의 (가) 테이블에서는 다른 회원의 첫 방문 삽입도 S1 이 커밋할 때까지 기다렸어요(X,INSERT_INTENTION 이 supremum 에서 WAITING). 실습에서는 S1 이 1초 뒤에 커밋했고 대기는 1.1초였어요. 이 스키마에서 같은 위치에 삽입하는 요청은 S1 의 잠금이 유지되는 동안 기다릴 수 있어요. 이 결과만으로 실제 서비스의 모든 INSERT 가 대기한다고 단정할 수는 없어요.

다른 키를 넣는 세션까지 기다리는 현상은 MySQL 버그 게시판에도 보고되어 있어요. 5.7 에서 8.0.28 로 올린 뒤 INSERT IGNORE 일괄 적재 중 다른 세션들이 잠금 대기 시간 초과로 실패했다는 내용이에요(Bug #116459). 첫 세션은 기존 sku 를 INSERT IGNORE 했고 둘째 세션은 다른 sku 를 넣었는데, 첫 세션의 잠금 목록에 "유니크 인덱스 S + 기본 키 supremum X" 가 있었어요. 글에서 인용한 상태는 Not a Bug 예요. 답변에서는 IGNORE 여부와 관계없이 잠금을 지켜야 하고 lock_wait_timeout 을 조정할 수 있지만, InnoDB 를 트랜잭션 없는 엔진처럼 바꾸는 플래그는 없다고 설명했어요. 교착이 나지 않는 경우에도 다른 키의 삽입 대기는 별도로 확인해야 해요.

4. 행이 없을 때: 세 요청으로 교착이 생기는 순서

첫 방문은 행이 없는 상태에서 시작해요. 이때는 먼저 도착한 S1 의 INSERT IGNORE 가 실제로 행을 넣습니다. S2 와 S3 는 중복을 보고 S 를 요청하는데, 그 행은 S1 이 아직 커밋하지 않은 새 행이라 기다려요.

📖 용어: 암묵 잠금 (implicit lock)
흔히 이렇게 부르는 InnoDB 의 내부 동작인데, 이 글이 인용한 매뉴얼 절들에는 설명이 없어서 data_locks 에서 보인 모습만 적어요. S1 이 혼자 행을 넣은 직후 data_locks 에는 레코드 잠금이 하나도 없었고, S2 가 같은 값을 넣으려 하자 그제야 S1 몫의 X,REC_NOT_GAP 이 나타났습니다. 새 행의 잠금이 "다른 트랜잭션이 부딪칠 때" 비로소 목록에 드러난다는 뜻이에요.

(1) (대기) | S1 | uk_member | X,REC_NOT_GAP | GRANTED | 1, 1 | | S2 | uk_member | S | WAITING | 1, 1 | [06] S3> INSERT IGNORE ... (1) (대기) | S3 | uk_member | S | WAITING | 1, 1 | [07] S1> COMMIT; S2, S3: Query OK, 0 rows affected, 1 warning | S2 | uk_member | S | GRANTED | 1, 1 | | S3 | uk_member | S | GRANTED | 1, 1 | [08] S2> SELECT ... FOR UPDATE (대기: X,REC_NOT_GAP WAITING) [09] S3> SELECT ... FOR UPDATE ERROR 1213 (40001): Deadlock found ...

→ S1 이 커밋하자 기다리던 S2 와 S3 의 S 요청이 함께 허용됐어요. 둘 다 S 를 보유한 채 FOR UPDATE 로 넘어가면서 2장과 같은 순환이 생겼어요. 이 실습 순서에서는 먼저 삽입하는 요청 하나와 S 를 함께 받을 대기자 둘, 모두 세 요청으로 교착을 재현했어요. 당시 파악한 "첫 방문 동시 요청 3개"와 요청 수는 같지만, 이 일치만으로 운영 장애의 원인을 확정할 수는 없어요.

그림 3. S1 종료 후 S2 와 S3 의 S 요청이 함께 허용돼요. 커밋 뒤에는 FOR UPDATE, 롤백 뒤에는 INSERT 에서 교착이 났어요

S1 이 커밋 대신 롤백하면 더 짧아집니다. 매뉴얼 locks-set 절의 세 세션 예제가 이 경우예요. 행이 사라졌으니 S 를 받은 S2 와 S3 가 둘 다 행을 넣으려 하고, 넣으려면 X 가 필요한데 서로의 S 에 막혀요. 실습에서도 FOR UPDATE 한 줄 없이, 롤백 직후 S3 의 INSERT IGNORE 자체가 1213 을 받았고 S2 가 행을 넣었습니다. IGNORE 가 있어도 교착은 무시되지 않아요. 교착은 "무시 가능한 오류"가 아니고, 받은 쪽 트랜잭션은 통째로 되돌려집니다(롤백 범위는 5편에서 다뤄요).

대조군으로 요청을 두 개만 보내 봤어요. 커밋이든 롤백이든 S 를 받는 대기자가 하나뿐이라 교착은 없었습니다.

(행이 없다. 칸 = 세 바퀴 중 1213 이 난 횟수) RR (가) RR (나) RC (가) RC (나) 세 요청, S1 COMMIT 뒤 FOR UPDATE 3/3 3/3 3/3 3/3 세 요청, S1 ROLLBACK (그 뒤 문장 없음) 3/3 3/3 3/3 3/3 두 요청, S1 COMMIT 뒤 FOR UPDATE 0/3 0/3 0/3 0/3 두 요청, S1 ROLLBACK 0/3 0/3 0/3 0/3

→ 행이 없는 경우에는 실습한 키 구조와 격리 수준 모두에서 같은 결과가 나왔어요. 세 요청에서는 커밋과 롤백 시나리오 각각 열두 번, 합계 스물네 번 모두 교착이 났고, 두 요청에서는 한 번도 나지 않았어요. 1213 을 받은 세션도 같았어요. 커밋 시나리오에서는 마지막에 FOR UPDATE 를 보낸 S3 가, 롤백 시나리오에서는 S3 의 INSERT IGNORE 가 오류를 받았고 S2 가 행을 넣었어요. 이 실행 순서의 교착을 확인하려면 두 스레드만으로 테스트해서는 부족해요.

5. READ COMMITTED 로 내리면 사라지나

READ COMMITTED 는 갭 잠금을 대부분 사용하지 않지만, 위에서 본 S→X 업그레이드 교착은 남았어요. 같은 레코드의 공유 잠금과 배타 잠금이 충돌하고, 중복 검사에서 생긴 S 는 RC 에서도 유지되기 때문이에요. 격리 수준별 실습 결과를 모으면 다음과 같아요.

(교착 시나리오 네 개 x 테이블 두 개 = 여덟 조합, 각 세 바퀴) RR RC 1213 이 난 조합 6 / 8 8 / 8 RR 에서 빠진 두 조합: (가) 테이블의 "행이 있을 때" 두 시나리오. 교착 대신 대기로 바뀌었다

→ RC 에서도 이 패턴의 교착이 났어요. (가)의 행이 있는 경우에는 RR 에서 대기하던 순서가 RC 에서는 교착으로 이어졌어요. 이 실습에서 RC 는 supremum X 를 남기지 않아 S2 도 S 를 받았기 때문이에요. 따라서 격리 수준만 바꾸기보다 같은 트랜잭션에서 S 를 보유한 뒤 X 를 요청하는 순서를 함께 검토해야 해요.

6. 행이 있을 때 비교한 세 가지 수정 방법

행이 있는 경우의 S→X 업그레이드를 줄이려고 세 가지 방법을 비교했어요. 처음부터 X 를 요청하거나, S 를 보유한 트랜잭션에서 X 를 요청하지 않도록 바꾸는 방법이에요.

그림 4. 행이 있을 때 S→X 업그레이드를 피하는 세 방법과 각각의 제약

① 처음부터 X: SELECT … FOR UPDATE 먼저

BEGIN; SELECT member_id, visit_count FROM first_visit WHERE member_id = ? FOR UPDATE; -- 있으면 UPDATE first_visit SET visit_count = visit_count + 1 WHERE member_id = ?; -- 없으면 INSERT (아래 주의) COMMIT;

행이 있으면 첫 FOR UPDATE 가 X 를 받고, 두 번째 세션은 S 를 거치지 않고 X 를 기다려요. 이 순서에서는 S→X 업그레이드로 인한 순환이 생기지 않았어요. 실습에서는 행이 있을 때 RR, RC 와 두 테이블의 네 조합 모두 세 번의 반복에서 1213 이 0 이었어요.

⚠️ 주의: 행이 없으면 ① 도 교착이 난다
없는 행에 FOR UPDATE 를 걸면 RR 에서는 레코드가 없으니 그 자리의 간격에 갭 잠금이 걸려요. 갭 잠금은 여러 트랜잭션이 동시에 쥘 수 있어서 둘 다 통과하고, 이어지는 두 INSERT 의 insert intention 이 서로의 갭 잠금에 막힙니다. 실습에서 행이 없는 상태에서 두 요청이 FOR UPDATE 다음 INSERT 를 하자 RR 에서는 두 테이블 모두 세 바퀴 내내 1213 이 났고, RC 에서는 갭 잠금이 없어 나지 않았어요. "없으면 넣기"를 교착 없이 짜는 방법은 6편에서 따로 다뤄요.

② 같은 트랜잭션에서 그 행을 잠그지 않는다

INSERT IGNORE 는 그대로 두고 그 뒤에 그 행을 잠그지 않습니다. 넣었는지는 영향받은 행 수(1 이면 새로 넣음, 0 이면 이미 있음)로 판정하고(단 IGNORE 는 중복 말고도 무시 가능한 다른 오류를 경고로 바꾸니, 0 일 때 경고가 정말 중복인지 SHOW WARNINGS 로 한 번 확인하세요), 읽어야 하면 잠그지 않는 일반 SELECT 로 읽어요. 일반 SELECT 는 스냅숏을 읽는 일관된 읽기라 잠금을 요청하지 않습니다. 실습에서 이 방법도 행이 있을 때 네 조합 모두 세 바퀴 내내 1213 이 0 이었습니다. S 두 개가 공존할 뿐 누구도 X 를 요청하지 않으니까요. 대신 그 트랜잭션 안에서 그 행을 고쳐야 한다면 이 방법은 쓸 수 없어요. UPDATE 가 다시 X 를 요청하니까요(2장의 exists-2s-update).

실습의 mysql 클라이언트에서는 중복이면 0 rows affected, 1 warning, 새로 넣으면 1 row affected 였어요. 앱에서는 JDBC 의 executeUpdate() 반환값으로 받는데, 반환값의 뜻은 드라이버 설정에 따라 달라질 수 있으니 자기 드라이버에서 한 번 찍어 보고 쓰세요. 같은 생각으로 ON DUPLICATE KEY UPDATE 의 반환값을 쓰다가 판정이 깨지는 이야기가 2편이에요.

③ 트랜잭션을 나눈다

INSERT IGNORE 만 실행하는 짧은 트랜잭션을 먼저 커밋해 S 를 해제하고, 새 트랜잭션에서 FOR UPDATE 와 UPDATE 를 실행해요. 두 번째 트랜잭션은 ① 과 같은 순서가 돼요. 실습에서는 행이 있을 때 네 조합 모두 1213 이 0 이었어요. 다만 삽입과 갱신을 하나의 원자적 작업으로 처리할 수 없어요. 두 트랜잭션 사이에 앱이 종료되면 행만 생기고 갱신은 누락될 수 있어요. 뒤 단계를 재실행해도 같은 결과가 되도록 설계한 경우에 사용할 수 있어요.

세 방법의 수치는 모두 "행이 이미 있을 때"의 결과예요. 행이 없고 첫 삽입자가 커밋하는 세 요청의 ②, ③ 과 ① 의 세 요청, 첫 삽입자 롤백 경우는 이 실습에서 실행하지 않았어요. ① 의 행 없음 조건은 위 주의 상자에 적은 두 요청만 확인했어요.

⚠️ 주의: 첫 삽입자가 롤백하는 경우는 ②, ③ 도 못 막는다
4장의 롤백 시나리오는 INSERT IGNORE 세 개만으로 교착이 났어요. ② 와 ③ 의 첫 단계가 바로 그 모양입니다. 먼저 삽입한 요청이 다른 이유로 롤백할 가능성도 고려해야 해요. 그래서 고친 뒤에도 1213 을 받으면 트랜잭션 전체를 다시 시도하는 처리가 필요합니다(5편).

7. 실습 돌려 보기

MySQL 8.4 컨테이너 하나와 표준 라이브러리만 쓰는 파이썬 스크립트 하나예요. 스크립트가 mysql 클라이언트 세션을 두세 개 열어 두고, 정해진 순서로 한 문장씩 보낸 뒤 1초 기다려 data_locks 를 찍습니다. 1초 안에 끝나지 않은 문장은 "잠금 대기"로 표시해요.

git clone https://github.com/DDINGJOO/Platform-study.git cd Platform-study/labs/db/dl-01-insert-ignore-upgrade ./scripts/run_all.sh # MySQL(127.0.0.1:39010) + 시나리오 전부, 세 바퀴 python3 scripts/sessions.py exists-2s RC # 하나만 단계별로 docker compose down -v

저장된 실행 기록은 MySQL 8.4.11 공식 이미지의 기본 설정(교착 감지 켜짐, innodb_lock_wait_timeout 50초)과 Docker 29.5.3 환경이에요(results/env.txt). 시나리오 열한 개 x 격리 수준 두 개 x 테이블 두 개를 세 번씩, 모두 132번 실행했고 같은 조합의 세 번 결과는 같았어요. 교착 수는 information_schema.INNODB_METRICS 의 lock_deadlocks 로 셌어요. 8.4.11 에서 SHOW GLOBAL STATUS LIKE 'Innodb_deadlocks' 는 빈 결과였어요(results/counters.txt). 코드는 labs/db/dl-01-insert-ignore-upgrade, 실행별 결과는 results/summary.txt 에 있어요. 이번 편집에서는 이 저장된 자료를 대조했으며 실습을 새로 실행하지는 않았어요.

💡 내 코드에서 바꿀 것
• INSERT IGNORE 를 찾고, 같은 트랜잭션 안에서 그 행에 FOR UPDATE, UPDATE, DELETE 가 뒤따르는지 보세요. JPA 라면 비관적 쓰기 잠금 조회(@Lock(PESSIMISTIC_WRITE))와 더티 체킹이 만드는 UPDATE 도 같은 것이니 SQL 로그로 확인하세요
• 행이 있을 때만 생각하지 말고 행이 없을 때 세 요청이 겹치는 경우로 테스트하세요. 두 요청짜리 동시성 테스트는 "없을 때" 교착을 재현하지 못합니다
• 격리 수준을 내리는 것으로 끝내지 마세요. RC 에서도 네 경우 모두 1213 이 났습니다
• 고칠 때는 ① 처음부터 X, ② 잠그지 않기, ③ 트랜잭션 나누기 중 하나를 고르고, 행이 없을 때와 첫 삽입자가 롤백할 때는 따로 대비하세요(6편, 5편)
• RR 의 대리 키 테이블에서 교착이 안 보인다면, 대신 다른 행의 INSERT 까지 줄 세우는 supremum 대기가 있는지 data_locks 로 확인하세요
• 수정 코드가 운영 빌드에 포함됐는지도 확인하세요. 저는 수정 PR 이 머지된 뒤에도 이전 커밋이 운영 중인 것으로 파악한 적이 있어요. 다만 이번에 배포 이력 원자료까지 대조하지는 못했어요
✍️ 확인한 결과와 적용 범위
INSERT IGNORE 는 중복 오류를 경고로 바꾸지만, 이번 실습에서는 중복 인덱스 레코드의 S 잠금이 트랜잭션 종료까지 남았어요. 그 S 를 보유한 두 세션이 같은 행에 FOR UPDATE 나 UPDATE 로 X 를 요청하면 교착이 생겼어요.

행이 있으면 키 구조와 격리 수준에 따라 두 요청이 교착이나 대기로 이어졌고, 행이 없으면 세 요청으로 교착을 재현했어요. READ COMMITTED 로 바꿔도 교착은 남았어요.

행이 있는 조건에서는 세 수정 방법 모두 교착이 나지 않았어요. 행이 없거나 첫 삽입자가 롤백하는 조건은 별도로 검토해야 해요. 저장된 실습 결과만으로 운영 장애의 원인이나 수정 완료를 입증할 수는 없어요.
