7편. 동시성 테스트가 통과한 게 아니라 실행되지 않았을 때

회원이 처음 들어오면 "첫 방문" 행을 하나 만드는 코드가 있습니다. 같은 회원 행이 두 번 생기면 안 되니 유니크 키를 걸고, 중복이면 조용히 넘어가도록 INSERT IGNORE 를 씁니다. 바로 다음 줄에서는 그 행을 SELECT … FOR UPDATE 로 잠그고 방문 횟수를 고쳐요. 테스트도 통과하고 한동안 잘 돕니다. 그러다 같은 회원의 첫 방문 요청이 세 개 동시에 들어오고, 그날부터 로그에 이 줄이 찍혀요.

ERROR 1213 (40001): Deadlock found when trying to get lock; try restarting transaction

→ 두 트랜잭션이 서로가 쥔 잠금을 기다려서 MySQL 이 한쪽을 강제로 되돌렸다는 뜻이에요. 이상한 점은 문장이 두 개뿐이라는 것입니다. 잠그는 행도 하나예요. 두 행을 서로 반대 순서로 잠근 것도 아닌데 교착이 납니다. 제 회사에서 겪은 첫 교착이 정확히 이 모양이었어요. 첫 방문 요청 세 개가 동시에 들어왔고, 코드는 INSERT IGNORE 다음 같은 행에 SELECT … FOR UPDATE 였습니다.

이 시리즈는 이 교착을 만난 개발자가 차례로 묻게 되는 질문에 한 편씩 답합니다. 왜 문장 두 개, 행 하나로 교착이 나나(1편)? ON DUPLICATE KEY UPDATE 로 바꾸면 되나(2편)? 교착 로그와 data_locks 로 원인을 어떻게 확정하나(3편)? 알람이 멈추면 교착도 끝난 건가(4편)? 1213 과 1205 는 각각 무엇을 되돌리나(5편)? "없으면 넣기"를 교착 없이 어떻게 짜나(6편)? 동시성 테스트가 통과했다는 결과를 믿어도 되나(7편)? 이 글은 첫 질문을 MySQL 8.4 에서 세션을 하나씩 움직이며 data_locks 로 확인합니다.

1. INSERT IGNORE 는 중복일 때도 잠금을 건다

먼저 잠금 두 종류부터 짚을게요.

📖 용어: 공유 잠금(S)과 배타 잠금(X)
InnoDB 의 행 잠금은 두 종류예요. S 는 "이 행을 읽는 동안 아무도 고치지 마라", X 는 "이 행을 고치거나 지울 테니 아무도 건드리지 마라"입니다. 한 행에 S 는 여러 트랜잭션이 동시에 가질 수 있지만, 누가 S 를 쥐고 있으면 다른 트랜잭션의 X 요청은 바로 받아들여지지 않아요.

MySQL 8.4 매뉴얼의 InnoDB Locking 절은 이 규칙을 그대로 적어 둡니다. T1 이 행 r 에 S 를 쥐고 있을 때 다른 트랜잭션 T2 가 S 를 요청하면 바로 허용되고, X 를 요청하면 바로 허용되지 않아요(InnoDB Locking). SELECT … FOR UPDATE 와 UPDATE 는 찾은 행에 X 를 겁니다.

그럼 INSERT 는 중복을 만났을 때 무엇을 할까요. 매뉴얼의 Locks Set by Different SQL Statements 절에 답이 있습니다. "중복 키 오류가 나면 중복된 인덱스 레코드에 공유 잠금이 걸린다"고 적고, 바로 이어서 이 공유 잠금 때문에 여러 세션이 같은 행을 넣으려 할 때 교착이 날 수 있다고 경고해요(Locks Set by Different SQL Statements).

문제는 같은 절 어디에도 INSERT IGNORE 가 나오지 않는다는 점입니다. INSERT … ON DUPLICATE KEY UPDATE 는 중복이면 S 가 아니라 X 를 건다고, REPLACE 는 X next-key 를 건다고 따로 적혀 있는데 IGNORE 는 없어요. INSERT 문서의 IGNORE 설명도 "무시 가능한 오류를 무시하고, 중복 행은 버리고 경고를 남긴다"까지만 말하고 잠금 이야기는 하지 않습니다(INSERT Statement). 그래서 "오류를 안 내니까 잠금도 안 걸겠지"라고 읽기 쉬워요. 직접 확인했습니다.

📖 용어: performance_schema.data_locks
지금 InnoDB 가 들고 있거나 기다리는 잠금을 한 행씩 보여 주는 테이블이에요. 어느 인덱스의 어느 값에(INDEX_NAME, LOCK_DATA), 어떤 모드로(LOCK_MODE), 받았는지 기다리는지(LOCK_STATUS)가 나옵니다. 교착을 "추측"이 아니라 "관찰"로 확정할 때 쓰는 도구예요.

실습 테이블은 이렇게 생겼어요. 흔한 모양인 대리 키 + 보조 유니크 키(가)와, member_id 가 곧 기본 키인 모양(나) 두 개를 같은 뜻으로 만들었습니다. 왜 둘인지는 3장에서 나와요.

-- (가) first_visit: 대리 키 + 보조 유니크 키 CREATE TABLE first_visit ( id BIGINT AUTO_INCREMENT PRIMARY KEY, member_id BIGINT NOT NULL, visit_count INT NOT NULL DEFAULT 1, UNIQUE KEY uk_member (member_id) ); -- (나) first_visit_pk: member_id 가 기본 키 CREATE TABLE first_visit_pk (member_id BIGINT PRIMARY KEY, visit_count INT NOT NULL DEFAULT 1);

member_id = 1 행을 미리 넣어 두고, READ COMMITTED 세션에서 INSERT IGNORE 로 같은 값을 넣은 직후의 data_locks 입니다(레코드 잠금만 추렸어요).

S1> INSERT IGNORE INTO first_visit (member_id) VALUES (1); Query OK, 0 rows affected, 1 warning | sess | idx | mode | status | data | | S1 | uk_member | S | GRANTED | 1, 1 |

→ 0행이 들어갔고 경고 하나로 끝났지만, 중복이 난 유니크 인덱스 레코드(uk_member 의 값 1, 기본 키 1)에 S 를 받아 들고 있다는 뜻이에요. 이 S 는 문장이 끝나도 풀리지 않고 트랜잭션이 끝날 때까지 남습니다. INSERT IGNORE 는 오류를 경고로 바꿀 뿐, 중복 검사가 건 S 잠금은 그대로 남겨요. 모드가 S,REC_NOT_GAP 이 아니라 S 인 것도 눈여겨볼 만해요. 레코드와 그 앞 간격을 같이 잠그는 next-key 잠금이라는 뜻이고, READ COMMITTED 에서도 그렇습니다((나) 테이블처럼 기본 키에서 중복이 나면 S,REC_NOT_GAP, 레코드만 잠갔어요). 매뉴얼의 격리 수준 절이 READ COMMITTED 에서 갭 잠금은 "외래 키 제약 검사와 중복 키 검사에만" 쓰인다고 적은 그 예외예요(Transaction Isolation Levels).

2. S 를 쥔 채 X 로 올리려는 두 트랜잭션

이제 두 번째 세션이 같은 일을 합니다. READ COMMITTED 이거나 유니크 키가 곧 기본 키인 테이블이라면, S 끼리는 서로 막지 않으니 S2 도 바로 S 를 받아요(REPEATABLE READ 의 대리 키 테이블에서는 다른 일이 생기는데, 3장에서 봅니다). 여기까지는 둘 다 아무 문제가 없습니다. 문제는 둘 다 다음 줄에서 그 행에 X 를 요청한다는 거예요.

그림 1. 잠금을 올리려는 쪽이 둘이면, 각자 쥔 S 가 상대의 X 를 막는다 (RC 이거나 유니크 키가 기본 키일 때)
📖 용어: 잠금 업그레이드 (S→X)
이미 S 를 쥔 트랜잭션이 같은 행에 X 를 요청하는 것이에요. 자기 S 는 문제가 안 되지만 다른 트랜잭션의 S 가 하나라도 있으면 X 는 기다려야 합니다. 두 트랜잭션이 동시에 업그레이드하려 하면 서로의 S 가 서로를 막아요.

매뉴얼의 교착 예제(An InnoDB Deadlock Example)도 같은 구조예요. 거기서는 SELECT … FOR SHARE 로 S 를 잡고 UPDATE 로 X 를 요청합니다. 우리 코드에서는 INSERT IGNORE 가 FOR SHARE 자리에 들어간 셈인데, 코드만 보면 S 를 잡는 줄이 없어 보인다는 점이 다릅니다. 실제로 돌린 화면이에요.

그림 2. READ COMMITTED, 대리 키 테이블. [04] 에서 S 가 둘, [05] 에서 S1 의 X 가 대기, [06] 에서 S2 가 1213

→ [04] 에서 같은 레코드에 S1 과 S2 의 S 가 나란히 GRANTED 예요. [05] 에서 S1 의 FOR UPDATE 가 X,REC_NOT_GAP 을 요청했고 S2 의 S 때문에 WAITING 입니다. [06] 에서 S2 도 X 를 요청하는 순간 순환이 생겨서 InnoDB 가 S2 를 되돌렸어요. S2 는 1213 을 받았고, 기다리던 S1 의 FOR UPDATE 는 그제야 끝났습니다. 교착 카운터(INNODB_METRICS 의 lock_deadlocks)도 1 올랐어요.

FOR UPDATE 대신 UPDATE … SET visit_count = visit_count + 1 을 써도 결과는 같았습니다. UPDATE 도 그 행에 X 가 필요하니까요. 제 회사에서도 1차 수정 뒤 남은 교착은 같은 패턴이 다른 테이블에서 난 것이었고, 그쪽은 INSERT IGNORE 다음에 그 행을 UPDATE 하는 코드였어요. FOR UPDATE 만 찾아 고치면 이런 곳이 남습니다.

3. 행이 이미 있을 때: 두 요청이면 충분하다, 단 키 구조와 격리 수준에 따라

"행이 이미 있으면 동시 요청 두 개로 교착"이라고 정리하고 넘어가고 싶지만, 실습에서 반례가 나왔어요. 같은 순서를 두 테이블, 두 격리 수준에서 세 바퀴씩 돌렸습니다.

(행 member_id = 1 이 있다. 두 요청. 칸 = 세 바퀴 중 1213 이 난 횟수) (가) = 대리 키 + 보조 유니크 키, (나) = member_id 가 기본 키 RR (가) RR (나) RC (가) RC (나) INSERT IGNORE → FOR UPDATE 0/3 (대기) 3/3 3/3 3/3 INSERT IGNORE → UPDATE 0/3 (대기) 3/3 3/3 3/3

→ 기본 격리 수준인 REPEATABLE READ 의 대리 키 테이블(가)에서만 교착이 나지 않았다는 뜻이에요. 이유는 data_locks 에 그대로 나옵니다.

REPEATABLE READ, first_visit (가). S1 의 INSERT IGNORE(중복) 직후 | sess | idx | mode | status | data | | S1 | PRIMARY | X | GRANTED | supremum pseudo-record | | S1 | uk_member | S | GRANTED | 1, 1 | S2 의 INSERT IGNORE 직후 | S2 | PRIMARY | X,INSERT_INTENTION | WAITING | supremum pseudo-record |

→ RR 에서는 중복 난 INSERT IGNORE 가 유니크 인덱스의 S 말고도 기본 키 인덱스 맨 끝(supremum, 인덱스의 마지막 값보다 큰 자리를 나타내는 가상 레코드)에 X 를 하나 더 남겼어요. supremum 은 실제 레코드가 아니라서, 여기 걸린 잠금은 인덱스의 가장 큰 값 뒤 간격만 막습니다(InnoDB Locking 의 Next-Key Locks 절). 즉 레코드를 독점하는 잠금이 아니라 "새 행을 맨 끝에 넣는 것"만 막는 간격 잠금이에요. 매뉴얼은 간격 잠금끼리는 충돌하지 않고 함께 쥘 수 있다고 적는데, 실제로 4장의 [07] 에서는 S2 와 S3 가 같은 supremum X 를 동시에 GRANTED 로 쥐고 있었습니다. 중복 난 INSERT IGNORE 가 왜 이 잠금을 남기는지는 매뉴얼에 없어서, 여기서는 MySQL 8.4.11 과 이 스키마에서 관찰한 사실로만 적어요. AUTO_INCREMENT 로 만든 새 id 는 늘 맨 끝에 들어가니, S2 의 INSERT IGNORE 는 중복 검사에 닿기도 전에 그 자리에 넣으려다 막혔습니다(X,INSERT_INTENTION 대기). S2 가 S 를 받지 못하니 S→X 를 올리려는 쪽이 하나뿐이고, 교착 대신 S1 이 커밋할 때까지 줄을 서는 것으로 끝났어요.

📖 용어: insert intention 잠금
INSERT 가 행을 넣기 직전에 "이 간격에 넣겠다"고 거는 갭 잠금의 한 종류예요. 같은 간격의 다른 위치에 넣는 INSERT 끼리는 서로 기다리지 않지만, 누가 그 간격에 갭 잠금이나 next-key 잠금을 쥐고 있으면 기다립니다.

이걸 "RR 이면 안전하다"로 읽으면 안 돼요. 세 가지 이유가 있습니다. 첫째, (나)처럼 유니크 키가 곧 기본 키인 테이블은 RR 에서도 교착이 났어요. 그쪽은 중복 검사가 기본 키에서 일어나 supremum 잠금이 생기지 않았습니다. 둘째, 다음 장에서 보듯 행이 없을 때는 (가)도 RR 에서 교착이 납니다. 셋째, 그 supremum X 는 같은 회원만 막지 않아요. 곁가지로 S1 의 중복 INSERT IGNORE 가 커밋되기 전에 S2 가 다른 회원(member_id = 2)을 넣어 봤습니다.

(행 member_id = 1 이 있다. S1 이 1 을 INSERT IGNORE 하고 커밋하기 전에, S2 가 2 를 넣는다) RR (가) RR (나) RC (가) RC (나) S2 의 INSERT IGNORE S1 커밋까지 대기 (3/3) 바로 끝 바로 끝 바로 끝

→ RR 의 (가) 테이블에서는 전혀 다른 회원의 첫 방문도 S1 이 커밋할 때까지 기다렸어요(X,INSERT_INTENTION 이 supremum 에서 WAITING). 실습은 S1 이 1초 뒤에 커밋해서 대기가 1.1초였지만, 실제 서비스에서는 S1 의 트랜잭션이 길수록 그만큼 그 테이블의 모든 INSERT 가 줄을 섭니다.

이 "다른 키를 넣는데도 기다린다"는 모양이 MySQL 버그 게시판에도 올라와 있어요. 5.7 에서 8.0.28 로 올린 뒤 INSERT IGNORE 일괄 적재 중에 다른 세션들이 잠금 대기 시간 초과로 실패한다는 보고(Bug #116459)입니다. 보고자의 첫 세션은 이미 있는 sku 를 INSERT IGNORE 했고 둘째 세션은 다른 sku 를 넣었는데, 첫 세션의 잠금 목록이 위와 같은 "유니크 인덱스 S + 기본 키 supremum X" 였어요. 상태는 Not a Bug 입니다. 답변은 IGNORE 여부와 상관없이 모든 잠금은 지켜져야 하고 lock_wait_timeout 은 조정할 수 있다는 것, InnoDB 를 트랜잭션 없는 엔진 같은 다른 것으로 바꾸는 플래그는 없다는 것이었어요. 교착이 대기로 바뀐 것뿐이고, 그 대기가 테이블의 모든 새 행으로 번질 수 있습니다.

4. 행이 없을 때: 세 번째 요청이 필요하다

첫 방문은 행이 없는 상태에서 시작해요. 이때는 먼저 도착한 S1 의 INSERT IGNORE 가 실제로 행을 넣습니다. S2 와 S3 는 중복을 보고 S 를 요청하는데, 그 행은 S1 이 아직 커밋하지 않은 새 행이라 기다려요.

📖 용어: 암묵 잠금 (implicit lock)
흔히 이렇게 부르는 InnoDB 의 내부 동작인데, 이 글이 인용한 매뉴얼 절들에는 설명이 없어서 data_locks 에서 보인 모습만 적어요. S1 이 혼자 행을 넣은 직후 data_locks 에는 레코드 잠금이 하나도 없었고, S2 가 같은 값을 넣으려 하자 그제야 S1 몫의 X,REC_NOT_GAP 이 나타났습니다. 새 행의 잠금이 "다른 트랜잭션이 부딪칠 때" 비로소 목록에 드러난다는 뜻이에요.
REPEATABLE READ, first_visit (가) [04] S1> INSERT IGNORE ... (1) Query OK, 1 row affected data_locks: (레코드 잠금 없음) [05] S2> INSERT IGNORE ... (1) (대기) | S1 | uk_member | X,REC_NOT_GAP | GRANTED | 1, 1 | | S2 | uk_member | S | WAITING | 1, 1 | [06] S3> INSERT IGNORE ... (1) (대기) | S3 | uk_member | S | WAITING | 1, 1 | [07] S1> COMMIT; S2, S3: Query OK, 0 rows affected, 1 warning | S2 | uk_member | S | GRANTED | 1, 1 | | S3 | uk_member | S | GRANTED | 1, 1 | [08] S2> SELECT ... FOR UPDATE (대기: X,REC_NOT_GAP WAITING) [09] S3> SELECT ... FOR UPDATE ERROR 1213 (40001): Deadlock found ...

→ S1 이 커밋하는 순간 줄 서 있던 S2 와 S3 의 S 요청이 한꺼번에 허용됐어요. 둘 다 S 를 쥔 채 FOR UPDATE 로 넘어가니 2장과 똑같은 순환입니다. 그래서 행이 없을 때는 먼저 넣는 요청 하나 + S 를 함께 받을 대기자 둘, 세 요청이 필요해요. 회사에서 처음 터진 교착이 "첫 방문 동시 요청 3개"였던 것과 맞아떨어집니다.

그림 3. S1 이 끝나는 순간 S 두 개가 동시에 풀려난다. 커밋이면 FOR UPDATE 에서, 롤백이면 INSERT 자체에서 순환

S1 이 커밋 대신 롤백하면 더 짧아집니다. 매뉴얼 locks-set 절의 세 세션 예제가 이 경우예요. 행이 사라졌으니 S 를 받은 S2 와 S3 가 둘 다 행을 넣으려 하고, 넣으려면 X 가 필요한데 서로의 S 에 막혀요. 실습에서도 FOR UPDATE 한 줄 없이, 롤백 직후 S3 의 INSERT IGNORE 자체가 1213 을 받았고 S2 가 행을 넣었습니다. IGNORE 가 있어도 교착은 무시되지 않아요. 교착은 "무시 가능한 오류"가 아니고, 받은 쪽 트랜잭션은 통째로 되돌려집니다(롤백 범위는 5편에서 다뤄요).

대조군으로 요청을 두 개만 보내 봤어요. 커밋이든 롤백이든 S 를 받는 대기자가 하나뿐이라 교착은 없었습니다.

(행이 없다. 칸 = 세 바퀴 중 1213 이 난 횟수) RR (가) RR (나) RC (가) RC (나) 세 요청, S1 COMMIT 뒤 FOR UPDATE 3/3 3/3 3/3 3/3 세 요청, S1 ROLLBACK (그 뒤 문장 없음) 3/3 3/3 3/3 3/3 두 요청, S1 COMMIT 뒤 FOR UPDATE 0/3 0/3 0/3 0/3 두 요청, S1 ROLLBACK 0/3 0/3 0/3 0/3

→ 행이 없을 때는 키 구조도 격리 수준도 결과를 바꾸지 못했어요. 세 요청이면 열두 번 모두 났고, 두 요청이면 한 번도 나지 않았습니다. 1213 을 받은 쪽도 매번 같았어요. 커밋 경우는 마지막에 FOR UPDATE 를 보낸 S3, 롤백 경우도 S3 의 INSERT IGNORE 였고 S2 가 행을 넣었습니다. 동시성 테스트를 두 스레드로만 짜면 이 교착은 재현되지 않아요.

5. READ COMMITTED 로 내리면 사라지나

교착 글에 자주 달리는 답이 "격리 수준을 READ COMMITTED 로 내리세요"예요. RC 는 갭 잠금을 대부분 끄니까 교착이 줄어든다는 이야기인데, 이 패턴에는 듣지 않습니다. 이 교착을 만드는 건 갭 잠금이 아니라 같은 레코드 위의 S 와 X 이고, 중복 검사의 S 는 RC 에서도 걸리기 때문이에요. 위 표들을 격리 수준으로 다시 모으면 이렇습니다.

(교착 시나리오 네 개 x 테이블 두 개 = 여덟 조합, 각 세 바퀴) RR RC 1213 이 난 조합 6 / 8 8 / 8 RR 에서 빠진 두 조합: (가) 테이블의 "행이 있을 때" 두 시나리오. 교착 대신 대기로 바뀌었다

→ RC 는 이 패턴을 없애지 못했고, (가) 테이블의 "행이 있을 때"는 오히려 RR 에서 대기였던 것이 RC 에서 교착으로 바뀌었어요. RC 에서는 supremum X 가 생기지 않아 S2 도 S 를 받기 때문입니다. 격리 수준은 이 교착을 없애지는 못해요. 대기로 바뀌는 조합이 있을 뿐이고, 없애는 스위치는 같은 트랜잭션 안에서 S 를 쥔 채 X 를 요청하는 코드입니다.

6. 고치는 법: S 를 쥔 채 X 를 요청하지 않는다

원인이 "S 를 쥔 두 트랜잭션이 X 로 올리기"이니 고치는 길은 둘이에요. 처음부터 X 를 잡거나, 같은 트랜잭션에서 그 행에 X 를 요청하지 않거나. 실습에서 세 가지 판을 돌렸습니다.

그림 4. 세 판 모두 "S 를 쥔 채 X 요청"을 없앤다. 대가는 각자 다른 곳에 있다

① 처음부터 X: SELECT … FOR UPDATE 먼저

BEGIN; SELECT member_id, visit_count FROM first_visit WHERE member_id = ? FOR UPDATE; -- 있으면 UPDATE first_visit SET visit_count = visit_count + 1 WHERE member_id = ?; -- 없으면 INSERT (아래 주의) COMMIT;

행이 있으면 첫 FOR UPDATE 가 X 를 받고, 두 번째는 S 를 거치지 않고 바로 X 를 기다리며 줄을 섭니다. 업그레이드가 없으니 순환도 없어요. 실습에서 이 판은 행이 있을 때 RR, RC 와 두 테이블의 네 조합 모두 세 바퀴 내내 1213 이 0 이었어요.

⚠️ 주의: 행이 없으면 ① 도 교착이 난다
없는 행에 FOR UPDATE 를 걸면 RR 에서는 레코드가 없으니 그 자리의 간격에 갭 잠금이 걸려요. 갭 잠금은 여러 트랜잭션이 동시에 쥘 수 있어서 둘 다 통과하고, 이어지는 두 INSERT 의 insert intention 이 서로의 갭 잠금에 막힙니다. 실습에서 행이 없는 상태에서 두 요청이 FOR UPDATE 다음 INSERT 를 하자 RR 에서는 두 테이블 모두 세 바퀴 내내 1213 이 났고, RC 에서는 갭 잠금이 없어 나지 않았어요. "없으면 넣기"를 교착 없이 짜는 방법은 6편에서 따로 다뤄요.

② 같은 트랜잭션에서 그 행을 잠그지 않는다

INSERT IGNORE 는 그대로 두고 그 뒤에 그 행을 잠그지 않습니다. 넣었는지는 영향받은 행 수(1 이면 새로 넣음, 0 이면 이미 있음)로 판정하고(단 IGNORE 는 중복 말고도 무시 가능한 다른 오류를 경고로 바꾸니, 0 일 때 경고가 정말 중복인지 SHOW WARNINGS 로 한 번 확인하세요), 읽어야 하면 잠그지 않는 일반 SELECT 로 읽어요. 일반 SELECT 는 스냅숏을 읽는 일관된 읽기라 잠금을 요청하지 않습니다. 실습에서 이 판도 행이 있을 때 네 조합 모두 세 바퀴 내내 1213 이 0 이었습니다. S 두 개가 공존할 뿐 누구도 X 를 요청하지 않으니까요. 대신 그 트랜잭션 안에서 그 행을 고쳐야 한다면 이 판은 못 씁니다. UPDATE 가 다시 X 를 요청하니까요(2장의 exists-2s-update).

실습의 mysql 클라이언트에서는 중복이면 0 rows affected, 1 warning, 새로 넣으면 1 row affected 였어요. 앱에서는 JDBC 의 executeUpdate() 반환값으로 받는데, 반환값의 뜻은 드라이버 설정에 따라 달라질 수 있으니 자기 드라이버에서 한 번 찍어 보고 쓰세요. 같은 생각으로 ON DUPLICATE KEY UPDATE 의 반환값을 쓰다가 판정이 깨지는 이야기가 2편이에요.

③ 트랜잭션을 나눈다

INSERT IGNORE 만 담은 짧은 트랜잭션을 먼저 커밋해서 S 를 놓고, 새 트랜잭션에서 FOR UPDATE 와 UPDATE 를 합니다. 두 번째 트랜잭션은 ① 과 같은 모양이 돼요. 실습에서 행이 있을 때 네 조합 모두 1213 이 0 이었어요. 대가는 원자성이에요. 두 트랜잭션 사이에서 앱이 죽으면 행은 생겼는데 뒤따르는 갱신은 없는 상태가 남습니다. 뒤 단계가 다시 돌려도 같은 결과를 내도록 짜여 있을 때만 쓰세요.

세 판의 숫자는 모두 "행이 이미 있을 때"만 잰 것이에요. 행이 없고 첫 삽입자가 커밋하는 세 요청의 ②, ③, 그리고 ① 의 세 요청이나 첫 삽입자 롤백 경우는 이 실습에서 돌리지 않았습니다(① 의 행 없음은 두 요청만, 위 주의 상자의 결과예요).

⚠️ 주의: 첫 삽입자가 롤백하는 경우는 ②, ③ 도 못 막는다
4장의 롤백 시나리오는 INSERT IGNORE 세 개만으로 교착이 났어요. ② 와 ③ 의 첫 단계가 바로 그 모양입니다. 먼저 넣은 요청이 다른 이유로 롤백되는 일은 드물지만 0 은 아니에요. 그래서 고친 뒤에도 1213 을 받으면 트랜잭션 전체를 다시 시도하는 처리가 필요합니다(5편).

git clone https://github.com/DDINGJOO/Platform-study.git cd Platform-study/labs/db/dl-01-insert-ignore-upgrade ./scripts/run_all.sh # MySQL(127.0.0.1:39010) + 시나리오 전부, 세 바퀴 python3 scripts/sessions.py exists-2s RC # 하나만 단계별로 docker compose down -v

💡 내 코드에서 바꿀 것
• INSERT IGNORE 를 찾고, 같은 트랜잭션 안에서 그 행에 FOR UPDATE, UPDATE, DELETE 가 뒤따르는지 보세요. JPA 라면 비관적 쓰기 잠금 조회(@Lock(PESSIMISTIC_WRITE))와 더티 체킹이 만드는 UPDATE 도 같은 것이니 SQL 로그로 확인하세요
• 행이 있을 때만 생각하지 말고 행이 없을 때 세 요청이 겹치는 경우로 테스트하세요. 두 요청짜리 동시성 테스트는 "없을 때" 교착을 재현하지 못합니다
• 격리 수준을 내리는 것으로 끝내지 마세요. RC 에서도 네 경우 모두 1213 이 났습니다
• 고칠 때는 ① 처음부터 X, ② 잠그지 않기, ③ 트랜잭션 나누기 중 하나를 고르고, 행이 없을 때와 첫 삽입자가 롤백할 때는 따로 대비하세요(6편, 5편)
• RR 의 대리 키 테이블에서 교착이 안 보인다면, 대신 다른 행의 INSERT 까지 줄 세우는 supremum 대기가 있는지 data_locks 로 확인하세요
• 고친 코드가 실제로 배포됐는지 확인하세요. 저는 수정 PR 이 머지된 뒤에도 운영 빌드가 수정 전 커밋이어서 "고쳤는데 그대로"를 한 번 겪었습니다
✍️ 오늘의 요약
INSERT IGNORE 는 중복일 때 오류를 경고로 바꿀 뿐, 중복 난 인덱스 레코드에 S 잠금을 걸고 트랜잭션 끝까지 들고 있습니다. 매뉴얼의 잠금 목록에는 이 문장이 없어서 data_locks 로 봐야 보여요.

그 S 를 쥔 두 트랜잭션이 같은 행에 FOR UPDATE 나 UPDATE 로 X 를 요청하면 서로를 막아 1213 이 납니다. 행이 있으면 두 요청으로(단 RR 의 대리 키 테이블은 supremum 대기로 바뀌었어요), 행이 없으면 먼저 넣은 요청이 끝나는 순간 S 를 함께 받는 세 번째 요청으로 납니다. READ COMMITTED 에서도 남았어요.

교착을 만든 건 격리 수준도 행 수도 아니고, 같은 트랜잭션 안에서 S 를 쥔 채 X 를 요청한 코드 한 줄이었습니다.
