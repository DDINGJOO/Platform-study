🔒 MySQL 교착 · 6편
1편. INSERT IGNORE 다음 SELECT … FOR UPDATE가 교착을 만드는 이유
2편. ON DUPLICATE KEY UPDATE 반환값으로 중복을 판정하면 안 된다
3편. LATEST DETECTED DEADLOCK 읽는 법과 data_locks로 원인을 확정하는 순서
4편. 교착 알람이 조용해졌다고 교착이 사라진 건 아니다
5편. 교착(1213)과 lock wait timeout(1205)은 롤백 범위가 다르다
6편. 같은 요청이 동시에 두 번 올 때 없으면 넣기를 교착 없이 짜는 다섯 가지 방법 ← 지금 이 글
7편. 동시성 테스트가 통과한 게 아니라 실행되지 않았을 때

앱이 응답을 늦게 받으면 클라이언트는 같은 본문을 다시 보냅니다. 로드밸런서는 그 재전송을 다른 인스턴스로 넘기고요. 그래서 "처음 온 사람이면 한 줄 넣는다"는 코드에 같은 키가 몇 ms 차이로 네 번 들어옵니다. 테스트에서 한 번씩 부를 때는 멀쩡하던 코드가 이때 Deadlock found when trying to get lock 을 냅니다.

"없으면 넣기"를 짜는 방법은 여럿입니다. INSERT IGNORE 후 다시 읽기, ON DUPLICATE KEY UPDATE, 그냥 넣고 중복 예외 잡기, 먼저 읽고 분기하기, 먼저 SELECT … FOR UPDATE 로 잠그기. 이 글은 다섯 가지를 같은 키 4건 동시 × 90라운드 = 360건으로 MySQL 8.4 에서 돌려, 몇 건이 실패하는지, 교착이 몇 번 나는지, "내가 넣었다/이미 있었다"를 맞게 판정하는지, 무엇을 얼마나 잠그는지를 숫자로 비교합니다.

• 재시도는 어디에 두어야 하나? Spring 7 의 @Retryable 과 @Transactional 을 같이 붙이면 어느 쪽이 바깥인가?
• 내 코드에서는 무엇으로 바꾸면 되나?

1. 실험: 같은 키 4건을 동시에, 90번

표 하나에 키 하나당 한 행만 있어야 합니다. 키에는 보조 유니크 인덱스가 있고, 기본 키는 따로 있는 AUTO_INCREMENT 입니다. 가장 흔한 모양이에요. 무작위 키 1000행을 미리 넣어 두어서 새 키는 기존 행 사이 아무 틈에나 떨어집니다.

CREATE TABLE visit ( id BIGINT AUTO_INCREMENT PRIMARY KEY, user_key VARCHAR(32) NOT NULL, payload VARCHAR(64) NOT NULL, inserted_by VARCHAR(40) NOT NULL, -- 채점용: 실제로 행을 넣은 요청 id UNIQUE KEY uk_user_key (user_key) );

한 라운드는 새 키 하나에 같은 본문 요청 4건입니다. 연결 4개는 풀을 공유하지 않아서 서로 다른 인스턴스에 도착한 재전송과 같고, 배리어로 출발을 맞춥니다. 요청 하나가 트랜잭션 하나이고 재시도는 없어요. 요청마다 패턴이 스스로 내린 판정(SAVED 내가 넣었다 / DUPLICATE 이미 있었다)을 inserted_by 와 대조해 채점합니다.

① INSERT IGNORE → 같은 행 SELECT … FOR UPDATE 판정: IGNORE 반환값 1/0 ② INSERT … ON DUPLICATE KEY UPDATE payload=payload 판정: 반환값 1 이면 저장 ②' 같은 문장, Connector/J useAffectedRows=true ③ INSERT → 1062 면 롤백하고 중복 판정: 예외 여부 ④ 잠금 없는 SELECT → 없으면 INSERT 판정: 조회 결과 → 1062 면 롤백하고 새로 읽어 같은 값인지 확인 ④' 1062 뒤 같은 트랜잭션에서 다시 읽기 (함정 확인용) ⑤ SELECT … FOR UPDATE → 없으면 INSERT 판정: 조회 결과
📖 용어: 교착 (deadlock, ERROR 1213)
두 트랜잭션이 서로 상대가 쥔 잠금을 기다려 둘 다 영영 못 끝나는 상태예요. InnoDB 는 이걸 바로 찾아내 한쪽을 골라 트랜잭션 전체를 롤백하고 1213 을 돌려줍니다. 남은 쪽은 계속 진행해요.

MySQL 8.4.11, Spring Boot 4.1.1(Spring Framework 7.0.9), Connector/J 9.7.0, Java 25 로 돌렸습니다. 패턴은 드라이버 기본값 그대로의 JDBC 로 짰고, 재시도와 Spring 동작만 Spring 으로 봤어요. 전체를 세 바퀴 돌렸고, 재시도 없는 패턴 비교에서는 세 바퀴의 실패 수와 판정 수가 한 건도 다르지 않았습니다.

git clone https://github.com/DDINGJOO/Platform-study.git cd Platform-study/labs/db/dl-06-upsert-patterns ./scripts/build.sh # JDK 21 이상 ./scripts/run_all.sh # MySQL(127.0.0.1:39060) + 세 바퀴, 약 5분 python3 scripts/summarize.py # results/summary.txt docker compose down -v

2. 결과: 교착이 나는 패턴 둘, 판정이 틀리는 패턴 둘

패턴 (RR, 360건) 실패 lock_deadlocks 틀린 판정 맞은 라운드 ① IGNORE + FOR UPDATE 180 (1213) +180 0 0/90 ② ODKU 무변경 (드라이버 기본값) 0 0 270 0/90 ②' ODKU + useAffectedRows=true 0 0 0 90/90 ③ INSERT, 1062 잡기 0 0 0 90/90 ④ 잠금 없는 조회 후 분기 0 0 0 90/90 ④' 1062 뒤 같은 트랜잭션 재조회 0 0 판정 불가 270 0/90 ⑤ FOR UPDATE 먼저 270 (1213) +270 0 0/90 READ COMMITTED 에서 달라진 것 ① 그대로 180 (1213) ④' 판정 불가 0 ⑤ 교착 0, 대신 1062 가 270

"맞은 라운드"는 4건이 모두 예외 없이 끝나고 판정이 전부 맞고 행이 정확히 한 개인 라운드입니다. 실패한 요청이 있어도 행은 매번 한 개였어요(0행 라운드 0). 즉 교착은 데이터를 망가뜨리지 않고, 같은 요청을 받은 클라이언트 일부에게 에러를 돌려줍니다. 사용자에게는 "가끔 실패하는 첫 방문"으로 보여요. 지연은 성공한 패턴끼리 큰 차이가 없었습니다. 중앙값이 ③ 1.6~2.3ms, ④ 2.9~3.3ms 로 ④ 가 조회 한 번만큼 느렸어요.

숫자가 이렇게 딱 떨어지는 데는 이유가 있습니다. 이 구성(풀을 공유하지 않는 독립 연결 4개, 배리어로 동시 출발)에서 ① 은 라운드마다 정확히 2건, ⑤ 는 정확히 3건이 실패했어요. 다음 장에서 잠금을 보면 왜 그런지 나옵니다.

⚠️ 주의: 교착 카운터는 상태 변수에 없었다
교착 수는 information_schema.INNODB_METRICS 의 lock_deadlocks 로 셌고, 실패한 1213 건수와 정확히 같았어요. 같이 본 SHOW GLOBAL STATUS LIKE 'Innodb_deadlocks' 는 MySQL 8.4.11 에서 빈 결과였습니다. 대시보드가 이 이름을 읽고 있다면 0 이 아니라 "없음"인지 확인해 보세요.

3. 교착이 나는 두 패턴: 잠금을 올리거나, 빈 틈을 잠그거나

① 은 1편에서 자세히 다뤘으니 짧게 짚겠습니다. 중복 키 때문에 INSERT IGNORE 가 행을 넣지 못하면 InnoDB 는 그 인덱스 레코드에 공유(S) 잠금을 겁니다. 이어지는 FOR UPDATE 는 같은 행에 배타(X) 잠금을 원해요. 중복을 맞은 요청이 둘 이상이면 서로 상대의 S 때문에 X 를 못 받습니다. 4건 중 3건이 중복이니, 교착 감지가 한 명을 롤백시켜도 남은 둘이 다시 같은 모양이 되어 한 번 더 롤백됩니다. 그래서 라운드마다 2건이에요.

READ COMMITTED 로 내려도 ① 은 똑같이 180건이었습니다. MySQL 문서는 READ COMMITTED 에서 갭 잠금을 끄지만 "외래 키 제약 검사와 중복 키 검사에는 쓴다"고 적어 두었어요. ① 의 S 잠금은 바로 그 중복 키 검사에서 나옵니다.

📖 용어: 갭 잠금 (gap lock)
인덱스 레코드 자체가 아니라 두 레코드 사이의 빈 구간을 잠그는 잠금이에요. 그 구간에 다른 트랜잭션이 행을 넣지 못하게 막는 것이 유일한 목적입니다. MySQL 문서에 따르면 갭 잠금끼리는 충돌하지 않아서, 두 트랜잭션이 같은 갭을 동시에 잠글 수 있어요.
📖 용어: insert intention 잠금
INSERT 가 행을 넣기 직전에 그 갭에 거는 특수한 갭 잠금이에요. 같은 갭이라도 서로 다른 위치에 넣는 INSERT 끼리는 기다리지 않지만, 다른 트랜잭션이 쥔 일반 갭 잠금과는 충돌합니다.

⑤ 는 "먼저 잠그고 확인하면 안전하다"는 직관이 어긋나는 경우입니다. REPEATABLE READ 에서 없는 키를 FOR UPDATE 로 찾으면, 잠글 레코드가 없으니 InnoDB 는 그 키가 들어갈 자리의 갭을 잠급니다. 갭 잠금끼리는 충돌하지 않으니 4건이 모두 같은 갭 잠금을 받고 "없다"는 답을 들어요. 그다음 각자 INSERT 를 하면 insert intention 이 다른 세 트랜잭션의 갭 잠금에 막힙니다. 네 명이 서로를 기다리니 셋이 롤백되고 하나만 넣습니다. 그래서 라운드마다 3건이에요. 시드 행 k100 k200 k300 사이에 k150 을 넣는 두 세션으로 찍은 data_locks 입니다.

A> SELECT id FROM visit WHERE user_key='k150' FOR UPDATE => rows=0 B> SELECT id FROM visit WHERE user_key='k150' FOR UPDATE => rows=0 A RECORD uk_user_key X,GAP GRANTED 'k200', 2 B RECORD uk_user_key X,GAP GRANTED 'k200', 2 A> INSERT INTO visit(...) VALUES ('k150', ...) => (waiting) A RECORD uk_user_key X,GAP,INSERT_INTENTION WAITING 'k200', 2 B> INSERT INTO visit(...) VALUES ('k150', ...) => ERROR 1213 Deadlock found when trying to get lock

LOCK_DATA 가 'k200', 2 인 것은 "k200 바로 앞의 갭", 즉 k100 과 k200 사이를 뜻해요. 행이 없는 k150 을 찾았는데 잠긴 건 그 이웃 구간입니다. 같은 갭에 떨어지는 다른 키(예를 들어 k120)의 INSERT 도 이 잠금에 막힌다는 뜻이기도 해요.

그림 1. ① 은 같은 행의 잠금을 S 에서 X 로 올리다가, ⑤ 는 갭 잠금 위에 INSERT 하다가 서로를 기다린다

READ COMMITTED 에서 ⑤ 는 교착이 0 이었습니다. 없는 행에 대한 FOR UPDATE 가 갭을 잠그지 않아서 아무것도 잠그지 않아요. 그 대신 4건이 모두 "없다"를 보고 INSERT 를 하니, 3건이 1062 Duplicate entry 로 실패해 360건 중 270건이 실패한 건 같았습니다. RC 로 내리면 ⑤ 의 교착은 사라지지만 "없으면 넣기"가 원자적이지 않다는 사실은 그대로입니다. 결국 1062 를 잡는 코드가 필요하고, 그러면 ③ 이 됩니다.

4. 교착이 없는 패턴 사이의 차이: 판정, 잠금 범위, 코드

②, ③, ④ 는 교착이 0 이었지만 같은 수준이 아니었어요.

② ODKU 무변경은 판정이 깨집니다. 360건이 전부 SAVED 였어요. MySQL 문서상 ODKU 의 영향 행 수는 새로 넣으면 1, 바꾸면 2, 같은 값이라 안 바뀌면 0 입니다. 그런데 Connector/J 는 기본값(useAffectedRows=false)에서 접속할 때 CLIENT_FOUND_ROWS 를 켜고, 그러면 무변경도 1 이 됩니다(2편). useAffectedRows=true 로 바꾼 ②' 는 90/90 이었지만, 이 옵션은 연결 전체의 UPDATE 반환값 의미를 바꿉니다. Connector/J 문서도 "JDBC 규약에 맞지 않고, found rows 에 기대는 대부분의 애플리케이션을 깨뜨린다"고 적어 두었어요. 판정 하나 때문에 켜기에는 영향 범위가 넓습니다.

③ 은 가장 짧고 정확합니다. 중복을 맞으면 S 잠금을 받지만 바로 롤백해서 놓기 때문에 그 잠금을 쥔 채 다른 잠금을 기다릴 일이 없어요. 대신 중복일 때마다 INSERT 를 시도하고 롤백합니다. 이미 있는 키로 들어오는 요청이 대부분인 경로라면(재방문, 재전송) 매번 1062 와 롤백을 치르는 셈이에요.

④ 는 이미 저장된 중복에서 잠금을 하나도 잡지 않습니다. 잠금 없는 조회로 같은 값이 있으면 그대로 중복으로 끝나요. 동시에 들어와서 조회 시점에는 없었던 경우만 INSERT 까지 가고, 그때 1062 가 나면 ③ 과 같이 롤백합니다. 코드는 셋 중 가장 길지만 재전송이 많은 경로에서 잠금이 가장 적습니다.

📖 용어: 잠금 없는 읽기 (consistent read)
FOR UPDATE/FOR SHARE 없는 평범한 SELECT 예요. 잠금을 걸지 않고 스냅숏에서 읽습니다. REPEATABLE READ 에서는 트랜잭션의 첫 읽기가 만든 스냅숏을 트랜잭션 끝까지 씁니다.

④' 가 그 스냅숏의 함정입니다. 조회로 "없다"를 본 뒤 INSERT 가 1062 를 받고, 같은 트랜잭션에서 다시 읽으면 RR 에서는 첫 조회의 스냅숏을 쓰므로 방금 남이 넣은 행이 안 보여요. "중복이라는데 행이 없다"가 270건이었습니다. 중복 키 검사는 최신 데이터를 보고, 잠금 없는 읽기는 옛 스냅숏을 보기 때문이에요. RC 에서는 읽을 때마다 새 스냅숏이라 0건이었습니다. 1062 뒤 확인 조회는 롤백한 다음 새 트랜잭션에서 해야 합니다.

그림 2. 중복 요청이 커밋까지 쥐는 잠금. 아무것도 쥐지 않는 건 ④ 뿐이다

그림 2 는 세션 하나가 커밋 직전까지 쥔 잠금을 performance_schema.data_locks 로 찍은 것입니다(results/footprint-*.txt). 새로 넣은 행은 암묵 잠금이라 data_locks 에 따로 안 보이고, 다른 트랜잭션이 그 행을 건드릴 때 명시 잠금으로 바뀌어 나타나요. 그림에 다 넣지 못한 관찰이 하나 더 있습니다. RR 에서 ①·②·③ 의 중복 요청은 보조 유니크 키 잠금 말고도 기본 키의 supremum pseudo-record(인덱스 맨 끝)에 X 잠금을 쥐고 있었어요. 기본 키가 AUTO_INCREMENT 라 새 행은 늘 맨 끝에 들어가니, 이 잠금이 있는 동안에는 다른 키의 INSERT 도 기다릴 수 있습니다(이 실습에서 따로 재지는 않았습니다). ④ 의 중복 요청에는 이 잠금도 없었어요. 정리하면 이렇습니다.

교착(360건) 판정 중복일 때 잠금 코드 ① IGNORE+FU 180 맞음 S 를 쥔 채 X 로 올림 2문장 ② ODKU 0 깨짐(기본) X next-key 1문장 ③ 1062 잡기 0 맞음 S, 롤백으로 즉시 해제 1문장 + catch ④ 조회 먼저 0 맞음 없음 2문장 + catch + 재조회 ⑤ FU 먼저 270 (RR) 맞음 RR: 다음 행 앞 갭 X 2문장 0 (RC) RC: 대신 1062 270건 (FU = SELECT … FOR UPDATE)

교착이 없는 쪽에도 한계가 있습니다. ③ 과 ④ 가 교착이 0 이었던 것은 이 실습에서 먼저 넣은 요청이 늘 커밋했기 때문이에요. MySQL 문서의 INSERT 잠금 설명에는 세 세션이 같은 키를 넣다가 첫 세션이 롤백하면, 중복 검사로 S 를 받고 기다리던 두 세션이 서로 X 를 못 받아 교착이 나는 예가 그대로 있습니다. 넣은 쪽이 같은 트랜잭션의 뒤 작업에서 실패해 롤백하는 구조라면 ③·④ 도 드물게 1213 을 받을 수 있다는 뜻이에요. 이 실습에서는 넣은 쪽이 롤백하는 경우를 재현하지 않았습니다. 그리고 ④ 에서 1062 를 받은 뒤 같은 트랜잭션에서 그 행을 UPDATE 하면 ① 과 같은 S→X 모양으로 돌아갑니다. 그래서 다음 장의 재시도는 교착이 0 인 패턴에도 붙여 둡니다.

5. 재시도는 트랜잭션 바깥에

MySQL 문서의 교착 대응 목록에는 "교착으로 실패하면 트랜잭션을 다시 낼 준비를 항상 해 두라"는 항목이 있습니다. 핵심은 무엇을 다시 내느냐예요. 1213 은 문장이 아니라 트랜잭션 전체를 롤백합니다(5편). 그러니 재시도도 트랜잭션 전체를 처음부터 다시 해야 합니다. 메서드 안에서 실패한 문장만 다시 돌리면 앞 문장의 결과는 이미 사라진 채 남은 문장만 실행됩니다.

그림 3. 재시도 한 번이 트랜잭션 하나를 처음부터 다시 여는 구조여야 한다

Spring Framework 7.0 부터는 Spring Retry 없이 코어에 재시도가 들어 있어요. 프로그램 방식은 RetryTemplate 입니다. 실습의 재시도는 이렇게 짰습니다. 1213 과 1205 만 다시 하고, 최대 3번 더, 20ms 에 지터 10ms 예요.

RetryTemplate retry = new RetryTemplate(RetryPolicy.builder() .includes(PessimisticLockingFailureException.class) // 교착·잠금 대기만 .maxRetries(3) .delay(Duration.ofMillis(20)) .jitter(Duration.ofMillis(10)) .build()); Verdict v = retry.invoke(() -> tx.execute(s -> firstVisit(key, payload))); // ↑ 바깥: 재시도 ↑ 안쪽: 시도마다 새 트랜잭션

(실습 코드는 원시 JDBC 라 예외 클래스 대신 오류 코드로 거르는 predicate 를 썼습니다.) 결과는 다음과 같아요.

실패 재시도한 요청 추가 시도 p50 p99 ① 재시도 없음 180 0 0 2.4~2.8ms 5.4~11.1ms ① RetryTemplate 0 180 188~199 9.8~27.6ms 65.3~71.1ms ⑤ 재시도 없음 270 0 0 1.9~2.2ms 5.7~7.2ms ⑤ RetryTemplate 0 270 270 30.8~31.5ms 40.5~42.5ms (세 바퀴의 범위, 각 360건, 판정 오류 0)

재시도로 실패는 0 이 됐고 판정도 전부 맞았어요. 다시 해 보면 행이 이미 있으니 ① 은 IGNORE 가 0 을, ⑤ 는 조회가 행을 돌려주기 때문입니다. 다만 ① 은 추가 시도가 실패 수보다 많았어요(180건에 188~199번). 재시도끼리 다시 교착한 경우입니다. lock_deadlocks 증가분도 재시도 없을 때 180 이던 것이 재시도를 붙이자 188~199 로 오히려 늘었어요. 지연도 p99 가 5~11ms 에서 65~71ms 로 늘었어요. 재시도는 교착을 숨길 뿐 줄이지 않습니다. 패턴을 바꾸는 것이 먼저이고, 재시도는 남은 드문 경우를 위한 것입니다.

어노테이션 방식은 @Retryable 이고 @EnableResilientMethods 로 켭니다. 레퍼런스 문서의 기본값은 "모든 예외에 대해 최대 3번 더, 간격 1초"라서 includes 로 좁혀야 해요. 문제는 @Transactional 과 같은 메서드에 붙일 때의 순서입니다. 이 실습이 쓴 7.0.9 레퍼런스 문서에는 이 순서가 없고, 개발 중인 7.1 문서(7.1.0-M2)의 "With @Transactional" 절에 "Retry (OUTER) → Transaction (INNER)", "Each retry attempt starts a fresh transaction"으로 명시되어 있어요. 7.0.9 소스를 보면 RetryAnnotationBeanPostProcessor 생성자가 setBeforeExistingAdvisors(true) 를 켜요. 이 플래그의 Javadoc 은 "이미 어드바이스가 붙은 객체를 만나면 기존 어드바이저를 감싸게 한다"입니다. 재시도가 트랜잭션 바깥에 온다는 뜻이에요. 실습의 order 모드로 확인했습니다. 첫 시도만 실패하게 만든 메서드입니다.

@Retryable(includes = PessimisticLockingFailureException.class, maxRetries = 3, delay = 20) @Transactional public String failOnce(String key) { ... } attempt 1 start: tx_active=true connection_id=452 inserted order-1 attempt 1 tx completed: ROLLED_BACK attempt 2 start: tx_active=true connection_id=452 inserted order-2 attempt 2 tx completed: COMMITTED rows left: [order-2]

시도마다 트랜잭션이 열리고 닫혔고, 첫 시도가 넣은 order-1 은 롤백으로 사라졌습니다. ① 을 JdbcTemplate 으로 짜서 같은 4건 동시 × 90라운드로 돌리면 재시도 없이는 360건 중 169~172건이 실패했고, @Retryable 을 붙이면 0건이었어요. 이 비교는 독립 연결 4개가 아니라 Spring 의 Hikari 공유 풀(최대 8개)을 거쳐서, 실패 수가 원시 JDBC 의 180 과 조금 다릅니다. 시도 수는 547~558번인데 이건 첫 시도를 포함한 수라, 앞 표의 "추가 시도"로 바꾸면 187~198번이에요. 주의할 점은 이 동작이 프록시를 거치는 호출에만 적용된다는 것입니다. 같은 클래스 안에서 this.firstVisit() 로 부르면 재시도도 트랜잭션도 붙지 않습니다.

⚠️ 주의: 재시도 조건은 공통 부모 예외로
이 실습(Spring Framework 7.0.9, JdbcTemplate)에서 교착 실패는 CannotAcquireLockException 으로 올라왔습니다. 클래스패스 루트에 sql-error-codes.xml 을 두지 않으면 SQLExceptionSubclassTranslator 가 쓰이고, 이 번역기는 SQLSTATE 40001 을 CannotAcquireLockException 으로 바꾸기 때문이에요. 루트에 그 파일을 두면 deprecated 인 DeadlockLoserDataAccessException 이 오고, EntityManager 를 직접 쓰는 빈에서는 Spring 예외가 아닌 JPA 예외가 옵니다(5편 실측). 그래서 재시도 조건은 두 Spring 예외의 공통 부모인 PessimisticLockingFailureException 으로 거는 편이 안전합니다.
📖 용어: 멱등 키 (idempotency key)
같은 요청을 여러 번 보내도 결과가 한 번 보낸 것과 같게 만들기 위해 요청마다 붙이는 고유 값이에요. 서버는 이 키로 "이미 처리한 요청인가"를 판단합니다.

재시도가 안전했던 이유는 이 작업이 "키 하나에 행 하나"라서, 두 번 해도 두 번째는 중복으로 끝나기 때문입니다. 요청이 외부 결제 호출이나 메시지 발행처럼 DB 밖의 일을 같이 한다면 재시도가 그 일까지 반복합니다. 그럴 때는 클라이언트가 보낸 멱등 키를 유니크 키로 둔 표를 먼저 "없으면 넣기"로 차지하고, 차지한 요청만 바깥 일을 하게 만듭니다. 그 표에 넣는 방법이 다시 이 글의 ③ 이나 ④ 예요.

6. 실제로 겪은 일: 360건 중 195건에서 0건으로

운영 DB 의 교착 알람을 따라가 보니, 첫 교착은 같은 사용자의 첫 방문 요청 3개가 동시에 들어온 데서 났습니다. 코드는 ① 이었어요.

수정 방법으로 ODKU 를 제안받았지만 쓰지 않았습니다. 무변경 갱신일 때 Connector/J 기본값에서 중복이어도 1 이 돌아와, 그 코드가 의존하던 저장/중복 판정이 깨지기 때문입니다. 이 글의 ② 가 270건을 틀린 것과 같은 이유예요. 2차 수정은 같은 값으로 이미 저장된 중복을 잠금 없는 조회로 확인하고 중복으로 끝내는 방식이었습니다. 같은 본문 4건을 동시에 재전송하는 시험을 360건 돌리자 2차 수정 전에는 195건이 실패했고, 2차 수정 뒤에는 0건이었어요.

함정이 하나 더 있었습니다. 실패한 요청의 응답 코드가 500 이 아니라 400 이었어요. 공통 예외 핸들러가 처리하지 않은 예외를 400 으로 돌려주고 있었습니다. 교착이 "클라이언트가 잘못 보낸 요청"으로 기록된 셈이에요. 재시도 정책이 4xx 는 다시 보내지 않는 클라이언트라면, 교착 한 번이 그대로 사용자 실패가 됩니다.

7. 고르는 법

반례부터 정리하면 이렇습니다. "먼저 FOR UPDATE 로 잠그면 안전하다"는 RR 에서 없는 행에 대해 거꾸로였어요(⑤, 270건). "RC 로 내리면 된다"는 ① 에는 효과가 없었고 ⑤ 는 교착을 1062 로 바꿨을 뿐이었습니다. "ODKU 한 문장이면 끝난다"는 교착은 맞지만 판정이 드라이버 설정에 달려 있었어요(②, 270건 오판).

💡 내 코드에서 바꿀 것
• INSERT IGNORE 나 1062 다음 같은 트랜잭션에서 그 행에 FOR UPDATE, UPDATE 를 하는 곳을 찾으세요. ① 모양입니다. 행을 잠가야 하는 이유가 없다면 잠금 없는 조회로 바꾸세요
• 없는 행에 SELECT … FOR UPDATE 를 걸고 INSERT 하는 곳도 찾으세요. RR 에서는 ⑤ 모양이고, RC 라도 1062 처리가 필요합니다
• 중복이 흔한 경로(재전송, 재방문)는 ④: 잠금 없는 조회 → 없으면 INSERT → 1062 면 롤백 후 새 트랜잭션에서 다시 읽어 같은 값인지 확인. 드문 경로는 ③ 으로 충분합니다
• 저장/중복 판정에 ODKU 반환값을 쓰고 있다면 useAffectedRows 설정부터 확인하세요. 기본값에서는 무변경 중복도 1 입니다
• 재시도는 트랜잭션 바깥에, PessimisticLockingFailureException 만, 지터를 넣어서. @Retryable 과 @Transactional 을 같은 메서드에 붙이면 Spring 7 에서는 재시도가 바깥입니다. 다만 프록시를 거치는 호출이어야 합니다
• 이 부모 예외는 1205(잠금 대기 시간 초과)도 잡습니다. 1205 를 덜 재시도하려면 원인 예외의 errorCode 로 거르는 predicate 를 쓰세요(5편). EntityManager 를 직접 쓰는 경로라면 jakarta.persistence.PessimisticLockException, LockTimeoutException 은 이 부모의 자식이 아니니 따로 넣어야 합니다
• 교착을 공통 예외 핸들러가 4xx 로 바꾸고 있지 않은지 보세요. 클라이언트가 재시도하지 않는 이유가 됩니다
• 시험은 "같은 키 N건 동시"로 쓰세요. 한 번씩 부르는 테스트로는 다섯 패턴이 모두 통과합니다

참고한 공개 자료: MySQL 8.4 Reference Manual 의 Locks Set by Different SQL Statements in InnoDB, InnoDB Locking, Transaction Isolation Levels, How to Minimize and Handle Deadlocks, INSERT … ON DUPLICATE KEY UPDATE, Connector/J 의 연결 속성(useAffectedRows), Spring Framework 의 Resilience Features(7.0.9, 그리고 @Transactional 순서가 명시된 7.1 개발판) 와 RetryAnnotationBeanPostProcessor 소스, AbstractAdvisingBeanPostProcessor Javadoc. 실습 코드는 labs/db/dl-06-upsert-patterns 에 있습니다.

✍️ 오늘의 요약
같은 키 4건 동시 × 90라운드에서 교착이 난 것은 INSERT IGNORE 다음 FOR UPDATE(360건 중 180건)와 없는 행에 FOR UPDATE 먼저(270건)였고, READ COMMITTED 는 앞의 것을 못 고치고 뒤의 것을 1062 로 바꿀 뿐이었습니다.

ODKU 무변경은 교착이 0 이지만 드라이버 기본값에서 중복도 1 이 돌아와 판정이 270건 틀렸어요. INSERT 후 1062 잡기와 잠금 없는 조회 후 분기는 교착 0, 판정 360건 전부 정확이었고, 이미 저장된 중복에서 잠금을 하나도 잡지 않는 건 뒤의 것뿐이었습니다. 재시도는 트랜잭션 바깥에 두면 실패를 0 으로 만들었지만 p99 를 65~71ms 로 늘렸어요.

"없으면 넣기"에서 고를 것은 잠그는 방법이 아니라, 중복일 때 아무것도 잠그지 않고 끝내는 길이 있느냐입니다.
