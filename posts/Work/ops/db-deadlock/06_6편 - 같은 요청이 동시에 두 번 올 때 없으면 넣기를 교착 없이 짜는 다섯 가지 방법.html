응답을 기다리던 클라이언트가 같은 본문으로 요청을 다시 보내면, 재전송된 요청이 로드밸런서를 거쳐 다른 인스턴스에 도착할 수 있어요. 그러면 "처음 온 사용자라면 한 행 넣는다"는 코드가 같은 키를 동시에 처리하게 됩니다. 요청을 한 번씩 보낼 때는 통과하던 코드도 이 상황에서는 Deadlock found when trying to get lock 오류를 낼 수 있어요.

"없으면 넣기"에는 INSERT IGNORE 후 다시 읽기, ON DUPLICATE KEY UPDATE, INSERT 후 중복 예외 처리, 먼저 조회하고 분기하기, SELECT … FOR UPDATE로 먼저 잠그기 같은 선택지가 있어요. 이 다섯 가지를 MySQL 8.4에서 같은 키 4건 동시 × 90라운드 = 360건으로 비교했어요. 실패와 교착 건수뿐 아니라 "내가 넣었다/이미 있었다"는 판정이 맞는지, 어떤 잠금을 유지하는지도 확인했습니다.

🧭 비교할 항목
• 동시 요청에서 교착이 발생한 패턴과 잠금 대기 원인
• 격리 수준을 READ COMMITTED로 낮췄을 때 달라지는 결과
• 교착 없이 끝나도 저장/중복 판정이 틀리는 경우
• 재시도 위치와 Spring 7의 @Retryable, @Transactional 적용 순서
• 중복 비율과 트랜잭션 구조에 맞는 선택 기준

1. 실험: 같은 키 4건을 동시에, 90번

실험에 쓴 테이블은 키 하나당 한 행만 저장해야 해요. 키에는 보조 유니크 인덱스를 두고, 기본 키는 별도의 AUTO_INCREMENT로 구성했어요. 무작위 키 1000행을 미리 넣어 새 키가 기존 인덱스 레코드 사이에 들어가도록 했습니다.

CREATE TABLE visit ( id BIGINT AUTO_INCREMENT PRIMARY KEY, user_key VARCHAR(32) NOT NULL, payload VARCHAR(64) NOT NULL, inserted_by VARCHAR(40) NOT NULL, -- 채점용: 실제로 행을 넣은 요청 id UNIQUE KEY uk_user_key (user_key) );

한 라운드에서는 새 키 하나로 같은 본문 요청 4건을 보내요. 서로 다른 인스턴스가 요청을 받는 상황을 흉내 내려고 풀을 공유하지 않는 연결 4개를 쓰고, 배리어로 시작 시점을 맞췄어요. 요청 하나가 트랜잭션 하나이며 이 비교에는 재시도가 없어요. 각 패턴이 내린 판정(SAVED: 내가 넣었다 / DUPLICATE: 이미 있었다)을 실제 삽입 요청이 기록된 inserted_by와 대조했습니다.

① INSERT IGNORE → 같은 행 SELECT … FOR UPDATE 판정: IGNORE 반환값 1/0 ② INSERT … ON DUPLICATE KEY UPDATE payload=payload 판정: 반환값 1 이면 저장 ②' 같은 문장, Connector/J useAffectedRows=true ③ INSERT → 1062 면 롤백하고 중복 판정: 예외 여부 ④ 잠금 없는 SELECT → 없으면 INSERT 판정: 조회 결과 → 1062 면 롤백하고 새로 읽어 같은 값인지 확인 ④' 1062 뒤 같은 트랜잭션에서 다시 읽기 (함정 확인용) ⑤ SELECT … FOR UPDATE → 없으면 INSERT 판정: 조회 결과
📖 용어: 교착 (deadlock, ERROR 1213)
트랜잭션들이 서로 상대의 잠금이 해제되기를 기다려 진행할 수 없는 상태예요. InnoDB는 교착을 감지하면 한 트랜잭션을 골라 전체를 롤백하고 1213을 반환해요. 남은 트랜잭션은 계속 진행할 수 있어요.

실행 환경은 MySQL 8.4.11, Spring Boot 4.1.1(Spring Framework 7.0.9), Connector/J 9.7.0, Java 25였어요. 패턴 비교에는 별도 옵션을 명시한 경우를 제외하고 드라이버 기본값의 JDBC를 썼고, 재시도와 Spring의 트랜잭션 동작은 따로 확인했어요. 전체를 세 차례 반복했으며, 재시도 없는 패턴 비교의 실패 수와 판정 수는 세 차례 모두 같았습니다.

git clone https://github.com/DDINGJOO/Platform-study.git cd Platform-study/labs/db/dl-06-upsert-patterns ./scripts/build.sh # JDK 21 이상 ./scripts/run_all.sh # MySQL(127.0.0.1:39060) + 세 바퀴, 약 5분 python3 scripts/summarize.py # results/summary.txt docker compose down -v

2. 결과: 교착이 나는 패턴 둘, 판정이 틀리는 패턴 둘

패턴 (RR, 360건) 실패 lock_deadlocks 틀린 판정 맞은 라운드 ① IGNORE + FOR UPDATE 180 (1213) +180 0 0/90 ② ODKU 무변경 (드라이버 기본값) 0 0 270 0/90 ②' ODKU + useAffectedRows=true 0 0 0 90/90 ③ INSERT, 1062 잡기 0 0 0 90/90 ④ 잠금 없는 조회 후 분기 0 0 0 90/90 ④' 1062 뒤 같은 트랜잭션 재조회 0 0 판정 불가 270 0/90 ⑤ FOR UPDATE 먼저 270 (1213) +270 0 0/90 READ COMMITTED 에서 달라진 것 ① 그대로 180 (1213) ④' 판정 불가 0 ⑤ 교착 0, 대신 1062 가 270

"맞은 라운드"는 4건이 모두 예외 없이 끝나고, 판정이 전부 맞으며, 저장된 행이 정확히 한 개인 라운드예요. 실패한 요청이 있는 라운드도 행은 한 개였어요(0행 라운드 0). 이 실험에서는 행이 중복되거나 사라지는 대신 일부 요청이 교착 오류로 끝났어요. API에서 이 오류를 처리하지 않으면 클라이언트도 실패 응답을 받게 돼요. 지연은 성공한 패턴끼리 큰 차이가 없었어요. 중앙값은 ③이 1.6~2.3ms, ④가 2.9~3.3ms였고, 먼저 조회하는 ④가 더 느렸습니다.

풀을 공유하지 않는 연결 4개를 배리어로 동시에 시작한 이번 구성에서는 ①이 라운드마다 2건, ⑤가 3건씩 실패했어요. 두 패턴의 잠금 대기를 보면 이 결과를 설명할 수 있어요.

⚠️ 주의: 교착 상태 변수의 존재 여부 확인
교착 수는 information_schema.INNODB_METRICS의 lock_deadlocks로 셌고, 1213 실패 건수와 같았어요. 함께 조회한 SHOW GLOBAL STATUS LIKE 'Innodb_deadlocks'는 MySQL 8.4.11에서 빈 결과였어요. 대시보드에서 이 이름을 읽는다면 값이 0인지, 상태 변수 자체가 없는 것인지 구분해 확인해야 해요.

3. 공유 잠금의 배타 전환과 없는 키의 갭 잠금

①은 1편에서 확인한 공유 잠금에서 배타 잠금으로의 전환 문제예요. 중복 키 때문에 INSERT IGNORE가 행을 넣지 못하면 InnoDB는 해당 인덱스 레코드에 공유(S) 잠금을 설정해요. 이어지는 FOR UPDATE는 같은 행에 배타(X) 잠금을 요청합니다. 중복 요청이 둘 이상이면 각자가 유지하는 S 잠금 때문에 다른 요청이 X 잠금을 받지 못해요. 이번 실험에서는 4건 중 3건이 중복이었고, 한 트랜잭션이 롤백된 뒤에도 남은 둘이 서로 기다려 한 번 더 롤백됐어요. 이렇게 라운드마다 2건이 실패했습니다.

READ COMMITTED에서도 ①의 교착 실패는 180건이었어요. MySQL 문서는 READ COMMITTED에서 갭 잠금을 사용하지 않더라도 외래 키 제약 검사와 중복 키 검사에는 예외가 있다고 설명해요. ①의 S 잠금은 중복 키 검사 과정에서 생기므로 격리 수준을 낮춰도 이 대기는 없어지지 않았어요.

📖 용어: 갭 잠금 (gap lock)
인덱스 레코드 자체가 아니라 두 레코드 사이의 빈 구간을 잠그는 잠금이에요. 다른 트랜잭션이 그 구간에 행을 삽입하지 못하게 해요. MySQL 문서에 따르면 갭 잠금끼리는 충돌하지 않아서, 두 트랜잭션이 같은 갭을 동시에 잠글 수 있어요.
📖 용어: insert intention 잠금
INSERT가 행을 넣기 직전에 해당 갭에 요청하는 특수한 갭 잠금이에요. 같은 갭이라도 서로 다른 위치에 삽입하는 요청끼리는 기다리지 않지만, 다른 트랜잭션이 설정한 일반 갭 잠금에는 대기해요.

⑤에서는 없는 행에 먼저 잠금을 요청한 것이 교착으로 이어졌어요. REPEATABLE READ에서 없는 키를 FOR UPDATE로 찾으면 InnoDB는 그 키가 들어갈 갭을 잠가요. 갭 잠금끼리는 충돌하지 않으므로 이번 실험에서는 요청 4건이 모두 같은 갭의 잠금을 얻고, 조회 결과로는 행이 없다는 응답을 받았어요. 이후 각 요청이 INSERT를 실행하면 insert intention 잠금이 다른 세 트랜잭션의 갭 잠금에 막힙니다. 교착 감지로 셋이 롤백되고 하나가 행을 넣어 라운드마다 3건이 실패했어요. 아래는 시드 행 k100 k200 k300 사이에 k150을 넣는 두 세션에서 확인한 data_locks예요.

A> SELECT id FROM visit WHERE user_key='k150' FOR UPDATE => rows=0 B> SELECT id FROM visit WHERE user_key='k150' FOR UPDATE => rows=0 A RECORD uk_user_key X,GAP GRANTED 'k200', 2 B RECORD uk_user_key X,GAP GRANTED 'k200', 2 A> INSERT INTO visit(...) VALUES ('k150', ...) => (waiting) A RECORD uk_user_key X,GAP,INSERT_INTENTION WAITING 'k200', 2 B> INSERT INTO visit(...) VALUES ('k150', ...) => ERROR 1213 Deadlock found when trying to get lock

이 덤프에서 LOCK_DATA가 'k200', 2이고 잠금 모드가 X,GAP인 것은 k200 바로 앞, 즉 k100과 k200 사이의 갭을 잠갔다는 뜻이에요. 조회한 k150 행은 없지만 그 키가 들어갈 구간에는 잠금이 설정됐어요. 같은 갭에 들어가는 다른 키(예를 들어 k120)의 INSERT도 이 잠금에 대기할 수 있어요.

그림 1. ①은 S에서 X로 전환할 때, ⑤는 갭 잠금이 설정된 구간에 INSERT할 때 교착이 발생했어요

READ COMMITTED에서 ⑤의 교착은 0건이었어요. 이 구성에서는 없는 행에 대한 FOR UPDATE가 갭 잠금을 설정하지 않았어요. 요청 4건은 모두 행이 없다고 조회한 뒤 INSERT를 시도했고, 3건이 1062 Duplicate entry로 끝났어요. 따라서 360건 중 270건이 실패한 점은 같아요. RC에서 ⑤의 교착은 없어졌지만, 조회와 삽입 사이의 중복 경쟁은 남았어요. 이 방식에도 ③처럼 1062를 처리하는 코드가 필요해요.

4. 교착 0건인 패턴의 판정과 잠금 범위 비교

②, ③, ④에서는 교착이 0건이었지만, 저장 여부의 판정과 중복 요청의 잠금 범위에는 차이가 있었어요.

②의 무변경 ODKU는 360건을 모두 SAVED로 판정했어요. MySQL 문서에서 ODKU의 영향 행 수는 새 행이면 1, 변경한 행이면 2, 같은 값이라 변경하지 않았으면 0이에요. 그런데 Connector/J는 기본값(useAffectedRows=false)에서 CLIENT_FOUND_ROWS를 켜므로, 무변경 중복도 1을 반환해요(2편). useAffectedRows=true를 쓴 ②'는 90/90라운드에서 판정이 맞았어요. 다만 이 옵션은 연결 전체의 UPDATE 반환값 의미를 바꿔요. Connector/J 문서도 JDBC 규약과 다르며 found rows에 의존하는 애플리케이션에 영향을 준다고 경고해요. 저장 여부 판정을 위해 옵션을 바꾼다면 같은 연결을 쓰는 다른 코드도 확인해야 해요.

③은 INSERT를 시도하고 1062가 나면 롤백 후 중복으로 끝내는 방식이에요. 중복 검사로 S 잠금을 받더라도 곧바로 롤백해 해제하므로, 이후 문장에서 X 잠금을 요청하지 않아요. 이번 비교에서는 코드가 짧고 판정도 맞았어요. 다만 이미 있는 키로 요청이 올 때마다 INSERT와 롤백을 실행하므로, 재방문이나 재전송이 많은 경로에서는 그 처리가 반복돼요.

④는 이미 저장된 값이 같으면 잠금 없는 조회만으로 중복 판정을 마쳐요. 조회 시점에 행이 없었던 요청만 INSERT를 시도하고, 그때 1062가 나면 ③처럼 롤백한 뒤 새 트랜잭션에서 값을 확인해요. 코드와 분기는 더 길지만, 이미 저장된 중복 요청이 많을 때 INSERT와 중복 검사 잠금을 줄일 수 있어요.

📖 용어: 잠금 없는 읽기 (consistent read)
FOR UPDATE/FOR SHARE가 없는 일반 SELECT예요. 행 잠금을 설정하지 않고 스냅숏에서 읽어요. REPEATABLE READ에서는 첫 일관 읽기가 만든 스냅숏을 트랜잭션 끝까지 사용해요.

④'에서는 1062 뒤에 같은 트랜잭션으로 재조회한 것이 문제가 됐어요. RR에서는 첫 조회에서 행이 없다고 본 스냅숏을 계속 쓰므로, 다른 트랜잭션이 삽입한 행을 재조회해도 보지 못했어요. 이렇게 중복 오류가 났는데 행을 찾지 못한 요청이 270건이었어요. 중복 키 검사는 최신 데이터를 확인하지만 잠금 없는 읽기는 기존 스냅숏을 사용하기 때문이에요. 읽을 때마다 새 스냅숏을 쓰는 RC에서는 이 요청이 0건이었어요. RR에서 1062 뒤 값을 확인하려면 롤백 후 새 트랜잭션으로 조회해야 해요.

그림 2. 이미 저장된 중복을 조회만으로 처리한 ④에서는 행 잠금이 관찰되지 않았어요

그림 2는 세션 하나가 삽입이나 중복 처리를 한 뒤 유지하는 잠금을 performance_schema.data_locks로 확인한 결과예요(results/footprint-*.txt). 새로 넣은 행의 암묵 잠금은 data_locks에 따로 표시되지 않다가, 다른 트랜잭션이 접근해 명시 잠금으로 전환되면 나타나요. RR에서 ①·②·③의 중복 요청에는 보조 유니크 키 잠금 외에 기본 키의 supremum pseudo-record(인덱스 맨 끝)에 대한 X 잠금도 있었어요. 기본 키가 AUTO_INCREMENT라 새 행이 맨 끝에 추가되므로 다른 키의 INSERT도 이 잠금을 기다릴 수 있지만, 이번 실습에서 그 대기를 따로 측정하지는 않았어요. ④의 중복 요청에서는 이 잠금도 관찰되지 않았습니다.

교착(360건) 판정 중복일 때 잠금 코드 ① IGNORE+FU 180 맞음 S 를 쥔 채 X 로 올림 2문장 ② ODKU 0 깨짐(기본) X next-key 1문장 ③ 1062 잡기 0 맞음 S, 롤백으로 즉시 해제 1문장 + catch ④ 조회 먼저 0 맞음 없음 2문장 + catch + 재조회 ⑤ FU 먼저 270 (RR) 맞음 RR: 다음 행 앞 갭 X 2문장 0 (RC) RC: 대신 1062 270건 (FU = SELECT … FOR UPDATE)

③과 ④에서 교착이 0건이었다는 결과에는 조건이 있어요. 이번 실습에서는 먼저 행을 넣은 요청이 항상 커밋했어요. MySQL 문서의 INSERT 잠금 설명에는 첫 삽입 트랜잭션이 롤백할 때, 같은 키의 중복 검사를 기다리던 두 세션이 S 잠금을 받은 뒤 서로 X 잠금을 얻지 못해 교착이 생기는 예가 있어요. 삽입 뒤의 다른 작업이 실패해 롤백되는 구조라면 ③·④도 1213을 받을 수 있다는 뜻이에요. 이 조건은 이번 실습에서 재현하지 않았어요. 또 ④에서 1062 뒤 같은 트랜잭션으로 행을 UPDATE하면 ①과 같은 S→X 잠금 전환이 생겨요. 따라서 이번 비교에서 교착이 없었던 패턴에도 트랜잭션 전체를 재시도할 준비는 필요해요.

5. 재시도는 트랜잭션 바깥에

MySQL 문서는 교착으로 실패한 트랜잭션을 재시도할 수 있도록 준비하라고 안내해요. 1213이 발생하면 문장 하나가 아닌 트랜잭션 전체가 롤백되므로(5편), 재시도도 전체 트랜잭션을 처음부터 실행해야 해요. 실패한 문장만 메서드 안에서 다시 실행하면 앞서 수행한 문장의 결과가 사라진 상태로 나머지 작업을 진행할 수 있어요.

그림 3. 매 재시도에서 새 트랜잭션으로 전체 작업을 다시 실행해야 해요

Spring Framework 7.0부터는 별도의 Spring Retry 없이 코어의 재시도 기능을 사용할 수 있어요. 프로그램 방식은 RetryTemplate이에요. 실습에서는 오류 코드 1213과 1205만 최대 3번 더 시도하도록 설정했어요. 지연은 20ms이고 지터는 10ms예요.

RetryTemplate retry = new RetryTemplate(RetryPolicy.builder() .includes(PessimisticLockingFailureException.class) // 교착·잠금 대기만 .maxRetries(3) .delay(Duration.ofMillis(20)) .jitter(Duration.ofMillis(10)) .build()); Verdict v = retry.invoke(() -> tx.execute(s -> firstVisit(key, payload))); // ↑ 바깥: 재시도 ↑ 안쪽: 시도마다 새 트랜잭션

아래 결과를 낸 실습 코드는 원시 JDBC를 사용하므로 예외 클래스 대신 오류 코드로 재시도 여부를 정하는 predicate를 썼어요.

실패 재시도한 요청 추가 시도 p50 p99 ① 재시도 없음 180 0 0 2.4~2.8ms 5.4~11.1ms ① RetryTemplate 0 180 188~199 9.8~27.6ms 65.3~71.1ms ⑤ 재시도 없음 270 0 0 1.9~2.2ms 5.7~7.2ms ⑤ RetryTemplate 0 270 270 30.8~31.5ms 40.5~42.5ms (세 바퀴의 범위, 각 360건, 판정 오류 0)

재시도를 적용한 비교에서는 실패가 0건이었고 판정도 모두 맞았어요. 다시 시도할 때 이미 행이 있으면 ①은 IGNORE가 0을 반환하고, ⑤는 조회 결과로 행을 확인해요. 다만 ①은 재시도한 요청 180건에 추가 시도가 188~199번 필요했어요. 재시도 중에도 교착이 생긴 거예요. lock_deadlocks 증가분도 재시도 전 180에서 188~199로 늘었고, p99 지연은 5~11ms에서 65~71ms로 증가했어요. 이번 실험에서 재시도는 최종 실패를 없앴지만 교착 횟수와 지연은 늘었어요. 먼저 교착을 줄이는 패턴을 선택하고, 남을 수 있는 실패에 재시도를 적용하는 편이 좋아요.

어노테이션 방식은 @Retryable이며 @EnableResilientMethods로 활성화해요. 실습에서 참고한 레퍼런스의 기본값은 모든 예외를 최대 3번 더, 1초 간격으로 시도하는 것이어서 includes로 대상을 좁혔어요. @Transactional과 같은 메서드에 붙일 때는 적용 순서도 확인해야 해요. 당시 7.0.9 레퍼런스에는 이 순서가 없었고, 개발 중이던 7.1 문서(7.1.0-M2)의 "With @Transactional" 절에는 "Retry (OUTER) → Transaction (INNER)"와 "Each retry attempt starts a fresh transaction"으로 명시돼 있었어요. 7.0.9 소스의 RetryAnnotationBeanPostProcessor 생성자는 setBeforeExistingAdvisors(true)를 설정해요. 이 플래그의 Javadoc은 기존 어드바이스가 붙은 객체를 만나면 그 어드바이저 바깥에 새 어드바이저를 배치한다고 설명해요. 실습에서도 재시도가 트랜잭션 바깥에 적용되는지 order 모드로 확인했어요. 아래 메서드는 첫 시도에서만 실패하도록 만들었습니다.

@Retryable(includes = PessimisticLockingFailureException.class, maxRetries = 3, delay = 20) @Transactional public String failOnce(String key) { ... } attempt 1 start: tx_active=true connection_id=452 inserted order-1 attempt 1 tx completed: ROLLED_BACK attempt 2 start: tx_active=true connection_id=452 inserted order-2 attempt 2 tx completed: COMMITTED rows left: [order-2]

각 시도에서 트랜잭션이 시작하고 종료됐으며, 첫 시도가 넣은 order-1은 롤백으로 사라졌어요. ①을 JdbcTemplate으로 구현해 같은 4건 동시 × 90라운드로 비교했을 때는 재시도 없이 360건 중 169~172건이 실패했고, @Retryable 적용 후에는 0건이었어요. 이 비교는 독립 연결 4개 대신 Spring의 Hikari 공유 풀(최대 8개)을 사용해서 원시 JDBC의 실패 수 180건과 조금 달랐어요. 전체 시도 수 547~558번에서 첫 시도 360번을 빼면 앞 표와 같은 기준의 추가 시도는 187~198번이에요. 이 동작은 프록시를 거치는 호출에 적용돼요. 같은 클래스 안에서 this.firstVisit()로 호출하면 해당 호출에 재시도와 트랜잭션 어드바이스가 새로 적용되지 않아요.

⚠️ 주의: 재시도 조건은 공통 부모 예외로
이 실습(Spring Framework 7.0.9, JdbcTemplate)에서는 교착 오류가 CannotAcquireLockException으로 전달됐어요. 클래스패스 루트에 sql-error-codes.xml이 없으면 SQLExceptionSubclassTranslator를 쓰고, 이 번역기가 SQLSTATE 40001을 CannotAcquireLockException으로 바꾸기 때문이에요. 루트에 그 파일을 둔 비교에서는 사용 중단 권고(deprecated) 상태인 DeadlockLoserDataAccessException이 전달됐고, EntityManager를 직접 쓰는 빈에서는 JPA 예외가 전달됐어요(5편 실측). 두 Spring 예외를 함께 처리하려면 공통 부모인 PessimisticLockingFailureException을 재시도 조건으로 지정할 수 있어요.
📖 용어: 멱등 키 (idempotency key)
같은 요청을 여러 번 보내도 결과가 한 번 보낸 것과 같게 만들기 위해 요청마다 붙이는 고유 값이에요. 서버는 이 키로 "이미 처리한 요청인가"를 판단합니다.

이번 실습에서는 같은 키로 다시 실행해도 두 번째는 중복으로 끝나므로 재시도 뒤에도 행이 하나였어요. 외부 결제 호출이나 메시지 발행처럼 DB 밖의 작업은 비교에 포함하지 않았어요. 그런 작업까지 반복해도 안전한지는 이 결과만으로 판단할 수 없어요. 클라이언트의 멱등 키를 유니크 키로 저장하는 데에는 ③이나 ④를 검토할 수 있지만, 외부 작업을 포함한 전체 흐름의 중복 처리는 별도로 확인해야 해요.

6. 기존 운영 사례와 API 시험 기록

기존 운영 사례에서는 같은 사용자의 첫 방문 요청 3개가 동시에 들어왔을 때 교착이 발생했어요. 당시 코드는 ① 방식이었어요.

ODKU로 바꾸는 제안도 있었지만 채택하지 않았어요. 무변경 갱신에서도 Connector/J 기본값은 1을 반환하므로, 기존 코드가 의존하던 저장/중복 판정을 유지할 수 없었기 때문이에요. 이번 비교에서 ②의 판정이 270건 틀린 것과 같은 문제예요. 2차 수정에서는 같은 값이 이미 저장돼 있으면 잠금 없는 조회로 확인하고 중복으로 끝내도록 바꿨어요. 당시 기록에는 같은 본문 요청 4건을 동시에 보내는 시험 360건에서 수정 전 195건이 실패했고 수정 뒤에는 0건이었다고 남아 있어요. 이 수치는 이번 패턴 비교의 180건과 구분해야 해요. 기존 글에는 같은 결과가 있지만, 당시 API 시험의 원출력은 이번에 대조한 로컬 실습 자료에 포함돼 있지 않았어요.

당시 실패 응답은 500이 아닌 400으로 기록됐어요. 공통 예외 핸들러가 처리하지 않은 예외를 400으로 돌려주던 것이 원인이었어요. 4xx 응답을 재시도하지 않는 클라이언트라면 이 교착 요청도 재전송 대상에서 빠질 수 있어요. 이 HTTP 응답 역시 기존 운영 기록에 따른 설명이며, 이번 DB 패턴 실험으로 다시 확인한 결과는 아니에요.

7. 중복 비율과 트랜잭션 범위에 맞춰 선택하기

이번 비교에서는 FOR UPDATE를 먼저 실행해도 없는 행에 대한 삽입 경쟁을 막지 못했어요(⑤, RR에서 교착 270건). RC로 낮춰도 ①의 교착은 그대로였고, ⑤는 1062로 실패한 요청 수가 270건이었어요. ODKU는 교착 없이 끝났지만 저장 여부의 판정이 드라이버 설정에 따라 달라졌어요(②, 270건 오판). 선택할 때는 교착 여부와 중복 판정을 함께 봐야 해요.

💡 내 코드에서 바꿀 것
• INSERT IGNORE나 1062 뒤에 같은 트랜잭션으로 FOR UPDATE, UPDATE를 실행하는 부분부터 확인하세요. ①과 같은 잠금 전환이 생길 수 있어요. 행을 잠글 필요가 없다면 잠금 없는 조회를 검토하세요.
• 없는 행을 SELECT … FOR UPDATE로 조회한 뒤 INSERT하는 부분도 확인하세요. RR에서는 ⑤처럼 갭 잠금이 생기고, RC에서도 1062 처리는 필요해요.
• 중복이 흔한 경로라면 ④를 검토하세요. 먼저 잠금 없이 조회하고, 없으면 INSERT하며, 1062가 나면 롤백 후 새 트랜잭션에서 같은 값인지 확인하는 방식이에요. 중복이 드물고 예외로 판정을 마칠 수 있으면 ③을 검토할 수 있어요.
• 저장/중복 판정에 ODKU 반환값을 쓰고 있다면 useAffectedRows 설정을 확인하세요. 기본값에서는 무변경 중복도 1을 반환해요.
• Spring JDBC에서는 PessimisticLockingFailureException처럼 재시도할 예외를 좁히고, 지터를 포함한 재시도를 트랜잭션 바깥에 두세요. 실습의 Spring 7.0.9에서는 같은 메서드의 @Retryable이 @Transactional 바깥에 적용됐어요. 프록시를 거치는 호출이어야 해요.
• 이 부모 예외에는 1205(잠금 대기 시간 초과)도 포함돼요. 1205의 재시도를 구분하려면 원인 예외의 errorCode를 확인하는 predicate를 사용하세요(5편). EntityManager를 직접 쓸 때 발생하는 jakarta.persistence.PessimisticLockException, LockTimeoutException은 이 부모의 하위 예외가 아니므로 따로 처리해야 해요.
• 공통 예외 핸들러가 교착 오류를 4xx로 바꾸는지도 확인하세요. 클라이언트의 재시도 정책에 영향을 줄 수 있어요.
• 같은 키로 N건을 동시에 보내는 테스트를 포함하세요. 요청을 한 번씩 실행하는 테스트만으로는 이번에 확인한 경쟁을 검증하기 어려워요.

참고한 공개 자료: MySQL 8.4 Reference Manual 의 Locks Set by Different SQL Statements in InnoDB, InnoDB Locking, Transaction Isolation Levels, How to Minimize and Handle Deadlocks, INSERT … ON DUPLICATE KEY UPDATE, Connector/J 의 연결 속성(useAffectedRows), Spring Framework 의 Resilience Features(7.0.9, 그리고 @Transactional 순서가 명시된 7.1 개발판) 와 RetryAnnotationBeanPostProcessor 소스, AbstractAdvisingBeanPostProcessor Javadoc. 실습 코드는 labs/db/dl-06-upsert-patterns 에 있습니다.

✍️ 비교 결과와 적용 범위
같은 키 4건 동시 × 90라운드에서 INSERT IGNORE 다음 FOR UPDATE는 360건 중 180건, 없는 행에 FOR UPDATE를 먼저 실행한 패턴은 270건이 교착으로 실패했어요. READ COMMITTED에서도 전자는 그대로였고 후자는 1062로 270건이 실패했어요.

ODKU 무변경은 드라이버 기본값에서 중복도 1을 반환해 270건을 잘못 판정했어요. INSERT 후 1062 처리와 잠금 없는 조회 후 분기는 이번 비교에서 교착이 0건이고 360건의 판정도 모두 맞았어요. 이미 저장된 중복을 조회만으로 처리하는 후자는 중복 검사 잠금도 없었어요. 다만 먼저 삽입한 트랜잭션이 롤백하는 조건까지 재현한 결과는 아니에요.

트랜잭션 바깥에 재시도를 둔 비교에서는 최종 실패가 0건이었지만, ①의 p99 지연은 65~71ms로 늘었어요. 중복이 잦으면 조회 후 분기를, 중복이 드물면 INSERT 후 1062 처리를 검토하되, 두 방식 모두 트랜잭션 전체를 다시 실행할 수 있도록 준비해야 해요.
