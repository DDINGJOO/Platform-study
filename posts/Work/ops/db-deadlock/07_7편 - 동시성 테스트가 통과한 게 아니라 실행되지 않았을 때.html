7편. Testcontainers 테스트가 SKIPPED로 끝나도 빌드는 성공하는 이유 ← 지금 이 글

교착을 고치는 PR에 같은 키로 요청 세 개를 동시에 보내는 테스트를 붙였다고 해 볼게요. 로컬 빌드에 BUILD SUCCESSFUL이 표시돼도, 테스트 리포트에는 PASSED 대신 SKIPPED가 남을 수 있어요. 이 경우 빌드는 성공했지만 확인하려던 테스트는 실행되지 않은 거예요.

아래 실무 경위는 당시 경험을 정리한 것이에요. 과거 실무 빌드와 테스트 결과의 원본은 이번에 대조하지 못했으며, 뒤의 별도 실습 결과와는 구분해야 해요.

실무에서 겪은 일도 테스트가 건너뛰어진 경우였어요. 로컬 Docker는 29, 프로젝트의 Testcontainers는 1.19.8이었어요. 이 조합에서 Testcontainers가 Docker를 찾지 못했고, 통합 테스트는 실패 대신 skip으로 끝났어요. 빌드는 성공했기 때문에 이미 실패하는 통합 테스트도 드러나지 않았어요. 이후 별도 실습에서 DB 엔진과 Testcontainers 버전을 바꾸며 결과를 비교하고, CI에서 테스트 실행 여부를 검사했어요.

🧭 이 글에서 확인할 것
• H2의 MySQL 모드로 1편의 교착 시나리오를 돌리면 재현되나?
• Testcontainers는 Docker를 못 찾으면 실패하나, 건너뛰나? DOCKER_HOST를 틀리게 주면 어떻게 되나?
• Docker 29에서 옛 Testcontainers는 왜 Docker가 "없다"고 하나? 몇 버전부터 되나?
• CI에서 skip이 0 인지 빌드가 검사하게 하려면?
• 수정 전 코드에서 실패하는 동시성 테스트를 어떻게 구성하나?

1. H2의 MySQL 모드는 고치기 전 코드도 통과시킨다

H2는 Docker 없이 테스트에 사용할 수 있는 인메모리 DB예요. MySQL 문법 일부를 지원하는 호환 모드도 있어서, 1편의 교착 시나리오를 H2에서도 돌려 봤어요.

📖 용어: H2 호환 모드 (MODE=MySQL)
JDBC URL에 MODE=MySQL을 붙이면 H2가 MySQL 문법 일부를 받아 주는 설정이에요. INSERT IGNORE, ON DUPLICATE KEY UPDATE 같은 문장이 오류 없이 실행됩니다. 문법을 받아 주는 것이지, 저장 엔진의 동작까지 MySQL 처럼 바뀌는 건 아니에요.

시나리오는 1편의 "첫 방문 동시 요청 3개" 입니다. 라운드마다 새 키를 하나 정하고, 스레드 세 개가 동시에 출발해서 각자 한 트랜잭션 안에서 INSERT IGNORE → SELECT … FOR UPDATE → UPDATE cnt = cnt + 1 → COMMIT을 합니다. 30 라운드, 요청 90개를 보내고 "90개가 전부 성공하고 키마다 cnt가 3" 이면 통과예요. 같은 테스트 클래스를 DB만 바꿔 돌렸습니다.

(results/summary.txt, 고치기 전 코드, 30 라운드 × 스레드 3) DB 성공 / 요청 실패 cnt 가 3 이 아닌 키 H2 2.4.240 MODE=MySQL 90 / 90 0 0 → PASSED MySQL 8.4 (Testcontainers) 60 / 90 1213 교착 30건 30 → FAILED (세 바퀴 모두 같음)

같은 코드가 H2에서는 통과했고, MySQL에서는 기본 격리 수준인 REPEATABLE READ를 유지한 상태로 30 라운드 전부에서 교착이 났다는 뜻이에요. MySQL 쪽은 라운드마다 정확히 한 요청이 1213으로 되돌려졌습니다. 이 실습에서 H2 쪽은 90개 요청이 모두 성공했어요. 1편의 교착은 중복을 만난 요청 둘이 함께 기다렸다가 둘 다 X 잠금을 요청할 때 납니다. 그 순서를 H2에서 세 세션으로 그대로 만들어 시각을 찍었어요. B와 C가 둘 다 INSERT IGNORE를 끝낸 것을 배리어로 맞춘 뒤에 둘 다 FOR UPDATE를 보내게 했습니다.

(results/h2.txt, H2LockProbeTest. A 가 넣고 1초 뒤에 FOR UPDATE, UPDATE, COMMIT) + 2ms A INSERT IGNORE -> 1 + 3ms B INSERT IGNORE 시작 + 3ms C INSERT IGNORE 시작 +1007ms A SELECT ... FOR UPDATE, UPDATE, COMMIT +1030ms C INSERT IGNORE -> 0 +1031ms B INSERT IGNORE -> 0 +1031ms B SELECT ... FOR UPDATE 시작 +1031ms C SELECT ... FOR UPDATE 시작 +1032ms B SELECT ... FOR UPDATE, UPDATE 끝 +1032ms B COMMIT +1033ms C SELECT ... FOR UPDATE, UPDATE 끝 +1033ms C COMMIT +1035ms 최종 cnt = 3

→ B와 C는 A가 커밋할 때까지 1초를 함께 기다렸다가 둘 다 0행으로 끝났어요. 그다음 둘이 거의 동시에 FOR UPDATE를 보냈는데, B가 먼저 끝내고 C가 1ms 뒤에 이어받았습니다. 당시 정리에는 세 차례 실행에서 같은 순서로 끝났다고 적혀 있지만, 보관 결과에서 확인할 수 있는 H2 잠금 조회 실행은 한 차례예요. 세 차례 반복의 독립 기록은 재확인하지 못했어요. 1편의 InnoDB 실습에서는 이 지점에서 B와 C가 중복 검사 후 얻은 S 잠금을 각각 유지한 채 X 잠금을 요청해 서로 기다렸어요. H2에서는 교착 없이 차례로 진행됐어요. H2 내부의 잠금까지 확인한 것은 아니므로, 이 실행에서는 InnoDB와 같은 교착이 관찰되지 않았다고 한정할 수 있어요.

그림 1. 같은 순서, 다른 결과. InnoDB는 B와 C가 서로 막히고, H2는 차례로 끝난다

H2 문서에도 호환 모드의 범위가 나와 있어요. 호환 모드 절은 데이터베이스 간 차이 가운데 "작은 일부만" 이런 방식으로 구현했다고 적고, MySQL 모드 항목에는 INSERT IGNORE가 "부분적으로 지원된다"고 적습니다(H2 Features, Compatibility). 문법이 통과하는 것과 잠금이 같은 것은 별개의 일이에요. H2 로 쓴 동시성 테스트는 "InnoDB에서 교착이 안 난다"가 아니라 "H2에서 교착이 안 난다"를 증명합니다.

리포지토리를 목(mock)으로 바꾸면 DB의 잠금 동작을 확인할 수 없어요. SQL이 DB에 닿지 않으니 잠금이 아예 없습니다. 목 테스트는 "1213이 오면 재시도하나"처럼 예외를 받은 뒤의 코드를 검사하는 데는 쓸 수 있지만, 교착이 나는지는 알려 주지 못해요. 그래서 동시성 테스트는 운영과 같은 엔진과 같은 메이저 버전으로 돌려야 하고, 보통 그 수단이 Testcontainers 입니다. 다만 Testcontainers를 사용하더라도 설정에 따라 테스트가 건너뛰어질 수 있어요.

2. Testcontainers가 Docker를 못 찾으면: 기본은 실패, 옵션을 켜면 SKIPPED

📖 용어: Testcontainers
테스트 코드에서 Docker 컨테이너를 띄우고 내리는 Java 라이브러리예요. JUnit 5에서는 클래스에 @Testcontainers, 필드에 @Container를 붙이면 테스트 전에 MySQL 같은 컨테이너가 뜨고 끝나면 정리됩니다.

@Testcontainers에는 disabledWithoutDocker 속성이 있어요. 소스의 Javadoc은 이 속성을 "Docker를 쓸 수 없을 때 테스트를 실패시키는 대신 비활성화할지"라고 설명하고, 기본값은 false 입니다(Testcontainers.java). Docker 없는 노트북에서도 빌드가 깨지지 않게 하려고 많이 켜는 옵션이에요. 같은 테스트를 두 클래스로 나눠 하나는 이 옵션을 켜고(SkippingMysqlTest), 하나는 기본값으로 뒀습니다(StrictMysqlTest).

@Testcontainers(disabledWithoutDocker = true) // StrictMysqlTest 는 그냥 @Testcontainers class SkippingMysqlTest extends FirstVisitContract { @Container static final GenericContainer<?> MYSQL = new GenericContainer<>("mysql:8.4") .withEnv("MYSQL_ROOT_PASSWORD", "lab").withEnv("MYSQL_DATABASE", "lab") .withExposedPorts(3306) .waitingFor(Wait.forLogMessage(".*ready for connections.*port: 3306.*", 1)); ... }
그림 2. Docker를 찾지 못했을 때 실패할지 건너뛸지는 옵션에 따라 달라져요

처음에는 Docker를 못 찾게 만들려고 DOCKER_HOST를 아무도 듣지 않는 주소(tcp://127.0.0.1:39071)로 줬어요. 결과는 예상과 달랐습니다. 두 클래스 모두 skip 되지 않고 실제로 MySQL을 띄워 교착 30건으로 실패했어요.

(results/a-dockerhost-fallback.txt, Testcontainers 2.0.5) WARN DockerClientProviderStrategy - DOCKER_HOST tcp://127.0.0.1:39071 is not listening INFO DockerClientProviderStrategy - Found Docker environment with local Unix socket (unix:///var/run/docker.sock)

→ DOCKER_HOST가 응답하지 않는다고 경고만 남기고, 다음 후보인 로컬 유닉스 소켓으로 넘어가 Docker를 찾았다는 뜻이에요. Testcontainers는 Docker를 찾는 방법(전략)을 여러 개 차례로 시도하고, 처음 성공한 것을 씁니다(DockerClientProviderStrategy.getFirstValidStrategy, 1.x도 같은 구조예요). 이 머신에서 그다음 후보는 예전 실행이 ~/.testcontainers.properties에 기록해 둔 유닉스 소켓 전략이었어요. 원출력에도 "Loaded … UnixSocketClientProviderStrategy from ~/.testcontainers.properties, will try it first" 가 찍혀 있습니다. 그러니 "Docker를 못 찾는다"는 건 주소 하나가 틀린 상황이 아니라 모든 후보가 실패한 상황이에요. Docker가 없는 CI 러너나 다음 절처럼 API 버전이 맞지 않는 경우에도 모든 후보가 실패할 수 있어요.

모든 후보가 실패했을 때 두 클래스가 어떻게 끝나는지는 다음 장의 실측에 같이 담았어요. 기본값 클래스는 테스트 메서드에 들어가기도 전에 initializationError 로 실패하고, 원인으로 IllegalStateException 과 "Could not find a valid Docker environment" 로그가 남습니다. 빌드가 실패하므로 테스트 환경을 확인하게 돼요. 옵션을 켠 클래스는 같은 로그를 테스트의 표준 오류에 남기고 SKIPPED 로 끝납니다. 그런데 Gradle은 testLogging을 따로 설정하지 않으면 콘솔에 SKIPPED 줄도, 그 원인 로그도 찍지 않아요. 테스트 하나가 skip 되는 최소 프로젝트를 Gradle 9.8.1 기본값으로 돌리니 콘솔에는 > Task :test 다음 BUILD SUCCESSFUL만 나왔고, XML 에만 skipped="1"이 남았습니다(results/gradle-default-console.txt). 이 글의 실행 화면에 SKIPPED 줄과 원인 로그가 보이는 건 실습의 build.gradle이 testLogging에 skipped와 표준 출력을 켜 두었기 때문이에요. 이 옵션으로 건너뛴 테스트는 빌드 성공 여부만 봐서는 구분할 수 없어요. 테스트 리포트나 실행 건수도 확인해야 해요.

3. Docker 29에서 구버전 Testcontainers가 Docker를 찾지 못한 이유

📖 용어: Docker API 버전
Docker 클라이언트가 데몬에 보내는 요청 경로 앞에 붙는 버전이에요(/v1.44/containers/json 처럼). 데몬은 받아 줄 최소 버전을 정해 두고, 그보다 낮은 버전으로 온 요청은 거절합니다.

Docker Engine 29.0.0(2025-11-10) 릴리스 노트에는 "데몬은 이제 API 버전 v1.44 이상(Docker v25.0+)을 요구한다"는 항목이 있어요. 그리고 29.3.0(2026-03-05)에서 "최소 API 버전을 v1.44에서 v1.40(Docker 19.03)으로 낮춘다"고 다시 내렸습니다(Docker Engine 29 release notes). Testcontainers 쪽 릴리스 노트는 이렇게 이어져요(testcontainers-java releases).

2.0.2 2025-11-13 Set default docker API version to 1.44 (#11216) 1.21.4 2025-12-15 This release makes version 1.21.x works with recent Docker Engine changes. 2.0.3 2025-12-15 Fix compatibility with older Docker Engines by falling back to v1.32 (#11346)

29.3.0에서 최소 API 버전이 1.40으로 낮아졌지만, 실습에서는 구버전 Testcontainers가 여전히 연결하지 못했어요. 이 글의 실습 머신은 Docker Desktop 4.78.0, 엔진 29.5.3 이고 최소 API가 1.40 입니다. 같은 SkippingMysqlTest를 Testcontainers 버전만 바꿔 돌렸어요.

그림 3. Docker는 떠 있는데 400, 그리고 SKIPPED와 BUILD SUCCESSFUL (실습은 testLogging에 skipped를 켜 둠)

→ 1.19.8은 유닉스 소켓도 Docker Desktop 소켓도 찾았지만 둘 다 Status 400으로 거절당해 "유효한 Docker 환경을 찾지 못했다"고 결론 냈어요. disabledWithoutDocker = true 라서 테스트는 SKIPPED, 빌드는 성공이었습니다. 교착이 30건 나야 하는 고치기 전 코드인데도요. 400 응답의 이유를 확인하려고 소켓을 통해 API 버전별로 직접 요청했어요.

(results/curl-api-versions.txt, Docker Desktop 4.78.0, 엔진 29.5.3) curl --unix-socket /var/run/docker.sock http://localhost/v1.32/version → 400 .../v1.39/version → 400 .../v1.40/version → 200 .../v1.44/version → 200

→ 1.40 미만은 전부 거절된다는 뜻이에요. 1.19.8 소스의 DockerClientProviderStrategy는 API 버전이 따로 정해지지 않았으면 RemoteApiVersion.VERSION_1_32를 넣어요(1.19.8 DockerClientProviderStrategy.java 409-410행). 같은 파일의 1.21.4와 2.0.5 판은 1.44를 먼저 씁니다. 최소 지원 버전이 1.44에서 1.40으로 낮아져도 1.32 요청은 여전히 지원 범위 밖이에요. 버전별 결과는 이랬습니다.

(results/summary.txt, Docker 29.5.3, 고치기 전 코드) Testcontainers 결과 1.19.8 Docker 못 찾음(400) → SKIPPED, BUILD SUCCESSFUL 1.21.3 Docker 못 찾음(400) → SKIPPED, BUILD SUCCESSFUL 1.21.4 붙음 → 교착 30/30 라운드 → FAILED 2.0.5 붙음 → 교착 30/30 라운드 → FAILED 1.19.8 + 시스템 속성 api.version=1.44 붙음 → 교착 30/30 라운드 → FAILED 1.19.8, @Testcontainers 기본값 initializationError (IllegalStateException) → FAILED
그림 4. 요청 API가 엔진의 최소 지원 버전보다 낮으면 연결할 수 없어요

이 버전 불일치를 해결하려면 Testcontainers를 올려야 해요. 1.x에 머물러야 하면 1.21.4 이상입니다. 2.x는 릴리스 노트상 2.0.2 부터 기본 API를 1.44 로 보내고, 2.0.3은 지원하는 최대 API가 1.44보다 낮은 엔진에도 연결할 수 있도록 1.32로 재시도하는 폴백을 추가했어요. 이 릴리스 설명을 기준으로 Docker 29와 이전 엔진을 함께 쓴다면 2.0.3 이상을 검토할 수 있어요. 실측은 1.21.4와 2.0.5 에서만 했어요(2.0.2~2.0.4는 돌려 보지 않았습니다). 2.0.0 과 2.0.1은 소스상 1.19.8 과 같은 1.32 기본값이라 Docker 29에서 같은 증상이 날 것으로 보지만, 이것도 돌려 보지는 않았어요. 당장 올릴 수 없다면 테스트 JVM에 docker-java의 api.version 시스템 속성을 1.44 로 주는 우회가 1.19.8에서도 통했어요. 다만 특정 API 버전을 강제하는 우회이므로, 라이브러리 업데이트 전까지의 임시 대응으로 구분해야 해요.

⚠️ 주의: 같은 저장소, 다른 결과
같은 커밋이라도 Docker 버전과 테스트 설정에 따라 결과가 달라질 수 있어요. Docker 29와 구버전 Testcontainers의 조합에서는 테스트가 건너뛰어질 수 있으니, 로컬 빌드 성공만으로 통합 테스트가 실행됐다고 판단하기 어려워요. 앞서 겪은 사례에서도 이 때문에 기존 통합 테스트의 실패가 드러나지 않았어요.

4. CI에서 skip이 0 인지 빌드가 검사하게 한다

버전을 맞추는 건 이번 원인 하나를 막을 뿐이에요. 다음에는 러너에 Docker가 빠지거나, 누가 assumeTrue를 넣을 수 있습니다. 원인과 상관없이 막으려면 "통합 테스트가 하나라도 실행되지 않았으면 빌드 실패"를 규칙으로 둬야 해요.

📖 용어: JUnit XML 리포트
테스트 실행 결과를 클래스마다 XML 파일로 남긴 것이에요. Gradle은 build/test-results/test/TEST-*.xml에 남기고, <testsuite tests="1" skipped="1" failures="0" ...> 처럼 건수가 속성으로 들어 있습니다. CI 도구들이 테스트 결과 화면을 그릴 때 읽는 형식이에요.

방법 1. XML의 skipped를 합쳐서 0이 아니면 실패

가장 일반적인 방법이에요. 빌드 도구나 테스트 라이브러리와 상관없이 XML만 읽습니다. Gradle에서는 태스크 하나로 붙여요.

def resultsDir = layout.buildDirectory.dir('test-results/test') def checkNoSkipped = tasks.register('checkNoSkipped') { inputs.dir(resultsDir).optional() doLast { def dir = resultsDir.get().asFile def files = dir.isDirectory() ? dir.listFiles({ f -> f.name.endsWith('.xml') } as FileFilter) : null if (files == null) throw new GradleException("테스트 결과 디렉터리가 없다: ${dir}") int tests = 0, skipped = 0 def names = [] files.each { f -> def suite = new groovy.xml.XmlSlurper().parse(f) tests += (suite['@tests'].text() ?: '0') as int int s = (suite['@skipped'].text() ?: '0') as int skipped += s if (s > 0) names << "${suite['@name'].text()} (${s})" } println "checkNoSkipped: tests=${tests} skipped=${skipped}" if (tests == 0) throw new GradleException('테스트가 하나도 실행되지 않았다') if (skipped > 0) throw new GradleException("skip 된 테스트가 ${skipped}개 있다: ${names.join(', ')}") } } if (hasProperty('noSkip')) { // CI 에서만: ./gradlew test -PnoSkip tasks.named('test') { finalizedBy checkNoSkipped } }

세 군데를 일부러 이렇게 했어요. finalizedBy 로 붙여서 테스트가 실패해도 검사가 돌아요. tests == 0 과 결과 디렉터리가 없는 경우도 실패로 봐서, 필터가 잘못돼 아무것도 안 돈 빌드를 잡습니다. 그래서 멀티 모듈이라면 통합 테스트가 있는 모듈의 test 태스크에만 붙여야 해요. 테스트가 없는 모듈에 붙이면 결과 디렉터리가 없어 거짓 실패가 납니다. 그리고 -PnoSkip 일 때만 켜서 Docker 없는 노트북의 로컬 빌드는 그대로 두고 CI만 엄격하게 해요. 같은 1.19.8 조합을 CI 모드로 돌린 화면입니다.

그림 5. 같은 SKIPPED가 이번에는 빌드를 막는다

→ 테스트 자체는 그림 3 과 똑같이 SKIPPED 였지만 checkNoSkipped가 tests=1 skipped=1을 세고 빌드를 실패시켰어요. JUnit의 Assumptions.assumeTrue(false) 로 중단된 테스트도 Gradle XML에 skipped="1" 로 남아서 같은 검사에 걸렸습니다(임시 테스트로 확인, results/assume-noskip.txt). Maven Surefire도 같은 모양의 TEST-*.xml을 남기니, 같은 검사를 작은 스크립트로 CI 단계에 붙일 수 있어요. 일부러 @Disabled 해 둔 테스트가 있는 저장소라면 통합 테스트만 따로 태스크로 돌리고 그 결과 디렉터리만 검사하면 됩니다.

방법 2. Testcontainers의 조건을 꺼서 skip 대신 실패로

disabledWithoutDocker는 JUnit의 실행 조건(ExecutionCondition)으로 동작해요. JUnit 5 사용자 가이드는 junit.jupiter.conditions.deactivate 설정에 패턴을 주면 그 조건들을 평가하지 않는다고 설명합니다. 예로 든 것은 @Disabled가 붙은 테스트를 일부러 돌려 보는 경우예요(JUnit 5 User Guide, Deactivating Conditions). CI에서 이 값을 org.testcontainers.* 로 주면 옵션은 소스에 그대로 두고 CI 에서만 꺼집니다.

// 예시: CI 환경 변수가 있을 때만. 실습은 같은 값을 -Pdeactivate='org.testcontainers.*' 로 넘겼다 tasks.named('test', Test) { if (System.getenv('CI')) systemProperty 'junit.jupiter.conditions.deactivate', 'org.testcontainers.*' } (results/b-deactivate-1.19.8.txt) SkippingMysqlTest > initializationError FAILED java.lang.IllegalStateException at DockerClientProviderStrategy.java:277 BUILD FAILED

→ 같은 1.19.8 조합이 SKIPPED가 아니라 기본값 클래스와 똑같이 initializationError 로 실패했어요. 원인 메시지가 바로 보인다는 게 장점입니다. 다만 Testcontainers의 조건만 끄니 assumeTrue 로 빠지는 테스트는 못 잡아요. 방법 1을 기본으로 두고, 방법 2는 원인을 빨리 보이게 하는 보조로 쓰는 게 맞습니다.

방법 3. 통합 테스트에서는 건너뛰는 장치를 쓰지 않는다

규칙으로 막는 방법도 있어요. 통합 테스트 디렉터리에서 disabledWithoutDocker = true, assumeTrue, Assumptions.를 금지하고, CI 첫 단계에서 grep으로 찾으면 실패시키는 식입니다. Docker가 없으면 실패하는 게 정상이라고 팀이 합의하는 거예요. 로컬에서 Docker 없이 일하는 사람이 많다면 방법 1 처럼 CI 에서만 엄격하게 하는 쪽이 덜 불편합니다.

5. 수정 전 코드에서 동시성 테스트가 실패하는지 확인하기

건너뛴 테스트가 없더라도 요청이 실제로 겹치는지 확인해야 해요. 스레드를 차례로 시작하면 앞 스레드가 커밋한 뒤에 다음 스레드가 실행될 수 있어요. 그러면 동시 요청에서 교착이 나는 코드도 테스트를 통과할 수 있어서, 이 실습에서는 요청의 출발 시점을 맞췄어요.

📖 용어: CountDownLatch
정해진 횟수만큼 countDown()이 불릴 때까지 await() 하는 스레드들을 대기시키는 Java 동기화 도구예요. 여러 스레드를 준비시켜 놓고 한 번에 출발시킬 때 씁니다.
for (int r = 1; r <= ROUNDS; r++) { // 라운드마다 새 키 = 매번 "첫 방문" long key = r; CountDownLatch ready = new CountDownLatch(THREADS); CountDownLatch start = new CountDownLatch(1); for (Connection c : conns) { // 스레드마다 미리 연 커넥션 futures.add(pool.submit(() -> { ready.countDown(); start.await(); // 전원 준비될 때까지 대기 try { visit(c, impl, key); return "ok"; } catch (SQLException e) { c.rollback(); return e.getSQLState() + "/" + e.getErrorCode(); } })); } ready.await(10, SECONDS); start.countDown(); // 한꺼번에 출발 for (Future<String> f : futures) record(f.get(60, SECONDS)); } assertEquals(0, failed); // 실패한 요청 0 assertEquals(0, keysWhereCntIsNot(THREADS)); // 최종 상태까지 확인

커넥션을 여는 시점부터 맞췄어요. 커넥션은 출발 전에 스레드마다 미리 열어 둡니다. 출발 뒤에 커넥션을 얻으면 그 시간만큼 출발이 흩어져요. ready와 start 래치 두 개로 모든 스레드가 준비된 뒤 함께 출발하게 했어요. 한 번이 아니라 여러 라운드를 돌리고 라운드마다 새 키를 써요. 1편의 교착은 행이 없을 때의 첫 방문에서 나니, 같은 키를 반복하면 두 번째부터는 다른 상황을 재게 됩니다. 예외는 SQLSTATE와 오류 코드별로 집계했어요. 40001/1213이 30건이면 교착으로 실패한 요청을 구분할 수 있어요. 또 "예외가 없다"만이 아니라 최종 상태(cnt가 3)도 확인해요. 교착에 걸린 요청이 재시도 없이 사라지면 예외를 잡는 쪽에서는 조용할 수 있습니다.

수정 전 코드에서도 같은 테스트를 실행했어요. 기존 교착을 재현해 실패하는지 먼저 확인해야 수정 후 통과 결과를 비교할 수 있어요. 수정 전에도 통과한다면 실행 여부, 요청이 겹치는 시점, DB 엔진이 맞는지부터 확인해야 해요. 이 실습은 고치기 전(-Pimpl=buggy)과 고친 뒤(-Pimpl=fixed)를 실제 MySQL 8.4에서 세 바퀴씩 돌렸습니다.

그림 6. 같은 테스트가 수정 전에는 실패, 수정 후에는 통과했고 skip은 모두 0이에요

→ 고치기 전 코드는 세 바퀴 모두 90 요청 중 60 성공, 1213 교착 30건, cnt가 3이 아닌 키 30개로 실패했어요. 고친 코드는 세 바퀴 모두 90 요청 전부 성공, cnt도 전부 3 이었습니다. 두 경우 모두 checkNoSkipped가 skipped=0을 확인했어요. 이 결과는 테스트를 건너뛰어 생긴 빌드 성공과 구분할 수 있어요.

실습에서는 트랜잭션 범위를 바꿨어요. INSERT IGNORE를 자동 커밋으로 먼저 끝내고, 그다음 트랜잭션에서 SELECT … FOR UPDATE와 UPDATE를 해요. FOR UPDATE 시점에 행은 이미 커밋돼 있고, 앞선 중복 검사에서 얻은 S 잠금을 유지하지 않으니 세 요청이 X 잠금을 차례로 받습니다. 대가도 있어요. 행을 넣는 일과 카운트를 올리는 일이 다른 트랜잭션이 되니, 뒤 트랜잭션이 실패하면 cnt가 0인 행이 남습니다. "첫 방문 행이 있다"는 사실 자체가 틀린 게 아닌 테이블이라 이 실습에서는 받아들였어요. 이것 말고도 고르는 방법이 여럿이고 각각 대가가 다른데, 그 비교는 6편에 정리했어요. 어떤 방법을 고르든 자신의 트랜잭션과 데이터 조건에 맞춘 테스트로 수정 전 실패와 수정 후 결과를 비교해야 해요.

6. 빌드 성공과 함께 확인할 항목

💡 내 코드에서 바꿀 것
• 교착·잠금을 검사하는 테스트를 H2 나 목으로 돌리고 있다면, 운영과 같은 엔진과 메이저 버전의 컨테이너로 옮기세요. H2 MySQL 모드는 1편의 시나리오를 90/90 성공으로 통과시켰습니다
• build.gradle / pom.xml에서 Testcontainers 버전을 확인하세요. Docker 29를 쓰는 사람이 있다면 1.21.4 이상, 2.x 라면 2.0.3 이상을 권합니다. 1.19.8 과 1.21.3은 29.5.3에서도 Docker를 못 찾았어요
• disabledWithoutDocker = true와 assumeTrue를 검색하세요. 있다면 CI에서 skip 0 검사(XML의 skipped 합계)를 붙이거나 junit.jupiter.conditions.deactivate 로 CI 에서만 끄세요
• 테스트 리포트에서 PASSED와 SKIPPED를 구분해 보세요. Gradle은 기본 설정에서 SKIPPED 줄을 콘솔에 찍지 않고, BUILD SUCCESSFUL은 둘을 구분하지 않습니다
• 동시성 테스트는 래치로 동시에 출발시키고, 라운드마다 새 키, 오류 코드별 집계, 최종 상태 확인까지 넣으세요
• 수정 전 코드에서 테스트가 기존 교착을 재현해 실패하는지 확인한 뒤, 같은 테스트로 수정 후 결과를 비교하세요
✍️ 오늘의 요약
H2 MySQL 모드에서는 90/90 요청이 성공했지만, MySQL 8.4에서는 30라운드 모두에서 1213 교착이 발생했어요. 이 실행 결과만으로 H2 내부의 잠금 구조까지 설명할 수는 없어요.

Docker 29.5.3에서 Testcontainers 1.19.8과 1.21.3은 API 버전 문제로 연결하지 못했고, disabledWithoutDocker = true일 때는 테스트를 건너뛴 채 빌드가 성공했어요. 1.21.4와 2.0.5는 연결됐어요. 잘못된 DOCKER_HOST만 지정하면 다른 소켓으로 연결되기도 했어요.

CI 검사에서는 JUnit XML의 skipped 합계가 0이 아니면 빌드를 실패시켰어요. 동시성 테스트는 수정 전 실패와 수정 후 통과를 비교하고 두 경우 모두 skip이 0인지 확인했어요. 직접 실행하지 않은 버전에 대한 설명은 소스와 릴리스 노트에 따른 예상으로 구분했어요.
