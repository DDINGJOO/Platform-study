📚 49분 전면 중단, 3부작
1편. 호스트 메모리 고갈로 판단하기까지의 가설 검증
2편. 재부팅 뒤 도커가 시작되지 않아 복구가 늦어졌어요 ← 지금 이 글

당시 대응 정리에는 전면 중단 49분 중 25분을 서버 접속 경로를 찾는 데 썼다고 남아 있어요. 재부팅 뒤에는 도커가 시작되지 않아 복구까지 약 9분이 더 걸렸다고 정리했어요.

아래 시간과 실행 순서는 당시 정리에 따른 것이에요. 사고 당시의 원시 로그와 시계열을 이번에 대조하지 못했으므로, 각 구간의 시간과 원인별 영향을 다시 검증한 결과로 보기는 어려워요.

1. 셸에 들어가는 데 25분

접속 경로를 찾는 데 대응 시간의 절반가량을 썼어요. 경로가 문서화돼 있지 않았고, 여러 접속 시도가 타임아웃이나 미연결로 끝나 어디부터 확인해야 할지 알기 어려웠어요. 베스천은 운영 서버에 접속할 때 거치는 중간 서버예요.

세션 관리자 (운영) TargetNotConnected 역할은 있는데 에이전트 미연결 (AMI 가 4년 전) 인스턴스 접속 엔드포인트 없음 생성된 적 없음 세션 관리자 (베스천) 미연결 베스천에 IAM 역할 자체가 없음 — 영원히 불가 베스천 SSH :22 타임아웃 보안그룹이 다른 포트만 허용 베스천 SSH :20022 성공 베스천 → 운영 타임아웃 재부팅 진행 중이었을 뿐 재부팅 후 재시도 열림

네 번째 시도에서는 보안그룹이 허용한 포트와 접속에 사용한 포트가 달랐어요. 타임아웃만 보고는 방화벽 설정, 네트워크 상태, 서버 응답 중 어디에 문제가 있는지 구분하기 어려웠어요.

베스천이 일시적으로 CPU 성능을 높여 쓰는 버스터블 인스턴스여서 CPU 크레딧 소진도 의심했어요. 당시 확인한 크레딧은 충분했고 CPU 사용률은 0.3%여서, 이 가설은 제외했어요. 포트를 먼저 확인했다면 불필요한 점검을 줄였겠지만, 실제로 얼마나 단축됐을지는 알 수 없어요.

💡 판별 순서: 포트 → 보안그룹 → NACL → 키
이번처럼 SSH 접속이 타임아웃으로 끝났다면 접속 포트와 허용 규칙부터 확인해요. 확인 항목을 미리 적어 두면 장애 중에 점검 순서를 정하는 부담을 줄일 수 있어요.

• 접속 포트가 맞는지 확인해요.
• 보안그룹이 그 포트와 접속 출발지를 허용하는지 확인해요.
• 서브넷의 네트워크 접근 규칙인 NACL에서 요청과 응답 방향을 확인해요.
• 연결이 성립한 뒤 인증에 실패한다면 키와 사용자를 확인해요.

목록에는 실제 접속 경로와 필요한 권한도 함께 적어 두는 편이 좋아요.
💡 시도하지 않았던 시리얼 콘솔
복기하면서 시도한 여섯 경로에 시리얼 콘솔이 빠져 있었다는 점을 확인했어요.

다만 당시 계정의 권한과 인스턴스 설정에서 실제로 접속할 수 있었는지는 확인하지 못했어요. 따라서 시리얼 콘솔을 썼다면 재부팅이나 뒤의 약 9분을 피했을 것이라고 단정할 수는 없어요.

접속 후보를 목록에 넣는 일과 실제로 접속 가능한지 미리 검증하는 일이 함께 필요했어요.

2. 재부팅 판단

중단 35분째에 재부팅을 결정했어요. 셸에 접속하지 못한 상태에서 다음과 같이 판단했어요.

셸이 안 되는 상태에서 가능한 복구 수단이 그것뿐이었다 재부팅은 되돌릴 수 없고, 메모리 상태·스레드 덤프 같은 휘발성 증거가 사라진다 그러나 이미 35분째 전면 중단 → 증거보다 복구가 우선

재부팅 전에는 디스크 스냅샷을 먼저 만들었어요. 디스크 상태를 보존하려는 조치였지만, 스냅샷으로 메모리 상태까지 보존한 것은 아니에요.

재기동 위험도 고려했어요. 당시에는 21개월 동안 재기동하지 않았고, 서버 생성에 쓴 AMI는 4년 전 이미지였으며, 오토스케일링 그룹에 속하지 않은 단독 서버라고 파악했어요. 재부팅 후 정상 기동을 보장할 수는 없었어요.

중단이 길어지면서 증거 수집보다 복구를 우선한 판단이었어요. 다만 재부팅 뒤 서비스가 어떤 순서로 시작되는지는 미리 확인하지 않았어요.

3. OS 기동 뒤에도 도커는 시작되지 않았어요

OS는 1~2분 만에 기동했지만, 로드밸런서가 요청을 보내는 타깃은 계속 타임아웃이었어요. 7분간 상태 변화가 없었어요.

접속 뒤 확인한 도커 데몬은 실행되지 않은 상태였어요. 아래 정리에서 inactive는 서비스가 실행 중이 아니라는 뜻이고, disabled는 부팅 시 자동 시작이 비활성화됐다는 뜻이에요.

docker.service inactive (dead) is-enabled disabled ← 부팅 시 자동 시작이 꺼져 있다

당시에는 컨테이너를 21개월 전 수동으로 시작한 뒤 호스트를 재부팅하지 않아 자동 시작 문제를 발견하지 못한 것으로 정리했어요. 다만 누가 어떤 명령으로 처음 시작했는지까지 이번에 확인한 것은 아니에요.

도커 데몬이 시작되지 않아 컨테이너도 실행되지 않았어요. 서비스를 복구하려면 도커부터 수동으로 시작해야 했어요.

도커 데몬을 시작하자 재시작 정책에 따라 프록시와 앱 컨테이너들이 기동했고, 3분 뒤 정상 응답이 돌아왔어요. 재부팅 후 서비스 기동까지 지연된 구간은 약 9분으로 정리했어요. 다만 원시 기록으로 세부 구간의 시작·종료점과 중첩을 대조하지 못했어요. OS 기동 1~2분, 상태 관찰 7분, 도커 시작 뒤 3분을 단순 합산해 약 9분을 재구성할 수는 없어요.

📄 재부팅 전에 확인하지 않은 호스트 문서
당시 정리에는 닷새 전 블루그린 작업 문서에 다음 경고를 남겼다고 적혀 있어요.

"부팅 시 도커 자동 시작이 꺼져 있다. 이 호스트가 재부팅되면 도커 자체가 안 뜨고 서비스가 통째로 죽은 채 남는다."

재부팅을 결정하기 전에 이 내용을 확인하지 않았어요. 자동 시작 비활성화에 관한 문서는 확인했지만, 작성 시점과 사고 대응 순서를 함께 대조할 실행 증거는 이번 확인에 없어요.

대응 체크리스트에는 접속 방법뿐 아니라 해당 호스트의 부팅 시 주의사항도 필요했어요.
그림 1. OS가 기동해도 도커와 컨테이너의 실행 상태는 따로 확인해야 해요

자동 시작을 유보한 이유도 다시 살펴봤어요. 당시 정리에는 닷새 전 문서에서 컴포즈 프로젝트 세 개를 기동하려면 별도 서비스 유닛이 필요하다고 판단했다고 남아 있어요. 반면 복구 과정에서는 재시작 정책만으로 컨테이너들이 기동했다고 정리했어요. 이 관찰이 맞다면 해당 구성에서는 별도 유닛 없이 복구된 셈이지만, 다른 구성에도 같은 결과를 보장하는 것은 아니에요.

4. 복구 49분, 후속 처리 50분

서비스 복구에는 49분, 복구 뒤 원인 검토와 설정 적용에는 50분이 걸렸어요.

접속 경로 확보 25분 ← 대응 시간의 절반 복구 완료 49분 (2차 중단 9분 포함) 후속 처리 50분 ← 이게 더 길다
그림 2. 당시 정리에 따른 접속 경로 확보, 복구, 후속 처리 시간이에요

당시에는 나흘 동안 메모리 사용이 누적된 것으로 추정했어요. 같은 설정을 유지하면 재발할 가능성을 고려해야 했지만, 다시 나흘 뒤 같은 장애가 난다고 예측할 근거까지 있는 것은 아니었어요.

후속 처리 중 25분은 원인 검토에, 25분은 조치 적용에 썼어요. 재부팅 전 메모리 상태가 없었기 때문에 시스템 통계 이력, 로그 도착 시각의 차이, 컨테이너 실행 스크립트로 경위를 재구성했다고 정리했어요. 다만 그 시계열과 원시 로그를 이번에 확보하지 못해, 추정 원인을 새로 확정하지는 못했어요.

5. 블루그린 전환으로 설정을 적용했어요

설정 적용에는 기존 블루그린 구조를 사용했어요. 실행 중인 쪽과 대기 중인 쪽을 번갈아 전환하는 방식이라, 별도 점검 시간을 잡지 않고 대기 쪽부터 변경했어요.

1차 대기 색을 메모리 상한 걸어 재생성 → 전환 → 이전 색 정지 발견 힙 옵션이 안 먹고 있었다 (3편에서 자세히) 2차 다른 방식으로 재적용 → 반대 색에 반영 → 전환 → 정지 마무리 멈춰둔 대기 색도 같은 설정으로 재생성

전환은 총 2회였고, 전환 전후 서비스 포트에서 200 응답을 확인했어요. 다만 이 관찰만으로 전 구간의 요청이 모두 성공했다고 보장할 수는 없어요.

블루그린 구조는 설정을 순차 적용하는 데 활용했어요. 다만 이 결과만으로 장애 원인이 블루그린 구조였다고 확정하거나, 자원 부족만 해결하면 재발하지 않는다고 결론 내릴 수는 없어요.

⚠️ 메모리 상한 적용 뒤에도 감시가 필요해요
당시에는 메모리 상한을 적용한 뒤, 그 상한 때문에 프로세스가 종료되는 상황을 어떻게 감지할지도 과제로 남겼어요.

강제 종료되면 앱 로그만으로 경위를 확인하기 어려울 수 있어요. 당시 정리의 30초 재기동 수치도 이번에 실행 기록으로 대조하지는 못했어요. 재시작만 보고 정상이라고 판단하지 않으려면 종료 원인과 재시작 횟수를 함께 확인해야 해요.

여기까지는 당시 남긴 후속 과제예요. 감시 장치가 이후 구현됐는지까지 확인한 것은 아니에요.

6. 대응을 되짚으면

당시 대응을 되짚으면서 남긴 평가는 아래와 같아요. 인용한 정리의 시간과 효과 역시 앞서 밝힌 검증 범위 안에서 읽어야 해요.

잘한 것 스냅샷을 먼저 떴다 — 되돌릴 수 없는 조작 전에 증거를 남겼다 가설마다 숫자로 죽였다 — 크레딧 소진도 측정으로 3분 만에 기각 블루그린으로 조치를 무중단 적용했다 복구 후에 멈추지 않았다 못한 것 접속 경로 목록이 없었다 — 25분, 그리고 시리얼 콘솔은 목록에도 없었다 그 호스트 문서를 안 읽고 재부팅했다 — 9분 조치 이후를 감시할 장치를 같이 안 만들었다

접속 경로 목록, 호스트의 부팅 시 주의사항, 조치 이후의 감시 항목을 평소에 준비해 두었다면 대응 중 확인할 대상을 더 빨리 찾을 수 있었을 거예요. 이번 대응에서 놓친 항목은 이 세 가지였어요.

✍️ 대응 정리
당시에는 접속 경로 확보에 25분, 전체 복구에 49분이 걸렸고 재부팅 뒤 서비스 기동 지연이 약 9분을 차지했다고 정리했어요. OS가 기동한 뒤에도 도커와 컨테이너의 상태를 따로 확인해야 했어요.

복구 뒤에는 50분 동안 원인을 검토하고 블루그린 전환으로 설정을 적용했다고 남아 있어요. 다만 원시 로그와 시계열을 이번에 대조하지 못했으므로, 당시의 추정 원인과 전환 전후 관찰을 확정 원인이나 전체 요청의 무중단 보장으로 넓히지는 않았어요.
