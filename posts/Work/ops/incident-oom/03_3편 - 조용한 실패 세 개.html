메모리 장애 후 조치를 적용하면서 설정과 실제 동작이 다른 문제 세 가지를 확인했어요. 컨테이너 메모리 제한이 적용되지 않았고, JVM 힙 상한도 기대한 값으로 줄지 않았어요. 대기 컨테이너를 정지하는 스크립트는 실행 중인 대상을 찾지 못했어요.

세 문제는 실패가 드러난 방식도 달랐어요. 컴포즈는 지원하지 않는 설정이라는 메시지를 냈고, 힙 옵션은 다른 값이 적용됐으며, 스크립트는 조회 오류를 숨겼어요. 아래 실행 결과와 조치는 당시 기록을 기준으로 설명해요. 원시 로그와 실행 환경을 다시 확인하지는 못했어요.

1. 컴포즈 설정과 실제 메모리 제한을 확인했어요

당시에는 호스트 메모리 고갈을 장애 원인으로 판단하고 컨테이너에 메모리 상한을 두기로 했어요. 한 컨테이너의 메모리 사용량을 제한하려는 조치였어요. 상한을 설정했다는 사실만으로 호스트 전체의 메모리 부족이나 중단 가능성이 사라지는 것은 아니에요.

기존 기록에는 컴포즈 파일 형식 2.4와 3.7에서 아래와 같이 다른 결과를 확인했다고 남아 있어요.

파일 버전 2.4 mem_limit: 6g → 적용됨 파일 버전 3.7 Unsupported config option → 무시됨

위 인용의 Unsupported config option은 구형 Compose에서 구성 검증 오류로 실행을 중단시키는 메시지예요. 이를 옵션만 무시하고 새 컨테이너를 정상 기동했다는 증거로 읽으면 안 돼요. 당시 실행 버전과 명령 원본이 없어 기존 컨테이너가 계속 실행됐는지도 확인하지 못했어요.

기존 파일의 형식은 v3.7이었고, 당시 기록은 mem_limit을 지원하지 않는다는 메시지가 나왔다고 설명해요. 다만 파일 형식 번호와 Compose 실행 도구의 버전은 구분해야 해요. 실행 버전과 명령 전체를 다시 확인하지 못했으므로, 이 결과를 모든 도커 컴포즈의 동작으로 일반화할 수는 없어요.

다음은 설정만 추가하고 실제 제한값을 확인하지 않았을 때를 가정한 메모예요. 앞의 지원 오류 메시지와 달리, 모든 실패가 에러나 경고 없이 일어났다는 뜻으로 읽으면 안 돼요.

파일에는 "메모리 6GB 제한" 이라고 적혀 있고 실제로는 무제한 그리고 에러도 경고도 없다

파일에 제한값이 적혀 있어도 컨테이너에 적용됐는지는 따로 확인해야 했어요.

2. 환경변수로 지정한 힙 상한이 적용되지 않았어요

같은 날 JVM 힙 설정도 확인했어요. 1편에서 설명한 이미지에는 힙 상한이 8GB로 고정돼 있었어요. 이미지를 다시 빌드하려면 앱팀과 일정을 맞춰야 해서 환경변수로 값을 바꾸려 했어요.

당시 확인 기록에는 적용 후에도 힙 상한이 8GB였다고 적혀 있어요. 아래는 같은 힙 옵션을 여러 곳에 지정했을 때의 적용 순서를 정리한 메모예요.

JAVA_TOOL_OPTIONS < 명령줄 인자 < _JAVA_OPTIONS (내가 준 -Xmx4g) (이미지의 -Xmx8192m) ← 이게 이겼다

처음 사용한 환경변수의 힙 옵션보다 이미지의 명령줄 옵션이 나중에 적용된 것으로 정리했어요.

다른 환경변수로 옮긴 뒤 실제 힙 상한이 바뀌었다고 기록했어요. 다만 해당 JVM의 버전과 옵션 확인 원본은 이번에 대조하지 못했어요. 여기서는 당시 확인 결과로 한정해요.

💡 실행 중인 적용값을 확인해야 해요
컴포즈의 지원 오류와 JVM 옵션의 중복 지정은 서로 다른 문제였어요. 파일에 원하는 값이 있다는 것만으로는 적용 여부를 판단할 수 없었어요.

컨테이너의 메모리 제한과 JVM의 실제 힙 상한을 각각 확인하는 단계가 필요했어요. 파일 검토는 먼저 하되, 실행 중인 값과 비교해야 했어요.

3. 조회 실패를 대기 컨테이너가 없는 것으로 처리했어요

세 번째 문제는 롤백에 쓰는 컨테이너 조회 과정에 있었어요.

당시 기록에는 새로 만든 대기 컨테이너 정지 스크립트를 실행했지만, 실행 중인 컨테이너가 있는데도 "대기 컨테이너가 없다"고 나왔다고 적혀 있어요. 롤백 전체를 실행해 실패한 결과와는 구분해야 해요.

당시에는 조회 명령이 읽는 컴포즈 파일에 필수 환경변수가 전달되지 않아 실패한 것으로 분석했어요. 스크립트는 에러 출력을 버린 뒤 빈 결과를 받아서, 조회 실패를 "대상 없음"으로 처리한 것으로 정리했어요.

조회 명령이 실패 → 에러가 버려짐 → 빈 결과 → "대기 컨테이너 없음" ↑ 여기서 죽는데 ↑ 여기서는 정상처럼 보인다

같은 조회 처리가 기존 롤백 스크립트에도 있었다고 기록했어요.

닷새 전부터 있던 롤백 스크립트도 같은 실행 환경이라면 대상을 찾지 못할 가능성이 있었어요. 실제 장애 중 롤백이 실패했다는 실행 증거를 확인한 것은 아니에요.

⚠️ 수정과 롤백 종단 검증을 구분했어요
조회 명령과 조건문을 읽는 것에 더해, 필요한 환경변수를 전달한 상태에서 실행 결과를 확인해야 했어요. 조회 실패를 빈 결과와 구분하는지도 확인 대상이에요.

당시에는 코드를 수정했지만 롤백의 종단 검증, 즉 전환부터 복구까지 전체 과정을 확인하지는 못했다고 남겼어요. 전환을 두 번 더 해야 해서 별도 일정으로 둔 상태였어요. 수정됐다는 기록만으로 실제 롤백이 검증됐다고 볼 수는 없어요.

4. 대기 컨테이너의 유지 시간을 줄이기로 했어요

블루그린 배포는 기존 버전과 새 버전의 실행 환경을 나눠 트래픽을 전환하는 방식이에요. 당시 구성은 같은 호스트에서 두 컨테이너를 계속 실행했어요. 두 JVM의 힙 설정 합계가 호스트 메모리보다 컸다는 점을 보고, 대기 컨테이너를 계속 유지할 필요가 있는지 검토했어요.

검토한 기준은 자원 사용량과 롤백이 필요한 기간이었어요.

별도 자동 정지 절차가 없는 단일 서버 구성에서는 대기 컨테이너도 계속 메모리를 사용해요. 배포가 끝난 뒤 누가 언제 대기 컨테이너를 정지할지 정해야 했어요. 오케스트레이터의 동작도 구성에 따라 달라지므로, 자동으로 자원이 회수된다고 전제할 수는 없어요.

당시에는 빠른 롤백이 특히 필요한 기간을 배포 직후 몇 분에서 몇 시간으로 봤어요. 사흘 뒤 문제를 발견하면 수정본 배포를 우선 고려한다는 운영 판단이었어요. 늦게 발견한 문제에는 롤백이 필요 없다는 일반 규칙은 아니에요.

그래서 배포 직후 상태를 관찰하는 기간인 소킹 창 동안만 두 컨테이너를 유지하는 방식으로 변경했다고 기록했어요.

그림 2. 당시 정한 두 컨테이너의 유지 기간과 예상 롤백 시간이에요

당시 정한 소킹 창은 배포 후 30~60분이었어요. 이후에는 대기 색, 즉 현재 트래픽을 받지 않는 컨테이너를 정지하는 방식이에요. 그림의 창 안 몇 초와 창 밖 약 60초는 당시 제시한 예상 시간이에요. 로컬 이미지를 재사용한다는 전제였고, 롤백을 끝까지 실행해 실측한 결과는 확인하지 못했어요.

⚠️ 대기 컨테이너 정지는 수동으로 남았어요
당시 구성에서는 사람이 스크립트를 실행해 대기 컨테이너를 정지하도록 했어요. 실행을 빠뜨리면 두 컨테이너가 계속 자원을 사용하는 한계가 있었어요.

타이머로 자동 정지하거나 대기 컨테이너의 실행 시간을 감지하는 방안을 후속 과제로 남겼어요. 이 설명은 당시 상태이며 이후 구현 여부를 확인한 결과는 아니에요.

대기 컨테이너 정지와 메모리 상한 설정은 별도로 필요했어요. 컨테이너 수를 줄여 사용량을 낮추더라도, 실행 중인 컨테이너의 사용 한도까지 정해지는 것은 아니기 때문이에요.

5. 메모리 제한으로 종료됐는지도 확인해야 해요

메모리 상한을 설정한 뒤에는 제한에 따른 강제 종료도 확인해야 해요. 아래는 당시 JVM 내부의 메모리 오류와 컨테이너 제한에 따른 종료를 비교한 메모예요.

이 메모는 두 경우를 단순화한 설명이에요. JVM의 메모리 오류가 항상 프로세스 종료와 앱 로그를 보장하는 것은 아니고, 커널의 강제 종료도 앱 로그만으로 확인하기 어려워요.

힙이 상한을 넘음 → JVM 이 오류를 던지고 스스로 종료 → 앱 로그에 남는다 ✅ 컨테이너 전체가 상한 초과 → 커널이 즉시 강제 종료 → 자바가 손쓸 틈 없음 → 앱 로그에 아무것도 없다 ❌

강제 종료 여부는 도커의 컨테이너 상태와 커널 로그도 함께 확인해야 해요. 당시에는 재시작까지 약 30초로 정리했지만, 이번에 정책과 실행 시각 원본을 대조하지는 못했어요. 재시작만 관찰하면 메모리 제한으로 종료됐는지를 놓칠 수 있어요.

당시 조사에서는 블루그린 전환 후 나흘 동안의 호스트 메모리 변화를 알 수 있는 지표가 부족했다고 정리했어요. 상한을 설정한 뒤에도 제한에 따른 종료를 확인할 신호는 별도로 필요했어요.

당시 후속 과제는 호스트 메모리 지표 수집과 컨테이너의 메모리 제한 종료 감지였어요. 이 글에서 다룬 설정 변경과 별개로 남겨 둔 항목이며, 이후 적용 여부는 이번 확인 범위에 포함하지 않았어요.

✍️ 조치와 확인 범위
컴포즈 메모리 제한과 JVM 힙 옵션의 실제 적용값을 확인하고, 조회 오류를 대상 없음으로 처리하던 스크립트를 수정했다고 당시 기록에 남겼어요. 롤백 전체 과정을 끝까지 검증한 것은 아니에요.

대기 컨테이너는 배포 후 30~60분만 유지하기로 했지만 정지는 수동으로 남았어요. 예상 롤백 시간과 실제 실행 결과를 구분해야 하고, 메모리 제한에 따른 종료 감지도 당시 후속 과제였어요.
