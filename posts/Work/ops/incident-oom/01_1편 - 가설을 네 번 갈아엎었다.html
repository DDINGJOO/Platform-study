📚 49분 전면 중단, 3부작
1편. 호스트 메모리 고갈로 판단하기까지의 가설 검증 ← 지금 이 글

월요일 오전 10시 35분에 전화가 왔어요. 타깃그룹에 정상 호스트가 하나도 없다는 알람이었습니다.

당시 정리한 장애 시간은 49분이었고, 조사 끝에 호스트 메모리 고갈이 원인이라고 판단했어요. 처음부터 그렇게 본 것은 아니에요. GC, 컨테이너 재시작, 외부 호출 재시도를 차례로 의심한 뒤 호스트 자원 쪽으로 조사 범위를 좁혔어요.

아래 시각과 수치는 당시 정리한 기록을 따른 것이에요. 이번에는 사고 당시의 원시 로그와 지표 시계열, 원인별 실행 증거를 다시 대조하지 못했어요. 그래서 당시의 관찰과 판단을 구분하고, 개별 수치만으로 원인을 확정하기 어려운 부분도 함께 적었어요.

1. 배포 6일 만에 장애를 감지한 알람

당시 기록상 증상이 시작된 뒤 전화 알림을 받기까지 7분 걸렸어요.

10:28:27 앱 정지. 증상 시작 10:29~30 헬스체크 3회 연속 실패 (30초 간격 × 3회) +90초 10:31, 32 정상 호스트 수 = 0 데이터포인트 2개 +2분 10:35:48 알람 발화 → 전화·Slack +7분

이 알람은 감지 체계를 정비하면서 엿새 전에 배포한 규칙 중 하나였어요. 배포 6일 만에 실제 장애를 처음 통지했어요.

당시 비교한 다른 로드밸런서 3개는 지표가 발행되지 않아 이 알람의 대상에서 빠져 있었어요. 조사 기록에는 타깃 없이 503을 반환하는 상태가 최소 2주간 감지되지 않았다고 적혀 있었어요.

정상 타깃이 없어 요청을 처리하지 못한다는 증상은 같았어요. 다만 다른 조건까지 같았다고 볼 수는 없고, 여기서 확인하려던 차이는 알람의 감지 범위였어요.

💡 증상 알람으로는 메모리 부족을 미리 알기 어려웠어요
이 알람은 정상 타깃이 사라진 뒤에 통지하는 증상 알람이에요. 메모리 부족을 미리 감지하는 용도로 만든 것은 아니었어요.

당시 조사에서는 메모리 사용률이 나흘 전부터 99%였다고 정리했어요. 하지만 CloudWatch에서 조회할 호스트 메모리 지표가 없어, 대응 중에는 그 추이를 보지 못했어요. 기본 EC2 지표와 별도로 메모리를 수집하고 알람을 연결할 필요가 있었어요.

2. 헬스체크 응답이 시간 안에 오지 않았어요

먼저 타깃 상태와 등록된 인스턴스 수를 확인했어요.

State : unhealthy Reason : Target.Timeout ← 연결 거부가 아니라 응답 지연 Target : 인스턴스 1대 ← 그 하나가 빠지면 전면 중단

기록된 사유는 연결 거부가 아니라 응답 시간 초과였어요. 헬스체크 타임아웃은 5초였고, 90초 넘게 응답 실패가 이어졌다고 정리했어요. 다만 이 사유만으로 프로세스와 포트가 모두 정상이라고 확정할 수는 없어요.

당시에는 타깃이 한 대뿐이어서 그 인스턴스가 비정상이 되자 요청을 처리할 정상 타깃이 남지 않았어요.

아래는 당시 초기 점검 메모예요. 오른쪽에는 그때의 판단이 적혀 있어요. 상태 점검 통과나 OOM 메시지 부재만으로 원인 전체를 배제했다고 볼 수는 없어요.

인스턴스 상태 점검 running, 시스템·인스턴스 모두 ok → 하드웨어·호스트 네트워크 아님 콘솔 로그 grep oom / killed 없음 → 커널 OOM Killer 아님 CPU 6시간 5~7% → 46%, 포화 아님 → 단순 트래픽 폭주 아님 호스트 자원 지표 조회 결과 비어 있음 → 메모리·디스크는 볼 수단이 없음

3. 가설 1: GC가 반복되어 멈춘 것은 아닐까

당시 기록에는 CPU 사용률이 평시 5~6%에서 46%로 올랐다고 적혀 있어요. 4 vCPU 기준으로 대략 두 코어에 해당하는 사용량이라 보고 GC를 의심했어요.

GC 스래싱은 메모리를 회수하는 GC가 반복되어 앱이 충분히 실행되지 못하는 상황을 말해요. 당시에는 GC 중 앱 실행이 멈추는 stop-the-world를 의심했어요. 다만 CPU 46%라는 값만으로 GC와 트래픽 증가를 구분할 수는 없어요.

힙을 확인하려 했지만 앱은 도커 컨테이너에서 실행 중이었고 호스트에는 자바가 없었어요. 당시에는 JVM 진단을 이어가지 못하고 다른 원인을 조사했어요. 진단 도구를 바로 쓸 수 없었다는 사실은 GC 가설을 반증하는 근거가 아니므로, 이 단계는 기각보다 미확인으로 보는 것이 맞아요.

4. 가설 2: 앱 컨테이너가 반복해서 종료됐을까

SSH로 접속되지 않아 콘솔 로그에서 커널 메시지를 읽었어요.

br-xxxx: port 3(vethXXXX) entered forwarding state br-xxxx: port 3(vethXXXX) entered disabled state ... br-xxxx: port 5(vethYYYY) entered forwarding state br-xxxx: port 5(vethYYYY) entered disabled state ↑ 0.137초 만에 사라짐

가상 네트워크 인터페이스의 상태가 반복해서 바뀌고 있었어요. 마지막 구간의 간격은 137밀리초였고, 커널 타임스탬프를 환산한 시각도 사고 시간대와 겹쳤다고 정리했어요. 이때는 컨테이너가 시작과 종료를 반복하는 크래시 루프를 의심했어요.

서버에 접속한 뒤 확인한 앱 컨테이너의 재시작 횟수는 0이었어요. 당시에는 반복 종료된 대상을 앱이 아닌 모니터링 에이전트 컨테이너로 정리했어요. 앱이 크래시 루프에 빠졌다는 초기 가설을 뒷받침하지 않는 결과였지만, 재시작 횟수만으로 이전 컨테이너의 이력까지 모두 설명할 수는 없어요.

⚠️ 인터페이스 로그만으로 앱을 특정했어요
위 로그에는 인터페이스 상태만 있고 앱 컨테이너 이름은 없어요. 그런데 앱 장애를 조사하던 중이라 그 로그도 앱에 관한 것이라고 먼저 판단했어요.

인터페이스가 어느 컨테이너에 연결됐는지와 앱의 재시작 이력을 함께 확인해야 했어요. 상태 변화가 사고 시간대와 겹친다는 이유만으로 앱 종료로 해석한 것이 문제였어요.

5. 가설 3: 외부 호출 재시도가 늘었을까

사고 직전 앱 로그에는 다음 오류가 있었어요.

Failed to resolve '...' [A(1)] Caused by: ReadTimeoutException at ...RetryWhenMainSubscriber.onError

주소 해석 실패와 재시도 처리 코드가 함께 보여, 외부 호출 재시도가 늘면서 스레드가 부족해졌을 가능성을 의심했어요. 먼저 오류 건수와 발생 시점을 비교했어요. 아래 메모의 단정적인 표현과 달리, 오류 건수만으로 원인 여부를 확정할 수는 없어요.

Failed to resolve 1건 ← 일회성. 원인일 수 없다 ReadTimeoutException 3,040건 ← 많다. 그런데?

3,040건을 분 단위로 나눠 봤어요. 이 로그는 UTC 기준이라 아래 01:27은 한국시간 10:27이에요.

22:33 12건 23:40 15건 00:25 12건 00:50 13건 01:05 14건 01:23 5건 01:27 ──── 사고 시작. 여기서부터 0건

당시 집계에서는 오류가 사고 시점에 급증하지 않고 직전에 끊겼어요. 이전 며칠 동안에도 10~20분마다 반복됐다고 정리했어요. 그래서 새로 발생한 재시도 폭주라는 설명은 지지하기 어려웠어요. 오류가 사라진 이유를 앱 전체의 정지로 해석했지만, 로그 중단만으로 그 원인까지 확인한 것은 아니에요.

💡 오류 건수는 평시와 비교해야 했어요
누적 오류가 많다는 사실과 사고 시점에 오류가 증가했다는 사실은 달라요. 이 경우에는 평시에도 같은 오류가 반복됐어요.

사고 전후를 비교하고 나니 확인할 대상도 달라졌어요. 오류 메시지의 내용뿐 아니라 로그가 언제부터 남지 않았는지도 봐야 했어요.

6. 로그가 지연되고 끊긴 시점을 비교했어요

앞선 조사만으로 원인을 확정하기 어려워, 오류 내용과 함께 기록 시각을 비교하기 시작했어요.

이때 비교한 로그에는 앱이 남긴 시각과 도커가 수신한 시각이 있었어요. 평소에는 두 시각이 몇 밀리초 정도 차이 났어요.

도커 수신 앱 기록 격차 10:25:00.986 ←→ 10:25:00.982 4ms 정상 10:27:43.014 ←→ 10:27:42.953 61ms 10:28:17.342 ←→ 10:28:17.177 165ms 10:28:25.117 ←→ 10:28:23.877 1,240ms ← 1.2초 10:28:27.535 ←→ 10:28:26.413 1,122ms 그리고 로그 완전 중단. 40분간 한 줄도 없음

앱 기록 시각과 도커 수신 시각의 차이가 커지다가 로그가 끊겼어요. 로그 전달 과정에도 지연이 생겼다고 볼 수 있지만, 이 두 시각만으로 표준 출력의 어느 단계에서 지연됐는지까지 알 수는 없어요.

다른 컨테이너에서도 로그 지연과 다음 경고가 확인됐다고 당시 기록에 남겼어요.

도커 수신 10:43 ←→ 앱 기록 10:35 격차 8분 도커 수신 10:58 ←→ 앱 기록 10:36 격차 22분 WARN [HikariPool-1 housekeeper] - Thread starvation or clock leap detected

당시에는 30초마다 실행되는 커넥션 풀 관리 작업이 몇 분씩 밀렸다고 해석했어요. 경고 자체는 스레드 실행 지연이나 시계 변화 가능성을 나타내므로, 이 메시지만으로 메모리 부족을 확정할 수는 없어요.

두 컨테이너에서 모두 지연이 관찰됐다는 점 때문에 호스트 자원을 우선 조사했어요. 한 컨테이너만의 문제로 설명하기 어려웠지만, 공통으로 쓰는 자원이나 의존성이 더 있을 수 있으므로 호스트 문제라고 바로 확정하지는 못해요.

7. 시스템 통계가 남지 않은 구간을 확인했어요

서버에는 시스템 통계 수집기가 실행되고 있었어요. 당시 조사에서는 남아 있던 통계와 기록이 없는 구간을 함께 확인했어요.

여유메모리 메모리사용률 캐시 커밋 블록된프로세스 01:00 160MB 99.00 56MB 132% 1 01:10 166MB 98.96 51MB 132% 2 01:20 158MB 99.01 62MB 132% 2 01:30 ───────── 기록 없음 ───────── 02:15 LINUX RESTART

이 통계에서는 메모리 사용량, 캐시 크기, 수집 공백을 함께 봤어요.

메모리 사용률은 약 99%였고, 15.6GB 중 여유가 158MB인 시점이 있었어요. 당시 기록에는 커밋 비율이 132%이고 스왑은 0이었다고 적혀 있어요.

캐시는 56MB로 기록된 시점이 있었어요. 별도 기록에는 디스크 큐가 0.4에서 3.8로 오른 뒤 45분간 유지됐다고 적혀 있어요. 당시에는 페이지 캐시 회수와 디스크 읽기 증가로 해석했어요. 다만 이 값들만으로 캐시가 전량 회수됐다거나 모든 페이지 폴트가 디스크 읽기를 일으켰다고 단정할 수는 없어요.

10분마다 실행되는 cron 통계는 01:30부터 다섯 번의 수집 기록이 없었어요. 앱 로그 외에 시스템 통계에도 공백이 있어 호스트의 실행 지연 가능성을 더 의심했어요.

⚠️ 수집 공백도 원인을 따로 확인해야 해요
앱 로그와 시스템 통계가 함께 끊긴 것은 조사 범위를 호스트로 넓힐 단서였어요. 하지만 수집 기록이 없다는 사실만으로 호스트 전체가 멈췄다고 확정할 수는 없어요.

수집 작업이 실행되지 않았는지, 실행됐지만 기록을 남기지 못했는지를 구분해야 해요. 당시에는 다른 로그의 지연과 높은 메모리 사용률을 함께 보고 호스트 자원 부족으로 판단했어요.

8. 두 JVM의 힙 설정과 호스트 메모리를 비교했어요

당시 조사에서 확인한 컨테이너 이미지의 실행 스크립트에는 다음 설정이 있었어요.

export OPTS="-Xmx8192m -Xms8192m"

최소 힙과 최대 힙을 모두 8GB로 고정한 설정이었어요. 다만 이 설정값만으로 각 시점의 실제 물리 메모리 점유량을 알 수는 없어요.

닷새 전에는 무중단 배포를 위해 블루그린 방식으로 전환했다고 정리했어요. 기존 앱과 새 앱을 함께 실행하면서 앱 컨테이너가 하나에서 둘이 된 상태였어요.

전환 전 JVM 1개 × 8GB = 8GB / 호스트 15.6GB → 여유 있음 전환 후 JVM 2개 × 8GB = 16GB / 호스트 15.6GB → 물리 메모리 초과

당시 통계에 기록한 커밋 값은 21.1GB였어요. 힙 설정 합계 16GB 외에 메타스페이스와 네이티브 영역도 있다고 보고 메모리 부족을 의심했어요. 다만 영역별 실측값이 없어 커밋 값의 구성을 정확히 대조한 것은 아니에요.

두 JVM의 힙 설정 합계가 호스트 메모리보다 크다는 점과 앞선 관찰을 합쳐, 당시에는 호스트 메모리 고갈을 원인으로 판단했어요. 다만 나흘 동안 힙이 어떻게 변했는지, 아침 트래픽이 어떤 영향을 줬는지까지 보여 주는 시계열은 이번에 확인하지 못했어요.

아래는 당시 원인을 설명하려고 정리한 흐름이에요. 전량 회수, I/O 대기, 트래픽 증가가 각 단계의 직접 원인이었다는 표현은 당시 해석이며, 원인별 실행 증거로 다시 검증한 결과는 아니에요.

8/12 블루그린 전환 — JVM 1개 → 2개, 메모리 제한 없음 ↓ 나흘간 힙 성장 → 메모리 99% 상주 (지표가 없어 아무도 모름) 10:25 아침 트래픽 램프업 → 남은 여유 소진 커널이 페이지 캐시 전량 회수 → 스왑 없어 스래싱 10:27 디스크 큐 0.4 → 3.8, CPU 5% → 46% (전부 회수·IO 대기) 10:28 JVM 정지. 관리 스레드 22분 지연. 헬스체크 5초 내 응답 불가 10:31 정상 호스트 0 → 알람

CPU 46%도 당시에는 메모리 회수와 I/O 지연에 관련된 값으로 해석했어요. 하지만 CPU 상태별 내역과 GC 자료를 대조하지 못했으므로, GC를 배제하거나 그 사용량 전부를 메모리 회수와 I/O 대기로 설명할 수는 없어요.

✍️ 조사 결과와 확인 범위
앱 컨테이너의 재시작 횟수와 평시 오류 발생 패턴을 보고 크래시 루프와 재시도 폭주 가설의 근거가 부족하다고 판단했어요. GC는 진단 자료를 확보하지 못해 확인하지 못했어요.

두 컨테이너의 로그 지연, 10분 주기 통계의 45분 수집 공백, 메모리 사용률과 힙 설정을 함께 보고 당시에는 호스트 메모리 고갈로 결론 냈어요. 원시 로그와 자원별 시계열을 다시 대조하지 못한 상태라, 당시의 결론을 현재 자료로 재검증했다고 볼 수는 없어요.
