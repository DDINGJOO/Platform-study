2편. P1 알람 전달 경로에서 변환 함수를 뺀 이유 ← 지금 이 글

감지 항목을 정리하면서 서버리스 함수의 동시성 고갈도 P1 대상으로 잡았어요. 계정 동시성 한도에 도달해 호출이 거부되면 바로 대응해야 한다고 본 거예요.

그런데 알람과 온콜 도구 사이에도 페이로드를 다듬는 함수가 있었어요. 감시 대상과 같은 동시성 한도를 쓰는 함수라면, 동시성이 고갈됐을 때 알람 전달까지 함께 실패할 수 있어요.

그래서 P1 전달 경로에는 직접 배포하고 운영하는 함수를 넣지 않기로 했어요. 변환은 관리형 기능으로 처리하고, 자동 복구용 함수는 호출 경로와 분리했어요.

1. 전달 함수가 감시 대상과 같은 한도를 쓸 때

CloudWatch 알람에서 SNS를 거쳐 온콜 도구 웹훅까지 가는 구간에 변환용 함수를 두지 않는 구성이에요. SNS는 알림을 구독자에게 전달하는 서비스이고, 웹훅은 온콜 도구가 알림을 받는 HTTP 주소예요. 아래에서 쓰는 입력 변환기는 EventBridge가 제공하는 설정 기능이에요.

변환 함수를 추가하면 감시해야 할 대상도 하나 늘어요. 특히 그 함수가 감시 대상과 계정 한도나 리전 자원을 공유한다면, 같은 원인으로 둘 다 실패할 수 있어요.

감시 대상 전달 수단으로 함수를 쓰면 -------------------------------------------------------------- 함수 동시성 고갈 전달 함수도 호출을 거부한다 계정 스로틀 같은 한도를 공유한다 리전 단위 서비스 이상 둘 다 그 리전에 있다 => 무작위로 고장 나는 것이 아니라 하필 필요한 순간에 함께 죽는다

위 표는 같은 계정 한도나 리전에 의존할 때 생길 수 있는 실패를 정리한 것이에요. 감시 대상과 전달 수단이 공유하는 자원을 확인해야 해요. 평소에 알림이 도착했다는 사실만으로 이런 상황의 전달까지 확인했다고 볼 수는 없어요.

전달 함수가 동작하지 않는 상황을 알아내려면 그 함수를 감시하는 알람과 별도의 전달 경로도 필요해요. 이번 구성에서는 변환 함수를 추가하지 않는 쪽을 택했어요.

호출이 없는 함수의 의미는 따로 확인해야 해요

당시 점검 자료에는 2주간 호출 기록이 없는 함수가 열 개, 그중 알림 용도로 분류한 함수가 셋으로 기록돼 있어요. 다만 호출이 없었다는 수치만으로 전달 장애가 있었다고 판단할 수는 없어요.

그중에는 알람을 슬랙으로 보내는 함수와 타깃그룹 이상을 알리는 함수도 있었어요. 알림이 발생하지 않아 호출이 없었는지, 연결이나 실행에 문제가 있었는지는 별도로 확인해야 해요.

이런 함수는 존재 여부뿐 아니라 알림을 받아 실제로 전달하는지도 점검해야 해요. 호출 기록이 없다는 사실을 그대로 고장이나 방치의 증거로 쓰지는 않았어요.

그림 1. 변환 함수가 감시 대상과 한도를 공유하는 경로와 관리형 경로의 차이

알럿 스택의 Terraform 코드에서 함수 리소스를 찾으면 0개예요. 이 범위에서는 변환 함수를 정의하지 않았음을 확인할 수 있어요. 코드 밖의 설정이나 실제 전달 성공 여부까지 증명하는 결과는 아니에요.

2. 페이로드는 입력 변환기로 정리했어요

함수를 쓰지 않아도 이벤트 내용을 사람이 읽을 수 있게 정리할 필요는 있어요. 이벤트 JSON 원문만 받으면 어떤 자원에서 무슨 일이 생겼는지 파악하기 어려워요.

EventBridge 룰의 타깃으로 SNS를 지정하면 이벤트 JSON을 전달할 수 있어요. 다만 당시 구성의 챗봇은 그 원문을 그대로 슬랙 카드로 표시하지 못했어요. CloudWatch 알람 형식과 이벤트 기반 알림의 메시지 형식을 구분해야 했어요.

호출을 받은 사람이 확인할 제목과 사유, 대응 절차 링크도 함께 전달하도록 메시지를 정리했어요.

이벤트에서 필요한 필드를 뽑아 문장을 조립하는 작업은 EventBridge의 입력 변환기로 처리했어요. 필드 경로와 템플릿을 지정하면 서비스가 메시지를 변환하므로 별도 함수는 필요하지 않아요.

input_paths = { service = "$.resources[0]" deploy = "$.detail.deploymentId" reason = "$.detail.reason" } input_template = <<-EOT {"version":"1.0","source":"custom","content":{ "textType":"client-markdown", "title":"컨테이너 배포 실패", "description":"서비스: <service>\n사유: <reason>\n\nrunbook: ..."}} EOT

위 설정은 서비스와 실패 사유, 런북 링크를 카드에 넣는 형태예요. 런북은 알림을 받았을 때 확인할 항목과 대응 절차를 정리한 문서예요. 입력 변환 설정이 있다는 것과 모든 이벤트에서 카드가 도착했는지는 구분해서 확인해야 해요.

템플릿과 배달 실패도 확인해야 해요

입력 변환기를 쓰더라도 변환 결과가 수신 측에서 처리할 수 있는 JSON인지 점검해야 해요. 아래 정리의 필드 누락도 누락 자체만이 아니라 치환 뒤의 메시지 형식과 함께 봐야 해요.

1. 치환 결과가 유효한 JSON 이 아니면 배달이 실패한다 원본 필드 값에 따옴표가 들어가면 템플릿이 깨진다 2. 없는 경로를 참조하면 치환이 비고 배달이 실패한다 $.detail.reason 이 그 이벤트에 없으면 통째로 사라진다 두 실패의 공통점 룰은 존재하고 타깃도 붙어 있어서 콘솔에서는 정상으로 보인다

위 블록은 당시 실패 설명을 보존한 것이에요. 없는 JSON 경로의 변수는 생성되지 않고 출력에 나타나지 않아요. 그렇다고 항상 배달 전체가 실패한다고 단정할 수는 없어요. 최종 템플릿과 타깃 형식에 따라 달라지므로 이벤트별 치환 결과와 수신 측에서 처리할 수 있는 메시지인지를 확인해야 해요.

이벤트 이름 넷을 함께 받는 룰에서는 reason 필드가 모든 이벤트에 있는지 확인되지 않아 템플릿에서 뺐어요. 일부 이벤트에만 있는 필드를 넣으면 변환 결과를 이벤트별로 확인해야 하기 때문이에요.

이벤트 이름이 하나인 배치 실패 룰에는 reason을 넣었어요. 실패 사유를 함께 전달하려는 설정이에요. 이 경우에도 해당 필드가 있는 이벤트와 변환 결과를 확인해야 해요.

필드를 넣을지는 메시지에 필요한 정보와 이벤트마다 확인할 수 있는 범위를 함께 보고 정했어요.

변환 설정과 함께 룰의 배달 실패 횟수를 감시하는 알람도 구성했어요. 함수가 없어도 잘못된 템플릿이나 권한 때문에 전달이 실패할 수 있으므로, 타깃을 연결한 뒤에는 전달 결과도 감시해야 해요.

3. 호출과 자동 복구는 별도 경로로 나눴어요

자동 복구에는 별도의 실행 코드가 필요할 수 있어요. 이번 설계에서는 복구용 함수를 쓰더라도 사람이 호출을 받는 경로에는 넣지 않기로 했어요.

호출과 복구가 같은 알람 상태를 받되, 각각 별도의 경로로 처리하도록 나눴어요.

호출 경로 알람의 alarm_actions 에 p1 토픽을 지정한다 여기에 붙는 것은 온콜 도구 구독과 슬랙 구독뿐이다 복구 경로 이벤트 버스가 알람 상태 변경 이벤트를 독립적으로 수신한다 토픽을 경유하지 않는다. 알람은 이 경로를 모른다

p1 토픽에 복구 함수를 구독자로 추가하는 방법도 있어요. 하나의 메시지를 여러 구독자에게 전달하는 팬아웃 구성이에요. 기존 토픽을 이용할 수 있지만 호출과 복구가 같은 구독 목록에서 관리돼요.

이 구성에서는 복구 함수를 추가하거나 삭제할 때 호출용 구독도 함께 관리하게 돼요. 구독 목록을 잘못 수정하면 호출 전달에 영향을 줄 수 있어요.

복구 경로를 EventBridge로 분리하면 복구 함수의 연결을 바꿀 때 호출용 SNS 구독 목록을 수정할 필요가 없어요. 다만 같은 계정과 서비스에 대한 의존성까지 없어지는 것은 아니에요.

분리할 때는 두 경로가 같은 신호를 받는지뿐 아니라, 변경할 설정을 어디까지 공유하는지도 봤어요. 복구 기능을 수정하는 작업이 호출용 구독에 영향을 주는 범위를 줄이려는 선택이었어요.

4. 토픽 암호화에는 발행 권한도 필요해요

토픽 암호화에도 알림 전달에 필요한 권한을 따로 설정해야 했어요.

AWS 관리형 키는 별칭으로 지정할 수 있어 설정이 간단해요. 하지만 SNS 토픽에 CloudWatch 알람을 발행하는 구성에서는 필요한 서비스 권한을 관리형 키 정책에 직접 추가할 수 없어요.

관리형 키로 토픽을 암호화하면 서비스 프린시펄이 그 키를 사용할 권한을 얻을 수 없다 관리형 키의 정책은 우리가 편집할 수 없기 때문이다 그래서 벌어지는 일 알람 상태는 정상적으로 ALARM 으로 바뀐다 상태 이력도 남는다 알림만 전달되지 않는다

여기서 구분해야 할 것은 알람 상태 변경과 알림 발행 결과예요. ALARM 상태와 상태 이력이 남아 있어도 발행에 성공했다는 뜻은 아니에요. 상태 화면만 확인하면 전달 실패를 놓칠 수 있어요.

그래서 고객 관리형 키를 만들고 키 정책에 서비스 프린시펄을 허용했어요. 서비스 프린시펄은 CloudWatch나 EventBridge처럼 권한을 부여할 AWS 서비스를 나타내는 식별자예요.

{ Sid = "AllowAwsServicesToEncrypt" Effect = "Allow" Principal = { Service = [ "cloudwatch.amazonaws.com", # CloudWatch 알람 "events.amazonaws.com", # EventBridge 룰 "scheduler.amazonaws.com", # 스케줄 기반 발행 "rds.amazonaws.com", # 데이터베이스 이벤트 구독 ]} Action = ["kms:GenerateDataKey*", "kms:Decrypt"] Resource = "*" }

키를 구성할 때는 리전과 발행 소스도 함께 확인했어요.

KMS 키는 리전 자원이므로 글로벌 서비스용 토픽을 다른 리전에 만들면 그 리전에도 키가 필요해요. ADR에는 설계 문서 초판이 키 하나만 정의해 해당 리전 세트를 적용하지 못했다고 남아 있어요.

발행 소스를 추가할 때는 키 정책에 필요한 서비스 프린시펄도 확인해야 해요. 예산 알림이나 다른 AWS 서비스를 연결하면서 이 권한을 빠뜨리면 알림 발행이 실패할 수 있어요.

⚠️ 알림 소스를 추가할 때 키 정책도 확인해요
서비스 프린시펄 목록을 코드 한 곳에 모으고, 소스를 추가할 때 확인할 이유를 주석으로 남겼어요. 목록이 있다는 것만으로 새 소스의 권한이 자동으로 추가되는 것은 아니에요.

키가 비활성화되면 같은 키로 암호화한 토픽의 발행도 영향을 받아요. 그 사실을 알리는 경로까지 같은 토픽에 의존하면 알림을 받지 못할 수 있으므로 별도로 감시해야 해요.

5. 재시도 시간과 DLQ 연결을 함께 확인해요

수신 측이 응답하지 않을 때 재시도를 얼마나 유지할지도 정해야 했어요.

SNS는 구독자에게 전달하지 못한 메시지를 재시도 정책에 따라 다시 보내요. 재시도를 소진한 뒤에도 메시지를 남기려면 DLQ 연결이 필요해요. DLQ는 최종 전달에 실패한 메시지를 보관하는 큐예요.

기본값 20초 간격 3회. 총 1분 수신 쪽이 1분 넘게 흔들리면 그 알림은 사라진다 그렇다고 몇 시간 재시도하면? DLQ 알람이 늦게 뜬다 즉 경로가 끊긴 사실을 늦게 안다 정한 값 5초에서 시작해 지수적으로 늘려 최대 60초 간격으로 20회 대략 15분. 그 뒤에는 구독 DLQ 로 보낸다

위 기본값과 사용자 재시도 정책은 이 글의 HTTP/S 웹훅 구독을 대상으로 읽어야 해요. 모든 SNS 구독 프로토콜에 같은 기본값이 적용되는 것은 아니에요. 시간은 정책을 대략 설명한 값이며 외부 도구가 다시 전화를 거는 정책과도 달라요. 구독 방식과 실제 설정을 함께 확인해야 해요.

재시도가 짧으면 일시적인 수신 장애에도 메시지를 잃을 수 있고, 길면 DLQ에 메시지가 들어오는 시점이 늦어져요. DLQ 깊이로 전달 실패를 감시한다면 재시도 시간만큼 감지도 늦어질 수 있어요. 위 표는 기본값과 이 구성에서 정한 재시도 정책을 비교한 것이에요.

DLQ의 보존 기간은 최대로 설정했어요. 다만 큐를 만드는 것과 구독에 연결하는 것은 별도 작업이에요. 재시도를 소진한 메시지가 큐에 남으려면 그 연결까지 되어 있어야 해요.

큐가 있어도 구독에 연결되지 않을 수 있어요

이 구성에서는 큐의 존재 여부와 구독 연결 여부를 나눠 확인할 필요가 있었어요.

구독이 Terraform 밖에 있으므로 재시도 정책과 DLQ 연결도 별도로 설정해야 해요. 큐가 조회된다는 이유만으로 연결까지 완료됐다고 볼 수는 없어요. ADR도 큐 생성은 Terraform, 연결은 콘솔 작업으로 구분하고 있어요.

DLQ를 만들 티어 목록도 따로 유지하면 토픽이나 구독 목록과 어긋날 수 있어요. 한쪽에만 항목을 추가하면 구독은 있는데 DLQ가 없거나, 큐만 남는 상태가 될 수 있어요.

코드에서는 토픽 집합을 기준으로 DLQ를 만들도록 했어요. 같은 티어 목록을 두 곳에서 고치는 일을 줄이되, 코드 밖의 구독 연결은 따로 확인해야 해요.

6. 발화는 P1으로, 복구는 P2로 보내요

마지막으로 발화와 복구 신호를 어느 토픽으로 보낼지 나눴어요. 여기서 P1·P2·P3는 호출과 기록 같은 전달 방식을 구분하는 티어예요.

P1 알람이 정상으로 돌아올 때 나가는 복구 신호는 p2 토픽으로 보내도록 했어요. 복구 때는 새 호출 없이 상태를 갱신하려는 구성이에요.

이렇게 보내려면 p2에도 복구 신호를 받을 구독이 있어야 해요.

p2 에 구독이 없으면 전화는 간다 P1 발화가 p1 토픽으로 나가니까 복구는 안 간다 ok 신호가 p2 로 나가고 아무도 받지 않으니까 결과 인시던트가 열린 채로 남는다 다음 발화가 그 인시던트에 묶여 새 호출이 안 된다

위 표는 복구 신호가 도착하지 않았을 때 생길 수 있는 문제를 정리한 것이에요. 첫 발화의 호출만 확인하면 인시던트가 닫히는지는 놓칠 수 있어요. 다음 발화의 처리 방식은 온콜 도구 설정에도 영향을 받으므로 복구와 재발화까지 이어서 확인해야 해요.

당시 온콜 구성은 구독 URL에 팀 파라미터가 있는 경우에 호출 대상으로 연결했어요. 파라미터 없는 구독은 기록용으로 구분했어요. 구독을 유지하는 것과 전화 호출을 켜는 것을 따로 설정한 거예요.

토픽 구독 호출 용도 ------------------------------------------------------ p1 O 예 지금 대응해야 하는 것 p2 O 아니오 기록. P1 의 복구 신호가 여기로 온다 p3 O 아니오 하트비트. 사람을 부르면 안 된다

p3는 하트비트용으로 구분했어요. 하트비트는 경로가 살아 있는지 확인하려고 주기적으로 보내는 신호예요. 호출이나 슬랙 알림을 반복하지 않도록 구독도 용도에 맞게 나눴어요.

전달 실패는 다른 경로로 알려요

DLQ 알람은 알림 전달 경로의 실패를 감시해요. 그래서 실패한 경로를 그대로 다시 이용하지 않도록 알람의 전송 대상을 정했어요.

DLQ 알람을 모두 p2로 보내면 p2의 전달 실패도 p2로 알리게 돼요. 감시 대상 경로에 문제가 있을 때 그 문제를 알릴 메시지도 도착하지 않을 수 있어요.

코드의 경고 주석만으로는 라우팅을 확인할 수 없어요. 알람 액션이 실제로 감시 대상과 다른 토픽을 가리키는지 확인해야 해요.

이 글에서 다루는 라우팅은 아래와 같아요.

p1 DLQ -> p2 전화 경로가 끊겼으니 슬랙으로 p2 DLQ -> p1 슬랙이 끊겼으니 전화로 p3 DLQ -> p2 하트비트 배달 실패는 급하지 않다

티어별 전송 대상을 나누면 DLQ 알람도 다른 경로로 보낼 수 있어요. 다만 이 구성만으로 모든 전달 장애가 해결되는 것은 아니에요. p1과 p2가 함께 실패하는 상황까지 독립적으로 검증했다는 뜻은 아니에요.

p2 DLQ 알람을 p1으로 보내면 기록용 경로의 장애가 전화 호출로 이어질 수 있어요. p2로 다시 보내면 같은 경로에 의존하고 p3는 사람에게 알리지 않는 구성이므로, 전달 경로의 실패를 알리기 위해 이 호출은 허용했어요.

그림 2. 발화와 복구의 전송 대상, 전달 실패를 알리는 별도 경로
✍️ 정리
P1 전달 경로에는 변환 함수를 두지 않고 EventBridge 입력 변환기를 사용했어요. 감시 대상과 함수 동시성 한도를 공유하는 의존성을 줄이고, 자동 복구는 별도 경로로 나눴어요.

함수가 없어도 전달은 실패할 수 있어요. 입력 변환 결과, 고객 관리형 키의 발행 권한, 재시도 정책과 DLQ 연결을 함께 확인해야 해요. 발화는 p1, 복구는 p2로 나누고 전달 실패는 감시 대상과 다른 경로로 알리도록 구성했어요.

코드와 ADR에서 확인한 것은 설정과 일부 전달 시험 기록이에요. 코드 밖의 구독 연결, 모든 이벤트의 변환 결과, 장애 중 실제 호출 성공까지 한꺼번에 확인한 것은 아니에요.
