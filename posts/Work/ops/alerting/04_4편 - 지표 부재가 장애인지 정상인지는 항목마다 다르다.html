treat_missing_data = ? breaching 데이터가 없으면 위반으로 본다 -> 알람이 울린다 notBreaching 데이터가 없으면 정상으로 본다 -> 조용하다

지표가 없는 상태를 위반으로 볼지 정상으로 볼지 정하는 설정이에요. 어느 쪽을 선택할지는 알람이 감시하는 지표에 따라 달라요.

자원 삭제 여부를 판단할 때도 값이 0인 경우와 지표가 아예 없는 경우를 구분했어요. 알람에서는 이 구분을 바탕으로 지표가 없을 때 담당자에게 전화할지 정해야 해요.

1. 결측 처리를 호출부에서 직접 정하게 했어요

결측을 무시하도록 설정하면 지표가 오지 않아도 알람은 마지막 상태를 유지해요. 이 설명은 결측 무시 설정을 선택한 경우에 한정해요. CloudWatch 자체의 기본값까지 이번 코드·문서 대조로 확인한 것은 아니에요.

계속 보고되어야 할 지표라면 결측을 무시하기 어려워요. 인스턴스가 응답을 멈추면서 지표도 끊기는 경우를 감지해야 하기 때문이에요. 설계 문서에서도 이런 지표의 결측은 위반으로 보도록 했어요.

반대로 모든 지표의 결측을 위반으로 보면 정상 상태에서도 알람이 울릴 수 있어요. 모듈 주석에는 트래픽이 없는 상황을 예로 들었어요.

새벽 3시, 트래픽 0 -> 함수가 호출되지 않는다 -> 쓰로틀 지표가 발행되지 않는다 -> 결측을 위반으로 봄 -> ALARM -> P1 전화 실제로는 아무 문제 없다. 장애가 없어서 알람이 울린 것이다.

위 예시는 실제 새벽 호출 기록이 아니라 결측을 위반으로 처리했을 때 생길 수 있는 상황이에요. 사건이 없으면 지표도 발행되지 않는 항목에는 같은 결측 처리를 적용할 수 없어요. 그래서 모듈에 기본값을 두지 않고 호출부에서 매번 명시하도록 했어요.

알람을 추가할 때마다 설정을 채워야 해서 호출부는 길어져요. 그 대신 지표가 계속 보고되는 상태 값인지, 사건이 있을 때만 발행되는 횟수인지 판단하게 했어요. 선택 기준도 변수 설명에 적어뒀어요.

variable "missing_data" { description = <<-EOT 데이터가 없을 때의 처리. 기본값이 없다. 매번 판단해야 한다. breaching 상태 게이지. 값이 계속 보고되는 지표. 없어지면 진짜 이상이다 notBreaching 이벤트 카운터. 사건이 없으면 데이터포인트 자체가 없다 EOT type = string validation { ... } }

2. 지표를 발행하지 않는 대상도 확인해야 해요

복제 지연이 대표적인 사례였어요. AuroraReplicaLag는 리더가 라이터를 얼마나 늦게 따라가는지 밀리초로 보고하는 지표예요.

이 지표의 알람은 클러스터의 모든 인스턴스에 설정했어요. 코드 주석에서는 라이터가 이 지표를 발행하지 않는 것을 전제로 했어요. 이 전제에서 결측을 위반으로 두면 라이터 쪽 알람은 배포 후 ALARM 상태가 돼요.

라이터 역할을 유지하며 지표를 발행하지 않는 동안에는 ALARM 상태가 계속돼요. 이런 알람이 남으면 실제 이상으로 발생한 알람을 구분하기도 어려워져요.

버스터블 인스턴스에서 사용하는 CPU 크레딧 지표도 대상 구분이 필요했어요. 비버스터블 인스턴스까지 같은 목록에 넣으면 발행되지 않는 지표에 알람을 설정하게 돼요.

자원을 삭제할 때도 결측 처리를 고려해야 해요. 결측을 위반으로 둔 채 대상부터 삭제하면 지표가 끊겨 ALARM 상태가 계속될 수 있어요. 서버 그룹을 정리할 때는 알람을 먼저 삭제하는 순서로 바꿨어요.

잘못된 순서 실물 삭제 -> 지표 끊김 -> 영구 ALARM -> 알람 삭제 올바른 순서 알람 삭제 -> 실물 삭제

대상 삭제로 생기는 알림을 피하려고 정리 순서도 코드에 남겼어요.

그림 1. 지표 발행 여부에 따라 결측 처리의 결과가 달라져요

3. 지표 소실을 감지할 알람을 정했어요

계속 보고되는 지표 중 하나를 골라 인스턴스의 지표 소실을 감지하도록 했어요.

DB 인스턴스 한 대에는 로컬 스토리지, 엔진 가동 시간, 복제 지연, 데드락, 디스크 큐 깊이의 다섯 종 알람을 설정했어요. 여러 지표가 동시에 끊겼을 때 모두 결측을 위반으로 처리하면 한 사건에 알람이 중복될 수 있어요.

지표 소실을 감지할 기준으로 엔진 가동 시간을 골랐어요. 인스턴스가 동작하는 동안 계속 보고되는 지표이기 때문이에요. 다만 값이 없다는 사실만으로 인스턴스가 삭제됐다고 단정할 수는 없어요. 나머지 알람은 아래 예외를 제외하고 결측을 정상으로 처리하며 각 지표의 임계값을 확인하도록 했어요.

인스턴스 한 대의 알람 다섯 종 엔진 가동 시간 breaching <- 지표 소실 담당. 이 한 명만 로컬 스토리지 잔량 breaching <- 예외. 아래 설명 복제 지연 notBreaching 데드락 notBreaching 디스크 큐 깊이 notBreaching 주석이 서로를 가리킨다 "인스턴스 소실은 엔진 가동 시간 알람이 잡는다. 여기서 중복으로 울리지 않는다"

이 구성에서 결측을 정상으로 처리한 근거는 주석으로 연결해뒀어요. 지표 소실을 어느 알람이 감지하는지 이름을 적어 설정을 함께 확인할 수 있게 했어요.

로컬 스토리지 잔량은 예외로 결측을 위반으로 뒀어요. 계속 보고되는 값이고 P1 전화 알람이어서 결측도 확인할 필요가 있다고 판단했어요. 서버 그룹에서도 전체 인스턴스 부족과 일부 부족을 감지하는 알람은 지표 수집이 꺼지면 함께 울릴 수 있어요. 하나는 전화, 다른 하나는 슬랙 기록을 위한 설정이어서 중복을 남겼어요.

기본적으로 지표 소실을 감지하는 알람을 정하되, 중복을 허용한 항목에는 이유도 적어뒀어요.

4. 역할이 바뀌어도 감시하도록 전체에 설정했어요

당시 역할을 기준으로 리더에만 복제 지연 알람을 설정하면 알람 여섯 개를 줄일 수 있었어요. 다만 역할이 바뀔 때도 감시가 유지되어야 해서 인스턴스 전체를 대상으로 뒀어요.

이름만으로는 리더를 고를 수 없었어요. 이름에 writer가 있어도 실제 역할은 리더였고, 같은 클러스터에서 이름에 reader 계열 문자가 있는 인스턴스가 라이터인 사례가 있었어요. 페일오버로 역할이 바뀌어도 이름은 그대로였기 때문이에요.

이름으로 대상을 골랐다면 실제 리더를 감시에서 빠뜨릴 수 있었어요. 실제 라이터를 잘못 포함하고 결측을 위반으로 처리하면 지속적인 ALARM도 생길 수 있었고요.

실제 역할을 조회해서 대상을 정하는 방법도 있지만 두 가지 제약이 있었어요.

역할은 페일오버 때 바뀔 수 있어요. 코드 적용 시점에 조회한 역할로 목록을 고정하면 이후 역할 변경을 반영하지 못해요.

또 이 스택은 알람이 지표 차원 문자열로 대상을 지정하므로 자원을 조회하는 데이터 소스가 필요 없다는 전제로 시작했어요. 알람은 대상 자원을 생성하거나 소유하지 않아요. 이 특성도 처음 코드화할 스택을 고른 근거였어요.

그래서 모든 인스턴스에 복제 지연 알람을 설정하고 결측을 정상으로 처리했어요. 역할이 바뀌면 새 리더가 발행하는 지표를 같은 알람 설정으로 감시하려는 구성이에요. 이것은 코드와 주석에서 확인한 설계 의도이며, 페일오버 후 동작을 이번에 실측한 결과는 아니에요.

이 구성에는 지표가 발행되지 않는 역할의 알람도 남아 비용이 들어요. 결측을 정상으로 처리한 상태만 보고 지표가 수집되고 있다고 판단해서는 안 돼요. 인스턴스의 지표 소실은 앞서 정한 다른 알람으로 감지하고, 그 관계를 주석에 적어뒀어요.

그림 2. 알람 여섯 개를 줄이기보다 역할 변경을 반영하는 구성을 선택했어요

서버 그룹 알람에서도 비슷하게 처리했어요. 목표 대수가 0인 그룹을 목록에서 빼는 대신 알람 식의 조건으로 구분했어요. 목표 대수는 런타임에 0에서 2로 바뀔 수도 있으므로, 목록 수정 없이 전체 인스턴스가 부족한 상태를 감지하도록 한 구성이에요.

⚠️ 데이터 소스가 대상을 찾지 못하면 계획이 실패해요
로드밸런서 알람은 데이터 소스를 사용했어요. 지표 차원에 붙는 랜덤 16진수 접미사를 손으로 적다가 틀리면 알람이 데이터를 받지 못할 수 있기 때문이에요. 결측을 위반으로 두면 ALARM이 계속되고, 정상으로 두면 지표가 없는 상태를 놓칠 수 있어요.

이름만 목록으로 두고 접미사는 데이터 소스로 조회했어요. 접미사를 직접 적는 오류는 줄일 수 있지만, 대상이 사라지면 조회에 실패해요.

로드밸런서를 콘솔에서 삭제한 뒤 목록에 남겨둬 스택 전체의 계획이 막힌 경위가 있었어요. 이 문제로 서로 무관한 변경 두 개가 멈췄다는 세부 경위는 이번에 대조한 자료만으로 확인하지 못했어요.

조회 실패로 다른 계획까지 막힐 수 있어도, 존재하지 않는 대상을 감시 중인 것처럼 남겨두지 않으려고 이 구성을 유지했어요.

5. 관측값을 기준으로 임계값을 정했어요

임계값도 명세의 문구를 그대로 설정값으로 옮기기 어려웠어요. 실제 대상과 관측값을 확인해야 했어요.

감지 목록에는 조건이 "급증", "임계 초과", "증가 추세"처럼 자연어로 적혀 있었어요. 실제 값을 조회해보니 임계값을 바꾸거나 대상 유무부터 다시 확인해야 하는 항목이 있었어요.

명세 실측 결과 ------------------------------------------------------------------------ NAT 패킷 드롭 "급증" 14일간 정확히 0 > 0 으로 바꿈 스트림 지연 "증가 추세" 지표 발행 자체가 없다 대상 없음 함수 DLQ 오류 DLQ 설정된 함수가 0개 대상 없음 메시지 적체 "임계 초과" 12시간 적체는 개발 큐였다 기준 재설정

NAT 패킷 드롭은 14일 동안 0으로 관측되어 "급증" 대신 0 초과를 임계값으로 정했어요. 관측 기간에 없던 패킷 드롭이 발생하면 확인하겠다는 판단이에요.

복제 지연 임계값은 1초로 뒀어요. 리더들의 평시 지연이 수십 밀리초였던 관측에 비하면 스무 배 이상 여유를 둔 값이에요. 디스크 큐 깊이는 관측된 최대의 약 1.5배로 정했어요.

디스크 큐 깊이의 임계값은 근거가 약하다고 코드에 적어뒀어요. 이 DB는 분산 스토리지를 사용해서 지표 해석이 일반적인 경우와 다르다는 설명도 남겼어요. 여기서 확인한 임계값의 근거는 관측된 최대보다 큰 값이라는 범위까지예요.

관측값이 이미 이상 조건에 해당하면 알람을 피하려고 임계값을 높이거나 대상을 빼지는 않았어요. 기록상 데드락 알람과 서버 부족 알람은 배포 직후 울렸고, 실제 문제로 판단했어요. 이번에는 해당 판단이 남은 문서를 대조했으며 당시 알림 로그를 새로 확인한 것은 아니에요.

관측 기간의 한계는 남아요. 14일 동안 0이었던 값이 15일째 발생할 수도 있어요. 패킷 드롭 임계값은 그 경우 알람을 받고 원인을 확인하는 쪽으로 정했어요.

6. 비율 알람은 집계 주기당 호출 수를 확인해요

명세에 실패율로 적힌 항목도 있었어요. 오류 수를 호출 수로 나눈 값인데, 호출이 적은 대상에 적용할 때는 집계 주기까지 함께 봐야 했어요.

호출이 적은 구간에서는 1회 호출 중 1회 실패만으로도 실패율이 100%가 돼요. 이런 경우를 구분하려고 호출 수가 일정 수를 넘을 때만 비율을 계산하는 조건을 뒀어요. 이 조건을 분모 가드라고 불렀어요.

IF(m1 > 10, m0/m1*100, 0) > 5 m0 = 오류, m1 = 호출

처음에는 집계 주기를 5분, 가드를 10으로 뒀어요. 작업 기록에는 배포 직후 오류가 있는 함수의 알람이 정상으로 표시됐다고 남아 있어요. 호출 총량을 집계 주기당 호출 수로 환산하지 않은 것이 문제였어요.

14일 호출 11,438회 많아 보인다 = 하루 817회 = 5분당 2.8회 가드 10 을 산술적으로 넘을 수 없다 네 함수 전부 같았다. 총량만 보고 주기당 환산을 안 했다.

위 환산값은 5분당 평균이에요. 평균만으로 모든 5분 구간의 호출 수가 10 미만이라고 단정할 수는 없고, 당시 구간별 조회 결과는 이번 대조에서 확인하지 못했어요. 기록상 주기를 1시간으로 바꾸자 셋은 비율 알람 조건을 사용할 수 있었고, 시간당 한 번 실행되는 하나는 여전히 맞지 않았어요.

호출이 드문 함수는 오류 건수를 보는 절대값 알람으로 옮겼어요. 한 번의 실패도 확인해야 하는 대상이어서 비율 조건을 적용하지 않았어요. 당시 정리한 구성은 비율 셋과 절대값 여섯이지만, 이 분할 개수와 변경 당시 실행 결과를 모두 입증하는 자료는 이번 대조에서 확인하지 못했어요.

호출이 아예 없는 함수는 대상에서 뺐어요. 비율을 계산할 수 없고, 실행되지 않는 동안에는 오류 건수 알람도 울리지 않기 때문이에요.

🔇 알람 설정만으로 감시 여부를 판단하기 어려운 경우
계획과 적용이 성공해도 지표와 조건이 맞지 않으면 필요한 알람이 울리지 않을 수 있어요.

• 발행되지 않는 지표를 대상으로 설정한 경우에는 임계값을 바꿔도 데이터를 받지 못해요.
• 대상이 0건인 조건도 확인해야 해요. DLQ가 설정된 함수가 없는데 DLQ 오류를 감시하는 경우가 여기에 해당해요.
• 분모 가드는 집계 주기당 호출 수와 함께 확인해야 해요. 호출 수가 가드를 넘지 못하면 오류율 식은 0을 반환해요.
• 필드 이름과 값의 형태도 확인해야 해요. 심각도를 문자열로 매칭했는데 실제 값은 숫자였던 사례가 있었어요.

먼저 지표가 발행되는지와 감시할 대상이 있는지 확인하고, 대상이 없으면 "미배포"와 구분해 "대상 없음"으로 적었어요. 아직 구현할 항목과 적용할 대상이 없는 항목을 나눠야 감시 범위를 확인할 수 있어요.

결측 처리, 임계값, 비율·절대값 선택은 지표와 대상별로 정했어요. 같은 설정을 일괄 적용하기보다 지표 발행 여부와 집계 주기당 관측값을 먼저 확인했어요.

✍️ 설정한 내용과 확인 범위
결측 처리는 지표별로 정하도록 모듈의 필수 변수로 뒀어요. 계속 보고되는 지표와 사건이 있을 때만 발행되는 지표를 구분하고, 지표 소실을 감지할 알람도 정했어요. 중복을 허용한 항목에는 그 이유를 남겼어요.

인스턴스 이름에 writer가 들어 있어도 실제 역할은 다를 수 있었어요. 복제 지연 알람은 역할 변경을 고려해 전체 인스턴스에 설정하고 결측을 정상으로 처리했어요. 코드에서 확인한 구성과 별개로 페일오버 뒤 동작을 이번에 실측하지는 않았어요.

임계값은 관측 기간의 값을 기준으로 정했고 근거가 약한 값에는 한계를 적었어요. 비율 알람은 집계 주기당 호출 수로 분모 가드를 확인해야 했어요. 평균 호출 수와 개별 구간의 호출 수는 구분해야 하며, 당시 구간별 결과와 일부 실행 경위는 추가 확인이 필요해요.
