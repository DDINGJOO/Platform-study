1편. 온콜 탐지·라우팅·호출을 나누고 전달 경로부터 검증하기 ← 지금 이 글

온콜을 준비하면서는 도구 선택부터 생각하기 쉬워요. 당번 스케줄을 어떻게 돌릴지, 응답이 없을 때 다음 담당자에게 몇 분 뒤에 넘길지, 전화와 앱 푸시를 어떤 순서로 보낼지를 비교하게 됩니다.

하지만 스케줄과 에스컬레이션 정책을 갖췄다고 장애를 알 수 있는 건 아니에요. 어떤 상태를 장애로 판단하고 그 결과를 호출 도구에 보낼지가 먼저 정해져 있어야 합니다. 그 연결이 없으면 장애가 생겨도 전화가 오지 않을 수 있어요.

이번 설계에서는 탐지, 라우팅, 호출을 나눠 봤어요. 호출 도구는 기존 관측 도구의 온콜 기능을 쓰되, AWS 지표의 임계값 판단은 CloudWatch에 두었습니다. 도구 선택과 별개로 알람이 담당자에게 전달되는 경로도 먼저 확인하기로 했어요.

1. 탐지, 라우팅, 호출을 나눠 확인해요

세 부분을 나누면 어디까지 준비됐는지 따로 확인할 수 있어요. 장애를 판별하는 탐지, 심각도에 맞는 곳으로 보내는 라우팅, 당번에게 알리는 호출입니다. 아래는 이 설계에서 정한 역할이에요.

계층 역할 구현 수단 -------------------------------------------------------------------- 탐지 (Detection) 무엇이 잘못됐는지 판별한다 CloudWatch 알람 EventBridge 룰 RDS 이벤트 구독 라우팅 (Routing) 심각도를 판정하고 SNS 토픽 3개 어디로 보낼지 결정한다 p1 / p2 / p3 호출 (Paging) 누구를 어떤 순서로 깨울지 온콜 도구 p1 구독으로 호출

탐지 계층에서 신호를 보내지 않으면 호출 도구에 스케줄이 있어도 장애 알림으로 이어지지 않아요. 따라서 도구 설정과 탐지 범위를 별개로 확인해야 했어요.

스케줄과 정책은 도구 화면에서 바로 확인할 수 있지만, 탐지는 서비스별로 어떤 장애를 봐야 하는지부터 조사해야 해요. 도구 설정을 끝낸 것을 온콜 준비가 끝난 것으로 받아들이지 않으려고 이 구분을 두었습니다.

라우팅은 SNS 토픽으로 결정하기로 했어요. SNS 토픽은 알림을 발행하고 구독자에게 전달하는 단위예요. 알람이 p1, p2, p3 중 어디로 보내는지에 따라 심각도 등급을 나누고, 별도의 분기 코드는 두지 않았어요.

장애가 난 순간에도 동작해야 하는 경로라서 연결 상태를 확인하기 쉽게 두고 싶었어요. 알람에 지정한 토픽과 그 토픽의 구독을 보면 어떤 경로로 전달되는지 확인할 수 있습니다. 다만 설정 조회만으로 실제 전화 수신까지 검증할 수는 없어요.

2. 기존 지표로 놓칠 수 있는 상태를 찾아요

기존에 보던 CPU나 오류율만으로는 바로 알아채기 어려운 문제가 있었어요. 탐지 대상을 정할 때 정리한 인지 경로는 아래와 같습니다. 표의 조사 시간과 장애 영향은 당시 정리한 내용이며, 별도의 실행 로그로 다시 확인한 측정 결과는 아니에요.

장애 유형 지금까지의 인지 경로 문제 ------------------------------------------------------------- VPN 터널 단절 대외 연동 실패 문의 사용자가 먼저 발견한다 DLQ 적재 주기적 수동 확인 처리 누락 건이 방치된다 NAT 포트 고갈 간헐적 타임아웃 조사 원인 규명에 반나절 걸린다 ECS 태스크 배치 실패 배포 후 확인 야간 발생 시 인지 불가

VPN 터널이 끊겨도 우리 쪽 CPU나 HTTP 오류율에 바로 변화가 나타난다고 보기는 어려워요. 그래서 애플리케이션 지표와 별도로 터널 상태를 확인하려 했습니다. 사용자 문의를 기다리지 않고 연결 문제를 알아채는 것이 목적이었어요.

NAT 게이트웨이의 포트 할당 실패도 별도로 보고 싶었어요. 앱 로그의 타임아웃만 보면 애플리케이션과 네트워크 중 어디를 조사해야 할지 바로 알기 어렵기 때문이에요. 해당 지표는 원인 후보를 좁히는 데 쓸 수 있지만, 알람 하나로 조사 시간이 얼마나 줄었는지는 확인하지 않았어요.

그래서 1차 대상으로 VPN 터널 상태, DLQ 메시지 수, 데이터베이스 이벤트 구독, NAT 포트 할당 실패를 골랐어요. DLQ는 처리에 실패한 메시지를 따로 보관하는 큐예요. 오류율만으로 처리 누락을 놓치지 않으려는 선택이었습니다.

탐지를 설정하려면 실제 대상과 기존 알람을 먼저 대조해야 했어요. 아래는 당시 정리한 계획과 현황입니다. 대상 개수와 기존 설정의 유무를 적은 것으로, 모든 알람의 전달 검증까지 마쳤다는 의미는 아니에요.

계획한 것 실제로 만들 때 드러난 것 ---------------------------------------------------------- VPN 3세트에 알람 실물 VPN 은 8개였다. 전수로 걸었다 DLQ 알람 운영 환경에는 알람이 없었다. 개발 환경만 있었다 데이터베이스 이벤트 구독 계정에 구독이 하나도 없었다 NAT 포트 알람 한 게이트웨이는 이 지표를 발행한 적이 없었다

DLQ는 알람 이름만 보고 감시되고 있다고 판단하기 어려웠어요. 개발 환경의 알람이 있어도 운영 환경의 큐를 감시한다는 뜻은 아니니까요. 대상 큐와 환경을 함께 대조할 필요가 있었습니다.

당시 정리에는 알람을 추가한 직후 경보 상태가 된 항목도 있었어요. 경보가 발생한 원인과 별도 조치가 끝났는지는 이 기록만으로 확인되지 않아요. 탐지를 추가하면서 기존 상태를 함께 조사할 필요가 드러났습니다.

3. 호출에는 기존 도구의 온콜 기능을 선택했어요

호출 계층에는 이미 쓰던 관측 도구의 온콜 기능을 선택했어요. 지표와 대시보드가 있는 도구에서 알림을 받은 뒤 조사를 이어갈 수 있고, 스케줄과 에스컬레이션 정책, 전화와 앱 푸시를 함께 설정할 수 있다는 점을 고려했습니다.

아래는 당시 채택하지 않은 세 선택지를 정리한 표예요. 제품의 기능이나 지원 종료, 비용에 대한 평가는 당시 검토 기준이며 현재의 제품 비교 결과는 아니에요.

검토 대상 판단 ------------------------------------------------------------------ EOL 이 진행 중인 상용 도구 신규 도입 대상이 아니다 업계 표준으로 불리는 전문 도구 기능은 가장 낫다 2인 팀에는 과하고 비용 부담이 크다 자체 구현 스케줄러 + 함수 + 슬랙 + 알림 서비스 슬랙 알림까지는 쉽다 국내 번호 전화 발신이 병목이다

자체 구현은 슬랙 메시지를 보내는 것까지와 전화 호출까지의 범위가 달랐어요. 스케줄러가 실행 시점을 정하고 함수가 담당자를 골라 멘션을 보낼 수는 있지만, 그 구성을 만들었다고 음성 발신까지 해결되는 건 아니에요.

당시 검토에서는 국내 번호로 전화하려면 별도 음성 발신 연동이 필요하다고 봤어요. 계약과 연동 작업뿐 아니라, 전화 전달을 맡긴 게이트웨이의 실패를 어떻게 감지할지도 고려해야 했습니다. 자체 구현에 걸릴 시간이나 신뢰성을 실제로 측정해 비교한 것은 아니에요.

기존 슬랙 알림에 전화 호출을 더하는 것이 필요한 상황이었어요. 그 기능을 직접 만들고 운영하는 부담을 고려해 기존 도구를 선택했습니다.

시트 수는 호출에 참여하는 사용자를 기준으로 계산해요

비용을 검토할 때는 유저 시트, 즉 과금 대상 사용자 수를 셌어요. 당시 검토한 조건에서는 단순히 팀에 속한 사람 수보다 스케줄과 에스컬레이션 정책, 페이지 수신 설정에 참여하는지가 중요했습니다. 페이지는 담당자에게 보내는 장애 호출을 뜻해요.

시트를 소모하는 사람 온콜 스케줄에 포함된 유저 에스컬레이션 폴리시에 포함된 유저 페이지 수신 설정을 한 유저 시트가 필요 없는 사람 스케줄 · 폴리시 · 페이지를 조회만 하는 유저

당시 조건에서는 스케줄이나 페이지를 조회만 하는 사용자는 과금 대상에 포함하지 않았어요. 이 구분에 맞춰 실제 호출에 참여할 사용자를 셌습니다. 조회 권한만 준 사람과 호출을 받는 사람을 구분한 것이에요.

그래서 초기 계획은 인프라 담당 두 명에게 2시트를 배정하는 것이었어요. 실제 청구 내역이나 모든 사용자의 설정을 대조한 결과까지 확인한 것은 아닙니다.

💡 비용을 검토할 때 나눠 본 항목
당시 비용 검토에서는 AWS 알람·키·이벤트·메시지 비용보다 온콜 도구의 시트 수와 기존 관측 도구의 AWS 폴링 비용을 주요 변수로 봤어요. 실제 청구 내역을 대조한 결과는 아니므로 AWS 비용을 무시해도 된다고 일반화할 수는 없습니다.

CloudWatch에서 탐지한 결과를 SNS로 보내면 그 호출 경로는 관측 도구의 지표 폴링을 기다리지 않아요. 따라서 폴링 주기와 대상을 별도로 검토할 수 있다고 봤습니다. 이 선택으로 실제 비용이 줄었다는 측정 결과는 확인하지 않았어요.

4. AWS 상태 탐지는 CloudWatch 쪽에 뒀어요

처음에는 관측 도구의 AWS 연동이 지표를 수집하고, 그 도구의 모니터가 임계값을 판정한 뒤 온콜로 보내는 구성을 생각했어요. 탐지부터 호출까지 한 도구에 두는 방식입니다.

설계를 구체화하면서 이진 조건과 AWS 서비스 이벤트의 탐지를 AWS 쪽에 두기로 했어요. 이진 조건은 터널의 연결 여부처럼 정해진 조건의 참과 거짓으로 판단할 수 있는 항목이에요. 이유는 아래와 같습니다.

지표가 이미 CloudWatch 에 있다 다른 도구로 넘기면 수집 지연이 붙고 폴링 비용이 붙는다 넘긴 다음에 판정하는 것은 같은 판정을 더 늦게 하는 것이다 탐지를 코드로 관리할 수 있다 CloudWatch 알람은 Terraform 리소스다 콘솔에서 만든 모니터는 drift 감지가 못 본다 누가 임계값을 바꿨는지도, 지웠는지도 알 수 없다 장애 경로가 짧다 그 도구가 흔들려도 CloudWatch 에서 SNS 를 거쳐 슬랙까지는 살아 있다 탐지를 그쪽에 두면 그 도구의 장애가 곧 감시 공백이다

기존 drift 검사는 Terraform에 선언한 설정과 실제 설정의 차이를 확인해요. 콘솔에서 따로 만든 모니터는 그 검사 대상에 자동으로 들어오지 않습니다. CloudWatch 알람을 Terraform으로 관리하면 임계값이나 삭제 여부도 같은 방식으로 비교할 수 있다는 점을 고려했어요.

관측 도구에는 추세와 이상 탐지, 앱 성능처럼 다른 판단이 필요한 항목을 두기로 했어요. 아래 지연 값은 당시 설계에서 사용한 범위이며, 실제 장애 발생부터 담당자에게 도달하기까지 측정한 값은 아니에요.

성격 담당 지연 ------------------------------------------------------------------ 이진 조건 (터널 down, DLQ 적재, 정상 CloudWatch 알람 1~2분 호스트 0) AWS 서비스 이벤트 (컨테이너, 확장 EventBridge 룰 1~2분 그룹, 위협 탐지, 구성 변경) 추세 · 이상탐지 · 지표 부재 · 합성 감시 관측 도구 모니터 10~20분

당시 기준은 빠른 판단이 필요한 AWS 상태와 추세를 봐야 하는 항목을 구분하는 것이었어요. 이 구분은 CloudWatch로 추세나 지표 부재를 다룰 수 없다는 뜻은 아닙니다. 이 설계에서 각 도구에 맡긴 범위예요.

그림 2. AWS 상태 탐지와 관측 도구의 호출 역할을 나눴어요

앱 모니터의 실제 설정은 별도로 확인해야 해요

앱 응답시간 같은 성능 지표는 관측 도구에 맡기기로 했어요. 다만 역할을 정한 것만으로 필요한 모니터가 실제로 설정됐다고 볼 수는 없습니다.

트레이스 데이터가 들어오는 것과 임계값을 넘었을 때 담당자에게 알리는 것은 별개예요. 당시 자료만으로는 필요한 앱 모니터의 존재와 수신자 설정을 모두 확인할 수 없었어요. 이 범위는 감시 역할을 정한 단계와 실제 설정을 확인한 단계를 구분해야 합니다.

5. 알람을 늘리기 전에 전달 경로를 확인했어요

원래 계획은 1주차에 토픽과 암호화 키, 알람 넷을 만들고, 2주차에는 이벤트를 슬랙으로만 보내 관찰하는 것이었어요. 노이즈를 실측한 뒤 온콜 팀을 만들어 연결하려 했습니다.

실제로는 알람을 늘리기 전에 온콜 전달 경로를 먼저 연결해 확인하는 순서로 바꿨어요.

알람을 서른 개 만들어도 사람에게 전달되는지 확인하지 않았다면 호출 경로에는 같은 불확실성이 남아요. 경로를 먼저 확인한 뒤 알람을 늘리되, 새 알람의 조건과 전달 설정도 각각 확인하기로 했습니다.

그 과정에서 별도 리전의 구독 누락을 확인했어요. 아래는 당시 발견 내용입니다.

글로벌 리전 세트를 만든 이유 CloudWatch 알람은 같은 리전의 SNS 토픽만 액션으로 지정할 수 있다 인증서 만료, 비용 이상, 일부 헬스체크 지표는 그 리전에만 존재한다 그래서 토픽과 키를 그 리전에도 한 세트 더 만들었다 그런데 확인해보니 그 리전에는 온콜 도구 구독이 아예 없었다 즉 그 리전의 P1 알람은 슬랙에만 가고 아무도 전화를 안 받는다

해당 리전에는 토픽과 알람이 있었지만 온콜 도구로 보내는 구독이 빠져 있었어요. 알람을 만드는 작업과 담당자 호출 경로를 완성하는 작업을 따로 확인해야 하는 사례였습니다.

기존 구독 검사도 이 누락을 구별하지 못했어요. HTTPS 구독이 하나 이상인지만 셌는데, 슬랙으로 알림을 보내는 Chatbot 구독도 HTTPS를 사용했기 때문이에요. 온콜 구독이 없어도 개수 조건은 충족할 수 있었습니다.

원래 계획대로 관찰부터 했다면 이 확인도 뒤로 밀릴 수 있었어요. 발견 시점이 얼마나 앞당겨졌는지는 확인할 수 없지만, 알람을 늘리기 전에 구독 대상을 확인할 필요는 분명해졌어요.

✅ 전달 검증은 네 단계로 나눠요
더미 알람의 상태를 강제로 바꿔 아래 네 단계를 확인하도록 했어요. 다음은 검증 절차이며, 네 단계가 모두 성공했다는 실행 결과는 아니에요.

1. 관측 도구에 이벤트가 생기는지 확인해요. 없다면 SNS 구독 URL, 키, 원문 전달 옵션, 암호화 키 정책 등을 조사해요.
2. 전화가 실제로 오는지 확인해요. 이벤트 생성과 페이지 호출은 별도 단계예요.
3. 스케줄상 맞는 담당자에게 오는지 확인해요. 팀 식별자와 에스컬레이션 정책을 함께 봐요.
4. OK로 되돌렸을 때 페이지가 자동 종료되는지 확인해요. 복구 알림을 보낼 토픽을 결정할 때 필요한 확인이에요.

자료에서 확인한 실증은 이벤트 도달과 당번의 SMS 수신, 슬랙 전달, ALARM·OK 이벤트 도달이에요. 이것만으로 전화 수신과 페이지 자동 종료까지 성공했다고 볼 수는 없습니다.

호출을 먼저 연결하면 노이즈가 많은 상태에서 불필요한 전화가 올 수 있다는 우려도 있어요. 순서를 바꾼다고 이 문제가 사라지는 것은 아니어서, P1으로 올릴 기준도 함께 정해야 했습니다.

그 기준으로 런북을 요구했어요. 런북은 알림을 받은 사람이 확인하고 조치할 절차를 적은 문서예요. 대응할 일이 없는 항목을 P1으로 올리지 않기로 하고, 알람 모듈이 런북 링크를 필수로 받게 했습니다. 다만 링크가 있다는 검사만으로 절차의 내용까지 보장되지는 않아요.

이후 실제로 쌓이는 알림을 보고 노이즈를 조정하기로 했어요. 설정 전에는 대응 기준을 정하고, 운영 중에는 반복 빈도와 실제 대응 필요성을 확인하는 순서입니다.

✍️ 정리
탐지, 라우팅, 호출을 나누고 AWS 상태 탐지는 CloudWatch와 이벤트 규칙으로, 라우팅은 SNS 토픽으로 구성했어요. 호출에는 기존 관측 도구의 온콜 기능을 선택했습니다.

알람을 늘리기 전에 전달 경로를 확인하면서 별도 리전의 온콜 구독 누락과 HTTPS 개수 검사만으로는 이를 구별할 수 없는 문제를 찾았어요. 이벤트 도달, 실제 전화 수신, 담당자 일치, 복구 시 자동 종료는 각각 확인해야 합니다.

실행 기록에서 확인되는 범위는 이벤트 도달과 SMS 수신이며, 전화 수신과 페이지 자동 종료까지 확인된 것은 아니에요. P1에는 런북 링크를 요구하고, 실제 알림을 관찰한 뒤 노이즈를 조정하기로 했습니다.
