태스크 배치 실패는 태스크를 실행할 자원을 스케줄러가 찾지 못했다는 이벤트예요. 기존 기록에는 서버를 늘리거나 배포하는 중에도 이 이벤트가 나오고, 몇 분 뒤 태스크가 실행되는 경우가 있었다고 적혀 있어요. 다만 하루치를 세었다는 원래 서술의 집계 결과는 이번에 확인한 자료에서 찾지 못했어요.

이벤트가 올 때마다 전화를 걸면 일시적인 실패에도 반복해서 대응해야 해요. 그렇다고 이벤트를 제외하면 태스크가 계속 실행되지 않는 상황을 놓칠 수 있어서, 어느 조건에서 전화할지 구분할 필요가 있었어요.

티어별 전송 대상과 P1 판단 기준을 함께 정했어요. 아래에서는 설계와 코드에 남은 선택을 설명해요. 당시 배포 결과와 실제 전화 횟수는 실행 이력으로 별도 확인하지 못했으므로, 설정의 동작과 수신 결과를 구분해서 볼 필요가 있어요.

1. 티어별로 전송 대상을 정하기

티어는 알림의 전송 경로를 나눈 값이에요. 전화가 가는 P1, 슬랙 멘션까지인 P2, 기록만 남는 P3로 나누고 티어마다 알림 토픽을 하나씩 뒀어요.

알람 모듈은 토픽 세 개의 주소를 맵으로 받아 티어 값에 맞는 주소를 선택해요. 알람에 연결한 토픽이 전송 대상을 정하므로, 별도 코드가 심각도를 다시 판정해 경로를 고를 필요는 없어요.

alarm_actions = [ topic_arns[ tier ] ] ok_actions = [ topic_arns[ tier == "p1" ? "p2" : tier ] ]

두 번째 줄은 복구 알림의 전송 대상을 정해요. P1의 복구 알림은 P2로 보내고, P2와 P3는 기존 티어를 유지해요. 예를 들어 장애 전화 후 15분 뒤 자동 복구됐을 때, 복구 사실은 슬랙으로 확인할 수 있게 한 구성이에요. 위 코드의 삼항 연산자가 이 차이를 처리해요.

티어를 표시하는 위치는 설계 문서와 달라졌어요. 문서에서는 알람 이름 끝에 티어 접미사를 붙이기로 했지만, 이름을 바꿔 알람을 다시 만들면 기존 히스토리를 이어서 보기 어려워져요. 도입 계획에는 노이즈를 실측한 뒤 티어를 올리는 과정도 있었기 때문에, 티어 변경 때 이름은 유지하도록 태그에 표시했어요. 태그별로 알람을 조회하고 연결된 토픽과 대조할 수도 있어요.

배달 실패를 감시하는 알람도 전송 대상을 기준으로 보면 이해하기 쉬워요.

알림 배달 실패 감시 보내는 곳 -------------------------------------------- p1 배달이 실패했다 -> p2 전화 경로가 끊겼으니 슬랙으로 p2 배달이 실패했다 -> p1 슬랙이 끊겼으니 전화로 p3 배달이 실패했다 -> p2 급하지 않다

P1 경로의 배달 실패는 P2로, P2 경로의 배달 실패는 P1으로 보내요. 고장 난 경로에만 그 경로의 실패 알림을 보내지 않도록 한 구성이에요. 기존 기록에는 P2 배달 실패 알람이 P2로 연결돼 있던 사례도 있어요. 이 경우에는 감시 대상과 알림 전송 경로가 겹친다는 문제가 있어요.

환경과 티어의 조합도 모듈에서 검증해요. 운영은 세 티어를 모두 쓸 수 있고, 스테이징은 P2와 P3, 개발은 P3만 허용해요. 개발 환경 알람에 P1을 잘못 지정하는 일을 문서 안내에만 맡기지 않기 위한 제한이에요.

2. 태스크 배치 실패 이벤트를 선택하기

여기서 사용하는 신호는 CPU나 메모리 지표와 달라요. 태스크 배치 실패는 스케줄러가 발행하는 이벤트를 EventBridge에서 받아요. 아래 패턴은 ECS 서비스의 태스크 배치 실패 이벤트를 선택하는 설정이에요.

{ "source": ["aws.ecs"], "detail-type": ["ECS Service Action"], "detail": { "eventName": ["SERVICE_TASK_PLACEMENT_FAILURE"] } }

자원이 부족한 이유도 이벤트 안의 필드에서 확인할 수 있어요. 메모리가 부족한지 CPU가 부족한지 알 수 있으면, 대응할 때 어떤 자원을 먼저 확인할지 정하는 데 도움이 돼요.

이 필드로 자원 부족만 선택하고 설정 오류는 제외할 수도 있지만, 여기서는 조건을 더 좁히지 않았어요. 필드명이나 값의 형태를 잘못 쓰면 룰 배포에 성공해도 실제 이벤트는 매치하지 못할 수 있기 때문이에요. 배포 성공만으로 감지가 동작한다고 판단할 수는 없어요.

넓게 선택하면 놓칠 가능성은 줄어들지만, P1에 연결했을 때 전화가 늘어날 수 있어요. 이 설정에서는 우선 이벤트를 받고 실제 값을 확인한 뒤 조건을 좁힐지 정하는 쪽을 선택했어요. 필터를 넓게 둔 선택이므로, 호출 빈도를 확인하는 작업은 별도로 필요해요.

💡 입력 변환에 쓰는 이벤트 필드 확인하기
이벤트 버스의 타깃을 알림 토픽으로 지정하면 JSON 원본이 전달돼요. 슬랙 카드에서 필요한 내용을 읽기 쉽게 하려고 룰의 입력 변환 기능을 사용했어요.

변환 함수를 추가하면 그 함수의 실패도 감시해야 하므로, 이 구성에서는 룰 자체의 기능으로 문자열을 만들었어요. 다만 필드 경로가 잘못되면 변환이나 배달이 실패할 수 있다는 제약이 기록돼 있어요. 없는 경로를 참조할 때 항상 배달 전체가 실패하는지는 여기서 별도로 검증하지 않았어요.

여러 이벤트를 받는 룰의 카드에는 공통으로 확인한 필드만 넣고, 자원 부족 사유는 단일 이벤트를 받는 룰의 카드에만 넣었어요.

3. 서비스 부족 증상을 P1 기준으로 삼기

기본적인 P1 기준은 서비스가 실제로 부족한 상태예요. 원하는 실행 대수가 있는데 서비스 중인 대수가 0이거나, 로드밸런서 뒤에 정상 타깃이 없는 상태를 대상으로 삼았어요.

증상에 거는 P1 띄우려는 대수는 있는데 서비스 중인 대수가 0 이다 로드밸런서 뒤에 정상 타깃이 하나도 없다 원인 이벤트 (맥락) 놓을 자리가 없다 이미지를 못 가져온다 설정이 틀렸다 컨테이너가 메모리 상한을 넘었다 ...

이 조건은 자원 부족, 이미지 다운로드 실패, 애플리케이션 기동 실패를 원인별로 모두 나열하지 않아도 돼요. 그 결과 서비스 중인 대수가 0이 되면 같은 증상 조건으로 감지할 수 있어요. 다만 이 조건으로 모든 장애를 감지한다는 뜻은 아니에요.

증상 알람만으로는 왜 서비스가 부족해졌는지 알 수 없어요. 그래서 원인 이벤트는 버리지 않고 더 낮은 티어의 슬랙 카드로 남기도록 했어요. 전화를 받은 뒤 같은 시각의 원인 이벤트를 찾아 진단에 활용하는 구성이에요.

기존 수정 기록에는 배치 클러스터에서 태스크 종료 코드로 실패를 구분했다가 배포 때 오탐이 난 사례가 있어요. 스케줄러가 이전 태스크를 멈추는 과정에서도 컨테이너의 종료 코드가 0이 아니어서 실패로 분류됐다는 내용이에요. 당시 전화가 배포마다 왔는지와 애플리케이션의 종료 신호 처리 과정은 수신·실행 로그로 확인하지 못했어요.

수정한 규칙은 종료 코드 대신 태스크가 멈춘 사유를 나타내는 필드를 사용해요. 그중 시작 자체에 실패한 경우만 전화 대상으로 선택했어요. 배포 과정에서 스케줄러가 정상적으로 멈춘 태스크를 실패로 분류하지 않으려는 변경이에요.

컨테이너가 스스로 종료되는 경우에는 제약이 남아요. 이 배치를 서비스 형태로 실행하는 구성에서는 정상 완료와 크래시가 같은 값으로 나타난다고 기록돼 있어요. 그 값만으로 둘을 구분하지 못하므로, 해당 이벤트는 전화 대신 기록 대상으로 뒀어요.

그림 1. 서비스 부족 증상으로 호출하고 원인 이벤트는 진단 자료로 남겨요

4. 배치 실패 이벤트를 P1으로 선택한 예외

태스크 배치 실패 이벤트는 기본 기준의 예외로 P1에 연결했어요. 감지 목록에는 단발 발생은 기록만 남기도록 적혀 있었지만, 구현에서는 전화 대상으로 선택했어요.

태스크를 배치할 자원이 없으면 실행을 시작할 수 없다는 점을 우선한 판단이에요. 다만 도입부에서 본 것처럼 일시적인 실패 뒤 실행될 수도 있어요. 이 이벤트만으로 지속적인 서비스 부족을 확정할 수는 없으므로, 증상 기준과 완전히 같다고 볼 수는 없어요.

이벤트 룰 자체에는 설계 문서의 "5분 안에 3회 이상"을 집계하는 조건이 없어요. 함수나 로그 지표 필터도 이 경로에는 붙이지 않았기 때문에, 직접 P1 토픽으로 보내는 설정은 이벤트마다 전화 요청을 보내는 구성이에요.

원자료에도 발생 빈도를 측정하기 전에 P1을 선택했다는 제약이 남아 있어요. 한 배포에서 배치 실패가 연달아 나면 알림도 반복될 수 있어요. 그래서 코드 주석에는 티어를 낮추거나 집계를 도입하는 순서도 적어뒀어요.

시끄러우면 되돌리는 순서 1. 타깃을 p2 로 내린다 전화 -> 슬랙. 코드 한 줄이다 2. 그래도 시끄러우면 p3 기록만 남는다 3. 세는 것이 정말 필요하면 로그 지표 필터를 도입한다

배치 클러스터 쪽에서는 로그 지표 필터를 추가하는 대신 EventBridge 룰이 발행하는 매치 수 지표를 사용했어요.

룰이 매치한 이벤트 수에 CloudWatch 알람을 걸면 상태 변화를 기준으로 통지할 수 있어요. 아래 그림처럼 연속된 실패 동안 ALARM 상태가 유지된다면 ALARM 진입 알림은 한 번이에요. 정상으로 돌아오면 복구 알림을 보내요. 따라서 "실패 5회에 전화 1통"은 이 상태가 유지되는 예시이지, 실제 수신 횟수를 측정한 결과는 아니에요.

그림 2. ALARM 상태가 유지되는 동안에는 반복 이벤트마다 전화하지 않아요

5. 알람에 런북과 대응 정보를 넣기

호출 경로를 먼저 구성하면서, 어떤 조건을 P1으로 분류할지도 함께 정해야 했어요. 전화를 받은 사람이 확인할 내용과 대응 방법이 있어야 하기 때문이에요.

알람을 추가할 때 런북 URL을 필수로 받도록 했어요. 런북은 알람을 받은 사람이 확인하고 조치할 절차를 적은 문서예요.

variable "runbook_url" { type = string validation { condition = can(regex("^https://", var.runbook_url)) error_message = "런북 URL 이 없으면 알람을 만들 수 없다. 먼저 런북을 쓸 것." } }

이 변수에는 기본값이 없어서 호출하는 쪽에서 URL을 전달해야 해요. 검증식은 HTTPS로 시작하는지도 확인해요. 다만 URL 입력을 강제하는 것만으로 대응 절차의 내용까지 검증되지는 않아요. 런북을 작성할 때 실제로 할 수 있는 조치가 있는지 확인하고 P1 여부를 판단해야 해요.

런북 URL은 알람 설명에 들어가고, 그 설명은 슬랙 카드 본문으로 전달돼요. 이 구성에서는 카드에 필요한 정보를 알람 이름과 설명에 담았어요. 전화를 받은 사람이 카드에서 대응 절차를 찾을 수 있도록 한 것이에요.

모듈에는 사람이 읽을 설명을 넣는 칸도 따로 뒀어요. 카드에 이미 나오는 지표 이름을 반복하기보다는, 어떤 상태가 됐고 지금 무엇이 동작하지 않는지를 적도록 했어요.

6. 복합 알람 도입을 미룬 이유와 재검토 조건

설계 문서에는 상위 원인 알람이 ALARM 상태일 때 하위 알람의 액션을 억제하고, 복합 알람이 대표로 전화하는 구성이 있었어요. 예를 들어 DB 페일오버 한 건에 P1 알람 다섯 개가 연결돼 있다면 같은 사건으로 전화 다섯 통을 요청할 수 있어서, 중복 호출을 줄이려는 설계였어요.

구현에서는 일단 각 알람이 직접 통지하도록 선택했어요. 당시 알람 수와 무음 설정을 빠뜨렸을 때의 동작을 함께 고려했어요.

설계는 알람 145개 규모를 상정했지만, 판단 당시 기록에 나온 알람은 19개였어요. 그 규모에서 복합 알람을 먼저 도입하면 중복 호출을 줄이는 효과보다 설정과 관리할 대상이 늘어나는 부담이 크다고 봤어요.

기존 기록에는 알람의 직접 통지 여부를 정하는 값의 기본값이 거짓이었다고 적혀 있어요. 이 값을 생략하면 알람은 만들어져도 직접 알림을 보내지 않는 구성이었어요. 알람 생성 여부만 확인하면 이 차이를 놓칠 수 있어요.

1차 알람을 추가하던 중 열한 개가 그 값 없이 작성돼 있었다는 기록도 있어요. 대신 통지할 복합 알람도 없는 상태였으므로, 해당 구성으로는 알람이 상태를 바꿔도 알림을 받을 경로가 없었다는 내용이에요. 이는 당시 구성의 문제를 설명하는 기록이며, 실제 배포나 수신 결과를 확인한 것은 아니에요.

⚠️ 직접 통지와 복합 알람의 역할을 함께 확인하기
기본값을 참으로 바꾸면 생략한 알람도 직접 통지하게 돼요. 다만 무음 알람과 복합 알람을 함께 쓰려면, 어떤 알람이 대신 통지하는지 계속 확인해야 해요.

여기서는 각 알람이 직접 통지하는 구성을 기본으로 선택했어요. 무음 설정은 해당 알람을 대신 통지할 복합 알람이 실제로 있을 때만 쓰도록 했어요. 누락으로 알림이 사라지는 일을 피하고, 여러 알람을 통해 같은 사건의 영향 범위를 볼 수 있다는 점도 고려했어요. 당시 19개였던 규모에서 내린 선택이므로 알람 수가 늘면 재검토해야 해요.

복합 알람을 다시 검토할 조건도 정했어요. 한 사건에 전화가 세 통 이상 온 일이 두 번 생기면 해당 묶음에 복합 알람을 적용하고, 알람이 50개를 넘으면 선제적으로 재검토하기로 했어요.

후속 기록에는 알람이 200개를 넘었고, DB 한 대의 페일오버에 이벤트 구독 하나, 재시작 알람 둘, 복제 지연 알람 하나가 연결돼 최대 네 통을 요청할 수 있다고 적혀 있어요. 따라서 알람 수에 관한 재검토 조건은 이미 넘었다는 점이 남아요. 실제로 세 통 이상 받은 일이 두 번 있었는지와 그 뒤 재검토를 수행했는지는 이번 자료만으로 확인하지 못했어요. 네 통이 올 수 있다는 경로 계산과 실제 수신 결과도 구분해야 해요.

✍️ 설정과 확인 범위
티어마다 SNS 토픽을 연결하고, P1 복구 알림은 P2로 보내도록 했어요. 서비스 부족 증상을 기본 호출 기준으로 삼되, 태스크 배치 실패 이벤트는 P1으로 선택한 예외와 반복 호출 가능성을 함께 남겼어요.

배치 클러스터에서는 룰의 매치 수 지표에 상태를 가진 알람을 연결했어요. 런북 URL은 필수로 받고, 복합 알람 도입은 직접 통지를 기본으로 둔 뒤 재검토하기로 했어요. 후속 기록의 알람 수는 이미 재검토 기준을 넘었지만, 실제 호출 횟수와 재검토 수행 여부는 확인하지 못했어요. 설정에서 예상한 통지와 실제로 받은 전화를 같은 결과로 단정할 수는 없어요.
