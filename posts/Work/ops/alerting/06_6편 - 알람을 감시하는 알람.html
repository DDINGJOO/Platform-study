6편. DLQ와 하트비트로 알림 경로를 점검하는 방법 ← 지금 이 글

알람이 이백 개를 넘겼을 때는 개별 알람뿐 아니라 알림이 사람에게 도달하는지도 확인할 필요가 있었어요.

Slack에 알림이 없다는 사실만으로는 경로가 정상인지 알 수 없어요. 알림을 보낼 사건이 없는 상태와, 사건이 있어도 알림이 전달되지 않는 상태가 채널에서는 같게 보이기 때문이에요.

그래서 알림 경로의 실패와 신호의 부재, 감시 대상 누락을 각각 확인하는 장치를 구성했어요. 아래의 당시 경위와 수치는 기존 작업 기록을 유지한 것이에요. 이번 대조에서는 고정한 저장소의 설정과 주석을 확인했으며, 당시 배포·발행·수신 이력이나 외부 모니터 수정 후의 동작까지 다시 검증하지는 못했어요.

1. 발화 기록만으로는 전달 여부를 알기 어려워요

알람이 발화해도 알림이 담당자에게 도달하지 않으면 대응이 늦어질 수 있어요. 전달 경로에는 여러 서비스가 연결돼 있어요.

알람 · 이벤트 룰 · DB 이벤트 구독 -> 티어별 알림 토픽 (암호화 키로 암호화) -> 채팅 연동 -> 팀 채널 -> 온콜 도구 구독 -> 전화 · 문자 · 에스컬레이션 조각마다 조용히 죽는 방식이 따로 있다

이 경로의 어느 지점에서 전달이 실패하더라도 알람의 발화 기록만으로는 그 뒤의 수신 여부를 알기 어려워요. 발화 기록과 전달 실패 지표를 함께 봐야 해요.

다른 이백 개의 조건이 정확해도 알림 경로가 끊기면 대응할 수 없어요. 그래서 개별 조건을 조정하는 일과 별개로 경로 자체를 확인하도록 했어요.

2. DLQ 알람은 다른 전달 경로로 보내요

실패 메시지를 보관하는 큐인 DLQ를 붙인 이유와 재시도 정책은 2편에서 설명했어요. 여기서는 큐에 메시지가 쌓였는지 알람으로 확인해요. 이벤트 룰의 타깃 호출 실패 알람도 함께 사용해 전달 실패를 살펴봐요.

이 알람은 감시하는 경로가 실패했을 때도 전달돼야 하므로 수신 경로를 따로 정해야 했어요.

당시 기록에는 처음에 모두 낮은 티어로 보냈다고 남아 있어요. 그 티어의 전달 실패를 알리는 알람도 같은 티어로 보내는 구성이었어요. 주석에서는 이를 경고했지만, 액션에는 같은 경로가 지정돼 있었어요.

수정한 구성은 감시 대상과 다른 티어로 보내도록 했어요.

p1 배달 실패 -> p2 로 전화 경로가 끊겼으니 채팅으로 p2 배달 실패 -> p1 로 채팅이 끊겼으니 전화로 p3 배달 실패 -> p2 로 하트비트 배달 실패는 급하지 않다

3편에서는 티어를 알림의 전달 경로로 정의했어요. 이 정의를 유지하면 별도 예외 장치를 추가하지 않고 티어 값으로 교차 라우팅을 표현할 수 있어요.

이 선택에는 채팅 경로의 장애가 전화 호출로 이어질 수 있다는 부담이 있어요. 야간에도 호출될 수 있지만, 같은 경로로 보내다 전달 실패를 놓치는 것보다는 다른 경로로 알리는 쪽을 택했어요.

🕓 실패 메시지를 오래 보관한 이유
실패 메시지의 보존 기간을 최대로 설정했어요. 전달이 복구돼도 큐에 남은 메시지를 조사할 시간을 확보하려는 선택이에요.

메시지가 남아 있는 동안에는 큐 깊이 알람도 유지될 수 있어요. 다만 보존 기간이 지나면 메시지가 만료되므로 사람이 비울 때까지 무기한 유지되는 것은 아니에요. 알람이 해제됐다는 사실만으로 조사가 끝났다고 판단하지 않도록 했어요.
그림 1. 전달 실패 알람은 감시 대상과 다른 티어로 보내요

3. 신호가 오지 않는 상태는 하트비트로 확인해요

위의 두 장치는 전달 과정에서 드러나는 실패를 확인해요. 하지만 아래처럼 별도로 확인해야 하는 경우도 있어요.

이 둘이 못 잡는 것 온콜 스케줄이 비어 있다 (담당자 이동, 로테이션 만료) -> 수신 측이 정상 응답을 돌려주므로 실패 큐에도 안 걸린다 팀 핸들이 바뀌었다 이벤트 룰이 삭제됐다 -> 발행 자체가 없으므로 실패도 없다 알림 토픽의 암호화 키가 비활성화됐다 -> 발행이 전부 실패한다 공통점: 배달 실패가 아니라 발행 자체가 없다. 실패한 메시지가 없으니 실패 큐는 계속 비어 있다

DLQ가 비어 있다는 사실만으로 알림 경로 전체가 정상이라고 판단할 수는 없어요. 위 예시의 온콜 스케줄 누락은 수신 뒤 담당자가 정해지지 않는 문제이고, 이벤트 룰 삭제는 발행이 없는 문제예요. 보호한 예시 블록에는 이를 모두 발행 부재로 묶었지만, 실제로는 실패 지점이 달라요.

이를 보완하려고 15분마다 로그 전용 티어로 신호를 보내는 하트비트를 구성했어요. 하트비트는 주기적인 신호를 받아 경로가 계속 동작하는지 확인하는 방식이에요. 신호가 오지 않는지는 외부 관측 도구에서 판단하도록 했어요.

판단 주체를 클라우드 밖에 두면 발행 측 리전의 장애로 신호가 끊기는 경우도 관측할 수 있도록 설계할 수 있어요. 다만 외부 도구의 수신·모니터·호출 경로까지 정상이어야 하고, 리전 장애 상황에서의 실제 호출을 이번에 확인한 것은 아니에요.

이 하트비트로 확인하는 범위는 주기 신호의 발행부터 외부 도구의 수신·매칭까지예요. 로그 전용 P3 경로를 쓰므로 P1 구독과 당번 스케줄, 실제 전화 수신 및 복구 후 재호출은 별도로 점검해야 해요. P3 신호가 계속 들어온다고 P1 호출 경로까지 정상이라고 확인한 것은 아니에요.

당시 기록에는 로그 전용 티어의 토픽과 실패 큐만 있고 발행 주체는 없었다고 남아 있어요. 문서에 하트비트 용도로 적혀 있어도 신호를 주기적으로 보내는 설정이 별도로 필요했어요.

🔇 하트비트는 채팅 구독이 없는 티어로 보내요
하트비트를 채팅 채널이 연결된 티어로 보내면 15분마다 카드가 표시돼요. 반복되는 카드 때문에 채널을 뮤트하면 실제 알람도 놓칠 수 있어요.

그래서 사람이 확인하는 채팅 구독이 없는 티어로 보내고 관측 도구에서 신호 수를 확인하도록 했어요. 부재를 판단하는 창은 네 주기로 잡았으므로 한 시간 분량의 신호를 기준으로 해요. 이 설정만으로 실제 호출까지의 최대 시간을 보장하는 것은 아니에요.

4. 하트비트 본문과 모니터 태그 조건이 달랐어요

하트비트는 발행 설정과 부재를 판단하는 모니터로 나뉘어요. 발행 측은 코드로 관리하고, 당시에는 관측 도구의 프로바이더를 도입하지 않아 모니터를 수동으로 관리했어요. 코드 주석에도 이 파일만으로 구성이 끝나지 않는다고 적혀 있어요.

당시 실패 기록은 수동으로 관리하던 모니터 조건에 관한 것이에요.

이벤트 본문에 넣은 식별용 필드 값을 모니터의 태그 조건에도 사용했어요. 그런데 당시 수신 방식에서는 본문 필드가 같은 이름의 태그로 변환되지 않았어요. 수신 측이 붙이는 토픽·리전 등의 태그와 본문 텍스트를 구분해서 조건을 작성해야 했어요.

우리가 발행한 본문 { "source": "...-heartbeat", "env": "prod", "message": "..." } 수신 측이 실제로 붙이는 태그 source:<메시징 서비스> topic:<토픽 이름> region:<리전> 모니터 조건을 본문 필드 이름으로 쓰면 매치 0건. 세어야 할 신호를 하나도 세지 않는다

당시 기록상 발행 룰의 주기는 15분이었지만 모니터 조건에 맞는 이벤트는 없었어요. 다만 이번에는 당시 발행 이력과 모니터 결과를 직접 확인하지 못했으므로, 정시 발행과 매치 0건을 재검증한 결과로 보지는 않아요.

조건을 태그 하나와 본문 자유 텍스트 하나로 수정했다는 기록이 남아 있어요. 이 방식에서는 토픽 이름이나 발행 문구가 바뀔 때 모니터 조건도 함께 고쳐야 해요. 수동으로 관리하는 모니터는 Terraform 드리프트 검사 범위 밖이므로 별도 확인이 필요해요. 수정 뒤 실제 수신·호출까지 정상화됐는지는 이번 자료 대조로 확인하지 못했어요.

5편에서 다룬 것처럼 배포된 설정이 있어도 실제 이벤트에 조건이 맞는지는 별도로 확인해야 해요. 하트비트도 예외가 아니었어요.

5. 코드 목록과 실제 리소스를 양방향으로 비교해요

다음으로 알람이 연결된 대상 목록을 계정의 실제 리소스와 대조하는 스크립트를 사용했어요.

5편의 3장에서 다룬 알람 중에는 감시 대상을 코드에 직접 나열한 것도 있었어요. 대상 선정 기준이 태그여도 최종 목록을 수동으로 관리하면 누락되거나 삭제된 대상이 남을 수 있어요.

감시 밖 실물에 있는데 코드에 없다 새 리소스에 알람이 안 붙는다 plan 은 +0, CI 는 초록불. 아무 신호가 없다 유령 코드에 있는데 실물에 없다 지워진 리소스가 목록에 남는다 지표 부재를 장애로 보는 알람이면 그 순간부터 영구 발화 중복 두 스택이 같은 대상을 본다 경고만 한다. 알람을 옮기는 중에는 정상이다

기존 기록에는 이런 차이를 네 번 발견했다고 남아 있어요. 사흘 사이에 세 번, 그리고 며칠 뒤에 한 번이에요. 아래 개수와 경위는 당시 기록이며, 이번에 계정 실물을 조회해 다시 센 값은 아니에요.

VPN 3세트인 줄 알았는데 실제 8개 DB 2대인 줄 알았는데 실제 13대 (11대가 감시 밖) ASG 7개에 걸었는데 계정에 12개 연결 하나가 삭제됐는데 코드에는 남아 있었다 (아무것도 알려주지 않았다)

네 번째 사례가 대조 검사를 만든 계기였어요. 앞의 셋은 사람이 조회하다 발견했지만, 삭제된 연결이 목록에 남는 경우에는 이를 정기적으로 확인할 검사가 필요했어요.

스크립트는 코드에서 읽은 목록과 계정에서 조회한 목록을 양방향으로 비교해요. 검사 범위와 조회 실패 처리에서 두 가지를 정했어요.

알람을 리소스 소유 스택으로 옮겨도 누락으로 판정하지 않도록 여러 스택에서 읽은 목록의 합집합을 사용해요. 파일 경로 하나에만 의존하면 정상적인 스택 이동도 감시 누락으로 오탐할 수 있어요.

실물 조회에 실패하거나 비교에 필요한 목록을 얻지 못하면 대조 결과를 내지 않고 중단하도록 했어요. 조회 실패를 빈 계정으로 취급하면 코드의 모든 대상을 삭제된 리소스로 잘못 판정할 수 있기 때문이에요.

6. 파서가 빈 목록을 반환하는 경우도 검사해요

실물 조회와 별개로 코드에서 목록을 읽는 파서도 확인해야 해요. 스크립트에는 다음과 같은 경고가 남아 있어요.

# ── 자기검사 ──────────────────────────────────────── # 파서가 조용히 빈 목록을 내면 "감시 밖 0개" 로 보이고, 그건 통과와 구분되지 않는다. # 그 경우가 이 검사에서 가장 나쁜 실패다.

이 주석은 파서가 아무 목록도 읽지 못한 상태를 정상 결과로 오인하지 말자는 경고예요. 다만 코드 목록이 비었다고 항상 감시 밖이 0개가 되는 것은 아니에요. 실물 목록과 어떻게 비교하는지, 대상 종류의 순회를 생략하는지에 따라 결과가 달라지므로 빈 입력 처리도 함께 확인해야 해요.

파서가 읽은 결과가 비었는데 이를 허용하면 실제 대조를 건너뛰어도 검사 성공으로 보일 수 있어요. 목록 파싱 실패와 정상적인 일치 결과를 구분해야 했어요.

그래서 자격증명 없이 실행할 수 있는 파서 자체검사를 추가했어요. 고정한 소스에는 다음 항목을 확인하는 자체검사가 있지만, 과거 CI에서 매번 실행됐는지를 이번에 재검증하지는 않았어요.

맵과 집합 두 형태를 각각 파싱하는가 주석 안에 남아 있는 옛 식별자를 목록으로 주워오지 않는가 -> 주워오면 지워진 리소스가 계속 코드에 있는 것처럼 보여 유령 판정이 조용히 사라진다 없는 목록을 찾았다고 대답하지 않는가 같은 키가 서로 다른 값을 가리키면 오류로 멈추는가 저장소에서 각 종류의 목록을 실제로 하나 이상 찾는가 -> 파일 패턴이 아무것도 못 잡으면 이 검사는 조용히 통과한다

마지막 항목은 실제 저장소에서 각 종류의 목록을 하나 이상 찾는지 확인해요. 파일 탐색 패턴이 달라져 입력이 사라진 경우에도 검사 성공으로 끝나지 않게 하려는 확인이에요.

7. 하루 한 번의 검사는 짧은 누락을 놓칠 수 있어요

대조 검사는 하루 한 번 실행하는 드리프트 잡에 연결한 구성이에요. 계정의 리소스를 조회해야 하므로 자격증명이 필요해요. 이번에는 잡의 과거 실행 이력까지 확인하지 않았어요.

알람이 몇 시간 동안 없다가 다음 검사 전에 복구되면 실행 시점의 목록은 다시 일치할 수 있어요. 하루 한 번의 대조만으로는 그 사이의 누락을 발견하기 어려워요. 다른 로그에 흔적이 남을 수는 있지만 이 검사만으로는 확인할 수 없어요.

삭제된 대상이 코드에 남은 경우에는 지표 부재를 장애로 보는 알람이 계속 발화할 수 있어요. 반대로 새 리소스에 알람이 빠진 경우에는 그 누락 자체를 알릴 장치가 없으므로, 정상적으로 보이는 동안에도 감시 대상 대조가 필요해요.

각 장치의 확인 범위와 한계를 정리하면 다음과 같아요. 아래 블록의 과거 실행 서술은 기존 기록을 유지한 것이며 이번에 재현한 결과는 아니에요.

가드가 실패하는 방식 세 가지 못 봄 감시 대상 자체가 목록에 없거나 발행 주체가 없다 틀린 답 매치 0건인데 출력이 통과와 같다 주기가 김 사건이 실행 간격 안에서 열리고 닫힌다 그리고 우리 자기 감시가 각각 그 셋에 하나씩 걸렸다 실패 큐 알람 -> 발행이 없는 상태를 못 본다 하트비트 -> 세는 쪽의 조건이 달라 매치 0건이었다 목록 대조 -> 하루 한 번 돈다
그림 2. 전달 실패, 신호 부재, 대상 누락은 확인하는 지점이 달라요

실패 큐 알람은 전달 실패를, 하트비트는 신호의 부재를, 목록 대조는 감시 대상의 차이를 확인해요. 확인하는 지점이 달라 함께 사용할 수 있지만, 세 장치가 모든 공통 장애에서 독립적으로 동작한다고 확인한 것은 아니에요.

운영할 때는 각 장치가 받는 입력과 알림이 나가는 경로, 실행 주기를 함께 확인해야 해요. 설정이 존재한다는 사실과 실제 사건을 감지했다는 결과를 구분해서 관리할 필요가 있어요.

✍️ 구성과 확인 범위
DLQ와 타깃 호출 실패 알람은 다른 전달 경로로 보내고, 신호의 부재는 외부 하트비트 모니터로 확인하도록 구성했어요. 코드 목록과 실물의 대조에는 파서 자체검사를 더했지만 하루 한 번보다 짧은 누락은 놓칠 수 있어요.

이번 대조에서는 저장소의 설정과 주석을 확인했어요. 본문의 당시 수치·실패 경위는 기존 기록을 유지했으며, 과거 실행 이력과 수동 모니터 수정 후의 실제 수신·호출 결과는 확인하지 못했어요.
