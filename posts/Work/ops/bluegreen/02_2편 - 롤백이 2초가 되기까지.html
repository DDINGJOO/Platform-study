📚 블루그린, 2부작
1편. 배포 중 healthy host 알람을 줄이고 블루그린을 선택한 이유
2편. 트래픽 네 경로를 nginx에서 함께 전환한 이유 ← 지금 이 글

1편에서 블루그린을 선택한 이유는 롤백이었어요. 이전 버전이 실행 중이면 다시 배포하는 대신 트래픽의 목적지를 바꿔 되돌릴 수 있기 때문이에요.

다음으로는 트래픽을 어디서 전환할지 정해야 했어요. 로드밸런서 가중치를 검토하다가 호스트의 nginx로 전환하는 방식을 선택했어요. 당시에는 롤백을 2초 안에 끝내도록 설계했지만, 뒤의 정정처럼 실제 롤백으로 측정한 시간은 아니었어요. 아래 경로와 실행 수치는 당시 본문과 로그 발췌에 남은 값이며, 이번 확인에서 실행 원본까지 대조하지는 못했어요.

1. 로드밸런서 가중치 전환을 검토했어요

blue 타깃그룹과 green 타깃그룹을 만들고, 리스너의 forward 규칙에 가중치를 100/0으로 두는 방식이에요. 전환할 때는 이를 0/100으로 바꿔요.

이 방식을 쓰려면 리스너가 가중치를 받는 형태여야 하고, 그 리스너를 바꿀 권한도 있어야 해요. 당시 확인한 내용으로는 리스너는 이미 가중치 forward 형태였고 권한을 추가하면 됐어요.

권한을 추가하기 전에 해당 인스턴스의 역할을 다른 인스턴스도 쓰는지 조회했어요.

이 역할을 쓰는 인스턴스 수: 25대 prod 와 dev 가 섞여 있고, 서로 다른 서비스 여섯 종류가 같은 역할을 쓴다

당시 조회에는 같은 역할을 쓰는 인스턴스가 25대 있었어요. 공용 역할에 리스너 변경 권한을 넓게 추가하면 다른 인스턴스도 그 권한을 갖게 돼요. 그래서 전용 역할을 만들고 변경 대상을 리스너 하나로 한정하는 쪽으로 준비했어요. 이 역할이 실제 배포에 쓰였다는 뜻은 아니에요.

💡 허용 대상과 거부 대상을 함께 확인했어요
당시 정책 시뮬레이터에는 다음 두 결과가 나왔다고 남겼어요.
대상 리스너 → allowed · 관계없는 리스너 → implicitDeny
대상 작업이 허용되는지만 보면 권한 범위가 지나치게 넓어도 통과할 수 있어요. 허용하지 않을 대상도 함께 확인해야 해요. 시뮬레이션 결과는 실제 배포 실행을 확인한 것과는 구분해야 해요.

2. 트래픽은 네 경로로 들어왔어요

이어서 타깃그룹을 어디에 연결할지 정하려고 로드밸런서와 연결 관계를 조회했어요.

이름 실제 노출 종류 ...-nlb-prod internal network ...-nlb-prod-internal internet-facing network ← 이름과 반대다 ...-alb-prod internet-facing application ...-internal-alb-prod internal application

조회 결과에서는 -internal이 붙은 쪽이 인터넷에 공개된 구성이었어요. 이름만 보고 내부 경로라고 판단하지 않고 실제 설정을 확인해야 했어요.

타깃 타입과 연결 관계를 확인하고, 앱 로그에 남은 호출도 살펴봤어요. 당시 파악한 경로는 다음과 같았어요.

GET http://<사설IP>/api/v1/... ← Host 헤더가 사설 IP POST http://<사설IP>/auth/login/... ← 로그인도 이 경로로 POST http://<dev도메인>/api/... ← dev 도메인이 prod 를 때린다

여기에는 로드밸런서를 거치지 않고 인스턴스를 직접 호출하는 경로도 있었어요.

그림 1. ①과 ③은 독립된 경로이고 ④는 로드밸런서를 거치지 않아요

②는 내부 LB를 타깃으로 쓰므로 ③을 바꾸면 함께 전환되는 구조였어요. 반면 ①은 공인 LB가 인스턴스를 직접 가리키는 별개 경로였어요. 두 경로를 따로 전환해야 하므로 리스너 변경 작업도 두 배로 늘어나요.

경로 1개 가정 실제 (2개) 타깃그룹 2개 4개 리스너 전환 1회 2회 전환 원자성 보장 없음

두 리스너를 각각 호출하면 그 사이에 공인은 green, 내부는 blue를 가리키는 구간이 생길 수 있어요.

그림 2. 롤백할 때도 두 리스너를 각각 변경해야 해요

④는 리스너 변경으로 전환할 수 없었어요. 사설 IP로 직접 들어오는 요청은 로드밸런서를 거치지 않으므로, 가중치를 바꿔도 기존 목적지로 향해요.

⚠️ 직접 호출 경로도 함께 전환해야 해요
일부 경로만 새 버전으로 바뀌면 롤백할 때도 경로마다 다른 버전을 보게 돼요. 이번 구성에는 로드밸런서를 거치지 않는 직접 호출이 있었으므로, 리스너 가중치만으로 모든 경로를 전환할 수는 없었어요.

3. 호스트의 nginx에서 전환하기로 했어요

그림 1에서 확인한 네 경로는 모두 호스트의 같은 포트로 들어왔어요.

그 포트에 nginx를 두고 blue와 green을 서로 다른 포트로 띄우면, nginx의 목적지를 한 번 바꿔 네 경로를 함께 전환할 수 있어요.

공인 LB ─┐ NLB → 내부 LB ─┼─→ 호스트 :8080 = nginx ─┬─ blue → :8081 VPC 내부 LB ─┤ └─ green → :8082 사설 IP 직접 ─┘ ↑ 목적지 한 줄 + reload

이 구성에서는 다음 세 가지를 기대했어요.

AWS 리소스 변경 0건 (타깃그룹·리스너·권한 추가 없음) 전환 원자성 있음 (reload 한 번 — 어긋나는 구간이 없다) 적용 범위 전체 (LB 를 안 거치는 호출까지 포함)

위 블록의 전환 원자성은 여러 리스너를 순차 수정하는 대신 공통 프록시의 목적지 설정을 한 번에 바꾼다는 의미로 한정해야 해요. 기존 연결과 처리 중 요청까지 같은 순간 새 버전으로 바뀐다는 보장을 확인한 것은 아니에요. nginx는 새 worker를 시작하면서 기존 worker의 진행 중 요청을 마치게 하므로, 두 버전의 응답이 겹칠 수 있어요.

이 방식을 선택하면서 앞서 준비한 전용 역할은 사용하지 않게 됐어요. 공용 역할의 사용 범위는 배포 방식과 별개로 검토할 항목으로 남았어요.

4. 전환 전 검증을 배포 절차에 넣었어요

배포 절차에는 전환 전 검증을 넣었어요. 검증을 통과하면 nginx가 요청을 보낼 목적지를 변경하는 구성이에요.

그림 3. 상태 확인을 통과한 뒤 목적지를 바꾸는 배포 절차예요

③에서는 HTTP 200 응답이 연속 3회 나오는지 확인하도록 했어요. 한 번의 성공만으로 기동이 안정됐다고 판단하지 않기 위해서예요.

④에서는 기존 blue를 종료하지 않도록 했어요. 바로 되돌릴 대상을 남겨두려는 선택이었지만, 뒤에서 설명하는 자원 조건을 충분히 고려하지 못했어요.

당시에는 0.2초 간격으로 요청을 보내면서 전환을 확인했다고 남겼어요. 아래는 그때 본문에 실은 결과 발췌예요.

전환 중 폴링 총 244회 → 200 이 244회 nginx 접근 로그 blue 365회 → green 16회 ← 폴링과 실사용 트래픽을 합친 수. 주소가 실제로 갈렸다

발췌에는 목적지가 바뀐 로그도 있어요. HTTP 200이 계속 나온 것만으로는 전환 여부를 알 수 없으므로, 목적지 변경과 응답 상태를 함께 봐야 해요. 다만 이 발췌만으로 모든 요청의 무중단을 확인한 것은 아니에요.

5. 2초 롤백을 목표로 정한 조건

롤백 때 다시 배포하는 시간을 줄이려고 다음 세 가지를 설계했어요.

① 대기 컨테이너를 유지해요

초기 구성에서는 blue와 green을 모두 실행해 두고, 하나가 트래픽을 받는 동안 다른 하나는 롤백 대상으로 대기하도록 했어요.

그림 4. 대기 컨테이너를 유지하려면 두 배의 자원을 감당할 수 있어야 해요

다음 배포 때는 대기 중인 색에 새 버전을 배포하므로, 의도한 컨테이너 수는 3개나 4개로 늘지 않고 두 개를 유지해요. 두 개를 계속 실행할 자원이 충분한지는 별도로 확인해야 해요.

⚠️ 2026-08-17 정정: 닷새 뒤 49분 중단 기록과 자원 조건
초기 설명에는 컨테이너 두 개를 계속 실행할 자원이 충분한지 확인하는 조건이 빠져 있었어요.
당시 정정에는 이미지의 힙 설정이 -Xmx8192m으로 고정돼 있었다고 적었어요.
JVM 1개 × 8GB = 8GB → 여유 있음
JVM 2개 × 8GB = 16GB → 호스트 물리 메모리 15.6GB 초과
정정에는 전환 후 나흘 동안 힙이 늘어 메모리 사용률이 99%에 이르렀고, 월요일 아침 남은 메모리가 158MB였다고 남겼어요. 페이지 캐시 회수와 스래싱으로 호스트가 멎었다는 당시 조사 해석도 있었어요. 다만 힙 상한의 합이 물리 메모리보다 크다는 계산만으로 장애가 필연이었다고 단정할 수는 없고, 이번 확인에서는 당시 측정 원본과 장애 원인을 대조하지 못했어요.

배포 중에만 자원이 늘어나는 구성과 대기 컨테이너를 계속 실행하는 구성은 필요한 용량이 달라요. 두 개를 유지한다면 그만큼의 자원을 별도로 확보해야 해요.

후속 정정에는 배포 후 30~60분의 소킹 창, 즉 새 버전을 관찰하는 기간에만 두 개를 실행하고 이후 대기 색을 정지하도록 바꿨다고 적었어요. 그 창 안에서는 롤백 2초를 목표로 하고, 밖에서는 docker start와 기동에 약 60초가 든다는 설명이었어요. 컨테이너 메모리 상한을 추가했다는 내용도 있지만, 이 조치의 적용 상태와 소요 시간은 이번에 독립적으로 확인하지 못했어요.

또 롤백 대상 조회가 실패해도 대상이 없는 것으로 처리하는 결함이 뒤늦게 드러났다고 정정했어요. 당시에는 롤백을 한 번도 실행해 보지 않았으므로, 2초는 측정값이 아니라 설계값이었어요. 뒤의 시간 비교도 이 한계를 전제로 읽어야 해요.

② 버전을 SHA로 고정해요

이전 컨테이너가 남아 있어도 어떤 버전인지 모르면 되돌릴 대상을 정확히 정하기 어려워요.

:latest 로 띄우면 지금 뜬 게 어느 커밋인지 알 수 없다 → "직전 버전" 이 무엇인지도 알 수 없다 → 살려둔 컨테이너가 롤백 대상인지 확신할 수 없다 SHA 로 고정하면 두 색이 각각 어느 커밋인지 분명하다 → 롤백 대상이 남는다

배포할 때 :latest가 가리키는 실제 커밋 태그를 찾아 그 태그로 실행하도록 했어요. 당시 CI가 커밋 태그도 함께 푸시하는 구성을 이용한 거예요.

③ 되돌리기 전에도 확인해요

롤백 스크립트는 목적지를 바꾸기 전에 대상 컨테이너와 HTTP 200 응답을 확인하도록 설계했어요. 다만 조회 실패를 처리하는 결함이 뒤늦게 드러났고, 당시에는 이 절차를 실제 롤백으로 검증하지 않았어요.

확인 없이 전환하면 대기 중인 쪽에서도 응답을 받지 못할 수 있어요. 그래서 상태 확인을 롤백 절차에 포함했어요. 확인 시간까지 포함한 2초라는 설계값은 실행으로 다시 검증해야 해요.

6. 되돌릴 절차도 실행으로 확인해야 해요

기존 40초와 새 설계의 2초를 비교했지만, 두 값을 실측한 전후 비교로 볼 수는 없어요. 목표는 문제가 생겼을 때 재배포보다 짧은 절차로 되돌릴 수 있게 하는 것이었어요.

롤백이 40초짜리 재배포일 때 "조금 더 보자" → 그 몇 분이 장애 시간이 된다 롤백이 2초일 때 일단 되돌린다 → 그다음에 원인을 본다

배포 전에 확인할 것은 되돌릴 버전과 절차, 그리고 그 절차가 실제로 동작하는지였어요. 이를 검증해야 배포 후 문제가 생겼을 때 사용할 수 있어요.

이전 버전을 실행해 두는 것만으로 롤백 준비가 끝나지는 않아요. 버전을 식별할 수 있어야 하고, 상태 확인과 전환 절차도 실행해 봐야 해요.

⚠️ 최초 컷오버 1회는 검증 범위가 달랐어요
당시 기록에는 기존 컨테이너를 내리고 프록시를 올리는 최초 전환에 5.6초의 응답 공백이 있었고, 알람과 오류 응답은 각각 0건이었다고 남겼어요.
같은 기록에서는 그 5.6초에 요청이 없었다고 설명했어요. 따라서 요청 손실이 없음을 검증한 결과로 볼 수는 없어요. 244회 폴링은 이후 전환에서 확인한 범위이고, 최초 컷오버의 무중단을 입증하지는 않아요. 이번 확인에서는 해당 요청·알람 원본도 대조하지 못했어요.

7. 호스트 운영과 자동화는 별도 과제였어요

호스트에 프록시를 추가하는 방식은 배포 절차를 개선하기 위한 임시 구성이었어요. 호스트 운영과 배포 자동화까지 해결한 구성으로 볼 수는 없어요.

당시 설명에는 다른 두 곳에서 컨테이너 오케스트레이터로 자동 배포를 하고 있었고, 이 저장소는 이미지 푸시 이후 수동 작업이 남아 있었다고 적혀 있어요. 오케스트레이터로 옮기는 방안은 후속 선택지였으며, 이 작업으로 이전까지 끝냈다는 뜻은 아니에요.
