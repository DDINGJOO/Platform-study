📚 블루그린, 2부작
1편. 배포 중 healthy host 알람을 줄이고 블루그린을 선택한 이유 ← 지금 이 글

당시 작업 기록에는 오후에 P1 온콜 알람이 두 번 발생한 것으로 남아 있어요. 타깃그룹에서 요청을 받을 수 있다고 판정한 대상, 즉 healthy host가 없다는 알람이었어요.

15:29 타깃그룹에 healthy host 가 없음 16:18 같은 알람

기록에는 호스트에서 docker ps를 확인했을 때 앱 컨테이너가 33분 전에 생성된 상태였다고 적혀 있어요. 다만 조회 시각이 없어서 이 정보만으로 16:18 알람과 생성 시각이 일치한다고 단정할 수는 없어요.

당시에는 호스트에 접속해 컨테이너를 직접 교체하는 배포 과정에서 알람이 발생한 것으로 판단했어요. 배포 중 발생했다는 이유로 서비스 영향까지 없었다고 볼 수는 없어요.

배포 중 알람을 줄이려면 감지 조건과 배포 절차를 함께 살펴봐야 했어요. 아래 알람 시각과 기동 시간은 기존 작업 기록의 값이며, 이번 확인에서는 당시 실행 로그 원본까지 대조하지 못했어요.

1. 컨테이너 교체 중 healthy host가 없어지는 구간

기존 기록에 따르면 배포는 컨테이너를 내렸다가 새로 올리는 방식이었어요. 새 컨테이너가 요청을 받을 때까지 서비스 포트에 응답할 프로세스가 없는 구간이 생겨요.

처음에는 앱 부팅 시간을 의심했어요. 기존 기록의 기동 시간과 헬스체크 설정을 나란히 놓으면 다음과 같아요.

앱 기동 시간 32 ~ 38초 타깃그룹 헬스체크 Interval 30초 HealthyThreshold 5회 → healthy 복귀에 최소 150초 UnhealthyThreshold 2회 → 장애 판정 60초 알람 임계 120초

기록의 앱 기동 시간은 35초 안팎이에요. 150초는 헬스체크 간격 30초와 성공 기준 5회를 곱한 계산값이에요. 위 표의 “최소 150초”를 실제 복귀 시간의 하한으로 보거나, 앱 기동 뒤에 반드시 150초를 더 기다린다고 해석하기는 어려워요. 검사 시점과 타깃 상태를 포함한 실행 기록이 필요해요.

당시에는 healthy host가 0인 구간을 약 160초로 적었고, 알람 임계는 120초였어요. 이 조건이면 임계를 넘을 수 있지만, 이 수치만으로 모든 배포에서 알람이 발생한다고 단정할 수는 없어요.

💡 기동 시간과 healthy 복귀 시간을 구분해요
앱 기동을 35초에서 10초나 0초로 줄인다는 가정을 해도, healthy로 판정되는 시점은 별도로 확인해야 해요. 기동 시간과 헬스체크 대기 시간을 단순히 더해서 알람 발생 여부를 확정할 수는 없어요.

앱 최적화에 앞서 헬스체크 설정과 실제 상태 변화 시점을 함께 확인할 필요가 있었어요.
그림 1. 기동 시간 기록과 헬스체크 계산값을 비교한 그림이며, 실제 대기 시간을 합산한 결과는 아니에요

2. 감지 지연을 늘리기 전에 헬스체크를 검토했어요

먼저 알람 임계를 늘리거나 배포 중 알람을 억제하는 방법을 검토했어요.

임계를 2분에서 5분으로 늘리면 짧은 배포 중단으로 인한 알람은 줄일 수 있어요. 다만 실제 장애의 감지도 늦어지므로 이 방법을 우선하지 않았어요.

healthy host가 없는 상태의 지속 시간만으로는 계획된 배포와 그 밖의 장애를 구분하기 어려워요.

이 알람은 healthy host가 0인 상태가 얼마나 이어지는지 봐요. 배포 때문인지 인스턴스 문제 때문인지는 다른 정보로 확인해야 해요. 임계를 5분으로 늘리면 원인과 관계없이 같은 조건의 감지가 늦어져요.

파이프라인의 배포 상태를 이용해 그동안만 알람을 억제할 수도 있어요. 다만 배포 종료나 실패 때 억제를 확실하게 해제하는 절차가 필요해요. 당시 실제로 억제를 적용했는지는 이번 자료로 확인하지 못했어요.

기존 기록에는 헬스체크를 아래처럼 조정했다고 남아 있어요. 조회한 코드에서도 변경 후 설정을 확인했지만, 그 사실만으로 당시 적용 시점이나 개선 결과까지 확인한 것은 아니에요.

전 후 효과 Interval 30초 10초 HealthyThreshold 5회 2회 복귀 150초 → 20초 UnhealthyThreshold 2회 5회 장애 판정 60초 → 50초

Interval을 10초로 줄이고 실패 기준을 2회로 유지하면 단순 계산은 20초예요. 그래서 실패 기준은 5회로 높였어요. 이때 계산값은 기존 60초에서 50초가 되므로, 기존보다 장애 판정이 늦어졌다는 뜻은 아니에요. 타깃이 한 대라는 조건도 고려했지만, unhealthy 판정만으로 요청이 100% 중단됐다고 단정할 수는 없어요.

그림 2. 기존 기록의 변경 전후 비교이며, 약 40초와 알람 해소 결과는 이번 확인에서 재검증하지 못했어요

3. 헬스체크 조정만으로 해결되지 않는 배포 절차

헬스체크 조정으로 알람이 줄어들더라도 배포 절차에는 별도의 확인이 필요했어요.

당시 작업 기록에는 배포 절차의 제약이 다음과 같이 정리돼 있어요.

새 버전이 정상인지 확인하는 단계 없음 문제가 있을 때 되돌리는 절차 옛 이미지를 다시 받아 띄우기 (40초+) 어떤 버전이 떠 있는지 기록 :latest 라 알 수 없음

이 절차에서는 새 버전이 정상인지 확인한 뒤 트래픽을 전환하는 단계가 없었어요. 헬스체크 설정을 조정해도 버전 검증과 복구 절차는 따로 마련해야 해요.

확인할 범위는 알람 발생 여부뿐 아니라 새 버전 검증과 이전 버전으로의 복구까지였어요.

그래서 기존 컨테이너를 먼저 내리지 않고 새 버전을 준비하는 무중단 배포 방식을 검토했어요.

4. 서버 한 대에서 적용할 배포 방식을 비교했어요

롤링, 카나리, 블루그린을 비교했어요. 아래 그림은 각 방식의 일반적인 가능성 전체가 아니라 당시 환경에서 검토한 구성을 나타내요.

그림 3. 당시 환경에 적용할 구성과 롤백 절차를 함께 비교했어요

롤링은 실행 중인 대상을 차례로 교체하는 방식이에요. 당시 검토한 구성은 서버를 한 대씩 제외하는 형태였는데, 인스턴스 한 대에서 컨테이너 하나만 실행하던 구조에는 그대로 적용하기 어려웠어요. 롤링 배포 자체가 언제나 서버 두 대를 요구한다는 뜻은 아니에요.

카나리는 새 버전에 일부 트래픽을 보내고 지표를 보며 비율을 늘려요. 이를 적용하려면 트래픽 분배와 진행 여부를 판단할 지표를 준비해야 해서 당시 우선순위에서는 제외했어요.

블루그린은 새 버전을 별도로 띄우고 확인한 뒤 트래픽을 전환해요. 서버 한 대에서 다른 포트로 두 버전을 실행하는 구성을 선택했어요. 포트만 추가하면 되는 것은 아니고 두 버전을 동시에 실행할 자원 여유도 필요해요.

5. 이전 버전을 유지해 롤백 절차를 줄이려 했어요

선택할 때 중요하게 본 것은 문제가 생겼을 때 되돌리는 절차였어요.

이전 버전을 전환 후에도 일정 기간 유지하면 이미지를 다시 받아 기동하지 않고 트래픽을 되돌릴 수 있어요. 이전 버전 유지가 블루그린이라는 이름만으로 보장되는 것은 아니므로, 유지와 정리 시점도 절차에 포함해야 해요.

옛 버전을 지우는 방식의 롤백 옛 이미지 pull → 컨테이너 기동 → 부팅 32초 40초 + 옛 버전이 살아 있는 방식의 롤백 목적지를 되돌린다 2초

기존 기록은 재기동이 필요한 복구를 40초 이상, 트래픽 전환을 2초로 비교했어요. 이번 확인에서는 해당 측정 로그를 대조하지 못했으므로 보장되는 복구 시간으로 해석하지는 않아요. 여기서 줄이려던 것은 롤백 때 이미지를 다시 받고 앱이 기동하기를 기다리는 절차예요.

새 버전의 정상 동작을 확인하는 절차와 함께, 이전 버전으로 신속하게 돌아갈 수 있는 구성을 선택 기준으로 삼았어요.

이 기준에 따라 블루그린을 선택하고 로드밸런서 가중치로 트래픽을 전환하는 안을 검토했어요. 여기서는 선택 이유까지만 다루며, 실제 전환 시간과 배포 성공 여부를 이 비교만으로 확정하지는 않아요.

✍️ 검토 결과와 확인 범위
배포 중 healthy host가 없어지는 알람을 계기로 기동 시간, 헬스체크 설정, 버전 검증 절차를 함께 살펴봤어요. 새 버전을 먼저 확인하고 이전 버전을 유지해 트래픽을 되돌릴 수 있는 블루그린 구성을 선택했어요.

조회한 코드에서 변경 후 헬스체크 설정은 확인했어요. 다만 당시 알람 시각과 기동·복구 시간의 원본 로그는 확인하지 못했으므로, 기존 기록의 수치를 모든 배포의 결과나 보장 시간으로 해석하지 않아요.
