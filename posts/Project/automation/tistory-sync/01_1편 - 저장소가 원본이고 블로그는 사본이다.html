2편. 성공처럼 보이는 실패 열 개

8월 초, 티스토리 HTML 모드에 글 두 편을 연달아 붙여넣었는데 다이어그램이 사라졌어요. SVG 만 통째로 빠지고, 그림 안에 있던 <text> 라벨들이 본문에 맨 글자로 쏟아져 있었습니다. 로컬 브라우저에서 열면 멀쩡한 파일이었어요.

이미 정상 발행된 글들과 파일을 기계적으로 대조하면서 가설을 세 개 세웠습니다. 낯선 유니코드 문자, SVG 안의 HTML 주석, 파일 크기였어요. 셋 다 반증됐고 원인은 끝내 못 찾았습니다. 그래서 SVG 를 PNG 로 뽑은 "이미지판"을 따로 만들어 blog/ 폴더에 쌓기 시작했어요. 원본 한 벌에 사본이 한 벌 더 붙은 셈입니다. SVG 문제가 풀리지 않자 그 뒤로 발행도 멈췄어요. 저장소에는 글이 91편 있었는데, 블로그에 이미 올라간 글은 처음 세어 보니 20편이었습니다.

이 시리즈는 그 손 붙여넣기를 걷어낸 기록이에요. 1편에서는 무엇을 왜 만들었는지를 적습니다. 질문은 하나예요. "저장소를 원본으로 두고 블로그를 그 사본으로 맞추는 기계는 무엇을 지켜야 하는가."

이 글에서 다룰 것
· 8월에 SVG 를 지운 것은 파일이었을까, 붙여넣기였을까?
· 공개 저장소에서 감춰야 할 이름이 새지 않게 하려면 검사를 어디에 둬야 할까?
· 업로더를 두 번 돌려도 같은 글이 두 번 올라가지 않게 하려면 무엇을 기억해야 할까?
· 발행일을 되돌릴 수 없는 블로그에서 글 순서는 어떻게 정할까?
· 손으로 올려 둔 옛 글은 저장소 파일과 무엇으로 짝지어야 할까?

1. 붙여넣기를 걷어내니 SVG 가 멀쩡했다

먼저 올리는 방법부터 정해야 했어요. 티스토리 오픈 API 는 2024년 2월에 글쓰기가 닫혔습니다. 남은 길은 사람이 하던 일을 브라우저가 대신 하게 하는 것뿐이라, Playwright 로 시스템 Chrome 을 띄워 글쓰기 화면의 에디터를 직접 조작하기로 했어요.

📖 용어: Playwright
코드로 브라우저를 띄우고 조작하는 라이브러리예요. 클릭, 키보드 입력, 페이지 안의 요소 세기를 사람 대신 스크립트가 합니다. 글쓰기 API 가 없는 서비스에 사람과 같은 경로로 글을 넣을 때 쓸 수 있어요. 여기서는 따로 받는 브라우저 대신 Mac 에 설치된 Chrome 을 띄웁니다.

첫 검증은 일부러 가장 작은 글로 했습니다. 9.8KB 에 SVG 가 1개뿐인 글을 비공개로 저장하고, 렌더된 글 페이지에서 요소를 세어 봤어요. SVG 1개, <text> 10개, 도형 6개, 그리고 <style> 블록까지 전부 남아 있었습니다. 손글씨 폰트도 그대로 나왔고요.

이 결과가 8월의 문제를 설명해 줍니다. 파일은 한 글자도 바꾸지 않았는데, 넣는 방법을 바꾸자 SVG 가 살아 있었어요. 한 편 시험으로 끝나지 않고, 나중에 올린 87편도 전부 저장 뒤 SVG 개수 검증을 통과했습니다. SVG 가 사라진 원인은 파일이 아니라 파일이 티스토리에 들어가던 붙여넣기 경로였습니다. 파일만 뜯어보며 세운 가설 세 개가 전부 틀린 이유도 이것으로 설명돼요. 애초에 파일 안에 원인이 없었으니까요. 붙여넣기 경로의 어느 단계에서 SVG 가 지워졌는지는 확인하지 않았습니다. 그 경로를 더 쓰지 않게 되면서 확인할 이유도 사라졌어요.

그래서 PNG 이미지판을 지웠습니다. HTML 91편과 PNG 203장이었어요. 업로더는 인라인 SVG 를 원본 그대로 올리므로 사본을 두 벌 유지할 필요가 없어졌습니다.

2. 공개 저장소에서는 push 가 곧 공개다

업로더보다 먼저 만든 것이 있어요. 이 저장소는 공개 저장소라서, 글이 블로그에 올라가기 전에 GitHub 에 push 하는 순간 이미 누구나 볼 수 있습니다. 마스킹 검사를 업로드 직전에 두면 그 검사는 이미 공개된 뒤에 도는 셈이에요. 그래서 검사는 업로드 직전이 아니라 커밋 직전에 있어야 했습니다.

기존 검사기 mask-check.py 를 pre-commit 훅으로 붙이기로 했어요.

📖 용어: pre-commit 훅
git commit 을 실행하면 커밋이 만들어지기 직전에 git 이 자동으로 돌려 주는 스크립트예요. 스크립트가 실패로 끝나면 커밋이 만들어지지 않아요. 그래서 여기에 검사를 두면 걸린 내용은 push 는커녕 커밋까지도 가지 못합니다.

그런데 기존 검사기는 훅에 붙이기에는 세 가지가 모자랐어요. 첫째, 경로를 보지 않았습니다. 예전에 한 번 뚫린 적이 있는데, 그때 노출된 곳이 본문이 아니라 조직을 가리키는 약어가 들어간 폴더 이름이었어요. 둘째, 디스크의 파일을 읽었습니다. 실제로 커밋되는 것은 스테이징된 blob 인데도요. 셋째, 허용 목록이 없어서 오탐(문제없는 값을 문제로 잘못 판정하는 것) 하나가 그 파일의 커밋을 영구히 막을 수 있었습니다.

📖 용어: 스테이징과 blob
git add 로 "다음 커밋에 넣겠다"고 올려 둔 상태가 스테이징이에요. git 은 그 순간의 파일 내용을 blob 이라는 객체로 따로 저장해 둡니다. 그래서 add 한 뒤에 파일을 더 고치면 디스크의 내용과 커밋될 내용이 달라져요. 커밋 전에 검사할 것은 디스크가 아니라 이 blob 입니다.

그래서 스테이징된 내용과 경로를 함께 보는 --staged, 추적 중인 전 파일을 보는 --all, 오탐을 통과시키는 .mask-allow 를 더했어요. 허용 목록은 일반 패턴의 오탐에만 적용하고, 조직 목록(감출 회사·조직 이름을 저장소 밖 파일에 적어 둔 목록)에 걸린 값은 언제나 막습니다. 훅은 조직 목록 파일이 없으면 검사하지 않고 통과시키는 대신 커밋을 막아요.

# .githooks/pre-commit (요지) EXTRA="${BLOG_MASK_FILE:-$HOME/.config/blog-mask.txt}" if [ ! -f "$EXTRA" ]; then echo "조직 목록이 없어 마스킹 검사를 할 수 없다. 커밋을 막는다." >&2 exit 1 # 목록 없는 검사는 회사명을 못 잡는다 fi exec python3 .claude/skills/blog-post-pipeline/assets/mask-check.py \ --staged --extra "$EXTRA"

→ 조직 목록 파일이 없으면 검사 없이 통과시키지 않고 커밋을 막고, 있으면 스테이징된 내용과 경로로 검사기를 돌린다는 뜻이에요. 이 훅은 core.hooksPath 를 .githooks 로 설정한 저장소에서만 돕니다.

붙이고 나서 두 가지를 확인했어요. 추적 중인 파일 전부를 검사한 결과 노출은 0건, 오탐은 2건(알람 임계값 50MiB, 날짜)이었고, 둘은 판정 이유와 함께 허용 목록에 적었습니다. 그리고 시험 삼아 본문에 12자리 숫자(AWS 계정 ID 모양)를 넣은 커밋과 폴더 이름에만 조직 목록 값이 있는 커밋을 만들어, 둘 다 막히는 것을 봤어요.

이 검사는 나중에 저를 한 번 막았습니다. 매니페스트(3절에서 다룰, 파일마다 블로그 글 번호를 적어 둔 파일)에 적힌 SHA-256 해시 안에 우연히 12자리 연속 숫자가 나왔고, 검사기가 그것을 AWS 계정 ID(12자리 숫자)로 판정했어요.

📖 용어: 해시 (SHA-256)
파일 내용을 넣으면 긴 16진수 문자열 하나가 나오는 함수예요. 내용이 한 글자만 달라도 결과가 완전히 달라지므로, 업로더는 이 값만 비교해서 파일이 바뀌었는지 판단합니다. 16진수는 0~9 와 a~f 로 이루어져 있어서, 숫자만 길게 이어지는 구간이 우연히 생길 수 있어요.

해시는 글이 바뀔 때마다 바뀌니 허용 목록으로는 해결할 수 없습니다. 그래서 규칙을 고쳤어요. 앞뒤가 영숫자이면 더 긴 토큰의 일부로 보고, ARN(계정 ID 가 콜론 사이에 들어가는 AWS 자원의 전체 이름)처럼 콜론으로 둘러싸인 계정 ID 는 계속 잡습니다.

💡 실무에서는: 훅만 믿지 않고 CI 에서 한 번 더
훅은 각자의 컴퓨터에서만 돌아요. 저장소를 새로 받으면 훅은 켜져 있지 않아요. core.hooksPath 를 설정해야 돌고, git commit --no-verify 로 건너뛸 수도 있습니다. 그래서 같은 검사를 CI 에서도 --all 로 한 번 더 돌려요. 다만 CI 는 push 뒤에 돌기 때문에 이미 저장소에 올라간 내용이 공개되는 것은 막지 못해요. 막을 수 있는 것은 그 내용이 블로그로 퍼지는 것까지입니다.

3. 기억하는 곳이 없으면, 다시 돌릴 때 같은 글이 또 올라간다

업로더를 두 번 돌린다고 해 볼게요. 첫 실행에서 무엇을 올렸는지 기억하지 못하면, 두 번째 실행은 같은 파일을 또 새 글로 만듭니다. 반대로 파일을 고쳤다면 새 글이 아니라 원래 글을 고쳐야 하는데, 그러려면 그 파일이 블로그의 몇 번 글인지 알아야 해요. 어떤 파일이 어떤 글인지 적어 두는 곳이 필요했습니다. 그게 매니페스트예요.

📖 용어: 매니페스트 (manifest)
어떤 파일이 블로그의 몇 번 글인지, 마지막으로 올렸을 때 내용이 어땠는지(해시)를 적어 둔 대장이에요. 업로더는 이걸 보고 새 글을 만들지, 기존 글을 고칠지, 그냥 둘지 정합니다.

업로더의 상태는 저장소 안의 파일 두 개가 전부예요. tistory-series.json 에는 시리즈 폴더별 제목 접두어가 있고, tistory-manifest.json 에는 파일 경로마다 블로그 글 번호가 적혀 있습니다. 한 항목은 이렇게 생겼어요.

"posts/AWS/SDLC/sdlc/01_SDLC 다섯 단계와 CodePipeline.html": { "id": "458", "title": "소프트웨어 개발 생명주기 1편 - SDLC 다섯 단계와 CodePipeline", "category": "AWS/SDLC", "visibility": "public", "sha256": "30cc9e45...", "synced_at": "2026-09-28T15:01:29+00:00" }

→ 이 경로의 파일은 블로그의 458번 글이고, 마지막으로 올렸을 때의 제목·카테고리·공개 범위·내용 해시가 이랬다는 기록이에요.

실행할 때마다 업로더는 파일마다 해시, 제목, 카테고리를 계산해서 이 항목과 비교합니다. 매니페스트에 없으면 새 글이고, 있는데 셋 중 하나라도 다르면 같은 번호의 글을 고쳐요. 파일 이름을 바꿔 경로가 달라져도, 사라진 옛 경로 중에 해시가 같은 항목이 있으면 그 번호를 이어받습니다.

그림 1. 글 번호는 경로에 묶여 있고, 해시가 달라지면 같은 번호에서 고친다

그런데 매니페스트만으로는 막을 수 없는 틈이 있었어요. 저장 직후에는 관리 목록에 새 글이 늦게 나타나서, 업로더가 "글 번호를 못 찾았다"며 멈춘 적이 있었습니다. 글은 이미 저장돼 있었는데 매니페스트에는 번호가 없는 상태였어요. 이대로 다시 돌리면 매니페스트에 없는 파일이니 같은 글을 또 만들게 됩니다.

그래서 장치 두 개를 두었어요. 하나는 저장 직후의 번호 찾기입니다. 저장 뒤 넘어간 주소에서 글 번호를 먼저 읽고, 못 읽으면 관리 목록을 3초 간격으로 최대 5번 찾아요. 다른 하나는 새 글을 만들기 전의 이어받기(adopt)예요. 블로그 관리 목록에서 같은 제목의 글을 먼저 찾고, 있으면 새로 만들지 않고 그 글을 고칩니다. 이 검색은 처음에 한 번뿐이었는데, 목록 반영이 늦으면 한 번으로는 놓칠 수 있어 세 번으로 늘렸어요. 이어받기 덕분에 이런 상태에서 다시 실행해도 대개 중복이 생기지 않지만, 목록에 새 글이 아직 뜨지 않은 짧은 순간에는 여전히 놓칠 수 있어요. 재실행이 안전해야 도중에 멈춰도 부담 없이 다시 돌릴 수 있습니다.

그리고 저장 버튼이 성공을 알려 줘도 믿지 않기로 했어요. 한 편을 저장할 때마다 글 페이지를 열어 세 가지를 확인합니다. SVG 개수가 원본과 같은지, 본문 글자 수가 원본의 90% 이상인지, 공개 범위가 목표와 같은지예요. 검증에 실패해도 글은 이미 존재하므로 번호는 기록하고, 해시를 빈 값으로 둡니다. 그러면 다음 실행에서 "내용이 다르다"로 판정돼 그 글을 다시 써요. 그림 1의 "해시가 null" 칸과는 다른 경우예요. null 은 손으로 올린 글과 짝지어 두기만 한 항목이라는 표시입니다(6절).

⚠️ 주의: "저장 성공"을 믿으면 안 돼요 (자세한 건 2편에서)
이 검증 단계는 처음부터 있던 것이 아니에요. 저장은 성공했는데 본문이 비어 있던 일, 비공개여야 할 글이 공개로 저장된 일처럼 겉으로는 성공이었던 실패를 차례로 겪으면서 하나씩 늘었습니다. 새 글이 예전 임시저장본에 덮일 뻔한 일도 있었는데, 그건 저장 전에 입력값 비교에서 오류로 잡혔어요. 로그인 세션, 하루 새 글 제한, 러너의 잠자기까지 포함해 그 목록은 2편에서 하나씩 다룹니다.

4. 발행일을 되돌릴 수 없어서, 순서와 카테고리는 저장소가 정한다

블로그 목록의 순서도 정해야 했어요. 티스토리는 발행일을 과거로 돌릴 수 없습니다. 고를 수 있는 것은 "현재"와 "예약"뿐이에요. 그러면 목록 순서는 글을 만드는 순서로만 정해집니다. 그래서 새 글은 git 에 처음 커밋된 날짜 순으로 만들고, 같은 시리즈 안에서는 파일 번호를 날짜보다 우선하게 했어요. 여러 편을 한 커밋에 넣었거나 번호와 다른 순서로 커밋한 시리즈가 있었기 때문입니다.

그런데 이 순서는 로컬에서 돌릴 때만 맞았어요. CI 의 checkout 은 기본이 얕은 클론(최근 커밋 하나만 받는 것)이라, 모든 파일의 최초 커밋일이 같은 날짜로 보여 이 정렬이 동작하지 않았습니다. 이 글을 퇴고하다 알게 됐고, fetch-depth: 0 한 줄로 전체 이력을 받게 고쳤어요. 지금까지 새 글은 대부분 로컬 실행으로 만들어서 순서는 맞습니다.

⚠️ 주의: 공개로 바꿀 때 "현재"를 누르지 않는다
나중에 비공개 글을 공개로 바꿀 때 "현재"를 누르지 않으면 저장된 날짜가 유지되므로 이 순서가 그대로 남아요. 누르면 발행일이 전환한 순간으로 바뀌어, 커밋일로 맞춰 둔 순서가 흐트러집니다.

카테고리는 폴더 경로에서 읽게 했습니다. 글 원본을 posts/<블로그 카테고리>/<시리즈>/ 구조로 옮기고, 시리즈 폴더의 부모 경로를 카테고리로 봐요. 예를 들어 posts/Work/IaC/iac-log/ 의 글은 Work/IaC 카테고리로 올라갑니다. posts/_archive/ 아래는 올리지 않아요. 원래 시리즈 설정 파일에도 카테고리 항목이 있었는데 지웠습니다. 같은 정보를 두 곳에 적으면 언젠가 둘이 어긋나기 때문이에요.

폴더를 옮길 때 매니페스트 키는 같은 규칙으로 직접 바꿨어요. 업로더의 이름 변경 감지에 맡기면 85편을 한 번씩 다시 저장하게 됩니다. rename 으로 판정된 글은 옛 번호를 이어받으면서 글을 한 번 다시 저장하기 때문이에요. 옮긴 뒤 plan(올리지는 않고 할 일만 계산해 보여 주는 명령)을 돌려 보니 할 일은 아직 올라가지 않은 새 글 2편뿐이었고, 경로에서 계산한 카테고리는 85편 모두 블로그와 일치했어요.

이 무렵 블로그 카테고리 이름 하나에 회사명이 들어가 있던 것도 발견해서 손으로 바꿨습니다. 마스킹 검사는 저장소 안의 파일과 경로만 보기 때문에, 블로그 설정에 직접 적은 이름은 검사 대상이 아니었어요.

5. 러너는 이 Mac 이고, 트리거는 셋뿐이다

업로드를 자동으로 돌리려면 티스토리에 로그인된 브라우저가 필요해요. 그런데 GitHub 이 빌려주는 러너는 실행할 때마다 새로 만든 깨끗한 가상 머신이라 로그인한 흔적이 없습니다. 티스토리 로그인 세션(로그인했다는 표시로 브라우저가 들고 있는 쿠키)은 저장소 밖, 이 Mac 에만 있어요. 그래서 업로드는 GitHub Actions 로 돌리되, 이 Mac 에 등록한 self-hosted 러너에서 돌립니다.

📖 용어: self-hosted 러너
GitHub Actions 의 작업을 실제로 실행하는 컴퓨터를 러너라고 해요. 보통은 GitHub 이 빌려주는 러너를 쓰지만, 내 컴퓨터에 러너 프로그램을 설치해 등록하면 작업이 그 컴퓨터에서 돕니다. 여기서는 이 Mac 이 러너이고, launchd(macOS 가 프로그램을 띄우고 관리해 주는 시스템 서비스)의 서비스로 떠 있어요.

그런데 공개 저장소에 self-hosted 러너를 붙이면 조심할 것이 생겨요. 누구나 포크(남의 저장소를 자기 계정으로 복사하는 것)해서 PR 을 올릴 수 있는데, PR 이벤트로 워크플로가 돌면 남이 쓴 코드가 제 노트북에서 실행될 수 있습니다. 그래서 트리거를 셋으로만 열었어요. main 에 push 가 들어갈 때, 사람이 수동으로 실행할 때, 그리고 매일 00:10 KST 정기 실행입니다. pull_request 는 넣지 않았어요.

on: push: branches: [main] paths: ["posts/**", "tistory-series.json"] workflow_dispatch: schedule: - cron: "10 15 * * *" # UTC 15:10 = 00:10 KST concurrency: group: tistory-sync cancel-in-progress: false # 올리는 도중에 끊으면 매니페스트에 안 적힌 글이 생긴다

→ posts/ 나 시리즈 설정이 바뀐 main push, 수동 실행, 매일 한 번의 정기 실행에만 잡이 돌고, 이미 도는 잡이 있으면 새 실행은 그것을 끊지 않고 기다린다는 뜻이에요. 기다리는 실행은 하나만 남고 그 전에 대기하던 것은 취소되지만, sync 는 다시 돌려도 안전해서 영향이 적어요.

잡은 전수 마스킹 검사, plan, sync(plan 이 계산한 일을 실제로 블로그에 저장하는 명령), 매니페스트 커밋 순서로 돌아요. 저장 뒤 검증은 sync 안에서 글마다 합니다. sync 는 caffeinate -is 로 감싸 도는 동안 노트북이 잠들지 않게 했어요. 매니페스트 커밋은 앞 단계가 실패해도 반드시 돕니다. 이미 올린 글의 번호를 남겨 둬야 다음 실행이 같은 글을 또 만들지 않기 때문이에요. 실패한 실행도 무엇을 올렸는지는 남겨야 합니다. 그 뒤에 sync 의 종료 코드를 잡의 결과로 돌려주는 단계가 하나 더 있습니다.

그림 2. 검사는 push 앞에, 기록은 실패 뒤에도 남는다

정기 실행을 둔 이유는 티스토리의 하루 새 글 제한이에요. 하루에 새 글 50편을 넘기면 저장이 거부되는데, 업로더는 그 거부 응답을 읽어 종료 코드 4 로 멈추고 워크플로는 경고로 끝냅니다. 제한은 자정에 풀리므로 00:10 에 돌면서 남은 글을 이어서 올려요. 실제로 인프라 절감 21·22편이 이렇게 다음 날 올라갔습니다. 다만 한 번에 끝나지는 않았어요. 정기 실행은 00:10 으로 설정했지만 GitHub 이 늦게 띄워 실제로는 05:08 에 시작했고, 21편과 22편 사이인 05:09~05:25 에 Mac 이 잠들었습니다. 22편까지 저장하고 검증한 뒤 잡이 취소됐고, 매니페스트도 push 되지 않았어요. 바로 다음 수동 실행은 로그인 만료로 실패했습니다. 제가 다시 로그인하고 아래의 keepalive 를 붙인 뒤 수동으로 다시 돌리자, 그제야 두 글을 이어받아 검증하고 매니페스트 커밋까지 러너가 혼자 push 했어요. 끊긴 원인과 고친 방법은 2편에 적었습니다.

로그인 세션이 30~40분 쓰지 않으면 끊기는 문제도 있어서, launchd 가 15분마다 쿠키만으로 관리 페이지를 한 번 열어 세션을 살려 두게 했습니다. 이것이 실제 만료를 막아 주는지는 아직 지켜보는 중이에요.

6. 제목으로 짝을 지으면 놓친다

마지막 문제는 이미 손으로 올려 둔 글들이었어요. 이 글들을 새로 올리면 같은 글이 블로그에 두 벌 생깁니다. 그래서 먼저 기존 글과 저장소 파일을 짝지어 매니페스트에 번호를 넣어야 했어요. 처음에는 제목으로 짝을 지었고, 그 결과가 도입부의 20편입니다.

그런데 8편을 놓쳤어요. 부제 없이 올렸던 글, 그리고 올린 뒤 저장소에서 번호나 부제가 바뀐 글이었습니다. 짝을 못 찾은 파일은 새 글로 판정됐고, 이미 블로그에 있는 글이 비공개로 한 벌 더 생겼어요. 제목은 사람이 언제든 고치는 값이라서 짝을 찾는 기준으로 쓸 수 없었습니다.

그래서 기준을 제목에서 본문으로 바꿨어요. 짝이 안 된 블로그 글의 본문을 전부 읽어 와 저장소 파일과 본문 유사도(두 본문 텍스트를 비교해 0~1 로 낸 값, 1이면 같은 글)를 계산했고, 놓친 8편이 0.84~0.99 사이의 유사도로 짝을 찾았습니다. 최종적으로 기존 공개 글은 20편이 아니라 28편이었어요. 놓친 8편 때문에 생겼던 중복 비공개 글은 지우거나, 그 번호를 아직 만들 차례가 오지 않은 새 글에 넘겨서 없앴습니다. 번호를 넘긴 이유는 발행 순서를 맞추기 위해서예요(4절). 이 재배정 과정에도 함정이 하나 있었는데, 그것도 2편에서 다룹니다.

짝지은 글은 매니페스트에 해시를 null 로 두고, 업로더가 기본으로는 건드리지 않아요. --update-linked 를 줄 때만 저장소 본문으로 덮습니다. 기존 28편은 이 옵션으로, 지우고 다시 올리지 않고 같은 번호에서 저장소 본문으로 고쳤어요. 그래서 글 주소와 댓글이 그대로 남았습니다. 옛 제목 중에는 비공개 저장소 이름이 남아 있던 것이 있었는데, 저장소의 제목으로 덮이면서 그것도 함께 사라졌어요.

저장소 91편 - 발행하지 않는 폴더 4편 = 87편 기존 글, 같은 번호에서 수정 28편 (제목 짝 20 + 본문 유사도 8) 새 글, 비공개로 저장 59편 (공개 전환은 사람이 한다) 세션 중 몇 번 멈추고 다시 돌린 뒤 최종 중복 글 0편

→ 올릴 87편 중 28편은 원래 번호에서 고치고 59편은 새로 만들었으며, 여러 번 끊기고 다시 돌았는데도 같은 글이 두 벌 생긴 경우는 남지 않았다는 뜻이에요.

새 글 59편은 모두 비공개로 두었어요. 올리는 일은 기계가 하지만, 공개로 바꾸는 버튼은 제가 누릅니다. 올라간 글을 한 번 읽고 공개할지 판단하는 일까지 기계에 맡길 이유는 없었어요. 그런데 퇴고하다 보니 업로더가 매니페스트에 적힌 공개 범위를 목표값으로 써서, 사람이 공개로 바꾼 글을 다음 수정 때 비공개로 되돌리는 버그가 있었어요. 지금은 기존 글이면 블로그의 현재 공개 범위를 읽어 그대로 지킵니다. 자세한 건 2편에서 다룹니다.

✍️ 오늘의 요약
8월부터 SVG 를 지운 것은 파일이 아니라 붙여넣기 경로였고, 경로를 기계로 바꾸자 원본이 그대로 렌더됐다. 그 뒤에 남은 일은 사본을 원본에 맞추는 규칙을 저장소 안에 적는 것이었다. 커밋 전 마스킹 검사, 경로마다 글 번호와 해시를 적은 매니페스트, 저장 후 검증, 커밋일 순서, 폴더 경로 카테고리가 그 규칙이다.

기존 글과 짝을 지을 때 제목을 믿었다가 8편을 놓쳤고, 본문으로 다시 찾았다. 사본을 원본에 맞추려면, 사람이 바꾸는 값이 아니라 바뀌지 않는 값으로 둘을 이어야 한다.
