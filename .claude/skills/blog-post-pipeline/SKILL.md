# Blog Post Pipeline — 작성부터 퇴고 통과까지

블로그 글을 사람이 두 번 시키지 않아도 되도록, **작성 → 패널 퇴고 → 수정 → 재검**을 한 번의 흐름으로 처리하는 스킬.
탄생 배경: 혼자 쓴 초안에는 반드시 구멍이 생긴다 — 독자가 모르는 사내 용어("역머지")가 설명 없이 튀어나오고,
다이어그램 캡션이 본문 뒷장과 모순되고, 할 일을 "했습니다"로 쓰는 시제 붕괴가 섞인다.
쓴 사람 눈에는 절대 안 보이므로, 퇴고는 쓴 사람이 아닌 패널이 한다.

## 파이프라인

```
0. 목록 확정  쓸 글 전체를 먼저 정한다. 제목·파일명·시리즈 번호까지 (아래 "왜 먼저" 참고)
1. 작성      글마다 서브에이전트 하나. 전부 동시에 띄운다
2. 퇴고      글마다 4인 패널 검수. 이것도 전부 동시에
3. 수정      지적을 반영. 반영 못 하는 지적은 사유와 함께 사용자에게 보고
4. 재검      수정된 부분만 다시 검수. 지적 0건이면 통과
5. 반복      통과할 때까지 2~4를 반복. 최대 3라운드 — 남는 지적은 사용자 판단으로 넘김
6. 마무리    태그 짝 검증 → 통과하면 커밋 여부를 사용자에게 확인
```

각 라운드가 끝나면 "라운드 N: 지적 M건 → 반영 K건" 한 줄을 사용자에게 보여준다.
지적과 수정을 조용히 처리하고 결과만 내밀지 않는다 — 무엇이 걸렸고 어떻게 고쳤는지가 사용자의 학습 재료다.

## 병렬이 기본이다 (한 편만 쓸 때도 구조는 같다)

**글이 두 편 이상이면 순차로 쓰지 않는다.** 한 편에 서브에이전트 하나를 붙여 한 번에 전부 띄운다.
글은 서로 독립적이고 각자 파일이 다르므로 병렬화 이득이 그대로 나온다.
퇴고도 마찬가지 — 글 N편이면 퇴고 에이전트도 N개를 동시에 띄운다.

Agent 호출을 **한 메시지에 여러 개** 넣어야 실제로 동시에 돈다. 하나씩 띄우고 기다리면 병렬이 아니다.

### 왜 목록을 먼저 확정하는가 (병렬화의 유일한 함정)

글들끼리 서로를 참조하는 부분이 있다 — **시리즈 박스, "N편", 다른 편으로 가는 링크.**
목록을 확정하지 않고 병렬로 띄우면 각 에이전트가 자기가 몇 편인지 모르고, 시리즈 박스가
글마다 다르게 나오거나 존재하지 않는 편을 가리킨다. 나중에 손으로 맞추는 비용이 병렬 이득을 잡아먹는다.

그래서 0단계에서 **전체 목록(번호 · 제목 · 파일명)을 표로 확정하고, 그 표를 모든 에이전트 브리핑에 똑같이 넣는다.**
각 에이전트는 "너는 이 표의 N번이다"만 알면 시리즈 박스를 스스로 정확히 만든다.

### 공통 브리핑 (모든 작성 에이전트에 동일하게 넣을 것)

병렬 에이전트는 서로의 맥락을 못 본다. 각자에게 다음을 빠짐없이 전달한다:

- 읽을 파일 경로 — `tistory-sketch-post` 의 SKILL.md, `references/svg-sketch-guide.md`, `assets/template.html`
- **스타일 기준이 될 기존 글 1편의 경로** (톤·구조를 맞추는 앵커. 없으면 편마다 톤이 갈린다)
- 0단계에서 확정한 전체 목록 표 + "너는 N번"
- 내용 브리핑 (그 편이 담을 것. 사실관계 근거가 될 코드/문서 경로까지)
- 출력 경로 (파일명은 0단계 표 그대로)
- 검증 요구 — 태그 짝 스크립트를 **실제로 돌려서** 통과 확인하고 결과를 보고할 것
- 알려진 함정: 한글 파일명은 macOS 유니코드 정규화 때문에 Read 도구가 실패할 수 있다 (Bash/python 으로 우회)

### 파일 충돌 방지

**한 파일에 에이전트 하나.** 두 에이전트가 같은 파일을 만지면 나중 쓰기가 앞 쓰기를 덮는다.
공통 자산(스킬 파일, 인덱스 문서)은 에이전트가 건드리지 않고, 필요하면 전부 끝난 뒤 오케스트레이터가 한 번에 갱신한다.

## 퇴고 패널 (study-tikitaka의 4인이 퇴고자로 전환)

각자 시선이 겹치지 않게 역할을 고정한다. 지적할 때 담당자를 이모지로 표시한다.

- **🌩️ 사실관계** — 기술적 주장 전수 검사. 에러 메시지·API 응답·버전·수치가 실제와 맞는가?
  원문 소스(코드, ADR, 커밋 로그)가 있으면 대조한다. 기억으로 쓴 스펙 주장은 의심부터 한다.
- **🔥 논리 모순** — 글 안의 두 문장이 충돌하는 지점. 앞장의 단언을 뒷장이 뒤집는가?
  다이어그램·캡션이 본문과 어긋나는가? 모순이 서사 장치로 살릴 수 있는 것이면 삭제 대신 "…라고 믿었다"류의 반전으로 바꾼다.
- **🏗️ 독자 시점** — 이 글을 처음 읽는 외부인이 걸려 넘어질 곳. 설명 없이 등장하는 사내 용어·관행
  ("역머지", 조직 내부 저장소 이름), 맥락 없는 약어, "우리 조직"만 아는 전제. 처음 등장할 때 반 줄 설명을 붙이거나 뺀다.
- **☕ 문장 일관성** — 시제(한 일 vs 할 일), 존댓말 톤 유지, 형광펜 남발(챕터당 1~2회 초과),
  같은 개념의 표기 흔들림(plan/플랜 혼용 등), 번호 매긴 목록의 병렬 구조.

## 퇴고 규칙

- **지적은 근거와 수정안을 함께.** "어색하다"는 지적이 아니다. "5장 ①이 '아무도 확인 안 함'인데 destroy 가드는 있으므로 과장 — '가드는 destroy만 잡는다' 반 줄 추가" 형식으로.
- **원문 소스가 있는 글은 소스와 대조한다.** 작업일지·회고 글이면 해당 저장소의 코드/커밋/ADR을 실제로 읽고 사실관계를 검증한다.
- **스타일 규칙은 재론하지 않는다.** 폰트·팔레트·구조는 tistory-sketch-post 소관. 퇴고는 내용만 본다.
- **분량 지적은 챕터 단위로.** "길다"가 아니라 "N장이 같은 말을 두 번 한다 — 두 번째 단락 삭제 가능" 형식으로.
- 취향 차이(어미 선택, 비유 선호)는 지적하지 않는다. 틀린 것과 다른 것을 구분한다.

## 마무리 검증 (매 라운드 후)

```python
html = open('post.html', encoding='utf-8').read()
assert html.count('<svg') == html.count('</svg>')
assert html.count('<div') == html.count('</div>')
# path/text 태그 짝, 코드블록 내 < > & 이스케이프도 확인
```

통과하면 사용자에게 라운드 요약과 함께 전달하고, 커밋/푸시는 사용자 확인 후 진행한다.
(이 저장소는 DDINGJOO 계정으로 푸시 — `gh auth status`로 활성 계정 확인)
