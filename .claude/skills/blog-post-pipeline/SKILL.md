# Blog Post Pipeline — 작성부터 퇴고 통과까지

블로그 글을 사람이 두 번 시키지 않아도 되도록, **작성 → 패널 퇴고 → 수정 → 재검**을 한 번의 흐름으로 처리하는 스킬.
탄생 배경: 혼자 쓴 초안에는 반드시 구멍이 생긴다 — 독자가 모르는 사내 용어("역머지")가 설명 없이 튀어나오고,
다이어그램 캡션이 본문 뒷장과 모순되고, 할 일을 "했습니다"로 쓰는 시제 붕괴가 섞인다.
쓴 사람 눈에는 절대 안 보이므로, 퇴고는 쓴 사람이 아닌 패널이 한다.

## 파이프라인

```
0. 목록 확정  쓸 글 전체를 먼저 정한다. 제목·파일명·시리즈 번호까지 (아래 "왜 먼저" 참고)
1. 작성      글마다 서브에이전트 하나. 전부 동시에 띄운다
2. 퇴고      글마다 4인 패널 검수. 이것도 전부 동시에
3. 수정      지적을 반영. 반영 못 하는 지적은 사유와 함께 사용자에게 보고
4. 재검      수정된 부분만 다시 검수. 지적 0건이면 통과
5. 감사      원본 저장소·문서와 사실관계를 직접 대조 (아래 "사실관계 감사" — 생략 금지)
6. 반복      통과할 때까지 2~5를 반복. 최대 3라운드 — 남는 지적은 사용자 판단으로 넘김
7. 마무리    태그 짝 검증 → 통과하면 커밋 여부를 사용자에게 확인
```

## 자료는 어디서 오나 (작성 에이전트에게 경로를 주는 곳)

글의 사실관계는 기억이 아니라 **원본에서** 온다. 브리핑에 아래 경로를 직접 넣는다.

| 출처 | 위치 | 무엇을 얻나 |
|---|---|---|
| IaC 저장소 | 로컬 `~/orca/platform-IaC` (원격은 `{조직}/platform-IaC`) | ADR, 스택 README, 커밋 본문, 스크립트 docstring, `.tf` 주석 |
| 프로젝트 문서 | Notion (인프라 절감 계획 · AWS 온콜 · IaC 페이지) | 실행 기록, 제외 목록과 근거, 설계서와 구축 결과 대조표 |
| 알림 이력 | Slack `#platform-infra` | 알람이 실제로 어떻게 왔나, 노이즈 실측 |

**원격 저장소는 `dding-arch` 계정으로만 보인다.** `gh auth switch --user dding-arch`.
Platform-study 로 푸시할 때는 `DDINGJOO` 로 되돌린다.

**저장소는 읽기 전용이다.** 글 쓰려고 저장소 파일을 수정·커밋·푸시하지 않는다.
에이전트 브리핑에 이 문장을 그대로 넣고, 작업 후 `git status --porcelain` 이
비어 있는지 보고하게 한다.

이 저장소가 특히 값진 이유는 **자기 오판을 기록해두기 때문이다.** ADR 의 취소선
항목, "진단이 틀렸다", "완료로 기록한 것이 사실과 다르다", 커밋 본문의 "네 번째로
걸렸다" 같은 것들이 글의 반전을 만든다. 성공 기록만 읽으면 그 글은 홍보물이 된다.

각 라운드가 끝나면 "라운드 N: 지적 M건 → 반영 K건" 한 줄을 사용자에게 보여준다.
지적과 수정을 조용히 처리하고 결과만 내밀지 않는다 — 무엇이 걸렸고 어떻게 고쳤는지가 사용자의 학습 재료다.

## 병렬이 기본이다 (한 편만 쓸 때도 구조는 같다)

**글이 두 편 이상이면 순차로 쓰지 않는다.** 한 편에 서브에이전트 하나를 붙여 한 번에 전부 띄운다.
글은 서로 독립적이고 각자 파일이 다르므로 병렬화 이득이 그대로 나온다.
퇴고도 마찬가지 — 글 N편이면 퇴고 에이전트도 N개를 동시에 띄운다.

Agent 호출을 **한 메시지에 여러 개** 넣어야 실제로 동시에 돈다. 하나씩 띄우고 기다리면 병렬이 아니다.

### 왜 목록을 먼저 확정하는가 (병렬화의 유일한 함정)

글들끼리 서로를 참조하는 부분이 있다 — **시리즈 박스, "N편", 다른 편으로 가는 링크.**
목록을 확정하지 않고 병렬로 띄우면 각 에이전트가 자기가 몇 편인지 모르고, 시리즈 박스가
글마다 다르게 나오거나 존재하지 않는 편을 가리킨다. 나중에 손으로 맞추는 비용이 병렬 이득을 잡아먹는다.

그래서 0단계에서 **전체 목록(번호 · 제목 · 파일명)을 표로 확정하고, 그 표를 모든 에이전트 브리핑에 똑같이 넣는다.**
각 에이전트는 "너는 이 표의 N번이다"만 알면 자기 위치를 안다.

**목록만으로는 부족하다 — 형식까지 못 박아야 한다.** 2026-08-05에 5편을 병렬로 쓰면서 실제로 겪었다.
전체 표를 브리핑에 넣었는데도 한 에이전트가 시리즈 박스를 자기 주변만 남겨 축약했다
(9개 항목 → 5개, 구분자도 `.` 대신 `—`). 목록은 맞았지만 **형식이 갈렸다.**

그러니 브리핑에 표가 아니라 **완성된 시리즈 박스 HTML 을 그대로** 넣고 "이 블록을 복사해서
너에 해당하는 줄만 `<b>...</b> &larr; 지금 이 글` 로 바꿔라"고 지시한다.
그래도 어긋나면 전부 끝난 뒤 오케스트레이터가 정규식으로 한 번에 통일한다
(`<div class="obsv-series">.*?\n</div>` 를 정본으로 치환 — 편 번호만 바꿔 끼우면 된다).

### 공통 브리핑 (모든 작성 에이전트에 동일하게 넣을 것)

병렬 에이전트는 서로의 맥락을 못 본다. 각자에게 다음을 빠짐없이 전달한다:

- 읽을 파일 경로 — `tistory-sketch-post` 의 SKILL.md, `references/svg-sketch-guide.md`, `assets/template.html`
- **스타일 기준이 될 기존 글 1편의 경로** (톤·구조를 맞추는 앵커. 없으면 편마다 톤이 갈린다)
- 0단계에서 확정한 전체 목록 표 + "너는 N번"
- 내용 브리핑 (그 편이 담을 것. 사실관계 근거가 될 코드/문서 경로까지)
- 출력 경로 (파일명은 0단계 표 그대로)
- 검증 요구 — 태그 짝 스크립트를 **실제로 돌려서** 통과 확인하고 결과를 보고할 것
- 알려진 함정: 한글 파일명은 macOS 유니코드 정규화 때문에 Read 도구가 실패할 수 있다 (Bash/python 으로 우회)

### 파일 충돌 방지

**한 파일에 에이전트 하나.** 두 에이전트가 같은 파일을 만지면 나중 쓰기가 앞 쓰기를 덮는다.
공통 자산(스킬 파일, 인덱스 문서)은 에이전트가 건드리지 않고, 필요하면 전부 끝난 뒤 오케스트레이터가 한 번에 갱신한다.

## 🔒 발행 전 마스킹 관문 (패널과 별개로 반드시 거친다)

기술 블로그는 회사 인프라를 소재로 쓴다. **초안은 사내 문서처럼 쓰이고, 발행은 공개다.**
글을 쓴 에이전트는 원본 코드를 읽으며 쓰기 때문에 실제 값을 그대로 옮긴다 — 그게 정상 동작이므로,
걸러내는 일은 별도 관문이 맡아야 한다.

```bash
python3 .claude/skills/blog-post-pipeline/assets/mask-check.py <글.html>...
python3 ... mask-check.py <글.html> --extra ~/.config/blog-mask.txt --apply
```

무설정으로 계정 ID·토큰 접두사·이메일·사설 IP·내부 URL·8자리 이상 연속 숫자를 잡고,
조직 고유 문자열(회사명·내부 저장소명)은 `--extra` 목록으로 넘긴다.

**커밋 단계에서 자동으로 한 번 더 막는다.** `.githooks/pre-commit` 이 스테이징된 내용과 **경로**를
`--staged` 로 검사하고, 조직 목록 파일이 없으면 커밋 자체를 막는다(목록 없는 검사는 회사명을 못 잡는다).
새로 클론했다면 `git config core.hooksPath .githooks` 를 한 번 실행해야 켜진다.
오탐(임계값·날짜)은 저장소의 `.mask-allow` 에 값과 판정 이유를 적어 통과시킨다 — 조직 목록 적중에는 적용되지 않는다.

**그 목록 파일을 저장소에 커밋하지 마라.** 파일 자체가 노출이다. 저장소 밖(`~/.config/`)에 둔다.
같은 이유로 이 스킬 문서에도 실제 조직명·ID를 예시로 적지 않는다.

### 무엇을 가리고 무엇을 남기는가

| 반드시 가린다 | 자리표시자 예 |
|---|---|
| 회사·조직명 | `{조직}` |
| 조직 ID · 저장소 ID · AWS 계정 ID | `{조직ID}` `{저장소ID}` `{계정ID}` |
| **전역 고유 이름**(S3 버킷 등 — 열거가 가능하다) | `{state 버킷}` |
| 내부 서비스 저장소명 | `{서비스 저장소}` |
| Slack 채널, Notion·위키 URL | `#{인프라 채널}` / 링크 제거 |
| 사람 이름·이메일·계정 핸들 | `{동료}` |

| 남겨도 된다 (판단 근거를 함께 남길 것) | 이유 |
|---|---|
| 일반적인 저장소·디렉터리 이름 (`envs/dev`, `modules/`) | 어느 조직에나 있을 수 있는 이름 |
| 일반명사 프리픽스, 리전, 서비스명, 도구 버전 | 조직을 특정하지 않는다 |

식별력은 **조합**에서 나온다. 일반적인 이름 하나는 괜찮지만, 회사명과 붙는 순간 특정된다.

### 금액은 비율과 배수로만 (사용자가 정한 규칙)

비용 이야기를 쓸 때 **절대 금액은 회사 재무 정보다.** 청구액·목표액·기준선·항목별
절감액·시간당 단가·벤더명(청구 대행사, 계약 플랫폼) 전부 금지다.

| 금지 | 대체 |
|---|---|
| "83.5만원에서 12.8만원으로 하향" | "처음 적었던 값의 6분의 1 수준으로" |
| "월 청구액 2,104만원" | "월 청구액의 30%" |
| "손익분기 352배, 실제 $0.14" | "손익분기의 수백 분의 일" |
| "여유 $2" | "목표 절감액의 0.1% 미만" |

**논지는 비율로도 그대로 선다.** 실제로 11편을 이 규칙으로 썼고 절대 금액 0건으로
"여유가 사실상 없다", "6분의 1로 하향했는데 갭이 1.8배로 늘었다"가 다 성립했다.
AWS 공시 단가도 합산하면 규모가 추정되니 논지에 반드시 필요할 때만 쓴다.
시간(730)·기간·개수·용량(GB·vCPU)은 규모 노출이 아니므로 정확히 쓴다.

검사는 `mask-check.py` 로 안 잡히니 따로 grep 한다.

```bash
grep -nE '[0-9][0-9,.]*\s*(만원|억원|달러|USD)|\$\s?[0-9]|₩[0-9]' <글.html>
```

`원` 단독 히트는 "자**원**", "**원**인", "**원**래" 오탐이 대부분이니 문맥을 본다.

### ⚠️ 아직 조치되지 않은 취약점은 쓰지 않는다

이건 마스킹이 아니라 **취약점 공개** 문제다. 자원 이름을 가려도, 지금 살아 있는
약점을 공개 블로그에 적으면 그 자체가 위험이다.

판단 절차는 이렇다.

1. **저장소에서 조치 여부를 확인한다** (`git log -S"<설정키>"`, 문서의 취소선·완료 표시)
2. 조치됐으면 **과거형·해결형**으로 쓴다 — "그때 이런 상태였고 이렇게 고쳤다"
3. 조치 전이면 **구체 상태를 지우고 교훈만** 남긴다 — 어느 자원인지, 현재 값이
   얼마인지, 몇 대인지 쓰지 않는다

실제 사례. "타깃 한 대 + 삭제 보호 꺼짐 + 최근 세 번 healthy 0" 을 쓰려다
저장소를 확인해보니 미조치였다(설정이 그대로고 수정 커밋이 없었다). 그래서
**"이중화도 삭제 보호도 없는 자원이 드러났다"** 로 추상화했다. 논지("코드로 옮기니
콘솔에서 세 화면에 흩어져 있던 사실이 몇 줄 안에 붙었다")는 그대로 섰다.

같은 이유로 **대외 연동 상대를 특정할 수 있는 조합**(시각 + 인과 방향 + 상대측 장비)과
**서비스 도메인**(업종을 특정하는 서술)도 뺀다. 원본 문서에 등급 표시(L2-내부 등)가
있으면 그건 그 문서가 스스로 외부 공유 불가라고 말한 것이다.

**작성 에이전트에게 이 목록을 브리핑에 그대로 넣는다.** 다 쓴 뒤 지우는 것보다
안 쓰는 게 싸고, 초고에 한 번 들어가면 퇴고에서 살아남는다.

### 값을 지우지 말고 자리표시자로 바꾼다

```
나쁨:  repo:***/***:ref:refs/heads/main          형식이 안 보인다
좋음:  repo:{조직}@{조직ID}/{저장소}@{저장소ID}:ref:refs/heads/main
```

자리표시자는 실제 값보다 **독자에게 더 유용하다** — 독자가 알아야 하는 건 남의 회사 ID가 아니라 형식이다.
치환하면 코드블록의 정렬(`^^^^` 캐럿 줄, 표 칸)이 깨지므로, 캐럿 줄은 지우고 자리표시자가 스스로 설명하게 둔다.

### 이미 푸시한 뒤에 발견했다면

마스킹 커밋만으로는 **git 히스토리에 값이 남는다.** 저장소가 공개면 이미 공개된 것이다.
- 자격증명(토큰·키)이면 즉시 폐기·재발급한다. 히스토리 정리는 그다음이다.
- 식별자(조직 ID 등)면 폐기할 수 없으므로 **사용자에게 사실을 알리고 판단을 맡긴다.**
  히스토리 재작성은 공개 저장소에서 파괴적이므로 오케스트레이터가 임의로 하지 않는다.

## 퇴고 패널 (study-tikitaka의 4인이 퇴고자로 전환)

각자 시선이 겹치지 않게 역할을 고정한다. 지적할 때 담당자를 이모지로 표시한다.

- **🌩️ 사실관계** — 기술적 주장 전수 검사. 에러 메시지·API 응답·버전·수치가 실제와 맞는가?
  원문 소스(코드, ADR, 커밋 로그)가 있으면 대조한다. 기억으로 쓴 스펙 주장은 의심부터 한다.
- **🔥 논리 모순** — 글 안의 두 문장이 충돌하는 지점. 앞장의 단언을 뒷장이 뒤집는가?
  다이어그램·캡션이 본문과 어긋나는가? 모순이 서사 장치로 살릴 수 있는 것이면 삭제 대신 "…라고 믿었다"류의 반전으로 바꾼다.
- **🏗️ 독자 시점** — 이 글을 처음 읽는 외부인이 걸려 넘어질 곳. 설명 없이 등장하는 사내 용어·관행
  ("역머지", 조직 내부 저장소 이름), 맥락 없는 약어, "우리 조직"만 아는 전제. 처음 등장할 때 반 줄 설명을 붙이거나 뺀다.
- **☕ 문장 일관성** — 시제(한 일 vs 할 일), 존댓말 톤 유지, 형광펜 남발(챕터당 1~2회 초과),
  같은 개념의 표기 흔들림(plan/플랜 혼용 등), 번호 매긴 목록의 병렬 구조.

## 퇴고 규칙

- **지적은 근거와 수정안을 함께.** "어색하다"는 지적이 아니다. "5장 ①이 '아무도 확인 안 함'인데 destroy 가드는 있으므로 과장 — '가드는 destroy만 잡는다' 반 줄 추가" 형식으로.
- **원문 소스가 있는 글은 소스와 대조한다.** 작업일지·회고 글이면 해당 저장소의 코드/커밋/ADR을 실제로 읽고 사실관계를 검증한다.
- **스타일 규칙은 재론하지 않는다.** 폰트·팔레트·구조는 tistory-sketch-post 소관. 퇴고는 내용만 본다.
- **분량 지적은 챕터 단위로.** "길다"가 아니라 "N장이 같은 말을 두 번 한다 — 두 번째 단락 삭제 가능" 형식으로.
- 취향 차이(어미 선택, 비유 선호)는 지적하지 않는다. 틀린 것과 다른 것을 구분한다.

### 하우스 스타일 — 신규 글이 기존 글과 갈리는 지점

확정된 글과 신규 초고를 대조해서 **분포가 다른 것**을 찾는다. 취향이 아니라 통일 문제다.

**엠대시(`&mdash;`, 리터럴 `—`)를 쓰지 않는다.** 확정된 글들은 본문 0개인데 신규 초고는
편당 20~30개씩 나온다. 쉼표·콜론·괄호·문장 분리로 자연스러운 한국어로 바꾼다.
**기계적 치환 금지** — 문장마다 읽고 가장 자연스러운 형태를 고른다. h2 제목의 부제
구분자와 SVG `<text>` 라벨도 포함이다.

측정은 이렇게 한다.

```bash
for f in <확정된 글> <신규 글>; do
  printf "%s  mdash %s / em %s\n" "$(basename "$f" | cut -c1-30)" \
    "$(grep -c '&mdash;' "$f")" "$(python3 -c "print(open('$f',encoding='utf-8').read().count(chr(0x2014)))")"
done
```

같은 방식으로 대조할 것들: 인용부호(`「」` vs `"`), 표기 흔들림(순익분기/손익분기),
같은 수치의 다른 표현(한 편은 "수십에서 수백 배", 다른 편은 "수십 배에서 천 배 넘게"
— 원자료가 96~1200배면 후자가 맞다).

## 사실관계 감사 (퇴고와 별개로 반드시 거친다)

**퇴고 패널이 "사실관계 확인했다"고 보고해도 그건 검증된 게 아니다.**

2026-08-23에 실제로 그랬다. 퇴고를 통과한 다섯 편을 별도 감사자에게 넘겨 저장소와
대조하게 했더니 **126건 중 불일치 8건 · 과장 5건**이 나왔다. 형식 검증(태그 짝·엠대시·
마스킹)은 그 다섯 편 모두 통과한 상태였다. **글이 사실을 말하는지는 아무도 안 봤기
때문이다.**

그래서 감사는 **퇴고한 에이전트가 아닌 다른 에이전트**가 한다. 자기 글의 근거를
다시 읽는 사람은 자기가 그때 읽은 것을 다시 읽는다.

### 감사자에게 주는 지시

- 원본 저장소를 **읽기만** 하고, 검증 가능한 주장(숫자·건수·파일명·설정값·에러 원문·
  커밋 존재·ADR 인용)을 하나씩 대조한다
- 판정은 넷 중 하나: **확인 / 불일치 / 확인 불가 / 과장**. "확인 불가"는 글이
  완충 표현("대개 이런 모양이에요")으로 처리했는지도 함께 판정한다
- **글을 고치지 않는다.** 발견만 보고하고 수정은 따로 붙인다
- 문체·분량·취향 지적 금지. 사실관계와 논리 정합성만
- **퇴고 보고를 믿지 않는다.** "확인했다"고 한 것도 다시 확인한다
- 마지막에 **가장 신뢰도가 낮은 편과 그 이유**, 그리고 판정 분포를 낸다

### 특히 파야 하는 문형 — 완결 주장

세 편에서 같은 유형이 나왔고 **셋 다 거짓이었다.**

| 글이 쓴 것 | 실제 |
|---|---|
| "그 뒤로는 한 번도 안 막혔어요" | 나흘 뒤 또 막혔고, 커밋 본문이 그걸 "네 번째로 걸렸다"고 적어뒀다 |
| "마지막에 클러스터를 지웠어요" | 삭제가 거부된 상태였고, 원자료에 "완료로 기록한 것이 사실과 다르다"가 있었다 |
| "별건 목록으로 옮겼습니다" | 추적 항목이 0건이었다 |

공통 원인은 **관찰 범위의 한계를 처방의 성질로 착각한 것**이다. 그러니 이런 문형을
만나면 **반례를 먼저 찾는다** — "그 뒤", "한 번도", "전부", "마지막으로", "이제
안 그런다", "옮겼다", "고쳤다".

그리고 자주 나오는 결함 유형이 넷 더 있다.

- **시리즈 내부 모순** — 같은 사실을 1편은 정확히 한정하고 2편은 계정 전체로 읽히게
  썼다. 인접 편을 같이 읽어야 잡힌다
- **자기 규칙 위반** — 3장이 "발행되지 않은 것과 0은 다르다"인데 5장 표에서 원자료의
  "데이터 없음"을 "0"으로 옮겨 적었다. **글의 논지를 글의 근거가 위반하는지** 본다
- **존재한 적 없는 규칙** — "검사가 원래 중복을 오류로 처리했다"인데 그런 규칙이 없었다.
  "원래 X였다 → Y로 바꿨다" 서술은 X의 존재를 이력에서 확인한다(`git log -S`)
- **원자료 자체의 오류** — 문서 세 곳에서 개수가 어긋나거나, "$9로 5배"가 실제 5.5배거나,
  "11종"인데 표는 9종이었다. 글이 아니라 **원본이 틀린 경우**이니 고치지 말고 보고한다

### 지시가 틀렸으면 기각하게 한다

감사자·수정자에게 **"내 지적이 틀렸다면 그렇게 보고하고 고치지 마라"** 를 명시한다.
실제로 두 번 기각당했다 — "제외 목록 10건을 확인하라"고 했는데 그 글에 개수를 적은
문장이 아예 없었고, "30일 제약 방향이 뒤집혔을 것"이라 의심했는데 방향은 맞고 표의
열 이름이 틀린 것이었다.

**그리고 고치는 사람이 감사자보다 더 찾는다.** 문장을 다시 쓰려면 그게 참인 이유를
알아야 하기 때문이다. 위 감사에서 13건이 나온 뒤, 그것을 고치던 에이전트들이 감사가
놓친 3건을 추가로 찾았다. 그러니 수정 담당에게도 "범위 밖에서 발견한 것은 플래그하라"
고 열어둔다.

## 마무리 검증 (매 라운드 후)

```python
html = open('post.html', encoding='utf-8').read()
assert html.count('<svg') == html.count('</svg>')
assert html.count('<div') == html.count('</div>')
# path/text 태그 짝, 코드블록 내 < > & 이스케이프도 확인
```

**이 검증이 통과했다는 것은 형식이 맞다는 뜻일 뿐이다.** 위 감사 없이 발행하면
"태그 짝 OK, 마스킹 깨끗함, 그리고 결론이 거짓"인 글이 나간다.

통과하면 사용자에게 라운드 요약과 함께 전달하고, 커밋/푸시는 사용자 확인 후 진행한다.
(이 저장소는 DDINGJOO 계정으로 푸시 — `gh auth status`로 활성 계정 확인)

### 이미지판을 재생성했으면 장수를 대조한다

`notion/` 에서 `blog/` 를 만든 뒤(`assets/make-image-version.py`), 스크립트가 출력한
"그림 N장"과 실제 PNG 파일 수가 **같은지 반드시 확인한다.**

```bash
python3 - <<'PY'
import re
from pathlib import Path
ref = sum(len(re.findall(r'<img src="images/', p.read_text(encoding='utf-8')))
          for p in Path('blog').rglob('*.html'))
print('img 참조', ref, '/ PNG', len(list(Path('blog').rglob('*.png'))))
PY
```

두 수가 다르면 **그림이 덮어써졌다.** 참조가 깨지지 않으니 눈에 안 띄는데,
글 A 의 자리에 글 B 의 그림이 들어가 있는 상태다. 링크 검사로는 절대 안 잡힌다.

2026-08-23에 실제로 났던 사고다. 이미지 폴더 이름을 글 번호로만 만들던 탓에
`study/MSA_SRE/ch2` 의 `01_` 세 편이 같은 `images/01/` 을 쓰면서 서로의
`fig1.png` 를 덮었다. **필요 23장 중 8장만 남아 있었고, 그 상태로 커밋돼 있었다.**
스크립트는 이제 같은 폴더에 번호가 겹칠 때만 `01a`·`01b` 로 갈라준다.

교훈은 검사기 쪽이다. "깨진 참조 0건"과 "미참조 PNG 0건"을 둘 다 통과해도
내용이 뒤바뀐 건 못 잡는다. **개수 보존을 따로 세야 한다.**
