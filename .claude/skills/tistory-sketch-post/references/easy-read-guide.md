# 쉽게 읽히게 쓰기

작업일지 톤으로 쓴 글은 그 일을 같이 겪은 사람의 눈높이로 쓰인다. "import 블록",
"state rm", "adopt" 가 설명 없이 나오고, 필자에게 당연한 전제가 빠진다.
이 가이드는 그 간극을 메우는 장치를 정한다. 시각 스타일(폰트·스케치 그림)은 건드리지 않는다.

기준이 된 글: 사용자가 쉽게 읽힌다고 꼽은 k8s 입문 가이드(`~/Downloads/k8s-best-practices-ch9-12-13.html`).
그 글은 약 9만 자에 용어 박스 92개, 실무 팁 22개, 주의 13개를 썼다(비유도 27개 있었지만 이 블로그는 쓰지 않는다).
블로그 한 편(3~7천 자)에 맞게 줄이면 아래 수치가 된다.

## 누구를 위해 쓰는가

**독자는 이 분야 1~2년차 개발자다.** 코드와 Git, 기본 클라우드 용어(서버, 로드밸런서)는 알지만,
이 글의 도구(Terraform, Datadog, Playwright…)는 써 본 적이 없거나 이름만 안다.
필자의 회사 사정은 전혀 모른다.

## 장치

### 1. 📖 용어 박스 — 처음 나오는 자리에서 정의한다

독자가 모를 수 있는 용어가 **처음 등장하는 문단 바로 뒤**에 둔다. 글 끝의 용어집이 아니다.

```html
<div class="obsv-term">
  <div class="obsv-tt">📖 용어: 매니페스트 (manifest)</div>
  어떤 파일이 블로그의 몇 번 글인지 적어 둔 대장입니다. 업로더는 이걸 보고 새 글을 만들지,
  기존 글을 고칠지 정해요.
</div>
```

- 정의는 **한두 문장**. 교과서 정의가 아니라 "이 글에서 무슨 일을 하는가"로 쓴다
- 한 편에 **4~8개**. 그보다 많으면 글이 용어집이 된다. 아는 사람이 대부분인 말(API, JSON)은 넣지 않는다
- 같은 용어는 한 번만. 두 번째부터는 설명 없이 쓴다
- 인라인으로 충분하면 박스 대신 괄호: "플래그(`--staged`, 스테이징된 내용만 보라는 옵션)"

### 2. 비유는 쓰지 않는다 (사용자가 정한 규칙, 2026-09-30)

"택배 송장 대장", "회사 대표번호" 같은 비유 박스도, 본문 속 "~처럼" 비유도 쓰지 않는다.
비유는 짝을 맞추는 수고를 독자에게 넘기고, 어디서 깨지는지까지 설명해야 해서 오히려 길어진다.
이해는 **문제를 먼저 보여 주기**, **용어 박스**, **오류 원문 한 줄 풀이**로 돕는다.

### 3. 문제 먼저, 해결은 그다음

개념을 소개하기 전에 **그 개념이 없으면 무엇이 곤란한지**를 먼저 보여 준다.

```
나쁨: "매니페스트는 경로와 글 번호를 매핑한다. 그래서 재실행이 안전하다."
좋음: "업로드가 중간에 끊겼다고 해 볼게요. 다시 돌리면 이미 올린 글도 또 올라갑니다.
      어디까지 올렸는지 기억하는 곳이 필요해요. 그게 매니페스트입니다."
```

절 제목도 문제를 드러내는 쪽이 좋다: "재실행하면 글이 두 번 올라간다" > "매니페스트 설계".

### 4. 💡 실무에서는 / ⚠️ 주의 — 기존 콜아웃을 두 종류로 나눠 쓴다

기존 `.obsv-callout` 을 제목만 바꿔 쓴다.
- **💡 실무에서는**: 원리 뒤에 "실제로는 이렇게 쓴다". 명령어, 설정값, 판단 기준
- **⚠️ 주의**: 흔히 틀리는 지점. 이 블로그의 작업일지에서는 "나도 여기서 틀렸다"가 제일 좋은 주의다

한 편에 합쳐서 **2~5개**.

### 5. 절마다 한 줄 정리, 글 첫머리에 지도

- 긴 절(화면 두 개 이상) 끝에는 **한 줄 정리**를 둔다. 형광펜(`.obsv-mark`) 한 번으로 충분하다
- 글이 길면(5천 자 이상) 도입 뒤에 **이 글에서 다룰 것** 3~5줄을 둔다. 목차가 아니라 질문 형태:
  "업로드가 끊기면 어떻게 이어서 하나?", "블로그 글 순서는 어떻게 정하나?"

## 작업일지 톤과 같이 쓰는 법

작업일지의 장점(실제로 겪은 일, 틀렸던 판단, 반전)은 그대로 둔다. 쉽게 쓰기는 **설명을 더하는 것이지
사건을 빼는 것이 아니다.**

- 장면으로 여는 도입, 해요체, 반전 구조는 기존 SKILL.md 규칙 그대로
- 사건을 서술하다가 낯선 개념이 나오면 → 용어 박스로 끊고 → 사건으로 돌아온다
- 코드·오류 원문은 그대로 싣되, **바로 아래에 한 줄로 무슨 뜻인지** 풀어 준다

```
<div class="obsv-code">403 하루에 작성할 수 있는 글은 최대 50개까지입니다.</div>
→ 티스토리 서버가 저장을 거절했다는 뜻이에요. 화면에는 아무것도 뜨지 않았습니다.
```

## 점검 (퇴고 패널의 🏗️ 독자 시점이 이 목록으로 본다)

- [ ] 1~2년차 개발자가 **처음 멈칫할 용어**마다 용어 박스나 괄호 설명이 있는가 (처음 등장하는 자리에)
- [ ] 용어 박스가 4~8개 범위인가. 넘으면 뺄 것을 고른다
- [ ] 비유(박스·"~처럼" 문장)가 0개인가
- [ ] 개념 소개 전에 "그게 없으면 무엇이 곤란한가"가 먼저 나오는가
- [ ] 오류 원문·코드 아래에 한 줄 풀이가 있는가
- [ ] 필자의 회사·저장소 사정을 모르는 사람이 읽어도 문장이 성립하는가

측정:

```bash
f=<글.html>
for c in obsv-term obsv-callout; do printf "%s %s\n" $c $(grep -c "class=\"$c\"" "$f"); done
```
