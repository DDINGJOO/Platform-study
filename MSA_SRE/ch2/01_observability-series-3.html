관측성 데이터를 얻는 전통적인 방법은 코드에 계측을 심는 것이었습니다. 언어마다 라이브러리를 붙이고, 재배포하고, 옆 팀을 설득하고. 그런데 마이크로서비스가 수백 개가 되면 이 방식은 벽에 부딪혀요. "코드를 안 고치고 어디까지 볼 수 있는가" — 이 질문에 대한 세 가지 답이 이번 편의 주인공입니다.

1. eBPF: 커널이라는 길목에서 관찰하기

출발점은 단순한 관찰입니다. 모든 앱의 모든 동작은 결국 커널을 지나갑니다. 네트워크도, 파일도, 프로세스 생성도 전부 시스템 콜이에요. 그렇다면 커널에서 관찰하면 앱을 안 건드려도 다 보이지 않을까?

eBPF는 커널 안에서 안전하게 실행되는 작은 프로그램을 밖에서 주입하는 기술입니다. 프로그램을 커널의 특정 이벤트에 후크로 붙여요 — "시스템 콜 read가 호출될 때마다", "TCP 패킷이 도착할 때마다". 이벤트가 발생하면 커널이 그 자리에서 프로그램을 실행하고, 수집한 데이터를 map이라는 커널 내 공유 저장소에 적어둡니다. 유저스페이스의 수집 데몬이 이걸 비동기로 퍼가면 끝이에요.

후크 지점 중 uprobe(유저스페이스 함수 후킹)가 특히 강력합니다. OpenSSL의 SSL_read/SSL_write에 걸면 암호화되기 전의 평문을 볼 수 있어요. 네트워크에선 TLS라 안 보이는 HTTP 내용이, 앱이 암호화 함수를 부르는 순간을 잡으면 보이는 거죠.

"커널에 코드 주입"인데 왜 안전한가

커널이 죽으면 서버 전체가 죽습니다. eBPF가 커널 모듈과 결정적으로 다른 점은, 프로그램이 로드되기 전에 verifier라는 정적 검증기가 전수 검사를 한다는 거예요. 무한루프 불가(모든 실행 경로가 유한함을 증명해야 통과), 경계 밖 메모리 접근 불가, 크기·복잡도 제한. 증명이 안 되면 로드 자체가 거부됩니다. "커널 안에서 돌지만 커널을 죽일 수 없는" 샌드박스 — 이 보장 덕에 프로덕션에 넣을 수 있어요.

왜 빠른가: hot path에서 하는 일의 차이

그림 1. 비싼 일을 hot path 밖으로 밀어낸 것이 eBPF의 속도 비결

APM 라이브러리는 span 객체 생성(GC 부담), 직렬화, 소켓 전송을 요청을 처리해야 할 앱의 스레드에서 합니다. eBPF는 어차피 발생하는 시스템 콜에 붙어서, JIT 컴파일된 네이티브 코드가 고정 메모리에 몇 바이트 적는 게 전부예요. 무거운 일(파싱, 전송)은 전부 별도 데몬이 비동기로 처리하고요. 오버헤드가 보통 1% 미만이라 프로덕션 상시 가동이 성립합니다.

이 원리 위에 프로토콜 파서를 얹은 게 요즘 도구들입니다. 데이터독의 USM(Universal Service Monitoring)이 계측 안 된 서비스도 서비스 맵에 올려주는 비결이 eBPF고(Agent의 system-probe 컴포넌트), Cilium/Hubble, Grafana Beyla, Pixie도 같은 계열이에요.

⚠️ 하지만 eBPF가 APM을 대체하진 못한다
eBPF가 보는 건 경계에서 일어나는 일(시스템 콜, 네트워크)이다. 비즈니스 컨텍스트(이 요청이 어떤 user의 어떤 주문인지)와 앱 내부 로직의 의미는 앱만 안다. 그래서 eBPF = 코드 수정 없이 전체를 커버하는 베이스라인, APM 계측 = 핵심 서비스에 깊이를 더하는 레이어로 조합한다.

2. OpenTelemetry: 계측 락인을 끊다

그럼 계측을 하기로 했다면, 이번엔 다른 문제가 기다립니다. 벤더 라이브러리(dd-trace 등)로 계측하면 그 코드가 코드베이스 전체에 스며들어요. "데이터독 비싸니 갈아타자"가 나오는 순간 수백 군데를 걷어내고 다시 심어야 합니다. 사실상 못 갈아타요. 이게 계측 락인(lock-in)입니다.

OpenTelemetry(OTel)의 제안: 계측은 벤더 중립 표준으로 한 번만 하고, 데이터를 어디로 보낼지는 설정으로 바꾸자. OpenTracing과 OpenCensus가 2019년 합쳐진 프로젝트로, 지금은 사실상 업계 표준이에요.

그림 2. OTel 3층 구조 — 락인을 설정 파일 안에 가둔다

구조의 백미는 API와 SDK의 분리입니다. API는 껍데기뿐이라 SDK가 없으면 아무것도 안 해요(no-op). 덕분에 DB 드라이버 같은 오픈소스 라이브러리들이 부담 없이 OTel 계측을 미리 내장하기 시작했고, 이게 생태계 승리의 비결이에요. Collector는 receiver → processor → exporter로 조립하는 파이프라인인데, 1편의 tail 샘플링(tailsampling 프로세서)이 바로 여기서 돌아갑니다.

서비스 간 트레이스 연결은 W3C Trace Context 표준 헤더로 합니다. 실물은 이렇게 생겼어요.

traceparent: 00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01 │ └ trace ID (전체 여정) └ 부모 span ID └ 샘플링 플래그 └ 버전

마지막 01이 "이 트레이스 저장하기로 했음" 표시 — 1편의 head 샘플링 결정이 전파되는 방식이 바로 이 플래그입니다.

데이터독과의 긴장 관계

데이터독 입장에서 OTel은 양날의 검입니다. 업계 표준이라 밀어낼 수 없어서 OTLP 수신을 Agent에 내장했고 자체 Collector 배포판(DDOT)까지 내놨지만, 프로파일링 연동이나 일부 보안 기능은 여전히 자사 라이브러리(dd-trace)로 계측해야 매끄럽게 동작해요. 자사 라이브러리의 락인은 수익 방어선이니까요.

실용적 판단 기준: 데이터독에 오래 머물 확정이면 dd-trace가 기능 커버리지에서 유리하고, 벤더 교체·멀티 백엔드 가능성을 열어두려면 OTel + Collector가 맞다. 신규 프로젝트라면 OTel로 시작하는 게 요즘 대세입니다. 계측은 자산이고, 벤더 중립 자산이 더 안전하니까요.

3. Continuous Profiling: 마지막 블랙박스를 열다

여기까지 오면 트레이스가 "결제 서비스의 이 span이 800ms"까지 알려줍니다. 그런데 그 800ms 동안 CPU가 정확히 어느 함수에서 뭘 했는지는 span 안쪽이라 다시 블랙박스예요. 이 마지막 구간을 여는 게 프로파일링입니다.

프로파일러 자체는 수십 년 된 도구지만 너무 무거워서 개발 장비 전용이었어요. "Continuous" Profiling은 이 판을 바꿉니다 — 프로덕션에서, 전체 서비스에, 24시간 상시로. 비결은 전수 조사를 포기한 통계적 샘플링이에요. 초당 약 100번, 프로세스의 콜스택 스냅샷을 찍습니다.

스냅샷 순간의 콜스택: main() → handleCheckout() → calcDiscount() → parseJSON() ← 지금 실행 중 스냅샷 10만 장 중 3만 장에서 parseJSON이 목격됨 → CPU 시간의 약 30%를 parseJSON이 먹는다 (통계적 추론)

비용이 "초당 100번 스택 읽기"뿐이라 오버헤드 1~2%로 상시 가동이 됩니다. eBPF 편과 같은 구조죠 — hot path에선 최소한의 기록만, 분석은 밖에서. 실제로 요즘 시스템 전체 프로파일러(Parca, Pyroscope 등)는 eBPF로 커널에서 스택을 찍고, 데이터독 프로파일러 같은 런타임 내장형(JVM의 JFR, Go의 pprof)은 언어별 디테일(GC, 락 대기, 힙 할당)이 더 풍부해요.

결과는 플레임 그래프로 봅니다. 가로 폭 = CPU 시간 점유율, 세로 = 콜스택 깊이.

그림 3. 플레임 그래프 읽는 법 — 넓고 평평한 꼭대기를 찾아라

읽는 요령은 하나예요. 넓은데 그 위에 자식이 없는 블록 = 실제로 CPU를 태우는 지점. 성능 최적화가 "감으로 찔러보기"에서 "제일 넓은 블록부터 공략"으로 바뀝니다.

트레이스와 연결되면 진짜 완성

프로파일만 있으면 "이 서비스는 전체적으로 parseJSON에 30% 쓴다"까지만 압니다. 그런데 span이 실행되는 동안 찍힌 스택 샘플에 그 span ID를 태깅해두면, "이 느렸던 특정 요청의 이 span 동안 CPU가 무슨 함수에 있었나"를 볼 수 있어요. 데이터독에서 Code Hotspots라고 부르는 기능입니다. 메트릭·로그·트레이스에 이어 프로파일이 "4번째 시그널"로 불리는 이유예요.

4. 조사 경로의 완성

3부작의 조각들이 여기서 하나로 이어집니다.

그림 4. 대시보드에서 소스코드 한 줄까지, 조사 경로의 완성

2편의 SLO 알람이 "사용자가 아프다"를 알리면, 1편에서 tail 샘플링으로 남겨둔 에러 트레이스가 "이 서비스의 이 span"을 찾아주고, span에 연결된 프로파일이 "이 함수의 이 줄"을 가리킵니다. 관측성 스택 전체가 하나의 조사 경로예요.

🐶 데이터독 실무 메모
• USM(eBPF)으로 전체 서비스 지도를 공짜로 깔고, 핵심 서비스만 APM 계측
• dd-trace를 쓴다면 프로파일러는 설정 플래그 하나로 켜짐 (단, 호스트당 과금 → 핵심 서비스부터)
• CPU 프로파일 외에 할당·락·월타임 프로파일도 있음 — "CPU는 한가한데 느려요" 미스터리는 월타임으로
✍️ 오늘의 요약, 그리고 시리즈 완결
eBPF는 verifier로 안전이 증명된 프로그램을 커널에 후킹해 코드 수정 없이 전체를 관찰하고, OTel은 계측을 벤더 중립 표준으로 만들어 락인을 설정 파일 안에 가두고, Continuous Profiling은 통계적 샘플링으로 span 안쪽 마지막 블랙박스를 연다.

1편(무엇을 남길까) → 2편(언제 울릴까) → 3편(어떻게 수집할까). 결국 관측성이란 "사용자의 아픔에서 코드 한 줄까지, 끊기지 않는 길을 미리 닦아두는 일"이다.
