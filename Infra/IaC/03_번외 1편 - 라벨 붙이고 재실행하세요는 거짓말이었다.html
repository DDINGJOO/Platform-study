Terraform 코드를 관리하는 저장소 이야기예요. PR 을 올리면 dev/prod plan 을 떠서 요약을 코멘트로 남기고, 거기에 삭제나 재생성이 섞여 있으면 allow-destroy 라벨 없이는 체크를 실패시키는 가드를 달아뒀습니다. 어느 날 동료가 낡은 dev 리소스를 정리하는 PR 을 올렸어요. plan 요약 코멘트에 삭제 3건 — 의도한 변경입니다. 그 가드가 빨간불을 켜고 이렇게 안내했어요. "의도한 변경이라면 PR 에 allow-destroy 라벨을 붙이고 다시 실행하세요." 시키는 대로 라벨을 붙이고 Actions 에서 Re-run failed jobs 를 누릅니다. 또 실패해요. 다시 누릅니다. 또 실패합니다.

세 번쯤 되면 사람은 이렇게 결론 내려요 — 파이프라인이 고장났구나. 그리고 자기 admin 권한으로 우회할 방법을 찾기 시작하죠. 그런데 고장난 건 파이프라인이 아니라 제가 가드에 쓴 그 한 줄이었습니다.

1. 문제의 한 줄

가드는 이렇게 생겼었어요. 읽으면 아무 문제가 없어 보이는 게 함정입니다.

- name: 파괴적 변경 가드 run: | if [ "${{ contains(github.event.pull_request.labels.*.name, 'allow-destroy') }}" != "true" ]; then echo "::error::라벨을 붙이고 다시 실행하세요." exit 1 fi

로컬 감각으로 읽으면 "지금 이 PR 에 붙어 있는 라벨을 본다"로 읽히죠. 그래서 라벨을 붙이면 다음 실행은 통과할 거라 믿게 돼요. 그 믿음이 틀렸고, 그래서 에러 메시지가 안내하는 절차가 구조적으로 불가능했습니다.

2. github.event 는 박제된 payload 다

github.event 는 실행 시점에 GitHub API 를 호출해 가져오는 살아있는 값이 아니에요. 이벤트가 발생한 그 순간의 webhook payload JSON 이 run 에 통째로 박제된 것입니다. 여기서 그 이벤트는 마지막 커밋 push, 즉 synchronize 였고, 그때 PR 에는 라벨이 없었죠.

그리고 Re-run 은 새 이벤트를 발생시키는 버튼이 아니에요. 박제된 payload 를 그대로 들고 job 만 다시 돌리는 버튼입니다. 라벨은 payload 가 찍힌 뒤에 붙였으니, 재실행이 읽는 labels 배열은 여전히 비어 있어요. 몇 번을 눌러도 결과가 같습니다.

실제로 통과하려면 새 이벤트를 만들어야 해요 — 라벨을 붙인 뒤 빈 커밋이라도 push 해서 synchronize 를 일으키거나, PR 을 닫고 다시 열어 reopened 를 만드는 것. 어느 쪽도 에러 메시지에서는 유추할 수 없습니다. 가드가 우회 충동을 만들면 그 가드는 이미 실패한 겁니다.

그림 1. Re-run 은 새 이벤트가 아니라 옛 스냅샷의 재생이다

3. 반대 방향도 뚫려 있었다

더 무서운 건 반대편이에요. 트리거는 on: pull_request 한 줄이었고, 이건 기본값 세 종류(opened, synchronize, reopened)만 잡습니다. unlabeled 가 없으니 체크가 초록불이 된 뒤에 라벨을 떼도 워크플로가 다시 돌지 않아요. 필수 상태 체크는 그 커밋에 같은 이름으로 마지막에 보고된 결과만 보고, 새 run 이 없으면 옛 초록불이 그대로 남습니다. 결과는 라벨 없는 PR 이 머지 가능한 초록불로 방치되는 상태입니다. 붙일 때는 안 통하고, 뗄 때는 그냥 통과하는 가드였어요.

4. 수리 두 가지와 트레이드오프

방법 A — 트리거를 types: [opened, synchronize, reopened, labeled, unlabeled] 로 늘립니다. 라벨을 붙이거나 떼면 신선한 payload 로 워크플로가 재실행되죠. 단점은 값이에요. 라벨 하나 붙일 때마다 dev/prod plan 이 통째로 다시 돕니다. AWS 왕복 2회.

방법 B — 실행 시점에 API 로 조회합니다. 그러면 Re-run 버튼이 에러 메시지 그대로 동작해요.

env: GH_TOKEN: ${{ github.token }} PR_NUMBER: ${{ github.event.pull_request.number }} run: | labels=$(gh pr view "$PR_NUMBER" --repo "$GITHUB_REPOSITORY" \ --json labels --jq '.labels[].name') if ! printf '%s\n' "$labels" | grep -qx 'allow-destroy'; then exit 1 fi

그래서 B 를 쓰고 types 에는 unlabeled 만 추가했어요. 붙일 때는 싼 Re-run 으로 해결하고, 뗄 때는 강제로 재검사를 걸어 초록불을 지웁니다. labeled 는 넣지 않아요 — B 가 있으니 굳이 plan 두 판을 더 돌릴 이유가 없죠.

5. 박제가 오히려 정확한 값도 있다

여기서 "그럼 github.event 를 쓰지 말라는 거냐"로 넘어가면 과잉 학습이에요. 위 코드에서도 PR 번호는 github.event 에서 읽고 있잖아요. 구분선은 딱 하나입니다 — 이 값이 이벤트 이후에 바뀔 수 있는가.

커밋 SHA, PR 번호, 브랜치명은 그 이벤트에 고정된 값이라 박제가 오히려 정확해요. 실행 중에 PR 에 새 커밋이 올라와도 이 run 이 검사한 대상은 t1 의 SHA 여야 하니까요. 반면 라벨, 리뷰 승인 상태, 코멘트, assignee, PR 제목은 이벤트 이후에 얼마든지 바뀝니다. 가변 상태를 payload 스냅샷으로 검사하는 모든 가드는 같은 박제 문제를 갖습니다.

✍️ 오늘의 요약
github.event 는 이벤트 순간의 webhook payload 박제이고, Re-run 은 그 스냅샷을 다시 재생하는 버튼이다. 그래서 라벨을 붙인 뒤 재실행하라는 안내는 구조적으로 실현 불가능한 절차였다. 가변 상태는 실행 시점에 조회하고, 되돌림을 잡으려면 unlabeled 를 트리거에 둔다.

안내한 절차대로 따라 해도 통과하지 못하는 가드는, 안전장치가 아니라 우회 충동을 만드는 장치다.
